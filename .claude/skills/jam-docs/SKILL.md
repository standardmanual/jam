# jam-docs — JAM! 문서 체계 작성·갱신 절차

CLAUDE.md에는 "어느 카테고리에 해당하는지" 판단 기준만 있다. 실제 **작성 규칙·파일명 규칙·필수 항목**은 이 문서에 있다.

## 카테고리 판정 먼저

| # | 카테고리 | 대상 | 위치 | 수정 방식 |
|---|---|---|---|---|
| ① | PRD | 기능·스펙·로직 정의 | `Service Plan/Specs/PRD/` | 기존 파일 직접 수정 |
| ② | 티켓 | 실행 계획·작업 이력 | `Service Plan/Tickets/` | 신규 파일 생성 |
| ③ | 컨텐츠 | 배지·아이템북·세계관·POI | `Service Plan/Specs/Content/` | 기존 파일 직접 수정 |
| ④ | 배지엔진 | 발급·드랍 판정 로직 | `Service Plan/Specs/BadgeEngine/BADGE_ENGINE_UNIFIED.md` | 기존 파일 직접 수정 |
| ⑤ | 서비스플랜 | 비전·장기 전략 | `Service Plan/Business/서비스플랜/` | 기존 파일 직접 수정 |

하나의 변경이 여러 카테고리에 걸치면 **각 카테고리 문서를 모두** 갱신한다.

## ② 티켓 (가장 자주 쓰는 절차)

### 파일명
`Service Plan/Tickets/YYYYMMDD_HHMM_[카테고리]_[제목].md`

- `HHMM`: **티켓 생성 시각(KST, 24시간)**. 기존 파일을 조회해 번호를 계산하지 않는다.
- `제목`: 한국어 또는 영어, 공백 대신 `-`
- 템플릿: `Service Plan/Tickets/_TEMPLATE.md`
- `id` 프론트매터도 파일명과 동일하게 `YYYYMMDD_HHMM`

> **2026-08-27 규칙 전환.** 구 규칙은 `NNN`(당일 최대 번호 +1)이었으나, 병렬 세션이 같은
> 번호를 동시에 선점해 **충돌 32건**과 재번호 커밋이 반복됐다. 기존 `NNN` 티켓은 소급
> 개명하지 않는다 — 번호가 브랜치명·커밋 메시지·코드 주석에 박혀 있어 참조가 끊긴다.

### 카테고리 8종

| 카테고리 | 범위 |
|---|---|
| Admin | 어드민 패널 기능·UI |
| Service | 배지엔진·드랍엔진·Strava 동기화 등 핵심 서비스 로직 |
| Feature | 사용자 대면 기능 단위 |
| Content | 배지·아이템·텍스트 컨텐츠 |
| BadgeEngine | 배지 엔진 전용 |
| Infra | DB 마이그레이션, 환경변수, 도메인, 배포 설정 |
| UI | UI/UX 개선 |
| API | API 라우트 변경·추가·삭제 |

> `/jam-work`의 작업 유형(ui·ds·bug·engine·db·api·content·copy·admin·infra·docs·research)과는 별개 축이다.
> 유형은 파이프라인 라우팅용, 카테고리는 문서 분류용 — 매핑표는 `.claude/skills/jam-work/SKILL.md` 참조.

### 언제 만드는가
1. **개선·기능 요청 접수 시** → `status: OPEN` 초안 생성. 뭉뚱그려진 요구사항은 카테고리·범위별로 분리.
2. **"기존 유지" 결정도 티켓으로 남긴다** — 검토 후 미채택한 경우도 의사결정 기록.
3. **작업 완료 시** → `status: CLOSED` + 완료 기록 작성.

### 접수 시 기존 티켓 먼저 검토 (필수)
구현 전에 반드시:
1. Ticket 폴더에서 유사·관련 티켓 확인
2. 파악할 것: 이미 완료된 작업인지(재구현 방지) / 미채택 대안과 이유(반복 검토 방지) / 잔여 이슈인지(이어서 처리)
3. 컨텍스트 확보 후 구현 시작 — **티켓은 PRD와 함께 코드보다 우선하는 정보 소스**

### CLOSED 시 필수 항목
- 구현 내용 요약
- 변경된 파일 목록
- 테스트 결과
- UX Writing 검증 (사용자 노출 텍스트가 있을 경우)
- 배포 정보 (날짜, 환경, 커밋 해시)
- 주요 의사결정 / 검토한 대안과 미채택 이유
- 잔여 이슈

### CLOSED 처리 권한
review 브랜치(`claude/jamwork-*`)에서는 `status: CLOSED` 커밋이 **pre-commit 훅으로 차단된다.**
CLOSED는 사용자 최종 승인 후 오케스트레이터가 staging에서만 처리한다.

## ① PRD

**대상 변경**: 신규 기능 페이지 추가 / `jam-web/src/app/api/` 라우트 추가·변경·삭제 / 기존 기능의 정책·플로우 변경

**절차**:
1. `Service Plan/Specs/PRD/` 하위 관련 문서 확인 (`01_PRD.md`, `02_DATA_MODEL.md`, `03_PHASES.md`, `04_PROJECT_SPEC.md`, 주제별 폴더 `PRD/{주제}/`)
2. 새 기능 영역이면 `PRD/{주제}/` 하위 폴더 신설 (예: `PRD/AdminUI/`). 파일명에 날짜·Phase 접두어를 붙이지 않고 폴더로 구분
3. **기존 파일 직접 수정** — PRD는 "현재 기준 최신 스펙"이 원칙
4. 문서 간 상호 링크를 경로 변경 시 함께 갱신

## ⑤ 서비스 플랜

**대상 변경**: 기능 레벨의 추가·변경·삭제 (①에 해당하는 수준). 사소한 버그 수정·경미한 UI 조정은 대상 아님.

**위치**: `Service Plan/Business/서비스플랜/`

**갱신 방식** — ①에 해당하는 수준의 변경이 발생한 작업에서 함께 갱신한다:
1. 폴더 내 단일 현행 파일 `02 JAM! 서비스 플랜.md`를 연다
2. 이번 변경사항을 반영
3. 🟢현재구현 / 🟡부분구현 / 🔵향후업그레이드 태그 체계 유지
4. **기존 파일을 직접 수정한다** (①③④와 동일 원칙)

> **새 버전 파일을 만들지 않는다.** `v{n}.{m}` 접미사를 붙인 사본 생성은 금지한다.
> 버전 이력은 git이 갖는다 — 과거 상태가 필요하면 `git log --follow`로 조회한다.
> (2026-08-27 규칙 전환: v3.0~v4.3 15개 사본이 누적돼 최신본 판별이 불가능해진 문제를 해소)

## 폐기된 규칙

더 이상 생성하지 않으며, 기존 파일은 `Service Plan/Archive/Operations/`에 읽기 전용으로 보관한다.
