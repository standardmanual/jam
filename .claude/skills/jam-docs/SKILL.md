# jam-docs — JAM! 문서 체계 작성·갱신 절차

CLAUDE.md에는 "어느 카테고리에 해당하는지" 판단 기준만 있다. 실제 **작성 규칙·파일명 규칙·필수 항목**은 이 문서에 있다.

## 카테고리 판정 먼저

카테고리 5종과 위치는 루트 `CLAUDE.md` 「문서 체계 개요」 표가 단일 원천이다. 폴더별 쓰기 방식(신규 생성만 하는
폴더와 덮어쓰는 폴더)·버전 규칙·경로 표기는 `docs/README.md`가 원천이다. 여기에는 카테고리별 작성 절차만 적는다.

## 문서 스키마: 모든 문서 공통

frontmatter·태그·검사 등급은 `docs/DOCUMENT_SCHEMA.md`가 원천이다. 커밋할 때 `.githooks/pre-commit`이
`scripts/doc-check.mjs`로 검사하고 위반이면 차단한다.

- 새 문서(티켓 제외)는 스키마 §3·§4대로 frontmatter를 붙이고 주제 태그(§6)를 단다. 티켓은 템플릿 frontmatter를 그대로 쓴다.
- 새 문서의 폴더는 `docs/README.md` 폴더 지도에서 고른다.
- 다른 문서가 가리키는 파일을 이동·삭제하면 가리키는 문서를 같은 커밋에서 고친다(훅이 막는다). 이력
  문서를 고치지 않을 때의 우회와 전체 현황 명령은 스키마 §10에 있다.

## ② 티켓 (가장 자주 쓰는 절차)

### 파일명
`docs/tickets/p{0-3}-{라벨}/YYYYMMDD_HHMM_[카테고리]_[제목].md` (형식과 카테고리 이름은 `.githooks/pre-commit`이 막는다)

- `HHMM`: **티켓 생성 시각(KST, 24시간)**. 기존 파일을 조회해 번호를 계산하지 않는다.
- `제목`: 한국어 또는 영어, 공백 대신 `-`
- 템플릿: `docs/tickets/_TEMPLATE.md`
- `id` 프론트매터도 파일명과 동일하게 `YYYYMMDD_HHMM`
- 옛 `NNN` 번호 티켓은 개명하지 않는다(브랜치명·커밋 메시지·코드 주석의 참조가 끊긴다).

### 카테고리 8종

| 카테고리 | 범위 |
|---|---|
| Admin | 어드민 패널 기능·UI |
| Service | 배지엔진·드랍엔진·Strava 동기화 등 핵심 서비스 로직 |
| Feature | 사용자 대면 기능 단위 |
| Content | 배지·아이템·텍스트 컨텐츠 |
| BadgeEngine | 배지 엔진 전용 |
| Infra | DB 마이그레이션, 환경변수, 도메인, 배포 설정 |
| UI | UI/UX 개선 |
| API | API 라우트 변경·추가·삭제 |

> `/jam-work`의 작업 유형(ui·ds·bug·engine·db·api·content·copy·admin·infra·docs·research)과는 별개 축이다.
> 유형은 파이프라인 라우팅용, 카테고리는 문서 분류용 — 매핑표는 `.claude/skills/jam-work/SKILL.md` 참조.

### 우선순위 (P0~P3)

폴더로 표시한다(위 파일명 경로의 `p{0-3}-{라벨}`).

| 폴더 | 기준 |
|---|---|
| `p0-urgent` | 장애·매출·보안에 직결 |
| `p1-high` | 핵심 서비스 로직(배지엔진·드랍엔진·인증·결제 등) |
| `p2-normal` | 일반 기능·UI |
| `p3-low` | 사소한 개선·문서 |

frontmatter `priority:`도 폴더와 같은 값(`P0`~`P3`)으로 채운다 — 폴더를 옮기지 않고도 grep으로 조회하기
위함이며, 폴더와 값이 어긋나면 안 된다.

**한번 배정한 폴더는 옮기지 않는다** — `status`가 CLOSED로 바뀌어도 그대로 둔다 ("폴더 =
수명주기" 원칙, CLAUDE.md 참고). 우선순위 판단이 틀렸다고 나중에 판명되면 frontmatter 값과
파일 위치를 함께 고쳐 옮긴다 (둘 중 하나만 고치지 않는다).

### 상태값

| 상태 | 뜻 |
|---|---|
| `OPEN` | 접수됐지만 아직 시작 전 |
| `IN_PROGRESS` | 구현·리뷰 진행 중 |
| `WAITING` | 구현은 끝났거나 준비됐지만 **사용자 승인·결정을 기다리는 중** (예: 혜린 기획 승인 대기, 시즌 제안 승인 대기) |
| `CLOSED` | 완료 (또는 폐기/대체 — 사유를 완료 기록에 남긴다) |

`WAITING` 티켓은 현황판(`.claude/skills/jam-work/references/dashboard-format.md`)의
"승인 대기" 절에 자동으로 표시된다.

### 초안(분류 대기) 티켓

무인 세션(예약 루틴)은 티켓 파일을 만들지 못한다(`.githooks/pre-commit`이 막는다). 초안 처리 방식은
`scheduled-jobs.md` 4-3이 원천이고, 티켓화는 다음 세션의 카리나가 위 정식 규칙으로 한다.

### 핵심 요약 · 완료 조건 칸

- **핵심 요약**: 요구사항·구현 계획·관련 파일을 한두 줄로 압축한 절. 카리나가 서브에이전트에게
  티켓 전체 대신 이 절만 전달할 때 쓴다 (팀 공통 규칙 2번).
- **완료 조건**: "무엇을 어떻게 확인하면 끝인지"를 검증 가능한 문장으로 적는다. 비어 있으면
  민지(판정 리뷰)가 판정하지 않고 돌려보낸다 (팀 공통 규칙 22번).
- 완료 조건이 두 담당(구현·머지 뒤 후속)에 걸치면 템플릿 안내대로 「구현 범위」·「후속 범위」로 나눈다.

두 칸 모두 `docs/tickets/_TEMPLATE.md`에 있다.

### 언제 만드는가
1. **개선·기능 요청 접수 시** → `status: OPEN` 초안 생성. 뭉뚱그려진 요구사항은 카테고리·범위별로 분리.
2. **"기존 유지" 결정도 티켓으로 남긴다** — 검토 후 미채택한 경우도 의사결정 기록.
3. **승인·결정 대기 상태가 되면** → `status: WAITING`으로 바꾼다.
4. **작업 완료 시** → `status: CLOSED` + 완료 기록 작성.

### 접수 시 기존 티켓 먼저 검토 (필수)
구현 전에 `docs/tickets/`에서 유사 티켓을 찾아 완료 여부·미채택 대안·잔여 이슈를 확인한다. **티켓은 PRD와
함께 코드보다 우선하는 정보 소스**다.

### CLOSED 처리
- 완료 기록은 `docs/tickets/_TEMPLATE.md` 「완료 기록」 절의 칸을 채운다.
- CLOSED는 사용자 최종 승인 뒤 오케스트레이터가 staging에서 처리한다(리뷰 브랜치에서는 훅이 막는다).

3. **기존 파일 직접 수정** — PRD는 "현재 기준 최신 스펙"이 원칙
4. 문서 간 상호 링크를 경로 변경 시 함께 갱신

**홈피드(홈 「투데이」) 기능 정의**: 정본은 `docs/service/prd/home-feed/PRD.md`다. 그 문서 frontmatter `code:`의

표(템플릿·레이아웃·노출 태그·목적지)는 생성 구간이라 손으로 고치지 않고 `node scripts/gen-home-feed-doc.mjs`로
다시 만든다. 동작이 바뀌지 않은 변경은 `JAM_SKIP_DOCLINT=1`로 우회하고 사유를 커밋 메시지에 남긴다.

## ⑤ 서비스 플랜

**대상 변경**: 기능 레벨의 추가·변경·삭제 (①에 해당하는 수준). 사소한 버그 수정·경미한 UI 조정은 대상 아님.

**위치**: `docs/plan/vision/` (코드와 함께 커밋한다)

**갱신 방식** — ①에 해당하는 수준의 변경이 발생한 작업에서 함께 갱신한다:
1. 폴더 내 단일 현행 파일 `02 JAM! 서비스 플랜.md`를 연다
2. 이번 변경사항을 반영
3. 🟢현재구현 / 🟡부분구현 / 🔵향후업그레이드 태그 체계 유지

> 버전 사본 금지는 `docs/README.md` 「버전 규칙」이고 훅이 막는다. 과거 상태는 `git log --follow`로 조회한다.

## ⑥ 서비스 운영 정책 대시보드 (`policiesData.ts`)

**대상 변경**: 서비스 운영 정책, 밸런스 수치(확률·비용·임계값·배율 등), 속도/어뷰징 판정 기준, 챕터/미션/포인트/보상 등 도메인 규칙 변경

**위치**: `jam-web/src/lib/admin/policyDashboard/policiesData.ts`

**갱신 원칙**:
1. 서비스 운영 정책 대시보드(`/admin/policy-dashboard`)는 장별 정책 카탈로그를 관리자에게 단일 관제로 제공한다.
2. 정책 수치나 비즈니스 규칙이 코드나 문서에서 변경되면, 대시보드 카탈로그(`policiesData.ts`)의 해당 항목(`value`, `description`, `userImpact`, `status` 등)도 반드시 같은 작업에서 함께 갱신한다.
3. 신규 정책이 도입되면 해당 챕터 배열에 새 `PolicyItem`을 추가하고 고유한 `id`를 부여한다.
