# jam-docs — JAM! 문서 체계 작성·갱신 절차

CLAUDE.md에는 "어느 카테고리에 해당하는지" 판단 기준만 있다. 실제 **작성 규칙·파일명 규칙·필수 항목**은 이 문서에 있다.

## 문서 스키마: 모든 문서 공통 (2026-09-19, 티켓 20260919_1223)

문서를 새로 만들거나 고칠 때 `docs/specs/DOCUMENT_SCHEMA.md`를 따른다. 커밋할 때
`.githooks/pre-commit`이 `scripts/doc-check.mjs`로 검사하고 위반이면 차단한다.

- **새 문서(티켓 제외)에는 frontmatter의 `type`과 `description`(한 줄, 100자 이내)을 붙인다.**
  type은 15개 중 하나이고 목록은 스키마 §3에 있다. 티켓은 경로로 type을 판정하므로 기존
  frontmatter를 그대로 쓴다.
- type별 필수 필드(예: `catalog`의 `tags`·`source_of_truth`)와 태그 어휘(스키마 §6.2, 공백 없이
  붙여 쓴다)는 스키마 §4·§6을 확인한다. 어휘 밖 태그는 커밋이 차단된다.
- `title`과 수정일 필드는 두지 않는다(첫 H1과 `git log`가 대신한다. H1이 없는 문서만 `title` 예외).
- 새 태그는 스키마 §6.2와 `scripts/doc-check.config.json`에 함께 추가한다. 개체·종목 태그는
  UX 가이드라인 §1.3 고정 용어에서 뽑는다.
- **링크는 존재하는 경로만 추가한다.** 다른 문서가 링크하는 파일을 이동·삭제하면 그 문서를 같은
  커밋에서 고친다. 옛 티켓처럼 이력 문서를 고치지 않을 것이면 `JAM_SKIP_DOCLINT=1 git commit ...`으로
  우회하고 사유를 커밋 메시지에 남긴다. 이동·삭제 뒤 티켓 본문의 백틱 경로 경고가 수백 건 나오는
  것은 정상이며 커밋은 진행된다.
- 전체 현황은 `node scripts/doc-check.mjs --all --summary`로 본다.
- `jam-doc/` 문서도 같은 저장소의 같은 훅·같은 설정으로 검사받는다(2026-09-20 재통합 전에 있던
  `jam-doc` 전용 훅·엔진 복사본은 없어졌다, 티켓 20260920_1412).

## ② 티켓 (가장 자주 쓰는 절차)

### 파일명
`docs/tickets/YYYYMMDD_HHMM_[카테고리]_[제목].md`

- `HHMM`: **티켓 생성 시각(KST, 24시간)**. 기존 파일을 조회해 번호를 계산하지 않는다.
- `제목`: 한국어 또는 영어, 공백 대신 `-`
- 템플릿: `docs/tickets/_TEMPLATE.md`
- `id` 프론트매터도 파일명과 동일하게 `YYYYMMDD_HHMM`

> **2026-08-27 규칙 전환.** 구 규칙은 `NNN`(당일 최대 번호 +1)이었으나, 병렬 세션이 같은
> 번호를 동시에 선점해 **충돌 32건**과 재번호 커밋이 반복됐다. 기존 `NNN` 티켓은 소급
> 개명하지 않는다 — 번호가 브랜치명·커밋 메시지·코드 주석에 박혀 있어 참조가 끊긴다.

### 우선순위 (P0~P3)

**2026-09-07 도입, 신규 티켓부터 적용한다.** 그 시점 기존 티켓 582개(OPEN 15·CLOSED 567)는
소급 이동하지 않는다 — 필요해지면 별도로 요청해서 진행한다.

폴더로 표시한다: `docs/tickets/p{0-3}-{라벨}/YYYYMMDD_HHMM_[카테고리]_[제목].md`.
**파일명 규칙은 폴더 안에서도 그대로**다 — pre-commit 검사는 파일명(basename)만 보므로
서브폴더에 넣어도 그대로 통과한다(2026-09-07 검증 완료).

| 폴더 | 기준 |
|---|---|
| `p0-urgent` | 장애·매출·보안에 직결 |
| `p1-high` | 핵심 서비스 로직(배지엔진·드랍엔진·인증·결제 등) |
| `p2-normal` | 일반 기능·UI |
| `p3-low` | 사소한 개선·문서 |

> 2026-09-18 폴더명을 영문 소문자로 바꾸면서 중복이던 `P2-일반`·`P2-보통`을 `p2-normal` 하나로 합쳤다.
> frontmatter `priority:` 값은 그대로 `P0`~`P3`이다.

frontmatter `priority:`도 폴더와 같은 값으로 채운다 — 폴더를 옮기지 않고도 grep으로 조회하기
위함이며, 폴더와 값이 어긋나면 안 된다.

**한번 배정한 폴더는 옮기지 않는다** — `status`가 CLOSED로 바뀌어도 그대로 둔다 ("폴더 =
수명주기" 원칙, CLAUDE.md 참고). 우선순위 판단이 틀렸다고 나중에 판명되면 frontmatter 값과
파일 위치를 함께 고쳐 옮긴다 (둘 중 하나만 고치지 않는다).

| 상태 | 뜻 |
|---|---|
| `OPEN` | 접수됐지만 아직 시작 전 |

### 초안(분류 대기) 티켓

카즈하(예약 세션)가 만드는 티켓 초안은 `priority`를 비우고 제목 앞에 `[분류 대기]`를 붙여
`docs/tickets/` **최상위**(P폴더 밖)에 둔다. 카리나가 우선순위를 확정하면 값을 채우고
해당 `p{0-3}-…` 폴더로 옮긴다.

### 핵심 요약 · 완료 조건 칸 (2026-09-18 추가)

- **핵심 요약**: 요구사항·구현 계획·관련 파일을 한두 줄로 압축한 절. 카리나가 서브에이전트에게
  티켓 전체 대신 이 절만 전달할 때 쓴다 (팀 공통 규칙 2번).
- **완료 조건**: "무엇을 어떻게 확인하면 끝인지"를 검증 가능한 문장으로 적는다. 비어 있으면
  민지(판정 리뷰)가 판정하지 않고 돌려보낸다 (팀 공통 규칙 22번).
- **완료 조건이 두 담당에 걸칠 때**: 한 티켓에 아현이 구현하는 일과 카리나가 머지 뒤에 하는 일이
  함께 있으면 완료 조건을 「구현 범위」와 「후속 범위(담당·시점)」로 나눠 적는다. 민지는 구현
  범위만 판정하고, 후속 범위는 담당과 시점이 적혀 있는 한 판정 대상에서 뺀다. 한 목록에 섞으면
  게이트마다 "이 조건이 이번 판정 대상인가"를 다시 해석해야 한다 (티켓 20260921_2303).

두 칸 모두 `docs/tickets/_TEMPLATE.md`에 있다.

### 언제 만드는가
1. **개선·기능 요청 접수 시** → `status: OPEN` 초안 생성. 뭉뚱그려진 요구사항은 카테고리·범위별로 분리.
2. **"기존 유지" 결정도 티켓으로 남긴다** — 검토 후 미채택한 경우도 의사결정 기록.
3. **승인·결정 대기 상태가 되면** → `status: WAITING`으로 바꾼다.
4. **작업 완료 시** → `status: CLOSED` + 완료 기록 작성.

### 접수 시 기존 티켓 먼저 검토 (필수)
구현 전에 반드시:
1. `docs/tickets/`에서 유사·관련 티켓 확인
2. 파악할 것: 이미 완료된 작업인지(재구현 방지) / 미채택 대안과 이유(반복 검토 방지) / 잔여 이슈인지(이어서 처리)
3. 컨텍스트 확보 후 구현 시작 — **티켓은 PRD와 함께 코드보다 우선하는 정보 소스**

### CLOSED 시 필수 항목
- 구현 내용 요약
- 변경된 파일 목록
- 테스트 결과
- UX Writing 검증 (사용자 노출 텍스트가 있을 경우)
- 배포 정보 (날짜, 환경, 커밋 해시)
- 주요 의사결정 / 검토한 대안과 미채택 이유
- 잔여 이슈

### CLOSED 처리 권한
review 브랜치(`claude/jamwork-*`)에서는 `status: CLOSED` 커밋이 **pre-commit 훅으로 차단된다.**
CLOSED는 사용자 최종 승인 후 오케스트레이터가 staging에서만 처리한다.
