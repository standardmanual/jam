# /jam-img — 배지 이미지 제작 파이프라인

## 핵심 원칙

1. **각 단계 사이의 "결과 확인" 지점은 오케스트레이터가 임의로 건너뛰지 않는다.** 자동화
   가능한 단계라도 사용자가 눈으로 보고 다음으로 넘어가라고 말할 때까지 대기한다.
2. **사이즈·투명배경 유무는 매 작업(단건/컬렉션/다건 모두)마다 반드시 먼저 질문한다.** 이전
   작업에서 확인한 값을 다음 작업에 임의로 재사용하지 않는다 — 아이템마다 용도가 다를 수 있다.
3. **프롬프트는 항상 그 배지의 이름·설명과 소속 트라이브 설명을 최대한 반영하는 것을 목표로
   한다.** 컨텐츠 브리프의 "생성해야 하는 표현" 칸이 채워져 있어도 이름·설명을 함께 참고해
   구체성을 더하고, 칸이 비어 있을 때만 이름·설명에 의존하는 것이 아니다.

```
0. 시작 전 확인 (대상·스코프·사이즈·투명배경) ──사용자 응답──▶
① 스타일 결정 (정의서 + Recraft 스타일 등록) ──Claude──▶ ② 결과 확인 ──사용자──▶
③ 샘플 이미지 생성 (Recraft API) ──Claude Code──▶ ④ 결과 확인 ──사용자──▶
⑤ 프롬프트 문서 작성 (단건/컬렉션/다건) ──Claude──▶ ⑥ 결과 확인 ──사용자──▶
⑦ 이미지 생성 + (필요 시) 배경 투명화 ──Claude Code(Recraft API)──▶
⑧ 피그마 반영 여부 분기 ──사용자 선택──┬─▶ ⑧-A 피그마에 추가해 편집
                                        └─▶ ⑧-B 피그마 없이 바로 사용
⑨ 결과 확인 ──사용자──▶ ⑩ DB 반영 ──Claude Code──▶ 완료
```

> **2026-09-13 갱신**: 2026-08-22에 폐지했던 Recraft API 자동 생성을 다시 도입한다. 배경
> 투명화도 사용자의 수동 후처리 대신 Recraft `removeBackground` API로 Claude Code가 직접
> 처리한다 (`remove-background.js`, 아래 ⑦ 참조). Gemini 수동 입력 방식은 더 이상 쓰지 않는다.
> 로고 합성은 여전히 필수 단계가 아니며, 필요할 때만(⑧ 분기) 스크립트 또는 피그마로 처리한다.
> 히스토리는 `Service Plan/Assets/IMAGE_PRODUCTION/00_워크플로우/워크플로우_확정.md` 3절 참조.

## 0. 시작 전 확인

1. **대상 트라이브/컬렉션/아이템** — `Service Plan/Assets/IMAGE_PRODUCTION/02_스타일그룹/
   {NN 트라이브명}/` 폴더와 그 안의 `컨텐츠_브리프/{컬렉션ID} {컬렉션이름}/{컬렉션ID}
   {컬렉션이름}.md`를 확인해 대상 아이템과 각 아이템의 "생성해야 하는 표현"을 파악한다 (칸이
   비어 있으면 ⑤단계에서 이름·설명을 근거로 직접 구상해 채운다).
2. **작업 스코프를 확정한다 — 단건 / 컬렉션 / 다건 중 하나.**
   - **단건**: 특정 아이템 1개만 (신규 등록 또는 기존 이미지 교체)
   - **컬렉션**: `item_books` 하나에 속한 아이템 전체
   - **다건**: 컬렉션 경계와 무관하게 사용자가 지정한 아이템 여러 개 (서로 다른 컬렉션에 걸칠
     수 있음)
   - 다건이 여러 실제 컬렉션에 걸치면, ⑤~⑩ 단계를 **컬렉션별로 나눠 반복**한다 (아이템은
     항상 자신이 속한 컬렉션 폴더에 배치 — 스크립트·폴더 구조 변경 없이 기존 규칙을 그대로
     따른다). 단건도 마찬가지로 그 아이템이 속한 컬렉션 폴더를 그대로 쓴다.
3. **사이즈와 투명배경 유무를 사용자에게 질문한다 (핵심 원칙 2).**
   - 사이즈: 정사각형 배지가 기본이므로 `1024x1024`를 기본안으로 제시하되, 확정은 사용자
     응답을 따른다. 다른 값을 요청받으면 Recraft가 지원하는 값인지는 ③ 샘플 생성 단계에서
     실제 호출로 검증한다 (API가 지원하지 않는 값이면 에러로 즉시 드러난다).
   - 투명배경: 필요하면 ⑦ 단계에서 `remove-background.js`를 자동 실행한다. 필요 없으면
     생성 결과를 그대로 쓴다.
4. **스타일그룹 정의서 완결 여부** — 트라이브 폴더의 `스타일그룹_정의서.md`가 팔레트·렌더링
   규칙·절대 금지 요소·텍스트 사용 여부·캐릭터화 규칙·톤까지 채워져 있는지 확인한다.
   - 비어 있거나 없으면 ①단계부터 시작한다.
   - 채워져 있으면(다른 컬렉션 작업 시 재사용) 스타일 등록(`recraft_style.json`) 존재 여부만
     확인하고 ③단계로 넘어간다 — 스타일은 트라이브 전체에서 동일해야 하므로 컬렉션·아이템마다
     새로 정의하거나 재등록하지 않는다.

## ① 스타일 결정 — Claude

정의서와 실제 Recraft 스타일(`style_id`)을 함께 확정하는 단계다.

1. `01_템플릿/정의서_작성_요청_프롬프트.md`의 재사용 템플릿을 사용자가 채워서 요청하면(또는
   레퍼런스 이미지 + 요구사항만 주면 이 템플릿 형식에 맞춰), 트라이브 폴더의
   `스타일그룹_정의서.md`를 `01_템플릿/스타일그룹_정의서_양식.md` 양식에 맞춰 작성한다.
   - 레퍼런스 이미지는 그림체·선 스타일·표현 기법·컬러톤·조형적 밸런스만 참고하고, 이미지 속
     구체적인 사물·캐릭터·문구는 참고하지 않는다.
   - 사용자가 준 요구사항이 레퍼런스 이미지 내용과 상충하면 요구사항을 우선한다.
   - 이 트라이브의 전체 아이템 수를 전제하는 표현을 쓰지 않는다 (컬렉션 1개만 대상으로 작업할
     수도 있으므로).
2. 정의서가 승인되면(② 이후) `레퍼런스_이미지/` 폴더(최대 5장)를 기준으로 Recraft 커스텀
   스타일을 등록한다 — 트라이브 1개당 1회만 실행하면 되며, 이미 `recraft_style.json`이 있으면
   재실행하지 않는다.
   ```bash
   node jam-web/scripts/recraft/register-style.js "<트라이브 폴더 절대경로>" <baseStyle> <model>
   ```
   결과가 트라이브 폴더의 `recraft_style.json`에 `style_id`로 저장된다.

## ② 결과 확인 — 사용자

작성된 정의서와(재등록한 경우) 새 `style_id`를 사용자가 검토한다. 팔레트·규칙이 의도와
다르면 요구사항을 조정해 ①을 다시 돈다. **승인 전에는 ③으로 넘어가지 않는다.**

## ③ 샘플 이미지 생성 — Claude Code

정의서·style_id를 실제 이미지로 확인해보는 단계. 아이템별 프롬프트 문서(⑤)를 전부 쓰기
전에, 대표 프롬프트 1개로 스타일·구도 문법이 의도대로 나오는지 먼저 검증한다.

1. 정의서의 팔레트·렌더링 규칙·절대 금지 요소·캐릭터화 규칙·톤을 반영한 대표 프롬프트(실제
   대상 아이템 중 하나, 또는 트라이브를 대표하는 가상의 장면)를 작성한다. 확정된 사이즈·
   투명배경 여부(0-3)를 그대로 적용한다.
2. 컬렉션의 `컨텐츠_브리프/{컬렉션ID} {컬렉션이름}_프롬프트/_샘플/` 폴더에
   `recraft_batch_config.json`을 만들고 실행한다 (형식은 ⑦과 동일, `items`에 1~2개만 담는다).
   ```bash
   node jam-web/scripts/recraft/generate-batch.js "<..._샘플 폴더 절대경로>"
   ```
3. 투명배경이 필요한 스코프라면 샘플에도 배경 제거를 적용해 최종 결과물과 동일한 조건으로
   확인한다.
   ```bash
   node jam-web/scripts/recraft/remove-background.js "<샘플 PNG 경로>"
   ```

## ④ 결과 확인 — 사용자

샘플 이미지를 실제로 렌더링해 보여주고(Artifact/SendUserFile) 스타일·구도·사이즈·투명배경
처리가 의도대로 나왔는지 확인받는다.
- 반려되면 원인에 따라 ①(정의서/스타일 자체 문제)이나 ③(프롬프트 표현 문제)로 되돌아간다.
- **승인 전에는 ⑤로 넘어가지 않는다** — 프롬프트 문법이 틀린 채로 전체 아이템 문서를 쓰면
  전량 재작업해야 한다.

## ⑤ 프롬프트 문서 작성 — Claude

트라이브의 `스타일그룹_정의서.md`와 대상 아이템의 `컨텐츠_브리프/{컬렉션ID} {컬렉션이름}/
{컬렉션ID} {컬렉션이름}.md`를 합쳐서, `01_템플릿/컨텐츠_브리프_프롬프트_양식.md` 구조에 맞춰
아이템별 프롬프트 문서를 작성한다. 단건·컬렉션·다건 모두 같은 양식을 쓰며, 처리할 아이템
개수만 다르다.

- **폴더를 이미지 결과 폴더와 분리한다.** `컨텐츠_브리프/` 안에 이미지·config 파일이 쌓이는
  `{컬렉션ID} {컬렉션이름}` 폴더와는 별도로 `{컬렉션ID} {컬렉션이름}_프롬프트` 폴더를 새로
  만들고, 프롬프트 문서는 전부 그 안에 둔다.
- **아이템별로 파일을 나눈다** (단건이면 파일 1개). 파일명은
  `{컬렉션ID}_{#}_{아이템이름}_프롬프트.md` (아이템 이름은 공백을 뺀 붙임표기 — 이미지
  파일명 규칙과 동일하게 맞춘다).
- 각 파일에는 두 항목을 반드시 포함한다:
  - **negative prompt**: 정의서의 "절대 금지 요소" 전체 + (텍스트_사용여부가 no면 텍스트·레터링
    관련 금지도 포함)
  - **생성 prompt**: 정의서의 팔레트·렌더링 규칙·캐릭터화 규칙·톤/다이나믹함을 문장으로 녹이고,
    그 아이템의 이름·설명(컨텐츠_브리프 표의 "생성해야 하는 표현" 포함, 비어 있으면 이름·설명
    으로 직접 구상)과 소속 트라이브 설명을 핵심 장면에 최대한 반영한다 (핵심 원칙 3). 정의서의
    "톤/다이나믹함"에 정해둔 문법(예: 중앙 오브젝트 + 상태 과장 묘사)이 있으면 모든 아이템
    파일에 동일하게 적용한다.
- 정의서의 "생성해야 하는 표현"을 스타일 규칙을 이유로 생략·변형하지 않는다 (정의서 대원칙).
- 이 문서들은 작업마다 새로 만드는 완성된 산출물이다 — 재사용 템플릿이 아니다.

## ⑥ 결과 확인 — 사용자

아이템별 negative/생성 prompt가 정의서·브리프·이름·설명을 정확히 반영했는지 확인받는다.
**승인 전에는 이미지 생성으로 넘어가지 않는다** — 프롬프트 자체가 최종 산출물에 가장 큰
영향을 주므로 여기서 틀리면 크레딧을 들여 다시 생성해야 한다.

## ⑦ 이미지 생성 + 배경 투명화 — Claude Code

1. ⑤에서 승인된 프롬프트 문서를 `recraft_batch_config.json`으로 변환해 같은 폴더에 둔다
   (0-3에서 확정한 사이즈 포함).
   ```json
   {
     "style_id": "...", "model": "recraftv3", "size": "1024x1024",
     "negative_prompt": "...", "no_text": true,
     "items": [{ "filename": "item-01-01-1.png", "prompt": "..." }, ...]
   }
   ```
2. 배치 생성 실행.
   ```bash
   node jam-web/scripts/recraft/generate-batch.js "<컬렉션 폴더 절대경로>"
   ```
3. 0-3에서 투명배경이 필요하다고 확인했으면, 생성된 파일 전체에 배경 제거를 실행한다 (사용자가
   수동으로 후처리하지 않는다 — Claude Code가 대신 처리).
   ```bash
   node jam-web/scripts/recraft/remove-background.js <생성된 PNG 경로들...>
   ```
   내부적으로 Recraft `POST /v1/images/removeBackground`를 호출해 알파 채널이 있는 PNG로
   원본을 덮어쓴다.

## ⑧ 피그마 반영 여부 — 사용자 선택 (분기)

로고 합성·프레임 정렬 등 추가 편집이 필요한지 사용자에게 확인한다.

### ⑧-A 피그마에 추가해 편집 (경우에 따라)

추가 편집이 필요하면 선택한다.
- 피그마 MCP(`figma` 커넥터)가 이 세션에 연결되어 있어야 자동 삽입이 가능하다 — 연결이
  안 되어 있으면 사용자에게 먼저 인증을 안내한다 (연결 전까지는 이 브랜치를 자동화할 수 없다).
- 연결되어 있으면 `figma-use` 스킬을 먼저 로드한 뒤 `use_figma`로 지정된 파일(또는 새 프레임)에
  ⑦에서 생성한 이미지를 노드로 삽입한다.
- 로고 합성처럼 고정 배치라 자동화가 더 간단한 경우, 피그마 대신 기존 스크립트로 대체할 수도
  있다 — `compose-logo.js`(하단 중앙 고정) 또는 `compose-logo-edge.py`(디자인 실루엣을 분석해
  우측 하단 바깥에 접선 각도로 배치). 무엇을 쓸지는 사용자와 그때그때 정한다.
- 사용자가 피그마에서 편집을 마치면 그 프레임을 최종 이미지로 export한다(PNG). 이 export 파일이
  ⑨의 확인 대상이자 ⑩ 등록 대상이 된다.

### ⑧-B 피그마 없이 바로 사용 (경우에 따라)

추가 편집이 필요 없으면 ⑦에서 생성(+배경 제거)된 이미지를 그대로 최종 파일로 쓴다.

## ⑨ 결과 확인 — 사용자

⑧-A의 피그마 export 파일 또는 ⑧-B의 생성 파일을, 사용자가 준비했다면 오케스트레이터에게
전달하고, 실제로 렌더링해 보여주거나(Artifact/SendUserFile) 육안 확인을 요청한다.

## ⑩ DB 반영 — Claude Code

```bash
node jam-web/scripts/recraft/register-badge-images.js "<컬렉션 폴더 절대경로>"
```

- `recraft_badge_mapping.json`(아이템별 파일명 → badge id 목록)을 읽어 Storage 업로드 +
  `badges.image_url` UPDATE.
- 다건 작업이 여러 실제 컬렉션에 걸쳤다면, 컬렉션별로 이 스크립트를 각각 실행한다.
- 재업로드 시에도 이 스크립트가 자동으로 `?v=<timestamp>` 캐시버스팅 쿼리스트링을 붙인다
  (Vercel Image Optimization 엣지 캐시가 예전 이미지를 서빙하는 문제 방지).
- 실행한 UPDATE문은 스크립트가 컬렉션 폴더에 `seed_{collection_id}_badge_images.sql`로 자동
  저장 — 이 파일과 이미지 파일들을 staging에 커밋+push한다 (레포 관례).
- 컬렉션 대표 이미지(`item_books.image_url`)를 함께 갱신해야 하면(보통 등록이 끝난 컬렉션은
  첫 번째 아이템 이미지를 대표 이미지로도 반영하는 것이 기본 규칙) 별도 UPDATE 후 SQL로 기록한다.

## 참고: 크레딧 사용 지점

Recraft API 호출은 전부 유료 크레딧을 쓴다. 순서상 크레딧을 쓰는 지점은 ①의 스타일 등록
(트라이브당 1회), ③의 샘플 생성(승인 전 최소 수량), ⑦의 배치 생성·배경 제거뿐이다 — ②④⑥⑨
결과 확인 게이트를 건너뛰지 않는 이유가 여기에 있다: 승인 전에 크레딧을 쓰는 재작업을 막기
위해서다. 잔액 확인은 다음으로 한다.
```bash
node jam-web/scripts/recraft/test-connection.js
```
