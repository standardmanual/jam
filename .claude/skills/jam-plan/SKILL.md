# /jam-plan — 기획 (혜린)

담당은 혜린(`jam-pm`). **먼저 묻고 나중에 쓴다.** 대부분의 아이디어는 1단계에서 끝난다.

## 0. 이 스킬을 쓰지 않는 경우

- 이미 무엇을 만들지 정해진 요청 → `/jam-work`
- 문서 정리·체계 개편 → `/jam-docs`
- 세계관 설정·컨텐츠 창작 → `/jam-story`

## 1단계 — 문답 (메인 대화)

`jam-pm`을 호출하기 전, 요청에서 읽은 가정을 목록으로 먼저 사용자에게 보여 주고 고쳐 받는다
(양식은 `.claude/skills/jam-work/SKILL.md` 0.0절 가정 목록 참조 — 옮겨 적지 않는다). 세계관
가정이 섞이면 윈터(`/jam-story`) 검수를 붙인다.

`jam-pm`을 호출해 **질문 5개 이내**를 한 번에 하나씩 받는다. 질문마다 선택지·추천·이유가
붙는다. 질문을 사용자에게 그대로 전달하고, 의도 확인이 필요한 지점에서는 답을 받기 전
다음 질문으로 넘어가지 않는다. 결과물은 **반쪽 요약**이다:

```
문제:       지금 무엇이 불편한가
사용자:     누구의 문제인가
성공 기준:  무엇이 달라지면 해결된 것인가
크기:       대략 몇 개의 티켓인가
첫 판단:    만들자 / 미루자 / 만들지 말자 + 이유
```

**여기서 멈춘다.** 사용자가 2단계를 원할 때만 진행한다.

## 조사 (선택) — 가벼운 모델로 위임

2단계 전에 사실 확인이 필요하면 Haiku로 조사만 돌린다. 반환은 요약뿐이다.

- 유사 티켓 (`docs/tickets/`) — 이미 한 일인가, 미채택 대안이 있었나
- 기존 기획·PRD (`docs/specs/prd/`)
- 코드·DB 구조 — 지금 구조로 되는가

## 2단계 — 기획서 (요청 시에만)

`jam-pm`이 `.claude/skills/jam-work/references/forms/brief-format.md` 형식으로 낸다(항목 목록의
원천은 그 파일 하나다 — 여기서는 옮겨 적지 않는다). 측정 가능한 성공 기준, 열린 질문, 가정
(확인됨/미확인)이 고정 항목이다. **문서 파일은 만들지 않는다** — 안만 받아서 오케스트레이터가
`/jam-docs` 규칙대로 반영한다.

## 리스크 점검 (JAM 전용)

경제 균형(드랍 확률·포인트 인플레·희귀도 가치) · 세계관 충돌 · 유저가 이미 학습한 규칙의 변경 ·
운영 부담 · 개인정보·외부 의존(Strava·지도 API) · 비용

- **경제 수치를 바꾸는 기획은 시뮬레이터 검증 결과를 리스크 항목에 실측값으로 넣는다.**
  시뮬레이션이 없으면 "미검증"이라고 명시한다. 추정치를 실측처럼 적지 않는다.
- 세계관에 닿으면 윈터(`/jam-story`) 검수를 붙인다.
- 운영 부담이 걸리면 카즈하(`jam-ops`)의 현재 수치를 먼저 확인한다.

## 기획서 승인 후

```
기획서 승인 → 기획 티켓 저장 → PRD 갱신 → 분해안대로 티켓 생성 → 순서대로 /jam-work
```

- 여러 담당이 얽힌 기획은 **상위 티켓 1개 + 하위 티켓** 구조로 만든다.
- 티켓마다 **완료 조건**을 반드시 채운다 — 비어 있으면 민지가 판정을 거부한다.
- 하위 티켓 표기(선행 티켓·세로 조각·체크포인트·크기 상한)는 `brief-format.md`의 「작업 분해
  표기」를 따른다.
- 사용자가 제안을 거절하면 **거절 이유**를 결정 기록에 남긴다.

## 월간 워크플로 회고

카즈하가 모은 수치(재시도 횟수·실패 사유·티켓 소요·비용·승인 대기·생략 규칙 발동·사용자가
불편을 말한 순간)를 입력으로 `jam-pm`이 개선안을 **3개 이내**로 낸다.
에이전트 정의·워크플로 변경은 사용자 승인 없이 반영하지 않는다.
