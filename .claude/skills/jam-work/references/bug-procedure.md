# `bug` 유형 절차 (아현)

> 신설 문서 (티켓 20260922_1521). `workType`이 `bug`인 티켓을 구현하기 전에 읽는다.
> 정의 파일(`jam-developer.md`)에는 이 문서를 읽으라는 한 줄만 있다 — 매 호출에 실리는
> 정의 크기를 늘리지 않기 위해서다.

## 재현 테스트 5단계 (Prove-It Pattern)

버그를 고치기 전에 먼저 그 버그를 증명한다.

1. 버그를 재현하는 테스트를 작성한다
2. 테스트를 실행해 **FAIL**을 확인한다(버그가 실제로 있다는 증거)
3. 최소한의 수정을 구현한다
4. 테스트를 실행해 **PASS**를 확인한다(수정이 됐다는 증거)
5. 전체 회귀 테스트를 실행한다(다른 곳을 깨뜨리지 않았다는 증거) — `scripts/verify.sh`

재현 테스트를 만들 수 없으면(예: 타이밍 의존·환경 의존이라 결정적으로 재현이 안 됨) 구현
요약의 `tests_added`에 사유를 적는다. 만들 수 없다고 수정을 건너뛰지는 않는다.

> 이식 출처: `test-driven-development` skill §The Prove-It Pattern.

## 디버깅 4단계

원본의 6단계(재현→국소화→축소→수정→방지→E2E검증) 중 "축소"는 재현 테스트를 최소 사례로
좁히는 것과 같은 일이라 2단계에 흡수하고, "E2E검증"은 위 5단계의 전체 회귀 실행과 같은
일이라 별도 단계로 두지 않는다.

1. **재현** — 실패를 안정적으로 재현한다. 바로 안 되면 로그·환경 정보를 모으고 최소
   조건에서 다시 시도한다. 재현이 끝내 안 되면 조건을 기록하고 관찰을 이어간다.
2. **국소화** — 어느 계층에서 실패하는지 좁힌다(UI·API·DB·빌드 설정·외부 서비스·테스트
   자체 중 하나). 최소 재현 사례로 좁히는 것도 이 단계에 포함한다. 회귀라면
   `git bisect`로 원인 커밋을 찾는다.
3. **수정** — 증상이 아니라 근본 원인을 고친다. "왜 이런 일이 일어나는가"를 실제 원인에
   닿을 때까지 반복해서 묻는다.
4. **재발 방지** — 위 재현 테스트 5단계가 재발 방지 테스트를 겸한다. 가드레일 문서에
   남길 만한 패턴을 발견하면 코드를 고치지 말고 구현 요약의 `doc_updates`에 제안으로
   적는다(범위 밖 개선은 손대지 않는다, Hard rule 7).

> 이식 출처: `debugging-and-error-recovery` skill §The Triage Checklist(6단계 → 4단계로 압축).
