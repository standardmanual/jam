> 티켓 20260918_0423에서 파일화. 민지가 게이트 리뷰 결과를 반환할 때 쓰는 형식.
>
> **길이 상한: 전체 40줄 이내.** 칸마다 1~3문장으로 쓴다. 코드·로그·diff 원문은 붙이지 않고 파일 경로와 줄 번호로 가리킨다. 메인 세션 컨텍스트에 보고가 그대로 쌓이기 때문이다(2026-09-21 컨텍스트 실측).

## 판정 값

| 판정 | 뜻 | 표시 |
| --- | --- | --- |
| 통과 | 스펙대로 동작, 회귀 없음 | ✅ |
| 조건부 통과 | 동작은 하나 우려 있음 | 🟡 |
| 실패 | 스펙 불일치·회귀·확신 없음 | 🔴 |

## 점검표 (매번 전부)

1. 기계 검사(push 성공 여부)
2. 스펙 일치
3. 회귀
4. 테스트 적절성
5. 범위 이탈
6. 디자인 판정 준수
7. Storybook
8. SQL 파일
9. 보안(권한·RLS. `api`·`db`·`admin` 유형별 하위 항목은 `jam-reviewer.md` 참조)
10. 오류 처리
11. 문서 반영 (`docs/`·`jam-doc/` 모두 diff에 포함된다 — 변경 내용으로 판단)

## 결과 형식

`verdict` · `checklist` · `fail_items`(항목/재현 방법/기대 동작/관련 파일) · `concerns` ·
`side_findings`(위험 줄이는 개선점 포함) · `korean_copy`(copy·ui·content) · `diff_lines`

`fail_items`는 그대로 아현의 재시도 입력이 된다.

## side_findings 표기 — 축 · 신호

각 항목은 `[축/신호] 내용 — 파일:줄` 형식으로 쓴다.

축(5개): 정확성 · 가독성 · 구조 · 보안 · 성능

신호(3개, 원본 agent-skills 심각도 4단계와의 대응):

| JAM 신호 | 원본 심각도 |
| --- | --- |
| 중단 | Critical |
| 주의 | Required |
| 참고 | Optional · Nit · FYI |

`[중단]` 항목은 이번 티켓 범위 밖이어도 `side_findings` 배열 맨 앞에 두어 즉시 보고한다.
`verdict` 값은 바꾸지 않는다 — 범위 밖 발견물이기 때문이다.

## 확인 사항

- 판정은 티켓의 **완료 조건** + `definition-of-done.md`(끝낼 기준) 두 층을 기준으로 한다.
  완료 조건이 비어 있으면 판정하지 않고 카리나에게 돌려보낸다.
- 읽는 순서: 완료 조건 → 테스트 diff → 구현 diff.
- 세계관·엔진 변경 티켓은 시뮬레이터 검증 결과(자동화 B2)를 근거로 확인한다.
