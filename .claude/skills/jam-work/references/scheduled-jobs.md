## 공통 원칙

### 무엇을 예약 실행하나 (안건 2·4-8)

- 예약 실행 대상은 **점검형(카즈하·하니)** 과 **형식이 고정된 반복 초안**(윤진의 홈피드 7일치 등)뿐이다.
- 되묻기가 핵심인 일(혜린·윈터·윤진의 기획·창작·시즌 제안)은 워크플로로 만들지 않고 세션에서
  `/jam-plan`·`/jam-story`로 대화하며 진행한다. 백그라운드 실행은 중간에 사용자에게 물을 수 없기
  때문이다.
- 단서(4-8): 형식이 고정되어 방향이 틀릴 여지가 적고, 승인이 어차피 사후에 이뤄지는 반복 초안은
  예약 실행해도 된다.
- 단서(4-12, 티켓 20260925_1414 신설·20260926_1207 개정·20260930_1519 축소, 사용자 명시 승인 2026-09-25·2026-09-26): 정기 산출물(주간 홈피드 초안·월간 「배지·미션
  제안 재료」 절)에서 신규 배지·미션·홈피드 카드의 **기획안**은 예약 실행해도 된다. 형식은 고정이다: 이름 · 설명 · 조건(또는 템플릿) · 트렌드·지표 근거 ·
  「세계관과 닿음/무관」과 사유. 등록은 하지 않는다.
  - **이미지는 만들지 않는다**(티켓 20260930_1519, 사용자 결정 2026-09-30·티켓 20260930_1451 결정 3·3-1): 주간 예약 실행은 이미지·등록 묶음·`--dry-run`을 만들지 않고,
    채원·윈터의 이미지용 호출과 루틴 본체의 `npm ci`도 하지 않는다. 이미지가 필요한 홈피드 카드는 리포트 표에 「이미지: 승인 뒤 세션에서 만든다」로 적는다. 이미지가 필요한지는
    `HOME_FEED_REGISTRATION_BUNDLE.md` §1.1 표(코드로 확인한 사실)가 정본이고, 필요 없는 카드는 「이미지 없음(사유)」로 적는다. 월간 「배지·미션 제안 재료」와 배지·미션도
    예약 실행의 이미지 대상이 아니며 월간은 「이미지 준비 대기」를 그대로 쓴다(「이미지: 승인 뒤 세션에서 만든다」는 주간 표기다).
    요일별 「전원 카드」는 매일 `large_thumbnail`이고 미션 소개 카드는 미션 대표 이미지(`missions.image_url`)를 재사용한다(정본 PRD §8, 2026-09-26 사용자 결정) — 새로 만드는 이미지가 아니라 지금 규칙을 그대로 둔다.
  - **승인 뒤 세션**: 이미지는 사용자가 편성안을 승인한 뒤 세션에서 만든다. 절차는 윤진 ⑧의 세션 실행(`.claude/skills/jam-story/references/marketer-assets.md`)을 그대로 쓰고 등록은 메인 세션이 한다. 새 절차를 만들지 않는다.
  - **서비스 롤 키는 여전히 예약 환경에 두지 않는다**(4-1). 그 키는 RLS를 우회하는 전체 DB 권한이라 무인 실행에 주지 않는다.
  - **하지 않는 것**: 등록 실행(`--dry-run` 없는 `register-*.mjs`)·`--undo`·프리셋 생성·수정·DB·스토리지 쓰기는 예약 실행에서 금지다. 등록은 컨펌 뒤 메인 세션이 한다.
    예외는 읽기 토큰으로 열린 두 경로의 POST뿐이다: 받은 기획함 제출(`POST /api/admin/ops-inbox`)과 루틴 시작 기록(`POST /api/admin/ops-inbox/routine-start`, 티켓 20261026_2032). 경로는 정확히 일치할 때만 열리고 서비스 롤 키는 여전히 예약 환경에 두지 않는다.
    이 두 POST를 보내는 허용 명령은 `scripts/ops-submit.mjs`(`bundle`·`start`) 하나뿐이다(티켓 20260930_1504). `curl`이나 직접 요청으로 보내지 않는다.
    시즌 캘린더·앰비언트 드랍 일정·경제 수치 제안은 그대로 세션 전용이다(4-9). 이 개정에 맞춘 클라우드 루틴 저장 프롬프트 교체는 사용자 승인 뒤 카리나가 한다(티켓 20260930_1519 후속 범위, 2026-10-06 09:11 KST 정기 실행 전). 교체 전에 발화하는 실행은 저장된 옛 프롬프트를 따른다.

| 롤백 | 하지 않음 | 기존 안전장치를 유지한다. 이상이 보이면 `#jam-alert`에 올리고 사용자 결정을 기다린다. 롤백은 사용자 승인 후 세션에서 한다 |

위 표는 배포 점검의 범위다. 같은 무인 경로에서 쓰는 **기획함 도구**는 두 스크립트만 허용 명령이다(티켓 20260930_1504, 본문은 「데이터 출처」).
`scripts/ops-read.mjs`는 허용 목록의 GET만 읽고, `scripts/ops-submit.mjs`는 읽기 토큰으로 열린 두 경로(제출·시작 기록)의 POST만 보낸다.
둘 다 `ADMIN_API_BASE_URL`이 `https://`이거나 `http://localhost`일 때만 실행하고, 토큰과 본문 전체는 출력하지 않는다.

스크립트는 두 명령을 쓴다.

- `node scripts/deploy-gate.mjs check` — 위 표의 git 점검 셋(비밀값·마이그레이션 되돌림·라우트 인증).
  종료 코드는 0 통과 · 1 차단 · 2 게이트 실행 오류이고, 0이 아니면 모두 배포하지 않는다.
- `node scripts/deploy-gate.mjs served` — 프로덕션 도메인이 지금 서빙하는 배포 id(응답 HTML의
  `?dpl=dpl_…`)를 출력한다. 종료 코드는 0 찾음 · 2 네트워크 오류·시간 초과 · 3 식별자 없음 ·
  4 `--wait-change` 시간 안에 바뀌지 않음이다.

**스크립트는 작업 트리에서 실행하지 않고 `origin/staging`에서 임시 파일로 꺼내 실행한다.**

```bash
git show origin/staging:scripts/deploy-gate.mjs > /tmp/deploy-gate.mjs && test -s /tmp/deploy-gate.mjs
```

클라우드 세션이 시작하는 브랜치에는 이 스크립트가 없을 수 있고, 확인 루틴은 `checkout`을 하지 않으며,
실행 루틴은 `git checkout --detach`로 분리된 HEAD를 남기지 않아야 하기 때문이다. 꺼내지 못했거나 파일이
비어 있으면 게이트를 실행하지 못한 것이므로 **통과로 보지 않는다**(빈 파일은 종료 코드 0으로 끝나므로
`test -s`가 필요하다). 이후 명령은 `node /tmp/deploy-gate.mjs …`로 쓴다. 이 방식은 배포하려는 staging
팁의 스크립트를 쓴다. `contract.json`의 기준선과 공개 라우트 선언도 그 팁에서 읽는다.

이 스크립트는 단일 파일이어야 하며(다른 스크립트를 불러오지 않는다) `check-contract.mjs`가 그것을 확인한다.

`served`는 `j-a-m.app`이 클라우드 환경의 네트워크 허용 목록에 없으면 종료 코드 2로 끝난다. 이때 배포는
막히지 않고 "확인 불가"로만 기록된다. 무인 루틴에서 이미 성공한 GA4 스크립트(`ga4-weekly-metrics.mjs`)도
같은 Node 전역 `fetch`를 쓰므로 fetch 자체는 나가는 환경이다. 도메인 허용은 사용자가 환경 설정에서 한다.
`served`는 쿠키를 저장하지 않아 자동 로그인 리다이렉트가 걸린 스테이징(`stage.j-a-m.app`)에서는
`redirect count exceeded`로 종료 코드 2가 난다. 무인 경로는 프로덕션에만 쓰므로 영향이 없다.

### 루틴 ① 확인 — 목요일 15:00 KST

1. `git fetch origin main staging` 후 `git log origin/main..origin/staging`로 대기 중인 커밋을 확인한다.

   메시지에 같이 적는다(사용자가 "이슈 있나" 판단할 근거).
3. 위 방식으로 게이트 스크립트를 꺼낸 뒤 배포 게이트와 프로덕션 현재 배포를 확인한다.
   - `node /tmp/deploy-gate.mjs check`: 출력의 첫 두 줄(`배포 게이트`·`신규 마이그레이션`)을

     코드가 2이면 `확인 불가(세션 네트워크 제약)`, 3이면 `확인 불가(식별자 없음)`로 적는다.

```
[오늘 밤 배포 확인] 오늘(YYYY-MM-DD) 23:59 KST에 프로덕션 배포 예정입니다.
staging 대기: N건
- <커밋 요약 3~5줄, 커밋 메시지 첫 줄만>

배포 게이트: <통과 / 차단(사유)>
신규 마이그레이션: 번호 N건(되돌림 SQL 있음/없음), seed M건
프로덕션 현재 배포: dpl_…
문제 없으면 이 글에 "승인"이라고 답장해 주세요. 답장이 없으면 오늘 밤 배포하지 않습니다.
```

- `프로덕션 현재 배포`는 이번 배포 뒤 문제가 생겼을 때 되돌릴 직전 배포다. 롤백은 사용자 승인 후
  세션에서 `/jam-ship` 4단계 「롤백 계획」의 절차로 한다.
- 게이트가 `차단`이면 승인 답장이 있어도 실행 루틴이 배포하지 않는다. 이때 마지막 줄을
  `게이트가 차단 상태라 승인해도 오늘 밤 배포하지 않습니다.`로 바꾼다.

### 배포 실행 (승인 + 스테이징 정상일 때만, `/jam-ship`의 「사전 확인」·「배포 전 점검표」 중 git만으로 되는 점검·「main 승격」·「배포 검증」을 무인으로 수행)

무인 경로의 범위는 위 「무인 경로에 적용하는 점검」 표가 정한다. 단계는 번호가 아니라 이름으로
가리킨다. `/jam-ship`의 단계 번호가 바뀌어도 이 절이 어긋나지 않게 하기 위해서다.

```bash
git fetch origin main staging
git log --oneline origin/main..origin/staging   # 승격될 커밋 재확인 (비었으면 중단)
git show origin/staging:scripts/deploy-gate.mjs > /tmp/deploy-gate.mjs && test -s /tmp/deploy-gate.mjs \
  && node /tmp/deploy-gate.mjs check            # 종료 코드가 0이 아니면(스크립트를 못 꺼낸 경우 포함) 여기서 중단, #jam-alert
git diff --quiet origin/main origin/staging -- jam-web    # 종료 코드 1이면 jam-web 변경이 있다(새 프로덕션 빌드가 생긴다)
node /tmp/deploy-gate.mjs served                # 배포 전 서빙 배포 id (아래 「배포 뒤 확인」에서 쓴다)
git checkout main                               # 로컬 main이 원격과 다른 이력이면 jam-ship 7절의 복구 안내를 따른다
git merge --ff-only origin/staging              # 실패 시 즉시 중단, #jam-alert
JAM_SHIP=1 git push origin main
git checkout staging
```

**배포 전 게이트.** `check`의 종료 코드가 0이 아니면 main을 건드리지 않고 `#jam-alert`에 출력의
`배포 게이트` 줄과 차단 항목을 올린다. 승인 답장이 있어도 같다. 종료 코드 1은 차단, 2는 게이트 실행
오류이고, 명령이 실행되지 않은 경우도 통과하지 못한 것으로 본다.

**배포 뒤 확인.** push 뒤에 아래 둘을 한다.

1. 헬스체크: `curl -o /dev/null -w '%{http_code}' https://j-a-m.app`을 push 후 최대 2분간 30초 간격으로
   재시도한다. 사이트가 응답하는지만 본다. 롤백 뒤 자동 할당이 꺼진 상태에서는 새 배포가 공개되지
   않아도 옛 배포가 200으로 응답하므로, 새 배포가 공개됐는지는 2번이 본다.
2. 서빙 배포 id: 배포 전에 jam-web 변경이 있었으면(`check` 출력의 `jam-web 변경`이 1개 이상이거나 위
   `git diff --quiet`의 종료 코드가 1이면)
   `node /tmp/deploy-gate.mjs served --wait-change <배포 전 id>`를 실행한다(30초 간격, 최대 6분).
   종료 코드별 행동은 아래 표와 같다.

| 종료 코드 | 뜻 | 기록·행동 |
| --- | --- | --- |
| 0 | id가 바뀜 — 새 배포가 공개됨 | 새 id를 기록한다 |
| 4 | 6분 안에 id가 바뀌지 않음 | `#jam-alert`에 "새 배포가 공개되지 않음: 빌드 지연·빌드 실패·롤백 상태 중 하나로 의심, 롤백은 하지 않음"을 올린다 |
| 2 | 응답을 받지 못함 | "확인 불가(세션 네트워크 제약)"로 기록한다 |
| 3 | 응답은 왔으나 식별자가 없음 | "확인 불가(식별자 없음)"로 기록한다 |

배포 전에 id를 읽지 못했으면(위 `served`가 0이 아니었으면) 2번은 하지 않고 "확인 불가"로 기록한다.
`jam-web 변경`이 0개이면 Vercel의 `ignoreCommand`가 빌드를 건너뛰므로(`jam-web/scripts/vercel-ignore.sh`
규칙 ②) 새 배포가 만들어지지 않는 것이 정상이다. 이때는 id가 그대로여도 이상이 아니므로 2번을 하지 않는다.
