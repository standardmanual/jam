2. `#jam-alert`에서 **오늘 날짜로 올라온** "[오늘 밤 배포 확인]" 메시지를 찾는다(루틴 ①이 몇
   시간 전에 올린 바로 그 글). 없으면 승인 대상이 없는 것이므로 승인 없음으로 간주한다.
3. 그 스레드의 답장을 확인해 승인 신호(위 "승인 신호" 행 기준)가 있는지 판단한다.
4. **승인 있음** → 스테이징을 다시 한번 확인하고(`curl stage.j-a-m.app`), 정상이면 아래
   "배포 실행"을 수행한다. 불안정하면 배포를 건너뛰고 사유를 기록한다.
5. **승인 없음(답장 없음·거절·메시지 자체를 못 찾음)** → main을 건드리지 않는다. "이번 주 배포
   보류"로 기록한다.
6. 이번 실행 결과(대기 커밋 수·확인 메시지 존재 여부·승인 여부와 근거·배포 실행 여부·Vercel
   검증 결과)를 `Service Plan/Reports/배포/YYYY-MM-DD.md`에 기록하고 `staging`에 커밋·push한다.

### 배포 실행 (승인 + 스테이징 정상일 때만, `/jam-ship`의 1·3·4단계를 무인으로 그대로 수행)

```bash
git fetch origin main staging
git log --oneline origin/main..origin/staging   # 승격될 커밋 재확인 (비었으면 중단)
git checkout main
git merge --ff-only origin/staging              # 실패 시 즉시 중단, #jam-alert
JAM_SHIP=1 git push origin main
git checkout staging
```

이어서 프로덕션 도메인이 새 배포로 반영됐는지 확인한다
(`curl -o /dev/null -w '%{http_code}' https://j-a-m.app`을 push 후 최대 2분간 30초 간격 재시도).
