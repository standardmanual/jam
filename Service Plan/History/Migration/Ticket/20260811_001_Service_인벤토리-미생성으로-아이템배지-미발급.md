# [Service] handle_new_user() 인벤토리 생성 누락 — 신규 유저 아이템 배지 미발급

## 배경 / 문제 정의
`kangwonc` 계정이 Strava 활동을 정상 동기화했고 액티비티 배지(러닝 배지 등)도 정상 발급됐는데, 아이템 배지(드랍 엔진)만 하나도 발급되지 않는다는 문의가 접수됨. `engine_decision_log`에 badge 엔진 로그는 남아 있는데 drop 엔진 로그는 전무했고, `user_drop_state`에도 이 유저 행이 없었음.

**근본 원인 조사 결과**: `inventory` 테이블에 이 유저 행 자체가 없었다.
- 신규 가입 시 `users` 행과 함께 `inventory` 행을 자동 생성하는 `handle_new_user()` 트리거가 있고, 레포 마이그레이션(`001_initial_schema_rerun.sql`)에는 `INSERT INTO public.inventory` 구문이 포함돼 있음.
- 하지만 **운영 DB에 실제로 걸려있던 함수 정의를 조회해보니 이 구문이 통째로 빠진 채 재정의**되어 있었음(레포 커밋 이력에 없는 변경 — 운영 DB에서 직접, 또는 추적 안 된 방식으로 함수가 재정의됨).
- `tryItemDrop()`([drop-engine/index.ts:497](../../../../jam-web/src/lib/drop-engine/index.ts))은 `inventory`가 없으면 `console.error`만 남기고 조용히 종료 — DB 로그(`engine_decision_log`)에는 아무것도 남기지 않아 어드민에서 감지가 불가능했음.

**영향 범위**: `users.created_at` 기준 조사 결과, 2026-08-04 이후 가입한 계정 중 3명이 인벤토리 없이 방치되어 있었음 — `9irrun`(2026-08-04), `kangwonc`(2026-08-09), `jeeni`(2026-08-10). 이들은 첫 동기화 시점부터 아이템 드랍이 전혀 발생하지 않고 있었음(`jeeni`는 아직 첫 동기화 자체를 안 해서 처리된 활동 없음).

## 상세 요구사항

### 서비스/코드베이스 관점
- 운영 DB `handle_new_user()` 함수에 인벤토리 생성 구문 복원
- 레포 마이그레이션 파일로 반영해 운영 DB·레포 정합성 복구
- 피해 3계정 `inventory` 행 백필
- 이미 처리된 활동 중 드랍이 누락된 건에 대해 정산 발급(아래 참고)

## 구현 계획
1. `handle_new_user()`를 `CREATE OR REPLACE FUNCTION`으로 재정의 — `INSERT INTO public.inventory (user_id) VALUES (NEW.id) ON CONFLICT (user_id) DO NOTHING;` 복원
2. `supabase/migrations/079_fix_handle_new_user_missing_inventory.sql` 신규 마이그레이션 파일 추가
3. `9irrun`, `kangwonc`, `jeeni` 3계정에 `inventory` 행 직접 insert (컬럼 기본값 `max_slots=50`, `used_slots=0` 그대로 사용)
4. 정산 발급: `strava_activities.normalized`(각 활동의 정규화 스냅샷)를 이용해 `sync.ts`의 `dropTargets` 선정 로직(첫 싱크=최신 1건, 이후 싱크=배치당 최신 3건, 어뷰징 속도 필터 적용)을 그대로 재현하는 1회성 스크립트(`scripts/settle-missed-item-drops.ts`, 실행 후 삭제)를 작성해 `tryItemDrop()`을 실제로 호출

### 주요 의사결정 / 핵심 메모
- **정산 시 실제 드랍 엔진 재호출 방식 채택**: 정산 시점에 "무엇이 나왔어야 했는가"를 역산하는 대신, 원래 싱크 배치 구조(첫 싱크=1건, 이후=최대 3건)를 그대로 재현해 `tryItemDrop()`을 실제로 호출하는 방식을 택함 — 드랍 결과가 확률적(rollRarityV2 등)이라 "정답"을 역산할 수 없고, 엔진의 실제 로직(세계관/아이템북 선택, pity, 온보딩 게이트 등)을 그대로 타는 것이 가장 정합적이라 판단.
- **정산 스크립트는 1회성으로 실행 후 삭제**: 하드코딩된 특정 유저 ID 대상 스크립트라 재사용성이 없어 레포에 남기지 않음(scripts/ 폴더의 기존 재사용 가능한 스크립트들과 성격이 다름).
- **운영 DB 함수가 레포와 어긋난 근본 원인은 특정하지 못함**: 언제/어떻게 `handle_new_user()`가 인벤토리 구문 없이 재정의됐는지는 `schema_migrations` 추적 기록이 4건뿐이라 규명 불가. 재발 방지를 위해 마이그레이션 파일로 명시 반영.

### 잔여 이슈
- 운영 DB 함수 정의가 레포 마이그레이션과 어긋나는 사례가 또 있을 수 있음 — 다른 트리거/함수도 전수 점검이 필요할 수 있으나 이번 티켓 범위 밖으로 남김
