# [Service] 스트라바 동기화 타이밍 ↔ 드랍엔진 판정 시간차로 인한 보상 스킵/미발급/홍수 점검

## 배경 / 문제 정의

신규 가입자 및 일반 가입자의 Strava 동기화가 실행되는 시점(서버가 활동을 처리하는 시각)과
실제 액티비티가 발생한 시각 사이에 시간차가 있을 때, 드랍엔진(및 배지엔진)이:
1. 보상을 건너뛰거나(skip)
2. 발급하지 않거나(미발급)
3. 배지 홍수(flood)가 일어나는

현상이 있는지 점검한다.

## 상세 요구사항

### 서비스/코드베이스 관점
1. `src/lib/strava/sync.ts`가 한 번의 동기화 호출에서 **여러 개의 미동기화 활동을 한꺼번에 처리**할 때(신규 가입자 첫 백필, 또는 실패 후 재시도로 여러 건 밀린 경우), 배지엔진/드랍엔진에 전달되는 처리 순서가 **실제 활동 발생 시각 순서와 일치하는지** 확인 — 순서가 뒤바뀌면 홍수 방지 캡(30일 윈도우 내 3개 제한)이 최신 활동이 아니라 처리 순서 기준으로 잘못 캡될 수 있음
2. 동기화가 지연되어 실제 활동 시각과 동기화 처리 시각 사이에 며칠~몇 주 간격이 벌어질 때, `daily_drop_date`(일일 드랍 카운터)나 30일 롤링 윈도우 계산이 "동기화 시각"과 "활동 시각" 중 어느 쪽 기준인지 코드로 확인 — 기준이 섞여 있으면 스킵/미발급/홍수 셋 다 가능
3. 첫 싱크 게이트(`initial_sync_done`)가 활동을 **동기화 처리 순서대로** true로 넘어가는지, 아니면 실제 활동 시각 기준으로 "첫 활동"을 판별하는지 확인 — 뒤바뀌면 원래 Common만 나와야 할 첫 싱크에서 순서상 뒤늦게 처리된 오래된 고가치 활동이 Rare+로 새는 경우가 있는지
4. 20260810_002에서 미실시로 남은 "실제 Strava 신규 연동 시나리오 재현 테스트"를 가능한 범위에서 코드 추적으로 대체 검증

## 완료 기록 *(작업 완료 후 작성)*

### 점검 결과 — 조사 항목별

**1. 처리 순서 vs 활동 시각 순서 (버그 발견 → 수정 완료)**

`jam-web/src/lib/strava/sync.ts`의 `processFetchedActivities()`에서 아이템 드랍 대상
(`dropTargets`)을 `start_date` 기준 **내림차순(최신 우선)** 으로 골라낸 뒤, 그 순서
그대로 `tryItemDrop()`을 호출하고 있었다.

`tryItemDrop()`(`jam-web/src/lib/drop-engine/index.ts`)은 호출마다 `user_drop_state`를
DB에서 새로 읽고(`getDropState`), 처리 후 다시 저장한다(`saveDropState`). 이때
`state.last_activity_at`, `state.daily_drop_date`, `state.last_drop_faction_id`,
`state.last_drop_book_id` 등은 **가장 마지막에 처리된 호출의 값**으로 최종 저장된다.

배치가 여러 건(신규 가입자 백필 다건, 또는 재시도로 밀린 여러 건)일 때 dropTargets가
내림차순이었기 때문에, 루프의 마지막 반복은 배치 중 **가장 오래된** 활동이었다.
결과적으로 싱크 1회가 끝난 뒤 DB에 저장되는 "마지막 활동 시각/드랍 상태"가 실제
사용자의 진짜 최신 활동이 아니라 그 싱크 배치 안에서 가장 오래된 활동 기준으로
뒤바뀌어 있었다.

**실질적 영향:**
- 다음 싱크에서 `isComebackActivity()`가 실제보다 더 오래 쉰 것처럼 계산되어(진짜
  최근 활동 시각 대신 더 예전 시각을 기준으로 gap을 계산) 복귀 보너스(레어리티 상향)가
  부정확하게 발동될 수 있었음 — 배지/아이템 "홍수"에 해당하는 방향의 오류.
- `daily_drop_date`/`daily_drop_count`가 최신 활동일이 아니라 배치 내 최고령 활동일
  기준으로 저장돼, 실제로는 소진됐어야 할 일일 하향(daily_downgrade) 누적치가 다음
  싱크에서 조용히 리셋되는 경우가 있었음.
- `last_drop_faction_id`/`last_drop_book_id`(모멘텀 가중치 기준)도 실제 마지막 드랍이
  아닌 배치 내 최고령 드랍 기준으로 저장되어 다음 드랍의 세계관 선택이 다소 어긋날
  수 있었음.

일반 싱크(웹훅 기반, 1건씩 처리)에서는 배치 크기가 1이라 드러나지 않고,
**백필/재시도로 여러 건이 한 번에 밀렸을 때만** 나타나는 문제였다.

→ `dropTargets` 선정(최신 N건 고르기)은 그대로 유지하되, `tryItemDrop()` 호출
**순서**만 오름차순(오래된 → 최신)으로 뒤집어 최종 저장 상태가 항상 진짜 최신
활동을 반영하도록 수정.

**2. `daily_drop_date`/30일 윈도우 — "동기화 시각" vs "활동 시각" 기준**

`drop-engine/index.ts`의 `daily_drop_date` 리셋은 `activityStartDate.slice(0, 10)`
(활동의 로컬 시작일)을 기준으로 하며, 동기화 실행 시각과는 무관하다 — 코드 레벨로
확인 결과 기준 시각이 섞여 있지 않음. (단, 위 1번 순서 버그로 인해 "어느 활동의"
날짜가 최종 저장되는지는 뒤틀려 있었음 — 이번 수정으로 해소됨)

`badge-engine/index.ts`에는 더 이상 30일 롤링 윈도우 홍수 방지 캡이 없음 — 과거
온보딩 첫 싱크에서 common 배지 여러 개가 캡을 자기들끼리 소진해 정당한 후속 발급을
막는 문제로 이미 제거된 상태(코드 주석 656~663행). 성과 배지는 명시적 수치 조건으로만
검증되고, 아이템 드랍은 `drop-engine`의 확률·섀도우밴·일일 하향으로 별도 방어한다.
BADGE_ENGINE_UNIFIED.md §2.6에 남은 "30일 윈도우 캡" 서술은 이미 지난 티켓들에서
폐기된 정책이며 이번 조사 범위 밖(문서 정합성은 별도 이슈로 취급).

**3. 첫 싱크 게이트(`initial_sync_done`) 순서**

`syncStravaActivities()`에서 `isFirstSync`이면 `rawActivities`를 배지/드랍 엔진에
넘기기 전에 이미 **최신 활동 1건**으로 제한한다(`start_date` 내림차순 정렬 후
`slice(0, 1)`, sync.ts 399~406행). 드랍엔진도 동일하게 첫 싱크는 1건만 처리
(`isFirstSync ? 1 : MAX_DROP_ACTIVITIES_PER_SYNC`). 첫 싱크에서 처리 순서상 오래된
고가치 활동이 뒤늦게 반영돼 Rare+가 새는 경로는 없음 — "최신 1건만" 필터가 순서
문제 이전에 이미 적용됨.

**4. 20260810_002 "실제 Strava 신규 연동 시나리오 재현 테스트" 대체 검증**

실제 Strava 계정 재현 테스트는 이번에도 인프라 제약상 미실시. 대신 코드 추적으로
`syncStravaActivities()`의 동시 싱크 잠금(4-1) → 실패 시 롤백(catch 블록) 경로를
재확인 — 20260810_002에서 수정된 로직은 그대로 유지돼 있고 이번 조사에서 별도 결함은
발견되지 않음.
