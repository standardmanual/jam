# [Infra] 로컬 개발서버 전용 구글로그인 우회(테스트 계정) 도입

## 배경 / 문제 정의

JAM!은 구글 로그인이 필수라, 오케스트레이터(Claude)가 실제 화면을 스크린샷으로 검토(배포 전
로컬 검증, 배포 후 확인 등)할 방법이 없었다. 사용자가 명확히 요구한 방향:

> "실제 서버에 최종 적용하기 전에 구글로그인 없이 가상의 계정을 만들어서 실서비스에 적용된 것을
> 확인할 수 있는 가짜 계정 DB 값을 부여해서 거기서 확인하고 배포할 수 있는 방법 — 로컬서버를
> 사용한다거나."

즉: **프로덕션/프리뷰 배포에는 절대 영향 주지 않고, 로컬 개발서버(`next dev`)에서만** 고정된
가짜 테스트 계정으로 구글 로그인 없이 들어갈 수 있게 한다.

## 기존 티켓 검토 (레인저 사전 검토)

관련 기존 티켓 없음 (신규 인프라 영역). Supabase 프로젝트는 `jam-prod`(free 플랜, 브랜칭 미지원)
단일 프로젝트이며 로컬 개발도 이 DB를 그대로 씀 — 별도 로컬 DB는 없음. 따라서 "가짜 계정"은
같은 DB 안에 고정 UUID로 격리된 한 명의 유저 row로 존재하게 된다 (다른 유저 데이터에는 영향 없음,
RLS/user_id 스코프로 격리됨).

## 상세 요구사항

### 서비스/코드베이스 관점 — 반드시 지킬 것 (보안 핵심)

1. **`process.env.NODE_ENV !== 'development'`이면 무조건 404를 반환한다.** Vercel은 프리뷰든
   프로덕션이든 빌드 시 `NODE_ENV=production`으로 고정되므로, 이 체크 하나로 배포된 환경
   (프리뷰 포함)에서는 이 라우트 자체가 절대 동작하지 않는다. **이게 이번 작업의 유일하게 진짜
   중요한 요구사항** — 다른 어떤 요구사항보다 우선한다.
2. `jam-web/src/app/api/dev-login/route.ts` 신규 — 고정된 테스트 유저(아래 4번)로 세션을 발급하고
   `/`로 리다이렉트한다. Supabase service_role의 `auth.admin.generateLink({ type: 'magiclink', email })`
   + `verifyOtp`(또는 동등한 서버사이드 세션 발급 방식)로 실제 OAuth 없이 세션 쿠키를 만든다 —
   기존 `src/app/auth/callback/route.ts`의 쿠키 설정 방식을 최대한 재사용.
3. 로그인 페이지(`src/app/(auth)/login/page.tsx`)에 `process.env.NODE_ENV === 'development'`일
   때만 보이는 "테스트 로그인(개발 전용)" 버튼을 추가해 위 라우트로 이동시킨다. 구글 로그인 버튼
   로직·문구는 손대지 않는다.
4. 고정 테스트 유저 시딩 SQL 파일 작성(`jam-web/supabase/seed_dev_test_user.sql`) — **작성만
   하고 직접 실행하지 않는다** (기존 규칙대로 오케스트레이터가 사용자 승인 후 실행). 내용:
   - 고정 UUID(예: `00000000-0000-0000-0000-000000000dev`), 이메일 `dev-tester@jam.local`
   - 배지 상세화면 등을 실제처럼 검토할 수 있도록 액티비티 배지 몇 개, POI 배지 이력 몇 건,
     인벤토리 아이템 몇 개 정도의 최소 시드 데이터 포함 (과하게 많이 만들 필요 없음 — 화면
     검토용으로 각 카테고리 1~3건 수준)
   - `ON CONFLICT DO NOTHING` 등으로 여러 번 실행해도 안전하게(idempotent) 작성

### UI/UX 관점
- "테스트 로그인" 버튼은 로컬 개발 환경에서만 보이므로 UX 라이팅 가이드라인 대상 아님(사용자에게
  노출 안 됨).

## 구현 계획
`jam-developer`가 위 3개 코드 변경 + 1개 시드 SQL 파일 작성. review 브랜치까지 push.
conservative-reviewer는 **1번 요구사항(NODE_ENV 게이트)이 실제로 프리뷰/프로덕션 빌드에서
막히는지를 최우선·최고 강도로 검증**한다 — 이 부분이 뚫리면 인증 우회 취약점이 실서비스에
생기므로, 애매하면 무조건 FAIL.
