# [Service] GPS 조작 감지 임계값 오탐(false positive) 및 최소 경과시간 가드 부재

## 배경 / 문제 정의

사용자(sihyunrr@gmail.com, POI "산김영준국어논술전문학원 반포 직영학원"에서 본인이 드랍한
"후회 없는 미소" 배지 픽업 시도)가 도보 이동 중 드랍메뉴를 열어 확인만 했는데
"이 POI에서 일시적으로 이용이 제한됐어요" 오류로 픽업이 막혔다고 제보.

조사 결과 `poi_blocks`에 2026-08-12 21:32 KST 발생한 `gps_spoof_detected (속도 43km/h)`
기록 확인. 3시간 차단 정책(`poi_block_hours`)으로 조회 시점(익일 09:59 KST)엔 이미 만료됐으나,
동시에 적용된 `user_shadow_bans`(soft, `expires_at: null`)는 영구 잔존 — legendary/mythic
등급 드랍률이 계속 0으로 유지됨.

같은 계정의 `abusing_logs` 이력을 보면 2026-07-25에 **거의 동일한 좌표**(소수점 6자리까지 일치)
에서 943km/h · 906km/h · 669km/h · 383km/h로 판정된 사례가 반복 발견됨 — 물리적으로 불가능한
값으로, 실제 이동이 아니라 판정 로직 자체의 구조적 오탐으로 판단됨.

### 원인 분석

1. **최소 경과시간 가드 부재**: [gps-detector.ts](../../../../jam-web/src/lib/abusing/gps-detector.ts)의
   `checkAndUpdateLocation()`은 최소 이동거리 가드(`MIN_DISTANCE_KM = 0.15km`, 2026-07-25
   [007번 티켓](20260725_007_Admin_GPS-조작-감지-오탐false-positive으로-실내-픽업-드랍이.md)에서 추가)만
   있고 최소 경과시간 가드가 없음. 앱 재실행 시 GPS 재수신 과정에서 좌표가 150m 이상
   튀는 경우(실내·고층 밀집 지역에서 흔함) + 두 요청 사이 시간이 짧으면 `거리/시간` 계산상
   비현실적인 속도가 산출됨.
2. **정책값이 코드 기본값과 크게 괴리**: `policy.ts`의 `DEFAULT_POLICY.gps_max_speed_kmh = 300`
   (2026-07-25 오탐 수정 시 설계된 값)인데, 실제 DB `abusing_policy` 행은
   `gps_max_speed_kmh = 30`, `poi_block_hours = 3` (updated_at 2026-07-10, 007/008번 오탐
   수정 이전 시점) — 10배 낮은 임계값이 그대로 운영 중이라 007/008 수정의 오탐 방지 효과가
   사실상 무력화됨.
3. **소프트밴 영구 잔존**: `applyBan()`이 `expiresAt` 없이 호출되어(`shadow-ban.ts` 호출부인
   `drops/[dropId]/pickup/route.ts`) 오탐이어도 소프트밴이 자동 해제 없이 영구 유지됨. 관리자가
   수동으로 `/admin/abusing`에서 해제해야만 풀림.

## 상세 요구사항

### 서비스/코드베이스 관점
- [gps-detector.ts](../../../../jam-web/src/lib/abusing/gps-detector.ts)에 최소 경과시간 가드 추가

  (`300`, `72`) 또는 사용자와 합의된 값으로 정정 — 어드민 화면에서 수동 변경할지, 마이그레이션으로
  되돌릴지 결정 필요
- 소프트밴에 만료시간(`expiresAt`) 부여 여부 검토 (현재는 무기한)

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
원인 분석 3가지 모두 반영.

1. **최소 경과시간 가드 추가**: `gps-detector.ts`의 `checkAndUpdateLocation()`에
   `MIN_ELAPSED_SECONDS = 5` 가드 추가. 직전 위치 기록과 현재 요청 사이 경과시간이
   5초 미만이면 최소 이동거리 가드(`MIN_DISTANCE_KM`)를 통과하는 거리라도 속도/일일
   누적거리 판정을 건너뛴다 — GPS 재수신 시 좌표가 튀는 상황(앱 재실행, 실내·고층
   밀집 지역)에서 "거리/시간"이 비현실적인 속도로 계산되는 구조적 오탐을 방지.
2. **abusing_policy DB 값 정정**: `081_fix_abusing_policy_gps_thresholds.sql` 마이그레이션
   작성 (실행은 오케스트레이터가 사용자 승인 하에 별도 진행). `gps_max_speed_kmh`
   30→300, `poi_block_hours` 3→72로 되돌림 — `010_abusing_policy.sql`의 원래 DEFAULT
   값과 동일.
3. **소프트밴 만료시간 부여**: `drops/[dropId]/pickup/route.ts`의 `applyBan()` 호출에
   `policy.poi_block_hours` 기준 만료시간(`banExpiresAt`) 추가. 기존엔 `expiresAt` 없이
   호출돼 오탐이어도 소프트밴이 무기한 유지되고 관리자가 수동 해제해야만 풀렸음.
   POI 블록(`blockPoiForUser`)과 동일한 기간으로 맞춰 일관성 확보.

### 주요 의사결정 / 핵심 메모
- `MIN_ELAPSED_SECONDS` 값은 5초로 설정. 너무 짧으면(1~2초) GPS 재수신 튐을 충분히
  걸러내지 못하고, 너무 길면(수십 초) 실제 빠른 텔레포트형 어뷰징을 놓칠 위험이 있어
  절충값으로 선택. 구체적 튜닝값은 007/008 티켓 사례(짧은 시간 간격 + 큰 좌표 튐)를
  기준으로 판단.
- 소프트밴 만료시간은 POI 블록과 동일하게 `policy.poi_block_hours`로 통일 — 별도
  파라미터를 신설하지 않고 기존 정책값을 재사용해 범위 확장을 최소화.
- abusing_policy DB 값 정정은 마이그레이션 파일 작성까지만 수행 (CLAUDE.md 규칙상
  jam-developer에게 DB 실행 권한 위임 안 함). 실행은 오케스트레이터가 사용자 승인 후 진행.
