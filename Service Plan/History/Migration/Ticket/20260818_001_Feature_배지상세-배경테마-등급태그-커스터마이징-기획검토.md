# [Feature] 배지 상세화면 배경 테마·등급 태그 커스터마이징 기획 검토

## 배경 / 문제 정의
액티비티·아이템·POI 배지 상세화면(`/badges/[id]`)을 개편하려는 방향성 제안이 있었음. 코드 구현
전 단계로, 방향이 현재 코드베이스·데이터 모델·MODULAR 디자인 시스템과 어떻게 맞물리는지 조사하고
의견을 정리하는 **research 유형** 작업 (코드 변경 없음).

## 요청 원문 (사용자 제안)
1. 배지 생성 시 어드민에서 여러 요소를 설정하고 배지별로 다르게 적용
   1. 배경색/배경 쉐이더 — TopNav+Footer 전체를 하나의 배경으로 통합 적용
   2. 등급 태그 선택 — MODULAR에 가이드된 태그 쉐입 타입 중 하나를 선정
   3. 배경색/쉐이더는 상세화면뿐 아니라 추후 개발할 획득 알림 중앙 모달에도 적용 예정
   4. 컬러값 입력 또는 배경 쉐이더 선택 어드민 기능 개발
   5. 다양한 쉐이더 코드 개발 포함
   6. 컬러값 기본값 = 등록된 배지 이미지에서 자동 추출한 평균 컬러값
2. 어드민의 세계관/컬렉션(아이템북) PRD에서 하위 컨텐츠 일괄 적용 옵션 노출
3. 쉐이더는 개발로 계속 추가 가능해야 함 (어드민 아님)

## 조사 결과

### 1. TopNav+Footer 통합 배경 — 구조적 재검토 필요 (가장 큰 리스크)
- `Footer`(`jam-web/src/components/ui/Footer.tsx`)는 배지 상세 페이지 전용이 아니라
  `(main)/layout.tsx`에서 **`(main)` 라우트 그룹 전체(미션·프로필·인벤토리 등 전 화면)에 공통으로
  렌더링**된다. 현재 홈(`/`)만 `pathname` 체크로 제외하는 방식.
- 반면 `TopNav`는 각 페이지(`page.tsx`)가 개별적으로 import해서 쓰고, 이미
  `headerStyle` prop으로 커스텀 배경 주입 사례가 있음(`missions/[id]/MissionDetailClient.tsx:133`).
- 결론: **TopNav는 페이지별 배경 주입이 이미 쉬움(재사용 가능한 패턴 존재)**. 하지만 **Footer를
  배지별로 다르게 칠하려면 전역 레이아웃 구조를 건드려야 함** — Footer 렌더링을 레이아웃에서
  각 페이지로 내리거나, 레이아웃이 현재 경로별 테마값을 받아 조건 렌더링하도록 바꿔야 함.
  이 변경은 배지 상세 화면 밖의 **모든 (main) 페이지에 회귀 리스크**를 만든다.
- **제안**: 1차 스코프는 TopNav+본문 영역까지만 배경 적용하고, Footer는 배지 페이지에서만
  로컬로 별도 렌더링(레이아웃의 공용 Footer를 배지 상세에서 숨기고 페이지 자체 Footer로 교체)하는
  쪽이 전역 레이아웃 변경보다 안전함. 상세 설계는 구현 단계(`ui` 유형 티켓)에서 확정.

### 2. "등급 태그 쉐입 선택" — MODULAR 설계 원칙과 정면 충돌
- MODULAR에는 두 개의 다른 컴포넌트가 있음:
  - `RarityBadge` — rarity(common/rare/legend/mythic) 전용, **"Fixed 4-color mapping... never
    re-map these, users have learned the color language"**라고 명시적으로 문서화됨(고정 pill 모양).
  - `ShapeTag` — 카테고리 칩/썸네일용, 7 shape × 8 color를 index로 cycle. 등급과 무관.
- 사용자 제안대로 "등급 태그"에 ShapeTag의 쉐입을 배지별로 선택 가능하게 하면, **등급을 색+모양으로
  즉시 인지하던 학습된 패턴이 깨짐** — 신화 등급이 배지마다 삼각형이었다가 육각형이었다가 하면
  "이 배지가 몇 등급인지"를 색으로만 겨우 구분해야 함. 이는 등급 태그의 원래 목적(즉각적 등급 인지)과
  상충함.
- **의견**: 등급(rarity)과 "배지별 개성 있는 비주얼"은 분리해서 다뤄야 함. 등급 태그(RarityBadge)는
  현재처럼 고정 유지하고, 쉐입 선택은 배경 테마 쪽(예: 카드 프레임 모양, 챕터/세계관 아이덴티티
  요소)으로 용도를 재정의하는 게 나을 가능성이 큼. 정확히 어느 요소에 쉐입을 적용하고 싶은 것인지
  (등급 표시 자체 vs 배지 개성 표현) 확인 필요.

### 3. 평균 컬러 자동 추출 — 새 의존성 + 파이프라인 필요
- `package.json`에 `sharp`/`canvas`/`color-thief`류 이미지 처리 라이브러리 없음. 신규 추가 필요.
- 어드민 PRD(`ADMIN_PRD.md:288`)에 명시: **"이미지 업로드 — 배지 이미지는 외부 URL 입력. Supabase
  Storage 업로드는 미포함"**. 즉 배지 이미지가 외부 URL을 가리키는 구조라, 평균 컬러 추출을 어드민
  저장 시점에 서버에서 하려면 외부 URL을 fetch해서 처리해야 함 (URL 만료/CORS/외부 서비스 장애에
  취약). Storage 업로드로 전환하는 게 같이 검토되면 더 안정적.
- 런타임(페이지 로드마다) 추출이 아니라 **어드민 저장 시점에 1회 계산해 `badges` 테이블 컬럼에
  저장**하는 방식이 맞음 (성능·일관성).

### 4. 배경 쉐이더 — 스코프에 따라 비용이 크게 갈림
- `three.js`/`framer-motion`/WebGL 관련 라이브러리 없음. "쉐이더"를 실제 GLSL/WebGL로 구현하면
  신규 대형 의존성 + 모바일 배터리/성능 이슈(뷰포트가 `max-w-[430px]` 모바일 전용 서비스임을
  고려하면 특히 민감).
- CSS 기반 그라디언트/애니메이션("페이크 쉐이더")으로 시작하면 의존성 없이 훨씬 가볍게 구현 가능.
  "계속 추가 가능해야 함(개발로)" 요구사항은 **쉐이더 레지스트리 패턴**(id → 렌더러 컴포넌트 매핑)
  으로 CSS/WebGL 어느 쪽이든 동일하게 만족 가능.
- **의견**: 1차는 CSS 기반 프리셋 3~5종으로 시작하고, WebGL 확장은 실제 니즈가 확인된 뒤 Phase 2로
  미루는 걸 추천.

### 5. 데이터 모델 — 기존 패턴 재사용 가능
- `badges` 테이블에는 아직 컬러/테마 필드 없음. 다만 어드민에 이미 `theme_presets`
  (`main_color`/`sub_color`) 테이블 + `ThemeManager.tsx` 관리 화면 **선례가 존재** — 완전히 새로운
  패턴을 발명할 필요 없이 이 구조를 참고해 `badges`에 `background_color`/`background_shader_id`
  컬럼을 추가하는 쪽이 자연스러움.
- 세계관(`factions`)·아이템북(`item_books`) 일괄 적용 요구사항도 기존 FK 구조(배지가
  `faction_id`/`item_book_id`를 가짐)와 잘 맞음 — "컬렉션 기본값 → 배지 개별 override" 패턴으로
  구현 가능 (예: 배지 컬럼이 NULL이면 상위 faction/item_book 값을 fallback으로 사용).

### 6. 배지 상세 페이지 구조 — 이번 참에 정리할 여지
- `badges/[id]/page.tsx`가 650줄, item/poi/activity 3개 변형의 hero-section이 3중 복사된 상태
  (직전 티켓 [20260816_006](20260816_006_UI_배지상세-상단-카드-레이아웃-변경.md) "잔여 이슈"에
  이미 `BadgeHeroSection` 컴포넌트 추출 필요성이 기록돼 있음). 배경 테마 로직을 3곳에 각각 추가하면
  복잡도가 더 쌓이므로, 이번 개편을 계기로 hero-section을 공통 컴포넌트로 먼저 추출하는 걸 권장.

### 7. 획득 알림 중앙 모달 연동 — 설계상 문제 없음
- 모달은 아직 미개발이므로, 배경 테마 값(색/쉐이더 id)을 배지 상세와 모달이 공유하는 재사용 가능한
  primitive(예: `BadgeThemeBackground` 컴포넌트 또는 CSS 커스텀 프로퍼티)로 처음부터 설계하면
  향후 모달 개발 시 추가 작업 없이 그대로 재사용 가능. 문제 되는 지점 없음.

## 종합 의견
방향성 자체(배지별 개성 있는 비주얼, 세계관 단위 일괄 적용, 확장 가능한 쉐이더 레지스트리)는
타당하고 데이터 모델과도 잘 맞는다. 다만 그대로 한 번에 구현하면:
- Footer 전역 레이아웃 변경 → 전체 서비스 회귀 리스크
- 등급 태그 쉐입 커스터마이징 → 등급 인지성 저하 (원래 취지와 상충 가능성)
- 외부 URL 이미지 기반 평균 컬러 추출 → 안정성 이슈
- WebGL 쉐이더 → 모바일 성능/의존성 비용

네 가지가 리스크로 걸린다. **범위를 좁혀 단계적으로 가는 걸 권장**:
- Phase 1: 배지별 배경색(수동 입력 + 이미지 평균색 자동 추출, TopNav+본문 스코프) + CSS 프리셋
  쉐이더 3~5종 + `badges` 테이블 컬럼 추가 + 어드민 폼 확장
- Phase 2: 세계관/아이템북 일괄 적용 (기본값 fallback 구조)
- Phase 3: Footer까지 배경 확장 (레이아웃 구조 변경 별도 검토) + 획득 알림 모달 연동
- 등급 태그 쉐입 건은 별도로 "정확히 무엇에 적용하려는 것인지" 재확인 필요 (아래 미해결 이슈 참조)

      표현 요소(예: hero 카드 프레임 모양)를 가리키는지 확인

- [ ] 쉐이더를 CSS 기반으로 시작할지, 처음부터 WebGL까지 고려할지 결정
- [ ] 배지 이미지를 Supabase Storage로 옮기는 작업을 병행할지 (외부 URL 유지 시 컬러 추출 안정성
      저하)
