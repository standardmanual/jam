# [UI] 배지 배경색 어드민 개발 + 상세화면 실제 렌더링 연동

## 배경 / 문제 정의
[20260818_002](20260818_002_UI_배지상세-배경테마-기반구조-개편.md)에서 배경 테마를 위한 선행
구조(`getBadgeBackgroundStyle` no-op, 고정 배경 레이어, `badges.background_color`/
`background_shader_id` 컬럼)를 준비해뒀다. 쉐이더 기술 스택은 여전히 미정이지만, **배경색
기능은 지금 바로 실사용 가능하게 완성**한다. 쉐이더는 어드민에서 값만 선택·저장할 수 있는
자리만 마련하고(임시), 실제 렌더링에는 연결하지 않는다.

## 확정된 결정 사항
- 배경색 기본값: 배지 이미지 업로드 시 **평균 컬러 자동 추출** + 관리자가 수동으로 덮어쓸 수 있음
- 쉐이더: 어드민에서 **임시 선택 UI만** 제공 (값 저장은 되나 상세화면 렌더링에는 미연결 — 기술
  스택 결정 후 별도 티켓)
- 배지 상세화면(프론트엔드)이 `background_color`를 **실제로 렌더링**하도록 이번 티켓에 포함

## 상세 요구사항

### 서비스/코드베이스 관점

1. **평균 컬러 자동 추출**
   - 신규 의존성 추가: `sharp` (Node/Vercel 서버 환경 표준 이미지 처리 라이브러리)
   - 배지 이미지 업로드 완료 시(`/api/admin/upload-image` 또는 별도 처리 지점) 업로드된 이미지의
     평균 컬러를 서버에서 계산해 hex 값으로 반환
   - 어드민 배지 폼의 배경색 입력 필드 기본값으로 이 값을 채움 — 관리자가 색상 피커/hex 입력으로
     직접 덮어쓸 수 있어야 함 (자동 추출값은 "기본값"일 뿐 강제 아님)
   - 계산 실패 시(이미지 처리 오류 등) 필드를 빈 값으로 두고 관리자가 수동 입력하도록 함 —
     저장 자체를 막지 않음

2. **어드민 배지 폼 — 배경색 필드**
   - 대상: `jam-web/src/app/admin/badges/BadgeForm.tsx`
   - `badges.background_color` 입력 필드 추가 (색상 피커 + hex 텍스트 입력 겸용)
   - 이미지 업로드 완료 시 자동 추출값으로 프리필, 미리보기(색상 스와치)로 현재 값 표시
   - nullable 허용 (배경색 미지정 시 기존처럼 기본 배경 유지)

3. **어드민 배지 폼 — 쉐이더 임시 선택 필드**
   - `badges.background_shader_id` 입력 필드 추가 — **단순 드롭다운**, 선택지는 하드코딩된
     placeholder 목록 (예: "없음", "프리셋 A(개발 예정)", "프리셋 B(개발 예정)", "프리셋
     C(개발 예정)")
   - 값은 저장되지만 **상세화면 렌더링에는 연결하지 않음** — 필드 근처에 "쉐이더는 아직 상세화면에
     적용되지 않습니다" 안내 문구 표시
   - 쉐이더 목록은 향후 개발로 계속 추가될 예정이므로, 옵션 배열을 코드 한 곳에서 관리해 추가가
     쉬운 구조로 작성 (어드민 UI 자체를 손대지 않고 배열만 늘리면 되는 형태)

4. **배지 상세화면 — 배경색 실제 렌더링 연결**
   - 대상: `jam-web/src/lib/badgeBackgroundTheme.ts`, `jam-web/src/app/(main)/badges/[id]/page.tsx`
   - `getBadgeBackgroundStyle(badge)`가 no-op을 벗어나 `badge.background_color`가 있으면 해당
     색을 실제로 반환하도록 수정 (없으면 기존처럼 빈 값 반환 — 기본 배경 유지)
   - [20260818_002] 잔여 이슈에 기록된 대로, 고정 배경 레이어(`z-index: 0`)가 본문 콘텐츠·전역
     Footer보다 페인트 순서상 아래로 가려지지 않는지 실제 색상이 들어간 상태로 재검증 필요
     (필요 시 콘텐츠 쪽에 최소한의 z-index 보정)
   - `background_shader_id`는 이번 티켓에서 렌더링에 관여하지 않음 (값이 있어도 무시)

### UI/UX 관점
- 어드민 색상 피커는 관리자 내부 도구이므로 MODULAR 대상 아님, 서비스 전용 구현
- 배지 상세화면에 실제 색이 반영되므로, 기존 텍스트(배지명·설명 등) 가독성이 다양한 배경색에서도
  유지되는지 확인 (예: 밝은 배경색에서 흰 텍스트가 묻히지 않는지) — 필요 시 텍스트에 그림자/오버레이
  보정 검토
- 신규 사용자 노출 텍스트(쉐이더 미적용 안내 등)는 UX Writing 가이드 준수

### DS 재사용 판정 (오케스트레이터, 1.5단계)
- 어드민 색상 피커·드롭다운은 admin 정책상 MODULAR 탐색 대상 아님
- 배지 상세화면 변경은 기존 `getBadgeBackgroundStyle`/고정 배경 레이어에 실제 값만 흘려보내는
  것으로, [20260818_002]에서 이미 구조가 마련돼 있어 신규 UI 컴포넌트 불필요

## 구현 계획
1. `sharp` 의존성 추가, 이미지 평균 컬러 계산 유틸 작성 (업로드 파이프라인에 연결)
2. `BadgeForm.tsx`에 배경색 입력(피커+hex, 자동 추출 프리필) + 쉐이더 placeholder 드롭다운 추가
3. `badgeBackgroundTheme.ts`의 `getBadgeBackgroundStyle`을 실제 `background_color` 반환하도록 수정
4. `badges/[id]/page.tsx` 고정 배경 레이어 실제 색상 적용 후 콘텐츠 가려짐 여부 재검증
5. 색상값이 있는 배지로 실제 브라우저(Playwright) 검증 — 텍스트 가독성, 링크 클릭 가능 여부 포함

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- **평균 컬러 자동 추출**: `sharp` 의존성을 추가하고 `src/lib/imageAverageColor.ts`
  (`computeAverageColorHex`)를 신규 작성 — 업로드된 이미지를 1×1로 리사이즈해 평균 픽셀을
  hex로 반환한다. `/api/admin/upload-image`에서 업로드 직후 계산해 응답에 `averageColor`
  필드로 함께 내려준다. 계산 실패(SVG 등) 시 `null`을 반환하고 업로드 자체는 그대로 성공
  처리한다(요구사항대로 저장을 막지 않음).
- **어드민 배지 폼 — 배경색 필드**: `BadgeForm.tsx`에 배경색 입력(색상 피커 `input[type=color]`
  + hex 텍스트 입력 + 스와치 미리보기 + "지우기" 버튼)을 추가. `ImageUploadField`에
  `onAverageColor` 콜백을 새로 추가해, 이미지 업로드 성공 시 서버가 계산한 평균 컬러로 배경색
  필드를 자동 프리필한다(관리자가 이후 직접 덮어쓸 수 있음, nullable). 저장 시 hex 형식
  (`/^#[0-9a-fA-F]{6}$/`)이 아니면 저장을 막고 안내 메시지를 띄운다.
- **어드민 배지 폼 — 쉐이더 임시 선택 필드**: `src/lib/badgeBackgroundShaderOptions.ts`에
  옵션 배열(`BADGE_BACKGROUND_SHADER_OPTIONS`)을 신규 정의(없음/프리셋 A·B·C — 모두
  "개발 예정" placeholder)하고 `BadgeForm.tsx`에 단순 드롭다운으로 노출. 값은
  `badges.background_shader_id`에 저장되지만 상세화면 렌더링에는 연결하지 않았고, 필드
  아래에 "쉐이더는 아직 상세화면에 적용되지 않아요" 안내 문구를 넣었다. 향후 쉐이더가
  늘어나면 옵션 배열에만 항목을 추가하면 되는 구조.
- **API 반영**: `/api/admin/badges` (POST), `/api/admin/badges/[id]` (PUT)에
  `background_color`/`background_shader_id` 필드를 추가해 폼에서 보낸 값을 그대로
  저장하도록 배선.
- **상세화면 실제 렌더링 연결**: `getBadgeBackgroundStyle(badge)`가 no-op을 벗어나
  `badge.background_color`가 있으면 `{ backgroundColor }`를 반환하도록 수정
  (`background_shader_id`는 이번 범위에서 값이 있어도 항상 무시). 이 함수를 공유하는 3개
  지점(TopNav `headerStyle`, `BadgeHeroSection` 카드, 고정 배경 레이어) 모두 실제 색상을
  받게 됐다.
- **[20260818_002] 잔여 이슈(콘텐츠·Footer가 고정 배경 레이어에 가려질 수 있음) 수정**: 실제
  색상이 채워지면 `position:fixed; z-index:0` 배경 레이어가 CSS 스태킹 규칙상 non-positioned
  본문 콘텐츠보다 페인트 순서상 위에 그려져(콘텐츠가 시각적으로 가려짐) 실제로 문제가
  재현됨을 로컬 검증으로 확인했다. `BadgeHeroSection`의 최상위 div와 `page.tsx`의
  info/desc/action-section div들에 `relative z-10`을 부여해 배경 레이어(z:0)보다 항상 위에서
  그려지도록 승격했다. 전역 `Footer`(`(main)/layout.tsx`가 렌더링하는, 배지 상세 페이지의
  고정 배경 레이어와 겹치는 지점)도 동일한 이유로 `Footer.tsx`에 `relative z-10`을 추가했다
  (Footer는 `bg-transparent`라 다른 화면에는 시각적 영향이 없음을 확인).
- **텍스트 가독성 보정**: `background_color`가 있을 때만 페이지 최상위 wrapper에
  `textShadow: '0 1px 2px rgba(0,0,0,0.65), 0 1px 10px rgba(0,0,0,0.4)'`를 적용(CSS 상속으로
  하위 텍스트 전체에 자동 반영). 밝은 배경색에서도 배지명 등 흰 텍스트의 최소 가독성을
  보장하기 위한 최소한의 보정이며, `background_color`가 없으면 기존과 동일(그림자 없음).

### 검증 방법 (DB 미접근 원칙 준수)
jam-developer는 DB 데이터 변경 실행 권한이 위임되지 않아(CLAUDE.md 예외 규칙), 실 배지
row에 `background_color`를 기록해 검증할 수 없었다. 대신 저장소 밖으로 커밋되지 않는 임시
라우트 2개(`(main)/badges/bgtest003tmp`, `bgformtest003tmp` — mock 데이터로 실제
`BadgeHeroSection`/`page.tsx`/`BadgeForm` 컴포넌트를 그대로 렌더링)를 로컬에만 만들어
Playwright 실제 브라우저로 검증한 뒤 **검증 완료 즉시 삭제**했다(커밋 이력에 없음). 어드민
폼 검증 과정에서 실제 업로드 API(`/api/admin/upload-image`)를 통해 Supabase Storage에
테스트 이미지 3건이 업로드됐는데, 이는 SQL/DB row 변경이 아니라 정상적인 업로드 기능
경로였음을 확인 후 service role로 즉시 삭제해 정리했다(스토리지 잔여물 없음). DB 테이블에는
어떤 행도 추가·수정·삭제하지 않았다.

### 주요 의사결정 / 핵심 메모
- CSS 스태킹 컨텍스트 분석: `position:fixed; z-index:0`인 고정 배경 레이어는 CSS2.1 페인트
  순서 규칙상 "in-flow, non-positioned 콘텐츠"(레벨 3)보다 "z-index:0 positioned 콘텐츠"
  (레벨 6)가 항상 나중에(위에) 그려지므로, [20260818_002]가 우려했던 잔여 이슈가 실제
  색상이 들어가면 반드시 재현됨을 확인했다. 해결책은 배경 레이어의 z-index를 낮추는 것이
  아니라(그러면 `main`의 불투명 `bg-surface` 아래로 숨어버려 색이 아예 안 보이게 됨),
  콘텐츠 쪽을 `relative z-10`으로 승격하는 방향으로 잡았다 — 티켓에 명시된 "콘텐츠 쪽에
  최소한의 z-index 보정"과 일치.
- `getBadgeBackgroundStyle`이 TopNav·히어로 카드·고정 배경 레이어 3곳에 동일하게 배선돼
  있어([20260818_002] 구조), 배경색을 설정하면 히어로 카드 자체도 배경과 같은 색으로
  물들어 카드 경계가 시각적으로 사라지고 전체 화면이 하나의 색면처럼 보인다. 이 배선은
  [20260818_002]에서 이미 확정된 구조이고 이번 티켓 범위에서 변경 지시가 없어 그대로
  유지했다 — 앨범아트 색 배경처럼 화면 전체를 물들이는 디자인을 의도한 것으로 판단.
- DB에 직접 접근할 수 없는 제약 때문에 검증은 "실제 DB 데이터를 읽어와 렌더링"이 아니라
  "실제 컴포넌트 코드에 mock 데이터를 주입해 렌더링"하는 방식을 택했다. 렌더링에 쓰인
  JSX/CSS/컴포넌트는 실제 프로덕션 코드와 동일하므로 z-index·pointer-events·텍스트 그림자
  검증의 신뢰도는 유지되지만, "실제 admin 폼 저장 → 실제 DB 저장 → 실제 상세화면 조회"
  전체 파이프라인의 종단 간(end-to-end) 검증은 이번 서브에이전트 권한 밖이라 수행하지
  못했다 — 오케스트레이터/사용자가 실 배지 1건에 배경색을 설정해 최종 확인하는 것을 권장.

### 잔여 이슈
- 보조 설명 텍스트(`--color-text-secondary`, 회색)는 밝은 배경색(예: 파스텔톤 자동 추출
  컬러)에서 텍스트 그림자를 적용해도 여전히 대비가 낮을 수 있다. 완전한 해결(예: 배경
  밝기에 따라 텍스트 색을 동적으로 흑/백 전환)은 이번 "최소한의 보정" 범위를 넘어서는
  설계 변경이라 포함하지 않았다. 실제 배지에 밝은 배경색을 설정한 뒤 육안으로 재확인하고,
  체감상 문제가 크면 후속 티켓에서 동적 텍스트 색상 전환을 검토할 것을 권장한다.
- 어드민 폼 저장(`POST /api/admin/badges`, `PUT /api/admin/badges/[id]`) → 실제 DB 반영 →
  상세화면 실 조회로 이어지는 종단 간 검증은 jam-developer의 DB 접근 제약으로 수행하지
  못했다. 오케스트레이터/사용자가 실 배지 1건으로 최종 확인 권장.
- `background_shader_id` 드롭다운은 요구사항대로 렌더링에 관여하지 않지만, 쉐이더 스택이
  확정되면 [20260818_001]/[20260818_002]에서 예고된 별도 후속 티켓이 필요하다(변경 없음,
  참고용 기록).
