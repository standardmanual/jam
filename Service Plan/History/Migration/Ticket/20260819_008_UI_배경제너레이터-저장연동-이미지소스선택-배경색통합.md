# [UI] 배경 제너레이터 — 실제 저장 연동 + 이미지 소스 선택 + 배경색 통합

## 배경 / 문제 정의
티켓 20260819_007은 "저작 UI + 라이브 미리보기까지만"으로 스코프를 의도적으로 좁혀서, 제너레이터
컨트롤 값이 `BadgeForm`의 저장(`handleSubmit`)과 연결돼 있지 않았다. 사용자가 이를 실제로 사용해보고
"저장해도 반영 안 됨"을 보고했는데, 이는 회귀 버그가 아니라 007의 의도된 스코프였다(확인 완료 —
`background_color`/`background_shader_id` 기존 저장 경로는 정상 동작).

이번 티켓은 그 다음 단계다: **실제로 저장되고, 실제 배지 상세화면에 반영**되도록 만든다. 동시에
사용자가 요청한 UX 개선 3가지를 함께 반영한다.

## 확정된 설계 결정 (대화로 확정, 재확인 없이 진행)

1. **저장 방식**: "저장" 시점에 현재 미리보기(패턴 또는 애니메이션의 일시정지 프레임 위에 Paper
   필터가 적용된 합성 결과)를 **static PNG로 구워(bake) Storage에 업로드**하고, 그 URL을
   `badges.background_image_url`(신규 컬럼)에 저장한다. 원시 설정값(JSON)은 저장하지 않는다 —
   즉 이번 범위에서는 "재편집 가능한 설정"이 아니라 "완성된 배경 이미지 1장"을 만드는 것이다.
   - 애니메이션 모드는 이번 범위에서 **정지 이미지로만** 굽는다(반복 영상 굽기는 별도 후속 티켓).
     티켓 007 이전 논의에서 확정한 "일시정지 버튼 = 배경 확정 트리거" 원칙을 따른다 —
     애니메이션 모드에서 저장 시점의 캔버스 상태(정지 여부와 무관하게 그 순간 프레임)를 그대로 굽는다.
2. **배경색 vs 제너레이터 공존**: **상호 배타적**(라디오 버튼). 어느 쪽을 선택했느냐에 따라 저장 시
   나머지 하나는 비운다(둘 다 값이 남아있게 하지 않는다 — 렌더링 시 우선순위 혼란 방지).
3. **배경색 설정 위치**: 기존 `BackgroundColorField`를 제너레이터 영역 **안으로 이동**해서, "단색"과
   "제너레이터" 두 모드 중 하나를 선택하는 라디오 UI 밑에 각각의 설정 패널이 나오는 구조로 만든다.
4. **이미지 소스 선택**: 제너레이터의 이미지 입력 단계에서 ① 새 이미지 업로드 또는 ② 이미 등록된
   배지 이미지(`image_url`, 폼에 이미 로드돼 있음) 재사용 중 **선택** 가능하게 한다.

## 상세 요구사항

### DB 스키마 관점 (중요 — 실행 주체 제한)
- `badges` 테이블에 `background_image_url` (text, nullable) 컬럼을 추가하는 마이그레이션 SQL 파일을
  `jam-web/supabase/migrations/088_add_badges_background_image_url.sql`로 작성한다.
- **jam-developer는 이 SQL 파일을 작성만 하고 절대 실행하지 않는다.** 실행은 사용자 승인 후
  오케스트레이터(베이스캠프)가 직접 처리한다 — 프로젝트 규칙(`CLAUDE.md` 5번 항목).

### 서비스/코드베이스 관점
- **저장 파이프라인**:
  - 제너레이터의 통합 미리보기 노드(캔버스 또는 이미지)를 PNG Blob으로 변환하는 함수를 추가한다
    (신규 유틸, 예: `bakePreviewToBlob`).
  - 기존 이미지 업로드 API(`jam-web/src/app/api/admin/upload-image/route.ts`)를 재사용해 이 Blob을
    업로드한다(별도 API 신설 불필요 — 파일 형태로만 감싸면 됨). 응답의 이미지 URL을 받는다.
  - `BadgeForm.tsx`의 `handleSubmit`: 저장 직전, 배경 모드가 "제너레이터"면 위 굽기+업로드를 먼저
    수행해 `background_image_url`을 얻고, 모드가 "단색"이면 `background_image_url: null`을
    payload에 포함한다(반대쪽은 항상 null로 정리). `background_color`도 마찬가지로 모드에 따라
    값 또는 null.
  - `jam-web/src/app/api/admin/badges/[id]/route.ts` (및 POST 라우트)의 body 파싱·update에
    `background_image_url` 필드를 추가한다.
  - `jam-web/src/types/database.ts`의 `BadgeRow` 타입에 `background_image_url` 필드 추가.
- **실제 배지 상세화면 반영** (`ui` 유형 — 서비스 렌더링 변경이므로 신중히):
  - `jam-web/src/lib/badgeBackgroundTheme.ts`의 `getBadgeBackgroundStyle`을 확장한다:
    `background_image_url`이 있으면 그것을 우선(`backgroundImage: url(...)`, 적절한
    `backgroundSize`/`backgroundPosition` — 이미 430px 기준으로 합성된 최종 이미지이므로
    `cover` 또는 `100% 100%` 중 실제 비율에 맞는 쪽으로 판단), 없으면 기존처럼 `background_color`
    로 폴백한다.
  - `BadgeBackgroundThemeSource` Pick 타입에 `background_image_url` 추가.
  - `jam-web/src/app/(main)/badges/[id]/page.tsx`·`BadgeHeroSection.tsx`의 호출부가 이미
    `getBadgeBackgroundStyle(badge)`로 badge 객체 전체(또는 필요한 필드)를 넘기는 기존 패턴을
    따르는지 확인하고, 필요한 최소 범위만 수정한다(기존 패턴 재사용, 새 구조 발명 금지).
- **UI 재구성** (`BackgroundGeneratorPreview.tsx` 또는 `BadgeForm.tsx`):
  - "단색" / "제너레이터" 라디오 선택 UI 신설. "단색" 선택 시 기존 `BackgroundColorField` 노출,
    "제너레이터" 선택 시 기존 이미지 업로드+패턴/애니메이션+필터 컨트롤 노출.
  - 이미지 입력 단계에 "새 이미지 업로드" / "등록된 배지 이미지 사용" 선택 UI 추가. 후자를 선택하면
    폼의 현재 `imageUrl` state를 `loadImage.ts`(스파이크에서 이미 재사용 중인 유틸)로 로드해서
    그대로 제너레이터 파이프라인에 흘려보낸다.
- 신규 의존성 추가 금지. Three.js 등 금지 목록은 이전 티켓과 동일.

### UI/UX 관점

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- **마이그레이션**: `badges.background_image_url`(text, nullable) 추가 SQL만 작성(실행 안 함,
  `088_add_badges_background_image_url.sql`).
- **저장 파이프라인**: `bakePreviewToBlob.ts`(신규) — 제너레이터 라이브 미리보기 컨테이너 DOM을
  그대로 캡처해 PNG Blob으로 굽는다. 필터 적용 상태(Paper 셰이더 `<canvas>`)면 그 캔버스를
  바로 `toBlob()`, 필터 없음(`<img>`, 패턴/애니메이션 평면화 data URL)이면 지정 크기 2D 캔버스에
  그려서 `toBlob()`. 별도 오프스크린 재렌더링 파이프라인을 새로 만들지 않고 "화면에 보이는 그대로"
  캡처하는 방식을 택했다.
  - WebGL 드로잉 버퍼가 컴포지팅 후 비워지는 문제를 막기 위해 `FilterPreview.tsx`의 Paper 셰이더
    5종 모두에 `webGlContextAttributes={{ preserveDrawingBuffer: true }}`를 추가(시각 결과·성능
    영향 없음, export 시점 빈 프레임 방지용).
  - `BadgeForm.tsx`의 `handleSubmit`이 굽기+업로드+payload 구성을 담당. 기존
    `/api/admin/upload-image`를 그대로 재사용(별도 API 신설 없음). 모드가 "제너레이터"이고 이번
    세션에 이미지를 하나도 고르지 않았으면(`bakeToBlob()` → null) 기존에 저장된
    `background_image_url`을 그대로 유지한다(폼을 열었다 그냥 저장만 해도 배경이 사라지지 않게).
- **배경색 vs 제너레이터 상호 배타**: `BadgeForm`에 `backgroundMode`('color'|'generator') state를
  새로 두고(수정 모드는 `badge.background_image_url` 유무로 기본값 결정), 저장 시 반대쪽 값은 항상
  null로 정리. 배경색 hex 형식 검증도 "단색" 모드일 때만 수행하도록 조정(제너레이터 모드에서
  숨겨진 잔여 입력값 때문에 저장이 막히지 않도록).
- **UI 재구성**: 기존 `BackgroundColorField`를 `BadgeForm`에서 빼내 `BackgroundGeneratorPreview`
  내부로 이동. "단색"/"제너레이터" 라디오 아래 선택된 모드의 패널만 노출하고, 전환 시 반대쪽 값이
  지워진다는 안내 문구를 상시 노출. 라이브 미리보기도 선택된 모드 결과만 반영하도록 배타적으로
  바꿨다(제너레이터 모드에서 새 이미지를 아직 안 골랐고 기존 저장된 배경이 있으면 그 이미지를
  미리보기에 표시 — "저장돼 있던 게 사라진 것처럼" 보이지 않게 하는 안내용, 원시 설정 재편집은
  여전히 불가).
- **이미지 소스 선택**: "새 이미지 업로드"/"등록된 배지 이미지 사용" 라디오 추가. 후자는 폼의
  `imageUrl`(배지 본체 이미지)을 `loadImageFromUrl(url, { crossOrigin: 'anonymous' })`로 로드해
  기존 패턴/애니메이션 파이프라인에 그대로 흘려보낸다. `loadImage.ts`에 `crossOrigin` 옵션을
  추가(기본 미지정이라 기존 objectURL 로드 경로는 영향 없음) — 원격 Storage 이미지를 캔버스
  소스로 쓰면 이후 `toDataURL`/`toBlob`이 CORS로 막히는 것을 방지하기 위함.
  등록된 배지 이미지가 없으면(`imageUrl` 미입력) 이 라디오는 비활성화.
- **실제 배지 상세화면 반영**: `getBadgeBackgroundStyle`을 확장해 `background_image_url`이 있으면
  최우선(`backgroundImage` + `backgroundSize: cover` + `backgroundPosition: center`), 없으면 기존
  `background_color` 폴백. `BadgeBackgroundThemeSource` Pick 타입, `BadgeHeroSection`의 Pick 타입에
  `background_image_url` 추가. `badges/[id]/page.tsx`는 `select('*')`로 이미 신규 컬럼을 포함하므로
  호출부 자체는 변경 불필요 — `themedTextStyle`(가독성용 텍스트 그림자) 조건에만
  `background_image_url` 존재 여부를 추가(배경 이미지가 있을 때도 그림자가 적용되도록, 최소
  변경).
- API 라우트(`badges/[id]` PUT, `badges` POST) body 파싱·update/insert에 `background_image_url`
  필드 추가. `BadgeRow` 타입에도 필드 추가.

  - 회귀 확인: "단색" 모드로 hex(#336699) 입력 후 저장 시도 → payload에

  - 검증 스크립트/이미지는 스크래치패드에만 저장, 저장소에는 커밋하지 않음(임시 파일 정리 완료)

### 주요 의사결정 / 핵심 메모
- **"화면에 보이는 그대로" 캡처 원칙**: 별도 오프스크린 렌더러를 새로 만들지 않고, 실제
  `BackgroundGeneratorPreview`가 렌더링한 DOM(패턴/애니메이션+필터 최종 합성 노드)을 그대로
  `bakePreviewToBlob`이 캡처한다. Paper 셰이더는 WebGL `<canvas>`를 그대로 `toBlob()`하고, 필터
  없음(순수 이미지)은 이미 data URL이므로 2D 캔버스에 한 번 그려서 export한다 — 두 경로 모두
  기존 렌더링 로직을 재작성하지 않았다.
- **WebGL 드로잉 버퍼 보존**: `toBlob()`은 캡처 시점 캔버스의 실제 드로잉 버퍼를 읽는데, 기본
  WebGL 컨텍스트는 컴포지팅 이후 버퍼를 비울 수 있어(브라우저별 타이밍 차이) 저장 시점에 빈/오래된
  프레임이 구워질 위험이 있었다. Paper 셰이더 컴포넌트가 노출하는 `webGlContextAttributes` prop에
  `preserveDrawingBuffer: true`를 주는 것으로 해결 — 신규 의존성 추가 없이 기존 라이브러리 옵션만
  사용.
- **CORS**: "등록된 배지 이미지 사용" 시 원격 Storage URL을 캔버스 소스로 쓰므로
  `crossOrigin: 'anonymous'`가 필요했다(그렇지 않으면 이후 `toDataURL`/`toBlob`이 tainted canvas
  SecurityError). 반대로, 패턴/애니메이션의 최종 합성 결과(FilterPreview에 흘러들어가는 소스)는
  내부적으로 항상 `canvas.toDataURL()`을 거친 data URL이라 필터 단계 자체는 원본 이미지 출처와
  무관하게 CORS 문제가 없다 — CORS 대응이 필요한 지점은 "원본 이미지를 최초로 `<img>`에 로드하는"
  단 한 곳뿐임을 검증 과정에서 확인했다.
- **기존 저장값 유지 원칙**: 제너레이터 모드에서 원시 설정을 재저장할 수 없다는 제약(티켓 확정
  사항) 때문에, "수정 폼을 열었다가 아무 것도 안 바꾸고 저장"하면 기존 `background_image_url`이
  null로 덮어써지는 회귀가 생기기 쉬운 구조였다. `bakeToBlob()`이 null(이번 세션에 이미지 미선택)을
  반환하면 `badge.background_image_url`을 그대로 payload에 싣는 방식으로 이 회귀를 막았다.
- **라이브 미리보기의 "기존 배경 자리표시"**: 재편집 시 원시 설정은 복원 불가하지만, 제너레이터
  모드로 진입했는데 미리보기가 텅 비어 보이면 "저장된 게 없어졌다"는 오해를 살 수 있어, 새 이미지를
  아직 안 고른 상태에서는 저장된 `background_image_url` 이미지를 그대로 오버레이에 띄우고 안내
  문구를 덧붙였다.

### 재검증 기록 (2026-08-19, 마이그레이션 088 적용 후)
오케스트레이터가 마이그레이션 088(`badges.background_image_url` 컬럼)을 jam-prod DB에 직접 적용
완료한 뒤, 아래 순서로 이전에 막혀 있던 end-to-end round-trip 전체를 재검증했다. 코드는 이전
세션(커밋 `6792e11`)에서 이미 게이트 리뷰를 통과한 상태 그대로이며, 이번엔 수정 없이 검증만
수행했다(코드 변경 없음).

- **사전 확인**: service_role로 `badges` 테이블에 `background_image_url` 컬럼이 실제로 조회
  가능한지 read-only로 확인(200 응답, 마이그레이션 반영 확인).
- **로컬 검증 방식**: 로컬 `next dev` + `/api/dev-login` + `.env.local`에 로컬 전용 임시
  `ADMIN_EMAILS` 설정(검증 후 원상 복구, `git status`로 diff 없음 확인) + Playwright 스크립트로
  실제 브라우저 자동화 수행(스크립트·스크린샷은 스크래치패드에만 저장, 저장소에 커밋하지 않음).
- **① 저장 → DB 반영**: `/admin/badges/new`에서 배지 본체 이미지 업로드 → 배경 모드 "제너레이터"
  선택 → 제너레이터용 이미지 업로드(패턴 모드 기본값) → Paper 필터 "Fluted Glass" 적용 → "배지
  등록" 클릭. `POST /api/admin/upload-image` 200(배경 PNG가 실제 Storage에 업로드됨) → `POST
  /api/admin/badges` **201**로 성공(이전 세션 FAIL 사유였던 500 스키마 캐시 에러가 더 이상
  발생하지 않음을 확인). REST API로 해당 배지 행을 직접 조회해 `background_image_url`에 방금
  업로드된 Storage URL이 실제로 저장돼 있음을 확인.
- **② `/badges/[id]` 실제 렌더링**: 생성된 배지 id로 실제 서비스 페이지(`/badges/[id]`)에 접속해
  스크린샷 확인(`v2-badge-detail-page.png`) — 페이지 전체 고정 배경 레이어에 Fluted Glass로 합성된
  배경 이미지가 `cover`로 적용돼 렌더링됨을 시각적으로 확인. (테스트 배지 이미지가 100×100 단색
  자리표시 이미지라 히어로 카드 내 배지 아이콘 자체는 잘 안 보이지만, 이는 "미획득 배지" 상태의
  기존 UI 동작이며 배경 레이어 렌더링 검증과는 무관.)
- **③ 재진입 시 모드 자동 판정**: 같은 배지의 어드민 수정 폼(`/admin/badges/[id]/edit`)에 재진입해
  스크린샷 확인(`v3-admin-edit-reentry.png`) — "제너레이터" 라디오가 자동으로 선택돼 있음(DOM에서
  `checked` 상태 직접 확인) + 기존 저장된 배경 이미지가 `alt="저장된 배경"` `<img>`로 미리보기에
  1개 렌더링됨을 확인. `initialBackgroundImageUrl` 프리필 로직이 실제 수정 모드에서 정상 동작함을
  검증.
- **④ 상호 배타 동작의 실제 DB 레벨 검증**: 같은 폼에서 "단색"으로 전환 → hex `#336699` 입력 →

  null` 필터를 쓰므로 더 이상 노출되지 않음을 코드로 확인. 로컬 `.env.local`의 임시 `ADMIN_EMAILS`

### 잔여 이슈
- 애니메이션 모드에서 저장하면 "일시정지 여부와 무관하게 저장 시점의 프레임"이 구워진다(확정
  설계). 애니메이션 모드로 굽는 경로는 이번 재검증에서도 패턴 모드만큼 반복 확인하지 않았다(로직은
  패턴 모드와 동일하게 `<canvas>`를 그대로 `toBlob()`하는 경로를 타므로 별도 분기 없음 — 코드
  경로상 위험은 낮다고 판단하나, 실제 애니메이션 굽기 결과를 시각 확인한 것은 아니다).
- 배경 이미지가 Hero 카드(정사각, 패딩 있음)와 페이지 전체 고정 배경 레이어(전체 폭)에 각각
  독립적으로 `cover`로 적용되므로, 두 레이어 경계에서 이음매가 보일 수 있다 — 이는 007에서
  `background_color`도 동일하게 겪던 기존 아키텍처 한계이며, 이번 티켓 범위("필요한 최소 범위만
  수정")에서는 그대로 두었다.
- 테스트에 사용한 배지 이미지가 매우 단순한 100×100 단색 자리표시 이미지였기 때문에, 실제 사진
  이미지를 소스로 한 패턴/애니메이션 합성 결과의 시각 품질까지는 이번 재검증 범위에 포함하지
  않았다(007에서 이미 실제 이미지로 패턴/필터 조합을 검증한 바 있어 별도 재확인은 생략).
