# [Infra] sharp 네이티브 모듈 프로덕션 로딩 실패 긴급 수정

## 배경 / 문제 정의
프로덕션 배포(`dpl_ifaQVvgbVYeMwcHSqNW3SN3TtVJs`, 티켓 20260819_008 반영분) 이후, 사용자가
배지 수정 페이지에서 배경 제너레이터로 저장하면 `Unexpected token '<', "<!DOCTYPE "... is not
valid JSON` 오류가 발생한다고 보고했다.

Vercel 런타임 에러 로그(`get_runtime_errors`)로 근본 원인 확인:

```
Error: Failed to load external module sharp-10c1ab0fa4c72150: Error: Could not load the
"sharp" module using the linux-x64 runtime
ERR_DLOPEN_FAILED: libvips-cpp.so.8.18.3: cannot open shared object file
routes=/api/admin/upload-image
```

`/api/admin/upload-image`가 업로드된 이미지의 평균 컬러 계산에 `sharp`를 쓰는데(티켓
20260818_003), 프로덕션 Linux 런타임에서 `sharp`의 네이티브 바이너리(`libvips-cpp`)를 로드하지
못해 서버 함수가 처리되지 않은 예외로 죽는다. Next.js가 그 결과로 기본 HTML 에러 페이지를
반환하고, 클라이언트는 이를 JSON으로 파싱하려다 실패해서 "Unexpected token '<'" 에러로 보인 것.

**영향 범위는 배경 제너레이터에 국한되지 않는다** — `/api/admin/upload-image`를 쓰는 **모든
이미지 업로드**(배지 신규 등록 포함)가 이 배포 이후 전부 실패하는 상태다.

**원인 추정**: `jam-web/next.config.ts`에는 애초에 `sharp`를 서버 외부 패키지로 명시하는 설정이
없었다. 이번 세션에서 신규 의존성(`@paper-design/shaders-react`, 티켓 20260819_001)을 추가하며
`package-lock.json`의 의존성 트리가 재구성됐고, 그 결과 Vercel 빌드의 파일 트레이싱이 `sharp`의
플랫폼별 네이티브 바이너리(`@img/sharp-linux-x64`)를 서버리스 함수 번들에 올바르게 포함하지
못하게 된 것으로 보인다(`package-lock.json`에는 `@img/sharp-linux-x64`가 최상위와
`next/node_modules` 아래 두 벌 존재 — 버전 충돌 가능성).

## 상세 요구사항

### 서비스/코드베이스 관점
- `jam-web/next.config.ts`에 `serverExternalPackages: ['sharp']`를 추가한다. 이는 Next.js가
  `sharp`를 webpack/turbopack로 번들링·트레이싱하지 않고 Node.js가 직접
  `require`하도록 만드는 공식 권장 해결책으로, 이 종류의 네이티브 모듈 로딩 실패를 해결하는
  표준 방법이다.
- 이 설정만으로 해결되지 않을 경우(로그로 재확인 필요)에 대비해, `package-lock.json`의
  `@img/sharp-linux-x64` 중복/버전 불일치(최상위 vs `next/node_modules` 하위) 여부도 함께
  조사하고 필요하면 `npm install`로 lockfile을 정리한다.
- 절대 `sharp` 의존성 자체를 제거하거나 평균 컬러 추출 기능을 비활성화하는 방식으로 "우회"하지
  말 것 — 근본 원인(번들링 설정)을 고칠 것.

## 구현 계획
1. `next.config.ts`에 `serverExternalPackages: ['sharp']` 추가
2. `npm run build` 로컬 성공 확인

   확인 — 로컬에서는 Vercel Linux 런타임을 완전히 재현할 수 없으므로 **실제 배포 후 로그 확인이
   필수 검증 단계**다
5. 완료 기록에 로그 확인 결과(에러 재발 여부)를 근거로 남길 것

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- `jam-web/next.config.ts`에 `serverExternalPackages: ['sharp']`를 추가했다. Next.js가
  `sharp`를 webpack/turbopack로 번들링·트레이싱하지 않고 Node.js가 직접 `require`하게 만들어,
  서버리스 함수 번들에서 플랫폼별 네이티브 바이너리(`libvips`)가 누락되는 문제를 근본적으로
  해결하는 공식 권장 설정이다.
- `package-lock.json`의 `@img/sharp-linux-x64` 중복(최상위 `node_modules/@img/sharp-linux-x64`
  0.35.3 vs `node_modules/next/node_modules/@img/sharp-linux-x64` 0.34.5)을 조사했다. 이는
  버전 충돌/lockfile 손상이 아니라 **정상적인 npm 중첩 설치**로 확인됐다 — `next@16.2.10`
  패키지 자체가 자신의 이미지 최적화 API용으로 `optionalDependencies.sharp: "^0.34.5"`를
  선언하고 있고, 우리 코드(`src/lib/imageAverageColor.ts`)는 `package.json`의
  `sharp: "^0.35.3"`(최상위 설치본)을 import한다. 서로 다른 소비자가 서로 다른 버전 범위를
  요구하면 npm이 하나를 중첩 설치하는 것은 표준 동작이며, 두 설치본 모두 유효하고 서로 충돌하지
  않는다. 따라서 `npm install`로 lockfile을 추가로 정리하지 않았다(불필요한 변경 방지).
- sharp 의존성 제거나 평균 컬러 추출 기능 비활성화 등의 우회는 하지 않았다.

### 주요 의사결정 / 핵심 메모
- 로컬 macOS 환경에서는 Vercel Linux 런타임(`linux-x64`, glibc)의 `dlopen` 동작을 재현할 수
  없어 이번 수정의 실질적 효과는 로컬 빌드 성공만으로 완전히 검증되지 않는다. 실제 검증은
  오케스트레이터의 staging 배포 후 런타임 로그 확인 단계에서 이뤄져야 한다.
- `package-lock.json`은 이번 수정에서 건드리지 않았다(조사 결과 정상 상태로 판단).

  처리 항목).
