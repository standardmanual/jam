# [Infra] sharp 네이티브 모듈 로딩 실패 2차 긴급 수정 — 트레이싱 루트 불일치

## 배경 / 문제 정의
티켓 [20260819_009](20260819_009_Infra_sharp네이티브모듈-프로덕션로딩실패-긴급수정.md)에서
`serverExternalPackages: ['sharp']`를 추가해 배포했으나, 프로덕션에 재배포
(`dpl_B4NdDgjReJcLbm5mQmWGyc6fu6VF`) 후에도 **동일한 에러가 그대로 재발**했다(사용자 재보고,
Vercel 런타임 로그로 재확인 — 에러 해시까지 완전히 동일: `sharp-10c1ab0fa4c72150`).

새 배포의 빌드 로그를 직접 확인해 추가 원인을 찾았다:

```
⚠ Both `outputFileTracingRoot` and `turbopack.root` are set, but they must have the same value.
Using `outputFileTracingRoot` value: /vercel/path0.
```

`jam-web/next.config.ts`는 로컬 개발 환경 문제(`$HOME/package-lock.json`을 워크스페이스 루트로
잘못 추론해 CSS import가 깨지던 문제, 커밋 `fb0ab75`, 2026-08-17)를 고치려고
`turbopack.root: path.join(__dirname)`만 설정해뒀다. Vercel 프로덕션 빌드에서는 이 값이
Vercel이 자동 추론하는 `outputFileTracingRoot`(`/vercel/path0`)와 일치하지 않아 **무시되고
`outputFileTracingRoot` 쪽이 우선 적용**된다. Next.js의 서버리스 함수 출력 파일 트레이싱은
`outputFileTracingRoot` 기준으로 동작하므로, 이 불일치가 `sharp`처럼 소스 코드에서 직접
import하지 않는(설치 시점 optional dependency로만 존재하는) 네이티브 바이너리 파일을 트레이싱
결과에서 누락시키는 원인일 가능성이 높다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `jam-web/next.config.ts`에서 `outputFileTracingRoot`와 `turbopack.root`를 **동일한 값**으로
  명시적으로 설정한다(둘 다 `path.join(__dirname)` 등 같은 계산식 사용). Vercel의 자동 추론에
  맡기지 않고 명시적으로 고정해서 경고 자체를 없앤다.
- 티켓 009의 `serverExternalPackages: ['sharp']`는 그대로 유지한다(제거하지 말 것 — 문제
  해결에 필요한 조건 중 하나일 수 있음, 둘 다 있어야 해결될 가능성).
- 이 수정만으로 해결되지 않을 경우를 대비해, `outputFileTracingIncludes`로
  `/api/admin/upload-image` 라우트에 `sharp` 네이티브 바이너리 경로
  (`./node_modules/@img/sharp-linux-x64/**/*`, `./node_modules/@img/sharp-libvips-linux-x64/**/*`)
  를 명시적으로 포함시키는 방법도 조사해서 필요하면 함께 적용한다(Next.js 공식 문서의 sharp+Vercel
  네이티브 모듈 트러블슈팅 가이드에 언급되는 표준 대안).
- sharp 의존성 제거나 기능 비활성화 등 우회는 여전히 금지.

## 구현 계획
1. `next.config.ts`에서 `outputFileTracingRoot`/`turbopack.root`를 같은 값으로 명시
2. `npm run build` 로컬 성공 확인 — 이번엔 특히 "Both ... must have the same value" 경고가
   사라지는지 로그로 확인
3. staging에 배포 후 빌드 로그에서 해당 경고가 실제로 사라졌는지 확인 (오케스트레이터 처리)
4. 여전히 sharp 로딩 에러가 재발하면 `outputFileTracingIncludes`로 네이티브 바이너리 경로를
   명시적으로 포함시키는 추가 조치 적용
5. **오케스트레이터가 production 배포 후 반드시 Vercel 런타임 로그(`get_runtime_errors`)로
   `ERR_DLOPEN_FAILED` 완전 재발 여부를 재확인**한다 — 이번엔 로컬 검증만으로 완료 처리하지
   않는다(009에서 로컬 성공 판정만으로 넘어갔다가 실제로는 해결 안 됐던 전례가 있음)

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
`jam-web/next.config.ts`에서 `projectRoot = path.join(__dirname)` 상수를 하나만 계산해
`outputFileTracingRoot`와 `turbopack.root`에 동일하게 대입했다. 기존에는 `turbopack.root`만
명시돼 있어 Vercel 빌드에서 자동 추론된 `outputFileTracingRoot`(`/vercel/path0`)와 값이 어긋나
경고와 함께 `outputFileTracingRoot` 쪽이 우선 적용됐다. 티켓 009의
`serverExternalPackages: ['sharp']`는 그대로 유지했다.
추가 안전장치로 `outputFileTracingIncludes`에 `/api/admin/upload-image` 라우트 키를 두고
`./node_modules/@img/sharp-linux-x64/**/*`, `./node_modules/@img/sharp-libvips-linux-x64/**/*`
글롭을 명시적으로 포함시켰다(Next.js 공식 `output.md` 트러블슈팅 가이드의 표준 대안, 로컬 macOS
환경에는 해당 `@img/sharp-linux-x64` 패키지가 설치돼 있지 않지만 — sharp의 optional
dependency가 플랫폼별로 설치되므로 — Vercel Linux 빌드 환경에서는 설치되어 트레이싱된다).

### 주요 의사결정 / 핵심 메모
- `outputFileTracingRoot`/`turbopack.root`를 별도 상수(`projectRoot`)로 통합해 두 값이 다시
  어긋날 여지를 코드 구조적으로 차단했다.
- `outputFileTracingIncludes`의 라우트 키는 Next.js가 picomatch로 매칭하는 라우트 경로 문자열이며,
  실제 파일 경로(`src/app/api/admin/upload-image/route.ts`)가 아니라 URL 경로
  (`/api/admin/upload-image`)를 사용해야 한다 — `node_modules/next/dist/docs/.../output.md`
  예시로 확인.
- 이번 조치가 트레이싱 루트 불일치와 네이티브 바이너리 누락 두 가능성을 모두 다루지만, 실제
  Vercel Linux 런타임에서 `ERR_DLOPEN_FAILED`가 사라지는지는 로컬에서 검증 불가능하다(로컬은
  macOS라 `@img/sharp-linux-x64` 패키지 자체가 설치되지 않음). 반드시 production 런타임 로그로
  재확인 필요.

### 잔여 이슈
- staging/production 배포 및 런타임 로그 재확인은 오케스트레이터 처리 대기 중
- 이번 조치로도 재발할 경우, `output: 'standalone'` 모드 전환이나 sharp를 별도 함수/서비스로
  분리하는 등 더 근본적인 대안 검토가 필요할 수 있음 (이번 티켓 범위 밖)
