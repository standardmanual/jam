# [bug] 애니메이션 배경 — 영상 타일이 상단 2개뿐, 페이지 하단은 정지된 채로 남는 버그

## 배경 / 문제 정의

사용자가 화면 녹화(`화면 기록 2026-08-19 오후 6.37.40.mov`)로 재현: 배지 상세화면에서 애니메이션
모드 배경을 적용하면 **상단 두 타일(패턴 반복 단위)만 움직이고, 그 아래는 정지 이미지 그대로**다.
프레임을 추출해 실제로 비교한 결과 확인됨 — 상단부는 미세하게 회전/이동하는데 하단부는 프레임 간
완전히 동일(정지).

### 근본 원인 (코드 확인 완료)

`(main)/badges/[id]/page.tsx`와 `(main)/itembooks/[id]/page.tsx`(티켓 011/012, 014) 양쪽 모두
동일한 구조:

- 고정 배경 레이어(`position:fixed`, 뷰포트 전체 높이)의 CSS `background-image`는
  `background_image_url`(정지 이미지)을 `backgroundSize:'100% auto'` + `backgroundRepeat:'repeat'`로
  **세로 전체에 반복**한다.
- 그 위에 `<video>` 엘리먼트 하나를 `position:absolute; top:0; width:100%; height:auto`로 얹는데,
  영상 자체가 **430×860(정사각 타일 2장 분량)으로 구워져 있어** 영상의 실제 렌더링 높이도 860px
  뿐이다. `<video>`는 `background-repeat`처럼 타일링할 수 있는 CSS 속성이 없다.
- 결과: 레이어 상단 860px는 `<video>`가 덮어 애니메이션이 보이고, 그 아래는 `<video>`가 없는
  빈 영역이라 밑에 깔린 CSS 배경(정지 이미지의 반복)이 그대로 노출된다 — 페이지가 860px보다 길면
  전부 이 증상이 나타난다(배지 상세·컬렉션 상세 둘 다 일반적으로 860px를 넘는 길이).

## 상세 요구사항

### 서비스/코드베이스 관점

1. **전수 점검 대상**: 이 문제는 애니메이션 배경이 렌더링되는 **모든** 지점에서 동일하게
   발생한다 — `(main)/badges/[id]/page.tsx`, `(main)/itembooks/[id]/page.tsx` 둘 다 수정 대상.
   (어드민 프리뷰 `BadgeDetailPreviewFrame`/`ItemBookDetailPreviewFrame`는 프레임 높이가
   고정이라 증상 발현 여부가 다를 수 있음 — 확인 후 필요하면 함께 수정.)

2. **수정 방향**: 영상이 페이지 전체 스크롤 높이를 실제로 덮도록 타일링한다. 제안 접근(다른
   대안이 더 낫다고 판단되면 그쪽으로 진행해도 됨, 단 이유를 완료 기록에 남길 것):
   - 같은 `src`의 `<video>` 엘리먼트를 세로로 필요한 만큼 반복 배치하는 **공용 클라이언트
     컴포넌트**(예: `BadgeBackgroundVideoLayer.tsx`, `lib/` 또는 공용 위치)를 새로 만들어
     배지·컬렉션 양쪽에서 재사용한다.
   - 타일 개수는 실제 콘텐츠 높이(`document.documentElement.scrollHeight`/컨테이너
     `ResizeObserver` 등)를 클라이언트에서 측정해 동적으로 계산 — 배지/컬렉션마다 본문 길이가
     다르므로 하드코딩 개수로는 부족한 경우가 생긴다. 초기 렌더(측정 전)에는 최소 1~2장으로
     시작해 레이아웃 시프트를 최소화하고, 측정 후 필요한 만큼 늘린다.
   - 각 타일은 동일 소스를 독립 재생하므로 타일 간 프레임 동기화가 완벽하지 않을 수 있다 —
     짧고 잔잔한 반복 애니메이션이라 육안상 어긋남이 크지 않을 것으로 예상되지만, 실제로
     확인해서 눈에 띄게 어긋나면(예: 모두 `autoPlay`로 거의 동시 시작하므로 큰 문제는 없을
     것으로 예상) 완료 기록에 관찰 결과를 남길 것.
   - **WebGL·Canvas 기반 접근은 쓰지 않는다** — 유저단은 `<video>` 태그로만 재생한다는 기존
     설계 원칙(20260818_002 이후 계속 유지) 그대로.
   - `prefers-reduced-motion`(display:none 처리), `pointerEvents:'none'`, iOS 자동재생 4종
     세트(autoPlay/muted/loop/playsInline) 등 기존에 지켜온 규칙은 타일마다 동일하게 적용.
   - poster 이미지(정지 프레임)의 CSS 배경 반복은 그대로 유지 — 영상 로드 전/실패 시, 그리고
     혹시 타일 계산이 부족해 영상이 안 덮는 최하단 여백이 아주 잠깐 생기더라도(리사이즈 중 등)
     자연스러운 폴백이 되도록.

3. **성능/자원 고려**: `<video>` 엘리먼트를 여러 개 동시 재생하면 디코딩 비용이 늘어난다.
   과도하게 긴 페이지(예: 배지가 아주 많은 컬렉션)에서 타일 수가 지나치게 많아지지 않도록
   상한(예: 8~10장)을 두고, 그 이상은 기존처럼 정지 이미지 폴백으로 남겨도 무방 — 실제
   서비스에서 이 상한을 넘는 페이지가 있는지 감안해서 값을 정할 것.

### UI/UX 관점

### 구현 내용 요약
- 제안 접근을 그대로 채택: 같은 `src`의 `<video>`를 세로로 필요한 만큼 반복 배치하는 공용
  클라이언트 컴포넌트 `BadgeBackgroundVideoTiles`를 신설해 배지 상세·컬렉션(아이템북) 상세
  양쪽 고정 배경 레이어에서 재사용하도록 교체했다.
- 각 타일은 `width:100%` + `aspectRatio:'1 / 2'`(430:860과 동일 비율) CSS로 크기를 잡고 정상
  문서 흐름으로 세로 스택되므로, 픽셀 단위 top 오프셋 계산 없이도 항상 원본 비율을 유지한다.
- 타일 수는 클라이언트에서 동적으로 계산한다. `(main)/layout.tsx`의 `<main class="overflow-y-auto">`
  가 실제 스크롤 컨테이너이고 문서(`document`) 자체는 스크롤하지 않는 앱 셸 구조라, 배경 레이어
  DOM에서 가장 가까운 `overflow-y: auto|scroll` 조상을 찾아 그 `scrollHeight`를 콘텐츠 실제
  높이로 사용하고(못 찾으면 `document.documentElement` 폴백), 타일 폭 기준 타일 1장의 높이로
  나눠 필요한 개수를 구한다. 초기 렌더(측정 전)는 `minTiles=2`로 시작해 레이아웃 시프트를
  최소화하고, 마운트 후 `requestAnimationFrame`으로 재계산한다.
- 콘텐츠 높이 변화 대응: 스크롤 컨테이너에 `ResizeObserver`(뷰포트/컨테이너 크기 변화),
  `MutationObserver`(childList+subtree, 콘텐츠 추가/제거)를 모두 걸어 재계산을 트리거하고,
  `window`의 `resize`·`load`(이미지 로딩 완료) 이벤트에서도 재계산한다.
- 타일 상한은 `maxTiles=10`(기본값)으로 뒀다 — 티켓이 제시한 8~10장 범위 중 상단값을 택했다.
  현재 서비스의 배지 상세·컬렉션 상세는 슬롯 그리드가 있어도 일반적으로 이 상한을 넘길 만큼
  길지 않다(가장 긴 케이스인 대형 컬렉션 슬롯 그리드도 10 × 860px ≈ 8600px보다 훨씬 짧음).

  남는다(설계상 의도된 동작 — 배경 레이어의 poster용 정적 이미지가 그대로 깔려 있어 자연스럽다).
- 기존 규칙 유지 확인: iOS 자동재생 4종 세트(autoPlay/muted/loop/playsInline), `prefers-reduced-
  motion`(globals.css `.badge-background-video` 클래스 재사용, 타일마다 동일 적용),
  `pointerEvents:'none'`(레이어·컨테이너·영상 전부) 모두 타일마다 동일하게 적용했다.
- 각 타일이 같은 `src`로 독립 재생돼 프레임 동기화가 완벽하지 않을 수 있다는 점은 티켓에서도

### 게이트 리뷰 FAIL 수정 (2차)
- **FAIL 사유**: 배경 레이어는 `position:fixed, top:0, bottom:0, overflow:hidden`이라 항상
  뷰포트 높이에 고정되고 그 이상은 영구히 잘려 절대 보이지 않는다. 그런데 1차 구현은 타일 개수를
  스크롤 컨테이너의 `scrollHeight`(페이지 전체 콘텐츠 길이, 보통 수천 px)로 계산해, 실제로는
  앞쪽 1~2장만 보이는데도 최대 10개의 `<video>`를 동시 생성·autoPlay·디코딩하는 리소스 낭비를
  만들었다.
- **수정 내용**: `BadgeBackgroundVideoTiles.tsx`의 타일 수 계산 기준을 "스크롤 컨테이너의
  `scrollHeight`"에서 "배경 레이어 자신의 실제 렌더 높이"로 바꿨다. 이 컴포넌트의 루트 div는
  배경 레이어(`overflow:hidden`인 부모)의 직계 자식이므로, `el.parentElement.clientHeight`
  (= 뷰포트 높이)를 기준으로 삼는다. 부모를 못 찾는 예외적인 경우에만 `window.innerHeight`로
  폴백한다.
  - `findScrollContainer` 헬퍼와 `MutationObserver`(콘텐츠 DOM 변경 감지)는 배경 레이어의
    렌더 높이와 무관해 완전히 제거했다. `ResizeObserver`는 유지하되 관찰 대상을 스크롤
    컨테이너가 아니라 배경 레이어(부모) 자신으로 바꿨고, `window`의 `resize`·
    `orientationchange`(회전 시 뷰포트 높이 변화 대응)에서 재계산한다. `window`의 `load`
    이벤트는 콘텐츠 이미지 로딩과 관련된 것이라 더 이상 뷰포트 높이 변화와 무관해 제거했다.
  - `maxTiles` 상한을 10 → 4로 낮췄다. 뷰포트 높이는 기기별로 달라도 보통 수백~2000px
    이내이므로(타일 1장 높이 = 타일 폭 × 2, 예: 폭 375px 기준 타일 높이 ≈ 750px), 필요한
    타일 수는 대략 2~4장 수준으로 재계산된다 — 티켓이 예상한 범위와 일치.
  - `minTiles` 기본값(2)은 그대로 유지 — 초기 렌더(측정 전) 레이아웃 시프트 최소화 목적은
    변함없다.
- **인코더 기본값(430×430) 변경**: 사용자가 제안한 개선 아이디어(바킹 기본 타일을 정적 이미지
  패턴과 동일하게 430×430·1타일로 줄이는 것)는 이번 FAIL 수정의 필수 범위가 아니고, 기존에
  이미 구워진 배지/컬렉션 영상(860 그대로)에는 소급 적용되지 않아 재굽기 전까지 두 가지 타일
  크기(430×430 신규분, 430×860 기존분)가 혼재하게 된다. 이 컴포넌트는 `aspectRatio` prop으로
  이미 두 비율 모두 대응 가능하도록 설계되어 있어(하드코딩 없음) 인코더 기본값을 나중에 바꿔도
  이 컴포넌트 쪽 추가 수정은 필요 없다. 시간 관계상 이번 티켓에서는 측정 기준 수정(필수 범위)만
  완료하고, 인코더 기본값 변경은 범위 밖으로 남겨 별도 판단이 필요하면 새 티켓으로 분리할 것을
  제안한다.
