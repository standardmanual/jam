# [UI] 모듈러 컴포넌트 실연결 파일럿 — MissionDetailClient → ProgressBar

## 배경 / 문제 정의

티켓 20260820_003으로 **토큰**(색상·반경·모션·스페이싱·타이포)은 `globals.css`가
`design-system/tokens/*.css`를 실제 `@import`하도록 연결했다. 아직 남은 건
**컴포넌트**(`design-system/components/*`)— `tsconfig.json`에 `@ds/*` alias는 있지만
`jam-web/src/` 어디에서도 이 alias로 실제 React 컴포넌트를 import하는 곳이 0건이다.
MODULAR는 지금까지 Storybook 카탈로그로만 존재했다.

이 티켓은 그 첫 실연결 사례(파일럿)를 만든다 — 성공하면 이후 컴포넌트를 화면 하나씩
순차 전환하는 정식 절차가 확립된다.

## 파일럿 대상 선정 근거

`MissionDetailClient.tsx`의 진행도 바(`jam-web/src/app/(main)/missions/[id]/MissionDetailClient.tsx`)를
`design-system/components/feedback/ProgressBar.jsx`(티켓 20260820_001에서 신설, 이미 이 파일의
실제 마크업을 캐노니컬 스펙으로 삼아 만들어짐)로 교체한다. 이유:
- 캐노니컬 스펙의 출처 자체가 이 파일이라 회귀 위험이 가장 낮다.
- 이미 토큰(`var(--color-primary)`, `bg-border`, `var(--radius-pill)`)을 올바르게 쓰고 있어
  티켓 003 연결과의 상호작용도 이미 검증된 조합이다.
- `labelType="percent"` + `labelPosition="top"` 조합(퍼센트를 바 위 우측 정렬)이 이미
  `ProgressBar`에 구현돼 있어 별도 컴포넌트 확장 없이 바로 대응 가능.

## 상세 요구사항

### 서비스/코드베이스 관점

1. **빌드 호환성 사전 확인**: `@ds/components/feedback/ProgressBar`를 `.tsx` 파일에서
   import했을 때 Next.js(Turbopack) 빌드·타입체크·ESLint가 정상 통과하는지 먼저 확인한다.
   - `ProgressBar.jsx` + `ProgressBar.d.ts` 페어가 TypeScript에 타입으로 인식되는지
   - 문제가 있으면(예: 모듈 해석 실패, JSX 파일 특수 처리 필요 등) 원인을 정확히 파악해
     해결하거나, 해결 불가 시 알려진 제약으로 HALT 보고
2. **교체**: `MissionDetailClient.tsx`의 인라인 진행도 바 마크업(`div` 2단 구조)을
   `<ProgressBar current={...} total={...} labelType="percent" labelPosition="top" />`
   (또는 실제 API에 맞는 prop)로 교체. 스트릭형(`n일 중 m일`)과 수치형(`현재/목표 단위`) 두
   변형 모두 있으므로 각각 대응.
3. **동작 동일성 확인**: 교체 전후로 렌더링 결과(트랙/필 색상, 높이, radius, 애니메이션
   전환)가 시각적으로 동일해야 한다 — 이 컴포넌트가 이미 그 마크업을 그대로 캐노니컬화한
   것이므로 완전히 동일해야 정상.
4. **패턴 문서화**: 이 파일럿에서 확인된 "서비스 코드가 `@ds/*` 컴포넌트를 import하는 올바른
   방법"을 완료 기록에 구체적으로 남긴다 — 후속 컴포넌트 전환 작업이 이 기록을 참고해
   반복 조사 없이 바로 시작할 수 있도록.

### UI/UX 관점

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

`MissionDetailClient.tsx`에서 `@ds/components/feedback/ProgressBar`를 최초로 실제 import해
스트릭형·수치형 진행도 바 2곳의 트랙+필 마크업(`div` 2단 구조: `bg-border` 트랙 div 안에
`width:%` 필 div)을 `<ProgressBar percent={...} />`로 교체했다.

**교체 범위를 "순수 바"로 한정한 이유**: 요구사항 3번 "동작 동일성(시각적으로 완전히 동일)"을
지키려면, 각 변형 위에 있던 라벨 행(좌측 커스텀 텍스트 `"N일 중 M일"`/`"3.2km / 5km"` + 우측
퍼센트, `items-baseline justify-between`, `gap-3`=12px)까지 함께 `ProgressBar`의
`labelType="percent" labelPosition="top"`으로 교체하면 시각이 달라진다:
- `ProgressBar`의 `top` 라벨은 퍼센트만 우측 정렬로 렌더링하고 좌측 커스텀 텍스트 슬롯이 없다.
- `ProgressBar`의 라벨-바 간격은 `var(--spacing-8)`=8px로, 기존 `gap-3`(12px)와 다르다.

따라서 라벨 행은 손대지 않고 그대로 유지했고(퍼센트 표시가 이미 라벨 행에 있으므로 중복도
없음), "인라인 진행도 바 마크업(div 2단 구조)"만 리터럴하게 `ProgressBar`(labelType 기본값
`'none'`, height 기본값 8px)로 교체했다. `trackColor`/`color`/`radius` 기본값이 기존 인라인
마크업과 완전히 동일해 prop 오버라이드가 필요 없었다.

**애니메이션 이징 차이 1건 확인** — alerts 참고.

### 빌드 호환성 스파이크 결과

`.jsx` + `.d.ts` 페어를 `.tsx`에서 `@ds/*` alias로 import하는 것 자체는 **문제없이 작동**했다.
- `npx tsc --noEmit`: 변경 전/후 에러 라인 수 동일(400줄, 모두 기존 테스트 파일의 vitest 전역
  타입 누락 문제로 이 티켓과 무관 — `git stash`로 비교 검증). `MissionDetailClient`/`ProgressBar`
  관련 에러 0건.
- `npx eslint "src/app/(main)/missions/[id]/MissionDetailClient.tsx"`: 통과, 경고 0건.
- `npm run build` (Next.js/Turbopack 프로덕션 빌드): 전체 통과, `/missions/[id]` 라우트 정상
  컴파일. import 관련 에러/경고 없음.

### "서비스가 @ds/* 컴포넌트를 import하는 올바른 방법" (후속 전환 작업 참고용)

```tsx
import { ProgressBar } from '@ds/components/feedback/ProgressBar'
```

- 그대로 이렇게 쓰면 된다. **확장자를 붙이지 않는다** (`ProgressBar.jsx`가 아니라
  `ProgressBar`) — TypeScript가 `moduleResolution: "bundler"` 하에서 같은 디렉터리의
  `ProgressBar.d.ts`를 타입 소스로, 번들러(Turbopack)가 `ProgressBar.jsx`를 런타임 소스로
  각각 알아서 매칭한다. 별도 설정 변경이나 `// @ts-ignore` 없이 그대로 동작했다.
  - 전제조건: `tsconfig.json`에 이미 있는 `"allowJs": true` + `"@ds/*": ["./design-system/*"]`
    두 설정만 있으면 되고, 이번 티켓에서 이 둘을 변경할 필요는 없었다(기존 설정으로 충분).
- MODULAR 컴포넌트는 인라인 `style` 객체로 토큰(`var(--color-primary)` 등)을 직접 참조하는
  패턴이라(className이 아니라) 서비스 쪽 Tailwind 유틸리티 클래스와 섞어 써도 충돌 없다.
- prop은 `.d.ts`의 JSDoc 주석을 그대로 신뢰할 수 있다 — 에디터 자동완성/타입체크에 정상 반영됨.
