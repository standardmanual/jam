# [research] 모듈러-서비스 전체 연결 + 소스코드-스토리북-스테이징/프로덕션 동기화 파이프라인 조사

## 배경 / 문제 정의

티켓 013(2026-08-19), 003~006(2026-08-20)으로 다음까지 완료됐다:
- **토큰**: `globals.css`가 `design-system/tokens/*.css` 전체를 `@import` — 완전 연결
- **컴포넌트**: 22개 중 `ProgressBar` 1개만 서비스가 실제 `@ds/*` import — 21개는 여전히 미연결

사용자의 원래 목표는 "모듈러 전체"와 서비스의 연결이었다. 이 티켓은 코드 변경 없이,
① 나머지 21개 컴포넌트 각각의 실제 상태를 전수조사하고 ② 향후 "소스코드 변경 → 스토리북 →
스테이징/프로덕션"이 자동으로 동기화되는 파이프라인을 어떻게 구축할지 설계안을 정리한다.
실제 구현은 이 조사 결과를 바탕으로 후속 티켓에서 진행한다.

## 조사 범위

### 1. 22개 모듈러 컴포넌트 전수 상태 분류

`design-system/_ds_manifest.json`의 컴포넌트 각각에 대해:
- 서비스(`jam-web/src/`)에 이름이 같거나 대응하는 자체 구현이 있는가 (있다면 파일 경로)
- 있다면 마크업/스타일이 지금 모듈러 캐노니컬 스펙과 얼마나 다른가 (완전 동일/부분 다름/전혀 다름)
- 없다면 서비스에 아직 그 UI 개념 자체가 없는 것인지, 이미 다른 방식으로 흩어져 구현된 것인지
- 전환 리스크 추정(낮음/중간/높음) — 티켓 004~006에서 썼던 기준(캐노니컬 스펙 출처가 그 파일
  자신인지, 이미 토큰을 쓰고 있는지, 호출처가 몇 곳인지)을 그대로 적용

결과를 표로 정리해 우선순위(리스크 낮은 순)를 매긴다.

### 2. "연결 파이프라인" 설계안

사용자가 요청한 "추후 소스코드-스토리북-스테이징/프로덕션의 상호 연결성을 동기화"를
구체적인 메커니즘으로 제안한다. 최소한 다음을 조사·검토:

- **회귀 방지**: 모듈러 컴포넌트/토큰이 바뀌었는데 서비스 호출부가 여전히 구버전 값을
  하드코딩하고 있는 상태(드리프트)를 자동으로 감지할 방법이 있는가?
  - 예: `--radius-md` 삭제됐는데 서비스가 계속 참조하던 사례(티켓 002)가 재발하지 않게
    하려면 무엇이 필요한가 — lint 규칙, CI 스크립트, `.githooks/pre-commit` 확장 등
- **Storybook ↔ 서비스 소스 일치성**: `_ds_manifest.json`이 이미 실제 토큰값과 어긋난 전례가
  있었다(티켓 003 리뷰에서 발견) — 매니페스트를 소스에서 자동 생성/검증하는 방법이 있는가?
- **신규 컴포넌트 확장 시 서비스 반영 강제 여부**: `ds` 유형 작업(1.5/1.6단계)이 "재사용 판정"은
  강제하지만, 재사용하기로 결정된 뒤 실제로 서비스가 그 컴포넌트를 쓰도록 만드는 것까지는
  강제하지 않는다 — 이 갭을 메울 절차가 필요한지 검토.
- **배포 파이프라인 자체 재확인**: 티켓 1.6단계에 이미 기록된 대로 스토리북은 staging
  머지 시 자동 배포된다 — 이 부분은 이미 해결된 것으로 보고 재검증만.

### 3. 산출물

- 21개 컴포넌트 상태표 + 전환 우선순위
- "연결 파이프라인" 구체적 제안(도구/스크립트/훅 후보, 각각의 트레이드오프)
- 다음 착수 순서 제안(예: 리스크 낮은 컴포넌트부터 티켓 020260820_004~006과 같은 패턴 반복)

## 완료 기록 *(작업 완료 후 작성)*

### 조사 결과 요약

**컴포넌트 총 개수 정정**: `_ds_manifest.json` 기준 24개(ProgressBar 포함). ProgressBar 1개는
완료, 나머지 23개 중 서비스에 이름이 같은 대응 파일이 있는 건 15개, 없는 건 8개.

**토큰과 컴포넌트는 연결 상태가 다르다**: 토큰(색상·반경·모션·스페이싱·타이포)은 티켓 003으로
이미 `@import` 완전 연결됐다. 컴포넌트(React 마크업/구조/prop)는 ProgressBar 1개만 연결—
`grep -rln "@ds/" src` 결과 정확히 6개 파일, 전부 ProgressBar용.

**분류 결과** (근거는 조사 원본 표 참고):

| 분류 | 의미 | 컴포넌트 |
|---|---|---|
| **A (즉시 전환 가능)** | 토큰 이미 일치·캐노니컬 스펙이 서비스 기준으로 만들어짐·호출처 적음 | RarityBadge(서비스 파일명 `Badge.tsx`, 토큰 100%일치), WanderingEyesLoader(캐노니컬 자체가 "서비스 1:1 재현"), CollectionGridCard(이미 ProgressBar 부분연결, 호출처 2곳) |
| **B (전환 시 시각 변경 수반)** | 색상은 토큰 공유하나 크기/타이포/구조 실제로 다름 | Card(tone 1종으로 축소), TopNav(타이틀 폰트 24px→16px 등 실제로 다름), BadgeGridCard, ListRowCard |
| **C (리스크 높음)** | 구조/API가 아예 다르거나 서비스 로직과 깊게 결합, 이미 독자 진화 중 | TabBar(라우팅 로직 결합, "두 파일 수동 동기화" 관행 이미 존재), BottomSheet(기능 격차 큼), SlidingTabs(서비스가 이미 성숙한 자체 표준), Toast(아키텍처 자체 다름 - controlled prop vs context queue), Button(variant 체계 완전히 다름, 서비스가 최신 디자인 가이드로 독자 진화 중) |
| **D (서비스 대응 없음/죽은 코드)** | 서비스에 그 UI 개념이 아직 산발적이거나 없음 | Skeleton(CSS 클래스로 산발 구현), EmptyState(화면마다 다른 로컬 재정의), IconButton(매번 인라인), ModalToast/ShapeTag/BadgeFrame(대응 0건), **Checkbox/Input/Select/Textarea(서비스 전체에서 import 0건 — 죽은 코드)**, Accordion(admin 전용, 정책상 비대상) |

**부가 발견**: `src/components/ui/`에 `CollectionGridCard 2.tsx` 등 iCloud 동기화 충돌로 보이는
중복 파일이 다시 나타났다(세션 초반 815개 삭제했던 것과 같은 패턴). 이번 조사 범위 밖이라 손대지
않음 — 재발 여부 확인 필요.

### 연결 파이프라인 설계안

1. **드리프트 감지(가장 시급)**: `.githooks/pre-commit`에 이미 "모듈러 컴포넌트 변경 시 Story
   동반 확인"이 있지만 `EXIT_ON_MISSING=0`이라 경고만 하고 커밋을 막지 않는다. 같은 스크립트에
   조건을 추가하는 방식으로 확장 가능(신규 인프라 불필요) — 우선순위:
   - `--radius-md` 삭제 후에도 서비스가 참조하던 사례(티켓 002) 재발 방지: 토큰 파일에서 삭제된
     이름을 서비스가 여전히 참조하면 pre-commit이 fail하도록.
2. **`_ds_manifest.json` 신뢰성**: 손으로 유지되는 스냅샷이라 이미 한 번 실제 토큰값과 어긋난
   전례가 있다(티켓 003 리뷰). `npm run build`(또는 `build-storybook`) 이전에 소스 파일을
   스캔해 자동 생성하는 스크립트로 교체하는 게 근본 해결책 — 이번 조사 범위에서는 설계만,
   구현은 후속 티켓.
3. **CI 부재**: GitHub Actions 등 CI 파이프라인이 전혀 없다. `pre-commit`/`pre-push` 훅과
   로컬 `npm run build`가 유일한 게이트 — lint/test는 CI에 안 걸려있고 강제되지 않는다.
   당장 CI 구축까지는 이번 조사 범위 밖이나, 연결 파이프라인의 최종 형태를 생각하면 필요.
4. **신규 컴포넌트 서비스 반영 강제 갭**: `ds` 유형 1.5/1.6단계는 "재사용 판정"까지는 강제하지만
   재사용 결정 이후 실제 연결까지는 강제하지 않는다 — 이 갭은 프로세스(매 `ds` 티켓 완료 시
   "이 컴포넌트를 실제로 쓸 서비스 호출처가 있는가"를 완료 기록에 명시하도록 1.6단계에 이미
   반영된 규칙으로 충분해 보이며, 추가 자동화는 불필요 판단.

### 다음 단계 제안

리스크 낮은 순서로 티켓 004~006과 같은 패턴(파일럿 → 전환 → staging 확인)을 반복:
1. **A 그룹부터**: RarityBadge, WanderingEyesLoader, CollectionGridCard(나머지 프레임 부분)
2. **B 그룹**(시각 변경 고지 필요): Card, TopNav, BadgeGridCard, ListRowCard
3. **C 그룹**은 단순 스왑이 아니라 컴포넌트 자체 재설계가 선행돼야 함 — 별도 설계 티켓 필요
4. **D 그룹**은 "전환"이 아니라 "신규 도입 여부 판단" — Checkbox/Input/Select/Textarea는 죽은
   코드이므로 삭제 여부부터 사용자 확인 필요
