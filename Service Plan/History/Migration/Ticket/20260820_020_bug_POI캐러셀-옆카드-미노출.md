# [bug] POI 캐러셀 옆 카드 미노출 (풀폭 슬라이드로 캐러셀처럼 안 보임)

## 배경 / 문제 정의
티켓 20260820_018로 프로덕션에 배포된 드랍 POI 캐러셀 모달이 실사용에서 "캐러셀로 안 보인다"는
사용자 피드백을 받았다. 원인 확인: [Carousel.jsx](../../../../jam-web/design-system/components/navigation/Carousel.jsx)의
슬라이드가 `flex: '0 0 100%', minWidth: '100%'`(카드 1개 = 컨테이너 전체 폭)로 구현되어 있어,
옆 카드가 화면에 전혀 보이지 않고 스와이프해야만 다음 카드가 나타난다.
[PoiCarouselModal.tsx](../../../../jam-web/src/components/PoiCarouselModal.tsx)의 `PoiCard`에는 비활성
카드용 반투명·축소 스타일(`opacity: 0.55`, `scale: 0.92`)이 이미 있으나, 컨테이너가 카드를
풀폭으로 감춰버려서 이 스타일이 노출될 기회 자체가 없다. 티켓 018의 원 요구사항("모달
오른쪽에 캐러셀 방식으로 반경 내 다른 POI가 보이도록")과 어긋난 상태다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `Carousel.jsx`의 슬라이드 폭을 100%보다 작게(예: 78~85%) 줄이고 카드 사이 gap을 둬서,
  중앙 카드 좌우로 다음/이전 카드가 부분적으로("peek") 보이도록 한다.
- `scroll-snap-align: center`는 유지하되, 컨테이너에 `scroll-padding`(좌우)을 적용해 첫/마지막
  실제 카드도 중앙 정렬되도록 한다.
- 기존 무한 루프(클론 슬라이드 트릭), 활성 인덱스 판정(`handleScroll`의 폭 기반 위치 계산)이
  슬라이드 폭 변경에 맞춰 정상 동작하는지 재검증한다(`el.clientWidth` 기준 로직이 카드 폭이 아닌
  "한 스텝의 스크롤 거리"를 의미하도록 일관되게 조정 필요 — 슬라이드 폭이 변경되면 이 스텝
  거리도 같이 바뀌어야 함).
- `PoiCarouselModal.tsx`의 좌우 패딩(`px-[var(--spacing-16)]`)이 peek 레이아웃과 시각적으로
  자연스럽게 맞는지 함께 확인한다.
- 기존 하단 정렬(`alignItems:'flex-end'`), 카드 활성/비활성 트랜지션(opacity/scale)은 유지한다.

### UI/UX 관점
- peek 폭·gap 값은 MODULAR spacing 토큰(`--spacing-*`) 기준으로 정한다.

## 구현 계획
1. `Carousel.jsx` 슬라이드 스타일 및 스크롤 위치 계산 로직을 peek 레이아웃에 맞게 수정
2. `Carousel.stories.tsx`에 peek 레이아웃 반영 확인

4. tsc/eslint/build 검증 후 소스코드 → 스테이징 → 프로덕션까지 반영 (긴급 수정, staging 확인 후 바로 승격)

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
`Carousel.jsx`의 슬라이드 레이아웃을 풀폭(`flex:'0 0 100%'`)에서 peek 레이아웃(`flex:'0 0 80%'`,
좌우 여백 각 10%)으로 변경했다. 컨테이너에 `paddingLeft/Right: '10%'` + `scrollPaddingLeft/Right: '10%'`
+ `gap: 'var(--spacing-16)'`를 적용해, 첫/마지막 실제 카드도 정확히 중앙까지 스크롤되고 카드
사이에 간격이 생기도록 했다.

슬라이드 폭이 더 이상 컨테이너 폭(100%)과 같지 않으므로, 기존 `el.clientWidth`를 "한 스텝 거리"로
가정하던 위치 계산 로직을 실제 렌더된 슬라이드 DOM 요소 기준으로 다시 작성했다:

#### 재시도(게이트 리뷰 FAIL 대응, 2026-08-20)
1차 구현이 게이트 리뷰에서 FAIL했다. 원인: 컨테이너에 `paddingLeft/Right:10%`(box-sizing:
border-box)를 걸어 콘텐츠 박스를 80%로 줄인 뒤, 그 안의 슬라이드에 다시 `flex:'0 0 80%'`를
적용했다. CSS 스펙상 flex-basis 퍼센트는 부모의 **콘텐츠 박스**(패딩 제외) 기준으로 해석되므로
두 퍼센트가 곱연산되어(0.8×0.8) 실제 렌더 결과는 컨테이너 폭의 64%가 됐다.

수정 방법(티켓 지침 (a)): 컨테이너 padding을 제거하고, 슬라이드의 `flex:'0 0 80%'`만 유지했다.
첫/마지막 실제 카드 중앙 정렬은 `scroll-padding`(좌우 10%) + 무한 루프 클론 슬라이드(앞뒤에
항상 존재하는 여분 슬라이드가 여백 역할을 겸함)로 처리했다 — 클론 슬라이드가 스크롤 가능한
여유 공간을 제공하므로 별도 컨테이너 padding 없이도 첫/마지막 실카드가 정확히 중앙까지
스크롤된다.

이 과정에서 컨테이너에 임시로 `justifyContent:'center'`를 추가했다가(아이템이 1개뿐이라
overflow가 없을 때 중앙 배치하려는 의도) Playwright 실측으로 새로운 버그를 발견했다: 아이템이
여러 개라 overflow가 발생하는 경우 `justifyContent:'center'`를 쓰면 브라우저가 flex 라인
전체를 중앙 정렬하면서 콘텐츠 앞부분을 **음수 offsetLeft**로 밀어내는데, `scrollLeft`는 0
미만으로 내려갈 수 없으므로 그 영역은 스크롤로 절대 도달할 수 없는 상태가 된다(고전적인
"overflow + justify-content:center" 함정). 이를 `justifyContent: n <= 1 ? 'center' : 'flex-start'`로
수정해, 스크롤이 필요 없는 단일 아이템일 때만 중앙 배치하고 다중 아이템(overflow 있음)일 때는
반드시 `flex-start`를 유지하도록 했다.

**Playwright 실측 결과** (`storybook build` 대신 `storybook dev` 로컬 서버 기동 후
`modular-navigation-carousel--center-focus-infinite-loop` 스토리에서 측정, 뷰포트 800×900):
- 슬라이드 실제 렌더 폭 / 컨테이너 폭 = 640px / 800px = **정확히 0.800 (80%)** — 요구 범위
  78~85% 충족, 곱연산 없음 확인.
- 활성(중앙) 슬라이드 중심과 컨테이너 중심의 픽셀 차이 = **0px** — 완전히 중앙 정렬됨
  (`scrollLeft=576`, target 계산값 `slideEl.offsetLeft(656) - (clientWidth(800)-slideWidth(640))/2 = 576`과 일치).
- `SingleItem` 스토리(아이템 1개)에서도 폭 0.800(640/800), 중심 diff 0px 확인 — justifyContent
  분기가 정상 동작.
- 키보드(ArrowRight) 5회 연타로 무한 루프 끝까지 순회 → 마지막 카드에서 다시 첫 카드로
  자연스럽게 되돌아가는지 확인: 마지막 카드(`5/5`)에서 `scrollLeft=3200`(target과 일치), 첫
  카드로 순간 이동(클론 안착) 후 다시 `1/5` 상태에서 `scrollLeft=576`으로 정확히 복귀 —
  회귀 없음 확인.

슬라이드 폭이 컨테이너 폭과 달라지므로, 기존 `el.clientWidth`를 "한 스텝 거리"로 가정하던
위치 계산 로직을 실제 렌더된 슬라이드 DOM 요소 기준으로 다시 작성했다(1차 구현에서 이미 반영,
재시도에서도 변경 없이 유지):
- 각 슬라이드에 콜백 ref(`registerSlideRef`)를 달아 `extended` 배열의 위치(pos)별 실제
  DOM 요소를 `slideElsRef`(Map)에 보관한다.
- `scrollToPos(pos, behavior)`: 목표 슬라이드의 `offsetLeft`와 `offsetWidth`, 컨테이너의
  `clientWidth`로 "그 슬라이드를 뷰포트 중앙에 오게 하는 scrollLeft"를 계산해 `scrollTo`한다.
  기존에는 `extPosition * clientWidth`로 계산했던 부분(activeIndex 변경 시 이동, 클론 슬라이드
  안착 시 순간 이동)을 모두 이 함수로 교체했다.
- `handleScroll`의 위치 판정도 "스크롤 뷰포트 중앙에 가장 가까운 슬라이드"를 실측 `offsetLeft +
  offsetWidth/2`로 찾는 방식으로 교체했다(폭 기반 나눗셈 대신 최근접 슬라이드 탐색).

무한 루프(클론 슬라이드 트릭), 3개 단위 windowing(`PoiCarouselModal.tsx`, 미변경), 지도 포커싱
연동(`activeIndex` 변경 시 `onCenterChange` 호출, 미변경)에는 로직 변경이 없다 — 이 값들은
`Carousel`이 아닌 `PoiCarouselModal`이 관리한다. 하단 정렬(`alignItems:'flex-end'`)도 그대로 유지.

`Carousel.stories.tsx`의 데모 카드 스타일에서 고정 `width:280`/`margin:'0 16px'`를 제거하고
`width:'100%', maxWidth:280, margin:'0 auto'`로 바꿨다 — 슬라이드 폭·간격을 이제 `Carousel`
자체가 관리하므로 데모 카드가 이를 다시 지정하면 이중으로 좁아진다.

`PoiCarouselModal.tsx`의 `px-[var(--spacing-16)]` 래퍼 패딩은 peek 레이아웃과 시각적으로
자연스럽게 맞아 별도 수정하지 않았다(Carousel 자체 인셋 10% + 모달 좌우 패딩이 중첩되어
카드 바깥 여백이 다소 넉넉해지는 정도).

### 주요 의사결정 / 핵심 메모
- peek 슬라이드 폭은 78~85% 권장 범위 내에서 80%로 결정(좌우 인셋 각 10%) — 중앙 카드가
  충분히 크게 보이면서도 옆 카드가 명확히 "다음 카드가 있다"는 힌트를 주는 균형점.
- 위치 판정을 폭 기반 나눗셈에서 실측 DOM 최근접 탐색으로 바꾼 것은 peek 레이아웃에서 슬라이드
  폭이 컨테이너 폭과 달라지는 문제를 근본적으로 해결하기 위함이며, 슬라이드 폭 상수가 향후
  다시 바뀌어도(반응형 등) 로직 변경 없이 자동으로 맞는다.
- (재시도) padding + flex-basis 퍼센트 곱연산 문제를 해결하며 컨테이너 padding을 제거했는데,
  이 과정에서 발견한 "overflow + justify-content:center → 콘텐츠 앞부분 도달 불가" 함정을
  `n <= 1`일 때만 center를 적용하는 조건부 분기로 막았다. 이 분기가 없으면 아이템이 1개일
  때는 왼쪽 정렬로 보이는 미세한 시각적 결함이 남았을 것이나, 다중 아이템(실사용 케이스)에서는
  치명적 버그(콘텐츠 절반 접근 불가)로 이어질 뻔했다 — Playwright 실측 없이 코드 리뷰만
  했다면 놓쳤을 문제.
