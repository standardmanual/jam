# [Admin] 컬렉션 비활성화 → 소속 아이템배지 연쇄 회수

## 배경 / 문제 정의
어드민 컬렉션 관리 화면(`/admin/itembooks`)에서 컬렉션을 비활성화할 때, 지금은 신규 드랍/완성
판정만 막힐 뿐(기존 `item_books.is_active`) 이미 등록된 아이템배지와 유저가 이미 획득한 배지는
그대로 노출된다. 컬렉션을 완전히 내려야 하는 상황(정책 변경·컨텐츠 회수 등)에서 소속 배지까지
한 번에 비활성화하고, 이미 획득한 유저에게서도 회수하는 기능이 필요하다.

**핵심 제약**: "회수"는 물리적 삭제가 아니다 — 내부 시스템상의 획득 이력(`inventory_items`,
`user_activity_badges`, `user_poi_badge_earns` 등)은 그대로 남기고, 유저에게 노출되는 화면에서만
안 보이게 한다.

## 조사 결과 — 신규 스키마 변경 불필요
1. `item_books.is_active`(BOOLEAN, `016_itembooks_faction.sql`) — **이미 존재**. 드랍 엔진
   (`src/lib/drop-engine/index.ts:185`)·완성 판정(`src/lib/itembook/checker.ts:31`)이 이미
   `is_active=true`인 컬렉션만 대상으로 삼는다.
2. `badges.deleted_at`(TIMESTAMPTZ, `060_badge_soft_delete.sql`) — **이미 존재하고, 정확히
   이번 요구사항과 같은 목적으로 이미 쓰이고 있다**. `src/app/api/admin/badges/[id]/route.ts`
   DELETE 핸들러가 배지 1개를 소프트 삭제할 때 이미 `deleted_at`만 세팅하고 원본 행은
   보존한다(주석: "이미 발급된 유저의 이력은 FK 그대로 참조, 하드 삭제 시 위반/이력 소실").
   서비스 화면 전반(`inventory/page.tsx`, `badges/page.tsx`, `[username]/page.tsx` 등)과
   발급/드랍 로직(`badge-engine`, `itembook/checker`, `ambient-drop`, `drop-engine`, `combine`)이
   이미 `badges.deleted_at IS NULL`로 필터링 중.
3. **결론**: "컬렉션 비활성화 → 소속 배지 연쇄 비활성화"는 `item_books.is_active = false`로
   바꾸면서, `badges.item_book_id = 해당 컬렉션 AND deleted_at IS NULL`인 배지들에
   `deleted_at = now()`를 일괄 세팅하면 된다. **DB 마이그레이션 불필요** — 순수 애플리케이션
   로직(API route 확장)으로 구현.
4. **재활성화 시 배지 자동 복구는 하지 않는다(중요 설계 결정)**: `item_books.is_active`를
   다시 켜도 컬렉션 비활성화로 인해 `deleted_at`이 세팅된 배지들을 자동으로 되살리지 않는다.
   이유: 컬렉션 비활성화 *이전에* 개별 사유로 이미 소프트 삭제됐던 배지와, 이번 컬렉션
   비활성화로 인해 새로 소프트 삭제된 배지를 구분할 안전한 방법이 없다(별도 컬럼을 추가하지
   않는 한). 재활성화 시 되살릴 배지가 있다면 어드민이 배지 목록에서 개별적으로 재활성화한다
   (배지 소프트 삭제/복구 API가 이미 있다면 재사용, 없다면 이번 범위 밖).

## 상세 요구사항

### 서비스/코드베이스 관점
- **API**: `src/app/api/admin/itembooks/[id]/route.ts`의 `PUT` 핸들러를 확장한다.
  - 업데이트 전 현재 `is_active` 값을 조회해 `true → false` 전환인지 판별.
  - 전환이면 하나의 트랜잭션처럼 처리(Supabase는 멀티스테이트먼트 트랜잭션 API가 제한적이므로
    "① item_books.is_active=false 업데이트 → ② badges 일괄 소프트 삭제" 순서로 순차 실행하고,
    ②가 실패하면 최소한 에러를 명확히 반환해 어드민이 재시도할 수 있게 한다).
  - `badges` 일괄 업데이트: `.update({ deleted_at: now }).eq('item_book_id', id).is('deleted_at', null)`
  - `false → true` 전환(재활성화)은 `item_books.is_active`만 갱신, 배지는 건드리지 않는다
    (조사 결과 4번 참고).
- **영향 범위 조회 API 신규 추가** (확인 모달에 표시할 숫자용):
  `GET /api/admin/itembooks/[id]/deactivation-impact` — 응답: 소속 활성 배지 수, 그 배지들을
  보유한 distinct 유저 수(`inventory_items`/`user_activity_badges`/`user_poi_badge_earns` 중
  해당 배지 타입에 맞는 테이블에서 `badge_id IN (...)`로 distinct `user_id`/`holder_user_id`
  집계 — 배지 타입별로 어느 테이블을 봐야 하는지는 `badges.type` 컬럼과 기존 조회 로직
  (`src/lib/badge-engine/`, `src/app/(main)/inventory/page.tsx` 등)의 패턴을 따른다).
  이미 어드민 인증(`getAdminUser`)이 되어 있어야 호출 가능.
- **UI**: `src/app/admin/itembooks/ItemBookForm.tsx`(366~374행)의 네이티브
  `<input type="checkbox">` 활성화 토글을 **shadcn `Switch`**로 교체한다
  (`components/ui/switch.tsx`가 없으면 `npx shadcn add switch`로 추가 — 프로젝트 shadcn 설정은
  `components.json` 참조).
  - **켜짐 → 꺼짐으로 토글할 때만** 확인 모달을 띄운다(꺼짐 → 켜짐은 확인 없이 즉시 반영).
  - 확인 모달은 **shadcn `AlertDialog`**로 신규 추가(`components/ui/alert-dialog.tsx` —
    없으면 `npx shadcn add alert-dialog`). 모달 내용: 위 영향 범위 API 결과를 로딩 후 표시
    — "이 컬렉션을 비활성화하면 소속 아이템배지 N개가 함께 비활성화되고, 이미 획득한 유저
    M명에게서 회수됩니다. 계속하시겠습니까?" (정확한 문구는 UX Writing 가이드 참고, 아래
    UX Writing 섹션 참고). 모달을 취소하면 Switch는 다시 켜진 상태로 되돌아간다(폼 저장 전
    임시 상태이므로 API 호출 없이 로컬 상태만 되돌리면 됨).
  - 폼을 "저장" 버튼으로 제출하는 기존 흐름과의 관계: Switch를 끄는 시점에 바로
    비활성화하지 말고, 확인 모달에서 "계속"을 누르면 `isActive` 로컬 상태만 `false`로
    확정하고 실제 반영은 기존처럼 폼 "저장" 시 `PUT`으로 나간다(다른 필드 수정과 동일한
    저장 흐름 유지 — 저장 전까지는 이탈 가능). PUT 핸들러가 연쇄 회수를 수행한다.

### UI/UX 관점
- 어드민 화면은 MODULAR 적용 대상 아님(정책) — service-specific으로 구현.
- 확인 모달 문구는 `Service Plan/Specs/UX_WRITING_GUIDELINE.md`를 참고하되, 어드민 내부용이라
  사용자 노출 톤 요구사항은 완화 적용 가능. 다만 **[현상] → [영향 범위 숫자] → [확인/취소]**
  구조는 지켜서 실수로 대량 회수하는 사고를 막는다.
- 영향 범위 조회 중(API 응답 대기)에는 로딩 상태를 모달 안에 표시하고, 조회 실패 시 숫자
  없이 "영향 범위를 확인할 수 없습니다 — 신중히 진행하세요" 같은 안전 문구로 대체(조회
  실패가 진행 자체를 막지는 않되, 눈에 띄게 경고한다).

### 컨텐츠 관점
- 해당 없음 (기능 자체가 데이터 상태 전환 로직).

## 구현 계획
- 신규 DB 마이그레이션 없음 (조사 결과 참고).
- 수정: `src/app/api/admin/itembooks/[id]/route.ts`(PUT 확장), `ItemBookForm.tsx`(Switch+확인
  모달).
- 신규: `src/app/api/admin/itembooks/[id]/deactivation-impact/route.ts`(GET),
  `components/ui/switch.tsx`, `components/ui/alert-dialog.tsx`(shadcn 표준 추가).
- 회귀 위험: 기존에 `is_active`를 껐다 켰다 하며 드랍 엔진 필터링만 의존하던 운영 흐름이
  있다면(단순 껐다 켜기), 이번 변경으로 끌 때마다 배지가 대량 소프트 삭제되므로 **동작이
  달라진다** — 어드민이 명확히 인지하도록 확인 모달 문구가 핵심 안전장치다.
- `deactivation-impact` 조회 시 배지 타입(activity/item/poi)별로 이력 테이블이 다르므로,
  이 부분은 `src/lib/badge-engine/`나 기존 어드민 통계 코드(`src/lib/admin/`)에 이미 유사
  집계 로직이 있는지 먼저 찾아보고 재사용을 우선한다(중복 구현 방지).

## 구현 결과 (구현 담당자 기록 — status 변경 없음, 최종 승인은 오케스트레이터)

- **API**: `src/app/api/admin/itembooks/[id]/route.ts`의 PUT 핸들러가 `is_active`를
  갱신한 뒤, **저장 결과 값이 `false`이면** 항상 `badges.item_book_id = 해당 컬렉션 AND
  deleted_at IS NULL` 조건으로 일괄 소프트 삭제(`deleted_at = now()`)를 실행하도록 구현했다.
  스펙 원문은 "갱신 전 값 조회 → true→false 전환 판별"이었으나, 그대로 구현하면 1차 시도에서
  컬렉션 업데이트는 성공하고 배지 소프트삭제만 실패했을 때 재저장으로 재시도할 방법이 없다
  (이미 DB상 `is_active=false`라 "전환"이 재감지되지 않음). `deleted_at IS NULL` 조건 덕에
  이 쿼리 자체가 멱등이라, "저장 결과가 false면 매번 실행"으로 바꿔도 부작용 없이 스펙이 요구한
  재시도 가능성을 실제로 만족시킨다는 판단으로 이렇게 구현했다(리뷰 시 재검토 요망).
- **영향 범위 조회**: `GET /api/admin/itembooks/[id]/deactivation-impact` 신규 추가.
  `badges.type`별로 `user_activity_badges`(activity) / `user_poi_badge_earns`(poi) /
  `inventory_items → inventory.user_id`(item) 세 테이블에서 distinct 유저 수를 집계한다.
- **UI**: `ItemBookForm.tsx`의 활성화 토글을 shadcn `Switch`로 교체, 켜짐→꺼짐 전환 시에만
  영향 범위를 조회해 shadcn `AlertDialog`로 확인받는다. "계속" 전까지 로컬 `isActive`는
  `true`로 유지되므로 취소 시 별도 되돌림 로직 없이 자연히 원상복구된다. 실제 반영은 기존과
  동일하게 폼 "저장" 시 PUT으로 나간다.
- **shadcn 컴포넌트 팔레트 조정**: `npx shadcn add switch alert-dialog`로 생성한 원본은
  이 프로젝트 `globals.css`에 정의되지 않은 테마 토큰(`bg-primary`/`bg-input`/
  `text-muted-foreground`/`ring-ring` 등)과, MODULAR 서비스용 `Button.tsx`(cva 기반이
  아닌 커스텀 컴포넌트라 `buttonVariants` export가 없음)를 참조해 그대로 두면 스타일이
  깨지거나 빌드가 실패했다. 어드민 기존 팔레트(#111111 accent, 흰/회색 배경)에 맞춰 직접
  색상값으로 교체했다 — `src/components/ui/checkbox.tsx`가 이미 동일한 방식으로 조정돼
  있어 이 저장소의 기존 관례를 따른 것.
- **회귀 위험 확인**: 기존에 있던 신규 컬렉션 등록 화면에서는 `isEdit=false`일 때 확인 모달을
  건너뛰고 즉시 `isActive=false`로 반영하도록 처리했다(신규 등록 단계에는 소속 배지가 아직
  있을 수 없으므로).
- **검증**: `npx tsc --noEmit`(변경 파일 관련 에러 없음, 기존 테스트 파일의 무관한 jest 타입
  누락 에러는 이번 변경과 무관), `npx eslint`(변경 파일 전체 클린), `npm run build`(성공,
  `/api/admin/itembooks/[id]/deactivation-impact` 라우트 정상 등록 확인). Staging 미병합
  상태라 `jam-stage.vercel.app`에서는 아직 확인 불가 — staging 병합 후 실제 화면 확인 필요.
