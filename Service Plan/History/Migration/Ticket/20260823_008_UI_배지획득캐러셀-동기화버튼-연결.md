# [UI] 배지 획득 캐러셀 — 실제 동기화 버튼에 연결

> 선행 티켓 **20260823_007**(백엔드 응답 확장 + MODULAR 패턴 + 스파이크 페이지) 완료 후속.
> **사용자가 `jam-stage.vercel.app/spike/badge-reveal`에서 캐러셀 동작을 확인하고 승인한 뒤에
> 착수한다.** 승인 전에는 시작하지 않는다.

## 배경 / 문제 정의

티켓 007에서 `patterns/BadgeRevealCarousel`과 `/api/strava/sync`의 `earnedBadges[]`가
준비됐지만, 서비스 화면 어디에도 연결되지 않았다. 현재 동기화 후 사용자에게 보이는 것은
여전히 탭바 위 `"배지 N개 획득"` 토스트뿐이다.

이 티켓에서 실제 동기화 버튼에 캐러셀을 연결한다.

## 착수 전 확정해야 할 사항

### 🔴 `badges` 카운터와 `earnedBadges.length`가 어긋난다 (게이트·개선 리뷰 공통 지적)

`src/lib/strava/sync.ts`의 `badges: badgesEarned + poiBadgesEarned + rewardBadgesIssued`에는
**아이템 드랍 배지와 미션 보상 배지가 포함되지 않는다.** 반면 `earnedBadges`에는 들어간다.
반대로 중복 id 제거(`Array.from(new Set())`)와 소프트삭제 제외로 `earnedBadges`가 더
짧아질 수도 있다.

→ **확정(2026-08-24 사용자 결정): `earnedBadges.length`를 단일 기준으로 삼는다.**
캐러셀 노출 여부·카드 수·잔여 개수 전부 이 값으로 판단한다. 기존 `badges` 카운터는
응답에 그대로 남기되 **UI 판단에는 쓰지 않는다**(싱크 엔진 집계 로직을 건드리지 않아
회귀 위험을 만들지 않는다).
이유: `badges` 카운터를 쓰면 아이템배지만 드랍된 날 카운터가 0이라 배지를 받았는데도
캐러셀이 안 뜨고 "동기화 완료" 토스트만 뜬다.
(배지엔진 문서 §3.7.1에 두 값이 다른 집합이라는 경고 기재)

### 🔴 최초 연동 콜백 경로에 "대기 표현"이 비어 있다 (20260824_001로 새로 생긴 공백)

20260824_001이 "대기 표현은 호출부 버튼의 `loading` 스피너가 담당한다"를 컴포넌트 계약으로
확정했다. 그런데 **최초 Strava 연동 콜백 경로에는 스피너를 걸 버튼이 없다** —
`api/strava/callback/route.ts` → 리다이렉트 → 도착 페이지에서 최근 획득 조회, 이 구간
전체가 버튼 없는 대기다. 스핀이 있을 때는 이 구간도 스핀이 덮고 있었다.

→ **확정(2026-08-24 사용자 결정): `WanderingEyesLoader`를 쓴다.**
이미 MODULAR에 있고 `src/components/NavigationLoader.tsx`에서 쓰이는 JAM 전용 로더라
브랜드 일관성이 있고 추가 구현이 거의 없다.
`feedback/Skeleton`은 방금 제거한 빈 카드 스핀과 사실상 같은 발상이라 채택하지 않는다.

### `MAX_CARDS = 10` 상수가 갈라질 위험

현재 스파이크 클라이언트(`BadgeRevealSpikeClient.tsx`)에만 있는데, `.d.ts`의 `items` 주석은
"10장을 넘기면 호출부에서 자른다"고 규칙을 컴포넌트 문서에 적어두고 있다.

→ **확정(2026-08-24 사용자 결정): 서버 응답(`/api/strava/sync`)에서 자른다.**
- `earnedBadges`는 상세 10건까지만 내려보내고, 잔여 개수는 별도 숫자 필드로 전달한다
  (예: `earnedBadgesTotal` 또는 `earnedBadgesMore`). 필드명은 구현 시 정한다
- 상한 상수가 **서버 한 곳에만** 존재하므로 스파이크·서비스·타입 문서로 갈라지지 않는다
- 장기 미접속 후 싱크로 배지를 대량 획득해도 `description` 포함 페이로드가 커지지 않는다
- 클라이언트는 받은 배열을 그대로 그리고, 잔여 숫자를 `moreCount`로 넘긴다
- 스파이크 페이지의 `MAX_CARDS` 상수는 제거하고 같은 계약을 따르게 맞춘다
- `.d.ts`의 `items` 주석도 "호출부에서 자른다" → "서버가 잘라 내려준다"로 갱신한다

  정확하다(먼저 10건으로 자르고 조회하면 소프트삭제분만큼 개수가 어긋난다).
- `syncStravaActivities()` 반환에 `earnedBadgesMore: number`를 추가했다. 동시 싱크 조기 반환
  경로도 `earnedBadgesMore: 0`으로 맞췄다.

**2. `SyncButton.tsx` — 성공 토스트 제거 + 오버레이 마운트**
- 성공 분기 4줄 중 3줄(컬렉션 완성/미션 달성/배지 획득)을 제거하고, **배지 0개일 때의
  "동기화 완료" 토스트만 유지**했다. 실패 토스트(`syncFailed`)·네트워크 에러 토스트는 그대로다.
- 노출 판단은 `earnedBadges.length` 단일 기준이다. 응답이 도착하는 그 시점에 `open`으로
  전환한다(최소 노출 대기 없음). 대기 표현은 기존 `Button loading` 스피너 그대로.
- `router.refresh()`를 **캐러셀을 닫을 때**로 옮겼다. 배지 0개 경로(캐러셀 미노출)는 기존처럼
  즉시 refresh한다.
- 미사용이 된 i18n 키 3종(`syncBadgeDone`·`syncMissionDone`·`syncItembookDone`)을 삭제했다.
- "배지 전부 보기" 이동 경로에 쓸 `username`을 `(main)/page.tsx`에서 prop으로 받는다.

**3. 서비스 래퍼 `src/components/BadgeRevealOverlay.tsx` (신규)**
MODULAR 패턴은 손대지 않고 호출부에서 처리해야 하는 것들을 한 곳에 모았다.
두 진입 경로(수동 동기화 / 최초 연동)가 공유한다.

### 주요 의사결정 / 핵심 메모

- **상한을 "조회 뒤 자르기"로 구현했다.** id를 먼저 10개로 자르고 조회하면 소프트삭제된
  배지가 섞였을 때 카드 수와 잔여 개수가 함께 어긋난다. 조회는 전체로 하고(중복 제거·삭제
  제외를 끝낸 뒤) 응답에 싣는 단계에서만 자른다. 티켓이 우려한 "description 포함 페이로드가
  커지는 문제"는 HTTP 응답 크기 문제이므로 이 방식으로 그대로 해결된다.
- **잔여 개수 필드명은 `earnedBadgesMore`로 정했다.** 클라이언트가 그대로 `moreCount`에
  넘기는 값이라 `Total`보다 의미가 직접적이다.
- **서비스 래퍼를 하나 만들어 두 진입 경로가 공유한다.** 탭바 숨김·스크롤 락·컬럼 폭·문구
  주입·라이브 리전이 두 곳에 중복되면 한쪽만 고쳐지는 사고가 난다. 신규 MODULAR 컴포넌트는
  만들지 않았다(서비스 호출부 코드다).
- **최초 연동 연출을 `(main)/layout.tsx`에 마운트했다.** 콜백 목적지가 `/profile` →
  `/{username}`으로 한 번 더 리다이렉트되므로 특정 페이지에 달면 경로에 따라 놓친다.
  대신 `/profile` 경유지에서 `reveal=1`을 목적지 URL에 다시 실어주는 처리가 필요했다.
- **`reveal=1`은 도착 즉시 URL에서 지운다.** 남겨두면 새로고침·뒤로가기마다 연출이 다시
  뜬다. `router.replace`가 searchParams를 바꿔 이펙트를 한 번 더 돌리므로, 재요청 방지는
  `startedRef`로, 언마운트 후 setState 방지는 `mountedRef`로 나눠 처리했다
  (이펙트 정리 함수로 취소 플래그를 세우면 진행 중인 요청 결과가 버려진다).
- **오픈 공지와 카드 이동 공지를 분리했다.** 라이브 리전은 마운트 시점의 초기 내용을 읽지
  않는다. 그래서 "열렸다 + N개 획득"은 **닫혀 있을 때도 마운트돼 있는** 호출부 라이브 리전이,
  "중앙 카드가 바뀌었다"는 컴포넌트 안 라이브 리전이 담당한다.
- **컴포넌트를 고칠 수밖에 없었던 이유**: `BadgeRevealCarousel`은 중앙 카드 인덱스를 밖으로
  노출하지 않아 호출부가 "지금 어떤 카드가 중앙인지" 알 방법이 없다. 카드마다 `aria-live`를
  붙이는 방식은 노드가 순환하며 옮겨다녀 실제로는 공지되지 않는다(속성만 바뀌는 경우 대부분의
  스크린리더가 읽지 않는다). 그래서 안정적인 노드 하나를 라이브 리전으로 두는 방식을 택했다.

### 잔여 이슈
- **실제 Strava 동기화 왕복은 로컬에서 검증하지 못했다.** 로컬/스테이징이 프로덕션과 같은
  Supabase를 쓰기 때문에 드랍·배지 엔진을 실제로 돌리면 `user_activity_badges`의
  `UNIQUE(user_id, badge_id)` 때문에 재테스트가 불가능해지고 인벤토리 슬롯·시리얼이 소모된다.
  응답을 가로채는 방식으로 UI 계약 전체를 검증했으므로, staging 병합 후 **Strava 연동 계정으로
  실제 동기화 1회**만 확인하면 된다.
- 최초 연동 경로의 `?strava=connected` 파라미터는 현재 어떤 화면도 읽지 않는다(전수 확인).
  이번 티켓에서는 손대지 않고 그대로 뒀다.
