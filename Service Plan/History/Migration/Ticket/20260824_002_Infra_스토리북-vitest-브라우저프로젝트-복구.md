# [Infra] Storybook vitest 브라우저 프로젝트 복구 — play 회귀 테스트가 전부 실행 불가

> # ⚠️ 이 티켓의 전제는 틀렸다 (2026-08-24 게이트 리뷰)
>
> **저장소는 깨져 있지 않았다.** 게이트 리뷰어가 기점 커밋(`127f0d9`)을 **격리된 git
> worktree**에 clean `npm ci`로 설치해 `npx vitest run --project=storybook`을 실행한 결과
> **32 파일 / 193 테스트가 전부 통과**했다(`node_modules/.vite` 캐시를 매번 지운 콜드 런 4회,
> flaky 아님).
>
> 즉 "스토리 파일 32개 전부 실패"는 **저장소 속성이 아니라 당시 공유 워킹트리 한 곳의
> 속성**이었다. 여러 세션이 같은 워킹트리에서 동시에 작업하면서 `node_modules`(또는 Vite
> 옵티마이저 캐시)가 오염된 상태였던 것으로 보인다.
>
> **이 오진이 티켓 20260823_007·20260823_008·20260824_001·20260824_004의 리뷰에서 반복적으로
> "선행 이슈"로 보고됐다.** 앞으로 같은 증상을 만나면 **저장소를 고치기 전에 격리된
> worktree + clean `npm ci`로 먼저 재현**할 것.
>
> 아래 "배경 / 문제 정의"는 당시 판단을 남기는 이력이며 사실이 아니다.

## 배경 / 문제 정의

`npx vitest run --project=storybook`이 **저장소 전역에서 깨져 있다.** 스토리 파일 32개가
전부 동일한 오류로 실패한다:

```
Failed to import node_modules/@storybook/addon-vitest/dist/vitest-plugin/setup-file-with-project-annotations.js
SyntaxError: '@testing-library/dom/node_modules/aria-query/lib/index.js'
             does not provide an export named 'elementRoles'
```

`@testing-library/dom`이 물고 있는 중첩 `aria-query@5.3.0`의 CJS/ESM interop 문제다.
**스토리 소스를 평가하기 전 setup 단계에서 실패**하므로 특정 컴포넌트와 무관하며,
`Button.stories.tsx` 같은 단순 스토리로도 동일하게 재현된다.

### 왜 지금 고쳐야 하나

티켓 20260824_001에서 **실제 회귀가 발생했고**, 그 회귀를 잡는 `play` 테스트
(`BadgeRevealCarousel.stories.tsx`의 `ReopenResetRegression`)를 추가했다. 검출력도 검증했다 —
컴포넌트를 수정 전 커밋으로 되돌리면 `expected '한강 러너 2' to be '한강 러너 1'`로 실패한다.

**그런데 이 테스트가 CI에서도 로컬에서도 자동 실행되지 않는다.** 현재 회귀 방어망은
사람이 매번 Storybook을 직접 열어보는 것뿐이다.

20260824_001의 회귀는 "스핀이 우연히 겸하던 리셋 역할이 스핀 제거와 함께 사라진" 유형이었다.
이런 **암묵적 의존이 끊기는 회귀는 코드 리뷰로 잡기 어렵고, 자동 테스트가 유일한 방어선**이다.
같은 유형의 사고가 반복될 가능성이 높다.

3. 나머지 31개 스토리 파일도 실행되는지 확인하고, 이 과정에서 드러나는 기존 스토리 실패는
   별도 목록으로 정리한다 (이번 티켓에서 전부 고칠 필요는 없다 — 현황 파악이 목적)

**타입체크를 상시 적색으로 만들어 진짜 오류를 묻어버린다.** 같은 테스트 환경 문제이므로

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

> 아래 "원인" 분석은 **게이트 리뷰에서 반증됐다.** 정정 내용을 먼저 읽을 것.

#### ✅ 실제로 해결된 것 — `tsc` 오류 400건 → 0건

`jam-web/vitest.shims.d.ts`에 `/// <reference types="vitest/globals" />` 한 줄을 추가했다.

- 400건의 정체: `expect` 220 / `it` 134 / `describe` 35 / `vi` 9 + 파생 2건. **전부
  `__tests__` 파일 내부의 vitest 전역**이며, 게이트가 오류코드·식별자·파일 분포를 전수
  분류해 **실제 타입 오류를 가리지 않음**을 확인했다.
- `tsconfig.json`의 `compilerOptions.types` 지정 방식은 `@types/*` 자동 포함이 끊겨
  `node`/`react`까지 직접 나열해야 하므로 채택하지 않았다. 테스트 전용 tsconfig 분리도
  파일 한 줄로 끝나는 이 방법보다 비용이 커 제외했다.
- 이 변경은 **오진과 무관하게 그 자체로 가치가 있다.** 타입 게이트가 상시 적색이면
  진짜 오류가 묻힌다.

#### ✅ 확인된 것 — `ReopenResetRegression`의 검출력은 진짜다

`BadgeRevealCarousel.jsx`의 `prevOpen` 렌더 중 조정 블록(177~181행)을 제거하면
`BadgeRevealCarousel.stories.tsx:226`에서 `expected '한강 러너 2' to be '한강 러너 1'`로
1 failed / 13 passed, 원복하면 14/14 통과. 티켓 20260824_001 기록과 정확히 일치한다.
개발자·게이트 양쪽이 독립적으로 A/B 실측했다.

#### ❌ 반증된 것 — "저장소의 vitest가 깨져 있다"

**티켓 전제 자체가 틀렸다.** 게이트 리뷰어가 기점 커밋(`127f0d9`)을 격리 worktree에
clean `npm ci`로 설치해 실행하니 **32 파일 / 193 테스트 전부 통과**했다(콜드 런 4회).

원인 분석도 직접 측정으로 반증됐다 — 기점 상태의 중첩 `aria-query@5.3.0`의
`lib/index.js` 6번 줄은 이미
`exports.roles = exports.roleElements = exports.elementRoles = exports.dom = exports.aria = void 0;`
형태로, `elementRoles`가 cjs-module-lexer가 탐지 가능한 선언형으로 존재한다.
"5.3.0은 선언과 분리된 별도 대입문이라 탐지 실패한다"는 서술은 사실이 아니다.

**따라서 `overrides: { "aria-query": "5.3.2" }`는 이번 증상 해결에 기여한 인과가 측정상 0이다.**
개발자 세션에서 증상이 사라진 것은 override가 아니라 `npm install`이 `node_modules`를
재생성한 부수 효과였을 가능성이 높다.

#### 🔴 진짜 원인 — 공유 워킹트리 오염

여러 jam-work 세션이 **같은 워킹트리에서 동시 실행**되면서 `node_modules`(또는 Vite
옵티마이저 캐시)가 오염된 상태였다. 실제로 이번 작업 중 **002 세션의 커밋이 003 브랜치에
들어가는 사고**까지 발생했고 `git branch -f`로 수습했다(티켓 20260820_019의 조상 오염 사고
변종).

**교훈: 같은 증상을 만나면 저장소를 고치기 전에 격리된 worktree + clean `npm ci`로 먼저
재현할 것.** 이 오진이 티켓 007·008·001·004의 리뷰에서 반복적으로 "선행 이슈"로 보고됐다.

### 주요 의사결정 / 핵심 메모

- **overrides vs vitest 설정 우회**: `optimizeDeps.include: ['aria-query']`로도 증상은 가릴 수 있으나,
  깨진 5.3.0이 트리에 남아 다른 도구(스토리북 dev 서버, 향후 addon 업데이트)에서 재발할 수 있다.
  버전 통일이 근본 해결이라 판단했다.
- **`npm install` 부수 효과 확인**: lock에서 제거된 것은 중첩 `aria-query@5.3.0`과 그 전용 의존
  `dequal@2.0.3` 둘뿐이다(총 2 패키지 제거, 추가 0). 빌드·타입체크·전체 테스트로 회귀 없음을 확인했다.
- **CI 연결은 범위 밖**: 저장소에 `.github/workflows`가 없어 이번 복구만으로 자동 실행되는 CI는 없다.
  `npm test`(= `vitest run`)가 두 프로젝트를 모두 돌리므로 CI를 붙일 때 별도 설정은 필요 없다.
