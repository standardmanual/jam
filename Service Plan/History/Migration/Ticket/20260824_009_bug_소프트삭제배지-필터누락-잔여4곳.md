# [bug] 소프트 삭제 배지 필터 누락 — 잔여 4개 지점

> 티켓 20260824_007 개선 리뷰에서 발견. 007이 고친 6곳과 동일한 패턴이며,
> 007 완료 후에도 "이게 전부다"라는 전제가 또 틀렸다(004→005 전례와 동일 구조).

## 배경 / 문제 정의

007에서 배지 상세·컬렉션 상세·미션 상세·홈·포인트 내역·공유 API 6곳에
`deleted_at IS NULL` 필터를 추가했다. 개선 리뷰가 리뷰 브랜치 코드를 직접 재검토하며
**같은 필터 누락 패턴이 4곳 더 있음을 발견**했다.

**#1이 가장 눈에 띄는 불일치다.** `collections/[id]/page.tsx`(상세, 007에서 이미 필터
추가됨)는 진행도 분모를 정확히 계산하는데, 위 4개 목록/API 지점은 여전히 삭제된 배지를
분모에 포함한다. **같은 컬렉션의 진행도(예: 3/8)가 화면마다 다른 숫자로 보일 수 있다** —
007이 없애려던 바로 그 "화면마다 다르게 보임" 패턴이 다른 형태로 남아 있다.

**#3은 방향이 반대인 불일치다.** 메인 인벤토리 목록(`inventory/page.tsx`, 이미 정상
필터링됨)에서는 안 보이는 아이템을, POI 드랍 선택 화면(`PoiCarouselModal.tsx`가 이
API를 소비)에서는 여전히 골라서 드랍할 수 있다.

### 검증

각 지점에서 실제로 삭제된 배지가 노출/포함되는지 A/B로 확인. 목록형 화면은 항목만
빠지고 전체가 죽지 않는지 함께 확인 (20260824_004의 교훈).

## 구현 계획

1. 7개 위치에 `deleted_at IS NULL` 필터 추가 (표의 #1~#4)
2. 진행도 분모 계산이 상세 페이지와 일치하는지 확인 (#1)
3. 실측 검증
4. 이 패턴이 또 남아있지 않은지 마지막으로 한 번 더 전수 grep

### 구현 내용 요약
표의 7개 지점 모두에 `.is('deleted_at', null)` 필터를 추가했다.

- `badges/page.tsx`: 아이템북 진행도 분모를 만드는 두 쿼리(`ownedBadgesWithBook`, `bookBadgesRaw`)
  모두에 필터 추가 — 컬렉션 상세(`collections/[id]/page.tsx`)와 동일한 분모가 나오도록 맞춤
- `[username]/collections/page.tsx`: 타인 컬렉션 탭의 `bookBadgesRaw` 쿼리에 필터 추가
- `api/users/[username]/itembooks/route.ts`, `api/itembooks/route.ts`: 각각 아이템북 발견 여부
  판정 쿼리 + 분모 계산 쿼리에 필터 추가 (itembooks/route.ts는 두 곳 모두 누락돼 있었음)
- `missions/page.tsx`: 보상 배지명 조회 쿼리에 필터 추가
- `api/inventory/items/route.ts`: 조인 셀렉트에 `deleted_at`을 추가해 가져온 뒤,
  `inventory/page.tsx`와 동일한 사후 필터(`filter((d) => d.badges && !d.badges.deleted_at)`)
  패턴으로 드랍 후보 목록에서 제외 (PostgREST 임베디드 리소스는 `.is()` 체이닝으로 직접
  필터링되지 않아 join select에 컬럼을 추가하고 JS에서 걸러내는 기존 코드베이스 패턴을 따름)
- `combine/page.tsx`: 조합 재료 배지 조회 쿼리에 필터 추가 (기존 `filter(Boolean)` 로직이
  삭제된 배지에 매칭되는 인벤토리 아이템만 조용히 제외해줌 — 20260824_004의 교훈대로 전체가
  죽지 않음)
