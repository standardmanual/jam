# [Feature] 알림(소식) 기능 PRD 수립

## 배경 / 문제 정의

JAM!은 배지 발급·드랍 픽업·미션 진행·팔로우처럼 **비동기로 발생하는 사건**이 많은데,
현재 유저가 이를 알 방법이 앱을 직접 열어 각 화면을 돌아다니는 것뿐이다.

특히 다음 두 가지는 **모르면 손해를 보는** 상태다.

- **Strava 연결이 끊어져도 유저가 알 수 없다.** 배지 발급이 완전히 멈추는데 아무 신호가 없다.
- 내가 드랍한 아이템 배지를 누가 픽업해도, 참가한 미션이 마감돼도 통보가 없다.

[01_PRD.md](../../../Specs/PRD/01_PRD.md) §6에 "거래 알림은 앱 내 알림으로만"이라고 이미
명시돼 있고, 푸시 알림은 PWA/Service Worker 인프라 자체가 없어 착수 미정 상태다(§7).
즉 인앱 알림은 신규 발상이 아니라 **이미 필요하다고 인지된 갭을 채우는 작업**이다.

### 이 기능의 정체성 — "알림"이 아니라 "소식의 히스토리"

메뉴 이름이 알림일 뿐, 실제로는 **최신순으로 쌓이는 소식 히스토리**다. 푸시 노티가 아니며,
실시간성 요구도 사실상 없다. 유저가 앱을 여는 시점에 준비돼 있기만 하면 된다.

| 제외 대상 | 이유 |

### 게이미피케이션 윤리 기준

`gamification-loops` 스킬의 sharp_edges 기준을 적용했다.

- **숫자 배지 대신 dot** — 강박적 확인 유도 회피
- **완성 임박 소식은 컬렉션당 평생 1회** — 반복 발송은 즉시 다크패턴
- **순위 하락 소식 없음** — 상승만 알림. 리더보드는 하위 30%를 이탈시킨다
- **팔로잉 활동 하루 상한 2건** — 남의 소식이 내 보상 소식을 묻지 않게
- **FOMO 톤 금지** — "지금 안 하면 놓쳐요" 류 문구 사용 안 함

### 주요 의사결정 / 핵심 메모

- **"알림"이 아니라 "소식 히스토리"로 정체성을 못박았다.** 이 한 줄이 설계 전반을 결정한다 —
  실시간성 불필요, 개별 읽음 플래그 불필요, 상태가 아닌 사건만 수록.
- **읽음을 타임스탬프 1개(`users.notifications_seen_at`)로 축소.** "진입 시 전체 읽음"이라는
  UX 결정이 데이터 모델을 통째로 줄였다. 소식이 수만 건이어도 읽음 처리 UPDATE는 항상 1행.
- **①보상 획득은 dot을 켜지 않는다(`bumps_badge=false`).** Strava 동기화가 webhook 없이 100%
  수동이라, 유저가 버튼을 눌러 오버레이로 이미 본 배지가 다시 dot을 켜면 신호가 죽는다.
  리스트에는 남겨 히스토리 가치는 유지.
- **강조 규칙을 "슬롯 = 볼드" 하나로 통일.** 사용자가 지정한 강조 지점을 전수 대조한 결과
  `payload` 슬롯과 정확히 일치했다. 소식마다 강조를 따로 정의할 필요가 없어지고, 신규 소식
  추가 시에도 문구만 쓰면 강조가 따라온다.
- **⑥ 팔로잉 활동은 반드시 배치.** 인라인이면 (1) 팔로워 500명 유저의 배지 1개가 500행을
  만들고 (2) 하루 상한 2건을 구현할 수 없다(이미 넣은 걸 취소해야 함).
- **알림 종 노출을 화면 목록이 아니라 규칙으로 정의.** "back chevron이 없는 루트 화면에만"으로
  두면 호출부 변경이 0이고 루트 화면이 늘어나도 따라온다. `/drops`는 TopNav 자체가 없어 자동 제외.
- **착지점을 DB에 저장하지 않는다.** `type`은 안정적이고 라우트는 변한다 — 변하는 쪽을 코드에 둔다.
- **경고 스타일을 동적 재평가.** ⑧의 40·41·42는 렌더 시점에 현재 상태를 조회해 경고 여부를
  결정한다. "인벤토리 비웠는데 아직 경고가 떠 있는" 상태를 막으면서 히스토리는 보존.
- **제외 판단**: 섀도우밴·GPS 조작 감지는 은닉이 목적이라 알리면 기능이 무력화된다.
  세계관 마일스톤은 착지할 화면이 없어 제외. 순위 하락은 하위권 이탈을 가속해 제외.

### 잔여 이슈

- **후속 구현 티켓 3개** (PRD §8):
  - `019` (db) — `notifications` 테이블 + `users.notifications_seen_at` + T1 인라인 생성
  - `020` (ui) — `/notifications` 화면 + TopNav 종 아이콘·빨간 버블 + `BellIcon` + 컬러 토큰
  - `021` (api) — T2 배치 cron (KST 18:00)
  - 019 → 020 → 021 순서 의존. 020은 019의 테이블이 있어야 읽을 화면이 생기고,
    021은 019의 생성 함수를 재사용한다.
- **열린 질문 4건** (PRD §9) — 구현 전 확정 필요한 것은 #18 "다녀갔다" 정의와
  #32 "활동 지역" 매칭 기준. 나머지 2건은 019~021 진행 중 판단 가능.
- **[NEEDS CLARIFICATION] 3건** (DATA_MODEL §8) — 특히 `group_key` 시간창의 KST/UTC 기준은
  019 착수 시 확정해야 한다. 티켓 20260824_006에서 `event_at`을 로컬 벽시계로 오해석한 전례가 있다.
- **선행 의존**: `--color-notification-dot` / `--color-warning` 시맨틱 토큰이 없다(020 범위).
  `BellIcon`도 신규 추가 대상 — 기존 아이콘 세트가 stroke 1.5px 규칙이라 Material Symbols의
  fill 기반 path를 그대로 쓰면 톤이 어긋난다.
