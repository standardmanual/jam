### 2단 타겟 구현 방법 (판정 포함)

PRD §3이 요구하는 **아바타 탭 → 사람 / 본문 탭 → 대상**은 #13·#26 단건·#30·#32에 해당한다.

`ListRowCard`는 `href`면 `<Link>`, `onClick`이면 `<button>`으로 **행 전체를 래핑**한다.
그 안에 또 링크를 넣으면 `<a>` 안의 `<a>`라 HTML상 무효다.

→ **2단 타겟이 필요한 행은 `href`·`onClick`을 넘기지 않고 wrapper 없는 `<div>` 모드로 쓰고,
`icon` 슬롯과 `children` 슬롯 각각에 링크를 넣는다.** `children`이 `flex-1`이라 행의 대부분을
차지하므로 터치 타깃 손실이 거의 없다. 인스타그램의 실제 구현과 같은 방식이다.
2단 타겟이 없는 나머지 행은 평소대로 `href` 모드를 쓴다.

### 1.6 모듈러-서비스 연결 범위

이 티켓은 `design-system/tokens/colors.css`를 건드리므로 표기 대상이다.

- **부류: 토큰** — `src/app/globals.css`가 `design-system/tokens/`를 직접 `@import`하므로
  **서비스 화면에 즉시 반영**된다
- 추가할 시맨틱 토큰 2개. **base 색은 기존 팔레트를 재사용하고 새 색을 도입하지 않는다**
  (아이콘 세트의 "제3의 컬러 도입 금지" 정신)

  | 토큰 | 값 | 용도 |
  |---|---|---|
  | `--color-notification-dot` | `var(--color-base-red)` (#e8461f) | 안 읽은 소식 있음 |
  | `--color-warning` | `var(--color-base-amber)` (#ffb800) | ⑧ 경고 상태 |

  같은 빨강 계열로 두면 "소식 있음"과 "문제 있음"이 구분되지 않는다. amber는 경고의 관례색이고
  검정 캔버스에서 대비도 충분하다. `--color-primary`가 이미 `--color-base-red`지만, 의미가
  다르므로 토큰을 분리해 나중에 갈라칠 수 있게 둔다.
- **병존 구현(`ListRowCard`·`Skeleton`)은 서비스 쪽만 사용하고 DS를 고치지 않는다** → 양쪽
  동기화 이슈 없음

## 2. 상세 요구사항

### 2-1. `/notifications` 화면

- 전체 페이지, **최신순**(`updated_at DESC`) 단일 리스트
- 시간 구간 헤더 — **오늘 / 이번 주 / 이번 달 / 이전** (KST 기준)
- 커서 페이지네이션 — `user_activity_feed`가 쓰는 기존 패턴을 따를 것
- 빈 상태 처리

**읽음 처리** — [DATA_MODEL.md](../../../Specs/PRD/Notification/DATA_MODEL.md) §3

1. 진입 시 `UPDATE users SET notifications_seen_at = NOW()` **1회**
2. 단, **진입 직전의 `seen_at`을 서버에서 스냅샷해 응답에 함께 실어 보낸다**
3. 클라이언트가 그 값으로 **"새 소식 N" 구분선**을 그린다
4. 읽음 처리는 이미 끝났으므로 새로고침하면 구분선이 사라진다

이걸 빠뜨리면 유저가 뭐가 새 거였는지 알 수 없다.

### 2-2. 문구 렌더링

**`payload` 슬롯 = 볼드. 고정 텍스트 = 일반. 컬러 강조는 쓰지 않는다.** (PRD §5)

- 소식 종류마다 강조 지점을 따로 정의하지 말 것 — **템플릿의 슬롯을 볼드로 감싸는 렌더러 1개**로
  28종이 자동 일관된다
- **닉네임은 `payload`에 없다.** `actor_user_id`·`user_id`로 조인해 렌더 시점에 읽는다
  (유저가 닉네임을 바꾸면 과거 소식도 따라와야 한다)
- **#44의 `payload.reason`은 코드다.** 반드시 기존 `adminReasonLabel()`
  (`src/lib/points/reasons.ts:45`)을 경유할 것. 코드가 그대로 노출되면 가이드 위반이다
- ⚠️ **`payload.count`는 병합 후 신뢰할 수 없다.** #1·#3·#4는 `badge_ids`가 누적되는데 `count`는
  얕은 병합이라 "이번 이벤트분"으로 남는다. **개수는 배열 길이로 렌더할 것**

### 2-3. 착지점 — 저장하지 않고 런타임 계산

`type` + `payload` → href 매핑 함수 **1개**. PRD §3의 28종 표가 그 함수의 명세다.
컬럼으로 저장하면 라우트를 바꿀 때 과거 소식이 전부 깨진다.

**신규 라우트 파라미터 3종**도 이 티켓 범위다.

| 파라미터 | 쓰이는 소식 |
|---|---|
| `?highlight=<ids>` — 배지·인벤토리 목록 하이라이트 | 1, 3, 4 |
| `/collections/[id]` **장착 모드** 진입 | 11 |
| `/drops?poi=<id>` — 지도 카메라 이동 | 18, 32 |

### 2-4. ⑧ 경고 스타일 — 동적 재평가

40·41·42·44는 경고 아이콘 + `--color-warning`으로 표시하되, **경고 여부를 저장하지 않고
렌더 시점에 현재 상태를 조회해 결정한다.** (PRD §6-2)

| 소식 | 경고 유지 조건 | 해소되면 |
|---|---|---|
| 40 Strava 끊김 | 토큰이 여전히 무효 | 일반 텍스트로 강등 |
| 41 동기화 지연 | 마지막 sync가 여전히 3일+ 경과 | 강등 |
| 42 인벤토리 포화 | 잔여 슬롯이 여전히 부족 | 강등 |
| 44 포인트 **차감** | 항상 유지 (되돌릴 수 없는 사건) | — |

"인벤토리 비웠는데 아직 경고가 떠 있는" 상태를 막으면서 히스토리는 보존한다.

### 2-5. TopNav 진입점

```
[logoSlot │ back+title] ─── [centerSlot: 동기화] ─── [rightSlot] [avatarSlot: 프로필]
                                                        ↑ 알림 종
```

- **DS 변경 없이** 기존 `rightSlot`을 쓴다 (`avatarSlot` 바로 앞에 붙도록 이미 설계돼 있음)
- **`rightSlot` 충돌 처리**: 배지 상세의 공유 버튼이 이미 쓴다. 서비스 래퍼
  (`src/components/ui/TopNav.tsx`)가 `centerSlot`·`avatarSlot`을 자동 주입하듯 합성한다.
  `rightSlot = <>{호출부 값}{알림 종}</>` — **종을 뒤에** 붙여야 아바타 바로 왼쪽에 온다
- **표시**: 우측 상단 빨간 버블, **숫자 없음**. `bumps_badge=true`인 안 읽은 소식이 하나라도
  있으면 노출 (dot 판정 쿼리는 DATA_MODEL §3)

### 2-6. 노출 범위 — 화면 목록이 아니라 규칙으로

> **back chevron이 없는 루트 화면에만 알림 종을 주입한다** (`logo` 또는 `showBack={false}`)

| 화면 | 종 |
|---|---|
| 홈 `/` · 배지 · 미션 · 인벤토리 (전부 `logo`) | ✅ |
| **본인** 프로필 `/[me]` | ✅ **TopNav 신규 추가** (`logo` 모드) |
| 타인 프로필 `/[username]` | ❌ back + 닉네임 타이틀 |
| 드랍 `/drops` | ❌ TopNav 자체가 없어 자동 제외 |
| 상세 화면 전반 | ❌ |

호출부를 손대지 않고 이 규칙으로 판정하면 루트 화면이 늘어나도 알아서 따라온다.

### 2-7. `BellIcon`

- Material Symbols `notifications`(FILL 0 / wght 400 / opsz 24)의 **형태를 따르되**,

  기존 아이콘과 선 굵기·질감이 어긋난다

⚠️ **`at`을 클라이언트가 보낸 타임스탬프로 채우지 말 것.** 라우트 핸들러에서 서버 `new Date()`

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

**1) 문구 렌더러 — 규칙 1개로 28종**
`payload` 슬롯만 볼드로 감싸는 토크나이저 하나(`tokenizeMessage`)가 28종의 강조를 전부
결정한다. 소식별 강조 지점을 따로 정의하지 않는다. 문구는 `i18n/ko.ts`의
`notifications.msg*` 키에 PRD §3 예시 그대로 옮겼다.

- **조사(`을/를`·`이/가`)는 볼드가 아니다** — 변수가 아니라 문법이므로 `{을/를}` 마커를
  바로 앞 슬롯 값의 받침으로 치환한다. 따옴표(`'잃어버린 시간'을`)를 건너뛰고 실제 글자를
  읽으며, 숫자는 음독 받침(1 일→있음, 2 이→없음), 영문은 받침 없음으로 본다
  (PRD의 `'한강 100km'가`와 일치).
- **개수는 배열 길이로 렌더한다** — `payload.count`는 append 병합 후 "이번 이벤트분"만
  남아 신뢰할 수 없다(#1·#3·#4). 회귀 테스트로 못 박았다.
- **닉네임은 조인해서 읽는다** — `payload`에 박제하지 않으므로 `actor_user_id`·`user_id`로
  페이지 단위 일괄 조회(N+1 없음).
- **#44의 `reason`은 `adminReasonLabel()`을 경유**한다. 코드가 그대로 새어 나오지 않는지
  테스트로 단언했다. 사유가 없으면 `'—'`를 노출하지 않고 괄호째 뺀다.

**2) 착지점 — 저장하지 않고 런타임 계산**
`notificationTarget(view)`가 `type`+`payload`로 `{ href, avatarHref }`를 만든다.
`avatarHref`가 있는 행(#13 단건·#26 단건·#30·#32)은 `ListRowCard`에 `href`를 넘기지 않고
`icon`·`children` 슬롯에 각각 링크를 넣는다(`<a>` 안의 `<a>` 회피 — §1.5 판정 그대로).

**3) 신규 라우트 파라미터 3종**
- `?highlight=` — `/badges`(+`?tab=`), `/inventory`. `BadgeGridCard`에 `highlighted` prop 추가
  (기존 `selected`와 의미가 달라 분리)
- `/collections/[id]?slot=1` — 장착 모드. 슬롯 그리드로 스크롤하고 아직 안 넣은 칸을 짚어준다
- `/drops?poi=` — 서버가 POI 좌표를 읽어 넘기고 지도 준비 시점에 `focusPoi()` 1회

**4) 읽음 처리와 "새 소식 N" 구분선**
서버 컴포넌트가 진입 **직전**의 `seen_at`을 스냅샷해 내려주고, 화면 마운트 후
`POST /api/notifications/seen`이 전체 읽음 처리(UPDATE 1행)한다. 읽음 처리를 렌더 중
부수효과로 두지 않은 이유는 프리페치·재렌더만으로 "열지 않았는데 읽음"이 될 수 있어서다.

**5) ⑧ 경고 스타일 — 동적 재평가**
`isWarningNotification()`이 렌더 시점의 현재 상태(Strava 연결 유무 / 마지막 sync 경과 /
잔여 슬롯 / 차감 방향)로 판정한다. 상태 조회는 해당 종류가 그 페이지에 있을 때만 한다.
판정 기준 상수(`SYNC_STALLED_DAYS=3`, `INVENTORY_LOW_SLOTS_THRESHOLD=3`)는 025 배치가
같은 값을 쓰도록 `warning.ts`에서 export한다.

**6) TopNav 진입점 — 규칙 판정**
서비스 래퍼가 `rightSlot = <>{호출부 값}{알림 종}</>`로 합성하고, 노출 여부는

`notifications`가 0건이라 동일 구조(uuid PK + timestamptz)인 `user_activity_feed`의
동률 23행 구간에서 같은 쿼리를 조립해 끝까지 페이지를 넘겼다.

| 방식 | 수집 | 누락 |
|---|---|---|
| 기존 단일 키 `.lt()` | 6건 | **21건** |
| 복합 `(updated_at, id)` | 27건 | **0건** |

동률 유실이 실재했고 이번 수정이 막는다는 것이 확인됐다. 025 배치를 돌린 뒤였다면
"소식이 가끔 사라진다"는 원인 불명 버그로 남았을 것이다.

**그 밖의 실측 검증**

- 읽음 처리 — `seen_at` 갱신 확인, "새 소식 4" 구분선이 대상 4건과 정확히 일치, 처리 후 dot 1→0
- ⑧ 동적 재평가 — 인벤토리 49/50 → 10/50으로 바꾸자 경고 아이콘 2개 → 1개(#42 강등, #44 유지)
- #44 라벨 — 어드민 사유 6종 전부 렌더해 「지급/회수/차감/어뷰징」 미노출 확인
- 빈 슬롯 로그 — 키를 틀린 payload로 `missingMessageSlots()`가 `['bookName']` 반환 확인
- 중첩 링크 — 실제 HTML에서 아바타 `<a>`와 본문 `<a>`가 형제로 분리

**"소식 0건"은 정상이었다** — 게이트가 "활동은 있었는데 0건"이라며 인라인 생성 미작동을
의심했으나 타임라인 대조 결과 오판이었다. 마이그레이션 096 적용은 **14:58:49 UTC**이고
`badge_earned`·`item_dropped`는 **12:45 UTC로 그 이전**이다. 적용 이후 발생한 유일한 이벤트인
`mission_joined`(14:36)는 PRD가 "내가 방금 한 행동"으로 명시 제외한 T1 비대상이다.

### 주요 의사결정 / 핵심 메모

1. **읽음 처리를 서버 렌더가 아니라 클라이언트 POST로** — 렌더 중 부수효과로 두면 Next.js의
   프리페치·재렌더만으로 "열지 않았는데 읽음"이 될 수 있다. 구분선용 `seen_at` 스냅샷은
   그 호출 이전에 서버가 이미 읽어 내려보낸다.
2. **dot 판정을 EXISTS 대신 "최신 bumping 소식 1건"으로** — `seen_at`과 병렬로 조회할 수 있어
   `(main)` 레이아웃에 왕복 지연을 더하지 않는다. 비교는 문자열이 아니라 시각으로 한다.
3. **#45(공지)의 제목은 슬롯이 아니다** — 어드민이 쓴 완성 문장이라 슬롯으로 두면 한 줄
   전체가 볼드가 되어 강조 규칙이 오히려 무의미해진다. 일반체로 렌더한다.
4. **#2·#29의 등급 라벨은 고정 텍스트** — PRD §3 예시가 배지명만 볼드로 두었다. 슬롯이 아니라
   템플릿 문자열에 합쳐 렌더러는 그대로 두었다.
5. **`AlertTriangleIcon`을 아이콘 세트에 추가** — §2-4가 요구하는 "경고 아이콘"이 기존 23종에
   없었다. `BellIcon`과 같은 부류(서비스 아이콘 세트 확장)로 처리했다.
6. **경고 판정 상수를 `warning.ts`에서 export** — 025 배치의 생성 기준과 렌더 시점 재평가
   기준이 갈리면 "만들자마자 강등되는 소식"이 생긴다.
7. **배치 생성 소식 14종의 payload 계약을 `types.ts`에 선반영** — 렌더러가 기대하는 키
   이름을 못 박아 두지 않으면 025가 다른 이름으로 채울 때 조용히 빈 문구가 된다.

### 잔여 이슈
- **POI 열람 계측은 캐러셀 "오픈" 시점만 기록한다.** 티켓 §2-8 문구를 그대로 따랐다.
  캐러셀을 옆으로 스와이프해 다른 POI를 본 것은 기록하지 않으므로 #18의 고유 인원이
  과소 집계될 수 있다. 필요하면 `onCenterChange`로 옮기면 되지만 요청당 POST가 늘어난다.
- **#40의 "토큰이 여전히 무효" 판정을 연결 행 유무로 근사했다.** 실제 토큰 유효성은 갱신을
  시도해야 알 수 있어 렌더 경로에서 확인할 수 없다. 재동기화하면 연결이 생겨 경고가
  강등되므로 이 소식의 목적(재동기화 유도)과는 일치한다.
- **"새 소식 N"의 N은 현재 로드된 목록 기준**이다. 첫 페이지(20건)를 넘는 안 읽은 소식이
  있으면 더 불러오기 전까지 20으로 보인다. 2차에서 선을 경계로 옮기면서, 로드된 목록이
  **전부** 새 소식이면(=경계가 아직 화면 밖) 구분선이 그려지지 않는다 — 나눌 대상이
  없는 선을 그리지 않는다는 판단이다.
- **구분선·버블 전환은 실데이터로 확인하지 못했다.** 알림 테이블이 아직 비어 있고
  (T1 인라인 생성분 없음) 이 브랜치는 staging에 병합 전이라, 실제 소식이 쌓인 화면은
  staging 병합 후 확인이 필요하다. 마크업·API 경로는 로컬 dev-login으로 실측했다.
- 소식 #18·#21·#23·#24·#29~#32·#34는 025 배치가 만들기 전까지 실제 데이터가 없다.
  이 티켓에서는 문구·착지점 단위 테스트로만 검증했다.
