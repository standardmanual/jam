# [API] 알림(소식) 배치 cron — T2 13종

## 배경 / 문제 정의

[019](20260824_019_Infra_알림소식-스키마-인라인생성.md)가 스키마와 T1 인라인 생성을,
[021](20260824_021_UI_알림함-화면-TopNav-진입점.md)이 화면을 완성해 **둘 다 프로덕션에 배포**됐다.

지금 알림함은 T1이 만드는 소식만 담는다. **PRD §4의 T2 13종이 비어 있어** 알림함이 아직
제 모습을 갖추지 못했다. 이 티켓이 마지막 조각이다.

> **읽기 전 필독**
> - [PRD.md](../../../Specs/PRD/Notification/PRD.md) — §3 소식 정의, **§4 생성 트리거**, §4-1 배치 스케줄
> - [DATA_MODEL.md](../../../Specs/PRD/Notification/DATA_MODEL.md) — §4 묶음 모델, §6 payload

## 상세 요구사항

### 1. 단일 cron으로 통합

**신규 cron은 1개만 만든다.** 소식 종류마다 cron을 만들면 Vercel cron 예산을 소모하고
(과거 [20260723_004](20260723_004_Admin_배포가-안-되던-근본-원인Vercel-Hobby-플랜-cron-빈도-제.md)에서
cron 빈도 제한이 배포 실패 원인이었다) 실행 시각도 제각각이 된다.

```
경로     : /api/cron/notifications
스케줄   : 0 9 * * *   (UTC 09:00 = KST 18:00)
```

**KST 18:00인 이유** — [01_PRD.md](../../../Specs/PRD/01_PRD.md) §2의 핵심 시나리오가
"운동 후 귀가해서 저녁에 확인"이다. 저녁 접속 시점에 소식이 갓 만들어져 있는 게 가장 신선하다.
기존 cron 2개(UTC 00:00 `poi-cleanup`, UTC 18:00 `ambient-drop-monitor`)와도 겹치지 않는다.

`CRON_SECRET` Bearer 인증은 기존 cron 라우트와 동일하게 적용한다.

### 3. ⚠️ 반드시 지킬 계약 — 019·021 리뷰에서 누적된 것

이 절이 이 티켓의 핵심이다. **어기면 조용히 깨지는** 것들만 모았다.

#### 3-1. payload 키를 `types.ts` 계약 그대로 쓸 것

021이 각 type의 payload 키를 `src/lib/notifications/types.ts`에 **선반영해 뒀다.**
렌더러는 값이 빈 슬롯을 통째로 버리므로, 키를 하나라도 틀리면
**`''에 넣을 수 있는 아이템 배지가 3개 있어요`** 처럼 빈 따옴표만 남은 문장이 나간다.

| type | 필수 키 |
|---|---|
| `collection_slottable` | `item_book_id`, `book_name`, `count` |
| `collection_near_complete` | `item_book_id`, `book_name` |
| `drop_spot_active` | `poi_id`, `poi_name`, `visitor_count` |
| `mission_deadline` | `mission_id`, `mission_title`, `days`, `remaining`, `unit` |
| `mission_rank_up` | `mission_id`, `mission_title`, `rank` |
| `mission_ended` | `mission_id`, `mission_title` |
| `following_rare_badge` | `badge_id`, `badge_name`, `rarity` |
| `following_collection_complete` | `item_book_id`, `book_name` |
| `following_mission_complete` | `mission_id`, `mission_title`, `actor_ids` |
| `following_nearby_drop` | `poi_id`, `region` |
| `nearby_drops` | `count`, `region` |
| `sync_stalled` | `days` |
| `inventory_full` | `max_slots`, `used_slots` |

021이 넣어둔 `missingMessageSlots()` 경고(`console.warn('[notifications] 빈 슬롯', …)`)가
서버 로그에 찍히는지 배포 직후 확인할 것.

#### 3-2. 시각을 한 번만 캡처해 모든 빌더에 넘길 것

`dailyGroupKey`·`sixHourGroupKey`는 `at`을 생략하면 **각각 `new Date()`를 개별 평가**한다.
배치가 KST 자정을 걸쳐 길게 돌면 같은 배치가 두 날짜 키로 갈린다.

→ **배치 시작 시각을 한 번 캡처해 모든 `group_key` 빌더와 날짜 계산에 넘긴다.**
`poi_views` 집계의 "KST 7일 전"도 반드시 같은 `kst.ts`를 경유할 것.

#### 3-3. 숫자 슬롯이 0이면 소식을 만들지 말 것

렌더러의 `num()`은 키가 없으면 0을 돌려준다. `0일째 활동을 못 불러오고 있어요`,
`0명이 다녀갔어요` 같은 문장이 그대로 나간다. ①은 배열 길이라 회귀 테스트로 잠겨 있지만
**T2의 숫자 슬롯(#18·#21·#23·#34·#41·#42)은 열려 있다.**

→ **0이면 그 소식을 만들지 않는다**를 배치 쪽에서 보장하고 테스트로 잠글 것.

#### 3-4. `warning.ts`의 판정 상수를 import할 것

021이 배치와 공유하려고 export해 뒀다. 값을 복사하지 말 것.

```
SYNC_STALLED_DAYS             = 3    (#41)
INVENTORY_LOW_SLOTS_THRESHOLD = 3    (#42)
```

⚠️ **#42는 문구와 임계값이 어긋난다.** 상수는 "잔여 3칸 이하"인데 문구는
`인벤토리가 꽉 찼어요. 50개까지만 보관할 수 있어서 픽업이 안 될 수 있어요`다.
잔여 3칸인 유저에게 사실과 다른 문장이 간다. **둘 중 하나로 정할 것** —
(가) 생성 조건을 잔여 0칸으로 좁힌다 (나) 문구를 `거의 찼어요` + 잔여 칸 슬롯으로 바꾼다.
판단 근거를 완료 기록에 남길 것.

#### 3-5. ⑥ 팔로잉 활동은 하루 상한 2건

PRD §3 ⑥이 규정한다. 상한이 없으면 알림함이 남의 소식으로 도배되고 내 보상 소식이 묻힌다.
**희귀도 단독으로 선별**한다(PRD §9 — 친밀도 지표가 생기면 재검토).

#### 3-6. 팬아웃 비용

`createNotification()`이 호출마다 `createServiceClient()`를 새로 만들고 RPC를 1회 왕복한다.
T1(호출 14곳, 건당 1~3회)에는 충분하지만 **배치는 수백~수천 왕복**이 된다.
클라이언트 주입 인자나 `p_user_ids UUID[]` 벌크 RPC를 검토할 것. DB 변경이 필요하면
**SQL 파일 작성까지만** 하고 실행은 오케스트레이터가 처리한다.

#### 3-7. 멱등성 — 재실행해도 중복이 생기면 안 된다

cron은 재시도될 수 있다. `group_key` + `once` 모드로 DB가 막게 한다.

PRD §4-2 표에서 #10·#23·#24·#34는 현재 `group_key` NULL로 분류돼 있는데, **NULL이면 중복 방지
수단이 DB에 없어** 배치가 매번 SELECT로 존재를 확인해야 하고 재시도 시 중복이 샌다.

→ `once` 모드에 키를 주는 방향을 검토할 것. 예: `collection_near_complete:{book_id}`,
`mission_rank_up:{mission_id}:{KST일자}`, `mission_ended:{mission_id}`,
`nearby_drops:{KST일자}`. 채택 시 **DATA_MODEL §4-2 표를 함께 갱신**한다.

#### 3-8. 소식 생성 실패가 배치 전체를 죽이면 안 된다

한 유저의 소식 생성이 실패해도 나머지 유저는 처리돼야 한다. 다만 **조용히 삼키지 말 것** —
`console.error`로 남긴다(이 프로젝트의 기존 원칙, `createNotification()`이 이미 그렇게 동작).

### 4. 문구는 PRD §3 표 그대로

021이 렌더러를 이미 만들었다. 이 티켓은 **payload만 정확히 채우면** 문구는 자동으로 나온다.
새 문구를 만들지 말 것.

**§3 「반드시 지킬 계약」 대응**

- **§3-1 payload 키** — `NotificationDraft`를 `NotificationPayloadMap`에서 파생한 판별 유니온으로
  정의해 **키를 틀리면 `tsc`가 깨진다.** 실제로 `poi_name` → `poiName`으로 바꿔 컴파일 실패를
  확인했다. 여기에 더해 테스트가 모든 초안을 `missingMessageSlots()`에 통과시켜
  **버려진 슬롯이 0개**이고 평문에 `''`가 없음을 검증한다.
- **§3-2 시각 캡처** — `createBatchContext(startedAt)`가 `startedAt`·`today`를 한 번 만들고 8개
  단계가 그 값만 쓴다. 날짜 계산은 전부 `kst.ts` 경유(`kstDateString`·`kstDateOffset`·
  `kstWeekKey`). #18의 "KST 7일 전"도 `kstDateOffset`으로 계산해 `viewed_on`(KST DATE)과 맞췄다.
- **§3-3 0 렌더 방지** — #18(visitor_count) · #21(remaining) · #23(rank) · #34(count) ·
  #41(days) · #42(max_slots) 전부 0이면 만들지 않고, 각각 회귀 테스트가 있다.
  #9의 `count`도 같은 규칙으로 막았다.
- **§3-4 상수 import** — `warning.ts`의 `SYNC_STALLED_DAYS`·`INVENTORY_LOW_SLOTS_THRESHOLD`를
  import한다. 값 복사 없음(테스트가 상수를 참조해 임계값이 바뀌면 테스트도 같이 움직인다).
- **§3-5 #42** — 아래 「주요 의사결정」 참고.
- **§3-6 팬아웃** — `createNotification()`에 선택 인자 `client`를 추가해 배치가
  service_role 클라이언트를 **한 번 만들어 재사용**한다(T1 호출부는 생략 → 기존 동작 그대로).
  RPC 왕복은 동시 8개로 파이프라인화했다. 벌크 RPC는 채택하지 않았다 — 이유는 아래.
- **§3-7 멱등성** — **13종 전부 `group_key` + `once`.** `merge`를 쓰지 않은 이유까지 포함해
  DATA_MODEL §4-3을 신설했다.
- **§3-8 실패 격리** — `runStep()`이 단계를 격리하고, `emitDrafts()`가 소식 1건 단위로 격리한다.
  둘 다 `console.error`를 남긴다.

### 주요 의사결정 / 핵심 메모

**1. #42는 (가) "생성 조건을 잔여 0칸으로" 를 택했다** (§3-5)

이 티켓은 §4에서 **문구를 만들지 않기로 못박혀 있다.** (나)를 택하면 `ko.ts`의
`msgInventoryFull`을 고치고 PRD §3 ⑧ 표와 §5 강조 규칙 표(「42 … 슬롯 없음」)까지 함께
바꿔야 해서 021의 렌더러 범위를 침범한다. 그래서 문구는 그대로 두고 사실과 맞을 때만 보낸다.

`INVENTORY_LOW_SLOTS_THRESHOLD`는 버리지 않고 **후보 스캔**에 계속 쓴다(§3-4 준수). 그리고
T3 경고 재평가는 기존대로 잔여 3칸 이하까지 경고를 유지하므로 "칸 하나 비웠다고 경고가
사라지는" 문제도 생기지 않는다. 잔여 1~3칸 구간을 알리고 싶어지면 그때 문구를 새로 정의하는
별도 티켓으로 다룬다.

**2. #23을 위해 `mission_rank_snapshots` 테이블을 신설했다 (마이그레이션 099, 미실행)**

"상승 시만"은 직전 순위를 알아야 판정된다. 순위는 어디에도 저장되지 않고 status API가 매번
계산한다. 기존 소식 행을 기준선으로 쓰는 안은 **첫 기준선을 만들 수 없어**(소식이 있어야
기준선이 생기고 기준선이 있어야 소식이 생긴다) 영원히 발화하지 않는다.

- 첫 배치는 **기준선만 남기고 소식을 만들지 않는다** — 오르지도 않은 유저에게
  "5위로 올라섰어요"가 나가면 거짓말이다.
- 마이그레이션이 아직 적용되지 않아도 **`mission-rank` 단계만 실패**하고 나머지 12종은 정상
  생성된다. 무증상이 되지 않도록 `[notifications-batch] 단계 실패 — mission-rank` 로그가 남는다.
- 정렬 규칙을 `lib/missions/ranking.ts`로 뽑아 status 라우트와 배치가 **같은 비교 함수**를
  쓰게 했다. 복사해 뒀다면 "5위로 올라섰어요"를 눌러 들어간 화면이 6위를 보여줄 수 있다.

**3. 벌크 RPC(`p_user_ids UUID[]`)는 채택하지 않았다** (§3-6)

블래스트 반경 때문이다. 벌크 RPC를 만들면 **마이그레이션이 적용되기 전까지 13종 전부가
생성되지 않는다.** 반면 클라이언트 주입 + 동시 8개 파이프라인은 DDL 의존이 전혀 없고,
현재 규모(유저 수 기준 수백~수천 왕복)에서는 `maxDuration = 60` 안에 충분히 들어온다.
왕복이 병목이 되는 시점에 별도 티켓으로 벌크 RPC를 도입하는 편이 안전하다.

**4. 재발송 정책 — `group_key`에 "날짜"가 아니라 "상태의 시작 시점"을 넣었다**

배치는 매일 도는데 일자 키 + `once`를 쓰면 상태가 유지되는 동안 **매일 새 소식**이 나간다
(PRD §2-4가 금지한 반복 발송). 상태가 바뀔 때만 키가 바뀌게 하면 `once` 하나로
"해소될 때까지 침묵"이 구현된다.

- #9 : `collection_slottable:{book_id}:{최신 미장착 아이템의 획득 KST일자}`
  → 그 컬렉션에 넣을 **새 아이템**이 들어와야 다시 알린다.
  `{book_id}`만 쓰면 평생 1회가 되어 이후 아이템이 쌓여도 침묵한다.
- #41: `sync_stalled:{정체 시작 KST일자}` → 다시 동기화한 뒤 또 정체돼야 다시 알린다.
- #42만 예외로 발송 이력을 SELECT한다. 인벤토리에는 "언제부터 꽉 찼는가"를 알 수 있는 데이터가
  없어 상태 시작 시점을 키에 넣을 수 없다. 일자 키로 재시도 멱등성을 확보하고 최근 7일 내
  발송 이력이 있으면 건너뛴다.
- #18은 "주 1회"를 요일 게이트가 아니라 `{poi_id}:{KST주}` + `once`로 구현했다. 집계 창이
  지난 7일 롤링이라 어느 요일에 돌아도 결과가 같고, cron 실패로 하루를 건너뛰어도 복구된다.

**5. ⑥ 하루 상한 2건의 선별 — 희귀도 단독(PRD §9)**

mythic → legend → 컬렉션 완성(#30) → 미션 완료(#31) → 근처 드랍(#32), 동순위는 최근 이벤트
우선. #30·#31·#32는 희귀도 축이 없어 "얻기 어려운 순"으로 고정 우선순위를 줬다.
친밀도 지표가 생기면 PRD §9에 따라 재검토한다.

**6. #21에서 단위 없는 달성형 미션(poi_visit·item_collect)은 제외했다**

문구가 `{remaining} 남았어요`라 목표치가 0/1인 미션에서는 "1 남았어요"가 된다. 문장이 아니다.
#20(마일스톤)이 같은 이유로 이미 제외하고 있어 규칙이 일관된다. 이 유형에 마감 임박을
보내려면 새 문구가 필요하고, 그건 이 티켓 범위 밖이다.

### 잔여 이슈

- **마이그레이션 099 미실행** — `mission_rank_snapshots`. 적용 전까지 #23만 생성되지 않는다
  (나머지 12종은 정상). 적용 후 `[notifications-batch] 단계 실패 — mission-rank` 로그가
  사라지는지 확인할 것.
- **`users.region`이 비어 있어 #32·#34는 발화하지 않는다** — DB 기본값이 `''`이고 온보딩은
  username만 저장한다(어떤 코드도 이 컬럼을 쓰지 않는다). 코드는 완성돼 있으나 지역 입력
  경로가 생겨야 동작한다. 빈 문자열끼리 "일치"로 보면 지역 미설정 유저 전원이 서로 묶여
  대량 오발송이 되므로 배치가 빈 region을 명시적으로 제외한다. PRD §9에 남은 질문으로 추가.
- **#34의 POI→지역 판정이 외부 API(NCP 역지오코딩)에 의존한다.** region 설정 유저가 없으면
  호출 자체를 건너뛰고, 있어도 배치당 최대 50개 POI로 제한한다. `poi`에 region 컬럼을 두는
  편이 근본적이지만 스키마·수집 파이프라인 변경이라 별도 티켓 대상이다.
- **배포 직후 확인** — 021이 넣어둔 `missingMessageSlots()` 경고
  (`console.warn('[notifications] 빈 슬롯', …)`)가 서버 로그에 찍히지 않는지 확인할 것.
  테스트로 잠갔지만 실데이터(이름이 빈 배지·컬렉션 등)에서 새어 나올 수 있다.
- **첫 실행 규모** — #24(종료 결과)는 최근 2일 내 종료 미션, #18은 활성 드랍이 있는 POI로
  제한돼 있어 첫 실행이 폭주하지 않는다. 다만 #9·#10은 **전 유저 × 전 컬렉션** 스캔이라
  첫 실행에서 소식이 한꺼번에 생길 수 있다(모두 `once`라 다음 날부터는 잠잠해진다).
