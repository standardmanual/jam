# [bug] 미들웨어가 cron 요청을 차단해 예약 작업이 실행되지 않음

## 배경 / 문제 정의

`jam-web/src/proxy.ts`의 미들웨어가 `/api/cron/*`를 가로채, **Vercel cron 호출이 라우트
핸들러에 닿지 못하고 307 리다이렉트된다.** 결과적으로 예약 작업 전부가 조용히 실행되지 않는다.

[20260825_002](20260825_002_API_알림소식-배치-cron.md)의 게이트 리뷰에서 발견됐다.

### 원인

`proxy.ts`의 `config.matcher`가 정적 파일만 제외하므로 `/api/cron/*`도 미들웨어를 탄다.
그런데 `publicPaths`에 cron 경로가 없다.

```js
publicPaths = ['/login', '/auth/callback', '/forbidden', '/api/dev-login', '/spike']
```

Vercel cron은 `Authorization: Bearer $CRON_SECRET`만 보내고 **Supabase 세션 쿠키가 없다.**
따라서 `user`가 null → `!user && !isPublicPath` → 307 리다이렉트.

### 증거

| 지표 | 값 | 의미 |
|---|---|---|
| 만료됐는데 `is_available=true`인 드랍 | **1건, 13시간 경과** | `poi-cleanup`(매일 00:00 UTC)이 돌았다면 정리됐어야 함 |
| `poi_drops` 중 `source='system'` | **0건** | `ambient-drop-monitor`(매일 18:00 UTC)가 한 번도 생성 안 함 |
| 프로덕션 curl | 3개 cron 경로 모두 **307** | 핸들러 미도달 |

`poi-cleanup`은 누구도 "미사용 기능"이라 할 수 없는 핵심 정리 작업인데 명백히 안 돌고 있다.

### 왜 지금 고쳐야 하나

[20260825_002](20260825_002_API_알림소식-배치-cron.md)의 알림 배치가 같은 경로를 쓴다.
이 상태로 배포하면 **배치가 죽은 채로 나간다.** 002가 3차 보강으로 넣은 "단계 실패 시
non-2xx 반환"조차 핸들러에 닿지 못해 무의미해진다.

## 상세 요구사항

`publicPaths`에 `/api/cron`을 추가한다.

**보안이 약해지는 게 아니다** — cron 라우트 3개(`poi-cleanup`·`ambient-drop-monitor`·
`notifications`)가 **전부 자체적으로 `CRON_SECRET` Bearer 토큰을 검사**한다(확인 완료).
인증 주체가 미들웨어에서 라우트로 옮겨질 뿐이며, 애초에 세션 인증은 cron에 맞지 않는 수단이다.

## 구현 계획

경미 수정(1파일·1줄)이라 파이프라인 없이 직접 처리한다.

### 주요 의사결정 / 핵심 메모

- **미들웨어에서 빼는 쪽을 택했다.** 대안은 미들웨어가 `CRON_SECRET`을 직접 검사하는 것인데,
  그러면 인증 로직이 두 곳으로 갈라지고 라우트별로 다른 시크릿을 쓰기 어려워진다.
  라우트가 이미 검사하고 있으므로 미들웨어는 비켜서는 게 맞다.
- **`matcher`를 고치지 않은 이유** — `matcher`에서 제외하면 미들웨어가 아예 실행되지 않아
  Supabase 세션 갱신(`supabase.auth.getUser()`)도 건너뛴다. 지금은 무관하지만 향후 cron이
  세션 컨텍스트를 필요로 하게 되면 원인 찾기가 어려워진다. `publicPaths`는 "미들웨어는 타되
  리다이렉트하지 않는다"는 의미라 의도가 더 명확하다.

### 잔여 이슈

- **배포 후 cron이 실제로 도는지 확인해야 한다.** 이 티켓은 차단 요인을 제거했을 뿐,
  cron이 지금까지 안 돌았다는 것이 **추정**이다(Vercel 대시보드 Cron 실행 로그 미확인).
  확인 방법:
  1. `curl -H "Authorization: Bearer $CRON_SECRET" https://j-a-m.app/api/cron/notifications`
     → 307이 아니라 JSON 응답이 오는지
  2. 다음날 만료 드랍이 `is_available=false`로 정리됐는지
  3. Vercel 대시보드 Cron 탭의 실행 이력
- 이 문제가 언제부터였는지는 추적하지 않았다. `proxy.ts`의 `publicPaths` 도입 시점부터일 것이다.
