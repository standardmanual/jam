# [Feature] 앰비언트(시스템) 드랍 기능 제거

## 배경 / 문제 정의

유저 행동과 무관하게 시스템이 POI에 아이템배지를 상시 배치하는 **앰비언트 드랍**을 제거한다.
사용자 결정(2026-08-25).

### ⚠️ 판단 경위를 정확히 남긴다

이 결정은 **"기능이 미완성이라서"가 아니다.** 오해 없이 기록해 둔다.

`poi_drops`에 `source='system'` 행이 **0건**인 것이 발견의 계기였으나, 원인을 추적한 결과
**cron 자체가 실행되지 않고 있었다** — 미들웨어가 `/api/cron/*`를 307로 가로채고 있었다
([20260825_003](20260825_003_bug_미들웨어가-cron-요청을-차단.md)에서 수정, 프로덕션 배포 후
`307 → 401` 전환으로 확정).

즉 **앰비언트 드랍이 0건인 것은 기능 결함이 아니라 cron 차단 탓일 가능성이 높다.**
기능 자체는 갖춰져 있었다.

| 지표 | 상태 |
|---|---|
| `ambient_drop_policy` | **정책이 튜닝돼 있음** — common 86%/rare 12%/legend 2%, 커버리지 15%, POI당 1개, 보충 30개 (최종 수정 2026-07-23) |
| 어드민 화면 | **있음** (`/admin/ambient-drop-policy`) |
| PRD | **✅ 완료**로 3곳에 기재 |
| 코드 | `lib/ambient-drop/` 2파일 + cron 라우트 |

오케스트레이터가 "cron을 고쳤으니 하루 관측 후 판단하자"고 두 차례 제안했으나,
**사용자가 관측과 무관하게 기능을 쓰지 않기로 결정**했다. 되살릴 경우 이 티켓의 역순으로
복원하면 되며, 정책 값은 위 표에 남겨 두었다.

### 2. `poi_drops.source` — 판단이 필요하다

`source`는 `'user' | 'system'` 두 값인데, 앰비언트가 사라지면 **`'user'` 하나만 남아 컬럼이
사실상 무의미해진다.** 다만 제거 범위가 넓다.

`source`에 의존하는 곳:
- `api/drops/[dropId]/route.ts` — `is_ambient`, `dropper_name` 분기
- `api/drops/[dropId]/pickup/route.ts`
- `api/drops/poi/[poiId]/route.ts`
- `app/(main)/drops/BadgeDetailSheet.tsx` — 앰비언트 표시 분기
- `lib/activity-feed/index.ts`
- **마이그레이션 047의 `pickup_drop()` RPC** ← 핵심 유저 경로

**구현자가 판단할 것.** 판단 기준:

- `pickup_drop()` RPC는 **픽업이라는 핵심 유저 경로**다. 여기를 건드렸다가 회귀가 나면
  앰비언트 제거보다 훨씬 큰 손해다.
- 컬럼을 남겨도 실해는 없다(전 행이 `'user'`, 0건 오염 없음).
- 반대로 죽은 분기를 남기면 다음 사람이 "앰비언트가 뭐지?"를 다시 추적하게 된다.

→ **(가) 컬럼까지 제거** 또는 **(나) 컬럼은 남기되 죽은 표시 분기만 정리하고 컬럼에
"레거시 — 전 행 'user'" 주석을 남긴다** 중 택일하고, **근거를 완료 기록에 남길 것.**
어느 쪽이든 `pickup_drop()` 회귀 검증은 필수다.

### 주요 의사결정 / 핵심 메모

**§2 `poi_drops.source` — (나) 컬럼 유지 + 죽은 분기 정리를 선택했다.**

근거:

1. **`pickup_drop()`은 사실 `source`를 안 읽는다. 진짜 의존처는 `assign_random_serial()` 트리거다.**
   047의 `pickup_drop()`은 `SELECT * INTO v_drop`뿐이라 컬럼을 지워도 그대로 동작한다. 반면
   044의 `assign_random_serial()`은 `SELECT (source = 'system') FROM poi_drops WHERE id = NEW.drop_id`로
   이 컬럼을 직접 조회한다. 이 트리거는 `inventory_items` **BEFORE INSERT** 전체에 걸린다 —
   픽업뿐 아니라 드랍엔진 발급·믹스·미션 보상까지. 즉 컬럼 제거의 폭발 반경은 픽업 하나가 아니라
   **아이템 획득 경로 전부**다. (티켓 §2가 지목한 것보다 넓다)
2. **`poi_drops_source_consistency` CHECK가 유저 드랍의 무결성을 지킨다.**
   이 제약이 `source='user' → dropper_user_id NOT NULL AND expires_at NOT NULL`을 강제한다.
   컬럼을 지우면 이 장치를 다시 설계해야 하는데(두 컬럼에 NOT NULL 재부여 등), 앰비언트 제거로
   얻을 것이 없는 순수 리스크다.
3. **남겨도 실해가 없다.** 전 행이 `'user'`이고 DB DEFAULT도 `'user'`라, 생성 경로가 사라진 이상
   `'system'`은 다시 만들어지지 않는다.

"다음 사람이 앰비언트가 뭔지 다시 추적하게 된다"는 우려는 **주석으로 봉인**했다 —
`PoiDropSource` 타입 주석, `PoiDropRow.source` 필드 주석, DB `COMMENT ON COLUMN`,
`02_DATA_MODEL.md`의 `poi_drops` 절, `BADGE_ENGINE_UNIFIED.md` §3.12 네 곳에서 모두
"레거시 — 전 행 `'user'`"와 그 이유를 명시했다.

**판단 경위 (문서에 정확히 남긴 것)**

이 제거는 미완성 기능을 접은 것이 **아니다**. `source='system'` 0건은 미들웨어가 `/api/cron/*`를
307로 가로채 cron이 아예 실행되지 않은 결과였다([20260825_003](./20260825_003_bug_미들웨어가-cron-요청을-차단.md)에서
수정, 프로덕션 307 → 401 전환으로 확정). 이 사실을 `01_PRD.md` §6 "안 만드는 것",
`BADGE_ENGINE_UNIFIED.md` §3.12, `04_PROJECT_SPEC.md` Cron 절, 서비스 플랜 v4.2, 마이그레이션 100
헤더 주석에 모두 명시했고, **복원용 정책값**(common 0.86 / rare 0.12 / legend 0.02, 커버리지 0.15,
min 20 / max 2000, POI당 1개, 보충 30개)도 함께 남겼다.

### 잔여 이슈

- **마이그레이션 100 미실행** — 승인 후 오케스트레이터가 실행한다. 실행 전까지
  `ambient_drop_policy` 테이블은 DB에 남아 있으나 참조하는 코드가 없어 무해하다.
- **마이그레이션 100의 `DELETE FROM poi_drops WHERE source='system' AND is_available=TRUE`는
  티켓 §1 표에 없는 추가 항목이다.** 근거: (ㄱ) 20260825_003으로 cron이 살아난 뒤 이 티켓이
  배포되기 전 사이에 `0 18 * * *` 스케줄이 한 번이라도 실행됐다면 앰비언트 드랍이 실제로
  생성됐을 수 있고, (ㄴ) 앰비언트 드랍은 `expires_at IS NULL`이라 `poi-cleanup`이 영원히
  회수하지 못하며, (ㄷ) 표시 분기를 제거했으므로 그런 행은 화면에 '익명'이 드랍한 것으로
  보인다. 픽업이 끝난 행(`is_available = FALSE`)은 `inventory_items.drop_id`가 참조하므로
  건드리지 않는다. **범위 밖이라 판단되면 이 DELETE 블록만 빼고 실행해도 나머지는 문제없다.**
