# [UI] 푸터를 항상 화면 바깥쪽(스크롤 하단)에 위치시킨다

## 배경 / 문제 정의
전역 `Footer`(`jam-web/src/components/ui/Footer.tsx`)는 각 페이지 `main` 스크롤 컨테이너 안에서
`{children}` 바로 뒤에 렌더링된다. 컨텐츠가 뷰포트를 채울 만큼 많으면 자연스럽게 스크롤해야
보이지만, 컨텐츠가 적은 화면(예: 항목이 적은 리스트, 빈 상태)에서는 `main`의 남는 공간에
푸터가 그대로 나타나 화면 중간쯤에 떠 보인다.

기대 동작: 컨텐츠 양과 무관하게 푸터는 항상 뷰포트 바깥(스크롤해야 보이는 위치)에 있어야 한다 —
컨텐츠가 많으면 자연히 아래로 밀려나고, 적으면 빈 공간만큼 푸터도 함께 아래로 밀려나야 한다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `jam-web/src/app/(main)/layout.tsx`의 `main` 스크롤 컨테이너 구조 수정
  - `{children}`을 감싸는 wrapper에 `min-h-full`(스크롤 컨테이너의 가시 높이 100%)을 적용해,
    컨텐츠가 짧아도 컨텐츠 영역이 뷰포트 높이만큼 확보되고 `Footer`는 항상 그 아래로 밀려나게 한다
  - 표준 CSS "sticky footer" 트릭(`overflow:auto` 스크롤 부모 + `min-height:100%` 자식) 적용
- `jam-web/src/app/admin/badges/BadgeDetailPreviewFrame.tsx`는 실제 배지 상세화면과 동일 구조를
  재현하는 어드민 미리보기 컴포넌트다 — 동일 구조 변경이 필요한지 확인만 하고, 어드민 전용 기존
  고정 프레임 크기(932px) 특성상 실익이 없으면 변경하지 않는다 (판단은 구현 단계에서)

### UI/UX 관점 (해당 시)
- 시각적으로 푸터 자체의 스타일·문구는 변경하지 않는다. 위치 로직만 수정한다.
- TabBar(고정 플로팅 캡슐)와의 겹침이 새로 생기지 않는지 확인한다 (`main`의 기존
  `pb-[calc(5rem+env(safe-area-inset-bottom))]`가 이미 TabBar 회피용 패딩 — 유지)

## 구현 계획
`min-h-full` 래퍼 적용 후 컨텐츠가 짧은 화면(예: 빈 상태 화면)과 긴 화면(예: 배지 목록) 양쪽에서
브라우저로 직접 확인한다. 재사용 판정: 기존 `Footer`/`layout.tsx` 구조를 그대로 쓰고 새 컴포넌트를
만들지 않으므로 0.5단계 탐색에서 신규 UI 불필요로 판정.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
`(main)/layout.tsx`의 `main` 스크롤 컨테이너 안에서 `{children}`을 `min-h-full` 래퍼 div로 감싸는
표준 CSS sticky-footer 트릭을 적용했다. `overflow-y-auto`인 `main`이 스크롤 부모, 새 래퍼가
`min-height: 100%` 자식이 되어 컨텐츠가 짧아도 컨텐츠 영역이 뷰포트(정확히는 `main`의 가시 높이,
TabBar 회피용 `pb`가 이미 빠진 영역) 높이만큼 확보되고 `Footer`는 항상 그 아래로 밀려난다.
`Footer` 자체 스타일·문구는 변경하지 않았다.

`admin/badges/BadgeDetailPreviewFrame.tsx`는 확인 결과 변경하지 않았다 — 고정 프레임(430×932)
안에서 배지 상세화면과 동일 구조(Hero + 조건 카드)를 렌더링하는데, Hero 섹션 자체가 이미
프레임 높이에 가깝게 크므로 컨텐츠가 짧아 Footer가 중간에 뜨는 문제가 재현되지 않아 실익이 없다고
판단했다(오케스트레이터 판정에 따른 스킵 허용 범위).
