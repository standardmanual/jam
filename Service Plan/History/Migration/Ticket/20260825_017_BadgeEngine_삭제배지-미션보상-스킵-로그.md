# [BadgeEngine] 삭제 배지로 인한 미션 보상 스킵을 엔진 로그에 기록

> 티켓 20260825_016 개선 리뷰(progressive-reviewer) 후속 제안.

## 배경 / 문제 정의

20260825_016에서 `grantMissionRewards()`(`jam-web/src/lib/missions/rewards.ts:42`)의 보상 배지
조회 쿼리에 `.is('deleted_at', null)` 필터를 추가해, 소프트 삭제된 배지는 조회 결과에서
제외되고 지급도 조용히 스킵되도록 했다.

같은 함수 내 "인벤토리 없음" 케이스(`no_inventory`, `rewards.ts:91`)는
`logEngineDecision('drop', 'drop_attempt', ...)`으로 기록을 남기는데, 정작 이번 정책의 핵심
시나리오(삭제된 배지라 스킵)는 아무 흔적도 남기지 않는다. "왜 유저가 보상 배지를 못 받았는지"를
운영/디버깅 관점에서 사후에 SQL 조회만으로 재구성할 수 없다는 뜻이다 — `engine-log`
모듈이 원래 존재하는 목적(`jam-web/src/lib/engine-log/index.ts` 상단 문서 참조)에 정확히 부합하는
공백이다.

또한 조회 결과가 요청보다 적은 원인은 두 가지로 서로 다르다.
- (a) 배지가 정책적으로 삭제되어 스킵 — 정상 동작
- (b) `mission.reward_badge_ids` 설정 실수로 애초에 존재하지 않는 badge_id가 들어감 — 데이터 오류

이 둘을 구분하지 않고 뭉뚱그려 기록하면 오지급이 아닌 설정 실수를 늦게 발견하게 된다.
`deleted_at`이 세팅된 `badges` 행이 실제 존재하는지 여부로 두 케이스를 구분할 수 있다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `grantMissionRewards()`에서 요청한 `badgeIds.length`와 조회된 `badges.length`를 비교해
  차이가 있으면 `logEngineDecision`으로 한 줄 기록한다.
- 차이가 난 badge_id들을 별도 조회(삭제 여부 포함 전체 조회)해 "삭제됨"과 "존재하지 않음"을
  구분해 payload에 담는다.
- `engine-log`의 기존 사용 패턴(`no_inventory` 사례)과 이벤트 네이밍·로그 실패 처리 방식을
  일관되게 맞춘다. 신규 이벤트명이 필요하면 `EngineDecisionEvent` 유니온에 추가한다
  (payload 컬럼은 CHECK 제약이 없으므로 마이그레이션 불필요 — `engine` 컬럼 값을 새로
  추가할 때만 마이그레이션 필요, 이번엔 기존 `'badge'` 재사용이라 불필요).

## 구현 계획
1. `EngineDecisionEvent`에 `'reward_badge_skipped'` 추가 (`jam-web/src/lib/engine-log/index.ts`)
2. `rewards.ts`에서 배지 조회 후 `badges.length < badgeIds.length`면:
   - 빠진 badge_id 목록 계산
   - 빠진 id들을 삭제 여부 무관하게 재조회해 "삭제됨" / "존재하지 않음"으로 분류
   - `logEngineDecision('badge', 'reward_badge_skipped', userId, { source: 'mission_reward', missionId, deletedBadgeIds, nonexistentBadgeIds })` 호출
3. `npx tsc --noEmit` 통과 확인

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- `EngineDecisionEvent`에 `'reward_badge_skipped'` 이벤트 추가.
- `grantMissionRewards()`에서 요청한 `badgeIds.length`와 조회된 `badges.length`를 비교해
  차이가 있으면, 빠진 badge_id들을 `deleted_at` 포함 재조회해 "삭제됨"(`deletedBadgeIds`)과
  "존재하지 않음"(`nonexistentBadgeIds`)으로 분류한 뒤 `logEngineDecision('badge',
  'reward_badge_skipped', userId, { source: 'mission_reward', missionId, deletedBadgeIds,
  nonexistentBadgeIds })`로 기록.
- 기존 `no_inventory` 사례와 동일하게 로그는 본 지급 흐름을 막지 않고(logEngineDecision 자체가
  실패를 삼키는 정책) 부가 정보로만 남긴다.

### 주요 의사결정 / 핵심 메모
- "삭제됨"과 "존재하지 않음"은 빠진 badge_id를 `deleted_at` 컬럼 포함해 재조회한 뒤,
  반환된 행의 `deleted_at`이 null이 아니면 삭제됨, 아예 반환되지 않으면 존재하지 않음으로 구분.
- 새 engine 값 추가가 아니라 기존 `'badge'`를 재사용하므로 DB 마이그레이션 불필요(티켓 명시대로).
