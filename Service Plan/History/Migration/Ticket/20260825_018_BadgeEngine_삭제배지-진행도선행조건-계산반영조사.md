# [BadgeEngine] 소프트 삭제 배지의 진행도·선행조건 계산 반영 여부 조사 (research)

> 20260825_017 완료 기록 "주요 의사결정"에서 badge-engine/index.ts의 미해결 정책 이슈로
> 추정된 사항의 후속 조사. 004→005→007→009→015→017로 6차례 반복된 "필터 누락" 패턴과는
> 성격이 다른 이슈인지 확인하기 위한 순수 조사(코드 무변경) 티켓.

## 배경 / 문제 정의

017 완료 기록: `badge-engine/index.ts`의 `.from('badges')` 유일 호출(라인 543)에는 이미
`.is('deleted_at', null)` 필터가 걸려 있어 **필터 누락 문제는 아니다**. 017 작업자는 남은
미해결 이슈가 "이미 지급된(user_activity_badges에 기록된) 삭제 배지가 진행도/선행조건
계산에 계속 반영되는 문제"일 가능성이 높다고 추정했다. 이번 티켓은 그 추정을 코드로
검증한다.

## 조사 결과

### 1. 실제로 존재하는 문제 확인됨 — 필터 누락이 아니라 로직 순서 문제

`evaluateBadgesDetailed()`(`jam-web/src/lib/badge-engine/index.ts:543~586`)의 흐름:

1. `allBadges` = `badges` 테이블에서 `type='activity'` AND `deleted_at IS NULL`로 조회
   (543~551행) — **카탈로그는 정상적으로 삭제 배지를 제외한다.**
2. `ownedBadgeIds` = `user_activity_badges`에서 `user_id`로 조회한 `badge_id` 집합
   (558~570행) — **여기는 `deleted_at` 필터가 없다 (올바름 — 이력 테이블이므로).**
3. **문제 지점**: `ownedBadgeNames`(선행조건 게이트용)와 `highestOwnedTierByName`
   (진행 트랙 최고 티어 판정용)를 만드는 두 반복문(573~585행)이 `ownedBadgeIds`를
   직접 순회하지 않고, **이미 삭제 배지가 빠진 `allBadges`를 순회하면서
   `ownedBadgeIds.has(b.id)`로 걸러낸다.**
   ```
   for (const b of allBadges) {              // allBadges는 이미 deleted_at IS NULL
     if (ownedBadgeIds.has(b.id)) ownedBadgeNames.add(b.name)
   }
   for (const badge of allBadges) {           // 동일 패턴
     if (ownedBadgeIds.has(badge.id)) { ...highestOwnedTierByName... }
   }
   ```
   그 결과, 유저가 실제로 획득한(`user_activity_badges`에 행이 있는) 배지라도 그
   **배지 정의(badges 행)가 나중에 소프트 삭제되면 `allBadges`에서 빠지므로
   `ownedBadgeNames`/`highestOwnedTierByName`에도 반영되지 않는다** — 즉 엔진이
   "이 유저는 이 배지를 가진 적이 없다"고 잘못 판단한다.

### 2. 영향받는 두 가지 판정 (둘 다 확인됨)

- **선행조건 게이트 오작동** (612~619행): `prerequisite_badge_names`에 지정된 배지를
  유저가 실제로 보유했더라도, 그 배지가 나중에 삭제되면 `ownedBadgeNames`에서 빠져
  `prereqs.some(n => ownedBadgeNames.has(n))`이 거짓이 된다. → 이미 선행조건을
  만족한 유저가 상위 배지(Rare/Legend/Mythic)를 영영 발급받지 못하게 막힌다
  (`missed`에 "선행 배지 미보유"로 잘못 기록됨).

- **진행 트랙 역행/중복 발급 위험** (578~585, 605~610행): "이름당 최상위 티어 1개만
  보유"가 전제인 성장 배지 트랙에서, 유저가 이미 획득한 최고 티어(예: Epic)가 나중에
  삭제되고 하위 티어(Rare/Common)는 살아있는 경우, `highestOwnedTierByName`이 0으로
  계산돼 하위 티어가 다시 "미보유·발급 가능"으로 취급된다. 유저는 이미 Epic까지
  달성했는데 엔진 입장에서는 처음부터 다시 시작하는 것처럼 보여, 이미 능가한 하위
  티어가 재발급될 수 있다.

### 3. 004의 확립된 정책과 대조 — 이건 정책 미정이 아니라 그 정책의 적용 누락

20260823_004 티켓에서 이미 사용자 승인으로 확정된 원칙(코드 주석에도 명시):
> "이미 발급된 유저의 이력은 FK 그대로 참조, 하드 삭제 시 위반/이력 소실" —
> 소프트 삭제는 **노출/신규 지급만 막고, 이미 획득한 유저의 이력은 그대로 유지**한다.

이 원칙은 20260825_016(미션 보상 지급 정책)에서도 "카탈로그 조회만 필터링, 지급 로직은
그 결과를 따라간다"는 형태로 일관되게 적용됐다. 그런데 badge-engine의 진행도/선행조건
계산은 **유저의 과거 획득 이력(`user_activity_badges`)을, 이미 삭제 필터가 걸린
카탈로그(`allBadges`)를 매개로 재해석**하고 있어, 결과적으로 "이력은 유지"라는 원칙과
반대로 동작한다 — 유저가 실제로 가진 이력이 카탈로그에서 사라지는 순간 없던 일처럼
취급된다.

즉 이건 "삭제된 배지를 어떻게 취급할지"를 새로 정해야 하는 미정 정책이 아니라,
**이미 정해진 정책(이력 유지)이 이 두 계산 지점에서만 깨져 있는 로직 결함**으로
판단된다. `BADGE_ENGINE_UNIFIED.md`에도 이 갭을 인지한 문서화는 없음(§2.12는 미션
보상 지급만 다룸, 진행도/선행조건 언급 없음).

### 4. `BADGE_ENGINE_UNIFIED.md` 대조 결과

§2.5(진행 트랙 정책)·§2.7(첫 싱크 게이트+선행 배지 게이트) 어디에도 "배지 정의가
삭제된 경우 유저의 기존 보유 이력을 어떻게 반영하는지"에 대한 언급이 없다 — 이 갭은
문서화되지 않은 상태였다.

## 결론 및 후속 조치 제안

문제가 실재하며, 004에서 이미 확정된 정책(이력 유지)의 적용 누락으로 판단된다.
다만 두 가지 이유로 구현에 바로 들어가지 않고 사용자 확인을 거치기로 한다:

1. 실제 발생 가능성 — 활동 배지가 소프트 삭제되는 경로 자체가 드물어(어드민 수동
   삭제 또는 소속 아이템배지 컬렉션 비활성화 연쇄, activity 타입은 컬렉션 소속이
   아니므로 사실상 어드민 수동 삭제만 해당) 실사용 영향 범위가 크지 않을 수 있다.
2. 수정 방향에 두 가지 선택지가 있어 확정이 필요하다:
   - (a) `ownedBadgeNames`/`highestOwnedTierByName`을 `allBadges`가 아니라
     `ownedBadgeIds`를 위한 별도의 (deleted_at 필터 없는) 배지 이름/티어 조회로
     계산 — 삭제 여부와 무관하게 유저의 실제 이력을 그대로 반영
   - (b) 그대로 두되 이 갭을 의도된 동작으로 문서화(비권장 — 004 원칙과 모순)

**권장**: (a). 근거는 위 §3.

이번 티켓은 조사만 수행하며 코드를 변경하지 않는다. 사용자 확인 후 구현이 필요하면
별도 `engine` 유형 티켓으로 분리한다.

않았다. 004에서 확정된 "이력 유지" 원칙에 비춰보면 이는 새 정책 결정이 필요한 사안이
