# [Service] 스테이징 전용 테스트 계정이 프로덕션 유저 화면에 노출됨

## 배경 / 문제 정의
`jam-web/src/app/api/dev-login/route.ts`가 로컬 개발·staging 전용 구글 로그인 우회를 위해
고정 UUID(`00000000-0000-0000-0000-000000000001`, username `589132427_stage`)로 테스트 유저를
생성한다. staging과 production은 동일한 Supabase DB를 공유하는 구조라서(이 프로젝트의 알려진
제약 — `Service Plan` 내 관련 메모 참조), 이 테스트 계정이 그대로 프로덕션의 랭킹/리더보드,
팔로잉·팔로워 목록, 피드, 유저 검색 등 실제 유저에게 노출되는 화면에 함께 표시된다.

동일 DB 공유 구조상 이 계정을 직접 삭제하거나 DB 레벨에서만 숨기면 staging에서의 테스트 용도
(로그인 우회 확인)까지 함께 사라진다. 따라서 **삭제가 아니라 환경별 조건부 필터**로 처리해야 한다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 프로덕션(= `STAGING_MODE !== 'true'` && `NODE_ENV !== 'development'`)에서만 이 고정 테스트
  유저 ID(`00000000-0000-0000-0000-000000000001`)를 공개 노출 쿼리에서 제외
- staging/로컬 개발 환경에서는 계속 노출 (테스트 계정 자체 확인 용도이므로 필터링하지 않음)
- 제외 대상 화면(전수 확인 필요, 아래는 확인된 후보):
  - 랭킹/리더보드 (미션 진행상황 랭킹형 유저 목록)
  - 팔로잉·팔로워 목록
  - 활동 피드
  - 유저 검색/프로필 탐색
  - 기타 "전체 유저" 성격의 공개 목록이 있다면 함께 확인
- `jam-web/src/app/api/dev-login/route.ts`의 `isAllowedEnv()` 판별 패턴을 재사용할 것
  (환경 판별 로직 이중 구현 금지 — 공용 헬퍼로 추출하는 것을 권장)
- 특정 유저 하나를 하드코딩 제외하는 방식이므로, 향후 테스트 계정이 늘어날 가능성을 고려해
  하드코딩 위치를 한 곳(상수/헬퍼)으로 모을 것

## 구현 계획
1. 환경 판별 + 제외 대상 유저 ID 목록을 반환하는 공용 헬퍼 작성 (예: `lib/env/test-accounts.ts`)
2. 위 헬퍼를 사용해 프로덕션에서만 조건부로 `.neq('user_id', ...)` 또는 동등한 필터를
   랭킹/팔로잉/피드/검색 등 공개 유저 목록 쿼리에 적용
3. 유사 패턴이 반복되는 위치가 많다면(020~026 배지 필터 사고와 유사한 반복 우려) 전수 grep으로
   "공개 유저 목록" 쿼리 지점을 먼저 특정한 뒤 일괄 적용

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
`isAllowedEnv()` 판별 패턴을 `jam-web/src/lib/env/test-accounts.ts`(신규)로 추출해
`isStagingOrDevEnv()`로 공용화하고, 스테이징 전용 테스트 계정 ID를 `TEST_ACCOUNT_USER_IDS`
배열 한 곳에 모았다. `excludedTestUserIds()`는 프로덕션에서만 이 배열을 반환하고
staging/로컬에서는 빈 배열을 반환한다. `dev-login/route.ts`는 이 헬퍼를 재사용하도록
수정(이중 구현 제거)했고, "공개 유저 목록" 성격의 조회 지점에 이 헬퍼로 필터를 적용했다.

전수 확인 결과 "공개 유저 목록" 지점은 다음 6개 기능·9개 파일이었다 (팔로잉/팔로워·유저
검색은 API 라우트와 서버 컴포넌트 페이지에 로직이 각각 인라인으로 중복 구현돼 있어 양쪽 다
수정 필요):
- 미션 랭킹/달성 현황 (`/api/missions/[id]/status`)
- 팔로워 목록 (API + 페이지)
- 팔로잉 목록 (API + 페이지)
- 유저 검색 (API + 페이지)
- POI 드랍 목록의 드랍한 유저 이름 (제외 대상이면 기존 "익명" 폴백으로 표시, 아이템 자체는 유지)

활동 피드(`/api/badges/recent-earned`, `[username]/page.tsx`의 피드 섹션)는 항상
`user_id = 특정 유저 한 명`으로 스코프되는 개인별 피드라 "여러 유저가 섞인 공개 목록"에
해당하지 않아 별도 필터를 적용하지 않았다 — 프로필 URL을 직접 알고 방문하는 경우는
이번 티켓 범위(공개 목록 노출) 밖으로 판단했다(잔여 이슈 참고).

### 주요 의사결정 / 핵심 메모
- 필터는 SQL 쿼리 단계(`.neq`/`.not…in`)가 아니라 조회 후 JS 배열 `.filter()`로 적용했다.
  대상 목록이 모두 최대 100~150건 규모로 제한돼 있어 성능 영향이 없고, PostgREST의
  `not(...,'in',...)` 구문 이스케이프 리스크를 피할 수 있어 더 안전하다고 판단(medium 근거).
- 팔로잉/팔로워·유저 검색은 API 라우트와 서버 컴포넌트 페이지가 같은 쿼리를 완전히 별도로
  인라인 구현하고 있었다(기존 구조, 이번 티켓 범위 밖). 공용 헬퍼(`excludedTestUserIds`)는
  두 구현 모두에 각각 적용해 로직 중복 자체는 그대로 두고 "환경 판별+제외 대상"만 단일화했다.

### 잔여 이슈
- 테스트 계정 프로필 페이지(`/589132427_stage`)를 URL로 직접 알고 방문하면 프로덕션에서도
  프로필·피드가 그대로 보인다. "공개 목록에 섞여 노출"이 아니라 "URL을 아는 사람만 접근"이라
  이번 티켓 범위(공개 유저 목록) 밖으로 판단해 손대지 않았다 — 필요하면 별도 티켓으로 분리 검토.
- 미션 참가자 수(`totalParticipants`), 팔로워/팔로잉 카운트(`/api/users/[username]/stats`) 등
  "목록"이 아닌 "숫자"에는 필터를 적용하지 않았다 — 티켓 요구사항이 명시적으로 "목록"이었고,
  카운트까지 건드리면 범위가 커져 별도 판단이 필요하다고 봤다.
