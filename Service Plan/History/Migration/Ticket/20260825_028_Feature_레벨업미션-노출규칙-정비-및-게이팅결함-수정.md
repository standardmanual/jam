# [Feature] 레벨업 미션 노출 규칙 정비 및 미션 게이팅 무력화 결함 수정

## 배경 / 문제 정의

티켓 [20260813_001](20260813_001_BadgeEngine_종목별-대표배지-레벨업-미션-게이팅-설계.md)로 도입된
"종목별 대표 배지 레벨업 미션 게이팅"(5개 트리 × Rare/Legend/Mythic = 미션 15종)에서 세 가지 문제가 확인됐다.

### 문제 1 — 완료한 미션이 계속 보이고 재참가까지 가능

미션 목록(`missions/page.tsx`)은 활성 미션을 **전부** 내려주고 클라이언트는 `done` 태그만 붙인다.
완료한 미션이 '진행중' 탭에 그대로 남고, `POST /api/missions/[id]/join`에도 완료 여부 검사가 없어
URL만 알면 재참가된다. 재참가해도 `user_mission_completions`의 `UNIQUE(user_id, mission_id)` 때문에
재완료·재보상은 불가능하므로, 노출과 참가 모두 무의미한 행동이다.

### 문제 2 — 상위 단계 미션이 동시에 노출돼 순서가 무너짐

레벨업 미션 15종은 서로 선행 관계가 없어 3단계가 동시에 보이고 동시에 참가된다.
조건이 포함 관계라 상위 미션 하나로 하위 미션이 함께 충족되기도 한다(연속 14일 달성 = 연속 7일도 달성).
실제로 **동네 산책러 레벨업/Hard/Ultra 3개를 모두 완료한 유저가 1명** 존재한다.
"레전드 배지를 받아야 하는 상태에서 미스틱용 미션까지 보이는" 상황이 그대로 발생 중이다.

### 문제 3 — 🔴 미션 게이팅이 이미 무력화돼 있음 (이번 조사 중 발견)

마이그레이션 [`084_badge_condition_cleanup.sql`](../../../../jam-web/supabase/migrations/084_badge_condition_cleanup.sql)(2026-08-13,
커밋 "배지 획득 조건 **표시** 정비")이 미션보상배지 15종의 `condition_json`에
`{"mission_reward": true}`를 UPDATE했다. 배지 상세 화면에서 미션 보상 배지임을 표시하려는 목적이었으나
(`badges/[id]/page.tsx:88`), 배지엔진 평가에 부작용이 생겼다:

```ts
// src/lib/badge-engine/index.ts:241 evaluateConditionDetailed
if (!condition || Object.keys(condition).length === 0) {
  return { pass: false, reason: '조건 없음' }   // ← 키가 1개라 여기 안 걸림
}
... 알려진 조건 필드가 하나도 없어 모든 검사 블록을 건너뜀 ...
return { pass: true, reason: '조건 충족' }      // ← 무조건 통과
```

`mission_reward`는 엔진이 모르는 필드라 어떤 검사에도 걸리지 않고 마지막 `pass: true`에 도달한다.
게다가 "○○ 레벨업 / 레벨업 Hard / 레벨업 Ultra"는 이름이 서로 달라 성장 티어 그룹으로 묶이지 않아
3개가 각각 독립 발급된다.

**결과**: 해당 종목 활동을 한 번만 동기화해도 미션 없이 미션보상배지 3개가 발급되고,
본 배지 Rare/Legend/Mythic의 `prerequisite_badge_names` 게이트가 전부 열린다.
티켓 20260813_001 결정사항 7번(`condition_json: null`로 생성해 `grantMissionRewards` 경로로만 지급)이
084에 의해 깨진 상태다. 유일하게 null로 남아 있던 '첫 숨결 레벨업' 1종만 원래 설계대로다.

**이 결함을 고치지 않으면 아래 [요구사항 5]의 배지 회수가 무의미하다** — 다음 동기화에 그대로 재발급된다.

## 상세 요구사항

### 1. 완료한 미션 숨김 (전체 45개 미션 공통)

- 완료 판정 기준은 **`user_mission_completions` 단일 기준**. "보상배지 보유" 기준을 쓰지 않는다 —
  배지 소프트삭제 시 지급이 스킵되는 정책(티켓 20260825_016·018) 때문에 완료했는데도 미션이 되살아난다.
- '진행중'·'참여중' 탭에서 제외한다.
- **'종료' 탭을 '완료/지난 미션'으로 확장**해 완료 건을 이쪽으로 보낸다.
  레벨업 미션은 `ends_at = NULL`(상시)이라 현재 종료 탭 조건(`ends_at < now`)에 영원히 걸리지 않는다.
  그냥 숨기면 유저가 자기가 완료한 미션을 어디에서도 볼 수 없다 — 성취 이력이 사라지면 안 된다.
- `POST /api/missions/[id]/join`에 **서버 가드** 추가 — 완료 기록이 있으면 409.
  UI 숨김만으로는 URL 직접 호출을 막지 못한다.

### 2. 상위 단계 미션 순차 노출 (레벨업 트리 15종 한정)

- **판정 기준은 본 배지 보유 등급** (미션 완료 기준이 아니다).
  예) '첫 숨결' Rare 배지를 실제로 획득해야 '첫 숨결 레벨업 Hard' 미션이 열린다.
- **바로 다음 1단계만** 참가 가능하게 노출한다.
- 아직 열리지 않은 **바로 그 다음 단계 1개는 잠금 카드**로 노출한다 —
  회색 처리, 참가 불가, "첫 숨결 Rare 획득 후 열려요" 안내. 그보다 위 단계는 목록에서 완전 제외한다.
- Common 배지 미보유 신규 유저에게도 **첫 레벨업 미션(Rare용)은 항상 노출**한다.
- 나머지 30개 기간형 미션은 [요구사항 1]만 적용한다.

### 3. 미션↔배지 연결을 데이터에 명시

현재는 `미션.reward_badge_ids` → 보상배지 이름 → 그 이름을 `prerequisite_badge_names`에 가진 본 배지 로
**역추적**해야만 트리·단계를 알 수 있다. 배지명이 바뀌면 조용히 끊기고, 목록 조회마다 badges JSONB
역참조가 필요하다. 미션 제목의 "Hard"/"Ultra" 문자열 파싱은 더 취약하다.

- `missions`에 **`gated_badge_id`**(이 미션이 여는 본 배지 id, nullable, FK → `badges.id`) 컬럼 추가.
  → 노출 판정이 "`gated_badge_id`의 rarity ≤ 유저 보유 등급 + 1"로 단순해진다.
- 레벨업 미션 15종에 값을 채우는 SQL을 함께 남긴다.
- **노출 판정 로직은 `src/lib/missions/`의 단일 함수로 모은다.**
  목록·상세·join API·오늘카드(`mission_spotlight`)가 같은 규칙을 쓰게 해야 규칙이 갈라지지 않는다.
- 어드민 미션 생성/수정 폼(`MissionList.tsx`)에도 `gated_badge_id` 선택을 추가한다.
  배지 선택 목록은 소프트삭제 필터(`deleted_at IS NULL`)를 반드시 건다 (티켓 20260825_019·026 선례).

### 4. 조건값·플래그 불일치 정리

**4-a. 미션보상배지 `condition_json` 통일 + 엔진 제외 분기 (문제 3의 해법)**

- 15종 전부 `{"mission_reward": true}`로 통일한다 ('첫 숨결 레벨업'만 현재 null).
  null 통일이 아닌 이유: 배지 상세 화면이 이미 이 플래그로 "미션 보상" 표시를 하고 있고,
  플래그가 있어야 엔진이 명시적으로 걸러낼 수 있다.
- **배지엔진이 `condition_json.mission_reward === true`인 배지를 발급 후보에서 제외**하도록
  명시적 분기를 추가한다 (Step 1 배지 조회 단계에서 거르는 쪽이 명확하다).
  `evaluateConditionDetailed`에도 방어 분기를 두어, 알 수 없는 필드만 있는 조건이
  `pass: true`로 떨어지지 않게 한다.
- 유닛테스트로 회귀를 막는다 — `{mission_reward: true}` 단독 조건이 절대 pass되지 않을 것.

**4-b. 5개 트리 조건값 3자 대조 결과 — 불일치 1건**

사용자 지시로 5개 트리 전체를 티켓·`ACTIVITY_BADGES.md`·DB 3자 대조했다. 결과:

| 트리 | Common | Rare | Legend | Mythic | 문서·티켓 | DB 현행 | 판정 |
|---|---|---|---|---|---|---|---|
| 동네 산책러 | 5km | 30km | 100km | 300km | 일치 | 일치 | ✅ |
| **첫 숨결** | 3km | 20km | **40km** | **100km** | 40/100 | **60/150** | ❌ **DB만 불일치** |
| 언덕의 도전자 | 100m | 500m | 1500m | 5000m | 일치 | 일치 | ✅ |
| 첫 고도 | 200m | 800m | 2000m | 6000m | 일치 | 일치 | ✅ |
| 야생의 주자 | 10km | 30km | 60km | 100km | 일치 | 일치 | ✅ |

가장 마지막 생성 기준은 **2026-08-13 확정값**이다 — 티켓 20260813_001과
`ACTIVITY_BADGES.md`(6행·199행 "60km/150km → 40km/100km로 하향 조정됨") 양쪽이 일치하고,
DB만 반영이 누락됐다. → **DB를 40km/100km로 맞춘다.**

### 5. 기존 이력 초기화 (테스터 데이터 정리)

현재 보유자는 전원 테스터·더미 계정이므로 게이팅을 원점에서 다시 시작한다. 실측치(2026-08-25 프로덕션 DB 재측정):

| 대상 | 건수 |
|---|---|
| 미션보상배지 15종 발급분 (`user_activity_badges`) | 104건 |
| 5개 트리 본 배지 Rare/Legend/Mythic 발급분 | 37건 |
| 레벨업 미션 15종 참가 기록 (`user_mission_participations`) | 33건 |
| 레벨업 미션 15종 완료 기록 (`user_mission_completions`) | 3건 |
| 미션보상배지 보유 유저 | 7명 |
| 본 배지 Rare+ 보유 유저 | 8명 |
| **삭제 SQL 영향 유저(합집합)** | **9명** (전원 테스터·더미 계정) |

> 최초 조사 시 기재한 105건은 재측정으로 **104건**으로 정정했다.
> 유저 수는 기준이 갈려 세 줄로 분리했다 — 최초의 "9명"은 합집합 기준으로 맞고,
> 2차 재측정의 "7명"은 미션보상배지 보유자만 센 값이다. 삭제 SQL은 4종을 모두 지우므로
> 실제 영향 유저는 **9명**이다.
> 삭제 SQL(`seed_reset_levelup_missions_20260825.sql`) 주석도 같은 값으로 맞췄다.

- 위 4종을 **전량 삭제**한다.
- ⚠️ **영구 데이터 삭제는 Claude가 직접 실행하지 않는다** (플랫폼 안전 규칙, 티켓 20260813_001 전례 동일).
  `jam-web/supabase/seed_reset_levelup_missions_20260825.sql`로 파일만 작성하고 실행은 사용자가 직접 한다.
- 삭제 SQL은 반드시 **대상 건수를 먼저 SELECT로 확인할 수 있는 주석**을 포함하고,
  배지명·미션명이 아니라 **id 목록으로 한정**해 오삭제를 막는다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

**1. 배지엔진 게이팅 무력화 결함 수정 (문제 3 — 최우선)**
- `evaluateBadgesDetailed` Step 1 배지 조회 직후 `condition_json.mission_reward === true`인 배지를
  **발급 후보에서 제외**. 미션보상배지는 `grantMissionRewards` 경로로만 지급된다.
- `evaluateConditionDetailed`에 방어 분기 2개 추가:
  (a) `mission_reward === true` → 항상 `pass:false`
  (b) 수치 검사 필드(`MEASURABLE_CONDITION_KEYS`)가 하나도 없으면 → `pass:false`("평가 가능한 조건 없음").
  알 수 없는 필드/필터 전용 필드(`activity_type`·`day_of_week`)만 남은 조건이 함수 마지막 줄의
  `pass:true`로 새는 경로를 구조적으로 차단.
- 회귀 테스트 11케이스 신규(`mission-reward-gate.test.ts`) — `{mission_reward: true}` 단독 조건이
  활동 이력 50건에서도 절대 pass되지 않음을 고정.

**2. 노출 판정 단일 함수화**
- `src/lib/missions/visibility.ts`(순수 함수, 신규) — `open`/`locked`/`hidden`/`completed` 판정.
  완료는 `user_mission_completions` 단일 기준, 게이팅은 `gated_badge_id`의 등급 대비 유저 보유 등급
  (미보유는 Common 보유로 취급 → 첫 레벨업 미션은 항상 노출).
- `src/lib/missions/visibility-server.ts`(신규) — 판정에 필요한 DB 컨텍스트 조회만 담당.
- 목록(`missions/page.tsx`)·상세(`missions/[id]/page.tsx`)·참가 API(`join/route.ts`)·
  오늘카드(`lib/today/cards.ts`의 `mission_spotlight`) 4곳이 모두 이 함수를 사용.

  확인 쿼리: `SELECT id, name, condition_json FROM badges WHERE type='activity' AND deleted_at IS NULL
  AND NOT (condition_json ?| array['distance_km','elevation_gain_m','duration_minutes','min_speed_kmh',
  'max_pace_sec_per_km','temperature_min_c','temperature_max_c','weekend_duration_hours','total_count',
  'streak_days','weekly_count','month','monthly_km','season_count','season_count_all','active_days_count',
  'time_range','poi_id','mission_reward']);`
- 미션 상황 화면(`/missions/[id]/status`)에는 잠금 처리를 적용하지 않았다(티켓 범위 밖).
  참가하지 않은 유저에게는 원래 빈 진행상황만 표시된다.
