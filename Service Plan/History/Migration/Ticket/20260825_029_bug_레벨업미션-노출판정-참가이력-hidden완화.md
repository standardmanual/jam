# [Service] 미션 노출 판정에 참가 이력 반영 — hidden 완화

## 배경 / 문제 정의

티켓 [20260825_028](20260825_028_Feature_레벨업미션-노출규칙-정비-및-게이팅결함-수정.md)이 도입한
`jam-web/src/lib/missions/visibility.ts`의 노출 판정은 **본 배지 보유 등급만** 본다.
참가 여부(`user_mission_participations`)는 판정에 들어가지 않는다. 그 결과:

- 게이팅 도입 이전에 상위 단계 미션에 참가해 둔 유저는, 코드 배포 시점부터 정리 SQL
  (`seed_reset_levelup_missions_20260825.sql`) 실행 전까지 "참가는 했는데 진행중·참가중·
  완료/지난 어디에도 없는" 상태가 된다.
- `locked`면 잠김 칩으로라도 보이지만, `hidden`이면 목록에서 완전히 빠져 유저가 자기
  참가 이력을 어디서도 볼 수 없다.
- 실제로 프로덕션에 참가 기록 34건이 남아 있고, 그중에는 더미 계정이 아닌 실유저
  (`jae_everydae`, `589132427`, `kangwonc`)의 참가도 포함된다.
- 잠금 UX 작업 중 로컬에서도 재현됐다 — dev-login 유저가 "참가했는데 잠긴" 상태여서
  잠김 칩과 참가중 칩이 충돌했다(칩 우선순위는 커밋 `f32265bc`에서 정리됨).

티켓 028의 잔여 이슈에 "참가 이력 있는 미션의 `hidden` 완화"로 이미 기재돼 있던 항목을
별도 티켓으로 분리해 처리한다.

## 상세 요구사항

### 서비스/코드베이스 관점

1. **참가 이력 반영** — `MissionVisibilityContext`(`visibility.ts`)에
   `participatedMissionIds`(또는 동등한 입력)를 추가한다. 참가 기록이 있는 미션은
   `hidden` 대신 `locked`로 완화한다(완전 숨김 금지). `open`/`completed`/`locked`
   판정 우선순위는 기존 로직을 따르고, 참가 이력은 오직 `hidden` → `locked` 완화에만 관여한다.
   - `visibility-server.ts`에서 `user_mission_participations` 조회를 추가해
     `participatedMissionIds`를 채운다.
   - 순수 함수(`visibility.ts`)의 유닛테스트에 케이스 추가:
     참가 이력 있음 + 게이트 미달(원래 hidden 대상) → `locked`로 완화되는지.
   - 실행 결과는 정리 SQL(`seed_reset_levelup_missions_20260825.sql`) 실행 여부와
     무관하게 참가 이력이 사라지지 않아야 한다.

2. **fail-open 조기 감지 로깅** — `visibility-server.ts`에서 `gated_badge_id`를 가진
   미션인데 조회 결과에 해당 배지가 없는 경우(소프트삭제·오설정으로 fail-open이 발동하는
   경우) `console.warn`으로 남긴다. 판정 함수(`visibility.ts`) 자체의 fail-open 동작은
   변경하지 않는다 — 순수 함수는 그대로 두고 조회 계층에서만 관측성을 추가한다.

### UI/UX 관점

- 잠긴(locked) 미션인데 참가 이력이 있는 경우, 상세 화면의 진행도 블록
  (`MissionDetailClient.tsx:244` 진행도 블록, `:358` '미션 상황 보기' 링크)은
  **현행 유지** — 별도 조건 분기 추가하지 않는다. 참가 CTA는 이미 잠김으로 차단돼 있어
  기능 결함이 아니며, 참가 이력을 보여주는 것이 이번 티켓의 취지와도 부합한다.
  (사용자 확정: "그대로 유지")

## 구현 계획

1. `visibility-server.ts`에 `user_mission_participations` 조회 추가 → `participatedMissionIds` 구성
2. `visibility.ts`의 `MissionVisibilityContext` 타입에 `participatedMissionIds` 필드 추가,
   판정 로직에서 `hidden` 판정 직전에 참가 이력이 있으면 `locked`로 완화하는 분기 추가
3. `visibility-server.ts`에 `gated_badge_id` 조회 실패 시 `console.warn` 추가
   (배지 id/미션 id를 포함해 원인 추적 가능하게)
4. 유닛테스트 추가 (`visibility-logic.test.ts` 등 기존 테스트 파일에 케이스 추가)
5. 로컬 실화면 확인 — 참가 이력이 있고 게이트 미달인 미션이 `hidden`이 아닌 `locked`로
   렌더되는지 확인 (dev-login 유저 또는 임시 목킹 후 원복)

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

1. **참가 이력 반영 (hidden → locked 완화)**
   - `visibility.ts`의 `MissionVisibilityContext`에 `participatedMissionIds: ReadonlySet<string>` 필드 추가.
   - `resolveMissionVisibility`에서 게이트 판정이 `hidden`(gateTier가 ownedTier+2보다 위)에
     도달했을 때, `ctx.participatedMissionIds`에 해당 미션 id가 있으면 `locked`로 완화해 반환
     (requiredBadge는 기존 계산값 그대로 사용). `open`/`completed`/`locked` 분기·우선순위는
     변경하지 않았다 — 오직 마지막 `hidden` 반환 직전에만 관여한다.
   - `visibility-server.ts`의 `loadMissionVisibilityContext`에 `user_mission_participations`
     조회를 추가해 `participatedMissionIds`를 구성. 호출부가 이미 참가 기록을 조회해 둔 경우
     재조회를 생략하도록 `options.participatedMissionIds` 오버라이드를 `completedMissionIds`와
     동일한 패턴으로 추가.
   - 호출부 반영: `missions/page.tsx`는 이미 조회해 둔 `participationSet`을 그대로 전달(중복
     쿼리 방지), `missions/[id]/page.tsx`는 이미 조회한 단건 참가 레코드 유무로 Set을 구성해
     전달. `join/route.ts`·`today/cards.ts`는 기존 호출부에 사전 조회된 참가 데이터가 없어
     `loadMissionVisibilityContext`가 새로 쿼리하도록 그대로 둠(두 곳 모두 open 여부만 보므로
     이번 완화가 판정 결과에 영향을 주지 않음 — hidden·locked 둘 다 참가 불가 상태로 취급됨).
2. **fail-open 조기 감지 로깅**
   - `visibility-server.ts`에 `warnMissingGatedBadges` 헬퍼 추가. `gated_badge_id` 조회 대상
     id 중 `badges` 조회 결과(소프트삭제 제외)에 없는 id가 있으면, 그 배지 id와 영향받은
     미션 id 목록을 `console.warn`으로 남긴다. 순수 함수(`visibility.ts`)의 fail-open(open
     반환) 동작 자체는 그대로 유지.
3. **UI 변경 없음** — `MissionDetailClient.tsx`의 진행도 블록(구 `:244`)·'미션 상황 보기'
   링크(구 `:358`)는 모두 `participating || isCompleted` 조건으로 이미 렌더되고 있어 요구사항대로
   손대지 않았다. 상세 페이지의 `locked` boolean은 `visibility === 'locked' || 'hidden'`으로
   기존과 동일하게 계산되므로(참가 이력으로 hidden→locked가 되어도 `locked` boolean 값은
   그대로 `true`) 이 파일은 아예 수정하지 않았다.
