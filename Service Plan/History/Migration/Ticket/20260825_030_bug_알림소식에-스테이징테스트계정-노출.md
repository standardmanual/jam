# [bug] 알림(소식)에 스테이징 테스트 계정이 노출됨 — 027 후속

## 배경 / 문제 정의

[20260825_027](20260825_027_bug_스테이징테스트계정-프로덕션노출.md)이 스테이징 전용 테스트
계정(`00000000-0000-0000-0000-000000000001`, `589132427_stage` 외 시드 계정 3개)을 프로덕션의
"공개 유저 목록"(랭킹·팔로잉/팔로워·검색·POI 드랍자 표시)에서 제외하는 필터를 만들었다.
`lib/env/test-accounts.ts`가 단일 진실이다.

**알림(소식) 기능이 027보다 나중에 만들어져 이 필터를 적용받지 못했다.** 실제로 미적용을
확인했다:

```
src/lib/notifications/batch/following.ts  — test-accounts.ts import 없음
src/lib/notifications/feed.ts             — 소식 목록·dot 판정 모두 미적용
```

알림은 "여러 유저가 섞인 공개 목록"이 아니라 **수신자 개인에게 온 소식**이라 027의 기준상으로는
검토 대상이 아니었을 것이다. 그런데 소식의 `actor_user_id`(행위자)에 테스트 계정이 들어가면,
**프로덕션의 실제 유저가 "jiwon.kim님이 회원님을 팔로우해요" 같은 소식을 받는다.**
공개 목록 노출과는 다른 경로지만 결과는 같다 — 내부 QA 도구가 실유저에게 노출된다.

### 재현 경로

`/api/dev-login`은 스테이징/로컬에서만 동작하지만, **staging과 프로덕션이 같은 Supabase DB를
공유**하므로 스테이징에서 테스트 계정으로 한 행동(팔로우·픽업 등)이 만든 `notifications` 행은
프로덕션에서도 그대로 조회된다. 실제로 이번 알림 기능 QA 과정에서 테스트 계정을 `actor_user_id`로
하는 소식이 프로덕션 DB에 10건 생성된 것을 확인했다(수동 시드 포함 — 아래 「잔여 이슈」 참고).

## 상세 요구사항

### 서비스/코드베이스 관점

**027과 동일한 아키텍처를 따른다** — 삭제·생성 차단이 아니라 **환경별 조건부 필터**.
`lib/env/test-accounts.ts`의 `excludedTestUserIds()`를 그대로 재사용한다(이중 구현 금지).

027이 "쓰기 시점이 아니라 읽기 시점에 필터"한 것과 같은 이유로, **이번에도 쓰기(T1 인라인
생성·T2 배치)가 아니라 읽기(조회) 시점에 필터한다.**

- 쓰기 경로(T1 14곳 + T2 `following.ts`)를 건드리면 `create_notification()` RPC·`once` 멱등성·
  `group_key` 병합처럼 방금 안정화한 로직을 다시 흔들게 된다
- 테스트 계정이 행위자인 행은 **여전히 DB에 생성**되지만(스테이징 QA 용도로는 오히려 필요할
  수 있다), 프로덕션 조회 시점에 걸러지면 실유저에게는 보이지 않는다

**정확한 수정 지점 2곳** (`src/lib/notifications/feed.ts`):

1. **`listNotificationViews()`/`hydrateNotifications()`** — 조회한 행 중
   `actor_user_id ∈ excludedTestUserIds()`인 것을 제외한다(프로덕션에서만). 필터는 커서 계산
   **이후**에 적용할 것 — `nextCursor`는 필터 전 마지막 행 기준으로 그대로 두어야 페이지네이션이
   깨지지 않는다(027이 "조회 후 JS `.filter()`" 방식을 택한 것과 같은 이유).
2. **`latestBumpingNotificationAt()`(dot 판정)** — 현재 `updated_at`만 select하고 `limit(1)`이라
   행위자를 알 수 없다. `actor_user_id`도 select하고 `limit`을 5~10 정도로 늘려, 제외 대상이
   아닌 첫 행의 `updated_at`을 찾아 반환하도록 고친다. 이걸 안 하면 **"종에 빨간 점이 떴는데
   들어가면 새 소식이 안 보이는"** 혼란스러운 상태가 된다(방문하면 `seen_at`이 전진해 다음
   로드부터는 사라지지만, 그 사이 유저가 "왜 새 게 없지" 하고 의아해한다).

**건드리지 않는 것**: `src/lib/notifications/batch/following.ts`의 생성 로직, T1 14개 호출부,
`create_notification()` RPC. 읽기 시점 필터만으로 충분하다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
`src/lib/notifications/feed.ts` 두 지점에 `excludedTestUserIds()`(027, `lib/env/test-accounts.ts`)를
그대로 재사용해 필터를 적용했다. 이중 구현 없음.

1. `listNotificationViews()` — `.limit(limit + 1)` 조회 후 `hasMore`/`nextCursor` 계산까지
   **먼저** 끝내고, 그다음에 `rows`(필터 전, 커서 계산에 쓰인 배열)를 `actor_user_id ∈
   excludedTestUserIds()` 기준으로 걸러 `visibleRows`를 만들어 `hydrateNotifications()`에
   넘긴다. `nextCursor`는 필터 전 마지막 행 기준을 그대로 쓰므로 페이지네이션이 깨지지 않는다.
   `actor_user_id`가 `null`인 시스템 소식은 필터 대상이 아니다(제외 조건은 `!row.actor_user_id
   || !excludedIds.includes(...)`).
2. `latestBumpingNotificationAt()` — 기존 `select('updated_at').limit(1).maybeSingle()`을
   `select('updated_at, actor_user_id').limit(10)`(상수 `LATEST_BUMPING_LOOKAHEAD`)으로 바꾸고,
   조회된 최대 10건 중 제외 대상이 아닌 첫 행을 `Array.prototype.find`로 찾아 그 `updated_at`을
   반환한다. 10건이 모두 제외 대상이면(이론상 가능) `null`을 반환한다 — dot이 안 켜지는 쪽으로
   fail-safe(빨간 점이 잘못 뜨는 것보다 안전).

두 지점 모두 `isStagingOrDevEnv()`가 참인 스테이징/로컬 환경에서는 `excludedTestUserIds()`가
빈 배열을 반환하므로 필터가 아무 영향을 주지 않는다(스테이징 QA에서 테스트 계정 소식이 계속
보여야 하므로 의도된 동작).

### 주요 의사결정 / 핵심 메모
- `latestBumpingNotificationAt()`의 lookahead 크기는 티켓이 제시한 "5~10" 범위 중 10을 택했다
  (여유를 최대로 둬 제외 대상이 여러 건 연속될 때도 유효 행을 찾을 확률을 높임 — 인덱스
  `(user_id, updated_at DESC)`를 그대로 타므로 1건 조회와 비용 차이가 거의 없다).
- 필터는 `listNotificationViews()` 내부에서만 적용했다. `hydrateNotifications()`는
  `listNotificationViews()`에서만 호출되는 내부 함수라(다른 호출부 없음, grep으로 확인)
  별도로 다시 필터할 지점이 없다 — 티켓이 "두 지점"이라 부른 것은 사실상 "목록 경로 1곳 +
  dot 판정 1곳"으로, 코드상 정확히 두 함수(`listNotificationViews`, `latestBumpingNotificationAt`)
  수정으로 충분했다.
- 쓰기 경로(T1 14곳, `batch/following.ts`, `create_notification()` RPC)는 지시대로 손대지 않았다.

### ⚠️ 게이트 리뷰가 발견한 더 큰 구멍 — `test-accounts.ts` 배열 자체가 불완전했다

`TEST_ACCOUNT_USER_IDS`에 계정이 **1개**(dev-login이 만드는 `0001`)뿐이었다. 그런데 프로덕션에는
`@jam.local` 이메일의 계정이 **4개** 존재한다 — `0002`(jiwon.kim)·`0003`(minjun.park)·
`0004`(sora.lee), 생성일 2026-08-15. 코드베이스 전체를 grep해도 이 3개를 만드는 코드가 없다 —
**Supabase에 직접 수동 INSERT된 QA 픽스처**다(알림 기능 검증 과정에서 팔로잉/팔로워 상대로
쓰기 위해 만들어진 것으로 추정).

결과적으로 **027·030을 배포해도 이 3개 계정은 랭킹·팔로잉/팔로워·검색·알림 소식 어디서도
막히지 않았다** — 027이 도입될 때 이 계정들의 존재 자체를 놓쳤던 것이다.

**대응**: `TEST_ACCOUNT_USER_IDS` 배열에 3개를 추가했다(사용자 결정 — 이메일 도메인 기반
동적 판별 대안도 검토했으나, 배열 방식이 DB 조회 없이 즉시 반환되는 현재 구조를 유지할 수
있어 더 안전하다고 판단). 027이 만든 필터 로직(6개 기능·9개 파일) + 030이 만든 알림 필터
2곳 전부가 이 3개 계정에도 즉시 적용된다 — 로직 재사용 지점이 하나뿐이라 배열 수정만으로 끝났다.

### 잔여 이슈
- **프로덕션 DB에 이미 생성된 테스트 계정 발신 소식 정리 필요** — 이번 알림 기능 QA 과정에서
  `589132427_stage` 계정에 수동 시드한 소식 9건, 그리고 그 안에 `actor_user_id`로 들어간
  `jiwon.kim`·`minjun.park`·`sora.lee` 관련 행이 있다. 코드 수정과 무관한 데이터 정리이므로
  배포 후 별도로 처리한다.
- **`TEST_ACCOUNT_USER_IDS`가 여전히 정적 배열이다** — 미래에 또 수동 시드 계정이 생기면
  똑같이 놓칠 수 있다. 이메일 `@jam.local` 도메인 기반 동적 판별로 바꾸는 안을 검토했으나
  캐싱·DB 조회 설계가 필요해 범위가 커져 이번엔 채택하지 않았다. 재발하면 별도 티켓 대상.
