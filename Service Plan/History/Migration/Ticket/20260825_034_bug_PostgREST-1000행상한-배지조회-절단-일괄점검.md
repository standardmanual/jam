# [bug] PostgREST 1000행 응답 상한으로 인한 배지 전량 조회 절단 — 일괄 점검·수정

## 배경 / 문제 정의

티켓 [20260825_028](20260825_028_Feature_레벨업미션-노출규칙-정비-및-게이팅결함-수정.md) 작업 중
`admin/missions/page.tsx`의 배지 조회가 페이지네이션 없이 PostgREST 기본 응답 상한(1000행)에서 잘려,
미삭제 배지 2172건 중 5개 레벨업 트리 가운데 '동네 산책러'만 조회되고 나머지 4개 트리('첫 숨결'은
name 오름차순 1905번째)는 검색 자체가 되지 않는 결함이 발견됐다. 해당 파일은 `range()` 루프 +
`.order('name').order('id')` tie-break로 수정 완료(커밋 `dce8f5fa`).

028 완료 기록의 "잔여 이슈"에 아래 항목들이 **"범위 밖으로 분류, 별도 티켓으로 분리 예정"**으로
명시돼 있다 — 이 티켓이 그 후속이다.

- `visibility-server` 페이지네이션
- 어드민 보상배지 DOM 렌더량

동일 유형인 "소프트 삭제 필터 누락"은 티켓 [20260825_022](20260825_022_bug_소프트삭제배지-필터누락-잔여정리-및-구조적해법.md)가
`.from('badges')` 74곳을 전수 감사해 표로 남겼다. 이번 문제(1000행 절단)는 필터 유무가 아니라
**행 수 상한**이 기준이므로 판정 축이 다르지만, 74곳 목록 자체는 재사용 가능하다.

## 상세 요구사항

### 서비스/코드베이스 관점

**1. `jam-web/src/lib/missions/visibility-server.ts` (우선순위 높음)**
- `user_activity_badges`를 `.select('badge_id').eq('user_id', userId)`로 전량 조회 — 페이지네이션 없음
- 보유 배지가 1000행을 넘는 유저는 최고 등급 배지가 잘려 `ownedTier`가 낮게 잡히고, **열려야 할
  레벨업 미션이 locked로 잠기는** 방향의 오판이 난다
- 현재 유저당 최대 보유는 175행(`00000000-…-0001`)이라 실동작 영향은 없으나 구조적 결함
- 권장 방향(진행 담당이 최종 판단): 쿼리 방향을 뒤집으면 절단 문제와 `in()` URL 길이 문제가
  동시에 해소된다. 먼저 `badges.in('name', gatedNames)`로 게이트 트리 배지 id(최대 5트리×4등급=20개)를
  뽑고, 그 id로 `user_activity_badges.eq(user_id).in('badge_id', ids)`를 조회하면 두 쿼리 모두 최대 20행

**2. `badges` 전량 조회 지점 전수 재판정**
- `grep -rn "from('badges')" jam-web/src`로 전 조회 지점을 열거한다 (022 티켓의 74곳 표를
  출발점으로 활용 가능하나, 이번 판정 기준은 다르므로 처음부터 다시 확인할 것)
- 각 지점에 대해 (a) 필터(`type` 등)로 1000행 미만이 구조적으로 보장되는지, (b) 절단이 실제로
  발생했을 때 오판(잘못된 노출/카운트/게이팅)으로 이어지는지 판정
- 참고로 확인된 사실: 미삭제 배지 2172건 / 전체 5585건이므로 `type` 필터가 없는 조회는 전부
  절단 위험이 있다. 배지엔진 Step 1(`evaluateBadgesDetailed`)은 `type='activity'` 필터로 175건만
  조회해 안전함이 이미 실측 확인됐다(028 작업 중)
- **오판 가능한 지점만 수정한다** — 전부 고칠 필요는 없다. 수정하지 않는 지점도 판정 근거를
  완료 기록의 표에 남길 것 (022의 표 형식 참고)

**3. `jam-web/src/app/admin/missions/MissionList.tsx` — '보상 배지' 선택 목록**
- 검색어가 비어 있으면 `badges` 전량을 DOM에 렌더한다. 1번 항목(`admin/missions/page.tsx`)의
  절단이 028에서 해소되면서 실제 렌더량이 1000 → 2172개로 늘었다
- 같은 파일의 게이트 배지 목록은 검색어 입력 시에만 렌더하는 패턴(`gatedBadgeQuery.trim() &&`)이
  이미 있으므로 동일 패턴 적용 또는 `slice(0, 50)` 등으로 렌더량을 제한한다

**4. 페이지 크기 하드코딩 개선 (선택, 개선 리뷰 대상)**
- `range()` 루프에서 페이지 크기 1000을 하드코딩하면 DB 설정(`db-max-rows`) 변경 시 조용히
  조기 종료할 수 있다
- 첫 요청에 `{ count: 'exact' }`를 붙여 `rows.length < count`인 동안 반복하거나, 실제 반환된
  행 길이를 페이지 크기로 채택하는 방식을 검토한다 (신규 도입한 루프에 한해 — 기존
  `admin/missions/page.tsx`의 루프까지 되돌릴 필요는 없음, 필요시 함께 개선 가능)

## 구현 계획

1. `visibility-server.ts`의 `user_activity_badges` 조회를 게이트 배지 id 역참조 방식으로 재작성
   (또는 range 루프 페이지네이션 — 진행 담당이 근거와 함께 택일)
2. `grep -rn "from('badges')" jam-web/src` 전수 재판정, 오판 가능 지점만 수정, 판정 표를
   완료 기록에 남긴다
3. `MissionList.tsx`의 보상 배지 선택 목록 DOM 렌더량 제한 (게이트 배지 목록과 동일 패턴 또는 slice)
4. 페이지 크기 하드코딩 방식 개선 여부는 개선 리뷰에서 판단

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

**1. `visibility-server.ts` (우선순위 높음) — 쿼리 방향 역전으로 재작성**

기존: `user_activity_badges.select('badge_id').eq('user_id', userId)`로 유저 보유 배지
전량을 페이지네이션 없이 조회 → `badges.select('name,rarity').in('id', ownedBadgeIds).in('name', gatedNames)`.

변경: 먼저 `badges.select('id,name,rarity').in('name', gatedNames)`로 게이트 배지와 이름이
같은 전체 등급 변형(최대 5트리×4등급≈20개)의 id를 구하고, 그 id로
`user_activity_badges.eq('user_id', userId).in('badge_id', variantIds)`를 조회하도록 순서를
뒤집었다. 두 쿼리 모두 이제 유저 보유량과 무관하게 최대 수십 행으로 고정된다 — 절단
위험과 `in()` URL 길이 위험이 동시에 해소된다. 소프트삭제 필터를 걸지 않는 기존 정책
(20260823_004/20260825_020·021)은 그대로 유지.

**2. `badges` 전량 조회 지점 전수 재판정 (아래 판정 표) — 오판 가능 지점 6곳 수정**

- `app/api/admin/badges/route.ts` GET — `select('*').limit(5000)`이 PostgREST 서버
  `db-max-rows`(1000) 상한을 못 넘겨 최신 1000/5585건만 반환하던 것을 range 페이지네이션으로
  교체. `BadgeForm.tsx`(형제 배지 drop_weight 합산 미리보기)·`ItemBookForm.tsx`(일괄 배경적용
  대상 수 미리보기)가 이 응답을 그대로 클라이언트 필터링해 쓰므로, 절단되면 두 미리보기
  숫자가 실제보다 적게 표시되는 오판이었다.
- `app/admin/today/page.tsx` — type 필터 없는 미삭제 배지 전량(2172건) 조회가 name 오름차순
  1000건에서 잘리던 것을 range 페이지네이션으로 교체. "오늘" 카드 배지 스포트라이트
  선택/기존 선택 칩 표시가 뒤쪽 배지에 대해 누락되는 오판이었다(admin/missions/page.tsx와
  동일 원인, 028 dce8f5fa 선례).
- `app/admin/itembooks/page.tsx` — badges를 필터 전혀 없이(5585건) 조회해 `badgeMap`을
  만들던 것을, 실제 용도(각 북의 `required_activity_badge_id`/`reward_badge_id` 이름
  조회, 북 수×2 ≈ 20개 안팎)에 맞춰 `.in('id', labelIds)` bounded 조회로 교체
  (`admin/itembooks/[id]/page.tsx`의 기존 labelIds 패턴과 동일). 절단되면 목록에서
  필요/보상 배지 이름이 빈 값으로 표시되는 오판이었다.
- `app/admin/recipes/page.tsx` — type 필터 없는 미삭제 배지 전량(2172건, `.limit(10000)`도
  서버 상한을 못 넘김) 조회를 재검토한 결과, `RecipeList.tsx`는 이 목록을 배지 **선택**에는
  전혀 쓰지 않고(신규 레시피 배지 선택은 이미 검색 기반 `BadgeSearchSelect` 사용) 기존
  레시피가 참조하는 배지 이름 표시에만 쓰는데, 그 이름 조회는 바로 아래 `usedBadgeIds`
  bounded 조회로 이미 완전히 커버되고 있었다(전량 조회 결과는 매번 덮어써져 사실상 아무
  역할도 하지 않음). 페이지네이션을 추가하는 대신 이 불필요한 전량 조회 자체를 제거했다 —
  절단 위험 제거 + 성능 개선을 동시에 달성.
- `app/admin/missions/MissionList.tsx` — 보상 배지 선택 목록이 검색어 없을 때 `badges`
  전체(028 절단 해소 후 최대 2172개)를 DOM에 그대로 렌더하던 것을 50개로 제한하고
  "N개 중 50개 표시 — 검색으로 좁혀보세요" 안내를 추가. 게이트 배지 목록의 "검색어 있을
  때만 렌더" 패턴 대신 slice(0,50)을 택한 이유: 보상 배지는 다중 선택 UI라 검색 없이도
  일부를 바로 훑어볼 수 있는 기존 UX를 유지하는 쪽이 낫다고 판단(티켓 §구현계획 4-3에서
  선택지로 제시된 두 방식 중 택일).
- `lib/itembook/checker.ts` / `lib/itembook/completable.ts` — 활성 아이템북 전체(bookIds) ×
  `type IN ('item','poi')` 조회. POI 배지만도 1,800건이 넘고(`(main)/badges/page.tsx` 기존
  주석) Phase 16 규칙상 POI 배지도 `item_book_id`로 컬렉션에 소속될 수 있어, type 필터만으로는
  1000행 미만이 구조적으로 보장되지 않는다고 판단해(정확한 현재 실측치는 DB 접근 권한 밖이라
  확인 못 함 — "주요 의사결정" 참고) 두 곳 모두 range 페이지네이션으로 방어적으로 수정했다.
  절단되면 컬렉션 완성 판정의 분모(총 배지 수)가 실제보다 작게 잡혀 **미완성 컬렉션이
  완성으로 오판되어 보상 배지가 오발급**되거나(`checker.ts`), 완성 가능 소식이 잘못된
  타이밍에 발송되는(`completable.ts`) 방향의 오판으로 이어진다 — 게임 경제 정합성에 직결되는
  로직이라 현재 실측치와 무관하게 방어적 수정을 택했다.

**3. 페이지 크기 하드코딩 개선 — 이번 티켓 범위에서는 보류**

신규로 도입한 모든 range 루프는 티켓 §4에서 언급한 "실제 반환 길이를 페이지 크기로 채택"
방식이 아니라 `admin/missions/page.tsx`(028)와 동일한 고정 `PAGE_SIZE=1000` 방식을 그대로
따랐다 — 기존 established 패턴과의 일관성을 우선했다. `{ count: 'exact' }` 동적 페이지 크기
전환은 progressive review 대상으로 남긴다(아래 "잔여 이슈" 참고).
