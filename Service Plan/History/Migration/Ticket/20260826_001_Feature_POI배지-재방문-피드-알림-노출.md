# [Feature] POI 배지 재방문도 피드·알림에 노출 ("N번째 방문했어요")

## 배경 / 문제 정의

사용자 제보: 계정 `589132427`(id `3649ed39-2be2-402e-82ae-41e0cd328105`)이 2026-08-25 20:29(KST)
Strava 동기화로 서초역·응봉역·한남역 POI 배지를 재획득했는데(이전에도 8/3·8/7에 이미 획득 이력이
있는 배지), 프로필의 최근 활동 피드에는 이 재획득에 대한 항목이 전혀 없었다.

**원인 확인** (`jam-web/src/lib/strava/sync.ts`):
- POI 배지는 `user_poi_badge_earns` 테이블에 방문마다 새 행이 쌓이는 반복 획득 설계다
  (UNIQUE는 `user_id, badge_id, poi_id, triggered_by_strava_id` 조합 — 같은 활동 재처리만 막음).
  실측: 위 계정의 서초역 배지는 8/7, 8/25 두 번 정상적으로 재획득됨.
- **피드**: 361~408행에서 `isFirstEarn`(이전 획득 이력 존재 여부)이 `true`일 때만
  `recordFeedEvent('badge_earned', ...)`를 호출한다 — 재방문은 피드에 아예 기록되지 않는다
  (주석: "프로필 배지 갤러리/피드에는 '고유 배지' 개념으로 최초 획득 시점 1건만 노출").
  실측으로 재확인: 해당 시각 `user_activity_feed`에 같은 동기화의 `item_dropped` 이벤트는
  남아있는데 POI 배지 재획득 이벤트는 없음.
- **알림**: 444~462행 `poi_badge_earned` 알림은 `isFirstEarn` 여부와 **무관하게** 항상
  생성된다(피드와 다르게 재방문도 알림은 이미 뜬다). 다만 문구가 항상 고정이다 —
  `src/lib/i18n/ko.ts:644` `msgPoiBadgeEarned: '{poiName}에서 체크인 배지를 획득했어요'`는
  최초/재방문 구분 없이 "획득했어요"로 나간다.

사용자 결정: **재방문도 피드에 노출한다.** 문구는 최초 획득 시에만 "획득"을 쓰고, 두 번째
방문부터는 "N번째 방문했어요"로 표현한다. 알림 문구도 동일 규칙을 적용한다.

## 상세 요구사항

### 서비스/코드베이스 관점

1. **피드**: `sync.ts`의 `isFirstEarn` 분기(401~408행)를 수정해 재방문도 피드 이벤트를
   기록한다. 최초/재방문을 구분할 수 있는 정보(예: `is_first_earn` 플래그, 방문 횟수)를
   이벤트 metadata에 남긴다 — 프론트(`FeedSection.tsx`)가 이 값으로 문구를 분기해야 한다.
2. **방문 횟수 계산**: `user_poi_badge_earns`에서 해당 `user_id`+`badge_id`(또는 `poi_id`,
   어느 단위로 셀지 판단 필요 — 아래 참고) 조합의 총 획득 건수를 센다. 이미 361~367행에서
   `priorEarn` 조회를 하고 있으니 그 지점에서 카운트까지 함께 얻도록 확장하는 것이 자연스럽다.
   - **판단 필요**: "N번째 방문"의 N이 "이 POI 배지(badge_id) 자체"를 기준인지, "이 POI 지점
     (poi_id)"을 기준인지. 대부분 1:1이겠지만 한 배지에 여러 poi_id가 연결된 경우가 있는지
     확인하고 근거를 완료 기록에 남길 것.
3. **문구 규칙**:
   - 최초 획득: 기존 문구·톤 유지 ("배지 획득", "체크인 배지를 획득했어요" 등)
   - 재방문(2회차부터): "{POI명}을(를) {N}번째 방문했어요" 형태 (사용자 지정 문구, 조사
     "을/를" 처리 필요 — 기존 코드베이스에 한국어 조사 처리 유틸이 있는지 확인 후 없으면 추가)
   - `UX_WRITING_GUIDELINE.md` 고정 용어표에 "방문 인증"은 이미 있으나 "N번째 방문" 패턴은
     신규 표현이므로, 가이드라인 §1-3 규칙대로 용어표에 추가한 뒤 사용할 것
4. **피드 렌더링**: `FeedSection.tsx`(현재 `eventBadgeEarned: '배지 획득'` 고정 라벨,
   `src/lib/i18n/ko.ts:97`)가 재방문 이벤트일 때 다른 제목/문구를 렌더하도록 분기 추가
5. **알림**: `message.ts`의 `poi_badge_earned` 케이스(235~243행)와 `ko.ts`의
   `msgPoiBadgeEarned`가 최초/재방문을 구분해 문구를 다르게 렌더하도록 수정.
   - **판단 필요**: 알림은 활동 1건 단위로 여러 POI를 묶어서 보내는 구조다(`poiEarnsByActivity`,
     444행). 한 활동에서 최초 획득 POI와 재방문 POI가 섞이면 문구를 어떻게 합성할지
     결정이 필요하다(예: 최초 획득이 하나라도 있으면 그쪽을 대표 문구로 쓰고 나머지는
     `slotPlaceMore` 패턴처럼 뭉치는지, 아니면 완전히 분리해서 알림을 2건으로 나누는지).
     진행 담당이 UX 관점에서 판단하고 근거를 완료 기록에 남길 것.
6. 관련 파일: `jam-web/src/lib/strava/sync.ts`(346~462행), `jam-web/src/lib/notifications/message.ts`
   (235~243행), `jam-web/src/lib/i18n/ko.ts`(97행, 644행 근처), `jam-web/src/app/(main)/FeedSection.tsx`,
   `jam-web/src/app/(main)/notifications/NotificationsClient.tsx`

### UI/UX 관점

- 문구 톤은 기존 배지 획득 계열과 통일감 있게 — "배지=신남" 톤 유지, 다만 재방문은 최초 획득보다
  담담한 톤이어도 된다(반복 방문 자체를 신남으로 과장할 필요는 없음, 최종 톤은 UX Writing

  (오케스트레이터 판정, MODULAR 탐색 불필요)

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

1. **`sync.ts`**: `priorEarn`(존재 여부만 확인하던 `.limit(1).maybeSingle()`)을
   `{ count: 'exact', head: true }`로 바꿔 이전 획득 건수를 직접 세고, `visitCount = 이전 건수 + 1`,
   `isFirstEarn = visitCount === 1`을 계산한다. `if (isFirstEarn)` 게이트를 제거해 피드 이벤트를
   최초/재방문 무관하게 항상 기록하며, `poi_name`·`visit_count`를 metadata에 함께 싣는다.
   알림용 `poiEarnsByActivity` 맵에도 `isFirstEarns`·`visitCounts` 배열을 badgeIds/poiNames와
   같은 인덱스로 나란히 쌓는다.
2. **알림 대표값 선정**: 한 활동에 최초 획득 POI와 재방문 POI가 섞이면 `isFirstEarns.findIndex(v=>v)`로
   찾은 최초 획득 항목을 대표(헤드라인)로 쓴다. 없으면(전부 재방문) 0번 인덱스를 대표로 쓴다.
   payload에 `is_first_earn`·`visit_count`를 대표값으로 추가.
3. **`message.ts`**: `poi_badge_earned` 케이스에 `boolField()` 헬퍼(신규)로 `is_first_earn`을 읽어
   (payload에 없으면 `true`로 기본값 — 과거 소식 하위호환), `false`이고 `visit_count > 1`이면
   `msgPoiBadgeRevisited`("{poiName}{을/를} {visitCount}번째 방문했어요")를, 아니면 기존
   `msgPoiBadgeEarned`를 쓴다. 묶음 표기("외 N곳")는 `poi_name`(대표값)을 기준으로 계속 동작.
4. **`ko.ts`**: `feed.eventPoiRevisited`("{poiName}{josa} {visitCount}번째 방문했어요")와
   `notifications.msgPoiBadgeRevisited` 신규 키 추가.
5. **`FeedSection.tsx`**: `eventLabel()`에 badge_earned + poi_name + visit_count>1 분기를 추가해
   재방문이면 "N번째 방문했어요" 라벨을, 아니면 기존 "배지 획득" 라벨을 쓴다. 조사(을/를)는
   `message.ts`의 `hasBatchim()`을 그대로 재사용(신규 유틸 추가 없이 기존 것 재사용).
   `DetailSheet`/`FeedCard`가 공통으로 `eventLabel()`을 쓰므로 두 곳 다 자동 반영.
6. **타입**: `activity-feed/index.ts`의 `FeedEventMeta.badge_earned`에 `poi_name?`·`visit_count?`
   추가, `notifications/types.ts`의 `NotificationPayloadMap.poi_badge_earned`에 `is_first_earn?`·
   `visit_count?` 추가.
7. **문서**: `UX_WRITING_GUIDELINE.md` 용어표에 "N번째 방문했어요" 신규 행 추가(체크인 행 아래).
   `Specs/PRD/Notification/PRD.md` §3 표(#4 행)와 각주에 재방문 문구·대표값 선정 규칙·N 산정
   기준을 반영.

**판단 필요 ① — N을 badge_id 기준으로 셀지 poi_id 기준으로 셀지**: **badge_id 기준으로 결정**.
근거: (a) 기존 `priorEarn` 조회가 이미 `badge_id`만으로 필터링하고 있었다(`poi_id` 조건 없음) —
`isFirstEarn` 판정의 기존 관행이 badge_id 단위였다. (b) 배지 상세 화면의 재방문 이력
(`PoiEarnHistory`, `src/app/(main)/badges/[id]/page.tsx:316`)도 `.eq('badge_id', id)`로 조회해
badge_id 단위로 이력을 모은다 — 유저가 배지 상세에서 보는 "N번" 표기와 피드/알림의 N이 어긋나면
혼란스럽다. (c) `poi` 테이블의 `linked_badge_id`에는 UNIQUE 제약이 없어 이론상 여러 POI가 같은
배지를 공유할 수 있지만, 코드베이스 전체(배지 상세·기존 isFirstEarn 판정)가 이미 badge_id 단위로
설계돼 있어 그 관행을 깨지 않는 쪽을 택했다.

**판단 필요 ② — 최초/재방문이 섞인 묶음 알림 합성 방식**: **최초 획득 쪽을 대표(헤드라인)로 쓰고,
나머지는 기존 `slotPlaceMore`("{name} 외 {count}곳") 패턴 그대로 뭉친다.** 알림을 2건으로 쪼개는
방식은 채택하지 않았다. 근거: (a) "새로 획득"이 "몇 번째 방문"보다 알림 가치가 크다 —
UX Writing 가이드의 "배지=신남" 톤에서 최초 획득이 더 축하할 일이다. (b) 2건 분리는 `groupKey`가
활동 단위(`syncGroupKey('poi_badge_earned', activityId)`)로 이미 고정돼 있어 구조 변경이
필요한데, 이 티켓 범위를 넘어서는 리팩터링이라 판단했다. (c) 기존에도 여러 POI를 "외 N곳"으로
뭉치는 방식이 이미 있어 그 패턴을 그대로 재사용하는 게 최소 변경이다.

### 반영 내용

1. **트렁케이션 → 2줄 허용(`line-clamp-2`)으로 통일** (사용자 명시적 결정)
   - `FeedSection.tsx`의 `eventLabel()` 렌더 슬롯 2곳을 모두 `truncate`(1줄, 우측 컷) →
     `line-clamp-2`(2줄까지 허용, 이후 말줄임)로 변경.
     - `FeedCard`(피드 목록 카드): 기존에 `truncate`였던 라벨 `<p>`를 `line-clamp-2`로 교체.
     - `DetailSheet`(상세 시트): 기존에 **오버플로우 정책 자체가 없던**(truncate도 line-clamp도
       미적용) 라벨 `<p>`에 `line-clamp-2`를 신규 적용 — 두 렌더 지점의 정책을 명시적으로
       "2줄 허용"으로 통일했다. 레이아웃상 2줄 허용이 문제 되는 지점은 없었다(아래 스크린샷
       검증 참고 — 긴 POI명 케이스에서 2줄로 자연스럽게 줄바꿈되고 다음 요소(배지명 `<h2>`/`<p>`)와의
       간격도 깨지지 않음).
   - `title`(배지명)·`sub`(보조 문구) 등 다른 텍스트 슬롯은 이번 지시 범위가 아니므로 `truncate`
     그대로 유지(범위 확대 안 함).

2. **재방문 이벤트 시각 신호 추가** (인터랙션 리뷰 발견 3, 제안대로 진행)
   - 신규 컴포넌트 없이 기존 요소의 스타일 분기만으로 처리. `RevisitCountBadge` 헬퍼 함수
     (JSX만 반환하는 내부 렌더 함수, `design-system` 컴포넌트가 아님)를 추가해 재방문 이벤트의
     배지 썸네일 모서리에 "×N" 카운터 배지를 오버레이했다.
   - 스타일은 `ProfileClient.tsx`의 아바타 모서리 편집 버튼과 동일한 하우스 패턴
     (`absolute -bottom-1 -right-1`, `bg-surface-elevated`, `border-[color:var(--color-border)]`,
     `rounded-[var(--radius-pill)]`)을 재사용 — 신규 톤/컬러 도입 없음.
   - `FeedCard`(40×40 썸네일)·`DetailSheet`(112×112 썸네일) 양쪽 모두에 동일하게 적용.
   - 최초 획득 카드에는 배지가 붙지 않아 재방문과 시각적으로 명확히 구분된다(스크린샷 검증 참고).

3. **eventLabel 슬롯 타이포그래피 — 숫자만 인라인 강조** (인터랙션 리뷰 발견 4, 제안대로 진행)
   - 전체 문장 스타일은 그대로 두고(`text-body-sm`, `text-text/60`), "N번째"의 숫자 부분만
     `<strong className="font-bold text-text">`로 감싸 굵기·색(60% → 100% 불투명도)으로
     살짝 강조했다.
   - 구현 방식: `eventLabel()`이 기존에는 `t()`로 완성된 문자열을 반환했는데, 숫자만 부분
     강조하려면 문자열을 쪼개야 해서 반환 타입을 `string` → `ReactNode`로 바꿨다. `ko.ts`의
     `feed.eventPoiRevisited` 템플릿("{poiName}{josa} {visitCount}번째 방문했어요")을
     `{visitCount}` 마커로 split해 prefix/suffix로 나누고, 그 사이에 `<strong>{visitCount}</strong>`를
     끼워 넣는 방식이라 **템플릿 자체는 `ko.ts` 한 곳에서 계속 관리**되고 신규 i18n 인프라를
     추가하지 않았다.
   - `eventLabel` 반환 타입이 `ReactNode`로 바뀌었지만 호출부(`<p>{eventLabel(item)}</p>`)는
     문자열이든 JSX든 그대로 렌더 가능해 다른 변경 없이 호환됨.
