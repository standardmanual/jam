## 상세 요구사항

### 공통

- 각 화면의 테이블을 3단계a의 공용 Data Table 컴포넌트로 교체. 컬럼 구성(어떤 필드를
  보여줄지)은 기존 테이블의 컬럼을 그대로 유지 — 임의로 컬럼을 추가/제거하지 않는다.
- 필터 UI는 각 화면이 기존에 가진 필터를 공식 Toolbar 패턴으로 재구현(3단계a와 동일 방식).
  필터가 없던 화면(유저 상세, 포인트 등)에 새 필터를 억지로 만들 필요는 없다.
- 서버 페이지네이션이 없는 화면(미션·투데이·레시피·유저·세계관·포인트·어뷰징)은 **현재
  규모를 먼저 확인**하고, 수백 건 이상이면 POI/아이템북과 동일한 서버 페이지네이션을
  함께 도입한다. 수십 건 이하로 확인되면 페이지네이션 없이 Data Table만 적용해도 된다
  (판단 근거를 완료 기록에 남길 것).
- 모바일 카드/리스트 뷰가 있는 화면(배지·POI·아이템북처럼 이미 `use-is-desktop.ts` 조건부
  렌더 구조가 있는 화면)은 그 구조를 유지 — Data Table은 데스크탑 전용. 모바일 카드 뷰가
  아직 없던 화면(미션·투데이·레시피·유저·세계관·포인트·어뷰징)은 **이 티켓 범위에서 새로
  만들 필요 없음** — 데스크탑 Data Table만 적용하고 모바일은 기존 방식(원시 테이블이든
  뭐든) 그대로 두거나, 최소한의 반응형 처리만 한다. 모바일 카드뷰 신설은 범위 밖.

### 화면별 일괄 액션(bulk action) 정책 — 신중하게 판단할 것

**일괄 삭제 API는 어디에도 없다**(3단계a 사전 확인과 동일). 화면마다 아래 원칙을 따른다:

- **POI·아이템북·미션·투데이·레시피**: 배지와 동일하게 소프트 삭제/비활성화 성격이라
  "선택 항목 비활성화" 일괄 액션 추가 가능(기존 단건 API 순차 호출, 배지 파일럿과 동일 방식).
- **세계관**: 팩션 활성/비활성 개념이 있으면 동일하게 일괄 비활성화 추가 가능. 없으면
  일괄 액션 없이 행 선택 UI만 제공하거나 아예 생략.
- **유저**: **일괄 삭제/정지 액션을 넣지 않는다.** 유저 계정에 대한 대량 조치는 정책상
  민감하고 이 티켓 범위 밖이다. 행 선택 UI 자체도 필요 없으면 생략 — Data Table 전환은
  표시 방식(정렬·컬럼 관리)만 목적으로 한다.
- **유저 상세(배지 획득 이력)**: 읽기 전용 목록이라 행 선택/일괄 액션 개념 자체가 없다 —
  Data Table 컴포넌트를 표시 용도로만 쓴다(정렬 정도만 있어도 충분).
- **포인트(거래 로그)**: 지급/회수 기록은 회계성 로그라 삭제·수정 대상이 아니다 — 여기도
  일괄 액션 없이 표시/정렬 용도로만 Data Table을 쓴다.
- **어뷰징(밴 기록)**: 밴 해제(unban) 같은 일괄 액션이 실제로 필요한지는 기존 화면에 단건
  해제 기능이 있는지 먼저 확인하고 판단할 것 — 있으면 그 API를 순차 호출하는 일괄 해제를
  추가해도 되고, 없으면 표시 용도로만 사용.
