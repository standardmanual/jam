# [bug] 소프트 삭제된 배지를 가리키는 월드 드랍이 남아 픽업 시 알림 404

## 배경 / 문제 정의

사용자 신고: 알림 목록의 "cheerslovelymate님이 '정체불명의 보라색 액체'를 픽업했어요"를
누르면 404 페이지가 뜬다.

### 원인 조사 (프로덕션 DB 실측, 2026-08-26)

`notifications` 테이블에서 해당 알림을 직접 조회한 결과:

```
type: drop_picked_up
actor_user_id: 25782789-... (cheerslovelymate)
payload.badge_ids: ["985e1772-a08b-44ea-b78e-41a277d6d7f1"]
payload.badge_name: "정체불명의 보라색 액체"
```

이 `badge_id`로 `badges` 테이블을 조회하면 **`deleted_at`이 채워져 있다**(소프트 삭제됨).
[href.ts](jam-web/src/lib/notifications/href.ts)의 `drop_picked_up` 케이스는 PRD 스펙대로
`/badges/${badgeId}`로 이동시키는데, [badges/[id]/page.tsx](jam-web/src/app/(main)/badges/[id]/page.tsx)는
티켓 [20260824_007](20260824_007_bug_소프트삭제-배지가-인벤토리에-잔존.md)에서 사용자가 이미
확정한 정책대로 소프트 삭제된 배지를 존재하지 않는 배지와 동일하게 `notFound()` 처리한다 —
**이 부분은 의도대로 동작 중이며 변경 대상이 아니다.**

**진짜 문제는 타임라인에 있다** (`poi_drops` 테이블 실측):

| 시각 (UTC) | 사건 |
|---|---|
| 2026-08-23 12:14 | 회원님이 '정체불명의 보라색 액체'를 지점에 드랍 (`poi_drops` 행 생성, `is_available=true`) |
| 2026-08-24 03:05 | 이 아이템의 배지 원본이 소프트 삭제됨 (`badges.deleted_at`) — 020260824_007이 언급한 "2026-08-23 orphan 아이템배지 1,245건 소프트 삭제(커밋 `1e77419`)" 배치의 일부로 추정 |
| 2026-08-26 12:28 | **삭제된 지 2일 넘게 지난 시점에도 여전히 `is_available=true`로 맵에 남아있던** 이 드랍을 cheerslovelymate님이 픽업 → `drop_picked_up` 알림 생성, 이미 삭제된 배지 ID가 그대로 payload에 박힘 |

즉 **배지를 소프트 삭제해도 그 배지를 가리키는, 아직 안 주워진 월드 드랍은 무효화되지 않는다.**
그 결과 이미 카탈로그에서 사라진 콘텐츠가 계속 주울 수 있는 상태로 남고, 픽업되면 드랍한
사람에게는 클릭할 수 없는 알림이, 주운 사람의 인벤토리에는 상세 조회 시 404가 나는 아이템이
생긴다.

### 현재도 진행 중인 문제 (일회성 아님)

프로덕션 DB에서 `is_available=true AND picked_up_at IS NULL`이면서 배지가 이미 소프트
삭제된 행을 조회한 결과, **이미 발생한 1건 외에 4건이 지금도 맵 위에 남아있다**:

| poi_drops.id | badge_id | 배지명 | 배지 삭제 시각 |
|---|---|---|---|
| `d663f223-8e16-4c38-a2fe-56a8b8220219` | `f0cb33f9-6b5f-4111-860d-23854a3be46c` | 한도 초과 알림 | 2026-08-23 07:10:38 |
| `b545f5e5-2716-4232-99f7-0259e5f75850` | `9ef2f5fb-4b41-48c1-a322-0a9b64edb0f9` | 핫팩 내용물 가루 | 2026-08-23 07:09:24 |
| `d742eebc-c8fb-4523-abaf-a3cd0fb29abe` | `c613ce8d-1ef5-4ad9-80e3-65b4e4f5f6f5` | 군고구마 껍질 | 2026-08-23 06:06:54 |
| `a04d66a0-5c4f-4c21-bee4-dc01b864a8ba` | `585c0e90-070e-49ff-9b66-c5c507a212bc` | 후회 없는 미소 | 2026-08-23 07:10:38 |

누군가 이 4개 중 하나라도 주우면 오늘 신고된 것과 똑같은 문제가 재현된다.

## 상세 요구사항

### 서비스/코드베이스 관점

**1. 근본 원인 차단 — 배지 소프트 삭제 시 미픽업 드랍 함께 무효화**

[api/admin/badges/[id]/route.ts](jam-web/src/app/api/admin/badges/[id]/route.ts)의 `DELETE`
핸들러(66~80행)와 `PATCH` 핸들러 중 `active: false` 분기(88~111행) — 둘 다 `deleted_at`을
채우는 소프트 삭제 지점이다. 두 곳 모두에서, `deleted_at`을 새로 채우는 경우(활성화 방향이
아닌 경우)에 한해 다음을 이어서 실행한다:

```
poi_drops
  SET is_available = false
  WHERE badge_id = {id}
    AND picked_up_at IS NULL
    AND is_available = true
```

- 이미 픽업된(`picked_up_at IS NOT NULL`) 행은 건드리지 않는다 — 이력 보존.
- `PATCH`로 배지를 다시 활성화(`active: true`)하는 경우는 드랍을 되살리지 않는다 — 무효화된
  드랍을 자동 부활시키면 "언제 다시 나타났는지 알 수 없는 아이템"이라는 별도 혼란을 만든다.
  되살릴 필요가 있으면 관리자가 명시적으로 새로 드랍해야 한다(범위 밖).

**2. 안전망 — 다른 경로(수동 DB 조작 등)로 소프트 삭제된 경우도 매일 소각**

[api/cron/poi-cleanup/route.ts](jam-web/src/app/api/cron/poi-cleanup/route.ts)는 현재
`expires_at`이 지난 드랍만 매일 00:00 UTC에 `is_available=false`로 소각한다. 이번 사고의
실제 원인이었던 "2026-08-23 orphan 배지 1,245건 소프트 삭제"는 위 API가 아니라 **DB에
직접 실행된 일회성 작업**이었다(커밋 `1e77419`) — 즉 1번 항목만으로는 앞으로도 같은 경로의
사고를 못 막는다. 이 크론에 조건을 하나 추가한다:

```
poi_drops
  JOIN badges ON badges.id = poi_drops.badge_id
  SET poi_drops.is_available = false
  WHERE poi_drops.is_available = true
    AND poi_drops.picked_up_at IS NULL
    AND badges.deleted_at IS NOT NULL
```

(`expires_at` 조건과 무관하게 별도 조건으로 추가 — 기존 만료 소각 로직은 그대로 둔다.)
응답 JSON에 이 경로로 소각된 건수도 함께 보고한다(예: `{ expired, orphanedByDeletedBadge }`).

**3. 현재 살아있는 4건 정리 (DB, 오케스트레이터가 승인 후 직접 실행)**

위 표의 `poi_drops.id` 4건을 `is_available = false`로 직접 업데이트한다. 스키마 변경이
아니라 1회성 데이터 정리이므로 `jam-web/supabase/seed_20260826_orphan_drop_cleanup.sql`로
남긴다(내용: 위 4개 ID를 대상으로 한 UPDATE문 + 실행 전/후 건수 확인 주석).

### UI/UX 관점

없음 — 이번 신고 건 알림(이미 발급됨)은 가리키는 배지가 정책상 영구히 삭제 상태이므로
클릭 시 404가 계속된다(20260824_007에서 사용자가 이미 확정한 "소프트 삭제 배지 직접 접근
= 존재하지 않는 배지와 동일 처리" 정책 그대로 — 이번 티켓에서 재론하지 않는다). 이번 수정은
**앞으로 같은 상황이 재발하지 않도록** 하는 것이 목적이다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

1. **근본 원인 차단** — `api/admin/badges/[id]/route.ts`에 `invalidateUnclaimedDrops` 헬퍼를
   추가하고, `DELETE` 핸들러(소프트 삭제)와 `PATCH` 핸들러의 `active: false` 분기 양쪽에서
   `deleted_at`을 채운 직후 호출한다. 이 헬퍼는 `poi_drops`에서 `badge_id`가 일치하고
   `picked_up_at IS NULL`이면서 `is_available = true`인 행만 `is_available = false`로
   무효화한다. `PATCH`의 `active: true`(되살리기) 분기는 호출하지 않는다 — 드랍 자동 부활
   방지. 드랍 무효화가 실패해도 배지 소프트 삭제 자체는 이미 끝난 뒤이므로 요청을 실패시키지
   않고 로그만 남긴다(크론 안전망이 다음 주기에 정리).
2. **안전망** — `api/cron/poi-cleanup/route.ts`에 기존 `expires_at` 기반 소각과 별개로,
   `poi_drops`를 `badges!inner(deleted_at)`로 조인해 `is_available=true AND
   picked_up_at IS NULL AND badges.deleted_at IS NOT NULL`인 행을 찾아 소각하는 로직을
   추가했다. 두 소각 블록은 독립적으로 실행되며(만료 소각이 먼저 `is_available=false`로
   갱신한 행은 두 번째 조회의 `is_available=true` 조건에서 자동으로 제외돼 중복 집계되지
   않는다), 응답 JSON에 `{ expired, orphanedByDeletedBadge }` 두 건수를 모두 반환한다.
   기존 `ids.length === 0` 조기 리턴 분기는 제거했다 — 만료 건이 0건이어도 두 번째(orphan)
   조건은 별도로 계속 확인해야 하기 때문.
3. **데이터 정리 SQL** — 티켓에 명시된 4개 `poi_drops.id`를 `is_available=false`로 갱신하는
   `seed_20260826_orphan_drop_cleanup.sql`을 작성했다(대상 건수가 정확히 4건일 때만
   실행되는 안전장치 `DO` 블록 + 실행 전/후 확인 SELECT 포함). **실행하지 않음** — 사용자
   승인 후 오케스트레이터가 직접 실행.
