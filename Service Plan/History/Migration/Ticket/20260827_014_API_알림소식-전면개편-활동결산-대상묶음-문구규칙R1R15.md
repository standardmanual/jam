# [API] 알림 소식 전면 개편 — 활동 결산·대상 묶음·문구 규칙 R1~R15 적용

## 배경 / 문제 정의

알림함이 **한 사건을 여러 줄로 쪼개서 보여준다.** 유저 관점에서는 로직상 옳은 분리도 홍수로
읽힌다.

### 현상 1 — 결산 카테고리 (사용자 스크린샷)

```
활동 중에 아이템 배지 1개가 떨어졌어요        1시간 전
활동 중에 아이템 배지 1개가 떨어졌어요        1시간 전
```

버그가 아니다. `item_badge_earned`의 묶음 키가 `item_badge_earned:sync:{strava_activity_id}`라
**동기화 1회가 아니라 액티비티 1건**이 단위이고, 문구가 활동을 구분해주지 않아 두 행이 글자
하나까지 같아진다.

### 현상 2 — 컬렉션 (프로덕션 DB 실측, 2026-08-25 09:00:58)

한 유저가 배치 1회에서 **0.09초 안에 `collection_slottable` 5행**을 받았다.

```
새벽 물안개 몽환에 넣을 수 있는 아이템 배지가 1개 있어요        09:00:58.187
비밀의 카페 탐험에 넣을 수 있는 아이템 배지가 1개 있어요        09:00:58.189
티타늄 맹신에 넣을 수 있는 아이템 배지가 2개 있어요             09:00:58.213
180 BPM의 심장에 넣을 수 있는 아이템 배지가 2개 있어요          09:00:58.278
노을 헌터의 기록에 넣을 수 있는 아이템 배지가 1개 있어요        09:00:58.280
```

전체 알림 37건 중 `collection_slottable`이 10건(27%)으로 1위이고, 유저 10명 중 3명이 다중 행을
받았다.

### 근본 원인

**묶음의 1차 축이 「소식 종류」와 「대상(활동·컬렉션·미션·POI)」이라 대상 수만큼 행이 생긴다.**
유저의 멘탈모델은 반대다 — "오늘 아침에 달린 그거, 뭐 받았지?"

### 검토 산출물

문장을 먼저 쓰고 문장에서 정책을 역산하는 방식으로 두 라운드를 돌았다. 이 티켓의 스펙은
아래 두 문서가 **단일 진실**이다.

- [RECAP_CASEBOOK.md](../../../Specs/PRD/Notification/RECAP_CASEBOOK.md) — ① 보상 획득 6종 (v3 확정)
- [REST_CASEBOOK.md](../../../Specs/PRD/Notification/REST_CASEBOOK.md) — 그 외 17종 (v3 확정)

## 상세 요구사항

### 문구 규칙 R1~R15 (두 케이스북에서 확정)

| # | 규칙 |
|---|---|
| R1 | 「이번 활동으로」 접두를 쓰지 않는다 |
| R2 | 고유명사에 작은따옴표를 쓰지 않는다 (볼드가 슬롯을 표시한다) |
| R3 | 화폐 단위는 「포인트」다. 「JAM 포인트」·「P」를 쓰지 않는다 |
| R4 | 미션 소식은 「완료했다」만 말한다. 미션 자체의 보상은 문구에 넣지 않는다 (진행 정보는 남긴다) |
| R5 | 결산에서 2종 이상이면 나열하지 않고 총량으로 말한다 |
| R6 | 새 결산 화면을 만들지 않는다. 착지는 기존 화면 |
| R7 | 미션은 「완료」다 (「달성」 아님) |
| R8 | 대표는 희귀도 최상위로 고른다 |
| R9 | **R11에 흡수됨** — 활동은 「대상」의 한 종류다 |
| R10 | 착지가 다르면 행을 나눈다 |
| R11 | 같은 종류의 소식이 **대상 2건 이상이면 한 행으로 묶고 착지를 목록 화면으로 올린다** (전면 채택, 카테고리 예외 없음) |
| R12 | 부족한 것을 이름으로 부른다 — **컬렉션 #10에만 적용** (아래 결정 사항 참고) |
| R13 | 컬렉션의 목표는 「완성」이다. 「추가」·「장착」을 쓰지 않는다 |
| R14 | 본인 닉네임을 문장에서 부르지 않는다 |
| R15 | 팔로잉 소식은 사람 단위로 묶고, 하루 상한도 사람 수로 센다 |

### 서비스/코드베이스 관점

#### A. ① 보상 획득 — 활동 결산으로 재편

**새 객체를 만들지 않는다.** `strava_activities`가 이미 활동을 영속 저장하고 모든 보상이
`activity_id`를 payload에 싣고 있다. 필요한 것은 소식 종류 하나와 문구·묶음 규칙이다.

- `notification_type` ENUM에 **결산 타입 추가** (마이그레이션 필요)
- 묶음 단위 = **KST 하루** *(2026-08-27 정정 — 최초 「활동 1건」에서 변경)*
  - 「활동 단위 + 임계값 2건(F2)」을 합치면 사실상 하루 단위가 된다. 활동별 키를 쓰면 F2를
    위한 fold가 따로 필요한데 결산은 인라인 생성이라 배치의 `foldTargets`를 쓸 수 없다.
  - 대가 두 가지를 수용한다 — ① 오전 소식의 문장이 오후 활동으로 덮인다(`bumps_badge=false`라
    dot은 다시 켜지지 않는다) ② 심야 경계(23:50·00:10 동기화)는 F2로 접히지 않고 2행이 된다.
- 사다리 — 케이스북 A~F 표가 명세다

| 칸 | 상황 | 문구 | 착지 |
|---|---|---|---|
| A | 1종·1개 | 개체를 이름으로 | 그 개체 상세 |
| B | 1종·N개 | 대표 + 외 N | 카테고리 목록 |
| C·D | 2종 이상 | 총량 | `/badges` 또는 프로필 |
| E | 강한 신호 혼재 | 강한 신호를 헤드라인으로 | 그 신호의 상세 |
| F2 | 활동 2건 이상 | 활동 수 + 총량 | 프로필 |

- **포인트는 종류로 세지 않는다.** 문장 꼬리에 붙는 부속으로 다룬다
- **컬렉션 소식은 결산에 넣지 않는다** — 결과가 아니라 초대다. 별행 유지
- **미션 완료도 결산과 별행** — 착지가 다르다(R10). 케이스북 E2 참고

#### B. R11 — 대상 2건 이상 묶음 (신규 묶음 문구 9개)

| 소식 | 묶음 문구 | 착지 |
|---|---|---|
| #9 컬렉션 장착 가능 | 컬렉션에 넣을 수 있는 **아이템 배지 N개**가 있어요 | **인벤토리** |
| #10 완성 임박 | 한 칸만 남은 컬렉션이 **N개** 있어요 | `/collections` |
| #11 완성 가능 | 다 모은 컬렉션 **N개**를 완성해보세요 | `/collections` |
| #18 드랍 지점 활성 | 드랍한 **N곳**에 **M명**이 다녀갔어요 | `/drops` |
| #20 마일스톤 | 미션 **N개**가 목표에 가까워졌어요 | `/missions` |
| #21 마감 임박 | 미션 **N개**가 **이틀** 뒤 끝나요 | `/missions` |
| #23 순위 상승 | 미션 **N개**에서 순위가 올랐어요 | `/missions` |
| #24 종료 (전원 완료) | 축하해요! 미션 **N개**를 끝냈어요. 결과를 확인해보세요 | `/missions` |
| #24 종료 (미완료 포함) | 미션 **N개**가 끝났어요. 결과를 확인해보세요 | `/missions` |

> #9 묶음은 **컬렉션이 아니라 배지를 센다.** 착지도 배지가 있는 곳(인벤토리)이다.

#### C. 컬렉션 #9·#10·#11 우선순위 — 한 컬렉션에 하나만

세 조건이 동시에 참일 수 있어(잔여 1칸 + 그 배지를 미장착 보유) 한 컬렉션이 3행을 만든다.

| 상태 | 보낼 소식 |
|---|---|
| 완성 가능 (전부 보유·미장착) | **#11만** |
| 잔여 1칸 도달 (아직 그 배지 없음) | **#10만** |
| 그 외 넣을 게 있음 | **#9만** |

**순서** — 컬렉션마다 우선순위로 종류를 정한 뒤, 같은 종류가 2건 이상이면 R11로 묶는다.

**이 우선순위는 R12의 전제 조건이다.** 없으면 이미 보유한 배지를 "찾아"라고 말하게 된다.

#### D. 개별 문구 변경

| 소식 | 변경 |
|---|---|
| #10 완성 임박 | `'{bookName}', 한 칸만 남았어요` → **`{badgeName}`을 찾아 `{bookName}`을 완성해보세요** (R12) |
| #11 완성 가능 | `컬렉션에 추가해보세요` → **`컬렉션을 완성해보세요`** (R13) |
| #13 픽업됨 (묶음) | **착지 제거** — 링크 없음. 픽업된 아이템은 소프트 삭제 상태라 갈 곳이 없다 |
| #18 드랍 지점 | `{me}님이 드랍한 자리에` → **`드랍한 곳에`** (R14, 「자리」→「곳」) |
| #24 종료 | **완료/미완료 분기** — 완료자만 「축하해요!」 |
| #26 팔로우 | `{actor}님이 {me}님을 팔로우해요` → **`{actor}님이 팔로우해요`** (R14) |
| #41 동기화 지연 | `Strava 동기화가 끊겼을 수 있어요` → **`Strava에 활동이 기록됐는지 확인해보세요`** |
| #44 포인트 | `{points} JAM 포인트` → **`{points} 포인트`** (R3) |
| 따옴표 제거 | 컬렉션명·미션명·배지명을 쓰는 **문구 11개** (R2) |

#### E. #27 맞팔 소식 제거 + 공백 메우기

맞팔은 유저가 방금 자기 손으로 성립시킨 결과다 — PRD §2-2 「자기 행동의 메아리」.

**그냥 지우면 소식이 통째로 사라지는 경우가 생긴다.** 현재 로직은 맞팔 성립 시
`mutual_follow` 하나만 만들고 `followed`를 만들지 않는다.

| 상황 | 지금 | 변경 후 |
|---|---|---|
| 내가 먼저 팔로우 → **상대가 되팔로우** | `mutual_follow` | **`followed` 생성** ("**예린**님이 팔로우해요") |
| 상대가 먼저 팔로우 → **내가 되팔로우** | `mutual_follow` | **소식 없음** (내 행동) |

ENUM 값 `mutual_follow`는 **DB에서 지우지 않는다** — Postgres는 ENUM 값 제거가 안전하지 않다.
TS 타입에서만 제외하고 「예약됐으나 사용하지 않음」으로 표시한다
(`following_nearby_drop`·`nearby_drops` 선례).

#### F. #40·#41 중복 제거

끊긴 채로 3일이 지나면 확정(#40) 뒤에 추측(#41 "끊겼을 수 있어요")이 따라붙어, 정보가 더 적은
문장이 뒤에 온다.

- **#40이 미해소 상태면 #41을 만들지 않는다**
- #41은 **토큰은 멀쩡한데 새 활동이 안 들어오는 경우** 전용으로 좁히고 문구를 교체한다

#### G. ⑥ 팔로잉 — 사람 단위 묶음 (R15)

- 한 사람의 소식이 하루 2건 이상이면 대표 하나 + "소식이 **N건** 더 있어요"
- 대표 선정은 기존 배치 우선순위 재사용 (mythic > legend > 컬렉션 완성 > 미션 완료, 동순위 최근 순)
- 묶음 행의 착지 = **`/{username}` 프로필**
- **하루 상한을 「2건」에서 「사람 2명」으로** 변경

### DB 관점 (⚠️ 실행은 오케스트레이터가, 개발자는 파일 작성까지만)

1. **마이그레이션** — `notification_type` ENUM에 결산 타입 추가
   → `jam-web/supabase/migrations/0XX_notification_recap_type.sql`
2. **기존 알림 전량 삭제 + 재생성** (배포 시점 1회성)
   → `jam-web/supabase/seed_*.sql` 또는 운영 절차로 기록
   - `DELETE FROM notifications` (전량)
   - **`users.notifications_seen_at`은 건드리지 않는다** — 재생성된 소식이 「새 소식」으로
     뜨고 dot이 켜지도록 한다 (사용자 확정)
   - 삭제 후 `/api/cron/notifications` 배치를 1회 수동 실행해 상태 기반 소식을 되살린다
   - **결산 소식(①)은 백필하지 않는다** — 다음 동기화부터 새 형식으로 쌓인다 (사용자 확정)

> **Supabase는 staging·프로덕션 공용 단일 DB다.** DELETE는 즉시 프로덕션에 반영된다.
> 실행 전 반드시 사용자 승인을 받는다.

### 구현 순서

1. 마이그레이션 SQL 작성 (실행 안 함) + 타입 갱신
2. 문구(`ko.ts`) — R2·R3 일괄 적용 + 신규 문구
3. 렌더·착지(`message.ts`·`href.ts`) — 결산 + R11 묶음
4. 배치 5개 — 우선순위·묶음·분기

6. `api/follows` 맞팔 처리
7. 테스트 갱신

### 결산 조립 시점 — 판단 필요

현재는 발급 지점마다 `createNotification`을 흩어서 호출하고 `appendKeys`로 점진 병합한다.
종류별로 쪼개져 있으면 sync 중간 실패가 티 안 나지만, **하나로 합치면 반쪽 결산**(배지만 있고
포인트가 빠진 채 확정된 것처럼 보이는 행)이 남을 수 있다.

원칙적으로는 **활동 처리가 끝난 뒤 한 번 조립해 넣는 것**이 맞다. 다만 호출이 세 파일에
흩어져 있어 구조 변경 비용이 있다. 점진 병합을 유지하는 절충도 가능하다 — **구현자가 판단하고
근거를 완료 기록에 남긴다.**

### 잔여 이슈

**배포 순서 (필수)** — ① 마이그레이션 105 *(완료)* → ② 프로덕션 승격 → ③ seed 실행(전량 삭제)

다시 만들어 삭제 효과가 사라진다.

- **전량 삭제가 #40을 지운다** (게이트 WARN ③, 사용자 확정하에 수용) — 배치는 #40을
  재생성하지 않으므로 리셋 직후 배치에서 토큰 만료 유저에게 #41 오안내가 1회 나간다.
  실행 전 `SELECT count(*) FROM strava_connections WHERE token_expires_at < now()`로 대상
  유무를 확인한다.
- **프로필 착지가 준비되지 않았다** — 결산 C3·D1·E3·F2가 프로필로 향하는데
  `user_activity_feed`에 활동 참조가 없어 같은 활동 이벤트가 평면 나열된다. 알림함의 홍수가
  프로필에서 재현된다. **후속 티켓 필요.**
- **레거시 6종 + `mutual_follow` 죽은 코드** — 전량 삭제 이후 렌더 경로가 도달 불가능해진다.
  단 `msgRareBadgeEarned`는 ⑥ #29가 계속 쓰므로 삭제 시 주의. **정리 티켓 필요.**
- **`ko.ts`의 「P」 표기 잔존 4곳** — `pointBalance`·`badges.rewardPoints`·`pointsValue`·
  `missions.rewardPoints`가 가이드 §3이 Bad로 명시한 `{n}P`를 쓴다. 이번 R3 범위(「JAM 포인트」)
  밖이라 손대지 않았다. **정리 티켓 필요.**
- **`missions.rewardPointsLine` 호출부에 `toLocaleString` 누락** — 가이드 §3의 「1,200 포인트」
  형식이 아니다(변경 전과 동일한 기존 문제).
- **`confirmDrop`의 작은따옴표** — 알림 문구가 아니라 이번 범위 밖.
- **`activity_ids` 귀속 입도가 경로마다 다르다** — `sync.ts`는 배치가 처리한 활동 전부를,
  `drop-engine`은 드랍이 발생한 활동만 싣는다. 배지 1개만 나온 5건 동기화가
  "활동 5건에서 배지 1개를 획득했어요"가 될 수 있다(거짓은 아니나 체감이 어긋난다).
- **`activity_ids` 누적 상한 없음** — 하루 동안 자란다. 현재 트래픽에서는 문제없으나
  방어적 컷(배열당 100개) 검토 여지.
