# 개발 프로세스 가드레일

> 이 문서는 "버그 하나하나"가 아니라, **그 버그들을 반복해서 만든 개발 프로세스 패턴**을 다룬다.
> 2026-08-11 기준 티켓 146개 + 운영 이력 문서 66개 전체를 감사(20260811_001, 20260811_002)해
> 추출한 것 — 코드를 고치거나 DB를 만질 때, 특히 핵심 루프(Strava 동기화 → 배지/드랍/포인트
> 발급)에 손대는 작업 전에 이 문서를 먼저 확인한다.

## 왜 이 문서가 필요한가

JAM!의 핵심 신뢰 루프는 "활동을 하면 정확히 그에 맞는 보상을 받는다"는 약속이다. 지금까지
발생한 가장 심각한 버그들은 전부 **"실패했는데 아무 신호도 없어서 아무도 몰랐다"**는 공통점을
가진다. 개별 버그를 하나씩 고치는 것만으로는 부족한 이유가 여기 있다 — 같은 클래스의 실수가
다른 파일, 다른 테이블에서 계속 재발했다(아래 패턴별 사례 참고).

---

## 반복된 개발 프로세스 실수 패턴

### 패턴 1 — 공유 함수·트리거를 통째로 재정의하면서 이전 수정사항을 잃어버림

`CREATE OR REPLACE FUNCTION`으로 함수 전체를 새로 쓰면, 그 사이 다른 마이그레이션이 쌓아온
수정사항이 통째로 사라질 수 있다.

- 실제 사례: `pickup_drop()` — 007에서 "본인 드랍 픽업 허용"으로 고쳤는데, 044가 다른 버그를
  고치며 함수를 통째로 재정의하면서 007의 정책이 되돌아감(047에서 재수정)
- 실제 사례: `handle_new_user()` — 020이 컬럼명을 바꾼 뒤 누군가 마이그레이션 파일 없이
  운영 DB에서 직접 함수를 패치하며 인벤토리 생성 구문을 통째로 빠뜨림(20260811_001)

**규칙**: 공유 RPC/트리거 함수를 고칠 땐 `pg_get_functiondef`로 **현재 운영 DB의 실물**을
먼저 확인하고, 그 위에 필요한 부분만 바꾼다. "예전에 이랬을 것"이라는 기억이나 레포의 가장
최근 마이그레이션 파일만 믿지 않는다 — 레포와 운영 DB가 어긋나 있을 수 있다(패턴 2 참고).

### 패턴 2 — 코드 배포와 DB 마이그레이션 적용이 분리되어 있고, 적용 여부를 추적하는 장치가 없음

이 프로젝트는 `supabase_migrations.schema_migrations`에 4건만 기록돼 있다(레포엔 80개 파일).
즉 대부분의 마이그레이션이 CLI(`supabase db push`)가 아니라 SQL Editor·MCP `execute_sql`
등으로 수동 적용돼 왔고, "적용했는지 안 했는지"를 기계적으로 확인할 방법이 없었다.

- 실제 사례: 포인트 시스템(045/080) 도입 당시 "로컬 환경 제약으로 SQL 파일만 작성, 원격
  미적용" 상태로 세션이 끝났던 적이 있음 — 코드는 이미 `awardPoints()`를 호출하도록
  배포됐는데 DB에 테이블이 없으면, 실패는 예외 없이 로그만 남기므로(패턴 4) 조용히 샜다.
- 실제 사례: 068 데이터 정합화 마이그레이션도 같은 이유로 "배포 후 수동 실행 필요"로 남음.

**규칙**: DB 스키마·함수·트리거 변경은 **마이그레이션 파일 작성 → 즉시 적용(`apply_migration`
또는 동등한 방식) → 커밋을 한 세트**로 묶어 같은 턴 안에 끝낸다. "일단 파일만 써두고 나중에
적용"을 기본 흐름으로 만들지 않는다. ([04_PROJECT_SPEC.md](PRD/04_PROJECT_SPEC.md) "절대 하지
마" 목록에도 명문화됨)

### 패턴 3 — 대용량 테이블을 페이지네이션 없이 조회해 조용히 잘려나감

Supabase/PostgREST는 한 번의 조회에서 기본 1,000행까지만 반환한다. `.select('*')` 등으로
전체를 가져오려 하면 에러 없이 뒤쪽 데이터가 그냥 잘려나간다.

- 실제 사례: 2026-07-31 하루에만 `poi` 테이블 관련 3곳(지점 매칭, 드랍 지도 API, 체크인 배지
  탭)에서 각각 독립적으로 발견·수정됨 — 대량 등록된 산 POI가 반복적으로 누락됐었음
- 이번 감사에서 4번째 사례 발견: 드랍엔진의 아이템배지 후보 조회가 900/1,000행까지 근접해
  있었음(20260811_002에서 페이지네이션으로 구조적 수정)
- 2026-08-25, 5번째 사례: `admin/missions/page.tsx`의 `badges` 선택 목록 조회(필터 없음,
  미삭제 배지 2,172건)가 name 오름차순 1,000행에서 잘려 5개 레벨업 게이트 트리 중 4개가
  어드민 검색에서 아예 안 잡힘(20260825_028, `range()` 루프로 수정). 같은 유형을 코드베이스
  전반에서 재판정한 후속 티켓(20260825_037)에서 `api/admin/badges/route.ts`(GET),
  `admin/today/page.tsx`, `admin/itembooks/page.tsx`, `lib/itembook/checker.ts`/
  `completable.ts` 등 6곳을 추가로 발견·수정. `lib/missions/visibility-server.ts`는
  페이지네이션 대신 **쿼리 방향을 뒤집어**(먼저 게이트 배지 이름으로 소수의 id를 구하고,
  그 id로 유저 보유 여부를 조회) 절단 가능성 자체를 구조적으로 없앤 사례 — "범위를 좁힐 수
  있으면 페이지네이션보다 방향 역전이 더 근본적인 해법"이라는 대안 패턴으로 참고할 만하다.

**규칙**: 테이블 전체 또는 큰 하위집합을 조회할 땐 (a) 조건으로 범위를 좁히거나(bbox 등)
(b) `.range()` 기반으로 끝까지 순회하는 헬퍼를 쓰거나 (c) 가능하면 조회 방향 자체를 뒤집어
결과 집합을 구조적으로 작게 만든다(위 `visibility-server.ts` 사례). 절대 "지금은 1,000행
안 넘으니 괜찮다"고 가정하지 않는다 — 컨텐츠는 계속 늘어난다.

### 패턴 4 — 실패를 예외 없이 로그만 남기고 흡수하는 코드가 감지 사각지대를 만듦

"본 흐름을 막지 않기 위해" 실패를 조용히 삼키는 방어적 코드 자체는 합리적인 선택이지만,
**로그가 사람이 봐야만 발견되는 곳(콘솔)에만 남으면 사실상 안 남긴 것과 같다.**

- 실제 사례: 포인트 지급 실패, 드랍엔진 인벤토리 부재 — 둘 다 `console.error`만 남기고
  `engine_decision_log`(SQL로 조회 가능한 구조화 로그)에는 기록되지 않고 있었음
  (20260811_002에서 `awardPoints()` 중앙화 + 드랍엔진 조기 return 로깅으로 수정)

**규칙**: 보상(배지·아이템·포인트) 발급 경로에서 실패를 흡수할 땐, 반드시
`logEngineDecision()`으로 `engine_decision_log`에도 기록한다. "언젠가 문의 오면 그때 콘솔
로그 뒤진다"를 감지 전략으로 삼지 않는다.

### 패턴 5 — 일부 케이스만 처리하고 나머지는 조용히 스킵하는 비완전 분기

`if (type === 'X') { ... }` 형태로 특정 케이스만 처리하고 나머지 케이스는 아무 처리도,
아무 로그도 없이 지나가는 코드.

- 실제 사례: 미션 완료 보상 지급 로직이 `reward_type === 'points'`만 처리해, 배지 보상으로
  설정된 미션은 완료돼도 배지가 발급된 적이 없었음(20260724_1805에서 발견·수정, 과거 미발급분
  소급 지급은 안 함)

**규칙**: 타입/enum으로 분기하는 코드를 새로 짜거나 수정할 땐, 마지막에 "그 외의 경우"를
명시적으로 처리하거나 최소한 로그를 남긴다. "지금 있는 값만 고려하면 된다"고 가정하지 않는다
— 나중에 새 값이 추가되면 조용히 새는 코드가 된다.

### 패턴 6 — 암묵적으로 사람이 기억해서 연동해야 하는 등록 지점이 있음

"새로운 X를 추가하면 Y 목록에도 수동으로 등록해야 한다"는 규칙이 코드 주석에만 있고
강제되지 않는 경우.

- 실제 사례: 피드 이벤트가 배지 정보를 스냅샷으로 저장하는 이벤트 타입을 추가할 때마다
  `BADGE_METADATA_EVENTS` 집합에 수동으로 등록해야 하는데, 깜빡하면 그 이벤트만 배지 정보
  갱신이 안 반영됨(20260722_1120)

**규칙**: 이런 "수동 등록 지점"을 새로 만들 수밖에 없다면, 최소한 그 지점을 이 문서나
[핵심 루프 의존성 지도](#핵심-루프-의존성-지도)에 추가해 어디서든 검색으로 찾을 수 있게 한다.
가능하면애초에 수동 등록이 필요 없는 구조(전체 목록을 코드에서 자동 순회)로 설계한다.

### 패턴 7 — 마이그레이션 번호/네이밍 충돌

같은 날 여러 작업이 진행되며 마이그레이션 번호가 중복 부여된 사례(045가 두 파일에 부여됨,
20260811_002에서 발견·정리).

**규칙**: 새 마이그레이션 작성 전엔 `ls supabase/migrations | tail`로 최신 번호를 항상 직접
확인한다. 레포 상태를 기억에 의존하지 않는다.

## 핵심 루프 의존성 지도

아래 테이블·함수 중 하나라도 건드리는 작업이면, **작업 시작 전에 오른쪽 열의 파일들을 전부
확인**하고, 어떤 걸 건드리는지 사용자에게 평문으로 먼저 보고한다([04_PROJECT_SPEC.md](PRD/04_PROJECT_SPEC.md)
"항상 해" 참고).

| 건드리는 대상 | 반드시 같이 확인할 것 |
|---|---|
| `strava_activities` 테이블/컬럼 | `src/lib/strava/sync.ts`, `src/types/database.ts`의 `StravaActivityRow`·`NormalizedActivity`, `src/lib/badge-engine/index.ts`, `src/lib/drop-engine/index.ts`(둘 다 `normalized` 스냅샷을 그대로 읽음) |
| `strava_connections.last_synced_at` (동기화 커서) | `src/lib/strava/sync.ts`의 잠금(4-1)·롤백(catch) 로직, `/api/admin/users/[id]/reset` (수동 복구 경로) |
| `inventory` / `inventory_items` | DB 트리거 `handle_new_user()`(가입 시 자동 생성), `src/lib/drop-engine/index.ts`의 `fetchDropStructure`, `pickup_drop()` RPC |
| `badges` 테이블(조건·보상 필드) | `src/lib/badge-engine/index.ts`(activity 타입), `src/lib/drop-engine/index.ts`(item 타입), `src/lib/strava/sync.ts`(poi 타입), `Service Plan/Specs/BadgeEngine/BADGE_ENGINE_UNIFIED.md` |
| `award_points()` RPC / `point_*` 테이블 | `src/lib/points/index.ts`(유일한 호출 경로), 호출부 6곳(배지·드랍·미션×2·조합·어드민 지급) — 새 보상 지급 지점을 추가해도 반드시 이 함수를 거치게 할 것, 직접 INSERT/UPDATE 금지 |
| `poi` 테이블(반경·좌표) | `src/lib/poi/matcher.ts`(활동-POI 매칭), `src/app/api/drops/route.ts`(드랍 지도), `src/app/api/checkin-badges/route.ts`(체크인 배지 탭) — 셋 다 max-rows 대응이 되어 있어야 함(패턴 3) |
| `engine_decision_log` 이벤트 타입 | `src/lib/engine-log/index.ts`의 `EngineDecisionEvent` 유니언 — 새 실패/판정 지점을 로깅할 땐 여기 타입부터 추가 |
| `users` 테이블 컬럼 | `src/types/database.ts`의 `UserRow` — `database.generated.ts`(자동 생성본)와 대조해 누락 없는지 확인(`npm run db:types`로 재생성) |

## 작업 전 영향범위 보고 규칙

핵심 루프(위 표의 대상)에 손대는 작업은, 코드를 고치기 전에 다음을 평문 한국어로 먼저
보고하고 진행 여부를 확인받는다:

1. 어떤 테이블/함수/파일을 건드리는지
2. 위 의존성 지도에서 같이 확인해야 할 항목 중 실제로 영향받는 것
3. DB 스키마 변경이 포함되면, 마이그레이션 파일 작성부터 적용·커밋까지 한 번에 끝낼 계획인지

이건 사용자가 코드를 읽고 검토하라는 뜻이 아니라, **"어디까지 건드리는지"를 확인받는 절차**다
— 비개발자도 판단할 수 있는 수준의 정보다.
