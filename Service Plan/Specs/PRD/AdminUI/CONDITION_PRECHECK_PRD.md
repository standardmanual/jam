# PRD: 배지·미션 생성 전 드랍엔진 사전 시뮬레이션

## 1. 요약

어드민이 배지나 미션을 새로 만들거나 조건을 고칠 때, **저장하기 전에** 그 조건이 실제
드랍엔진(배지엔진)에서 어떻게 판정되는지 미리 계산해서 보여주는 기능이다. 지금은 조건의
"형태"만 검사하고 저장한 뒤에야 실제 판정 결과를 알 수 있어서, 회차가 영원히 0으로 고정되거나
발급 조건이 스펙과 다르게 동작하는 버그가 사후에야 발견되고 있다. 이 기능은 그 발견 시점을
생성 화면으로 앞당긴다.

## 2. 담당자

| 이름 | 역할 | 코멘트 |
|---|---|---|
| 시현 | PM 겸 개발 | 배지엔진·어드민 전체를 혼자 운영. 이 문서의 승인·구현·검증을 모두 담당 |

## 3. 배경

JAM!의 배지엔진은 43개의 `engine` 조건 타입과 3개의 `pending`(미구현) 조건 타입을 레지스트리로
관리하고, 조건이 저장될 때 필드 형태만 정적으로 검사한다. 실제 발급 여부는 유저의 활동 이력이
쌓이고 배지엔진이 그 이력에 대해 조건을 평가할 때에만 계산된다. 그래서 다음과 같은 문제가 반복해서
발생했다.

- **20260908_1438**: 반복형 조건이 게이트나 기간 필드와 결합되면 회차가 영원히 0으로 멈추는
  버그가 26개 계열, 49종의 배지에서 동시에 발생했다. 저장은 정상적으로 됐지만 실제로는 아무도
  발급받을 수 없는 상태였다.
- **20260908_1512**: `running:R2` 배지의 발급 로직이 콘텐츠 기획 문서의 스펙과 다르게 동작하고
  있었다. 조건 화면에는 문제가 없어 보였지만 실제 판정 결과가 의도와 어긋났다.
- **20260906_1432**: 조건을 충족한 유저에게 배지가 발급되지 않는 문제를 발견할 수단이 없어서,
  유저가 우연히 알아채기 전까지 아무도 몰랐다.

이 버그들의 공통점은 **저장 시점의 형태 검사로는 절대 걸러지지 않고, 실제 유저 데이터에 대해
판정을 돌려봐야만 드러난다**는 점이다. 다행히 이 판정을 재현하는 함수(`evaluateConditionDetailed`,
`evaluateBadgesDetailed`)는 이미 배지엔진 안에 존재하고, 어드민의 `badge-diagnosis`·`simulator`
기능이 같은 함수를 다른 목적(사후 진단)으로 이미 쓰고 있다. 새 엔진을 만들 필요 없이, 같은 함수를
저장 전 시점에 한 번 더 호출하기만 하면 되는 상황이라 지금이 이 기능을 붙이기 적절한 시점이다.

## 4. 목표

**목표**: 배지·미션 조건을 저장하기 전에 오작동 여부를 어드민 화면에서 바로 확인할 수 있게 해서,
지금처럼 사후에 발견되는 발급 버그를 생성·수정 시점으로 앞당겨 막는다.

**핵심 결과(수용 기준)**
- 배지·미션 생성/수정 폼에서 "시뮬레이션 실행" 버튼을 누르면 저장하지 않은 현재 조건값 그대로
  판정 결과(발급 가능/불가능, 실제값 대 필요값, 실패 사유)를 화면에서 확인할 수 있다.
- 최근 발생했던 버그 패턴(회차 0 고정, 짝필드 누락으로 인한 fail-closed, pending 필드 사용)이
  시뮬레이션 단계에서 명확한 경고 문구로 나타난다.
- 시뮬레이션은 DB에 어떤 것도 기록하지 않는다(dry run 전용).
- 배포 후 한 달간, 같은 유형(형태는 정상이지만 판정이 어긋나는)의 배지엔진 버그 티켓이 신규로
  발생하지 않는다.

## 5. 대상

어드민 화면을 쓰는 사람은 현재 시현 1명뿐이다. 이 기능이 풀어야 하는 문제는 "배지를 만드는 사람과
그 판정 결과를 실제로 확인하는 시점이 분리되어 있어서, 문제를 나중에야 발견하게 되는 상황"이다.
제약은 다음과 같다.

- 판정에는 실제 유저의 활동 이력이 필요한데, 새로 만드는 조건은 아직 아무 유저에게도 적용된 적이
  없다. 그래서 실제 유저를 골라 그 유저의 기존 활동 이력에 대해 조건을 시험해보거나, 가상의 활동
  수치를 입력해서 시험해보는 두 가지 방식이 모두 필요하다.
- 조건 종류가 43개(+ 6개 external, 3개 pending)로 많고 계속 늘어나므로, 조건 종류마다 시뮬레이션
  UI를 따로 만드는 방식은 유지보수 비용이 크다.

## 6. 가치 제안

- **얻는 것**: 저장 버튼을 누르기 전에 "이 조건이 실제로 작동하는가"를 바로 확인할 수 있다.
- **피하는 것**: 배지를 만들고 배포한 뒤, 유저 데이터가 쌓이고 나서야 회차가 0에 멈춰 있다는 것을
  발견하고 P0 티켓으로 급하게 고치는 상황.
- **차별점**: 이미 존재하는 판정 함수를 그대로 재사용하기 때문에, 시뮬레이션 결과와 실제 프로덕션
  판정 결과가 서로 다른 로직으로 계산되어 어긋날 위험이 없다. 별도의 검증 엔진을 새로 만들면 그
  엔진 자체가 실제 배지엔진과 다르게 동작해서 "시뮬레이션은 통과했는데 실제로는 안 되는" 새로운
  종류의 버그를 만들 수 있는데, 이 방식은 그 위험을 원천적으로 없앤다.

## 7. 솔루션

### 7.1 UX / 플로우

1. 어드민이 `/admin/badges/new`(또는 수정 화면)에서 조건 필드를 입력한다.
2. 폼 하단에 "판정 시뮬레이션" 버튼이 새로 생긴다. 기존의 저장 버튼과는 별개이며 저장을 하지
   않아도 언제든 누를 수 있다.
3. 버튼을 누르면 대상을 고르는 작은 패널이 열린다.
   - **기존 유저로 시험**: 유저를 검색해서 선택하면, 그 유저의 실제 활동 이력을 그대로 이 조건에
     대입해서 판정한다.
   - **가상 활동으로 시험**: 이미 시뮬레이터(`/admin/simulator`)에 있는 가상 활동 입력 폼(수치
     직접입력 또는 GPX 업로드)을 재사용해서, 없는 유저·없는 활동을 상정해 판정한다.
4. 결과가 같은 화면에 나타난다.
   - 판정 가능 여부(통과/실패/차단)
   - 실패 사유 — 특히 조건이 `pending` 필드를 쓰고 있거나, 반복형 조건에 필수 짝필드가 빠져서
     fail-closed로 막힌 경우, 그 사실을 일반적인 "조건 불충족"과 구분해서 명확한 경고로 보여준다.
   - 실제값 대 필요값(예: 실제 12회 / 필요 15회)
   - 반복형 조건이라면 회차가 정상적으로 올라가는지(0에 고정되지 않는지)
5. 어드민은 이 결과를 보고 조건을 수정하거나, 문제가 없으면 그대로 저장한다. 시뮬레이션 실행
   자체는 DB에 아무 흔적도 남기지 않는다.

### 7.2 핵심 기능

- **저장 전 단건 조건 판정**: 폼에 입력된(아직 저장되지 않은) `condition_json` 하나를 대상으로,
  선택한 유저(실제 또는 가상)의 활동 이력에 대해 판정을 실행한다.
- **fail-closed 사유 구분 표시**: "조건은 유효하지만 아직 미충족"과 "조건 자체가 구조적으로 막혀
  있어 영원히 발급될 수 없음(pending 필드 사용, 필수 짝필드 누락, 게이트 결합 미지원 조합 등)"을
  화면에서 서로 다른 색/문구로 구분한다. 최근 사고들이 전부 후자였는데 형태 검사만으로는 구분이
  안 됐던 문제를 직접 겨냥한다.
- **기존 유저 재활용 판정**: 시뮬레이터에 이미 있는 "유저 선택 → 그 유저 이력에 조건 대입" 경로를
  가상 활동 입력 없이도 쓸 수 있게 한다. 새 조건을 이미 활동 이력이 많은 실제 유저에게 대입해보는
  쪽이, 매번 가상 활동을 새로 입력하는 것보다 반복형·기간형 조건을 검증하기에 더 실전적이다.
- **미션 화면에서도 동일 기능 제공**: 미션 생성/수정 화면에도 같은 시뮬레이션 버튼을 붙인다.
  미션은 배지와 판정 경로가 다른 부분(§2.2의 external 조건 등)이 있으므로, 미션 쪽 판정 진입점을
  먼저 확인하고 그에 맞춰 연결한다.

### 7.3 기술

- 새 엔진을 만들지 않고 기존 `jam-web/src/lib/badge-engine/index.ts`의
  `evaluateConditionDetailed(condition, activities, options)`를 그대로 호출한다. 이 함수는 이미
  순수 함수 형태로 단일 조건을 활동 배열에 대해 평가하고 `pass/reason/actual/required`를 반환하므로
  저장 여부와 무관하게 호출할 수 있다.
- 새 API 라우트(예: `/api/admin/badges/simulate-condition`)를 만들어 폼에서 넘어온
  `condition_json`(미저장)과 대상 유저(또는 가상 활동)를 받아 위 함수를 호출하고 결과를 반환한다.
  이미 저장된 조건을 대상으로 진단하는 `badge-diagnosis` API, 가상 활동을 만드는 `simulate` API와
  같은 패턴을 따르되, "condition_json을 저장 없이 그대로 받는다"는 점만 다르다.
- 클라이언트에서 저장 전 정적 검사를 담당하는 기존 `findBlockingConditionKeys`,
  `findConditionShapeSaveError`(`@/lib/admin/badge-condition-guards.ts`)는 그대로 유지한다. 이번
  기능은 그 형태 검사를 대체하는 것이 아니라, 형태 검사를 통과한 뒤에도 남아있는 "실제 판정 결과"
  라는 다음 단계를 보완하는 것이다.

### 7.4 가정

- `evaluateConditionDetailed`를 저장되지 않은 임의의 `condition_json`에 대해 호출해도 안전하다고
  가정한다(부수효과 없음). 실제 코드를 확인해 이 가정이 맞는지 구현 착수 전에 검증이 필요하다.
- 미션의 판정 경로가 배지엔진과 완전히 분리되어 있지는 않을 것이라고 가정한다. 만약 미션 판정이
  구조적으로 크게 다르면, 미션 쪽은 이번 범위에서 제외하고 배지만 먼저 적용할 수도 있다.
- 가상 유저(아직 존재하지 않는 활동 패턴)에 대한 시뮬레이션 UI는 기존 `/admin/simulator`의 입력
  폼을 그대로 재사용할 수 있다고 가정한다. 새로 만들지 않는다.

## 8. 릴리즈

- **1차 범위**: 배지 생성/수정 화면에 "판정 시뮬레이션" 버튼 추가. 기존 유저 선택 방식과 fail-closed
  사유 구분 표시까지 포함. 최근 사고 패턴(회차 0, 짝필드 누락)을 재현해서 화면에서 걸러지는지
  검증하는 것을 완료 기준으로 삼는다.
- **2차 범위**: 가상 활동 입력(시뮬레이터 폼 재사용) 연결, 미션 화면에 동일 기능 적용.
- 전체 소요는 기존 판정 함수를 재사용하는 구조라 크지 않을 것으로 예상하지만, 정확한 일정은
  `/jam-work` 파이프라인에서 티켓 단위로 산정한다. 이 PRD는 티켓 작성의 근거 문서 역할을 한다.
