# 활동 결산 소식 — 문구 케이스북

> 작성: 2026-08-27 / **v3 — 2차 검토 반영** (규칙 R1~R10 확정, 남은 확인 3건)
> 관련: [PRD.md](./PRD.md) §3 소식 26종 · §5 문구 강조 규칙 / [DATA_MODEL.md](./DATA_MODEL.md) §4 묶음 모델 / [UX_WRITING_GUIDELINE.md](../../UX_WRITING_GUIDELINE.md)

한 번의 활동에서 나올 수 있는 보상 조합마다 문구를 써보고, **문장을 보면서 정책을 역산**하기
위한 검토판이다. 정책을 먼저 확정하고 구현으로 넘어가지 않는다.

굵은 글씨는 `payload` 슬롯이다 (PRD §5 「슬롯=볼드」).

**갱신 이력**

| 판 | 날짜 | 내용 |
|---|---|---|
| v1 | 2026-08-27 | 24개 케이스 초안 |
| v2 | 2026-08-27 | 1차 검토 반영 — 규칙 R1~R8 확정, 남은 확인 6건 |
| v3 | 2026-08-27 | 2차 검토 반영 — R9·R10 추가, R3 확정, 남은 확인 3건 |

## 왜 만들었나

알림함에 같은 문장이 두 줄 연속으로 나온 화면이 출발점이었다.

```
활동 중에 **아이템 배지 1개**가 떨어졌어요        1시간 전
활동 중에 **아이템 배지 1개**가 떨어졌어요        1시간 전
```

버그가 아니라 설계대로 나온 결과다. `item_badge_earned`의 묶음 키는
`item_badge_earned:sync:{strava_activity_id}` — **동기화 1회가 아니라 액티비티 1건**이 단위라,
한 번 동기화에서 활동 2건이 들어오면 각각 별도 행이 된다. 그리고 문구가 활동 이름을 부르지
않아 두 행이 글자 하나까지 같아진다.

> **문서 정정 완료 (2026-08-27)** — 집필 당시 PRD §3과 DATA_MODEL §4-2가 이 단위를 계속
> "동기화 1회"라고 썼다. 이후 축이 **KST 하루**(`activity_recap:{YYYY-MM-DD}`)로 확정되면서
> 두 곳 모두 닫혔다 — PRD §3은 20260827_014에서 「소식 20종 · 활동 결산 1종」으로 재편,
> DATA_MODEL §4-2는 20260827_016에서 각주로 정정. 마지막까지 남아 있던 PRD §2-1 인스타
> 대응표의 "동기화 1회" 표기는 20260827_023에서 정정했다.

> *이 절은 **개편 전** 동작을 근거로 서술한다. 여기 나오는 레거시 6종은 20260827_014에서
> 활동 결산 1종으로 재편됐고, 016에서 렌더 경로까지 제거됐다 — 현행 동작은 §「결산 설계」
> 이후를 보라.*

근본 원인은 표면이 아니라 개념 모델에 있다. **묶음의 1차 축이 「소식 종류」이고 「활동」이
2차 축**인데, 유저의 멘탈모델은 정반대다 — "오늘 아침에 달린 그거, 뭐 받았지?" 축이 직교하니
활동 1건이 구조적으로 여러 행으로 흩어진다.

| 소식 | 한 활동에서 생기는 행 수 |
|---|---|
| `badge_earned` | 1 |
| `rare_badge_earned` | **`group_key` NULL → 희귀 배지 개수만큼** |
| `item_badge_earned` | 1 |
| `checkin_badge_earned` | 1 |
| `points_earned` | 하루 1 (여러 활동이 공유) |
| `mission_milestone` / `mission_completed` | 미션·구간마다 |

**정책 방향** — 행이 여러 개인 것 자체가 유저에게는 홍수다. 로직상 여러 개가 옳더라도
심리적으로는 홍수로 읽힌다. 그리고 **알림이 착지점을 위해 존재하는 게 아니라, 알림이 먼저이고
착지점은 거기 맞춰 고른다.**

## 확정된 규칙

검토에서 문장에 직접 손을 대 확정된 것들이다. 개별 케이스보다 이 규칙이 상위다.

| # | 규칙 | 확정 |
|---|---|---|
| **R1** | **「이번 활동으로」 접두를 쓰지 않는다.** 묶음이 활동 단위이므로 문장에서 다시 말할 필요가 없고, 알림함의 모든 행이 같은 말로 시작하면 반복적이다 | v2 |
| **R2** | **고유명사에 작은따옴표를 쓰지 않는다.** 볼드가 이미 슬롯을 표시하므로 따옴표는 중복이다 | v2 |
| **R3** | **화폐 단위는 「포인트」다.** 유저 노출 문구에서 「JAM 포인트」·「P」 표기를 쓰지 않는다 → `250 포인트` | **v3** |
| **R4** | **미션 소식은 「완료했다」만 말한다.** 보상은 착지한 미션 상세에서 확인한다. **미션이 끝났다는 사실이 보상보다 중요하다** | v2 → **v3 강화** |
| **R5** | **2종 이상이면 나열하지 않고 총량으로 말한다.** 체크인 배지·아이템 배지가 모두 배지라 총량이 성립한다 | v2 |
| **R6** | **새 결산 화면을 만들지 않는다.** 기존 화면으로 보낸다 (착지 규칙은 아래) | v2 |
| **R7** | **미션은 「완료」다.** 「달성」을 쓰지 않는다 | v2 |
| **R8** | **대표 배지는 희귀도 최상위로 고른다.** 첫 획득 순서가 아니다 | v2 |
| **R9** | **활동이 2건 이상이면 한 단계 더 올라간다.** 활동별 행을 만들지 않고 「활동 N건에서…」로 묶는다 | **v3** |
| **R10** | **착지가 다르면 행을 나눈다.** 한 행은 한 곳으로만 갈 수 있다 | **v3** |

### R6의 착지 규칙

| 결산 내용 | 착지 |
|---|---|
| 배지류만 (활동·체크인·아이템) | `/badges` |
| 포인트가 섞임 | 프로필 페이지 |
| 미션 완료 | `/missions/{id}` (2건 이상이면 `/missions`) |
| 첫 배지 | 프로필 페이지 |
| 활동이 여러 건 | 프로필 페이지 |
| 단일 개체 (A칸) | 그 개체 상세 |
| 컬렉션 완성 가능 | `/collections/{id}` 장착 모드 |

> **R6은 v1의 「결산 화면」 논의를 닫는다.** 검토하던 두 안(피드에 활동 축 추가 / 전용 결산
> 라우트 신설) 중 **어느 쪽도 만들지 않고** 기존 `/badges`·프로필로 보낸다.
> 프로필 페이지 자체의 개선은 **별도 후속 과제**로 분리했다.

#### 프로필은 착지를 어떻게 받는가 *(티켓 20260827_018에서 구현, 2026-08-27)*

C3·D1·E3·F2가 프로필로 향하는데, 도착하면 **방금 한 행으로 접어준 보상이 다시 개별
이벤트로 평면 나열**되는 문제가 있었다. 알림함에서 없앤 홍수가 착지점에서 재현된 셈이다.
`user_activity_feed`에 활동 참조가 없어 묶을 키 자체가 없었기 때문이다.

- `user_activity_feed.strava_activity_id`(마이그레이션 107)를 추가했다. **결산 payload의
  `activity_ids`와 같은 Strava 숫자 id 규약**이라 알림과 피드가 같은 키로 말한다.
- 프로필 「최근 활동」이 같은 활동의 이벤트를 **2건 이상일 때만** 한 카드로 접는다.
  임계값 2건은 F2(R9)와 같은 판단이다. 카드를 펼치면 개별 이벤트가 나온다.
- **인라인 아코디언이다.** R6의 「새 결산 화면을 만들지 않는다」가 프로필 안에서도 유효해
  새 라우트·새 시트를 만들지 않았다.
- 문구는 R1·R2·R3·R5를 그대로 따른다 → `배지 5개와 250 포인트를 획득했어요`.

**알려진 한계 2가지**

| 한계 | 내용 |
|---|---|
| 과거 이벤트는 묶이지 않는다 | 107 이전 행은 어느 활동에서 나왔는지 복원할 방법이 없어 백필하지 않았다(`event_at`이 부정확하다는 것은 093·094에서 실측). 단건으로 남는다 — graceful degradation |
| 포인트 총액이 과거 행에서 어긋날 수 있다 | 묶음 카드는 metadata의 `point_reward`를 합산한다. 드랍엔진은 포인트를 지급하면서도 이 필드를 남기지 않았고 20260827_018에서 맞췄다. **그 이전 `item_dropped` 행은 0으로 계산돼** 결산이 말한 총액보다 작게 나올 수 있다 |

> 합계는 프로필이 가져오는 피드 윈도우(`limit 150`) 안에서만 계산된다. 목록 맨 아래에서
> 활동이 잘리면 헤드라인 숫자가 실제 총량보다 작아질 수 있다.

### 사다리

| 칸 | 상황 | 문구 | 착지 |
|---|---|---|---|
| A | 1종 · 1개 | 개체를 이름으로 | 그 개체 상세 |
| B | 1종 · N개 | 대표 + 외 N | 해당 카테고리 목록 |
| C·D | 2종 이상 | 총량 | `/badges` 또는 프로필 |
| E | 강한 신호 혼재 | 강한 신호를 헤드라인으로 (필요하면 R10으로 분행) | 그 신호의 상세 |
| F2 | 활동 2건 이상 | 활동 수 + 총량 | 프로필 |

> v1에서 C를 "나열"로 뒀으나 검토에서 **총량**으로 확정됐다(R5). C와 D의 문구 규칙이 같아져
> 사다리는 **A·B(구체) / C·D(총량) / E(승격) / F2(활동 묶음)** 네 단이 됐다.

## A. 한 종류 · 한 개

가장 구체적인 칸. **개체를 이름으로 부른다.**

### A1 · 활동배지 1개

| | |
|---|---|
| 현재 | 오늘 활동으로 **배지 1개**를 획득했어요 |
| **확정** | **한강 러너** 배지를 획득했어요 |
| 착지 | `/badges/{badgeId}` |

### A2 · 활동배지 1개 + 포인트 — 2행 → 1행

| | |
|---|---|
| 현재 | 오늘 활동으로 **배지 1개**를 획득했어요<br>오늘 획득한 배지로 **50 JAM 포인트**를 획득했어요 |
| **확정** | **한강 러너** 배지와 **50 포인트**를 획득했어요 |
| 착지 | `/badges/{badgeId}` |

포인트 소식(#5)은 현재 하루 단위라 활동 단위로 내리면 활동마다 붙는다. 독립 행을 없애고 꼬리로
흡수한다.

### A3 · 희귀 배지 1개 (Legend / Mythic)

| | |
|---|---|
| 현재 | **Mythic** 배지 '**별을 삼킨 바퀴**'를 획득했어요 |
| **확정** | **Mythic** 배지 **별을 삼킨 바퀴**를 획득했어요 |
| 착지 | `/badges/{badgeId}` |

Mythic이 첫 단어로 오는 현재 구조가 유지됐다.

### A4 · 체크인 배지 1곳 · 최초 획득 — 현행 유지

| | |
|---|---|
| **확정** | **북한산**에서 체크인 배지를 획득했어요 |
| 착지 | `/badges/{badgeId}` |

### A5 · 체크인 배지 1곳 · 반복 획득 — 조사 수정

| | |
|---|---|
| 현재 | **북한산**에서 **3**번째 체크인 했어요 |
| **확정** | **북한산**에 **3**번째 체크인 했어요 |
| 착지 | `/badges/{badgeId}` |

「에서」→「에」. A4가 「에서」를 유지하는 것과 갈리지만 서술어가 달라 각각 맞다 —
"~에서 배지를 획득하다" / "~에 체크인하다".

### A6 · 아이템 배지 1개 (스크린샷의 그 케이스)

| | |
|---|---|
| 현재 | 활동 중에 **아이템 배지 1개**를 획득했어요<br>활동 중에 **아이템 배지 1개**를 획득했어요 |
| **확정** | **멈춘 초시계**를 획득했어요 |
| 착지 | `/inventory/{itemId}` — 도감이 아니라 내가 받은 개체 |

종류를 밝히지 않는 짧은 안 채택. 아이콘이 이미 상자다.

### A7 · 미션 1개 완료 (배지 + 포인트 보상)

| | |
|---|---|
| 현재 | '**한강 100km**'를 완료했어요. 배지 **1개**와 **500 JAM 포인트**를 획득했어요 |
| **확정** | **한강 100km**를 완료했어요 |
| 착지 | `/missions/{id}` |

**R4** — 미션이 끝났다는 사실이 보상보다 중요하다. 보상은 착지한 미션 상세에서 본다.

### A8 · 첫 배지 (평생 1회) — 현행 유지

| | |
|---|---|
| **확정** | **첫 배지**가 도착했어요 |
| 착지 | `/badges/{badgeId}` |

## C. 두 종류

**총량으로 말한다**(R5).

### C1 · 활동배지 4개 + 아이템 배지 2개

| | |
|---|---|
| 현재 | 오늘 활동으로 **배지 4개**를 획득했어요<br>활동 중에 **아이템 배지 2개**를 획득했어요 |
| **확정** | 획득한 **배지 6개**를 확인해보세요 |
| 착지 | `/badges` |

### C2 · 체크인 1곳 + 아이템 배지 1개

| | |
|---|---|
| **확정** | **배지 2개**를 획득했어요 |
| 착지 | `/badges` |

"총 항목 수가 2개 이하면 종류가 둘이어도 이름을 다 부르자"는 안은 채택하지 않았다.
**기준은 종류 수 하나로 유지**한다.

### C3 · 활동배지 3개 + 체크인 2곳 + 포인트

| | |
|---|---|
| **확정** | **배지 5개**와 **250 포인트**를 획득했어요 |
| 착지 | 프로필 페이지 |

포인트가 섞이면 배지 목록으로 보낼 수 없어 프로필로 올라간다.

## D. 세 종류 이상

### D1 · 활동배지 4개 + 체크인 3곳 + 아이템 2개 + 포인트

**현재 (4행)**

```
오늘 활동으로 **배지 4개**를 획득했어요                      1시간 전
**북한산 외 2곳**에서 체크인 배지를 획득했어요                1시간 전
활동 중에 **아이템 배지 2개**를 획득했어요                    1시간 전
오늘 획득한 배지로 **420 JAM 포인트**를 획득했어요            1시간 전
```

| | |
|---|---|
| **확정** | **배지 9개**와 **420 포인트**를 획득했어요 |
| 착지 | 프로필 페이지 |

총괄 안("이번 활동으로 얻은 보상을 확인해보세요")은 기각됐다. **총량을 말하는 쪽**이
정보량이 있으면서 문장도 짧다. C3와 문구 규칙이 완전히 같다.

**성립 근거** — 체크인 배지·아이템 배지가 모두 배지라서 총량이 말이 된다. 미션·포인트는
배지가 아니라 총량에 못 들어간다.

## E. 강한 신호가 섞였을 때

미션 완료·Mythic·첫 배지·컬렉션 완성은 헤드라인 자격을 갖고, 나머지가 개수로 접힌다.
**착지가 갈리면 R10에 따라 행을 나눈다.**

### E1 · Mythic 1개 + 일반 배지 5개 + 아이템 2개 — 승격

| | |
|---|---|
| **확정** | **Mythic** 배지 **별을 삼킨 바퀴** 외 **배지 7개**를 획득했어요 |
| 착지 | `/badges` |

Mythic 상세로 직행하면 나머지 7개를 못 본다. 전부 배지라 한 행에 담기고 착지도 하나다.

### E2 · 미션 완료 + 배지 5개 + 아이템 1개 — **2행 분리** (v3 변경)

```
**한강 100km**를 완료했어요                          1시간 전  → /missions/{id}
획득한 **배지 6개**를 확인해보세요                    1시간 전  → /badges
```

**v2에서 한 행("**한강 100km**를 완료하고 **배지 6개**를 획득했어요")으로 뒀으나 R4·R10과
충돌해 나눴다.**

- R4는 미션 문구에서 보상을 뺀다. 한 행에 "배지 6개"를 붙이면 그 규칙이 미션 소식에서만
  깨진다.
- R10 — 미션 완료는 `/missions/{id}`로, 배지 6개는 `/badges`로 가야 한다. 한 행은 한 곳으로만
  갈 수 있다.
- 한 행으로 두고 배지를 빼면(**한강 100km**를 완료했어요) **그 활동에서 미션과 무관하게 얻은
  배지 6개가 알림에서도 착지에서도 사라진다.** 미션 상세에는 활동 배지가 없다.

E4가 이미 같은 논리로 2행이다. **성격과 착지가 다르면 행을 나눈다** — 홍수는 같은 성격이
쪼개질 때 생긴다.

### E3 · 최초 연동 직후 첫 동기화 (첫 배지 + 배지 12개)

| | |
|---|---|
| **확정** | **첫 배지**가 도착했어요. 프로필을 확인해보세요 |
| 착지 | 프로필 페이지 |

최초 연동은 과거 활동을 한꺼번에 훑어 배지가 쏟아진다. R1로 「이번 활동으로」를 쓰지 않기로
해서 **별도 예외 문안 없이 성립한다.**

### E4 · 위 조합 + 컬렉션 완성 가능 — 2행 분리

```
**한강 100km**를 완료했어요                                  1시간 전  → /missions/{id}
**잃어버린 시간**을 다 모았어요. 컬렉션을 완성해보세요        1시간 전  → /collections/{id}
```

컬렉션 3종은 **결과가 아니라 초대**다. 결산에 넣으면 행동 유도가 죽고 장착 모드라는 고유
착지점도 잃는다.

## F. 경계

### F1 · 보상이 하나도 없는 활동 — 소식 없음

소식을 만들지 않는다. "이번 활동은 조용했어요" 류는 순수 노이즈이고, ①보상 카테고리는 dot도
켜지 않아 만들 이유가 없다.

### F2 · 활동 2건 이상 — **임계값 2건 확정** (R9)

**활동 단위 그대로면 (5행)**

```
**배지 3개**를 획득했어요                      2분 전
**새벽 개근** 배지를 획득했어요                 2분 전
**남산**에서 체크인 배지를 획득했어요           2분 전
**멈춘 초시계**를 획득했어요                    2분 전
**배지 2개**를 획득했어요                       2분 전
```

| | |
|---|---|
| **확정** | **활동 5건**에서 **배지 11개**를 획득했어요 |
| 착지 | 프로필 페이지 |

**임계값은 2건이다.** 활동이 2건만 돼도 한 단계 올라가 한 행으로 묶인다. 처음의 스크린샷이
정확히 이 케이스(활동 2건)였고, R1로 접두를 없앤 뒤 활동 간 구분 단서가 더 줄어 2건 쪽 근거가
확정적이 됐다.

> **R9는 A·B칸의 적용 범위를 좁힌다.** A·B의 구체적인 문구는 **활동이 1건일 때만** 쓰인다.
> 활동이 2건 이상이면 종류·개수와 무관하게 F2 형태로 올라간다.

### F3 · 체크인 최초 + 반복 혼재 — 현행 유지

최초 획득 쪽을 대표로 쓰는 현행 규칙(20260826_001)을 유지한다. R8(희귀도 최상위)과 갈리지만
체크인은 희귀도 축이 의미가 없다.

### F4 · 인벤토리 포화로 드랍 실패 — 별행 유지

| | |
|---|---|
| **확정** | 인벤토리가 꽉 찼어요. **50개**까지만 보관할 수 있어서 픽업이 안 될 수 있어요 |
| 착지 | `/inventory` |

⑧ 계정·시스템은 경고 스타일이고 dot을 켠다. 보상 결산과 성격이 완전히 달라 섞지 않는다.

### F5 · 같은 활동 재처리 (동기화 재시도) — 병합

`group_key`가 활동 단위라 기존 행에 병합된다. ①보상은 `bumps_badge=false`라 dot도 다시 켜지지
않는다. 현행 구조 그대로 성립.

## 남은 확인 3건

v2의 6건 중 ①②⑤⑥은 닫혔다(R9·R3·후속 과제 분리·R1). ③은 R4 강화 + E2 분행으로 처리했으나
그 처리 방식 자체의 확인이 필요하다.

### ① 「확인해보세요」를 언제 붙이나 — 라벨과 케이스가 어긋난다

주신 라벨과 확정 문구가 맞지 않는 지점이 있다.

| 케이스 | 실제 구성 | 확정 문구 | 주신 라벨 |
|---|---|---|---|
| C1 | **2종** · 6개 | 획득한 **배지 6개**를 **확인해보세요** | 여러 종류의 배지가 다수일 때 |
| C2 | **2종** · 2개 | **배지 2개**를 **획득했어요** | 단일 종류의 배지가 다수일 때 |
| C3 | 3종 + 포인트 · 5개 | **배지 5개**와 **250 포인트**를 **획득했어요** | — |
| D1 | 4종 + 포인트 · 9개 | **배지 9개**와 **420 포인트**를 **획득했어요** | — |

C2는 체크인 1곳 + 아이템 1개라 **실제로는 2종**이다. 라벨대로 "여러 종류면 확인해보세요"를
적용하면 C2도 CTA가 되어야 하는데 확정 문구는 서술형이다. C3·D1도 여러 종류인데 서술형이다.

가장 정합적인 재구성은 **포인트 유무가 가른다**는 것이다.

| 조건 | 문구 |
|---|---|
| 배지만 있고 개수가 많다 | 획득한 **배지 N개**를 **확인해보세요** — 숫자만으로는 뭘 받았는지 몰라 보러 가게 한다 |
| 포인트가 섞였다 | **배지 N개**와 **M 포인트**를 **획득했어요** — 정보가 둘이라 서술로 충분 |
| 개수가 적다 (2개) | **배지 2개**를 **획득했어요** |

이러면 C1·C2·C3·D1이 전부 설명되지만 **"개수가 많다"의 경계가 미정**이다. C2(2개)와 C1(6개)
사이 어딘가다. 3개부터로 두면 네 케이스가 모두 맞는다.

### ② R3의 적용 범위 — 「JAM 포인트」를 어디까지 지우나

실측한 사용 범위다.

| 위치 | 건수 | 성격 |
|---|---|---|
| `src/lib/i18n/ko.ts` | 4 | **유저 노출 문구** — `slotPoints`·`rewardPointsLine`·`consolationPoints` 외 |
| `src/lib/notifications/__tests__/` | 9 | 테스트 기대값 |
| `UX_WRITING_GUIDELINE.md` §3 | 1 | 표기 규칙 원본 |
| `PRD/01_PRD.md`·`02_DATA_MODEL.md` | 3 | **시스템·도메인 이름** ("JAM 포인트 시스템", "9. 포인트 (JAM 포인트)") |
| `서비스플랜 v4.3` | 3 | 시스템 이름 |
| `서비스플랜 v3.0~v4.2` 등 아카이브 | 60+ | 과거 판본 — 손대지 않는다 |

**「완전 삭제」의 범위를 나눠야 한다.** 유저 노출 문구(ko.ts 4건 + 가이드 §3)를 「포인트」로
바꾸는 것은 명확하다. 다만 **시스템·도메인 이름으로서의 「JAM 포인트 시스템」**은 성격이
다르다 — 가이드 §1-3이 금지한 것은 유저 노출 용어이지 내부 도메인명이 아니다. 도메인명까지
바꾸면 PRD·데이터모델·서비스플랜의 시스템 명칭이 연쇄로 흔들린다.

> **곁가지 발견** — `ko.ts:473`의 `rewardPointsLine: 'JAM 포인트 {points}P'`는
> 가이드 §3이 **Bad로 명시한 `1200P` 표기**를 그대로 쓰고 있다. R3와 무관하게 기존 위반이라
> 이번에 함께 정리 대상이다.

### ③ E2의 2행 분리가 맞나

R4("미션은 완료만 말한다")를 그대로 적용하면 E2도 "**한강 100km**를 완료했어요" 한 줄이
된다. 그런데 그러면 **그 활동에서 미션과 무관하게 얻은 배지 6개가 알림에서도, 착지한 미션
상세에서도 보이지 않는다.**

그래서 v3는 R10을 세워 2행으로 나눴다. E4(컬렉션)와 같은 처리다.

| 안 | 결과 | 대가 |
|---|---|---|
| **2행 분리** (v3 채택) | 미션 완료 → `/missions/{id}`<br>배지 6개 → `/badges` | 한 활동이 2행. E4와는 일관 |
| 1행 · 미션만 | **한강 100km**를 완료했어요 | 배지 6개가 유저 인지에서 증발 |
| 1행 · 배지 포함 (v2) | **한강 100km**를 완료하고 **배지 6개**를 획득했어요 | R4가 미션 소식에서만 깨지고, 착지가 둘인데 하나만 고를 수 있다 |
