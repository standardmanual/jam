# JAM! UX 라이팅 가이드라인

> 생성일: 2026-07-31
> 최종 수정: 2026-09-15
> 적용 범위: 화면 텍스트, 알림, 에러 메시지, 버튼 문구, 커밋 메시지 외 사용자 노출 문구 전체

---

## 핵심 철학: "운동 마치고 돌아온 사람이, 앱을 켜자마자 바로 이해할 수 있는가?"

JAM!은 **트래커가 아니라 보상 수확 경험**이다. 사용자는 이미 Strava에서 운동을 기록했고,
JAM!에서는 "오늘 뭘 획득했는지" 확인하러 온다. 은행/시스템의 사무적 언어가 아니라,
**함께 운동하는 친구가 오늘의 성과를 축하해주는 어조**를 기본값으로 삼는다.

또한 JAM!은 배지·아이템·드랍·믹스라는 **수집·게임 메커니즘**을 가진 서비스다.
**신남/설렘의 톤**을 허용하되, 사기·거래·소각처럼
되돌릴 수 없는 행동 앞에서는 토스와 동일하게 냉정하고 명확해야 한다.

---

## 1. 용어 및 시점 원칙

### 1.1 공급자 언어를 JAM! 사용자 언어로 번역

시스템/운영 관점 용어를 사용자가 실제로 겪는 행동으로 바꾼다.

| 공급자 언어 (지양)    | JAM! 사용자 언어 (지향) |
| -------------- | ---------------- |
| 배지 발급 완료       | 배지 획득!            |
| 조건 충족 확인       | 조건을 다 채웠어요       |
| Strava 동기화 실행  | 오늘 활동 불러오는 중     |
| 아이템 드랍 이벤트 생성됨 | 근처에 아이템이 떨어졌어요   |
| POI 반경 매칭 성공   | 여기 체크인됐어요        |
| 컬렉션 레시피 충족      | 컬렉션을 다 모았어요       |
| 인벤토리 슬롯 초과    | 인벤토리가 꽉 찼어요       |
| 아이템 만료 처리      | 아이템이 포인트로 바뀌었어요  |
| 거래 체결 완료       | 교환을 완료했어요        |

### 1.2 사용자 중심의 호칭과 주어 설정

- '당사', '고객님', '유저님' 지양 → **'JAM!'**, **'OO님'** (닉네임/이름) 사용
  - 당사가 제공하는 배지입니다 ➔ JAM!이 준비한 배지예요
  - 고객님이 획득한 아이템 ➔ 시현님이 획득한 아이템
  - **'OO'는 닉네임 자리표시자 전용이다.** 검색어 등 그 외 사용자 입력값을 문구 안에
    끼워 넣을 때는 `{검색어}`처럼 중괄호로 표기해 닉네임 자리표시자와 구분한다(§4.3 참고).
- '시스템' 시점 지양 → **'사용자' 시점** 적용
  - 배지 발급 처리가 완료되었습니다 ➔ 배지를 획득했어요
  - POI 방문 인증이 확인되었습니다 ➔ 체크인됐어요
- **드랍/아이템 계열은 '트라이브 속 사건'처럼 서술**한다 (JAM!만의 톤)
  - 드랍 아이템이 생성되었습니다 ➔ 근처에 아이템이 떨어졌어요
  - 조합에 실패하였습니다 ➔ 재료가 뒤섞이더니 흔적도 없이 사라졌어요

### 1.3 용어 일관성 (Consistency)

동일 개념을 화면마다 다른 단어로 섞어 쓰지 않는다. JAM!의 고정 용어는 다음과 같다.

| 개념 | 고정 용어 | 사용 기준 |
|---|---|---|
| 배지나 아이템을 얻는 행위 | **획득 (GET)** | 배지·아이템을 획득하는 모든 맥락에 적용. X: 겟, 수령, 발급받음, 취득, 언락 |
| 아이템을 조합해 새로운 결과물을 얻는 행위 | **믹스 (MIX)** | 여러 아이템을 소모하여 확률에 따라 새로운 결과물을 얻는 고유 기능. X: 조합, 합성, 믹스 |
| 아이템을 특정 위치에 두는 것 | **드랍 (DROP)** | 유저가 아이템을 특정 위치에 두는 행위. X: 배치, 생성, 놓기 |
| 아이템을 특정 위치에서 가져오는 것 | **픽업 (PICKUP)** | 유저가 특정 위치의 아이템을 가져오는 행위. X: 수집, 채집, 회수 |
| 드랍·픽업·체크인이 일어나는 실제 위치 | **지점 (SPOT)** | 어드민이 등록한 좌표와 반경을 가진 실제 위치. 화면에 내부 약어 POI를 노출하지 않는다. X: POI, 장소, 스팟, 위치, 거점<br>**예외** — 개수를 세는 일상 문장에서는 「곳」을 쓴다(「드랍한 3지점에」가 어색하다). 라벨·제목·명사구는 「지점」 고정. 티켓 20260827_014 |
| 지점에 실제로 다녀간 것이 기록되는 것 | **체크인 (CHECK-IN)** | 활동의 GPS 경로가 지점 반경을 지나면 성립한다. X: 방문, 체크, 인증, 매칭, 확인 |
| 체크인으로 획득하는 배지 | **체크인 배지 (CHECK-IN BADGE)** | 지점에 체크인하면 획득되는 배지. 배지도감 탭명·컬렉션 섹션명·알림 문구에 모두 이 표기를 쓴다. X: 장소 배지, POI 배지, 장소, 방문 배지 |
| 같은 체크인 배지를 두 번째 이상 반복 획득한 것을 알리는 것 | **N번째 체크인 했어요** | 체크인 배지 재획득 시 피드·알림에 쓰는 고정 패턴. 첫 획득은 '체크인 했어요', 두 번째부터 이 패턴을 쓴다. X: N번째 방문했어요, 재획득, 재체크인, 반복 획득 |
| 유저가 보유한 아이템 보관 공간 | **인벤토리 (INVENTORY)** | 유저가 보유한 아이템을 확인하고 관리하는 공간. X: 인벤, 보관함, 창고 |
| 유저가 온보딩에서 선택하는 소속 진영 | **트라이브 (TRIBE)** | 10개 중 하나를 온보딩에서 한 번 고르며 이후에는 바꿀 수 없다. 배지·컬렉션이 소속되는 컨텐츠 분류 단위이기도 하다. DB 테이블·컬럼도 `tribes`/`tribe_id`로 통일되어 있다(티켓 20260910_1129 코드·화면 통일 → 20260910_1226 DB 스키마 통일). X: 세계관, 팩션, faction, 진영 |
| 특정 배지·아이템 세트를 모으는 목표 및 진행 상태 | **컬렉션 (COLLECTION)** | 트라이브별 아이템배지 세트 단위의 수집 목표와 진행 상태를 지칭. X: 아이템북, 컬렉션북, 도감 |
| 보유한 아이템배지 개체를 컬렉션의 빈 자리에 채워 넣는 행위 | **장착 (EQUIP)** | 컬렉션 화면에서 아이템배지 개체를 골라 채우는 행위. 데이터 모델의 내부 명칭 「슬롯」은 사용자 노출 화면에 쓰지 않는다 — 「슬롯에 실패했어요」가 아니라 「장착에 실패했어요」로 쓴다. 획득(배지를 얻는 것)과 장착(얻은 배지를 컬렉션에 채우는 것)은 서로 다른 단계이므로 한 문장에서 섞어 쓰지 않는다. X: 끼우기, 넣기, 세팅, 장비 (2026-09-14 신설, 티켓 20260907_2138) |
| 같은 배지를 여러 개 보유했을 때 개체를 구분하는 식별자 | **일련번호 (SERIAL NUMBER)** | 장착·드랍·픽업 대상 개체를 고르는 선택 시트 등에서 개체를 구분할 때 쓴다. X: 시리얼, 시리얼넘버, S/N (2026-09-14 신설, 티켓 20260907_2138) |
| 서비스 내 보유 화폐 | **포인트 (POINT)** | 배지·아이템 획득 등에 사용되는 서비스 내 화폐 단위. **유저 노출 문구에 「JAM」을 붙이지 않는다**(「JAM 포인트 시스템」은 내부 도메인명으로만 유지). X: 잼포인트, JAM 포인트, 캐시, P |
| Strava 계정과 서비스를 연결하는 것 | **Strava 동기화 (Strava Sync)** | Strava 계정을 서비스와 연결하는 기능. X: Strava 연동, 스트라바 계정 연결, 트래커 연동, 트래커 연결 |
| 하루(KST 기준) 동안 Strava 동기화가 성공적으로 일어난 횟수 | **하루 동기화 횟수** | JAM! 카테고리(서비스 사용량) 배지 조건·설명에 쓰는 지표명. X: 일일 싱크 횟수, 동기화 카운트, 싱크 횟수 (2026-09-10 신설, 티켓 20260910_1557) |
| 다른 유저가 나를 팔로우한 관계에서, 나를 팔로우한 사람(또는 그 수) | **팔로워 (FOLLOWER)** | 유저 프로필·JAM! 카테고리 배지 조건에서 쓰는 소셜 지표. X: 구독자, 팬 |
| 내가 다른 유저를 팔로우한 관계에서, 내가 팔로우한 사람(또는 그 수) | **팔로잉 (FOLLOWING)** | 유저 프로필·JAM! 카테고리 배지 조건에서 쓰는 소셜 지표. X: 구독, 팔로우 목록 |
| 배지와 연계된 실물 자수 제품 | **패치 (PATCH)** | 배지 달성 시 구매 가능한 실물 자수 제품. X: 굿즈, 상품 |
| 배지 희귀도 등급명 | **Common / Rare / Epic / Mystic** | 배지의 4단계 희귀도 등급(낮은 순). 영문 표기 고정, 첫 글자만 대문자. DB enum은 소문자(`common`/`rare`/`epic`/`mystic`). X: Legend, Legendary, Mythic, 레전더리, 레전드, 신화, 미스틱, 에픽 — 등급을 한글로 쓰지 않는다. 상세는 아래 «등급명 표기» 참고 |
| 미션에 참여하는 행위 | **참가 (Join)** | 미션에 참여 신청하는 행위. X: 신청, 등록, 참여 |
| 진행도·지표 값으로 유저 순서를 매겨 보여주는 것 | **랭킹 (RANKING)** | 홈 피드 랭킹 카드와 미션 상세 순위 리스트에서 유저 순서를 매겨 보여주는 화면·문구에 적용. X: 순위, 랭크, 서열 (2026-09-11 신설, 티켓 20260911_1440) |
| 어드민이 유저 포인트를 추가하는 것 | **지급** | 어드민 전용 포인트 추가 행위. 유저 노출 화면에는 사용 금지. X: 추가, 충전 |
| 어드민이 유저 포인트를 차감하는 것 | **회수** | 어드민 전용 포인트 차감 행위. 유저 노출 화면에는 사용 금지. X: 차감, 환수 |
| 선행 조건을 채우지 못해 참가·진입이 막힌 상태 | **잠김 (LOCKED)** | 상태 라벨은 '잠김', 해제 안내는 '열려요'로 고정 (예: "첫 숨결 Rare 배지를 획득하면 열려요"). X: 잠금, 미해금, 비활성, 언락, 해금 |
| 배지 트리에서 아직 그 눈금까지 진행되지 않은 상태(스크린리더 전용 — 화면 표기는 '—'이거나 조건값) | **아직** | 보조기술 전용 라벨. '미도달'처럼 딱딱한 한자어 대신 일상어를 쓴다. X: 미도달, 미달성, 비도달 (2026-09-06 신설). **이 행은 스크린리더 라벨로서의 고정 용어 지정이며, '아직'을 일상적 부사(예: "아직 획득한 배지가 없어요")로 본문에 쓰는 것까지 막지 않는다** — 고정 용어는 다른 말로 바꿔 쓰지 말라는 규정이지, 일상어 사용 자체를 제한하는 규정이 아니다. |
| 잠긴 눈금을 탭했을 때 열리는 화면(버튼·시트 제목 공통 개념) | **받는 방법** | 버튼은 '받는 방법 보기'(동사형, §5.1), 시트 제목은 '받는 방법'(명사형)으로 짝을 맞춘다 — 누르는 곳과 열리는 화면이 같은 말을 써야 한 흐름으로 읽힌다. '잠김' 행의 금지어(잠금·해제)가 이 버튼·제목에도 그대로 적용된다는 뜻이라 별도 행으로 명시한다. X: 잠금 해제 조건 보기, 잠금 해제 조건, 해제 조건 확인 (2026-09-06 신설) |
| 눈금이 하나뿐인 계열들의 묶음 | **한 번에 끝나는 배지** | 단계를 밟지 않고 한 조건만 채우면 받는 계열. 배지 트리에서 이 계열들을 카드 한 장에 그리드로 묶을 때 그 카드의 제목이다. X: 단일 배지, 원샷 배지, 단계 없는 배지, 1단계 배지 (2026-09-06 신설, 티켓 20260906_2140) |
| 수치 조건은 채웠지만 미션 등 별도 조건이 남아 아직 발급되지 않은 상태 | **조건을 다 채웠어요** | 배지 트리 등에서 '잠김'과 구분되는 중간 상태 라벨. '획득'과 혼동 금지 — 배지가 아직 발급되지 않았다. 시트 배너와 같은 문구를 상태 라벨에도 그대로 쓴다(같은 개념은 같은 말로, 화면이 달라져도). X: 충족, 조건 충족, 완료, 조건 달성, 준비 완료 (2026-09-06 갱신 — '충족'은 남은 일을 말하지 않는 상태 이름일 뿐이라 전면 금지어로 올린다) |
| 1분당 심장 박동 수 | **심박수** | 활동 중 측정된 심장 박동 수. 지표 라벨은 「평균 심박수」(bpm). 심박계가 있는 활동에서만 값이 들어오며, 없으면 그 조건의 배지는 대상이 아니다. X: 심박, 하트레이트, HR |
| 배지 플레이버 텍스트에서 운동·이동을 문학적으로 표현하는 말 | **발걸음 / 궤적 — 본인 활동에만 사용** | 유저 본인이 직접 수행한 운동·이동(액티비티배지·체크인배지)을 가리킬 때만 쓴다. 팔로워 수·팔로잉 수처럼 타인과의 관계나 소셜 지표를 묘사할 때는 쓰지 않는다 — "만 명이 이 사람의 발걸음을 지켜본다" 같은 표현은 팔로워(타인)의 행위를 본인 활동 어휘로 뒤섞어 혼동을 준다. (2026-09-10 신설, 티켓 20260910_1959 한국어 리뷰 권고) |
| 자전거 페달을 밟아 낸 일률 | **파워** | 지표 라벨은 「평균 파워」(W). X: 출력, 와트, 파워출력 |
| 분당 회전수(러닝은 걸음, 자전거는 페달) | **케이던스** | 지표 라벨은 「평균 케이던스」. **단위를 붙이지 않는다** — 종목마다 다르다(러닝 spm · 자전거 rpm). X: 회전수, 스텝수, 피치 |
| 활동 후반이 전반보다 빠른 것 | **후반 구간 페이스** | 하나의 활동을 반으로 나눠 뒤쪽이 더 빠른지 보는 지표. X: 네거티브 스플릿, 후반 스퍼트, 이븐페이스 |
| 활동이 없는 기간 | **휴식** | 활동과 활동 사이의 공백. 배지 진행 표기는 **상태만 적는다** — 「휴식 2/5일」. **권유형 문구를 쓰지 않는다**: 운동을 권하는 서비스가 휴식을 재촉하는 모양이 된다. X: 3일 더 쉬면 획득, 휴식하세요, 쉬어 보세요, 회복, 공백, 휴식기 |
| 무한레벨형 배지의 단계 | **레벨** | 등급(Common~Mystic)이 없는 계열에서 계속 올라가는 단계. 화면 표기는 「Lv.N」. X: 단계, 티어, 스테이지, 렙 |
| 같은 이름·목표를 공유하는 배지 묶음 | **계열** | 등급형 4단계 묶음, 또는 무한레벨형의 레벨 묶음. 화면에 내부 키(`family_key`)를 노출하지 않는다. X: 시리즈, 그룹, 패밀리, 트랙 |
| 배지 조건에서 측정되는 지표 하나 | **축** | 「거리」·「고도」처럼 진행률을 그릴 수 있는 지표 단위. 배지 하나에 축이 여럿일 수 있다. X: 지표, 항목, 조건값, 메트릭 |
| 활동이 없는 기간을 조건으로 하는 배지의 상태 | **휴식** | 배지 트리 캡션은 「휴식 2/5일」처럼 **상태만 표기**한다. 「N일 더 쉬면 획득」 같은 **권유형 금지** — 운동을 권하는 서비스가 휴식을 재촉하는 모양이 된다(티켓 20260905_0031). X: 쉬기, 휴식일 채우기, 회복 |
| 등급 없이 숫자로만 올라가는 배지의 단계 | **Lv.N** | 「Lv.3」 형태로 고정한다(등급명이 영문 고정인 것과 같은 규칙). 등급형의 Common/Rare/Epic/Mystic과 **배타**다 — 한 배지가 둘을 동시에 갖지 않는다. X: 레벨 3, 3레벨, LV3, Lv 3 |
| 같은 이름으로 묶인 배지 묶음 | **계열** | 등급형은 Common~Mystic 4장, 무한레벨형은 Lv.1~∞가 한 계열이다. X: 시리즈, 세트, 그룹, 패밀리 |
| 배지 조건이 재는 지표의 갈래 | **축** | 「거리 축」·「연속 축」처럼 쓴다. 교차 게이트가 「축 내 교차」·「축 간 교차」로 이 말을 쓴다. X: 항목, 카테고리, 지표군 |

#### 저작 도구 용어 (어드민 전용)

어드민 저작 화면에서만 쓰는 용어다. 유저 노출 화면에는 나타나지 않지만, 같은 개념이 화면마다
다른 단어로 갈라지지 않도록 여기에 고정한다.

| 개념 | 고정 용어 | 사용 기준 |
|---|---|---|
| 형태의 경계를 흐리게 만드는 정도 | **블러** | 배경 애니메이션 등 저작 파라미터 라벨. X: 흐림, 블러 처리, 번짐 |
| 절차적 생성의 초깃값 | **시드** | 같은 값이면 항상 같은 결과가 나오는 생성 초깃값. X: seed, 씨드, 난수값 |
| 값을 임의로 다시 뽑는 액션 | **무작위** | 시드 재추첨 등 저작 중 값을 임의로 다시 뽑는 버튼·토글 문구. X: 랜덤, 셔플, 다시 뽑기 |
| 이미 저장된 데이터를 다시 훑어 빠진 값을 채우는 작업 | **백필** | 운영 도구의 소급 데이터 보정 작업명. X: 소급 반영, 재수집, 채우기, 마이그레이션 |
| 쓰기 없이 결과만 확인하는 실행 | **미리보기** | 실행 결과 건수만 보고 아직 반영하지 않는 단계. X: 시뮬레이션, 드라이런, dry-run, 테스트 실행 |
| 미리보기 결과를 실제로 반영하는 실행 | **적용** | 되돌릴 수 없는 쓰기 단계. 버튼 문구와 결과 라벨에 같은 말을 쓴다. X: 반영, 실행, 저장, 커밋 |

이 표에 없는 새 용어가 필요해지면, 이 문서의 표를 갱신한 뒤 사용한다 (자체 판단으로 임의 표기 확산 금지).

#### "충족" 자체를 사용자 화면에 쓰지 않는다 (2026-09-06)

위 표의 개별 X-리스트에도 나오지만, 개별 용어를 넘어선 **일반 원칙**으로 못박는다.
"충족"은 시스템이 조건을 판정했다는 사실만 말하고 **사용자가 다음에 뭘 하면 되는지는
말하지 않는다.** 새 문구를 쓸 때 아래처럼 바꾼다 (예시, 고정 용어 아님 — 문맥에 맞게 조정):

| 지양 | 지향 |
|---|---|
| 10회 충족 | 10회 |
| 조건 충족 | 조건을 다 채웠어요 |
| 한 번의 활동에서 모두 충족 | 한 번의 활동에서 동시에 채워야 해요 (`DualAxisGauge`의 "두 조건을 동시에 채워야 해요"와 같은 어순) |
| 미충족 / N개 미충족 | 아직 / 앞으로 N개 더 |

어드민 저작 화면(`src/app/admin/`)과 내부 로그·`reason` 필드는 이 원칙의 적용 대상이 아니다
— 사용자가 보지 않는다.

### 등급명 표기 — 매핑 이력과 주의사항

> 이 절은 **옛 등급명을 의도적으로 적어 둔 유일한 곳**이다. 다른 문서·코드·컨텐츠에서 옛
> 이름이 검색되면 그건 잔재이므로 고쳐야 한다. 잔재 검사 시 이 절만 예외로 둔다.
> (티켓 20260831_1115 산출물. 이름이 또 바뀌면 아래 표에 열을 하나 더한다)

**현행 4단계는 `common` · `rare` · `epic` · `mystic`이다.** 서열은 이 순서이고, 색상은 서열에
고정돼 있다(3단계 금색 `#f5a300`, 4단계 핑크 `#ff2d87`). 이름이 바뀌어도 색은 옮기지 않는다 —
유저가 학습한 색 언어이기 때문이다(`RarityBadge.prompt.md`).

#### 이름 변경 이력 (서열은 한 번도 바뀌지 않았다)

| 서열 | 현행 (2026-08-31~) | 2026-08-13 ~ 08-30 | ~2026-08-12 |
|---|---|---|---|
| 1 | `common` / Common | 동일 | 동일 |
| 2 | `rare` / Rare | 동일 | 동일 |
| 3 | **`epic` / Epic** | `legend` / Legend | `legendary` / Legendary |
| 4 | **`mystic` / Mystic** | `mythic` / Mythic | `mythic` / Mythic |

- **과거 티켓·문서의 `Legend`·`Legendary`는 현재의 `Epic`이다.** 이름만 보고 최상위 등급으로
  오독하지 않는다 — 4단계가 아니라 3단계다.
- **과거의 `Mythic`은 현재의 `Mystic`이다.** 서열은 그대로 4단계다.

#### Mystic / Mythic 철자 혼동 주의

**한 글자 차이다.** `mystic`(현행, 신비로운)과 `mythic`(옛 이름, 신화의)은 세 번째 글자만
다르고 눈으로 구분하기 어렵다. 현행은 **`mystic`**이다.

- 치환 작업 뒤에는 반드시 `rg -i mythic`으로 잔재가 0건인지 확인한다(이 절 제외).
- **`myst`로 뭉뚱그려 검색·치환하지 않는다.** 드랍 엔진에는 등급과 무관한 `mystery` 어휘가
  따로 있다(`MYSTERY_TRIBE_ID`·`mystery_spice_rate` 등 "미스터리 헌터" 트라이브 전용 로직).
  등급 작업 중 이 어휘를 건드리면 안 된다.
- 한글 등급 표기(「레전더리」·「레전드」·「신화」)는 전부 폐기했다. 등급은 영문으로만 쓴다.
  「신화」는 트라이브 카피에서 등급과 무관한 뜻으로 쓰일 수 있으니, 치환할 때 등급을 가리키는
  맥락인지 건별로 확인한다(일괄 치환 금지).
- **예외** — 삭제된 `wandering_mythic_state` 테이블처럼 **더 이상 존재하지 않는 코드 식별자**는
  역사적 사실이므로 원문 그대로 둔다(티켓 20260824_017로 기능째 제거됨). 등급 표기가 아니다.

## 2. 문장 구조 및 톤앤매너

### 2.1 대화하듯 자연스러운 '해요체'

- Good: 배지를 획득했어요.
- Bad: 배지가 발급되었습니다.

**예외 — 배지 이름·설명문(플레이버 텍스트)은 `-습니다`체를 쓴다.** 위 원칙은 배지 획득을
알리는 시스템 문구(토스트·피드·상태 라벨)에 적용되는 것이지, 배지 도감에 새겨지는 배지
자체의 이름·설명에는 적용되지 않는다. 배지 설명문은 관행적으로 `-습니다`체로 써왔다
("만 명이 이 사람의 발걸음을 눈여겨보고 있습니다" 등) — 화자가 유저 본인이 아니라 배지가
새겨진 문구를 읽는 제3의 시점이라 해요체보다 `-습니다`체가 자연스럽다. X: 배지 설명문에
해요체를 적용해 어색해지는 경우 (2026-09-10 신설, 티켓 20260910_1959 한국어 리뷰 확인)

### 2.2 간결함과 명확성

- Good: 지금 드랍할까요?
- Bad: 아이템을 드랍하려면 아래 버튼을 눌러 진행해 주시기 바랍니다.
- 원칙: 한 문장에는 하나의 의미와 행동만 담는다.

### 2.3 상황별 톤앤매너 완급 조절

JAM!은 게임적 재미(드랍·픽업·믹스)와 실물 자산(패치 구매 자격·JAM 포인트·거래)이
공존하는 서비스이므로, 상황에 따라 톤을 명확히 구분한다.

| 상황 | 톤 | 예시 |
|---|---|---|
| 배지/아이템 획득, 컬렉션 완성   | **신남 · 축하 (Warm & Cheerful)** | 배지 획득! 오늘도 한 걸음 더 갔어요 🎉 |
| 동기화·로딩 등 일반 진행 | **담담 · 안내 (Conversational)** | 오늘 활동을 불러오는 중이에요. 잠시만요. |
| 체크인·드랍·픽업·조합 이벤트 | **설렘 · 몰입 (Playful & Immersive)** | 근처에 Mystic 배지가 떨어졌어요! |
| 아이템 만료, 인벤토리 초과, 소각 확정 | **단호 · 명확 (Professional & Direct)** | 이 아이템은 30일 후 사라져요. 포인트로 미리 바꿔둘까요? |
| 거래(P2P)·환전·되돌릴 수 없는 확정 | **단호 · 명확 (Professional & Direct)** | 교환은 취소할 수 없어요. 이대로 진행할까요? |
| 계정·Strava 동기화 오류, 부정 어뷰징 감지 | **전문 · 직접 (Professional & Direct)** | Strava 동기화가 끊겼어요. 다시 동기화해야 배지를 획득할 수 있어요. |
| 목록이 비어 있음 (빈 상태, empty state) | **담담 · 안내 (Conversational)** | 아직 획득한 배지가 없어요 |
| 문의(VOC) 접수·처리 안내 | **차분 · 공감 (Calm & Empathetic)** | 문의를 받았어요. 확인하고 답변드릴게요. |

**원칙**: 되돌릴 수 없는 행동(소각·거래 확정·환전·동기화 해제)일수록 신남 톤을 배제하고
현상 → 결과 → 확인 순서로 단호하게 전달한다. 게임적 재미와 되돌릴 수 없는 결정을 같은 톤으로 섞지 않는다.

**"차분·공감"은 이번에 새로 추가한 7번째 톤이다** — "담담·안내"를 그대로 쓰지 않은 이유는,
담담·안내는 로딩·동기화처럼 사용자가 불편을 겪지 않은 일반 진행 상황에 쓰는 톤이라 이미
불편을 겪고 문의를 접수한 사용자에게 쓰면 무심하게 읽히기 때문이다. 새 톤을 또 늘리기 전에
먼저 이 표의 기존 6개 톤으로 표현이 되는지부터 확인한다.

### 2.4 톤 경계가 흐려지기 쉬운 지점 (2026-09-15 신설, 티켓 20260915_2236)

위 표의 6개 톤은 서로 인접해 헷갈리기 쉽다. 실제로 반복적인 개선 작업 중 문구가 뒤섞인
지점들을 아래에 못박는다.

- **로딩이 실패로 바뀌는 순간**: "담담·안내" 톤으로 시작한 로딩 문구("불러오는 중이에요")를
  그대로 두고 뒤에 원인만 덧붙이지 않는다. 실패가 확정되면 즉시 "전문·직접" 톤의
  [현상→원인→해결책] 3단계 구조(§4.1)로 문구 자체를 새로 쓴다.
- **빈 상태 vs 에러**: "없어요"라는 말이 같아도 목록이 원래 비어 있는 것과 조회 자체가
  실패한 것은 다른 상황이다. 전자는 이 절의 빈 상태 톤(§4.3), 후자는 3단계 구조(§4.1)를
  따른다 — 빈 상태에 원인·해결책을 억지로 붙이지 않는다.
- **소셜 액션(팔로우 등) vs 되돌릴 수 없는 확정**: 팔로우/언팔로우처럼 즉시 되돌릴 수 있는
  가벼운 행동에 "신남·축하" 톤을 남용하지 않는다. 담담·안내 수준에서 완료 사실만 짧게
  알린다. "단호·명확" 톤은 소각·거래·환전처럼 정말 되돌릴 수 없는 행동에만 쓴다.
- **문의(VOC) 안내 vs 되돌릴 수 없는 확정 경고**: 둘 다 "단호"해 보이지만 다르다. "단호·
  명확"은 사용자의 다음 결정을 재촉·확정시키는 상황에, "차분·공감"은 사용자가 이미 불편을
  겪어 문의를 접수한 상황에 쓴다. 문제를 해결하겠다는 의지는 담되, 사무적으로 딱딱하게
  자르지 않는다.

### 2.5 SEO 메타데이터(title/description)는 예외적으로 격식체를 허용한다

`app/layout.tsx` 등의 `title`·`description`은 대화가 아니라 검색 결과·SNS 공유 미리보기에
노출되는 서비스 소개문이다. `-습니다`체 또는 명사형 종결을 쓰고, 이모지·구어체 감탄사(예:
"우와")는 쓰지 않는다. 용어 일관성(§1.3)과 금지어 규정은 이 예외와 무관하게 그대로 적용한다.

## 4. 에러 대응 가이드라인

### 4.0 서버-클라이언트 단일 진실 소스 (ADR 0001, 2026-09-15 신설)

에러 메시지는 **서버 API route가 `d.*` 딕셔너리를 직접 참조해 최종 문구까지 완성**하고,
클라이언트는 그 문구를 가공 없이 그대로 신뢰해 노출한다. 같은 에러 문구를 서버와
클라이언트 양쪽에 중복 정의하지 않는다 — 서버만 아는 상태 의존적 사유(예: "이미 신청한
미션입니다")를 클라이언트가 재현하려고 조건 분기를 따로 만들면 두 군데서 문구가 갈라진다.

- **서버**: `src/lib/i18n`은 `'use client'` 없는 순수 모듈이라 API route(`app/api/**`)에서도
  그대로 import한다. 에러 응답 바디에 담는 `message`는 이 가이드의 톤·용어 규칙을 그대로
  따르는 완성된 문장이어야 한다 — "internal error" 같은 로그성 문자열을 그대로 내려보내지
  않는다.
- **클라이언트**: 토스트·인라인 에러에 서버가 보낸 `message`를 그대로 표시한다. 자체
  딕셔너리 문구로 덮어쓰거나(과거 `DropsClient.tsx`·`CombineClient.tsx` 사례), 서버의
  하드코딩 원문을 검증 없이 그대로 노출하는(과거 `MissionDetailClient.tsx` 사례) 두 패턴
  모두 금지 대상이다 — 전자는 서버가 아는 구체적 사유를 사용자에게 숨기고, 후자는 서버
  쪽 문구가 이 가이드를 거치지 않았을 위험을 그대로 방치한다.
- 어드민 전용 라우트(`src/app/api/admin/**`)는 이 규칙의 적용 대상이 아니다 — §1.3 저작
  도구 용어와 같은 경계.
- 상세 배경·검토한 대안은 `docs/adr/0001-server-error-message-single-source.md` 참고.

### 4.1 [현상 → 원인 → 해결책] 3단계 구조

시스템 관점 오류 통보를 피하고 **[현상 → 원인 → 해결책]** 3단계 구조를 지킨다.
JAM! 특화 시나리오 예시:

| 구형 방식 (Bad) | JAM! 3단계 적용 (Good) |
|---|---|
| Strava 동기화 실패 (Error 401) | Strava 동기화가 끊겼어요. (현상) 비밀번호를 바꾸셨거나 동기화 권한이 해제됐을 수 있어요. (원인) [Strava 다시 동기화하기] (해결책/CTA) |
| 체크인 실패 | 여기 체크인이 안 됐어요. (현상) GPS 신호가 약했거나 반경 50m 밖이었을 수 있어요. (원인) [활동 다시 확인하기] (해결책/CTA) |
| 인벤토리 용량 초과로 드랍 불가 | 인벤토리가 꽉 찼어요. (현상) 50개까지만 보관할 수 있어요. (원인) [정리하러 가기] (해결책/CTA) |
| 아이템 만료 처리됨 (단순 통보) | 아이템이 사라졌어요. (현상) 30일이 지나 자동으로 300 포인트로 바뀌었어요. (원인) [내 포인트 보기] (해결책/CTA) |
| 어뷰징 감지 (차단 사유 비공개) | 이 활동은 배지로 인정하지 않았어요. (현상) 이동 속도가 너무 빨라 운동으로 보기 어려웠어요. (원인) [기준 자세히 보기] (해결책/CTA) |

### 4.2 인라인 폼 검증 에러는 [현상+해결책] 한 문장으로 축약 (2026-09-15 신설)

닉네임·문의 내용처럼 입력 필드 바로 아래 붙는 검증 에러는 토스트·다이얼로그가 아니라
**필드 옆 한 문장**이므로 3단계를 다 펼치면 형식이 장황해진다. **[현상]과 [해결책]을
가능하면 한 문장에 함께 담는다** — 제약 자체를 말하는 문구는 [현상]과 [해결책]이 이미
한 문장에 겹쳐 있어 그대로 두고, 이미 벌어진 충돌(중복 닉네임 등)을 알리는 문구는
[현상]에 이어 짧은 해결책 문장을 덧붙인다. CTA 버튼은 달지 않는다 — 입력을 고치는
행동 자체가 해결책이다.

| 구형 방식 (Bad) | JAM! 축약 적용 (Good) |
|---|---|
| 닉네임 형식이 올바르지 않습니다 | 닉네임은 2자에서 12자까지 쓸 수 있어요 |
| 필수 입력값입니다 | 어떤 점이 궁금한지 적어 주세요 |
| 이미 사용 중인 닉네임입니다 (Error 409) | 이미 다른 사람이 쓰고 있는 닉네임이에요. 다른 이름을 지어볼까요? |

### 4.3 빈 상태(empty state)는 에러가 아니다 (2026-09-15 신설)

목록에 아직 아무것도 없는 것은 실패가 아니라 "아직 안 쌓인 것"이다. 3단계 구조(현상→원인→
해결책, §4.1)를 적용하지 않는다 — 설명할 원인이 없다. 담담하게 현재 상태만 말한다. 어조는
§2.3 톤 매트릭스의 "담담·안내"에 가깝게 유지하고, 사과하거나 아쉬워하는 투를 쓰지 않는다.
사용자 입력값(검색어 등)을 문구에 끼워 넣을 때는 `{검색어}`로 표기한다 — §1.2에서 정한 대로
닉네임 자리표시자 'OO'와 구분하기 위함이다.

| 구형 방식 (Bad) | JAM! 적용 (Good) |
|---|---|
| 조회된 배지가 없습니다 | 아직 획득한 배지가 없어요 |
| 데이터가 없습니다 | 근처에 떨어진 아이템이 없어요 |
| 검색 결과가 존재하지 않습니다 | "{검색어}" 검색 결과가 없어요 |

## 5. 행동 유도 버튼 규칙 (CTA)

### 5.1 예측 가능한 행동 동사 사용

버튼을 눌렀을 때 일어날 결과가 명확히 드러나는 동사를 쓴다.

- Good: 배지 획득하러 가기, 포인트로 바꾸기, Strava 다시 동기화하기
- Bad: 확인, 다음, 실행, 완료
- **예외** — 드랍·픽업처럼 §1.3에서 이미 고정 용어로 정의됐고 화면에서 반복 노출되는 액션은
  버튼 레이블을 명사형(드랍, 픽업)으로 축약한다. 확인 다이얼로그 본문 등 문장 안에서는
  계속 동사형(드랍할까요?, 픽업할 수 있어요)을 쓴다 — 축약은 버튼 레이블에만 적용. (티켓 20260830_2015)

### 5.2 1화면 1주요 버튼 원칙

한 화면에서 가장 중요한 행동 버튼은 1개만 강조 배치한다.
드랍/픽업처럼 되돌릴 수 없는 행동은 보조 버튼("취소", "나중에")을
반드시 동일한 시각적 무게로 함께 노출해, 실수로 확정 버튼만 누르지 않게 한다.

### 5.3 처리 중 상태의 버튼 라벨 (2026-09-15 신설)

버튼을 누른 뒤 응답을 기다리는 동안에는 원래 동사에 "~하는 중"을 붙인 진행형을 쓴다.
"처리 중...", "잠시만요" 같은 별도 로딩 문구로 바꿔치기하지 않는다 — 사용자가 방금 누른
버튼이 지금 무슨 동작을 하는 중인지 라벨만 보고 알 수 있어야 한다. **적용 위치에 따라
형태가 갈린다** — 기본형은 동사형(문장·토스트), §5.1 예외로 명사형 축약이 허용된
버튼·칩 레이블에서만 명사형을 쓴다. 같은 화면에서 두 형태를 섞어 쓰지 않는다.

| 위치 | 형태 | 예시 |
|---|---|---|
| 문장 · 토스트 (기본형) | 동사형 | 드랍하는 중 |
| 버튼 · 칩 레이블 (§5.1 예외 대상만) | 명사형 축약 | 드랍 중 |

- Bad: 처리 중..., 잠시만요, Loading...

## 6. 네비게이션 — TopNav 뒤로가기 레이블 정책

### TopNav title의 역할

TopNav 렌더 구조는 `[← title ──────] [rightSlot]` 이다.
`title`은 항상 **"어디로 돌아가는가"를 뜻하는 back-label**이다.
현재 화면명이 아니다. (iOS HIG Back Button 패턴과 동일)

### 화면 유형별 결정 기준

| 조건 | title | backHref |
|---|---|---|
| 목록 → 상세, 진입 경로 고정 | 목록 화면명 ("미션", "인벤토리") | 있음 (목록 URL) |
| 프로필 → 하위 화면 | 유저명 (username) | 있음 (`/{username}`) |
| 다양한 경로로 진입 가능 | `d.common.back` ("뒤로") | 없음 (router.back) |
| 탭바 루트 화면 | 없음 | showBack=false |

### 적용 예시

| 화면 | title | 근거 |
|---|---|---|
| `/missions/{id}` | "미션" | 미션 목록에서만 진입 |
| `/inventory/{id}` | "인벤토리" | 인벤토리 목록에서만 진입 |
| `/{username}/following` | username | 프로필 화면으로 돌아감 |
| `/{username}/followers` | username | 프로필 화면으로 돌아감 |
| `/profile/edit` | "프로필" | 프로필 화면으로 돌아감 |
| `/search` | "뒤로" | 여러 경로(투데이, 내비 등)에서 진입 |
| `/points` | "뒤로" | 여러 경로(프로필, 투데이 등)에서 진입 |

### 레이블 텍스트 규칙

- "뒤로" 고정 문구는 `d.common.back` 키를 사용한다. 화면마다 다른 표현("돌아가기", "이전" 등)을 쓰지 않는다.
- 유저명(username)을 그대로 쓴다. "OO님의 프로필"처럼 부연하지 않는다.
- 목록 화면명은 탭바 라벨(`d.nav.*`)과 일치시킨다.
- 마침표 없음, 해요체 불필요 (레이블이므로).

## 7. Anti-slop 판단 기준 (`/im-not-ai` 참조용, 2026-09-15 신설)

이 절은 전수검사(`/im-not-ai`, 플러그인 `humanize-korean`)가 JAM! 사용자 노출 문구를
판정할 때 쓰는 **서비스 특화 기준**이다. 일반적인 한국어 유창성 규칙은
`.claude/output-styles/fluent-korean.md`를 따르고, 이 절은 그 위에 JAM! 톤·용어와 자주
충돌하는 패턴만 추린다.

### 7.1 번역투

| 패턴 | 문제 | 대체 |
|---|---|---|
| "~에 대해", "~에 대한" 남용 | 목적어를 두 단계로 에둘러 지칭 | 조사로 직접 연결 (「배지에 대해 축하드립니다」→「배지 획득을 축하해요」) |
| "~하시기 바랍니다", "~해 주시기 바랍니다" | 격식체 요청문, JAM! 해요체와 충돌 | "~해 주세요" 또는 상황에 맞는 CTA 문장 |
| "~되었습니다" 계열 수동태(시스템 시점) | §2.1 해요체 원칙 위반의 번역투 버전 | 사용자 시점 능동태 (「배지가 발급되었습니다」→「배지를 획득했어요」) |
| "귀하", "고객님" | 은행식 존칭 | §1.2에 따라 닉네임 또는 'OO님' |

### 7.2 상투적 표현(클리셰)

| 패턴 | 문제 | 대체 |
|---|---|---|
| "소중한 의견 감사합니다", "많은 이용 바랍니다" | 어느 서비스에나 붙는 정형구, JAM! 목소리가 아님 | 상황에 맞는 구체적 문장으로 직접 서술 |
| "빠른 시일 내에" | 구체적 시점을 숨기는 관용구 | 아는 만큼 구체적으로("1~2일 안에"), 모르면 생략 |
| "다양한", "다양하고 풍부한" 등 근거 없는 수식어 남발 | 정보값 없이 문장만 늘림 | 수식어를 빼거나 구체적 수치·예시로 대체 |
| "~해보세요!" 남발, 느낌표 연속 | 과잉된 텐션, §2.3 톤 매트릭스 위반 가능성 | 해당 상황에 지정된 톤 하나만 쓰고 느낌표는 문장당 최대 1개 |

### 7.3 부자연스러운 어미·구조

- 한 문장에 여러 종결어미를 이유 없이 섞지 않는다(예: 해요체와 `-습니다`체가 한 문단에서
  뒤섞이는 경우 — 배지 설명문의 `-습니다`체 예외는 §2.1에서 이미 별도로 허용됨).
- 이모지는 §2.3 "신남·축하" 톤에만, 그것도 문장당 최대 1개로 제한한다. 그 외 톤(담담·설렘·
  단호·차분)에는 이모지를 쓰지 않는다.
- 엠대시(—)는 문장 관계를 지나치게 함축하므로 사용자 노출 문구에는 쓰지 않는다(이 문서
  자체나 코드 주석과는 다른 기준 — 이 항목은 유저가 읽는 화면 문구에만 적용된다).
- 일반 어휘를 써야 할 자리에 비유적 어휘를 남용하지 않는다. 다만 배지 플레이버 텍스트처럼
  의도된 문학적 표현(§2.1 예외, §1.3 "발걸음/궤적" 용어)은 비유 남용이 아니라 장르 규칙이므로
  판정 대상에서 제외한다.

### 7.4 적용 범위

이 절의 기준이 §1·§4·§5의 구체 규칙과 충돌하면 구체 규칙이 우선한다(예: 배지 플레이버
텍스트의 `-습니다`체는 §2.1 예외로 이미 허용됨 — 이 절의 "수동태 번역투" 항목과 혼동하지
않는다). 어드민 화면(`src/app/admin/`)은 §1.3과 동일하게 이 절의 적용 대상이 아니다.

## 8. 적용 방법

- 신규 기능 개발, 기존 화면 문구 수정, 알림/에러 메시지 작성 시 **이 문서를 항상 우선 참조**한다.
- 새로운 용어가 필요하면 1절 3항 "용어 일관성" 표를 갱신한 뒤 사용한다. 표에 없는 용어를 임의로 만들어 쓰지 않는다.
- 서버 API route에서 에러 메시지를 작성할 때는 §4.0 "서버-클라이언트 단일 진실 소스" 규칙을 따른다.
- 이 가이드라인 자체가 변경되면(용어 추가, 톤 기준 조정 등) 버전 사본을 만들지 않고
  `UX_WRITING_GUIDELINE.md` 이 파일을 직접 덮어써 갱신한다 (SERVICE_OPERATIONS류 스냅샷 문서와
  달리 이 문서는 살아있는 단일 기준 문서로 유지한다).
