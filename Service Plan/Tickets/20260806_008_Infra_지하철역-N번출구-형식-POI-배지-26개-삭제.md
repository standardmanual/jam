# [Infra] 지하철역 'N번출구' 형식 POI/배지 26개 삭제

## 배경 / 문제 정의
지하철역 POI 중 역 단위가 아니라 "N번출구" 단위로 개별 등록된 POI가 26개 있었음
(예: "석촌역(한솔병원)1번출구", "석촌역(한솔병원)2번출구" ...). 역 하나에 출구별로 여러
POI/배지가 중복 생성되는 것은 배지 목록 관리 관점에서 불필요한 세분화로 판단, 일괄 삭제
결정.

## 상세 요구사항

### 서비스/코드베이스 관점
- `public.poi`에서 `category='transit' AND name ~ '[0-9]+번출구$'` 패턴 26개 삭제
- 연결된 `public.badges` 22개(4개는 애초에 `linked_badge_id` 없음)도 함께 삭제
- 삭제 전 참조 무결성(FK) 전수 확인 후 실유저 데이터 영향이 없도록 처리

## 구현 계획
1. `poi.name` 정규식(`[0-9]+번출구$`)으로 대상 26개 확정 — "출구" 텍스트가 들어간 다른
   변형 표기(출입구 등)가 있는지도 별도 확인해 누락 없음을 검증
2. `badges`/`poi`를 참조하는 모든 FK 제약을 전수 조회해 하드 삭제 시 막히거나 연쇄 삭제되는
   테이블을 먼저 파악
3. 유저 영향 확인 후 삭제 진행 (사용자 확인: 전부 테스트 유저)

## 완료 기록

### 구현 내용 요약
1. `poi.name ~ '[0-9]+번출구$'` 패턴으로 26개 확정. `name LIKE '%출구%'`로 재검증해 이
   패턴 외 "출구" 텍스트가 들어간 POI는 없음을 확인(누락 없음)
2. `badges`/`poi`를 참조하는 전체 FK를 조회해 영향 범위 확정:
   - `user_poi_badge_earns`: 12건 (`poi_id`/`badge_id` 모두 `CASCADE`)
   - `user_activity_badges`: 5건 (`badge_id`가 `NO ACTION` — 명시적 사전 삭제 필요)
   - `poi_drops`: 1건 (`poi_id CASCADE`)
   - `combination_recipes`/`item_books`/`user_item_book_slots`/`wandering_mythic_state`/
     `poi_blocks`/`point_transactions`: 참조 0건
3. 1차 삭제 시도 중 예상 못한 추가 의존성 발견: 위 `poi_drops` 1건에 **삭제 대상과 무관한
   실제 유저 소유 인벤토리 아이템**("에어로 프레임 데칼")의 출처 링크(`inventory_items.drop_id`)가
   걸려있어 `NO ACTION` FK로 삭제가 막힘 → 아이템 자체는 보존하고 `drop_id`만 NULL 처리 후 진행
4. 순서: `inventory_items.drop_id` NULL 처리 → `user_activity_badges` 삭제(5건) →
   `poi` 삭제(26건, cascade로 `user_poi_badge_earns`/`poi_drops`/`poi_blocks` 연쇄 삭제) →
   `badges` 삭제(22건)
5. 삭제 완료 검증(잔존 0건) + 보존 대상 아이템 존재 확인
6. orphan된 배지 이미지 파일 22개(`public/badges/poi/transit/`) 제거 + 커밋/푸시

### 주요 의사결정 / 핵심 메모
- **하드 삭제 vs 소프트 삭제**: [[20260806_006]]에서 산 배지 작업 시 참고했던
  `060_badge_soft_delete.sql` 컨벤션(유저 이력 보존을 위한 소프트 삭제)을 이번에도
  1순위로 제안했으나, 사용자가 "모두 테스트 유저라 삭제해도 됨"이라고 명시적으로 확인해
  하드 삭제로 진행. 프로덕션 실유저가 걸려있었다면 소프트 삭제(`badges.deleted_at`)가
  맞는 선택이었을 것.
- **1차 시도 실패 → 트랜잭션 롤백 확인 후 재시도**: `poi_drops → inventory_items.drop_id`
  FK는 사전 조사(badges/poi를 직접 참조하는 FK만 조회)에서 놓쳤던 간접 의존성(2단계 참조:
  poi → poi_drops → inventory_items)이었음. 에러 발생 시 트랜잭션이 전부 롤백되어 부분
  삭제가 남지 않았음을 먼저 확인한 뒤, 원인이 된 인벤토리 아이템을 특정해 사용자에게
  다시 확인받고 진행 — "유저와 무관한 문제도 알려달라"는 사용자 요청에 따라 발견 즉시 보고.
- **iCloud 동기화 충돌 파일 정리**: 작업 중 `jam-web/public/badges/poi/mountain/`에
  `{id} 2.png` 형식의 iCloud 동기화 충돌 파일 264개가 발견됨(프로젝트가 iCloud Drive
  경로에 위치해 빠른 연속 파일 쓰기 시 발생). 이번 작업과 무관한 이전 산 배지 재생성
  과정의 잔재로 판단해 함께 정리(git에는 애초에 커밋되지 않은 상태였음).
