# [Infra] 개발 프로세스 가드레일 문서화 + DB 타입 자동생성 전환

## 배경 / 문제 정의
20260811_001·002 인시던트 이후, 사용자(비개발자, 서비스 운영자)가 "핵심 루프 신뢰가 무너지는
오류를 막기 위해 클로드 코드의 개발·리뷰 과정 자체를 최적화하고 싶다"고 요청. 구체적으로는
"코드나 DB 테이블 등 챙겨야 하는 것을 놓쳐서 사이드 이펙트가 생기는 것"이 가장 큰 문제라고
짚었고, 이어서 과거 티켓·운영 문서 전체를 분석해 "개발 프로세스 자체의 반복된 실수 패턴"까지
찾아서 개선에 반영해 달라고 요청함.

## 상세 요구사항

### 서비스/코드베이스 관점
1. DB 스키마 → TypeScript 타입 자동생성 체계 도입 (기존엔 899줄 손타이핑, "Supabase 연결 전
   이므로 수동 정의"라는 주석이 연결 후에도 갱신 안 된 채 방치돼 있었음)
2. 20260811_001·002 감사에서 추출한 "개발 프로세스 실수 패턴" 7가지를 문서화하고, 각각에
   대응하는 규칙을 명문화
3. 핵심 루프(동기화→배지→드랍→포인트) 의존성 지도 작성 — 무엇을 건드리면 무엇을 같이 확인해야
   하는지
4. 핵심 루프 작업 전 "영향범위 평문 보고" 규칙을 프로젝트 규칙에 명문화

## 구현 계획
1. `supabase gen types typescript`(MCP `generate_typescript_types`)로 `database.generated.ts`
   생성 — 손으로 쓴 `database.ts`(도메인 주석이 많아 유지 가치가 있음)는 그대로 두되, 재생성
   워크플로우(`npm run db:types`)를 추가해 둘을 주기적으로 대조할 수 있게 함
2. 실제 대조 결과 발견된 드리프트(`UserRow`에 GPS 위치/거리 관련 컬럼 5개 누락)를 바로 수정,
   해당 컬럼을 `as any` 캐스팅으로 우회하고 있던 `gps-detector.ts`도 정식 타입으로 전환해
   드리프트 방지 효과를 실증
3. `Service Plan/Specs/DEV_PROCESS_GUARDRAILS.md` 신규 작성 — 패턴 7가지 + 핵심 루프
   의존성 지도 + 영향범위 보고 규칙
4. `04_PROJECT_SPEC.md`에 새 문서 링크 + 관련 규칙 추가

### 주요 의사결정 / 핵심 메모
- **`database.ts` 전면 교체 대신 병행 유지 채택**: 899줄 손타이핑 파일을 자동생성본으로
  완전히 대체하는 안도 검토했으나, (a) 116개 파일이 이 파일의 친숙한 타입 이름(`UserRow` 등)에
  의존하고 있어 전면 교체가 큰 리팩터링이 되고, (b) 손으로 쓴 주석에 담긴 도메인 지식(예:
  "initial_sync_done: false이면 배지 엔진이 Common만 발급")이 자동생성본엔 없어 유지 가치가
  있다고 판단. 대신 재생성 워크플로우로 주기적 대조가 가능하게 하는 절충안 채택.
- **전체 54개 테이블이 아닌 실제 드리프트 발견된 것만 수정**: 시간 제약상 전 테이블 대조
  스크립트를 1회 돌려(핵심 루프 11개 테이블 우선 확인) 실제 차이가 있는 `UserRow`만 수정.
  나머지 43개 테이블은 미대조 상태로 남아 있음 — 다음에 `database.ts`를 만질 때 같은 방식으로
  대조 권장.
- **as any 전수 제거는 별도 작업으로 분리**: 51개 파일 규모라 이번 티켓에서 처리하면 범위가
  과도하게 커짐. spawn_task로 후속 세션 제안 등록(task_0713d81d).

### 잔여 이슈
- `database.ts`의 핵심 루프 외 43개 테이블 타입 미대조
- `as any` 캐스팅 51개 파일 전수 정리 필요(후속 작업 제안 등록됨)
- `DEV_PROCESS_GUARDRAILS.md`의 "영향범위 보고" 규칙은 문서화만 됐고, 실제로 매 작업마다
  지켜지는지는 운영하면서 검증 필요
