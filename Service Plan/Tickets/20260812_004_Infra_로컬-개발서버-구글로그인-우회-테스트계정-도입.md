# [Infra] 로그인 우회(테스트 계정) + Staging 환경 도입

## 배경 / 문제 정의

JAM!은 구글 로그인이 필수라, 오케스트레이터(Claude)가 실제 화면을 검토하거나 사용자가
배포 전에 스테이징 환경에서 확인할 방법이 없었다. 두 가지 필요를 동시에 해결한다:

1. **로컬**: Claude가 `next dev`에서 구글 로그인 없이 테스트 계정으로 접속해 UI 확인
2. **Staging**: 사용자가 프로덕션 배포 전 Vercel staging 환경에서 구글 로그인 없이 확인

## 배포 흐름 (이 티켓 완료 후 기준)

```
로컬 개발 → claude/jamwork-* → staging 머지 → Vercel staging 확인(로그인 없이) → main 머지 → 프로덕션
```

## 기존 티켓 검토

관련 기존 티켓 없음. Supabase는 `jam-prod` 단일 프로젝트(free, 브랜칭 없음) — staging도 동일 DB 사용.
테스트 계정은 같은 DB에 고정 UUID로 격리된 row로 존재 (RLS/user_id 스코프 격리).

이전 워크플로우 세션에서 코드 일부가 이미 작성된 상태:
- `jam-web/src/app/api/dev-login/route.ts` — 존재하나 검토 필요
- `jam-web/src/app/(auth)/login/page.tsx` — 테스트 로그인 버튼 추가된 상태
- `jam-web/src/proxy.ts` — `/api/dev-login` 공개 경로 추가된 상태

기존 코드를 기반으로 `STAGING_MODE` 지원을 추가한다.

## 상세 요구사항

### 서비스/코드베이스 관점 — 보안 핵심 (우선순위 순)

**게이트 조건 (이게 전부)**

`/api/dev-login` 라우트 접근 허용 조건:
- `process.env.NODE_ENV === 'development'` (로컬 next dev)  
- **또는** `process.env.STAGING_MODE === 'true'` (Vercel staging 프로젝트 전용 서버 환경변수)

둘 다 아니면 → **무조건 404**. Vercel은 staging이든 production이든 `NODE_ENV=production`으로 고정하므로,
프로덕션 Vercel 프로젝트에 `STAGING_MODE`가 없으면 절대 동작하지 않는다.

**구현 항목**

1. `jam-web/src/app/api/dev-login/route.ts` — 위 게이트 조건 적용. 고정 테스트 유저로 세션 발급 후 `/`로 리다이렉트.
   Supabase service_role의 `auth.admin.generateLink({ type: 'magiclink', email })` + `verifyOtp` 방식
   (기존 `src/app/auth/callback/route.ts` 쿠키 설정 방식 재사용).

2. `jam-web/src/proxy.ts` — `STAGING_MODE === 'true'`일 때 미인증 요청을 `/login` 대신
   `/api/dev-login`으로 자동 리다이렉트 (staging에서 URL 접속 시 즉시 테스트 계정으로 진입).
   `/api/dev-login`은 공개 경로로 유지 (이미 추가된 상태 확인 후 유지).

3. `jam-web/src/app/(auth)/login/page.tsx` — `NODE_ENV === 'development'`일 때만 "테스트 로그인" 버튼 노출.
   staging에서는 미들웨어가 login 페이지 도달 전에 자동 리다이렉트하므로 버튼 불필요.
   기존 구글 로그인 버튼은 절대 건드리지 않는다.

4. `jam-web/supabase/seed_dev_test_user.sql` — **작성만, 직접 실행 안 함** (오케스트레이터가 승인 후 실행).
   - UUID: `00000000-0000-0000-0000-000000000dev`, 이메일: `dev-tester@jam.local`
   - 최소 시드: 액티비티 배지 1~3건, POI 배지 이력 1~3건, 인벤토리 아이템 1~3건
   - idempotent (`ON CONFLICT DO NOTHING`)

### UI/UX 관점
- "테스트 로그인" 버튼은 로컬 전용, UX 라이팅 가이드라인 대상 아님.

### Vercel staging 프로젝트 설정 (오케스트레이터가 안내, 사용자가 직접 수행)
코드 배포 후 사용자가 Vercel 대시보드에서:
1. 새 프로젝트 생성 → 같은 리포지토리 연결 → `staging` 브랜치 자동배포 설정
2. Environment Variables: `STAGING_MODE = true` (Production/Preview 환경 아닌 별도 프로젝트에만)
3. 기존 프로덕션 프로젝트의 다른 env vars 동일하게 복사

## 구현 계획

`jam-developer`가 코드 4개 항목 작성 후 review 브랜치 push.
conservative-reviewer는 **게이트 조건이 프로덕션에서 절대 동작하지 않음을 최우선 검증**
— `NODE_ENV`와 `STAGING_MODE` 둘 다 없는 환경에서 라우트가 404를 반환하는지 코드 레벨 확인.
애매하면 무조건 FAIL.

## 완료 기록

### 구현 내용 요약
`NODE_ENV=development`(로컬) 및 `STAGING_MODE=true`(Vercel staging) 두 환경에서
구글 로그인 없이 고정 테스트 계정으로 자동 진입하는 인프라 구축. Vercel staging 프로젝트(`jam-stage`)도
함께 셋업하여 `local → staging → production` 3단계 배포 파이프라인 완성.

### 변경된 파일
- `jam-web/src/app/api/dev-login/route.ts` (신규) — `isAllowedEnv()` 이중 게이트, 세션 발급 후 `/` 리다이렉트
- `jam-web/src/proxy.ts` — `STAGING_MODE=true`일 때 미인증 요청 → `/api/dev-login` 자동 리다이렉트
- `jam-web/src/app/(auth)/login/page.tsx` — `NODE_ENV=development`일 때만 "테스트 로그인" 버튼 노출
- `jam-web/supabase/seed_dev_test_user.sql` (신규) — 테스트 계정 시드 (activity 3건, poi 2건, inventory 3건)

### 테스트 결과
- [x] `tsc --noEmit` 통과
- [x] 보안 게이트: `NODE_ENV=production` + `STAGING_MODE` 미설정 시 `/api/dev-login` → 404
- [x] seed SQL 실행 완료 — users/activity_badges/poi_badge_earns/inventory_items 각 정상 삽입 확인
- [x] Vercel staging(`jam-stage.vercel.app`) 배포 성공 — 구글 로그인 없이 접속 확인

### 주요 의사결정
- `NODE_ENV` 대신 `STAGING_MODE` 서버 환경변수 사용 — Vercel은 staging/production 모두 `NODE_ENV=production`으로 고정하므로 별도 변수 필요
- Vercel staging 프로젝트 Framework Preset을 "Next.js"로 수동 설정 필요했음 — 프로젝트 생성 시 자동 감지 실패(Other로 잡힘), 이후 재배포로 해결
- 테스트 계정 UUID: `00000000-0000-0000-0000-000000000001` (티켓 원안의 `000000000dev`는 비-hex 문자 포함으로 무효, `000000000001`로 통일)

### 잔여 이슈
- production 머지는 사용자가 staging 충분히 검토 후 별도 승인
- 로컬에서 테스트 시 seed SQL이 실행되어 있어야 `/api/dev-login` 진입 후 데이터가 보임
