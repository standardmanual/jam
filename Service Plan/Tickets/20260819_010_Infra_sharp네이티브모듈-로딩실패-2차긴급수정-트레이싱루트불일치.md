# [Infra] sharp 네이티브 모듈 로딩 실패 2차 긴급 수정 — 트레이싱 루트 불일치

## 배경 / 문제 정의
티켓 [20260819_009](20260819_009_Infra_sharp네이티브모듈-프로덕션로딩실패-긴급수정.md)에서
`serverExternalPackages: ['sharp']`를 추가해 배포했으나, 프로덕션에 재배포
(`dpl_B4NdDgjReJcLbm5mQmWGyc6fu6VF`) 후에도 **동일한 에러가 그대로 재발**했다(사용자 재보고,
Vercel 런타임 로그로 재확인 — 에러 해시까지 완전히 동일: `sharp-10c1ab0fa4c72150`).

새 배포의 빌드 로그를 직접 확인해 추가 원인을 찾았다:

```
⚠ Both `outputFileTracingRoot` and `turbopack.root` are set, but they must have the same value.
Using `outputFileTracingRoot` value: /vercel/path0.
```

`jam-web/next.config.ts`는 로컬 개발 환경 문제(`$HOME/package-lock.json`을 워크스페이스 루트로
잘못 추론해 CSS import가 깨지던 문제, 커밋 `fb0ab75`, 2026-08-17)를 고치려고
`turbopack.root: path.join(__dirname)`만 설정해뒀다. Vercel 프로덕션 빌드에서는 이 값이
Vercel이 자동 추론하는 `outputFileTracingRoot`(`/vercel/path0`)와 일치하지 않아 **무시되고
`outputFileTracingRoot` 쪽이 우선 적용**된다. Next.js의 서버리스 함수 출력 파일 트레이싱은
`outputFileTracingRoot` 기준으로 동작하므로, 이 불일치가 `sharp`처럼 소스 코드에서 직접
import하지 않는(설치 시점 optional dependency로만 존재하는) 네이티브 바이너리 파일을 트레이싱
결과에서 누락시키는 원인일 가능성이 높다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `jam-web/next.config.ts`에서 `outputFileTracingRoot`와 `turbopack.root`를 **동일한 값**으로
  명시적으로 설정한다(둘 다 `path.join(__dirname)` 등 같은 계산식 사용). Vercel의 자동 추론에
  맡기지 않고 명시적으로 고정해서 경고 자체를 없앤다.
- 티켓 009의 `serverExternalPackages: ['sharp']`는 그대로 유지한다(제거하지 말 것 — 문제
  해결에 필요한 조건 중 하나일 수 있음, 둘 다 있어야 해결될 가능성).
- 이 수정만으로 해결되지 않을 경우를 대비해, `outputFileTracingIncludes`로
  `/api/admin/upload-image` 라우트에 `sharp` 네이티브 바이너리 경로
  (`./node_modules/@img/sharp-linux-x64/**/*`, `./node_modules/@img/sharp-libvips-linux-x64/**/*`)
  를 명시적으로 포함시키는 방법도 조사해서 필요하면 함께 적용한다(Next.js 공식 문서의 sharp+Vercel
  네이티브 모듈 트러블슈팅 가이드에 언급되는 표준 대안).
- sharp 의존성 제거나 기능 비활성화 등 우회는 여전히 금지.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
**1차 시도(jam-developer, 커밋 `47d6c29`)**: `projectRoot = path.join(__dirname)` 상수를 계산해
`outputFileTracingRoot`와 `turbopack.root`에 동일하게 대입. 로컬 `npm run build`는 성공하고
"Both ... must have the same value" 경고도 사라졌으나, **staging 배포 시 빌드 자체가 실패**했다:

```
Build Failed
ENOENT: no such file or directory, lstat '/vercel/path0/.next/server/pages-manifest.json'
```

원인: `outputFileTracingRoot`를 명시적으로 지정하자, `next build`는 성공했지만(라우트 매니페스트
정상 생성 로그까지 확인됨) 그 **직후 Vercel의 배포 패키징 단계("Deploying outputs...")가 실패**했다.
Vercel은 `outputFileTracingRoot`가 자신이 자동 추론하는 `/vercel/path0`와 같다는 전제로 배포
아티팩트를 패키징하는데, 우리가 명시한 값이 `/vercel/path0`와 (심볼릭 링크 해석 차이 등으로)
바이트 단위로 다르면 이 전제가 깨져 매니페스트 파일을 못 찾는다. 즉 **원래 경고("Both ... must
have the same value")는 사실 무해했고, `outputFileTracingRoot`는 Vercel의 자동 추론값을 그대로
쓰는 게 맞았다** — 이걸 억지로 맞추려 한 시도 자체가 새로운 빌드 실패를 만들었다.

**2차 수정(오케스트레이터가 직접, 파이프라인 없이 처리 — 활성 빌드 장애 대응)**:
`outputFileTracingRoot` 명시 설정을 제거하고 Vercel 자동 추론에 다시 맡겼다. `turbopack.root`는
로컬 개발 환경 문제(커밋 `fb0ab75`) 방지 목적 그대로 유지 — 프로덕션에서 값이 어긋나 경고가 뜨는
건 감수한다(경고일 뿐 빌드 실패 아님을 이번에 확인함). 티켓 009의 `serverExternalPackages:
['sharp']`와 `outputFileTracingIncludes`(sharp 네이티브 바이너리 경로 명시 포함)는 그대로 유지 —
이 둘은 이번 빌드 실패의 원인이 아니었다.

### 주요 의사결정 / 핵심 메모
- **`outputFileTracingRoot`를 수동으로 Vercel 자동 추론값과 맞추려는 시도는 하지 않는다** — 이미
  Vercel이 올바르게 추론하고 있었고(경고는 `turbopack.root`와의 불일치일 뿐), 수동 설정이 오히려
  배포 패키징을 깨뜨렸다. 향후 이 경고를 다시 마주쳐도 `outputFileTracingRoot`는 건드리지 말 것.
- `outputFileTracingIncludes`의 라우트 키는 Next.js가 picomatch로 매칭하는 라우트 경로 문자열이며,
  실제 파일 경로가 아니라 URL 경로(`/api/admin/upload-image`)를 사용해야 한다 — `node_modules/
  next/dist/docs/.../output.md` 예시로 확인.
- sharp 로딩 실패의 진짜 원인이 `outputFileTracingRoot` 불일치였는지는 결국 확인되지 않았다(그
  가설로 시도한 수정이 배포 자체를 막아서 검증할 수 없었다). 최종적으로 남은 수정은 티켓 009의
  `serverExternalPackages`+`outputFileTracingIncludes`뿐이며, 이걸로 실제 해결되는지는 production
  배포 후 런타임 로그로만 확인 가능하다.

### 잔여 이슈
- production 배포 및 런타임 로그 재확인 필요(진행 중)
- `serverExternalPackages`+`outputFileTracingIncludes`로도 여전히 재발하면, `output: 'standalone'`
  모드 전환이나 sharp를 별도 함수/서비스로 분리하는 등 더 근본적인 대안 검토가 필요할 수 있음
