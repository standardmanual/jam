# [UI] 애니메이션 배경 — 반복 영상 굽기 + 유저단 재생

## 배경 / 문제 정의
사용자가 어드민에서 배경 제너레이터를 **애니메이션 모드**로 설정해 저장했는데 실제 서비스에서
움직이지 않는다고 보고했다. 확인 결과 **버그가 아니라 티켓 20260819_008에서 명시적으로 미뤄둔
범위**다 — `bakePreviewToBlob.ts`가 `canvas.toBlob(..., 'image/png')`로 정지 PNG만 굽고 있고,
티켓 008 완료 기록에도 "애니메이션 모드도 이번 범위에서는 정지 이미지로만 굽는다(반복 영상 굽기는
별도 후속 티켓)"이라고 기재돼 있다.

이번 티켓이 그 후속이다: **애니메이션 모드를 짧은 반복 영상으로 구워 저장하고, 유저단에서
재생**한다.

**전체 설계 원칙은 유지된다** — 유저단(모바일 웹)에는 WebGL을 로드하지 않는다. 어드민에서 영상으로
구워 Storage에 저장하고, 서비스는 `<video>` 태그로 재생만 한다.

## 참고 자료
티켓 20260819_002에서 kaleidoscope를 이식할 때, 원본 리포
(`collidingScopes/collidingScopes.github.io`)에 `videoExportFunctions.js`(mp4-muxer 기반 비디오
녹화)가 있는 것을 확인하고 "향후 정식 기능의 영상 굽기 참고자료"로 기록해뒀다. 이번에 활용한다.

## 상세 요구사항

### 인코딩 (어드민 측)
- 출력 포맷은 **MP4(H.264)** 를 권장한다. 최종 결과물이 **iOS Safari에서 재생**되어야 하므로
  WebM은 부적합하다. 브라우저에서 MP4를 만드는 방법은 `mp4-muxer` + WebCodecs `VideoEncoder`
  조합(원본 리포와 동일한 접근)이 유력하다. 실제 구현 전에 대안(`MediaRecorder`)과 비교 검토하고
  선택 근거를 완료 기록에 남길 것.
- 신규 의존성(`mp4-muxer` 등) 추가는 이 티켓에 한해 허용한다. 단 **Three.js는 여전히 금지**.
- 녹화 대상: 현재 미리보기와 동일한 합성 결과(애니메이션 + Paper 필터). 별도 오프스크린 렌더러를
  새로 만들지 말고 기존 캔버스를 `captureStream()`하거나 프레임 단위로 인코더에 넣는 방식으로
  "보이는 그대로" 굽는다(티켓 008의 원칙 유지).
- **용량 최적화가 이 티켓의 핵심 요구사항이다** (사용자 명시). 모바일 유저가 배지 상세를 열
  때마다 내려받는 파일이므로 최대한 작게 만든다. 조절 가능한 레버를 모두 검토하고, 각 선택의
  근거와 실제 결과 파일 크기를 완료 기록에 수치로 남길 것:
  - **프레임레이트**: 배경 애니메이션은 60fps가 필요 없다. **15~24fps**로 낮추면 비트레이트가
    크게 줄어든다 — 가장 효과가 큰 레버.
  - **길이**: 짧을수록 작다. 정현파 주기에 맞춰 **가능한 짧은 seamless 루프**(2~4초)를 찾는다.
  - **해상도**: 앱 컬럼 폭 430px 기준. 배경(패턴·만화경)은 디테일이 덜 중요하므로 **430px 이하로
    낮추고 CSS로 확대**해도 체감 품질 저하가 작을 수 있다 — 실제로 비교해보고 판단할 것.
    레티나 2배(860px)는 용량 대비 이득이 크지 않으면 채택하지 않는다.
  - **비트레이트/품질 파라미터**: H.264 인코딩 시 목표 비트레이트나 품질값 상한을 명시적으로 건다.
  - **코덱**: 호환성 우선으로 H.264(baseline/main)를 기본으로 한다. HEVC/AV1은 더 작지만 재생
    호환성 리스크가 있어 이번 범위에서는 채택하지 않는다.
  - 패턴·만화경 배경은 평탄한 색 면이 많아 압축률이 좋은 편이다 — 실제 인코딩 결과로 확인할 것.
- **결과 파일 크기 목표**: 명시적 상한을 정하고(예: 수백 KB 수준) 초과하면 위 레버로 조정한다.
  최종 목표치와 달성 수치를 완료 기록에 남길 것.
- **루프 이음매**: kaleidoscope 애니메이션은 `Math.sin()` 기반 정현파 오프셋으로 왕복한다
  (티켓 002 이식 기록 참고). 녹화 구간을 이 주기에 맞추면 이음매 없는 루프를 만들 수 있는지
  검토한다. 완벽한 seamless가 어렵다면 그대로 두되 완료 기록에 한계를 남길 것.
- **poster(정지 프레임) 동시 생성**: 영상과 함께 첫 프레임을 PNG로도 구워 저장한다. `<video
  poster>`로 쓰면 첫 페인트가 빠르고, 영상 로드 실패·`prefers-reduced-motion` 시 폴백이 된다.

### 저장 (API·DB)
- `jam-web/src/app/api/admin/upload-image/route.ts`는 현재 `ALLOWED_TYPES`가 이미지 MIME만
  허용하고(line 8, 19), **모든 업로드에 sharp 평균색 추출(`computeAverageColorHex`)을 실행**한다
  (line 33). 영상 버퍼에서는 이 추출이 실패하므로 확장이 필요하다:
  - `video/mp4`(및 선택한 포맷) 허용 추가
  - 영상일 때는 평균색 추출을 건너뛰도록 분기 (이미지 업로드 기존 동작은 그대로 유지 — 회귀 금지)
  - 파일 크기 상한이 있다면 영상 기준으로 재검토
- `badges` 테이블에 `background_video_url`(text, nullable) 컬럼을 추가하는 마이그레이션 SQL을
  `jam-web/supabase/migrations/089_add_badges_background_video_url.sql`로 작성한다.
  기존 `background_image_url`은 **poster/폴백 이미지로 계속 사용**한다(영상 모드일 때도 채운다).
- **jam-developer는 이 SQL을 작성만 하고 절대 실행하지 않는다.** 실행은 오케스트레이터가
  사용자 승인 후 직접 처리한다 (`CLAUDE.md` 5번 항목).
- API 라우트(`badges` POST, `badges/[id]` PUT)와 `BadgeRow` 타입에 `background_video_url` 반영.
  세 배경 모드(단색 / 정적 제너레이터 / 애니메이션 제너레이터)가 상호 배타적으로 저장되도록
  나머지 필드는 null로 정리하는 기존 규칙을 이어간다.

### 유저단 재생 (서비스)
- 배경 레이어에 영상이 있으면 `<video>`로 재생한다. **iOS 자동재생 필수 속성**: `autoPlay`,
  `muted`, `loop`, `playsInline` (넷 다 없으면 iOS에서 재생 안 됨). `poster`에 정지 이미지 지정.
- **배경은 단일 레이어에만 적용한다** — 티켓 20260819_011에서 확정한 구조(430px 앱 컬럼 폭 고정
  레이어 한 곳)를 그대로 따른다. TopNav·Hero 카드에 중복 적용 금지.
  ※ 이 티켓은 **011 머지 이후에 착수**하므로, 011이 정리한 최신 구조 위에서 작업할 것.
- `getBadgeBackgroundStyle`은 CSS 스타일을 반환하는 순수 함수라 `<video>` 엘리먼트를 직접 만들 수
  없다. 영상 재생을 위한 별도 처리가 필요하며, 기존 호출부 계약을 어떻게 확장할지는 구현 시
  판단하되 **호출부가 늘어나지 않도록**(단일 레이어 원칙) 설계할 것.
- `pointerEvents: 'none'`(클릭 차단 회귀 방지)을 영상 레이어에도 유지한다.
- **접근성**: `prefers-reduced-motion: reduce`일 때는 영상을 재생하지 않고 poster 정지 이미지를
  보여준다.

### 어드민 UI
- 애니메이션 모드로 저장하면 영상으로 굽는다. 정적 패턴 모드는 기존대로 PNG만 굽는다.
- **"일시정지 = 배경 확정" 아이디어는 폐기 — 사용자 확인 완료**: 이 티켓 이전(정지 이미지만
  가능하던 시절)에 "일시정지 버튼을 누른 그 프레임이 최종 배경"이라는 결정이 있었으나, 영상
  굽기가 생기면서 무효가 됐다. **애니메이션 모드는 영상으로 굽고, 일시정지 버튼은 미리보기
  조작용으로만 사용한다** (2026-08-19 사용자 확정).
- 굽기·인코딩은 시간이 걸리므로 진행 상태를 사용자에게 표시한다(기존 `loading` state 활용 가능).

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

**① 인코딩 방식 선택 — WebCodecs `VideoEncoder` + `mp4-muxer`(채택)**

| 후보 | 판단 |
|---|---|
| `MediaRecorder` + `canvas.captureStream()` | **기각.** Chrome/Firefox 출력이 WebM(VP8/VP9)이라 iOS Safari 재생이 안 된다. 프레임레이트·비트레이트·키프레임 위치를 통제할 수 없어 "용량 최적화가 핵심"인 이번 요구사항과 맞지 않는다. |
| **WebCodecs `VideoEncoder` + `mp4-muxer`** | **채택.** H.264를 직접 인코딩해 MP4로 먹싱. 코덱 프로파일/레벨·프레임레이트·키프레임 위치를 전부 명시할 수 있고, 캡처한 프레임 배열의 순서를 바꿔 인코딩(왕복 루프)하는 것도 가능하다. 티켓 20260819_002의 이식 원본 리포가 쓰는 조합과 동일. 단점인 브라우저 지원 범위는 어드민 저작 도구라 수용 가능하며, 미지원 브라우저에는 안내 메시지를 띄운다. |

신규 의존성: `mp4-muxer@5.2.2` (MIT). Three.js는 추가하지 않았다.

**② 영상 굽기 유틸** — `bakeBackgroundVideo.ts` 신설. 기존 `bakePreviewToBlob`과 동일하게 **지금
미리보기에 보이는 노드를 그대로 캡처**한다(별도 오프스크린 렌더러 신규 작성 없음). 캡처 프레임에서
poster 정지 PNG도 함께 굽는다.

**③ 루프 이음매 — 왕복(ping-pong) 방식으로 해결**
kaleidoscope 오프셋은 `sin((counter/animationSpeed)*PI)*600`이고 counter는 프레임당 2씩 증가한다.
즉 한 주기 = `animationSpeed` 프레임인데, 기본값(speed 3, numTiles 5)에서 animationSpeed는 5333이라
60fps 기준 **한 주기가 약 89초**다. 2~4초 루프를 정현파 주기에 맞추는 것은 불가능하고, counter를
건너뛰어 한 주기를 압축하면 저작자가 지정한 애니메이션 속도가 결과물에 반영되지 않는다.
→ **실시간 속도 그대로 16프레임을 캡처한 뒤 끝점을 중복시키지 않고 되감아 붙인다**(0..15, 14..1 =
30프레임). 루프가 되감길 때 마지막 프레임(타일1) 다음이 첫 프레임(타일0)이라 정확히 한 프레임
분량만 진행하므로, 파라미터와 무관하게 항상 위치 점프가 없다. 실측으로 확인(아래 테스트 결과).

**④ 저장 경로** — 마이그레이션 SQL 작성(실행하지 않음), upload API 영상 허용, API 라우트·`BadgeRow`
타입에 `background_video_url` 반영, 3모드 상호 배타 정리 유지.

**④-1 게이트 리뷰 반영 — Storage 버킷 MIME 허용 + 용량 상한 정합 (2차)**
1차 게이트 리뷰에서 실제 `storage.buckets` 설정이 확인됐다:
`allowed_mime_types = [image/jpeg, image/jpg, image/png, image/webp, image/gif, image/svg+xml]`,
`file_size_limit = 5242880`(5MB). 이 상태로는 MP4 업로드가 API는 통과하고 Storage에서 거부돼
기능 전체가 동작하지 않는다. 두 가지를 수정했다.
- `090_allow_video_mime_in_images_bucket.sql` 신설 — `images` 버킷 `allowed_mime_types`에
  `video/mp4`만 추가(멱등: 이미 있으면 no-op). **작성만 하고 실행하지 않았다.**
- `file_size_limit`은 5MB **그대로 두고 API 상한을 낮췄다.** 실측 결과물 최대가 473KB라 5MB로
  충분하고, 버킷 상한을 올리면 이미지 업로드 경로의 상한까지 함께 느슨해진다(버킷 단위 설정이라
  영상만 따로 올릴 수 없음). `MAX_VIDEO_SIZE`를 20MB → `MAX_SIZE`(5MB)로 맞춰
  **API 상한 = 버킷 상한**이 되도록 했고, 안내 문구도 "영상 파일 크기는 5MB 이하여야 합니다."로
  수정했다. 이전에는 5~20MB 영상이 "20MB 이하" 안내를 통과한 뒤 Storage에서 거부되는 모순이 있었다.

**⑤ 유저단** — 20260819_011이 만든 단일 배경 레이어 **한 곳**에만 `<video autoplay muted loop
playsinline poster>`를 추가했다. 배경 적용 지점은 늘리지 않았다.

### 주요 의사결정 / 핵심 메모

1. **세로 반복은 CSS가 아니라 "굽는 시점"에 처리한다.** `background-repeat`는 `<video>`에 쓸 수
   없고, `<video>`를 여러 개 쌓으면 서로 위상이 어긋나고 모바일 동시 재생 제약도 걸린다. 그래서
   프레임을 세로로 2장 이어붙여 430×860으로 굽고, 유저단은 `width:100%; height:auto`만 주면
   원본 비율(1:2)이 그대로 유지된다 — 20260819_011의 `backgroundSize:'100% auto'` + repeat와
   같은 그림이 된다.
2. **poster는 CSS 배경으로도 계속 깔아둔다.** `<video poster>`와 별개로 레이어의
   `background-image`(= `background_image_url`)를 유지해서, ① 영상 로드 전 첫 페인트 ② 로드 실패
   폴백 ③ `prefers-reduced-motion` 대체 ④ 영상 높이(860px)를 넘는 아래쪽을 전부 같은 정지
   이미지가 받아준다. 그래서 영상 모드에서도 `background_image_url`을 항상 함께 저장한다.
3. **`prefers-reduced-motion`은 JS 없이 CSS로 처리했다.** `globals.css`의
   `.badge-background-video { display: none }` 한 줄. 서버 컴포넌트/하이드레이션 불일치·깜빡임이
   없고, 영상만 사라지고 poster가 그대로 보인다.
   **(3차 수정) 이 방식을 쓰려면 `display`를 인라인 style에 두면 안 된다** — 인라인 선언이 항상
   스타일시트를 이겨 규칙이 통째로 무력화된다. `display: block`도 같은 클래스로 옮겼다.
4. **일시정지 버튼은 결과물에 영향을 주지 않는다.** 사용자가 일시정지해 둔 상태로 저장하면 정지
   화면만 녹화되므로, 굽는 동안에는 `forcePlay`로 엔진을 강제 재생한다(2026-08-19 확정 사항 반영).
5. **미리보기 스냅샷 간격을 굽는 동안만 낮춘다.** 기존 파이프라인은 400ms(=2.5fps) 스로틀링이라
   그대로 녹화하면 뚝뚝 끊긴다. `snapshotIntervalMs` prop을 추가해 굽는 동안만 66ms(15fps)로
   낮추고, 평소 미리보기 동작은 기존 그대로 유지했다.
6. **정적 패턴 모드는 건드리지 않았다** — 기존대로 PNG 1장만 굽는다.
7. `getBadgeBackgroundStyle`은 CSS 반환 순수 함수 그대로 두고, "영상을 틀어야 하는가" 판단만
   `getBadgeBackgroundVideoUrl`로 분리했다. 엘리먼트 생성은 단일 배경 레이어가 담당 —
   **호출부는 늘지 않았다.**
