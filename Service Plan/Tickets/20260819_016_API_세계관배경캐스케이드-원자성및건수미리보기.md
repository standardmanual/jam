# [API] 세계관 배경 캐스케이드 — 원자성 확보 + 서버 건수 미리보기

## 배경 / 문제 정의

티켓 015(세계관 배경 일괄 적용 3단 캐스케이드) 개선 리뷰에서 지적된 두 항목을 해결한다:

1. **원자성 없음**: `/api/admin/factions/[id]/apply-background`가 (a) 직속 배지 →
   (b) 소속 컬렉션 → (c) 그 컬렉션의 아이템배지 순으로 **3개의 개별 Supabase update 호출**을
   순차 실행한다. 트랜잭션이 없어 중간 단계(예: (b) 성공, (c) 실패)에서 멈추면 부분 적용된
   상태로 남는다 — 재시도 전까지 데이터가 일관되지 않은 중간 상태가 된다.
2. **건수 미리보기 비효율**: `FactionForm.tsx`의 일괄 적용 확인 다이얼로그가 `/api/admin/badges`,
   `/api/admin/itembooks` **전체 목록**을 fetch해 클라이언트에서 필터링·집계해 예상 건수를
   계산한다. 배지·컬렉션 수가 늘어나면 다이얼로그를 열 때마다 불필요하게 느려진다.

## 상세 요구사항

### 서비스/코드베이스 관점

1. **원자성**: 3단 캐스케이드를 단일 Postgres 함수(plpgsql RPC)로 옮긴다. 하나의 함수 호출은
   기본적으로 원자적 트랜잭션이므로, 함수 내부에서 (a)→(b)→(c) 순서로 UPDATE를 실행하고 각
   단계의 적용 건수를 반환하게 하면 별도 트랜잭션 제어 코드 없이 all-or-nothing이 보장된다.
   - 함수명 예: `apply_faction_background_cascade(p_faction_id uuid)` — 리턴 타입은
     `TABLE(direct_badges int, item_books int, item_book_badges int)` 또는 단일 row/JSON,
     구현 편한 쪽으로.
   - `/api/admin/factions/[id]/apply-background/route.ts`는 이 함수를 `supabase.rpc(...)`로
     호출하는 얇은 래�퍼로 단순화한다. 응답 형식(`directBadges`/`itemBooks`/`itemBookBadges`/
     `appliedCount`)은 기존 그대로 유지 — `FactionForm.tsx` 쪽 변경 불필요.
   - 마이그레이션 SQL 파일만 작성한다 (`jam-web/supabase/migrations/0XX_...sql`).
     **실행하지 않는다** — 오케스트레이터가 사용자 승인 후 직접 실행.
   - 컬렉션(item_book) 단위 일괄 적용은 이미 단일 UPDATE 문 하나뿐이라 원자성 문제가 없다 —
     이번 범위에서 손댈 필요 없음.

2. **건수 미리보기**: 확인 다이얼로그가 열릴 때 실제 적용 전에 예상 건수만 가볍게 조회하는
   경로를 만든다. 두 가지 방식 중 구현하기 적절한 쪽으로 판단해서 진행:
   - (A) 위 1번 함수와 짝을 이루는 카운트 전용 함수(`count_faction_background_cascade` 등,
     UPDATE 없이 SELECT COUNT만)를 만들고 별도 GET 라우트로 노출, 또는
   - (B) `/api/admin/factions/[id]/apply-background`에 `?dryRun=true` 같은 조회 전용 모드를
     추가해 같은 라우트가 카운트만 반환하도록.
   - 어느 쪽이든 **전체 배지/컬렉션 목록을 클라이언트로 내려보내지 않고**, 서버에서 3단 조건과
     동일한 `WHERE` 절로 `COUNT`만 계산해 가벼운 응답(`{ directBadges, itemBooks,
     itemBookBadges }`)만 반환해야 한다.
   - `FactionForm.tsx`의 `handleBulkApplyClick`이 `/api/admin/badges`·`/api/admin/itembooks`
     전체 목록을 fetch하던 부분을 이 새 미리보기 경로 호출로 교체한다.
   - 미리보기 건수와 실제 적용 후 건수(서버 응답)가 다를 수 있음(동시 편집 등)을 감안해,
     기존처럼 "결과 배너의 건수가 최종 진실값"이라는 원칙은 유지한다.

### UI/UX 관점

- 어드민 화면 — MODULAR 적용 대상 아님.
- 다이얼로그 문구·동작은 티켓 015에서 확정된 형태를 유지, 건수 계산 경로만 바뀐다
  (사용자가 보는 결과는 동일해야 함 — 회귀 없음).

## 구현 계획

1. 3단 캐스케이드용 plpgsql 함수 작성 (마이그레이션 SQL, 미실행)
2. `apply-background/route.ts`를 RPC 호출로 단순화
3. 건수 미리보기 경로 구현 (함수 또는 dryRun 방식 택1)
4. `FactionForm.tsx`의 확인 다이얼로그가 새 미리보기 경로를 쓰도록 교체
5. 기존 동작(적용 결과 배너 건수, 항상 덮어쓰기, 화면 문구) 회귀 없는지 확인

### 구현 내용 요약
1. 마이그레이션 092에 plpgsql 함수 2개 작성: `apply_faction_background_cascade(p_faction_id uuid)`
   (기존 3단 UPDATE를 단일 함수 호출로 묶어 all-or-nothing 보장) / `count_faction_background_cascade
   (p_faction_id uuid)` (동일 WHERE 조건으로 UPDATE 없이 COUNT만 반환).
2. `apply-background/route.ts`의 POST가 3개 개별 update 대신 `supabase.rpc('apply_faction_
   background_cascade', ...)` 한 번만 호출하도록 단순화. 응답 형식(`directBadges`/`itemBooks`/
   `itemBookBadges`/`appliedCount`)은 그대로 유지.
3. 같은 라우트에 GET 핸들러를 추가해 `count_faction_background_cascade`를 호출하는 가벼운 미리보기
   경로로 노출(옵션 B가 아니라 옵션 A를 같은 파일에 결합한 형태 — 별도 GET 라우트).
4. `FactionForm.tsx`의 `handleBulkApplyClick`이 `/api/admin/badges`·`/api/admin/itembooks` 전체
   목록 fetch + 클라이언트 필터링을 제거하고, 새 GET 미리보기 경로 한 번만 호출하도록 교체.

- 건수 미리보기는 티켓의 (A)/(B) 중 "카운트 전용 함수 + 별도 GET 라우트"를 택하되, 별도 파일이

- RPC 응답 필드명(`direct_badges` 등 snake_case)을 라우트에서 기존 camelCase 응답 형식으로
  변환해 `FactionForm.tsx` 쪽 코드는 전혀 손대지 않아도 되게 했다(POST 기준). GET도 동일 규칙.
