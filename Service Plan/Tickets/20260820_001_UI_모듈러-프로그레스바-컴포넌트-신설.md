# [UI] MODULAR 프로그레스바 컴포넌트 신설 (3종 패턴)

## 배경 / 문제 정의

서비스 곳곳에서 진행도 바(progress bar)를 이미 쓰고 있지만 MODULAR 디자인 시스템에는
등록돼 있지 않다 — `_ds_manifest.json`의 22개 컴포넌트 중 progress bar 계열이 전혀 없다.
그 결과 6곳의 실사용처가 각자 따로 구현되며 색상·높이·구현 방식이 파편화됐다:

| 위치 | 트랙 배경 | 필 색상 | height | 부가정보 |
|---|---|---|---|---|
| `ItemBookHeroSection.tsx` (컬렉션 상세) | `#FFFFFF` 하드코딩 | `#E8461F` 하드코딩 | 8px | n/n |
| `CollectionGridCard.tsx` | `bg-white/20` | `bg-[#E8461F]` 하드코딩 | 6px | n/n |
| `[username]/itembooks/page.tsx` | `bg-black/[0.08]` | `bg-text-inverse` | 6px | n/n |
| `MissionDetailClient.tsx` | `bg-border`(토큰) | `var(--color-primary)`(토큰) | 8px, radius 토큰 | %+n/n |
| `inventory/page.tsx` | `bg-border`(토큰) | `bg-text` | 6px | 바 밑 문장 |
| `MissionStatusClient.tsx` | `var(--color-surface-elevated)`(토큰) | 순위별 그라데이션 | 6px, radius 3px | 없음 |

`#E8461F`은 `--color-primary`(`--color-base-red`)의 실제 값과 정확히 일치한다 — 즉 별개의
색이 아니라 **토큰 변수 참조 대신 값을 그대로 박아넣은 것**이다. `MissionDetailClient`만
토큰(`var(--color-primary)`, `bg-border`, `var(--radius-pill)`)을 올바르게 참조한다.

## 상세 요구사항

### 서비스/코드베이스 관점

1. **신규 컴포넌트 `ProgressBar`를 MODULAR에 추가**한다. 위치는 새 그룹
   `design-system/components/indicators/`(또는 `feedback/` 그룹에 편입 — 기존 6개 그룹
   구성과 비교해 더 적절한 쪽으로 판단) 아래, 기존 `RarityBadge` 패턴(4파일 세트)을 그대로
   따른다:
   - `ProgressBar.jsx` — 순수 함수형, 인라인 `style`에서 `var(--token-name)` 직접 참조
   - `ProgressBar.d.ts` — Props 타입 선언
   - `ProgressBar.prompt.md` — 설명 + 최소 사용 예시
   - `ProgressBar.stories.tsx` — `title: 'MODULAR/{그룹}/ProgressBar'`, variant별 Story +
     전체 모아보기 Story + 실사용 맥락 Story
   - `_ds_manifest.json`의 `components` 배열과 `readme.md` 색인 양쪽에 등록

2. **디자인 토큰 통일**: 위 표의 파편화된 값들을 캐노니컬 스펙 하나로 정리한다.
   `MissionDetailClient`가 유일하게 토큰을 올바르게 쓰고 있으므로 이를 기준으로:
   - 트랙: `var(--color-border)` (다크 테마 실값 `--color-base-grey-700`)
   - 필: `var(--color-primary)` 기본값, prop으로 색상 오버라이드 가능(순위 그라데이션 등
     예외 케이스 대응)
   - radius: `var(--radius-pill)`
   - height: prop으로 노출(기본값은 실사용 최빈값인 8px 또는 6px 중 적절한 쪽 — 실제
     사용처 비율 참고해서 결정)
   - `tokens/colors.css`(원본)를 기준으로 삼을 것 — `_ds_manifest.json`에 스냅샷된 토큰
     값은 최신이 아닐 수 있음(조사 중 `--color-text-secondary` 불일치 확인됨)

3. **3종 패턴화**: 요청하신 3개 변형을 `ProgressBar` 하나의 컴포넌트 API로 구현한다
   (컴포넌트를 3개 따로 만들지 않고, prop 조합으로 표현하는 쪽을 우선 검토 — 예:
   `labelType?: 'none' | 'percent' | 'fraction'`, `current`/`total` 또는 `percent` prop):
   - **①프로그래스바 단독** — 바만, 부가 텍스트 없음 (`MissionStatusClient` 케이스에 해당)
   - **②프로그래스바 + 숫자(%)** — 바 옆/위에 퍼센트 숫자
   - **③프로그래스바 + n/n** — 바 옆에 `현재/전체` 형태 (`ItemBookHeroSection`,
     `CollectionGridCard`, `[username]/itembooks` 케이스에 해당)
   - Storybook에 3개 변형을 각각의 Story로, 실제 서비스에서 쓰이는 실측값(예: 컬렉션
     3/10, 미션 진행 60% 등)을 예시 데이터로 사용할 것 — "현재 서비스 값을 활용"이라는
     요청 그대로.

4. **기존 서비스 호출부 마이그레이션 여부**: 이번 티켓의 필수 범위는 **컴포넌트 신설**이다.
   6개 실사용처를 전부 이 컴포넌트로 교체하는 것은 이번 범위에 포함하지 않아도 된다 —
   다만 회귀 없이 안전하게 교체 가능한 곳(특히 `MissionDetailClient`처럼 이미 토큰을 쓰고
   있어 마이그레이션 리스크가 낮은 곳)이 있다면 함께 교체해도 좋다. 전부 교체하지 않을
   경우 완료 기록에 "남은 호출부 목록"을 명시할 것 — 후속 정리 작업의 근거가 되도록.

### UI/UX 관점

- MODULAR 컴포넌트이므로 다크 테마 기준(서비스가 다크 전용)으로 대비 확인.
- 신규 사용자 노출 문구는 없음(퍼센트/n/n은 데이터값이지 UX 라이팅 대상 문구가 아님).

### 주요 의사결정 / 핵심 메모
- 3종 패턴을 컴포넌트 3개가 아닌 `labelType` prop 조합 하나로 구현 (티켓 권고안 채택).
- height 기본값 8px 채택: 6개 실사용처 중 8px(ItemBookHeroSection, MissionDetailClient×2회 사용
  패턴) vs 6px(CollectionGridCard, itembooks/page, inventory/page, MissionStatusClient) —
  단순 빈도로는 6px 우세이나, 토큰을 올바르게 참조하는 유일한 캐노니컬 소스인
  `MissionDetailClient`가 8px을 쓰고 있어 이를 기본값으로 채택. 6px이 필요한 호출부는
  `height={6}`으로 오버라이드하면 된다.
- **기존 호출부 마이그레이션은 이번 티켓 범위에서 수행하지 않았다.** 사유: 코드베이스
  전수조사 결과 `tsconfig.json`에 `@ds/*` alias가 이미 설정돼 있음에도 `src/` 어디에서도
  design-system 컴포넌트를 실제로 import하는 곳이 **단 한 곳도 없었다**(`grep -rl '@ds/' src/`
  결과 0건). 즉 MODULAR는 현재 Storybook 카탈로그로만 존재하고 프로덕션 코드와 아직 연결된
  전례가 없다. `MissionDetailClient.tsx`가 이미 토큰을 올바르게 쓰고 있어 회귀 위험은 낮지만,
  "최초의 design-system → 서비스 코드 연결"이라는 구조적 결정은 이번 티켓 범위(컴포넌트 신설)를
  벗어난다고 판단해 보류했다. 아래 alerts에도 별도 기재.
