## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

1. **Checkbox/Input/Select/Textarea** (`design-system/components/forms/`, 서비스 전체 import 0건):
   **유지 — 삭제하지 않음.** 사용자 결정: "향후 해당 컴포넌트를 사용할 수 있다"는 이유로 Storybook
   카탈로그에 그대로 둔다. 죽은 코드이지만 향후 실제 폼 화면이 생길 때 재사용할 잠재 자산으로 보존.
   추가 조치 없음 — 재조사 시점은 실제 폼 UI 도입 티켓이 생길 때.

2. **ModalToast/ShapeTag/BadgeFrame** (서비스에 대응 개념 자체 없음):
   **유지 — 도입 보류.** 사용자 결정: "유지함 추후 사용 예정". 지금 서비스 화면을 이 컴포넌트에
   맞춰 억지로 만들 이유가 없다는 판단. Storybook 카탈로그에만 존재하는 상태 유지.

3. **Skeleton** (`design-system/components/feedback/Skeleton.jsx` ↔ 서비스
   `transitions.css`/`transitions-pages.css`의 `.t-skel-*` 클래스 체계 + `useSkeletonReveal` 훅):
   **이번엔 보류.** 조사 결과 DS는 단일 shimmer 컴포넌트인 반면, 서비스는 cross-fade reveal
   (`--pulse-dur`, `--pulse-min` 등 자체 CSS 변수 세트, 설계 문서 `14-skeleton-reveal.md` 기반)
   + pulse 2단 애니메이션 구조로 **DS보다 오히려 더 정교한 독자 시스템**이다. 단순 스왑 시
   reveal 트랜지션 기능이 소실되므로, 전환하려면 DS Skeleton 자체를 서비스 구조에 맞게
   재설계해야 한다 — 이번 라운드 범위에서 제외, 별도 설계 티켓 필요 시 착수.
