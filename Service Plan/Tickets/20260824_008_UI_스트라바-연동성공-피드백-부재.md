# [UI] Strava 연동 성공 피드백이 사용자에게 전달되지 않는다

> 티켓 20260823_008·20260824_003 게이트 리뷰에서 반복 확인. 범위 밖이라 미뤄둔 사안.

## 배경 / 문제 정의

`/api/strava/callback`은 연동 성공 시 `?strava=connected` 파라미터를 붙여 리다이렉트한다.

**그런데 이 파라미터를 읽는 화면이 하나도 없다** (전수 확인 완료).

게다가 `/profile`은 `/{username}`으로 넘길 때 `reveal`만 다시 싣고 `strava`는 버린다
(20260824_003 이전에도 버렸으므로 회귀는 아니다).

### 사용자가 겪는 것

| 상황 | 현재 피드백 |
|---|---|
| 연동 성공 + 배지 획득 | 획득 연출 캐러셀 (20260824_003) ✅ |
| **연동 성공 + 배지 0개** | **아무것도 없음** 🔴 |
| 연동 실패 | `?strava=error&reason=...` — 이것도 읽는 화면 없음 🔴 |

배지 0개는 드문 경우가 아니다. 첫 동기화는 최신 활동 1건만 처리하므로
(`sync.ts`의 백필 폭주 방지), 그 활동으로 배지가 안 나오면 **연동했는데 화면이
그대로**다. 사용자는 연동이 됐는지 알 수 없다.

연동 상태 자체는 프로필의 Strava 연동 UI에 반영되지만, **그 화면으로 갔다는 것과
"방금 연동에 성공했다"는 것은 다른 정보**다.

## 상세 요구사항

### 서비스/코드베이스 관점

- `?strava=connected` / `?strava=error&reason=...`를 도착 화면에서 소비해 피드백을 준다
- `/profile` → `/{username}` 리다이렉트에서 파라미터가 유실되지 않게 한다
  (20260824_003이 `reveal`에 대해 이미 같은 처리를 했으므로 그 패턴을 따른다)
- 피드백 표시 후 URL에서 파라미터를 제거한다 — 새로고침·뒤로가기로 다시 뜨면 안 된다
  (`StravaConnectReveal`의 `router.replace` 패턴 참고)
- **획득 연출과 겹치지 않게** 한다. 배지가 있으면 캐러셀이 뜨므로 토스트까지 겹치면 과하다.
  배지 0개일 때만 연동 성공 피드백을 보여주는 쪽이 자연스럽다

### UI/UX 관점

- 기존 `Toast`로 충분한지, 더 강한 표현이 필요한지 판단한다.
  최초 연동은 사용자당 한 번뿐인 순간이라 토스트가 가벼울 수 있다
- 실패 케이스는 `reason`별로 다른 안내가 필요한지 확인한다
  (현재 `reason=server_error` 등이 붙는다)

### UX Writing

- 에러 메시지는 **[현상] → [원인] → [해결책] 3단계** 구조를 따른다
  (`Service Plan/Specs/UX_WRITING_GUIDELINE.md`)
- "연동" 용어가 용어표에 등재돼 있는지 확인한다

## 구현 계획

1. `?strava=` 파라미터의 전체 값 종류 확인 (`callback/route.ts`)
2. 도착 화면에서 소비 + URL 정리
3. 배지 획득 연출과의 우선순위 정리 (배지 0개일 때만 노출)
4. 실패 케이스 안내 문구 작성 (3단계 구조)
5. 실측 검증 — 연동 성공/실패 각각

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- `StravaConnectReveal`(20260824_003이 만든, `?reveal=1` 도착 화면 피드백 컴포넌트)을
  확장해 `?strava=connected|error&reason=...`를 소비하도록 했다.
  - 성공 + 배지 0개: 기존 `reveal` 이펙트의 "배지 없음" 분기에 성공 토스트를 추가.
    배지가 있으면(캐러셀이 뜨면) 토스트를 띄우지 않는다.
  - 실패(`strava=error`): 별도 이펙트로 `reason`을 읽어 토스트를 띄운다. `access_denied`
    (사용자가 Strava 인가 화면에서 직접 거부)는 "취소" 톤으로, 나머지 기술적 사유
    (`missing_params`/`token_exchange`/`db_error`/`server_error`)는 "다시 시도" 안내
    하나로 묶었다 — 사용자가 취할 행동이 동일해서다.
  - 두 경우 모두 토스트 노출과 동시에 `router.replace`로 URL에서 파라미터를 지워
    새로고침·뒤로가기 재노출을 막는다 (기존 `reveal` 처리와 동일 패턴).
  - `/profile → /{username}` 리다이렉트가 `reveal`만 넘기고 `strava`/`reason`은
    버리던 문제를 수정 — `URLSearchParams`로 세 파라미터를 함께 전달한다.
- **구현 중 발견한 레이스 컨디션을 함께 수정**: `router.replace()` 직후 호출하는
  `setPhase('loading')`의 커밋이 그 replace가 만든 트랜지션에 밀려 수백 ms 지연될 수
  있었다(useSearchParams + Suspense 조합 특성). `/api/badges/recent-earned` 응답이 그보다
  먼저 도착하면 "취소 여부" 판정에 쓰던 `phaseRef`(= phase state를 effect로 미러링한 값)가
  아직 'idle'이라 정상 응답을 취소된 것으로 오판, 배지 캐러셀도 토스트도 뜨지 않는 문제가
  있었다. React 렌더와 무관하게 동기로 갱신되는 `cancelledRef`로 판정 기준을 바꿔 제거했다
  (Escape 키 핸들러에서만 `true`로 세팅). 이 레이스는 20260824_003의 캐러셀 경로도 동일하게
  영향을 받고 있었다 — 이번 수정으로 함께 해결됨.

### 게이트 WARN 2건 대응 (오케스트레이터, 머지 전)

**WARN A — Escape 레이스 컨디션.** Escape 리스너가 `phase==='loading'` 게이트로 별도
이펙트에 등록됐는데, 그 `phase` 커밋이 `router.replace()` 트랜지션에 밀려 지연되는
구간(관측 ~470ms)에서는 리스너가 아직 없어 Escape가 무시됐다. 개발자가 "근본 원인을
제거했다"고 주장한 `cancelledRef` 교체는 판정 시점의 취소 여부만 고쳤을 뿐, 리스너
등록 자체가 늦는 문제는 그대로 남아 있었다(게이트가 정확히 재현).

`listeningRef`를 추가해 구조를 바꿨다 — 이 ref는 `setPhase('loading')`과 같은 동기
블록에서 즉시 `true`가 되므로 React 렌더 커밋을 기다리지 않는다. Escape 리스너는
마운트 시 한 번만 등록(빈 deps)하고, keydown마다 `listeningRef.current`를 그 자리에서
읽어 판정한다.

브라우저 자동화로 로그 타임스탬프를 직접 찍어 확인했다: `listeningRef=true`는 페이지
마운트 직후(~900ms) 동기 확정되고, 토스트 호출은 그보다 한참 뒤(~2.4초)에야 일어난다
— 그 사이 전 구간이 취소 가능 구간이다. **밀리초 단위 사전-커밋 구간 자체를 자동화
도구로 안정 재현하지는 못했다** — 도구의 키 입력 전달 지연이 수백ms~수초로 들쭉날쭉해
그 자체가 측정 잡음이 됐다(디버그 로그로 실제 원인을 특정: 자동화 도구가 `navigate`
직후 페이지에 실제 포커스를 못 주는 경우가 있었다). 다만 코드가 React 커밋 타이밍에
대한 의존을 아예 제거했다는 점에서 **구조적으로 해결됐다**고 판단했다.

**WARN B — 실패 토스트 3단계 구조.** `stravaConnectFailedToast`에 원인절을 추가해
[현상]→[원인]→[해결책]에 맞췄다. `UX_WRITING_GUIDELINE.md`의 정확히 같은 시나리오
예시("Strava 동기화가 끊겼어요. 비밀번호를 바꾸셨거나...")를 참고하되, 이 티켓의
케이스(최초 연결 실패로 missing_params/token_exchange/db_error/server_error 등
기술적 원인 통합)에 맞는 문구로 조정했다: "Strava 동기화에 실패했어요. 네트워크가
불안정했거나 일시적인 오류일 수 있어요. 잠시 후 다시 시도해주세요."
