# [Infra] 알림(소식) 스키마 + T1 인라인 생성

## 배경 / 문제 정의

[20260824_018](20260824_018_Feature_알림소식-PRD수립.md)에서 수립한 알림(소식) 기능의
**첫 번째 구현 티켓**이다. 스펙은 [Specs/PRD/Notification/](../Specs/PRD/Notification/)에 있다.

이 티켓은 **데이터 기반과 인라인 생성 경로**를 만든다. 화면(020)과 배치(021)는 후속이다.

> **읽기 전 필독**
> - [PRD.md](../Specs/PRD/Notification/PRD.md) — 소식 28종 정의, §4 생성 트리거
> - [DATA_MODEL.md](../Specs/PRD/Notification/DATA_MODEL.md) — 스키마 전문

## 상세 요구사항

### 1. DB 스키마 — SQL 파일 작성만, 실행 금지

`db` 유형 규칙에 따라 **마이그레이션 SQL 파일을 작성하는 데까지만** 한다. 실행은 승인 후
오케스트레이터가 처리한다. 파일 경로: `jam-web/supabase/migrations/0XX_notifications.sql`
(`0XX` = 기존 최대 번호 +1. **현재 최대는 095**이며, 094가 두 개로 중복된 이력이 있으니
번호 확인 시 주의할 것)

DDL 전문은 [DATA_MODEL.md](../Specs/PRD/Notification/DATA_MODEL.md) §2·§2-1·§3에 있다.
그대로 옮기되, 다음을 반드시 지킨다.

- `notification_type` ENUM **28값** — PRD §3의 28종과 1:1 대응해야 한다
- `notifications` 테이블 + 인덱스 2개(부분 UNIQUE `group_key`, `user_id, updated_at DESC`)
- **RLS**: SELECT는 본인만(`auth.uid() = user_id`). INSERT/UPDATE 정책은 열지 않는다
  (쓰기는 `service_role` 전용)
- `users.notifications_seen_at TIMESTAMPTZ` 컬럼 추가
- `poi_views` 테이블 + 인덱스 2개 (#18 계측용)
- `updated_at` 자동 갱신 트리거가 필요한지 판단할 것 — UPSERT에서 명시적으로 `NOW()`를 넣으므로
  트리거 없이도 동작하지만, 다른 경로의 UPDATE를 대비할지는 구현자 판단

### 2. 알림 생성 라이브러리

`jam-web/src/lib/notifications/` 신설. 다른 코드가 한 줄로 소식을 남길 수 있어야 한다.

**핵심 요구사항**

- **UPSERT 병합** — `group_key`가 있으면 `ON CONFLICT (user_id, group_key) DO UPDATE`로
  `actor_count` 증가 + `updated_at = NOW()`. DATA_MODEL §4의 쿼리 참고.
  `group_key`가 NULL이면 항상 새 행.
- **`group_key` 시간창은 KST 기준** — `points:{YYYY-MM-DD}` 같은 일 단위 키를 UTC로 계산하면
  KST 09:00에 날짜가 바뀐다. 티켓 [20260824_006](20260824_006_bug_피드-event_at-로컬벽시계-UTC오해석.md)에서
  `event_at`을 로컬 벽시계로 오해석한 전례가 있으니 **시간대 처리를 특히 조심할 것**
- **`bumps_badge`는 type에서 파생** — ①보상 획득 6종(`badge_earned`·`rare_badge_earned`·
  `item_badge_earned`·`poi_badge_earned`·`points_earned`·`first_badge`)만 `false`.
  호출부가 매번 넘기게 하지 말고 **type → bumps_badge 매핑을 라이브러리 안에** 둘 것
- **닉네임을 `payload`에 박제하지 말 것** — `actor_user_id`로 조인해 렌더 시점에 읽는다.
  유저가 닉네임을 바꾸면 과거 소식도 따라와야 한다
- **소식 생성 실패가 본 트랜잭션을 깨뜨리면 안 된다** — 배지 발급이나 픽업이 알림 INSERT
  실패로 롤백되는 건 본말전도다. 실패는 삼키되 **반드시 `console.error`로 로그를 남길 것**
  (조용한 실패는 이 프로젝트의 기존 구조적 이슈이므로 새로 만들지 말 것)

### 3-1. ⚠️ 추가 요구 — `actor_count`를 고유 인원으로 (2026-08-24 추가)

**1차 구현 리뷰에서 020이 막힐 문제가 드러나 스키마를 보강한다.** DDL을 아직 실행하지 않은
지금이 가장 싼 시점이다.

**문제**: PRD §3이 요구하는 L2 규칙("2명까지 이름 나열 → 3명+ 축약")을 구현하려면 묶음에 속한
행위자를 2명 이상 알아야 하는데, 저장되는 건 `actor_user_id` 1개(최신)와 `actor_count`뿐이다.
게다가 현재 `actor_count`는 merge마다 무조건 +1이라 **인원이 아니라 병합 횟수**다 — 한 사람이
6시간 안에 내 드랍 3건을 픽업하면 `actor_count=3`인데 실제 인원은 1명이라 "예린님 외 2명"이라는
거짓말이 된다.

**해결** — 상세는 [DATA_MODEL.md](../Specs/PRD/Notification/DATA_MODEL.md) §4·§4-1

1. `create_notification()`에 **`p_append_keys TEXT[]`** 모드 추가 — payload의 지정 키를
   배열로 이어붙이고 **중복 제거**한다
2. 행위자가 있는 묶음 소식은 `payload.actor_ids`를 누적하고,
   **`actor_count = jsonb_array_length(payload->'actor_ids')`**(중복 제거 후)로 갱신한다
3. 적용 대상:

   | 소식 | `append_keys` |
   |---|---|
   | 13 픽업됨 | `actor_ids`, `badge_ids` |
   | 26 팔로우 | `actor_ids` |
   | 31 팔로잉 미션 완료 (021에서 사용) | `actor_ids` |

4. 행위자가 없는 묶음 소식(1·3·4·5·34)은 `actor_ids`를 쓰지 않는다. 개수는 payload 배열 길이나
   `sum_keys` 합산값으로 렌더한다
5. **#13의 `badge_ids`도 append여야 한다** — 현재 `payload: { badge_id, badge_name, poi_id }`는
   얕은 병합이라 6시간 창에서 직전 픽업 배지가 덮어써진다

### 3-2. 그 밖의 보완

- **`create_notification()`·`jsonb_merge_sum()`에 `SET search_path = public` 추가** —
  080 `award_points`·092 선례. Supabase 린터의 `function_search_path_mutable` 대상
- **`kstDateString()`에 Invalid Date 가드** — `Number.isNaN(d.getTime())` 한 줄.
  현재는 잘못된 입력이 `NaN-NaN-NaN`을 만들어 DB DATE 파싱 에러로 넘어간다
- **`096_notifications.sql` 헤더에 실행 순서 제약 블록 추가** — 095의 형식을 따를 것.
  **이번엔 방향이 반대다: DDL 먼저 → 코드 배포.** 역순이면 테이블·RPC가 404라 소식 생성이
  전부 no-op이 되면서 `console.error`만 쌓이는 무증상 상태가 된다. 롤백 DDL도 함께 명시
- **`@ts-expect-error` 2곳** (`index.ts:79`·`:132`) — 오류가 사라지면 그 줄 자체가 컴파일
  오류가 된다. 주석으로 의도를 남기거나 타입을 맞출 것

### 2차 보강 (2026-08-24, §3-1·§3-2)

게이트 리뷰 WARN을 받아 **1차 구현 위에 보강**했다. 다시 만들지 않았다.

1. **`actor_count`를 고유 인원으로** — `create_notification()`에 `p_append_keys TEXT[]` 추가.
   payload의 지정 키를 배열로 이어붙이고 **중복 제거**한 뒤
   `actor_count = jsonb_array_length(payload->'actor_ids')`로 갱신한다.
   - #13 픽업됨: `append_keys = [actor_ids, badge_ids]` — badge_ids가 얕은 병합이라
     6시간 창에서 직전 배지가 덮어써지던 문제도 함께 해소
   - #26 팔로우: `append_keys = [actor_ids]`
   - 행위자가 없는 묶음(#1·#3·#4)은 `actor_ids`를 쓰지 않고 `actor_count`도 건드리지 않는다.
     다만 DATA_MODEL §6의 "배열 필드는 append로 누적한다"에 따라 `badge_ids`·`poi_names`·
     `inventory_item_ids`는 `append_keys`에 넣었다(개수 렌더의 근거가 배열 길이이므로).
2. **`SET search_path = public`** — `create_notification()`·`jsonb_merge_sum()`·
   신규 `jsonb_as_array()` 전부. Supabase 린터 `function_search_path_mutable` 대상.
3. **`kstDateString()` Invalid Date 가드** — `Number.isNaN(d.getTime())`이면 현재 시각으로
   대체하고 `console.error`. 던지지 않는 이유는 키 빌더가 `createNotification()` 인자
   위치(호출부 try 바깥)에서 평가되기 때문이다. `recordPoiView`의 `viewed_at`도 같은 가드를 탄다.
4. **`096_notifications.sql` 헤더에 실행 순서 제약 + 롤백 DDL** — 095와 **방향이 반대**(DDL 먼저
   → 코드 배포)임을 명시했다.
5. **`@ts-expect-error` 2곳 제거** — 원인이 사라지면 그 줄 자체가 컴파일 오류가 되므로,
   `CreateNotificationArgs`·`PoiViewRow`로 좁힌 로컬 타입 캐스팅으로 바꿨다(인자는 계속 타입 검사됨).
6. **검증 스크립트 신설** — `supabase/tests/096_notifications_merge.test.sql`
   (BEGIN…ROLLBACK, ASSERT 기반. append 중복 제거·actor_count 고유 인원·badge_ids 누적·sum·once)

### 3차 수정 (2026-08-24, 게이트 리뷰 FAIL 2건)

1차·2차 구현 위에 **FAIL 2건만** 고쳤다. 통과 판정된 부분(p_append_keys 병합, actor_count
고유 인원, #13 badge_ids 누적, KST·키 규칙·mode='once'·bumps_badge 파생·실패 격리·RLS·T1 14개
지점, SQL 헤더의 실행 순서 제약과 롤백 DDL)은 손대지 않았다.

**FAIL 1 — #5(포인트 적립)가 개정된 PRD와 어긋났다**

PRD가 커밋 `47456141`에서 #5의 트리거를 「`badge_point_reward` 중 **미션 보상 경유가 아닌 것**」
으로 좁혔는데 2차 보강이 이를 반영하지 못했다. `grantMissionRewards()`가 미션 보상 배지의
포인트도 같은 reason으로 지급하므로, 미션 1건 완료가 #5·#22 **두 줄**로 보이고 #5의 하루 합계
금액(`sumKeys:['amount']`)까지 부풀려지는 상태였다.

- `missions/rewards.ts` — 배지 포인트 지급 시 `awardPoints()`에 **`sourceMissionId`를 함께 전달**
- `points/index.ts` `notifyPointChange()` — `reason === 'badge_point_reward' && amount > 0 &&
  **!options.sourceMissionId**`일 때만 #5를 만든다

`skipNotification` 같은 전용 옵션 대신 이 방식을 택한 이유: 미션 보상 배지의 포인트가
`point_transactions` 원장에서 **미션 귀속을 잃고 있던 범위 밖 정합성 문제**를 함께 해소한다
(리뷰어 권장안). `reason`은 `badge_point_reward` 그대로라 `/points`·어드민 집계의 표시 분기
(`reason`으로 먼저 갈라진다)는 변하지 않고, 미션 귀속 정보만 원장에 추가된다.
`badge-engine`·`drop-engine`의 지급은 `sourceMissionId`가 없어 **여전히 #5를 만든다.**

**FAIL 2 — SQL 테스트의 once 단언이 항상 참이었다**

`096_notifications_merge.test.sql` ④-3의 `ASSERT v_n.updated_at = v_prev`는 스크립트 전체가
하나의 `BEGIN…ROLLBACK` 안에서 돌고 PostgreSQL의 `NOW()`가 `transaction_timestamp()`라,
`once`가 잘못 UPDATE를 수행해도 값이 같아 회귀를 잡지 못한다(`pg_sleep`도 무효). 두 축의
단언으로 교체했다.

- **의미 축** — 두 번째 호출에 payload(`current` 52→91)·`actor_user_id`·`append_keys`를 전부
  다르게 주고, `payload`·`actor_count`·`actor_user_id` **불변**을 단언
- **물리 축** — `ctid` 불변. UPDATE는 반드시 새 튜플 버전을 만들므로 "UPDATE가 아예 없었음"의
  직접 증거가 된다
- 유효했던 행 개수 단언(`count(*) = 1`)은 그대로 유지

### 주요 의사결정 / 핵심 메모

**1. `group_key`에 type을 접두로 붙인다** (스펙 보정)

DATA_MODEL §4 표는 소식 1·3·4에 모두 `sync:{strava_activity_id}`를 배정하는데, UNIQUE
인덱스는 `(user_id, group_key)`뿐이라 **type이 키에 없다.** 그대로 구현하면 한 번의 동기화에서
세 종류가 같은 행으로 병합돼 payload가 서로를 덮어쓰고 type도 먼저 들어온 하나로 고정된다.
그래서 `{type}:{scope}` 형태로 만든다 — 표의 다른 키(`points:…`·`follow:…`)도 사실상 같은
형태이고, 이 티켓이 제시한 `mission_milestone:{mission_id}:{50|80}`이 정확히 이 규칙이다.

**2. `mode: 'once'` 도입** — "구간당 1회"를 실제로 구현하려면 필요했다

티켓은 "#20은 `group_key`를 두면 UNIQUE가 막아준다"고 했으나, DATA_MODEL §4의 병합 UPSERT는
충돌 시 `DO UPDATE`라 **막는 게 아니라 `updated_at`을 갱신**한다. 그러면 동기화할 때마다 dot이
다시 켜져 반복 발송과 같아진다(다크패턴). `create_notification(p_mode)`에 `once`(이미 있으면
아무것도 하지 않음)를 두고 #11·#20·#40에 적용했다.

**3. 소식 생성은 RPC로 한다**

PostgREST(`supabase-js`)의 `.upsert()`는 "행 전체 교체"만 표현할 수 있어
`actor_count = actor_count + 1` 같은 증분 갱신을 만들 수 없다. DATA_MODEL §4의 병합 규칙을
그대로 구현하려면 DB 함수가 필요하다.

**4. #26/#27 순서 — 맞팔이 성립하면 `mutual_follow`만 남긴다**

같은 사건("A가 B를 팔로우했다")이 알림함에 두 줄로 보이는 걸 막는다. PRD §3 ④의 "#22는 완료와
보상을 한 건으로 합친다 — 따로 보내면 같은 사건이 두 줄로 보인다"와 같은 원칙이고, 둘 중
맞팔이 더 강한 신호(개별·압축 금지)라 그쪽을 남겼다. 받는 사람은 팔로우당한 쪽이며, 팔로우한
본인에게는 만들지 않는다(자기 행동의 메아리).

**5. #40은 KST 하루 단위 `group_key` + `once`**

스펙상 "묶지 않는 소식"이지만, 연결이 끊긴 상태에서는 동기화 버튼을 누를 때마다 이 지점을 지나
같은 소식이 무한히 쌓인다. 하루 1건이면 개별 소식의 성격은 유지하면서 폭주만 막는다.

**6. #1의 묶음 키 대표값 = 이번 배치에서 가장 최신 활동**

배지 엔진은 배치 전체를 한 번에 평가해 개별 활동에 귀속시킬 수 없다. `start_date`가 같은 활동이
섞여도 결정론적이도록 `stravaId`를 보조 정렬 키로 뒀다.

**7. `insertDrop()` 반환을 boolean → `inventory_items.id`로 넓혔다**

소식 #3의 착지점이 배지 도감이 아니라 인벤토리 인스턴스(`/inventory/[itemId]`)라 그 id가 필요하다.

**8. KST 계산은 epoch +9시간 후 UTC 게터로 읽는다**

`toLocaleDateString`·`getDate()` 같은 로컬 벽시계 API를 쓰지 않는다. 서버(Vercel)는 UTC로 도는데
개발 머신은 KST라 환경마다 결과가 갈린다. KST는 서머타임이 없어 오프셋이 고정이다.

### 잔여 이슈
- **`src/types/database.ts`가 supabase-js 타입을 통째로 무력화하고 있다 (2차 보강 중 발견)** —
  `XxxRow`·`XxxArgs`를 `interface`로 선언해 `GenericSchema`의 `Row: Record<string, unknown>`
  제약을 만족하지 못한다(인터페이스는 암묵적 인덱스 시그니처를 얻지 못한다). 그 결과
  `SupabaseClient`의 `Schema`가 `never`로 접혀 **모든 테이블의 `.insert()/.upsert()` 인자가
  `never[]`, `.rpc()` 인자가 `undefined`로 추론**된다 — 리포 전역 `@ts-expect-error` 89곳의
  단일 원인이다. `interface` → `type` 일괄 변경으로 해소되지만, 그 순간 89개 억제 주석이
  전부 "사용되지 않은 @ts-expect-error" 컴파일 오류가 되므로 **별도 티켓**이 필요하다.
