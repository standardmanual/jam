# [BadgeEngine] 삭제된 배지도 유저의 진행도·선행조건 이력에서는 유지되도록 수정

> 20260825_020(research) 조사 결과 후속. 사용자 승인(2026-08-25) — 방향 (a) 채택.

## 배경 / 문제 정의

020 조사에서 확인된 결함: `evaluateBadgesDetailed()`(`jam-web/src/lib/badge-engine/index.ts`)가
유저의 배지 보유 이력(`ownedBadgeNames`, `highestOwnedTierByName`)을 계산할 때
`user_activity_badges`를 직접 쓰지 않고, 이미 `deleted_at IS NULL`로 필터링된
`allBadges` 카탈로그를 매개로 재확인한다(573~585행). 그 결과 유저가 실제로 획득한
배지라도 그 배지 정의가 나중에 소프트 삭제되면 "가진 적 없음"으로 잘못 계산된다.

**영향**:
1. 선행조건 게이트(612~619행) — 이미 선행 배지를 획득한 유저가 그 배지 삭제 후
   상위 배지(Rare/Legend/Mythic)를 영영 발급받지 못하게 막힘.
2. 진행 트랙 최고 티어 판정(605~610행) — 이미 최고 티어를 달성했는데 그 배지가
   삭제되면 처음부터 다시 시작하는 것처럼 계산돼, 이미 능가한 하위 티어가
   재발급될 위험.

**정책 근거**: 20260823_004에서 확정된 원칙 — "소프트 삭제는 노출·신규지급만
막고, 이미 획득한 유저의 이력은 그대로 유지" — 을 그대로 적용한다. 새 정책이
아니라 기존 정책의 적용 누락을 바로잡는 수정이다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `jam-web/src/lib/badge-engine/index.ts`의 `ownedBadgeNames`/`highestOwnedTierByName`
  계산(573~585행)을 `allBadges`(삭제 필터 적용됨) 순회 대신, 유저가 실제로 보유한
  배지(`ownedBadgeIds`)에 대한 이름·레어리티를 **삭제 여부와 무관하게** 조회해서
  채우도록 수정한다.
  - 구현 방법은 자유— 예: `user_activity_badges`에서 얻은 `badge_id` 목록으로
    `badges` 테이블을 `deleted_at` 필터 없이 별도 조회(`id, name, rarity`만
    select)하거나, 기존 `allBadges` 조회와 별개로 "삭제 여부 무관 전체 배지"
    조회를 하나 더 두는 방식.
  - `allBadges`(발급 후보 카탈로그) 자체의 `deleted_at IS NULL` 필터는 그대로
    유지한다 — 신규 발급 후보에서 삭제 배지를 제외하는 동작은 올바르므로 변경하지
    않는다. 바뀌는 건 오직 "유저가 이미 가진 게 무엇인지"를 판단하는 부분이다.
- 회귀 확인: 삭제되지 않은 일반적인 경우(대다수)에는 결과가 기존과 100% 동일해야
  한다 — `ownedBadgeNames`/`highestOwnedTierByName`이 늘어나는 건 오직 "보유
  배지가 삭제된" 케이스뿐.

### 컨텐츠/문서 관점
- `Service Plan/Specs/BadgeEngine/BADGE_ENGINE_UNIFIED.md`에 이 정책을 명문화한다
  (§2.5 진행 트랙 정책 또는 §2.7 선행 배지 게이트 근처에 추가 — "배지 정의가
  나중에 소프트 삭제되어도 유저가 이미 획득한 이력은 진행도·선행조건 판정에서
  계속 유효하다", 근거로 004 원칙 링크).

## 구현 계획
1. `evaluateBadgesDetailed()`에서 유저 보유 배지의 이름/티어를 삭제 여부 무관하게
   조회하도록 수정 (573~585행 로직 교체)
2. 선행조건 게이트·진행 트랙 최고 티어 판정이 삭제된 보유 배지를 정상적으로
   인식하는지 실측 검증 — 가능하면 테스트 시나리오: (a) 선행 배지 획득 후 삭제 →
   상위 배지 발급 여부, (b) 최고 티어 획득 후 삭제 → 하위 티어 재발급 안 되는지
3. 회귀 확인: 삭제 이력이 없는 일반 케이스에서 기존 로직과 결과 동일한지 확인
4. `BADGE_ENGINE_UNIFIED.md`에 정책 명문화
5. 이번 참에 `itembook/checker.ts`·`itembook/completable.ts` 등 유사 패턴("유저
   이력을 삭제 필터 걸린 카탈로그 매개로 재해석") 존재 여부를 가볍게 점검
   (수정은 발견 시 sideFindings로만 보고, 이번 티켓 범위는 badge-engine/index.ts로 한정)

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
`evaluateBadgesDetailed()`에서 `ownedBadgeNames`/`highestOwnedTierByName`을 계산하던 로직을,
삭제 필터가 걸린 `allBadges` 카탈로그 순회 방식에서 `ownedBadgeIds`(유저의 실제 보유 배지 id)를
기준으로 `badges` 테이블을 `deleted_at` 필터 없이 별도 조회(`id, name, rarity`)하는 방식으로
교체했다. `allBadges`(발급 후보 카탈로그) 자체의 `deleted_at IS NULL` 필터는 그대로 유지했다.
`BADGE_ENGINE_UNIFIED.md` §2.7 근처에 "소프트 삭제와 보유 이력의 관계" 정책을 명문화했다.

itembook/checker.ts·completable.ts의 유사 패턴 점검 결과는 sideFindings로 아래 alerts에 기록.
