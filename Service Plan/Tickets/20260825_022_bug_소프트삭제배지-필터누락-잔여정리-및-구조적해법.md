# [bug] 소프트 삭제 배지 필터 누락 — 전수 재감사 잔여분 정리 + 배지엔진 진행도 버그 + 구조적 해법 도입

> 004→005→007→009→015→016→017(x2)→(이 티켓)로 7차례 이어진 동일 패턴의 마무리 티켓.
> 이번에는 (1) 전체 `badges` 쿼리 지점을 처음부터 다시 전수 재감사하고, (2) 기존에 알려지지
> 않았던 badge-engine의 진행도 계산 버그를 함께 다루며, (3) 반복을 끊기 위한 구조적 해법의
> 채택 여부를 이 티켓에서 최종 결정한다.

## 배경 / 문제 정의

`badges` 테이블 조회 시 `deleted_at IS NULL` 필터가 누락되면 소프트 삭제된 배지가 화면
노출·카운트·지급 로직에 계속 반영된다. 007이 6곳, 009가 7곳, 015가 3곳, 016이 1곳,
017(두 건)이 2곳을 고쳤다. 이번 작업 착수 전 `.from('badges')` 68개 호출 지점 전체를
처음부터 다시 감사한 결과, 015~017에서 지목했던 지점(오늘 카드/피드, 드랍엔진, 아이템북
완성 판정, 포인트 요약)은 **이미 모두 정상**이었으나, 그 목록에 없던 지점 중 **5곳의 실질적
누락**과 **낮은 우선순위 관리자 화면 5곳 + 이미 존재하는 OPEN 티켓 1곳**을 새로 확인했다.

추가로, badge-engine의 진행도 계산 로직 자체에서 "삭제된 배지가 유저의 기존 진행도를
지워버리는" 별도 버그를 발견했다 — 단순 표시 필터 누락이 아니라 로직 버그이므로 함께 다룬다.

### 재감사 방법 (오탐 방지)
이전 015→017 인수인계 중 `.from('badges')` 라인만 보고 다음 줄의 `.is('deleted_at', null)`
체이닝을 놓친 오탐이 반복됐다. 이번에는 각 지점의 전체 쿼리 체인(다음 쿼리 메서드 종료 지점까지)과
호출부 문맥(select 결과를 어디에 쓰는지)까지 함께 확인해 오탐을 줄였다.

### 개선 검토 (progressive review 대상) — 구조적 해법 최종 결정

004→005→007→009→015→016→017(x2)→018로 8차례 반복된 패턴이다. 매 티켓마다 "이게 전부다"가
틀렸고, 이번에도 015~017이 지목한 지점은 모두 정상이었던 반면 지목되지 않았던 지점에서
새로 6곳(A그룹)이 발견됐다. **이 티켓에서 아래 중 최소 1개는 채택 여부를 확정한다**:

1. **공용 쿼리 헬퍼** (`selectActiveBadges(supabase, ...)` 형태) — `badges` 조회를 감싸서
   `deleted_at IS NULL`을 기본 포함시키고, 이력성 조회만 명시적으로 옵트아웃(`{ includeDeleted: true }`)
   하게 만드는 방식. 장점: 그렙 오탐 없이 타입 레벨에서 강제 가능. 단점: 기존 68개 호출부
   전체를 마이그레이션해야 함(점진적 적용 가능).
2. **DB 뷰** (`active_badges`) — `CREATE VIEW active_badges AS SELECT * FROM badges WHERE
   deleted_at IS NULL`. 장점: 쿼리 레벨에서 원천 차단. 단점: PostgREST 임베디드 리소스(join
   select)나 관리자 화면처럼 삭제된 것도 봐야 하는 경우 뷰를 쓸 수 없어 여전히 원본 테이블
   접근이 필요 — 완전 대체는 불가능하고 "노출/카운트/지급용 조회"에서만 뷰 사용을 권장하는
   컨벤션으로 남을 가능성.
3. **grep 기반 CI 체크** — 완벽하지 않음(정상적인 "select+JS 사후 필터" 패턴을 015 인수인계
   중 오탐한 전례, `api/admin/badges/route.ts:11`도 이번 재감사에서 유사 사례로 재확인).
   다만 "새 `.from('badges')` 호출이 추가됐는데 `deleted_at` 언급이 전혀 없다"는 최소
   신호만으로도 리뷰어에게 체크리스트 알림을 주는 용도로는 완전 대체보다 보조 장치로 유효.

진행 담당(jam-developer)은 이 중 실제로 채택할 안(또는 "채택하지 않고 유지")을 판단해
근거와 함께 완료 기록에 남긴다. 채택 시 최소 범위(신규 헬퍼/뷰 도입 + 가장 위험도 높은
호출부 일부 마이그레이션, 또는 그 이상)를 구현하고, 전체 68개 호출부 전면 마이그레이션까지는
이 티켓 범위로 강제하지 않는다(별도 후속 작업으로 분리 가능).
