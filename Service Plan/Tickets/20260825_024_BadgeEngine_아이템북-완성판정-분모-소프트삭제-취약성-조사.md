# [BadgeEngine] 아이템북 완성 판정 분모의 소프트 삭제 취약성 조사 (research)

> badge-engine의 진행도·선행조건 결함(020/021)과 같은 "이력을 삭제 필터 걸린
> 카탈로그 매개로 재해석" 패턴이 아이템북 완성 판정에도 있는지 확인하는 순수
> 조사(코드 무변경) 티켓.

> **번호 안내**: 최초 작성 시 로컬에서 20260825_022로 만들었으나, staging에
> 동일 날짜의 다른 022 티켓(소프트삭제 배지 필터 잔여 정리)이 이미 존재해
> 024로 재채번했다.

## 배경 / 문제 정의

`jam-web/src/lib/itembook/checker.ts`(52~59행)와 `completable.ts`(45~56행)는 북
소속 배지 수(완성 판정 분모)를 `badges` 테이블에서 `.is('deleted_at', null)`
필터를 걸어 계산한다. 020/021에서 badge-engine의 유사 패턴이 "유저 이력 유실"
버그로 확정된 바 있어, 아이템북 쪽에도 같은 종류의 왜곡이 있는지 코드를 다시
읽어 검증한다.

## 조사 결과

### 1. badge-engine과는 다른 종류의 문제 — "이력 유실"이 아니라 "분자·분모 집합 불일치"

badge-engine(020/021)의 결함은 유저의 실제 보유 이력(`user_activity_badges`)을
**삭제 필터가 걸린 카탈로그를 매개로 재조회**해서 "가진 적 없음"으로 오판정하는
것이었다(과소 판정, false negative). 아이템북 쪽은 구조가 다르다:

- **분모** (`checker.ts` 52~59행 `badgeCountByBook`, `completable.ts` 45~56행
  `badgeIdsByBook`) — `badges` 테이블을 `deleted_at IS NULL`로 필터링해서 집계.
- **분자** (`checker.ts` 74~78행 `slotCountByBook`) — `user_item_book_slots`
  테이블을 `item_book_id`로 **직접 row count**. 배지의 `deleted_at` 상태를
  전혀 확인하지 않는다.

즉 분자는 카탈로그를 매개로 재해석되는 게 아니라 완전히 독립적인 raw count다.
문제는 "이력이 사라진다"가 아니라 **분모의 집합(비삭제 배지)과 분자의 집합
(유저가 슬롯에 넣은 모든 배지, 삭제 여부 무관)이 서로 다른 기준으로 계산돼
불일치**한다는 점이다.

### 2. 실제 왜곡 시나리오 확인됨 (checker.ts) — 과대 판정(false positive)

북 소속 배지가 A~J 10개, 유저가 A~I(9개, J만 미보유) 슬롯 보유 중이라고 하자.

1. 삭제 전: `total=10`(A~J), `slotted=9` → `9 < 10`, 미완성.
2. 관리자가 **A를 소프트 삭제**(A는 유저가 이미 보유한 배지):
   - `badgeCountByBook`: A가 `deleted_at IS NULL` 조건에서 빠지므로
     `total = B~J = 9`로 감소.
   - `slotCountByBook`: `user_item_book_slots`는 배지 삭제 여부를 보지 않고
     row 자체를 세므로 A의 슬롯 row는 그대로 남아 `slotted = 9`(A~I) 유지.
   - 결과: `slotted(9) >= total(9)` → **완성으로 오판정**된다.
   - 그런데 유저는 여전히 J를 갖고 있지 않다. "A가 삭제됐으니 분모에서
     빠진다"는 논리와 "A의 슬롯은 여전히 분자에 카운트된다"는 논리가 같은
     배지에 대해 서로 다른 기준(분모=현재 카탈로그 기준, 분자=과거 행위
     기준)을 적용하면서 발생하는 순수한 계산 버그다.
3. 완성으로 오판정되면 `checkItemBookCompletion()`이 `user_item_book_completions`
   upsert + `book.reward_badge_id` 보상 배지까지 실제로 지급한다(161~200행) —
   단순 표시 버그가 아니라 **잘못된 보상 지급**으로 이어진다.

badge-engine 쪽 결함(선행조건 미충족 오판, 하위 티어 재발급)은 유저에게
불리한 방향(과소 판정)이었던 반면, 이쪽은 **유저에게 유리하지만 정책상 잘못된
방향**(과대 판정 + 보상 오지급)이라 영향의 성격이 반대다.

### 3. completable.ts는 같은 버그 없음 — 다른 이유로 여전히 취약

`completable.ts`는 raw count가 아니라 `Set` 멤버십(`remaining.every(id =>
ownedUnslottedBadgeIds.has(id))`, badge_id 단위)으로 판정하므로 checker.ts와
같은 분자·분모 불일치 버그는 없다. 삭제된 배지는 `badgeIdsByBook`에서 그냥
빠지고 `remaining` 계산에도 등장하지 않아 카운트가 어긋나지 않는다.

다만 여전히 "분모(총 배지 수) 자체가 삭제로 인해 줄어든다"는 정책적 영향은
동일하게 받는다 — 아래 4번 참조.

### 4. 004 원칙과의 대조 — badge-engine과 달리 "그대로 적용"이 애매한 사안

20260823_004 원칙: "이미 발급된 유저의 이력은 FK 그대로 참조 — 소프트 삭제는
**노출/신규 지급만** 막고, 이미 획득한 유저의 이력은 그대로 유지한다."

badge-engine에서는 이 원칙이 명확히 적용 가능했다 — "유저가 이미 가진 것"을
가리키는 데이터(`user_activity_badges`)가 따로 있었고, 버그는 그걸 조회할 때
불필요하게 카탈로그를 거친 것뿐이었다. 수정도 "유저 이력은 삭제 필터 없이
직접 조회"로 명확했다.

아이템북의 "분모"(북 완성에 필요한 총 배지 수)는 성격이 다르다. 이건 특정
유저의 이력이 아니라 **"이 컬렉션을 완성하려면 몇 개가 필요한가"라는 완성
기준선(threshold) 자체**다. 004 원칙을 그대로 적용해 "분모도 삭제 배지를
포함해야 한다"고 결론 내리면, 그 배지를 갖지 못한 유저(A를 못 가진 유저 기준)는
**그 북을 영원히 완성할 수 없게 된다** — 이미 발급 중단된 배지를 새로 얻을
방법이 없기 때문이다. 이는 004가 막으려던 문제(이력 유실)와는 다른 새로운
부작용이며, "노출/신규지급만 막는다"는 문구가 완성 기준선까지 규율하는지는
문서상 명시돼 있지 않다.

즉 정리하면 두 개의 서로 다른 사안이 섞여 있다:

- **(버그, 정책 무관 확정)**: checker.ts의 분자·분모 불일치는 어느 정책을
  택하든 고쳐야 하는 순수 로직 결함이다. 분자(`slotCountByBook`)와 분모
  (`badgeCountByBook`)는 반드시 같은 배지 집합 기준으로 계산되어야 한다.
- **(정책 미정, 사용자 확인 필요)**: 북 소속 배지가 삭제됐을 때 분모를 어떻게
  다룰지는 004의 단순 적용으로 결론 낼 수 없는 별도 판단이 필요하다. 예:
  - (a) 분모 유지(삭제 배지도 계속 카운트) — 완성 기준은 불변, 단 해당 배지를
    이미 못 가진 유저는 그 북을 영구히 완성 불가
  - (b) 분모 축소(현재 동작, 삭제 배지 제외) — 완성 기준선이 낮아지되,
    분자도 반드시 같은 배지 집합으로 재계산해 checker.ts 버그를 없애야 함
    (즉 이미 슬롯에 있던 삭제 배지의 슬롯도 "채움"으로 안 치거나, 애초에
    분모·분자 모두 동일 필터를 적용)
  - (c) 북 소속 배지 삭제 시 관리자가 북 자체를 `is_active=false` 처리하도록
    운영 프로세스로 강제(코드 변경 없이 정책으로 해결)

### 5. `BADGE_ENGINE_UNIFIED.md` 대조

아이템북 완성 판정(§?)에도 "북 소속 배지가 소프트 삭제된 경우 분모를 어떻게
다루는지"에 대한 문서화는 없음. badge-engine과 마찬가지로 문서화되지 않은 갭.

## 결론 및 후속 조치 제안

1. **분자·분모 불일치 버그(checker.ts)는 정책과 무관하게 확정된 결함**으로
   판단된다 — 별도 `bug` 유형 티켓으로 분리해 수정을 권장한다. 다만 수정
   방향은 4번의 (a)/(b) 정책 결정에 따라 달라지므로, 정책 확인 전에는
   최소 대응(분자에서도 삭제 배지의 슬롯을 분모와 같은 기준으로 제외)만
   임시로 적용하거나, 정책 확정과 함께 한 번에 처리하는 게 나을 수 있다.
2. **분모를 삭제 배지 포함/제외 중 어느 쪽으로 할지는 004의 단순 적용이 아닌
   별도 정책 판단**이 필요하다 — 사용자 확인 필요.
3. 실제 발생 빈도: 활동 배지(activity)와 달리 아이템/POI 배지는 **컬렉션
   비활성화 연쇄 삭제(20260823_004)** 경로로도 소프트 삭제될 수 있어,
   badge-engine 케이스(어드민 수동 삭제만 해당)보다 발생 경로가 더 넓다.
   컬렉션이 비활성화되면 북 자체도 함께 비활성화되는지 확인 필요 — 만약
   북은 살아있는데 소속 배지 일부만 연쇄 삭제되는 경우가 있다면 이 버그의
   실사용 영향이 020/021 케이스보다 클 수 있다.

이번 티켓은 조사만 수행하며 코드를 변경하지 않는다. 사용자 확인 후 구현이
필요하면 별도 `bug`(분자·분모 불일치) 및/또는 `engine`(분모 정책 확정) 유형
티켓으로 분리한다.

## 완료 기록

### 구현 내용 요약
`jam-web/src/lib/itembook/checker.ts`·`completable.ts`를 정독해 020/021에서
발견된 badge-engine의 "이력을 삭제 필터 걸린 카탈로그 매개로 재해석" 패턴과
비교했다. 같은 패턴은 아니었으나, checker.ts에서 별도의 실재하는 버그(분모는
`deleted_at IS NULL`로 집합 필터링, 분자는 `user_item_book_slots` raw row
count로 배지 삭제 여부 무관 — 두 집합 기준이 어긋남)를 확인했다. 북 소속
배지가 소프트 삭제되면 분모가 줄어드는데 유저의 기존 슬롯 카운트는 줄지
않아, 실제로는 미보유 배지가 남아있는데도 "완성"으로 오판정되고 보상 배지가
잘못 지급될 수 있다. completable.ts는 집합 멤버십 방식이라 이 특정 버그는
없으나, 분모가 삭제로 축소된다는 정책적 영향은 동일하게 받는다.

004 원칙("이력 유지, 노출/신규지급만 필터링")은 badge-engine처럼 명확히
적용되지 않는다 — 아이템북의 "분모"는 유저 개별 이력이 아니라 컬렉션 완성
기준선 자체이므로, 그대로 적용하면 삭제된 배지를 못 가진 유저는 해당 북을
영구히 완성할 수 없게 되는 새로운 부작용이 생긴다. 이는 사용자 정책 판단이
필요한 사안으로 별도 결론 없이 조사만 완료했다.

사용자가 방향 (a)(분모 유지)를 승인해 후속 구현 티켓 20260825_025로 이어졌다.
