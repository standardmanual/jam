# [BadgeEngine] 어드민 폼 미지원 필드 저장 시 유실 위험 (day_of_week 등)

## 배경 / 문제 정의

티켓 [20260825_031](20260825_031_BadgeEngine_condition-json-데이터계약-검증-도입.md)에서
`mission_reward` 필드가 `BadgeForm.tsx`에 입력 UI가 없어 어드민에서 배지를 수정 저장하면
플래그가 조용히 유실되는 실제 회귀를 발견·수정했다. 같은 조사 과정에서, `mission_reward`와
동일한 패턴의 잠재 위험이 다른 필드에도 남아 있음을 게이트 리뷰·개선 리뷰 양쪽이 지적했다.

`BadgeForm.tsx`의 `buildConditionJson`(→ `conditionFormFields.ts`의
`buildConditionJsonFromFields`)이 여전히 다루지 않는 `condition_json` 필드:

- `day_of_week`
- `active_days_count`
- `poi_id`
- `route`

`src/app/api/admin/badges/[id]/route.ts`의 PUT은 `condition_json`을 부분 병합이 아니라
**전체 교체**로 저장한다. 따라서 이 필드들 중 하나가 설정된 배지를 어드민 폼에서 열어
저장하면, 폼이 모르는 필드는 조립 과정에서 빠지고 그 값 그대로 DB에 덮어써져 조용히
사라진다 — 084 마이그레이션·`mission_reward` 사고와 동일한 유형이다.

**실측(2026-08-25, jam-prod)**: 현재 `day_of_week`·`active_days_count`·`route`를 가진
`activity` 배지는 0건, `poi_id`를 가진 `poi` 배지는 1건 존재(단, `poi` 타입은 조건 빌더
자체를 쓰지 않으므로 이 배지는 영향받지 않는다). **즉 현재 시점 실피해는 없다.**
다만 이 필드들은 향후 배지 설계에 쓰일 수 있는 정의된 필드이므로, 실제로 쓰이기 시작하면
동일한 사고가 재발할 수 있다.

## 상세 요구사항

### 서비스/코드베이스 관점

다음 중 비용 대비 효과를 판단해 하나 이상 적용:

- **최소 방어선(권장 후보)**: `BadgeForm.tsx`에서 `initCond`에 폼이 다루지 않는 키가 있으면
  저장 버튼을 비활성화하고 "이 배지는 어드민 폼이 지원하지 않는 조건 필드(`{keys}`)를
  가지고 있어 여기서 수정할 수 없습니다"류 안내를 노출
- **또는**: `buildConditionJsonFromFields`가 폼 미지원 필드를 `initCond`(원본)에서 그대로
  보존하도록 수정 (부분 병합처럼 동작하게)
- **또는**: `day_of_week`·`active_days_count`·`route`용 입력 UI를 실제로 추가해 폼이
  완전히 커버하게 함 (`poi_id`는 애초에 POI 배지 전용이라 조건 빌더 대상이 아님 — 제외 검토)

`condition-schema.ts`의 `ALL_CONDITION_KEYS`를 기준으로 "폼 커버 필드"와 "폼 미지원 필드"를
구분하는 상수를 두면 향후 필드 추가 시에도 이 문제가 재발하지 않는다.

## 구현 계획
> 착수 시 위 후보 중 택일해 상세화

**택일: "initCond 미지원 필드 보존" (2번째 후보)를 조건-빌더 대상 필드 전체에 일반화해 적용.**
저장 차단(1번 후보)은 실사용 중인 필드(현재는 `season_count_all`, 아래 발견 참고)를 가진
배지를 어드민에서 아예 못 고치게 막는 비용이 크고, 실제 입력 UI 추가(3번 후보)는
`route`처럼 badge-engine에 평가 로직 자체가 없는 필드에 입력 UI를 만들면 오히려 "넣어도
무의미한 UI"로 혼란을 유발한다(오케스트레이터 사전 조사). 반면 보존 방식은 어떤 필드가
추가되든(`ALL_CONDITION_KEYS` 기준 자동 계산) 유실만 막고, 폼이 지원하지 않는 필드는
안내 문구로 투명하게 드러내는 최소 비용 방어선이다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- `conditionFormFields.ts`에 `FORM_COVERED_CONDITION_KEYS`(폼이 실제로 입력 UI를 갖고 조립하는
  필드 목록)와, `condition-schema.ts`의 `ALL_CONDITION_KEYS`와의 차집합인
  `FORM_UNSUPPORTED_CONDITION_KEYS`를 도입. 새 조건 필드가 생겨도 이 두 상수가 자동으로
  "폼 미지원 필드"를 계산하므로, 폼 반영을 빠뜨려도 최소한 유실은 발생하지 않는 구조.
- `buildConditionJsonFromFields`가 2번째 인자로 `initCond`(배지를 열 때의 원본 조건)를 받아,
  폼 미지원 필드는 값이 있으면 그대로 결과에 병합(보존)하도록 수정. 폼이 실제로 조립하는
  필드는 항상 폼 입력값이 우선하며 보존 로직에 덮어써지지 않는다.
- `getUnsupportedConditionKeys(cond)` 헬퍼 추가 — 값이 있는 미지원 필드 키 목록 반환.
- `BadgeForm.tsx`: `buildConditionJson` 호출 시 `initCond`를 함께 넘기도록 수정, 조건 빌더
  섹션에 "이 폼에서 다룰 수 없는 조건 필드가 있어요" 안내 박스 추가(값 유지는 되지만 이
  화면에서 보거나 고칠 수는 없다는 것을 명시).

**구현 중 발견(범위 확장)**: `ALL_CONDITION_KEYS` 기준으로 자동 계산하니 티켓 원문의 4개
필드(`day_of_week`, `active_days_count`, `poi_id`, `route`) 외에 **`season_count_all`도
폼 미지원 필드**로 잡혔다. 이 필드는 `route`와 달리 `badge-engine`(`evaluateConditionDetailed`)이
실제로 평가하고, `migrations/076_walking_badges_v4.sql`에 시딩된 "사계절의 발걸음" 배지가
`{"season_count_all":10}`으로 이미 사용 중이다 — 즉 이 배지를 어드민에서 열어 수정 저장하면
이번 수정 전에는 조건이 조용히 사라졌을 실질 위험이 있었다(자세한 내용은 `alerts` 참고).
이번 보존 로직이 이 필드도 함께 커버한다.

### 잔여 이슈
- `season_count_all` 입력 UI가 없는 상태는 이번 티켓 범위에서는 "보존"으로만 방어했다.

  더 편하게 편집하고 싶다는 요구가 생기면 별도 티켓으로 입력 UI 추가를 검토할 것.
