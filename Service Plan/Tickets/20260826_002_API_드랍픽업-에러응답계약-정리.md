# [API] 드랍·픽업 API 에러 응답 계약 정리 (서버 원문 노출 차단)

## 배경 / 문제 정의

티켓 20260825_039에서 바텀시트 포털화·토스트 레이어 상승으로 **그동안 시트에 가려져 있던
픽업 실패 토스트가 실제로 보이게 되면서**, 서버의 개발자용 축약 문구가 사용자에게 노출되는
문제가 드러났다. 픽업 경로는 그 티켓에서 응급 처치했지만 **구조적 원인은 그대로 남아 있다.**

### 원인 — 같은 `error` 필드에 두 갈래가 섞여 있다

`src/app/api/drops/[dropId]/pickup/route.ts`와 `src/app/api/drops/route.ts`가
같은 `error` 필드에 서로 다른 종류의 값을 담는다:

- **기계 판독용 snake_case 코드** — `inventory_full`, `cannot_pickup_own_drop` 등 (RPC 결과 경유)
- **개발자용 한국어 축약 문구** — `'드랍 없음'`, `'POI 없음'`, `'인벤토리 없음'`, `'인증 필요'`,
  `'아이템 없음 또는 소유 아님'`, `'필수 파라미터 누락'` 등

클라이언트가 코드 매핑과 원문 표시를 **동시에** 시도(`msg[err.error] ?? err.error`)하는 구조가
여기서 비롯된다.

### 아직 남아 있는 실제 노출 경로

`src/components/PoiCarouselModal.tsx`의 **드랍(drop) 경로**는 여전히 서버 원문을 그대로 띄운다:
- 약 L197 `toast(err.error ?? d.drops.dropFailed, 'error')`
- L122·L125 드랍 목록 조회 실패 시 `json.error` 그대로 노출

> ⚠️ **단순 제거 금지**: 드랍 경로의 `'컬렉션에 장착된 아이템은 드랍할 수 없어요.'`
> (`api/drops/route.ts:262`)는 이미 **좋은 사용자 문구**다. `?? err.error`만 없애면 이 유용한
> 메시지를 잃는다. 픽업과 마찬가지로 **코드화 + 문구 매핑을 함께** 해야 한다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 두 라우트의 에러 응답을 `{ code, message }`로 분리하거나, 최소한 **모든 응답이 안정적인
  snake_case 코드만** 반환하도록 통일한다.
- 사용자 문구는 전부 `src/lib/i18n/ko.ts`에서 관리하고 클라이언트가 코드로 매핑한다.
  **서버 원문이 사용자에게 도달하는 경로를 전부 없앤다.**
- 20260825_039에서 픽업 경로에 이미 적용한 방식(`?? err.error` 제거 + 코드 매핑)을
  드랍 경로와 목록 조회 경로에도 동일하게 적용한다.

### 컨텐츠(UX Writing) 관점
`Service Plan/Specs/UX_WRITING_GUIDELINE.md`의 [현상]→[원인]→[해결책] 구조와 해요체를 따른다.
토스트는 1줄이라 CTA 버튼 대신 **해결책을 문장에 포함**시킨다
(20260825_039의 `pickupOutOfRange`·`pickupOwnDrop` 참고).

### ⚠️ 반경 상수 불일치 — 반드시 함께 수정
`src/app/api/drops/route.ts:226`이 `'POI 반경 50m 밖'`이라고 적고 있으나 실제
`DROP_RADIUS_METERS`(`src/lib/poi/proximity.ts:5`)는 **500**이다.
픽업 라우트에서는 20260825_039에서 이미 고쳤다. 드랍 라우트의 문구·주석도 바로잡고,
사용자 문구에는 **숫자를 하드코딩하지 말고** `t()` 치환으로 상수를 주입한다(`{m}m`).

## 구현 계획

1. 두 라우트의 에러 응답을 코드 기반으로 통일
2. `ko.ts`에 대응 문구 추가·정비
3. `PoiCarouselModal`의 3개 노출 경로(픽업·드랍·목록조회) 전부 코드 매핑으로 교체
4. 반경 상수 불일치 수정

## 완료 기록

### ⚠️ 프로세스 사고 — 리뷰 미통과 상태로 프로덕션 유입

**이 티켓의 변경은 게이트 리뷰를 통과하기 전에 프로덕션까지 배포됐다.** 경위:

1. 구현 서브에이전트가 **공유 작업 폴더**(`~/Desktop/JAM!`)에서 작업했다.
2. 그 변경이 아직 커밋 전인 상태에서, 동시에 진행 중이던 다른 세션(티켓 20260826_004
   체크인 용어 통일)이 광범위한 커밋으로 이 티켓의 파일 5개를 함께 쓸어담았다.
3. 그 커밋이 병합 커밋 `c5d27a90`으로 staging → **main까지 머지**되고 프로덕션 배포됐다.
   `origin/staging`·`origin/main`·`004 브랜치`가 모두 `c5d27a90`을 가리키는 상태였다.

**원인**: 오케스트레이터가 병렬 세션 위험을 인지하고 **자신만** 격리 워크트리로 옮겼고,
서브에이전트는 공유 폴더에 그대로 뒀다.

**재발 방지**: `/jam-work`의 서브에이전트를 격리 워크트리에서 실행한다
(`isolation: 'worktree'`). 공유 작업 폴더에 미커밋 변경을 남기지 않는다.

**사후 판정**: 게이트 리뷰를 사후에 수행한 결과 **WARN**(FAIL 아님)이었고, 병합 결과가
정상임을 확인했다 — 이 티켓의 신규 키와 004의 용어 키가 양쪽 다 반영됐고 타입체크를
통과하며, 배포된 스테이징에 실제 요청을 보내 응답 코드가 올바름을 확인했다.
DB 변경은 없었다. 따라서 롤백(004 병합과 엉켜 위험)이 아니라 **현상 유지 + 결함 즉시 수정**을
택했다(사용자 승인).

### 구현 내용 요약

**본 작업 (커밋 `c5d27a90`에 포함되어 이미 배포됨)**

- 3개 라우트(`api/drops`, `api/drops/[dropId]/pickup`, `api/drops/poi/[poiId]`)의 `error`를
  **snake_case 코드만** 담도록 통일. 한국어 원문 반환 0건.
- 사용자 문구를 `ko.ts` drops 섹션으로 이관하고 [현상]→[원인/해결책] 구조·해요체로 재작성.
- `PoiCarouselModal`의 노출 경로 3곳(픽업·드랍·목록조회)에서 서버 값 노출 제거.
  `?? err.error`·`?? json.error` 잔존 0건.
- 반경 상수 불일치 수정: 드랍 라우트의 `'POI 반경 50m 밖'`·`'50m 검증'` 주석 →
  `out_of_range` 코드 + `t(d.drops.dropOutOfRange, { m: DROP_RADIUS_METERS })`(500 주입).
- 부수: `poi/[poiId]` 500 응답의 DB 원문 `detail` 제거, 픽업의 `inventory_not_found` →
  '인벤토리가 꽉 찼어요' 오매핑 정정.

**후속 수정 (리뷰 지적 반영, 별도 커밋)**

리뷰가 지목한, 프로덕션에 살아 있던 결함 2건:

1. **`unauthorized`가 양쪽 매핑 테이블에 없었다.** 세션 만료(401) 시 "잠시 후 다시 시도해
   주세요"가 떴는데 **다시 시도해도 영원히 실패**한다 — 해결책이 원인과 어긋난 유일한 코드였다.
   `sessionExpired: '로그인이 풀렸어요. 다시 로그인하고 시도해 주세요'`를 추가해 양쪽에 매핑.
2. **`ko.ts`의 `outOfRange`·`moveCloser`가 `50m`를 하드코딩**하고 있었다(실제 500m).
   바로 아래 `noNearbyPlaces`가 이미 `500m`라 **같은 블록 안에서 값이 어긋난 상태**였다.
   셋 다 `{m}` 치환으로 상수를 주입하도록 바꾸고 `DropsClient` 호출부 3곳에 주입.

### 주요 의사결정 / 핵심 메모

- **롤백하지 않고 현상 유지 + 즉시 수정을 택했다.** 병합 결과가 검증됐고(타입체크·실서버 응답),
  004 병합과 엉켜 있어 revert가 오히려 위험하기 때문이다. 사용자 승인 하에 결정.
- **거리 문구의 상수 주입을 원칙으로 굳혔다.** 이 티켓에서만 반경 불일치가 **세 곳**
  (드랍 라우트, `outOfRange`, `moveCloser`)에서 나왔다. 숫자를 문구에 박으면 상수가 바뀔 때
  조용히 어긋난다. `noNearbyPlaces`가 500m인데 바로 아래 `moveCloser`가 50m였던 것이 그 증거다.
- **`unauthorized`는 "재시도" 계열 문구를 쓰면 안 되는 유일한 코드다.** 세션이 풀린 상태라
  재시도로 풀리지 않는다. 해결책이 실제로 작동하는지가 문구 판정 기준이어야 한다.

### 잔여 이슈

- `missing_params` → `locationMissing` 매핑이 과잉 일반화다. 드랍 라우트의 `missing_params`는
  `poi_id`·`inventory_item_id` 누락(클라이언트 버그)에서도 나오는데 "위치를 확인하지 못했어요"가
  뜬다. 서버에서 좌표 누락만 `location_missing`으로 분리하면 문구와 원인이 맞아떨어진다.
- `PoiCarouselModal.openInventory()`와 `DropsClient.loadNearbyPois()`가 `res.ok`를 확인하지
  않아 401/500에서도 빈 목록으로 흘러 **실패가 빈 상태로 위장**된다
  (`DEV_PROCESS_GUARDRAILS.md` 패턴 4와 같은 형태).
- `api/drops/[dropId]/route.ts`(사문화)와 `api/drops/debug/route.ts`에 한국어 원문 에러가
  남아 있다. 현재 클라이언트 호출부가 없어 노출 경로는 없다.
- `pickup/route.ts`의 `@ts-expect-error` — `pickup_drop` RPC가 `src/types/database.ts` Functions에
  미등록이다. 주석은 "별도 티켓 필요"라고 적고 있으나 채번된 티켓이 없음을 전수 검색으로 확인했다.
- `api/drops/poi/[poiId]/route.ts`의 `any` 2곳이 `@typescript-eslint/no-explicit-any` 에러를
  낸다(기존 코드). `npm run lint`를 CI 게이트로 쓰면 걸린다.
