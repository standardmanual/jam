# [UI] z-index 레이어 체계 문서화 (스태킹 컨텍스트 사고 재발 방지)

## 배경 / 문제 정의

티켓 20260825_039에서 바텀시트가 호출부의 `relative z-10` 스태킹 컨텍스트에 갇혀 탭바에
가려지는 버그를 고쳤다. **이 티켓이 1차·2차·3차로 쪼개진 이유가 바로**
"포털화로 DOM 순서가 바뀌면 동일 z에서 승자가 바뀐다"는 규칙이 어디에도 문서화돼 있지 않아서였다.

- 1차(포털화) → 토스트가 시트 뒤로 숨는 회귀 발생 → 2차(토스트 z 상승)
- 2차 → 가려져 있던 서버 원문이 노출되기 시작 → 3차(문구 차단)
- 게이트 리뷰도 이를 확인하려고 `src` 전역 z-index **전수 조사를 다시 수행**해야 했다

앞으로 오버레이를 하나 추가할 때마다 같은 전수 조사가 반복된다.

## 상세 요구사항

`Service Plan/Specs/PRD/2026-08-15 DESIGN_RENEWAL_SPEC.md`에 **"z-index 레이어 체계"** 절을 신설한다.
(이 문서에 이미 탭바 높이·safe-area·오버레이 관련 규정이 있어 맥락이 맞다.
별도 신규 문서를 만들 만큼의 분량은 아니다.)

### 담을 내용

1. **층 정의 표** — 작성 전 실제 코드를 grep해 현황을 재확인할 것.
   2026-08-25 기준 조사 결과(이후 20260826_005로 토스트가 포털화되면 갱신 필요):

   | z | 층 | 대표 파일 |
   |---|---|---|
   | `z-10` | 페이지 섹션 | `badges/[id]/page.tsx`의 info/action 섹션 등 |
   | `z-30` | POI 캐러셀 모달 | `PoiCarouselModal.tsx` |
   | `z-40` | 플로팅 탭바 | `TabBar.tsx` |
   | `z-50` | 시트·모달 오버레이 (23곳) | `BottomSheet`, `alert-dialog`, `dialog`, `sheet`, `select`, `FeedSection` 패널, `BadgeShareButton` 팝오버, 어드민 폼 |
   | `z-60` | 토스트 | `Toast.tsx` + `BadgeRevealOverlay.tsx:56`(인라인 `zIndex: 60`) |
   | `z-[9999]` | 전역 로더 | `NavigationLoader.tsx` |

2. **동일 z에서는 DOM 순서가 승자를 정한다**는 규칙과, 그 따름정리인
   **"`document.body` 포털은 항상 맨 뒤에 붙는다"**
3. **`z-index: auto`인 조상은 스태킹 컨텍스트를 만들지 않는다**는 판정 기준.
   이번에 `(main)/layout.tsx:47`의 앱 셸이 여기 해당했고, 반대로 `relative z-10`은
   컨텍스트를 만들어 사고 원인이 됐다.
4. **새 오버레이 추가 시 체크리스트** — "기존 층에 배치할 것 / 새 값 도입은 표 갱신 필수 /
   포털 여부 명시"

### 함께 짚을 것 — 취약한 동률

`BadgeRevealOverlay.tsx:56`이 인라인 `zIndex: 60`으로 **토스트와 동률**이다.
현재는 토스트 컨테이너가 DOM상 앱 셸보다 뒤라 동률에서 토스트가 이기고,
`SyncButton`·`StravaConnectReveal` 모두 "배지 0개일 때만 토스트, 1개 이상이면 오버레이"라
**상호 배타적이어서 실제 충돌은 없다.** 다만 프로바이더 순서가 바뀌면 조용히 뒤집히는
취약한 동률이므로, 문서에 이 사실을 명시하거나 값을 분리하는 방안을 제안한다.

> 티켓 20260826_005로 토스트가 포털화되면 이 동률 관계가 달라질 수 있다 —
> **005 완료 후 실제 상태를 재확인하고 문서에 반영할 것.**

   - **기하값은 추정하지 말고 실측한다** (20260826_005의 오판 3건을 표로 기록)
   - 트랜지션 중 위치(`--toast-distance`)를 간격 계산에 넣는다
3. **새 오버레이 추가 시 체크리스트** 4항목
4. **알려진 취약점** — `BadgeRevealOverlay`(인라인 60)와 `Toast`(z-[60])의 동률,

### 주요 의사결정 / 핵심 메모

- **별도 신규 문서를 만들지 않고 기존 `DESIGN_RENEWAL_SPEC.md`에 절로 넣었다.** 이 문서에
  이미 탭바 높이·safe-area·컨테이너 폭 규정이 있어 레이아웃 맥락이 맞고, 분량도 독립 문서를
  세울 정도는 아니다. 문서가 흩어지면 읽히지 않는다.
- **규칙마다 실제 사고를 근거로 붙였다.** 추상적인 "z-index를 잘 관리하자"가 아니라
  "2026-08-25에 이래서 이렇게 깨졌다"를 함께 적어야 다음 사람이 규칙을 무시하지 않는다.
- **`CLAUDE.md` 링크가 실질적인 장치다.** PRD 문서는 찾아 읽어야 하지만 `CLAUDE.md`는
  세션마다 자동으로 로드된다. 규칙의 존재를 알리는 지점을 여기 둔 이유다.

### 잔여 이슈

- `BadgeRevealOverlay`(인라인 `zIndex: 60`)와 `Toast`(`z-[60]`)의 **동률은 해소하지 않고
  문서화만 했다.** 현재 두 화면이 상호 배타적이라 실피해가 없고, 값을 바꾸면 별도 검증이
  필요해 범위를 넘는다. 규칙 1에 해당하는 취약 상태로 문서에 명시했다.
- `PoiCarouselModal`(`z-30`)이 하단 점유(`safe+92px`)를 신고하지 않아, 시트 없이 캐러셀만
  열린 상태의 토스트는 여전히 카드 하단과 겹친다. `pushBottomOverlay()` 한 줄이면 되지만
  이 티켓은 문서화 범위라 손대지 않았다 — 별도 처리 필요.
