# [Service] 프로필 피드 — 활동 참조 컬럼 추가 및 동일 활동 이벤트 묶음 렌더

## 배경 / 문제 정의

티켓 [20260827_014](20260827_014_API_알림소식-전면개편-활동결산-대상묶음-문구규칙R1R15.md)(CLOSED)가
알림함의 홍수를 「활동 결산」 한 행으로 접었다. 그 과정에서 착지 규칙 R6이 정해졌고,
**포인트가 섞이거나(C3·D1) 첫 배지(E3)거나 활동이 2건 이상(F2)이면 프로필 페이지로 보낸다.**

문제는 **프로필이 그 착지를 받을 준비가 안 됐다는 것**이다.

- `jam-web/src/lib/activity-feed/index.ts`의 `recordFeedEvent(userId, eventType, metadata, eventAt)`는
  **어느 활동에서 나온 이벤트인지를 받지 않는다.**
- `user_activity_feed` 테이블에도 활동 참조 컬럼이 없다
  (`id / user_id / event_type / event_at / created_at / metadata` 6개뿐).

그래서 유저가 알림함에서 "**배지 9개**와 **420 포인트**를 획득했어요"를 눌러 프로필에 도착하면,
**방금 한 행으로 접어준 그 9개가 다시 9줄로 평면 나열된 화면**을 만난다.
알림함에서 없앤 홍수가 착지점에서 그대로 재현된다.

014 티켓의 잔여 이슈가 이 건을 "후속 티켓 필요"로 남겼다.

### 기대 상태

프로필 「최근 활동」 피드가 **같은 활동에서 나온 이벤트를 한 카드로 묶어** 보여준다.
카드를 펼치면 그 활동의 개별 이벤트가 나온다. 알림함의 결산과 프로필의 묶음 카드가
**같은 단위(활동)를 말하게** 되어 착지가 성립한다.

## 상세 요구사항

### 서비스/코드베이스 관점

**(1) DB — 마이그레이션 `107_user_activity_feed_strava_activity_id.sql`**

- `public.user_activity_feed`에 `strava_activity_id BIGINT NULL` 추가.
- **UUID FK(`strava_activities.id`)가 아니라 Strava 숫자 id를 쓴다.** 근거:
  - 기록 지점 3곳이 이미 이 값을 손에 들고 있다
    (`rawActivity.id` · `triggerActivity.stravaId` · `act.stravaId`) — 추가 조회가 없다.
  - `user_activity_badges.triggered_by_strava_id`가 이미 같은 규약을 쓴다.
  - 014의 결산 payload `activity_ids`도 Strava 숫자 id다. **알림과 피드가 같은 키로 말한다.**
- NULL 허용이 핵심이다. 활동과 무관한 이벤트(`mission_joined`·`item_picked_up`)와
  **과거 행 전부**가 NULL로 남는다.
- 인덱스: `(user_id, strava_activity_id)` — `WHERE strava_activity_id IS NOT NULL` 부분 인덱스.
- `COMMENT ON COLUMN`으로 "NULL = 활동 귀속 불명(과거 행 포함), 묶지 않고 단건 렌더" 명시.

> **백필하지 않는다.** 과거 이벤트는 어느 활동에서 나왔는지 복원할 방법이 없다
> (`event_at`이 부정확하다는 게 마이그레이션 093·094에서 이미 실측됐다).
> 추정 매칭으로 잘못 묶는 것보다 단건으로 남기는 쪽이 안전하다 — **graceful degradation**.

> ⚠️ **SQL 파일 작성까지만 한다. 실행하지 않는다.** 승인 후 오케스트레이터가 실행한다.

**(2) 기록 — `recordFeedEvent` 시그니처 확장**

```ts
recordFeedEvent(userId, eventType, metadata, eventAt?, stravaActivityId?)
```

- **5번째 위치 인자로 추가한다.** 옵션 객체로 바꾸지 않는다 —
  `database.ts`·`badges/recent-earned/route.ts`·`093` 마이그레이션 주석이 모두
  "`recordFeedEvent()`의 **4번째 인자**"라고 명시하고 있어, 순서를 바꾸면 그 주석들이 전부 거짓이 된다.
- 값을 넘길 곳 3곳:

| 파일 | 위치 | 넘길 값 |
|---|---|---|
| `lib/badge-engine/index.ts` | `badge_earned` 기록 | `triggerActivity?.stravaId` |
| `lib/strava/sync.ts` | 체크인 `badge_earned` 기록 | `rawActivity.id` |
| `lib/drop-engine/index.ts` | `item_dropped` 기록 | 활동 파라미터의 `stravaId` (없으면 미전달) |

- 나머지 3곳(`missions/[id]/join` · `drops/[dropId]/pickup` · `missions/checker`)은 그대로 둔다.
  미션 참가·픽업은 활동 단위가 아니다.
  - `missions/checker.ts`의 `mission_completed`는 **판단이 필요하다** — 활동 동기화가 계기지만
    미션은 여러 활동에 걸친 누적이다. **넘기지 않는 쪽으로 한다**(단건 유지).
    묶으면 "이 활동에서 미션이 완료됐다"가 되어 사실과 어긋난다.
- **`drop-engine`의 귀속 입도 주의** — 014 잔여 이슈가 지적한 대로 경로마다 실어 보내는
  활동 집합이 다르다. 여기서는 **드랍이 실제로 발생한 그 활동 1건만** 싣는다.

**(3) 타입 — `ActivityFeedRow`**

- `strava_activity_id: number | null` 추가 (`src/types/database.ts`).
- `database.generated.ts`도 함께 맞춘다.
- `[username]/page.tsx`의 `makeFeedItem()`이 합성하는 레거시 행은 **항상 `null`**로 채운다.

**(4) 조회 — `[username]/page.tsx`**

- `user_activity_feed` 조회는 `select('*')`라 컬럼이 자동으로 따라온다.
- **활동 이름을 함께 가져온다.** 묶음 카드에 "어느 활동인지"가 없으면 헤드라인이 허공에 뜬다.
  케이스북이 짚은 유저 멘탈모델("오늘 아침에 달린 그거, 뭐 받았지?")의 앵커가 활동 이름이다.
  - 피드 150행에서 non-null `strava_activity_id`를 모아
    `strava_activities.select('strava_id, normalized, start_date').eq('user_id', subjectId).in('strava_id', ids)` 1회 조회.
  - `normalized.name`을 꺼내 묶음 헤더에 쓴다.
  - **조회 실패·이름 없음이면 이름 없는 헤드라인으로 폴백한다.** 묶음 자체는 유지한다.
  - `ProfileClient` → `FeedSection`으로 `activityNames?: Record<string, string>`(키=strava_id 문자열)
    형태의 맵을 내려보낸다. 옵셔널 prop이라 안 넘겨도 동작해야 한다.

### UI/UX 관점

**묶음 규칙 (FeedSection.tsx)**

1. **필터를 먼저 걸고, 그다음 묶는다.** 묶음은 표현 계층이다.
   「아이템」 탭에서 묶음 카드를 열면 아이템 이벤트만 들어 있어야 한다.
2. `strava_activity_id`가 non-null인 행끼리 그 값으로 묶는다.
3. **2건 이상일 때만 묶음 카드로 그린다.** 1건이면 지금과 똑같은 `FeedCard`로 그린다 —
   장식만 붙고 정보가 없는 껍데기를 만들지 않는다. (알림 F2의 임계값 2건과 같은 판단)
4. `strava_activity_id`가 NULL인 행은 **절대 서로 묶지 않는다.** 각자 단건이다.
5. 정렬은 **묶음 안 최신 멤버의 `created_at`** 기준. 기존 `created_at` desc 정렬을 유지한다.
6. 페이지네이션(`PAGE_SIZE = 20`)은 **묶음 카드 1개를 1개로 센다.** 상단 카운트
   `d.common.countItems`는 **개별 이벤트 수를 유지한다**(총 획득량 정보라 접으면 손해다).

**묶음 카드**

- 접힘 상태: 활동 이름(있으면) + **총량 문구** + 대표 썸네일 몇 개 + 상대 시각 + 펼침 어포던스.
- 펼침 상태: 기존 `FeedCard`들을 그대로 안에 나열. 카드를 누르면 기존 `DetailSheet`가 뜬다.
- **인라인 아코디언이다.** 새 라우트·새 시트를 만들지 않는다 —
  케이스북 **R6**("새 결산 화면을 만들지 않는다")이 프로필 안에서도 유효하다.
- 접근성: 펼침 트리거는 `<button>` + `aria-expanded` + `aria-controls`.
- 모션: `prefers-reduced-motion` 존중. 기존 `transitions.css`·`--motion-*` 토큰 재사용.

**UX Writing** — 케이스북의 확정 규칙을 그대로 따른다.

- **R1** 「이번 활동으로」 접두 금지.
- **R2** 고유명사에 작은따옴표 금지.
- **R3** 화폐 단위는 「포인트」(「JAM 포인트」·「P」 금지).
- **R5** 2종 이상이면 나열하지 않고 **총량**으로 말한다 → `배지 5개를 획득했어요`.
- 모든 문안은 `lib/i18n/ko.ts`의 `d.feed`에 넣는다. **컴포넌트에 한글 리터럴 금지.**

> `d.feed.rewardPoints`가 아직 `'+{points}P'`다. **이번 범위 밖**이다
> (014 잔여 이슈의 「ko.ts 「P」 표기 잔존 4곳」 정리 티켓 소관). 새로 추가하는 문안에만 R3을 적용한다.

### 구현 내용 요약

알림 결산(20260827_014)이 활동 단위로 접어준 보상이 착지점인 프로필 피드에서 다시 평면
나열되던 문제를 해소했다. `user_activity_feed`에 활동 참조 컬럼을 추가하고, 프로필
「최근 활동」이 같은 활동의 이벤트를 한 카드로 접는다.

1. **마이그레이션 107** — `user_activity_feed.strava_activity_id BIGINT NULL` +
   `(user_id, strava_activity_id) WHERE strava_activity_id IS NOT NULL` 부분 인덱스 +
   `COMMENT ON COLUMN`. FK 없음, 백필 없음.
2. **`recordFeedEvent` 5번째 위치 인자** `stravaActivityId?: number | null`.
   전달 3곳(`badge-engine`·`strava/sync`·`drop-engine`), 미전달 3곳(미션 참가·픽업·미션 완료).
3. **타입** — `ActivityFeedRow.strava_activity_id`, `Database` Insert, `database.generated.ts`.
   `makeFeedItem()`의 레거시 합성 행은 항상 `null`.
4. **`[username]/page.tsx`** — non-null id를 모아 `strava_activities` 1회 조회로 활동 이름 맵
   생성 → `ProfileClient` → `FeedSection`(옵셔널 `activityNames`).
5. **`FeedSection.tsx`** — `buildFeedEntries()`(필터 먼저 → 묶음, NULL 미묶음, 임계값 2건,
   위치는 최신 멤버 자리) + `ActivityGroupCard`(인라인 아코디언, `inert`로 접힌 패널을
   탭 순서에서 제외).
6. **`ko.ts`** — `groupBadges`·`groupBadgesWithPoints`·`groupRecords`·`groupMoreCount`.
   컴포넌트에 한글 리터럴 0.
7. **WARN 반영** — `drop-engine`이 지급한 `point_reward`를 `item_dropped` 피드 metadata에도
   싣는다(아래 「주요 의사결정」 참고).

### 잔여 이슈

- **프로필 묶음 카드 실물 미확인** — 마이그레이션 실행 시점에 활동 참조가 실린 행이 0건이라
  묶음이 원리적으로 나올 수 없다. **신규 Strava 동기화 1회 이후** staging 프로필에서 확인 필요.
- **인터랙션 리뷰 제안 미반영** — apple-design 기준 리뷰가 낸 제안 중 아래가 남았다.
  머지를 막는 항목은 없었고 사용자 확인 후 별도 처리 예정.
  1. 펼친 자식 간 간격과 그룹 밖 이웃 카드 간격이 둘 다 `spacing-8`이라 펼치는 순간 그룹
     경계가 사라진다 → 들여쓰기 자리에 세로 레일
  2. 40×40 리딩 슬롯에 제네릭 `ActivityIcon`이 들어가고 배지 아트는 24px 셋째 줄로 밀렸다
     → 겹친 배지 스택을 리딩으로 (「여러 개가 접혀 있다」 어포던스도 함께 생긴다)
  3. 펼침·접힘 모두 easeOutQuint라 접을 때 끝이 끌린다 → 접힘은 역곡선·짧게
  4. 열린 상태에서 헤더만 `scale(0.98)`이라 눌리는 순간 카드가 두 조각으로 보인다
  5. `focus-visible` 링 부재 — `ListRowCard`가 이번에 disclosure 컨트롤이 됐다
- **`.githooks/pre-commit`의 staging 동기화 머지 오탐** — 훅이 `git diff --cached`에서
  `+status: CLOSED`를 찾는데, staging을 머지하면 다른 세션이 이미 승인·CLOSED 처리한 티켓이
  신규 추가로 잡혀 항상 차단된다. 머지 커밋(`MERGE_HEAD` 존재)일 때는 건너뛰는 보완이 필요하다.
- **`recordFeedEvent`가 실패를 완전히 삼킨다** — `try/catch` 후 `console.error`만 남긴다.
  이번 컬럼 추가와 무관하게 피드 기록 유실이 항상 무증상으로 진행되는 구조다.
  실패 카운터·모니터링 훅이 없다. **별도 티켓 소관.**
- **`activityNames` 조회가 타인 프로필에서도 실행된다** — `FeedSection`은 본인 프로필에서만
  렌더되므로 불필요한 쿼리 1회. 경미.
