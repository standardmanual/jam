# [Infra] 스토리북 프로덕션 제외 빌드 분기 + EEXIST 레이스 근본 원인 제거

## 배경 / 문제 정의

배포 파이프라인에서 서로 얽힌 두 가지 문제가 확인됐다.

### ① 스킬 문서 서술이 사실과 다름

`.claude/skills/jam-work/SKILL.md` 1.6절이 다음과 같이 적고 있다:

> (main/프로덕션 빌드 스크립트는 `next build`만 실행 — 스토리북은 의도적으로 프로덕션에 나가지 않는다)

실제로는 `jam-web/package.json`의 `build` 스크립트가 **브랜치 구분 없이 하나뿐**이다:

```
rm -rf storybook-static public/storybook && storybook build && cp -r storybook-static public/storybook && next build
```

`origin/main`·`origin/staging`·작업 브랜치의 `package.json`이 모두 동일함을 확인했다
(`git show origin/main:jam-web/package.json`). 즉 **프로덕션 빌드도 스토리북을 굽고
`public/storybook`으로 배포한다.** 문서가 서술하는 "의도"는 코드에 구현된 적이 없다.

부수 영향: `jam-web/public`은 133MB(그중 `public/badges` 97MB)다. 이 전체가
`storybook-static`으로 복사된 뒤 다시 `public/storybook`으로 복사되므로, 프로덕션 배포
산출물에 100MB대 자산이 통째로 중복 적재된다. 서비스 코드에서 `/storybook`을 참조하는
곳은 한 군데도 없다(`grep -rn "/storybook" jam-web/src/` 결과 0건).

### ② 스토리북 빌드 EEXIST 플레이크

2026-08-27 staging 배포가 아래 오류로 실패했다가, 동일 커밋 재배포로 그냥 통과했다:

```
■ Error: EEXIST: file already exists, mkdir './storybook-static/badges/activity'
  at async mkDirAndCopy (node:internal/fs/cp/cp:318:3)
  ... Copying static files: public at storybook-static
```

이는 재발이다. 선행 티켓 `20260823_001`에서 동일 증상(`storybook-static/badges/poi/mountain`)을
"이전 빌드 잔여물" 가설로 보고 `build` 스크립트 앞에 `rm -rf storybook-static public/storybook`을
추가했으나, **그 방어가 이미 들어간 상태에서 다시 발생했다.** 잔여물 가설이 틀렸다는 뜻이다.

#### 근본 원인 (이번에 특정)

`public`을 `storybook-static`으로 복사하는 주체가 **둘이고, 이 둘이 동시에 실행된다.**

1. **Storybook의 `staticDirs` 복사** — `.storybook/main.ts`의 `staticDirs: ['../public']`.
   `storybook/dist/core-server/index.js:8359`에서 `fs.cp(from, targetPath, { recursive, force })`.

2. **Vite의 `copyPublicDir`** — `@storybook/builder-vite`가 Vite `root`를 `resolve(configDir, '..')`
   = `jam-web/`으로 잡는다(`builder-vite/dist/index.js:1455`). 그런데 **`publicDir`을 어디서도
   설정하지 않는다** (`storybook`·`@storybook/*` 패키지 전체 grep에서 `publicDir` 0건).
   따라서 Vite 기본값인 `<root>/public` = `jam-web/public`이 그대로 적용되고,
   `build.outDir`은 같은 `storybook-static`이다(`builder-vite/dist/index.js:1487`).
   Vite는 빌드 종료 시 `publicDir`을 `outDir`로 복사한다.

`storybook/dist/core-server/index.js:10064`에서 staticDirs 복사가 `effects` 배열에 push되고,
프리뷰(Vite) 빌드와 함께 `Promise.all`로 **동시 실행**된다(`:10085`).

Node의 `fs.cp`는 대상 디렉터리가 없다고 판단하면 `mkDirAndCopy`에서 **`recursive` 옵션 없이
`mkdir`을 호출**한다(`node:internal/fs/cp/cp:318`). stat 시점과 mkdir 시점 사이에 Vite가 같은
디렉터리를 만들면 EEXIST가 난다. 타이밍 의존이라 재배포로 통과한 것도 설명된다.

`rm -rf`가 무력했던 이유가 여기 있다. 빌드 **시작 전** 상태를 정리하는 조치인데, 실제 충돌은
빌드 **도중** 두 복사 주체 사이에서 일어나기 때문이다.

#### 위험도

①에서 프로덕션도 스토리북을 굽는 것이 확인된 이상, 이 플레이크는 **프로덕션 배포도 때릴 수 있다.**

## 상세 요구사항

### 서비스/코드베이스 관점

**② 근본 원인 제거 (선행 — 두 환경 모두에 적용)**

- 대상: `jam-web/.storybook/main.ts`
- `viteFinal`에서 `publicDir: false`를 설정해 **Vite 쪽 중복 복사를 제거**한다.
  `public` 자산 제공은 Storybook의 `staticDirs: ['../public']`이 이미 담당하므로 기능 손실이 없다.
- 이로써 동시에 같은 목적지에 쓰는 주체가 하나로 줄어 레이스 자체가 사라진다.
- 부수 효과: 133MB를 두 번 복사하던 것이 한 번으로 줄어 스토리북 빌드 시간도 단축된다.
- 선행 티켓이 넣은 `rm -rf storybook-static public/storybook`은 **유지한다.** 근본 원인은
  아니었지만, `cp -r storybook-static public/storybook`이 대상 디렉터리가 이미 있으면
  중첩 복사(`public/storybook/storybook`)를 만드는 것을 막는 별개의 유효한 방어다.

**① 프로덕션에서 스토리북 제외 (사용자 결정: 문서 정정이 아니라 원래 의도대로 빌드를 가른다)**

- 대상: `jam-web/package.json`의 `build` 스크립트
- Vercel의 `VERCEL_ENV` 환경변수로 분기한다. `VERCEL_ENV=production`(= main 배포)일 때만
  `storybook build` + `cp` 단계를 건너뛰고 `next build`만 실행한다.
- **로컬 `npm run build`와 staging 빌드는 기존과 동일하게 스토리북을 포함한다.**
  (`VERCEL_ENV`가 없거나 `preview`이므로) — staging에서 스토리북 빌드 경로가 계속 검증된다.
- 분기 로직은 `package.json`의 한 줄짜리 셸 체인에 밀어넣지 말고 **별도 스크립트 파일**로
  분리해 가독성과 리뷰 가능성을 확보한다.
- 프로덕션에 `public/storybook`이 없어도 `next build`가 실패하지 않아야 한다
  (단순 정적 디렉터리이므로 부재해도 무방함을 확인할 것).

**① 문서 정정**

- 대상: `.claude/skills/jam-work/SKILL.md` 1.6절
- "스토리북 배포는 이미 자동화돼 있다" 문단을 **실제 동작에 맞게 다시 쓴다.**
  - staging 머지·push 시 스토리북이 함께 구워져 배포된다 → 유지 (사실)
  - "main/프로덕션 빌드 스크립트는 `next build`만 실행" → 이번 변경으로 **비로소 사실이 됨.**
    다만 "브랜치 기준"이 아니라 **`VERCEL_ENV=production` 기준**으로 갈린다는 점을 정확히 적는다.
  - 스토리북 확인은 staging 도메인(`jam-stage.vercel.app/storybook`)에서 한다는 점을 명시한다.

### 구현 내용 요약

**② EEXIST 근본 원인 제거** — `jam-web/.storybook/main.ts`의 `viteFinal`이 반환하는
`mergeConfig` 대상에 `publicDir: false`를 추가했다. `@storybook/builder-vite`가 Vite `root`를
`jam-web/`으로 잡고 `publicDir`을 설정하지 않아 기본값 `<root>/public`이 적용되던 것을 끈다.
이로써 `storybook-static`에 `public`을 복사하는 주체가 Storybook `staticDirs` 하나로 줄어
동시 쓰기 레이스 자체가 사라진다. `staticDirs: ['../public']`은 그대로라 자산 제공은 동일하다.

**① 프로덕션에서 스토리북 제외** — `jam-web/scripts/build.mjs`(신규)를 만들어 `VERCEL_ENV`로
분기한다. `production`이면 `next build`만, 그 외(로컬·`preview`=staging)면
`storybook build` → `public/storybook` 복사 → `next build`를 순차 실행한다.
어느 경로로 갔는지 첫 줄에 로그를 남겨 Vercel 빌드 로그에서 판별 가능하다.
선행 티켓 20260823_001의 `rm -rf storybook-static public/storybook` 방어는 유지했고
(중첩 복사 방지), 프로덕션 경로에서도 수행해 잔여물이 산출물에 섞이지 않게 했다.
`jam-web/package.json`의 `build`는 `node scripts/build.mjs` 한 줄로 교체했다.

**① 문서 정정** — `.claude/skills/jam-work/SKILL.md` 1.6절의 "스토리북 배포는 이미 자동화돼
있다" 문단을 다시 썼다. 분기 기준이 **브랜치가 아니라 `VERCEL_ENV`**임을 표로 명시하고,
스토리북 확인은 `https://jam-stage.vercel.app/storybook`에서 하며 프로덕션에서는
`/storybook`이 404임을 적었다.

### 배포 후 회귀 발견 및 수정 (같은 날 추가 조치)

머지·CLOSED 처리 후 사용자가 직접 `jam-stage.vercel.app/storybook`이 404임을 신고해 확인한
결과, **`VERCEL_ENV` 기준 판정 자체가 이 저장소 구성에서 틀렸다**는 게 드러났다.

- 원인: Vercel 프로젝트가 "jam"(main→Production, 그 외 브랜치→Preview)과 "jam-stage" 둘로
  나뉘어 있다. `jam-stage.vercel.app`을 서빙하는 건 **"jam-stage" 프로젝트**이고, 이 프로젝트는
  **`staging` 브랜치 자체를 자기 "Production" 환경으로 매핑**해뒀다. 그 결과
  `VERCEL_ENV === 'production'` 판정이 jam-stage 배포에서도 참이 되어 스토리북이 빠졌다.
  실측: `vercel inspect <jam-stage 배포> --logs`에서
  `[build] VERCEL_ENV=production → 스토리북 제외 (프로덕션)`을 확인.
  반면 실제 프로덕션(`j-a-m.app`, "jam" 프로젝트 Production)은 원래도 정상적으로 제외 상태였다
  (이쪽은 회귀가 아니었다).
- 수정: 판정 기준을 `VERCEL_ENV`에서 **`VERCEL_GIT_COMMIT_REF === 'main'`(git 브랜치명)**으로
  교체(`jam-web/scripts/build.mjs`). 브랜치명은 Vercel 프로젝트의 환경 라벨 설정과 무관하게
  항상 동일하므로 프로젝트가 몇 개로 나뉘어 있든 정확하다.
- `.claude/skills/jam-work/SKILL.md` 1.6절에도 이 사고 경위와 "VERCEL_ENV로 판정하면 안 되는
  이유"를 경고로 남겼다 — 다음에 같은 실수가 재발하지 않도록.
- 로컬 재검증: `VERCEL_GIT_COMMIT_REF=main npm run build` → `storybook-static` 미생성 확인.
  `VERCEL_GIT_COMMIT_REF=staging npm run build` → `public/storybook` 정상 생성, EEXIST 없음 확인.
- **실환경 재검증 필요**: 이 수정을 staging에 push한 뒤 jam-stage 프로젝트의 다음 빌드 로그에서
  `[build] VERCEL_GIT_COMMIT_REF=staging → 스토리북 포함`을 확인하고,
  `https://jam-stage.vercel.app/storybook/index.html`이 (로그인 후) 200으로 실제 서빙되는지
  재확인할 것.
