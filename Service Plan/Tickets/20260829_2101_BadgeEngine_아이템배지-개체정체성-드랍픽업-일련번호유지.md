# [BadgeEngine] 아이템배지 개체 정체성 — 드랍·픽업 시 일련번호 유지 + 인터랙션 플로우

## 배경 / 문제 정의

드랍 메뉴(POI 캐러셀 → 배지 상세 바텀시트)에 아이템배지의 일련번호(`serial_prefix`+`serial_number`,
예: `FLOQ710411`)를 표시해달라는 요청에서 출발해, 현재 드랍·픽업 구현을 점검한 결과 **개체
정체성 모델 자체가 의도와 반대로 동작**하고 있음을 확인했다.

### 현재 구현 (코드 확인 완료)

- `poi_drops`(`004_phase7_user_drops.sql`)는 `badge_id`(배지 "종류")만 참조하고, 구체적
  개체(`inventory_items`)를 가리키는 컬럼이 없다.
- **유저 드랍**(`POST /api/drops`, [route.ts:274-303](../../jam-web/src/app/api/drops/route.ts)):
  원래 갖고 있던 `inventory_items` row(고유 일련번호 보유)를 `dropped_at`/`drop_id`로
  **소프트 삭제**하고, `poi_drops`엔 `badge_id`만 복사한다 — 원본 개체와의 연결이 끊긴다.
- **픽업**(`pickup_drop()` RPC, `004_phase7_user_drops.sql`): `poi_drops.badge_id`를 갖고
  **완전히 새로운 `inventory_items` row를 INSERT**한다. `BEFORE INSERT` 트리거
  (`008_serial_prefix.sql`, `034_drop_engine_v2_schema.sql`)가 이 새 row에 새 일련번호를
  뽑는다.
- 결과: 드랍한 사람의 원본 개체는 고아로 소프트 삭제된 채 남고, 픽업한 사람은 **전혀 다른
  일련번호를 가진 새 개체**를 받는다 — "발급 시점에 확정된 일련번호가 소멸할 때까지
  유지"라는 의도와 정반대다.
- 유저 드랍의 `expires_at`은 `011_phases_15_18.sql:57`의 컬럼 `DEFAULT (NOW() + INTERVAL
  '30 days')`로 인해 예외 없이 30일 후 자동 소각된다(`/api/cron/poi-cleanup`) — 이 역시
  의도(유저 드랍은 기간 개념이 없어야 함)와 어긋난다.
- 일련번호 유니크 체크(`assign_random_serial()`)가 `WHERE serial_number = candidate`로
  **소프트 삭제 여부와 무관하게 테이블 전체**를 스캔해, 개체가 파괴되어도 번호가 영구히
  묶여 반환되지 않는다.
- **(2026-08-29 추가 발견)** `inventory_items.inventory_id → inventory.id → inventory
  → public.users.id → auth.users`가 전부 `ON DELETE CASCADE`([001_initial_schema.sql:135,155](../../jam-web/supabase/migrations/001_initial_schema.sql))로
  연결돼 있다. 즉 유저가 탈퇴하면 그가 **현재 보유(Held/Slotted) 중인 `inventory_items`가
  그 즉시 하드 삭제**된다 — 이력을 남길 새도 없이 개체 자체가 사라져, "개체는 소멸할
  때까지 유지"라는 의도와 "탈퇴해도 이력은 조회 가능해야 한다"는 어드민 요구
  모두와 충돌한다.

### 의도 (정책 확인 완료)

- 아이템배지는 유저에게 발급되는 순간 난수 일련번호가 1회 확정되고, **그 개체가 소멸할
  때까지 유지**된다. 동일 이름이라도 개체마다 번호가 다른 이유는 향후 유저 간
  거래·수집 기능에서 **개체를 고유하게 식별·검증하는 수단**으로 쓰기 위함이다.
- 드랍은 이 개체를 다른 위치로 옮기는 것일 뿐, 재발급이 아니다. 픽업은 항상 **소유권
  이전**이며, 어떤 경우에도 새 일련번호를 만들지 않는다.
- **일련번호가 확정(발급/Minting)되는 시점은 정확히 둘뿐이다**: ① 드랍엔진을 통한
  직접 지급(활동 보상 등), ② 시스템(앰비언트) 드랍이 **POI에 배치되는 순간**. 픽업은
  이 중 어디에도 속하지 않는다 — 즉 `source`가 `system`이든 `user`든, `poi_drops`는
  항상 **이미 발급된 `inventory_items` row를 참조**해야 한다.
- 기한이 있는(시스템) 드랍이 미픽업 상태로 만료되면 개체는 소멸하고, 그 일련번호는
  재사용 가능한 풀로 돌아가야 한다.
- 유저 드랍은 기한 개념이 없다 — 회수 액션도, 만료도 없이 **픽업될 때까지 영구 대기**한다.
  (열린 채로 남겨두는 게 의도된 정책이며 버그가 아님을 확인함, 2026-08-29.)

## 확정된 개념 모델

### 객체

| 객체 | 정의 |
|---|---|
| `Badge` | 배지 도안(카탈로그). `name`/`rarity`/`image_url`/`item_book_id`. 인스턴스화되지 않는 종류 |
| `InventoryItem` | 발급된 실물 개체. `serial_prefix`+`serial_number`로 유일하게 식별. 하나의 `Badge`에 여러 개체가 대응(1:N) |
| `PoiDrop` | "지금 POI에 무언가 놓여 있다"는 사실. **`Badge`가 아니라 항상 `InventoryItem`을 참조해야 한다** (현재는 `badge_id`로 잘못 참조 중) |
| `CustodyEvent` | `InventoryItem` 한 개체에 점유(custody) 변화가 일어날 때마다 쌓이는, 수정 불가능한 이력 항목. 어드민 조회 필요(2026-08-29 추가)로 신규 도입 |

### 상태 전이 (`InventoryItem`)

```
Minted(발급 — ①드랍엔진 직접지급 또는 ②시스템드랍 배치 시점, 이때 serial 확정)
  │
  ├─ ①직접지급 ──────────────────────────────▶ Held(즉시 소유자 있음)
  │
  └─ ②시스템드랍 배치 ─▶ AtPoi(소유자 없음, 관리자 설정 기한 有)
                            ├─ 픽업(소유권 이전, serial 불변) ─▶ Held
                            └─ 기한 만료(미픽업)              ─▶ Destroyed(serial 재사용 풀로 반환)

Held(보유중)
  ├─▶ Slotted(컬렉션 장착) ─▶ Held
  ├─▶ Consumed(조합 재료 소모) ─▶ Destroyed(serial 재사용 풀로 반환)
  ├─▶ Dropped(유저가 POI에 배치 — 무기한, 소유자 없음, 만료·회수 경로 없음)
  │      └─ 픽업(소유권 이전, serial 불변) ─▶ Held(새 소유자)
  └─▶ Orphaned(소유자 계정 탈퇴 — 유저에게 비노출, 어드민 전용, 이후 처리 미정) ※ 2026-08-29 추가

Slotted(장착중)
  └─▶ Orphaned(소유자 계정 탈퇴) ※ 2026-08-29 추가 — 장착 중에도 소유자는 여전히 존재하므로 동일하게 적용
```

**`Orphaned` 상태의 후속 처리(어드민이 무엇을 할 수 있는지)는 이 티켓의 스코프가
아니다** — 별도 티켓 [20260829_2150](20260829_2150_Admin_고아-아이템배지-관리-기능.md)
참고. 여기서는 "소유자를 잃어도 개체가 파괴되지 않고 보존된다"는 상태 존재 여부까지만
정의한다.

### 표준 불변식 (신규 스코프 아님 — 이 모델이 요구하는 조건)

1. **원자적 소유권 이전** — `InventoryItem`의 소유권을 바꾸는 모든 액션(현재는 픽업)은
   `SELECT ... FOR UPDATE` 등 배타 락 하에 실행되어야 한다. 동시 픽업 경합 시 하나만
   성공해야 하며, 절대 같은 개체가 두 계정에 동시에 존재해선 안 된다. (기존
   `pickup_drop()`도 이미 이 패턴을 쓰고 있었다 — 재작성 시에도 유지해야 하는 조건이다.)
2. **Custody(점유) 상태의 상호 배타성** — `Held`/`Dropped`/`Slotted`/`Consumed`는 한
   개체에 대해 항상 정확히 하나만 참이어야 한다. 지금은 개별 nullable 컬럼(`dropped_at`,
   `slotted_in` 등) 조합과 애플리케이션 레벨 체크(`item_slotted`, `already_dropped`)로
   느슨하게 유지되고 있다 — 재구현 시 이 배타성을 명시적으로 지켜야 새 상태가 추가돼도
   깨지지 않는다.

### 이력 로그 (`CustodyEvent`) — 어드민 조회 요구로 신규 도입 (2026-08-29)

어드민에서 "발급된 배지가 지금 어디에·누구에게 있는지, 최초 생성부터 어떻게 흘러왔는지"를
조회해야 한다는 요구가 확인됨(잡스토리: 유저 조회 화면과 같은 성격의 조회 + 전체 현황
감사·투명성 확보. 어뷰징 모니터링 대시보드는 스코프 아님). "현재 상태(어디에·누가)"는
`InventoryItem`의 현재 값만으로 충분하지만, "흘러온 흐름"은 지금 모델에 전혀 없다 —
상태가 바뀔 때마다 이전 값을 덮어쓸 뿐 기록이 남지 않는다.

**이벤트 종류** — 위 상태 전이 다이어그램의 화살표와 1:1 대응(새 전이를 지어내지 않음):

| event_type | 대응 화살표 | 참여자(역할) |
|---|---|---|
| `Minted`(발급) | ─ → Held / ─ → AtPoi | to_user(직접지급 시 즉시 소유자, 시스템드랍 배치 시 없음) |
| `UserDrop`(유저 드랍 배치) | Held → Dropped | from_user(내려놓은 사람), POI |
| `Pickup`(픽업=소유권 이전) | Dropped/AtPoi → Held | to_user(주운 사람), from_user(직전 소유자, 시스템드랍 픽업 시 없음), POI |
| `Expire`(만료 소각) | AtPoi → Destroyed | POI만(유저 없음) |
| `Slot`(컬렉션 장착) | Held → Slotted | actor(=소유자) |
| `Unslot`(장착 해제) | Slotted → Held | actor(=소유자) |
| `Consume`(조합 소모) | Held → Consumed | actor(=소유자) |
| `Orphan`(소유자 탈퇴) | Held/Slotted → Orphaned | from_user(탈퇴한 이전 소유자) — 2026-08-29 추가 |

`User`는 이벤트 종류에 따라 **from_user(이전 점유자)**·**to_user(새 점유자)**·**actor(변화를
일으킨 소유자)** 중 해당 역할만 채워진다 — 세 역할을 하나의 컬럼으로 뭉개면 역할 정보가
사라진다. **Append-only 불변식**: `CustodyEvent`는 생성 후 절대 수정·삭제되지 않으며, 항상
그 시점의 사실을 자체 보유한다(`InventoryItem`의 현재 값을 참조해 역산하지 않는다).

**스냅샷 불변식(2026-08-29 추가, 필수)**: `from_user`/`to_user`/`actor`는 `users` row에
대한 살아있는 참조만으로는 안 된다 — **그 시점의 유저 식별자(예: username)를 이벤트
자체에 값으로 복사해 저장**해야 한다. 유저가 탈퇴하면 `public.users` row가 하드
삭제되므로(위 CASCADE 문제), 라이브 조인에만 의존하면 탈퇴 후 이력에서 그 유저를
가리키는 자리가 전부 빈 값이 된다 — "탈퇴해도 유저 아이디는 표시돼야 한다"는 요구를
만족하려면 이 스냅샷이 필수다.

### 개체 파괴 방식 — 소프트 삭제로 확정 (2026-08-29, 열린 결정 2 해소)

파괴된(`Destroyed`) 개체를 하드 삭제하면 그 개체의 `CustodyEvent` 이력이 고아가 되어 위
어드민 요구 자체가 성립하지 않는다 — **소프트 삭제로 확정**한다. `InventoryItem`에
`destroyed_at`(기존 `dropped_at`과 같은 관례) 컬럼을 추가하고, `assign_random_serial()`의
유니크 체크를 `WHERE serial_number = candidate AND destroyed_at IS NULL`로 좁힌다. 개체
row와 이력은 파괴 후에도 그대로 남고, 번호만 새 개체에 재사용 가능해진다.

### 신규 결정 — 어드민 "재발급된 일련번호" 필터

**정의**: 어떤 `InventoryItem`이 "재발급된 일련번호"를 가졌다는 건, 같은
(`serial_prefix`+`serial_number`) 조합을 가진 **다른(파괴된) `InventoryItem`이 과거에
존재했다**는 뜻이다. 새 객체가 아니라 소프트 삭제 모델 위의 조회(파괴된 개체도 row가
남아있으므로 같은 번호를 가진 row가 2개 이상 존재하는지 확인) — `CustodyEvent`의
`Minted` 이벤트 이력으로도 같은 답을 얻을 수 있다.

**부수 효과(참고, 스코프 확장 아님)**: 만약 이 필터에서 **파괴되지 않은(둘 다 살아있는)**
개체가 같은 번호로 2개 이상 걸리면, 이건 정상적인 재발급이 아니라 지난 게이미피케이션
리뷰에서 지적한 **복제(duplication) 버그**가 실제로 발생했다는 신호다. 어드민 화면에서
이 두 경우(정상 재발급 vs 동시 존재 이상)를 시각적으로 구분해서 보여주는 게 좋다.

### 스코프 밖 (provisional — 지금 구현하지 않음)

거래·경매장 기능은 이번 스코프가 아니다. 검토는 했으나 현재 어떤 흐름도 요구하지 않아
**신규 객체·스키마를 만들지 않는다**: `Listing`(거래 등록) 상태, `Currency` 객체 통합,
`TradeRecord`(거래 이력 — 위 `CustodyEvent`와는 목적이 다르다: `TradeRecord`는 유저 대면
수집 서사/가치검증용이고, `CustodyEvent`는 어드민 조회·감사용이다), 자전거래 방지
quality gate, 완성조건-거래 분리 가드레일. 필요해지는 시점에 위 불변식(원자성·상호배타
상태) 위에 얹으면 된다 — 지금 미리 만들면 검증되지 않은 스키마만 남는다.

## 인터랙션 플로우 브레드보드

**잡스토리**: POI 반경 내에 있는 유저가 드랍 캐러셀에서 특정 POI에 놓인 아이템배지를
확인하고, 상세(일련번호 포함)를 본 뒤 픽업한다. (드랍하는 쪽 플로우도 같은 화면 내
상태이므로 함께 다룬다.)

### 현재 구현 매핑

- POI 드랍 캐러셀 = `PoiCarouselModal.tsx` (`PoiCard`)
- 배지 상세 바텀시트 = `BadgeDetailSheet.tsx`

### 브레드보드

```
POI 드랍 캐러셀 (PoiCarouselModal / PoiCard)
- [닫기] → 지도로 복귀

- (POI에 드랍된 아이템배지가 없는 경우)
  [ POI 이름, 거리, 빈 상태 안내(기존 문구 유지) ]
  - [여기에 드랍] → 인벤토리 그리드(같은 카드 내 전환)
```

### 신규 결정 — 일련번호 표시 위치

개념 모델 수정(픽업=소유권 이전, 재발급 아님) 덕분에 **모든 `PoiDrop`이 항상 이미
발급된 `InventoryItem`을 가리키므로, 픽업 전에도 일련번호가 이미 존재한다.** 즉 애초
막혔던 문제(드랍 상태엔 일련번호를 가진 실물이 없음)가 개념 모델 수정으로 해소된다.
`BadgeDetailSheet`의 "드랍 컨텍스트" 카드(POI명·드랍한 사람 표시 영역)에 일련번호를
함께 노출하면 된다 — 별도 화면 신설 불필요.

### 신규 결정 — 픽업 목록과 드랍 액션은 서로 배타적이지 않다

현재 `PoiCard`([PoiCarouselModal.tsx:404](../../jam-web/src/components/PoiCarouselModal.tsx))는
`isPickupState = drops.length > 0`로 분기해 **픽업 목록이 있으면 드랍하기 버튼 자체를
렌더링하지 않는다.** 이건 "No broken objects"(대상의 속성·액션이 화면에서 분리되면
안 된다) 위반이다 — POI에 이미 다른 유저가 드랍해 둔 배지가 있어도, 자신도 보유 아이템이
있다면 같은 POI에 함께 드랍할 수 있어야 한다. 두 조건(픽업 가능 목록 유무, 드랍 액션
노출 여부)은 독립적인 축으로 재설계해야 한다 — 위 브레드보드에 반영함.

### 서비스/코드베이스 관점
- `poi_drops`에 `inventory_item_id` FK 추가 (`badge_id`는 조인으로 파생, 컬럼 유지 여부는
  마이그레이션 설계 시 결정)
- 유저 드랍 생성(`POST /api/drops`): 기존 `inventory_items` 소프트 삭제 대신
  `poi_drops.inventory_item_id`로 연결 + 소유자 필드만 비움
- `pickup_drop()` RPC: 신규 INSERT 제거, 기존 row의 소유자만 UPDATE하는 방식으로 재작성
  (원자적 락 유지)
- 유저 드랍 `expires_at` 컬럼 기본값(`011_phases_15_18.sql`) 제거 — 유저 드랍은
  `expires_at IS NULL`
- 앰비언트 드랍 생성 로직이 배치 시점에 `InventoryItem`을 선발급하도록 변경
- `inventory_items`에 `destroyed_at` 컬럼 추가, `assign_random_serial()` 유니크 체크를
  `destroyed_at IS NULL` 조건으로 좁힘 (개체 파괴 방식 — 소프트 삭제 참고)
- `CustodyEvent` 신규 테이블 도입 — `Minted`/`UserDrop`/`Pickup`/`Expire`/`Slot`/`Unslot`/
  `Consume`/`Orphan` 8종 이벤트, append-only. `from_user`/`to_user`/`actor`는 유저
  식별자를 스냅샷 값으로 저장(위 스냅샷 불변식 참고). 드랍·픽업·만료소각·장착·해제·
  조합소모·탈퇴처리 각 로직이 상태 변경과 같은 트랜잭션 내에서 이벤트 row도 함께
  INSERT해야 함
- `inventory_items.inventory_id`의 FK를 `ON DELETE CASCADE`에서 `ON DELETE SET NULL`로
  전환하고 컬럼을 nullable화 — 계정 탈퇴 시 `inventory`가 삭제돼도 `inventory_items`
  row 자체는 하드 삭제되지 않고 `inventory_id`만 비워져 `Orphaned` 상태가 된다(위
  CASCADE 문제 해결). 탈퇴 처리 로직이 삭제 직전에 `Orphan` 이벤트를 기록해야 함
  (`public.users` row가 사라지기 전에 유저 식별자를 스냅샷해야 하므로 순서 중요)
- 기존 데이터 마이그레이션 정책 결정 필요 — 이미 소프트 삭제된 과거 드랍 데이터를
  소급 정합시킬지, 시행일 이후 데이터에만 적용할지 (과거분은 `CustodyEvent` 이력이
  비어있는 채로 시작하게 됨 — 감수 여부 확인 필요)

  요구와 "재발급된 일련번호" 필터 요구를 동시에 만족하기 위함(위 "개체 파괴 방식" 절)
- 탈퇴 처리: 앱 레벨 탈퇴 로직이 저장소에 없어 `BEFORE DELETE ON public.users` DB
  트리거로 `Orphan` 이벤트 기록 — 어떤 경로로 삭제되든 항상 실행되는 게 더 견고하다고
  판단(오케스트레이터 승인)
- 앰비언트 드랍 원자성: 개체 선발급 + `poi_drops` 연결 + `Minted` 기록을 애플리케이션
  레벨 순차 실행 대신 `mint_and_place_ambient_drop()` RPC로 묶어 부분 실패 시 고아
  방지(1차 게이트 리뷰 지적으로 확정)
- Minted 이벤트는 앰비언트 배치 경로만 연결하고, 활동보상 직접지급 경로는 스코프 밖으로
  남김(아래 잔여 이슈 참고) — 티켓 원문의 구현계획 목록(7개 로직)에 포함되지 않았고,
  스코프를 넓히면 드랍엔진 전체를 건드리게 돼 별도 검토가 필요하다고 판단
- 게이트 리뷰 중 발견된 사전 존재 이슈(RPC들이 SECURITY DEFINER + anon/authenticated
  직접 호출 가능, 인증 검증 없음)는 이 티켓 스코프 밖으로 판단해 별도 작업 칩으로
  분리(task_18728e27) — 새로 만든 4개 함수가 기존 `pickup_drop`과 같은 패턴을
  그대로 따랐을 뿐 이 티켓이 만든 신규 취약점은 아님
