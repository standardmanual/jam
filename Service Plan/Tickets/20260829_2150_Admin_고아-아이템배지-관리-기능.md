# [Admin] 고아(`Orphaned`) 아이템배지 관리 기능

## 배경 / 문제 정의

[20260829_2101](20260829_2101_BadgeEngine_아이템배지-개체정체성-드랍픽업-일련번호유지.md)에서
`inventory_items`가 계정 탈퇴 시 CASCADE로 하드 삭제되는 문제를 발견했다 — 유저가
탈퇴하면 그가 보유(Held/Slotted) 중이던 아이템배지 개체가 이력을 남길 새도 없이
즉시 사라진다.

**확정한 방향**: 개체를 삭제하지 않고 소유자 필드만 비운 채 보존한다(`Orphaned` 상태
신설). 유저에게는 노출되지 않고 어드민만 볼 수 있다. **단, 이 개체를 어드민이 실제로
"관리"한다는 게 구체적으로 무엇을 뜻하는지는 아직 정의되지 않았다** — 그래서 별도
티켓으로 분리했다.

## 아직 없는 것 — 잡스토리

[20260829_2139](20260829_2139_Admin_아이템배지-발급현황-이력조회-화면.md)의 조회
화면에서 `Orphaned` 상태인 개체를 "보는" 것까지는 그 티켓 스코프에 포함돼 있다.
이 티켓이 다뤄야 하는 건 그다음이다 — **어드민이 고아 개체를 왜 들여다보고, 무엇을
하고 싶어 하는가?** 예를 들어:

- 희귀 등급 배지가 고아 상태로 묶여 유통량이 줄어드는 걸 막고 싶은가?
- 탈퇴한 유저의 잔여 자산을 정리(영구 폐기)하고 싶은가?
- 특정 유저에게 보상으로 재배정하고 싶은가?
- 아니면 그냥 "사라지지 않았다"는 사실만 확인하면 충분하고, 별도 액션은 필요 없는가?

이 질문에 따라 나올 화면과 액션이 완전히 달라진다 — 지금 임의로 하나를 골라 설계하면
검증되지 않은 기능이 된다("No speculative additions"). 착수 전에 `/layers-user-needs`로
이 잡스토리부터 확정하는 걸 권장한다.

**해소(2026-08-30)**: 아래 "확정된 잡스토리·스펙" 절 참고 — 위 4개 후보 중 하나만 고르는
대신, 조회 + 두 가지 관리 액션(영구 폐기·재배정)이 **모두** 필요하다는 게 확인됐다.

## 확정된 잡스토리 (2026-08-30, `/layers-user-needs`)

**When** — 어드민이 다음 상황 중 하나에서 `Orphaned` 개체를 마주친다: 일반적인 유통량
모니터링 중 / 특정 희귀 등급 배지의 유통량이 부족해 보여 원인을 추적할 때 / 정기 운영
점검 루틴 중 / 특정 유저의 CS 문의(과거 자산 문의 등)에 대응하는 중.

**Want / So that** (세 액션 모두 필요, 상호 배타적이지 않음):
1. **조회만으로 충분한 경우** — "사라지지 않고 보존됐다"는 사실 확인만 필요. 별도
   액션 없이 [20260829_2139](20260829_2139_Admin_아이템배지-발급현황-이력조회-화면.md)의
   조회 화면(`Orphaned` 필터)으로 이미 해소됨.
2. **영구 폐기** — 희귀 배지가 고아 상태로 묶여 유통량을 왜곡하는 게 확인되면, 그 개체를
   영구히 파괴해 유통량 계산에서 제외하고 싶다.
3. **재배정** — 특정 유저(CS 대응 등)에게 보상 목적으로 그 개체를 다시 지급하고 싶다.

## 확정된 스펙 — 관리 액션

### 공통
- 진입 상태는 항상 `Orphaned`(선행 티켓에서 정의) 하나뿐 — `Held`/`Slotted`에서 소유자
  계정 탈퇴로만 도달.
- 권한: 신규 역할 체계를 만들지 않는다. 기존 `users.is_admin`/`ADMIN_EMAILS` 화이트리스트
  그대로 사용(No speculative additions) — 어드민 화면 진입 권한과 동일.
- **일괄 처리 필요**: 여러 `Orphaned` 개체를 목록에서 다중 선택해 한 번에 폐기 또는
  한 명의 재배정 대상에게 한 번에 재배정할 수 있어야 한다(탈퇴 러시 시 개체가 누적되는
  상황을 상정).

### 액션 A — 영구 폐기 (`Orphaned → Destroyed`)
- 기존 `Destroyed` 상태와 동일하게 소프트 삭제(`destroyed_at`) 처리, 일련번호는 재사용
  풀로 반환 (선행 티켓 "개체 파괴 방식" 절과 동일 메커니즘 — 신규 파괴 방식을 만들지 않음).
- 되돌릴 수 없는 액션 — 확인 모달 필수(단건·일괄 모두). 일괄 폐기는 선택 개수를 모달에
  명시한다.
- 신규 `CustodyEvent` 이벤트 타입 필요: `AdminDestroy` (`Orphaned → Destroyed`). 기존
  8종에 없는 전이이므로 추가.

### 액션 B — 재배정 (`Orphaned → Held`)
- 대상 유저 지정: 유저명/이메일 검색 UI (유저 ID 직접 입력 방식은 채택하지 않음 —
  검색이 CS·모니터링 시나리오 모두에 더 자연스러움).
- **알림 없음** — 재배정된 유저에게 별도 알림을 보내지 않는다("조용히 지급"). 기존
  배지획득 알림 파이프라인을 재사용하지 않는다(의도적 결정, 사후 CS 대응 성격상
  유저가 능동적으로 알아채길 기다리지 않아도 됨).
- **인벤토리 용량 제약 적용**: 대상 유저의 `inventory.max_slots`가 꽉 찬 경우 실패
  처리 — 픽업(`inventory_full`, 422)과 동일 정책, 신규 예외 규칙을 만들지 않음. 일괄
  재배정 중 일부만 실패할 수 있으므로 개체별 성공/실패 결과를 구분해 보여줘야 한다.
- 신규 `CustodyEvent` 이벤트 타입 필요: `AdminReassign` (`Orphaned → Held`). `to_user`
  = 재배정 대상, `from_user` = 없음(직전 소유자는 이미 `Orphan` 이벤트에 스냅샷돼 있음).

### 설계 논점 해소 (2026-08-30, 구현 착수 시점)
- **`CustodyEvent.actor` 확장 불필요로 해소**: `108_item_identity_custody_model.sql`의
  `custody_events.actor_user_id`/`actor_username`은 애초에 `public.users(id)`를 가리키는
  범용 컬럼이다 — 어드민도 `public.users` row(`is_admin=true`)이므로 별도 컬럼 신설 없이
  그대로 재사용 가능. `AdminDestroy`/`AdminReassign` 이벤트는 `actor_user_id`/
  `actor_username`에 **액션을 수행한 어드민**의 식별자를 채우면 된다.
- **필요한 마이그레이션**: `custody_events.event_type` `CHECK` 제약(현재
  `'Minted','UserDrop','Pickup','Expire','Slot','Unslot','Consume','Orphan'` 8종)에
  `'AdminDestroy'`, `'AdminReassign'`을 추가해야 한다. `ALTER TABLE ... DROP CONSTRAINT
  ... ADD CONSTRAINT`로 처리(마이그레이션 파일 작성은 jam-developer, 실행은 사용자 승인
  후 오케스트레이터).
- **일괄 처리 트랜잭션 경계 확정**: 개체별 독립 트랜잭션으로 처리한다 — 일괄 재배정 중
  일부 개체가 대상 유저 인벤토리 꽉 참으로 실패해도 나머지는 계속 처리하고, 개체별
  성공/실패 결과를 응답에 담아 화면에서 구분 표시한다(전체 롤백 안 함).

## 확정된 것 (선행 티켓에서 결정됨, 여기선 전제로만 사용)

- `Orphaned`는 `Held`/`Slotted`에서만 진입 가능하고, 트리거는 소유자 계정 탈퇴뿐이다
- 개체는 파괴되지 않고, 일련번호·`CustodyEvent` 이력 전부 보존된다
- 진입 시 `Orphan` 이벤트가 기록되며, 탈퇴한 유저의 식별자가 스냅샷으로 남는다
- `Orphaned`에서 나가는 전이(액션)는 아직 없다 — 이 티켓이 정의해야 할 부분
