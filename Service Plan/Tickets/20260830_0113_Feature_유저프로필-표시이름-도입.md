# [Feature] 유저 프로필 표시 이름(display_name) 도입

## 배경
현재 유저를 화면에 노출할 때 쓰는 유일한 텍스트는 `username`(아이디, 온보딩에서 정한
`@handle` 형식)이다. 아이디 외에 자유 형식의 "이름"을 별도로 입력할 수 있게 하고,
이름이 설정된 유저는 화면에서 아이디 대신 이름이 보이도록 한다.

## 상세 요구사항 (요청 원문 기준)
1. 프로필 편집 화면에 아이디(username) 입력란과 별개로 "이름" 입력란을 추가한다.
2. 이름을 입력하면, 현재 아이디(username)가 노출되던 위치에 **이름이 대신** 노출된다.
3. 이름을 입력하지 않았거나(NULL) 빈 문자열로 지웠으면, 그 위치에는 **아이디(username)를
   그대로** 노출한다 (표시 전용 폴백 — DB에 username을 복사해 채우지 않는다. NULL이면
   화면 렌더 시점에 username으로 대체).
4. 이름은 필수 입력값이 아니다. 비워둔 채 다른 필드(예: 아이디)만 저장해도 된다.
5. 수정 횟수 제한 없음 — username과 달리 쿨다운·이력 제약을 두지 않는다.
6. **글자 수 제한은 인스타그램의 "이름(Name)" 필드 정책과 동일하게 반영한다** — 최대
   **30자**. 그 외 형식 제한(허용 문자·중복 검사·금칙어)은 인스타그램과 마찬가지로
   두지 않는다 — 공백·이모지·특수문자·대소문자 모두 허용. 저장 시 앞뒤 공백만 trim.
   trim 후 빈 문자열이면 NULL로 저장한다(= "이름 없음" 상태로 취급, 아이디로 폴백).

## 범위 밖 (이번 티켓에서 건드리지 않음)
- **어드민 화면**(`src/app/admin/**`)은 대상 아님 — 내부 운영자는 계속 실제 username으로
  유저를 식별해야 한다. `admin` 유형은 MODULAR/이 정책과 무관하게 별도 파이프라인.
- **URL 슬러그** `/{username}` 라우팅 자체는 변경하지 않는다. 이름은 "노출 텍스트"만
  대체하며, 프로필 URL·팔로워API 조회 키(`username`)는 계속 username 기준이다.
- `/{username}` 페이지의 `generateMetadata` 브라우저 탭 타이틀은 이번 범위에서 제외
  (별도 DB 조회가 필요해 비용 대비 우선순위 낮음 — 개선 리뷰에서 판단).
- 온보딩 화면(최초 가입 시 username 설정)에는 이름 입력란을 추가하지 않는다 — 이름은
  프로필 편집 화면에서만 설정 가능.

## DB 변경
`users` 테이블에 nullable 컬럼 추가:
```sql
ALTER TABLE users ADD COLUMN display_name text;
ALTER TABLE users ADD CONSTRAINT users_display_name_length CHECK (
  display_name IS NULL OR length(display_name) BETWEEN 1 AND 30
);
```
- 형식 제한 없음(username과 달리 `~ '^[a-z0-9._]+$'` 같은 CHECK 없음).
- 마이그레이션 번호는 저장소 `jam-web/supabase/migrations/` 기준 **다음 번호**를 push
  직전 재확인해서 사용한다 (현재 로컬·원격 staging 모두 최신 110 — 111부터 시작하되
  구현 시점에 다시 확인할 것. 병렬 세션 충돌 이력 있음).
- jam-developer는 SQL 파일 작성까지만 하고 실제 실행은 하지 않는다 (오케스트레이터가
  4단계 승인 후 실행).

## API 변경
1. `PATCH /api/profile` (`src/app/api/profile/route.ts`)
   - `display_name` 필드를 옵셔널로 받는다.
   - 검증: trim 후 30자 초과면 400 (`INVALID_FORMAT` 재사용 또는 신규 코드).
     trim 후 빈 문자열이면 `null`로 저장(폴백 상태로 전환).
   - 중복 검사 없음 (username과 다른 지점).
2. 유저 목록/카드를 반환하는 API들의 select에 `display_name` 추가하고 응답에 포함:
   - `src/app/api/users/[username]/followers/route.ts`
   - `src/app/api/users/[username]/following/route.ts`
   - `src/app/api/users/search/route.ts`
   - (같은 패턴의 다른 유저 카드 API가 더 있는지 확인 후 포함)

  범위 밖으로 제외

각 API에서 "이름 우선, 없으면 username" 판정은 두 가지 방식으로 나눴다:
1. 클라이언트가 라우팅에도 username을 써야 하는 경우(팔로워/팔로잉 목록 등) — API는
   `username`·`display_name`을 모두 내려주고 화면이 `getDisplayName()`으로 렌더 시점에 계산
2. 순수 표시 텍스트만 필요한 경우(미션 랭킹, 드랍 목록, 인벤토리 이력) — 서버가
   `getDisplayName()`으로 미리 계산해 기존 필드(`username`/`dropper_name`)에 그대로 담아
   내려줘 클라이언트 변경을 최소화
