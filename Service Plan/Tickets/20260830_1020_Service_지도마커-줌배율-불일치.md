# [bug] 드랍 지도 — 마커 크기와 지도 줌 배율 불일치

## 배경
프로덕션(`j-a-m.app`)에서 사용자가 실기기(iOS Safari, 위치 아이콘으로 미루어 GPS 사용 중)로
드랍 지도를 확인하던 중 스크린샷을 제보. 지도 타일(도로·건물·라벨 크기)이 보여주는
줌 배율에 비해 POI/체크인 배지 마커(회색·주황 원형 아이콘, 파란 위치 점)가 과도하게
커 보이고 서로 심하게 겹쳐 있음. 사용자 소견: "웹페이지 확대 액션과 지도 확대 액션이
동시에 또는 중첩되어 발생하는 현상 같다."

## 관련 코드 (사전 조사 — 오케스트레이터)
`jam-web/src/components/map/MapView.tsx`:
- 마커 크기는 React state `zoom` → `getZoomScaleMultiplier(zoom)`(3단계: 1.3/1.69/2.08배)으로
  계산되고, `zoom_changed` 이벤트를 120ms 디바운스해 `setZoom(map.getZoom())`으로 갱신한다
  (`MapView.tsx:242,345-348`).
- 마커는 `useEffect` deps에 `zoomScale`이 걸려 있어 값이 바뀔 때마다 전체 재생성된다
  (`MapView.tsx:374-404,406-462`).
- 뷰포트 메타는 `initialScale:1, maximumScale:1`로 페이지 자체 핀치줌을 막으려 하고 있으나
  (`src/app/layout.tsx:22-29`), iOS Safari는 접근성 정책상 `maximum-scale`/`user-scalable`을
  최신 버전에서 무시하는 경우가 있어 완전히 막히지 않을 수 있다.
- 지도 컨테이너(`mapRef` div, `MapView.tsx:485`)에 `touch-action` 제약이 없어, 두 손가락
  제스처가 네이버 지도 SDK의 자체 핀치줌과 브라우저 네이티브 페이지 핀치줌 양쪽에 동시에
  걸릴 가능성이 있다.

## 가설 (검증 필요 — jam-developer가 확인)
1. 브라우저 네이티브 페이지 핀치줌과 네이버 지도 자체 핀치줌 제스처가 동일 터치 이벤트에
   중첩 반응해, 지도 타일은 지도 SDK 기준 줌으로 렌더되는 반면 화면 자체는 브라우저가
   추가로 확대해 보여주는 상태일 수 있다 → `touch-action: none`(또는 `pan-x pan-y`
   제외)을 지도 컨테이너에 걸어 네이티브 페이지 줌 자체를 원천 차단해야 할 수 있다.
2. `zoom_changed` 120ms 디바운스 중 연속 핀치 제스처가 짧게 여러 단계를 오가며, 최종
   settle 값과 debounce 시점에 캡처된 `map.getZoom()` 값이 어긋나는 타이밍 이슈일 수 있다.
3. 위 두 가지가 동시에 겹쳐(네이티브 줌으로 뷰포트 스케일이 바뀌는 도중 지도 SDK의
   zoom_changed도 함께 튀어) 마커 재계산 시점의 zoom 값이 실제 화면과 어긋났을 수 있다.

## 요청 원문
스크린샷을 보면 지도배율과 마커크기가 맞지 않아. 이건 웹페이지를 확대한 액션과 지도
확대 액션이 동시에 또는 중첩되어서 발생하는 현상 같은데 확인이 필요.

## 완료 기록

### 조사 결과 (코드 레벨 — 실기기 재현 불가로 코드 검토 기반)

**1) `touch-action` 미설정 — 확인됨, 실제 결함**
`MapView.tsx`의 지도 컨테이너(`mapRef` div)에 `touch-action` 제약이 전혀 없었다. `layout.tsx`의
`maximumScale: 1`은 iOS Safari가 접근성 정책상(WebKit이 iOS 10부터 `user-scalable=no`/
`maximum-scale`을 의도적으로 무시함) 완전히 신뢰할 수 없어, 지도 위 핀치 제스처가 브라우저
네이티브 페이지 핀치줌으로도 동시에 해석될 여지가 있었다. `touch-action`은 viewport meta와
무관하게 항상 적용되는 별도의 CSS 계약이라, 이 컨테이너에 한해 브라우저의 기본 터치 제스처
처리(페이지 핀치줌 포함)를 원천 차단하는 것이 근본적이고 부작용 없는 수정이다. 네이버 지도
SDK는 CSS가 아니라 자체 JS 터치 리스너로 팬/줌을 처리하므로 지도 자체의 조작감에는 영향이
없다. → `touch-none`(Tailwind, `touch-action: none`) 클래스를 컨테이너에 추가.

**2) `zoom_changed` 120ms 디바운스 — 이론적으로 가능한 레이스, 확정은 불가**
디바운스 콜백은 발화 시점이 아니라 콜백 실행 시점의 `map.getZoom()`을 읽으므로, 단순히
"디바운스 중 캡처된 값이 오래된 값"이라는 시나리오는 성립하지 않는다(항상 최신값을 읽음).
다만 네이버 지도 SDK가 핀치 종료 후 관성/모프 애니메이션을 `zoom_changed` 이벤트 없이
내부적으로 이어갈 경우, 마지막 `zoom_changed` 발화 시점 + 120ms에 캡처된 값이 애니메이션이
실제로 끝난 뒤의 최종 줌과 다를 가능성은 배제할 수 없다(SDK 내부 동작이라 코드 레벨로는
확정 불가). → 아래 3번 방어책으로 커버.

**3) 방어책 — `idle` 이벤트 시점 강제 재동기화 (신규 적용)**
근본 원인을 100% 특정할 수 없으므로, `idle`(팬/줌/관성 애니메이션이 모두 끝난 뒤에만 발생하는
지도 SDK의 최종 상태 신호) 리스너에서 무조건 `setZoom(map.getZoom())`을 호출하도록 추가했다.
이 경로는 `zoom_changed` 디바운스와 완전히 독립적이므로, 어떤 원인(디바운스 타이밍, SDK 내부
애니메이션, 네이티브 페이지 줌과의 상호작용 등)으로 중간에 어긋나더라도 지도가 실제로 멈춘
시점에는 항상 최종적으로 정확한 줌 값으로 수렴한다.

### 변경 내용
- `jam-web/src/components/map/MapView.tsx`
  - 지도 컨테이너 div에 `touch-none`(`touch-action: none`) 클래스 추가 — 브라우저 네이티브
    페이지 핀치줌이 지도 위 터치 제스처에 동시 반응하지 않도록 차단.
  - `idle` 이벤트 리스너에 `setZoom(map.getZoom())` 추가 — 지도가 완전히 정지할 때마다
    실제 줌 값으로 무조건 재동기화(디바운스 레이스와 무관하게 항상 최종 수렴 보장).
  - 관련 주석 갱신(`zoom_changed` 디바운스 옆에 idle 보정과의 관계 설명 추가).
