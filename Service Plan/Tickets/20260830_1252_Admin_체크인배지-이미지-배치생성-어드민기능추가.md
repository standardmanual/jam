# [Admin] 체크인 배지 이미지 배치 생성 어드민 기능 추가 + 누락 22개 배지 백필

## 배경 / 문제 정의
과거 지하철역 체크인 배지 973개를 METRO 디자인으로 일괄 재생성할 때
(`20260824_020_Content_지하철역-POI-배지-METRO디자인-929개-일괄-재생성.md`),
이름이 "역"으로 끝나지 않는 22개(버스정류장·리무진·정류소 등, `category='transit'`)는
새 텍스트 레이아웃이 맞지 않는다는 이유로 의도적으로 제외되어 구 디자인 이미지가 그대로 남아있다.

이번에 사용자가 이 22개도 동일한 METRO 디자인으로 채우기로 결정했다. 또한 지금까지 이런 배치
작업은 `jam-web/scripts/badge-image-gen/generate.js`를 CLI로 직접 실행하는 방식이었는데,
앞으로 신규 체크인 배지(신규 역·신규 산 등)가 생길 때마다 개발자 개입 없이 관리자가 어드민에서
바로 이미지를 생성할 수 있도록 UI로 노출해달라는 요청이 추가되었다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 기존 파이프라인(`jam-web/scripts/badge-image-gen/`)의 로직을 재사용해 어드민 API 라우트로 노출한다.
  - `generate.js` 엔진 자체는 디자인 무관 — 그대로 재사용
  - `configs/metro-poi-badge.config.js`, `configs/mountain-poi-badge.config.js` 등 기존 config를
    디자인 선택지로 어드민에 노출
  - 배경 SVG(`backgrounds/*.svg`)·폰트 캐시는 기존 자산 재사용, 신규 디자인 추가 시에만 확장
- 어드민 화면에 "체크인 배지 이미지 배치 생성" 메뉴/섹션 추가
  - 디자인(METRO/MOUNTAIN 등) 선택 → 대상 배지 목록 미리보기(dry-run) → 실행 흐름
  - 대상 필터: 기존 config의 `dataSource` 쿼리를 그대로 쓰되, 22개 백필을 위해
    METRO config의 데이터소스 필터(`이름이 '역'으로 끝나는 것만`)를 완화하거나
    별도 옵션으로 `category='transit'` 전체를 포함할 수 있게 조정
  - 실행 결과: 이미지 파일 생성 + `public.badges.image_url` UPDATE용 SQL 생성
    (기존 관례대로 `jam-web/supabase/seed/update_{design-name}_images.sql`로 저장)
  - **DB 반영은 어드민에서 자동 실행하지 않는다** — SQL 파일 생성까지만 하고, 실제 UPDATE 실행은
    이미지 배포 확인 후 사람이 별도로 승인·실행한다 (이미지-DB 배포 순서 사고 재발 방지,
    `20260824_020` 참고)
  - 서비스 role 키 등 민감 정보는 서버 사이드(API 라우트)에서만 사용, 클라이언트 노출 금지
- 22개 백필 실행: 위 기능(또는 CLI 직접 실행)으로 22개 배지에 대해 METRO 디자인 이미지 생성
  → SQL 파일 커밋까지 진행. **실제 UPDATE 실행은 이미지가 프로덕션에 배포된 이후, 사용자 승인 하에
  오케스트레이터가 처리한다** (jam-developer 권한 밖).

## 구현 계획
1. 기존 `generate.js` + config 구조를 분석해 어드민 API 라우트(`/api/admin/badge-image-batch` 등)로
   감싼다 — dry-run 조회, 실행(이미지 생성+SQL 파일 생성) 두 단계로 분리
2. 어드민 화면에 배치 생성 UI 추가 (디자인 선택, 대상 미리보기, 실행 버튼, 결과/SQL 파일 경로 표시)
3. METRO config의 대상 필터를 조정해 22개 미디자인 배지를 포함 옵션 제공
4. 22개 배지 대상으로 실제 생성 실행 → SQL 파일 커밋
5. SQL 실행(DB UPDATE)은 게이트 리뷰 통과 후, 이미지 배포 확인 → 사용자 승인 → 오케스트레이터가 처리

  실제로는 정확히 이 22개만 추가로 잡힘). updateSqlTemplate의 WHERE절도 동일하게 확장.
- 어드민 API 라우트 `/api/admin/badge-image-batch`(POST: mode=preview|execute, GET: 디자인 목록)
  추가. `createRequire(process.cwd()+'/package.json')`로 engine.js/config를 실제 파일시스템에서
  동적 require — 웹팩 정적 번들링을 우회해 CLI와 완전히 동일한 __dirname 상대경로 로직이 그대로
  동작하도록 함. `next.config.ts`에 `outputFileTracingIncludes['/api/admin/badge-image-batch']`를
  추가해 `scripts/badge-image-gen/**`(엔진·config·폰트·배경 SVG)가 Vercel 배포 번들에 포함되도록 함.
- 어드민 화면 `/admin/badge-image-batch` 추가 — 디자인 선택(Select) → 대상 미리보기(preview,
  개수+샘플 목록) → 실행(execute) 흐름. 실행 결과는 성공/실패 개수, SQL(복사 버튼 포함) 표시.
  DB UPDATE는 이 화면에서 자동 실행하지 않는다.
- 사이드바 "운영 도구" 그룹에 "체크인 배지 이미지 배치 생성" 메뉴 추가.

  `public/badges/poi/metro/*.png`에 생성하고 `supabase/seed/update_metro-poi-badge_images.sql`을

### 게이트 리뷰 1차 FAIL 수정 (badge id 다대일 연결 dedupe)
- 게이트 리뷰에서 지적한 대로, `category IN ('train_subway','transit')`로 필터를 확장하면서
  같은 `badges.id`가 두 POI 행에 동시에 `linked_badge_id`로 연결된 케이스가 실제 프로덕션
  DB에 존재함을 재확인했다(읽기 전용 조회로 검증) — **강남역·선릉역·수서역 3개**
  (게이트 리뷰가 언급한 선릉역·수서역 2개 외에 강남역도 동일 패턴으로 추가 발견).
  전체 954행 중 고유 배지는 951개.
- `scripts/badge-image-gen/lib/dedupe-by-badge-id.js`(신규)로 badge id 기준 dedupe 유틸을
  분리했다. `category` 우선순위 배열(`['train_subway','transit']`)을 받아 우선순위가 높은
  행을 유지하고, 버려지는 행은 `console.warn`으로 남긴다(CLI stdout·API 라우트 서버 로그
  양쪽에서 확인 가능).
- `metro-poi-badge.config.js`의 `dataSource()`에 `category` 컬럼을 select에 추가하고 이
  dedupe 유틸을 적용 — train_subway 쪽 이름("강남역")을 우선해, 이미 934개 배치로 정확히
  배포된 이미지가 transit 중복 행("강남역 신분당선" 등)에 덮어써지지 않도록 했다.
- `mountain-poi-badge-v2.config.js`에도 동일 패턴 위험을 점검했다(단일 category='mountain'
  이라 우선순위 배열 없이 적용). 실제 조회 결과 현재는 중복이 0건이었으나, 방어적으로 동일
  dedupe 유틸을 적용했다(향후 POI 데이터 정합성 문제 예방).
- **재검증 결과**: `metro-poi-badge.config.js` dataSource 실제 실행 → 반환 951행, 고유 badge
  id 951개로 정확히 일치(불일치 없음). `mountain-poi-badge-v2.config.js` → 847행, 847개
  일치(원래도 중복 없었음, dedupe는 no-op으로 확인). 22개 백필에 사용한 `--ids` 목록에는
  중복 3개(강남역·선릉역·수서역)가 포함되지 않아 기존에 배포한 22개 이미지·SQL은 영향 없음.
  강남역·선릉역·수서역 이미지 파일도 이번 세션에서 수정되지 않았음을 `git status`로 확인
  (기존 934개 배치 산출물 그대로 유지).

  이름이 바뀌었다. 이 config들은 그 이후 재실행된 적이 없어 방치돼 있었고, 그대로 실행했다면
  대상이 0건으로 조회되는 버그였다(이번 22개 백필을 위해 실제 실행하며 발견). 이번 티켓
  범위에서 함께 수정했다 — 이미 생성된 기존 934/847개 이미지에는 영향 없음(파일은 이미
  존재, DB image_url도 이미 반영됨).
- **METRO 필터 확장 방식**: 별도 "22개 포함" 체크박스 UI를 추가하는 대신, `category IN
  ('train_subway','transit')`로 config 자체를 완화했다. `linked_badge_id IS NOT NULL` 조건과
  결합하면 transit 카테고리에서 실제로 걸리는 것은 22개(백필 대상)뿐이라(69개 중 47개는
  배지 미연결) 안전하고, 향후 신규 transit POI가 배지에 연결되면 자동으로 이 파이프라인
  대상이 되어 티켓의 "향후 신규 체크인 배지" 요구에도 부합한다.
  **(게이트 리뷰 수정)** 다만 이 확장은 강남역·선릉역·수서역 3개 배지에서 train_subway
  POI("강남역")와 transit POI("강남역 신분당선")가 같은 `badges.id`에 동시에
  `linked_badge_id`로 연결된 다대일 케이스를 함께 끌어들였다. 이 3개는 이미 934개 배치로
  정확히 이미지가 배포돼 있는데, 처리 순서상 나중 행(transit 쪽)이 같은 파일명에 덮어써
  잘못된 텍스트로 깨뜨릴 위험이 있었다. `dedupeByBadgeId`(train_subway 우선)로 dataSource
  단계에서 정리해 실제로는 951개(22개 백필 + 929개 기존, 강남역·선릉역·수서역 중복 3건
  제외)가 대상이 된다.
- **프로덕션 Vercel 파일쓰기 제약 대응**: Vercel 서버리스 함수는 배포 번들이 읽기 전용이라
  `public/`에 새 PNG를 쓰거나 `supabase/seed/`에 SQL을 저장하는 것이 실패할 수 있다. API
  라우트는 로컬(npm run dev) 실행 시엔 CLI와 동일하게 파일을 직접 저장하고, 파일쓰기가
  막힌 환경에서는 자동으로 base64 다운로드 폴백 + SQL 텍스트 응답으로 전환한다(응답 크기
  보호를 위해 base64 폴백은 150개로 제한). 이 제약은 플랫폼 레벨이라 완전히 우회할 수 없고,
  대량(수백 개) 배치는 기존처럼 로컬 CLI 실행을 권장 — 어드민 화면은 "향후 소량 증분"
  시나리오에 최적화했다.
- **엔진 코드 재사용 방식**: 웹팩 정적 import 대신 `createRequire` 기반 동적 require를
  선택했다 — engine.js 내부의 `__dirname` 상대경로 로직이 실제 파일시스템 경로에서만
  정확히 동작하기 때문에, CLI와 API 라우트가 완전히 동일한 코드·동일한 경로 계산 방식을
  공유하도록 했다(웹팩 번들 안에서 `__dirname`이 어떻게 재작성되는지에 기대는 대신).
