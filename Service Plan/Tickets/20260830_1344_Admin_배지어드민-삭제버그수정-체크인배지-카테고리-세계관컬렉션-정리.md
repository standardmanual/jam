# [Admin] 배지 삭제 버그 수정 + 체크인 배지 세부설정 카테고리 추가·세계관/컬렉션 제거

## 배경 / 문제 정의
어드민 배지 관리 화면(`/admin/badges/[id]`)에서 사용자가 다음 3가지 문제를 보고했다.

1. 배지 삭제 기능이 동작하지 않는다.
2. 체크인 배지(`type === 'checkin'`)의 세부 설정에 이 배지가 속한 **카테고리**를 지정하는
   기능이 없다.
3. 체크인 배지의 세부 설정에 **소속 세계관**·**소속 컬렉션** 선택 UI가 노출되는데, 체크인
   배지에는 이 개념이 맞지 않으므로 제거해야 한다.

### 코드 조사 메모 (오케스트레이터 사전 조사, 구현자가 재확인할 것)
- 삭제 흐름: `BadgeForm.tsx`의 `handleDelete()` → `DELETE /api/admin/badges/[id]`
  (`jam-web/src/app/api/admin/badges/[id]/route.ts` 93~121행). 코드만 보면 존재 확인(404) →
  소프트 삭제(`deleted_at` 세팅) → `invalidateUnclaimedDrops` 흐름이 정상으로 보이고,
  20260827_012에서 이미 존재하지 않는 id 404 처리를 붙였다. **정적으로는 버그가 보이지 않으므로
  실제 브라우저(또는 API 직접 호출)로 재현해 원인을 좁혀야 한다.** 의심 지점:
  - `getAdminUser()` 인증/세션 문제로 403이 나는데 프론트에서 에러 메시지가 묻히는 경우
  - 삭제 확인 모달(`showDeleteConfirm`)의 클릭 핸들러가 이벤트 버블링·form submit과 충돌하는
    경우 (모달 버튼이 `<form>` 안에 있고 `type="button"`이 맞는지 재확인)
  - FK 제약(예: `poi.linked_badge_id`, `checkin_badge_images` 등 체크인 배지 이미지 배치
    기능 — 티켓 20260830_1252 — 이 최근 추가한 테이블)이 소프트 삭제 update 자체에는 영향
    없어야 하지만, 연관 테이블 트리거·제약이 있는지 확인
  - 목록 화면(BadgeList/BadgesTable/BadgeCard)에 별도 삭제 버튼이 있는지도 확인 —
    `grep -rn "DELETE\|handleDelete\|삭제" jam-web/src/components/admin/badges/` 로 전수 확인
- 세계관/컬렉션 선택 UI: `BadgeForm.tsx` 491~527행. **타입 조건 없이 모든 배지 타입에
  공통으로 렌더링된다** — `type === 'item'` 전용 블록(530행~)과 달리 조건부 렌더링이 아님.
  체크인 배지일 때만 숨기려면 `type !== 'checkin'` 조건으로 감싸야 한다 (다른 타입에는
  그대로 유지).
- 체크인 배지 카테고리 개념: 목록 화면(`page.tsx` 36~42행 주석)에 따르면 "체크인 배지에는
  카테고리 컬럼이 없고, 연결된 지점(poi.category)으로만 분류된다"고 명시돼 있다. 즉 현재
  스키마상 `badges` 테이블에 체크인 배지 전용 카테고리 컬럼이 없다 — **이번 요청이 새 컬럼
  추가(DB 마이그레이션)를 요구하는지, 아니면 기존 `poi_categories`/`poi.category` 체계를
  배지 자체에도 노출하는 것인지 구현자가 판단해야 한다.** `poi_categories` 테이블이 이미
  존재하므로(`page.tsx` 80행에서 조회), 배지가 여러 지점에 연결될 수 있는 구조(N:M,
  `poi.linked_badge_id`)임을 감안하면 "배지의 카테고리"가 무엇을 의미하는지 모호할 수 있다 —
  가장 가능성 높은 해석은 badges 테이블에 nullable `category` 컬럼(slug, `poi_categories.slug`
  참조 또는 자유 슬러그)을 추가해 관리자가 이 체크인 배지가 어떤 지점 카테고리 계열인지
  직접 태깅하는 것. 모호하면 HALT로 보고할 것.

## 상세 요구사항

### 서비스/코드베이스 관점
1. **배지 삭제 버그 수정**
   - 먼저 재현: 로컬 또는 staging 어드민에서 실제로 배지 삭제를 시도해 어떤 에러가 나는지
     (네트워크 탭 응답 코드/본문, 콘솔 에러) 확인한다.
   - 근본 원인을 찾아 수정한다. 원인이 API인지 프론트인지에 따라 수정 범위가 달라진다.
   - 수정 후 실제 삭제 흐름(목록에서 삭제된 배지가 `status=active` 필터에 안 잡히고
     `status=inactive`/`all`에는 잡히는지)까지 확인한다.

2. **체크인 배지 카테고리 설정 추가**
   - `badges` 테이블에 체크인 배지용 카테고리 컬럼 추가 여부를 판단한다. 추가한다면:
     - 마이그레이션 파일을 `jam-web/supabase/migrations/0XX_설명.sql`로 작성한다
       (실행은 하지 않는다 — 5단계에서 오케스트레이터가 사용자 승인 하에 직접 실행).
     - 컬럼은 nullable로 추가하고 기존 행에는 영향 없어야 한다.
     - 값 후보는 `poi_categories.slug`를 재사용할지, 별도 값 집합을 쓸지 정하고 근거를
       완료 기록에 남긴다.
   - `BadgeForm.tsx`에 `type === 'checkin'`일 때만 보이는 "카테고리" Select를 추가한다.
     `poiCategories` prop을 이미 `page.tsx`에서 조회하고 있으니(80행) 재사용 가능한지 확인—
     단, 현재 `poiCategories`는 `BadgesFilterBar`에만 전달되고 `BadgeForm`에는 전달되지 않으므로
     `BadgeForm` 호출부(`new/page.tsx`, `[id]/page.tsx`)까지 prop 전달 경로를 확인해 연결한다.
   - API(`PUT /api/admin/badges/[id]`, `POST /api/admin/badges`)에 새 필드 저장 로직을 추가한다.
   - 목록 화면 카테고리 필터(`filterByPoiCategory`, `page.tsx` 36~42행)와의 관계를 확인한다 —
     이 필터는 POI 연결 기반이므로, 신규 배지 자체 카테고리 필드와 별개 개념인지 명확히 하고
     혼동되지 않도록 라벨을 구분한다 (예: 기존은 "연결 지점 카테고리", 신규는 "배지 카테고리"
     처럼 UI 라벨을 다르게 하거나, 완료 기록에 두 개념의 차이를 명시).

3. **체크인 배지 세계관/컬렉션 UI 제거**
   - `BadgeForm.tsx` 491~527행의 "소속 세계관"·"소속 컬렉션" Select 블록을
     `{type !== 'checkin' && (...)}` 조건으로 감싼다.
   - 체크인 배지 저장 시 `faction_id`·`item_book_id`를 항상 `null`로 강제할지(UI 숨김만으로는
     기존 값이 남아있을 수 있음), 아니면 단순히 UI만 숨기고 값은 그대로 둘지 판단한다.
     기존 체크인 배지에 이미 `faction_id`/`item_book_id`가 설정돼 있을 수 있으므로, UI만
     숨기면 "숨겨진 값이 남아있다"는 혼란을 줄 수 있다 — **체크인 타입으로 저장할 때 두
     필드를 명시적으로 null로 정리하는 것을 권장**하되, 기존 데이터에 영향이 있을 수
     있으니(다른 배지 타입으로 다시 바꿀 가능성 등) 신중히 판단하고 근거를 남긴다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

1. **배지 삭제 버그** — 원인 2가지를 모두 찾아 수정했다.
   - **주 원인**: `/admin/badges/[id]` 상세화면(`components/admin/badges/BadgeDetail.tsx`)의
     "삭제" 버튼이 애초에 `confirm()` 뒤 `console.log('Delete badge:', badge.id)`만 찍는
     미구현 스텁이었다("삭제 로직은 추후 구현" 주석). 사용자가 실제로 클릭하는 삭제 버튼이
     이거라서 "동작하지 않는다"는 보고와 정확히 일치한다. `BadgeActiveToggleButton.tsx`와
     동일한 shadcn `AlertDialog` 패턴으로 교체하고, 실제 `DELETE /api/admin/badges/[id]`를
     호출하도록 구현했다.
   - **부 원인**: `/admin/badges/[id]/edit`의 `BadgeForm.tsx` 삭제 확인 모달 버튼 2개
     ("삭제 확인"·"취소")에 `type="button"`이 빠져 있었다. 이 모달은 `<form onSubmit=...>`
     내부에 있어, 버튼 기본 타입(`submit`)이 적용되면 클릭 시 `handleDelete`(DELETE 요청)와
     동시에 `<form>`의 `onSubmit`(저장용 PUT 요청)이 함께 발화해 두 요청이 경합한다.
     `type="button"`을 추가해 해결했다.
   - 목록 화면(`BadgeList`/`BadgesTable`/`BadgeCard`)에는 별도 삭제 버튼이 없음을 확인했다
     (전수 grep 결과 상세화면 스텁 1건만 검출).

2. **체크인 배지 카테고리 설정 추가**
   - `badges` 테이블에 nullable `category`(text) 컬럼을 추가하는 마이그레이션을 작성했다
     (`jam-web/supabase/migrations/113_badges_category.sql`, 실행은 보류 — 사용자 승인 후
     오케스트레이터가 직접 실행).
   - 값 집합은 기존 `poi_categories.slug`를 재사용한다 (FK, `ON DELETE SET NULL`). 근거는
     아래 "주요 의사결정" 참조.
   - `BadgeForm.tsx`에 `type === 'checkin'`일 때만 보이는 "배지 카테고리" Select를 추가했다.
     `poiCategories` prop을 `new/page.tsx`·`[id]/edit/page.tsx`에서 `poi_categories` 테이블을
     조회해 새로 전달하도록 연결했다 (기존에는 목록 화면 `page.tsx`에서만 조회하고 있었음).
   - API(`POST /api/admin/badges`, `PUT /api/admin/badges/[id]`)에 `category` 필드 저장 로직을
     추가했다. 클라이언트뿐 아니라 서버에서도 `type === 'checkin'`이 아니면 항상 `null`로
     강제한다 (기존 `condition_json`의 체크인 강제 null 패턴과 동일선상).
   - 목록 화면의 기존 "지점 카테고리" 필터(연결된 지점의 `poi.category` 기준)와는 별개
     개념임을 라벨로 구분했다 — 신규 필드는 "배지 카테고리"로 명명하고, Select 하단에
     "연결된 지점의 카테고리와는 별개로, 이 배지 자체를 분류하는 값"이라는 설명 문구를
     추가했다. 목록 필터 자체는 변경하지 않았다(티켓 범위 밖).

3. **체크인 배지 세계관/컬렉션 UI 제거**
   - `BadgeForm.tsx`의 "소속 세계관"·"소속 컬렉션" Select 블록을 `{type !== 'checkin' && (...)}`
     조건으로 감쌌다. activity/item 타입에서는 기존과 동일하게 노출된다(회귀 없음).
   - 저장 시점에 `type === 'checkin'`이면 `faction_id`·`item_book_id`를 클라이언트·서버 양쪽
     모두 명시적으로 `null`로 정리하도록 했다(권장안 채택). 근거는 아래 "주요 의사결정" 참조.

### 주요 의사결정 / 핵심 메모
> 개발 과정에서 검토·결정된 사항, 선택하지 않은 대안과 그 이유.

- **카테고리 값 집합 — `poi_categories.slug` 재사용 vs 신규 값 집합**: 재사용을 선택했다.
  이미 어드민이 자유롭게 관리하는 단일 카테고리 소스가 있고("산", "자전거길", "공원" 등),
  "이 체크인 배지가 어떤 지점 계열에 속하는지"라는 의미가 지점 카테고리 개념과 사실상
  동일하다. 신규 값 집합을 만들면 관리 UI가 하나 더 필요해지고 두 카테고리 개념이 어긋날
  위험만 커진다. `poi.linked_badge_id`(배지가 여러 지점에 N:M 연결 가능)와는 독립적인
  필드임을 마이그레이션 주석·폼 안내 문구에 명시했다.
- **FK ON DELETE 정책 — SET NULL 채택**: `poi.category`는 `ON DELETE RESTRICT`(카테고리
  삭제 시 지점이 있으면 막힘)이지만, `badges.category`는 순수 분류/표시용 nullable
  필드이므로 카테고리가 삭제돼도 배지 저장 자체가 막히면 안 된다고 판단해 `SET NULL`을
  선택했다.
- **체크인 저장 시 faction_id/item_book_id 강제 null**: 티켓이 제시한 권장안을 채택했다.
  UI만 숨기고 값을 유지하면 "화면엔 안 보이는데 DB엔 남아있는" 상태가 되어, 이후 배지
  타입을 다시 activity/item으로 바꿨을 때 사용자가 설정한 적 없는 세계관/컬렉션 값이
  갑자기 나타나는 혼란이 생길 수 있다. 클라이언트(BadgeForm)와 서버(API) 양쪽에서 강제해
  방어를 이중화했다 — 클라이언트만 믿으면 API를 직접 호출하는 경로(예: 스크립트)에서
  값이 새어 들어갈 수 있기 때문.
- **카테고리 강제 null(비체크인 타입)도 동일 원칙 적용**: activity/item 배지에는 카테고리
  개념이 없으므로 서버에서 항상 null로 저장한다.
- **BadgeDetail.tsx(읽기 전용 상세화면)에 category 표시 추가 여부**: 하지 않았다. 티켓
  요구사항은 "세부 설정항목(저작 폼)에 카테고리 설정 기능 추가"이며 읽기 전용 상세화면의
  표시 항목 확장은 명시적으로 요청되지 않아 범위 밖으로 판단했다(알러트 INFO로 별도 기록).
