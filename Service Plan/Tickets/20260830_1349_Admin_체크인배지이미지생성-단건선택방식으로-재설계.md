# [Admin] 체크인 배지 이미지 생성 — 단건 선택 방식으로 재설계

## 배경 / 문제 정의
`20260830_1252`에서 "체크인 배지 이미지 배치 생성" 어드민 기능(`/admin/badge-image-batch`)을
만들었는데, 실제 사용 흐름과 맞지 않았다. 지금 구현은 **디자인(카테고리)을 고르면 그 카테고리
전체를 한 번에 배치 처리**하는 방식이다. 사용자가 원하는 건 그게 아니라, **특정 체크인 배지
1개를 찾아 선택하고, 그 배지에 표시할 텍스트를 직접 입력해 이미지를 생성/교체**하는 방식이다.
카테고리는 대상을 찾는 검색 필터로만 쓰인다.

## 상세 요구사항

### 서비스/코드베이스 관점
- **메뉴명 변경**: 사이드바 "체크인 배지 이미지 배치 생성" → **"체크인 배지 이미지 생성"**
  (`src/components/admin/adminNavItems.ts`, 페이지 타이틀도 동일하게)
- **기존 배치 실행(카테고리 전체 대상 preview→execute) 플로우는 제거**하고 아래 단건 플로우로
  대체한다:
  1. **검색**: 텍스트 검색(배지/POI 이름 키워드) + 카테고리 필터(디자인별 대상 카테고리,
     예: 지하철역/대중교통=`train_subway`,`transit`, 산=`mountain`)를 조합해 대상 배지를 조회.
     검색은 `poi` 조인에만 의존하지 말 것 — `20260830_1252`에서 POI 연결이 없는 배지
     3개(석촌역 9호선 등)가 조인 기반 조회에서 누락됐던 사고가 있었다. `badges` 테이블을
     기준으로 이름 검색(ILIKE)하고, 카테고리 필터는 가능하면 poi 조인으로 보조하되 조인이
     없어도 검색·선택 자체는 가능해야 한다.
  2. **목록 출력**: 검색 결과를 목록으로 보여주고(이름, 현재 이미지 유무/카테고리 등) 관리자가
     그중 **정확히 1개**를 선택한다.
  3. **선택 후**: 배지를 렌더링할 디자인(METRO/MOUNTAIN 등 — 기존 `BADGE_IMAGE_DESIGNS` 재사용)과,
     **이미지에 입력할 텍스트 입력창**(기본값은 배지/POI 이름으로 채워두되 자유 편집 가능)을
     보여준다.
  4. **생성/교체 실행**: 입력한 텍스트로 **그 배지 1개만** 렌더링해 이미지를 생성·교체한다.
     기존 `scripts/badge-image-gen/lib/engine.js`의 렌더링 엔진(`renderBadge` 등)을 재사용하되,
     `row.name` 대신 관리자가 입력한 텍스트를 렌더링에 사용하도록 확장 필요(엔진 시그니처
     조정 또는 렌더링 시 텍스트를 오버라이드하는 래퍼 추가).
  5. **DB 반영 정책 유지**: 이번에도 DB `image_url` UPDATE를 화면에서 자동 실행하지 않는다.
     생성된 이미지 파일을 배포 확인한 뒤 적용할 **해당 배지 1건짜리 UPDATE SQL**을 보여주고
     복사할 수 있게 한다(`20260824_020`의 이미지-DB 순서 사고 재발 방지 원칙 그대로 유지).
  6. 서버 사이드 처리(API 라우트), 인증 가드(`getAdminUser`) 등 기존 보안 구조는 그대로 유지.
- 기존 `/api/admin/badge-image-batch` 라우트의 `preview`/`execute`(카테고리 전체 대상) 모드는
  이번 요구사항과 맞지 않으므로 검색(search) + 단건 생성(generate-one) 모드로 교체한다.
  라우트 경로·이름은 자유롭게 재구성해도 된다(예: `/api/admin/badge-image/search`,
  `/api/admin/badge-image/generate`).
- 향후 신규 디자인 추가 시에도 이 단건 플로우가 그대로 확장 가능하도록 설계할 것
  (`BADGE_IMAGE_DESIGNS` 목록에 새 config만 추가하면 검색 카테고리 옵션에도 자동 반영되게).

### UI/UX 관점 (해당 시)
- MODULAR 적용 대상 아님(admin 유형 — 탐색 생략), shadcn/ui 표준 컴포넌트 사용

### 컨텐츠 관점 (해당 시)

## 구현 계획
1. `/api/admin/badge-image-batch` 라우트를 검색(search)·단건 생성(generate-one) 모드로 재작성
   — `config.dataSource`를 그대로 쓰지 않고 이름 검색 + 카테고리 필터를 지원하는 조회 로직 추가
2. `scripts/badge-image-gen/lib/engine.js`에 커스텀 텍스트로 렌더링할 수 있는 경로 추가
   (예: `renderBadge`가 받는 row에 `name` 대신 렌더링용 override 텍스트 필드를 허용)
3. 어드민 페이지를 검색/목록/선택/텍스트입력/생성 단계형 UI로 재작성, 메뉴명 변경
4. 로컬에서 검색→선택→텍스트 편집→생성까지 전 흐름 실제 실행 검증(스크린샷 또는 API 응답 기록)
5. 게이트 리뷰 통과 후 staging 반영

### 구현 내용 요약
`/admin/badge-image-batch`(카테고리 전체 배치 preview→execute)를 제거하고, 검색 → 목록 →
단건 선택 → 디자인/텍스트 확인·편집 → 생성 흐름의 `/admin/badge-image`로 재작성했다.

- 검색은 `badges` 테이블 이름 ILIKE를 기준으로 하고(poi 조인에 의존하지 않음), 카테고리
  필터는 poi 조인으로 보조만 한다. 실제로 `20260830_1252`에서 조인 기반 조회에 누락됐던
  POI 미연결 배지 "석촌역 9호선"이 이번 검색 로직으로는 정상 조회됨을 직접 확인했다(아래
  테스트 결과 참고).
- 카테고리 필터 옵션은 `BADGE_IMAGE_DESIGNS`에 추가한 `poiCategories` 필드에서 파생된다 —
  새 디자인을 config에 추가하면 검색 카테고리 옵션에도 자동 반영된다.
- 커스텀 텍스트 렌더링은 `engine.js`에 `renderBadgeWithText(row, overrideText, ...)`
  래퍼를 추가해 처리한다. 기존 `renderBadge`(CLI 배치 경로)는 건드리지 않았다 — 모든
  config의 `text.template`이 `'{{name}}'` 하나뿐이라 `row.name`을 관리자 입력 텍스트로
  바꿔치기하는 것만으로 별도 템플릿 변경 없이 오버라이드가 된다.
- 생성 결과는 항상 base64 미리보기 이미지를 응답에 포함한다(배치 버전은 파일 저장 실패
  시에만 폴백으로 포함했으나, 단건은 응답 크기 부담이 없어 매번 포함해 화면에서 바로
  확인 가능하게 했다).
- DB `image_url` UPDATE는 이번에도 화면에서 자동 실행하지 않는다 — 생성된 배지 1건짜리
  UPDATE SQL을 응답에 담아 복사 버튼을 제공한다.
- API 경로를 `/api/admin/badge-image-batch`(preview/execute) → `/api/admin/badge-image/search`,
  `/api/admin/badge-image/generate`로 재구성했다. `next.config.ts`의
  `outputFileTracingIncludes` 키도 `/api/admin/badge-image/generate`로 갱신했다(엔진 동적
  require 경로를 배포 번들에 포함시키기 위함).
- 사이드바 메뉴명을 "체크인 배지 이미지 배치 생성" → "체크인 배지 이미지 생성"으로 변경.

### 주요 의사결정 / 핵심 메모
- **engine.js를 최소 변경으로 확장**: 구현계획은 "row에 name 대신 렌더링용 override 필드
  허용" 또는 "엔진 시그니처 조정"을 제안했다. 모든 현재 config의 `text.template`이
  `'{{name}}'` 고정이라, `renderBadge` 자체를 바꾸는 대신 `row.name`을 오버라이드해
  기존 함수를 호출하는 얇은 래퍼(`renderBadgeWithText`)만 추가했다 — CLI 배치 경로
  (`generate.js`, `renderBadge` 직접 호출)는 전혀 건드리지 않아 회귀 위험이 없다.
- **카테고리 필터 옵션을 BADGE_IMAGE_DESIGNS에서 파생**: 별도 카테고리 목록을 새로 만들지
  않고 기존 디자인 화이트리스트에 `poiCategories` 필드만 추가했다 — 신규 디자인 추가 시
  검색 카테고리 옵션도 자동으로 늘어난다(티켓 요구사항).
- **검색은 badges 기준, 카테고리는 poi 조인 보조**: 이름 검색은 poi 연결 여부와 무관하게
  항상 동작해야 한다는 티켓 요구를 그대로 따랐다. 카테고리 필터를 걸 때만 poi 조인 결과와
  교집합을 취한다.
- **생성 결과 미리보기 이미지 항상 포함**: 배치 버전은 응답 크기 때문에 파일 저장 실패
  시에만 base64를 포함했지만, 단건 생성은 이미지 1장뿐이라 성공 여부와 무관하게 항상
  base64 미리보기를 포함해 관리자가 즉시 육안 확인할 수 있게 했다(티켓의 "생성 결과에는
  미리보기 이미지... 포함" 요구를 배치 버전보다 더 충실히 반영).
- **badges.category 컬럼(티켓 20260830_1344)과의 관계 — 별도 alerts 항목 참고**: 이번
  검색은 이 티켓 스펙대로 poi 조인만 카테고리 필터에 사용했다. 병렬로 진행 중인 1344가
  도입한 `badges.category`(어드민이 직접 태깅하는 대표 카테고리)는 개념이 다르고 아직
  staging에 반영되지 않아 이번 구현에 포함하지 않았다.

### 게이트 리뷰 1차 FAIL 수정 기록 (검색 API 대용량 카테고리 조회 오버플로)

**문제**: 카테고리 필터만으로(검색어 없이) 검색하면 poi 조인으로 badge id를 최대 500개 모은 뒤
`badges.in('id', [...최대 500개 UUID])`로 통째로 넘기는 방식이었다. 실제 프로덕션 규모
(MOUNTAIN 847건, METRO=train_subway+transit 948건)로 재현한 결과 URL이 19,000자를 넘어
HeadersOverflowError/fetch failed로 검색 자체가 실패했다.

**수정**: `/api/admin/badge-image/search/route.ts`를 재설계했다.
- **카테고리 단독 검색**: badge id 리스트를 애플리케이션에서 조립해 `.in()`으로 넘기는 단계를
  완전히 제거했다. `src/app/admin/badges/page.tsx`(체크인 배지 목록의 카테고리 필터)가 이미
  동일한 문제를 해결해둔 FK 임베디드 inner join 패턴(`poi!poi_linked_badge_id_fkey!inner`)을
  재사용해, `badges` 쿼리 자체에서 `.in('poi.category', poiCategories)`로 직접 필터한다.
  `.in()`으로 badge id를 넘기는 호출이 전혀 없어 대상 규모(847건/948건)와 무관하게 안전하다.
- **이름 검색 경로**: PostgREST의 `or=()` 필터가 임베디드 리소스 컬럼(`poi.name`)과 최상위
  컬럼(`name`)을 한 논리식으로 묶는 것을 지원하지 않음을 직접 확인했다(PGRST100: "failed to
  parse logic tree"). 그래서 `badges.name ILIKE q`(+카테고리 join)와 `poi.name ILIKE q`(+카테고리
  필터)를 별도 쿼리로 각각 최대 50건(MAX_RESULTS)까지만 조회한 뒤 애플리케이션에서 병합·정렬한다.
  이어지는 보조 조회(`poi.name`으로만 매칭된 badge id 조회)의 `.in()` 대상도 항상 50건 이하로만
  구성되도록 해 동일한 오버플로 재발을 원천 차단했다.
