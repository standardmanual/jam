# [Content] POI 블록(픽업 차단) 실패 토스트 문구 개선

## 배경 / 문제 정의

GPS 조작(스푸핑) 감지 시 해당 유저는 그 지점(POI)에서 72시간 동안 픽업이 막히고,
픽업 시도 시 `poi_blocked` 에러가 나며 아래 토스트가 뜬다.

> "이 지점에서는 잠시 이용이 제한됐어요. 시간이 지난 뒤 다시 시도해 주세요"
> ([ko.ts:416](../../jam-web/src/lib/i18n/ko.ts))

문제:
1. 문구가 기계적이라 유저가 "왜"·"무슨 상태"인지 이해하기 어렵다.
2. 이 차단은 **오탐(false positive) 가능성이 낮지 않다** — 실내·터널·건물 밀집지역 등
   GPS 신호 불안정으로 정상 유저도 걸릴 수 있다. 그런데 문구가 마치 부정행위자 취급하듯
   들리면 안 된다 (탐지 로직 자체를 UX_WRITING_GUIDELINE.md 4절의 "차단 사유 비공개" 원칙에
   따라 노출하지 않는 것과는 별개로, 톤 자체가 비난조가 되지 않아야 함).
3. 해결 방법(시간이 지나면 풀린다)은 있지만 "포지티브"하게 전달되지 않는다.

## 상세 요구사항

### 컨텐츠 관점
- `pickupPoiBlocked` 문구를 UX_WRITING_GUIDELINE.md 4절 [현상]→[원인]→[해결책] 구조로 재작성한다.
- 톤: 가이드 2-3절 표에 따르면 "부정 어뷰징 감지"는 전문·직접(Professional & Direct) 톤이
  기본값이지만, 이 케이스는 오탐 비중이 높은 상황이므로 **비난·의심의 뉘앙스를 배제**하고
  "확인 중/보호 조치"에 가까운 중립~안심 톤으로 조정한다. 어느 쪽으로 얼마나 조정할지는
  구현 시 두 가지 안을 만들어 비교 후 확정한다.
- **탐지 메커니즘(GPS 조작 감지)은 노출하지 않는다** — 가이드 4절 "어뷰징 감지 (차단 사유 비공개)"
  원칙 유지. "왜 막혔는지"를 구체적으로 설명하기보다 "이 지점은 확인이 더 필요해서 잠시
  쉬어가는 상태"처럼 상태를 설명하는 방향으로 접근.
- 해결책은 명확히: 다른 지점은 정상 이용 가능하고, 이 지점은 일정 시간 후 자동으로
  풀린다는 것을 전달한다. (정확한 시간(72시간)을 노출할지는 정책 노출 범위 검토 후 결정 —
  노출 시 어뷰저가 재시도 타이밍을 계산할 수 있다는 점 고려)
- 토스트 UI 공간 제약 고려 (기존 `pickupOutOfRange`, `pickupInventoryFull` 등과 길이·톤 일관성).
- 다른 pickup 실패 문구들의 패턴(1문장, 해요체, 마침표 없음 - 기존 코드 확인 필요)을 따른다.

- 기존: "이 지점에서는 잠시 이용이 제한됐어요. 시간이 지난 뒤 다시 시도해 주세요"

- **최종안** (사용자 피드백 반영): "이 지점 근처에서 비정상적으로 빠른 이동이 확인돼 픽업이
  제한됐어요. 문의하시면 확인해 드릴게요"

**재수정 사유**: 사용자가 1차 안의 "다른 지점 이용 가능" 문구는 불필요하다고 판단했고,
대신 (1) 해당 유저가 어떤 상황 때문에 지금 이용할 수 없는지, (2) 해결하려면 어떻게 해야
하는지(고객 문의)를 담백하게 전달할 것을 요청했다.

구조는 [현상]→[해결책]:
- 현상: "이 지점 근처에서 비정상적으로 빠른 이동이 확인돼 픽업이 제한됐어요" — "GPS 조작
  감지"·"부정행위" 같은 비난성 표현 대신, UX_WRITING_GUIDELINE.md 4절의 다른 어뷰징 사례
  ("이동 속도가 너무 빨라 운동으로 보기 어려웠어요")와 동일한 수준으로 관찰된 상황만 담백하게
  서술한다. 정확한 탐지 로직(GPS 조작 감지 자체)이나 임계값 수치는 노출하지 않는다.
- 해결책: "문의하시면 확인해 드릴게요" — 시간이 지나면 자동 해제된다는 안내 대신, 실제로
  존재하는 해결 경로(VOC 문의 게시판 → 어드민이 `/admin/abusing`의 POI 블록 관리 화면에서
  오탐이면 수동 해제)를 가리킨다. 토스트 컴포넌트(`Toast.tsx`)가 메시지 텍스트만 지원하고
  CTA 버튼을 지원하지 않아, "문의하기" 버튼 대신 텍스트로 안내했다. 정확한 해제 시간(72시간)은
  여전히 비노출.

`PoiCarouselModal.tsx:262`의 `poi_blocked` 매핑 자체는 변경 없음(이미 `d.drops.pickupPoiBlocked`를
그대로 참조). 매핑 로직에 대한 별도 주석도 다른 실패 코드들과 톤이 달라 추가할 필요가 없어 갱신하지

### 주요 의사결정 / 핵심 메모

**1차 라운드** — 두 안을 비교해 "쉬어가는 중" 안을 선택했었다.
- 선택안: "이 지점은 지금 쉬어가는 중이에요. 다른 지점은 바로 이용할 수 있고, 여긴 시간이
  지나면 다시 열려요" — 게이트 리뷰 PASS.
- 기각안: "이 지점 이용에 일시적인 제한이 있어요. 다른 지점을 먼저 이용해 보시고, 잠시 후
  다시 확인해 주세요" — "제한"이라는 단어가 기존 원문과 같은 계열이라 오탐 유저에게 여전히
  "제재당했다"는 인상을 줄 수 있어 기각.

**2차 라운드** — 사용자가 1차 안을 검토한 뒤 방향을 바꿨다: "다른 지점 이용 가능" 언급은
불필요하고, 대신 (1) 어떤 상황 때문에 지금 못 쓰는지, (2) 해결 방법(문의)을 담백하게
전달해야 한다고 지시. 이에 따라 최종안으로 교체:
"이 지점 근처에서 비정상적으로 빠른 이동이 확인돼 픽업이 제한됐어요. 문의하시면 확인해 드릴게요"
- "다른 지점은 이용 가능"(포지티브 대안 제시)이라는 1차 방향은 폐기 — 사용자가 불필요하다고
  명시적으로 판단했다.
- "시간이 지나면 자동 해제"(1차 안의 해결책) 대신 "문의"를 해결책으로 제시 — 실제로 어드민이
  `/admin/abusing`의 POI 블록 관리 화면에서 오탐이면 즉시 수동 해제할 수 있으므로, 무작정
  기다리라는 안내보다 정확하고 유저가 취할 수 있는 능동적 행동이다.
- 현상 서술("비정상적으로 빠른 이동")은 완전 비공개 대신 UX_WRITING_GUIDELINE.md 4절의 기존
  어뷰징 사례와 동일한 노출 수준을 택했다 — 아무 설명 없이 "문의하세요"만 있으면 유저가
  더 답답해하고 문의 게시판 부하만 늘어날 수 있다고 판단했다.
