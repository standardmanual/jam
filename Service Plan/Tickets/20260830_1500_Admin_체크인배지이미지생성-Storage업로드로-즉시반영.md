# [Admin] 체크인 배지 이미지 생성 — Supabase Storage 업로드로 즉시 반영

## 배경 / 문제 정의
`20260830_1349`로 만든 "체크인 배지 이미지 생성"(`/admin/badge-image`)은 이미지를 Next.js
`public/` 디렉터리에 파일로 직접 쓰려고 시도한다. 로컬 개발 서버에서는 되지만, 프로덕션
Vercel 서버리스 환경은 배포 번들이 읽기 전용이라 파일 저장이 실패하고, 지금은 base64로
다운로드시켜 관리자가 직접 git에 커밋하고 SQL을 복사해 DB에 수동 반영하는 방식으로
폴백하고 있다(실제로 사용자가 "뚝섬역" 텍스트로 이미지를 생성했을 때 이 폴백이 그대로
발동했다).

사용자는 이 수동 커밋/SQL 복사 과정 없이 **어드민에서 생성하면 즉시 DB의 이미지가
교체되길** 원한다.

### 이미 확립된 해결 패턴이 있다
`src/app/api/admin/upload-image/route.ts`(범용 이미지 업로드 API, `ImageUploadField.tsx`가
`BadgeForm.tsx`/`ItemBookForm.tsx`/`FactionForm.tsx`/`MissionList.tsx`에서 재사용 중)는
정확히 같은 문제를 이미 Supabase Storage로 풀어뒀다:
- 서버사이드(`getAdminUser` 인증 후)에서 `createServiceClient().storage.from('images').upload(...)`
- `getPublicUrl()`로 절대 URL 확보 — Next.js 배포와 무관하게 **즉시** 퍼블릭으로 서빙됨
- 이 URL을 `badges.image_url`에 바로 반영

실제 프로덕션 DB(`badges.image_url`)를 조회해보면 이미 447개 배지가 이 Storage 절대 URL
형태(`https://ceehnkzdbecxwzxrhhns.supabase.co/storage/v1/object/public/images/badges/...`)를
쓰고 있다 — public/ 상대경로가 유일한 방식이 아니며, Storage URL 렌더링 경로는 이미
실서비스에서 검증된 상태다.

`20260830_1349`가 이 패턴을 쓰지 않고 public/ 파일쓰기 + 수동 SQL 방식을 택한 건, 예전
배치 작업(`20260824_020`)에서 "public/ 정적 파일이 Vercel 배포가 끝나야 live되는데,
배포 전에 DB부터 UPDATE하면 이미지가 깨져 보이는" 순서 사고를 겪었기 때문에 그 원칙을
그대로 이어받은 것이다. 하지만 **Storage 업로드는 Next.js 배포와 무관하게 즉시 live되므로
이 순서 사고 자체가 구조적으로 발생하지 않는다** — 그 원칙을 이 기능에 적용할 필요가 없다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `src/app/api/admin/badge-image/generate/route.ts`를 다음과 같이 바꾼다:
  1. `public/`에 `fs.writeFileSync`로 파일을 쓰던 부분을 제거
  2. 렌더링된 PNG 버퍼를 `upload-image/route.ts`와 동일한 방식으로 Supabase Storage
     `images` 버킷에 업로드 (`folder`는 기존 447개와 동일 네임스페이스인 `badges`를
     쓰거나, 체크인 배지임을 구분하고 싶다면 `badges/checkin` 등 하위 폴더 — 자유롭게
     판단)
  3. `getPublicUrl()`로 얻은 URL로 **그 자리에서 바로**
     `supabase.from('badges').update({ image_url: publicUrl }).eq('id', badgeId)` 실행
     (별도 SQL 복사·수동 실행 없이 API 응답 전에 DB 반영까지 끝낸다)
  4. 응답에서 `sql`/`sqlPath`/`filesWritten`/`fallbackImages` 등 기존 "수동 반영" 관련
     필드는 제거하고, 대신 반영된 `imageUrl`(Storage 절대 URL)과 미리보기용 이미지 정보를
     내려준다
- 어드민 화면(`src/app/admin/badge-image/page.tsx`)도 이에 맞춰 결과 UI를 단순화한다 —
  "파일 다운로드", "SQL 복사" 안내/버튼을 제거하고, "이미지가 즉시 반영됐습니다" 같은
  완료 안내 + 미리보기 이미지만 보여준다.
- **기존 22개 배치 결과(`public/badges/poi/metro/*.png`, `category IN
  ('train_subway','transit')` 배지들의 image_url)는 이번 변경과 무관하게 그대로 둔다** —
  이번 티켓은 새로 만든 "단건 생성" 도구의 저장 방식만 바꾸는 것이지, 기존에 이미 public/
  경로로 반영된 배지들을 Storage로 마이그레이션하는 작업이 아니다. 이번 도구로 그 배지들
  중 하나를 다시 생성하면(예: 이번에 실제로 있었던 "뚝섬역 2호선" 재생성처럼) 그 배지만
  자연스럽게 Storage URL로 전환된다.
- `next.config.ts`의 `outputFileTracingIncludes['/api/admin/badge-image/generate']`가
  더 이상 필요 없어질 수 있다(엔진·config·폰트·배경 SVG 파일은 여전히 필요하지만, public/
  쓰기 관련 트레이싱은 무관) — 실제로 무엇이 여전히 필요한지 확인 후 정리한다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- `generate/route.ts`에서 `public/`에 `fs.writeFileSync`하던 로직을 제거하고,
  `upload-image/route.ts`와 동일한 패턴으로 렌더링된 PNG를 Supabase Storage `images` 버킷의
  `badges/checkin/{badgeId}.png`(배지 id 고정 경로, `upsert: true`)에 업로드한다. 업로드 직후
  `getPublicUrl()`로 얻은 절대 URL을 그 자리에서 바로 `badges.image_url`에 UPDATE한다 — 별도
  SQL 복사·수동 반영 단계가 없다.
- 고정 경로 upsert 특성상 CDN/브라우저가 재생성 전 이미지를 캐시하고 있을 수 있어, DB에
  저장하는 URL에는 `?v={timestamp}` 캐시 무효화 쿼리스트링을 붙였다(재생성 즉시 새 이미지가
  보이도록 보장 — 티켓의 "즉시 반영" 요구를 실제로 만족시키기 위한 최소 추가, 티켓 범위
  안에서 판단).
- 응답 스키마에서 `filesWritten`/`outputDir`/`fileName`/`sql`/`previewBase64` 필드를 제거하고
  `imageUrl`(Storage 절대 URL, 캐시버스터 포함)만 반환한다.
- 어드민 화면(`badge-image/page.tsx`)에서 "파일 다운로드"/"SQL 복사" UI, 관련 상태(`copied`)와
  아이콘 import(`IconCopy`, `IconDownload`)를 제거하고, 결과 카드는 Storage URL로 직접 미리보기
  이미지를 렌더링 + "이미지가 즉시 반영됐습니다" 안내만 표시하도록 단순화했다. 상단 설명
  문구도 "즉시 반영됩니다 — 별도 배포나 SQL 적용이 필요 없습니다"로 갱신.
- `next.config.ts`의 `outputFileTracingIncludes['/api/admin/badge-image/generate']`는 확인
  결과 그대로 유지했다 — `engine.js`가 여전히 `scripts/badge-image-gen/{lib,configs,fonts,
  backgrounds}` 하위 파일들을 동적 require/fs로 읽으므로(폰트 캐시, 배경 SVG, config), public/
  쓰기와 무관하게 계속 필요하다.
- 기존 22개 배치 결과(`public/badges/poi/metro/*.png` 기반 image_url)는 건드리지 않았다 —
  이번 변경은 새 업로드 경로에만 적용되고, 기존 배지는 이 도구로 재생성할 때만 자연스럽게
  Storage URL로 전환된다(코드 변경 없이 동작으로 보장됨).

### 주요 의사결정 / 핵심 메모
- **Storage 경로를 배지 id 고정 + upsert로 설계**: `upload-image/route.ts`는 매번 랜덤
  파일명을 써서 충돌을 원천적으로 피하지만, 이 라우트는 "같은 배지 재생성 시 이미지만
  교체"가 자연스러운 사용 패턴이라 배지 id를 경로로 고정하고 `upsert: true`를 택했다.
  대신 고정 경로 재사용의 부작용(캐시로 인해 재생성 후에도 옛 이미지가 보일 수 있음)을
  막기 위해 DB에 저장하는 URL에 `?v={timestamp}` 쿼리스트링을 붙였다 — 실측으로도 해당
  버킷의 `cache-control: no-cache` 헤더를 확인했지만(브라우저 자체 캐시까지는 헤더로
  통제되지 않으므로) 안전장치로 유지했다.
- **폴더는 `badges/checkin/`으로 선택**: 티켓이 "자유롭게 판단"으로 남겨둔 부분. 기존
  447개 활동 배지는 `badges/` 바로 아래 랜덤 파일명이라 이름 충돌 우려는 없지만, 체크인
  배지 전용 렌더링 파이프라인이 만든 산출물임을 경로로도 구분하고 싶어 하위 폴더를 뒀다.
- **`sql`/`previewBase64` 등 필드를 완전히 제거**(하위호환 유지 안 함) — 티켓이 "제거"를
  명시했고, 이 화면은 이번 티켓으로 아직 실사용 이력이 짧아(20260830_1349 신설) 하위호환
  걱정 없이 스키마를 바로 단순화하는 편이 낫다고 판단.
