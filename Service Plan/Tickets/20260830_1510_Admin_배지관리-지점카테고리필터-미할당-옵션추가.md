# [Admin] 배지 관리 필터 — 체크인 배지 "지점 카테고리" 필터에 '미할당' 옵션 추가

## 배경 / 문제 정의
`/admin/badges` 목록 화면 상단 필터에서 타입을 "체크인"으로 선택하면 "지점 카테고리" 서브
필터(`BadgesFilterBar.tsx` 159~167행)가 나타난다. 이 필터는 `poi_categories` 테이블의
카테고리 목록만 옵션으로 제공하는데, **어느 지점에도 연결되지 않은 체크인 배지를 걸러볼
방법이 없다.** 사용자는 이 필터에 "미할당" 옵션을 추가해 지점이 하나도 연결되지 않은
체크인 배지만 모아 보고 싶어한다.

### 코드 조사 메모 (오케스트레이터 사전 조사, 구현자가 재확인할 것)
- 필터 UI: `jam-web/src/app/admin/badges/BadgesFilterBar.tsx` 159~167행.
  `poiCategories.map(...)`로 옵션을 구성하는 `DataTableFacetedFilter`.
- 서버 쿼리: `jam-web/src/app/admin/badges/page.tsx` 36~59행.
  ```ts
  const filterByPoiCategory = filterType === 'checkin' && !!filterPoiCategory
  const selectClause = filterByPoiCategory
    ? `${BADGE_LIST_COLUMNS}, poi!poi_linked_badge_id_fkey!inner(category)`
    : BADGE_LIST_COLUMNS
  ...
  if (filterByPoiCategory) query = query.eq('poi.category', filterPoiCategory)
  ```
  `poi.linked_badge_id → badges.id`는 배지 하나에 여러 지점이 연결될 수 있는 구조
  (badges 입장에서 1:N)다. 현재는 `!inner` 조인 + `poi.category` 값 일치로 필터한다 —
  즉 **연결된 지점이 하나도 없는 배지는 이 조인에서 항상 제외된다** (INNER JOIN이라
  매칭 없으면 행 자체가 빠짐).
- **`poi.category`는 NOT NULL이다** (`jam-web/supabase/migrations/050_poi_categories_table.sql`
  29~31행, 기본값 `'other'`). 즉 지점 자체는 항상 카테고리를 갖는다 — "카테고리 미할당"이
  지점 레벨에서는 발생할 수 없다. 따라서 "미할당"의 의미는 **"이 체크인 배지에 연결된
  지점이 하나도 없다"** 로 해석하는 것이 유일하게 말이 된다(연결된 지점이 없으니 지점
  카테고리로 분류할 수 없는 상태). 애매하면 HALT로 보고할 것.
- 이건 티켓 20260830_1344에서 추가한 `badges.category`(배지 자체의 분류 태그, nullable)와는
  **완전히 다른 개념**이다 — 이번 요청은 목록 필터(`poi_category` 파라미터, 연결된 지점
  기반)에 관한 것이지, 배지 저작 폼의 `category` 필드(20260830_1344)와는 무관하다. 혼동하지
  말 것.
- PostgREST로 "관계가 없는 행"을 거르는 안티조인은 `!inner`로는 표현할 수 없다(반대 방향).
  가장 단순하고 안전한 방법: 서버 컴포넌트(`page.tsx`)에서 별도 쿼리로
  `poi.select('linked_badge_id').not('linked_badge_id', 'is', null)`을 먼저 조회해 "지점이
  연결된 배지 id 집합"을 구하고, "미할당" 필터가 선택되면 badges 쿼리에
  `.not('id', 'in', '(...)')`로 그 집합을 제외한다. 참고: 티켓 20260825_035(PostgREST 절단
  위험)가 `.in()`/`.not(...'in'...)`에 넘기는 리스트가 커지면 URL이 잘릴 위험을 지적한 바
  있다 — 다만 그 티켓은 "배지 수백~900개"급 리스트를 걱정한 것이고, 여기서 제외 대상은
  "지점이 하나 이상 연결된 배지"의 집합이라 실제 규모가 훨씬 작을 가능성이 높다. 그래도
  구현자는 현재 `poi` 테이블에서 `linked_badge_id IS NOT NULL`인 행이 대략 몇 건인지
  확인하고(`select count(*)` 또는 이미 아는 규모), 만약 수백 건 이상이면 절단 위험 완화
  방법(RPC/뷰 등)을 고려할 것 — 소규모면 지금 방식 그대로 진행.

## 상세 요구사항

### 서비스/코드베이스 관점
- `BadgesFilterBar.tsx`의 "지점 카테고리" 옵션 목록에 "미할당" 항목을 추가한다. 실제
  `poi_categories.slug` 값과 충돌하지 않는 전용 sentinel 값을 쓴다(예: `__unassigned__`).
  URL 쿼리 파라미터(`poi_category`)에는 이 sentinel 값이 그대로 실려도 무방하다 — 백엔드에서
  분기 처리.
- `page.tsx`에서 `poi_category=__unassigned__`일 때는 기존 inner-join 로직 대신, "지점이
  연결된 배지 id 목록"을 조회해 그 목록에 없는 체크인 배지만 반환하도록 분기한다.
- 기존 카테고리별 필터(`poi.category` 일치)와 "전체"(필터 없음) 동작은 그대로 유지 —
  회귀 금지.
- 필터 초기화·타입 변경 시 서브필터 초기화 로직(`SUB_FILTER_KEYS`)은 이미 `poi_category`를
  포함하고 있으므로 추가 수정 불필요 — 재확인만 할 것.

### UI/UX 관점
- "미할당" 라벨은 `Service Plan/Specs/UX_WRITING_GUIDELINE.md` 톤에 맞게 간결하게 유지한다
  (제안: "미할당" 그대로 — 관리자 내부 용어로 이미 직관적).
- 옵션 목록에서의 위치는 카테고리 목록 앞 또는 뒤 어디든 무방하나, 일관성 있게 배치한다
  (예: 카테고리 목록 뒤에 구분자 없이 추가).

- 해당 없음

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- `BadgesFilterBar.tsx`의 "지점 카테고리" 필터 옵션에 전용 sentinel 값
  `UNASSIGNED_POI_CATEGORY = '__unassigned__'`(`badge-labels.ts`에 상수화, 서버/클라이언트 공유)로
  "미할당" 옵션을 추가했다.
- `page.tsx`에서 `poi_category=__unassigned__`이면 기존 inner-join 분기(`filterByPoiCategory`)를
  타지 않고 별도 분기(`isUnassignedPoiFilter`)로 처리한다.
- **구현 전 실측**: `poi.linked_badge_id IS NOT NULL`인 행이 1,799건, distinct 배지 id 기준
  1,796건(2026-08-30 기준, 체크인 배지 총 1,800건 중). 티켓이 우려한 "수백 건 이상"을 훨씬
  초과하는 규모라, 티켓이 제시한 1차 방법(지점 연결된 배지 id 목록을 `.not('id','in',...)`에
  통째로 넘기는 안티조인)은 URL 절단 위험이 실제로 크다고 판단해 **다른 방식으로 구현**했다:
  1. 체크인 배지 id 전체와 지점이 연결된 배지 id 전체를 각각 `fetchAllRows`(PostgREST 기본
     응답 상한 1000행 대응 페이지네이션, `ambient-drop/index.ts`·`recipes/page.tsx`와 동일한
     기존 패턴)로 완전히 조회한다.
  2. 서버 메모리에서 두 집합의 차집합(= 미할당 배지, 실측 4건 내외)을 구한다.
  3. 이 **작은** 결과만 메인 쿼리에 `.in('id', ...)`으로 넘긴다 — URL에 실리는 id 목록이
     "미할당"(작은 집합)이지 "할당됨"(큰 집합)이 아니므로 절단 위험이 없다.
  - 빈 배열을 `.in()`에 그대로 넘기는 PostgREST 위험은 `combine/index.ts` 200행과 동일한
    관용구(존재할 수 없는 UUID로 대체)로 방어했다.
- 기존 카테고리별 필터(`poi.category` 일치)·"전체" 동작, `SUB_FILTER_KEYS` 초기화 로직은
  손대지 않았다(재확인 결과 `poi_category`가 이미 포함돼 있어 추가 수정 불필요).

### 주요 의사결정 / 핵심 메모
- **티켓이 제시한 1차 구현 방법(안티조인 대상을 "지점 연결된 배지 id" 큰 집합으로 잡아
  `.not('id','in',...)`)을 채택하지 않았다.** 사전 실측 결과 그 집합이 1,796건으로
  "수백 건 이상"을 크게 웃돌아 URL 절단 위험이 실질적이라고 판단했기 때문. 대신 두 전체
  집합(체크인 배지 전체·연결된 배지 전체)을 페이지네이션으로 완전히 조회한 뒤 서버
  메모리에서 차집합을 구해 **작은 결과(미할당 배지, 실측 4건 내외)만** `.in()`에 넘기는
  방식으로 구현했다. RPC/뷰 신설(마이그레이션 필요) 대신 기존 코드베이스에 이미 있는
  `fetchAllRows` 페이지네이션 패턴(`ambient-drop/index.ts`, `recipes/page.tsx`)을 재사용해
  DB 변경 없이 해결했다.
- sentinel 값은 `poi_categories.slug`와 절대 충돌하지 않는 `__unassigned__`로 정하고
  `badge-labels.ts`에 상수화해 서버(`page.tsx`)·클라이언트(`BadgesFilterBar.tsx`)가
  같은 값을 참조하도록 했다(하드코딩 이중화 방지).
