# [Service] 체크인 배지 "카테고리" 변경이 실제 분류(대중교통/기차·지하철 등)에 반영되지 않음

## 배경 / 문제 정의
사용자가 어드민에서 성수역 체크인 배지의 카테고리를 "기차/지하철"로 변경했는데, 목록에서는
여전히 "대중교통" 카테고리에 노출된다고 보고했다. 사용자 상세 요청: 성수역 한 건만이 아니라
**체크인 배지 전체의 카테고리 변경 기능이 실제로 동작하는지 확인**, 그리고 상세 화면의
레이블 "배지 카테고리"를 "지점 카테고리"로 변경.

### 코드/DB 조사 결과 (오케스트레이터 사전 조사, 구현자가 재확인할 것)

**핵심 원인 — 두 개의 서로 다른 "카테고리" 값이 존재하고, 화면마다 참조하는 값이 다르다.**

1. `badges.category` (nullable text, `jam-web/supabase/migrations/113_badges_category.sql`,
   티켓 [[20260830_1344]]에서 신설) — 어드민 배지 편집 화면
   (`jam-web/src/app/admin/badges/BadgeForm.tsx:144,379,549`)에서 "배지 카테고리" Select로
   저장하는 값. **사용자가 실제로 편집하는 값이 이것이다.**
2. `poi.category` — 체크인 배지에 연결된 지점(POI)의 카테고리. 다음 두 화면의 실제 분류/필터
   기준은 **이 값뿐**이고 `badges.category`는 전혀 읽지 않는다:
   - 어드민 목록(`jam-web/src/app/admin/badges/page.tsx:65-73,112`) — `poi.category`로
     `.eq()` 필터. 65행 주석 "체크인 배지에는 카테고리 컬럼이 없고, 연결된 지점(poi.category)
     으로만 분류된다"는 이제 **사실과 다른 낡은 주석**이다(113 마이그레이션으로 컬럼이 생겼음).
   - 공개 화면(`jam-web/src/app/(main)/badges/page.tsx:167-190`) — 획득한 체크인 배지를
     연결된 POI의 `category`로 그룹핑(`categoryByBadge` 맵). `badges.category`는 쿼리에
     포함되지도 않는다.

DB 실측(2026-08-30, service_role 직접 조회):
```
성수역 POI: category = 'transit' (대중교통)
성수역 체크인 배지: category = 'train_subway' (기차/지하철) ← 사용자가 어드민에서 방금 바꾼 값
```
→ 사용자가 바꾼 값은 정확히 저장돼 있다. 하지만 목록 분류는 `poi.category='transit'`만
보므로 대중교통에 그대로 남는다. **"성수역만의 문제"가 아니라 `badges.category`를 읽는
분류/필터 로직이 어디에도 없는 구조적 문제**다 — 현재 `type='checkin'` 배지 1800건 중
`category`가 채워진 건 4건뿐이며(전부 최근 사용자 테스트), 그 4건 모두 동일하게 무효하다.

**참고 — 부수 발견(이번 티켓 범위 밖, 별도 확인 필요)**: `poi_categories` 분리 작업
([[20260824_023]])이 "역"으로 끝나는 POI 929개를 `train_subway`로 옮겼다고 기록했지만,
실측 결과 이름이 "OO역"으로 끝나면서 여전히 `category='transit'`로 남아있고 체크인 배지가
연결된 POI가 15건 있다(성수역, 선릉역, 수서역, 신답역, 답십리역, 한성대입구역, 종로3가역,
자양역, 송파역, 석촌역, 서울숲역, 마장역, 을지로입구역, 교대역, 뚝섬역 — 전부 마이그레이션
실행일 2026-08-24 이전에 생성됨). 이번 티켓의 근본 원인과는 별개 사안(마이그레이션 누락)이라
**이 티켓에서 직접 고치지 않는다** — 완료 후 사용자에게 별도 확인 여부를 묻는다.

## 상세 요구사항

### 서비스/코드베이스 관점
1. **`badges.category`를 체크인 배지 분류의 실제 기준으로 반영한다.**
   - 값이 있으면 `badges.category`를 우선 사용하고, 없으면(`null`) 기존처럼 연결된
     `poi.category`로 폴백한다 — 이렇게 해야 아직 아무도 설정하지 않은 기존 1796건이
     회귀 없이 그대로 동작한다.
   - 대상 두 곳:
     - `jam-web/src/app/admin/badges/page.tsx` — 카테고리 필터 쿼리 (65~112행)
     - `jam-web/src/app/(main)/badges/page.tsx` — 공개 배지함 카테고리 그룹핑 (167~190행)
   - 두 곳 모두 카테고리 드롭다운/필터 옵션 목록(`poi_categories` 조회해 라벨 붙이는 부분)이
     `badges.category` 값도 유효한 슬러그로 인식하는지 확인 — `badges.category`는
     `poi_categories.slug`를 FK로 재사용하므로(113 마이그레이션) 라벨 매핑은 동일 테이블을
     쓰면 된다.
   - 65행의 낡은 주석("카테고리 컬럼이 없고")을 현재 구조에 맞게 갱신한다.
2. **전체 체크인 배지 대상 동작 확인** — 성수역 외 나머지 3건(현재 `category` 설정된 전체)도
   포함해 카테고리 변경 → 목록 반영까지 실제로 되는지 검증한다. `category`가 `null`인
   기존 배지는 종전과 동일하게 `poi.category` 기준으로 노출되어야 한다(회귀 금지).

### 구현 내용 요약
`badges.category`가 목록/배지함 분류 로직에서 전혀 읽히지 않던 구조적 문제를 수정했다.
`badges.category`가 있으면 우선 사용하고, 없으면(`null`) 기존처럼 연결된 `poi.category`로
폴백하는 방식으로 두 화면을 고쳤다.

- **어드민 목록 필터** (`admin/badges/page.tsx`): 기존에는 `poi!poi_linked_badge_id_fkey!inner`
  조인으로 `poi.category`만 필터했다. `badges.category`는 poi 연결 없이도 값을 가질 수 있어
  DB 조인 하나로 두 값을 합성할 수 없었고, 매칭 id 목록을 그대로 `.in()`에 넘기면 카테고리
  하나가 900건을 넘을 때 URL이 수십 KB가 되는 문제(20260825_035)가 재발할 수 있었다(실측
  결과 `train_subway` 유효 카테고리가 930건으로 실제로 900건을 넘음 — 아래 테스트 결과 참고).
  그래서 체크인 배지 전체(1800건대)와 연결된 poi 전체를 페이지네이션으로 완전히 조회해 메모리에서
  유효 카테고리를 계산하고, 상태/검색어/등급 필터·정렬·페이지네이션까지 이 분기 안에서 전부
  처리하도록 재작성했다. "미할당" 필터(20260830_1510)도 같은 유효 카테고리 계산 결과가 `null`인
  경우로 통합했다.
- **공개 배지함 그룹핑** (`(main)/badges/page.tsx`): `categoryByBadge` 맵 우선순위를
  `badge.category ?? poi.category`로 수정 (한 줄 변경, 이미 `select('*')`로 badge.category를
  가져오고 있었음).
- **어드민 편집 폼 레이블** (`BadgeForm.tsx`): "배지 카테고리" → "지점 카테고리", 안내 문구를

### 주요 의사결정 / 핵심 메모
- **`.in()` 대신 전체 조회 후 메모리 필터링을 선택한 이유**: `badges.category`(오버라이드)는
  연결된 poi 없이도 값을 가질 수 있어 DB 조인 하나로 `badges.category ?? poi.category`를
  표현할 수 없다. 오버라이드 건수가 소수(4건)일 때는 "조인 필터 + 오버라이드 id만 별도
  `.in()`"으로도 될 것 같지만, 조인과 비조인 조건을 OR로 묶는 PostgREST 문법이 임베디드
  리소스 필터와 안정적으로 결합되는지 검증이 어렵고, 오버라이드 건수가 앞으로 늘어날 가능성도
  배제할 수 없어 더 견고한 방식(전체 조회 후 메모리 계산)을 택했다. 어드민 전용 화면이라
  체크인 배지 전체(1800건대)를 완전 조회하는 비용은 페이지 응답 시간에 문제되지 않는 규모다.
- **"미할당" 필터 정의 확장**: 기존에는 "연결된 poi가 하나도 없는 배지"만 미할당으로 판정했다.
  이번 변경으로 `badges.category`가 설정돼 있으면 poi 연결 여부와 무관하게 그 값이 유효
  카테고리가 되므로, 미할당의 정의도 "유효 카테고리 계산 결과가 null인 배지"(= `category`도
  없고 연결 poi도 없는 배지)로 자연스럽게 확장했다. 티켓의 65~112행 대상 범위에 이 로직이
  포함돼 있어 범위 이탈이 아니라고 판단했다.
