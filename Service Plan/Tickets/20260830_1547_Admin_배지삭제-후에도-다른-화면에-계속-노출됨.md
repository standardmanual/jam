# [Admin] 배지 삭제 후에도 다른 화면·상세 페이지에 계속 노출됨

## 배경 / 문제 정의
사용자가 "배지 삭제 기능이 동작하지 않는다"고 보고했다. 구체적으로 다음 4가지 현상을 모두
겪었다고 확인함: (1) 클릭해도 반응 없음/에러, (2) 목록에 계속 노출됨, (3) 상세 페이지가
계속 열림, (4) 다른 화면(POI 등)에서 계속 보임.

### 코드/프로덕션 로그/DB 조사 결과 (오케스트레이터 사전 조사, 구현자가 재확인할 것)

**삭제 API 자체는 정상 동작하고 있음을 실측으로 확인했다.** Vercel 프로덕션 런타임 로그를
직접 조회한 결과, 지난 1시간 반 동안(05:09~06:32) 서로 다른 배포 3개(`dpl_CYYs53SD...`,
`dpl_6Pv2bjFm...`, `dpl_CzYcYmej...`, 전부 `branch=main`)에 걸쳐 `DELETE
/api/admin/badges/{id}`가 반복 호출됐고 **전부 200을 반환**했다. DB로 직접 확인한 결과
`deleted_at`도 정확히 세팅돼 있다(예: "남산 정복자" `deleted_at=2026-08-30 06:32:31+00`).
→ **소프트 삭제 자체(API+DB)는 매번 성공하고 있다.**

**그런데 같은 배지 id가 30분~1시간 간격으로 3번씩 반복 삭제 시도됐다**
(`37bba4c1-...`: 06:03:37 / 06:28:35 / 06:29:34 / 06:29:54, `86a700b5-...`: 05:09:58 /
06:28:16, `40a25e90-...`: 06:04:30 / 06:27:37 / 06:28:32 등). API가 매번 성공했는데도
사용자가 반복 삭제를 시도했다는 것은 **삭제 이후 어딘가에서 여전히 "살아있는 것처럼"
보였다는 강한 신호**다.

**확인된 실제 버그 1건 — POI 상세화면이 삭제된 배지를 필터링 없이 그대로 보여준다.**
`jam-web/src/app/admin/poi/[id]/page.tsx:22-24`:
```ts
if (poi.linked_badge_id) {
  const { data: badgeRaw } = await supabase.from('badges').select('name').eq('id', poi.linked_badge_id).maybeSingle()
  linkedBadgeLabel = (badgeRaw as { name: string } | null)?.name
}
```
`deleted_at` 조건이 전혀 없다 — 배지를 삭제해도 `poi.linked_badge_id` FK는 그대로 남아있고
(삭제 API가 poi 테이블을 건드리지 않음), 이 쿼리는 삭제 여부와 무관하게 이름을 그대로
가져와 "연결된 배지: OOO"로 계속 표시한다. **체크인 배지는 POI와 1:1로 연결되는 구조라
([[20260824_023]]), 관리자가 배지↔POI를 오가며 확인하는 워크플로우에서 이 화면이 특히
자주 보이는 화면이다** — "다른 화면에서 계속 보임" 증상과 정확히 일치.

**목록 화면(`admin/badges/page.tsx`) 자체의 기본 필터는 정상이다** — `status` 기본값이
`'active'`이고 `.is('deleted_at', null)` 필터가 정확히 걸려있어, 필터를 건드리지 않았다면
삭제된 배지는 기본 목록에 나타나지 않는다(코드 확인 완료). 다만 `BadgesFilterBar.tsx`의
`status` 드롭다운을 `all`/`inactive`로 바꿔둔 상태였다면 삭제된 배지가 "비활성화됨" 배지와
함께 계속 보이는 게 **의도된 동작**이다 — 사용자가 실제로 어떤 필터 상태였는지는 확인 불가,
구현자가 재현 시 확인 필요.

**"클릭해도 반응 없음/에러" 증상은 런타임 로그에서 근거를 찾지 못했다** — 조회된 모든
DELETE 호출이 200이었고 에러 레벨 로그도 없었다. 클라이언트 측에서만 발생하는 문제(예:
`handleDelete`의 `router.push`/`router.refresh` 실패, 특정 브라우저·네트워크 상태에서의
경합)일 가능성이 있다 — 구현자가 `BadgeDetail.tsx`(97~110행 부근 `handleDelete`)의 삭제 후
흐름을 재검토하고, 가능하면 실제 브라우저에서 재현할 것.

## 상세 요구사항

### 서비스/코드베이스 관점
1. **POI 상세화면의 연결 배지 조회에 `deleted_at is null` 필터를 추가하거나, 삭제된 배지면
   그 사실을 명확히 표시한다.** (`jam-web/src/app/admin/poi/[id]/page.tsx:22-24`)
   - 어떤 방식을 택할지는 구현자 판단: (a) 삭제된 배지는 연결이 끊긴 것처럼 안 보이게
     처리(`linked_badge_id`가 가리키는 배지가 삭제됐으면 표시 안 함), 또는 (b) "OOO
     (삭제됨)"처럼 명시적으로 표시. `poi.linked_badge_id` FK 자체를 정리(null화)할지는
     범위가 커지므로 이번 티켓에서는 **표시 로직만** 고친다(FK 정리는 별도 판단 필요 시
     HALT로 보고).
2. **삭제 흐름 재검토 및 실제 재현** — `BadgeDetail.tsx`의 `handleDelete` 이후 흐름
   (`router.push('/admin/badges')` → `router.refresh()`)이 실패하거나 사용자에게 아무
   피드백 없이 끝나는 경로가 있는지 코드로 재검토한다. 가능하면 실제 프로덕션 어드민에서
   브라우저로 삭제를 재현해 콘솔 에러·네트워크 응답을 직접 확인한다(사용자 확인 없이는
   스테이징에서 검증 불가 — 실제 재현은 프로덕션에서 조심스럽게, 테스트용으로 이미 만든
   배지 등 영향이 적은 대상으로).
3. **목록 화면 필터 상태 확인** — `BadgesFilterBar.tsx`의 `status` 필터가 URL에 없을 때
   기본값이 정확히 `active`로 렌더링되는지, 필터 변경 후 다른 배지 상세로 이동했다가
   돌아왔을 때 필터가 의도치 않게 유지/초기화되는지 확인한다(회귀는 아니지만 혼동 유발
   가능성 점검).

### UI/UX 관점
- POI 상세화면에 "삭제됨" 표시를 추가한다면 `BadgeDetail.tsx`/`BadgeCard.tsx`가 이미 쓰는
  "비활성화됨" 문구·스타일 컨벤션을 그대로 따른다(신규 표현 만들지 않음).

### 구현 내용 요약
1. **확인된 실제 버그 수정** — `admin/poi/[id]/page.tsx`의 연결 배지 조회를
   `select('name')` → `select('name, deleted_at')`로 바꾸고, `PoiDetail.tsx`에
   `linkedBadgeDeletedAt` prop을 추가해 삭제(비활성화)된 배지면 "비활성화됨 · YYYY.MM.DD
   회수" 배지를 표시한다. `BadgeDetail.tsx`/`BadgeCard.tsx`/`BadgesTable.tsx`가 이미 쓰는
   문구·스타일(빨강 필, `formatYmd`)을 그대로 재사용했다(신규 표현 없음). 편집 폼
   (`PoiForm.tsx`)에 넘기는 `linkedBadgeLabel`은 손대지 않았다 — 표시 로직만 고치는
   범위이며, `poi.linked_badge_id` FK 자체는 정리하지 않는다(티켓 명시 범위).
2. **삭제 흐름(`BadgeDetail.tsx` handleDelete) 재검토** — 코드상 결함을 찾지 못했다.
   `DELETE` 실패 시 `alert()`로 에러를 노출하고, 성공 시 `router.push('/admin/badges')` →
   `router.refresh()`로 이동한다. 이 push+refresh 패턴은 `BadgeForm.tsx`,
   `FactionForm.tsx`, `ItemBookForm.tsx`, `PoiForm.tsx` 등 어드민 전역에서 동일하게
   쓰이는 확립된 패턴이라 이 화면만의 결함이 아니다. 실제 프로덕션 브라우저 재현은
   수행하지 못했다(아래 alerts 참고).
3. **목록 화면(`BadgesFilterBar.tsx`/`admin/badges/page.tsx`) 필터 기본값 확인** —
   URL에 `status` 파라미터가 없을 때 두 파일 모두 정확히 `'active'`로 폴백함을 코드로
   확인했다(버그 없음). 필터는 URL(searchParams)에만 저장되므로 상세 화면을 오갈 때
   "유지"되는 것은 브라우저 히스토리에 의한 의도된 동작이다 — 사용자가 `status=all`/
   `inactive`로 바꿔둔 채였다면 삭제된 배지가 계속 보이는 것은 정상 동작이다.
