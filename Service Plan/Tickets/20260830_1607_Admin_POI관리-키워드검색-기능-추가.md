# [Admin] POI 관리 화면에 키워드 검색 기능 추가

## 배경 / 문제 정의
`/admin/poi` 목록 화면에는 카테고리 필터와 정렬만 있고, 이름으로 검색하는 기능이 없다.
등록된 POI가 많아지면(현재 배지 연결 기준 실측 1,800건 내외 — 티켓 20260830_1510 참고)
카테고리만으로는 원하는 지점을 찾기 어렵다. 배지 관리 화면(`/admin/badges`)에는 이미 이름·
설명 키워드 검색이 있으므로 동일한 패턴을 POI 관리 화면에도 적용한다.

### 코드 조사 메모 (오케스트레이터 사전 조사, 구현자가 재확인할 것)
- 대상 화면: `jam-web/src/app/admin/poi/page.tsx`(서버 컴포넌트, 목록 쿼리) +
  `jam-web/src/app/admin/poi/PoiFilters.tsx`(클라이언트, 필터 UI — `'use client'`).
- **참고 패턴 1 — 검색 입력 UI**: `jam-web/src/app/admin/badges/BadgesFilterBar.tsx` 84~92행.
  `searchInput` 로컬 state + `useEffect`로 400ms 디바운스 후 `q` 쿼리 파라미터를 갱신한다.
  POI 필터에도 동일한 디바운스 패턴을 그대로 적용한다.
- **참고 패턴 2 — 서버 쿼리**: `jam-web/src/app/admin/badges/page.tsx` 27행
  `if (q) query = query.or(\`name.ilike.%${q}%,description.ilike.%${q}%\`)`.
  단, `PoiRow`에는 `description` 필드가 없다(`jam-web/src/types/database.ts` 301~311행 —
  `id, name, latitude, longitude, radius_meters, category, linked_badge_id, osm_id, naver_id,
  poi_tier, created_at`). **검색 대상은 `name` 하나뿐**이므로 `.or(...)` 대신 단순
  `query.ilike('name', \`%${q}%\`)`를 쓰면 된다 — PostgREST 필터 문법 이스케이프 문제도
  피할 수 있다(콤마·괄호가 포함된 검색어를 넣어도 `.or()` 문자열 파싱과 달리 안전).
- **참고 패턴 3 — 기존 POI 이름 검색 API**: `jam-web/src/app/api/admin/poi/search/route.ts`.
  배지 폼에서 지점을 연결할 때 쓰는 별도 API로, `raw.replace(/[,()%_*\\]/g, ' ')`로 LIKE
  와일드카드·PostgREST 특수문자를 정리한 뒤 `.ilike('name', '%query%')`를 쓴다. 이번 목록
  검색은 `.ilike()`를 직접 호출(문자열 보간이 아니라 쿼리 빌더 파라미터)하므로 이 API처럼
  PostgREST 문법 이스케이프까지는 필요 없지만, `%`/`_`가 LIKE 와일드카드로 해석되는 것까지
  막을지는 구현자 판단(배지 검색 Input도 이 처리를 안 하므로 굳이 다르게 할 필요는 없어
  보임 — 일관성 우선).
- 검색어 변경 시 `page` 파라미터를 초기화해야 한다(기존 `updateParams`가 이미
  `params.delete('page')`를 하므로 검색도 이 경로를 타면 자동으로 해결됨).
- `hasFilter`(35행, "필터 초기화" 버튼 노출 조건)에 `q` 파라미터 존재 여부도 포함시킨다 —
  현재는 `category`만 검사한다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `PoiFilters.tsx`에 검색 Input을 추가한다. `BadgesFilterBar.tsx`와 동일하게 400ms 디바운스
  후 `q` 쿼리 파라미터를 갱신하는 방식.
- `page.tsx`에서 `params.q`를 읽어 `name`에 대해 `ilike` 검색을 적용한다(대소문자 구분 없음).
- 카테고리 필터·정렬과 함께 조합 가능해야 한다(AND 조건).
- `hasFilter` 판정에 검색어도 포함시켜 "필터 초기화" 버튼이 정상 노출/숨김되도록 한다.

### UI/UX 관점
- placeholder 문구는 배지 검색 Input(`"배지 이름, 설명으로 검색..."`)과 톤을 맞춰
  간결하게 작성한다 (예: `"지점 이름으로 검색..."`). `UX_WRITING_GUIDELINE.md` 참고.
- 검색 Input의 배치·크기는 `BadgesFilterBar.tsx`의 `Input` 컴포넌트 스타일
  (`h-8 w-[180px] lg:w-[260px]`)과 일관되게 맞춘다.

### 컨텐츠 관점
- 해당 없음

### 구현 내용 요약
`PoiFilters.tsx`에 배지 관리 화면(`BadgesFilterBar.tsx`)과 동일한 400ms 디바운스 검색 Input을

### 주요 의사결정 / 핵심 메모
- 검색 대상은 `name` 단일 컬럼이라 `.or()` 대신 `.ilike('name', ...)`를 직접 호출했다(티켓
  사전 조사 메모 그대로 채택). `PoiRow`에 `description` 필드가 없어 배지 화면의
  `.or('name.ilike...,description.ilike...')` 패턴은 적용 대상이 아니다.
- `%`/`_`(LIKE 와일드카드) 이스케이프는 배지 검색 Input도 처리하지 않는 점에 맞춰 일관성을
  우선해 동일하게 처리하지 않았다(티켓 사전 조사 메모의 판단 위임을 그대로 따름).
- 카운트 표시("총 N개")에 배지 화면처럼 "(필터 적용 중)" 문구를 추가할지 검토했으나, 티켓
  요구사항에 없고 POI 화면의 기존 카운트 UI를 건드리는 범위 확장이라 이번 티켓에서는
  추가하지 않았다.
