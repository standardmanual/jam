# [Admin] 배지 삭제 버튼이 비활성화와 동일하게 동작 — 이력 없는 배지는 실제 삭제되도록 분리

## 배경 / 문제 정의
사용자가 `/admin/badges`에서 체크인 배지·액티비티 배지 여러 건을 "비활성" 필터로 보다가,
이미 비활성 상태인 배지의 상세 화면에서 "삭제" 버튼을 눌러도 아무 변화가 없다고 보고했다.

**오케스트레이터 사전 조사 결과(원인 확정):**
- `/admin/badges/[id]` 상세 화면의 "삭제" 버튼(`BadgeDetail.tsx` 299~306행)과 "비활성화" 토글
  버튼(`BadgeActiveToggleButton.tsx`)이 **완전히 동일한 백엔드 동작**을 호출한다 — 둘 다
  `badges.deleted_at`에 타임스탬프만 세팅하는 소프트 삭제(`DELETE /api/admin/badges/[id]`,
  `PATCH /api/admin/badges/[id]` 모두 같은 필드를 갱신). 그래서 이미 비활성 상태(=이미
  `deleted_at`이 세팅된 상태)인 배지에서 "삭제"를 눌러도 값이 이미 같아 화면상 아무 변화가
  없는 것처럼 보인다. DB 조회로 실제 확인함 — 사용자가 언급한 배지 전부 이미 `deleted_at`이
  세팅돼 있었다(20260830_1344에서 삭제 스텁 버그는 이미 수정되어 프로덕션에 반영된 상태,
  `b0e3bb58`가 `origin/main`에 포함됨을 확인).
- 이건 애초에 버그가 아니라 **"삭제"와 "비활성화"가 사용자 기대와 달리 같은 동작**이라는
  설계 결함이다. 사용자는 "삭제를 눌렀으면 실제로 삭제되어야 한다"는 기대를 명시했다
  (2026-08-30 확인 완료).
- **FK 조사 결과(오케스트레이터, Supabase 직접 조회)** — `badges.id`를 참조하는 12개 테이블
  중 하드 삭제 시 문제가 되는 것들:
  - `user_activity_badges.badge_id`, `inventory_items.badge_id`, `poi_drops.badge_id`:
    NOT NULL + `ON DELETE NO ACTION` → 이력이 있으면 하드 삭제 시 FK 위반으로 그냥 실패한다.
  - `user_checkin_badge_earns.badge_id`, `user_item_book_slots.badge_id`: NOT NULL +
    **`ON DELETE CASCADE`** → 하드 삭제하면 이 두 테이블의 관련 행이 **자동으로 통째로
    삭제된다.** 즉 지금 스키마 그대로 하드 삭제를 강행하면 "이력 보존"이 아니라 정반대로
    유저의 체크인 획득 기록·아이템북 슬롯 진행 기록이 조용히 사라진다.
  - `poi.linked_badge_id`: nullable이지만 `ON DELETE NO ACTION` → 연결된 지점이 있으면
    하드 삭제가 막힌다.
- **범위 결정(사용자 확인, 2026-08-30)**: "이력을 남기면서 강제 삭제"는 위 6개 테이블의
  FK를 nullable + `ON DELETE SET NULL`로 바꾸는 스키마 마이그레이션이 필요해 리스크가 크다
  (인벤토리·포인트·체크인 획득 기록 등 핵심 유저 데이터 테이블). **이번 티켓은 안전한
  범위로 한정한다: 이력이 전혀 없는 배지만 실제 하드 삭제, 이력이 하나라도 있으면 삭제를
  차단하고 명확한 안내 메시지를 보여준다.** 스키마를 바꿔 이력 보존형 강제 삭제를 지원하는
  것은 별도 티켓으로 분리한다(이번 범위 아님).

## 상세 요구사항

### 서비스/코드베이스 관점
- `DELETE /api/admin/badges/[id]`(`jam-web/src/app/api/admin/badges/[id]/route.ts` 91~125행)
  동작을 변경한다:
  1. 대상 배지 존재 확인(기존 로직 유지).
  2. 아래 6개 테이블에서 해당 `badge_id`(또는 `poi.linked_badge_id`) 참조가 하나라도
     있는지 확인한다: `user_activity_badges`, `inventory_items`, `poi_drops`,
     `user_checkin_badge_earns`, `user_item_book_slots`, `poi`(linked_badge_id).
  3. **참조가 하나도 없으면** `badges` 행을 실제로 `DELETE`(하드 삭제)한다.
  4. **참조가 하나라도 있으면** 삭제하지 않고 409 등 적절한 상태 코드로 명확한 에러 메시지를
     반환한다 (예: "이미 N명의 유저에게 발급된 배지라 완전히 삭제할 수 없습니다. 비활성화를
     이용해주세요." — 실제 이력 건수를 합산해 N에 반영하면 더 명확하다).
  5. 기존 소프트 삭제(`deleted_at` 세팅) 로직은 **완전히 대체되는 게 아니라 유지**해야 한다 —
     "비활성화" 버튼(`BadgeActiveToggleButton`, `PATCH { active: false }`)은 계속 소프트
     삭제로 동작해야 한다(가역적 동작이므로 그대로 둔다). 오직 `DELETE`(하드 삭제 대상)
     엔드포인트의 의미만 바뀐다.
  6. `invalidateUnclaimedDrops` 호출은 하드 삭제가 실제로 일어난 경우에만 의미가 있다 —
     차단된 경우(409)에는 호출하지 않는다. 하드 삭제된 경우 미픽업 드랍이 있었다면(이력
     0건 조건에 `poi_drops`가 포함되므로 사실상 없어야 하지만) 방어적으로 유지할지 구현자
     판단.
- `BadgeDetail.tsx`의 `handleDelete()`는 이미 API 에러 메시지를 `alert()`로 노출하는 구조라
  (95~110행) 프론트 수정은 최소화될 것으로 예상되나, 409 응답의 에러 메시지가 실제로 그대로
  노출되는지 확인한다.
- `BadgesTable.tsx`/`BadgeCard.tsx`/`BadgeList.tsx`에는 별도 삭제 버튼이 없음을 이전
  티켓(20260830_1344)에서 이미 전수 확인했다 — 이번에도 grep으로 재확인만 하면 된다.

## 구현 계획
1. `DELETE /api/admin/badges/[id]`에 6개 테이블 참조 존재 여부 확인 쿼리 추가.
2. 참조 없음 → 실제 `DELETE FROM badges WHERE id = ...` 수행(하드 삭제)로 교체.
3. 참조 있음 → 409 + 안내 메시지 응답으로 변경(기존 소프트 삭제 폴백 없이 명확히 차단).
4. `BadgeDetail.tsx`의 에러 처리(`alert(data.error ?? ...)`)가 새 메시지를 그대로 보여주는지
   확인, 필요 시 문구만 다듬는다.
5. 회귀 확인: "비활성화" 토글(`PATCH`)은 기존과 동일하게 소프트 삭제로 동작하는지(이번
   변경은 `DELETE`에만 적용되고 `PATCH`는 건드리지 않음) 정적 검토.
6. `npx tsc --noEmit -p .`, `npm run lint` 확인.
7. 이력 없는 배지 1건 + 이력 있는 배지 1건을 실제로 API 직접 호출(curl 등) 또는 정적 코드
   경로 검토로 두 분기 모두 확인. 실제 브라우저 클릭 재현은 어드민 스테이징 검증 불가
   제약상 프로덕션 배포 후 사용자가 확인.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- `DELETE /api/admin/badges/[id]`를 하드 삭제로 교체: `user_activity_badges`·`inventory_items`·
  `poi_drops`·`user_checkin_badge_earns`·`user_item_book_slots`(모두 `badge_id`)·`poi`
  (`linked_badge_id`) 6개 테이블 참조 건수를 `Promise.all` + `count: 'exact', head: true`로
  합산 조회 후, 합계가 0이면 실제 `DELETE FROM badges`(하드 삭제), 1건이라도 있으면 409 +
  [현상]→[원인]→[해결책] 구조 에러 메시지를 반환하고 삭제를 차단한다.
- `PATCH`(비활성화 토글)는 건드리지 않았다 — 기존과 동일하게 `deleted_at` 세팅/해제만 하는
  가역적 소프트 삭제로 유지. 두 핸들러의 관계를 설명하던 stale 주석(PATCH가 "기존 DELETE
  핸들러와 동일 동작"이라던 부분)을 새 동작에 맞게 갱신.
- 하드 삭제가 실제 발생한 경우에만 `invalidateUnclaimedDrops`를 호출(차단된 409 응답에는
  호출하지 않음). 이력 0건 조건에 `poi_drops`도 포함돼 있어 이 시점엔 사실상 no-op이지만
  방어적으로 유지.
- `BadgeDetail.tsx`(`/admin/badges/[id]` 상세)·`BadgeForm.tsx`(`/admin/badges/[id]/edit`) 두
  삭제 확인 다이얼로그 문구를 "완전히 삭제합니다 + 이력 있는 배지는 비활성화만 가능하다"는
  안내로 보강. 두 컴포넌트 모두 기존에 `alert()`/`setError()`로 API의 `data.error`를 그대로
  노출하는 구조라 409 에러 메시지 노출 자체는 추가 수정 없이 동작함을 확인.
- `BadgesTable.tsx`/`BadgeCard.tsx`/`BadgeList.tsx`에 별도 삭제 버튼이 없음을 grep으로
  재확인(이전 티켓 20260830_1344와 동일 결론). 대신 `BadgeForm.tsx`에도 같은 DELETE
  엔드포인트를 호출하는 삭제 흐름이 있어 함께 문구를 갱신함(티켓 본문엔 명시 안 됐으나
  같은 API·같은 UX 기대를 공유해 범위에 포함).
