# [Infra] 수기 타입 ↔ Supabase 생성 타입 불일치 전수 점검 (research)

## 배경 / 문제 정의

티켓 [20260831_1118](20260831_1118_Service_어드민-드랍정책-저장-조용한실패-upsert에러삼킴.md)에서
어드민 드랍 정책 저장이 41일간 조용히 실패했다. 근본 원인 중 하나가 **타입 파일 이중 관리**였다 —
수기 `src/types/database.ts`(앱 키 기준)와 생성 `src/types/database.generated.ts`(DB 실제 컬럼 기준)가
어긋나 있는데, 코드는 수기 타입을 참조하고 upsert의 `@ts-expect-error`가 남은 오류까지 눌러
컬럼명 불일치가 타입 시스템에 전혀 걸리지 않았다.

그 티켓의 "범위 밖 발견물 3번"으로 분리된 전수 점검이 이 티켓이다.
**핵심 질문: 이미 아는 `drop_policy`·`abusing_policy` 외에 어긋난 테이블이 더 있는가?**

## 상세 요구사항

### 서비스/코드베이스 관점
- 두 타입 파일을 전체 대조해 어긋난 테이블·컬럼을 전부 찾는다
- 생성 타입이 최신인지 먼저 검증한다 (낡은 파일과 비교하면 결론이 틀어진다)
- 발견한 각 불일치에 대해 실제 피해(쓰기 실패) 여부를 판정한다
- 구조적 재발 방지책을 비용 대비 효과로 따져 추천안 하나를 제시한다

### 범위 밖 (이번 티켓에서 하지 않는다)
- **컬럼 개명 금지.** 배지 등급명 `common/rare/legend/mythic` → `common/rare/epic/mystic` 개명
  작업이 별도로 예정돼 있고 `rarity_legendary` → `rarity_epic` 등이 거기 포함된다
- `drop_policy`는 `lib/drop-engine/policy.ts`의 `APP_KEY_TO_DB_COLUMN`으로 이미 대응 완료
- `abusing_policy`는 별도 티켓에서 같은 방식으로 대응 예정 — 중복 수정하지 않는다

## 구현 계획
코드 변경 없는 조사(`research`). 조사 방법:
1. 두 타입 파일을 파싱해 테이블→컬럼 집합 추출 (의존성 없는 자체 파서)
2. `information_schema.columns` 직접 조회를 **제3의 기준**으로 삼아 3자 대조
3. 쓰기 없는 PostgREST 프로브(`PATCH ?id=eq.-1`)로 스키마 캐시 수용 여부 실측
4. 타입 전환 실험으로 재발 방지책의 실효성과 비용을 실측

### 3. 실제 피해 판정 — PostgREST 스키마 수용 프로브

어떤 행도 매칭하지 않는 필터로 PATCH를 보내 **쓰기 없이** 스키마 캐시 수용 여부만 확인했다
(`drop_policy`·`abusing_policy`는 `id` integer라 `?id=eq.-1`, `badges`·`poi`는 uuid라 nil uuid).

```
drop_policy    rarity_legend           → HTTP 400 PGRST204   ← 수기 키는 DB가 거부
drop_policy    rarity_legendary        → HTTP 204            ← 실제 컬럼은 수용
abusing_policy soft_legend_rate        → HTTP 400 PGRST204
abusing_policy hard_legend_rate        → HTTP 400 PGRST204
abusing_policy soft_legendary_rate     → HTTP 204
abusing_policy hard_legendary_rate     → HTTP 204
badges         category                → HTTP 204            ← DB·캐시는 정상, 생성타입만 낡음
poi            is_active               → HTTP 204            ← 동일
[대조군] drop_policy __no_such_column__ → HTTP 400 PGRST204   ← 프로브가 실제로 검출함을 확인
```

대조군까지 넣어 프로브 자체의 유효성을 확인했고, 매칭 행이 0이므로 **데이터 변경 0건**이다.

| 불일치 | 실제 피해 | 조치 |
|---|---|---|
| `drop_policy.rarity_legend` | 저장 전체 실패였음 → **해소됨** | 20260831_1118의 `APP_KEY_TO_DB_COLUMN`으로 대응 완료. `updated_at` 2026-08-31 02:40로 갱신 확인 |
| `abusing_policy.soft/hard_legend_rate` | **저장 실패 지속 중** | `updated_at`이 `2026-08-13 01:28`에 고착 (18일). 별도 티켓 예정 — 이번엔 손대지 않음 |
| `badges.category`, `poi.is_active` | **런타임 피해 없음** | `database.generated.ts`를 import하는 코드가 **0건**(전 저장소 grep). 코드는 전부 수기 타입을 쓰고, 수기 타입엔 두 컬럼이 있어 정상 동작 |

`badges.category`·`poi.is_active`의 피해는 런타임이 아니라 **판단 오염**이다. 생성 타입은
"DB 실제 스키마"라는 이름으로 참조되는 파일인데 실제로는 틀려 있어, 이번 조사처럼 그것을
기준 삼는 모든 검증·CI가 오판한다.

### 4. 구조적 원인 실증 — `@ts-expect-error` 92개가 쓰기 검사를 전면 무력화

`src/` 전체에 `@ts-expect-error` 지시자가 **92개**(55개 파일)다.

| 분류 | 개수 |
|---|---|
| Supabase 쓰기 페이로드 `never` 추론 우회 | 55 |
| RPC 함수가 `database.ts` Functions에 미등록 | 11 |
| 기타(추론 특이 케이스 등) | 26 |

**왜 `never`로 붕괴하는가 — 원인을 특정했다.**
수기 파일은 Row 타입을 `export interface UserRow {...}`로 선언한다. TypeScript에서 `interface`는
암묵적 인덱스 시그니처를 갖지 않아 supabase-js의 `GenericTable`(`Row: Record<string, unknown>`)
제약을 만족하지 못한다. 그 결과 클라이언트 제네릭 해석이 무너지며 모든 쓰기 페이로드가
`never[]`로 추론된다.

실증 (`npx tsc --noEmit`, 임시 프로브 파일):

```
수기 타입 + 올바른 앱 키       → TS2353 'never[]'  ← 맞는 값도 오류
수기 타입 + 실제 DB 컬럼        → TS2353 'never[]'
수기 타입 + 없는 컬럼           → TS2353 'never[]'
Row를 매핑 타입으로 감싼 경우:
  + 올바른 앱 키                → 통과 ✅
  + 없는 컬럼                   → TS2322 오류로 검출 ✅
```

`CompositeTypes`·`__InternalSupabase`를 추가하는 것만으로는 해소되지 않았고,
**Row를 매핑 타입(`{ [K in keyof T]: T[K] }`)으로 감싸자 검사가 즉시 정상 작동**했다.

이것이 사고의 진짜 메커니즘이다: 수기 타입이 모든 쓰기를 오류로 만드니 개발자는 쓰기 지점마다
`@ts-expect-error`를 달 수밖에 없었고, **그 지시자가 컬럼명 검증까지 함께 꺼버렸다.**
→ **두 타입 파일의 정합성만 맞춰도 쓰기 경로 방어는 여전히 0이다.**

### 5. 재발 방지책 — 전환 비용 실측

Supabase 클라이언트 제네릭을 생성 타입으로 바꾸면 검사가 살아나는지 실측했다.

```
생성 타입 + soft_legend_rate   → TS2345 오류 ✅  ← 이번 사고를 컴파일에서 잡는다
생성 타입 + soft_legendary_rate → 통과 ✅
생성 타입 + 없는 컬럼           → TS2345 오류 ✅
```

`src/lib/supabase/{client,server}.ts` 3줄(`client.ts:9`, `server.ts:13`, `server.ts:41`)의
import를 생성 타입으로 바꾸고 `@ts-expect-error` 92개를 전부 제거한 뒤 측정:

| 상태 | 오류 수 |
|---|---|
| 현재(억제 92개 유지) | 0 |
| 생성 타입 전환 + 억제 전부 제거 | **38** |
| 위 + 생성 타입의 낡은 2컬럼 보정 | **27** (17개 파일) |

잔여 27건의 근본 원인은 8종 정도로 수렴한다:

| 원인 | 건수 |
|---|---|
| 테스트 파일 목(mock) 오버로드 | 5 |
| `points/index.ts` RPC Args nullable(`string\|null` vs `string\|undefined`) | 4 |
| `inventory_items.obtained_by` enum 좁히기 (4개 호출부 동일 원인) | 4 |
| `PostgrestFilterBuilder` 대입 — supabase-js 잔여 추론 한계 | 5 |
| **`abusing_policy` 실제 컬럼 불일치 (= 잡아내야 할 진짜 버그)** | **2** |
| enum/nullable 정합 기타 | 7 |

### 6. 추천안 (하나만)

> **Supabase 클라이언트 제네릭을 `database.generated.ts`로 교체하고, 수기 `database.ts`는
> 클라이언트에서 분리해 도메인 타입·주석 자산으로만 남긴다.**

- **전환점이 3줄뿐이다.** 수기 타입을 import하는 파일은 168개지만 대부분 Row 타입을
  도메인 용도로 쓸 뿐이고, `Database` 제네릭 주입은 `client.ts`·`server.ts` 3곳에만 있다.
- **효과가 직접 실증됐다.** 이번 사고의 `soft_legend_rate`가 컴파일 오류로 잡히고,
  `never` 계열 억제 55개가 통째로 사라진다.
- **비용이 실측됐다.** 27건 / 17파일, 원인 8종. 억제를 한 번에 다 걷지 않고 파일 단위로
  나눠 진행할 수 있어 단계적 처리가 가능하다.
- 수기 파일의 도메인 주석(각 컬럼의 의미·마이그레이션 근거)은 이 저장소의 실질 자산이라
  삭제하지 않고 유지한다. 다만 **더 이상 런타임 타입의 진실 원천이 아님**을 명확히 한다.

**대안 검토 (채택하지 않음):**

| 대안 | 판정 |
|---|---|
| 두 파일 정합성 CI 스크립트 | **단독으로는 부족.** 이번에 생성 파일 자체가 낡아 있었다 — 두 파일 diff는 "어느 쪽이 틀렸는지"를 못 가린다. 필요한 건 `npm run db:types` 재생성 후 `git diff --exit-code` 한 줄(= 생성 타입 최신성 검사)이고, 이건 추천안과 함께 쓰면 되는 보조 수단이다 |
| 수기 Row를 매핑 타입으로 감싸기 | **부분 해결.** `never` 붕괴는 풀리지만 검사 기준이 여전히 수기 타입이라 DB 드리프트 계열(이번 사고)은 못 잡는다. 3줄 교체와 비용이 비슷한데 효과가 작다 |
| 수기 타입 전면 삭제 | **비추천.** 168개 파일이 영향받고, 도메인 주석 자산을 잃는다. 얻는 것은 추천안과 같다 |
