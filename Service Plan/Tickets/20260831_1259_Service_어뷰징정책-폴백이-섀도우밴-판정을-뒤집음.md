# [Service] 어뷰징 정책 폴백이 섀도우밴 판정을 뒤집는다 — DEFAULT_POLICY 불일치 + fail-open

## 배경 / 문제 정의

티켓 20260831_1149의 "범위 밖 발견물" 2번에서 분리된 건이다. 그 티켓은 어뷰징 정책의
**저장 경로와 읽기 관측**을 복구했고, 이 티켓은 **폴백이 정책 자체를 바꿔버리는 문제**를 다룬다.

두 결함이 맞물려 있다.

### 1. `DEFAULT_POLICY`가 실제 운영값과 반대다

`jam-web/src/lib/abusing/policy.ts`의 `DEFAULT_POLICY`는 `soft_epic_rate: 0.0`,
`hard_epic_rate: 0.0`(= 차단)인데 **실제 DB 값은 둘 다 1.00**(= 차단 꺼짐)이다.
마이그레이션 115(`115_rename_rarity_epic_mystic.sql` §5)가 사용자 확인(2026-08-31) 하에
"유저 체감 동작을 바꾸지 않는다"는 이유로 그렇게 설정했고, **차단을 실제로 켤지는 별도 티켓으로
미뤄뒀다.**

따라서 DB 조회가 실패해 `DEFAULT_POLICY`로 폴백하는 순간 **의도적으로 꺼둔 Epic 차단이 켜진다.**
폴백이 장애 대응이 아니라 정책 변경이 되는 셈이다.

**2026-08-31 12:59 실측 DB 값** (읽기 전용 조회, `abusing_policy` id=1):
```json
{"id":1,"soft_common_rate":1.00,"soft_rare_rate":1.00,"soft_epic_rate":1.00,"soft_mystic_rate":0.00,
 "hard_common_rate":1.00,"hard_rare_rate":0.00,"hard_epic_rate":1.00,"hard_mystic_rate":0.00,
 "gps_max_speed_kmh":300,"poi_block_hours":72,"vehicle_speed_filter_kmh":60,
 "gps_daily_distance_cap_km":3000,"updated_at":"2026-08-31T03:48:29.414791+00:00"}
```
→ `DEFAULT_POLICY`와 어긋나는 키는 **`soft_epic_rate`·`hard_epic_rate` 2개뿐**이고, 나머지 10개는
일치한다. 즉 이 두 값만 맞추면 `DEFAULT_POLICY`는 운영 행의 **정확한 미러**가 된다.

### 2. `shouldAllowDrop`의 fail-open

`jam-web/src/lib/abusing/shadow-ban.ts:42-43`:
```ts
const rateKey = `${banLevel}_${rarity}_rate` as keyof AbusingPolicy
const rate = policy[rateKey] as number ?? 1.0
```

- 정책 키가 없으면 `1.0`(전면 허용)으로 떨어진다. 이 fail-open 때문에 2026-08-13 ~ 08-31
  **18일간** 컬럼명 불일치가 곧 **Epic 차단 무력화**로 이어졌는데도 신호가 하나도 없었다.
- 키를 런타임 문자열로 조합(`${banLevel}_${rarity}_rate`)하므로 등급명이 바뀌어도
  **타입 검사에 걸리지 않는다.** 티켓 20260813_003이 rename 3곳을 놓친 것과 같은 구조다.
- `?? 0`(fail-closed)으로 뒤집으면 조회 실패 시 **모든 등급 드랍이 차단**돼 과하다.
  common까지 막히면 장애가 서비스 정지로 번진다.

### 폴백 방향이 두 곳에서 서로 모순인 상태

지금 폴백 소스가 두 개고 방향이 반대다.

| 폴백 지점 | epic에 대한 방향 |
|---|---|
| `getAbusingPolicy()` → `DEFAULT_POLICY` | 0.0 = **차단** |
| `shouldAllowDrop()` → `?? 1.0` | 1.0 = **허용** |

어느 쪽을 타느냐에 따라 결과가 갈리는데 둘 다 무음이다. **폴백 소스를 하나로 합치는 것이
이 티켓의 핵심**이다.

## 상세 요구사항

### 서비스/코드베이스 관점

#### (핵심 1) `DEFAULT_POLICY`를 운영 행에 정렬한다 — DB는 건드리지 않는다

- `soft_epic_rate`·`hard_epic_rate`를 **`0.0` → `1.0`** 으로 바꾼다.
- **DB 값 변경(1.00 → 0.00, 즉 Epic 차단 켜기)은 이 티켓에서 하지 않는다.**
  마이그레이션 115 §5가 사용자 확인 하에 미뤄둔 판단이고, 유저 체감 동작이 바뀐다.
  이 티켓은 **"폴백이 정책을 바꾸지 않는다"는 불변식만 세운다.**
- 근거를 주석으로 남긴다: `DEFAULT_POLICY`는 **"바람직한 값"이 아니라 "DB를 못 읽을 때
  현행 운영값을 그대로 재현하는 값"** 이다. 실측 일자와 마이그레이션 115 §5,
  `SERVICE_OPERATIONS.md` §12-5를 함께 인용한다.
- **DB 배율을 바꾸면 같은 티켓에서 `DEFAULT_POLICY`도 바꿔야 한다**는 규칙을 주석과
  `SERVICE_OPERATIONS.md` §12-5 양쪽에 명시한다 (패턴 6 "암묵적 등록 지점" 완화).

#### (핵심 2) 등급 → 정책 키 매핑을 타입으로 고정한다

문자열 조합을 없애고 **`Record<BadgeRarity, keyof AbusingPolicy>`** 로 명시한다.
티켓 20260831_1115의 커밋 `cbdb5047`이 다른 등급 맵(`RARITY_LABEL`·`RARITY_TIER`·
`RARITY_RANK` 등)에 이미 적용한 방식을 그대로 따른다.

```ts
/** 밴 레벨 × 등급 → 정책 배율 키. Record로 고정해 등급이 늘거나 이름이 바뀌면 tsc가 잡는다 */
const BAN_RATE_KEY: Record<Exclude<BanLevel, 'none'>, Record<BadgeRarity, keyof AbusingPolicy>> = {
  soft: { common: 'soft_common_rate', rare: 'soft_rare_rate', epic: 'soft_epic_rate', mystic: 'soft_mystic_rate' },
  hard: { common: 'hard_common_rate', rare: 'hard_rare_rate', epic: 'hard_epic_rate', mystic: 'hard_mystic_rate' },
}
```

- 등급이 추가되거나 이름이 바뀌면 **컴파일 에러**가 난다. 키 문자열도 `keyof AbusingPolicy`라
  인터페이스와 어긋나면 잡힌다. 이번 사고의 근본 원인(런타임 문자열 조합)이 사라진다.
- 맵 위치는 `shadow-ban.ts` 안. `policy.ts`는 `shadow-ban.ts`를 import하지 않으므로 순환 없다.

#### (핵심 3) 폴백 방향을 등급별로 나눈다 — 폴백 소스는 `DEFAULT_POLICY` 하나

`?? 1.0`(전면 허용)도 `?? 0`(전면 차단)도 쓰지 않는다. 두 경우를 분리한다.

| 상황 | 처리 | 방향 |
|---|---|---|
| **A. 맵에 없는 등급** (DB enum이 TS 타입보다 앞서간 구간) | `console.error` 후 **`false` 반환** | **fail-closed** |
| **B. 키는 있으나 값이 없거나 숫자가 아님** | `console.error` 후 **`DEFAULT_POLICY[rateKey]`** 적용 | **등급별 정책 기본값** |

- **A를 fail-closed로 두는 근거**: 이 분기는 `banLevel !== 'none'`, 즉 **이미 밴이 확인된 유저**
  에게만 닿는다. 정상 유저는 함수 첫 줄 `if (banLevel === 'none') return true`에서 빠져나가므로
  영향이 없다. 밴 유저의 미지 등급 드랍을 막는 쪽이 안전하고, 서비스 정지로 번지지 않는다.
- **B를 `DEFAULT_POLICY`로 폴백하는 근거**: 폴백 소스가 `getAbusingPolicy()`와 같아져
  **"어느 폴백을 타든 결과가 같다"** 는 성질이 생긴다. 등급별 의도(common은 허용, mystic은 차단)도
  보존된다. 전면 허용/전면 차단은 둘 다 정책 의도를 뭉갠다.
- 두 분기 모두 **반드시 `console.error`를 남긴다.** 18일 무음의 직접 원인이 "폴백에 신호가
  없었다"는 점이다 (`DEV_PROCESS_GUARDRAILS.md` 패턴 9 규칙 3·6).
- fail-open이 아님을 함수 주석에 명시한다 (패턴 9 규칙 6은 fail-open을 택했을 때 주석을
  요구하지만, 방향을 바꾼 이번 건도 근거를 남긴다).

#### 오늘 시점 동작 변화 — 없다

`getAbusingPolicy()`는 마이그레이션 115 적용 후 12개 키를 모두 숫자로 정규화해 돌려주므로,
`shouldAllowDrop`이 실제로 폴백을 타는 경로는 **현재 존재하지 않는다.** 이 변경은
장애·롤백 구간의 동작만 바꾼다. 정리하면:

| 구간 | 변경 전 | 변경 후 |
|---|---|---|
| 정상 (키 12종 정상) | 정책값 그대로 | **동일** (변화 없음) |
| 정책 조회 실패 + 밴 조회 성공 | epic 차단(DEFAULT 0.0) | epic 허용(DEFAULT 1.0) = **운영값과 일치** |
| DB 전체 장애 | 영향 없음 (`getUserBanLevel`이 `'none'` 반환 → 첫 줄에서 허용) | **동일** |
| 마이그레이션 115 롤백 구간 | 미지 등급 → 허용(`?? 1.0`) | 미지 등급 → **차단** |

> 마지막 행은 유일한 실질 변경이다. 115 롤백 시 DB의 구 컬럼 저장값은
> `soft|hard_legendary_rate = 0.00`, `soft|hard_mythic_rate = 0.00`(1149 티켓의 백업값)이므로,
> **fail-closed 결과가 DB에 적힌 의도와 일치한다.** 반대로 변경 전 동작(허용)은 그 저장값을
> 무시하는 쪽이었다.

### 범위 밖 (이번 티켓에서 하지 않는다)

- **DB의 `soft_epic_rate`·`hard_epic_rate`를 0.00으로 되돌리지 않는다** (= Epic 차단을 켜지
  않는다). 유저 체감 동작 변경이고 115 §5가 별도 판단으로 미뤄뒀다. **사용자 승인 없이 금지.**
  이 티켓의 결과물은 "차단을 켜기로 하면 DB와 `DEFAULT_POLICY`를 한 번에 바꾸면 된다"는
  상태를 만드는 것까지다.
- **`getAbusingPolicy()`의 `{ ...row, ...normalized }` 상위집합 스프레드를 제거하지 않는다.**
  1149의 잔여 이슈다. 다만 핵심 2를 넣으면 **이 스프레드가 `shadow-ban`을 돕던 근거는
  사라진다**(구 컬럼 키를 보존해도 타입 맵이 그 키를 찾지 않는다). 이 사실을 완료 기록에 남긴다.
- `strava/sync.ts:458`의 truthy 검사 버그, `drop-policy/route.ts`의 합니다체 잔존,
  어드민 밴 부여·해제 무음 실패는 별건이다. 발견분은 `sideFindings`로만 보고한다.
- 어드민 화면·API 라우트는 건드리지 않는다. `DEFAULT_POLICY`의 **키 목록**은 그대로이므로
  화이트리스트 동작에 영향이 없다.

## 구현 계획

1. **`jam-web/src/lib/abusing/policy.ts`**
   - `DEFAULT_POLICY.soft_epic_rate`·`hard_epic_rate`: `0.0` → `1.0`.
   - 상수 위 주석에 성격 정의(운영 행 미러) + 실측 일자 + 115 §5·`SERVICE_OPERATIONS` §12-5
     참조 + "DB 배율 변경 시 같은 티켓에서 함께 갱신" 규칙을 적는다.

2. **`jam-web/src/lib/abusing/shadow-ban.ts`**
   - `DEFAULT_POLICY`를 값으로 import (현재는 타입만 import).
   - `BAN_RATE_KEY` 맵 추가 (핵심 2).
   - `shouldAllowDrop` 재작성 (핵심 3). 런타임 방어를 위해 맵 조회 결과를
     `keyof AbusingPolicy | undefined`로 받되, **타입 단언 사유를 주석으로 남긴다**
     (DB enum이 TS 타입보다 앞서갈 수 있는 구간 방어).
   - 로그 접두사는 기존 관행에 맞춰 `[shadow-ban]`.
   - `if (rate <= 0) return false` / `if (rate >= 1) return true` / 부분 확률 롤은 유지.

3. **테스트 — `jam-web/src/lib/abusing/__tests__/`**
   기존 `policy-save.test.ts`가 `shouldAllowDrop`을 이미 쓴다. 그 파일의 기대값은 유지되지만
   **성립 근거가 바뀌므로**(상위집합 보존 → fail-closed) 해당 테스트의 주석을 갱신한다.
   신규 케이스는 `shadow-ban.test.ts`(신규) 또는 기존 파일 확장 중 개발자가 판단해 배치한다.
   - `DEFAULT_POLICY`의 8개 배율이 **2026-08-31 실측 운영 행과 일치**한다 (불변식 고정).
   - 밴이 없으면(`'none'`) 정책과 무관하게 항상 허용된다.
   - 정상 정책에서 등급별 판정: soft → common·rare·epic 허용, mystic 차단 /
     hard → common·epic 허용, rare·mystic 차단.
   - **미지 등급은 차단하고 `console.error`를 남긴다** (`'legendary' as BadgeRarity`).
   - **값이 없거나 NaN이면 `DEFAULT_POLICY` 값을 쓰고 `console.error`를 남긴다**
     (예: `hard_rare_rate` 삭제 → 여전히 차단 / `soft_epic_rate` 삭제 → 여전히 허용).
   - 부분 확률(0 < rate < 1)이 `Math.random()`을 타는 경로가 유지된다 (스텁으로 고정).
   - **회귀 가드 실효성 실증**: `BAN_RATE_KEY`의 `epic` 키를 구 이름으로 되돌리면
     `tsc`가 잡는지 확인하고 원복한다 (문자열 조합에서는 잡지 못했던 지점).

4. **문서**
   - `Service Plan/Specs/SERVICE_OPERATIONS.md` §12-5: `DEFAULT_POLICY`가 이 행의 미러라는
     불변식과 "DB 배율을 바꾸면 `policy.ts`도 같은 티켓에서 바꾼다"를 추가한다.
     **§12-3의 "Epic 차단은 현재 꺼져 있다"는 서술은 그대로 유효하다**(동작을 바꾸지 않았으므로).
   - `Service Plan/Specs/DEV_PROCESS_GUARDRAILS.md` 패턴 9 규칙 6: 이번 적용 사례를 한두 줄로

     만들고 미지 키만 fail-closed로 두는 방법".
   - PRD·배지엔진 문서는 갱신 대상이 아니다 (드랍 확률·정책 값이 바뀌지 않음).

5. **검증**

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

1. **`DEFAULT_POLICY`를 운영 행에 정렬** — `soft_epic_rate`·`hard_epic_rate`를 `0.0` → `1.0`.
   상수 위에 성격 정의(운영 행 미러, 2026-08-31 실측), 마이그레이션 115 §5·`SERVICE_OPERATIONS` §12-5
   참조, "DB 배율을 바꾸면 같은 티켓에서 이 상수도 바꾼다" 규칙을 주석으로 남겼다.
   **DB는 읽지도 쓰지도 않았다.**
2. **등급 → 정책 키 매핑을 타입으로 고정** — `BAN_RATE_KEY: Record<Exclude<BanLevel,'none'>,
   Record<BadgeRarity, keyof AbusingPolicy>>`를 `shadow-ban.ts`에 추가하고 문자열 조합을 제거했다.
3. **폴백 방향 분리** — 미지 등급은 `console.error` + `false`(fail-closed), 값 결여·NaN은
   `console.error` + `DEFAULT_POLICY[rateKey]`. 폴백 소스를 `getAbusingPolicy()`와 통일해
