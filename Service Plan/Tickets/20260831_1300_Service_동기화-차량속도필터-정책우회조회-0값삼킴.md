# [Service] 동기화 차량 속도 필터가 정책 로더를 우회 조회하며 0 값을 삼킴

## 배경 / 문제 정의

`jam-web/src/lib/strava/sync.ts:456-466`은 차량 속도 필터 임계값
(`abusing_policy.vehicle_speed_filter_kmh`)을 **정식 경로 `getAbusingPolicy()`를 우회해**
직접 select한다. 이 우회 조회에 결함 세 가지가 겹쳐 있다.

```ts
let vehicleSpeedFilterKmh = 60
const { data: abusingPolicy } = await supabase
  .from('abusing_policy')
  .select('vehicle_speed_filter_kmh')
  .limit(1)
  .single()
if (abusingPolicy && (abusingPolicy as { vehicle_speed_filter_kmh?: number }).vehicle_speed_filter_kmh) {
  vehicleSpeedFilterKmh = (abusingPolicy as { vehicle_speed_filter_kmh: number }).vehicle_speed_filter_kmh
}
```

### 결함 1 — truthy 검사가 `0`을 삼킨다

조건이 truthy 검사라 값이 `0`이면 falsy로 떨어져 **하드코딩 기본값 60**이 조용히 적용된다.
`/api/admin/abusing/policy`의 PUT 검증은 `n < 0`만 막으므로 **어드민에서 0은 저장 가능한 값**이다.
운영자가 0을 저장하면 DB에는 0이 들어가고 화면에도 0이 보이지만 실제 동기화는 60으로 돈다.
저장은 성공했는데 동작은 다른 **조용한 불일치**다.

### 결함 2 — 반환 `error`를 확인하지 않는다

`const { data } = ...`로 `error`를 구조분해조차 하지 않아, 조회가 실패해도 로그 한 줄 없이
기본값 60으로 넘어간다. `Specs/DEV_PROCESS_GUARDRAILS.md` 패턴 9 규칙 1·3 위반이다
(폴백은 서비스를 살리는 장치지 불일치를 감추는 장치가 아니다).

### 결함 3 — `abusing_policy`의 두 번째 접근 지점

정식 경로 `jam-web/src/lib/abusing/policy.ts`의 `getAbusingPolicy()`를 우회하므로,
직전 티켓 20260831_1149가 그 함수에 넣은 **NUMERIC 문자열 정규화 · 조회 실패 로그 ·
키 누락 관측 · 원본 행 상위집합 반환**이 이 경로에는 하나도 적용되지 않는다.
`.limit(1).single()`로 `id` 조건 없이 읽는 점도 정식 경로(`.eq('id', 1)`)와 다르다 —
지금은 행이 1건이라 우연히 맞지만, 행이 늘면 어떤 행을 읽을지 보장이 없다.

`Specs/DEV_PROCESS_GUARDRAILS.md`의 "핵심 루프 의존성 지도" `abusing_policy` 행에
이 우회 조회가 이미 명시돼 있다.

### 영향 범위가 "배지 평가"보다 넓다

어드민 UI 문구와 `SERVICE_OPERATIONS.md`는 이 필터를 "배지 평가에서 제외"로 설명하지만,
실측하면 `activitiesFiltered`는 **핵심 보상 루프 전체**에 흘러든다.

| 소비 지점 | sync.ts 줄 | 영향 |
|---|---|---|
| `dropTargets` (아이템 드랍 대상 선정) | 479 | 아이템 드랍 |
| `tryItemDrop(userId, activity, activitiesFiltered)` | 494 | 아이템 드랍 |
| `evaluateBadges(userId, activitiesFiltered)` | 540 | 액티비티 배지 |
| `checkMissions(userId, activitiesFiltered)` | 572 | 미션 진행·보상 |

즉 이 임계값이 잘못되면 배지뿐 아니라 **드랍·미션까지 동시에 멈춘다.**

### 현재 운영값 (2026-08-31 13:00 KST 실측, 읽기 전용)

```
id=1, vehicle_speed_filter_kmh=60, gps_max_speed_kmh=300,
poi_block_hours=72, gps_daily_distance_cap_km=3000,
updated_at=2026-08-31T03:48:29Z   ← 행은 1건뿐
```

운영값이 60이므로 **현재 실피해는 없다.** 이번 작업은 예방 조치다.

## 상세 요구사항

### 서비스/코드베이스 관점

1. **`sync.ts`의 우회 조회를 제거하고 `getAbusingPolicy()`를 쓴다.**
   정규화·에러 로그·키 누락 관측·`id=1` 조건을 그대로 물려받는다.
2. **주입된 supabase 클라이언트를 유지한다.**
   `processFetchedActivities(supabase, ...)`는 클라이언트를 인자로 받는 구조이고
   테스트(`sync-drop-order.test.ts`)가 여기에 페이크를 주입한다. `getAbusingPolicy()`가
   내부에서 무조건 `createServiceClient()`를 부르면 이 주입이 끊긴다 —
   `getAbusingPolicy(client?)`로 **선택적 클라이언트 인자**를 받게 하고 sync.ts가 넘긴다.
   기존 호출부 4곳(어드민 페이지·정책 라우트·pickup 라우트·drop-engine)은 인자 없이 그대로 동작해야 한다.
3. **소비 지점에 degenerate 값 페일세이프를 둔다.**
   DB에서 읽은 값이 유한수가 아니거나 `<= 0`이면 `DEFAULT_POLICY.vehicle_speed_filter_kmh`로
   폴백하고 `console.error`로 남긴다. 하드코딩 리터럴 `60`은 제거한다(중복 상수 = 암묵적 등록 지점).
   폴백 방향은 **"핵심 루프를 살리는 쪽"** 이며, 그 이유를 주석으로 남긴다(패턴 9 규칙 6).
4. **어드민 라우트에 하한을 둔다.** `vehicle_speed_filter_kmh`에 최소값 20km/h를 강제하고,
   위반 시 400과 함께 [현상]→[원인]→[해결책] 3단계 한국어 메시지를 돌려준다.
   근거는 아래 "0을 어떻게 다룰 것인가" 참조.
5. **회귀 방지 테스트를 남긴다.** 최소한 "정책값 0이 60으로 둔갑하지 않는다"와
   "조회 실패 시 기본값 폴백 + 로그"를 덮는다.

### UI/UX 관점

- 어드민 차량 속도 필터 입력의 도움말 문구가 실제 영향 범위(드랍·미션 포함)와 하한을
  반영하도록 갱신한다. 현재 문구는 "배지 평가에서 제외"라 실제보다 좁게 설명한다.

## 구현 계획

### 0을 어떻게 다룰 것인가 — 판단과 근거

**결론: 0을 "필터 끄기"로 재해석하지 않는다. 어드민 라우트에서 하한(20km/h)으로 막는다.**

근거:

1. **0은 "끄기"가 아니라 "전면 차단"이다.**
   필터식은 `averageSpeedKmh <= vehicleSpeedFilterKmh`(이하만 통과)다. 0이면 평균속도가
   0보다 큰 모든 활동, 즉 **실질적으로 전부**가 탈락한다. 위 표대로 배지·드랍·미션이
   동시에 멈춘다. 운영자가 "끄기"를 의도하고 입력한 값이 정반대로 **서비스 핵심 루프
   전면 정지**를 일으킨다.
2. **이 필드에는 "끄기"가 이미 존재한다 — 값을 올리는 것이다.**
   상한 임계값이므로 999 같은 큰 값을 넣으면 사실상 무력화된다. 단조적 의미를 가진
   필드에 0만 특수 케이스로 뒤집으면(0 = 무한대) 규칙이 하나 더 늘고, 그 규칙은
   소비 지점 코드에만 존재하는 **암묵적 등록 지점**(패턴 6)이 된다.
3. **하한을 20km/h로 잡는 이유.**
   이 값은 "차량 탑승 판정 기준"이다. JAM!이 지원하는 활동은 걷기·하이킹·달리기·
   트레일러닝·사이클링(`STRAVA_TYPE_TO_JAM`)이고, 사이클링 평균속도는 통상 20~30km/h다.
   20km/h 미만으로 내리면 차량이 아니라 **정상 사이클링·달리기 카테고리를 통째로
   배제**하게 되어 "차량 필터"라는 필드의 정의 자체가 성립하지 않는다. 반대로 20 이상은
   전동킥보드·오토바이를 겨냥해 조이는 정당한 운영 여지로 남는다.
4. **오류 방향의 비대칭이 하한을 정당화한다.**
   하한이 너무 높으면 운영자는 **눈에 보이는 400 메시지**를 받고 즉시 인지한다(복구 쉬움).
   하한이 없으면 잘못된 값이 **아무 신호 없이** 핵심 루프를 정지시킨다. 직전 티켓
   20260831_1149에서 어뷰징 정책 저장이 18일간 무음으로 실패했던 전례를 보면, 무음
   고장은 며칠~수주간 발견되지 않는다. 따라서 보수적(높은) 하한이 옳다.

**선택하지 않은 대안**
- *(대안 A) sync.ts에서 0을 무한대로 해석* — 위 2·3번 이유로 기각. 정책 의미를 소비
  지점에 숨기게 되고, 어드민 화면의 0과 실제 동작이 여전히 어긋난다.
- *(대안 B) 라우트는 그대로 두고 소비 지점에서만 하한 클램프* — 기각. 저장은 되는데
  적용은 다른 값이 되는 현재 버그의 구조를 그대로 반복한다. 정책 검증은 저장 경로가 소유해야 한다.

**두 겹 방어의 역할 분담** (중복이 아니라 책임이 다르다)
- **라우트 = 정책 소유자.** 하한 20을 강제한다. 운영자에게 즉시 피드백한다.
- **소비 지점 = 페일세이프.** `<= 0`·비유한수만 막는다(하한 20을 재검사하지 않는다 —
  운영자가 의도적으로 넣은 값을 코드가 조용히 덮어쓰면 같은 종류의 불일치가 재발한다).
  DB 직접 수정이나 이 가드 이전에 저장된 값을 방어하는 마지막 그물이다.

### 사전 확인 사항 (핵심 루프 의존성 지도)

- `abusing_policy` 행 — `policy.ts`·`shadow-ban.ts`·`sync.ts`·정책 라우트·`AbusingClient` 확인 완료.
  이번 변경은 `shadow-ban.ts`가 쓰는 rate 키에는 손대지 않는다.
- `strava_activities` 행 — `activitiesFiltered`가 배지·드랍·미션 엔진으로 흘러가는 경로를
  확인 완료. **활동 스냅샷의 형태(`NormalizedActivity`)는 바꾸지 않고 임계값 출처만 교체**하므로
  `badge-engine`·`drop-engine`의 소비 방식에는 영향이 없다.

### 주의

- Supabase는 staging·프로덕션 **공용 단일 DB**다. 검증은 **값을 바꾸지 않는 방식**으로만 한다.
  이번 작업에는 DB 마이그레이션도 데이터 변경도 없다.
- `sync-drop-order.test.ts`는 이 작업 이전부터 **2건 상시 red**다(`findCompletableItemBooks`가
  내부에서 `createServiceClient()`를 부르는데 테스트 환경에 env가 없음 — 티켓 20260831_1149 기록).
  이번 변경이 이 실패를 **더 이르게 만들지 않아야** 한다. 즉 `getAbusingPolicy()`가 주입된
  클라이언트를 쓰게 해서 기존 페이크 스텁이 계속 통하게 한다.
