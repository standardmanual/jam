# [Service] 등급 배율 키맵의 배선 오류를 테스트가 못 잡는다

## 배경 / 문제 정의

티켓 20260831_1259가 `shadow-ban.ts`의 런타임 문자열 키 조합을 타입 맵으로 바꿨다.

```ts
const BAN_RATE_KEY: Record<Exclude<BanLevel,'none'>, Record<BadgeRarity, keyof AbusingPolicy>> = {
  soft: { common: 'soft_common_rate', rare: 'soft_rare_rate', epic: 'soft_epic_rate', mystic: 'soft_mystic_rate' },
  hard: { ... },
}
```

`tsc`는 **값이 `keyof AbusingPolicy`인지만** 검사한다. **어느 키를 가리키는지는 검사하지
않는다.** 즉 `soft.rare`를 `'soft_common_rate'`로, `hard.common`을 `'hard_epic_rate'`로
잘못 적어도 컴파일이 통과한다.

현재 운영 배율이 `1.0`과 `0.0` 두 값뿐이라 **같은 값끼리의 오배선은 기존 11케이스가 전부
통과한다.** 예컨대 `soft.common`(1.0) ↔ `soft.rare`(1.0)를 맞바꿔도 어떤 테스트도 red가 되지
않는다. 지금은 우연히 값이 겹쳐 안전한 것이고, 배율을 하나라도 조정하는 순간 오배선이
드랍 판정을 조용히 틀어놓는다.

이 맵은 어뷰징 차단이라는 **핵심 루프의 판정 지점**이고, 같은 종류의 무음 결함이 이미
18일간 지속된 이력이 있다(티켓 20260831_1149).

## 상세 요구사항

### 서비스/코드베이스 관점

- **"각 (밴 레벨, 등급) 조합이 자기 키를 읽는다"를 고정하는 테스트를 추가한다.**
  8개 배율 키에 **서로 다른 sentinel 값**을 넣은 정책 객체를 만들고(예: 0.11 ~ 0.88),
  `Math.random()`을 고정한 뒤 각 조합의 판정 결과가 자기 키의 값에서만 나오는지 검증한다.
  값이 겹치지 않으므로 어떤 오배선도 반드시 red가 된다.
- 케이스 수를 늘리기보다 **1케이스로 8조합을 모두 덮는 형태**가 낫다 (테이블 순회).
- 위치는 `jam-web/src/lib/abusing/__tests__/shadow-ban.test.ts`.
- `Math.random` 스텁은 기존 확률 롤 케이스가 쓰는 방식을 그대로 따른다.

### 함께 검토할 것 (같은 원인의 다른 얼굴)

- **`RATE_KEYS`(policy.ts)와 `BAN_RATE_KEY`(shadow-ban.ts)가 같은 8개 키를 각각 하드코딩한다.**
  등급이 추가되면 `BAN_RATE_KEY`는 `tsc`가 잡지만 `RATE_KEYS`는 누락돼도 조용히 통과하고,
  그 결과 **새 배율 키가 어드민의 0~1 범위 검증을 빠져나간다**
  (`api/admin/abusing/policy/route.ts`가 `RATE_KEYS`로 배율/임계값을 가른다).
  한쪽에서 다른 쪽을 파생시키는 게 옳지만 `policy.ts`가 `shadow-ban.ts`를 import하면 순환이
  되므로, 맵을 `abusing/rate-keys.ts` 같은 중립 모듈로 빼는 리팩터가 전제다.
  **이 티켓에서 같이 할지, 더 미룰지 먼저 판단하고 근거를 남긴다.**

### 범위 밖

- `DEFAULT_POLICY` 값 변경·DB 쓰기 없음.
- 등급 추가·개명은 이 티켓의 대상이 아니다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
1. `shadow-ban.test.ts`에 sentinel 배선 테스트 1케이스를 추가했다. 8개 배율 키
   (`soft_common_rate`~`hard_mystic_rate`)에 서로 다른 sentinel 값(0.11~0.88)을 넣은 정책을
   만들고, 8개 (밴레벨, 등급) 조합을 테이블로 순회하며 `Math.random`을 각 조합의 sentinel
   값 바로 위/아래로 고정해 그 조합이 정확히 자기 키의 값에서만 임계값을 읽는지 검증했다.
   기대값(조합→키)은 `BAN_RATE_KEY`를 재사용하지 않고 필드명을 테스트 파일에 직접 나열해,
   프로덕션 맵 자체가 잘못돼도 테스트가 항상 통과하는 순환 논리를 피했다.
2. **실효성 실증**: `rate-keys.ts`의 `BAN_RATE_KEY`에서 `soft.common`/`soft.rare` 키를
   일부러 맞바꿔(`'soft_rare_rate'` ↔ `'soft_common_rate'`) 테스트를 돌린 결과 sentinel
   케이스가 즉시 red가 됐다(원본 복원 후 재실행해 10/10 통과 재확인). 오배선 탐지가
   실제로 동작함을 확인했다.
3. **`RATE_KEYS`/`BAN_RATE_KEY` 중복 하드코딩**: 같은 티켓에서 통합하기로 판단했다. 근거 —
   ticket이 제시한 해법(중립 모듈 분리)이 순환 import를 실제로 피하는지 검토한 결과, 새 모듈
   `abusing/rate-keys.ts`가 `BAN_RATE_KEY`(구체 배선)를 소유하고 `RATE_KEYS`는 거기서
   `Object.values().flatMap()`으로 파생시키면 된다. `policy.ts → rate-keys.ts`는 값 import,
   `rate-keys.ts → policy.ts`는 `import type`(런타임에 완전히 소거)이라 순환이 생기지 않는다.
   `shadow-ban.ts`가 `rate-keys.ts`의 `BanLevel`을 참조할 필요가 없도록(순환 여지 제거)
   `RateBanLevel = 'soft' | 'hard'` 리터럴을 별도로 정의했다 — `BanLevel`(shadow-ban.ts)의
   `Exclude<BanLevel,'none'>`과 구조적으로 동일해 타입 검사는 그대로 유지된다.
   변경 비용이 낮고(파일 이동 수준) 근본 원인을 직접 없애므로 미루지 않았다.
   `policy.ts`는 `export { RATE_KEYS }`로 재노출해 `api/admin/abusing/policy/route.ts`의
   기존 import 경로(`from './policy'` / `@/lib/abusing/policy`)를 그대로 유지했다.
