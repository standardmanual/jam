# [Admin] 어뷰징 정책을 어드민에서 바꾸면 DEFAULT_POLICY 미러가 조용히 깨진다

## 배경 / 문제 정의

티켓 20260831_1259가 `jam-web/src/lib/abusing/policy.ts`의 `DEFAULT_POLICY`를
**`abusing_policy` id=1 행의 미러**로 정의했다. 폴백이 정책을 바꾸지 않게 하려는 불변식이다.
불변식을 지키는 장치로 코드 주석과 `SERVICE_OPERATIONS.md` §12-5에
**"DB 배율을 바꾸면 같은 티켓에서 `policy.ts`도 함께 바꾼다"** 를 명시했다.

문제는 **이 규칙이 "티켓" 경로만 가정한다**는 점이다. 배율을 바꾸는 가장 흔한 경로는 티켓이
아니라 **어드민 화면**이다 — 운영자가 `/admin/abusing`에서 슬라이더를 움직이고
`PUT /api/admin/abusing/policy`로 저장하면 DB만 바뀌고 `policy.ts`는 그대로 남는다.
문서에 적힌 규칙은 그 경로를 덮지 못한다.

불일치가 생기면 **정상 경로와 폴백 경로의 판정이 갈리고, 그 차이는 무음이다.** 이번 사고의
본질이 정확히 "규율이 문서에만 있고 코드에 붙어 있지 않았다"였다.

## 상세 요구사항

### 서비스/코드베이스 관점

- **저장 시점에 불일치를 감지해 신호를 남긴다.** `updateAbusingPolicy()` 성공 직후
  배율 8종(`RATE_KEYS`)을 `DEFAULT_POLICY`와 비교해 다르면 `console.warn` 1회.
  드랍마다가 아니라 **저장 시 1회**라 로그 노이즈가 없다.
  문구에 "어느 키가 얼마에서 얼마로 갈렸는지"와 "`policy.ts`를 같이 갱신해야 한다"를 담는다.
- **어드민 화면에 불일치 배너를 띄울지 함께 판단한다.** 로그는 보는 사람이 있어야 신호가 되고,
  이 규칙을 지켜야 하는 사람은 운영자다. 배너를 넣는다면:
  - 위치는 `/admin/abusing` 정책 섹션 상단
  - **어드민 UI는 shadcn/ui 표준을 따른다** (`components/ui`의 기존 컴포넌트 사용)
  - 문구는 `Specs/UX_WRITING_GUIDELINE.md`의 [현상] → [원인] → [해결책] 3단계
  - 운영자가 코드를 고칠 수는 없으므로 **"개발자에게 알려달라"는 행동 지시**가 맞다
- 배너를 넣지 않기로 하면 그 이유를 티켓에 남긴다 (로그만으로 충분하다고 볼 근거가 있는지).

### 범위 밖

- **DB 배율 값 자체를 바꾸지 않는다.** Epic 차단을 켤지는 여전히 별도 판단이다
  (마이그레이션 115 §5). Supabase는 staging·프로덕션 공용 단일 DB다.
- `DEFAULT_POLICY` 값 변경도 하지 않는다.

## 구현 계획

1. `updateAbusingPolicy()` 성공 경로에 배율 8종 대조 + `console.warn` 추가
2. 어드민 배너 도입 여부 판단, 도입 시 shadcn 컴포넌트로 구현 + UX 라이팅 검증
3. 단위 테스트 — 불일치 시 경고가 나가고, 일치 시 나가지 않는다
4. `npx tsc --noEmit` / `npm run lint` / `npx vitest run src/lib/abusing` / `npm run build`
5. **어드민은 staging 검증 대상이 아니다** — 실화면 확인은 프로덕션 배포 후

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- `policy.ts`에 `findPolicyRateMismatches(current)`를 추가했다. `RATE_KEYS` 8종을
  `DEFAULT_POLICY`와 비교해 갈린 항목을 `{ key, dbValue, codeValue }[]`로 돌려주는 순수
  함수라, 저장 경로(서버 로그)와 어드민 배너가 같은 검사 로직을 공유한다.
- `updateAbusingPolicy()`가 upsert 성공 직후 `getAbusingPolicy(supabase)`로 저장된 값을
  다시 읽어 `findPolicyRateMismatches`로 대조하고, 갈린 항목이 있으면 `console.warn` 1회로
  "어느 키가 DB=x, policy.ts=y로 갈렸는지"와 "policy.ts의 DEFAULT_POLICY도 같이 갱신하라"는
  행동 지시를 남긴다. 드랍마다가 아니라 저장 시 1회라 로그 노이즈가 없다.
- `PUT /api/admin/abusing/policy`(및 `GET`) 응답에 `mismatch` 필드를 추가해 저장 직후
  다시 읽은 값의 불일치 목록을 그대로 실어 보낸다.
- 어드민 배너를 도입했다 — `/admin/abusing` 정책 탭 상단에 shadcn `Alert`
  (`variant="destructive"`, `components/admin/ui/alert.tsx`, 기존 `badge-image`·
  `item-badges` 페이지와 동일 컴포넌트)로 불일치 항목과 값을 나열하고, 운영자가 코드를 고칠
  수 없으므로 "개발자에게 알려서 DEFAULT_POLICY를 같이 갱신해 달라"는 행동 지시로 마무리했다.
  최초 진입 시 값은 `page.tsx`(서버 컴포넌트)가 `findPolicyRateMismatches`로 계산해 props로
  내려주고, 저장 후에는 API 응답의 `mismatch` 필드로 갱신한다 — `DEFAULT_POLICY`를 클라이언트
  번들에 노출하지 않기 위해 비교는 항상 서버에서 하고 클라이언트는 결과(직렬화 가능한 배열)만
  받는다.
- 배너를 넣지 않는 대신 넣기로 판단한 근거: 이 규칙(같은 티켓에서 policy.ts도 함께 바꾼다)을
  지켜야 하는 사람은 운영자이고, 서버 로그만으로는 운영자가 보지 못한다. 배너는 정책 저장이
  일어날 때(그리고 페이지 진입 시)마다 자연히 노출되므로 별도 모니터링 없이 신호가 전달된다.

### 주요 의사결정 / 핵심 메모
- 불일치 검사는 "저장 직후 DB에서 다시 읽은 값"과 `DEFAULT_POLICY`를 비교한다(요청 patch가
  아니라). 이번에 건드리지 않은 키에 이미 존재하던 불일치도 저장할 때마다 다시 드러나야
  "규칙이 조용히 깨진 상태"가 계속 방치되지 않기 때문이다.
- `DEFAULT_POLICY`·`findPolicyRateMismatches`는 `policy.ts`(service_role 클라이언트를 만드는
  서버 전용 모듈)에만 존재한다. 클라이언트 컴포넌트(`AbusingClient.tsx`)가 이 값을 직접
  import하면 서버 전용 모듈이 클라이언트 번들에 딸려 들어갈 위험이 있어, 비교는 항상
  서버(`page.tsx`·API route)에서 수행하고 클라이언트는 계산된 배열만 props/응답으로 받는다.
