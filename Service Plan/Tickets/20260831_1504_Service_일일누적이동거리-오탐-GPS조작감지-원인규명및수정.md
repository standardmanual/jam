# [Service] 일일 누적 이동거리(GPS 조작 감지) 오탐 — 원인 규명 및 수정

## 배경 / 문제 정의

어드민 `/admin/abusing`에 현재 활성 상태로 떠 있는 섀도우밴 1건 + POI 블록 1건을 분석한 결과,
`user_shadow_bans`·`poi_blocks`·`abusing_logs` 전체 이력(7건)이 **전부 `sihyunrr@gmail.com`
(username `jamfather`, `is_admin: false`) 계정 하나**에서만 발생했다. 실제 외부 유저 어뷰징
사례는 아직 없다.

이 중 앞선 6건은 이미 원인이 규명·수정됐다:

| 시점 | 사유 | 원인 | 처리 |
|---|---|---|---|
| 2026-07-25 10:52~11:18 (5건) | 속도 943→906→669→592→383km/h, 거의 동일 좌표 반복 | GPS 재수신 시 좌표 튐 + 최소 경과시간 가드 부재 | 티켓 20260813_002, `MIN_ELAPSED_SECONDS=5초` 가드 추가로 해결 |
| 2026-08-12 12:32 (1건) | 속도 43km/h (도보 수준인데도 차단) | DB `gps_max_speed_kmh`가 300이 아니라 30으로 잘못 설정 | 같은 티켓, 마이그레이션 081로 300 복구 |

**이번 티켓의 대상은 남은 2건**이며, 성격이 다르다 — 순간 속도가 아니라 **하루 누적 이동거리
캡(`policy.gps_daily_distance_cap_km`, 기본 3000km)** 초과로 판정됐다.

| 시점(UTC) | 사유 | 이때 순간 속도 |
|---|---|---|
| 2026-08-28 14:18:30 | `일일 누적 이동거리 초과 (7173km/일)` | 19km/h (도보 수준, 정상) |
| 2026-08-31 05:35:18 | `일일 누적 이동거리 초과 (7219km/일)` — **현재 어드민에 활성 상태로 노출 중** | 192km/h |

두 건 다 속도 자체는 임계값(300km/h) 미만이라 텔레포트형 조작으로 보기 어렵다.
`jam-web/src/lib/abusing/gps-detector.ts`의 `checkAndUpdateLocation()`은
`dailyDistanceKm += distKm`로 위치 갱신마다 무조건 누적하는데, `MIN_ELAPSED_SECONDS=5초`
가드는 **짧은 간격의 GPS 노이즈만** 걸러낸다. 하루 동안 앱을 여러 번 열고 닫거나 실내·고층
밀집 지역에서 GPS가 반복적으로 100~300m씩(`MIN_DISTANCE_KM=0.15km` 이상) 튀는 상황이
5초 이상 간격을 두고 여러 번 발생하면, 실제 순 이동거리는 얼마 안 되는데도 누적치만
계속 쌓여 하루 수천km까지 부풀 수 있다 — **가설이며 이 티켓에서 실제로 검증해야 한다.**

참고 `abusing_logs` 원본(jam-prod, 이 세션에서 실측):
```json
// 2026-08-28 14:18:30
{"reason":"daily_distance","speed_kmh":19,"daily_distance_km":7173,"poi_id":"62551b70-7860-42b9-8286-3f95a17978b1"}
// 2026-08-31 05:35:18
{"reason":"daily_distance","speed_kmh":192,"daily_distance_km":7219,"poi_id":"204db6bd-b8e6-40c7-83ad-3698a7a536af"}
```

## 상세 요구사항

### 서비스/코드베이스 관점

1. **원인 검증 (구현 전 필수)** — 위 가설(GPS 노이즈 누적)이 실제 원인인지 코드·데이터로
   확인한다. 다음 대안 원인도 함께 배제하거나 확인한다:
   - UTC 날짜 리셋 타이밍 문제 (`todayStr`가 UTC 기준이라 KST 자정 전후로 하루치가
     이중 집계되거나 리셋 타이밍이 사용자 체감과 어긋나는지)
   - 여러 기기/세션에서 `last_location_*` 경쟁 갱신 (동시에 여러 요청이 들어와 각자
     다른 `last_location`을 기준으로 거리를 계산하면서 중복 누적되는지)
   - 실제 GPS 좌표 자체의 정밀도/드리프트 문제
   - 결론(어느 원인이 실제로 맞았는지, 배제한 원인은 왜 아니라고 판단했는지)을
     완료 기록에 반드시 남긴다.
2. **수정 구현** — 검증된 원인에 맞춰 판단한다. 후보:
   - 누적 로직에 GPS 노이즈 필터링 추가 (예: 매우 짧은 시간 내 반복되는 소규모 이동은
     누적에서 제외, 또는 순간 속도가 비현실적이지 않은 이동만 누적)
   - `gps_daily_distance_cap_km` 캡 자체를 실측 기반으로 재검토
   - 날짜 리셋 로직 수정 (원인으로 확인될 경우)
   - **오탐 방지가 목적이지, 실제 조작을 놓치는 방향으로 완화해서는 안 된다** — 007/008/002
     티켓에서 반복된 "오탐 수정이 탐지 자체를 무력화"하는 패턴을 재현하지 않는다.
3. **폴백/로그 규율** — 이번 사고 조사가 `abusing_logs`·`user_shadow_bans`·`poi_blocks`를
   직접 substring 없이 SQL로 읽어서 가능했다. 수정 후에도 판정 근거(순간속도·누적거리·좌표)가
   로그에 남도록 유지한다.

### 활성 밴/블록 처리

현재 `sihyunrr@gmail.com` 계정에 걸린 소프트밴 1건(`user_shadow_bans`, 만료 9/3) + POI 블록
1건(`poi_blocks`, poi_id `204db6bd-b8e6-40c7-83ad-3698a7a536af`, 해제 9/3)은 **원인 검증
결과 오탐으로 결론 나면 해제한다.** 실제 조작으로 확인되면 유지하고 그 근거를 완료 기록에 남긴다.
DB 쓰기(해제)는 jam-developer 권한 밖이므로 — CLAUDE.md 규칙상 SQL만 작성하고 실행은
오케스트레이터가 사용자 승인 하에 진행한다.
