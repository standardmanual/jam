# [Service] 프로필 통계탭 레드-온-레드 대비 버그 + 뒤로가기 알림 정책

## 배경 / 문제 정의

티켓 `20260831_2038`에서 프로필 딥링크(알림에서 특정 탭이 초기 선택된 상태로 진입)의 탭
텍스트 대비 문제를 고쳤으나, 사용자가 화면 녹화로 **다른 케이스**의 잔여 문제를 재현했다.
이번 티켓은 그 후속이다.

**원인 조사 결과 (조사 완료, 코드 수정 없음)**:

### 1. 통계탭(배지/컬렉션/팔로워/팔로잉) 클릭 전환 시 레드-온-레드 대비 소실
사용자가 화면 녹화에서 상단 통계 바(`SlidingTabs variant="onCard"`)를 직접 손으로 클릭해
전환하는 동안, 활성 pill(레드 배경)이 목표 탭 위치로 이동하는 순간 그 위 숫자가 흰색이
아니라 오렌지/레드 계열로 잠깐 표시되는 프레임을 확인했다(프레임 캡처로 재현 확인됨).

- `20260831_2038`에서 고친 것은 **딥링크 최초 진입**(`moveTo(key, animate=false)`) 시
  pill과 텍스트 전환 시점이 어긋나는 문제였다. 이번 건은 **사용자가 직접 탭을 클릭하는
  경우**(`animate=true`)에서 발생하며 원인이 다르다.
- pill과 `.t-tab` 텍스트 color의 transition duration/easing은 동일하다
  (`--tabs-dur: 300ms`, `--tabs-ease`, `transitions.css:148,170-171`) — 타이밍 값 차이로 인한
  버그가 아니다.
- 진짜 원인: `ProfileClient.tsx:408-434`에서 통계 숫자(예: "30")는 `.t-tab`의 공용 색
  transition 메커니즘을 타지 않고, `isActive` 여부로 `text-[color:var(--tabs-text-active)]`
  (흰색) ↔ `text-[color:var(--color-primary)]`(레드)를 즉시 스왑하는 별도 className을 쓴다.
  그런데 **비활성(muted) 숫자 색(`--color-primary`, 레드)과 pill 배경색
  (`--tabs-pill-bg: var(--color-primary)`, 동일한 레드)이 완전히 같다.** pill은 순간이동이
  아니라 300ms 동안 탭 바 위를 물리적으로 슬라이드하므로, 클릭한 탭이 인접하지 않으면
  (예: "팔로잉"→"배지") pill이 경유하는 다른 탭들("팔로워"·"컬렉션")의 숫자 위를 실제로
  지나간다. 경유하는 탭은 활성화된 게 아니므로 숫자가 계속 muted 레드 상태라 "레드 pill이
  레드 숫자를 스치는" 프레임이 필연적으로 생긴다. 탭 간 이동 거리가 멀수록(배지↔팔로잉)
  노출 빈도·시간이 커진다.
- 라벨("배지" 등 캡션 텍스트)은 `--tabs-text-muted`(검정 40%)를 써서 pill과 겹쳐도 대비가
  유지되므로 이 문제가 없다. 숫자만 별도로 강조색(레드)을 강제하고 있어 문제가 생긴다.

### 2. 알림에서 진입한 프로필 페이지에서 `<` 버튼이 알림으로 안 돌아감
- `TopNav`의 `<` 버튼(`TopNav.tsx:77`)은 `backHref`/`onBack` prop이 없으면 순수
  `router.back()`이다. `/[username]`(다른 유저 프로필) 호출부(`ProfileClient.tsx:444`
  `<TopNav title="" showBack />`)는 둘 다 넘기지 않는다.
- `ProfileClient.tsx:209-211`의 `handleTabClick`이 탭을 클릭할 때마다
  `window.location.hash = tab`을 실행하는데, 이는 `history.pushState`와 동등하게 동작해
  **탭을 누를 때마다 브라우저 히스토리에 새 엔트리가 쌓인다**(주석엔 "뒤로가기 지원"이라고
  의도가 적혀 있으나, 그 의도된 동작 자체가 이번 문제의 원인이다).
- 결과: 알림함에서 진입해 탭을 몇 번 눌렀다면, `<`(`router.back()`)는 그 탭 히스토리를
  하나씩 되짚어갈 뿐이라 사용자 체감상 "통계탭 이동처럼" 동작하고, 알림 페이지로 돌아가려면
  탭을 누른 횟수 + 1번을 더 눌러야 한다.
- **"알림에서 왔다"는 정보를 프로필 페이지가 구분할 방법이 현재 전혀 없다** — 코드베이스
  전체에 `document.referrer`·`sessionStorage` 사용처 0건, 쿼리 파라미터로 출처를 넘기는
  기존 패턴도 없다. 유일하게 존재하는 "출처 인지" 패턴은 `TopNav`의 `backHref` prop을
  호출부가 정적으로(하드코딩) 넘기는 방식뿐이다(예: `[username]/followers/page.tsx:77`
  `backHref={`/${username}`}`) — `/[username]`처럼 여러 경로(알림/검색/팔로워목록/직접
  URL)에서 올 수 있는 라우트에는 이 정적 패턴이 안 맞아 동적 구분 메커니즘을 새로 만들어야
  한다.
- 알림함→프로필 이동은 전부 표준 `<Link href>`(`NotificationsClient.tsx`,
  `src/lib/notifications/href.ts`의 `notificationTarget()`이 목적지 계산)이고, 이 링크에
  쿼리 파라미터를 추가하는 방식이 가장 자연스럽다.

## 상세 요구사항

### 서비스/코드베이스 관점

**1. 레드-온-레드 대비 해결**
- 목표: pill이 경유하는 동안에도 그 순간 덮인 탭의 숫자가 항상 읽혀야 한다(대비 확보).
- 구현 방법은 여러 후보가 있으니 판단해 적용한다(택일 또는 조합):
  - (a) pill이 현재 덮고 있는 탭을 실시간으로 계산해, 그 탭의 숫자에도 임시로 활성 색(흰색)을
    적용한다 — 가장 정확하지만 구현 복잡도 있음.
  - (b) 숫자의 muted 색상을 pill 배경색(`--color-primary`)과 겹치지 않는 색(예: 라벨과
    동일한 `--tabs-text-muted` 계열)으로 바꾼다 — 간단하지만 "비활성 상태에서도 숫자가
    항상 레드로 강조되는" 기존 시각 언어가 프로필 통계 탭에서만 사라짐. 다른 화면(예: 프로필
    최상단 요약 등)에서 통계 숫자가 항상 레드로 보이는 기존 패턴과의 일관성을 함께 검토한다.
  - (c) pill의 이동 애니메이션 자체를 슬라이드가 아니라 사라짐/나타남(fade)으로 바꾼다 —
    "SlidingTabs"라는 컴포넌트 정체성과 다른 화면(하단 필터 탭 등)의 모션 일관성에 영향을
    줄 수 있어 신중히 판단.
  - 최종 선택은 구현 시점에 판단하되, **다른 SlidingTabs 사용처(하단 필터 탭 등, `variant`
    다름)에는 영향을 주지 않는 범위**로 한정한다(onCard variant 국소 수정 우선 검토).

**2. 알림 진입 시 `<` 버튼이 알림 페이지로 직행**
- `src/lib/notifications/href.ts`의 `notificationTarget()`이 프로필로 연결하는 링크(단건
  `followed`, `following_rare_badge`, `following_collection_complete` 등)에 출처를 알리는
  쿼리 파라미터(예: `?from=notifications`)를 추가한다.
- `ProfileClient.tsx`가 `useSearchParams()`로 이 파라미터를 읽어, 있으면 `TopNav`에
  `backHref="/notifications"`를 조건부로 전달한다. 없으면(검색·팔로워 목록·직접 URL 접근 등
  기존 경로) 기존 `router.back()` 동작을 그대로 유지한다.
- 알림 외 다른 진입 경로(검색·팔로워/팔로잉 목록 등)까지 이 정책을 확장할지는 이번 범위가
  아니다 — "알림에서 온 경우"에 한정한다.

### UI/UX 관점 (해당 시)
- 1번 수정 후 통계탭 간 먼 거리 전환(예: 배지↔팔로잉)을 여러 차례 반복 클릭해 레드-온-레드
  프레임이 재현되지 않는지 확인한다.
- 2번 수정 후 알림함에서 프로필로 진입 → 통계탭을 여러 번 전환 → `<` 클릭 시 한 번에
  알림 페이지로 돌아가는지 확인한다. 알림이 아닌 경로(예: 검색)로 진입했을 때는 기존처럼
  `router.back()`이 정상 동작하는지(회귀 없는지)도 함께 확인한다.
