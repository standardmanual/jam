# [UI] 액티비티 배지 스킬트리 화면 신규

## 배경 / 문제 정의

액티비티 배지(걷기/러닝/사이클링/등산/트레일러닝, 종목당 8속성×4등급=총 40종×4=160개)는 서로 선행조건(OR)
으로 묶여 있고, 종목별 대표배지 5종(동네 산책러/첫 숨결/언덕의 도전자/첫 고도/야생의 주자)은 미션 완료로만
상위 등급이 열린다. 현재 `/badges` 화면은 평면 그리드로만 배지를 나열해 이 구조(무엇을 먼저 얻어야
다음이 열리는지)가 전혀 보이지 않는다.

직전 세션에서 이 구조를 게임 스킬트리 형태로 시각화한 **정적 프리뷰 HTML**(로컬 스크래치패드, 서비스 코드
아님)을 만들어 사용자가 검토했고, 실제 서비스 화면으로 반영해달라는 요청을 받았다. 프리뷰는 SVG 방사형
레이아웃 + 검색 기능이 있었으나, 실제 서비스 반영본은 아래 요구사항에 따라 레이아웃을 종스크롤 형태로
재설계하고 검색은 제외한다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 신규 라우트 `/badges/tree` (App Router 정적 세그먼트 — `/badges/[id]`보다 우선 매칭되므로 충돌 없음)
  - `jam-web/src/app/(main)/badges/page.tsx` 패턴을 따라 **서버 컴포넌트에서 Supabase를 직접 조회**한다.
    API route를 새로 만들지 않는다 (기존 배지 목록/상세 페이지도 API route 없이 서버 컴포넌트 직접 조회).
  - **정적 스냅샷 금지** — 빌드 타임에 굳지 않고 요청 시점 DB 상태를 그대로 반영해야 한다 (요구사항 7).
    `badges/page.tsx`가 캐싱을 어떻게 처리하는지(`export const dynamic`, revalidate 여부 등) 먼저 확인하고
    동일한 방식을 따른다 — 이 저장소의 Next.js는 표준과 다르므로(`jam-web/AGENTS.md`) 임의로 판단하지 말고
    `node_modules/next/dist/docs/`에서 캐싱 관련 가이드를 확인한 뒤 적용한다.
  - 조회 대상: `badges` 테이블 `type='activity' AND deleted_at IS NULL AND activity_types IS NOT NULL`,
    필요 컬럼은 `id, name, rarity, description, image_url, activity_types, condition_json, point_reward`.
  - `condition_json.mission_reward = true`인 행(레벨업/Hard/Ultra 미션보상배지, 15종)은 트리 노드로
    직접 그리지 않고, 종목 대표배지 5종의 등급 승급 게이트 표시에만 사용한다.
  - **미션 상세 링크는 배지 이름 매칭이 아니라 `missions.gated_badge_id`로 조인한다.**
    `condition_json.prerequisite_badge_names`에는 미션보상배지 "이름"만 있고 미션 id가 없다. 반드시
    `missions` 테이블에서 `gated_badge_id = <해당 등급(rare/epic/mystic) 배지의 badges.id>`인 행을 찾아
    그 미션의 `id`로 `/missions/{id}` 링크를 만든다.
    **(오케스트레이터가 SQL로 실측 확인 완료, 2026-08-31)** `gated_badge_id`는 정확히 "이 미션 완료 시
    승급되는 그 등급 배지"의 id를 1:1로 가리킨다 — 15개 레벨업 미션 전부 대상 배지의 rare/epic/mystic
    행과 정확히 하나씩 매칭됨 (예: 미션 "동네 산책러 레벨업" → `동네 산책러` Rare 행의 id,
    "동네 산책러 레벨업 Hard" → Epic 행의 id, "동네 산책러 레벨업 Ultra" → Mystic 행의 id — 5종목 ×
    3단계 = 15건 전부 확인). 따라서 구현 시 `missions` 테이블을 `gated_badge_id`로 미리 맵으로 만들어
    두면(`Map<badgeId, missionId>`), 종목 대표배지의 rare/epic/mystic 카드마다 그 카드 자신의
    `badges.id`로 바로 조회해 잠금 칩을 만들 수 있다 — 이름 매칭이나 레벨업 배지 테이블 별도 조회가
    필요 없다. `visibility.ts` 확인은 "잠금/숨김 배지 표시 정책"(다른 요구사항)까지 참고하고 싶을 때만
    추가로 보면 된다.
  - 종목 대표배지가 아닌 나머지 배지(각 종목 7개)의 Rare 이상 선행조건은 기존 방식대로
    `condition_json.prerequisite_badge_names`(동일 종목 내 배지 이름)로 판단하고, 해당 배지의
    Common 등급 `badges.id`로 `/badges/{id}` 링크를 만든다 (이름→id는 같은 조회 결과 안에서 매핑).
  - **배지 자신의 상세 페이지 링크**: 트리에 그려지는 모든 배지 카드(각 등급 포함)는
    `/badges/{해당 등급 badges.id}`로 이동 가능해야 한다 (요구사항 4).

### UI/UX 관점

- **레이아웃 — 종스크롤 전용, 횡스크롤 금지** (요구사항 8). 종목 전환은 상단 탭(`SlidingTabs` — 이미
  `BadgesClient.tsx`에서 쓰는 서비스 컴포넌트 재사용, 5개 탭은 모바일 폭에서 가로 스크롤 없이 들어가는지
  실제로 확인할 것 — 안 들어가면 줄바꿈 없는 탭 자체의 가로 스크롤은 이 요구사항의 "화면 전체 횡스크롤
  지양"과는 다른 문제이므로 허용되지만, 우선 폭에 맞는지부터 확인).
- **"먼저 얻어야 하는 배지 → 그다음 배지들" 순서를 세로로 명확히 표현** (요구사항 6). 그래프를 2D로
  그리지 않고, 종목 대표배지를 루트로 한 **선행조건 그래프의 BFS 깊이**로 세로 단계를 나눈다:
  - 1단계: 종목 대표배지 (예: 걷기="동네 산책러")
  - 2단계: `prerequisite_badge_names`에 대표배지가 직접 포함된 배지들
  - 3단계: 2단계 배지 중 하나를 선행조건으로 가진 나머지 배지들
  - (OR 그래프라 한 배지가 여러 깊이 후보를 가질 수 있으면 **최단 깊이**를 채택. 동일 깊이 내 정렬은
    종목별 속성 순서(문서 `Service Plan/Specs/Content/ACTIVITY_BADGES.md`의 W1~W8 등 번호 순)를 따른다)
  - 각 단계는 세로로 쌓인 섹션으로 표시하고, 단계 사이에 세로 커넥터(화살표/연결선)를 넣어 "이 배지들을
    얻어야 다음 단계가 열린다"는 게 스크롤만으로 읽힌다.
  - 각 배지 섹션 내부에는 Common→Rare→Legend→Mythic 4단계 미니 카드(현재 조건값·설명·이미지)를 세로로
    쌓고, Rare 이상 카드에는 선행조건이 배지면 "🔒 {배지명} 보유 필요" 칩(클릭 시 `/badges/{id}`), 미션
    게이팅이면 "🔒 미션 {미션명} 완료 필요" 칩(클릭 시 `/missions/{id}`)을 붙인다.
- **컴포넌트 재사용 판정 (1.5단계, 오케스트레이터 확정)**:
  - 배지 개별 카드: **`src/components/ui/BadgeGridCard.tsx`를 그대로 재사용** (MODULAR
    `design-system/components/patterns/BadgeGridCard.jsx`가 아니라 이 서비스 구현을 기준으로 삼을 것 —
    `highlighted` prop 등 서비스판에만 있는 기능이 있어 두 구현이 완전히 동기화돼 있지 않음). 그리드가
    아니라 세로 리스트에 배치하는 형태로 wrapping만 새로 만든다.
  - 종목 탭: **`SlidingTabs`(서비스 `src/components/ui/`) 재사용**, `BadgesClient.tsx`와 동일 패턴.
  - rarity 표시: **`@ds/components/cards/RarityBadge` 재사용** (BadgeGridCard 내부에서 이미 사용 중이라
    별도 작업 불필요).
  - **신규(서비스 전용, MODULAR 승격 대상 아님)**: 단계 구분 세로 커넥터/화살표, 선행조건·미션 게이팅
    잠금 칩(🔒 배지/미션 링크), 종목 대표배지 강조 표시(⚡ 등). 아직 이 화면 하나에서만 쓰이는 실험적
    UI라 `/jam-design` 판정 기준(2개 이상 화면에서 재사용)을 충족하지 못함 — `src/components/badges/`
    하위에 서비스 전용으로 구현한다.
- **접근성 (WCAG 2.2 AA)**: 잠금 칩·배지 카드 등 모든 탭 가능한 요소는 터치 타겟 44×44px 이상, 포커스
  링 가시성 확보, rarity를 색상만으로 구분하지 말고 텍스트 라벨(Common/Rare/Legend/Mythic) 병기(이미
  `RarityBadge`가 라벨을 렌더링하므로 그대로 쓰면 충족됨).
- 사용자 노출 텍스트는 `Service Plan/Specs/UX_WRITING_GUIDELINE.md` 준수 (해요체, 고정 용어).

## 구현 계획

1. Supabase에서 최신 `badges`(activity, 15 미션보상 포함)·`missions`(gated_badge_id 있는 행) 실측
   조회로 조건값·이미지가 직전 세션 조사 시점과 달라졌는지 먼저 확인 (요구사항 1 — "조건값이 변경됐다"는
   전제가 실제로 어떻게 바뀌었는지 구현 중 diff로 확인해도 됨, 별도 사전 조사 불필요. 서버 컴포넌트가 항상
   최신값을 읽으므로 자동으로 반영됨).
2. `/badges/tree` 서버 컴포넌트: 배지·미션 조회 → BFS 깊이 계산 → 종목별 단계별 배지 리스트를 클라이언트
   컴포넌트에 props로 전달.
3. 클라이언트 컴포넌트: `SlidingTabs`로 종목 전환, 선택 종목의 단계별 세로 리스트 렌더링. 각 배지는
   `BadgeGridCard` 기반으로 4등급 미니 카드 스택 + 잠금 칩.
4. `BadgesClient.tsx` 타이틀 줄에 진입 버�튼 추가.
5. `gated_badge_id` 조인 로직은 실제 데이터로 검증(예: "동네 산책러" Rare의 id가 "동네 산책러 레벨업"
   미션의 `gated_badge_id`와 일치하는지 SQL로 직접 확인 후 구현).

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- `/badges/tree` 신규 라우트(정적 세그먼트, `/badges/[id]`와 충돌 없음 — `next build` 라우트 표에서
  두 경로가 별도로 등록됨을 확인). 서버 컴포넌트가 `badges`(type=activity, deleted_at is null,
  activity_types not null)와 `missions`(gated_badge_id not null)를 요청마다 직접 조회한다.
  `supabase.auth.getUser()`(쿠키 기반) 호출로 `badges/page.tsx`와 동일하게 자동 동적 렌더링되어
  정적 스냅샷이 아니다(별도 `dynamic`/`revalidate` 설정 불필요 — 기존 페이지도 동일 패턴).
- `src/lib/badgeTree.ts`: 배지를 이름 기준 family로 묶고, `missions.gated_badge_id`가 가리키는
  등급으로 종목 대표배지 5종을 **하드코딩 없이** 판정한 뒤, family 간 `prerequisite_badge_names`
  간선을 BFS로 순회해 단계(depth)를 계산한다. D01~D11·트로피 매트릭스(걷기 32종, 선행조건 없음)
  는 BFS로 도달하지 않아 "선행 조건 없이 얻는 배지" 섹션으로 분리했다(아래 alerts 참고).
- 각 배지 카드의 잠금 칩은 Rare 이상 등급 자신의 id로 `missions` 맵을 직접 조회해 미션
  게이팅인지, 아니면 `prerequisite_badge_names`(다른 배지, OR)인지 구분한다 — 이름 매칭이나
  레벨업 배지 별도 조회 없이 처리(티켓 지시대로).
- UI: `SlidingTabs`(종목 전환, 5개 탭)+`BadgeGridCard`(등급별 미니 카드, 재사용) 세로 스택.
  단계 사이 세로 커넥터, 대표배지 강조(TargetIcon), 잠금 칩(LockIcon)은
  `src/components/badges/` 하위 서비스 전용 신규 컴포넌트.
- `/badges` 타이틀 줄 우측에 "배지 트리" 버튼 추가(요구사항 9).
- 잠금 칩 문구는 기존 `missions.lockedHint`("{badge} {rarity} 배지를 획득하면 열려요")와 동일한
  "~하면 열려요"(고정 용어: 잠김/열려요) 패턴을 새 i18n 키로 확장해 재사용.

### 주요 의사결정 / 핵심 메모
- **종목 대표배지 판정을 이름 하드코딩 대신 `missions.gated_badge_id` 역참조로 구현.** 티켓이
  예시로 든 5개 이름(동네 산책러 등)과 결과가 정확히 일치함을 확인했지만, 코드는 이름을
  전혀 참조하지 않는다 — 나중에 대표배지 구성이 바뀌어도 자동으로 반영된다(요구사항 7).
- **D01~D11(누적 걷기 일수)·트로피 매트릭스(T01~T23, 걷기 전용 32종, `Specs/Content/
  ACTIVITY_BADGES.md`에 "선행 배지: 없음(전부 독립 발급)"로 명시)를 별도 "선행 조건 없이 얻는
  배지" 섹션으로 분리했다.** 티켓 배경 문단은 "종목당 8속성×4등급" 구조만 언급하지만, 티켓의
  조회 스펙(`type='activity' AND activity_types IS NOT NULL`)은 이 32종도 문자 그대로 포함한다.
  이 배지들은 선행조건이 전혀 없어 BFS로 대표배지에서 도달할 수 없고, 그레이드가 1개뿐이라
  "Common→Mystic 4단계 카드 스택" 모델에도 맞지 않는다 — 억지로 특정 단계에 끼워 넣지 않고
  분리된 섹션으로 노출해 요구사항 4(모든 카드가 상세로 링크)만 만족시켰다. 아래 alerts에 WARN으로
  남긴다.
- **선행조건 OR가 2개면 잠금 칩도 2개(각각 독립 클릭 가능)로 렌더링.** 문장 중간에 배지명을
  인라인 링크로 넣는 방식도 검토했으나, 인라인 텍스트는 44×44px 터치 타겟을 보장할 수 없어
  (WCAG 요구사항, 요구사항 상세 참고) 기각했다.
- **동일 단계 내 정렬은 `ACTIVITY_BADGES.md`의 W1~W8 등 번호 순서를 코드에 하드코딩.** DB에는
  이 순서를 나타내는 컬럼이 없고(같은 마이그레이션 배치로 삽입된 행은 created_at이 전부 동일
  타임스탬프라 원래 삽입 순서를 신뢰할 수 없음을 실측 확인), 조건값 자체는 전부 라이브
  DB 조회이므로 "정적 스냅샷 금지"(요구사항 7)를 어기지 않는다고 판단했다.
- **BadgeGridCard를 그리드가 아니라 [카드]+[설명/잠금칩] 가로 행으로 배치.** 티켓이 명시한
  "Common→Rare→Legend→Mystic 4단계 미니 카드를 세로로 쌓고"를 그대로 따르되, `BadgeGridCard`
  내부 구조는 손대지 않고 `className="w-[110px] shrink-0"`으로 폭만 제한해 wrapping했다.
- **point_reward는 조회 컬럼에는 포함했으나(티켓 필요 컬럼 목록에 명시) 화면에는 표시하지
  않았다.** 요구사항 6이 명시한 미니 카드 표시 내용은 "조건값·설명·이미지" 3가지뿐이라
  포인트 텍스트를 추가하면 스펙에 없는 정보 추가가 될 수 있다고 판단했다.
