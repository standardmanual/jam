# [UI] 배지 메뉴 액티비티 탭 — 미획득 배지 비노출

## 배경 / 문제 정의

`/badges/tree`(티켓 20260831_2208·2250, 20260901_0809)가 "어떤 배지를 어떤 순서로, 무엇을
해야 얻는지" 보여주는 화면을 전담하게 됐다. 그런데 `/badges`의 액티비티 탭은 여전히 미획득
배지까지 흑백/반투명으로 그리드에 노출하고 있어(`BadgesClient.tsx:166-179`,
`sortedActivityBadges`가 `earned`+`unearned`를 이어붙임), 두 화면이 같은 정보(무엇을 아직
못 얻었는지)를 서로 다른 방식으로 중복 노출한다. 사용자 요청: 배지 트리가 이 역할을
넘겨받았으니 액티비티 탭은 **획득한 배지만** 보여주도록 바꾼다.

**이미 확립된 선례가 있다** — 같은 화면의 체크인 탭이 정확히 이 정책을 쓰고 있다
(`BadgesClient.tsx:134-137` 주석: "획득한 것만 보여준다 — 미획득 배지는 노출하지 않음",
`page.tsx:50-56` 주석: "전체 checkin 타입 배지는 1,800개가 넘어... 애초에 '획득한 것만'
보여주면 되므로 전체 조회 자체를 하지 않는 방식으로 근본 해결"). 액티비티 탭도 이 패턴을
그대로 따라가면 된다.

## 상세 요구사항

### 서비스/코드베이스 관점

- `jam-web/src/app/(main)/badges/page.tsx`: `allActivityBadges` 전체 조회(27~44행,
  `badges` 테이블 `type='activity'` 전체)를 없애고, 이미 조회 중인 `earnedBadges`
  (`user_activity_badges.*, badge:badges(*)`, `earned_at` 내림차순)만으로 `badges` prop을
  구성한다 — 체크인 탭이 이미 쓰는 "획득분만 조회"와 동일한 방식. 소프트 삭제 배지 제외
  필터(`!r.badge.deleted_at`)는 그대로 유지.
  - `earnedMap`은 더 이상 필요 없다(전체 카탈로그와의 매칭 목적이었으므로) — 제거하거나,
    `BadgeRow`+`earned_at`을 바로 매핑하는 형태로 단순화한다.
  - `BadgesClientProps.badges`의 타입(`Array<{ badge: BadgeRow; earned: UserActivityBadgeRow |
    null }>`)은 유지해도 되고(항상 `earned`가 non-null이 되는 셈), 이번 기회에
    `Array<{ badge: BadgeRow; earned: UserActivityBadgeRow }>`로 좁혀도 된다 — 어느 쪽이든
    `BadgeGridCard`의 `earned` prop은 항상 `true`가 되므로 흑백 처리 코드 경로 자체가
    이 탭에서는 더 이상 실행되지 않는다(그대로 둬도 무해하지만, 정리하면 더 명확하다).
- `jam-web/src/app/(main)/badges/BadgesClient.tsx`:
  - `sortedActivityBadges`(163~179행)에서 `unearned` 분리·정렬·병합 로직 제거 — 입력이
    이미 전부 획득분이므로 획득일 내림차순 정렬만 남는다(또는 서버가 이미 `earned_at desc`로
    정렬해 오므로 클라이언트 정렬 자체를 없애도 된다 — 서버 정렬 순서를 신뢰할지 확인 후 결정).
  - `earnedCount`(124행)는 이제 `badges.length`와 같아진다 — 탭 라벨 카운트 배지가 여전히
    올바르게 "보유 개수"를 보여주는지 확인.
  - 필터 드롭다운(종목·등급, 220~240행)은 고정 상수(`ACTIVITY_TYPE_ORDER`/`RARITY_ORDER`)
    기반이라 손댈 필요 없음 — 획득분이 하나도 없는 종목/등급을 선택하면 자연스럽게 빈 결과
    (`EmptyState`)가 뜨는 기존 동작 그대로 유지.
  - 빈 상태 문구(`d.badges.emptyActivityTitle`/`emptyActivityBody`)가 "아직 배지가 없어요"
    류라면 그대로 재사용 가능한지 확인 — "전체 배지를 못 봐서 아쉽다"는 오해가 없는 문구인지
    UX Writing 가이드 기준으로 점검(필요 시만 수정, 억지로 새 문구 만들지 않음).

### 컨텐츠/UX 관점

- 이 변경으로 "액티비티 배지가 몇 종 있는지, 어떻게 얻는지"를 확인하는 경로는 `/badges/tree`
  하나로 일원화된다. `/badges` 액티비티 탭 우측 상단의 "배지 트리" 진입 버튼(이미 존재,
  `BadgesClient.tsx:195-200`)이 그 경로이므로 별도 안내 문구 추가는 불필요.
- 체크인 탭·아이템배지(컬렉션) 탭은 이번 범위 밖 — 건드리지 않는다.

## 구현 계획

1. `page.tsx`에서 `allActivityBadges` 조회 제거, `earnedBadges` 쿼리 결과로 `badges` prop 직접 구성.
2. `BadgesClient.tsx`의 `sortedActivityBadges`를 획득분 전용으로 단순화, `earnedCount` 계산 정리.
3. 빈 상태 문구가 여전히 자연스러운지 확인(필요하면 UX Writing 가이드에 맞춰 손질).
4. 로컬에서 이 유저가 일부만 획득한 상태로 액티비티 탭에 미획득 배지가 전혀 안 뜨는지,
   필터가 여전히 정상 동작하는지, 탭 카운트 숫자가 맞는지 확인.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
`page.tsx`에서 `badges` 테이블 전체 조회(`allActivityBadges`)를 제거하고, 이미 조회 중이던
`earnedBadges`(`user_activity_badges.*, badge:badges(*)`, `earned_at desc`) 결과만으로
`badges` prop을 구성했다 — 체크인 탭이 쓰던 "획득분만 조회" 패턴을 그대로 적용. `earnedMap`
(카탈로그 매칭용)은 더 이상 필요 없어 제거했고, `BadgesClientProps.badges`의 `earned` 타입도
`UserActivityBadgeRow | null` → `UserActivityBadgeRow`로 좁혔다.

`BadgesClient.tsx`의 `sortedActivityBadges`(획득/미획득 분리·병합 정렬)를 제거하고 서버가
이미 `earned_at desc`로 정렬해 오는 `badges`를 그대로 필터링만 하도록 단순화했다. 미획득
정렬에만 쓰이던 `activitySortIndex`·`RARITY_RANK`도 함께 제거(미사용 lint 오류 방지).
`earnedCount`는 `badges.length`로 단순화(이제 badges가 획득분만 담기 때문).

빈 상태 문구(`d.badges.emptyActivityTitle`: "아직 획득한 배지가 없어요", `emptyActivityBody`:
"Strava를 동기화하고 활동하면 배지를 획득할 수 있어요")는 이미 "획득한 것만" 기준으로 쓰여
있어 오해 소지가 없다고 판단, 수정하지 않음. 필터 드롭다운(종목·등급)·체크인 탭·아이템배지
탭은 손대지 않음.
