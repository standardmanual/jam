# [UI] 프로필 통계탭 숫자 — 포인트 강조색 적용

## 배경 / 문제 정의

사용자가 프로필 화면 스크린샷과 함께 "통계탭(배지/컬렉션/팔로워/팔로잉) 숫자가 포인트
강조색(위쪽 "5,000 포인트"와 같은 `--color-primary` 레드)이어야 한다"고 요청했다.

현재는 어제(2026-08-31) 티켓 `20260831_2201`에서 의도적으로 회색(`--tabs-text-muted`)으로
바꾼 상태였다 — 활성 pill(레드) 배경이 300ms 슬라이드 애니메이션 중 다른 탭 위를 지나가는데,
그 탭의 숫자가 pill과 같은 레드면 "레드 위에 레드"로 대비가 사라지는 버그가 화면 녹화로
확인됐기 때문이다.

사용자에게 두 방식(간단한 절충 vs 정확한 해결) 중 선택을 물었고, **"정확한 해결"**을
선택했다 — 평소엔 항상 강조색(레드)을 쓰되, pill이 실제로 그 숫자 위를 지나가는 애니메이션
프레임에서만 일시적으로 흰색으로 바꿔 버그를 재발 없이 해결하는 방식.

## 상세 요구사항

### 서비스/코드베이스 관점

1. **실시간 pill 겹침 추적** (`jam-web/src/components/ui/SlidingTabs.tsx`)
   - `moveTo(key, animate=true)` 호출 시(사용자가 직접 탭을 클릭하는 애니메이션 전환)
     `requestAnimationFrame` 루프를 돌며 pill의 `getBoundingClientRect()`와 각 탭 버튼의
     rect를 비교해 실질적으로 겹치는(겹침 폭이 탭 폭의 30% 초과) 탭에 `data-pill-over="true"`
     속성을 붙인다.
   - 전환 시간(`--tabs-dur: 300ms`) + 여유 버퍼(350ms) 후 자동으로 추적을 멈추고 속성을 지운다.
   - `prefers-reduced-motion`이면 애초에 pill이 순간이동해 경유 프레임이 없으므로 추적 자체를
     시작하지 않는다.
   - 이 속성을 읽는 CSS가 기본으로 전혀 없어(각 사용처가 필요할 때만 스코프 클래스로 추가)
     다른 `SlidingTabs` 사용처(하단 필터 탭 등)는 전혀 영향받지 않는다.

2. **프로필 통계탭 색상 규칙** (`transitions.css`의 `.jam-stat-tabs` 스코프,
   `ProfileClient.tsx`)
   - 숫자는 기본적으로 `--color-primary`(포인트와 동일한 강조색).
   - `aria-selected="true"`(도착해 머문 활성 탭) 또는 `data-pill-over="true"`(pill이 지금
     이 순간 지나가는 탭) 상태에서만 `--tabs-text-active`(흰색, pill 배경 위에서 대비 확보).
   - `ProfileClient.tsx`의 `isActive` 삼항 로직을 제거하고 고정 클래스(`jam-stat-number`)로
     교체 — 색상 분기는 전부 CSS가 DOM 속성을 보고 처리.

### UI/UX 관점

- 정지 상태(선택된 탭 없음, 프로필 기본뷰): 4개 숫자 전부 강조색(레드) — 요청한 스크린샷과
  동일한 모습.
- 탭 클릭 후: 클릭된 탭의 숫자만 흰색(pill 배경 위), 나머지는 강조색 유지.
- 탭 간 애니메이션 전환 중: pill이 지나가는 순간의 탭 숫자만 일시적으로 흰색, 그 외엔 강조색
  유지 — 레드온레드 프레임 없음.

## 구현 계획

1. `SlidingTabs.tsx`에 `trackOverlap`/`stopOverlapTracking` 추가, `moveTo`의 animate 분기에
   연결.
2. `transitions.css`에 `.jam-stat-tabs` 스코프 규칙 추가.
3. `ProfileClient.tsx`의 통계 숫자 렌더링을 `jam-stat-number` 고정 클래스로 단순화,
   `SlidingTabs`에 `className="jam-stat-tabs"` 전달.
4. 로컬에서 정지 상태·활성 탭 색상을 스크린샷으로 확인.

### 구현 내용 요약
계획대로 구현. 초기 자체 검증에서 `getComputedStyle()`을 이용한 JS 자동화 스크립트가 계속
잘못된(오래된) 색상값을 보고해 한동안 원인을 오인했으나(수동으로 규칙을 지워도 값이 안 바뀜),
실제 스크린샷으로 확인한 결과 **CSS 자체는 처음부터 정상 동작**하고 있었다 — 이 세션의
브라우저 자동화 도구가 `getComputedStyle` 값을 신뢰할 수 없게 캐싱하는 것으로 보인다(실제
페인트와 무관). 이후 스크린샷 기반으로만 검증했다.

### 주요 의사결정 / 핵심 메모
- 사용자에게 "간단한 절충(버그 재발 위험 감수)" vs "정확한 해결(구현 복잡도 있음)" 중 선택을
  물었고 "정확한 해결"을 명시적으로 선택받았다 — 임의로 더 쉬운 쪽을 고르지 않음.
  (참고: 처음엔 "간단한 절충"이 선택됐으나 사용자가 "다시 질문해줘"라고 요청해 재확인한
  결과 "정확한 해결"로 최종 확정됨.)
- 겹침 판정 임계값(탭 폭의 30%)은 pill이 스치기만 하는 경계 프레임을 노이즈로 걸러내기 위한
  값이다 — 더 낮추면 과민 반응(거의 안 겹쳐도 흰색), 더 높이면 실제로 덮인 순간을 놓칠 수
  있어 중간값을 택했다. 실측 튜닝은 아직 안 했다(위 잔여 이슈 참고).
- `SlidingTabs.tsx`는 공유 컴포넌트지만, `data-pill-over` 속성 부여 자체는 항상 실행되고
  이를 스타일링하는 CSS는 `.jam-stat-tabs` 스코프에만 있어 다른 사용처에 영향이 없다 —
  20260831_2201의 "절대 건드리면 안 되는 것"(다른 SlidingTabs 사용처)을 준수했다.
