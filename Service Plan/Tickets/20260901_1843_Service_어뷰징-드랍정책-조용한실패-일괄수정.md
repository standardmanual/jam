## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

1. **`combine/policy.ts`** — `updateCombinePolicy`가 upsert `error`를 확인하지 않아 저장 실패가
   "성공"으로 응답됐다. `drop-engine/policy.ts`의 `updateDropPolicy` 패턴을 그대로 따라 error를
   확인해 로그 후 예외를 던지도록 수정. `getCombinePolicy`의 select 실패도 무음 폴백이라 로그를
   추가(폴백 방향은 유지 — 믹스 기능이 죽으면 안 됨). `app/api/admin/combine-policy/route.ts`의
   PUT을 try/catch로 감싸 500 + 사유를 응답하도록 수정(기존 `drop-policy`·`abusing/policy` 라우트와
   동일 패턴).
2. **`drop-engine/index.ts`** — `saveDropState`(스트릭·pity·일일 카운터 저장)가 upsert `error`를
   버려 상태 저장 실패가 무음이었다. error 확인 후 로그·예외로 수정. 호출부(`tryItemDrop`)는 이미
   배지가 지급된 뒤 이 함수를 부르므로, 던진 예외는 `strava/sync.ts`의 활동 단위 try/catch(기존에
   이미 있던 "배치 중 한 건 실패해도 나머지는 계속" 가드)가 로깅 후 흡수한다. 같은 함수 바로 아래
   있던 `last_activity_at 불일치` 가드 주석이 정확히 이 시나리오("최신 활동의 드랍 실패, 위
   try/catch로 흡수된 경우")를 이미 전제하고 있어 기존 설계와 정합적이다. `getDropState`의 조회
   실패도 로그를 추가(폴백 방향은 유지 — 조회 실패를 신규 유저와 구분하지 않으면 상태가 무음으로
   리셋되므로 최소한 로그는 남긴다).
3. **`poi/search-cache.ts`** — `shouldSearch`/`markSearched`가 error를 버렸다. 캐시 계층이라
   실패해도 최악은 "네이버 API 재호출"뿐이라 fail-open 방향은 유지하되 로그를 추가. 상위
   호출부(`refreshPoisInBackground`)가 이미 백그라운드 실패를 통째로 흡수하는 설계라 throw는
   불필요.
4. **`abusing/poi-block.ts`** — `isPoiBlocked`(모든 픽업 요청마다 호출)는 fail-open을 유지하되
   로그를 추가(`getUserBanLevel`의 DB 전체 장애 시 fail-open과 같은 근거 — 전체 유저의 픽업을
   막는 것이 더 위험). `blockPoiForUser`/`unblockPoi`는 error를 확인해 로그·예외로 수정.
5. **`abusing/shadow-ban.ts`**:
   - `applyBan`/`removeBan` — upsert/delete `error`를 버려 밴 부여·해제 실패가 "적용/해제됨"으로
     응답됐다. error 확인 후 로그·예외로 수정.
   - `logAbusingEvent` — `catch {}`로 완전히 무음이었다. 예외는 던지지 않되(부가 로그가 핵심
     동작을 막으면 안 됨) `console.error`를 추가.
   - `getUserBanLevel()` — DB `ban_level`을 검증 없이 `as BanLevel`로 캐스팅하던 지점에 방어
     코드 추가. `'soft'`/`'hard'`가 아닌 값이면 fail-closed로 `'hard'`로 취급하고 로그를 남긴다
     (밴 레코드 자체는 존재하므로 "이미 제재 대상으로 확인된 유저"라는 전제 하에 어뷰징 판정
     fail-closed 원칙 적용, 20260831_1259 §5). 함수 자체가 통째로 실패했을 때의 기존
     fail-open(`catch` → `'none'`)은 그대로 뒀다 — 20260831_1259가 "DB 전체 장애 시 영향 없음"으로
     이미 검증해 둔 설계라 이 티켓에서 다시 바꿀 근거가 없다.
6. **호출부 정합성**:
   - `app/api/admin/abusing/bans/route.ts`(POST/DELETE), `app/api/admin/abusing/poi-blocks/route.ts`
     (DELETE) — 이제 던지는 `applyBan`/`removeBan`/`unblockPoi`를 try/catch로 감싸 500 + 사유를
     응답하도록 수정(기존 `abusing/policy`·`drop-policy` 라우트와 동일 패턴).
   - `app/api/drops/[dropId]/pickup/route.ts` — GPS 스푸핑 감지 시 `applyBan`·`blockPoiForUser`·
     `logAbusingEvent`를 `Promise.all`로 부르던 지점을 try/catch로 감쌌다. 제재 기록이 실패해도
     이번 픽업 응답(`location_unverified` 403)은 그대로 유지하되(스푸핑은 이미 감지됐으므로 이
     요청의 판정을 바꿀 이유가 없음), 제재가 실제로 안 걸렸을 수 있다는 신호는 반드시 로그로
     남긴다.
   - `app/admin/abusing/AbusingClient.tsx` — 단건 `removeBan`/`removePoiBlock`에 `!res.ok`일 때
     서버가 보낸 오류 사유를 그대로 노출하는 else 분기를 추가(기존에는 실패해도 화면에 아무
     신호가 없었다). 일괄 해제(`bulkRemoveBans`/`bulkRemovePoiBlocks`)는 이미 실패 카운트를
     보여주고 있어 손대지 않았다.

### 주요 의사결정 / 핵심 메모

- **fail-open을 유지한 지점과 fail-closed로 바꾼 지점을 명확히 구분했다** (20260831_1259 §5의
  "어뷰징 판정은 fail-closed가 기본"을 기계적으로 전부 적용하지 않았다):
  - fail-open 유지 + 로그만 추가: `isPoiBlocked`(모든 픽업 요청마다 호출 — fail-closed면 DB
    일시 장애가 전체 픽업 정지로 번짐), `shouldSearch`/`markSearched`(캐시 계층, 최악이
    "API 재호출"뿐), `getUserBanLevel`의 최외곽 catch(DB 전체 장애 — 20260831_1259가 이미
    "영향 없음"으로 검증해 둔 설계).
  - fail-closed로 신규 결정: `getUserBanLevel`의 `ban_level` 값 캐스팅 방어만 — 이 분기는
    "밴 레코드는 있는데 레벨 값이 이상한" 경우로, 이미 제재 대상 확인된 유저에게만 닿아 정상
    유저에게 영향이 없다(`shouldAllowDrop`의 기존 미지-등급 fail-closed와 동일 근거 구조).
  - throw로 전환(어드민 직접 조작 경로): `updateCombinePolicy`·`applyBan`·`removeBan`·
    `blockPoiForUser`·`unblockPoi` — 전부 어드민이 명시적으로 요청한 단일 쓰기이므로 실패를
    호출부가 알아야 재시도·수동 개입이 가능하다. `drop-engine/policy.ts`(`updateDropPolicy`)·
    `abusing/policy.ts`(`updateAbusingPolicy`)가 이미 확립한 패턴을 그대로 복제했다.
  - throw로 전환하되 자동 경로에 흡수 장치를 새로 마련: `saveDropState`(→ `strava/sync.ts`의
    기존 활동 단위 try/catch), `blockPoiForUser`/`applyBan`(→ `pickup/route.ts`에 새로 추가한
    try/catch, 픽업 거부 응답은 유지).
- **`logAbusingEvent`는 끝까지 던지지 않기로 결정**했다 — 부가 로그(어뷰징 이벤트 기록) 실패가
  핵심 동작(밴 적용·GPS 감지·픽업 거부)을 막으면 안 된다는 원칙. 대신 `catch {}`였던 것을
  `console.error`로 바꿔 "무음"만 없앴다.
- **`getAbusingPolicy()`/`getDropPolicy()`처럼 이미 error 체크가 있던 함수는 손대지 않았다** —
  이 티켓이 지목한 5개 지점 + 관련 호출부만 범위로 삼았다.

### 잔여 이슈
- **로컬 환경의 `jam-web/.env.local`이 자기 자신을 가리키는 깨진 심볼릭 링크였다**

  임시로 추가해 테스트를 실행한 뒤(전부 통과) 원상복구해 커밋에는 포함하지 않았다. **다음
  세션에서 이 워크스페이스로 테스트를 돌릴 때 같은 문제가 재발하면 `/jam-sync`로 심볼릭 링크를
  다시 연결해야 한다.**
- `strava/sync.ts:458`의 truthy 검사 버그 등 20260831_1259가 "범위 밖"으로 남긴 다른 항목은

  `getUserBanLevel()`로 범위가 명시돼 있었다).
