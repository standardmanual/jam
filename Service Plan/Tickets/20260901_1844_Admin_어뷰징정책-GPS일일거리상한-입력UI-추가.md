## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- `/admin/abusing` 정책 탭의 "GPS 조작 감지" 섹션에 `gps_daily_distance_cap_km` 입력 필드를
  추가했다. 기존 `gps_max_speed_kmh`·`vehicle_speed_filter_kmh`·`poi_block_hours`와 동일한
  숫자 입력 패턴(number input + 단위 라벨)을 그대로 따랐고, 순간 속도 임계값 바로 다음 위치에
  배치했다(둘 다 `gps-detector.ts`의 같은 GPS 조작 감지 로직이 소비하는 값이라 논리적으로
  묶었다 — `vehicle_speed_filter_kmh`는 별도 목적(차량 활동 배제)이라 그 뒤에 유지).
- 저장 API(`api/admin/abusing/policy/route.ts`) 화이트리스트는 `Object.keys(DEFAULT_POLICY)`를
  순회하는 구조라 `gps_daily_distance_cap_km`이 `AbusingPolicy`/`DEFAULT_POLICY`(`policy.ts`)에
  이미 존재하는 이상 별도 코드 변경 없이 이미 포함돼 있었다(확인만 하고 코드는 수정하지 않음).
  `RATE_KEYS`(0~1 상한 검증 대상)에도 포함돼 있지 않아 0 이상 정수 검증만 적용된다 — 의도한 대로.

### 주요 의사결정 / 핵심 메모
- API 화이트리스트는 코드 변경 없이 이미 충족돼 있음을 확인했다. `Object.keys(DEFAULT_POLICY)`
  기반 순회 구조 덕분에 `policy.ts`에 필드가 있으면 어드민 저장 API는 자동으로 그 필드를
  받아들인다 — 티켓 요구사항인 "화이트리스트 포함 확인"은 검증 완료로 처리하고 별도 수정은
  하지 않았다(스펙에 없는 변경 방지).
- 필드 배치는 "GPS 조작 감지" 섹션 내 `gps_max_speed_kmh` 바로 다음으로 정했다 — 두 값 모두
  `gps-detector.ts`의 같은 판정 함수(순간 속도 → 하루 누적 거리 순서)가 순차로 검사하는 값이라
  코드 흐름과 화면 순서를 맞췄다.
