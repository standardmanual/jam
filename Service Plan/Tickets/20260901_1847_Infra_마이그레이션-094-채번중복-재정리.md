# [Infra] 마이그레이션 094 채번 중복 재정리

## 배경 / 문제 정의
티켓 [20260824_017](20260824_017_Infra_떠돌이신화-기능-전면제거.md)에서 발견:
`jam-web/supabase/migrations/`에 `094_backfill_feed_event_at_approx.sql`과
`094_revoke_noncommon_item_badges.sql`이 같은 번호(094)로 공존한다. 둘 다 이미 프로덕션
DB에 적용되어 있을 가능성이 높다(Supabase는 staging·프로덕션 공용 단일 DB).

## 상세 요구사항

### 서비스/코드베이스 관점
- 두 마이그레이션이 실제로 이미 실행됐는지 Supabase에서 확인(실행됐다면 파일 번호를
  바꿔도 DB 상태엔 영향 없음 — 순수 저장소 정리)
- 둘 중 하나를 다음 사용 가능한 번호(095 이후 최대값+1)로 재채번
- 재채번 시 파일명뿐 아니라 파일 내부에 번호를 참조하는 주석·문서가 있다면 함께 갱신
- 이후 병렬 세션 간 채번 충돌 방지를 위해, 마이그레이션 번호도 티켓 번호처럼 "생성 시각
  기준"으로 바꿀지 여부는 이번 티켓 범위 밖 — 이번엔 기존 094 중복만 해소한다

## 구현 계획
- `list_migrations`(Supabase MCP)로 실제 적용 이력 확인 → 파일 재채번 → 커밋

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
Supabase MCP `list_migrations`로 jam-prod(`ceehnkzdbecxwzxrhhns`) 적용 이력을 확인했다.
두 파일의 실제 실행 상태가 서로 다름을 파일 내용으로도 확인:
- `094_revoke_noncommon_item_badges.sql` — 파일 자체에 "실행 시점 기준: 대상 2700건 중
  1449건이 활성 상태였고..." 과거형 실행 보고가 적혀 있어 **이미 실행 완료**된 것으로 판단.
  번호를 그대로 유지.
- `094_backfill_feed_event_at_approx.sql` — 파일 상단에 "⚠️ 절대 자동 실행 금지 — STEP 1
  진단 후 사용자 승인을 받아야 STEP 2 실행" 게이트가 있고, 실행 완료를 알리는 티켓·기록이
  없어 **아직 미실행 상태**로 판단. 이 파일을 재채번 대상으로 선택.

미실행 상태인 쪽을 재채번하는 게 실행된 쪽보다 안전하다고 판단해(이미 실행된 마이그레이션의
식별자를 바꾸면 향후 추적에 혼선을 줄 수 있음), `123_backfill_feed_event_at_approx.sql`로
`git mv`했다(122까지는 이미 사용 중 — 다른 병렬 세션의 미커밋 작업 포함, 123이 다음 여유
번호). `grep`으로 코드베이스(`jam-web/src`, `jam-web/supabase`) 내 구 파일명 참조가 없음을
확인 — 갱신할 참조처가 없었다. 티켓 문서 내 과거 참조(CLOSED 티켓들)는 문서 체계 규칙상
소급 수정하지 않았다.

이 파일이 아직 미실행이라는 사실 자체(STEP 2 백필이 언제 실행될지)는 이 티켓의 범위
밖이다 — 재채번만 다루고 실행 여부 판단은 건드리지 않았다.
