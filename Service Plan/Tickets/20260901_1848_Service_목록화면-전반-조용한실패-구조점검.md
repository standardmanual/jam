# [Service] 목록성 화면 전반 Supabase 조회 조용한 실패 구조 점검·수정

## 배경 / 문제 정의
티켓 [20260824_017](20260824_017_Infra_떠돌이신화-기능-전면제거.md)에서 지적된 구조적
이슈: `badges/page.tsx`를 포함해 서비스 전반이 Supabase 쿼리의 `error`를 무시하고
`data ?? []`로 폴백한다. DB 오류가 "빈 목록"으로 위장돼 무증상 장애가 된다. 티켓
[20260901_1843](20260901_1843_Service_어뷰징-드랍정책-조용한실패-일괄수정.md)이 어뷰징·
드랍정책 영역을 다루는 것과 별개로, 이 티켓은 목록성 화면(배지 목록, 아이템북 목록,
프로필 컬렉션 등) 전반을 대상으로 한다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `grep -rn "?? \[\]"` 등으로 목록성 API 라우트·서버 컴포넌트 전수 조사해 대상 지점 목록화
- 각 지점에서 "빈 목록"과 "조회 실패"를 구분할 수 있도록 최소한의 에러 로깅 추가
  (사용자 화면까지 에러 UI를 새로 설계하는 것은 과도할 수 있으니, 우선 서버 로그·모니터링
  관점의 가시성 확보를 우선순위로 하고 화면단 처리는 지점별 위험도에 따라 판단)
- 범위가 넓으므로 지점 수가 많으면 우선순위(사용자 노출 빈도·오탐 시 파급력)로 정렬해
  진행하고, 다 못 끝내면 잔여 지점을 "잔여 이슈"에 남긴다

## 구현 계획
- 전수 조사 → 지점별 위험도 분류 → 상위 위험군부터 에러 가시성 확보
- 이번 티켓에서 UX(에러 화면 디자인)까지 바꾸지 않는다 — 서버 로그 레벨의 가시성 확보가
  1차 목표

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
`grep -rn "?? \[\]"` + 스크립트(`const { data... } = await supabase|service` 패턴 정적 분석)로
목록성 API 라우트·서버 컴포넌트를 전수 조사했다. 실제 Supabase 쿼리 결과를 `error` 체크 없이
`data ?? []`(또는 `.single()`/`.maybeSingle()` 후 `!data`만으로 404 처리)로 폴백하는 지점이
150곳 이상 확인됐다 — 티켓 20260824_017이 지적한 `badges/page.tsx`뿐 아니라 서비스 전반의
구조적 패턴이었다.

사용자 노출 빈도(홈·배지목록·프로필·아이템북 컬렉션·팔로워/팔로잉·피드·미션·드랍맵·인벤토리·
검색·조합 등 매 방문마다 실행되는 화면)와 오탐 시 파급력(조회 실패가 "완전히 빈 화면"·
"근거 없는 404"·"팔로잉 0명" 등 오해를 부르는 특정 빈 상태로 위장되는 지점)을 기준으로
상위 위험군부터 최소한의 `console.error` 로깅을 추가했다. 화면 동작(폴백 값·표시 문구)은
전혀 바꾸지 않았다 — 이번 티켓은 서버 로그 가시성 확보만이 목표.

우선순위 상위로 처리한 영역:
1. 티켓 20260824_017의 원 사례인 `badges/[id]/page.tsx`, `badges/page.tsx` — 배지 상세·목록
2. 홈(`(main)/page.tsx`), 피드(`feed/page.tsx`), 프로필(`[username]/page.tsx`) — 방문 빈도 최상위
3. 아이템북 컬렉션(`collections/[id]/page.tsx`, `[username]/collections/page.tsx`,
   `api/users/[username]/itembooks/route.ts`) — 티켓에 명시된 예시
4. 미션 목록(`missions/page.tsx`), 배지 트리(`badges/tree/page.tsx`)
5. 팔로워/팔로잉(서버 컴포넌트 + API 라우트 양쪽)
6. 드랍맵 핵심 쿼리(`api/drops/route.ts`의 T1 POI 조회 — 실패 시 "이 근처엔 지점 없음"으로
   위장되는 가장 파급력 큰 지점 중 하나), `api/drops/[dropId]/route.ts`,
   `api/drops/poi/[poiId]/route.ts`
7. 인벤토리(`inventory/page.tsx`, `api/inventory/items/route.ts`,
   `api/inventory/items/[itemId]/history/route.ts`), 조합(`combine/page.tsx`), 검색(`search/page.tsx`),
   체크인 배지 지도(`api/checkin-badges/route.ts`)

`.single()`/`.maybeSingle()`을 쓰는 조회는 실패 시 `!data`만으로 `notFound()`/404를 반환하는
지점이 많았다 — 이 경우 실제 DB 오류가 "그 유저/아이템/컬렉션이 존재하지 않음"으로 완전히
다른 원인으로 위장된다. 이런 지점은 `if (error) console.error(...)`를 `!data` 체크 직전에
추가해 로그로만 구분되게 했다(응답 자체는 기존과 동일하게 404 유지 — UX 변경 아님).

### 주요 의사결정 / 핵심 메모
> 개발 과정에서 검토·결정된 사항, 선택하지 않은 대안과 그 이유.

- **공용 로깅 헬퍼를 새로 만들지 않았다.** 코드베이스에 이미 `if (xError) console.error('[컨텍스트]
  설명:', xError)` 인라인 패턴이 광범위하게 쓰이고 있어(`src/lib/drop-engine/index.ts`,
  `src/lib/itembook/checker.ts` 등) 그 관례를 그대로 따랐다. 추상화 레이어 추가는 스펙 밖 리팩터링.
- **`.single()`/`.maybeSingle()` 뒤 `!data`로 404 처리하는 패턴 자체는 고치지 않았다** — "행 없음"과
  "조회 실패"를 코드에서 구분하려면 `error.code === 'PGRST116'` 판정이 필요한데, 이는 화면 응답을
  바꾸는 로직 변경이라 이번 티켓 범위(로그 가시성만) 밖으로 판단했다. 로그만 남기고 응답은 그대로 뒀다.
- **정적 분석 스크립트로 전수 조사했다** — `const { data: X, error: Y } = await supabase|service`
  패턴과 `error` 키가 아예 없는 단일 `data` 구조분해를 정규식으로 찾아 파일:라인 목록을 뽑고,
  이후 각 지점의 실제 사용 맥락(빈 배열 폴백인지/single 후 404인지/단순 표시값인지)을 읽어
  위험도를 판단했다. grep만으로는 150곳 이상이 나와 전수 확인이 비현실적이었다.
- **admin 화면은 이번 우선순위에서 제외했다** — 사용자 노출 빈도가 낮고(운영자 전용, 스테이징
  검증도 불가), 티켓 배경에 명시된 예시(배지 목록·아이템북 목록·프로필 컬렉션)가 모두 유저단
  화면이라 유저단을 먼저 처리했다. 잔여 이슈에 남긴다.

### 잔여 이슈
정적 분석으로 확인했으나 이번 라운드에서 처리하지 못한 지점 — 후속 티켓에서 우선순위 재판단 필요.

**유저단(우선순위 중) — 조회 실패해도 "완전히 빈 화면"까지는 아니고 일부 표시값만 어긋나는 지점**
- `src/app/api/points/route.ts` — 배지/미션 이름 조회 실패 시 일반 사유 라벨로 자동 폴백(완전
  빈 화면 아님, 표시만 다소 부정확해짐)
- `src/app/api/missions/[id]/status/route.ts`, `src/app/api/missions/[id]/join/route.ts`
- `src/app/api/badges/[id]/share-data/route.ts` — 공유 카드 생성용
- `src/app/(main)/profile/page.tsx`, `profile/edit/page.tsx`, `onboarding/page.tsx`,
  `notifications/NotificationsClient.tsx`, `voc/page.tsx`
- `src/app/(main)/drops/DropsClient.tsx`, `combine/CombineClient.tsx` 등 클라이언트 컴포넌트의
  `fetch` 실패 처리(서버 라우트가 아니라 브라우저 측 — 별도 관점의 점검 필요)

**API인데 현재 프론트엔드에서 호출하는 곳을 찾지 못한 지점** (외부/모바일 클라이언트용일 수 있어

**어드민 화면 전반** (`src/app/admin/**`) — 배지·아이템북·POI·세계관·유저·포인트·미션·리사이클·
