# [UI] MODULAR 5종 컴포넌트 API 분화 — 서비스 기준으로 재정렬

## 배경 / 문제 정의

`/jam-ds` 첫 정리(티켓 20260901_1854)에서 `ds:check` 의 `PROPS_DRIFT` 로 드러났다.
서비스 UI 가 계속 발전하는 동안 MODULAR 쪽 구현이 따라오지 못해, 같은 이름의 컴포넌트가
**서로 다른 API** 를 갖게 됐다.

| 컴포넌트 | 서비스에만 있는 props | MODULAR 타입에만 |
|---|---|---|
| BottomSheet | `onClose` `detent` `footer` `topGapPx` `footerBottomInset` `contentScrollable` | `onDismiss` |
| SlidingTabs | `items` `variant` `size` `shape` `block` `outlined` `tabClassName` | `tabs` `active` |
| TopNav | `backHref` `headerStyle` `logo` | `logoSlot` `centerSlot` `avatarSlot` `titleSize` `titleWeight` `titleLineHeight` `titleTracking` |
| TabBar | `username` | `active` |
| BadgeGridCard | `highlighted` | — |

특히 `BottomSheet` 는 콜백 이름부터 다르고(`onClose` ↔ `onDismiss`), `SlidingTabs` 는
데이터 prop 이름과 변형 체계가 통째로 다르다. **Storybook 카탈로그를 보고 재사용을 판단하면
실제 서비스 컴포넌트와 맞지 않는 API 를 기대하게 된다** — `/jam-design` 의 "탐색 → 재사용"
선순환이 깨지는 지점이다.

## 상세 요구사항

### 서비스/코드베이스 관점

- **기준은 서비스 UI** (`src/components/ui/*.tsx`). MODULAR 을 여기 맞춘다
  (기준값 방향은 `/jam-ds` 스킬 0절 참조)
- `.d.ts` 만 고치면 타입과 구현이 어긋나 더 나빠진다. **`.jsx` 구현까지 함께** 바꾼다
- 컴포넌트를 바꾸면 대응 `*.stories.tsx` 도 새 API 로 갱신한다

### 검증

- `cd jam-web && npm run ds:check` 의 `PROPS_DRIFT` 가 해당 컴포넌트에서 사라질 것
- Storybook(`npm run storybook`, :6006)에서 각 Story 가 실제로 렌더될 것
  — 20260901_1854 에서는 `node_modules` 가 없어 이 검증을 못 했다

## 구현 계획

컴포넌트당 독립적이므로 **하나씩 끊어서** 처리한다. 한 번에 5개를 바꾸면 회귀 범위가 커진다.
분화 폭이 큰 순서로:

1. `SlidingTabs` — 데이터 prop·변형 체계 전면 재정렬
2. `TopNav` — 슬롯 방식(`*Slot`) ↔ 서비스 방식(`logo`/`backHref`) 중 서비스 기준 채택
3. `BottomSheet` — `onDismiss` → `onClose`, detent·footer 관련 props 추가
4. `TabBar` — `username` 추가, `active` 는 서비스가 pathname 으로 판단하는지 확인
5. `BadgeGridCard` — `highlighted` 추가

각 단계마다 Story 갱신 + `ds:check` 재실행.
