# [Feature] GA4 연동 및 핵심 여정 커스텀 이벤트 계측

## 배경 / 문제 정의
현재 JAM!에는 방문자·사용자 행동을 정량적으로 파악할 수단이 없다. PRD에 정의된 핵심
사용자 시나리오(가입→온보딩→Strava 동기화→첫 배지, 홈 재방문, 드랍/픽업, 컬렉션/믹스/미션)가
실제로 어느 단계에서 이탈하는지 알 수 없어 개선 우선순위를 데이터 기반으로 정하지 못한다.

Google Analytics 4를 연동해 기본 페이지뷰 데이터와 함께, 핵심 여정 전환 지점에 커스텀 이벤트를
심어 퍼널 분석이 가능하게 한다.

측정 ID: `G-7K884Q399P` (사용자가 GA4 콘솔에서 직접 발급)

## 상세 요구사항

### 서비스/코드베이스 관점
- `@next/third-parties/google`의 `GoogleAnalytics` 컴포넌트를 루트 레이아웃에 연동
- 측정 ID는 하드코딩하지 말고 env var(`NEXT_PUBLIC_GA_MEASUREMENT_ID`)로 관리
  - `jam-web/.env.local`(로컬/staging 공용 여부는 구현 시 판단) 및 Vercel 프로젝트(jam, jam-stage)
    환경변수에 설정 필요 — 실제 Vercel 환경변수 설정은 사용자 승인 후 오케스트레이터가 처리
  - staging 트래픽과 production 트래픽이 섞이지 않도록 스트림 분리 여부는 jam-developer가
    현재 이 프로젝트의 배포 구조(jam vs jam-stage, VERCEL_GIT_COMMIT_REF 기준 분기)를 참고해
    설계하고 티켓에 근거를 남길 것 — 스트림을 하나만 쓴다면 최소한 이벤트에 환경 구분 파라미터를
    붙일 것
- 커스텀 이벤트 계측 지점 (전부 `gtag('event', ...)` 또는 GA4 권장 방식으로):
  - `sign_up_complete` — 구글 로그인 최초 완료 시점
  - `onboarding_complete` — username·활동 종목·지역 설정 완료 시점
  - `strava_connect_complete` — Strava OAuth 연동 완료 시점
  - `first_badge_earned` — 유저 최초 배지 획득 시점 (10초 보상 플로우 핵심 지표 — 반드시
    "최초 1회"만 발생하도록 서버/클라이언트 상태 확인 로직 필요)
  - `home_view` — 홈("투데이") 화면 진입 (재방문 지표)
  - `item_drop` — 아이템 드랍 액션
  - `item_pickup` — 아이템 픽업 액션
  - `combine_attempt` / `combine_success` — 믹스 시도/성공
  - `mission_join` / `mission_complete` — 미션 참가/완료
- 각 이벤트에 필요한 파라미터(예: badge_id, item_id, mission_id 등)는 기존 도메인 모델
  (`02_DATA_MODEL.md`) 필드명과 일치시켜 추후 분석 시 혼선이 없게 할 것

- 사용자 노출 UI 변경 없음 (계측 전용)

## 구현 계획
1. `@next/third-parties/google` 설치, 루트 레이아웃에 `GoogleAnalytics` 삽입 (env var 기반)
2. 이벤트 발생 지점별 기존 로직 파악 후 최소 침습적으로 계측 코드 삽입
3. `first_badge_earned`는 중복 발생 방지 로직 확인 필수 (스펙 위반 시 게이트 FAIL 대상)
4. 계측 이벤트 명세를 `Service Plan/Specs/PRD/` 하위에 문서화 (이벤트명·트리거 조건·파라미터 표)
   — PRD 루트에 새 섹션을 추가할지, `PRD/{주제}/` 하위에 별도 파일을 만들지는 `/jam-docs` 규칙에
   따라 progressive-reviewer 단계에서 판단

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- `@next/third-parties/google`의 `GoogleAnalytics`를 루트 레이아웃에 연동. 측정 ID는
  `NEXT_PUBLIC_GA_MEASUREMENT_ID`(미설정 시 스크립트 자체 미렌더 — 로컬 트래픽 유입 차단).
- 커스텀 이벤트는 `src/lib/analytics/gtag.ts`의 `trackEvent()` 한 곳으로만 전송(`sendGAEvent` 래퍼).
- **스트림 분리 근거**: GA4 측정 ID가 1개(`G-7K884Q399P`)뿐이라 스트림을 나누지 않았다. 대신
  이미 분리된 두 Vercel 프로젝트(`jam`=production, `jam-stage`=staging) 각각에
  `NEXT_PUBLIC_GA_ENVIRONMENT`를 다르게 설정해, 모든 이벤트에 `environment` 파라미터를
  자동으로 붙인다. `STAGING_MODE`(서버 전용)와 별개로 클라이언트에서 읽을 수 있는 새 env var가
  필요해 추가했다.
- 11개 이벤트 전부 계측 완료 (표는 `Specs/PRD/Analytics/GA4_EVENTS.md` 참고).
  - `sign_up_complete`: `auth/callback/route.ts`가 신규 가입(기존 row 없음)만 판별해
    `?new_signup=1` 플래그를 온보딩 도착 화면에 넘기고, 클라이언트가 1회 전송 후 URL 정리.
  - `onboarding_complete`: username 설정 성공 시점(현재 온보딩의 유일한 단계 — 아래 알림 참고).
  - `strava_connect_complete`: `StravaConnectReveal`의 `strava=connected` 도착 판정 재사용.
  - `first_badge_earned`: **서버가 판정**한다. `buildEarnedBadgePayload()`가
    `user_activity_badges` 전체 카운트와 "이번에 되읽은 배지 수"를 비교해 `isFirstBadgeEver`를
    응답에 싣고, `/api/strava/sync`·`/api/badges/recent-earned` 양쪽 다 이 값을 반환한다.
    클라이언트는 이 값만 신뢰해 1회 전송(세션 상태로 자체 판정하지 않음).
  - `mission_complete`: `checkMissions()`가 새로 완료한 `mission_id` 배열을
    `processFetchedActivities → syncStravaActivities → /api/strava/sync` 응답까지 그대로
    관통시켜, `SyncButton`이 응답받은 id마다 1회씩 전송(완료 INSERT 자체가 유니크 제약이라
    항상 "새로" 완료된 것만 실린다).
  - `item_drop`/`item_pickup`/`combine_attempt`/`combine_success`/`mission_join`/`home_view`:
    각 성공 콜백/마운트 시점에 최소 침습적으로 삽입.

### 주요 의사결정 / 핵심 메모
- **환경 구분 방식**: `STAGING_MODE`(서버 전용, `/api/dev-login` 게이트와 동일 기준)를 그대로
  쓸 수 없어(클라이언트 번들에 노출 안 됨) `NEXT_PUBLIC_GA_ENVIRONMENT`를 새로 추가했다.
  Vercel의 "Automatically expose System Environment Variables"(`NEXT_PUBLIC_VERCEL_ENV`)로
  대체할 수도 있었지만, 프로젝트 설정 변경(인프라 변경)은 이 티켓 범위를 벗어나 새 명시적
  env var로 결정했다.
- **first_badge_earned/mission_complete 판정을 서버로 옮긴 이유**: 클라이언트 상태(세션
  스토리지 등)로 "최초 여부"를 판정하면 새로고침·재방문·멀티탭에서 재현이 불안정하다.
  `user_activity_badges`/`user_mission_completions`의 유니크 제약이 이미 "평생 1회"를
  DB 레벨에서 보장하므로, 그 제약을 그대로 판정 근거로 재사용했다.

### 잔여 이슈
- Vercel(`jam`·`jam-stage`) 환경변수(`NEXT_PUBLIC_GA_MEASUREMENT_ID`,
  `NEXT_PUBLIC_GA_ENVIRONMENT`) 설정은 사용자 승인 후 오케스트레이터가 처리.
- `Specs/PRD/Analytics/GA4_EVENTS.md`의 "알려진 계측 공백" 절 참고 — combine/mission 보상
  경로의 `first_badge_earned` 미커버, 최초 Strava 연동 시점의 `mission_complete` 미전송,
  `onboarding_complete`의 실제 범위(username만)가 원 요청 시나리오(종목·지역 포함)와
  다른 점.
