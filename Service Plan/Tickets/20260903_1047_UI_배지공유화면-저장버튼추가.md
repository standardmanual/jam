# [UI] 배지 공유 화면 하단에 저장 버튼 추가

## 배경 / 문제 정의

배지 상세 화면의 공유 바텀시트(`BadgeShareButton.tsx`)는 현재 하단에 버튼 1개만 노출한다.
`navigator.share` 지원 여부에 따라 라벨만 "공유하기"/"저장하기"로 바뀔 뿐, 항상 같은 동작
(OS 공유시트 열기 또는 데스크톱 파일 다운로드)을 수행한다.

사용자가 배지 이미지를 앱 밖으로 공유하지 않고 **스마트폰 사진 앱(카메라 롤)에 바로 보관**하고
싶은 경우를 위해, "공유"와 "저장" 두 개의 버튼을 나란히 제공한다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 대상 파일: [BadgeShareButton.tsx](jam-web/src/app/(main)/badges/[id]/BadgeShareButton.tsx),
  이미지 생성 로직인 [buildBadgeShareBlob.ts](jam-web/src/app/(main)/badges/[id]/buildBadgeShareBlob.ts)는 변경 불필요(기존 blob 재사용)
- 바텀시트 `footer`에 버튼 1개 → **"공유" · "저장" 2개**로 변경 (`effectiveState.kind === 'ready'`일 때만 노출, 기존과 동일)
  - **공유**: 기존 `handleAction` 로직 유지 — `navigator.share` 파일 공유 지원 시 OS 공유시트, 미지원(주로 데스크톱) 시 `<a download>` 폴백
  - **저장**: 신규 동작 — 배지 이미지를 **스마트폰 사진 앱(카메라 롤)에 저장**
- **플랫폼 제약 검토 필수** (구현 전 조사):
  - 웹 표준상 브라우저가 사용자 승인 없이 iOS Photos 라이브러리에 직접 쓰는 API는 존재하지 않는다
    (권한 모델상 의도적으로 막혀 있음). Android는 `<a download>`로 다운로드 폴더에 저장 시
    MediaStore가 스캔해 갤러리/사진 앱에 자동 노출되는 경우가 많지만, iOS Safari의 `download`
    속성은 Files 앱(다운로드 폴더)에 저장될 뿐 사진 앱에는 들어가지 않는다.
  - iOS에서 "사진 앱에 저장"에 가장 가까운 방법은 (a) `navigator.share`로 열리는 공유시트의
    "이미지 저장" 액션(1탭 추가), 또는 (b) 이미지를 새 탭/전체화면으로 열어 길게 눌러
    "사진에 추가"하도록 안내하는 방식이다. 이 중 실제 동작을 리서치해 선택하고, **"공유"
    버튼과 동일한 시트가 뜨는 것으로 귀결되지 않도록** 두 버튼의 결과가 사용자에게 명확히
    다르게 느껴지는 방식을 택할 것.
  - 최종 채택한 플랫폼별 실제 동작(iOS/Android/데스크톱)을 완료 기록에 남긴다.

### UI/UX 관점
- 버튼 2개는 나란히 배치 (가로 분할). 기존 DS `Button`(`@ds/components/buttons/Button`) 재사용 —
  `fullWidth` 대신 각각 `flex-1`(또는 동등 폭)로 감싸는 wrapper 레이아웃. 신규 컴포넌트 불필요.
- 두 버튼의 시각적 무게(variant: primary/secondary)는 이 화면에서 어느 쪽이 더 자주 쓰일
  주요 행동인지 판단해 결정. 되돌릴 수 없는 위험 행동이 아니므로 UX_WRITING_GUIDELINE §5.2
  "1화면 1주요 버튼" 원칙(위험 행동용)은 그대로 적용되지 않는다 — 단, 두 버튼이 시각적으로
  동등한 무게로 혼동되지 않게 구분할 것.
- 저장 성공/실패 피드백 필요 (예: 저장 완료 토스트, 실패 시 에러 메시지) — 조용히 아무 반응
  없이 끝나지 않도록 한다.

### UX Writing 관점
- `Service Plan/Specs/UX_WRITING_GUIDELINE.md` 적용
- 버튼 레이블: 기존 i18n 키 `d.badges.shareActionShare`("공유하기") 재사용,
  신규 저장 액션은 `d.badges.shareActionShare`와 구분되는 새 키(가칭 `shareActionSave`, "저장하기")
  추가 — 기존 `shareActionDownload`("저장하기", 데스크톱 폴백용)와 문구 통일 가능성 검토
  (동일 문구면 새 키를 만들지 않고 재사용 가능한지 판단)
- §5.1 "예측 가능한 행동 동사" 원칙에 따라 "저장하기"로 결과가 명확히 드러나야 함
- 저장 성공/실패 안내 문구는 §4 에러 대응 가이드([현상]→[원인]→[해결책]) 및 §2.3 톤
  (일반 진행=담담·안내, 실패는 전문·직접) 준수
- 아이콘 버튼 IconButton 사용 시 `label` prop(`d.badges.shareButtonLabel`, 현재 "공유")도
  이번 변경으로 두 버튼이 되는 것과 무관하게(트리거는 여전히 IconButton 1개) 그대로 유지

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
바텀시트 footer를 "공유"·"저장" 2버튼(가로 `flex-1` wrapper)으로 변경했다. "공유"는 기존
`handleAction`(navigator.share 파일 공유 지원 시 OS 공유시트, 미지원 시 `<a download>`)을 그대로
쓰고, "저장"은 신규 `handleSave`로 분리해 아래 "플랫폼 제약 검토" 결과에 따라 iOS만 별도 분기했다.
버튼 레이블은 두 버튼 모두 항상 고정(플랫폼별 조건 분기 없음): "공유"=`shareActionShare`("공유하기"),
"저장"=기존 `shareActionDownload`("저장하기") 재사용(새 키 미생성, 아래 의사결정 참고). variant는
"공유"=primary(기본값), "저장"=secondary로 시각적 무게를 구분했다.

**플랫폼 제약 검토 결과(리서치 기반, 완료 기록 요구사항):**
- **iOS(Safari 및 WebView)**: 웹 표준상 사용자 승인 없이 Photos 라이브러리에 직접 쓰는 API가 없다.
  `<a download>`는 Files 앱 다운로드 폴더에만 저장되고 사진 앱에는 들어가지 않는다. "공유" 버튼과
  동일한 `navigator.share` 시트를 띄우면(옵션 a) 두 버튼의 결과가 사용자에게 구분되지 않으므로
  **옵션 (b)를 채택** — 이미지를 담은 blob URL을 `<a target="_blank">`로 새 탭에 연다. iOS Safari는
  이미지 응답을 전체화면 이미지 뷰어로 렌더링하며, 사용자가 길게 눌러 "사진에 추가"를 선택하면
  사진 앱에 저장된다. 공유시트(다중 앱 선택 UI)와는 화면 전환 자체가 확연히 달라 "공유" 버튼과
  혼동되지 않는다. 코드에서 실제 저장 완료 여부를 확인할 방법이 없으므로, "저장했어요"로 단정하지
  않고 `shareSaveIOSHint`("새 탭에서 이미지를 길게 눌러 사진에 저장해보세요") 안내 토스트(info)를
  띄운다. iPadOS 13+는 데스크톱 Safari와 동일한 UA 문자열을 쓰므로 UA 정규식만으로 iPad를 못
  잡는다 — `navigator.platform === 'MacIntel' && navigator.maxTouchPoints > 1`로 보정하는
  `isIOS()` 헬퍼를 별도로 만들었다(코드베이스에 기존 UA 판별 유틸이 없어 신규 작성).
- **Android**: `<a download>`로 다운로드 폴더에 저장하면 MediaStore가 이미지 MIME 타입을 스캔해
  갤러리/사진 앱(Google Photos 등)에 자동 노출된다. "공유" 버튼(OS 공유시트)과 동작 자체가
  달라(직접 저장 vs 공유시트 오픈) 구분된다. 저장 트리거 직후 성공 토스트(`shareSaveSuccess`,
  "이미지를 저장했어요")를 띄운다.
- **데스크톱**: 사진 앱 개념이 없어 `<a download>`로 파일을 내려받는 것이 곧 "저장"이다. Android와
  동일한 분기(비-iOS)를 타며 동일한 성공 토스트를 쓴다. "공유" 버튼도 `navigator.share`(파일)
  미지원이 일반적이라 사실상 같은 다운로드 동작이 될 수 있으나(플랫폼 특성상 불가피 — Photos
  앱이라는 개념 자체가 없는 환경이라 두 버튼을 강제로 다르게 만들 표준 API가 없음), 레이블은
  "공유하기"/"저장하기"로 여전히 의도가 다르게 보이도록 유지했다.

`buildBadgeShareBlob.ts`는 요구사항대로 변경하지 않았다(기존 blob 재사용).

### 주요 의사결정 / 핵심 메모
- **저장 버튼 레이블에 새 i18n 키를 만들지 않고 기존 `shareActionDownload`("저장하기")를
  재사용했다.** 티켓이 명시한 "동일 문구면 새 키를 만들지 않고 재사용 가능한지 판단" 지시에 따른
  결정. 대신 "공유" 버튼의 레이블은 기존처럼 `supportsFileShare()` 여부에 따라
  `shareActionShare`/`shareActionDownload`를 오가던 조건부 로직을 없애고 항상 `shareActionShare`
  ("공유하기")로 고정했다 — 두 버튼이 동시에 화면에 노출되는 지금 구조에서, "공유" 버튼이 상황에
  따라 "저장하기"로 바뀌면 바로 옆 전용 "저장" 버튼과 레이블이 겹쳐 혼동을 준다. 이 조건부 분기는
  버튼이 1개였던 이전 구조(공유 지원 시 "공유하기", 미지원 데스크톱은 "저장하기"로 그 자리에서
  의미를 바꿔 표시)에만 필요했던 것으로 판단해 제거했다.
- **variant 배정(공유=primary, 저장=secondary)**: 이 화면은 원래 "공유" 단일 액션이 존재하던
  화면에 "저장"을 추가하는 구조이고, 트리거 자체(IconButton)도 여전히 "공유" 아이콘 하나뿐이라
  진입 의도가 공유 쪽에 가깝다고 판단해 공유=primary로 정했다. 두 액션 다 위험 행동이 아니라
  §5.2 "1화면 1주요 버튼(위험 행동용)" 원칙이 강제하는 사안은 아니며, 사용 빈도 데이터가 없는
  상태의 판단이므로 confidence는 medium으로 본다(리뷰에서 반대 근거가 있으면 뒤집을 수 있음).
- **iOS 저장 방식으로 옵션(b)(새 탭+길게 눌러 저장 안내) 채택, 옵션(a)(공유시트의 "이미지 저장"
  액션) 기각**: 옵션 (a)는 구현이 "공유" 버튼과 동일한 `navigator.share` 호출이라 두 버튼의 실행
  결과 화면이 완전히 같아 보여 티켓이 명시적으로 금지한 "공유 버튼과 동일한 시트가 뜨는 것"에
  해당한다. 옵션 (b)는 한 단계(길게 누르기)가 더 필요한 대신 시각적으로 명확히 다른 화면(전체화면
  이미지 뷰어)로 전환돼 두 버튼의 구분이 뚜렷하다.
- **iOS 저장 액션에 "성공" 토스트를 쓰지 않고 "안내" 토스트(info)를 쓴 이유**: 새 탭을 여는 것과
  실제로 사진 앱에 저장되는 것 사이에 사용자의 추가 동작(길게 누르기)이 끼어 있어, JS에서 저장
  완료 여부를 확인할 수 없다. "저장했어요"라고 단정하면 §5.1 "예측 가능한 행동 동사"(버튼을
  눌렀을 때 일어날 결과가 명확히 드러나야 함) 원칙에 반해 실제 결과와 다른 정보를 줄 수 있으므로,
  다음 행동을 안내하는 문구로 대체했다.
