# [bug] 배지 공유화면 "저장" 버튼 — iOS에서 사진 앱에 저장되지 않음

## 배경 / 문제 정의

티켓 `20260903_1047`(배지 공유화면에 "공유"·"저장" 2버튼 추가)로 배포한 "저장" 버튼이
iOS 실기기에서 요구사항대로 동작하지 않는다. 사용자 실기기 테스트 결과:

1. "저장" 버튼을 눌러도 사진 앱에 저장되지 않는다.
2. 대신 새 탭이 열리고 배지 이미지만 보인다(운동데이터·로고가 안 보임 — 아래 원인 분석 참고).
3. **사용자가 이미 확인한 정상 동작 경로**: "공유" 버튼을 눌러 OS 공유시트가 뜨면, 그 시트
   안의 "저장" 액션을 누르면 운동데이터(거리/페이스/시간)와 로고가 포함된 투명 이미지가
   정상적으로 사진 앱에 저장된다. 즉 `navigator.share`로 여는 시트 자체는 정상 동작한다 —
   문제는 우리가 만든 "저장" 버튼이 이 경로를 타지 않고 별도의 "새 탭 열기" 방식
   (`handleSave`의 iOS 분기, `BadgeShareButton.tsx`)을 쓴 것이다.

## 원인 분석 (오케스트레이터 사전 조사)

- `handleSave`의 iOS 분기는 blob URL을 `<a target="_blank">`로 새 탭에 여는 방식이었다
  (`20260903_1047` 완료 기록: "옵션 (b)" 채택, 근거는 "공유 버튼과 동일한 시트가 뜨는 것을
  피하기 위함"). 하지만 실기기에서 이 방식은:
  - 사진 앱에 저장까지 이어지지 않는다(길게 눌러 "사진에 추가"하는 과정 자체가 사용자에게
    발견되지 않았거나, iOS 버전/설정에 따라 동작하지 않을 수 있음).
  - **더 근본적인 문제**: `buildBadgeShareBlob.ts`가 그리는 거리/페이스/시간 텍스트와 로고는
    흰색(`#FFFFFF`)이고 캔버스 배경은 투명이다. 브라우저가 투명 PNG를 새 탭에 직접 열면 기본
    배경이 흰색이므로, **흰색 텍스트·로고가 흰색 배경과 겹쳐 안 보인다.** 사용자가 "배지
    이미지만 보인다"고 느낀 것은 실제로 이 때문일 가능성이 높다(합성 자체는 정상이었을 것).
- 반면 `navigator.share({ files: [file] })`로 뜨는 OS 공유시트는 iOS가 자체 UI로 이미지를
  렌더링하므로 이 문제가 없고, 시트 안의 "저장" 액션이 실제로 Photos에 정상 기록한다
  (사용자 확인 완료).

## 상세 요구사항

### 기술적 제약 재확인
- 웹 플랫폼은 시스템 공유시트를 띄우지 않고 곧장 Photos에 쓰는 API를 제공하지 않는다(의도적
  제약, 이전 티켓에서도 동일하게 확인됨). **"시트 없이 1탭으로 저장"은 불가능하다.**
- 사용자가 확인한 유일한 실제 동작 경로는 `navigator.share` → 시트 안 "저장" 액션이다.

### 수정 방향
- iOS에서 "저장" 버튼 클릭 시 **새 탭 열기 방식(`handleSave`의 iOS 분기)을 제거**하고,
  `navigator.share({ files: [file] })`를 호출한다 (기존 `handleAction`과 동일한 호출 —
  코드 재사용/공통화할 것, 로직 중복 작성 금지).
- iOS에서는 결과적으로 "공유"·"저장" 두 버튼이 동일한 OS 공유시트를 띄우게 된다. 이는 웹
  플랫폼 제약상 불가피하며, **사용자가 실측으로 확인한 유일하게 작동하는 경로를 그대로 쓰는
  것이 최우선 목표**다 — 이전 티켓이 세운 "시트가 겹치면 안 된다"는 제약보다 "실제로
  저장돼야 한다"는 요구가 우선한다.
- (선택, 있으면 좋음) 시트가 뜨기 직전 또는 뜬 직후 "표시되는 시트에서 '저장'을 눌러주세요"
  류의 안내를 토스트로 짧게 보여줘, 사용자가 시트 안에서 어떤 액션을 눌러야 하는지 헤매지
  않게 한다. UX_WRITING_GUIDELINE 톤(§2.3 담담·안내) 적용.
- Android 분기(`<a download>`)는 이번 실기기 테스트에서 문제 보고가 없었으므로 그대로 둔다
  (단, 코드 재검토 중 명백한 결함이 보이면 함께 고친다).
- `shareSaveIOSHint`("새 탭에서 길게 눌러 저장") i18n 키는 새 탭 방식 폐기와 함께 더 이상
  쓰이지 않으므로, 제거하거나 새 안내 문구로 재정의한다(죽은 키로 남기지 않는다).

## 구현 계획
1. `handleSave`의 iOS 분기를 `handleAction`과 동일한 `navigator.share` 호출로 교체(공통 함수로 추출 검토)
2. 불필요해진 새 탭 관련 코드(`target="_blank"` 분기, 관련 주석) 제거
3. iOS 안내 토스트 문구 재검토 — 필요 없으면 제거, 필요하면 새 문구로 교체
4. lint/tsc 통과 확인
5. **가능하면 이번엔 실기기 또는 iOS 시뮬레이터로 실제 확인** — 이전 티켓은 실기기 미검증
   상태로 배포해 이 결함을 그대로 프로덕션에 내보냈다. 최소한 코드 경로가 "공유" 버튼과
   완전히 동일한 호출이 되는지(=이미 사용자가 검증한 경로와 100% 같은지) 대조 검증할 것.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- `handleSave`의 iOS 분기(blob URL을 `<a target="_blank">`로 새 탭에 여는 방식)를 제거하고,
  "공유" 버튼이 쓰는 `handleAction(blob)`을 그대로 호출하도록 교체했다 — iOS에서 "저장" 버튼도
  `navigator.share({ files: [file] })`를 타므로, 사용자가 실기기로 검증한 "공유시트 → 시트 안
  '저장' 액션 → Photos 저장" 경로와 코드 레벨에서 100% 동일한 호출이 된다.
- 시트가 화면 대부분을 덮어 안내가 묻히는 걸 감안해, `navigator.share` 호출 직전에 토스트로
  "곧 열리는 공유 시트에서 '저장'을 눌러주세요" 안내를 추가했다(선택 항목 반영).
- `shareSaveIOSHint` i18n 키는 새 탭 방식 전제의 문구("새 탭에서 이미지를 길게 눌러…")를
  폐기하고 시트 안내 문구로 재정의했다 — 죽은 키로 남기지 않음(UX_WRITING_GUIDELINE §2.3
  담담·안내 톤 적용).
- Android(`<a download>`) 분기는 재검토 결과 명백한 결함이 없어 그대로 유지했다.
