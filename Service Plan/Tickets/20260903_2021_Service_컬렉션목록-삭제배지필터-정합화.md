# [Service] 컬렉션 목록의 삭제배지 필터 누락 정합화

## 배경 / 문제 정의

티켓 20260903_1949(타인 프로필 통계탭 컬렉션 수에서 미슬롯 아이템북 제외) 작업 중, 게이트
리뷰(conservative-reviewer)가 범위 밖 발견물로 보고한 항목이다. **이번 변경이 만든 문제가
아니라 티켓 20260824_016 이전부터 존재하던 구조적 축 어긋남**이다.

프로필 컬렉션 수를 세는 로직과 컬렉션 목록을 만드는 로직이 **`badges.deleted_at IS NULL`
필터에서 서로 다르다**:

- **통계 카운트**: `jam-web/src/app/(main)/[username]/page.tsx` (약 121행) —
  `.is('deleted_at', null)` **있음**
- **목록 API**: `jam-web/src/app/api/users/[username]/itembooks/route.ts` (약 40~56행) —
  `discoveredByBook` 구성 시 `deleted_at` 필터 **없음**
- **컬렉션 풀페이지**: `jam-web/src/app/(main)/[username]/collections/page.tsx` (약 61~82행) —
  동일하게 **없음**

### 문제가 실현되는 조건

소프트 삭제된 아이템배지(`badges.deleted_at IS NOT NULL`)를 `dropped_at IS NULL` 상태로 보유
중인 `inventory_items` 행이 **실DB에 293건 존재**한다. 그 배지가 속한 아이템북이
(a) `is_active = true`이고 (b) 해당 유저의 슬롯이 1개 이상이면, **"목록에는 뜨는데 통계
숫자에는 안 잡히는"** 비대칭이 성립한다.

현재는 `item_books` 100개 중 96개가 비활성이거나 해당 북의 슬롯이 0개라 전수 대조에서
불일치가 0건으로 나온다. 즉 **버그가 우연히 가려져 있을 뿐** 구조는 어긋나 있다. 아이템북이
활성화되거나 슬롯이 채워지면 그때 드러난다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 세 곳의 `deleted_at` 필터 축을 맞춘다. 방향은 **통계 쪽(필터 있음)에 목록 쪽을 맞추는 것**이
  자연스러워 보이나, 소프트 삭제된 배지를 보유한 유저 화면에서 무엇이 사라지는지 실데이터로
  영향 범위를 먼저 확인하고 판단할 것. (293건이 어느 유저·어느 아이템북에 걸쳐 있는지
  service_role로 조회해 파악)
- 수정 후에는 **통계 숫자와 목록 개수가 항상 일치하는지 전수 대조**로 검증한다. 티켓
  20260903_1949에서 conservative-reviewer가 쓴 검증 방식(service_role로 양쪽 로직을 각각
  재현해 아이템북 보유 유저 전원 대조)을 그대로 따르면 된다.
- 티켓 20260903_1949의 "후속 검토 과제"에 적힌 **공용 헬퍼 추출**을 이번에 함께 하는 것을
  검토한다. `isOwnList || slottedCount > 0` 판정이 현재 4개 파일에 흩어져 있고
  (`api/users/[username]/itembooks/route.ts`, `[username]/collections/page.tsx`,
  `collections/[id]/page.tsx`, `[username]/page.tsx`), 20260903_1949 버그가 정확히 "한 곳만
  빠져서" 생긴 것이다. `deleted_at` 필터도 같은 이유로 어긋나 있으므로, 두 조건을 한 함수
  (`src/lib/itembook/` 아래 등)로 묶으면 다음 정책 변경에서 같은 누락이 구조적으로 불가능해진다.
  다만 범위가 커지므로 무리라고 판단되면 헬퍼 추출은 제외하고 필터 정합만 처리한 뒤 그 판단
  근거를 보고할 것.

## 구현 계획

1. service_role로 293건의 `inventory_items`가 어느 유저·어느 아이템북에 걸쳐 있는지, 활성
   아이템북·슬롯 1개 이상 조건과 겹치는 실제 건수를 조회해 영향 범위 확정.
2. 목록 API·컬렉션 풀페이지의 `discoveredByBook`/동등 구성에 `badges.deleted_at IS NULL` 필터
   추가.
3. (검토 후 채택 시) 공용 헬퍼 `filterVisibleBookIds` 등으로 4개 파일의 판정 로직 통합.
4. 통계 숫자 vs 목록 개수 전수 대조 검증, `npm run lint` / `tsc --noEmit` 통과 확인.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
목록 API(`api/users/[username]/itembooks/route.ts`)와 컬렉션 풀페이지
(`[username]/collections/page.tsx`)의 `discoveredByBook` 구성 시 `badges.deleted_at IS NULL`
필터를 추가했다. 방향은 티켓이 제시한 대로 **통계 쪽(이미 필터 있음)에 목록 쪽을 맞추는 것**을
그대로 채택했다 — 소프트 삭제된 배지를 컬렉션 목록에 계속 노출할 근거가 없고, 통계 카운트
(`[username]/page.tsx`)·상세 페이지(`collections/[id]/page.tsx`)·완성 판정
(`checkItemBookCompletion`/`findCompletableItemBooks`가 아니라 실사용자 화면인 슬롯 그리드)
모두 이미 삭제 배지를 숨기는 쪽으로 일관되어 있었다.

구체적으로는 `inventory_items` 조회의 `badge:badges(...)` select에 `deleted_at`을 추가하고,
`discoveredByBook` 구성 루프에서 `it.badge?.deleted_at`이 있으면 스킵하도록 조건을 확장했다
(기존 `type !== 'item'` 스킵과 같은 자리). 쿼리 레벨 `!inner` 조인 방식(통계 카운트가 쓰는
`badges!inner(deleted_at)` + `.is('badges.deleted_at', null)`) 대신 select에 컬럼만 추가하고
JS에서 필터링하는 방식을 택했다 — 이 파일들의 다른 소프트-삭제 필터(예:
`collections/[id]/page.tsx`의 레거시 피드 처리부, `[username]/page.tsx`의 `if (!b || b.deleted_at)
continue`)도 전부 이 패턴이라 코드베이스 관례와 일치하고, LEFT JOIN 결과 구조(`it.badge`가
`null`일 수 있음)를 그대로 살릴 수 있다.

- **`collections/[id]/page.tsx`는 이미 정상.** 이 파일은 `badges` 테이블을 직접
  `.is('deleted_at', null)`로 조회해 `badgeIds`를 뽑고, `inventory_items`는 그 `badgeIds`에
  대해서만 조회하므로 삭제된 배지가 애초에 슬롯 그리드에 나타날 경로가 없다(20260824_007에서
  이미 처리됨). 티켓 본문의 "세 곳" 서술과 달리 실제로 축이 어긋난 곳은 목록 API·풀페이지
  2곳뿐임을 코드 확인으로 재확인했다.
- **공용 헬퍼(`filterVisibleBookIds`) 추출은 이번에 하지 않았다.** 4개 파일의 판정 로직 형태가
  서로 다르다 — 목록 API·풀페이지는 `discoveredByBook: Map<bookId, Set<badgeId>>`를 먼저 만들고
  거기서 `slottedCount`를 계산해 필터링하고, 통계 카운트(`[username]/page.tsx`)는 `bookIdsForCount:
  string[]`에 슬롯 조회 결과로 교집합을 취하고, 상세 페이지(`collections/[id]/page.tsx`)는
  `slots.length === 0`이면 `notFound()`로 접근 자체를 막는 게이트다. 셋 다 최종적으로
  "슬롯 1개 이상 있어야 타인에게 보인다"는 같은 정책을 구현하지만, 입출력 타입이 서로 달라
  진짜 공용 함수로 묶으려면 데이터 조회 형태 자체를 통일하는 리팩터링이 필요하다. 이번 티켓
  범위(필터 정합화)를 넘어서는 크기라 판단해 제외했고, `deleted_at` 필터도 같은 이유로 각
  파일에 개별 적용했다. 정책 중복 자체는 20260903_1949가 이미 "후속 검토 과제"로 남긴 사항이라
  중복 기록하지 않는다.
