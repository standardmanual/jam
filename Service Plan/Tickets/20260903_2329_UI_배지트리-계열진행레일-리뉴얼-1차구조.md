# [UI] 배지 트리 — 계열 진행 레일 리뉴얼 (1차: 구조 전환)

## 배경 / 문제 정의

`/badges/tree`는 배지를 등급 우선 정렬의 평탄한 카드 나열로 보여준다. 걷기 탭 하나가 카드
64장·약 8,000px 스크롤이며, 같은 계열의 Common~Mystic 4장이 스크롤 전역에 흩어져 위계·진행
감각이 없다(티켓 20260901_0809가 카드 레이아웃·잠금칩 문구를 개선했지만 이 구조 문제는
범위 밖이었다).

별도 세션에서 사전 검토한 프로토타입(Artifact `968bd51c`)이 이 문제를 계열별 진행 레일로
재구성하는 안을 코드·DB 실측 기반으로 설계했다(§01~§08). `/layers-orient`·
`/layers-conceptual-model`로 어드민 필요성·확장성·객체 경계까지 검토를 마쳤다.

**이번 티켓은 프로토타입 전체(§08 A~H, 3단계 로드맵) 중 1차(구조 전환)만 다룬다.**
진행값(수치)·직전 동기화 비교·라벨 어드민화는 후속 티켓으로 분리한다 — 근거는 아래
"단계 분리 근거" 참조.

## 1.5 UI 탐색·재사용 판정 (오케스트레이터 판정)

`_ds_manifest.json`(29개 컴포넌트) + 관련 `.stories.*` 직접 확인 결과:

**그대로 재사용**
- `RarityBadge` — 등급칩. 그대로 사용.
- `ProgressBar` — 선형 진행바(current/total, color/trackColor prop). 레일 연결선·다음목표
  카드 하단 막대에 재사용 가능(색만 `--status-*` 토큰으로 오버라이드).
- `BottomSheet` — **병존 구현**(`design-system/components/navigation/BottomSheet.jsx` vs
  `src/components/ui/BottomSheet.tsx`). 실제 화면은 서비스 쪽을 쓴다 — 잠금 해제 조건
  콘텐츠는 서비스 `BottomSheet` 위에 얹는 신규 콘텐츠 패턴으로 처리(§1.6 병존 구현 규칙).

**패턴만 참고(재사용 아님)**
- `MissionCard.jsx`의 grayscale+lock 오버레이 컨벤션(§02② "잠금=grayscale" 규칙과 일치) —
  구현 시 같은 방식 유지.
- `BadgeGridCard`/`CollectionGridCard`의 그리드 셀 구조 — 트로피 그리드 셀 확장 기반으로
  검토(완전 신규보다 우선 시도).

**신규 MODULAR 패턴 (디자인시스템 + 스토리북에 추가, 이번 티켓 범위)**
1. `BadgeStageRail` — 계열 진행 레일(눈금+연결선+게이트). 눈금 상태는 이번 범위에선
   획득/게이트잠김/미도달 + 조건충족(라임) 4종 — "다음 목표" 강조 링·아크는 2차에서.
2. `BadgeTreeSummaryHeader` — 등급 분포 막대 + 획득/전체 요약(진행 요약 카드).
3. `RecentSyncBanner` — 직전 동기화 배너(1차는 boolean 이벤트만, 시안 색·아이콘 확정).
4. `UnlockConditionSheetContent` — 잠금 해제 조건 시트 내용(서비스 `BottomSheet` 위에 얹음).

**2차 이후로 미루는 신규 패턴**(이번 티켓 범위 아님, 후속 티켓에서 다룸)
- `DualAxisGauge`, `MultiCounterGauge` — 병목 지목·세그먼트 계산에 §08 A(진행 계산)가 필요.
- 레일의 "다음 목표" 강조 아크/링, "N 남음" 수치 — 같은 이유.

## 단계 분리 근거

프로토타입 §08 표(A~H)의 8개 항목 중 **엔진의 기존 판정 결과(`evaluateConditionDetailed`
pass/fail, `badgeTree.ts`의 기존 family/gate-fulfillment 로직)만으로 되는 것과, 새 계산
모듈(A)·새 테이블(C)·새 어드민 화면(G)이 필요한 것을 갈랐다.

| 단계 | 포함 | 새 백엔드 로직 |
|---|---|---|
| **1차(이번 티켓)** | 레일 구조·게이트·트로피 그리드·요약 헤더·동기화 배너(이벤트만)·잠금 시트 | **없음** — 기존 `evaluateConditionDetailed` pass/fail + 기존 gate-fulfillment 재사용 |
| 2차(후속) | 진행 수치(§08 A·B)·2축/다중카운터 게이지·"N 남음"·트로피 진행률 정렬·라벨 어드민 테이블(G)·미지원 고지(H) | `computeBadgeProgress()` 신규, `badge_metric_labels` 신규 |
| 3차(후속) | 진행 스냅샷(§08 C)·정합성 트리거(D2)·활동 단위 기여도(D)·아쉬움 줄·붉은(시안) 꼬리 | `user_family_progress` 신규 테이블 + 트리거 |

1차는 §08 원안이 "데이터 변경 없음"이라 명시한 것과 일치한다 — `badgeTree.ts` 정렬을
계열 우선으로 바꾸는 것이 핵심이고, 신규 계산 모듈이 없어 회귀 위험이 가장 낮다.

### 주요 의사결정 / 핵심 메모
- **조건값(수치 임계값) 라벨은 1차에서 표시하지 않는다.** "30km" 같은 값을 보여주려면
  condition_json 키 → 사람이 읽는 지표명·단위 매핑이 필요한데, 이건 §08 G(`badge_metric_labels`
  어드민 테이블)가 2차 이후에 만들 계층이다. 1차는 그 매핑 없이 등급칩·상태 단어·(펼친
  뷰에서는) 기존 `description`만으로 위계를 전달한다 — 라벨 테이블이 생기기 전까지 진행
  중인 안전한 축소판이다.
- **"조건 충족"(ready) 판정은 실제로 서버에서 `checkCondition`을 호출해 계산한다.** 처음엔
  이걸 "1차 = 계산 없음"이라 오해해 lock 데이터만으로 판정하려 했으나, 티켓의 "단계 분리
  근거" 표가 "기존 evaluateConditionDetailed pass/fail 재사용"을 1차 항목으로 명시하고
  있어 — 기존 함수 재사용이지 신규 계산 모듈이 아니다. `getActivityHistory`는 badge-engine·
  missions checker와 동일하게 **service client**로 호출해야 한다([username]/feed 페이지의
  strava_activities 조회 전례와 동일) — 일반 세션 클라이언트로는 RLS에 막혀 조용히 빈
  결과가 나올 뻔한 걸 기존 호출부 조사로 미리 잡았다.
- **선행 배지 OR 게이트의 "미충족" 판정을 수정했다.** 초안 로직은 `locks.some(비충족)`으로
  게이트가 안 열렸는지 봤는데, OR 관계에서는 틀린 식이다(하나만 충족해도 게이트는 열림).
  `hasUnfulfilledGate`를 "전부 미충족일 때만 안 열림"으로 고쳤다 — 안 고쳤으면 이미 선행
  배지를 하나 보유한 유저에게도 계속 "게이트잠김"이 잘못 표시됐을 것이다.
- **트로피 그리드는 신규 DS 컴포넌트를 만들지 않았다.** `BadgeGridCard`(서비스판) 그대로
  재사용 — earned boolean만으로 색 규칙이 충분해 "확장 필요"가 아니라 "그대로 맞음"이었다.
- **잠긴 눈금은 상세 페이지로 이동하지 않고 시트를 연다.** 앵커 안에 버튼을 중첩할 수
  없어서, 상태별로 링크(획득/미도달)와 버튼(조건충족/게이트잠김) 중 하나로만 렌더한다 —
  잠긴 배지의 상세 페이지 진입 경로가 이번 레일에는 없다(트레이드오프, alerts 참고).
- **DS `.jsx` 컴포넌트의 JS 타입 추론 함정.** `nextRarityLabel = null` 같은 널 리터럴
  기본값은 TS가 정확히 `null` 타입 하나로 좁혀버려 문자열을 넘기는 실제 호출부가 타입
  에러가 났다(문자열/불리언 리터럴 기본값은 넓혀지지만 null/undefined는 안 넓혀짐). 널이
  될 수 있는 prop은 기본값을 두지 않고 항상 명시적으로 넘기는 쪽으로 통일했다.
