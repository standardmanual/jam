# [Admin] 배지 지표(metric) 라벨·단위 관리 테이블

## 배경 / 문제 정의

티켓 20260903_2329(배지 트리 계열 진행 레일 리뉴얼 1차)가 "고도"·"금요일"·"km"·"분" 같은
지표 라벨을 1차 화면에서 아예 표시하지 않기로 미뤘다 — 이 매핑이 코드에도 DB에도 없기
때문이다(§08 G, 프로토타입 조사 결과: `index.ts`의 라벨 상수는 비공개에 6개뿐, `badges.
description`은 세계관 산문이라 구조화된 라벨로 못 씀).

**2차(진행 수치 표시)가 이 테이블을 전제로 한다** — `computeBadgeProgress()`(후속 티켓)가
`condition_json`의 필드 키(`distance_km`, `friday` 등)로 이 테이블을 조회해 화면에 보여줄
한글 라벨·단위를 채운다. 이 티켓이 먼저 끝나야 후속 티켓이 라벨을 렌더할 수 있다.

**어드민 편집 테이블로 만드는 이유(코드 상수가 아니라)**: 코드(TS 상수)로 만들면 새
지표·새 액티비티 종목이 추가될 때마다 배포가 필요하다. 어드민 편집 테이블이면 콘텐츠
담당자가 배포 없이 라벨을 추가할 수 있다 — `/layers-orient` 검토에서 확정한 방향.

## 상세 요구사항

### 서비스/코드베이스 관점
- 신규 테이블 `badge_metric_labels`:
  ```sql
  create table badge_metric_labels (
    metric_key   text primary key,   -- 'distance_km' | 'friday' | 'winter' …
    label_ko     text not null,      -- '누적 거리' | '금요일' | '겨울'
    unit_ko      text,               -- 'km' | '분' | '회' — 없으면 단위 없이 표시
    updated_at   timestamptz default now()
  );
  ```
  마이그레이션 파일만 작성한다(`jam-web/supabase/migrations/0XX_badge_metric_labels.sql`) —
  **실행은 하지 않는다.** 오케스트레이터가 사용자 승인 하에 직접 실행한다
  (`jam-web/CLAUDE.md` "DB 변경은 직접 실행" 규칙, jam-developer 권한 예외).
- 조회 함수(어디서 쓸지는 후속 2b 티켓 몫이지만, 인터페이스는 지금 확정): 여러 키를 한 번에
  조회하는 배치 함수를 하나 둔다(예: `getMetricLabels(keys: string[]): Promise<Map<string,
  {label: string, unit: string | null}>>`) — 배지 192개마다 개별 쿼리하면 안 된다.
- `condition-schema.ts`의 `ALL_CONDITION_KEYS`(또는 동급 상수)에 있는 **모든** 측정 필드
  키를 시드 데이터로 채운다 — 최소한 이 티켓이 끝났을 때 기존 배지 192개가 쓰는 모든 축은
  라벨이 있어야 한다. `index.ts`의 비공개 `DAY_LABEL_KO`·`SEASON_LABEL_KO`·
  `INDEPENDENT_FIELD_LABEL_KO`(6개)가 이미 올바른 한글 라벨을 갖고 있으니 그대로 시드값으로
  가져다 쓴다(추측해서 새로 짓지 않는다).

### UI/UX 관점 (어드민 전용 — MODULAR 적용 대상 아님)

### 게이트 리뷰 후 반영한 수정
게이트는 PASS였으나, `day_of_week` 시드 7개 전부가 `DAY_LABEL_KO`의 1글자 압축 표기
("금"·"월" 등)를 그대로 썼다는 걸 병합 전에 짚었다. `DAY_LABEL_KO`는 5칸짜리 다중 카운터
게이지 하나를 위한 공간 제약형 표기인데, 이 테이블은 2b 이후 여러 화면이 공통 조회하는
범용 저장소다 — 한 화면의 사정을 전체 정답값으로 박아두면 다른 화면(레일 등)에 그대로
노출된다. 사용자 승인 하에 요일 7개 전부를 전체 요일명("금요일" 등)으로 교정했다
(커밋 `ad9fbc05`). 지시 문구가 "DAY_LABEL_KO를 그대로 이식"이었으나, 그 지시의 의도
(추측해서 새로 짓지 않는다)와 실제 목적(범용 라벨 저장소) 사이에 충돌이 있었던 경우다.

### DB 반영
오케스트레이터가 Supabase MCP로 프로덕션(`jam-prod`, `ceehnkzdbecxwzxrhhns`)에 직접
마이그레이션 `127_badge_metric_labels` 적용 완료. 시드 29건 전체를 `select`로 재조회해
값 일치 확인. `get_advisors`(security)로 RLS 상태 확인 — `badge_metric_labels`는
`poi_categories`와 동일한 정상 패턴(INFO: RLS enabled, no policy — 의도된 상태).
`generate_typescript_types`로 실제 생성 타입을 뽑아 `database.generated.ts`의 수기
작성분과 대조 — **완전히 일치**, 재작성 불필요.

### 주요 의사결정 / 핵심 메모
- **어드민 편집 테이블 vs 코드 상수**: 코드 상수는 새 지표마다 배포가 필요해 "지속가능성"
  요건에 안 맞는다고 판단해 어드민 테이블로 결정(`/layers-orient` 검토 결과 반영).
- **`metric_key`가 필드명과 필드값을 같은 네임스페이스에 공유** — `'all'` 같은 범용 값이
  다른 필드의 값과 충돌할 수 있는 설계상 리스크. 티켓이 지정한 스키마라 이번엔 그대로
  두지만, 2b(computeBadgeProgress) 설계 시 인지 필요(게이트 리뷰 side finding).
- **`max_pace_sec_per_km`은 `unit_ko`를 NULL로 시드** — `formatPaceSecPerKm()`이 이미
  "5:30/km" 형태로 단위를 포함해 포맷하므로 중복 표기 방지.
