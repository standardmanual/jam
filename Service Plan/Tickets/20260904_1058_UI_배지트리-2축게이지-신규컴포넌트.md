# [UI] 배지트리 — 2축형 게이지 신규 컴포넌트 (레일 전용)

## 배경 / 문제 정의

2차(진행 수치 표시)의 마지막 조각. 2c(티켓 20260904_0921)가 누적·기록·주기 3종(단일 축,
170개)을 레일·트로피그리드에 연결했고, 남은 건 **2축형(dual, 20개)** 뿐이다.

**다중카운터형(multi)은 이 티켓에 없다.** 2c가 실제 카탈로그를 대조한 결과(완료 기록
"카탈로그 확인 결과" 절), 다중카운터형 2개(`평일의 성실함`·`사계절의 발걸음`)는 전부
트로피그리드 소속이고, 그리드는 이미 kind-무관 공통 포맷("병목 축 한 줄")으로 다섯 유형
전부를 처리하므로 **추가 작업이 필요 없다.** 프로토타입(§05)이 설계한 "세그먼트 게이지"는
현재 카탈로그의 어느 화면에도 필요한 자리가 없다 — 만들면 쓰이지 않는 컴포넌트가 된다.
새 계열이 추가돼 레일에 다중카운터형이 등장하면 그때 다시 판단한다(§08 H가 정확히 이런
상황을 위한 고지 장치다).

**데이터는 이미 흐르고 있다.** 2c의 `page.tsx`가 프런티어 눈금마다 `computeBadgeProgress()`를
이미 호출하고 있고(kind로 사전 필터링하지 않음), `BadgeFamilyRailItem.tsx`도 `progressByBadgeId`
전체를 이미 받는다 — 다만 `formatFrontierProgressText()`가 `kind === 'dual'`이면 `null`을
반환해 화면에서 버려지고 있을 뿐이다(2c 게이트 리뷰 확인 사항). **이 티켓은 새 데이터 배관이
필요 없다** — 이미 있는 `BadgeProgress` 객체를 화면에 꺼내 쓰는 것만 남았다.

## 상세 요구사항

### 1.5 단계 — UI 탐색·재사용 판정 (오케스트레이터 확정, 그대로 따를 것)

- **신규 MODULAR 패턴 `DualAxisGauge` 1개만 만든다.** DS 매니페스트에 2축 표현 가능한
  기존 컴포넌트가 없음을 확인했다(2c와 동일 결론 — `ProgressBar` 하나뿐).
- **`DualAxisGauge`는 얇은 합성이면 된다** — 프로토타입 §05 목업(산악 라이더/야생의 첫발)
  구조: 배지 썸네일(큰 사이즈) + 축 2줄(각 줄 = 라벨 + DS `ProgressBar` + "current/target
  unit" + 충족 시 체크 마커) + 규칙 문장("각각 다른 활동 가능" 또는 "한 번의 활동에서
  동시에") + 병목 안내 한 줄("{안 채운 축} 조건은 이미 채웠어요" 또는 사용 안 함). 축 한 줄
  자체는 새로 그리지 말고 DS `ProgressBar`(`design-system/components/feedback/ProgressBar.jsx`)
  를 `labelType='fraction'` 등으로 재사용한다.
- 숫자→문구 변환은 2c와 같은 원칙 — `badgeProgressText.ts`에 추가하는 새 포맷 함수(예:
  `formatDualAxisGaugeProps()`)가 담당하고, `DualAxisGauge` 자체는 완성 문자열/숫자만
  props로 받는다(kind를 모른다 — 2c의 `BadgeStageRail`/`BadgeTrophyGridCard`와 동일 원칙).
- Story 필수(pre-commit 확인 대상): `sameActivity:true`/`false` 각 1개 이상, 한 축만 충족한
  상태 1개.

### 서비스/코드베이스 관점

#### 통합 지점 — 레일을 없애지 않는다 (기본값, 이탈 시 근거 필요)

- 프로토타입 §05 목업은 2축형 배지를 레일 없이 큰 카드 하나로만 보여준다. **이 티켓은
  그 방식을 그대로 따르지 않는다** — 4등급 레일(계열 진행 감각, 1차의 핵심 산출물)을
  없애면 산악 라이더 같은 계열도 다른 계열과 다르게 보여 화면의 일관성이 깨진다.
  **기본 방향: 기존 `BadgeStageRail`(4등급 눈금)은 그대로 유지**하고, `DualAxisGauge`는
  `regretLine`과 같은 위치(레일 아래 보충 블록)에 프런티어가 dual일 때만 추가로 렌더한다.
  프로토타입처럼 레일을 완전히 대체하는 방향으로 가고 싶다면, 왜 이 계열만 예외로 둬야
  하는지 근거를 완료 기록에 남기고 진행할 것 — 임의로 택하지 않는다.
- 계열 하나(같은 `badges.name`)는 등급 4개가 조건 필드 조합이 전부 같다(2b/2c가 이미 확인한
  전제) — 즉 한 계열이 dual이면 미획득 등급 전부 dual이다. 프런티어(첫 미획득 눈금)만
  게이지를 그리면 된다(2c의 "진행 표시는 프런티어 한 곳만" 원칙 그대로).
- `BadgeFamilyRailItem.tsx`(69행 `frontierProgress`)에서 `progressByBadgeId[nextStop.id]`의
  `kind`가 `'dual'`이면 `DualAxisGauge`용 props를 만들어 `BadgeStageRail` 아래에 추가
  렌더한다. `BadgeStageRail` 자체를 더 고칠 필요는 없다(레일은 지금처럼 상태 라벨만
  그리게 두고, `frontierProgress`는 dual일 때 계속 `null` — 캡션 없이).

#### 계산 — 신규 계산은 최소화한다

- **양쪽 축의 current/target/met/label/unit은 `computeBadgeProgress()`가 이미 계산해
  `axes[0]`/`axes[1]`에 담아 넘긴다** — 새 계산 불필요.
- **병목 안내 문구**("{축} 조건은 이미 채웠어요")는 `axes`에서 `met:true`인 축을 찾아
  조립하면 된다 — 새 계산 불필요, 표시 레이어(`badgeProgressText.ts`)에서 문자열만 조립.
- **"가장 가까운 기록"(sameActivity:true 전용, 프로토타입 예시: "가장 가까운 기록은
  9월 1일 12.4km·260m")은 선택 사항이다.** 이건 `computeRecordRegretLine()`(기록형 전용,
  2c)과 같은 결의 계산이 필요한데 — "가장 최근 활동 하나가 두 축을 동시에 얼마나
  채웠는가" — 2c 범위에 없던 새 계산이다. 이 티켓의 필수 범위가 아니다 — 시간이 남으면
  `computeRecordRegretLine()`을 참고해 2축 버전을 추가해도 좋지만, 없어도 게이트를 막지
  않는다. 없으면 그 줄만 생략한다.

#### 카탈로그 확인 — 구현 전에 반드시 검증

- 5개 계열(러닝 `스피드 엔듀러`, 사이클링 `산악 라이더`, 등산 `혹한 장정`, 트레일러닝
  `야생의 첫발`·`알파인 트레일러`) 각각의 `condition_json`을 실제로 조회해 `same_activity`
  값과 두 축이 무엇인지 확인하고 완료 기록에 남긴다 — 프로토타입 목업 2건(산악 라이더=
  각각, 야생의 첫발=동시)만으로 5개 전부의 패턴을 추측하지 않는다.

- **`badge-engine/badgeProgress.ts`** — `BadgeProgressAxis`에 `fraction: number` 필드 추가.

### 주요 의사결정 / 핵심 메모
- **레일을 대체하지 않고 아래에 추가하는 기본값을 그대로 따랐다** — 이탈할 근거를 찾지
  못했다(오히려 위 카탈로그 확인으로 dual 20개가 전부 정규 계열/레일 소속임이 재확인돼
  기본값의 근거가 더 강해졌다).
- **"가장 가까운 기록" 문장(sameActivity 전용, 선택 사항)은 구현하지 않았다.** 티켓이 이미
  "새 계산 필요·필수 아님"으로 명시했고, 두 축의 `rangeText`(예: "12.4/15.0km"·"260/300m")가
  이미 "가장 근접한 시도"의 실측값을 보여주고 있어(`buildSameActivityDualAxes`가 병목 비율
  최댓값 활동을 고른 결과) 정보 자체는 중복이다 — 날짜("9월 1일")만 추가 정보인데, 이건
  `computeRecordRegretLine`과 별개로 "그 활동의 날짜"를 계산에 더 실어야 해 새 계산이 맞다.
  시간 대비 가치가 낮다고 판단해 생략했다(게이트를 막지 않는 항목으로 티켓에 명시됨).
- **병목 안내 문구는 "met:true인 축을 찾아 조립"(§계산 섹션)을 그대로 따랐다** — 1.5단계
  절의 "{안 채운 축} 조건은 이미 채웠어요" 표현은 문맥상(프로토타입 예시 "속도 조건은 이미
  채웠어요" — 속도가 met인 축) 앞뒤가 안 맞는 표현으로 판단해 더 정확한 §계산 섹션 쪽을
  따랐다 — met인 축 하나를 지목해 "이 축은 이미 끝났다"는 뜻이다.
- **콤마(천 단위 구분자) 없음.** 프로토타입 목업은 "1,180 / 1,500 m"처럼 콤마를 쓰지만,
  기존 `formatAxisRange`/`formatAxisNumber`(2c 산출물, 레일·그리드가 이미 쓰는 중)는 콤마를
  넣지 않는다. 이 축 값 포맷을 새로 만들지 않고 기존 함수를 그대로 재사용하는 쪽을
  택했다 — 화면 전체 표기 일관성(레일·그리드·게이지가 같은 규칙)이 목업 1건의 콤마
  스타일보다 우선한다고 판단했다. **confidence 판단 지점 — 디자인 리뷰에서 콤마 표기가
  필요하다고 판단되면 `formatAxisNumber` 자체를 고쳐 3곳(레일·그리드·게이지)에 동시 적용
  해야 한다(게이지만 콤마를 넣으면 화면 안에서 표기가 갈린다).**
- **접근성 — 그룹 `aria-label` 요약을 얹지 않았다.** `BadgeStageRail`은 인터랙티브 눈금
  (링크/버튼)이라 `role="group"` 요약이 필요했지만(2c 개선 리뷰 지적), `DualAxisGauge`는
  인터랙티브 요소가 전혀 없는 정적 텍스트 블록이라 화면에 보이는 라벨·수치·문장을 스크린
  리더가 DOM 순서 그대로 읽어도 정보가 그대로 전달된다 — 중복 요약을 얹으면 오히려 두 번
  읽히는 잡음이 생긴다고 판단했다.
- **`.d.ts` 파일을 만들지 않았다** — 직접 통합 지점이자 가장 최근 형제 컴포넌트인
  `BadgeStageRail.jsx`도 `.d.ts`가 없어(패턴 폴더 내 다른 컴포넌트는 있는 것도 있음) 같은
  전례를 따랐다.
