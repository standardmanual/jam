# [BadgeEngine] 배지 진행 스냅샷 테이블 + 계열 정합성 트리거

## 배경 / 문제 정의

3차(프로토타입 §08 C·D)의 첫 단계. 2a~2d(2차)로 다섯 조건 유형 전부가 화면에 진행 수치를
보여주지만, **전부 "지금 이 순간" 값만 실시간 재계산**한다 — 이전 상태와 비교할 방법이
없다. "직전 동기화로 얼마나 나아갔는지"(레일 채움 막대 끝 밝은 꼬리, 프로토타입 §05)를
보여주려면 **비교 기준이 되는 이전 값을 저장**해야 한다. 이 티켓은 그 저장소를 만든다.

**이번 범위에는 화면이 없다.** 스냅샷 테이블 + 싱크 파이프라인 write-hook까지만 하고,
"꼬리" 시각화(레일에 실제로 그리는 것)는 데이터가 최소 한 번 이상 쌓인 뒤에야 의미가
있으므로 후속 티켓(3b)으로 미룬다 — 2b(계산)→2c/2d(화면)로 나눴을 때와 같은 이유
(1차·2c 둘 다 "여러 난이도를 한 티켓에 섞어서" FAIL을 겪었다).

**이 티켓은 프로덕션 배지 발급 파이프라인(`sync.ts`)에 새 코드를 추가하고, `badges` 테이블에
쓰기를 막을 수도 있는 트리거를 새로 건다.** 지금까지(1차~2d)는 전부 읽기 전용 계산이었는데
이번이 처음으로 **실제 유저 싱크 흐름에 부작용을 추가하는 변경**이다 — 그만큼 검증 기준을
높인다(아래 "검증" 절 필수).

## 상세 요구사항

### A. 신규 테이블 `user_family_progress`

```sql
create table user_family_progress (
  user_id           uuid not null references auth.users(id),
  activity_type     text not null,
  family_name       text not null,   -- = badges.name, 계열의 유일한 식별자(2b/2c가 이미 확인)
  progress          real not null,   -- 0~1, 계열 안 미획득 최고 등급(프런티어) 기준
  current           jsonb not null,  -- 프런티어의 BadgeProgress.axes 스냅샷
  prev              jsonb,           -- 직전 동기화 시점의 current (최초 1회는 null)
  last_activity_id  uuid references strava_activities(id),
  updated_at        timestamptz not null default now(),
  primary key (user_id, activity_type, family_name)
);
```
- `auth.users`/`strava_activities`의 정확한 참조 스키마·컬럼명은 기존 마이그레이션
  (`supabase/migrations/`에서 `user_id uuid references`로 검색)에서 실제 관례를 확인해 맞춘다
  — 이 문서가 예시로 쓴 게 아니라 실제 제약이 통과해야 한다.
- RLS: `badge_metric_labels`(마이그레이션 127)와 다르다 — **이 테이블은 유저별 데이터**다.
  service_role만 쓰고 읽는 현재 구조(서버 컴포넌트가 항상 service client로 배지 트리를
  조회 — `badges/tree/page.tsx` 기존 패턴)를 유지할지, `authenticated`에게 자기 행 read
  정책을 열어줄지 판단해 완료 기록에 근거를 남긴다. **기본값은 닫아두는 쪽**(지금 이
  테이블을 직접 읽는 클라이언트 코드가 없다 — 필요해지면 그때 정책을 추가하는 게 더 안전).

### B. 계열 정합성 트리거 (DB advisor 정합성 체크 — 이전 세션 의사결정 D2)

**동기**: `family_name`이 유일한 식별자이므로, 어드민에서 조건을 잘못 고치면 그 계열
안에서 `computeBadgeProgress()`가 가정하는 "계열 하나 = 조건 필드 조합 하나"가 깨진다.
쓰기 시점에 막는 트리거로 방지한다 — 기존 `102_condition_json_check_constraint.sql`이
이미 쓰는 "DB가 조건 형태를 직접 검증한다"는 방침의 연장이다.

**⚠️ 아래는 1차 시도(HALT)에서 발견한 두 가지 결함을 반영해 수정한 버전이다 — "1차 시도
기록" 절을 먼저 읽을 것.**

```sql
-- 비교 범위는 MEASURABLE_CONDITION_KEYS(condition-schema.ts)로 좁힌다 — jsonb_object_keys
-- 전체를 비교하면 안 된다. prerequisite_badge_names(FILTER_ONLY_CONDITION_KEYS 소속)는
-- Common엔 없고 Rare 이상엔 있는 게 정상 설계라, 전체 키 비교는 다등급 계열 40/40개를
-- 즉시 위반시킨다(1차 시도 실측). 이 배열은 condition-schema.ts의 MEASURABLE_CONDITION_KEYS와
-- 반드시 동기화돼야 한다(102_condition_json_check_constraint.sql과 같은 관행).
create function check_family_condition_consistency() returns trigger as $$
declare
  measurable_keys text[] := array[
    'distance_km','elevation_gain_m','duration_minutes','min_speed_kmh','max_pace_sec_per_km',
    'temperature_min_c','temperature_max_c','weekend_duration_hours','total_count','streak_days',
    'weekly_count','month','monthly_km','season_count','season_count_all','active_days_count','time_range'
  ];
  sibling_keys text[];
  new_keys     text[] := (
    select array_agg(k order by k) from jsonb_object_keys(new.condition_json) k
    where k = any(measurable_keys)
  );
begin
  if (new.condition_json->>'mission_reward')::boolean is true then
    return new;  -- mission_reward 배지는 애초에 계열 그룹핑에서 빠진다(badgeTree.ts:166) — 대상 아님
  end if;

  select array_agg(distinct k order by k) into sibling_keys
  from badges, jsonb_object_keys(condition_json) k
  where activity_types = new.activity_types  -- activity_type(단수) 컬럼은 없다 — 배열 전체 비교
    and name = new.name
    and id <> new.id
    and deleted_at is null
    and (condition_json->>'mission_reward')::boolean is not true  -- 형제 쪽도 동일 제외(1차 시도 지적)
    and k = any(measurable_keys)

  if sibling_keys is not null and sibling_keys <> new_keys then
    raise exception '"%" 계열(%) 측정 조건 필드 불일치 — 기존 % / 신규 %',
      new.name, new.activity_types, sibling_keys, new_keys;
  end if;
  return new;
end;
$$ language plpgsql;

create trigger badges_family_consistency
  before insert or update of name, activity_types, condition_json on badges
  for each row execute function check_family_condition_consistency();
```

**알려진 한계(고치지 않고 그대로 남겨둔다 — 문서화만 한다)**: 이 트리거는 형제 존재
여부로 비교 대상을 찾는다. 그래서 어드민이 `name`을 완전히 다른 문자열로 오타 내면,
그 순간 "형제가 0건"이 되어 검사 자체가 스킵된다 — **이름 오타로 계열이 쪼개지는
시나리오는 이 트리거로 막히지 않는다.** 이 트리거가 실제로 막는 건 (a) 기존 계열에
형태가 다른 배지를 새로 추가하는 것, (b) 이름은 그대로 두고 `condition_json` 측정
필드 조합만 어긋나게 고치는 것, 두 가지다. 더 넓은 보호가 필요하면 별도 후속(예:
카탈로그 전체 정합성을 주기적으로 재검사하는 크론)으로 판단한다 — 이 티켓 범위가 아니다.

- **PASS 전 필수 사전 점검(재확인)**: 위 SQL로 바뀐 뒤에도, 이 트리거를 걸기 전에
  **현재 카탈로그 전체를 `(activity_types, name)`로 묶어 `MEASURABLE_CONDITION_KEYS`
  교집합이 계열마다 정확히 1가지인지 다시 확인**한다(1차 시도에서 이 범위로는 위반
  0건이었지만, 최신 상태로 다시 조회해서 확정할 것 — 조회 시 반드시 페이지네이션 또는
  `.eq()` 필터로 PostgREST 기본 1000행 제한을 피할 것, 1차 시도가 이 함정에 걸릴 뻔했다).
- `deleted_at is null` 필터는 유지한다 — 소프트 삭제된 형제 배지의 옛 조건 형태가 살아있는
  배지 수정을 막지 않게 한다. 현재 활동배지 중 소프트 삭제 0건이라 실측 검증은 못 했다 —
  구현 시 badge-engine 테스트에 "소프트 삭제된 형제가 있어도 막히지 않는다" 케이스를
  하나 추가해 이 가정을 코드로 고정한다(개선 리뷰 제안).
- 이 트리거는 `badges` 테이블 전체(활동배지·아이템배지·체크인 등 모든 `type`)에 적용된다.
  `item`·`checkin` 타입은 `condition_json`이 전량 NULL이라 실질적 영향은 없지만(1차 시도
  실측), 그래도 `type='activity'`로 범위를 좁히는 방향을 권장한다.

### 1차 시도 기록 (HALT — 위 B절은 이미 이 발견을 반영해 수정됨)

첫 시도에서 "사전 점검"(구현 계획 1) 단계가 두 가지 결함을 찾아내 트리거 SQL 작성 전에
멈췄다(정상 동작 — 게이트 리뷰 PASS로 확인됨). 실측(Supabase 읽기 전용 SELECT, 마이그레이션
실행 없음):

- `badges` 전체 5,596행(item 3600·activity 207·checkin 1789), `mission_reward` 15건 제외
  활동배지 후보 192건, `(activity_types[0], name)` 계열 72개 — 전부 2b 티켓 인용과 일치.
- **원안(전체 `jsonb_object_keys` 비교) 기준 다등급 계열 40/72개(100%) 즉시 위반.** 원인은
  전수 동일: Common엔 `prerequisite_badge_names`가 없고 Rare 이상엔 있음(계열의 정상
  설계 — `badgeTree.ts:238`, `ACTIVITY_BADGES.md`에도 이미 명시된 사실). 이 필드 하나만
  비교에서 빼면(=`MEASURABLE_CONDITION_KEYS`로 범위를 좁히면) 위반 0건.
- 트리거 SQL 자체의 컬럼명 버그도 발견: `badges`에는 `activity_type`(단수) 컬럼이 없다
  (`activity_types text[]`만 있음, 길이는 207건 전부 정확히 1) — `CREATE TRIGGER ... OF
  ... activity_type ...`가 그대로는 생성 자체에 실패했을 것.
  이 두 결함은 위 B절 SQL에 반영해 수정했다.

### C. 싱크 파이프라인 write-hook

- **훅 위치**: `src/lib/strava/sync.ts`의 `processFetchedActivities()` 안,
  `recordProcessedActivities()` 호출(현재 616행 부근) **직후**. 그 시점이면 이번 싱크의
  새 활동이 이미 `strava_activities`에 기록돼 있어 `getActivityHistory(supabase, userId)`
  하나로 전체 이력을 얻을 수 있다(병합 로직 중복 불필요 — `mergeActivityHistory`가 필요한
  이유는 그 전 시점, 즉 `evaluateBadgesDetailed` 내부(604행 부근)뿐이다).
- **새 계산 없음** — (activity_type, family_name) 쌍마다 이미 있는 `computeUserPeriodMetrics()`
  (activity_type당 1회) + `computeBadgeProgress()`(프런티어 1개당 1회, 2b/2c/2d 그대로)를
  호출해 얻은 결과를 저장할 뿐이다. 유저가 가진 모든 계열(약 72개, 미획득 프런티어가 있는
  것만)을 순회한다 — 배지 192개마다가 아니라 계열마다 1회.
- **`prev`는 "이전 행의 `current`"를 그대로 옮긴 것**이다 — 새로 계산하지 않는다. upsert 전에
  기존 행을 읽어 `current`를 `prev` 자리로 옮기고, 새로 계산한 값을 `current`에 넣는다.
- **일괄 upsert로 처리한다** — 계열마다 개별 쿼리 금지(최대 72개 왕복은 싱크 지연으로
  바로 체감된다). Supabase의 배열 `.upsert()`로 한 번에 처리한다.
- **이 훅이 실패해도 싱크 자체는 죽지 않아야 한다** — try/catch로 감싸고 실패 시 로그만
  남긴다(배지 발급·미션 판정 등 기존 로직은 이 훅과 무관하게 이미 끝난 뒤이므로, 이 훅의
  실패가 유저에게 보이는 배지 획득 결과에 영향을 주면 안 된다).

### D. 활동 단위 기여도 — 새 함수를 만들지 않는다 (설계 수정)

프로토타입 원안은 "`last_activity_id`로 그 활동 하나를 다시 읽어 계산하는 순수 함수"를
제안했지만, **이 테이블이 이미 `prev`/`current`를 둘 다 갖고 있으므로 그럴 필요가 없다** —
"이번 동기화가 얼마나 밀었는가"는 축마다 `current.axes[i].current - prev.axes[i].current`
(jsonb 안의 두 스냅샷 차이)면 충분하다. 활동 하나만 콕 집어 재평가하는 것보다 **오히려 더
정확하다** — 한 번의 동기화에 활동이 여러 건 들어와도(예: 백필) 그 합산이 자연스럽게
잡힌다. 이 계산은 표시 시점(3b, 화면 티켓)에 하면 되고, **이 티켓에서 만들 필요는 없다**
— 이 티켓은 `prev`/`current`를 정확히 채우는 것까지만 한다.

## 완료 기록 (2차 시도)

### 사전 점검 재실측 (구현 계획 1, 필수)
읽기 전용 SELECT만 수행(마이그레이션 실행 없음). PostgREST 기본 1000행 제한은 `type=eq.activity`
필터(활동배지 후보 자체가 207건 < 1000) + 이중 안전장치로 Range 헤더 페이지네이션을 함께
적용해 회피했다(스크립트: 세션 스크래치패드, 저장소에는 남기지 않음).

- `badges` 전체 5,596행(item 3600 · activity 207 · checkin 1789), `activity_types` 배열 길이
  전부 1, 소프트 삭제 0건 — 1차 시도 실측과 완전히 동일.
- `mission_reward=true` 15건 제외 활동배지 후보 192건, `(activity_types, name)` 계열 72개
  (다등급 40 · 단일등급 32) — 이 역시 1차 시도와 동일.
- **수정된 B절 SQL(MEASURABLE_CONDITION_KEYS 범위) 기준 계열별 교집합 불일치 0건.** 원안
  (전체 `jsonb_object_keys` 비교)이었다면 40/72건이 즉시 위반했을 조합인데, 실제로는

### 구현 내용 요약

### 구현 중 발견한 결함 — 티켓 B절 SQL에 남아 있던 문제 2건 (오케스트레이터 1차 수정 이후에도 존재)
1차 시도의 두 결함(전체 키 비교, `activity_type` 단수 컬럼 오류)은 티켓 B절에 이미
반영돼 있었지만, 그 수정된 SQL을 그대로 마이그레이션 파일에 옮기는 과정에서 실제로
실행하면 실패했을 문제를 추가로 발견해 고쳤다(둘 다 실행 전 코드 리뷰로 발견 — 마이그레이션은
여전히 미실행 상태):
1. **세미콜론 누락** — "형제 계열 조회" `SELECT ... INTO sibling_keys FROM ... WHERE ...
   AND k = ANY(measurable_keys)` 문 끝에 세미콜론이 없어, 다음 줄의 `IF sibling_keys IS NOT
   NULL ...`과 이어져 plpgsql 파서가 `CREATE FUNCTION` 자체를 구문 오류로 거부했을
   것이다. 세미콜론을 추가했다.
2. **테이블 스키마 미한정** — 형제 조회의 `FROM badges, jsonb_object_keys(condition_json) k`가
   스키마를 명시하지 않았다. 이 저장소의 다른 트리거/함수(`008_serial_prefix.sql`,
   `092_faction_background_cascade_rpc.sql` 등)는 전부 `public.` 접두를 쓰는 관례라
   `public.badges`로 통일했다(동작 자체는 `search_path`가 기본값이면 문제없었을
   가능성이 높지만, 이 저장소 관례 일치 및 방어적 명시성을 위해 교정).
빠뜨렸을 경우의 여파: 마이그레이션이 실제로 실행됐다면 `CREATE FUNCTION` 문 자체가 실패해
전체 마이그레이션이 롤백되고(단일 트랜잭션 기준) 테이블(A)까지 함께 생성되지 못했을
것이다 — 사용자 승인 전 코드 리뷰 단계에서 잡힌 것이 다행이다.

### 주요 의사결정 / 핵심 메모
- **`labelMap`은 빈 Map을 넘긴다 — `getMetricLabels()`를 호출하지 않는다.** 티켓 C절이
  재사용 대상으로 명시한 함수는 `computeUserPeriodMetrics()`/`computeBadgeProgress()`
  둘뿐이라 라벨 조회는 범위 밖으로 판단했다. 게다가 `getMetricLabels()`는 내부에서 자체
  `createServiceClient()`를 새로 만들어(주입된 클라이언트 미사용) 이 파일이 지키는 규율
  (티켓 20260831_1300, `sync-vehicle-speed-filter.test.ts`의 "정책 조회에 주입된 supabase
  클라이언트를 쓴다" 회귀 테스트가 감시)을 깬다 — 실제로 호출해 봤더니 그 테스트의
  `serviceClientCalls` 카운터가 올라가 회귀를 일으키는 것을 구현 중 직접 확인했다.
  결과적으로 `current`(jsonb 축 스냅샷)는 `label`이 원문 key로 채워진 채 저장되고, 실제
  라벨은 표시 시점(3b)에 `badge_metric_labels`를 다시 조회해 붙이는 구조가 된다 —
  스냅샷은 "숫자"만, "문구"는 항상 최신 라벨 테이블에서 조립하는 셈이라 라벨을 나중에
  고쳐도 과거 스냅샷 표시가 자동으로 갱신된다는 부수 이점도 있다.
- **`locks`도 빈 배열을 넘긴다.** `computeBadgeProgress()`가 반환하는 `gate` 필드는 이
  테이블에 저장하지 않으므로(스키마에 칸이 없음 — `progress`/`current`/`prev`만 저장),
  `missions` 조인을 포함한 잠금 그래프(`badgeTree.ts`의 BFS)를 다시 만들 필요가 없다.
  `buildGate([])`는 `null`을 돌려줄 뿐 `axes`/`progress` 계산에는 전혀 관여하지 않는다
  (badgeProgress.ts 확인).
- **`last_activity_id`는 계열별이 아니라 "이번 싱크 배치 전체" 기준 단일 값이다.** 티켓이
  이 필드의 정확한 산출 규칙을 명시하지 않아(D절이 오히려 "활동 단위 기여도 계산에는
  필요 없다"고 설계를 수정함) 감사(audit) 목적의 최소 해석을 택했다 — 이번 배치(활동
  여러 종목이 섞여도)의 최신 활동 1건의 `strava_activities.id`를 조회해 이번 호출에서
  upsert하는 모든 계열 행에 동일하게 채운다. "그 계열과 무관한 종목의 활동 id가 채워질
  수 있다"는 절충이 있다(예: 이번이 사이클링 활동뿐인 싱크여도 걷기 계열 행에도 같은
  id가 채워짐) — **confidence 판단 지점**, 다른 해석(계열별 activity_type과 일치하는
  최신 활동만 찾기)이 필요하면 후속 리뷰에서 조정 가능하다.
- **계열은 유저 활동 여부와 무관하게 카탈로그 전체(약 72개)를 순회한다.** 티켓 문구
  "유저가 가진 모든 계열(약 72개, 미획득 프런티어가 있는 것만)"의 "72개"가 카탈로그
  전체 계열 수와 정확히 일치하고(사전 점검으로 재확인), `/badges/tree` 라이브 페이지도
  유저가 그 종목을 한 적 없어도 모든 activityType의 트리를 항상 빌드하는 것과 동일한
  전제라고 판단했다 — 유저가 한 번도 안 한 종목의 계열도 `progress:0` 상태로 매 싱크
  upsert 대상이 된다(값 자체는 변하지 않으므로 실질적 낭비는 최대 72행 upsert 1회 수준).
- **`getActivityHistory(supabase, userId)`를 필터 없이 그대로 쓴다(차량 속도 필터 미적용).**
  `recordProcessedActivities`가 필터 전 `activities`(전체)를 기록하고, `/badges/tree`
  라이브 페이지(`page.tsx`)도 `getActivityHistory` 결과를 필터 없이 그대로
  `computeUserPeriodMetrics`에 넘긴다 — 이 훅을 그 라이브 계산과 다르게 필터링하면
  스냅샷과 화면이 서로 다른 값을 갖게 되므로, 기존 라이브 페이지와 동일한 입력을
  그대로 재사용했다(새 정책 판단 아님, 기존 동작 일치).
- **family 그룹핑 키에 원본 문자열(공백 포함 가능)을 다시 split하지 않는다.** `family_name`
  (배지 이름)이 "동네 산책러"처럼 공백을 포함해, 문자열 키를 조합해 뒀다가 다시 잘라
  쓰는 방식은 구분자 선택에 따라 취약해질 수 있다(구현 중 실제로 이스케이프 문자
  선택을 잘못해 파일에 제어문자가 섞여 들어간 사고를 겪고 복구했다 — 아래 alerts 참고) —
  Map의 값 객체에 `activityType`/`familyName`을 원본 그대로 함께 담아 split 자체를
  없앴다.
- **`FAMILY_RARITY_ORDER`를 `badgeTree.ts`의 비공개 `RARITY_ORDER`에서 재사용하지 않고
  재선언했다.** `badgeProgress.ts`가 `index.ts`의 `PER_ACTIVITY_KEYS`를 재선언한 것과
  동일한 이유(그 파일이 export하지 않고, 이 티켓도 재사용 대상으로 지정하지 않음) —
  값은 반드시 `['common','rare','epic','mystic']`로 동일해야 하며 `badgeTree.ts`가
  바뀌면 함께 봐야 한다는 주석을 남겼다.
- **트리거 "소프트 삭제된 형제가 있어도 막히지 않는다" 테스트는 추가하지 않았다.**
  티켓이 이 항목을 "개선 리뷰 제안"으로 명시적으로 미뤄뒀고(현재 활동배지 소프트 삭제
  0건이라 실측 검증 불가라는 티켓 자체의 판단), 이번 구현은 그 지시를 그대로 따랐다 —
  개선 리뷰 단계에서 필요 시 추가 판단.
