# [UI] 배지 트리 — 직전 동기화 대비 배너 실데이터 연결

## 배경 / 문제 정의
"배지 스테이지 레일" 리뉴얼 1차(티켓 20260903_2329)에서 `RecentSyncBanner` DS 컴포넌트를
만들었으나, 그 컴포넌트 자신의 헤더 주석이 명시하듯 지금은 "boolean 이벤트만" 지원한다 —
실제 서비스 연결도 `<RecentSyncBanner visible={hasRecentSync} />`(`BadgeTreeClient.tsx:178`)
하나뿐이라, 최근 24시간 안에 동기화가 있었는지만 보고 고정 문구("최근 활동이 동기화됐어요")를
띄운다. "직전 상태값과의 비교"(제안서 §08 C가 정의한 요구, 유저 니즈 ⑦)는 아직 화면에
없다.

이후 티켓 20260904_1156이 `user_family_progress` 테이블(계열별 `current`/`prev` jsonb
컬럼)과 Strava 싱크 write-hook(`updateFamilyProgressSnapshots()`)을 완성해, 매 싱크마다
계열별 진행값이 쌓이기 시작했다. 그 데이터를 읽어 배너에 실제 비교 문구로 표시하는 화면
쪽 작업은 1156 티켓이 "데이터가 최소 1회 이상 쌓인 뒤 별도 티켓으로 진행"이라고 명시적으로
범위 밖에 남겼다 — 이 티켓이 그 후속이다.

배지 트리 화면 코드(레일·게이지·트로피 그리드 전부)는 2026-09-04 오늘 프로덕션에 이미
반영되어 실유저 싱크가 `user_family_progress`에 쌓이기 시작한 상태다. `prev`가 의미
있으려면 유저가 배포 이후 **두 번째** 싱크를 해야 채워진다(최초 싱크는 `current`만 생성) —
구현 자체는 지금 진행하되, 실계정 육안 확인은 그 시점 이후에나 가능하다는 전제를 감안한다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `/badges/tree` `page.tsx`(서버 컴포넌트)에서 `user_family_progress`를 로그인 유저
  기준으로 조회해 계열별(`activity_type + family_name`) `current`/`prev`/`updated_at`을
  가져온다. 기존 `progressByBadgeId` 계산 흐름(티켓 20260904_0921)과 같은 요청 안에서
  처리한다 — 별도 왕복 쿼리를 늘리지 않는다.
- **표시 대상 계열 선정 기준을 정한다** (구현 계획에서 확정): 가장 최근에 `updated_at`이
  갱신된 계열 1개인지, `prev`→`current` 변화폭이 가장 큰 계열인지. 후자가 "가장 눈에 띄는
  진전"을 보여주지만 계산이 더 필요하다.
- `prev`가 없거나(최초 싱크 전) `current`와 축값이 완전히 동일하면(진전 없음) 배너를
  숨기거나 기존 "최근 활동이 동기화됐어요"로 폴백한다 — 빈 비교문(예: "0km → 0km")을
  보여주지 않는다.
- 축별 수치 차이를 사람이 읽는 문장으로 조립한다. 라벨은 기존 `getMetricLabels()`
  (`badge_metric_labels` 테이블, 티켓 20260904_0430)를 재사용한다. `formatAxisRange` 등
  기존 숫자 포맷 함수(`badgeProgressText.ts`)를 그대로 쓴다 — 새 포맷 규칙을 만들지 않는다.
- 발급 판정 로직(`evaluateConditionDetailed`)·`condition_json` 스키마는 건드리지 않는다.
  이번 작업은 이미 저장된 스냅샷을 읽어 문장으로 조립하는 표시 레이어일 뿐이다.

### UI/UX 관점
- `RecentSyncBanner.jsx`(DS, `jam-web/design-system/components/patterns/`)에 새 prop을
  얹어 확장한다 — 컴포넌트의 색·레이아웃(시안 점 + 카드)은 1차에서 이미 확정됐으므로 그대로
  두고, `message` 자리에 비교 문구가 들어가도록 배선한다. 신규 컴포넌트를 만들지 않는다
  (1.5단계 재사용 판정 참고).
- "데이터 없음"(최초 싱크 전)과 "변화 없음"을 구분해 보여줄지, 아니면 기존 문구로 통합
  폴백할지는 UX 라이팅 검증 시 함께 정한다. `Service Plan/Specs/UX_WRITING_GUIDELINE.md`
  기준(해요체, 담담한 안내 톤 — 배지 트리는 열람 화면이라 신남 톤 강요 안 함, 티켓
  20260831_2208 기존 결정과 동일 원칙) 적용.

## MODULAR 재사용 판정 (오케스트레이터, 1.5단계)
**재사용 — 신규 컴포넌트 없음.** `RecentSyncBanner.jsx`가 이미 존재하고(`_ds_manifest.json`
등록 완료, `.stories.tsx`·`.prompt.md` 보유), 이번 작업은 그 컴포넌트에 prop을 추가해
데이터를 배선하는 것뿐이다 — 컴포넌트 자신의 헤더 주석이 "구체적인 수치·개수는 2·3차에서
이 컴포넌트에 새 prop으로 얹는다"고 이미 예고해뒀다. 기존 7개 스토리(1차 boolean 상태)는
유지하고, 신규 prop 조합 스토리를 추가한다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
`user_family_progress`(티켓 20260904_1156)의 계열별 `current`/`prev` 축 스냅샷에서 "가장 눈에
띄는 진전"(fraction 증가폭이 가장 큰 축) 하나를 골라 "직전 동기화보다 {라벨} {델타}{단위}
가까워졌어요" 문장으로 조립하고, `RecentSyncBanner`(DS)에 새 prop `comparisonMessage`로
배선했다. 재계산 없이 이미 저장된 스냅샷 값만 읽는다 — `page.tsx`가 `user_family_progress`를
1회 조회해 대표 축을 고르고(순수 함수, 라벨 불필요), 그 축의 key를 기존 `axisKeys` 수집
Set에 합류시켜 **왕복을 늘리지 않고** 같은 `getMetricLabels()` 호출에서 라벨을 얻은 뒤
문장을 완성한다.

- **대표 계열 선정 기준**: "가장 최근 갱신"(updated_at) 대신 "fraction 증가폭이 가장 큰
  축"을 택했다(구현 계획이 확정하라고 지정한 항목). 한 번의 싱크가 여러 계열을 같은
  트랜잭션으로 일괄 upsert하므로(티켓 20260904_1156 C절) `updated_at`만으론 동시각 갱신을
  가를 수 없고, `fraction`은 축 종류(높을수록/낮을수록 좋음)와 무관하게 이미 0~1로
  정규화돼 있어 계열·축을 가로질러 직접 비교 가능한 유일한 값이었다.
- **"데이터 없음"과 "변화 없음" 구분 여부**: 구분하지 않고 하나로 통합 폴백했다(구현 계획이
  확정하라고 지정한 항목). `prev`가 없거나(최초 싱크 전) 모든 축의 fraction 변화가 0 이하면
  (증가 없음·주기 리셋으로 감소) `pickSyncComparisonCandidate()`가 동일하게 `null`을 반환하고,
  `RecentSyncBanner`는 기존 "최근 활동이 동기화됐어요"로 자동 폴백한다 — 유저 입장에서 두
  상태를 구분해 알려줄 실익이 없다고 판단(둘 다 "지금은 비교해 보여줄 게 없다"는 동일한 결론).
- **`RecentSyncBanner`에 추가한 prop**: `comparisonMessage`(문자열|null, 기본값 없음). 값이
  있으면(truthy) 배너의 유일한 텍스트 슬롯에 표시하고, 없으면(null) 기존 `message` prop
  기본값으로 자동 폴백한다 — 호출부가 분기할 필요가 없다. 레이아웃·색은 1차 그대로.

### 주요 의사결정 / 핵심 메모
- **가장 큰 fraction 증가폭 축 "하나"만 보여준다 — 계열명(family_name)은 문장에 넣지
  않았다.** 티켓의 문장 템플릿이 "{무엇이 얼마나} 가까워졌다"(축 라벨 + 델타 2개 빈칸)라서,
  라벨은 `getMetricLabels()`가 이미 붙여주는 축 라벨("누적 거리" 등) 하나로 충분하다고
  판단했다. 어느 계열(배지)인지까지 명시하려면 배너에 클릭 시 해당 레일로 스크롤/딥링크하는
  기능이 자연스럽게 뒤따르는데, 이는 티켓 상세 요구사항에 없고 레이아웃도 "그대로 둔다"고
  명시돼 있어(칩 형태 클릭 영역 등 신규 UI 없음) 범위 밖으로 판단했다 — **confidence 판단
  지점**, 리뷰에서 "계열명이 있어야 더 유용하다"고 판단하면 후속으로 조정 가능.
- **선정 기준으로 "가장 최근 갱신"이 아니라 "fraction 증가폭 최댓값"을 택한 근거**를 위
  구현 요약에 남겼다 — 요약하면 "한 트랜잭션 다중 upsert 때문에 updated_at만으론 못
  가른다"가 핵심 이유.
- **델타 반올림은 항상 내림(floor)** — `formatCurrentValue`/`formatRegretLineText`의
  "아직 못 미친 쪽으로 표기해 실제보다 부풀리지 않는다" 원칙을 그대로 델타에도 적용했다.
  내림 결과가 0 이하면(예: 3.21km→3.24km처럼 표시 단위로 구분 안 되는 미세 변화)
  `formatSyncComparisonText()`가 `null`을 반환해 상세 요구사항의 "빈 비교문(0km 가까워졌어요)을
  보여주지 않는다"를 코드로 강제했다.
- **페이스(max_pace_sec_per_km) 델타는 mm:ss가 아니라 정수 초**로 표기했다 —
  `formatRegretLineText`가 이미 같은 축의 "부족분"을 정수 초로 표기하는 선례를 그대로
  따랐다(절대값은 `formatPaceSecPerKm()`으로 mm:ss, 차이값은 초 — 라벨 테이블의
  `max_pace_sec_per_km` 행 자체가 `unit_ko=NULL`인 이유와 동일하게 mm:ss 표기에 이미
  단위가 내장돼 있어 델타에 그 형식을 그대로 쓰면 오히려 부자연스럽다).
- **가정 검증 — current/prev 축 key 불일치 가능성**: 계열 정합성 트리거(마이그레이션 128,
  `badges_family_consistency`)가 같은 계열의 등급 간 측정 조건 필드 조합을 항상 동일하게
  강제하므로, 프런티어 등급이 두 싱크 사이에 바뀌어도(예: Common 완료 → Rare로 전진)
  `current`/`prev`의 축 key 집합은 항상 같다 — 다만 이건 **DB 트리거가 보장하는 불변식에
  기댄 가정**이라, `pickSyncComparisonCandidate()`는 그래도 key로 매칭해(순서 의존 안 함)
  방어적으로 짝을 못 찾으면 스킵하도록 짰다(테스트로 고정).
- 선택하지 않은 대안: "계열 배지 개수 기준"(프로토타입 §08 초안의 "배지 {N}개가
  가까워졌어요") — 이 티켓의 상세 요구사항이 명시적으로 "축별 수치 차이"·`getMetricLabels()`
  재사용·`badgeProgressText.ts`의 숫자 포맷 함수 재사용을 지정해, 개수 집계가 아니라
  축 단위 비교라는 게 문맥상 명확했다(개수 집계였다면 저 재사용 지시들이 대부분 무의미).

### 잔여 이슈
- **실계정 육안 확인은 아직 불가능** — 티켓 배경에 명시된 대로, `prev`가 채워지려면 배포
  이후 유저가 **두 번째** 싱크를 해야 한다(최초 싱크는 `current`만 생성). 오늘(2026-09-04)
  배포된 배지 트리 화면 코드 기준으로 아직 두 번째 싱크가 쌓인 계정이 없을 수 있다 —
  staging 병합 후에도 "폴백 문구(최근 활동이 동기화됐어요)만 보인다"는 결과가 정상일 수
  있다는 점을 리뷰 시 감안할 것.
- 티켓 본문이 "기존 7개 스토리(1차 boolean 상태)는 유지"라고 언급했으나, 실제
  `RecentSyncBanner.stories.tsx`에는 1차 산출물이 **3개**(Visible/CustomMessage/Hidden)뿐이었다
  (직접 카운트 확인). 3개 전부 그대로 유지하고 `comparisonMessage={null}`만 명시적으로
  추가했다(TS 추론 이슈 회피 목적, 동작 변화 없음) — 티켓의 "7개"는 다른 컴포넌트(예:
  `BadgeStageRail`)와 착각했을 가능성이 있어 보이나 구현에는 영향 없어 그대로 진행했다.
- 배너 자체에 클릭 시 해당 계열 레일로 이동하는 기능은 없다(위 "주요 의사결정" 참고,
  범위 밖 판단) — 후속 필요 시 별도 티켓.
