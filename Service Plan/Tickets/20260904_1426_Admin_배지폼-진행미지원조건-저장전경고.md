# [Admin] 배지 폼 — 진행 미지원 조건 저장 전 경고

## 배경 / 문제 정의
"배지 스테이지 레일" 제안서(§08 H)는 진행 미지원 고지를 두 갈래로 설계했다 — 화면 쪽
(레일·트로피 그리드에 "진행 표시 준비 중" 표시)은 티켓 20260904_0921에서 이미 구현됐지만,
어드민 쪽(`BadgeForm.tsx` 저장 전 경고 배너)은 그 티켓이 명시적으로 범위 밖에 남겼다.

`computeBadgeProgress()`(티켓 20260904_0631)의 `classifyBadgeProgressKind()`는 다섯 유형
(누적·기록·주기·2축·다중카운터)으로 분류되지 않는 조건을 `{kind:'unsupported'}`로 반환한다.
지금 카탈로그는 `mission_reward:true`(15건)만 여기 해당하고, 이 배지들은 `badgeTree.ts`가
트리 자체에서 걸러내 화면에 아예 안 뜨므로 현재는 실질적 영향이 없다. 하지만 어드민이 새
조건 조합의 배지를 만들면 그 순간부터 화면에서 조용히 빠지거나 잘못 그려질 위험이 있다 —
저장 시점에 경고해야, 나중에 "배지는 발급되는데 화면에 안 보인다"는 문의를 받고서야
알게 되는 상황을 막는다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `/admin/badges`의 `BadgeForm.tsx`가 조건을 저장하기 전, `classifyBadgeProgressKind()`
  (또는 그 판정을 감싼 동일 분류 함수)로 폼에 입력된 `condition_json`이 `unsupported`인지
  확인한다.
- **저장 자체는 막지 않는다.** `unsupported`면 "이 조건은 배지 트리 화면에 진행률이
  표시되지 않습니다 — 발급은 정상 동작합니다" 배너를 보여주는 것으로 그친다. 배지 출시가
  화면 개발 완료를 기다릴 필요는 없다는 게 제안서의 명시적 전제다.
- **분류 함수는 화면 쪽(0921)이 쓰는 것과 동일한 하나를 그대로 재사용한다** — 어드민
  경고와 화면 렌더링이 각자 판정 로직을 새로 구현하면, 이미 여러 곳에 흩어져 있는 조건
  목록 문제(`condition-schema.ts`·DB CHECK 제약·`PER_ACTIVITY_KEYS`)를 하나 더 만드는
  셈이다(제안서 §08 H가 이 원칙을 명시).
- `classifyBadgeProgressKind`가 어드민 폼(클라이언트 컴포넌트)에서 그대로 import 가능한지
  먼저 확인한다 — 같은 계열 함수(`badgeProgress.ts`)가 `next/headers` 전이 의존 때문에
  실패했던 전례가 있다(티켓 20260904_0631의 게이트 리뷰 1차 FAIL 사유). 서버 전용 의존이
  섞여 있으면 클라이언트 세이프하게 분리하거나, 폼 제출 시 서버 액션/API 라우트에서
  판정하는 방식으로 조정한다.
- `BadgeForm.tsx`가 이미 `getUnsupportedConditionKeys`로 "폼이 지원 안 하는 필드"를
  감지해 경고하는 동일 패턴을 갖고 있다 — 새 UI 패턴을 만들지 않고 그 패턴을 그대로
  확장한다.

### UI/UX 관점
- 저장을 막지 않는 경고이므로 폼 하단 등 비침습적 위치에 배치한다. 기존
  `getUnsupportedConditionKeys` 경고와 시각적으로 구분되거나 통합되는지는 구현 계획에서
  정한다(두 경고가 동시에 뜰 수 있는 조합이 있는지 먼저 확인).
- 문구는 `Service Plan/Specs/UX_WRITING_GUIDELINE.md` 기준(해요체, 안내형 톤, 에러가
  아니므로 사과·경고조 지양)으로 작성한다.

### 어드민 예외 규칙
이 티켓은 `admin` 유형이므로 MODULAR 디자인 시스템 탐색·재사용 판정(1.5단계)을 생략한다
(jam-work 라우팅 규칙).

### 클라이언트 세이프 여부 확인 (착수 시 최우선 확인 사항)
`classifyBadgeProgressKind`는 `src/lib/badge-engine/badgeProgress.ts`가 export하는 순수
함수다. 이 파일은 `./index`(→ `@/lib/supabase/server` → `next/headers` 전이 의존, 티켓
20260904_0631 1차 FAIL 원인)를 거치지 않고 `./activityFilters`(순수 함수, 타입 외 무의존)만
import하도록 이미 그 티켓에서 고쳐져 있었다. 게다가 `badgeProgressText.ts`가 같은 모듈에서
`LOWER_IS_BETTER_KEYS`를 **값(value)** import해 `BadgeFamilyRailItem.tsx`/
`BadgeTrophyGridCard.tsx`(둘 다 `'use client'`)에서 이미 쓰고 있고, 그 상태로 티켓
20260904_0921 게이트 리뷰가 `npm run build`를 실행해 통과한 전례가 있다 — 즉 착수 전에 이미
클라이언트 세이프성이 실증돼 있었다. 이번 작업에서도 `BadgeForm.tsx`(`'use client'`)에
`classifyBadgeProgressKind`를 값으로 직접 import한 뒤 `npm run build`를 재실행해 재검증했다
(exit 0, `/admin/badges/new`·`/admin/badges/[id]/edit` 정상 포함 — 아래 테스트 결과 참고).
서버 전용 의존 분리 작업은 필요 없었다.

### 구현 내용 요약
- `BadgeForm.tsx`에 `classifyBadgeProgressKind`(화면 쪽 0921과 완전히 동일한 함수, 재사용 —
  새 분류 로직 없음)를 값 import하고, 조건 빌더의 실시간 `condPreview`(기존 JSON 미리보기가
  쓰는 값과 동일)를 그 함수로 분류해 `'unsupported'`면 `isProgressUnsupported` 플래그를 세운다.
- `isProgressUnsupported`가 true면 조건 빌더 카드 안, 기존 `getUnsupportedConditionKeys` 배너
  바로 아래·JSON 미리보기 바로 위에 같은 스타일(`rounded-xl border border-amber-300
  bg-amber-50 p-3` + 볼드 헤딩 + 보조 문구)의 새 배너를 렌더한다. **저장은 막지 않는다** —
  `handleSubmit`에는 어떤 조건도 추가하지 않았다.
- **`type === 'activity'`일 때만 분류를 수행하도록 게이트를 추가했다** (아래 "주요
  의사결정" 참고 — 티켓 본문에 명시되진 않았지만 판단이 개입된 지점).
- `getUnsupportedConditionKeys`와의 관계: 두 경고는 동시에 뜰 수 있는 관계임을 확인했고(아래
  "주요 의사결결" 참고), 통합하지 않고 별도 박스로 유지하되 시각 스타일은 동일하게 맞췄다
  ("그 패턴을 그대로 확장" 요구 충족).

### 주요 의사결정 / 핵심 메모
- **`type === 'activity'`로 게이트를 추가함 (티켓 본문에 명시되지 않은, 판단이 개입된
  지점 — confidence를 medium으로 낮춘 이유).** `/badges/tree/page.tsx`가 배지를 조회할 때
  `.eq('type', 'activity')`로 걸러 활동 배지만 화면에 올라간다. item·checkin 배지는
  `classifyBadgeProgressKind`의 분류 결과와 무관하게 그 화면에 애초에 등장하지 않으므로,
  게이트 없이 모든 타입에 이 배너를 띄우면 "배지 트리 화면에 표시 안 됨"이라는 문구가
  item 배지에 대해서는 (표시 안 되는 게 맞지만) "분류가 지원되면 표시된다"는 잘못된 인상을
  줄 수 있다고 판단했다. checkin은 조건 빌더 블록 자체가 `{type !== 'checkin' && (...)}`
  안에 있어 이미 자동 배제된다.
- **배너를 `handleSubmit` 내부(제출 시 1회성 계산)가 아니라 렌더 시점 실시간 계산으로
  구현했다.** 저장 성공 시 `router.push('/admin/badges')`로 즉시 이동해버려, 제출 순간에만
  계산하면 사용자가 배너를 볼 새도 없이 화면이 넘어간다. `condPreview`(JSON 미리보기가 이미
  쓰는 값)를 그대로 재사용해 `getUnsupportedConditionKeys`와 동일하게 "폼이 열려 있는 동안
  계속 보이는" 방식을 택했다 — 이게 "저장 전에 경고"의 실질적 의미에 더 부합한다고 판단.
- **두 amber 배너를 통합하지 않고 별도 박스로 유지했다.** 두 경고가 동시에 뜰 수 있는 조합이
  실제로 있다 — 예: `day_of_week`을 단독으로(총 횟수 없이) 설정하면 `getUnsupportedConditionKeys`
  (폼에 입력 UI 없음)와 `classifyBadgeProgressKind`(측정 가능 필드 0개 → unsupported) 양쪽에
  걸린다. 반대로 `active_days_count`는 폼 UI는 없지만(`unsupportedConditionKeys`에 걸림)
  진행 계산은 지원한다(`cumulative`로 분류) — 즉 두 판정이 독립적이라 하나의 문구로 합치면
  조건부 조립이 복잡해지고 두 관심사(폼 한계 vs 화면 표시 한계)가 뒤섞인다. 스타일(박스
  모양·색)만 동일하게 맞춰 "그 패턴을 그대로 확장"하라는 요구를 만족시켰다.
- **`classifyBadgeProgressKind(condPreview ?? {})`** — 함수 시그니처가 `BadgeCondition`
  (non-null)만 받아 `condPreview`(`BadgeCondition | null`)를 그대로 넘길 수 없다. `{}`로
  보정해도 결과는 `null`을 넘겼을 때와 동일하게 `'unsupported'`다(전자는 `axisCount===0`
  폴스루, 후자는 `!condition` 얼리리턴 — 코드 경로만 다르고 결과는 같음). 즉 활동 배지인데
  조건을 아예 안 채운 상태에서도 이 배너가 뜨는데, 이는 정확한 신호다 — `page.tsx`는 조건이
  없는 배지를 애초에 `progressTargets`에 넣지 않아 진행 수치 계산 자체를 생략한다("표시 안
  됨"이 사실과 일치).
