# [UI] 배지획득캐러셀 — Common 등급 라이브 리전 공지 누락 수정

## 배경 / 문제 정의

`BadgeRevealCarousel.stories.tsx`의 "접근성 — 중앙 카드 텍스트 라이브 리전"
(`CenterCardAnnouncement`) 인터랙션 테스트가 `expected '한강 러너 1. 한강을...'
to contain 'Common'`로 실패한다. 티켓 20260904_1426(배지 폼 진행 미지원 조건 경고)
작업 중 발견됐으며, 게이트/개선 리뷰 양쪽이 해당 컴포넌트와 무관한 변경(격리
워크트리에서 재현)임을 확인해 별도 이슈로 분리했다.

**원인 분석 (커밋 타임라인 대조로 확정)**

1. 티켓 20260823_008(`b07b5123`)에서 `BadgeRevealCarousel`에 상시 마운트 라이브
   리전을 도입했다. 중앙 카드의 "등급·이름·설명"을 읽도록 설계했고, 그 티켓 본문
   216행에 명시된 대로 **"등급 라벨은 라이브 리전 안에서 `RarityBadge`를 그대로
   렌더해 얻는다(라벨 매핑 중복 금지)"** — 즉 `<RarityBadge rarity=.../>`를 라이브
   리전 JSX 안에 직접 합성하는 방식을 의도적으로 택했다. 같은 티켓 QA(253행)에서
   "라이브 리전이 `Common 한강 러너 1. …`"로 정상 동작함을 실측 확인했다.
2. 4일 뒤 티켓 20260827_024(`5fa630c3`)가 `RarityBadge`를 "`rarity==='common'`이면
   `null` 반환"으로 전역 변경했다. 이 티켓의 배경은 명확히 **그리드/리스트에서 반복
   노출되는 시각적 칩(BadgeGridCard·CollectionGridCard·FeedSection)의 노이즈
   축소**였고, 본문 어디에도 `BadgeRevealCarousel`이나 라이브 리전은 언급되지 않는다.
   즉 시각 전용 결정이었고, `BadgeRevealCarousel`이 `RarityBadge`를 텍스트 소스로
   재사용하고 있다는 사실은 고려 대상이 아니었다.

결과적으로 `RarityBadge`가 common 등급에서 `null`을 반환하면서, 원래 항상 렌더되던
시각용 `<span>`이 사라졌을 뿐 아니라 **그 안의 라벨 텍스트("Common")까지 라이브
리전에서 통째로 사라졌다** — 두 컴포넌트가 서로 다른 이유로 같은 자리를 썼기 때문에
생긴 결합도 문제다.

**"테스트가 깨진 것"이 아니라 "컴포넌트가 회귀한 것"인 근거**
- 스토리의 `RARITIES` 배열은 생성 시점(20260823_007)부터 `['common', 'rare', ...]`
  순서가 바뀐 적이 없다 — `makeItems(3)`의 1번 카드는 항상 common이었다.
- 테스트 어서션(`toContain('Common')`)은 티켓 20260823_008이 실측 확인한 원래 스펙
  그대로다.
- 즉 스토리 콘텐츠·테스트 어서션 둘 다 변경된 적이 없고, 그 사이에 있는
  `RarityBadge`만 변경됐다.

**실사용 영향**: `BadgeRevealCarousel`은 스토리북 전용이 아니라
`src/components/BadgeRevealOverlay.tsx`를 통해 실제 스트라바 동기화 완료 화면
(`NotificationsClient.tsx`, `src/lib/strava/sync.ts`)에 연결돼 있다. 현재 상태로는
스크린리더 사용자가 common 등급 배지를 획득했을 때 등급 정보를 전혀 듣지 못한다
(이름·설명만 들림) — sighted 사용자가 "칩이 없다 = common"이라는 시각적 관례를
학습할 수 있는 것과 달리, 화면낭독기 사용자에게는 "등급 정보가 아예 언급되지
않음"과 "common이라 침묵함"을 구분할 방법이 없다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `BadgeRevealCarousel.jsx`의 라이브 리전이 중앙 카드의 등급을 **모든 등급(common
  포함)에서** 텍스트로 공지해야 한다.
- `RarityBadge`의 기존 시각적 동작(`rarity==='common'`이면 칩 미표시)은 **그대로
  유지한다** — 티켓 20260827_024의 정책을 되돌리지 않는다. 그리드/리스트의 시각적
  노이즈 축소 목적은 여전히 유효하며, 이번 티켓의 범위가 아니다.
- 라벨 문자열("Common"/"Rare"/"Epic"/"Mystic")의 단일 소스 원칙(티켓 20260823_008의
  결정)도 유지한다 — `BadgeRevealCarousel.jsx`에 라벨 맵을 새로 복제하지 않는다.

### UI/UX 관점 (해당 시)
- 시각적 변화는 없어야 한다 (라이브 리전은 `SR_ONLY_STYLE`로 항상 화면에 보이지
  않는 영역). `RarityBadge`가 렌더하던 색상·패딩 등 시각 스타일은 애초에 SR-only
  노드 안에서 낭비였을 뿐 아니라, 이번 문제의 근본 원인(시각 컴포넌트를 텍스트
  용도로 재사용)이기도 하다.

### 컨텐츠 관점 (해당 시)
- 해당 없음

## 구현 계획

`RarityBadge.jsx`에 텍스트 라벨만 반환하는 헬퍼(예: `getRarityLabel(rarity)`)를
추가로 export해서, 기존 `config` 맵(라벨 단일 소스)은 그대로 두고 "시각적 칩을
렌더링할지"와 "이 등급의 텍스트 라벨이 무엇인지"를 분리한다. `RarityBadge` 컴포넌트
자체의 동작(및 다른 모든 호출부)은 변경하지 않는다 — 새 named export를 추가하는
것뿐이므로 연결된 서비스 화면(RarityBadge를 직접 쓰는 9종 컴포넌트 중 하나)에
회귀가 생기지 않는다.

`BadgeRevealCarousel.jsx`의 라이브 리전은 `<RarityBadge rarity={...} />`를 렌더하는
대신 `getRarityLabel(...)`의 텍스트를 직접 삽입하도록 변경한다.

**영향 범위**
- `design-system/components/cards/RarityBadge.jsx` (+`.d.ts`) — named export 추가만,
  기존 `RarityBadge` 컴포넌트 동작 무변경
- `design-system/components/patterns/BadgeRevealCarousel.jsx` — 라이브 리전 구현만
  변경, 시각적 렌더링(카드 안쪽 `<RarityBadge>`)은 무변경
- 서비스 코드(`jam-web/src/`) 변경 없음

**모듈러-서비스 연결 범위 (1.6)**: `RarityBadge`는 서비스에 즉시 반영되는 "연결된
컴포넌트 9종"에 속하지만, 이번 변경은 `RarityBadge`의 기존 렌더링 동작을 건드리지
않고 새 헬퍼 함수를 추가로 export하는 것뿐이라 기존 서비스 호출부(`RarityBadge`를
직접 import하는 화면들)에는 아무 영향이 없다. `BadgeRevealCarousel` 쪽 변경은
`BadgeRevealOverlay.tsx`를 통해 실제 스트라바 동기화 배지 획득 연출에 반영된다
(시각적 변화 없음, 스크린리더 공지 내용만 정상화).

**재사용 판정 (1.5)**: 신규 UI·신규 컴포넌트 없음. 기존 `RarityBadge`의 라벨 맵을
헬퍼로 노출해 재사용하는 리팩터링 성격의 버그 수정.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- `RarityBadge.jsx`의 기존 `config` 맵(라벨 단일 소스)을 그대로 재사용하는
  `getRarityLabel(rarity)` named export를 추가했다. `RarityBadge` 컴포넌트 자체의 로직
  (`rarity==='common'`이면 `null` 반환 포함)은 한 글자도 건드리지 않았다 — 새 함수를
  추가만 했다.
- `BadgeRevealCarousel.jsx`의 라이브 리전이 `<RarityBadge rarity={...} />`를 렌더해 텍스트를
  얻던 방식을 `{getRarityLabel(center.item?.rarity ?? 'common')}` 직접 삽입으로 교체했다.
  이제 common을 포함한 모든 등급에서 라이브 리전이 등급 텍스트를 공지한다.
- 카드 안쪽 시각적 렌더링(`BadgeCard` 내부의 `<RarityBadge rarity={item?.rarity ?? 'common'} />`,
  452~546행)은 요구사항대로 손대지 않았다 — common일 때 칩 미표시는 여전히 그 자리에서
  유효하다(시각적 노이즈 축소 목적 그대로 유지).
- `RarityBadge.d.ts`에 `getRarityLabel(rarity?: Rarity): string` 타입 선언을 추가했다.
- 두 `.stories.tsx`(`BadgeRevealCarousel.stories.tsx`, `RarityBadge.stories.tsx`)는 요구사항대로
  전혀 수정하지 않았다 — 테스트를 고치는 게 아니라 컴포넌트가 기존 테스트를 다시
  통과하도록 만드는 것이 목표였다.

### 주요 의사결정 / 핵심 메모
- **`getRarityLabel`의 기본값을 `RarityBadge`와 동일하게 `rarity = 'common'`으로 맞췄다.**
  호출부(`BadgeRevealCarousel.jsx`)는 이미 `center.item?.rarity ?? 'common'`으로 널 보정을
  하고 있어 사실상 기본값이 쓰일 일은 없지만, 두 함수가 같은 config를 공유하는 자매
  함수라는 점을 시그니처로도 드러내고 싶어 통일했다(오케스트레이터 구현 계획에 명시된
  선택은 아니고 이번 구현에서 판단한 지점).
- **`BadgeRevealCarousel.jsx`의 `RarityBadge` import는 제거하지 않고 유지했다.** 라이브
  리전은 `getRarityLabel`로 교체했지만, `BadgeCard` 내부의 시각적 칩 렌더링(505행)은
  여전히 `<RarityBadge>` 컴포넌트를 그대로 쓰기 때문이다 — 두 import를 나란히 두는 것이
  "시각 렌더링 여부"와 "텍스트 라벨"이 같은 소스에서 갈라진다는 사실을 코드에서도 보여준다.
- **오케스트레이터가 확정한 원인·재사용 판정을 그대로 따랐다** — 대안(예: `BadgeRevealCarousel.jsx`
  안에 라벨 맵 복제, 또는 `RarityBadge` 자체가 `renderChip` 같은 prop을 받아 common도
  렌더하게 바꾸는 안)은 검토하지 않았다. 후자는 `RarityBadge`의 기존 동작(9개 연결 호출부에
  즉시 영향)을 바꾸는 것이라 티켓이 명시적으로 금지한 범위였고, 전자는 티켓
  20260823_008이 피하려던 라벨 매핑 중복을 재발시키므로 애초에 고려 대상이 아니었다.
