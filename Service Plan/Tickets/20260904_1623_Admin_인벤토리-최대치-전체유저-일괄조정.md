# [Admin] 인벤토리 최대치(max_slots) 전체 유저 일괄 조정 기능

## 배경 / 문제 정의
`inventory.max_slots`는 현재 어디서도 어드민이 조정할 수 없다. DB 마이그레이션의
`DEFAULT 50`(`jam-web/supabase/migrations/001_initial_schema.sql:137`)이 사실상 하드코딩된
전역 정책값이며, 신규 유저는 `handle_new_user()` 트리거(`079_fix_handle_new_user_missing_inventory.sql`)가
`INSERT INTO public.inventory (user_id)`만 실행해 이 컬럼 DEFAULT를 그대로 물려받는다.
어드민 코드 전체에서 `max_slots`를 다루는 곳은 `src/app/api/admin/simulate/route.ts:128`
(드랍 시뮬레이터용 SELECT) 하나뿐이고 수정(UPDATE) 로직은 없다. 값을 바꾸려면 지금은
Supabase에 직접 SQL을 실행하는 방법뿐이다 (참고: `Service Plan/Specs/PRD/04_PROJECT_SPEC.md:219`,
`SERVICE_OPERATIONS.md`에 "50슬롯 고정" 정책으로 명시돼 있고, 티켓
`20260730_001_Infra_아이템북-슬롯-정책-확정...`에서 슬롯 소모 정책 자체는 이미 확정된 바 있음 —
이번 작업은 그 슬롯 정책이 아니라 **최대치 숫자 자체**를 어드민이 바꿀 수 있게 하는 것).

이번 작업은 "전체 유저 일괄" 조정이 목표다. 유저별 개별 조정 UI는 범위 밖이다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 어드민에 인벤토리 최대치 정책을 조회/수정할 수 있는 화면·API 추가
  (기존 `src/app/admin/drop-policy` + `src/app/api/admin/drop-policy/route.ts` 패턴 참고 —
  싱글톤 정책 테이블(`drop_policy`, id=1) + GET/PUT 라우트 + 서버 검증 구조를 따를 것)
- **두 가지를 모두 만족해야 "전체 유저 일괄 조정"이 완성된다**:
  1. **기존 유저**: `inventory` 테이블의 모든 row에 대해 `max_slots`를 새 값으로 일괄 UPDATE
  2. **향후 신규 유저**: `handle_new_user()` 트리거가 새 기본값을 물려받도록 처리
     (현재는 컬럼 `DEFAULT 50`에 의존 — 컬럼 DEFAULT를 바꾸는 마이그레이션이 필요하거나,
     트리거 함수가 정책 테이블에서 값을 읽어와 `INSERT ... (user_id, max_slots) VALUES (..., 정책값)`
     하도록 바꾸는 방법 중 택 1. 후자가 향후 재조정 시 마이그레이션이 필요 없어 더 낫다면 그렇게 할 것 —
     구현 방식은 jam-developer가 기존 정책 테이블 패턴과 일관되게 판단)
- 값 검증: 정수, 1 이상 (0 이하 방지 — `notifications/batch/account.ts:102` 주석에 "max_slots가
  0 이하면 [인벤토리 꽉참] 알림을 만들지 않는다"는 기존 로직이 있으니 회귀 없는지 확인)
- **DB 스키마/트리거 변경이 필요하면 SQL 마이그레이션 파일로 작성만 하고 실행하지 않는다**
  (`jam-web/supabase/migrations/0XX_설명.sql`) — 실행은 게이트 통과 후 사용자 승인 하에
  오케스트레이터가 처리한다 (프로젝트 규칙 5번)

### UI/UX 관점
- 어드민 화면(`admin` 유형)이므로 MODULAR 디자인 시스템 적용 대상 아님 — 기존 어드민 화면의
  shadcn/ui 컴포넌트 스타일을 따를 것
- 현재 값(정책값)과 영향받는 유저 수를 보여주고, 일괄 변경은 되돌리기 어려운 작업이므로
  저장 전 확인(confirm) 단계를 둘 것
- 에러 메시지는 `drop-policy` API의 기존 패턴처럼 [현상] → [원인] → [해결책] 구조로 작성

## 구현 계획
1. 정책 저장 방식 결정 (신규 싱글톤 테이블 vs 기존 테이블 확장) — `drop_policy`/`abusing` 정책 패턴 참고

4. `src/app/admin/inventory-policy/page.tsx` 화면 작성 — 현재 값 표시, 입력, 확인 후 저장

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- `inventory_policy` 싱글톤 정책 테이블(id=1) 신설 — drop_policy/combine_policy와 동일 패턴,
  RLS ON + 정책 없음(service_role 전용).
- `handle_new_user()` 트리거를 `CREATE OR REPLACE`로 갱신 — 신규 인벤토리 INSERT 시
  `inventory_policy.max_slots`를 읽어와 반영(기존 컬럼 DEFAULT 50 의존 제거). 정책값을 다시
  바꿔도 이후 마이그레이션이 필요 없다.
- `set_inventory_max_slots(p_max_slots)` DB 함수 신설 — ①`inventory` 전체 row UPDATE,
  ②`inventory_policy` upsert를 한 함수 안에서 원자적으로 처리(supabase-js가 여러 테이블
  트랜잭션을 지원하지 않아 DB 함수로 묶음). 새 최대치보다 이미 많은 아이템을 보유한 유저가
  있으면 `used_slots_within_limit` CHECK에 걸리기 전에 미리 카운트해 명확한 예외 메시지로
  중단한다. PUBLIC EXECUTE는 REVOKE, service_role만 GRANT(109 마이그레이션과 동일한 이유).
- 어드민 API `GET/PUT /api/admin/inventory-policy` — GET은 현재 정책값 + 적용 대상 유저 수
  (inventory row 총계), PUT은 정수·1 이상 검증 후 위 DB 함수 호출. 에러는 [현상]→[원인]→[해결책]
  구조(드랍정책 API와 동일 스타일)로 변환해 반환.
- 어드민 화면 `/admin/inventory-policy` — 현재 값·적용 대상 유저 수 표시, 입력 후 저장 클릭 시
  AlertDialog로 확인(되돌리기 어려운 일괄 작업이므로 즉시 반영하지 않음, AdminRoleToggle.tsx와
  동일 패턴). 사이드바 "정책 및 밸런스" 그룹에 진입점 추가.
- `src/types/database.generated.ts`·`database.ts`에 `inventory_policy` 테이블·
  `set_inventory_max_slots` RPC 타입 수기 추가(마이그레이션 미실행 상태이므로 `db:types` 재생성
  불가 — 배포 후 실제 생성 타입과 대조 필요).

### 주요 의사결정 / 핵심 메모
- **정책 저장 방식**: 신규 싱글톤 테이블(`inventory_policy`) 신설을 택함. `inventory` 테이블
  자체에 정책 컬럼을 얹는 대신 drop_policy/combine_policy와 동일한 별도 싱글톤 패턴을 따라
  일관성을 유지.
- **신규 유저 기본값 반영 방식**: 컬럼 `DEFAULT` 값 변경이 아니라 트리거가 정책 테이블을 읽는
  방식을 택함(티켓이 제시한 두 옵션 중 후자) — 향후 재조정 시 마이그레이션이 필요 없다.
- **원자성**: 기존 유저 일괄 UPDATE + 정책 upsert를 API 라우트에서 순차 호출하지 않고 DB 함수
  (`set_inventory_max_slots`)로 묶었다. supabase-js가 여러 테이블에 걸친 트랜잭션을 지원하지
  않아, 순차 호출 시 "정책값은 바뀌었는데 기존 유저는 반영 안 됨" 같은 부분 반영 상태가 생길 수
  있었기 때문. 다만 이 함수는 `SECURITY DEFINER`가 아니라 `SECURITY INVOKER`(기본값)로
  선언했다 — service_role이 이미 RLS를 우회하므로 DEFINER가 굳이 필요 없고, 새 DEFINER
  함수를 늘리지 않는 편이 109 마이그레이션이 정리한 보안 표면을 다시 넓히지 않는다고 판단.
- **하한 CHECK 충돌 처리**: 새 최대치보다 이미 많은 아이템을 보유한 유저가 있으면
  `used_slots_within_limit` CHECK 위반으로 전체 UPDATE가 실패하는 문제를 발견(티켓에 명시된
  요구사항은 아니었으나 실제 사용 시 반드시 마주치는 케이스). DB 함수 안에서 사전에 count로
  검사해 몇 명이 걸리는지 알려주는 예외로 바꿔 UX 가이드 3단계 구조로 노출.
