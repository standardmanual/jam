# [BadgeEngine] 배지 스키마 v5 확장 — 레벨·계열·반복 획득

> 마스터: `20260905_0026`. **이 티켓이 v5의 첫 단계다** — 여기서 정하지 않으면 아래 모든 티켓이 재작업된다.

## 배경 / 문제 정의

v5의 세 가지 신규 구조가 현재 스키마에서 **물리적으로 표현 불가능**하다.

**① 무한레벨형은 영원히 발급되지 않는다.**
`badges.rarity`는 `badge_rarity` ENUM(common/rare/epic/mystic) **NOT NULL DEFAULT 'common'**이다.
등급 없는 배지를 표현할 자리가 없고, 새 enum 값을 넣어도 `RARITY_TIER`(`src/lib/rarity.ts:22-27`)에
없는 값은 `?? 0`으로 떨어져 `badge-engine/index.ts:700`의 `(RARITY_TIER[badge.rarity] ?? 0) <= highestOwned`
에서 `0 <= 0`이 되어 **후보에서 매번 탈락**한다.

**② 반복 획득은 UNIQUE 제약이 막는다.**
`user_activity_badges_user_id_badge_id_key UNIQUE (user_id, badge_id)`
(`migrations/001_initial_schema.sql:119`, 주석 "동일 배지 중복 발급 방지").

**③ 계열 개념이 DB에 없다.**
서비스는 `badges.name` 문자열로 계열을 묶지만(`src/lib/badgeTree.ts:180-183`), 정렬 순서를 나타낼
컬럼이 없어 **배지 이름 72개를 코드에 하드코딩**하고 있다(`badgeTree.ts:34-80`, 주석에 명시).
550종에서는 유지 불가능하고, 목록에 없는 이름은 `indexOf`가 `-1`을 반환해 **그리드 맨 앞으로 튀어나온다**.

**④ 계열 정합성 트리거가 재시드를 막을 수 있다.**
`badges_family_consistency`(`migrations/128`)가 같은 `(activity_types, name)` 계열의 모든 배지에
동일한 `MEASURABLE_CONDITION_KEYS` 조합을 강제한다. 무한레벨이 레벨마다 다른 필드를 쓰면
INSERT 자체가 EXCEPTION으로 실패한다.

## 상세 요구사항

### 서비스/코드베이스 관점

**badges 테이블**
- `level INTEGER NULL` — 무한레벨형의 레벨. 등급형은 NULL
- `family_key TEXT NULL` — 계열 식별자. 이름 문자열 대신 안정적인 키
- `sort_order INTEGER NOT NULL DEFAULT 0` — 표시 순서. **하드코딩 배열 72개를 대체**
- **`rarity`를 nullable로 전환한다 (2026-09-05 확정, 대안 A)**
  - 판정 기준은 **`rarity IS NULL` 하나뿐이다** — 등급이 비어 있으면 무한레벨형.
    별도 `badge_kind` 컬럼을 두지 않는다. 두 개의 판정 기준은 서로 어긋날 수 있다
  - DB가 강제한다: `CHECK ((rarity IS NULL) = (level IS NOT NULL))`
  - **컴파일 에러가 작업 목록이다.** `badge.rarity` 타입이 `BadgeRarity | null`이 되면서
    등급을 읽는 모든 지점이 드러난다. 각 지점은 «등급 칩 대신 Lv.N 칩» 분기를 어차피 넣어야 하므로
    수정 지점이 많은 것은 비용이 아니라 누락 방지 장치다
  - ⚠️ **컴파일이 잡지 못하는 경계 3곳은 수동 점검한다** — `rarity: string`으로 느슨해져 있어
    타입이 좁혀지지 않는다: `lib/today/cards.ts:54-59`, `lib/activity-feed/index.ts:15-17`,
    `hydrate.ts:39`. 이 3곳은 **컴파일을 통과하고 화면만 틀린다**
  - 미채택: `badge_kind ENUM('graded','leveled')` 신설 — 기존 코드가 그대로 컴파일되는 대신
    레벨형에도 `rarity='common'`이 들어가, `badge_kind`를 모르는 화면이 **조용히 Common 칩을 띄운다**

**user_activity_badges — 반복 획득**
- **`earn_count` + `earn_history`로 누적한다. `UNIQUE(user_id, badge_id)`는 유지한다
  (2026-09-05 확정, 대안 B)**
  - `earn_count INTEGER NOT NULL DEFAULT 1` — 획득 횟수
  - `earn_history JSONB NOT NULL DEFAULT '[]'` — 회차별 획득 시각·근거 활동 id
  - 행 수가 그대로라 **`user_activity_badges`를 참조하는 33개 파일이 전부 무변경으로 동작한다**
    (실측 2026-09-05: `grep -rln user_activity_badges src/`)
- 미채택: `UNIQUE` 해제 + 행 누적 — 선례는 있다(`user_checkin_badge_earns`, `migrations/053`).
  그러나 활동 배지는 «보유 여부»를 행 1개 전제로 판정하는 코드가 33개 파일에 퍼져 있어
  전수 점검 비용이 이력 보존의 이득을 넘는다. 회차별 이력은 `earn_history`로 동등하게 남는다

**계열 정합성 트리거 조정**
- `check_family_condition_consistency()`가 무한레벨 계열을 어떻게 다룰지 정의
- 레벨형은 계열 내 조건 필드가 동일해야 하므로 원칙적으로 통과하나, **재시드 전 드라이런 필수**

### 리뷰 반영 — 조용한 오동작 4건 차단 (커밋 `67851e88`)

게이트 WARN·개선 리뷰가 잡은 것 중 «에러 없이 틀리게 보이는» 종류만 골라 지금 고쳤다.
넷 다 `rarity` NULL 행이 생기는 티켓 0030 시점에 결함이 되는 것들이다.

1. **`RarityBadge`가 `rarity={null}`에 "COMMON" 칩을 실제로 그렸다.** 기본값 `= 'common'`은
   `undefined`에만 걸려 명시적 `null`이 `if (rarity === 'common') return null`을 통과하고
   `config[null] ?? config.common`으로 떨어졌다. 호출부 4곳 중 `BadgeGridCard`만 `?? undefined`로
   우회하고 있었다. 가드를 DS 단일 소스에 두어 호출부가 우회를 기억할 필요를 없앴다.
   `getRarityLabel`도 nullish에 `null`을 반환하고, `.d.ts`의 props를 `Rarity | null`로 열었다.
2. **`BadgeStageRail`이 `"동네 산책러 null, 획득"`을 aria-label과 img alt로 내보냈다.** null 가드가
   라벨 *생성*만 막고 문자열 *조립*은 막지 않았다. 조각을 `filter(Boolean)`으로 빼도록 접힌
   레일·펼친 목록 양쪽을 고쳤다.
3. **`earn_count = jsonb_array_length(earn_history)` 불변식을 백필로 성립시켰다.** 그냥 두면
   최초 발급 행이 count=1인데 history 원소 0개로 출발해, 표시 단계(0038)가 배열 길이를 회차로
   읽으면 항상 1 적게 나온다.
4. **트리거 `UPDATE OF` 목록에 `level`·`rarity` 추가.** 셋뿐이던 예전 정의는 레벨형을 등급형으로
   되돌리는 UPDATE가 검사를 통째로 건너뛰게 했다. 트리거가 이미 있는 환경에서는 조건부 CREATE가
   컬럼 목록을 갱신하지 못하므로 `DROP` 후 `CREATE`로 바꿨다.

Story 2종을 추가해 1·2의 회귀를 고정했다(커밋 `5bcf2e8b`) — `RarityBadge` «등급 없음(null)»과
`BadgeStageRail` «등급 없는 계열». 후자는 `expanded`로 두어 접힌 레일과 펼친 목록 두 경로를
한 스토리에서 모두 렌더하고, 모든 aria-label·alt에 `"null"`이 새지 않음을 `play`에서 실측한다.
