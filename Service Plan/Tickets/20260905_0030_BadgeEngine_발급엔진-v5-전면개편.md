# [BadgeEngine] 발급 엔진 v5 전면 개편

> 마스터: `20260905_0026`. 선행: `20260905_0027`(스키마) · `20260905_0028`(조건 필드).

## 배경 / 문제 정의

`evaluateBadgesDetailed`의 후보 선정·게이트 판정이 «등급 4단 + 1회 보유»를 전제로 짜여 있어
v5의 네 구조를 하나도 수용하지 못한다.

| 지점 | 코드 | v5 충돌 |
|---|---|---|
| 성장 티어 | `index.ts:656-675` · `:700` | 이름당 최상위 1개만 보유 — 무한레벨·반복 불가 |
| 선행 배지 게이트 | `index.ts:703-709` | `prerequisite_badge_names` **OR 하나뿐** — 2단 게이트 표현 불가 |
| 진행 트랙 병합 | `index.ts:732-747` · `getProgressionKey():903-933` | 같은 트랙 최고값 1개만 남긴다 |
| 첫 싱크 게이트 | `index.ts:756-770` | `rarity !== 'common'` 탈락 — 등급 없는 배지에 무의미 |
| 가입 시점 | `index.ts:604` | `getActivityHistory(supabase, userId)` — **3번째 인자 `sinceDate`를 안 쓴다** |

## 상세 요구사항

### 1. 무한레벨 발급
- 후보 선정 루프(`index.ts:694-730`)를 `level` 기반 분기로 재작성
- 같은 `family_key`에서 **현재 보유 레벨 + 1**만 후보. 여러 레벨을 한 번에 넘겨도 순차 발급 또는 최상위 1개
- `RARITY_TIER` 비교를 레벨형에는 적용하지 않는다

### 2. 반복 획득
- **「발급」과 「카운터 증가」를 분리한다** — 매 회차는 `earn_count` 증가(피드 이벤트 없음),
  등급 임계값(1·5·20·50)에서만 실제 배지 발급 + 피드 기록
- 이 분리가 홍수 방지의 핵심이다. 카운터는 홍수 집계에 잡히지 않는다
- ⚠️ `23505`(중복키)를 동시 싱크 방어에 쓰는 4곳(`index.ts:825`, `sync.ts:649`,
  `itembook/checker.ts:209`, `missions/rewards.ts:115`)의 멱등 보장을 대체할 수단 필요

### 3. 2단 교차 게이트
- `condition_json`에 신규 필드 — 예: `cross_in_axis` · `cross_between_axis` · `gate_mission_badge`
- Rare→Epic은 축 내 교차(성립하는 4개 축) 또는 축 간 교차, Epic→Mystic은 축 간 교차 **AND** 미션 보상 배지
- **AND 관계를 표현할 수 있어야 한다** — 현재는 OR 배열 하나뿐
- 교차 대상은 **조건이 겹치지 않는 계열**이어야 한다. 겹치면 같은 활동으로 동시 달성돼 게이트가 자동 통과된다
  (걷기 검사 결과: 9축 중 4축만 축 내 교차 성립)

### 4. 휴식 조건
- 활동이 없는 기간을 판정하는 신규 블록. `activityFilters.ts`에 순수 헬퍼로 작성해
  **`index.ts`와 `badgeProgress.ts`가 같은 함수를 공유**하게 한다(진행률과 발급 판정이 어긋나는 사고 방지)
- **발급 시점**: 휴식은 싱크 트리거가 없으므로 **다음 활동 시 소급 판정**한다
- 역인센티브 차단: 활동이 선행되어야 성립하는 조건으로 설계(6일 연속 후 휴식 / 장거리 다음날 휴식).
  순수 공백 기반(「겨울잠」)만 쿨다운 90일

### 5. 가입 시점 앵커
- `getActivityHistory(supabase, userId, sinceDate)`의 **미사용 3번째 인자를 활성화**한다
  (`activity-history.ts:13, 20-22` — 이미 구현돼 있고 호출처 4곳이 전부 생략 중)
- 앵커: `strava_connections.created_at` 또는 `users.created_at`
- 호출처 4곳 전부 적용 — `index.ts:604` · `missions/checker.ts:119` · `sync.ts:397` · `badges/tree/page.tsx:184`
- **현재는 «그 테이블에 그것만 들어있다»는 암묵적 불변식**이라, 어드민 재동기화나 시뮬레이터가
  과거 활동을 주입하면 즉시 깨진다

### 6. 첫 싱크 게이트 재정의
- 등급 없는 배지에 `rarity !== 'common'` 판정은 무의미. 레벨형은 Lv.1만 허용하는 식으로 재정의

## 판단 (2026-09-05 확정)

### ① 반복 획득 멱등 — 조건부 원자 UPDATE

`UNIQUE(user_id, badge_id)`는 티켓 `0027`에서 유지하기로 확정됐으므로 유니크 키를 늘리는 안은
성립하지 않는다. 대신 **근거 활동 id가 이미 `earn_history`에 있으면 증가시키지 않는다**를
한 문장에 담는다:

```sql
UPDATE public.user_activity_badges
   SET earn_count   = earn_count + 1,
       earn_history = earn_history || $entry::jsonb
 WHERE user_id = $1 AND badge_id = $2
   AND NOT (earn_history @> jsonb_build_array(jsonb_build_object('strava_activity_id', $3)))
```

읽고-고치고-쓰는 왕복이 없어 동시 싱크에서 회차가 유실되지도, 이중 계상되지도 않는다.
`23505`(중복키)를 방어에 쓰던 4곳의 역할을 이 조건절이 대신한다.

**`earn_history` 상한은 200으로 둔다.** `earn_count`가 총계를 들고 있어 정보 손실이 작다.
⚠️ 상한을 넘겨 오래된 원소가 밀려나면 그 활동은 위 조건절로 막히지 않는다 — 다만 싱크는
`getProcessedStravaIds`가 이미 처리한 활동을 상위에서 걸러내므로 이 조건절은 **이중 방어**다.
둘 다 뚫리는 경로가 생기면 그때 상한을 재검토한다.

### ② 케이던스는 spm으로 환산해 보여준다 (사용자 확정)

`0029` 실측: Strava `average_cadence`는 **한쪽 발 기준**이다(달리기 중앙값 86.5 · 범위 67.9~110.2).

- **저장은 Strava 원값 그대로 둔다** — 재백필이 필요 없고, 나중에 Strava와 대조할 때 어긋나지 않는다
- **평가·표시 경계에서만 ×2한다** — 배지 조건값·진행률·어드민 표시·지표 라벨이 전부 spm으로 말한다.
  유저는 「분당 180보」를 보고, 이건 러너에게 익숙한 숫자다
- **달리기·트레일러닝에만 적용한다.** 자전거 케이던스는 rpm(크랭크 1회전)이라 한쪽 발 기준이
  아니다. ⚠️ **자전거 케이던스 실측이 0건이라 이 전제를 검증하지 못했다** — 자전거 데이터가
  들어오는 즉시 확인할 것
- 변환 지점은 **한 곳**이어야 한다. 두 곳에 두면 진행률과 발급 판정이 어긋난다(§4 휴식 조건과 같은 원칙)

### ③ `avg_watts`에 실측 파워 필터를 걸지 않는다

`0029` 실측: 파워가 있는 달리기 활동 **571건 전부** `device_watts: true`이고, 자전거는 3건 중
실측 **0건**이다. 필터를 걸면 달리기에서는 아무것도 안 걸러지고 자전거에서는 전부 걸러진다 —
의미 없는 비대칭이다. `deviceWatts`는 수집만 해 두고 판정에 쓰지 않는다.

## 선행 티켓이 확정한 전제 (20260905_0028, 2026-09-05 완료)

- **평가 구현만으로는 배지가 발급되지 않는다.** `conditionRegistry.ts`의 `evaluation`을
  `'pending'` → `'engine'`으로 **함께 뒤집어야** 한다. 안 뒤집으면 fail-closed가 계속 막는다.
- 필드를 뒤집을 때 `condition-registry.test.ts`의 해당 회귀 테스트를 **「막힘」 → 「판정됨」으로
  교체**하는 것까지가 완료 조건이다. 남겨 두면 통과하는 테스트가 거짓말을 한다.
- `evaluation`은 3상태다 — `engine`(엔진이 직접 검사) / `external`(엔진 밖 파이프라인:
  `poi_id`·`mission_reward`·`prerequisite_badge_names`) / `pending`(아무도 평가 안 함).
  v5 신규 20종과 `route`가 `pending`이다.
- **짝 필드(`pairedWith`)는 아직 아무도 강제하지 않는다.** `rest_after_streak`↔`streak_days`,
  `rest_after_long`↔`single_distance_km`는 짝이 없으면 「며칠 연속 뒤」·「무엇이 장거리인지」가
  정의되지 않는데 짝 없이 저장돼도 통과한다. 평가를 구현하는 순간 조용한 오판정이 된다 —
  **신규 20종에 한해** `findBlockingConditionKeys`에 「짝 필드 미충족」을 한 종류 더 추가하라
  (기존 25종은 카탈로그 실적이 있어 즉시 강제하면 회귀 위험이 있다).
- **`earn_history` 누적은 반드시 한 문장 원자 갱신으로 하라.** 앱 코드의 read-modify-write는
  동시 싱크에서 회차를 유실한다:
  `INSERT ... ON CONFLICT (user_id, badge_id) DO UPDATE SET earn_count = user_activity_badges.earn_count + 1,
   earn_history = user_activity_badges.earn_history || $entry::jsonb`.
  **배열 상한**도 여기서 정한다 — 반복 획득이 무한이면 수년 뒤 수백 원소가 된다.
  `earn_count`가 총계를 들고 있으므로 최근 N건만 남겨도 정보 손실이 작다(티켓 0027 개선 리뷰).
- **결산 알림·획득 연출이 레벨형을 조용히 Common으로 표시한다.** `strava/sync.ts:200`의 하드
  캐스팅 → `notifications/message.ts:240`의 `asRarity()`가 null을 `'common'`으로 고정하고,
  `message.ts:305`의 `rarityRank < epic` 게이트에서도 항상 탈락한다. payload가 JSON이라
  **타입이 잡지 못한다.** 레벨형이 실제로 발급되는 이 티켓에서 반드시 함께 다뤄야 한다.

### 티켓 0029가 넘긴 것 (2026-09-05)

- **`maxSpeedKmh`는 어뷰징 필터를 통과한 값이 아니다.** `sync.ts:699`의 차량 필터는
  `averageSpeedKmh <= vehicle_speed_filter_kmh(60)`, 즉 **평균속도** 기준이다. 자전거 활동에
  차량 이동 구간이 섞이면 평균은 통과하고 `max_speed`만 100km/h대로 남는다. 러닝의 GPS
  스파이크(순간 40km/h)도 같은 경로다. `max_speed_kmh` 평가 시 종목별 상한이나 기존
  `abusing_policy.gps_max_speed_kmh` 재사용을 검토하라 — 안 하면 0035 시딩 후
  「최고속도 배지가 이상하게 나온다」로 되돌아온다.
- **`avg_watts`는 추정 파워로도 채워진다.** 구분자 `deviceWatts`를 0029에서 함께 수집하도록
  했다(`true`=파워미터 실측). 「실측만 인정」할지 이 티켓에서 정하라.
- **`avgCadence` 러닝 원값 단위가 미확인이다.** Strava가 한쪽 발 기준(≈spm/2, 85~95)으로
  주는지 spm(180대)으로 주는지는 백필 실데이터로만 판명된다. 잘못 잡으면 「180 황금 케이던스」
  계열이 **영원히 안 나오는 배지**가 된다. 0029의 커버리지 쿼리가 이걸 함께 판정한다.
- **`CONDITION_ACTIVITY_FIELD`의 「대응 없음」은 두 가지 뜻을 겸한다.** `distance_km`·
  `elevation_gain_m`은 «누적이라 대응 없음»이지만 `same_activity: true`가 붙으면 실제로는
  단일 활동 값과 비교된다. 매핑 테이블만 보고 「활동 스칼라가 아니다」로 읽으면 이미 있는
  `same_activity` 경로를 다시 짜게 된다.
- **`elapsedTimeSec`은 수집만 하고 대응하는 조건 키가 없다.** 휴식 시간(= elapsed − moving)
  계산에 쓰려면 이 티켓에서 조건 키를 만들어야 한다.

## A묶음 실측·결정 기록 (2026-09-05)
