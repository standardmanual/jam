# [Admin] 게이트 미션 전용 관리 화면

> 마스터: `20260905_0026`. 선행: `20260905_0030`(발급 엔진 — 게이트 판정).

## 배경 / 문제 정의

v5는 **종목당 8개 × 5종목 = 미션 40개**가 Mystic·Lv.8+를 여는 열쇠가 된다.
기간형 이벤트 미션과 데이터 모델·운영 리듬이 완전히 달라 같은 화면에서 관리하면 실수가 난다.

**현재 미션 관리 화면의 한계**
- 폼이 인라인 접이식이고 별도 페이지가 없다(`MissionList.tsx:175-315`)
- `condition_json`을 **생짜 JSON 텍스트에어리어**로 입력하고 `JSON.parse` 성공 여부만 검증(`:124-129`)
- API가 `body`를 **검증 없이 그대로 insert**(`api/admin/missions/route.ts:19-34`)
- 목록 컬럼이 4개(제목/타입/완료수/상태)뿐 — **게이트 배지 컬럼·필터·검색이 전부 없다**
- 게이트 배지 연결이 `gated_badge_id` 단일 선택(`:261-276`)

**스키마에 축 개념이 없다.** `missions` 테이블(`database.generated.ts:932-985`)에
「어느 축을 여는지」를 저장할 컬럼이 없다.

**노출 규칙이 코드에 하드코딩돼 있다.**
`visibility.ts:85-114`가 `gated_badge_id` → 그 배지의 rarity tier → 유저의 **같은 이름** 배지
최고 tier를 ±1로 비교한다. v5의 «해당 축 Epic 보유 AND Mystic 미보유»는 이 규칙으로 표현할 수 없다.

⚠️ **`visibility.ts:92`의 `RARITY_TIER[rarity] ?? 0`은 등급 없는 배지를 게이트로 걸면
`0 <= 1`이 되어 `OPEN`을 반환한다 — 에러도 로그도 없이 게이팅이 꺼진다.**

## 상세 요구사항

### 스키마
- `missions.gate_axis` — 여는 축
- `missions.gate_stage` — 단계(Rare→Epic / Epic→Mystic)
- `missions.visibility_rule_json` — 노출 조건
- 또는 별도 `gate_missions` 테이블. 기간형 미션과 컬럼이 거의 겹치지 않으므로 분리도 합리적

### 화면 `/admin/gate-missions` (신규)
- **매트릭스 목록** — 축 × 단계 격자. 축별로 두 단계가 다 채워졌는지 **커버리지가 한눈에**
- **구조화 입력** — 여는 축 / 게이트 단계 / 보상 배지 / 노출 조건을 자유 JSON이 아니라 선택 UI로
- **노출 미리보기** — 유저 id를 넣으면 그 유저에게 `open`/`locked`/`hidden` 중 무엇으로 보이는지 판정.
  **현재 `visibility` 로직을 어드민에서 확인할 방법이 전혀 없다**
- **정합성 검사** — 축은 있는데 미션이 없는 구멍 / 같은 축·단계에 미션 2개 이상 /
  보상 배지가 비활성·삭제됨

### 노출 판정 재작성
- `visibility.ts:85-114`를 축·단계 기반으로 교체
- `visibility-server.ts:106-117`의 「최대 5트리×4등급=20개, 유저당 175행」 전제가 550종에서 붕괴 —

### ① `missions`에 컬럼을 더한다 — 별도 테이블을 만들지 않는다 (사용자 확정)

모든 조회에 조인을 걸어야 한다 — 컬럼 3개를 아끼려고 파이프라인을 복제하는 교환이다.

### ② 기존 게이트 미션 15개는 **폐기하고 새로 만든다** (사용자 확정)

**근거**: 그 15개가 가리키는 보상 배지는 티켓 `0035`가 카탈로그를 전량 교체하면 사라진다.
전환하려 해도 대상이 없어진다. v5는 **종목당 8개 × 5종목 = 40개**를 새로 설계한다.

⚠️ 폐기 시점은 `0035` 시딩과 맞춰야 한다 — 먼저 지우면 그동안 게이트가 열린 채로 남는다.

## 착수 전 반드시 알 것

### `visibility.ts`의 게이팅이 조용히 꺼진다

`visibility.ts:92`의 `RARITY_TIER[rarity] ?? 0`은 **등급 없는 배지(v5 레벨형)를 게이트로 걸면
`0 <= 1`이 되어 `OPEN`을 반환한다 — 에러도 로그도 없이 게이팅이 통째로 꺼진다.**
v5는 레벨형이 다수이므로 이건 «언젠가»가 아니라 `0035` 시딩 직후의 문제다.

이 저장소가 반복해 겪은 유형이다 — 마스터 티켓 B-1의 `(RARITY_TIER[badge.rarity] ?? 0) <= highestOwned`도
같은 형태였고(레벨형이 **영원히 발급되지 않던** 원인), 티켓 `0027`이 `rarityTier()`를 만들어
**`0`은 「서열의 맨 아래」가 아니라 「이 서열에 속하지 않는다」**는 뜻임을 명시했다.
같은 함수를 여기서도 쓸 것.

### 선행 티켓이 만들어 둔 것 (다시 만들지 마라)
- **배지 종류 판정** — `src/lib/badge-engine/badgeKind.ts`
- **교차 게이트 판정** — `src/lib/badge-engine/crossGate.ts`. 게이트 미션은 `gate_mission_badge`
  요구의 **대상**이다(티켓 `0030` B2). 미션 보상 배지가 그 계열에 있어야 Mystic이 열린다
- **계열 개념** — `family_key`. 미션이 여는 「축」과 배지 계열의 관계를 여기에 붙일 수 있다
- **미션 조건 키 화이트리스트** — `src/lib/missions/condition-keys.ts`(병렬 티켓 `20260905_1141`)

### 노출 판정 재작성
- `visibility.ts` — 축 경로(`gate_axis`)를 먼저 태우고, 없으면 레거시 경로로 떨어진다.
  **`RARITY_TIER[rarity] ?? 0` 제거**: `rarityTier()`로 바꾸고 **0을 「서열 밖」으로 다룬다** —
  등급 없는 배지가 레거시 게이트에 걸려 있으면 `open`이 아니라 `locked` + 경고 로그다.
  노출 규칙 형태 오류도 fail-closed(`locked`).
- 계열 요구의 형태 검증은 `crossGate.ts`의 `normalizeGateRequirement()`를 **export해 공유**한다
  (재선언 0). 게이트 미션은 `gate_mission_badge` 요구의 대상이라 두 판정이 갈리면
  「미션은 열렸는데 Mystic은 안 열리는」 상태가 된다.
- `visibility-server.ts` — 「최대 5트리×4등급=20개, 유저당 175행」 전제를 걷어내고 **모든 조회를
  페이지 끝까지** 넘긴다. 계열 보유 조회는 `familyKeyOf()` 기준(`#name:` 폴백 포함).
- 4개 진입점(목록·상세·참가 API·오늘 카드)은 그대로 같은 함수를 쓴다. `today/cards.ts`의
  컬럼 명시 `select`를 `select('*')`로 바꿔 **135 실행 전에 배포돼도 쿼리가 깨지지 않게** 했다.
