# [Infra] 유저 전체 초기화 · 액티비티 배지 정의 폐기

> 마스터: `20260905_0026`. **⚠️ 코드 배포 완료 후에 실행한다.**

## 배경 / 문제 정의

v5 전환을 위해 **유저 12명 전원과 액티비티 배지 정의 207종을 초기화**한다.
현 유저는 전부 테스트·초기 사용자이며, 모두 「최초 가입자」 경험으로 다시 시작한다.

**결정 사항**
- `public.users` + `auth.users` **전원 삭제** — 아이템 177개·포인트 14,056·팔로우 23건도 함께
- `point_treasury` **0으로 리셋**
- 배지 정의는 **액티비티 207종만 폐기** — 체크인 1,789종·아이템 1,825종은 유지
  (체크인 정의를 지우면 지도 POI 1,795개가 통째로 사라진다)
- 어드민 확보 순서는 **실행 직전 결정** — 스크립트는 두 경로를 모두 지원

## 리스크 점검 결과

유저 전삭제로 **6개 중 5개가 해소**된다.

| 상태 | 항목 |
|---|---|
| 해소 | 재발급 폭탄 — 유저가 없으니 평가가 일어나지 않는다 |
| 해소 | 프로필 피드 재합성 · 고아 스냅샷 · 포인트 드리프트 · 미션 이중지급 (FK 33개 중 **27개 CASCADE**) |
| 해소 | 고아 아이템·드랍 — `migrations/108`이 계정 탈퇴를 **이미 설계**해뒀다 |
| **존속** | **미션 게이팅 fail-open** — 배지 정의 삭제 문제라 유저와 무관 |
| 신규 | 순서 함정 — `today_cards.created_by`만 NO ACTION |
| 미결 | 어드민 확보 |

**고아 아이템은 별도 SQL이 필요 없다.**
`poi_drops.dropper_user_id`의 SET NULL은 사고가 아니라 **「드랍한 사람이 탈퇴해도 미픽업 유저 드랍은
사라지지 않는다(무기한 대기가 정책)」는 의도된 전환**이다(`migrations/108` 4항).
`inventory_items`도 하드 삭제 대신 Orphaned로 전이되고, `BEFORE DELETE ON users` 트리거
`log_orphan_custody_events`가 Orphan 이벤트를 자동 기록한다.
**어드민 「미소유 아이템배지 현황」에서 일괄 폐기·일괄 재배정**으로 정리하면 된다.

⚠️ **`custody_events`(191건)는 지우지 않는다** — 고아 판정의 후보군 축소 기반이자
유저명을 스냅샷으로 저장해 탈퇴 후에도 남아야 하는 append-only 이력이다.

⚠️ **`missions.gated_badge_id`를 찾지 못하면 `OPEN`을 반환한다**(`visibility.ts:87-90`).
하드삭제(FK SET NULL)든 소프트삭제든 결과가 같아 **미션 15개의 잠금이 전부 풀린다**.
목록·상세·**참가 API 가드**·오늘 카드 4개 진입점이 모두 열리므로
**배지 정의 삭제와 미션 정리를 같은 배포에 넣어야 한다.**

## 실행 절차

```sql
-- Phase 0. 백업
CREATE TABLE backup_users           AS SELECT * FROM public.users;
CREATE TABLE backup_badges_activity AS SELECT * FROM badges WHERE type='activity';
CREATE TABLE backup_missions        AS SELECT * FROM missions;
CREATE TABLE backup_today_cards     AS SELECT * FROM today_cards;

-- Phase 1. NO ACTION FK 해제 — 안 하면 Phase 2가 FK 위반으로 막힌다
UPDATE today_cards SET created_by = NULL WHERE created_by IS NOT NULL;   -- 현재 0건

-- Phase 2. 유저 전원 삭제 — 27개 테이블 CASCADE
DELETE FROM public.users;   -- 12명 · 배지 426 · 피드 456 · 알림 37 · 활동 872 · 팔로우 23
DELETE FROM auth.users;     -- 12개 (별도 스키마 — CASCADE 아님)

-- Phase 3. 전역 장부
UPDATE point_treasury SET total_minted = 0, total_burned = 0;   -- 컬럼명 실행 전 확인

-- Phase 4. 배지 정의 + 참조 정리 (코드 배포와 같은 시점)
UPDATE missions    SET reward_badge_ids = '{}' WHERE array_length(reward_badge_ids,1) > 0;  -- 15
UPDATE missions    SET gated_badge_id   = NULL WHERE gated_badge_id IS NOT NULL;            -- 15
UPDATE today_cards SET badge_ids        = '{}' WHERE array_length(badge_ids,1) > 0;         -- 16장
DELETE FROM badges WHERE type = 'activity';    -- 207종만

-- Phase 5. 고아 아이템 — SQL 아님. /admin/item-badges/orphaned 에서 일괄 폐기

-- Phase 6. 어드민 확보 (실행 직전 결정)
--   A안: 구글 재가입 후  UPDATE public.users SET is_admin = true WHERE email = '...';
--   B안: Phase 2 이전에 전용 계정을 만들어 is_admin 부여 후 나머지만 삭제
```

**절대 지우지 않는다** — `strava_activities`(누적 조건 평가·백필의 유일한 기반) ·
`point_transactions`·`point_wallets`(트리거가 아니라 RPC가 3중 관리, 직접 DELETE 시 잔액 드리프트) ·
체크인 배지 1,789종 · `poi.linked_badge_id` 1,795 · 아이템 배지 1,825 · `custody_events` 191

## 실행 시점

**코드 배포 완료 후.**
Supabase는 staging·프로덕션 공용 단일 DB라 DB를 지우면 즉시 프로덕션에 반영되지만 배포는 별도다.
그 시차에 **투데이 카드 16장이 빈 배지로 렌더되고 링크가 404**, **미션 15개의 게이팅이 풀린 채** 노출된다.

## 후속
- Storage `images/badges/activity/` **175MB**는 배포 안정화 후 별도 정리
- 어드민 유저 리셋 API(`api/admin/users/[id]/reset/route.ts`)의 기존 결함 —
  파생 데이터를 안 지우고 `strava_activities`를 남긴 채 `last_synced_at=NULL`로 만들어
  **재싱크가 0건 처리**된다. 별도 티켓 대상
