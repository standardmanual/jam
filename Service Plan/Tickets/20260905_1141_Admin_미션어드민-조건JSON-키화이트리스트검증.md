# [Admin] 미션 어드민 — 조건 JSON 키 화이트리스트 검증

> 선행: `20260905_0028`(조건 필드 메타 레지스트리 + fail-closed).
> 그 티켓의 「남긴 것」 표 3행 — «미션 어드민의 검증 없는 자유 JSON `condition_json`,
> 별도 티켓으로 분리(`MissionList.tsx:227`)» — 이 항목을 처리한다.

## 배경 / 문제 정의

**① fail-closed가 미션 어드민의 오타를 «영구 미달성»으로 바꿨다.**

티켓 20260905_0028이 `evaluateConditionDetailed`에 fail-closed를 도입했다. 조건 평가를
시작하기 전에 `conditionRegistry.ts`와 모든 키를 대조해, 레지스트리에 없는 키(오타)나 아직
평가 구현이 없는 키(`evaluation: 'pending'`)가 하나라도 있으면 즉시 fail한다.

미션도 같은 함수를 쓴다 — `missions/checker.ts`의 `ENGINE_DELEGATED_MISSION_TYPES`
(`streak_days`·`duration_minutes`·`elevation_gain_m`) 경로가 `MissionCondition`을
`BadgeCondition`으로 캐스팅해 넘긴다. 미션 고유 어휘(`count`·`badge_id`)는
`MISSION_ONLY_CONDITION_KEYS`로 통과시켜 뒀지만 **오타는 여전히 막힌다** — 그게 fail-closed의
목적이므로 올바른 동작이다.

**② 그런데 미션 어드민에는 그 오타를 막을 검증이 없다.**

`admin/missions/MissionList.tsx:227`이 `condition_json`을 **검증 없는 자유 JSON
텍스트에어리어**로 받는다. 저장 경로 전체에 키 검증이 한 군데도 없다:

| 층 | 배지 | 미션 |
|---|---|---|
| 어드민 폼 | `BadgeForm.tsx` 조건 빌더(레지스트리 파생 UI) | 자유 JSON textarea — `JSON.parse` 성공 여부만 확인 |
| API | `badge-validation.ts`의 `findUnknownConditionKeyError` | **없음** (`body`를 그대로 insert/update) |
| DB | CHECK 제약 `badges_condition_json_known_keys` | **없음** |

결과: 어드민이 `distnace_km`처럼 한 글자를 틀리면 저장은 성공하고, 그 미션은 **아무 에러 없이
영구 미달성**이 된다. fail-closed 도입 전에는 오타 키가 무시되고 나머지로 판정됐으므로,
그 변경이 이 입력구의 위험도를 올렸다.

**③ 허용 키 목록의 출처가 셋으로 갈려 있다.**

- `conditionRegistry.ts`의 `ALL_CONDITION_KEYS` — 배지 조건 45종 (`CONDITION_FIELDS`에서 파생)
- `checker.ts:34`의 `MISSION_ONLY_CONDITION_KEYS` — `new Set(['count', 'badge_id'])` **하드코딩**
- `types/database.ts:498`의 `MissionCondition` 타입 — 8개 필드

셋 중 어느 하나에 필드를 추가해도 나머지는 따라오지 않는다. 20260905_0028이 배지 쪽에서
없앤 «같은 목록이 여러 곳에 복제된다» 문제가 미션 쪽에 그대로 남아 있다.

**실측 (2026-09-05, 프로덕션 `missions` 45행 · 조건 조합 9종)**

| mission_type | 사용 중인 키 | 건수 |
|---|---|---|
| `distance` | `activity_type`, `distance_km` | 9 |
| `duration_minutes` | `activity_type`, `duration_minutes` | 9 |
| `item_collect` | `badge_id` | 6 |
| `activity_count` | `count` | 5 |
| `activity_count` | `activity_type`, `count` | 5 |
| `checkin` | `poi_id` | 4 |
| `elevation_gain_m` | `activity_type`, `elevation_gain_m` | 3 |
| `streak_days` | `activity_type`, `streak_days` | 3 |
| `distance` | `distance_km` | 1 |

- 전 미션이 쓰는 키는 **8종**뿐이고 전부 `MissionCondition`에 선언돼 있다. 오타로 깨진 미션은 **0건**
- 엔진 위임 타입(fail-closed 경로)은 **15건**(`duration_minutes` 9 + `elevation_gain_m` 3 +
  `streak_days` 3) — 티켓 0028이 적은 「15건」 그대로다
- `evaluation: 'pending'`인 키를 쓰는 미션도 **0건**
- 같은 mission_type이라도 `activity_type` 유무로 조합이 갈린다(`activity_count`·`distance`) —
  필터 키는 선택이므로 픽스처에 둘 다 넣는다

> 초판에 「74건 / 7개 조합 / 엔진 위임 30건」으로 적었던 것은 집계 오류였다
> (`lateral jsonb_object_keys`가 미션 한 건을 키 개수만큼 행으로 늘렸다). 위 값이 실측이다.

즉 **지금 고장난 것은 없고, 다음 입력 실수를 막는 예방 작업**이다.

## 상세 요구사항

### 서비스/코드베이스 관점

**1. 미션 조건 허용 키의 단일 출처를 만든다 (이 티켓의 핵심)**

- `MISSION_ONLY_CONDITION_KEYS`의 하드코딩을 없애고 **`MissionCondition` 타입에서 파생**시킨다.
  `conditionRegistry.ts`가 `AssertAllConditionKeysCovered`로 쓰는 컴파일 타임 단언 패턴을
  그대로 따른다 — `MissionCondition`에 필드를 추가했는데 그게 배지 레지스트리에도 없고
  미션 고유 키 목록에도 없으면 **컴파일 에러**가 나야 한다.
- 허용 키 = `ALL_CONDITION_KEYS` ∪ 미션 고유 키. 이 합집합을 한 곳에서 export하고,
  `checker.ts`의 fail-closed 통과 목록과 신규 저장 검증이 **같은 값을 참조**한다.
  두 곳이 서로 다른 목록을 들면 «저장은 되는데 평가에서 막힌다»(또는 그 반대)가 다시 생긴다.
- 배치 위치는 구현자가 정하되, `checker.ts`(서버 전용 의존 있음)를 API에서 통째로 끌어오지
  않도록 주의한다 — 20260904_0631의 게이트 리뷰 1차 FAIL이 같은 종류의 전이 의존 사고였다.

**2. 미션 저장 API에 키 검증을 붙인다**

- `POST /api/admin/missions`와 `PATCH /api/admin/missions/[id]` 양쪽. 지금은 둘 다
  `body`를 그대로 Supabase에 넘긴다.
- `badge-validation.ts`의 `findUnknownConditionKeyError`와 **같은 패턴**을 따른다
  (검증 함수는 순수 함수로 분리 → 라우트는 400 + 한국어 메시지 반환).
- PATCH는 부분 갱신이라 `condition_json`이 body에 없을 수 있다 — 그때는 검증을 건너뛴다
  (기존 값을 건드리지 않는 갱신을 막으면 안 된다).
- `condition_json`이 객체가 아닌 경우(배열·스칼라·null)도 방어한다. 자유 textarea라
  `JSON.parse('[1,2]')`가 그대로 통과해 들어올 수 있다.

**3. `evaluation: 'pending'` 키는 엔진 위임 타입에서 저장을 막는다**

- 대상: `ENGINE_DELEGATED_MISSION_TYPES`(`streak_days`·`duration_minutes`·`elevation_gain_m`).
  이 타입만 `evaluateConditionDetailed`를 타므로 pending 키가 곧 영구 미달성이 된다.
- 그 외 타입(`distance`·`activity_count`·`checkin`·`item_collect`)은 `progressValue >= target`
  경로라 fail-closed에 걸리지 않는다. 다만 pending 키를 넣어도 **아무 효과가 없다**는 점은
  같으므로, 막지는 않되 어떻게 알릴지는 구현 계획에서 정한다.
- 선례 참조: 티켓 20260904_1426은 「저장은 막지 않고 배너로 고지」를 택했다. 그 티켓의 대상은
  «발급은 되는데 화면에 진행률이 안 그려지는» 경우라 저장을 막을 이유가 없었지만, 이번 건은
  «저장하면 그 미션이 영원히 달성되지 않는» 경우다 — **엔진 위임 타입에 한해 막는 쪽이 맞다.**
  둘의 차이를 티켓 완료 기록에 남긴다.

**4. 어드민 폼이 API 에러를 실제로 보여주게 한다 (필수)**

`MissionList.tsx`의 `handleSave`가 `await fetch(...)` 후 **응답을 전혀 확인하지 않고**
`cancelForm()` + `router.refresh()`를 호출한다. 이대로면 API에 400을 추가해도 어드민 화면은
«저장됐다»처럼 보이고 폼이 닫힌다 — 검증을 붙이는 의미가 사라진다.
`res.ok`가 아니면 서버 메시지를 `conditionError`(이미 있는 상태)에 넣고 폼을 유지한다.

> 이 수정은 이번 검증이 사용자에게 도달하기 위한 최소 조건이므로 범위 안이다.
> 다만 `condition_json` 입력구를 배지처럼 **구조화된 조건 빌더**로 바꾸는 것은 범위 밖이다.

### UI/UX 관점

- 에러 문구는 `Service Plan/Specs/UX_WRITING_GUIDELINE.md` 기준
  ([현상] → [원인] → [해결책] 3단계, 해요체)으로 작성한다.
- 배지 쪽 문구(「condition_json에 엔진이 모르는 필드(...)가 있습니다」)를 그대로 복사하지 않는다
  — 미션 어드민 사용자에게 「엔진」은 낯선 말이고, 오타 교정이라는 해결책이 문구에 없다.
- pending 키 차단 문구는 «필드가 잘못됐다»가 아니라 «아직 판정이 준비되지 않았다»는 사실과
  그래서 미션이 달성되지 않는다는 결과를 함께 알린다.

### 어드민 예외 규칙

`admin` 유형이므로 MODULAR 디자인 시스템 탐색·재사용 판정(1.5단계)을 생략한다
(jam-work 라우팅 규칙). 개선 리뷰도 생략되는 라이트 파이프라인이다.

## 테스트 요구사항

- 오타 키(`distnace_km`) → 거부, 에러 메시지에 문제 키가 나온다
- 미션 고유 키(`count`·`badge_id`) → 통과 (배지 레지스트리에 없지만 허용)
- 배지 조건 키(`distance_km`·`activity_type`·`streak_days` 등) → 통과
- 엔진 위임 타입 + pending 키 → 거부 / 비-엔진위임 타입 + pending 키 → 정한 정책대로
- `condition_json` 부재(PATCH 부분 갱신) → 통과
- `condition_json`이 배열·스칼라 → 거부(터지지 않는다)
- **프로덕션 45건의 실제 조건이 전부 통과** — 위 실측 표의 9개 조합을 픽스처로 넣는다
- `MissionCondition`에 필드를 추가했을 때 키 목록 누락이 컴파일 에러로 드러나는지
  (타입 단언이 실제로 작동하는지 확인)

### pending 키 정책 — 20260904_1426과의 차이

| | 20260904_1426 (배지 지표 라벨) | 이번 티켓 (미션 pending 키) |

| 저장하면 벌어지는 일 | 발급은 정상, 화면에 진행률만 안 그려짐 | 엔진 위임 타입이면 **그 미션이 영원히 달성되지 않음** |

경로라 pending 키가 있어도 판정이 막히지 않는다 — 대신 아무 효과도 없으므로 어드민 폼에서
조건 JSON 아래 고지 문구로 알린다(저장은 그대로 된다).

### 주요 의사결정 / 핵심 메모

**티켓 요구 밖이지만 범위에 넣은 것 — `MissionList.handleSave`의 응답 확인.**
`await fetch(...)` 뒤 응답을 보지 않고 폼을 닫고 있었다. 이걸 그대로 두면 API에 400을
붙여도 어드민 화면은 「저장됨」처럼 보인다 — 이번 검증이 사용자에게 도달하는 최소 조건이라
범위 안으로 판단했다. 반면 `condition_json` 입력구를 배지처럼 구조화된 조건 빌더로 바꾸는
것은 범위 밖으로 두었다.

**실측 정정.** 티켓 초판의 「74건 / 7개 조합 / 엔진 위임 30건」은 집계 오류였다
(`lateral jsonb_object_keys`가 미션 한 건을 키 개수만큼 행으로 늘렸다). 실제는
**45행 / 9개 조합 / 엔진 위임 15건**이고, 티켓 0028이 적은 「15건」이 맞았다. 게이트 리뷰가
실데이터를 직접 조회해 이 불일치를 잡았다. 픽스처에 빠져 있던 두 조합
(`activity_count {count}`·`distance {distance_km}` — 둘 다 `activity_type` 없음)을 추가했다.

**방어선은 API·폼 층까지다.** `missions.condition_json`에는 배지의
`badges_condition_json_known_keys` 같은 DB CHECK 제약이 없다. service_role 스크립트나 MCP
직접 insert는 여전히 오타 키를 넣을 수 있다 — 티켓이 정한 범위 그대로다.
