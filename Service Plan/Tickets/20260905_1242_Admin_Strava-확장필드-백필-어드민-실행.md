# [Admin] Strava 확장 필드 백필 — 어드민 실행 경로

> 선행: `20260905_0029`(확장 필드 수집·백필 로직). 마스터: `20260905_0026`.

## 배경 / 문제 정의

티켓 `20260905_0029`가 백필 로직(`src/lib/strava/backfill.ts`)과 CLI 스크립트를 만들었고
게이트 리뷰 PASS를 받았다. **그런데 이 머신에서 돌릴 수 없다.**

`strava_connections`의 토큰이 `ENCRYPTION_KEY`로 암호화돼 있는데(`src/lib/utils.ts:77`),
그 키가 로컬 `jam-web/.env.local`에 없다. Vercel에는 있으나 **Secret 타입이라
`vercel env pull`로 내려받을 수 없다** — 실제 시도 결과 「21 Secret values cannot be pulled」와
`[SENSITIVE]` 플레이스홀더만 받았다.

**사용자 결정(2026-09-05): 어드민 API 라우트로 만들어 서버에서 돌린다.**

### 프로덕션에서만 돌아간다 — 설계대로다

**어드민은 원래 프로덕션에만 있다.** staging에 어드민 인증·복호화 키가 없는 것은 환경 누락이
아니라 의도된 구성이다. staging은 프로덕션과 **DB를 공유**하므로, 거기서 어드민이 열리면
실데이터를 건드릴 경로가 하나 더 생긴다. 그래서 이 기능은 처음부터 «프로덕션 배포 후
프로덕션 어드민에서 실행»이 정상 경로다.

환경변수 실측(2026-09-05):

| 환경변수 | jam (프로덕션) | jam-stage |
|---|---|---|
| `ENCRYPTION_KEY` | 있음 | **없음** |
| `ADMIN_EMAILS` | 있음 | **없음** |
| `GOOGLE_CLIENT_ID` / `SECRET` | 있음 | **없음** |
| `STRAVA_CLIENT_ID` / `SECRET` | 있음 | 있음 |
| `SUPABASE_SERVICE_ROLE_KEY` | 있음 | 있음 |

즉 staging에서는 어드민 로그인도 토큰 복호화도 되지 않는다 — **의도한 대로다.**
이 기능은 프로덕션 배포(`/jam-ship`) 후 프로덕션 어드민에서 실행한다.

> 같은 이유로 staging에서는 Strava 동기화가 토큰 복호화 단계를 넘지 못한다. 이것도
> 결함이 아니라 «staging이 실유저 토큰을 다루지 않는다»는 안전 속성이다.

## 상세 요구사항

### 서버리스 실행 시간 제약이 설계를 정한다

이 저장소의 무거운 라우트는 전부 `export const maxDuration = 60`이다
(`api/strava/sync`·`api/cron/notifications`·`api/admin/badge-image/generate`).

`0029`의 CLI 기본값(요청 예산 90 · 간격 1,500ms)은 **대기 시간만 135초**라 60초에 안 들어간다.
→ **유저 1명 = 1회 호출**로 쪼갠다. 실측 기준 유저 10명 / 활동 873건이라 유저당 약 87건이고,
목록 엔드포인트가 `per_page=200`이므로 유저당 **1~2회 호출**이면 끝난다(대기 3초 남짓).

### API 라우트
- `POST /api/admin/strava-backfill` — 어드민 세션 인증(`getAdminUser()`)
- 입력: `{ userId: string, apply?: boolean }`. `apply` 기본 `false`(미리보기)
- **`src/lib/strava/backfill.ts`의 `backfillExtendedFields`를 그대로 재사용한다.**
  이미 게이트 리뷰를 통과한 코드다 — 로직을 다시 구현하지 마라
- `maxDuration = 60`, 요청 예산은 유저 1명에 맞춰 낮게

### 어드민 화면
- 대상 유저 목록 + 유저별 «저장된 활동 수 / 확장 필드 보유 수 / 마지막 백필 시각»
- 유저별 «미리보기» → «적용» 2단계. 결과(대조·갱신·요청 수)를 표시
- 어드민 UI는 **shadcn/ui 표준**을 따른다 (`components/ui`) — 네이티브 select 금지

### 실행 직후 측정 (이게 이번 작업의 목적이다)
`0039`가 유저를 전원 삭제하면 이 실데이터는 사라진다. **`0035` 임계값 설계의 유일한 실측
근거가 백필 직후 한 번의 측정이다.** 종목별 커버리지·분포를 화면이나 로그로 남긴다.

특히 **`avgCadence` 러닝 원값이 90대(한쪽 발 기준)인지 180대(spm)인지** — 컨텐츠에 이미
「180 황금 케이던스」 계열이 있어 잘못 잡으면 **영원히 안 나오는 배지**가 된다.

## 하지 않는 것
- 배지 평가·아이템 드랍·미션 판정·소식·피드 — 어느 것도 트리거하지 않는다. 돌리는 순간 배지 홍수
- `last_synced_at` 갱신
- `processed_via` 덮어쓰기 (`0029`에서 제거했다 — 표시는 `normalized.extendedBackfilledAt`)
- 활동당 Detailed 호출 (`splits_metric`은 v5 1차 제외, `0029` 판단 ①)

## 잔여 이슈
- 미리보기 모드에서도 만료된 access_token은 갱신·저장된다(Strava 호출에 유효 토큰이 필요하고,
  저장하지 않으면 회전된 refresh_token 유실로 유저 연동이 끊긴다). 화면에 이 사실을 알린다

### 설계 판단
1. **요청 예산 6회 · 간격 1,000ms.** 최악의 대기 총합이 5초라 60초 안에 든다(CLI 기본값은 135초).
   6회 = 활동 1,200건까지 커버 — 실측 유저당 약 87건이라 실제로는 1회로 끝난다.
2. **집계 함수 하나를 화면 최초 렌더와 실행 직후 응답이 공유한다.** 두 숫자가 서로 다른 방식으로
   계산되면 「돌렸는데 얼마나 채워졌나」를 판단할 수 없다.
3. **케이던스는 중앙값만이 아니라 최소·최대까지 낸다.** 러닝 원값이 90대(한쪽 발)인지
   180대(spm)인지 가르는 게 이번 측정의 핵심이고, 중앙값 하나로는 표본이 섞였을 때 못 잡는다.
4. **연결은 있는데 활동이 0건인 유저도 목록에 남긴다.** 목록에서 사라지면 「백필할 게 없는 유저」와
   「Strava 동기화가 안 된 유저」를 구분할 수 없다.
5. **대상 유저의 `strava_connections` 존재를 라우트에서 먼저 확인한다.** `backfillExtendedFields`는
   대상이 0명이면 조용히 성공으로 끝나는데, 화면에서는 그게 「실행됨」으로 보인다.
