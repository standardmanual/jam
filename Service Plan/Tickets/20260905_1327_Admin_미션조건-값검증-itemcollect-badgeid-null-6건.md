# [Admin] 미션 조건 값 검증 — `item_collect` 6건이 `{"badge_id": null}`로 달성 불가

> 선행: `20260905_1141`(미션 조건 **키** 화이트리스트 검증). 그 티켓이 남긴 잔여 이슈 2번을
> 분리한다. 1141은 «키»만 검증했고, 이 티켓은 «값»을 다룬다.

## 배경 / 문제 정의

**프로덕션의 `item_collect` 미션 6건 전부가 `{"badge_id": null}`이다.** 목표 배지가 지정되지
않아 구조적으로 영원히 달성되지 않는다. 6건 모두 **현재 활성**이고, **참가자 19명**이
붙어 있는데 **완료자는 0명**이다.

### 왜 영원히 달성되지 않는가 (코드 확인)

`missions/checker.ts`의 두 함수가 갈린다.

| 함수 | `item_collect`일 때 |
|---|---|
| `getTarget()` (438행) | 달성형이므로 **항상 `1`** |
| `calculateProgress()` (467~469행) | `condition.badge_id && ownership.ownedBadgeIds.has(...) ? 1 : 0` |

`badge_id`가 `null`이면 `&&`의 좌변이 falsy라 `has()`를 부르지도 않고 **`0`**을 돌려준다.
판정은 `progressValue >= target` = `0 >= 1` = **항상 false**. 유저가 어떤 배지를 갖고 있든
무관하다. 참가자 19명 / 완료 0명이 이 판정을 실측으로 뒷받침한다.

### 왜 이렇게 됐는가

`jam-web/supabase/seed_phase13_missions_30.sql`이 배지를 **이름으로 조회해** 넣는다:

```sql
jsonb_build_object('badge_id',
  (SELECT id FROM public.badges WHERE type = 'item' AND name = '다운 애로우' LIMIT 1))
```

그 시드 파일은 이 위험을 **주석으로 이미 경고하고 있었다** (6~8행):

> item_collect / reward_badge_ids look up badges by name (from migration
> 012_item_badges_100.sql). If a name was changed since, that lookup returns NULL
> and the field stays empty for that row.

서브쿼리가 `NULL`을 돌려주면 `jsonb_build_object`는 `{"badge_id": null}`을 만들고 **INSERT는
그대로 성공한다.** 경고는 남겼지만 막는 장치가 없었다.

### 원래 배지는 복구할 수 없다 — «재지정»이 필요하다

시드가 참조한 6종(`다운 애로우`·`레인보우 하트`·`오픈 키`·`아이 오브 더 선`·
`굿 바이브스 온리`·`러브 세이브`)은 **소프트 삭제된 행 중에도 없다.** 아이템 배지 카탈로그가
통째로 교체됐다.

**실측 (2026-09-05, 프로덕션)**

- 아이템 배지 3,600행 중 **3,564행이 소프트 삭제** — 살아 있는 것은 **36종**
- 살아 있는 36종은 전부 `rarity = 'common'`이고, 이름이 다른 세계관이다
  (「구겨진 배달 영수증」·「나침반이 가리키는 다른 우주」 계열)
- 미션 제목이 광고하는 **`Epic`·`Mystic` 등급 아이템 배지는 현재 카탈로그에 존재하지 않는다**

| 미션 제목 | 참가자 | 완료 | 보상 포인트 |
|---|---|---|---|
| '굿 바이브스 온리' Epic 배지 획득하기 | 4 | 0 | 300 |
| '러브 세이브' Mystic 배지 획득하기 | 3 | 0 | 500 |
| '아이 오브 더 선' Mystic 배지 획득하기 | 3 | 0 | 500 |
| '다운 애로우' 배지 획득하기 | 3 | 0 | 30 |
| '레인보우 하트' 배지 획득하기 | 3 | 0 | 50 |
| '오픈 키' 배지 획득하기 | 3 | 0 | 40 |

즉 `badge_id` 하나를 채우는 작업이 아니다. 제목·설명·보상 포인트가 전부 없어진 등급 체계를
전제하고 있어 **컨텐츠 판단이 먼저 필요하다.**

### 왜 6주간 아무도 몰랐는가

- 어드민 미션 목록(`MissionTable.tsx`)은 **`condition_json`을 표시하지 않는다.** 편집 폼을
  열어 JSON을 눈으로 읽는 것 말고는 이 상태를 볼 방법이 없다
- 달성형(`item_collect`·`checkin`)은 진행률 개념이 없어(`MISSION_PROGRESS_UNIT`이 빈 문자열)
  「0%에서 멈춰 있다」는 신호조차 나오지 않는다
- 미션 진행도 마일스톤 소식(#20)도 달성형은 제외 대상이라 알림이 발생하지 않는다
- 티켓 `20260905_1141`이 붙인 검증은 **키**만 본다. `badge_id`는 허용 키이므로 값이 `null`이든
  통과한다 (거기서 막으면 이 6건의 수정 저장이 전부 거부되므로 의도적으로 통과시켰다)

**다른 타입에는 같은 문제가 없다** — 미션 45건 전수 조사 결과 조건 값이 `null`인 것은
`item_collect`의 `badge_id` 6건이 유일하다(`checkin`의 `poi_id` 4건은 모두 값이 있다).

## 상세 요구사항

### ① 컨텐츠 결정 (선행 — 이것부터 정해야 나머지가 정해진다)

세 갈래 중 하나를 사용자가 정한다. **구현자가 임의로 고르지 않는다.**

| 안 | 내용 | 고려사항 |
|---|---|---|
| A. 폐기 | 6건을 종료 처리(`ends_at`을 과거로) 또는 삭제 | 참가자 19명의 참가 기록을 어떻게 할지 함께 정해야 한다 |
| B. 재지정 | 살아 있는 36종 중에서 다시 고르고 제목·설명·보상을 새로 쓴다 | 36종이 전부 `common`이라 500P 보상과 등급 문구가 성립하지 않는다 — 사실상 미션 재작성 |
| C. 보류 | 티켓 `20260905_0035`(v5 카탈로그 550종 시딩) 이후로 미루고 그때 함께 정리 | 그때까지 참가자 19명은 달성 불가 미션을 계속 보게 된다 |

> `20260905_0039`가 유저를 전원 삭제할 예정이라는 점도 판단 재료다 — 참가 기록 19건의
> 처리 부담이 그 시점에 사라진다면 C의 비용이 낮아진다. 착수 시 0039·0035의 현재 상태를
> 먼저 확인한다.

### ② 재발 방지 — 미션 조건 «값» 검증 (컨텐츠 결정과 독립적으로 진행 가능)

`20260905_1141`이 만든 `lib/missions/condition-keys.ts`의 `checkMissionCondition()`을
확장하거나 그 옆에 값 검증을 둔다. **같은 파일의 단일 출처 원칙을 깨지 않는다.**

- **미션 타입별 필수 키와 그 값의 유효성을 검증한다.** 타입별 필수 키는 `getTarget()`·
  `calculateProgress()`가 실제로 읽는 키에서 파생시킨다 — 새로 목록을 적으면 그 둘과
  갈라진다(1141이 없앤 문제를 다시 만드는 셈).
  - `item_collect` → `badge_id`가 있고 `null`이 아니고 UUID 형태여야 한다
  - `checkin` → `poi_id` 동일
  - `distance`·`activity_count`·`streak_days`·`duration_minutes`·`elevation_gain_m` →
    대응 수치 키가 있고 0보다 커야 한다 (`?? 0` 폴백이 목표를 0으로 만들면 **즉시 달성**이
    되는 반대 방향 사고가 난다 — 함께 막는다)
- **기존 6건의 수정 저장을 막지 않도록 주의한다.** 어드민이 이 미션을 고치러 폼을 열었을 때
  저장이 거부되면 복구 자체가 불가능해진다. 「저장하려는 값」을 검증하는 것이지
  「이미 저장된 값」을 막는 게 아니다 — 새 값이 유효하면 통과해야 한다.
- 존재하지 않는 배지·POI를 가리키는 UUID까지 볼지(참조 무결성)는 구현 계획에서 정한다.
  형태 검증만으로는 「형식은 맞는데 없는 배지」를 놓친다. DB 조회가 필요하므로 순수 함수가
  아니게 되는 트레이드오프가 있다 — 라우트 층에서 별도로 확인하는 방식도 검토한다.

### ③ 어드민 가시성

- 미션 목록(`MissionTable.tsx`)에서 조건이 깨진 미션을 알아볼 수 있게 한다. 최소한
  「목표 미지정」 같은 표시가 목록에 보여야 한다 — 지금은 편집 폼을 열어야만 알 수 있다.
- 표시 판정은 ②의 검증 함수를 그대로 재사용한다(별도 판정 로직을 만들지 않는다).
- 문구는 `Service Plan/Specs/UX_WRITING_GUIDELINE.md` 기준.

### ④ 시드 파일의 조용한 실패 차단

`seed_phase13_missions_30.sql`은 1회성 시드라 다시 돌지 않지만, **같은 패턴이 재사용된다.**
앞으로 이름 조회로 `condition_json`을 만드는 시드는 조회 실패 시 INSERT가 실패하도록 쓴다
(`jsonb_build_object` 앞에서 서브쿼리 결과를 확인하거나, `NOT NULL` 제약을 거는 방식).
기존 시드 파일은 이미 실행된 이력이므로 수정하지 않고, 규약을 문서에 남긴다.

### 어드민 예외 규칙

`admin` 유형이므로 MODULAR 디자인 시스템 탐색·재사용 판정(1.5단계)을 생략한다.

## 구현 계획

착수 순서:

1. `20260905_0035`·`20260905_0039`의 현재 상태를 확인하고 ①을 사용자에게 확인받는다
2. ②(값 검증)를 먼저 구현한다 — ①의 결과와 무관하게 필요하고, ①의 데이터 수정을
   저장 경로로 처리한다면 그 검증이 먼저 있어야 한다
3. ③(어드민 가시성)
4. ①의 결정에 따른 데이터 처리. SQL 파일로 남기고 실행은 사용자 승인 후

영향 범위:

```
jam-web/src/lib/missions/condition-keys.ts        값 검증 추가 (키 검증과 같은 파일)
jam-web/src/lib/missions/checker.ts               필수 키 파생의 출처 (getTarget/calculateProgress)
jam-web/src/app/api/admin/missions/route.ts       POST — 값 검증 연결
jam-web/src/app/api/admin/missions/[id]/route.ts  PATCH — 값 검증 연결
jam-web/src/app/admin/missions/MissionTable.tsx   목록에 깨진 조건 표시
jam-web/src/lib/missions/__tests__/               회귀 테스트
jam-web/supabase/seed_*.sql                       ①의 결정에 따른 데이터 수정 (실행은 승인 후)
```

## 테스트 요구사항

- `item_collect` + `{"badge_id": null}` → 거부 / 유효 UUID → 통과
- `checkin` + `{"poi_id": null}` → 거부
- 수치 타입 + 목표 0 또는 음수 → 거부 (즉시 달성 사고 방지)
- 수치 타입 + 키 자체 부재 → 거부 (`?? 0` 폴백이 목표를 0으로 만든다)
- **기존 6건을 유효한 값으로 고치는 저장은 통과한다** (복구 경로를 막지 않는다)
- 필수 키 목록이 `getTarget()`·`calculateProgress()`가 읽는 키와 어긋나면 드러나는 장치
  (컴파일 타임 단언 또는 테스트)
- 프로덕션 45건 중 나머지 39건은 그대로 통과 (`item_collect` 6건만 걸린다)
