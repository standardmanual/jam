### 2. staging Strava 연동이 깨져 있다 — **원인 2개 중 1개 해소, 1개 미해결(보류)**

콘솔 에러:
```
redirect_uri=https%3A%2F%2Fjam-stage.vercel.ap%2Fapi%2Fstrava%2Fcallback
```
**`jam-stage.vercel.ap`** — `.app`이 아니다. Vercel `jam-stage` 프로젝트의
`NEXT_PUBLIC_BASE_URL`에 오타가 있었다(`src/app/api/strava/auth/route.ts:19`가 그대로 쓴다).
코드 문제가 아니라 **환경변수 설정 문제**였다.

#### 왜 오타 수정만으로는 안 됐나

`jam-stage.vercel.app`으로 고쳐도 Strava가 **400**을 준다. Strava 앱의 Authorization
Callback Domain 칸은 **하나뿐이고 프로덕션 `j-a-m.app`이 차지**하고 있어서, 다른 도메인을
추가 등록할 수 없다.

실측으로 Strava의 매칭 규칙이 **진짜 서브도메인까지 허용**한다는 걸 확인했다:

| `redirect_uri` 호스트 | Strava 응답 |
|---|---|
| `j-a-m.app` | 302 (수락) |
| `stage.j-a-m.app` | 302 (수락) |
| `zzz.j-a-m.app` | 302 (수락) |
| `evil-j-a-m.app` | 400 (거부 — 접두 문자열 일치가 아니다) |
| `jam-stage.vercel.app` | 400 (거부) |

`*.j-a-m.app` 와일드카드 DNS가 이미 Vercel을 가리키고 있어 추가 DNS 작업도 없었다.

#### 조치 (사용자 수행)

1. Vercel `jam-stage` 프로젝트에 도메인 **`stage.j-a-m.app`** 추가 (기존
   `jam-stage.vercel.app`은 여기로 리다이렉트된다)
2. `NEXT_PUBLIC_BASE_URL` 을 `https://stage.j-a-m.app` 으로 변경
3. 재배포 (`NEXT_PUBLIC_*`은 빌드 시점에 코드에 구워지므로 값만 바꾸면 반영되지 않는다)

#### 검증 (2026-09-06 11:30 실측)

- `https://stage.j-a-m.app/api/dev-login` → 307, staging 앱 서빙 정상
- `https://jam-stage.vercel.app/` → 307 → `https://stage.j-a-m.app/` 리다이렉트
- `/api/strava/auth` Location 헤더:
  `…redirect_uri=https%3A%2F%2Fstage.j-a-m.app%2Fapi%2Fstrava%2Fcallback…`
- 그 URL에 대한 Strava 응답: **302** (`/login`으로 유도 — 수락된 것)
- 옛 값 `jam-stage.vercel.app`로 같은 요청: **400** (대조군)
- `/api/strava/callback` → 307 → `https://stage.j-a-m.app/profile?strava=error&reason=missing_params`
  (code 없이 호출한 정상 반응. 콜백도 새 도메인으로 되돌아온다)

> **함정 기록** — 도메인 교체 직후 브라우저로 확인하면 **옛 `redirect_uri`가 그대로 보인다.**
> `/api/strava/auth`가 307을 주고 브라우저가 그 리다이렉트를 캐시하기 때문이다. 서버가 실제로
> 무엇을 내보내는지는 `curl`로 `Location` 헤더를 직접 읽어야 한다. 이 캐시 때문에 「재배포했는데
> 안 고쳐졌다」고 오판할 뻔했다.

#### 여기까지가 1차 원인 — 그런데 여전히 실패한다

`redirect_uri`는 고쳐졌고 Strava도 수락하지만, **콜백이 서버에서 크래시**한다.
런타임 로그(2026-09-06 02:33, `dpl_FG6uyX…`):

```
GET /api/strava/callback 307 [error/serverless]
[JAM! Strava] 콜백 처리 오류: TypeError: The first argument must be of type
string or an instance of Buffer, ArrayBuffer, or Array or an Array-like Object.
Received undefined   { code: 'ERR_INVALID_ARG_TYPE' }
```

발생 지점은 `src/lib/utils.ts:77`이다.

```ts
const key = Buffer.from(process.env.ENCRYPTION_KEY!, 'hex')
```

`ENCRYPTION_KEY`가 `undefined`면 `Buffer.from(undefined, 'hex')`가 **정확히 이 예외**를 던진다.
`!`(non-null 단언)가 타입 검사를 통과시켜 런타임까지 숨겨져 있었다.

교차 확인:

| 확인 | 결과 |
|---|---|
| `589132427_stage`의 `strava_connections` 행 | **없음** — 2단계(암호화)에서 죽어 3단계(upsert)까지 못 갔다 |
| 프로덕션 전체 연동 | 6건 전부 형식 정상 → `jam` 프로젝트에는 키가 있다 |
| 빈 문자열 가능성 | 아니다. 빈 값이면 `Invalid key length`가 난다. "Received undefined"는 **변수 부재**다 |

사용자가 키를 넣고 재배포(`dpl_BESo3we…`, 02:43 반영)했으나 **여전히 실패**한다.
2026-09-06 사용자 판단으로 **여기서 중단하고 기록만 남긴다.**

남은 가설 두 가지 — 다음에 재개할 때 이 순서로 확인한다:
1. **스코프 문제**: `jam-stage`는 `staging` 브랜치를 자기 "Production" 환경으로 매핑한다.
   Preview에만 넣으면 잡히지 않는다
2. **값 불일치**: Supabase가 staging·프로덕션 **공용 단일 DB**라, 키를 새로 발급하면
   기존 프로덕션 연동 6건을 staging이 전부 복호화하지 못한다. 반드시 `jam` 프로젝트의

가장 가벼운 API(`/api/badges/recent-earned`)조차 워밍 후 **0.71초**다 — 하는 일은
`getUser` + 피드 1건 조회뿐인데.

미들웨어(Edge)는 87ms로 빠르다. 즉 **Node 서버 컴포넌트/라우트 안에서만** 이 비용이 난다.

#### 관측된 구조적 사실

`supabase.auth.getUser()`가 요청 한 번에 **최소 3번** 호출된다. 각각 Supabase Auth로
나가는 별도 HTTPS 왕복이고, React `cache()`로 묶여 있지 않아 중복 제거가 되지 않는다.

| 호출 지점 | 위치 |
|---|---|
| 미들웨어 | `src/proxy.ts:39` |
| 레이아웃 | `src/app/(main)/layout.tsx:14` |
| 각 페이지 | 예: 홈 `page.tsx:30`, 트리·배지 등 전부 |

전 저장소에서 `auth.getUser()` **60회**, `await createClient()` **57회**다.

다만 이것만으로 0.7초가 설명되지는 않는다 — 미들웨어의 `getUser`는 실측 **~25ms**다
(정적 `/login`을 쿠키 유무로 비교: 75ms → 87~106ms). 3회면 75ms 수준이어야 한다.

#### 결론과 다음 단계

**여기서부터는 서버 사이드 계측 없이는 더 쪼갤 수 없다.** 밖에서 잴 수 있는 축
(네트워크·DB·콜드스타트·함수기동)은 전부 배제됐고, 남은 ~630ms는 함수 내부에 있다.

다음 단계는 `Server-Timing` 헤더나 라우트 내 `console.time`으로
`createClient` / `getUser` / 각 쿼리 구간을 나눠 찍는 것이다. 추측으로 최적화하면
엉뚱한 곳을 고칠 위험이 크다.

**프로덕션 재측정은 여전히 필요하다** — 다만 함수 기동 비용은 양쪽이 같음을 이미 확인했으므로,
차이가 난다면 트래픽에 의한 워밍 차이일 가능성이 높다.
