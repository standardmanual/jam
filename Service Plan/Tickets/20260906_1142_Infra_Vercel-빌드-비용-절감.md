# [Infra] Vercel Build CPU 비용 절감 — 프리뷰 이중 빌드·문서 커밋 빌드·스토리북 133MB 중복

## 배경 / 문제 정의

2026-09-06 청구 주기(잔여 10일) 기준 On-Demand $50.20 중 **Build CPU가 $66.15**로 사실상
전부를 차지했다. 나머지 항목은 합쳐도 $3.75다.

```
Build CPU Minutes                $66.15   ← 96%
Observability Events              $1.38
Fast Origin Transfer              $0.76
Fluid Active CPU                  $0.61
Image Optimization                $0.63
그 외                             $0.37
```

원인을 Vercel 배포 이력과 저장소에서 실측했다.

### ① `jam` 프로젝트가 `staging`을 한 번 더 빌드하고 있었다 — 빌드의 정확히 절반

같은 GitHub 저장소(`standardmanual/jam`)에 Vercel 프로젝트가 둘 붙어 있다.

| 프로젝트 | 프로덕션 브랜치 | `staging` push 시 동작 |
|---|---|---|
| `jam` (j-a-m.app) | `main` | **프리뷰 빌드 실행** ← 낭비 |
| `jam-stage` (stage.j-a-m.app) | `staging` | 프로덕션 빌드 실행 ← 필요 |

`jam`이 만드는 `jam-git-staging-standard-manual.vercel.app`을 참조하는 곳이 저장소에
하나도 없다. `/jam-work`(SKILL.md 94행)도 `/jam-ship`(SKILL.md 25행)도 확인은 전부
`jam-stage.vercel.app`에서 한다. 매 커밋마다 아무도 열지 않는 배포가 하나씩 만들어졌다.

기존 `jam-web/vercel.json`의 `ignoreCommand`(`[[ "$VERCEL_GIT_COMMIT_REF" == claude/* ]]`)는 review 브랜치만
걸렀고 이 경로는 열려 있었다.

### ② 커밋 1개 = push 1개 = 빌드 2개

`origin/staging`의 최근 20일 커밋 **1,212개**. 배포 이력과 대조하니 1:1이었다 —
`c2499ca3..eabcd75` 구간의 커밋 14개가 배포 14건을 만들었고, 최근 40개 커밋 전부가
비머지 커밋(부모 1개)이다. 즉 커밋마다 개별 push가 나갔다. **20일간 약 2,400회 빌드.**

### ③ 문서만 바꾼 커밋 208개(17%)도 앱 전체를 다시 빌드

`Service Plan/*.md`만 바뀐 커밋에서도 Storybook + Next.js를 통째로 다시 굽는다.
실측: 배포 `dpl_7zkVGhqvSteYNEhWGbHKrCfF9BuK`(커밋 `eabcd75`, 문서 전용)가 4코어 머신에서
클론~빌드캐시 업로드까지 **2분 25초**를 썼다.

### ④ 스토리북이 배지 이미지 133MB를 배포마다 두 번 실어 날랐다

`.storybook/main.ts`의 `staticDirs: ['../public']`이 `public/` 전체를 `storybook-static`으로
복사하고, `scripts/build.mjs`가 그것을 다시 `public/storybook`으로 복사한다.

```
public/            277M
├─ public/storybook  144M   ← public/ 자신의 복사본
├─ public/badges      97M
└─ public/itembooks   36M
```

그런데 배포된 스토리북은 같은 도메인의 `/storybook/` 아래에 서빙되므로, 스토리가 쓰는
절대 경로(`/badges/sample/s222.png`)는 **사이트 루트의 `public/`이 이미 그대로 응답한다.**
복사 자체가 불필요했다.

> ⚠️ **초기 진단 정정.** 이 중복의 근거로 배포 로그의 `Uploading build cache [227.82 MB]`를
> 지목했는데 틀렸다. 그 캐시는 `.next/cache`이고 `public/`과 무관하다 — 변경 후 배포에서도
> 227.82MB 그대로다. 중복이 실제로 무는 비용은 **배포 산출물 크기**이며, 효과는 아래
> 「테스트 결과」의 전후 실측(전체 145초 → 129초, Deploying outputs 26초 → 17초)이 전부다.
> ①·③에 비하면 부수적이다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 프로덕션 대상이 아닌 배포는 빌드하지 않는다 (`jam`은 `main`만, `jam-stage`는 `staging`만)

- `/jam-work`가 커밋마다 push하지 않도록 규칙을 바꾼다

### UI/UX 관점
해당 없음 — 사용자 노출 화면 변경 없음.

## 완료 기록

### 구현 내용 요약

**A. 프로덕션 대상이 아닌 배포를 전부 차단** (`vercel-ignore.sh` 규칙 ①)

`VERCEL_ENV != production`이면 종료 코드 0(빌드 건너뜀)을 반환한다. 결과적으로
`jam`은 `main`만, `jam-stage`는 `staging`만 빌드한다. 기존 `claude/*` 규칙을 포함하므로
review 브랜치 push는 종전대로 자유롭게 해도 빌드가 돌지 않는다.

> ⚠️ 이 판정은 **vercel.json 전용**이다. `build.mjs`의 스토리북 포함 여부는 여전히
> 브랜치명(`VERCEL_GIT_COMMIT_REF`)으로 판정한다 — `jam-stage`가 `staging`을 자기
> production으로 매핑해둔 탓에 `VERCEL_ENV`로 판정하면 스토리북이 빠지는 회귀가 난다
> (2026-08-27 사고). 두 파일의 기준이 다른 건 실수가 아니며 양쪽 주석에 못박았다.

**B. 문서 전용 구간 스킵** (`vercel-ignore.sh` 규칙 ②)

비교 기준을 `HEAD^`가 아니라 **직전에 실제로 빌드한 커밋**으로 잡았다. `build.mjs`가
빌드 성공 시 `.next/cache/jam-last-built-sha`에 SHA를 남기고, Vercel이 이 디렉토리를
빌드 캐시로 보존했다가 다음 배포의 `ignoreCommand` **실행 직전에** 복원한다
(배포 로그상 캐시 복원 02:05:09 → ignoreCommand 02:05:10).

`HEAD^` 비교를 쓰지 않은 이유: 한 번의 push에 코드 커밋과 문서 커밋이 섞이면 마지막
커밋만 보고 "문서 전용"으로 오판해 **코드 변경이 배포되지 않는다.** 마커 방식은 건너뛴
구간을 누적해서 비교하므로 그 사고가 구조적으로 불가능하다. 아래 C(push 묶기)로 push당
커밋 수가 늘어나기 때문에 이 차이가 실제로 중요해진다.

판단 근거가 없으면(캐시 콜드 · 얕은 클론에 기준 커밋 없음) 항상 빌드하는 쪽으로 넘어진다.

**C. staging push를 티켓당 1회로** (`jam-work/SKILL.md` 4.1 신설)

구현 커밋·문서 갱신·티켓 CLOSED를 로컬에 쌓은 뒤 마지막에 한 번 push한다. staging 배포를
눈으로 확인해야 하는 티켓은 확인이 필요한 시점에만 push하고, 확인 후 나오는 수정·문서
커밋은 다시 묶는다. 병렬 세션이 같은 파일을 건드려 먼저 올려두는 편이 안전할 때는
예외로 두되 사유를 사용자에게 알린다.

**D. 스토리북 배포 산출물에서 `public/` 중복 제거**

`build.mjs`가 `storybook build`를 `JAM_STORYBOOK_DEPLOY=1`로 실행하고, `main.ts`가
그때만 `staticDirs`에서 `../public`을 뺀다. `storybook dev`(:6006)는 사이트 루트가
없으므로 종전대로 복사한다.

> 애초 후보였던 "스토리북을 변경 있을 때만 굽기"는 채택하지 않았다. 스토리 파일을
> 건드리지 않은 커밋의 배포에서 `public/storybook`이 통째로 비어 2026-08-27 사고
> (`jam-stage.vercel.app/storybook` 404)를 그대로 재현한다. 중복 제거는 빌드는 그대로
> 수행하므로 그 실패 모드가 없으면서 절감폭은 더 크다.

### 주요 의사결정 / 핵심 메모

**절감 기여도 — 실측 기준으로 A·C가 지배적이고 D는 부수적이다**

빌드 1회는 129초, 스킵된 빌드는 12초(전체의 9%)다. 따라서 **빌드를 아예 없애는 수단**이
**빌드를 빠르게 만드는 수단**보다 압도적으로 크다.

| 수단 | 실측 근거 | 기여 |
|---|---|---|
| A 프리뷰 차단 | 145초 → 12초 (프로덕션 실증) | 빌드 횟수 −50% |
| C push 묶기 | staging 커밋 1,212개 = 배포 1,212건 (1:1 실측) | 남은 빌드의 대부분 |
| B 문서 스킵 | 20일간 문서 전용 커밋 208개(17%) | C가 흡수하고 남는 몫 |
| D 스토리북 중복 제거 | 145초 → 129초 (−11%), 산출물 −133MB | 빌드 1회당 11% |

`$66.15` → 한 자릿수 수준을 기대하지만 이건 추정이다. **다음 청구 주기에 실측으로 확인할 것.**

**선택하지 않은 대안**
- *스토리북 조건부 빌드*: 위 D 주석 참고. 2026-08-27 사고 재현 위험.
- *`HEAD^` 기반 문서 스킵*: C와 결합하면 코드 변경 누락을 낳는다. 마커 방식 채택.
- *`staticDirs`에서 `../public`을 상시 제거*: `storybook dev`(:6006)가 깨진다.

### 잔여 이슈

1. **크론이 두 프로젝트에서 각각 돈다 (미확인 · 별도 검토 필요)**
   `jam-web/vercel.json`의 `crons` 3종(`poi-cleanup` 00:00 · `notifications` 09:00 ·
   `ambient-drop` 18:00)은 두 프로젝트가 같은 Root Directory(`jam-web`)를 쓰므로 양쪽에 그대로 적용된다.
   두 프로젝트 모두 자기 브랜치를 production으로 보므로 **같은 크론이 하루 두 번 실행될
   수 있다.** Supabase는 staging·프로덕션 공용 단일 DB라 알림 중복 발송·드랍 중복 판정
   가능성이 있다. 이번 티켓 범위 밖이라 손대지 않았다 — 실제 중복 여부 확인이 먼저다.

2. **배포 스토리북의 `/ds-assets/*`는 원래 깨져 있다**
   `staticDirs`의 `{ from: '../design-system/assets', to: '/ds-assets' }`는
   `public/storybook/ds-assets`로 들어가 `/storybook/ds-assets`로 서빙되는데, 스토리는
   절대 경로 `/ds-assets/...`를 참조한다. 이번 변경과 무관한 기존 상태이며
   `storybook dev`(:6006)에서는 정상이다. `BadgeRevealCarousel.stories.tsx` 29~31행
   주석이 이미 관련 혼선을 기록해두고 있다.
