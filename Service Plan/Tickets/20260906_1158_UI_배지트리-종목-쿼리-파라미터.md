# [UI] 배지 트리가 `?activity=` 쿼리로 종목을 열도록

## 배경 / 문제 정의

`/badges/tree?activity=running`으로 들어가도 항상 첫 트리(걷기)가 열린다. 탭 클릭은 정상
동작하므로 특정 종목을 가리키는 URL을 만들 수 없다 — 딥링크·공유가 불가능하다.

티켓 `20260906_0940`(v5 전반 QA) ④번 항목이고, 코드 확인 결과 **결함이 아니라 미구현**이다.
읽는 코드가 아예 없다.

```ts
// src/app/(main)/badges/tree/page.tsx
export default async function BadgeTreePage() {   // ← searchParams 인자 자체가 없다
```

```tsx
// src/app/(main)/badges/tree/BadgeTreeClient.tsx:73
const [activeActivity, setActiveActivity] = useState<ActivityType>(
  trees[0]?.activityType ?? 'walking'          // ← 항상 첫 트리
)
```

### 왜 지금 하는가 — 트리만 관례에서 이탈해 있다

`(main)` 그룹에서 `searchParams`를 읽는 화면은 7개다(`badges`·`badges/[id]`·
`collections/[id]`·`drops`·`onboarding`·`profile`·`search`). **트리만 빠져 있다.**

> 초안에 「8개」로 적었으나 실제 나열은 7개다 — 실측치로 정정한다.

특히 바로 옆 `/badges`는 `?tab=`을 이미 읽는다. 즉 「명세에 없던 신기능」이 아니라
**이 저장소의 기존 패턴을 트리에 마저 적용하는 일**이다.

### 선례 확인 — 쿼리 기반 이동은 승인된 패턴이다

티켓 `20260826_006`은 `highlight` 쿼리 파라미터를 제거했지만 **`?tab=activity` 이동 자체는
명시적으로 유지**했다("탭 이동 자체는 유지, 하이라이트만 제거"). 제거 대상은 시각 강조였지
쿼리 기반 이동이 아니다. 이번 작업은 그 유지된 쪽과 같은 부류다.

`20260905_0037`(트리 전면 리뉴얼)에는 딥링크·쿼리에 대한 논의나 미채택 기록이 없다.
의도적으로 배제된 게 아니라 다뤄지지 않았다.

## 상세 요구사항

### 서비스/코드베이스 관점

**형제 화면 `/badges`의 패턴을 그대로 따른다.** 새 패턴을 만들지 않는다.

1. **`src/app/(main)/badges/tree/page.tsx`**
   - `searchParams: Promise<{ activity?: string }>`를 받아 `await`한다
   - 값을 `BadgeTreeClient`에 `initialActivity` prop으로 넘긴다
   - 서버에서 조회 범위를 바꾸지 않는다 — 트리는 전 종목을 이미 다 만든다.
     쿼리는 **어느 탭을 열지만** 정한다

2. **`src/app/(main)/badges/tree/BadgeTreeClient.tsx`**
   - `initialActivity?: string` prop 추가
   - `activeActivity` 초기값을 지연 초기화(`useState(() => ...)`)로 바꿔
     정규화 결과 → 기존 폴백(`trees[0]?.activityType ?? 'walking'`) 순으로 결정
   - **정규화**: `raw.trim().toLowerCase()`로 다듬은 뒤 **그 종목의 트리가 실제로 `trees`에
     있는지**로 판정한다. 유효하지 않으면 `null`을 돌려주고 기존 폴백으로 떨어진다
     (`/badges`의 `normalizeTab`이 미지 값에 `null`을 주는 것과 같은 처리)
   - **`trim().toLowerCase()`를 넣는 이유**: URL은 사람이 손으로 고치고 메신저가 대문자화하는
     입력이다. `?activity=Running`이 아무 피드백 없이 걷기로 떨어지는 것을 막는다
   - **`ActivityType` 5종 하드코딩 Set을 따로 두지 않는다.** `trees.some()`이 이미 모든 무효값을
     거른다(`'bogus'`는 어떤 트리와도 맞지 않는다). Set을 두면 종목 목록의 출처가 둘이 되어,
     6번째 종목이 추가될 때 **트리는 있는데 Set에 없어 딥링크만 조용히 실패**하는 방향으로 썩는다.
     매칭에 성공했다는 것 자체가 유효한 `ActivityType`임을 보증하므로 캐스팅도 안전하다
   - ⚠️ 트리 존재 여부 검사를 빠뜨리면 `?activity=hiking`인데 등산 트리가 없을 때 탭이 하나도
     선택되지 않아 화면이 비어 보인다 — 반드시 `trees` 기준으로 판정할 것

3. **탭 클릭 시 URL을 `?activity=`로 갱신한다.** (2026-09-06 사용자 승인으로 범위 확장)

   > ⚠️ **초안의 근거가 틀렸다.** 초안은 「`/badges`도 URL을 갱신하지 않는다(`router.replace`가
   > 없다)」를 근거로 쓰기를 범위 밖에 뒀다. 실제로 `/badges`는 갱신한다 — `router.replace`가
   > 없을 뿐 `BadgesClient.tsx:114`가 `window.history.replaceState`를 쓰고 `:105`에
   > `popstate` 리스너까지 있다. **`router.replace`만 grep한 오케스트레이터의 오류**이며,
   > 그 틀린 전제 위에 범위가 그어져 있었다.

   읽기만 넣으면 **이번 변경이 왕복 비대칭을 새로 만든다**: `?activity=running`으로 열고
   자전거 탭으로 옮긴 뒤 주소를 공유하면 상대는 달리기를 본다. 뒤로가기·새로고침도 처음
   쿼리로 되돌아간다. 쿼리가 없던 때는 항상 첫 트리라 어긋날 것이 없었으므로, 이건
   **읽기를 추가했기 때문에 생기는 결함**이다.

   - 탭 변경 시 `window.history.replaceState`로 `?activity={종목}` 갱신
     (`BadgesClient.tsx:113-116`과 같은 형태). `router.replace`를 쓰지 않는다 —
     서버 재조회가 불필요하고 형제 화면 선례와도 다르다
   - `popstate` 리스너로 뒤로/앞으로 탐색 시 쿼리를 다시 탭에 반영
     (`BadgesClient.tsx:104-111` 참고)
   - 현재 트리 화면에 다른 쿼리 파라미터는 없지만, **기존 파라미터를 지우지 않도록**
     현재 URL에서 `URLSearchParams`를 만들어 `activity`만 갈아끼운다

### URL 규약 — query로 통일한다 (2026-09-06 사용자 확정)

`/badges`는 읽기는 query(`?tab=`), 쓰기는 hash(`#activity`)로 **그 화면 안에서 이미
어긋나 있다**(알림이 `href.ts`에서 `/badges?tab=activity`로 링크를 만든다).
트리는 그 혼선을 물려받지 않고 **읽기·쓰기 모두 query**로 간다.

- 근거: `?activity=`는 이 순간부터 공유·알림에 남는 **공개 URL 계약**이 된다. hash는
  서버로 전송되지 않아 SSR이 초기 탭을 알 수 없고, 알림 링크에서도 불리하다
- **`/badges`를 query로 옮기는 것은 이번 범위가 아니다** — 기존 공개 URL 호환
  (`LEGACY_TAB_ALIASES`를 영구 호환으로 두는 것과 같은 성격)이 걸려 별도 판단이 필요하다

### UI/UX 관점

- 유효한 종목이면 그 탭이 선택된 상태로 화면이 열린다. 그 외 동작은 변화 없다
- 잘못된 값·없는 종목이면 **오류를 보이지 않고** 기존 기본 탭으로 연다
  (URL은 사용자가 손으로 고칠 수 있는 입력이므로 조용히 폴백하는 편이 맞다)
- 사용자 노출 문구 추가·변경 없음

### 컨텐츠 관점

해당 없음.

## 구현 계획

1. `page.tsx`에 `searchParams` 수신 → `initialActivity` 전달
2. `BadgeTreeClient.tsx`에 prop 추가 + 지연 초기화 + 정규화(유효값 ∧ 트리 존재)
3. 회귀 확인: 쿼리 없이 들어갔을 때 기존과 동일하게 첫 트리가 열리는지

### 1.5 UI 탐색·재사용 판정 (오케스트레이터 결정 — 이대로 따를 것)

**판정: 재사용. 신규 컴포넌트를 만들지 않는다. MODULAR(`design-system/`)를 건드리지 않는다.**

근거:
- 이번 변경은 **초기 상태값의 출처만 바꾸는 데이터 흐름 작업**이다. 새로 그리는 UI가 없다
- 탭 UI는 이미 `SlidingTabs`가 담당하고 `activeKey`를 받는 제어형이다.
  선택된 탭을 바꾸는 것은 기존 prop으로 끝난다
- 따라서 1.6(모듈러-서비스 연결 범위)도 해당 없음 — `design-system/` 변경이 없다

**하지 말 것**: 종목 선택용 새 컴포넌트·새 훅·URL 동기화 유틸을 만들지 않는다.
`/badges`의 `normalizeTab` 패턴을 트리에 맞게 옮기는 선에서 끝낸다.

### 범위 밖 (이번 티켓에서 하지 않음)

- **`/badges`의 쓰기를 hash에서 query로 옮기는 것** — 기존 공개 URL 호환이 걸린다
- `?activity=`를 만들어내는 내부 링크 추가 — 현재 트리로 오는 내부 링크는
  `BadgesClient.tsx:185` 하나뿐이고 파라미터가 없다. 이 티켓은 **트리 자신의 읽기·쓰기**까지만 다룬다
- 트리 안 특정 눈금·계열로 바로 여는 딥링크

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

`/badges/tree`가 `?activity=`를 읽어 해당 종목 탭을 연 상태로 열리고, 탭을 옮기면 URL도
같이 갱신되게 했다. `/badges`의 `?tab=`·`history.replaceState`·`popstate` 패턴을 그대로 옮겼다.

- `page.tsx`: `searchParams: Promise<{ activity?: string }>` 수신 → `initialActivity` prop 전달.
  서버 조회 범위는 그대로 둔다(트리는 어차피 전 종목을 만든다)
- `BadgeTreeClient.tsx`: `initialActivity` prop + `normalizeActivity()` 추가.
  `raw.trim().toLowerCase()`로 다듬은 뒤 **그 종목의 트리가 `trees`에 실재하는가** 하나로만
  판정하고, 아니면 `null`을 돌려 기존 폴백(`trees[0]?.activityType ?? 'walking'`)으로 떨어진다
- **쓰기(2026-09-06 범위 확장)**: 탭 변경 시 `window.history.replaceState`로 `?activity=` 갱신.
  현재 URL에서 `URLSearchParams`를 만들어 `activity`만 갈아끼우므로 다른 파라미터는 남는다.
  `popstate` 리스너로 뒤로/앞으로 탐색 시 쿼리를 다시 탭에 반영하고, 정규화를 통과하지
  못한 값이면 상태를 바꾸지 않는다(현재 탭 유지)
- **`ActivityType` 5종 하드코딩 Set은 두지 않는다**: `trees` 매칭이 모든 무효값을 이미 거르고,
  출처가 둘이면 6번째 종목 추가 시 딥링크만 조용히 실패한다. 되돌리지 말라는 주석을 코드에 남겼다
- **중복 쿼리 파라미터 방어(2차 게이트 FAIL 대응)**: `?activity=a&activity=b`처럼 같은 키가 두 번
  오면 Next가 `string[]`을 넘긴다. `searchParams`를 `{ activity?: string }`으로 선언한 탓에 그
  사실이 가려져 타입체크가 못 잡았고, `normalizeActivity`의 `raw.trim()`이 배열에서 터져 화면이
  500이 됐다(변경 전에는 `searchParams`를 아예 읽지 않아 200이었으므로 **이번 변경이 만든 회귀**).
  - `page.tsx`의 선언을 `{ activity?: string | string[] }`로 정정해 배열 가능성을 타입에 드러냈다
  - `normalizeActivity`의 `if (!raw)`를 `if (typeof raw !== 'string' || !raw)`로 바꿔 배열이면
    `null` → 기존 폴백으로 조용히 떨어진다(형제 화면 `normalizeTab`이 `VALID_TABS.has(raw)`로
    같은 입력을 견디는 것과 같은 결과). Set 미도입 판단은 그대로 유지한다
  - 양쪽에 «지우지 말 것» 주석을 남겨 다음 사람이 되돌리지 않게 했다
  - `popstate` 경로는 `URLSearchParams.get()`이 항상 `string | null`을 주므로 원래 위험이 없었다

**읽기**
- 쿼리 없음 → 걷기(기존과 동일), `?activity=running` → 달리기, `?activity=hiking` → 등산
- `?activity=Running` → 달리기, `?activity=%20cycling%20` → 자전거 (`trim().toLowerCase()` 동작)
- `?activity=bogus` → 걷기(조용히 폴백)
- 종목별로 본문 HTML이 실제로 달라지는 것까지 확인(탭 표시만 바뀌는 게 아님)

**쓰기**
- `?activity=running`에서 달리기 탭 클릭 → `/badges/tree?activity=running`,
  등산 탭 클릭 → `?activity=hiking`
- `?foo=1&activity=running`에서 자전거 탭 클릭 → `?foo=1&activity=cycling` (기존 파라미터 보존)

**popstate**
- `?activity=running` → `?activity=cycling` 이동 후 뒤로가기 → 달리기, 앞으로 → 자전거
- 클라이언트 히스토리(pushState) 이동 후 뒤로 → `?activity=running`에서 탭이 달리기로 되돌아옴
- 뒤로 간 곳의 쿼리가 무효값(`?activity=bogus`)이면 탭을 바꾸지 않고 직전 탭(달리기) 유지

**중복 쿼리 파라미터 (2차 게이트 FAIL 재현 URL)**
- `?activity=running&activity=hiking` → HTTP 200, 걷기(폴백)
- `?activity=running&activity=running` → HTTP 200, 걷기(폴백)
- `?activity=` (빈 값) → HTTP 200, 걷기(폴백)
- 중복 URL에서 달리기 탭 클릭 → `?activity=running`으로 정리됨
- 중복 URL을 히스토리에 두고 뒤로/앞으로 왕복 → 전 구간 200, `pageerror` 0건
