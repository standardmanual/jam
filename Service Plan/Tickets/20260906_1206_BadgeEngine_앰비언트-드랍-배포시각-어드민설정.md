# [BadgeEngine] 앰비언트 드랍 트리거 리뉴얼 — 어드민이 배포 시각을 정한다

## 배경 / 문제 정의

**어드민이 시각을 설정하면 그 시각에 자동 배포되는 줄 알았는데, 실제로는 그런 기능이 없다.**
2026-09-06 확인 과정에서 드러났다.

### 현재 실제 구조 (실측)

`ambient_drop_config` 전체 컬럼 — **시각 컬럼이 없다**:

```
id · auto_enabled · exclusion_window_minutes · all_random
category_mode · category_slug
rarity_mode · rarity_common/rare/epic/mystic
collection_mode · collection_ids · batch_size · max_active_per_poi · updated_at
```

어드민 화면(`AmbientDropForm.tsx` 「트리거」 섹션)이 조작 가능한 것은 **스위치와 분(分)
입력 둘뿐**이고, 시각은 읽기 전용 표시다:

> 자동 스케줄 시각은 {scheduleLabel}로 고정돼요. 아래 스위치는 그 스케줄이 실제로 배치를
> 수행할지를 켜고 끕니다.

`scheduleLabel`의 출처는 코드 상수 `AMBIENT_DROP_SCHEDULE_UTC_HOUR = 18`
(`src/lib/ambient-drop/schedule.ts`)이고, `jam-web/vercel.json`의 `"0 18 * * *"`와 손으로
동기화하도록 돼 있다.

즉 **「자동 스케줄 등록」 스위치와 매일 18:00 UTC 크론은 별개가 아니라 같은 하나다.**
스위치가 켜져 있어서 크론이 배치를 수행한다.

### 왜 이렇게 돼 있었나 — 그 이유는 이미 사라졌다

재도입 티켓 20260826_009의 의사결정 기록:

> 스케줄 시각은 어드민이 자유 설정하는 게 아니라 **코드 상수로 고정**(18:00 UTC,
> vercel.json과 동기화). `auto_enabled`는 "그 고정 시각에 실제로 배치할지"를 켜고 끄는
> 스위치다.

근거는 **"Vercel Hobby 플랜이 일 1회 초과 cron을 배포 시점에 거부한다"**(인시던트
20260723_004)였다. **현재는 Pro 플랜이라 그 제약이 없다.** 시각을 어드민이 정하게 만드는
길이 열려 있는데 설계 당시의 제약 때문에 막아둔 상태로 남아 있었던 것이다.

같은 티켓이 지금의 오해를 예견해두기도 했다 — 다른 대안을 검토하며
`시각을 설정한 것으로 착각할 수 있어(정직하지 않은 UI) 채택하지 않았다`고 적혀 있다.
설계자는 착각을 피하려 했으나 실제로 착각이 발생했다.

### 부수 문제 — 18:00 UTC는 KST 03:00이다

알림 크론은 `매일 09:00(UTC) = KST 18:00`을 "운동 후 귀가해 저녁에 확인"이라는 근거로
골랐다. 반면 앰비언트 드랍의 18:00은 20260826_009 기록상 **구 `ambient-drop-monitor`의 값을
그대로 물려받은 것**이고 사용자 시간대를 따진 값이 아니다. 결과적으로 드랍이 매일 한국시간
새벽 3시에 깔리고 있다.

### 현재 동작 실측 (2026-09-06)

- `auto_enabled = true` — 크론이 **실제로 돌고 있다**
- 2026-09-05 18:00 UTC 프로덕션 로그:
  `[ambient-drop-cron] category=mountain collections=1 eligiblePoi=817 spawned=30`
- `poi_drops`의 `source='system'` 배치가 최근 21일간 매일 18:00~18:03 UTC에 1회씩
  (스케줄 밖 08-29 15:39 · 08-30 14:18 두 건은 어드민 수동 배치 — 사용자 확인)

## 상세 요구사항

**트리거를 두 갈래로 리뉴얼한다** (2026-09-06 사용자 확정):

| 갈래 | 동작 |
|---|---|
| **예약 배포** | 어드민이 정한 **시각(KST)** 에, 저장된 3축 설정값(또는 전체 무작위)으로 매일 자동 배포 |
| **즉시 배포** | 어드민이 「지금 배포」를 누르면 저장된 설정값으로 그 자리에서 1회 배포 |

두 갈래 모두 **같은 설정값**(3축 + `all_random` + `batch_size` + `max_active_per_poi`)을
쓴다. 설정은 하나이고 실행 시점만 다르다.

### 서비스/코드베이스 관점

**① Vercel 크론 표현식은 동적일 수 없다 — 매시 정각으로 돌리고 핸들러가 판정한다**

`jam-web/vercel.json`의 `/api/cron/ambient-drop` 스케줄을 `"0 18 * * *"` → `"0 * * * *"`로
바꾼다. 핸들러가 "지금이 어드민이 정한 시각인가"를 판정해 아닐 때는 즉시 no-op으로 반환한다.

- **시각 단위는 정시(KST 0~23시)** 로 한다. 분 단위 가짜 정밀도를 만들지 않는다.
  나중에 30분 단위가 필요해지면 크론 표현식(`0,30 * * * *`)과 UI만 바꾸면 된다
- `poi-cleanup`(00:00)·`notifications`(09:00) 크론은 **건드리지 않는다**

**② 하루 두 번 실행되지 않도록 원자적으로 막는다**

매시 실행이므로 중복 방어가 필수다. 판정과 기록을 **하나의 조건부 UPDATE로** 처리한다:

```sql
update ambient_drop_config
   set last_auto_run_on = <오늘(KST)>
 where id = 1
   and (last_auto_run_on is null or last_auto_run_on < <오늘(KST)>)
returning id;
```

0행이 반환되면 이미 오늘 실행된 것이므로 배치를 건너뛴다. **먼저 이 UPDATE로 선점한 뒤에
배치를 실행한다** — 조회 후 갱신 방식은 동시 호출에서 둘 다 통과한다.

**③ DB 마이그레이션** (`jam-web/supabase/migrations/`에 **작성만**, 실행은 4단계 승인 후)

```
schedule_hour_kst  smallint not null default 3   -- KST 기준 정시(0~23)
last_auto_run_on   date                          -- KST 날짜 기준 마지막 자동 배포일
```

`default 3`은 **현행 동작(18:00 UTC = KST 03:00)을 그대로 유지**하기 위한 값이다.
배포 즉시 배포 시각이 바뀌어 운영자가 놀라는 일이 없어야 한다.

`auto_enabled`와 `exclusion_window_minutes`는 **유지한다** — 스위치는 여전히 예약 배포를
켜고 끄고, 상호 배제 창은 이제 어드민이 정한 시각을 기준으로 계산된다.

**④ 시각 관련 코드**

- `src/lib/ambient-drop/schedule.ts` — 상수 `AMBIENT_DROP_SCHEDULE_UTC_HOUR/MINUTE`를 없애고,
  `schedule_hour_kst`(설정값)를 인자로 받아 판정하도록 고친다.
  `isWithinAmbientDropExclusionWindow`도 설정 시각 기준으로 바꾼다.
  **KST↔UTC 변환을 한 곳에만 둔다** — 두 곳에 두면 어긋난다
- `src/app/api/cron/ambient-drop/route.ts` — 위 ①②를 구현
- `src/app/api/admin/ambient-drop/deploy/route.ts` — 상호 배제 판정에 설정 시각을 넘긴다
- `src/lib/ambient-drop/config.ts` — 두 신규 필드를 `AmbientDropConfig`·
  `DEFAULT_AMBIENT_DROP_CONFIG`·`NUMERIC_KEYS`에 반영
- `src/app/api/admin/ambient-drop/config/route.ts` — `schedule_hour_kst` 저장 수용.
  **`last_auto_run_on`은 어드민이 쓰지 못하게 한다** (시스템 전용 필드)
- `src/types/database.generated.ts` — 신규 컬럼 반영

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

트리거를 **예약 배포 + 즉시 배포** 두 갈래로 리뉴얼했다.

1. **크론 매시화** — `vercel.json`의 `/api/cron/ambient-drop`을 `"0 18 * * *"` → `"0 * * * *"`.
   핸들러가 ①`auto_enabled` ②`schedule_hour_kst`(KST 정시)와 현재 시각 일치 ③당일 미실행
   셋을 모두 만족할 때만 배치한다. `poi-cleanup`·`notifications` 크론은 손대지 않았다.
2. **하루 1회 원자적 선점** — `claimAmbientDropAutoRun(kstDate)`가 `last_auto_run_on`에 대한
   조건부 UPDATE(`or(is.null, lt.오늘)`) 한 번으로 오늘 몫을 선점하고, **선점 성공 뒤에만**
   배치한다. 조회 후 갱신 방식은 쓰지 않았다.
3. **DB 마이그레이션 작성** — `137_ambient_drop_schedule_hour.sql`
   (`schedule_hour_kst smallint not null default 3` + CHECK 0~23, `last_auto_run_on date`).
   default 3 = 현행 18:00 UTC와 동일한 KST 03:00 → 적용 즉시 배포 시각이 바뀌지 않는다.
   **작성만 했고 실행하지 않았다.**
4. **시각 코드 정리** — `AMBIENT_DROP_SCHEDULE_UTC_HOUR/MINUTE` 상수 제거.
   `isWithinAmbientDropExclusionWindow(now, scheduleHourKst, windowMinutes)`로 설정 시각 기준
   판정. KST↔UTC 변환은 새로 만들지 않고 공용 헬퍼 `@/lib/notifications/kst`
   (`kstHour`/`kstDateString`)를 그대로 쓴다 — 오프셋 계산이 복제되지 않는다.
5. **어드민 UI** — 「트리거」를 「배포 트리거」로 고치고 배포 시각 선택(shadcn `Select`,
   KST 0~23시)을 추가. 읽기 전용 고정 안내문 제거, 스위치 문안을 「예약 배포 켜기」로,
   수동 배포 섹션 제목을 「즉시 배포」로 바꿔 두 갈래가 한 화면에서 읽히게 했다.
   `last_auto_run_on`은 config PUT의 patch 타입에서 `Omit`으로 배제해 어드민이 쓰지 못한다.

1. **상호 배제 창에 상한이 없었다 — 자충수 경로였다.**
   `isWithinAmbientDropExclusionWindow`의 랩어라운드 최댓값이 720분(12시간)이라
   `exclusion_window_minutes >= 720`이면 **하루 24시간 내내 「지금 배포」가 409로 막힌다.**
   서버 검증은 `>= 0`만 보고 있었다. `AMBIENT_DROP_EXCLUSION_WINDOW_MAX_MINUTES = 180`을
   두고 서버 검증·`input max` 양쪽에 걸었으며, 400 메시지에 이유와 권장값(15분 안팎)을 담았다.
2. **시각 Select에 때를 함께 적는다** — `03:00 KST` → `03:00 KST · 새벽`
   (`formatAmbientDropScheduleOption`). 24시간제 숫자만으로는 하루 중 언제인지 읽히지 않고,
   **이 티켓의 발단이 정확히 그것이었다** — 18:00(UTC)로 적혀 있어 드랍이 매일 한국시간
   새벽 3시에 깔린다는 사실을 아무도 읽어내지 못했다.
3. **「오늘은 안 바뀔 수 있다」 안내 추가** — 오늘 예약 배포가 이미 돌아 `last_auto_run_on`이
   선점된 상태에서 시각을 바꾸면 새 시각은 내일부터 적용된다. 「바꿨는데 왜 안 오지」로
   읽힐 자리라 시각 선택 아래에 한 줄 넣었다.
4. **합쇼체 잔재 2곳 정리**(UX 가이드 §2.1) — `저장되었습니다. 다음 배포부터 즉시
   적용됩니다.` → `저장했어요. 다음 배포부터 적용돼요.`, `직접 배치합니다.` →
   `직접 배치해요.` 도입문의 「맨 아래 「지금 배포」」도 실제 위치(그 아래에 「최근 실행
   이력」이 또 있다)에 맞게 「아래 「즉시 배포」의 「지금 배포」」로 고쳤다.

### 주요 의사결정 / 핵심 메모

- **KST 변환 헬퍼를 새로 만들지 않았다.** 티켓은 "KST↔UTC 변환을 한 곳에만 둔다"고 했고,
  이미 `@/lib/notifications/kst`에 `kstHour`/`kstDateString`(서머타임 없음 근거까지 기록된)
  공용 헬퍼가 있어 그대로 재사용했다. `ambient-drop/schedule.ts`에는 오프셋 상수가 없다.
- **분 단위를 만들지 않았다.** 정시(0~23)만 고르게 했고 UI에도 「분 단위는 정할 수 없어요」로
  명시했다(문안은 개선 리뷰 반영으로 「정시 단위로만 정할 수 있어요」로 바뀌었다).
  필요해지면 크론 표현식과 UI만 바꾸면 된다.
- **선점 실패(DB 오류) 시 배치하지 않는다.** 중복 배포보다 미배포가 안전하다고 판단했다.

  배제 창에 진입/이탈해도 갱신되지 않는다(기존 동작 그대로). 실제 강제는 API 409가 한다.

  루트 밖을 가리켜 Turbopack이 거부한다(환경 제약이지 코드 문제가 아니다). 신규 의존성·신규
  컴포넌트가 없고 `tsc`·`lint`·테스트가 전부 그린이라 실패 가능성은 낮지만 미검증은 미검증이다.
  staging 머지 후 Vercel 빌드가 이를 대신 검증한다.
- **정시 완전일치라 크론이 다음 시로 밀리면 그날 예약 배포가 통째로 누락된다.**
  `kstHour(now) === scheduleHourKst`이므로 크론 발사가 다음 시로 지연되면 그 날은 건너뛴다.
  Vercel Pro는 분 단위 오차라 실현 가능성은 낮고, 앞당겨 밀리는 경우는 다음 시 호출이 흡수한다.
  기존(일 1회 크론·시각 무판정) 대비 **새로 생긴 실패 모드**라 기록해둔다.
  > 대안: `kstHour(now) >= scheduleHourKst` + 선점 조합(캐치업)으로 하면 이 실패 모드가
  > 사라진다 — 중복 방어는 이미 `last_auto_run_on`이 하므로 안전성은 그대로다. 다만 장애 시
  > 배포 시각이 뒤로 흐르고, `auto_enabled`를 낮에 켜면 즉시 발사되는 부작용이 생긴다.
  > 트레이드오프라 지금은 채택하지 않았다. **다음 사람이 재발명하지 않도록 여기 적어둔다.**
- **배치 실패가 어디에도 남지 않는다.** cron 라우트에 `try/catch`가 없어
  `runAmbientDropBatch`가 throw하면 선점만 된 채 500으로 끝나고 `engine_decision_log`에
  흔적이 없다. 「그날은 재시도하지 않는다」와 겹치면 **오늘 드랍이 없는데 이유를 화면에서
  알 수 없는** 상태가 된다. `event='ambient_batch_error'` 한 줄을 남기는 안을 검토할 것.
- **매시 no-op 로그가 하루 최대 24줄 쌓인다.** `not_scheduled_hour`/`auto_disabled`
  `console.info` 둘은 정상 상태에서도 계속 쌓인다. 정상 no-op은 로그를 생략하고 실제 배치·
  선점 실패만 남기는 편이 신호 대비 잡음에 낫다.
- **`getAmbientDropConfig`가 DB 읽기 실패를 삼킨다**(이번 변경 이전부터). 모든 예외를
  `catch`해 `DEFAULT_AMBIENT_DROP_CONFIG`(`auto_enabled=false`)로 폴백하므로, DB 일시 장애 시
  예약 배포가 "꺼진 것처럼" 조용히 스킵되고 로그로는 원인 구분이 안 된다. 매시 크론이 되면서
  이 경로를 하루 24번 지나가게 됐다.
