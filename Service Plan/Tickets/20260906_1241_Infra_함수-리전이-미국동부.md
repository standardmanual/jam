# [Infra] 함수가 미국 동부에서 돈다 — 모든 DB 왕복이 태평양을 건넌다

## 배경 / 문제 정의

티켓 `20260906_0940` ③(TTFB 3~5초)의 **원인이다.**

Vercel 함수가 **`iad1`(미국 버지니아)** 에서 실행되는데 Supabase는 **`ap-northeast-2`(서울)** 에 있다.
DB 왕복 한 번마다 태평양을 왕복하므로 **왕복당 약 200ms**가 붙는다.

```
x-vercel-id: icn1::iad1::72hnc-...
             ↑엣지 ↑함수 실행
```

요청은 서울 엣지(`icn1`)로 들어와 **버지니아(`iad1`)로 넘겨져 실행**된다. 그 함수가 다시
서울의 Supabase를 부른다.

> 처음 조사에서 정적 자산의 `x-vercel-id: icn1::...`만 보고 「함수도 서울」이라고 오판했다.
> 세그먼트가 2개면 엣지에서 끝난 요청이고, **3개여야 두 번째가 함수 실행 리전**이다.

### 실측 — `/api/diag-perf` (2026-09-06, staging)

구간별 벽시계 시간과 `process.cpuUsage()` 델타를 함께 찍었다(6회 중 대표 3회):

| 구간 | wall (ms) | cpu (ms) |
|---|---:|---:|
| `createClient` (네트워크 없음) | 0.6~1.9 | 동일 |
| `auth.getUser` | **202~287** | 6~103 |
| `createServiceClient` (네트워크 없음) | 0.4~1.2 | 동일 |
| 가벼운 쿼리 #1 | **216~650** | 4~81 |
| 가벼운 쿼리 #2 | **220~695** | 4~13 |
| `auth.getUser` #2 | **199~579** | 5~9 |
| **합계** | **848~1,710** | **24~209** |

- **네트워크를 타지 않는 구간(클라이언트 생성)은 1ms 미만**이다. 코드가 느린 게 아니다
- **네트워크를 타는 구간은 예외 없이 200ms 이상**이다. 서울↔버지니아 RTT와 정확히 일치한다
- 가끔 나오는 **600ms대는 새 커넥션**이다 — TLS 핸드셰이크 3 RTT × 200ms ≈ 600ms.
  200ms대는 커넥션 재사용(1 RTT)
- 같은 쿼리를 DB에서 직접 재면 **3.1ms**다(`EXPLAIN ANALYZE`). 실행이 아니라 거리다

### `cpuRatio`가 비용 판단을 뒤집는다

**`cpuRatio` = 0.019 ~ 0.147** (총 CPU / 총 벽시계). 즉 **이 시간의 95~98%는 I/O 대기이고
CPU를 태우지 않는다.**

Vercel Fluid compute는 **Active CPU와 대기 시간의 단가가 다르다.** 따라서 비용 추정에 있던
「TTFB가 5초면 1초짜리보다 CPU 요금이 몇 배」는 **이 서비스에는 해당하지 않는다** —
CPU를 안 쓰고 기다리고 있기 때문이다.

다만 **대기 시간이 공짜는 아니다**(Provisioned Memory는 벽시계 기준). 리전을 고치면
UX와 이 축 모두 한 자릿수 배로 줄어든다. 5,000명 비용 추정의 상단 시나리오는 이 발견으로
**과대평가였음이 드러났다** — 근거를 CPU에 두고 있었기 때문이다.

## 상세 요구사항

### 서비스/코드베이스 관점

`jam-web/vercel.json` 최상위에 실행 리전을 명시한다.

```json
{
  "regions": ["icn1"]
}
```

- `icn1` = 서울. 유저도 한국, Supabase도 서울이라 **두 축 모두 가까워진다**
- 현재 `vercel.json`·`next.config`에 `regions` 설정이 **아예 없다.** 즉 `iad1`은 누가 고른 게
  아니라 **Vercel 기본값**이 그대로 쓰인 것이다
- 프로젝트 단위 기본값이므로 라우트별 예외는 두지 않는다

### 검증

- 배포 후 `x-vercel-id`의 두 번째 세그먼트가 `icn1`인지 확인
- `/api/diag-perf`를 다시 돌려 구간별 수치를 **전후 비교**한다.
  기대: 네트워크 구간 200ms대 → 한 자릿수~수십 ms
- 주요 화면 TTFB 재측정 (기준선: `/search` 0.71s · `/badges/tree` 1.87s · `/` 2.82s)

### 미확인 — 프로덕션 리전

**`jam-stage`에서만 실측했다.** 프로덕션(`jam`)은 미들웨어가 모든 비인증 요청을 가로채
함수까지 보내지 않아 밖에서 리전을 읽을 수 없었다. 다만:

- `regions` 설정이 저장소에 없으므로 두 프로젝트 모두 Vercel 기본값을 쓸 가능성이 높다
- 리전은 **프로젝트별 설정**이라 다를 수 있다 — 단정하지 않는다
- `vercel.json`에 넣으면 두 프로젝트 모두 이 값을 쓰게 되므로, 프로덕션이 이미 `icn1`이었더라도
  해가 없다

## 구현 계획

1. `jam-web/vercel.json`에 `"regions": ["icn1"]` 추가
2. staging 배포 → `x-vercel-id` 두 번째 세그먼트 확인
3. `/api/diag-perf` 전후 비교 · 주요 화면 TTFB 재측정
4. 프로덕션 반영은 `/jam-ship`으로 별도 승인

### 남은 것 — 리전을 고쳐도 왕복 횟수는 그대로다

리전은 **왕복당 비용**을 줄인다. **왕복 횟수**는 그대로다:

- `auth.getUser()`가 요청당 최소 3회 나간다(`proxy.ts:39` · `(main)/layout.tsx:14` · 각 페이지).
  React `cache()`로 묶여 있지 않아 중복 제거가 없다
- 저장소 전체에 `auth.getUser()` 60회, `await createClient()` 57회

리전 수정 후 남는 시간이 여전히 크면 이쪽을 별건으로 다룬다. **먼저 리전을 고치고 재측정한 뒤
판단한다** — 지금 왕복 횟수를 줄여봐야 200ms짜리를 3개에서 1개로 줄이는 것이고,
리전을 고치면 애초에 5ms짜리가 된다.

### 왕복 횟수 정리는 하지 않기로 했다

착수 전에 「리전을 고친 뒤 남는 시간이 크면 `getUser` 중복 호출을 별건으로 다룬다」고
적어뒀는데, **재측정 결과 그럴 필요가 없다.** `getUser` 한 번이 25~29ms이므로 3회 = 약 80ms다.
`cache()` 도입은 호출 60곳을 건드리는 변경인데 얻는 것이 50ms 남짓이라 비용 대비가 맞지 않는다.

리전이 200ms짜리를 25ms로 만든 이상, **왕복 횟수를 줄이는 작업의 근거 자체가 약해졌다.**
필요해지면 그때 다시 측정해 판단한다.
