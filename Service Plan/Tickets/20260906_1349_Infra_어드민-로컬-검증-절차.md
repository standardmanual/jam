# [Infra] 어드민을 로컬에서 실렌더 검증하는 절차를 표준으로 만든다

## 배경 / 문제 정의

**「어드민 화면은 staging에서 검증 불가」가 오랫동안 전제로 굳어 있었다.** 그래서 어드민을
건드리는 티켓마다 실화면 확인이 「프로덕션 배포 후로 미룸」으로 남았고, 결함이 프로덕션에서
처음 드러나는 구조였다.

티켓 `20260906_1312` 게이트 리뷰가 **이 전제를 깼다.** 로컬 `next dev`에
`ADMIN_EMAILS=<dev-login 계정 이메일>`을 셸 환경변수로 주입하면(저장소·DB 무변경)
어드민 전 화면이 정상 렌더된다. 실제로 그 방법으로 9개 화면을 전부 실측했다:

- `/admin/today?date=2026-09-01` → 해당 날짜 렌더
- `/admin/item-badges?q=쉐이커` → 해당 배지 노출, 중복 `q`는 무필터
- `/admin/badges?page=2` → 페이지네이션이 page=2 기준

### 왜 티켓으로 남기는가

**한 번 쓰고 잊히면 다음 티켓이 또 「확인 불가」로 넘어간다.** 실제로 같은 티켓에서
개발자는 「로컬에서도 307이라 확인 불가」로 보고했고 게이트가 뒤이어 방법을 찾아냈다 —
**같은 저장소, 같은 날, 두 에이전트가 서로 다른 결론에 도달했다.** 절차가 문서에 없기
때문이다.

## 상세 요구사항

### 서비스/코드베이스 관점

**① 절차를 실측으로 확정한다**

문서에 적기 전에 **직접 재현해 확인할 것.** 게이트의 보고를 그대로 옮기지 말고:

- `ADMIN_EMAILS`를 어떻게 주입해야 하는가 (셸 앞에 붙이는가, `.env.local`을 고쳐야 하는가)
- **`.env.local`을 고치는 방식이면 안 된다** — 그 파일은 아이클라우드의 `JAM-secrets`에
  심볼릭 링크로 연결돼 있어 모든 PC에 전파된다. 셸 환경변수로만 되는지 확인할 것
- `dev-login` 계정의 이메일이 무엇인가 (`src/app/api/dev-login/route.ts`가 단일 출처)
- 어드민 권한 판정이 이메일만 보는가, DB 역할도 보는가 (`hasAdminAccess`가 `proxy.ts:77`)

**② 어디에 적을 것인가**

`Specs/DEV_PROCESS_GUARDRAILS.md`가 1순위 후보다(횡단 참조 문서). 다만 **실제로 서브에이전트가
읽는 곳에 있어야 의미가 있다** — `.claude/agents/conservative-reviewer.md`나
`.claude/skills/jam-work/SKILL.md`의 `admin` 유형 행에서 이 문서를 가리키게 할지 판단할 것.
문서에만 적고 아무도 안 읽으면 이번과 같은 일이 반복된다.

**③ 기존 전제를 함께 정정한다**

「어드민은 staging에서 검증 불가」라고 적힌 곳을 찾아 **「staging에서는 불가하지만 로컬에서는
가능하다」로 정정**한다. 낡은 전제를 남겨두면 새 문서와 충돌한다.

### 보안 — 반드시 지킬 것

- **프로덕션·staging의 `ADMIN_EMAILS`를 바꾸지 않는다.** 이건 로컬 개발 환경 한정 절차다
- `.env.local`·`JAM-secrets`의 내용을 문서에 옮겨 적지 않는다
- `dev-login`이 프로덕션에서 404인 이유(`STAGING_MODE` 게이트, 티켓 `20260812_004`)를
  문서에 함께 남겨, 「그럼 프로덕션에도 열자」는 잘못된 후속이 나오지 않게 한다

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

직접 재현으로 절차를 실측·확정했다:

1. `dev-login` 계정 이메일은 `src/app/api/dev-login/route.ts`의 `DEV_USER_EMAIL`
   (`dev-tester@jam.local`) — DB 확인 결과 이 계정은 기본 `is_admin = false`.
2. `hasAdminAccess()`(`src/lib/admin/auth.ts`)는 `ADMIN_EMAILS` 환경변수 화이트리스트
   **OR** `users.is_admin` 컬럼으로 판정한다 (proxy.ts·admin/layout.tsx·getAdminUser() 3곳 공유).
3. **셸 환경변수만으로 된다** — `.env.local`을 고칠 필요 없음:
   `ADMIN_EMAILS=dev-tester@jam.local npm run dev`
4. `/api/dev-login` → 세션 쿠키 발급 → `/admin/badges` 실제 렌더 확인 완료
   (Browser 도구로 실측, "배지 관리" 헤더·`dev-tester@jam.local` 표시·배지 목록 2455개 정상 노출).

문서 위치는 `Specs/DEV_PROCESS_GUARDRAILS.md`(패턴 13, 횡단 참조 문서 1순위)로 확정하고,
`.claude/skills/jam-work/SKILL.md`의 `admin` 유형 행과 `.claude/agents/conservative-reviewer.md`
양쪽에서 이 패턴을 가리키도록 갱신했다 — 서브에이전트가 실제로 읽는 두 곳이다.

기존 「어드민은 staging에서 검증 불가」 전제는 **배포된 staging 도메인 한정**으로 범위를
좁혀 정정했다(오케스트레이터 메모리 `project_admin_no_staging_verification` 포함).
staging 도메인 자체는 여전히 검증 불가(환경변수 자체가 없음, 프로덕션과 DB 공유) —
이 부분은 그대로 유지.
