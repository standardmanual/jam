# [Admin] 드랍 가중치 미리보기가 배지 테이블 전체를 스캔한다

> 어드민 배지 생성/수정/상세 화면 구성 점검(2026-09-06) 중 발견. 관련: `20260906_1420`·`20260906_1421`·`20260906_1423`·`20260906_1424`

## 배경 / 문제 정의

`jam-web/src/app/admin/badges/BadgeForm.tsx` 177-196행은 아이템 타입 배지를 만들 때
"같은 컬렉션·희귀도 내 다른 배지 대비 이 배지가 뽑힐 상대 확률"을 미리보기로 보여준다.
이 계산을 위해 `GET /api/admin/badges`를 호출하는데, 이 엔드포인트
(`jam-web/src/app/api/admin/badges/route.ts` 8-38행)는 PostgREST의 1,000행 응답 상한을
우회하려고 **배지 테이블 전체(주석 기준 과거 5,585건, 지금은 그보다 많을 것)를 1,000건씩
페이지네이션으로 끝까지 조회**한다. `BadgeForm`은 이 전체 목록을 받아 클라이언트에서
`item_book_id`+`rarity`로 필터링해 합계 하나만 뽑아 쓴다.

즉 아이템 배지 등록/수정 화면에서 컬렉션을 선택할 때마다(또는 희귀도를 바꿀 때마다)
배지 테이블 전체를 여러 번의 요청으로 긁어오는 구조다. 이미 서버 필터링 방식의
`/api/admin/badges/search`(`jam-web/src/app/api/admin/badges/search/route.ts`)가 있다 —
지금은 이름 검색(`ilike name`) + `type`/`unassigned` 파라미터만 지원하고 `LIMIT 20`으로
결과를 제한하는 패턴인데, 같은 골격으로 `item_book_id`+`rarity` 필터를 받아 해당 조건에
맞는 배지의 `drop_weight` 목록(또는 합계)만 반환하는 전용 조회로 바꾸면 이 문제가 해결된다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 신규(또는 기존 `search` 라우트 확장) 엔드포인트: `item_book_id`+`rarity`(+ 수정 중인
  배지 자신을 제외하기 위한 `excludeId`)를 받아 `deleted_at IS NULL`인 같은 조건의 배지
  `drop_weight` 목록(또는 합계)만 서버에서 계산해 반환
  - `search` 라우트를 확장할지, 별도 라우트(`/api/admin/badges/sibling-weight` 등)를 만들지는
    구현자가 판단 — `search`는 "이름 검색" 의미가 이미 있어 확장보다 별도 라우트가 더
    명확할 수 있음
- `BadgeForm.tsx` 177-196행의 `siblingWeightSum` 계산 로직을 새 엔드포인트 호출로 교체
- `GET /api/admin/badges`(전체 조회)는 이 미리보기 용도 외에 `ItemBookForm.tsx`(일괄 배경
  적용 전 대상 배지 수 미리보기)도 쓰고 있다(`route.ts` 14-19행 주석) — 이번 티켓은
  `BadgeForm.tsx`의 소비만 걷어내며, `ItemBookForm.tsx` 쪽은 범위 밖(아래 참조)

### UI/UX 관점 (해당 시)
- 상대 확률 미리보기 문구·표시 형태는 그대로 유지 — 데이터 소스만 바뀐다

### 컨텐츠 관점 (해당 시)
해당 없음.

## 구현 계획

1. 서버 필터링 엔드포인트 추가/확장 (item_book_id + rarity, deleted_at 제외, 자기 자신 제외)
2. `BadgeForm.tsx`의 `fetchedSiblingWeightSum` effect를 새 엔드포인트 호출로 교체
3. 회귀 확인: 아이템 배지 등록/수정 화면에서 컬렉션+희귀도를 바꿔가며 상대 확률 숫자가
   이전과 동일하게 계산되는지 확인(같은 컬렉션·희귀도에 배지가 여러 개 있는 케이스로 검증)
4. 네트워크 탭에서 더 이상 전체 배지 목록을 조회하지 않는지 확인

### 범위 밖
- `GET /api/admin/badges` 자체의 페이지네이션 전체 스캔 구조 변경 — `ItemBookForm.tsx`가
  같은 엔드포인트를 다른 목적으로 쓰고 있어(`route.ts` 14-19행), 그쪽 소비까지 걷어내는
  건 별도 판단이 필요하다. 이번 티켓은 `BadgeForm.tsx`의 사용만 걷어낸다
