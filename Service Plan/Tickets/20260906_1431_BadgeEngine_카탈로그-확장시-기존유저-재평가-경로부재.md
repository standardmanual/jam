# [BadgeEngine] 배지를 새로 시딩해도 기존 유저를 재평가할 경로가 없다

> 근거 조사: `20260906_1426`. 후속 3건 중 **②(스펙 판단 필요)**.
> 형제 티켓: `20260906_1430`(수동 동기화 게이트) · `20260906_1432`(지연 관측 수단)

## 배경 / 문제 정의

카탈로그에 배지를 추가해도 기존 유저에게 **재평가가 일어나지 않는다.**
발급은 각 유저의 다음 활동 동기화 때 개별적으로 일어나므로,
같은 날 시딩한 배지가 유저마다 며칠씩 흩어져 발급된다.

실측(티켓 1426): v5 신규 630종 시딩(`2026-09-05 20:25 UTC`) 후 관측 시점까지
**신규 카탈로그 배지를 받은 유저는 12명 중 1명뿐**이었다(시딩 후에 달린 유저 1명).

### 현재 존재하는 경로 — 전부 이 용도가 아니다

| 경로 | 배지 평가 | 비고 |
|---|---|---|
| `/api/strava/callback`·`/api/strava/sync` | O | 새 활동이 있어야 실행 (→ 티켓 `20260906_1430`) |
| 크론 3종 (`poi-cleanup`·`notifications`·`ambient-drop`) | **X** | `vercel.json`에 배지 평가 크론은 없다 |
| `/api/admin/strava-backfill` | **X** | Strava 확장필드 백필 전용 |
| `/api/admin/simulate` | △ | **가상 활동 1건 주입형**(`activity` 파라미터 필수). `dryRun:false`면 실제 발급되지만 유저 일괄 재평가 도구가 아니다 |

> ⚠️ **「소급 발급 기능 신설」로 접근하지 말 것.** 조건 평가창은 이미 소급이다 —
> `evaluateBadgesDetailed`는 매 실행마다 `getActivityHistory(앵커~)` 전체를 다시 본다.
> 없는 것은 **평가를 돌릴 계기**이지 소급 평가 능력이 아니다.

## 상세 요구사항

### 먼저 정할 것 — 스펙 판단

어느 쪽인지부터 정해야 구현이 갈린다. **구현 전에 결론을 이 티켓에 적는다.**

- **A안 — 어드민 일괄 재평가 버튼** (dry-run 지원). 운영자가 시점을 고른다.
- **B안 — 시딩 후 1회 배치.** 카탈로그 변경과 발급을 같은 작업으로 묶는다.
- **C안 — 정기 배치.** 발급 지연 상한을 시간으로 보장하지만 비용이 붙는다
  (Vercel Build/Function 비용은 티켓 `20260906_1142` 참조 — 크론 추가는 신중히).

### 서비스/코드베이스 관점 (안이 정해진 뒤)

- **대량 발급의 부수효과 정책을 함께 정해야 한다.** `evaluateBadgesDetailed`는 발급마다
  포인트 지급(`awardPoints`)·피드 기록(`recordFeedEvent`)·결산(`recordActivityRecap`)을
  일으킨다. 재평가로 유저당 수십 종이 한 번에 나오면 피드와 알림이 폭발한다.
  - `silent: true` 옵션이 이미 있다(피드 기록 생략). 재평가에 쓸지 결정할 것.
  - 포인트는 `silent`와 무관하게 지급된다 — **재평가 지급이 맞는지 별도 판단이 필요하다.**
- 앵커(`users.created_at`) 이후 이력만 대상이라는 현행 정책은 유지한다.
- `engine_decision_log`에 남길 `triggeredBy` 값을 새로 정의한다(`strava_sync`와 구분).

### UI/UX 관점

- 유저 관점에서 「달리지도 않았는데 배지가 쏟아진다」가 된다.
  결산·알림 문안이 이 상황을 설명할 수 있어야 한다.

## 구현 계획

1. A/B/C 안 결정 (사용자 판단)
2. 부수효과 정책 확정 — 피드·알림·포인트 각각
3. 구현 + dry-run 경로
4. 실행 전 영향 규모 실측 (대상 유저·예상 발급 건수·예상 포인트)
