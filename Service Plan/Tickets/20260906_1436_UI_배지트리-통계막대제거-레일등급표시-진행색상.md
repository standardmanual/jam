# [UI] 배지 트리 화면 — 전체 통계 막대 제거·레일 등급 표시 조정·진행 수치 색상 변경

> 선행: `20260906_1323`(배지 트리 화면 정리 9건 — 통계 2행 3열 배치·레일 `not-reached` 조건값
> 표시를 이번 티켓과 같은 화면에 먼저 적용했다)
> 대상 화면: `/badges/tree` 하나. 다른 화면은 건드리지 않는다.

## 배경 / 문제 정의

`20260906_1323` 반영 후 화면을 다시 확인한 사용자가 지적한 3건이다. 전부 **표시 층의
문제**이고 발급 로직·진행 계산에는 손대지 않는다.

1. **전체 통계 칸의 막대가 불필요하다.** `20260906_1323` §6에서 "막대·라벨·값의 세로 위치가
   세 칸에서 정확히 맞는다"는 근거로 전체(`전체 0/145`) 칸에도 등급 칸과 같은 6px 진행 막대를
   넣기로 했는데, 사용자가 다시 보니 이 칸은 막대 없이 레이블+값만 있는 편이 더 조화롭다는
   판단이다. **이번 티켓은 그 결정을 되돌린다.**
2. **레일(`BadgeStageRail`) 표시가 세 군데 어색하다.**
   - 「자세히」로 펼친 목록의 상태 줄이 `not-reached`일 때 여전히 `'—'`만 보여준다.
     `20260906_1323` §7이 접힌 레일 눈금의 캡션은 조건값으로 바꿨지만, 펼친 목록 쪽은
     범위를 "레일 눈금 캡션 한 곳"으로 못박아 손대지 않았다 — 그 티켓 완료 기록의
     잔여 이슈에 정확히 이 항목이 남아 있다.
   - 펼친 목록에서 배지 이미지 아래 등급색 3px 바가 뜨는데, 같은 줄 오른쪽에 이미
     `RarityBadge` 칩이 등급을 텍스트로 보여주고 있어 중복이다.
   - 반대로 펼치기 전(접힌) 레일에서는 등급을 3px 색 바 하나로만 표시한다 — 등급명이
     `aria-label`에만 있고 화면에는 안 보인다. 이 자리를 칩으로 바꿔 화면에서도 등급이
     바로 읽히게 한다.
   - 눈금 사이 연결선("레일바")이 간격 중앙이 아니라 한쪽으로 치우쳐 보인다.
3. **진행 중인 수치값의 색이 눈에 거슬린다.** 지금 계산 중인(=아직 조건을 못 채운) 배지의
   진행 수치를 옐로우(`--status-short-solid`, `#f2cb00`)로 표시하는데, 이를 화이트 계열로
   바꾼다.

## 상세 요구사항

### 1. 전체 통계 칸 — 막대 제거, 레이블·값 재배치

**대상**: `design-system/components/patterns/BadgeTreeSummaryHeader.jsx`

- `cells` 중 `key: 'total'`(`primary: true`) 칸만 6px 진행 막대(74~84행의
  `<div style={{height:6, ...}}>` 블록)를 렌더하지 않는다. 등급 칸(Mystic·Epic·Rare·Common)의
  막대는 그대로 둔다 — 이번 요청은 "전체" 칸 하나에 한정된다.
- 막대가 빠진 자리에서 레이블(`전체`)과 값(`{earned} / {total}`)이 **조화롭게** 배치되도록
  정렬·여백을 다시 잡는다. 지금 레이블은 `marginTop:8`(막대 기준), 값은 `marginTop:4`인데
  막대가 없으면 이 간격이 어색할 수 있다 — 등급 칸과 세로 정렬(baseline)이 흔들리지 않는
  범위에서 값을 조정한다.
- `20260906_1323` §6의 "요약 헤더 첫 칸에도 6px 막대를 둔다" 결정을 **이 칸에 한해 되돌린다**는
  점을 구현 요약에 명시할 것 (문서상 결정 번복 이력을 남긴다).
- 스토리(`BadgeTreeSummaryHeader.stories.tsx`) 갱신 — 전체 칸에 막대가 없는 상태를 반영.

### 2. 레일 영역 — `BadgeStageRail.jsx`

#### 2-1. 펼친 목록에도 `not-reached` 조건값 표시

- 582행 `{STATUS_LABEL[stop.status]}` — 펼친 목록(`expanded`, 552~599행)의 상태 줄이 지금은
  `stop.status`만 보고 라벨을 고른다. 접힌 레일(492~533행)이 이미 하는 것과 같은 규칙을
  적용한다: `stop.status === 'not-reached' && stop.conditionText != null`이면 상태 라벨
  `'—'` 대신 `stop.conditionText`를 보여준다. 조건값이 없으면 기존 `'—'` 그대로.
- `stopAriaLabel`과 같은 방식으로 접근성 텍스트도 갱신이 필요한지 확인할 것 — 지금 펼친
  목록의 상태 `<p>`는 시각 텍스트 자체가 스크린리더에도 그대로 읽히므로, 텍스트만 바꾸면
  자동으로 해결될 가능성이 높다(접힌 레일처럼 aria 전용 라벨을 따로 만든 구조가 아니다).

#### 2-2. 펼친 목록 — 배지 이미지 아래 등급 바 제거

- `StopThumbnail`(144~198행)의 `barColor` 렌더(190~195행)를 **펼친 목록 호출부(560행)에서만**
  끈다. 접힌 레일 호출부(491행)는 2-3에서 다시 다루므로 당장은 손대지 않아도 되지만, 결과적으로
  2-3이 접힌 쪽 바도 없애므로 최종적으로는 `StopThumbnail`이 바를 그리는 경우 자체가 사라질
  수 있다 — 구현 시 2-2·2-3을 함께 보고 `StopThumbnail`에 바 렌더 로직을 통째로 남길지
  제거할지 판단할 것(둘 다 안 쓰면 죽은 코드가 된다).
- 펼친 목록은 이미 `RarityBadge` 칩(563행)으로 등급을 보여주므로 바가 없어도 정보 손실이
  없다.

#### 2-3. 접힌 레일 — 등급 바 제거하고 등급칩 표시

- 접힌 레일 눈금(371~538행, `StopThumbnail` 호출 491행)의 3px 등급 바를 없애고, 대신
  **등급칩**을 표시한다. 칩은 44px 썸네일 폭 안에 들어가야 하므로 펼친 목록의 `RarityBadge`
  (텍스트 포함, 폭 가변)를 그대로 쓸 수 없다 — 압축된 형태(색 배경 + 짧은 라벨 또는 색만
  다른 소형 칩)가 필요할 가능성이 높다. 정확한 시각 형태(크기·라벨 유무·배치 위치 — 썸네일
  아래인지 옆인지)는 구현 시 `RarityBadge.jsx`의 기존 변형을 먼저 찾아보고, 없으면 신규 소형
  변형이 필요한지 `/jam-design`으로 재사용 여부부터 판단할 것.
- `rarity`가 없는 눈금(레벨형은 애초에 이 컴포넌트를 안 쓰므로 실질적으로 발생하지 않지만)
  방어적으로 `barColor` 조건과 동일하게 `rarity`가 있을 때만 칩을 그린다.
- 등급칩 도입 후 `stopAriaLabel`의 등급 정보(현재 `rarityLabel`이 `stopName`에 포함되어
  aria로는 이미 전달됨, 63~70행 `STATUS_ARIA_LABEL`)는 중복 변경 없이 그대로 둘 것.

#### 2-4. 눈금 사이 연결선("레일바") 간격 중앙 정렬

- 421~483행의 연결선 `<span>`(`marginTop: 19`, `flex: isGateBefore ? '0 0 44px' : '1 1 14px'`)이
  화면에서 한쪽으로 치우쳐 보인다는 지적이다. 다만 정확한 원인(수직 위치 기준점 문제인지,
  좌우 여백 배분 문제인지)은 이번 조사에서 코드만으로 단정하기 어렵다 — 2-3의 등급 바 제거로
  눈금 하단 구성(썸네일+바 유무)이 바뀌면 연결선의 적정 `marginTop`도 같이 달라질 수 있으므로,
  **2-3을 먼저 반영한 뒤 실제 화면(스크린샷)으로 치우침을 재확인하고 고칠 것.**
- 확인 시 참고: `marginTop: 19`는 44px 썸네일의 세로 중앙(22px) 근처를 겨냥한 값으로 보이며,
  좌우 폭은 `flex: '1 1 14px'`로 눈금 사이 남는 공간을 균등 배분한다 — 게이트 자리
  (`isGateBefore`, `flex: '0 0 44px'`)가 있는 구간만 폭이 고정이라 그 앞뒤 일반 연결선과
  시각적으로 안 맞을 가능성을 우선 의심할 것.

### 3. 진행 중인 배지 수치값 — 옐로우 → 화이트

**대상**: `BadgeStageRail.jsx`(502~508행 `captionColor`), `BadgeLevelGauge.jsx`(57행
`valueColor`) — 둘 다 "조건을 아직 못 채운(진행 중)" 상태의 수치 텍스트에
`var(--status-short-solid)`(옐로우 `#f2cb00`)를 쓴다.

- ⚠️ **토큰 값 자체(`--status-short-solid`)를 바꾸지 않는다.** 이 토큰은
  `design-system/tokens/colors.css`에 "배지 트리 상태 채널" 공용 시맨틱으로 선언돼 있고
  `ProgressBar.jsx`(DS 공용)·`DualAxisGauge.jsx`·`src/components/badges/BadgeTrophyGridCard.tsx`
  (`/badges` 등 다른 화면)에서도 참조한다. 토큰을 바꾸면 배지 트리 밖 화면(`/badges` 트로피
  그리드 등)의 진행 막대·게이지 색까지 함께 바뀐다 — 이번 요청은 "배지 트리 화면"으로
  범위가 못박혀 있으므로, **두 컴포넌트의 해당 텍스트 색만** 화이트 계열
  (`--color-text` 등, 정확한 토큰은 구현 시 확정)로 개별 override한다.
- 진행 막대·연결선의 **채움색**(예: `BadgeStageRail`의 `connectorBackground` 그라데이션,
  411~419행)까지 바꾸라는 요청인지, 텍스트(수치) 한정인지 사용자 표현("수치값")상으로는
  텍스트 한정으로 읽힌다 — **막대·연결선 채움색은 이번 범위에서 유지**하고 캡션·값 텍스트
  색만 바꾼다. 구현 착수 시 화면으로 재확인할 것.
- `progressComplete`(획득 조건은 채웠지만 게이트만 남은 상태, 501행)의 라임 색은 이번 변경
  대상이 아니다 — "진행 중"(조건 미충족) 상태 하나만 바꾼다.

## 구현 계획

> 개략적 순서 — 착수 시 최신 화면 스크린샷으로 2-4·3의 세부를 재확인한 뒤 확정할 것.

1. `BadgeTreeSummaryHeader.jsx` — 1번(전체 칸 막대 제거·재배치) + 스토리 갱신.
2. `BadgeStageRail.jsx` — 2-1(펼친 목록 조건값) → 2-2/2-3(등급 바→칩, 두 호출부 함께 정리)
   → 2-4(연결선 위치, 2-3 반영 후 재확인) → 3(캡션 색) 순으로 처리. 같은 파일을 여러 항목이
   건드리므로 항목 간 되돌아가지 않도록 이 순서를 지킬 것.
3. `BadgeLevelGauge.jsx` — 3번(값 색)만 해당.
4. 등급칩 형태가 신규 UI면 `/jam-design`으로 재사용 판정 먼저.
5. 스토리 갱신: `BadgeStageRail.stories.tsx`(등급칩·펼친 목록 조건값 케이스),
   `BadgeLevelGauge.stories.tsx`(진행 중 값 색).
6. 검증: `npx tsc --noEmit` · `npx eslint`(변경 파일) · `npm run ds:check`.

### 하지 않는 것

- 발급 엔진·`computeBadgeProgress`·진행 계산 로직 변경
- `--status-short-solid` 등 공용 시맨틱 토큰 값 변경 (다른 화면에 영향)
- `RarityBadge.jsx`의 기존 변형(펼친 목록용) 변경 — 신규 소형 변형이 필요하면 별도 컴포넌트로
- 진행 막대·연결선 채움색 변경 (수치 텍스트 색만)
- `/badges`·`/badges/[id]` 등 다른 화면 변경
- `20260906_1323`에서 다룬 나머지 8건 재작업
