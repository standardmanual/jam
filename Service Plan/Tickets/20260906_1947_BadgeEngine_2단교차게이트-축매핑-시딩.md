# [BadgeEngine] 2단 교차 게이트 — 축→계열 확장 매핑·시딩·중복구현 통합

> 분리 출처: `20260906_0110`「함께 다뤄야 하는 것」·「교차 게이트 판정이 두 곳에 재구현돼 있다」.
> 마스터: `20260905_0026`. `0110`(엔진 확장 5건)과 병렬로 진행 가능 — 서로 다른 파일을 건드린다.

## 배경 / 문제 정의

v5 630종 시딩(`0035` B2)에서 **2단 교차 게이트를 한 행도 넣지 않았다.** 설계 데이터의
`cross`/`cross2` 표시가 걷기 사다리에만 있고 4종목 사다리에는 0건이라, 지어내지 않고
비워둔 것이 타당한 판단이었다(`0110` B1 판단 재확인).

**실측(2026-09-06, 이 티켓 착수 전 재확인)**:
```sql
select count(*) filter (where condition_json ? 'gate_mission_badge') as gate_mission_badge_cnt,
       count(*) filter (where condition_json ? 'cross_in_axis') as cross_in_axis_cnt,
       count(*) filter (where condition_json ? 'cross_between_axis') as cross_between_axis_cnt,
       count(*) filter (where rarity = 'mystic') as mystic_cnt
from badges where type='activity' and deleted_at is null;
-- {gate_mission_badge_cnt:0, cross_in_axis_cnt:0, cross_between_axis_cnt:0, mystic_cnt:98}
```
```sql
select count(*) as total, count(*) filter (where gate_axis is not null) as axis_based,
       count(*) filter (where gated_badge_id is not null) as legacy_gate
from missions;
-- {total:30, axis_based:0, legacy_gate:0}
```
Mystic 98종 전부 무관문 상태고, 미션 30건 중 게이트 배지를 여는 미션도 0건이다.
`mission_reward` 조건을 가진 게이트 배지 40종(종목당 8)은 이미 시딩돼 있으나 연결이 없다.

**엔진 코드는 이미 있다** — `crossGate.ts`(`normalizeGateRequirement`·`countSatisfiedFamilies`),
`visibility.ts`(축 경로), 마이그레이션 135(`missions.gate_axis`·`gate_stage`·
`visibility_rule_json`)까지 전부 구현·배포됐다(`0030`·`0033`). **비어 있는 건 데이터뿐이다.**

## 상세 요구사항

### 서비스/코드베이스 관점

**① 축→계열 확장 규칙 확정**
- 설계 원본에 이미 있는 교차짝 데이터를 사용한다 — **새로 지어내지 않는다**:
  - `Specs/Content/v5_catalog_design.json`의 `걷기.축간교차`·`걷기.축내교차짝`·
    `four종목.교차짝`(러닝 4·자전거 3·등산 2·트레일 2, `0035` A묶음이 실제 계열 조건과
    전수 대조해 일치 확인함)
  - `Specs/Content/v5_mission_badges.json`의 `여는축`(미션 32종이 여는 축, `0110`이
    "축 배정 32건이 확정본과 완전 일치" 검증 완료)
  - `Specs/Content/v5_catalog_verified.json`의 `교차게이트_정정` 7건(러닝 이정표 관문을
    스플릿→휴식으로 대체 등, `0035` A묶음 게이트 리뷰에서 확정)
- Rare→Epic(축 내 교차 또는 축 간 교차)·Epic→Mystic(축 간 교차 + 미션 보상 배지) 두 단계를
  `family_key` 단위 `condition_json`(`cross_in_axis`/`cross_between_axis`/`gate_mission_badge`)
  으로 변환한다 — 마스터 티켓(`0026`) §게이트(2단) 표가 원 설계다.
- **누적 축을 관문으로 지정한 교차짝 11건은 자동 통과된다**(`0110` 잔여 이슈 — 레벨형은
  `min_level` 표현 수단이 없어 「Lv.1 보유」가 전부). 이번 범위에서 고치지 않는다면
  왜 미루는지 완료 기록에 남긴다.

**② 미션 30건 → 게이트 미션으로 전환 또는 신규 생성**
- 4종목 미션 보상 배지 32종(`0035` B묶음 선행조건 ⑥ 산출물, `v5_mission_badges.json`)의
  「여는 축」에 맞춰 `missions.gate_axis`·`gate_stage`·`visibility_rule_json`을 채운다.
- 걷기 미션 8종도 같은 방식으로 채운다(`0035`가 이미 걷기 8종을 시딩했다 — `mission_reward`
  조건 배지 확인 필요).
- 어드민 `/admin/gate-missions`(`0033`)의 정합성 검사(축은 있는데 미션 없는 구멍 등)로
  커버리지를 검증한다 — `0033` 잔여 이슈의 "카탈로그 기준 축 커버리지 대조"가 이 작업이다.

**②-b `min_level` 부재로 인한 누적 축 관문 자동통과 (2026-09-06 사용자 지시로 범위 편입)**
- 레벨형(무한레벨) 계열은 등급이 없어 「Lv.N 이상」을 게이트 요구 조건으로 표현할 수단이
  없다 — 지금은 「그 계열을 하나라도 보유」(=Lv.1)가 전부라, 첫 주에 달성되는 Lv.1로
  관문 11건이 사실상 자동 통과된다.
- `normalizeGateRequirement`/`countSatisfiedFamilies`(`crossGate.ts`)의 요구 객체에
  `min_level`(선택 필드)을 추가하고, 레벨형 계열 보유 판정 시 `level >= min_level`을
  함께 확인하도록 확장한다. 등급형(`min_rarity`)과 나란한 필드로 설계한다.
- 11건의 교차짝 각각에 적절한 `min_level` 값을 정하는 것은 콘텐츠 판단이 필요하다 —
  `v5_catalog_verified.json`의 사다리 데이터(각 레벨의 임계값)를 참고해 "Epic 등급형의
  관문 강도와 비슷한 체감 난이도"가 되는 레벨을 고른다. 애매하면 오케스트레이터에게 확인한다.
- 마이그레이션 135의 CHECK 제약(노출 규칙 허용 키 3개)에 `min_level`이 포함돼 있는지
  먼저 확인 — 없으면 소규모 마이그레이션이 추가로 필요하다.

**③ `crossGate.ts` ↔ `badgeTree.ts` 중복 구현 통합**
- `0110`이 찾은 결함: `badgeTree.ts`(화면)가 `crossGate.ts`의 `countSatisfiedFamilies` 규칙을
  **별도로 재구현**했다. 두 구현이 갈리면 "열려 보이는데 발급은 안 되는" 상태가 생긴다.
  게이트 데이터를 채우기 **전에** 하나로 합친다 — 지금은 데이터가 0건이라 사용자 영향이
  없지만, 이번 티켓이 데이터를 채우는 순간 그 위험이 실현된다.
- `crossGate.ts` 쪽 함수가 `ownedDefs` 전량을 요구해 `badgeTree.ts`가 조회를 늘리기 싫어서
  재구현한 것이 원인이었다(`0110` 기록) — 조회 시그니처를 조정해 공유하거나, `badgeTree.ts`가
  이미 들고 있는 데이터로 `crossGate.ts` 함수를 호출할 수 있게 인터페이스를 바꾼다.

### 컨텐츠 관점

## 구현 기록 (2026-09-06, status는 오케스트레이터 승인 전까지 OPEN 유지)

### ① 축→계열 매핑 — 스크립트로 산출

`Service Plan/Specs/Content/v5_gate_mapping_build.py`가 설계 원본 3종
(`v5_catalog_design.json`의 걷기.축간교차·걷기.축내교차짝·four종목.교차짝,
`v5_catalog_verified.json`의 교차게이트_정정 7건 전부 반영, `v5_mission_badges.json`·
`v5_mission_axis_groups.json`의 여는축)에서 실제 시딩된 194계열(`seed_v5_activity_badges.rows.json`)
을 기준으로 family_key 단위 매핑을 기계적으로 추출해 `v5_gate_mapping.json`(정본, 135계열)으로
산출했다. `v5_gate_mapping_sql_build.py`가 그 JSON만 읽어 `142_gate_cross_badges_v5.sql`
(UPDATE 270건 — 대상 없는 계열은 안전하게 no-op)을 만들었다.

**판정 규칙**(모두 원본 데이터 기반, 임의 창작 없음):
- 축 내 교차 가능(원본이 「축 내」로 표시하고 걷기는 페어를 명시): 그 페어를 `cross_in_axis`로,
  2단 보완축을 `cross_between_axis`로 **둘 다** 건다(OR).
- 축 내 교차 불가(원본이 다른 축 이름을 명시): 그 축을 `cross_between_axis`로만 Rare→Epic에,
  2단 보완축을 Epic→Mystic에 건다(축이 다르면 서로 다른 필드).
- **원본이 축 내 페어를 특정하지 않은 경우**(러닝 휴식 R-X2, 러닝·자전거·등산 달력 3계열
  조합) — 페어를 지어내면 "같은 활동으로 동시 달성되는 가짜 관문"을 만들 위험이 있어(달력
  축 자체가 이 위험으로 이미 한 번 정정됐다) 축 내 교차를 비우고 축 간 교차만 건다.

### ②-b `min_level` — crossGate.ts·visibility.ts 양쪽 확장

`BadgeGateRequirement`/`NormalizedGateRequirement`에 `min_level`을 추가했다(`min_rarity`와
동시 지정 불가). `crossGate.ts`의 `familyMeetsGateRequirement`가 `level >= min_level`을
판정한다. **`missions.visibility_rule_json`도 같은 타입·같은 검증 함수를 쓰므로**
`src/lib/missions/visibility.ts`·`visibility-server.ts`도 함께 확장했다(`ownedFamilyLevels`
맵 추가) — 배지 발급만 고치고 미션 노출 판정을 놓치면 "미션은 계속 보이는데 Mystic은 막힌"
반대 방향 불일치가 생긴다.

무한레벨(누적) 축이 보완 축으로 지정된 관계는 5종목 합쳐 **13건**(0110이 예고한 "11건"은
개략치 — 스크립트가 관계 단위로 정밀히 세어 확정)이며 전부 `min_level: 5`(Epic→Mystic 상당,
걷기 K1 사다리 원본의 "Lv.5~7=cross 관문 진입" 경계를 그대로 씀)를 받았다.

**마이그레이션 135의 CHECK 확인 결과**: `min_level`을 위한 추가 마이그레이션은 **불필요**하다
— 135의 `missions_visibility_rule_shape` CHECK와 134의 `badges_condition_json_known_keys`
CHECK는 둘 다 **최상위 키 이름만** 검사하고, `cross_between_axis`/`require_owned` 등 내부
객체의 필드(`min_level` 포함)는 애초에 DB 제약 대상이 아니다(앱의 `normalizeGateRequirement`가
유일한 검증 지점).

### ③ crossGate.ts ↔ badgeTree.ts 중복 통합

`crossGate.ts`에 `familyMeetsGateRequirement()`를 export해 엔진(`countSatisfiedFamilies`)과
화면(`badgeTree.ts`의 `familyLock`)이 같은 함수를 부르게 했다. `badgeTree.ts`는 이미 들고 있는
`BadgeTreeSourceBadge[]`를 `earnedBadgeIds`로 필터링해 `ownedDefs`를 만들 뿐 추가 조회는 없다
(화면이 재구현했던 이유 자체가 성립하지 않았다).

### ② 미션 40건 — UPDATE-or-INSERT

`v5_gate_missions_sql_build.py`가 `v5_gate_mapping.json`의 `gate_mission_badge` 역참조로
`gate_axis`(대표 축)·`visibility_rule_json`(연 축 전체 합집합)을 산출하고, 미션 **자체의
달성 조건**은 표로 직접 명시해 `143_gate_missions_v5.sql`을 만들었다(기존 30건 중 제목이
일치하고 `gate_axis IS NULL`인 것은 UPDATE로 전환, 없으면 INSERT — idempotent).

### 실측 중 발견해 함께 고친 것 (④ 어드민 정합성 검사 관련)

시뮬레이션 데이터로 `checkGateMissionConsistency`를 직접 돌려 "0건" 목표를 검증하다가
그 검사 함수 자체의 결함 2건을 발견해 함께 고쳤다(`src/lib/missions/gateMissions.ts`):
1. `axis_stage_gap`이 `rare_to_epic`도 항상 요구해, 이 카탈로그(게이트 미션 40건 전부
   Epic→Mystic 전용, 마스터 티켓 설계 자체가 Rare→Epic에 미션을 요구하지 않는다)에서는
   축 53개 전부가 영구 오탐됐다. `rare_to_epic`이 비어 있는 것은 더 이상 오류가 아니다.
2. 레벨형+등급형이 섞인 `visibility_rule_json`(「누적+이정표」 동시 개방 미션 4건)에
   등급 하한을 걸면 절반이 영원히 미충족이었다. 이 4건은 하한 없이 완화했다(발급 게이트
   자체는 각 배지의 `cross_between_axis`가 그대로 지킨다).

수정 후 시뮬레이션 재실행 — **issues 0건** (`checkGateMissionConsistency`, 135계열·40미션
합성 데이터 기준).

### 커버리지 관측성 한계 (알려진 채로 남김)

53개 게이트 대상 축 중 13개는 항상 "다른 미션의 부축"으로만 열려(미션 40개 < 축 53개는
설계 의도) 매트릭스에 행 자체가 생기지 않는다 — 기능은 정확하지만 어드민 화면만으로는
그 13개 축의 커버리지를 확인할 수 없다. 상세는 `BADGE_ENGINE_UNIFIED.md` §2.15 참조.

### 미션 조건 근사 (32건 중 다수, [WARN])

`MissionCondition`(및 어드민 게이트 미션 폼)이 "필드 하나 + activity_type" 단일값만
지원해, 원문의 복합 조건(단일활동 임계값+반복, 페이스, 시간대, 다음 날 휴식, 서로 다른
두 달 등)을 표현할 mission_type이 없다 — 근접한 단일 누적값으로 근사했다. 상세 목록은
아래 구현 요약 alerts 참조.
