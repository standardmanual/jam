# [UI] 배지 트리 대시보드 — 정렬 엣지 통합·진행률 스캔 컬럼·상태 색 램프

## 배경 / 문제 정의

`/badges/tree`의 일은 **「전체 액티비티 배지를 조망하고, 지금 내가 어디이고, 앞으로
얼마나 더 가야 하는지」를 한 번에 알려주는 것**이다. 지금은 39장의 카드가 각자 다른
문법으로 그려져 **세로로 훑을 축이 하나도 없다.**

배포된 staging(`stage.j-a-m.app/badges/tree?activity=walking`, 걷기 탭 0/145)을
Chromium 375·320px에서 직접 실측한 값이다:

| 측정 항목 | 실측값 | 문제 |
|---|---|---|
| 계열명 시작 x | **32 / 88 px** | 레일 카드는 카드 패딩 엣지, 레벨·반복 카드는 썸네일(44)+갭(12) 뒤 |
| 계열명 글자 | **16 / 14 px** | 같은 위계인데 두 크기 |
| 그리드 셀 계열명 | x=16 · **12px** | 세 번째 문법(티켓 20260906_1425가 추가) |
| 레일 연결선 폭 | **37 / 25 / 21 / 14 px** | 한 화면 네 카드에서 제각각 |
| 한 레일 안 캡션 높이 | **14 / 29 / 43 px** | 눈금 열 높이가 86 / 101 / 115px로 어긋남 |
| 등급칩 · 레벨칩 | **8 px** | 등급이 이 화면의 핵심 정보인데 판독 불가 |
| 진행률 스캔 컬럼 | **없음** | 수치가 타입마다 다른 자리 |

**레일 결함의 기전이 실측으로 확정됐다.** 눈금 열이 `flex:none; minWidth:48`인데
캡션은 `maxWidth:92`까지 번진다 — **열 폭을 캡션 글자 수가 정한다.** 그래서 카드마다
레일 간격이 2.6배까지 벌어진다. 「텍스트 양에 따라 위치가 흔들린다」의 정체다.

색은 OKLCH로 환산해 쟀다:

```
lime  #d6f24a  L .911  H 118.6°   ← 다 채움
amber #f2cb00  L .851  H  94.9°   ← 채우는 중
                      ─────────
                      23.7° 차이, 밝기 0.06 차이
```

색상 23.7°·밝기 0.06으로는 「시작 전 / 진행 중 / 다 채움」 세 단계를 못 가른다.
게다가 amber는 **Epic 등급칩(H 73.2°)과 21.7°**로 붙어 있어 같은 카드에서 진행색과
등급색이 한 덩어리로 읽힌다. 그리고 **진행 중인 카드(42%·33%)의 진행률이 lime**으로
칠해져 있다 — lime은 이 서비스에서 「다 채웠다」 하나만 뜻한다.

## 상세 요구사항

### A. DS 토큰 추가 (`design-system/tokens/colors.css`)

**색값을 새로 만들지 않는다.** 다섯 줄 전부 기존 토큰을 가리키는 역할 별칭이라,
추가만으로는 `RarityBadge`를 쓰는 서비스 9개 파일을 포함해 **어떤 값도 달라지지 않는다.**

```css
/* ── 진행 상태 채널 (티켓 20260906_2140) ──────────────────────
 * 밝기가 「지금 얼마나 신경 쓸 곳인가」를, 색상이 「어떤 종류인가」를 맡는다.
 * lime(H 118.6°)과 amber(H 94.9°)가 23.7°밖에 안 떨어져 있어 색만으로는
 * 3단계를 가를 수 없다 — 가운데 단계에서 색을 빼고 밝기를 최대로 올린다.
 *
 * 왜 컴포넌트가 --color-text를 그냥 쓰면 안 되나: 「진행 중이면 가장 밝게」는
 * 본문 위계가 아니라 상태 규칙이다. 나중에 본문 색을 낮춰도 상태 채널은
 * 따라가면 안 된다(토큰을 역할 밖에서 빌려 쓰지 않는다). */
--status-progress-idle:   var(--color-text-secondary); /* 시작 전 */
--status-progress-active: var(--color-text);           /* 진행 중 — 지금 내 차례 */
--status-progress-near:   var(--status-short-solid);   /* 거의 다 (≥80%) */
--status-progress-done:   var(--status-done-solid);    /* 다 채움 · 획득 */

/* 채움 스윕 — 트랙 전체에 깔고 clip-path로 잘라 「어디까지 초록으로 넘어갔나」가
 * 곧 진행도가 되게 한다. ProgressBar.jsx의 PROGRESS_TRACK_GRADIENT를 CSS로 옮긴 것 —
 * 레일 연결선·링이 JS 상수를 import할 수 없어 한 화면에서 진행 표현이 셋으로 갈라져 있었다. */
--status-progress-sweep: linear-gradient(90deg in oklab,
    var(--status-short-solid), var(--status-done-solid));
```

- `ProgressBar.jsx`의 `PROGRESS_TRACK_GRADIENT`를 **새 토큰을 가리키게** 바꿔 그라데이션
  정의가 한 군데만 남게 한다. (기존 값은 `to right` + sRGB 보간 → `90deg in oklab`으로
  바뀐다. amber↔lime은 인접 색상이라 시각 변화는 미미하다. 이 1건이 이번 티켓에서 유일하게
  **기존 화면에 영향을 주는 변경**이므로 완료 기록에 명시할 것)

**상태 램프 적용 규칙** — 진행률 `fraction`(0~1) 기준:

| 상태 | 토큰 | 조건 |
|---|---|---|
| 시작 전 | `--status-progress-idle` | `fraction === 0` 또는 진행 계산 불가(muted) |
| 진행 중 | `--status-progress-active` | `0 < fraction < 0.8` |
| 거의 다 | `--status-progress-near` | `0.8 <= fraction < 1` |
| 다 채움·획득 | `--status-progress-done` | `fraction >= 1` 또는 `status === 'earned'` |

임계값 `0.8`은 CSS 토큰이 아니라 **공유 JS 상수**로 둔다
(`src/lib/badgeProgressText.ts`에 `NEAR_THRESHOLD = 0.8` 등). 정책 숫자라 색 토큰이 아니다.

### B. 신규 MODULAR 패턴 — `BadgeFamilyCardHeader`

**정렬 엣지가 갈라진 근본 원인은 네 패턴이 각자 헤더를 그린다는 것이다.**
매니페스트 확인 결과 공유 헤더 부품이 없다. 각 파일을 따로 고치면 지금은 맞지만 다음
패턴이 추가되는 순간 또 갈라진다 — 실제로 `BadgeProgressRingCard`(20260906_1425)가
세 번째 이름 위치를 만들어 냈다.

```
[계열 이름 1fr]  [87% EPIC auto — 카드 우측 패딩 엣지에 정렬]
[메타 한 줄 1fr] [자세히 ⌄ auto — 펼침 가능한 카드만]
```

props(안): `name` · `fraction` · `pctLabel`(예 `Rare`·`Lv.8`·`26회`) · `metaText`(ReactNode) ·
`expanded` · `onToggleExpand`(없으면 자세히 미표시). **문구 조립은 하지 않는다** —
완성 문자열만 받는다(기존 DS 원칙 유지).

- 이름: `--text-body`(16px) / 600 / `word-break: keep-all` + `overflow-wrap: anywhere`.
  **말줄임 금지** — 계열명이 곧 지표다(20260906_1323 §5 유지)
- 진행률 블록: **`87%`와 등급/레벨 라벨을 한 줄에 나란히 둔다.** 세로로 쌓지 않는다
  (2026-09-06 사용자 지시 — 예시 `자정의 정복자  87% EPIC`)
  - 퍼센트: `--text-body`(16px) / 600 / `tabular-nums` / 상태 램프 색
  - 라벨: `--text-micro`(11px) / `--status-progress-idle` / 대문자 / 퍼센트와 `--spacing-4` 간격
  - 블록 전체는 `white-space: nowrap`, 카드 **우측 패딩 엣지에 붙인다**
- 메타 줄: `--text-small`(14px) / `--color-text-secondary`

### D. 요약 헤더 재편 (`BadgeTreeSummaryHeader.jsx`)

현재 3열 셀 안의 순서가 **막대 → 라벨 → 값**이라 무엇에 대한 막대인지 모른 채 막대를
먼저 본다. 셀 폭이 96px이라 값이 12px·막대가 6px로 눌린다.

- **1층 히어로**: `획득 12 / 145`(`--text-h3` 28px) + 우측 `8%`(`--text-body-l`)
  - ⚠️ **전체 진행 막대는 넣지 않는다** — 티켓 20260906_1436의 결정을 **유지**한다
    (2026-09-06 사용자 재확인). 등급 버킷의 막대는 그대로 남는다
- **2층 버킷**: **2열** 그리드로 바꿔 셀 폭 ~148px 확보. 값 `--text-small`(14px), 막대 8px
- 셀 안 순서를 **라벨 + 값 → 막대**로 뒤집는다
- 라벨 앞에 등급색 8px 도트 (등급 식별을 색으로도)
- **등급 순서를 Common → Rare → Epic → Mystic → 레벨**로 (2026-09-06 사용자 확정).
  「앞으로 얼마나 더」를 읽는 순서와 같아진다. 레벨 칸은 2열 전체를 쓴다(다른 축이고,
  5개를 2열에 넣으면 마지막 하나가 혼자 남는다)

### F. 별도 수정사항 (2026-09-06 사용자 지시)

1. **「다음 목표」 섹션의 접고 펴는 기능 제거.**
   `BadgeStatusSection`의 chevron·토글을 이 화면에서 쓰지 않는다. 섹션은 항상 펼쳐진
   상태로 제목 + 개수만 보여준다.
   ⚠️ `BadgeStatusSection`은 **서비스 1곳만** import한다(`BadgeTreeClient`). 컴포넌트를
   지우지 말고 **호출부에서 접힘을 쓰지 않는 형태**로 바꾸거나, 정적 헤더로 대체할지
   구현자가 판단해 티켓에 근거를 남길 것. 접힘 제거로 「펼친 섹션만 계산」 최적화
   (`BadgeStatusSection` 주석)가 무의미해지는데, 어차피 `defaultOpen`이라 현행도 항상
   계산하고 있다 — 회귀 없음을 확인할 것.

2. **자물쇠는 이모지가 아니라 TabBar 아이콘 스타일 SVG.**
   실측 결과 **코드에는 이모지가 없다** — 시안(아티팩트)의 🔒는 목업 플레이스홀더였다.
   현행 `LockGlyph`는 이미 `viewBox="0 -960 960 960" fill="currentColor"`(TabBar와 동일한
   Material Symbols 채움 스타일)이다. 따라서 요구사항은 두 가지다:
   - 구현에 **이모지를 절대 도입하지 않는다**
   - `BadgeStageRail.jsx:112`와 `BadgeProgressRingCard.jsx:51`에 **중복 선언된
     `LockGlyph`를 공유 모듈 하나로 통합**한다(체크 글리프도 같은 중복). 지금은 두 벌이라
     한쪽만 고치면 갈라진다
   - ⚠️ `src/components/ui/icons.tsx`의 `LockIcon`은 **stroke 아웃라인 스타일**이라 다르다.
     이걸 쓰지 말 것 — TabBar 스타일은 채움(fill)이다

3. **배지 이미지를 여백 없이 프레임에 꽉 채운다.** 보더 라운드로 잘리게 한다.
   - 현행: `padding: 3px`(레일·레벨·스탬프) / `4px`(2축) / `6px`(링) + `objectFit: contain`
   - 변경: `padding: 0` + `objectFit: cover` + 프레임에 `overflow: hidden`
   - ⚠️ 프레임의 `border-radius`와 이미지의 radius가 **따로 걸려 있으면** 모서리가 삐져
     나온다. 이미지에 radius를 걸지 말고 **프레임의 `overflow: hidden`으로만** 자른다

4. **진행률/등급을 계열명 오른쪽에, 한 줄로 둔다.**

   목표 형태 (2026-09-06 사용자 지시, 예시 그대로):

   ```
   자정의 정복자                    87% EPIC
   다음 Epic · 두 조건을 한 번의 활동에서   자세히 ⌄
   ```

   - **`87%`와 `EPIC`을 세로로 쌓지 않는다.** 한 줄에 나란히 둔다
   - 이 블록을 **카드 우측 패딩 엣지에 붙인다** — 모든 카드 타입에서 같은 우측 엣지를
     공유해야 세로로 훑는 스캔 컬럼이 성립한다(이번 티켓의 핵심)
   - chevron이 그 오른쪽을 차지하면 진행률이 안쪽으로 밀려 컬럼이 어긋난다.
     **「자세히 ⌄」는 헤더 2행(메타 줄) 오른쪽 끝**으로 옮겨, 1행 진행률과 2행 자세히가
     같은 우측 엣지를 쓰게 한다
   - 등급 라벨은 **텍스트**다 — `RarityBadge` 칩을 여기에 쓰지 않는다. 칩을 쓰면 레일
     안의 등급칩과 경쟁해 같은 카드에 등급 표기가 두 종류가 된다

   > 구현자 재량 아님 — 이 배치가 이번 티켓의 요구사항이다. 다른 배치가 낫다고 판단되면
   > 구현하지 말고 티켓에 근거를 적어 오케스트레이터에게 보고할 것.

5. **미획득 배지는 그레이스케일.**
   현행 `filter: grayscale(1)`이 이미 적용돼 있다(2026-09-06 사용자 확정 이력). **유지하고,
   위 3번(padding 0 + cover)으로 바꾸는 과정에서 필터가 유실되지 않는지 확인**한다.
   획득 배지는 원본 컬러.

  토큰으로 스냅하고, 기하값(52px 썸네일 등)은 **컴포넌트 로컬 상수**로 둔다
