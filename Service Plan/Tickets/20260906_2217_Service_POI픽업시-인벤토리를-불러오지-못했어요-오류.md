# [Service] 지도 POI 아이템 배지 픽업 시 "인벤토리를 불러오지 못했어요" 오류

## 배경 / 문제 정의
사용자가 지도 POI에서 드랍된 아이템 배지를 픽업하려고 하면
"인벤토리를 불러오지 못했어요. 잠시 후 다시 시도해 주세요" 토스트가 뜨며 픽업이 실패한다.
재시도해도 같은 오류가 반복되는 것으로 보인다(문구가 "잠시 후 재시도"를 안내하지만
일시적 오류가 아닐 가능성).

## 상세 요구사항

### 서비스/코드베이스 관점
- 오류 문구는 `jam-web/src/lib/i18n/ko.ts:436` `drops.loadInventoryFailed`.
- 이 문구가 뜨는 경로는 [PoiCarouselModal.tsx](jam-web/src/components/PoiCarouselModal.tsx) 세 곳:
  1. `openInventory()` (179줄) — `/api/inventory/items` fetch 자체가 실패(네트워크/파싱 예외)
  2. `executeDrop()` 중 서버가 `inventory_not_found` 코드 반환 (207줄, 드랍 시)
  3. `executePickup()` 중 서버가 `inventory_not_found` 코드 반환 (261줄, **이번 신고 케이스**)
- 픽업 플로우([pickup/route.ts](jam-web/src/app/api/drops/[dropId]/pickup/route.ts))는
  114~123줄에서 픽업하려는 유저의 `inventory` 테이블 행을 조회하고, 없으면 `inventory_not_found`를
  반환한다. RPC `pickup_drop()` 내부에서도 146줄 매핑처럼 같은 코드를 돌려줄 수 있다.
  → **즉 이 유저는 `inventory` 테이블에 자신의 행이 없다는 뜻.**
- `inventory` 행은 회원가입 시 `handle_new_user()` 트리거(`001_initial_schema.sql`)가 생성한다.
  이 트리거는 과거 한 번 인벤토리 생성 구문이 누락된 채 운영 DB에 반영된 적이 있고
  (`079_fix_handle_new_user_missing_inventory.sql`), 이후 `129_inventory_policy_max_slots.sql`에서
  시그니처가 다시 갱신됐다. **신고한 유저가 언제 가입했는지, 현재 `handle_new_user()` 정의가
  실제로 inventory를 생성하는지, 그리고 해당 유저의 `inventory` 테이블에 행이 있는지부터
  Supabase에서 직접 확인할 것.**
- **오케스트레이터가 Supabase MCP(`ceehnkzdbecxwzxrhhns`, jam-prod — staging·프로덕션 공용
  단일 DB)로 직접 진단 완료. 원인 확정됨:**
  - `auth.users` 12명 / `public.users` 12명 / **`public.inventory` 0행** — 가입 유저 전원이
    인벤토리 레코드 자체가 없다. 신고 유저만의 문제가 아니라 **전체 유저 100% 결측**.
  - 트리거(`trg_on_auth_user_created`, `AFTER INSERT ON auth.users`, enabled)에 실제로 바인딩된
    함수(`handle_new_user()`, oid 17825)는 `INSERT INTO public.inventory (user_id, max_slots)`
    구문을 포함한 **정상 버전**이다 — DO 블록으로 동일 로직을 수동 실행해(즉시 롤백) 확인함.
    RLS는 함수 소유자가 `postgres`(`rolbypassrls=true`)라 무관.
  - 이 정상 버전은 **마이그레이션 129(`129_inventory_policy_max_slots.sql`, 실제 적용 시각
    `2026-09-04 07:41:58 UTC`)에서 도입**됐다. 최근 가입자(`ziyo88@gmail.com`,
    `2026-09-03 11:30:58 UTC`)도 이 적용 시각보다 앞선다 — **129 적용 이후 신규 가입자가
    아직 한 명도 없어 "트리거가 지금부터는 정상"이라는 사실만으로는 검증되지 않은 상태였다.**
  - `supabase_migrations.schema_migrations`에는 **079번 마이그레이션(`079_fix_handle_new_user_
    missing_inventory.sql`) 자체가 기록에 없다** — 078 다음이 082로 바로 뛴다. 즉 079는
    로컬 파일로는 존재하지만 **실제로 프로덕션에 적용된 적이 없다.** 이번에 함수가 정상인
    이유는 079가 아니라 129의 `CREATE OR REPLACE FUNCTION` 전체 재정의 덕분이다.
  - **결론**: 트리거는 이미 고쳐져 있다(129로). 남은 문제는 **129 적용 이전에 가입한 기존
    유저 12명 전원에 대한 `inventory` 행 백필**뿐이다. 트리거 자체를 다시 고칠 필요는 없다.
- **필요한 조치 (jam-developer가 SQL 파일로 작성 → 오케스트레이터가 승인 후 실행)**:
  ```sql
  INSERT INTO public.inventory (user_id, max_slots)
  SELECT u.id, COALESCE((SELECT max_slots FROM public.inventory_policy WHERE id = 1), 50)
  FROM auth.users u
  WHERE NOT EXISTS (SELECT 1 FROM public.inventory i WHERE i.user_id = u.id)
  ON CONFLICT (user_id) DO NOTHING;
  ```
  `jam-web/supabase/migrations/`에 `seed_` 접두사(1회성 데이터)로 저장 — 신규 컬럼/스키마
  변경이 아니라 데이터 백필이므로 `NNN_설명.sql`이 아니라 `seed_backfill_missing_inventory.sql`
  형태가 맞다.
- **회귀 방지**: 향후 같은 결측이 재발해도 사용자가 막히지 않도록, API 레벨(픽업/드랍/인벤토리
  조회 3곳)에서 `inventory_not_found`를 만났을 때 즉석에서 inventory 행을 생성하는 방어 로직
  추가를 검토. (근본 원인은 이미 백필로 해소되므로 이건 향후 재발 방지용 안전망 성격.)

### 구현 내용 요약
1. **백필 SQL 작성** — `jam-web/supabase/migrations/seed_backfill_missing_inventory.sql`
   (129 적용 이전 가입자 12명 전원의 `inventory` 행 결측을 `inventory_policy.max_slots` 기준으로
   백필. `WHERE NOT EXISTS` + `ON CONFLICT DO NOTHING` 이중 방어로 멱등. **작성만 하고 미실행** —
   실행은 사용자 승인 후 오케스트레이터가 처리).
2. **회귀 방지(get-or-create)** — `jam-web/src/lib/inventory/get-or-create.ts` 신규 작성.
   `inventory` 행이 없으면 `inventory_policy`의 `max_slots`(기존 `getInventoryPolicy()` 재사용)로
   즉석 생성. 동시 요청 경합(UNIQUE(user_id) 위반, 23505)은 재조회로 흡수. 아래 3곳에 적용:
   - `/api/drops/[dropId]/pickup` (114~123줄 대체) — 픽업 시 인벤토리 결측이면 즉석 생성 후 계속 진행
   - `/api/drops` POST(드랍) (260~268줄 대체) — 존재 확인만 필요(RPC가 user_id로 자체 재조회)
   - `/api/inventory/items` GET — 기존에는 `.single()` 에러를 무인벤토리와 실제 오류 구분 없이
     `{ items: [] }`로 흘려보냈는데, 이제 결측이면 생성까지 하고 여전히 빈 배열을 반환
     (신규 생성된 인벤토리는 아이템이 없는 게 맞으므로 사용자 체감 변화는 없음 — 다만 이후
     드랍/픽업 요청에서 결측 재발이 원천적으로 사라짐).
3. **UX 문구는 변경하지 않음** — get-or-create 도입 후 `inventory_not_found` 경로는 실제 DB
   삽입 실패(진짜 일시적 오류) 때만 도달하므로, 기존 "인벤토리를 불러오지 못했어요. 잠시 후
   다시 시도해 주세요" 문구가 여전히 적절하다고 판단.

### 주요 의사결정 / 핵심 메모
- **왜 트리거를 다시 고치지 않았나**: 오케스트레이터 진단으로 129 마이그레이션이 이미
  `handle_new_user()`를 정상 버전으로 재정의했음을 DO 블록 실측으로 확인했다. 남은 문제는
  과거 데이터 결측뿐이라 백필 SQL 하나로 충분하다고 판단.
- **get-or-create를 3곳 모두에 적용한 이유**: 티켓은 "inventory_not_found를 반환하는 지점"만
  명시했는데, `/api/inventory/items`는 원래 이 코드를 반환하지 않고 조용히 `{ items: [] }`로
  흘렸다. 그래도 같은 결측 시나리오이므로 여기서도 생성해 두면 이후 같은 유저의 드랍/픽업
  요청에서 결측이 재발할 여지가 완전히 사라진다 — 세 지점을 일관되게 방어하는 편이 안전하다고
  판단해 포함시켰다.
- **`/api/drops` POST에서 get-or-create 반환값을 RPC 인자로 넘기지 않은 이유**: `create_user_drop()`
  RPC(108_item_identity_custody_model.sql:236)가 `user_id`로 `inventory`를 `FOR UPDATE`로 직접
  재조회한다 — 라우트 레벨에서는 "존재 확인(및 필요시 생성)"만 하면 되고 id 값 자체는 쓰이지
  않는다(원래 코드도 그랬다).

### 잔여 이슈
- 백필 SQL 실행은 사용자 승인 후 오케스트레이터가 처리 (직접 실행 금지 규칙).
- 실행 후 검증 쿼리는 SQL 파일 하단에 포함해 둠(`auth.users` 대비 `inventory` 결측 0건 확인).
