# [Service] POI 픽업 재실패 — 2026-08-29 이전 드랍 2건의 inventory_item_id 백필 누락

## 배경 / 문제 정의
[티켓 20260906_2217](20260906_2217_Service_POI픽업시-인벤토리를-불러오지-못했어요-오류.md)의
인벤토리 결측 백필 배포 이후에도 사용자가 "픽업 안됨"으로 재신고했다. 조사 결과 **완전히
별개의 기존 결함**으로 확인됐다.

## 상세 요구사항

### 서비스/코드베이스 관점
- Vercel 런타임 로그(`jam-stage` 프로젝트)에서 `POST /api/drops/858a70bd-.../pickup`이
  최근 1시간 동안 반복적으로 404를 반환하는 것을 확인 — 배포된 최신 코드(get-or-create
  안전망 포함)에서도 동일하게 재현되어, 2217의 인벤토리 결측과는 무관함을 알 수 있었다.
- 원인: `poi_drops.inventory_item_id`가 NULL. [pickup RPC](jam-web/src/app/api/drops/[dropId]/pickup/route.ts)가
  호출하는 `pickup_drop()` 함수는 `v_drop.inventory_item_id IS NULL`이면
  `item_not_found`(→ 404)를 방어적으로 반환한다 — 주석: "이론상 도달하지 않아야 함
  (백필로 전부 채움)".
- 근본 원인: **2026-08-29 "개체 정체성 모델" 마이그레이션**(아이템 소유권 이전을
  `poi_drops.inventory_item_id` → `inventory_items` 연결로 관리하도록 개편, 티켓
  20260829_2101)이 그 이전(2026-08-27~28)에 생성된 활성 드랍 일부의 백필을 놓쳤다.
  전체 활성 드랍 82건 중 2건(`858a70bd-...`, `fa4c4c34-...`)이 해당 — 둘 다 `dropped_at`이
  2026-08-29보다 이전이다. 애초에 건네줄 아이템 개체가 연결된 적이 없어 복구 불가능.
- **2217과의 관계**: 무관한 별개 결함. 우연히 같은 날 같은 사용자가 연달아 픽업 실패를
  겪어 같은 사고로 오인하기 쉬웠다.

### UI/UX 관점 (해당 시)
- 이 경로(`item_not_found`)는 클라이언트의 픽업 에러 매핑(`PoiCarouselModal.tsx`)에
  명시적 항목이 없어 일반 실패 문구(`d.drops.pickupFailed`)로 흘렀다 — 결과 자체를
  무효화하므로 별도 문구 대응은 불필요하다고 판단.
