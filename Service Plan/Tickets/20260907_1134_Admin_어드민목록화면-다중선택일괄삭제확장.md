# [Admin] 어드민 목록 화면 다중선택 일괄삭제 확장

## 배경 / 문제 정의
> 왜 이 작업이 필요한가. 현재 상태와 기대 상태의 차이.

사용자 요청: "어드민의 모든 목록 페이지에서 다중선택으로 '일괄 삭제' 할 수 있는 기능을 추가해".

사전 조사(Explore 에이전트) 결과, 어드민 25개 메뉴 중 공용 `DataTable` +
`DataTableBulkActionBar`(`src/components/admin/data-table/`)를 이미 쓰는 화면이 8개 있고,
그중 POI·레시피는 이미 다중선택 하드 일괄삭제가 있다. 반면:

- **삭제 개념 자체가 없는 화면**(계열 관리·포인트 관리·유저 조회·아이템배지 현황 조회 전용·
  테마 컬러)은 대상에서 제외한다 — 사용자 확정.
- **미션 관리**는 참여 이력이 `ON DELETE CASCADE`로 걸려 있어 과거 티켓
  `20260826_015`에서 **의도적으로 다중선택 UI 자체를 뺐다.** 이번에 참조 가드를 새로
  만들어서 포함하기로 사용자가 결정.
- **컬렉션·세계관**은 현재 하드삭제(상세 폼에만 존재)에 참조 가드가 없어, 세계관은
  드랍정책 인접행렬이, 컬렉션은 유저 진행 슬롯(`user_item_book_slots`)이 CASCADE로
  조용히 사라질 수 있다. 가드부터 만든 뒤 일괄삭제를 추가하기로 사용자가 결정.
- **배지 관리**는 단건 하드삭제에 이미 참조 가드(`lib/admin/badge-references.ts`)가
  있으나, 다중선택 일괄 액션은 현재 소프트 비활성화만 지원한다. 기존 가드를 재사용해
  일괄 하드삭제를 추가한다.
- **POI·레시피**(이미 하드 일괄삭제 존재, 가드 없음)는 이번 티켓 범위 밖이다.
  별도 작업(spawn_task `task_8332fcef`)으로 분리했다.

## 상세 요구사항

### 서비스/코드베이스 관점

**1. 참조 가드 유틸 신설 (미션·컬렉션·세계관)**

`lib/admin/badge-references.ts` 패턴(참조처 목록 → 카운트 → blockingTotal/cascadeTotal
판정)을 일반화해 아래 엔티티용으로 만든다. 완전히 공통 함수 하나로 추상화하지 말고
(엔티티마다 참조처·CASCADE 여부가 다름) 각 엔티티 전용 함수를 배지 파일과 유사한 형태로
작성하거나, `lib/admin/reference-guards.ts` 같은 공용 파일에 엔티티별 함수를 모아둔다.

- **미션**: 미션 참여 이력 테이블(`CASCADE` 대상), 보상/게이트로 미션을 참조하는 배지·
  게이트 미션 매트릭스를 확인해 참조 카운트 산출
- **컬렉션(item_books)**: `user_item_book_slots.item_book_id`(CASCADE), 그 외 이 배지
  가 컬렉션 조건/보상으로 참조되는 경우가 있다면 함께 포함
- **세계관(factions)**: 드랍엔진 인접행렬 테이블(`faction_id`/`adjacent_faction_id`,
  CASCADE), `badges.faction_id`·`item_books.faction_id`(`SET NULL` — 차단 사유는
  아니지만 안내 문구에는 포함)

각 삭제 API(단건 DELETE, 신규 일괄 DELETE 모두)에서 이 가드를 호출해 차단 대상이면
409 등으로 거부하고, 프런트에서 차단 사유(참조 개수)를 사용자에게 보여준다.

**2. 일괄 하드삭제 API**

- 미션: 신규 일괄삭제 API 라우트 추가 (참조 가드 통과 시에만 삭제)
- 컬렉션·세계관: 기존 단건 DELETE에 위 가드를 추가하고, 일괄삭제 API 신설
- 배지: 기존 단건 DELETE의 가드(`badge-references.ts`)를 그대로 재사용하는 일괄삭제
  API 신설 (이미 검증된 로직이므로 새 가드 불필요)
- 투데이 콘텐츠: 참조 위험이 낮다고 보고됨 — 별도 가드 없이 일괄 하드삭제 API 신설
  (기존 상세 편집기의 단건 하드삭제 로직을 참고)

순차 단건 호출(`Promise.all`로 개별 DELETE 반복)이 아니라, 가능하면 서버가 배열을 받아
한 번에 처리하는 진짜 배치 엔드포인트로 구현한다 (부분 실패 시 어느 것이 실패했는지
프런트에 알려줄 것 — 트랜잭션이 아니어도 결과는 항목별로 보고).

**3. 프런트 UI**

- 미션 관리(`/admin/missions`): `DataTable`에 `rowSelection` 활성화 + `DataTableBulkActionBar`
  에 "선택 항목 삭제" 버튼 추가. 차단된 항목이 섞여 있으면 결과를 항목별로 안내
- 컬렉션·세계관: 기존 "선택 항목 비활성화"(소프트) 옆에 "선택 항목 삭제"(하드) 버튼 추가.
  파괴적 동작이므로 확인 다이얼로그에 "되돌릴 수 없습니다"·영향받는 참조 개수를 표시
- 배지 관리: 기존 다중선택 액션바에 "선택 항목 삭제" 버튼 추가 (참조 있는 배지는 결과에서
  실패로 안내)
- 투데이 콘텐츠: 기존 액션바에 "선택 항목 삭제" 버튼 추가

### UI/UX 관점
- 모든 신규 "일괄 삭제" 버튼은 확인 다이얼로그(shadcn AlertDialog 등)를 거친다 —
  실행 즉시 삭제되는 버튼을 두지 않는다
- 참조 때문에 차단된 항목이 있으면 "N건 삭제됨, M건은 참조가 있어 건너뜀(사유)" 형태로
  결과를 안내한다 (전부 성공/전부 실패 이분법 금지)
- UX Writing 가이드(`Specs/UX_WRITING_GUIDELINE.md`)의 에러 메시지 3단계 구조 준수

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

1. `lib/admin/reference-guards.ts` 신설 — 미션·컬렉션(item_books)·세계관(factions) 전용
   참조 카운트 함수 3종(`collectMissionReferences`/`collectItemBookReferences`/
   `collectFactionReferences`) + 공용 포맷터 `summarizeReference`. `badge-references.ts`를
   참고해 만들었으나 하나의 공용 함수로 묶지 않고 엔티티별 함수로 분리했다(티켓 지시).
   FK 규칙은 마이그레이션 011·012·017·034·048·080·099를 직접 읽어 실측했다.
2. 단건 하드 DELETE 3곳(미션·컬렉션·세계관)에 위 가드를 연결 — 참조가 있으면 409로 차단.
   배지는 기존 `badge-references.ts` 가드를 그대로 재사용(신규 가드 없음), 투데이 콘텐츠는
   가드 없음(사전 조사대로 참조 위험 낮음).
3. 진짜 배치 엔드포인트 5종 신설(순차 단건 DELETE 반복 아님, 한 번의 `DELETE ... WHERE id IN (...)`):
   `missions/bulk-delete`, `itembooks/bulk-delete`, `factions/bulk-delete`,
   `badges/bulk-delete`(기존 필터 기반 `badges/bulk` 도구와는 별개), `today/bulk-delete`.
   전부 대상별 참조 여부를 나눠 `{ deleted: string[], blocked: {id, reason}[] }` 형태로
   항목별 결과를 보고한다.
4. 프런트 5개 화면에 "선택 항목 삭제" 버튼 + AlertDialog 확인 다이얼로그 연결
   (`MissionTable.tsx`는 이번 티켓에서 rowSelection 자체를 신규 도입 — 20260826_015가
   의도적으로 뺐던 기능). 컬렉션·세계관·배지는 기존 "비활성화" 버튼 옆에 "삭제" 버튼을
   추가했다. 결과 안내는 기존 코드베이스 관례(POI/팩션 등)를 따라 `alert()`로 "N건
   삭제됨, M건은 참조가 있어 건너뜀(사유)" 형태를 보여준다.
5. 미션 단건 삭제(`MissionList.tsx`)는 기존에 응답을 확인하지 않고 무조건 새로고침했다 —
   가드가 409를 돌려줘도 사용자가 알 수 없었으므로 에러 표시를 추가했다.

**사전 조사에 없던 발견(WARN)**: 컬렉션·세계관 가드 설계 중 `user_drop_state.last_drop_book_id`·
`user_drop_state.last_drop_faction_id`가 **ON DELETE 미지정(NO ACTION)**인 것을 마이그레이션
034에서 발견했다. 티켓 배경에 나열된 참조처(드랍 인접행렬·유저 진행 슬롯)에는 없던 자리다.
거의 모든 활성 유저가 `user_drop_state` 행을 가지므로, 실무에서는 이 한 자리가 컬렉션·세계관
하드 삭제를 사실상 항상 막는다(의도된 안전장치 방향이라 막되, 가드 설계 시점에 놓치기 쉬운
지점이라 별도로 남긴다).

**티켓 배경 문구와 실제 스키마의 불일치(INFO)**: "미션 참조 가드"절이 "보상/게이트로 미션을
참조하는 배지·게이트 미션 매트릭스"를 언급하나, 실제 스키마에는 `badges`가 `missions.id`를
참조하는 컬럼이 없다(반대로 `missions.gated_badge_id`/`reward_badge_ids`가 배지를 참조하는
방향뿐). "게이트 미션"도 별도 매트릭스 테이블이 아니라 `missions` 행에 `gate_axis`/`gate_stage`
컬럼을 추가한 것뿐(마이그레이션 135, 별도 테이블을 안 만든 이유가 그 파일에 명시돼 있음).
실제로 미션을 참조하는 자리는 `user_mission_completions`·`user_mission_participations`·
`mission_rank_snapshots`(CASCADE)와 `point_transactions.source_mission_id`(NO ACTION),
`today_cards.mission_id`(SET NULL) 다섯 곳이며, 가드는 이 다섯 곳을 기준으로 구현했다.
