# [UI] 아이템배지 개체별 상세 라우팅 + 컬렉션 장착 개체 선택 UI

## 배경 / 문제 정의

동일 배지를 여러 개 보유해도 **어디서 눌러도 같은 개체(같은 일련번호)의 상세 화면으로 간다.**
개체(`inventory_items`)는 DB상 이미 고유 일련번호로 구분되는데(티켓 20260829_2101에서 개체
정체성 확립), **URL이 전부 `badge_id` 기준이라 "어느 개체를 눌렀는가"가 화면에 도달하기 전에
소실**된다.

### 실측 재현 (sihyunrr@gmail.com, 2026-09-07 프로덕션 DB 조회)

| 배지 | 보유 | 일련번호 |
|---|---|---|
| 자외선 차단제 빈 통 | 3개 | `ZPRS545679` **[장착]** · `LJAE830165` · `LFCC439094` |
| 뜨거운 아스팔트 조각 | 2개 | `UPTF472117` **[장착]** · `ZHVQ777120` |
| 아지랑이의 환영 | 2개 | `MMBT829356` **[장착]** · `HGIB165351` |

현재 동작: 인벤토리의 `LJAE830165`를 눌러도, `LFCC439094`를 눌러도, 컬렉션에 장착된
`ZPRS545679`를 눌러도 **전부 `LFCC439094`가 표시된다.**

### 원인 (3중 복합)

1. **인벤토리 경로에서 개체 id 소실** — `InventoryGrid.tsx:63`이 `/inventory/{item_id}`로
   링크하지만, `inventory/[itemId]/page.tsx:32`가 `redirect('/badges/' + badge_id)`로
   개체 정보를 버린다. 티켓 [20260816_007](../P2-일반/20260816_007_UI_아이템배지-상세-hero-공통-컴포넌트화.md)에서
   "아이템배지 상세는 어디서 접근하든 내용이 동일하다"는 전제로 도입한 redirect다.
   **이번 요구사항이 그 전제를 무효화한다.**
2. **컬렉션 경로는 개체 id를 애초에 안 싣는다** — `SlotGrid.tsx:151`이
   `href={/badges/${badge.id}}`. 슬롯이 참조하는 `inventory_item_id`가 있는데도 쓰지 않는다.
3. **상세 화면이 대표 개체 1개를 임의 선정** — `badges/[id]/page.tsx:304`가
   `obtained_at DESC` 첫 번째(=가장 최근 획득분)를 대표로 잡아 `ItemSerialCode`에 넘긴다.

### 파생 정합성 오류 (원인 2+3의 결합)

컬렉션 슬롯 자동 장착은 `obtained_at ASC`(가장 오래된 것,
`collections/[id]/page.tsx:186-194`)를 고르는데, 배지 상세 대표는 `obtained_at DESC`(가장 최신)를
고른다. **정렬 방향이 반대**라, 컬렉션에서 장착 배지를 눌러 들어가면 실제 슬롯에 꽂힌 개체가
아닌 다른 개체의 일련번호가 크게 표시된다. 위 실측이 정확히 이 상태다
(장착=`ZPRS545679`, 표시=`LFCC439094`).

### 관련 문제 — 장착 개체를 사용자가 고를 수 없다

동일 배지를 여러 개 보유해도 컬렉션 장착 시 **선택 UI가 없다.** 서버가
`obtained_at ASC` 첫 번째를 말없이 장착한다. 사용자가 특정 일련번호를 골라 넣을 수단이 없다.

## 상세 요구사항

### 서비스/코드베이스 관점

**A. 개체 식별을 URL에 싣는다 — `?item={inventory_item_id}` 쿼리 파라미터 방식**

- `/badges/[id]`에 `item` searchParam 추가. 기존 `?u={username}`와 같은 계열로 확장한다.
- `inventory/[itemId]/page.tsx`: `redirect('/badges/{badge_id}?item={itemId}')`로 변경
  (redirect 자체는 유지 — 뒤로가기 히스토리 동작을 그대로 보존한다).
- `SlotGrid.tsx:151`: 슬롯이 있으면 `?item={slot.inventory_item_id}`를 붙인다.
  이를 위해 `collections/[id]/page.tsx`가 슬롯의 `inventory_item_id`를 SlotGrid까지 전달해야
  한다(현재 장착 칸은 `inventoryItem: null`로 떨어진다 — `page.tsx:196-208`).
- `badges/[id]/page.tsx`의 대표 개체 선정 로직:
  1. `?item`이 있고 **유효하면**(해당 개체가 이 `badge_id`이고, 조회 주체가 소유) 그 개체를 쓴다
  2. 없거나 무효하면 기존 fallback(미드랍 중 최신) 유지 — 배지 탭 직접 진입 경로 무영향
- **`?item` 검증 필수**: 타인 소유·타 배지·파괴된(`destroyed_at`) 개체 id를 넘겨도 남의
  일련번호가 노출되지 않아야 한다. 무효 시 `notFound()`가 아니라 **조용히 fallback**으로
  떨어뜨린다(링크 공유 시 깨지지 않게).
- 타인 프로필 열람(`?u=`) 시 일련번호 비노출 정책(`showSerial = isOwnBadge`)은 **그대로 유지**한다.

**B. 컬렉션 장착 시 개체 선택 UI**

- `collections/[id]/page.tsx`: `inventoryMap`이 badge_id당 1개만 남기는 것을 **후보 배열 전체**로
  바꾼다(미장착 + `destroyed_at IS NULL`, `obtained_at ASC` 정렬 유지).
- `SlotGrid`의 장착 버튼:
  - 후보 **1개** → 지금처럼 즉시 장착 (불필요한 시트 노출 금지)
  - 후보 **2개 이상** → 개체 선택 시트를 열고, 각 후보의 **일련번호를 표시**한다
  - 선택 → 해당 `inventory_item_id`로 기존 `POST /api/itembooks/{id}/slot` 호출
- **API·RPC 변경 불필요** — `slot_item_into_book(p_user_id, p_item_book_id, p_inventory_item_id)`가
  이미 개체 id를 받아 소유·중복 장착을 검증한다(`migrations/111_item_slot_atomic_rpc.sql:77-108`).
  `UNIQUE(user_id, item_book_id, badge_id)` 제약도 그대로 유지된다(컬렉션당 같은 배지 1개).

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

**A. 개체 식별을 URL에 싣는다 (`?item={inventory_item_id}`)**

1. `inventory/[itemId]/page.tsx` — `redirect('/badges/{badge_id}?item={itemId}')`.
   redirect 자체는 유지해 뒤로가기 히스토리 동작을 보존했다.
2. `badges/[id]/page.tsx` — `searchParams`에 `item` 추가(`SearchParamValue` + `singleQueryParam`,
   기존 `?u=`와 동일 계열). 대표 개체 선정을 「`?item`으로 지목된 개체 → 없으면 기존
   fallback(미드랍 중 최신)」 순으로 바꿨다.
   **검증은 추가 쿼리 없이 끝난다** — `allItemInventory`가 이미
   `inventory_id = 조회주체의 인벤토리` + `badge_id = 이 배지`로 좁혀 조회한 목록이라,
   그 안에서 id가 일치하는지 + `dropped_at`·`destroyed_at`이 비어 있는지만 보면
   소유·배지일치·생존이 모두 걸러진다. 무효값은 `notFound()`가 아니라 조용히 fallback.
   (`destroyed_at`을 이 판정에 쓰기 위해 select에 컬럼 하나를 추가했다)
3. `collections/[id]/page.tsx` — 슬롯 조회에 `inventory_item_id`를 추가해 SlotGrid까지 전달.
4. `SlotGrid.tsx` — 장착된 칸의 링크에 `?item`(또는 `?u=` 뒤에 `&item=`)을 붙인다.
   이로써 「컬렉션 자동 장착은 `obtained_at ASC`, 배지 상세 대표는 `DESC`」라 서로 다른
   개체를 가리키던 파생 정합성 오류가 근본적으로 사라진다(정렬 방향을 맞추는 대신,
   실제로 꽂힌 개체 id를 그대로 넘기는 방식으로 해결).

**B. 컬렉션 장착 시 개체 선택 UI**

- `collections/[id]/page.tsx` — `inventoryMap`(badge_id당 1개)을 `inventoryCandidates`
  (badge_id당 **미장착 후보 배열 전체**, `obtained_at ASC` 유지)로 교체.
  후보 조회에 `destroyed_at IS NULL`을 추가했다(파괴된 개체는 RPC가 어차피 거절하므로,
  나열하기 전에 목록 단계에서 제외).
- `SlotGrid.tsx` — 「추가」 버튼이 후보 수로 분기한다. **1개면 종전과 동일하게 즉시 장착**,
  2개 이상이면 개체 선택 시트를 연다. 선택 시 기존 `POST /api/itembooks/{id}/slot`을
  그대로 호출한다(API·RPC·스키마 변경 없음).

**UI 재사용 — 신규 MODULAR 컴포넌트 없음** (오케스트레이터 판정대로)

| 용도 | 사용한 것 |
|---|---|
| 선택 시트 | `src/components/ui/BottomSheet` (body 포털 + z-50, 기존 층 그대로. footer 없어 `pushBottomOverlay` 신고 대상 아님) |
| 후보 그리드 | `InventoryGrid` `mode="select"` + `BadgeGridCard` (`PoiCarouselModal`의 드랍 선택과 같은 조합) |
| 일련번호 | `@ds/components/patterns/ItemSerialCode` (`height=14`) |

`InventoryGridItem`에 `serial?: string`을 optional로 추가했다. **`serial`이 없으면 자식 노드가
종전과 완전히 동일**하도록 분기해, 기존 호출부 2곳(`/inventory`, 드랍 바텀시트)의 레이아웃이
바뀌지 않게 했다.

`height=14`는 추정이 아니라 `ItemSerialCode`의 비율 상수(`TILE_WIDTH_RATIO` 0.7 ×4 +
`GAP_RATIO` 0.025 ×4 + 숫자 타일 2.41h = **총 5.31h**)로 역산한 값이다. 3열 그리드에서 카드
콘텐츠 폭이 가장 좁아지는 360px 뷰포트가 80px인데, 14 × 5.31 ≈ **74.3px**로 들어간다
(390px→90px, 430px→103px).

검토한 대안:
- **(A) `/inventory/[itemId]` 개체 전용 화면 부활** — 티켓 20260816_007이 "단일 소스 유지"를
  위해 없앤 것을 되돌리는 셈이라 미채택. 화면 2벌 관리 부담이 그대로 재발한다.
- **(B) `/badges/[id]?item={inventory_item_id}`** — **채택.** 20260816_007의 단일 소스 원칙을
  깨지 않으면서 개체 식별만 얹는다. 기존 `?u=` 쿼리와 일관되고, `?item` 없는 진입은 기존
  동작을 그대로 유지하므로 회귀 표면이 좁다. redirect도 유지되어 뒤로가기 히스토리 동작이 보존된다.
- **(C) `/inventory/[itemId]`를 실화면으로 두고 컴포넌트만 공유** — (A)보다 낫지만 라우트가
  둘로 갈려 "어느 URL이 정본인가"가 다시 모호해진다. 미채택.

**「후보 1개면 시트를 열지 않는다」를 코드 분기로 둔 이유**

시트를 항상 열고 후보가 1개면 자동 선택하는 방식이 코드는 짧지만, 고를 것이 없는데 시트가
한 번 뜨는 것은 불필요한 단계다. 티켓 요구사항대로 호출부에서 갈랐다.

**정렬 방향을 맞추는 대신 개체 id를 넘기는 방식으로 고친 이유**

파생 정합성 오류(자동 장착 `obtained_at ASC` vs 상세 대표 `DESC`)는 양쪽 정렬을 같은 방향으로
맞춰도 겉으로는 해결된 것처럼 보인다. 하지만 그건 "우연히 같은 개체를 고르게" 만드는 것일 뿐,
**개체 선택을 사용자가 하게 되는 순간(요구사항 B) 다시 깨진다.** 실제로 꽂힌 id를 링크에
싣는 방식만이 선택 기능과 함께 성립한다.

  `height=14`(숫자 fontSize 7px)가 실제 기기에서 읽히는 크기인지 눈으로 봐야 한다.
