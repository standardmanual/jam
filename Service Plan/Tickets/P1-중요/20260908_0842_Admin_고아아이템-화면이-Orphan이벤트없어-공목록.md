# [Admin] `/admin/item-badges/orphaned` — 실제로는 325건 있는데 화면엔 0건("소유자 없는 개체가 없습니다")

> 관련: `20260906_1409`(v5 전환 뒷정리 4건)의 ①(고아 아이템 폐기)이 이 화면을 통해서만
> 가능한데, 그 항목이 이 버그 때문에 계속 미착수 상태로 막혀 있었다.

## 배경 / 문제 정의

사용자가 `/admin/item-badges/orphaned`에 접속했을 때 데이터가 전혀 조회되지 않는다고
보고했다. DB를 직접 조회해 원인을 확인했다(추측 아님).

**이 화면의 조회 로직(`page.tsx`)은 2단계로 되어 있다:**
1. `custody_events`에서 `event_type = 'Orphan'`인 행의 `inventory_item_id`를 후보로 모은다
2. 그 후보들만 대상으로 "지금도 실제로 소유자 없는지" 재확인한다

1단계가 이런 구조인 이유는 코드 주석에 명시돼 있다 — "Orphaned 상태로 들어가는 경로는
계정 탈퇴 하나뿐이고, 그 트리거(`log_orphan_custody_events`, `BEFORE DELETE ON
public.users`)는 항상 `custody_events`에 `Orphan` 이벤트를 남긴다"는 전제다.

**DB로 직접 확인한 결과, 이 전제가 지금 깨져 있다.**

```sql
-- custody_events.event_type 분포 (전체)
Minted: 317, Slot: 44, Pickup: 27, UserDrop: 10, Unslot: 10, Consume: 4, Expire: 4
-- Orphan: 0건 ← 화면의 1단계 후보군이 원천적으로 비어 있다

-- 반면 실제 "지금 소유자 없는" 개체(inventory_id IS NULL, destroyed_at IS NULL,
-- 활성 poi_drops 없음)는:
truly_orphaned_now: 325건
  ├─ with_any_custody_event: 156건 (Minted 등 다른 이벤트는 있음, Orphan만 없음)
  └─ with_no_custody_event: 169건 (custody_events 자체가 전혀 없음)
```

즉 이 화면은 **1단계에서 후보 0건 → "소유자 없는 개체가 없습니다"를 반환**하고 있고,
실제로는 325건이 존재한다.

### 근본 원인 추정 (검증 필요)

`20260906_1409` 배경에 따르면 이 325건(티켓 당시 429건)은 v5 전환 유저 초기화
(`20260905_0039` 결정 ②-A)에서 `inventory`/`inventory_items`를 직접 조작해 발생했다.
계정(`users` 행) 자체를 `DELETE`하는 정상 탈퇴 경로가 아니라 데이터만 초기화하는
방식이었다면, `BEFORE DELETE ON public.users` 트리거가 발동하지 않아 `Orphan` 이벤트가
전혀 남지 않는다 — 위 실측(`Orphan: 0건`, 다수가 `with_no_custody_event`)과 정확히 들어맞는다.

이 화면의 "Orphan 이벤트로 후보를 좁힌다"는 최적화(`DEV_PROCESS_GUARDRAILS.md`가 말하는
"쿼리 방향 역전")는 **"이 경로 하나뿐"이라는 전제가 깨지는 순간 정확성보다 성능을
우선시켜 데이터를 통째로 놓치는 구조**다. 유저 초기화 같은 일회성 대량 작업이 이 트리거를
우회하는 것은 충분히 있을 수 있는 일이므로, 근본적으로는 **후보 좁히기 자체를 신뢰할 수
없는 최적화로 봐야 한다.**

## 상세 요구사항

### 서비스/코드베이스 관점

- **필수 — 화면이 지금 실제 오퍼팬 상태를 놓치지 않도록 조회 방식을 고친다.** 판단이
  필요한 지점: `custody_events` 후보 좁히기를 완전히 버리고 `inventory_items`를
  직접 스캔(`inventory_id IS NULL AND destroyed_at IS NULL`)하는 방식으로 되돌릴지,
  아니면 두 방식을 **OR로 합집합**해서(Orphan 이벤트 후보 ∪ 전체 스캔 후보) 안전망을
  유지하면서 최적화도 살릴지는 구현자가 성능 영향(현재 488건 규모라 전체 스캔도 부담
  없어 보임)을 확인해 판단한다.
- 위 SQL로 이미 확인했듯 이번 325건 자체는 `is_available=true`인 `poi_drops`와 겹치지
  않으므로(합계가 딱 맞아떨어짐), 3단계(활성 드랍 제외) 로직 자체는 정상이다 — 1단계
  후보군만 고친다.
- 근본 원인 확정을 위해, v5 전환 유저 초기화 스크립트/SQL이 실제로 `users` 행을
  `DELETE`했는지 아니면 `inventory`/`inventory_items`만 건드렸는지 확인한다
  (`20260905_0039` 티켓 또는 실행 당시 마이그레이션 참조). 확인되면 향후 유사한 대량
  초기화 작업에서 이 트리거를 의도적으로 우회할지, 아니면 `Orphan` 이벤트를 수동으로
  남기게 할지도 결정한다(이 티켓의 "화면을 고친다" 범위와는 별개 — 후속 판단 사항으로
  기록만 하고 넘어가도 된다).

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

`page.tsx`의 1단계("Orphan 이벤트 후보 좁히기")를 완전히 폐기하고, `inventory_items`를
`inventory_id IS NULL AND destroyed_at IS NULL` 조건으로 직접 스캔하는 방식으로 대체했다.
`custody_events`를 통한 사전 후보 좁히기는 아예 제거했다(OR 합집합이 아니라 완전 대체).

**판단 근거(성능 실측, 2026-09-08 기준 실 DB 값)**:
- `inventory_items` 전체: 515건
- `inventory_id IS NULL AND destroyed_at IS NULL`: 488건
- 활성(`is_available=true`) `poi_drops`: 163건
- 488 - 163 = 325 (티켓의 "325건"과 정확히 일치 — 검증 완료)

488건은 애플리케이션 메모리에 올려도 부담 없는 규모이고, `custody_events` 경유 후보
좁히기가 "Orphan 이벤트를 항상 남긴다"는 전제 자체를 신뢰할 수 없게 된 이상(v5 전환
유저 초기화가 실측으로 증명), 최적화를 유지할 이유가 없다고 판단해 OR 합집합이 아닌
완전 대체를 선택했다. `custody_events`를 경유하지 않으므로 향후 다른 경로로 Orphan
이벤트가 누락되더라도 화면이 다시 이 문제를 겪지 않는다.

**근본 원인 확정** (`20260905_0039` 재확인): 원안은 `public.users` 전원 `DELETE`(CASCADE로
`BEFORE DELETE ON users` 트리거가 정상 발동)였으나, 2026-09-06 사용자 지시로 방향이
바뀌어 users 행은 남기고 서비스 데이터만 초기화하는 방식으로 변경됐다. 이때
`inventory_items.inventory_id`(SET NULL 관계)의 참조원인 `inventory` 테이블만 직접
`DELETE`해 아이템을 Orphaned 상태로 전이시켰다 — `users` 행 자체는 지우지 않았으므로
`BEFORE DELETE ON users` 트리거가 발동하지 않아 `Orphan` custody_events가 전혀 남지
않았다. 티켓의 추정이 정확히 들어맞았다.

이 근본 원인은 "화면을 고친다" 범위와 별개인 후속 판단 사항으로, 이번 티켓에서는 기록만
남기고 별도 조치는 하지 않았다(티켓 지시대로).
