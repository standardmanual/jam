# [BadgeEngine] v5 잔여 5종 조건 필드 평가엔진 구현 + 어드민 「평가 대기」 표시 개선

## 배경 / 문제 정의

어드민 「계열 관리」(`/admin/badge-families`) 화면에서 아래 7개 계열이 "평가 대기 N종"으로
표시되고 있다는 사용자 확인이 있었다. 원인은 조건 필드가 `conditionRegistry.ts`에
`evaluation: 'pending'`으로 선언돼 있어, 조건은 저장되지만 드랍 엔진이 fail-closed로
발급 자체를 막고 있기 때문이다(`CONDITION_JSON_SPEC.md` §4).

`20260906_0110`(v5 카탈로그가 요구하는 엔진 확장 5건)이 7개 잔여 pending 필드 중
2개(`daily_once_count`·`negative_split`)를 다루지 않고 남겨뒀고, 이번 요청 대상 5개
(`distinct_time_bands`·`day_of_month`·`activities_within_hours`·`month_over_month_ratio`·
`vs_personal_average`)는 그 티켓에서도 범위 밖으로 명시적으로 남겨진 항목이다.

### 대상 배지 계열 (7개, 모두 `badges` 테이블 실측 확인 완료 2026-09-08)

| 계열 | family_key | 걸린 pending 필드 | 종수 |
|---|---|---|---|
| 리듬 브레이커 | `walking:A3` | `distinct_time_bands` | 3 (rare/epic/mystic) |
| 스물넷의 산책 | `walking:A4` | `activities_within_hours` | 3 |
| 초하루의 사람 | `walking:A6` | `day_of_month` | 3 |
| 지난달의 나에게 | `walking:B3` | `month_over_month_ratio` (`personal_record_break`는 이미 engine) | 8 (Lv1~8) |
| 지난달의 라이더 | `cycling:R2` | `month_over_month_ratio` | 8 |
| 지난달의 주자 | `running:R3` | `month_over_month_ratio` | 8 |
| 평균의 배신 | `walking:B4` | `vs_personal_average` | 8 |

## 상세 요구사항

### 서비스/코드베이스 관점

**작업 1 — 5개 pending 필드 평가 로직 구현**

`jam-web/src/lib/badge-engine/conditionRegistry.ts`에 필드 정의가 이미 있다
(`distinct_time_bands`: 1194행대, `day_of_month`: 1209행대, `activities_within_hours`:
1230행대, `month_over_month_ratio`: 1315행대, `vs_personal_average`: 1330행대). 스펙은
`Service Plan/Specs/BadgeEngine/CONDITION_JSON_SPEC.md` 181~187행 표 참고.

1. `distinct_time_bands` (integer 2~6, measurable, higher) — "서로 다른 시간대 N개 이상".
   활동 발생 시각을 시간대로 나눠 서로 다른 시간대에서 발생한 활동이 몇 개인지 센다.
   시간대 분류 기준이 기존 코드에 이미 있는지(`activityFilters.ts` 등) 먼저 확인하고,
   없으면 새로 정의해야 한다 — 몇 구간으로 나눌지(새벽/오전/오후/저녁/밤 등)는 애매하면
   진행을 멈추고 사용자에게 확인한다.
2. `day_of_month` (integer 1~31, **filter**, `pairedWith: total_count`) — "매달 N일".
   `total_count`와 짝을 이뤄 "매달 지정일에 활동한 누적 횟수"를 센다. filter 필드이므로
   `personal_record_break_metric`처럼 짝 필드(`total_count`)가 실제 값을 읽어 판정하는
   패턴을 참고한다.
3. `activities_within_hours` ({hours, count}, measurable, higher) — "H시간 안에 N회 이상".
   지정 시간 윈도우 내 활동 횟수 판정.
4. `month_over_month_ratio` (number 1~10 step 0.1, measurable, higher) — "전월 대비 N배
   이상". 이번 달 실적이 전월 대비 지정 배수 이상인지 판정. 전월 실적 0(분모 0) 시 안전
   처리 필요.
5. `vs_personal_average` (number 1~10 step 0.1, measurable, higher) — "평소 평균 대비 N배
   이상". 개인 평균 대비 배수 판정. 평균 계산 기간·활동 이력 부족 시 처리 방침을 명시한다.

각 필드 구현이 끝나면 `evaluation: 'pending'` → `'engine'`으로 뒤집는다. `personal_record_break`
(`20260906_2055`)·`weekly_streak`/스칼라 7종(`20260906_0110` ②) 전환 사례의 구현 패턴·
회귀 검증 방식을 먼저 참고할 것. 전환 전 **해당 필드로 이미 발급된 배지가 0건인지 확인**해
회귀 위험 낮음의 근거로 완료 기록에 남긴다(기존 사례와 동일한 절차).

**작업 2 — 「평가 대기」 메시지에 필드명 노출**

`jam-web/src/app/admin/badge-families/page.tsx` 153~157행의 "평가 대기 {length}종" 배지가
현재 개수만 보여준다. `family.pendingKeys`(`ConditionKey[]`)로 실제 필드 라벨
(`getConditionField(k)?.label`)을 함께 표시한다 — 예: "평가 대기 1종 (서로 다른 시간대)".
계열 상세 화면(`jam-web/src/app/admin/badge-families/[key]/`)에도 같은 표시가 필요한지
확인해 일관되게 반영한다.

### UI/UX 관점

어드민 화면 문구 변경이므로 `Service Plan/Specs/UX_WRITING_GUIDELINE.md` 준수. 어드민은
`/jam-work` 라이트 유형(`admin`)이 아니라 이번 작업은 엔진 구현이 핵심이라 `engine` 유형으로
진행하되, 이 문구 변경 부분만 UX 가이드 대상이다.

## 구현 계획

- `conditionRegistry.ts`: 5개 필드 `evaluation` 전환
- 평가 로직은 기존 pending→engine 전환 사례가 위치한 모듈(`jam-web/src/lib/drop-engine/`,
  `badgeProgress.ts`, `repeatOccurrences.ts`, `activityFilters.ts` 등) 중 해당하는 곳에 추가
- `badge-families/page.tsx`: pendingKeys 라벨 표시
- 이번 작업으로 위 7개 계열의 "평가 대기" 표시가 전부 사라져야 한다 — 회귀 확인 대상
- `Specs/BadgeEngine/CONDITION_JSON_SPEC.md`의 pending 필드 목록·표(181~194행, 356~420행)를
  구현 완료 후 갱신 필요 (문서 갱신은 승인 후 처리 단계에서)

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

5개 필드(`distinct_time_bands`·`day_of_month`·`activities_within_hours`·
`month_over_month_ratio`·`vs_personal_average`)의 평가 로직을 구현하고
`conditionRegistry.ts`의 `evaluation`을 `'pending'` → `'engine'`으로 전환했다.

- **`distinct_time_bands`**: `badgeConditionText.ts`의 `timeSlotLabel`과 동일한 6구간
  (새벽·아침·점심·오후·저녁·심야) 경계로 서로 다른 시간대 수를 센다(`countDistinctTimeBands`,
  activityFilters.ts). min:2~max:6이 이 6구간 수와 정확히 일치해 별도 확인 없이 진행했다.
  `streak_days`와 결합되면(walking:A3) 그 스트릭 창 **안에서만** 시간대 수를 세도록
  `repeatOccurrences.ts`의 `collectStreakDayOccurrences`를 확장했다(단순 이력 전체 독립
  평가로는 "사흘 내리 시간대를 흔들었다"는 의미가 만들어지지 않는다).
- **`day_of_month`**: `day_of_week` 단일값과 같은 자리에서 `filtered`를 좁히는 필터로
  추가했다. `total_count`와 짝을 이루고, 걷기 하루 1회 상한도 `day_of_week`와 동일하게 적용.
- **`activities_within_hours`**: `startDate`(UTC) 기준 슬라이딩 윈도우로 구현
  (`maxActivitiesWithinHours`). 하루 여러 번이 배지의 핵심 의도라 걷기 하루 1회 상한을
  **의도적으로 적용하지 않았다.** `repeat_count`와 결합되면(walking:A4)
  `repeatOccurrences.ts`에 전용 회차 계산(`collectActivitiesWithinHoursOccurrences`, 창을
  채울 때마다 리셋)을 추가했다.
- **`month_over_month_ratio`/`vs_personal_average`**: 지표를 **거리(km)로 고정**했다 —
  `seed_v5_activity_badges.sql`의 배지 설명 주석("지난달 거리의 120%"·"평소 평균 거리의
  2배")이 유일한 콘텐츠 근거이고, 두 필드 모두 `personal_record_break`와 달리 지표를
  고르는 짝 필드가 레지스트리에 없어 다른 지표를 쓸 계획이 없다고 판단했다. 전월 실적
  0(분모 0)·비교할 이전 활동 없음(최초 활동)은 판정에서 제외한다(자동 통과시키지 않음).

**작업 중 발견해 함께 처리한 것**:
1. `badgeProgress.ts`의 진행률 분류(`classifyConditionKind`)가 `month_over_month_ratio`·
   `vs_personal_average`를 `conditionAxes.ts`의 어떤 축 목록에도 인식하지 못해, 이 필드가
   `personal_record_break` 등 다른 축과 함께 오면 그 축만으로 100% 진행률을 그리고
   이 필드는 화면에서 통째로 사라지는 「숨은 축」 버그가 있었다(회귀 테스트로 확인,
   `unabsorbedAxisKeys`가 원래 막던 것과 같은 실패 모드). 진행 축 지원 자체는 이번 티켓
   범위 밖이라 안전하게 `unsupported`로 떨어뜨리는 가드만 추가했다.
2. `personal_record_break_metric`이 `walking:B3`·`walking:B4`·`running:R3`·`cycling:R2`
   (32종)에 채워져 있지 않아, `month_over_month_ratio`/`vs_personal_average`를 engine으로
   바꿔도 `personal_record_break`의 짝 필드 강제(`PAIR_ENFORCED_CONDITION_KEYS`)에 계속
   막힌다는 것을 발견했다. `seed_personal_record_break_metric.sql`(티켓 20260906_2055)이
   7계열만 채우고 이 4계열을 범위 밖으로 남긴 결과다. 콘텐츠 주석이 전부 "거리" 기준이라
   `single_distance_km`으로 채우는 마이그레이션을 작성했다(직접 실행하지 않음 — 아래 참조).

전환 전 5개 필드 모두 `evaluation: 'pending'`으로 fail-closed에 막혀 있어(대상 7계열의
발급 이력 0건은 CONDITION_JSON_SPEC.md §4·§6에 이미 실측 기록됨), 회귀 위험은 낮다.

### 주요 의사결정 / 핵심 메모

- **시간대 6구간 경계**: `badgeConditionText.ts`의 `timeSlotLabel`과 동일하게 새벽(4-8)·
  아침(8-11)·점심(11-14)·오후(14-18)·저녁(18-22)·심야(22-4)로 고정했다.
  `distinct_time_bands`의 min:2~max:6이 이 6구간 수와 정확히 일치하는 것을 근거로
  삼아 HALT 없이 진행했다.
- **`month_over_month_ratio`/`vs_personal_average`의 지표를 거리(km)로 고정**한 근거는
  seed SQL 주석뿐이다 — 향후 다른 지표가 필요해지면 `personal_record_break_metric`처럼
  짝 필드를 추가해야 한다(현재 레지스트리엔 없음).
- **badgeProgress.ts 진행 축 미지원은 의도적으로 범위 밖에 뒀다** — 축 종류 설계(어떤
  kind로 그릴지, 표시 포맷)가 필요한 별도 작업이라 이번 티켓(엔진 평가)과 섞지 않았다.
  대신 「숨은 축」 회귀를 막는 안전 가드만 추가했다.
