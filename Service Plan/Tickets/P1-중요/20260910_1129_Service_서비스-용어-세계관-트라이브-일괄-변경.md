# [Service] 서비스 용어 일괄 변경 — 세계관 → 트라이브, faction → tribe

## 배경 / 문제 정의

티켓 `20260909_2119`(온보딩 재설계)에서 유저 대면 명칭을 **"트라이브"**로 확정하고
온보딩 화면에만 먼저 적용했다. 그 결과 지금은 **온보딩만 새 용어이고 나머지 전부가
옛 용어인 불일치 상태**다:

- 어드민 화면은 "세계관 관리", "소속 세계관", "최소 세계관 다양성"으로 노출된다
- 서비스 화면·주석·타입·변수는 전부 `faction` 계열 식별자를 쓴다
- `Specs/`·`Business/`의 현재 상태 문서도 "세계관"으로 서술되어 있다

운영자와 개발자가 같은 개념을 두 이름으로 부르게 되어, 문서를 검색할 때도 두 용어를
모두 시도해야 하는 상태다. 용어를 하나로 수렴시킨다.

## 상세 요구사항

### 핵심 제약 — DB는 건드리지 않는다

Supabase는 staging·프로덕션 **공용 단일 DB**다. 컬럼·테이블을 리네임하면 아직 배포되지
않은 프로덕션 코드가 즉시 깨지므로, 이번 티켓에서 **DB 스키마는 전혀 바꾸지 않는다.**

따라서 코드에는 두 이름이 의도적으로 공존한다:

```ts
const [tribeId, setTribeId] = useState(book?.faction_id ?? '')  // 우변은 DB 컬럼
...
faction_id: tribeId || null,                                     // 키는 DB 컬럼, 값은 코드 변수
```

**절대 바꾸면 안 되는 것** (바꾸면 런타임에 DB와 어긋나 즉시 장애):

| 대상 | 건수 | 비고 |
|---|---|---|
| `faction_id` 컬럼명 | 125건 | 쿼리 문자열·객체 키·Row 타입 필드 전부 |
| `'factions'` 테이블명 문자열 | 62건 | `.from('factions')` 등 |
| `tier{1,2,3}_min_factions` 컬럼 | 24건 | 조합 정책 싱글톤 |
| `faction_adjacency` 테이블 | — | 인접 관계 |
| `faction_background_cascade` RPC | — | 배경 일괄 적용 함수 |
| `src/types/database.generated.ts` | 전체 | Supabase 자동 생성 파일, 손대지 않음 |
| `supabase/migrations/*.sql` | 220건 | 실행 완료된 기록, 소급 수정 금지 |
| `supabase/seed_*.sql` | — | 실행 완료된 1회성 데이터, 파일명 포함 유지 |

### 변경 대상

**1. 소스코드 식별자 (`jam-web/src/`)** — DB에 묶이지 않은 것만

- 변수·함수: `factionId` → `tribeId`, `factionMap` → `tribeMap`, `pickFaction` → `pickTribe`,
  `loadFactions` → `loadTribes` 등
- 타입: `FactionRow` → `TribeRow`, `FactionAdjacencyRow` → `TribeAdjacencyRow`,
  `ItemBookWithFaction` → `ItemBookWithTribe`
- 컴포넌트: `FactionForm` → `TribeForm`, `FactionsTable` → `TribesTable`
- **주의**: `FactionRow`의 **필드명**(`faction_id` 등)은 DB 컬럼이므로 유지한다.
  바뀌는 건 타입의 **이름**뿐이다.

**2. 라우트·디렉터리**

- `src/app/admin/factions/` → `src/app/admin/tribes/`
- `src/app/api/admin/factions/` → `src/app/api/admin/tribes/`
- `components/admin/adminNavItems.ts`의 경로·라벨 동시 수정

**3. 한글 UI 문구·주석 (138건)**

"세계관" → "트라이브". 어드민 화면 라벨·placeholder·다이얼로그 문구·에러 메시지 포함.
서비스 화면은 이미 트라이브로 노출되므로 잔여 지점만 정리한다.

**4. MODULAR 디자인 시스템**

`design-system/components/cards/ShapeTag.{jsx,d.ts,stories.tsx}`의 `faction` prop →
`tribe`, `FACTION_COLORS` → `TRIBE_COLORS`. `design-system/readme.md`의 "세계관" 표기.

**모듈러-서비스 연결 범위 판정** (`ds-connection-scope.md` 기준): `ShapeTag`는 **미도입 8종**에
해당한다. `grep -rn "ShapeTag" jam-web/src` 결과가 0건으로, 서비스에 대응 개념이 없는
스토리북 전용 컴포넌트다. 따라서 prop 이름을 바꿔도 **서비스 호출부 영향이 없고**,
`src/components/ui/`에 함께 고쳐야 할 병존 구현도 없다.

**UI 재사용 판정** (1.5단계): 이번 티켓은 순수 리네이밍으로 **신규 컴포넌트를 만들지
않는다.** 기존 컴포넌트의 이름과 prop만 바뀌므로 MODULAR 탐색·재사용 판정은 해당 없음.

**5. 문서 — 현재 상태 문서만**

- `Service Plan/Specs/` 45건 (11개 파일). `Specs/Content/FACTIONS.md` → `TRIBES.md`로 파일명 변경
- `Service Plan/Business/` 9건. `Business/04 JAM! 세계관.md` → `04 JAM! 트라이브.md`
- `jam-web/PRODUCT.md`, `jam-web/docs/storybook/*.md`
- `jam-web/scripts/recraft/*.js` 주석·변수

문서에서도 DB 식별자(`factions` 테이블, `faction_id` 컬럼)를 **지칭하는 문장은 사실이므로
그대로 둔다.** 예: `02_DATA_MODEL.md`의 컬럼 정의표.

### 변경 제외

- **완료된 과거 티켓 315건 (파일명 12개 포함)** — 티켓은 작업 이력이다. 당시 용어와 당시
  DB 상태를 기록한 문서이므로 소급 수정하지 않는다. 특히 `20260716_001_Infra_factions-
  item_books-배지-마이그레이션.md`처럼 실제 테이블명을 서술한 기록은 지금도 사실이다.
- `Service Plan/Archive/` — 읽기 전용 폐기 기록
- `Service Plan/Assets/` — 파이프라인 산출물, 문서 아님
- `jam-web/public/storybook/` — 빌드 산출물, 소스 변경 후 재빌드로 갱신

## 구현 계획

1. **DB 경계 먼저 고정** — 위 "절대 바꾸면 안 되는 것" 목록을 정규식으로 보호 대상으로
   삼고, 나머지만 치환한다. 단순 `sed 's/faction/tribe/g'`는 절대 쓰지 않는다.
2. 디렉터리 이동(`git mv`) → import 경로 수정 → 식별자 치환 → 한글 문구 치환 순으로 진행
3. `npx tsc --noEmit`으로 타입 검증, `npm run build`로 빌드 검증
4. 드랍엔진·조합 테스트(`src/lib/drop-engine/__tests__/`, `src/lib/combine/__tests__/`) 통과 확인
5. 문서는 코드 변경이 끝난 뒤 일괄 반영
