# [Infra] DB 스키마 트라이브 완전 통일 — factions → tribes 리네임

## 배경 / 문제 정의

티켓 `20260910_1129`에서 코드·UI 명칭을 "세계관"에서 "트라이브"로 통일하면서, DB 스키마는
의도적으로 `factions`/`faction_id`를 유지했다 — 당시는 staging·프로덕션 공용 단일 DB에
아직 배포되지 않은 코드가 있어 스키마를 바꾸면 즉시 장애가 나는 상황을 우려했기 때문이다.

**아직 서비스 런칭 전이라 이 제약의 성격이 달라졌다.** 실사용자 데이터는 없다. 다만
staging과 main은 여전히 별도 배포이고 여전히 같은 DB를 공유하므로, "실사용자 피해"는
없어도 "마이그레이션 실행 시점과 코드 배포 시점 사이의 불일치로 일시적 500/502가 난다"는
위험 자체는 남아있다. 이번 티켓은 그 위험을 짧은 창으로 좁히는 방식으로 완전히 정리한다.

### 변경 대상 — 전부 tribe로 통일한다 (이번 티켓의 결정)

이전 티켓과 달리 `faction_name`(피드 메타 키)·Storage 경로도 포함해 전부 통일한다.
남겨두면 "DB 완전 통일"이라는 이번 목적에 예외가 남기 때문이다.

1. **테이블 리네임**: `factions` → `tribes`, `faction_adjacency` → `tribe_adjacency`
   (`ALTER TABLE ... RENAME TO` — 메타데이터 변경만이라 데이터 이동 없음, 즉시 완료)
2. **컬럼 리네임**: `badges.faction_id`→`tribe_id`, `item_books.faction_id`→`tribe_id`,
   `users.faction_id`→`tribe_id`, `faction_adjacency.faction_id`→`tribe_id`,
   `.adjacent_faction_id`→`adjacent_tribe_id`, `user_drop_state.last_drop_faction_id`→
   `last_drop_tribe_id`, `combine_policy.tier{1,2,3}_min_factions`→`tier{1,2,3}_min_tribes`
3. **RPC 리네임**: `count_faction_background_cascade`→`count_tribe_background_cascade`,
   `apply_faction_background_cascade`→`apply_tribe_background_cascade`
   (`ALTER FUNCTION ... RENAME TO` — 함수 본문 내부에서 테이블·컬럼을 구식별자로 참조하는
   부분도 새 이름으로 함께 고쳐야 한다. `CREATE OR REPLACE` 필요 여부를 마이그레이션 작성 시
   함수 본문을 직접 열어 확인한다)
4. **jsonb 키 리네임**: `user_activity_feed.metadata`의 `faction_name` → `tribe_name`
   (11행만 UPDATE), `engine_decision_log.payload`의 faction 관련 키 → tribe (11행)
5. **Storage 파일 이동**: `images` 버킷의 `badges/factions/{collectionId}/*` 175개 파일을
   `badges/tribes/{collectionId}/*`로 이동 (Storage API의 move, service_role 키 사용)
6. **DB 값 갱신**: 위 이동에 맞춰 `badges.image_url`(90행)·`item_books.image_url`(10행)의
   URL 문자열을 `factions/`→`tribes/`로 교체
7. **코드 최종 정리**: 위 스키마 변경에 맞춰 `jam-web/src`의 잔여 46개 파일을 갱신
   (`faction_id`→`tribe_id`, 쿼리 문자열 `'factions'`→`'tribes'` 등)
8. **타입 재생성**: `src/types/database.generated.ts`를 Supabase에서 재생성

### 무중단이 아니라 "짧은 창"이 목표다

실사용자가 없으므로 완전 무중단(뷰·이중쓰기 호환 레이어)을 만드는 비용을 들이지 않는다.
대신 **DB 마이그레이션 실행과 코드 배포를 최대한 붙여서** 창을 좁힌다:

1. 코드 변경을 먼저 전부 끝내고 리뷰까지 통과시켜 배포 직전 상태로 둔다
2. DB 마이그레이션을 실행한다 (`ALTER TABLE/COLUMN/FUNCTION RENAME` — 각각 수 ms, 락 시간
   매우 짧음. jsonb UPDATE와 Storage 이동은 별도 처리로 스키마 리네임과 순서 무관)
3. 마이그레이션 실행 직후 코드를 staging→main 순서로 신속히 배포한다
4. 이 창 안에 배포된 코드가 옛 스키마를 참조해 에러가 나더라도, 실사용자가 없으므로
   그 자체는 허용하되 **창을 최소화**하는 것이 목표임을 인지한다

### 순서 (의존성 고려)

1. Storage 파일 이동 + `image_url` 갱신 — 스키마 변경과 독립적이라 먼저 해도 무방
2. jsonb 키 UPDATE (`faction_name`→`tribe_name` 등) — 역시 독립적
3. 코드 변경 (46개 파일) — 아직 옛 컬럼명 기준으로 작성, 개발 완료까지는 배포하지 않는다
4. 게이트 리뷰·개선 리뷰 통과
5. **여기서 오케스트레이터가 직접**: DB 마이그레이션 실행 (`ALTER TABLE/COLUMN/FUNCTION`)
   → 타입 재생성 → 곧바로 staging push → main 승격까지 이어서 진행

   `ALTER FUNCTION ... RENAME TO` 후 `CREATE OR REPLACE`가 `42P13: cannot change
   name of input parameter`로 거부됐다 — 파라미터가 `p_faction_id`→`p_tribe_id`로
   바뀌었기 때문. 단일 트랜잭션이라 전체 롤백됨을 실측 확인 후, `DROP FUNCTION` +
   `CREATE FUNCTION` + 명시적 `REVOKE/GRANT`(마이그레이션 109가 잠가둔 PUBLIC 차단·
   service_role 전용 권한 재설정)로 재작성해 재실행, 성공.
2. 테이블 2개(`factions`→`tribes`, `faction_adjacency`→`tribe_adjacency`), 컬럼 7개,
   PK/FK 제약, RLS 정책 2개, RPC 함수 2개가 전부 리네임됐다.
3. 이미 쌓인 jsonb 데이터: `user_activity_feed.metadata`의 `faction_name`→`tribe_name`

### 주요 의사결정 / 핵심 메모

- **`apply-background` 라우트에는 dryRun이 없다.** 실렌더 검증 중 `dryRun: true`를 보내며
  POST를 호출했는데, 라우트가 이 파라미터를 무시하고 `apply_tribe_background_cascade`를
  즉시 실행해 미스터리 헌터 트라이브 소속 컬렉션 10건의 `background_color`/
  `background_animation`을 실제로 덮어썼다. 확인 결과 전체 서비스에 배경 테마가 설정된
  트라이브·컬렉션이 **하나도 없어서**(0/10, 0/100) null→null이라 실질 피해는 없었지만,
  다음에 이 라우트를 검증할 때는 GET(count, 실제 변경 없음)만 호출해야 한다.
- **완전 통일 범위 확장**: 티켓 20260910_1129 때는 DB를 남겨뒀지만, 이번엔 PK/FK 제약명·
  RLS 정책명까지 리네임 대상에 포함했다(동작 영향 없는 메타데이터지만 "완전 통일"이라는
  목적에 맞춤).
- **Storage 자동화 스크립트가 한 번 원인 불명으로 죽었다.** 최초 실행에서 171개 중 0개만
  처리된 채 프로세스도 로그도 남기지 않고 조용히 멈췄다. `nohup`+`disown`으로 완전히
  분리해 재실행하니 정상 동작했다 — 원래 백그라운드 전환 방식(foreground 타임아웃 후
  detach)이 원인일 가능성이 있으나 재현하지 못해 근본 원인은 특정하지 못했다.
