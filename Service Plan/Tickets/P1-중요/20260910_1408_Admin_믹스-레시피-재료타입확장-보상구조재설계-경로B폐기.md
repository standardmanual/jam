# [Admin] 믹스 레시피 재료 타입 확장 · 보상 구조 재설계 · 경로 B 폐기

## 배경 / 문제 정의

믹스 레시피 어드민은 재료를 아이템 배지로만 지정할 수 있고, 보상은 결과 배지 1종에 성공률
슬라이더가 붙은 형태다. 이 구조에서는 액티비티 배지를 1개까지만 보유 조건으로 걸 수 있고,
체크인 배지는 조건으로 쓸 수 없으며, 포인트를 보상으로 줄 수 없다. 카탈로그 규모(액티비티
633종, 체크인 1,790종)에 비해 레시피 설계의 폭이 지나치게 좁다.

동시에 조합 엔진의 확률 경로(경로 B)가 카탈로그 현실과 어긋난 채 방치되어 있다. 아래
「현재 상태 검증」의 실측이 근거다.

프로덕션 `combination_recipes`가 0건인 지금이 하위 호환 없이 스키마를 다시 잡을 수 있는
시점이다.

## 현재 상태 검증 (2026-09-10, 프로덕션 실측)

| 항목 | 현재 | 근거 |
|---|---|---|

### 경로 B가 망가져 있는 근거

`COMBINE_RECIPES.md`와 최초 티켓 `20260727_007`이 정의한 설계는 **트라이브 10종 각각에
고유한 소재 아이템 배지가 존재하는 세계관**을 전제로 한다. "소재 트라이브를 제외한 다른
트라이브의 common 배지를 준다"는 규칙도, 다양성 3종·5종이라는 티어 임계값도 그 전제 위에서만
의미를 갖는다.

실제 카탈로그는 다르다.

| 항목 | 설계 전제 | 프로덕션 실측 |
|---|---|---|
| 아이템 배지 보유 트라이브 | 10종 | **2종** (낭만 미식가 90개, 아스팔트 레인저 18개) |
| 아이템 배지 등급 분포 | Epic·Mystic 결과 배지 존재 | **전부 common** |
| 정석 레시피 | 33선 | **0건** |

그 결과 세 가지 문제가 프로덕션에서 실제로 발생한다.

1. **인센티브 역전**: 유저가 두 트라이브의 재료를 섞으면 "소재 트라이브를 제외한" 후보가
   0종이 되어, 확률 판정을 통과해도 지급할 배지가 없어 실패로 떨어진다
   (`combine/index.ts:213-220`). 다양성을 높일수록 보상이 좋아져야 하는데, 현 카탈로그에서
   달성 가능한 최대 다양성(2종)을 채우면 무조건 빈손이 된다.
2. **죽은 설정**: `tier2_min_tribes=3` / `tier3_min_tribes=5`는 도달 불가능하다. 어드민
   화면에는 조정 가능한 것처럼 입력란 8개가 떠 있다.
3. **강등 구간**: 재료 7개에 트라이브 3종이면 티어3 요건(5종)에 미달하고 티어2 요건(재료
   6개 이하)에도 걸려 티어1로 강등된다(`policy.ts:78-88`). 재료 6개일 때보다 확률과 지급
   개수가 모두 낮아진다.

**결정(2026-09-10)**: 경로 B와 피티 시스템을 전면 폐기하고, 믹스를 「레시피 정확 매칭 →
지정 보상」과 「미매칭 → 고정 포인트」 두 갈래로 단순화한다. 배지 지급은 어드민이 등록한
레시피를 통해서만 일어난다.

## 상세 요구사항

### 서비스/코드베이스 관점

**1. 재료 선택을 배지 타입 무관으로 확장**

재료 슬롯에서 `typeFilter`를 제거해 아이템·액티비티·체크인 배지를 모두 검색할 수 있게 한다.
저장 시점에 시스템이 배지 타입으로 자동 분류한다.

- 아이템 배지 → `ingredient_badge_ids`. 믹스 시 소각된다.
- 액티비티·체크인 배지 → `required_badge_ids`. 보유 여부만 검증하고 소각하지 않는다.

기존 `required_activity_badge_id` 단일 컬럼은 `required_badge_ids` 배열로 대체하고, 폼에
따로 있던 "필수 액티비티 배지" 입력란은 없앤다. 재료 슬롯 하나에서 전부 고르되, 각 슬롯
옆에 **소모 / 보유 조건** 표시를 띄워 어느 쪽으로 처리되는지 어드민이 즉시 알 수 있게 한다.

매칭 규칙:

```
매칭 성립 = (유저가 투입한 아이템 배지 집합 == ingredient_badge_ids, 순서 무관 완전 일치)
          AND (required_badge_ids의 모든 배지를 유저가 보유)
```

보유 검증은 액티비티 배지가 `user_activity_badges`, 체크인 배지가
`user_checkin_badge_earns`를 조회한다.

**2. 보상 구조 재설계**

`success_rate`를 제거한다. 재료가 정확히 일치하면 지정한 보상이 확정 지급된다.

`result_badge_id` 단일 컬럼을 다음으로 대체한다.

- `reward_points integer NOT NULL DEFAULT 0` — 고정 금액. 0이면 미지급.
- `reward_badge_ids uuid[] NOT NULL DEFAULT '{}'` — 다중 선택. 추가한 배지를 전부 지급.
- 둘 다 값이 있으면 포인트와 배지를 함께 지급한다.

배지 선택 UI는 트라이브 · 컬렉션 · 등급으로 후보를 좁혀 검색하는 다중 선택 컴포넌트를
새로 만든다. **이 세 필터는 어드민이 원하는 배지를 찾기 위한 검색 도구이며, 무작위 추첨
풀이 아니다.** 추가한 배지는 무작위 없이 전부 지급된다.

**3. 믹스 정책 정리 — 경로 B·피티 전면 폐기**

| 컬럼 | 조치 |
|---|---|
| `fail_reward_points` | 신설. 레시피 미매칭 시 지급할 고정 포인트 |
| `tier1~3_max_items` · `_min_tribes` · `_b_rate` · `_b_count` | 제거 (12개) |
| `pity_points_start_streak` · `_base` · `_step` · `_increment` · `_cap` | 제거 (5개) |
| `pity_prob_increment` · `pity_prob_cap` | 제거 (2개) |

`combine_policy`는 싱글톤(id=1) 구조를 유지하되 `fail_reward_points` 하나만 남는다.
정책 로딩 패턴(기본값 폴백, 저장 실패 시 예외)은 그대로 지킨다.

피티가 사라지므로 `user_combine_state`(1행)는 쓰이지 않는다. 실패 이력 테이블이 그 역할을
대신하므로 테이블째 제거한다.

포인트 사유 코드 `combine_pity_reward`는 지급 이력이 0건이지만 타입 유니온·요약 라벨 등
6개 파일에 퍼져 있으므로 코드값은 유지하고 표시 라벨만 "믹스 실패 보상"으로 바꾼다.

**4. 실패 이력 기록**

```sql
create table user_combine_fail_logs (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references users(id) on delete cascade,
  attempted_at timestamptz not null default now(),
  ingredient_badge_ids uuid[] not null default '{}',
  fail_reason text not null,   -- 'no_recipe_match' | 'items_not_found' | 'invalid_count'
  points_awarded integer not null default 0
);
create index on user_combine_fail_logs (user_id, attempted_at desc);
```

RLS는 어드민(service_role) 조회 전용으로 건다. 유저 화면에는 노출하지 않는다.

### 컨텐츠 관점

`COMBINE_RECIPES.md`의 정석 레시피 33선은 **2026-09-10 폐기했다**(커밋 `926b8206`). 폐기
사유는 `057_seed_combine_recipes.sql`의 자동 시딩이 전량 조용히 스킵되어 프로덕션 레시피가
0건이었고, 33선이 전제한 트라이브 10종 소재 배지 카탈로그가 구축되지 않았기 때문이다.

따라서 이번 재설계는 **마이그레이션할 레시피 데이터가 전혀 없는 상태에서 진행한다.** 레시피는
향후 `/admin/recipes`에서 새 스키마로 개별 등록한다. 8개 트라이브의 소재 아이템 배지와
epic·mystic 등급 배지 확보는 별도 컨텐츠 작업으로 남는다.

### 수용 기준

1. 레시피 재료 슬롯에서 아이템·액티비티·체크인 배지가 모두 검색되고, 선택하면 슬롯 옆에
   "소모" 또는 "보유 조건" 표시가 나타난다.
2. 아이템 배지 2개 + 액티비티 배지 1개 + 체크인 배지 1개로 레시피를 저장하면
   `ingredient_badge_ids` 2건, `required_badge_ids` 2건으로 분리 저장된다.
3. 아이템 배지 재료가 2개 미만인 레시피는 저장이 거부되고 사유가 화면에 표시된다.
4. 필수 보유 배지를 갖지 않은 유저가 재료를 정확히 투입하면 매칭되지 않고 실패로 처리되며,
   아이템 배지는 소각되고 필수 보유 배지는 소각되지 않는다.
5. 재료가 정확히 일치하고 필수 보유 배지를 모두 가진 유저는 `reward_points`와
   `reward_badge_ids`의 모든 배지를 100% 확률로 지급받는다.
6. 레시피 폼에 성공률 슬라이더가 없고, `combination_recipes.success_rate` 컬럼이 제거되어
   있다.
7. 보상 배지 선택 컴포넌트에서 트라이브·컬렉션·등급 필터를 조합해 후보를 좁힐 수 있고,
   고른 배지가 다중으로 누적되며, 지급 시 무작위 없이 전부 지급된다.
8. 믹스 정책 화면에 "실패 시 지급 포인트" 입력란만 있고, 티어·피티 입력란 19개가 모두
   사라져 있다.
9. 레시피에 매칭되지 않는 조합은 배지를 전혀 지급하지 않고, 정책에 설정한 고정 포인트만
   지급한다.
10. 믹스 실패 시 `user_combine_fail_logs`에 행이 1건 쌓이고, 어드민 유저 상세 화면에
    최신순으로 표시된다.
11. `user_combine_state` 테이블과 이를 참조하는 코드가 남아 있지 않다.
12. 기존 테스트가 모두 통과하고, 아래 신규 테스트가 추가되어 통과한다.

### 롤백 계획

DB는 staging과 프로덕션이 공용 단일 인스턴스라 마이그레이션 실행 즉시 프로덕션에 반영된다.
되돌릴 때는 역방향 마이그레이션으로 컬럼을 복원한 뒤 코드를 revert한다. 레시피 0건 · 피티
지급 이력 0건 · `user_combine_state` 1행이므로 복원 시 손실되는 운영 데이터는 없다. 다만
`user_combine_fail_logs`에 쌓인 이력은 롤백 시 사라진다.
