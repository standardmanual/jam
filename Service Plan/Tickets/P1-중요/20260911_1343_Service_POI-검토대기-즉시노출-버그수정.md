# [Service] POI 검토대기 상태가 지도에 즉시 노출되는 버그 수정

## 배경 / 문제 정의
티켓 `20260911_1310`으로 POI 자동수집을 재개하면서 `poi_categories.requires_review`도
10개 카테고리에 함께 켰다. 그런데 실제 자동수집 저장 로직(`jam-web/src/app/api/drops/route.ts`
`searchAndPersistCategories`, 123~140행)을 확인한 결과, `pending_review`와 `is_active`가
서로 **완전히 독립적으로** 결정되고 있었다.

```ts
is_active: displayOnMapByCategory.get(p.category) ?? true
```

`is_active`는 오직 카테고리의 `display_on_map` 값만 따르며, 검증 게이트 통과 여부
(`pending_review`)와 무관하다. 이번에 켠 10개 카테고리 중 `display_on_map=true`인 6개
(government/convenience/nature/school/stadium/tourist_attraction)는:

- 검증 게이트를 통과하지 못해 `pending_review=true`(검토대기)가 되더라도
- **`is_active`는 곧바로 `true`로 저장되어 지도에 즉시 노출된다**

`jam-web/src/lib/admin/poi-review.ts`의 `approvePendingPois` 함수 주석("노출(is_active)은
건드리지 않는다 — 검토 대기 중에도 이미 노출되고 있었으므로 승인은 그 상태를 그대로
확정할 뿐이다")도 이 사실을 뒷받침한다. 즉 "승인"은 `pending_review`만 `false`로 내리는
것이고, `is_active`를 바꾸는 액션이 아니다.

이는 09-07 오전 티켓(`20260907_1242`)이 의도한 "검증 게이트를 통과하지 못한 POI는 검토
전까지 노출하지 않는다"는 원칙과 어긋난다. `display_on_map=false`인 4개 카테고리
(food/hospital/park/pharmacy)만 등록 시점부터 비활성 상태를 유지하고, 나머지 6개는
검증 게이트가 사실상 무의미해진다.

사용자가 20260911_1310 작업 중 이를 지적해 발견됐다. 사용자는 "코드 수정 — `pending_review=true`면
`is_active`도 `false`로 강제"하는 방향을 선택했다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `jam-web/src/app/api/drops/route.ts`의 `searchAndPersistCategories`(139행 부근)에서
  `is_active` 계산식을 `pendingReview`를 우선 고려하도록 수정한다:
  `pendingReview`가 `true`이면 `display_on_map` 값과 무관하게 `is_active=false`로 저장하고,
  `pendingReview`가 `false`(자동승인 또는 게이트 자체가 꺼진 카테고리)일 때만 기존처럼
  `display_on_map` 값을 따른다.
- `jam-web/src/lib/admin/poi-review.ts`의 `approvePendingPois` 주석("검토 대기 중에도 이미
  노출되고 있었으므로 승인은 그 상태를 그대로 확정할 뿐이다")이 이번 수정으로 더 이상 사실이
  아니게 된다. 승인 시 `is_active`를 명시적으로 활성화(카테고리의 `display_on_map` 값에 따라)
  하도록 로직을 함께 보완할지, 아니면 승인 후에도 `/admin/poi/[id]`에서 별도 활성화를 거치게
  둘지 판단이 필요하다 — **권장: 승인 시점에 `display_on_map=true`인 카테고리는 `is_active=true`로
  같이 올려준다.** 그렇지 않으면 승인해도 여전히 지도에 안 보이는 역방향 문제가 생긴다.
- 거부(`rejectPendingPois`)는 기존처럼 `is_active=false` 유지로 변경 없음.
- 이미 이번 정책 재개(SQL 실행) 이후 `pending_review=true`이면서 `is_active=true`로 잘못
  저장된 기존 행이 있는지 확인하고, 있다면 별도 데이터 보정(UPDATE)이 필요한지 판단한다.

## 구현 계획
1. `gatePois`/`searchAndPersistCategories`의 `is_active` 계산 로직 수정.
2. `approvePendingPois`에 승인 시 `is_active` 활성화 로직 추가 여부 결정 및 반영.
3. 수정 후 재현 테스트: `requires_review=true`이고 게이트 판정이 `pending`인 카테고리로
   신규 POI가 수집될 때 `is_active=false`로 저장되는지 확인.
4. 정책 재개(20260911_1310) 이후 실제로 잘못 노출된 행이 있는지 Supabase에서 조회하고,
   있으면 보정 SQL을 작성한다(실행은 5단계, 사용자 승인 후).
5. `Service Plan/Specs/Content/POI.md`의 관련 서술도 실제 동작과 일치하도록 재검토.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
1. `searchAndPersistCategories`의 `is_active` 계산식을 `pendingReview ? false :
   (displayOnMapByCategory.get(...) ?? true)`로 수정 — 검토대기 판정이면 `display_on_map`
   값과 무관하게 무조건 `is_active=false`로 저장한다.
2. `approvePendingPois`를 보완해 승인 시 배정 카테고리(`targetCategory` 우선, 없으면 기존
   `category`)의 `display_on_map`을 조회해 `true`면 `is_active=true`도 함께 세팅하도록
   변경(권장안 채택 — 그렇지 않으면 승인해도 계속 비노출로 남는 역방향 문제가 생김).
   `targetCategory` 없이 다건 승인 시 행마다 기존 카테고리가 다를 수 있어 `display_on_map`
   값별로 id를 묶어 그룹 UPDATE한다. `rejectPendingPois`는 변경 없음.
3. Supabase에 직접 접근할 수 있는 도구(MCP·`.env.local`)가 이 서브에이전트에는 없어
   기존 잘못 저장된 행의 실존 여부를 직접 조회하지 못했다 — 대신 버그 조건 자체
   (`pending_review=true AND is_active=true`)를 WHERE절로 삼는 확인용 SELECT + 보정 UPDATE를
   `seed_20260911_1343_poi_pending_review_is_active_fix.sql`에 작성했다. 어드민 수동등록
   경로(`api/admin/poi/route.ts`)는 이미 이 불변식(`pending_review=true`⇒`is_active=false`)을
   지키고 있어, 이 조건으로 걸러도 자동수집 버그로 잘못 저장된 행만 잡힌다.
4. `Service Plan/Specs/Content/POI.md`의 "검증 게이트·검토 큐 동작" 절을 수정 후 동작(승인
   시 노출 함께 활성화, pending_review 우선순위)에 맞게 갱신.
