# [Admin] 배지 계열 관리 — meta 지표 편집 불가 버그 + 용어 쉬운말 개선

## 배경 / 문제 정의
사용자가 어드민 `/admin/badge-families/[familyKey]`에서 'JAM! 출석!' 계열을 관리하려는데,
이미 만들어진 LV1~LV3의 조건값이 "계열 구성" 인라인 편집 표에 아예 표시되지 않아 수정할 수
없다고 보고했다.

원인 조사 결과(오케스트레이터 직접 확인, DB 조회 포함):
- 'JAM! 출석!' 계열의 LV1~LV3 `condition_json`은 전부 `{"daily_sync_count": 1}`이다.
- `daily_sync_count`는 `conditionRegistry.ts`에서 `role: 'meta'`로 정의되어 있다.
- `FamilyDetailManager.tsx`의 인라인 편집 표는 `numericAxisKeysOf()`(`badge-families.ts`)로
  열을 만드는데, 이 함수는 `MEASURABLE_CONDITION_KEYS`(`role: 'measurable'`만)로 필터링한다.
  → `role: 'meta'`인 수치 지표는 열 후보에 아예 안 들어가서 표에 조건값 칸 자체가 없다.
- 목록 화면(`page.tsx`)은 이미 `usageMetricKeys`(meta 지표 포함)를 따로 참조해 "조건지표"
  칸에 표시하고 있어(티켓 20260910_2055), 상세 화면 인라인 표에만 이 처리가 빠져 있다.
- "자리 추가"(다음 레벨 만들기) 폼의 `draft.axes`도 같은 이유로 measurable 지표만 다뤄서,
  meta 지표만 쓰는 계열은 증가량을 입력해도 실제로는 반영되지 않고 상위 자리 조건을
  그대로 복사만 한다.

추가로 사용자가 이 화면 전반의 UI와 용어가 어렵다고 지적했다 — "계열", "자리", "인라인 편집",
"증가 규칙(등차/등비/수동)", "조건 축", "일괄 재계산", "임계값 공식", "2단 교차 게이트" 등
도메인 전문 용어가 화면에 그대로 노출되어 있다. 중학생도 이해할 수 있는 쉬운 말로 순화해달라는
요청이다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `FamilyDetailManager.tsx`의 인라인 편집 표(`axisKeys`)가 `role: 'meta'`인 수치 지표도
  포함하도록 열 구성 로직을 고친다. `numericAxisKeysOf()` 자체를 바꿀지, 별도 함수로
  measurable + meta 수치 지표를 합칠지는 구현 단계에서 판단한다. 단, `numericAxisKeysOf()`는
  다른 곳(다음 레벨 상속·일괄 재계산)에서도 쓰이므로 그 호출부들의 의미(measurable만 다뤄야
  하는지, meta도 포함해야 하는지)를 각각 확인하고 필요한 곳만 넓힌다 — 무분별한 전역 확장 금지.
- "자리 추가" 폼(`buildNextLevelDraft`, `draft.axes`)도 meta 수치 지표를 다룰 수 있게 맞춘다.
  증가량 입력이 meta 지표에 실제로 반영되어야 한다.
- 저장 API(`PUT /api/admin/badges/{id}`)·검증 로직이 meta 지표 키를 condition_json에
  써도 막지 않는지 확인한다(정합성 트리거 등 기존 저장 경로는 그대로 재사용).

### UI/UX 관점 (해당 시)
- 대상 화면: `jam-web/src/app/admin/badge-families/page.tsx`(목록),
  `jam-web/src/app/admin/badge-families/[familyKey]/FamilyDetailManager.tsx`(상세)
- 라벨·안내문구·버튼 텍스트를 중학생도 이해할 수 있는 쉬운 말로 순화한다. 기능·데이터
  구조·API는 그대로 두고 화면에 보이는 텍스트만 바꾼다.
- 예시 방향(최종 문구는 구현 단계에서 화면 맥락에 맞게 판단):
  - "자리" → "단계"(레벨/등급을 아우르는 쉬운 말)
  - "계열 구성" → 단계별 값을 고친다는 의미가 바로 오는 말
  - "증가 규칙(등차/등비/수동)" → 값이 어떻게 늘어나는지 쉬운 설명 붙이기
  - "조건 축" → "조건값"처럼 더 쉬운 말
  - "일괄 재계산", "임계값 공식" → 무엇을 하는 기능인지 짧게 풀어쓰기
- `family_key`(계열 키)처럼 백엔드 개념과 직접 연결된 용어는 완전히 다른 말로 바꾸면 오히려
  혼란을 줄 수 있으므로, 이런 경우는 쉬운 설명을 덧붙이는 방향으로 판단해도 된다.
- `UX_WRITING_GUIDELINE.md`의 톤 규칙(해요체, 간결하게)을 지킨다.

## 구현 계획
1. `numericAxisKeysOf()` 호출부 전수 확인 (인라인 표 열 구성, 다음 레벨 초안, 일괄 재계산) —
   각 호출부가 meta 수치 지표까지 다뤄야 하는지 판단 후 필요한 곳만 확장.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- 버그: `numericAxisKeysOf()`(`role: 'measurable'`만 필터)를 인라인 편집 표(열 구성·행 값)와
  「자리 추가」 초안(`buildNextLevelDraft`)에서 그대로 쓰던 것이 원인이었다. `role: 'meta'`인
  사용량 지표(`daily_sync_count` 등)는 아예 열 후보에 들지 않아 'JAM! 출석!' 계열의 조건값이
  화면에 나타나지 않았다. `badge-families.ts`에 새 함수 `editableAxisKeysOf()`(measurable +
  usage-metric 합집합)를 추가해 두 지점(인라인 표·자리 추가 초안)에서만 이 함수로 교체했다.
  `numericAxisKeysOf()` 자체는 손대지 않았다 — 기존 테스트(측정 지표 role 분리 의도)가 이미
  그 경계를 고정해 두고 있었다.
  - **부수 확인·수정**: `numericAxisKeysOf()`는 「일괄 재계산」 섹션의 축 선택 목록에도
    쓰이고 있었는데, 재계산 API(`/api/admin/badge-families/recalculate`)는 여전히
    `MEASURABLE_CONDITION_KEYS`로만 축을 검증한다. 인라인 표용 축 목록을 넓히면서 이 축
    목록을 공유했다면 meta 지표를 재계산 축으로 고를 수 있게 되어 API가 「다시 계산할 수
    없는 지표입니다」로 거절하는 새 버그가 생겼을 것이다 — 발견해서 `recalcAxisKeys`를
    별도로 분리해(측정 지표만, 기존 `numericAxisKeysOf()` 그대로) 막았다.
  - 저장 API(`PUT /api/admin/badges/{id}`)·`findBadgeConditionSaveError`는 `ALL_CONDITION_KEYS`
    (meta 포함) 기준으로 이미 meta 키를 허용하고 있어 수정이 필요 없었다(코드 확인만).
- 용어 순화: `page.tsx`(목록)·`FamilyDetailManager.tsx`(상세)의 라벨·안내문구·버튼 텍스트를
  순화했다. "자리"→"단계", "계열 구성"→"단계별 값 고치기", "자리 추가"→"단계 추가",
  "증가 규칙(등차/등비/수동)"→"값이 느는 방식(일정하게 늘어남/배로 늘어남/직접 입력)",
  "조건 축"→"조건값", "일괄 재계산"→"여러 단계 값 한번에 바꾸기", "사용 조건 지표"→"조건값",
  "변경 전후 확인"→"바뀔 값 미리 보기" 등. `family_key`·`2단 교차 게이트`는 완전히 다른 말로
  바꾸지 않고 쉬운 설명을 덧붙였다(예: "다른 미션 조건(2단 교차 게이트)이 이 키로 이 계열을
  가리킬 수 있어요"). "계열" 자체는 이 화면 밖(어드민 내비게이션 라벨·게이트 미션 화면 등)에서
  같은 용어로 폭넓게 쓰이고 있어 두 화면만 다른 말로 바꾸면 오히려 일관성이 깨진다고 판단해
  유지하고, 목록 화면 첫 문단에서 "이 시리즈를 '계열'이라고 불러요"로 쉬운 설명을 덧붙였다.

### 주요 의사결정 / 핵심 메모
- `numericAxisKeysOf()`를 직접 넓히지 않고 `editableAxisKeysOf()`를 신설했다 — 티켓이 명시한
  "무분별한 전역 확장 금지"와, 기존 테스트가 이미 `numericAxisKeysOf`를 "엔진이 발급 판정에
  쓰는 measurable 필드만"으로 문서화·검증하고 있었기 때문이다.
- 「일괄 재계산」 섹션의 축 목록은 인라인 표와 공유하지 않고 별도(`recalcAxisKeys`, 기존
  `numericAxisKeysOf` 그대로)로 유지했다 — 재계산 API가 여전히 measurable만 허용하기 때문에,
  공유했다면 meta 지표를 골랐을 때 API가 거절하는 새 버그가 생겼을 것이다. 재계산 API 자체를
  meta까지 허용하도록 넓히는 것은 이 티켓 범위 밖이라 하지 않았다(재계산 API 검증 확장은
  범위 밖 판단·후속 필요 시 별도 티켓 권고).
- "계열"이라는 용어 자체는 두 화면만 바꾸지 않고 유지했다 — 어드민 내비게이션·게이트 미션
  화면 등 스코프 밖 화면에서도 같은 용어를 쓰고 있어, 이 두 화면만 다른 말로 바꾸면 오히려
  전체 어드민 안에서 용어가 갈린다고 판단했다. 대신 목록 화면 첫 문단에 쉬운 설명을 붙였다.
