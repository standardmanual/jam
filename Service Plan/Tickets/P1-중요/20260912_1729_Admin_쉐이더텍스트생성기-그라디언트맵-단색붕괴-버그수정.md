# [Admin] 버그 — 쉐이더 텍스트 생성기 그라디언트맵 단색 붕괴

## 배경 / 문제 정의

`20260912_1532`(쉐이더 텍스트 생성기 신규)로 프로덕션에 배포한 직후, 사용자가 실사용
중 "컬러를 동일하게 설정하고 옵션값을 최대한 비슷하게 맞췄는데도 전혀 다른 이미지가
나온다"고 보고했다. 참고했던 Brik 예시("LOVE")와 우리 도구 결과("5일 연속 달리기")를
비교한 스크린샷 두 장을 받았다.

**Brik 소스를 가져와 분석하는 방식은 쓰지 않았다** — 이전 결정(저작권·이용약관 문제)을
그대로 유지했다. 대신 실제로 배포된 우리 코드를 esbuild로 번들해 Playwright 헤드리스
Chromium에서 직접 렌더링하고, 단계별 중간 캔버스(에코 합성 → 헤일로 → 그라디언트맵 →
노이즈/그레인)를 스냅샷으로 떠서 눈으로 원인을 추적했다.

### 재현 및 원인 확정

Supabase `shader_text_presets` 테이블에서 사용자가 실제로 저장한 프리셋("111",
2026-09-12 08:03 UTC)을 찾아 그 값 그대로 재현했다. 핵심 값:

```json
"gradientMap": { "core": "#ffffff", "halo": "#ffffff", "shadow": "#ff0000",
                  "innerCore": "#ffffff", "corePosition": 0, "haloPosition": 0 }
```

`composeShaderTextDissolve.ts`의 `buildGradientLut()`은 4개 색 정지점을
`[0, haloPosition, corePosition, 1]` 위치에 배치하고 그 사이를 보간한다. 이때
`haloPosition`과 `corePosition`을 그대로(하한 없이) 썼기 때문에, 사용자가 둘 다 `0`으로
두면 두 정지점 사이 폭이 **0**이 되어 `그림자(shadow)` 색이 사실상 도달 불가능해지고
결과 전체가 `이너 코어` 색(위 값 기준 흰색) 한 가지로 뭉개진다. `그림자`를 빨간색으로
지정했는데도 최종 이미지 어디에도 빨간색이 나타나지 않았다 — 이게 "완전히 다른 이미지"로
보인 직접적인 원인이다.

Brik 참고 툴의 패널 스크린샷에도 Halo/Core Position 기본값이 `0`으로 표시돼 있었는데,
사용자가 이를 보고 그대로 입력한 것으로 보인다. 우리 구현과 Brik의 내부 파라미터화가
다르므로(우리는 0~1 절대 위치, Brik은 아마도 상대 오프셋) 같은 숫자를 넣어도 결과가
같지 않다 — 이건 값 자체의 문제라기보다 **슬라이더 조합이 만들 수 있는 퇴화 상태를
코드가 방어하지 않은 것**이 근본 원인이다.

## 상세 요구사항 / 수정 내용

`buildGradientLut()`에 최소 구간 폭(`GRADIENT_STOP_MIN_GAP = 0.05`, 256단계 LUT 기준
약 13단계)을 강제한다 — `haloPosition`·`corePosition`을 어떤 값으로 두더라도(같은 값,
역순 포함) 그림자→헤일로→코어→이너코어 4구간이 항상 눈에 보이는 폭을 유지한다.

```ts
const GRADIENT_STOP_MIN_GAP = 0.05
const haloPos = clamp(gm.haloPosition, GRADIENT_STOP_MIN_GAP, 1 - GRADIENT_STOP_MIN_GAP * 2)
const corePos = clamp(gm.corePosition, haloPos + GRADIENT_STOP_MIN_GAP, 1 - GRADIENT_STOP_MIN_GAP)
```

이 티켓은 **경미 수정 기준(0.1절)에 해당**한다고 판단해 풀 파이프라인(Workflow) 없이
오케스트레이터가 직접 처리했다 — 변경 파일 1개, diff 10줄 이내, 원인과 수정이 investigation
결과로 명확히 설명 가능. 다만 사용자가 실사용 중 겪은 회귀라 우선순위는 P1로 잡았다.

## 구현 계획

1. `jam-web/src/lib/admin/composeShaderTextDissolve.ts`의 `buildGradientLut()`에 최소
   구간 폭 하한 적용
2. esbuild + Playwright 헤드리스로 실제 shipped 파일을 번들해 사용자의 실제 저장 프리셋
   ("111")을 그대로 재생해 수정 전/후 시각 비교
3. 변경 파일 1개에 한해 `npx eslint`, 프로젝트 전체 `npx tsc --noEmit` 실행
4. staging에 직접 commit

## 유예된 판단 (이 티켓에서 다루지 않음)

- 저장된 프리셋 "111"은 폰트 굵기 45(가변 축 최솟값, 매우 가는 획) + 에코 60개를 반경
  20px 원형 배치(오프셋을 0으로 둬 기본 반경 적용) + 페이드 0(전체 카피가 완전 불투명)으로
  구성돼 있어, 이번 수정 이후에도 "에코가 뚜렷이 갈라져 보이는" Brik 느낌과는 다르게
  나올 수 있다. 이는 슬라이더 값 선택의 문제이지 버그가 아니라고 판단해 범위에서 뺐다.
- Brik과 우리 도구의 Halo/Core Position 의미 차이(절대 위치 vs 추정 상대 오프셋)를 더
  가깝게 맞출지는 별도 논의 사항 — 이번 티켓은 "어떤 값을 넣어도 결과가 퇴화하지 않게"
  방어하는 것까지만 다룬다.

### 주요 의사결정 / 핵심 메모

- **Brik 소스 재분석 요청은 거절하고 우리 코드 자체를 실렌더로 디버깅했다.** 저작권/이용약관
  우려는 코드를 그대로 베끼든 구조만 참고해 재구현하든 동일하게 적용된다고 판단했다 —
  이 판단은 이번 티켓에서도 유지했다.
- **최소 구간 폭을 0.05로 정한 근거**: 256단계 LUT에서 약 13단계 폭이면 육안으로 색 전환이
  인지 가능한 최소 수준이라고 판단했다(임의 값 — 실사용 피드백에 따라 조정 가능).
- **경미 수정 경로로 처리**: 1개 파일, ~10줄 diff, 원인이 이미 실증됐다는 점에서 0.1절
  기준을 충족한다고 판단해 Workflow(jam-developer/리뷰어) 없이 직접 구현했다.

### 잔여 이슈
- 폰트 굵기 45(가변 축 최솟값)처럼 극단적인 값 조합에서 텍스트 획 자체가 매우 가늘어
  보이는 현상은 이번 티켓에서 다루지 않았다 — 버그가 아니라 슬라이더 선택의 결과.
- Halo/Core Position의 UX(0~1 절대 위치라는 게 직관적인지, 사용자가 어떤 값을 넣어도
  "합리적인" 결과가 나오도록 슬라이더 자체의 기본값·설명 문구를 더 손볼지)는 실사용
  피드백을 더 받은 뒤 별도 티켓에서 검토한다.
