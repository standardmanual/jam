# [Service] 인벤토리 조합(믹스) 소비 시 used_slots 카운터 미반영

## 배경 / 문제 정의
> 왜 이 작업이 필요한가. 현재 상태와 기대 상태의 차이.

sihyunrr@gmail.com 계정에서 인벤토리 화면은 비어 보이는데(자유 아이템 0개, 보유 20개 전부
아이템북 슬롯에 장착됨) 슬롯 프로그레스바는 "5/10"으로 표시되는 증상이 접수됐다.

`inventory.used_slots`는 실시간 COUNT가 아니라 픽업·슬롯 장착/해제·드랍·관리자 재배정
이벤트마다 개별적으로 증감시키는 캐시 카운터다(`068_used_slots_slot_policy_fix.sql` 정책:
`dropped_at IS NULL AND slotted_in IS NULL`인 아이템 수). 슬롯 장착/해제
(`111_item_slot_atomic_rpc.sql`), 픽업/드랍(004/007/047/108 마이그레이션), 관리자 재배정
(`110_admin_orphaned_item_actions.sql`)은 전부 이 카운터를 정상적으로 증감시키는데,
**아이템 조합(믹스) 경로(`jam-web/src/lib/combine/index.ts`의 `combineItems()`)만 누락돼
있다.**

- 재료 아이템 소각(120~126행: `destroyed_at` 세팅 + `inventory_id`를 NULL로 비움) 시
  `used_slots` 감소 처리 없음.
- 조합 성공 시 `grantBadge()`(235~272행)로 보상 아이템을 인벤토리에 INSERT할 때도
  `used_slots` 증가 처리 없음.

DB 조사 결과 이 계정은 2026-09-09 15:10:24에 재료 5개를 조합에 소비했고, 그 5칸이
반환되지 않은 채 캐시 카운터에 남아 프로그레스바가 어긋났다. 전체 8개 유저 계정을 전수
비교한 결과 이 계정만 불일치가 있었다(다른 계정은 아직 조합 기능을 써보지 않음) — 즉
잠재적으로 조합 기능을 쓰는 모든 유저에게 재발 가능한 버그다.

이 계정의 데이터 불일치는 `seed_fix_used_slots_combine_consume_desync.sql`로 이미
직접 보정해 staging에 반영 완료했다(커밋 dbec4d49). 이 티켓은 근본 원인인 코드 버그
수정만 다룬다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `combineItems()`에서 재료 아이템 소각 직후 `inventory.used_slots`를 소각한 개수만큼
  감소시킨다 (`GREATEST(0, used_slots - N)` 패턴 — `111_item_slot_atomic_rpc.sql` 참고,
  음수 방지 필수).
- `grantBadge()`로 보상 아이템 지급 시 `inventory.used_slots`를 증가시킨다. 인벤토리가
  가득 찬 상태에서 조합 보상을 받는 경우의 정책(칸을 초과해서라도 지급할지, 아니면 어떻게
  처리할지)을 정해야 한다 — 재료 소각으로 이미 빈 칸이 생긴 뒤 보상이 들어오는 흐름이므로
  일반적으로는 여유가 있겠지만, 레시피가 재료 수보다 많은 보상 배지를 지급하는 경우도
  있어(`reward_badge_ids` 배열) 검토가 필요하다.
- 기존 `combineItems()`가 이미 원자적 UPDATE(`destroyed_at IS NULL` 필터)로 동시 요청
  레이스를 막고 있으니, 카운터 증감도 그 범위 안에서 함께 처리해 정합성이 깨지지 않게 한다.

## 구현 계획
> 어떻게 구현할지. 접근 방법, 영향 범위, 주요 변경 포인트.

`jam-web/src/lib/combine/index.ts` 단일 파일 수정으로 예상. 소각 UPDATE 직후
`inventory.used_slots`를 감소시키고, `grantBadge()` 내부(또는 호출부)에서 지급 성공 시
증가시킨다. 회귀 재현 경로: 재료 2개 이상으로 조합 실행 → 조합 전후 `used_slots`가
정확히 (감소분 - 증가분)만큼 변하는지 확인. 레시피 매칭 성공/실패 양쪽 경로 모두 확인
(실패 시에도 재료는 소각되므로 감소 처리는 동일하게 필요, 보상 배지 지급만 없음).

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
`combineItems()`가 인벤토리를 조회할 때 `used_slots`/`max_slots`도 함께 읽어 함수 실행
내내 로컬로 추적하는 `InventorySlotState` 타입을 도입했다.

- **재료 소각 직후**: 소각이 확정된 개수(`destroyedRows.length`)만큼
  `Math.max(0, used_slots - N)`으로 감소시키고 즉시 DB에 반영한다(`111_item_slot_atomic_rpc.sql`의
  `GREATEST(0, ...)` 클램프를 TS로 이식). 레시피 매칭 성공/실패 양쪽 경로 모두 이 지점을
  공통으로 지나므로 실패 시에도 동일하게 반영된다.
- **보상 배지 지급 시(`grantBadge()`)**: 배지 존재 확인 이후, 인벤토리 INSERT 직전에
  `used_slots >= max_slots`인지 확인해 가득 찼으면 **그 배지 지급을 생략**하고(칸을 초과해서
  지급하지 않음), 아니면 INSERT 후 `used_slots + 1`로 증가시키고 로컬 상태도 갱신해 같은 조합
  호출 안에서 여러 보상 배지를 순차 지급할 때마다 최신값을 반영한다.

**정책 결정(인벤토리가 가득 찬 상태에서 보상을 받는 경우)**: 이미 코드베이스에 확립된
동일 정책(`jam-web/src/lib/missions/rewards.ts`의 미션 아이템배지 보상 — `used_slots >=
max_slots`면 조용히 skip)과 `jam-web/src/lib/drop-engine/index.ts`(드랍 시 슬롯 초과분은
드랍 자체를 취소)을 그대로 따랐다. 즉 **칸을 초과해서까지 지급하지 않고, 그 보상 배지만
조용히 생략한다**(에러가 아니라 `console.info` 로그만 남김). 레시피의 `reward_points`는
칸과 무관하므로 그대로 지급된다. 재료 소각 → 보상 지급 순서라 일반적으로는 소각된 칸만큼
여유가 생기지만, 레시피의 `reward_badge_ids` 개수가 소각한 재료 개수보다 많은 경우엔 이
스킵 정책이 실제로 발동할 수 있다(회귀 테스트로 검증).

### 주요 의사결정 / 핵심 메모
> 개발 과정에서 검토·결정된 사항, 선택하지 않은 대안과 그 이유.

- **새 RPC를 만들지 않고 TS 레벨 read-modify-write로 구현**: 티켓의 구현 계획이
  "단일 파일 수정"으로 범위를 명시했고, 슬롯 장착/해제(111)나 드랍/픽업(004/007/108)처럼
  이미 RPC로 묶인 경로와 달리, `missions/rewards.ts`·`drop-engine/index.ts`도 동일하게
  TS에서 조회한 값을 로컬로 들고 있다가 최종 UPDATE 한 번으로 반영하는 비-원자적 패턴을
  쓰고 있다 — 이번 변경도 그 기존 패턴을 그대로 따랐다. 재료 소각 자체는 이미
  `.is('destroyed_at', null)` 필터의 원자적 UPDATE로 동시 요청 레이스를 막고 있어, 그
  보호 범위 안에서 카운터 값을 계산하므로 "같은 요청 안에서" 벌어지는 레이스는 없다.
  다만 이 요청과 **동시에** 다른 경로(슬롯 장착/해제·드랍·픽업 등)가 같은 인벤토리의
  `used_slots`를 건드리는 극히 드문 교차 레이스는 이 구현으로 완전히 배제되진 않는다 —
  기존 `missions/rewards.ts`·`drop-engine/index.ts`도 동일한 한계를 이미 갖고 있어 이번
  변경이 새로 도입한 리스크는 아니다(아래 alerts 참고).
- **보상 지급 중 슬롯 부족 시 정책은 "조용히 skip"으로 확정**: 티켓이 열어둔 질문이었으나,
  코드베이스에 이미 있는 동일 상황(미션 아이템배지 보상)의 선례를 그대로 따르는 것이
  일관성 있다고 판단했다. 별도 실패 사유(`CombineFailReason`)를 추가하지 않았다 — 레시피
  매칭 자체는 성공(`success: true`)이고 배지 지급 개수만 줄어드는 것으로 처리했다(포인트는
  그대로 지급).
