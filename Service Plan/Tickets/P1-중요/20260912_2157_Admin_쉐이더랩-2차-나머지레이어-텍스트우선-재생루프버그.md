## 배경 / 문제 정의

1차 티켓 `20260912_1951`(`Service Plan/Tickets/P1-중요/20260912_1951_Admin_쉐이더랩-신규-1차-에디터골격및핵심이펙트.md`)에서 `/admin/shader-lab`을 신규 구현하고 프로덕션(main)까지 배포했다. 대표 이펙트 6종(이미지·디스플레이스먼트맵·블룸·디더링·ASCII·하프톤)만 다뤘고, 사용자가 이 티켓에서 나머지 레이어 확장을 요청했다.

## 확정된 버그 — 재생 루프 레이스 컨디션 (프로덕션에서 실사용자가 겪음, 이 티켓에서 함께 수정)

**증상**: 프로덕션(`j-a-m.app`, Chrome, WebGPU 하드웨어 가속 정상)에서 레이어를 추가하고 이미지를 업로드해도 미리보기에 아무것도 안 나타남. 콘솔에 다음 에러가 찍혔다(실사용자 확인, `dpl_CdouLWFVzmz2ocefRgWFhMdbJ32N` 배포):

```
Uncaught Error: Renderer: .render() called before the backend is initialized. Use "await renderer.init();" before rendering.
```

**원인 (이 세션에서 확정)**: `jam-web/src/lib/admin/shaderLab/useShaderLabPlayback.ts`의 RAF 루프가 `useShaderLabCanvasSource`가 반환하는 `ready` 상태를 확인하지 않고 마운트 즉시 매 프레임 `update()`를 호출한다.

```ts
const loop = (now: number) => {
  ...
  update(timeRef.current, playingRef.current ? delta : 0)   // ← WebGPU 백엔드 init 완료 전이면 여기서 throw
  frameId = window.requestAnimationFrame(loop)               // ← throw 때문에 이 줄이 실행 안 됨
}
```

`update()`가 예외를 던지면 그다음 줄(`requestAnimationFrame(loop)`)이 실행되지 않아 **루프 자체가 영구히 멈춘다.** 이후로는 레이어를 추가하든 이미지를 올리든 캔버스가 다시는 안 그려진다. WebGPU 백엔드 초기화(`ShaderLabCanvasSource.initialize()`, 비동기)가 첫 `requestAnimationFrame` 콜백보다 늦게 끝나면 발생하는 타이밍 문제라 기기·환경에 따라 재현 여부가 갈린다(이 세션에서 아이폰 사파리는 우연히 안 겹쳐서 정상 동작, 사용자의 맥 크롬 데스크톱은 겹쳐서 실패했다 — GPU 성능·드라이버 문제가 아니라 순수 타이밍 문제임을 `chrome://gpu`로 확인 완료: WebGPU Hardware accelerated).

**수정 방향**:
1. `ready`가 `true`가 되기 전에는 `update()` 호출을 건너뛰고 다음 프레임만 예약한다(`requestAnimationFrame(loop)`는 항상 호출되도록 순서 보장).
2. 방어적으로 `update()` 호출을 `try/catch`로 감싸, 혹시 모를 다른 런타임 예외(리사이즈 중 일시적 컨텍스트 문제 등)에도 루프가 영구히 죽지 않도록 한다(에러는 로그만 남기고 다음 프레임으로 계속 진행).
3. 수정 후 **반드시 실제 타이밍 재현 검증**을 한다 — 이 문제는 로컬에서 우연히 안 터질 수 있으므로(1차 게이트·오케스트레이터 검증 모두 통과했다가 프로덕션에서 실제로 터진 전례가 있다), `ready`가 늦게 true가 되는 상황을 인위적으로 만들어(예: `useShaderLabCanvasSource` 반환값을 임시로 delay하거나, 느린 네트워크/CPU 스로틀링으로) 수정 전에는 재현되고 수정 후에는 재현 안 됨을 확인할 것.

#### 1. RAF 재생 루프 레이스 컨디션 수정 (`useShaderLabPlayback.ts`)

티켓이 지목한 정확한 원인(`ready` 미확인 + 예외로 인한 `requestAnimationFrame(loop)` 재예약 누락)을 그대로 확인했다. 수정 내용:
- `readyRef`를 추가해 `ready` 최신값을 ref로 추적(`playingRef`와 동일 패턴).
- `loop` 함수 맨 앞에서 `requestAnimationFrame(loop)`를 **가장 먼저** 호출해, 이후 어떤 코드가 던지는 예외와도 무관하게 다음 프레임이 항상 예약되도록 순서를 바꿨다.
- `readyRef.current`가 `false`면 `update()` 호출 자체를 건너뛴다(시간 누적도 하지 않음 — 재생 중 대기 시간이 애니메이션 점프로 이어지지 않도록).
- `update()` 호출을 `try/catch`로 감싸 방어적으로 처리(에러는 `console.error`로만 남기고 루프는 계속 진행).

**실측 검증(실제 hook 코드 대상, 목은 `@basementstudio/shader-lab`의 `useShaderLabCanvasSource`만 교체)**:

#### 2. 기존 6종 레이어 파라미터 범위 감사

원본 `gh api repos/basementstudio/shader-lab/contents/src/lib/editor/config/layer-registry.ts`를 재조회해 노출 중인 모든 필드를 대조했다.

- **이미지·디스플레이스먼트맵·블룸**: 노출 필드의 min/max/step/기본값이 전부 원본과 일치 — 수정 없음.
- **하프톤**: 노출 필드(색상 모드 3종 축소·shape·spacing·dotSize·angle·contrast·softness·invertLuma·ink·duotoneLight·duotoneDark)의 범위 전부 원본과 일치 — 수정 없음. 원본에만 있는 CMYK/커스텀 팔레트·잉크 프리셋·중첩 블룸 등은 1차 때 의도적으로 축소한 범위라 이번에도 추가하지 않았다(기존 결정 유지, 원본 문서 재확인만).
- **디더링**: 노출 필드는 전부 원본과 일치했으나, 원본에 있고 런타임(`dithering-pass.js`)이 실제로 읽는 `dotScale`(min 0.1/max 1/step 0.1/기본값 1)이 1차에서 누락돼 있었다 — **추가함**. 원본에도 있는 `preset`(Custom/Game Boy)은 여러 필드를 한 번에 프리셋으로 덮어쓰는 **에디터 UI 전용 편의 기능**이고 런타임 `updateParams()`가 직접 읽는 파라미터가 아니라 이번에 추가하지 않았다(프리셋 적용 로직 자체가 별도 구현 필요 — 다음 세션 이후 판단).
- **ASCII**: 노출 필드의 범위 자체는 원본과 일치했지만, 원본에 있고 런타임(`ascii-pass.js`)이 실제로 읽는 파라미터 다수가 1차에서 통째로 누락돼 있었다 — **추가함**: `fontWeight`(100~900, 기본 400 — 글리프 자체 굵기), `bgOpacity`(0~1, 기본 0, colorMode가 원본색상일 때만), `signalBlackPoint`/`signalWhitePoint`(0~1, 기본 0/1), `rowWarp`(0~1, 기본 0), `breakGrid`(select, 기본 off)+`breakThreshold`(0.001~0.5, 기본 0.06, breakGrid가 off가 아닐 때만), `charset`에 "커스텀" 옵션 추가 + `customChars`(텍스트, 기본 " .:-=+*#%@", 최대 128자). 기존 `boldness`(두께 보정, -1~1)와 이름이 겹쳐 보이지 않도록 신규 `fontWeight`는 "폰트 굵기"로 라벨을 구분했다.
- 모든 신규/변경 파라미터 키 이름은 실제 설치된 `ascii-pass.js`/`dithering-pass.js`의 `updateParams(params)` 본문에서 `params.<key>`로 실제로 읽는지 소스 코드로 직접 대조했다(추측 없음).

#### 3. 텍스트(Text) 레이어 신규 구현

- **파라미터 스키마**: 원본 `textParams`(재조회로 최신 확인)와 `text`/`anchor`/`offset`/`fontSize`/`letterSpacing`/`textColor`/`backgroundColor`/`backgroundAlpha`의 key·범위·기본값이 100% 일치하도록 작성했다. `fontFamily`/`fontWeight`만 아래 이유로 원본과 다르다.
- **`fontFamily` 값 매핑(중요한 발견)**: 실제 설치된 패키지의 `renderer/text-pass.js`는 `fontFamily` 파라미터를 자유 문자열로 쓰지 않고, `renderer/text-fonts.js`의 내부 고정 목록(`sans`/`mono`/`bsmnt-grotesque`/`display-serif`/`adhesion`/...16종)에서만 찾는다 — 목록에 없는 값은 조용히 `display-serif`(Georgia 고정 폴백)로 대체돼 원하는 폰트가 전혀 반영되지 않는다. 이 중 `cssVariable`이 지정된 슬롯(예: `sans`→`--geist-sans`)은 `getComputedStyle(document.documentElement)`로 그 CSS 커스텀 프로퍼티 값을 읽어 실제 font-family로 쓴다 — 즉 **그 CSS 변수를 우리가 이 라우트 안에서만 덮어쓰면 원하는 웹폰트를 끼워 넣을 수 있다.** `sans`/`mono`는 이미 1차에서 ASCII의 "고딕"/"고정폭" 옵션으로 쓰고 있어 재활용하면 그 기존 기능이 깨진다. 미사용 슬롯 중 유일하게 "range"(연속 굵기 축)를 지원하는 `bsmnt-grotesque`(→`--bsmnt-grotesque`)를 골라 `/admin/shader-lab/layout.tsx`에서 `"Pretendard Variable"`로 덮어썼다(근거·향후 폰트 추가 방법 전부 `textFontOptions.ts` 주석에 문서화). `!important`로 덮어써 fonts.css의 로드 순서에 기대지 않도록 했다.
- **`fontWeight` 범위 400~900(원본 100~900, Pretendard 실제 축 45~920 어느 쪽도 아님)**: `normalizeTextFontWeight()`는 우리 UI 슬라이더 범위와 무관하게 **선택된 폰트 슬롯의 패키지 내부 하드코딩 범위**로 최종 값을 clamp한다. `bsmnt-grotesque` 슬롯의 하드코딩 범위가 `{min:400, max:900}`이라 우리가 UI에 그보다 넓은 범위(원본 100~900이든 Pretendard 실제 45~920이든)를 보여주면 실제로는 반영되지 않는 값을 사용자에게 보여주는 셈이 된다 — **UI 범위 자체를 400~900으로 좁혔다.** 이 판단 근거를 `textFontOptions.ts`에 상세히 남겼다.
- **UI**: `paramFields.ts`에 `text` 필드 타입(자유 입력 한 줄, `maxLength`) 신규 추가 — ASCII의 `customChars`와 텍스트 레이어의 `text` 둘 다 이 타입을 쓴다. `ShaderLabParamField.tsx`에 렌더러 추가(shadcn `Input`). `effectRegistry.ts`의 `SHADER_LAB_LAYER_TYPES`에 `'text'` 추가 — `ShaderLabLayerSidebar.tsx`는 이 배열을 그대로 매핑해 드롭다운을 그리므로 **별도 코드 수정 없이** 텍스트가 자동으로 목록에 나타난다(파일 자체는 변경하지 않음 — 데이터 기반 구조라 변경이 불필요했다).
- **폰트 로드**: `shaderTextDissolve.ts`의 `PRETENDARD_VARIABLE_CSS_URL`을 값 복사 없이 그대로 import해 재사용(`/admin/shader-lab/layout.tsx`), `/admin/shader-text/layout.tsx`와 동일한 `<link rel="stylesheet" precedence="default">` 패턴을 따랐다.

**실렌더 검증(esbuild+playwright, 워크트리 제약으로 `next dev`/`build` 불가 — 1차와 동일한 방식)**:

### 주요 의사결정 / 핵심 메모

1. **텍스트 레이어 `fontFamily`/`fontWeight` 하이재킹 방식** — 위 "구현 내용 요약" 3번 및 `textFontOptions.ts` 주석에 상세 근거. 요약: 패키지가 자유 폰트 문자열을 허용하지 않아 미사용 CSS 변수 슬롯(`--bsmnt-grotesque`)을 이 라우트 안에서만 하이재킹했고, 그 슬롯의 패키지 내부 하드코딩 굵기 범위(400~900)에 맞춰 UI 슬라이더 범위도 좁혔다(원본 100~900도, Pretendard 실제 축 45~920도 아님 — 실제로 반영되는 값만 노출하기 위한 선택).

3. **`ShaderLabLayerSidebar.tsx`를 수정하지 않음** — 티켓이 "레이어 타입 추가 목록에 텍스트를 넣는다"고 명시했지만, 실제로는 `effectRegistry.ts`의 `SHADER_LAB_LAYER_TYPES` 배열을 그대로 매핑해 드롭다운을 그리는 데이터 기반 구조라, 그 배열에 `'text'`를 추가하는 것만으로 사이드바에 자동 반영된다. 코드 자체를 건드릴 필요가 없어 그대로 뒀다(디자인 의도가 이미 확장 가능하게 짜여 있었음).
4. **(알려야 할 발견, HALT 아님, alerts 참고)** `ShaderLabCanvasSource`를 React 훅 없이 완전히 정적인 config로 직접 사용하고 첫 렌더 이후 아무 파라미터도 바뀌지 않으면, 패키지 내부 dirty 최적화상 딱 한 번 실행된 첫 프레임의 렌더 결과가 그대로 고정된다 — 격리 테스트(순수 클래스 직접 사용, config 완전 고정)에서 이 경로로 텍스트 레이어가 검은 화면에 영구히 고정되는 현상을 재현했다. 다만 **실제 프로덕션 경로(`useShaderLabPlayback` 훅을 통한 `ShaderLabViewport` 사용, `playing=false` 기본 상태 포함)는 별도로 재현되지 않음을 확인했다** — 위 "텍스트 단독" 실렌더 검증이 정확히 이 시나리오(슬라이더 조작 없이 방치)를 재현했는데도 정상 렌더링됐다. `MediaPass`(이미지)는 비동기 로드 완료 시 `.then(() => { this.dirty = true })`로 명시적으로 재렌더를 보장하는 콜백이 있지만 `TextPass`에는 그런 보장이 코드상 안 보인다 — 왜 훅 경로에서는 재현되지 않는지 근본 원인까지는 특정하지 못했다(추정: 훅의 초기화 effect 타이밍이나 React 커밋 사이클과 관련된 차이로 보이나 확정 못함). **실사용에 지장이 없음을 확인했으므로 이번 티켓 범위에서 추가 조치는 하지 않지만**, 향후 훅을 거치지 않고 `ShaderLabCanvasSource`를 직접 쓰는 새 진입점(예: 3차의 서버사이드/헤드리스 내보내기)을 만들 경우 이 특성을 반드시 인지해야 한다.
