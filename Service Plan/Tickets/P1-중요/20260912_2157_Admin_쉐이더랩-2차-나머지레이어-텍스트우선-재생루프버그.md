# [Admin] 쉐이더 랩 2차 — 나머지 레이어 확장(텍스트 우선) + 재생 루프 레이스 컨디션 수정

## 배경 / 문제 정의

1차 티켓 `20260912_1951`(`Service Plan/Tickets/P1-중요/20260912_1951_Admin_쉐이더랩-신규-1차-에디터골격및핵심이펙트.md`)에서 `/admin/shader-lab`을 신규 구현하고 프로덕션(main)까지 배포했다. 대표 이펙트 6종(이미지·디스플레이스먼트맵·블룸·디더링·ASCII·하프톤)만 다뤘고, 사용자가 이 티켓에서 나머지 레이어 확장을 요청했다.

**이 티켓 착수 전 1차 티켓 전문을 반드시 읽을 것** — 원본 저장소 조사 결과, 라이선스 준수 방식, 기존 아키텍처 결정(공개 API만 사용, `useShaderLabCanvasSource` 채택 이유 등)이 전부 그 문서에 있다. 여기서는 반복하지 않는다.

## 이번 세션에서 확정된 사항 (사용자 결정)

1. **범위**: shader-lab 원본 전체 32종 레이어 중 **비디오·카메라·커스텀 셰이더 3종은 제외**한다(사용자 명시). 남는 건 아래 "레이어 목록" 참고.
2. **우선순위**: 이번 2차에서 **텍스트(Text) 레이어가 최우선**이다. 다른 레이어보다 먼저 완성해서 검증할 것.
3. **텍스트 레이어 폰트**: `Pretendard Variable`을 쓴다. 이미 `/admin/shader-text`(티켓 `20260912_1532`)가 이 라우트 전용으로 CDN 로드하는 방식을 확립해뒀다 — 그대로 재사용한다.
   - CDN URL: `jam-web/src/lib/admin/shaderTextDissolve.ts`의 `PRETENDARD_VARIABLE_CSS_URL` 상수 값 그대로 사용 (같은 버전 태그 고정, 직접 값을 다시 베끼지 말고 이 상수를 import해서 재사용하거나 공용 lib로 뽑아낼 것 — 두 라우트가 서로 다른 CDN 버전을 쓰게 되는 사고를 막기 위함).
   - `layout.tsx`에서 `<link rel="stylesheet" precedence="default">`로 로드하는 패턴도 `jam-web/src/app/admin/shader-text/layout.tsx`를 그대로 참고한다.
   - **구글 폰트 추가는 이번 범위 밖이다** — 사용자가 "추후 추가 예정"이라고만 밝혔다. 다만 폰트 선택 UI(`fontFamily` 파라미터, 아래 표 참고)를 만들 때 나중에 옵션을 추가하기 쉬운 구조(예: 폰트 목록을 배열 상수로 분리)로 짜두면 좋다 — 이번에 구글 폰트 통합 자체를 구현하지는 않는다.
4. **파라미터 값 범위 일치 필수**: 사용자가 "shader-lab에서 설정한 프로퍼티의 값의 범위와 동일하게 해야 비슷한 효과가 나온다"고 명시적으로 요구했다. **min/max/step/기본값을 임의로 추측하지 말고 원본 저장소에서 그대로 가져올 것.**
   - 원본 소스 위치: `src/lib/editor/config/layer-registry.ts` (각 레이어 타입의 `ParameterDefinitions` 배열 — key/label/min/max/step/defaultValue/type/options 전부 정의되어 있음)
   - select 옵션 목록(폰트 목록 등)은 `src/lib/editor/text-fonts.ts`(`TEXT_FONT_OPTIONS`, `GLYPH_FONT_OPTIONS`) 등 관련 파일도 함께 확인할 것.
   - 1차 때 `effectRegistry.ts`를 만들 때는 **런타임 패스 구현**(`packages/shader-lab-react/src/renderer/*-pass.ts`)의 `updateParams()`만 대조해서 파라미터 *이름*은 정확했지만, UI 슬라이더의 *범위*까지 원본 에디터와 일치시켰는지는 확인되지 않았다 — 이 티켓에서 6종 기존 레이어의 범위도 `layer-registry.ts`와 대조해 어긋난 게 있으면 함께 바로잡을 것(발견 시 완료 기록에 남길 것).
   - 원본 저장소 조회 방법: `gh api repos/basementstudio/shader-lab/contents/<경로> --jq '.content' | base64 -d` (이 세션에서 이 방식으로 조회했다). 리포지토리 전체 파일 트리는 `gh api "repos/basementstudio/shader-lab/git/trees/main?recursive=1" --jq '.tree[].path'`.

## 확정된 버그 — 재생 루프 레이스 컨디션 (프로덕션에서 실사용자가 겪음, 이 티켓에서 함께 수정)

**증상**: 프로덕션(`j-a-m.app`, Chrome, WebGPU 하드웨어 가속 정상)에서 레이어를 추가하고 이미지를 업로드해도 미리보기에 아무것도 안 나타남. 콘솔에 다음 에러가 찍혔다(실사용자 확인, `dpl_CdouLWFVzmz2ocefRgWFhMdbJ32N` 배포):

```
Uncaught Error: Renderer: .render() called before the backend is initialized. Use "await renderer.init();" before rendering.
```

**원인 (이 세션에서 확정)**: `jam-web/src/lib/admin/shaderLab/useShaderLabPlayback.ts`의 RAF 루프가 `useShaderLabCanvasSource`가 반환하는 `ready` 상태를 확인하지 않고 마운트 즉시 매 프레임 `update()`를 호출한다.

```ts
const loop = (now: number) => {
  ...
  update(timeRef.current, playingRef.current ? delta : 0)   // ← WebGPU 백엔드 init 완료 전이면 여기서 throw
  frameId = window.requestAnimationFrame(loop)               // ← throw 때문에 이 줄이 실행 안 됨
}
```

`update()`가 예외를 던지면 그다음 줄(`requestAnimationFrame(loop)`)이 실행되지 않아 **루프 자체가 영구히 멈춘다.** 이후로는 레이어를 추가하든 이미지를 올리든 캔버스가 다시는 안 그려진다. WebGPU 백엔드 초기화(`ShaderLabCanvasSource.initialize()`, 비동기)가 첫 `requestAnimationFrame` 콜백보다 늦게 끝나면 발생하는 타이밍 문제라 기기·환경에 따라 재현 여부가 갈린다(이 세션에서 아이폰 사파리는 우연히 안 겹쳐서 정상 동작, 사용자의 맥 크롬 데스크톱은 겹쳐서 실패했다 — GPU 성능·드라이버 문제가 아니라 순수 타이밍 문제임을 `chrome://gpu`로 확인 완료: WebGPU Hardware accelerated).

**수정 방향**:
1. `ready`가 `true`가 되기 전에는 `update()` 호출을 건너뛰고 다음 프레임만 예약한다(`requestAnimationFrame(loop)`는 항상 호출되도록 순서 보장).
2. 방어적으로 `update()` 호출을 `try/catch`로 감싸, 혹시 모를 다른 런타임 예외(리사이즈 중 일시적 컨텍스트 문제 등)에도 루프가 영구히 죽지 않도록 한다(에러는 로그만 남기고 다음 프레임으로 계속 진행).
3. 수정 후 **반드시 실제 타이밍 재현 검증**을 한다 — 이 문제는 로컬에서 우연히 안 터질 수 있으므로(1차 게이트·오케스트레이터 검증 모두 통과했다가 프로덕션에서 실제로 터진 전례가 있다), `ready`가 늦게 true가 되는 상황을 인위적으로 만들어(예: `useShaderLabCanvasSource` 반환값을 임시로 delay하거나, 느린 네트워크/CPU 스로틀링으로) 수정 전에는 재현되고 수정 후에는 재현 안 됨을 확인할 것.

## 구현 계획

1. 원본 `layer-registry.ts` 전체를 조회해 29종 전체(텍스트 우선)의 파라미터 정의(범위 포함)를 확보
2. 재생 루프 레이스 컨디션 수정 (위 절 1~3번) — 다른 작업보다 먼저 처리 권장(프로덕션 활성 버그)
3. 기존 6종의 파라미터 범위도 `layer-registry.ts`와 대조해 어긋난 부분 수정
4. 텍스트 레이어부터 구현: `effectRegistry.ts`/`paramFields.ts`에 스키마 추가, 실제 런타임 text pass의 `updateParams()`와 대조, Pretendard Variable 폰트 로드(`shaderTextDissolve.ts`의 상수 재사용), 실제 브라우저(WebGPU)로 렌더 확인
5. 텍스트 검증 완료 후 나머지 소스 4종 + 이펙트 18종 순차 추가
6. `/admin/shader-lab` 페이지 상단 안내 문구("1차 범위는 6종...")를 실제 지원 레이어 수에 맞게 갱신
7. 로컬 `ADMIN_EMAILS` 실렌더 확인 (레이어별로 최소 1회씩) — 이번엔 프로덕션에서 실제로 문제가 터진 전례가 있으므로 특히 꼼꼼히 할 것

## 유예된 판단

1. 구글 폰트 추가는 범위 밖(사용자가 추후 요청 예정).
2. 비디오·카메라·커스텀 셰이더는 로드맵 전체에서 범위 밖(사용자 결정, 재검토 시 별도 요청 필요).
3. 3차(배지·컬렉션·미션 자동 등록)는 여전히 범위 밖.
4. `fontWeight` 범위를 원본(100~900) 그대로 둘지 Pretendard Variable 실제 지원 범위(45~920)로 조정할지는 구현 시 확정.
