# [Admin] 쉐이더 랩 — 배경 투명 설정이 PNG export에 반영되지 않음

## 배경 / 문제 정의

사용자가 쉐이더 랩에서 레이어의 배경색 알파(투명도)를 0(완전 투명)으로 설정했는데, PNG를
저장(export)하면 투명하게 저장되지 않고 불투명하게 나온다고 보고했다. 컴포지션 전체 배경색을
따로 설정하는 UI는 없으므로, 사용자가 말한 "배경색"은 텍스트 레이어 `textColor` 또는 리퀴드
메탈 `colorBack`의 알파 슬라이더(둘 다 티켓
[20260913_2110](../P2-일반/20260913_2110_Admin_쉐이더랩-리퀴드메탈이미지마스크-색상투명도지원.md)에서
`alpha: true`로 추가됨)를 가리키는 것으로 판단된다.

## 사전 조사 결과 (오케스트레이터, Explore 에이전트 위임)

### 원인

`ShaderLabExportPanel.tsx`의 `canvasToBlob()`, `bakePreviewToBlob.ts`의 `canvas.toBlob(...,
'image/png')` 자체에는 배경을 강제로 채우는 로직이 없다 — 문제는 export 이전에 렌더링되는
캔버스 자체가 처음부터 알파를 가질 수 없는 상태로 만들어진다는 데 있다. 원인은 JAM! 코드가
아니라 `@basementstudio/shader-lab` 패키지(node_modules, `patches/@basementstudio+shader-lab
+3.0.2.patch`가 건드리지 않는 파일들)의 렌더러 설계에 있다:

1. **`create-webgpu-renderer.js:6-11`**: `new THREE.WebGPURenderer({ alpha: false, ... })`로
   WebGPU 컨텍스트 자체가 opaque로 생성된다.
2. **같은 파일 `:25`**: `renderer.setClearColor("#0a0d10", 1)` — 매 프레임 alpha=1(완전
   불투명)로 클리어한다.
3. **`pipeline-manager.js:130-136, 204-205`**: `PipelineManager` 생성자가
   `MeshBasicMaterial({ color: "#080808" })`의 풀스크린 쿼드(`baseMesh`)를 만들어, 모든 레이어
   패스가 돌기 **전에** 프레임 전체를 opaque `#080808`로 먼저 채운다. 레이어가 하나도
   없거나(`activePasses.length === 0`) 전부 alpha=0이어도 이 base scene만 그려진 채 끝난다.

레이어 자신의 텍스처(Canvas 2D `fillStyle` / `getShaderColorFromString`) 안에서는 알파가
정확히 계산된다 — 티켓 20260913_2110의 QA는 "**아래 레이어가** 비쳐 보이는지"(레이어 간 합성)
만 검증했고, 최상단 캔버스가 opaque로 시작한다는 사실은 그때 발견되지 않았다. 즉 레이어 내부
알파 계산과 export UI(패널·훅) 코드는 정상이며, 파이프라인 최상단(WebGPU 컨텍스트·클리어
컬러·베이스 메시)이 문제다.

### 게이트 리뷰 sideFinding(티켓 20260914_1025)과의 관계 — 별개 문제

티켓 [20260914_1025](../P3-낮음/20260914_1025_Admin_쉐이더랩PNG-export-헤드리스환경alpha0-잠재이슈.md)
(P3, OPEN)는 **헤드리스(WebGPU 미지원) 환경에서 PNG export가 완전 투명(alpha=0)하게 나온다**는
내용으로, 실제 GPU 환경(macOS Chrome)에서는 문제없다고 보고됐었다. 이번 사용자 보고는 그
반대다 — **실제 지원 브라우저에서, 알파를 0으로 설정해도 export가 항상 완전 불투명하게
나온다.** 한쪽은 "항상 불투명"(이 티켓), 다른 한쪽은 "항상 투명"(20260914_1025)이라 증상이
반대이고 코드 경로도 다르다(하나는 정상 렌더링 파이프라인 내부의 opaque 하드코딩, 다른 하나는
렌더링 자체가 실패/유실되는 특수 테스트 환경 현상). **두 티켓을 하나로 묶어 고치려 하면 안
된다** — 20260914_1025는 그대로 별도 유지한다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 레이어 알파가 0에 가까울수록 최종 export PNG의 해당 영역도 그에 비례해 투명해지도록
  렌더링 파이프라인을 수정한다.
- 수정은 `patches/@basementstudio+shader-lab+3.0.2.patch`에 `create-webgpu-renderer.js`·
  `pipeline-manager.js` 패치를 추가하는 방식이 될 가능성이 높다(`WebGPURenderer({ alpha: true
  })`, `setClearColor`의 alpha 인자를 0으로, `baseMesh`를 조건부 처리 또는 알파 인식하도록
  변경 등) — 착수 시 실측으로 최소 변경 지점을 확정한다.
- **사이드 이펙트 위험**: `baseMesh`(#080808 배경판)를 단순 제거하거나 투명화하면, 레이어가
  없는/약한 상태에서 배경이 무엇으로 보여야 하는지(현재는 짙은 회색으로 안정적으로 보임)가
  바뀐다 — 다른 모든 레이어 타입(그라디언트·하프톤·ASCII·디더링 등 29종)의 기존 시각적
  결과물에 회귀가 없는지 반드시 확인한다. 특히 alpha 블렌딩이 기본으로 꺼져 있던 레이어들이
  이번 변경으로 의도치 않게 반투명해지지 않는지 주의한다.
- `ShaderLabViewport`(미리보기)·`ShaderLabExportPanel`(PNG export)·`ShaderLabApplyTab`(배지/
  미션/컬렉션 적용)이 모두 같은 캔버스/텍스처를 공유하므로, 수정 하나로 세 화면 모두 일관되게
  반영되는지 확인한다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

사전 조사가 지목한 두 지점(`create-webgpu-renderer.js`의 `alpha:false`/클리어알파,
`pipeline-manager.js`의 opaque `baseMesh`) 외에, 실제 코드를 직접 추적한 결과 **세 번째
하드코딩 지점**을 추가로 발견했다 — `blend-modes.js`의 `buildBlendNode()`가 `compositeMode
=== "filter"`(텍스트·리퀴드 메탈 등 대부분의 레이어가 쓰는 기본 합성 모드) 분기에서 최종
알파를 무조건 `float(1)`로 반환하고 있었다. 이 세 번째 지점이 실질적인 병목이었다 — 앞의 두
곳만 고쳐도 매 레이어 패스를 거칠 때마다 `blend-modes.js`가 알파를 다시 1로 덮어써, 레이어
자신의 알파 계산(텍스트 `textColor`/리퀴드 메탈 `colorBack`)이 아무리 정확해도 최종 합성
결과는 항상 완전 불투명으로 돌아왔다.

3개 파일을 함께 patch했다:
1. **`create-webgpu-renderer.js`**: `WebGPURenderer({ alpha: true })`로 변경(캔버스
   프레젠테이션 자체가 알파를 지원하도록), `setClearColor(..., 0)`으로 클리어 알파도 0으로.
2. **`pipeline-manager.js`**: 매 프레임 최하단에 깔리는 `baseMesh`(RGB `#080808` 풀스크린
   쿼드)를 `MeshBasicMaterial` 대신 `MeshBasicNodeMaterial` + `colorNode`로 바꿔, RGB는
   `#080808` 그대로 유지하되 알파만 0으로 직접 기록하도록 했다. `material.opacity`/
   `transparent` 조합은 블렌딩 여부만 바꿀 뿐 프래그먼트가 쓰는 실제 알파값 자체를 지정할
   수 없어서(불투명 렌더는 GPU 블렌딩만 끌 뿐, 알파 채널 자체는 여전히 임의 값으로 기록
   가능) `colorNode`로 직접 alpha=0을 반환하는 방식을 택했다 — `transparent:false`(블렌딩
   비활성) 상태를 유지하므로 다른 29종 레이어가 기대하는 "완전 불투명 덮어쓰기(replace)"
   동작은 그대로다.
3. **`blend-modes.js`**: `compositeMode === "filter"` 분기의 알파 계산을 표준 소스-오버
   공식(`outAlpha = baseAlpha + blendFactor·(1−baseAlpha)`, `blendFactor = opacity×
   blendAlpha`)으로 바꿨다. RGB 합성(`mix`) 식은 회귀 방지를 위해 손대지 않았다 — base
   알파가 항상 1이던 기존 동작에서는 새 공식도 결과가 동일하다(`base.a=1`이면
   `1 + blendFactor·0 = 1`, 즉 이전 하드코딩 `float(1)`과 100% 일치). `compositeMode ===
   "mask"` 분기(마스크 기능)는 이 티켓 범위 밖이라 건드리지 않고 `float(1)` 하드코딩을
   그대로 뒀다 — 마스크 모드는 자체적으로 항상 완전 불투명을 의도하는 별개 기능이라
   회귀 위험을 피했다.

회귀 확인: `applySharedColorAdjustments()`가 넘기는 `sourceNode.a`는 텍스트/리퀴드 메탈처럼
직접 알파를 계산하는 2개 레이어 외의 나머지(그라디언트·하프톤·ASCII·디더링 등)는 거의 항상
1을 반환한다(`effectNode` 소스 확인) — 이 경우 새 알파 공식도 `outAlpha = baseAlpha +
1×(1−baseAlpha)`로 결국 1에 수렴해 기존 "완전 불투명" 결과와 동일하다. `media-pass.js`처럼
업로드 이미지 자체가 알파를 가질 수 있는 레이어는 이번 수정으로 그 알파가 처음으로 올바르게
전파되는데, 이는 사이드이펙트가 아니라 이 티켓이 요구하는 "레이어 알파가 최종 export에
비례 반영"의 정확한 적용이다(레이어 타입에 무관하게 동일 메커니즘을 씀).

### 주요 의사결정 / 핵심 메모

- **사전 조사에 없던 세 번째 원인(`blend-modes.js`)을 직접 코드 추적으로 발견**했다 —
  `create-webgpu-renderer.js`·`pipeline-manager.js`만 고치고 `blend-modes.js`를 그대로
  뒀다면, `baseMesh`의 알파를 0으로 바꿔도 매 레이어 패스가 `buildBlendNode()`를 거치며
  알파를 다시 1로 덮어써 증상이 전혀 해결되지 않았을 것이다. 세 파일을 함께 고쳐야만
  알파가 최종 캔버스까지 실제로 전파된다.
- **`baseMesh`의 알파를 0으로 바꾸는 방법으로 `MeshBasicNodeMaterial`을 선택**했다 —
  기존 `MeshBasicMaterial({ color, opacity, transparent })` 조합으로는 "블렌딩 비활성 +
  알파만 0" 조합을 만들 수 없었다(opacity를 낮추면 transparent:true가 되어 블렌딩이
  켜지고, 그러면 클리어 컬러가 그대로 노출되는 등 다른 부작용이 생김). `colorNode`로
  RGBA를 직접 지정하는 방식이 "RGB는 유지, 알파만 변경, 블렌딩은 비활성 유지"라는 요구를
  정확히 충족했다.
- **`compositeMode === "mask"` 분기는 의도적으로 그대로 뒀다** — 마스크 기능은 이 티켓의
  대상(텍스트/리퀴드 메탈의 배경 알파)이 아니고, `float(1)` 하드코딩을 건드리면 마스크
  레이어가 항상 완전 불투명하던 기존 동작이 바뀌어 별도 회귀 위험이 생긴다.

### 잔여 이슈
- **esbuild+playwright 실측이 이 워크트리/에이전트 환경에서 완전히 실패했다.** 티켓
  20260913_2110의 완료 기록은 같은 패턴으로 실제 픽셀값을 얻었다고 남겼지만, 이번 세션
  에서는 Playwright 번들 Chromium(기본)·실제 `Google Chrome` 채널 모두, headless/headed
  모두에서 WebGPU 캔버스가 완전히 빈 상태(RGBA 전부 0, `canvas.toDataURL()`도 빈 PNG)로만
  나왔다 — `navigator.gpu.requestAdapter()`는 성공("ok")하는데 실제 렌더 패스 결과물이
  캔버스에 전혀 반영되지 않는다. 이 세션에서 시도한 조합: (1) Playwright 번들 Chromium +
  `--enable-unsafe-webgpu --enable-features=Vulkan,UseSkiaRenderer` → GPU 커맨드 인코더
  단계에서 "Invalid Texture/TextureView" 오류 발생, (2) 실제 `channel: "chrome"` +
  `--enable-unsafe-webgpu`, headless → 오류는 없지만 빈 캔버스, (3) 동일 조합 headed
  (`headless:false`) → 동일하게 빈 캔버스. **원본 패치(수정 전)로 되돌려도 동일하게
  빈 캔버스**였으므로 이번 patch가 원인이 아니라, 이 에이전트 실행 환경 자체가 실제 GPU
  렌더 패스를 완주시키지 못하는 것으로 보인다(같은 증상을 별도로 다루는 티켓
