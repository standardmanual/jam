# [Admin] 쉐이더 랩 — PNG 투명배경, 알파를 그레이스케일 마스크로 병행 렌더링하는 방식으로 재설계

## 배경 / 문제 정의

티켓 [20260914_1139](20260914_1139_Admin_쉐이더랩-PNG투명배경-재현-근본원인-readback.md)
(canvas swap chain을 우회하고 `renderer.readRenderTargetPixelsAsync()`로 렌더타겟 raw 픽셀을
직접 읽는 접근)를 오케스트레이터가 로컬 실제 GPU 환경에서 직접 검증한 결과, **이 접근으로도
투명 배경이 반영되지 않는다**는 것을 확인했다. 게이트 리뷰가 FAIL로 판정했던 이유(실제 GPU
환경 미검증)가 그대로 실제 실패로 이어진 것이다.

## 오케스트레이터 로컬 실측으로 확정한 새 근본 원인

1139 티켓의 `captureFrame()`(half-float 디코딩, WebGPU 256바이트 행 패딩 스트리핑, Y flip)
자체는 **정확하게 구현되어 있고 정상 동작한다** — 실측으로 알파값을 raw half-float 비트
패턴(`15360 = 0x3C00 = IEEE754 half-float 1.0`) 단위까지 정확히 읽어냈다. 문제는 이 함수가
읽어오는 **렌더타겟(rtA/rtB) 자체에 이미 alpha=1.0(완전 불투명)이 고정되어 저장돼 있다**는
것이었다 — readback 로직이 아니라 그 이전 단계(GPU 렌더링 자체)가 원인이다.

원인은 three.js WebGPU `NodeMaterial`의 다음 로직이다
(`node_modules/three/build/three.webgpu.js`, 소스는 `three/src/materials/nodes/
NodeMaterial.js`):
```js
// OPAQUE
if ( builder.isOpaque() ) {
    diffuseColor.a.assign( 1.0 );
}
```
```js
isOpaque() {
    const material = this.material;
    return material.transparent === false && material.blending === NormalBlending
        && material.alphaToCoverage === false;
}
```
`material.transparent`가 기본값(`false`)인 모든 `MeshBasicNodeMaterial`(baseMesh, 각
레이어 pass, blit 단계 전부)은 **GPU 셰이더 컴파일 단계에서 알파가 무조건 1.0으로
하드코딩**된다. 레이어가 알파를 아무리 정확히 계산해도(리퀴드 메탈 `colorBack`, 텍스트
`textColor`), 이 최적화가 결과를 덮어써 버린다.

## 우회 시도 4건 — 모두 렌더타겟 레벨에서 실패

`isOpaque()`의 세 조건과 `NodeMaterial.outputNode`(설정 시 `isOpaque()` 체크 전체를
우회하는 커스텀 출력 경로)를 각각 로컬에서 실측 시도했으나 전부 실패했다:

1. `material.transparent = true` — 실패
2. `material.blending = THREE.NoBlending` — 실패
3. `material.alphaToCoverage = true` — 실패
4. `material.outputNode = colorNode`(커스텀 출력으로 `isOpaque()` 완전 우회) — **swap
   chain(화면에 보이는 canvas)에서 `drawImage`로 읽으면 효과가 있는 것처럼 보였으나**, 이는
   착시였다. `blitMaterial`은 swap chain(최종 화면 표시)에만 관여하고, `readRenderTargetPixelsAsync`가
   읽는 대상(`pipeline.lastReadTarget`, 즉 각 레이어 pass가 순차로 그려 넣는 rtA/rtB)은
   `blitMaterial`과 무관한 별개의 렌더타겟이다. `baseMesh`와 각 pass(`PassNode`)의 material에
   동일한 `outputNode` 트릭을 적용해도 rtA/rtB에 저장되는 실제 값은 여전히 alpha=1.0이었다
   (`readRenderTargetPixelsAsync` 기준 실측 확인 — 이게 유일하게 신뢰할 수 있는 검증
   방법이라는 점도 이번에 재확인했다. `canvas.toDataURL()`/`toBlob()`/`drawImage()`로
   WebGPU 캔버스를 직접 읽는 모든 방법은 premultiplied swap chain 특성상 신뢰할 수 없다).

이 네 가지 시도로 미뤄보면, `isOpaque()` 강제 로직은 material 속성 조정 수준으로는
우회되지 않는, three.js WebGPU 백엔드에 깊이 박힌 최적화로 보인다. 정확한 내부 메커니즘
(예: 파이프라인 캐시 키 계산이 이 속성 변경을 반영 못 하는 것인지, 아니면 다른 레이어에서
또 강제되는 것인지)은 이번 조사로도 규명하지 못했다.

## 사용자와 합의한 새 방향 — 알파를 별도 그레이스케일 채널로 병행 렌더링

"알파"라는 개념 자체를 쓰지 않고 **밝기(RGB) 값으로 알파 정보를 인코딩**하면 `isOpaque()`
강제와 충돌하지 않는다(밝기 채널은 애초에 알파가 아니므로 이 로직의 영향을 받지 않는다).

### 설계

1. **컬러 패스(기존 유지)**: 지금처럼 각 레이어를 합성한 최종 컬러(RGB)를 그대로 렌더링한다.
   알파는 무시된다(현재도 이미 그렇게 동작 중 — 항상 완전 불투명 RGB로 나온다는 사실 자체는
   문제가 아니다, RGB 값 자체는 정확하다).
2. **알파 패스(신규)**: 각 레이어의 최종 누적 알파값(`blend-modes.js`의 filter 알파 공식이
   계산하는 `outAlpha`)을 `vec4(outAlpha, outAlpha, outAlpha, 1)`로 복제한 별도 material로,
   컬러 패스와 동일한 레이어 순서·블렌드 로직을 거쳐 **별도의 렌더타겟 체인**(예: `alphaRtA`/
   `alphaRtB`, 컬러용 `rtA`/`rtB`와 병행)에 렌더링한다. 이 결과물은 실질적으로 "알파를
   그레이스케일로 시각화한 흑백 마스크 이미지"가 된다.
3. **캡처**: `captureFrame()`을 확장해 컬러 렌더타겟과 알파 렌더타겟 양쪽을
   `readRenderTargetPixelsAsync()`로 각각 읽는다(1139 티켓의 half-float 디코딩 로직은
   그대로 재사용 가능 — 렌더타겟 포맷·리드백 메커니즘 자체는 정상 동작이 이미 검증됐다).
4. **합성**: `captureShaderLabFrameToBlob.ts`(또는 그 대체 함수)에서 두 픽셀 배열을
   클라이언트 사이드로 합성한다: `finalRGBA[i] = (colorPixels[i].rgb, alphaPixels[i].r)`.
   `ImageData`를 만들어 2D 캔버스에 `putImageData()` 후 `toBlob()`하면 정확한 알파를 가진
   PNG가 나온다.

### 구현 범위 참고

- 알파 패스는 `PipelineManager.render()`의 로직을 컬러 패스와 병행해서 한 번 더 실행해야
  한다 — 매 캡처 요청마다(연속 렌더링 루프가 아니라 export 버튼을 눌렀을 때만) 1회 추가
  렌더면 충분할 가능성이 높다. 애니메이션 미리보기용 매 프레임 렌더까지 두 배로 만들 필요는
  없다 — **export/적용 시점에만** 알파 패스를 트리거하는 방향으로 설계해 성능 영향을
  최소화한다(착수 시 재검토).
- 각 `PassNode`의 `composeColorNode()`(→ `buildBlendNode()`의 filter 분기가 계산하는
  `outAlpha`)를 재사용해 알파 전용 material의 colorNode를 만들어야 한다 — `blend-modes.js`에
  RGB 대신 알파를 3채널에 복제해 반환하는 별도 모드나 헬퍼가 필요할 수 있다.
- `compositeMode === "mask"`(마스크 기능) 레이어는 이 티켓 범위 밖으로 유지한다(20260914_1045
  때와 동일한 판단 — `float(1)` 하드코딩을 그대로 둔다).

## 상세 요구사항

### 서비스/코드베이스 관점

- 위 설계대로 알파 패스를 구현하고, 컬러+알파 두 렌더타겟을 합성해 최종 PNG의 alpha
  채널이 레이어 알파값에 정확히 비례하는지 로컬 실측(실제 GPU 환경, 이 티켓의 실측 방법을
  그대로 따를 것)으로 확인한다.
- `ShaderLabExportPanel.tsx`(PNG export), `ShaderLabApplyTab.tsx`(적용·미리보기 스냅샷) 세
  경로 모두 새 합성 함수를 쓰도록 갱신한다.
- 회귀 확인: 알파를 안 쓰는 나머지 27종 레이어 타입의 기존 export 결과(RGB)가 이번
  변경으로 달라지지 않는지 대표 몇 종을 픽셀 비교로 확인한다.

## 구현 계획

1. `blend-modes.js`에 알파 전용 출력 헬퍼(또는 기존 `buildBlendNode()`에 옵션 추가)를
   만들어 filter 분기의 `outAlpha`를 `vec4(a,a,a,1)`로 반환할 수 있게 한다.
2. `PipelineManager`에 알파 전용 렌더타겟 체인과, 컬러 패스와 동일한 레이어 순서로 이를
   채우는 렌더 경로를 추가한다(export 시점에만 트리거하는 방향 우선 검토).
3. `create-webgpu-renderer.js`의 `captureFrame()`을 확장해 컬러+알파 두 렌더타겟을 모두
   읽어 반환하도록 수정한다(또는 별도 `captureAlphaFrame()` 추가).
4. `captureShaderLabFrameToBlob.ts`(또는 신규 합성 함수)에서 두 픽셀 배열을 합성해 최종
   `ImageData`를 만들고 `toBlob()`한다.
5. `useShaderLabPlayback.ts`/`ShaderLabExportPanel.tsx`/`ShaderLabApplyTab.tsx`를 새 합성
   경로로 갱신한다.
6. 로컬 실렌더(실제 GPU 환경, `DEV_PROCESS_GUARDRAILS.md` 패턴 13)로 텍스트/리퀴드 메탈
   알파 0/0.5/1 조합 export를 재측정하고, alpha 채널이 정확히 비례하는지 확인한다.
7. 알파 미사용 레이어 대표 몇 종의 회귀 확인.
8. `npx tsc --noEmit`, `npm run lint`, `npx vitest run` 재확인, patch-package 재적용성
   (postinstall) 확인.

## 참고 — 재사용 가능한 기존 자산

1139 티켓의 다음 부분은 이번 설계에서도 그대로 유효하므로 재사용한다:
- `decodeHalfFloatRgbaToUint8()`(half-float→8bit 변환, WebGPU 256바이트 행 패딩 스트리핑,
  Y flip) — 렌더타겟 raw 픽셀을 8bit로 바꾸는 로직 자체는 실측으로 정확함이 확인됐다.
- `PipelineManager.readPixelsAsync()`/`renderer.readRenderTargetPixelsAsync()` 기반
  캡처 메커니즘 — 컬러 렌더타겟은 이미 이 경로로 정상 캡처되고 있다(RGB 값 자체는 항상
  정확했다). 알파 렌더타겟도 동일한 메커니즘으로 읽으면 된다.
