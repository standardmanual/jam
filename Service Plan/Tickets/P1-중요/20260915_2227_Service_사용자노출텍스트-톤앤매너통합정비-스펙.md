# [Service] 사용자 노출 텍스트 톤앤매너 통합 정비 — 스펙

> 이 티켓은 `/to-spec`으로 작성된 상위 스펙이다. 실제 구현은 `/to-tickets`로 화면·API 라우트 단위 하위 티켓으로 쪼개 `/jam-work` 파이프라인으로 처리한다. 이 티켓 자체는 구현하지 않는다 — 하위 티켓이 모두 CLOSED되면 이 티켓도 CLOSED로 닫는다.
>
> 관련 문서: [`CONTEXT.md`](../../../CONTEXT.md), [`docs/adr/0001-server-error-message-single-source.md`](../../../docs/adr/0001-server-error-message-single-source.md)

## Problem Statement

반복적인 기능 개선 작업이 쌓이면서, 서비스 곳곳의 안내 문구·에러 메시지·버튼 라벨이 서로 다른 시점에 서로 다른 어조로 작성됐다. 그 결과 사용자는 같은 성격의 상황(예: 축하, 안내, 오류)에서도 화면마다 다른 톤의 메시지를 받는다. 또한 일부 문구에는 AI가 작성한 티(번역투, 상투적 수사, 부자연스러운 어미)가 남아 있어 서비스의 완성도와 신뢰도를 낮춘다.

구체적으로 확인된 원인:
- 딕셔너리(`jam-web/src/lib/i18n/ko.ts`) 체계가 이미 있음에도 불구하고, 사용자 노출 화면 46개(추가 확인분 포함)와 서버 API 라우트 약 35개에 텍스트가 여전히 하드코딩되어 딕셔너리를 거치지 않는다.
- 서버가 보낸 에러 메시지를 클라이언트가 처리하는 방식이 파일마다 다르다 — 어떤 화면은 서버 메시지를 무시하고 자체 문구를 쓰고(`DropsClient.tsx`, `CombineClient.tsx`), 어떤 화면은 서버의 하드코딩된 원문을 그대로 노출한다(`MissionDetailClient.tsx`).
- `UX_WRITING_GUIDELINE.md`가 있지만, 실제 텍스트가 이 가이드를 준수하는지 전수 검증된 적이 없다.

## Solution

서비스 전체의 사용자 노출 텍스트(화면 문구 + 서버 에러 메시지)를 딕셔너리(`ko.ts`) 하나로 통합하고, 보완된 `UX_WRITING_GUIDELINE.md` 기준으로 `/im-not-ai` 전수검사를 통과시켜 서비스 언어를 하나의 목소리로 통일한다.

작업은 다음 순서로 진행한다:
1. `UX_WRITING_GUIDELINE.md` 재검토·보완 (선행)
2. 화면·API 라우트 단위로 `/im-not-ai` 전수검사와 딕셔너리 편입을 병행 — 검사에서 발견된 문제를 고치면서 동시에 딕셔너리로 옮긴다
3. 검사 중 가이드 자체의 문제가 발견되면 그 즉시 가이드도 갱신한다

## User Stories

1. As a JAM 사용자, 나는 배지를 획득했을 때와 미션에 실패했을 때 서로 다른, 상황에 맞는 톤의 메시지를 원한다. 그래야 지금 벌어진 일이 좋은 일인지 아닌지 문구만 보고도 바로 알 수 있다.
2. As a JAM 사용자, 나는 에러가 발생했을 때 [현상]→[원인]→[해결책] 구조의 메시지를 원한다. 그래야 무엇이 잘못됐고 어떻게 해야 할지 스스로 판단할 수 있다.
3. As a JAM 사용자, 나는 미션에 참여할 때와 배지를 조합할 때 서버가 알려주는 에러 사유(예: "이미 신청한 미션입니다")를 화면에서 정확히 보고 싶다. 그래야 왜 실패했는지 추측하지 않아도 된다.
4. As a JAM 사용자, 나는 앱 어디를 가든 같은 개념(획득·드랍·픽업·체크인·인벤토리 등)이 같은 단어로 불리길 원한다. 그래야 새 화면을 만났을 때도 헷갈리지 않는다.
5. As a JAM 사용자, 나는 서비스 문구에서 번역투나 AI가 쓴 것 같은 어색한 표현을 느끼고 싶지 않다. 그래야 서비스를 만든 사람이 직접 신경 써서 쓴 글이라는 느낌을 받는다.
6. As a JAM 개발자, 나는 새 화면을 만들 때 텍스트를 하드코딩하지 않고 딕셔너리 키 하나만 참조하면 되길 원한다. 그래야 문구 통일성을 신경 쓰지 않고도 자동으로 일관성이 지켜진다.
7. As a JAM 개발자, 나는 API route에서 에러를 던질 때 딕셔너리(`d.*`)를 직접 import해서 쓰길 원한다. 그래야 같은 에러 문구를 서버와 클라이언트 양쪽에 중복으로 정의하지 않는다.
8. As a JAM 개발자, 나는 클라이언트 컴포넌트에서 서버가 보낸 에러 메시지를 별도 가공 없이 그대로 토스트에 띄우길 원한다. 그래야 화면마다 에러 처리 로직을 다르게 짤 필요가 없다.
9. As a JAM 개발자, 나는 배지 조건·진행률처럼 동적으로 조합되는 문장도 템플릿 문자열(`t(template, vars)`)로 딕셔너리에 등록하고 싶다. 그래야 로직과 텍스트가 분리되어 유지보수가 쉬워진다.
10. As a 콘텐츠 담당자(카피라이터 역할), 나는 `UX_WRITING_GUIDELINE.md`를 보면 서비스 전체에서 어떤 용어와 톤을 써야 하는지 바로 알 수 있길 원한다. 그래야 새 문구를 쓸 때마다 기존 화면을 일일이 뒤져보지 않아도 된다.
11. As a 콘텐츠 담당자, 나는 가이드에 없는 새로운 상황(예: 신규 기능의 안내 문구)을 만났을 때 가이드를 그 자리에서 보완할 수 있길 원한다. 그래야 가이드가 실제 서비스 상태와 계속 일치한다.
12. As a 게이트 리뷰어(`conservative-reviewer`), 나는 새로 작성된 문구가 딕셔너리를 거치는지, 가이드의 톤·용어 규칙을 지키는지 기계적으로 확인할 수 있는 체크리스트를 원한다. 그래야 리뷰 때마다 판단 기준이 흔들리지 않는다.
13. As a JAM 사용자, 나는 랭크(등급)명을 볼 때 언제나 같은 철자·표기(Common/Rare/Epic/Mystic)로 보고 싶다. 그래야 과거 변경 이력 때문에 헷갈리지 않는다.
14. As a JAM 사용자, 나는 버튼의 동사(예: "확인", "삭제", "저장")가 실제로 그 버튼이 하는 행동과 정확히 일치하길 원한다. 그래야 실수로 원치 않는 동작을 누르지 않는다.
15. As a JAM 개발자, 나는 SEO 메타데이터(`app/layout.tsx`의 description 등)에 남은 하드코딩 텍스트도 딕셔너리로 옮기고 싶다. 그래야 서비스 소개 문구가 화면 문구와 따로 놀지 않는다.
16. As a JAM 개발자, 나는 최초 조사(정규식 기반 grep)가 놓쳤을 수 있는 하드코딩 텍스트가 더 있는지 전수검사 단계에서 한 번 더 확인하고 싶다. 그래야 "빠진 곳 없음"을 자신 있게 말할 수 있다.
17. As a JAM 사용자, 나는 어드민이 아닌 일반 사용자 화면에서만 이 정비의 영향을 받길 원한다(어드민 UI는 이번 범위 밖). 그래야 어드민 작업 도구의 문구 스타일이 바뀌어 관리자 업무 흐름이 흔들리지 않는다.

## Implementation Decisions

- **딕셔너리 아키텍처 유지**: 신규 체계를 만들지 않는다. 기존 `jam-web/src/lib/i18n/ko.ts`(23개 네임스페이스)와 `d`/`t(template, vars)`/`getDictionary()` 구조를 그대로 확장 대상으로 삼는다.
- **서버-클라이언트 단일 진실 소스** ([ADR 0001](../../../docs/adr/0001-server-error-message-single-source.md)): API route는 `d.*`를 직접 import해 에러 메시지를 만들고, 클라이언트는 서버가 보낸 메시지를 가공 없이 그대로 신뢰해 노출한다. 같은 문구를 서버·클라이언트에 중복 정의하지 않는다. (`src/lib/i18n`는 `'use client'` 지시어가 없는 순수 모듈이라 서버에서도 바로 import 가능함을 확인함.)
- **동적 생성 텍스트**(`badgeConditionText.ts`, `badgeProgressText.ts`): 완전 재작성이 아니라 기존 `t(template, vars)` 체계의 적용 여부를 감사(audit)하고, 이 체계를 벗어나 하드코딩된 조각을 찾아 딕셔너리 템플릿으로 옮긴다.
- **작업 단위**: 화면(.tsx) 또는 API 라우트 단위로 "전수검사(`/im-not-ai`) → 문제 수정 → 딕셔너리 편입"을 한 번에 처리한다. 검사와 편입을 별개 단계로 완전히 분리하지 않는다.
- **가이드는 살아있는 문서**: `UX_WRITING_GUIDELINE.md`는 이번 작업 도중 발견되는 문제(누락 규정, AI 티가 나는 예시 문구 등)를 그때그때 반영해 덮어쓴다. 버전 사본을 만들지 않는다.
- **범위 경계**:
  - 포함: 사용자 노출 화면 텍스트(딕셔너리 미편입분 포함), 서버 API 에러 메시지, `app/layout.tsx` 등 SEO 메타데이터의 하드코딩 텍스트, `UX_WRITING_GUIDELINE.md` 문서 자체
  - 제외: 어드민 화면(`src/app/admin/**`) 전체, DB 소스 텍스트(배지 이름·설명 등 `badges` 테이블 컬럼), 다국어(로케일 확장) 자체는 이번 범위 밖 — 기존 ko 단일 로케일 구조는 유지

## Testing Decisions

- 이 작업은 로직 변경이 아니라 텍스트·구조 정비이므로, 전통적 유닛 테스트보다 다음 두 가지가 "좋은 테스트"의 기준이 된다:
  1. **`/im-not-ai` 전수검사 통과** — 각 하위 티켓이 다루는 화면·라우트·문서에 대해 실행하고 결과를 티켓의 "테스트 결과" 항목에 남긴다.
  2. **JAM 기존 티켓 템플릿의 "UX Writing 검증" 체크리스트 통과** — 용어 일관성, 톤앤매너, 에러 메시지 3단계 구조, 문장 규칙, 표기 규칙 5개 항목. `_TEMPLATE.md`에 이미 정의돼 있으므로 하위 티켓 작성 시 그대로 사용한다.
- 회귀 확인: 하드코딩 텍스트를 딕셔너리 키로 치환한 뒤에는 해당 화면을 실제로 렌더링해 원래 문구와 정확히 같은 텍스트가 나오는지 눈으로 대조한다(문구를 다듬으면서 동시에 편입하는 경우, 다듬어진 결과가 가이드 기준에 맞는지 별도 확인).
- 게이트 리뷰(`conservative-reviewer`)에서 "딕셔너리를 거치는가"와 "가이드 규칙 준수 여부"를 기계적 체크 항목으로 검증한다.

## Out of Scope

- DB에 저장된 배지 이름·설명(플레이버 텍스트) — 코드가 아니라 DB가 소스이며, 어드민 폼에서 별도 관리됨
- 어드민 화면(`src/app/admin/**`)의 UI 텍스트 전체
- 다국어(ko 외 로케일) 지원 신설 — 이번 작업은 ko 단일 로케일 안에서의 통합·정비
- 푸시 알림·이메일 발송 텍스트 — 조사 결과 해당 발송 채널 자체가 존재하지 않음(인앱 소식함만 있음, 이미 딕셔너리 경유)
- zod 검증 스키마 에러 메시지 — 조사 결과 한글 하드코딩 없음, 해당 없음
