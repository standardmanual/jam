# [Admin] 쉐이더 랩 구글 폰트 선택 직후 미리보기에 반영 안 됨

## 배경 / 문제 정의
티켓 20260916_2001로 staging에 반영한 쉐이더 랩 텍스트 레이어 구글 폰트 기능에서, 사용자가
배포된 staging(`stage.j-a-m.app/admin/shader-lab`)에서 실제로 확인한 결과 **폰트 드롭다운
라벨은 선택한 구글 폰트 이름으로 바뀌지만, 미리보기 캔버스의 텍스트 글꼴은 바뀌지 않는다**고
보고했다.

## 원인 (오케스트레이터가 코드 추적으로 확정)

**staging에서 직접 재현**: 텍스트 레이어 추가 → 폰트 필드에서 "Roboto" 검색·선택 →
드롭다운 라벨은 "Roboto"로 바뀌고, `document.documentElement.style`의 `--adhesion:
"Roboto"`도 정확히 주입됐고, `fonts.googleapis.com` `<link>`도 정확히 로드됐으며,
`document.fonts.ready`도 정상적으로 resolve되고 `document.fonts`에 `Roboto` `status:
"loaded"` 항목도 존재하는데, **미리보기 캔버스만 계속 이전 글꼴 모양 그대로**였다(스크린샷
대조로 확인). 즉 React 상태·CSS 변수·폰트 다운로드는 전부 정상인데 캔버스 렌더링만 갱신되지
않는다.

패키지(`@basementstudio/shader-lab@3.0.2`) 내부 렌더링 파이프라인을 추적한 결과:

1. `jam-web/src/app/admin/shader-lab/ShaderLabPropertiesPanel.tsx`의 `onSelectGoogleFont`가
   `assignGoogleFont` 호출 직후(내부에서 `applyGoogleFontToSlot`으로 CSS 변수 설정 +
   `ensureGoogleFontLoaded`로 `<link>` 삽입) **곧바로** `layer.params.fontFamily`를 새
   슬롯 id로 바꿔 `onChange`를 호출한다.
2. 이 변경이 `page.tsx`의 `layers` state → `config`(`useMemo`) → `useShaderLabCanvasSource`
   → 패키지 내부 `PipelineManager.syncLayers()`로 전파되고, `layer.params`의 시그니처가
   바뀌었으므로 `pass.updateParams(layer.params)`가 호출되며 `TextPass.dirty = true`가
   세팅된다.
3. 다음 렌더 프레임에서 `TextPass.render()`가 `dirty === true`를 보고
   `rebuildTextTexture()`를 **즉시** 호출한다. 이 함수는
   `resolveTextFontFamily(fontFamilyValue)`로 CSS 변수 값을 읽어 `context.font = "... 'Roboto',
   Arial, sans-serif"` 형태로 캔버스 2D `font` 속성을 설정하고 `fillText`로 즉시 굽는다
   (`node_modules/@basementstudio/shader-lab/dist/src/renderer/text-pass.js` 121~158행).
4. **문제**: 브라우저의 canvas 2D `context.font`는 아직 다운로드 중인 웹폰트를 요청받으면
   조용히 시스템 폴백 글꼴로 렌더링하고, **폰트가 나중에 실제로 로드 완료돼도 이미 구워진
   텍스처를 스스로 다시 그리지 않는다.** `TextPass`는 `dirty` 플래그가 다시 `true`가 될
   때만 재렌더링하는데, 웹폰트 다운로드 완료 이벤트(`document.fonts.ready` /
   `FontFace.load()` 완료)는 이 `dirty` 플래그와 전혀 연결돼 있지 않다 — 즉 **한 번
   폴백으로 구워지면 그 레이어의 다른 파라미터를 바꾸기 전까지는 영원히 폴백 상태로
   남는다.**
5. 로컬 `npm run dev`에서는(1차 검증 세션 당시) 브라우저 폰트 캐시가 따뜻하거나 로컬
   네트워크 왕복이 빨라 `context.font` 설정 시점에 이미 폰트가 파싱까지 끝나 있어 우연히
   즉시 반영된 것으로 보인다 — staging(원격 CDN 왕복)에서는 그 경합에서 거의 항상 진다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 구글 폰트를 슬롯에 배정할 때, **웹폰트가 실제로 로드 완료된 뒤에** 텍스트 레이어가
  다시 그려지도록 보장한다. 구체적으로는 `document.fonts.load()`(또는 `FontFace` API)로
  해당 굵기·패밀리를 명시적으로 로드 요청하고, 그 Promise가 resolve된 뒤 **레이어 params의
  시그니처를 다시 한번 바꿔**(예: 내부 전용 nonce/revision 필드를 params에 추가해 매번
  값을 바꾸는 방식 — `parameterValuesSignature`가 params 전체를 시그니처에 포함하므로 이
  필드 하나만 바뀌어도 `PipelineManager`가 다시 `pass.updateParams`를 호출해
  `TextPass.dirty`가 다시 서게 된다) `TextPass`가 재렌더링하도록 만든다.
- 폰트가 이미 로드돼 있는 경우(같은 폰트를 이미 다른 레이어가 쓰고 있어 `<link>`가 중복
  삽입되지 않는 케이스)에는 불필요한 지연 없이 즉시 반영되어야 한다.
- 로딩 중임을 사용자에게 아주 짧게라도 표시할지(스피너/로딩 상태)는 UX 관점에서 결정한다 —
  다만 구글 폰트 css2 응답은 보통 수십~수백 ms 안에 끝나므로 필수는 아닐 수 있다.
- 이 수정은 `useGoogleFontSlots.ts`(슬롯 배정 시점)와 `googleFonts.ts`
  (`ensureGoogleFontLoaded`)를 중심으로 이뤄질 가능성이 높다 — 정확한 구현 지점은
  담당자가 재량껏 판단한다.
- 기존 슬롯 재사용(같은 폰트를 쓰는 다른 레이어)·11개 초과 처리 로직은 그대로 유지한다.

### UI/UX 관점 (해당 시)
- 특별한 문구 변경 필요 없음(기존 안내 문구 유지). 로딩 상태를 표시하기로 결정하면
  UX Writing 가이드에 맞는 짧은 문구를 추가한다.

### 컨텐츠 관점 (해당 시)
- 해당 없음.

## 구현 계획
1. `document.fonts.load(font-spec, text?)` 또는 `FontFace` API로 구글 폰트 로드 완료를
   Promise로 명시적으로 기다리는 헬퍼를 `googleFonts.ts`에 추가한다(현재
   `ensureGoogleFontLoaded`는 `<link>` 삽입만 하고 로드 완료를 기다리지 않는다).
2. `useGoogleFontSlots.ts`의 `assignFont`(및 컴포지션 불러오기 동기화 `useEffect`)에서
   폰트 로드 완료 후 해당 레이어의 params를 다시 한번 갱신해 `TextPass`가 재렌더링하도록
   만드는 메커니즘을 추가한다(레이어 상태를 직접 변경할 방법이 필요 — `page.tsx`의
   `handleUpdateLayer`를 호출할 콜백을 `useGoogleFontSlots`에 전달하거나, 다른 설계를
   선택해도 된다).
3. 로컬 `npm run dev`로 느린 네트워크(Chrome DevTools 네트워크 쓰로틀링 "Slow 3G" 등)를
   흉내 내 재현 후 수정이 실제로 문제를 해결하는지 확인한다 — 이번 조사에서 로컬은 빠른
   네트워크라 재현이 어려웠으므로, 인위적으로 지연을 줘야 검증 가능하다.
4. staging 배포 후(또는 이 티켓 파이프라인의 게이트 리뷰가 가능하다면) 실제
   `stage.j-a-m.app`에서 이번에 재현한 시나리오(텍스트 레이어 추가 → Roboto 검색·선택)를
   다시 실행해 미리보기가 실제로 바뀌는지 확인한다.

### 주요 의사결정 / 핵심 메모
> 개발 과정에서 검토·결정된 사항, 선택하지 않은 대안과 그 이유.

- 오케스트레이터가 staging에서 직접 재현하고 패키지 소스(`text-pass.js`·
  `pipeline-manager.js`·`text-fonts.js`)를 추적해 원인을 확정했다 — 웹폰트 비동기 로드
  완료와 `TextPass`의 `dirty` 재렌더링 트리거가 연결돼 있지 않은 경합 조건(race
  condition)이다. jam-developer는 이 문서의 "원인" 절을 그대로 신뢰하고 재조사 없이
  수정에 착수할 수 있다.
