# [Admin] 믹스 레시피 슬롯 기반 OR 매칭 재설계

## 배경 / 문제 정의

현재(`153_combine_v3.sql`, 티켓 `20260910_1408`) `combination_recipes`는 재료를
`ingredient_badge_ids`(소각) · `required_badge_ids`(보유 조건) 두 배열로 저장하고,
매칭은 "유저가 투입한 배지 집합이 이 배열들과 정확히 일치하는가"로 판정한다. 즉 레시피 하나당
허용되는 조합은 정확히 하나뿐이다.

레시피 설계 폭을 넓히기 위해 **슬롯 개념**을 도입한다. 슬롯 하나는 "이 자리에 넣을 수 있는
배지 후보 목록(OR)"을 어드민이 지정하고, 실제 믹스 시도에서 유저는 슬롯 하나당 배지 하나만
채운다. 후보 중 아무거나 하나만 있으면 그 슬롯은 충족되고, 전체 슬롯이 충족되면 성공이다.
예: 슬롯 1 = {겨울등반 배지, 설산완주 배지 중 1개 보유}, 슬롯 2 = {손전등 아이템 배지 1개 보유}.

이 구조는 기존 "정확히 일치" 방식을 완전히 대체한다 — 기존 레시피는 슬롯마다 후보가 1개뿐인
특수 케이스로 표현 가능하므로 하위 호환 손실은 없다. `combination_recipes`의 현재 레시피
등록 건수가 어드민 등록 이후 아직 미미하므로(선행 티켓 기준 0건이었음), 재설계 시점으로 적절함.

## 상세 요구사항

### 서비스/코드베이스 관점

**1. 슬롯 스키마 신설**

```sql
create table combination_recipe_slots (
  id uuid primary key default gen_random_uuid(),
  recipe_id uuid not null references combination_recipes(id) on delete cascade,
  slot_order integer not null,
  badge_type text not null check (badge_type in ('item', 'activity', 'checkin')),
  allowed_badge_ids uuid[] not null check (array_length(allowed_badge_ids, 1) >= 1),
  unique (recipe_id, slot_order)
);
create index on combination_recipe_slots (recipe_id);
```

- `badge_type`을 슬롯 단위로 고정한다 — 한 슬롯 안에는 **같은 타입의 배지만** 후보로 넣을 수
  있다(어드민 UI·API 양쪽에서 검증, 사용자 확인 완료 사항). `allowed_badge_ids`에 들어가는
  모든 배지는 이 타입이어야 한다.
- `combination_recipes`에서 `ingredient_badge_ids`·`required_badge_ids` 컬럼을 제거한다.
  `reward_points`·`reward_badge_ids`·`hint_text`·`is_public`은 그대로 유지한다.
- 소각 여부는 슬롯에 별도 컬럼을 두지 않고 **`badge_type = 'item'`이면 항상 소각, 그 외
  타입이면 항상 비소각**으로 판정 시점에 고정 결정한다(기존 정책과 동일, 예외 없음).
- 레시피당 슬롯 개수 제약: 최소 2개, 최대 10개(기존 `MIN_INGREDIENTS`/`MAX_INGREDIENTS`
  상수를 슬롯 개수 기준으로 재정의). 단 최소 1개의 아이템 타입 슬롯이 있어야 한다(소각되는
  재료가 전혀 없는 레시피 방지 — 기존 "소모 아이템 2개 이상" 제약을 슬롯 구조에 맞게 조정한
  것이므로, 정확한 하한은 구현 단계에서 재검토 가능).

**2. 매칭 로직 재작성** — `jam-web/src/lib/combine/index.ts`

기존의 "배지 집합 정확 일치"(`sameBadgeSet`) 판정을 슬롯 단위 판정으로 교체한다.

```
매칭 성립 =
  레시피의 모든 슬롯에 대해,
    (해당 슬롯 badge_type이 'item'이면: 유저가 투입한 아이템 배지 중
       allowed_badge_ids에 속하는 것이 정확히 1개 대응)
    (해당 슬롯 badge_type이 'activity'|'checkin'이면: 유저가 보유한 배지 중
       allowed_badge_ids에 속하는 것이 1개 이상 존재 — 보유만 확인, 소각 없음)
  → 하나라도 대응/보유 실패 시 그 레시피는 미매칭
```

- 아이템 슬롯은 "유저가 투입한 아이템 배지"와 1:1로 대응시켜야 한다(투입 개수와 아이템 슬롯
  개수가 일치해야 함 — 기존처럼 여분 투입을 허용할지는 구현 단계에서 재확인).
- 하나의 투입 아이템 배지가 여러 슬롯에 중복 대응되지 않도록 한다(슬롯당 서로 다른 배지
  인스턴스여야 함).
- 액티비티·체크인 슬롯은 보유 여부만 확인하고 소각하지 않는다(`user_activity_badges`,
  `user_checkin_badge_earns` 조회는 기존 로직 재사용).
- 매칭 성공 시 `reward_points`+`reward_badge_ids` 지급, 실패 시 `combine_policy.
  fail_reward_points` 지급 — 이 부분은 변경 없음.
- 여러 레시피가 동시에 매칭 가능한 경우의 우선순위 규칙이 필요하면 구현 단계에서 정의한다
  (현재 정확 일치 구조에서는 이 문제가 발생하지 않았으나, OR 매칭 도입으로 한 유저의 투입이
  여러 레시피 조건을 동시에 만족할 가능성이 생긴다).

**3. API 검증** — `jam-web/src/app/api/admin/recipes/route.ts`, `[id]/route.ts`,
`jam-web/src/lib/admin/recipe-write.ts`

- 슬롯 배열을 받아 슬롯별 `badge_type` 일치 검증(같은 슬롯 안 배지가 전부 같은 타입인지),
  슬롯 개수 하한/상한 검증, 배지 존재 검증을 수행한다.
- 슬롯 저장은 `combination_recipe_slots`에 대한 delete-then-insert(레시피 수정 시 슬롯
  전체 교체) 방식을 기본으로 한다.

### UI/UX 관점

`jam-web/src/app/admin/recipes/RecipeForm.tsx` 전면 수정.

- 슬롯을 카드 목록으로 표시. 카드마다:
  - 배지 타입 선택(아이템/액티비티/체크인) — 최초 배지 추가 시점에 타입이 고정되고, 이후
    다른 타입 배지를 추가하려 하면 검색에서 제외하고 **카드 하단에 안내 문구를 표시**한다.
    문구 예: "이 슬롯은 {타입} 배지만 넣을 수 있어요. 다른 타입을 쓰려면 슬롯을 새로 추가해
    주세요." (UX Writing 가이드의 해요체·간결함 준수)
  - `MultiBadgeSearchSelect`(기존 보상 배지 칸에서 쓰는 컴포넌트)를 재사용해 후보 배지를
    칩으로 추가/삭제. 타입 필터를 슬롯의 고정 타입으로 넘긴다.
  - 칩마다 타입 색상 표시(아이템=호박색, 액티비티·체크인=하늘색) 유지.
  - 슬롯 삭제 버튼.
- "+ 슬롯 추가" 버튼으로 슬롯 카드 신설(최대 10개 도달 시 비활성화).
- 저장 시 검증: 슬롯당 후보 배지 최소 1개, 아이템 타입 슬롯 최소 1개, 전체 슬롯 2~10개.
  위반 시 기존 폼과 동일한 스타일의 에러 메시지(현상 → 원인 → 해결책)를 표시한다.
- `RecipeTable.tsx`(목록 화면)의 재료 표시 열도 슬롯 구조에 맞게 "슬롯 N개(아이템 X · 조건
  Y)" 형태로 갱신한다.
- 어드민 UI는 기존과 동일하게 shadcn/ui 표준을 따른다.

### 유저 화면 관점 (2026-09-17 추가) — 레시피 선택형 플로우로 전환

기존 `/combine` 화면은 유저가 인벤토리에서 아이템을 자유롭게 최대 10개 선택하면, 서버가
전체 공개·비공개 레시피를 훑어 매칭되는 것을 찾는 방식이다(`CombineClient.tsx`,
`api/combine/route.ts`). 슬롯 OR 매칭 도입으로 여러 레시피가 동시에 조건을 만족할 수
있게 되면서 "어느 레시피와 매칭할지"를 서버가 임의로(배열 순회 순서) 정하는 문제가
생겼는데, **이를 유저가 직접 레시피를 먼저 선택하는 방식으로 해결한다.**

- 유저는 노출된(공개) 레시피 목록 중 하나를 먼저 선택한다. 비공개 레시피는 기존처럼
  힌트 문구로만 노출되고 선택 목록에는 뜨지 않는다(현행 유지).
- 레시피를 선택하면 그 레시피의 슬롯 목록이 표시된다. 슬롯마다 유저는 자신이 보유한
  배지 중 해당 슬롯 후보(`allowed_badge_ids`)에 속하는 배지를 하나 골라 채운다(아이템
  배지는 인벤토리에서, 액티비티·체크인 배지는 보유 배지 중에서 선택 — 실제로는 보유
  여부만 확인하면 되므로 "선택"이라기보다 자동으로 슬롯에 표시될 수도 있음, 구현 단계
  판단).
- 제출 시 서버는 **선택한 레시피 하나만** 검증한다: 슬롯마다 채운 배지가 그 슬롯의
  `allowed_badge_ids`에 속하는지, 아이템 슬롯은 실제 인벤토리에 보유(투입)했는지,
  액티비티·체크인 슬롯은 보유하고 있는지 확인. 전체 슬롯이 유효하면 성공, 하나라도
  무효하면 실패(기존과 동일하게 아이템은 소각, 액티비티·체크인은 비소각).
- **이 변경으로 "여러 레시피 동시 매칭 시 우선순위" 문제 자체가 사라진다** — 유저가
  레시피를 특정해서 시도하므로 서버는 후보 레시피 전체를 스캔할 필요가 없다. 이전
  구현의 배열 순회 순서 채택 로직(게이트 리뷰에서 확인된 medium-confidence 판단)은
  제거한다.
- API(`api/combine/route.ts`) 요청 바디에 `recipe_id`(필수)와 슬롯별 채운 값을 추가한다
  (정확한 페이로드 형태는 구현 단계에서 확정, 예: `{ recipe_id, slot_fills: [{ slot_id,
  badge_id_or_item_id }] }`).
- UI 재사용: 레시피 선택 목록은 기존 공개 레시피 카드(`Card tone="inverse"`)를 선택
  가능한 형태(탭 시 하이라이트)로 확장하고, 슬롯 채우기는 기존 `BadgeGridCard`의 선택
  토글 패턴을 재사용한다. 신규 MODULAR 컴포넌트는 만들지 않는다.

### 수용 기준

1. 어드민이 슬롯 2~10개를 만들고, 슬롯마다 같은 타입의 배지를 여러 개 후보로 지정해 저장할
   수 있다.
2. 슬롯에 이미 아이템 배지가 있는 상태에서 액티비티 배지를 검색해도 후보에 나타나지 않고,
   카드 하단에 안내 문구가 표시된다.
3. 유저가 슬롯마다 후보 배지 중 하나씩 보유(아이템은 투입)한 상태로 믹스를 시도하면 매칭
   성공 처리되고, 아이템 슬롯에 대응된 배지만 소각되며 액티비티·체크인 슬롯 배지는 소각되지
   않는다.
4. 슬롯 하나라도 후보 배지를 보유/투입하지 못하면 매칭 실패로 처리되고 `fail_reward_points`가
   지급된다.
5. 아이템 타입 슬롯이 하나도 없는 레시피는 저장이 거부되고 사유가 화면에 표시된다.
6. 기존 `ingredient_badge_ids`·`required_badge_ids` 컬럼과 이를 참조하는 코드가 남아있지
   않다.
7. 기존 테스트가 모두 통과하고, 슬롯 매칭·타입 검증에 대한 신규 테스트가 추가되어 통과한다.
8. 유저 화면(`/combine`)에서 공개 레시피 목록 중 하나를 먼저 선택해야 슬롯 채우기 단계로
   진입한다.
9. 슬롯을 전부 유효하게 채우고 제출하면 선택한 레시피만 검증되어 성공 처리되고, 아이템
   슬롯 배지만 소각된다.
10. 슬롯 중 하나라도 무효(후보에 없는 배지, 미보유)한 상태로 제출하면 실패 처리되고
    투입한 아이템 슬롯 배지는 소각되며 고정 포인트가 지급된다.
11. 서버가 선택된 레시피 외 다른 레시피를 훑어 매칭을 시도하지 않는다(단일 레시피
    검증만 수행).

| 통합 | 전체 슬롯 충족 → 보상 지급 · 슬롯 1개 미충족 → 실패 + 아이템 슬롯만 소각 |
| 어드민 실렌더 | `/admin/recipes` 슬롯 카드 추가/삭제, 타입 고정 안내 문구 노출, 저장 검증 메시지 |

### 롤백 계획

DB는 staging·프로덕션 공용 단일 인스턴스라 마이그레이션 실행 즉시 반영된다. 레시피 등록
건수가 적은 현재 시점에 진행하되, 실행 전 `combination_recipes` 행 수를 실측해 영향 범위를
확인한다. 되돌릴 때는 역방향 마이그레이션으로 기존 배열 컬럼을 복원하고 코드를 revert한다.

### 주요 의사결정 / 핵심 메모
> 개발 과정에서 검토·결정된 사항, 선택하지 않은 대안과 그 이유.

- 슬롯 도입 전 구조(정확 집합 일치, 티켓 `20260910_1408`)를 완전히 대체한다. 슬롯당 후보
  1개로 표현하면 기존 레시피와 동등하므로 하위 호환 손실 없음.
- 슬롯 내 배지 타입 혼용은 사용자 결정으로 금지(같은 타입만 허용) — 혼용 시 소각 여부가
  유저의 선택에 따라 갈리는 예측 불가능한 레시피가 생기는 것을 방지하기 위함.
- 소각 여부는 슬롯 컬럼이 아니라 `badge_type` 값으로 항상 고정 결정(아이템=소각,
  액티비티·체크인=비소각) — 별도 토글을 두지 않아 어드민 실수 여지를 없앰.
