## 배경 / 문제 정의
2026-09-18 세션에서 새 파이프라인을 처음 실사용하며 다음이 드러났다.

- **카리나(메인 세션) 정의가 사실상 비어 있다.** 설계 원본(`docs/agents/Workflow/agents/
  00_카리나_오케스트레이터.md`)의 원칙·하는 일/금지·처음 보는 유형 절차가 활성 문서 어디에도
  없고, 있는 조각(보고 양식·처리 규칙표·`orchestrator.md`)도 메인 세션이 자동으로 읽지 않는다.
  실제로 그 세션은 티켓 15건 이상을 한 세션에서 처리했고, 보고 양식을 쓰지 않았고, 바로잡힌
  일을 규칙표에 남기지 않았다.
- **토큰 실측**: 34줄짜리 여백 수정 티켓(20260915_2016)이 약 22만 8천 토큰·16분을 썼다
  (채원① 5.2만 · 아현 8만 · 민지 6.1만 · 채원② 3.5만).
- **파이프라인 결함**: 채원①의 `needs_approval`이 있어도 멈추지 않고 구현이 진행된다.
  워크트리가 최신 `origin/staging`보다 뒤처진 채 배정된다.
- **자동화·보고 경로 미정**: 예약 작업 스펙은 있으나 미등록, 리포트 저장 위치 없음, Slack은
  이전 결정("즉시 알림 도입 안 함", 티켓 0421)과 새 요구가 부딪힘.

### 안건 0 — 카리나 정의 (2026-09-18)
- **0-1 주입 방식: 세션 시작 hook.** 기존 현황판 hook(티켓 0421)에 "카리나 카드" 출력을 더한다.
  저장소에서 관리돼 모든 PC에 적용되고 서브에이전트에는 전달되지 않는다(구현 시 검증).
  거절: CLAUDE.md 직접 삽입(서브에이전트 8명에게 매번 전달돼 토큰 증가), 개인 메모리(PC별 관리).
- **0-2 카드 범위: 핵심 + 위치 링크.** 원칙·하는 일/넘기는 일/금지·처음 보는 유형 절차만 담고
  (40줄 이내), 보고 양식·처리 규칙표·운영 규칙(`orchestrator.md`)은 위치만 안내한다.
  거절: 전부 담기(세션마다 고정 비용 증가).
- **0-3 세션 원칙: 권고 + 묶음 예외.** 기본은 티켓마다 새 세션. 상위 티켓으로 묶인 시리즈는 한
  세션 허용. 대화가 길어지면 카리나가 인수인계를 남기고 새 세션을 먼저 제안한다.
  거절: 엄격 적용(연속 작업이 번거로움), 자유(오늘처럼 한 세션이 끝없이 길어짐).
- **0-4 보고 양식: 티켓 결과·승인 요청 때만.** 일상 문답은 자유 형식.
  거절: 모든 응답(짧은 질문에도 길어짐).
- **0-5 규칙의 원본: 운영 규칙은 처리 규칙표(저장소).** 프로젝트 운영 교훈(티켓 번호 충돌,
  리베이스 동기화, 격리 워크트리 등)은 `handling-rules.md`가 원본이다. 개인 메모리에는 사용자
  개인 선호(설명 방식·추천안 제시 방식 등)만 남기고, 기존 메모리의 운영 규칙은 규칙표로 옮긴다.
  카리나는 바로잡힌 일이 생기면 규칙표에 한 줄 추가한다.
  거절: 둘 다 유지(같은 교훈이 두 곳에 있어 어긋나고, 다른 PC는 메모리 쪽을 모름).
- **0-6 카리나 모델: 기본 Sonnet, 설계 세션만 Opus.** `settings.json`의 `model: sonnet` 유지.
  구조 설계처럼 판단이 많은 세션만 사용자가 `/model`로 Opus를 켠다.
  거절: 항상 Opus(비용 급증), 항상 Sonnet(설계 품질 저하).

**안건 0 결정 완료.** 구현은 하위 티켓으로 분리한다: 카리나 카드 작성(`orchestrator.md` 보강) +
