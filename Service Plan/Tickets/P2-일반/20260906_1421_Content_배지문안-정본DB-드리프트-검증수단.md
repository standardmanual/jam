# [Content] 배지 문안 정본↔DB 드리프트를 잡을 검증 수단이 없다

> 선행: `20260906_1305`(등급별 설명 분화 — 이 구조적 문제를 드러낸 티켓)
> 개선 리뷰 제안에서 분리 (2026-09-06 사용자 승인)

## 배경 / 문제 정의

`jam-web/supabase/migrations/seed_v5_activity_badges.sql`은 **`INSERT … WHERE NOT EXISTS`
멱등 구조**다. 재실행해도 이미 있는 행의 `description`을 갱신하지 않는다.

즉 **정본(`v5_catalog_writing.json`)과 DB의 문안이 갈라져도 시드 재실행으로는 절대 수렴하지
않는다.** `20260906_1305`에서 문안 436행을 고칠 때도 시드 재생성만으로는 화면이 그대로였고,
별도의 UPDATE 마이그레이션(`138_badge_rarity_descriptions.sql`)을 따로 써야 했다.

문제는 그 사실이 **어디에도 적혀 있지 않고, 어긋났는지 확인할 수단도 없다**는 점이다.
문안 변경은 반복될 영역이므로, 다음번에 「시드 고쳤으니 반영됐겠지」로 넘어가면
**정본과 화면이 조용히 갈라진 채 아무도 모른다.**

같은 뿌리의 문제가 하나 더 있다. `Service Plan/Specs/Content/`의 정본 JSON을 읽는 소비자가
최소 3개(`v5_seed_build.py` · `v5_doc_build.mjs` · 산출물 `seed_*.sql`)인데 **서로를 참조하지
않아**, 정본을 고칠 때 무엇을 함께 돌려야 하는지가 파일 어디에도 없다.
`20260906_1305`에서 `.mjs`가 빠진 것이 그 결과다(→ 티켓 `20260906_1420`).

## 상세 요구사항

### 컨텐츠 관점

**① 정본↔DB 대조 수단** (핵심)
- `v5_seed_build.py`에 `--verify-db` 모드를 추가하거나, 별도 검증 스크립트를 둔다
- `rows.json`(정본에서 생성된 630행)의 `description`·`name`을 DB의 살아 있는 v5 배지와
  전수 대조해 **불일치 행을 나열**한다
- `jam-web/.env.local`의 `SUPABASE_SERVICE_ROLE_KEY`로 읽기만 한다. **쓰기 금지** —
  이 스크립트가 DB를 고치기 시작하면 마이그레이션 이력이 남지 않는다
- 대조 대상은 `type='activity' AND deleted_at IS NULL` + v5 `family_key` 패턴으로 한정한다
  (v4 레거시 207행은 이미 소프트 삭제 상태다)

**② 정본 JSON에 소비자 목록을 남긴다** (저비용 방어)
- `v5_catalog_writing.json`의 `_meta`에 「이 파일을 고치면 함께 돌릴 것」 목록 한 줄:
  `v5_seed_build.py` → 시드 재생성 · `v5_doc_build.mjs` → 문서 재생성 ·
  **DB 반영은 별도 UPDATE 마이그레이션이 필요하다**(시드 재실행으로는 안 된다)
- 같은 문장을 `seed_v5_activity_badges.sql` 머리 주석에도 남긴다 — 그 파일을 여는 사람이
  「이걸 다시 돌리면 되겠지」라고 오해하는 지점이 바로 거기다

## 구현 계획

1. 검증 모드/스크립트 작성 — 읽기 전용, 불일치 행 목록 출력, 종료 코드로 성패 표시
2. 지금 시점에 한 번 돌려 **불일치 0**임을 확인(= `20260906_1305` 적용 결과 재확인)
3. `_meta`·시드 SQL 주석에 소비자 목록 추가
4. 완료 기록에 「다음 문안 변경 시 이 순서로 한다」를 3줄로 남긴다

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
① 읽기 전용 검증 스크립트 `v5_verify_db.py`를 별도로 만들었다(기존 `v5_seed_build.py`는
   「SQL 파일만 쓴다」는 계약이 확고해 DB 접속 코드를 섞지 않았다). `jam-web/.env.local`의
   `SUPABASE_SERVICE_ROLE_KEY`로 PostgREST GET만 호출해 `type='activity' AND deleted_at IS NULL`인
   배지를 페이지네이션으로 전량 읽고, `family_key`가 v5 패턴
   (`^(walking|running|cycling|hiking|trail_running):[A-Z][0-9]*$`)인 행만 남긴다.
   `rows.json`(정본 산출물) 630행과 `(family_key, rarity, level)` 키로 매칭해
   name·description을 비교하고, [MISMATCH]/[MISSING]/[EXTRA] 세 종류로 나열한 뒤
   불일치가 있으면 종료 코드 1을 반환한다. 실제 실행 결과 **정본 630행 = DB 630행,
   불일치 0건** — `20260906_1305`(등급별 설명 분화)가 프로덕션에 정확히 반영돼 있음을
   재확인했다.
② `v5_catalog_writing.json`의 `_meta`에 `고치면_함께_돌릴_것` 키를 추가해 소비자 목록
   (`v5_seed_build.py`→시드·rows.json 재생성, `v5_doc_build.mjs`→문서 재생성, DB 반영은
   별도 UPDATE 마이그레이션 필요)을 한 줄로 남겼다. 같은 문장을 `v5_seed_build.py`의
   SQL 헤더 생성부에 추가해 `seed_v5_activity_badges.sql` 머리 주석에도 반영했다(스크립트를
   재실행하면 이 주석도 함께 생성되므로 「손으로 고치지 말 것」 원칙을 지켰다). 재생성 후
   `rows.json`·`v5_condition_mapping.json`은 바이트 단위로 동일했고 SQL은 주석 추가분만
   diff에 잡혀, 문안 내용에는 아무 변화가 없음을 확인했다.

다음 문안 변경 시 순서:
1. `v5_catalog_writing.json` 수정 → `python3 v5_seed_build.py`로 시드·rows.json 재생성,
   `node v5_doc_build.mjs`로 문서 재생성
2. DB에 이미 반영된 배지의 문안을 바꾸는 경우, 시드 재실행으로는 갱신되지 않으므로
   별도 UPDATE 마이그레이션 파일을 손으로 작성해 실행 요청
3. `python3 v5_verify_db.py`로 정본↔DB 드리프트가 0건인지 재확인 후 마무리

### 주요 의사결정 / 핵심 메모
- `v5_seed_build.py`에 `--verify-db` 모드를 넣는 대신 별도 스크립트로 분리했다: 이 스크립트는
  「SQL 파일만 쓰고 DB에 접속하지 않는다」는 계약을 파일 docstring에 명시하고 있어, 같은 파일에
  DB 읽기 코드를 넣으면 그 계약 문구가 거짓이 된다.
- 대조 키는 `(family_key, rarity, level)`로 잡았다 — `rows.json` 630행 안에서 유일함을
  사전에 확인했다(중복 0건). `name` 자체를 키로 쓰지 않은 이유는 이름 변경이 곧 드리프트의
  한 형태이기 때문이다(그 경우 [MISSING]+[EXTRA] 쌍으로 나타난다).
- v4 레거시 207행은 이미 소프트 삭제 상태라 `deleted_at IS NULL` 필터만으로도 걸러졌지만,
  티켓 지시대로 `family_key` 정규식 필터를 추가로 적용해 향후 다른 타입의 배지가 섞여도
  안전하게 걸러지도록 했다.
