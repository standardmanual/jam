# [Admin] 어드민 시뮬레이션 — POI(체크인) 배지가 `user_activity_badges`에 오기록됨

## 배경 / 문제 정의

사용자 보고: "체크인 배지가 액티비티 배지에 리스팅되고 있어" — v5 회귀인지 확인 요청.

**조사 결과 v5와 무관한 기존(v4 시절) 결함으로 확인됐다.** 오늘(2026-09-06) v5 전환을 위한
유저 전체 초기화(`20260905_0039`)에서 만든 백업 테이블 `bak20260906_user_activity_badges`에서
아래 5건이 발견됐다 — 전부 `type='checkin'` 배지인데 `user_activity_badges`(활동 배지 전용
이어야 할 테이블)에 들어가 있었다:

| 배지 | 타입 | triggered_by | 획득일 |
|---|---|---|---|
| 종로3가역 3호선 | checkin | `admin_simulate` | 2026-07-31 01:21:48 |
| 신답역 | checkin | `admin_simulate` | 2026-07-31 01:21:48 |
| 답십리역 | checkin | `admin_simulate` | 2026-07-31 01:21:49 |
| 광나루역 | checkin | `admin_simulate` | 2026-07-31 01:21:49 |
| 북한산우이역 | checkin | `admin_simulate` | 2026-07-31 03:43:08 |

`triggered_by`가 전부 `admin_simulate` — 실유저 정상 체크인 경로(`/api/checkin-badges/route.ts`,
`user_checkin_badge_earns`에 정상 기록)가 아니라 **어드민 시뮬레이션 도구**에서 발생했다.
획득일이 v5 착수(2026-09-05~06)보다 훨씬 이전이므로 **v5가 만든 회귀가 아니다.**

오늘 유저 초기화로 `user_activity_badges`가 비워져(0행) **지금 프로덕션엔 증상이 안 보인다.**
다만 코드 결함 자체는 그대로 남아 있어, 어드민이 실유저 계정에 POI 통과 경로를 포함한
시뮬레이션을 다시 돌리면 재발한다.

## 원인 — 코드 위치

`jam-web/src/app/api/admin/simulate/route.ts`의 "3. POI 매칭" 블록:

```ts
for (const poi of matchedPois) {
  if (!poi.linked_badge_id) continue
  if (earnedBadgeIds.has(poi.linked_badge_id)) continue
  const badge = poiBadgesById.get(poi.linked_badge_id)
  if (badge) {
    badgesEarned.push({ id: badge.id, name: badge.name, rarity: badge.rarity, reason: `POI 통과: ${poi.name}` })
    earnedBadgeIds.add(badge.id)
    if (!dryRun) {
      const userActivityBadgesQuery = supabase.from('user_activity_badges')
      await userActivityBadgesQuery.insert({ user_id: userId, badge_id: badge.id, triggered_by: 'admin_simulate' })
    }
  }
}
```

`poi.linked_badge_id`가 가리키는 배지는 항상 `type='checkin'`인데, 무조건
`user_activity_badges`에 쓴다. 정상 체크인 경로는 `user_checkin_badge_earns`에 쓴다
(반복 획득 이력 테이블, UNIQUE 제약 없음) — 이 두 경로가 갈라져 있다.

## 부가 발견 — 방어 결핍 (근본 원인과 별개, 화면단)

`jam-web/src/app/(main)/badges/page.tsx`의 "액티비티" 탭 데이터는 `user_activity_badges`를
`badge:badges(*)`로 조인만 하고 **`badge.type`을 전혀 필터링하지 않는다.**
`user_activity_badges`는 설계상 "배지 종류 무관 소유권 통합 테이블"이라(`src/lib/strava/sync.ts:177-180`
주석 참고) 이 필터가 원래 없었던 것으로 보인다. 이번처럼 상위 쓰기 경로가 타입을 안 가리면
화면에 그대로 샌다.

같은 패턴의 잠재 위험 지점 — 아직 실제 데이터로 발현되진 않았다(확인 완료, 아래 참고):
- `jam-web/src/lib/itembook/checker.ts:192-215` — 아이템북 완성 보상(`reward_badge_id`)을
  타입 확인 없이 무조건 `user_activity_badges`에 쓴다("보상 배지는 activity badge이므로"라는
  가정이 주석에 명시돼 있음). **DB 실측(2026-09-06): 현재 `item_books.reward_badge_id`가
  `type != 'activity'`인 배지를 가리키는 행 0건** — 지금 당장 터지진 않지만 가정이 코드에
  하드코딩돼 있어 콘텐츠 쪽에서 체크인/아이템 배지를 보상으로 지정하는 순간 같은 버그가 재현된다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `admin/simulate/route.ts`의 POI 매칭 블록: `badge.type`을 확인해 `checkin`이면
  `user_checkin_badge_earns`에, 그 외(활동 배지 자체가 POI에 연결되는 경우가 있다면)는
  기존대로 `user_activity_badges`에 쓰도록 분기
- (선택, 방어책) `badges/page.tsx` 활동 탭 조회에 `badge.type === 'activity'` 필터 추가 —
  상위 쓰기 경로 결함이 있어도 화면에 새지 않도록
- (선택) `itembook/checker.ts`의 하드코딩된 "보상 배지는 항상 activity" 가정도 같은 김에
  방어적으로 타입 분기하거나, 최소한 타입이 다르면 로그를 남기도록

### 데이터 정리
- 이번에 발견된 5건은 오늘 유저 초기화로 이미 삭제됨 — 별도 데이터 정리 불필요

## 구현 계획
1. `admin/simulate/route.ts` POI 매칭 블록에 배지 타입 분기 추가
2. (선택) `badges/page.tsx` 활동 탭 조회에 방어 필터 추가
3. 회귀 테스트: 어드민 시뮬레이션에서 체크인 배지를 낀 POI 경로로 시뮬레이션 →
   `user_checkin_badge_earns`에 기록되고 `user_activity_badges`엔 안 남는지 확인

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- `admin/simulate/route.ts` POI 매칭 블록에 `badge.type` 분기를 추가했다. `poiBadgesById` 조회
  select에 `type`을 추가하고, `checkin` 타입이면 `user_checkin_badge_earns`에(payload:
  `user_id`, `badge_id`, `poi_id: poi.id`, `triggered_by_activity_name: 'admin_simulate'`),
  그 외 타입이면 기존대로 `user_activity_badges`에 삽입하도록 분기했다.
- 방어선: `badges/page.tsx` 활동 탭 조회에 `badge.type === 'activity'` 필터를 추가해, 상위
  쓰기 경로에 같은 결함이 재발해도 화면에 새지 않도록 했다.
- `itembook/checker.ts`: reward_badge 타입을 배치 조회해 `type !== 'activity'`인 경우
  `console.error`로 경고만 남기도록 했다(동작 변경 없음 — 현재 DB에 해당 케이스 0건 확인됨,
  오케스트레이터 사전 실측).
- 스코프 밖 참고: `ownedBadgeIds`(POI 배지 중복 방지 dedup, 124행)는 여전히
  `user_activity_badges`만 조회한다. checkin 타입 배지는 이 수정 후 그 테이블에 기록되지
  않으므로 시뮬레이션 내에서 기존 체크인 이력이 dedup에 반영되지 않지만, 체크인 배지는
  원래 반복 획득 가능(고유 제약 없음)이 정책이라 회귀가 아니다.
