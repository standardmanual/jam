# [Content] 배지 진행 미지원 사유에 폐지어 「충족」과 내부 키가 노출된다

## 배경 / 문제 정의

`jam-web/src/lib/badge-engine/badgeProgress.ts:678`의 사용자 노출 문구:

```
"휴식 조건은 1개까지만 충족 횟수(repeat_count)와 함께 쓸 수 있어 발급 자체가 막혀요."
```

두 가지가 걸린다.

1. **「충족」은 전면 폐지어다** — `UX_WRITING_GUIDELINE.md` §1.3 (2026-09-06 갱신, 커밋
   `00ead78f`). "「충족」은 시스템이 조건을 판정했다는 사실만 말하고 사용자가 다음에 뭘
   하면 되는지는 말하지 않는다"
2. **`repeat_count`는 내부 식별자다** — 화면에 내부 키를 노출하지 않는다는 기존 원칙
   (「지점(SPOT)」 행이 POI를 노출하지 않는 것과 같은 이유)

**DB까지 함께 봐야 한다.** 같은 함수의 `hiddenAxisLabels`가 `getConditionField(k).label`을
쓰는데, 그 라벨이 `conditionRegistry.ts:1396`과 마이그레이션 `132_repeat_earn_counter.sql:150`
에서 **「충족 횟수」**로 시딩돼 있다. 노출 경로가 있다면 데이터도 같이 고쳐야 한다.

## 상세 요구사항

### 서비스/코드베이스 관점
- **먼저 이 `reason` 문자열이 실제로 화면에 닿는 경로인지 확인한다.** 내부 로그 전용이면
  범위가 크게 줄어든다 (배지엔진의 다른 `reason`들은 어드민 진단용이다)
- 화면에 닿는다면 문구를 고친다. 방향: 「충족 횟수」 → 「달성 횟수」 또는 수치만,
  `repeat_count` 제거, 남은 일을 말하는 형태로
- `conditionRegistry.ts`의 라벨과 DB 시딩 값이 사용자 화면에 닿는지 함께 확인

### 컨텐츠 관점
- DB 값을 고쳐야 하면 `jam-web/supabase/migrations/`에 SQL 파일을 남긴다

## 구현 계획

1. `badgeProgress.ts:678`의 `describe()` 반환값이 어디까지 흘러가는지 추적
2. 노출 경로가 있으면 문구 + 라벨 + (필요 시) DB 시딩까지 한 벌로 수정
3. 노출 경로가 없으면 주석으로 「내부 전용」임을 명시하고 닫는다

**코드 변경 없이 조사만으로 종결.** `explainUnsupportedProgress()`의 호출부를 전수

어드민 배지 저작 화면뿐이었다(`progressIssue.reason`이 1004행에 그대로 렌더링됨,
노출 경로 자체는 확인됨).

`conditionRegistry.ts`의 「충족」 관련 라벨(882·890·893·1396·1405·1406·1409행)을 쓰는
화면도 전수 검색한 결과 `admin/badge-families/page.tsx` ·
`admin/badge-families/[familyKey]/FamilyDetailManager.tsx` · `admin/badges/BadgeForm.tsx` ·
`admin/badges/conditionFormFields.ts` · `components/admin/badges/BadgeDetail.tsx` ·
`components/admin/badges/BadgesTable.tsx` — 예외 없이 `src/app/admin/` 또는
`src/components/admin/` 하위였다. 서비스(일반 유저) 화면에는 이 registry나
`explainUnsupportedProgress`가 전혀 닿지 않는다.

`UX_WRITING_GUIDELINE.md` 108~122행("충족" 자체를 사용자 화면에 쓰지 않는다)을 다시
읽어보니, 정확히 이 케이스를 이미 명시적으로 면제하고 있었다:

> 어드민 저작 화면(`src/app/admin/`)과 내부 로그·`reason` 필드는 이 원칙의 적용 대상이
> 아니다 — 사용자가 보지 않는다.

이번 노출 경로는 "어드민 화면"과 "`reason` 필드" 둘 다에 해당해 이중으로 예외 대상이다.
`repeat_count` 내부 키 노출도 같은 이유로(운영자만 보는 화면) 이번 티켓 범위에서는
문제로 다루지 않는다.

보인다. 조사 결과 실제 노출 경로가 정확히 이 예외 대상과 일치해, 코드·DB 어느 쪽도
고칠 필요가 없다고 판단했다.
