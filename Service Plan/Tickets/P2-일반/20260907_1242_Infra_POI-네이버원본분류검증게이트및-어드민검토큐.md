# [Infra] POI 네이버 원본 분류 검증 게이트 + 어드민 검토 큐

## 배경 / 문제 정의
네이버 지역검색 오픈API는 좌표·반경 파라미터를 지원하지 않는다. `jam-web/src/lib/poi/naver.ts`가
`"{지역명} {키워드}"` 형태로 쿼리를 보내는데(예: `"마포구 연남동 국립공원"`), 해당 동에 대상이
없으면 네이버는 빈 결과 대신 유사도 낮은 무관한 장소를 반환한다. 그런데 현재 코드
([naver.ts:123-130](../../jam-web/src/lib/poi/naver.ts))가 네이버가 함께 내려주는 원본 분류
문자열(`item.category`, 예: `"음식점>분식"`)을 검증 없이 버리고 우리가 지정한 카테고리를 그대로
붙여 저장한다.

실측(2026-09-07, 프로덕션 DB): 자연(nature) 카테고리 자동수집 16건 중 실제 자연 장소는 2건뿐
(오염률 87.5%). "아리계곡"처럼 이름에 자연 키워드가 들어간 것도 실제로는 카페 체인이라 이름
매칭으로도 걸러낼 수 없다 — 재분류하려면 네이버 원본 분류가 반드시 필요하다.

카테고리 재정리([20260907_1243 티켓](20260907_1243_Infra_POI-카테고리체계-재정리-및-기존POI재분류.md))로
nature·tourist_attraction 등 그리드당 수확률이 낮은(0.09~0.55) 카테고리를 계속 자동수집 대상으로
유지하기로 했으므로, 검증 게이트 없이는 오염 데이터가 서비스 지역 확대에 비례해 계속 증식한다.
게이트만으로 100% 걸러지지 않는 애매한 사례는 어드민이 직접 검토해 승인·거부하는 큐가 필요하다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `poi` 테이블에 `naver_category`(text, nullable) 컬럼 추가 — 네이버 응답의 원본 분류 문자열을
  가공 없이 저장. 수동 등록(T1) POI는 값 없음(null)
- `poi_categories` 테이블에 `requires_review`(boolean, default false) 컬럼 추가 — 카테고리별로
  검토 큐 대상 여부를 어드민에서 켜고 끌 수 있게 함. 지도 노출 카테고리 위주로 켜는 것을 권장
  (비노출 카테고리는 당장 급하지 않으므로 기본 꺼짐)
- 수집 시 판정 로직 3단계:
  1. **자동 거부** — 네이버 원본 분류가 기대 카테고리와 명백히 불일치 (저장하지 않음)
  2. **자동 승인** — 명백히 일치 (현재처럼 즉시 저장, `is_active=true`)
  3. **검토 대기** — 애매함 (저장은 하되 검토 대기 상태로 표시, 노출 여부는 카테고리의
     `display_on_map`을 따름 — 게이트 로직과 노출 로직은 분리)
  판정 기준(허용 분류 패턴)은 카테고리별로 하드코딩 상수로 시작해도 무방 — 처음부터 완벽한
  분류 사전을 만들기보다 실제 수집 데이터로 반복 보정하는 편이 낫다
- `jam-web/src/app/api/admin/poi/review` 등 검토 큐 API 라우트 신설 — 목록 조회(카테고리·수집일
  필터), 승인/카테고리 변경 후 승인/거부 액션, 다중선택 일괄 처리
- 거부된 POI 처리 방식 결정 필요 — 즉시 삭제 vs `unassigned` 카테고리로 이관 후 보관
  (재현 데이터로 판정 기준 보정에 쓸 수 있으므로 후자를 권장)

### UI/UX 관점
- 어드민 화면 `/admin/poi/review` 신설
  - 목록 항목: 이름 / **네이버 원본 분류**(판단 근거로 가장 중요) / 배정 카테고리 / 수집
    키워드 / 좌표 / 수집일
  - 액션: 승인 · 카테고리 바꿔서 승인 · 거부
  - 다중선택 일괄 처리 (진행 중인 어드민 다중선택 일괄삭제 패턴 재사용 검토)
  - 필터: 카테고리별, 수집일자별
  - shadcn/ui 컴포넌트 사용 (프로젝트 어드민 UI 표준)

### 주요 의사결정 / 핵심 메모
> 개발 과정에서 검토·결정된 사항, 선택하지 않은 대안과 그 이유.

- 검토 큐 없이 게이트만 두는 안, 게이트 없이 검토 큐만 두는 안 모두 기각 — 전자는 애매한
  케이스를 놓치고, 후자는 큐가 유저 수 증가에 비례해 무한정 쌓여 검토자 1명으로 감당 불가
  (실측: 오염률 87.5% 카테고리를 게이트 없이 전부 사람이 보게 하면 검토 부담 8배)
- 승인 전 POI 노출 정책은 "게이트 통과분 즉시 노출, 애매한 것만 대기"로 결정 — 승인 전
  전면 비노출은 신규 지역 첫 유저에게 빈 지도를 보여주는 문제가 있어 기각
- **`poi.pending_review` 컬럼 추가(상단 요구사항 목록에는 없던 항목)**: "검토 대기 상태로
  표시"를 문자 그대로 구현하려면 POI별로 "아직 큐에 남아있는지"를 저장할 수단이 필수다.
  `naver_category`/카테고리 재대조만으로는 판정 함수를 매번 다시 돌려도 관리자가 이미 승인한
  건이 계속 pending으로 재등장한다(승인해도 naver_category·category 조합 자체는 그대로라
  결정 이력을 어딘가에 저장해야 함). boolean 하나로 충분(거부 이력은 category='unassigned'로
  이미 구분되므로 별도 enum 불필요)
- **`poi.naver_keyword` 컬럼 추가(상단 요구사항 목록에는 없던 항목)**: UI 요구사항이 명시적으로
  "수집 키워드"를 목록 컬럼에 포함하라고 지시했는데, 이 정보는 카테고리당 키워드가 여럿일 때
  어느 키워드가 오염을 유발했는지 구분하는 유일한 근거라 파생/생략이 불가능해 함께 추가
- **`display_on_map` 미구현**: "노출 여부는 카테고리의 `display_on_map`을 따름" 요구사항 문장이
  참조하는 이 필드는 코드베이스 어디에도 없다(전수 검색 확인). 대신 바로 아래 의사결정
  ("게이트 통과분 즉시 노출, 애매한 것만 대기" — 즉 대기도 노출됨, 전면 비노출 기각)과 결합해
  해석하면 요지는 "노출 여부가 게이트 상태에 좌우되지 않는다"는 것이므로, 신규 컬럼 없이
  기존 `is_active`를 그대로 사용해 승인/대기 모두 `is_active=true`로 저장하는 것으로 그 의도를
  충족했다. `display_on_map` 자체를 신설하는 건 명시된 스키마 변경 범위 밖이라 보류
- 거부 처리: `unassigned` 카테고리로 이관 + `is_active=false`(요구사항의 "보관" 지시 + 실사용상
  잘못 분류된 채 지도에 남는 걸 막기 위한 판단 — unassigned는 사용자 대상 실제 카테고리가
  아니므로). 하드 삭제가 아니므로 `/admin/poi/[id]`에서 언제든 되돌릴 수 있음
- 행 단건 승인/거부는 확인 다이얼로그 없이 즉시 실행(`PoiActiveToggleButton`과 동일 원칙 —
  되돌릴 수 있는 상태 변경이라 삭제와 다르게 취급). 다중선택 일괄 액션만 확인 다이얼로그(한
  클릭이 여러 행에 영향을 주므로) — "카테고리 변경 후 승인"은 카테고리 선택 자체가 확인 단계를
  겸해 단건·일괄 공통으로 다이얼로그 사용
- `requires_review`는 파이프라인 미연동(수동등록 전용) 카테고리에는 자동수집 자체가 없어
  무의미 — `CategoryManager.tsx`에서 `pipeline_linked=true`일 때만 토글 노출
- **`npm run db:types` 미실행으로 인한 타입 우회**: DB 마이그레이션 미실행 상태라 생성 타입
  (`database.generated.ts`)이 이번에 추가한 4개 컬럼을 모르는 상태다. `.insert()`/`.update()`는
  초과 속성을 `never`로 막고, `.select()`는 미인식 컬럼을 `SelectQueryError`로, `.eq()`는 컬럼명
  리터럴 자체를 거부해 전방위 컴파일 오류가 났다. `jam-web/CLAUDE.md`가 명시한 "전체 캐스팅
  금지, 좁은 단위로" 원칙에 따라 호출부별로 최소 범위 우회: `.insert()`/`.update()`는 빌더를
  실제 사용 컬럼만 있는 최소 인터페이스로 캐스팅(`lib/engine-log/index.ts` 기존 패턴 재사용,
  다른 컬럼명 검사는 그대로 유지), `.select()` 결과는 `as unknown as`로 경유, `.eq()` 컬럼명은
  `as string`으로 개별 우회. 결과적으로 `npx tsc --noEmit` 전체 통과 확인(0 errors) — db:types
  재생성 전까지 임시 우회이며, 재생성 후에는 정리 검토 권장(잔여 이슈 참고)

### 잔여 이슈
- `database.generated.ts`가 이번 마이그레이션(143)의 4개 컬럼을 아직 반영하지 못함 — 마이그레이션
  실행 후 `supabase` CLI가 있는 환경에서 `npm run db:types` 재생성 필요. 재생성 후에는 이번에
