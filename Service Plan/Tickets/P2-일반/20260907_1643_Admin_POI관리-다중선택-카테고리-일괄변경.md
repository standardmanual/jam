# [Admin] POI 관리 목록에 다중선택 카테고리 일괄변경 추가

## 배경 / 문제 정의
`/admin/poi` 목록(`PoiTable.tsx`)에는 이미 다중선택(`rowSelection`) + `DataTableBulkActionBar`
+ 일괄 삭제(`handleBulkDelete`)·일괄 활성화/비활성화(`handleBulkSetActive`)가 구현돼
있다([20260830_1619](20260830_1619_Admin_POI관리-활성비활성-및-일괄처리-기능-추가.md)). 카테고리
변경만 아직 단건 수정 폼(`PoiForm.tsx`)에서 POI 하나씩 열어야 한다.

마침 [20260907_1243 카테고리 재정리](20260907_1243_Infra_POI-카테고리체계-재정리-및-기존POI재분류.md)
직후라 재분류 스크립트가 놓친 잔여 POI(네이버 API 레이트리밋으로 스킵된 건 등)를 어드민에서
직접 여러 개 골라 한 번에 재배정할 수요가 바로 있다.

### 코드 조사 메모 (오케스트레이터 사전 조사)
- **일괄 처리 기존 패턴**: `PoiTable.tsx`의 `handleBulkSetActive`(238행 부근)가 정확한 참고
  대상이다 — `selectedIds`를 순회하며 단건 PATCH API를 순차 호출하는 구조. 신규
  `handleBulkSetCategory`도 동일 구조로 만든다(전용 bulk 엔드포인트를 새로 만들지 않는다 —
  `/admin/poi/review/bulk`처럼 검토 큐 전용 로직과 이 목록의 단순 카테고리 변경은 성격이 달라
  같은 엔드포인트를 억지로 공유할 필요 없음).
- **단건 PATCH 핸들러가 `category`를 안 받는다**: `app/api/admin/poi/[id]/route.ts`의 PATCH는
  현재 `{ is_active: boolean }`만 받고 그 외 필드는 무시한다(42~57행). `{ category?: string }`을
  추가로 받아 `category`가 오면 `poi_categories`에 존재하는 슬러그인지 검증 후 갱신하도록 확장한다.
- **반경(radius_meters) 재계산 필수**: PUT(전체수정) 핸들러는 카테고리 변경 시
  `resolvePoiRadiusMeters(category, radius_meters)`로 반경을 재계산한다(20행). PATCH로
  카테고리만 바꿀 때도 **반드시 같은 재계산을 적용해야 한다** — 안 하면 예: 일반 카테고리에서
  `train_subway`로 옮긴 POI가 기존 500m 반경 그대로 남아 [[20260811_006]] 오탐 버그가
  재발한다. `lib/poi/radius-policy.ts`의 `resolvePoiRadiusMeters` 재사용.
- **카테고리 선택 UI 참고**: `PoiForm.tsx`(218행)의 `<Select value={category}
  onValueChange={...}>` — shadcn Select, `categories` prop(`PoiCategoryRow[]`)을 옵션으로
  렌더링. 다중선택 카테고리 변경 다이얼로그도 동일한 Select를 재사용한다(신규 공용 컴포넌트로
  뽑을지는 구현자 판단 — 폼 하나만 더 있는 수준이라 강제하지 않음).
- **`categories` 데이터가 `PoiTable`에 아직 전달되지 않음**: `page.tsx`(47~68행)가 이미
  `poi_categories` 전체를 로드해 `PoiFilters`에는 넘기고 있으나(98행) `PoiTable`에는 안
  넘긴다. `PoiTable` props에 `categories: PoiCategoryRow[]` 추가 필요(새 fetch 불필요, 있는
  데이터를 한 단계 더 넘기기만 하면 됨).
- **확인 다이얼로그 필요**: 카테고리 변경은 되돌릴 수 있는 동작이지만(재변경 가능), 여러 건에
  한꺼번에 적용되고 실수 시 데이터 정합성에 혼란을 주므로(반경 재계산까지 연쇄) 기존 "선택 항목
  삭제"와 동일하게 **확인 다이얼로그를 거친다**(활성화/비활성화처럼 확인 없이 즉시 실행하지
  않는다) — 다이얼로그 안에 카테고리 Select를 넣어 "어느 카테고리로 바꿀지"까지 그 안에서 고르게
  한다.
- **참고, 이번 범위 아님**: `PoiForm.tsx:33`의 `categories[0]?.slug ?? 'other'` 폴백이 삭제된
  `other` 카테고리를 여전히 참조한다([20260907_1243 게이트 리뷰](20260907_1243_Infra_POI-카테고리체계-재정리-및-기존POI재분류.md)에서
  이미 발견, 낮은 위험으로 범위 밖 처리됨 — `categories` 배열이 항상 채워져 있어 실질적으로
  도달하지 않는 코드). 이번 티켓에서 같은 파일을 만지게 되면 `'other'` → `'unassigned'` 정도로
  간단히 고쳐도 되지만 필수는 아니다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `app/api/admin/poi/[id]/route.ts` PATCH 핸들러가 `{ category?: string }`도 받도록 확장.
  `category`가 오면: (1) `poi_categories`에 존재하는 슬러그인지 검증(없으면 400), (2)
  `radius_meters`를 `resolvePoiRadiusMeters(category, 기존radius_meters)`로 재계산해 함께
  UPDATE. `is_active`와 `category` 중 하나만 와도, 둘 다 와도 동작해야 한다(둘 다 optional).
- `page.tsx`: `<PoiTable>`에 `categories` prop 전달.
- `PoiTable.tsx`: `handleBulkSetCategory(newSlug: string)` 추가 — `selectedIds`를 순회하며
  확장된 PATCH를 순차 호출(기존 `handleBulkSetActive`와 동일 구조: 실패 건은 skip하고 계속
  진행, 완료 후 목록 refresh).
- 신규 상태: 카테고리 선택 다이얼로그의 선택값(`useState`), 로딩 상태는 기존 `bulkLoading`
  재사용.

### UI/UX 관점
- `DataTableBulkActionBar`에 "카테고리 일괄 변경" 버튼 추가(기존 "활성화"/"비활성화"/"삭제"
  버튼과 나란히).
- 클릭 시 확인 다이얼로그(AlertDialog 또는 Dialog) 오픈 — 안에 카테고리 Select 하나 + "변경"/
  "취소" 버튼. 문구는 "선택한 {N}개 POI의 카테고리를 변경합니다"류로 기존 삭제 확인 문구
  톤(해요체 아님, 어드민 담백 톤)을 따른다.
- 변경 완료 후 토스트 또는 기존 방식(목록 refresh로 갈음하는지 확인 — `handleBulkDelete`가
  완료 후 어떻게 사용자에게 알리는지 동일 패턴 따름).

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- `app/api/admin/poi/[id]/route.ts`의 PATCH 핸들러를 확장해 `category`도 받도록 했다.
  `category`가 오면 (1) `poi_categories`에 `.maybeSingle()`로 존재 여부를 검증(없으면 400),
  (2) 이 POI의 기존 `radius_meters`를 먼저 조회해 `resolvePoiRadiusMeters(category,
  기존값)`으로 재계산 후 `category`와 함께 UPDATE한다. `is_active`/`category`는 각각
  optional이며 최소 하나는 있어야 한다(둘 다 없으면 400, 타입이 맞지 않아도 400).
- `page.tsx` → `PoiList.tsx` → `PoiTable.tsx`로 이미 로드돼 있던 `categories`
  (`PoiCategoryRow[]`)를 한 단계씩 그대로 전달했다(신규 fetch 없음). `page.tsx`는
  `PoiTable`을 직접 렌더링하지 않고 `PoiList`를 거치므로, `PoiList`의 props에도
  `categories`를 추가해 중계했다(모바일 카드 뷰 `PoiCard`에는 다중선택 자체가 없어 전달
  불필요).
- `PoiTable.tsx`에 `handleBulkSetCategory(newSlug: string)`를 추가했다 —
  `handleBulkSetActive`와 동일하게 `selectedIds`를 순회하며 확장된 PATCH를 순차 호출하고,
  실패 건은 skip, 완료 후 `router.refresh()` + 선택 해제.
- `DataTableBulkActionBar`에 "선택 항목 카테고리 변경" 버튼을 기존 활성화/비활성화/삭제
  버튼과 나란히 추가했다. 클릭 시 shadcn `Dialog` + 카테고리 `Select`가 열리고, "변경"
  버튼은 카테고리를 고르기 전까지 비활성 상태다 — 카테고리 선택 자체가 확인 단계를 겸한다.

### 주요 의사결정 / 핵심 메모
> 개발 과정에서 검토·결정된 사항, 선택하지 않은 대안과 그 이유.

- 확인 다이얼로그는 `AlertDialog`가 아닌 `Dialog`를 선택했다 — 같은 POI 관리 영역인
  `PoiReviewTable.tsx`(티켓 20260907_1242)가 "카테고리 Select + 확인" 조합에 이미 `Dialog`를
  쓰고 있어(카테고리 변경 후 승인) 그 선례를 그대로 따랐다. 티켓 본문이 AlertDialog/Dialog
  둘 다 허용했고, Radix Select를 내부에 넣는 조합은 이 코드베이스에서 이미 검증된 조합이다.
- 카테고리 옵션 목록에서 `unassigned`(거부된 POI 홀딩 카테고리)를 필터링하지 않았다 — 단건
  수정 폼(`PoiForm.tsx`)도 필터링하지 않으므로 일괄 변경도 동일하게 동작해야 한다고 판단했다
  (검토 큐의 `PoiReviewTable.tsx`는 "승인" 맥락이라 `unassigned`를 제외하는 것이 맞지만,
  이 목록은 이미 노출 중인 POI를 다루므로 성격이 다르다).
- 일괄 실패 알림은 여전히 네이티브 `alert()`를 썼다 — 같은 파일의 기존 `handleBulkDelete`/
  `handleBulkSetActive`와 동일한 패턴이며, shadcn toast로의 전환은 별도 티켓(20260907_1219,
  OPEN 상태)의 명시적 범위라 이번 티켓에서 선점하지 않았다.
- 버튼 레이블은 티켓 원문의 예시 문구("카테고리 일괄 변경") 대신 "선택 항목 카테고리
  변경"으로 붙였다 — 같은 액션 바의 기존 3개 버튼("선택 항목 활성화/비활성화/삭제")과
  접두사를 통일하기 위한 판단이다. 다이얼로그 제목은 "POI 카테고리 일괄 변경"으로 붙여
  기존 "POI 일괄 삭제" 제목 패턴과 짝을 맞췄다.
- PATCH 핸들러에서 category 변경 시 반경 재계산 기준값을 얻기 위해 POI를 한 번 추가 조회한다
  (`SELECT radius_meters ... maybeSingle()`). 요청 바디에 기존 반경이 없어서, 조회하지 않고
  `resolvePoiRadiusMeters(category, undefined)`를 호출하면 정확 매칭 정책이 없는 카테고리로
  옮길 때 커스텀 반경이 기본값(500m)으로 조용히 초기화되는 회귀가 생긴다 — 그래서 조회를
  생략하지 않았다.
