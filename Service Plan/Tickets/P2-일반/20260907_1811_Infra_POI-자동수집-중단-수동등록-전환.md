# [Infra] POI 자동수집 중단 및 수동등록 전환

## 배경 / 문제 정의

sihyunrr@gmail.com 계정이 드랍메뉴 접근 시 주변에 편의점이 실제로 많은데도 POI가 거의
등록되지 않는다는 문의로 시작된 대화형 진단에서, T2(네이버 지역검색 기반 자동수집) 파이프라인
전반의 구조적 한계가 다수 실측 확인됐다.

### 1) 네이버 지역검색 API의 근본 한계 (반경/밀도 문제)

`openapi.naver.com/v1/search/local.json`([naver.ts](../../../jam-web/src/lib/poi/naver.ts))은
좌표·반경 파라미터를 지원하지 않고 `"{지역명} {키워드}"` 텍스트 검색만 가능하며, 결과도
`display=5`·관련도(인기도) 순이라 실제 최근접 매장이 반경 500m(`NAVER_RADIUS_M`,
[drops/route.ts:20](../../../jam-web/src/app/api/drops/route.ts)) 안에 들 확률이 낮다.

**실측(서초구 서초중앙로 85 인근, 37.4894/127.0141, 2026-09-07)**:
- "서초1동 편의점" 검색 결과 5개 전부 진짜 편의점(GS25/CU/세븐일레븐)이었으나 전부
  501m~1626m로 500m 밖 — 0/5 통과
- 지역명 접두어를 제거하면 더 악화(서울 중구 등 9km 밖 결과 반환). "구" 단위로 넓혀도 악화
  (동 단위보다 결과가 더 멀어짐)
- 브랜드명(GS25/CU/세븐일레븐/이마트24)으로 키워드를 세분화하면 개선됨: 포괄어 "편의점"은
  0/5 통과였던 반면, 브랜드명 4종 합산 3/20 통과(GS25 178m, 이마트24 169m·405m) — 개선
  여지는 있으나 근본 해결은 아님

### 2) 검증 게이트가 서비스 전역에서 사실상 꺼져 있음

카테고리 검증 게이트([category-gate.ts](../../../jam-web/src/lib/poi/category-gate.ts),
오늘 [20260907_1242](20260907_1242_Infra_POI-네이버원본분류검증게이트및-어드민검토큐.md)로
신설)가 현재 파이프라인 연동 10개 카테고리(government/convenience/nature/
tourist_attraction/stadium/school/park/hospital/pharmacy/food) **전부 `requires_review=false`**
상태임을 DB 실측(`poi_categories` 조회)으로 확인했다. 게이트는 설계·구현됐지만 실제로는 어느
카테고리에도 적용되지 않고 있었다.

### 3) 포괄 명사 키워드의 명칭 오염 — 실측/DB 확인 다수

한 단어짜리 포괄 키워드는 그 글자가 무관한 상호명에 섞여 있기만 해도 걸린다.

| 카테고리 | 키워드 | 오염 사례 | 확인 방식 |
|---|---|---|---|
| government | 시청 | 5건 중 4건 완전 무관(파티룸/기업정보/건축설계/음향가전), 유일한 진짜(과천시청)도 관할 밖 | 실측 |
| nature | 국립공원 | 5건 전부 무관(어린이집/도서관/과학관 부속시설) | 실측 |
| tourist_attraction | 전망대 | 떡볶이집("이태원떡볶이전망대") 등 이름 낚시 다수, 진짜는 8km 밖 | 실측 |
| tourist_attraction | 미술관 | 사진 셀프스튜디오("그날의미술관") | 실측 |

| park | 공원 | 일식 우동집("코시 교대점")이 공원으로 저장됨 | **실제 DB 확인** |

### 4) 대안 검토 결과 — 좌표 기반 서드파티 API 전무

- **NCP Maps** 전 제품군(Geocoding/Reverse Geocoding/Directions/Static·Dynamic Map)에
  좌표+반경 기반 장소검색 없음. 과거 Place API가 있었으나 단종됨(공식 문서·실측 모두 확인).
  Geocoding API는 `coordinate` 파라미터로 근접순 정렬을 지원한다고 문서에 나오지만, 실제로
  "편의점"/"마트"/"가산빌딩" 등 업종·건물 키워드를 넣어 호출하면 전부 0건 — 구조화된 주소
  문자열 전용이라 확인됨
- **카카오 로컬 API**(`category.json`)는 기술적으로 완벽하다(x,y,radius 최대 20km,
  `category_group_code` CS2=편의점/MT1=대형마트, `sort=distance`). 그러나 카카오 이용정책상
  검색결과(장소명·주소·좌표 등) 원본의 자체 DB 영구저장이 금지되고 장소ID+URL만 허용된다
  (카카오 개발자 포럼 공식 답변 확인). JAM!의 `poi` 테이블은 체크인 배지 GPS 매칭
  (`matchPoisForActivity`)·배지명 표시(POI명 그대로 사용, `BADGE_ENGINE_UNIFIED.md` §3.16)에
  영구 저장 데이터를 계속 재사용하는 구조라 정면 충돌
- "장소ID만 저장 후 실시간 재조회"안도 검토했으나, 카카오에 ID 단건조회 공식 엔드포인트
  자체가 없어 기술적으로 불가능함을 확인(비공식 `place.map.kakao.com` 내부 엔드포인트뿐).
  실시간화를 강행할 경우 GET /api/drops 응답 지연 증가(기존 티켓 20260820_022가 이미 해결한
  "네이버 검색 최대 13초+ 블로킹" 문제를 역행), Strava 동기화 배치의 외부 API 호출량 폭증,
  이미 발급된 배지를 포함한 배지 상세 페이지의 장소명 표시 불가 등 부작용이 확인돼 기각

## 상세 요구사항

점진적 개선(게이트 5개 카테고리 켜기, 편의점 키워드 브랜드명 교체)도 검토했으나, 사용자가
더 큰 구조 변경으로 최종 결정했다.

### 서비스/코드베이스 관점

1. **자동수집 전면 중단**: `poi_categories.pipeline_linked`를 연동된 10개 카테고리
   (government/convenience/nature/tourist_attraction/stadium/school/park/hospital/
   pharmacy/food) 전부 `false`로 전환. 순수 데이터 변경(스키마·코드 변경 없음). 코드
   (`naver.ts`/`category-gate.ts`/`search-cache.ts`, `drops/route.ts`의
   `searchAndPersistCategories`·`refreshPoisInBackground`)는 삭제하지 않고 그대로 남겨
   나중에 재사용 가능하게 한다.

2. **기존 자동수집 POI는 변경 없음**: `poi_tier=2`(오늘 599건 재분류 결과 hospital 239·
   unassigned 215·food 37·convenience 36·park 31·government 7·nature 7·
   tourist_attraction 6·pharmacy 3, 합계 581) 및 mountain(847)·train_subway(967)는
   지금 상태(활성/비활성) 그대로 유지한다. 검토 큐로 옮기거나 일괄 비활성화하지 않는다.
   (mountain·train_subway는 애초에 네이버 키워드 검색이 아니라 별도 공공데이터 스크립트로
   등록된 신뢰 데이터라 이번 오염 문제와 무관.)

3. **앞으로 신규 POI는 전부 수동등록**하되, "임시등록(비활성/검토대기) → 사용자가 이름·
   카테고리·좌표·반경 등 최종 정보 확인·수정 → 저장 → 명시적으로 활성화" 흐름을 적용한다.
   오늘 [20260907_1242](20260907_1242_Infra_POI-네이버원본분류검증게이트및-어드민검토큐.md)로
   만든 검토 큐 화면(`/admin/poi/review`, `pending_review` 플래그)을 재사용하되, 그 화면은
   현재 "승인·카테고리 변경 후 승인·거부"만 지원하고 이름/좌표 수정은 별도 화면
   (`/admin/poi/[id]`)에 있어 — 검토 큐에서 개별 항목을 편집 화면으로 연결하거나 검토 큐
   자체에 편집 기능을 넣는 통합 작업이 필요하다.

### UI/UX 관점

- `/admin/poi/new`(신규 등록 폼)의 기본 저장 상태를 비활성/검토대기로 바꿀지, 아니면 별도
  "임시저장" 액션을 추가할지는 구현 단계에서 결정
- 검토 큐(`/admin/poi/review`) ↔ 편집 화면(`/admin/poi/[id]`) 연결 방식(리다이렉트 vs
  검토 큐 자체에 편집 필드 추가)도 구현 단계에서 결정

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- `poi_categories.pipeline_linked` 10개 카테고리 false 전환은 SQL 파일만 작성(실행 안 함) —
  `jam-web/supabase/seed_20260907_poi_pipeline_linked_off.sql`. 사용자 승인 후
  오케스트레이터가 직접 Supabase에 반영해야 실제로 자동수집이 꺼진다.
- `/admin/poi/new`(신규 등록)에서 저장하면 클라이언트 입력과 무관하게 서버(`POST
  /api/admin/poi`)가 항상 `is_active=false, pending_review=true`(임시등록)로 강제 저장하도록
  변경. 폼에서도 활성화 토글을 숨기고 "임시등록(비활성·검토대기)으로 저장됩니다" 안내와
  버튼 레이블 "임시등록"으로 교체.
- `/admin/poi/[id]`(편집 화면, `PUT /api/admin/poi/[id]`)에서 활성화 스위치를 켜고 저장하면
  `is_active=true`와 함께 `pending_review=false`도 서버가 자동으로 함께 내려 "확인·수정 →
  저장 → 명시적 활성화"를 한 번의 저장 액션으로 완결시킴. 비활성 상태로 저장할 때는 기존
  `pending_review` 값을 건드리지 않음(이미 검토 완료된 일반 POI를 잠시 끄는 것과 아직 검토
  전인 임시등록을 구분).
- 검토 큐(`/admin/poi/review`) ↔ 편집 화면(`/admin/poi/[id]`) 통합: 검토 큐 테이블의
  "이름" 열이 이미 `/admin/poi/[id]`로 링크돼 있어(기존 구현, 20260907_1242) 별도 라우팅
  추가 없이 그대로 연결 지점으로 채택. 대신 검토 큐 테이블에 "노출"(is_active) 열을 추가해
  "승인" 버튼이 노출 여부를 바꾸지 않는다는 점을 화면에서 바로 확인할 수 있게 함. 검토 큐
  상단 안내문·`PoiDetail`(상세 카드) "검토대기" 배지·`/admin/poi/new` 안내문도 함께 갱신.
- `Service Plan/Specs/Content/POI.md`에 "신규 등록 정책" 절 신설 — 자동수집 중단 사유
  요약, 기존 자동수집 POI 유지 방침, 신규 수동등록 흐름(임시등록→검토→활성화) 기술.
- 요청받은 대로 `naver.ts`/`category-gate.ts`/`search-cache.ts`, `drops/route.ts`의
  `searchAndPersistCategories`·`refreshPoisInBackground`는 그대로 남겨둠(삭제 없음).
