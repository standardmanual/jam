# [Admin] 배지 조건 사전 시뮬레이션에 가상 활동 입력 연결

## 배경 / 문제 정의
> 왜 이 작업이 필요한가. 현재 상태와 기대 상태의 차이.

티켓 [20260908_1554](20260908_1554_Admin_배지미션-조건-사전시뮬레이션.md)로 배지 조건 저장 전
시뮬레이션(`/api/admin/badges/simulate-condition`)을 구현했다. 1차 범위는 **기존 유저의 실제
활동 이력**에 조건을 대입하는 방식만 지원한다.

이 방식은 반복형·기간형 조건처럼 오랜 이력이 쌓여야 드러나는 문제를 검증하기에는 실전적이지만,
다음 상황에서는 한계가 있다.

- 신규 배지가 겨냥하는 활동 패턴(예: 특정 거리·페이스·시간대 조합)을 가진 유저가 아직 없을 때
  검증할 방법이 없다.
- 극단값(예: 조건 임계값 바로 위/아래)을 의도적으로 넣어 경계 조건을 확인하고 싶을 때, 그런
  활동을 가진 유저를 찾아야 하는 우회가 필요하다.

`/admin/simulator`에는 이미 가상 활동 입력 UI(GPX 업로드 또는 수치 직접입력)가 있고, 같은
`evaluateConditionDetailed`/`evaluateBadgesDetailed` 계열 함수를 dry-run으로 호출하는 패턴도
이미 검증돼 있다. 새로 만들 필요 없이 그 입력 폼을 배지 생성 화면의 시뮬레이션 패널에 재사용
연결하면 된다.

근거: `Service Plan/Specs/PRD/AdminUI/CONDITION_PRECHECK_PRD.md` §8 2차 범위,
티켓 `20260908_1554` 완료 기록의 잔여 이슈.

## 상세 요구사항

### 서비스/코드베이스 관점
- `/admin/simulator`가 가상 GPX·수치 활동을 만드는 로직(파일 위치 확인 필요)을 그대로 재사용해,
  `simulate-condition` API가 `userId` 대신 가상 활동 배열을 직접 받는 경로를 추가한다.
  기존 유저 방식과 가상 활동 방식을 같은 API 안에서 요청 바디로 분기하거나, 필요하면 별도
  파라미터로 구분한다.
- 가상 활동은 `NormalizedActivity` 형태와 동일해야 `evaluateConditionDetailed`에 그대로 넘길 수
  있다 — 형 변환 지점을 시뮬레이터 코드에서 그대로 가져온다.

### UI/UX 관점 (해당 시)
- 배지 생성/수정 폼의 "판정 시뮬레이션" 패널에 대상 선택 방식을 2종으로 확장한다: 기존 유저 검색
  (현재 구현됨) / 가상 활동 입력(신규, 시뮬레이터 폼 재사용).
- 가상 활동 입력 UI는 기존 시뮬레이터 화면의 컴포넌트를 그대로 재사용하고, 새로 디자인하지 않는다.

### 컨텐츠 관점 (해당 시)
- 해당 없음.

## 구현 계획
> 어떻게 구현할지. 접근 방법, 영향 범위, 주요 변경 포인트.

1. `/admin/simulator` 관련 코드(가상 활동 생성 폼·API)를 먼저 읽어 재사용 가능한 컴포넌트/함수
   단위를 파악한다.
2. `simulate-condition` API에 가상 활동 입력 경로를 추가한다(기존 유저 경로는 그대로 유지).
3. `BadgeForm.tsx` 시뮬레이션 패널에 입력 방식 전환 UI를 추가한다.
4. 극단값(임계값 경계) 시나리오로 검증한다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
`/admin/simulator`의 GPX 파싱·가상 활동 변환 로직을 공용 모듈로 뽑아 배지 조건 사전
시뮬레이션(`simulate-condition`)의 "가상 활동으로 시험" 경로에 그대로 재사용했다.

- `lib/admin/gpxParse.ts`: `/admin/simulator/page.tsx`에 있던 `parseGpx`·`downsampleRoute`·
  `formatDuration` 등 순수 함수를 그대로 옮겼다(로직 변경 없음).
- `lib/admin/virtualActivity.ts`: `/api/admin/simulate`가 가상 활동을 `NormalizedActivity[]`로
  바꾸던 변환 로직(`readExtendedFields`, 반복 회차 생성)을 옮겼다. `/api/admin/simulate`와
  `/api/admin/badges/simulate-condition`이 이제 같은 함수를 공유한다.
- `components/admin/VirtualActivityForm.tsx`: GPX 업로드 또는 수치 직접입력(거리·시간·고도·
  시작시각)으로 가상 활동을 만드는 공용 폼. 활동 종류·반복 횟수·v5 확장 6필드 입력도 포함하며,
  완성된 값을 `onActivityChange` 콜백으로만 상위에 전달한다(값을 직접 들고 있지 않음). 시뮬레이터
  페이지와 배지 폼 양쪽에서 재사용한다.
- `/admin/simulator/page.tsx`: GPX/활동설정/확장필드 패널을 `VirtualActivityForm`으로 교체.
  대상 유저 선택·결과 표시 로직은 그대로 유지.
- `/api/admin/badges/simulate-condition/route.ts`: 요청 바디에 `userId`(기존) 또는
  `virtualActivity`+`repeatCount`(신규) 중 하나를 받는다. `userId`가 있으면 기존 유저 이력 조회
  경로, 없으면 `buildVirtualActivities`로 만든 가상 이력을 그대로 판정에 대입한다. 가상 경로는
  가입 앵커 개념이 없어 `anchorDate`를 `null`로 응답한다(응답 스키마는 기존과 동일하게 유지).
- `BadgeForm.tsx`: "판정 시뮬레이션" 패널에 "기존 유저로 시험" / "가상 활동으로 시험" 탭을
  추가했다. 가상 활동 탭은 `VirtualActivityForm`을 그대로 렌더링하고, 실행 버튼은 선택한 모드에
  따라 필요한 입력이 채워졌을 때만 활성화된다.

### 주요 의사결정 / 핵심 메모
- `VirtualActivityForm`은 자체 상태를 들고 있고 완성된 값만 콜백으로 올려보내는 구조를 택했다.
  BadgeForm과 simulator 페이지가 서로 다른 방식으로 값을 쓰기 때문에(하나는 즉시 POST, 하나는
  버튼 클릭 시 POST) "제어 컴포넌트로 만들어 부모가 값을 들고 있는" 대신 "완성 시에만 알림" 방식이
  두 소비처 모두에 더 단순했다.
- `simulate-condition` API는 `userId` 아니면 `virtualActivity` 중 정확히 하나만 받는 구조로
  분기했다(별도 `target.type` 래퍼를 두지 않음) — 티켓 본문이 "필요하면 별도 파라미터로 구분"을
  허용했고, 기존 `userId` 단일 필드 계약을 그대로 유지하는 쪽이 기존 소비처(BadgeForm의 유저 경로)
  변경을 없앤다.
- `/api/admin/simulate`(가상 활동 → 실제 배지 발급 시뮬레이션)도 같은 `buildVirtualActivities`로
  리팩터했다. 티켓 범위는 `simulate-condition`이지만, "형 변환 지점을 시뮬레이터 코드에서 그대로
  가져온다"는 요구사항을 지키려면 원본 로직을 옮기는 것이 유일한 선택지였고, 옮기는 김에 원래
  호출부도 새 함수를 쓰도록 정리해 로직이 두 곳에 따로 존재하는 상태를 피했다.
- **머지 시점 충돌 조정**: 이 티켓(1631)과 20260908_1632가 같은 origin/staging 시점에서 독립
  분기해 `BadgeForm.tsx`·`simulate-condition/route.ts`를 각자 다르게 고치면서 머지 충돌이 났다.
  jam-developer에게 별도 조정 작업을 맡겨, 이 티켓의 `simulate-condition` 로직(`userId`/
  `virtualActivity` 두 경로)이 1632가 만든 공용 헬퍼 `lib/admin/conditionSimulation.ts`의
  `simulateCondition(condition, target, extraAllowedKeys?)`로 흡수됐다. 기능은 그대로 보존됐고,
  게이트 리뷰(conservative-reviewer)가 조정 결과를 diff로 재검증해 PASS 판정했다.
