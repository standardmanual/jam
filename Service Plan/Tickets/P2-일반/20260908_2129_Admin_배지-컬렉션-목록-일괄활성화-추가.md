# [Admin] 배지·컬렉션 관리 목록에 일괄 활성화 기능을 추가한다

## 배경 / 문제 정의

사용자 요청 원문:
1. 배지 관리 메뉴 — 목록에서 다중 선택 시 "선택 항목 활성화" 버튼 제공
2. 컬렉션 관리 메뉴 — 컬렉션 활성화 시 소속된 아이템 배지도 모두 활성화 함

오케스트레이터 사전 조사(Explore 에이전트) 결과:

- **배지 관리** (`src/app/admin/badges/`, `BadgesTable.tsx`): 이미 체크박스 다중 선택
  UI(`RowSelectionState`)와 `DataTableBulkActionBar`가 있고, "선택 항목 비활성화"
  (`handleBulkDeactivate`, 순차 PATCH)·"선택 항목 삭제" 버튼만 있다. **"일괄 활성화"
  버튼만 대칭적으로 빠져 있다.** 활성화 개념은 `is_active` 컬럼이 아니라 `deleted_at`
  soft-delete다 — 개별 활성화 API(`/api/admin/badges/[id]` PATCH, `active:true` →
  `deleted_at=null`)는 이미 존재한다.
- **컬렉션 관리** = UI 문구일 뿐 실제로는 아이템북(`itembooks`/`item_books` 테이블,
  `src/app/admin/itembooks/`). 마찬가지로 다중 선택 UI·"일괄 비활성화" 버튼은 있고
  **"일괄 활성화" 버튼만 빠져 있다.** 컬렉션은 `is_active` 컬럼을 쓴다.
  - **⚠️ 기존 설계 결정과 충돌**: 개별 활성화 API(`/api/admin/itembooks/[id]` PATCH)는
    `is_active:false`(비활성화)일 때만 `cascadeDeactivateItemBookBadges`로 하위 아이템
    배지를 연쇄 소프트삭제하고, **`is_active:true`(재활성화)는 의도적으로 캐스케이드
    없음** — 코드 주석에 "배지는 건드리지 않는다(기존 설계 결정 유지)"라고 명시돼 있다.
    **이번 사용자 요청("컬렉션 활성화 시 소속 아이템 배지도 모두 활성화")은 이 기존
    결정을 뒤집는 것이다.** 왜 원래 캐스케이드하지 않기로 했는지 히스토리(어느 티켓의
    어느 결정인지)를 구현 전에 추적해, 뒤집어도 안전한지 확인한다 — 단순 누락이 아니라
    의도적 결정이었을 가능성이 있다(예: 컬렉션은 활성화해도 개별 배지는 별도 사유로
    비활성 상태를 유지하고 싶을 수 있다는 관리자 시나리오).
  - 관련 기존 티켓 `20260907_1134`(다중선택 일괄삭제 확장)에도 "다중선택 일괄 액션은
    현재 소프트 비활성화만 지원한다"는 언급이 있다 — 일괄 활성화 자체가 없는 게 우연이
    아니라 의도였을 가능성도 함께 확인한다.

## 상세 요구사항

### 서비스/코드베이스 관점
1. **배지 관리 일괄 활성화**: `BadgesTable.tsx`의 기존 `handleBulkDeactivate` 패턴을
   그대로 복제해 `handleBulkActivate`를 추가하고, `DataTableBulkActionBar`에 "선택 항목
   활성화" 버튼을 대칭 위치에 배치한다. 선택 id를 순회하며 `/api/admin/badges/[id]`
   PATCH `{active: true}`를 순차 호출(기존 비활성화와 동일한 호출 패턴).
2. **컬렉션 일괄 활성화**: `ItemBookTable.tsx`에 동일한 패턴으로 `handleBulkActivate`와
   버튼을 추가한다. `/api/admin/itembooks/[id]` PATCH `{is_active: true}`를 순차 호출.
3. **컬렉션 활성화 → 하위 아이템 배지 연쇄 활성화**: 위 "기존 설계 결정과 충돌" 항목의
   히스토리 확인 결과에 따라 진행 방향을 정한다.
   - 히스토리상 명확한 안전 이유가 없다면: `is_active:true` 처리 시에도
     `cascadeDeactivateItemBookBadges`와 대칭되는 연쇄 활성화 로직(예:
     `cascadeActivateItemBookBadges`)을 `/api/admin/itembooks/[id]` route.ts에 추가한다.
     비활성화 캐스케이드가 "이 컬렉션 소속 배지 중 `deleted_at`이 이 컬렉션 비활성화로
     인해 세팅된 것만" 되돌리는지, 아니면 무조건 전체를 되돌리는지 기존
     `cascadeDeactivateItemBookBadges` 구현을 참고해 대칭적으로 설계한다 — **컬렉션과
     무관한 사유로 이미 비활성화된 배지까지 실수로 되살리지 않도록 주의.**
   - 히스토리상 명확한 안전 이유가 있다면: 구현을 보류하고 사용자에게 그 이유를 보고한
     뒤 재확인을 받는다.
4. 개별 화면(`BadgeActiveToggleButton.tsx`류)의 기존 단건 활성화 동작은 건드리지 않는다
   — 이번 범위는 다중 선택 목록의 일괄 액션뿐이다.
5. 어드민 UI는 shadcn/ui 표준을 따른다(기존 `DataTableBulkActionBar`·`Button` 재사용,
   신규 UI 컴포넌트 불필요).

### UX Writing 관점
- 버튼 레이블은 기존 "선택 항목 비활성화"·"선택 항목 삭제"와 대칭되는 "선택 항목 활성화".
- 컬렉션 쪽에 캐스케이드 활성화를 구현한다면, 확인 다이얼로그(있다면)에 "소속 아이템
  배지 N개도 함께 활성화됩니다" 같은 영향 범위 안내 문구를 넣는다 — 기존 비활성화
  확인 다이얼로그(`ItemBookForm.tsx`의 `deactivation-impact` 미리보기)와 같은 원칙.

## 2차 — 사용자 확정: 캐스케이드 활성화 진행 (2026-09-08)

1차 완료 보고 후 사용자가 "자동 활성화 해"로 명시적으로 확정 — 스키마 변경을 감수하고
캐스케이드 활성화를 구현한다. 3번에서 확인한 "구분 불가" 문제를 **사유 컬럼 추가로
해소**하는 방향이다(오케스트레이터 사전 설계):

### 스키마 변경
`badges` 테이블에 컬럼 추가: `deactivated_by_item_book_id uuid null references item_books(id)`
- 컬렉션 캐스케이드 비활성화가 이 배지를 죽인 것이면 그 컬렉션 id를 기록, 아니면 NULL.
- 마이그레이션 파일: `jam-web/supabase/migrations/146_badges_deactivated_by_item_book.sql`

### 로직 변경
1. **`cascadeDeactivateItemBookBadges`**(`src/lib/admin/itembook-deactivation.ts`):
   `deleted_at` 세팅과 함께 `deactivated_by_item_book_id: itemBookId`도 세팅한다.
2. **신규 `cascadeActivateItemBookBadges`**(같은 파일): `item_book_id = itemBookId`
   **AND** `deactivated_by_item_book_id = itemBookId`인 배지만 골라
   `deleted_at: null, deactivated_by_item_book_id: null`로 되돌린다. 개별 사유로 죽은
   배지(`deactivated_by_item_book_id`가 NULL이거나 다른 컬렉션 id)는 절대 건드리지 않는다
   — 이게 이번 기능의 안전장치 핵심이므로 게이트 리뷰에서 반드시 재확인할 것.
3. **개별 배지 활성화/비활성화 API**(`/api/admin/badges/[id]` PATCH): 개별 조작이 있으면
   "이제 컬렉션 캐스케이드 관리 대상에서 벗어났다"는 뜻이므로, `active` 값에 관계없이
   `deactivated_by_item_book_id`를 NULL로 리셋한다. 이렇게 해야 "컬렉션 비활성화로 죽은
   배지를 관리자가 나중에 개별로 다시 살렸다가, 그 후 컬렉션이 재활성화될 때 또 건드려지는"
   이중 처리를 막는다. 배지 관리 화면의 일괄 활성화/비활성화(다중 선택)도 결국 이 개별 API를
   순차 호출하므로 자동으로 같은 규칙을 따른다.
4. **`/api/admin/itembooks/[id]` PATCH**: `is_active: false→true`(재활성화) 분기에
   `cascadeActivateItemBookBadges`를 호출하도록 추가한다. 기존 "배지는 건드리지 않는다"
   주석은 이번 변경으로 대체되므로 함께 갱신한다.
5. **컬렉션 목록 일괄 활성화**(`ItemBookTable.tsx`의 `handleBulkActivate`, 1차 구현)는
   이미 `/api/admin/itembooks/[id]` PATCH를 순차 호출하는 구조이므로, 4번이 반영되면
   자동으로 캐스케이드가 적용된다 — 이 컴포넌트 자체를 다시 고칠 필요는 없다.

### UX Writing
- 컬렉션 활성화 확인 다이얼로그(있다면)에 "이 컬렉션 비활성화로 함께 내려갔던 아이템
  배지 N개도 다시 활성화됩니다" 같은 영향 범위 안내를 추가한다 — 개별 사유로 비활성화된
  배지는 영향받지 않는다는 점까지 명확히 전달할 것.

### 구현 계획 (2차)
1. 마이그레이션 `146_badges_deactivated_by_item_book.sql` 작성(실행은 SQL 파일 작성까지만
   — DB 실행은 사용자 승인 후 오케스트레이터가 처리)
2. `npm run db:types`로 생성 타입 재생성 — 로컬 CLI 미설치 시 MCP
   `generate_typescript_types`로 대조(project memory 참고)
3. `cascadeDeactivateItemBookBadges` 수정 + `cascadeActivateItemBookBadges` 신규
4. `/api/admin/itembooks/[id]` PATCH에 캐스케이드 활성화 연결, 기존 주석 갱신
5. `/api/admin/badges/[id]` PATCH에 `deactivated_by_item_book_id` 리셋 로직 추가
6. 확인 다이얼로그 문구 갱신(있다면)
7. 로컬 `ADMIN_EMAILS`로 실렌더 검증: 컬렉션 비활성화(캐스케이드 배지 확인) →
   컬렉션 재활성화(그 배지들만 되살아나는지 확인) → 컬렉션 비활성화 후 배지 1개를
   개별로 먼저 활성화 → 컬렉션 재활성화(그 배지는 중복 처리 없이 그대로인지 확인)
   — 이 3번째 시나리오가 안전장치 검증의 핵심이다

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

**1차 — 일괄 활성화 버튼**: `BadgesTable.tsx`·`ItemBookTable.tsx`에 기존 "선택 항목
비활성화"(`handleBulkDeactivate`)와 대칭되는 `handleBulkActivate`를 추가. 선택 id를
순회하며 각각 `/api/admin/badges/[id]` PATCH `{active:true}` 또는
`/api/admin/itembooks/[id]` PATCH `{is_active:true}`를 순차 호출. 확인 다이얼로그 없이
즉시 반영(기존 단건 활성화 버튼과 동일한 UX).

**2차·3차 — 컬렉션 캐스케이드 활성화**: 사용자가 "자동 활성화 해"로 확정. 기존
`cascadeDeactivateItemBookBadges`가 컬렉션 비활성화 시 소속 배지를 연쇄 소프트삭제하는
것과 대칭으로, 재활성화 시에도 "이 컬렉션이 죽인 배지만" 되살리는 캐스케이드를 구현했다.

- `badges` 테이블에 `deactivated_by_item_book_id`(uuid null, `item_books(id)` FK,
  `ON DELETE SET NULL`) 컬럼 신설(마이그레이션 146). 컬렉션 캐스케이드로 죽은 배지는 그
  컬렉션 id를, 개별 사유로 죽었거나 활성 상태면 `NULL`을 가진다.
- `cascadeDeactivateItemBookBadges`가 `deleted_at`과 함께 이 컬럼도 세팅하도록 수정.
- 신규 `cascadeActivateItemBookBadges`: `item_book_id = X AND deactivated_by_item_book_id
  = X`인 배지만 골라 `deleted_at`·`deactivated_by_item_book_id`를 `NULL`로 되돌린다.
- 개별 배지 활성/비활성 API(`/api/admin/badges/[id]` PATCH)는 `active` 값과 무관하게 매
  호출마다 `deactivated_by_item_book_id`를 `NULL`로 리셋 — "개별 관리로 전환됨"을
  표시해 이후 컬렉션 재활성화 때 이중 처리를 막는다.
- `/api/admin/itembooks/[id]` PATCH의 재활성화(`is_active: false→true`) 분기에
  `cascadeActivateItemBookBadges`를 연결. 기존 "배지는 건드리지 않는다" 주석은 이번
  결정으로 대체.
- 1차 구현한 `ItemBookTable.tsx`의 일괄 활성화는 이 PATCH를 그대로 순차 호출하는
  구조라 별도 수정 없이 캐스케이드가 자동 적용됨.
- 3차: 2차에서 `database.ts`의 `BadgeRow`에 신규 컬럼을 필수 필드로 추가하며 깨진
  기존 테스트 픽스처 3개(`badge-engine-v5.test.ts` 등)를 수정 — 이번 티켓과 무관한
  회귀였다.

### 잔여 이슈
- 이 컬럼 신설 **이전**에 이미 컬렉션 캐스케이드로 죽어 있던 과거 배지들은
  `deactivated_by_item_book_id`가 `NULL`이라 신규 캐스케이드 활성화 대상에서 자동으로
  제외된다. 과거 데이터를 백필할지, 이 컬럼 신설 이후 발생 건만 추적 대상으로 삼을지는
  별도 판단이 필요하다 — 운영 중 "재활성화했는데 옛날 배지는 왜 안 살아나지" 문의가
  들어오면 그때 판단.

  드랍(`invalidateUnclaimedDrops`)까지 복구하지는 않는다(정책 미확정 — 필요시 별도 티켓).
