# [Feature] 온보딩 재설계 — 트라이브(세계관) 선택 도입, 지역·운동종목 제거

## 배경 / 문제 정의
현재 온보딩은 `username` 설정 1단계뿐이다. `users.region`, `users.activity_types`는
마이그레이션 001부터 DB에 존재하지만 입력 UI가 한 번도 만들어진 적 없는 죽은
컬럼이고, PRD(`Specs/PRD/01_PRD.md` 41·71행, `02_DATA_MODEL.md` 69-70행)는 여전히
"온보딩에서 활동 종목·지역 선택"을 스펙으로 기술해 문서-구현이 어긋나 있다.

요청 사항:
1. 온보딩에서 아이디·이름·트라이브(트라이브)·프로필이미지를 설정한다 (프로필이미지만
   선택, 나머지 필수).
2. 지역·운동종목 설정 기능(DB 컬럼 포함)을 완전히 제거한다.
3. "세계관"은 운영자 용어이므로 유저 대면 UI에서는 **"트라이브"**로 노출한다.
4. 트라이브는 온보딩에서 한 번 정하면 탈퇴할 때까지 유저가 직접 변경할 수 없다.
   프로필 편집 화면에서는 프로필이미지·아이디·닉네임만 변경 가능하다.
5. 프로필 페이지의 프로필 편집 진입 동선을 변경한다 — 현재 아바타 모서리에 있는
   편집 버튼을 없애고, 포인트 표시 행("OOO 포인트 >")의 우측 끝에 "편집" 버튼을
   새로 노출해 그걸로 프로필 편집 페이지에 진입한다.

`/office-hours`로 진행한 설계 논의 결과를 티켓으로 정리한 문서다.

## 상세 요구사항

### 서비스/코드베이스 관점 (착수 전 재확인된 실제 코드 상태 기준)
- **`users.display_name`은 이미 존재한다** (마이그레이션 `112_users_display_name.sql`,
  `UserRow.display_name`). 자유 텍스트, 최대 30자, 중복확인 없음 — 인스타그램 "이름"
  필드 정책과 이미 동일하게 구현되어 있다. `/api/profile/route.ts`(PATCH)에서 이미
  username·display_name 변경을 지원한다. **신규 컬럼 추가·API 신설이 필요 없다** —
  온보딩 화면에만 이 필드의 입력 단계가 빠져 있을 뿐이다.
- **`users.faction_id`는 존재하지 않는다** — `badges.faction_id`, `item_books.faction_id`
  등 컨텐츠 쪽에만 있고 유저 쪽에는 없다. **신규 컬럼 추가 필요** (FK →
  `factions.id`, nullable로 추가). DB 레벨 NOT NULL 강제는 기존 유저 백필 전까지 보류,
  온보딩 API 레벨에서만 필수 검증한다.
- **프로필 이미지 업로드도 이미 구현되어 있다** (`/api/profile/avatar/route.ts`,
  Supabase Storage `avatars` 버킷). 온보딩에서는 구글 `avatar_url` 기본값을 보여주고
  이 기존 업로드 API를 재사용해 변경 옵션을 제공한다. `avatar_url`이 없으면 서비스
  기본 아바타로 폴백.
- `users.region`, `users.activity_types` 컬럼 삭제. 착수 시
  `grep -rn "region\|activity_types" jam-web/src`로 참조 코드 전수 재확인 후 삭제
  (현재 확인된 참조: `search/page.tsx`, `api/users/search/route.ts`, 어드민 유저 화면).
  드랍엔진의 신규 유저 첫 3드랍 로직(`drop-engine/index.ts`,
  `ONBOARDING_FACTION_BY_ACTIVITY`)은 **정적 매핑 상수의 전체 값을 후보군으로 쓸 뿐
  `users.activity_types`를 직접 참조하지 않으므로 컬럼 삭제로 영향받지 않는다** (착수
  시 재확인).
- `POST /api/onboarding/complete`는 현재 `username`만 받는다 → `display_name`,
  `faction_id`도 함께 받아 검증·저장하도록 확장(신규 컬럼은 `faction_id` 하나뿐).
  이 API는 다음 3가지를 반드시 검증한다 (`/plan-ceo-review`에서 발견):
  1. **`faction_id` 존재+활성 검증**: `SELECT id FROM factions WHERE id=? AND is_active=true`로
     조회해 없으면 400 `INVALID_FACTION`. 온보딩 카드는 활성 트라이브만 보여주지만,
     유저가 화면을 띄운 사이 어드민이 비활성화할 수 있으므로 서버가 다시 검증해야 한다.
  2. **트라이브 불변 강제**: 이미 `faction_id`가 설정된 유저가 이 API를 재호출하면
     (devtools/curl 등으로) 값을 덮어쓸 수 없도록, 기존 `faction_id`가 NULL이 아니면
     409 `ALREADY_SET`으로 거부한다. username 필드의 기존 "이미 있으면" 처리 패턴과
     동일하게 맞춘다. "프로필 편집 API에 엔드포인트를 안 만든다"만으로는 온보딩 API
     자체의 재호출까지 막지 못하므로 별도로 필요하다.
  3. `faction_id` 중복 제출 거부(409)·비활성 트라이브 제출 시도(400)는 각각
     `console.error`로 로깅한다(어뷰징·UI 버그 조기 감지용).
- **온보딩 완료 판정 로직 변경 필요**: `/auth/callback/route.ts`의
  `needsOnboarding = !existingProfile?.username`을
  **`needsOnboarding = !existingProfile?.onboarding_completed_at`**으로 바꾼다.
  `users.onboarding_completed_at`은 이미 존재하는 컬럼이다(`SERVICE_OPERATIONS.md`
  2-3절). 온보딩 완료 API가 **2단계(트라이브 포함)까지 전부 채워졌을 때만**
  `onboarding_completed_at`을 기록하도록 바꾼다.
  - 이렇게 하면 1단계(아이디·이름)만 마치고 이탈한 신규 유저는 이 값이 여전히
    null이라 재로그인 시 온보딩 2단계로 정확히 돌아간다.
  - **기존 유저는 이미 과거(구 1단계 온보딩 시절)에 이 값이 채워져 있으므로 강제
    재온보딩되지 않는다** — `faction_id`를 기준으로 판정했다면 기존 유저(username은
    있지만 faction_id가 null)도 로그인마다 온보딩으로 튕겨 "강제 재온보딩 안 함"
    정책과 충돌했을 것(`/plan-ceo-review`에서 1차로 잘못 반영했다가 수정한 지점).
  - 기존 유저의 `faction_id` 백필(점진적 유도)은 이 판정 로직과 무관하게 별도
    후속 과제로 남는다(아래 참고).
- 온보딩 트라이브 카드는 `factions WHERE is_active = true`만 조회(기존 어드민 활성화
  인프라 재사용). 활성 트라이브가 0개인 경우 방어 로직 필요.
- **트라이브 불변**: `faction_id`는 온보딩 완료 시 1회 설정 후, 탈퇴 전까지 변경 불가.
  `/api/profile`(PATCH)에는 애초에 `faction_id`를 다루는 코드가 없으므로 이 제약은
  "프로필 편집 API에 트라이브 변경 엔드포인트를 추가하지 않는다"는 소극적 방식으로
  자연히 충족된다 — 별도의 잠금 플래그·차단 로직이 필요 없다.

### UI/UX 관점
- 2단계 카드형 온보딩:
  1. **1단계 — 아이디·이름**: username(중복확인, 기존 `/api/username/check` 재사용) +
     display_name(자유 텍스트, 30자, 기존 검증 로직과 동일 기준으로 실시간 글자수
     카운터 표시).
  2. **2단계 — 트라이브 선택 + 프로필이미지(선택)**: 각 진영 캐치프레이즈를 카드에
     노출하는 게임식 클래스 선택 UI. 프로필이미지는 구글 기본값 + 기존 업로드 API로
     변경 옵션.
- **프로필 편집 화면(`/profile/edit`)은 변경 범위를 넓히지 않는다** — 현재처럼
  프로필이미지·아이디·닉네임만 계속 변경 가능하고, 트라이브 변경 UI는 추가하지 않는다.
- **프로필 편집 진입 동선 변경** (`ProfileClient.tsx`): 아바타 우측 상단 오버레이의
  22px 원형 편집 버튼(`PencilIcon`, `/profile/edit`로 이동)을 제거한다. 대신 아이디
  아래 포인트 표시 행("OOO 포인트 >", 클릭 시 `/points`로 이동하는 기존 버튼)의
  같은 행 우측 끝에 "편집" 버튼을 새로 추가해 `/profile/edit`로 이동시킨다. 포인트
  버튼(→ `/points`)과 편집 버튼(→ `/profile/edit`)은 같은 행에 나란히 배치되는
  별개의 클릭 영역이며, 서로의 터치 타겟을 침범하지 않도록 간격을 둔다.
- 유저 대면 문구: "당신의 트라이브를 선택하세요" / "OO님의 트라이브: 낭만 미식가"
  — 운영 문서·DB·어드민에서는 "트라이브(faction)" 그대로 유지, 이번 변경은 유저
  대면 UI 라벨에 한정.

### 컨텐츠 관점
- `Specs/Content/FACTIONS.md`의 트라이브 10종·캐치프레이즈는 그대로 재사용(신규
  컨텐츠 제작 불필요). 트라이브별 아이콘·컬러 등 카드 UI용 비주얼 자산이 이미
  존재하는지 착수 전 확인 필요 — 없으면 별도 자산 준비 공수 추가.

## 구현 계획

**스코프: 이번 티켓은 온보딩 UI + `faction_id` 컬럼 추가 + 컬럼 정리까지만.**
드랍엔진 반영은 별도 후속 티켓(아래 참고) — 단, 병합 방식은 이번 논의에서 이미
확정했다.

1. DB 마이그레이션·배포 순서 (`/plan-ceo-review` 섹션 9에서 확정 — 파괴적 컬럼 삭제라
   순서를 반드시 분리한다):
   1) `users.faction_id` 추가(nullable, FK → `factions.id`) — 안전, 코드 배포와 동시 가능.
   2) `region`·`activity_types` 참조 코드를 **먼저 전수 제거하고 배포·안정화 확인**.
   3) 배포 안정화 확인 후, **별도 커밋/마이그레이션으로** `users.region`,
      `users.activity_types` 컬럼을 `DROP`한다. 컬럼 삭제 직전 DB 스냅샷을 남겨
      롤백 여지를 확보한다(삭제는 비가역 — 스냅샷 없이는 데이터 복구 불가).
   `display_name`은 기존 컬럼이라 마이그레이션 불필요.
2. `/api/onboarding/complete` 확장: username·display_name·faction_id 검증·저장 로직
   추가.
3. 온보딩 UI 2단계 리뉴얼: 1단계(아이디·이름) + 2단계(트라이브 카드 그리드 +
   프로필이미지). 프로필이미지·display_name은 기존 `/api/profile/avatar`,
   `/api/profile` 로직/검증 기준을 그대로 재사용.
3-1. 프로필 페이지(`ProfileClient.tsx`) 편집 진입 동선 변경: 아바타 모서리 편집
   버튼 제거, 포인트 표시 행 우측 끝에 "편집" 버튼 추가(`/profile/edit`로 이동).
   온보딩 로직과 무관한 독립적인 UI 변경이라 별도 커밋으로 진행 가능.
4. 기존 유저 마이그레이션: 강제 재온보딩 없이 `faction_id` null 허용, 점진적 유도
   UI는 후속 과제로 분리. (`display_name`은 이미 프로필 편집에서 임의 시점에
   채울 수 있으므로 별도 백필 이슈 없음.)
5. **완료 시 `Specs/SERVICE_OPERATIONS.md` 갱신 필수** — "2-3. 온보딩 흐름" 섹션을
   새 2단계 흐름(아이디·이름 → 트라이브·프로필이미지)으로 다시 쓴다. 이 김에
   현재 문서에 남아있는 기존 오기(유저네임 "3~20자"로 서술되어 있으나 실제 코드는
   30자, "프로필 이미지 업로드 → `/api/profile/avatar`"를 온보딩 흐름인 것처럼 서술한
   부분)도 함께 바로잡는다.

**후속 티켓(별도 착수) — 드랍엔진 트라이브 가중치 반영**:
- **병합 방식 확정**: 별도 가중치 파라미터를 새로 만들지 않는다. `BADGE_ENGINE_UNIFIED.md`
  1110행의 기존 설계 원칙("집중은 보이지 않는 가중치로만" — 하드캡·트라이브 선택 UI
  없이 자연 수렴)과 이번 "유저가 명시적으로 트라이브를 고른다"는 결정이 정면으로
  충돌하므로, **온보딩에서 고른 트라이브를 `last_drop_faction_id`의 초기 시드값으로
  설정**해 기존 마르코프 모멘텀 로직(모멘텀 50%)을 그대로 태우는 방식으로 흡수한다.
  - 신규 유저는 드랍 이력이 없어 `last_drop_faction_id`가 비어있는데, 이 초기값을
    온보딩에서 고른 `faction_id`로 채운다.
  - 첫 드랍부터 기존 모멘텀(50%)이 자연히 그 트라이브에 적용되고, 실제 드랍 이력이
    쌓이며 시간이 지나면 다른 트라이브으로 자연히 옮겨간다("서사적 졸업"과 동일 패턴).
  - 신규 유저 첫 3드랍 제한 후보군(작심삼일 클럽 + 활동종목 매핑 트라이브,
    `drop-engine/index.ts`)에 **유저가 고른 트라이브도 추가**해 충돌 방지.
  - 별도의 +N% 계수·확률표 신설이 필요 없어 기존 드랍엔진 코드 변경 범위가 최소화된다.
- `Specs/BadgeEngine/BADGE_ENGINE_UNIFIED.md`(단일 진실 원천)를 구현 전에 먼저
  갱신(위 병합 방식 반영)하고, 구현 완료 후 실제 로직과 문서가 일치하는지 재확인한다.
- 기존 유저 백필이 일정 수준 진행된 뒤 DB NOT NULL 전환 여부 재검토.

## Success Criteria

**이번 온보딩 UI 티켓 범위:**
- 신규 유저 온보딩 완료 시 `users.username`, `users.display_name`, `users.faction_id`가
  모두 채워진다 (`avatar_url`은 선택). DB 레벨 NOT NULL 강제는 이번 범위 밖.
- `users.region`, `users.activity_types` 컬럼과 그 참조 코드(전수 재확인 후)가
  저장소에서 제거된다.
- 온보딩 트라이브 카드는 `factions.is_active = true`인 항목만 노출하고, 활성
  트라이브가 0개인 상황에 대한 방어 로직이 있다.
- 기존 유저(이미 `username` 보유)는 강제 재온보딩 없이 `faction_id`가 널인 채로
  서비스를 계속 이용할 수 있다(점진적 유도 UI는 후속 과제).
- `faction_id`를 변경하는 API 엔드포인트가 어디에도 존재하지 않는다(온보딩
  완료 API 제외) — 프로필 편집은 프로필이미지·아이디·닉네임만 계속 지원한다.
- 프로필 페이지 아바타 모서리에는 더 이상 편집 버튼이 없고, 포인트 표시 행 우측
  끝의 "편집" 버튼으로만 `/profile/edit` 진입이 가능하다.
- 이미 `faction_id`가 설정된 유저가 `/api/onboarding/complete`를 재호출하면
  409로 거부되고 값이 바뀌지 않는다. 비활성(`is_active=false`) 트라이브를
  제출하면 400으로 거부된다.
- `onboarding_completed_at`이 2단계(트라이브 포함) 완료 시에만 기록되어,
  1단계만 마친 유저는 재로그인 시 온보딩 2단계로 돌아간다.
- `users.region`, `users.activity_types` 컬럼 삭제는 참조 코드 제거·배포 후
  별도 커밋으로 진행되며, 삭제 직전 DB 스냅샷이 남아 있다.

**후속 티켓 범위 (별도 착수):**
- `BADGE_ENGINE_UNIFIED.md`에 `last_drop_faction_id` 초기 시드 방식이 문서화된 뒤
  드랍엔진 반영.
- 기존 유저 백필이 일정 수준 진행된 뒤 DB NOT NULL 전환 여부 재검토.

### 주요 의사결정 / 핵심 메모
> `/office-hours`로 진행한 설계 논의 결과. 어드버서리얼 리뷰(품질점수 7/10 →
> 이슈 반영) 및 실제 코드 재확인을 거쳤다.

- **트라이브 이름 충돌**: 유저가 고르는 "트라이브"은 기존 배지·아이템 귀속 트라이브
  (`FACTIONS.md` 10개 진영)과 이름만 같은 신규 개념이 아니라 **그 10개 진영 중 하나를
  유저가 직접 선택**하는 것으로 확정.
- **유저 대면 명칭**: "트라이브"로 확정. 검토했던 대안 — 무브먼트·세력·라인·팩션·클랜.
  크루(Crew)는 기존 팔로잉·친구 개념과 혼동 소지가 커서 제외.
- **지역·운동종목 제거 범위**: 입력 UI가 없던 죽은 컬럼이라 "제거" = PRD 삭제 + DB
  컬럼 삭제 + 참조 코드 정리로 확정.
- **`display_name`은 신규 컬럼이 아니었다**: 초기 설계 문서 작성 시 온보딩 화면만
  조사하고 프로필 편집 화면·API를 재확인하지 않아 "신규 컬럼"으로 잘못 서술했다.
  실제로는 마이그레이션 112번으로 이미 존재하고 `/api/profile`에서 이미 완전히
  지원된다 — 온보딩 화면에 입력 단계만 추가하면 된다. 이번 티켓 갱신에서 정정.
- **NOT NULL 시점**: `faction_id`를 DB 레벨에서 즉시 NOT NULL로 강제하면 기존 유저
  로우가 제약 위반된다 — 온보딩 API 레벨 필수 검증으로 시작하고 DB 제약 전환은
  백필 이후로 미루기로 결정.
- **드랍엔진 가중치 병합 방식**: 별도 +N% 파라미터를 새로 만들지 않고, 온보딩에서
  고른 트라이브를 `last_drop_faction_id` 초기 시드값으로 써서 기존 모멘텀 로직에
  얹는 방식으로 확정. 이는 `BADGE_ENGINE_UNIFIED.md`의 "트라이브 선택 UI 없이 보이지
  않는 가중치로만 집중" 설계 원칙과의 정면 충돌을 최소화하기 위한 선택.
- **트라이브 불변**: 온보딩에서 정한 트라이브는 탈퇴 전까지 유저가 직접 변경 불가.
  프로필 편집 API에 트라이브 변경 엔드포인트를 아예 추가하지 않는 방식으로 구현한다
  (별도 잠금 로직 불필요).
