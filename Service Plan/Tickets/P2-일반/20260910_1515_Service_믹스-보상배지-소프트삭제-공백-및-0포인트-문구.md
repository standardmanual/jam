# [Service] 보상 배지를 삭제하면 믹스 성공이 빈손이 되고 "0 포인트 획득"이 뜬다

## 배경 / 문제 정의

믹스 v3(티켓 `20260910_1408`)는 레시피 저장 시점에 보상 배지의 존재·미삭제·타입을 검증한다.
그러나 레시피를 등록한 뒤 어드민이 그 보상 배지를 소프트 삭제하면 검증을 통과한 레시피가
그대로 남는다.

이때 유저가 그 레시피를 성공시키면 이렇게 된다.

1. 재료 아이템은 정상적으로 소각된다.
2. `grantBadge`가 삭제된 배지의 지급을 건너뛴다.
3. `resultBadges`가 비어 있는데 응답은 `success: true`다.
4. `reward_points`가 0인 레시피라면 유저 화면에 "0 포인트 획득!"이 뜬다
   (`CombineClient`의 `successPointsOnly` 분기).

유저는 재료를 잃고 아무것도 받지 못한 채 성공 화면을 본다. 발생 빈도는 낮지만 재현 가능하며,
게이트 리뷰에서 WARN 사유로 지적되었다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 지급 시점에 `reward_badge_ids`가 비어 있지 않은데 `resultBadges`가 비면 레시피 id와 배지
  id를 로그로 남겨 운영이 탐지할 수 있게 한다.
- 배지 삭제 API가 레시피의 `ingredient_badge_ids`·`reward_badge_ids` 참조를 확인하도록 한다.
  배열 컬럼이라 FK가 걸리지 않으므로 `&&` 연산자로 참조 레시피 수를 세어 경고한다.
  `lib/admin/recipe-references.ts`에 이미 유사한 참조 가드 패턴이 있으니 그 방식을 따른다.

### UI/UX 관점
- `CombineClient`의 `successPointsOnly` 분기가 지급 포인트 0일 때 "0 포인트 획득!"을 띄우지
  않도록 가드한다. 배지도 포인트도 없는 성공은 실패에 가깝게 안내하는 편이 정직하다.
- 문구는 `Specs/UX_WRITING_GUIDELINE.md`를 따른다.

## 구현 계획

지급 시점 로깅과 UI 가드를 먼저 넣고, 배지 삭제 참조 가드는 기존 참조 가드 패턴을 재사용한다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
1. `combineItems()` 지급 로직에서 `matched.reward_badge_ids`가 비어있지 않은데 실제 지급된
   `resultBadges`가 0건이면 레시피 id·의도했던 보상 배지 id·userId를 `console.error`로 남긴다.
2. `combination_recipes.ingredient_badge_ids`·`reward_badge_ids`(배열 컬럼, FK 없음) 참조를
   PostgREST `.overlaps()`(Postgres `&&` 연산자)로 세는 `countRecipesReferencingBadge()`를
   `lib/admin/recipe-references.ts`에 추가했다. 배지 소프트 삭제 PATCH(`active: false`)가
   삭제 직후 이 함수를 호출해 참조 레시피가 있으면 `console.warn`으로 경고만 남긴다(기존
   가역적 토글 성격을 유지하기 위해 차단하지는 않음 — 티켓 요구사항 그대로).
3. `CombineClient`의 성공 처리 분기를 재료가 소각됐는데 배지도 포인트도 0건인 경우
   `success: false`로 취급해 `recipeFail` 문구("믹스에 실패했어요. 아이템이 소각됐어요.")를
   띄우도록 가드했다. 배지 또는 포인트 중 하나라도 있으면 기존 성공 흐름을 그대로 탄다.

### 주요 의사결정 / 핵심 메모
- 배지 삭제 API 중 하드 삭제(`DELETE`)는 이미 `badge-references.ts`로 레시피 재료·보상·보유
  조건 참조를 전량 카운트해 차단하고 있었다(티켓 20260905_0034). 이번 버그는 **소프트
  삭제(`PATCH active:false`)** 경로에는 그런 참조 확인이 전혀 없었다는 점이었다 — 소프트
  삭제는 가역적 토글이라는 기존 성격을 그대로 유지하되(차단하지 않음), 참조가 있으면 운영이
  알 수 있도록 경고 로그만 추가했다.
- 신규 함수는 `badge-references.ts`처럼 전체 레시피를 페이지네이션으로 끌어와 메모리에서
  필터링하지 않고, 티켓이 명시한 대로 `.overlaps()`(`&&`)로 DB에서 바로 센다 — 배지 1건
  삭제마다 레시피 테이블 전체를 읽지 않아도 된다.
- CombineClient 가드는 `success: true`를 `success: false`로 바꿔치는 방식을 택했다 —
  체크마크 애니메이션·`successResult`/`successPointsOnly` 문구 전부가 "뭔가 받았다"는 것을
  전제하므로, 별도 문구를 새로 만들기보다 기존 실패 문구(`recipeFail`)를 재사용하는 편이
  유저 입장에서 더 정직하고 UX_WRITING_GUIDELINE의 "냉정하고 명확하게" 원칙에도 맞는다고
  판단했다.
