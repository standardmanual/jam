# [Content] JAM! 카테고리 — 사용량 배지 3종(팔로워·팔로잉·일일동기화) 신규 생성

## 배경 / 문제 정의

티켓 20260910_1557이 서비스 사용량(팔로워 수·팔로잉 수·일일 동기화 횟수) 조건으로 배지를
만들 수 있는 **엔진**을 완성했지만, 실제 배지 콘텐츠는 의도적으로 범위 밖으로 뺐다
("사용자가 어드민에서 직접 생성한다"). 그 결과 DB에는 이 조건을 쓰는 배지가 0건이라, 엔진은
배포됐지만 실질적으로 아무 효과가 없는 상태다(어드민·유저 화면 어디에도 이 배지가 보이지
않는다는 사용자 확인으로 이번 티켓이 시작됨).

이번 티켓은 각 지표당 배지 1개씩, 총 3개를 최초로 채워 넣는다.

## 상세 요구사항

### 서비스/코드베이스 관점

**현재 상태 (조사 결과, 2026-09-10 기준)**

- 어드민 배지 생성 폼(`/admin/badges/new`)에 "메타데이터" 섹션이 정상 렌더되며, "팔로워 수"·
  "팔로잉 수"·"하루 동기화 횟수" 숫자 입력 3개가 있다 — 로컬 실렌더로 확인.
- DB 조회 결과 `follower_count`/`following_count`/`daily_sync_count` 조건을 가진 배지는
  현재 0건이다(`SELECT ... WHERE condition_json ? 'follower_count' OR ...` → 빈 결과).
- `badges.image_url`은 DB 레벨에서 nullable이다 — 이미지 없이도 insert 자체는 가능하다.
- 단, 유저 화면([badges/page.tsx:80](../../../jam-web/src/app/(main)/badges/page.tsx:80))은
  `deleted_at`이 NULL인(=활성) 배지만 보여준다는 필터만 있을 뿐, `image_url`이 비어 있는지는
  걸러내지 않는다. 즉 이미지 없이 활성 상태로 등록하면 깨진 이미지가 그대로 노출된다.
- 어드민 "삭제" 버튼은 발급 이력이 없으면 실삭제, 있으면 `deleted_at`을 채우는 소프트
  삭제(="비활성화")로 동작한다([BadgeForm.tsx:1227](../../../jam-web/src/app/admin/badges/BadgeForm.tsx:1227)
  안내 문구). `deleted_at`이 채워진 배지는 유저 화면에서 완전히 숨는다(위 필터).
- 배지 이미지 실제 생성은 `/jam-img` 파이프라인이 전담하며, 5단계(이미지 생성 자체)는 Claude
  Code가 관여하지 않고 사용자가 Gemini에 직접 프롬프트를 입력해야 하는 수작업이다
  ([jam-img/SKILL.md](../../../.claude/skills/jam-img/SKILL.md)). 즉 이미지 준비까지 포함하면
  이번 티켓만으로 끝나지 않는 별도 후속 작업이다.

**제안 변경**

1. **배지 3종 신규 생성** — 아래 스펙대로 `type='activity'`·`activity_types=[]`(배지 트리
   미노출, 일반 목록/프로필에는 노출 — 티켓 20260910_1557 설계 그대로 계승)로 만든다.
   트라이브 종속이 아닌 서비스 전역 지표이므로 `tribe_id`는 없음으로 둔다.
   이름·설명은 가제이며, 최종 확정은 이 티켓 검토 단계에서 사용자가 한다.

   | 조건 | 조건값 | 등급 | 이름(가제) | 설명(가제) |
   |---|---|---|---|---|
   | `follower_count` | 10,000 | Mystic | 만 명의 동행 | 만 명이 이 사람의 발걸음을 눈여겨보고 있습니다. |
   | `following_count` | 10,000 | Mystic | 만 개의 손짓 | 만 명의 궤적을 하나하나 따라가고 있습니다. |
   | `daily_sync_count` | 1,000,000 | Mystic | 닿지 않는 하루 | 하루 동안 쉬지 않고 손을 뻗었습니다. |

   `daily_sync_count: 1,000,000`은 오타가 아니라 사용자가 명시적으로 확인한 값 — 스트라바
   동기화 횟수로는 사실상 영원히 달성 불가능한 히든/전설급 조건으로 의도됐다.

2. **비활성 상태로 우선 등록** — 이미지가 없는 상태에서 활성으로 두면 유저 화면에 깨진
   이미지가 노출되므로, 최초 insert 시 `deleted_at`을 현재 시각으로 채워 비활성 상태로
   만든다. `/jam-img`로 실제 이미지가 준비되면 별도 작업으로 `deleted_at`을 NULL로
   되돌려 활성화한다(이번 티켓 범위 밖 — 후속 조치로 남김).

3. **seed SQL 파일 작성** — `jam-web/supabase/seed_20260910_1959_usage_badges.sql`로 3건
   insert문 저장. 스키마 마이그레이션이 아니라 1회성 데이터이므로 `migrations/`가 아닌
   `seed_*.sql` 명명을 따른다(CLAUDE.md 절대 규칙 5).

### 구현 내용 요약

스펙 표(조건 필드·조건값·등급·이름·설명)를 그대로 따라 `jam-web/supabase/seed_20260910_1959_usage_badges.sql`을
신규 작성했다(실행은 하지 않음 — CLAUDE.md 절대 규칙 5, 실행은 사용자 승인 후 오케스트레이터
담당). 배지 3건 모두 `type='activity'`·`rarity='mystic'`·`activity_types=ARRAY[]::text[]`·
`tribe_id`는 지정하지 않아 컬럼 기본값 NULL을 따르고, `deleted_at=now()`로 비활성(소프트 삭제)
상태로 생성하도록 작성했다. `condition_json`은 각 배지마다 해당 지표 키 1개만 담는다
(`{"follower_count":10000}` 등) — 마이그레이션 155가 이미 이 3개 키를 CHECK 제약 허용 목록에
추가해둬 정상 통과한다.

각 INSERT는 `WHERE NOT EXISTS (... condition_json ? '{metric}')` 가드를 둬 재실행해도 중복
삽입되지 않는다(기존 시드 파일 관례를 따름). 실행 전 확인 쿼리·실행 후 검증 쿼리·롤백 DELETE문을
전부 주석으로 남겨 오케스트레이터가 실행 단계에서 바로 쓸 수 있게 했다.

`usageBadges.ts`(티켓 20260910_1557)의 등급형 평가 로직을 대조 확인했다 — 같은 이름(name)
그룹 안에서 미보유 + 조건 충족 중 최상위 tier 1개만 발급하는 방식이라, 각 배지가 이름별로
정확히 1개 tier(mystic)만 있어도(하위 common/rare/epic 없이도) 정상 동작한다. `family_key`는
지정하지 않았다 — 계열 정합성 트리거가 `#name:{name}` 폴백으로 그룹핑하는데, 세 이름 모두
신규라 충돌 대상 형제 행이 없다.

### 주요 의사결정 / 핵심 메모
- `patch_available` 컬럼은 명시적으로 지정하지 않았다 — DB 기본값이 이미 `FALSE`이고
  (`001_initial_schema.sql`), 티켓 스펙 표에도 언급이 없어 스펙 밖 값을 임의로 넣지 않기 위해
  컬럼 목록에서 뺐다. 참고로 살펴본 유사 사례(`seed_gate_mission_rest_axis_mystic_badges.sql`)는
  `patch_available=false`를 명시했지만, 그 파일은 여러 등급이 섞인 계열(family_key) 삽입이라
  명시가 더 유용했던 맥락이고 이번 3건은 맥락이 달라 그대로 따르지 않았다.
- `family_key`는 지정하지 않았다 — 세 배지 모두 신규 이름이라 `#name:{name}` 폴백 그룹핑으로
  충돌 없이 안전하게 처리된다(위 "구현 내용 요약" 참고).
- 이름·설명 문구는 사용자가 "그대로 따를 것"이라고 명시해, 대안 문구를 만들지 않고 스펙 표
  그대로 반영했다.
