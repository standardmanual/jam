# [Infra] jam-work 파이프라인 소요 시간 단축

## 배경 / 문제 정의

사용자가 "jam-work 워크플로우의 규모가 커져서 간단한 작업도 시간이 매우 오래 걸린다"고
문제를 제기했다. `SKILL.md`·`jam-work.js`·세 에이전트 정의(`jam-developer`·
`conservative-reviewer`·`progressive-reviewer`)를 직접 읽어 확인한 결과, 짐작이 아니라
구조 자체에서 세 가지 원인을 확인했다.

1. **`bug` 유형처럼 흔한 작업도 예외 없이 서브에이전트 3개를 직렬로 거친다.** 한 줄짜리
   조건문 수정이라도 jam-developer(구현) → conservative-reviewer(게이트) →
   progressive-reviewer(개선 제안) 순서를 그대로 따른다. 기존 "경미 수정" 예외
   (SKILL.md 참고 항목, 1파일·수 줄·**로직 무변경**)는 문서 맨 아래에 있어 판정 순서상
   맨 나중에 고려됐고, "로직 무변경" 제약 때문에 버그 수정 자체가 대부분 해당하지 않았다.
2. **전체 lint가 파이프라인 한 번에 최소 두 번 실행된다.** jam-developer가 구현 후 자체
   검증으로 `npm run lint` 전체를 한 번 돌리고, conservative-reviewer가 게이트 판정을 위해
   같은 명령을 프로젝트 전체 대상으로 처음부터 다시 돌린다. push 시점 `.githooks/pre-push`
   까지 더하면 같은 검사가 최대 세 번 반복된다.
3. **서로 독립적인 리뷰 세 단계가 순차 실행된다.** `jam-work.js`의 progressive-reviewer·
   interface-reviewer·korean-writing-reviewer 세 단계는 전부 `devResult`와 `gate` 결과만
   참조할 뿐 서로의 결과를 쓰지 않는데도, 코드가 세 개를 순서대로 `await`했다.

사용자에게 4가지 개선 레버(3번 병렬화 / 2번 lint 중복 제거 / 개선 리뷰 생략 기준 확대 /
1번 경미 수정 예외 확대)를 제시하고 트레이드오프를 설명한 뒤 확인받았다. **네 가지 모두
적용**하기로 결정했다.

해당 없음. `jam-web/`은 건드리지 않는다 — `.claude/` 워크플로·에이전트 설정과 스킬 문서만
변경한다.

## 구현 계획

1. `jam-work.js`: progressive-reviewer·interface-reviewer·korean-writing-reviewer 세
   `agent()` 호출을 순차 `await`에서 `parallel()` 기반 동시 실행으로 바꾼다. 각 조건
   (FULL 유형 여부·diff 크기·한국어 카피 존재 여부)은 그대로 유지하고, 조건이 꺼진 단계는
   `Promise.resolve(null)`로 즉시 해소되는 thunk를 넣어 결과 배열 순서를 고정한다.
   인터페이스 리뷰 전용이던 `INTERFACE_REVIEW_MIN_DIFF_LINES`(15줄) 임계값을
   `SMALL_DIFF_LINE_THRESHOLD`로 승격해 개선 리뷰 생략 판단에도 재사용한다.
2. `conservative-reviewer.md`: `diffLineCount` 계산을 `ui` 유형 전용에서 전 유형 공통으로
   확대한다(개선 리뷰 생략·게이트 lint 재실행 생략 판단에 모두 쓰이므로). lint 검증 규칙에
   "diff가 작고 jam-developer가 이미 깨끗한 lint 결과를 보고했다면 재실행을 생략하고 그
   수치를 인용한다"는 예외를 추가하되, 에러 존재·경고 초과·confidence: low·WARN/HALT
   alerts 중 하나라도 있으면 diff 크기와 무관하게 재실행하도록 안전장치를 둔다.
3. `SKILL.md`: "0. 유형 판정" 절 맨 앞에 "0.1 경미 수정 여부 먼저 확인"을 신설해 기존
   "참고" 항목의 예외 규정을 판정 순서상 최우선으로 승격하고, "로직 무변경" 제약을
   "diff 규모(1~2파일·10줄 내외) + 원인·수정의 명백성" 기준으로 교체한다. 기존 유형
   자동 판정 문단은 "0.2 유형 자동 판정"으로 이동한다. 풀 파이프라인 표·3.1절 PASS
   분기·맨 아래 참고 항목도 위 변경사항이 일관되게 반영되도록 갱신한다.

**영향 범위**: `.claude/workflows/jam-work.js`, `.claude/agents/conservative-reviewer.md`,
`.claude/skills/jam-work/SKILL.md`. `jam-web/` 무변경이므로 Vercel 빌드는 발생하지 않는다.

**리스크**: 이번 변경은 검증 절차 자체를 다루는 인프라라 블라스트 반경이 전체 향후 작업에
걸친다. 특히 게이트 lint 중복 제거·개선 리뷰 생략·경미 수정 확대 세 가지는 속도와 독립
검증의 정도를 맞바꾸는 선택이며, 사용자가 트레이드오프를 인지한 상태로 승인했다. 병렬화
(레버 1)만은 검증 내용을 전혀 바꾸지 않는 손실 없는 변경이다.

**검증 방법**: 구조 변경이라 실제 파이프라인을 한 번 돌려보는 것이 유일한 확증이다. 이
세션에서는 정적 검증(`node --check`, diff 대조, 문서 일관성 grep)까지만 하고 실동작 확인은
다음 `jam-work` 호출에 맡긴다 (선례: 티켓 20260910_1246과 동일한 검증 방침).

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

**레버 1 — 리뷰 3단계 병렬 실행**
- `jam-work.js`에서 progressive-reviewer·interface-reviewer·korean-writing-reviewer
  호출을 `parallel([...])` 배열로 묶었다. 각 `agent()` 호출에 `opts.phase`를 개별
  지정해(`'개선 리뷰'`·`'인터페이스 리뷰'`·`'한국어 리뷰'`) 동시 실행 중에도 진행 표시가
  올바른 제목으로 묶이게 했다(workflow-authoring 스킬의 "pipeline/parallel 단계에서는
  전역 phase() 대신 opts.phase를 쓴다" 권고를 따름).
- 세 단계의 실행 조건(`runProgressive`/`runInterfaceReview`/`runKoreanReview`)은 기존
  로직과 100% 동일하게 유지했다 — 병렬화는 순수하게 실행 순서만 바꾼 것이라 검증 내용에
  변화가 없다.

**레버 2 — 게이트 lint 중복 제거**
- `conservative-reviewer.md` 5번 규칙에 예외를 추가했다: `diffLineCount` 15줄 미만이고
  jam-developer의 구현 요약에 이미 `npm run lint` 전체 실행 결과(에러 0건·경고 26건 이하)가
  명시돼 있다면 게이트에서 재실행하지 않고 그 수치를 인용한다.
- 안전장치: 개발자 보고에 에러가 있거나, 경고 수치가 없거나 26건을 초과하거나,
  `confidence: low`이거나, `alerts`에 WARN·HALT가 있으면 diff 크기와 무관하게 직접
  재실행한다. push 시점 `.githooks/pre-push`의 전체 lint 재검증이 최종 안전망으로
  남아있으므로, 이 예외는 "중복 실행 제거"이지 "검증 제거"가 아니다.

**레버 3 — 개선 리뷰 생략 기준 확대**
- 기존에 `ui` 유형 인터페이스 리뷰에만 있던 `diffLineCount < 15` 생략 기준을 개선 리뷰에도
  적용했다 (`runProgressive` 조건에 `diffLineCount >= SMALL_DIFF_LINE_THRESHOLD` 추가).
  `content`·`copy`·`admin`·`infra`(라이트 유형)는 원래도 개선 리뷰가 없었으므로 영향 없고,
  `ui`·`ds`·`bug`·`engine`·`db`·`api`(풀 유형)에서 작은 diff일 때만 개선 리뷰가 생략된다.
- 이를 위해 `conservative-reviewer.md`의 `diffLineCount` 계산을 `ui` 유형 전용에서 전
  유형 공통으로 바꿨다(계산 자체가 `git diff --numstat` 한 번이라 비용이 낮다).
- `SKILL.md` 3.1절 PASS 분기에 "`progressive`가 `null`이면 생략 사실을 함께 보고한다"는
  문구를 추가해, 개선 리뷰가 생략됐을 때 사용자가 그 사실을 알 수 있게 했다.

**레버 4 — 경미 수정 예외 확대·승격**
- `SKILL.md` "0. 유형 판정" 절 맨 앞에 "0.1 경미 수정 여부 먼저 확인"을 신설했다. 기존
  "참고" 항목 맨 아래에 있던 규정(판정 순서상 사실상 맨 나중)을 판정 순서 최우선으로
  옮겼다.
- 기준을 "1파일·수 줄·**로직 무변경**"에서 "① 변경 파일 1~2개·diff 10줄 내외 ② 원인과
  수정이 조사 없이 바로 설명 가능(명백성)"으로 바꿨다. "로직 무변경" 제약을 없애서, 원인이
  명확한 1~2줄짜리 버그 수정도 이제 이 경로로 처리할 수 있다. 확신이 없으면 풀 파이프라인
  으로 넘어가도록 안전장치를 명시했다(conservative-reviewer가 확신 없을 때 FAIL로 기우는
  것과 같은 원칙).
- 이 경로를 택하면: 오케스트레이터 직접 구현(jam-developer 위임 없음, review 브랜치 없음),
  변경 파일 한정 `npx eslint`로 최소 검증(전체 lint는 생략, push 시점 pre-push가 안전망),
  티켓은 그대로 남기고 staging에 직접 commit한다.
- 기존 유형 자동 판정 문단은 "0.2 유형 자동 판정"으로 옮겼다(번호만 붙였고 내용은 그대로).

**문서 일관성**
- `SKILL.md` 참고 절의 낡은 문구(옛 "경미 수정" 규정, `INTERFACE_REVIEW_MIN_DIFF_LINES`
  이름)를 갱신하고, 병렬화·lint 중복 제거·diffLineCount 전 유형 공통화를 각각 설명하는
  bullet 3개를 추가했다.
- 전체 저장소(워크트리 제외)에서 `INTERFACE_REVIEW_MIN_DIFF_LINES`·구버전 "경미 수정"
  문구가 살아있는 트리에 남아있지 않은지 grep으로 재확인했다 — 남은 참조는 전부
  `.claude/worktrees/`(다른 세션의 스냅샷 사본) 안에만 있고, 이번 작업 범위 밖이다.

### 주요 의사결정 / 핵심 메모
- 사용자가 4개 레버를 모두 선택했다 — "리뷰 병렬 실행"은 무손실 개선이라 이견이 없었고,
  나머지 3개(lint 중복 제거·개선 리뷰 생략 확대·경미 수정 확대)는 속도와 독립 검증의 정도를
  맞바꾸는 선택임을 명시적으로 설명한 뒤 승인받았다.
- 게이트 lint 재실행 생략(레버 2)을 "파일 단위 eslint로 대체"가 아니라 "개발자가 이미 돌린
  전체 lint 결과를 diff가 작을 때만 인용"으로 설계했다 — `conservative-reviewer.md`에는
  "파일 단위 검증(`npx eslint <파일>`)으로 대체하지 않는다"는 기존 규칙이 티켓 20260827_022
  사고(파일 단위 검증이 다른 파일에 밀어넣은 위반을 놓침) 근거로 이미 존재해서, 그 교훈과
  충돌하지 않는 형태를 택했다. push 시점 pre-push 훅이 전체 lint를 기계적으로 재검증하는
  안전망이 있다는 점을 근거로 "완전히 검증을 생략"이 아니라 "중복 실행만 제거"로 한정했다.
- 경미 수정 예외(레버 4)에서도 완전 무검증 대신 "변경 파일 한정 eslint"라는 최소 검증을
  남겼다 — 리뷰어가 아예 없는 경로이므로 최소한의 기계적 확인 없이 staging에 바로 올라가는
  것은 과하다고 판단했다.
- `.claude/worktrees/` 아래 오래된 워크트리 11개(옛 SKILL.md·에이전트 정의 사본 포함)는
  이번 범위 밖으로 판단해 손대지 않았다. 대신 별도 백그라운드 작업 제안(`spawn_task`,
  task_id: task_1f79e251)으로 남겨 사용자가 원할 때 별도 세션에서 안전하게 정리하도록 했다.

### 잔여 이슈
1. 실제 `jam-work` 파이프라인 실행 검증이 아직 없다. 다음 호출에서 다음을 관찰해야 한다:
   - `parallel()` 호출이 의도대로 세 단계를 동시 진행 표시하는지
   - `diffLineCount`가 `ui` 외 유형에서도 실제로 채워지는지
   - 게이트가 작은 diff에서 실제로 lint 재실행을 생략하고 개발자 수치를 인용하는지
   - 0.1절 경미 수정 판정이 실제 요청에서 오케스트레이터(다음 세션 포함)에게 일관되게
     적용되는지 — 프롬프트 규칙이라 강제 수단이 없고, 관찰로만 검증 가능하다
   어긋나면 이 티켓을 참고해 조정한다.
2. 경미 수정 판정 기준("diff 10줄 내외", "명백성")은 정성적이라 사람마다·세션마다 판단이
