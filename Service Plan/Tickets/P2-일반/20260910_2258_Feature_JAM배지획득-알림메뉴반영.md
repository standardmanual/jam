# [Feature] JAM! 배지 획득 시 알림 메뉴 반영

## 배경 / 문제 정의

JAM! 배지(서비스 사용량 배지 3종)의 발급은 `usageBadges.ts`의 `evaluateUsageBadges`/
`recordDailySyncAndEvaluate`가 동기화·팔로우 시점에 실시간으로 처리하며, 팔로우 경로는
이미 `BadgeRevealOverlay` 리빌 애니메이션과 연동돼 있다(티켓 20260910_2056). 그런데
조사 결과 **JAM! 배지 획득이 알림함(`/notifications`)에는 전혀 반영되지 않는다** —
표시 방식 문제가 아니라 완전한 기능 누락이다.

- **동기화 경유**: `sync.ts:967`의 `notifyActivityBadgesEarned(supabase, userId,
  activityBadgeIds, ...)`는 Strava 활동배지 ID만 인자로 받는다. JAM! 사용량 배지 평가
  (`recordDailySyncAndEvaluate`)는 그보다 **뒤인 `sync.ts:1019-1020`**에서 이뤄져
  `earnedBadgeIds`(리빌 연출용)에만 합류하고, 알림 결산 호출은 이미 끝난 뒤라 반영되지 않는다.
- **팔로우 경유**: `follows/route.ts:90,107`의 `evaluateUsageBadges` 호출 어디에도
  `createNotification` 호출이 없다 — 발급돼도 `BadgeRevealOverlay`(클라이언트 응답
  payload)로만 보이고 알림함 행은 생기지 않는다.
- **참고(정상 동작)**: `following.ts`(246-249, 288-366행) 팔로잉 활동 배치는
  `admin_category` 구분 없이 `user_activity_badges`를 통째로 읽어 rarity epic/mystic
  또는 level≥6이면 `following_rare_badge`를 만든다. JAM! 배지가 이 등급대면 **팔로워에게는**
  알림이 뜰 수 있지만, 정작 **획득한 본인에게는** 여전히 아무 알림도 없다 — 이 비대칭이
  이번 티켓의 핵심 문제다.
- 알림 "설정"(구독 on/off) 화면은 코드베이스 전체에 존재하지 않는다 — 만들 필요 없다.

## 상세 요구사항

### 서비스/코드베이스 관점

1. **`sync.ts`** — `recordDailySyncAndEvaluate`가 반환하는 JAM! 배지 평가 결과
   (`usageEarned`류)를 `notifyActivityBadgesEarned` 호출(967행) 이전으로 옮기거나, 그
   결과를 합류시켜 함께 알림 결산에 반영한다. 활동결산(`activity_recap`) 알림 문구·아이콘은
   이미 종목 무관(제네릭)이라 별도 수정이 필요 없다 — 호출 순서·인자 결합만 바로잡는다.
2. **`follows/route.ts`** — `evaluateUsageBadges` 발급 결과가 있으면(빈 배열이 아니면)
   해당 유저에게 배지 획득 알림을 생성하는 호출을 추가한다. 동기화 경로가 쓰는 알림 생성
   함수·타입을 그대로 재사용해 새 `NotificationType`을 만들지 않는다(기존 20종 체계 안에서
   해결되는지 먼저 확인).
3. 알림함 렌더링(`NotificationsClient.tsx`)은 타입별 아이콘(`TypeIcon`, 45-84행)이 이미
   종목 무관하게 20종 `NotificationType`에 1:1 매핑되므로 별도 수정이 필요 없다 — 2번에서
   기존 배지 획득 알림 타입을 그대로 재사용한다는 전제하에.

### UI/UX 관점

- 새로 뜨는 JAM! 배지 알림 문구가 기존 활동배지 알림 문구와 톤이 어긋나지 않는지 확인한다
  (`UX_WRITING_GUIDELINE.md` — 배지 획득은 "신남" 톤).

## 구현 계획

`sync.ts`(동기화 경로)와 `follows/route.ts`(팔로우 경로)는 서로 다른 진입점이라 독립적으로
고칠 수 있다. 기존 `notifyActivityBadgesEarned`/알림 생성 함수의 시그니처를 최대한 재사용해,
JAM! 전용 알림 파이프라인을 새로 만들지 않는다.

## Out of Scope

- 알림 "설정"(구독 on/off) 화면 신설 — 존재하지 않고 이번 범위도 아니다
- `following.ts`의 "팔로워에게 알림" 로직 변경 — 이미 정상 동작
- 프로필 활동 피드("전체"·"배지" 탭) — 조사 결과 이미 정상 노출 중이라 이번 티켓과 무관

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

두 경로 모두 **기존 `notifyActivityBadgesEarned`(sync.ts)를 그대로 재사용**해 JAM! 배지
획득을 `activity_recap` 결산에 합류시켰다. 새 `NotificationType`·새 문구·새 아이콘은
만들지 않았다.

- **`sync.ts`**: `notifyActivityBadgesEarned` 호출을 `evaluateBadges` 직후(옛 967행)에서
  `recordDailySyncAndEvaluate` 호출 **이후**로 이동하고, 인자를
  `[...activityBadgeIds, ...usageEarned.map(b => b.id)]`로 합쳤다. `recordDailySyncAndEvaluate`가
  실패해도(try/catch) `usageEarned`는 빈 배열로 남아 활동배지만으로 결산이 만들어진다 —
  기존 폴백 동작 그대로 유지.
  `notifyActivityBadgesEarned`는 badge id 목록으로 `badges` 테이블을 되읽어 결산에 실을
  뿐 배지 "종류"를 가정하지 않으므로, JAM! 배지 id를 섞어 넘겨도 그대로 동작한다(함수 내부
  변경 없음). 함수를 `export`로 바꿔 `follows/route.ts`에서도 재사용할 수 있게 했다.
- **`follows/route.ts`**: `evaluateUsageBadges` 두 호출(actor의 following_count, target의
  follower_count) 각각에서 발급 결과가 있으면(`length > 0`) `notifyActivityBadgesEarned`를
  호출해 해당 유저(actor 또는 target) 앞으로 결산 알림을 남긴다. `activityIds` 인자는 빈
  배열(`[]`) — 팔로우 액션에는 귀속시킬 Strava 활동이 없다(sync.ts의 "새 활동 0건" 이른
  반환 경로가 이미 쓰는 패턴과 동일). 기존에 캡처하지 않던 `evaluateUsageBadges(targetUserId, ...)`
  반환값을 `targetEarned`로 받도록 바꿨다(이전엔 버려졌음).
  §2-2 "자기 행동의 메아리를 넣지 않는다" 원칙은 `followed` 소식(팔로우한 사람 본인에게는
  안 감)에만 적용된다 — actor·target 모두 "자기 자신이 배지를 획득"한 사건의 당사자이므로
  둘 다 알림 대상이 맞다(팔로우한 행위 자체의 메아리가 아니라 배지 획득이라는 별개 결과).

### 주요 의사결정 / 핵심 메모

- **함수 재사용 방식**: 티켓이 제시한 두 옵션(① `recordDailySyncAndEvaluate`를
  `notifyActivityBadgesEarned` 호출보다 앞으로 옮기기, ② 결과를 합류시켜 함께 반영) 중
  ②를 택했다 — `notifyActivityBadgesEarned` 호출 자체를 `recordDailySyncAndEvaluate`
  이후로 늦추고 두 id 배열을 합쳐 한 번만 호출했다. ①(단순히 `recordDailySyncAndEvaluate`
  호출만 끌어올리는 방식)은 `earnedBadgeIds`에 JAM! 배지가 push되는 위치가 앞당겨져
  리빌 연출(`BadgeRevealCarousel`)의 기존 "체크인 → 아이템 드랍 → 액티비티 → 컬렉션·미션
  보상" push 순서 문서화 계약을 건드릴 수 있어 피했다. ②는 `earnedBadgeIds` push 순서는
  그대로 두고 알림 결산 호출 시점·인자만 조정해 부작용 범위가 더 좁다.
- **`notifyActivityBadgesEarned` export**: 함수 로직은 전혀 바꾸지 않고 `export` 키워드만
  추가했다 — badge id → `badges` 재조회 → `activity_recap` 결산이라는 동작이 배지 "종류"를
  가정하지 않아 그대로 재사용 가능했다(함수 상단 doc에 재사용처 2곳을 명시).
- **`follows/route.ts`의 `activityIds: []`**: sync.ts가 "새 활동 0건" 이른 반환 경로에서
  이미 `notifyActivityBadgesEarned(supabase, userId, activityBadgeIds, [])` 형태로 빈
  배열을 넘기는 선례가 있어 그 패턴을 그대로 따랐다. `recap.ts`의 `isEmpty()`가
  `activity_ids`는 비어있음 판정에 포함하지 않으므로(활동배지가 있으면 결산이 만들어짐)
  안전하다.
