# [Admin] 배지 생성·수정 화면 — 타입별 개편

## 배경 / 문제 정의

`BadgeForm.tsx`(1283줄, 생성·수정 공용)는 최초 구축 이후 기능이 계속 그대로 추가돼,
배지 분류·기본정보·획득조건·보상조건·연결정보·부가정보·디자인요소·미리보기·시뮬레이션이
하나의 긴 스크롤 폼 안에 뒤섞여 있다. `better-interface` 크로스 도메인 리뷰(2026-09-10)로
확인한 근거:

1. **접근성 HIGH** — 삭제 확인이 `<div className="fixed inset-0...">`로 직접 구현돼
   role/aria-modal/포커스 트랩/ESC 닫기가 전혀 없다(`BadgeForm.tsx:1253-1280`). 같은
   프로젝트의 `BadgeDetail.tsx:319-342`는 정확히 같은 액션을 Radix `AlertDialog`로
   구현해 이 문제가 없다.
2. **컴포넌트 불일치** — `BadgeForm.tsx` 전체가 shadcn 컴포넌트(`Button` 등)를 쓰지 않고
   네이티브 HTML을 Tailwind로 직접 스타일링한다. 삭제 버튼은 `text-red-600`(원시값)이고
   `BadgeDetail.tsx`·`BadgeCard.tsx`는 `variant="destructive/default/outline"`을 쓴다.
3. **영역 뒤섞임** — 최상위 `grid grid-cols-2 gap-4`(586-859행) 안에 13개 이상의 서로
   다른 주제(기본정보/분류/연결정보/보상/디자인요소)가 같은 16px 간격으로 나열돼 그룹
   구분이 없다. 조건빌더·연결지점·유효기간 섹션(922·1069·1188행)만 카드로 분리돼 있어
   폼 전반부·후반부의 그룹화 패턴이 불일치한다.
4. **타입별 최적화 부재** — "활동 종류(+JAM!)" 체크박스 그룹(861-893행)이 조건부 렌더링
   없이 **모든 타입에서 무조건** 노출된다 — 체크인·아이템 배지를 만들 때도 뜬다. JAM!
   배지를 선택해도 조건 빌더 전체·판정 시뮬레이션 패널·트라이브/컬렉션 선택이 그대로
   노출되는데, JAM!은 서비스 사용량 지표(`usageBadges.ts`)로 실시간 판정돼 이 필드들이
   전부 무의미하고, 시뮬레이터도 JAM! 배지를 이미 후보에서 제외한다.
5. 그 외 MEDIUM/LOW: 경고 박스 4종의 색상 하드코딩 중복(991·1006·1019·1036행), 입력
   필드 `text-sm`(14px)로 모바일 iOS 확대 유발 가능(502·1089행), `grid-cols-2`에 반응형
   접두사 부재(586·937·949행), 폴백 에러 메시지 부실(391·420행), rarity 라벨/색상 매핑
   3개 파일 중복(`BadgeCard.tsx`·`BadgesTable.tsx`·`BadgeDetail.tsx`).

**목록→상세→수정 흐름은 이미 정상 구현돼 있다** — 카드·테이블 모두 "상세보기" 버튼이
`/admin/badges/{id}`(조회 전용, `BadgeDetail.tsx`)로 가고, 거기서 "수정" 버튼을 눌러야
`/admin/badges/{id}/edit`(`BadgeForm.tsx`)로 이동한다. 이번 티켓은 이 흐름을 건드리지
않는다.

## 상세 요구사항

### 1단계 — 컴포넌트 교체 (접근성 HIGH 해소)

1. 삭제 확인 모달(`BadgeForm.tsx:1253-1280`)을 커스텀 `<div>`에서 `BadgeDetail.tsx:319-342`가
   쓰는 Radix `AlertDialog` 패턴(themeContainer 포털 포함)으로 교체한다. 문구는 기존과 동일하게
   유지한다(두 화면이 이미 같은 문구를 쓰고 있음).
2. 저장·취소·삭제 버튼(1227-1251행)을 `@/components/admin/ui/button`의
   `<Button variant="default/outline/destructive">`로 교체한다.
3. 경고 박스 4종(평가대기 991·미지원필드 1006·재현불가 1019·진행미지원 1036행)의
   `border-amber-300 bg-amber-50 text-amber-900` 반복을 공용 서브컴포넌트 또는 시맨틱
   토큰으로 통합한다.

### 2단계 — 레이아웃 재편

1. 최상위 `grid grid-cols-2`(586-859행)를 주제별 카드(`border rounded-2xl p-5` — 조건빌더
   섹션이 이미 쓰는 패턴)로 분리한다: 기본정보(이름/설명/이미지) / 보상·유효기간(포인트/패치/
   기간) / 디자인요소(배경테마·미리보기)를 최소 단위로 나눈다. 정확한 카드 경계는 3단계
   결과(타입별 필드 매트릭스)와 맞물리므로 구현 중 조정 가능하다.
2. `grid-cols-2`(586·937·949행)에 `sm:` 접두사를 추가해 좁은 화면에서 1열로 무너지게 한다.

### 3단계 — 타입별 최적화

1. "활동 종류(+JAM!)" 체크박스 그룹(861-893행)을 `type === 'activity'`일 때만 렌더링하도록
   조건부 처리한다.
2. `admin_category === 'jam'`일 때 조건 빌더 전체(922-1065행, 판정 시뮬레이션 패널 포함)를
   숨기고, 대신 "이 배지는 사용량 지표로 판정됩니다"류의 안내 카드로 대체한다. 저장 로직
   (`handleSubmit`)이 JAM! 배지에 대해 `condition_json`을 어떻게 다루는지(현재는
   `buildConditionJson()` 결과를 그대로 저장) 변경이 필요한지 확인하고, 필요하면 저장
   페이로드도 함께 조정한다 — 단, `admin_category` 저장 자체(363-365행)는 건드리지 않는다.
3. 타입 선택(611-622행)을 최상단 "분류" 카드로 고정하고, 이후 모든 섹션이 그 선택을 따라
   조건부로 나타나는 구조로 정리한다.

## Out of Scope

- 4단계(`BadgeForm.tsx`를 타입별 하위 컴포넌트로 분리, rarity 라벨/색상 매핑 공용화)는
  이번 범위에서 제외 — 후속 티켓으로 별도 진행

  판단(기존 프로젝트 토큰 우선 재사용)

## 구현 계획

1~3단계 순서로 진행한다. 1단계(컴포넌트 교체)는 다른 단계와 독립적이라 먼저 끝내도
무방하다. 2단계(레이아웃)와 3단계(타입별 최적화)는 서로 얽혀 있으므로 — 카드 경계를
정할 때 이미 타입별로 뭘 숨길지 알아야 한다 — 순서대로 진행하되 필요하면 함께 조정한다.

저장 API(`api/admin/badges/route.ts`, `api/admin/badges/[id]/route.ts`)와 검증 로직
(`validateCondition`, `findConditionShapeSaveError` 등)은 화면 표시만 바뀌는 한 손대지
않는다. JAM! 배지의 조건 빌더를 숨기면서 `condition_json` 저장 방식을 바꿔야 한다면
(3단계 2번), 그 변경이 저장 API·판정 로직과 충돌하지 않는지 반드시 확인한다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

1단계~3단계를 계획대로 구현했다. 다만 3단계 2번(JAM! 카테고리의 조건 빌더 숨김)은
티켓 원문의 "조건 빌더 전체를 숨긴다"를 문자 그대로 구현하지 않고, 사용량 지표 조건
필드(팔로워 수/팔로잉 수/하루 동기화 횟수 — `conditionRegistry.ts`의 `role: 'meta'`
필드 3종)만은 별도의 "사용량 지표 조건" 카드에 남겨두는 형태로 구현했다. 이 3개 필드는
`usageBadges.ts`가 실제로 조회하는 JAM! 배지의 **유일한 조건 저장 경로**라, 완전히
숨기면 JAM! 배지의 획득 임계값을 이 화면에서 설정·수정할 방법이 사라진다(신규 작성
시에는 아예 만들 수 없게 된다). 자세한 근거와 판단은 아래 "주요 의사결정" 및 최종
응답의 `alerts`에 남겼다.

- 1단계: 삭제 확인 모달을 `BadgeDetail.tsx`와 동일한 Radix `AlertDialog` 패턴으로 교체.
  저장/취소/삭제 버튼을 shadcn `Button`(`default`/`outline`/`destructive`)으로 교체.
  경고 박스 4종의 `border-amber-300 bg-amber-50 text-amber-900` 반복을
  `components/admin/ui/alert.tsx`에 `warning` variant로 추가해 통합(기존 색상 값 그대로
  재사용, 새 색상 도입 없음).
- 2단계: 최상위 `grid grid-cols-2`를 5개 주제별 카드(분류/기본정보/연결정보/보상·유효기간/
  디자인요소)로 분리했다. 문제정의에서 언급한 5개 테마(기본정보/분류/연결정보/보상/
  디자인요소)를 그대로 카드 경계로 채택했다 — 2단계 지시문이 명시한 3개 카드(기본정보/
  보상·유효기간/디자인요소) 외에 "분류"·"연결정보" 카드를 추가로 만든 것은 "정확한 카드
  경계는 구현 중 조정 가능"이라는 티켓 문구에 근거한 판단이다(타입/등급/레벨/family_key/
  트라이브/컬렉션/카테고리/드랍가중치가 어느 카드에도 안 들어가는 공백을 메워야 했음).
  파일 내 모든 `grid-cols-2`에 `sm:` 접두사를 적용해 반응형으로 통일했다(원래 지시된
  3곳뿐 아니라 유효기간 날짜 쌍·교차 게이트 내부 그리드까지 동일 패턴으로 확장).
- 3단계: 활동 종류(+JAM!) 체크박스를 `type === 'activity'`일 때만 렌더링하도록 변경.
  타입 Select를 최상단 "분류" 카드로 고정. `admin_category === 'jam'`일 때 조건
  빌더 대신 "사용량 지표 조건" 카드를 보여주되, 위에서 설명한 이유로 메타데이터
  섹션(팔로워/팔로잉/일일동기화)의 입력 필드와 JSON 미리보기, 미지원/왕복불가 경고는
  유지했다. 2단 게이트·미션 보상 체크박스·판정 시뮬레이션 패널은 완전히 숨겼다(이 부분은
  `usageBadges.ts`가 평가하지 않아 원 지시대로 무의미함이 코드로 확인됨).
  `progressIssue`(배지 트리 진행률 미지원 경고)는 JAM! 카테고리에서 조건 자체가 항상
  무의미해 `isJamCategory` 분기로 추가 억제했다(JAM! 배지는 `activity_types=[]`라
  배지 트리 화면에 애초에 노출되지 않음 — `usageBadges.ts` 주석 근거).
  저장 로직(`handleSubmit`)은 변경하지 않았다 — `buildConditionJson()`이 여전히
  `condFields`(메타 필드 포함) 전체를 그대로 읽어 저장하므로 화면 표시만 바뀌어도
  저장 페이로드는 기존과 동일하다.

### 주요 의사결정 / 핵심 메모

1. **JAM! 카테고리의 "조건 빌더 전체 숨김"을 문자 그대로 구현하지 않은 이유** —

   판정한다 — 즉 이 3개 필드는 "무의미한 필드"가 아니라 **JAM! 배지의 유일한 조건
   입력 경로**다. 조건 빌더를 완전히 숨기면 신규 JAM! 배지를 만들 때 임계값을 입력할
   방법이 이 화면에서 사라진다. 그래서 조건 빌더의 "메타데이터" 섹션만 별도 카드에
   남기고, 나머지(측정 가능 조건·2단 게이트·미션 보상·판정 시뮬레이션)만 숨겼다.
   이 판단은 최종 응답의 `alerts`에 WARN으로 별도 보고했다.
2. **카드 경계(분류/기본정보/연결정보/보상·유효기간/디자인요소) 5개는 판단이 개입된
   설계다** — 2단계 지시문이 명시한 것은 3개 카드뿐이라, 나머지 필드(타입/등급·레벨/
   family_key/트라이브/컬렉션/카테고리/드랍가중치)를 문제정의 섹션이 이미 언급한
   "분류"·"연결정보" 테마로 묶었다. 다른 경계 판단도 합리적일 수 있어 리뷰에서 조정
   여지를 남긴다.
