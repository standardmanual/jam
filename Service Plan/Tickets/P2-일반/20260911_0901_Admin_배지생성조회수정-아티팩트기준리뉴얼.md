# [Admin] 배지 생성·조회·수정 화면 — 아티팩트 기준 리뉴얼

## 배경 / 문제 정의

티켓 [20260911_0202](20260911_0202_Admin_배지생성수정화면-타입별개편.md)로 `BadgeForm.tsx`를
5개 카드와 타입별 조건부 렌더링으로 1차 개편했다. 이후 사용자와 아티팩트로 전체 폼을 다시
설계했고, 이번 티켓은 그 설계를 실제 화면에 옮긴다.

- **설계 원본(목업)**: `Service Plan/Assets/20260911_badge-form-renewal-prototype.html`
  (브라우저로 열면 동작한다. 공유 링크: https://claude.ai/code/artifact/f171b3fb-4f35-4a35-bc7f-66b77f5813e2)
- 목업은 claude.ai 쪽 폰트와 색으로 그렸다. **구현은 어드민 shadcn 컴포넌트·테마 토큰을 그대로
  쓴다.** 목업에서 가져올 것은 구조, 그룹핑, 문구, 타입별 동작이고 색·폰트는 가져오지 않는다.

사용자가 제기한 획득 조건 영역의 문제는 네 가지다. 입력 필드가 많아 서로 구분하기 어렵고,
주제별 그룹이 없고, 플레이스홀더에 "예:" 접두사가 붙어 있고, 필드가 그리드로 정렬되지 않는다.
조사해 보니 현재 "기본 조건" 섹션 하나에 누적 목표, 한 번의 활동 기록(최소 속도·페이스·이동
시간), 필터(종목·단일 활동)가 섞여 있고, 이 가운데 한 번의 활동 기록 필드는 "단일 활동 지표"
섹션과도 겹친다.

  바뀔 때 `admin_category='jam'`을 비우는 처리로 해소한다.

## 상세 요구사항

### A. 공통 레이아웃 (생성·수정·조회 3화면)

1. **2단 구성**: 왼쪽은 섹션 카드 열, 오른쪽은 `sticky` 레일로 둔다. 레일에는 미리보기, 섹션
   목차, 액션 버튼이 들어간다. `lg` 미만 폭에서는 1단으로 접고 레일을 섹션 열 위로 올린다.
2. **섹션 순서**: 분류 → 기본 정보 → 획득 조건(아이템은 "드랍 조건") → 연결 정보 →
   보상·유효기간 → 디자인. 각 섹션 머리에는 제목, 한 줄 설명, 상태 배지를 둔다.
3. **섹션 목차**(레일): 섹션마다 상태를 보여 주고 누르면 해당 섹션으로 이동한다. 상태 값은
   완료, 필수 N개 남음, N개 설정, 선택, 이미지 필요 등이다. 타입 때문에 숨긴 섹션은 목차에서도
   숨긴다.

### B. 생성·수정 폼 (`BadgeForm.tsx`, `new/page.tsx`, `[id]/edit/page.tsx`)

**분류**
- 배지 타입은 3칸 세그먼트(액티비티/체크인/아이템)로 고르고, 각 칸 아래에 한 줄 설명을 붙인다.
- 액티비티를 고르면 "분류" 태그 행이 나온다. 태그는 러닝·사이클·트레일러닝·하이킹·걷기(한글
  라벨)와 JAM!이다. 기존의 종목·JAM! 상호배타 로직은 유지한다. **액티비티이고 JAM!이 아니면
  종목을 1개 이상 고르도록 검증한다**(2314 해소).
- 배지 종류(등급형/레벨형)는 액티비티에서만 보인다. 레벨형이면 등급 대신 레벨 입력을 보여 준다.
- **타입이 `activity`에서 다른 타입으로 바뀌면 `adminCategory`를 비운다**(0233 해소).

**기본 정보**
- 이름과 설명을 넣는다. 설명에는 글자 수만 표시하고, 기존 데이터를 깨지 않도록 새 최대 길이
  제한은 두지 않는다. 계열 키는 수정 화면에서만 읽기 전용으로 보여 준다.
- **배지 이미지는 이 섹션에 두지 않고 디자인 섹션으로 옮긴다.**

**획득 조건** (JAM!·아이템·체크인 규칙은 아래 "타입별 동작" 참조)
- 섹션 맨 위에 발급 방식 세그먼트(조건 충족 시 자동 발급 / 미션 완료로만 지급)를 둔다. 값은
  기존 `condFields.missionReward`와 연결한다. 미션 모드에서는 조건 그룹을 흐리게 하고 안내문을
  띄운다. 기존의 노란 "미션 보상 배지" 체크박스 박스는 이 세그먼트로 대체한다.
- 필드 찾기 검색창을 둔다. 라벨로 필터링하고, 일치하는 필드가 있는 그룹을 펼친다.
- 설정한 조건은 요약 칩 줄로 보여 준다. 칩 문구는 기존 `formatConditionChips`를 재사용하고,
  칩을 누르면 해당 그룹이 펼쳐지며 그 위치로 이동한다.
- 그룹은 네이티브 `<details>`로 만든다. 머리에 설정 개수를 표시하고, 값이 있는 그룹만 처음부터
  펼친다.
- 그룹 재편은 **`conditionRegistry.ts`의 `CONDITION_FORM_SECTIONS`·`CONDITION_FORM_SECTION_LABEL`과
  각 필드의 `form.section`을 바꾸는 방식**으로 한다. 레지스트리를 유일한 출처로 두는 원칙은
  유지한다. 새 그룹과 필드 매핑은 아래와 같다.

| 그룹(키 예시) | 라벨 · 설명 | 필드 |
|---|---|---|
| `scope` | 대상 활동 · 어떤 활동만 셀지 좁혀요 | activity_type, day_of_week(현재 폼 입력이 없으면 추가하지 않는다), season, month, day_of_month, time_range(시작~끝 한 줄), temp_min_c/temp_max_c(한 줄) |
| `cumulative` | 누적 목표 · 가입 후 지금까지 얼마나 쌓였나요 | single_activity(맨 위 체크), distance_km, elevation_gain_m, 누적 이동시간, total_count, active_days_count, streak_days, daily_once_count |
| `single` | 한 번의 활동 기록 · 활동 1건에서 얼마나 해냈나요 | 소제목 3개로 나눈다. 거리·고도·시간(single_distance_km, single_elevation_m, duration_minutes, max_elevation_m), 속도·페이스(min_speed_kmh, max_speed_kmh, max_pace, negative_split), 센서 데이터(avg_heartrate_bpm, avg_watts, avg_cadence) |
| `period` | 기간 · 주기 · 정해진 기간 안에서 얼마나 꾸준했나요 | weekly_count, weekly_streak, 월간 활동 횟수, monthly_km, 주말 활동시간, season_count, season_count_all |
| `rhythm` | 휴식 · 간격 · 쉬고 돌아오는 리듬을 봐요 | 연속 후 휴식일, 장거리 후 휴식일, return_gap_days, interval_days, distinct_time_bands, activities_within_hours(기준 시간과 횟수 한 줄) |
| `record` | 개인 기록 비교 · 과거의 나를 넘어섰나요 | personal_record_break, personal_record_break_metric, month_over_month_ratio, vs_personal_average |
| `repeat` | 반복 획득 · 같은 조건을 몇 번 채워야 하나요 | repeat_count |
| `gate` | 획득 게이트 · 먼저 갖춰야 할 배지가 있나요 | 선행 배지, 교차 게이트 2종(또는), 미션 보상 배지 게이트(그리고). 기존 전용 블록을 유지한다 |
| `meta` | 사용량 지표 · 서비스를 얼마나 쓰는지로 판정해요 | follower_count, following_count, daily_sync_count. JAM! 배지일 때만 보인다 |

  위 표의 필드 이름은 목업 기준 표기다. 실제 레지스트리 키와 폼 state 키에 맞춰 대응시킨다.
  **폼 입력이 있는 레지스트리 필드는 빠짐없이 한 그룹에 들어가야 한다.** 목업에 없는 필드가
  나오면 가장 가까운 그룹에 넣고 완료 기록에 적는다.
- **플레이스홀더에서 "예:" 접두사를 모두 뺀다**(`예: 30` → `30`). 뒤에 붙은 설명
  (`예: 5:30 (값이 작을수록 빠름)`, `예: 8 · 여러 달은 6, 7`)은 help 문구로 옮긴다.
- **단위는 라벨 괄호에서 빼서 입력칸 안쪽 오른쪽 접미사로 옮긴다**(`최소 거리 (km)` →
  라벨 `누적 거리`, 접미사 `km`). 단위 값은 레지스트리의 `meta.unit`을 쓰고, 컨트롤 라벨에 단위가
  박혀 있으면 걷어낸다. 접미사는 `aria-describedby`로 입력과 연결한다.
- **그리드는 3열**로 한다(`grid-cols-1 sm:grid-cols-2 lg:grid-cols-3`). 체크박스와 짝 입력
  (시간대, 기온, 기준 시간과 횟수)은 여러 칸을 차지하게 한다.
- **필드 간 제약은 필드 옆에 바로 안내한다.** 연속 활동 후 휴식일은 연속 활동 일수가, 장거리 후
  휴식일은 한 번의 거리나 한 번의 이동시간이, 계절 활동 횟수는 계절이, 개인 기록 갱신은 비교
  지표가 함께 필요하다. 조건이 빠지면 해당 필드 아래에 빨간 한 줄 안내를 보여 준다. 저장을
  막는 최종 판정은 기존 검증(`validateCondition`·서버)을 그대로 따른다.
- 저장될 JSON 미리보기는 기본으로 접힌 `<details>`로 바꾼다. 판정 시뮬레이션 패널, 평가 대기·
  미지원·재현 불가·진행 미지원 경고(`Alert` warning variant)는 그대로 유지한다.

**연결 정보**
- 액티비티(JAM! 제외)는 소속 트라이브와 소속 컬렉션을 보여 준다.
- 아이템은 여기에 드랍 가중치와 상대 확률 안내(기존 로직)를 더한다.
- 체크인은 지점 카테고리와 연결된 지점 검색·목록(기존 로직)을 보여 준다.

**보상·유효기간**
- 포인트 보상 입력에는 `포인트` 접미사를 붙인다.
- 패치 구매는 체크박스를 켜야 가격 입력이 활성화되고, 가격 입력에는 `원` 접미사를 붙인다.
- 유효기간은 시작일~종료일을 한 줄에 둔다. 안내문은 기존처럼 아이템과 그 외 타입이 다르다.

**디자인**
- 배지 이미지(`ImageUploadField`)를 섹션 맨 위에 두고, 그 아래에 배경(`BackgroundGeneratorPreview`,
  배경색/애니메이션)을 둔다.

**레일**
- 레일에는 상세 화면 미리보기, 섹션 목차, 저장(등록)·취소·삭제 버튼을 둔다.
- 미리보기는 기존 `BadgeDetailPreviewFrame`을 재사용한다. 가능하면 `BackgroundGeneratorPreview`의
  `renderPreview`로 만들던 미리보기를 레일로 옮긴다. 상태를 끌어올리기가 지나치게 침습적이면
  배경 미리보기는 디자인 섹션에 두고, 레일에는 이미지·이름·등급·조건 요약만 담은 간단한 카드를
  둔다. 어느 쪽을 택했는지와 이유는 완료 기록에 적는다.
- 미리보기의 조건 줄은 기존 `PREVIEW_CONDITION_TEXT` 대신 실제 조건 요약(칩 문구 앞 2~3개)을
  보여 준다. 체크인은 "{지점명} 통과 시 획득", 미션 모드는 "미션 완료 시 지급"으로 표시한다.
- 저장을 누르면 누락 개수를 버튼 아래에 알리고, 첫 번째 누락 필드로 포커스와 스크롤을 옮긴다.
  누락 필드에는 `aria-invalid`를 붙인다.

**타입별 동작 (목업 기준)**

| 타입 | 분류 | 획득 조건 | 연결 정보 |
|---|---|---|---|
| 액티비티 | 분류 태그, 배지 종류 | 발급 방식 세그먼트, 8개 그룹(`meta` 제외) | 트라이브·컬렉션 |
| 액티비티 · JAM! | 분류 태그, 배지 종류 | `meta` 그룹만. 발급 방식·게이트·시뮬레이션은 숨김 | **숨김** |
| 아이템 | 등급만 | 제목 "드랍 조건". 누적 조건 5개(`CUMULATIVE_CONDITION_KEYS`)는 비활성화하고 안내. 발급 방식은 숨김 | 트라이브·컬렉션·드랍 가중치 |
| 체크인 | 등급만 | 섹션 숨김 | 지점 카테고리·연결된 지점 |

- **숨긴 입력의 기존 값은 저장 페이로드에서 바꾸지 않는다.** JAM!의 `tribe_id`·`item_book_id`,
  아이템의 `missionReward` 값이 여기에 해당한다. 화면에서만 숨기고, 저장 로직의 기존 규칙
  (체크인에서 tribe·item_book을 null로 보내는 것 등)은 그대로 둔다.

### C. 조회 화면 (`BadgeDetail.tsx`, `[id]/page.tsx`)

1. 폼과 같은 섹션 순서·레일 구조로 바꾸고, 각 섹션은 **읽기 전용 라벨-값 그리드**로 만든다.
   - **분류**: 타입, 분류(한글 종목명 또는 JAM!), 배지 종류, 등급 또는 레벨을 보여 준다.
     현재처럼 `running` 같은 원문 키를 그대로 노출하지 않는다.
   - **기본 정보**: 이름, 설명, 계열 키를 보여 준다.
   - **획득 조건**: 폼과 같은 그룹 제목 아래에 설정된 조건만 표시한다. 문구는 기존
     `formatConditionDetail`을 재사용하고, 미션 보상 배지이면 그 사실을 표시한다. 체크인은 섹션을
     숨긴다.
   - **연결 정보**: 액티비티·아이템은 트라이브·컬렉션(아이템은 드랍 가중치 포함), 체크인은 지점
     카테고리와 연결된 지점 목록(이름·카테고리·반경)을 보여 준다. 연결된 지점은 `[id]/page.tsx`
     서버에서 조회한다.
   - **보상·유효기간**: 포인트, 패치, 기간을 보여 준다.
   - **디자인**: 이미지와 배경(색 견본 또는 "애니메이션")을 보여 준다.
2. 레일에는 미리보기(`BadgeDetailPreviewFrame` 재사용 권장), 수정 버튼, 활성·비활성 토글
   (`BadgeActiveToggleButton`), 삭제(기존 `AlertDialog`) 버튼을 둔다.

### D. 보완 — 타입 전환 시 숨겨진 값 정리 (2026-09-11 추가, 리뉴얼 파이프라인 착수 후 합의)

B의 "숨긴 입력의 기존 값은 저장 페이로드에서 바꾸지 않는다" 원칙은 기존 배지를 수정할 때는
안전하다. 하지만 **타입을 바꾸는 순간 숨겨진 값이 딸려 간다**. 그래서 아래 세 가지를 보완한다.
리뉴얼 결과가 나온 뒤 오케스트레이터가 review 브랜치 위에 직접 커밋하고, 게이트 리뷰어에게
보완분만 따로 검증받는다.

1. **(필수) 타입을 아이템으로 바꾸면 `missionReward`를 해제한다.** 아이템 배지에서
   `{mission_reward: true}`는 드랍 엔진에서 "평가할 수 있는 조건 없음"으로 판정되어 드랍
   후보에서 영구히 빠진다(`drop-engine/index.ts`의 `isDroppableForActivity`). 전환 스위치가
   숨겨져 있으면 원인이 화면에 보이지 않는다. 실데이터 기준으로 `mission_reward`가 켜진 아이템
   배지는 0건이다(2026-09-11 조회).
2. **(필수, 사용성) 아이템 배지에서 막는 조건 목록을 드랍 엔진 기준으로 맞춘다.** 폼의
   `CUMULATIVE_CONDITION_KEYS`는 5개인데, 드랍 엔진의 `CUMULATIVE_CONDITION_FIELDS`는 11개다.
   폼에는 누적 거리, 누적 고도, 휴식 4종이 빠져 있다. 서버 저장 검증
   (`badge-validation.ts`의 `findCumulativeConditionError`)은 이미 11개 목록을 써서 저장을
   거절하므로 데이터가 잘못 저장되지는 않는다. 다만 폼에서는 입력을 허용하고 저장을 누른 뒤에야
   서버 오류로 거절되는 불일치가 있다. 폼 상수를 복제하지 말고, 서버 전용 의존이 없는 모듈로
   목록을 옮겨 드랍 엔진·서버 검증·폼이 같은 목록을 가져다 쓰게 한다.
3. **(선택 → 적용) 타입·분류가 JAM!으로 바뀌면 트라이브와 컬렉션을 비운다.** 액티비티
   배지의 `tribe_id`·`item_book_id`는 발급 판정에 쓰이지 않으므로 기능 영향은 없다. 화면에
   보이지 않는 값이 DB에 남지 않도록 정리하는 조치다. JAM! 배지 3종은 현재 둘 다 `null`이다.

### 주요 의사결정 / 핵심 메모

- **게이트 WARN 사유와 처리**
  1. 오류 표시(`aria-invalid`)가 이름·설명에만 붙었다. 보완 커밋에서 `aria-describedby` 연결로
     해소했다. 분류 태그·이미지는 버튼이라 `aria-invalid`가 ARIA 규격상 지원되지 않는다.

  3. 보완 D 미반영은 오케스트레이터 보완 커밋으로 처리했다(게이트 PASS).
