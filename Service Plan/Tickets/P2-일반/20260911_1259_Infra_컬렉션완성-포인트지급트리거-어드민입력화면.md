# [Infra] 컬렉션(아이템북) 완성 시 포인트 지급 트리거 + 어드민 입력 화면 추가

## 배경 / 문제 정의

현재 잼 포인트는 ①배지 발급(`badges.point_reward`) ②미션 완료(`missions.reward_points`)
③운영자 수동 지급/회수, 세 경로로만 지급된다(`Service Plan/Specs/PRD/PointSystem/
OBJECT_MODEL.md` 44행). 컬렉션(아이템북) 완성은 지급 트리거 목록에 없고, 실제로
`slot_item_into_book()` RPC(`jam-web/supabase/migrations/111_item_slot_atomic_rpc.sql`
127~139행)도 슬롯이 다 채워지면 `user_item_book_completions`에 완성 기록만 INSERT할 뿐
`award_points()` 호출이 없다.

사용자 요청: 컬렉션 완성 시 포인트를 지급하는 트리거를 추가하고, 컬렉션(아이템북)
생성·상세(수정) 화면에서 그 지급액을 운영자가 입력할 수 있게 한다.

## 상세 요구사항

### 서비스/코드베이스 관점

- **스키마**
  - `item_books` 테이블에 `reward_points INTEGER NOT NULL DEFAULT 0` 컬럼 추가
    (배지의 `point_reward`와 동일한 명명·기본값 규칙).
  - `point_transactions`에 `source_item_book_id UUID REFERENCES item_books(id)` 컬럼 추가
    (기존 `source_badge_id`/`source_mission_id`와 동일한 출처 추적 패턴).
- **`award_points()` RPC 확장** (`080_point_system_renumbered_from_045_duplicate.sql` 참고)
  - `p_source_item_book_id UUID DEFAULT NULL` 파라미터 추가, INSERT 문에 반영.
  - 기존 시그니처 호출부(배지·미션 지급 경로)는 하위 호환 유지(신규 파라미터는 기본값 NULL).
- **`slot_item_into_book()` RPC 수정**
  - 완성 판정(`v_total_badges > 0 AND v_slotted_count >= v_total_badges`) 분기 안에서
    `user_item_book_completions` INSERT가 **실제로 새로 완성된 순간**(최초 1회)에만
    `award_points()`를 호출하도록 분기 — `ON CONFLICT DO NOTHING`이 실제로 아무 것도
    하지 않은 경우(이미 완성된 컬렉션에 재슬롯 등 재진입)에는 중복 지급하면 안 된다.
    `INSERT ... ON CONFLICT DO NOTHING`의 영향 행 수(`FOUND` 또는 `GET DIAGNOSTICS`)로
    판별.
  - `item_books.reward_points`가 0이면 지급 자체를 생략(배지 패턴과 동일 — "0이면
    지급하지 않는다").
  - 지급 사유(`p_reason`)는 기존 배지/미션 지급 문구 규칙에 맞춰 명확히 표기
    (예: "컬렉션 완성" 등 — 정확한 문구는 구현 시 기존 `point_transactions.reason` 값
    표기 관례를 확인해서 맞춘다).
- **소급 지급 없음** — `OBJECT_MODEL.md` 원칙(51행)과 동일하게, 이 기능 배포 전에 이미
  `user_item_book_completions`에 쌓여 있는 기존 완성 기록에는 소급 지급하지 않는다.
- **타입 재생성**: 마이그레이션 반영 후 `npm run db:types`(현재 CLI 미설치 상태 —
  `project_db_types_cli_missing` 메모리 참고, MCP `generate_typescript_types`로 대조
  확인 필요) — 생성 타입이 컬럼 인식 못 하면 `src/types/database.generated.ts` 수동
  동기화 필요.

### 주요 의사결정 / 핵심 메모
- `slot_item_into_book()`이 `award_points()`를 직접 SQL 레벨에서 호출하므로,
  TS 레이어의 `lib/points/index.ts`(`awardPoints()`)가 담당하는 알림(`recordActivityRecap`,
  `createNotification`) 로직은 이번 지급 경로에 타지 않는다. 티켓 범위가 "DB 트리거 +
  어드민 입력 화면"으로 명시돼 있고 알림 요구사항이 없어 이번 범위에서는 알림을 추가하지
  않았다 — 유저가 컬렉션 완성 포인트를 받아도 별도 알림/피드 문구는 뜨지 않는다. 필요하면
  후속 티켓으로 검토.
- **1차 구현의 회귀 버그와 수정**: `award_points()`에 파라미터를 추가하며 `CREATE OR REPLACE
  FUNCTION`만 쓰면, PostgreSQL은 파라미터 개수가 다른 경우 기존 함수를 교체하지 않고 새
  오버로드를 추가한다. 1차 구현은 이 사실을 놓쳐 7-인자(기존)·8-인자(신규) 함수가 공존하게
  만들었고, 그러면 `lib/points/index.ts`의 기존 7개 명명 인자 호출이 두 오버로드 모두에
  들어맞아 `function award_points(...) is not unique` 에러로 배지·미션·믹스·어드민 지급 등
  기존 포인트 지급 경로 전체가 마이그레이션 반영 즉시 깨질 뻔했다. 게이트 리뷰가 1차 PASS를
  줬지만 오케스트레이터가 SQL을 직접 읽고 발견해 반려했고, 재시도에서 8-인자 `CREATE OR
  REPLACE FUNCTION` 직전에 `DROP FUNCTION IF EXISTS public.award_points(UUID, INTEGER, TEXT,
  UUID, UUID, TEXT, TEXT);`를 추가해 오버로드가 하나만 남도록 고쳤다. 실 DB 반영 후
  `pg_get_function_identity_arguments`로 오버로드가 8-인자 1개뿐임을, `DO $$ ... $$` 블록으로
  7개 명명 인자 호출이 모호성 없이 성공함을 직접 확인했다(테스트 결과 참고). 이 사고 경위와
  재발 방지 규칙은 `Service Plan/Specs/DEV_PROCESS_GUARDRAILS.md` 패턴 14로 별도 기록했다.
- 같은 사고에서 개선 리뷰(progressive-reviewer)가 "어드민 UI 필드·API 페이로드·타입 정의가
  누락됐다"는 반대 방향의 오탐도 냈는데, 오케스트레이터가 `git diff origin/staging..review
  브랜치`로 직접 대조한 결과 전부 사실이 아니었다(정상 구현 상태). 게이트·개선 리뷰 결과는
  판정만 보지 말고 필요 시 실제 diff로 재검증해야 한다는 근거 사례로 남긴다.
