# [Feature] 홈 피드 랭킹보드 노출

> `to-prd` 스킬(탐색 → 테스트 경계 스케치 → PRD 작성) 프로세스로 작성했다. 원본 스킬은
> 완성된 PRD를 이슈 트래커에 발행하도록 되어 있으나, JAM!은 이슈 트래커 대신 이 티켓
> 체계를 쓰므로 그 부분만 `jam-docs` 규칙으로 바꿔 적용했다. 원본 스킬 지침에 따라
> **파일 경로·코드 스니펫은 의도적으로 넣지 않았다** — 빨리 낡기 때문에, 실제 구현
> 시점에 코드를 보고 정한다.

## 배경 / 문제 정의

지금은 미션의 순위 경쟁 현황을 미션 상세 화면(`/missions/[id]/status`)에 들어가야만 볼 수
있다. 앱의 첫 화면인 홈 피드(투데이 컨텐츠)에는 노출되지 않아, 경쟁 요소가 있다는 사실
자체를 미션 상세를 열어보기 전까지는 알기 어렵다. 운영자 입장에서도 "지금 이 미션 경쟁이
불붙었다"는 걸 홈 화면에서 큐레이션해 보여줄 방법이 없다.

목표는 운영자가 어드민에서 특정 조건의 랭킹을 만들어두면, 투데이 컨텐츠 카드 하나로
홈 피드에 노출할 수 있게 하는 것이다. 다만 이번 요청에는 지금 바로 만들 수 있는 범위와,
아직 뒷받침하는 기능이 없어 별도 설계가 필요한 범위가 섞여 있다 — 이 둘을 가르는 것이
이 PRD의 핵심 목적이다.

## 상세 요구사항

### User Stories

**운영자(어드민)**
1. As an 운영자, I want 특정 미션을 골라 랭킹모드를 생성, so that 그 미션의 순위를 홈
   피드에도 노출할 수 있다.
2. As an 운영자, I want 랭킹모드의 미션 선택 목록에 랭킹형이 아닌 미션(성취형·개인형)이
   아예 안 뜨길, so that 순위 개념이 없는 미션을 실수로 랭킹으로 노출하지 않는다.
3. As an 운영자, I want 랭킹 집계 시작·종료 일시를 지정, so that 원하는 기간의 데이터만
   반영된 순위를 보여줄 수 있다.
4. As an 운영자, I want 투데이 컨텐츠 카드를 만들 때 카드 타입 중 하나로 "랭킹보드"를
   고르고 만들어둔 랭킹모드를 연결, so that 원하는 발행 일정에 맞춰 노출할 수 있다.
5. As an 운영자, I want 랭킹보드 카드에 제목·설명을 직접 입력, so that 어떤 경쟁인지
   맥락을 유저에게 전달할 수 있다.
6. As an 운영자, I want 발행 전에 랭킹보드가 실제로 어떻게 보일지 미리보기로 확인,
   so that 데이터가 비정상인 채로 유저에게 노출되는 걸 막을 수 있다.
7. As an 운영자, I want 랭킹모드 하나를 여러 투데이카드에서 재사용, so that 같은 경쟁을
   다른 시점에 다시 노출할 때 매번 새로 설정하지 않아도 된다.
8. As an 운영자, I want 랭킹모드에 연결된 미션이 삭제되거나 랭킹형이 아니게 바뀌면
   경고를 받길, so that 깨진 랭킹보드가 그대로 노출되는 사고를 막을 수 있다.

**앱 유저**
9. As an 앱 유저, I want 홈 피드에서 랭킹보드 카드를 보면, so that 미션 상세로 들어가지
   않아도 지금 순위 경쟁이 어떻게 돌아가는지 바로 알 수 있다.
10. As an 앱 유저, I want 랭킹보드 카드를 탭하면 해당 미션의 랭킹 화면으로 이동,
    so that 더 자세한 순위와 내 진행 내역을 볼 수 있다.
11. As an 앱 유저, I want 랭킹 리스트에서 내 순위가 눈에 띄게 표시되길, so that 내
    위치를 빠르게 파악할 수 있다(기존 미션 상세 랭킹 화면과 동일한 동작).
12. As an 앱 유저, I want 랭킹보드가 1·2·3위 강조 그래프 없이 리스트 형태로만 보이길,
    so that 홈 피드의 간결한 카드 레이아웃과 어울린다.
13. As an 앱 유저, I want 집계 기간이 끝난 뒤에도 랭킹보드가 최종 결과를 그대로
    유지해서 보여주길, so that 경쟁이 끝난 뒤에도 결과를 확인할 수 있다.

**운영자(어드민) — 유저 직접 지정 랭킹**
14. As an 운영자, I want 여러 유저를 관리자 화면에서 직접 검색해 지정, so that 미션
    참가자가 아니라 내가 고른 유저들만으로 랭킹을 만들 수 있다.
15. As an 운영자, I want 지정한 유저 목록을 정렬할 지표를, 액티비티 배지를 만들 때
    쓰는 조건값(누적 거리·연속 출석일수·한 번의 활동 기록·개인 기록 경신 등) 중에서
    고르길, so that 배지 설계에 쓰는 것과 같은 폭넓은 기준으로 경쟁을 보여줄 수 있다.
16. As an 운영자, I want 지정한 유저 중 일부를 나중에 빼거나 새 유저를 추가, so that
    이벤트 진행 중에도 대상 목록을 조정할 수 있다.

**운영자(어드민) — 배지 조건 기반 지표**
17. As an 운영자, I want 정렬 지표를 고를 때 배지 만들 때 보던 것과 같은 필드 검색·
    그룹(대상 활동/누적 목표/한 번의 활동 기록/기간·주기/휴식·간격/개인 기록 비교
    등)으로 찾을 수 있길, so that 새로 익힐 필요 없이 익숙한 방식으로 원하는 지표를
    찾을 수 있다.
18. As an 운영자, I want 배지 보유 개수를 정렬 지표로 쓸 때 배지 타입(액티비티/아이템/
    체크인)을 먼저 고르길, so that "액티비티 배지를 가장 많이 모은 사람" 같은 구체적인
    경쟁을 만들 수 있다.

**(참고용 — 여전히 Out of Scope인 story)**
19. As an 운영자, I want 여러 지표를 가중치를 줘서 하나의 점수로 조합, so that "배지
    개수와 누적 거리를 함께 반영한" 복합 랭킹을 만들 수 있다. — 조합 수식이 아직
    정해지지 않아 이번 범위는 지표 하나만 선택하는 것으로 한정한다(뒤 Out of Scope
    참고).

### 서비스/코드베이스 관점

- 지금 랭킹은 항상 특정 미션에 종속된 속성(랭킹형/성취형/개인형을 가르는 표시 방식
  설정)으로만 존재하고, 랭킹 자체가 독립된 개념으로 존재하지 않는다. 이번 작업의
  핵심은 "랭킹모드"라는 새 독립 엔티티를 만들어, 랭킹이 미션에 종속되지 않고도 존재할
  수 있게 하는 것이다.
- **모델 재정리** — 처음 요청에서는 "미션 선택"·"유저 선택"·"배지 선택"을 서로 다른
  3갈래 랭킹 방식으로 다뤘는데, 뜯어보면 실제로는 두 축의 조합이다.
  - **대상을 무엇으로 고를지(target)**: 미션 참가자 전원(기존), 또는 운영자가 수동으로
    지정한 유저 목록(신규).
  - **무엇으로 정렬할지(metric)**: 미션 참가자를 대상으로 할 때는 지금처럼 미션 진행도
    하나로 정해지지만, 수동 지정 유저를 대상으로 할 때는 배지 보유 개수·동기화 수·
    팔로워 수·누적 달리기 거리 같은 지표 중 하나를 운영자가 고른다. "배지 선택" 요구는
    사실 이 지표 중 하나(배지 보유 개수)를 고를 때 배지 타입을 함께 지정하는 것에
    해당한다 — 별도의 세 번째 대상 선정 방식이 아니다.
- **지표 풀은 "액티비티 배지를 만들 때 쓰는 조건값 전체"로 정했다.** 이 조건값들은
  이미 배지 조건 레지스트리라는 하나의 목록에 정리되어 있고(오늘 오전 배지 화면
  리뉴얼에서 9개 그룹으로 재편한 바로 그 목록 — 대상 활동·누적 목표·한 번의 활동
  기록·기간·주기·휴식·간격·개인 기록 비교·반복 획득·획득 게이트·사용량 지표),
  정렬 지표 선택지도 새로 설계하지 않고 이 목록을 그대로 가져다 쓴다.
- **다만 "조건값"과 "정렬 지표"는 성격이 다르다.** 배지 조건은 "이 값이 기준치를
  넘었는가"만 boolean으로 보면 되지만, 랭킹은 그 값 자체를 유저 간에 비교해서
  순서를 매겨야 한다. 레지스트리의 필드 중 상당수는 애초에 하나의 숫자로 떨어지는
  성격이 아니다 — 예를 들어 "어떤 종목만 셀지"를 정하는 필드는 값이 아니라 필터고,
  "선행 배지를 가지고 있는지"를 보는 필드는 관계(보유 여부)를 보는 것이지 크기 비교
  대상이 아니다. 그러니 "모든 조건값을 선택할 수 있게" 한다는 건 레지스트리 전체를
  그대로 다 옮기는 게 아니라, **그중 유저 한 명당 숫자 하나로 떨어지는 필드만** 정렬
  지표 후보로 추리는 작업이 함께 필요하다.
- **지표 값을 구하는 방법이 생각보다 많이 이미 있다는 걸 재확인했다.** 배지 판정
  로직 자체(조건 충족 여부만 보는 함수)와는 별개로, "화면에 진행률을 보여주기 위한"
  용도로 이미 배지 판정과 완전히 분리된 순수 계산 계층이 있다 — 유저의 활동 이력만
  넣으면 판정 로직 없이 누적 거리·누적 고도·누적 시간·총 횟수·활동일수·연속
  출석일수 같은 값들을 한 번에 계산해서 돌려준다. 이 계층이 다루는 필드가 레지스트리
  9개 그룹 중 "누적 목표"·"한 번의 활동 기록" 그룹 대부분과 겹친다 — 즉 지표로 쓸
  값을 구하는 계산 자체는 상당 부분 이미 만들어져 있고, 랭킹에서 할 일은 그걸
  가져다가 "필드 하나를 고르면 그 값을 돌려주는" 형태로 다시 감싸는 것에 가깝다.
  팔로워 수·동기화 수처럼 활동 이력과 무관한 지표는 이미 별도 경로로 값을 구하고
  있다는 것도 이전에 확인한 그대로다.
- **그래도 전부가 이렇게 수월하지는 않다.** 레지스트리 필드 중 세 부류는 이번
  범위에서 지표로 쓰기 어렵다: ① 아직 엔진이 실제로 계산하지 않는 필드(설정은
  가능해도 판정에 쓰인 적이 없는 것들), ② 필드 하나만으로는 값이 정해지지 않고
  추가 설정(예: "몇 시간 안에"의 그 시간 값, "어떤 지표와 비교할지"의 그 지표 선택)이
  같이 있어야 값이 나오는 필드, ③ 선행 배지·교차 조건처럼 관계를 보는 필드. 이런
  필드들은 이번 1차 범위에서는 지표 선택지에서 제외하고, 뒤 Out of Scope에 정리한다.
- **"누적값"이 아니라 "활동 한 번의 기록"이나 "과거 대비 비교"를 보는 필드는 유저
  한 명당 대표값을 어떻게 뽑을지 결정이 필요하다.** 예를 들어 "한 번에 가장 멀리
  달린 기록"류 필드는 "역대 최고 기록"으로 뽑을 수도 있고 "가장 최근 활동의 기록"으로
  뽑을 수도 있는데, 흥미롭게도 이 두 가지 관례가 이미 다른 목적(배지 판정은 역대
  최고, 화면 진행률 표시는 최근 기록)으로 코드에 각각 존재한다. 랭킹에 어느 쪽을
  쓸지는 새로 계산 로직을 짜야 하는 문제가 아니라 어느 기존 관례를 따를지 고르는
  문제에 가깝다 — 다만 그 선택 자체는 이 PRD가 정할 수 있는 게 아니라 제품 판단이
  필요하다(뒤 Out of Scope 참고).
- 미션 기반 랭킹모드의 순위 계산은 지금 미션 상세 화면이 쓰는 비교 규칙(완료 여부 →
  완료 시각 → 진행도)을 그대로 따른다. 새로 발명하지 않는다.
- 투데이 컨텐츠는 이미 "카드 종류에 따라 필요한 참조 데이터가 다른" 구조로 여러
  종류의 카드를 다루고 있다. 랭킹보드도 그 카드 종류 중 하나로 자연스럽게 추가한다.

### UI/UX 관점

- **MODULAR 탐색·재사용 판정(2026-09-11, `/jam-design` 절차)**: 디자인 시스템 컴포넌트
  전체(43종)를 확인한 결과, "순위 리스트"에 정확히 대응하는 완성형 컴포넌트는 없다.
  다만 조립에 쓸 조각은 이미 있다 — 행 레이아웃 뼈대를 맡는 `ListRowCard`(patterns,
  아이콘·제목·보조텍스트·trailing을 받는 단일 행 primitive, 배열 반복은 호출부
  책임)와 진행값 그래프를 맡는 `ProgressBar`(feedback, 이미 미션 상세 랭킹 바의
  실측 레퍼런스로 등록돼 있음) 둘 다 신규 생성하지 않고 그대로 재사용한다.
  - 지금 미션 상세 화면의 순위 행(`RankingListRow`, `MissionStatusClient.tsx` 파일
    로컬 컴포넌트)이 이 두 조각을 조합해 순위 번호·아바타·이름·진행값을 그리고
    있는데, `ListRowCard`는 MODULAR 원본이 아니라 서비스 로컬에 이미 포팅된 사본
    (`@/components/ui/ListRowCard`)을 쓰고 있었다. 이번에 데이터 외부 주입 형태로
    분리하는 작업(아래 UI/UX 관점 다음 항목, Implementation Decisions)을 할 때는
    이 포팅 사본을 그대로 재사용하면 된다.
  - 이 조합(순위 행) 자체를 MODULAR 신규 컴포넌트로 승격할지도 검토했다 — 재사용성
    (미션 상세 + 홈 피드 랭킹보드, 2곳 이상) · 안정성(이미 프로덕션에서 검증된 디자인)
    · 토큰 준수(재료 두 조각이 이미 MODULAR)는 충족하는 편이나, 범용성(진행값
    포맷이 지표마다 다름 — 거리·횟수·팔로워 수 등)은 이번에 분리하면서 포맷터를
    외부 주입받는 형태로 정리해야 비로소 갖춰진다. **이번 범위에서 승격까지
    강제하지 않고**, 서비스 레이어에서 먼저 범용화된 형태로 구현한다 — `/jam-design`
    선순환 원칙대로 승격 여부는 개선 리뷰 단계 제안에 맡긴다. 다만 구현 시 포맷터
    외부 주입 등으로 도메인 결합을 최소화해 두면 이후 승격이 쉬워진다.
- 랭킹 리스트 UI 자체(순위·이름·진행값·본인 강조)는 지금 미션 상세 화면의 것을
  최대한 그대로 따르되, 1·2·3위를 그래프로 강조하는 부분만 뺀 형태로 홈 피드 카드에
  얹는다. "그대로 재사용"이라기보다는 "리스트 부분만 뽑아서 두 화면에서 같이 쓰는"
  형태에 가깝다 — 지금 그 UI는 미션 상세 화면 전용으로 짜여 있어 데이터를 그 화면이
  직접 가져오는 구조라서, 홈 피드에서도 쓰려면 데이터를 바깥에서 넣어주는 방식으로
  바꾸는 작업이 먼저 필요하다(뒤 Implementation Decisions 참고).
- 어드민에서 "배지 선택 + 조건값"·"유저 선택 + 상태값 조합" 같은 조건 입력 UI를 새로
  만들 때 참고할 수 있는 기존 조건 입력 화면 패턴(필드를 목록으로 선언하면 폼이
  자동으로 그려지는 방식)이 이미 배지 조건 설정 화면에 있다 — 이번 범위(미션 선택)에는
  해당하지 않지만, Out of Scope 항목을 나중에 구현할 때 이 패턴을 그대로 본뜰 수 있다.

## 구현 계획

**모듈 구성**
- 랭킹 계산을 담당하는 새 도메인 모듈을 하나 둔다. 이 모듈은 "랭킹모드 정의 + 대상
  데이터"를 받아 "순위가 매겨진 목록"을 돌려주는 순수 계산 계층으로, 대상 선정
  방식(미션 참가자 / 수동 지정 유저)과 정렬 지표(미션 진행도 / 배지 조건 레지스트리
  필드 중 하나 / 배지 보유 개수)를 서로 독립적으로 조합할 수 있게 나눈다.
  - 미션 참가자 + 미션 진행도 조합은 지금 있는 순위 비교 규칙을 그대로 감싸 재사용한다.
  - 수동 지정 유저 + 지표 하나 조합은, 지정된 유저 각각에 대해 그 지표의 현재 값을
    구해서 내림차순(지표에 따라 작을수록 좋은 경우도 있다 — 예: 페이스)으로
    정렬하는 형태다. 동점 처리 규칙은 구현 시점에 정한다.
  - **지표별 현재값 조회 — 필드 키 하나를 받아 "이 유저의 지금 값"을 돌려주는
    조회 계층을 새로 만든다.** 통째로 새로 짜는 게 아니라, 이미 있는 두 갈래 계산
    로직을 필드 키로 갈아타는 하나의 창구로 감싸는 작업에 가깝다: 활동 이력 기반
    지표(누적 거리 등, 배지 화면 진행률 표시가 쓰는 것과 같은 계산)와 활동 이력과
    무관한 지표(팔로워 수·동기화 수 등, 별도 경로로 이미 값을 구하고 있는 것). 배지
    보유 개수는 이 두 갈래 어디에도 속하지 않는 별도 조회(타입별 카운트)로 둔다.
  - **1차로 지원하는 지표 범위는 레지스트리 전체가 아니라, 위 조회 계층으로 바로
    값을 낼 수 있는 필드로 한정한다.** 주로 누적 목표·한 번의 활동 기록 그룹과
    사용량 지표, 배지 보유 개수가 여기 해당한다. 추가 설정이 있어야 값이 정해지는
    필드(예: "몇 시간 안에"류)나 아직 엔진이 계산해 본 적 없는 필드는 1차에서
    제외한다(뒤 Out of Scope). 다만 **어드민 화면의 지표 선택지 자체는 레지스트리
    전체 필드·그룹 구성을 그대로 보여주되, 1차에서 지원하지 않는 필드는 선택은
    가능해도 비활성 처리(사유 안내 포함)하는 방식을 권장한다** — 그래야 이후 지표를
    하나씩 추가할 때 선택 UI를 다시 만들 필요 없이 활성화만 하면 된다.
- 투데이 컨텐츠 쪽 모듈에 랭킹보드용 카드 종류를 하나 추가한다. 기존 카드 종류들과
  동일하게 "카드 종류 → 필요한 참조 필드 → 노출 방식"을 매핑하는 방식을 그대로 따른다.
- 어드민에 "랭킹모드 관리" 화면을 신설한다:
  - 대상 선정 방식으로 "미션 참가자" 또는 "유저 직접 지정"을 고른다.
  - 미션 참가자를 고르면 랭킹형 미션 중에서 하나를 선택한다(정렬 지표는 자동으로
    진행도가 된다).
  - 유저 직접 지정을 고르면, 유저를 검색해 여러 명을 목록에 담는 입력(기존 배지
    선택 화면의 "검색해서 목록에 담는" 패턴을 그대로 참고할 수 있다)과, 정렬 지표를
    고르는 선택지를 둔다. **이 지표 선택지는 배지 조건 입력 화면의 필드 검색·그룹
    구조(대상 활동/누적 목표/한 번의 활동 기록/기간·주기/…)를 그대로 재사용해,
    운영자가 배지를 만들 때 보던 것과 같은 화면에서 지표를 고르게 한다.** 지표로
    배지 보유 개수를 고르면 배지 타입(액티비티/아이템/체크인)을 추가로 고르게 한다.
  - 집계 시작·종료 일시 입력은 대상 선정 방식과 무관하게 공통으로 둔다.
- 어드민 투데이 컨텐츠 생성 화면에 카드 종류 선택지로 "랭킹보드"를 추가하고, 선택 시
  기존에 만든 랭킹모드 중 하나를 고르는 입력을 추가한다.
- 랭킹 리스트를 보여주는 화면 조각을 미션 상세 전용 구현에서 분리해, 데이터(순위가
  매겨진 목록)를 바깥에서 주입받는 형태로 만든다. 상단 강조 그래프 노출 여부는
  옵션으로 분리해서, 랭킹보드 카드에서는 리스트만 쓴다. 이 분리·리팩토링이 미션 상세
  화면 자체의 기존 동작을 바꾸면 안 된다. 이 리스트는 대상이 미션 참가자든 수동 지정
  유저든 "순위 매겨진 목록"이라는 동일한 형태만 받으면 그대로 동작해야 한다.

**인터페이스 결정**
- 랭킹모드: 제목, 대상 선정 방식(미션 참가자 / 유저 직접 지정), 대상 설정(미션
  참가자면 미션 하나 참조, 유저 직접 지정이면 유저 id 목록), 정렬 지표(미션
  참가자일 때는 고정으로 진행도, 유저 직접 지정일 때는 배지 조건 레지스트리의 필드
  키 하나 — 예: `distance_km`, `streak_days` — 또는 배지 보유 개수), 지표가 배지
  보유 개수일 때의 배지 타입, 집계 시작·종료 일시, 공개할 순위 인원 제한(선택, 미션
  상세 화면에 이미 있는 개념을 그대로 가져옴), 생성자, 생성일.
- **정렬 지표를 "레지스트리의 필드 키"로 저장한다는 게 핵심 결정이다.** 지표 종류를
  랭킹모드 전용으로 새로 열거하지 않고, 이미 있는 배지 조건 필드 목록을 그대로
  참조한다 — 이렇게 하면 배지 조건이 늘어날 때(새 조건 필드 추가) 랭킹 지표
  선택지도 자동으로 함께 늘어난다. 다만 그 필드가 "1차로 실제 계산 가능한지"는
  별도 플래그(또는 화이트리스트)로 관리해서, 선택은 보이되 계산이 안 되는 필드는
  안내와 함께 막는다.
- 대상 설정과 정렬 지표 설정은 조합에 따라 담는 내용이 달라지는 유연한 구조로 둬서,
  이후 대상 선정 방식이 늘거나("가중치 조합" 등) 지표가 늘 때 랭킹모드 테이블
  자체는 바꾸지 않고 계산기와 설정 내용만 추가하면 되게 한다.
- 투데이카드 – 랭킹모드는 카드 여러 개가 같은 랭킹모드 하나를 참조할 수 있는 단순한
  참조 관계로 둔다(카드 하나가 랭킹모드 여러 개를 갖지는 않는다).

**기술적 명확화**
- 어드민의 미션 선택 목록은 표시 방식이 랭킹형으로 설정된 미션만 노출한다.
- 수동 지정 유저 목록에 넣을 수 있는 인원 수 상한(있다면 몇 명까지인지)은 구현 시점에
  정한다 — 운영 목적상 대개 소수 인원을 큐레이션하는 용도일 것으로 보이지만, 정확한
  상한 여부는 확인이 필요하다(뒤 Out of Scope 참고).
- 지표가 "누적값"이 아니라 "한 번의 활동 기록"이나 "과거 대비 비교"류일 때, 유저
  한 명당 대표값을 역대 최고 기록으로 뽑을지 가장 최근 활동 기록으로 뽑을지는 제품
  판단이 필요하다 — 어느 쪽이든 계산 로직은 이미 있다(뒤 Out of Scope 참고).
- 지표 중 "이번 주 활동 횟수"·"이번 달 누적 거리"류는 배지 판정에서는 "역대 가장
  잘한 주/달"을 보고, 화면 진행률 표시에서는 "지금 이번 주/달"을 보는 서로 다른
  정의가 이미 쓰이고 있다. 랭킹에 어느 정의를 쓸지도 같은 이유로 제품 판단이
  필요하다.

## 테스트 결정

- 좋은 테스트의 기준: 랭킹모드 정의와 대상 데이터가 주어졌을 때 계산된 순위 목록만
  검증한다. 계산기 내부에서 데이터를 어떻게 가져오는지, 화면이 어떻게 그려지는지 같은
  구현 세부사항은 테스트하지 않는다.
- 테스트 대상: 새로 만드는 랭킹 계산기(순수 함수 — 대상·지표값 목록을 넣으면 순위가
  매겨진 목록이 나오는 형태. 미션 참가자 조합과 수동 지정 유저 조합 둘 다), 지표
  키 → 현재값을 돌려주는 조회 계층(1차 지원 필드 각각에 대해, 같은 활동 이력을
  넣었을 때 배지 화면 진행률 표시가 보여주는 값과 같은 값이 나오는지가 특히 중요한
  회귀 기준이다 — 같은 계산 로직을 감싸 쓰는 것이므로 두 곳의 결과가 어긋나면 안
  된다), 투데이 카드 종류 판별 로직에 랭킹보드 케이스가 추가된 부분.
- 이 프로젝트의 선례:
  - 조합(믹스) 판정과 드랍 판정처럼 복잡한 로직을 도메인 모듈의 순수 함수로 분리하고
    별도 테스트 폴더에서 단위테스트하는 관례가 이미 있다 — 새 랭킹 계산기도 같은
    결로 만든다.
  - 배지 발급 조건 중 "서비스 사용량"(팔로워 수·팔로잉 수·하루 동기화 횟수) 판정
    로직에는 이미 지표별로 값을 넣어 결과를 확인하는 테스트가 있다 — 같은 지표를
    랭킹 정렬에 쓸 때도 값 조회 부분은 이 선례의 검증 방식을 그대로 참고할 수 있다.
  - 투데이 카드 로직은 이미 자체 테스트가 있으니 그 파일에 케이스를 추가하는 형태가
    자연스럽다.
  - API 라우트 자체는 이 프로젝트에서 보통 도메인 모듈을 그대로 호출하는 얇은
    통로로만 두고 별도 테스트를 두지 않는 관례이므로 이번에도 그 관례를 따른다.
- 참고로 지금 쓰이는 미션 순위 비교 규칙에는 테스트가 없었다 — 이번에 계산기를
  분리하면서 이 로직도 함께 테스트 대상에 넣는 게 자연스럽다.

## Out of Scope

> 2026-09-11 업데이트 — 처음 버전에서는 "유저 직접 지정 랭킹"과 "배지 조건 랭킹" 둘 다
> Out of Scope였으나, 대상 선정 방식(관리자 수동 지정 확정)이 구체화되어 이번 범위
> (User Stories 14~18)로 편입했다. 같은 날 지표 풀을 "배지 보유 개수·동기화 수·
> 팔로워 수·누적 달리기 거리 4종"에서 "액티비티 배지 조건 레지스트리 전체"로 다시
> 넓혔다 — 다만 레지스트리 전체가 그대로 1차 범위인 건 아니고, 아래처럼 필드
> 성격에 따라 갈린다.

- **정렬 지표로 쓰기 어려운 레지스트리 필드.** 배지 조건 레지스트리에는 정렬 지표로
  바로 쓰기 힘든 필드가 섞여 있다 — 대상을 좁히는 필터 성격 필드(어떤 종목만 셀지
  등), 값이 정해지려면 추가 설정이 같이 있어야 하는 필드(예: "몇 시간 안에 몇 번"
  류), 아직 엔진이 실제로 계산해 본 적 없는 필드(조건으로 설정은 가능해도 판정에
  쓰인 적이 없는 것들), 선행 배지·교차 조건처럼 관계를 보는 필드. 대략 레지스트리
  필드의 절반 정도가 여기 해당하는 것으로 파악됐다. 어드민 지표 선택 화면에는 이런
  필드도 함께 보이되(User Story 17), 선택하면 "아직 이 지표는 지원하지 않는다"는
  안내와 함께 막는 것을 1차 방식으로 제안한다. 어떤 필드를 언제 순차로 열지는 이번
  범위가 아니라 하나씩 후속으로 진행한다.
- **"한 번의 활동 기록"·"과거 대비 비교"류 지표의 대표값 기준.** 이런 지표는 유저
  한 명당 "역대 최고 기록"을 볼지 "가장 최근 활동의 기록"을 볼지가 정해지지 않았다.
  계산 로직은 이미 둘 다 있으므로 개발 난이도 문제가 아니라 어느 쪽이 랭킹의 취지에
  맞는지 제품 판단이 필요하다.
- **"이번 주/이번 달"류 지표의 기준 시점.** 같은 이유로 "역대 가장 잘한 주(달)"를
  볼지 "지금 이 주(달)"를 볼지 정해지지 않았다.
- **여러 지표를 가중치를 줘서 하나의 점수로 합성하는 것.** 지표를 여러 개 쓰고
  싶다는 요청은 확인됐지만, 정확한 조합 방식(단순 가중합인지, 서로 단위가 다른
  지표를 어떻게 같은 척도로 맞출지 등)은 아직 정해지지 않았다. 이번 범위는 랭킹모드
  하나당 지표 하나만 고르는 것으로 한정하고, 조합은 방식이 정해진 뒤 후속 작업으로
  진행한다.
- **활동 이력 기반 지표(누적 거리 등)의 집계 기간.** 가입 이후 전체 누적인지,
  랭킹모드의 집계 기간 안에서만 계산하는지 등 세부 기준은 구현 시점에 확인이
  필요하다(대상이 미션 참가자일 때는 이미 미션 참가 기간으로 자연스럽게 정해지지만,
  수동 지정 유저는 그런 기준이 없다). 랭킹모드에 있는 집계 시작·종료 일시를 그대로
  적용하는 안을 기본으로 제안한다.
- **수동 지정 유저 목록의 인원 수 상한.** 몇 명까지 지정 가능하게 할지는 정해지지
  않았다.
- 랭킹 결과에 대한 알림·시상 자동화(집계 종료 시 상위권 유저에게 알림을 보내는 등).
- 랭킹모드 하나를 투데이카드 이외의 다른 위치(예: 미션 상세 화면 자체의 구조 변경)에
  노출하는 것 — 이번 범위는 투데이카드의 랭킹보드 카드 종류 하나로 한정한다.

## Further Notes

- 미션 상세 화면의 지금 랭킹 UI는 그 화면 전용 API에서 데이터를 직접 가져오는
  구조라, "재사용"이 컴포넌트를 그대로 가져다 쓰는 수준이 아니라 데이터를 바깥에서
  주입하는 방식으로 바꾸는 리팩토링을 동반한다. 이 리팩토링 자체가 미션 상세 화면의
  기존 동작에 회귀를 만들지 않는 게 조건이다.
- **정정 — 이전 버전에서 "유저 통계를 조합하는 로직이 프로젝트에 전혀 없다"고 적었던
  건 절반만 맞았다.** 다시 확인해보니 배지 발급 조건 중 "서비스 사용량" 카테고리가
  팔로워 수·팔로잉 수·하루 동기화 횟수를 이미 유저 단위 숫자값으로 다루고 있었다
  (기준치와 비교해 배지를 주는 용도로). "여러 지표를 조합해서 점수화"하는 로직은
  여전히 없지만, "지표 하나의 값을 구하는" 부분은 이미 있는 게 많다는 게 이번에
  다시 확인한 사실이다 — 이번 범위(지표 하나만 선택)가 애초 걱정했던 것보다 수월할
  수 있다.
- **2026-09-11 추가 조사 — 지표 풀을 배지 조건 레지스트리 전체로 넓힌 근거.** "화면에
  진행률을 보여주기 위한" 용도로, 배지 판정과는 완전히 별개로 유저의 활동 이력만
  넣으면 누적 거리·고도·시간·횟수·연속일수 같은 값들을 한 번에 계산해 돌려주는
  계산 계층이 이미 있다는 걸 확인했다(오늘 오전 배지 화면 리뉴얼과는 별개로 예전부터
  있던 코드다). 이 계층이 레지스트리 "누적 목표"·"한 번의 활동 기록" 그룹 대부분과
  겹쳐서, 지표 풀을 4종에서 레지스트리 전체로 넓히는 게 생각보다 급격한 확장이
  아니었다. 다만 완전 자동은 아니다 — 레지스트리 필드의 대략 절반은 필터 성격이거나,
  추가 설정이 있어야 값이 정해지거나, 아직 엔진이 계산해 본 적 없는 필드라 1차
  범위에서 빠진다(위 Out of Scope 참고). "한 번의 활동 기록"류와 "이번 주/이번 달"류
  필드는 이미 코드에 두 가지 관례(역대 최고 vs 최근·현재 시점)가 공존하고 있어,
  랭킹에 어느 쪽을 쓸지는 개발이 아니라 선택의 문제로 남는다.
- 조사 중에 발견한 사소한 별건: PRD 문서의 배지 종류 설명에 지금은 쓰지 않는 옛
  명칭이 하나 남아 있었다(체크인 배지로 이름이 바뀐 지 오래됐는데 문서만 안 바뀜).
  이번 작업과는 무관하지만, 다음에 그 문서를 만질 일이 있으면 같이 정정하면 좋겠다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

핵심 요구사항 4가지(어드민 랭킹모드 생성 · 투데이 카드에서 랭킹보드로 연결 · 대상×지표 조합 ·
포디엄 없는 랭킹 리스트 재사용)를 모두 구현했다.

- **`ranking_modes` 신규 테이블**(마이그레이션 158, 미실행) — 대상 선정(`target_type`:
  `mission_participants`/`manual_users`) × 정렬 지표(`metric_type`: `mission_progress`/
  `condition_field`/`badge_count`)를 독립 축으로 저장. 정렬 지표는 배지 조건 레지스트리의
  필드 키를 그대로 참조(`metric_field_key`)해 레지스트리가 늘어나도 랭킹모드 스키마를 바꾸지
  않는다. `today_cards.ranking_mode_id`(신규 FK) + `template_type`에 `ranking_board` +
  `layout_type`에 `ranking_list`(포디엄 없는 순위 리스트 전용 노출 형태) 추가.
- **랭킹 계산 도메인 모듈**(`src/lib/ranking/`) — `rankingCalculator.ts`(순수, 지표값 정렬),
  `metricValues.ts`(순수, 1차 지원 지표 화이트리스트 8종: 누적 목표 5종 + 사용량 3종 —
  "한 번의 활동 기록"·"개인 기록 비교"·"이번 주/달"류는 대표값 기준 미정으로 Out of Scope에
  따라 제외), `rankingDataSource.ts`(서버 전용 — DB 조회 + 계산 조합, 미션 참가자는
  `lib/missions/ranking.ts`의 기존 순위 규칙을 그대로 감싸 재사용), `format.ts`(지표별 값
  표시 포맷 — mission_progress는 기존 `formatMissionProgress` 그대로, 나머지는 레지스트리
  단위를 붙임).
- **랭킹 리스트 UI 재사용** — `MissionStatusClient.tsx`의 파일 로컬 `RankingListRow`를
  `src/components/ranking/RankingListRow.tsx`(서비스 공용)로 분리하고 `formatValue`를 외부
  주입받게 했다(오케스트레이터 UI 재사용 판정 그대로 — `ListRowCard`·`ProgressBar` 재료는
  신규 생성 없이 그대로 재사용, MODULAR 승격은 이번 범위에서 강제하지 않음). 미션 상세
  화면은 이 컴포넌트를 호출하는 형태로 바뀌었을 뿐 동작은 동일(회귀 없음, 아래 테스트 참고).
  `TodayCardStack.tsx`에 `ranking_list` 레이아웃 분기(`RankingListCard`)를 추가 — 카드
  전체를 `<Link>`로 감싸는 기존 방식 대신 제목 영역만 링크하고 각 순위 행이 유저 프로필로
  개별 링크한다(앵커 중첩 방지, 아래 "주요 의사결정" 참고).
- **어드민 랭킹모드 관리 화면**(`/admin/ranking-modes`, `new`, `[id]/edit`) — 단일 열 폼(배지·
  투데이 화면의 2단 레일 레이아웃까지는 강제하지 않음, 어드민은 MODULAR 비적용). 정렬 지표
  필드 선택은 배지 조건 폼의 그룹 구조(9개 섹션)를 그대로 재사용해 그룹별로 보여주되, 1차
  미지원 필드는 "준비 중"으로 비활성 표시(User Story 17 — 지표를 하나씩 추가할 때 선택 UI를
  다시 만들 필요가 없도록). 목록 화면은 랭킹모드마다 참조 무결성을 확인해 경고 칩을 보여준다
  (User Story 8 — 연결된 미션 삭제/랭킹형 아님).
- **투데이 카드 연동** — `today-sections.ts`에 `ranking_board` 템플릿(참조 필드: 랭킹모드 선택
  + 이동경로)을 기존 템플릿과 동일한 매트릭스 방식으로 추가. `TodayCardForm.tsx`의 레일
  실시간 미리보기가 선택한 랭킹모드의 실제 계산 결과를 가져와(`/api/admin/ranking-modes/[id]/
  preview`) 보여준다(User Story 6). `resolveTargetHref`는 랭킹모드의 대상이 미션 참가자면
  그 미션의 기존 랭킹 화면(`/missions/{id}/status`)으로, 아니면 `/missions`로 이동한다(아래
  "주요 의사결정" 참고).
- **집계 기간 반영**(User Story 13) — 수동 지정 유저 + 활동 이력 기반 지표는 랭킹모드의 집계
  시작·종료 일시로 활동 범위를 제한한다(가입 시점 앵커와 늦은 쪽을 하한으로) — 집계 기간이
  끝난 뒤에도 카드가 계속 노출되는 동안 순위가 계속 바뀌지 않게 한다. 팔로워 수·팔로잉 수·
  하루 동기화 횟수는 스냅샷 이력이 없어 이 범위에서 얼릴 수 없다(아래 alerts 참고).
- **UX Writing** — 신규 유저 노출 문구(`rankingEmpty` 등)는 `fluent-korean` 지침(완결된
  문장, 해요체)을 따랐다. 어드민 전용 문구는 사용자 노출 고정 용어 대상이 아니다(선례와
  동일 — 티켓 20260911_1454 UX Writing 검증 각주).

### 주요 의사결정 / 핵심 메모

- **1차 지원 지표 화이트리스트를 8종으로 좁힘(누적 목표 5종 + 사용량 3종)** — 오케스트레이터
  지시("역대최고/최근값 선택... 이번 범위에 포함시키지 말 것")와 티켓 Out of Scope를 근거로,
  "한 번의 활동 기록"(single 섹션 — max_speed_kmh 등)·"개인 기록 비교"(record 섹션)·
  "기간류"(weekly_count·monthly_km 등, period 섹션)는 대표값 기준(역대 최고 vs 최근값,
  역대 최고 주 vs 지금 이 주)이 미정이라 제외했다. 어드민 화면에는 전체 레지스트리 그룹을
  보여주되 이 8종만 선택 가능하고 나머지는 "준비 중"으로 비활성화했다(구현 계획 권장 그대로).
- **랭킹보드 카드의 이동 경로 — 대상이 미션 참가자면 그 미션의 기존 랭킹 화면, 수동 지정
  유저면 `/missions`.** User Story 10("탭하면 해당 미션의 랭킹 화면으로 이동")과 Out of
  Scope("랭킹모드를 투데이카드 이외의 위치에 노출하지 않음")를 함께 읽으면, 미션 참가자
  대상은 **이미 존재하는** 미션 상세 화면으로 보내는 것이지 새 노출 위치를 만드는 게
  아니므로 허용되지만, 수동 지정 유저 대상은 "더 자세히 보여줄 기존 화면"이 없다(그런
  화면을 새로 만드는 것은 범위 밖) — 그래서 미션 화면 링크 대신 `/missions` 목록으로
  보낸다. **확신도: medium** — 이 특정 분기(수동 지정 유저의 탭 목적지)는 티켓에 명시적
  서술이 없어 위 논리로 추론했다. `resolveTargetHref(card, ctx)`에 선택적 2번째 인자를
  추가하는 방식(순수 함수 유지, `getTodayCards`가 랭킹모드를 배치 조회해 ctx로 넘김)으로
  구현해 향후 이 판단이 바뀌어도 한 곳만 고치면 되게 했다.
- **랭킹 리스트 카드는 전체를 `<Link>`로 감싸지 않는다.** 순위 행이 각자 유저 프로필로
  이동하는 자체 `<Link>`를 갖고 있어(User Story 11, 미션 상세와 동일 동작 유지) 카드
  전체를 감싸면 앵커 중첩(무효 HTML, 클릭 동작 미정의)이 된다 — 제목 영역만 카드 이동
  경로로 링크했다(`TodayCardStack.tsx`의 `RankingListCard` 주석 참고).
- **어드민 랭킹모드 화면은 배지·투데이 화면의 2단 레일 레이아웃을 쓰지 않는다.** 필드 수가
  적고(대상·지표·기간 정도) 레일에 넣을 "실시간 미리보기" 대상이 뚜렷하지 않아(리스트
  카드 미리보기가 아니라 표 형태 데이터) 단일 열 폼으로 충분하다고 판단했다 — 어드민은
  MODULAR 적용 대상이 아니므로 다른 어드민 화면과의 시각적 일관성보다 화면 성격에 맞는
  단순함을 택했다.
- **집계 기간(starts_at~ends_at)을 활동 이력 기반 지표에만 적용했다.** 팔로워 수·팔로잉
  수·하루 동기화 횟수는 시점별 스냅샷 이력이 DB에 없어(현재 값만 조회 가능) 얼릴 방법이
  없다 — Out of Scope 절이 이 트레이드오프를 이미 인지하고 있었다("집계 기간... 세부
  기준은 구현 시점에 확인이 필요... 기본으로 제안한다"는 문구를 그 제안대로 구현).
- **배지 보유 개수는 배지 타입(활동/아이템/체크인) 안에서 distinct badge_id로 센다.**
  체크인 배지(같은 지점 반복 체크인)와 아이템 배지(같은 배지 여러 개 보유 가능)는 원시
  행 개수를 세면 "보유 개수"가 아니라 "획득 이벤트/인스턴스 개수"가 된다 — "몇 종류의
  배지를 가졌는가"로 통일했다.
- **선택하지 않은 대안**: 어드민 랭킹모드 화면 자체에도 미리보기를 두는 안을 검토했으나,
  User Story 6("발행 전 미리보기")이 실제로는 투데이 카드 발행 흐름을 가리키고 있고
  투데이 카드 폼의 기존 레일 미리보기 메커니즘(`TodayCardStack` 재사용)이 이미 그 역할을
  하므로 중복 UI를 만들지 않았다. 대신 두 화면(랭킹모드 폼 미리보기·투데이 카드 레일)이
  같은 `GET /api/admin/ranking-modes/[id]/preview`를 공유할 수 있게 설계해뒀다.

### WARN 대응 (탭 이동·용어 정리) *(2026-09-11 게이트 리뷰 WARN 재작업)*

직전 게이트 리뷰 판정은 WARN(재구현 불필요)이었다. 사용자가 WARN 사유 중 탭 이동 경로 하나와
개선 리뷰가 제안한 용어 정리 하나, 이 두 가지만 명시적으로 승인해 그 범위만 반영했다 — 그 외
접근성·레이아웃·색상·인터랙션 세부 이슈, 문장 표현 교정, 어드민 관례 정렬 등 나머지 제안은
이번 범위에 포함하지 않았다(사용자가 별도로 검토 중).

**A. 탭 이동 경로 수정**
- 대상이 유저 직접 지정인 랭킹보드 카드는 제목 영역에 걸려 있던 `/missions` 목록 링크를
  없앴다 — 탭해도 아무 곳으로도 이동하지 않는다. `TodayCardStack.tsx`의 `RankingListCard`가
  `ranking.metricType === 'mission_progress'`일 때만(대상이 미션 참가자일 때만 정렬 지표가 이
  값으로 고정된다 — `lib/admin/ranking-modes.ts`의 `buildRankingModeSavePayload` 참고) 제목
  영역을 `<Link>`로 감싸고, 그 외에는 링크 없는 `<div>`로 렌더링한다.
- 대상이 미션 참가자인 카드는 기존 동작(카드가 `/missions/{id}/status`로 이동) 그대로 뒀다 —
  이 분기는 이미 맞게 구현돼 있었다.
- 순위 행(`RankingListRow`)은 대상 방식과 무관하게 이미 `entry.username`이 있으면 유저
  프로필(`/{username}`)로 이동하는 `<Link>`를 갖고 있었다(`ListRowCard`의 `href` prop 경유) —
  추가 구현 없이 그대로 유지된다(User Story 11).
- `resolveTargetHref`의 `ranking_board` 케이스가 유저 직접 지정 대상일 때 반환하는 `/missions`
  값은 그대로 뒀다 — `resolved_href: string`(non-null) 계약을 지키는 타입 안전 폴백일 뿐, 실제
  탭 동작은 더 이상 이 값을 쓰지 않는다(주석에 명시). 순수 함수의 반환 타입을 바꾸는 대신 UI
  쪽 판단 지점 하나만 수정해 회귀 영향을 좁혔다.

**B. 용어 정리**
1. 어드민 화면(랭킹모드 관리 목록·생성·수정 폼 제목/버튼/안내문, 투데이 카드 폼의 필드
   라벨·도움말, 투데이 카드 조회 화면의 읽기전용 라벨, 사이드바 메뉴, API 404 에러 메시지)에서
   사람이 보는 문구의 '랭킹모드'를 전부 '랭킹 규칙'으로 바꿨다. `ranking_modes` 테이블명·
   `RankingModeRow` 타입명·`/api/admin/ranking-modes` 경로·파일명(`RankingModeForm.tsx` 등)
   같은 내부 코드·DB 식별자는 바꾸지 않았다 — 코드 주석(개발자 문서 성격)·테스트 설명 문자열도
   "사람이 보는 화면 문구"의 범위 밖으로 보고 그대로 뒀다.
2. 유저 노출 문구를 '랭킹'으로 통일했다: 투데이 카드 칩 라벨(`d.todayCard.rankingBoard`)
   '랭킹보드' → '랭킹', 홈 피드 빈 상태(`d.todayCard.rankingEmpty`) '아직 순위가 없어요' →
   '아직 랭킹이 없어요'로 바꿨다. 같은 순위 리스트 UI를 공유하는 미션 상세 화면의 섹션 라벨
   (`d.missions.statusAllRanks`) '전체 순위'도 '전체 랭킹'으로 맞췄다 — 실제로 화면에 렌더링되는
   문구이고 랭킹보드가 재사용하는 것과 같은 리스트라 "다른 유저 노출 문구도 자연스러운 범위에서"
   조항에 해당한다고 판단했다.
   - **범위를 넓히지 않은 것(확신도 medium인 경계 판단)**: `d.missions.statusMeRanking`
     ('— 내 순위 —')은 코드베이스 어디에서도 실제로 렌더링되지 않는 죽은 i18n 키라 "유저 노출
     문구" 자체에 해당하지 않는다고 보고 그대로 뒀다. 알림 문구 `msgMissionRankUpGrouped`
     ('미션 {count}에서 순위가 올랐어요', #23 순위 상승 알림)는 이번 랭킹보드 기능과 무관한
     별도 알림 배치 파이프라인(`lib/notifications/batch/missions.ts`, `mission_rank_snapshots`
     테이블 기반)의 기존 표현이라 범위 밖으로 뒀다 — 이번 티켓이 손대지 않은 화면(알림 피드)의
     오래된 개념이라 "다른 유저 노출 문구"의 자연스러운 범위를 벗어난다고 판단했다. 어드민 전용
