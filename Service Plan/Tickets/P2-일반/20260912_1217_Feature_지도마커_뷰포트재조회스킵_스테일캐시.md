# [Feature] 지도 마커 뷰포트 재조회 스킵으로 인한 스테일(오래된) 캐시 노출

## 배경 / 문제 정의
티켓 `20260912_1121`(체크인 배지 유효기간↔지도 마커 연동) 검증 과정에서 발견된 범위 밖
문제. 서버(`/api/checkin-badges`)의 유효기간 필터링 로직·데이터는 전수 검증을 마쳐 정상이지만,
프론트엔드 지도 컴포넌트의 재조회 스킵 최적화 때문에 **서버가 이미 최신 데이터를 갖고 있어도
클라이언트가 다시 물어보지 않아 오래된 마커가 화면에 남는** 문제가 있다.

원인: `jam-web/src/components/map/MapView.tsx`의 `emitViewport()`(약 342행)가 사용자가 지도를
움직여도 그 위치가 `lastViewportRef`(마지막으로 실제 fetch를 트리거한 뷰포트) ± 마진
(`VIEWPORT_MARGIN_RATIO`, 약 550~559행 `isWithin()`) 범위 안이면, 같은 줌 레벨에서
`/api/checkin-badges` 재호출 자체를 스킵한다. `badgeMarkers`/`badgeClusters` state는 그
이전 응답 그대로 유지된다.

재현: 유저가 특정 지역을 한 번 지나가며 데이터를 받아온 뒤, 그 이후 서버 데이터가 바뀌어도
(배지 유효기간 시작/종료, `show_on_map` 토글, 배지 신규 추가/삭제 등) 유저가 그 지역 안에서만
움직이는 한(마진 범위 내) 앱을 완전히 새로고침하기 전까지는 절대 최신 상태로 갱신되지 않는다.
- `DropsClient.tsx`의 `handleViewportChange`(147~162행) 자체는 응답을 완전 교체
  (`setBadgeMarkers(json.pois ?? [])`)하므로 배열을 이어붙이는 버그는 아니다 — "재조회 자체가
  스킵되는 것"이 원인이다.
- 브라우저를 완전히 새로고침하면 `lastViewportRef`가 초기화되어 즉시 해결되지만, 앱 내
  탭 전환만으로는 컴포넌트가 언마운트되지 않아 캐시가 살아있다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 재조회 스킵 최적화(마진 기반 팬 최적화) 자체는 유지한다 — 의도된 성능 최적화이므로 걷어내지
  않는다.
- 마지막 실제 fetch로부터 일정 시간(TTL, 예: 60~120초)이 지났으면, 뷰포트가 마진 범위 안이라도
  강제로 재조회하도록 staleness 판정을 추가한다. 정확한 TTL 값과 구현 방식(예: `lastFetchAtRef`
  추가, `emitViewport()` 조건에 시간 체크 병합)은 구현 단계에서 기존 코드 구조에 맞게 정한다.
- 대안으로 탭 재진입(지도 탭으로 다시 전환) 시 강제 재조회하는 방법도 검토 가능 — 다만 이것만으로는
  "지도 탭에 계속 머무른 채 오래 있는" 경우를 못 잡으므로 TTL 방식을 우선 검토한다.

### UI/UX 관점 (해당 시)
- 없음 (사용자에게 노출되는 시각적 변화 없음, 내부 재조회 타이밍만 조정)

### 컨텐츠 관점 (해당 시)
- 없음

## 구현 계획
1. `MapView.tsx`의 `emitViewport()`/`isWithin()` 주변에 마지막 실제 fetch 시각을 기록하는
   ref를 추가한다.
2. `isWithin()` 판정이 참이더라도, 마지막 fetch로부터 TTL 이상 지났으면 재조회를 진행하도록
   조건을 수정한다.
3. 회귀 확인: 짧은 시간 안에 좁은 범위를 왔다갔다 할 때는 여전히 재조회가 스킵되어 기존 성능
   최적화 효과가 유지되는지, TTL 경과 후에는 같은 자리에 머물러 있어도 최신 데이터로 갱신되는지
   확인한다.
