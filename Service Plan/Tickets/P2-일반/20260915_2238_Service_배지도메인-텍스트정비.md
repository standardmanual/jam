## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
badges 도메인 화면·컴포넌트·API·동적 문장 생성 로직을 전수 검사했다. 화면 10개
(`BadgesClient.tsx`, `badges/[id]/page.tsx`, `BadgeConditionCard.tsx`, `BadgeHeroSection.tsx`,
`PoiEarnHistory.tsx`, `PoiMapButton.tsx`, `ItemEarnHistory.tsx`, `BadgeShareButton.tsx`,
`badges/tree/page.tsx`, `badges/tree/BadgeTreeClient.tsx`)와 공용 컴포넌트 4개
(`BadgeFamilyRow.tsx`, `BadgeProgressGridCell.tsx`, `BadgeTrophyGridCard.tsx`, `BadgeUnlockSheet.tsx`)
중 대다수는 이미 `d.badges.*` 딕셔너리를 온전히 쓰고 있었다 — 실제로 손댄 곳은 감사 중 발견한
**하드코딩 잔재**뿐이다:
- `BadgeShareButton.tsx`: 공유 캐러셀 aria-label 2곳(`공유 이미지 선택`·`통계 포함 공유 카드`/
  `배지 이미지 단독`)을 `d.badges.*`로 편입
- `badges/tree/page.tsx`: 숨김 미션 게이트의 대체 제목(`다음 미션 공개 예정`)을 편입
- `BadgeTreeClient.tsx`: 트레일러닝 탭 축약 라벨·"한 번에 끝나는 배지" 섹션 제목/aria-label·
  정렬 안내(`진행률 높은 순`) 3곳 편입
- `BadgeFamilyRow.tsx`: 무한레벨형 헤더 메타(`다음 Lv.N`)·잠금 버튼 aria-label
  (`{배지명} 받는 방법 보기`)을 `t(template, vars)`로 편입
- `badgeTree.ts`: 「받는 방법」 시트 note 3곳(등급 제한 유무·교차/미션 게이트 N개 이상)을 편입

API 3곳(`share-data/route.ts`, `recent-earned/route.ts`, `checkin-badges/route.ts`)은
ADR 0001(서버-클라이언트 단일 진실 소스)에 따라 정비했다. `recent-earned`·`checkin-badges`는
하드코딩 한글 에러 문구(`인증이 필요합니다.`·`인증 필요`·`POI 조회 실패` 등)를 `d.common.authRequired`·
`d.badges.checkinMap*Error`로 옮겼다. `share-data/route.ts`는 원래 사유 코드(`strava_disconnected`
등)만 내려보내고 클라이언트(`BadgeShareButton.tsx`)가 그 코드로 `d.badges.*` 문구를 **직접 다시
조립**하는 구조였다 — ADR 0001이 금지하는 "같은 문구를 서버·클라이언트 양쪽에 중복 정의"에
해당해, 서버가 재현 가능한 사유 4종에 한해 `title`/`body`를 `d.badges.*`로 완성해 응답에
포함시키고, 클라이언트는 그 값을 그대로 신뢰해 노출하도록(`errorCopy()` 재작성) 고쳤다. 로그인·
권한 등 클릭 전에 이미 걸러지는 사유는 서버 응답에 title/body가 없으므로 기존과 동일하게 일반
실패 문구로 폴백한다.

동적 문장 생성 로직 4개 감사 결과:
- `badgeConditionText.ts`: 배지 조건 문구를 `conditionRegistry.ts`(조건 필드 단일 출처)의
  라벨·단위·방향으로 조립하는 전용 템플릿 엔진이다. 630종 조건 조합을 딕셔너리에 개별 키로
  나열하면 이 파일이 애초에 없애려던 "키 나열 → 신규 조건 추가 시 누락" 문제가 재발한다 —
  의도된 설계로 판단해 딕셔너리 이관 대상에서 제외했다.
- `badgeProgressText.ts`: 위 파일과 같은 이유로 축값(현재/목표 수치)은 딕셔너리 대상이 아니지만,
  그 안에 섞여 있던 **고정 문구**(상태 라벨 4종, 주기형 기간 명사, 2축 규칙문, 남은 양 접미사,
  아쉬움 줄, 동기화 비교문 등 12곳)는 조합형이 아니라 매번 같은 문장이라 전부 `d.badges.*` +
  `t(template, vars)`로 편입했다.
- `badgeTree.ts`: 「받는 방법」 시트 note 3곳(위에 기록)만 하드코딩이었고 나머지는 순수 그래프
  빌더 로직.
- `badgeBackgroundTheme.ts`: 하드코딩 한글 텍스트 없음(순수 스타일 계산).

배지 이름·설명(플레이버 텍스트)은 티켓 범위에서 제외했다(DB 컬럼이 소스). `checkin-badges/route.ts`·
`poi-views/route.ts`의 drops 고유 문구는 건드리지 않았다 — `checkin-badges/route.ts`에서 고친
문구는 badges 도메인 문구(체크인 배지 지도 마커 조회 에러)에 한정된다. `poi-views/route.ts`는
badges 도메인 텍스트가 없어 변경하지 않았다.

### 주요 의사결정 / 핵심 메모
- **badgeConditionText.ts·badgeProgressText.ts의 축값 조합 로직은 딕셔너리 이관 대상에서
  제외했다.** 두 파일 모두 "레지스트리가 단일 출처, 코드가 조합만 담당"이라는 명시적 설계
  원칙이 파일 상단 주석에 이미 기록돼 있고, 630종 조건 조합을 `d.badges.*`에 개별 키로
  펼치면 그 설계가 막으려던 "신규 조건 추가 시 문구 누락" 문제가 그대로 재발한다. 대신 그
  안에 섞여 있던 **고정 문구**(조합과 무관하게 매번 같은 문장)만 골라 이관했다 — 이 구분
  기준(조합형 vs 고정형)이 이번 감사의 핵심 판단이었다.
- **`share-data/route.ts`를 ADR 0001에 맞춰 구조 변경했다.** 기존에는 서버가 사유 코드만
  주고 클라이언트가 `d.badges.*`로 재조립하는 구조라, "같은 문구를 서버·클라이언트 양쪽에
  중복 정의"하지는 않았지만(클라이언트만 문구를 알았다) 서버가 재현 가능한 사유의 최종
  문구를 전혀 모르는 상태였다. 클라이언트가 재현 가능한 4개 사유(스트라바 연동 해제·트리거
  없음·조회 실패·활동 없음)만 서버가 title/body를 완성해 내려주도록 바꾸고, 클라이언트는
  그 값을 신뢰하되 값이 없으면(로그인 세션 만료 등 사전에 이미 걸러지는 사유) 기존 일반
  실패 문구로 폴백하게 했다 — 전체를 토스트 단일 `message` 패턴으로 통일하지 않고 기존
  title+body 2줄 구조를 유지한 이유는, 이 화면이 ADR이 다룬 토스트/인라인 에러가 아니라
  캐러셀 미리보기 패널이라 구조 자체를 바꾸면 회귀 위험이 커서다.
- **`checkin-badges/route.ts`의 새 에러 문구는 3단계 구조를 완전히 적용하지 않았다.**
  확인 결과 호출부(`DropsClient.tsx`)가 `!res.ok`면 본문을 읽지 않고 조용히 무시하므로
  실사용자에게 노출되지 않는다 — 그래도 ADR 0001·이 티켓의 명시적 대상이라 하드코딩은
  제거했지만, 노출되지 않는 문구에 과도한 구조를 씌우는 대신 담백한 안내로 작성했다.
