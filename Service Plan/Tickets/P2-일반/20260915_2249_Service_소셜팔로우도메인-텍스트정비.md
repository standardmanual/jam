## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
화면 5곳(`[username]/page.tsx`, `FollowButton.tsx`, `FollowUserList.tsx`, `followers/page.tsx`,
`following/page.tsx`) + `ProfileClient.tsx`(`[username]/page.tsx`가 실제로 렌더링을 위임하는
6번째 화면, `/api/follows`를 직접 호출하는 헤더 팔로우 버튼·목록 내 팔로우 토글을 갖고 있어
같은 도메인)를 검사했다. `FollowUserList.tsx`·`followers/page.tsx`·`following/page.tsx`는
이미 `d.social.*` 딕셔너리로 전량 편입돼 있었고, `[username]/page.tsx`의 `generateMetadata`
title만 하드코딩(`${username} — JAM!`)이 남아 있어 `d.social.profileTitle` 템플릿으로
편입했다. `notifications/page.tsx`도 같은 `— JAM!` 접미 관례를 쓰고 있지만 §7.3이 사용자
노출 문구의 엠대시를 금지하므로 그대로 베끼지 않고, 이 티켓 범위 안의 `profileTitle`은
파이프(`{username} | JAM!`) 구분자로 새로 정했다(`notifications/page.tsx`는 이 티켓의
대상 파일이 아니라 손대지 않았다).

API 라우트 4곳(`api/follows/route.ts`, `api/follows/[userId]/route.ts`,
`api/users/[username]/followers/route.ts`, `api/users/[username]/following/route.ts`)은
전부 `'UNAUTHORIZED'`·`'MISSING_TARGET'`·`'SELF_FOLLOW'`·`'SERVER_ERROR'`·`'NOT_FOUND'` 같은
코드 문자열만 반환했다. ADR 0001에 따라 각 라우트가 `d.common.authRequired`(값 자체는
티켓 20260916_0904에서 별도 정비 중이라 참조만 함)·`d.social.followError`·
`d.social.unfollowError`·`d.social.selfFollowError`·`d.social.userNotFound`를 직접 참조해
완성된 문구를 반환하도록 고쳤다.

클라이언트 쪽(`FollowButton.tsx`, `ProfileClient.tsx`의 `handleFollow`/`handleListFollow`)은
서버 응답을 전혀 검사하지 않고 낙관적 UI만 적용한 채 실패를 조용히 삼키던 구조였다(에러
토스트 없음). ADR 0001 "클라이언트는 서버가 완성한 문구를 그대로 신뢰해 노출한다"는 규칙을
지키려면 애초에 실패를 노출하는 경로 자체가 있어야 해서, `useToast`를 붙여 실패 시
낙관적 상태를 롤백하고 서버 `error` 문구(없으면 `d.social.*` 폴백)를 토스트로 띄우도록
보완했다. §2.4 "소셜 액션(팔로우 등) vs 되돌릴 수 없는 확정" 원칙대로 담담한 톤으로
짧게 재시도만 안내하는 문구로 작성했다.

`api/users/[username]/followers|following` 두 라우트는 실제 클라이언트 소비처가
없는(grep 확인) 채 `followers/page.tsx`·`following/page.tsx`의 서버 컴포넌트 로직과
중복 구현된 상태였지만, 티켓이 명시적으로 대상 파일로 지정해 동일하게 정비했다.

### 주요 의사결정 / 핵심 메모
- **6번째 화면 = `ProfileClient.tsx`**: 티켓의 "등 6개"에서 이름이 빠진 화면은
  `[username]/page.tsx`가 렌더링을 위임하는 `../profile/ProfileClient.tsx`로 판단했다.
  헤더 팔로우 버튼·목록 내 팔로우 토글이 `/api/follows`를 직접 호출하는 이 도메인의
  핵심 클라이언트 로직이라 함께 정비하지 않으면 `FollowButton.tsx`와 에러 처리 방식이
  갈라진다.
- **`d.social.followError`를 여러 실패 사유에 재사용**: `MISSING_TARGET`(400, 클라이언트가
  항상 target_user_id를 보내 실질적으로 도달 불가한 방어적 분기)과 `SERVER_ERROR`(500) 둘
  다 사용자 입장에서는 "지금은 팔로우할 수 없다"는 같은 사실이라 구분되는 원인을 알려줄
  수 없다. 원인을 알 수 없는 실패에 억지로 3단계 구조를 적용하기보다 짧은 재시도 안내
  하나로 통일했다(§4.2 축약 원칙과 동일한 논리).
- **SEO title의 엠대시(`— JAM!`) 제거**: §7.3은 사용자 노출 문구의 엠대시 사용을 금지한다.
  최초 구현에서 `notifications/page.tsx`의 `${title} — JAM!` 관례를 그대로 베껴 게이트
  리뷰에서 FAIL을 받았다. 재작업하면서 이 티켓이 담당하는 `profileTitle`을
  `{username} | JAM!`(파이프 구분자)로 새로 정해 엠대시를 없앴다. `notifications/page.tsx`는
  이 티켓의 대상 파일이 아니므로 손대지 않았고, 같은 위반이 남아 있다는 사실만 아래
  잔여 이슈로 남긴다.
- **`api/users/[username]/followers|following`는 현재 미사용 라우트**: grep으로 클라이언트
  소비처가 없음을 확인했지만(사용자 표시 화면은 서버 컴포넌트에서 같은 쿼리를 직접
  실행), 티켓이 명시한 대상이라 동일하게 ADR 0001을 적용했다.

### 잔여 이슈
- `notifications/page.tsx`의 SEO 메타데이터 title이 여전히 `${title} — JAM!` 형태로
  엠대시를 쓰고 있다(이 티켓의 대상 파일이 아니라 손대지 않음). §7.3 anti-slop 기준(엠대시
  금지)을 전면 적용하려면 이 화면을 포함한 별도 티켓이 필요하다(이번 티켓 범위 밖).
