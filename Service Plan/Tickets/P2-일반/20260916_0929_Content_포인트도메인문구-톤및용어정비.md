# [Content] 포인트 도메인 문구 톤 및 용어 정비

> 상위 스펙: [`20260915_2227_Service_사용자노출텍스트-톤앤매너통합정비-스펙.md`](../P1-중요/20260915_2227_Service_사용자노출텍스트-톤앤매너통합정비-스펙.md)
> 출처: 티켓 20260915_2247(포인트 도메인 텍스트 정비) 한국어 리뷰에서 나온 제안 — 게이트는 PASS했으나 병합 전 반영하지 않고 이 후속 티켓으로 분리(사용자 결정, 2026-09-16)

## 배경 / 문제 정의

티켓 20260915_2247의 딕셔너리 이관 구조는 게이트 PASS했지만, 한국어 리뷰가 `d.points.reasonKind*`
6개 라벨의 표현(잉여어 반복, 사무적 명사화)과 용어표 미등재를 지적했다.

**한 가지는 검증 결과 실제 문제가 아니었다**: 리뷰가 지적한 "`reasonKindAdminAdjustment`를
어드민 라우트도 쓰면 지급/회수 구분이 사라진다"는 우려는, `api/admin/points/route.ts`가
독립된 별도 `REASON_KIND` 맵("운영자 지급"/"운영자 회수" 유지)을 갖고 있어 실제로는 공유되지
않음을 코드 대조로 확인했다. 이 항목은 이 티켓 범위에서 제외한다.

## 상세 요구사항 — `jam-web/src/lib/i18n/ko.ts`의 `d.points.reasonKind*` 값 수정

### (a) "보상" 접미어 반복 — 잉여어 제거
목록에서 5개 중 4개가 "보상"으로 끝나 기계적으로 읽히고, 같은 행에 이미 `+1,200 포인트`가
있어 "보상"은 정보값이 없다. 사건만 남긴다:
- `reasonKindBadgeReward`: "배지 보상" → "배지 획득"(§1.3 고정 용어 '획득' 사용)
- `reasonKindMissionReward`: "미션 보상" → "미션 완료"
- `reasonKindCombineFailReward`: "믹스 실패 보상" → "믹스 실패"
- `reasonKindCombineRecipeReward`: "믹스 보상" → "믹스 성공" (실패/성공 짝을 맞춰 "믹스 보상"이
  실패까지 포함하는 것처럼 오독되지 않게 함)
- `reasonKindItemBookCompletionReward`: "컬렉션 완성 보상" → "컬렉션 완성"

### (b) "포인트 조정" 사무적 명사화
`reasonKindAdminAdjustment`("포인트 조정")의 "조정"은 무슨 일이 있었는지 말하지 않는
공급자 언어다. 포인트 내역 화면은 모든 행이 포인트 변동이라 "포인트" 접두도 잉여다 →
"운영자 조정"

### (c) i18n 키 네이밍 — 폐기 용어 반영 (선택, 낮은 우선순위)
`reasonKindItemBookCompletionReward`의 "ItemBook"은 §1.3에서 "컬렉션"의 금지어로 명시된
"아이템북"이다. DB enum(`item_book_completion_point_reward`)은 그대로 두되, 새로 만드는
i18n 키 이름까지 옛 용어를 물려받을 이유는 없다 → `reasonKindCollectionCompletionReward`로
리네이밍 검토(참조하는 `route.ts` 코드도 함께 변경 필요, 키 이름만 바꾸는 리팩터링이라
우선순위는 낮음).

### (d) 용어표 등재(§1.3)
- "운영자"가 §1.3 용어표에 없다 — "어드민"/"관리자"와 갈라지기 전에 고정 등재
- 포인트 내역 사유 라벨 원칙(사건 중심, "보상" 접미어 지양)을 §1.3 또는 별도 절에 명시해
  향후 새 사유가 추가될 때 같은 실수가 반복되지 않게 한다

## 구현 계획
- `ko.ts`의 6개 키 값을 수정한다(구조 변경 없음).
- (c)는 별도 작업으로 분리해도 무방하다.
- (d) 용어표 등재를 `UX_WRITING_GUIDELINE.md`에 반영한다.
- 완료 후 `/im-not-ai`로 재검사한다.
