# [Content] 프로필 도메인 문구 톤 정비 및 "아이디" 용어 통일

> 상위 스펙: [`20260915_2227_Service_사용자노출텍스트-톤앤매너통합정비-스펙.md`](../P1-중요/20260915_2227_Service_사용자노출텍스트-톤앤매너통합정비-스펙.md)
> 출처: 티켓 20260915_2248(프로필 도메인 텍스트 정비) 한국어 리뷰에서 나온 제안 — 게이트는 PASS했으나 병합 전 반영하지 않고 이 후속 티켓으로 분리(사용자 결정, 2026-09-16)

## 배경 / 문제 정의

티켓 20260915_2248의 딕셔너리 이관·ADR 0001 적용 구조는 게이트 PASS했지만, 한국어 리뷰가
**"아이디"라는 개념이 §1.3 용어표에 아예 등재돼 있지 않아, 코드 안에서 "ID"·"아이디"·
"닉네임"·"유저명" 4가지로 갈라져 있다는 구조적 결함**을 발견했다. 이번 티켓의 문구 개선은
용어표 등재가 선행돼야 의미가 있다.

## 상세 요구사항

### (A) `UX_WRITING_GUIDELINE.md` §1.3 용어표 신설 — 선행 작업
"유저를 가리키는 고유 식별자"를 **"아이디(ID)"**로 고정 등재한다.
(X: ID, 닉네임, 유저명, 사용자명, 계정명 — 단, 이미 §4.2 Good 예시와
`jam-web/src/app/(main)/privacy/page.tsx`(142·170·428행)가 "닉네임"을 쓰고 있으므로, 이
문서 예시와 코드도 함께 "아이디"로 맞춰야 한다 — 그러지 않으면 등재 자체가 새로운 불일치를
만든다.)

### (B) `jam-web/src/lib/i18n/ko.ts` 값 수정 (A 확정 후 진행)
- `onboarding.usernamePlaceholder`("ID를 입력해 주세요") → 지시문 대신 예시값(`jam_runner`)으로
  전환 — `profileEdit.usernameLabel`("아이디")과 `errorEmpty`("아이디를 입력해 주세요")가
  이미 같은 말을 하고 있어 placeholder의 지시문은 중복
- `onboarding.errorTooLong`("30자 이하로 입력해 주세요") → 주어 없음, §3 물결표 규칙 미적용
  → "아이디는 2~30자까지 쓸 수 있어요"
- `onboarding.errorFormat`("영문, 숫자, ., _ 만 사용할 수 있어요") → 쉼표·마침표 나열로
  가독성 저하, 조사 붙여쓰기 오류 → "영문·숫자와 점(.), 밑줄(_)만 쓸 수 있어요"
- `onboarding.errorDot`류 → 금지형을 긍정형으로 전환: "점(.)은 아이디 가운데에만 쓸 수
  있어요" / "점(.)은 연달아 쓸 수 없어요"
- `onboarding.available`("사용 가능한 아이디예요") → "쓸 수 있는 아이디예요"
- `onboarding.taken`("이미 사용 중인 아이디예요") → §4.2 이미 벌어진 충돌 유형, [현상+해결책]
  → "이미 다른 사람이 쓰고 있어요. 다른 아이디를 지어볼까요?"
- `profileEdit.fileTypeError`/`fileSizeError` → "JPEG·PNG·WebP 사진만 올릴 수 있어요" /
  "5MB 이하 사진만 올릴 수 있어요"
- `profileEdit.uploadError`/`saveError` → §4.1 3단계 중 원인이 빠짐 →
  "사진을 올리지 못했어요. 연결이 불안정했을 수 있어요." (+ CTA `[다시 시도]`) /
  "프로필을 저장하지 못했어요. 연결이 불안정했을 수 있어요." (+ CTA `[다시 시도]`)
- `d.common.authRequired`("인증이 필요해요")는 **티켓 20260916_0904로 이미 통합됨** — 이
  티켓에서는 중복 수정하지 않는다.

## 구현 계획
1. (A) 용어표 등재 + §4.2 예시·`privacy/page.tsx` 정합화를 먼저 처리한다.
2. (B) `ko.ts` 값을 확정된 용어에 맞춰 교정한다.
3. 완료 후 `/im-not-ai`로 재검사한다.

### 구현 내용 요약
1. `UX_WRITING_GUIDELINE.md` §1.3에 "아이디(ID)" 용어를 신규 등재했다 — "유저를 가리키는
   고유 식별자"로 정의하고, 자유롭게 바꿀 수 있는 `display_name`(표시 이름)과 구분되는
   개념임을 명시했다. X-리스트: ID, 닉네임, 유저명, 사용자명, 계정명.
2. §4.2(인라인 폼 검증 에러) Good/Bad 예시의 "닉네임"을 모두 "아이디"로 교체하고, 실제
   `ko.ts` 값(2~30자, 이미 다른 사람이 쓰고 있어요 등)과 예시 문구를 일치시켰다.
3. `privacy/page.tsx`(142·170·428행)의 "닉네임"을 코드로 대조한 뒤 "아이디"로 교체했다.
   170행에서 "사용자명(닉네임)"과 "표시 이름"이 이미 서로 다른 두 항목으로 나열돼 있어
   (`display_name`과 명확히 분리) — "닉네임"이 가리키는 대상이 `username` 필드라는 점을
   확인하고 안전하게 치환했다.
4. `NotificationsClient.tsx`는 코드 주석("닉네임이 밖으로 삐져나오는 것을 막는 최후 수단")
   뿐이며 사용자 노출 문구가 아니다. 또한 그 자리에 실제로 렌더되는 값은 `getDisplayName()`이
   `display_name` 우선, 없으면 `username`으로 대체하는 로직이라 순수한 "아이디" 개념이
   아니다 — display_name과 혼동될 수 있는 지점이라 판단해 건드리지 않았다.
5. `ko.ts` `onboarding`/`profileEdit` 딕셔너리 값을 티켓 (B) 요구사항대로 전부 교정했다
   (예시값 placeholder 전환, 긍정형 점(.) 규칙, 3단계 구조 원인 보강 등). `uploadError`/
   `saveError`가 렌더되는 위치(onboarding/page.tsx, profile/edit/page.tsx)에는 실제
   버튼이 없어 CTA는 붙이지 않고 문구만 완성했다.
6. `d.common.authRequired`는 티켓 20260916_0904에서 이미 처리돼 있어 손대지 않았다.
7. 코드베이스 전체를 grep해 "닉네임/유저명/사용자명/계정명"이 남아있는 다른 지점을 확인한
   결과, 남은 항목은 전부 (a) 어드민 화면(`src/app/admin/**`, 티켓 범위 제외 대상) 아니면
   (b) 코드 주석으로, 사용자 노출 문구 충돌은 없었다.

### 주요 의사결정 / 핵심 메모
- `privacy/page.tsx`는 "닉네임(사용자명)"·"사용자명(닉네임)" 두 형태로 같은 개념(username)을
  괄호 병기하고 있었다. 병기를 유지하지 않고 "아이디" 단독 표기로 정리했다 — 이미 §1.3에
  고정 용어로 등재됐으므로 굳이 옛 표기를 병기해 법적 문서에 불일치를 남길 이유가 없다고
  판단했다.
- NotificationsClient.tsx는 건드리지 않기로 한 판단의 근거: 그 자리에 렌더되는 값이
  `getDisplayName({ username, display_name })` 함수를 통해 display_name 우선으로 결정되므로,
  "아이디"(username 고유 개념)로 단정해 교체하면 오히려 부정확한 표기가 된다.

- `/im-not-ai` 명령이 이 저장소/환경에 정의돼 있지 않아 실제 실행은 못 했다. 사용자가 별도
  환경에서 재검사를 원하면 위에서 나열한 변경 파일 3건을 대상으로 돌리면 된다.
