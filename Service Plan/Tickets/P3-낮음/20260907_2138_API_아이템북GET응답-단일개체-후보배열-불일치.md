# [API] 아이템북 GET 응답이 개체 후보 배열이 아닌 단일 개체를 반환한다

## 배경 / 문제 정의

티켓 [20260907_2059](20260907_2059_UI_아이템배지-개체별-상세라우팅-및-장착개체-선택.md)
게이트 리뷰에서 발견된 범위 밖 항목이다.

`jam-web/src/app/api/itembooks/[id]/route.ts:95-122`는 배지당 **단일** `inventoryItem`(슬롯이
없으면 미장착 첫 번째)을 반환한다. 반면 컬렉션 상세 페이지(`collections/[id]/page.tsx`)는
20260907_2059에서 **미장착 개체 후보 배열 전체**를 들고 오도록 바뀌었다. 같은 데이터를 만드는
두 경로의 shape가 어긋난 상태로 남았다.

현재 이 GET을 소비하는 클라이언트는 검색되지 않아 **사용자 영향은 없다.** 다만 방치하면
다음 작업자가 이 API를 정본으로 오해해, 개체 선택 기능이 없는 옛 전제 위에 화면을 만들 수 있다.

부수적으로, 페이지 쪽은 `obtained_at ASC`로 정렬해 후보를 뽑는데 API 쪽은 정렬 없이
`invItems.find(...)`로 임의 순서 첫 번째를 고른다 — 선택 규칙 자체도 서로 다르다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 다음 중 하나를 택한다:
  1. **API를 페이지와 같은 shape로 맞춘다** — 후보 배열 + `obtained_at ASC` 정렬
  2. **미사용 API를 제거한다** — 소비자가 없음을 재확인한 뒤 삭제
- 선택 전에 소비자 유무를 다시 검색할 것 (이 티켓 작성 시점 기준 0건)

## 구현 계획
1. `GET /api/itembooks/[id]`를 실제로 호출하는 클라이언트가 있는지 재검색
2. 소비자가 없으면 옵션 2(API 제거)를 채택

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
`GET /api/itembooks/[id]`(`route.ts`)를 소비하는 클라이언트를 재검색한 결과, 사용처가
0건임을 재확인했다 — `fetch(`/api/itembooks/${...}`)` 패턴은 `SlotGrid.tsx`에서 `/slot`
서브라우트(POST)만 호출하고 있었고, `collections/[id]/page.tsx`(실제 서비스 화면)는 이
GET을 거치지 않고 서버 컴포넌트에서 직접 Supabase 쿼리로 데이터를 구성한다. 티켓의 정책
결정에 따라 shape을 맞추는 대신 **미사용 API 자체를 삭제**했다. 같은 디렉터리의
`[id]/slot` 서브라우트(POST 핸들러)는 실사용 중이므로 그대로 유지했다.
