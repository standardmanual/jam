# [UI] 장착 개체 선택 시트 — 요청 진행 중 상태의 잔여 엣지케이스 4건

## 배경 / 문제 정의

티켓 [20260907_2221](20260907_2221_UI_장착개체-선택시트-ListRowCard-재구성.md) 3차 보완의
게이트 재리뷰가 남긴 사이드 파인딩이다. 전부 경미하고 지시 범위 밖이라 그 티켓에서는 손대지
않았다. 발생 빈도가 낮거나 사용자 영향이 작아 P3로 둔다.

## 상세 요구사항

### 1. 요청 중단 판정이 배지 단위가 아니라 전역이다

`sheetBusy`가 `pendingBadgeId != null`이라, 배지 A의 장착 요청이 도는 동안(그리드에서는 A의
버튼만 비활성) 배지 B의 「추가」를 눌러 시트를 열면 **B의 시트도 모든 행이 억제되고 닫기도
막힌다.** A의 요청이 끝나면 자동으로 풀리는 1초 미만의 과도 상태이고, 1차 구현부터 있던 같은
전역 판정(`disabled={pendingBadgeId != null}`)이라 이번 리팩터가 만든 회귀는 아니다.

### 2. 네트워크가 끊기면 시트에 갇힌다

요청 중 닫기를 무시하도록 만들었는데(20260907_2221 3차, 의도된 설계), 요청에 타임아웃이나
`AbortController`가 없어 응답이 영영 안 오면 그동안 시트를 닫을 수 없다.

### 3. 억제된 행이 키보드로는 여전히 접근된다

`opacity-40 pointer-events-none`만 주고 `disabled`를 쓰지 않아, 마우스 클릭은 막히지만
키보드 Tab으로는 여전히 포커스·Enter 입력이 된다(동작 자체는 `handleSelectCandidate`의 가드가
막아 무동작으로 끝난다). 완전한 키보드 억제는 `ListRowCard`(13개 화면 공용)에 `disabled` prop이
필요해 범위 밖으로 남겨졌다.

### 4. 장착 실패 후 후보 목록이 스스로 갱신되지 않는다

`requestSlot`은 성공 시에만 `router.refresh()`를 부른다. 409(이미 다른 개체가 장착됨) 실패 후
후보 목록은 능동으로 다시 조회되지 않는다 — 3차의 `sheetView` 이중 폴백은 "상위에서 갱신이
도착하면 시트가 따라간다"만 보장할 뿐, 실패 자체가 갱신을 유발하지는 않는다.

## 구현 계획
> 착수 시 방향을 정한다. 넷 다 굳이 함께 고칠 필요는 없다 — 개별 우선순위로 봐도 된다.

- 1번: 판정을 배지별로 좁히거나(맵 형태), 과도 상태 자체를 없앨 필요는 없다고 판단해 현행 유지
- 2번: fetch에 타임아웃 추가, 또는 진행 중에도 닫기를 허용하되 완료 후 실패를 별도로 알리는
  방식으로 전환(20260907_2221이 배제한 배너 방식이 아닌 토스트 등)
- 3번: `ListRowCard`에 `disabled`/`aria-disabled` 추가 여부 판단 — 13개 화면 회귀 표면 고려
- 4번: 실패 시에도 `router.refresh()`를 부르거나, 시트 안에서 후보를 능동 재조회
