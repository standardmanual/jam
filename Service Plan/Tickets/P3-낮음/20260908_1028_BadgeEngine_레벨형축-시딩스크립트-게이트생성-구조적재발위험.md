# [BadgeEngine] 레벨형(무한레벨) 축 게이트 처리가 시딩 스크립트 두 곳에서 구조적으로 빠져 있음

## 배경 / 문제 정의

티켓 [20260908_1017](20260908_1017_BadgeEngine_게이트미션-누적축-노출조건-등급오류-보상게이트-연결.md)
개선 리뷰(progressive-reviewer)에서 나온 범위 밖 발견물.

이번에 고친 "누적" 축 5종 미션의 두 버그(노출조건 등급오류·보상 게이트 미연결)는 **데이터만**
교정했다 — 근본 원인인 시딩 스크립트 자체는 그대로 남아 있다:

- [v5_mission_seed_build.py](v5_mission_seed_build.py) 250~251행:
  게이트 미션 40종의 `visibility_rule_json`을 축 종류(등급형/레벨형) 구분 없이 전부
  `min_rarity: epic/mystic`로 일괄 생성한다.
- [v5_gate_build.py](v5_gate_build.py) 262행:
  `if f.kind not in ('graded', 'repeatable'): continue`로 레벨형(`kind='leveled'`) 계열을
  `gate_mission_badge` 부여 대상에서 완전히 제외한다.

지금은 "누적" 축(모든 종목에 걸쳐 유일한 레벨형 게이트 축)만 이 사각지대에 있어 5종 미션에서만
문제가 됐지만, **향후 새 종목이나 새 레벨형 축이 추가되면 같은 두 버그(무한 불충족 노출조건,
미연결 보상 게이트)가 그대로 재발한다.**

## 상세 요구사항

### 서비스/코드베이스 관점
- `v5_mission_seed_build.py`에 "대상 축이 레벨형이면 `min_level` 사용" 분기 추가
- `v5_gate_build.py` 262행의 leveled 계열 제외 로직을 "레벨형은 별도 규칙(자기 최고 레벨 행에
  게이트)으로 처리"하도록 확장

## 구현 계획

다음에 레벨형 축이 있는 게이트 미션을 새로 시딩할 때, 이번 티켓(20260908_1017)에서 확정한
"레벨형 축은 `min_level` 기준 + 자기 최고 레벨 행에 `gate_mission_badge`" 패턴을 스크립트
로직으로 일반화한다. 지금 당장 급한 작업은 아니다 — 새 레벨형 축이 실제로 추가될 때 함께
처리해도 무방하다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
두 시딩 스크립트에 "대상 축이 등급형인지 레벨형인지"를 `FAMS`(`f.kind`)로 기계적으로 판정하는
분기를 추가했다 — 더 이상 "누적" 축을 하드코딩으로 특별 취급하지 않는다.

- **`v5_mission_seed_build.py`**: `v5_gate_build.py`의 `FAMS`를 추가로 가져와
  `FAM_BY_KEY`/`max_level_of()` 헬퍼를 만들었다. `visibility_rule_json` 생성부에서 대상
  `visibility_family_keys`가 전부 `kind == 'leveled'`면 `min_rarity` 대신 `min_level`을 쓴다
  (`hide_when_owned` = 대상 계열 중 최단 사다리 상한, `require_owned` = 그 절반을 내림 — 티켓
  20260908_1017이 수기로 확정한 산정 기준을 그대로 공식화했다).
- **`v5_gate_build.py`**: `f.kind == 'leveled'` 전용 분기를 신설해 `leveled_results` 리스트에
  담는다(등급형 `results`와 완전히 분리 — 기존 `epic_rows`/`mystic_rows`/`min_level_rows`
  카운트 assert에 영향 없음). 각 레벨형 계열의 "자기 최고 레벨"(`f.rows`에서 `lv is not None`인
  값의 최댓값)에 `gate_mission_badge`를 건다. SQL 생성부에도 `level = {level} AND rarity IS
  NULL` 매칭 UPDATE 블록을 추가하고, `v5_gate_mapping.json`에도 `레벨형_패치` 키로 감사
  가능하게 남겼다.

**검증**: 두 스크립트를 로컬에서 직접 실행해(DB 미접속, 파일 쓰기만) 생성된 SQL을 확인한 결과,
티켓 20260908_1017이 수기로 확정해 이미 DB에 실행한 값(레벨형 5축 12행의 `min_level: 3/6`,
`gate_mission_badge` 대상 family_key·level 12건)과 **완전히 일치**했다 — 일반화 로직이 기존
수기 결정을 정확히 재현한다는 교차검증이다. 확인 후 두 출력 파일(`seed_v5_gate_conditions.sql`,
`seed_v5_gate_missions.sql`)과 `v5_gate_mapping.json`은 이미 실행된 마이그레이션 산출물이므로
`git checkout`으로 원상복구했다 — 이 티켓은 **스크립트 로직만** 고치고 새 SQL을 재생성/재실행
하지 않는다(재발 방지 목적, 지금 당장 급하지 않다는 티켓 본문 지시와 일치).
