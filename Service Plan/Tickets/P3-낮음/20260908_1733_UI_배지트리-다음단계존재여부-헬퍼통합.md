# [UI] 배지 트리 "다음 단계 존재 여부" 판정을 공통 헬퍼로 통합

## 배경 / 문제 정의
> 왜 이 작업이 필요한가. 현재 상태와 기대 상태의 차이.

티켓 [20260908_1727](../P2-일반/20260908_1727_UI_배지트리-반복형-다음등급칩-오표시.md)의
progressive-reviewer 개선 제안이다.

`jam-web/src/components/badges/BadgeFamilyRow.tsx`는 배지 유형(반복형/등급형/무한레벨형) 3종
분기에서 "다음 단계가 남았는지"를 각각 다른 방식으로 계산한다.

- 등급형(`graded`): `stops.find(s => s.status !== 'earned')`로 미획득만 걸러 next로 삼음
- 무한레벨형(`leveled`): `nextLevel != null`일 때만 표시
- 반복형(`repeatable`): 이번 티켓(1727) 수정 전까지 획득 여부 체크가 아예 빠져 있었음

세 분기가 같은 목적("다음 단계가 있을 때만 칩 표시")을 서로 다른 패턴으로 구현하고 있어서, 이번처럼
한 분기만 체크가 빠지는 사고가 다시 생길 수 있다. 티켓 1727은 반복형 분기 하나만 급한 대로 고쳤고,
이 티켓은 세 분기의 판정 로직을 공통 헬퍼로 정리하는 리팩터링을 다룬다.

추가로, 1727 진행 중 발견된 별도 관찰도 이 티켓에서 함께 확인한다: 최고 등급을 이미 획득한 반복형
계열에서 "0/1회" 같은 회차 진행률 표시가 여전히 남아있는지(다음 등급칩은 사라졌지만 회차 카운터는
별도 로직이라 확인이 안 됐다) — 배포 후 실제 화면에서 확인 후 필요하면 범위에 포함한다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 세 분기의 "다음 단계 존재 여부" 판정을 공통 함수(예: `hasNextStage(family, kind, earnedBadgeIds)`
  또는 유사한 이름)로 뽑아, `BadgeFamilyRow.tsx`가 이 함수 하나만 호출하도록 정리한다.
- 리팩터링이므로 기존 세 분기의 실제 표시 결과(어떤 조건에서 칩이 뜨고 안 뜨는지)는 그대로
  유지해야 한다 — 동작 변경이 아니라 구조 정리다.

### UI/UX 관점 (해당 시)
- 최고 등급 달성 반복형 계열에서 회차 진행률("0/1회" 등) 표시가 여전히 남아있는지 실제 화면에서
  확인한다. 남아있고 부적절하다면(다음 단계가 없는데 진행률만 남는 게 어색하다면) 함께 정리한다 —
  단, 확인 결과 문제없다고 판단되면 이 항목은 건드리지 않는다.

### 컨텐츠 관점 (해당 시)
- 해당 없음.

## 구현 계획
> 어떻게 구현할지. 접근 방법, 영향 범위, 주요 변경 포인트.

1. 세 분기의 현재 조건식을 나란히 놓고 공통 시그니처를 설계한다.
2. 헬퍼 함수로 추출 후 `BadgeFamilyRow.tsx`가 그 함수를 호출하도록 교체한다.
3. 반복형/등급형/무한레벨형 각각 최소 1개 계열씩 표시 결과가 리팩터링 전후로 동일한지 확인한다.
4. 회차 진행률 잔존 여부는 실제 배포된 화면에서 확인 후 필요 시에만 손댄다.
5. 순수 리팩터링+선택적 소규모 UI 조정이라 라이트하게 처리 가능 — 다만 카테고리가 UI이므로
   기존 `bug` 파이프라인과 동일하게 회귀 확인에 집중한다.
