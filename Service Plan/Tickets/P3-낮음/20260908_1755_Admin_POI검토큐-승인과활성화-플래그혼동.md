# [Admin] POI 검토 큐의 "승인" 버튼과 편집 화면의 "활성화"가 서로 다른 플래그를 다뤄 혼동을 만든다

## 배경 / 문제 정의
> 왜 이 작업이 필요한가. 현재 상태와 기대 상태의 차이.

티켓 [20260907_1811(POI 자동수집 중단, 수동등록 전환)](20260907_1811_Infra_POI-자동수집-중단-수동등록-전환.md)
게이트 리뷰에서 범위 밖으로 지적된 사항이다.

임시등록으로 만든 POI에 대해 검토 큐(`/admin/poi/review`)에서 **"승인"** 버튼을 누르면
`pending_review`만 해제되고 `is_active`는 그대로 `false`로 남는다. 그 결과 POI가 검토 큐에서는
사라지지만 여전히 서비스에 노출되지 않는(비활성) 상태로 남는다. 실제 노출을 켜려면 편집 화면
(`/admin/poi/[id]`)에서 별도로 **"활성화"** 저장을 해야 한다.

즉 "승인 = 활성화"라고 오해하기 쉬운 구조인데, 실제로는 두 버튼이 서로 다른 플래그
(`pending_review` / `is_active`)를 각각 다룬다. 1811에서 검토 큐에 "노출" 열과 안내문을
추가해 혼동을 완화했지만, 근본적으로 동작 두 가지가 별개 버튼에 분산돼 있다는 구조는 그대로다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 판단이 필요한 지점: 검토 큐의 "승인" 버튼을 없애고, 편집 화면의 활성화 저장만을 유일한
  통과 경로로 만들지(1811 게이트 리뷰가 제안한 방향), 아니면 "승인" 버튼 자체가 `is_active`도
  함께 켜도록 동작을 바꿀지 결정한다.
- 검토 큐에 남겨질 정보(비노출 상태로 남은 "승인된" POI 목록을 어떻게 계속 추적할지)도 함께
  고려한다.

### UI/UX 관점 (해당 시)
- 어느 방향이든, 검토 큐와 편집 화면 두 곳에서 동작이 겹치지 않고 사용자가 "이 버튼을 누르면
  정확히 무슨 일이 일어나는지" 헷갈리지 않아야 한다.

### 컨텐츠 관점 (해당 시)
- 해당 없음.

## 구현 계획
> 어떻게 구현할지. 접근 방법, 영향 범위, 주요 변경 포인트.

1. 두 방향(승인 버튼 제거 vs 승인 버튼이 활성화까지 겸함) 중 하나를 결정한다.
2. `PoiReviewTable.tsx`·`/api/admin/poi/[id]/route.ts`(또는 검토 승인 전용 API가 있다면 그쪽)를
   결정에 맞게 수정한다.
3. 1811에서 추가한 "노출" 열·안내문이 새 동작과 여전히 맞는지 함께 점검한다.
