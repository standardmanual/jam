# [Infra] 스테이징 테스트 계정에 획득 배지 시드 데이터가 없음

## 배경 / 문제 정의
티켓 `20260911_1102`(배지 공유 시트 이미지 선택 캐러셀 추가) 게이트 리뷰 과정에서 발견된
범위 밖 사항이다.

스테이징 테스트 계정(`dev-tester@jam.local`, `user_id 00000000-0000-0000-0000-000000000001`)이
획득한 배지가 activity·item 유형 모두 0건이다. 이 때문에 배지 상세·공유 관련 UI 작업을
로컬/스테이징에서 실렌더로 검증하려면 매번 실제 배지 보유 계정을 별도로 찾아야 하고,
`admin` 관점의 실렌더 검증(`DEV_PROCESS_GUARDRAILS.md` 패턴 13)조차 이 제약 때문에 온전히
수행하지 못하는 경우가 생긴다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 스테이징 테스트 계정에 activity형·item형 배지를 각 1~2종 이상 시드하는 SQL 작성
  (`Service Plan/Specs/DEV_PROCESS_GUARDRAILS.md` 원칙에 맞춰 `seed_*.sql`로 저장).
- 레벨형·반복 획득형(COUNT ≥ 2) 배지도 최소 1종씩 포함해, 공유 카드의 LEVEL/COUNT 행
  렌더링까지 실렌더로 확인 가능하게 한다.

## 구현 계획
> DB 변경이므로 CLAUDE.md 5번 규칙에 따라 SQL 파일 작성 후 사용자 승인 하에
> 오케스트레이터가 직접 Supabase에 실행한다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
`seed_20260911_1116_dev_tester_badge_variety.sql` 작성. `seed_dev_test_user.sql`(기존, 유저·인벤토리·
activity 3건·item 3건·checkin 2건 시드)이 이미 적용돼 있다는 전제 위에서, 이 티켓이 지적한 공백인
**레벨형(LEVEL)·반복획득형(COUNT≥2)** 배지를 각 1종씩 추가로 채운다. 모두 실제 배지 ID를 하드코딩하지
않고 서브쿼리로 조회(시드 실행 시점 DB 상태 의존, 대상 없으면 해당 블록만 스킵)하며, 전 구간
idempotent(`ON CONFLICT DO NOTHING`)하게 작성했다.

- activity 등급형(`rarity IS NOT NULL`, `repeat_count` 없음) 미보유 2종 보강
- 레벨형(`rarity IS NULL AND level IS NOT NULL`) 1종 — `badgeRow.level` → 공유 카드 LEVEL 행 검증용
- 반복획득형(`condition_json ? 'repeat_count'`) 1종 — `earn_count=3`, `earn_history` 3건 채움 →
  공유 카드 COUNT(×N) 행 검증용 (BadgeShareBlob 로직상 `level`이 null이고 `earnCount>1`일 때만 노출)
- item 미보유 2종 보강 + `inventory.used_slots` 동기화
- 0번 블록에서 dev-tester `public.users` 행 부재 시 `RAISE EXCEPTION`으로 실행을 막아, 전제
  시드(`seed_dev_test_user.sql`) 미적용 상태에서 이 파일만 단독 실행되는 사고를 방지

### 주요 의사결정 / 핵심 메모
- 레벨형/반복형 판정 기준은 `BADGE_ENGINE_UNIFIED.md` §2("등급 판정은 `rarity IS NULL` 하나뿐",
  "반복형은 `rarity` + `condition_json.repeat_count`")를 그대로 따름.
- 공유 카드(`buildBadgeShareBlob.ts`)의 LEVEL/COUNT 행은 `badges.level`과
  `user_activity_badges.earn_count`에서 각각 나오며 상호 배타적이라, 두 종류를 서로 다른
  배지에 나눠 심었다(한 배지에 둘 다 채워도 LEVEL이 우선이라 COUNT 검증이 안 됨).
- DB에 레벨형/반복형 배지가 실제로 존재하지 않으면 해당 INSERT는 조용히 0건 처리된다 —
  이 경우 별도 콘텐츠 시드가 선행되어야 하므로, 실행 후 확인 쿼리 결과를 반드시 보고할 것.

### 잔여 이슈
- 이 SQL은 아직 실행되지 않았다. 사용자 승인 후 오케스트레이터가 Supabase에 직접 실행하고,
  결과(LEVEL 1건·COUNT≥2 1건 실제로 채워졌는지)를 확인해야 한다.
