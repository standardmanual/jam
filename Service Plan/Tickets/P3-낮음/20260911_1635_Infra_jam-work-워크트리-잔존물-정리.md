# [Infra] jam-work 재시도 후 낡은 워크트리가 브랜치명을 점유해 다음 재시도를 막을 뻔함

## 배경 / 문제 정의

티켓 [20260911_1454](../P2-일반/20260911_1454_Admin_투데이컨텐츠-화면리뉴얼.md)의 게이트
리뷰 FAIL 후 재시도에서, jam-developer가 지시받은 대로 review 브랜치
(`claude/jamwork-20260911_1454-today-content-renewal`)를 이어받으려 했으나 1차 구현이
만든 워크트리(`wf_23c105a9-c25-1`, 구 커밋 099d93a4 = FAIL 시점 상태)가 같은 브랜치명을
이미 점유하고 있어 `git checkout -B`가 `fatal: already used by worktree`로 실패했다.

개발자가 우회(로컬 브랜치를 origin에 맞춰 reset + `git push origin HEAD:<브랜치>`로 원격만
갱신)해서 이번엔 결과에 영향이 없었지만, 게이트 리뷰가 "다음 재시도에서도 같은 충돌이
재발할 수 있다"고 sideFinding으로 명시했다.

## 상세 요구사항

### 서비스/코드베이스 관점
- jam-work 파이프라인이 게이트 FAIL 후 재시도할 때, 직전 시도가 만든 워크트리를 정리하지
  않고 새 워크트리(`wf_{runId}-1`)를 또 만드는 구조로 보인다. FAIL이 반복되면 같은 브랜치를
  참조하는 워크트리가 계속 쌓여 언젠가는 개발자의 우회조차 불가능한 상황(예: 여러 워크트리가
  동시에 활성화된 경우)이 생길 수 있다.
- 근본 대응은 `.claude/workflows/jam-work.js`가 재시도 시작 전에 같은 티켓의 이전 워크트리를
  정리하거나, jam-developer 프롬프트에 "체크아웃 전에 기존 점유 워크트리를 먼저 제거하라"는
  절차를 포함시키는 것으로 보인다 — 이번 티켓 범위(투데이 컨텐츠 리뉴얼)를 벗어나 별도로
  다룬다.

## 구현 계획
이번 발견 시점에 실제로 잔존해 있던 `wf_23c105a9-c25-1`은 오케스트레이터가 직접
`git worktree remove`로 즉시 정리했다(미커밋 변경 없음 확인 후). 재발 방지(파이프라인
자체의 정리 로직 추가)는 이번 티켓에서 다루지 않는다.
