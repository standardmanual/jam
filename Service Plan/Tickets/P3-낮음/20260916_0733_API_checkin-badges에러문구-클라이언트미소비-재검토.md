# [API] checkin-badges 에러 문구 클라이언트 미소비 — 재검토

> 출처: 티켓 20260915_2238(배지 도메인 텍스트 정비) 게이트 리뷰 sideFinding — 자동 티켓화

## 배경 / 문제 정의

티켓 20260915_2238에서 `src/app/api/checkin-badges/route.ts`의 하드코딩 에러 문구를
`d.badges.checkinMap*Error`로 이관하고 ADR 0001에 맞춰 3단계 구조를 적용하려 했으나,
현재 클라이언트(`DropsClient.tsx`)가 `!res.ok`일 때 응답 본문을 읽지 않고 조용히 무시하고
있어 이 문구가 실제로는 사용자에게 노출되지 않는다는 사실이 게이트 리뷰에서 확인됐다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `DropsClient.tsx`가 `checkin-badges` 호출 실패 시 사용자에게 아무 피드백도 주지 않는
  현재 동작이 의도된 것인지 확인한다(예: 백그라운드 조회라 실패해도 무해한 경우 vs
  실제로는 사용자가 알아야 하는 실패인데 누락된 경우).
- 노출이 필요하다고 판단되면 `DropsClient.tsx`가 응답 본문의 `message`를 읽어 토스트로
  띄우도록 고치고(ADR 0001에 따라 서버 메시지를 그대로 신뢰), 이미 이관된
  `d.badges.checkinMapMissingBoundsError` 등 4개 문구가 실제로 3단계([현상]→[원인]→[해결책])
  구조를 충분히 갖추고 있는지 이 시점에 다시 검토한다(현재는 간결하게만 작성돼 있음 —
  후속 티켓 20260916_0734의 한국어 리뷰 지적사항 참고).
- 노출이 불필요하다고 판단되면(백그라운드 실패 허용) 그 판단과 근거를 이 티켓에 기록하고
  CLOSED 처리한다.

## 구현 계획
- 먼저 `DropsClient.tsx`의 `checkin-badges` 호출 목적과 실패 시 UX 의도를 코드·티켓 이력에서
  확인한다.
- 노출 여부 결정 후 필요한 만큼만 구현한다.
