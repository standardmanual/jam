# 서버 API 에러 메시지는 딕셔너리를 단일 진실 소스로 삼는다

조사 결과 `app/api/**` 내 다수의 비관리자용 라우트가 에러 메시지를 하드코딩하고 있었고, 클라이언트가 이를 처리하는 방식도 파일마다 달랐다 — `DropsClient.tsx`/`CombineClient.tsx`는 서버 메시지를 무시하고 자체 딕셔너리 문구를 표시하는 반면, `MissionDetailClient.tsx`는 서버가 보낸 하드코딩된 한글 원문을 그대로 토스트에 노출했다. 이런 혼재가 서비스 전반의 톤 불일치를 낳은 구체적 원인 중 하나로 확인됐다.

`src/lib/i18n`는 `'use client'` 지시어가 없는 순수 모듈이라 서버·클라이언트 양쪽에서 동일하게 import할 수 있다는 사실을 근거로, **서버 API route도 `d.*` 딕셔너리를 직접 참조해 에러 메시지를 생성하고, 클라이언트는 서버가 보낸 메시지를 그대로 신뢰해 노출한다**는 단일 규칙을 채택한다. 같은 에러 문구를 서버와 클라이언트 양쪽에 중복 정의하지 않는다.

## 고려한 대안

- **클라이언트가 항상 자체 문구 사용**(서버 메시지는 화면에 노출하지 않음): 단순하지만 서버만 아는 상태 의존적 사유(예: "이미 신청한 미션입니다")를 클라이언트가 재현하려면 동일한 조건 분기를 중복 구현해야 한다.
- **상황별 혼용**(서버 고유 사유만 노출, 일반 오류는 클라이언트 고정 문구): 유연해 보이지만 "서버 고유 사유"와 "일반 오류"의 경계가 또 모호해져, 지금 겪고 있는 파일별 불일치 문제를 반복할 위험이 크다고 판단해 기각했다.
