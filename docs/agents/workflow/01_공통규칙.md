# 팀 공통 규칙

| # | 규칙 |
| --- | --- |
| 1 | 에이전트 정의는 **영어**로 작성한다. 출력은 한국어다 |
| 2 | 카리나가 **티켓 요약본**(요구사항·구현 계획·관련 파일)만 전달한다. 전체 티켓은 필요할 때만 읽는다 |
| 3 | `CLAUDE.md`는 모두에게 필요한 규칙만 남긴다. 카리나 전용 내용은 참고 문서로 옮긴다 |
| 4 | 에이전트 정의에 매번 바뀌는 값을 넣지 않는다. 자주 수정하지 않는다 |
| 5 | 큰 파일은 검색으로 위치를 찾은 뒤 그 부분만 읽는다 |
| 6 | 이상 신호는 **참고 / 주의 / 중단**, 확신도는 **높음 / 보통 / 낮음** |
| 7 | 하니 말투(사용자에게 보이는 글의 말투)는 전체 설정이 끝난 뒤 정한다 |
| 8 | 한국어 문장 지침(`fluent-korean.md`)을 사용자에게 보이는 모든 글에 적용한다. 이 문서는 요약본을 만들지 않는다 |
| 9 | **슬롭 제거** — 글·시각·설계 세 종류를 각 담당이 관리한다 |
| 10 | 평소 개발 흐름에는 4명만 관여한다 (카리나·아현·민지·채원) |
| 11 | **묶음 승인** — 문서 갱신은 머지 승인과 함께, 홈피드는 주 1회 7건, 티켓 우선순위는 주간 브리핑에서 |
| 12 | 예약 작업은 2개로 묶는다. 주간(브리핑+피드 초안), 월간(트렌드+문서 점검+시즌 제안) |
| 13 | 스크립트는 1차 7개(`verify`·리뷰 준비·현황판·승인 후 처리·어드민 API 읽기·작업 공간 준비·push hook), 나머지는 2차. 목록은 `05_자동화목록.md` |
| 14 | 리스크는 시점으로 나눈다. 만들기 전 혜린 / 코드 단계 민지 / 운영 중 카즈하 |
| 15 | 문서는 시점으로 나눈다. 신규 기능 정의 혜린 / 구현 결과 반영 아현 / 누락 점검 민지 / 체계·템플릿·정기 점검 하니 |

## 슬롭 제거 기준

| 종류 | 걷어낼 것 | 담당 |
| --- | --- | --- |
| 글 슬롭 | 상투구("~을 통해", "혁신적인", "여정"), 번역투, 과장, 의미 없는 수식, 반복, 이모지 남발, 내용 없는 서론·맺음말 | 글 쓰는 전원 + 한국어 리뷰(건당 1회) |
| 시각 슬롭 | 의미 없는 그라디언트·유리질 효과, 뜻 없는 아이콘, 습관적 가운데 정렬, 재고 이미지 느낌 | 채원 (배지 이미지는 윈터와 함께) |
| 설계 슬롭 | 의미 없는 기능·배지 남발, 근거 없는 효과 주장, 채우기용 화면, 가짜 긴급감 | 혜린·민지·카즈하 |

**작동 방식:** JAM 문장 사전(금칙 표현 + 대체 표현) → `verify`의 스크립트 검사 → 한국어 리뷰 → 사용자가 거슬린 표현을 사전에 추가.
초기 목록은 AI 씬의 보편 기준으로 시작한다.

## 티켓 생성 권한

| 주체 | 권한 |
| --- | --- |
| 카리나 (메인 세션) | 티켓 생성·상태 변경·종료, 우선순위 확정, 중복 확인 |
| 혜린 | 티켓 내용·분해안·우선순위 제안 (확정은 카리나 절차) |
| 카즈하 (예약 세션) | 티켓 **초안**만 (`분류 대기` 표시, 우선순위 비움) |
| 그 외 서브에이전트 | 발견물·제안만 반환 |

| 16 | 데이터 쓰기·읽기는 DB 직접이 아니라 **어드민 API**를 통한다. 권한 검사와 검증 로직을 그대로 탄다 |
| 17 | 모델은 에이전트 정의의 `model` 키로 고정한다. 메인 세션은 `settings.json`의 `model`로 고정한다 |
| 18 | 서브에이전트는 호출마다 `CLAUDE.md` 전체를 자동으로 받는다(호출당 약 8.4KB). **에이전트별로 선택 제외하는 공식 기능은 없음** (2026-09-18 확인, 티켓 20260918_0422). 아현·민지 외 나머지도 기술적으로는 다 받는다 |
| 19 | `settings.json` 거부 목록에 `Bash(git commit --no-verify)`·`Bash(git push --no-verify)`를 넣어 검사 우회를 막는다 |
| 20 | 요약본·지도·패턴 카드를 만들지 않는다. 원본을 검색해서 필요한 부분만 읽는다 (사본이 낡는 위험을 없앤다) |
| 21 | 개선 리뷰 단계는 두지 않는다. 위험을 줄이는 개선점은 민지의 범위 밖 발견물로 처리한다 |
| 22 | 티켓에 **완료 조건**(무엇을 어떻게 확인하면 끝인지)을 반드시 적는다 |
| 23 | 사용자가 제안을 거절하면 **이유를 결정 기록에 남긴다** |
| 24 | 미션·홈피드·드랍·캠페인이 끝나면 **결과 한 줄**을 남긴다. 다음 제안은 그 기록을 먼저 본다 |
| 25 | 여러 에이전트가 얽힌 작업은 **상위 티켓 1개 + 하위 티켓** 구조로 묶는다 |
| 26 | 처리 규칙표는 **공용**이다. 에이전트별 섹션을 두고 각자 자기 섹션만 읽는다 |
