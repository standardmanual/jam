# 데일리 미팅

> 신설: 2026-10-14, 티켓 20261014_1647. 시험 회의 1회차 결과는 `docs/operations/reports/daily/2026-10-14.md`다.
> **이 문서는 진행 규칙만 정의한다.** 사용자의 피드백을 받아 발전시키는 문서이므로 바뀌면 같은 날 이 문서를 고치고 git 이력으로 변경을 남긴다.

## 목적

서비스와 JAM 2.0 재설계에 대해 각 분야의 시선을 하루에 한 번 한 자리에 모아, **사람이 읽고 결정할 것**을 짧게 올린다. 예약 루틴(주간·월간 리포트 등)이 2026-10-07에 모두 삭제된 뒤 비어 있는 점검 자리를 부분적으로 메우는 목적도 있다. 회의는 의견과 제안만 낸다.

## 참석

| 역할 | 에이전트 | 관점 |
|---|---|---|
| 사회 | 카리나(오케스트레이터) | 안건 준비, 사실 정정, 합의·이견 정리, 리포트 작성 |
| 참석 | 혜린(`jam-pm`) | 기획·우선순위, 열린 결정 |
| 참석 | 카즈하(`jam-ops`) | 운영 지표·위험 신호 |
| 참석 | 채원(`jam-designer`) | 디자인 시스템·UX. 사용자가 만드는 디자인 단계의 결정을 앞서가지 않는다 |
| 참석 | 윈터(`jam-tribe`) | 세계관·트라이브 정합 |
| 참석 | 윤진(`jam-marketer`) | 유저에게 가는 말·온보딩·홈피드 |
| 참석 | 하니(`jam-guide`) | 문서 체계의 건강 |

아현(`jam-developer`)과 민지(`jam-reviewer`)는 참석하지 않는다. 아현은 쓰기 권한이 있어 무인 회의에 맞지 않고, 민지는 게이트 판정이 일이다.

## 지키는 것

1. **읽고 말하기만 한다.** 코드·DB·티켓 생성·문서 수정·외부 발행(Slack 포함)을 하지 않는다. 리포트 파일은 사회자가 쓴다.
2. **구상 문서는 요청이 있을 때만 고친다.** JAM 2.0 1~4단계의 코드·DB·티켓은 5단계부터 사용자 승인으로 시작한다(`docs/plan/jam2/`의 진행 노트 규칙).
3. **사용자가 만드는 디자인 단계의 결정을 선점하지 않는다.** 돕겠다고 말하고, 선택은 사용자에게 돌린다.
4. **확인하지 못한 것은 확인하지 못했다고 쓴다.** 추정을 사실처럼 적지 않는다.
5. 문서는 이름으로 부르고 번호로 줄이지 않는다. 용어는 진행 노트의 규칙을 따른다(배지 획득 조건, 챕터, 캡슐, 아이템 배지).
6. 개인 식별 정보(닉네임·이메일·유저 ID)를 적지 않는다. 집계 수치만 남긴다.

## 진행

| 순서 | 내용 | 방식 |
|---|---|---|
| 0 | 준비 | 사회자가 오늘의 사실(티켓 현황, 최근 배포·정리, 지표, JAM 2.0 진행 상태)과 이전 회의의 사용자 피드백을 모은다 |
| 1 | 1라운드 | 참석자가 병렬로 450자 이내로 말한다: 관찰, 제안(하나), 사용자에게 |
| 2 | 사회자 정정 | 사회자가 발언 중 사실과 다른 것을 바로잡고, 오늘 확인된 사실을 덧붙인다 |
| 3 | 2라운드 | 참석자가 서로의 발언을 읽고 300자 이내로 반응한다: 가장 동의하는 제안, 충돌·우려, 오늘의 합의안 후보 |
| 4 | 정리 | 사회자가 합의, 제안, 이견, 사회자 확인, 확인하지 못한 것, 결정 요청, 비용을 한 리포트로 정리한다 |

## 안건 구조 (기본값)

1. 오늘 있었던 일이 JAM 2.0에 주는 시사점
2. JAM 2.0 디자인 단계 동안 각 분야가 미리 준비하거나 점검할 수 있는 것
3. 지금 돌아가는 서비스(기존 체계)에서 사람이 봐야 할 위험이나 공백
4. 사용자에게 올릴 질문이나 결정 요청(최대 2개)

안건은 사회자가 정한다. 사용자의 피드백으로 바뀌면 이 절을 고친다.

## 산출물

- 위치: `docs/operations/reports/daily/YYYY-MM-DD.md` (신규 생성, 덮어쓰지 않는다)
- 절 구성: 사용자가 볼 것 → 안건 → 합의 → 이견 → 사회자 확인 → 확인하지 못한 것 → 사용자에게 올리는 결정 요청 → 사용 비용 → 사용자 피드백 → 대화 전문
- 대화 전문은 발언을 그대로 남긴다. 요약은 위쪽 절에 둔다.
- 결정 요청은 선택지와 사회자 추천과 이유를 함께 적는다.

## 사용자 피드백

리포트 맨 아래 「사용자 피드백」 칸에 사용자가 적는다. 다음 회의의 사회자가 첫 안건으로 읽고 반영 여부를 확인한다. 반영한 내용은 이 문서의 해당 절을 고치는 것으로 남긴다.

## 비용

회의마다 라운드별 토큰을 리포트의 「사용 비용」 절에 실측으로 기록한다. 시험 회의 1회차는 합계 354,094토큰이었다(1라운드 217,794, 2라운드 136,300, 사회자 제외). 계정 한도 대비 비율은 환산표가 없어 회의 시작 직전과 직후의 사용량 조회 차이로 잰다.

## 읽기 상한

에이전트가 이전 회의를 참고할 때는 최근 7일치만 읽는다. 그보다 오래된 기록이 필요하면 그때 찾아 읽는다.

## 자동 실행

2026-10-14 기준으로 자동 실행은 등록하지 않았고 수동으로 연다. 매일 20:00 KST 실행으로 등록할지는 사용자가 결정한다(리포트 2026-10-14의 결정 요청 4). 등록하면 예약 작업의 일반 규칙(승인 주체 없음, 비용 상한, 알림 도구 차단)을 `scheduled-jobs.md` 기준으로 따른다.
