# 데일리 미팅

> 신설: 2026-10-14, 티켓 20261014_1647. 시험 회의 1회차 결과는 `docs/operations/reports/daily/2026-10-14.md`다.
> **이 문서는 진행 규칙만 정의한다.** 사용자의 피드백을 받아 발전시키는 문서이므로 바뀌면 같은 날 이 문서를 고치고 git 이력으로 변경을 남긴다.

## 목적

서비스와 JAM 2.0 재설계에 대해 각 분야의 시선을 한 자리에 모아, **사람이 읽고 결정할 것**을 짧게 올린다. 예약 루틴(주간·월간 리포트 등)이 2026-10-07에 모두 삭제된 뒤 비어 있는 점검 자리를 부분적으로 메우는 목적도 있다. 회의는 의견과 제안만 낸다.

## 참석

| 역할 | 에이전트 | 관점 |
|---|---|---|
| 사회 | 카리나(오케스트레이터) | 안건 준비, 사실 정정, 합의·이견 정리, 리포트 작성 |
| 참석 | 혜린(`jam-pm`) | 기획·우선순위, 열린 결정 |
| 참석 | 카즈하(`jam-ops`) | 운영 지표·위험 신호 |
| 참석 | 채원(`jam-designer`) | 디자인 시스템·UX. 사용자가 만드는 디자인 단계의 결정을 앞서가지 않는다 |
| 참석 | 윈터(`jam-tribe`) | 세계관·트라이브 정합 |
| 참석 | 윤진(`jam-marketer`) | 유저에게 가는 말·온보딩·홈피드 |
| 참석 | 하니(`jam-guide`) | 문서 체계의 건강 |

아현(`jam-developer`)과 민지(`jam-reviewer`)는 참석하지 않는다. 아현은 쓰기 권한이 있어 무인 회의에 맞지 않고, 민지는 게이트 판정이 일이다.

## 지키는 것

1. **읽고 말하기만 한다.** 코드·DB·티켓 생성·문서 수정·외부 발행(Slack 포함)을 하지 않는다. 리포트 파일은 사회자가 쓴다.
2. **구상 문서는 요청이 있을 때만 고친다.** JAM 2.0 1~4단계의 코드·DB·티켓은 5단계부터 사용자 승인으로 시작한다(`docs/plan/jam2/`의 진행 노트 규칙).
3. **사용자가 만드는 디자인 단계의 결정을 선점하지 않는다.** 돕겠다고 말하고, 선택은 사용자에게 돌린다.
4. **확인하지 못한 것은 확인하지 못했다고 쓴다.** 추정을 사실처럼 적지 않는다.
5. 문서는 이름으로 부르고 번호로 줄이지 않는다. 용어는 진행 노트의 규칙을 따른다(배지 획득 조건, 챕터, 캡슐, 아이템 배지).
6. 개인 식별 정보(닉네임·이메일·유저 ID)를 적지 않는다. 집계 수치만 남긴다.

## 진행

| 순서 | 내용 | 방식 |
|---|---|---|
| 0 | 준비 | 사회자가 오늘의 사실(티켓 현황, 최근 배포·정리, 지표, JAM 2.0 진행 상태)과 이전 회의의 사용자 피드백을 모은다 |
| 1 | 발언 | 참석자가 병렬로 한 번, 450자 이내로 말한다: 관찰, 제안(하나), 사용자에게 |
| 2 | 정리 | 사회자가 발언을 비교해 합의(둘 이상이 같은 방향)와 이견을 가르고, 사실과 다른 발언을 저장소로 확인해 바로잡고, 결정 요청을 정리해 한 리포트로 남긴다. **티켓에 관한 결정 요청은 그 티켓의 상태와 완료 기록을 읽고 올린다**(2026-10-15, 이미 프로덕션에 나간 로고 건을 적용 전으로 알고 물은 일이 있었다) |

**한 라운드로 한다.** 2026-10-14 시험 회의에서는 서로의 발언에 반응하는 2라운드까지 열었으나, 반응 대부분이 같은 제안에 대한 동의라 비용에 비해 새 정보가 적었다(사용자 판단, 같은 날). 합의와 이견은 사회자가 한 라운드의 발언을 읽어 정리한다.

## 안건 구조 (기본값)

1. 지난 회의 이후 있었던 일이 JAM 2.0에 주는 시사점
2. JAM 2.0 디자인 단계 동안 각 분야가 미리 준비하거나 점검할 수 있는 것
3. 지금 돌아가는 서비스(기존 체계)에서 사람이 봐야 할 위험이나 공백
4. 사용자에게 올릴 질문이나 결정 요청(최대 2개)

안건은 사회자가 정한다. 사용자의 피드백으로 바뀌면 이 절을 고친다.

## 산출물

- 위치: `docs/operations/reports/daily/YYYY-MM-DD.md` (신규 생성, 덮어쓰지 않는다)
- 절 구성: 사용자가 볼 것 → 안건 → 합의 → 이견 → 사회자 확인 → 확인하지 못한 것 → 사용자에게 올리는 결정 요청 → 사용 비용 → 사용자 피드백 → 대화 전문
- 대화 전문은 발언을 그대로 남긴다. 요약은 위쪽 절에 둔다.
- 결정 요청은 선택지와 사회자 추천과 이유를 함께 적는다.

## 사용자 피드백

리포트 맨 아래 「사용자 피드백」 칸에 사용자가 적는다. 다음 회의의 사회자가 첫 안건으로 읽고 반영 여부를 확인한다. 반영한 내용은 이 문서의 해당 절을 고치는 것으로 남긴다.

클라우드 루틴의 사회자는 리포트 폴더 밖을 고칠 수 없다. 그래서 문서나 티켓을 고쳐야 하는 피드백(결정 요청의 답 등)은 메인 세션(카리나)이 처리하고 결과를 해당 티켓에 남긴다. 다음 회의의 사회자는 피드백 칸과 티켓을 함께 보고, 처리된 결정 요청을 다시 올리지 않는다.

## 비용

회의마다 토큰을 리포트의 「사용 비용」 절에 실측으로 기록한다(보이지 않으면 「측정 불가」). 시험 회의 1회차는 두 라운드 합계가 354,094토큰이었다(1라운드 217,794, 2라운드 136,300, 사회자 제외). 한 라운드로 줄인 클라우드 시험 실행은 서브에이전트 여섯 명 합계 104,608토큰이었다(2026-10-14, 사회자 제외). 계정 한도 대비 비율은 환산표가 없어 회의 시작 직전과 직후의 사용량 조회 차이로 잰다.

## 읽기 상한

에이전트가 이전 회의를 참고할 때는 최근 7일치만 읽는다. 그보다 오래된 기록이 필요하면 그때 찾아 읽는다.

## 자동 실행

**월·수·금** 20:00 KST(UTC 11:00, cron `0 11 * * 1,3,5`)에 클라우드 루틴 `trig_01MVcETJSaatpjrj3MgBHxi7`이 연다(2026-10-14 등록, 사용자 요청. 처음에는 매일이었으나 같은 날 사용자가 주 3회로 줄였다). 이름은 데일리 미팅으로 두지만 실행은 주 3회다. 켜짐·꺼짐 상태와 저장 프롬프트의 원본은 claude.ai/code/routines다. 이 문서와 프롬프트가 다르면 이 문서를 따른다.

- 환경은 `jam-ops`, 저장소는 이 저장소다. 리포트는 `staging`에 커밋한다.
- **같은 날 두 번 열지 않는다.** 루틴은 오늘(KST) 날짜로 시작하는 파일이 `reports/daily/`에 있으면 회의를 열지 않고 끝낸다. 사용자가 그날 수동으로 회의를 열었거나 루틴을 다시 실행한 경우의 중복과 비용을 막는다.
- **변경 이력은 지난 회의 이후로 읽는다.** 일정이 이틀에서 사흘 간격이라 「26시간 전」으로 읽으면 빠지는 구간이 생긴다. 기준은 `reports/daily/`를 마지막으로 바꾼 커밋 시각이다.
- 시험 실행(2026-10-14): 약 2분 만에 끝났고, 리포트 한 파일만 커밋해 push했다(작성자 `noreply@anthropic.com`, 훅 통과). 서브에이전트 다수가 읽기 도구를 1~3회만 써서 발언이 얕다. 루틴 실행 기록의 완료 시각이 실제 저장보다 약 1분 빨랐다. 사회자가 서브에이전트를 기다리며 응답을 한 번 끝냈다가 발언이 도착하자 다시 이어졌기 때문이며, 첫 정기 실행에서도 리포트가 저장됐는지를 파일로 확인한다.
- **외부 도구(커넥터)는 붙이지 않는다.** 루틴을 만들 때 계정의 커넥터 11개(Supabase·Slack·Gmail·Drive·Vercel 등)가 지정하지 않았는데도 자동으로 붙었고, 같은 날 모두 제거했다. 루틴 설정을 고칠 때 다시 붙지 않았는지 확인한다.
- `PushNotification`은 막았다. 서비스 롤 키는 환경에 없다.
- 리포트 커밋 작성자는 `docs/operations/reports/` 밖을 쓰지 못한다(`docs/agents/contract.json`의 `routine_commit_restriction`).
- 무인 실행에는 승인 주체가 없다. 회의는 읽고 말하는 자리로만 두고, 결정은 사용자가 리포트를 읽은 뒤에 한다.
