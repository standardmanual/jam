# JAM 2.0 오픈 전후 적용 순서

> **초안이다(2026-10-25).** 티켓 7-9(`20261022_1140`)의 목록이며 7-4 2회, 7-5, 7-7b가 모두 끝났다(7-5는 2026-10-26). 4절 5·6번의 SQL은 방식을 정한(2026-10-26) 뒤 292, 293으로 작성했고(티켓 `20261026_2026`) 아직 적용하지 않았다. 아직 파일로 없는 SQL은 「미작성」으로 적었다. `/jam-ship`의 오픈 직전 점검과 「출시 뒤 실행 대기 목록」이 이 표를 참조한다.

## 1. 원칙

- Supabase는 staging과 프로덕션이 한 DB를 쓴다. 실행하는 순간 옛 프로덕션 코드에도 바로 반영된다. 그래서 **오픈 직전 SQL은 main 승격 직전에, `post_release` SQL은 승격 뒤에** 실행한다.
- SQL은 카리나가 실행한다. 승인을 기다리는 대신 드라이런·백업·롤백 실측·실행 직후 읽기 확인과 보고로 점검하는 규칙은 `docs/agents/orchestrator.md` 4절이 단일 원천이다(2026-10-25 사용자 결정). 290만은 2026-10-24 사용자 결정으로 드라이런을 보여 드리고 승인받은 뒤 실행한다. 파일별 점검 항목은 4.1절에 모았다.
- 아래 표의 「롤백 실측」 칸은 티켓에 적힌 사실만 옮겼다. 적히지 않은 것은 「기록 없음」이다.
- 마이그레이션 기록표(`schema_migrations`)는 SQL을 직접 실행한 건(281, 287 등)이 빠져 있어 적용 여부의 근거로 쓰지 않는다. 실제 객체를 읽어 확인한다.

### 4.1 오픈 직전 SQL 점검표 (244 → 245 → 248 → 포인트 합 확인 → 290 → 291 → 282 → 292 → 293)

순서와 이유는 위 3번 칸이 원천이고, 파일 안의 가드·드라이런·되돌림은 각 SQL 파일 머리가 원천이다. 이 절은 실행 직전에 읽을 확인 항목만 한곳에 모았다. «오늘» 값은 2026-10-26에 공용 DB를 읽기 전용으로 확인한 것이고, 앞 단계를 적용하면 값이 바뀌므로 **각 단계 직전에 같은 쿼리를 다시 읽는다.** 어긋나면 실행하지 않고 사유를 보고한다.

**모든 단계 공통**
- 파일에 되돌림 SQL이 있다. 없으면 멈추고 보완한다.
- 데이터를 바꾸는 단계는 백업이 먼저다: 244는 파일 끝 «사전 백업 SELECT» 결과(JSON)를 티켓에 남긴다(적용 뒤에는 복원할 수 없다), 290은 백업 표 `badge_point_backup_290`, 282는 `retire_backup_20261022`, 292·293은 `launch_backup_20261026`(두 파일이 같은 표를 쓴다).
- 롤백 실측(파일 뒤에 일부러 오류를 내는 문장을 붙여 한 번의 호출로 실행, DB가 그대로인지 확인)을 한 뒤 적용한다. 기록이 있는 것은 244·245(티켓 `20261018_1816`)와 282(`20261022_1138`)이고, **248·290·291·292·293은 기록이 없어** 오픈 직전에 실측한다. 290·291은 가드가 244·245·248을 적용한 뒤의 건수(390)를 요구해 그 전에는 실측할 수 없다.
- 실행은 각 파일의 «실행» 주석을 따른다(290·282·292·293은 BEGIN/COMMIT 없이 한 번의 호출). 적용 직후 읽기 쿼리로 건수를 확인하고 영향 범위(공용 DB라 프로덕션에 즉시 반영)와 건수를 사용자에게 바로 보고한다. 기대 건수와 다르거나 가드가 멈추면 되풀이하지 않는다.
- 245·248은 옛 프로덕션 코드가 새 조건 키를 판정하지 못하면 배지가 보이기만 하고 발급되지 않는다(두 파일의 주석). 291도 새 조건 키(`same_spot_checkin_days`)를 쓰므로 같은 점에 주의한다. 그래서 main 승격 직전에 하고, 마지막 SQL부터 승격까지의 간격을 짧게 둔다.
