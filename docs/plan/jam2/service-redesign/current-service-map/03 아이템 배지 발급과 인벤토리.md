# 아이템 배지 발급(드랍 엔진)과 인벤토리

조사 시점: 2026-10-09. DB 값은 `execute_sql` SELECT로 확인했다. 시각은 KST다.

## 0. 먼저 알아야 할 DB 사실
- DB에 있는 아이템 배지(`badges.type='item'`)는 900개이고 **전부 common**이다. 이 중 살아 있는 것(`deleted_at IS NULL`)은 270개(낭만 미식가·숲속의 갱단·아스팔트 레인저 각 90개)다. 나머지 7개 트라이브의 630개는 소프트 삭제 상태다.
- 활성 컬렉션은 30개(위 3개 트라이브 각 10개)다. 다른 7개 트라이브의 컬렉션 70개는 `is_active=false`다.
- 그래서 지금 드랍으로 나올 수 있는 아이템 배지는 270개 common뿐이다. 엔진이 rare 이상을 뽑아도 같은 등급 후보가 없어 common으로 내려간다(아래 1-3).
- `engine_decision_log` 최근 30일: 드랍 발급 57건 중 rare 이상을 뽑고 common을 받은 것이 36건, slot_full(칸 부족으로 취소) 12건이다. 2026-09-12~14에는 rare 4건·epic 2건이 실제로 발급됐으므로, rare 이상 아이템 배지는 그 뒤 하드 삭제됐다. 이 삭제를 한 마이그레이션 파일은 저장소에서 확인 못 함.

## 1. 동기화 드랍 (활동하면 아이템 배지를 받는다)
- **유저 화면**: 직접 고르는 화면은 없다. Strava 동기화(수동 동기화 버튼, 최초 연동) 때 서버가 지급하고, 결과 캐러셀(4절)과 결산 알림으로 보여 준다.
- **어드민**: `/admin/drop-policy`에서 아래 22개 값을 저장 즉시 반영한다. 저장 검증은 등급 비율 4개의 합 = 1(±0.001), 모멘텀+인접+탐험 ≤ 1, 모든 값 0 이상이다. `/admin/simulator`는 쓰기 없이 판정 순서를 따라가는 미리보기다(`lib/drop-engine/preview.ts`).
- **규칙과 값**:
  - **대상 활동**: 이번 동기화에서 처음 처리하는 활동 중 평균속도가 차량 속도 필터 이하이고 JAM 종목(running·trail_running·cycling·hiking·walking)으로 매핑되는 것. 그중 최신순 **최대 3건**(코드 상수 `MAX_DROP_ACTIVITIES_PER_SYNC`), 첫 동기화는 **1건**이다. 처리는 오래된 순이다. 어드민 변경 불가.
  - **활동 한 건에 받는 개수**: 1개 확정 + 보너스 1개. 보너스 확률 = `bonus_drop_rate` 0.15(고강도면 `bonus_drop_rate_intense` 0.3) × 종목 계수. 고강도 = 이동시간 ≥ `intense_duration_min` 60분 또는 상승고도 ≥ `intense_elevation_m` 300m. 종목 계수는 걷기 게이트를 통과한 걷기만 0.4, 나머지 1.0(코드 상수, 어드민 변경 불가). 따라서 한 번 동기화에 최대 6개다.
  - 활동 1건당 확정 1개는 칸이 가득 차면 취소된다(5절).
- **데이터**: `drop_policy`(id=1 단일 행), `user_drop_state`, `inventory_items`, `engine_decision_log`(engine='drop')
- **코드**: `jam-web/src/lib/strava/sync.ts`(990~1020행), `lib/drop-engine/index.ts`(2026-10-22 삭제)(`tryItemDrop`), `lib/drop-engine/layers.ts`, `lib/drop-engine/constants.ts`
- **알려진 문제**: `drop_state_last_activity_mismatch` 경고가 최근 30일 37건 기록됐다(저장된 마지막 활동 시각이 기대값과 다름).

### 1-1. 등급 추첨 (Layer 1)
- 기본 비율: common 0.6 / rare 0.28 / epic 0.09 / mystic 0.03 (코드 기본값 = DB 값).
- 우선순위 순서로 보정한다.
  1. rare 이상 확정: 복귀(직전 활동과 `comeback_gap_days` 7일 이상 공백) 또는 연속 common 누적이 `rare_pity_threshold` 5 이상. common을 빼고 rare:epic:mystic 비율로 뽑는다.
  2. 일일 하향: 그날(UTC 날짜) 드랍 수가 `daily_downgrade_from` 4 − 1 이상이면 common `daily_downgrade_common` 0.9.
  3. 주간 첫 활동(UTC 월요일 기준 주가 바뀜): rare 이상 확률 × `weekly_first_rare_mult` 2.0, 상한 0.95.
- 복귀·주간 보정은 그 활동의 첫 드랍에만 적용한다. 연속 common 누적은 걷기면 0.4씩 오른다.
- **알려진 문제**: 살아 있는 아이템 배지가 전부 common이라, 이 절의 등급 비율·보정 장치는 지금 결과에 영향이 없다. 일일·주간 기준이 UTC라 KST로는 오전 9시에 날짜·주가 바뀐다.

### 1-2. 트라이브 고르기 (Layer 2)
- 후보 트라이브 = 그 등급의 드랍 가능 배지가 있는 트라이브.
- 순서: ① epic 이상이면 `mystery_spice_rate` 0.15로 미스터리 헌터 ② 맥락 오버라이드 ③ 모멘텀(직전 트라이브) `momentum_weight` 0.5 / 인접 트라이브 `adjacent_weight` 0.25 / 탐험(전체 무작위) `explore_weight` 0.15, 남는 몫은 탐험이 흡수한다.
- **맥락 오버라이드**(`context.ts`, 발동률 `context_override_rate` 0.6, 복귀는 항상): 복귀 → 작심삼일 클럽 / 기온 ≤ −10℃ 또는 ≥ 33℃ → 아스팔트 레인저 / 05~07시 → 비트 마에스트로·셔터 마피아 / 23~04시 → 낭만 미식가·숲속의 갱단 / 상승 500m 이상 → 낭만 미식가·비트 마에스트로 / 이동 90분 이상 → 미스터리 헌터(rare 이상일 때). 임계값은 코드 상수이고 어드민 변경 불가.
- **신규 유저 온보딩**: 누적 드랍 3회 미만이면 후보를 작심삼일 클럽 + 종목 트라이브(걷기→숲속의 갱단, 러닝→비트 마에스트로, 자전거→장비병 환자들, 하이킹·트레일→아스팔트 레인저)로 좁힌다. 해당 후보가 없으면 좁히지 않는다. 코드 상수다.
- 인접 관계는 `tribe_adjacency`(어드민 `/admin/tribes`에서 편집)다. DB: 트라이브마다 2~3개, 미스터리 헌터 0개.
- **알려진 문제**: 맥락·온보딩에 하드코딩된 트라이브 중 비트 마에스트로·셔터 마피아·작심삼일 클럽·미스터리 헌터·장비병 환자들은 지금 활성 컬렉션이 없어 후보에서 빠진다. 러닝·자전거 신규 유저의 온보딩 좁히기는 사실상 작동하지 않는다. `tribes.drop_weight`는 어드민에서 편집되지만(DB 전부 1.00) 드랍 엔진은 읽지 않는다.

### 1-3. 컬렉션과 아이템 배지 고르기 (Layer 3)
- 등급 후보가 없으면 같은 순서로 다른 등급을 시도한다(추첨 등급 → 한 단계 낮은 쪽 → 높은 쪽 …).
- 마지막 조각 보정: 그 트라이브에서 1개만 빠진 컬렉션이, 그 트라이브 드랍이 `last_piece_pity_threshold` 5번 지나도록 완성되지 않으면 그 배지를 확정한다.
- 컬렉션 가중치 = 컬렉션 안 후보 배지의 `drop_weight` 합 × (1 − 수집률 × `completion_decay` 0.7). 완성한 컬렉션은 × `completed_book_weight` 0.3, 직전 컬렉션은 × `same_book_penalty` 0.5. 최소 0.001.
- 배지: 컬렉션 안에서 미보유 배지 우선, `drop_weight` 가중 무작위.
- 수집률 분모에서는 개별 드랍 제외 배지를 뺀다.
- **알려진 문제**: `badges.activity_types`는 아이템 드랍 선택에 쓰이지 않는다. `item_books.drop_condition_json`도 드랍 엔진이 읽지 않는다(DB 전부 비어 있음). `drop_weight`는 DB 전부 1.00이다.

### 1-4. 드랍 후보에서 빠지는 조건 (드랍 제외)
- 컬렉션: `is_active=false`, `item_books.drop_excluded=true`, 컬렉션 공개 기간(`valid_from`~`valid_until`) 밖.
- 배지: `deleted_at` 있음, `badges.drop_excluded=true`, 배지 공개 기간 밖, 누적·기간 조건(`monthly_km`·`total_count`·`distance_km` 등 11개 키)이 있는 `condition_json`, 이번 활동 묶음으로 조건 불충족.
- **어드민**: `/admin/drop-policy/exclusions` 탭 2개(배지 개별 / 컬렉션 전체) 토글과 일괄 처리. 드랍 후보에서만 빼고 화면 노출·보유 이력은 그대로다. 트라이브 단위 제외 기능은 없다.
- DB: `drop_excluded=true`인 컬렉션 0개, 살아 있는 배지 0개.

## 2. 일련번호
- **유저 화면**: 배지 상세·드랍 개체 선택 시트 등에서 `ABCD012345`(대문자 4자 + 6자리) 형식으로 보인다(`components/inventory/ItemCandidateRow.tsx` `formatSerial`).
- **어드민**: `/admin/item-badges/[badgeId]`에서 번호 목록 조회만 한다. 변경 수단 없음.
- **규칙과 값**: 발급(INSERT) 때 DB 트리거가 정한다. `trg_serial_prefix`가 무작위 대문자 4자, `trg_random_serial`이 1~999,999 난수(시스템 드랍 `obtained_by='ambient_drop'`은 50,001~999,999)이고 파괴되지 않은 개체끼리 중복 불가, 50회 실패 시 오류다. 픽업·드랍으로 번호가 바뀌지 않는다. 파괴된 개체의 번호는 다시 쓰일 수 있다. DB: 1,332개 전부 접두어 있음, 번호 범위 5,161~999,682.
- **데이터**: `inventory_items.serial_prefix`, `serial_number`
- **코드**: `jam-web/supabase/migrations/008_serial_prefix.sql`, `108_item_identity_custody_model.sql`

## 3. 기한(공개 종료일)과 아이템 배지 포인트
- **어드민**: `/admin/badges` 배지 양식의 공개 기간(시작·종료), 포인트 보상(`point_reward`).
- **규칙과 값**:
  - 동기화 드랍 개체의 `expires_at` = 그 배지의 `valid_until`. 공개 기간 밖의 배지는 드랍되지 않는다.
  - 만료일이 지나도 보유 개체를 파괴하는 처리는 없다. 화면 표시(7일 이내 「곧 만료」)에만 쓴다.
  - `point_reward`가 0보다 크면 드랍 직후 1회 지급한다(사유 `badge_point_reward`). DB: 살아 있는 아이템 배지 270개 모두 0점, 공개 기간 설정 0개, `expires_at`이 있는 개체 3개.
- **코드**: `lib/drop-engine/index.ts`(2026-10-22 삭제)(`insertDrop`)

## 4. 결과 캐러셀 (받은 아이템 배지 보여 주기)
- **유저 화면**: 동기화 직후 전체 화면 캐러셀(`components/BadgeRevealOverlay.tsx`, `components/SyncButton.tsx`). 체크인 → 아이템 드랍 → 활동 배지 → 컬렉션·미션 보상 순서로 이어 붙인다.
- **어드민**: 없음.
- **규칙과 값**: 상세 카드 최대 10장(`EARNED_BADGE_DETAIL_LIMIT`), 넘는 수는 「더 보기」 개수로만 전달한다. 같은 배지 id는 한 장으로 합친다. 소프트 삭제된 배지는 뺀다. 같은 날 받은 아이템 배지는 KST 하루 단위 활동 결산 알림(`recordActivityRecap`)과 피드 `item_dropped`에도 실린다.
- **코드**: `jam-web/src/lib/strava/sync.ts`(`buildEarnedBadgePayload`), `jam-web/src/lib/notifications/recap.ts`
- **알려진 문제**: 한 동기화에서 같은 아이템 배지를 2개 받으면 캐러셀에는 1장만 보인다. 회차(×N)는 `user_activity_badges`에서 읽으므로 아이템 배지는 항상 1로 표시된다.

## 5. 인벤토리 (가방)
- **유저 화면**: `/inventory` 그리드. 사용 칸/최대 칸 진행 막대, 가득 차면 「드랍하러 가기」(`/drops`) 안내, 믹스 버튼(`/combine`). 개체를 누르면 `/inventory/[itemId]` → `/badges/[badgeId]?item=…`로 이동한다. 그리드에는 장착·드랍되지 않은 개체만 보인다.
- **어드민**: `/admin/inventory-policy`에서 최대 칸 수 하나를 바꾼다. 확인 창을 거쳐 **모든 기존 유저와 신규 가입자**에게 즉시 일괄 적용된다(`set_inventory_max_slots` RPC). 이미 새 값보다 많이 가진 유저가 있으면 거부된다. 1 이상 정수만 받는다. 유저별 개별 조정 화면은 없다.
- **규칙과 값**:
  - 최대 칸: 기본 50칸(코드 폴백·컬럼 기본값) / DB 정책 **10칸**(2026-09-12 20:41 변경). 신규 가입 트리거 `handle_new_user`는 정책 값을 쓴다.
  - 사용 칸(`used_slots`) = 보유 중이고 컬렉션에 장착하지 않은 개체 수. 컬렉션에 장착하면 1칸 비고, 장착 해제는 빈칸이 있어야 한다.
  - 가득 참 처리: 지급마다 `grant_inventory_item` RPC가 잠금 안에서 확인하고, 가득 차면 지급하지 않는다. 동기화 드랍·미션 보상·믹스 보상·픽업·어드민 재배정이 모두 같은 규칙이다. 동기화 드랍은 그 자리에서 남은 드랍을 멈춘다.
- **데이터**: `inventory`(max_slots, used_slots), `inventory_policy`(id=1), `inventory_items`
- **코드**: `jam-web/src/lib/inventory/slots.ts`, `jam-web/src/lib/inventory/policy.ts`, `jam-web/src/app/(main)/inventory/page.tsx`, `jam-web/supabase/migrations/173_atomic_inventory_slot_grant.sql`, `129_inventory_policy_max_slots.sql`
- **알려진 문제**: DB 인벤토리 8개 중 1개가 최대 30칸이다(정책은 10칸). 원인은 확인 못 함. 인벤토리 화면은 소프트 삭제된 배지의 개체를 숨기지만 그 개체도 사용 칸에는 남는다(지금 해당 개체 0개). 인벤토리 행이 없으면 화면은 50칸으로 표시한다.
- **문서 어긋남**: `SERVICE_OPERATIONS.md` 2-2·7-1과 `01_PRD.md`(103·141행)·`02_DATA_MODEL.md`(219행)는 50칸으로 적는다. 실제 정책은 10칸이고 가입 트리거도 정책 값을 쓴다.

## 6. 인벤토리 가득 참 알림

## 8. 아이템 배지 개체의 상태
- **유저 화면**: 상태 이름은 노출하지 않는다. 보유(인벤토리)·장착(컬렉션)·드랍(지점)으로 위치가 나뉜다.
- **어드민**: `/admin/item-badges/[badgeId]`의 상태 필터와 `[itemId]` 이력(소유 이전 타임라인). 조회 전용이다.
- **규칙**: 상태 칸은 없고 여러 칸에서 파생한다. 파괴됨(`destroyed_at`) → 마지막 이벤트가 Consume이면 소모됨, 아니면 파괴됨(만료) / 소유자 있음 → 장착 칸(`slotted_in`) 유무로 장착중·보유중 / 소유자 없음 + 활성 지점 드랍 → 유저 드랍이면 드랍됨(유저), 아니면 드랍됨(시스템) / 그 외 → 소유자 없음.
- **DB 개체 수(1,332개, 전부 common 아이템 배지)**: 보유중 21, 장착중 81, 드랍됨(유저) 22, 드랍됨(시스템) 779, 소모됨 14, 파괴됨 415, 소유자 없음 0.
- 이력 이벤트(`custody_events`) DB 건수: Minted 1,069, AdminDestroy 411, Slot 123, Pickup 78, UserDrop 36, Unslot 17, Consume 14, AdminReassign 8, Orphan 5, Expire 4.
- **코드**: `jam-web/src/lib/admin/item-badge-status.ts`, `jam-web/src/app/admin/item-badges/[badgeId]/page.tsx`
- **알려진 문제**: 파괴됨 415개 중 대부분은 어드민 영구 폐기(AdminDestroy 411)다. 이벤트 없이 파괴된 옛 개체도 「파괴됨(만료)」으로 표기된다.

## 10. 아이템 배지 현황과 생성 (어드민)
- **현황** `/admin/item-badges`: 이름 검색, 트라이브·컬렉션·등급 필터, 정렬, 배지별 발급 수. 소프트 삭제 배지도 포함한다. 내보내기 API(`/api/admin/item-badges/export`) 있음.
- **생성·수정** `/admin/badges`(유형 item): 운영자가 바꿀 수 있는 값은 이름·설명·이미지·배경, **등급**(common/rare/epic/mystic), **컬렉션 연결**(`item_book_id`), **드랍 가중치**(0.1~10, 같은 컬렉션·등급 안 상대 확률 미리보기), **공개 기간**, **포인트 보상**, 조건(`condition_json`, 누적 조건은 저장 거부), 지도 표시 여부다. 드랍 제외는 제외 관리 화면에서 바꾼다.
- 레벨 입력은 유형이 activity일 때만 나온다(`BadgeForm.tsx` 159행). 아이템 배지는 레벨을 만들 수 없다.

## 11. 아이템 배지에 레벨처럼 오르는 장치가 있는가
- **지금은 없다.** 확인한 사실은 다음과 같다.
  - `badges`에 아이템 배지의 `level` 값이 있는 행은 0개다. 어드민 양식도 아이템 배지에 레벨을 허용하지 않는다. `drop-engine/index.ts` 706행 주석은 「레벨형은 활동 배지 전용」이라고 적는다.
  - 강화·승급 기능 코드는 없다(`lib`, `app`에서 해당 단어 검색 결과 없음).
  - 믹스 레시피 3개의 보상은 모두 common 아이템 배지이고 재료 칸도 모두 아이템 배지다. 등급을 올리는 레시피는 지금 없다.
- **과거에 있던 「등급 짝」**: 055가 common 900개마다 같은 컬렉션에 rare/legendary/mythic 짝을 트라이브별 접두어 이름으로 만들고, 컬렉션 등급 정책(`rarity_mode`)을 넣었다. 058이 등급 정책을 롤백, 059가 상위 등급을 컬렉션에서 분리, 061이 하드 삭제, 062가 이름을 그대로 둔 채 다시 만들고(컬렉션 없음), 063·066이 믹스 레시피 33개의 결과로 연결해 「common 재료 → 상위 등급 결과」 구조가 있었다. 094가 common 외 등급을 소프트 삭제하고 보유 개체를 회수, 레시피를 비공개로 돌렸다. 지금 DB에는 이 짝이 남아 있지 않다(0절).
