# 미션, 랭킹, 포인트

조사 기준: 코드 `jam-web/src`(staging 42f53e610), DB는 2026-10-09 SELECT 조회 결과다. 경로는 `jam-web/src` 기준이다.

## 미션의 틀 (순위형, 달성형, 개인형)
- **유저 화면**: 참가자만 `/missions/[id]/status`에서 미션 상황을 본다. 순위형은 등수 목록, 달성형은 달성자 목록, 개인형은 본인 진행값과 달성 여부만 본다.
- **어드민**: `/admin/missions/new`, `/admin/missions/[id]`의 「미션 상황 표시 방식」 칸에서 고른다. 「공개 인원」(`visible_rank_count`, 빈칸이면 전체)도 바꿀 수 있다.
- **규칙과 값**: 틀은 `status_display_type`(ranking, achievement, individual) 한 칸이다. 기본값은 ranking(코드, 일반 미션 폼)이다. 틀은 화면 표시와 순위 소식(#23)에만 영향을 주고, 달성 판정과 보상은 틀과 무관하다. DB 55건 전부 individual이다. ranking 0건, achievement 0건이다.
- **데이터**: `missions.status_display_type`, `missions.visible_rank_count`(DB 0건 사용).
- **코드**: `app/api/missions/[id]/status/route.ts`, `app/admin/missions/MissionForm.tsx`, `types/database.ts`(`MissionStatusDisplayType`)
- **알려진 문제**: 폼의 추천 문구는 체크인과 아이템 픽업이면 「달성형」, 그 밖이면 「순위형」이다. 실제 DB는 전부 개인형이다.

## 미션 조건 종류 (목표 유형 8종)
- **유저 화면**: 미션 상세의 달성 조건 카드와 진행 막대. 첫 줄은 `condition_text`가 있으면 그 문장을, 없으면 목표 유형별 기본 문구를 쓴다.
- **어드민**: 미션 폼의 「미션 타입」과 조건 빌더. 유형별로 칸이 바뀐다. 복합 조건은 판정 시뮬레이션 패널이 붙는다(`/api/admin/missions/simulate-condition`). 저장 시 서버가 키 검증(`checkMissionCondition`)과 값 검증(`checkMissionConditionValue`)을 한다.
- **규칙과 값** (`mission_type`, 어드민 표기, 판정):
  - `distance` 거리: 참가 이후 누적 km 합 ≥ `distance_km`. 종목 필터 선택.
  - `activity_count` 활동 횟수: 참가 이후 활동 수 ≥ `count`. 종목 필터 선택.
  - `checkin` 체크인: `poi_id` 지점에 체크인 배지를 받은 기록(`user_activity_badges.triggered_by_poi_id`)이 있으면 달성. 참가 전 체크인도 인정된다.
  - `item_collect` 아이템 픽업: `badge_id` 배지를 보유(활동 배지 또는 인벤토리)하면 달성. 참가 전 보유도 인정된다.
  - `streak_days` 연속 일수, `duration_minutes` 단일 활동 시간, `elevation_gain_m` 단일 활동 고도: 배지 엔진 `evaluateConditionDetailed`에 위임한다. 걷기는 진짜 걷기 판정(축1 게이트)을 통과한 활동만 센다.
  - `engine_condition` 복합 조건: 배지 엔진 어휘 14종(`activity_type`, `distance_km`, `elevation_gain_m`, `single_distance_km`, `single_elevation_m`, `max_elevation_m`, `max_pace_sec_per_km`, `min_speed_kmh`, `duration_minutes`, `same_activity`, `repeat_count`, `rest_after_long`, `streak_days`, `weekly_streak`)과 미션 전용 어휘 9종(`weekly_streak_min_count`, `monthly_streak`, `monthly_streak_min_count`, `streak_subset`, `distinct_weekday_count`, `time_band_counts`, `distinct_months_required`, `distinct_months_metric`, `distinct_months_threshold`)을 AND로 묶는다. 진행 막대가 없고 0/1 달성형이다.
  - 조건 하나에 종목은 하나만 지정한다. 아는 키가 하나도 없으면 미달성이다.
  - DB: engine_condition 53건(전부 게이트 미션), activity_count 2건. 나머지 6종은 0건이다.
- **데이터**: `missions.mission_type`(DB CHECK 8종), `missions.condition_json`, `missions.condition_text`(53건 사용).
- **코드**: `lib/missions/checker.ts`, `lib/missions/engineCondition.ts`, `lib/missions/condition-keys.ts`, `app/admin/missions/missionConditionFields.ts`, `lib/admin/badge-labels.ts`
- **알려진 문제**:
  - 어드민 라벨 「단일 활동 고도」(`elevation_gain_m`)와 실제 판정(참가 이후 누적 합계)이 다르다. 넘겨받은 확인 항목 2 참고.
  - `time_band_counts`는 폼에 입력 칸이 없다. 기존 값을 보존만 한다. DB 3건이 이 키를 쓴다.
  - 시뮬레이션 패널은 복합 조건 유형에만 있다.
  - `checkin`, `item_collect`의 대상 UUID가 실제 행인지는 저장 때 검사하지 않는다(형태만 검사).
- **문서 어긋남**: SERVICE_OPERATIONS.md 9-3, 9-4는 4종(`distance`, `activity_count`, `poi_visit`, `item_collect`)만 적고 `poi_visit`, `item_collect`를 미구현으로 적는다. 코드는 8종이고 `poi_visit`은 `checkin`으로 개명됐으며 둘 다 판정된다.

## 참가와 취소
- **유저 화면**: `/missions/[id]`에서 「참가하기」를 누르면 「한번 참가하면 취소할 수 없어요」 확인창이 뜬다. 참가 버튼은 시작 시각이 지났고 종료 전일 때만 보인다(`isActive`).
- **어드민**: 없음. 유저의 참가 기록을 어드민에서 바꾸는 화면은 찾지 못했다(유저 초기화 `resetUserData`가 참가·완료 기록을 지운다).
- **규칙과 값**: `POST /api/missions/[id]/join` 검사 순서는 미션 존재, 노출 여부(`isMissionExposed`, 숨김이면 404), 종료 시각 경과(400), 노출 판정이 completed면 409, open이 아니면 403, 중복 참가 409다. API는 시작 시각을 검사하지 않는다. 참가 취소 API는 없다. 파일 끝 주석은 「참가 취소(DELETE)는 Phase13에서 폐지」라고 적는다.
- **데이터**: `user_mission_participations`(user_id, mission_id, joined_at, progress_value). DB 10행, 유저 4명.
- **코드**: `app/api/missions/[id]/join/route.ts`, `app/(main)/missions/[id]/MissionDetailClient.tsx`
- **알려진 문제**: 화면은 시작 전 참가를 막지만 API는 막지 않는다. 확인 항목 1 참고.
- **문서 어긋남**: SERVICE_OPERATIONS.md 9-2는 `DELETE /api/missions/[id]/join` 취소와 `mission_cancelled` 피드 기록을 적는다. 코드에 없다. 9-1은 조건을 「ends_at > now」 하나로 적고 노출·잠금·완료 검사를 적지 않는다.

## 참가 인원과 선착순 완료 제한
- **유저 화면**: 상세 보상 카드 아래 「선착순 N명」 문구(`limitedSlots`).
- **어드민**: 미션 폼 「선착순 인원 (빈칸=무제한)」(`max_completions`). 게이트 미션 폼은 이 칸이 없고 항상 null로 저장한다.
- **규칙과 값**: 참가 인원 상한 칸은 없다. `max_completions`는 완료자 수 상한이다. 달성 시 완료 행 수를 센 뒤 상한 이상이면 완료 처리를 건너뛴다. 건너뛴 유저는 참가 상태로 남고 다음 동기화에서 다시 시도된다. DB 0건 사용.
- **데이터**: `missions.max_completions`, `user_mission_completions`(UNIQUE user_id, mission_id). DB 완료 3행.
- **코드**: `lib/missions/checker.ts`(선착순 체크 블록)
- **알려진 문제**: 세기와 INSERT 사이에 잠금이 없어 동시 동기화 시 상한을 넘을 수 있다(코드 구조에서 보이는 사실, 재현은 확인 못 함).

## 집계 기간
- **유저 화면**: 목록 카드의 남은 시간, 「상시」, 「시작전」 라벨.
- **어드민**: 시작 일시, 종료 일시, 「상시 미션 (종료일 없음)」 체크. 목록 일괄 「기간 종료」(`ends_at`을 지금으로).
- **규칙과 값**:
  - 판정은 Strava 동기화 직후 `checkMissions`에서만 돈다. 대상은 `starts_at ≤ now`이고 `ends_at`이 null이거나 now 이후인 미션이다.
  - 집계 대상 활동은 가입 시점 이후 이력 전체를 가져와 `startDate ≥ joined_at`으로 거른다. `starts_at` 하한과 `ends_at` 상한으로 거르지 않는다.
  - 종료 뒤에는 판정하지 않는다. 기간 안에 한 활동을 종료 뒤에 동기화하면 반영되지 않는다. 유예 시간은 없다.
  - DB: 상시 54건, 기간형 1건(「그루터기 살롱의 겨울 채비」, 2026-10-01 00:00 ~ 2026-10-31 23:59:59 KST). 시작 전 미션 0건, 종료 미션 0건이다.
- **데이터**: `missions.starts_at`, `missions.ends_at`(null이면 상시), `user_mission_participations.joined_at`
- **코드**: `lib/missions/checker.ts`(`activeMissionsQueryFilter`, 3단계 이력 필터), `lib/strava/sync.ts`(1088행 호출)
- **알려진 문제**: 활동 필터에 `ends_at` 상한이 없으나 종료 뒤에는 판정 자체가 돌지 않아 결과에 영향이 없다. 시작 전 참가가 생기면 시작 전 활동이 들어간다(확인 항목 1).
- **문서 어긋남**: SERVICE_OPERATIONS.md 9-3은 「starts_at <= now <= ends_at」만 적고 상시 미션과 참가 시점 하한을 적지 않는다.

## 순위 계산
- **유저 화면**: `/missions/[id]/status`. 순위형은 등수, 이름, 진행값을 보여 준다. 본인 행은 공개 인원 밖이어도 `me`로 따로 내려간다.
- **어드민**: 공개 인원 칸만 있다. 정렬 규칙은 코드 고정이다.
- **규칙과 값**: 완료자 우선, 먼저 완료한 순, 진행값 큰 순이다. 동점은 배열 순서대로 서로 다른 등수를 받는다. 달성형은 달성자 우선, 먼저 달성한 순이고 등수가 없다. 프로덕션에서는 staging 테스트 계정을 뺀다(`excludedTestUserIds`).
- **데이터**: `user_mission_participations.progress_value`, `user_mission_completions.completed_at`, `mission_rank_snapshots`(소식 #23용, DB 0행).
- **코드**: `lib/missions/ranking.ts`, `app/api/missions/[id]/status/route.ts`
- **알려진 문제**: 복합 조건 미션의 진행값은 0 또는 1이라 미완료자끼리 순위가 갈리지 않는다. 현황 API는 숨김 노출(`exposure_mode`)을 검사하지 않아 숨긴 미션도 참가자는 현황을 본다.

## 보상
- **유저 화면**: 상세의 보상 카드(배지, 포인트). 완료 소식에는 보상을 적지 않는다.
- **어드민**: 미션 폼 「미션 포인트」와 「보상 배지 (복수 선택 가능)」. 총 지급 포인트 미리보기(미션 포인트 + 배지 자체 포인트)가 뜬다. 게이트 미션 폼은 보상 배지만 받고 포인트는 항상 null로 저장한다.
- **규칙과 값**:
  - 보상 배지는 타입별로 갈린다. 활동 배지는 `user_activity_badges`에 넣고, 아이템 배지는 `grant_inventory_item` RPC로 인벤토리에 넣는다(획득 경로 `system_event`).
  - 이미 가진 활동 배지, 이미 가진 아이템 배지, 인벤토리 가득 참, 인벤토리 없음, 삭제된 배지는 조용히 건너뛴다. 유저에게 알리지 않고 다시 주지 않는다. 미션 완료와 미션 포인트는 그대로 처리된다.
  - 실제로 준 배지마다 그 배지의 `point_reward`를 `badge_point_reward`로 지급한다. 미션 포인트는 `mission_point_reward`로 따로 지급한다.
  - 폼 기본 미션 포인트 100(코드) / DB에서 포인트가 있는 미션 0건. 보상 배지가 있는 미션 55건(활동 배지와 아이템 배지 섞임).
- **데이터**: `missions.reward_badge_ids`, `missions.reward_points`. `reward_type`, `reward_id`는 Phase13 이후 미사용이다(DB 0건).
- **코드**: `lib/missions/rewards.ts`, `lib/inventory/slots.ts`
- **알려진 문제**: 인벤토리가 가득 차 받지 못한 보상은 복구 경로가 없다. 건너뛴 사실은 로그(`logEngineDecision`)에만 남는 경우와 아무 기록도 없는 경우(가득 참, 이미 보유)가 있다.

## 미리 보여 주기와 숨김 노출
- **유저 화면**: 목록에 open과 locked만 나온다. locked는 잠금 카드와 「앞 단계 배지를 먼저 획득하면 참가할 수 있어요」 문구로 보인다. 시작 전에 노출된 미션은 「시작전」 라벨로 흐리게 보인다.
- **어드민**: 미션 폼 「미션 노출」(숨김, 시작일 노출, 노출일 지정 + 노출 일시). 목록 일괄 「숨김」, 「노출」. 「게이트 배지」(레거시 `gated_badge_id`) 칸.
- **규칙과 값**:
  - 노출 레이어(`isMissionExposed`)가 먼저다. hidden은 어디에도 안 나온다. start_date는 `starts_at` 이후 노출, scheduled는 `exposure_at` 이후 노출이며 `exposure_at`이 비면 숨긴다. 기본 start_date(코드) / DB 55건 전부 start_date.
  - 그다음 노출 판정(`resolveMissionVisibility`): 완료 기록이 있으면 completed, `gate_axis`가 있으면 게이트 규칙, `gated_badge_id`가 있으면 레거시 등급 비교(보유 등급+1까지 open, +2는 locked, 그 위는 hidden), 둘 다 없으면 open이다. hidden이어도 참가 기록이 있으면 locked로 완화한다.
  - 같은 보상 배지 하나를 주는 미션 여러 개는 목록에서 대표 1개만 보인다(참가 중, open, 축 이름순).
- **데이터**: `missions.exposure_mode`, `exposure_at`, `gated_badge_id`(DB 0건), `gate_axis`, `visibility_rule_json`
- **코드**: `lib/missions/visibility.ts`, `lib/missions/visibility-server.ts`, `lib/missions/dedupeReward.ts`, `app/(main)/missions/page.tsx`
- **알려진 문제**: 노출일 지정으로 시작 전에 보이는 미션은 상세에서 참가 버튼이 없다(시작 전 미리 보기 전용).

## 넘겨받은 확인 항목

1. **시작 전에 참가한 경우, 시작 전 활동이 집계에 들어가는가**: 들어간다(코드 기준). `checkMissions`는 활동을 `a.startDate >= joinedAt`으로만 거르고 `starts_at`으로 거르지 않는다(`lib/missions/checker.ts` 3단계와 루프 안 `missionActivities`). 시작 전 참가는 화면에서는 막힌다(상세 참가 버튼이 `isActive`일 때만 보임). 참가 API(`app/api/missions/[id]/join/route.ts`)는 노출, 종료, 잠금, 완료만 검사하고 시작 시각을 검사하지 않으므로, 노출일 지정으로 시작 전에 보이는 미션은 API 직접 호출로 참가할 수 있다. 판정은 시작 뒤에야 돌지만 그때 시작 전 활동이 포함된다. 체크인과 아이템 픽업은 참가 전 보유도 인정한다. DB: 참가 10행 중 시작 전 참가 0행, 노출일 지정 미션 0건이다.

2. **고도 조건('단일 활동 고도')이 실제로 누적 합계로 판정되는가**: 누적 합계다. `elevation_gain_m` 유형은 배지 엔진 `evaluateConditionDetailed`에 위임되고, 엔진은 `same_activity`가 없으면 `elevation_gain_m`을 전체 이력(참가 이후) 누적 합계로 판정한다(`lib/badge-engine/index.ts` 530~548행, `conditionAxes.ts`의 `PER_ACTIVITY_KEYS`에 없음). 진행값도 합산이다(`checker.ts` `calculateProgress`의 reduce). 어드민 라벨만 「단일 활동 고도」다(`lib/admin/badge-labels.ts` 46행). 단일 활동 고도는 복합 조건의 `single_elevation_m`이다. DB에 `elevation_gain_m` 유형 미션은 0건이고, 복합 조건 4건이 `elevation_gain_m` 키를 누적 의미로 쓴다.

3. **DB의 미션 수, 진행 중 미션, 참가 기록 수**: 미션 55건. 틀별로 개인형 55, 순위형 0, 달성형 0이다. 유형별로 복합 조건 53(게이트), 활동 횟수 2(공개)다. 노출 모드는 전부 시작일 노출이고 숨김 0건이다. 55건 모두 진행 중이다(상시 54, 기간형 1, 시작 전 0, 종료 0). 참가 10행(유저 4명), 완료 3행이다. 참가가 있는 미션은 「겹쳐진 도시의 새 얼굴」 4명(완료 2), 「페이스의 증명」 2명(완료 1), 「그루터기 살롱의 겨울 채비」, 「오르내린 거리의 증명」, 「오르막의 증명」, 「울트라의 증명」 각 1명이다. 선착순, 공개 인원, 미션 포인트를 쓰는 미션은 0건이다.
