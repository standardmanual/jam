> 이 문서는 그 위에 얹는 **보여 주는 방식**과, 그 방식에 필요한 **추가 데이터**만 정한다. 자동화 규칙은 [`content-automation/PRD.md`](../content-automation/PRD.md)다.

## 1. 한 줄 정의

운영자가 어드민을 열면 세 가지를 바로 알게 한다: 에이전트 기획이 어디까지 왔고 내가 무엇을 결정해야 하는지(운영), 서비스 생태계가 목표대로 도는지와 바꿀 정책이 무엇인지(생태계), 개발과 배포가 어디까지 왔는지(개발·배포).

## 2. 왜 다시 짜는가 (2026-10-26 사용자 피드백)

| 피드백 | 지금 화면의 원인 |
|---|---|
| 텍스트가 길고 많아 상황을 이해하기 어렵다 | 항목 상세 1칸에 글 블록 7개, 확인창 4종에 안내 문장, 설정 설명 배열 20개 이상 |
| 에이전트별 상태와 워크플로가 보이지 않는다 | 화면의 단계는 운영자가 받은 뒤(도착→종료)뿐이다. 에이전트 단계는 데이터로 남지 않고, `routine_run`은 저장만 하고 그리지 않는다 |
| 승인·취소·미승인 같은 상태와 버튼이 흐름에서 명확하지 않다 | 상태 10개를 그대로 보여 주고, 승인과 예약 등록이 버튼 두 개로 나뉘어 있다 |
| 전체 흐름을 한눈에 보기 어렵다 | 운영 홈의 숫자 다섯 칸은 누를 수 없고, 주차별 흐름을 한 화면에서 보는 곳이 없다 |
| 내가 무엇을 결정해야 하는지 알기 어렵다 | 결정할 일이 목록 탭 안에 섞여 있다 |
| 기획의 이유와 트렌드가 보이지 않는다 | 묶음에 가설 문장 하나뿐이고 항목별 이유 필드가 없다 |

## 3. 공통 원칙

1. **요약이 먼저, 상세는 누르면.** 화면 첫 줄은 「내 차례」다. 설명은 한 줄을 넘기지 않고, 그 이상은 서랍이나 툴팁에 둔다.
2. **상태는 다섯 가지로 보인다.** 안쪽 상태 10개는 그대로 두고 화면에서만 묶는다(§3.1). 색만 쓰지 않고 점·글자를 함께 쓴다.
3. **버튼 하나에 행동 하나.** 버튼 이름은 동사로 끝나고 결과를 그대로 말한다(「31건 승인하고 예약」). 화면마다 주 버튼은 하나다.
4. **기획 이유는 칩으로 보인다.** 트렌드·시즌·날씨·신호·패턴 다섯 종류를 기호와 테두리로 상태 색과 구분한다(§5).
5. **카피는 짧게 쓴다.** 상태 이름은 두 단어 이내, 제목은 명사구, 오류는 [현상]·[원인]·[해결] 한 줄씩이다(`docs/service/writing/UX_WRITING_GUIDELINE.md`). 같은 뜻에 다른 말을 쓰지 않는다.
6. **어드민 UI는 shadcn/ui다.** `jam-web/src/components/admin/ui/`의 컴포넌트를 쓴다. 서비스 MODULAR을 쓰지 않는다. 다만 홈피드 미리보기의 카드는 서비스 카드 컴포넌트를 그대로 그린다(§6.3).

### 3.1 화면 상태 다섯 가지

| 화면 상태 | 안쪽 상태 | 뜻 | 내 차례에 뜨는가 |
|---|---|---|---|
| 결정 필요 | 도착, 검토중 | 내가 승인·반려할 차례 | 뜬다 |
| 진행 중 | (에이전트 단계), 승인됨, 준비중, 예약됨 | 사람 손 없이 다음 단계로 가는 중. 칸 안에 「예약됨」처럼 세부를 작게 쓴다 | 안 뜬다 |
| 게재 중 | 게재중 | 유저에게 보이는 중 | 안 뜬다 |
| 문제 | 실패 | 내가 손봐야 함 | 뜬다 |
| 끝남 | 종료, 반려, 취소 | 더 할 일 없음. 칸 안에 세부를 작게 쓴다 | 안 뜬다 |

**구현됨(계산·읽기): 티켓 20261026_2023 1회차.** 계산은 `jam-web/src/lib/admin/opsBoard/screenState.ts`다.
- `screenStateOfItemStatus`가 위 표대로 10개 상태를 다섯 화면 상태로 묶는다. 10개 밖 값은 어느 상태에도 넣지 않는다(null).
- `screenDetailOfItemStatus`는 칸 안에 작게 쓰는 세부를 돌려준다: 승인됨·준비중·예약됨·종료·반려·취소. 도착·검토중·게재중·실패는 세부가 없다.
- `isMyTurnState`는 결정 필요·문제만 참이다.

| D5 | 트렌드 출처는 운영자가 정한다 | 에이전트는 등록된 출처만 읽고, 기획 이유에 트렌드를 단다(§6.4) |

## 5. 묶음에 더하는 데이터

에이전트가 제출하는 묶음(`POST /api/admin/ops-inbox`)에 아래를 더한다. 모두 선택 필드로 시작하고, 없으면 화면은 지금처럼 그린다(옛 묶음·시험 묶음 호환).

**저장 위치 (결정: 티켓 [20261026_2021](../../../tickets/p2-normal/20261026_2021_Infra_기획-묶음에-제목-이유-단계기록-트렌드-필드.md), 2026-10-26).** 새 테이블을 만들지 않고 이미 있는 칸을 최대한 쓴다.

| 필드 | 저장 |
|---|---|
| 묶음 `title` | `ops_bundles.title TEXT NULL` 새 칸 |
| 묶음 `trends[]` | `ops_bundles.trends JSONB NULL` 새 칸 |
| `routine_run.stages[]` | 기존 `ops_bundles.routine_run`(JSONB) 안. 새 칸 없음 |
| 항목 `rationale`·`highlight` | 기존 `ops_bundle_items.original`(제출 항목 원본) 안. 새 칸 없음 |

형식이 틀린 `title`·`trends`는 저장하지 않고 NULL로 둔다(원본은 `raw`에 남는다). 오류는 제출 응답과 묶음·항목의 형식 오류 목록에 쌓이고 제출은 막지 않는다.
검증은 `jam-web/src/lib/admin/opsInbox/validate.ts`, 읽기는 `query.ts`의 `getOpsBundleDetail`(`title`·`trends`·`stages`)과 `readOpsItemRationales`·`readOpsItemHighlight`다.
`source_id`·`source_ids`의 출처 번호는 출처 등록(§6.4)이 아직 없어 비어 있지 않은 문자열이나 1 이상의 정수로 본다. `outcome_reason`은 자동 제외 범주 이름을 비어 있지 않은 문자열로 받는다(범주 목록은 [`content-automation/PRD.md`](../content-automation/PRD.md) §10.2, 허용 목록 검사는 하지 않는다).

### 5.1 기획 제목 (구현됨: 티켓 20261026_2021)
- `title`: 그 주 기획을 한 줄로 부르는 이름, 30자 이내(예: 「LP 리바이벌 × 억새 절정」). 주간 흐름의 주차 칸과 결정 패널 제목에 쓴다. 지금의 `hypothesis`는 결정 패널 안에서 한 줄 설명으로 남긴다.

### 5.2 기획 이유 (구현됨: 티켓 20261026_2021)
- 항목마다 `rationale` 1~3개: `{ kind, label, note?, source_id? }`
  - `kind`: `trend`(온라인 트렌드) · `season`(시즌·절기·기념일) · `weather`(날씨) · `signal`(서비스 데이터 신호) · `pattern`(패턴 사전 번호)
  - `label`: 칩에 쓰는 말, 12자 이내(예: 「LP 리바이벌」, 「잠긴 배지 누적」, 「P07」)
  - `note`: 서랍의 「왜 이 기획?」 한두 문장, 120자 이내. 근거 숫자를 넣는다
  - `source_id`: 트렌드일 때 출처(§6.4) 번호
- 항목마다 `highlight`(참·거짓): 이번 기획의 핵심 항목. 묶음당 5개 이하. 결정 패널 맨 위에 먼저 보인다.
- 묶음의 이유 칩은 항목 이유를 종류별로 세어 화면이 만든다(따로 저장하지 않는다).

### 5.3 에이전트 단계 기록 (D2) (제출 쪽 `routine_run.stages`는 구현됨: 티켓 20261026_2021. 「시작」 기록 경로·멈춤 판정 함수도 구현됨: 티켓 20261026_2032, 내 차례에 띄우는 화면은 티켓 20261026_2023)
- **쓰기 2번:** ① 루틴 시작 때 「시작」 기록 1번(주차, 시작 시각, 맡은 에이전트 목록. `POST /api/admin/ops-inbox/routine-start`, 저장 위치 `ops_routine_starts`, 본문 `run_key`·`week?`·`author`·`agents[]`. 제출 묶음의 `routine_run.run_key`가 같으면 이어진다), ② 제출 때 묶음 안의 `routine_run.stages`에 단계별 요약을 한 번에 싣는다.
- `stages[]`: `{ agent, stage, started_at, ended_at, in_count, out_count, excluded_count }`. `stage`는 `plan`·`world_review`·`balance_check` 셋이다. 지금의 `excluded_items[].stage` 값과 같은 이름을 쓴다.
- 시작과 제출 사이에는 단계별 진행을 실시간으로 알 수 없다. 이 동안 주간 흐름 칸에는 「진행 중 · 시작 후 N분」만 보인다. 제출 뒤에는 단계마다 걸린 시간과 「2건 뺌」 같은 결과가 보인다.
- 시작 기록이 있는데 3시간 안에 제출이 없으면 「문제 · 루틴이 멈췄어요」로 내 차례에 뜬다(기준 시간은 운영 설정 값). 판정은 `isRoutineStalled`(`routineStart.ts`)이고 기준은 `OPS_ROUTINE_STALL_HOURS`(3) 한 곳이다.

### 5.4 읽은 트렌드 (구현됨: 티켓 20261026_2021)
- 묶음에 `trends[]`: `{ label, source_ids, summary, series?, outcome, outcome_reason? }`
  - `outcome`: `used`(기획에 반영) · `held`(보류) · `excluded`(자동 제외)
  - `series`: 출처가 숫자 추이를 줄 때만 최근 14일 값
- 반영한 트렌드는 해당 항목의 `rationale.source_id`로 이어진다.

## 6. ① 운영 상황판

경로는 운영 홈 `/admin`이다. 지금 운영 홈의 구역(이번 주 상태, 신호, 서비스 점검, 최근 이력, 지표)은 이 화면으로 합치거나 생태계 상황판으로 옮긴다. 옮길 곳은 티켓 20261026_2023 2회차에서 정했다(Q3, 아래 「운영 홈 구역 이동」).

**구현됨(화면): 티켓 20261026_2023 2회차.** 운영 홈 `/admin` 맨 위에 내 차례 카드 줄 → 주간 흐름 지도 → 에이전트 줄·일정 띠 순서로 한 구역(`BoardSection`, `app/admin/_home/sections.tsx`)을 둔다. 부품은 `components/admin/ops/board/`(`OpsMyTurn`·`OpsWeekFlowMap`·`OpsAgentRows`)다. 지금 운영 홈의 「이번 주 상태」 다섯 칸·각주·다음 주 줄은 이 구역이 대신해 없앴다.

**운영 홈 구역 이동(PRD Q3, 추천안 채택).** 주간 핵심 지표·배지 경제 흐름·통계는 생태계 상황판(티켓 20261026_2027)으로 옮기고, 서비스 점검·신호·최근 이력은 운영에 남긴다. 이번 회차는 옮기지 않고 상황판·신호·서비스 점검·최근 이력 아래쪽에 그대로 두며, 실제 이동은 2027에서 한다.

### 6.1 내 차례
- 맨 위 카드 줄. 「결정 필요」와 「문제」만 뜬다. 카드마다 제목, 상태, 건수, 마감(결정 필요는 수 18:00), 이유 칩 요약, 주 버튼 1개.
- 상단 바의 상황판 탭 옆 숫자는 이 카드 수다.
- **구현됨(화면): 티켓 20261026_2023 2회차** (`OpsMyTurn.tsx`). 카드: 상태(점+아이콘+글자), 제목(한 줄 말줄임), 건수, 마감(결정 필요만 「수 18:00까지」, 지났으면 「마감이 지났어요」), 이유 칩 요약(「트렌드 2 · 시즌 1」), 주 버튼 1개(결정 필요 「결정하기」, 실패 항목 「확인하기」, 루틴 멈춤 「기획함 열기」)로 `href`로 간다. 카드가 0장이면 한 줄 「내 차례인 일이 없어요」, 많으면 가로로 스크롤한다. **하지 않은 것:** 사이드바 「운영 홈」의 내 차례 숫자 배지(서버에서 숫자를 읽는 별도 일이라 후속).
- **구현됨(계산·읽기): 티켓 20261026_2023 1회차** (`opsBoard/myTurn.ts`, 읽기는 `opsBoard/load.ts`).
  - 「결정 필요」 카드: 묶음마다 도착·검토중 항목이 있으면 한 장. 건수는 그 항목 수이고 패턴 제안도 결정할 항목이라 센다. 마감은 그 묶음 `week`의 수요일 18:00 KST다. 이유 칩은 항목의 기획 이유를 종류별로 세어 많은 순 최대 3개다.
  - 「문제」 카드: 실패 항목이 있는 묶음마다 한 장(건수 = 실패 항목 수), 멈춘 루틴 시작 기록(§5.3 `isRoutineStalled`)마다 한 장(제목 「루틴이 멈췄어요」, 건수 1).
  - 정렬은 문제 → 결정 필요. 결정 필요는 마감이 이른 순, 문제는 최근 순이다. 카드 수(`myTurnCount`)가 상단 바 숫자와 같은 값이다.
  - 시험 묶음은 시험 포함을 켤 때만 카드가 된다.

### 6.2 주간 흐름 지도
- 가로는 7단계: 기획(윤진) → 세계관 검수(윈터) → 밸런스 점검(혜린) → **내 결정** → 예약(시스템) → 게재(시스템) → 결과(카즈하). 「내 결정」 열은 바탕색으로 구분한다.
- 세로는 주차. 최근 5주를 보인다. 행 머리에 주차, 기획 제목(§5.1), 기간.
- 각 행은 선로처럼 지나온 단계를 이어 그리고, 지금 단계에 정류장(건수 + 화면 상태)을 둔다. 지나온 단계에는 시각이나 결과(「2건 뺌」, 「승인 26」)를 작게 쓴다.
- 「결정 필요」와 「문제」 정류장은 눈에 띄게 움직인다(동작 줄이기 설정에서는 멈춘다). 누르면 결정 패널이나 서랍으로 간다.
- 같은 행에서 일부 항목만 실패하면 해당 단계 칸에 「문제 N」 정류장을 하나 더 둔다.
- 결과 열에는 그 주의 대표 지표(카드 열람률) 하나만 쓴다. 자세한 것은 운영툴 S6(결과와 기록)으로 간다.
- **구현됨(화면): 티켓 20261026_2023 2회차** (`OpsWeekFlowMap.tsx`). 7열 격자(왼쪽 행 머리 120px)에 열 머리는 단계 이름과 담당(윤진·윈터·혜린·나(운영자)·시스템·시스템·카즈하)이고 「내 결정」 열만 호박색 바탕이다. 행 머리는 「44주차」·기획 제목(없으면 「제목 없음」)·기간(「10/26~11/1」)이다. 셀은 선로를 이어 그리고 `done`은 작은 점 + 결과 글, `current`는 정류장(「3 · 결정 필요」), `upcoming`은 빈 점이다. 정류장은 링크로, 결정 필요·문제는 그 주 묶음의 결정 패널(`/admin/ops-inbox/{묶음}`), 그 밖은 일정표로 간다. 좁으면 지도 영역만 가로로 스크롤한다(최소 폭 980px). 5주 모두 비면 「최근 5주에 올라온 기획이 없어요」와 받은 기획함 링크다. **하지 않은 것:** 결과 열의 대표 지표(카드 열람률).
- **구현됨(계산·읽기): 티켓 20261026_2023 1회차** (`opsBoard/weekFlow.ts`, 읽기는 `opsBoard/load.ts`). 열 상태는 주마다 아래 규칙으로 정한다.
  - **열 상태:** 열마다 `done`(지나옴)·`current`(정류장 있음)·`upcoming`(아직)이고, 정류장에는 건수와 화면 상태(§3.1)가 붙는다.
  - **묶음이 있는 주(규칙 1):** 항목 상태를 `stageOfItemStatus`로 센다. 「내 결정」 열 = 도착 + 검토중, 예약 열 = 승인됨 + 준비중 + 예약됨, 게재 열 = 게재중, 결과 열 = 종료. 가장 앞에 항목이 있는 열 앞은 `done`, 항목이 있는 열은 건수와 함께 `current`, 항목이 없는 뒤쪽 열은 `upcoming`이다. 반려·취소는 어느 열에도 세지 않는다. 센 항목이 하나도 없으면(전부 반려·취소) 「내 결정」 열까지만 `done`이다.
  - **정류장이 여러 개일 수 있다:** 일부 항목이 이미 게재중이면 예약 열과 게재 열이 둘 다 `current`로 그려진다. 일부 항목이 실패하면 예약 열에 「문제 N」 정류장을 하나 더 둔다(실패만 있어도 같다).
  - **기획·세계관 검수·밸런스 점검 열(규칙 2):** 묶음의 단계 기록(§5.3)이 있으면 `done`이고 결과 글은 「N건 뺌」(제외 건수가 1 이상일 때), 아니면 「N건」(남은 건수)이다. 기록이 없는 옛 묶음은 `done`이고 글은 「기록 없음」이다(묶음이 이미 도착했으므로 지나온 것으로 본다).
  - **묶음 없이 시작 기록만 있는 주(규칙 3):** 기획 열이 `current`이고 「진행 중 · 시작 후 N분」이다. 3시간이 지나도 제출이 없으면 「문제 · 루틴이 멈췄어요」다. 시작 기록도 묶음도 없는 주는 모든 열이 `upcoming`이다.
  - **한 주에 묶음이 여럿이면** 항목과 단계 기록을 합쳐 한 행으로 센다. 행 제목은 그 주에 가장 늦게 받은 묶음의 제목이다(제목이 없으면 비운다).
  - **세지 않는 것:** 10개 밖 상태 값, 패턴 제안 항목(유저에게 나가지 않는다). 시험 묶음은 시험 포함을 켤 때만 센다.
  - **주차:** 묶음의 `week` 칸(`YYYY-Www`)을 월요일로 바꿔 놓고, 칸이 비었거나 형식이 틀리면 받은 시각이 속한 주(KST)로 본다. 이번 주 월요일부터 거꾸로 5주다.

### 6.3 결정 패널과 홈피드 미리보기
- **결정 패널:** 머리에 기획 제목과 이유 칩, 그 아래 「이번 기획의 핵심」(highlight 항목, 종류 표·새 미션·새 지점 표시·이유 칩·확인 표시), 접힌 「종류별로 고르기」(종류별 체크와 건수), 바닥에 선택 건수·공개 시작 시각과 [홈피드로 보기] [반려] [N건 승인하고 예약].
- **구현됨(결정 패널): 티켓 20261026_2024 1회차** (`OpsDecisionPanel.tsx`). 기획 제목은 페이지 머리(`h1`, 제목이 없으면 주차 라벨)가 쓰고 제목이 있으면 그 아래 한 줄에 주차와 기간을 보인다. 패널은 묶음 이유 칩 줄 → 「이번 기획의 핵심」(핵심 항목 최대 5개: 종류·제목·「새 미션」·이유 칩 2개·「확인 필요」, 줄을 누르면 그 항목이 선택된다. 핵심이 없으면 제목이 「확인이 필요한 항목」이고 확인 필요 항목이 대신 올라온다) → 접힌 「종류별로 고르기」(머리줄에 「승인 대상 N건」, 단계 표시줄 주 버튼 건수와 같다. 종류 체크박스가 그 종류의 검토중 항목을 한꺼번에 체크·해제하고 일부만 체크면 `indeterminate`, 0건이면 「고른 항목이 없어요」) 순이다. **이유 칩 모양:** 상태 색과 헷갈리지 않게 점선 테두리 + 종류 아이콘(트렌드 `IconTrendingUp`·시즌 `IconLeaf`·날씨 `IconCloud`·신호 `IconActivity`·패턴 `IconHash`) + 회색 글자이고, 아이콘은 장식이라 글자가 이름이다(`OpsRationaleChip.tsx`, 「내 차례」 카드와 같은 부품). **하지 않은 것:** 새 지점 표시, 바닥 줄의 [홈피드로 보기]·[반려]·공개 시작 시각(홈피드 미리보기는 티켓 2025), 항목 서랍 내용(2회차).
- **확인창:** 세 줄만 쓴다(언제부터 공개되는지, 공개 전 취소 가능, 실패 시 연결 항목 함께 되돌림).
- **구현됨(티켓 [20261026_2031](../../../tickets/p2-normal/20261026_2031_Admin_승인하고-예약-화면-합치기.md), 지금 기획 상세 화면):** 단계 표시줄 오른쪽의 [N건 승인하고 예약] 하나가 승인과 예약을 함께 한다. 누르면 요약창이 사전 점검(`approve: true`)으로 열리고, 요약이 곧 확인이다(JAM! 배지 소급 수 포함). 옛 [N개 승인하기]·[N개 예약 등록하기]와 개별 [승인하기]는 없고, 패턴 제안만 [패턴 사전에 넣기]가 남는다. 결정 패널 전체 개편(위 항목)은 티켓 20261026_2024가 한다.
  - 승인과 예약이 성공하면 예약된 항목 중 `image_spec`이 있고 이미지가 빈 것은 이미지를 자동으로 만들어 올린다(티켓 20261026_2034). 만들지 못해도 예약은 유지되고 「이미지 제작 필요」로 남는다.
- **서랍:** 항목을 누르면 오른쪽에 열린다. 이유 칩, 미리보기, 「왜 이 기획?」(note), 검수 결과(윈터·혜린 통과·확인과 시각), 핵심 값(공개 기간·대상·모양·조건·보상), 버튼 [빼기] [고치기] [이대로 두기].
- **홈피드 미리보기:**
  - 기간: 그 주 7일을 칸으로 보이고, 칸마다 보이는 카드 수와 모양별 막대를 그린다.
  - 날짜: 칸을 누르면 휴대폰 틀 안에 그날 홈 순서대로 카드를 그린다.
  - 유저 조건: 트라이브, 시간대를 고른다. 날씨·특일은 그날 저장된 값이 있으면 쓰고 없으면 고를 수 있다.
  - 대상 카드: 예약됨·게재중 카드와 이 묶음의 결정 전 카드. 결정 전 카드는 점선과 「승인 전」 표시.
  - 「기획 이유 보기」를 켜면 카드 위에 이유 칩이 올라간다.
  - 노출 판정은 서비스와 같은 함수(`lib/today/exposure.ts`)와 홈 정렬 규칙을 쓰고, 카드는 서비스 카드 컴포넌트로 그린다. 지금의 `TodayPreviewModal`(투데이 화면)과 `OpsCardPreview`(운영툴)를 이 미리보기로 모을지는 티켓 20261026_2025에서 정한다.

### 6.4 트렌드 레이더
- **내가 등록한 출처:** 이름, 종류(해시태그·채널·검색어 추이·직접 올린 자료), 위치(주소나 검색어), 켜짐 여부. 운영자가 어드민에서 추가·끄기를 한다. 직접 올린 자료는 `docs/operations/inbox/trends/`의 파일이다. 출처마다 마지막 루틴이 읽었는지 표시한다.
- **읽은 트렌드:** 묶음의 `trends[]`(§5.4)를 최근 14일 기준으로 모아 보인다. 이름, 요약, 추이(있을 때), 결과(반영 N건·보류·자동 제외와 범주).
- 반영 결과를 누르면 그 트렌드에서 나온 항목만 걸러 결정 패널을 연다.

### 6.5 에이전트 줄
- **구현됨(화면): 티켓 20261026_2023 2회차** (`OpsAgentRows.tsx`, 계산은 `opsBoard/agentRows.ts`). 에이전트 네 줄(윤진·기획, 윈터·세계관 검수, 혜린·밸런스 점검, 카즈하·결과)의 한 줄은 이번 주 흐름 행의 해당 열에서 읽는다: `current`면 「진행 중 · 시작 후 N분」(멈춘 루틴은 「루틴이 멈췄어요」), `done`이면 열의 결과 글(「2건 뺌」·「기록 없음」), 둘 다 아니면 「대기 중」. 다음 실행은 예약 루틴 「주간」(`SCHEDULED_JOBS`)이 켜져 있으면 다음 실행 요일·시각(KST), 꺼져 있으면 「예약 꺼짐」이다. 일정 띠는 월~일 7칸에 화 기획·수 결정 마감·목 공개를 쓰고 오늘은 굵은 테두리와 「오늘」 글자로 알린다.
- 에이전트마다 한 줄: 이름·역할, 지금 하는 일 또는 마지막 결과, 화면 상태. 다음 실행 예정 시각.
- 이번 주 일정 띠: 월~일 칸에 화 기획, 수 결정 마감, 목 공개를 표시하고 오늘을 테두리로 강조한다.

## 7. ② 생태계 상황판

정책 대시보드(`/admin/policy-dashboard`), 밸런스 설정(`/admin/balance`), 운영 설정(`/admin/ops-settings`)을 한 화면에서 시작하게 묶는다. 값을 바꾸는 화면 자체는 지금 화면을 그대로 쓴다(변경 이력·동시 수정 검사·확률 확인창을 그 화면이 지킨다).

- **목표 대비:** 밸런스 목표 정책(`policiesData.ts`의 「밸런스 목표」 항목)마다 지금 값, 목표 범위 표시선, 화면 상태(정상·주의·중단). 주의 이상만 상단에 뜨고 상단 바 숫자에 더한다.
- **순환 지도:** 성장 순환(활동 동기화 → 잼 → 캡슐 → 아이템 배지 → 인벤토리 → 컬렉션)과 필드 순환(시스템 드랍·유저 드랍 → 지점 → 픽업 → 인벤토리)을 마디로 그린다. 마디마다 대표 지표 하나와 상태 점.
- **정책 패널:** 마디를 누르면 그 마디의 정책 목록(`policiesData.ts`)을 보인다. 설정값은 [값 바꾸기]로 해당 설정 화면에 가고, 코드에 고정된 값은 [개발 요청]으로 개발 항목을 만든다(§8).
- 지표의 계산식과 기간은 티켓 20261026_2027에서 정한다. 이 문서에 수치를 적지 않는다.

- **개발 항목 보드:** 대기 / 진행 / staging 반영 / 배포됨 네 칸. 카드마다 제목, 티켓 번호, 어디서 왔는지(운영에서·생태계에서·그 밖).
- **데이터(D3):** 서버에서 GitHub API로 저장소 `standardmanual/jam`을 읽는다. 티켓 목록은 파일 수백 개를 하나씩 읽지 않도록 저장소에 티켓 색인 파일을 두고 그 한 파일을 읽는다(색인 생성 방식은 티켓 20261026_2028). 배포 상태는 브랜치 비교와 GitHub 배포 기록에서 읽는다. 토큰은 서버 환경변수에만 둔다.
- **개발 요청:** 생태계·운영 상황판에서 만든 요청은 DB에 쌓이고 보드의 「대기」 칸에 「요청」으로 보인다. 카리나가 세션을 시작할 때 요청을 읽어 티켓으로 바꾼다. 어드민이 티켓 파일을 직접 만들지 않는다.
- 티켓에 출처를 적는 선택 필드 `origin`(`ops`·`eco`·`other`)을 더한다(`docs/DOCUMENT_SCHEMA.md` 확장 규칙 1).

## 9. 확인 방법

JAM 2.0 출시 전까지 main 배포가 멈춰 있고, 배포된 staging에서는 어드민을 확인할 수 없다. 그래서 하위 티켓은 메인 작업 트리의 로컬 `next dev`에서 실제 화면을 열어 확인한다. 프로덕션 어드민에는 출시 배포 때 함께 나간다.

## 10. 하지 않을 것

- 안쪽 상태 10개와 상태 맞추기 규칙을 바꾸지 않는다(화면에서만 묶는다).
- 에이전트가 단계마다 실시간으로 보고하게 하지 않는다(D2).
- 어드민에서 티켓 파일을 만들거나 고치지 않는다.
- 밸런스 수치를 상황판에서 바로 바꾸지 않는다(설정 화면으로 보낸다).
