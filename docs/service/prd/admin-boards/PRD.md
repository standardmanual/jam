## 1. 한 줄 정의

운영자가 어드민을 열면 세 가지를 바로 알게 한다: 에이전트 기획이 어디까지 왔고 내가 무엇을 결정해야 하는지(운영), 서비스 생태계가 목표대로 도는지와 바꿀 정책이 무엇인지(생태계), 개발과 배포가 어디까지 왔는지(개발·배포).

## 2. 왜 다시 짜는가 (2026-10-26 사용자 피드백)

| 피드백 | 지금 화면의 원인 |
|---|---|
| 텍스트가 길고 많아 상황을 이해하기 어렵다 | 항목 상세 1칸에 글 블록 7개, 확인창 4종에 안내 문장, 설정 설명 배열 20개 이상 |
| 에이전트별 상태와 워크플로가 보이지 않는다 | 화면의 단계는 운영자가 받은 뒤(도착→종료)뿐이다. 에이전트 단계는 데이터로 남지 않고, `routine_run`은 저장만 하고 그리지 않는다 |
| 승인·취소·미승인 같은 상태와 버튼이 흐름에서 명확하지 않다 | 상태 10개를 그대로 보여 주고, 승인과 예약 등록이 버튼 두 개로 나뉘어 있다 |
| 전체 흐름을 한눈에 보기 어렵다 | 운영 홈의 숫자 다섯 칸은 누를 수 없고, 주차별 흐름을 한 화면에서 보는 곳이 없다 |
| 내가 무엇을 결정해야 하는지 알기 어렵다 | 결정할 일이 목록 탭 안에 섞여 있다 |
| 기획의 이유와 트렌드가 보이지 않는다 | 묶음에 가설 문장 하나뿐이고 항목별 이유 필드가 없다 |

## 3. 공통 원칙

1. **요약이 먼저, 상세는 누르면.** 화면 첫 줄은 「내 차례」다. 설명은 한 줄을 넘기지 않고, 그 이상은 서랍이나 툴팁에 둔다.
2. **상태는 다섯 가지로 보인다.** 안쪽 상태 10개는 그대로 두고 화면에서만 묶는다(§3.1). 색만 쓰지 않고 점·글자를 함께 쓴다.
3. **버튼 하나에 행동 하나.** 버튼 이름은 동사로 끝나고 결과를 그대로 말한다(「31건 승인하고 예약」). 화면마다 주 버튼은 하나다.
4. **기획 이유는 칩으로 보인다.** 트렌드·시즌·날씨·신호·패턴 다섯 종류를 기호와 테두리로 상태 색과 구분한다(§5).
5. **카피는 짧게 쓴다.** 상태 이름은 두 단어 이내, 제목은 명사구, 오류는 [현상]·[원인]·[해결] 한 줄씩이다(`docs/service/writing/UX_WRITING_GUIDELINE.md`). 같은 뜻에 다른 말을 쓰지 않는다.
6. **어드민 UI는 shadcn/ui다.** `jam-web/src/components/admin/ui/`의 컴포넌트를 쓴다. 서비스 MODULAR을 쓰지 않는다. 다만 홈피드 미리보기의 카드는 서비스 카드 컴포넌트를 그대로 그린다(§6.3).

### 3.1 화면 상태 다섯 가지

| 화면 상태 | 안쪽 상태 | 뜻 | 내 차례에 뜨는가 |
|---|---|---|---|
| 결정 필요 | 도착, 검토중 | 내가 승인·반려할 차례 | 뜬다 |
| 진행 중 | (에이전트 단계), 승인됨, 준비중, 예약됨 | 사람 손 없이 다음 단계로 가는 중. 칸 안에 「예약됨」처럼 세부를 작게 쓴다 | 안 뜬다 |
| 게재 중 | 게재중 | 유저에게 보이는 중 | 안 뜬다 |
| 문제 | 실패 | 내가 손봐야 함 | 뜬다 |
| 끝남 | 종료, 반려, 취소 | 더 할 일 없음. 칸 안에 세부를 작게 쓴다 | 안 뜬다 |

**구현됨(계산·읽기): 티켓 20261026_2023 1회차.** 계산은 `jam-web/src/lib/admin/opsBoard/screenState.ts`다.
- `screenStateOfItemStatus`가 위 표대로 10개 상태를 다섯 화면 상태로 묶는다. 10개 밖 값은 어느 상태에도 넣지 않는다(null).
- `screenDetailOfItemStatus`는 칸 안에 작게 쓰는 세부를 돌려준다: 승인됨·준비중·예약됨·종료·반려·취소. 도착·검토중·게재중·실패는 세부가 없다.
- `isMyTurnState`는 결정 필요·문제만 참이다.

## 5. 묶음에 더하는 데이터

에이전트가 제출하는 묶음(`POST /api/admin/ops-inbox`)에 아래를 더한다. 모두 선택 필드로 시작하고, 없으면 화면은 지금처럼 그린다(옛 묶음·시험 묶음 호환).

**저장 위치 (결정: 티켓 [20261026_2021](../../../tickets/p2-normal/20261026_2021_Infra_기획-묶음에-제목-이유-단계기록-트렌드-필드.md), 2026-10-26).** 새 테이블을 만들지 않고 이미 있는 칸을 최대한 쓴다.

| 필드 | 저장 |
|---|---|
| 묶음 `title` | `ops_bundles.title TEXT NULL` 새 칸 |
| 묶음 `trends[]` | `ops_bundles.trends JSONB NULL` 새 칸 |
| `routine_run.stages[]` | 기존 `ops_bundles.routine_run`(JSONB) 안. 새 칸 없음 |
| 항목 `rationale`·`highlight` | 기존 `ops_bundle_items.original`(제출 항목 원본) 안. 새 칸 없음 |

형식이 틀린 `title`·`trends`는 저장하지 않고 NULL로 둔다(원본은 `raw`에 남는다). 오류는 제출 응답과 묶음·항목의 형식 오류 목록에 쌓이고 제출은 막지 않는다.
검증은 `jam-web/src/lib/admin/opsInbox/validate.ts`, 읽기는 `query.ts`의 `getOpsBundleDetail`(`title`·`trends`·`stages`)과 `readOpsItemRationales`·`readOpsItemHighlight`다.
`source_id`·`source_ids`의 출처 번호는 출처 등록(§6.4)이 아직 없어 비어 있지 않은 문자열이나 1 이상의 정수로 본다. `outcome_reason`은 자동 제외 범주 이름을 비어 있지 않은 문자열로 받는다(범주 목록은 [`content-automation/PRD.md`](../content-automation/PRD.md) §10.2, 허용 목록 검사는 하지 않는다).

### 5.1 기획 제목 (구현됨: 티켓 20261026_2021)
- `title`: 그 주 기획을 한 줄로 부르는 이름, 30자 이내(예: 「LP 리바이벌 × 억새 절정」). 주간 흐름의 주차 칸과 결정 패널 제목에 쓴다. 지금의 `hypothesis`는 결정 패널 안에서 한 줄 설명으로 남긴다.

### 5.2 기획 이유 (구현됨: 티켓 20261026_2021)
- 항목마다 `rationale` 1~3개: `{ kind, label, note?, source_id? }`
  - `kind`: `trend`(온라인 트렌드) · `season`(시즌·절기·기념일) · `weather`(날씨) · `signal`(서비스 데이터 신호) · `pattern`(패턴 사전 번호)
  - `label`: 칩에 쓰는 말, 12자 이내(예: 「LP 리바이벌」, 「잠긴 배지 누적」, 「P07」)
  - `note`: 서랍의 「왜 이 기획?」 한두 문장, 120자 이내. 근거 숫자를 넣는다
  - `source_id`: 트렌드일 때 출처(§6.4) 번호
- 항목마다 `highlight`(참·거짓): 이번 기획의 핵심 항목. 묶음당 5개 이하. 결정 패널 맨 위에 먼저 보인다.
- 묶음의 이유 칩은 항목 이유를 종류별로 세어 화면이 만든다(따로 저장하지 않는다).

### 5.3 에이전트 단계 기록 (D2) (제출 쪽 `routine_run.stages`는 구현됨: 티켓 20261026_2021. 「시작」 기록 경로·멈춤 판정 함수도 구현됨: 티켓 20261026_2032, 내 차례에 띄우는 화면은 티켓 20261026_2023)
- **쓰기 2번:** ① 루틴 시작 때 「시작」 기록 1번(주차, 시작 시각, 맡은 에이전트 목록. `POST /api/admin/ops-inbox/routine-start`, 저장 위치 `ops_routine_starts`, 본문 `run_key`·`week?`·`author`·`agents[]`. 제출 묶음의 `routine_run.run_key`가 같으면 이어진다), ② 제출 때 묶음 안의 `routine_run.stages`에 단계별 요약을 한 번에 싣는다.
- `stages[]`: `{ agent, stage, started_at, ended_at, in_count, out_count, excluded_count }`. `stage`는 `plan`·`world_review`·`balance_check` 셋이다. 지금의 `excluded_items[].stage` 값과 같은 이름을 쓴다.
- 시작과 제출 사이에는 단계별 진행을 실시간으로 알 수 없다. 이 동안 주간 흐름 칸에는 「진행 중 · 시작 후 N분」만 보인다. 제출 뒤에는 단계마다 걸린 시간과 「2건 뺌」 같은 결과가 보인다.
- 시작 기록이 있는데 3시간 안에 제출이 없으면 「문제 · 루틴이 멈췄어요」로 내 차례에 뜬다(기준 시간은 운영 설정 값). 판정은 `isRoutineStalled`(`routineStart.ts`)이고 기준은 `OPS_ROUTINE_STALL_HOURS`(3) 한 곳이다.

### 5.4 읽은 트렌드 (구현됨: 티켓 20261026_2021)
- 묶음에 `trends[]`: `{ label, source_ids, summary, series?, outcome, outcome_reason? }`
  - `outcome`: `used`(기획에 반영) · `held`(보류) · `excluded`(자동 제외)
  - `series`: 출처가 숫자 추이를 줄 때만 최근 14일 값
- 반영한 트렌드는 해당 항목의 `rationale.source_id`로 이어진다.
- `source_ids`(그리고 `rationale.source_id`)가 가리키는 출처 번호는 §6.4 출처 테이블의 `no`다(문자열 `"1"`과 정수 `1`을 같은 번호로 본다). 출처는 지우지 않고 끄기만 하므로 옛 묶음의 번호는 계속 같은 출처를 가리킨다. 한 번도 등록하지 않은 번호가 와도 묶음 제출은 막지 않는다.

## 6. ① 운영 상황판

경로는 운영 홈 `/admin`이다. 지금 운영 홈의 구역은 상황판·신호·서비스 점검·최근 이력·빠른 실행이고, 지표 구역(주간 핵심 지표·배지 경제 흐름·통계)은 생태계 상황판으로 옮겼다. 옮길 곳은 티켓 20261026_2023 2회차에서 정했다(Q3, 아래 「운영 홈 구역 이동」).

**구현됨(화면): 티켓 20261026_2023 2회차.** 운영 홈 `/admin` 맨 위에 내 차례 카드 줄 → 주간 흐름 지도 → 에이전트 줄·일정 띠 순서로 한 구역(`BoardSection`, `app/admin/_home/sections.tsx`)을 둔다. 부품은 `components/admin/ops/board/`(`OpsMyTurn`·`OpsWeekFlowMap`·`OpsAgentRows`)다. 지금 운영 홈의 「이번 주 상태」 다섯 칸·각주·다음 주 줄은 이 구역이 대신해 없앴다.

**운영 홈 구역 이동(PRD Q3, 추천안 채택).** 주간 핵심 지표·배지 경제 흐름·통계는 생태계 상황판(티켓 20261026_2027)으로 옮기고, 서비스 점검·신호·최근 이력은 운영에 남긴다.

**구현됨(구역 이동): 티켓 20261026_2027 3-2.** 세 구역을 `/admin/ecosystem`의 정책 패널 아래로 옮겼다(이 순서: 주간 핵심 지표 → 배지 경제 흐름 → 통계). 운영 홈은 상황판 → 신호 → 서비스 점검 → 최근 이력 → 빠른 실행이다. 내용과 계산은 그대로이고 위치만 바뀌었다. 배지 경제 흐름의 `?trend=`는 `/admin/ecosystem`이 읽고 기간 전환 링크가 선택한 마디(`?node=`)를 유지하며, 시험 묶음 스위치(`sample`)는 운영 홈 전용이라 이 화면에는 두지 않는다(배지 발급량과 앰비언트 드랍량은 시험 묶음과 무관하다). 주간 지표 읽기(`startKpiWeekly`)는 서비스 점검과 주간 핵심 지표가 함께 쓰므로 `lib/admin/kpiWeeklyPair.ts`에 두었다. 옛 주소 `/admin?trend=7`을 북마크했다면 운영 홈은 `trend`를 읽지 않으므로 기간이 적용되지 않고, `/admin/ecosystem?trend=7`로 바꿔 열어야 한다.

### 6.1 내 차례
- 맨 위 카드 줄. 「결정 필요」와 「문제」만 뜬다. 카드마다 제목, 상태, 건수, 마감(결정 필요는 수 18:00), 이유 칩 요약, 주 버튼 1개.
- 상단 바의 상황판 탭 옆 숫자는 이 카드 수다.
- **구현됨(화면): 티켓 20261026_2023 2회차** (`OpsMyTurn.tsx`). 카드: 상태(점+아이콘+글자), 제목(한 줄 말줄임), 건수, 마감(결정 필요만 「수 18:00까지」, 지났으면 「마감이 지났어요」), 이유 칩 요약(「트렌드 2 · 시즌 1」), 주 버튼 1개(결정 필요 「결정하기」, 실패 항목 「확인하기」, 루틴 멈춤 「기획함 열기」)로 `href`로 간다. 카드가 0장이면 한 줄 「내 차례인 일이 없어요」, 많으면 가로로 스크롤한다. **하지 않은 것:** 사이드바 「운영 홈」의 내 차례 숫자 배지(서버에서 숫자를 읽는 별도 일이라 후속).
- **구현됨(계산·읽기): 티켓 20261026_2023 1회차** (`opsBoard/myTurn.ts`, 읽기는 `opsBoard/load.ts`).
  - 「결정 필요」 카드: 묶음마다 도착·검토중 항목이 있으면 한 장. 건수는 그 항목 수이고 패턴 제안도 결정할 항목이라 센다. 마감은 그 묶음 `week`의 수요일 18:00 KST다. 이유 칩은 항목의 기획 이유를 종류별로 세어 많은 순 최대 3개다.
  - 「문제」 카드: 실패 항목이 있는 묶음마다 한 장(건수 = 실패 항목 수), 멈춘 루틴 시작 기록(§5.3 `isRoutineStalled`)마다 한 장(제목 「루틴이 멈췄어요」, 건수 1).
  - 정렬은 문제 → 결정 필요. 결정 필요는 마감이 이른 순, 문제는 최근 순이다. 카드 수(`myTurnCount`)가 상단 바 숫자와 같은 값이다.
  - 시험 묶음은 시험 포함을 켤 때만 카드가 된다.

### 6.2 주간 흐름 지도
- 가로는 7단계: 기획(윤진) → 세계관 검수(윈터) → 밸런스 점검(혜린) → **내 결정** → 예약(시스템) → 게재(시스템) → 결과(카즈하). 「내 결정」 열은 바탕색으로 구분한다.
- 세로는 주차. 최근 5주를 보인다. 행 머리에 주차, 기획 제목(§5.1), 기간.
- 각 행은 선로처럼 지나온 단계를 이어 그리고, 지금 단계에 정류장(건수 + 화면 상태)을 둔다. 지나온 단계에는 시각이나 결과(「2건 뺌」, 「승인 26」)를 작게 쓴다.
- 「결정 필요」와 「문제」 정류장은 눈에 띄게 움직인다(동작 줄이기 설정에서는 멈춘다). 누르면 결정 패널이나 서랍으로 간다.
- 같은 행에서 일부 항목만 실패하면 해당 단계 칸에 「문제 N」 정류장을 하나 더 둔다.
- 결과 열에는 그 주의 대표 지표(카드 열람률) 하나만 쓴다. 자세한 것은 운영툴 S6(결과와 기록)으로 간다.
- **구현됨(화면): 티켓 20261026_2023 2회차** (`OpsWeekFlowMap.tsx`). 7열 격자(왼쪽 행 머리 120px)에 열 머리는 단계 이름과 담당(윤진·윈터·혜린·나(운영자)·시스템·시스템·카즈하)이고 「내 결정」 열만 호박색 바탕이다. 행 머리는 「44주차」·기획 제목(없으면 「제목 없음」)·기간(「10/26~11/1」)이다. 셀은 선로를 이어 그리고 `done`은 작은 점 + 결과 글, `current`는 정류장(「3 · 결정 필요」), `upcoming`은 빈 점이다. 정류장은 링크로, 결정 필요·문제는 그 주 묶음의 결정 패널(`/admin/ops-inbox/{묶음}`), 그 밖은 일정표로 간다. 좁으면 지도 영역만 가로로 스크롤한다(최소 폭 980px). 5주 모두 비면 「최근 5주에 올라온 기획이 없어요」와 받은 기획함 링크다. **하지 않은 것:** 결과 열의 대표 지표(카드 열람률).
- **구현됨(계산·읽기): 티켓 20261026_2023 1회차** (`opsBoard/weekFlow.ts`, 읽기는 `opsBoard/load.ts`). 열 상태는 주마다 아래 규칙으로 정한다.
  - **열 상태:** 열마다 `done`(지나옴)·`current`(정류장 있음)·`upcoming`(아직)이고, 정류장에는 건수와 화면 상태(§3.1)가 붙는다.
  - **묶음이 있는 주(규칙 1):** 항목 상태를 `stageOfItemStatus`로 센다. 「내 결정」 열 = 도착 + 검토중, 예약 열 = 승인됨 + 준비중 + 예약됨, 게재 열 = 게재중, 결과 열 = 종료. 가장 앞에 항목이 있는 열 앞은 `done`, 항목이 있는 열은 건수와 함께 `current`, 항목이 없는 뒤쪽 열은 `upcoming`이다. 반려·취소는 어느 열에도 세지 않는다. 센 항목이 하나도 없으면(전부 반려·취소) 「내 결정」 열까지만 `done`이다.
  - **정류장이 여러 개일 수 있다:** 일부 항목이 이미 게재중이면 예약 열과 게재 열이 둘 다 `current`로 그려진다. 일부 항목이 실패하면 예약 열에 「문제 N」 정류장을 하나 더 둔다(실패만 있어도 같다).
  - **기획·세계관 검수·밸런스 점검 열(규칙 2):** 묶음의 단계 기록(§5.3)이 있으면 `done`이고 결과 글은 「N건 뺌」(제외 건수가 1 이상일 때), 아니면 「N건」(남은 건수)이다. 기록이 없는 옛 묶음은 `done`이고 글은 「기록 없음」이다(묶음이 이미 도착했으므로 지나온 것으로 본다).
  - **묶음 없이 시작 기록만 있는 주(규칙 3):** 기획 열이 `current`이고 「진행 중 · 시작 후 N분」이다. 3시간이 지나도 제출이 없으면 「문제 · 루틴이 멈췄어요」다. 시작 기록도 묶음도 없는 주는 모든 열이 `upcoming`이다.
  - **한 주에 묶음이 여럿이면** 항목과 단계 기록을 합쳐 한 행으로 센다. 행 제목은 그 주에 가장 늦게 받은 묶음의 제목이다(제목이 없으면 비운다).
  - **세지 않는 것:** 10개 밖 상태 값, 패턴 제안 항목(유저에게 나가지 않는다). 시험 묶음은 시험 포함을 켤 때만 센다.
  - **주차:** 묶음의 `week` 칸(`YYYY-Www`)을 월요일로 바꿔 놓고, 칸이 비었거나 형식이 틀리면 받은 시각이 속한 주(KST)로 본다. 이번 주 월요일부터 거꾸로 5주다.

### 6.3 결정 패널과 홈피드 미리보기
- **결정 패널:** 머리에 기획 제목과 이유 칩, 그 아래 「이번 기획의 핵심」(highlight 항목, 종류 표·새 미션·새 지점 표시·이유 칩·확인 표시), 접힌 「종류별로 고르기」(종류별 체크와 건수), 바닥에 선택 건수·공개 시작 시각과 [홈피드로 보기] [반려] [N건 승인하고 예약].
- **구현됨(결정 패널): 티켓 20261026_2024 1회차** (`OpsDecisionPanel.tsx`). 기획 제목은 페이지 머리(`h1`, 제목이 없으면 주차 라벨)가 쓰고 제목이 있으면 그 아래 한 줄에 주차와 기간을 보인다. 패널은 묶음 이유 칩 줄 → 「이번 기획의 핵심」(핵심 항목 최대 5개: 종류·제목·「새 미션」·이유 칩 2개·「확인 필요」, 줄을 누르면 그 항목이 선택된다. 핵심이 없으면 제목이 「확인이 필요한 항목」이고 확인 필요 항목이 대신 올라온다) → 접힌 「종류별로 고르기」(머리줄에 「승인 대상 N건」, 단계 표시줄 주 버튼 건수와 같다. 종류 체크박스가 그 종류의 검토중 항목을 한꺼번에 체크·해제하고 일부만 체크면 `indeterminate`, 0건이면 「고른 항목이 없어요」) 순이다. **이유 칩 모양:** 상태 색과 헷갈리지 않게 점선 테두리 + 종류 아이콘(트렌드 `IconTrendingUp`·시즌 `IconLeaf`·날씨 `IconCloud`·신호 `IconActivity`·패턴 `IconHash`) + 회색 글자이고, 아이콘은 장식이라 글자가 이름이다(`OpsRationaleChip.tsx`, 「내 차례」 카드와 같은 부품). **하지 않은 것:** 새 지점 표시, 바닥 줄의 [반려], 항목 서랍 내용(2회차). 바닥 줄의 [홈피드로 보기]·공개 시작 시각은 티켓 20261026_2025 2회차에서 구현했다(아래 홈피드 미리보기).
- **확인창:** 세 줄만 쓴다(언제부터 공개되는지, 공개 전 취소 가능, 실패 시 연결 항목 함께 되돌림).
- **구현됨(티켓 [20261026_2031](../../../tickets/p2-normal/20261026_2031_Admin_승인하고-예약-화면-합치기.md), 지금 기획 상세 화면):** 단계 표시줄 오른쪽의 [N건 승인하고 예약] 하나가 승인과 예약을 함께 한다. 누르면 요약창이 사전 점검(`approve: true`)으로 열리고, 요약이 곧 확인이다(JAM! 배지 소급 수 포함). 옛 [N개 승인하기]·[N개 예약 등록하기]와 개별 [승인하기]는 없고, 패턴 제안만 [패턴 사전에 넣기]가 남는다. 결정 패널 전체 개편(위 항목)은 티켓 20261026_2024가 한다.
  - 승인과 예약이 성공하면 예약된 항목 중 `image_spec`이 있고 이미지가 빈 것은 이미지를 자동으로 만들어 올린다(티켓 20261026_2034). 만들지 못해도 예약은 유지되고 「이미지 제작 필요」로 남는다.
- **서랍:** 항목을 누르면 오른쪽에 열린다. 이유 칩, 미리보기, 「왜 이 기획?」(note), 검수 결과(윈터·혜린 통과·확인과 시각), 핵심 값(공개 기간·대상·모양·조건·보상), 버튼 [빼기] [고치기] [이대로 두기].
- **구현됨(서랍): 티켓 20261026_2024 2회차** (`OpsItemDetail.tsx`, 읽는 규칙은 `lib/admin/opsBoard/drawerView.ts`의 `keyValuesOf`·`reviewResultsOf`·`nextDecidableItemId`). 지금 상세 열이 서랍이고 위에서 아래로 머리(종류·상태·「핵심」 표시·패턴 번호, 그 아래 이 항목의 이유 칩 전부) → 「왜 이 기획?」(이유마다 한 줄: 칩 + 메모 두 줄 제한 + 트렌드의 「출처 N」, 없으면 「적힌 이유가 없어요」) → 형식 오류·밸런스 경고 → 「유저가 겪는 것」 → 「핵심 값」(공개 기간 한 줄 「12/30(수) 09:00 ~ 10:00」·대상·모양·조건·보상, 읽을 수 없는 칸은 줄을 그리지 않는다) → 「검수 결과」(윈터 세계관 검수·혜린 밸런스 점검 두 줄: 점+글자로 「통과」·「확인 필요」·「검수 기록 없음」/「점검 기록 없음」, 한 줄 근거, 묶음 단계 기록 `stages`의 해당 단계 `endedAt` 시각. 아래 접힘 「검수 자세히」에 예전 검수·판정 문장) → 기본 접힘 셋(「내용 전체」·「제출 원본」·「결정 기록」) 순이다. 편집 중에는 「유저가 겪는 것」·「핵심 값」·「내용 전체」 자리를 편집 화면이 대신한다. **버튼 동작:** 검토중이고 패턴 제안이 아닌 항목에만 주 줄 [빼기]·[고치기]·[이대로 두기]를 두고 [반려하기](확인창 그대로)는 그 아래 보조 줄이다. [빼기] = 승인 대상 체크를 풀고 `position` 순으로 다음 결정할 항목을 연다. [고치기] = 예전 [수정하기]와 같은 직접 수정(이름만 바뀜). [이대로 두기] = 체크를 유지하고(꺼져 있었으면 켜고) 다음 결정할 항목을 연다. 다음 항목은 끝에 닿으면 처음부터 찾고 결정할 항목이 자기밖에 없으면 이동하지 않는다. 패턴 제안과 그 밖의 상태의 버튼, 일정표 서랍의 결정 줄은 그대로다. **하지 않은 것:** 서랍 안 카드 미리보기 자리 변경(미리보기는 따로 있다), 핵심 값 칸의 새 항목.
- **홈피드 미리보기:**
  - 기간: 그 주 7일을 칸으로 보이고, 칸마다 보이는 카드 수와 모양별 막대를 그린다.
  - 날짜: 칸을 누르면 휴대폰 틀 안에 그날 홈 순서대로 카드를 그린다.
  - 유저 조건: 트라이브, 시간대를 고른다. 날씨·특일은 그날 저장된 값이 있으면 쓰고 없으면 고를 수 있다.
  - 대상 카드: 예약됨·게재중 카드와 이 묶음의 결정 전 카드. 결정 전 카드는 점선과 「승인 전」 표시.
  - 「기획 이유 보기」를 켜면 카드 위에 이유 칩이 올라간다.
  - 노출 판정은 서비스와 같은 규칙 함수(`lib/today/cardSelection.ts`: 기간·태그 겹침·홈 정렬)를 쓰고, 카드는 서비스 카드 컴포넌트로 그린다. 투데이 화면의 `TodayPreviewModal`과 운영툴의 `OpsCardPreview`를 이 미리보기로 모을지는 티켓 20261026_2025에서 정했다(아래 2회차 합치기 결정).
- **구현됨(계산·읽기·API): 티켓 20261026_2025 1회차** (화면은 2회차). 읽기 API `GET /api/admin/home-preview`(관리자만, 쓰기 없음, 캐시 없음)가 `lib/admin/homePreview/load.ts`의 `loadHomePreview`를 부른다. 쿼리는 `date`·`days`(1~7, 기본 7)·`tribe`·`time`(기본 `time_morning`)·`weather`·`special`·`newUser`·`bundle`이고 형식이 틀리면 400, 읽기가 실패하면 500이다(빈 목록으로 보이지 않는다).
  - **가상 유저 조건:** 노출 태그는 `all` + 시간대 + (날씨가 있으면) `weather_*` + 특일 태그 + (신규면) `new_user`다(`lib/today/virtualViewer.ts`). 참가·보유·동기화 이력에서 나오는 개인 상태 태그는 가상 유저가 알 수 없어 넣지 않는다. 날씨·특일을 비우면 날마다 그날 저장된 값(`external_input_daily`)을 쓰고, 저장된 값이 없는 날(미래)은 그 태그를 넣지 않는다. 응답의 날마다 `inputs`에 저장된 값과 쓴 값이 함께 온다.
  - **실제 카드:** 기간 전체와 겹치는 켜진 카드를 한 번에 읽고 날마다 KST 하루 경계로 기간·태그·정렬을 적용한다. 미션 소개 카드와 미션을 가리키는 랭킹 보드 카드는 허용 트라이브에 가상 유저의 트라이브가 없으면 뺀다. 유저별 참가·완료 판정은 하지 않으므로 실제 유저가 보는 목록은 이 목록의 부분집합일 수 있다.
  - **승인 전 카드:** `bundle`을 주면 그 묶음의 `home_feed_card` 항목 중 도착·검토중인 것을 같은 태그 규칙으로 걸러 실제 카드 뒤에 `resource.sort_order` 순으로 붙이고(`source: 'pending'`, 기획 이유 포함), 날마다 `pendingCount`로 센다. 시작 시각을 읽을 수 없는 항목은 어느 날에도 놓지 않는다.
  - 날마다 `entries.length`가 그날 카드 수이고 `shapeCounts`(모양별 개수)는 `entries`에서 센다. **하지 않은 것:** 화면, 실제 홈 조회(`getTodayCards`) 변경.
- **구현됨(화면): 티켓 20261026_2025 2회차.** 화면 부품은 `components/admin/ops/preview/`의 `HomePreviewPanel`(속성 `initialDate`·`bundleId?`·`days?`) 하나다. 위에서 아래로 조건 줄 → 7일 칸(`HomePreviewWeekStrip`) → 선택한 날의 휴대폰 틀(`TodayCardPreview`)이고, 조건이나 시작 날짜가 바뀌면 `GET /api/admin/home-preview`를 한 번 부르며 이전 요청은 취소한다. 칸을 눌러 날을 바꾸는 것은 7일치가 이미 와 있어 다시 부르지 않는다. 실패는 한 줄 오류와 「다시 불러오기」다.
  - **합치기 결정:** 새 미리보기 부품을 하나 만들고 투데이 화면의 `TodayPreviewModal`(전에는 노출 태그를 무시한 「켜진 카드 전부」 상한선)이 그 부품을 담는 창이 된다. 결정 패널과 투데이가 같은 부품·같은 API를 쓰므로 노출 판정이 한 벌이다(근거: 두 곳이 따로 판정하면 한쪽만 고쳐져 어긋난다). 쓰이지 않게 된 `GET /api/admin/today/preview`와 `getAdminTodayPreviewCards`는 지웠다(`resolvePreviewCards`는 새 읽기가 쓰므로 남겼다). 운영툴 왼쪽 칸의 항목 한 장 미리보기(`OpsCardPreview`)는 그대로 둔다.
  - **진입 두 곳:** (a) 기획 상세 결정 패널 바닥 줄 — 「공개 시작 12/30(수) 09:00」(체크한 항목 중 가장 이른 공개 시각, 없으면 이 문구는 쓰지 않는다)과 [홈피드로 보기]. 누르면 오른쪽 시트가 열려 `bundleId` = 이 묶음, 처음 날짜 = 체크한 항목 중 가장 이른 공개일(없으면 묶음 주 월요일, 그것도 없으면 오늘)로 부품을 담는다. (b) 투데이 화면의 미리보기 창 — `initialDate` = 선택한 날짜, 묶음 없음.
  - **조건 줄:** 시작 날짜(미래 날짜도 고른다) · 트라이브(「전체(트라이브 없음)」와 응답의 `tribes` 이름순 목록) · 시간대(새벽·아침·낮·저녁·밤, 기본 아침) · 날씨(「저장된 값」·맑음·흐림·비·극단) · 특일(「저장된 값」과 공휴일·절기·기념일 토글, 다 끄면 `special=none`으로 특일 없음) · 신규 유저. 날씨·특일은 「저장된 값」이 기본이고, 선택한 날에 저장된 값이 없으면(미래) 「저장된 값이 없어요: 날씨, 특일」 한 줄로 알리고 그대로 고르게 한다.
  - **7일 칸:** 요일·날짜, 카드 수 숫자(`entries.length` — 휴대폰 틀에 그려지는 카드 수와 같다), 모양별 막대(카드 한 장이 한 조각, 모양마다 다른 회색, 범례 없이 `title` 툴팁 「히어로 2장」), 승인 전 카드가 있으면 점선 점과 「승인 전 N」. 선택한 칸은 테두리로 강조한다.
  - **휴대폰 틀:** `TodayCardPreview`의 새 선택 속성 `annotations`로 승인 전 카드에 점선 테두리와 「승인 전」, 「기획 이유 보기」(묶음이 있을 때만 보이는 스위치)를 켜면 이유 칩(`OpsRationaleChips`)을 카드 위에 올린다. 속성을 안 주는 호출부(카드 폼, 운영툴)는 그대로다. 카드가 0장이면 「이 날 보이는 카드가 없어요」.
  - **수동 비노출 규칙:** 미션 소개 카드는 가리키는 미션 중 관리자가 수동으로 비노출한 것(`isMissionExposed`, 그날 기준 시각)을 뺀다. 실제 홈 조회 `filterMissionSpotlightCards`와 같은 규칙이라 읽은 미션이 하나도 없으면 카드를 그대로 두고, 미션 행을 못 찾은 카드는 뺀다. 유저별 판정(완료·잠금·숨김)은 가상 유저가 없어 하지 않는다.
  - **하지 않은 것:** 유저별 참가·완료 판정, 새 지점 표시, 기간을 7일보다 길게 고르는 일.

### 6.4 트렌드 레이더
- **구현됨(DB·API): 티켓 20261026_2033 1회차** (화면은 아래 「구현됨(화면)」). 테이블 `ops_trend_sources`(마이그레이션 296)와 API 세 개다. 코드는 `lib/admin/opsTrends/`(`constants.ts`, 검증 `sources.ts`, 저장 `sourceStore.ts`)와 `app/api/admin/ops-trend-sources/`다.
  - **테이블:** `id`(UUID), `no`(자동 증가 출처 번호, 유일 — 루틴과 화면의 「출처 N」), `name`(앞뒤 공백 제외 1~60자, 공백·대소문자를 무시하고 유일), `kind`(`hashtag`·`channel`·`search_trend`·`manual_upload`), `location`(300자 이내, 직접 올린 자료만 비워도 됨), `enabled`, `created_at`, `updated_at`, `created_by`(응답에 싣지 않음). RLS만 켜고 정책이 없어 service_role만 접근한다.
  - **삭제 없음:** 끄기(`enabled=false`)로 대신한다. 옛 묶음의 `source_ids`가 번호로 남아 있기 때문이다.
  - **「마지막으로 읽은 시각」:** 칸을 두지 않고 읽을 때 계산한다. 최근 60일 묶음의 `trends[].source_ids`에 그 `no`가 든 묶음 중 가장 늦은 `received_at`이고, 없으면 `null`이다. 시험 묶음(`is_sample`)은 뺀다.
  - **`GET /api/admin/ops-trend-sources`:** 관리자 세션 또는 읽기 토큰. 읽기 토큰은 **켜진 출처만** `{ sources: [{ no, name, kind, location }] }`(`includeDisabled` 무시). 관리자 세션은 기본이 켜진 출처이고 `?includeDisabled=true`이면 전부 `{ sources: [{ id, no, name, kind, location, enabled, lastReadAt, createdAt }] }`.
  - **`POST /api/admin/ops-trend-sources`:** 관리자 세션만(읽기 토큰은 403). 본문 `{ name, kind, location? }` 8KB까지. 검증 실패 400(+`details`), 이름 중복 409, 성공 201 `{ source }`. 직접 올린 자료가 아닌 종류는 `location`이 비면 400.
  - **`PATCH /api/admin/ops-trend-sources/[id]`:** 관리자 세션만. 본문 `enabled`·`name`·`location` 중 하나 이상(종류는 바꿀 수 없다). `id`가 UUID가 아니거나 없는 행이면 404, 검증 실패 400(직접 올린 자료가 아닌 출처의 위치를 비우는 경우 포함), 이름 중복 409, 성공 200 `{ source }`.
  - **오류:** 저장소 실패는 500이고 고정 문장 하나만 싣는다(원문은 서버 로그 `[admin/ops-trend-sources]`에만 남는다).
- **구현됨(화면): 티켓 20261026_2033 2회차.** 새 페이지 `/admin/ops-trends`(사이드바 「라이브」의 「트렌드 레이더」, 「일정표」·「투데이」 다음 「패턴 사전」 앞)다. 머리 오른쪽에 운영 홈과 같은 시험 묶음 스위치(`?sample=1`)를 두고, 위쪽 「내가 등록한 출처」와 아래쪽 「읽은 트렌드」를 따로 읽어 한쪽을 못 읽으면 그 구역만 안내 카드다. 계산은 `lib/admin/opsTrends/radar.ts`(`readBundleTrends`·`trendLinkedItemIds`·`collectRadar`·`buildTrendFilter`), 읽기는 `radarLoad.ts`, 화면 부품은 `components/admin/ops/trends/`(`OpsTrendSources`·`OpsTrendRadar`·`OpsTrendSparkline`)다.
  - **출처 관리:** 표(번호·이름·종류 글자·위치·마지막으로 읽은 시각(KST, 없으면 「아직 읽지 않았어요」)·켜짐 스위치). 스위치는 누르면 `PATCH`로 바로 켜고 끄며, 요청 중에는 그 줄만 잠기고 실패하면 되돌리고 한 줄 오류를 보인다. [출처 추가]는 이름·종류·위치 양식이고 직접 올린 자료는 위치를 비워도 된다. 서버가 돌려준 오류 문장(400 `details`, 409)을 그대로 한 줄로 보인다. 삭제는 없다.
  - **읽은 트렌드:** 최근 14일에 받은 묶음의 `trends[]`를 받은 시각 내림차순으로 모은다. 위에 「반영 N · 보류 N · 자동 제외 N」 요약 줄(점+글자), 카드에 이름·한 줄 요약·출처 칩(「출처 N · 이름」, 목록에서 이름을 못 찾으면 「출처 N」)·추이 막대(`series`가 있을 때, SVG 속성만 사용)·결과 칩(자동 제외는 범주 한 줄)·받은 기획 제목과 시각이 나온다. 모양이 틀린 원소는 뺀다. 시험 묶음은 시험 포함이 켜졌을 때만 읽고 센다. 14일 안에 트렌드가 없으면 「최근 14일에 읽은 트렌드가 없어요」다.
  - **연결 항목 걸러 보기:** 반영(`used`) 트렌드에 「연결 항목 N건」 링크(`/admin/ops-inbox/{묶음 행 ID}?trend={트렌드 번호}`, 시험 포함 중이면 `sample=1`)가 붙는다. 연결 항목은 그 묶음 항목 중 기획 이유 `trend`의 `source_id`가 트렌드의 `source_ids`에 드는 항목이고 반려·취소 항목은 뺀다. 기획 상세는 `?trend=`를 읽어 목록과 탭 숫자를 그 항목으로 좁히고 알림 줄에 「「이름」 트렌드에서 나온 항목 N건만 보고 있어요」와 [전체 보기](쿼리의 `trend`를 지운다)를 둔다. 번호가 틀리거나 연결 항목이 없으면 걸러 보기를 열지 않는다. 결정 패널의 승인 대상 건수와 「N건 승인하고 예약」은 좁히기와 상관없이 전체 항목 기준 그대로다.
  - **하지 않은 것:** 루틴이 출처를 읽는 쪽(주간 루틴 티켓 20260930_1504), 출처 삭제, 서랍의 「출처 N」을 출처 이름으로 바꾸는 일, 운영 홈에 레이더 요약 구역을 더하는 일.
- **내가 등록한 출처:** 이름, 종류(해시태그·채널·검색어 추이·직접 올린 자료), 위치(주소나 검색어), 켜짐 여부. 운영자가 어드민에서 추가·끄기를 한다. 직접 올린 자료는 `docs/operations/inbox/trends/`의 파일이다. 출처마다 마지막 루틴이 읽었는지 표시한다.
- **읽은 트렌드:** 묶음의 `trends[]`(§5.4)를 최근 14일 기준으로 모아 보인다. 이름, 요약, 추이(있을 때), 결과(반영 N건·보류·자동 제외와 범주).
- 반영 결과를 누르면 그 트렌드에서 나온 항목만 걸러 결정 패널을 연다.

### 6.5 에이전트 줄

- 이번 주 일정 띠: 월~일 칸에 화 기획, 수 결정 마감, 목 공개를 표시하고 오늘을 테두리로 강조한다.

## 7. ② 생태계 상황판

정책 대시보드(`/admin/policy-dashboard`), 밸런스 설정(`/admin/balance`), 운영 설정(`/admin/ops-settings`)을 한 화면에서 시작하게 묶는다. 값을 바꾸는 화면 자체는 지금 화면을 그대로 쓴다(변경 이력·동시 수정 검사·확률 확인창을 그 화면이 지킨다).

- **목표 대비:** 밸런스 목표 정책(`policiesData.ts`의 「밸런스 목표」 항목)마다 지금 값, 목표 범위 표시선, 화면 상태(정상·주의·중단). 주의·중단 줄이 맨 위로 올라오고, 주의 이상 개수는 화면 머리의 요약 줄에 쓴다(상단 바 숫자는 만들지 않는다. 아래 「구현됨(화면)」 참고).
- **순환 지도:** 성장 순환(활동 동기화 → 잼 → 캡슐 → 아이템 배지 → 인벤토리 → 컬렉션)과 필드 순환(시스템 드랍·유저 드랍 → 지점 → 픽업 → 인벤토리)을 마디로 그린다. 마디마다 대표 지표 하나와 상태 점.
- **정책 패널:** 마디를 누르면 그 마디의 정책 목록(`policiesData.ts`)을 보인다. 설정값은 [값 바꾸기]로 해당 설정 화면에 가고, 코드에 고정된 값은 [개발 요청]으로 개발 항목을 만든다(§8).
- 지표의 계산식과 기간은 티켓 20261026_2027에서 정했다(아래 표). 임계값 수치는 코드 상수가 단일 원천이라 이 문서에는 상수 이름과 의미만 적는다.

- **상태 규칙:** 칸마다 목표와 견줘(`compareToTarget`) 목표 안이면 정상, 밖이면 주의다. 목표 한계(값이 가까운 쪽 끝)에서 벗어난 폭이 그 한계값의 `STOP_DEVIATION_RATIO` 이상이면 중단이고, 한계값이 0이면 벗어나는 순간 중단이다. **`STOP_DEVIATION_RATIO`(50%)는 가정 값**이라 오픈 뒤 실제 데이터로 맞춘다. 표본이 모자라면 부족, 읽기에 실패하면 읽지 못함, 목표가 없는 마디는 목표 없음(값만 보임)이다. 마디 상태는 칸 상태 중 가장 나쁜 것(중단 > 주의 > 읽지 못함 > 부족 > 정상)이다.
- **주의 이상 개수:** 목표 대비 행 중 주의와 중단의 합이다. 읽지 못함은 주의로 섞지 않고 따로 센다.
- **목표 대비 연결:** `ch19-kpi-capsule-speed`→`capsule_open`, `ch19-kpi-chapter-reach`→`chapter_reach`(마디 없음, 목표 대비 칸에만), `ch19-kpi-item-badges-monthly`→`monthly_items`+`rarity_feel`, `ch19-kpi-collection-speed`→`collection_complete`, `ch19-kpi-inventory-full`→`inventory_full`. 목표 대비 칸은 밸런스 서브 대시보드의 읽기(`loadBalanceDashboard`)를 그대로 재사용한다.
- **정책의 마디 연결:** `policiesData.ts`의 항목에 선택 칸 `nodes`를 더했다(3~9·11장과 19장 밸런스 목표 항목, 값·설명·상태는 그대로). 마디 정의·이음선·상수(`FIELD_WINDOW_DAYS`·`STOP_DEVIATION_RATIO`)는 `ecosystem/nodes.ts`가 단일 원천이다.
- 읽기 하나가 실패해도 그 마디만 읽지 못함이고, `loadEcosystemSnapshot`은 던지지 않고 마디 10개를 항상 돌려준다.

**구현됨(화면): 티켓 20261026_2027 3-1** (`/admin/ecosystem`, 사이드바 「밸런스」 그룹 맨 위 「생태계 상황판」, `jam-web/src/app/admin/ecosystem/`·`components/admin/ecosystem/`). 어드민 화면이라 채원 판정 없이 shadcn 부품으로 만들었고, 상태는 색만 쓰지 않고 기호(●·▲·■·◌·!·–)와 글자(정상·주의·중단·표본 부족·읽지 못함·목표 없음)를 함께 쓴다.

- **화면 구성(위에서 아래로):** 머리(제목·한 줄 설명·요약 줄 「주의 이상 N · 읽지 못함 M」과 기준 시각) → 목표 대비 → 순환 지도 → 정책 패널 → (3-2에서 옮겨 온) 주간 핵심 지표 → 배지 경제 흐름 → 통계. 구역마다 따로 읽고(`Suspense`), 한 구역이 실패하면 그 구역만 안내 카드다.
- **목표 대비:** 밸런스 목표 정책 5개마다 칸별 현재 값·목표 글자·상태와 목표 표시선 막대(SVG, 목표 범위 띠와 현재 값 표시선). 중단 → 주의 → 읽지 못함 → 부족 → 정상 순으로 위에 올린다(같은 상태는 원래 순서). 값이 없는 칸은 막대 없이 「부족」과 사유(「표본 N/M명」·「관찰 기간이 모자라요」)만 보인다.
- **순환 지도:** 두 줄. 성장 순환 6마디가 글자 화살표(→)로 이어지고, 필드 순환은 시스템 드랍·유저 드랍(위아래) → 지점 → 픽업 → 인벤토리다. 필드 쪽 인벤토리는 같은 마디의 바로가기다. 마디 카드는 이름·상태·대표 지표 값·보조 값·기간을 보이고 밸런스 마디가 부족이면 사유를 한 줄 더 쓴다.
- **`?node=<마디 ID>`:** 마디 선택은 주소 쿼리로 한다. 마디는 링크라서 서버에서 그리고, 공유하고 새로 고쳐도 같은 마디가 열린다. 허용 밖 값은 선택 없음으로 본다. 정책 패널은 마디가 선택됐을 때만 설정값(`loadPolicyLiveValues`, 정책 대시보드와 같은 읽기)과 열린 개발 요청을 읽는다.
- **정책 패널:** 선택한 마디의 정책을 설정값 → 코드 고정 → 그 밖 순서로 보인다. 설정값 정책은 현재 값과 [값 바꾸기](설정 화면으로 이동), 코드 고정 정책은 [개발 요청]이다. 마디가 하나도 없는 정책은 맨 아래 「순환 밖 정책 N개」 접힘 목록에 둔다.
- **열린 요청 표시:** 같은 정책에 `requested` 요청이 있으면 버튼 대신 「요청 N번 접수됨」과 [접기]를 보인다([접기]는 그 요청을 `dismissed`로 닫는다). [개발 요청]은 대화상자에서 `POST /api/admin/dev-requests`(`origin: 'eco'`)를 부르고, 409면 「같은 정책의 요청 N번이 이미 열려 있어요」를 보인다. 세션용 `GET /api/admin/dev-requests` 응답에는 행 `id`가 있고(PATCH용), 읽기 토큰 응답에는 없다.
- **상단 바 숫자를 만들지 않는 이유:** 지금 어드민에는 상단 바 숫자가 없고(`AdminHeader`는 제목과 이메일뿐), 숫자를 달면 모든 어드민 화면이 매번 지표를 읽게 된다. 그래서 이 화면의 요약 줄에 개수를 쓴다.
- **구현됨(구역 이동): 티켓 20261026_2027 3-2.** 운영 홈의 주간 핵심 지표·배지 경제 흐름·통계 구역을 이 화면 아래쪽으로 옮겼다(위 §6 「운영 홈 구역 이동」). 페이지는 `node`와 `trend` 두 쿼리를 읽고, 구역 하나가 실패하면 그 구역만 안내 카드다.

## 8. ③ 개발·배포 상황판

- **배포:** 프로덕션 마지막 배포 시각, staging에서 배포를 기다리는 커밋 수, 상태(배포 가능·동결), 다음 배포 일정.
- **JAM 2.0 묶음:** 상위 티켓 20261016_2335의 묶음 0~7마다 하위 티켓의 끝남·진행 중·남음 막대.
- **개발 항목 보드:** 대기 / 진행 / staging 반영 / 배포됨 네 칸. 카드마다 제목, 티켓 번호, 어디서 왔는지(운영에서·생태계에서·그 밖).
- **데이터(D3):** 서버에서 GitHub API로 저장소 `standardmanual/jam`을 읽는다. 티켓 목록은 파일 수백 개를 하나씩 읽지 않도록 저장소에 티켓 색인 파일을 두고 그 한 파일을 읽는다(색인 생성 방식은 티켓 20261026_2028). 배포 상태는 브랜치 비교와 GitHub 배포 기록에서 읽는다. 토큰은 서버 환경변수에만 둔다.
- **개발 요청:** 생태계·운영 상황판에서 만든 요청은 DB에 쌓이고 보드의 「대기」 칸에 「요청」으로 보인다. 카리나가 세션을 시작할 때 요청을 읽어 티켓으로 바꾼다. 어드민이 티켓 파일을 직접 만들지 않는다.
  - **구현됨(저장·API): 티켓 20261026_2027 1회차.** 테이블 `ops_dev_requests`(요청 번호 `no`, 제목, 내용, 출처 `ops`·`eco`·`other`, 정책 ID, 상태 `requested`·`ticketed`·`dismissed`, 티켓 ID). `GET /api/admin/dev-requests`(관리자 세션 또는 읽기 토큰, `status` 쿼리 기본 `requested`)·`POST`(관리자 세션만)·`PATCH /api/admin/dev-requests/[id]`(관리자 세션만, `requested`↔`dismissed`). 같은 정책(`policy_id`)에 `requested` 요청이 이미 있으면 새 요청을 만들지 않고 409로 기존 번호를 알려 준다(`policy_id`가 없는 요청은 검사하지 않음). `ticketed`와 `ticket_id`는 API가 받지 않고 카리나가 세션 시작 때 SQL로 정한다(절차는 `docs/agents/orchestrator.md` 카리나 카드).
- 티켓에 출처를 적는 선택 필드 `origin`(`ops`·`eco`·`other`)을 더했다(`docs/DOCUMENT_SCHEMA.md` 확장 규칙 1).
- **구현됨(색인): 티켓 20261026_2028 1회차.** 위 보드의 데이터 원천인 티켓 색인 파일과 그 판정 규칙이다. 2회차(GitHub 읽기)는 이 규칙을 따른다.
  - **색인 파일:** `docs/tickets/_index.json`. 생성물이라 손으로 고치지 않는다. 티켓 하나당 한 줄 `{id,title,status,category,priority,parent,origin,created,closed,path}`이고 id 오름차순(같으면 경로순)이다. 제목은 첫 H1 그대로(카테고리 접두 포함)이며 100자로 자른다. `modular/`·`_TEMPLATE.md`·`README.md`·`Archive` 폴더는 넣지 않는다.
  - **갱신 방식:** `scripts/gen-ticket-index.mjs`가 작업 폴더가 아니라 git 인덱스(스테이지된 상태)에서 티켓을 읽는다(병렬 세션의 미스테이지 변경이 섞이지 않게). `.githooks/pre-commit`이 스테이지된 티켓 `.md`가 있으면 색인을 다시 만들어 같은 커밋에 스테이지하고, `scripts/verify.sh`가 `--check`로 최신인지 본다. 병합으로 색인에 충돌이 나면 손으로 풀지 않고 생성기를 다시 돌린다.
  - **보드 칸 판정 규칙:** `OPEN`·`WAITING` = 대기, `IN_PROGRESS` = 진행. 색인을 `staging`과 `main` 두 브랜치에서 읽어 티켓마다 견준다. staging 색인에서 `CLOSED`이고 main 색인에서 `CLOSED`가 아니거나 없으면 「staging 반영」, main 색인에서도 `CLOSED`이면 「배포됨」이다(티켓 커밋이 main에 있는지와 같은 뜻이라 커밋 메시지에 티켓 번호가 있어야 한다는 전제가 필요 없다). 「배포됨」은 최근 14일(`closed` 기준)만 보인다.
  - **`origin`:** 색인의 `origin`은 티켓 frontmatter에 있을 때만 채우고(`ops`·`eco`·`other` 밖이면 빈 문자열), 보드 카드의 출처 표시는 `origin`이 있을 때만 쓴다. 기존 티켓은 소급하지 않는다. 개발 요청 행은 요청 행의 `origin`을 쓴다.
- **구현됨(읽기·계산): 티켓 20261026_2028 2회차.** 화면 없이 `jam-web/src/lib/admin/devBoard/`가 GitHub를 읽어 배포 현황·묶음 진행·보드 네 칸을 계산한다(`loadDevBoard`가 항상 스냅샷을 돌려준다). 화면은 3회차다.
  - **읽는 것:** staging·main 브랜치의 색인, 배포 상태 파일 `docs/operations/deploy-state.json`(`frozen`·`reason`·`nextDeploy`, 동결 결정과 다음 배포 일정의 단일 원천), `compare/main...staging`의 `ahead_by`(커밋 목록은 250개에서 잘려 개수만 쓴다), 환경 `Production – jam`(가운뎃줄은 엔대시)의 마지막 배포. 배포 기록이 없으면 main 마지막 커밋 시각으로 대신하고 추정으로 표시한다. 읽기는 모듈 안에서 60초 기억하고 동시 요청은 합친다.
  - **추정 규칙(main에 색인이 없을 때):** 지금 `main`에는 색인이 없다(main 배포 정지). 이때 `CLOSED`이고 `closed` 날짜(KST)가 프로덕션 마지막 배포의 KST 날짜 이하이면 「배포됨(추정)」, 그 뒤면 「staging 반영」이다. 마지막 배포 날짜도 모르면 모두 「staging 반영」이다. main에 색인이 생기면 위의 정확한 규칙이 자동으로 적용된다.
  - **상태 글자:** 동결이면 「동결」, 동결이 아니고 앞선 커밋이 있으면 「배포 가능」, 없으면 「배포할 것 없음」, 상태 파일을 못 읽으면 「확인 안 됨」.
  - **묶음:** 묶음 티켓의 자손 전체에서 끝남(`CLOSED`)·진행(`IN_PROGRESS`)·남음(그 밖)을 센다. 묶음 티켓 자신은 세지 않는다.
  - **보드:** 카드는 우선순위(P0→P3), 같으면 최근 id 순이고 칸마다 30장까지 담으며 전체 개수를 따로 준다. 개발 요청은 「대기」 칸 맨 앞에 요청 카드로 합친다.
  - **부분 실패:** 읽기 하나가 실패하면 그 부분만 `error`(한도 초과는 `rate_limited`)로 두고 나머지는 계산한다.
  - **환경변수(선택):** `GITHUB_READ_TOKEN`(읽기 전용 토큰). 없으면 토큰 없이 읽고 시간당 60번 한도라서 자주 열면 한도 초과가 날 수 있다. 값은 사용자가 Vercel에 넣는다.

## 9. 확인 방법

JAM 2.0 출시 전까지 main 배포가 멈춰 있고, 배포된 staging에서는 어드민을 확인할 수 없다. 그래서 하위 티켓은 메인 작업 트리의 로컬 `next dev`에서 실제 화면을 열어 확인한다. 프로덕션 어드민에는 출시 배포 때 함께 나간다.

## 10. 하지 않을 것

- 안쪽 상태 10개와 상태 맞추기 규칙을 바꾸지 않는다(화면에서만 묶는다).
- 에이전트가 단계마다 실시간으로 보고하게 하지 않는다(D2).
- 어드민에서 티켓 파일을 만들거나 고치지 않는다.
- 밸런스 수치를 상황판에서 바로 바꾸지 않는다(설정 화면으로 보낸다).
