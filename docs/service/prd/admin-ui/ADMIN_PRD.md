# JAM! 어드민 — PRD (Product Requirements Document)

> 생성일: 2026-07-09

---

## 1. 제품 개요

### 한 줄 요약
배지·POI·아이템북을 등록·관리하고, 가상 액티비티로 배지 발급과 장소 매칭을 시뮬레이션할 수 있는 내부 관리 도구. (옛 «아이템 드랍» 시뮬레이션은 2026-10-22 티켓 20261022_0938에서 지웠다.)

### 해결하는 문제
현재 배지/POI/아이템북은 Supabase 대시보드에서 SQL로 직접 INSERT해야 한다. 배지 발급 조건(condition_json)을 바꿀 때마다 실제 Strava 활동이 있어야만 테스트가 가능하다.  
→ **어드민 UI + 시뮬레이터**로 비개발자도 컨텐츠를 관리하고, 가상 데이터로 즉시 검증할 수 있게 한다.

## 5. 기능 상세

### 5-1. 어드민 인증

- 기존 Supabase Auth + Google OAuth 재사용
- 미들웨어에서 `/admin/*` 경로를 보호
- 환경변수 `ADMIN_EMAILS`(쉼표 구분 이메일 목록)에 등록된 계정만 접근 허용
- 미허용 계정은 403 페이지로 리다이렉트

### 5-2. 배지 CRUD

**목록 화면**
- 배지 이름, 타입(activity/item), 희귀도, 발급 조건 여부, 패치 가능 여부 표시
- 타입·희귀도 필터, 이름 검색

**등록·수정 폼 필드**

| 필드 | 입력 방식 | 필수 |
|------|----------|------|
| name | 텍스트 | O |
| description | 텍스트 에어리어 | O |
| type | 드롭다운 (activity / item) | O |
| rarity | 드롭다운 (common / rare / epic / mystic) | O |
| image_url | 파일 업로드 (Supabase Storage 저장, URL 직접 입력 불가) | O |
| activity_types | 복수 체크박스 (cycling / running / hiking / walking) | O |
| patch_available | 토글 | O |
| patch_price_krw | 숫자 입력 (patch_available=true 시 활성) | X |
| condition_json | **조건 빌더** (아래 별도 설명) | X (item 타입은 불필요) |
| always_locked | 체크박스 «잠긴 채로 받아요» (**item 타입에만 표시**) | X |
| unlock_required | 숫자 입력, 단위 «잼» (**item 타입에만 표시**) | X (비우면 등급 최소값) |
| is_hidden | 스위치 «숨김 배지로 만들어요» (**activity 타입에만 표시**) | X (기본 꺼짐) |
| branch_key | 드롭다운 «가지» — 분류 없음 / 리듬 / 회복 / 시간과 계절 / 탐험 / 운동 속성 / 이정표 / JAM 활동 (**activity 타입에만 표시**) | X (비우면 분류 없음) |

**잠금 칸(아이템 배지, 티켓 20261018_0051 2회, 운영 로직 7.4절)**
- «잠긴 채로 받아요»를 켜면 이 배지로 받은 개체는 늘 잠긴 채다. 끄면 동기화·캡슐이 설정 확률(`jam_policy.locked_roll_probability`)로 잠글 수 있다.
- «여는 데 필요한 양»을 비우면 저장은 null이고 발급 때 그 등급의 최소값(`jam_policy.locked_min_*`, 기본 Common 30·Rare 60·Epic 120·Mystic 240)을 쓴다. 값이 있으면 1 이상의 정수여야 하고
  **등급 최소값보다 적으면 저장 API가 400으로 거부한다**(양식도 같은 함수·문구로 저장 전에 막는다, `lib/admin/badge-lock-guard.ts`). 수정 때는 병합한 값(등급 변경 포함)으로 다시 판정한다.
- item 타입이 아니면 입력을 보이지 않고, 요청에 값이 실려 와도 저장하지 않는다(`always_locked` false, `unlock_required` null). 개체에 고정된 필요한 양은 나중에 바꿔도 이미 받은 개체에 영향이 없다.
- 아이템 배지 현황의 배지별 개체 목록(`/admin/item-badges/[badgeId]`)에 «잠김» 열이 있어 개체의 상태(잠김 채운 양/필요한 양잼, 열림, 연 개체)를 읽기로 보여 준다.

**숨김 배지·가지(티켓 20261018_1816 1회, 운영 로직 10.2·10.3절, 마이그레이션 243)**
- 숨김을 켜면 종류는 액티비티만, 포인트는 0, 등급은 Common만(레벨형은 등급 없음)이다. 양식은 켜는 순간 등급을 Common·포인트를 0으로 맞추고 포인트 입력을 잠그며, 등급 선택지를 Common 하나로 줄인다. 타입을 액티비티 밖으로 바꾸면 숨김과 가지를 비운다.
- 가지는 일곱 값(`rhythm`·`recovery`·`time_season`·`explore`·`attribute`·`milestone`·`jam_activity`) 중 하나 또는 비움이다. 목록 밖의 값은 거부한다.
- 저장 API(`POST·PUT /api/admin/badges`)가 DB 제약과 같은 규칙으로 먼저 400을 돌려준다. 양식도 같은 함수(`lib/admin/badge-hidden-guard.ts`)로 저장 전에 막는다. 수정(PUT)은 부분 본문이면 기존 값을 유지하고, 병합한 값으로 판정한다.
- 목록(카드·표)은 숨김 배지에 «숨김» 표시를 붙이고, 상세는 «가지»와 «숨김» 칸을 읽기로 보여 준다.
- 양식에 «기한» 칸은 없다. 기간 입력은 아래 유효기간(공개 기간)뿐이다.
- **숨김 배지 사용 제한(티켓 20261019_1313 2회, 티켓 20261019_0012)**: 숨김 배지는 미션 보상·게이트 미션의 본 배지·다른 배지의 선행 배지·교차 게이트로 쓸 수 없다. 서버가 저장에서 막는다 — 미션 저장(`POST·PATCH /api/admin/missions`)은 보상 배지의 존재(삭제 제외)·유형(액티비티·아이템만)·숨김·중복을, 배지 저장(`POST·PUT /api/admin/badges`)은 선행 배지 이름의 존재와 숨김, 교차 게이트 계열의 숨김 배지를 본다. 이미 쓰이는 배지를 숨김으로 바꾸는 저장은 사용처(미션·배지 이름)를 알리며 거절한다. 미션 양식의 보상 배지·게이트 배지와 게이트 미션 양식의 보상 배지 검색은 `excludeHidden=1`로 숨김 배지를 결과에서 뺀다. 오류 문구는 현상·원인·해결책 순서다.

**유효기간(valid_from·valid_until)**
- 기간은 KST 날짜·시각(`datetime-local`)으로 입력하고, 바꾸지 않은 칸은 원래 값을 그대로 저장한다
  (`resolvePeriodInputIso`, `jam-web/src/lib/admin/kst-format.ts`, 티켓 20261004_2043).

**condition_json 조건 빌더**
- **입력 UI를 제공하는 필드 목록은 여기에 나열하지 않는다** — `jam-web/src/lib/badge-engine/conditionRegistry.ts`의
  `form` 선언에서 파생된다(티켓 20260905_0028). 필드를 늘릴 때 이 문서가 낡지 않게 하기 위함이다.
  (그전까지 이 자리에 5개만 적혀 있었는데 실제로는 19개를 커버하고 있었다)
- 폼이 커버하지 않는 필드가 조건에 들어 있어도 **원본 값이 그대로 보존된다** — 폼이 모르는 키를 지우지 않는다
- 설정된 조건 JSON 미리보기 패널 표시
- ⚠️ 조건에 «아직 아무도 평가하지 않는 필드»(`evaluation: 'pending'`)가 있으면 배지가 발급되지 않는다.
  v5 신규 20종이 여기 해당하며 평가 구현은 티켓 20260905_0030이다

### 5-3. 장소(POI) 관리

> 화면 표기는 «장소»다(옛 «지점»·«POI»에서 바꿨다, 티켓 20261018_1813). 코드·DB 식별자 `poi`는 그대로다.

**목록 화면**
- POI 이름, 카테고리, 위도/경도, 반경(m), 연결 배지 이름 표시

**등록·수정 폼 필드**

| 필드 | 입력 방식 | 필수 |
|------|----------|------|
| name | 텍스트 | O |
| latitude | 소수 입력 | O |
| longitude | 소수 입력 | O |
| radius_meters | 숫자 입력 (기본값 50) | O |
| category | 드롭다운 (mountain / bike_route / trail / park / other) | O |
| linked_badge_id | 체크인 배지만 검색·선택하는 드롭다운(`typeFilter="checkin"`) | X |

**연결 배지 규칙(티켓 20261018_1813)**
- 장소에는 체크인 배지(`badges.type = 'checkin'`)만 연결한다. 폼의 배지 검색이 체크인 배지만 보여 주고, 저장 API(`POST /api/admin/poi`·`PUT /api/admin/poi/[id]`)가 체크인이 아니거나 없는·삭제된 배지를 400으로 거절한다(`lib/admin/poi-linked-badge-validation.ts`).
- 수정 저장에서 이 장소가 지금 이미 연결된 배지를 그대로 두면 종류를 다시 검사하지 않는다. 예전에 체크인이 아닌 배지가 연결된 장소의 다른 항목을 고치는 저장이 막히지 않게 하려는 것이다.
- 배지 쪽에서 장소를 묶는 `PUT /api/admin/badges/[id]/poi-links`는 체크인 배지 폼에서만 호출하며, 이 검증을 거치지 않는다.
- 배지 수정 폼은 연결된 장소를 불러오는 데 성공한 뒤에만 저장한다. 불러오는 중이거나 실패했으면 배지 본문도 저장하지 않고 안내를 보여 준다. 빈 목록이 `poi-links`로 전송되어 기존 연결이 지워지는 사고(티켓 20261006_1028)를 막는다(`lib/admin/badge-poi-links-guard.ts`).

### 5-4. 아이템북 관리

**등록·수정 폼 필드**

| 필드 | 입력 방식 | 필수 |
|------|----------|------|
| name | 텍스트 | O |
| description | 텍스트 에어리어 | O |
| required_activity_badge_id | 배지 검색·선택 (type=activity만 표시) | O |
| required_item_badge_ids | 배지 다중 검색·선택 (type=item만 표시) | O |
| reward_badge_id | 배지 검색·선택 (완성 시 발급 배지) | X |
| valid_from · valid_until | KST 날짜·시각(`datetime-local`) — 바꾸지 않은 칸은 원래 값을 그대로 저장 | X |

**4등급 방식 (JAM 2.0, 티켓 20261022_1139)** — 수정 화면(`/admin/itembooks/[id]`)에서 편집 폼 위에 두 구역이 붙는다.

- **«4등급 방식» 패널**: 켜짐·꺼짐 표시, 켜기 전 점검 세 가지(장착한 등급 분포·이름 점검·등급별 완성 기록), [4등급 방식 켜기]·[4등급 방식 끄기]와 확인창. 켜기는 여러 등급을 장착한 유저가 있으면 막고(유저 수와 등급 조합만 보인다), 이름 점검은 경고로만 보인다. 끄기는 등급별 완성 기록이 있으면 막는다. 변경 이력은 남기지 않는다. 읽기·쓰기는 `GET`·`PUT /api/admin/itembooks/[id]/tier`이고 `PUT /api/admin/itembooks/[id]`는 `tier_mode`를 쓰지 않는다. 점검 규칙은 `docs/service/content/ITEMBOOK_TIERS.md` 2절이다.
- **«등급별 보상» 편집기**: 4등급 방식이 켜진 컬렉션에만 패널 아래에 나온다. Common·Rare·Epic·Mystic 네 행에 포인트(비우면 기본값, 칸 안내에 기본값 표시, 0이면 지급 없음)와 보상 배지(`BadgeSearchSelect`, 비우면 없음)를 입력하고 [등급별 보상 저장]으로 한 번에 저장한다. 포인트가 0 이상의 정수가 아니거나 같은 배지를 두 등급에 고르면 안내를 보이고 저장을 막는다. 이미 받은 보상은 바뀌지 않는다. 읽기·쓰기는 `GET`·`PUT /api/admin/itembooks/[id]/tier-rewards`(꺼진 컬렉션은 409, 없거나 소프트 삭제된 배지는 400)다. 입력 규칙은 `ITEMBOOK_TIERS.md` 3절이다.
- **옛 보상 칸**: 4등급 방식이 켜진 컬렉션은 편집 폼의 «완성 보상 배지»·«포인트 보상» 칸을 접는다. 저장해 둔 값은 지우지 않는다.

### 5-5. 시뮬레이터

**목표**: 실제 Strava 계정 없이 가상 GPX 파일을 업로드해 배지 발급 파이프라인 전체를 테스트.

**GPX 파일 선택 이유**
- GPX 한 파일에 경로 좌표(트랙포인트)·타임스탬프·고도가 모두 포함됨
- 업로드 즉시 거리·이동시간·고도상승·평균속도·경로 좌표를 자동 파싱 → 수작업 입력 불필요
- POI 반경 매칭 테스트에 실제 경로 데이터 활용 가능
- 실제 Strava에서 내보낸 GPX 파일로 현실적인 시뮬레이션 가능

**입력 패널**

| 필드 | 설명 | 비고 |
|------|------|------|
| 대상 유저 | 유저 이메일/이름 검색·선택 | 필수 |
| GPX 파일 업로드 | `.gpx` 파일 드래그앤드롭 또는 파일 선택 | 필수 |
| 활동 종류 | cycling / running / hiking / walking | GPX에 없으므로 직접 선택 |
| 활동 횟수 배수 | 이 활동을 N회 반복 처리 (누적 횟수 배지 테스트용) | 기본값 1 |

**GPX 파싱 결과 미리보기** (업로드 직후 자동 표시)

**시뮬레이터 구현 원칙**
- GPX 파싱은 클라이언트 사이드에서 수행 (파일을 서버에 업로드하지 않음)
- 파싱 결과(`NormalizedActivity` + 경로 좌표 배열)를 JSON으로 API에 전송
- Dry Run: 배지 판정(`evaluateBadgesDetailed`)과 장소 매칭을 그대로 실행하되 INSERT를 skip하고 결과만 반환. 아이템 드랍은 시뮬레이션하지 않는다(옛 `tryItemDrop` 미리 보기는 티켓 20261022_0938에서 지웠다). 컬렉션 완성은 유저가 직접 슬롯을 채우는 방식이라 항상 빈 결과다
- Apply: 동일 로직을 실제 DB에 반영
- 미발급 배지도 조건별 미충족 이유(실제값 vs 필요값) 함께 표시

**GPX 파싱 스펙**
- 표준 GPX 1.1 형식 파싱 (`<trkpt lat="..." lon="..."><ele>...</ele><time>...</time></trkpt>`)
- 거리: 연속 트랙포인트 간 하버사인(Haversine) 공식으로 누적 계산
- 이동 시간: 첫 트랙포인트 ~ 마지막 트랙포인트 timestamp 차이
- 고도 상승: 연속 포인트 간 양(+)의 고도 차이 누적 합산
- 평균 속도: 거리 / 이동 시간
- 경로 좌표: 트랙포인트 `[lat, lng]` 배열 그대로 POI 매칭에 전달

### 5-6. 유저 조회 (P1)

- 유저 목록: 이름·이메일·트라이브, 어드민 여부, 제재 상태(이용 정지 중이면 «이용 정지»와 건 날짜), 보유 배지·아이템 수, 가입일.
  이름·이메일로 검색하고 트라이브·온보딩·제재 상태로 거른다. 가입 최신순·오래된순·이름순 정렬,
  한 쪽 50건의 서버 페이지 이동. 행을 누르면 같은 탭에서 유저 상세로 이동한다
  (조회·집계 `lib/admin/user-list.ts`). 제재 상태와 «제재 중» 필터는 `user_suspensions`의 진행 중 정지(`lifted_at` 없음)를 기준으로 한다(티켓 20261017_1426, 옛 섀도우밴 표는 읽지 않는다).
- 이용 정지 탭(`/admin/abusing?tab=suspensions`, 티켓 20261017_1426): 유저 UUID와 사유(필수, «유저에게 그대로 보여요» 안내)로 정지를 걸고, 이력 표(유저·사유·건 시각과 운영자·해제 기록)에서 진행 중인 줄만 «풀기»(확인창, 해제 메모 선택)로 푼다. 정지 중·풀림·전체로 거르고 이름·이메일로 검색한다. 일괄 처리는 없다. 정지를 걸거나 풀면 그 유저에게 소식 한 건이 간다(`suspension_started`·`suspension_lifted`, `lib/suspension/notify.ts`). 사유 글·어드민 이메일·해제 메모는 소식에 싣지 않고, 소식이 실패해도 정지·해제 결과는 그대로다(티켓 20261021_1249 5회). API는 `/api/admin/suspensions`(GET·POST)와 `/api/admin/suspensions/[id]`(PATCH)이며 어드민만 부를 수 있다. 옛 섀도우밴 관리 API(`/api/admin/abusing/bans`)는 6-4 2회(티켓 20261021_1250)에서 지웠다. 같은 화면의 «정책 설정» 탭에서는 6-4 2회에 «투트랙 정책» 안내, Soft-ban·Hard-ban 드랍 배율 입력 8칸, DB 배율과 코드 기본값의 불일치 경고를 지웠고(머리말은 «장소 GPS 조작 감지 + 이용 정지»), 7-3 2회(티켓 20261022_1134)에서 남은 기준값 열 칸(GPS 임계값·차량 속도 필터·교통수단·종목 불일치·장소 블록 시간)을 밸런스 설정 «어뷰징» 구역(§5-9)으로 옮기며 탭 자체와 저장 API(`PUT /api/admin/abusing/policy`)를 없앴다. 이 화면의 탭은 «이용 정지»(기본)와 «장소 블록» 둘이고, 옛 «정책 설정» 주소(`?tab=policy`)와 옛 섀도우밴 주소(`?tab=bans`)는 이용 정지 탭으로 열린다(`parseAbusingPageTab`). `abusing_policy`의 배율 열 8개는 코드가 쓰지 않음, 열 정리 대기(6-4 4회).
- GPS 조작 의심 알림과 «장소 블록» 탭 확인 흐름(티켓 20261022_0940, 운영 로직 16.5절): 유저가 픽업할 때 GPS 조작이 감지되면 앱이 응답 뒤에 `#jam-alert`에 글 한 건을 올린다
  (`lib/abusing/gpsSpoofAlert.ts`). 글에는 유저 ID, 장소 이름, 사유(속도 또는 하루 이동거리), 장소를 막은 시간을 적고 좌표와 이메일은 적지 않는다.
  운영자는 `/admin/abusing`의 «장소 블록» 탭(`PoiBlockTable.tsx`)에서 그 유저와 장소의 차단과 사유(`gps_spoof_detected (속도 N km/h)`), 차단 만료를 확인한 뒤
  이용 정지 탭에서 정지를 정한다. 정지는 자동으로 걸리지 않는다. `abusing_logs`를 읽는 어드민 기록 화면은 아직 없어 알림이 장소 블록 탭을 가리킨다.
  장소 차단이나 기록 저장이 실패해도 알림은 보내며, 그때 글이 저장 실패를 알린다.
- 유저 일괄 처리: 페이지를 넘겨 선택하고 「이 조건의 N명 모두 선택」으로 필터 결과 전체(상한 1,000명)를
  고른다. 대표 버튼은 내보내기(CSV), 「더보기」에 포인트 지급·회수·초기화·삭제를 둔다. 셋 다
  되돌릴 수 없어 미리보기가 영향 수치와 확인 문구를 보여 주고, 확인 문구를 입력해야 실행된다.
  **어드민 계정과 실행자 본인은 대상에서 자동으로 빠지며** 빠진 수를 확인창에 보여 주고 유저별
  결과를 돌려준다. 초기화·삭제는 한 번에 50명, 포인트는 유저마다 단건 지급과 같은 검증을 적용한다
  (`POST /api/admin/users/bulk`, 규칙 `lib/admin/user-bulk.ts`).
- 유저 상세: 보유 배지 목록(50건씩 번호 페이지 이동), 인벤토리 아이템, Strava 연동 상태, 포인트
  지급·회수, 어드민 권한, 계정 작업(초기화·완전 삭제). 어드민 계정과 본인 계정은 초기화할 수 없다
  (단건 API도 403). 완전 삭제는 유저 탈퇴와 같은 지우기 규칙(`deleteAccount`)을 쓴다 — 아바타 파일 삭제, 법정 보관 기록 복사, 이력 이름 비우기, 소유 아이템 «없어짐» 처리 뒤 계정 삭제, 성공하면 Strava 앱 승인 해제(실패해도 무시).
  실패하면 오류 원문 없이 고정 문구만 보인다. 규칙은 [데이터 모델](../02_DATA_MODEL.md)의 «계정 삭제» 절, 티켓 20261021_1249. 트라이브 구역(지금 트라이브·변경 양식·최근 변경 이력)은 계정 작업 뒤, 챕터 구역 바로 앞에 있다(티켓 20261021_1247 3회, 아래 «트라이브 변경»). 챕터 구역(지금 챕터·누적 점수·오른 기록·점수 기록 최근 50건)이 배지 히스토리 앞에 있다
  (티켓 20261019_1318 2회, 규칙은 [챕터 PRD](../chapter/PRD.md) 9.2절).
- 트라이브 변경(티켓 20261021_1247 2회 DB·API, 3회 유저 상세 화면): 어드민이 트라이브를 고른 유저의 트라이브를 바꾼다.
  `POST /api/admin/users/[id]/tribe`(본문 `{ newTribeId, reasonCode, memo? }`)가 DB 함수 `admin_change_user_tribe`(마이그레이션 259) 하나로 트라이브 갱신·참가 취소·변경 기록을 한 트랜잭션으로 처리하고,
  성공하면 유저에게 «트라이브가 바뀌었어요» 소식을 보낸다(취소된 미션이 있으면 참가 취소 소식이 한 건 더). 사유는 고정 목록(`lib/admin/user-tribe.ts`의 `TRIBE_CHANGE_REASONS`:
  유저가 잘못 골랐어요·유저가 옮기길 원해요·운영 정정·기타)에서 고르고 «기타»는 메모가 필수이며 메모는 200자까지다. 응답은 어드민이 아니면 403, 본문 검증 실패 400(고정 문구), 없는 유저 404,
  트라이브 없는 유저(`no_tribe`)·고를 수 없는 트라이브(`invalid_tribe`)·같은 트라이브(`same_tribe`)는 409로 서로 구분하고, 서버 오류는 DB 오류 원문 없이 고정 문구 500이다.
  `GET /api/admin/users/[id]/tribe`는 최근 변경 이력(최대 10건, 최신순 — 트라이브 이름·사유 라벨·바꾼 어드민 이메일·취소된 미션 수)과, `?newTribeId=`가 있으면 그 트라이브로 바꿨을 때 참가가 취소될
  미션 미리 보기를 돌려준다(읽기만, 읽지 못하면 빈 목록이 아니라 500). 트라이브 삭제(어드민 트라이브 화면)는 변경 이력(`user_tribe_changes`)이 있는 트라이브를 막고, 목록의 «삭제 불가 사유»에도 «트라이브 변경 이력 N건»으로 나온다.
  데이터 구조는 [02_DATA_MODEL.md](../02_DATA_MODEL.md) §8 «user_tribe_changes / admin_change_user_tribe …»다.
  유저 상세의 «트라이브» 구역(3회, `app/admin/users/[id]/UserTribeSection.tsx`, 읽기 `lib/admin/user-tribe-view.ts`)은 챕터 구역과 같은 방식으로 값을 읽는다(구역마다 읽기 성공·실패를 따로 알리고 화면 전체를 막지 않는다).
  ① 지금 트라이브의 이름. 트라이브를 아직 고르지 않은 유저는 «트라이브를 아직 고르지 않았어요. 유저가 직접 골라요.» 한 줄만 보이고 변경 양식과 버튼이 없다(트라이브가 없는 유저는 고르기 화면에서 스스로 고른다).
  ② 변경 양식(`UserTribeChangeForm.tsx`): 활성이고 지금 것이 아닌 트라이브를 고르는 선택 상자, 사유 고정 목록(`TRIBE_CHANGE_REASONS`), 메모(«기타»는 필수, 나머지는 선택, 200자). 새 트라이브를 고르면 `GET …/tribe?newTribeId=`로
  «취소되는 미션 N개»와 미션 이름 목록(없으면 «취소되는 미션이 없어요»)을 보인다. 미리 보기를 읽지 못하면 «다시 불러오기»만 열리고 확정은 막힌다(영향을 모른 채 바꾸지 않는다).
  ③ 확인창(`AlertDialog`) «트라이브를 바꿀까요?»: 옛 → 새 트라이브, 이미 가진 배지·잼·챕터는 그대로, 취소되는 미션 수, 바꾼 뒤 유저에게 알림이 감, 되돌릴 때는 다시 바꾸면 된다는 점을 알리고 `POST`로 확정한다.
  성공이면 성공 문구와 함께 양식을 비우고 구역을 새로 읽는다. 실패(409 `no_tribe`·`invalid_tribe`·`same_tribe`, 400·404·500, 네트워크 오류)는 확인창을 닫고 API의 `error` 문구를 그대로 보이며 입력을 유지한다(403의 영어 «Forbidden»은 한국어 안내로 바꿔 보인다).
  진행 중에는 입력과 버튼을 잠그고 중복 제출을 막는다.
  ④ 최근 변경 이력(최대 10건, KST): 바꾼 시각, 옛 → 새 트라이브, 사유 이름(목록에 없는 옛 코드는 코드 그대로), 메모, 처리자(어드민 이메일, 읽을 수 없으면 «알 수 없음»), 취소된 미션 수.
  이력이 없으면 «아직 바꾼 적이 없어요», 읽지 못하면 «변경 이력을 불러오지 못했어요…»로 서로 다르게 보인다.
- 아이템 배지 이력 상세(`/admin/item-badges/[badgeId]/[itemId]`)의 타임라인(티켓 20261021_1249 2회, 운영 로직 17.2절): From·To·실행자 칸에서 계정이 지워진 유저는 이름 대신 `₩*&%#@`로 보인다. 이벤트 종류별 필수 칸의 `*_user_id`가 NULL이면 탈퇴로 보고(표는
  [데이터 모델](../02_DATA_MODEL.md)의 «탈퇴 유저 표시»), `*_user_id`가 NULL인 칸에 남은 옛 이름 문자열은 쓰지 않는다. 살아 있는 유저는 유저 상세 링크이고, 탈퇴 텍스트는 링크가 아니며 `title`과 `aria-label`에만 «₩*&%#@님은 탈퇴한 사용자입니다»가 붙는다.
  시스템 드랍을 줍는 `Pickup`의 `from`은 원래 비어 있으므로 그리지 않는다(페이지가 같은 개체의 `poi_drops` 중 줍힌 시각이 이벤트 시각과 같은 행의 `source`로 가른다. 짝이 없으면 그리지 않는다).
  처음 티켓(20260829_2139)의 «탈퇴한 유저도 익명화하지 않는다» 결정은 이 규칙으로 바뀌었다.
- 챕터 이름 표(`/admin/chapter-names`)는 없다. 챕터는 트라이브와 상관없이 숫자로만 표기한다(2026-10-21 결정, 티켓 20261021_1539, [챕터 PRD](../chapter/PRD.md) 6절).

### 5-7. 운영 홈 (`/admin`)

운영자가 어드민에 들어오자마자 이번 주 라이브 운영의 진행과 신호, 서비스 점검, 자동화 일정을 한 화면에서 확인하는 곳이다. 사이드바 맨 위 항목·상단 바·화면 제목이 모두 「운영 홈」이다
(라벨의 원천은 `components/admin/adminNavItems.ts`의 `DASHBOARD_ITEM` 한 곳). 이번 주 상태·신호·최근 이력의 계산 규칙과 화면 구성표는 `docs/service/prd/ops-tool/PRD.md` §6.3이 정본이고 여기에는 옮겨 적지 않는다.

**현재 동작**
- **머리·시험 묶음 스위치**: 제목 「운영 홈」, 부제 「이번 주 라이브 운영의 진행과 신호를 한눈에 봐요」, 오른쪽에 스위치 「시험 묶음 포함해서 보기」(`OpsSampleSwitch`)가 있다.
  값은 URL `?sample=1`뿐이다(꺼짐이면 키가 없고 localStorage를 쓰지 않는다). 켜면 이번 주 상태·신호·최근 이력에 시험 묶음이 더해지고 그 화면의 링크와 배지 경제 흐름의 기간 전환
  링크에 `sample=1`이 이어 붙는다. 서비스 점검·주간 핵심 지표·통계는 시험 묶음과 무관하다.
- **구역과 순서**: 이번 주 상태 → 신호 → 서비스 점검 → 최근 이력 → 주간 핵심 지표 → 배지 경제 흐름 → 통계 → 빠른 실행. 페이지는 쿼리(`sample`·`trend`)만 읽고(옛 `?week=`는 읽지 않고 무시한다 — 주간 캘린더는 일정표 §5-8로 옮겼다)
  구역마다 `Suspense`와 스켈레톤(`role="status"`, `aria-label="불러오는 중"`)으로 따로 읽어, 느린 구역이 다른 구역을 막지 않는다(`loading.tsx`가 없고 `unstable_cache`·`revalidate`를 쓰지 않는다).
  구역의 조립은 `app/admin/_home/sections.tsx`다.
- **구역별 오류**: 구역이 읽는 것을 모두 못 읽으면 그 구역만 안내 카드(「…를 불러오지 못했어요」와 [새로 고치기], `OpsSectionNotice`)가 되고 나머지 구역은 그대로다. 구역 안의 출처가
  여럿이면 일부만 못 읽은 것은 그 칸·그래프의 오류 표시만 남는다(서비스 점검의 칸, 지난주 지표의 「비교 불가」, 경제 추이의 그래프, 통계의 칸). 실패를 0이나 빈 상태로
  보이지 않는다.
- **이번 주 상태**: 이번 주(월~일, KST)에 기간이 걸치는 항목을 다섯 칸(승인 대기 › 예약 등록 대기 › 예약됨 › 게재중 | 실패)으로 센다. 이번 주와 다음 주 14일치를 한 번에 읽고(`loadDayCompositions`),
  재료(카드·미션·묶음) 하나라도 못 읽으면 구역이 안내 카드다. 칸은 링크가 아니다. 승인 대기가 있으면 [받은 기획함에서 결정하기](`/admin/ops-inbox?tab=decide`), 이번 주 기획이 0이면
  「이번 주에 올라온 기획이 없어요」와 [받은 기획함 보기]다. 머리 오른쪽에는 [일정표 보기 →](`/admin/ops-schedule`, 시험 묶음을 켜고 있으면 `sample=1`을 이어 붙인다)가 늘 있다. 다음 주 줄은 S7의 기준 요일(`nextWeekCheckFromWeekday`, 기본 금요일)부터 또는 다음 주 기획이 이미 도착했을 때 보인다.
- **신호**: 신호 13종(`docs/service/prd/ops-tool/PRD.md` §5)을 뜬 신호·이상 없는 신호·아직 확인하지 않은 신호 가운데 한 구역에만 둔다(`OpsSignalPanel`). 재료 하나를 못 읽은 신호는 그 신호만
  「확인하지 못했어요」다. 구역 전체가 던지면 안내 카드다.
- **서비스 점검**: Strava 동기화 실패 건수·유효 제재 수·차단 POI 수·미션 공백을 한 줄 4칸(1024px 이상 4열, 좁으면 2열)으로 둔다(`ServiceCheckRow`, `DashboardSignals.tsx`).
  앞의 세 칸은 각각 `/admin/strava-backfill`·`/admin/abusing`·`/admin/abusing`로 이동하는 링크를 붙이고, 미션 공백은 `/admin/missions`로 간다. 조회에 실패한 카드도 링크는 유지한다.
  Strava 칸의 동기화 실패 건수에는 `failure_type = 'drop_attempt_failed'`(드랍 시도 실패) 행을 세지 않는다. 그 건수는 `/api/admin/kpi/weekly` 응답의 `dropAttemptFailures`(`{ value, definition }`)로 따로
  반환하며, 이 화면은 그 값을 쓰지 않는다.
  유효 제재 수는 진행 중인 이용 정지(`user_suspensions.lifted_at` 없음)를 센다(티켓 20261017_1426, 옛 섀도우밴 표는 읽지 않는다). 차단 POI 수는 차단 기간(`blocked_until`)이 끝나지 않은
  POI만 센다. 값이 0보다 크거나 지난주보다 늘었으면 강조색으로 표시하고, 빨간 카드의 글자색은 `text-red-700`이다. 네 출처(이번 주 집계·유효 제재 수·차단 POI 수·미션 공백)는 서로 독립적으로
  조회해 하나가 실패하면 그 칸만 오류 카드이고, 제재·차단 POI·미션 공백을 모두 못 읽으면 줄이 안내 카드다.
  - **미션 공백**: 「미션 공백」 칸은 정상이면 회색 "공백 없음", 문제가 있으면 빨간 카드에 내용을 쓰고 누르면 `/admin/missions`로 이동한다(`ContentGapCards.tsx`의 `MissionGapCard`, 판정은
    `lib/admin/contentGaps.ts`). 조회는 "지금" 기준이며 조회만 하고 DB를 바꾸지 않는다(2026-09-24 사용자 결정). 공개 미션(게이트 축·노출 조건이 없는 미션)의 정의와
    공백 금지·상시 입문 미션·시즌 공개 미션 규칙의 원천은 `docs/service/SERVICE_OPERATIONS.md` §9-5이며 여기에 옮겨 적지 않는다. 화면은 다음을 검사한다. (a) 이미 시작한 상시 공개 미션이 0건,
    (b) 오늘부터 60일(`MISSION_GAP_HORIZON_DAYS`) 중 공개 미션이 없는 날, (c) 종료일이 오늘+14일(`MISSION_ENDING_NOTICE_DAYS`)까지인 기간 공개 미션에 이어지는 기간 공개 미션이 없음(종료일이
    오늘+14일이면 검사하고 오늘+15일이면 제외). 시즌 캘린더가 데이터로 없어 시즌 규칙은 (c)로 근사하며, 상시 미션은 후속으로 인정하지 않는다. 날짜 비교는 KST 달력 날짜 기준이다.
  - **카드 편성 공백**: 카드는 없다. 카드 편성의 이상은 운영 신호(「비어 있는 컨텐츠」·「새 컨텐츠가 없는 날」 등, `docs/service/prd/ops-tool/PRD.md` §5)가 맡는다. 판정 함수(`checkCardGaps`)는 남아 있으나 이 화면은 쓰지 않는다.
- **최근 이력**: 결정 기록(`ops_decisions`)의 최신 10건을 한 줄씩 둔다(`OpsRecentDecisions`). 한 줄은 결정 문장(기획 상세의 결정 기록과 같은 함수)·종류·패턴·시각(KST)이고 시험 묶음의 줄은 시험을 켰을 때만 오며
  「시험」 칩이 붙는다. 줄을 누르면 그 항목의 기획 상세(`/admin/ops-inbox/{묶음}?item={항목}`)로 가고 묶음 단위 결정은 그 기획 상세로 간다. 0건이면 「아직 기록이 없어요」다. 머리 오른쪽 [받은 기획함]은 목록으로 간다.
- **주간 핵심 지표**: 미션 달성자 수·배지 발급량을 이번 주 값과 지난주 대비 증감으로 표시하며, `/api/admin/kpi/weekly`와 같은 집계 함수(`computeKpiWeeklyMetrics`)를 재사용해 두 응답이 항상 같은 정의를
  쓴다. 서비스 점검의 Strava 칸과 이 두 장은 같은 한 번의 읽기(이번 주·지난주 두 구간, `startKpiWeekly`)를 나눠 쓴다. 이번 주 집계를 못 읽으면 구역이 안내 카드이고 지난주만 못 읽으면 「지난주 대비 비교 불가」다.
- **배지 경제 흐름**: 주간 핵심 지표 아래에 최근 7일 또는 30일(기본 30일)의 일별 배지 발급량과 일별
  앰비언트 드랍량을 CSS 막대 그래프 두 개로 표시한다(`EconomyTrend.tsx`,
  `lib/admin/economyTrend.ts`). 배지 발급량은 `user_activity_badges.earned_at`(최초 발급 시각,
  주간 KPI와 같은 정의), 앰비언트 드랍량은 `poi_drops.dropped_at` 중 `source = 'system'`
  (`mint_and_place_ambient_drop`이 기록, 유저 드랍은 `source = 'user'`라 제외)이며 날짜 묶음은
  KST 달력 날짜 기준이다. 두 값의 크기가 크게 달라 **그래프마다 각자 최댓값으로 눈금을 따로
  잡는다**. 각 카드에 합계와 일 평균을 함께 표시하고, 오늘 칸은 진행 중인 값이라 "오늘"을
  붙인다. 기간 전환은 `/admin?trend=7`·`/admin?trend=30` 링크이며(그 외 값은 30일) 보고 있는
  `sample` 쿼리를 유지한다. 30일 범위로 두 조회를 한 번씩만 하고(시각 컬럼 하나만, 1,000행씩
  페이지) 7일 보기는 그 결과에서 잘라 쓴다. 값이 모두 0이면 막대 없이 "기간 내 없음"을
  표시하고, 두 조회는 독립적으로 실패해 한쪽만 오류 카드로 바뀐다(둘 다 실패하면 구역이 안내 카드다). 조회만 하며 경제 수치는
  바꾸지 않는다.
- **통계 요약**: 배지·POI·컬렉션·유저 개수 카드(링크 `/admin/badges`·`/admin/poi`·`/admin/itembooks`·`/admin/users`)를 배지 경제 흐름 아래에 두고, 맨 끝에 빠른 실행 4개(배지 등록·POI 등록·컬렉션 등록·
  시뮬레이터 실행)를 둔다. 한 칸을 못 읽으면 그 칸만 「—」과 「불러오지 못했어요」(0건과 구분)이고, 서비스 키가 없어 클라이언트를 만들지 못하면 통계 구역이 안내 카드로 서비스 키 설정
  (`SUPABASE_SERVICE_ROLE_KEY`)을 알린다.

**만들지 않기로 한 것**(모두 2026-09-24 사용자 결정):
- 배포 상태(staging·프로덕션의 마지막 배포 시각과 상태) 표시(티켓 20260924_0910)
- 가입·온보딩 지표 표시(티켓 20260924_0913). 이 수치는 주간 브리핑이 GA4에서 수집해 싣는다.

### 5-8. 일정표 (`/admin/ops-schedule`)

운영 홈에서 옮겨 온 주간 캘린더가 **일정표**가 되었다(티켓 20261006_1536·1537·1538·1539, 상위 20260930_1502). 한 주·한 달·몇 주 치 일정을 보고, 누르면 그 기획을 오른쪽 서랍에서 연다.
화면 구성표(보기·거르기·서랍·상태 표시)와 계산 규칙은 `docs/service/prd/ops-tool/PRD.md` §6.4가 정본이고 여기에는 칸에 올라오는 출처의 동작만 둔다. 사이드바 「받은 기획함」 아래 「일정표」와
운영 홈 「이번 주 상태」 머리의 [일정표 보기 →]로 들어간다. 이 화면은 캐시하지 않는다.

**현재 동작**
- **주소가 상태의 전부다**: `view=week|month|timeline`(기본 주간), `date=YYYY-MM-DD`(기본 오늘), `kind`·`tribe`·`pattern`(여러 개), `drawer=item|day`·`item`·`day`, `sample=1`.
  옛 `?week=YYYY-MM-DD`는 `date`가 없을 때만 읽는다. 잘못된 값은 기본값으로 떨어진다. 이동 링크는 시험 묶음 포함·기준일·거르기를 잃지 않는다.
- **칸에 올라오는 출처**: 운영 항목(받은 기획함, 상태·시험·신호가 붙는다)과 실제 카드·미션. 운영 항목이 `created_resource`로 가리키는 실제 카드·미션은 한 칸으로 합친다. 반려·취소 항목은 칸에 없고
  실패 항목은 타임라인에만 「실패」 색으로 남는다. 읽지 못한 출처는 「…를 읽지 못해 빠져 있어요」로 알리고 「없다」고 단정하지 않는다.
- **「미편성」은 없다**: 옛 캘린더가 활성 단기 카드가 없는 날에 빨간 「미편성」을 표시했으나(티켓 20260924_0906) 일정표에서는 만들지 않는다. 그 역할은 신호(「새 컨텐츠가 없는 날」·「비어 있는 컨텐츠」,
  `ops-tool/PRD.md` §5)가 칸 머리의 신호 칩으로 맡는다(승인 #15).
- **거르기**: 종류·트라이브·패턴. 트라이브·패턴으로 거르면 운영 항목만 남고(옛 카드·미션은 트라이브·패턴이 없다) 안내 문장이 뜬다. 거르기가 켜지면 자동 실행 줄을 숨기고, 장기 카드 줄은 종류 거르기에 「홈피드 카드」가
  있을 때만 남는다. 신호 칩은 거르기와 무관하게 그날 전체 기준이다. 남는 항목이 0건이면 「이 조건에 맞는 항목이 없어요」와 [거르기 지우기]다.
- **Vercel 크론 실행 예정**(주간 보기의 「자동 실행 N개」 접힘 줄): `jam-web/vercel.json`의 `crons`를 읽어 요일 칸에 KST 시각으로 표시한다. 크론 목록의 원천은 이 파일 하나이며 화면에 따로 적지 않는다.
  매시간 도는 크론은 요일마다 "매시간" 한 줄로, 분 칸이 `*/N`인 크론(예: 운영 상태 맞추기 `*/10`)은 요일마다 "N분마다" 한 줄로 묶는다. **예정만 표시하며 실제 실행 여부·성공 여부는 기록하지 않는다**(실행 기록 테이블 없음).
- **Claude 예약 루틴**(같은 접힘 줄): `.claude/skills/jam-work/references/scheduled-jobs.md`의 루틴 절(주간·선별·주간 배포 승인·월간)을 `scripts/gen-scheduled-jobs.mjs`가 `scheduledJobs.generated.ts`로 생성하고,
  화면은 그 생성 파일만 읽는다(md를 런타임에 직접 읽지 않는다). 주간 배포 승인처럼 하루에 라벨이 다른 실행이 2번(확인·실행) 있는 루틴은 항목도 2개로 나뉜다. 매월 루틴은 그 날짜가 보고 있는 주에 들어 있을 때만
  표시된다. 꺼진 루틴은 흐리게 표시하고 크론 항목과 구분되는 표식을 붙인다. md를 고치고 생성기를 다시 돌리지 않으면 커밋이 막힌다(`.githooks/pre-commit`·`scripts/verify.sh`).
- **홈피드 카드 편성**: 보고 있는 주 범위로 `today_cards`를 한 번 조회해(id·title·content_type_id·template_type·starts_at·ends_at·is_active·sort_order만) 순수 함수(`weeklyCards`, `lib/admin/weeklyCards.ts`)로
  요일에 배분한다. 하루 겹침 판정은 `/admin/today` 목록과 같다(`kstDayBoundsIso`의 `startIso`·`endIso`로 `starts_at <= endIso` 그리고 `ends_at >= startIso`). 기간(`ends_at - starts_at`)이 7일(`SHORT_CARD_MAX_DAYS`)
  이하면 단기 카드로 유형 ID(없으면 "유형 없음")·제목을 한 장씩 표시하고, 누르면 서랍이 열린다(서랍의 [기획 상세로 가기]·옛 카드의 `/admin/today/[id]?date=` 상세로 이어진다). 7일을 넘으면 장기 카드로
  "장기 카드 N장" 한 줄로 묶어 그 날짜의 `/admin/today?date=`로 링크하며, N은 활성 카드만 센다(비활성은 「· 비활성 M장」). 비활성 단기 카드는 흐리게 표시한다. 카드 항목은 칸 안에서 크론·루틴 항목보다 위에 온다.
  조회가 실패해도 크론·루틴 항목과 나머지 영역은 그대로 표시한다 — 이때 카드 관련 표시만 비워질 뿐 「없다」고 단정하지 않는다.
- **미션 표시**: 보고 있는 주 범위로 `missions`를 한 번 조회해(id·title·starts_at·ends_at·gate_axis만) 순수 함수(`weeklyMissions`, `lib/admin/weeklyMissions.ts`)로 배분한다. 기간 미션(`ends_at`이 있는 미션)만 7칸 그리드 위에
  가로 막대로 그리며, 이 주에 시작·종료하면 "시작"·"종료" 표식을, 게이트 미션(`gate_axis` 있음)에는 "게이트" 표식을 붙이고 누르면 서랍이 열린다(하루 겹침 판정은 카드와 같다). 주 밖으로 넘치는 쪽은 월·일 칸에서 자르고 표식을 붙이지
  않는다. 상시 미션(`ends_at`이 없는 미션)은 막대로 만들지 않고 "상시 미션 N개" 한 줄로 묶어 `/admin/missions`로 링크하며(N은 그 주 일요일 끝까지 시작한 미션 수, 시작 전 미션 제외), 그 주에 새로 시작하는 상시
  미션만 시작 요일 칸에 "시작" 항목으로 표시한다(2026-09-24 사용자 결정). 운영 미션(합친 미션 포함)은 상태와 함께 막대에도 두고 옛 막대에서는 합친 미션을 뺀다. 조회가 실패하면 막대와 "상시 미션 N개" 줄만 비워지고
  크론·루틴·카드 표시와 나머지 영역은 그대로 표시한다.
- **카드 반응 표시**: 단기 카드 항목 아래 작은 글씨 한 줄로 그날의 `노출 N · 열람 N`을 표시한다(0이어도 0으로 표시). 원천은 `today_card_events`이며 카드 ID·보고 있는 주 범위로 좁혀 1,000행씩 페이지를 넘겨 읽고
  (`lib/admin/weeklyCardMetrics.ts`), 칸의 KST 하루 안의 이벤트만 센다(여러 날에 걸친 카드는 칸마다 따로 나온다). 수집 시작일은 코드에 적지 않고 가장 이른 `occurred_at`의 KST 날짜를 조회해 쓰며, 그 이전 날짜는
  `집계 전`, 오늘보다 뒤 날짜는 표시하지 않는다(이벤트가 하나도 없으면 오늘 이전 날짜는 모두 `집계 전`). 장기 카드 줄에는 붙이지 않고, 오늘보다 뒤인 주는 조회하지 않는다. **후속 행동은 표시하지 않는다** — 이벤트 API가
  노출·열람만 받도록 수집하지 않기로 했다(2026-09-24 사용자 결정, 티켓 20260924_0810). "표본 적음" 같은 표본 판정 문구도 없다(PRD content-automation §11이 최소 표본 기준을 두지 않는다). 조회가 실패하면 수치 줄만
  비워지고 카드 항목과 나머지 영역은 그대로 표시한다. 이 줄은 주간 보기에만 있다(월간·타임라인은 읽지 않는다).
- **캘린더 컴포넌트**: `WeeklyCalendar`(`app/admin/ops-schedule/`)는 요일별 항목 목록과 칸 단위 선택 필드(장기 카드 수, 신호 칩, 자동 실행 줄)와 캘린더 단위 선택 필드(미션 막대, 상시 미션 수)만 받으며, 항목을 어디서
  가져오는지는 알지 못한다.

### 5-9. 밸런스 설정 (`/admin/balance`)

서비스의 밸런스 수치를 코드 수정 없이 바꾸는 화면이다(티켓 20261022_1132, 상위 20261022_1131, 운영 로직 19.1절). 사이드바 「정책 및 밸런스」 맨 위 「밸런스 설정」으로 들어간다.
**지금 구역은 「잼」「동기화」「캡슐」「잠긴 아이템 배지」「컬렉션과 믹스」「챕터」「인벤토리」「어뷰징」「시스템 드랍」「배지와 포인트」 열**(위에서 아래 순서)이고 뒤따르는 구역은 하나씩 더한다. 믹스 칸 수(5)와 등급 올리기 재료 수(5)는 코드에 있고 화면에 올리지 않는다.
옛 「믹스 정책」 화면(`/admin/combine-policy`)과 그 API(`/api/admin/combine-policy`), 사이드바 「믹스 정책」 항목은 「컬렉션과 믹스」 구역으로 옮기며 없앴다(티켓 20261022_1133).
옛 「인벤토리 최대치」 화면(`/admin/inventory-policy`)과 그 API(`/api/admin/inventory-policy`), 사이드바 「인벤토리」 항목은 「인벤토리」 구역으로 옮기며 없앴다(티켓 20261022_1134 1회).
옛 어뷰징 화면(`/admin/abusing`)의 «정책 설정» 탭과 그 API(`PUT /api/admin/abusing/policy`)는 「어뷰징」 구역으로 옮기며 없앴다(티켓 20261022_1134 2회). 같은 화면의 «이용 정지»·«장소 블록» 탭과 사이드바 「어뷰징」 항목은 제재 운영 도구라 그대로다(§5-6).
옛 앰비언트 드랍 화면(`/admin/ambient-drop`)의 **숫자 칸 8개**(배포 시각, 상호 배제 창, 배치 규모, 장소당 최대 활성 드랍, 등급 비율 4칸)와 그 저장은 「시스템 드랍」 구역으로 옮겼다(티켓 20261022_1134 3회). 같은 화면의 예약 배포 스위치, 카테고리·등급·컬렉션 고르기(세 축), 지금 배포, 날짜 예약, 최근 실행 이력과 사이드바 「앰비언트 드랍」 항목은 그대로다. 그 화면은 배포 시각을 읽기 전용 글자로 보이고 «밸런스 설정에서 바꿔요» 한 줄을 둔다(링크 없이).

**현재 동작**
- **한 화면에 구역을 세로로 쌓고 구역마다 따로 읽고 저장한다**(사용자 결정 1). 구역마다 `Suspense`로 읽어 한 구역이 실패해도 나머지는 보인다. 구역이 2개 이상이면 맨 위에 구역 바로가기(`OpsSettingsNav`)가 따라다닌다.
  한 구역을 저장해도 다른 구역은 건드리지 않는다. 구역 목록은 `lib/admin/balance/sections.tsx` 한 곳이고 구역을 더하는 일은 연결 객체(칸 정의·읽기·쓰기·칸 사이 검증) 하나, 본문 컴포넌트 하나, 배열 한 줄이다.
- **잼 구역의 칸**(`jam_policy` id=1): 강도 배율 3칸(`intensity_light`·`_normal`·`_hard`, 0 이상 정수)과 대량 수령 경보 기준 3칸(`mass_earn_alert_multiplier` 0.01~999.99·소수 둘째 자리,
  `_weeks` 1 이상 정수, `_no_history_amount` 1 이상 정수; 사용자 결정 3). 범위는 마이그레이션 226의 CHECK와 같다. 칸 옆에 코드 기본값(`DEFAULT_JAM_POLICY`)을 작게 보이고 **「기본값으로 되돌리기」 버튼은 없다.**
  편집 화면은 비정상 값을 기본값으로 바꿔 보이지 않고 DB에 저장된 값 그대로 읽는다(읽지 못하면 그 구역만 오류 카드다).
- **동기화 구역의 칸**(`jam_policy` id=1, 열한 칸): 확정으로 받는 개수 2칸(`sync_item_guaranteed` 일반 활동·`_hiking` 등산, 0 이상 정수), 보너스 3칸(`sync_item_bonus_rolls` 0 이상 정수·`_jam_divisor` 1 이상 정수·`_max_probability` 0~1·소수 셋째 자리),
  등급 확률 4칸(`sync_rarity_common`·`_rare`·`_epic`·`_mystic`, 합 100±0.001), 동기화와 캡슐이 한 값으로 쓰는 `common_streak_threshold`(1 이상 정수)·`locked_roll_probability`(0~1·소수 셋째 자리). 범위는 마이그레이션 227·231의 CHECK와 같다.
  **0개도 허용한다**(확정 0, 보너스 기회 0): 확정 개수 두 칸과 보너스 기회가 모두 0이면 «아이템 배지가 나오지 않아요» 경고를 보이되 막지 않는다. 잠긴 아이템 배지 등급별 최소값(`locked_min_*`)은 「잠긴 아이템 배지」 구역이 편집한다.
- **캡슐 구역의 칸**(`capsule_policy` id=1 열한 칸 + `capsule_chapter_costs` 챕터 1~10행): 확정·보너스 개수(0 허용, 모두 0이면 같은 경고), 보너스 확률·다른 트라이브 확률(0~1·소수 셋째 자리), 등급 확률 4칸(합 100±0.001), Epic 보정 `pity_epic_threshold`(1 이상 정수),
  퀘스트 전 두 칸(`pre_quest_fill_amount`·`pre_quest_unlock_required`, 1 이상 정수), **챕터별 채울 양 10행**(1 이상 정수, 칸 이름 `chapter:1`~`chapter:10`, 이력에도 그대로 남는다). **챕터 번호는 늘리거나 줄이지 않고 값만 바꾼다**(챕터 더하기는 후속 티켓 20261022_1718).
  바꾼 값은 앞으로 만들어지는 캡슐부터 적용된다(캡슐의 필요량은 만들 때 고정). `common_streak_threshold`와 `locked_roll_probability`는 동기화와 한 값이라 **동기화 구역에서만 편집하고** 캡슐 구역에는 «동기화와 같은 값이에요» 안내와 동기화 구역 링크만 둔다.
- **잠긴 아이템 배지 구역의 칸**(`jam_policy` id=1 네 칸, 티켓 20261022_1133): 잠긴 아이템 배지를 여는 데 필요한 양의 등급별 최소값 `locked_min_common`·`_rare`·`_epic`·`_mystic`(단위 잼, 1 이상 정수, 마이그레이션 231의 CHECK와 같다).
  등급 사이 순서는 검사하지 않는다(«등급마다 두 배»는 기본값이지 규칙이 아니다). 잠길 확률(`locked_roll_probability`)은 동기화와 한 값이라 이 구역에서 편집하지 않고 위에 «동기화와 같은 값이에요» 안내와 동기화 구역 링크를 둔다.
  아래에는 배지에 여는 데 필요한 양을 따로 정해 둔 경우 그 값이 먼저라서(`resolveUnlockRequired`), 최소값을 올려도 따로 정한 값은 그대로이고 새 최소값보다 낮은 값이 남을 수 있다는 안내를 둔다(저장을 막지 않는다). 이미 잠긴 개체가 여는 데 필요한 양은 배정 때 고정돼 바뀌지 않는다.
  잼·동기화 구역과 같은 행을 쓰므로 수정 시각도 같다(아래 «같은 행을 쓰는 구역»).
- **컬렉션과 믹스 구역의 칸**(`item_book_tier_default_rewards` 네 등급 행 + `combine_policy` id=1, 티켓 20261022_1133): 컬렉션 등급별 기본 완성 포인트 4칸(칸 이름 `default_reward:common`~`default_reward:mystic`, 0 이상 정수, 마이그레이션 222의 CHECK와 같다)과
  믹스 실패 포인트 `fail_reward_points`(0 이상 정수, 마이그레이션 153). **0이면 포인트를 주지 않는다.** 컬렉션마다 따로 정해 둔 완성 포인트(`item_book_tier_rewards.reward_points`)가 있으면 그 값이 먼저이고, 이미 받은 보상은 바뀌지 않는다는 안내를 폼 위에 둔다.
  믹스 실패 포인트는 레시피에 맞지 않는 재료로 믹스했을 때 재료가 사라지고 나가는 포인트다(옛 「믹스 정책」 화면이 하던 일). 「챕터 점수」(`chapter_score_rules.collection_complete_*`)와 이 구역의 「포인트」는 값이 같아도 다른 설정이다.
  정책 대시보드의 «믹스 실패 보상 포인트» 카드는 이 구역(`/admin/balance#collection`)으로 이어 준다(대시보드의 직접 저장 경로는 티켓 20261022_1717에서 없앴다. 대시보드는 값을 읽어 보여 주고 링크만 둔다).
- **챕터 구역의 칸**(`chapter_definitions` 챕터 1~10행 + `chapter_score_rules` 활동 12행, 45칸, 티켓 20261022_1133 2회): 챕터 2~10에 오르는 데 필요한 **누적 점수** 9칸(칸 이름 `required:2`~`required:10`, 단위 점, 1 이상 정수)과,
  활동 12종(모은 잼, 캡슐 열기, 잠긴 아이템 배지 열기, 배지 받기, 컬렉션 완성 Common·Rare·Epic·Mystic, 믹스 성공, 미션 완료, 드랍, 픽업 — `lib/chapter/kinds.ts`의 `CHAPTER_SCORE_KINDS`가 기준이다)마다 세 칸:
  단위당 점수(`rule:<활동>:points`, 0 이상·소수 둘째 자리), **주간 상한**(`:cap`, 0 이상 정수), 상한을 넘은 점수를 세는 비율(`:ratio`, 0~1·소수 셋째 자리). 범위는 마이그레이션 221의 CHECK와 같고 칸 이름은 이력에도 그대로 남는다.
  **주간 상한 0은 «상한 없음»이고 DB에는 NULL로 쓴다**(읽을 때 NULL은 0으로 보인다). 상한 칸이 있어야 드랍·픽업 5점처럼 상한 없는 활동을 반복해 점수가 쌓이는 틈(운영 로직 12.2절)을 이 화면에서 막을 수 있다.
  챕터 1은 퀘스트를 마치면 얻어서 필요한 점수가 0으로 고정이라 편집 칸이 없다. 필요한 누적 점수는 **앞 챕터보다 커야 하고**, 같거나 작으면 저장되지 않고 뒤쪽 챕터 칸에 «챕터 N(점수)보다 커야 해요.» 문장이 붙는다(서버가 합쳐진 전체 값으로 검사).

- **확률 확인창**(사용자 결정 2, 가정 마): 확률 안내 페이지(`/probability`)가 읽는 칸(`lib/probability/disclosure.ts`의 `JAM_COLUMNS`·`CAPSULE_COLUMNS`·`AMBIENT_COLUMNS` — «확률 안내에 반영되는 칸»의 단일 원천, 칸 정의의 `affectsDisclosure`)이 바뀐 저장은 [저장]을 누르면 확인창이 먼저 뜬다.
  창에는 바뀐 칸의 **전 → 후**, 「확률 안내 페이지에 바로 반영돼요. 바꾸기 전에 공지가 필요한지 확인해요.」, **저장하면 프로덕션에 바로 반영된다**는 안내(staging과 프로덕션이 같은 값을 쓴다), 함께 저장되는 그 밖의 칸 수, 변경 메모(선택)가 있고 [저장하기]를 눌러야 저장된다.
  공지하는 수단은 6-4도 확인하지 못해 확인창까지만 한다. 그 밖의 칸(잼 구역 여섯 칸, 퀘스트 전 두 칸, 챕터별 채울 양, 잠긴 아이템 배지 구역 네 칸, 컬렉션과 믹스 구역 다섯 칸, 챕터 구역 45칸, 인벤토리 구역 한 칸, 어뷰징 구역 열 칸, 시스템 드랍 구역 숫자 네 칸(배포 시각·상호 배제 창·배치 규모·장소당 한도), 배지와 포인트 구역 다섯 칸)만 바뀐 저장은 확인창이 없다. 이력에는 확률 안내 반영 칸이 포함됐는지가 남고 «최근 변경»에 «확률 안내에 반영된 칸 포함» 표시가 붙는다.
- **같은 행을 쓰는 화면**: 시스템 드랍 구역과 옛 앰비언트 드랍 화면(스위치·세 축 저장)이 `ambient_drop_config` 한 행을 나눠 쓴다. 옛 화면의 저장이 행의 `updated_at`을 올리므로, 구역 화면을 열어 둔 채 옛 화면에서 저장하면 구역의 다음 저장이 «다른 사람이 먼저 바꿨어요»(409)로 한 번 막힌다(안전한 쪽 오류, [새로 불러오기]로 풀린다).
- **같은 행을 쓰는 구역**: 잼과 동기화는 `jam_policy` 한 행을 나눠 쓴다. 한 구역을 저장하면 행의 `updated_at`이 올라 다른 구역의 수정 시각도 달라진다. 같은 화면에서는 고치던 값(저장 전 초안)을 지키고 새 수정 시각만 받는다. 다른 사람이 열어 둔 화면에서는 «다른 사람이 먼저 바꿨어요»(409)가 한 번 뜰 수 있다(안전한 쪽 오류, [새로 불러오기]로 이어진다).
- **캡슐 구역의 저장(행 단위)**: 구역의 수정 시각은 정책 행과 챕터 행들의 `updated_at` 가운데 가장 늦은 것이다. 저장은 모든 행의 수정 시각을 다시 읽어 화면이 본 값과 같을 때만 시작하고, 바뀐 행마다 «방금 읽은 수정 시각이 같을 때만» 갱신한다(정책 먼저, 챕터는 번호 순서).
  중간에 다른 곳이 먼저 바꾸거나 DB 오류가 나면 이미 쓴 행을 이전 값과 이전 수정 시각으로 되돌린 뒤 409·500으로 답한다(되돌리기까지 실패하면 로그와 함께 500). 이력을 쓰지 못한 경우의 되돌리기는 공용 저장이 같은 `write`로 부른다.
- **여러 표를 쓰는 구역의 공용 모듈**(`lib/admin/balance/rowwise.ts`, 티켓 20261022_1133): 컬렉션과 믹스 구역(등급 네 행 → 믹스 정책 행 순서)이 위 캡슐 구역과 같은 방식으로 저장한다. 수정 시각 계산(`latestStamp`)과
  «행마다 읽은 수정 시각이 같을 때만 갱신, 막히면 이미 쓴 행을 나중에 쓴 행부터 되돌림, 되돌리기 실패는 로그와 500»(`runRowOps`)을 공용 모듈에 두고, 구역은 표마다 갱신·되돌림 함수만 넘긴다. 챕터 구역(챕터 열 행 → 활동 규칙 12행 순서, 티켓 20261022_1133 2회)도 같은 모듈을 쓴다. 캡슐 구역은 자기 코드를 그대로 쓴다(공용 모듈로 옮길지는 7-2 뒤에 정한다).
- **변경 메모는 항상 선택**이다(사용자 결정 2). 어떤 값을 바꿔도 메모를 비워도 저장된다. 200자까지다.
- **저장**: `PUT /api/admin/balance/[section]`, 본문 `{ values, expectedUpdatedAt, note? }`. 서버가 ① 어드민 세션을 확인하고(읽기 토큰은 이 경로에서 쓰이지 않는다) ② 칸마다 정수·범위를 검사하고(`lib/jam/policy.ts`의 `VALIDATORS` 재사용, 모르는 칸은 거절)
  ③ 현재 값을 읽어 **바뀐 칸만** 가린 뒤(없으면 400 「바뀐 값이 없어요」) ④ 화면이 읽은 때의 `updated_at`과 같을 때만 갱신하고(다르면 409 「다른 사람이 먼저 바꿨어요. 새로 불러온 뒤 다시 바꿔 주세요」, `updated_at`은 저장이 직접 올린다)
  ⑤ 변경 이력 한 줄을 쓴다. **이력을 쓰지 못하면 방금 갱신을 이전 값과 이전 수정 시각으로 되돌리고** 500으로 답한다(되돌리기까지 실패하면 로그에 남기고 다른 문장의 500). 응답에 DB 오류 원문을 싣지 않는다. 칸 사이 검증(등급 확률 합 100±0.001 등)은 구역 연결 객체가 얹는다(동기화·캡슐 구역이 등급 확률 합 100을, 챕터 구역이 필요 누적 점수의 순서를 얹는다). 구역의 쓰기가 DB 규칙에 따른 **거절**을 [현상-원인-해결책] 문장으로 돌려주면(`rejected`, 인벤토리 구역이 쓴다) 그 문장 그대로 400으로 답하고 이력을 쓰지 않는다.
- **읽기**: `GET /api/admin/balance/[section]`이 현재 값·`updated_at`·최근 이력을 돌려준다. 알 수 없는 구역은 읽기·저장 모두 404다.
- **변경 이력**: 구역 아래 「최근 변경」에 최근 10건(누가 · 언제(KST), 칸 이름: 이전 → 새 값, 메모)이 보인다. 이력 표는 `balance_setting_changes`(마이그레이션 285, `02_DATA_MODEL.md` §12)이고 옛 설정 표에는 트리거를 달지 않는다.
  **바꾼 사람은 표시 이름(`username`)만** 보이고 어드민 ID·이메일은 읽기 결과에 싣지 않는다(이름을 모르면 「알 수 없음」).
- **프로덕션 즉시 반영**: 공용 DB를 staging과 프로덕션이 함께 쓰므로 저장하면 바로 프로덕션에 반영된다. 화면 머리와 저장 알림, 확률 확인창이 이를 알린다(잼 구역의 여섯 칸은 확률 안내 페이지가 읽지 않아 확인창이 없다).

**적용 순서**: 마이그레이션 285(새 표만, 되돌림 SQL 포함)를 **먼저** 공용 DB에 적용하고 코드 push는 나중이다. 코드가 먼저 나가면 이력 쓰기가 실패해 저장이 막힌다(저장은 되돌려지고 500이다).

## 6. 기술 스펙

### 라우팅
- 기존 `jam-web` Next.js 앱에 `/admin` 경로 추가 (별도 앱 X)
- `src/app/admin/` 디렉터리 신규 생성
- `src/middleware.ts`에 어드민 경로 보호 로직 추가

### 인증 미들웨어 로직
```
1. /admin/* 요청 수신
2. Supabase Auth 세션 확인
3. 미로그인 → /login?redirect=/admin 으로 리다이렉트
4. 로그인 상태이지만 이메일이 ADMIN_EMAILS에 없음 → /admin/forbidden
5. 허용된 이메일 → 통과
```

### 새 환경변수
```
ADMIN_EMAILS=admin@example.com,dev@example.com
```

### 시뮬레이터 API
```
POST /api/admin/simulate
Body: {
  userId: string
  dryRun: boolean
  activity: {
    // GPX 클라이언트 파싱 결과
    activityType: 'cycling' | 'running' | 'hiking' | 'walking'
    distanceKm: number
    movingTimeSec: number
    elevationGainM: number
    averageSpeedKmh: number
    startDate: string          // ISO 8601
    route: [number, number][]  // [[lat, lng], ...] POI 매칭용
  }
  repeatCount: number          // 활동 반복 횟수 배수 (기본 1)
}
Response: {
  parsed: {                    // GPX 파싱 요약 (확인용 echo)
    distanceKm: number
    durationMin: number
    elevationGainM: number
    averageSpeedKmh: number
    trackpointCount: number
  }
  badgesEarned: { id: string; name: string; rarity: string; reason: string }[]
  badgesMissed: { id: string; name: string; reason: string; actual: string; required: string }[]
  poisMatched: { id: string; name: string }[]
  // 아이템 드랍 필드(itemDrops·itemDropSkips·itemDropUnavailable)는 지웠다 — BADGE_ENGINE_UNIFIED §3.7.2
  itemBooksCompleted: { bookName: string; rewardBadgeName: string | null }[]
  applied: boolean
}
```

### 스타일
- 어드민은 모바일 최적화보다 **데스크탑 우선** (1024px+ 기준)
- 기존 Tailwind CSS 재사용, 다크 테마 유지
- 사이드바 네비게이션 레이아웃
