# JAM! 챕터 — PRD

> 정책의 출처는 `docs/plan/jam2/10 JAM 2.0 서비스 운영 로직.md` 12장이고, 이 문서는 그 정책을 서버가 어떻게 지키는지 코드 기준으로 적는다.
> 챕터 표 6개와 RPC 2개의 구조, 점수를 부르는 지점과 원천 id는 [02_DATA_MODEL.md](../02_DATA_MODEL.md) 9-3절이 단일 원천이라 여기에 다시 적지 않는다.
> 만든 티켓: 점수 연결 20261019_1315, 챕터 1 시작·오름 처리·읽기 20261019_1316, 프로필 챕터 줄·오름 축하 카드 20261019_1317(1회).

## 1. 범위

서버에 있는 것은 네 가지다.

1. 챕터 1 시작(퀘스트 완료 처리가 부른다).
2. 챕터가 오를 때의 처리(소식, 챕터 배지 판정).
3. 프로필이 쓸 읽기 함수 둘과 챕터 이름 조회.
4. 위 읽기 함수의 응답 모양 규칙(점수 숫자를 싣지 않는다).

화면에는 두 가지가 있다(7절). 프로필의 챕터 줄(내 프로필, 다른 유저 프로필)과 챕터가 올랐을 때의 축하 카드다.
API 라우트는 하나다. `GET /api/chapter/me`는 축하 카드를 띄울 때 챕터 이름을 읽는 데만 쓴다(7.3절).

## 2. 챕터가 생기는 흐름

- 유저는 가입 직후 챕터가 없다. 이때 `user_chapters` 행이 없거나 `chapter_no`가 NULL이다. 이 상태에서도 점수는 쌓이고, 쌓인 점수는 버려지지 않는다.
- 퀘스트 완료가 확정되면(`lib/onboarding-quest/completion.ts`의 `recordOnboardingQuestCompletion`) `chapter_start`를 불러 챕터 1을 받는다. 보상 지급 판정보다 앞이다.
  - 연출을 건너뛴 유저도 받는다(건너뛰기는 연출 단계만 건너뛰고 완료 보상만 받지 않는다).
  - 챕터 1은 점수와 상관없이 시작하고, 쌓인 점수로 오를 수 있는 챕터까지 한 번에 오른다. 오른 챕터마다 `chapter_ups`에 한 줄이 남는다.
- **재시도.** `chapter_start`가 일시 오류로 실패하면 완료 시각은 이미 기록돼 있다. 그래서 완료 기록이 있는 유저가 퀘스트 완료 처리에 들어올 때마다 `user_chapters.chapter_no`를 읽고, 비어 있을 때만 `chapter_start`를 다시 부른다(`lib/chapter/start.ts`의 `ensureChapterStarted`). 챕터가 있으면 DB 함수를 부르지 않는다.
- 옛 퀘스트를 마친 유저도 같은 경로로 다음 호출에서 챕터 1을 받는다. 기존 유저를 위한 별도 시작 정책은 없다(티켓 20261019_1316 사용자 결정 4).
- 시작이 실패해도 퀘스트 완료와 보상은 그대로 진행된다. 실패는 `console.error`와 `engine_decision_log`(`chapter_start_failed`)에 남는다.

호출 위치와 응답 계약 검사의 구현 세부는 [02_DATA_MODEL.md](../02_DATA_MODEL.md) 9-3절 「챕터 1 시작과 오름 처리」다.

## 3. 점수

점수를 세는 일 열두 종류와 호출 지점은 [02_DATA_MODEL.md](../02_DATA_MODEL.md) 9-3절 「점수 호출 지점과 원천 id」다. 점수 값(1당 몇 점, 주간 상한)은 DB 설정 행이 갖고 있고 앱 코드에 상수로 두지 않는다.

## 4. 오름 처리

챕터가 오른 순간(`chapter_add_score`나 `chapter_start`가 오른 챕터 목록을 돌려줄 때) `processChapterRise`(`lib/chapter/rise.ts`)가 한다.

| 처리 | 규칙 |
|---|---|
| 소식 | 오른 챕터 가운데 가장 높은 챕터가 **2 이상**일 때만 알림 종류 `chapter_up` 한 건을 보낸다. 한 번에 여러 챕터를 넘어도 한 건이다. 챕터 1 시작은 퀘스트 완료 보상이 이미 알리므로 보내지 않는다. 문구와 착지는 [알림 PRD](../notification/PRD.md) #48이다 |
| 챕터 배지 | 오름이 있으면(챕터 1 포함) 챕터 조건 배지(`chapter_reached`)를 그 자리에서 판정해 받게 한다. 챕터 도달값은 지금 챕터 하나라서 한 번에 여러 챕터를 넘어도 `chapter_reached >= N` 배지를 모두 받는다 |
| 이중 판정 | 동기화 끝 판정이 DB의 지금 챕터를 이어서 읽는 호출(잼 정산)만 챕터 배지 판정을 건너뛴다. 그 밖의 호출은 바로 판정한다. 판정이 겹쳐도 배지는 `UNIQUE(user_id, badge_id)`로 한 번만 발급된다. 호출별 구분과 근거는 [02_DATA_MODEL.md](../02_DATA_MODEL.md) 9-3절 |
| 서로 막지 않음 | 소식이 실패해도 판정은 하고, 판정이 실패해도 소식은 보낸다. 오름 처리는 던지지 않으며 점수와 챕터 시작의 결과를 바꾸지 않는다. 실패는 `chapter_rise_failed`로 남는다 |
| 점수 고리 | 챕터 배지는 다시 챕터 점수를 올리지 않는다(`chapter_reached` 조건 배지는 «배지 받기» 점수에서 뺀다) |

## 5. 읽기 함수와 응답 모양

프로필이 쓸 읽기 함수는 `lib/chapter/read.ts`에 둘, 이름 조회는 `lib/chapter/name.ts`에 하나 있다. 모두 서버 전용이고 `supabase` 클라이언트를 인자로 받는다.

### 5.1 점수의 숫자는 응답에 싣지 않는다

운영 로직 12.3절의 규칙이다. 누적 점수, 챕터별 필요 점수, 둘의 차이를 포함해 어떤 형태의 점수 값도 응답에 없다. 응답 객체는 아래 필드만 직접 채워 만들고, 읽은 행을 그대로 펼쳐 담지 않는다. 키 목록은 `lib/chapter/__tests__/read.test.ts`가 고정한다.

### 5.2 내 챕터 — `getMyChapter(supabase, userId)`

내 프로필용이다. 다음 챕터까지의 진행을 포함한다.

| 상태 | `chapterNo` | `name` | `nextChapterNo` | `progress` |
|---|---|---|---|---|
| 챕터 없음 (`user_chapters` 행 없음, `chapter_no` NULL) | null | null | null | null |
| 챕터 있음, 다음 챕터 정의가 있음 | 지금 챕터 | 이름 또는 null | 다음 챕터 번호 | 0 이상 1 이하 |
| 마지막 챕터 (번호가 더 큰 정의가 없음) | 지금 챕터 | 이름 또는 null | null | null |

- 성공 응답은 `ok: true`와 위 네 필드다. 화면은 `chapterNo`가 null이면 «챕터 없음», `nextChapterNo`가 null이면 «더 오를 챕터 없음»을 구분해 그린다.
- **진행 비율** = (누적 점수 − 지금 챕터의 `required_score`) ÷ (다음 챕터의 `required_score` − 지금 챕터의 `required_score`)를 0 이상 1 이하로 자르고 소수 둘째 자리까지 **내린다**. 다음 챕터 직전의 0.9992는 1이 아니라 0.99다. 챕터 정의 전체를 한 번 읽어 계산하고(`lib/chapter/progress.ts`), 다음 챕터는 지금 챕터보다 번호가 큰 정의 가운데 가장 작은 번호다.
- 챕터가 없는 유저는 정의와 트라이브 표를 읽지 않는다.

### 5.3 다른 유저에게 보이는 챕터 — `getPublicChapter(supabase, userId)`

다른 유저의 프로필용이다. 진행(비율, 다음 챕터)은 돌려주지 않고, 점수 열과 챕터 정의 표는 읽지도 않는다(운영 로직 12.3절).

| 필드 | 값 |
|---|---|
| `ok` | true |
| `tribe` | `{ id, name }`. 트라이브를 고르지 않은 유저는 null |
| `chapterNo` | 지금 챕터. 챕터가 없으면 null (트라이브는 그대로 돌려준다) |
| `name` | 지금 트라이브의 챕터 이름. 이름이 없거나 트라이브가 없거나 챕터가 없으면 null |

`tribe`는 `tribes`의 `id`와 `name`만 담는다. 기존 프로필 화면은 트라이브를 읽지 않는다. 표시에 다른 값(이미지 등)이 필요하면 5-7에서 응답을 넓힌다.

### 5.4 읽지 못함

세 함수 모두 던지지 않는다. 조회 오류, 예외, 해석할 수 없는 값을 만나면 `console.error`만 남기고 `{ ok: false }`를 돌려준다. 이 응답에는 다른 필드가 없고, **챕터 없음**(`ok: true`에 `chapterNo: null`)과 구분된다. 한 조회라도 실패하면 일부만 채운 응답을 만들지 않고 전체를 읽지 못함으로 돌려준다. 읽지 못했을 때 무엇을 그릴지는 부르는 화면이 정한다.

### 5.5 부르는 쪽이 지킬 것

- `user_chapters`는 본인 행만 읽는 정책이라 읽기 함수는 service 클라이언트를 받는다. service 클라이언트는 모든 유저의 행을 읽을 수 있으므로 «누구의 챕터를 보여도 되는가»는 부르는 쪽이 정한다.
- 이름이 null이면 화면은 «챕터 N»만 그린다(티켓 20261019_1316 사용자 결정 3).

## 6. 챕터 이름과 이름 표

- 이름은 `chapter_names`의 (트라이브, 챕터)로 읽는다(`getChapterName`). 읽는 트라이브는 유저의 **지금** 트라이브(`users.tribe_id`)다. 트라이브가 바뀌면 챕터 숫자는 그대로이고 이름만 새 트라이브의 것이 된다. 새 트라이브에 이름이 없으면 옛 트라이브의 이름을 쓰지 않고 null이다.
- 행이 없거나 `name`이 null, 빈 문자열, 공백뿐이면 null이다. 값이 있으면 저장된 그대로 돌려준다.
- 이름 표는 비어 있어도 되고, 티켓 20261019_1316 조사(2026-10-20) 시점에 0행이었다. 이 상태에서 읽기 함수는 이름만 null이고 나머지는 정상으로 동작한다. 임시 이름 시드는 넣지 않았다(사용자 결정 3).

## 7. 화면 규칙 (티켓 20261019_1317 1회)

화면은 서버가 읽은 값을 그대로 그린다. 클라이언트에서 점수를 계산하지 않고, 어떤 화면에도 점수 숫자를 그리지 않는다(운영 로직 12.3절).
화면 문구는 `d.chapter`(`lib/i18n/ko.ts`)에 있고 용어는 «챕터»다([UX 라이팅 가이드](../../writing/UX_WRITING_GUIDELINE.md) 1.3절).

### 7.1 프로필의 챕터 줄

프로필 서버 페이지(`app/(main)/[username]/page.tsx`)가 읽어 `ProfileClient`로 내린다. 한 컴포넌트(`ChapterLine`)가 두 모양을 맡는다.

| 어디 | 읽는 함수 | 모양 |
|---|---|---|
| 내 프로필 | `getMyChapter` | 캡슐 위젯 바로 위에 «챕터 3 · 단골» 줄, 오른쪽에 «다음 챕터까지», 아래에 게이지(`ProgressBar` 기본형, 숫자 없음). 줄·게이지·캡슐은 간격 8로 묶는다 |
| 다른 유저 프로필 | `getPublicChapter` | 헤더 아래 전폭 한 줄 «트라이브 · 챕터 3 · 단골». 게이지 없음 |

| 상태 | 내 프로필 | 다른 유저 프로필 |
|---|---|---|
| 챕터 있음, 이름 있음 | «챕터 3 · 단골» | «트라이브 · 챕터 3 · 단골» |
| 이름 없음 | «챕터 3»만 | «트라이브 · 챕터 3» |
| 트라이브 없음 | 해당 없음 | 트라이브 조각만 뺀다 |
| 마지막 챕터(`nextChapterNo` null) | 줄만 있고 «다음 챕터까지»와 게이지가 없다. «마지막» 같은 문구도 두지 않는다(챕터가 늘 수 있다) | 해당 없음 |
| 챕터 없음(퀘스트 전) | **줄이 없다.** 안내 줄도 «다시 시도» 버튼도 없다 | 트라이브가 있으면 트라이브 조각만, 없으면 줄이 없다 |
| 읽지 못함(`ok: false`) | **줄이 없다.** 챕터 없음과 화면에서 구분되지 않고 새로 고침이 유일한 재시도다(사용자 결정 4) | 줄이 없다 |

- **내 진행은 타인에게 실리지 않는다.** 내 프로필만 `getMyChapter`를 부르고 `chapterInitial` prop을 내린다(캡슐 `capsuleInitial`과 같은 방식). 다른 유저 프로필은 `getPublicChapter`만 부르고 `publicChapter` prop을 내려, 진행·다음 챕터 필드가 조회도 전달도 되지 않는다. `[username]/__tests__/page.test.tsx`가 직렬화한 prop으로 고정한다.
- 긴 이름은 줄여서(`truncate`) 320px에서 넘치지 않게 한다. 이름 칸은 줄어들고 «다음 챕터까지»는 줄바꿈하지 않는다.
- 줄은 서버가 그린 값이라 로딩 상태가 없다.

### 7.2 챕터 오름 축하 카드

챕터가 오르면 **다음에 앱을 열 때 기기마다 한 번** 축하 카드가 뜬다(사용자 결정 1). 오른 순간의 요청 응답에 싣는 방식은 쓰지 않는다 — 점수를 세는 라우트·클라이언트 약 10곳을 고쳐야 하고 `strava/callback`은 리다이렉트라 실을 수 없으며 화면을 떠나면 놓친다.

- **누가 정하나.** `(main)/layout.tsx`가 화면을 열 때마다 `user_chapters.chapter_no` 한 칸만 읽어 `ChapterRiseWatcher`에 내린다(챕터가 없으면 감시를 그리지 않는다). 읽기가 실패하면 로그만 남기고 연출하지 않는다.
- **판정(`lib/chapter/celebrate.ts`).** 기기 `localStorage`의 «마지막으로 축하한 챕터»(키는 유저 id별)와 견준다.

  | 조건 | 결과 |
  |---|---|
  | 저장값이 없음(처음 보는 기기·계정) | 연출 없이 지금 챕터를 저장만 한다 |
  | 지금 챕터가 1 이하 | 연출 없음(챕터 1은 «시작»이고 퀘스트 완료 보상이 알린다). 저장값보다 높으면 저장만 한다 |
  | 지금 챕터가 저장값보다 높음 | 지금(가장 높은) 챕터로 한 번 띄우고 저장한다. 한 번에 여러 챕터를 넘어도 한 번이다 |
  | 지금 챕터가 저장값 이하 | 아무것도 하지 않는다(저장값을 낮추지 않는다) |

- **저장소가 막힌 경우.** 읽기·쓰기는 모두 `try/catch`다. 읽을 수 없거나, 써도 값이 남지 않으면(쓴 뒤 다시 읽어 확인한다) 연출하지 않는다. 저장되지 않으면 열 때마다 다시 뜨기 때문이다.
- **다른 오버레이가 열려 있으면**(`useTabBarHidden`) 닫힐 때까지 기다린다. 기다리는 동안은 저장하지 않으므로 화면을 떠나도 다음에 다시 뜬다. 동기화 뒤에는 `SyncButton`이 배지 연출을 닫을 때 `router.refresh()`로 레이아웃을 다시 읽히므로 새 챕터가 내려와 연출 뒤에 바로 이어서 뜬다. 캡슐 열기 같은 다른 경로는 다음 로드에 뜬다.
- **모양(`ChapterRiseOverlay`).** 배지 획득 오버레이의 껍데기(탭바 숨김, `main` 스크롤 잠금, 430px 컬럼, 닫기 X와 Escape, 라이브 리전)를 따르고 `Card` 면에 «축하해요!» / «챕터 3에 올랐어요» / 이름(있을 때만)을 둔다. 점수·게이지 없음. `--duration-medium` 페이드와 16px 상승이고 모션 축소 설정이면 페이드만 남는다.

### 7.3 이름 읽기 — `GET /api/chapter/me`

레이아웃은 화면을 열 때마다 돌아 번호만 읽는다. 이름·진행은 읽지 않는다. 이름은 축하 카드를 띄울 때만 이 라우트가 `getMyChapter`로 읽는다.

- 응답 키는 `chapterNo`와 `name` 둘뿐이다(점수·다음 챕터·진행 비율 없음). 비로그인 401, 읽지 못함 500.
- 화면은 응답의 `chapterNo`가 띄운 챕터와 같을 때만 이름을 쓴다(읽는 사이 챕터가 또 오르면 다른 챕터의 이름이다). 읽지 못하거나 4초 안에 오지 않으면 이름 없이 띄운다.

### 7.4 한계

- **기기마다 한 번이다.** 저장값이 기기에 있어 다른 기기에서는 또 한 번 뜬다. 앱 데이터를 지우거나 사생활 보호 모드로 열면 저장값이 없어 연출 없이 저장만 하므로 그 챕터의 축하는 건너뛴다.
- **처음 보는 기기에서는 뜨지 않는다.** 저장값이 없으면 연출하지 않고 저장만 하기 때문이다(기존 유저가 앱을 열 때마다 축하받지 않게 하는 규칙). 챕터 1을 받자마자 챕터 2 이상으로 한 번에 오른 유저도 첫 열기에는 뜨지 않는다.
- **«읽지 못함»과 «챕터 없음»이 내 프로필에서 구분되지 않는다**(7.1절).
- 오름 소식(`chapter_up`)은 별개다. 소식 행은 서버가 오른 순간 만들고([알림 PRD](../notification/PRD.md) #48) 읽음 표시와 축하 카드의 «이미 축하했는가»는 이어지지 않는다.

## 8. 하지 않는 것

| 하지 않는 것 | 어디서 하나 |
|---|---|
| 챕터 이름 50개를 짓는 일, 이름 표의 어드민 입력 | 별도 주제 |
| 오른 순간 요청 응답에 챕터를 실어 그 화면에서 바로 축하 | 하지 않는다(7.2절) |
| 점수 숫자·진행 비율 숫자·«마지막 챕터» 문구 | 화면에 두지 않는다(7.1절) |
| 옛 퀘스트 완료자만을 위한 챕터 시작 정책 | 두지 않는다. 재시도 경로가 같은 일을 한다(2절) |
| 임시 이름 시드 | 두지 않는다 |
