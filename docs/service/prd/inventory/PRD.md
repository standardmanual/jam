# 인벤토리 포화 인지 및 드랍 순환 유도

> 배지엔진의 슬롯 초과 스킵 동작과 알림함 §⑧ #42(인벤토리 포화)를 전제로, 유저가 슬롯을
> 직접 비워 순환을 재개하게 만드는 상시 UI를 다룬다. 배지·드랍 로직 자체는 변경하지 않는다.

## 1. Problem Statement

유저가 액티비티를 동기화해도 인벤토리 슬롯(`inventory.used_slots` / `max_slots`)이 가득 차 있으면
아이템배지 드랍이 판정 단계에서 조용히 취소된다. 유저 입장에서는 "운동했는데 왜 배지가 하나도
안 나오지"라는 의문만 남고, 그 원인이 인벤토리 포화라는 사실도, 해결책이 "아이템을 드랍(버리기)해서
빈칸을 만드는 것"이라는 사실도 알 방법이 없다.

알림함에는 이미 하루 1회 배치로 도는 인지 경로(#42)가 있지만, 유저가 실제로 슬롯을 채우는
순간(인벤토리 화면 진입) 그 자리에서 원인과 해결책을 즉시 보여주는 상시 안내는 없다. 그 결과
"가득 참 → 드랍 없음 → 계속 가득 참"이 굳어져 순환(가득 참 인지 → 드랍 → 빈칸 확보 → 다시 픽업)이
시작되지 않는다.

## 2. Solution

인벤토리 화면의 슬롯 프로그레스바 바로 아래에, 슬롯이 가득 찼을 때만 나타나는 상시 안내 메시지를
추가한다. 메시지는 "왜 배지를 못 받는지"와 "무엇을 하면 되는지"를 함께 전달하고, 바로 아래에 CTA
버튼을 두어 기존 드랍(버리기) 흐름으로 즉시 진입시킨다. 슬롯이 다시 여유로워지면 안내는 자동으로
사라진다(저장하지 않고 매번 조회 시점 상태로 렌더).

드랍은 애초에 체크인 지점(POI) 근처에서만 가능하도록 설계돼 있다 — `/api/drops`가 poi_id와
사용자 위치가 그 POI 반경(500m) 안일 것을 강제한다. 인벤토리 화면은 위치·POI 컨텍스트가 없는
화면이라 그 자리에서 드랍을 바로 열 수 없으므로(2026-09-12, 구현 착수 중 확인), CTA는 드랍
시트를 직접 열지 않고 **드랍 지도 화면(`/drops`)으로 이동시킨다.** "체크인 지점에 가서 드랍해야
빈칸이 생긴다"는 인과관계 자체를 유저에게 가르치는 것이 목적이므로, 이 화면 전환이 곧 그
가르침이다.

## 3. User Stories

1. 인벤토리가 가득 찬 유저로서, 인벤토리 화면에 들어갔을 때 슬롯이 가득 찼다는 사실을 프로그레스바만
   보고 추측하는 게 아니라 문장으로 명확히 안내받고 싶다.
2. 인벤토리가 가득 찬 유저로서, 이 상태에서 액티비티를 동기화해도 아이템배지가 나오지 않는다는
   인과관계를 안내 문구에서 바로 이해하고 싶다.
3. 인벤토리가 가득 찬 유저로서, 안내를 읽은 직후 "그럼 뭘 하면 되는지"를 바로 실행할 수 있는 버튼을
   같은 화면에서 찾고 싶다.
4. 인벤토리가 가득 찬 유저로서, "드랍하기" CTA를 누르면 별도 설명 없이도 드랍 지도 화면(`/drops`)으로
   이동해, 근처 체크인 지점에서 아이템을 버리면 빈칸이 생긴다는 사실을 자연스럽게 알고 싶다.
5. 체크인 지점에서 아이템을 하나 이상 드랍한 유저로서, 다시 인벤토리 화면으로 돌아왔을 때 슬롯 여유가
   반영되어 안내 메시지가 사라진 것을 확인하고 싶다.
6. 슬롯에 여유가 있는 유저로서, 평소에는 이 안내 메시지를 전혀 보고 싶지 않다 — 가득 찼을 때만
   나타나야 한다.
7. 슬롯이 정확히 꽉 차기 직전(예: 49/50)인 유저로서, 아직 발급이 막힌 상태가 아니므로 이 상시
   안내가 아니라 기존 배치 알림(#42, 근접 임계치)의 영역임을 인지한다 — 이번 상시 안내는 "이미 꽉 찬"
   상태에서만 노출된다.
8. 아이템배지를 처음 받아보는 신규 유저로서, 슬롯이 50개로 제한된다는 사실 자체를 이 안내를 통해
   처음 인지하게 되더라도 문구만으로 이해할 수 있어야 한다.
9. 알림함에서 #42(인벤토리 포화) 소식을 보고 `/inventory`로 착지한 유저로서, 도착한 화면에서 알림과
   같은 원인·해결책을 다시 확인할 수 있어야 한다 — 알림함과 인벤토리 화면의 메시지가 서로 모순되지
   않아야 한다.
10. `/drops`로 이동했지만 아무것도 드랍하지 않고 인벤토리 화면으로 돌아온 유저로서, 안내 메시지가
    그대로 남아 있어(슬롯이 안 비었으므로) 상태가 꼬이지 않았음을 확인한다.
11. 아이템북 슬롯에 이미 장착된(`slotted_in` NOT NULL) 아이템만 갖고 있어 인벤토리 목록이 비어
    보이는 유저로서, 실제로는 `used_slots`가 가득 찼다면 빈 그리드 상태(`EmptyState`)와 무관하게
    안내 메시지는 정상적으로 노출되어야 한다.
12. 운영자로서, 이 안내가 UX 라이팅 가이드의 [현상 → 원인 → 해결책] 3단계 구조와 알림함 #42의
    고정 문구·용어(드랍·픽업 등)를 그대로 따르길 원한다 — 화면마다 다른 표현을 쓰면 유저가 같은
    상황을 다른 문제로 착각한다.

## 4. Implementation Decisions

- **대상 화면**: `app/(main)/inventory/page.tsx`. `ProgressBar`(현재 슬롯 프로그레스) 바로 아래,
  `d.inventory.slotsDetail` 텍스트와 같은 블록 안에 조건부 안내 문구를 추가한다. 새 화면을 만들지
  않는다.
- **노출 조건**: `remainingSlots === 0`(즉 `used_slots >= max_slots`)일 때만 렌더링. 서버 컴포넌트가
  매 요청마다 조회하는 현재 값 기준이므로 별도 상태 저장이 필요 없다 — 알림함 #42가 이미 채택한
  "렌더 시점 재평가" 원칙(§6-2)과 동일하게 간다.
- **문구**: [UX_WRITING_GUIDELINE.md](../../writing/UX_WRITING_GUIDELINE.md)의 [현상 → 원인 → 해결책] 3단계
  구조를 따르되, 알림함 #42의 톤·고정 용어(드랍·픽업)와 결이 어긋나지 않게 맞춘다. 정확한 최종
  카피는 UX 라이팅 검수 시점에 확정한다 — 이 PRD는 구조(현상: 가득 참 → 원인: 배지 미획득 →
  해결책: 드랍 CTA)만 고정한다.
- **CTA 버튼**: 안내 문구 바로 아래 "드랍하기" 버튼 하나. 클릭 시 `Link href="/drops"`로 드랍 지도
  화면으로 이동한다. 드랍 시트(`PoiCarouselModal`)나 `/api/drops`·`/api/inventory/items`의 계약은
  건드리지 않는다 — 이 CTA는 순수 네비게이션이며, 실제 드랍은 종전과 동일하게 그 화면에서 체크인
  지점을 골라 진행한다.
  - **드랍 시트를 인벤토리 화면에서 독립적으로 여는 방식은 채택하지 않는다.** `/api/drops`가
    poi_id + 500m 반경(`isUserNearPoi`) 검증을 강제하므로, 위치·POI 컨텍스트가 없는 인벤토리
    화면에서 시트를 열어도 실제 드랍은 API 단계에서 거부된다(2026-09-12 구현 착수 중 확인). 이
    제약을 풀려면 인벤토리 화면에 별도 지오로케이션·근처 POI 탐색 UX를 새로 설계하거나 API의 위치
    검증을 완화해야 하는데, 둘 다 이번 PRD 범위를 벗어난다.
- **드랍 후 갱신**: 유저가 `/drops`에서 드랍하고 인벤토리 화면으로 돌아오면, 서버 컴포넌트가 매
  요청마다 `used_slots`를 다시 조회하므로 별도 캐시 무효화 없이 최신 값이 반영된다.
- **아이템북 장착분 제외 원칙 유지**: 인벤토리 화면이 이미 `slotted_in IS NULL`인 아이템만 그리드에
  표시하는 것과 별개로, 안내 메시지 노출 조건은 `used_slots`(장착 여부와 무관하게 슬롯을 점유하는
  값) 기준을 그대로 쓴다 — 그리드가 비어 보여도 슬롯은 가득 찬 상태일 수 있다(user story 11).
- **배지엔진·알림 로직 변경 없음**: `drop-engine`의 `slot_full` 스킵 동작, 알림 #42의 배치 생성·
  경고 스타일 재평가 로직(`Notification/PRD.md` §3-⑧, §6-2)은 이번 PRD의 범위 밖이며 수정하지
  않는다.

## 5. Testing Decisions

- 좋은 테스트는 "안내가 어떤 조건에서 뜨고 지는가"라는 외부 관찰 가능한 동작만 검증하고, 컴포넌트
  내부 렌더 순서 같은 구현 디테일은 검증하지 않는다.
- 검증 대상:
  - `used_slots === max_slots`일 때 안내 문구와 CTA가 렌더되는지
  - `used_slots < max_slots`일 때(0개 포함) 안내가 렌더되지 않는지
  - CTA가 `/drops`로 이동하는 링크인지, 드랍 후 인벤토리 화면 재진입 시 슬롯 표시가 갱신되는지
- 프로젝트 내 유사 사례: 알림 #42의 "경고 스타일 유지 조건"을 렌더 시점에 재평가하는 로직
  (`lib/notifications/batch/account.ts`의 `selectInventoryFullDrafts`, `warning.ts`)이 조건부
  경고 노출의 선례이며, 같은 "저장하지 않고 매번 다시 판정" 패턴을 따른다.

## 6. Out of Scope

- 동기화 완료 화면(`SyncButton`)에서 `slot_full` 발생 사실을 별도로 토스트/모달로 즉시 알리는 것
  (사용자 확인: 인벤토리 상시 안내 + 기존 알림함 #42만으로 충분).
- 배지엔진의 슬롯 초과 처리 방식 변경(예: 자동으로 오래된 아이템을 밀어내는 정책, 대기열화).
- 알림 #42의 트리거 조건·배치 주기·문구 자체의 변경.
- 드랍 시트의 아이템 선택 UI·정렬·필터링 등 시트 내부 기능 개선(이미 존재하는 기능을 그대로
  둔다).
- 최대 슬롯 수(50개) 자체를 늘리거나 유료화하는 등의 정책 변경.
- 인벤토리 화면에서 위치 없이 즉시 드랍할 수 있게 하는 지오로케이션 UX 신규 설계, 또는
  `/api/drops`의 POI 반경 검증 완화 — 드랍은 체크인 지점에서만 가능하다는 기존 설계를 그대로
  유지한다.

## 7. Further Notes

- 최초 초안은 드랍 시트를 인벤토리 화면에서 독립적으로 여는 방식을 검토했으나, `/api/drops`의
  poi_id + 500m 반경 검증과 충돌해 채택하지 않았다(2026-09-12). CTA는 `/drops` 이동으로
  단순화했다 — "체크인 지점에서 드랍해야 빈칸이 생긴다"는 인과관계를 유저가 자연스럽게 학습하게
  하는 것이 원래 목적이었으므로, 이 단순화가 오히려 목적에 더 부합한다.
- 이번 상시 안내는 "가득 찼을 때"만 다룬다. "근접" 단계의 선제 안내는 알림이 담당한다(20261018_0056: 남은 칸 3개·1개 단계에 들어서는 순간 `inventory_slots_low`를 한 번씩, 꽉 찬 상태(0개)는 #42가 맡는다).
- 남은 칸이 1~3개일 때(20261018_0056) 인벤토리 화면은 안내 카드를 만들지 않고 칸 수 줄만 바꾼다. «{사용}/{최대}개 사용 중 · {남은 칸}개만 남았어요» 줄 전체를 `--foreground`로 올리고 «N개만 남았어요» 구간만 굵게 한다. 새 색·카드는 없고, 진행 막대 색도 바꾸지 않는다. 남은 칸 4개 이상은 평소 줄(`--muted`), 0개는 평소 줄에 안내 카드를 더한다.
- 가득 참 안내 카드 본문은 꽉 차도 동기화는 된다는 사실에 맞춰 «새 아이템 배지를 **바로** 받을 수 없어요»로 쓰고(새로 나온 아이템 배지는 보류로 남아 인벤토리를 비운 뒤 고를 수 있다, 8절), 해결 경로 장착·믹스·드랍을 모두 적는다.
- 장착 풀기는 인벤토리가 가득 차 있으면 `unslot_item_from_book`(마이그레이션 111)이 `inventory_full`로 거절한다. `DELETE /api/itembooks/[id]/slot`은 409에 `code: "inventory_full"`을 싣고 문구에 칸 수 숫자를 쓰지 않는다(칸 수는 어드민 정책값). 교체(swap)는 칸 수가 변하지 않아 허용한다.
- 컬렉션 상세의 «모두 해제하기»(티켓 20261028_1420)는 `DELETE /api/itembooks/[id]/slots`로 그 컬렉션에 장착한 배지 전부를 푼다. 소프트 삭제된 배지에 꽂힌 장착도 포함한다. 인벤토리 빈칸이 장착 수보다 적으면 아무것도 풀지 않고 409에 `code: "inventory_full"`을 싣는다(화면은 안내와 «인벤토리 보기» 링크를 보인다). 경합으로 중간에 가득 차면 해제한 수와 남은 수를 응답에 싣는다. 해제 한 건의 처리는 위 `unslot_item_from_book`을 그대로 쓰므로 새 SQL은 없다.
- 잠긴 개체의 장착·믹스·드랍이 막혔을 때(409 `locked_item_not_allowed`) 믹스는 결과 오버레이를 열지 않고 info 토스트, 드랍도 info 토스트로 낸다(오류 톤 아님). 컬렉션 장착은 SlotGrid의 기존 중립 배너가 서버 문구를 그대로 보인다. 컬렉션 완성 판정은 장착 슬롯에서만 센다. 잠긴 개체는 장착할 수 없어 완성에 들지 않는다(`completion-basis.ts`는 인벤토리를 입력으로 받지 않는다). «미장착 보유»를 세는 완성 가능·장착 가능 소식 조회도 잠긴 개체를 뺀다.
- 문구 최종본은 UX 라이팅 가이드 검수를 거쳐 확정한다. 이 PRD는 구조와 노출 조건까지만 고정한다.

## 8. 동기화 보류 고르기 화면 (JAM 2.0, 티켓 20261017_1425)

동기화로 받을 아이템 배지가 인벤토리 빈칸보다 많으면 서버가 전부 보류하고(`sync_pending_items`, 규칙은 `BADGE_ENGINE_UNIFIED.md` 아이템 배지 발급),
유저가 빈칸 수만큼 **정확히** 골라야 닫힌다. 고르지 않은 것은 받을 수 없고 다시 받을 수도 없다. 이 절은 그 화면 흐름을 고정한다
(위 1~7절의 «상시 안내»와는 별개 화면이다).

**화면**: 별도 오버레이(`PendingItemsPickOverlay`, z60, 430px 컬럼, 탭바 숨김, `main` 스크롤 잠금)다. MODULAR `BadgeRevealCarousel`의 선택 모드로
카드를 하나씩 넘겨 보며 카드 하단 토글(«고르기»/«골랐어요»)로 고른다. 선택된 카드는 안쪽 링과 체크 칩으로 구분한다. 헤더 패널에 «인벤토리에 담을 N개를
골라 주세요»와 «이번에 M개가 나왔어요», 푸터 패널에 «k/N개 골랐어요»(라이브 리전)·«고르지 않은 M-N개는 받을 수 없어요»(안 고른 것이 0개면 숨김)·«N개 담기»가 있다.
«N개 담기»는 정확히 N개일 때만 활성이다. 가득 선택하면 안 고른 카드의 토글은 비활성이고 고른 카드는 해제할 수 있다.

**확정 확인**: «N개 담기»를 누르면 같은 오버레이 안에서 푸터가 «이 N개만 담을까요?»와 [다시 고르기][N개 담기]로 바뀐다(두 버튼 같은 폭·같은 시각 무게,
«다시 고르기»는 선택을 유지). 확정 버튼을 눌러야만 `POST /api/strava/pending-items`를 보낸다. 제출 중에는 토글·버튼·닫기·Escape가 막히고 요청은 한 번만 나간다.

**칸이 0일 때**: 캐러셀 없이 안내 카드(«인벤토리가 가득 차서 받을 수 없어요»)를 보이고, [나중에](보류를 남기고 닫음)와 [받지 않고 닫기](빈 선택 `chosenIds: []`로
확정해 보류를 닫음) 두 버튼을 같은 무게로 둔다.

**오류**(오버레이 유지, 푸터 위 인라인 `role=alert`): 400 `wrong_count`는 선택을 유지하고 선택 화면으로 돌아간다, 400 `invalid_selection`은 목록을 다시 읽고 선택을 비운다,
409 `no_pending`은 이미 닫힌 것이라 오버레이를 닫고 화면을 새로 읽는다, 404·500·네트워크는 선택을 유지하고 다시 시도할 수 있다.

**세 진입 경로**(같은 오버레이): ① 앱을 열 때 — 레이아웃이 보류 개수를 읽어 내려 첫 마운트에서 자동으로 연다. «나중에»로 닫으면 같은 브라우저 세션(클라이언트 이동)에서는
다시 뜨지 않고 새로고침하면 다시 뜬다. 주소에 `reveal=1`(최초 Strava 연동 연출)이 있으면 그 연출이 끝난 뒤에 연다.
② 동기화 버튼이 409(`sync_pending_items`)를 받으면 고르기를 먼저 보이고, 마치면 동기화를 **한 번만** 다시 요청한다(두 번째 409면 멈춤). «나중에»면 안내 토스트만 보인다.
③ 동기화 응답(200)의 `pendingItems`가 0보다 크면 결과 연출보다 먼저 고르기를 보이고, 마치거나 닫은 뒤 획득 배지가 있으면 기존 결과 오버레이로 이어진다.

**후속 처리**: 보류에서 받은 개체도 바로 지급과 같이 `point_reward`가 있으면 포인트(`badge_point_reward`), 피드 `item_dropped`, 결산 알림이 이어진다
(고르기 API 성공 뒤 서버가 처리하고, 각 실패는 고르기 응답을 바꾸지 않는다).

**문구**: 단호·명확 톤(UX 라이팅 §2.3, 되돌릴 수 없는 결정)이며 키는 `d.syncPending.pick.*`다. 축하 연출·이모지를 쓰지 않고 버튼 라벨에 «확인»을 쓰지 않는다.

## 9. 잠긴 아이템 배지의 상태와 제한 (JAM 2.0, 티켓 20261018_0051 1회, 운영 로직 7.2~7.5절)

잠긴 아이템 배지는 따로 된 기능이 아니라 인벤토리 개체의 **상태**다. 어떤 아이템 배지인지는 얻을 때 이미 정해지고, 열기는 드러내는 일이다. 열기는 포인트를 내고 한 번에 하며, API 계약은 아래 «포인트로 열기», 화면은 «잠긴 아이템 배지 화면»이 원천이다.
저장 칸과 지급 함수는 `02_DATA_MODEL.md`의 `inventory_items`, 발급의 잠김 배정 규칙은 `BADGE_ENGINE_UNIFIED.md` §3.0이 원천이다. 이 절은 인벤토리 관점의 동작만 고정한다.

**잠기는 경우**: ① 잠김으로 만든 아이템 배지(`badges.always_locked`) ② 동기화·캡슐에서 나온 아이템 배지가 설정 확률(기본 25%)로 잠긴 채 배정됨 ③ 운영자가 지정한 보상(묶음 5).
무작위로 잠김을 정하는 것은 동기화와 캡슐뿐이다. 이미 있는 개체와 옛 지급 경로(믹스·보상·픽업·퀘스트)로 받은 개체는 열린 채다.

**잠긴 동안의 제한**(서버가 거절하고, 응답은 409와 코드 `locked_item_not_allowed`로 같다):
- 컬렉션 장착·교체: 거절. 장착 RPC가 올리는 트리거 오류도 같은 코드로 응답한다.
- 믹스 재료: 재료에 잠긴 개체가 섞이면 소각하기 전에 거절한다(재료·포인트·실패 이력 모두 그대로).
- 드랍: 묶음 4가 잠긴 채 드랍과 가린 모습을 만들 때까지 거절한다. 드랍 후보 목록(`GET /api/inventory/items`)은 잠긴 개체의 이름·그림을 가린다(아래 «가림 범위»).
  드랍 확인 시트에는 «채운 잼은 사라져요» 안내와 사라질 양 조회가 없다(티켓 20261028_1741 2회). 화면이 잼을 채우지 않으므로 알릴 양이 없다. 드랍 응답의 `lostFill`과 드랍 DB 함수는 U11 전까지 그대로 남는다(`02_DATA_MODEL.md`).
- 인벤토리 칸은 그대로 차지한다. 거절 문구는 `d.lockedItem.*`이고, 거절 전에 잠김을 미리 알리는 화면(잠김 표시 카드, 선택 막기)은 3-4·3-6이다.

**포인트**: 아이템 배지에 붙은 포인트는 열린 상태가 될 때 한 번 준다. 잠긴 채 받은 개체는 지급 때 포인트를 주지 않는다(동기화 바로 지급과 보류 고르기 모두).
잠긴 채 받은 개체는 연 때 주고(아래 «포인트로 열기»), 열린 채 받은 개체는 받을 때 준다. 옛 드랍 엔진이 주는 개체는 열린 채라 지금처럼 준다. 믹스 결과(티켓 20261019_1314 2회)도 같은 규칙이다: 열린 채 받으면 받을 때 일련번호마다 한 번(`inventory_items.point_awarded_at`으로 중복 방지)이고, 잠긴 채 받으면(레시피 `reward_locked`·배지 `always_locked`) 연 때 주며, 빈칸이 모자라 받지 않은 결과로 남으면 받을 때 이 규칙을 따른다. 미션 보상(티켓 20261019_1313)은 배지의 «잠김으로 만든 아이템 배지» 설정을 따른다 — 잠긴 배지는 잠긴 채 받고(포인트는 연 때), 그 밖에는 열린 채 받을 때 준다.

**보류 고르기**: 보류 조회(`GET /api/strava/pending-items`)는 잠긴 개체에 배지 id·이름·그림을 싣지 않고 `locked: true`와 등급(`rarity`)만 싣는다. 필요한 잼 값(`unlockRequired`)은 티켓 20261028_1741 2회에서 응답에서 뺐다.
응답 타입 `PendingItemView`는 `locked`로 갈리는 유니온(열린 개체 | 잠긴 개체)이고 화면은 `locked === true`로만 가른다(티켓 20261018_0051 2회).

**고르기 화면의 잠긴 카드**(채원 판정 2026-10-18): MODULAR `BadgeRevealCarousel`의 선택 모드 카드에서 그림 자리만 바뀐다. 항목에 선택 칸 `locked`가 있으면 그림·사람 모양 폴백 아이콘 대신
중립 «잠금 타일»(이미지 영역의 0.8배, 둥근 정사각, `--background` 바탕·1px `--border` 윤곽, 가운데 DS `LockIcon`·`--muted`)을 그린다. 등급은 기존 칩이 그리고(Common은 칩 없음)
등급 색 배경·그라데이션·글로우·모션은 쓰지 않는다. 이름 줄은 «잠긴 아이템 배지», 설명 줄은 숫자 없는 «포인트로 열 수 있어요»다(`d.lockedItem.card.description`, 티켓 20261028_1741 2회). 정확한 필요 포인트는 받은 뒤 잠긴 상세에서 보인다.
선택·선택됨·더 고를 수 없음·확정 확인은 열린 카드와 똑같이 동작한다. 열린 카드와 기존 호출부 화면은 달라지지 않는다. 열기 연출과 «열면 알 수 있어요» 같은 약속 문구는 3-3이다.

**가림 범위**(사용자 결정 2026-10-18): 어떤 아이템 배지인지 알 수 있는 값은 아래 네 곳에서 모두 가린다.
① 보류 조회: 위와 같다. ② 드랍 후보 목록: 잠긴 개체는 `badge_id`를 `locked:<등급>`으로, 이름을 «잠긴 아이템 배지»로 바꾸고 그림·일련번호 접두사를 비우며 `locked`와 `unlock_points_required`(개체 선택 행의 구분 값)를 싣는다. 필요한 잼 값(`unlock_required`)은 싣지 않는다
(드랍 목록이 `badge_id`로 묶으므로 등급이 다른 잠긴 개체가 한 카드로 섞이지 않게 등급별 키를 쓴다). ③ 활동 피드: 잠긴 채 받은 개체는 받을 때 `item_dropped`를 올리지 않는다(동기화로 받은 개체만 연 때 올린다. 캡슐에서 나온 잠긴 개체는 열어도 올리지 않는다. 아래 «채우기와 열기»의 열 때 소식).
④ 결산 알림: 결산 `item_badges`에 이름·배지·등급 없이 `locked: true`로만 담고 문구는 «잠긴 아이템 배지를 받았어요»(여럿이면 «잠긴 아이템 배지 N개를 받았어요»)다.
다른 종류와 섞이면 이름을 나열하지 않는 총량 문형(«배지 N개를 획득했어요»)으로 간다. 연 때는 동기화로 받은 개체만 `item_dropped`를 올린다(사용자 결정 2026-10-26, 티켓 20261026_1031). 캡슐에서 나온 잠긴 개체는 열어도 올리지 않는다.

**채우기와 열기**(티켓 20261018_0053, 운영 로직 7.2절): 저장·함수는 `02_DATA_MODEL.md`(마이그레이션 235)가 원천이고 이 절은 API 계약만 고정한다.
열기는 티켓 20261028_1737부터 **포인트를 내고 연다**(아래 «포인트로 열기»). 화면은 티켓 20261028_1741(U10)에서 바뀌어 **채우기를 부르지 않는다**. 채우기 API(`fill`)와 함수, 개체의 채운 양(`unlock_filled`)과 필요한 잼(`unlock_required`) 칸은 화면과 연결이 끊긴 채 함수를 지우는 U11까지 남아 있다. 그래서 아래 채우기 줄은 지금 서버에 있는 계약이다.
- `GET /api/inventory/items/[itemId]/lock`: 내 개체의 `locked`·`required`·`filled`·`remaining`·`balance`·`openable`(잠겨 있고 다 채움, 인벤토리 빈칸은 보지 않는다)와 `pointsRequired`·`pointBalance`(아래 «포인트로 열기»). 잠긴 상세 서버 페이지는 이 가운데 `pointsRequired`·`pointBalance`만 화면에 내린다. 이름·그림·설명·컬렉션·트라이브·일련번호는 싣지 않는다. 이용 정지 중에도 허용한다.
- `POST /api/inventory/items/[itemId]/fill { amount? }`: 한 번에 개체 하나. 기본값은 남은 양이고 가진 잼이 모자라면 가진 만큼, 줄여서 나눠 채울 수 있고, 남은 양보다 많이는 채울 수 없고, 채운 잼은 꺼낼 수 없다. 응답은 `applied`·`required`·`filled`·`remaining`·`balance`·`openable`이다.
  이용 정지 중 403(`user_suspended`), `already_full`·`exceeds_remaining`(남은 양 포함)·`invalid_amount` 400, `insufficient_jam`·`not_locked` 409, `item_not_found` 404.
- `POST /api/inventory/items/[itemId]/open`: 필요한 포인트를 내고 같은 개체가 열린 상태가 된다(일련번호 그대로, 새로 뽑지 않음, 확률 없음). 채우기를 마칠 필요가 없다. 인벤토리가 가득 차 있어도 열린다(이미 칸을 차지한다). 한 번 연 것은 다시 잠기지 않고, 동시에 두 번 열어도 한 번만 열린다(두 번째는 `not_locked` 409).
  성공 응답에만 이름·그림·설명·등급·컬렉션·트라이브·일련번호와 준 포인트(`pointsAwarded`)를 싣고, 낸 포인트(`pointsSpent`)와 연 뒤 잔액(`pointBalance`)은 이름·그림과 달리 항상 싣는다. 열기는 확정됐고 정보 조회만 실패한 드문 경우 `item`은 null이다.
  이용 정지 중 403, `insufficient_points`(`required`·`balance` 포함)·`not_locked` 409, `item_not_found` 404.
- 이용 정지 중에는 열기(와 남아 있는 채우기 API)를 막고 개체는 그대로 닫혀 있다. 트라이브가 바뀌어도 잠긴 개체는 그대로다.
- 포인트: 배지 포인트는 열린 상태가 될 때 연 유저에게 한 번만 준다(`inventory_items.point_awarded_at`이 «이미 줬다» 기록). DB 안에서 주므로 포인트 알림(`notifyPointChange`)은 나가지 않는다. 열기에 드는 포인트는 아래 «포인트로 열기»다.
- 이력: 열 때 `unlocked`를 `inventory_item_events`에 남긴다(채우기 API가 남아 있는 동안은 채울 때마다 `filled`도 남긴다).
- 열 때의 소식과 피드(티켓 20261026_1031, 사용자 결정 2026-10-26): 열기 경로(`openLockedItem`)가 열기 확정 뒤 둘을 낸다. 포인트 소식은 `pointsAwarded`가 0보다 클 때 활동 결산의 «포인트» 꼬리로 한 번 낸다.
  활동 피드 `item_dropped`는 받을 때는 올리지 않았으므로(위 «가림 범위» ③) 동기화로 받은 개체만 연 때 한 번 올린다. 칸(`inventory_item_id`·`badge_id`·`badge_name`·`badge_image_url`·`rarity`·`poi_name`·`tribe_name`·`is_last_piece`,
  포인트를 준 경우 `point_reward`)은 열린 채 받은 개체의 피드와 같고(`recordItemDroppedFeed`), 시각은 연 때이며 활동에는 묶지 않는다. 포인트가 0이어도 올리고, 연 개체의 정보를 읽지 못하면 올리지 않는다.
  출처는 발급 기록 `item_issue_log`에서 개체 id로 가장 앞선 한 줄의 경로(`route`)를 읽어 가른다. `capsule`이면 올리지 않고(캡슐 개봉 결과는 피드에 올리지 않는다, 운영 로직 15.3절), `sync`이거나 발급 기록 행이 없으면(운영자가 지정한 개체 등) 올리며, 경로를 읽다가 오류가 나면 올리지 않고 기록만 남긴다. 포인트 소식은 출처와 무관하게 나간다.
  피드와 소식은 서로와 열기 응답에 영향을 주지 않는다. 두 번째 열기는 `not_locked`로 거절돼 한 번만 올라간다. 화면은 3-4에서 정한다.

**포인트로 열기**(티켓 20261028_1737 1~3회, 운영 로직 7.2·14.1절): 잠긴 개체는 등급별 포인트를 내고 한 번에 연다. 저장·함수·트리거·원장 구조는 `02_DATA_MODEL.md` 3장 «잠긴 아이템 배지를 포인트로 여는 구조»(마이그레이션 300·304)가 원천이고 이 절은 앱 계약만 고정한다.
- 필요한 포인트(`pointsRequired`)는 개체에 고정된 값이다. 개체에 값이 없고 잠겨 있으면 등급별 정책값(`jam_policy.locked_points_*`, 등급이 없으면 common)이고, 열린 개체는 null이다. 퀘스트의 첫 잠긴 배지는 0으로 고정되므로 포인트 없이 열린다.
- 잔액(`pointBalance`)은 지갑이 없으면 0이다. 잔액이 모자라면 열리지 않고 `insufficient_points` 409(`required`·`balance`)이며 개체·잔액·원장이 그대로다. 필요한 포인트가 0이면 차감 줄이 없다.
- 원장에는 «잠긴 배지 열기 −N»(사유 `locked_unlock_cost`, 개체 연결)과 «아이템 배지 획득 +M»(사유 `badge_point_reward`, 배지 포인트가 있고 아직 주지 않았을 때만) 두 줄이 남는다.
- 열기가 확정된 뒤의 후속(서비스 활동 잼 `locked_unlock`, 퀘스트 완료 처리, 포인트 소식, 피드)은 위와 같고 `pointsAwarded`가 0보다 클 때만 포인트 소식이 나간다. 응답 계약은 `src/lib/inventory/lockedItemFill-contract.ts`다.
- 어드민 «밸런스 설정» 잠긴 아이템 배지 구역에서 등급별 값을 바꾼다. 바꿔도 이미 배정된 개체의 값은 바뀌지 않는다.
- 화면은 티켓 20261028_1741(U10)에서 바꿨다. 아래 «잠긴 아이템 배지 화면»이 현재 화면이다.

### 잠긴 아이템 배지 화면 (티켓 20261018_0054 2회, 20261028_1741 1~3회, 채원 판정 2026-10-30)

화면은 서버가 정한 값(필요 포인트·가진 포인트)을 그대로 그린다. 규칙을 다시 계산하지 않는다. 잼을 채우는 입력, 게이지, 가진 잼 줄은 이 화면 어디에도 없다. 문구는 `d.lockedItem`(카드·상세)이 원천이다.

- **인벤토리 그리드의 잠김 카드**: 서버 페이지(`inventory/page.tsx`)가 잠긴 개체의 이름·그림을 **클라이언트로 내리는 props에서 비운다**(등급만 싣는다).
  화면에서 가리는 것이 아니라 RSC 페이로드에 값이 없다. 카드는 서비스 쪽 `BadgeGridCard`의 `locked`다: 같은 면(`--surface`·1px `--border`·`--radius-2xl`), 썸네일 자리에 `LockedTile`, 이름 줄은 «잠긴 아이템 배지»,
  그 아래 등급 칩이 전부다. **게이지는 없다.** `locked`이면 `name`·`imageUrl`이 넘어와도 그리지 않는다. (디자인 시스템 쪽 `design-system/components/patterns/BadgeGridCard.*` 사본에는 옛 게이지 입력이 남아 서비스와 어긋나 있고, 서비스 코드가 원천이다.)
- **잠긴 상세** `/inventory/[itemId]`: 잠긴 개체면 `/badges/...`로 리다이렉트하지 않고 `LockedItemDetail`을 그린다(주소에 배지 id가 실리면 이름·그림이 드러나기 때문이다).
  클라이언트 props는 등급·필요 포인트(`pointsRequired`)·가진 포인트(`pointBalance`)·얻은 날과 경로뿐이고 배지 id·이름·그림·설명·일련번호와 잼 값은 없다. 화면 위에서 아래로: 큰 `LockedTile`, 등급 칩과 «잠김» 칩, «잠긴 아이템 배지»(제목),
  «열면 어떤 아이템 배지인지 볼 수 있어요»(설명), 포인트 블록, «얻은 날 · 경로» 한 줄, «열기» 버튼 하나. 이력 시트는 잠긴 상태에서 노출하지 않는다. 상세의 얻은 날 라벨은 «획득일»이 아니라 «얻은 날»이다(열기는 획득이 아니다, 운영 로직 7.2절).
- **포인트 블록**(서버 판정이 최종이고 화면은 미리 알릴 뿐이다):
  - 필요 포인트를 알고 0보다 크면 두 줄이다. «필요 포인트»(큰 숫자)와 «가진 포인트»(한 단계 작은 숫자). 두 숫자는 `--link` 색이다.
  - 가진 포인트가 필요 포인트보다 모자라면 두 줄 아래에 «{short} 포인트가 모자라서 지금은 열 수 없어요. 포인트가 생기면 열 수 있어요.»(`{short}` = 필요 − 가진) 안내를 보이고 «열기» 버튼을 막는다.
  - 필요 포인트가 0이면 두 줄 대신 «포인트 없이 열 수 있어요» 한 줄이고 버튼은 활성이다.
  - 필요 포인트를 모르면(null, 정책값을 읽지 못한 경우) 포인트 블록 없이 버튼이 활성이다. 열 수 있는지는 서버가 정책값으로 판정한다.
- **열기 뒤 제자리 전환**: 같은 화면에서 타일이 그림으로 크로스페이드하고(그림은 scale .96 → 1), 제목과 설명이 이름과 설명으로 바뀐다. 포인트 블록은 접히고, «잠김» 칩은 사라지며, 등급 칩은 그대로다.
  그 자리에 순서대로 나온다: 일련번호(`ItemSerialCode`, 열기 응답의 `serialPrefix`+`serialNumber`), 컬렉션·트라이브 한 줄씩, 낸 포인트(`pointsSpent > 0`, «{n} 포인트를 냈어요»), 받은 포인트(`pointsAwarded > 0`, «배지 보상으로 {n} 포인트를 받았어요»), 그리고 «열기» 버튼 자리에 «배지 상세 보기» 링크(`/badges/{badgeId}?item={itemId}&from=inventory`).
  낸 포인트와 받은 포인트를 한 줄로 합치지 않는다. 열기가 포인트를 받는 원인처럼 읽히지 않게 받은 쪽은 «배지 보상»이라고 밝힌다(열기는 획득이 아니다). 응답의 `item`이 null이면 전환 없이 서버 페이지를 다시 읽어 열린 개체를 배지 상세로 보낸다. 높은 등급 축하 연출은 없다.
- **응답 처리**: 이용 정지 403은 일반 실패가 아니라 info 토스트다(`d.suspension.lockedItemOpenBlocked`, 버튼은 미리 막지 않는다).
  `insufficient_points` 409는 info 토스트(서버 문구)를 낸 뒤 응답의 `required`·`balance`로 화면의 포인트를 바로 바꾸고 서버 값을 다시 읽는다(위 모자람 안내가 곧바로 보인다). 두 값 중 하나라도 숫자가 아니면 일반 거절로 처리한다.
  그 밖의 거절은 서버 문구를 그대로 보여 주고 서버 값을 다시 읽는다. `not_locked`는 안내 뒤 다시 읽어 서버 페이지가 배지 상세로 보내고, `item_not_found`는 안내 뒤 인벤토리로 이동한다. 그 밖의 실패는 `d.lockedItem.open.failed`(«… 포인트는 그대로 남아 있어요 …»)다.
- **열기 응답의 일련번호 접두사**: `POST .../open` 성공 응답에 `serialPrefix`(앞 4자, 읽지 못하면 null)를 더했다. 화면의 `ItemSerialCode`가 번호와 함께 쓴다. 거절 응답에는 싣지 않는다.

**다른 표면의 표시 규칙**(티켓 20261028_1741 2회, 채원 판정 2026-10-30): 고르는 표면에는 구분 값이 필요하고 확인하는 표면에는 필요 없다. 줍기는 무료이고 포인트는 열 때 내는 값이라 줍을지 말지의 판단 정보가 아니다. 정확한 값은 받은 뒤 잠긴 상세의 «필요 포인트»에서 본다.
- 숫자 없는 «포인트로 열 수 있어요»(`d.lockedItem.card.description`): 보류 고르기 카드(위), 믹스 보류 결과 시트, 보상 리빌(`BadgeRevealOverlay`), 스트라바 보류 선택(`PendingItemsPickOverlay`).
- 드랍 줍기 시트(`BadgeDetailSheet`): 잠긴 개체는 «픽업한 뒤에 포인트로 열 수 있어요» 한 줄만 보인다(`d.drops.pickupLockedHint`).
- 같은 등급 잠긴 개체 중에서 고르는 선택 시트 행(`ItemCandidateRow`)만 «{n} 포인트 필요»(`requiredChip`)를 보인다. 0이면 «포인트 없이 열 수 있어요», 값을 모르면(null) 등급 칩만 보인다. 값은 `unlock_points_required`다.
- 필요한 잼 값(`unlock_required`)은 줍기 응답·인벤토리 응답·믹스 응답·보류 조회에서 빠졌다. 캡슐 쪽 계약(`RevealBadge.unlockRequired`)은 캡슐 티켓(U8)이 정리할 때까지 남는다.

**가림 보강**(열기 전에는 이름·그림·설명·컬렉션·트라이브·일련번호를 어느 화면에도 보이지 않는다, 운영 로직 7.3절). 서버에서 잠긴 개체를 거르는 곳:
- 배지 상세 `/badges/[id]?item=`: `?item`이 내 잠긴 개체면 화면을 그리지 않고 `/inventory/[itemId]`로 보낸다. 그 밖의 경우에도 잠긴 개체는 보유 목록에서 빠져 대표 일련번호·이력 목록·획득 여부·만료 안내에 쓰이지 않는다.
- 프로필 `/{username}`(발견한 컬렉션 수, 레거시 피드 합성), `/{username}/collections`, `GET /api/users/[username]/itembooks`, `GET /api/itembooks`, `/badges`의 컬렉션 발견 판정: 잠긴 개체는 «어느 컬렉션의 배지를 얻었는지»가 드러나므로 세지 않는다(열면 센다).
- 컬렉션 상세 `/collections/[id]`의 장착 후보, 믹스 `/combine`의 재료 후보: 잠긴 개체는 쓸 수 없고 일련번호·이름이 드러나므로 후보에서 뺀다.
- 이력 API `GET /api/inventory/items/[itemId]/history`: 응답은 얻은 날과 경로, 드랍·픽업 이벤트(지점·유저 이름)만 싣고 개체 정보 표를 읽지 않아 가림 대상 값이 구조상 없다(시험으로 고정).

## 10. 캡슐 보상이 빈칸보다 많을 때 (JAM 2.0, 티켓 20261028_1734, 운영 로직 5.2·6.4절)

인벤토리 빈칸이 캡슐에서 나올 수 있는 최대 개수(확정 + 보너스)보다 적을 때 캡슐은 «열 수 없음»이 아니라 «보상 보류»로 처리한다. 규칙(최대 2개, 순서, 받기, 잼 소멸, 알림 단계)의 원천은 운영 로직 5.2절이고, 이 절은 인벤토리와 맞닿는 사실만 둔다. 저장과 함수는 `02_DATA_MODEL.md` 9-4가 원천이다.

- 빈칸이 모자라면 캡슐을 열지 않고 `capsule_pending_rewards`에 한 줄(챕터, 채운 양, 닿은 시각)을 둔다. 아이템은 정해 두지 않고 받을 때 추첨하므로 보류 때문에 인벤토리 칸을 쓰지 않는다.
- 받기(`POST /api/capsule/claim`)는 오래된 보류부터 하나씩 받고, 빈칸이 나올 수 있는 최대 개수 이상일 때만 지급한다. 빈칸이 모자라면 거기서 멈추고 남은 보상은 보류로 둔다. 빈칸을 만드는 방법(장착 풀기, 믹스, 드랍)은 이 PRD 1~7절과 같다.
- 받고 나서 남은 칸이 3칸이나 1칸 이하가 되면 남은 칸 알림(`inventory_slots_low`, 알림 PRD #46)이 평소처럼 나간다.
- 보상을 포기하는 동작은 없다.

> **구현 상태** (티켓 20261028_1734, 2026-10-29)
