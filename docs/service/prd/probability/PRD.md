# 확률 안내 — PRD

> 정책의 출처는 `docs/plan/jam2/10 JAM 2.0 서비스 운영 로직.md` 18.3절(확률 안내)과 18.4절(결제)이고, 이 문서는 그 정책을 서버와 화면이 어떻게 지키는지 코드 기준으로 적는다.
> 값을 정하는 곳은 5.4절(캡슐), 6.7절(동기화), 9.4절(시스템 드랍)이다. 만든 티켓: 20261021_1250(1회, 페이지·입구·읽기 모듈), 20261022_1700(바뀐 날짜 표를 변경 이력에서 읽기).

## 1. 범위

확률이 들어간 보상은 세 가지이고 모두 이 페이지가 표로 보인다.

| 보상 | 보이는 확률 |
|---|---|
| 동기화로 받는 아이템 배지 | 확정 개수(등산은 따로), 보너스 기회 수와 한 번의 확률, 잠길 확률, 등급 |
| 캡슐 | 확정 개수, 더 나올 개수와 확률, 다른 트라이브의 것일 확률, 잠길 확률, 등급 |
| 시스템 드랍 | 등급 |

확률이 없는 것(믹스, 잠긴 아이템 배지 열기, 액티비티 배지, 체크인 배지, 미션 보상, 유저가 직접 놓은 드랍)은 표 없이 한 문단으로 알린다. 유료 결제가 없다는 한 줄(18.4절)이 머리에 있다.
보정 장치(Epic 보정과 Common 연속 보정)는 접지 않고 사실 문장으로만 적는다. 개인별 남은 횟수, 확률 계산기, 「지금 열면」 같은 개인화 표시는 두지 않는다. 이 페이지는 누구에게나 같다.

## 2. 값의 원천과 읽기

값은 설정 표에서 서버가 읽어 만든다. 문자열로 적어 두지 않으므로 설정을 바꾸면 페이지가 따라 바뀐다(`force-dynamic`, 요청마다 다시 읽는다).

| 섹션 | 표 | 읽는 칸 | 단위 |
|---|---|---|---|
| 동기화 | `jam_policy` | `sync_item_guaranteed`, `sync_item_guaranteed_hiking`, `sync_item_bonus_rolls`, `sync_item_bonus_jam_divisor`, `sync_item_bonus_max_probability`, `sync_rarity_*`, `locked_roll_probability` | 등급은 퍼센트(84), 확률 칸은 0~1(0.25) |
| 캡슐 | `capsule_policy`와 `jam_policy` | `guaranteed_count`, `bonus_count`, `bonus_probability`, `other_tribe_probability`, `rarity_*`와 `locked_roll_probability` | 등급은 퍼센트(70), 확률 칸은 0~1(0.2) |
| 보정 장치 | 두 표 | `pity_epic_threshold`, `common_streak_threshold` | 횟수 |
| 시스템 드랍 | `ambient_drop_config` | `rarity_mode`, `rarity_*` | 등급은 0~1(1, 0, 0, 0) |

- 필요한 칸만 이름으로 읽는다(`select('*')`를 쓰지 않는다). `jam_policy`에는 대량 수령 경보 기준(`mass_earn_alert_*`)이 같은 행에 있고, 어뷰징 임계값은 공개하지 않는 것이 원칙이다.
- 잠길 확률은 동기화와 캡슐이 한 값(`jam_policy.locked_roll_probability`)이라 캡슐 표에도 같은 값이 나온다.
- 확률은 숫자에 %를 붙이고 소수는 필요한 자리까지만 쓴다. 0.07처럼 부동소수 오차가 나는 값은 소수 둘째 자리로 정리한다(`Number((x * 100).toFixed(2))`).
- 시스템 드랍은 `rarity_mode`가 `explicit`이면 등급 표(0%인 줄도 그대로), `random`이면 표 없이 설명 문장이다. `random`은 놓을 때마다 등급 분포를 무작위로 정해 고정된 표를 만들 수 없다. `category_mode`, `auto_enabled` 같은 설정은 보이지 않는다(옛 `all_random` 칸은 코드가 읽지 않는다).
- 0인 값: 확정 개수 0은 「0개」, 보너스 개수나 보너스 기회가 0이면 「없음」으로 쓰고 보너스 확률 줄은 뺀다.

### 읽기 실패

`getCapsulePolicy`, `getJamPolicy`, `getAmbientDropConfig`는 읽기 실패에 코드 상수 사본(`DEFAULT_*`)을 조용히 돌려준다. 확률 안내에서는 틀린 확률을 보이는 것이 더 나쁘므로 이 함수들을 쓰지 않는다.
`jam-web/src/lib/probability/disclosure.ts`가 세 표를 직접 읽고, 두 정책 파일의 칸별 검사(`VALIDATORS`)로 값을 확인한다.

| 실패 | 보이는 것 |
|---|---|
| `capsule_policy` 또는 `jam_policy`의 조회 오류·행 없음·예외, 칸 하나라도 검사 실패, 등급 네 칸 합계가 100이 아님 | 동기화·캡슐·보정 장치 세 섹션 모두 제목은 두고 표 자리에 안내 한 개 |
| `ambient_drop_config`의 조회 오류·행 없음·예외, 모드가 비정상, 등급 칸이 범위 밖이거나 합계가 1이 아님 | 시스템 드랍 섹션만 같은 안내. 다른 섹션은 그대로 |
| `balance_setting_changes`의 조회 오류·예외, 결과가 목록이 아님 | 바뀐 날짜 섹션은 «처음 열었어요» 줄만 남기고, 표 아래에 같은 안내 한 개. 다른 섹션은 그대로 (5절) |

- 안내 문구는 「지금 불러오지 못했어요. 잠시 뒤 새로고침해 주세요.」(`InlineNotice`)이고 숫자는 하나도 그리지 않는다. 원인은 추측해서 적지 않는다.
- 값이 없고 스스로 뜻이 닫히는 문장(확률이 없는 것, 바뀐 날짜 머리 문장, 트라이브 후보 문장, 시스템 드랍의 낮춤 규칙)은 읽기가 실패해도 그대로 둔다.
  표의 숫자를 한정하는 「이 확률은 처음 뽑는 등급이에요」는 가리킬 표가 없으므로 표와 함께 빠진다(동기화·캡슐 섹션은 안내 한 개만 남는다, 티켓 20261021_1250 머지 점검).

## 3. 화면

- 경로는 `/probability`이다. 법 페이지(`/privacy`, `/location-terms`)와 같은 `(legal)` 그룹이라 로그인 확인이 없고, 상단 바는 뒤로 가기와 제목 「확률 안내」뿐이다(`LegalTopNav`). 배경은 크림 단색이다.
- `proxy.ts` 공개 경로 목록에 `/probability`가 있어 로그인하지 않은 사람도 열 수 있다(정지 계정·탈퇴 대기도 같다). 법 페이지처럼 `metadata`는 두지 않는다.
- 섹션 순서: 머리(설명과 유료 결제 없음 한 줄) → 동기화로 받는 아이템 배지 → 캡슐 → 시스템 드랍 → 확률이 없는 것 → 보정 장치 → 바뀐 날짜.
- 표는 라벨(`th scope="row"`)과 값(`td`) 두 칸짜리 의미 있는 `<table>`이고 표마다 화면에 보이지 않는 `caption`이 있다. 열이 둘뿐이라 가로 스크롤 래퍼가 없다. 등급은 영문 서열 순(Common → Mystic)이고 글자로만 구분한다. 색, 그라데이션, 그래프, 아이콘, 진입 애니메이션, 숫자 카운트업을 쓰지 않는다.
- 표 안의 숫자는 초록(`--link`)으로 강조하지 않는다. 확률이 눈에 띄는 보상처럼 읽히지 않게 하려는 것이다.
- 동기화·캡슐 등급 표 바로 아래에 「이 확률은 처음 뽑는 등급이에요. 그 등급에 받을 수 있는 아이템 배지가 없으면 한 등급씩 낮춰서 무작위로 골라요.」가 있다. 캡슐 개수 표 아래에는 다른 트라이브 후보 문장이 있다.
  시스템 드랍은 낮추는 방식이 다르다. 높은 등급에서 내려가지 않고 Common부터 Rare, Epic, Mystic 순서로 찾아 아이템 배지가 있는 첫 등급에서 고른다(`jam-web/src/lib/ambient-drop/rarity.ts`의 `fallbackPickBadge`).
  그래서 시스템 드랍 표 아래 문장은 동기화·캡슐과 다르게 쓴다.
- 보정 장치 목록 아래에도 「그 등급에 받을 수 있는 아이템 배지가 없으면 한 등급씩 낮춰서 무작위로 골라요.」가 한 줄 있다. 보정으로 정해진 등급(Epic 이상, Rare 이상)도 캡슐·동기화와 같은 낮춤 함수(`pickWithRarityFallback`)를 지나므로, 지금처럼 발급 가능한 아이템 배지가 Common뿐이어도 목록 문장이 거짓이 되지 않게 하려는 것이다(사용자 결정 2, 티켓 20261021_1250).
- 문구 규칙은 [UX 라이팅 가이드](../../writing/UX_WRITING_GUIDELINE.md)의 확률 표기 절이 정본이다.

## 4. 입구

| 입구 | 위치 | 문구 |
|---|---|---|
| 푸터 | 링크 열 맨 아래(위치기반서비스 이용약관 다음) | 「확률 안내」 |
| 캡슐 시트 | 본문 맨 아래(가진 잼 다음 줄). 채우는 중·열 수 있음·빈칸 모자람에서 같은 자리이고 채우기 단계, 푸터, 열기 결과 오버레이에는 없다. 누르면 시트를 닫는다 | 「확률 안내」 |

- 푸터는 로그인 화면과 `(legal)` 페이지에 없고 로그인 화면의 약관 동의 문장에도 링크가 없다. 로그아웃 방문자는 주소를 직접 알아야 한다(공개 경로이지만 입구는 없다).
- 캡슐 시트 링크는 숫자·퍼센트·아이콘이 없는 조용한 밑줄 링크(`text-sm text-muted`, 44px 터치 영역)이다. 열기 결과 화면에 확률 링크를 두면 결과를 확률로 읽게 되므로 더하지 않는다.

## 5. 바뀐 날짜

표는 어드민 «밸런스 설정»(`/admin/balance`, 티켓 `20261022_1132`)의 변경 이력 `balance_setting_changes`(마이그레이션 285)에서 서버가 읽어 만든다(`jam-web/src/lib/probability/changeLog.ts`, 티켓 `20261022_1700`).
확률 안내에 반영되는 칸을 어드민에서 저장하면, 새로고침한 뒤 표 맨 위에 그날 날짜와 바뀐 내용이 한 줄 생긴다. 코드에 줄을 더하는 일은 없다.

| 항목 | 규칙 |
|---|---|
| 읽는 행 | `affects_disclosure = true`인 행만, `created_at` 내림차순(최신이 위). 읽는 칸은 `section_key, changes, created_at`뿐이라 변경 메모(`note`)와 바꾼 사람(`changed_by`)은 화면과 HTML에 실리지 않는다. 서버에서 service_role 클라이언트로만 읽는다(이력 표는 RLS 정책이 없다) |
| 한 줄 | 저장 한 번이 한 줄이다. 칸이 여럿이어도 같다. 같은 날 저장이 여러 번이면 날짜가 반복된다 |
| 날짜 | `created_at`을 한국 표준시로 바꿔 「2026년 10월 23일」로 쓴다. 연도를 포함하고 날짜 칸은 줄바꿈이 없다 |
| 문장 | 「{이름}{을/를} {전}에서 {후}{로/으로} 바꿨어요」. 칸이 여럿이면 쉼표로 잇고 「바꿨어요」는 끝에 한 번만 쓴다. 마침표가 없다. 조사는 이름 끝 글자와 단위 글자의 받침으로 가르고(「%」「개」는 「로」, 「번」「잼」은 「으로」) 값에는 항상 단위를 붙인다. 값은 표 위쪽 숫자와 같은 서식이다(84%, 2.5%, 0%) |
| 쓰지 않는 말 | 「올렸어요」「낮췄어요」 같은 방향어, 화살표, 엠대시, 「NEW」, 강조 색. 동사는 「바꿨어요」뿐이다(UX Writing 3.3, 다시 열기를 부추기지 않는다). 칸이 여럿이어도 「외 N개」로 줄이지 않는다 |
| 칸 이름 | 확률 안내가 읽는 20칸(`JAM_COLUMNS` 11칸, `CAPSULE_COLUMNS` 9칸)마다 유저용 이름이 있다(`JAM_COLUMN_LABELS`·`CAPSULE_COLUMN_LABELS`). 같은 「Common 확률」이 두 구역에 있어 「동기화 Common 확률」「캡슐 Common 확률」처럼 구역을 앞에 붙인다. 동기화와 캡슐이 한 값으로 쓰는 두 칸은 「동기화와 캡슐의 …」로 쓴다. 운영 이름(「보정 1」)과 내부 칸 이름을 쓰지 않는다 |
| 구역과 함께 읽기 | 이력 행의 구역 키(`sync`, `capsule`)가 어느 칸 목록을 쓸지 정한다. 칸 이름만 같은 다른 구역(예: 나중에 이력을 쓸 시스템 드랍의 `rarity_common`)의 칸을 캡슐 칸으로 읽지 않는다 |
| 표에 없는 칸 | 퀘스트 전 두 칸과 챕터별 채울 양처럼 확률 안내가 읽지 않는 칸은 내부 이름을 보이지 않는다. 전부 모르는 칸이면 「확률 안내의 값을 바꿨어요」, 일부만 모르면 끝에 「그 밖의 값도」를 붙인다 |
| 맨 아래 줄 | 「2026년 10월 21일 / 확률 안내를 처음 열었어요」는 이력에 없으므로 `page.tsx`의 상수 한 줄(`FIRST_OPENED_ROW`)이고 항상 이력 줄 아래에 붙는다. 날짜는 임시값이다. 시행일은 출시 전에 사용자가 확정한다 |
| 머리 문장 | 「확률 안내에 적힌 값을 바꾸면 바뀐 날짜와 내용을 여기에 적어요.」 |
| 이력을 읽지 못할 때 | 페이지는 열리고 「처음 열었어요」 줄만 보이며 표 아래에 「지금 불러오지 못했어요. 잠시 뒤 새로고침해 주세요.」(`InlineNotice`)가 한 개 붙는다. 이력이 없는 것(빈 배열)과는 다르다. 이력이 없으면 「처음 열었어요」 한 줄만 보이고 안내는 없다 |

- 표의 모양(`ProbabilityTable`)은 바뀌지 않았다. 최신 줄 강조, 아이콘, 진입 애니메이션을 두지 않는다. 저장한 뒤에는 새로고침해야 반영된다(`force-dynamic`).
- 이력을 쓰지 않는 경로의 변경은 이 표에 담기지 않는다. 옛 어드민 화면의 시스템 드랍(`ambient_drop_config`) 확률 저장이 그렇고, 같은 틀(밸런스 설정 구역)로 옮겨 오면 이력에 쓰여 자동으로 포함된다(티켓 `20261022_1132` 7-2·7-3).
  그 전까지 시스템 드랍 확률을 바꾸면 값은 새로 바뀌는데 이 표는 그대로다.
- `capsule_policy.updated_at`은 갱신 트리거가 없어 날짜로 쓸 수 없다. 믿을 수 있는 날짜는 변경 이력의 `created_at`이다.
- 「바꾸기 전에 공지한다」(운영 로직 18.3절)는 공지 수단이 정해지지 않아 페이지에 약속 문장으로 적지 않았다.

## 6. 알려진 차이

공개 문서이므로 설정값과 실제 결과가 어긋날 수 있는 곳을 숨기지 않는다. 페이지가 이미 적은 것과 아직 적지 않은 것을 나눠 둔다.

| 차이 | 페이지 |
|---|---|
| 뽑힌 등급에 후보가 없으면 낮춰서 고른다(지금 발급할 수 있는 아이템 배지가 Common뿐이라 결과가 설정값과 다를 수 있다) | 등급 표 아래 문장으로 적음 |
| 활성 트라이브가 적어 「나머지 넷 가운데」가 「후보가 있는 나머지 트라이브 가운데」로 동작한다 | 캡슐 개수 표 아래 문장으로 적음 |
| 시스템 드랍 `random` 모드는 고정된 표가 없다 | 설명 문장으로 적음 |
| 「잠김으로 만든」 아이템 배지는 잠길 확률과 별개로 늘 잠긴 채 나온다(운영 로직 7.2절) | 적지 않음 |
| 운영자가 장소와 아이템 배지를 지정해 놓는 시스템 드랍(행사)에는 등급 확률이 적용되지 않는다(9.4절) | 적지 않음 |
