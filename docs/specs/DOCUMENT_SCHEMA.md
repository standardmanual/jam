# JAM! 문서 스키마

문서 종류를 `type`으로 구분하고, frontmatter로 검색·검증·색인을 가능하게 하며, 서로 다른 주제의
문서 사이 연결을 명시하기 위한 규칙이다. 폴더 = 수명주기 원칙(`CLAUDE.md`)과 카테고리 ①~⑤는
그대로 유지하고, 그 위에 얹는 층이다.

## 1. 원칙

1. **기계가 읽고 검증하는 필드만 둔다.** 검증하지 않는 필드는 시간이 지나면 거짓이 된다.
2. **수정일·작성자 필드를 두지 않는다.** `git log`로 산출한다. 본문에 변경 이력을 누적하지 않는
   원칙(현재 상태 문서는 덮어쓰기)과도 맞는다.
3. **type은 늘리지 않는다.** 내용 구분(배지, 트라이브, 체크인 등)은 type이 아니라 `tags`가 맡는다.
   type은 "작성·사용 방식(구조와 수명주기)"이 다른 문서에만 둔다.
4. **연결은 한 방향으로만 적는다.** 하위 문서가 상위 문서를 가리키고, 역방향 목록은 조회 명령이 생성한다.
5. **스키마는 추가만 허용한다.** 새 필드는 선택으로 시작한다(§7).

## 2. 적용 범위

| 구분 | 대상 |
|---|---|
| 적용 | `docs/specs/`, `docs/agents/`, `docs/tickets/`(§4.2), `jam-doc/planning/`, `jam-doc/marketing/`, `jam-doc/operations/`, `jam-doc/inbox/` |
| 제외 | 도구가 형식을 정한 파일(`CLAUDE.md`, `AGENTS.md`, `.claude/agents/*`, `.claude/skills/*`), `jam-doc/archive/`, `jam-doc/assets/`, 컨텐츠 폴더의 산출물(`.json`·`.py`·`.mjs`·`.xlsx`), 옛 형식 티켓 `docs/tickets/modular/`, `docs/tickets/_TEMPLATE.md`, Storybook 문서, `jam-web/` 안의 문서 |

## 3. type (15개)

| type | 구분 | 용도 | 담는 문서 | 수명주기 |
|---|---|---|---|---|
| `guideline` | 범용 | 서비스 산출물과 코드가 따라야 하는 기준 | UX 라이팅, 개발 가드레일, 금지어 사전, 서비스 운영, 개인정보 처리방침, 에러 메시지 규칙, 마케팅 플레이북, 브랜드 보이스, 이 문서 | 덮어쓰기 |
| `log` | 범용 | 시간순 기록 | 작업 로그, 결정 사항, 인수인계, 컨텐츠 변경 이력 | 누적 |
| `report` | 범용 | 기간 단위 결과 보고 | 주간·월간·배포 리포트 | 신규 생성 |
| `research-note` | 범용 | 조사와 분석 메모 | 트렌드 노트, 분석 메모, 에이전트 조사 결과, 사용자 제출 트렌드 자료(`jam-doc/inbox/trends/`) | 신규 생성 |
| `catalog` | 범용 | 컨텐츠 목록 | 액티비티 배지, 컬렉션, 믹스 레시피, 지점, 트라이브 | 덮어쓰기 |
| `insight` | 범용 | 개인 지식에서 승격된 인사이트 카드 | `jam-doc/inbox/insights/` | 신규 생성 |
| `index` | 범용 | 디렉터리 안내 | 각 `README.md` | 덮어쓰기 |
| `ticket` | JAM | 실행 계획과 작업 이력 | `docs/tickets/p0~p3/*` | 신규 생성 |
| `prd` | JAM | 주제별 스펙 전반 | PRD, 프로젝트 스펙, 단계 문서, 디자인 개편 스펙, 상호작용 흐름, 측정 이벤트, 사례집 | 덮어쓰기 |
| `data-model` | JAM | 데이터·객체 모델 | 데이터 모델, 객체 모델 | 덮어쓰기 |
| `engine-spec` | JAM | 엔진 판정 로직과 데이터 계약 | 배지엔진 통합 문서, 조건 JSON 명세 | 덮어쓰기 |
| `agent-profile` | JAM | 에이전트 역할 카드 | `docs/agents/workflow/agents/*` | 덮어쓰기 |
| `workflow-rule` | JAM | 에이전트 팀이 일하는 방식 | 워크플로 규칙, 절차, 체크리스트, 팀·자동화 목록 | 덮어쓰기 |
| `service-plan` | JAM | 비전과 서비스 계획 | `jam-doc/planning/business-plan/*` | 덮어쓰기 |
| `campaign` | JAM | 기간이 있는 실행안 | 캠페인, 시즌 운영안, 홈피드 카드 초안 | 신규 생성 |

- **구분**은 개인 지식 묶음으로 방법론을 이식할 때의 범위다. 범용 7개가 키트에 포함되고, JAM 8개는
  JAM 묶음에서만 쓴다.
- `guideline`과 `workflow-rule`의 경계: 서비스 산출물과 코드가 따라야 하면 `guideline`, 에이전트
  팀의 작업 방식이면 `workflow-rule`이다.
- **type을 추가하려면** 먼저 기존 type과 tags로 수용할 수 있는지 확인한다(§8). 수용할 수 없을
  때만 티켓으로 결정하고 이 표를 고친다.
- 아직 문서가 없는 종류를 위한 예약 type은 만들지 않는다.
- `insight`와 `campaign`은 아직 문서가 없어 검사기 설정에서 비활성 상태로 시작하고, 첫 문서를 만들 때 활성화한다.

## 4. 필드

### 4.1 공통 필드

| 필드 | 필수 | 내용 |
|---|---|---|
| `type` | 필수 | §3의 type 하나 |
| `description` | 필수 | 한 줄 요약(권장 100자 이내). 조회 결과에 그대로 노출되고, 에이전트가 문서를 열기 전 관련성을 판단하는 근거다 |
| `status` | 선택 | §4.3의 허용값. 생략하면 `active` |
| `tags` | 선택 | §6의 통제 어휘 |
| `related` | 선택 | 단순히 관련된 문서 경로 또는 티켓 ID 목록 (방향 없음) |
| `basis` | 선택 | 이 문서가 근거로 삼는 상위 문서 경로 목록 (방향 있음) |

- `title`은 원칙적으로 두지 않는다. 첫 H1을 제목으로 읽는다. H1이 없거나 첫 H1이 문서 전체를 대표하지 않는
  문서(서비스 플랜 `01`·`02`)에서만 `title`을 쓰며, 있으면 H1보다 우선한다.
- 티켓은 `type`과 `description`이 면제다(§4.2).

### 4.2 type별 추가 필드

| type | 추가 필드 |
|---|---|
| `prd`, `data-model`, `engine-spec` | `code`(선택): 이 문서가 규정하는 코드 경로 목록 |
| `agent-profile` | `agent`(선택): 에이전트 정의명(예: `jam-developer`). `.claude/agents/{agent}.md`의 존재를 검증한다. 정의 파일이 없는 카리나는 생략한다 |
| `catalog` | `tags`(필수), `source_of_truth`(필수): `db` 또는 `doc`, `source`(선택): 원천 파일 목록, `snapshot`(선택): DB 기준일. 문서가 DB의 스냅샷인지 원천인지 밝혀 낡은 문서가 진실로 읽히는 것을 막는다 |
| `campaign` | `status`(필수), `start`·`end`(선택) |
| `research-note` | `tags`(필수), `sources`(선택): 출처 목록, `confidence`(선택): 높음·보통·낮음 |
| `report` | `period`(필수): `weekly`·`monthly`·`deploy`, `from`·`to`(필수): 대상 기간 |
| `insight` | `status`(필수), `tags`(필수), `source`(선택): 공개 출처만, `confidence`(선택), `outcome`(조건부 필수): 채택이면 티켓 ID, 기각이면 사유 한 줄 |
| `ticket` | 기존 `id`·`category`·`priority`·`status`·`created`·`closed`를 그대로 유지한다. 신규 선택 필드: `parent`(상위 티켓 ID), `specs`(영향받는 스펙 문서 경로 목록), `related` |
| 그 외 | 없음 |

**티켓 예외.** 티켓은 경로(`docs/tickets/p*/`)로 type을 판정하므로 기존 티켓 frontmatter를 고치지
않는다. 요약은 본문의 `핵심 요약` 절이 대신한다. 신규 필드는 모두 선택이라 기존 티켓에 영향이 없다.

**원천 파일 예외.** `ITEMBOOKS.xlsx`처럼 frontmatter를 담을 수 없는 원천 파일은 적용 대상이 아니다. 그 목록을 다루는 md 문서를 만들면 `source`에 원천 파일을 적는다.

### 4.3 status 허용값

| 대상 | 허용값 |
|---|---|
| `prd`, `data-model`, `engine-spec`, `guideline`, `agent-profile`, `workflow-rule`, `catalog`, `service-plan`, `index` | `draft`·`active`·`stub` (기본 `active`) |
| `campaign` | `draft`·`approved`·`running`·`done`·`dropped` |
| `insight` | `new`·`reviewing`·`adopted`·`parked`·`rejected` |
| `ticket` | 기존 대문자 유지: `OPEN`·`IN_PROGRESS`·`WAITING`·`CLOSED` (훅과 현황판이 이 값에 의존한다) |
| `research-note`, `report`, `log` | 사용하지 않는다 |

| 값 | 의미 |
|---|---|
| `active` | 현재 서비스와 일치하는 문서 |
| `draft` | 현재 서비스에 아직 반영되지 않은 내용을 포함하는 문서(작성 중 또는 계획 단계) |
| `stub` | 미작성 |

- **에이전트는 `draft` 문서를 현재 사실의 근거로 쓰지 않는다.**
- `docs/specs/`는 "현재 상태만 담는다"는 원칙이므로, 구현 전 계획은 티켓과 서비스 플랜의 🔵
  섹션에 두고 스펙의 `draft`는 구현이 진행되는 기간에만 허용한다.
- `draft`에서 `active`로의 전환은 `/jam-work`의 "머지·문서 갱신" 단계에서 처리한다.
- `draft` 문서의 `code` 경로는 아직 없는 파일을 가리킬 수 있으므로 존재 검사를 건너뛴다.

### 4.4 값 표기

- **티켓 ID는 반드시 따옴표로 감싼다**(`"20260918_1101"`). 따옴표가 없으면 YAML 1.1 파서가
  정수로 읽는다. 검사기는 `id`도 문자열로 취급한다.
- 문서 경로는 작업 폴더 기준으로 적는다(`docs/specs/prd/01_PRD.md`, `jam-doc/planning/content/TRIBES.md`).
- 목록은 YAML 리스트로 적는다.

### 4.5 새 버전 기획 표시 (2026-10-08)

다음 버전의 기획 문서는 지금 서비스 문서와 섞이지 않게 아래 세 가지를 똑같이 붙인다. 지금 버전명은 **JAM 2.0**이다.

1. `description` 맨 앞에 `[JAM 2.0] `을 붙인다. 문서 색인(`docs/specs/INDEX.md`)에서도 구분된다.
2. `tags`에 `JAM2.0`을 더한다(§6.2).
3. 본문 제목 바로 아래 첫 줄을 `> **JAM 2.0 기획 문서다.**`로 시작하고, 같은 줄에 그 문서의 상태를 이어 쓴다.

- 에이전트는 이 표시가 붙은 문서를 현재 서비스 사실의 근거로 쓰지 않는다.
- 지난 기획은 `jam-doc/archive/` 안에서 「버전명-기획내용」 폴더(예: `v4-service-plan/`)로 묶는다(CLAUDE.md 「폴더 = 수명주기」).

## 5. 연결

문서 사이 연결은 네 가지 경로로 만들어진다.

1. **본문 링크.** 본문의 마크다운 링크와 백틱으로 적은 작업 폴더 기준 경로를 검사기가 연결선으로
   수집한다. 작성자가 따로 적을 것이 없다. 마크다운 링크는 **파일 단위까지만** 검증한다(제목에
   이모지와 한글이 있어 앵커가 쉽게 어긋난다). 백틱 경로도 존재하지 않으면 차단한다. 일부러 없는 경로를
   적어야 하면 아래 「예외 표기」를 쓴다. 커밋 검사는 추가된 줄과, 이동·삭제된 파일을 가리키는 모든 문서를 대상으로 한다.
2. **`basis`.** "이 문서가 근거로 삼는 상위 문서"를 하위 문서에만 적는다. 상위 문서를 바꿀 때
   영향받는 문서는 역링크 조회 명령으로 찾는다. `catalog`와 `campaign`에서는 비어 있으면 경고한다.
3. **`related`·`code`·티켓의 `specs`.** 방향 없는 관련, 스펙에서 코드로, 티켓에서 스펙으로 가는 연결이다.
4. **공통 태그.** 서로 다른 type의 문서가 같은 개체를 다룰 때 같은 태그로 묶인다.

**조회.** 역링크와 문서 목록은 커밋하는 색인 파일이 아니라 필요할 때 실행하는 조회 명령으로
만든다(커밋되는 색인은 병렬 세션 충돌과 낡음 문제가 있다). 티켓은 조회 대상에서 제외한다(수가
많고 빠르게 늘어난다). 티켓의 `관련 파일` 칸에 코드 위치를 적는 관례(티켓 지도)는 이 조회와
별개다.

**고아 문서.** 조회 명령이 어디서도 링크·근거로 언급되지 않고 태그도 없는 문서를 출력한다.

## 6. 태그

### 6.1 규칙

- **통제 어휘만 쓴다.** 어휘에 없는 태그는 경고한다.
- **공백 없이 붙여 쓴다**(예: `체크인배지`, `Strava동기화`). 가이드라인 표기에서 공백만 제거한다.
- **개체와 종목 태그의 원천은 [UX_WRITING_GUIDELINE](UX_WRITING_GUIDELINE.md) §1.3의 고정 용어다.**
  이 태그는 별도 용어집이 아니라 그 표에서 뽑은 부분집합이다. 새 개체·종목 태그가 필요하면
  가이드라인 표를 먼저 갱신한 뒤 이 어휘에 추가한다.
- **주제 태그는 필요할 때 이 어휘에 직접 추가한다.** 주제는 화면에 노출되는 용어가 아니어서
  가이드라인 표에 없다. 기존 어휘로 표현되지 않는 문서가 생기면 §6.2의 표와 검사기 설정
  (`scripts/doc-check.config.json`)에 함께 추가하며, 이름은 가이드라인 표의 용어와 겹치지 않아야 한다.
- **금지 표기 검사는 `tags`에만 적용한다.** 가이드라인 표의 X 목록에 있는 표기가 태그에 들어가면
  경고한다. `description`과 본문은 식별자 병기 때문에 오탐이 많아 제외한다.
- **본문과 `description`은 고정 용어로 쓴다.** 코드·DB 식별자와 파일명(`ITEMBOOKS.xlsx`,
  `COMBINE_RECIPES.md`, `POI.md`, `poi`, `item_book`)은 원문을 유지하고 필요하면 괄호로 병기한다
  (예: "지점(POI)").

### 6.2 어휘 (32개)

| 그룹 | 태그 | 범위 |
|---|---|---|
| 개체 (18) | `배지`, `등급`, `컬렉션`, `트라이브`, `체크인`, `체크인배지`, `드랍`, `믹스`, `인벤토리`, `미션`, `포인트`, `랭킹`, `알림`, `피드`, `프로필`, `팔로우`, `Strava동기화`, `어드민` | 아래 범위 표기 참고 |
| 종목 (5) | `자전거`, `걷기`, `러닝`, `트레일러닝`, `등산` | `트레일러닝`은 정식 종목명이다. `트레일`은 탭 라벨 전용 축약이고 `트레킹`은 금지 표기다 |
| 주제 (9) | `리텐션`, `획득`, `어뷰징`, `마케팅`, `시즌`, `디자인시스템`, `계측`, `워크플로`, `JAM2.0` | 아래 범위 표기 참고 |

범위 표기:

- `배지`: 배지 체계 전반(계열·축·레벨 포함). `등급`: Common부터 Mystic까지의 희귀도.
- `획득`: **배지 획득**(발급 판정, 획득 알림, 획득 경로). 아이템을 얻는 것은 `드랍`(픽업 포함)이다.
- `체크인`: 지점(위치 데이터 포함)과 체크인 성립 판정. `체크인배지`: 체크인으로 획득하는 배지.
  둘은 따로 붙인다.
- `컬렉션`: 컬렉션과 장착·해제. 옛 표기 아이템북은 쓰지 않는다.
- `믹스`: 아이템 믹스와 재료. 옛 표기 조합은 쓰지 않는다.
- `마케팅`: 마케팅 지침, 플레이북, 트렌드, 캠페인 문서. `시즌`: 시즌 소재와 시즌 운영.
- `디자인시스템`: 디자인시스템(MODULAR, shadcn 기반 어드민)과 UI 리뉴얼. `계측`: 분석 이벤트(GA4)와 지표 수집.
- `워크플로`: 에이전트 팀의 작업 방식, 규칙, 자동화.
- `JAM2.0`: 새 버전(JAM 2.0) 기획 문서. 붙이는 방법은 §4.5다.

## 7. 확장 규칙

1. **필드는 추가만 허용하고 선택으로 시작한다.** 필수로 올리는 것은 기존 문서를 모두 이전한 뒤다.
2. **열거값은 검사기 코드가 아니라 묶음별 설정 파일에 둔다.** `status`, `period`, 태그 어휘가
   여기에 해당하므로 값을 늘려도 코드를 고치지 않는다.
3. **검사기는 미지의 type과 필드를 오류가 아닌 경고로 처리한다.** 묶음 설정으로 엄격 모드를
   켤 수 있다.
4. **스키마 버전은 묶음 설정 파일에 한 번만 적는다.** 문서마다 적으면 개정 때 전부 고쳐야 한다.

## 8. 수용 시험

새 사업 영역이나 문서 종류가 생기면 type을 늘리기 전에 다음을 확인한다.

1. 그 영역에서 생길 문서를 나열한다(계획, 스펙, 데이터, 목록, 정책, 실행안, 조사, 결과).
2. 각 문서를 §3의 type에 배정해 본다.
3. 구분이 필요하면 tags(새 태그는 §6.1 절차)로 해결한다.
4. 배정할 type이 하나라도 없을 때만 type 추가를 티켓으로 결정한다.

D2C 실물 패치, B2B 브랜드 스폰서십, 지자체 이벤트, SNS 연동, 거래·클랜, 종목 확장을 시험했을 때
모두 새 type 없이 수용됐다.

## 9. 묶음과 개인 지식

이 스키마는 `jam`과 `jam-doc`에 적용된다. 개인 지식 묶음은 내용을 공유하지 않고 **방법론만
공유한다**(범용 type 7개, 공통 필드, 검사기, 설정 파일 템플릿, 폴더 = 수명주기 관례). 두 묶음
사이에 참조 관계를 두지 않으며, 프로젝트 에이전트는 개인 지식에 접근하지 않는다. 개인 지식에서
서비스로 가는 유일한 통로는 사람이 승격한 `insight` 카드다.

## 10. 검사

커밋할 때 `.githooks/pre-commit`이 `scripts/doc-check.mjs --staged`를 실행한다. 적용 범위, 활성 type,
필드 규칙, 태그 어휘, 등급은 `scripts/doc-check.config.json`에 있다.

| 검사 | 등급 |
|---|---|
| 링크 대상이 없음(추가한 줄, 이동·삭제한 파일을 가리키는 문서) | 오류(차단) |
| `type`·`description` 누락, type별 필수 필드 누락, 허용값 위반, 어휘 밖 태그, 금지 표기 태그 | 오류(차단) |
| 백틱 경로가 없음(티켓 문서는 경고) | 오류(차단) |
| 경로를 해석할 수 없음(외부 폴더가 없는 환경 등) | 경고 |
| 미지의 type·필드, 활성화되지 않은 type | 경고 |

- **백틱 경로 예외 표기.** 자리표시자·시크릿·예정 위치처럼 일부러 존재하지 않는 경로는
  `scripts/doc-check.config.json`의 `codeSpanIgnore`(경로에 대한 정규식 문자열 배열)에 패턴을
  더해 검사에서 뺀다. 현재 목록은 `jam-web/.env*`, `jam-web/node_modules`, `YYYY`(날짜 자리표시자),
  `0XX_`(번호 자리표시자), `jam-doc/inbox/`, `docs/adr/`이다. 티켓은 옛 경로 인용이 관례라
  `codespanWarnPaths`(경로 접두어 배열, 현재 `docs/tickets/`)에 든 문서만 백틱 경로를 계속 경고로
  둔다. 패턴은 최소로 유지하고, 실제 오타는 예외에 넣지 말고 경로를 고친다.
- 위반은 종료 코드 10으로 커밋을 차단한다. 엔진 자체의 실패(설정 파싱 오류, 엔진 파일 없음 등)는
  경고를 내고 커밋을 통과시킨다.
- 정당한 예외는 `JAM_SKIP_DOCLINT=1 git commit ...`으로 우회하고 사유를 커밋 메시지에 남긴다.
- `node scripts/doc-check.mjs --all --summary`로 전체 문서의 현황을 본다.
- `jam-doc/` 문서도 같은 저장소의 같은 훅·엔진·설정(`scripts/doc-check.config.json`)으로 검사된다.
  2026-09-20 재통합 전에 있던 `jam-doc` 전용 엔진 복사본과 설정은 없어졌다(티켓 20260920_1412).
  무인 예약 루틴이 쓰는 `report`(주간·월간·배포 리포트)는
  `operations/reports/`가 설정의 `scope.exclude`에 있어 검사 대상 자체에서 빠지므로, 필드
  검사 등급과 무관하게 항상 통과한다.
- 사용자 제출 트렌드 자료(`jam-doc/inbox/trends/`, 사용법은 [그 폴더의 README](../../jam-doc/inbox/trends/README.md))는 검사 범위에서 빼지 않는다. 사용자는 본문만 쓰고, frontmatter
  (`type: research-note`·`description`·`tags`)와 파일 이름(`YYYY-MM-DD_제목.md`)은 카리나가 커밋할 때 맞춘다. 빠뜨리면
  필드 검사와 `.githooks/pre-commit` ⑩이 막는다. 승격 카드 폴더 `jam-doc/inbox/insights/`(`insight`, 비활성)와는 별개다.
  사용자 원문은 고치지 않으므로 `scripts/check-slop.mjs`의 검사 대상에서도 이 폴더를 뺀다(티켓 20260930_1518).
