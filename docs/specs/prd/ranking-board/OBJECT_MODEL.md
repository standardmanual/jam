## 0. 무엇을 위한 기능인가

기존 랭킹은 항상 특정 미션에 종속된 속성(`missions.status_display_type='ranking'`)으로만
존재했다. "랭킹"을 미션에 종속되지 않는 독립 엔티티(`ranking_modes`)로 분리해, 운영자가
어드민에서 만들어두면 투데이 컨텐츠 카드로 홈 피드에도 노출할 수 있게 한다.

## 1. `ranking_modes` — 대상 × 지표 두 독립 축

랭킹 하나는 "누구를 줄 세울지(대상)"와 "무엇으로 줄 세울지(지표)"의 조합이다.

| 필드 | 의미 |
|---|---|
| `target_type` | `mission_participants`(미션 참가자 전원) \| `manual_users`(운영자 수동 지정) |
| `target_mission_id` | `target_type='mission_participants'`일 때만. 미션 삭제 시 `SET NULL`(랭킹은 남고 참조만 풀림 — 어드민 화면이 경고 표시) |
| `target_user_ids` | `target_type='manual_users'`일 때만. UUID 배열(Postgres 배열엔 FK를 걸 수 없어 계산 시점에 애플리케이션이 존재 여부를 거름) |
| `metric_type` | `mission_progress`(대상이 미션 참가자일 때 고정) \| `condition_field`(배지 조건 필드 하나) \| `badge_count`(배지 보유 개수) |
| `metric_field_key` | `metric_type='condition_field'`일 때만. 아래 §2 참고 |
| `metric_badge_type` | `metric_type='badge_count'`일 때만. `activity` \| `item` \| `checkin`, 타입 안에서 distinct `badge_id`로 카운트 |
| `starts_at` / `ends_at` | 집계 기간. 종료 후에도 결과는 고정되어 그대로 노출됨(재계산 안 함) |
| `visible_rank_count` | 공개 순위 인원 제한(선택, `missions.visible_rank_count`와 같은 개념) |

미션 참가자 랭킹의 순위 계산은 기존 미션 랭킹 비교 규칙(완료 여부 → 완료 시각 → 진행도,
`lib/missions/ranking.ts`)을 그대로 감싸 재사용한다 — 새 규칙을 만들지 않았다.

## 2. 정렬 지표는 배지 조건 레지스트리를 그대로 참조한다

`metric_field_key`는 랭킹 전용으로 새로 열거하지 않고, 액티비티 배지를 만들 때 쓰는 조건
필드 목록(`conditionRegistry.ts`)의 키를 그대로 쓴다 — 배지 조건이 늘어나면 랭킹 지표
선택지도 자동으로 함께 늘어나는 구조다. DB는 그 값을 검증하지 않는다(레지스트리가 바뀔
때마다 이 테이블을 고치지 않기 위함).

다만 레지스트리 전체가 지금 당장 계산 가능한 건 아니다 — "이 값이 기준치를 넘었는가"만
보면 되는 배지 판정과 달리, 랭킹은 값 자체로 크기를 비교해야 한다. 실제로 값을 계산할 수
있는 필드는 애플리케이션 레이어의 화이트리스트(`lib/ranking/metricValues.ts`)가 별도
관리한다:

- **1차 지원(값 계산 가능)**: 누적 거리·누적 고도·누적 이동 시간·총 횟수·활동일수·
  연속 출석일수 같은 "누적 목표" 계열, 그리고 팔로워 수·팔로잉 수·하루 동기화 횟수 같은
  "사용량 지표" 계열. 누적 계열은 배지 화면 진행률 표시가 쓰는 것과 같은 계산 로직을
  재사용하고, 사용량 지표는 그 값을 이미 별도 경로로 구하고 있던 것을 그대로 쓴다.
- **1차 미지원(어드민 화면에는 보이되 선택하면 막힘)**: 대상을 좁히는 필터 성격 필드
  (종목·계절 등), 필드 하나만으로는 값이 안 정해지는 필드(예: "몇 시간 안에"류), 아직
  엔진이 계산한 적 없는 필드, 선행 배지 같은 관계형 필드. "한 번의 활동 기록"·"개인
  기록 비교" 계열은 유저 한 명당 대표값을 역대 최고로 뽑을지 최근 활동 기준으로 뽑을지
  결정이 나지 않아 이번 범위에서 제외했다.

## 3. 투데이 카드 연동

`today_cards.template_type`에 `ranking_board`, `layout_type`에 `ranking_list`를 추가하고
`ranking_mode_id`(FK, `ON DELETE SET NULL`)로 연결한다. 카드 하나가 랭킹 하나를 참조하는
단순 참조 관계이며, 랭킹 하나를 여러 카드가 동시에 참조할 수 있다. 유저 노출 화면은 기존
`TodayCardStack`이 그대로 렌더링하고, 순위 리스트 UI(`RankingListRow`)는 미션 상세 화면과
공유한다(1·2·3위 강조 그래프는 홈 피드에서 뺀다).

랭킹보드 카드 탭 시 이동 경로: 대상이 미션 참가자면 그 미션 상세(`/missions/{id}/status`)로,
대상이 수동 지정 유저면 카드 제목 영역은 이동 링크를 두지 않는다(그 랭킹 전용 화면이 없어서
— §5 참고). 순위 리스트의 개별 행은 대상 방식과 무관하게 항상 그 유저 프로필로 이동한다.

## 4. 유저 노출 용어

유저에게 보이는 문구는 "랭킹"으로 고정한다(`Service Plan/Specs/UX_WRITING_GUIDELINE.md`
§1.3에 등재). 어드민에서 랭킹을 만드는 저작 도구는 "랭킹 규칙"이라 부른다 — `ranking_mode`는
내부 코드·DB 식별자로만 남고 사람이 보는 문구에는 쓰지 않는다.

## 5. Out of Scope(다음 단계)

- 여러 지표를 가중치로 합성하는 복합 랭킹 — 조합 방식(단순 가중합 여부, 척도 정규화 등)
  미정.
- "한 번의 활동 기록"·"이번 주/이번 달"류 지표의 대표값 기준(역대 최고 vs 최근/현재
  시점) — 계산 로직은 이미 있으나 어느 관례를 쓸지는 제품 판단이 필요.
- 수동 지정 유저 대상 랭킹의 전용 화면(있으면 카드 탭 시 그곳으로 보낼 수 있다) 및 인원
  수 상한.
- 랭킹 결과에 대한 알림·시상 자동화.
