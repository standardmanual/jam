# [API] 프로필 사진 업로드 시 EXIF(GPS 좌표 포함)를 서버에서 제거한다

## 핵심 요약

- 요구사항: `POST /api/profile/avatar`가 업로드 파일을 원본 바이트 그대로 공개 버킷(`avatars`)에
  올려서, 휴대폰 사진의 GPS 좌표·기기 정보 EXIF가 공개 URL로 노출된다. 서버에서 sharp로 디코드 →
  EXIF 방향을 픽셀에 적용(`rotate()`) → 메타데이터 없이 재인코딩한 바이트만 저장한다.
- 구현 계획: 새 유틸 `jam-web/src/lib/avatarImage.ts`(`sanitizeAvatarImage`)를 만들고 라우트가 그
  결과를 업로드한다. 형식은 **실제 디코드한 형식**(jpeg/png/webp)을 유지하고, 디코드 실패·허용 외
  형식은 400(`d.profileEdit.fileTypeError`)으로 돌려보낸다. 상세는 「구현 계획」.
- 관련 파일:
  - `jam-web/src/app/api/profile/avatar/route.ts` — `POST` 47~54행(확장자 계산·`upload(path, file, …)`)
    을 정제된 Buffer 업로드로 바꾼다. `extFromMime`(11~15행)은 정제 결과의 형식을 받도록 조정
  - `jam-web/src/lib/avatarImage.ts` (신규) — 기존 sharp 유틸 `jam-web/src/lib/admin/badgeImageWebp.ts`
    와 같은 형태(순수 함수 + 상수)
  - `jam-web/src/lib/__tests__/avatarImage.test.ts` (신규) — 테스트 패턴은
    `jam-web/src/lib/admin/__tests__/badgeImageWebp.test.ts`
  - `jam-web/src/app/api/profile/avatar/__tests__/route.test.ts` (신규) — Supabase 목 패턴은
    `jam-web/src/app/api/today/events/__tests__/route.test.ts` 9~21행
  - `docs/specs/SERVICE_OPERATIONS.md` 1024행 API 표의 `/api/profile/avatar` 설명

## 배경 / 문제 정의

- 현재: 라우트 52~54행이 `File`을 그대로 `storage.upload`에 넘긴다. EXIF를 읽거나 지우는 코드는
  저장소에 없다. `avatars` 버킷은 `public = true`다.
- 재현(2026-09-29 13:16 KST, 카리나): exiftool로 GPS(37.5665N, 126.9780E)·`Make`·`Orientation=6`을
  넣은 샘플 JPEG를 실제 `POST` 핸들러에 넣고(Supabase만 목) `upload`에 전달된 바이트를 저장해 비교했다.
  저장 바이트가 원본과 `cmp` 기준 **완전히 동일**했고 GPS·기기·방향 태그가 모두 남아 있었다.
- 운영 실측(같은 날, 읽기 전용 조회): `avatars` 버킷 객체 6개(JPEG 4·PNG 2) 중 **JPEG 3개에 GPS
  좌표가 있고 공개 URL로 HTTP 200 조회된다.** 그중 2개는 현재 `users.avatar_url`이 가리키는 파일,
  1개는 교체 후 남은 이전 파일이다. 좌표 값 자체는 조회·기록하지 않았다.
- `docs/specs/PRIVACY_POLICY.md` 120행은 GPS 좌표를 "목적 달성 즉시 미보관"한다고 적고 있어, 현재
  동작은 고지 내용과 어긋난다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 저장되는 파일에 EXIF·XMP·IPTC가 남지 않는다(sharp는 `withMetadata`/`keepMetadata`를 부르지 않으면
  메타데이터를 쓰지 않는다 — 이 기본 동작에 기대고, 메타데이터 유지 옵션을 쓰지 않는다).
- EXIF `Orientation`은 지우기 전에 픽셀에 적용해 휴대폰 세로 사진이 눕지 않는다.
- 출력 형식은 **클라이언트가 보낸 `file.type`이 아니라 sharp가 디코드한 실제 형식**으로 정하고,
  `contentType`·확장자도 그 형식을 따른다. 실제 형식이 jpeg/png/webp가 아니거나 디코드에 실패하면
  400 `fileTypeError`를 돌려준다(업로드·DB 갱신을 하지 않는다).
- 기존 검사(인증 401, `ALLOWED_TYPES`, 5MB `MAX_SIZE`)와 응답 형태(`{ avatar_url }`)는 유지한다.
- 크기 조정(리사이즈)은 이 티켓 범위가 아니다.
- 클라이언트(`profile/edit/page.tsx`·`onboarding/page.tsx`)는 바꾸지 않는다 — 클라이언트 정제는 우회가
  가능하므로 서버를 단일 관문으로 둔다.

## 구현 계획

1. `jam-web/src/lib/avatarImage.ts` (신규, ~35줄)
   - `export type AvatarFormat = 'jpeg' | 'png' | 'webp'`
   - `export async function sanitizeAvatarImage(input: Buffer): Promise<{ buffer: Buffer; format: AvatarFormat }>`
     - `sharp(input).metadata()`로 형식 확인 → 허용 외면 `throw`(라우트가 400으로 변환)
     - `sharp(input).rotate()` 후 형식별 `.jpeg({ quality: 90 })` / `.png()` / `.webp({ quality: 90 })` →
       `.toBuffer()`
   - 주석에 "메타데이터 유지 옵션을 쓰지 않는 것이 제거 수단"임과 티켓 번호를 적는다.
2. `route.ts` (~15줄 변경): 크기 검사 뒤 `Buffer.from(await file.arrayBuffer())` → `sanitizeAvatarImage`
   (try/catch → 400 `fileTypeError`) → 확장자·`contentType`을 결과 `format`에서 정해 Buffer 업로드.
3. `avatarImage.test.ts` (~50줄): sharp로 만든 JPEG에 `withExif`로 GPS(IFD3)·`Make`를 넣고
   `Orientation`은 `withMetadata({ orientation: 6 })`로 넣어 입력을 만든다 →
   출력 `metadata()`의 `exif`·`xmp`·`iptc`가 `undefined`, `orientation`이 없음, 가로·세로가 뒤바뀜
   (예: 40×20 입력 → 20×40)을 확인. PNG·WebP 형식 유지, 이미지가 아닌 바이트는 reject.
4. `route.test.ts` (~60줄): 목 `upload`에 넘어간 본문을 `sharp().metadata()`로 읽어 `exif`가 없음,
   `contentType`이 실제 형식과 일치, 이미지 아닌 바이트를 `image/jpeg`로 보내면 400이고 `upload`
   미호출.
5. `SERVICE_OPERATIONS.md` 1024행 설명을 "아바타 업로드(서버에서 EXIF 제거·방향 적용 후 저장)"로 갱신.

합계 코드·테스트·문서 5개 파일, 약 160줄로 `plan_only` 기준(100줄)을 넘는다. 위처럼 파일 단위로
계획을 확정했으므로 첫 호출부터 계획 반환 면제를 넘긴다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)
- GPS·`Make`·`Orientation=6` EXIF가 든 JPEG를 `POST /api/profile/avatar` 핸들러에 넣으면, `upload`에
  전달된 바이트를 `sharp().metadata()`로 읽었을 때 `exif`가 `undefined`다(라우트 테스트로 확인).
- 같은 입력에서 출력 이미지의 가로·세로가 방향 적용 결과대로 뒤바뀐다(유틸 테스트로 확인).
- PNG·WebP 입력은 각각 같은 형식으로 저장되고 `contentType`·확장자가 일치한다.
- 이미지가 아닌 바이트를 `image/jpeg`로 보내면 400이고 `upload`·DB 갱신이 호출되지 않는다.
- `scripts/verify.sh` 통과.

### 후속 범위 (담당: 카리나, 시점: 머지 뒤 · 사용자 승인 후)
- 이미 올라간 아바타의 정제·정리는 별도 티켓에서 처리한다(운영 데이터 변경이라 승인 필요).
