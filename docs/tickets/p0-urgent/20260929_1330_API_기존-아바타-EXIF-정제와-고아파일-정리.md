# [API] 이미 올라간 아바타의 EXIF를 정제하고 교체 후 남은 이전 파일을 정리한다

## 핵심 요약

- 요구사항: 티켓 20260929_1317은 **앞으로** 올라오는 파일만 정제한다. 운영 `avatars` 버킷(공개)에 이미
  있는 파일 중 GPS가 든 3개는 계속 공개 URL로 조회된다. 현재 쓰이는 파일은 같은 경로에 정제본을
  덮어쓰고, 아무도 가리키지 않는 이전 파일은 삭제한다.
- 구현 계획: 일회성 스크립트(서비스 키, 드라이런 기본)로 처리한다. 운영 데이터 변경이므로 **사용자
  승인 후 카리나가 실행**한다. 상세는 「구현 계획」.
- 관련 파일: `jam-web/scripts/sanitize-existing-avatars.js`(작성 완료). 정제 규칙은 티켓 20260929_1317의
  유틸(`sanitizeAvatarImage`)과 같다(sharp `rotate()` → 같은 형식 재인코딩, 메타데이터 미유지).
- 진행 상태(2026-09-29): 사용자 승인을 받았다. 드라이런 결과는 아래 표와 일치했다(덮어쓰기 3개·삭제 3개).
  카리나 세션의 `--apply` 실행은 자동 모드 안전 분류기가 거부해, 적용은 사용자가 직접 실행하도록 넘겼다.

## 배경 / 문제 정의

2026-09-29 읽기 전용 실측(좌표 값은 조회·기록하지 않고 유무만 확인):

| # | 형식 | `users.avatar_url`이 가리킴 | GPS | EXIF 태그 수 |
|---|---|---|---|---|
| 1 | JPEG | 예 | 있음 | 63 |
| 2 | JPEG | 아니오(교체 전 파일) | 없음 | 55 (기기 정보 있음) |
| 3 | JPEG | 아니오(교체 전 파일) | 있음 | 61 |
| 4 | JPEG | 예 | 있음 | 61 |
| 5 | PNG | 아니오(교체 전 파일) | 없음 | 0 |
| 6 | PNG | 예 | 없음 | 3 |

- 버킷 전체 6개, 조회 시점 전부 HTTP 200. 객체 경로는 `storage.objects`(bucket_id='avatars')에서 다시 뽑는다.
- 교체 전 파일(2·3·5)이 남는 원인은 라우트가 매번 새 경로(`{user.id}/{Date.now()}.{ext}`)에 올리고
  이전 파일을 지우지 않기 때문이다 — 코드 수정은 티켓 20260929_1331에서 따로 한다.

## 구현 계획

1. 스크립트는 기본이 드라이런이다. `--apply`가 있을 때만 쓴다. 출력에 좌표 값을 찍지 않는다.
2. `users.avatar_url`이 가리키는 객체(1·4·6): 다운로드 → 정제 → **같은 경로에** `upsert: true`로
   다시 올린다. URL이 그대로라 DB는 바꾸지 않는다.
3. 아무도 가리키지 않는 객체(2·3·5): Storage API `remove()`로 삭제한다(SQL로 `storage.objects`를
   직접 지우지 않는다).
4. 실행 후 같은 공개 URL을 다시 받아 exiftool로 GPS·EXIF가 없음을 확인하고, 삭제 대상은 404인지 본다.
   CDN 캐시 때문에 곧바로 이전 바이트가 보일 수 있으므로 1시간 뒤 한 번 더 확인한다.

## 완료 조건

- 버킷에 남은 모든 객체를 공개 URL로 받았을 때 exiftool 기준 GPS 태그가 없다.
- `users.avatar_url`이 가리키지 않는 객체가 0개다.
- 현재 프로필 사진 3개가 화면에서 정상 방향으로 보인다.

## 결정 필요 (사용자)

- 덮어쓰기(URL 유지) 대신 새 경로로 올리고 `avatar_url`을 바꾸는 방식도 가능하다. 추천은 덮어쓰기다 —
  DB 변경이 없고, 어느 방식이든 CDN 잔존 시간은 비슷하다.
- 이미 외부에서 내려받힌 사본은 회수할 수 없다. GPS가 노출됐던 이용자 2명(현재 사진)과 이전 파일
  1건의 소유자에게 알릴지는 운영 판단이다.
