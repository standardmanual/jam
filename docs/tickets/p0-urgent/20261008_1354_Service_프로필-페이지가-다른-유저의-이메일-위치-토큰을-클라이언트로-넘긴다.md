# [Service] 프로필 페이지가 다른 유저의 이메일·마지막 위치·Strava 토큰 행을 클라이언트로 넘긴다

## 핵심 요약
- 요구사항: `/{username}` 프로필 페이지가 `ProfileClient`(클라이언트 컴포넌트)에 넘기는 대상 유저 데이터를 화면에 필요한 열로 줄인다. 다른 유저의 프로필을 볼 때 `email`·`last_location_*`·`is_admin`·`gps_daily_*`·`notifications_seen_at`과 `strava_connections`의 토큰·`strava_athlete_id`가 RSC 페이로드에 실리지 않아야 한다.
- 구현 계획: (미정 — 착수 시 작성) `select('*')`를 필요한 열 목록으로 바꾸고, `strava` prop은 연결 여부 등 화면이 쓰는 값만 담은 객체로 바꾸는 방향. `ProfileClient`가 실제로 읽는 필드를 먼저 전수 확인한다.
- 관련 파일: `jam-web/src/app/(main)/[username]/page.tsx` L41-45(`users.select('*')`), L89(`strava_connections.select('*')`), L92(`user_activity_feed.select('*')`), L366-378(`ProfileClient` props) / `jam-web/src/app/(main)/profile/ProfileClient.tsx`(1행 `'use client'`) / 같은 구조 확인 대상: `jam-web/src/app/(main)/[username]/followers/page.tsx`·`following/page.tsx`, `jam-web/src/app/(main)/feed/page.tsx` L54-57

## 배경 / 문제 정의

### 확인한 사실 (2026-10-08 13:50경 KST, 코드 읽기와 읽기 전용 SQL)
- `[username]/page.tsx`는 서비스 클라이언트(RLS 우회)로 대상 유저의 `users` 행을 `select('*')`로 읽고(L41-45), `strava_connections` 행도 `select('*')`로 읽는다(L89). 두 값을 그대로 `profile`·`strava` prop으로 `ProfileClient`에 넘긴다(L367-368).
- `ProfileClient.tsx` 1행은 `'use client'`다. 서버 컴포넌트가 클라이언트 컴포넌트에 넘긴 prop은 전체가 직렬화되어 브라우저로 간다.
- 운영 DB `users`의 열: `id, email, username, avatar_url, created_at, updated_at, last_location_lat, last_location_lng, last_location_at, initial_sync_done, gps_daily_distance_km, gps_daily_distance_date, notifications_seen_at, is_admin, display_name, tribe_id, onboarding_completed_at`.
- `strava_connections`의 열에는 암호화된 `access_token`·`refresh_token`과 `strava_athlete_id`가 있다.
- 이 경로는 티켓 20261008_1349(Strava OAuth state) 조사 중 유저 UUID 노출 경로를 찾다가 발견했다.

### 판단
- 로그인한 유저는 누구든 다른 유저의 프로필을 열어 그 유저의 이메일, 마지막 위치 좌표와 시각, 관리자 여부를 받는다(확신도 높음, 브라우저에서 실측은 하지 않음). 위치 좌표는 위치정보법상 개인위치정보에 해당할 수 있어 법적 위험도 있다.
- Strava 토큰은 서버 키로 암호화돼 있어 바로 쓸 수는 없지만, 클라이언트로 내보낼 이유가 없는 값이다.
- **위험도: 중단, 확신도 높음.**

## 완료 조건
- (착수 시 구체화) 다른 유저 프로필의 RSC 페이로드에 위 민감 열 값이 없다는 것을 테스트나 실렌더로 확인한다.
- 본인 프로필 화면의 동작은 바뀌지 않는다.
