# [Service] 중복 쿼리 파라미터가 화면을 500으로 죽인다

## 배경 / 문제 정의

**Next는 같은 쿼리 키가 두 번 오면 `string[]`을 넘긴다.** 그런데 대부분의 페이지가
`searchParams`를 단수 `string`으로 선언해 **타입체커가 그 사실을 가린다.** 그래서 값에
`.trim()` 같은 문자열 메서드를 부르는 순간 런타임에서 `TypeError`가 나고 화면이 500이 된다.

티켓 `20260906_1158`(배지 트리 `?activity=`)에서 게이트가 처음 잡았고, 그때 트리만 고치고
**나머지는 범위 밖으로 뒀다.** 이 티켓이 그 나머지다.

### 실측 — staging (2026-09-06)

**실제로 죽는 것 3건:**

| 경로 | 결과 |
|---|---|
| `/search?q=a&q=b` | **500** |
| `/badges/{id}?u=a&u=b` | **500** |
| `/collections/{id}?u=a&u=b` | **500** |

`[id]` 두 건은 **존재하지 않는 id로 대조군을 잡아 확인했다** — 중복 파라미터가 없으면
같은 id가 404를 주고, 중복이면 500이 된다. 「없는 id라서 죽는 것」이 아니다.

**지금은 견디지만 타입이 사실과 어긋난 것:**

| 경로 | 지금 200인 이유 |
|---|---|
| `/badges?tab=a&tab=b` | `VALID_TABS.has(raw)`가 배열을 false로 떨어뜨린다 |
| `/drops?poi=1&poi=2` | 값이 DB 조회로 흘러가 `data=null`이 되고 포커싱만 안 된다 |
| `/badges/tree?activity=a&activity=b` | 티켓 `1158`에서 이미 고쳤다 |
| `/profile?...` | 유일하게 `string \| string[] \| undefined`로 **올바르게** 선언돼 있다 |

우연히 견디는 것들도 **선언이 거짓말을 하고 있는 상태**라, 다음 사람이 그 값에 문자열
메서드를 붙이는 순간 같은 결함이 생긴다.

**어드민은 확인하지 못했다** — staging에서 어드민은 307로 막힌다(기존 제약).
선언은 전부 `Record<string, string | undefined>`라 같은 함정이 잠재한다.

### 왜 지금 하는가

- **로그인한 실사용자가 링크 하나로 흰 화면을 본다.** 중복 파라미터는 손으로 고친 URL,
  링크 합성, 리다이렉트 체인에서 흔히 생긴다
- 화면마다 방어를 반복하면 다음 화면에서 또 빠진다 — **공용 정규화 지점이 없는 것이 구조 문제**다

## 상세 요구사항

### 서비스/코드베이스 관점

**① 공용 헬퍼를 하나 만든다**

`searchParams` 값에서 **단일 문자열만 통과**시키고 나머지는 `undefined`로 떨어뜨린다.

```ts
/** 배열(중복 키)·부재를 undefined로 흡수한다. 호출부는 기존 폴백을 그대로 쓴다. */
function singleQueryParam(raw: string | string[] | undefined): string | undefined
```

- 배열이면 **첫 값을 고르지 않고 `undefined`** 를 돌려준다
- 위치는 구현자 판단(`src/lib/` 하위의 적절한 곳). 새 폴더를 만들지 말 것

**② 「첫 값 채택」이 아니라 「값 없음」인 이유 — 이대로 따를 것**

- 중복 파라미터는 정상 링크에서 나오지 않는다. **어느 쪽이 사용자 의도인지 알 수 없다**
- 티켓 `1158`이 트리에서 이미 「폴백」을 택했고, `/badges`의 `normalizeTab`이 같은 입력에
  보이는 결과와도 같다. **세 곳이 서로 다르게 동작하면 그게 더 나쁘다**
- 모든 호출부에서 「값 없음」이 안전한 기본값을 갖는다 —
  `?u=` 없으면 기본 시점, `?slot=` 없으면 비-슬롯 모드, `?page=` 없으면 1쪽, `?q=` 없으면 빈 검색

**③ 선언을 사실에 맞춘다**

죽는 3건뿐 아니라 **`searchParams`를 단수로 선언한 화면 전부**를 `string | string[]`
(어드민은 `Record<string, string | string[] | undefined>`)로 정정한다. 대상:

```
(main)/badges/page.tsx                    tab
(main)/badges/[id]/page.tsx               u          ← 500
(main)/collections/[id]/page.tsx          u, from, itemId, slot   ← 500
(main)/drops/page.tsx                     poi
(main)/search/page.tsx                    q          ← 500
admin/badges/page.tsx
admin/badge-families/page.tsx
admin/badges/bulk/page.tsx
admin/item-badges/page.tsx
admin/item-badges/[badgeId]/page.tsx
admin/item-badges/orphaned/page.tsx
admin/itembooks/page.tsx
admin/poi/page.tsx
admin/today/page.tsx                      date
```

**이미 올바른 두 곳은 건드리지 않는다**: `(main)/profile/page.tsx`,
`(main)/badges/tree/page.tsx`(티켓 `1158`에서 처리됨).

> 선언만 고치고 헬퍼를 안 끼우면 **타입 오류로 빌드가 깨진다.** 선언 정정과 헬퍼 적용은
> 한 파일 안에서 함께 간다.

**④ 되돌림 방지**

헬퍼에 **왜 배열이 오는지**와 **왜 첫 값을 안 쓰는지**를 주석으로 남긴다. 다음 사람이
「`string`으로 좁히면 깔끔한데」로 되돌리는 것을 막는 것이 이 티켓의 절반이다.

### UI/UX 관점

- 사용자 노출 문구 **추가·변경 없음**
- 중복 파라미터가 와도 **오류를 보이지 않고** 각 화면의 기본 상태로 연다
  (URL은 사용자가 손으로 고칠 수 있는 입력이므로 조용히 폴백하는 편이 맞다 — 티켓 `1158`과 같은 태도)

### 컨텐츠 관점

해당 없음.

## 구현 계획

1. 헬퍼 추가 (+ 단위 테스트: 문자열·빈문자열·배열·undefined)
2. 죽는 3건부터 적용 — `search` · `badges/[id]` · `collections/[id]`
3. 나머지 선언 정정 + 헬퍼 적용
4. 회귀 확인: **정상 파라미터가 지금과 똑같이 동작하는지**가 이 티켓의 최대 위험이다.
   `?tab=checkin` · `?u=` · `?slot=1` · `?page=2` · `?q=검색어` · `?poi=` · `?date=`

### 검증 — 어드민은 프로덕션에서만 된다

**staging에서 어드민은 307로 막힌다.** 어드민 화면은 코드 검토 + 타입 검사로만 확인하고,
실화면 확인은 프로덕션 배포 후로 미룬다. **이 제약을 완료 기록에 명시할 것** —
「확인했다」고 쓰면 안 된다.

### 범위 밖

- 클라이언트 쪽 `useSearchParams()` 사용처 — `URLSearchParams.get()`은 항상
  `string | null`이라 이 함정이 없다
- API 라우트의 `request.nextUrl.searchParams` — 같은 이유로 안전하다
- 중복 파라미터가 실제로 유통되는지 관측하는 로그 — 별건

### 구현 내용 요약

`src/lib/searchParams.ts`에 공용 정규화 헬퍼를 두고, `searchParams`를 단수 `string`으로
선언하던 화면 전부를 `string | string[]`로 정정하면서 그 헬퍼를 끼웠다.

- `singleQueryParam(raw)` — 값이 문자열이 아니면(=배열) `undefined`. **첫 값을 고르지 않는다.**
  빈 문자열(`?q=`)은 문자열이므로 그대로 통과시킨다(빈 값 처리는 각 화면의 기존 폴백이 담당).
- `pickSingleQueryParams(record)` — `searchParams`를 통째로 받아 쓰는 어드민 목록용.
  레코드 전체에 같은 규칙을 적용해 화면마다 필드별 방어를 반복하지 않게 했고, 반환 타입이
  `Record<string, string | undefined>`라 `Pagination`의 `searchParams` prop을 포함해
  하위 컴포넌트는 손대지 않았다.
- 헬퍼와 각 화면 선언부에 **왜 배열이 오는지 · 왜 첫 값을 안 쓰는지**를 주석으로 남겼다(요구사항 ④).

### 주요 의사결정 / 핵심 메모

- **배열 → `undefined`(첫 값 채택 아님)** — 티켓 ②의 결정을 그대로 따랐다. 배지 트리
  `normalizeActivity`(티켓 20260906_1158)·`/badges`의 `normalizeTab`이 이미 같은 입력에서
  폴백으로 동작하므로 세 곳의 동작이 일치한다.
- **어드민은 레코드 단위로 정규화** — 어드민 목록은 `params.page` · `params.type`처럼
  레코드에서 10여 개 필드를 직접 읽고 그 레코드를 `Pagination`에 통째로 넘긴다. 필드마다
  헬퍼를 부르면 「화면마다 방어를 반복하지 않는다」는 결정에 정면으로 어긋나고 호출부가
  40곳 가까이 늘어난다. 그래서 입구에서 한 번 정규화한다.
- **빈 문자열은 통과시킨다** — 헬퍼의 역할을 「배열·부재 흡수」로만 한정했다. `?q=`를
  `undefined`로 바꾸면 `UserSearchBar`의 `defaultValue` 등 기존 동작이 미묘하게 달라진다.
