# [BadgeEngine] 수동 동기화가 새 활동 0건이면 배지 평가를 통째로 건너뛴다

> 근거 조사: `20260906_1426`. 후속 3건 중 **①(가장 작은 수정)**.
> 형제 티켓: `20260906_1431`(카탈로그 확장 시 재평가) · `20260906_1432`(지연 관측 수단)

## 배경 / 문제 정의

배지 평가는 「새 활동이 1건 이상 동기화될 때」에만 실행된다. 평가가 돌면 이력 전체를 다시
보므로 과거 활동으로 이미 넘긴 조건이 한꺼번에 발급되지만, **그 실행을 유발할 수 있는 것이
새 활동뿐**이라 카탈로그가 늘어난 시점부터 그 유저의 다음 활동까지 「조건은 충족인데 미발급」인
창이 열린다.

```ts
// src/lib/strava/sync.ts:902
const activityBadgeIds = activitiesFiltered.length > 0 ? await evaluateBadges(userId, activitiesFiltered) : []
```

**유저가 「동기화」 버튼을 눌러도 새 활동이 0건이면 이 줄에서 평가가 스킵된다.**
그래서 유저에게는 지연을 스스로 푸는 수단이 없다.

### 실측 (티켓 1426)

- `jamfather` — 마지막 배지 엔진 실행 `2026-09-05 07:49 UTC`. v5 카탈로그 630종 시딩은
  `20:25 UTC`로 **12시간 36분 뒤**다. 그 사이 새 활동이 없어 엔진이 한 번도 돌지 않았고,
  `running:C1` Common(조건 1일)을 **22일**째에도 받지 못한 상태로 관측됐다.
- 대조군 `cheerslovelymate` — 시딩 후인 `23:38`에 새 활동이 들어와 싱크가 돌자
  **v5 신규 배지 22종을 한 번에** 받았다.
- 초기화 직후 `jamfather`의 `last_synced_at`은 갱신됐는데(싱크는 돌았다)
  새 활동이 0건이라 `engine_decision_log`에 `sync_result`가 **한 건도 남지 않았다** —
  이 게이트가 실제로 평가를 막는다는 직접 증거다.

## 상세 요구사항

### 서비스/코드베이스 관점

- `sync.ts:902`의 `activitiesFiltered.length > 0` 게이트를 **배지 평가에 한해** 해제한다.
- **드랍·미션까지 함께 풀지 않는다.** 같은 `activitiesFiltered`를 `tryItemDrop`(856행)과
  `checkMissions`(934행)도 소비하는데, 이쪽은 「활동 1건마다 시도」가 전제라 0건에서 돌리면
  의미가 없거나 부작용 범위가 커진다. 이번 변경의 대상은 배지 평가 한 곳이다.
- 빈 배열로 `evaluateBadges`를 호출해도 안전한지 확인할 것 —
  `evaluateBadgesDetailed`는 `mergeActivityHistory(history, [])`로 이력만 평가하게 되므로
  **논리상 문제없어 보이나 실제 경로로 검증이 필요하다**(특히 `selectTriggerActivity`가
  `undefined`를 반환할 때 피드 `event_at`·`triggered_by_*` 저장 경로).
- 첫 싱크 게이트(`index.ts:1115`)와의 상호작용을 확인할 것 — 새 활동 0건인 유저가
  `initial_sync_done=false`인 경우 이 호출이 첫 싱크로 소비돼 플래그만 올라가고
  Common 외 등급이 영구히 막히는 일이 없어야 한다.

### UI/UX 관점

- 새 활동 0건인데 배지가 나오는 경우, 동기화 결과 문안이 「새 활동 0개」와 「배지 N개 획득」을
  동시에 말하게 된다. 현재 결산·연출 문안이 이 조합을 감당하는지 확인하고,
  어색하면 `Specs/UX_WRITING_GUIDELINE.md` 기준으로 다듬는다.

## 구현 계획

1. `sync.ts:902` 조건 분기 제거 또는 배지 전용 분기로 분리
2. 빈 배치 경로 검증 — `evaluateBadgesDetailed`의 트리거 활동 부재 처리
3. `sync.ts` 계약 테스트 보강 (새 활동 0건 + 미발급 배지 보유 → 발급되는지)
4. 첫 싱크 게이트 상호작용 회귀 확인

## 완료 기록 *(작업 완료 후 작성)*

### 구현 요약

- **원인**: 배지 평가를 막는 게이트가 **두 곳**이었다.
  1. `processFetchedActivities` 최상단의 `rawActivities.length === 0` 이른 반환(617행) —
     Strava가 새 활동을 하나도 돌려주지 않으면 함수 전체(POI 매칭·드랍·아이템북·미션·
     배지 평가)가 통째로 스킵된다. 실측(jamfather, 티켓 20260906_1426)의 실제 진원지가
     이쪽이었다 — 티켓이 지목한 902행 게이트만 벗겨서는 이 이른 반환에서 이미 막혀
     무의미했다.
  2. 티켓이 지목한 `activitiesFiltered.length > 0 ? await evaluateBadges(...) : []`
     삼항 게이트(원래 902행, 수정 후 922행 부근) — 새 활동은 있었지만 차량 속도 필터로
     전부 걸러진 경우.
- **변경 내용**:
  - ① 이른 반환 분기에서 `evaluateBadges(userId, [])`를 호출하고 그 결과로 결산 소식
    (`notifyActivityBadgesEarned`)까지 남긴 뒤 반환하도록 바꿨다. 드랍(tryItemDrop)·
    미션(checkMissions)·아이템북 완성 체크는 "활동 1건마다 시도"가 전제라 이 이른
    반환을 그대로 유지해 건너뛴다.
  - ② 삼항 게이트를 제거하고 `evaluateBadges(userId, activitiesFiltered)`를 무조건
    호출하도록 바꿨다(빈 배열이어도 안전 — 아래 검증 참고).
  - `evaluateBadgesDetailed`는 내부에서 `getActivityHistory`로 이력 전체를 다시 읽어
    이번 배치와 합치므로, 빈 배치를 넘겨도 "카탈로그가 늘어난 뒤 조건은 충족인데
    미발급"인 배지를 그 호출 한 번으로 잡아낼 수 있다 — 기존 `badge-engine-v5.test.ts`가
    `evaluateBadgesDetailed(USER_ID, [], ...)` 형태로 이미 광범위하게 이 계약을
    검증하고 있어(50여 곳) 빈 배열 경로 자체는 새 위험이 아니었다.
  - 트리거 활동 부재(`selectTriggerActivity`가 `undefined` 반환) 시 `triggered_by_*`는
    `?? null`로, 피드 `event_at`은 `?? undefined`로 이미 안전하게 처리돼 있음을 코드
    확인으로 검증(변경 없음).
  - 첫 싱크 게이트(`initial_sync_done`)는 `evaluateBadgesDetailed` 내부에서 DB로
    독립적으로 재조회하므로 `processFetchedActivities`의 `isFirstSync` 파라미터와
    분리돼 있다 — 새 분기에서 별도 처리 불필요. "Common 외 등급이 영구히 막히는" 상황은
    없다: 이제 배지 평가가 항상 실행되므로 `initial_sync_done` 플래그가 더 이상 영원히
    `false`로 묶이는 경로 자체가 사라졌다(자세한 논의는 alerts 참고).
  - UI/UX 확인: `SyncButton.tsx`·`d.today.syncDone`(“동기화 완료”) 어디에도 "새 활동
    N건" 문구가 없고, 배지 결산 메시지 빌더(`buildRecapMessage`)도 `activityCount`가
    2 미만이면 활동 건수 문구를 아예 만들지 않는다 — "새 활동 0개"와 "배지 N개 획득"이
    같은 문장에서 충돌하는 조합 자체가 없어 UX 문구 수정은 불필요.
- **테스트**: `sync-empty-batch-badge-eval.test.ts` 신규 — (1) `rawActivities=[]`일 때
  `evaluateBadges`가 빈 배열로 호출되는지, (2) 미발급 배지가 있으면 발급·결산까지
  이어지는지, (3) 드랍·미션이 건드려지지 않는지, (4) 활동은 있었지만 필터로 전부
  걸러져도(`activitiesFiltered=0`) 배지 평가가 실행되는지 — 4건 모두 통과.
  기존 `sync-family-progress-snapshot.test.ts`·`sync-vehicle-speed-filter.test.ts`·
  `sync-drop-order.test.ts`·`badge-engine-v5.test.ts`·`walking-badges-v4.test.ts` 포함
  9개 파일 151건 회귀 없음. 전체 `npx vitest run` 1066건 통과(스토리북 브라우저 프로젝트
  44개 파일은 "No test suite found" 환경 이슈로 기존부터 실패 — 본 변경과 무관).

### alerts
- **[WARN] 티켓이 지목한 게이트(902행) 하나만으로는 문제가 재현·해결되지 않는다.**
  `processFetchedActivities` 최상단(617행)에 `rawActivities.length === 0`이면 함수
  전체를 건너뛰는 별도의 이른 반환이 있고, `syncStravaActivities`(유일한 실제 호출부)가
  "새로 동기화할 활동이 0건"일 때 정확히 이 경로로 빈 배열을 넘긴다. 즉 티켓 배경에
  실측된 jamfather 사고(새 활동 0건 → 엔진 미실행)는 이 617행 이른 반환이 만든
  것이었고, 902행 삼항 게이트만 벗기면 617행에서 이미 막혀 아무 효과가 없었다.
  두 지점을 함께 고쳤다.
- **[WARN] "초회 연동 시 새 활동 0건"인 극단적 신규 유저 엣지 케이스.** Strava 연동
  직후 첫 콜백 동기화에서 실제로 활동이 0건(예: 갓 만든 빈 Strava 계정)이면, 새로
  추가한 이른-반환 분기가 `evaluateBadges(userId, [])`를 호출하고 그 안에서
  `initial_sync_done`이 즉시 `true`로 확정된다(획득 배지 유무와 무관하게 무조건).
  이후 그 유저가 진짜 첫 활동을 동기화할 때는 첫 싱크 게이트(`isFirstSync`)가 이미
  풀린 상태라, 원래 "첫 백필은 Common만 발급"으로 완충하려던 설계가 그 유저에
  한해서는 적용되지 않는다(단일 활동으로 Rare 이상 조건을 즉시 채우는 경우에 한해
  영향). 반대 방향(영구 미발급)은 이번 수정으로 사라졌으므로 티켓이 명시한 인수
  기준("Common 외 등급이 영구히 막히는 일이 없어야 한다")은 충족한다. 다만 이 좁은
  엣지 케이스는 실사용 데이터로 검증하지 못해 리뷰어 확인을 권한다 — 필요하면 후속
  티켓으로 분리.
