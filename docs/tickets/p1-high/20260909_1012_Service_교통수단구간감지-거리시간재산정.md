# [Service] 걷기·러닝·자전거 활동에서 교통수단 구간 감지·거리/시간 재산정

## 배경 / 문제 정의
> 왜 이 작업이 필요한가. 현재 상태와 기대 상태의 차이.

`sihyunrr@gmail.com` 계정의 실사례(2026-09-08 "Morning Walk", distanceKm 2.5, maxSpeedKmh
119.5, averageSpeedKmh 7.0 — 집→지하철역 도보, 지하철 탑승, 하차 후 회사까지 도보)로 확인됐듯,
걷기 활동 중간에 지하철·버스 같은 교통수단 구간이 섞여도 현재 필터는 이를 걸러내지 못한다.

`processFetchedActivities`의 차량속도필터(`jam-web/src/lib/strava/sync.ts:856`)와
`passesWalkingGate`(`jam-web/src/lib/badge-engine/activityFilters.ts:33`) 둘 다
`averageSpeedKmh`만 검사하기 때문에, 짧은 교통수단 구간이 전체 평균을 크게 끌어올리지 않는 한
정상 활동으로 통과한다. 그 결과 실제보다 부풀려진 거리·시간이 배지·드랍·미션 판정에 그대로
반영된다.

## 현재 상태 (검증 완료, 2026-09-09 기준)

| 검증 지점 | 사용 필드 | 한계 |
|---|---|---|
| 차량속도필터(`sync.ts:856`) | `averageSpeedKmh` | 순간 최고속도·정지구간 비율 미반영 |
| 걷기 축1 게이트(`activityFilters.ts:33`) | `distanceKm`·`movingTimeSec`·`averageSpeedKmh` | 동일 |
| `getActivityStreams`(`api.ts:181`) | `latlng`만 요청 | 속도·시간 스트림 미조회 |

`getActivityStreams`는 이미 매 동기화마다 최근 10개 활동(`MAX_POI_MATCH_ACTIVITIES_PER_SYNC`,
`sync.ts:52`)에 대해 POI 체크인 매칭용으로 호출되고 있다(`sync.ts:660~665`). 이 호출을 확장하면
API 호출을 추가하지 않고 속도·시간 스트림을 함께 받을 수 있다.

## 상세 요구사항

### 서비스/코드베이스 관점

1. `getActivityStreams`가 요청하는 `keys`에 `velocity_smooth`·`time`을 추가하고, 반환 타입에
   그 두 배열을 포함시킨다.
2. 걷기·러닝·자전거 활동 중 `maxSpeedKmh`가 활동 타입별 임계값을 넘는 경우에만, 받아온
   `velocity_smooth` 배열에서 그 임계값을 **30초 이상 연속으로 초과하는 구간**을 찾는다.
   - **걷기**: 20km/h(엘리트 경보 선수 최고 기록보다도 높음)
   - **러닝**: 27km/h(800m~마일 세계기록 페이스 기준 — 30초 지속 구간을 감지하는 것이므로,
     2시간을 버티는 마라톤 페이스(~21km/h)가 아니라 1~2분대 단거리 세계기록 페이스가 물리적으로
     정확한 상한선이다. 이 값보다 낮으면 정상적인 인터벌 훈련·라스트 스퍼트를 오탐한다)
   - **자전거**: 55km/h(엘리트 로드 사이클링 평균속도 40~45km/h + 내리막 스퍼트 여유분. 기존
     차량속도필터(전체 활동 평균 60km/h 기준)가 이미 있으므로, 이번 신규 검증은 "평균은 정상
     범위인데 짧은 구간만 교통수단이 섞인" 케이스를 잡는 보완재 역할이다)
3. 그 구간의 거리·시간을 전체 `distanceKm`/`movingTimeSec`에서 제외해 재산정하고,
   `averageSpeedKmh`도 재계산한다.
4. 재산정된 값을 `normalizeActivity()` 이후·배지/드랍/미션 판정 이전에 해당
   `NormalizedActivity`에 반영한다.
5. 임계값(활동 타입별 속도·최소 지속시간)은 `abusing_policy`(`src/lib/abusing/policy.ts`의
   `AbusingPolicy`/`DEFAULT_POLICY`) 패턴을 그대로 따라 새 필드로 추가한다 — 기존
   `vehicle_speed_filter_kmh`와 같은 방식으로 어드민 화면에서 조정 가능해진다.
6. 스트림 조회 실패(네트워크 오류·404) 시 기존 `averageSpeedKmh` 기준 판정으로 되돌아간다
   (fail-open — 기존 POI 매칭 실패 처리 패턴과 동일).

### UI/UX 관점 (해당 시)
- 새 임계값 필드가 기존 `abusing_policy` 어드민 화면(`vehicle_speed_filter_kmh` 옆)에
  조회·수정 가능하게 노출되어야 한다. 신규 화면은 만들지 않는다.

### 컨텐츠 관점 (해당 시)

## 범위 밖 (후속 티켓으로 분리)

- **소급 재평가**: 이번 신규 판정 로직이 배포되기 전 이미 처리된 과거 활동·배지·드랍의 일괄
  재검토는 별도 티켓으로 분리한다.
- **배지·드랍 자동 회수**: 소급 재평가로 문제가 발견되더라도 자동 회수 기능은 만들지 않는다.
  검출 결과는 관리자 검토로 넘기고, 실제 회수는 기존 포인트의 `abuse_reclaim` 사유와 같은 수동
  절차를 따른다(자동 회수 기능은 현재 코드에 없다).
- `MAX_POI_MATCH_ACTIVITIES_PER_SYNC`(10개) 밖의 백필 활동은 이번 범위에서 스트림을 조회하지
  않아 이 검증을 받지 못한다 — 소급 재평가 티켓에서 함께 다룬다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- `getActivityStreams`(`api.ts`)가 `keys=latlng,velocity_smooth,time`을 요청해 route 외에
  velocity_smooth(m/s)·time(누적 초) 배열을 함께 돌려주도록 반환 타입을 `ActivityStreams`
  객체로 확장했다. 네트워크 오류·비-2xx는 여전히 `null`(fail-open 신호), 404는
  `{route:null, velocitySmooth:null, time:null}`.
- `abusing_policy`에 `transit_walk_max_speed_kmh`(20)·`transit_run_max_speed_kmh`(27)·
  `transit_cycling_max_speed_kmh`(55)·`transit_segment_min_duration_sec`(30) 4개 필드를
  추가했다 (마이그레이션 148, `DEFAULT_POLICY`·`database.ts`·`database.generated.ts` 동기화,
  어드민 `/admin/abusing` 화면에 입력 노출).
- 신규 `src/lib/strava/transitSegment.ts`의 `detectAndExcludeTransitSegments()`가 걷기·러닝·
  자전거 활동 중 `maxSpeedKmh`가 활동 타입별 임계값을 넘는 경우에만 `velocity_smooth`에서
  30초 이상 연속 초과 구간을 찾아 거리·시간을 제외하고 `averageSpeedKmh`를 재계산한다.
  스트림이 없거나 부족하면(길이 불일치 등) fail-open으로 원본을 그대로 돌려준다.
- `sync.ts`의 `processFetchedActivities`가 POI 매칭 대상(최신 10건)에 대해 이미 호출하던
  Streams API 응답을 재사용해(추가 API 호출 없음) `normalizeActivity()` 직후·차량속도필터
  (Phase 18)·배지/드랍/미션 판정 이전에 `activities` 배열을 제자리에서 교체한다.
  `getAbusingPolicy()` 호출을 앞으로 당겨 교통수단 구간 감지와 Phase 18 차량속도필터가
  같은 정책 스냅샷을 공유하도록 정리했다(기존 이중 조회 제거).
