# [BadgeEngine] 액티비티 배지 발급 경로에 섀도우밴 게이트가 전혀 연결돼 있지 않다

## 배경 / 문제 정의

티켓 [20260910_1557](20260910_1557_BadgeEngine_JAM카테고리-서비스사용량-배지엔진-신설.md)
(`/jam-work` engine 파이프라인)의 게이트 리뷰·개선 리뷰 양쪽에서 독립적으로 발견한 범위 밖
이슈.

일반 액티비티 배지 발급 경로(`jam-web/src/lib/badge-engine/index.ts`)에 어뷰징 방지용
섀도우밴 게이트(`getUserBanLevel`/`shouldAllowDrop`, `src/lib/abusing/shadow-ban.ts`)가
전혀 연결돼 있지 않다 — `grep` 결과 이 두 함수의 사용처는 `drop-engine/index.ts`(아이템 배지),
이번에 신설된 `usageBadges.ts`(서비스 사용량 배지), `abusing/poi-block.ts`뿐이다. 즉
**아이템 배지와 서비스 사용량 배지는 밴 레벨에 따라 고가치 발급이 차단되지만, 정작 가장 오래되고
큰 카탈로그인 액티비티 배지(147종)는 밴 유저도 조건만 채우면 등급형·레벨형을 제한 없이
획득할 수 있는 상태다.**

[BADGE_ENGINE_UNIFIED.md](../../Specs/BadgeEngine/BADGE_ENGINE_UNIFIED.md) §1의 "공통 정책
(두 엔진 공유)"에는 "섀도우밴: 밴 레벨에 따라 고가치(rarity) 발급 차단"이라고 명시돼 있어,
문서상 정책과 실제 코드 사이에 괴리가 있다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 이 공백이 **의도된 정책인지, 놓친 구현인지** 먼저 확인이 필요하다 (문서에는 "공통 정책"으로
  적혀 있어 놓친 구현일 가능성이 높다).
- 놓친 구현이라면: 액티비티 배지 발급 경로(`evaluateBadgesDetailed`)에도 밴 레벨에 따른 고가치
  rarity 차단을 연결한다. `usageBadges.ts`의 적용 방식(등급형 배지에만 적용, `shouldAllowDrop`
  재사용)을 참고할 수 있다.
- 기존 대규모 유저 데이터에 소급 적용 시 영향 범위(이미 발급된 배지에는 영향 없음, 신규 발급만
  차단) 확인 필요.

## 구현 계획
> 이 티켓은 조사 후 구현 계획을 구체화한다 — 지금은 발견 기록 단계.

1. `getUserBanLevel`/`shouldAllowDrop`이 실제로 액티비티 배지 경로에서 빠진 것이 의도인지
   과거 티켓·PRD에서 확인
2. 의도치 않은 공백이면 `evaluateBadgesDetailed`에 연결하는 구현 진행
3. 회귀 테스트: 밴 유저가 고가치 액티비티 배지를 못 받는지, 기존 정상 유저 발급 흐름에
   영향이 없는지

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

**조사 결과 — 놓친 구현으로 판단**: `shadow-ban.ts`(2026-07-10, "투트랙 섀도우밴" 도입
커밋)부터 이후 관련 티켓(20260811_009, 20260813_002, 20260831_1115/1149/1259 등) 전부를
확인했으나, "액티비티 배지에는 섀도우밴을 적용하지 않는다"는 명시적 결정 근거를 찾지
못했다. 오히려:
- `BADGE_ENGINE_UNIFIED.md` §1 "공통 정책(두 엔진 공유)"이 섀도우밴을 명시.
- `SERVICE_OPERATIONS.md` §12(어뷰징 방어 시스템)는 섀도우밴을 오로지 "드랍"(아이템 배지)
  관점으로만 서술해 실제 코드(액티비티 배지 미연결)와 정확히 일치했다 — 이 문서 자체가
  "놓친 구현"의 증거였다.
- 유일하게 근접한 티켓(20260811_009, 20260801 커밋 64437899)은 "성과 배지는 명시적 수치
  조건으로만 검증되므로 캡 불필요"라고 했지만, 이건 **30일 롤링 홍수 방지 캡**(activity_type당
  최대 3개)을 제거한 근거이지 섀도우밴(rarity 상한)과는 다른 메커니즘이다. 오히려 GPS
  조작 감지의 존재 이유가 "활동 조건을 부정하게 채우는 것"을 막는 것인데, 액티비티 배지가
  "조건 달성 = 무조건 발급"이면 GPS를 조작해 조건을 채운 유저가 고가치 배지를 무제한
  받을 수 있는 구조적 허점이 있었다.

**구현**: `evaluateBadgesDetailed`(`badge-engine/index.ts`)의 발급 파이프라인에 "2.9단계
섀도우밴 게이트"를 신설 — 첫 싱크 게이트(2.8단계) 통과 후, DB 반영(3단계) 직전에 위치.
`usageBadges.ts`(티켓 20260910_1557)가 세운 판정을 그대로 재사용한다:
- `getUserBanLevel()`·`shouldAllowDrop()`(`src/lib/abusing/shadow-ban.ts`) 재사용.
- **rarity가 있는 배지만 대상** (등급형 + 반복형 등급 사다리). 레벨형(`rarity` NULL)은
  `(rarity IS NULL) = (level IS NOT NULL)` CHECK 제약(마이그레이션 130)에 따라 등급
  서열이 없으므로 대상 밖.
- `action === 'increment'`(반복형이 이미 보유한 등급의 회차만 올리는 경로, 새 행을 만들지
  않음)는 첫 싱크 게이트와 동일하게 이 게이트의 대상에서도 제외.
- drop-engine의 `applyShadowBanCap()`과 달리 **강등(rarity 하향)은 하지 않는다** — 강등은
  "활동당 최소 1개 확정"이라는 드랍 고유의 보장을 지키는 장치이고, 액티비티 배지는 «조건을
  충족한 바로 그 배지»가 성취의 증명이라 대신 지급할 하위 등급이 없다. 차단되면 그 배치에서
  단순 미발급(`missed`에 사유 기록)으로 남고, 조건 자체는 유지되므로 밴 해제 후 다음 평가에서
  정상 발급된다.
- 조회 비용은 발급 후보(`action === 'issue'` && `rarity` 있음)가 있을 때만 든다(대부분의
  호출은 DB 왕복 없음 — usageBadges.ts와 동일한 최적화).

### 주요 의사결정 / 핵심 메모
- **삽입 위치**: `gatedIssueList`(첫 싱크 게이트 통과분)를 순회해 `finalIssueList`를 만드는
  "2.9단계"로 분리했다 — usageBadges.ts처럼 발급 루프 안에서 즉석 continue하는 방식도
  가능했지만, 기존 코드가 이미 "1단계(후보 선정) → 2단계(트랙 병합) → 2.8단계(첫 싱크
  게이트) → 3단계(DB 반영)"로 게이트를 단계별로 분리해 둔 스타일과 통일하는 쪽을 택했다.
  발급 루프(3단계)는 순회 대상만 `gatedIssueList` → `finalIssueList`로 바뀌고 내부 로직은
  그대로다.
- **"등급형에만 적용"의 해석**: 티켓 본문은 "등급형 배지에만 적용"이라 했는데, 코드베이스의
  배지 종류 3분류(등급형/무한레벨형/반복형) 기준으로는 반복형도 `rarity`를 가질 수 있다
  (등급 사다리 1·5·20·50회 등). `usageBadges.ts`의 실제 판정 코드(`if (badge.rarity && ...)`)
  와 그 주석("rarity가 있는(등급형) 후보만")을 근거로, "등급형"을 "`rarity` 필드 유무" 기준
  으로 넓게 해석해 반복형 최초 발급(`action==='issue'`)도 대상에 포함시켰다. 반복형 카운터
  증가(`action==='increment'`)는 애초에 새 행을 만들지 않으므로 제외 — 이 구분(발급 vs
  카운터 증가)은 rarity 유무와 무관하게 별도로 필요했다.
- **강등 미적용**: drop-engine은 차단된 rarity를 common으로 강등해 "활동당 최소 1개"를
  지키지만, 액티비티 배지·서비스 사용량 배지 둘 다 강등 없이 단순 차단한다 — 이미
  `usageBadges.ts`가 이 선례를 세웠고, 액티비티 배지도 "조건을 충족한 특정 배지"가 발급
  단위라 대신 지급할 하위 등급 개념이 없다는 점에서 같은 판단이 맞다고 봤다.
