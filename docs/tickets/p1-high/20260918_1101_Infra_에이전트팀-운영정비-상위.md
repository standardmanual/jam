## 배경 / 문제 정의
2026-09-18 세션에서 새 파이프라인을 처음 실사용하며 다음이 드러났다.

- **카리나(메인 세션) 정의가 사실상 비어 있다.** 설계 원본(`docs/agents/workflow/agents/
  00_카리나_오케스트레이터.md`)의 원칙·하는 일/금지·처음 보는 유형 절차가 활성 문서 어디에도

  실제로 그 세션은 티켓 15건 이상을 한 세션에서 처리했고, 보고 양식을 쓰지 않았고, 바로잡힌
  일을 규칙표에 남기지 않았다.
- **토큰 실측**: 34줄짜리 여백 수정 티켓(20260915_2016)이 약 22만 8천 토큰·16분을 썼다
  (채원① 5.2만 · 아현 8만 · 민지 6.1만 · 채원② 3.5만).
- **파이프라인 결함**: 채원①의 `needs_approval`이 있어도 멈추지 않고 구현이 진행된다.
  워크트리가 최신 `origin/staging`보다 뒤처진 채 배정된다.
- **자동화·보고 경로 미정**: 예약 작업 스펙은 있으나 미등록, 리포트 저장 위치 없음, Slack은
  이전 결정("즉시 알림 도입 안 함", 티켓 0421)과 새 요구가 부딪힘.

  거절: CLAUDE.md 직접 삽입(서브에이전트 8명에게 매번 전달돼 토큰 증가), 개인 메모리(PC별 관리).
- **0-2 카드 범위: 핵심 + 위치 링크.** 원칙·하는 일/넘기는 일/금지·처음 보는 유형 절차만 담고
  (40줄 이내), 보고 양식·처리 규칙표·운영 규칙(`orchestrator.md`)은 위치만 안내한다.
  거절: 전부 담기(세션마다 고정 비용 증가).
- **0-3 세션 원칙: 권고 + 묶음 예외.** 기본은 티켓마다 새 세션. 상위 티켓으로 묶인 시리즈는 한
  세션 허용. 대화가 길어지면 카리나가 인수인계를 남기고 새 세션을 먼저 제안한다.
  거절: 엄격 적용(연속 작업이 번거로움), 자유(오늘처럼 한 세션이 끝없이 길어짐).
- **0-4 보고 양식: 티켓 결과·승인 요청 때만.** 일상 문답은 자유 형식.
  거절: 모든 응답(짧은 질문에도 길어짐).
- **0-5 규칙의 원본: 운영 규칙은 처리 규칙표(저장소).** 프로젝트 운영 교훈(티켓 번호 충돌,
  리베이스 동기화, 격리 워크트리 등)은 `handling-rules.md`가 원본이다. 개인 메모리에는 사용자

  카리나는 바로잡힌 일이 생기면 규칙표에 한 줄 추가한다.
  거절: 둘 다 유지(같은 교훈이 두 곳에 있어 어긋나고, 다른 PC는 메모리 쪽을 모름).
- **0-6 카리나 모델: 기본 Sonnet, 설계 세션만 Opus.** `settings.json`의 `model: sonnet` 유지.
  구조 설계처럼 판단이 많은 세션만 사용자가 `/model`로 Opus를 켠다.

### 안건 1 — jam-work 파이프라인 정비 (2026-09-18)
근거 실측: 34줄 여백 수정 티켓(20260915_2016)이 22만 8천 토큰·16분. 채원①은 티켓에 문제가
이미 적혀 있었는데 처음부터 조사(5.2만), 민지는 낡은 워크트리로 생긴 `[주의]` 때문에 검사를
재실행(6.1만).

- **1-1 `needs_approval`: 멈추고 묻기.** 채원① 다음에 파이프라인을 멈추고 카리나가 사용자에게
  묻는다. 승인되면 채원① 판정을 `reuseDecision`으로 재사용해 아현부터 이어서 돌린다.
  거절: 진행 후 결과 보고 때 묻기(거절되면 재작업 비용 발생).
- **1-2 경로: 3단 분리.** ① 경미(파일 1~2개·10줄 이내) = 카리나 직접 / ② 가벼운 UI(로직 변경
  없는 스타일·문구 수정이고 티켓에 고칠 내용이 확정됨) = 아현→민지 / ③ 표준 = 채원①→아현→
  민지→채원②. 경로는 카리나가 유형 판정 때 정하고 사용자에게 먼저 알린다.
  거절: 현행 2단(여백 수정에도 4명이 모두 돎).
- **1-3 성공 기준: 같은 규모 티켓 토큰 절반 이하.** 정비 후 비슷한 규모의 UI 티켓을 돌려
  22만 8천 대비 약 11만 이하인지 확인한다. 거절: 수치 기준 없음(줄었는지 판단 불가).
- **결정 불필요(결함·기존 규칙):** 워크트리가 최신 `origin/staging`보다 뒤처져 배정되는 결함 수정.
  카리나 요청문은 티켓 경로 + 한 줄 지시로 줄인다(공통규칙 2번, 티켓 `핵심 요약` 절 활용).

**안건 1 결정 완료.**

### 안건 2 — 에이전트별 워크플로 필요 여부 (2026-09-18)
기준: 워크플로는 백그라운드로 끝까지 돌아 **중간에 사용자에게 물을 수 없다.** 되묻기가 핵심인
일에는 맞지 않는다.

- **2-1 대화형(혜린·윈터·윤진): 스킬로 대화형 유지.** `/jam-plan`·`/jam-story`로 부르고 카리나가
  중간에 사용자에게 물으며 진행한다. 워크플로는 만들지 않는다.
  거절: 초안까지 워크플로(초안 방향이 틀리면 토큰 낭비).
- **2-2 점검형(카즈하·하니): 예약 실행 워크플로 대상.** 실행 환경·권한·주기는 안건 4에서 정한다.
  필요할 때 수동 호출도 가능. 거절: 수동 호출만(점검을 잊기 쉬움).
- **2-3 신규 에이전트 검증: 실제 업무로 시범.** 테스트용 호출은 하지 않고, 실제 업무의 첫
  호출을 '시범'으로 표시해 결과를 평가한다(카리나 "처음 보는 유형" 절차와 동일). 단 카즈하·하니는
  무인 실행이라 예약 등록 전에 반드시 1회 수동 실행한다.
  거절: 지금 전원 스모크 테스트(실제 가치 없는 토큰 소모).
- 워크플로가 필요한 것은 결국 **jam-work(개발) + 정기 점검(카즈하·하니)** 둘뿐이다.

**안건 2 결정 완료.**

### 안건 3 — 리포트 저장·양식·보관 (2026-09-18)
현 상태: 주간 브리핑 양식은 있으나 저장 위치가 없어 보고가 대화와 함께 사라진다. 현황판은
`DASHBOARD.md`로 계약만 있고 파일은 없다.

- **3-1 저장 위치: `jam-doc/operations/reports/` 신설.** 주간 `Reports/주간/YYYY-Www.md`, 월간

  "시점별 기록(쌓기만 하고 덮어쓰지 않음)"이라는 새 수명주기를 CLAUDE.md 폴더표와

- **3-2 보관: 읽기 상한만.** 파일은 계속 남기고, 에이전트는 주간 최근 4주·월간 최근 3개월만
  읽는다. 오래된 기록은 필요할 때 찾아 읽는다.
  거절: 분기 요약 후 Archive 이동(요약 비용 + 공통규칙 20번 "요약본을 만들지 않는다"와 충돌).

  없다. "최근 결정·다음 할 일" 수동 메모는 두지 않고 티켓 상태(IN_PROGRESS·WAITING)로 대신한다.
  `dashboard-format.md`의 `DASHBOARD.md` 저장 계약은 폐기한다.
  거절: 파일 저장·커밋(병렬 세션 충돌).

### 안건 4 — 자동화(예약 실행) (2026-09-18)
- **4-1 실행 환경: 클라우드.** PC·외장 드라이브 상태와 무관하게 정해진 시간에 돈다. 이 PC에만 있는
  비밀 값은 쓸 수 없으므로 필요한 값은 클라우드에 따로 등록한다.
  거절: 이 PC(월요일 09:00에 PC가 꺼져 있거나 드라이브가 빠져 있으면 건너뜀).
- **4-2 데이터 범위: 어드민 지표까지 처음부터 포함.** (추천안 "저장소·배포 정보만 먼저"와 다른
  사용자 결정.) 따라서 선행 조건 두 가지를 먼저 해결한다: ① 클라우드에서 쓸 어드민 인증 수단
  (현재는 사람이 브라우저에서 복사한 로그인 쿠키라 만료되면 조용히 실패함) ② 리포트가 저장소에
  커밋되므로 개인정보 처리 규칙. 또 어드민 API에는 KPI 전용 엔드포인트가 없어(`admin-api-read.mjs`
  주석) 필요한 지표를 정한 뒤 집계 API 신설 여부를 판단한다.
- **4-3 무인 카리나 권한: 읽기 + 리포트 + 티켓 초안.** 저장소 읽기, `jam-doc/operations/reports/`에 리포트
  저장·커밋, 명확한 문제는 `분류 대기` 티켓 초안까지. 금지: 코드 수정, 티켓 종료·우선순위 확정,
  머지, DB 변경, 외부 발행. 거절: 읽기 + 리포트만(카리나가 다음 세션에 티켓을 따로 만들어야 함).
- **4-4 진행 방식: 예약 작업 전체의 작업 방식을 먼저 정확히 설계한 뒤 등록.** (추천안 "주간 브리핑
  먼저 등록"과 다른 사용자 결정.) `scheduled-jobs.md`의 주간·월간 작업을 항목별로 문답해 확정한다.
- **4-5 어드민 인증: 자동화 전용 읽기 토큰 신설.** 어드민 API에 읽기(GET)만 허용하는 자동화 토큰
  인증 경로를 추가한다. 만료가 없고, 유출돼도 쓰기는 불가하며, 토큰 교체로 즉시 차단할 수 있다.
  어드민 API 경유 원칙(권한 검사 유지)도 지킨다.
  거절: 로그인 쿠키(`getAdminUser()`는 관리자 세션이면 쓰기까지 전부 허용하므로 클라우드에 맡기면
  어드민 전체 권한을 맡기는 셈 + 만료 시 조용히 실패), DB 읽기 전용 계정(어드민 API 경유 원칙과
  충돌, 공용 프로덕션 DB 직접 노출).
- **4-6 개인정보: 리포트에는 집계 수치만.** 닉네임·이메일·유저 ID 등 개인 식별 정보는 리포트에
  남기지 않는다. 개별 사례(어뷰징 의심 등)는 "의심 계정 N건, 어드민 화면에서 확인 필요"로만 적는다.
  거절: 닉네임 허용(git 이력에 영구히 남고 Slack 등으로 퍼질 수 있음).

- **4-7 주간 브리핑 지표 출처: GA4 + 작은 집계 API.** (사용자가 기존 GA4 연동 활용을 제안.)
  성장·행동 지표(활성 유저·가입 퍼널·드랍·픽업·믹스·미션 참가)는 GA4 Data API로 읽는다. 서비스
  계정에 GA 뷰어 권한만 주고, 키는 클라우드에 등록한다(권한 부여는 사용자가 GA 관리 화면에서 직접).
  GA가 볼 수 없거나 실제보다 적게 세는 운영 이상 4개(미션 달성자 수, 배지 발급량·중복, Strava
  동기화 실패, 앰비언트 드랍 만료)만 어드민 집계 API(`/api/admin/kpi/weekly`, 숫자만 반환, 4-5의
  읽기 토큰으로 호출)로 DB 기준 집계한다. 뉴스레터는 기능이 없어 대조 목록에서 뺀다.
  근거: GA4는 광고 차단기 유저를 놓치고, `mission_complete`는 최초 연동 경로에서 전송되지 않으며,
  배지 이벤트는 동기화 경로만 계측한다(`GA4_EVENTS.md` "알려진 계측 공백") — "0건이면 고장" 판정에
  쓸 수 없다.
  거절: GA4만(미션 조건 오류·Strava 장애를 못 잡음), 집계 API에 전부(퍼널 집계를 새로 만들어야 함).
- **4-8 홈피드 초안: 주간 예약 작업에 포함, 브리핑과 같은 파일.** 카즈하 브리핑 다음에 윤진이 다음
  주 홈피드(투데이 카드) 7일치 초안을 써서 `Reports/주간/YYYY-Www.md`의 "홈피드 초안" 절에 넣는다.
  승인은 기존대로 주 1회 7건 묶음(자동화 B1)이며 월요일 세션에서 처리한다. 안건 2-1에 단서를
  추가한다: **형식이 고정된 반복 초안은 예약 실행 가능**(유형 10개 중 요일 배치라 방향이 틀릴 여지가
  적고, 승인이 어차피 사후라 중간에 물을 일이 없다).
  거절: 별도 파일(월요일에 두 파일을 열어야 함), 대화형 유지(매주 반복 작업을 세션에서 손으로 돌림).
- **4-9 월간 작업: ① 트렌드 수집·② 문서 점검만 예약, ③ 시즌 제안은 세션.** 윈터·윤진 트렌드
  수집(웹 검색, 읽기 전용이라 4-3 권한 안)과 하니 문서 점검을 `Reports/월간/YYYY-MM.md`의
  "트렌드 노트"·"문서 점검" 절에 저장한다. 문서 점검의 명확한 문제는 `분류 대기` 티켓 초안으로
  남긴다. 시즌 제안(미션·아이템배지 후보·드랍 일정·경제 수치)은 전략 작업이라 월간 리포트를
  재료로 세션에서 `/jam-story`로 만든다. 소재 카드 "6개월 미채택 시 폐기"는 매달 리포트에
  **살아 있는 소재 카드 목록을 이월**하는 방식으로 처리한다(3-2 읽기 상한 3개월과 충돌하지 않고
  지난달 파일 하나만 읽으면 됨). 경제 수치는 무인 경로에서 제안하지 않으며, 세션에서 기존 규칙
  (범위 안 = 사용자 승인, 범위 밖 = 혜린 리스크 점검 후 사용자 승인)을 따른다.
  거절: 시즌 제안까지 예약(방향이 틀리면 초안 전체 폐기), 문서 점검만 예약(트렌드 수집을 잊기 쉬움).

- **4-10 실패 처리: 부분 리포트 + 누락 감지.** 수집 출처(GA4·집계 API·Vercel 등)가 실패하면 그
  출처만 1회 재시도하고, 그래도 실패하면 나머지로 리포트를 완성하며 맨 위에 "수집 실패: 출처
  (사유) → 비어 있는 항목"을 적는다. 리포트 파일 자체가 없으면(전체 실패) 세션 시작 hook이
  "예정 시각이 지났는데 이번 주·이번 달 리포트가 없음"을 감지하고 카리나가 다음 세션 첫 보고로
  알린다. 외부 알림(Slack)은 안건 5에서 정한다.
  거절: 전체 중단(출처 하나 때문에 나머지 정보까지 잃음). 반복 재시도는 인증 만료 같은 원인을
  해결하지 못하고 비용만 늘려 1회로 제한한다.
- **4-11 비용 상한: 임시 상한 후 4회 실측.** 예약 작업의 에이전트는 모두 Sonnet으로 실행한다. 임시
  상한은 주간 15만·월간 30만 토큰(월간은 웹 검색 때문에 두 배)이다. 매 실행의 실제 사용량을 리포트
  "비용" 절에 기록하고, 4회 실행 뒤 실측값으로 상한을 다시 정한다. 예약 실행 도구가 토큰 상한을
  강제로 끊을 수 있는지는 구현 티켓에서 확인하고, 불가능하면 "상한에 가까우면 수집을 멈추고 있는
  자료로 마무리"하라는 지시와 사후 기록으로 운영한다.
  거절: 상한 없이 실측만(초기 비용 급증을 막지 못함), 더 낮은 상한(리포트가 자주 잘림).
