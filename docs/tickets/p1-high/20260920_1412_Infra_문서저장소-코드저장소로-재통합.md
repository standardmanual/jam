# [Infra] 문서 저장소(jam-doc)를 코드 저장소로 재통합

## 핵심 요약

- 요구사항: 2026-09-18에 분리한 문서 저장소 `standardmanual/jam-doc`을 `standardmanual/jam`
  안으로 되돌린다. 폴더 위치(`jam-doc/`)는 그대로 두므로 경로 참조는 바뀌지 않는다.
- 구현 계획: `.gitignore`에서 `/jam-doc`을 지우고, `jam-doc/.git`을 제거하고, `jam-doc`의
  pre-commit 규칙을 `jam`의 pre-commit으로 이식한 뒤, 두 저장소를 전제하던 문서와 설정을
  전부 하나로 고친다.
- 관련 파일: `.gitignore`, `.githooks/pre-commit`, `scripts/doc-check.config.json`,
  `CLAUDE.md`, `.claude/settings.json`, `.claude/agents/jam-developer.md`,
  `.claude/skills/jam-work/SKILL.md`, `.claude/skills/jam-sync/SKILL.md`,
  `scripts/workspace-setup.sh`, `docs/agents/orchestrator.md`
- 상위 티켓: [20260920_0042 문서 저장소 경계 관찰 체계와 시드 생성기 정리](../p2-normal/20260920_0042_Infra_문서저장소-경계-관찰체계와-시드생성기-정리.md)
- 경로: ③ 표준 (`infra` 유형)

## 배경 / 문제 정의

사용자가 저장소 연동, 접근 권한, push 권한이라는 세 가지 마찰을 반복해서 겪는다고 보고했다.
근원적으로 조사한 결과, 세 가지는 서로 다른 문제가 아니라 **규칙은 저장소 두 개를 전제하는데
도구 설정은 한 개만 알고 있다**는 하나의 어긋남에서 파생된 증상이었다.

### 실측으로 확인한 사실

**① 권한 문제는 권한 문제가 아니다.**
`git -C jam-doc push --dry-run origin main`이 종료 코드 0으로 성공한다. 이 세션은 `jam-doc`에
push할 권한을 이미 가지고 있다. 진짜 원인은 `.claude/settings.json`의 `permissions.allow`에
`git -C jam-doc ...` 패턴이 하나도 없다는 것이다. 허용 규칙은 명령어 앞부분을 문자열로
비교하므로, CLAUDE.md 규칙 3이 지시하는 `git -C jam-doc push origin main`은 어떤 규칙에도
걸리지 않아 매번 승인 프롬프트를 띄운다. 규칙과 권한 설정이 서로를 모르는 상태였다.

**② 두 저장소의 보호 수준이 정반대로 비대칭이다.**

| | `jam` (코드, 배포됨) | `jam-doc` (문서, 배포 없음) |
|---|---|---|
| 기준 브랜치 | `staging` | `main` |
| `pre-push` 훅 | 있음 (main 차단·lint·verify) | 없음 |
| main으로 push | 차단됨 | 아무 제약 없음 |

위험한 쪽은 겹겹이 막혀 있고 안전한 쪽에는 규칙이 없는데, 브랜치 이름이 `main`이라서 같은
긴장을 유발했다. 사용자가 "스테이징과 메인 push 권한 문제"로 인식한 혼란의 실체다.

**③ 격리 워크트리에 `jam-doc`이 없다.**
`.claude/agents/jam-developer.md` 규칙 9는 "심볼릭 링크로 연결되므로 워크트리에서 원문을 읽어
diff를 만들라"고 지시한다. 그러나 실제 워크트리(`wf_37cd829c-139-1`)에는 `jam-doc`이 없고,
`.claude/skills/jam-work/SKILL.md` 227행은 반대로 "격리 워크트리에는 `jam-doc`이 없어 아현은
갱신안만 적는다"고 적혀 있다. 두 문서가 정면으로 모순되며, 실제로 맞는 쪽은 후자다. 결과적으로
아현은 원문을 읽지 못한 채 diff를 만들어야 했고, 규칙 9의 1단계가 애초에 실행될 수 없었다.
티켓 7건(20260919_1249·1956·2254, 20260920_0042·0043·0044·0045)이 이 증상을 다뤘지만,
0043은 로그 남기기, 0045는 집계하기로 증상만 관리했고 원인은 그대로 남아 있었다.

**④ 분리를 지탱하던 물리적 근거가 이미 사라졌다.**
분리 당시 근거는 이미지 제작물 때문에 코드 저장소가 무거워진다는 것이었다. 2026-09-19에
`jam-doc`의 이미지를 지우고 이력을 재작성한 뒤 실측하면 `jam-doc` 작업본은 13MB(문서 3.5MB +
`assets/` 9.4MB)인 반면 `jam`의 `.git`은 82MB다. 문서 저장소가 코드 저장소보다 6배 가볍다.

### 통합 비용이 거의 없다는 확인

`jam-doc`을 `jam` 안으로 되돌려도 폴더 위치가 그대로이므로 경로가 하나도 바뀌지 않는다.
코드에서 `jam-doc/`을 참조하는 파일은 9개인데(`scripts/workspace-setup.sh`,
`scripts/ticket-dashboard.mjs`, `scripts/check-slop.mjs`, `scripts/verify.sh`,
`jam-web/src/components/admin/AdminEditorLayout.tsx`, `jam-web/src/lib/admin/badge-sections.ts`,
`jam-web/src/lib/badgeConditionText.ts`, `jam-web/src/lib/missions/gateMissions.ts`,
`jam-web/scripts/recraft/test-connection.js`) 전부 `jam-doc/planning/...` 형태라 통합 후에도
그대로 동작한다. 또한 `scripts/doc-check.config.json`은 이미 `jam-doc/` 경로를 검사 범위에
포함하고 있고, `scripts/doc-check.mjs`와 `jam-doc/scripts/doc-check.mjs`는 바이트 단위로
동일하다. 통합하면 이 중복이 저절로 해소된다.

## 상세 요구사항

### 서비스/코드베이스 관점

- `jam-web/` 코드는 한 줄도 바뀌지 않는다. 경로가 유지되기 때문이다.
- `jam-doc`의 과거 커밋 이력은 보존하지 않는다(사용자 결정, 2026-09-20). `jam-doc`은
  2026-09-19 이력 재작성으로 이미 과거 커밋이 한 번 끊어졌고, 원격 저장소
  `standardmanual/jam-doc`을 지우지 않고 남겨 두므로 이력이 필요하면 거기서 확인할 수 있다.
- `jam-doc/.githooks/pre-commit`의 규칙 3종(archive 읽기 전용, 서비스플랜 버전 사본 금지,
  TRIBES 버전 사본 금지)은 경로 앞에 `jam-doc/`을 붙여 `jam`의 pre-commit으로 이식한다.
- `jam-doc/scripts/`의 `doc-check.mjs`·`doc-check.config.json`·`doc-check-hook.test.mjs`는
  `jam` 쪽 사본과 중복이므로 제거한다.
- `scripts/doc-check.config.json`의 `externalPrefixes`에서 `jam-doc/`을 뺀다. 통합 후에는
  외부 경로가 아니므로 링크 검사 대상이 되어야 한다.

## 구현 계획

1. `jam-doc/.git`과 `jam-doc/.githooks`를 제거하고, `jam-doc/scripts/`의 중복 3파일을 지운다.
2. `.gitignore`에서 `/jam-doc` 줄을 지운다.
3. `jam-doc` pre-commit 규칙 3종을 `.githooks/pre-commit`으로 이식한다.
4. `scripts/doc-check.config.json`의 `externalPrefixes`를 고친다.
5. 두 저장소를 전제하던 문서·설정을 전부 하나로 고친다(관련 파일 목록 참조).
6. 잔여 워크트리와 브랜치를 정리한다.

## 완료 조건

- `git status`에 `jam-doc/`이 추적되지 않는 상태로 남아 있지 않다.
- `jam-doc/.git`이 존재하지 않는다.
- `scripts/verify.sh`가 통과한다.
- `jam-doc/` 안의 문서를 고친 뒤 `git commit` 한 번, `git push origin staging` 한 번으로
  작업이 끝난다.
- 격리 워크트리에서 `jam-doc/`을 읽을 수 있다.
- CLAUDE.md·`jam-developer.md`·`jam-work/SKILL.md`·`jam-sync/SKILL.md`에 "두 저장소",
  "갱신안", "중첩 복제"를 전제한 서술이 남아 있지 않다.
