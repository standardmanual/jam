# [Infra] 이식 ② 기준 방어 훅과 CI 검증 도장 — 검사 결과를 기계가 남기고, 기준을 낮추는 변경을 막는다

## 핵심 요약

- 요구사항: (a) GitHub Actions로 `scripts/verify.sh`를 커밋마다 실행해 결과를 커밋 상태로 남긴다(검증 도장). 민지의 점검표 1번과 카리나의 머지 전 확인은 이 상태를 읽는다. (b) `constraint-driven-development`의 「기준 방어(guard the bar)」를 pre-push에 이식한다: 새 `eslint-disable`·`@ts-ignore`·`.skip`·`.only`, `--max-warnings` 상향, 테스트 파일 삭제를 차단한다. (c) 링크드 워크트리에서의 `staging` push를 pre-push가 차단한다(20260921_2207 #4). (d) 기준 수치는 `docs/agents/contract.json`에 선언한다.
- 구현 계획: `.github/workflows/verify.yml` 신설(트리거: `claude/**`·`staging` push, 단계: checkout → node 설치 → `npm ci` → `scripts/verify.sh`), `.githooks/pre-push`에 기준 방어·워크트리 차단 절 추가, `contract.json`에 `quality_bar` 절 신설, `jam-reviewer.md` 점검표 1번 문구 갱신, `/jam-work` SKILL.md 4단계 머지 전 확인에 상태 확인 추가.
- 관련 파일: `.githooks/pre-push`, `.github/workflows/`(신규), `docs/agents/contract.json`, `scripts/check-contract.mjs`(선언 검사 확장 시), `.claude/agents/jam-reviewer.md`(Checklist 1·「Re-running checks yourself」), `.claude/skills/jam-work/SKILL.md`(4단계), `jam-web/package.json`(`lint:ci --max-warnings 26`). 원본 스킬: `~/.claude/plugins/cache/addy-agent-skills/agent-skills/0.6.10/skills/constraint-driven-development/SKILL.md`(§Step 6 Guard the bar·§Floor), `~/.claude/plugins/cache/addy-agent-skills/agent-skills/0.6.10/skills/ci-cd-and-automation/SKILL.md`
- 상위 티켓: 20260921_2219. 포함하는 개선점: 20260921_2207 #1(검증 도장)·#4(staging push 차단). 경로: ③ 표준(infra)
- **2026-09-22 사용자 결정으로 요구사항 1번(CI 범위)과 3번(워크트리 차단 범위)이 바뀌었다. 「사전 확인과 결정」 절이 상세 요구사항 원문보다 우선한다.**

## 배경 / 문제 정의

운영 점검(20260921_2207)에서 최근 CLOSED 59건 중 22건(37%)에서 민지가 `verify.sh`·테스트를 다시 돌렸고, 9건(15%)에서 `JAM_SKIP_*` 우회가 쓰였다. 원인은 "통과했다"는 사실을 기계가 어디에도 남기지 않아 확인 방법이 재실행뿐이라는 점이다. JAM에는 CI가 없고 훅만 있다(`.github/workflows` 부재). 또 아현의 `staging` push 금지는 프롬프트 규칙뿐이고(pre-push는 main만 차단), 검사 기준을 낮추는 변경(eslint-disable 추가·테스트 skip)을 막는 장치가 없다. 사고 이력의 결론("프롬프트로 막은 것은 예외 없이 뚫렸다")을 이 세 곳에 적용한다.

## 상세 요구사항

### 서비스/코드베이스 관점

1. **CI 검증 도장**: Actions 워크플로가 `claude/**`·`staging` push에서 `npm ci` 후 `scripts/verify.sh`를 훅 없이 직접 실행한다(`JAM_SKIP_*` 환경변수는 CI에서 무시된다). 결과는 커밋 상태(check)로 남는다. 카리나가 상태를 읽는 명령(`gh run list --commit <sha>` 또는 `gh api`)을 `/jam-work` 4단계 오염 검사 옆에 적는다. 민지 점검표 1번은 "push 시점 verify 통과"에서 "CI 상태 성공"으로 바꾸고, 재실행 조건에서 "[주의] 알림"을 뺀다(재실행은 상태가 없거나 실패했을 때만).
2. **기준 방어(pre-push)**: 이번 push 범위의 diff에서 다음을 차단한다 — `eslint-disable`(파일·줄 단위 모두)·`@ts-ignore`·`@ts-expect-error` 신규 추가, `it.skip`·`describe.skip`·`.only` 신규 추가, `*.test.*` 파일 삭제, `package.json`의 `--max-warnings` 값 상향. 정당한 예외는 우회 변수 대신 **diff 안의 사유 주석**(예: `// eslint-disable-next-line ... -- 사유`)이 있을 때만 통과시킨다.
3. **워크트리 차단**: `git rev-parse --git-common-dir`이 `.git`이 아닌 곳(링크드 워크트리)에서 `staging`으로 push하면 차단한다. 우회 변수는 두지 않는다. 카리나는 메인 트리에서만 push한다.
4. **선언**: `contract.json`에 `quality_bar` 절(`lint_max_warnings: 26`, 차단 패턴 목록)을 두고, `package.json` 값과 훅의 패턴이 선언과 일치하는지 `check-contract.mjs`가 대조한다.
5. **비용 기록**: Actions 실행 1회의 소요 시간과 분당 과금(비공개 저장소)을 완료 기록에 남긴다. 리뷰 브랜치 push는 Vercel 빌드를 만들지 않으므로 CI만 는다.

## 사전 확인과 결정 (카리나, 2026-09-22)

### 사용자 결정

1. **CI는 리뷰 브랜치(`claude/**`) push에서만 실행한다. staging push에서는 실행하지 않는다.** 비공개 저장소라 GitHub Actions 무료 한도(요금제에 따라 월 2,000~3,000분)를 쓰기 때문이다. 절약 장치를 함께 둔다.
   - 문서만 바뀐 push(`jam-web/`·`scripts/`·`.githooks/`·`.github/` 변경 없음)는 `npm ci`를 건너뛰고, 설치 없이 돌 수 있는 검사(`check-slop`·`check-contract`·`gen-team-doc --check` 등)만 실행한다. 지금의 `verify.sh`는 `jam-web/node_modules`가 없으면 곧바로 실패로 끝나므로, 이 경우를 위한 실행 방식이 필요하다.
   - 같은 브랜치의 이전 실행은 취소한다(`concurrency`의 `cancel-in-progress`).
   - 1주 실측 후 사용량에 여유가 있으면 staging 추가를 검토한다(잔여 이슈로 남긴다).
2. **워크트리 차단은 에이전트 작업 공간으로 좁힌다.** staging으로 가는 push를 다음 중 하나라도 해당하면 막는다. 우회 변수는 두지 않는다.
   - (a) 현재 위치가 링크드 워크트리이고, 그 폴더 이름이 `wf_`로 시작한다(Workflow가 만든 에이전트 작업 공간. 이번 세션에서 `.claude/worktrees/wf_fcd968f6-261-1`로 확인).
   - (b) push하는 로컬 브랜치가 `claude/jamwork-*`(아현의 리뷰 브랜치)이다. `git push origin HEAD:staging`처럼 로컬 ref가 `HEAD`로 들어오는 경우에도 현재 브랜치 이름으로 판정한다.
   - 카리나의 수동 격리 워크트리(처리 규칙표 17·21행)는 그대로 쓴다. 대신 카리나는 격리 브랜치에 `claude/jamwork-*` 이름을 쓰지 않는다. `.claude/skills/jam-work/references/handling-rules.md` 17행에 이 문구를 보탠다.

### 확인한 사실

- 링크드 워크트리 판별: 메인 트리에서는 `git rev-parse --git-dir`과 `--git-common-dir`이 둘 다 `.git`이고, 링크드 워크트리에서는 `--git-dir`이 `<메인>/.git/worktrees/<이름>`, `--git-common-dir`이 `<메인>/.git`이다(임시 저장소 실험). 원문의 "`--git-common-dir`이 `.git`이 아닌 곳"은 판별 기준이 되지 않는다. 두 값을 절대경로로 바꿔 비교한다.
- `core.hooksPath`는 절대경로 `<메인>/.githooks`로 설정돼 있어, 링크드 워크트리에서 push해도 **메인 트리의 `.githooks/pre-push`**가 돈다. 따라서 리뷰 브랜치에서 고친 훅은 그 브랜치 자신의 push에 적용되지 않는다. 동작 확인은 임시 저장소 테스트로 한다.
- pre-push의 staging lint 게이트는 `$(git rev-parse --show-toplevel)/jam-web`, 즉 명령을 실행한 폴더의 작업 파일을 검사한다.
- CI 환경:
  - Node는 24를 쓴다. Vercel `jam`·`jam-stage` 프로젝트가 모두 24.x다(`vercel project inspect`로 확인). 저장소에는 Node 버전 지정(`.nvmrc`·`engines`)이 없다.
  - 새 체크아웃에는 `core.hooksPath`가 비어 있어 `check-contract`의 `git_config` 검사가 실패한다. verify 전에 `git config core.hooksPath .githooks`를 실행한다.
  - `scripts/*.test.mjs` 중 커밋하는 테스트는 신원을 스스로 설정한다(`grep` 확인). 전역 git 신원이 없는 CI에서도 통과하는지는 실측으로 확인한다.
  - `jam-web/vitest.setup.ts`가 테스트마다 환경변수를 비우므로, 테스트는 실제 비밀값 없이 돈다.
  - 의존성 `node_modules`는 약 800MB, 저장소 pack은 약 134MB다. 로컬 `verify.sh` 전체 실행은 55초(lint 캐시가 있는 상태)였다. `actions/setup-node`의 npm 캐시(`cache-dependency-path: jam-web/package-lock.json`)를 쓴다.
- 워크플로 파일 push 권한: `gh` 토큰에는 `workflow` 권한이 있다(`gh auth status`). git push는 osxkeychain 자격 증명을 쓰는데, 그 토큰의 권한은 확인하지 못했다. `.github/workflows/` 파일 push가 권한 부족으로 거부되면 `git -c credential.helper= -c 'credential.helper=!gh auth git-credential' push ...`로 push한다.
- 저장소는 비공개이고 개인 계정 소유이며 Actions는 켜져 있다. 결제 설정(한도 초과 시 과금 여부)은 현재 `gh` 권한으로 조회되지 않는다.
- `jam-web/package.json`의 `lint:ci`는 `--max-warnings 26`이다(원문과 일치).

### 카리나 판단 (원문이 정하지 않은 부분)

- **테스트 파일 삭제의 예외**: 삭제된 파일에는 사유 주석을 남길 수 없으므로, 같은 push 범위의 커밋 메시지에 `테스트 삭제: <사유>` 줄이 있으면 통과시킨다. 커밋 메시지는 이력에 남으므로 우회 변수와 달리 추적할 수 있다.
- **`.only` 패턴**: `it.only(`·`test.only(`·`describe.only(`처럼 테스트 함수에 붙은 경우만 잡는다.
- **민지의 CI 상태 확인**: 문서만 바뀐 push의 도장은 가벼운 검사의 결과다. 민지 점검표 1번은 "해당 커밋의 CI 상태가 성공"으로 판정하고, 상태가 없거나 실패했을 때만 직접 재실행한다.

## 구현 계획

1. 임시 저장소에 훅을 복사해 기준 방어 4종과 워크트리 차단을 테스트한다(`scripts/*.test.mjs` 형식, `GIT_*` 제거 규칙 준수 — 가드레일 패턴 15).
2. 워크플로 파일을 작성하고 리뷰 브랜치 push로 1회 실측한다.
3. 정의·스킬·contract 문서를 갱신하고 `gen-team-doc` 생성 구간이 걸리면 생성기를 돌린다.

## 완료 조건

- 리뷰 브랜치 push 뒤 GitHub에 커밋 상태(verify)가 남고, `gh`로 조회한 결과가 완료 기록에 있다(실측 1회).
- 임시 저장소에서 기준 낮춤 변경 4종(eslint-disable 추가·@ts-ignore 추가·.skip 추가·테스트 파일 삭제)의 push가 각각 다른 문구로 막히고, 사유 주석이 있는 eslint-disable은 통과한다.
- 임시 저장소 테스트에서 `wf_*` 링크드 워크트리의 staging push와 `claude/jamwork-*` 브랜치의 staging push(`HEAD:staging` 포함)가 막히고, 다른 이름의 링크드 워크트리와 메인 트리에서의 staging push는 통과한다.
- 커밋 메시지에 `테스트 삭제: <사유>` 줄이 있는 push의 테스트 파일 삭제는 통과한다(임시 저장소 테스트).
- CI는 `claude/**` push에서만 돌고, 문서만 바뀐 push에서는 설치 없는 가벼운 검사로 상태가 남는다. 전체 검사와 가벼운 검사의 실행 시간을 각각 완료 기록에 남긴다.
- `handling-rules.md` 17행에 카리나의 격리 브랜치는 `claude/jamwork-*` 이름을 쓰지 않는다는 문구가 있다.
- `jam-reviewer.md` 점검표 1번과 재실행 조건이 갱신되어 있고, `/jam-work` SKILL.md 4단계에 상태 확인 명령이 있다.
- `contract.json`에 `quality_bar` 선언이 있고 `check-contract.mjs`가 대조한다. `scripts/verify.sh` 통과.
