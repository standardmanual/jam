# [Infra] 카리나의 여섯 단계 판정 규칙(진입 조건·정지 조건 단일 원천)과 묶음 실행 모드

## 핵심 요약

- 요구사항: 사용자 결정(2026-09-21)대로 워크플로 뿌리를 「카리나 주도 여섯 단계(Define→Plan→Build→Verify→Review→Ship)」로 확정한다. `/jam-work` SKILL.md의 유형 판정 앞에 **단계 판정**(각 단계의 진입 조건·실행 주체·사용자 승인 지점)을 두고, **정지 조건 목록**을 한 곳에만 정의해 묶음 실행·야간 루프·재작업이 모두 참조하게 한다. 묶음 실행 모드는 상위 티켓 단위로만 켠다.
- 구현 계획: SKILL.md 0절 앞에 「0.0 단계 판정」 표를 추가하고, `references/handling-rules.md`(또는 새 `references/stop-conditions.md`)에 정지 조건을 단일 원천으로 둔다. `jam-work.js`에 `batch` 인자(상위 티켓 ID)를 추가해 하위 티켓을 순서대로 실행하고, 티켓마다 게이트를 돌리며, 정지 조건에서 반환한다. 카리나 카드에 "단계 판정 → 유형 판정" 순서와 「가정 목록 공개」 규칙을 넣는다.

- 상위 티켓: 20260921_2219 §6. 경로: ③ 표준(infra)

- **2026-09-22 실측 참고(게이트 2회 FAIL 뒤 카리나 확인):** Workflow 스크립트는 파일시스템과 Node API를 전혀 쓸 수 없다(`import()`도 하네스가 시작 단계에서 거부한다 — 브랜치 스크립트를 `scriptPath`로 넘겨 실측). 따라서 "`jam-work.js`가 `docs/tickets/`를 읽어 하위 티켓을 찾는다"는 원래 설계는 실행이 불가능하다. 하위 티켓 조회·정렬·유형 판정은 `scripts/batch-tickets.mjs`(Node)로 옮기고, 워크플로는 그 출력을 `batch` 인자로 받아 순서대로 실행만 한다(참조 문서의 "목록은 스크립트 밖에서 먼저 구한다" 방식).

## 배경 / 문제 정의

이식 분석(20260921_2219 §6.1)에서 여섯 단계를 카리나의 판정 순서로 삼기로 했다. 지금 `/jam-work`는 유형 판정(0.2)만 있고 "이 요청이 어느 단계에 있는가"와 "다음 단계로 넘어갈 조건"이 문서에 없다. 정지 조건(게이트 FAIL·[중단]·`db`/`engine` 진입·되돌릴 수 없는 작업·채원 `needs_approval`)도 SKILL.md 3절, 루프 제안(20260921_2234), 아현 정의에 흩어져 있어 갈라질 위험이 있다.

## 상세 요구사항

### 서비스/코드베이스 관점

1. **단계 판정 표**(2219 §6.1 표를 옮긴다): DEFINE·PLAN·BUILD·VERIFY·REVIEW·SHIP마다 진입 조건 / 실행 주체 / 사용자 승인. 기계가 확인할 수 있는 조건(예: 완료 조건 절이 비어 있지 않다, `ui`·`ds`면 채원 판정이 있다)은 `check-contract`나 `ticket-dashboard`가 검사하도록 후속 항목으로 적는다.
2. **가정 목록**: 요청이 모호하면 BUILD로 보내기 전에 "이런 가정으로 진행한다" 목록을 사용자에게 보여 주고 확인받는다(`spec-driven-development` §Phase 1). 카리나 카드에 한 줄, SKILL.md 0절에 양식.
3. **정지 조건 단일 원천**: 목록을 한 파일에 두고 SKILL.md 3절·아현 정의·`jam-work.js` 주석·루프 문서는 그 파일을 가리킨다. 항목: 게이트 FAIL · `[중단]` 알림 · `db`/`engine` 유형 진입 · 되돌릴 수 없는 작업(DB 변경·외부 발행·프로덕션 배포) · 채원 `needsApproval` · 아현 `plan_only`/`needs_design`/`halted` · 같은 티켓 2회 연속 FAIL.
4. **묶음 실행(`batch`)**: 카리나가 먼저 `node scripts/batch-tickets.mjs <상위 티켓 ID>`를 실행해 하위 티켓 목록(JSON: 상위 ID, 티켓별 `id`·`path`·`status`·`category`·`workType`·`sequence`, 정지 예정 지점)을 얻는다. 이 스크립트가 `docs/tickets/`를 재귀로 훑어 `parent:` 필드가 일치하는 OPEN 티켓을 티켓 ID 순으로 모으고, 카테고리→유형 판정(Infra는 본문의 DB 단서로 `db`/`infra` 구분, frontmatter `workType:`이 있으면 최우선)을 한다. 그 출력을 `Workflow(name: 'jam-work', args: { batch: <스크립트 출력 객체> })`로 그대로 넘기면 워크플로가 목록을 순서대로 실행한다 — 워크플로는 파일을 읽지 않는다. 티켓마다 지금과 같은 파이프라인(채원①→아현→민지∥채원②)이 돌고, 정지 조건에 걸리면 그 티켓에서 멈춰 결과를 반환한다. 머지는 카리나가 순차로 한다(각 브랜치는 `origin/staging`에서 분기하므로 앞 티켓 머지 뒤 뒤 티켓은 오염 검사에 걸릴 수 있다 → 재분기 절차를 SKILL.md 4단계에 적는다). 기본은 끔. 사용자가 상위 티켓 분해안을 승인할 때 "묶음 실행"을 명시했을 때만 쓴다.
5. **토큰 기록**: batch 실행은 티켓별 `tokenUsage`를 티켓 ID로 나눠 반환한다.

## 구현 계획

1. 정지 조건 파일을 먼저 만들고 기존 문서 세 곳의 서술을 참조로 바꾼다.
2. SKILL.md 0.0절·가정 목록 양식·4단계 재분기 절차를 쓴다. 카리나 카드는 40줄 이내를 지킨다.
3. 하위 티켓 조회·정렬·유형 판정과 그 테스트를 `scripts/batch-tickets.mjs`·`scripts/batch-tickets.test.mjs`로 옮긴다(`verify.sh`의 scripts-test가 자동으로 돈다). `jam-work.js`의 `batch` 분기는 인자로 받은 목록을 순서대로 실행하고 정지 조건에서 멈추는 부분만 남긴다. 스크립트 안의 `import()`·파일 읽기는 전부 제거한다.
4. 드라이런 = `node scripts/batch-tickets.mjs <실제 상위 티켓 ID>` 출력. 아현이 실제 상위 티켓(예: 20260921_2207, OPEN 하위 5건) 1건으로 실행한 출력을 완료 기록 「테스트 결과」에 남긴다. 실제 하네스 실측(에이전트가 도는 batch)은 아래 「후속 범위」대로 카리나가 머지 뒤 수행한다.
5. 아현 정의를 손으로 옮겨 적은 미러 문서 `docs/agents/workflow/agents/01_아현_개발.md`의 `plan_only` 줄도 `stop-conditions.md` 참조로 바꾼다(2차 게이트 FAIL 사유).

## 완료 조건

- SKILL.md에 단계 판정 표와 가정 목록 양식이 있고, 카리나 카드에 "단계 판정 → 유형 판정" 순서가 한 줄로 있다(카드 40줄 이내 유지, `node scripts/ticket-dashboard.mjs` 출력 확인).
- 정지 조건이 한 파일에만 정의되어 있고, SKILL.md·아현 정의·`jam-work.js`·루프 검토 티켓의 후속 문서가 그 파일을 참조한다(`git grep`으로 중복 정의 0건).
- `scripts/batch-tickets.mjs`를 실제 상위 티켓으로 실행한 출력(드라이런 기록)이 완료 기록에 있고, 그 출력을 `batch` 인자로 받은 워크플로가 하위 티켓을 순서대로 실행하며 티켓별 결과·토큰을 나눠 반환한다(단위 테스트). `jam-work.js`에 파일시스템·`import()` 접근이 없다(`git grep`으로 확인).
- 기본 동작(`batch` 없이 호출)은 기존과 동일하다(기존 티켓 1건 실측으로 회귀 확인).

## 후속 범위 (이 티켓의 구현 범위 밖, 담당자·시점 명시)

- **실제 하네스 batch 실측**: 담당 카리나, 시점 이 브랜치 머지·push 뒤. `scripts/batch-tickets.mjs` 출력을 `batch` 인자로 넣어 실제 Workflow를 1회 돌리고 결과(티켓별 토큰·소요·정지 지점)를 이 티켓 완료 기록 「테스트 결과」에 추가한다. 아현은 Workflow 도구를 호출할 수 없으므로 이 항목은 게이트 판정 대상이 아니다.
- **기본 동작 회귀 확인(완료 조건 4)**: 담당 카리나, 시점 머지 뒤 다음 단일 티켓 실행 시. 이 티켓의 2·3차 재시도 자체가 리팩터링된 `runSingleTicket()`으로 돌았으므로 그 결과도 근거가 된다.
