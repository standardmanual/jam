# [Infra] 주간 무인 배포 경로에 `/jam-ship`의 새 관문을 어디까지 적용할지 정하고 루틴 프롬프트를 고친다

## 핵심 요약

- 요구사항: 티켓 20260921_2303이 `/jam-ship`에 신설한 「배포 전 점검표」「롤백 계획」「완료 기준」「배포 후 검증」은 사람이 세션에서 배포할 때만 적용된다. 목요일 23:59 KST 무인 배포(실행 루틴 `trig_01JRRY1cXt6uWGin8xbtS1Sk`)는 fetch → ff 머지 → push → `curl`만 수행한다. 무인 경로에 적용할 범위를 정하고, 루틴 프롬프트와 `scheduled-jobs.md`를 함께 고친다.
- 구현 계획: ① 클라우드 환경(`jam-ops`)에서 실행할 수 있는 점검을 가려낸다 ② 낮 확인 글에 마이그레이션 포함 여부와 롤백 계획 요약을 넣어, 사용자의 "승인" 답장이 그 계획까지 승인하도록 만든다 ③ 실행 루틴의 배포 확인을 "새 배포가 실제로 공개됐는가"까지 넓힌다 ④ 루틴 프롬프트를 교체한다.
- 관련 파일: `.claude/skills/jam-work/references/scheduled-jobs.md` 「주간 배포 승인」, `.claude/skills/jam-ship/SKILL.md`, 저장소 밖에 있는 루틴 프롬프트(claude.ai/code/routines)
- 상위 티켓: 20260921_2303. 출처: 민지 게이트 리뷰의 WARN 사유(회귀 위험). 경로: ③ 표준(infra). 무인 프로덕션 배포의 동작이 바뀌므로 적용 범위는 사용자 승인을 받아서 정한다.
- **2026-09-22 갱신:** 아래 「사전 확인과 결정」 절이 원문 요구사항·구현 계획보다 우선한다. 적용 범위를 확정했고 구현 명세를 추가했다. 저장소 안의 구현은 진행하고, **루틴 프롬프트 교체(외부 설정)만 사용자가 구체안을 확인한 뒤** 적용한다.

## 배경 / 문제 정의

확인된 사실(2026-09-22):

- 실행 루틴의 절차는 `scheduled-jobs.md` 「배포 실행」 절에 있는 bash 블록과 같다. 점검표·롤백 계획·완료 기준·배포 후 검증 단계가 없다.
- 주간 배포 루틴의 프롬프트는 "문서와 충돌하면 이 지시가 우선한다"고 명시한다(티켓 20260920_1933 완료 기록). 따라서 `scheduled-jobs.md`만 고쳐서는 무인 실행의 동작이 바뀌지 않는다.
- Vercel은 롤백을 실행한 뒤에 프로덕션 도메인 자동 할당을 끈다. 그 상태에서 main에 push하면 새 배포가 만들어져도 공개되지 않는다. 그런데 옛 배포가 계속 200으로 응답하므로, 실행 루틴의 `curl` 확인은 그대로 통과한다(Vercel 문서 「Performing an Instant Rollback」의 「Undo a rollback」 절).
- 첫 무인 실행 예정일은 2026-09-24(목)이다.

판단: 새 안전장치가 사람이 있는 경로에만 적용되어 있고, 사람이 없는 경로에는 적용되어 있지 않다. 다만 무인 경로의 동작 자체는 2303 이전과 같으므로, 기존보다 위험해진 것은 아니다.

## 상세 요구사항

### 서비스/코드베이스 관점

1. 무인 경로에서 실행할 수 있는 점검을 가려낸다. 비밀값 `grep`, 승격 범위 안의 신규 마이그레이션 파일 유무, 되돌림 SQL 동반 여부는 git만으로 확인된다. `scripts/verify.sh`·`npm audit`·`vercel env ls`·Supabase 적용 여부 대조는 클라우드 환경의 의존성 설치·인증·네트워크 허용 목록에 달려 있으므로, 실제로 실행되는지부터 확인한다.
2. 낮 확인 글(루틴 ①)에 "신규 마이그레이션 N건(되돌림 SQL 있음/없음)"과 롤백 계획 요약(되돌릴 직전 배포, 롤백은 사용자 승인 후 세션에서 실행)을 넣는다. 되돌림 SQL이 없는 마이그레이션이 포함된 주에는 무인 배포를 건너뛴다.
3. 실행 루틴의 배포 확인을 `curl` 200 확인에서 "프로덕션이 방금 push한 커밋의 배포를 가리키는가"로 강화한다. 클라우드에서 Vercel CLI 인증을 쓸 수 없으면 대안(빌드 커밋 SHA를 노출하는 응답 헤더나 엔드포인트)을 검토한다.
4. 무인 롤백은 계속 하지 않는다(기존 안전장치 유지). 이상이 감지되면 `#jam-alert`에 올리고 사용자 결정을 기다린다.
5. 루틴 프롬프트를 교체하고, 고친 부분의 before/after를 이 티켓에 남긴다. `scheduled-jobs.md` 「배포 실행」 절과 `/jam-ship` SKILL.md의 무인 경로 안내 문구를 같은 작업에서 맞춘다.

## 사전 확인과 결정 (카리나, 2026-09-22)

사용자 지시: "이 세션에서 생성된 범위밖발견물 티켓을 모두 실행해"(2026-09-22). 이 티켓은 원문 요구사항 5번대로 무인 프로덕션 배포의 동작을 바꾸는 일이라, 저장소 안의 구현은 진행하되 외부 설정인 루틴 프롬프트 교체는 사용자가 구체안(아래 「프롬프트 교체안」)을 확인한 뒤에 적용한다.

### 확인한 사실 (2026-09-22)

- 루틴 저장 프롬프트를 `RemoteTrigger get`으로 읽었다(읽기 전용). 확인 루틴(`trig_01XKT6nNQC1tgftdtzkYhw9R`, 목 15:00 KST)과 실행 루틴(`trig_01JRRY1cXt6uWGin8xbtS1Sk`, 목 23:59 KST)이 모두 켜져 있고, 다음 실행은 2026-09-24 15:02 KST와 23:59 KST다.
- 실행 루틴 프롬프트는 "scheduled-jobs.md를 먼저 읽어라"고 하면서도 "문서와 충돌하면 이 지시가 우선한다"고 적고, 절차 1~7이 프롬프트 안에 고정돼 있다. 문서에 새 점검을 적어도 프롬프트에 없으면 실행이 보장되지 않는다.
- 허용 도구는 `Bash·Read·Write·Grep·Glob`이고 Slack 커넥터가 붙어 있다. 세션의 결과 브랜치명은 `claude/hopeful-gates`이며 push는 `git checkout staging` 뒤 `git push origin staging`으로 한다.
- 프로덕션(`j-a-m.app`)과 스테이징(`stage.j-a-m.app`) 페이지 HTML의 정적 자원 주소에 `?dpl=dpl_...` 배포 식별자가 노출된다(공개 페이지 GET으로 확인). 스테이징 값 `dpl_36s5kY8qWaSbQL6ciuFZXF3drtd2`는 `vercel inspect`가 알려 주는 `jam-stage` 현재 프로덕션 배포 id와 같았다. **도메인이 지금 어느 배포를 서빙하는지를 Vercel 인증 없이, jam-web 코드 변경 없이 읽을 수 있다.** 롤백으로 자동 할당이 꺼진 상태에서는 새 배포를 push해도 이 값이 바뀌지 않으므로 그 상태가 감지된다.
- 현재 배포 대기 범위(`origin/main..origin/staging`)는 커밋 33개, `jam-web` 변경 파일 2개, 신규 마이그레이션은 번호 없는 `seed_*.sql` 2개다. 기존 비밀값 `grep`은 이 범위에서 오탐이 없었다. 지금까지 만든 번호 마이그레이션의 마지막은 179번이다.
- 클라우드 세션은 얕은 복제(shallow clone)일 수 있다(운영 지도 §9 ④). 그래서 점검은 이력 조회 없이 두 팁의 트리 비교(`git diff <base> <head>`)만 쓴다.

### 결정한 적용 범위

무인 경로에 넣는 점검은 모두 **배포를 막는 방향**이거나 읽기 전용이라 무인 권한이 늘지 않는다.

| 점검 | 무인 경로 | 사유 |
|---|---|---|
| 비밀값 노출(추가된 줄의 실제 비밀 형태) | 적용 | git만 쓴다 |
| 신규 번호 마이그레이션의 되돌림 SQL(번호 180 이상) | 적용 | git만 쓴다. 179 이하와 `seed_*.sql`은 규칙 신설(2026-09-22) 이전 파일이거나 1회성 데이터 스크립트라 요구하지 않는다 |
| 신규 API 라우트의 인증 확인 | 적용 | git만 쓴다 |
| 배포 뒤 서빙 배포 id 변경 확인 | 적용 | 공개 페이지 GET만 쓴다. 네트워크가 막히면 기존과 같이 "확인 불가(세션 네트워크 제약)"로 기록한다 |
| `scripts/verify.sh`·`npm audit`·`vercel env ls`·마이그레이션 적용 여부 대조 | 미적용 | 의존성 설치·Vercel 인증·DB 접근이 필요해 무인 환경에서 실행할 수 없다. 리뷰 브랜치 CI와 사람이 하는 `/jam-ship`이 맡는다 |
| 롤백 | 계속 하지 않음 | 기존 안전장치 유지. 이상이 보이면 `#jam-alert`에 올리고 사용자 결정을 기다린다 |

### 구현 명세 (아현)

1. `scripts/deploy-gate.mjs`: 의존성 없는 Node 스크립트(내장 모듈과 전역 `fetch`만 쓴다).
   - `check [--base <ref>] [--head <ref>] [--json]`: 기본값은 `origin/main` `origin/staging`. `git diff <base> <head>`(트리 비교)만 쓰고 `git log`·merge-base는 쓰지 않는다.
     - 비밀값: `jam-web/` 아래에서 **추가된 줄**만 검사한다. 걸리는 것은 `sb_secret_[A-Za-z0-9_-]{20,}`, JWT 형태 `eyJ[A-Za-z0-9_-]{15,}\.[A-Za-z0-9_-]{15,}\.[A-Za-z0-9_-]{15,}`, `(SUPABASE_SERVICE_ROLE_KEY|STRAVA_CLIENT_SECRET|ENCRYPTION_KEY|ADMIN_SECRET|CRON_SECRET)\s*[:=]\s*["'][^"'\s]{16,}["']`이다. 환경변수를 읽기만 하는 코드(`process.env.X`)는 걸리지 않아야 한다.
     - 마이그레이션: 추가된 `jam-web/supabase/migrations/NNN_*.sql` 가운데 NNN이 `contract.json`의 `deploy_gate.rollback_sql_required_from`(초기값 180) 이상이면, 파일 안에 되돌림 표식 줄(정규식 `^\s*--\s*(되돌림|ROLLBACK|DOWN)\b`, 대소문자 무시)이 있거나 같은 범위에 짝이 되는 `_down.sql`이 추가돼 있어야 한다. `seed_*.sql`은 개수만 보고하고 요구하지 않는다.
     - 새 API 라우트: 추가된 `jam-web/src/app/api/**/route.ts`는 `auth\.getUser|@/lib/admin/auth|CRON_SECRET|ADMIN_SECRET` 중 하나를 포함해야 한다. 의도한 공개 라우트는 `contract.json`의 `deploy_gate.public_routes`(현재 `dev-login`, `strava/callback`, `username/check`)에 등록한다.
     - 출력은 한국어 요약 줄(비밀값·마이그레이션·라우트별 결과, 신규 번호 마이그레이션 개수와 되돌림 SQL 유무, seed 파일 개수)이고 종료 코드는 0(통과)·1(차단)이다. `--json`은 같은 내용을 기계가 읽는 형태로 낸다.
   - `served [--url <url>] [--wait-change <이전 id>] [--timeout <초>] [--interval <초>]`: 페이지를 GET(리다이렉트를 따라간다)해 HTML에서 첫 `dpl=(dpl_[A-Za-z0-9]+)`을 출력한다. 없으면 `none`. 종료 코드는 0(찾음)·3(응답은 왔으나 식별자 없음)·2(네트워크 오류·타임아웃)다. `--wait-change`가 있으면 값이 이전 id와 달라질 때까지 `--interval`(기본 30초)마다 재시도하고, `--timeout`(기본 360초) 안에 바뀌지 않으면 종료 코드 4다.
2. `scripts/deploy-gate.test.mjs`: 임시 저장소에 두 브랜치를 만들어 `check`의 통과·차단 사례를 각각 검증한다(비밀값 3형태 각 1건과 `process.env` 읽기 코드의 비오탐, 179 이하와 180 이상 마이그레이션의 되돌림 유무, seed 파일, 인증 없는 새 라우트와 등록된 공개 라우트). 로컬 `http.createServer`로 `served`의 식별자 추출·`none`·변경 대기·타임아웃을 검증한다. 가드레일 패턴 15(`GIT_*` 제거)를 지키고, `verify.sh`의 `scripts-test` 단계에 자동 포함되는지 확인한다.
3. `docs/agents/contract.json`: `deploy_gate`(`rollback_sql_required_from: 180`, `public_routes` 목록)를 선언한다. `check-contract.mjs`가 (a) `scripts/deploy-gate.mjs`의 존재, (b) `public_routes` 각 항목에 실제 `route.ts`가 있는지(낡은 항목 방지)를 대조한다. `paths_exist`에 스크립트와 테스트를 추가한다.
