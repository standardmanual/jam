# [Infra] 배포 게이트가 공용 인증 함수를 쓰는 관리자 일괄 처리 라우트 2건을 "인증 확인 없음"으로 오탐해 오늘 밤 배포를 막는다

## 핵심 요약

- 요구사항: `scripts/deploy-gate.mjs check`가 관리자 일괄 처리 라우트 2건(`admin/badges/list-bulk`, `admin/poi/bulk`)을 "인증 확인 호출이 없음"으로 차단한다. 두 라우트는 공용 함수 `readBulkRequest`에 인증을 위임하는데, 게이트는 라우트 파일 안의 문자열만 보기 때문이다. **게이트가 선언된 인증 래퍼를 인식하되, 그 래퍼가 실제로 인증하는지도 함께 검증**하도록 고친다. 공개 라우트 목록(`public_routes`)에 등록하는 방식은 쓰지 않는다.
- 긴급도: 2026-09-24 23:59 KST 주간 무인 배포가 이 차단 때문에 보류된다(루틴이 #jam-alert에 게시). 대기 커밋 110건이 쌓여 있다. 오늘 밤 전에 staging에 반영돼야 한다.
- 구현 계획: 아래 「구현 계획」 1~6을 따른다.
- 관련 파일:
  - `scripts/deploy-gate.mjs` `ROUTE_AUTH` (67줄), `loadGateConfig` (154줄), `gatherRoutes` (275줄), `renderText` (334줄)
  - `docs/agents/contract.json` `deploy_gate` (`_why`, `rollback_sql_required_from`, `public_routes`)
  - `scripts/check-contract.mjs` deploy_gate 검증 구간 (387줄 부근)
  - `scripts/deploy-gate.test.mjs` (임시 저장소를 만들어 게이트를 실행하는 방식)
  - `jam-web/src/lib/admin/bulk/server.ts` `readBulkRequest` (36줄, 이 티켓이 선언할 래퍼. **이 파일은 고치지 않는다**)
  - `jam-web/src/app/api/admin/badges/list-bulk/route.ts`, `jam-web/src/app/api/admin/poi/bulk/route.ts` (**고치지 않는다**)
  - `.claude/skills/jam-ship/SKILL.md` 「새 API 라우트」 항목 (50~52줄)

## 배경 / 문제 정의

2026-09-24 오후 3시 루틴이 게이트를 돌려 "인증 확인이 없는 신규 admin API 라우트 2건" 차단을 보고했다. 카리나가 최신 staging(`19bb0f77`)에서 직접 재현했다.

```
배포 게이트: 차단(인증 확인 없는 새 API 라우트 2건)
- 비밀값: 통과 / 마이그레이션: 통과
- API 라우트: 차단 — jam-web/src/app/api/admin/badges/list-bulk/route.ts
- API 라우트: 차단 — jam-web/src/app/api/admin/poi/bulk/route.ts
```

**두 라우트는 실제로 인증한다(오탐).** 확인한 사실:
- 두 라우트는 `POST` 핸들러의 첫 줄에서 `readBulkRequest(req, ...)`를 부르고 결과가 `ok`가 아니면 곧바로 반환한다. 그 앞에 DB 접근이 없다.
- `readBulkRequest`(`jam-web/src/lib/admin/bulk/server.ts` 36줄)는 가장 먼저 `getAdminUser()`를 부르고 관리자가 아니면 본문을 읽기 전에 403을 돌려준다.
- `jam-web/src/lib/admin/__tests__/bulk-server.test.ts`에 "어드민이 아니면 403" 테스트가 있다.
- 프로덕션과 스테이징 모두 비로그인 POST에 로그인 리다이렉트(307)를 준다(2026-09-24 `curl`로 확인). 스테이징 307은 자동 로그인 리다이렉트이며 루틴 문서가 참고 정보로만 다루는 정상 동작이다.

게이트의 `ROUTE_AUTH`는 `auth\.getUser|@/lib/admin/auth|CRON_SECRET|ADMIN_SECRET`이 **라우트 파일 본문**에 있는지만 본다. 인증을 공용 함수로 옮긴 라우트는 잡지 못한다. 어드민 목록 공통화(티켓 20260924_0940 상위, 하위 티켓 11개)가 같은 래퍼를 쓰는 일괄 처리 라우트를 앞으로도 추가하므로, 이 문제는 매번 반복된다.

**선택하지 않은 방법**
- `public_routes`에 등록: 두 라우트는 공개가 아니다. 등록하면 앞으로 이 경로에서 인증이 사라져도 게이트가 영원히 잡지 못한다.
- 라우트에 `@/lib/admin/auth`가 든 주석을 추가: 문자열만 보는 게이트를 속이는 것이라 검사의 의미가 없어진다.
- 래퍼를 쪼개 라우트마다 인증을 다시 호출: 병렬 세션이 만든 공용 틀의 API를 바꾸는 일이고, 앞으로 나올 라우트마다 같은 중복이 생긴다.

## 상세 요구사항

### 서비스/코드베이스 관점
- **게이트를 느슨하게 하는 변경이므로 실패하면 배포를 막는 쪽(fail-closed)으로 설계한다.** 선언된 래퍼 파일이 없거나, 선언된 함수를 내보내지 않거나, 인증 호출이 없으면 그 래퍼에 기대는 라우트는 모두 차단한다.
- 라우트가 통과하려면 (a) 선언된 래퍼의 모듈에서 선언된 함수를 가져오고 (b) 그 함수를 호출해야 한다. 가져오기만 하고 호출하지 않는 라우트, 같은 이름의 지역 함수를 부르는 라우트는 차단한다.
- 래퍼 파일의 인증 확인은 `getAdminUser(`·`requireAdmin(`·`requireAdminRead(` 호출 중 하나가 본문에 있는지로 본다. 래퍼가 상대 경로(`../auth`)로 가져와도 통과해야 한다(현재 `server.ts`가 그렇다).
- 기존 판정은 그대로다: `ROUTE_AUTH`에 걸리면 `auth`, 공개 목록에 있으면 `public`, 그 외 `missing`(차단). 기존 테스트는 모두 통과해야 한다.
- `check-contract.mjs`가 커밋마다 선언과 실제를 대조한다: 선언된 래퍼 파일이 존재하고, 선언된 함수를 내보내며, 인증 호출이 있어야 한다.
- 게이트는 저장소·DB·Vercel에 쓰지 않는다는 성격을 유지한다. 의존성을 추가하지 않는다(Node 내장 모듈만).
- 이 티켓은 두 라우트와 `readBulkRequest`를 고치지 않는다. 다른 세션이 이 파일들을 작업 중이다.

## 구현 계획

1. `docs/agents/contract.json` `deploy_gate`에 `auth_wrappers`를 추가한다: `[{ "file": "jam-web/src/lib/admin/bulk/server.ts", "call": "readBulkRequest" }]`. `_why`에 래퍼 선언의 의미(인증 호출이 없어도 되는 것이 아니라, 인증을 대신 수행하는 공용 함수를 라우트가 부르는 경우)와 등록 절차를 적는다. 이 `_why`가 규칙의 단일 원천이다.
2. `scripts/deploy-gate.mjs` `loadGateConfig`가 `auth_wrappers`를 읽고 모양을 검증한다(없으면 빈 배열로 처리해 기존 선언과 호환). 형식이 잘못되면 기존처럼 `GateError`(실행 오류, 종료 코드 2)로 끝난다.
3. `gatherRoutes`가 래퍼를 인식한다. 래퍼마다 (i) head 시점의 래퍼 파일을 읽어 선언된 함수를 `export`하고 인증 호출이 있는지 검증(무결성)하고, (ii) 무결성이 통과한 래퍼에 대해서만 라우트의 가져오기(`import { ... call ... } from '<모듈 경로>'`, 모듈 경로는 `jam-web/src/` 아래 파일 경로에서 `@/`로 만든다)와 호출(`call(`)을 확인해 `auth`로 판정한다. 무결성이 깨진 래퍼가 있으면 그 사실을 결과에 담아 렌더링하고 그 래퍼에 기대는 라우트는 `missing`으로 둔다.
4. `renderText`가 새 차단 사유 두 가지를 알려 준다: 래퍼 무결성 실패(파일·함수·인증 호출 중 무엇이 없는지), 그리고 기존 차단 메시지에 "공용 인증 래퍼를 쓰는 라우트라면 `deploy_gate.auth_wrappers`에 선언" 안내를 덧붙인다. 비밀값·경로 외의 값을 출력하지 않는 원칙을 지킨다.
5. `scripts/check-contract.mjs`의 deploy_gate 검증에 `auth_wrappers` 대조를 추가한다(모양, 파일 존재, 함수 내보내기, 인증 호출). 위반 메시지는 기존 형식(`violate('deploy_gate', ...)`)을 따른다.
6. `scripts/deploy-gate.test.mjs`에 테스트를 추가한다(임시 저장소 방식 유지): (a) 선언된 래퍼를 가져와 호출하는 새 라우트는 통과, (b) 가져오기만 하고 호출하지 않으면 차단, (c) 같은 이름의 지역 함수를 호출하면 차단, (d) 래퍼 파일에 인증 호출이 없으면 그 래퍼를 쓰는 라우트가 차단되고 원인이 출력됨, (e) 선언된 래퍼 파일이 없으면 차단, (f) 래퍼를 안 쓰는 인증 없는 새 라우트는 여전히 차단, (g) 상대 경로 가져오기를 쓰는 래퍼(`../auth`)도 무결성 검증을 통과, (h) `auth_wrappers`가 없는 기존 선언과도 동작. `.claude/skills/jam-ship/SKILL.md`의 「새 API 라우트」 항목에는 `public_routes`와 나란히 `auth_wrappers`가 무엇인지 한 줄 참조만 넣는다(규칙 내용은 `contract.json`의 `_why`로 참조).

- (카리나, 머지 뒤) 인증 호출이 없는 가짜 래퍼와 그것을 부르는 임시 라우트로 게이트가 차단하는 것을 임시 저장소에서 확인한 결과(테스트 (d))를 기록한다.
