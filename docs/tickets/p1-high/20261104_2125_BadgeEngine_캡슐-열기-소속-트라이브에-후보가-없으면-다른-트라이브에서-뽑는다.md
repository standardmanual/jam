# [BadgeEngine] 캡슐 열기에서 소속 트라이브에 후보가 없으면 후보가 있는 다른 트라이브에서 뽑는다

## 핵심 요약

- 요구사항: 소속 트라이브에 받을 수 있는 아이템 배지(활성 컬렉션·공개 기간 안·드랍 제외 아님·삭제 아님)가 **하나도 없는** 유저도 캡슐이 열리게 한다. 지금은 가득 찬 캡슐이 열리지 않은 채 남고 지갑 잼이 쌓이기만 한다.
- 구현 계획: `rollCapsule`(`capsuleRoll.ts`)에서 개체 하나의 후보가 **소속 트라이브에서 나오지 않으면**(소속 트라이브가 뽑혔는데 모든 등급에 후보가 없음) 후보가 있는 다른 트라이브 가운데 고르게 하나를 골라 같은 처음 등급으로 다시 뽑는다. 그래도 없으면 지금처럼 건너뛴다. 소속에 후보가 있는 경우는 난수 사용 순서까지 그대로다.
- 관련 파일(함수·줄 위치):
  - `jam-web/src/lib/capsule/capsuleRoll.ts` — `rollCapsule`(147행, 개체 루프 153~183행, `pickWithRarityFallback` 호출 159~163행), `rollCapsuleTribe`(114행), 머리말 주석 8~17행
  - `jam-web/src/lib/capsule/open.ts` — `rollCapsuleItems`(196행, `tribesWithCandidates` 호출 208행, 건너뜀 로그 218~226행, 전부 비면 던지는 227행). 호출부 로직은 바꾸지 않아도 되는지 확인
  - `jam-web/src/lib/capsule/claim.ts`(보류 받기)가 같은 `rollCapsuleItems`를 쓰므로 함께 고쳐지는지만 확인
  - 시험: `jam-web/src/lib/capsule/__tests__/capsuleRoll.test.ts`(없는 경우를 더한다), `open.test.ts`

  - 문서·정책(동기화 필수): `docs/service/badge-engine/BADGE_ENGINE_UNIFIED.md`(§ 캡슐 열기 순서·후보 표, 1726·1729·1765~1773행 부근), `docs/plan/jam2/10 JAM 2.0 서비스 운영 로직.md`(5.2·5.4절), `jam-web/src/lib/admin/policyDashboard/policiesData.ts`(캡슐 열기 추첨 항목), 확률 안내 `jam-web/src/app/(legal)/probability/page.tsx`의 `TRIBE_NOTE`(59행)와 `docs/service/prd/probability/PRD.md`

## 배경 / 문제 정의

스테이징 테스트 계정(`00000000-0000-0000-0000-000000000001`, 트라이브 «낭만 미식가»)의 캡슐이 180/180으로 가득 찼는데 열리지 않는다. 홈에는 «캡슐이 가득 찼어요»만 뜨고 «받기» 버튼은 없다(보류가 0개라 받기 대상이 아니다).

실측(2026-11-04, 읽기 전용 조회):
- 이 트라이브의 활성 컬렉션은 0개다. 전체 15개 트라이브 중 활성 컬렉션이 있는 곳은 5개(각 3개)뿐이다.
- `capsule_policy`: `guaranteed_count` 1, `bonus_count` 1, `bonus_probability` 0.2, `other_tribe_probability` 0.2.
- 개체마다 20%만 다른 트라이브로 가므로, 열기를 시도할 때 모든 개체가 소속에서 비어 `rolled.items.length === 0` → «캡슐에서 나올 아이템 배지 후보가 하나도 없어 열지 않았다»가 던져진다. 확률은 약 76.8%다. 자동 채움은 이 오류를 `stopped: 'error'`로 끝내므로 캡슐이 가득 찬 채 남는다.
- 설계 의도: `tribesWithCandidates`는 «소속으로 뽑히는 길을 없애지 않는다»며 소속 트라이브를 후보 유무와 상관없이 남긴다. 그 결과 소속에 후보가 없는 유저가 구조적으로 막힌다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 개체 하나를 정하는 순서(트라이브 → 등급 → 후보 → 잠김)와 난수 사용 순서는 **소속에서 후보가 나오는 모든 경로에서 바뀌면 안 된다**(고정 난수 시험이 그대로 통과해야 한다). 새 난수는 «소속이 뽑혔는데 후보가 없을 때»의 다시 뽑기에서만 쓴다.
- 다시 뽑기 규칙: 대상은 `input.tribeIds`에서 소속을 뺀 트라이브(호출부가 이미 후보 있는 트라이브로 좁혀 넘긴다)이고 그 가운데 고르게 하나(`rand()` 한 번)를 고른다. 등급은 이미 뽑은 처음 등급을 그대로 쓰고 `pickWithRarityFallback`의 내림 규칙을 따른다. 결과 개체의 `tribeId`는 실제 뽑은 트라이브다(`recordOpenedItems`의 트라이브 이름이 그 값을 쓴다).
- 다른 트라이브가 뽑혔는데 후보가 없는 경우(좁혀 넘기므로 정상적으로는 없다)와, 다시 뽑아도 후보가 없는 경우는 지금처럼 `skipped`에 남기고 건너뛴다. 모든 개체가 비면 지금처럼 던진다.
- `skipped`·건너뜀 로그의 의미는 «모든 등급에 후보가 없어 건너뜀»으로 유지한다. 다시 뽑기가 성공한 개체는 건너뛴 것이 아니다.
- DB 마이그레이션이 필요하면 SQL 파일 작성까지만 하지 말고 멈추고 보고한다(위 «관련 파일» DB 항목).

### UI/UX 관점
- 화면 변경은 없다. 사용자 노출 문구는 확률 안내(`TRIBE_NOTE`)에 한 문장을 더하는 것뿐이다. `docs/service/writing/UX_WRITING_GUIDELINE.md`의 해요체·고정 용어를 따르고, 예: «내 트라이브에 받을 수 있는 아이템 배지가 없으면 다른 트라이브의 것이 나와요.» 같은 뜻으로 쓴다.

### 컨텐츠 관점
- 해당 없음(데이터는 바꾸지 않는다).

## 구현 계획

1. `capsuleRoll.ts`의 `rollCapsule` 개체 루프: `pickWithRarityFallback`이 `null`이고 `tribeId === input.tribeId`이면 다른 트라이브로 한 번 다시 뽑는다.
2. 머리말 주석·`tribesWithCandidates` 주석을 새 규칙에 맞게 정리한다(소속은 여전히 후보 없이도 남기되 다시 뽑기로 이어진다).
3. 시험을 더한다(`capsuleRoll.test.ts`): ① 소속에 후보 없음 + 소속이 뽑힘 + 다른 트라이브에 후보 있음 → 그 트라이브에서 뽑힘 ② 소속에 후보 없음 + 다른 트라이브도 없음 → 건너뜀 ③ 소속에 후보 있음 → 기존 난수 순서·결과 그대로 ④ 소속에 후보 없음 + 확률로 다른 트라이브가 뽑힘 → 지금처럼 그 트라이브. 필요하면 `open.test.ts`에 «소속에 후보가 없어도 열린다» 한 건.
4. 문서·정책 대시보드·확률 안내 문구를 동기화한다.
5. `scripts/verify.sh` 통과.

## 완료 조건

### 구현 범위 (게이트 판정 대상)
- 소속 트라이브의 모든 등급에 후보가 없고 다른 트라이브에 후보가 있을 때, 시험에서 `rollCapsule`이 개체를 반환한다(`items.length ≥ 1`, 그 `tribeId`가 소속이 아닌 후보 있는 트라이브).
- 소속에 후보가 있는 입력은 기존 시험이 그대로 통과한다(난수 사용 순서가 바뀌지 않았다는 증거).
- 다른 트라이브에도 후보가 없으면 지금처럼 `skipped`에 남고 `rollCapsuleItems`가 «후보가 하나도 없어 열지 않았다»를 던진다.
- 정책 대시보드(`policiesData.ts`)·BADGE_ENGINE_UNIFIED·운영 로직 10번 문서·확률 안내 문구와 PRD가 같은 규칙으로 갱신되어 서로 어긋나지 않는다.
- `scripts/verify.sh`가 통과한다.

### 후속 범위 (담당: 카리나, 시점: 머지 뒤)
- 스테이징에서 테스트 계정의 가득 찬 캡슐이 다음 동기화에서 열리는지 확인한다(배포 확인 수단이 없으면 로컬에서 같은 입력의 시험으로 갈음하고 그 사실을 보고한다).

### 구현 내용 요약

### 주요 의사결정 / 핵심 메모
- 계획 반환 면제(`planOnlyWaiver`) 사유: 바뀌는 파일이 8개 안팎(코드 1·시험 1~2·문서 4·정책 대시보드·확률 안내 페이지)이라 크기 기준(5개 초과)을 넘기지만 변경은 모두 작다. 「관련 파일」에 파일·함수·줄 위치를 적었고, 카리나가 원인(코드·DB 실측)을 먼저 확인했으며, 사용자가 이 방향(옵션 1, 문서·정책 동기화 포함)을 직접 선택했다.
- 사용자가 코드 수정(옵션 1)을 선택했다. 대안(테스트 계정만 다른 트라이브로 옮기기)은 채택하지 않았다: 활성 컬렉션이 없는 트라이브 유저는 오픈 뒤에도 같은 문제를 겪는다.

- 1회차는 티켓이 원격 staging에 없어 워크트리에서 보이지 않았고, 같은 세션에서 사용자가 보낸 다른 요청(미션 상세)이 아현의 입력에 섞여 «티켓과 요청 불일치»로 중단됐다. 티켓을 staging에 올린 뒤 입력에 «다른 요청은 무관»을 명시해 다시 돌렸다.
- 머지 때 `origin/staging`이 앞서 있었으나(다른 세션의 커밋 4개, 겹치는 파일 없음) review 브랜치 고유 커밋은 2개뿐이라 cherry-pick으로 이어 붙였다.

### 잔여 이슈
- 후속 범위(스테이징에서 테스트 계정 캡슐이 다음 동기화에 열리는지)는 배포 확인 수단이 없어 확인하지 못했다. 로컬 시험(소속에 후보가 없어도 열린다)으로 갈음했다. 이 계정의 캡슐은 가득 찬 채라 다음 동기화의 맨 앞에서 열린다.
