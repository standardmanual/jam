# [Infra] B1 DB 확장: 챕터별 필요 잼과 이번 챕터 진행값 열을 더한다

## 핵심 요약

- 요구사항: `chapter_definitions`에 챕터별 필요 잼 열(챕터 10은 NULL)과 시드 값을, `user_chapters`에 이번 챕터 진행값 열을 더한다. 옛 열과 함수는 그대로 두어 지금 모양이 계속 동작한다(확장→전환→축소 중 확장).
- 구현 계획: 마이그레이션 `364_chapter_jam_expand.sql`과 짝 파일 `364_chapter_jam_expand_down.sql`을 쓴다(아래 «구현 계획»의 SQL 명세). 아현은 파일만 쓰고 실행하지 않는다. 실행·생성 타입 재생성은 카리나가 한다.
- 관련 파일: `jam-web/supabase/migrations/364_chapter_jam_expand.sql`(신규), `364_chapter_jam_expand_down.sql`(신규). 현재 정의는 `221_chapters.sql`(28~36행 `chapter_definitions`, 86~95행 `user_chapters`)와 `300_capsule_auto_fill_expand.sql`(`capsule_full_count` 추가).
- 선행 티켓: 20261127_1722(A2, 닫힘)
- 상위 티켓: 20261127_1720(챕터 게이지 카드로 전환하고 캡슐을 폐지한다). 기획 경위와 사용자 확정 결정은 상위 티켓에 있다.

## 배경 / 문제 정의

상위 티켓 20261127_1720의 단계 B(DB 확장, 비가시)의 첫 조각이다. 챕터는 지금 `capsule_full_count`와 `capsule_chapter_costs.advance_count`로 오른다. 새 구조는 챕터마다 정한 양의 잼(필요 잼)이 이번 챕터에 모이면 오른다(2026-11-27 사용자 결정). 이 티켓은 새 값을 담을 자리만 만든다. 읽고 쓰는 코드는 이후 티켓(B2 적립 함수, B4 호출, C5a 읽기)이 만든다.

2026-11-27에 공용 DB(jam-prod, 읽기 전용)에서 확인한 현재 상태:

- `chapter_definitions`: 열 `chapter_no`(integer PK), `required_score`(bigint), `updated_at`. 10행(챕터 1~10).
- `user_chapters`: 열 `user_id`(uuid PK), `chapter_no`(integer, NULL 가능), `total_score`(bigint), `updated_at`, `capsule_full_count`(integer, 기본 0). 2행. 전체 유저는 8명.
- `capsule_chapter_costs`: 챕터 1~10, `fill_amount_v2 × advance_count`가 필요 잼 표(870, 1,120, 1,260, 1,600, 1,980, 2,205, 2,700, 3,300, 3,960)와 일치한다(챕터 10은 `advance_count` NULL).
- 적용된 마이그레이션은 363번(`363_item_books_tribes_name_en_cover_params`)까지다. 새 번호는 364다.

## 구현 계획

### `jam-web/supabase/migrations/364_chapter_jam_expand.sql` (신규)

머리 주석에 티켓 번호(20261127_1724, 상위 20261127_1720), 목적(확장 단계, 옛 열·함수 불변), 적용 대상(공용 단일 DB라 즉시 프로덕션 반영)을 적는다. 본문은 이 순서다.

1. `ALTER TABLE public.chapter_definitions ADD COLUMN IF NOT EXISTS required_jam INTEGER CHECK (required_jam IS NULL OR required_jam >= 1);`
2. 시드: `UPDATE public.chapter_definitions AS d SET required_jam = v.jam, updated_at = now() FROM (VALUES (1, 870), (2, 1120), (3, 1260), (4, 1600), (5, 1980), (6, 2205), (7, 2700), (8, 3300), (9, 3960)) AS v(chapter_no, jam) WHERE d.chapter_no = v.chapter_no AND d.required_jam IS DISTINCT FROM v.jam;` 챕터 10은 건드리지 않아 NULL로 남는다(마지막 챕터).
3. `ALTER TABLE public.user_chapters ADD COLUMN IF NOT EXISTS chapter_jam INTEGER NOT NULL DEFAULT 0 CHECK (chapter_jam >= 0);`
4. `COMMENT ON COLUMN`으로 두 열의 뜻을 적는다: `required_jam` = «이 챕터에서 다음 챕터로 오르는 데 필요한 잼, 마지막 챕터는 NULL, 필요량은 챕터 1~9가 `capsule_chapter_costs`의 `fill_amount_v2 × advance_count`와 같다(2026-11-27)», `chapter_jam` = «이번 챕터에서 모은 잼(챕터가 오르면 필요량을 빼고 넘친 잼은 이월한다, 새 구조 B2부터 쓴다)».
5. 기존 RLS 정책, 옛 열(`required_score`, `total_score`, `capsule_full_count`)과 모든 함수는 건드리지 않는다. 새 정책·함수·인덱스를 만들지 않는다.
6. 모든 문장은 다시 실행해도 같은 결과가 나오게(`IF NOT EXISTS`, `IS DISTINCT FROM`) 쓴다.

### `jam-web/supabase/migrations/364_chapter_jam_expand_down.sql` (신규, 되돌림)

`ALTER TABLE public.user_chapters DROP COLUMN IF EXISTS chapter_jam;`, `ALTER TABLE public.chapter_definitions DROP COLUMN IF EXISTS required_jam;`. 데이터는 이 두 열에만 있고 다른 곳에 쓰지 않으므로 되돌려도 서비스 데이터를 잃지 않는다(B2 이후에는 `chapter_jam`에 운영 값이 생기므로 그때는 백업 뒤에 되돌린다고 주석에 적는다).

### 하지 않는 일
- `database.generated.ts` 재생성은 하지 않는다(적용 뒤 카리나가 Supabase MCP로 받아 같은 흐름에서 반영한다).
- 코드, 함수, 정책, 이관(백필) 변경 없음. `user_chapters.chapter_jam` 채우기는 C1이다.

### 카리나 실행 절차(참고, 아현은 하지 않는다)
1. 번호·파일 확인, 되돌림 SQL 확인.
2. 드라이런: 한 번의 `execute_sql`에 «적용 → 점검(열 존재, 시드 9행, 챕터 10 NULL, 기존 행의 `chapter_jam` 0) → `RAISE EXCEPTION`»을 넣어 전체를 취소하고, 취소 뒤 원상(열 없음)을 읽기 전용으로 대조한다.
3. 되돌림 실측: 적용 → 되돌림 → 원상 대조 → 예외로 취소.
4. `apply_migration` 실행(이름 `364_chapter_jam_expand`), 직후 읽기 전용으로 결과를 확인하고 `generate_typescript_types`로 `jam-web/src/types/database.generated.ts`를 갱신해 대조한다.
5. 프로덕션(main) 코드가 새 열 없이도 동작하는지(새 열은 NULL 가능 또는 기본값이라 옛 코드가 깨지지 않는지) 확인한다.

## 완료 조건

- 새 열 `chapter_definitions.required_jam`이 있고 챕터 1~9가 870, 1,120, 1,260, 1,600, 1,980, 2,205, 2,700, 3,300, 3,960이며 챕터 10은 NULL이다.
- 새 열 `user_chapters.chapter_jam`이 있고 기존 모든 행이 0이다(NOT NULL, 기본 0).
- 옛 열(`required_score`, `total_score`, `capsule_full_count`)과 함수·정책이 바뀌지 않았고, 기존 시험과 `scripts/verify.sh`가 통과한다.
- 되돌림 SQL을 실측으로 확인했다(적용 → 되돌림 → 원상 대조).
- 생성 타입(`database.generated.ts`)이 새 두 열을 포함한다.

## 주요 의사결정 / 핵심 메모

- 상위 티켓의 사용자 확정 결정과 «하지 않을 것»을 따른다. 확인하지 않은 수치는 «미검증»이다.
- 계획 반환 면제 전제: 이 티켓은 생성 타입까지 더하면 파일 3개, 약 110줄이라 `plan_only` 임계에 닿을 수 있어 «구현 계획»을 SQL 문장 단위로 적었다. 사용자가 이 방식을 승인했다(2026-11-27). `/jam-work` 호출 때 카리나가 `planOnlyWaiver`로 넘긴다.
- 열 이름은 `required_jam`, `chapter_jam`으로 정했다. 공통 용어 3.4절은 데이터 이름을 `energy`로 두기로 했지만, 실제 DB는 이미 `jam_wallets`, `jam_transactions`를 쓰고 있어(220_jam_ledger) 같은 이름 체계를 따랐다.
- 챕터 10 이후에 챕터를 더하는 일은 어드민이 `chapter_definitions` 행을 추가하는 방식이다(C9a). 마지막 챕터의 `required_jam`은 NULL이고, 새 챕터를 더하면 이전 마지막 챕터에 값을 채운다.
- 공용 단일 DB라 변경이 즉시 프로덕션에 반영된다. 이 변경은 NULL 가능한 열과 기본값이 있는 열만 더해 옛 코드가 깨지지 않는다.
