# [Infra] B2 DB 확장: 진행값 적립과 승급 판정 함수를 더한다

## 핵심 요약

- 요구사항: 새 함수가 이번 챕터 진행값을 더하고, 필요량 이상이면 Q-a 규칙(여러 단계 가능, 넘친 잼 이월)대로 승급한다. 같은 일은 한 번만 적립되고 아직 아무도 호출하지 않는다.
- 구현 계획: 아래 «구현 계획»의 단계를 파일 단위로 따른다(4단계).
- 관련 파일: `jam-web/supabase/migrations/36x_chapter_jam_apply.sql`(+ `_down.sql`)
- 선행 티켓: 20261127_1724(B1)
- 상위 티켓: 20261127_1720(챕터 게이지 카드로 전환하고 캡슐을 폐지한다). 기획 경위와 사용자 확정 결정은 상위 티켓에 있다.

## 배경 / 문제 정의

상위 티켓 20261127_1720의 단계 B(DB 확장, 비가시)에 속하는 조각이다. 잼은 챕터를 올리는 경험치이고 포인트는 별도 재화이며, 캡슐은 폐지한다(2026-11-27 사용자 결정). 챕터 1~9의 필요 잼은 870, 1,120, 1,260, 1,600, 1,980, 2,205, 2,700, 3,300, 3,960이고, 넘친 잼은 이월한다.

## 구현 계획

1. 새 마이그레이션 `36x_chapter_jam_apply.sql`과 `_down.sql`: 적립·승급 판정 함수(새 이름이라 DROP 선행 규칙은 해당 없음). 승급 때 `chapter_ups`에 한 줄을 남긴다.
2. 기존 `jam_apply`와 `jam_apply_service_activity`(마이그레이션 303)는 건드리지 않는다.
3. 멱등 키와 하루 40·한 주 100 상한은 기존 규칙을 그대로 따른다.
4. 되돌림 SQL: 새 함수를 DROP한다.

## 완료 조건

- 같은 일(같은 멱등 키)을 두 번 적립해도 진행값이 한 번만 늘고, 필요량 이상이면 승급과 `chapter_ups` 한 줄이 생긴다.
- 넘친 잼이 이월되고 한 번에 여러 단계가 오를 수 있음을 SQL 시험으로 확인한다.
- 아직 앱이 호출하지 않아 서비스 동작이 바뀌지 않는다. 되돌림 SQL을 확인했다.

## 규모와 체크포인트

- 규모: 파일 2개, 약 200줄(추정, 미검증)
- 체크포인트: db 유형 단독 호출. 실행은 카리나가 한다. DB 안 훅과 앱 호출 중 무엇으로 적립할지 설계를 먼저 확인한다.

## 주요 의사결정 / 핵심 메모

- 상위 티켓의 사용자 확정 결정과 «하지 않을 것»을 따른다. 확인하지 않은 수치는 «미검증»이다.
- 계획 반환 면제 전제: 이 티켓은 파일 5개 초과 또는 100줄 이상이 예상돼 위 «구현 계획»을 파일 단위로 적었다. 사용자가 이 방식을 승인했다(2026-11-27). `/jam-work` 호출 때 카리나가 `planOnlyWaiver`로 넘기고, 면제 사유를 여기에 이어서 남긴다.
