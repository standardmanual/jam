# [Infra] B2 DB 확장: 진행값 적립과 승급 판정 함수를 더한다

## 핵심 요약

- 요구사항: 새 함수 `chapter_jam_apply`가 이번 챕터 진행값(`user_chapters.chapter_jam`)을 더하고, 필요량(`chapter_definitions.required_jam`) 이상이면 Q-a 규칙(한 번에 여러 챕터, 넘친 잼 이월)대로 승급한다. 같은 일(같은 멱등 키)은 한 번만 적립된다. 아직 아무도 호출하지 않는다.
- 구현 계획: 마이그레이션 `365_chapter_jam_apply.sql`과 짝 파일 `365_chapter_jam_apply_down.sql`을 쓴다. 새 표 `chapter_jam_events`(멱등 키 기록)와 새 함수 1개만 더한다. 기존 함수는 건드리지 않는다. 아현은 파일만 쓰고 실행하지 않는다.
- 관련 파일: `jam-web/supabase/migrations/365_chapter_jam_apply.sql`(신규), `365_chapter_jam_apply_down.sql`(신규). 참고: `303_service_activity_jam.sql`(권한 부여 패턴 175~177행, 멱등 키 규칙), 라이브 DB 함수 `capsule_auto_fill`(챕터 오름 처리), `221_chapters.sql`(`chapter_ups`).
- 선행 티켓: 20261127_1724(B1, 닫힘)
- 상위 티켓: 20261127_1720(챕터 게이지 카드로 전환하고 캡슐을 폐지한다). 기획 경위와 사용자 확정 결정은 상위 티켓에 있다.

## 배경 / 문제 정의

상위 티켓 20261127_1720의 단계 B(DB 확장, 비가시) 두 번째 조각이다. B1이 새 열(`required_jam`, `chapter_jam`)을 만들었고, 이 티켓이 그 열을 쓰는 함수를 만든다. 호출은 B4(이중 쓰기)와 C2(전환)가 한다.

2026-11-27에 공용 DB(jam-prod, 읽기 전용)에서 확인한 현재 모양:

- 잼은 `jam_wallets.balance`(지갑)에 쌓이고 `jam_transactions`(원장, `source_event_key`로 멱등)에 기록된다. 지갑 잔액은 `capsule_auto_fill`이 캡슐로 옮기며(`jam_apply(-양, 'capsule_fill')`) 챕터를 올린다.
- 챕터 오름은 지금 `capsule_auto_fill` 안에서 `user_chapters.capsule_full_count`와 `capsule_chapter_costs.advance_count`로 판정하고, `chapter_ups`(PK `user_id, chapter_no`)에 새 챕터를 넣는다(`ON CONFLICT DO NOTHING`). 호출부는 `reachedChapters`(이번 호출로 `chapter_ups`에 새로 들어간 챕터)를 받아 소식과 챕터 배지를 처리한다(`jam-web/src/lib/chapter/rise.ts`).
- 이용 정지는 `user_suspensions`에서 `lifted_at IS NULL`인 행이 있으면 정지다. 기존 함수들은 정지면 `{ok: false, error: 'user_suspended'}`를 돌려준다.
- 기존 SECURITY DEFINER 함수는 `service_role`만 실행한다(`303`의 REVOKE ALL FROM PUBLIC, anon, authenticated 후 GRANT TO service_role).

### 설계 결정: 적립만 하는 모드와 승급까지 하는 모드

B4(이중 쓰기) 기간에는 옛 방식(캡슐)이 챕터를 올린다. 이때 새 함수도 승급하면 챕터가 이중으로 오른다. 그래서 함수 인자 `p_promote`로 두 모드를 나눈다.

- `p_promote = FALSE`: 진행값만 더한다(B4 이중 쓰기). 챕터 번호와 `chapter_ups`는 건드리지 않는다.
- `p_promote = TRUE`: 더한 뒤 승급한다(C2 전환 뒤). 기본값은 TRUE다.
- B4가 쌓는 값은 C1(이관)이 원장 기준으로 다시 계산해 덮어쓰므로, 이중 쓰기 기간의 `chapter_jam`은 비교 기록용이다.

## 구현 계획

### `jam-web/supabase/migrations/365_chapter_jam_apply.sql` (신규)

머리 주석에 티켓 번호(20261127_1725, 상위 20261127_1720), 확장 단계임(옛 함수·열·표 불변), 호출하는 곳이 아직 없음, 공용 단일 DB라 즉시 프로덕션 반영, 되돌림은 `365_chapter_jam_apply_down.sql`임을 적는다. 본문은 이 순서다.

1. **표 `public.chapter_jam_events`**(멱등 키 기록): `user_id UUID NOT NULL REFERENCES public.users(id) ON DELETE CASCADE`, `event_key TEXT NOT NULL CHECK (btrim(event_key) <> '')`, `amount INTEGER NOT NULL CHECK (amount > 0)`, `promoted BOOLEAN NOT NULL DEFAULT FALSE`, `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`, `PRIMARY KEY (user_id, event_key)`. `CREATE TABLE IF NOT EXISTS`. `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`만 하고 정책은 만들지 않는다(service_role과 SECURITY DEFINER 함수만 접근). `COMMENT ON TABLE`로 뜻을 적는다.
2. **함수 `public.chapter_jam_apply(p_user_id UUID, p_amount INTEGER, p_event_key TEXT, p_promote BOOLEAN DEFAULT TRUE) RETURNS JSONB`**, `LANGUAGE plpgsql SECURITY DEFINER SET search_path TO 'public'`. 새 이름이라 `DROP FUNCTION`은 필요 없다. 동작 순서:
   1. 입력이 잘못되면(`p_user_id` NULL, `p_amount` NULL 또는 0 이하, `p_event_key` NULL 또는 공백) `{ok: false, error: 'invalid_input'}`을 돌려준다.
   2. 이용 정지 중이면(`user_suspensions`에 `lifted_at IS NULL`인 행) `{ok: false, error: 'user_suspended'}`.
   3. `user_chapters`에서 `p_user_id` 행을 `FOR UPDATE`로 잠그고 읽는다. 행이 없거나 `chapter_no`가 NULL이면(퀘스트 전·옛 유저) 아무것도 저장하지 않고 `{ok: false, error: 'no_chapter'}`.
   4. `chapter_jam_events`에 `(p_user_id, p_event_key, p_amount)`를 `ON CONFLICT (user_id, event_key) DO NOTHING`으로 넣고 `GET DIAGNOSTICS`로 행 수를 본다. 0이면 같은 일이므로 값을 바꾸지 않고 `{ok: true, duplicate: true, applied: 0, chapterNo, chapterJam, reachedChapters: []}`를 돌려준다.
   5. `chapter_jam = chapter_jam + p_amount`로 더한다.
   6. `p_promote`가 TRUE면 반복한다(안전 한도 100회). 현재 챕터의 `required_jam`을 읽어, NULL(마지막 챕터)이거나 `chapter_jam`이 그보다 작으면 멈춘다. 다음 챕터(`chapter_definitions`에서 현재보다 큰 가장 작은 `chapter_no`)가 없으면 멈춘다. 아니면 `chapter_jam`에서 필요량을 빼고, `chapter_ups`에 `(p_user_id, 다음 챕터)`를 `ON CONFLICT (user_id, chapter_no) DO NOTHING`으로 넣어 행이 새로 들어갔을 때만 `reachedChapters`에 더하며, 현재 챕터를 다음 챕터로 바꾼다. 승급이 한 번이라도 있으면 이벤트 행의 `promoted`를 TRUE로 바꾼다.
   7. `user_chapters`의 `chapter_no`, `chapter_jam`, `updated_at`을 한 번에 갱신한다. `capsule_full_count`, `total_score`는 건드리지 않는다.
   8. `{ok: true, duplicate: false, applied: p_amount, promote: p_promote, chapterNo, chapterJam, requiredJam(현재 챕터의 필요량, 마지막이면 null), reachedChapters}`를 돌려준다.
3. 권한: `REVOKE ALL ON FUNCTION public.chapter_jam_apply(UUID, INTEGER, TEXT, BOOLEAN) FROM PUBLIC;`, `... FROM anon, authenticated;`, `GRANT EXECUTE ON FUNCTION ... TO service_role;`(`303` 175~177행과 같은 형식).
4. `COMMENT ON FUNCTION`으로 두 모드와 «B4는 FALSE, C2부터 TRUE»를 적는다.
5. 기존 함수(`jam_apply`, `jam_apply_service_activity`, `capsule_auto_fill`, `chapter_start` 등), 열, 정책, 표는 건드리지 않는다.

### `jam-web/supabase/migrations/365_chapter_jam_apply_down.sql` (신규, 되돌림)

`DROP FUNCTION IF EXISTS public.chapter_jam_apply(UUID, INTEGER, TEXT, BOOLEAN);`, `DROP TABLE IF EXISTS public.chapter_jam_events;`. 주석에 «B4 이후에는 `chapter_jam_events`에 멱등 기록이 쌓이므로 백업한 뒤에 되돌린다»를 적는다.

## 완료 조건

- 새 함수 `chapter_jam_apply`와 새 표 `chapter_jam_events`가 있고, 함수는 `service_role`만 실행할 수 있다(PUBLIC·anon·authenticated 회수).
- 같은 멱등 키로 두 번 호출해도 진행값이 한 번만 늘고, 두 번째 응답은 `duplicate: true`다.
- 승급 모드에서 필요량을 넘으면 한 번에 여러 챕터가 오르고 넘친 잼이 이월된다. `reachedChapters`는 이번 호출로 `chapter_ups`에 새로 들어간 챕터만 담는다. 챕터 10에서는 진행값만 쌓인다.
- 적립만 하는 모드(`p_promote = FALSE`)는 챕터 번호와 `chapter_ups`를 바꾸지 않는다.
- 이용 정지 중, 입력 오류, 챕터 없는 유저는 거절되고 아무것도 저장되지 않는다.
- 아직 앱이 호출하지 않아 서비스 동작이 바뀌지 않고, 기존 함수의 본문·권한이 그대로다. 되돌림 SQL을 실측으로 확인했다.

## 주요 의사결정 / 핵심 메모

- 상위 티켓의 사용자 확정 결정과 «하지 않을 것»을 따른다. 확인하지 않은 수치는 «미검증»이다.
- 계획 반환 면제 전제: 이 티켓은 약 200줄이라 `plan_only` 임계에 닿는다. 그래서 «구현 계획»을 동작 순서와 SQL 문장 단위로 적었다. 사용자가 이 방식을 승인했다(2026-11-27). `/jam-work` 호출 때 카리나가 `planOnlyWaiver`로 넘긴다.
- 멱등 키 기록 표를 새로 둔 이유: `jam_transactions.source_event_key`는 지갑 입출금 원장이라 진행값 적립의 멱등을 겸하면 두 기능이 한 키에 묶인다. 진행값은 활동 정산과 서비스 활동 잼의 «받은 양»을 같은 키로 따로 기록해 B4가 두 호출을 독립적으로 재시도할 수 있게 한다.
- 호출부 설계(B4): 앱이 `jam_apply`·`jam_apply_service_activity` 성공 직후 같은 멱등 키로 `chapter_jam_apply(…, FALSE)`를 부른다. DB 안 훅(트리거)은 쓰지 않는다. 훅은 지갑 입출금마다 걸려 `capsule_fill`(음수)과 운영자 지급을 가려내기 어렵다. 운영자 지급 잼(`admin_grant`)은 진행값에 넣지 않는다(상위 티켓 «나중에 정해도 되는 것» 제안과 같다).
- 마지막 챕터(10)의 진행값은 쌓이기만 한다. 챕터를 더하면 이전 마지막 챕터에 필요량을 채우는 시점에 승급 판정이 일어날 수 있다.
- 공용 단일 DB라 변경이 즉시 프로덕션에 반영된다. 이 변경은 새 표와 새 함수만 더해 옛 코드가 깨지지 않는다.
