# [Infra] B3 DB 확장: 챕터 보상 지급 기록과 보상 설정 표를 더한다

## 핵심 요약

- 요구사항: (유저, 챕터)마다 1회 지급을 기록하는 표와, 어드민에서 개수·확률을 바꿀 수 있는 보상 설정 표를 만든다. 값은 A3 결과로 확정된 Q-b와 Q-c를 따른다.
- 구현 계획: 마이그레이션 `366_chapter_reward.sql`과 짝 파일 `366_chapter_reward_down.sql`을 쓴다. 새 표 2개(`chapter_reward_policy`, `chapter_reward_grants`)와 `chapter_definitions.reward_count` 열 1개를 더하고 후보 E 값을 시드로 넣는다. 기존 함수·열·정책은 건드리지 않는다. 아현은 파일만 쓰고 실행하지 않는다.
- 관련 파일: `jam-web/supabase/migrations/366_chapter_reward.sql`(신규), `366_chapter_reward_down.sql`(신규). 참고: `364_chapter_jam_expand.sql`(열 추가·시드 패턴), `365_chapter_jam_apply.sql`(표·권한 패턴), 라이브 DB 표 `capsule_policy`(단일 행 설정과 합계 100 제약), `sync_pending_items`(대기 상태 값). 생성 타입은 적용 뒤 카리나가 새 표와 새 열만 반영한다.
- 선행 티켓: 20261127_1723(A3), 20261127_1724(B1)
- 상위 티켓: 20261127_1720(챕터 게이지 카드로 전환하고 캡슐을 폐지한다). 기획 경위와 사용자 확정 결정은 상위 티켓에 있다.

## 배경 / 문제 정의

상위 티켓 20261127_1720의 단계 B(DB 확장, 비가시)에 속하는 조각이다. 잼은 챕터를 올리는 경험치이고 포인트는 별도 재화이며, 캡슐은 폐지한다(2026-11-27 사용자 결정). 챕터 1~9의 필요 잼은 870, 1,120, 1,260, 1,600, 1,980, 2,205, 2,700, 3,300, 3,960이고, 넘친 잼은 이월한다.

## 구현 계획

### 설계 결정 (카리나, 2026-11-27)

- **챕터별 개수는 `chapter_definitions.reward_count` 열**에 둔다. 필요 잼(`required_jam`)과 같은 «챕터를 마칠 때» 기준이라 한 행에 모인다. 챕터를 더하는 어드민 작업(C9a)이 한 곳만 고치면 된다. 마친 챕터 1~3은 3, 4~6은 4, 7~9는 5이고 마지막 챕터(10)는 NULL이다.
- **등급 확률·다른 트라이브 확률·보정은 단일 행 표 `chapter_reward_policy`**(`id = 1`)에 둔다. `capsule_policy`·`jam_policy`와 같은 관례다. 읽기는 서버만 한다(RLS 켜고 정책 없음).
- **지급 기록 표 `chapter_reward_grants`**는 (유저, 마친 챕터)당 1행이다. 뽑은 결과(`drawn_items`)를 처음에 저장해 다시 뽑을 수 없게 하고, 칸이 모자라면 `pending`으로 두며(Q-c), 칸에 넣으면 `claimed`로 바꾼다. 동기화 막힘(C2a)은 «유저에게 `pending` 행이 있는가»로 판정한다.
- 이 티켓에서 함수는 만들지 않는다. 추첨과 지급은 C3a·C3b다.
- **넣지 않는 것**: 잠금 비율(Q-i 미정, 정해지면 열을 더하는 확장 마이그레이션으로 처리), 보정의 «같은 등급 연속» 기준(`jam_policy.common_streak_threshold` 10을 그대로 쓴다, 열 중복을 피한다).

### `jam-web/supabase/migrations/366_chapter_reward.sql` (신규)

머리 주석에 티켓 번호(20261127_1726, 상위 20261127_1720), 확장 단계임(옛 함수·열·표 불변), 호출하는 곳이 아직 없음, 공용 단일 DB라 즉시 프로덕션 반영, 되돌림은 `366_chapter_reward_down.sql`임을 적는다. 본문은 이 순서다.

1. **열 `chapter_definitions.reward_count`**: `ALTER TABLE public.chapter_definitions ADD COLUMN IF NOT EXISTS reward_count INTEGER CHECK (reward_count IS NULL OR reward_count >= 0);` 뒤에 `COMMENT ON COLUMN`으로 «이 챕터를 마칠 때(다음 챕터로 오를 때) 받는 아이템 배지 개수, 마지막 챕터는 NULL»을 적는다.
2. **시드**: `UPDATE public.chapter_definitions SET reward_count = v.cnt FROM (VALUES (1,3),(2,3),(3,3),(4,4),(5,4),(6,4),(7,5),(8,5),(9,5)) AS v(no, cnt) WHERE chapter_definitions.chapter_no = v.no AND chapter_definitions.reward_count IS DISTINCT FROM v.cnt;`(다시 실행해도 같은 결과). 챕터 10은 NULL로 남긴다.
3. **표 `public.chapter_reward_policy`**: `id INTEGER PRIMARY KEY CHECK (id = 1)`, `rarity_common NUMERIC NOT NULL DEFAULT 30 CHECK (>= 0)`, `rarity_rare ... DEFAULT 40`, `rarity_epic ... DEFAULT 22`, `rarity_mystic ... DEFAULT 8`, `other_tribe_probability NUMERIC NOT NULL DEFAULT 0.2 CHECK (BETWEEN 0 AND 1)`, `pity_epic_threshold INTEGER NOT NULL DEFAULT 15 CHECK (>= 1)`, `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`. 표 제약으로 `CHECK (abs(rarity_common + rarity_rare + rarity_epic + rarity_mystic - 100) < 0.001)`(`capsule_policy`와 같은 형식). `CREATE TABLE IF NOT EXISTS`. `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`만 하고 정책은 만들지 않는다. `COMMENT ON TABLE`로 뜻을 적는다.
4. **시드**: `INSERT INTO public.chapter_reward_policy (id) VALUES (1) ON CONFLICT (id) DO NOTHING;`(기본값이 후보 E 값이다).
5. **표 `public.chapter_reward_grants`**: `user_id UUID NOT NULL REFERENCES public.users(id) ON DELETE CASCADE`, `chapter_no INTEGER NOT NULL REFERENCES public.chapter_definitions(chapter_no)`(마친 챕터 번호), `reward_count INTEGER NOT NULL CHECK (reward_count >= 0)`(지급 시점의 개수 기록), `drawn_items JSONB NOT NULL DEFAULT '[]'::jsonb CHECK (jsonb_typeof(drawn_items) = 'array')`(뽑은 결과, 항목 모양은 C3a가 정한다), `status TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','claimed'))`, `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`, `claimed_at TIMESTAMPTZ`, `PRIMARY KEY (user_id, chapter_no)`, `CHECK ((status = 'claimed') = (claimed_at IS NOT NULL))`. `CREATE TABLE IF NOT EXISTS`.
6. **색인**: `CREATE INDEX IF NOT EXISTS chapter_reward_grants_pending_idx ON public.chapter_reward_grants (user_id) WHERE status = 'pending';`(동기화 막힘 판정용). RLS는 켜고 정책은 만들지 않는다. `COMMENT ON TABLE`로 «(유저, 챕터) 1회 지급 기록, 같은 키는 한 번만 기록(`ON CONFLICT DO NOTHING`), `pending`이 있으면 동기화 막힘(Q-c)»을 적는다.
7. 기존 함수, 열, 정책, 표는 건드리지 않는다.

### `jam-web/supabase/migrations/366_chapter_reward_down.sql` (신규, 되돌림)

`DROP TABLE IF EXISTS public.chapter_reward_grants;`, `DROP TABLE IF EXISTS public.chapter_reward_policy;`, `ALTER TABLE public.chapter_definitions DROP COLUMN IF EXISTS reward_count;`. 주석에 «C3b 이후에는 `chapter_reward_grants`에 지급 기록이 쌓이므로 백업한 뒤에 되돌린다, 정책 표는 어드민에서 바꾼 값이 있으면 백업한다»를 적는다. 여러 번 실행해도 같은 결과여야 한다(`IF EXISTS`).

- 어드민 화면과 `balance_setting_changes` 구역 추가(C9b), 정책 대시보드 `policiesData.ts` 동기화(C10a)는 이 티켓에서 하지 않는다. 새 표는 아직 아무도 읽지 않아 노출되는 정책 수치가 바뀌지 않는다.

### 카리나 실행 절차(참고, 아현은 하지 않는다)
1. 번호·파일 확인, 되돌림 SQL 확인.
2. 드라이런(한 번의 `execute_sql` 안에 `DO` 블록, 끝에서 `RAISE EXCEPTION`으로 전체 취소): 적용 → 점검(챕터 1~9의 `reward_count`가 3,3,3,4,4,4,5,5,5이고 챕터 10은 NULL, 정책 행 1개와 값 30·40·22·8·0.2·15, 지급 표 비어 있음) → 시험 ① 같은 (유저, 챕터)를 `ON CONFLICT DO NOTHING`으로 두 번 넣으면 1행 ② 없는 챕터 번호 거절 ③ `status`가 `claimed`인데 `claimed_at`이 비면 거절, `pending`인데 `claimed_at`이 있어도 거절 ④ 등급 합이 100이 아니면 거절, `id = 2` 거절 ⑤ `drawn_items`가 배열이 아니면 거절 ⑥ 유저를 지우면 지급 행이 따라 지워짐(시험 유저로) ⑦ 재실행해도 시드가 그대로(멱등) → 되돌림 → 원상 대조(열 0개, 표 없음, 기존 `chapter_definitions` 값 불변) → 취소.
3. `apply_migration`으로 적용하고 직후 읽기 전용으로 새 표·열·시드·RLS를 확인한다. 새 표 2개와 새 열만 생성 타입에 반영한다.

## 완료 조건

- 지급 기록 표 `chapter_reward_grants`가 (유저, 챕터) 고유 제약을 갖고, 같은 키로 두 번 넣으면 한 번만 기록된다. 상태는 `pending`·`claimed`뿐이고 `claimed`일 때만 `claimed_at`이 있다.
- 보상 설정이 A3 확정 값(후보 E)으로 들어 있다: `chapter_definitions.reward_count`가 챕터 1~3은 3, 4~6은 4, 7~9는 5, 10은 NULL이고, `chapter_reward_policy`가 Common 30·Rare 40·Epic 22·Mystic 8(합 100), 다른 트라이브 0.2, 보정 15다.
- 새 표 2개는 RLS가 켜져 있고 정책이 없다(서버만 읽고 쓴다).
- 아직 앱이 읽지 않아 서비스 동작이 바뀌지 않고, 기존 함수·열·정책이 그대로다. 되돌림 SQL을 실측으로 확인했다. 생성 타입이 새 표 2개와 새 열을 포함한다.
