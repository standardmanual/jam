# [BadgeEngine] B4 진행값 적립 호출을 이중 쓰기로 붙인다

## 핵심 요약

- 요구사항: 활동 정산과 서비스 활동 잼 지급 때 새 함수로도 진행값을 쌓는다(승급은 아직 옛 방식). 같은 일은 한 번만 쌓이고, 두 값이 어긋나면 로그에 남긴다.
- 구현 계획: 래퍼 `applyChapterJam`(신규)을 만들고 활동 정산(`settlement.ts`)과 서비스 활동 잼(`serviceActivity.ts`)이 지급에 성공한 직후 적립만 하는 모드(`p_promote = FALSE`)로 부른다. 같은 일은 멱등 키로 한 번만 쌓이고, 실패는 `engine_decision_log`에 남기며 옛 흐름은 막지 않는다. DB는 건드리지 않는다.
- 관련 파일: `jam-web/src/lib/chapter/applyJam.ts`(신규)와 `jam-web/src/lib/chapter/__tests__/applyJam.test.ts`(신규) / `jam-web/src/lib/jam/settlement.ts`(`settleActivities`, `jam_apply` 성공 직후 약 160~172행) / `jam-web/src/lib/jam/serviceActivity.ts`(`awardServiceJam`, 지급 응답을 읽은 직후 약 170~178행) / `jam-web/src/lib/engine-log/index.ts`(`EngineDecisionEvent` 값 2개 추가) / 시험 `jam-web/src/lib/jam/__tests__/settlement.test.ts`(가짜 클라이언트 `makeLedgerClient` 약 128~160행), `serviceActivity.test.ts`, `settlement-rise.test.ts`
- 선행 티켓: 20261127_1725(B2)
- 상위 티켓: 20261127_1720(챕터 게이지 카드로 전환하고 캡슐을 폐지한다). 기획 경위와 사용자 확정 결정은 상위 티켓에 있다.

## 배경 / 문제 정의

상위 티켓 20261127_1720의 단계 B(DB 확장, 비가시)에 속하는 조각이다. 잼은 챕터를 올리는 경험치이고 포인트는 별도 재화이며, 캡슐은 폐지한다(2026-11-27 사용자 결정). 챕터 1~9의 필요 잼은 870, 1,120, 1,260, 1,600, 1,980, 2,205, 2,700, 3,300, 3,960이고, 넘친 잼은 이월한다.

## 구현 계획

### 설계 결정 (카리나, 2026-11-27)

- **적립만 한다.** 호출은 항상 `p_promote = FALSE`다. 챕터 승급은 지금처럼 캡슐이 한다. 새 함수가 승급하면 챕터가 이중으로 오른다(B2 설계). 래퍼는 `promote` 인자를 받되 이 티켓의 호출부는 모두 `false`를 넘기고, C2a가 `true`로 바꾼다.
- **멱등 키.** 활동 정산은 `activity_settlement:<strava_activities.id>`, 서비스 활동 잼은 기존 이벤트 키(`<kind>:<원천 id>`, `serviceActivityEventKey`)를 그대로 쓴다. 두 접두가 달라 키가 겹치지 않는다. 같은 키는 DB(`chapter_jam_events`)가 한 번만 센다.
- **적립 양.** 활동 정산은 `jam_apply`가 돌려준 `amount`(이미 정산된 활동이면 기존 양), 서비스 활동 잼은 응답의 `granted`(하루 40·한 주 100 상한이 이미 반영된 실제 지급량)다. 지급량이 0이면 부르지 않는다. 재전송(`duplicate`)이어도 `granted > 0`이면 같은 키로 다시 부른다(이전에 적립이 실패했던 것을 메운다. DB가 중복을 걸러낸다).
- **운영자 지급(`admin_grant`)과 캡슐 채움(음수)은 부르지 않는다.** 이 두 경로는 호출부가 없다(B2 설계 메모). 
- **실패는 옛 흐름을 막지 않는다.** 래퍼는 던지지 않는다. RPC 오류·해석 못 할 응답·예외, `invalid_input`, 보낸 양과 다른 `applied`(중복이 아닌데)는 `console.error`와 `engine_decision_log`(엔진 `points`)에 남기고 `{ ok: false }`를 돌려준다. `no_chapter`(챕터를 시작하지 않은 옛 유저)와 `user_suspended`(이용 정지)는 정상이라 기록 없이 건너뛴다(C1 이관이 원장 기준으로 진행값을 다시 계산한다).
- **«어긋남» 로그의 뜻**: 이 티켓에서는 호출마다 확인할 수 있는 어긋남(적립 실패, `applied`가 보낸 양과 다름)을 남긴다. 원장 합계와 `chapter_jam` 총량 대조는 이관(C1)의 검증이 맡는다(지금은 B4 이전 활동이 새 진행값에 없어 어차피 다르다).
- DB 변경은 없다(함수와 표는 B2·`engine_decision_log` 기존). `EngineDecisionEvent`는 TypeScript 유니온이라 값만 더하면 되고, DB 제약은 엔진(`points`)에만 걸려 있어 마이그레이션이 필요 없다.

### 1. `jam-web/src/lib/chapter/applyJam.ts` (신규)

- 상단 주석에 티켓 번호, «B4 이중 쓰기, 승급은 옛 방식이 한다, C2a에서 `promote`를 `true`로 전환», 던지지 않음, 서버 전용을 적는다.
- `export interface ApplyChapterJamInput { userId: string; amount: number; eventKey: string; promote: boolean }`
- `export type ApplyChapterJamResult = { ok: true; duplicate: boolean; skipped: 'no_chapter' | 'user_suspended' | null; applied: number; chapterNo: number | null; chapterJam: number | null; reachedChapters: number[] } | { ok: false }`
- `export async function applyChapterJam(supabase: SupabaseClient, input): Promise<ApplyChapterJamResult>`:
  1. 입력이 안 맞으면(`amount`가 1 이상의 정수가 아님, `eventKey`가 비었음) 호출 없이 기록하고 `{ ok: false }`.
  2. `supabase.rpc('chapter_jam_apply', { p_user_id, p_amount, p_event_key, p_promote })`를 부른다.
  3. 오류면 실패를 기록한다. 응답이 객체가 아니거나 `ok`가 불리언이 아니면 «해석 못 할 응답»으로 기록한다.
  4. `ok: false`면 `error`가 `no_chapter`·`user_suspended`일 때만 `{ ok: true, skipped, ... }`로 정상 처리하고, 그 밖의 오류(`invalid_input` 포함)는 기록한다.
  5. `ok: true`이고 `duplicate`가 아니며 `applied`가 보낸 양과 다르면 «어긋남»으로 기록한다(결과는 `ok: true`로 돌려주되 로그를 남긴다).
  6. 어떤 경우도 던지지 않는다(`try/catch`로 감싼다).
- 기록 함수 `recordChapterJamIssue(userId, kind, eventKey, detail)`: `console.error`(`[chapter-jam]` 접두)와 `logEngineDecision('points', 'chapter_jam_apply_failed' | 'chapter_jam_mismatch', userId, { eventKey, amount, ... })`. 기록 중 예외도 삼킨다(`serviceActivity.ts`의 `recordServiceJamFailure`와 같은 모양).

### 2. `jam-web/src/lib/engine-log/index.ts`

`EngineDecisionEvent` 유니온에 `'chapter_jam_apply_failed'`(적립 호출 실패, 같은 키로 다시 보낼 수 있다)와 `'chapter_jam_mismatch'`(응답의 `applied`가 보낸 양과 다름)를 설명 주석과 함께 더한다. 티켓 번호는 20261127_1727.

### 3. `jam-web/src/lib/jam/settlement.ts` (`settleActivities`)

`jam_apply` 응답을 읽어 `items.push(item)`을 한 직후(성공 경로)에 `await applyChapterJam(supabase, { userId, amount: item.amount, eventKey, promote: false })`를 부른다. `eventKey`는 문자열 `activity_settlement:`에 활동 id(`strava_activities.id`)를 이어 붙인 값이다. `item.amount`가 0 이하이면 부르지 않는다. 반환값은 쓰지 않는다(정산 결과·`total`은 그대로). 이 호출이 던져도 정산이 막히지 않도록 래퍼가 던지지 않는다는 점에 기대고, 호출 주변의 기존 `try/catch`를 바꾸지 않는다. 파일 머리 주석의 마지막 줄(«챕터 점수 «모은 잼»은 세지 않는다...»)과 `items.push` 뒤 주석을 «새 진행값 적립은 이중 쓰기(B4, 승급은 캡슐)»로 고친다.

### 4. `jam-web/src/lib/jam/serviceActivity.ts` (`awardServiceJam`)

`parseGrant`가 `ParsedGrant`를 돌려준 뒤, 캡슐 채움을 부르기 전에 `if (parsed.granted > 0) await applyChapterJam(supabase, { userId, amount: parsed.granted, eventKey, promote: false })`를 더한다. `blocked`는 `granted`가 0이라 자연히 제외된다. 호출은 캡슐 채움과 독립이며 반환값 `AwardServiceJamResult`는 바꾸지 않는다. 파일 머리 주석의 «지급 즉시 채움» 문단 뒤에 «새 진행값에도 쌓는다(B4)» 한 줄을 더한다.

### 5. 시험

- 새 `jam-web/src/lib/chapter/__tests__/applyJam.test.ts`: 래퍼 단위 시험. ① 정상 적립(`promote: false`가 RPC 인자로 간다) ② `duplicate`는 `ok: true, duplicate: true`이고 기록 없음 ③ `no_chapter`·`user_suspended`는 `skipped`로 정상이고 기록 없음 ④ RPC 오류·해석 못 할 응답·예외는 `{ ok: false }`이고 `chapter_jam_apply_failed` 기록 ⑤ `applied`가 보낸 양과 다르면 `chapter_jam_mismatch` 기록 ⑥ `amount`가 0·음수·소수·`eventKey`가 비면 RPC를 부르지 않고 `{ ok: false }` ⑦ 던지지 않음. `logEngineDecision`은 모의로 바꿔 호출 인자를 확인한다.
- `settlement.test.ts`: 가짜 클라이언트가 `chapter_jam_apply`를 알아보게 고친다(지금은 `jam_apply`가 아닌 RPC를 «기대하지 않은 RPC»로 센다). 시험 ① 정산 성공 뒤 활동마다 `activity_settlement:<활동 id>` 키로 적립이 한 번씩 불림, `p_promote`는 `false`, 양은 원장에 기록된 양 ② 같은 활동을 다시 정산해도 정산 결과는 그대로이고 같은 키로 불림(DB가 중복을 거름) ③ 적립 호출이 실패(RPC 오류)해도 정산 결과와 원장 줄이 그대로임 ④ 잼이 0인 활동·`jam_apply` 실패 활동은 적립을 부르지 않음.
- `serviceActivity.test.ts`(없으면 가장 가까운 시험 파일): ① 지급(`granted > 0`)마다 이벤트 키 그대로 적립이 불림 ② `granted`가 0(`rule_zero`·`capped` 지급 0·`blocked`)이면 불리지 않음 ③ 상한에 걸려 일부만 지급되면(`capped`, 하루 40·한 주 100 경계) `granted`만큼만 보냄 ④ 재전송(`duplicate`)이고 `granted > 0`이면 같은 키로 부름 ⑤ 적립 호출이 실패해도 지급 결과와 캡슐 채움이 그대로임.
- `settlement-rise.test.ts` 등 `settleActivities`·`awardServiceJam`의 가짜 클라이언트를 쓰는 기존 시험은 새 RPC 때문에 깨지지 않게 최소로 고친다.
- `scripts/verify.sh`가 통과해야 한다.

### 하지 않는 일
- 승급(`p_promote = TRUE`), 캡슐 채움·옛 점수 장부 변경, 이관(C1), 챕터 읽기 모델(C5a), 동기화 막힘 규칙, 운영자 지급 잼 적립은 하지 않는다.
- DB 마이그레이션, 생성 타입 변경, 문서·정책 대시보드 변경은 하지 않는다(보이지 않는 이중 쓰기라 사용자 노출 정책 수치가 바뀌지 않는다).
- 기존 호출부의 반환 모양과 로그 이름은 바꾸지 않는다.

## 완료 조건

- 활동 정산(`settleActivities`)과 서비스 활동 잼 지급(`awardServiceJam`)이 성공한 뒤 적립만 하는 모드(`p_promote = FALSE`)로 새 진행값을 쌓는다. 키는 `activity_settlement:<활동 id>`와 기존 서비스 이벤트 키이고, 같은 일을 다시 처리해도 DB에 한 번만 쌓인다. 챕터 승급은 옛 방식이 그대로 한다.
- 지급량이 0인 경우(`rule_zero`, 상한 도달 지급 0, `blocked`)에는 적립을 부르지 않고, 상한에 걸려 일부만 지급되면 실제 지급량만큼만 쌓는다.
- 적립 호출이 실패하거나(RPC 오류·해석 못 할 응답·예외·`invalid_input`) 응답의 `applied`가 보낸 양과 다르면 `engine_decision_log`(엔진 `points`)에 `chapter_jam_apply_failed`·`chapter_jam_mismatch`로 남는다. `no_chapter`·`user_suspended`는 정상 건너뜀이라 기록하지 않는다.
- 새 호출이 실패해도 정산 결과와 서비스 활동 잼 지급 결과, 캡슐 채움이 그대로 동작한다. 래퍼는 던지지 않는다. `scripts/verify.sh`가 통과한다.
