# [Infra] C1 기존 유저 이관: 이번 챕터 진행값을 원장으로 옮긴다 (준비: 함수·백업 표와 드라이런)

## 핵심 요약

- 요구사항: 유저별 이번 챕터 진행값을 (현재 챕터 도달 이후 `capsule_fill` 합계 + 지갑 잔액)으로 채운다. 챕터는 내려가지 않고, 대기 보상·아이템·기록 표는 그대로다.
- 구현 계획: 이 티켓은 **준비**다. 이관 함수 `chapter_jam_backfill_chunk`와 백업 표 `chapter_jam_backfill`을 더하고(데이터는 바꾸지 않는다) 드라이런과 되돌림을 실측한다. 실제 이관 실행은 오픈 직전이라 새 티켓 C1b(20261127_1750)로 나눈다.
- 관련 파일: `jam-web/supabase/migrations/367_chapter_jam_backfill_prepare.sql`(신규)와 짝 `367_chapter_jam_backfill_prepare_down.sql`(신규). 실행·되돌림 파일(`seed_20261127_chapter_jam_backfill_run.sql`와 `_down.sql`)은 C1b가 만든다. 참고: `365_chapter_jam_apply.sql`(승급 반복·권한 패턴), `366_chapter_reward.sql`, 라이브 DB `capsule_auto_fill`(옛 승급)·`jam_transactions` 제약
- 선행 티켓: 20261127_1724(B1), 20261127_1725(B2), 20261127_1726(B3), 20261127_1727(B4)
- 상위 티켓: 20261127_1720(챕터 게이지 카드로 전환하고 캡슐을 폐지한다). 기획 경위와 사용자 확정 결정은 상위 티켓에 있다.

## 배경 / 문제 정의

상위 티켓 20261127_1720의 단계 C(전환, 같은 배포 창)에 속하는 조각이다. 잼은 챕터를 올리는 경험치이고 포인트는 별도 재화이며, 캡슐은 폐지한다(2026-11-27 사용자 결정). 챕터 1~9의 필요 잼은 870, 1,120, 1,260, 1,600, 1,980, 2,205, 2,700, 3,300, 3,960이고, 넘친 잼은 이월한다.

## 구현 계획

### 확정된 결정 (사용자, 2026-11-27)

- **진행값 기준은 원장이다**: 이번 챕터 진행값 = (현재 챕터에 도달한 뒤의 `capsule_fill` 합계) + 지갑 잔액. 현재 챕터 도달 시각은 `chapter_ups`의 그 챕터 행 `reached_at`이고, 행이 없으면 모든 `capsule_fill`을 센다. 챕터 번호는 내려가지 않는다.
- **이관 판정도 평상 규칙이다**(Q-h): 진행값이 필요량(`required_jam`) 이상이면 한 번에 여러 챕터까지 올리고 넘친 잼은 이월한다.
- **보상은 이관으로 새로 오른 챕터만 준다.** 이미 마친 챕터는 소급하지 않는다. 지급은 오픈 뒤 첫 동기화에서 C3b가 한다(단계마다 (유저, 챕터)당 1회). 그래서 이관이 올린 챕터를 `chapter_jam_backfill.promoted_chapters`에 남긴다.

### 설계 결정 (카리나)

- **준비와 실행을 나눈다.** 이중 쓰기(B4) 기간에는 옛 방식이 챕터를 올려도 `chapter_jam`이 줄지 않아 값이 어긋난다. 그래서 이관은 전환 직전에 다시 계산해야 한다. 이 티켓은 함수와 백업 표를 만들어 지금 적용하고(데이터는 바뀌지 않는다), 실행은 C1b가 main 승격 직전에 한다.
- **함수 하나가 대조표와 이관을 모두 한다.** `p_apply = FALSE`(기본)면 아무것도 쓰지 않고 유저별 대조표만 돌려준다(실행 전 점검·사용자 보고용). `TRUE`면 유저마다 잠그고 쓴다. `p_limit`개씩 청크로 처리하고 `remaining`을 돌려줘 0이 될 때까지 반복 호출한다.
- **이미 센 일은 다시 세지 않게 키를 심는다.** 이관 때 그 유저의 원장 줄(`activity_settlement`는 `activity_settlement:<활동 id>`, `service_activity`는 `source_event_key`)을 `chapter_jam_events`에 멱등 키로 넣는다(`ON CONFLICT DO NOTHING`). 안 하면 이관 뒤 옛 활동이 다시 정산될 때 B4가 같은 양을 한 번 더 쌓는다. 심은 키는 백업 표에 남겨 되돌릴 때 지운다.
- **챕터가 없는 유저(`user_chapters` 행 없음, 퀘스트 전)는 대상이 아니다.** 지갑 잔액·`capsule_*` 표·인벤토리·대기 보상은 건드리지 않는다. 지갑 잔액은 진행값에 이미 포함되므로 그대로 두고 읽는 곳을 C2b가 정리한다.
- 이관이 챕터를 올린 유저만 `user_chapters.capsule_full_count`를 0으로 맞춘다(옛 승급이 하던 일과 같다). 그 밖의 옛 열은 그대로다.
- 실행 시각의 위험: 이관 계산과 B4 적립 사이에 새 잼이 들어오면 그 잼이 두 번 쌓일 수 있다. C1b는 동기화가 멈춘 배포 창에서 실행한다.

## 완료 조건

- 새 표 `chapter_jam_backfill`과 새 함수 `chapter_jam_backfill_chunk`가 있고, 함수는 `service_role`만 실행할 수 있다. 데이터는 바뀌지 않았다(이 티켓의 적용 직후 `chapter_jam_backfill`은 0행, `user_chapters`는 그대로).
- 대조 모드(`p_apply = FALSE`)는 아무것도 쓰지 않고 유저별 대조표(이전·이후 챕터와 진행값, 원장 합계, 옛 게이지 근사값, 게이지가 낮아지는 유저)를 돌려준다.
- 쓰기 모드(드라이런으로 시험)는 챕터 하향이 0명이고, 진행값이 원장 기준 계산과 100% 일치하며, `capsule_opens`·`capsule_unseen_results`·`capsule_pending_rewards` 행 수와 지갑·인벤토리가 그대로다. 필요량을 넘으면 한 번에 여러 챕터가 오르고 넘친 잼이 이월되며, 이관이 올린 챕터가 `promoted_chapters`에 남는다.
- 이관 때 원장 줄의 멱등 키가 `chapter_jam_events`에 들어가, 이관 뒤 같은 활동을 B4 방식으로 다시 적립해도 `duplicate`다. 다시 불러도 이미 이관한 유저는 건너뛴다.
- 되돌림 SQL(백업 표에서 복원, 심은 키·`chapter_ups` 제거)을 드라이런 안에서 실측으로 확인했다. 되돌림은 C1b가 실행 파일과 함께 낸다.
