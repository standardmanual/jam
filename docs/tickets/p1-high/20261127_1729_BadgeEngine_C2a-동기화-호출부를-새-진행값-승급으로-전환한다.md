# [BadgeEngine] C2a 동기화 호출부를 새 진행값 승급으로 전환한다

## 핵심 요약

- 요구사항: Strava 동기화가 자동 채움 대신 새 진행값으로 승급을 판정한다. 막힘 판정은 새 구조에 맞게 정리하고, 옛 대기 보상 지급은 비워질 때까지 유지한다.
- 구현 계획: 아래 «구현 계획»의 단계를 파일 단위로 따른다(4단계).
- 관련 파일: `jam-web/src/lib/strava/sync.ts`(21·22·49·471·935행 근처)와 시험 3~4개
- 선행 티켓: 20261127_1728(C1)
- 상위 티켓: 20261127_1720(챕터 게이지 카드로 전환하고 캡슐을 폐지한다). 기획 경위와 사용자 확정 결정은 상위 티켓에 있다.

## 배경 / 문제 정의

상위 티켓 20261127_1720의 단계 C(전환, 같은 배포 창)에 속하는 조각이다. 잼은 챕터를 올리는 경험치이고 포인트는 별도 재화이며, 캡슐은 폐지한다(2026-11-27 사용자 결정). 챕터 1~9의 필요 잼은 870, 1,120, 1,260, 1,600, 1,980, 2,205, 2,700, 3,300, 3,960이고, 넘친 잼은 이월한다.

## 구현 계획

1. `jam-web/src/lib/strava/sync.ts`: 21·22·49행 import, 471·935행의 `runSyncCapsuleAutoFill` 호출을 새 판정 호출로 바꾼다.
2. `readCapsuleReceiveBlocked` 사용부를 정리한다(Q-c 결정대로 막힘을 유지할지 확정).
3. `settleAfterSlotsFreed`(옛 대기 보상 지급)는 유지한다.
4. 시험: `sync-capsule-receive-block.test.ts` 외 동기화 시험을 새 흐름으로 고친다.

## 완료 조건

- 동기화로 받은 잼이 새 진행값에 쌓이고 필요량에 닿으면 승급하며, 같은 동기화를 두 번 해도 한 번만 반영된다.
- 옛 대기 보상 보유 유저의 지급이 그대로 동작한다.
- `scripts/verify.sh`가 통과한다.

## 규모와 체크포인트

- 규모: 파일 4~5개, 약 200줄(추정, 미검증)
- 체크포인트: engine 유형 단독 호출. 전환 배포 창 안에서 C1 이후 순서를 지킨다.

## 주요 의사결정 / 핵심 메모

- 상위 티켓의 사용자 확정 결정과 «하지 않을 것»을 따른다. 확인하지 않은 수치는 «미검증»이다.
- 계획 반환 면제 전제: 이 티켓은 파일 5개 초과 또는 100줄 이상이 예상돼 위 «구현 계획»을 파일 단위로 적었다. 사용자가 이 방식을 승인했다(2026-11-27). `/jam-work` 호출 때 카리나가 `planOnlyWaiver`로 넘기고, 면제 사유를 여기에 이어서 남긴다.
- 결정 반영(2026-11-27, A3 20261127_1723): Q-c 결정: 대기 보상이 있으면 동기화를 막는 규칙(`readCapsuleReceiveBlocked`)을 챕터 보상 대기 기준으로 옮겨 유지한다. 시뮬레이션은 막지 않는 가정이었으므로 막힘 규칙을 넣은 재측정(Q-l)을 C3b 전에 한다.
