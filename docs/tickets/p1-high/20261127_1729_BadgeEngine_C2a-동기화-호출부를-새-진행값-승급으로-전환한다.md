# [BadgeEngine] C2a 동기화 호출부를 새 진행값 승급으로 전환한다

## 핵심 요약

- 요구사항: Strava 동기화가 자동 채움 대신 새 진행값으로 승급을 판정한다. 막힘 판정은 새 구조에 맞게 정리하고, 옛 대기 보상 지급은 비워질 때까지 유지한다.
- 구현 계획: 활동 정산(`settleActivities`)의 진행값 적립을 승급 모드(`promote: true`)로 바꿔 오른 챕터를 돌려주고, 동기화(`sync.ts`)가 옛 캡슐 자동 채움 대신 그 챕터로 오름 처리(`processChapterRise`)를 부르게 한다. 막힘 판정(`readCapsuleReceiveBlocked`)에는 챕터 보상 대기를 더한다. 서비스 활동 잼 쪽은 C2b다.
- 관련 파일: `jam-web/src/lib/jam/settlement.ts`(`settleActivities`, `applyChapterJam` 호출 약 197~210행, `JamSettlementResult`·`emptySettlement`) / `jam-web/src/lib/strava/sync.ts`(import 21·22·49행, 정산 없는 경로 `evaluateWithoutNewActivities` 약 471~490행, 정상 경로 정산 뒤 약 930~936행, 끝 판정 약 1027행, 진입 막힘 약 1145~1155행) / `jam-web/src/lib/capsule/receive-block.ts`(`readCapsuleReceiveBlocked`) / 시험 `jam-web/src/lib/jam/__tests__/settlement.test.ts`, `settlement-rise.test.ts`, `jam-web/src/lib/strava/__tests__/sync-jam-settlement.test.ts`, `sync-capsule-receive-block.test.ts`, `sync-jam-action-hook.test.ts`(`runSyncCapsuleAutoFill` 모의가 있다), `sync-empty-batch-badge-eval.test.ts`, `jam-web/src/lib/capsule/__tests__/receive-block.test.ts`
- 선행 티켓: 20261127_1728(C1)
- 상위 티켓: 20261127_1720(챕터 게이지 카드로 전환하고 캡슐을 폐지한다). 기획 경위와 사용자 확정 결정은 상위 티켓에 있다.

## 배경 / 문제 정의

상위 티켓 20261127_1720의 단계 C(전환, 같은 배포 창)에 속하는 조각이다. 잼은 챕터를 올리는 경험치이고 포인트는 별도 재화이며, 캡슐은 폐지한다(2026-11-27 사용자 결정). 챕터 1~9의 필요 잼은 870, 1,120, 1,260, 1,600, 1,980, 2,205, 2,700, 3,300, 3,960이고, 넘친 잼은 이월한다.

## 구현 계획

### 설계 결정 (카리나, 2026-11-27)

- **승급은 정산 안에서 한다.** `settleActivities`가 활동마다 `applyChapterJam`을 `promote: true`로 부른다(B4는 `false`였다). 승급 판정과 이월은 DB 함수 `chapter_jam_apply`(B2)가 하고, 코드는 «이번 정산으로 새로 오른 챕터(`reachedChapters`)»를 모아 돌려준다. 같은 활동을 다시 정산해도 같은 멱등 키라 DB가 한 번만 센다(이중 승급 없음).
- **오름 처리는 동기화가 부른다.** 정산 결과의 `reachedChapters`가 비어 있지 않으면 동기화가 `processChapterRise({ userId, reachedChapters }, { skipBadgeEvaluation: true })`를 부른다(소식·피드). 챕터 배지 판정은 동기화 끝 판정(`JAM_SYNC_TRIGGERS`의 `chapter_reached`, 이미 목록에 있다)이 이어서 읽으므로 건너뛴다(이중 판정 규칙, `rise.ts` 머리말). 던지지 않는다. 챕터 오름 보상 지급은 C3b가 `processChapterRise`에 더한다.
- **옛 자동 채움은 동기화에서 걷는다.** `runSyncCapsuleAutoFill`의 동기화 호출 2곳(정상 경로, 정산 없는 경로)을 지운다. 정산 없는 경로(`evaluateWithoutNewActivities`)에는 챕터가 오를 일이 없으므로 `chapter_reached`와 캡슐 열기 지표를 더하지 않는다. 캡슐 열기 지표 판정(`jamTriggersForCapsuleOpen`)을 동기화에서 걷는다. `sync-auto-fill.ts`와 `capsule/*` 모듈은 서비스 활동 잼(`awardServiceJam`)이 아직 쓰므로 지우지 않는다(C2b, 제거는 D단계).
- **막힘은 챕터 보상 대기까지 본다(Q-c).** `readCapsuleReceiveBlocked`가 옛 `capsule_receive_blocked`(옛 대기 보상, 비워질 때까지 유지)의 결과에 챕터 보상 대기를 합친다. `chapter_reward_grants`에서 이 유저의 `status = 'pending'` 행을 읽어 개수를 센다(`drawn_items`가 배열이면 그 길이, 아니면 `reward_count`). 합쳐서 `pending`은 두 값의 합, `needed = pending`, `blocked`는 둘 중 하나라도 대기가 있을 때, `shortfall = max(0, pending - free)`이고 `free`는 옛 함수가 돌려준 값을 그대로 쓴다. 읽지 못하면 던진다(옛 규칙과 같다, «막히지 않음»으로 보면 안 된다). 호출부(`/api/strava/sync`의 409, 홈 막힘 카드)와 계약 모양(`CapsuleReceiveBlockedResult`)은 바꾸지 않는다. 챕터 보상을 만드는 쪽은 C3b라 지금은 대기 행이 없어 동작이 달라지지 않는다.
- **`settleAfterSlotsFreed`(옛 대기 보상 지급)는 그대로 둔다.** 챕터 보상 대기의 지급(`pending`을 `claimed`로)은 C3b가 같은 자리에 더한다.
- **지갑 잔액은 건드리지 않는다.** `jam_apply`가 지갑에 넣는 것은 그대로다(읽는 곳과 의미 정리는 C2b). 새 진행값과 지갑 잔액은 같은 잼을 두 군데에 기록하는 상태로 남는다.
- **전환 순서**: 이 티켓은 C2b(서비스 활동 잼·승급 후속)와 같은 배포 창에서 나간다. 배포 전에 C1b(이관 실행)가 끝나 있어야 한다. 서비스 활동 잼 쪽이 `promote: false`로 남아 있어도 챕터 번호가 두 번 오르지는 않는다(적립만 하고 승급하지 않는다, C2b가 `true`로 바꾼다).

### 1. `jam-web/src/lib/jam/settlement.ts`

- `JamSettlementResult`에 `reachedChapters: number[]`(이번 정산으로 새로 오른 챕터, 오른 순서)를 더하고 `emptySettlement()`가 빈 배열을 돌려준다.
- `settleActivities`의 `if (item.amount > 0)` 블록: `applyChapterJam(..., promote: true)`로 바꾸고, 결과가 `ok: true`이고 `duplicate`가 아니면 `reachedChapters`를 합친다(중복 챕터 번호는 한 번만). 머리 주석과 호출부 주석을 «승급 모드(C2a)»로 고친다. 반환 시 `total`·`items`는 그대로다.

### 2. `jam-web/src/lib/strava/sync.ts`

- import에서 `runSyncCapsuleAutoFill`(49행)과, 더는 안 쓰는 `jamTriggersForCapsuleOpen`을 지운다(다른 곳에서 쓰면 남긴다). `processChapterRise`를 `@/lib/chapter/rise`에서 가져온다.
- `evaluateWithoutNewActivities`: 첫 문장 `const capsuleStep = await runSyncCapsuleAutoFill(...)`와 그 주석을 지우고, 판정 트리거는 `JAM_EMPTY_SYNC_TRIGGERS`만 쓴다(`chapter_reached`와 캡슐 열기 지표 더하기를 지운다).
- 정상 경로: `const capsuleStep = await runSyncCapsuleAutoFill(...)`를 `if (jamSettlement.reachedChapters.length > 0) await processChapterRise({ userId, reachedChapters: jamSettlement.reachedChapters }, { skipBadgeEvaluation: true })`로 바꾸고 주석을 다시 쓴다. 끝 판정 호출(약 1027행)은 `JAM_SYNC_TRIGGERS`만 넘긴다(`capsuleStep.opened` 분기를 지운다).
- 진입 막힘(약 1145~1155행)은 코드를 바꾸지 않는다(`readCapsuleReceiveBlocked`의 결과가 바뀐다). 주석의 «캡슐이 가득 차고»를 «대기 보상이 있고»로 맞춘다.

### 3. `jam-web/src/lib/capsule/receive-block.ts`

`readCapsuleReceiveBlocked`가 기존 RPC 결과를 읽은 뒤 `supabase.from('chapter_reward_grants').select('drawn_items, reward_count').eq('user_id', userId).eq('status', 'pending')`로 챕터 보상 대기를 읽고(오류면 던진다) 위 설계대로 합쳐 돌려준다. 파일 머리 주석에 «챕터 보상 대기도 본다(C2a, Q-c)»를 더한다. 새 함수·새 타입은 만들지 않는다.

### 4. 시험

- `settlement.test.ts`·`settlement-rise.test.ts`: 가짜 클라이언트가 `chapter_jam_apply`의 `p_promote`가 `true`로 오고, 응답의 `reachedChapters`가 정산 결과에 모이는지(여러 활동에서 오른 챕터 합침, 중복 제거), `duplicate`면 모으지 않는지, 적립 실패해도 정산 결과가 그대로인지 확인한다. B4 시험(`p_promote: false` 기대)은 `true`로 고친다.
- `sync-jam-settlement.test.ts`·`sync-jam-action-hook.test.ts`·`sync-empty-batch-badge-eval.test.ts` 등 `runSyncCapsuleAutoFill`을 모의하던 시험: 모의를 걷고 새 흐름(정산 결과의 `reachedChapters`로 `processChapterRise`가 `skipBadgeEvaluation: true`로 불리고, 챕터가 오르지 않으면 안 불림, 정산 없는 경로는 캡슐 단계 없이 `days_since_signup`만 판정)을 확인한다. 끝 판정 트리거에 캡슐 열기 지표가 더는 안 들어가는지 확인한다.
- `receive-block.test.ts`·`sync-capsule-receive-block.test.ts`: 챕터 보상 대기만 있어도 `blocked: true`, 옛 대기와 합산, 둘 다 없으면 `false`, `shortfall` 계산, 챕터 보상 읽기 오류면 던짐, 동기화가 막히면 같은 409 계약이 나옴을 확인한다.
- 같은 동기화를 두 번 해도(같은 활동) 진행값·승급이 한 번만 반영되는 경로(DB가 거름)를 가짜 클라이언트로 확인한다.
- `scripts/verify.sh`가 통과해야 한다.

## 완료 조건

- 동기화로 정산한 잼이 새 진행값에 쌓이고 필요량에 닿으면 승급한다(`chapter_jam_apply`를 `promote: true`로 호출, 한 번에 여러 챕터 가능). 같은 동기화(같은 활동)를 두 번 해도 한 번만 반영된다.
- 정산 결과가 `reachedChapters`를 돌려주고, 동기화가 그 챕터로 오름 처리(소식·피드)를 부르며 챕터 배지 판정은 끝 판정이 이어서 읽는다. 동기화에서 옛 캡슐 자동 채움과 캡슐 열기 지표 판정이 빠진다.
- 막힘 판정이 옛 대기 보상과 챕터 보상 대기를 합쳐 본다(둘 중 하나라도 있으면 막힘, 같은 409 계약). 옛 대기 보상 보유 유저의 지급(`settleAfterSlotsFreed`)이 그대로 동작한다.
- `scripts/verify.sh`가 통과한다.
