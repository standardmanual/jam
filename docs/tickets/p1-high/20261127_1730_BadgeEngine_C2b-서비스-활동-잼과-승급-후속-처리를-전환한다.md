# [BadgeEngine] C2b 서비스 활동 잼과 승급 후속 처리를 전환한다

## 핵심 요약

- 요구사항: 서비스 활동 잼의 즉시 채움을 새 진행값 적립으로 바꾸고, 승급 후속 처리(소식, 챕터 배지 판정)를 이어서 부른다. 챕터 오름 소식은 유지한다.
- 구현 계획: 서비스 활동 잼 지급 뒤 즉시 채움(`fillCapsuleAfterGrant`)을 «승급 모드 적립 + 오름 처리»로 바꾸고, 옛 대기 보상 지급(`settle-pending.ts`) 뒤의 캡슐 재채움을 걷어 옛 승급 경로를 모두 닫는다. 챕터 보상 대기가 있으면 서비스 활동 잼 지급도 막는다(옛 규칙을 옮김).
- 관련 파일: `jam-web/src/lib/jam/serviceActivity.ts`(`fillCapsuleAfterGrant` 약 144~153행, `awardServiceJam` 약 156~190행, 머리 주석, `loadAutoFill`) / `jam-web/src/lib/capsule/settle-pending.ts`(`settle()` 4단계 약 68~74행, `runSyncCapsuleAutoFill` import 30행, 머리 주석 11행) / `jam-web/src/lib/capsule/receive-block.ts`(`readPendingChapterRewardCount`를 내보냄) / 시험 `jam-web/src/lib/jam/__tests__/serviceActivity.test.ts`, `jam-web/src/lib/capsule/__tests__/settle-pending.test.ts`, 그리고 `awardServiceJam`을 거치는 `chapter/__tests__/badge-receive.test.ts`·`collection.test.ts`, `combine/__tests__/combine-engine.test.ts`, `inventory/__tests__/lockedItemFill.test.ts`, `badge-engine/__tests__/badge-receive-score-engine.test.ts`·`badge-receive-score-usage.test.ts`, `chapter/__tests__/score-wiring.test.ts`의 모의
- 선행 티켓: 20261127_1729(C2a)
- 상위 티켓: 20261127_1720(챕터 게이지 카드로 전환하고 캡슐을 폐지한다). 기획 경위와 사용자 확정 결정은 상위 티켓에 있다.

## 배경 / 문제 정의

상위 티켓 20261127_1720의 단계 C(전환, 같은 배포 창)에 속하는 조각이다. 잼은 챕터를 올리는 경험치이고 포인트는 별도 재화이며, 캡슐은 폐지한다(2026-11-27 사용자 결정). 챕터 1~9의 필요 잼은 870, 1,120, 1,260, 1,600, 1,980, 2,205, 2,700, 3,300, 3,960이고, 넘친 잼은 이월한다.

## 구현 계획

### 설계 결정 (카리나, 2026-11-27)

- **서비스 활동 잼도 승급 모드로 적립한다.** `awardServiceJam`이 지급(`granted > 0`)한 뒤 `applyChapterJam`을 `promote: true`로 부르고(B4는 `false`), `ok`이며 `duplicate`가 아닌 결과의 `reachedChapters`를 받는다. 재전송(`duplicate`)이어도 `granted > 0`이면 같은 키로 다시 부르는 B4의 규칙은 그대로다(이전에 적립이 실패했다면 이때 메운다, DB가 중복을 거른다).
- **오름 처리와 후속 판정은 지급 직후에 한다.** 오른 챕터가 있으면 `processChapterRise({ userId, reachedChapters }, { skipBadgeEvaluation: true })`(소식·피드)를 부르고, 행동 지표 판정(`scheduleJamActionEvaluation`)에 `chapter_reached`를 더한다. 챕터 배지 판정은 이 한 번의 지표 판정이 맡는다(이중 판정 규칙, `rise.ts` 머리말, 옛 `fillCapsuleAfterGrant`와 같은 모양). 잼 조건 주 키 4개(`jamTriggersForServiceJam()`)는 항상 판정한다. 캡슐 열기 지표(`jamTriggersForCapsuleOpen()`)는 더하지 않는다. 오름 처리·판정은 던지지 않는다.
- **옛 승급 경로를 모두 닫는다.** `fillCapsuleAfterGrant`가 부르던 `runSyncCapsuleAutoFill`과 `loadAutoFill`을 지운다. 또 `settle-pending.ts`의 `settle()` 4단계(옛 대기 보상을 지급한 뒤 지갑 잔액으로 캡슐을 다시 채움)도 걷는다. 이 단계가 남으면 이관(C1b) 뒤에도 지갑 잔액이 캡슐을 채우고 옛 방식(`capsule_full_count`)으로 챕터가 한 번 더 오를 수 있다. 걷은 뒤 `settle()`은 옛 대기 보상을 지급하고 캡슐 열기 지표만 판정한다(지급한 보상도 캡슐 연 횟수에 들어간다). 이 변경 뒤에는 `runSyncCapsuleAutoFill`·`runCapsuleAutoFill`을 부르는 곳이 코드에 없다(파일 제거는 D단계).
- **챕터 보상 대기가 있으면 서비스 활동 잼 지급도 막는다(옛 규칙을 옮김).** 옛 DB 함수는 대기 보상이 있으면 서비스 활동 잼을 «지급 0, `blocked`»로 거절한다(기록·보충 없음). 챕터 보상 대기(`chapter_reward_grants`의 `pending`)도 같은 규칙으로 막는다: `awardServiceJam`이 RPC를 부르기 전에 `readPendingChapterRewardCount`(`receive-block.ts`에서 내보낸다)를 읽어 0보다 크면 RPC 없이 `{ ok: true, granted: 0, duplicate: false, capped: false, blocked: true }`를 돌려준다. 읽지 못하면 막지 않고 진행한다(옛 DB 함수와 같은 방향, `console.error`만 남긴다). 챕터 보상을 만드는 쪽이 C3b라 지금은 대기 행이 없어 동작이 달라지지 않는다.
- **이용 정지 중에는 쌓이지 않는다.** 지급 RPC가 정지를 먼저 거절하고(`{ ok: false }`) 적립 함수도 정지를 건너뛴다(`user_suspended`, 기록 없음). 이 동작을 시험으로 확인한다.
- `AwardServiceJamResult`의 모양과 호출부 11곳은 바꾸지 않는다.

### 1. `jam-web/src/lib/capsule/receive-block.ts`
`readPendingChapterRewardCount`에 `export`를 붙인다(함수 본문은 C2a 그대로).

### 2. `jam-web/src/lib/jam/serviceActivity.ts`
- `fillCapsuleAfterGrant`를 `afterServiceJamGrant(supabase, input)` 같은 이름으로 바꿔 «적립(승급 모드) → 오름 처리 → 지표 판정» 순서로 다시 쓴다. `loadAutoFill`과 `runSyncCapsuleAutoFill` import를 지운다. 판정 목록은 `[...jamTriggersForServiceJam()]`에 오른 챕터가 있을 때만 `'chapter_reached'`를 더한다. `jamTriggersForCapsuleOpen` import를 지운다.
- `awardServiceJam`: RPC 호출 전에 챕터 보상 대기 사전 확인(위 설계), 지급 응답을 읽은 뒤 B4의 `applyChapterJam(promote: false)` 호출을 `afterServiceJamGrant`로 합친다(적립은 `granted > 0`이면 재전송에도 부르고, 오름 처리·판정은 새로 오른 챕터가 있을 때만, 지표 판정은 새 지급(`!duplicate`)이거나 오른 챕터가 있을 때). 반환값과 실패 기록(`recordServiceJamFailure`) 동작은 그대로다.
- 머리 주석의 «지급 즉시 채움» 문단과 B4 줄을 «지급 즉시 승급 모드 적립(C2b)»으로 다시 쓴다.

### 3. `jam-web/src/lib/capsule/settle-pending.ts`
`settle()`의 4단계(`claim.remainingPending === 0`이면 `runSyncCapsuleAutoFill`)와 그 import, `chapter_reached` 더하기를 지운다. 머리 주석 11행을 «지급 뒤 캡슐을 다시 채우지 않는다(C2b)»로 고친다.

### 4. 시험
- `serviceActivity.test.ts`: 지급 후 `p_promote: true`로 적립, 오른 챕터가 있으면 오름 처리가 `skipBadgeEvaluation: true`로 한 번 불리고 판정 목록에 `chapter_reached`가 들어감, 오르지 않으면 오름 처리 안 부름, 캡슐 열기 지표가 더는 안 들어감, 재전송이어도 `granted > 0`이면 같은 키로 적립을 부르되 오름 처리는 새로 오른 챕터가 있을 때만, 이용 정지(`{ ok: false }`)는 적립을 안 부름, 챕터 보상 대기가 있으면 RPC를 부르지 않고 `blocked` 결과, 대기 읽기 오류면 막지 않고 진행, 적립·오름 처리 실패가 지급 결과를 바꾸지 않음, 하루 40·한 주 100 상한에 걸려 일부만 지급되면 실제 지급량만 적립. 옛 `runSyncCapsuleAutoFill` 모의와 시험은 걷는다.
- `settle-pending.test.ts`: 지급 뒤 캡슐 재채움이 일어나지 않고(`runSyncCapsuleAutoFill`을 부르는 곳이 없음) 캡슐 열기 지표만 판정됨을 확인한다. 기존 지급·막힘 시험은 유지한다.
- 나머지 모의 시험들은 `serviceActivity` 변경으로 깨지지 않게 최소로 고친다.
- `scripts/verify.sh`가 통과해야 한다.

## 완료 조건

- 서비스 활동 잼 지급(`granted > 0`)이 승급 모드(`promote: true`)로 새 진행값에 쌓이고, 승급하면 챕터 오름 소식·피드가 한 번 처리되고 챕터 배지 판정(`chapter_reached`)이 한 번 실행된다. 하루 40·한 주 100 상한에 걸려 일부만 지급되면 실제 지급량만 쌓인다.
- 이용 정지 중에는 진행값이 쌓이지 않는다. 챕터 보상 대기가 있으면 서비스 활동 잼 지급이 막힌다(지급 0, `blocked`). 새 호출이 실패해도 지급 결과는 그대로다.
- 코드에 `runSyncCapsuleAutoFill`·`runCapsuleAutoFill`을 부르는 곳이 없다(서비스 활동 잼과 옛 대기 보상 지급 뒤 재채움을 모두 걷었다). 옛 대기 보상 지급(`settleAfterSlotsFreed`)은 그대로 동작한다.
- `scripts/verify.sh`가 통과한다.
