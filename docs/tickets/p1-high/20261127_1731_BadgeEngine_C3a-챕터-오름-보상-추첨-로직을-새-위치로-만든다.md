# [BadgeEngine] C3a 챕터 오름 보상 추첨 로직을 새 위치로 만든다

## 핵심 요약

- 요구사항: A3에서 확정한 값대로 개수·트라이브·등급·잠김·보정 장치를 추첨한다. 캡슐의 추첨 함수를 재사용하되, 제거 단계에서 같이 지워지지 않게 새 위치로 옮긴다.
- 구현 계획: 아래 «구현 계획»의 단계를 파일 단위로 따른다(3단계).
- 관련 파일: `jam-web/src/lib/capsule/capsuleRoll.ts`, `jam-web/src/lib/capsule/open.ts`(추출 원본) / `jam-web/src/lib/chapter/reward/*`(신규)와 시험
- 선행 티켓: 20261127_1723(A3), 20261127_1726(B3)
- 상위 티켓: 20261127_1720(챕터 게이지 카드로 전환하고 캡슐을 폐지한다). 기획 경위와 사용자 확정 결정은 상위 티켓에 있다.

## 배경 / 문제 정의

상위 티켓 20261127_1720의 단계 C(전환, 같은 배포 창)에 속하는 조각이다. 잼은 챕터를 올리는 경험치이고 포인트는 별도 재화이며, 캡슐은 폐지한다(2026-11-27 사용자 결정). 챕터 1~9의 필요 잼은 870, 1,120, 1,260, 1,600, 1,980, 2,205, 2,700, 3,300, 3,960이고, 넘친 잼은 이월한다.

## 구현 계획

1. `jam-web/src/lib/capsule/capsuleRoll.ts`의 `rollCapsule` 외 순수 추첨 함수와 `lib/capsule/open.ts`의 `rollCapsuleItems`, `toRpcItems`, `rebuildRolledFromDrawn`, `recordOpenedItems`를 새 `jam-web/src/lib/chapter/reward/`로 추출한다.
2. 새 보상 설정 표(B3)에서 개수·확률을 읽도록 바꾼다.
3. 시험을 함께 옮긴다. 옛 캡슐 호출부는 이번 티켓에서 건드리지 않는다.

## 완료 조건

- 같은 시드에서 추첨 결과가 확정 값(개수·등급 확률·보정 장치)대로 나오고, 시험이 그 값을 고정한다.
- 옛 캡슐 코드가 그대로 동작한다(추출만 했고 삭제는 D3에서 한다).
- 확률·보정을 바꿨으므로 `policiesData.ts` 동기화 대상(C10a)을 티켓에 적어 둔다. `scripts/verify.sh` 통과.

## 규모와 체크포인트

- 규모: 파일 4~5개, 약 300줄(대부분 이동, 추정, 미검증)
- 체크포인트: engine 유형 단독 호출. 등급 확률·보정이 바뀌므로 사용자가 확정한 A3 값만 쓴다.

## 주요 의사결정 / 핵심 메모

- 상위 티켓의 사용자 확정 결정과 «하지 않을 것»을 따른다. 확인하지 않은 수치는 «미검증»이다.
- 계획 반환 면제 전제: 이 티켓은 파일 5개 초과 또는 100줄 이상이 예상돼 위 «구현 계획»을 파일 단위로 적었다. 사용자가 이 방식을 승인했다(2026-11-27). `/jam-work` 호출 때 카리나가 `planOnlyWaiver`로 넘기고, 면제 사유를 여기에 이어서 남긴다.
