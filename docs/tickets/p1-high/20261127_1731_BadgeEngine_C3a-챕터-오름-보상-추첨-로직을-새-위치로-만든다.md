# [BadgeEngine] C3a 챕터 오름 보상 추첨 로직을 새 위치로 만든다

## 핵심 요약

- 요구사항: A3에서 확정한 값대로 개수·트라이브·등급·잠김·보정 장치를 추첨한다. 캡슐의 추첨 함수를 재사용하되, 제거 단계에서 같이 지워지지 않게 새 위치로 옮긴다.
- 구현 계획: `jam-web/src/lib/chapter/reward/`에 순수 추첨(`roll.ts`), 설정·데이터 읽기와 추첨 실행(`policy.ts`, `draw.ts`), 저장 모양 변환·복원(`stored.ts`), 지급 뒤 후속 처리(`record.ts`)를 만든다. 옛 캡슐 코드는 그대로 두고 복사해 오며, 새 위치는 `lib/capsule/*`를 가져오지 않는다(D단계에서 캡슐을 지워도 깨지지 않게). 지급(DB 함수)은 B5·C3b다.
- 관련 파일: 원본(읽기만, 고치지 않는다) `jam-web/src/lib/capsule/capsuleRoll.ts`(`tribesWithCandidates`, `rollCapsuleTribe`, `rollCapsuleRarity`, `rollCapsule`), `jam-web/src/lib/capsule/open.ts`(`loadRollData`, `rollCapsuleItems`, `toRpcItems`, `StoredDrawnItem`, `rebuildRolledFromDrawn`, `recordOpenedItems`, `toOpenedItem`), `jam-web/src/lib/jam/policy.ts`(`getJamPolicy`), `jam-web/src/lib/drop-engine/lockAssignment.ts`(`assignLock`) / 신규 `jam-web/src/lib/chapter/reward/roll.ts`, `policy.ts`, `draw.ts`, `stored.ts`, `record.ts`와 시험 `jam-web/src/lib/chapter/reward/__tests__/*.test.ts`
- 선행 티켓: 20261127_1723(A3), 20261127_1726(B3)
- 상위 티켓: 20261127_1720(챕터 게이지 카드로 전환하고 캡슐을 폐지한다). 기획 경위와 사용자 확정 결정은 상위 티켓에 있다.

## 배경 / 문제 정의

상위 티켓 20261127_1720의 단계 C(전환, 같은 배포 창)에 속하는 조각이다. 잼은 챕터를 올리는 경험치이고 포인트는 별도 재화이며, 캡슐은 폐지한다(2026-11-27 사용자 결정). 챕터 1~9의 필요 잼은 870, 1,120, 1,260, 1,600, 1,980, 2,205, 2,700, 3,300, 3,960이고, 넘친 잼은 이월한다.

## 구현 계획

### 설계 결정 (카리나, 2026-11-27)

- **복사해 오고 옛 코드는 건드리지 않는다.** 순수 추첨과 읽기·저장 변환을 `chapter/reward/`에 새로 만든다. 옛 `capsule/*`는 이번 티켓에서 고치지 않는다(D단계에서 지운다). 새 파일은 `@/lib/capsule/*`를 가져오지 않는다. 공용인 `@/lib/drop-engine/lockAssignment`·`syncIssue`, `@/lib/jam/policy`, `@/lib/engine-log`, `@/lib/drop-engine/issueFollowUp`, `@/lib/db/fetchAllRows`는 가져와도 된다.
- **개수는 고정이다.** 옛 캡슐의 «확정 + 확률 보너스» 개수 추첨(`rollCapsuleCount`)은 가져오지 않는다. 개수는 마친 챕터의 `chapter_definitions.reward_count`(3·4·5)를 그대로 쓴다. 난수는 개수에 쓰지 않는다.
- **정책은 두 곳에서 읽는다.** 등급 확률·다른 트라이브 확률·에픽 보정 임계값은 `chapter_reward_policy`(B3, `id = 1`), 같은 등급 연속 임계값(`common_streak_threshold`)과 잠금 확률·최소값은 `jam_policy`(`getJamPolicy`)다. 퀘스트 전 캡슐 규칙(`preQuest`, `pre_quest_unlock_required`)은 가져오지 않는다.
- **추첨 순서는 옛 규칙과 같다**: (개체마다) 트라이브 → 등급 → 후보(한 등급씩 내려 가며) → 잠금(`assignLock`, 경로 `capsule`과 같은 규칙, 확정 Q-i). 보정 1(에픽 이상)은 **첫 개체**에만, 보정 2(Common 연속 임계값 이상이면 Rare 이상)는 개체를 받을 때마다 실제 받은 등급으로 이어 센다. 소속에 후보가 없으면 다른 트라이브에서 한 번 다시 뽑는다. 후보 없는 개체는 건너뛰고 `skipped`에 남긴다. 난수 소비 순서를 옛 `rollCapsule`과 같게 맞춰, 같은 입력·같은 난수면 개체가 같다.
- **추첨만 하고 저장·지급은 하지 않는다.** `drawChapterReward`는 추첨 결과(저장 모양)와 트라이브 이름을 돌려준다. `chapter_reward_grants`에 기록하거나 인벤토리에 넣는 일은 B5(DB 함수)와 C3b가 한다. 나올 개체가 하나도 없으면(모든 등급에 후보 없음) 던지지 않고 빈 목록을 돌려줘 C3b가 기록 없이 다음 기회로 미루게 한다. 소속 트라이브가 없으면 `ChapterRewardError('no_tribe')`를 던진다.

4. `jam-web/src/lib/chapter/reward/draw.ts`: `loadChapterRewardRollData(supabase, userId)`(옛 `loadRollData` 복사: 소속 트라이브, 트라이브 목록, 활성 컬렉션, 아이템 배지, `user_drop_state`의 `common_streak`·`capsule_epic_miss`), `drawChapterReward(supabase, userId, { finishedChapterNo, rand, now })`: 개수와 두 정책을 읽고 추첨한 뒤 후보 없는 개체를 `engine_decision_log`(`drop`/`drop_attempt`, `path: 'chapter_reward'`, `outcome: 'no_candidate'`)에 남기고 `{ items: StoredChapterRewardItem[], tribes, count, skippedCount }`를 돌려준다. `ChapterRewardError`와 코드 `no_tribe`도 여기서 정의한다.

### 구현 내용 요약

챕터 오름 보상의 추첨 로직을 `jam-web/src/lib/chapter/reward/`에 새로 만들었다. 옛 `capsule/*`는 고치지 않고 복사해 왔으며, 새 소스 5개는 `lib/capsule/*`를 가져오지 않는다. 아현이 구현하고 민지가 판정(PASS)했으며, 카리나가 설치본에서 전체 verify를 돌린 뒤 로컬 staging에 머지했다. DB 변경은 없다. 아직 호출하는 곳이 없어 서비스 동작은 바뀌지 않았다.

- `roll.ts`(순수): 개수는 `input.count` 고정이고 난수를 개수에 쓰지 않는다. 등급 확률 30/40/22/8, 에픽 보정(첫 개체에만), 같은 등급 연속 보정(실제 받은 등급으로 이어 셈), 트라이브 80/20, 소속에 후보가 없으면 다른 트라이브에서 재추첨, 잠금은 공용 `assignLock`(경로 `capsule` 규칙, Q-i 확정). 퀘스트 전 규칙은 가져오지 않았다. 난수 소비 순서가 옛 `rollCapsule`과 같다.
- `policy.ts`: `getChapterRewardPolicy`는 `chapter_reward_policy`의 `id = 1`을 읽고 행이 없거나 읽기 오류거나 값이 비정상이면 기본값으로 대체하지 않고 던진다. `getChapterRewardCount`는 마친 챕터의 `reward_count`를 읽고 NULL이면 `null`(보상 없음)을 돌려준다.
- `stored.ts`: `toStoredItems`와 `rebuildChapterRewardItems`(저장된 항목을 다시 추첨하지 않고 되살림, 배지가 없으면 던짐).

- `record.ts`: `recordChapterRewardItems`(지급된 개체마다 `recordIssuedRewards`를 `skipFeed: true`로 부름, 잠긴 개체는 포인트에서 빠짐, 후속 처리가 던져도 지급은 유지). 호출은 C3b가 한다.
