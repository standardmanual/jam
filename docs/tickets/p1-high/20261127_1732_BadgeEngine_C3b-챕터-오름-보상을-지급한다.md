# [BadgeEngine] C3b 챕터 오름 보상을 지급한다

## 핵심 요약

- 요구사항: 챕터가 오른 직후 (유저, 챕터)당 1회 보상을 지급한다. 활동 피드에서는 제외하고, 인벤토리 빈칸이 모자라면 Q-c 결정대로 처리하며, 이용 정지 중에는 막는다.
- 구현 계획: 챕터 오름 처리(`processChapterRise`)가 오른 챕터마다 추첨(C3a)→DB 지급(B5)→후속 처리를 하게 연결하고, 칸이 비면 대기 보상을 받게 하며, 이관·누락으로 지급되지 않은 챕터를 동기화 입구에서 보충 지급한다. 발급 경로 값 `chapter_reward`를 활동 피드 제외 규칙과 획득 경로 표시에 반영한다. DB 변경은 없다.
- 관련 파일: 신규 `jam-web/src/lib/chapter/reward/route.ts`, `grant.ts` / 수정 `jam-web/src/lib/chapter/rise.ts`(`processChapterRise`), `jam-web/src/lib/capsule/settle-pending.ts`(`settle()`), `jam-web/src/lib/strava/sync.ts`(진입 막힘 약 1132행 앞), `jam-web/src/lib/engine-log/index.ts`(이벤트 값), `jam-web/src/lib/activity-feed/capsuleItems.ts`, `jam-web/src/lib/inventory/lockedItemFill.ts`(`canPostOpenedFeed`), `jam-web/src/lib/inventory/obtainRoute.ts`와 그 표시처 `jam-web/src/app/(main)/inventory/[itemId]/LockedItemDetail.tsx` / 시험 `jam-web/src/lib/chapter/reward/__tests__/grant.test.ts`와 위 파일들의 기존 시험
- 선행 티켓: 20261127_1731(C3a), 20261127_1751(B5, 지급 DB 함수)
- 상위 티켓: 20261127_1720(챕터 게이지 카드로 전환하고 캡슐을 폐지한다). 기획 경위와 사용자 확정 결정은 상위 티켓에 있다.

## 배경 / 문제 정의

상위 티켓 20261127_1720의 단계 C(전환, 같은 배포 창)에 속하는 조각이다. 잼은 챕터를 올리는 경험치이고 포인트는 별도 재화이며, 캡슐은 폐지한다(2026-11-27 사용자 결정). 챕터 1~9의 필요 잼은 870, 1,120, 1,260, 1,600, 1,980, 2,205, 2,700, 3,300, 3,960이고, 넘친 잼은 이월한다.

## 구현 계획

### 설계 결정 (카리나, 2026-11-27)

- **지급 대상 챕터**: 챕터 K에 올랐다는 것은 챕터 K-1을 마쳤다는 뜻이다. `reachedChapters`의 각 K(K가 2 이상)에 대해 마친 챕터 K-1의 보상(`chapter_definitions.reward_count`, C3a)을 준다. 한 번에 여러 챕터를 넘으면 단계마다 한 번씩 준다. K = 1(챕터 시작)은 보상이 없다.
- **연결 지점은 `processChapterRise`다.** 소식·피드 뒤에 지급 단계를 더한다(서로 막지 않는다, 던지지 않는다, 실패는 `engine_decision_log`의 `chapter_rise_failed`에 `step: 'reward'`로 남긴다). 정산(C2a)·서비스 활동 잼(C2b)·챕터 시작이 모두 이 함수를 부르므로 한 곳이다. 순환 import를 피하려고 `rise.ts`는 지급 모듈을 호출 시점에 불러온다(`await import()`, 기존 챕터 배지 판정과 같은 방식, `rise-import-cycle.test.ts`가 지킨다).
- **한 챕터의 지급** `issueChapterReward(supabase, userId, finishedChapterNo, { rand, now })`: ① 이미 지급 기록이 있으면(`chapter_reward_grants`) 추첨하지 않고 `duplicate`로 끝낸다. ② `drawChapterReward`(C3a)로 추첨한다. 보상 없음(`count: null`)·나올 개체 없음(빈 목록)·소속 트라이브 없음(`no_tribe`)이면 기록하지 않고 «다음 기회로 미룸»(`skipped`)이다(다음 보충 때 다시 시도한다). ③ RPC `chapter_reward_issue(p_user_id, p_chapter_no, p_items = 추첨 저장 모양)`를 부른다. ④ 응답이 `claimed`면 `rebuildChapterRewardItems`로 되살려 `recordChapterRewardItems`(포인트, `skipFeed: true`)를 부르고 `notifyInventorySlotsLow`를 부른다. `pending`(칸 부족)이면 기록만 남기고 판정 로그(`drop`/`drop_attempt`, `path: 'chapter_reward'`, `outcome: 'held'`)를 남긴다. `duplicate`는 아무것도 안 한다. `user_suspended`는 조용히 넘긴다. 그 밖의 오류는 `chapter_reward_failed`로 기록하고 `{ status: 'failed' }`를 돌려준다. 지급은 확정된 뒤 후속 처리가 실패해도 되돌리지 않는다. 던지지 않는다.
- **대기 보상 받기** `claimPendingChapterRewards(supabase, userId)`: `chapter_reward_grants`의 이 유저 `pending` 행을 오래된 순(`created_at`, `chapter_no`)으로 읽어 RPC `chapter_reward_claim`을 부른다. `insufficient_slots`면 거기서 멈추고(부분 지급 없음, 뒤 행도 건너뜀), 지급되면 저장된 `drawn_items`로 `rebuildChapterRewardItems` → `recordChapterRewardItems` → `notifyInventorySlotsLow`를 한다. 던지지 않는다.
- **보충 지급** `findMissingRewardChapters(supabase, userId)`: 지급 기록이 없는 «마친 챕터» 번호를 돌려준다. 대상은 두 가지다. (a) 이관(C1b)이 새로 올린 챕터: `chapter_jam_backfill.promoted_chapters`의 각 K → 마친 챕터 K-1(사용자 결정: 이관이 올린 챕터만, 이미 마친 챕터는 소급하지 않는다). (b) 새 방식이 올렸지만 오름 처리 전에 프로세스가 죽어 지급이 빠진 챕터: `chapter_ups`의 챕터 K 가운데 도달 시각(`reached_at`)이 «승급이 일어난 적립 기록»(`chapter_jam_events`에서 `promoted = true`인 행)의 `created_at`과 같은 것(승급 함수가 같은 트랜잭션에서 둘을 적으므로 시각이 같다) → 마친 챕터 K-1. 옛 방식으로 오른 챕터는 이 조건에 걸리지 않아 소급되지 않는다. K가 2 미만이면 제외하고 이미 지급 기록이 있는 챕터를 뺀다.
- **`settleChapterRewards(supabase, userId, { scanMissing })`**: `claimPendingChapterRewards`를 먼저 하고, `scanMissing`이 참이면 `findMissingRewardChapters`로 찾은 챕터를 오래된 순으로 `issueChapterReward`한다(칸이 모자라 `pending`이 생기면 그 뒤 챕터는 이어서 기록만 되고 지급은 `claim`이 한다). 같은 프로세스에서 한 유저를 동시에 돌리지 않는다(`settlingUsers` 같은 집합). 던지지 않는다. 호출은 두 곳이다. (1) `settle-pending.ts`의 `settle()` 맨 앞에서 `scanMissing: false`로(홈 조회·칸이 줄어드는 서버 경로·캡슐 상태 조회마다 `pending` 한 번 읽기만 늘어난다), 그 뒤에 옛 대기 보상 지급이 이어진다. (2) `sync.ts` 진입(`settleAfterSlotsFreed` 바로 앞)에서 `scanMissing: true`로 — 이관이 올린 챕터가 «오픈 뒤 첫 동기화»에서 지급된다. 새 지급이 `pending`이면 같은 진입의 막힘 판정(`readCapsuleReceiveBlocked`, C2a가 챕터 보상 대기를 합산)이 동기화를 막는다(Q-c).
- **발급 경로 값 `chapter_reward`를 한 곳에서 정의한다**: `chapter/reward/route.ts`에 `CHAPTER_REWARD_ISSUE_ROUTE = 'chapter_reward'`, 옛 값 `'capsule'`(리터럴, `lib/capsule/*`를 가져오지 않는다), `FEED_EXCLUDED_ISSUE_ROUTES`, `isFeedExcludedIssueRoute(route)`를 둔다. 아래 세 곳이 이것을 쓴다.
  - `activity-feed/capsuleItems.ts`의 `.eq('route', CAPSULE_ISSUE_ROUTE)`를 `.in('route', [...FEED_EXCLUDED_ISSUE_ROUTES])`로 바꾼다(프로필 «아이템 드랍» 카드 합성에서 챕터 보상 개체를 뺀다).
  - `inventory/lockedItemFill.ts`의 `canPostOpenedFeed`가 `isFeedExcludedIssueRoute`로 가른다(챕터 보상에서 나온 잠긴 개체를 열어도 활동 피드에 올리지 않는다).
  - `inventory/obtainRoute.ts`: `ObtainRouteKey`에 `'chapterReward'`를 더하고 발급 경로 `'chapter_reward'`를 그 키로 옮긴다. `LockedItemDetail.tsx`의 «획득 경로» 줄이 그 키를 «챕터 오름 보상»(A2 윈터 검수로 정한 호칭)으로 보여 준다. 글자 상수 위치는 기존 «캡슐» 키가 쓰는 곳(`LockedItemDetail.tsx` 또는 문구 모듈)을 따른다.
- 새 이벤트 값 `chapter_reward_failed`(`engine='points'`)를 `EngineDecisionEvent`에 더한다. DB 변경은 없다(엔진 값은 `points`로 이미 허용된다).
- **하지 않는 일**: 소식·화면 문구 신설(오름 소식 `chapter_up`은 그대로, 보상 받음 안내 문구는 C6 이후 화면 티켓), 옛 `capsule/*` 삭제, 정책 대시보드·문서(C10a, C14), DB 변경, Q-l(동기화 막힘을 넣은 재측정, 카리나가 따로 한다).

## 완료 조건

- 승급하면 마친 챕터마다 (유저, 챕터)당 1회만 지급되고(한 번에 여러 챕터를 넘으면 단계마다), 같은 승급을 다시 처리해도 중복 지급이 없다. 지급은 추첨(C3a)→DB 함수 `chapter_reward_issue`(B5)→후속 처리(포인트, 칸 알림) 순서이고 후속 처리 실패가 지급을 되돌리지 않는다.
- 인벤토리 빈칸이 모자라면 `pending`으로 남고(Q-c) 동기화를 막으며, 칸이 비면(`settleAfterSlotsFreed` 경로) 저장된 결과 그대로 받는다. 이용 정지 중에는 지급되지 않는다.
- 이관(C1b)이 올린 챕터와 새 방식이 올렸지만 지급이 빠진 챕터가 동기화 입구에서 보충 지급된다. 옛 방식으로 이미 마친 챕터는 소급하지 않는다.
- 챕터 보상으로 받은 아이템 배지는 활동 피드에 올라가지 않는다(발급 경로 `chapter_reward`를 프로필 카드 합성과 잠긴 개체 열기 피드 모두에서 제외). 획득 경로 표시가 «챕터 오름 보상»이다.
- 지급·보충·받기 모두 던지지 않고 실패는 `engine_decision_log`에 남는다. `scripts/verify.sh` 통과.
