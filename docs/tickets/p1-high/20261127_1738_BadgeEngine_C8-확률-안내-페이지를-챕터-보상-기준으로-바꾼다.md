# [BadgeEngine] C8 확률 안내 페이지를 챕터 보상 기준으로 바꾼다

## 핵심 요약

- 요구사항: 확률 안내 페이지에서 «캡슐» 구역을 걷고, 챕터 보상에 확률이 있으면 그 표를 보인다. 변경 이력에 바뀐 날짜를 남긴다.
- 구현 계획: 아래 «구현 계획»의 단계를 파일 단위로 따른다(3단계).
- 관련 파일: `jam-web/src/app/(legal)/probability/page.tsx`, `jam-web/src/lib/probability/disclosure.ts`, `changeLog.ts` / 시험 3개, `docs/service/prd/probability/PRD.md`
- 선행 티켓: 20261127_1731(C3a)
- 상위 티켓: 20261127_1720(챕터 게이지 카드로 전환하고 캡슐을 폐지한다). 기획 경위와 사용자 확정 결정은 상위 티켓에 있다.

## 배경 / 문제 정의

상위 티켓 20261127_1720의 단계 C(전환, 같은 배포 창)에 속하는 조각이다. 잼은 챕터를 올리는 경험치이고 포인트는 별도 재화이며, 캡슐은 폐지한다(2026-11-27 사용자 결정). 챕터 1~9의 필요 잼은 870, 1,120, 1,260, 1,600, 1,980, 2,205, 2,700, 3,300, 3,960이고, 넘친 잼은 이월한다.

## 사용자 결정 (2026-11-28, 카리나 문의에 대한 답)

- 옛 변경 이력 행: 확률 안내 «바뀐 날짜» 표에 지금도 실리는 어드민의 옛 «캡슐» 설정 변경 이력(`section_key = 'capsule'`)은 **«캡슐» 없이 문구를 바꿔 보인다.** DB 행은 그대로다. 지난 설정이었음이 읽히게 «이전 보상» 계열 말로 바꾸고(최종 문구는 윈터 검수), 값은 바꾸지 않는다.
- 전환 날짜: 캡슐 보상이 챕터 오름 보상으로 바뀐 사실의 «바뀐 날짜»는 **전환 배포 때 이력 행 1건을 SQL로 넣는다.** 이번 티켓은 SQL 파일과 표시 코드까지만 만들고, 실제 삽입은 메인 세션(카리나)이 이관 실행(C1b)과 같은 배포 창에서 한다(DB는 공용 단일 DB라 지금 넣으면 전환 전에 날짜가 노출된다). 이번에는 SQL을 실행하지 않는다.
- 사전 공지 규칙(`ch18-probability-pre-notice`, `BalanceProbabilityConfirm.tsx`)은 어드민이 확률 칸을 저장할 때 뜨는 확인 모달이다. 이번 코드 전환은 이 모달을 거치지 않으므로, 이미 게시한 확률 안내 화면의 변경에 대한 사전 공지는 상위 성공 기준 11(전환 배포 전 법무 확인·공지)로 따로 다룬다. 이 티켓은 그 판단을 하지 않고 상위 티켓에 «배포 전 확인 항목»으로 남긴다.

## 구현 계획

확률 안내 페이지가 읽는 값의 출처를 `capsule_policy`에서 새 보상 설정으로 바꾸고, 표시 문구를 챕터 오름 보상 기준으로 다시 쓴다. 보상 추첨 설정의 단일 원천은 `jam-web/src/lib/chapter/reward/policy.ts`(`getChapterRewardPolicy`: `chapter_reward_policy` id=1 한 행의 `other_tribe_probability`, `rarity_common/rare/epic/mystic`, `pity_epic_threshold`)와 `chapter_definitions.reward_count`(챕터별 개수), 공용 `jam_policy`(`common_streak_threshold`, `locked_roll_probability`)다.

1. `jam-web/src/lib/probability/disclosure.ts`(약 408줄): `CapsulePolicy`·`CAPSULE_COLUMNS`(112행)·`CapsuleDisclosureInput`(98행)·`buildCapsule`(209행 이하)·`buildPity`(264행)·`readSingleRow(... 'capsule_policy' ...)`(339행)를 챕터 오름 보상 기준으로 바꾼다. 개수 행은 `chapter_definitions`를 읽어 같은 개수가 이어지는 챕터를 묶어(마친 챕터 1~3은 3개, 4~6은 4개, 7~9는 5개) 보인다. 확률 칸은 A3 확정 값과 같게 읽은 값 그대로 보인다(Common 30·Rare 40·Epic 22·Mystic 8, 다른 트라이브 20%). 보정 장치 문장은 `roll.ts`의 실제 보정 규칙대로 쓴다. «JAM! 시작하기에서 여는 첫 캡슐» 행은 신규 가입 보상(`lib/chapter/signup-reward.ts`)의 실제 규칙으로 확인해 맞게 바꾸거나 규칙이 사라졌으면 뺀다. 읽기 실패·비정상 값이면 기본값으로 대신하지 않고 그 구역을 보이지 않는다(기존 원칙 유지). 등급 합계 100 검사와 «동기화 · 보상 · 보정 장치»가 따로 실패하는 구조를 지킨다.
2. `jam-web/src/app/(legal)/probability/page.tsx`(347줄): `CapsuleSection`(198행 이하, «캡슐» 제목·«잼을 채워서 여는 캡슐이에요.»·캡션 둘)을 «챕터 오름 보상» 구역으로 바꾼다. 소개 문장과 캡션은 «챕터를 마치면 받아요» 기준으로 쓰고 «캡슐»·«채우다»를 쓰지 않는다. 섹션 순서(동기화 → 보상 → 시스템 드랍 → 등급 UP → 바뀐 날짜)는 그대로다. 파일 머리 주석도 맞춘다.

## 완료 기록

### 구현 내용 요약

확률 안내 페이지(`/probability`)의 «캡슐» 구역을 «챕터 오름 보상» 구역으로 바꿨다. 확률 값은 바꾸지 않았고 읽는 출처만 바꿨다: `chapter_reward_policy`(추첨과 같은 `getChapterRewardPolicy`), `chapter_definitions.reward_count`(챕터별 개수, 같은 개수가 이어지는 챕터를 묶어 1~3은 3개, 4~6은 4개, 7~9는 5개), 공용 `jam_policy`. 표시 값은 A3 확정 값(등급 30·40·22·8, 다른 트라이브 20%)과 같다. 읽기 실패나 비정상 값이면 기본값으로 대신하지 않고 안내로 바뀐다.
- 바뀐 날짜 표: 옛 `capsule` 이력 행은 DB를 그대로 두고 «이전 잼 보상 …»으로 보인다(Q: 사용자 결정 2026-11-28). 표 머리에 «이전 잼 보상은 잼을 모아 받던 지난 보상이에요»를 더했다. 동기화와 공유하던 두 칸은 날짜와 상관없이 맞는 «동기화와 보상 공통 …»이다. 보상이 바뀐 날 한 줄(구역 키 `chapter_reward_switch`, «아이템 배지를 받는 보상을 이전 잼 보상에서 챕터 오름 보상으로 바꿨어요»)은 SQL로 넣는다.
- SQL `369_probability_chapter_reward_switch_log.sql`: `balance_setting_changes`에 한 행 삽입(`affects_disclosure = true`, 같은 키가 있으면 넣지 않음, 되돌림 SQL 포함). **실행하지 않았다.** 이관(C1b)과 같은 배포 창에서 카리나가 실행한다. 실행 시각이 «바뀐 날짜»가 된다.

### UX Writing 검증 / 윈터 검수 (2026-11-28)
윈터는 코드를 열지 못해 카리나가 전달한 문구만 판단했다. 반영한 것: 옛 이력 이름 «이전 보상»을 C7의 출처 문구와 같은 «이전 잼 보상»으로, 전환 한 줄을 «아이템 배지를 받는 보상을 …»로, 소개를 «챕터를 마쳐 다음 챕터에 오르면 아이템 배지를 받아요»로, 개수 행을 «챕터 1~3을 마칠 때마다»로, 공유 칸을 «동기화와 보상 공통 …»으로, 바뀐 날짜 표 머리 설명 한 문장.
- 보류 1: 보정 장치 문장 «챕터 오름 보상을 15번 받는 동안…». 챕터 보상은 최대 9번이라 새 유저는 닿기 어렵다. 이관(C1b)이 옛 열기 횟수(`capsule_epic_miss`)를 이어받으면 기존 유저는 닿을 수 있어 «닿지 않아요»를 덧붙일 수 없다. C1b 결정 뒤 문장을 정한다. 값은 바꾸지 않았다.
- 보류 2: «챕터 오름 보상»을 화면 고정 용어로 등록하는 안건(가이드 406행·공통 용어 55행과의 정합). 용어표 결정 사안이다.
- 후속 문서: 가이드 3.3절 403행과 공통 용어 116행의 «캡슐을 15번 여는 동안» 예시는 C14b에서 바꾼다.
