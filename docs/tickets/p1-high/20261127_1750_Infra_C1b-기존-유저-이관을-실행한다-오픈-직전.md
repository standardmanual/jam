# [Infra] C1b 기존 유저 이관을 실행한다 (오픈 직전)

- 요구사항: C1이 만든 함수 `chapter_jam_backfill_chunk`로 기존 유저의 이번 챕터 진행값을 원장 기준으로 채운다(챕터 하향 0, 이관이 올린 챕터를 기록). main 승격 직전에, 동기화가 멈춘 배포 창에서 한 번 실행한다.
- 구현 계획: 실행 파일 `seed_20261127_chapter_jam_backfill_run.sql`과 되돌림 `..._run_down.sql`을 쓰고, 아래 «실행 순서»대로 실행한다.
- 관련 파일: `jam-web/supabase/migrations/seed_20261127_chapter_jam_backfill_run.sql`(신규), `seed_20261127_chapter_jam_backfill_run_down.sql`(신규), 참고: `367_chapter_jam_backfill_prepare.sql`
- 선행 티켓: 20261127_1728(C1). 코드 전환(C2a) 배포와 같은 창에서, 배포 직전에 실행한다.
- 상위 티켓: 20261127_1720(챕터 게이지 카드로 전환하고 캡슐을 폐지한다).

## 배경 / 문제 정의

C1이 이관 함수와 백업 표를 준비해 둔다. 이중 쓰기(B4) 기간에는 옛 방식이 챕터를 올려도 `user_chapters.chapter_jam`이 줄지 않아 값이 어긋나므로, 새 진행값으로 읽기를 전환하기 직전에 원장 기준으로 다시 계산해야 한다. 이 티켓이 그 실행이다. 사용자 결정(2026-11-27): 진행값은 원장 기준, 이관 판정도 평상 규칙(여러 단계 가능, 이월), 보상은 이관으로 새로 오른 챕터만(오픈 뒤 첫 동기화에서 C3b가 지급).

## 실행 순서 (오픈 직전, 카리나)

1. 카즈하가 현재 유저 수와 분포(`user_chapters` 행 수, 챕터별 인원, 지갑 잔액 분포)를 확인해 보고한다.
2. 대조 모드로 대조표를 만든다: `SELECT public.chapter_jam_backfill_chunk(200, FALSE);`를 `remaining`이 청크 크기 이하가 될 때까지 필요한 만큼. 게이지가 낮아지는 유저(`gaugeDrop`)와 이관이 올리는 유저(`promoted`)를 사용자에게 보고하고 진행 여부를 확인받는다.
3. 동기화가 멈춘 배포 창에서 쓰기 모드로 실행한다: `SELECT public.chapter_jam_backfill_chunk(200, TRUE);`를 `remaining = 0`이 될 때까지 반복한다.
4. 실행 직후 읽기 전용 확인: 이전·이후 유저별 대조표(챕터 하향 0, 진행값이 계산과 일치), `capsule_opens`·`capsule_unseen_results`·`capsule_pending_rewards` 행 수 불변, `chapter_jam_backfill` 행 수 = 이관한 유저 수.
5. 결과를 사용자에게 보고한다.

## 완료 조건

- 이관 전후 유저별 대조표에서 챕터 하향 0명, 이번 챕터 진행값 일치율 100%다.
- `capsule_opens`, `capsule_unseen_results`, `capsule_pending_rewards` 행 수 변화가 0이고 대기 보상·받은 아이템이 그대로다.
- 되돌림 SQL을 실측으로 확인했고 사용자에게 보고했다.

## 규모와 체크포인트

- 체크포인트: 대조표 보고와 사용자 확인 뒤에만 쓰기 모드로 실행한다. 사용자 승인 없이 쓰기 모드를 부르지 않는다(데이터를 바꾸므로).

## 주요 의사결정 / 핵심 메모

- 실행은 동기화가 멈춘 창에서 한다. 이관 계산과 B4 적립 사이에 새 잼이 들어오면 그 잼이 두 번 쌓일 수 있다.
- 이관 때 `chapter_jam_events`에 원장 줄의 키를 심어 두었으므로 옛 활동이 다시 정산돼도 진행값이 두 번 쌓이지 않는다(C1 설계).
- 이관이 올린 챕터는 `chapter_jam_backfill.promoted_chapters`에 남는다. C3b가 오픈 뒤 첫 동기화에서 이 기록으로 보상을 지급한다.
