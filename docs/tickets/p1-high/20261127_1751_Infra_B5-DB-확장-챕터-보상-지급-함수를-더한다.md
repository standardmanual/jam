# [Infra] B5 DB 확장: 챕터 보상 지급 함수를 더한다

## 핵심 요약

- 요구사항: 챕터 오름 보상(추첨 결과)을 인벤토리에 넣는 DB 함수를 만든다. 칸 확인, 아이템 지급, 발급 기록, 같은 등급 연속·에픽 보정 카운터 갱신, 지급 기록(`chapter_reward_grants`) 상태 갱신이 한 트랜잭션이다. 옛 캡슐 함수(`capsule_open_counted`, `capsule_claim_pending`)는 캡슐 표에 묶여 있어 재사용할 수 없다.
- 구현 계획: 마이그레이션 `368_chapter_reward_grant.sql`(+ 짝 `_down.sql`)에 함수 2개를 더한다. 아래 «구현 계획»을 따른다.
- 관련 파일: `jam-web/supabase/migrations/368_chapter_reward_grant.sql`(신규), `368_chapter_reward_grant_down.sql`(신규). 참고: 라이브 DB 함수 `capsule_claim_pending`(지급 순서), `grant_inventory_item_locked`, `item_issue_log`, `user_drop_state`, `366_chapter_reward.sql`
- 선행 티켓: 20261127_1726(B3)
- 상위 티켓: 20261127_1720(챕터 게이지 카드로 전환하고 캡슐을 폐지한다).

## 배경 / 문제 정의

C3b(챕터 오름 보상 지급)가 추첨한 결과를 인벤토리에 넣어야 하는데, 지금 지급은 옛 캡슐 DB 함수 안에 있다(2026-11-27 라이브 DB 확인). `capsule_claim_pending`은 `capsule_pending_rewards`(유저당 슬롯 1·2개)와 `user_capsules`를 잠그고 `capsule_opens`에 기록하므로 챕터 보상(챕터마다 1건, 최대 9건)에 쓸 수 없다. 칸 확인과 지급이 같은 트랜잭션이어야 부분 지급이 없다. 기존 지급 순서(인벤토리 행 잠금 → 칸 확인 → `grant_inventory_item_locked` → `item_issue_log` → 카운터 갱신)를 따른다.

## 구현 계획

### 설계 결정 (카리나, 2026-11-27)

- **함수 2개**(내부 보조 함수는 만들지 않는다): `chapter_reward_claim(p_user_id, p_chapter_no)`가 `pending` 행의 저장된 `drawn_items`를 그대로(다시 추첨하지 않는다) 인벤토리에 넣고 `claimed`로 바꾼다. `chapter_reward_issue(p_user_id, p_chapter_no, p_items)`는 추첨 결과를 `chapter_reward_grants`에 `pending`으로 기록한 뒤(같은 (유저, 챕터)는 한 번만) 곧바로 `chapter_reward_claim`을 불러 빈칸이 충분하면 지급한다. 모자라면 `pending`으로 남긴다.
- **지급 순서는 `capsule_claim_pending`을 따른다**: 이용 정지 확인 → 지급 행 잠금 → 인벤토리 행 잠금 → 빈칸 확인(모자라면 아무것도 바꾸지 않음) → 항목마다 `grant_inventory_item_locked`(`obtained_by`는 캡슐과 같은 `'drop'`), 발급 기록 `item_issue_log`, 같은 등급 연속(`user_drop_state.common_streak`)·에픽 보정(`capsule_epic_miss`) 카운터 갱신(보정은 묶음에 에픽 이상이 하나라도 있으면 0, 아니면 +1) → 지급 행 `claimed`. `capsule_*` 표와 `capsule_opens`는 건드리지 않는다.
- **발급 기록 경로 값은 새 값 `'chapter_reward'`** 다(`item_issue_log.route`는 문자열이고 검사 제약이 없다). 활동 피드 제외 규칙이 지금 `'capsule'`을 직접 읽으므로(`jam-web/src/lib/activity-feed/capsuleItems.ts`, `jam-web/src/lib/inventory/lockedItemFill.ts`), 이 두 곳이 `'chapter_reward'`도 같은 규칙으로 다루도록 C3b가 고친다(새 값으로 두면 보상 출처별 집계를 따로 볼 수 있다). 배포 전에 C3b가 끝나 있어야 한다.
- **멱등과 직렬화**: (유저, 챕터)가 기본 키라 같은 호출이 두 번 와도 한 번만 기록·지급된다. 지급 행 잠금(`FOR UPDATE`)이 같은 유저의 동시 호출을 직렬화한다. 이미 `claimed`인 행에 `claim`을 다시 부르면 아무것도 하지 않고 `duplicate`로 답한다.
- **응답 모양**: 지급 항목은 `capsule_claim_pending`과 같은 모양(`inventoryItemId`, `badgeId`, `rarity`, `locked`, `serialNumber`)이라 TS의 후속 처리(`recordChapterRewardItems`)가 그대로 받는다.
- **하지 않는 일**: 캡슐 연 횟수 기록(`capsule_opens`), 포인트 지급(TS 후속 처리가 한다), 칸 부족 알림(TS가 한다), 옛 함수·표 변경, 데이터 이관.

### `jam-web/supabase/migrations/368_chapter_reward_grant.sql` (신규)

머리 주석에 티켓 번호(20261127_1751, 상위 20261127_1720), 확장 단계(새 함수 2개만 더하고 데이터·옛 함수를 바꾸지 않음), 아직 호출하는 곳이 없음(C3b가 부른다), 공용 단일 DB라 즉시 프로덕션 반영, 되돌림은 `368_chapter_reward_grant_down.sql`임을 적는다. 본문 순서:

1. **`public.chapter_reward_claim(p_user_id UUID, p_chapter_no INTEGER) RETURNS JSONB`** (plpgsql, SECURITY DEFINER, `SET search_path TO 'public'`). 동작:
   1. 입력 검사: `p_user_id`·`p_chapter_no` 중 하나라도 NULL이거나 `p_chapter_no < 1`이면 `{ok: false, error: 'invalid_input'}`.
   2. 이용 정지(`user_suspensions`에 `lifted_at IS NULL`인 행)면 `{ok: false, error: 'user_suspended'}`.
   3. `chapter_reward_grants`에서 (유저, 챕터) 행을 `FOR UPDATE`로 읽는다. 없으면 `{ok: false, error: 'grant_not_found'}`. `status`가 `claimed`면 `{ok: true, duplicate: true, status: 'claimed', chapterNo}`.
   4. 저장된 항목이 배열이 아니거나 비어 있으면 `{ok: false, error: 'invalid_items'}`.
   5. 인벤토리 행(`inventory`, `user_id`)을 `FOR UPDATE`로 읽는다. 없으면 `{ok: false, error: 'inventory_not_found'}`. 빈칸 = `GREATEST(0, max_slots - used_slots)`가 항목 수보다 작으면 아무것도 바꾸지 않고 `{ok: false, error: 'insufficient_slots', free, needed}`.
   6. `user_drop_state`의 `common_streak`, `capsule_epic_miss`를 읽는다(행이 없으면 0).
   7. 항목마다(순서대로): `grant_inventory_item_locked(inventory.id, badge_id, 'drop', NULL, locked, lock_reason, unlock_required)`를 부르고 `ok`가 아니면 `RAISE EXCEPTION 'chapter_reward_claim_grant_failed: ...'`(트랜잭션 전체가 취소된다). 지급된 아이템의 일련번호를 읽고 `item_issue_log`에 `(user_id, inventory_item_id, route = 'chapter_reward', source_activity_id = NULL, badge_id, rarity, rolled_rarity, locked, serial_number)`를 넣는다. 등급이 `common`이면 연속 +1, 아니면 0. `epic`·`mystic`이 있으면 표시한다.
   8. 카운터 저장: `user_drop_state`를 `INSERT ... ON CONFLICT (user_id) DO UPDATE`로 `common_streak`, `capsule_epic_miss`(에픽 이상이 있었으면 0, 아니면 +1), `updated_at`을 갱신한다.
   9. 지급 행을 `status = 'claimed'`, `claimed_at = now()`로 바꾼다.
   10. `{ok: true, duplicate: false, chapterNo, items: [...], pendingCount: 이 유저의 남은 pending 행 수}`를 돌려준다.
2. **`public.chapter_reward_issue(p_user_id UUID, p_chapter_no INTEGER, p_items JSONB) RETURNS JSONB`** (같은 속성). 동작:
   1. 입력 검사: 위와 같고, `p_items`가 NULL이거나 배열이 아니거나 길이가 1 미만 또는 50 초과이거나 어느 항목에 `badge_id`·`rarity`가 없으면 `{ok: false, error: 'invalid_items'}`.
   2. 이용 정지면 `{ok: false, error: 'user_suspended'}`.
   3. 챕터가 `chapter_definitions`에 없으면 `{ok: false, error: 'chapter_not_found'}`.
   4. `chapter_reward_grants`에 `(p_user_id, p_chapter_no, jsonb_array_length(p_items), p_items, 'pending')`를 `ON CONFLICT (user_id, chapter_no) DO NOTHING`으로 넣고 `GET DIAGNOSTICS`로 행 수를 본다. 0이면 이미 있는 행이므로 현재 상태를 읽어 `{ok: true, duplicate: true, status, chapterNo}`를 돌려준다(다시 지급하지 않는다).
   5. 새로 넣었으면 `chapter_reward_claim(p_user_id, p_chapter_no)`를 부른다. 결과가 `ok`면 `{ok: true, duplicate: false, status: 'claimed', chapterNo, items}`, 오류가 `insufficient_slots`면 `{ok: true, duplicate: false, status: 'pending', chapterNo, free, needed}`(행은 남는다), 그 밖의 오류(`inventory_not_found`, `invalid_items` 등)는 방금 넣은 `pending` 행을 `DELETE`로 지운 뒤 그 오류를 그대로 돌려준다(오류를 반환하면 트랜잭션이 취소되지 않으므로 직접 지운다. `RAISE EXCEPTION`이 나면 트랜잭션 전체가 취소돼 행도 남지 않는다).
3. 권한: 두 함수 모두 `REVOKE ALL ... FROM PUBLIC;`, `... FROM anon, authenticated;`, `GRANT EXECUTE ... TO service_role;`. `COMMENT ON FUNCTION`으로 동작과 «C3b가 부른다, 경로 값 chapter_reward»를 적는다.
4. 옛 함수(`capsule_*`, `grant_inventory_item*`)와 표는 건드리지 않는다.

### `jam-web/supabase/migrations/368_chapter_reward_grant_down.sql` (신규, 되돌림)

`DROP FUNCTION IF EXISTS public.chapter_reward_issue(UUID, INTEGER, JSONB);`, `DROP FUNCTION IF EXISTS public.chapter_reward_claim(UUID, INTEGER);`. 주석에 «이 함수로 지급한 아이템과 발급 기록(`route = 'chapter_reward'`)은 되돌림이 지우지 않는다. 지급이 일어난 뒤에는 함수만 지운다고 데이터가 원상이 되지 않는다»를 적는다. 여러 번 실행해도 같은 결과여야 한다.

### 하지 않는 일
- 코드(TS) 변경, 생성 타입 반영(적용 뒤 카리나가 함수 시그니처를 확인하고 필요하면 반영), 포인트·알림·피드 처리, 이관(C1b), 옛 함수 변경은 하지 않는다.

### 카리나 실행 절차(참고, 아현은 하지 않는다)
1. 드라이런(한 `DO` 블록, 끝에서 `RAISE EXCEPTION`으로 전체 취소, 시험 유저 `3649ed39`, 라이브 아이템 배지 사용): ① 빈칸 충분하면 `issue`가 3개를 지급해 `claimed`: 인벤토리 아이템 3행, `used_slots` +3, 발급 기록 3행(`route = 'chapter_reward'`), 카운터 갱신, 응답 일련번호 ② 같은 `issue` 재호출은 `duplicate`이고 아이템·카운터 불변 ③ 빈칸이 모자라면(최대 칸 수를 임시로 줄임) `pending`으로 남고 아이템·카운터 불변, 빈칸을 늘려 `claim`하면 지급되고 한 번 더 `claim`하면 `duplicate` ④ 잠긴 항목이 잠금 열(`locked`, `lock_reason`, `unlock_required`)로 들어가고 발급 기록의 `locked`가 참, 잠금 인자가 잘못되면(이유 없음) 호출 전체가 취소돼 지급 행도 남지 않음 ⑤ 이용 정지 중이면 거절되고 아무것도 기록되지 않음(시험용 정지 행을 같은 트랜잭션에서 넣었다 뺌) ⑥ 잘못된 입력(빈 배열, 배열 아님, `badge_id` 없음, 없는 챕터)은 거절 ⑦ 같은 등급 연속·에픽 보정 카운터 계산(Common만이면 연속 증가·보정 +1, 에픽 이상이 있으면 보정 0) ⑧ 권한(`anon`·`authenticated` 실행 불가, `service_role` 가능) ⑨ 되돌림 파일 두 번 실행 → 원상 대조(함수 수, 기존 함수 본문·권한 해시, 유저의 인벤토리·발급 기록·카운터·지급 행) → 취소.
2. `apply_migration`으로 적용하고 직후 읽기 전용으로 함수·권한·데이터 불변을 확인한다.

## 완료 조건

- `chapter_reward_issue`가 같은 (유저, 챕터)를 두 번 불러도 한 번만 기록·지급하고, 빈칸이 충분하면 지급해 `claimed`로, 모자라면 `pending`으로 남긴다(부분 지급 없음).
- `chapter_reward_claim`이 `pending` 행을 저장된 항목 그대로 지급하고 `claimed`로 바꾸며, 같은 호출을 다시 해도 중복 지급이 없다.
- 지급한 아이템마다 발급 기록이 남고 같은 등급 연속·에픽 보정 카운터가 갱신된다. 이용 정지·인벤토리 없음은 거절된다.
- 드라이런(적용, 시험, 되돌림, 원상 대조)을 통과했고 기존 함수 본문·권한이 그대로다.
