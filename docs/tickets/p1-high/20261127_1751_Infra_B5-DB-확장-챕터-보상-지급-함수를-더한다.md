# [Infra] B5 DB 확장: 챕터 보상 지급 함수를 더한다

## 핵심 요약

- 요구사항: 챕터 오름 보상(추첨 결과)을 인벤토리에 넣는 DB 함수를 만든다. 칸 확인, 아이템 지급, 발급 기록, 같은 등급 연속·에픽 보정 카운터 갱신, 지급 기록(`chapter_reward_grants`) 상태 갱신이 한 트랜잭션이다. 옛 캡슐 함수(`capsule_open_counted`, `capsule_claim_pending`)는 캡슐 표에 묶여 있어 재사용할 수 없다.
- 구현 계획: 마이그레이션 `368_chapter_reward_grant.sql`(+ 짝 `_down.sql`)에 함수 2개를 더한다. 아래 «구현 계획»을 따른다.
- 관련 파일: `jam-web/supabase/migrations/368_chapter_reward_grant.sql`(신규), `368_chapter_reward_grant_down.sql`(신규). 참고: 라이브 DB 함수 `capsule_claim_pending`(지급 순서), `grant_inventory_item_locked`, `item_issue_log`, `user_drop_state`, `366_chapter_reward.sql`
- 선행 티켓: 20261127_1726(B3)
- 상위 티켓: 20261127_1720(챕터 게이지 카드로 전환하고 캡슐을 폐지한다).

## 배경 / 문제 정의

C3b(챕터 오름 보상 지급)가 추첨한 결과를 인벤토리에 넣어야 하는데, 지금 지급은 옛 캡슐 DB 함수 안에 있다(2026-11-27 라이브 DB 확인). `capsule_claim_pending`은 `capsule_pending_rewards`(유저당 슬롯 1·2개)와 `user_capsules`를 잠그고 `capsule_opens`에 기록하므로 챕터 보상(챕터마다 1건, 최대 9건)에 쓸 수 없다. 칸 확인과 지급이 같은 트랜잭션이어야 부분 지급이 없다. 기존 지급 순서(인벤토리 행 잠금 → 칸 확인 → `grant_inventory_item_locked` → `item_issue_log` → 카운터 갱신)를 따른다.

## 구현 계획

### 설계 결정 (카리나, 2026-11-27)

- **함수 2개**: `chapter_reward_issue(p_user_id, p_chapter_no, p_items jsonb)`는 추첨 결과를 `chapter_reward_grants`에 기록하고(같은 (유저, 챕터)는 한 번만, `ON CONFLICT DO NOTHING`) 빈칸이 충분하면 곧바로 지급해 `claimed`로 바꾼다. 모자라면 `pending`으로 남긴다. `chapter_reward_claim(p_user_id, p_chapter_no)`는 `pending` 행을 저장된 `drawn_items` 그대로(다시 추첨하지 않는다) 지급한다. 지급 순서·잠금·카운터는 `capsule_claim_pending`을 따른다.
- 이용 정지면 거절(`user_suspended`), 인벤토리가 없으면 `inventory_not_found`. 칸이 모자라면 아무것도 바꾸지 않는다(`insufficient_slots`, 이미 `pending`으로 기록한 행은 그대로 남는다).
- 발급 기록 경로 값(`item_issue_log.route`)과 `obtained_by`는 구현할 때 기존 제약·트리거를 확인해 정하고(라이브에서 `item_issue_log`에 검사 제약은 없다) 시험으로 확인한다.
- 지급 응답은 `capsule_claim_pending`과 같은 모양(`items`: 인벤토리 아이템 id, 배지 id, 등급, 잠금, 일련번호)이라 TS가 `recordIssuedRewards`(포인트)를 이어서 부를 수 있다.
- 권한은 service_role만(PUBLIC·anon·authenticated 회수). 확장 단계(새 함수 2개만, 옛 함수·표 불변). 되돌림 SQL을 짝 파일로 둔다.

세부(SQL 문장 단위)는 이 티켓을 시작할 때 라이브 함수 본문을 다시 읽고 보강한다.

## 완료 조건

- `chapter_reward_issue`가 같은 (유저, 챕터)를 두 번 불러도 한 번만 기록·지급하고, 빈칸이 충분하면 지급해 `claimed`로, 모자라면 `pending`으로 남긴다(부분 지급 없음).
- `chapter_reward_claim`이 `pending` 행을 저장된 항목 그대로 지급하고 `claimed`로 바꾸며, 같은 호출을 다시 해도 중복 지급이 없다.
- 지급한 아이템마다 발급 기록이 남고 같은 등급 연속·에픽 보정 카운터가 갱신된다. 이용 정지·인벤토리 없음은 거절된다.
- 드라이런(적용, 시험, 되돌림, 원상 대조)을 통과했고 기존 함수 본문·권한이 그대로다.
