# [UI] 배지 트리 — 눈금 1개 계열을 그리드로 묶고 진행을 배지 보더 링으로 표시

> 선행: `20260906_1323`(배지 트리 화면 정리 9건 — `BadgeStageRail`·`BadgeFamilyRow`·
> `badgeProgressText`를 재구성했다. **그 티켓이 머지된 뒤에 착수한다**)
> 대상 화면: `/badges/tree` 하나.

## 배경 / 문제 정의

**눈금이 1개뿐인 계열에서 「레일」이라는 형식이 거짓말을 한다.**

사용자가 지적한 화면: 「100km 클럽」·「500km 클럽」·「1000km 클럽」이 각각 카드 한 장을
통째로 쓰는데, 안에는 썸네일 **하나**와 캡션(`0.0/100.0km`) 한 줄뿐이다. 연결선이 없고,
아코디언을 열어도 등급 하나가 나온다. 레일의 은유(눈금과 눈금을 잇는 진행)가 성립하지 않는
자리에 레일 카드를 쓰고 있다.

**DB 실측 — 계열별 눈금 수 분포** (2026-09-06, v5 활동 배지 194계열 630종
`family_key ~ '^(walking|running|cycling|hiking|trail_running):[A-Z]+[0-9]+$'`):

| 눈금 수 | 계열 | 배지 | 현재 표현 |
|---|---|---|---|
| **1개** | **63** | **63** | `BadgeStageRail` — 연결선 없음 ← **이번 대상** |
| 2개 | 10 | 20 | `BadgeStageRail` |
| 3개 | 26 | 78 | `BadgeStageRail` |
| 4개 | 69 | 276 | `BadgeStageRail` |
| 6·7·8개 | 26 | 193 | `BadgeLevelGauge`(레벨형) |

**전체 계열의 1/3(63계열)이 눈금 1개**다. 이들이 세로로 한 줄씩 차지해 스크롤만 길어진다.

부수 문제: 「100km 클럽」·「500km 클럽」·「1000km 클럽」은 사용자에게 한 시리즈로 읽히지만
`family_key`가 각각 달라 계열로 묶이지 않는다. 세로 목록에서는 서로 떨어져 놓인다.

## 사용자 확정 사항 (2026-09-06)

- **눈금 1개 계열(63계열)은 그리드로 묶는다** — 한 줄씩 두지 않는다
- **2눈금 계열(10계열)은 레일을 유지한다** — 연결선이 의미를 가진다
- **진행 표시는 배지 이미지 보더를 따라 그라데이션으로 채우는 링**

## 상세 요구사항

### UI/UX 관점

**왜 링만 바꾸는 것으로는 부족한가** (착수 전 검토 결론, 사용자 동의):
44px 썸네일에 링을 두르면 두께가 3px 남짓이라 진행이 안 보이고, 보이게 하려면 썸네일을
72~90px로 키워야 하는데 그러면 카드가 지금보다 커져 스크롤이 그대로다. **그리드로 묶어야
실제 이득(63계열이 1~2스크린)이 나온다.** 그래서 이 티켓은 「표현 교체 + 배치 변경」이 한 건이다.

**신규 MODULAR 패턴 1종이 필요하다.** 재사용 가능한 기존 컴포넌트가 없음을 실측했다:
- `BadgeFrame`(`design-system/components/cards/`)은 이미지를 7가지 모양으로 **클리핑**하는
  컴포넌트이고 진행과 무관하다(그리고 MODULAR 미도입 8종에 속한다)
- `ProgressBar`는 선형 전용이다
- 코드베이스에 `conic-gradient` 진행 표시 구현이 **0건**이다

**설계 제약 — 반드시 지킬 것:**

1. **링은 상태색 하나로만 채운다.** 지금 썸네일 아래 3px 바가 등급색
   (rare/epic/mystic — `RARITY_BAR_COLOR`)이고 진행은 상태색(앰버=채우는 중 / 라임=다 채움)이다.
   §06 색 시스템이 두 채널을 일부러 분리해 뒀다. 링을 **등급색** 그라데이션으로 채우면 같은
   물체 주위에서 두 채널이 섞여 「초록 링 = 다 채웠다」인지 「초록 링 = Rare다」인지 구분이
   사라진다. **등급은 지금의 3px 바(또는 등급 칩)에 남긴다.**
2. **수치 캡션을 남긴다.** 원형 진행은 작은 값에서 못 읽는다 — `0.0/100.0km`(0%)와 2%가
   눈으로 구분되지 않는다. 링은 「대략 어디쯤인가」의 앰비언트 신호이고, 정확한 값은 숫자
   한 줄이 말한다. **`aria-label`에도 수치를 유지한다**(형태만으로는 값이 전달되지 않는다).
3. **획득 체크·게이트 자물쇠 마커는 링 바깥에 둔다.** 지금 `BadgeStageRail`의
   `StopThumbnail`이 쓰는 마커를 그대로 얹되, 링과 같은 원 위에서 부딪히지 않게 한다.
4. **`prefers-reduced-motion`에서 채우기 전이를 끈다.** 링에 전이를 넣는다면
   `transform`/`opacity` 계열만 쓴다(레일·요약 헤더가 `width %`를 쓰는 것과 달리).

**배치**: 그리드 열 수는 구현자가 375px 기준으로 정하되(2열 또는 3열), 판단 근거를 완료
기록에 적는다. 배지 이미지가 주인공이므로 셀 안 위계는 `링+이미지 → 이름 → 수치` 순이다.

### 서비스/코드베이스 관점

- **분기 지점**은 `BadgeFamilyRow.tsx`가 아니라 그 **위**다. 지금 `BadgeFamilyRow`는 계열
  하나 = 한 줄을 그리는 컴포넌트라, 「여러 계열을 한 그리드에 묶는다」는 이 컴포넌트가 할 수
  없다. `BadgeTreeClient`의 `nextGoals`를 **두 갈래로 나눠** 렌더해야 한다:
  - `family.kind === 'graded' && family.stages.length === 1` → 그리드 셀 묶음
  - 그 외 → 지금처럼 `BadgeFamilyRow` 한 줄씩
- **정렬**: 지금 `nextGoals`는 「진행이 가까운 순 → sortOrder」로 정렬된다. 두 갈래로 나눌 때
  **각 갈래 안에서 그 정렬을 유지**한다. 두 묶음의 화면 순서(그리드가 위인지 아래인지)는
  구현자가 정하고 근거를 적는다 — 「진행이 가까운 것이 위」라는 지금 원칙과 어긋나지 않게 할 것.
- 진행 데이터는 이미 있다. `progressByBadgeId`·`frontierBadgeIdByFamilyKey`
  (`20260906_1323` §8이 만든 앵커)를 그대로 쓴다. **서버 조회·계산을 새로 추가하지 않는다.**
- 문구 조립은 `badgeProgressText.ts`가 한다 — DS는 완성 문자열만 받는다(기존 원칙).

### 하지 않는 것

- 2눈금 이상 계열의 표현 변경 (사용자 확정: 레일 유지)
- 레벨형(`BadgeLevelGauge`)·반복형(`BadgeStampRow`) 표현 변경

- 발급 엔진·진행 계산 로직
- 색 토큰 값 변경

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

MODULAR 신규 패턴 `BadgeProgressRingCard`(design-system/components/patterns/)를 만들고,
`BadgeTreeClient`의 `nextGoals`를 두 갈래(`kind==='graded' && stages.length===1` → 그리드 /
그 외 → 기존 `BadgeFamilyRow` 레일)로 나눠 렌더한다. 서비스 쪽 계산 계층(상태 판정·캡션
조립)은 `BadgeFamilyRow`의 등급형 분기와 같은 방식을 재사용하는 신규 얇은 wrapper
`BadgeProgressGridCell.tsx`가 담당하고, 문구는 `formatFrontierProgressText`를 그대로
재사용하는 신규 함수 `formatGridCellCaption`(badgeProgressText.ts)이 조립한다. 서버
조회·진행 계산은 추가하지 않았다 — `progressByBadgeId`·`frontierBadgeIdByFamilyKey`를
그대로 재사용.

**링 구현**: 두 겹 원 트릭(바깥 원을 `conic-gradient`로 채우고, 그보다 작은 안쪽 원으로
가운데를 덮어 링 두께만 보이게 함) — 등급색은 절대 올리지 않고 상태색(앰버=채우는 중 /
라임=다 채움 또는 획득)만 쓴다. 마커(체크/자물쇠)는 링 바깥(우상단, -6px 오프셋)에 얹는다.
캡션(수치)은 항상 그리고, `ariaLabel`도 호출부가 수치 포함 완성 문장으로 조립해서 넘긴다.
`prefers-reduced-motion`에서는 카드 진입 페이드(`transform`/`opacity`)만 끈다 — 채우기 %
(링 각도) 자체엔 애초에 전이를 걸지 않는다(스냅샷 표시, 게이지가 아님).

**그리드 열 수**: 3열(375px 기준)로 정했다. esbuild+playwright로 실렌더 확인한 결과
(아래 검증 참고), 2열보다 행 수를 더 줄이면서도 이름(`--text-caption`)·캡션(`--text-micro`)이
읽히고 72px 링도 시각적으로 명확했다.

**섹션 순서**: 그리드/레일 두 섹션을 진행률로 다시 인터리빙하지 않고, `nextGoals[0]`
(전체에서 가장 가까운 목표)이 어느 갈래에 속하는지로 어느 섹션을 위에 둘지 정했다 — 두
묶음을 잘게 쪼개 번갈아 배치하면 "63계열을 그리드로 묶어 스크롤을 줄인다"는 이번 티켓의
목적이 무너지고, 섹션 단위로는 "가장 가까운 목표가 위" 원칙이 그대로 유지된다.

### 주요 의사결정 / 핵심 메모

- **분기 지점**: 티켓 지시대로 `BadgeFamilyRow` 안이 아니라 `BadgeTreeClient`의 `nextGoals`
  단계에서 나눴다. `BadgeFamilyRow`는 그대로(수정 없음) — 2눈금 이상 계열의 표현은 손대지

  kind나 progress 부재 시 `null`을 돌려준다. `BadgeStageRail.jsx`는 그 경우 상태 라벨
  (`STATUS_LABEL`, DS 내부 상수)로 폴백하는데, 그 상수가 DS 파일 안에 비공개로 있어
  서비스(TS) 레이어에서 재사용할 수 없었다. 완성 문자열만 받는 프레젠테이션 전용 원칙을
  지키려면 이 폴백 판단도 서비스 쪽(`badgeProgressText.ts`)에서 끝내야 해서 함수를 추가했다.
- **아쉬움 줄(regret line)을 그리드 셀에 넣지 않았다**: 티켓의 설계 제약 목록에 없고, 스펙에
  없는 기능을 추가하지 않기 위해 제외했다. 필요하면 별도 티켓으로 판단할 사안.
- **2눈금 이상의 dual/multi 조건을 가진 단일눈금 계열**: 현재 DB에 실존 여부를 확인하지
  않았다(§ alerts). 존재한다면 `BadgeFamilyRow`가 함께 그리던 `DualAxisGauge`가 그리드
  셀에는 없어 2축 상세가 "조건 충족"/"잠김" 텍스트로 축약된다 — 티켓 범위(DualAxisGauge
  통합은 구현 계획에 없음) 밖이라 손대지 않았다.

### 잔여 이슈
- 게이트 리뷰가 "63계열(4~6스크린)"로 우려했던 수치는 **5개 활동 종목(걷기·달리기·자전거·
  등산·트레일러닝) 전체를 합산한 값**이었다. 실제 화면은 종목별 탭으로 분리돼 있어, 탭 하나가
  보여주는 눈금 1개 계열은 5~13개 수준이다(걷기 탭 5개, 자전거 탭 5개를 staging 실측). 3열
  기준 탭당 2행 안팎이라 우려했던 스크롤 길이 문제는 실사용에서 발생하지 않는다 — 사용자
  확인 후 "일단 머지해서 실화면 확인" 결정, 실측 결과 열 수 조정은 불필요한 것으로 확정.
- 눈금 1개 + 2축/다중(dual/multi) 조건 조합의 실존 여부는 이번에도 확인하지 않았다 — 그리드
  섹션에 렌더된 계열은 모두 누적/기록/주기형(단일 캡션)이었고, dual/multi가 있었다면
  "조건 충족"/"잠김" 텍스트로 보였을 것이나 이번 실측 범위(걷기·자전거 2개 탭)에서는
  발견되지 않았다. 나머지 탭(달리기·등산·트레일러닝)은 확인하지 않았다.
- 인터랙션 리뷰가 제안한 5가지(탭 피드백 scale 통일·링 채움 애니메이션·그리드 진입 모션과
  레일의 무모션 통일·마커-인접셀 겹침 실측·이름 줄바꿈 2줄 상한)는 사용자 확정으로 이번
  티켓 범위에서 제외 — 필요 시 별도 티켓으로 진행.
