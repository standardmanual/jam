# [Admin] POI·레시피 하드 삭제에 참조 카운트 가드 추가

## 배경 / 문제 정의

`/admin/poi`(POI 관리)와 `/admin/recipes`(믹스 레시피)는 이미 다중선택 + 하드 일괄삭제가
있다(`DataTable` + `DataTableBulkActionBar` 재사용, `PoiTable.tsx`·`RecipeTable.tsx`).
**둘 다 별도 일괄삭제 API가 없다** — 선택된 행 각각에 대해 기존 단건
`DELETE /api/admin/poi/[id]` · `DELETE /api/admin/recipes/[id]`를 순차 호출하는 구조다
(`PoiTable.tsx:213-233`, `RecipeTable.tsx:194-208`). 즉 **단건 DELETE 라우트 하나만 가드하면
단건·일괄 양쪽 다 막힌다** — 별도 일괄 API를 새로 만들 필요는 없다.

그런데 `/admin/badges`(배지 관리)와 달리 이 두 라우트는 삭제 전 참조 카운트 체크가 전혀 없다
(`src/app/api/admin/poi/[id]/route.ts` DELETE, `src/app/api/admin/recipes/[id]/route.ts` DELETE
둘 다 `supabase.from(...).delete().eq('id', id)`를 바로 실행).

### 실측한 참조 관계

**POI (`poi` 테이블)** — 위험도 높음. 마이그레이션 실측 결과 아래가 `poi_id`로 `poi(id)`를
참조한다:

| 소스 | 컬럼 | ON DELETE | 결과 |
|---|---|---|---|
| `poi_drops` (004) | `poi_id` | CASCADE | 삭제 성공, 월드 드랍 기록 조용히 소실 |
| `user_poi_badge_earns` (053) | `poi_id` | CASCADE | 삭제 성공, **유저 획득 이력 조용히 소실** |
| `poi_blocks` (010, 어뷰징 정책) | `poi_id` | CASCADE | 삭제 성공, GPS 조작 차단 이력 소실 |
| `notifications` (096) | `poi_id` | CASCADE | 삭제 성공, 알림 기록 소실 |
| 미상 테이블 (011, `current_poi_id`) | `current_poi_id` | 미지정(NO ACTION) | **DELETE가 FK 위반으로 실패, raw Postgres 에러가 500으로 노출** |
| 미상 테이블 (002, `triggered_by_poi_id`) | `triggered_by_poi_id` | 미지정(NO ACTION) | 위와 동일 |

`badges` 테이블에서 `point_transactions.source_badge_id`가 겪었던 것과 같은 패턴이다
(NO ACTION FK가 있는지 모르고 있다가 500으로 터짐) — `badge-references.ts`를 만든 계기가 된
바로 그 사고(티켓 20260905_0034)가 POI에도 그대로 잠재해 있다.

**레시피 (`combination_recipes` 테이블)** — 마이그레이션 전수 검색(`recipe_id` 컬럼, `REFERENCES
combination_recipes` 전부) 결과 **`combination_recipes.id`를 참조하는 테이블이 없다.** 레시피는
`ingredient_badge_ids`·`result_badge_id`·`required_activity_badge_id`로 **배지를 참조하는
방향**이지, 반대로 레시피를 참조하는 것은 없다. 사용자가 "상대적으로 안전하다고 보고됐지만
재확인 필요"라고 한 부분 — **이번 조사로는 안전(하드 삭제 시 FK 위반도 CASCADE 소실도 없음)으로
확인됐다.** 다만 이 조사는 오케스트레이터가 마이그레이션 파일 grep으로만 확인한 것이므로,
구현 시 jam-developer가 실제 스키마(`information_schema` 또는 Supabase MCP)로 한 번 더
재검증하고 결론을 완료 기록에 남긴다. 안전이 재확인되면 레시피 쪽은 가드보다 **삭제 전 확인
UX(현재도 있음, `RecipeTable.tsx:237` 확인 다이얼로그)로 충분**할 수 있다 — 이 경우 가드
유틸은 만들되 "참조 없음" 경로만 타는 것도 정상이다.

## 상세 요구사항

### 서비스/코드베이스 관점

- `jam-web/src/lib/admin/badge-references.ts` 패턴을 참고해 POI·레시피용 참조 가드 유틸을
  만든다. 파일 분리는 구현자 재량(예: `poi-references.ts`, `recipe-references.ts`, 또는
  공용 헬퍼 확장) — 다만 `badge-references.ts`가 잡아둔 계약은 그대로 따른다:
  - `blockingTotal`(FK NO ACTION — 삭제가 실패하는 자리) / `cascadeTotal`(FK CASCADE — 삭제는
    성공하지만 유저 데이터가 조용히 사라지는 자리)을 분리 집계
  - 조회 실패 시 **fail-closed** (`error` 필드가 있으면 삭제 자체를 막는다 — 부분 카운트로
    "참조 0건"을 오판하지 않는다)
  - id 목록이 커질 수 있는 자리는 청크(`ID_CHUNK`) 처리
- `blockingTotal + cascadeTotal > 0`이면 DELETE를 막고 `409`로 참조 내역을 응답한다
  (`badges/[id]/route.ts` DELETE의 응답 형태를 그대로 따른다).
- 적용 대상은 **단건 DELETE 라우트 두 곳뿐**이다:
  - `src/app/api/admin/poi/[id]/route.ts`의 `DELETE`
  - `src/app/api/admin/recipes/[id]/route.ts`의 `DELETE`
  - 새 일괄삭제 API를 만들지 않는다 — 클라이언트가 이미 이 두 라우트를 순차 호출하는 구조를
    그대로 활용한다.
- 클라이언트(`PoiTable.tsx`·`RecipeTable.tsx`)의 `failCount` 방식 알림은 이미 "N개 삭제
  실패" 정도는 보여준다 — 이번 작업의 최소 기준은 **서버가 위험한 삭제를 막는 것**이다.
  실패 사유(참조 내역)까지 클라이언트에 노출할지는 구현자 판단에 맡기되, 최소한 서버 콘솔
  로그(`console.error`, `badges` DELETE 패턴 참고)는 남긴다.

## 구현 계획

1. 실제 스키마 재검증: `poi`·`combination_recipes`를 참조하는 모든 FK를 Supabase MCP 또는
   `information_schema.table_constraints`로 다시 확인 — 위 표의 011/002 미상 테이블명을
   구체적으로 특정한다.
2. 참조 가드 유틸 작성 (`badge-references.ts` 패턴: 소스 목록 상수 + `collect*References`
   함수 + `blockingTotal`/`cascadeTotal`/`error` 계약).
3. `poi/[id]/route.ts`·`recipes/[id]/route.ts`의 `DELETE`에 가드 적용, 409 응답.
4. 로컬 실렌더로 확인: 참조가 있는 POI/레시피를 하나씩 골라 단건 삭제 → 409 확인, 다중선택
   일괄삭제 → 일부만 막히고 나머지는 정상 삭제되는지 확인 (`ADMIN_EMAILS` 로컬 환경변수로

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

`jam-web/src/lib/admin/poi-references.ts`(POI)·`jam-web/src/lib/admin/recipe-references.ts`
(레시피)를 `badge-references.ts` 계약(`collect*References` → `blockingTotal`/`cascadeTotal`/
`total`/`error`, fail-closed, `ID_CHUNK` 청크 조회)에 맞춰 신규 작성하고, 두 단건 `DELETE`
라우트(`poi/[id]/route.ts`, `recipes/[id]/route.ts`)에 존재 확인 → 참조 카운트 조회
(fail-closed 시 500) → 참조 있으면 409 차단 → 통과 시 실제 삭제 순서로 가드를 적용했다.
클라이언트(`PoiTable.tsx`·`RecipeTable.tsx`)는 변경하지 않았다 — 이미 있는 `failCount` 알림이
서버 차단을 그대로 반영한다.

**실제 스키마 재검증 결과, 티켓 초안의 표 3곳이 부정확했다** (근거: `poi(id)` REFERENCES
전체 마이그레이션 grep + `src/types/database.generated.ts`의 Relationships 블록 대조):

- **011의 "미상 테이블"(`current_poi_id`)은 `wandering_mythic_state`였다.** 그런데 이
  테이블은 마이그레이션 `095_remove_wandering_mythic.sql`(티켓 20260824_017)에서 이미
  `DROP TABLE`로 제거됐다 — **더 이상 존재하지 않는다.** 참조 목록에서 제외했다.
- **002의 "미상 테이블"(`triggered_by_poi_id`)은 `user_activity_badges`였다.** ON DELETE
  미지정(NO ACTION)이 그대로 살아있어 `blocksDelete: true`로 반영했다.
- 티켓이 "notifications(096)"로 적은 CASCADE 참조는 **실제로는 같은 파일(096) 안의
  `poi_views` 테이블**이다 — `notifications` 테이블 자체에는 `poi_id` 컬럼이 없다. 정정
  반영했다.
- `user_poi_badge_earns`(053)는 마이그레이션 `103_rename_poi_badge_to_checkin.sql`(티켓
  20260826_004)에서 **`user_checkin_badge_earns`로 테이블명이 바뀌었다.** 새 이름으로
  반영했다(컬럼명 `poi_id`는 유지).
- **티켓에 없던 신규 발견: `custody_events.poi_id`**(마이그레이션 108, 아이템 소유권 이력).
  `ON DELETE SET NULL`이라 FK 위반으로 막히지도, 행이 CASCADE로 사라지지도 않지만, 이
  테이블은 "append-only 이력"으로 설계된 소유권 감사 기록이라 POI 삭제 시 "어느 지점
  근처였는지" 맥락이 조용히 사라진다. 가드 목적상 `cascades: true` 버킷에 포함해 차단
  대상으로 잡았다.

**레시피(`combination_recipes`)**: 마이그레이션 전체 grep(`recipe_id` 컬럼, `REFERENCES
combination_recipes` 패턴) + `database.generated.ts` Relationships 대조 둘 다 인바운드 참조
0건으로 재확인했다. `recipe-references.ts`는 소스 목록이 비어 있어 항상 "참조 없음" 경로만
탄다(티켓 구현 계획에서 명시적으로 허용한 경로) — 향후 인바운드 참조가 추가되면 그 시점에
소스를 채워 넣으면 된다.

**범위 밖에서 발견한 것(수정하지 않음, alerts 참고)**: `RecipeList.tsx`의 단건(행별) 삭제
버튼(`handleDelete`)은 `fetch` 응답의 `res.ok`를 확인하지 않는다 — 지금은 레시피 참조가
항상 0건이라 실제로 막히는 케이스가 없어 무증상이지만, 향후 레시피 참조 소스가 추가되면
이 경로는 409를 받아도 화면에 아무 피드백 없이 조용히 실패한다. `PoiForm.tsx`(POI 상세
페이지 단건 삭제)와 `PoiTable.tsx`/`RecipeTable.tsx`(양쪽 다 벌크 삭제)는 전부 `res.ok`를
확인해 에러를 표시한다.

### 주요 의사결정 / 핵심 메모
> 개발 과정에서 검토·결정된 사항, 선택하지 않은 대안과 그 이유.

- **`custody_events.poi_id`(ON DELETE SET NULL)를 어느 버킷에 넣을지**: `badge-references.ts`
  원본 계약은 `blocksDelete`(FK 위반)와 `cascades`(행 자체가 CASCADE로 사라짐) 두 종류만
  구분한다. SET NULL은 둘 다 아니다(FK 위반도 없고, 행도 살아남는다) — 그런데 이 테이블은
  "append-only 감사 이력"으로 설계돼 있어, poi_id가 조용히 null이 되면 "이 소유권 이벤트가
  어느 지점 근처였는지"를 다시는 알 수 없게 된다. 새 타입을 만들지 않고 기존 `cascades`
  버킷에 포함시켰다 — 계약을 단순하게 유지하면서도 "조용한 데이터 손실"이라는 가드의 원래
  목적에 더 부합한다고 판단했다.
- **레시피 참조 소스를 빈 배열로 둔 것**: 실측 결과 진짜로 인바운드 참조가 없다. 억지로
  더미 소스를 만들지 않고, 티켓이 명시적으로 허용한 "참조 없음 경로만 타는 것도 정상"을
  그대로 따랐다.
- **POI/레시피 DELETE에 존재 확인(404) 단계를 추가한 것**: 원래 코드엔 없었다. `badges`
  DELETE 참고 패턴을 그대로 따르면서 자연스럽게 포함됐다 — 존재하지 않는 id에 대해
  불필요한 참조 카운트 조회를 하지 않기 위함이고, 티켓이 명시적으로 지정한 참고 구현
  (`badges/[id]/route.ts` DELETE)의 일부다.

### 잔여 이슈
