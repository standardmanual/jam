# [Admin] 배지·미션 생성 화면에 드랍엔진 사전 시뮬레이션 추가

## 배경 / 문제 정의
> 왜 이 작업이 필요한가. 현재 상태와 기대 상태의 차이.

배지·미션의 `condition_json`은 저장 시점에 필드 "형태"만 정적으로 검사한다
(`findBlockingConditionKeys`, `findConditionShapeSaveError` — `@/lib/admin/badge-condition-guards.ts`).
실제 발급 가능 여부는 유저의 활동 이력이 쌓이고 배지엔진이 그 이력에 대해 조건을 평가할 때에만
드러나는데, 지금은 그 시점이 저장 이후로 미뤄져 있다.

이 간극 때문에 다음과 같은 사고가 반복됐다 — 전부 저장은 정상적으로 됐지만 실제 판정에서만
드러난 문제다.

- 티켓 `20260908_1438`(P0): 반복형 조건이 게이트·기간 필드와 결합되면 회차가 영원히 0에 고정.
  26개 계열, 49종 배지가 동시에 영향받음.
- 티켓 `20260908_1512`(P1): `running:R2` 발급 로직이 콘텐츠 스펙과 다르게 동작.
- 티켓 `20260906_1432`(P1): 조건을 충족했는데도 미발급인 상태를 발견할 수단이 없었음.

배지엔진에는 이미 단일 조건을 순수하게 판정하는 함수(`evaluateConditionDetailed`,
`jam-web/src/lib/badge-engine/index.ts`)가 있고, 어드민의 `badge-diagnosis`·`simulator`
API가 사후 진단 목적으로 같은 함수를 이미 재사용하고 있다. 새 판정 로직을 만들 필요 없이,
같은 함수를 **저장 전** 시점에 한 번 더 호출하기만 하면 이 간극을 메울 수 있다.

근거 PRD: [`Service Plan/Specs/PRD/AdminUI/CONDITION_PRECHECK_PRD.md`](../../Specs/PRD/AdminUI/CONDITION_PRECHECK_PRD.md)

## 상세 요구사항

### 서비스/코드베이스 관점
- 새 API 라우트(예: `/api/admin/badges/simulate-condition`)를 만들어, 폼에서 넘어온
  미저장 `condition_json`과 대상(기존 유저 또는 가상 활동)을 받아 `evaluateConditionDetailed`를
  호출하고 `pass/reason/actual/required`를 반환한다. DB에는 어떤 것도 기록하지 않는다(dry run 전용).
- 결과에서 다음 두 가지를 명확히 구분해서 반환한다.
  - 조건은 유효하지만 아직 미충족(정상적인 "조건 불충족")
  - 조건 자체가 구조적으로 막혀 있어 영원히 발급될 수 없음(`pending` 필드 사용, 반복형 필수
    짝필드 누락, 게이트 결합 미지원 조합 등 fail-closed 사유)
- 미션 쪽 판정 진입점이 배지엔진과 어떻게 다른지 먼저 확인한 뒤, 같은 패턴으로 연결 가능한지
  판단한다. 구조가 크게 다르면 미션은 후속 범위로 분리한다.

### UI/UX 관점 (해당 시)
- 배지 생성/수정 폼(`jam-web/src/app/admin/badges/BadgeForm.tsx`)에 "판정 시뮬레이션" 버튼을
  추가한다. 기존 저장 버튼과 별개이며 저장하지 않아도 언제든 실행할 수 있다.
- 버튼을 누르면 대상을 고르는 패널이 열린다: 기존 유저 검색 선택(그 유저의 실제 활동 이력으로
  판정) 또는 가상 활동 입력(기존 시뮬레이터의 GPX 업로드·수치 직접입력 폼 재사용).
- 결과 화면에 통과/실패/차단 여부, 실패 사유, 실제값 대 필요값, 반복형이라면 회차 진행 여부를
  보여준다. fail-closed로 차단된 경우는 별도 경고 스타일로 구분한다.

### 컨텐츠 관점 (해당 시)
- 해당 없음.

## 구현 계획
> 어떻게 구현할지. 접근 방법, 영향 범위, 주요 변경 포인트.

1. `evaluateConditionDetailed`를 저장되지 않은 임의의 `condition_json`에 대해 호출해도 부수효과가
   없는지 코드로 확인한다(가정 검증).
2. 1차 범위: 배지 생성/수정 화면 + 기존 유저 선택 방식 + fail-closed 사유 구분 표시.
   최근 사고 패턴(회차 0, 짝필드 누락)을 재현해서 화면에서 걸러지는지 검증하는 것을 완료 기준으로
   삼는다.
3. 2차 범위: 가상 활동 입력 연결, 미션 화면 동일 기능 적용.
4. 기존 정적 형태 검사(`findBlockingConditionKeys` 등)는 그대로 유지 — 이번 기능은 그 다음
   단계(실제 판정 결과 확인)를 보완하는 것이지 대체하는 것이 아니다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- 신규 API `POST /api/admin/badges/simulate-condition`: 폼에서 넘어온 미저장 `condition_json`과
  대상 `userId`를 받아, 배지엔진의 기존 순수 함수 `evaluateConditionDetailed`를 실제 발급 판정과
  동일한 순서(가입앵커 조회 → 활동이력 조회 → 조건 평가)로 그대로 호출한다. DB에는 아무것도
  쓰지 않는다.
- 판정 결과를 `kind: 'pass' | 'blocked' | 'unmet'` 3종으로 분류. `findBlockingConditionKeys`로
  필드 구조 자체의 차단(알 수 없는 키·`pending`·짝필드 누락)을 먼저 잡고, 그 외 활동값과 무관하게
  항상 같은 이유로 떨어지는 배지엔진의 고정 문구 5종(`STRUCTURAL_BLOCK_REASONS`)을 매칭해 "정상
  미충족"과 구분했다.
- `BadgeForm.tsx`에 "판정 시뮬레이션" 접이식 패널 추가: 기존 `/api/admin/users?q=` 검색으로 유저를
  선택해 실행하면 통과(초록)/미충족(황색)/구조적 차단(빨강) 3색으로 사유·실제값 대 필요값·대입
  활동 건수를 보여준다.
- 게이트(선행배지·2단교차) 판정은 범위에서 제외했다 — `evaluateConditionDetailed` 자체가 게이트를
  평가하지 않는 함수이므로 스펙("같은 함수를 저장 전에 한 번 더 호출") 그대로다. 게이트 결합
  배지는 이 시뮬레이션 결과가 게이트 통과 여부를 반영하지 않는다.
- 가상 활동 입력(시뮬레이터 GPX·수치 폼 재사용)과 미션 화면 적용은 2차 범위로 후속 티켓으로 분리.

### 주요 의사결정 / 핵심 메모
- 새 판정 엔진을 만들지 않고 기존 `evaluateConditionDetailed`를 그대로 재사용 — 시뮬레이션 결과와
  실제 프로덕션 판정이 서로 다른 로직으로 갈라져 어긋나는 위험을 원천 차단하기 위함(PRD 근거와 동일).
- 미션 화면 적용은 미채택 — 미션 5개 타입 중 4개(`distance`·`checkin`·`activity_count`·
  `item_collect`·`streak_days` 등)는 `checker.ts`의 완전히 별도 경로이며 boolean만 반환해 사유
  표시 자체가 불가능하다. `mission_type='engine_condition'`만 이미 `evaluateConditionDetailed`를
  위임 재사용하고 있어 실질적으로 이번 API를 그대로 쓸 수 있지만, UI 연결은 후속 범위로 미룬다.
- 가상 활동 입력은 미채택 — 기존 유저 이력을 대입하는 방식만으로 1차 목표(회차 0 고정·짝필드
  누락 같은 fail-closed 사고 재현·조기 발견)를 충분히 검증할 수 있어, `/admin/simulator`의 GPX·
  수치 입력 폼 재사용은 2차 범위로 분리했다.
