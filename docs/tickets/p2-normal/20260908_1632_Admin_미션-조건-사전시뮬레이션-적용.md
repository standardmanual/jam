# [Admin] 미션 화면(engine_condition 타입)에 조건 사전 시뮬레이션 적용

## 배경 / 문제 정의
> 왜 이 작업이 필요한가. 현재 상태와 기대 상태의 차이.

티켓 [20260908_1554](20260908_1554_Admin_배지미션-조건-사전시뮬레이션.md)로 배지 조건 저장 전
시뮬레이션을 구현하면서, 미션 화면 적용은 조사 후 범위에서 제외했다. 조사 결과는 다음과 같다.

- 미션 타입은 5종(`distance`·`checkin`·`activity_count`·`item_collect`·`streak_days`)과
  `engine_condition` 1종으로 나뉜다.
- 5종은 `checker.ts`의 완전히 별도 판정 경로이며 **boolean만 반환**해 사유 표시 자체가
  불가능하다 — 이번 기능(사유·실제값 대 필요값 표시)과 구조적으로 맞지 않는다.
- `mission_type='engine_condition'`만 배지엔진의 `evaluateConditionDetailed`를 **위임 재사용**
  하고 있어, 이미 만들어둔 `/api/admin/badges/simulate-condition` API를 그대로(또는 거의 그대로)
  쓸 수 있는 상태다.

즉 미션 5종 전체에 이 기능을 적용하는 것은 이번 범위에서도, 구조상으로도 맞지 않지만,
`engine_condition` 타입 하나만큼은 배지와 동일한 방식으로 저장 전 시뮬레이션을 붙일 수 있다.

근거: `Service Plan/Specs/PRD/AdminUI/CONDITION_PRECHECK_PRD.md` §8 2차 범위,
티켓 `20260908_1554` 완료 기록의 주요 의사결정·잔여 이슈.

## 상세 요구사항

### 서비스/코드베이스 관점
- 미션 생성/수정 폼에서 `mission_type='engine_condition'`을 선택했을 때만 시뮬레이션 버튼을
  노출한다(나머지 5종은 이번 범위에서 제외 — boolean-only 판정이라 사유 표시가 불가능하다는
  구조적 이유를 UI에도 반영해, 버튼 자체를 숨긴다).
- `/api/admin/badges/simulate-condition`을 미션 폼에서도 호출할 수 있도록 경로를 공유하거나,
  필요 시 `/api/admin/missions/simulate-condition`으로 얇게 감싼다 — 판정 로직 자체는 배지와
  동일하게 `evaluateConditionDetailed`를 그대로 쓴다(새 판정 로직 금지).

### UI/UX 관점 (해당 시)
- `jam-web/src/app/admin/missions/` 화면에 배지 화면과 동일한 "판정 시뮬레이션" 패널을
  붙인다(같은 컴포넌트를 재사용, `mission_type`이 `engine_condition`일 때만 표시).
- 결과 표시 방식(통과/미충족/구조적 차단 3색, 사유·실제값 대 필요값)도 배지 화면과 동일하게
  맞춘다 — 어드민이 배지와 미션에서 서로 다른 UI를 다시 학습하지 않도록 한다.

### 컨텐츠 관점 (해당 시)
- 해당 없음.

## 구현 계획
> 어떻게 구현할지. 접근 방법, 영향 범위, 주요 변경 포인트.

1. `BadgeForm.tsx`에 추가했던 시뮬레이션 패널을 공통 컴포넌트로 뽑아낼 수 있는지 먼저 확인한다
   (미션 폼과 배지 폼이 같은 패널을 재사용할 수 있으면 중복 구현을 피할 수 있다).
2. 미션 폼에 `mission_type` 분기로 패널을 조건부 렌더링한다.
3. API 경로를 배지와 공유할지, 별도로 얇게 감쌀지는 구현 시점에 `mission_json`/`badge_json`
   스키마 차이를 확인하고 결정한다.
4. `evaluateConditionDetailed`가 배지·미션 두 컨텍스트 모두에서 부수효과 없이 안전한지 재확인한다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- 판정 로직·API 로직을 배지·미션이 공유하도록 `src/lib/admin/conditionSimulation.ts`로 뽑았다.
  `simulateCondition(condition, userId, extraAllowedKeys?)` 하나가 유저 조회 → 구조적 차단 판정
  (`findBlockingConditionKeys`) → 가입 앵커·활동 이력 조회 → `evaluateConditionDetailed` 호출까지
  전부 맡는다. 배지 라우트(`/api/admin/badges/simulate-condition`, 티켓 20260908_1554)는 이 함수를
  부르는 얇은 래퍼로 리팩터링했고(동작 변화 없음), 신규 미션 라우트
  (`/api/admin/missions/simulate-condition`)도 같은 함수를 부른다.
- UI도 동일하게 공용화했다 — 배지 폼(`BadgeForm.tsx`)의 "판정 시뮬레이션" 패널(상태·검색·실행·
  결과 표시 전부)을 `src/components/admin/ConditionSimulationPanel.tsx`로 뽑아 `condition`·
  `apiPath` 두 prop만 받게 했다. 배지 폼은 이 컴포넌트로 교체했고, 미션 폼
  (`MissionList.tsx`)은 `mission_type === 'engine_condition'`일 때만 조건부로 붙였다(나머지
  5종은 boolean-only 판정이라 버튼 자체를 숨긴다 — 스펙 그대로).
- **미션 라우트는 배지 라우트와 완전히 동일하지 않다** — `findBlockingConditionKeys`(이미
  `extraAllowedKeys` 파라미터가 있었다, `checker.ts`가 쓰던 것과 같은 장치)에
  `MISSION_ONLY_CONDITION_KEYS`를 넘겨 미션 전용 어휘(`weekly_streak_min_count`·
  `monthly_streak`·`distinct_weekday_count`·`time_band_counts`·`distinct_months_required` 등)가
  "알 수 없는 필드"로 오탐되지 않게 열었다. 응답에 `missionOnlyKeysPresent`를 추가해, 조건에
  그 키가 있으면 패널이 "이 시뮬레이션이 그 부분을 평가하지 못해 실제 판정과 다를 수 있다"는
  고지를 보여준다.
- **구현 중 발견해 함께 고친 버그**: `evaluateConditionDetailed`도 내부에
  `findBlockingConditionKeys`를 다시 호출하는데(fail-closed 진입점), 기존
  `simulateCondition`(1554 원본 그대로 이관한 코드)은 자신이 만든 `blocking` 계산에만
  `extraAllowedKeys`를 넘기고 `evaluateConditionDetailed` 호출에는 넘기지 않고 있었다. 배지
  라우트는 이 옵션을 항상 `undefined`로 호출해 왔으므로 드러나지 않았지만, 미션 라우트가
  `extraAllowedKeys`를 실제로 쓰면서 "fieldBlocked=false인데 evalResult.reason은 여전히 '알 수
  없는 필드'"라는 모순된 조합이 나왔다(kind가 'unmet'인데 사유 문구는 차단 사유인 상태). 두
  호출에 같은 `extraAllowedKeys`를 넘기도록 고쳤다 — 아래 잔여 이슈 참고.

### 머지 시점 충돌 조정
이 티켓과 `20260908_1631`이 같은 origin/staging 시점(2fef116c)에서 독립 분기해 `BadgeForm.tsx`·
`simulate-condition/route.ts`를 각자 다르게 고치면서 자동 머지가 실패했다(양쪽 모두 게이트 리뷰
PASS를 받은 뒤 병합 단계에서 발견). jam-developer에게 별도 조정 작업을 맡겨 두 기능을 다음과 같이
합쳤다.

- `simulateCondition(condition, userId, extraAllowedKeys?)` → `simulateCondition(condition,
  target, extraAllowedKeys?)`로 시그니처 확장. `target`이 `userId`면 이 티켓이 원래 쓰던 유저
  경로, `virtualActivity`+`repeatCount`면 1631이 만든 가상 활동 경로 — 두 분기를 하나의 헬퍼가
  모두 처리한다.
- `ConditionSimulationPanel.tsx`가 1631의 "기존 유저로 시험"/"가상 활동으로 시험" 탭 UI를
  흡수해, 결과적으로 미션 화면(`engine_condition` 타입)에도 가상 활동 탭이 자동으로 붙었다 —
  의도치 않았지만 해로울 것 없는 부수 효과로 판단해 그대로 뒀다.
- 조정 후 conservative-reviewer가 diff를 다시 읽고 두 티켓 스펙(배지 두 경로, 미션 조건부 노출,
  배지/미션 어휘 격리, repeatCount 0 방지 등)을 모두 재검증해 PASS 판정했다.

### 주요 의사결정 / 핵심 메모
- 새 판정 로직을 만들지 않았다 — 배지·미션 두 라우트가 `simulateCondition` 하나(내부적으로
  `evaluateConditionDetailed` 그대로)를 공유한다. 스펙 요구("판정 로직은 새로 만들지 말고 기존
  evaluateConditionDetailed... 그대로 쓴다")를 그대로 따랐다.
- UI도 컴포넌트 하나로 공유했다(구현 계획 1번의 "공통 컴포넌트로 뽑아낼 수 있는지 먼저 확인" —
  가능했다). 배지·미션이 서로 다른 UI를 학습할 필요가 없다.
- API 경로는 공유하지 않고 얇게 분리했다(`/api/admin/badges/...` vs `/api/admin/missions/...`) —
  기존 `findBlockingConditionKeys`/`evaluateConditionDetailed`가 이미 갖고 있던
  `extraAllowedKeys` 장치를 미션 라우트에서만 켜야 해서, 두 라우트를 하나로 합치면 그 스위치를
  가리는 조건 분기가 라우트 안에 생긴다. 공유 헬퍼(`conditionSimulation.ts`)로 로직은 합치고
  라우트 얇은 래퍼만 둘로 남기는 편이 "판정 로직은 하나"라는 스펙 의도에 더 맞는다고 판단했다.

### 잔여 이슈
- **[WARN] 이 시뮬레이션은 `engine_condition` 미션의 미션 전용 어휘(주간/월간 연속·요일 분산·
  월별 문턱 등)를 평가하지 않는다.** 실제 판정 함수는 `evaluateEngineMissionCondition`
  (`@/lib/missions/engineCondition.ts`)인데, 이 함수는 위임 가능한 배지 어휘만
  `evaluateConditionDetailed`로 넘기고 미션 전용 어휘는 자체 로직(연속 기간 계산 등)으로 직접
  판정한다 — boolean만 반환하고 사유·실제값·필요값도 없다. 이번 티켓은 스펙대로
  `evaluateConditionDetailed`/배지 API를 "새 판정 로직 없이" 재사용하는 것이 목표였으므로, 그
  전제상 이 간극은 구조적으로 남는다. `missionOnlyKeysPresent` 고지로 완화했지만, 미션 전용
  어휘만으로 구성된(또는 그게 핵심인) `engine_condition` 미션은 이 패널이 "구조적으로
  차단됨"으로만 보여줄 뿐 실제 진행 상황(예: 지금 몇 주 연속인지)은 알려주지 못한다. 이
  어휘까지 시뮬레이션하려면 `evaluateEngineMissionCondition`을 detailed 버전으로 확장하는
  새 작업이 필요하다(범위 밖).
- 로컬 브라우저 수동 조작 검증은 못했다 — dev-login 테스트 계정(`dev-tester@jam.local`)이
  `is_admin=false`이고 `ADMIN_EMAILS` 환경변수도 로컬 `.env.local`에 없다. 어드민 접근이
  가능한 계정으로 staging 배포 후 확인이 필요하다.
- 게이트 리뷰에서 범위 밖 발견물로 지적된 "판정 시뮬레이션 패널의 통과 문구가 배지·미션 공용으로
  '발급 가능해요'로 고정돼 미션 컨텍스트에 맞지 않을 수 있음" 건은 후속 티켓
  [20260908_1700](../P3-낮음/20260908_1700_Admin_판정시뮬레이션-미션용어-발급→달성.md)으로
  분리했다.
