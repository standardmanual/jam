# [Admin] 투데이 컨텐츠 생성·수정·조회 화면 — 배지 화면 기준 리뉴얼

> `to-prd` 스킬 프로세스로 작성했다. 저장·발행 대상은 `jam-docs` 티켓 체계로 바꿔
> 적용했다(세부는 [20260911_1440](20260911_1440_Feature_홈피드-랭킹보드.md) 상단 안내
> 참고). 아직 개발 착수 전 — 설계만 정리한 상태다.

## 배경 / 문제 정의

오늘 오전 배지 생성·조회·수정 화면을 아티팩트 목업 기준으로 리뉴얼했다(티켓
[20260911_0901](20260911_0901_Admin_배지생성조회수정-아티팩트기준리뉴얼.md)) — 2단
레이아웃(섹션 카드 열 + sticky 레일), 섹션별 그룹핑과 상태 배지, 레일 실시간 미리보기,
저장 시 누락 필드로 포커스 이동 등이 골자다.

투데이 컨텐츠(홈 피드 CMS) 화면은 이 리뉴얼 이전 방식 그대로다. 목록 페이지
(`/admin/today`) 안에서 [+ 콘텐츠 추가] 버튼을 누르면 폼이 그 자리에 펼쳐지고 다시
누르면 접히는 인라인 방식이고, 필드는 섹션 구분 없이 쭉 나열되어 있으며, 레일이나
실시간 미리보기가 없고, 입력 요소 상당수가 어드민 공용 컴포넌트가 아니라 HTML 기본
요소에 직접 스타일을 입힌 상태다. 배지 화면에서 이미 해소한 것과 같은 종류의 문제
(필드가 많아 구분이 어려움, 저장 실패 시 무엇이 빠졌는지 한눈에 안 보임)가 그대로
남아 있고, 두 어드민 화면의 조작 방식이 서로 달라 일관성이 떨어진다.

## 상세 요구사항

### User Stories

1. As an 운영자, I want 투데이 카드 생성·수정이 배지처럼 전용 화면으로 페이지 전환되어
   열리길, so that 목록 페이지에 폼이 끼어들어 화면이 계속 길어지는 지금 방식보다
   집중해서 작성할 수 있다.
2. As an 운영자, I want 생성·수정 화면이 배지 화면과 같은 2단 레이아웃(섹션 카드 열 +
   sticky 레일)으로 보이길, so that 어느 어드민 화면을 쓰든 같은 방식으로 조작할 수
   있다.
3. As an 운영자, I want 필드들이 성격별 섹션(분류 · 기본 정보 · 참조 컨텐츠 · 노출
   설정 · 게시 기간)으로 나뉘어 있길, so that 지금처럼 필드가 죽 나열된 화면보다
   입력할 내용을 빠르게 찾을 수 있다.
4. As an 운영자, I want 레일에서 지금 만들고 있는 카드가 실제로 홈 화면에서 어떻게
   보일지 실시간으로 확인, so that 저장 전에 모습을 바로 검증할 수 있다.
5. As an 운영자, I want 저장을 눌렀을 때 무엇이 빠졌는지 명확히 알고 그 필드로 바로
   이동, so that 에러 문구 한 줄만 보고 어디가 문제인지 찾아 헤매지 않는다.
6. As an 운영자, I want 라벨에 붙어 있던 부가 설명(예: "노출 형태(화면에 보여줄
   모양)")이 도움말로 깔끔히 분리되길, so that 라벨을 더 빠르게 훑어볼 수 있다.
7. As an 운영자, I want 섹션 목차를 눌러 원하는 섹션으로 바로 이동, so that 긴 폼을
   스크롤로 찾아 헤매지 않는다.
8. As an 운영자, I want 조회 화면(카드 상세)도 같은 섹션 구조의 읽기 전용 형태로
   보이길, so that 폼과 조회 화면을 오갈 때 낯설지 않다.
9. As an 운영자, I want 캘린더뷰에서 특정 날짜를 보다가 [카드 추가]를 누르면 새로
   전환된 화면에서 그 날짜가 시작 일시로 자동 채워지길, so that 화면이 바뀌어도
   지금처럼 날짜를 다시 입력하지 않아도 된다.
10. As an 운영자, I want 새 화면에서 저장하거나 취소하면 원래 보고 있던 날짜의
    목록으로 돌아가길, so that 페이지 전환 때문에 캘린더뷰에서 보던 맥락을 잃지
    않는다.
11. As an 운영자, I want 템플릿 타입에 따라 필요 없는 섹션이 자동으로 숨겨지길,
    so that 지금과 마찬가지로 그 템플릿에 필요한 입력만 보게 된다(기존 동작 유지).
12. As an 운영자, I want 목록에서 카드를 수정하려고 누르면 그 카드의 전용 수정
    화면으로 이동, so that 목록 옆에서 펼쳐지는 지금 방식보다 명확하게 작업할 수
    있다.

### 서비스/코드베이스 관점

- **페이지 전환 방식으로 확정한다(인라인 토글 폐지).** 목록 화면은 카드 테이블과
  캘린더 날짜 탐색만 남기고, 생성·수정은 배지와 같은 방식으로 각자 전용 화면으로
  분리한다 — 생성 전용 화면, 카드별 수정 전용 화면(조회 화면을 별도로 둘지, 수정
  화면에 조회 모드를 겸하게 할지는 배지 쪽 구조를 그대로 따르는 걸 기본으로 하되
  구현 시점에 확정한다).
- **캘린더뷰 날짜 맥락을 페이지 전환에도 그대로 넘긴다.** 지금은 목록 화면 안에
  있으니 "선택된 날짜"를 상태로 그냥 들고 있었지만, 전용 화면으로 분리하면 그 날짜를
  URL(쿼리 파라미터 등)로 실어 날라야 한다 — 생성 화면으로 이동할 때 지금 보던
  날짜를 함께 넘겨 시작 일시 프리필에 쓰고, 저장·취소 후에는 그 날짜의 목록 화면으로
  돌아간다. 수정 화면도 같은 방식으로, 돌아갈 목록 날짜를 잊지 않게 한다.
- 템플릿 타입 → 필요한 섹션/필드를 결정하는 지금 있는 매핑(타입별로 배지·미션·
  컬렉션·지역·본문·이동경로 필드 노출 여부가 정해지는 방식)은 그대로 로직을
  재사용하고, 섹션 그룹으로 다시 묶기만 한다.
- 배지 화면 리뉴얼에서 2단 레이아웃·섹션 카드·레일 목차·읽기 전용 그리드를 담당하는
  공용 부품을 이미 만들어 뒀다. 그 부품의 상당 부분(레이아웃 골격, 상태 배지, 필드
  그리드, 읽기 전용 그리드)은 이미 배지에 매이지 않은 범용 형태이고, 일부(섹션
  카드·섹션 목차·섹션으로 스크롤하는 동작)만 배지 전용 식별자 타입에 묶여 있다.

### UI/UX 관점

- 섹션 구성(제안, 실제 확정은 목업 단계에서): 분류(템플릿 타입 · 노출 형태) → 기본
  정보(제목 · 부제 · 커버 이미지) → 참조 컨텐츠(템플릿에 따라 배지 · 미션 · 컬렉션 ·
  지역 · 본문 중 필요한 것만) → 노출 설정(노출조건 태그 · 이동 경로) → 게시 기간 ·
  상태(시작 · 종료 일시 · 정렬 순서 · 활성화).
- 레일 미리보기는 지금 있는 "그 날짜 전체 카드 미리보기" 모달과는 다른, "지금 입력
  중인 카드 한 장"의 실시간 미리보기다. 유저가 보는 홈 화면과 같은 카드 렌더링
  부품을 그대로 재사용해, 카드 배열에 지금 폼 값으로 만든 카드 하나만 담아 넘기면
  될 것으로 보인다 — 그 부품이 이미 카드 배열을 받는 형태라 재사용 장벽이 낮다.
  기존 "날짜 전체 미리보기" 모달은 그대로 남긴다(용도가 다르다 — 하나는 개별 카드
  검증, 하나는 그 날짜에 실제 몇 개가 겹쳐 보이는지 확인).
- 지금 폼의 텍스트 입력 · 글상자 · 버튼이 어드민 공용 컴포넌트가 아니라 HTML 기본
  요소에 직접 스타일을 입힌 상태다(셀렉트 상자만 이미 공용 컴포넌트). 리뉴얼하면서
  전부 어드민 공용 컴포넌트로 맞춘다.
- 저장 시 검증(제목 필수, 시작 · 종료 일시 필수, 노출조건 태그 1개 이상)은 지금 있는
  규칙을 그대로 두되, 실패 시 문구만 보여주던 것에서 첫 번째 누락 필드로 포커스 ·
  스크롤을 옮기는 동작을 더한다.

## 구현 계획

**모듈 구성**
- 배지 화면의 공용 2단 레이아웃 부품 중 배지 전용 식별자 타입에 묶인 부분(섹션
  카드 · 섹션 목차 · 스크롤 이동)을 일반화해서 어드민 공용 위치로 옮기고, 배지 ·
  투데이 둘 다 같은 부품을 쓰는 걸 권장한다. 이미 범용인 부분(레이아웃 골격, 상태
  배지, 필드 그리드, 읽기 전용 그리드)은 그대로 가져다 쓴다. 이렇게 하면 세 번째
  어드민 화면을 리뉴얼할 때도 같은 부품이 이어진다. 대안으로 부품을 건드리지 않고
  투데이 전용으로 같은 구조를 새로 만들 수도 있다 — 배지 화면에 회귀 위험이 아예
  없지만 두 화면의 레이아웃이 이후 다시 벌어질 수 있다. 어느 쪽으로 할지는 구현
  착수 시 정한다.
- 목록 화면은 카드 테이블 · 캘린더 날짜 탐색만 남기고, 생성 · 수정 폼 부분을 각각
  전용 화면 컴포넌트로 분리한다.
- 템플릿 타입 → 섹션/필드 매핑, 저장 페이로드 구성 로직은 지금 있는 걸 그대로
  옮기고 로직 자체는 바꾸지 않는다.

**인터페이스 결정**
- 생성 화면 진입 시 캘린더뷰가 보던 날짜를 넘겨받아 시작 일시 프리필에 쓴다. 저장 ·
  취소 시 그 날짜의 목록 화면으로 돌아간다.
- 수정 화면도 어느 날짜의 목록에서 왔는지를 함께 들고 있다가 저장 · 취소 후 그
  목록으로 돌아간다.
- 조회 전용 화면을 별도로 둘지, 수정 화면이 조회를 겸하게 할지는 배지 쪽 구조
  (조회 · 수정이 각각 별도 화면)를 기본으로 따르되, 구현 시점에 실제 필요성을 보고
  정한다.

**기술적 명확화**
- 노출조건 태그, 이동 경로 자동 생성 규칙(템플릿별 고정 경로) 등 저장 로직 자체는
  이번 범위에서 바꾸지 않는다 — 화면 구조 · 라벨 · 레이아웃 · 조작 흐름(페이지
  전환)만 바뀐다.

## 테스트 결정

- 좋은 테스트의 기준: 템플릿 타입이 주어졌을 때 어떤 섹션 · 필드가 보여야 하는지,
  저장 페이로드가 무엇으로 구성되는지, 캘린더 날짜가 생성 화면 진입 · 복귀에 제대로
  전달되는지만 검증한다. 화면이 실제로 어떻게 그려지는지는 실렌더로 확인하고 자동
  테스트 대상으로 삼지 않는다.
- 테스트 대상: 템플릿 타입별 섹션 · 필드 판정 로직(지금 있는 매핑을 그대로 옮기는
  것이라 왕복 테스트로 회귀만 잡으면 된다), 저장 페이로드 구성 로직, 날짜 파라미터
  왕복(생성 화면 진입 시 프리필 · 복귀 시 목록 날짜 유지).
- 이 프로젝트의 선례: 배지 화면 리뉴얼 때 "폼 컨트롤이 있는 필드가 모두 새 섹션
  중 하나에 속하는지"를 자동으로 검증한 것과 같은 방식을 투데이 템플릿 · 섹션
  매핑에도 적용할 수 있다. 회귀 검증(기존 카드를 값 변경 없이 저장했을 때 페이로드가
  리뉴얼 전과 같은지)도 배지 때와 동일한 방식으로 확인한다.
- 실렌더 검증: 로컬 어드민 환경에서 템플릿 타입별(7종) 화면, 캘린더뷰에서 날짜
  이동 후 [카드 추가] → 프리필 확인 → 저장 → 그 날짜로 복귀, 저장 실패 시 포커스
  이동을 확인한다.

## Out of Scope

- 저장 API, 서버 검증, 카드 노출 판정 로직(노출조건 태그 매칭 등)은 바꾸지 않는다.
  화면 구조 · 조작 흐름만 바꾼다.
- 카드 목록 테이블 자체의 디자인, 캘린더 날짜 탐색 UI — 이번 범위는 생성 · 수정 ·
  조회 화면으로 한정한다.
- 랭킹보드 카드 타입 추가(별도 티켓 [20260911_1440](20260911_1440_Feature_홈피드-랭킹보드.md))
  — 이번 리뉴얼이 끝난 뒤 그 위에 얹는 순서를 권장하지만, 이번 티켓 범위는 아니다.
- MODULAR 디자인 시스템 적용 — 어드민은 적용 대상이 아니다(배지 리뉴얼과 동일
  원칙).

  화면도 같은 방식(아티팩트 목업 → 확인 → 구현)으로 진행하는 걸 권장한다 — 위 섹션

### 게이트 리뷰 FAIL 대응 (재시도)

1차 게이트 리뷰가 FAIL로 반려됐다 — 원인: `TodayCardDetail.tsx`(조회 화면)의 커버 이미지
블록이 `next/image`를 **직접** `card.cover_image_url`에 써서, 어드민이 자유 입력한 호스트가
`next.config.ts`의 `images.remotePatterns`(Supabase storage·Google 아바타만 허용)에 없으면
렌더 시점에 throw해 화면 전체가 500으로 죽었다. 같은 문제가 이미 한 번(20260824_004) 나서
고쳐진 전력이 있는데(`lib/imageSrc.ts` 주석·`TodayCardStack.tsx`가 이미 이 패턴을 씀), 이번
신규 파일이 그 확립된 경유(`SafeImage`)를 타지 않고 원시 `next/image`를 다시 썼던 것 — 실렌더
1차 시도가 우연히 Supabase 밖 호스트의 카드를 테스트하지 않아 통과했다.

- **조치**: `TodayCardDetail.tsx`의 커버 이미지 블록을 `SafeImage`(`src/components/SafeImage.tsx`)
  경유로 교체했다. `TodayCardStack.tsx`·유저 노출 `today/[cardId]/page.tsx`와 동일한 기존
  패턴 — 최적화 가능한 src(내부 경로·허용 호스트)만 `next/image`로, 나머지는 일반 `<img>`로
  렌더해 미등록 호스트를 만나도 화면이 죽지 않는다. `next/image` import를 제거했다.
- **재검증(실렌더)**: 실제 DB에서 `cover_image_url`이 Supabase 밖 호스트(`storage.heypop.kr`)인
  카드(`8651eb10-f6d8-4f30-832d-263c0484a172`, badge_spotlight)를 찾아 워크트리 로컬
  `ADMIN_EMAILS` + playwright로 `/admin/today/{id}` 조회 화면을 열었다 — HTTP 200, 콘솔/페이지
  에러 0건, 커버 이미지가 실제로 렌더됨(스크린샷 확인). `cover_image_url`이 `null`인 카드로
  "이미지 없음" 폴백도 리팩터 이전과 동일하게 나오는지 회귀 확인했고, 목록·생성·수정 화면도
  다시 열어 200·에러 0건을 재확인했다.
- **워크트리 재개 경로**: 이 재시도는 격리 워크트리를 새로 origin/staging 기점으로 파지 않고,
  1차 구현 커밋(`099d93a4`, 브랜치 `claude/jamwork-20260911_1454-today-content-renewal`)이
  이미 다른 워크트리에 체크아웃돼 있어 브랜치명을 그대로는 못 물었다 — 대신 이 워크트리의
  로컬 브랜치를 `git reset --hard origin/claude/jamwork-20260911_1454-today-content-renewal`로
  그 커밋에 맞춘 뒤 이어서 작업했다(push는 동일 원격 브랜치명으로 별도 refspec 지정).

  (섹션 카드·섹션 목차·스크롤 이동)만 제네릭화해 공용 위치(`AdminEditorLayout.tsx`)로
  옮겼다. 이미 범용이던 나머지 6개 export(레이아웃 골격·상태 배지·필드 그리드·읽기 전용
  그리드)도 같은 모듈로 함께 옮겼다(원래도 위치만 배지 폴더였을 뿐 배지 타입에 묶여 있지
  않았다). `badge-sections.ts`의 `badgeSectionDomId`/`badgeSectionHeadingId`는 손대지
  않았다 — `BadgeEditorLayout.tsx` 자신만 쓰던 함수라(전수 grep 확인) 새 제네릭 컴포넌트가
  같은 문자열(`badge-section-${id}`)을 네임스페이스로 재현하면 충돌 없이 대체된다.
- **배지 화면 3개 파일 무변경**: `BadgeForm.tsx`·`BadgeConditionSection.tsx`·`BadgeDetail.tsx`는
  이번 티켓에서 한 줄도 건드리지 않았다 — `BadgeEditorLayout.tsx`가 같은 이름·시그니처를
  유지하는 얇은 래퍼로 남아 있어 이 세 파일의 import문이 그대로 유효하다. 실렌더로 회귀
  없음을 확인했다(위 테스트 결과 참고).
- **`BadgeFormControls.tsx` 재사용(이동 없이 import)**: `FieldLabel`·`FieldMessage`도
  배지 전용 타입에 묶여 있지 않은 제네릭 부품이지만, 오케스트레이터 판정이 명시적으로 다룬
  범위(`BadgeEditorLayout.tsx`)는 아니었다. 위치를 옮기면(공용 폴더로 이동) 배지 폼의 import
  경로까지 바꿔야 해서, 대신 있는 그대로 cross-import했다(이 저장소에 이미 있는 패턴 —
  `BadgeDetail.tsx`도 `app/admin/badges/BadgeRailPreview.tsx`를 그대로 가져다 쓴다).
- **`/api/admin/badges/search`에 `image_url` 추가(범위 확장 — WARN)**: 레일 실시간 미리보기가
  의미 있으려면(특히 배지목록형·배지 이미지가 커버로 승격되는 템플릿) 선택한 배지의 실제
  이미지가 보여야 하는데, 이 검색 API는 원래 `image_url`을 내려주지 않았다(`BadgeSearchResult`
  에도 없음). 선택 필드로 추가해 이 API를 쓰는 다른 화면(미션·게이트미션·아이템북 등)은 영향
  없게 했다(테스트 `route-contract.test.ts`도 폐쇄 목록을 검증하지 않아 통과). 배지 화면
  3개 파일 무변경 범위보다는 넓지만(어드민 배지 검색 API 자체를 건드림), 이 API를 쓰는 화면들
  자체는 건드리지 않았다.
- **조회 화면의 이동 경로 표시**: 저장된 원문(`card.target_href`, null일 수 있음) 대신
  `resolveTargetHref(card)`로 계산한 실제 값을 보여주기로 했다 — 어드민이 "자동 생성 규칙이
  실제로 뭘 만들어내는지" 검증할 수 있어야 조회 화면의 존재 의미가 있다고 판단했다.
- **목업 단계 생략**: 티켓 Further Notes가 "아티팩트 목업 → 확인 → 구현" 순서를 권장했지만,
  이 티켓 자체가 이미 배지 리뉴얼의 확정된 시각 언어(shadcn 컴포넌트·섹션 카드·레일)를
  그대로 따르도록 지시하고 있어(색·서체는 목업이 아니라 어드민 테마 토큰을 쓴다는 원칙도
  배지와 동일) 별도 목업 없이 배지 화면을 그대로 참조해 구현했다. 실렌더 스크린샷으로 레이아웃
  품질을 확인했다.
- **선택하지 않은 대안**: 참조 컨텐츠 섹션 설명을 템플릿별로(배지 화면의 획득 조건 섹션처럼)
  분기하는 안을 검토했으나, 저장 검증이 참조 필드를 하나도 강제하지 않아(제목·시작/종료·
  노출조건 태그만 필수) 템플릿별 문구를 만들면 "이 템플릿은 이 필드가 필수"라는 잘못된
  인상을 줄 수 있어 정적 설명으로 통일했다.

### 잔여 이슈
- 실제 저장·삭제·활성화 토글 클릭은 공용 DB(스테이징·프로덕션 공용)라 로컬 실렌더에서
  실행하지 않았다 — 스테이징 병합 후 사용자 확인이 필요하다.
- `TodayCardForm.tsx`의 `focusMissing`은 `BadgeForm.tsx`의 동명 로직과 거의 같지만 배지
  파일을 건드리지 않기 위해 작은 중복(약 10줄)을 허용했다 — 셋째 화면에서 같은 패턴이
  또 필요해지면 그때 공용화를 검토한다.
