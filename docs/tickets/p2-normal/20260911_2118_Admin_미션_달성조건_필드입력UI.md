# [Admin] 미션 달성 조건 입력 방식을 필드 UI로 전환

## 배경 / 문제 정의

어드민 미션 생성/수정 화면(`src/app/admin/missions/MissionForm.tsx`)의 달성 조건 입력란은
현재 `조건 JSON`이라는 라벨의 `textarea`에 raw JSON 문자열을 직접 입력하는 방식이다
(`form.condition_json`, 238~244행). 저장 시 `JSON.parse`로 파싱하고 실패하면 에러만
보여줄 뿐(140~146행), 어떤 키를 쓸 수 있는지·값의 형식이 무엇인지는 운영자가 직접
`MissionCondition` 타입 정의나 문서를 찾아봐야 알 수 있다.

반면 어드민 액티비티 배지 생성 화면(`src/app/admin/badges/BadgeConditionSection.tsx` +
`conditionRegistry.ts` + `conditionFormFields.ts`)은 조건 필드 카탈로그를 그룹별
아코디언으로 펼쳐두고, 운영자가 채울 필드만 값을 입력하면 `buildConditionJsonFromFields`가
`BadgeCondition` JSON으로 조립해주는 구조다. 여러 필드에 값을 채우면 AND로 결합된다는 점에서
사실상 "다중 조건"을 이미 지원하고 있다.

미션 조건 입력도 이와 같은 방식으로 바꿔, 운영자가 raw JSON 문법을 몰라도 조건 종류를
고르고 값을 입력하는 것만으로 다중 조건을 조합할 수 있게 한다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `MissionForm.tsx`의 `조건 JSON` textarea를, `MISSION_TYPES` 중 선택된 `mission_type`에
  맞는 조건 필드만 노출하는 필드 UI로 교체한다.
- 조건 필드 카탈로그는 `MissionCondition` 타입(`src/types/database.ts` 575~657행)의 키
  전체를 대상으로 하되, `mission_type`별로 실제 의미 있는 필드만 보이도록 그룹/필터링한다
  (`checker.ts`의 `calculateProgress`/`getTarget` switch, `condition-keys.ts`,
  `engineCondition.ts`가 타입별로 어떤 키를 쓰는지의 근거가 된다).
- `mission_type='engine_condition'`은 배지엔진 어휘(`BadgeCondition`, `conditionRegistry.ts`
  재사용 가능)와 미션 전용 확장 어휘(`weekly_streak_min_count`/`monthly_streak`/
  `streak_subset`/`distinct_weekday_count`/`distinct_months_required`/
  `time_band_counts` 등)가 공존하므로, 두 어휘를 한 화면에서 구분해 보여주되 값을 채운
  필드는 모두 AND로 결합해 하나의 JSON으로 조립한다.
- 배지 폼과 동일하게 react-hook-form 없이 `useState` 기반 필드 상태(`ConditionFormFields`
  패턴 참고)로 구현하고, 저장 시점에 최종 `MissionCondition` JSON을 조립한다.
- 기존 raw JSON 방식과의 호환: 이미 저장된 미션을 편집 화면에서 열었을 때, 저장된
  `condition_json`의 키들이 필드 UI에 올바르게 매핑되어 초기값으로 채워져야 한다
  (매핑 안 되는 미지 키가 있다면 손실 없이 보존하거나 최소한 사용자에게 알린다).
- `Service Plan/Specs/PRD/AdminUI/CONDITION_PRECHECK_PRD.md`가 `engine_condition` 타입에
  한해 조건 사전검증을 이미 적용해뒀다는 점을 확인하고, 이번 필드 UI와 충돌·중복이 없는지
  검토한다.

### UI/UX 관점 (해당 시)
- MODULAR 디자인 시스템 적용 대상 아님(어드민 화면, `/jam-work` 분기표상 MODULAR 제외).
  배지 폼과 톤을 맞추되 어드민 내 기존 shadcn/ui 컴포넌트로 구현한다.
- 다중 조건이 AND로 결합된다는 점을 운영자가 오인하지 않도록 화면에 명시한다(배지 폼의
  요약 칩·검증 패턴 참고 가능).

### 컨텐츠 관점 (해당 시)
- 해당 없음.

## 구현 계획

1. `MissionCondition` 타입의 키를 `mission_type`별로 그룹화한 필드 카탈로그를 정의한다
   (`conditionRegistry.ts`를 그대로 재사용할 수 있는 배지엔진 위임 키와, 미션 전용 키를
   구분).
2. `MissionForm.tsx`에서 raw textarea를 걷어내고, 선택된 `mission_type`에 따라 필드 카탈로그
   일부를 렌더링하는 하위 컴포넌트(가칭 `MissionConditionSection.tsx`)로 교체한다.
3. 필드 상태 → `MissionCondition` JSON 조립 함수를 작성하고, 기존 저장값 → 필드 상태
   역매핑(편집 진입 시 초기화) 로직도 구현한다.
4. `mission_type` 7종 각각에 대해 필드 UI로 조건을 만들고 실제 저장 → 재조회 시 JSON이
   기존 raw JSON 입력과 동일하게 만들어지는지 로컬 실렌더로 확인한다.

## 완료 기록

### 구현 내용 요약

배지 조건 빌더와 같은 원칙(레지스트리 → 폼 필드)으로 미션 조건 필드 빌더를 신설했다.
단순 7종 미션 타입(거리/체크인/횟수/아이템수집/연속일수/시간/획득고도)은 목표값 1개 +
선택적 종목 필터만 노출하고, `engine_condition` 타입은 배지엔진 위임 어휘 14종
(`conditionRegistry.ts`의 `form.read`/`form.write` 재사용) + 미션 전용 확장 어휘 9종
(주기 연속·부분집합·요일 수·달력 등)을 자유 조합하는 다중 조건(AND) 빌더로 구현했다.
`time_band_counts`만 전용 입력 UI가 없어 값이 있으면 원본 그대로 보존하고 안내 문구를
띄운다. 체크인 타입의 목표 POI 선택을 위해 `PoiSearchSelect` 컴포넌트를 신규 작성했고,
수정 화면 진입 시 `condition_json`의 `badge_id`(item_collect)·`poi_id`(checkin)를
서버에서 조회해 라벨로 미리 채운다.

### 주요 의사결정 / 핵심 메모

- 배지 조건 UI는 "필드 카탈로그 전체를 펼쳐두고 채울 것만 채우는" 방식이라, 미션 쪽도
  드롭다운 하나로 조건 종류를 고르는 방식 대신 같은 카탈로그형 UI로 통일했다. 사용자가
  요청한 "조건 선택과 값 입력" 방식의 실체는 이 카탈로그형 패턴이며, 배지 폼과의 일관성을
  우선했다.
- `MISSION_ENGINE_DELEGATED_KEYS`(클라이언트)는 `engineCondition.ts`의 `DELEGATED_KEYS`
  (서버 전용)를 거울 복제했다 — 클라이언트 폼이 서버 전용 모듈을 import할 수 없기 때문.
  신규 테스트가 두 목록의 일치를 대조하지만, 향후 `engineCondition.ts` 수정 시 이 파일도
  함께 봐야 한다.
- `checkMissionCondition`의 null 오류 문구, `gate-family-options-contract.test.ts` 사전
  실패 3건은 범위 밖으로 판단해 손대지 않고 각각 티켓 20260911_2137(P3)·20260911_2137
  (Infra, P2)로 분리했다.
