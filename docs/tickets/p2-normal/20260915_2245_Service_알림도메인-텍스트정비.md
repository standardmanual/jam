### 구현 내용 요약
- **화면(`NotificationsClient.tsx`, `notifications/page.tsx`) 및 공용 컴포넌트
  (`NotificationBell.tsx`) 감사**: 하드코딩된 사용자 노출 한글 텍스트 없음 — 이미 `d.notifications.*`
  딕셔너리(23개 이상 키, ①~⑧ 소식 유형 전부 커버)를 완전히 경유하고 있었다. 코드 변경 없음.
- **API route 2건에서 ADR 0001 위반 발견·수정**: `api/notifications/route.ts`,
  `api/notifications/seen/route.ts` 두 라우트가 인증 필요 에러('인증 필요')와 조회/읽음 처리
  실패 에러('소식을 불러오지 못했어요', '읽음 처리 실패')를 하드코딩하고 있었다. 딕셔너리로 교체:
  - `d.common.authRequired`(재사용, '인증이 필요해요') — 두 라우트 공통
  - `d.notifications.errorTitle`(기존 키 재사용, '소식을 불러오지 못했어요') — GET 조회 실패
  - `d.notifications.markSeenError`(신설, '읽음 처리에 실패했어요') — POST 읽음 처리 실패
  - 참고: 현재 클라이언트(`NotificationsClient.tsx`)는 이 두 응답의 `error` 필드를 화면에
    그대로 노출하지 않는다(GET 실패는 `setError(true)`로만 받아 `d.notifications.loadError`
    고정 문구를 보여주고, POST 실패는 `catch`로 무시). 서버 문구가 곧바로 화면에 뜨지는
    않지만, ADR 0001은 "서버가 완성된 문구까지 만든다"는 서버 쪽 규율이므로 응답 바디 자체의
    하드코딩을 그대로 두면 안 된다고 판단해 딕셔너리로 옮겼다 — 클라이언트 로직은 티켓 범위
    밖이라 변경하지 않았다.
- **lib 감사 — `src/lib/notifications/message.ts`**: 티켓에 적힌 "한글 리터럴 9건"을 재검사한
  결과, 실제로는 사용자 노출 문자열이 아니라 (1) 조사(josa) 치환용 문법 테이블
  `JOSA_MARKERS`/`DIGIT_HAS_BATCHIM`(예: `'을/를': ['을', '를']`)과 (2) 주석 안의 예시 문구였다.
  이 파일은 이미 전체가 `d`/`t(template, vars)` 딕셔너리 체계로 동작하며(§4행 헤더 주석에
  명시), 실제 하드코딩 조각은 없어 코드 변경 없음 — 초기 grep이 작은따옴표 조사 테이블을
  "리터럴 9건"으로 오탐한 것으로 보인다(미션 도메인 티켓의 `ranking/format.ts` 사례와 동일한
  패턴).
- **lib 감사 — `src/lib/notifications/batch/*.ts`(6개 파일)**: 전수 검색 결과 발견된 한글
  문자열은 전부 코드 주석(설계 근거 설명)이거나 내부 로그(`missions.ts`의
  `console.error('[notifications-batch] mission_rank_snapshots 저장 실패:', ...)` — 유저에게
  노출되지 않는 서버 로그)였다. 실제 소식 문구 생성은 모두 `message.ts`의 `d.notifications.*`
  템플릿을 통해서만 이뤄짐을 확인 — 코드 변경 없음.
- **`points/reasons.ts` 참조만 하고 수정하지 않음**: `message.ts`가 `userFacingReasonLabel()`을
  import해 쓰고 있으나, 이 파일은 포인트(12) 도메인 티켓 소유라 손대지 않았다(티켓 지시 준수).

### 주요 의사결정 / 핵심 메모
- **`d.common.authRequired` 재사용 시 문구가 '인증 필요'→'인증이 필요해요'로 바뀐다.** 이
  값은 API 응답 바디에만 담기고 현재 어떤 클라이언트 코드도 화면에 그대로 표시하지 않으므로
  (양쪽 다 fetch 실패 시 별도 고정 문구/무시 처리), 사용자에게 보이는 텍스트가 실제로
  달라지는 곳은 없다고 확인했다. 다른 도메인 티켓(미션·인벤토리 등)에서 이미 이 키를
  재사용해온 것과 동일한 처리다.
- **message.ts·batch/*.ts의 "한글 리터럴 9건" 추정치는 실측 결과 0건이었다.** 티켓에 적힌
  수치는 상위 스펙(20260915_2227)의 초기 정규식 grep 추정(User Story 16이 이미 "누락·오탐
  가능성"을 명시)에서 나온 것으로, 조사 치환 테이블(`{을/를}` 등)과 주석을 문자열 리터럴로
  오탐한 결과로 판단된다. 실제 코드 감사로 재확인했으며 화면·API·lib 전 구간에서 추가로
  발견된 하드코딩은 API route 2건뿐이었다.
- **클라이언트의 서버 에러 메시지 미노출은 이번 티켓 범위 밖으로 판단**: ADR 0001은 "서버가
  완성 문구를 만들고 클라이언트가 그대로 신뢰해 노출"하라는 규칙이다. 알림 도메인은 클라이언트가
  애초에 그 값을 읽지 않는 구조라 완전한 ADR 준수(클라이언트가 서버 메시지를 노출)에는 못
  미치지만, 이는 클라이언트 로직 변경(별도 스펙 판단 필요)이 필요한 사안이라 이 텍스트 정비
  티켓 범위에서는 건드리지 않았다 — 필요하면 별도 티켓으로 제안.

### 잔여 이슈
- `NotificationsClient.tsx`가 `/api/notifications`·`/api/notifications/seen` 응답의 `error`
  필드를 화면에 노출하지 않아, ADR 0001이 의도한 "서버 문구를 클라이언트가 그대로 신뢰해
  노출"이 알림 도메인에서는 완전히 실현되지 않는다(현재는 고정 문구/무시로 대체). 로직 변경이
  필요한 사안이라 이 티켓에서는 다루지 않았다.
 별도 태스크로 분리해 확인 중(칩으로 표시됨).
