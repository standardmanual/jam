## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
대상 화면(`ProfileClient.tsx`, `profile/edit/page.tsx`, `profile/page.tsx`)을 전수 검사한 결과
이미 `d.profile`/`d.profileEdit`/`d.tabs` 등 딕셔너리로 전량 편입돼 있어 신규 하드코딩 텍스트는
없었다. 실제 정비 대상은 API route 3개였다 — ADR 0001(서버-클라이언트 단일 진실 소스)을 따르지
않고 `'UNAUTHORIZED'`·`'DUPLICATE'`·`'INVALID_FORMAT'` 같은 기계용 코드 문자열만 반환했고,
클라이언트가 그 코드를 보고 자체 딕셔너리 문구로 재번역하던 구조였다.

- `api/profile/route.ts`(PATCH): username/display_name 검증·중복·저장 실패를 전부
  `d.onboarding.*`/`d.profileEdit.saveError`/`d.common.authRequired`로 완성된 문구를 직접
  반환하도록 변경.
- `api/profile/avatar/route.ts`(POST): 인증·파일형식·용량·업로드·DB갱신 실패를 전부
  `d.profileEdit.*`/`d.common.authRequired` 완성 문구로 반환하도록 변경.
- `api/username/check/route.ts`(GET): 형식오류·중복·사용가능 여부에 `message` 필드를 추가해
  완성된 문구를 함께 반환(기존 `reason: 'INVALID_FORMAT'`는 제거, `available` boolean은 유지해
  하위호환).
- `profile/edit/page.tsx`: 위 세 라우트 응답을 소비하던 자체 코드-매핑 로직(`json.error ===
  'DUPLICATE'` 등)을 제거하고 서버가 보낸 `message`/`error` 문구를 그대로 신뢰해 노출하도록 변경.
  단, 어느 UI 위치(인라인 필드 vs 하단 배너)에 표시할지의 **분기**는 여전히 `res.status`로
  클라이언트가 판단한다(ADR 0001은 "문구 중복 정의 금지"를 요구하는 것이지 상태분기 제거를
  요구하지 않는다).

### 주요 의사결정 / 핵심 메모
- **`d.profile.*`가 아니라 `d.onboarding.*`/`d.profileEdit.*`를 재사용한 이유**: 티켓 지시문은
  "API route가 `d.profile.*`를 직접 참조"라고 썼지만, 실제로 `/api/profile/route.ts`가 검증하는
  아이디 형식 오류·중복 문구는 `/api/username/check`·온보딩 화면의 클라이언트 사전 검증
  (`validateFormat`)과 **완전히 같은 규칙, 같은 문구**를 써야 한다(용어 일관성, §1.3). 이미
  `d.onboarding.errorEmpty` 등으로 확정된 문구를 두고 `d.profile` 네임스페이스에 같은 내용을
  복제하면 오히려 "동일 개념을 다른 곳에 두 번 정의"하는 안티패턴이 된다고 판단해, 기존
  네임스페이스를 그대로 import해 참조하는 쪽을 선택했다. 이 판단이 티켓 문구의 문자적 지시와
  다르므로 여기에 근거를 남긴다.
- **`/api/username/check`·`/api/profile/avatar`는 온보딩 화면과 공유하는 라우트**다. 이번
  티켓 범위는 프로필 도메인 화면(`ProfileClient.tsx`, `profile/edit/page.tsx`,
  `profile/page.tsx`)으로 한정되어 있어, 공유 라우트의 응답 스키마를 **추가(additive)** 방식으로만
  바꿨다(`available` 필드 유지 + `message` 필드 신설, `error` 필드는 코드 문자열 대신 완성 문구로
  교체하되 필드명은 유지). 이렇게 하면 온보딩 화면(`onboarding/page.tsx`, 이미 티켓 20260915_2246로
  종료됨)은 코드를 건드리지 않아도 계속 정상 동작한다 — 다만 온보딩 화면은 여전히 서버 메시지를
  쓰지 않고 자체 `d.onboarding.available`/`taken` 매핑을 유지하고 있어 ADR 0001 관점에서는
  이 티켓 범위 밖의 잔여 중복이 남는다(아래 alerts 참고).

### 잔여 이슈
- `onboarding/page.tsx`가 `/api/username/check`·`/api/profile/avatar` 응답의 `message`/`error`
  필드를 아직 활용하지 않고 자체 문구 매핑을 유지 중이다(동작에는 문제 없음, 문구도 동일).
  ADR 0001을 온보딩 화면까지 완전히 적용하려면 별도 후속 티켓이 필요하다.
