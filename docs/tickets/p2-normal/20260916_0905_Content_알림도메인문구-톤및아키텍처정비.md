## 배경 / 문제 정의

티켓 20260915_2245의 딕셔너리 이관 구조는 게이트 PASS했지만, 한국어 리뷰가 신설 문구
`markSeenError`의 내부 동작명 노출, `d.notifications.errorTitle` 키를 API 응답에 재사용한
것의 구조적 문제, 그리고 이 티켓과 무관하게 기존부터 있던 `loadError`/`errorBody`의
띄어쓰기 오류를 지적했다.

## 상세 요구사항 — `jam-web/src/lib/i18n/ko.ts`의 `d.notifications` 값 수정

### (a) `markSeenError` — 내부 동작명 노출
"읽음 처리에 실패했어요"의 "읽음 처리"는 `mark seen`을 직역한 내부 동작명이다. 같은 화면의
고정 어휘는 "소식"이므로 여기서만 갈라진다.
→ "읽음 표시를 저장하지 못했어요" (재시도 안내가 필요하면 "읽음 표시를 저장하지
못했어요. 잠시 후 다시 시도해 주세요")

### (b) `d.notifications.errorTitle` API 응답 재사용 — 구조 재검토
API route가 화면 제목용 키(`errorTitle`)를 그대로 서버 응답 `message`로 내려보내고 있다.
이 키는 원래 짝인 `errorBody`("연결 상태를 확인하고 다시 시도해주세요")와 합쳐져야 3단계가
완성되는데, 제목만 떼어 쓰면 [현상]만 남은 반쪽 문장이 된다. 또한 화면 제목과 API 응답
문구는 역할이 달라(전자는 UI 문구, 후자는 서버가 완성하는 에러 사유) 같은 키를 겸용하면
나중에 한쪽만 수정할 때 다른 쪽이 의도치 않게 바뀐다.
→ 서버 응답 전용 완성 문구를 별도 키로 신설: `d.notifications.fetchFailed`
("소식을 불러오지 못했어요. 잠시 후 다시 시도해 주세요"). 화면 제목 `errorTitle`/`errorBody`는
그대로 유지.

### (c) 기존 부채 — `loadError`/`errorBody`의 띄어쓰기(§3)
이번 신설 문구와 무관하게 기존부터 있던 `loadError`·`errorBody`가 "다시 시도해주세요"로
붙여 쓰고 있다 — §3(보조용언 띄어쓰기, 가이드 예시 "적어 주세요") 위반. "다시 시도해
주세요"로 함께 교정한다.

## 구현 계획
- `ko.ts`의 해당 키 값을 수정하고, (b)는 API route가 새 키(`fetchFailed`)를 참조하도록
  코드도 함께 고친다(순수 문구 교체를 넘는 작은 구조 변경).
- 완료 후 `/im-not-ai`로 재검사한다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- (a) `markSeenError`를 "읽음 처리에 실패했어요"(내부 동작명 노출) → "읽음 표시를 저장하지
  못했어요"로 교체.
- (b) 서버 응답 전용 완성 문구 `d.notifications.fetchFailed`("소식을 불러오지 못했어요.
  잠시 후 다시 시도해 주세요")를 신설하고, `GET /api/notifications`가 실패 시 이 키를
  참조하도록 수정. 화면 제목 `errorTitle`/`errorBody`는 그대로 유지(둘 다 여전히
  `NotificationsClient.tsx`에서만 참조됨을 grep으로 확인).
- (c) `loadError`·`errorBody`의 "다시 시도해주세요" 띄어쓰기는 확인 결과 이미 "다시
  시도해 주세요"로 올바르게 표기돼 있었다 — 다른 선행 티켓에서 함께 수정된 것으로 보여
  변경 사항 없음.
