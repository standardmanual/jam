# [Content] 배지 이미지 일괄 후처리 — 모서리 라운드(radius 12px) + 배경 투명화

## 배경 / 문제 정의
사용자가 특정 배지 이미지들의 모서리가 직각(정사각형)이라 지적하고, radius 12px로 둥글게
처리하고 배경을 투명하게 만들어달라고 요청했다.

오케스트레이터가 대상 이미지 샘플 2장을 직접 다운로드해 확인한 결과, 요청의 의미는
"인물/오브젝트만 오려내는 전체 배경 제거"가 아니라 **이미지 전체에 라운드 사각형(radius
12px) 알파 마스크를 씌워, 네 모서리의 잘려나가는 삼각형 영역만 투명하게 만드는 것**이다
(이미지 내부 콘텐츠·배경색은 그대로 유지, 모서리 바깥만 투명).

## 상세 요구사항

### 대상 범위 (DB 직접 조회로 확정, 오케스트레이터가 이미 조회 완료)
1. **컬렉션 "JAM! 레벨 0" 전체** — 19개 배지, 전부 `badges/shader-lab/{badge_id}.png`
   경로 (쉐이더 랩으로 생성된 이미지, 그라디언트 배경 완전 불투명 정사각형)
2. **트라이브 "아스팔트 레인저" 전체** — 10개 컬렉션(02-01~02-10), 90개 배지, 전부
   `badges/factions/{collectionSlug}/item-{collectionSlug}-{n}.png` 경로 (검정 배경
   완전 불투명 정사각형)
- 총 109개 배지. 정확한 목록(badge id·image_url)은 완료 기록에 SQL로 남긴다.

### 서비스/코드베이스 관점
- `jam-web/scripts/recraft/` 폴더 관례를 따라 신규 스크립트를 작성한다(예:
  `round-corners.js`). 기존 `remove-background-local.py`(PIL 기반 배경 제거)와는 목적이
  다르므로 그대로 재사용하지 말고, `sharp`(이미 `jam-web/package.json`에 설치돼 있음)로
  구현한다.
- 처리 로직: 각 이미지를 실제 크기(w×h)로 로드 → radius 12px의 라운드 사각형 SVG 마스크를
  같은 크기로 생성 → `composite`로 `dest-in` 블렌드 적용(마스크 바깥은 투명, 안쪽은 원본
  유지) → PNG(알파 채널 포함)로 저장.
- **이미 라운드+투명 처리된 이미지가 섞여 있을 가능성**을 배제하지 않는다 — 스크립트 실행
  전 각 이미지의 네 모서리 픽셀이 이미 투명(alpha=0)인지 검사해, 이미 처리된 이미지는
  건너뛰고 처리 대상만 추려서 로그로 남긴다(멱등성 확보, 중복 처리로 이미 둥근 모서리를
  또 깎아 화질 손상되는 것 방지).
- 업로드는 기존 `register-badge-images.js`와 같은 방식(Storage 버킷 `images`, 같은 경로에
  upsert, `?v={timestamp}` 캐시버스팅 쿼리스트링 추가)을 재사용하거나 그 로직을 참고해
  새 스크립트에 포함한다.
- `badges.image_url`을 새 캐시버스팅 URL로 UPDATE한다.
- 실행한 UPDATE문은 기존 레포 관례대로 `seed_배지이미지라운드처리_20260916.sql` 형태로
  저장해 커밋한다.

### UI/UX 관점 (해당 시)
- 해당 없음(이미지 에셋 자체 수정).

### 컨텐츠 관점 (해당 시)
- `item_books`(컬렉션)·`tribes`의 대표 이미지(`image_url`)는 이번 요청 범위에 포함되지
  않는다 — 사용자가 명시한 "배지 이미지"만 처리한다. 대표 이미지도 같은 처리가 필요하면
  별도 요청으로 진행한다.

## 구현 계획
1. 신규 스크립트(`round-corners.js`) 작성 — radius 12px 고정 상수, 대상 목록은 DB
   쿼리(위 대상 범위)로 직접 가져오거나, 이 티켓에 첨부된 목록을 JSON으로 하드코딩해 받는다.
2. 처리 전 각 이미지의 모서리 alpha 값을 검사해 "이미 처리됨" 여부를 판별하고 로그 출력.
3. 처리 대상만 라운드 마스크 적용 → Storage 재업로드(upsert) → `badges.image_url` UPDATE.
4. 처리 전/후 샘플 이미지(각 그룹에서 1장씩, 총 2장)를 사용자에게 보여주고 확인받는다 —
   전량 처리 전에 반드시 승인 게이트를 거친다(이미지 파이프라인 관례).
5. 승인 후 나머지 전량 처리.
6. SQL 로그 파일 커밋.

### 구현 내용 요약 (1단계 — 샘플 검증만 완료, 2단계 전량 처리는 승인 후 진행)
- `sharp` 기반 `round-corners.js`를 작성했다. `--sample`/`--full` 두 모드로 구분되며,
  이번 호출에서는 `--sample`만 실행했다.
  - `--sample`: 쉐이더랩 1장 + factions 1장을 다운로드 → 모서리 alpha 검사(멱등성) →
    radius 12px SVG 마스크를 `composite(dest-in)`로 적용 → 로컬 임시 폴더에만 저장.
    Storage 업로드·`badges.image_url` UPDATE는 전혀 수행하지 않는다.
  - `--full`: (이번 호출에서 미실행) `item_books.name = 'JAM! 레벨 0'` /
    `tribes.name = '아스팔트 레인저'`로 대상 109개를 DB에서 조회 → 동일한 멱등성 검사·마스크
    적용 → Storage `images` 버킷에 같은 경로로 upsert 재업로드 → `?v={timestamp}`
    캐시버스팅 URL로 `badges.image_url` UPDATE → `seed_배지이미지라운드처리_20260916.sql`
    저장. 다음 단계 승인 후 같은 스크립트를 `--full`로 재실행하면 된다.
- 멱등성 검사(`isAlreadyProcessed`)는 네 모서리 픽셀의 alpha가 모두 0인지 확인한다.
- 처리 결과 검증: 원본은 1920×1920/913×913 완전 불투명 정사각형이었고, 처리 후 이미지의
  네 모서리 alpha=0, 라운드 경계 안쪽 alpha=255를 코드로 직접 확인했다(육안 확인 병행).

### 2단계 — radius 조정·전량 처리 (오케스트레이터 직접 수행)

사용자가 샘플(JAM! 레벨 0 배지 1개)로 radius 12→24→48→72px를 순서대로 직접 확인하고
72px로 최종 확정했다. `round-corners.js`의 `RADIUS` 상수를 72로 변경해 review 브랜치에
커밋·push하고, staging에 머지한 뒤 메인 작업 트리(`.env.local` 심볼릭 링크 보유)에서
`node scripts/recraft/round-corners.js --full`을 실행했다.

- 대상 조회 쿼리(`item_books.name = 'JAM! 레벨 0'` OR `tribes.name = '아스팔트 레인저'`)가
  실제로 109개를 정확히 반환함을 확인(사전 직접 SQL 조회로 이미 실측했던 개수와 일치).
- 109개 전량 처리 완료 — Storage `images` 버킷 upsert 재업로드 + `badges.image_url`을
  `?v={timestamp}` 캐시버스팅 URL로 UPDATE.
- 실행 직후 DB를 재조회해 109개 전부 `image_url`에 `?v=` 쿼리스트링이 반영됐음을 확인.
- Storage에 실제 저장된 파일 1개(`factions/02-01/item-02-01-1.png`)를 재다운로드해 모서리
  픽셀 alpha=0임을 직접 확인(코드 반영뿐 아니라 실제 파일 반영까지 검증).
- SQL 로그 108줄(UPDATE문, 헤더 주석 1줄 포함 109줄) 저장 확인.

### 주요 의사결정 / 핵심 메모
- radius 값은 사용자가 실제 처리된 샘플을 눈으로 보고 12→24→48→72px 순서로 점진적으로
  올려가며 확정했다 — 애초 티켓 초안의 12px은 최종 값이 아니다.
- Supabase는 staging·프로덕션 공용 단일 DB([[project_supabase_shared_staging_prod]] 메모리
  참고)이므로, 이번 Storage 재업로드·DB UPDATE는 실행 즉시 프로덕션에도 반영됐다 — 별도
  `/jam-ship` 배포 없이도 이미지 자체는 바로 바뀐 상태다.

### 잔여 이슈
- `item_books`(컬렉션)·`tribes`의 대표 이미지는 이번 범위에 포함하지 않았다 — 필요하면
  별도 요청으로 진행.
