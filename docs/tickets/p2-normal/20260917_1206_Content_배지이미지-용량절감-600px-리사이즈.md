# [Content] 배지 이미지 전량 600px 리사이즈 — Storage 용량 절감

## 배경 / 문제 정의
사용자가 Supabase 프로젝트(`jam-prod`) 용량이 1GB를 넘겼다고 확인을 요청했다. 조사 결과
DB 자체는 30MB에 불과하고, Storage `images` 버킷(1,231MB)이 원인이었다. 그중
`badges/` 폴더가 1,193MB(전체의 97%)를 차지했고, 개별 파일 대부분이 1080×1080px 원본
PNG를 그대로 저장하고 있었다. 실제 서비스 화면에서 배지 이미지가 표시되는 최대 크기는
200×200px(배지 상세 히어로)로, 원본이 표시 크기 대비 5배 이상 큰 해상도였다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 최근 스마트폰 기준 DPR(기기 픽셀 비율) 3배를 고려해, 표시 최대 크기 200px의 3배인
  600px를 목표 해상도로 정했다.
- PNG 무손실 리사이즈만 사용해 알파 채널(투명도)을 100% 보존한다. JPEG 변환은
  알파 채널을 지원하지 않아 투명도가 손실되므로 사용하지 않는다.
- 이미 600px 이하인 파일은 건드리지 않는다(멱등성 확보, 스킵 처리).
- 파일 경로(파일명)는 변경하지 않고 같은 위치에 upsert 덮어쓰기하므로,
  `badges.image_url` 등 DB 컬럼 값 변경이 필요 없다.

### 컨텐츠 관점 (해당 시)
- 대상은 Storage `images` 버킷의 `badges/` 하위 전체(activity·tribes·factions·
  shader-lab·backgrounds·checkin·기타 루트 직속 파일 포함).
- `avatars`, `mission-images` 버킷은 이번 범위에 포함하지 않았다.

## 구현 계획
1. 샘플 6개(activity 폴더)를 직접 다운로드해 원본 해상도(1080×1080) 확인 및
   600px·270px 리사이즈 시뮬레이션으로 용량 절감률·투명도 보존 여부를 먼저 검증.
2. `jam-web/scripts/recraft/` 관례를 따라 신규 스크립트(`resize-badges-600.py`) 작성.
   Storage list API로 `badges/` 하위 전체 파일을 재귀 조회 → 다운로드 → 최대변 600px로
   비율 유지 리사이즈(정사각형이 아닌 파일도 안전하게 처리) → 원본을 로컬에 백업 →
   같은 경로에 upsert 재업로드.
3. `--dry-run` 모드로 전체 대상·예상 절감량을 먼저 확인한 뒤 사용자 승인을 받고 실행.
4. 실행 후 Storage 총 용량 재조회 및 샘플 파일 재다운로드로 해상도·투명도 검증.

## 완료 기록

### 구현 내용 요약
- `jam-web/scripts/recraft/resize-badges-600.py`를 작성했다. Python 표준 라이브러리
  + `curl` 서브프로세스(로컬 환경의 Python SSL 인증서 체인 문제를 우회하기 위해 urllib
  대신 curl 사용) + Pillow(PIL)로 구성.
  - Storage REST API(`/storage/v1/object/list/{bucket}`)를 재귀 호출해 `badges/` 하위
    전체 파일 목록을 얻는다.
  - 각 파일을 공개 URL로 다운로드 → 원본을 `/tmp/badge-resize-backup/`에 경로 그대로
    백업 → `max(width, height) > 600`인 경우에만 비율 유지 LANCZOS 리사이즈
    (PNG는 RGBA 유지, JPEG는 RGB) → `optimize=True` PNG 저장 → `service_role` 키로
    같은 경로에 `x-upsert: true` PUT 업로드.
  - `--dry-run` 옵션으로 실제 업로드 없이 대상·예상 용량만 미리 확인 가능.
- dry-run 결과: 처리 대상 1,222개, 스킵(이미 600px 이하) 50개, 실패 0개,
  예상 1,192.1MB → 350.9MB(29.4%, 절감 841.2MB). 사용자에게 보고 후 승인받아 실제 실행.
- 실제 실행 결과도 dry-run과 동일(처리 1,222개, 실패 0개). Storage 실측 재조회로
  `images` 버킷 총 용량이 **1,231MB → 389MB**로 감소한 것을 확인했다
  (`avatars`·`mission-images`는 변동 없음).
- 검증: 처리된 파일 1개(`badges/activity/298385ab-....png`)를 재다운로드해
  `PIL.Image`로 열어 크기 600×600, 모드 RGBA, 알파 채널 최솟값 0(완전 투명 픽셀 존재)을
  직접 확인. 사용자에게도 결과 파일을 전달해 육안 확인 가능하도록 했다.

### 주요 의사결정 / 핵심 메모
- 목표 해상도 600px는 임의값이 아니라, 코드 조사로 확인한 실제 표시 최대 크기
  200px(`BadgeHeroSection.tsx`)에 최신 스마트폰 DPR 3배를 곱해 산정했다. 그리드 카드
  (90px)·드랍 바텀시트(176px)는 모두 200px보다 작아 600px 원본 하나로 커버된다.
- "압축하면 투명도가 사라지는 것 아니냐"는 사용자 우려에 대해, 투명도 손실은 JPEG
  변환처럼 알파 채널을 지원하지 않는 포맷으로 바꿀 때 발생하는 것이며, 이번 작업은
  PNG→PNG 무손실 리사이즈만 사용해 알파 채널을 그대로 보존한다는 점을 먼저 설명하고
  실제 알파값 검증까지 거쳐 진행했다.
- Python 표준 `urllib`이 로컬 환경의 SSL 인증서 체인 문제(`CERTIFICATE_VERIFY_FAILED`)로
  동작하지 않아, 이미 정상 동작이 확인된 `curl` 서브프로세스 호출로 전환했다.
- 원본 백업은 되돌리기 안전망 목적으로 로컬 `/tmp/badge-resize-backup`(1.2GB, 1,222개
  전량)에 저장했다. `/tmp`라 시스템 재시작 시 사라질 수 있음을 사용자에게 안내했다.

### 잔여 이슈
- `/tmp/badge-resize-backup`의 원본 백업은 임시 보관 상태다. 문제없음이 최종 확인되면
  삭제하거나, 장기 보관이 필요하면 다른 위치로 옮겨야 한다.
- `avatars`, `mission-images` 버킷은 이번 범위에 포함하지 않았다(용량이 작아 우선순위
  낮음, 필요 시 별도 요청으로 진행).
