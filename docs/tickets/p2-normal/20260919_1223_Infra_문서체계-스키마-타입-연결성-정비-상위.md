# [Infra] 문서 체계 정비: type·frontmatter 스키마와 문서 간 연결성 (상위 티켓)

## 핵심 요약

- 요구사항: `jam`·`jam-doc` 전체 문서에 type과 frontmatter 스키마를 적용하고, 링크 무결성 검사와 역링크 색인으로 서로 다른 주제의 문서 사이 연결성을 높인다. 같은 방법론을 개인 지식 묶음에 이식할 수 있게 검사기와 규칙을 서비스 고유 내용과 분리한다.
- 구현 계획: ① 확정 사항 기록(스펙 초안 + 이 티켓) → ② 혜린 기획 검토와 하위 티켓 분해 → ③ 링크 검사기 → ④ 스키마 적용 → ⑤ 색인과 연결 지표 → ⑥ 규칙 문서 갱신 → ⑦ 키트 분리(개인 vault 생성 시점).
- 관련 파일: `docs/specs/DOCUMENT_SCHEMA.md`(신규, 초안), `.githooks/pre-commit`(링크 검사 연동), `docs/specs/UX_WRITING_GUIDELINE.md:60`(믹스 행 X 목록), `docs/adr/0001-server-error-message-single-source.md`(이동 대상), `.claude/skills/jam-docs/SKILL.md`, `CLAUDE.md`(문서 체계 절)

## 배경 / 문제 정의

측정 결과(임시 스크립트, 코드 블록 안 예시가 섞여 정확한 값은 아님):

- 문서 978건 중 티켓이 924건이며, 티켓 frontmatter는 923건이 갖췄다(`pre-commit`이 `status`를 강제).
- 티켓을 제외한 스펙·에이전트·컨텐츠·마케팅 문서는 거의 frontmatter가 없다. 가진 5건도 서비스 플랜 3건(`Title`·`modified`), 개인정보 처리방침(`title`·`status: published`·`last_updated`), `CONDITION_PRECHECK_PRD`(`status: implemented`)로 필드 이름과 값이 제각각이다.
- 내부 링크 697개 중 약 411개가 깨져 있다. 대부분 티켓이 옛 경로(`../P1-중요/`, `../Specs/PRD`)를 참조한다. 8월 27일과 9월 18일의 폴더 재편 때마다 상대경로 링크가 끊어졌다.
- 주제가 다른 문서(예: 트라이브 원천 설정과 캠페인)를 잇는 장치가 없어, 영향 검토와 에이전트의 관련 문서 탐색이 사람의 기억에 의존한다.

기대 상태: 문서마다 type과 한 줄 요약이 있고, 새로 깨지는 링크는 커밋에서 차단되며, 상위 문서를 바꿀 때 영향받는 문서를 역링크로 조회할 수 있다.

## 상세 요구사항

### 서비스/코드베이스 관점

- **검사기 엔진은 `jam`에 두고 JAM 고유 문자열을 넣지 않는다.** 묶음별 설정 파일(필수 필드, 열거값, 태그 어휘, 링크 강제 여부, 제외 폴더)을 읽어 동작한다. `jam`의 `pre-commit`은 `jam-doc`이 없는 환경에서도 돌아야 하므로 `jam-doc`에는 복사본을 둔다.
- 링크 검사는 새로 깨지는 링크만 차단하고 기존 깨진 링크는 기준선 목록으로 저장한다. 앵커는 검증하지 않는다.
- 검사기는 미지의 type·필드를 경고로 처리하고, 티켓 ID는 문자열로 취급한다.
- 색인 생성은 티켓을 제외한다.

### UI/UX 관점 (해당 시)
- 해당 없음.

### 컨텐츠 관점 (해당 시)

- 태그 어휘 v1(26개)은 `docs/specs/UX_WRITING_GUIDELINE.md` §1.3 고정 용어에서 뽑는다. 가이드라인 §1.3 믹스 행의 X 목록에 고정 용어 `믹스`가 들어 있어(`docs/specs/UX_WRITING_GUIDELINE.md:60`) 오탈자로 보이므로 `조합, 합성`으로 고친다.
- 문서 본문·`description`은 고정 용어를 쓰고 코드·DB 식별자와 파일명은 원문을 유지한다. 서비스 플랜과 활동 배지 문서에 남은 "달리기" 4건은 러닝으로 통일할지 4단계에서 정한다.

### 주요 의사결정 / 핵심 메모

확정한 결정(2026-09-19 기획 논의):

- **type 15개**: 파일당 type 방식(약 55개)에서 줄였다. 기준은 "작성·사용 방식이 다른가"이며 내용 구분은 tags가 맡는다. `adr`은 삭제하고 기존 문서는 `guideline`으로 분류해 `docs/specs/`로 옮긴다. `reference`는 실무에서 '자료'를 뜻하므로 `guideline`으로 이름을 바꿨고, `brand-guide`는 `guideline`에 합쳤다.
- **frontmatter**: 필수는 `type`과 `description`뿐이다. `title`과 수정일은 두지 않는다(첫 H1, `git log`).
- **연결**: 본문 링크 자동 수집, `basis`(하위 문서에만 기재), 개체 중심 태그, 고아 문서 지표.
- **개인 지식**: 별도 저장소로 분리하고 프로젝트 에이전트는 접근하지 않는다. 공유하는 것은 방법론(키트)뿐이다. 개인 지식에서 서비스로 가는 통로는 사람이 승격한 `insight` 카드 하나이며, 전달은 사람 또는 개인 쪽 도구가 하는 단방향 push다(프로젝트 에이전트가 개인 노트의 표시를 읽지 않는다).
- **태그 어휘**: 사업 영역(D2C·스폰서십·지자체·SNS연동·거래·클랜)은 제외했다. `획득`은 배지 획득, `체크인`과 `체크인배지`는 분리, 아이템북은 컬렉션, 조합은 믹스로 통일했고 종목에 `트레일러닝`을 추가했다.

선택하지 않은 대안:

- 파일 단위 세분 type과 예약 type: 실제로 만들지 않을 문서 종류가 많아 유지 비용만 늘어서 기각.
- OKF 스펙 전체 도입: 발표 3개월 차라 도구가 성숙하지 않아 `type` 필드와 `index.md` 관례만 차용. 깨진 링크 허용 철학은 채택하지 않았다(현재 상태 문서는 링크를 강제).
- 외부 프레임워크(LLM Wiki 계열 도구 등): 기존 훅·현황판·에이전트 체계와 이중 관리가 되어 기각.
- 개인 지식을 같은 저장소나 심볼릭 링크로 통합: 에이전트 접근 차단이 불가능하고 아이클라우드가 심볼릭 링크를 지우는 문제가 있어 기각.
- 에이전트의 개인 지식 직접 열람: 개인 노트에 사적 내용이 섞이므로 기각.
