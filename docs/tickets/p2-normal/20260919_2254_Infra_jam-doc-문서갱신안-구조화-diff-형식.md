# [Infra] jam-doc 문서 갱신안을 구조화된 diff 형식으로

> 발견 경위: 카즈하 역할(Workflow 개선점 발견)에 해당하는 관찰을 오케스트레이터가 세션 중
> 직접 포착했다. 티켓 20260919_1246(T2)·20260919_1249(T5)·20260919_1956 세 건이 모두
> "아현이 jam-doc 문서 갱신안을 자유 서술로 작성 → 오케스트레이터가 직접 jam-doc 파일에
> 옮겨 적고 커밋"을 반복했다(3회 반복 = 규칙표 기준 티켓화 조건 충족).

## 핵심 요약

- 요구사항: 아현이 `jam-doc` 문서 갱신안을 작성할 때, 자유 서술 대신 구조화된 unified diff
  (patch) 형식으로 출력하게 하고, 오케스트레이터는 그 patch를 `git apply`로 그대로 반영한다.
- 구현 계획: `jam-developer.md` 규칙 9(jam-doc read-only)의 "문서 갱신안" 서식을 diff 형식
  지침으로 바꾼다. 아현은 워크트리 안의 `jam-doc` 심볼릭 링크 원본은 건드리지 않고, 스크래치
  경로에 수정본을 써서 `diff -u <원본> <수정본>`으로 patch를 생성해 `summary`에 첨부한다.
  `jam-work/SKILL.md` 4단계(승인 후 처리)에 "문서 갱신안이 diff 형식이면 `git apply`로 적용,
  실패하면(컨텍스트 불일치 등) 기존처럼 읽고 수동 반영" 절차를 추가한다.
- 관련 파일: `.claude/agents/jam-developer.md:59-67`(규칙 9), `:110-124`(문서 갱신안 서식),
  `.claude/skills/jam-work/SKILL.md`(4단계 "승인 후 처리" 절)

## 배경 / 문제 정의

`jam-doc`은 격리 워크트리 안에서 메인 작업 폴더를 가리키는 심볼릭 링크라, 아현이 직접 쓰면
병렬 세션 충돌 위험이 있어 편집이 금지되어 있다(하드 규칙, 정당한 안전장치). 대신 아현은
"문서 경로 / 섹션 / 바꿀 내용 / 근거"를 자유 서술로 적고, 오케스트레이터가 그 서술을 읽고
직접 파일을 고쳐 커밋한다.

이 세션에서 이 흐름이 3번 반복됐다:
- T2(20260919_1246): jam-doc 3개 파일, 서술형 갱신안 → 오케스트레이터가 직접 커밋
- T5(20260919_1249): jam-doc 엔진 복사본 동기화, 서술형 → 오케스트레이터가 `cp`로 반영
- 20260919_1956: jam-doc 4개 파일·15곳 정정, 각 줄 번호·전후 텍스트를 서술로 나열 →
  오케스트레이터가 15곳을 하나씩 옮겨 적어야 함(수작업 옮김 과정에서 오탈자·누락 위험)

정정 위치가 늘어날수록(이번 15곳) 서술을 사람이 다시 파일에 옮기는 과정 자체가 오류 원인이
된다. `jam-doc`이 문서 저장소로 막 분리된 참이라(티켓 20260918_2105) 이런 패턴은 앞으로도
늘어날 것으로 예상된다.

병렬 세션 충돌 방지라는 근본 제약(아현이 jam-doc에 직접 쓰지 못함)은 유지한다 — 이번 개선은
"어떤 형식으로 오케스트레이터에게 넘기는가"만 바꾼다.

## 상세 요구사항

### 서비스/코드베이스 관점

- `jam-developer.md` 규칙 9: jam-doc 변경이 필요할 때 아현이 밟을 절차를 명시한다 —
  1) 워크트리 안 `jam-doc/<경로>`를 읽어 원본 확보, 2) 스크래치 파일(예:
  `/tmp/<ticket>-<slug>.new`)에 수정본을 쓴다, 3) `diff -u jam-doc/<경로> /tmp/<...>.new`로
  patch를 만든다, 4) `summary`의 "문서 갱신안" 칸에 `git apply`로 그대로 적용 가능한 patch
  블록(````diff` 펜스)을 넣는다. 파일이 여러 개면 파일마다 별도 patch 블록.
  - 새 파일 생성(예: T2의 `doc-check.config.json` 신규)은 `git diff --no-index /dev/null
    <새파일>` 형태로 patch를 만들 수 있음을 예시로 남긴다.
  - patch로 표현하기 어려운 경우(전체 재작성 등)는 기존처럼 자유 서술로 폴백해도 된다는
    예외를 남긴다 — 모든 경우를 patch로 강제하면 오히려 부자연스러운 사례가 생길 수 있다.
- `jam-work/SKILL.md` 4단계 "승인 후 처리": "아현의 문서 갱신안"을 반영하는 기존 문장 뒤에,
  diff 블록이 있으면 오케스트레이터가 `git -C jam-doc apply` 시도 → 성공하면 그대로 커밋,
  실패하면(컨텍스트 불일치 등) 기존처럼 diff 내용을 직접 읽고 수동 반영한다는 분기를 추가한다.
