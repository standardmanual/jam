# [Infra] 컨텐츠 시드 생성기를 jam 저장소로 이동

## 핵심 요약

- 요구사항: `jam-doc/planning/content/v5_*.py` 시드 생성기를 `jam` 저장소로 옮긴다. 정본
  JSON과 컨텐츠 문서는 `jam-doc`에 그대로 남긴다.
- 구현 계획: 스크립트를 `jam` 안의 적절한 위치(`scripts/` 또는 `jam-web/scripts/`)로 옮기고,
  정본 JSON을 읽는 경로를 새 위치 기준으로 고친다. `jam-developer.md` 규칙 9의 "Content seed
  generators" 문구도 새 경로로 갱신한다.
- 관련 파일:
  - `jam-doc/planning/content/v5_*.py` (이동 대상, 파일 목록은 착수 시 확인)
  - `.claude/agents/jam-developer.md` — 규칙 9 마지막 문단("Content seed generators ...")
  - `.claude/skills/jam-work/references/scheduled-jobs.md` — 예약 작업이 이 경로를 참조하는지 확인
- 상위 티켓: [20260920_0042 문서 저장소 경계 관찰 체계와 시드 생성기 정리](20260920_0042_Infra_문서저장소-경계-관찰체계와-시드생성기-정리.md)
- 경로: ③ 표준 (`infra` 유형이라 채원 없이 아현에서 민지로)

## 배경 / 문제 정의

시드 생성기는 `jam-doc`에 있으면서 결과물을 `jam-web/supabase/migrations/`에 쓴다. 두 저장소
사이에서 실제로 실행되며 경계를 가로지르는 유일한 경로다.

**이동의 근거를 정확히 적어 둔다.** 혜린의 기획서는 이동하면 "경계를 가로지르는 유일한 실행
경로가 사라진다"고 적었으나 이는 사실과 다르다. 생성기는 정본 JSON을 읽어 마이그레이션을
쓰는데, 정본 JSON은 `jam-doc`에 남기기로 했으므로 스크립트를 옮기면 경계가 사라지는 것이
아니라 **방향이 뒤집힐 뿐이다.** 지금은 `jam-doc`의 스크립트가 `jam`에 쓰고, 옮기면 `jam`의
스크립트가 `jam-doc`을 읽는다.

그럼에도 이동할 만한 이유는 따로 있다.

1. **실행 코드가 산출물과 같은 저장소에 놓인다.** 생성기가 만드는 것은 `jam`의 마이그레이션
   파일이므로, 생성기와 산출물이 한 커밋 안에서 함께 움직이는 편이 분리 기준과 정합한다.
2. **검증 대상 안으로 들어온다.** `jam`에 있으면 `scripts/verify.sh`와 게이트 리뷰의 범위에
   포함되지만, `jam-doc`에 있으면 어떤 자동 검사도 받지 않는다.
3. **읽기 관계는 이미 허용된 형태다.** 아현은 `jam-doc`을 읽을 수 있고 쓰지 못한다. 옮긴
   스크립트가 `jam-doc`의 JSON을 읽기만 하는 것은 그 권한 구조와 어긋나지 않는다.

이 이동은 티켓 20260919_1246·1249·1956에서 반복된 갱신안 우회 문제를 해결하지 않는다. 별개의
개선이며, 상위 티켓의 관찰 조건과도 독립적이다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 이동 위치는 착수 시 판단한다. 생성기가 `jam-web/supabase/migrations/`에만 쓰면
  `jam-web/scripts/`가, 저장소 전반의 도구 성격이면 루트 `scripts/`가 맞다.
- 정본 JSON 경로는 새 위치에서 `jam-doc/planning/content/`를 가리키도록 고친다. `jam-doc`이
  복제되지 않은 환경에서 실행하면 경로를 추측하지 말고 명확한 오류로 멈춰야 한다.
- 이동 전에 카즈하의 예약 작업과 리포트 스크립트가 옛 경로를 참조하는지 확인한다. 참조가 있으면
  같은 티켓에서 함께 고친다.
- `jam-developer.md` 규칙 9의 "Content seed generators" 문단을 새 경로 기준으로 다시 쓴다.

## 구현 계획

`jam-doc`의 파일을 지우는 쪽과 `jam`에 추가하는 쪽이 저장소가 달라 커밋이 둘로 갈린다. 두 커밋
메시지에 이 티켓 번호를 모두 적는다. 아현은 `jam-doc` 쪽을 직접 지울 수 없으므로, 삭제는
갱신안으로 넘기고 오케스트레이터가 처리한다.

## 완료 조건

- 새 위치에서 생성기를 실행했을 때 이동 전과 **동일한 마이그레이션 파일**이 나온다 (생성 결과를
  비교해 차이가 없음을 확인한다).
- `jam-doc/planning/content/`에 실행 스크립트(`*.py`)가 남아 있지 않다.
- `scripts/verify.sh`가 통과한다.
- `jam-developer.md` 규칙 9의 경로 안내가 새 위치와 일치한다.
- 카즈하의 예약 작업·리포트 스크립트에 옛 경로 참조가 남아 있지 않다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

**착수 조사 결과 기각했다. 이동하지 않는다.**

착수 전 조사에서 세 시드 생성기가 파일 이동을 근본적으로 막는 구조로 얽혀 있음을 확인했다.

1. **`exec` 사슬.** `v5_gate_build.py`는 `v5_seed_build.py`의 소스 코드 앞부분을
   `os.path.join(HERE, 'v5_seed_build.py')`로 열어 `exec(compile(...))`으로 직접 실행해
   `FAMS`·`CODE_PREFIX` 등을 재사용한다. `v5_mission_seed_build.py`도 같은 방식으로
   `v5_gate_build.py`의 소스를 `exec`한다. 셋 다 `HERE`(자기 파일 기준 상대경로)로 서로를
   찾으므로, 하나만 옮기면 즉시 깨지고 셋 다 옮겨도 상대경로를 전부 다시 짜야 한다.
2. **`v5_gate_build.py`가 `jam-doc` 자신에게도 쓴다.** 코드:
   ```python
   OUT_SQL = os.path.join(REPO, 'jam-web', 'supabase', 'migrations', 'seed_v5_gate_conditions.sql')
   OUT_MAP = os.path.join(HERE, 'v5_gate_mapping.json')  # jam-doc 자기 자신
   ```
   즉 티켓 원문(27~30행)이 "경계를 가로지르는 유일한 실행 경로"라고 적은 서술과 달리,
   가로지르는 방향이 이미 `jam-doc → jam-web`인데, 스크립트를 `jam`으로 옮기면
   `jam → jam-doc`(읽기 + 이 파일에 한해 쓰기)이 **추가로** 생긴다. 경계가 사라지는 게
   아니라 늘어난다.

이동해서 얻는 이득(검증 대상 편입, `verify.sh` 범위 포함)보다, 이동해서 새로 생기는 비용
(exec 사슬의 상대경로 전면 재작업, `jam`의 스크립트가 `jam-doc`에 쓰는 새로운 예외 규칙 신설,
아현의 규칙 9 "jam-doc 쓰기 금지"와의 정합성 재검토)이 크다고 판단해 착수하지 않고 기각했다.

이 판단은 상위 티켓 20260920_0042의 결정("저장소 재구조화를 지금 하지 않는다")을 다른
각도에서 한 번 더 뒷받침한다 — 컨텐츠 문서뿐 아니라 그 생성 파이프라인도 저장소 경계와
무관하게 본질적으로 양쪽을 오가는 구조라는 뜻이다. 상위 티켓에 이 근거를 옮겨 적었다.

혜린의 기획서(2단계)가 이 티켓의 이동 근거로 제시한 "경계를 가로지르는 유일한 실행 경로가
