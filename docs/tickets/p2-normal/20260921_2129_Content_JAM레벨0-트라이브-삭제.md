# [Content] 트라이브 "JAM! 레벨 0"과 남은 배지 6건 삭제

## 핵심 요약

- 요구사항: 예외 트라이브 "JAM! 레벨 0"과, 트라이브 삭제 후 남은 배지 6건을 DB에서 삭제하고 문서를 정리한다.
- 구현 계획: 삭제 SQL을 파일로 남기고 실행한다(트라이브 → 남은 배지 순서). `TRIBES.md`에서 해당 트라이브 절을 걷어낸다.
- 관련 파일: `jam-web/supabase/migrations/seed_delete_jam_level0_tribe.sql`,
  `jam-web/supabase/migrations/seed_delete_jam_level0_leftover_badges.sql`,
  `jam-doc/planning/content/TRIBES.md`, `docs/specs/INDEX.md`(자동 생성)

## 배경 / 문제 정의

사용자가 처음에는 "레벨 0 컬렉션과 그 컬렉션의 배지를 완전 삭제"하도록 요청했고, 이어서
"트라이브를 삭제해"라고 범위를 좁혀 지시했다. 티켓 20260911_2119에는 트라이브 1건·컬렉션 1건·
배지 18건이 등록된 것으로 기록돼 있으나, 삭제 시점의 DB 상태는 달랐다.

| 항목 | 티켓 기록 | 삭제 시점의 DB |
|---|---|---|
| 트라이브 "JAM! 레벨 0" | 1건 | 1건 (`187a57e5-4b7c-4eef-934a-78804cb31582`) |
| 컬렉션 "JAM! 레벨 0" | 1건 | 0건 (이름·소속 트라이브 어느 쪽으로 찾아도 없음) |
| 배지 | 18건 | 6건 (희귀 4·에픽 2), 전부 `item_book_id`가 NULL |

트라이브를 참조하는 유저·드랍 상태·인접 관계는 0건이었다.

## 상세 요구사항

### 서비스/코드베이스 관점

- `public.tribes`에서 "JAM! 레벨 0" 1건을 삭제한다. `jam-web/src`에는 이 이름을 쓰는 코드가 없다.
- `badges.tribe_id`는 `ON DELETE SET NULL`이므로 트라이브를 지우면 남은 배지 6건의 `tribe_id`가 NULL이 된다.
- 사용자가 이어서 남은 배지 6건도 삭제하도록 지시했다. 이 배지를 참조하는 `inventory_items` 6건은
  `inventory_items_badge_id_fkey`에 ON DELETE 동작이 없어 먼저 지워야 하고, 여기에 연쇄되는
  `custody_events` 10건도 함께 삭제된다.

### 컨텐츠 관점

- `TRIBES.md`에서 예외 트라이브 11번 절, 표의 11번 행, 예외 관련 총계·설명, 데이터 소스 행을 제거한다.

## 구현 계획

1. 롤백 정보를 담은 SQL 파일을 저장한다.
2. 사용자 지시를 승인으로 보고 `jam-prod`에서 직접 실행한 뒤 검증 쿼리로 확인한다.
3. 남은 배지 6건은 삭제 전에 참조 관계를 다시 조회하고, 복원용 백업 SQL을 만든 뒤 삭제한다.
4. `TRIBES.md`를 고치고 `docs/specs/INDEX.md`를 재생성한다.

## 완료 조건

- `SELECT count(*) FROM public.tribes WHERE name = 'JAM! 레벨 0'`이 0이다.
- `SELECT count(*) FROM public.tribes`가 10이다.
- 남은 배지 6건과 그 보유 기록(`inventory_items` 6건)이 모두 삭제되어 조회되지 않는다.
- `TRIBES.md`에 "JAM! 레벨 0" 언급이 남아 있지 않다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

`jam-prod`에서 `tribes`의 "JAM! 레벨 0" 1건을 삭제했다. 삭제 후 검증 쿼리 결과는 다음과 같다.

- 이름이 "JAM! 레벨 0"인 트라이브: 0건
- 전체 트라이브: 10건
- 남은 배지 6건: 트라이브 삭제 직후에는 행이 그대로였고 `tribe_id`만 NULL로 바뀌었다

이어서 사용자 지시로 남은 배지 6건을 삭제했다. 삭제 전에 `inventory_items`가 참조하는 `trades`·
`custody_events`·슬롯·POI 등을 조회해 거래 연결이 0건임을 확인했다. 한 문장(CTE)으로 실행해
`inventory_items` 6건과 `badges` 6건을 지웠고, `custody_events` 10건은 연쇄 삭제됐다. 삭제 후
배지·보유 기록·이력이 모두 0건인 것을 검증했다.

`TRIBES.md`에서 예외 트라이브 관련 문구(표 11번 행, 총계 보조 줄, 안내 인용문, 11번 절,
데이터 소스 행)를 제거하고 `docs/specs/INDEX.md`를 재생성했다.

### 주요 의사결정 / 핵심 메모

- 사용자가 처음에는 컬렉션·배지 삭제를 요청했다가 "트라이브를 삭제해"로 범위를 좁혔고, 트라이브 삭제
  후에 "남은 배지 6건도 삭제해"라고 다시 지시했다. 그래서 두 단계로 나눠 실행했다.
- 남은 배지 6건의 보유 기록 6건은 모두 2026-09-14 관리자 마이그레이션(`admin_migration_20260914_1945`)이
  `destroyed_at`을 채운 파기 기록이었다. 티켓 20260911_2119의 18건 중 나머지 12건과 컬렉션도 이때
  정리됐을 가능성이 있으나, 그 마이그레이션은 확인하지 않았다.
- 복원용 백업 SQL은 `custody_events`에 유저명이 들어 있어 저장소에 넣지 않았다. 실행 세션의 임시
  폴더에만 있었고 세션이 끝나면 사라진다.

### 잔여 이슈
- 삭제한 배지의 이미지 파일이 스토리지 `images/badges/shader-lab/<배지 id>.png`에 남아 있다.
  파일 삭제는 SQL 삭제와 별개이므로 정리 여부를 사용자가 정해야 한다.
- 티켓 20260911_2119 기록의 18건 중 12건이 언제 어떻게 사라졌는지는 확인하지 못했다.
