## 2. 맞는 것 (그대로 채택)

- **진단**: 만드는 쪽(아현)과 검사하는 쪽(민지)의 분리, 훅으로 막은 것만 뚫리지 않았다는 관찰, "큐는 있는데 소비자가 사람"이라는 빈칸. 전부 사실과 맞는다.
- **선별 4기준**(범위가 닫힘 · 검증이 기계적 · 되물을 일 없음 · 되돌릴 수 있음): 타당하다. 기준 1은 아현의 `plan_only` 임계(파일 5개·100줄)로 수치화하면 판정이 기계적이 된다. 무인 실행에서 아현이 `plan_only`를 반환하면 그 밤은 버려진다.
- **읽기 전용 2주 → 쓰기**: 순서가 옳다. 오늘 사고가 근거를 더한다.
- **2회 연속 FAIL이면 적격 회수**: `/jam-work` 3.1절과 같은 규칙이다.
- **카즈하 모드 ③**: 새 에이전트를 만들지 않는 판단에 동의한다. 단 카즈하는 세션 안에서 실행된 기록이 0회이고 클라우드 루틴에서만 돌아왔다(2207 §2.1). 첫 2주는 판정 근거를 티켓당 한 줄 이상 남기게 하고 동의율을 잰다.
- **워크트리·순차 머지·오염 검사**: 맞다. 워크트리는 인덱스가 분리돼 `git add -A` 충돌은 없다(메모리의 사례들은 메인 트리를 공유했을 때 일이다).

## 3. 고칠 것

**① 무인 권한표와 충돌한다 (원칙 문제).** `scheduled-jobs.md` §4-3과 `team-operations.md` §6은 무인 실행에 "코드 수정"을 금지하고, 머지·배포 예외는 주간 배포 승인 루틴 하나뿐이라고 못 박았다. 2단계(코드 수정·리뷰 브랜치 push)는 이 원칙의 두 번째 예외다. 티켓 20260918_1650이 그랬듯 **사용자 명시 승인으로 예외를 신설하고 두 문서를 같은 커밋에서 고쳐야** 한다. 1단계(리포트 저장·커밋, Slack 요약)는 허용 열에 그대로 들어맞아 승인이 필요 없다.

**② 실행 장소가 정해지지 않았다.** 제안은 클라우드 루틴처럼 시각(06:00·03:00)을 정하면서, 워크트리 동시 한도(로컬 개념)를 말한다.

| | 클라우드 루틴 | 로컬(이 PC) |
|---|---|---|
| 장점 | PC가 꺼져 있어도 돈다. 실행마다 새 클론이라 공용 트리·설정 부작용이 없다 | node_modules·캐시가 있어 verify가 78초로 끝난다 |
| 제약 | shallow clone(빈틈 ④), `npm install`이 매번 필요(수 분, `jam-ops` 환경의 npm 레지스트리 접근 허용 여부 미확인), 워크트리 한도는 무의미 | PC 상시 가동 필요. 앱 스케줄러(등록 0건)나 살아 있는 세션 필요. 하네스 훅 경로 재기록·GIT_DIR 오염 같은 공용 `.git` 부작용을 공유 |
| 추천 | **1단계 선별** (읽기 전용, 저렴) | **2단계 야간 소화**는 PC를 밤새 켜 둘 수 있을 때만. 아니면 클라우드로 가되 npm 접근을 먼저 확인 |

**③ 비용 상한이 없다.** 09-18 이후 티켓당 75,134~190,039토큰(2207 §2.5). 3건/밤이면 30만~50만 토큰/밤, 월 1천만 토큰대다. 오늘 기준 주간 요금제 사용률이 42%라 여유가 있지만 상한 없이 시작하면 안 된다. 선별도 매일 26건 본문을 읽으면 회당 수만 토큰이다.
- 선별은 **증분**으로: 전날 이후 생성·수정된 티켓만 읽고, 판정을 frontmatter에 캐시한다. 조용한 날은 거의 0.
- 야간은 **1건**부터. 월 토큰 예산과 정지선을 루틴 프롬프트에 명시.
- 루프 안 **자동 재시도 금지**(`/jam-work`의 임의 재시도 금지 규칙과 동일). FAIL이면 브랜치와 사유만 남긴다.

**④ 검증 도장이 먼저다.** 2단계의 "verify.sh 통과 + 민지 PASS"는 루프 자신의 주장이다. 민지는 [주의] 알림이 있으면 검사를 다시 돌리고(최근 59건 중 22건), 우회 플래그 `JAM_SKIP_*`는 15%에서 쓰였다. CI 기록(2219 §4 2단계, 2207 #1)이 있어야 아침 리뷰가 "브랜치를 열어 보기"가 아니라 "도장 확인"이 된다. 루프 환경에서는 `JAM_SKIP_*`를 쓸 수 없게 한다.

**⑤ 선별 기준 추가.** 훅·워크트리·git 설정·`CLAUDE.md`·에이전트 정의를 건드리는 티켓은 제외한다(오늘 두 사고 모두 이 영역). 유형이 `infra`·`db`·`engine`이면 제외. 티켓에 관련 파일 지도가 없으면 제외(아현 정의의 지도 규칙).

**⑥ 문서 스키마.** `loop_attempts`·`loop_last_verdict` 같은 frontmatter 필드는 `DOCUMENT_SCHEMA.md` §4의 선택 필드로 먼저 등록한다(하니). pre-commit이 막지는 않지만 규칙 5(단일 원천)다.

**⑦ 사용자 부담.** 2주 동의율은 사용자가 매일 대조해야 나온다. 선별 리포트는 티켓당 한 줄(판정 + 이유)로 하고 사용자는 체크만 한다. 동의율 계산은 카즈하가 주간 브리핑에서 한다.

**⑧ 무인 커밋의 경로 제한.** 선별 루틴의 커밋 작성자를 고정하고, pre-commit이 그 작성자의 커밋은 `jam-doc/operations/reports/` 밖 변경을 막게 하면, "읽기 전용"이 프롬프트가 아니라 훅으로 보장된다. 2207 §2.7의 "프롬프트만 막는 규칙" 하나를 더 닫는다.

## 4. 여섯 단계 수명주기와의 관계

루프는 **카리나가 없는 시간의 BUILD 소비자**다. 2219 §6의 BUILD 진입 조건(완료 조건 있는 티켓, UI면 채원 판정)과 위 선별 기준을 **하나의 규칙표**로 합쳐 단일 원천으로 둔다. 묶음 실행 모드(2219 §6.1)의 정지 조건과 야간 루프의 정지 조건도 같은 목록이어야 한다. 그래야 낮에 카리나가 하는 판정과 밤에 루프가 하는 판정이 갈라지지 않는다.
