# [Infra] CI 1주 실측 후 staging push까지 넓힐지 정한다

## 핵심 요약

- 요구사항: 리뷰 브랜치(`claude/**`)에만 켠 GitHub Actions `verify`의 1주 사용량을 집계하고, 무료 한도 안에서 staging push까지 넓힐 여유가 있는지 사용자에게 보고해 결정받는다.
- 구현 계획: 2026-09-29 이후에 `gh run list --workflow verify.yml --created '>=2026-09-21T15:00:00Z' --json databaseId,conclusion,createdAt,startedAt,updatedAt,headBranch --limit 500`으로 실행 횟수·실행별 시간·경로(전체·가벼운 검사)를 집계한다. 월 환산 사용량과 staging을 추가했을 때의 예상치를 함께 보고한다.
- 관련 파일: `.github/workflows/verify.yml`, `docs/agents/team-operations.md` §3, `docs/plan/vision/02 JAM! 서비스 플랜.md` §8.2 16번
- 상위 티켓: 20260921_2304(2026-09-22 사용자 결정: "1주 실측 후 여유가 있으면 staging을 추가한다"). 경로: 카리나 직접(research). staging 추가를 결정하면 별도 infra 티켓으로 구현한다.

## 배경 / 문제 정의

저장소가 비공개라 GitHub Actions는 무료 한도(GitHub Free 월 2,000분, Pro 월 3,000분)를 쓴다. 초과분은 Linux 2코어 기준 분당 $0.006이고, 결제 수단이 없으면 한도를 다 쓴 뒤 실행이 막힌다(GitHub 문서 「GitHub Actions billing」, 2026-09-22 확인). 2304의 사전 추정은 "하루 리뷰 브랜치 push 12회, 그중 70%가 코드 변경"이라는 가정에서 월 약 860분이었고 실측값이 아니다.

## 상세 요구사항

### 서비스/코드베이스 관점

1. 7일간의 실행 횟수, 전체 검사와 가벼운 검사의 횟수와 평균 시간, 취소된 실행 수를 집계한다.
2. 월 환산 사용량을 계산하고, staging push(하루 push 수는 `git log origin/staging`의 push 단위가 아니므로 티켓 종료 수로 근사한다)를 추가했을 때의 예상치를 함께 낸다.
3. 결제 설정(요금제·결제 수단)은 `gh` 권한으로 조회되지 않으므로 사용자에게 확인을 요청한다.

## 사전 확인 (카리나, 2026-09-22)

- **지금은 실행할 수 없다.** 1주 실측이 목적이라 2026-09-29(화) 이후에야 집계할 수 있어 상태를 `WAITING`으로 둔다(사용자 지시 "모두 실행"에도 시간 조건은 앞당길 수 없다).
- 미리 명령을 검증했다. GitHub의 날짜 필터는 UTC 기준이라 원문의 `>=2026-09-22`는 09-22 00:00~09:00 KST에 실행된 건을 놓친다. 09-22 00:00 KST는 `2026-09-21T15:00:00Z`이므로 이 값으로 고쳤다(고친 명령이 2304 실측 5건을 정상 조회했다). 소요 시간은 `updatedAt - startedAt`으로 계산한다.
- 기준선: 2304 실측 5건의 합계는 471초(7분 51초)이고 1분 단위로 올림하면 11분이다. 리뷰 브랜치 실험 실행이라 운영 사용량으로는 세지 않는다.

## 실측 결과 (카리나, 2026-10-23, 읽기 전용 집계로 아무것도 바꾸지 않았다)

시간 조건(2026-09-29 이후)이 풀려 집계를 마쳤다. 집계를 보고한 직후 사용자 결정(A 보류)을 받아 같은 날 닫았으나(아래 「사용자 결정」), 사용자가 저장소를 공개로 전환해 결정의 전제가 사라졌으므로 다시 열었다(아래 「전제 변경」). 이어서 사용자가 staging CI 추가를 결정해 닫았다(아래 「사용자 결정 2차」). 이 아래 「실측 결과」의 과금 분·월 환산·비용은 비공개 저장소 시절의 수치다.

### 집계 방법 (사실)

- 구간은 2026-09-22 00:00~09-29 00:00 KST(`2026-09-21T15:00:00Z` 이상 `2026-09-28T15:00:00Z` 미만)이고 대상은 `verify` 워크플로의 push 실행 271건이다.
- 티켓의 `gh run list --limit 500`은 두 번째 페이지부터 프록시가 거부했다(숫자 ID 경로 미지원, HTTP 403). `gh api repos/standardmanual/jam/actions/workflows/verify.yml/runs?per_page=100&page=N&created=>=2026-09-21T15:00:00Z`로 7페이지(09-22 이후 전체 630건)를 받았다.
- 티켓은 소요 시간을 `updatedAt - startedAt`으로 정했으나, 과금은 잡마다 1분 단위로 올리므로 잡의 `started_at`~`completed_at`을 올린 값을 «과금 분»으로 썼다. 실행 `timing` API의 `billable`은 이 저장소에서 0으로 나와 근거로 쓰지 못했다. 과금 분은 이 계산에 따른 추정치이고 GitHub 청구 화면과 다를 수 있다.
- 경로(전체·가벼운)는 `전체 검증`·`가벼운 검증` 단계가 건너뛰어졌는지로 구분했다.
- 이 저장소 클론은 얕은 클론(99커밋)이라 `git log`에서 `verify.yml`이 10-22 커밋의 새 파일로 보인다. GitHub 이력상 실제 생성은 09-21T16:20Z(09-22 01:20 KST)다.

### 판단 (카리나, 확신도 보통)

- 결정 조건은 «1주 실측 후 여유가 있으면 staging 추가»였다. 실측상 여유가 없다. 지금 구성만으로 Free 한도를 넘었고 Pro 한도에 근접하거나 넘는다. 확신도가 보통인 이유는 요금제, 결제 수단, 같은 계정의 다른 저장소 사용량을 모르기 때문이다.
- 권고는 A(보류)다. 사용자에게 물을 것은 (1) 요금제·결제 수단·지출 한도(`gh` 권한으로 조회되지 않음) (2) 아래 A/B/C 중 선택이다.
  - A. 보류(추천): 추가 사용량 없음.
  - B. staging은 코드 변경 push만: 약 500분/주, 월 2,142분 추가(347건 × 40% × 3.6분).
  - C. staging 전체 추가: 월 약 3,034분 추가(위 기준).
- 결정과 별개의 절감 후보(결정 아님): 전체 경로가 과금의 95%(827/871분)이고 잡 올림 손실이 17.5%다. `verify.sh` 시간을 줄이면 어느 선택에서도 효과가 있다.

### 사용자 결정 (2026-10-23)

- 사용자가 집계 보고에 «제안대로 실행»이라고 답했다. 제안 가운데 추천이 붙은 것은 A(보류) 하나였고, 커밋 방법은 첫 번째 안(이 커밋 한 건에 한해 사용자 명의로 커밋하고 push)이었다. 카리나는 이를 «staging 추가 보류(A) + 위 커밋 방법 승인»으로 해석해 처리했다. 해석이 틀렸으면 사용자가 정정하고, 그때 이 티켓을 다시 연다.
- 결과: staging push에는 CI를 추가하지 않는다. `verify.yml`은 그대로 `claude/**` push에서만 돈다. (공개 전환으로 전제가 바뀌어 이 결정은 효력을 잃었다. 아래 「전제 변경」)

### 전제 변경 (2026-10-23 밤)

- 사실(사용자 확인): 사용자가 이 저장소를 공개로 전환했다. 전환 시각은 확인하지 못했다. 같은 날 밤 확인에서 GitHub API는 `visibility: public`을 반환했고, 인증 없는 `raw.githubusercontent.com` 접근이 HTTP 200이었으며, 저장소 `updated_at`은 13:30:27 KST였다. 13:22:25 KST 차단과 13:36:39 KST 재개 사이에 전환했다는 것은 시각이 맞는 추정이다.
- 사실: 13:36 이후 계정 결제 차단 메시지는 다시 나타나지 않았고 `verify` 실행이 이어졌다. 결제·사용량 API는 이 세션에서 모두 막혀 있어(프록시가 저장소 범위 밖 경로를 거부) 과금 분을 직접 볼 수 없다.
- 해석: 공개 저장소의 표준 호스티드 러너 사용은 무료로 알려져 있으나, 이 사실을 공식 문서로 확인하지는 못했다(`docs.github.com` 접속 불가). 위 관찰은 이 해석과 모순되지 않는다.
