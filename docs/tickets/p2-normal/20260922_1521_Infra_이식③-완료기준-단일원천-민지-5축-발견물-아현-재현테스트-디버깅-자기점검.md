## 배경 / 문제 정의

이식 분석(20260921_2219 §1.3)에서 REVIEW 단계는 agent-skills와 JAM의 철학이 다르다고 확인했다. agent-skills의 리뷰는 5축 개선 지향이고 JAM의 게이트는 판정 전용이다. §2 판단 2에 따라 5축은 머지 관문이 아니라 민지의 범위 밖 발견물 분류와 아현의 제출 전 자기 점검으로 흡수한다.

BUILD 단계에서는 실패 테스트→수정의 명시 사이클, 재현→국소화→수정→방지의 디버깅 순서, 안전 기본값이 JAM에 없다(§1.3). 아현 정의는 "로직 변경 시 테스트"까지만 말한다.

완료 기준(DoD)은 지금 암묵적이다. "이것을 만들었나"(티켓 완료 조건)와 "끝낼 기준을 지켰나"(DoD)가 한 층으로 섞여 있어, 민지는 완료 조건만 보고 판정한다(§3 첫 행). `/jam-ship` 5단계는 Ship-readiness 네 항목을 이미 갖고 있으므로, 이 티켓은 나머지 묶음(정확성·품질)을 채우고 5단계가 새 파일을 가리키게 바꾼다.

## 상세 요구사항

### 서비스/코드베이스 관점

1. **완료 기준(DoD) 파일** (`definition-of-done.md` 원본 기준): 정확성 · 품질 · 배포 준비 세 묶음으로 옮긴다. 항목마다 JAM의 확인 방법을 붙인다(예: 테스트 = `scripts/verify.sh`의 test 단계, 기준 방어 = pre-push 통과, 문서 반영 = 민지 점검표 11번). 배포 준비 묶음은 `/jam-ship` 5단계의 네 항목(보안 검토·관측·롤백 경로·사람 승인)을 그대로 옮기고, 5단계에는 "이 파일의 배포 준비 묶음이 전부 충족돼야 진행한다"는 참조와 판정 규칙만 남긴다. 파일 첫머리에 티켓 완료 조건과의 구분("완료 조건은 이것을 만들었나, DoD는 끝낼 기준을 지켰나")과 「참조하는 곳」 목록을 둔다.
2. **민지 — 범위 밖 발견물의 5축·신호 분류** (`code-review-and-quality` §5축·심각도 기준): `sideFindings`의 각 항목을 `[축/신호] 내용 — 파일:줄` 형식으로 쓴다. 축은 정확성·가독성·구조·보안·성능 다섯 가지, 신호는 JAM의 참고/주의/중단 세 가지다. 원본의 Critical→중단, Required→주의, Optional·Nit→참고로 대응한다. 중단급은 이번 티켓 범위 밖이어도 `verdict` 요약 첫 줄에 올린다(판정 값은 바꾸지 않는다 — 범위 밖이므로). `jam-work.js` 109행의 스키마(문자열 배열)는 바꾸지 않는다. 객체 배열로 바꾸면 `jam-work.test.mjs`와 3.2절 자동 티켓화가 함께 바뀌어야 하기 때문이다.
3. **민지 — 판정 기준 두 층과 읽는 순서**: Principles에 "판정 기준은 티켓 완료 조건 + DoD 두 층"임을 명시하고, 읽는 순서를 "완료 조건 → 테스트 diff → 구현 diff"로 적는다(원본의 "테스트부터 읽는다"). 점검표 9번(보안)에 유형별 하위 항목을 넣는다: `api`(인증 확인 호출, 인가, 입력 검증, 오류 응답의 내부 정보 미노출), `db`(RLS 정책 동반, `SECURITY DEFINER`면 `REVOKE FROM PUBLIC` — 가드레일 패턴 8, service_role 경로 최소화), `admin`(`ADMIN_EMAILS`·`ADMIN_SECRET` 확인 경로). 항목은 원본 `security-checklist.md`와 `DEV_PROCESS_GUARDRAILS.md`에서 JAM에 해당하는 것만 고른다. Forbidden의 개선 제안 금지·코드 수정 금지는 유지하고, 판정 양식 40줄 상한도 유지한다.
4. **`/jam-work` 3.2절**: 자동 티켓화의 우선순위 기본값을 신호로 정한다 — 중단은 P1, 주의는 P2, 참고는 P3. 한 줄이면 된다.
5. **아현 — `bug` 유형 절차** (`test-driven-development` §Prove-It·`debugging-and-error-recovery`): 재현 실패 테스트 작성 → 실패 확인(RED) → 최소 수정 → 통과 확인(GREEN) → 전체 회귀. 재현 테스트를 만들 수 없으면 `tests_added`에 사유를 적는다. 디버깅은 재현 → 원인 국소화 → 수정 → 재발 방지(가드레일 패턴 제안은 `doc_updates`로) 순서다. 상세 절차는 `bug-procedure.md`에 두고, 정의에는 "`bug` 유형이면 구현 전에 이 파일을 읽는다" 한 줄만 둔다. 매 호출에 실리는 정의 크기를 늘리지 않기 위해서다(2219 §2 판단 3).
6. **아현 — 점진 구현·자기 점검** (`incremental-implementation`·`git-workflow-and-versioning`): 세로 조각 단위 원자 커밋과 커밋 메시지의 변경 요약, 단순성·범위·안전 기본값 원칙, 제출 전 자기 점검(DoD의 정확성·품질 항목을 스스로 확인해 `checks` 옆에 결과). 구현 요약 양식에 `assumptions` 칸(해석이 들어간 가정, 없으면 "없음")을 추가하고 30줄 상한은 유지한다.
7. **채원**: ① 사전 판정의 상태 목록에 로딩·빈·오류 상태를 필수 열거 항목으로 넣는다. ② 점검표 §1은 이미 대비·터치 영역·라벨·키보드·색·모션을 갖고 있으므로 원본 `accessibility-checklist.md`와 대조해 빠진 항목만 추가한다(예: 포커스 순서, 스크린리더 읽기 순서, 오류 메시지와 입력의 연결). §4 상태 절에 `frontend-ui-engineering`의 마감 점검(긴 텍스트, 작은 화면, 상태 전환)을 보강한다. 대조 결과는 표로 완료 기록에 남긴다.
8. 문서에는 "무엇을 하는가"만 적고 이식 출처는 절 끝에 한 줄로 남긴다. 원본 전문을 복사해 넣지 않는다. 제외한 항목은 「제외 목록」에 사유와 함께 적는다. 예상되는 제외: 원본의 "코드 건강을 개선하면 승인" 규칙(판정 전용 원칙과 충돌), `code-simplification` 자동 적용(2219 §3), semver·changelog·기능 플래그(Vercel 연속 배포), 전면 RED→GREEN 강제(로직 변경과 `bug`에만 적용, `copy`·`content`는 제외).

## 구현 계획

1. 원본 스킬·참조 문서를 전문으로 읽고 항목별 「이식 / 조정 / 제외(사유)」 표를 만든다. 이 표가 계획 반환의 본문이다.
2. `definition-of-done.md`를 만들고 `/jam-ship` 5단계·민지 점검표를 참조 형태로 고친다.
3. 민지 정의와 `review-verdict-format.md`를 고친다(축·신호 표, 접두 형식, 즉시 보고 규칙, 9번 하위 항목).
4. 아현 정의·`implementation-summary-format.md`·`bug-procedure.md`를 고친다. 정의 크기 전후 바이트를 기록한다.
5. 채원 정의·`ui-review-checklist.md`를 고친다.
6. `/jam-work` 3.2절 한 줄, `contract.json` 존재 검사, `scripts/verify.sh`·`node .claude/workflows/jam-work.test.mjs` 통과.
