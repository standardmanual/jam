# [Infra] 이식 ④ DEFINE·PLAN 양식 — 혜린 문답에 가정 목록·한 번에 한 질문, 기획서 고정 항목(측정 가능한 성공 기준·열린 질문·가정), 작업 분해에 선행 순서·세로 조각·체크포인트·크기 상한

## 핵심 요약

- 요구사항: agent-skills의 DEFINE·PLAN 단계 스킬을 혜린 정의와 `/jam-plan`·기획서 양식에 이식한다. (a) 문답은 가정 목록을 먼저 보여 준 뒤 한 번에 한 질문씩, 선택지+추천+이유를 붙여 묻고, 의도 확인이 필요하면 사용자 답 전에 진행하지 않는다. (b) 기획서에 측정 가능한 성공 기준, 열린 질문, 가정(확인됨/미확인)을 고정 항목으로 넣는다. (c) 작업 분해에 하위 티켓마다 선행 티켓, 세로 조각(끝나면 사용자에게 보이는 동작 하나가 완성되는 단위), 체크포인트(묶음 실행의 정지·확인 지점), 크기 상한(`plan_only` 기준을 넘지 않게 나눈다)을 넣는다. 사용자 결정(2026-09-21): 원본 세부를 살려 이식하고 제외 항목은 사유와 함께 남긴다. 메모리 피드백 "추천 방향을 함께 제시"는 이미 혜린 원칙에 있으므로 (a)와 합친다.
- 구현 계획: 원본 4종을 전문으로 읽고 「이식 / 조정 / 제외(사유)」 표 → `/jam-plan` 1단계·2단계·승인 후 절 → 혜린 정의(Principles·Stages·기획서 형식) → `brief-format.md` → 작업 분해 표기 규칙(상위 티켓 표의 「선행」 열) → `scripts/verify.sh`.

## 배경 / 문제 정의

이식 분석(20260921_2219 §1.3)에서 DEFINE 단계는 JAM과 겹침이 높지만 두 가지가 없다고 확인했다. 가정 목록을 명시하는 절차와 스펙을 살아 있게 유지하는 규칙이다. PLAN 단계에는 의존 그래프와 세로 조각 지침이 없다. 2305에서 카리나의 가정 목록 양식(`/jam-work` 0.0절)은 생겼지만, 그것은 DEFINE을 건너뛰고 BUILD로 갈 때 쓰는 것이다. 혜린의 문답에는 아직 가정 목록이 없다.

혜린은 지금 "질문 5개 이내"를 한 번에 넘긴다. 원본 `interview-me`는 한 번에 한 질문을 묻고, 의도가 확인될 때까지 턴을 멈춘다(0.6.10의 변경 #497). 기획서 형식에는 성공 기준이 있지만 측정 가능 여부를 요구하지 않고, 열린 질문·가정 항목이 없다. 작업 분해는 "티켓별 완료 조건 포함"까지만 요구한다. 묶음 실행 모드(2305)가 하위 티켓을 순서대로 돌리므로, 선행 순서와 체크포인트가 분해안에 없으면 `batch-tickets.mjs`의 티켓 ID 순서가 곧 실행 순서가 된다.

## 상세 요구사항

### 서비스/코드베이스 관점

1. **가정 목록 선행** (`spec-driven-development` §Phase 1): 1단계 문답을 시작하기 전에 혜린이 요청에서 읽어낸 가정을 목록으로 먼저 보여 주고, 틀린 것을 고쳐 받는다. 양식은 `/jam-work` 0.0절의 가정 목록과 같으므로 참조만 한다. 세계관 가정이 섞이면 윈터 검수를 붙인다(2219 §6.2 윈터 행).
2. **한 번에 한 질문·턴 정지** (`interview-me`): 질문 5개 이내 상한은 유지하되, 한 번에 한 질문씩 묻고 답을 받은 뒤 다음 질문을 정한다. 각 질문에는 선택지·추천·이유를 붙인다(이미 있는 원칙 1과 합친다). 의도 확인이 필요한 지점에서는 사용자 답 전에 다음 단계로 가지 않는다. `/jam-plan` 1단계의 "질문을 사용자에게 그대로 전달하고, 답을 모아 다시 넘긴다"를 이 순서에 맞게 고친다.
3. **기획서 고정 항목** (`spec-driven-development` 스펙 6영역 중 JAM에 없는 것): 성공 기준은 측정 가능한 문장으로(무엇을 어떻게 재면 달성인지), 열린 질문(답이 없으면 진행하지 못하는 것과 나중에 정해도 되는 것을 구분), 가정(확인됨/미확인). 6영역 중 Commands·Boundaries는 JAM에 고정돼 있어 제외하고, Capabilities map은 상위·하위 티켓 구조로 이미 있다(2219 §3). `brief-format.md`와 혜린 정의의 기획서 형식은 같은 목록을 두 번 정의하지 않는다 — 한 곳이 원천이고 다른 곳은 참조한다(현재 두 곳에 같은 목록이 있다).
4. **작업 분해 표기** (`planning-and-task-breakdown`): 하위 티켓마다 (a) 완료 조건(이미 있음), (b) 선행 티켓(없으면 "없음"), (c) 세로 조각 — 티켓 하나가 끝나면 사용자에게 보이는 동작 하나가 완성되는 단위로 자른다. 층별(DB만, API만, 화면만)로 자르지 않는다, (d) 체크포인트 — 묶음 실행 시 사용자 확인이 필요한 지점을 표시한다(정지 조건은 `stop-conditions.md`가 원천이므로 옮겨 적지 않는다), (e) 크기 상한 — 티켓 하나가 `plan_only` 기준을 넘지 않게 나눈다(수치는 `stop-conditions.md` 참조). 선행 순서는 상위 티켓 표의 「선행」 열에 적는다. 티켓 frontmatter는 늘리지 않는다.
5. **아이디어 다듬기** (`idea-refine`): 원본과 혜린의 현재 1단계(문제·사용자·성공 기준·크기·첫 판단)를 대조해 빠진 것만 넣는다. "만들지 말자"가 정당한 결론이라는 원칙은 이미 있다.
6. 월간 워크플로 회고 절은 바꾸지 않는다.
7. 문서에는 "무엇을 하는가"만 적고 이식 출처는 절 끝 한 줄로 남긴다. 제외 항목은 「제외 목록」에 사유와 함께 적는다. 예상되는 제외: `SPEC.md` 파일 생성(PRD·티켓과 중복, 2219 §2 판단 4), Commands·Boundaries 영역, 스펙 갱신을 강제하는 훅.

## 구현 계획

1. 원본 4종을 전문으로 읽고 「이식 / 조정 / 제외(사유)」 표를 만든다. 이 표가 계획 반환의 본문이다.
2. `/jam-plan` SKILL.md의 1단계를 "가정 목록 → 한 번에 한 질문 → 반쪽 요약" 순서로 고치고, 2단계·승인 후 절에 기획서 고정 항목과 분해 표기를 반영한다.
3. 혜린 정의의 Principles·Stages·기획서 형식을 고친다. 기획서 항목 목록은 `brief-format.md` 한 곳을 원천으로 두고 정의는 참조한다.
4. `issue-tracker.md`에 「선행」 열 규칙 한 줄을 확인·추가한다.
5. `scripts/verify.sh` 통과(`contract`·`team-doc` 포함).

- `issue-tracker.md`에 상위 티켓 표의 「선행」 열 규칙이 있다.
