## 사전 결정 (착수 전 사용자 확인)

- **한글 이름**: 2219 결정 5는 "배포 밖에서도 쓰게 될 때 정한다"였는데, 저장소 안 에이전트가 되는 순간 팀 표에 이름이 필요하다. 카리나 추천: 보안 점검 「해린」, 테스트 점검 「은채」. 다른 이름을 원하면 착수 시 바꾼다.
- **모델**: 주간 배포 1회에 두 에이전트가 도는 구조라 비용 여유가 있다. 추천 `sonnet`(판단이 필요한 점검). 라우팅 평가 실행은 `haiku`.

## 배경 / 문제 정의

이식 분석(20260921_2219 §1.3·§3)에서 SHIP 단계의 3인 팬아웃(코드 리뷰·보안·테스트)은 "다듬어 채택"으로 분류됐다. `code-reviewer`는 민지와 겹쳐 쓰지 않고, 보안·테스트 두 페르소나만 `/jam-ship`에서 병렬로 돌리기로 했다. 원래 설계는 플러그인의 페르소나를 그대로 호출하는 것이었지만, 플러그인을 켜 둔 채로는 세션마다 메타 스킬 약 10KB와 스킬 25종·에이전트 4종·커맨드 9종이 실리고, 다른 PC에서는 플러그인 설치 여부에 동작이 좌우된다. 2026-09-22 사용자가 페르소나를 저장소 안으로 옮기기로 정했고 플러그인은 같은 날 비활성화했다.

평가(eval)는 JAM에 없는 종류의 도구다(2219 §2 판단 6). `/jam-*` 스킬 설명문이 의도한 요청에 라우팅되는지를 지금은 아무도 확인하지 않는다. 구조 평가(frontmatter·설명문 존재)는 기계로 할 수 있고, 라우팅 평가는 LLM이 필요해 토큰이 든다.

## 상세 요구사항

### 서비스/코드베이스 관점

1. **페르소나 이관** (`agents/security-auditor.md`·`agents/test-engineer.md`): 원본의 점검 범위(입력 처리·인증/인가·비밀값·의존성·OWASP 항목 / 해피 패스·엣지·오류 경로·동시성의 커버리지 공백)는 살린다. JAM 적응으로 다음을 넣는다. (a) 한국어 출력, 보고 40줄 이내, 신호(참고/주의/중단)와 확신도(높음/보통/낮음). (b) 도구는 `Read, Grep, Glob, Bash`이고 Bash는 읽기 명령만(`git diff`·`git log`·`grep`). 코드 수정·티켓 생성·파일 쓰기 금지. (c) 입력은 카리나가 넘기는 커밋 범위(`baseSha..headSha`, 기본 `origin/main..origin/staging`)이고 그 밖은 읽지 않는다. (d) JAM 특화 항목: 보안 — Supabase RLS·`SECURITY DEFINER`·service_role 키 사용 경로·`ADMIN_EMAILS`/`ADMIN_SECRET` 확인·Strava 토큰 저장·비밀값 형태(`deploy-gate.mjs`와 중복되는 기계 검사는 하지 않고 판단이 필요한 것만). 테스트 — `jam-web/vitest.setup.ts` 환경, 배지·드랍 엔진 변경 시 시뮬레이터 검증 기록 존재, `scripts/*.test.mjs` 규칙(가드레일 패턴 15). (e) 다른 에이전트를 부르지 않는다(팬아웃은 평평하게 — 원본 ship.toml 제약). `code-reviewer`는 옮기지 않고(민지 중복), `web-performance-auditor`는 보류한다(성능 요구가 생기면). 두 결정의 사유를 「제외 목록」에 남긴다.
2. **팀 문서와 계약**: `contract.json` `agents` 절에 두 에이전트를 선언하고(`presence`는 "배포 관문에서만"), `gen-team-doc.mjs`로 생성 구간을 다시 만든다. `team-composition.md`·`CLAUDE.md` 팀 표에 두 행을 넣는다. 권한은 읽기 전용이며 워크트리를 만들지 않는다(`team-operations.md` 접근 범위 표).
3. **`/jam-ship` 병렬 점검** (`commands/ship.toml` Phase A·B): 4단계 롤백 계획 뒤, 5단계 완료 기준 앞에 절을 만든다. 카리나가 두 에이전트를 **한 턴에 동시에** 호출하고(순차 호출 금지 — 원본 제약) 커밋 범위를 넘긴다. 병합 규칙: 보안 중단급 → 승격 차단(사용자 보고 후 결정), 보안 주의급 → 보고하고 진행 여부는 사용자, 테스트 공백 → 주의로 보고(차단하지 않음). 결과는 9단계 보고에 「병렬 점검」 항목으로 남긴다. `deploy-gate.mjs`(기계 검사)와의 역할 구분을 한 문장으로 적는다. 무인 배포 경로(티켓 20260922_0001)에는 적용하지 않는다 — 무인 세션은 승인 주체가 없고 비용 상한이 있다. 「주간 무인 배포와의 관계」에 명시한다.
4. **구조 평가** (`evals/` 1단): `scripts/check-skills.mjs`가 `.claude/skills/*/SKILL.md`의 frontmatter(`name`·`description` 존재, `description`이 트리거 문구 예시를 포함)와 `.claude/agents/*.md`의 frontmatter(`name`·`description`·`tools`·`model`, description 안의 한글 이름)를 검사한다. `contract.json`의 `agents._order`와 실제 파일 목록이 일치하는지도 본다. `scripts/verify.sh`에 연결하고 테스트(`check-skills.test.mjs`)를 둔다.
5. **라우팅 평가** (`evals/` 2단, 선택 실행): `scripts/skill-eval-cases.json`에 요청 문장 → 기대 스킬(`/jam-work`·`/jam-plan`·`/jam-story`·`/jam-ship`·`/jam-sync`·`/jam-docs`·`/jam-design`·`/jam-ds`·`/jam-img`)과 기대 유형(`/jam-work` 0.2절 12종) 사례를 30건 이상 둔다. 실행은 카리나가 요청 시 Haiku 서브에이전트에게 사례를 주고 판정을 받아 일치율을 기록하는 절차로 두며, `verify.sh`에는 넣지 않는다(토큰). 원본 `evals/cases/*.json` 형식을 참고하되 JAM 필드로 줄인다.
6. 문서에는 "무엇을 하는가"만 적고 이식 출처는 절 끝 한 줄로 남긴다. 제외 항목은 「제외 목록」에 사유와 함께 적는다. 예상되는 제외: 3인 팬아웃의 `code-reviewer`, 행동 평가(3단), `/ship`의 GO/NO-GO 양식 중 `/jam-ship` 4·5단계와 겹치는 부분.

## 구현 계획

1. 원본 페르소나·`ship.toml`·`evals/README.md`를 읽고 「이식 / 조정 / 제외(사유)」 표를 만든다. 이 표가 계획 반환의 본문이다.
2. 에이전트 정의 2개를 만들고 `contract.json`·팀 문서 3곳을 고친 뒤 `node scripts/gen-team-doc.mjs`를 실행한다.
3. `/jam-ship`에 병렬 점검 절을 만들고 관련 절(9단계 보고·무인 배포 관계·하지 않는 것)을 맞춘다. 카리나 카드 한 줄.

5. `scripts/skill-eval-cases.json`과 실행 절차를 쓴다.
6. `scripts/verify.sh` 통과.
