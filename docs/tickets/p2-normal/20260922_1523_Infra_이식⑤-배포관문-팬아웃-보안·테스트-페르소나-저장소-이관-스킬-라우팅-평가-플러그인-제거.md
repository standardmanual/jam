## 배경 / 문제 정의

이식 분석(20260921_2219 §1.3·§3)에서 SHIP 단계의 3인 팬아웃(코드 리뷰·보안·테스트)은 "다듬어 채택"으로 분류됐다. `code-reviewer`는 민지와 겹쳐 쓰지 않고, 보안·테스트 두 페르소나만 `/jam-ship`에서 병렬로 돌리기로 했다. §6.2는 "에이전트 수는 늘지 않는다"를 전제로 플러그인의 페르소나를 호출 프롬프트로 쓰려 했다. 그런데 플러그인을 켜 둔 채로는 세션마다 메타 스킬 약 10KB와 스킬 25종·에이전트 4종·커맨드 9종이 실리고, 다른 PC에서는 플러그인 설치 여부에 동작이 좌우된다.

2026-09-22 사용자는 플러그인을 비활성화하고 페르소나를 저장소 안으로 옮기기로 정했다. 같은 날 후속 결정으로 새 에이전트를 만들지 않고 **민지의 모드로 편입**하기로 했다(B안). 민지 점검표에는 이미 보안(9번)과 테스트 적절성(4번)이 있어, 배포 전 점검은 같은 판단을 티켓 단위 대신 `main..staging` 전체 범위에 적용하는 일이다. 판정 전용·읽기 전용 원칙이 그대로 맞고, 채원이 모드 ①~④로 나뉘어 호출되듯 민지도 한 턴에 두 모드로 동시에 부를 수 있다.

평가(eval)는 JAM에 없는 종류의 도구다(2219 §2 판단 6). `/jam-*` 스킬 설명문이 의도한 요청에 라우팅되는지를 지금은 아무도 확인하지 않는다. 구조 평가(frontmatter·설명문 존재)는 기계로 할 수 있고, 라우팅 평가는 LLM이 필요해 토큰이 든다.

## 상세 요구사항

### 서비스/코드베이스 관점

1. **민지 모드 ②·③** (`agents/security-auditor.md`·`agents/test-engineer.md`): 정의에 「Modes」 절을 두고 호출 프롬프트가 모드를 지정한다(채원 방식). 모드 ①(티켓 게이트)은 지금 그대로다. 모드 ② 배포 전 보안 점검과 ③ 배포 전 테스트 공백 점검은 다음을 공유한다. (a) 입력은 카리나가 넘기는 커밋 범위(`baseSha..headSha`, 기본 `origin/main..origin/staging`)이고 그 밖은 읽지 않는다. (b) 출력은 한국어, 40줄 이내, 신호(참고/주의/중단)와 확신도(높음/보통/낮음), 발견물마다 파일:줄. `verdict`는 내지 않는다(판정은 카리나가 병합해서 한다). (c) 읽기 전용은 모드 ①과 같다. 코드 수정·티켓 생성·다른 에이전트 호출 금지(팬아웃은 평평하게 — 원본 ship.toml 제약). (d) 모드별 점검표는 `ship-security-check.md`·`ship-test-check.md`에 두고, 정의에는 "해당 모드면 이 파일을 먼저 읽는다" 한 줄만 둔다. 게이트 호출이 무거워지지 않게 하기 위해서다. 원본의 점검 범위는 살린다 — 보안: 입력 처리·인증/인가·비밀값·의존성·OWASP 항목. 테스트: 해피 패스·엣지·오류 경로·동시성의 커버리지 공백. JAM 특화 항목을 더한다 — 보안: Supabase RLS·`SECURITY DEFINER`·service_role 키 사용 경로·`ADMIN_EMAILS`/`ADMIN_SECRET` 확인·Strava 토큰 저장(`deploy-gate.mjs`와 중복되는 기계 검사는 하지 않고 판단이 필요한 것만). 테스트: `jam-web/vitest.setup.ts` 환경, 배지·드랍 엔진 변경 시 시뮬레이터 검증 기록 존재, `scripts/*.test.mjs` 규칙(가드레일 패턴 15). `code-reviewer`는 옮기지 않고(모드 ①과 중복), `web-performance-auditor`는 보류한다(성능 요구가 생기면). 두 결정의 사유를 「제외 목록」에 남긴다. 정의 파일의 전후 바이트 수를 기록한다.
2. **계약과 팀 표**: `contract.json`의 `agents.jam-reviewer` `role`·`presence` 문구에 배포 전 점검을 반영하고 `gen-team-doc.mjs`로 생성 구간을 다시 만든다. 참조 파일 2개의 존재 검사를 추가한다. `team-composition.md`·`CLAUDE.md` 팀 표의 민지 행 역할 문구를 같은 뜻으로 맞춘다. 에이전트 수·이름·모델은 바뀌지 않는다.
3. **`/jam-ship` 병렬 점검** (`commands/ship.toml` Phase A·B): 4단계 롤백 계획 뒤, 5단계 완료 기준 앞에 절을 만든다. 카리나가 민지를 **한 턴에 모드 ②·③으로 동시에** 호출하고(순차 호출 금지 — 원본 제약) 커밋 범위를 넘긴다. 병합 규칙: 보안 중단급 → 승격 차단(사용자 보고 후 결정), 보안 주의급 → 보고하고 진행 여부는 사용자, 테스트 공백 → 주의로 보고(차단하지 않음). 발견물 중 이번 배포에서 처리하지 않는 것은 `/jam-work` 3.2절과 같은 방식으로 티켓이 된다. 결과는 9단계 보고에 「병렬 점검」 항목으로 남긴다. `deploy-gate.mjs`(기계 검사)와의 역할 구분을 한 문장으로 적는다. 무인 배포 경로(티켓 20260922_0001)에는 적용하지 않는다 — 무인 세션은 승인 주체가 없고 비용 상한이 있다. 「주간 무인 배포와의 관계」에 명시한다.
4. **구조 평가** (`evals/` 1단): `scripts/check-skills.mjs`가 `.claude/skills/*/SKILL.md`의 frontmatter(`name`·`description` 존재, `description`이 트리거 문구 예시를 포함)와 `.claude/agents/*.md`의 frontmatter(`name`·`description`·`tools`·`model`, description 안의 한글 이름)를 검사한다. `contract.json`의 `agents._order`와 실제 파일 목록이 일치하는지도 본다. `scripts/verify.sh`에 연결하고 테스트(`check-skills.test.mjs`)를 둔다.
5. **라우팅 평가** (`evals/` 2단, 선택 실행): `scripts/skill-eval-cases.json`에 요청 문장 → 기대 스킬(`/jam-work`·`/jam-plan`·`/jam-story`·`/jam-ship`·`/jam-sync`·`/jam-docs`·`/jam-design`·`/jam-ds`·`/jam-img`)과 기대 유형(`/jam-work` 0.2절 12종) 사례를 30건 이상 둔다. 실행은 카리나가 요청 시 Haiku 서브에이전트에게 사례를 주고 판정을 받아 일치율을 기록하는 절차로 두며, `verify.sh`에는 넣지 않는다(토큰). 원본 `evals/cases/*.json` 형식을 참고하되 JAM 필드로 줄인다.
6. 문서에는 "무엇을 하는가"만 적고 이식 출처는 절 끝 한 줄로 남긴다. 제외 항목은 「제외 목록」에 사유와 함께 적는다. 예상되는 제외: 3인 팬아웃의 `code-reviewer`, 행동 평가(3단), `/ship`의 GO/NO-GO 양식 중 `/jam-ship` 4·5단계와 겹치는 부분, 원본 페르소나의 "수정안 작성"(민지는 제안하지 않는다 — 발견물은 티켓 경로로).
