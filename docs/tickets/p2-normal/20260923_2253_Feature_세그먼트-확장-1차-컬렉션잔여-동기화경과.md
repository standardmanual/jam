# [Feature] 세그먼트 확장 1차 — 컬렉션 잔여·동기화 경과 태그

## 핵심 요약

- 요구사항: 투데이 카드 노출 세그먼트(`exposure_tags`)에 "컬렉션 잔여 N개 이하"와 "Strava 동기화 경과 N일 이상"
  태그를 추가해, 조건을 충족한 유저가 실제로 다른 오늘 카드를 받게 한다. PRD §5.
- 구현 계획: `computeUserExposureTags`에 두 태그 계산을 추가하고, 어드민 투데이 카드 폼의 태그 선택지에 노출한다.
  임계값은 상수로 두되 확정 전 사용자 확인(체크포인트).
- 관련 파일: `jam-web/src/lib/today/exposure.ts`(`computeUserExposureTags`, `hasIncompleteBook` 135~144행 근처),
  `jam-web/src/lib/admin/today-sections.ts`(태그 선택지), `jam-web/src/lib/itembook/completion-basis.ts`
  (`computeBookCompletion`), DB `strava_connections.last_synced_at`, `user_item_book_slots`.
  스펙: `docs/service/prd/content-automation/PRD.md` §5.

## 배경 / 문제 정의

현재 태그는 `all`·시간대 5종·참여 중 미션·마감 임박 미션·미완성 아이템북·신규 유저 9종뿐이라 "거의 완성한 컬렉션"이나
"오래 동기화하지 않은 유저"를 겨냥한 카드를 만들 수 없다. 유형 T02(컬렉션 완성 독려)·T03(동기화 독려)의 전제다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 태그 2종 이상 추가(이름은 기존 명명 관례를 따른다. 예: 잔여 개수 임계값과 경과일 임계값을 이름에 드러낸다).
- 동기화 경과일은 `strava_connections.last_synced_at` 기준. **선행 확인**: 열린 티켓 20260922_2207(동기화 커서를
  마지막 활동 시작 시각 기준으로 변경)이 이 컬럼의 의미를 바꾸는지 먼저 확인하고, 바뀌면 그 결론을 따른다.
- 컬렉션 잔여는 미완성 컬렉션 중 남은 슬롯 수 최소값이 임계값 이하일 때.
- 계산은 기존 태그와 같은 호출 경로에서 하고, 추가 쿼리는 유저당 상수 회수로 제한한다.

### UI/UX 관점
- 어드민 투데이 카드 폼에서 새 태그를 선택할 수 있다. 사용자 화면 변경은 없다.

## 구현 계획 (파일 단위, 계획 반환 면제 근거)

선행 확인(2026-09-23 카리나): 20260922_2207은 구현·staging 병합이 끝났고 `last_synced_at`은 동기화 실행 시각(잠금·롤백 용도)으로
계속 기록된다. 따라서 동기화 경과일 기준 컬럼은 `strava_connections.last_synced_at`로 확정한다. 연결 자체가 없는 유저는 태그를
붙이지 않는다(동기화 독려 대상은 "연결했지만 오래 안 한" 유저다).

임계값(가정, 상수로 두어 조정 가능): 컬렉션 잔여 **3개 이하**(사용자 요청 원문), 동기화 경과 **14일 이상**(윤진 편성표 샘플). 두 값은
`exposure.ts` 상단 상수로 모은다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)
- 신규 태그 2종(`itembook_remaining_le3`, `strava_stale_14d`)이 `computeUserExposureTags` 결과에 포함되고 단위 테스트(경계값: 잔여 0·3·4개, 경과 13·14일, 연결 없음)가 통과한다.
- 어드민 투데이 카드 폼의 태그 선택지에 두 태그가 있다.
- Supabase 클라이언트를 모킹한 **통합 테스트 파일이 저장소에 남아** 조건 충족 유저·미충족 유저·Strava 미연결 유저 3종이 같은 시각에 서로 다른 태그 집합을 받는 것을 확인한다(임시 파일로 실행 후 삭제하지 않는다).
- 임계값은 상수 두 개(`ITEMBOOK_REMAINING_MAX = 3`, `STRAVA_STALE_DAYS = 14`)로 모여 있다.

### 후속 범위 (담당: 카리나, 시점: staging 병합 뒤)
- staging에서 테스트 계정 2개(조건 충족·미충족)로 실제 카드 노출 차이를 확인하고 재현 경로를 완료 기록에 적는다.
- 완료 기록에 임계값 현재 값을 적고, PRD §5의 "후보 태그" 표를 확정된 태그 이름으로 고친다(아현이 이미 반영했으면 확인만).

> 2026-09-23 정정: 1차 게이트(FAIL)에서 "실계정 수동 테스트"와 "완료 기록 기재"가 구현 범위에 있어 아현이 워크트리에서 채울 수 없었다.
> 두 항목은 카리나 후속 범위로 옮기고, 대신 모킹 통합 테스트를 정식 파일로 남기는 조건을 구현 범위에 넣었다.
