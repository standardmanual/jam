# [Infra] 유형 ID·노출·열람 계측 도입 (DB + API)

## 핵심 요약

- 요구사항: 투데이 카드에 유형 ID를 붙이고, 노출·열람·후속 행동 이벤트를 유형 ID와 함께 기록해 어드민에서 유형별
  누적 수치를 볼 수 있게 한다. 개인 식별자는 저장하지 않는다(집계만, 결정 4-6). PRD §9.
- 구현 계획: 먼저 현재 GA4 카드 단위 이벤트 유무를 코드에서 확인(카즈하 미확인). `today_cards`에 유형 ID 컬럼,
  이벤트 집계 테이블, 기록 API, 어드민 집계 조회를 만든다. **SQL은 마이그레이션 파일 작성까지, 실행은 사용자 승인 후
  메인 세션.** 되돌림 SQL 포함.
- 관련 파일: `jam-web/supabase/migrations/`(신규), `jam-web/src/app/(main)/TodayCardStack.tsx`(노출·클릭 지점),
  `jam-web/src/app/api/today/`(이벤트 기록 라우트 신규), `jam-web/src/lib/analytics/gtag.ts`(GA4 이벤트 현황 확인),
  `docs/specs/prd/analytics/`(GA4 이벤트 명세). 스펙: PRD §9, 규칙: `.claude/skills/jam-work/references/db-migration-rules.md`.

## 배경 / 문제 정의

카드 단위 반응 기록이 없으면 전략 변경안(⑤)과 유형 리뷰(⑥)가 설 수 없다. 카즈하 확인(2026-09-23): GA4는 켜져 있으나
카드 단위 이벤트 전송은 코드에서 확인되지 않았다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `today_cards`에 유형 ID 컬럼(PRD §6의 T01~T17, nullable. 기존 카드는 비움).
- 이벤트 저장은 집계 목적만: 카드 ID·유형 ID·이벤트 종류(노출·열람·후속 행동)·발생 시각. 유저 식별자는 저장하지
  않는다. 노출 중복 완화가 필요하면 세션 단위 클라이언트 측 억제로 처리한다.
- 후속 행동(픽업·믹스·동기화·체크인·미션 참가 등)은 1단계에서는 열람 후 N분 안의 행동을 클라이언트가 카드 ID와 함께
  보고하는 방식으로 시작한다. 서버 조인은 후속.
- 어드민에서 유형 ID별 누적(노출·열람·후속 행동·채택률은 리포트에서 합산)을 조회하는 API 또는 화면.
- 확장→전환→축소 분할과 되돌림 SQL 규칙을 따른다.

## 구현 계획

1. GA4 카드 이벤트 현황 확인 → 있으면 재사용 범위 판단
2. 마이그레이션 SQL(확장 단계) + 되돌림 SQL 작성
3. 기록 API + 카드 스택의 노출·클릭 훅
4. 어드민 집계 조회
5. 사용자 승인 후 메인 세션이 SQL 실행

## 완료 조건

### 구현 범위 (게이트 판정 대상)
- 마이그레이션 SQL과 되돌림 SQL이 `jam-web/supabase/migrations/`에 있고 규칙 문서의 분할 형식을 따른다.
- 테스트 환경에서 카드 노출·클릭 시 유형 ID가 포함된 이벤트가 기록되고, 유저 식별자가 저장되지 않는 것을 확인한다.
- 어드민 집계 조회로 유형 ID별 누적 수치가 나온다.

### 후속 범위 (담당: 카리나, 시점: 사용자 승인 뒤)
- SQL 실행(공용 단일 DB, 즉시 프로덕션 반영). 실행 전 사용자 승인. 체크포인트.
- `02_DATA_MODEL.md`에 새 컬럼·테이블 반영.

크기 상한: 5파일/100줄(SQL 제외).
