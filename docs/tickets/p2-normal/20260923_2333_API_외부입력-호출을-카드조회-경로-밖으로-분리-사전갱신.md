# [API] 외부 입력(날씨·특일) 호출을 카드 조회 경로 밖으로 분리하고 특일 캐시 테스트를 보강한다

> 티켓 20260923_2254 게이트 WARN 사유 1·3의 후속. 타임아웃 단축(20260923_2332)은 임시 상한이고, 이 티켓이 근본 해결이다.

## 핵심 요약

- 요구사항: `computeUserExposureTags`가 외부 API를 직접 기다리지 않게 한다. 날씨·특일 값은 요청 경로 밖에서 미리 갱신해 두고(예: 하루 1회 cron 또는 첫 요청 후 백그라운드 갱신), 카드 조회는 저장된 값만 읽는다. 값이 없으면 지금처럼 태그만 빠진다. 특일 모듈의 캐시 히트(재호출 없음) 테스트를 추가한다.
- 구현 계획: **선행 20260924_0602(테이블 `external_input_daily`, 마이그레이션 184) 실행 뒤 착수한다.**
  ① 새 모듈 `jam-web/src/lib/inputs/daily-store.ts`: `readDailyInput(kind, dateKst)`(서비스 클라이언트로 읽기, 오류·없음이면 null,
  요청 경로용)와 `writeDailyInput(kind, dateKst, value)`(upsert, cron 전용). ② `weather.ts`·`holidays.ts`: 외부 호출 본체를
  `refreshTodayWeather()`·`refreshTodaySpecialDays()`로 분리해 export하고, `getTodayWeather()`·`getTodaySpecialDays()`는 저장값만 읽는다
  (모듈 하루 캐시는 저장 조회 결과에만 유지, 값이 없으면 지금처럼 null·빈 배열). ③ 새 라우트 `jam-web/src/app/api/cron/external-inputs/route.ts`:
  `CRON_SECRET` 검증 후 두 갱신 함수를 호출해 저장(패턴은 `poi-cleanup/route.ts`). ④ `jam-web/vercel.json` crons에 `"0 21 * * *"`(06:00 KST) 추가.
  ⑤ 테스트: `getToday*`가 fetch를 부르지 않음, 특일 캐시 히트(두 번째 호출이 fetch 재호출 없음), refresh 함수 동작.
- 관련 파일: `jam-web/src/lib/inputs/weather.ts`(`getTodayWeather`, 캐시), `jam-web/src/lib/inputs/holidays.ts`(`getTodaySpecialDays`), `jam-web/src/lib/today/exposure.ts`(`computeUserExposureTags` 151행 근방), `jam-web/src/lib/inputs/__tests__/inputs.test.ts`, `jam-web/src/lib/today/cards.ts`(70행 호출 지점), `jam-web/src/app/api/cron/poi-cleanup/route.ts`(cron 라우트 패턴),
  `jam-web/vercel.json`, `docs/specs/prd/04_PROJECT_SPEC.md`(Cron 절, 97행 근방 갱신).

## 배경 / 문제 정의

민지 게이트(2254): 오늘 카드 조회는 모든 유저가 매번 거치는 공유 경로인데 그 안에 외부 호출 2건이 들어가, 서버리스 인스턴스별 캐시가 비어 있을 때마다 타임아웃까지 지연될 수 있다. 특일 모듈은 캐시 히트 테스트가 없다.

## 완료 기록

### 구현 내용 요약
카드 조회 경로(`getTodayCards` → `computeUserExposureTags`)가 외부 API를 직접 기다리지 않게 했다. 외부 호출은 cron(`/api/cron/external-inputs`, 매일 21:00 UTC = 06:00 KST)이
하루 1회 수행해 `external_input_daily`(마이그레이션 184)에 저장하고, `getTodayWeather()`·`getTodaySpecialDays()`는 저장값만 읽는다. 값이 없으면 지금처럼 태그만 빠진다.
- `daily-store.ts` 신설: `readDailyInput`(행 없음·오류면 null, 던지지 않음)·`writeDailyInput`(upsert, 실패 시 throw)·`ymdToDateKst`.
- `weather.ts`·`holidays.ts`: 외부 호출 본체를 `refreshTodayWeather`·`refreshTodaySpecialDays`로 분리. 모듈 하루 캐시는 저장값을 찾았을 때만 둔다(값이 없을 때 캐시하면 cron 저장 뒤에도 그 인스턴스가 못 본다). 특일은 "오늘 특일 없음" 빈 배열도 값으로 캐시하고, 세 오퍼레이션이 모두 실패한 경우(null)와 구분한다.
- cron 라우트: `CRON_SECRET` 검증, 두 갱신을 병렬 실행해 각각 저장. 한쪽 실패는 다른 쪽 저장에 영향이 없고, 실패가 있으면 502.
- `vercel.json` crons에 `0 21 * * *` 추가(사용자 승인), `04_PROJECT_SPEC.md` Cron 표에 행 추가. 같은 문서의 "Cron 4건" 표기가 실제 3건과 어긋나 있었는데 이번 추가로 맞아졌다.
- 게이트 WARN 사유 1(cron 라우트·저장소 테스트 공백)은 머지 뒤 카리나가 테스트 2파일을 추가해 해소했다(승인: 사용자 "제안대로 함").

### 주요 의사결정 / 핵심 메모
- 크기 면제: 계획 7파일·약 150줄이 기준(5파일 초과·100줄 이상)을 넘어, 사용자가 2026-09-24에 파일 단위 계획을 검토·승인한 뒤 `planOnlyWaiver`로 진행했다. 실제 diff는 341줄(기존 테스트 재작성 약 150줄 포함)로 예상보다 컸다.
- 머지 전 오염 검사가 실패했으나 원인은 다른 세션이 `origin/staging`에 올린 커밋(0625)이었고, 리뷰 브랜치에는 아현의 커밋만 있어 로컬 staging 최신화 뒤 머지했다.
- 카리나의 직접 테스트 추가는 규칙표의 "파일 2개·10줄 이내" 패치 기준을 줄 수로는 넘긴다. 사용자가 명시 승인했고 코드 변경 없이 테스트만 추가했으며 게이트 재실행은 하지 않았다.
- 가정: 저장 값 형태는 날씨 `{"kind":...}`, 특일은 `{name,type}` 배열. 갱신 실패일에는 전날 값을 쓰지 않는다.

### 잔여 이슈
- **배포 후 수동 호출(카리나, main 배포 시)**: 프로덕션 cron이 처음 도는 06:00 KST 전까지 저장값이 없어 날씨·기념일 태그가 빠진다. 배포 직후 `Authorization: Bearer <CRON_SECRET>`로 `/api/cron/external-inputs`를 한 번 호출해 채운다.
- cron이 하루 1회라 실패한 날은 재시도가 없다(티켓 폴백 요구와 일치).
- `refreshTodayWeather(now)`가 인자 `now`를 받지만 내부 `fetchKmaForecast`가 `latestKmaBaseTime(new Date())`를 써서 발표시각 계산에 반영되지 않는다(`weather.ts:96`, 영향 없음). 후속 티켓 20260924_0648로 분리했다.
