# [API] 카드 이벤트 기록 API에 유저별 빈도 제한과 카드 노출 상태 검증을 추가한다

> 티켓 20260924_0004 게이트 리뷰(민지)의 범위 밖 발견물에서 자동 생성.

## 핵심 요약

- 요구사항: `POST /api/today/events`는 로그인만 확인하고 카드 ID의 노출 여부·요청 빈도를 검증하지 않아, 로그인 유저가 임의 카드 ID로 노출·클릭을 반복 전송해 전략 변경안·유형 리뷰 집계를 조작할 수 있다. 카드가 현재 활성·노출 기간 안인지 검증하고, 유저별 분당 요청 상한(예: 60건)을 둔다. 상한 판정에 쓰는 유저 키는 요청 처리 중에만 쓰고 저장·로그하지 않는다(집계 전용 원칙 유지).
- 관련 파일: `jam-web/src/app/api/today/events/route.ts`, `jam-web/src/lib/today/events.ts`(`recordTodayCardEvent` 앞 검증), 테스트 `jam-web/src/lib/today/__tests__/events.test.ts`

## 구현 계획 (파일 단위)

| 파일 | 할 일 |
|---|---|
| `jam-web/src/lib/today/events.ts` | `assertCardExposable(cardId, now)`: 카드가 존재하고 `is_active`이며 `starts_at`·`ends_at` 기간 안일 때만 통과(아니면 검증 오류). `recordTodayCardEvent` 앞에서 호출. 빈도 제한 헬퍼 `checkRateLimit(key, limit, windowMs)`: 인스턴스 메모리 Map(키 → 타임스탬프 배열)으로 분당 60건 상한. 키는 요청 처리 중 유저 ID로만 계산하고 저장·로그·응답에 남기지 않는다(서버리스라 인스턴스별 최선 노력임을 주석에 명시) |
| `jam-web/src/app/api/today/events/route.ts` | 로그인 확인 뒤 빈도 제한(초과 시 429, 본문은 일반 메시지) → 카드 노출 검증(실패 400) → 기록. 유저 ID는 제한 판정 후 변수에서 쓰지 않는다 |
| `jam-web/src/lib/today/__tests__/events.test.ts` | 비활성·기간 밖·미존재 카드 거부 3건, 분당 상한 초과 시 거부 1건, 기록 페이로드·로그에 식별자 없음 유지 1건 |

예상 규모: 파일 3개, 약 80줄(임계값 미만). 착수 전 확인(2026-09-24 카리나): 현재 라우트는 `auth.getUser()`로 로그인만 확인하고 카드 검증·빈도 제한이 없다(0004 게이트 발견물).

## 완료 조건

- 비활성·기간 밖 카드 ID는 400으로 거부되고, 분당 상한 초과는 429로 거부되며, 저장 페이로드와 로그에 유저 식별자가 없다(테스트로 확인).

크기 상한: 파일 3개, 60줄 이내.
