# [Infra] 외부 입력(날씨·특일) 일일값을 저장하는 테이블 신설 (db, 확장 단계)

> 티켓 20260923_2333(외부 호출을 카드 조회 경로 밖으로 분리)의 선행 티켓이다. 사전 갱신값을 서버리스
> 인스턴스끼리 공유하려면 인스턴스 밖 저장소가 필요해서 소형 테이블 하나를 만든다. 스키마만 연다 —
> 읽기·쓰기 코드는 2333이 맡는다.

## 핵심 요약

- 요구사항: 날씨 구분과 특일 목록을 하루 단위로 저장하는 테이블 `external_input_daily`를 만든다. 행은
  (`kind`, `date_kst`)당 하나이고 값은 JSONB다. 유저 식별자는 두지 않는다.
- 구현 계획: `jam-web/supabase/migrations/184_external_input_daily.sql` 한 파일. `CREATE TABLE IF NOT EXISTS`,
  `kind` CHECK(`weather`·`special_days`), 기본키 (`kind`, `date_kst`), `value JSONB`, `fetched_at TIMESTAMPTZ`.
  RLS는 켜고 정책은 만들지 않는다(서비스 롤 전용, 183의 `today_card_events`와 같은 패턴). 되돌림 SQL을 파일 끝 주석으로 싣는다.
- 관련 파일: `jam-web/supabase/migrations/183_today_card_type_and_events.sql`(스타일·RLS 패턴 참고),
  `docs/specs/prd/02_DATA_MODEL.md`(테이블 절 추가).

## 배경 / 문제 정의

날씨·특일 값이 서버리스 인스턴스의 모듈 변수에만 캐시돼서, 인스턴스가 새로 뜰 때마다 카드 조회가 외부 API를 직접 기다린다
(2333). 사전 갱신 경로(cron)와 카드 조회 경로가 서로 다른 인스턴스에서 돌기 때문에 공유 저장소가 필요하다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 확장 단계 마이그레이션이라 옛 모양을 지우는 문장은 없다. 재실행해도 안전하게(idempotent) 쓴다.
- `date_kst`는 `DATE` 타입이고 값은 한국 표준시 기준 날짜다. `value`는 날씨면 `{"kind":"clear"|"mild"|"rain"|"extreme"}`,
  특일이면 정규화된 특일 배열이다(형태는 2333에서 정한다. 이 테이블은 스키마만 고정한다).
- 오래된 행 정리는 이 티켓 범위 밖이다(행이 하루 2건씩이라 1년에 730건이다).
- Supabase는 staging·프로덕션 공용 단일 DB이므로 적용 즉시 프로덕션에 반영된다. 새 테이블을 읽는 코드가 아직 없으니 영향은 없다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)
- `184_external_input_daily.sql`이 위 스키마로 작성되고, 되돌림 SQL 표식이 있다.
- RLS가 켜져 있고 anon·authenticated용 정책이 없다.
- `02_DATA_MODEL.md`에 테이블 설명이 추가된다.

### 후속 범위 (담당: 카리나, 시점: 머지 뒤)
- 사용자 승인 후 SQL 실행(사용자가 SQL 편집기에서 직접 실행 — 이 환경은 MCP 쓰기가 차단될 수 있다). 실행 뒤 타입 대조.

크기 상한: 2파일/60줄.

## 완료 기록

### 구현 내용 요약
날씨·특일 일일값을 저장하는 테이블 `external_input_daily`를 만드는 확장 단계 마이그레이션 184를 작성하고, 사용자가 SQL 편집기에서 실행했다.
`kind`(`weather`·`special_days` CHECK)·`date_kst`(DATE)·`value`(JSONB NOT NULL)·`fetched_at`, 기본키 (`kind`, `date_kst`), RLS 켜고 정책 없음(서비스 롤 전용).
실행 뒤 Supabase MCP 조회로 테이블·컬럼·CHECK·기본키·RLS 상태가 SQL과 일치하고 0행임을 확인했다. 생성 타입(`database.generated.ts`)에 테이블을 추가했고 `tsc --noEmit`이 통과했다.

### 주요 의사결정 / 핵심 메모
- 저장소로 KV 대신 DB 소형 테이블을 골랐다. 프로젝트에 KV가 없고, 테이블은 서비스 롤 전용 RLS로 183과 같은 패턴을 재사용할 수 있다.
- 특일 `value`의 배열 형태는 2333에서 정한다. 그래서 `value`에 형태 CHECK는 걸지 않았다.
- 크기는 2파일·65줄로 티켓 상한(60줄)보다 5줄 많았다. 초과분은 주석과 검증 쿼리라 게이트는 통과시켰다.
- 머지 전 오염 검사에서 `origin/staging`이 앞서 있었으나, 원인은 예약 루틴의 선별 리포트 1건(`3746a383`)이었다. 브랜치에는 아현의 커밋만 있어 로컬 staging을 fast-forward한 뒤 머지했다.
- 초기에 "DB 쓰기는 사용자만 실행 가능"이라고 안내한 것은 부정확했다(시도한 적 없음). 사용자와 "승인 뒤 MCP로 먼저 시도"로 합의했으나, 사용자가 이번에는 직접 실행했다. 규칙표 반영 편집은 분류기가 거부해 보류 중이다.
