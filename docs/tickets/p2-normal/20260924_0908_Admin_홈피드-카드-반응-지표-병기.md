# [Admin] 캘린더의 홈피드 카드 옆에 노출·열람 수를 표시한다

## 핵심 요약

- 요구사항: 어드민 메인 주간 캘린더에서 0906이 표시한 **단기 카드**마다 그날의 **노출 수와 열람 수**를 함께 표시한다. 수집이 시작되기 전 날짜는 "집계 전"으로, 오늘보다 뒤 날짜는 아무것도 표시하지 않는다. **후속 행동은 표시하지 않는다**(수집하지 않기로 한 결정, 아래 배경).
- 구현 계획: 아래 「구현 계획」 1~5를 따른다.
- 관련 파일:
  - `jam-web/src/lib/today/events.ts` `aggregateTodayCardEvents` (160줄, 유형별 집계 — 이 티켓은 카드별·날짜별 집계가 필요해 재사용하지 않고 새 파일에서 같은 방식으로 페이지를 넘겨 읽는다), 페이지 크기 상수 `AGGREGATE_PAGE_SIZE`
  - `jam-web/supabase/migrations/183_today_card_type_and_events.sql` (`today_card_events` 구조: `card_id`, `content_type_id`, `event`, `occurred_at`)
  - `jam-web/src/lib/admin/weeklyCards.ts` (단기 카드 배분, 0906)
  - `jam-web/src/lib/admin/today-calendar.ts` `kstDayBoundsIso` (45줄), `todayKstDateString` (14줄)
  - `jam-web/src/app/admin/WeeklyCalendar.tsx` `CalendarCellItem` (9~18줄), 항목 렌더 (86~94줄)
  - `jam-web/src/app/admin/page.tsx` 카드 조회·배분 구간
  - 스펙: `docs/specs/prd/content-automation/PRD.md` §9(계측), §11(표본 기준), `docs/specs/prd/admin-ui/ADMIN_PRD.md` §5-7

## 배경 / 문제 정의

주간 브리핑에서 윤진이 읽는 카드 반응 수치를 운영자도 캘린더에서 바로 확인하기 위함이다.

2026-09-24 확인한 사실(계획의 근거):
- 원천 `today_card_events`에는 `card_id`가 있어 카드별 집계가 가능하다. 기존 `GET /api/admin/today/metrics`와 `aggregateTodayCardEvents`는 **유형 ID별**로만 묶어 돌려주므로 그대로 쓸 수 없다.
- 수집은 2026-09-24 09:33 KST에 시작됐다. 같은 날 14:07까지 34건이며 전부 노출이고 열람은 0건이다. 34건은 카드 30장에 걸쳐 있고 전부 `content_type_id`가 비어 있다(장기 카드). 단기 카드(9/28~)의 이벤트는 아직 없다.
- **후속 행동(`followup`)은 수집하지 않기로 했다**(2026-09-24 사용자 결정, 티켓 20260924_0810 — `jam-web/src/lib/today/events.ts` 15~17줄). 이벤트 API가 노출·열람만 받는다.
- PRD §11은 **표본 크기의 최소 숫자 기준을 두지 않는다**(2026-09-24 결정). 처음 계획에 적었던 "표본 적음 표시"는 이 결정과 어긋나서 뺀다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 표시 대상은 0906이 한 장씩 표시하는 단기 카드뿐이다. 장기 카드 줄에는 반응 수치를 붙이지 않는다.
- 카드별·날짜별 집계는 그 칸의 KST 하루(`kstDayBoundsIso`) 안의 이벤트만 센다. 여러 날에 걸친 단기 카드는 칸마다 그날 수치가 따로 나온다.
- 표시 문구 규칙(칸 하나의 카드 항목 아래 작은 글씨 한 줄):
  - 오늘 이전 또는 오늘이면서 수집 시작일 이후: `노출 N · 열람 N` (0이어도 0으로 표시)
  - 수집 시작일보다 이전 날짜: `집계 전`
  - 오늘보다 뒤 날짜: 표시 없음
- 수집 시작일은 코드에 적어 두지 않고 `today_card_events`에서 가장 이른 `occurred_at`의 KST 날짜를 한 번 조회해 쓴다(이벤트가 하나도 없으면 모든 날짜를 `집계 전`으로 본다).
- 개인 식별 정보는 다루지 않는다(원천에 유저 식별 컬럼이 없고, 집계 수치만 표시한다).
- 이벤트 조회가 실패해도 카드 항목과 나머지 영역은 그대로 표시한다(카드 항목 아래 수치 줄만 비운다).
- 조회는 카드 ID·주 범위로 좁히고 1,000행 상한에서 잘리지 않게 페이지를 넘겨 읽는다(`.order('id')` + `.range()`, 기존 집계와 같은 방식).
- 어드민 유형이므로 MODULAR를 적용하지 않는다. 조회만 하며 DB 변경은 없다.
- 실렌더는 격리 워크트리에서 시도하지 않는다(티켓 20260924_1016). 머지 뒤 카리나가 확인한다.

## 구현 계획

1. `jam-web/src/lib/admin/weeklyCardMetrics.ts` (신규): (a) 순수 함수 `bucketCardEvents(rows)` — `{ card_id, event, occurred_at }` 행을 `카드ID|KST날짜 → { impression, click }`로 센다(`followup`·알 수 없는 이벤트는 무시). (b) 순수 함수 `formatCardMetricsNote({ date, today, firstEventDate, counts })` — 위 표시 문구 규칙을 적용해 문자열 또는 `null`을 돌려준다. (c) 조회 함수 `fetchWeeklyCardMetrics(cardIds, weekStartIso, weekEndIso)`와 `fetchFirstEventKstDate()` — `createServiceClient()`로 `today_card_events`를 읽는다.
2. `jam-web/src/lib/admin/__tests__/weeklyCardMetrics.test.ts` (신규): 버킷 집계(KST 자정 경계 23:59:59.999·00:00:00.000), 여러 날 카드의 날짜별 분리, `followup` 무시, 문구 규칙 4가지(오늘 이전·수집 시작 전 `집계 전`·오늘·미래 없음), 이벤트 없음일 때 `집계 전`.
3. `WeeklyCalendar.tsx`: `CalendarCellItem`에 선택 필드 `note?: string`을 추가하고 항목 아래 작은 글씨(`text-[11px] text-muted-foreground`)로 표시한다. 기존 크론·루틴·카드·미션 표시는 바뀌지 않아야 한다.
4. `page.tsx`: 그 주의 단기 카드 ID를 모아 오늘 이전(포함) 날짜가 있는 경우에만 1번 조회 함수를 부르고(출처별 try/catch), 각 카드 항목에 `note`를 붙인다. 오늘보다 뒤인 주(미래 주)에서는 이벤트 조회를 하지 않는다.
5. `ADMIN_PRD.md` §5-7: 「현재 동작」에 카드 반응 표시(노출·열람, 집계 전, 후속 행동 미표시와 그 이유)를 추가하고 「예정」에서 뺀다.

## 완료 조건

- 1번의 순수 함수에 단위 테스트가 있다: KST 자정 경계, 여러 날 카드 분리, `followup` 무시, 문구 규칙 4가지, 이벤트 없음.
- (카리나 실렌더, 머지 뒤) 수치가 표시된 카드가 화면에 있으면, 그 값이 `today_card_events`를 직접 센 값과 같다(대조 SQL을 완료 기록에 남긴다). 2026-09-24 기준으로 단기 카드는 9/28부터라 수치가 붙는 날짜가 아직 없다. 그 경우에는 단위 테스트 통과와 "대조할 카드 없음"이라는 사실을 완료 기록에 남기고, 첫 단기 카드일(9/28) 이후의 수치 대조를 잔여 이슈로 적는다.
- 후속 행동은 표시되지 않고, "표본 적음" 같은 표본 판정 문구도 없다.
- 이벤트 조회가 실패해도 카드 항목과 크론·루틴·미션·이상 신호는 표시된다.
- 기존 크론·루틴·카드·미션 표시는 바뀌지 않는다.
