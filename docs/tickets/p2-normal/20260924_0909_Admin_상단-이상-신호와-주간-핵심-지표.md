# [Admin] 어드민 메인 상단에 이상 신호(Strava 동기화·어뷰징)와 주간 핵심 지표를 표시한다

## 핵심 요약

- 요구사항: 페이지 최상단에 C Strava 동기화 실패 건수, D 제재 수·차단 POI 수를 표시하고, 그 아래 A 주간 핵심 지표(미션 달성자 수·배지 발급량)를 지난주와 비교해 표시한다.
- 구현 계획: `computeKpiWeeklyMetrics()`를 이번 주와 지난주 범위로 두 번 호출해 비교값을 만든다. D는 `user_shadow_bans`와 POI 차단 테이블의 개수를 조회한다(`/api/admin/abusing/*`의 조회 로직 재사용). C는 `/admin/strava-backfill`, D는 `/admin/abusing` 링크를 붙인다.
- 관련 파일:
  - `jam-web/src/lib/admin/kpiWeekly.ts` `computeKpiWeeklyMetrics` (92줄), `resolveKpiWeeklyRange` (55줄)
  - `jam-web/src/app/api/admin/abusing/bans/route.ts` `GET`, `jam-web/src/app/api/admin/abusing/poi-blocks/route.ts`
  - `jam-web/src/app/admin/page.tsx`
  - 신규: `jam-web/src/app/admin/DashboardSignals.tsx`

## 배경 / 문제 정의

Strava 동기화가 멈추면 배지와 미션 판정이 함께 멈춘다. 지금은 주간 브리핑이 나와야 알 수 있다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 이상 신호는 0보다 크거나 지난주보다 늘었을 때 강조 색으로 표시한다(판정 기준은 구현 계획에 상수로 명시).
- 집계 수치만 표시한다.
- 어드민 유형이므로 MODULAR를 적용하지 않는다. 조회만 하며 DB 변경은 없다.
- 표시하는 시각은 모두 KST다. 데이터 하나를 불러오지 못해도 해당 영역만 오류 문구를 보이고 페이지 전체는 렌더된다(기존 `serviceError` 패턴).
- 실렌더 검증은 `docs/specs/DEV_PROCESS_GUARDRAILS.md` 패턴 13(로컬 `ADMIN_EMAILS` 셸 환경변수)으로 한다.

## 구현 계획

`computeKpiWeeklyMetrics()`를 이번 주와 지난주 범위로 두 번 호출해 비교값을 만든다. D는 `user_shadow_bans`와 POI 차단 테이블의 개수를 조회한다(`/api/admin/abusing/*`의 조회 로직 재사용). C는 `/admin/strava-backfill`, D는 `/admin/abusing` 링크를 붙인다.

## 완료 조건

- 상단에 Strava 동기화 실패 건수, 제재 수, 차단 POI 수가 표시되고 각 운영 화면으로 이동하는 링크가 있다.
- 주간 핵심 지표가 이번 주 값과 지난주 대비 증감으로 표시되며 `/api/admin/kpi/weekly` 응답과 일치한다.
- 한 출처가 실패해도 나머지 수치는 표시된다.
- 증감·강조 판정 함수에 단위 테스트가 있다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- 어드민 메인 최상단에 「이상 신호」(Strava 동기화 실패 건수·유효 제재 수·차단 POI 수)와 「주간 핵심 지표」(미션 달성자 수·배지 발급량, 지난주 대비 증감)를 추가했다. 이상 신호 카드는 `/admin/strava-backfill`·`/admin/abusing`로 이동하며, 조회에 실패한 카드도 링크를 유지한다.
- 강조 판정은 `DashboardSignals.tsx`의 `ANOMALY_BASELINE = 0` 상수와 순수 함수 `buildWeeklyComparison(value, previousValue)`가 맡는다(0보다 크거나 지난주보다 늘면 강조).
- 주간 지표는 `computeKpiWeeklyMetrics()`를 이번 주·지난주 구간으로 한 번씩 호출한다. 지난주 구간은 `resolveKpiWeeklyRange(null, 7일 전 시각)`으로 만들어 새 함수를 두지 않았다.
- 유효 제재 수는 `expires_at`이 없거나 현재보다 뒤인 제재만 센다(`lib/abusing/shadow-ban.ts:34`의 만료 판정과 같은 기준). 차단 POI 수는 `blocked_until`이 현재보다 뒤인 행만 센다.
- 출처 4개(이번 주 집계·지난주 집계·유효 제재·차단 POI)를 각각 따로 감싸 하나가 실패해도 나머지는 표시한다.

### 주요 의사결정 / 핵심 메모
- 제재 수·차단 POI 수는 구현 계획 문구대로 지난주 비교 없이 현재 개수만 표시한다(아현 판단). 두 카드는 `previousValue`가 없어 강조 판정이 "0보다 큼"만 적용된다.
- 1차 게이트의 범위 밖 발견물 3건 처리:
  1. `[정확성/주의]` 제재 수가 만료된 제재까지 세어 이상 신호가 스스로 꺼지지 않음: 사용자가 머지 전 보완(A안)을 선택해 이 티켓에서 고쳤다. 라벨도 「유효 제재 수」로 바꿨다(어뷰징 화면 목록은 만료 제재를 포함하므로 숫자 차이로 인한 혼동 방지).
  2. `[정확성/주의]` 격리 워크트리에서 어드민 실렌더 불가: 티켓 20260924_1016(P2)으로 분리했다.
  3. `[정확성/참고]` 조회 실패 카드에서 운영 화면 링크가 사라짐: 1번과 같은 패치로 고쳤다.
- 보완 패치는 SKILL 3.1절 「게이트만 재실행」 절차로 처리했다(카리나가 임시 워크트리에서 2개 파일·10줄 패치, review 브랜치 push, `gateOnly`로 민지만 재판정).
- 머지 전 오염 검사(`merge-base --is-ancestor`)가 종료 코드 1로 실패했다. 원인은 브랜치 분기(67d2ce92) 뒤 staging에 들어온 커밋 10여 개이며, 일부는 `jam-web/` 코드(홈피드 카드·날씨 입력·노출 태그)를 바꿨다. 0909가 바꾼 파일·사용하는 함수와 겹치지 않고 `git merge-tree`에서 충돌이 없음을 확인한 뒤 그대로 머지했고, 머지 결과에 typecheck와 전체 테스트를 다시 돌렸다.
