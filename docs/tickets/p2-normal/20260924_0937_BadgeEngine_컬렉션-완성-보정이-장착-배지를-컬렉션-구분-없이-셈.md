# [BadgeEngine] 컬렉션 완성 보정 함수가 장착 배지를 컬렉션 구분 없이 세어 잘못된 완성·보상이 나갈 수 있다

## 핵심 요약

- 요구사항: 동기화 때 도는 컬렉션 완성 보정(`checkItemBookCompletion`)이 컬렉션별로 **그 컬렉션에 장착된 슬롯만**
  세도록 고친다. 장착 순간의 완성 판정 RPC(`mig/179`)와 기준을 맞춘다.
- 구현 계획: `filledBadgeIds`를 하나의 집합이 아니라 `item_book_id`별 집합으로 만든다. 두 판정 경로의 차이를 표로
  정리해 ④ 배지엔진 문서에 적는다.
- 관련 파일: `jam-web/src/lib/itembook/checker.ts:96-111`(장착 배지 집합), `:150-173`(북별 분자 계산),
  `jam-web/supabase/migrations/179_*.sql:96-143`(장착 RPC의 분모·분자), `docs/specs/badge-engine/`

### 파일 단위 계획 (규모 사전 판정, 2026-09-26)

`computeBookCompletion`은 화면 표시 쪽(`completable.ts:152`)도 쓰는 공용 함수라서 **기존 시그니처와 동작을 바꾸지 않고**
선택 옵션만 추가한다. `completable.ts`는 건드리지 않는다(표시 쪽 기준 정리는 티켓 20260921_1114·1129가 맡는다).

## 배경 / 문제 정의

상위 티켓 20260924_0916의 파일 지도 작성 중에 발견했다(2026-09-24).

- `checker.ts:96-111`은 유저의 슬롯을 `item_book_id`와 관계없이 `filledBadgeIds` 하나에 모은다. 북별 분자는 이
  집합과 그 북 소속 배지(분모)의 교집합으로 계산한다.
- 장착 RPC(`mig/179:118-143`)는 **그 컬렉션에 장착된** 슬롯만 센다.
- 평소에는 두 결과가 같다. 그러나 어드민이 배지의 컬렉션을 A에서 B로 바꾸면 달라진다. A에 장착된 배지가 B의
  분모에 들어가므로, 보정 함수는 B의 분자에도 그 배지를 센다. 그 결과 B의 완성 기록과 보상 배지가 나갈 수 있다.
- 보정 경로는 잼 포인트를 주지 않는다. 이후 장착 RPC는 완성 기록이 이미 있으면 아무것도 하지 않으므로, 이 유저는
  B의 완성 포인트를 끝내 받지 못한다.
- 한 번 만든 완성 기록과 보상은 배지를 되돌려도 회수되지 않는다.

지금은 배지 수정 폼에서 한 건씩 컬렉션을 바꿀 때만 일어난다. 상위 티켓의 "배지 컬렉션 일괄 지정"은 이 티켓이
끝날 때까지 보류한다.

## 완료 조건

- 배지 X가 컬렉션 A에 장착된 상태에서 X의 컬렉션을 B로 바꿔도, 보정 함수가 B의 분자에 X를 세지 않는다. 확인:
  `checker.ts`의 순수 계산부를 단위 테스트로 검증(A 장착 슬롯 + B 소속 배지 조합).
- 장착 RPC와 보정 함수의 분모·분자 기준 차이가 `docs/specs/badge-engine/`에 표로 적혀 있다.
- 이미 잘못 만들어진 완성 기록이 있는지 읽기 전용 쿼리로 점검한 결과를 완료 기록에 남긴다(정정은 별도 승인).

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- `computeBookCompletion`(`completion-basis.ts`)에 선택 옵션 `filledByBook`을 추가했다. 값이 있으면 각 북의 분자를 그 북의 집합으로만 세고(없는 북은 빈 집합), 값이 없으면 종전과 같이 `filledBadgeIds` 하나로 센다. 시그니처는 뒤에 옵션만 붙였고 표시 쪽 호출부(`completable.ts`)는 건드리지 않았다.
- `checker.ts`는 슬롯을 `item_book_id`별 집합에 담고, checkin 획득 이력은 그 배지가 속한 북(`poiBadgesByBook`)의 집합에만 넣는다. 완성 기록 upsert와 보상 발급 흐름은 그대로다.
- `docs/specs/badge-engine/BADGE_ENGINE_UNIFIED.md` §3.16-1에 장착 RPC(mig/179)와 보정 함수의 분모·분자 기준 비교표를 추가했다.
- DB 마이그레이션 없음.

### 주요 의사결정 / 핵심 메모
- **공용 함수는 시그니처를 유지하고 선택 옵션만 추가했다.** `computeBookCompletion`은 화면 표시 쪽도 쓰므로 기존 호출의 동작을 바꾸지 않기 위해서다. 표시 쪽 정리는 별도 티켓으로 분리한다.
- **계획 반환 면제.** 파일 4개·예상 약 95줄이라 100줄 기준에 걸려 있어, 티켓에 파일 단위 계획을 적고 첫 호출부터 `planOnlyWaiver`를 넘겼다. 실제 diff는 jam-web 76줄이었다.
- **게이트 WARN을 재작업 사유로 보지 않았다.** 우려는 `checker.ts`의 북별 집합 구성이 Supabase 호출과 한 함수에 섞여 자동 테스트가 없다는 점이고, 완료 조건은 "순수 계산부 단위 테스트"라 충족한다. 구성부 분리와 테스트는 후속 티켓으로 뺐다.
- **병합 방식.** 다른 세션이 공유 폴더에서 병합을 진행 중이라 카리나는 임시 워크트리에서 병합했다. 조상 검사는 분기 이후 staging에 커밋이 쌓여 실패했으나 브랜치에만 있는 커밋 2개가 모두 이 티켓 것이고 겹치는 파일이 없어 `--no-ff`로 합쳤다.
- **범위 밖 발견물(민지 [참고])** → P3 티켓 생성: 표시 쪽 `completable.ts`도 컬렉션별 집합으로 맞추기, `checker.ts` 북별 집합 구성의 순수 함수 분리와 테스트. 소프트 삭제 배지의 분모 처리 차이는 기존 티켓 20260921_1114·1129 소관이다.
- 이 티켓의 「후속」에 따라 "배지 컬렉션 일괄 지정(확인 문구 입력 + 영향 표시)" 티켓을 새로 만들었다.

### 잔여 이슈
- 표시 쪽(`completable.ts:152`)은 여전히 슬롯 집합 하나를 모든 북에 공통으로 쓴다. 컬렉션이 바뀐 배지가 있으면 보정 함수와 표시가 다른 완성 결과를 낼 수 있다(후속 티켓).
