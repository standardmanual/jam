# [Admin] 목록 공통화 ② 서버 일괄 처리 틀과 공용 서버 도구, 체크인 관리(POI) 목록 시범 적용

## 핵심 요약

- 요구사항: 모든 메뉴가 쓸 **서버 일괄 처리 틀**과 공용 서버 도구(정확한 건수 집계, 검색어 정제, 어드민 계정 판정)를 만들고,
  체크인 관리(POI, 2,451건) 목록을 ①의 부품과 이 틀로 옮겨 전체 흐름을 검증한다.
- 구현 계획: 아래 「구현 계획」의 파일 단위 목록. ①(티켓 20260924_0940)의 계약을 그대로 쓴다. 시범 적용 중 ①의 부품에 결함이
  보이면 이 티켓에서 고쳐도 된다(고친 내용을 완료 기록에 적는다).
- 관련 파일: `jam-web/src/app/admin/poi/page.tsx:11-45,70,107`, `jam-web/src/app/admin/poi/PoiFilters.tsx`,
  `jam-web/src/components/admin/poi/PoiTable.tsx:46-389`, `jam-web/src/lib/admin/poi-references.ts:5-8,229`,
  `jam-web/src/app/api/admin/poi/[id]/route.ts`, `jam-web/src/lib/admin/auth.ts:4-11`(어드민 이메일 판정),
  `jam-web/src/app/api/admin/users/search/route.ts:19`·`jam-web/src/app/api/admin/itembooks/search/route.ts:16`(검색어 정제 중복)

## 배경 / 문제 정의

- POI 목록의 일괄 처리(활성화·비활성화·카테고리 변경·삭제)는 단건 요청을 한 건씩 반복한다(`PoiTable.tsx:219-293`). 중간에
  실패하면 일부만 운영 DB에 남는다.
- PostgREST는 `.in()` 목록을 URL에 싣고 URL 상한은 16KB다(`jam-web/src/lib/notifications/batch/shared.ts:90-98`). 그래서 한
  문장으로 처리할 수 있는 ID는 약 200건까지다. POI(2,451건)와 배지(4,091건)만 200건을 넘을 수 있다.
- `collectPoiReferences`는 전체 합계만 돌려줘서, 삭제에서 막힌 항목만 골라 건너뛸 수 없다.
- 20260830_1620 이후 POI의 `is_active`는 체크인·드랍·앰비언트 드랍·지도에 연동된다. 그래서 비활성화는 유저에게 보이는 변경이다
  (상위 티켓 §3 등급 2).

## 상세 요구사항

### 서버 틀 (`jam-web/src/lib/admin/bulk/server.ts`)
- `readBulkRequest(req, { actions, idFormat = 'uuid' })`: `getAdminUser()`로 확인(아니면 403) → JSON 파싱 → ①의 `parseBulkBody`.
  반환값에 실행 어드민 `{ id, email }`을 포함한다(후속 티켓의 "본인 계정 제외"에 쓴다). `actions`는 동작별 `maxIds`를 받는다.
- `updateByIdsAllOrNothing(client, table, ids, patch)`:
  - 200건 이하: `.update(patch).in('id', ids).select('id')` 한 문장.
  - 200건 초과: 바꿀 칸의 현재 값을 먼저 저장 → 200건씩 반영 → 중간에 실패하면 이미 반영한 묶음을 저장한 값으로 되돌린다.
    되돌리기까지 실패하면 "일부만 반영"으로 보고한다. DB 함수(RPC)는 만들지 않는다(상위 티켓 결정).
  - 부수효과(드랍 무효화 등)가 있는 동작은 모든 묶음이 성공한 뒤에만 부수효과를 실행한다.
- `deleteByIds`: 200건씩 삭제. 한 묶음이 FK 위반으로 실패하면 그 묶음만 한 건씩 다시 시도하고, 실패분은 건너뜀으로 보고한다.
- `bulkJson(result)`: 표준 응답. 감사 기록은 `console.info` 한 줄(실행 어드민, 동작, 처리·건너뜀 수). 새 테이블은 만들지 않는다.

### 공용 서버 도구 (후속 티켓 ③~⑪이 쓴다)
- `jam-web/src/lib/admin/list-counts.ts` `countRowsByKey(client, table, keyColumn, ids, extraFilter?)`: ID를 200개씩 나눠 조회하고
  1,000행씩 끝까지 읽어 키별 건수를 정확히 센다. 1,000행 상한으로 건수가 잘리는 문제(트라이브·컬렉션·미션·아이템배지·유저
  화면)를 후속 티켓이 이 함수로 고친다.
- `jam-web/src/lib/admin/search-term.ts` `sanitizeSearchTerm(raw)`: PostgREST 필터 문법(쉼표·괄호)과 LIKE 와일드카드를 깨는 문자
  (`, ( ) % _ * \`)를 공백으로 바꾸고 100자로 자른다. 위 두 라우트의 인라인 정제를 이 함수로 바꾼다.
- `jam-web/src/lib/admin/auth.ts`: `isWhitelistedAdminEmail`을 export하고, `isAdminAccount({ email, is_admin })`을 추가한다
  (유저 일괄 처리의 어드민 자동 제외에 쓴다).

### POI 시범 적용
- 목록 쿼리 단일화 `jam-web/src/lib/admin/poi-list-query.ts`: `POI_LIST_COLUMNS`, `PoiListRow`, `parsePoiListParams`
  (`{ q, category, status, tier(1|2), linked('yes'|'no'), sort }`), `applyPoiListQuery`, `POI_EXPORT_COLUMNS`.
  목록 페이지·ID 조회·내보내기가 모두 이 모듈을 쓴다. 검색어는 `sanitizeSearchTerm`을 거친다. 정렬은 이름 오름·내림, 최근 등록순,
  오래된순이고 `id`를 보조 정렬로 붙인다.
- `jam-web/src/lib/admin/poi-bulk.ts`: `buildPoiCategoryPatch(cat)`(반경 정책이 있으면 `{ category, radius_meters }` — 단건 PATCH의
  `resolvePoiRadiusMeters`와 같은 결과), `classifyPoiDeletion`(참조가 하나라도 있거나 없는 ID면 건너뜀. 사유는 단건 DELETE 409와
  같은 형식).
- `jam-web/src/lib/admin/poi-references.ts` 229행 뒤 `collectPoiReferencesById`: `from('poi').select('id, name, poi_drops(count),
  user_checkin_badge_earns(count), poi_blocks(count), poi_views(count), user_activity_badges(count), custody_events(count)')`를
  80건씩. 조회가 하나라도 실패하면 삭제를 막는다. 임베디드 `(count)`는 저장소에서 처음 쓰는 방식이므로 로컬에서 읽기 전용으로
  형식을 확인한다. 안 되면 묶음 합계를 먼저 보고 참조가 있는 묶음만 반씩 나눠 찾는다. 5-8행의 낡은 주석을 고친다.
- API 3개:
  - `POST jam-web/src/app/api/admin/poi/bulk/route.ts`(`maxDuration` 60):
    - 활성화(등급 1): `{ is_active: true }`. `pending_review`는 건드리지 않는다(단건 PATCH와 같음).
    - 비활성화(등급 2): `dry_run`이면 `impact: { activeCount }`(선택 중 지금 활성인 POI 수)를 돌려준다.
    - 카테고리 변경(등급 1): `validatePoiCategoryExists` → `buildPoiCategoryPatch`.
    - 삭제(등급 3, `maxIds` 200): 참조 집계 → 분류 → `confirmPhraseFor('삭제', 삭제 가능 건수)`. `dry_run`이면 결과만, 실행이면 확인
      문구를 대조(다르면 409)한 뒤 `deleteByIds`.
  - `GET jam-web/src/app/api/admin/poi/ids/route.ts`: `requireAdmin` → `pickSingleQueryParamsFromURL` → 같은 쿼리 빌더로
    `select('id', { count: 'exact' }).range(0, 999)`. 전체가 1,000건을 넘으면 422와 안내 문구.
  - `POST jam-web/src/app/api/admin/poi/export/route.ts`: ID 목록 → 200건씩 조회 + 연결 배지 이름·카테고리 라벨 → `toCsv` →
    파일명 `poi_YYYYMMDD.csv`.

## 구현 계획

계획 반환 면제 사유: 신규 13개(소스 9·테스트 4)·수정 9개·삭제 1개, 약 +1,400/−450줄. 서버 틀은 첫 사용처(POI)와 함께 검증해야
계약 결함이 드러나므로 한 티켓으로 둔다. 파일 단위 계획은 위 「상세 요구사항」과 같다.

## 완료 조건

- `rg -n "for \(const id of" jam-web/src/components/admin/poi` 결과가 0건이고, 계약 테스트(소스 스캔)가 `PoiTable`에 단건 반복이
  없음을 고정한다.
- 단위 테스트:
  - `parsePoiListParams`, 기록형 스텁으로 필터별 쿼리 호출 검증(`jam-web/src/lib/notifications/__tests__/batch-query.test.ts` 방식)
  - `buildPoiCategoryPatch`가 모든 카테고리에서 `resolvePoiRadiusMeters`와 같은 결과
  - `classifyPoiDeletion`
  - `updateByIdsAllOrNothing`(스텁): 200건 이하는 1문장, 450건은 3묶음, 2번째 묶음이 실패하면 이전 값으로 되돌리는 호출이 나가고,
    되돌리기 실패도 보고한다
  - `countRowsByKey`(스텁): 1,000행을 넘는 결과를 끝까지 읽어 정확히 센다
  - `sanitizeSearchTerm`
- API를 로컬에서 직접 호출했을 때(쓰기 없음): 어드민이 아니면 403, ID 1,001건이면 400, 모르는 동작이면 400, 삭제 미리보기는
  `{ processed, skipped, dryRun, requiredPhrase }`를 돌려주고 POI 행 수는 그대로, 확인 문구 없는 삭제는 409.
- `GET /api/admin/poi/ids`의 건수가 같은 필터 목록의 "총 N개"와 같고, 필터가 없으면(2,451건) 422다.
- 로컬 실렌더(패턴 13, **저장하지 않고 읽기만**):
  - 머리 체크박스 → 안내 배너 → "모두 선택"을 누르면 바에 N건이 표시된다. 2쪽으로 넘겨도 선택이 유지되고, 필터를 바꾸면 1쪽으로
    가며 선택이 풀린다.
  - 행 빈 곳을 누르면 같은 탭에서 상세로 이동하고 로더가 없다. 체크박스·스위치를 눌러도 이동하지 않는다. 이름을 Cmd+클릭하면
    새 탭이 열린다.
  - 확인창은 열기만 하고 실행하지 않는다. 삭제 확인 버튼은 확인 문구가 일치할 때만 활성화된다.
  - 한 쪽 크기가 50이다. 내보낸 CSV를 엑셀에서 열면 한글이 정상이고 첫 줄이 머리글이다.
- 스위치 실패 시 복원은 브라우저 개발자 도구로 요청을 막아 확인한다(운영 DB에 쓰지 않음).
