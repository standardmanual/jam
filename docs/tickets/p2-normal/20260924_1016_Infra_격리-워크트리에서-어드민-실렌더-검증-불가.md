# [Infra] 격리 워크트리에서 next dev가 뜨지 않아 아현·민지가 어드민 실렌더 검증(패턴 13)을 할 수 없다

## 핵심 요약

- 요구사항: `docs/specs/DEV_PROCESS_GUARDRAILS.md` 패턴 13은 "로컬 `next dev`에서 어드민 실렌더 검증이 가능하다"고 적고 있다. 그런데 `/jam-work` 파이프라인의 격리 워크트리에서는 `next dev`가 두 번들러 모두 뜨지 않는다. 어드민 티켓의 실렌더를 누가, 언제, 어디서 하는지 정하고 그 절차를 한 곳에 적는다.
- 구현 계획: 아래 「구현 계획」의 대안 중 하나를 사용자와 정한 뒤 진행한다. 추천은 대안 A(현재 우회 절차를 공식 절차로 문서화)다.
- 관련 파일:
  - `docs/specs/DEV_PROCESS_GUARDRAILS.md` 패턴 13 (306줄 부근)
  - `.claude/skills/jam-work/references/handling-rules.md` 「어드민 화면 로컬 실렌더」 행 (46줄 부근)
  - `.claude/skills/jam-work/SKILL.md` 0.2절 유형 표의 `admin` 행
  - `.claude/workflows/jam-work.js` (아현·민지 프롬프트에 실렌더 지시가 들어가는 곳)
  - `scripts/workspace-setup.sh` `link_node_modules` (18줄 부근)
  - `jam-web/next.config.ts` `turbopack.root` (22줄 부근)

## 배경 / 문제 정의

티켓 20260924_0904와 0909에서 아현과 민지가 각각 명령을 실행해 같은 증상을 재현했다.

- Turbopack: `Symlink [project]/node_modules is invalid, it points out of the filesystem root`. `scripts/workspace-setup.sh link`가 워크트리의 `jam-web/node_modules`를 메인 폴더의 node_modules로 연결하는 심볼릭 링크로 만들고, `jam-web/next.config.ts`의 `turbopack.root`는 워크트리 안쪽을 가리킨다.
- webpack(`next dev --webpack`): 작업 폴더 이름 `JAM!`의 느낌표를 거부한다(`contains exclamation mark (!) which is not allowed`).

티켓 20260923_0100(같은 심볼릭 링크 때문에 npm install이 원본을 바꾸는 문제)과는 증상이 다르다.

0904에서는 카리나가 로컬 staging에 머지한 뒤, push하기 전에 메인 폴더에서 처리 규칙표의 방법(`launch.json` 임시 설정, 3100번 포트, 원복)으로 실렌더를 확인했다. 메인 폴더는 node_modules가 실제 폴더라 Turbopack이 정상적으로 뜬다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 패턴 13의 사실 서술("로컬에서 검증 가능")을 환경별로 정확하게 고친다. 확인된 사실만 적고, 판단과 한 문장에 섞지 않는다(CLAUDE.md 규칙 5).
- 같은 절차를 여러 문서에 옮겨 적지 않는다. 단일 원천을 정하고 나머지는 참조한다.

## 구현 계획

- **대안 A (추천)**: 어드민 티켓의 실렌더는 카리나가 "로컬 staging 머지 뒤, push 전"에 메인 폴더에서 한다고 패턴 13에 적는다. 아현·민지 프롬프트에서는 워크트리 실렌더 시도를 빼고 단위 테스트·CI로 검증하게 한다. 실렌더에서 문제가 나오면 push 전이므로 로컬 머지를 되돌린다. 코드 변경이 없다.
- **대안 B**: `turbopack.root`를 메인 저장소 루트까지 넓혀 워크트리에서도 Turbopack이 뜨게 한다. 번들 추적 범위가 바뀌므로 배포 번들 영향을 따로 검증해야 한다.
- **대안 D (2026-09-24 티켓 0907 머지 검증에서 확인)**: 원격 staging 기준 워크트리에 `jam-web/node_modules`를 심볼릭 링크가 아니라 복제본(`cp -Rc jam-web/node_modules <워크트리>/jam-web/node_modules`, APFS 복제)으로 두고 `scripts/workspace-setup.sh link-secrets <워크트리>`로 시크릿을 연결하면, 그 워크트리에서 `ADMIN_EMAILS=<dev-login 이메일> npm run dev -- -p 3100`이 떠서 `/admin` 실렌더가 된다(Turbopack, 오류 로그 없음). 메인 폴더 `.claude/launch.json`에 `cwd`가 그 워크트리인 임시 설정을 넣어 `preview_start`로 띄우고, 서버가 뜬 직후 원복했다. 아직 아현·민지 워크트리(`wf_*`)에서는 시도하지 않았다.
- **대안 C**: 어드민 티켓만 워크트리에서 `npm ci`로 실제 node_modules를 만든다. 설치 시간이 늘고, 느낌표 문제 때문에 webpack은 여전히 쓸 수 없다.

## 완료 조건

- 어드민 티켓의 실렌더 담당·시점·장소가 패턴 13 한 곳에 적혀 있고, 처리 규칙표와 jam-work 문서는 그곳을 참조한다.
- 대안 B·C를 택했다면: 격리 워크트리에서 `ADMIN_EMAILS=<dev-login 이메일> npm run dev`가 떠서 `/admin`이 렌더되는 것을 명령 실행으로 확인한 기록이 있다.

### 구현 내용 요약
- **대안 A를 채택했다**(2026-09-24 사용자 결정: "1016은 추천안대로 진행"). 어드민 티켓의 실렌더는 카리나가 게이트 통과 뒤 review 브랜치를 staging에 머지한 결과에서 push 전에 한다. 아현·민지는 격리 워크트리에서 실렌더를 시도하지 않고 단위 테스트·CI·diff 대조로 확인한다. 화면에서만 볼 수 있는 항목은 티켓 완료 조건에 「카리나 실렌더, 머지 뒤」로 적는다.
- 담당·시점·장소를 `docs/specs/DEV_PROCESS_GUARDRAILS.md` 패턴 13 「규칙」 한 곳에 적었다(단일 원천). 처리 규칙표 두 행, `SKILL.md`의 `admin` 행, 아현의 완료 점검표는 그곳을 참조한다. 민지·아현 정의에서 워크트리 실렌더를 시키던 지시를 바꿨다.
- 패턴 13의 "로컬 `next dev`에서는 실렌더 검증이 가능하다"는 문장에 조건(`node_modules`가 실제 폴더인 작업 폴더)을 붙여 사실을 정확히 했다.
- **장소는 추천안 원문의 "메인 폴더"에서 한 단계 넓혔다.** 메인 폴더의 로컬 staging을 병렬 세션이 함께 쓰는 것이 실제로 확인되어(티켓 0905 진행 중 미push 커밋 혼입), 병렬 세션이 있으면 원격 staging 기준 별도 워크트리에서 머지·검증하도록 적었다. 그 워크트리의 의존성은 링크가 아니라 복제본(`cp -Rc`)으로 둔다. 이 방식은 대안 D로 기록해 두었던 것이며, 티켓 0907·0908·0911에서 Turbopack 개발 서버가 뜨는 것을 확인했다. 대안 B(`turbopack.root` 변경)와 C(`npm ci`)는 채택하지 않았다.
