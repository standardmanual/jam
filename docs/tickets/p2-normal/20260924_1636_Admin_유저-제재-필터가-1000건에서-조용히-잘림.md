# [Admin] 유저 제재 필터가 user_shadow_bans를 1,000건까지만 읽어 조용히 틀린 결과를 낸다

## 핵심 요약

- 요구사항: 티켓 20260924_0951(⑩ 유저 조회) 게이트(민지)가 범위 밖 발견물로 남긴 항목을 검토하고, 필요한 것만 고친다.
- 구현 계획: 항목마다 고칠지 두고 볼지 판단한다. 고치지 않는 항목은 사유를 완료 기록에 적는다.
- 관련 파일: `jam-web/src/lib/admin/user-list.ts`

## 배경 / 문제 정의

어드민 목록 공통화 상위 티켓(20260924_0916)의 하위 티켓 ⑩ 유저 조회 게이트에서 나온 [주의] 항목이다(2026-09-24).

1. [주의/정합성] fetchActiveBanUserIds가 user_shadow_bans를 .limit(1000)으로 읽는다. 제재 행이 1,000건을 넘으면 제재 필터가 조용히 틀린 결과를 낸다. 주석은 조용히 틀리지 않는다고 적어 사실과 어긋난다. 실제로는 URL 상한 오류보다 먼저 잘린다 — jam-web/src/lib/admin/user-list.ts:fetchActiveBanUserIds

## 완료 조건

- 위 항목마다 (a) 고쳤고 확인 방법을 남겼거나, (b) 고치지 않기로 한 사유를 완료 기록에 적었다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- 묶음 티켓 20260926_1345로 처리했다. 상세와 실행 지표는 그 티켓의 완료 기록에 있다.
- `fetchActiveBanUserIds`(`user-list.ts`)가 읽은 행 수가 한도(`BAN_FETCH_LIMIT` = 1,000)에 닿으면 "제재 기록이 한도(1,000건)를 넘어 제재 필터를 신뢰할 수 없습니다" 오류를 던진다. 조용히 잘린 결과를 내던 것을 명시적 오류로 바꿨다. 사실과 어긋났던 옛 주석을 고치고, 제재 행이 수백 건에 가까워지면 필터를 재설계한다는 근거(제재 id를 `.in()`·`.not()`에 통째로 넣는 방식은 요청 주소 길이 한계가 먼저 온다)를 주석에 남겼다.
- **결정: 필터 구조 재설계는 하지 않았다.** 2026-09-26 조회로 `user_shadow_bans`는 0건이라 잠재 위험이다. 재설계 트리거용 후속 티켓을 만들었다.
