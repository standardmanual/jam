# [Infra] 에셋 제너레이터 공용 모듈 분리 — 곡선·스탬프·색 입히기·레이어 합성 (브라우저·서버 공용)

## 핵심 요약

- 요구사항: 프로토타입 HTML 안에 있는 그리기 로직을 브라우저(어드민 화면)와 서버(Node CLI) 양쪽에서 쓰는 공용 모듈로
  분리한다. 같은 입력·같은 시드면 두 환경에서 같은 결과가 나와야 한다. PRD §2-1·§11.
- 구현 계획: 아래 파일 단위 표. 캔버스 API에 의존하는 부분(그리기)과 의존하지 않는 부분(곡선·랜덤·시드)을 나눈다. 서버 렌더링용
  캔버스 라이브러리 선택은 **승인 항목**(아래 체크포인트).
- 관련 파일: `jam-doc/assets/prototypes/20260924_jam-asset-generator.html`(원본. `mulberry32`·`makeCandidate`·`unitCurve`·
  `sampleFitted`·`candidateStats`·`buildPath`·`posAt`·`buildStamp`·`drawScene`·`randomPalette`·전체 랜덤 규칙), 신규
  `jam-web/src/lib/asset-generator/`(아래 표), `docs/specs/prd/asset-generator/PRD.md`

## 배경 / 문제 정의

프로토타입은 단일 HTML 파일이라 어드민 화면과 에이전트 CLI가 같은 로직을 쓸 수 없다. 두 경로가 같은 엔진을 공유해야
"컨펌한 이미지 = 등록되는 이미지"가 보장되고, 시드 재현(PRD §11)도 성립한다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 순수 계산 모듈(캔버스 의존 없음): 시드 난수(`mulberry32`), 곡선 후보 생성·평가·선택, 곡선 샘플링과 호 길이 테이블, 위치·접선
  조회, 불규칙성 매핑(슬라이더 0~100 → 내부 0.6~1.5), 전체 랜덤 규칙(값 범위는 프로토타입 `randomBtn` 처리와 동일), 랜덤
  팔레트.
- 그리기 모듈(캔버스 추상화): 스탬프 생성(알파 영역에 그라데이션, 블러는 모양에만 적용한 뒤 색 입히기), 장면 그리기(리본 레이어),
  레이어 합성 훅(이미지·텍스트 레이어는 후속 티켓에서 이 훅에 얹는다). 캔버스 생성·이미지 로드는 주입받는다(브라우저: DOM 캔버스,
  서버: 캔버스 라이브러리).
- 프로토타입 HTML은 분리한 모듈을 불러와 기존과 동일하게 동작해야 한다(회귀 없음). `file://`로 열어도 되어야 하므로 번들 결과물
  하나를 프로토타입 옆에 두거나, 프로토타입 안에 모듈을 인라인으로 포함하는 빌드 스크립트를 둔다 — 방식은 아현이 정하되 프로토타입을
  손으로 두 벌 유지하지 않는다.
- 결정성: 같은 시드·같은 입력에서 브라우저와 서버 결과의 픽셀 차이는 블러·리샘플링 구현 차이에서 오는 미세 차이만 허용한다. 곡선
  좌표·스탬프 위치·회전은 완전히 같아야 한다(테스트로 확인).

## 완료 조건

### 구현 범위 (게이트 판정 대상)
- `jam-web/src/lib/asset-generator/` 아래 모듈이 생기고, 프로토타입 HTML이 그 모듈을 사용해 기존과 동일하게 동작한다(시드를 고정한
  같은 설정에서 곡선 좌표가 이전 프로토타입과 일치함을 테스트 또는 비교 스크립트로 보인다).
- 곡선 테스트가 통과한다: 같은 시드 → 같은 좌표, 화면 밖 길이 비율 15%±1%p, 슬라이더 0·100에서 최소 회전 반경이 짧은 변의 5% 이상.
- `shader-lab` 파일은 변경하지 않는다. `npm run lint`·`npm test`가 통과한다.

### 후속 범위 (담당: 카리나, 시점: 머지 뒤)
- 서버 캔버스 라이브러리 추가 승인 여부를 2201 착수 전에 결정한다.

- 프로토타입 HTML 안의 그리기 로직을 `jam-web/src/lib/asset-generator/`로 분리했다. 커밋 5c866eb8 하나, staging 병합 94317f87.

  - `render.ts`: `buildStamp`(알파 모양에만 블러를 적용한 뒤 그라데이션 색 입히기), `fillBackground`·`drawRibbonLayer`. 캔버스 팩토리·이미지 로더는 인터페이스로만 선언해 주입받는다. 서버 캔버스 라이브러리는 추가하지 않았다(승인 항목, 하위 티켓 2201).
  - `types.ts`: 리본·이미지·텍스트 레이어와 프리셋 타입(PRD §4·§5). 이미지·텍스트 레이어는 타입만 선언했다.
  - 프로토타입: `index.ts` 배럴을 esbuild로 IIFE 번들링한 옆 파일 `20260924_jam-asset-generator.core.js`(`window.AssetGeneratorCore`)를 `<script src>`로 불러온다. `file://`로 열어도 동작하고, 로직을 손으로 두 벌 유지하지 않는다. HTML은 899줄에서 674줄로 줄었다. 재생성: `node jam-web/scripts/asset-generator/build-prototype.mjs`.

### 주요 의사결정 / 핵심 메모
- 유형 `infra`(라이트 파이프라인, 아현 → 민지), 경로 ③ 표준. 채원①·②는 유형상 생략.
- 규모 사전 판정: 파일 6개·수백 줄로 `plan_only` 임계값을 넘겼으나, 티켓 「구현 계획」이 파일 단위(경로 + 옮길 함수명)로 적혀 있고 상위 티켓 2154의 기획서·분해안을 사용자가 2026-09-24에 승인했으므로 카리나가 첫 호출부터 `planOnlyWaiver`를 부여했다. 아현에게는 프로토타입 함수 위치 지도(줄 번호)를 `userRequest`로 전달했다(워크트리가 `origin/staging` 기준이라 티켓 로컬 수정은 보이지 않기 때문).
- 게이트 PASS. 근거: 구현 계획 표의 신규 파일 5개가 계획대로 생겼고 각 함수가 원본과 라인 단위로 동일, 테스트가 완료 조건과 1:1 대응, 변경 파일이 티켓 명시 목록과 정확히 일치, PRD §15 반영 확인. `render.ts`·`random.ts`는 별도 단위 테스트가 없으나 순수 이관이라 '새 동작 테스트' 요건에 해당하지 않는다고 판정.
- 아현 가정: (1) 레이어 합성 훅은 `fillBackground` → `drawRibbonLayer`를 호출자가 순서대로 부르는 최소 구조다. 후속 이미지·텍스트 레이어 티켓(2157·2158)이 그 뒤에 자체 그리기 함수를 덧붙이는 형태를 전제하며, 레지스트리·플러그인 구조는 만들지 않았다(스펙에 없는 선구현 방지). (2) 그라데이션 시작색을 배경색과 연결할지(PRD §6)는 호출자 책임으로 뒀다(`buildStamp`는 결정된 `startColor`만 받는다). (3) `random.ts`의 랜덤 함수는 기본값 `Math.random`을 쓰되 시드 주입도 가능하게 했다. 원본은 항상 `Math.random` 직접 호출이라 기본 동작은 같다. (4) `pickCandidate` 결과를 모듈 스코프에 캐시했다. 출력값에는 영향 없고 재호출 시 재계산만 줄인다.
- 프로토타입 번들 방식: 인라인 빌드가 아니라 옆 파일 `.core.js` + `<script src>`를 택했다(아현). HTML 본문과 생성 산출물이 분리되어 diff가 읽기 쉽다.
