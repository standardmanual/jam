# [Infra] 에셋 제너레이터 프로토타입 번들(.core.js)이 TS 원본과 어긋나면 verify.sh가 잡아내게 한다

> 티켓 20260924_2155 게이트 리뷰에서 민지가 낸 범위 밖 발견물(`[구조/주의]`)을 3.2절대로 자동 티켓화했다.

## 핵심 요약

- 요구사항: `jam-doc/assets/prototypes/20260924_jam-asset-generator.core.js`는 `jam-web/src/lib/asset-generator/*.ts`를
  esbuild로 묶은 수동 재생성 산출물이다. TS만 고치고 번들 재생성을 빠뜨려도 지금은 어떤 검사도 이를 잡지 못한다.
  `scripts/verify.sh`에 번들 최신성 검사를 넣어 어긋나면 실패하게 한다.
- 구현 계획: `build-prototype.mjs`에 `--check` 모드(임시 경로로 빌드 → 커밋된 `.core.js`와 바이트 비교 → 다르면 종료 코드 1)를
  추가하고, `verify.sh`의 `run_step` 목록에 한 줄 추가한다.
- 관련 파일: `jam-web/scripts/asset-generator/build-prototype.mjs`(`outfile` 정의 약 21줄, `build()` 호출 약 29~39줄 —
  `--check` 분기 추가), `scripts/verify.sh`(`run_step lint/typecheck/test/ds` 34~37줄 뒤에 `run_step asset-bundle …` 추가,
  107줄 통과 메시지에 항목명 추가)

## 배경 / 문제 정의

2155에서 프로토타입 HTML은 `<script src="./20260924_jam-asset-generator.core.js">`로 공용 모듈 번들을 불러오는 구조가 됐다.
번들은 `node jam-web/scripts/asset-generator/build-prototype.mjs`로 사람이 다시 만든다. 후속 하위 티켓(2156~2201)이
`curve.ts`·`render.ts`를 계속 고칠 예정이라, 재생성을 빠뜨리면 프로토타입이 옛 로직으로 조용히 남는다.

영향 범위는 프로토타입에 한정된다. 어드민 화면(2156)과 에이전트 CLI(2201)는 TS 모듈을 직접 불러오므로 번들 드리프트가
"컨펌한 이미지 = 등록되는 이미지" 보장을 직접 깨지는 않는다. 다만 프로토타입은 회귀 대조 기준이자 디자인 탐색 도구로 계속
쓰이므로 검사가 필요하다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `build-prototype.mjs --check`: 임시 파일로 빌드한 결과와 저장소의 `.core.js`를 비교한다. 다르면 "번들이 원본과 다릅니다.
  `node jam-web/scripts/asset-generator/build-prototype.mjs`를 실행하세요" 안내와 함께 종료 코드 1을 낸다.
- `scripts/verify.sh`: 기존 `run_step` 패턴대로 한 줄 추가한다. CI(`verify` 워크플로)와 pre-push가 같은 스크립트를 쓰므로
  별도 훅 수정은 필요 없다(확인 후 필요하면 기록).
- esbuild 출력이 환경에 따라 달라지지 않는지 확인한다(배너·`legalComments: 'none'`·고정 `target`이라 결정적이어야 함).
  달라지면 정규화 방법을 정한다.

## 구현 계획

1. `build-prototype.mjs`에 `--check` 인자 처리 추가(빌드 → 비교 → 종료 코드).
2. `scripts/verify.sh`에 `run_step asset-bundle node jam-web/scripts/asset-generator/build-prototype.mjs --check` 추가.
3. TS 한 줄을 고치고 번들을 재생성하지 않은 상태에서 `verify.sh`가 실패하는지, 재생성 뒤 통과하는지 확인한다.

## 완료 조건
- `jam-web/src/lib/asset-generator/random.ts`를 고치고 번들을 재생성하지 않으면 `scripts/verify.sh`가 `asset-bundle` 단계에서
  실패한다. 재생성 뒤에는 통과한다.
- 변경 없는 저장소에서 `verify.sh` 전체가 통과한다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- `build-prototype.mjs`에 `--check` 모드를 추가했다. 임시 디렉터리로 빌드한 결과를 저장소의 `.core.js`와 바이트 비교하고, 다르면
  안내 문구와 함께 종료 코드 1을 낸다. 일치하면 0. 인자 없이 실행하면 기존과 같이 번들을 재생성한다.
- `scripts/verify.sh`에 `run_step asset-bundle node scripts/asset-generator/build-prototype.mjs --check`를 `ds` 단계 뒤에 추가하고
  통과 메시지에 `asset-bundle`을 넣었다(`run_step`이 `jam-web`에서 실행하므로 경로는 `scripts/...`).
- **현재 커밋된 번들은 이미 TS 원본과 어긋나 있다.** `--check`가 첫 실행에서 종료 코드 1을 냈고, 임시 빌드와 diff한 결과 원본
  `index.ts`에 이후 추가된 `presetSerialize.ts`(PRESET_TARGET_TYPES·PRESET_TARGET_TYPE_LABELS·isPresetTargetType·serializePresetLayers·
  deserializePresetLayers)와 `random.ts`의 `deriveRibbonFromSeed`가 번들에 없다(번들이 오래됨). 요청대로 번들은 재생성해 커밋하지 않았다.
  따라서 이 브랜치의 `scripts/verify.sh`와 CI `verify`는 `asset-bundle` 단계에서 실패하는 것이 정상이다. 번들 재생성 커밋은 카리나 판단으로 별도 진행한다.

### 주요 의사결정 / 핵심 메모
- esbuild 출력이 결정적인지: 같은 환경에서 재생성 직후 `--check`가 통과했고, 배너·`legalComments: 'none'`·고정 `target`이라 환경 의존
  요소가 없다. CI(ubuntu, Node 24)에서의 결과는 push 후 실행으로 확인해야 한다(미확인).
- 별도 훅 수정은 필요 없다. `.githooks/pre-push`와 `.github/workflows/verify.yml`이 모두 `scripts/verify.sh`를 호출한다(`grep`으로 확인).
  `verify.yml`의 변경 범위 판별은 `jam-web/` 변경을 전체 검증으로 분류하므로 TS 원본 변경은 항상 이 검사를 탄다.
  다만 `jam-doc/`만 바뀐 push(번들 손편집)는 가벼운 검증 경로라 이 검사를 타지 않는다.
- 기준 방어 저촉: `scripts/verify.sh` 변경은 pre-push·CI가 막는 항목(eslint-disable·skip·max-warnings 등)에 해당하지 않는다.
  다만 드리프트 때문에 이 브랜치의 verify는 `asset-bundle` 실패로 끝난다(위 참조).

### 잔여 이슈
- 번들 재생성 후 커밋 필요(`node jam-web/scripts/asset-generator/build-prototype.mjs`). 프로토타입이 최신 프리셋 직렬화 모듈을 쓰는지 함께 확인할 것.
