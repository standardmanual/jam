# [Infra] `register-badge.mjs --undo`가 조용히 지우거나 끊는 관계까지 확인하도록 참조 검사를 넓힌다

> 티켓 20260924_2202 게이트 리뷰에서 민지가 낸 범위 밖 발견물을 3.2절대로 자동 티켓화했다. 카리나가 실제 스키마로 확인한 사실을 덧붙였다.

## 핵심 요약

- 요구사항: `--undo`는 배지 행을 지우기 전에 `user_activity_badges`·`inventory_items`·`poi_drops` 세 곳만 참조를 확인한다. 세 곳은 모두 삭제를 막는 관계(NO ACTION)라 DB가 이미 지켜 준다. 정작 조용히 번지는 관계는 확인하지 않는다. 실제 스키마 조회(2026-09-25, `pg_constraint`) 결과 `badges`를 참조하는 관계는 다음과 같다.
  - **연쇄 삭제(CASCADE)**: `user_checkin_badge_earns.badge_id`, `user_item_book_slots.badge_id` — 배지를 지우면 유저의 체크인 획득 기록과 컬렉션 슬롯 행이 경고 없이 함께 지워진다.
  - **연결 해제(SET NULL)**: `item_books.reward_badge_id`, `item_books.required_activity_badge_id`, `missions.gated_badge_id` — 컬렉션 보상·필요 배지와 미션 게이트 배지가 조용히 끊긴다.
  - **삭제 차단(NO ACTION)**: `inventory_items`, `poi.linked_badge_id`, `poi_drops`, `point_transactions.source_badge_id`, `user_activity_badges` — DB가 막아 주지만 `--undo`가 중간에 실패하면 저장소 파일만 남거나 반대가 될 수 있다.
  민지 보고에 있던 `combination_recipes`·`wandering_mythic_state`는 현재 `badges`를 가리키는 외래 키가 없다(후자는 2026-08-24 테이블 제거).
- 구현 계획: 참조 확인 대상 표를 위 표대로 확장하고(외래 키 이름을 코드에 박지 말고 목록 상수 한 곳에), 하나라도 붙어 있으면 어느 관계에 몇 건인지 보이며 중단한다. `--undo --dry-run`도 같은 검사를 보여 준다. 스키마가 바뀌어도 알아채도록 `information_schema`로 외래 키 목록과 상수 목록이 어긋나면 경고하는 것도 검토한다.
- 관련 파일: `jam-web/scripts/asset-generator/registerFlow.mjs`(참조 검사 상수 43줄, 되돌림 흐름 266줄 근처), `jam-web/scripts/asset-generator/__tests__/registerFlow.test.ts`, `docs/service/prd/asset-generator/REGISTRATION_BUNDLE.md`(되돌림 절)

## 완료 조건
- 연쇄 삭제·연결 해제 관계 5곳 중 하나라도 이 배지를 가리키는 행이 있으면 `--undo`가 지우기 전에 중단하고 관계와 건수를 보고한다(스텁 테스트).
- 어떤 참조도 없으면 기존처럼 배지 행과 파일 2개가 지워진다.
- `npm run lint`·`npm test` 통과.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- `registerFlow.mjs`의 `UNDO_REFERENCE_TABLES`를 표 이름 배열에서 `{ table, column, effect }` 목록 10곳으로 넓혔다(삭제 차단 5·연쇄 삭제 2·연결 해제 3). 외래 키 이름은 코드에 없고 이 상수 한 곳뿐이다.
- `undoRegistration`이 각 관계를 그 표의 배지 id 컬럼으로 센다(`select(column, { count, head })`). 하나라도 있으면 아무것도 지우지 않고 `표.컬럼 N건(효과)`를 모두 나열하며 중단한다. `--undo --dry-run`도 같은 검사를 거친다. 참조를 읽지 못해도 중단한다(기존과 같음).
- 참조가 없으면 기존처럼 배지 행 삭제 뒤 파일 2개를 지운다.
- SQL 기록의 되돌림 주석에 적는 표 이름은 상수에서 나오도록 `buildRegistrationSql`에 `undoTables` 인자를 추가했다(호출부가 상수에서 넘긴다. `registerRecord.mjs`가 `registerFlow.mjs`를 가져오면 순환이라 인자로 받는다).
- `docs/service/prd/asset-generator/REGISTRATION_BUNDLE.md` `--undo` 절을 10곳 표로 갱신했다.

### 주요 의사결정 / 핵심 메모
- 「스키마가 바뀌어도 알아채도록 `information_schema`로 대조」(검토 사항)는 채택하지 않고, 미션 등록이 쓰는 방식(생성 타입 `database.generated.ts` 대조 테스트)을 그대로 따랐다. 실행 시점에 DB를 더 읽지 않고, 마이그레이션 뒤 생성 타입을 재생성하면 테스트가 어긋남을 알려 준다(생성 타입 재생성은 이미 마이그레이션의 필수 절차). 한계: 생성 타입을 재생성하기 전에는 새 외래 키를 못 잡는다.
- 실제 스키마(`pg_constraint`)는 이 작업에서 조회하지 않았다(DB 접근 없음). 티켓에 적힌 2026-09-25 조회 결과 10곳과 생성 타입의 10곳이 일치함을 확인했다.
- 오류 문구를 `이미 사용자 데이터나 다른 항목의 연결이 붙어서 되돌리지 않고 중단했어요 — <표.컬럼 N건(효과)>, ...`로 바꿨다(연결 해제 관계는 «사용자 데이터»가 아니라서).

### 잔여 이슈
- `missions.reward_badge_ids`(uuid[] 컬럼)처럼 외래 키가 아닌 배열 참조는 이 검사 범위 밖이다(티켓의 관계 표에 없음).

## 종료 기록 (2026-09-26, 카리나)

- 묶음 실행(티켓 0540·0542·0549)이다. 병합 커밋 c8bc1efa. 사용자가 병합을 승인했다(2026-09-26). 게이트(민지) **WARN**, 재작업 없음.
- **WARN의 원인은 이 묶음이 아니다.** 브랜치 CI(`verify`)가 `asset-bundle` 단계에서 실패했는데, 민지가 기준 커밋에서도 같은 오류를 재현했다. 원인은 카리나가 묶음 B(0239, 프리셋 타입 통합)를 묶음 C의 번들 재생성 뒤에 병합해 생긴 staging의 번들 드리프트였다. 카리나가 번들을 재생성해 해소했다(`95f8708c`). 병합 뒤 `scripts/verify.sh` 전체(lint·typecheck·test·ds:check·asset-bundle·slop·scripts-test·contract 등)가 통과했다.
- 병합 전 오염 검사가 「조상 아님」으로 나왔으나 원인은 브랜치 기준(`a023a714`) 이후 카리나가 staging에 올린 커밋 2개(번들 재생성 `95f8708c`, 티켓 생성 `028fa5c9`)였다. 브랜치 고유 커밋은 예상한 5개뿐이었다.
- 스크립트 테스트 334건(14파일)이 통과한다(민지가 재실행). 전부 스텁이라 실제 DB·Storage에 쓰지 않았다.
- 후속 티켓 20260926_0120(미션·홈피드 등록 스크립트의 정규식 복제와 dry-run 요약 표기, OPEN, P3).
- 이 티켓의 판정: `UNDO_REFERENCE_TABLES`가 `{table, column, effect}` 10곳(삭제 차단 5·연쇄 삭제 2·연결 해제 3)이고, 하나라도 참조가 있으면 `표.컬럼 N건(효과)`를 모두 나열하며 삭제 전에 중단한다(`--undo --dry-run`도 같음). 참조가 없으면 기존처럼 행과 파일 2개를 삭제한다. 10개 관계 전부에 개별 중단 테스트가 있고 생성 타입의 `badges` 참조 FK 10곳과 대조하는 테스트도 있다. 문서 `REGISTRATION_BUNDLE.md` §7을 10곳 관계 표로 바꿨다.
- **한계**: 티켓의 「`information_schema` 대조 경고(검토)」는 런타임 DB 조회 대신 생성 타입 대조 테스트로 대체했다(검토 항목, 완료 조건 아님). 그래서 마이그레이션만 나가고 생성 타입을 재생성하지 않으면 새 외래 키를 놓친다. 실제 `pg_constraint`는 이번에 조회하지 않았다(아현이 티켓의 10곳 = 생성 타입의 10곳임을 확인).
- 이번에 `--undo`를 실제 DB에 실행해 보지는 않았다(스텁 테스트만).
