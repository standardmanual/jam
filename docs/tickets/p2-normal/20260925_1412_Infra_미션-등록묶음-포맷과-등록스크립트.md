# [Infra] 미션 등록 묶음 포맷과 등록 스크립트

> 상위 티켓 [20260925_1404](20260925_1404_Feature_에셋제너레이터-2차-미션컬렉션홈피드확장-윤진신규기획-상위.md)
> 하위 8번. 기획 경위·결정 기록·리스크는 상위 티켓 참고.

## 핵심 요약

- 요구사항: 윤진이 신규 미션 기획안(이름·설명·조건·보상 등 필드 + 이미지 + 시드)을 등록 묶음
  파일로 준비하고, 사용자 컨펌 뒤 메인 세션이 `register-mission.mjs`를 실행하면 미션 데이터와
  이미지가 함께 등록되는 흐름을 만든다. 배지의 `register-badge.mjs`/`REGISTRATION_BUNDLE.md`와
  같은 패턴이되, 필드는 미션 스키마(`mission_type`·`condition_json`·`reward_type` 등)에 맞춘다.
- 구현 계획: 등록 묶음 형식 문서(`MISSION_REGISTRATION_BUNDLE.md` 또는 `REGISTRATION_BUNDLE.md` 확장
  — 착수 시 아현·카리나가 최종 판단, 혜린 추천은 분리 신규 문서)를 정본으로 만든다.
  `register-mission.mjs`(`tsx`)가 묶음 검증 → 이미지 업로드(원본 PNG + WebP) → 미션 행 insert →
  등록 기록·되돌림 SQL 생성을 맡는다. `--dry-run`은 아무것도 쓰지 않고, `--undo`는 파일 2개와
  미션 행을 지운다. 어드민 미션 생성 API의 검증 함수(`checkMissionCondition`·
  `checkMissionConditionValue`·`findGateMissionSaveError` 등, 코드 확인 필요)를 재사용해 규칙이
  갈라지지 않게 한다.
- 관련 파일: `jam-web/scripts/asset-generator/register-badge.mjs`(참고 틀),
  `docs/service/prd/asset-generator/REGISTRATION_BUNDLE.md`(참고 틀),
  `jam-web/src/app/api/admin/missions/route.ts`(검증 함수 재사용 대상)

## 배경 / 문제 정의

상위 티켓 결정 6·8: 배지·미션·주간 홈피드는 윤진이 정기 산출물에서 신규 콘텐츠를 기획+이미지
생성해 제안하고, 사용자 컨펌 뒤 메인 세션이 등록한다(CLAUDE.md 6항). 미션은 필드가 배지와 크게
달라 별도 등록 스크립트가 필요하다.

## 결정 기록 (카리나, 2026-09-25 착수 시 판단)

이 티켓 「구현 계획」이 「착수 시 아현·카리나가 최종 판단」으로 위임한 두 가지를 정했다.

1. **형식 문서는 분리 신규 문서다**: `docs/service/prd/asset-generator/MISSION_REGISTRATION_BUNDLE.md`
   (혜린 추천 그대로). 1413의 `HOME_FEED_REGISTRATION_BUNDLE.md`와 이름 규칙을 맞춘다.
2. **배지 등록 스크립트는 건드리지 않는다.** 티켓 2202로 실제 등록·되돌림까지 검증된 자산이라, 미션용을
   위해 공통 모듈을 일반화하는 리팩터링은 하지 않는다. 배지 모듈에서 내용과 무관한 공통 부품은 **가져다
   쓰고(import), 미션 전용 부분만 새 파일로 만든다.** 유형별 중복은 남지만 기존 배지 등록이 깨질 위험이
   없다. 세 유형(배지·미션·홈피드)이 모두 생긴 뒤 공통화가 필요하면 별도 티켓으로 다룬다.

## 구현 계획 (파일 단위)

**수정 금지(읽기·import만 허용)**: `jam-web/scripts/asset-generator/register-badge.mjs`,
`registerArgs.mjs`, `registerBundle.mjs`, `registerFlow.mjs`, `registerRecord.mjs`와 그 테스트·픽스처.
재사용 후보(모두 기존 export): `parseRegisterArgs`(registerArgs), `UUID_PATTERN`·`AGENT_IMAGE_SOURCE`·
`readBundleFile`(registerBundle), `formatKst`·`toKstIso`·`sqlLiteral`·`migrationFileName`·
`RECORD_FILE_NAME`·`SQL_FILE_NAME`(registerRecord), `STORAGE_BUCKET`·`writeRegistrationFiles`
(registerFlow). 재사용이 어려우면(배지 전용으로 묶여 있으면) 그 부분만 새 파일에 미션용으로 쓴다.

신규 파일(예상 13~14개, 배지 선례 2202는 14개 파일·약 3,000줄 — 임계값 초과 확실 → `planOnlyWaiver` 부여):
1. `docs/service/prd/asset-generator/MISSION_REGISTRATION_BUNDLE.md`: 정본. 필드표·검증 규칙·실행 절차·
   되돌림. 문서 frontmatter(`type`·`description`)는 `docs/DOCUMENT_SCHEMA.md`를 따르고
   `docs/INDEX.md`는 배지 정본 추가 때와 같은 방식으로 갱신한다.
2. `jam-web/scripts/asset-generator/register-mission.mjs`: 진입점(`register-badge.mjs` 95줄에 대응).
   `@/` 별칭 때문에 cwd는 `jam-web`이고, 흐름 모듈은 동적 import로 불러 실패 시 안내 문구를 찍는다.
3. `registerMissionBundle.mjs`: 묶음 검증과 insert 페이로드. **어드민 미션 생성 API의 검증 3종을
   그대로 재사용한다**: `checkMissionCondition`·`checkMissionConditionValue`
   (`@/lib/missions/condition-keys`), `findGateMissionSaveError`(`@/lib/missions/gateMissions`) —
   `api/admin/missions/route.ts` POST(20~48행)와 같은 호출 순서. 필드는 `missions` 테이블 컬럼
   (`jam-web/src/types/database.generated.ts`의 missions Insert 타입)을 기준으로 필수·선택을 나눈다.
   `image_source`는 스크립트가 `'agent-generator'`로 직접 넣는다(묶음 값은 받지 않는다).
   1404 리스크 절에 따라 묶음에 「윈터 검수 여부·사유」 필드를 둔다(세계관 내용이 있을 때만 필수).
4. `registerMissionFlow.mjs`: `runRegister`·`runUndo`. 저장 경로는 적용 탭과 같은 규칙
   `missions/asset-generator/{missionId}.png|webp`(버킷은 `STORAGE_BUCKET`)이다. 되돌림 전 「사용자
   데이터가 붙었는지」 읽기 검사 대상 테이블(`UNDO_REFERENCE_TABLES` 대응)은 **`mission_id`를 가진 테이블을
   코드·타입에서 직접 찾아 정한다**(예: `user_mission_completions`. 추측하지 말고 확인한다).
5. `registerMissionRecord.mjs`: 등록 기록(`registration-record.json`)과 되돌림 SQL(`registration.sql`)의
   미션 필드판.
6. 픽스처 `__fixtures__/example-mission-bundle/bundle.json`·`image.png`.
7. 테스트 3개: `registerMissionBundle.test.ts`, `registerMissionFlow.test.ts`,
   `registerMissionRecord.test.ts`(배지 테스트의 검증 관점을 미션 필드에 맞게 옮긴다. 공통 부품 자체는
   다시 시험하지 않는다).
8. `docs/service/prd/asset-generator/PRD.md` §8·§14·§15에 미션 자동 경로를 반영한다(2202 때 갱신한 절).

배지 게이트에서 나온 보안 교훈을 처음부터 반영한다(티켓 2202 완료 기록 참조): 작성자·이름 등 문자열
필드의 **줄바꿈 거절**, 등록 기록 SQL 주석에 사용자 입력이 새지 않게 하기, UUID 정규식은 한 곳만 쓰기.

## 담당·실행 경계

- 아현은 스크립트·문서·테스트 작성까지만 한다. **실제 등록(`--dry-run` 없이)과 `--undo` 실행은 데이터
  변경이므로 사용자 승인 뒤 메인 세션이 한다.** 시험 등록은 배지 때(2202)처럼 비활성·임시 미션 1건으로
  하고 되돌림까지 확인한다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)
- `--dry-run`이 실제 쓰기 없이 검증만 수행하고 컨펌 자료로 쓸 수 있는 출력을 낸다(테스트로 고정).
- 등록 흐름이 미션 행 insert 페이로드에 `image_url`·`image_source='agent-generator'`를 넣고, 원본
  PNG+WebP 저장 경로가 `missions/asset-generator/{id}.png|webp`이다(주입한 가짜 supabase로 테스트).
- `--undo` 흐름이 미션 행과 파일 2개를 지우고, 사용자 데이터가 붙어 있으면 중단한다(테스트).
- 어드민 미션 생성 API와 같은 검증 3종(`checkMissionCondition`·`checkMissionConditionValue`·
  `findGateMissionSaveError`)을 거치고, 검증에 실패한 묶음은 등록되지 않는다(테스트).
- 배지 등록 스크립트 파일(`register-badge.mjs`·`registerArgs.mjs`·`registerBundle.mjs`·
  `registerFlow.mjs`·`registerRecord.mjs`)과 그 테스트가 변경되지 않았다.
- 정본 문서 `MISSION_REGISTRATION_BUNDLE.md`와 PRD 갱신이 반영되어 있다.
- `scripts/verify.sh` 통과.

### 후속 범위 (담당: 카리나, 시점: 머지 뒤, 데이터 변경이라 사용자 승인 필요)
- 임시·비활성 미션 1건으로 실제 등록해 `missions` 행 생성, 원본 PNG+WebP 업로드,
  `image_url`·`image_source='agent-generator'` 반영을 확인한다.
- `--undo`로 미션 행과 파일 2개가 지워지고 원상태로 복구되는지 실제로 확인한다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- 미션 등록 묶음 정본 `MISSION_REGISTRATION_BUNDLE.md`와 등록 스크립트 `register-mission.mjs`를 만들었다.
  흐름은 배지 등록과 같다: 묶음 검증 → 이미지 업로드(PNG+WebP) → 미션 행 insert → 등록 기록·되돌림 SQL.
- **배지 등록 스크립트 5개 파일과 그 테스트·픽스처는 수정하지 않았다**(base 대비 diff 0줄, 민지와 병합 후
  카리나가 각각 확인). 내용과 무관한 부품만 import했다(`parseRegisterArgs`, `UUID_PATTERN`,
  `AGENT_IMAGE_SOURCE`, `readBundleFile`, `findPreviousRecordError`, `RECORD_FILE_NAME`, `SQL_FILE_NAME`,
  `formatKst`, `toKstIso`, `sqlLiteral`, `STORAGE_BUCKET`, `writeRegistrationFiles`). 배지 전용 비공개
  부품은 미션 모듈에 다시 적었다.
- 어드민 미션 API의 검증 3종(`checkMissionCondition` → `checkMissionConditionValue` →
  `findGateMissionSaveError`)을 같은 순서로 재사용하고, 테스트가 라우트 소스의 호출 순서와 대조한다.
- `image_source`는 `agent-generator`로 고정한다(묶음에 넣으면 거절). 저장 경로는
  `missions/asset-generator/{id}.png|webp`이다.
- 묶음에 `world_review`(세계관과 닿는지·윈터 검수 여부·사유)를 필수로 두었다. 세계관 내용이 있는데 윈터
  검수를 거치지 않았으면 거절한다(상위 티켓 1404 리스크 절 반영).
- DB 읽기 검사: 제목 중복, 보상 배지 존재, 조건 배지 존재(`item_collect`), 조건 지점 존재(`checkin`).
- 되돌림 전 사용자 데이터 검사는 미션을 참조하는 6곳이다: `user_mission_completions`,
  `user_mission_participations`, `mission_rank_snapshots`, `point_transactions.source_mission_id`,
  `today_cards.mission_id`, `ranking_modes.target_mission_id`. 생성 타입의 `referencedRelation:
  "missions"` 외래 키 6건과 일치하며 그 대조를 테스트가 지킨다.

  홈피드)이 모두 생긴 뒤 공통화가 필요하면 별도 티켓으로 다룬다.
- 계획 반환 면제를 처음부터 부여했다(파일 단위 지도 작성, 신규 12개 + 수정 3개 파일, 약 2,400줄).
- 사용자 승인 2건(2026-09-25): 병합, 시험 등록·되돌림.
- 아현 가정: (1) `description`은 DB에서 nullable이나 화면 문구라 필수로 뒀다. (2) 폐기 예정 필드
  `reward_type`·`reward_id`·`gated_badge_id`는 받지 않고 null. (3) `status_display_type`·`exposure_mode`
  생략 시 `ranking`·`start_date`. (4) 시험 등록은 `exposure_mode: hidden`으로 노출을 막는다. (5) 묶음
  폴더 권장 위치는 `docs/assets/mission-bundles/<묶음 ID>/`.
