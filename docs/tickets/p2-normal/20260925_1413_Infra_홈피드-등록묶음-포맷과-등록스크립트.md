# [Infra] 홈피드 등록 묶음 포맷과 등록 스크립트

> 상위 티켓 [20260925_1404](20260925_1404_Feature_에셋제너레이터-2차-미션컬렉션홈피드확장-윤진신규기획-상위.md)
> 하위 9번. 기획 경위·결정 기록·리스크는 상위 티켓 참고.

## 핵심 요약

- 요구사항: 윤진이 신규 주간 홈피드 카드 기획안(템플릿·문구·노출기간 등 필드 + 이미지 + 시드)을
  등록 묶음 파일로 준비하고, 사용자 컨펌 뒤 메인 세션이 `register-home-feed-card.mjs`를 실행하면
  카드 데이터와 이미지가 함께 등록되는 흐름을 만든다. 기존 주간 편성(20260923_2252)의 seed SQL
  등록 경로와는 별개이며, 등록 기록 형식으로 두 경로가 구분되게 한다(상위 티켓 리스크: 홈피드
  등록 경로 이중화).
- 구현 계획: 등록 묶음 형식 문서(`HOME_FEED_REGISTRATION_BUNDLE.md`, 배지·미션과 같은 필드표·
  검증 규칙·실행 절차·되돌림 구조)를 정본으로 만든다. `register-home-feed-card.mjs`(`tsx`)가 묶음
  검증 → 이미지 업로드(원본 PNG + WebP) → `today_cards` 행 insert → 등록 기록·되돌림 SQL 생성을
  맡는다. `--dry-run`/`--undo` 지원. 어드민 `today_cards` 생성 API의 검증 함수를 재사용한다.
- 관련 파일: `jam-web/scripts/asset-generator/register-badge.mjs`(참고 틀),
  `docs/specs/prd/asset-generator/REGISTRATION_BUNDLE.md`(참고 틀),
  `jam-web/src/app/api/admin/today/route.ts`(검증 함수 재사용 대상),
  `docs/specs/prd/content-automation/PRD.md` §8-2(기존 seed SQL 경로, 각주 대상)

## 배경 / 문제 정의

상위 티켓 결정 6·7·8: 홈피드도 배지·미션과 같은 신규 기획+이미지 생성 패턴을 쓰되, 기존 컨텐츠
자동화 파이프라인(20260923_2252, 여전히 "기존 활성 컨텐츠 추천·편성" 전용)과는 통합하지 않는다.

## 결정 기록 (카리나, 2026-09-25 착수 시 판단)

티켓 1412(미션 등록 스크립트, 병합·시험 등록까지 완료)와 같은 방침을 적용하고, 코드를 읽어 확인한 홈피드
고유 사실을 반영한다.

1. **형식 문서는 분리 신규 문서**(`HOME_FEED_REGISTRATION_BUNDLE.md`)다. 미션 정본과 같은 구조로 쓴다.
2. **배지·미션 등록 스크립트는 건드리지 않는다.** 배지 5개 파일(`register-badge.mjs`·`registerArgs.mjs`·
   `registerBundle.mjs`·`registerFlow.mjs`·`registerRecord.mjs`)과 미션 4개 파일(`register-mission.mjs`·
   `registerMission{Bundle,Flow,Record}.mjs`)은 모두 검증이 끝난 자산이라 **수정 금지**다. 내용과 무관한
   부품은 가져다 쓰고(import) 홈피드 전용 부분만 새 파일로 만든다. 미션 모듈은 1412 게이트에서 다듬은
   보안 처리(줄바꿈 거절·SQL 주석 방어 등)의 참고 틀로 읽는다.
3. **검증 규칙의 원천 정정**: 티켓 「구현 계획」의 「어드민 `today_cards` 생성 API의 검증 함수를 재사용한다」는
   사실과 다르다. `api/admin/today/route.ts` POST는 본문을 검증 없이 insert한다(코드 확인). 검증 규칙은
   폼(`TodayCardForm.tsx`의 `collectMissing`: 제목 필수, 시작·종료 일시 필수, 노출조건 태그 1개 이상)과
   `jam-web/src/lib/admin/today-sections.ts`의 상수(`TODAY_TEMPLATE_OPTIONS`·`TODAY_LAYOUT_OPTIONS`·
   `TODAY_EXPOSURE_TAG_OPTIONS`·`TODAY_CONTENT_TYPE_OPTIONS`·`TODAY_FIELDS_FOR`)와 DB CHECK 제약
   (`template_type`·`layout_type`, 마이그레이션 048·049·158)에 있다. 스크립트는 **폼이 UI 컴포넌트라 직접
   가져올 수 없으므로 같은 규칙을 스크립트 쪽 순수 함수로 다시 쓰되, 허용값 목록은 `today-sections.ts`
   상수를 import해 갈라지지 않게 한다.** 폼 컴포넌트 파일은 수정하지 않는다.
4. **중복 검사는 「제목 + 시작 일시」 조합**이다. 카드는 날짜만 다르게 같은 제목을 재사용할 수 있어 제목만
   보면 정상 카드를 막는다. 같은 제목·같은 시작 일시 카드가 이미 있으면 거절한다. 동시 등록 경합은 티켓
   [20260925_2106](../p3-low/20260925_2106_Infra_등록-스크립트-제목-중복-검사의-동시-등록-경합.md) 결정 전까지 미션과
   같은 전제(단일 메인 세션 실행)를 정본에 명시한다.

## 구현 계획 (파일 단위)

홈피드 고유 사실(2026-09-25 코드로 확인): `today_cards` 생성 필수 필드는 `title`·`template_type`·
`starts_at`·`ends_at` 4개다. 선택 필드는 `subtitle`·`cover_image_url`·`badge_ids`·`mission_id`·
`item_book_id`·`region_label`·`body_markdown`·`ranking_mode_id`·`content_type_id`·`target_href`·
`exposure_tags`·`sort_order`·`is_active`·`layout_type`·`image_source`다(`database.generated.ts`
`today_cards` Insert). 이 테이블을 참조하는 외래 키는 생성 타입상 `today_card_events.card_id` 하나다.

신규 파일(예상 13~14개, 선례 1412가 15개 파일·약 2,400줄 — 임계값 초과 확실 → `planOnlyWaiver` 부여):
1. `docs/specs/prd/asset-generator/HOME_FEED_REGISTRATION_BUNDLE.md`: 정본(필드표·검증 규칙·실행 절차·
   되돌림). 문서 frontmatter는 `docs/specs/DOCUMENT_SCHEMA.md`, `docs/specs/INDEX.md` 갱신은 미션 정본
   추가 때와 같은 방식이다.
2. `jam-web/scripts/asset-generator/register-home-feed-card.mjs`: 진입점(`register-mission.mjs`에 대응).
3. `registerHomeFeedBundle.mjs`: 묶음 검증과 insert 페이로드. 이미지 컬럼은 `cover_image_url`(`image_url`
   아님), `image_source`는 스크립트가 `'agent-generator'`로 직접 넣는다(묶음 값은 받지 않는다). 위 결정 3의
   규칙(4개 필수 필드, 템플릿·레이아웃·노출 태그 허용값, 템플릿별 참조 필수 여부 `TODAY_FIELDS_FOR`, 노출
   태그 1개 이상, 시작<종료)을 검증한다. `world_review`(세계관과 닿는지·윈터 검수 여부·사유)를 미션과
   같은 규칙으로 필수로 둔다.
4. `registerHomeFeedFlow.mjs`: `runRegister`·`runUndo`. 저장 경로는 적용 탭과 같은 규칙
   `today_cards/asset-generator/{cardId}.png|webp`(버킷은 `STORAGE_BUCKET`)이다. DB 읽기 검사: 제목+시작
   일시 중복, 참조 필드가 있으면 그 행의 존재(`mission_id`→`missions`, `item_book_id`→`item_books`,
   `badge_ids`→`badges` 소프트 삭제 제외, `ranking_mode_id`→`ranking_modes`, `content_type_id` 허용값).
   되돌림 전 「사용자 데이터가 붙었는지」 검사 대상은 **`today_card_events.card_id`**이며, 삭제 규칙(CASCADE·
   NO ACTION 등)을 마이그레이션 183에서 직접 확인해 보고한다. 다른 테이블이 이 카드를 참조하는지 생성
   타입과 코드에서 한 번 더 확인한다.
5. `registerHomeFeedRecord.mjs`: 등록 기록과 되돌림 SQL의 홈피드 필드판. 기존 seed SQL 등록 경로와 구분되도록
   기록에 경로 표지(`image_source`)를 남긴다.
6. 픽스처 `__fixtures__/example-home-feed-bundle/bundle.json`·`image.png`.
7. 테스트 3개: `registerHomeFeedBundle.test.ts`, `registerHomeFeedFlow.test.ts`,
   `registerHomeFeedRecord.test.ts`(공통 부품은 다시 시험하지 않는다). 허용값 상수가 `today-sections.ts`와
   갈라지지 않는지 대조하는 테스트를 넣는다.
8. `docs/specs/prd/asset-generator/PRD.md` §8·§14·§15와 `docs/specs/prd/content-automation/PRD.md` §8-2
   각주(1411이 넣은 「1413 완성 후엔 `agent-generator`」 문구를 사실로 갱신)를 반영한다.

배지·미션 게이트에서 나온 보안 교훈(2202·1412)을 처음부터 반영한다: 작성자·제목·사유 등 문자열 필드의
**줄바꿈·제어 문자 거절**, 등록 기록 SQL 주석에 사용자 입력이 새지 않게 하기, UUID 정규식은 한 곳만 쓰기.

## 담당·실행 경계

- 아현은 스크립트·문서·테스트 작성까지만 한다. **실제 등록(`--dry-run` 없이)과 `--undo` 실행은 데이터
  변경이므로 사용자 승인 뒤 메인 세션이 한다.** 시험 등록은 미션 때처럼 **비활성(`is_active=false`)·기간
  2099년의 임시 카드 1건**으로 하고 되돌림까지 확인한다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)
- `--dry-run`이 실제 쓰기 없이 검증만 수행하고 컨펌 자료로 쓸 수 있는 출력을 낸다(테스트로 고정).
- 등록 흐름이 `today_cards` insert 페이로드에 `cover_image_url`·`image_source='agent-generator'`를 넣고, 원본
  PNG+WebP 저장 경로가 `today_cards/asset-generator/{id}.png|webp`이다(주입한 가짜 supabase로 테스트).
- `--undo` 흐름이 카드 행과 파일 2개를 지우고, 사용자 데이터(`today_card_events`)가 붙어 있으면 중단한다
  (테스트).
- 필수 필드·허용값 위반 묶음은 등록되지 않고, 허용값 상수가 `today-sections.ts`와 갈라지지 않는다(테스트).
- 기존 seed SQL 등록 카드(`image_source` NULL)와 이번 스크립트로 등록한 카드가 `image_source` 값으로
  구분된다.
- 배지·미션 등록 스크립트 파일 9개(위 「수정 금지」 목록)와 그 테스트가 변경되지 않았다.
- 정본 문서 `HOME_FEED_REGISTRATION_BUNDLE.md`, PRD 두 곳의 갱신이 반영되어 있다.
- `scripts/verify.sh` 통과.

### 후속 범위 (담당: 카리나, 시점: 머지 뒤, 데이터 변경이라 사용자 승인 필요)
- 서비스 키가 있는 환경에서 읽기 전용 `--dry-run`으로 DB 읽기 검사(중복·참조 행 존재)를 실제 DB로 확인한다.
- 비활성·2099년 임시 카드 1건을 실제 등록해 `today_cards` 행 생성, 원본 PNG+WebP 업로드,
  `cover_image_url`·`image_source='agent-generator'` 반영을 확인한다.
- `--undo`로 카드 행과 파일 2개가 지워지고 원상태로 복구되는지 실제로 확인한다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- 홈피드 카드 등록 묶음 정본 `HOME_FEED_REGISTRATION_BUNDLE.md`와 등록 스크립트
  `register-home-feed-card.mjs`(전용 모듈 3개: Bundle·Flow·Record)를 만들었다. 흐름은 미션 등록과 같다: 묶음 검증
  → 이미지 업로드(PNG+WebP, `today_cards/asset-generator/{id}.png|webp`) → `today_cards` insert
  (`cover_image_url`·`image_source='agent-generator'`) → 등록 기록·되돌림 SQL. `--dry-run`·`--undo` 지원.
- **배지·미션 등록 스크립트 9개 파일과 그 테스트, `TodayCardForm.tsx`, `today-sections.ts`는 수정하지 않았다**
  (병합 전 대비 diff 0줄, 민지와 병합 후 카리나가 각각 확인). 공통 부품만 import했다.
- **검증 규칙 원천 정정**: 티켓의 「생성 API의 검증 함수 재사용」은 사실과 달랐다(`api/admin/today/route.ts`
  POST는 검증 없이 insert). 규칙은 폼 `collectMissing`, `today-sections.ts` 상수, DB CHECK(마이그레이션
  158·183·190)에서 가져왔다. 허용값은 상수를 import하고, 상수와 DB CHECK를 대조하는 테스트가 갈라짐을 막는다.
- 중복 검사는 「제목 + 시작 일시」다(카드는 날짜만 달리해 같은 제목을 재사용할 수 있다).
- 묶음에 `world_review`(세계관과 닿는지·윈터 검수 여부·사유)를 필수로 두었다(1404 리스크 절 반영).
- 되돌림 전 사용자 데이터 검사: `today_card_events.card_id` 하나(생성 타입상 `today_cards`를 참조하는 외래 키는
  이것뿐이며 테스트로 고정). 삭제 규칙은 마이그레이션 183의 `ON DELETE SET NULL`이지만, 이벤트가 붙어 있으면
  이미 유저에게 나간 카드라 되돌림을 중단하는 보수적 동작을 택했다.
- **템플릿별 필수 참조 규칙(스크립트 자체 규칙)**: 템플릿이 쓰지 않는 참조 필드는 거절하고, 템플릿별 필수 참조
  (예: `mission_spotlight`→`mission_id`)가 비어 있으면 거절한다. 폼·DB에 없는 규칙이라 아현이 확인을
  요청했고 민지는 스펙 위반이 아니라고 판정했으며(정본 §3.3에 「스크립트 자체 규칙」으로 명시), **사용자가
  유지하기로 결정했다(2026-09-25)**.
- `content-automation/PRD.md` §8-2 각주를 「1413 완성 후엔 `agent-generator`」 예정 문구에서 사실 서술로 갱신했다.
