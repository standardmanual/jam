# [Admin] 에셋 제너레이터 기존 미션 대표 이미지 일괄 생성·적용 도구

## 핵심 요약

- 요구사항: 등록된 미션 55건(제목 42종)의 대표 이미지를 에셋 제너레이터의 「미션」 프리셋으로 일괄 생성해 적용한다. 프리셋 텍스트 3개 중 조건 문구와 미션 이름을 미션별로 채우고, 배경색·끝색은 미션 이름에 맞춰 지정하고, 나머지 리본 옵션은 어드민 「전체 무작위」와 같은 규칙(시드 기반)으로 정한다.
- 구현 계획: 이미 있는 렌더 엔진(`renderCardPng`)과 WebP 변환기(`convertBadgeImageToWebp`)를 그대로 쓴다. 막힌 두 곳만 얇게 잇는다. (1) `fillTextLayers`가 텍스트 레이어 3개 이상을 오류로 막는 규칙을 완화한다: 1번째 ← `--text`, 2번째 ← `--subtext`는 그대로, 3번째 이후는 프리셋에 저장된 글자를 그대로 둔다. (2) 기존 미션에 이미지를 적용하는 CLI 도구를 새로 만든다(어드민 적용 API와 같은 일). 미리보기(파일 저장만)와 실제 적용을 분리하고, 실제 적용은 사용자 승인 뒤에만 실행한다.

## 배경 / 문제 정의

미션 55건 중 54건은 대표 이미지가 없고, 1건(겹쳐진 도시의 새 얼굴)은 400px WebP라 화면에서 뭉개진다(티켓 20260926_2312에서 1280px로 통일). 어드민 적용 탭은 한 번에 한 미션만 처리하고 로그인한 화면에서만 동작해 55건을 일괄 처리할 수 없다.

기존 렌더 CLI(`render.mjs`)는 프리셋 ID·배경색·끝색·시드를 받고 나머지 리본 옵션을 어드민 「전체 무작위」와 같은 규칙(`deriveRibbonFromSeed`)으로 정하지만, 텍스트 레이어가 3개 이상인 프리셋은 오류로 막는다. 「미션」 프리셋은 텍스트 레이어가 3개(조건 문구 → 미션 이름 → 고정 라벨 MISSION, 배열 순서)다. 기존 CLI 등록(`register-mission.mjs`)은 새 미션을 만드는 용도라 기존 미션의 이미지를 바꾸지 못한다.

## 상세 요구사항

### 서비스/코드베이스 관점
- **텍스트 채우기**: 「미션」 프리셋(id `98562783-36c9-44aa-8fba-3c4793608f28`)의 텍스트 레이어 배열 순서는 1번째 조건 문구, 2번째 미션 이름, 3번째 `MISSION`이다. 도구는 조건 문구를 `text`, 미션 이름을 `subtext`로 넘긴다. 3번째(MISSION)는 프리셋에 저장된 글자 그대로다.
- **계획 파일**: 제목 기준 항목 목록이다. 각 항목은 `title`, `condition`, `bg`, `end`, `expectCount`(그 제목의 미션 수)를 가진다. 같은 제목의 미션이 여러 건이면 항목 하나가 여러 미션에 적용되고, 시드는 미션마다 따로 뽑는다(제목은 같아도 이미지는 다르다).
- **검증(아무것도 쓰기 전)**: 프리셋 id 형식, 색 형식(`#RRGGBB`), 문구 비어 있지 않음, 계획의 제목별 DB 미션 수가 `expectCount`와 같음(다르면 전체 중단), 배경색·끝색과 프리셋 텍스트 색의 대비 4.5:1 이상. 계획에 없는 미션이 DB에 있으면 알림만 한다.
- **미리보기(`--preview`, 기본)**: 미션마다 PNG를 `<out-dir>/<미션 id>.png`로 저장하고, 미션별 시드·색·문구·PNG 크기를 `<out-dir>/resolved.json`에 기록하고, 모든 이미지를 한 장에 모은 `<out-dir>/contact-sheet.png`를 만든다. DB·저장소에는 아무것도 쓰지 않는다. 텍스트가 스테이지 오른쪽 여백(가로 3%)을 넘는 이미지는 경고 목록에 올린다(텍스트 레이어만 빈 캔버스에 그려 알파를 검사).
- **적용(`--apply`)**: 같은 `<out-dir>`에 미리보기 결과(PNG·`resolved.json`)가 있어야 한다. 검토한 이미지 그대로 적용한다(다시 렌더하지 않는다). 쓰기 전에 모든 PNG 존재·5MB 이하·미션 존재를 먼저 확인한다. 미션마다 순서는 (1) 기존 이미지가 있으면 저장소의 기존 PNG·WebP를 `<out-dir>/backup/`에 내려받기 (2) 원본 PNG 업로드(`missions/asset-generator/{id}.png`, upsert) (3) 1280px WebP 업로드(`{id}.webp`, upsert) (4) `missions.image_url`을 WebP 공개 URL(`?v=<시각>`)로, `image_source`를 `agent-generator`로 갱신이다. 시작 전 미션별 이전 `image_url`·`image_source`를 `<out-dir>/applied.json`에 기록한다. 한 건이라도 실패하면 즉시 멈추고 진행 상황을 출력한다(이미 적용한 건은 `applied.json`에 남아 있다).
- **롤백(`--rollback <out-dir>/applied.json`)**: 미션마다 이전 `image_url`·`image_source`(null 포함)를 되돌리고, 백업해 둔 기존 저장소 파일이 있으면 다시 올려 이전 이미지 내용도 복구한다.
- **출력**: 표준 출력에 진행 상황(건수, 경고 목록)을 한국어로 찍고, 오류는 한국어 메시지와 종료 코드 1로 끝난다. 필요한 환경변수는 `render.mjs` 상단 주석과 같다(서비스 롤 키).
- `image_source`는 `agent-generator`로 남긴다(CLI가 만든 이미지라는 뜻, 목록·상세 라벨에 그대로 보인다). 이 값의 행은 CLI 등록 되돌리기(`registerMissionFlow.mjs` 288줄)가 삭제 대상으로 삼지만, 삭제는 등록 기록 파일에 그 미션 id가 있을 때만 일어나고 이번 미션들은 기록이 없다.
- 실제 적용은 프로덕션 DB·저장소에 쓴다(Supabase는 staging·프로덕션 공용). 이 티켓의 구현 범위는 **도구 작성과 테스트까지**이고, 실제 미리보기 실행과 적용은 머지 뒤 카리나가 사용자 승인 하에 실행한다(후속 범위).

### 문서 관점
- PRD §8에 규칙 변경(3개 이상: 1·2번째만 채우고 나머지는 저장된 글자 유지)과 새 도구의 사용법·안전 절차(미리보기 → 승인 → 적용 → 롤백)를 적는다. 이전 서술은 남기지 않는다.

## 구현 계획

1. `fillTextLayers.mjs`: 텍스트 레이어 3개 이상에서 오류를 던지지 않고, 2개와 같은 조건(`subtext` 필수)으로 1·2번째만 채운다. 3번째 이후 레이어는 그대로 통과시킨다. 주석·테스트·PRD 서술을 새 규칙으로 맞춘다.
2. `applyMissionImagesFlow.mjs`(+진입점 `apply-mission-images.mjs`): 위 요구사항의 검증·미리보기·적용·롤백을 함수로 나눠 구현한다. 렌더는 `renderCardPng`, 변환은 `convertBadgeImageToWebp`를 인자로 받는다. 시드는 `generateRandomSeed`(`assetGeneratorHelpers.ts`)로 뽑고 `resolved.json`에 기록한다.
3. 테스트(`applyMissionImagesFlow.test.ts`, 스텁 Supabase·스텁 렌더러): 계획 검증 오류(색 형식·대비·`expectCount` 불일치·빈 문구), 미리보기가 DB·저장소에 쓰지 않음, 적용 순서(백업 → PNG → WebP → 갱신)와 첫 실패 시 중단, 롤백 복구, 기존 이미지가 없는 미션의 처리.
4. PRD §8을 고치고 `git grep -nE "텍스트 레이어(가|는)? ?[0-9]개|3개 이상|최대 2개"`로 낡은 서술이 없는지 확인한다.
