# [Feature] 신규 가입자가 5분 안에 서비스를 직접 눌러 보며 파악하는 온보딩 퀘스트를 도입한다 (상위 티켓)

## 핵심 요약
- 요구사항: 신규 가입자에게 홈 상단 퀘스트 카드로 연출용 데이터 기반의 단계형 체험(동기화→배지→픽업→믹스 실패·성공→드랍→둘러보기)을 제공하고, 실제 첫 Strava 활동 1건 이상이 들어온 시점을 완료로 판정해 온보딩 완료 액티비티 배지(100P)를 지급한다.
- 구현 계획: 하위 티켓을 「작업 분해」 표의 선행 순서(N1 → N2 → N3 → T2c → N4 → T3 → T4 → T5 → T5b → T6 → T7a → T7b → T8 → N5 → T9)대로 `/jam-work`로 처리한다.
- 관련 파일: `jam-web/src/app/(main)/page.tsx`(L36-38 `strava_disconnected` 타일), `jam-web/src/lib/strava/sync.ts`(L1247 `isFirstSync`, L1264 첫 싱크 최신 1건 제한), `jam-web/src/lib/badge-engine/index.ts`(L1024, L1584 `initial_sync_done` 갱신), `docs/specs/prd/01_PRD.md` §2·§3, `docs/specs/prd/02_DATA_MODEL.md` §1·§2

## 배경 / 문제 정의
가입 직후 흐름은 아이디·이름 → 트라이브 선택 → Strava 동기화 → 첫 배지 알림에서 끝나고 그다음 안내가 없다(`docs/specs/prd/01_PRD.md` §2 시나리오 1). 신규 유저는 배지·포인트·드랍·픽업·믹스가 무엇인지, 무엇이 재미있는지 모른 채 막연한 상태가 된다. 게임 튜토리얼처럼 간단한 행동을 하나씩 직접 해 보게 하는 장치가 필요하다.

## 확정한 결정 (2026-09-27 사용자 문답, 혜린 기획)
1. **방식**: 코치마크(말풍선)·설명 팝업이 아니라 퀘스트 방식으로 하나씩 해 보게 한다.
2. **데이터**: 퀘스트 1~7단계는 전부 연출용 데이터로 진행한다(동기화 포함). 서버에는 단계 진행·완료만 기록한다. 실제 데이터를 만들면 비공개 레시피 폐지(2026-07-27)·드랍 무기한 유지(2026-08-29) 정책과 충돌하고, 배지 컬렉션 수·배지 트리·포인트 유통량 대사 집계가 오염되기 때문이다.
3. **목적**: 현실 행동 유도가 아니라 가입 후 5분 안에 이것저것 눌러 보며 서비스를 파악하게 하는 것. 집/밖 구분은 두지 않는다(POI는 어디서든 반경 500m 안에서 확인 가능).
4. **흐름**
   1. 연출용 Strava 동기화 → 연출용 첫 배지
   2. 가방을 열어 배지 확인
   3. 지도에서 가까운 POI의 연출용 드랍 픽업
   4. 아무 재료로 믹스 → **실패**, 투입한 아이템배지가 소각되는 장면(실제 규칙과 동일: `jam-doc/planning/content/COMBINE_RECIPES.md` L28·L84, 성공·실패와 무관하게 재료 소각)
   5. 레시피 확인 → 정확한 재료로 믹스 **성공**. 레시피는 슬롯 2개인 「살롱의 장물 시세」로 고정한다
   6. 믹스 결과물을 POI에 드랍
   7. 미션 목록 또는 트라이브 화면 한 번 열기
   8. 기존 홈의 Strava 미연동 타일(첫 동기화 카드)로 이어져 **실제** 연동
5. **완료 판정**: 실제 첫 동기화로 활동이 **1건 이상 실제로 들어온 시점**. Strava 계정이 없거나 활동이 0건이면 미완료 상태로 남고 카드도 계속 노출된다. `users.initial_sync_done`은 활동 0건이어도 true가 되므로 판정 근거로 쓰지 않는다.
6. **보상**: 온보딩 완료 전용 액티비티 배지 1종(실제 데이터) + 100P. 완료 판정 시점에 지급한다. 100P는 시뮬레이터 미검증이다(계정당 1회).
7. **노출**: 완료할 때까지 홈 상단 카드로 계속 노출한다. 투데이 CMS(`today_cards`) 항목이 아니라 앱에서 유저별로 그리는 컴포넌트다.
8. **건너뛰기**: 허용한다. "이 순간을 넘기면 받을 수 없는 것이 있다"는 뉘앙스로 [계속하기]/[건너뛰기]를 선택하게 한다. 건너뛰면 곧바로 실제 동기화 카드로 넘어가고 완료 배지는 **영구히** 받을 수 없다(재도전 경로 없음).
9. **대상**: 배포 이후 가입한 신규 유저만. 기존 유저에게는 노출하지 않고 소급 지급도 하지 않는다.
10. **문구·세계관**: 중립 톤. 트라이브 목소리는 다음 버전으로 미룬다. 윈터 검수는 신규 완료 배지 이름·설명에만 필요하다.
11. **실제 동기화 지연 안내**: 연출 동기화(즉시)와 실제 동기화(최대 60초)의 차이는 따로 안내하지 않는다.

## 추가 결정 (2026-09-27 구현 착수 후)
12. **진행 방식 A**: 단계는 퀘스트 전용 화면 `/onboarding-quest`에서 진행하고, 실제 서비스의 화면 부품을 연출용 데이터로 재사용한다. 실제 동기화 버튼·인벤토리·지도·믹서 페이지에는 퀘스트 분기를 넣지 않는다. 미채택 B(실제 화면에 연출 분기)는 핵심 화면 네 곳에 분기가 생겨 연출 데이터가 실제 화면에 새어 나갈 위험과 티켓 수 증가 때문에 기각.
13. **홈부터 연출 화면**: 퀘스트 진행 중인 신규 유저의 홈은 연출용 홈이다(실제 홈과 같은 구성에 연출 데이터, 투데이 카드는 실제 컨텐츠). 7단계를 마치거나 건너뛰면 실제 홈으로 바뀐다(T2c). 미채택 (b) 퀘스트 카드만 있는 단순 홈.

## 결정 번복 (2026-09-28 사용자)
결정 12(진행 방식 A)와 13(연출용 홈)을 폐기한다. 사유: 퀘스트 전용 화면은 서비스에 없는 페이지라서, 그 화면을 눌러 봐도 실제 서비스를 익히는 온보딩이 되지 않는다.

14. **실제 메뉴 화면에서 진행**: 각 단계는 해당 기능의 실제 메뉴 화면으로 보내 그 화면의 UI 그대로 진행한다. 예: 인벤토리에 추가하는 단계는 실제 인벤토리 메뉴 UI, 드랍 단계는 가상의 지도 이미지 위에 드랍할 POI를 표시한다.
15. **데이터는 연출용 유지**: 결정 2는 그대로다. 실제 화면에 연출용 데이터를 채우고 DB에는 단계 진행만 기록한다.
16. **별도 화면 제거**: `/onboarding-quest`와 관리자 미리보기 `/onboarding-quest/preview`(T2a·T2b·P에서 staging 머지)는 제거한다. 1~2단계 연출 부품(배지 획득 연출·연출 도토리)은 실제 화면으로 옮긴다.
17. **홈**: 새 홈을 만들지 않는다. 퀘스트 중에는 실제 홈의 동기화 버튼이 1단계 연출 동기화로 동작한다(T2c를 이 작업으로 바꾼다, 사용자 선택 없음 → 카리나 추천안).

## 추가 결정 (2026-09-28 사용자, 결정 14~17 실행 반영)
18. **단계와 실제 화면의 대응**: `sync`=홈(`jam-web/src/app/(main)/page.tsx`의 동기화 버튼, 홈에서만 연출), `bag`=`/inventory`, `pickup`·`drop`=`/drops`(가상 지도 이미지), `mix_fail`·`mix_success`=`/combine`, `browse`=`/missions`만 인정(저장소에 전용 트라이브 화면이 없다).
19. **문지기 함수 하나**: 퀘스트 판정은 문지기 함수 하나(`jam-web/src/lib/onboarding-quest/screen-gate.ts`, 신규)로만 한다. 단계→화면 지도와 "지금 이 화면이 차례인가" 판정을 담는다. 차례가 아니면 null을 돌려주고 화면은 평소 실제 화면 그대로다. 연출 데이터는 클라이언트 전용 상수(`demo-data.ts`)이고, 연출 아이템을 눌러도 실제 API(동기화·픽업·믹스)를 부르지 않고 단계 기록 API `POST /api/onboarding-quest/step`만 부른다.
20. **자동 이동 없음**: 단계를 마치면 홈으로 돌아가고, 홈 퀘스트 카드의 [이어 하기]로 다음 실제 화면에 들어간다.
21. **정적 가상 지도**: 3·6단계 지도는 `/drops` 화면 안의 정적 가상 지도 이미지와 누를 수 있는 POI 하나로 보여 준다(실제 인터랙티브 지도에 마커를 얹는 방식은 쓰지 않는다).
22. **차례가 아니면 평소 화면**: 퀘스트 중에 차례가 아닌 실제 화면에 들어가면 연출 없이 평소 화면을 보여 준다. 차단하거나 안내하지 않는다.

23. **4단계 실패 체험 폐기 (2026-09-28 사용자, T4)**: 실제 `/combine`은 레시피 선택형이라 슬롯마다 후보 배지만 넣을 수 있어 틀린 재료로 실패하는 일이 구조적으로 없다. 결정 4-4의 "믹스 실패·소각 장면"을 폐기하고, 4단계(`mix_fail` 키는 이름만 유지)는 레시피 「살롱의 장물 시세」의 슬롯·필요 재료·소각 안내를 확인하는 단계로 바꾼다. 소각은 5단계 성공 때 재료가 사라지는 장면으로 전달한다. 4단계는 믹서에서 슬롯을 눌러 가방을 처음 연 시점에 완료되고, 4·5단계는 같은 화면에서 이어 간 뒤 5단계 결과를 닫으면 홈으로 간다(결정 20의 예외). 상세는 티켓 `20260927_2127`.
24. **건너뛴 유저도 완료 시각 기록 (2026-09-28 사용자, T6)**: 건너뛴 유저도 실제 첫 활동이 들어오면 `completed_at`을 기록한다(컬럼 정의 "실제 첫 활동 유입 시각"과 참고 지표 비교용). 보상 제외는 T7이 `skipped_at`으로 판정한다. 상세는 티켓 `20260927_2129`.
25. **연출 도중 연동은 마친 순간 완료 (2026-09-28 사용자, T6)**: 7단계를 마치기 전에 들어온 활동으로는 완료를 기록하지 않는다(기록하면 홈 퀘스트 카드가 사라져 남은 단계를 못 한다). 7단계(`browse`) 기록 직후, 그리고 건너뛰기 기록 직후(T8)에 이미 처리된 활동이 있으면 그 자리에서 완료를 기록한다. 자동 동기화 Cron은 존재하지 않아 완료 판정 경로는 연동 직후 첫 동기화와 수동 동기화 두 개다.
26. **완료 보상 표시는 `mission_reward` 재사용, T7 분할 (2026-09-28 사용자, T7)**: 새 플래그(`onboarding_reward`) 대신 기존 `mission_reward`로 자동 발급을 막는다. 대가로 배지 상세 문구가 「'<이름>' 미션을 완료하면 받을 수 있는 배지예요.」로 고정되고 어드민에 「미션 보상」 칩이 보인다(온보딩 구분은 `admin_category = 'jam'`과 이름). T7은 T7a(`20260928_1212`, 배지 행·문서)와 T7b(`20260927_2130`, 지급 로직)로 나눈다. 대표 이미지는 행 등록 후 사용자가 어드민 이미지 생성기로 만든다. 7단계 경로의 지급 표시 방식은 T7b 채원 판정에 맡긴다.

하위 티켓은 N1~N5(신규)·T2c~T9(수정)로 재분해한다. 상세는 「작업 분해」 표 참조.

## 검토한 대안과 미채택 이유
- **코치마크·설명 팝업**: 사용자가 명시적으로 배제했다. 읽게 하는 것보다 직접 해 보게 하는 편이 드랍·픽업·믹스를 빨리 이해시킨다.
- **실제 서비스 위에 나에게만 보이는 드랍·레시피를 얹는 혼합안**: 비공개 레시피 폐지·드랍 회수 없음 정책을 되돌리고, 퀘스트 아이템이 여러 집계에 섞여 제외 처리가 필요해 기각.
- **화면 전체를 복제한 완전 샌드박스**: 화면 이중 관리와 드리프트 때문에 기각. 실제 화면에 연출용 데이터를 채우는 방식으로 대체.
- **미션 테이블 재사용**: 미션은 배지엔진이 활동 데이터 조건만 판정하고 참가 필수·취소 불가라, "기능을 한 번 써 봤는지"를 기록하고 건너뛸 수 있어야 하는 온보딩과 맞지 않아 기각.
- **집/밖 두 챕터 구성**: POI 확인은 어디서든 가능하고 목적이 현실 행동 유도가 아니라서 기각.
- **기존 유저 소급 적용**: 이미 실제 배지·아이템이 있는 유저를 연출용 세계로 되돌리는 흐름이 어색하고 소급 보상 문제가 생겨 기각.
- **건너뛴 유저의 재도전 경로**: "다시 받을 수 없다"는 안내를 거짓으로 만들어 기각.
- **트라이브 목소리 문구·온보딩 전용 신규 아이템**: 세계관 검수 사이클이 늘고, 기존 아이템을 빌려 써야 실제 서비스로 체험이 이어져 기각(다음 버전 후보).

## 세션 인수인계 (2026-09-28, T4~T6 세션 → 다음 세션)
- **다음 작업: T7(`20260927_2130`, 완료 배지 + 100P 지급).** DB 변경(배지 행 등록 SQL은 아현이 작성만, 실행은 사용자 승인 후 메인 세션)과 윈터의 이름·설명 검수가 필요하다. 채원 판정은 "첫 배지 획득 알림에 포함하는 표시 방식"에만 걸린다.
- **T7 착수 전 확인할 것**
  - 규모: 배지 등록 SQL + 엔진 제외 처리(`condition_json` 보상 전용 플래그, `CONDITION_JSON_SPEC.md` L352 `mission_reward` 선례) + 지급 로직 + 문서 2종(`CONDITION_JSON_SPEC.md`·`BADGE_ENGINE_UNIFIED.md`) + 컨텐츠 문서(`ACTIVITY_BADGES.md`)라 plan_only 임계를 넘을 가능성이 높다. 착수 전에 쪼개거나(예: 윈터 검수+SQL / 엔진 제외 / 지급 연결) 파일 단위 계획을 적고 면제를 넘긴다. `engine` 유형이 섞이므로 민지는 시뮬레이터 결과를 근거로 판정한다.
  - 지급 연결 지점: T6의 `recordOnboardingQuestCompletion`(`jam-web/src/lib/onboarding-quest/completion.ts`)이 `completed_at`을 `.is('completed_at', null)` 조건으로 갱신한다. 이 갱신이 실제로 행을 바꾼 최초 1회에만, 그리고 `skipped_at`이 없을 때만 지급하고 `reward_granted_at`으로 멱등을 보장한다. 호출 지점이 동기화(`sync.ts`)와 단계 기록 API(`browse`) 두 곳이므로, 동기화 경로에서는 지급 배지를 `earnedBadges` 알림에 싣는 방법을, 단계 기록 경로에서는 알림을 어떻게 보여 줄지를 함께 정해야 한다.
- **T8(`20260927_2131`)**: 건너뛰기 기록 직후 `recordOnboardingQuestCompletion` 호출 요구사항이 이미 추가돼 있다(결정 25).
- **staging 실화면 확인 대기(사용자, 기능 스위치를 켠 테스트 계정)**: T4 믹스 연출, T5 드랍 연출(드랍 후 카드가 1~2초 이상 남는지), T5b `/missions` 진입 기록, T6 완료 판정(활동 0건·활동 있음·도중 연동 후 7단계 완료).
- **보류 중인 판단**: T5b에서 `/missions` 문지기 조회가 기존 `Promise.all`보다 먼저 순차 실행돼 스위치가 켜지면 진입마다 DB 왕복이 1회 늘어난다. 별도 티켓화 여부는 사용자 판단 대기(티켓 `20260928_0139` 잔여 이슈).
- **이 세션의 운영 교훈**: 매 티켓 착수 전에 카리나가 실제 코드를 먼저 확인해 티켓과 코드의 어긋남(T4 구조 불일치, T6 없는 Cron·충돌 문구)을 찾고, 결정·파일 단위 계획을 티켓에 적어 staging에 먼저 올린 뒤 계획 반환 면제와 함께 Workflow를 호출했다. 네 티켓 모두 재작업 없이 1회에 끝났다.
