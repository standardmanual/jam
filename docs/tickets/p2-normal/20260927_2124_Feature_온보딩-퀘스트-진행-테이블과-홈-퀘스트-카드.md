# [Feature] 온보딩 퀘스트 진행 상태를 유저별로 저장하고 홈 상단에 퀘스트 카드를 띄운다 (T1)

## 핵심 요약
- 요구사항: 신규 진행 테이블(유저당 1행: 단계별 완료 시각, 건너뛰기 시각, 완료 시각, 보상 지급 시각)과 홈 맨 위 퀘스트 카드. 대상은 기능 배포 이후 가입한 유저만.
- 구현 계획: 마이그레이션 SQL 작성(실행은 메인 세션) → 서버에서 진행 상태 조회 → 홈 상단에 앱 전용 카드 렌더.
- 관련 파일: `jam-web/src/app/(main)/page.tsx`(L15 `HomePage`, L25-38 Strava 연결 조회·`leftStatus`), `jam-web/supabase/migrations/`, `docs/specs/prd/02_DATA_MODEL.md` §1

## 배경 / 문제 정의
온보딩 퀘스트의 진행을 기기와 무관하게 이어 가려면 서버에 유저 단위 진행 상태가 필요하고, 완료 전까지 홈 상단에 카드가 보여야 한다. 기획 전문과 결정 이력은 상위 티켓 `20260927_2123`에 있다.

## 상세 요구사항
- 공통 원칙: 1~7단계는 연출용 데이터다. `inventory_items`·`poi_drops`·`badges`·`user_activity_badges`·`point_transactions`에 행을 만들지 않는다. 서버에는 T1의 진행 테이블에 단계 완료만 기록한다.
- 연출용 아이템·레시피는 실제 카탈로그의 기존 아이템·레시피(이름·이미지)를 빌려 쓴다. 안내 문구는 중립 톤이며 코치마크·설명 팝업은 쓰지 않는다.
- 신규 테이블(예: `user_onboarding_quests`)을 만든다. 유저당 1행이며, 단계별 완료 시각, 건너뛰기 시각, 퀘스트 완료 시각, 보상 지급 시각을 담는다. RLS는 본인 행 조회만 허용하고, 쓰기는 서버 경로로 제한한다.
- 대상 판정: 기능 배포 이후 가입한 유저만 행을 가진다(기존 유저는 행이 없고 카드도 없다). 판정 방법(가입 시각 기준 또는 온보딩 2단계 완료 시 행 생성)은 구현 계획에서 정한다.
- 홈 카드: `today_cards` CMS가 아니라 앱 컴포넌트다. 완료하거나 건너뛸 때까지 홈 맨 위에 유지하고 진행도(예: 3/7)를 보여 준다. 건너뛴 뒤 또는 7단계 완료 뒤에는 실제 연동 단계(T6)를 가리킨다.
- DB 규칙: 마이그레이션 파일은 `jam-web/supabase/migrations/`에 남기고, 되돌림 SQL을 함께 적는다(`.claude/skills/jam-work/references/db-migration-rules.md`). 실행은 사용자 승인 후 메인 세션만 한다.

## 구현 계획
채원 사전 판정(신규 홈 카드, 기존 컴포넌트 재사용 여부) → 마이그레이션 SQL 작성 → 승인 후 실행 → 조회 함수와 카드 구현.

## 완료 조건
- 배포 이후 가입한 테스트 계정은 홈 맨 위에 퀘스트 카드가 보이고, 기존 계정은 보이지 않는다.
- 진행 상태를 한 단계 기록한 뒤 다른 브라우저로 로그인해도 같은 진행도가 보인다.
- 다른 유저의 진행 행을 클라이언트에서 조회할 수 없다(RLS 확인).
- 마이그레이션 파일과 되돌림 SQL이 저장소에 있다.
