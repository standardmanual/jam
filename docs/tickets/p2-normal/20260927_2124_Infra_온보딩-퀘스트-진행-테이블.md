# [Infra] 온보딩 퀘스트 진행 상태를 유저별로 저장하는 테이블을 만들고, 온보딩을 마친 신규 유저에게 행을 만든다 (T1a)

## 핵심 요약
- 요구사항: 신규 테이블 `user_onboarding_quests`(유저당 1행: 단계별 완료 시각, 건너뛰기 시각, 퀘스트 완료 시각, 보상 지급 시각)를 만들고, 기능 배포 이후 온보딩 2단계를 마친 유저에게만 행을 만든다. 홈 카드는 T1b(`20260927_2133`)로 분리했다.
- 구현 계획: 마이그레이션 SQL 작성(실행은 사용자 승인 후 메인 세션) → 타입 반영 → 온보딩 완료 API에서 행 생성 → 데이터 모델 문서 갱신.
- 관련 파일: `jam-web/supabase/migrations/195_user_onboarding_quests.sql`(신규), `jam-web/src/types/database.ts`(L74 부근 `UserRow` 옆에 행 타입 추가), `jam-web/src/types/database.generated.ts`(`Tables`에 테이블 추가), `jam-web/src/app/api/onboarding/complete/route.ts`(L113-117 `onboarding_completed_at` 기록 직후), `docs/specs/prd/02_DATA_MODEL.md` §1(`users` 다음), `jam-web/src/lib/onboarding-quest/config.ts`(신규, 기능 스위치)

## 배경 / 문제 정의
온보딩 퀘스트의 진행을 기기와 무관하게 이어 가려면 서버에 유저 단위 진행 상태가 필요하다. 대상은 기능 배포 이후 가입한 신규 유저뿐이므로, 행의 존재 자체를 "퀘스트 대상"의 기준으로 삼는다. 기획 전문과 결정 이력은 상위 티켓 `20260927_2123`에 있다.

> 2026-09-27 분리: 원래 T1은 테이블과 홈 카드를 함께 다뤘으나, 바뀌는 파일이 규모 기준(5개)을 넘어 DB 쪽(T1a, 이 티켓)과 홈 카드(T1b, `20260927_2133`)로 나눴다.

## 상세 요구사항
- 공통 원칙: 퀘스트 1~7단계는 연출용 데이터다. 이 테이블 외의 실제 테이블(`inventory_items`·`poi_drops`·`user_activity_badges`·`point_transactions`)에는 퀘스트 때문에 행을 만들지 않는다.
- 테이블 `user_onboarding_quests`
  - `user_id` UUID PK, `users(id)` 참조, 유저 삭제 시 함께 삭제
  - `step_progress` JSONB NOT NULL 기본값 `'{}'`: 단계 키 → 완료 시각(ISO 문자열). 단계 키는 `sync`·`bag`·`pickup`·`mix_fail`·`mix_success`·`drop`·`browse` 7개다(순서대로 퀘스트 1~7단계)
  - `skipped_at` TIMESTAMPTZ NULL: 건너뛰기 시각(T8). 값이 있으면 완료 배지를 받을 수 없다
  - `completed_at` TIMESTAMPTZ NULL: 실제 첫 활동 유입 시각(T6)
  - `reward_granted_at` TIMESTAMPTZ NULL: 완료 배지·100P 지급 시각(T7, 멱등 기준)
  - `created_at` TIMESTAMPTZ NOT NULL 기본값 `now()`
- RLS: 켠다. 본인 행 SELECT만 허용한다. INSERT·UPDATE·DELETE 정책은 두지 않는다(서버의 service_role 경로만 쓴다).
- 행 생성: `POST /api/onboarding/complete`가 `onboarding_completed_at`을 처음 기록하는 경로에서, service_role 클라이언트로 `user_onboarding_quests`에 행을 만든다(이미 있으면 아무것도 하지 않음, `on conflict do nothing`). 행 생성이 실패해도 온보딩 완료 응답은 막지 않고 오류만 기록한다.
- 기존 유저에게는 행을 소급해서 만들지 않는다(백필 없음).
- **기능 스위치**: `jam-web/src/lib/onboarding-quest/config.ts`에 `ONBOARDING_QUEST_ENABLED = false` 상수를 둔다. 행 생성은 이 값이 true일 때만 한다(T1b 홈 카드도 같은 값을 본다). 하위 티켓이 staging을 거쳐 중간에 프로덕션으로 나가도, 스위치를 켜기 전에는 신규 유저에게 반쯤 만든 퀘스트가 보이지 않게 하기 위함이다. 스위치는 상위 티켓의 마지막 단계에서 켠다.
- 마이그레이션 파일 끝에 `-- 되돌림 SQL` 주석 블록(테이블 DROP)을 싣는다(`.claude/skills/jam-work/references/db-migration-rules.md` §4). 실행은 하지 않는다.
