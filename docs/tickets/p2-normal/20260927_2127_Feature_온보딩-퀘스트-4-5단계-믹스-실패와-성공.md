## 핵심 요약
- 요구사항: (사용자 결정 1로 변경) 4단계(`mix_fail` 키 유지)는 실제 `/combine` 화면에서 연출 레시피 「살롱의 장물 시세」를 열어 슬롯별 필요 재료와 소각 안내를 확인하는 단계다. 5단계(`mix_success`)는 두 슬롯을 연출 재료로 채워 믹스에 성공하고, 재료 두 개가 사라지며 「최고급 캣닢 뭉치」를 받는다.
- 구현 계획: `combine/page.tsx`가 N1 문지기 함수로 `mix_fail`/`mix_success` 차례인지 확인 → 맞으면 실제 레시피·인벤토리 대신 연출 레시피 1건·연출 재료 2개를 `CombineClient`에 넣고, 실제 `/api/combine` 대신 단계 기록 API만 부른다.
- 관련 파일: `jam-web/src/app/(main)/combine/page.tsx`(L12 `CombinePage`, 실제 재료·레시피 서버 조회), `jam-web/src/app/(main)/combine/CombineClient.tsx`(L75 `CombineClient`, `'use client'`), `jam-web/src/lib/onboarding-quest/screen-gate.ts`(N1, 읽기), `docs/service/content/COMBINE_RECIPES.md` L28·L84·L91, T3의 픽업 연출 재료(공유)

## 배경 / 문제 정의
실제 믹스는 성공·실패와 무관하게 투입한 아이템배지를 소각한다(`COMBINE_RECIPES.md` L84). 사용자는 실패하면 아이템배지를 잃을 수 있다는 점을 튜토리얼에서 강조하기를 원했다. 연출용이라 잃어도 손해가 없으므로 실패를 직접 겪게 한다. 결정 번복(2026-09-28)으로 퀘스트 전용 화면이 없어지고 실제 `/combine` 화면에서 진행한다(결정 14). 기획 전문과 결정 이력은 상위 티켓 `20260927_2123`에 있다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 공통 원칙: 연출용 데이터다. `inventory_items`·`poi_drops`·`badges`·`user_activity_badges`·`point_transactions`에 행을 만들지 않는다. 서버에는 `user_onboarding_quests.step_progress`에 `mix_fail`·`mix_success` 완료를 각각 기록한다.
- 연출용 아이템·레시피는 실제 카탈로그의 기존 아이템·레시피(이름·이미지)를 빌려 쓴다. 안내 문구는 중립 톤이며 코치마크·설명 팝업은 쓰지 않는다.
- 4단계(`mix_fail` 차례, 의미는 레시피 확인): 실제 `/combine` 레시피 목록에 연출 레시피 「살롱의 장물 시세」 1건만 보인다. 열면 실제 믹서 화면(슬롯 2개·보상 요약·`burnNotice`)이 뜨고, 슬롯을 누르면 실제 가방 시트에 후보가 보인다(보유한 연출 재료는 선택 가능, 나머지 후보는 회색). 완료 시점에 `POST /api/onboarding-quest/step`({ step: 'mix_fail' })을 호출한다.
- 5단계(`mix_success` 차례): 두 슬롯을 연출 재료(황금빛 도토리·잃어버린 결혼반지)로 채우고 [믹스하기]를 누르면 실제 `/api/combine`을 부르지 않고 `POST /api/onboarding-quest/step`({ step: 'mix_success' })만 부른다. 성공하면 실제 `BadgeRevealOverlay`로 「최고급 캣닢 뭉치」를 보여 주고, 두 재료는 연출 가방에서 사라진다.
- 실제 `/api/combine`·`trackEvent('combine_attempt'|'combine_success')`·`router.refresh()`는 연출 중에 호출하지 않는다.
- `mix_fail`·`mix_success`가 차례가 아닌 유저(퀘스트 미대상·다른 단계·완료·건너뜀)는 연출 없이 기존 `/combine` 화면(실제 재료·실제 레시피) 그대로다(결정 22).

### 주요 의사결정 / 핵심 메모
- 카리나가 착수 전 코드를 확인하다가 실제 `/combine`이 레시피 선택형이라 틀린 재료로 실패하는 일이 구조적으로 없다는 점을 발견했다. 사용자가 A안(4단계를 레시피 확인 단계로 변경, 키 `mix_fail`은 유지)을 선택해 상위 티켓 결정 4-4의 실패 체험을 폐기했다(상위 결정 23).
- 4·5단계는 같은 화면에서 이어 간다(상위 결정 20의 예외, 사용자 승인).
- `InventoryItemRow.serial_number`가 NOT NULL 타입이라 연출 재료의 일련번호를 null 대신 0으로 채웠다. 화면은 이 값을 쓰지 않는다.
- 규모는 계획(6개·약 200줄)과 파일 수는 같고 줄 수가 333줄로 늘었다. 테스트와 순수 함수 추출(상호작용 테스트 대체)이 원인이다.
