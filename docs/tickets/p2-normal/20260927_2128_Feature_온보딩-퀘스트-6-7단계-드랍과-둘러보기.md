# [Feature] 온보딩 퀘스트 6단계: 실제 `/drops` 가상 지도에 믹스 결과물을 드랍한다 (T5)

## 핵심 요약
- 요구사항: 6단계는 믹스 결과물을 `/drops`의 가상 지도 POI에 드랍하는 장면을 보여 준다. 7단계(미션 둘러보기)는 이 티켓에서 분리해 `T5b`(`20260928_0139`)로 옮겼다 — 저장소에 전용 트라이브 화면이 없어 `/missions`만 인정하기로 했기 때문이다(결정 18).
- 구현 계획: T3(픽업)와 같은 `/drops` 가상 지도·POI 부품을 재사용해, `drop` 차례일 때 믹스 결과물을 그 POI에 놓는 연출로 전환한다(결정 21 — 실제 인터랙티브 지도에는 마커를 얹지 않는다).
- 관련 파일: `jam-web/src/app/(main)/drops/page.tsx`(L43 `questStep` 전달), `jam-web/src/app/(main)/drops/DropsClient.tsx`(L52 props·L93 geolocation 가드·L220 연출 분기), `jam-web/src/app/(main)/drops/QuestPickupScene.tsx`(T3 연출 씬, 재사용), `jam-web/src/components/PoiCarouselModal.tsx`(L144 props·L338 `openInventory`·L380 `executeDrop`·L589 `hideDropAction`), `jam-web/src/lib/onboarding-quest/demo-data.ts`(L128 `DEMO_MIX_RECIPE`), `jam-web/src/lib/onboarding-quest/screen-gate.ts`(N1, 읽기)

## 배경 / 문제 정의
내가 만든 아이템을 세상에 내려놓는 드랍으로 연출 구간의 마지막 "행동" 단계를 마무리한다. 결정 번복(2026-09-28)으로 퀘스트 전용 화면이 없어지고 실제 `/drops` 화면에서 진행하며(결정 14), 7단계는 실제 화면이 없는 트라이브 대신 `/missions`만 인정하기로 하면서 별도 티켓(T5b)으로 분리했다(결정 18). 기획 전문과 결정 이력은 상위 티켓 `20260927_2123`에 있다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 공통 원칙: 연출용 데이터다. `inventory_items`·`poi_drops`·`badges`·`user_activity_badges`·`point_transactions`에 행을 만들지 않는다. 서버에는 `user_onboarding_quests.step_progress`에 `drop` 완료만 기록한다.
- 연출용 아이템·레시피는 실제 카탈로그의 기존 아이템·레시피(이름·이미지)를 빌려 쓴다. 안내 문구는 중립 톤이며 코치마크·설명 팝업은 쓰지 않는다.
- `drop` 차례인 유저가 `/drops`에 들어가면 T3와 같은 정적 가상 지도 이미지 + POI 1개를 보여 준다(같은 화면·부품을 재사용하되 이번엔 "드랍" 동작으로 구분).
- POI에 드랍하면 믹스 결과물(연출용 아이템)이 가방에서 빠지고 지도에 놓인 장면을 보여 준다. 실제 `poi_drops`는 만들지 않는다.
- 드랍하면 `POST /api/onboarding-quest/step`({ step: 'drop' })을 호출한다.
- `drop`이 차례가 아닌 유저(퀘스트 미대상·다른 단계·완료·건너뜀)는 연출 없이 기존 `/drops` 화면 그대로다(결정 22).

## 구현 계획
T3의 가상 지도·POI 부품을 재사용해 드랍 연출로 확장 → 화면 진입 판정(N1) → 연출 데이터 정리 → 진행 기록.

### 카리나 착수 전 코드 확인 (2026-09-28)
- 실제 드랍 흐름은 `PoiCarouselModal.tsx`의 POI 카드 [여기에 드랍] → L338 `openInventory()`(`/api/inventory/items` 조회) → 가방 그리드에서 배지 선택(L366 `handleSelectDropGroup`) → 확인 → L380 `executeDrop()`(`/api/drops` POST, 성공 토스트 `d.drops.dropSuccess`, `trackEvent('item_drop')`, `/api/drops/poi/:id` 재조회로 POI 목록 갱신)이다. 연출도 이 순서를 그대로 밟게 하면 실제 서비스와 같은 동작을 가르친다(결정 14와 일치, T4처럼 구조적 불일치는 없다).
- T3는 `demoMode`에서 [여기에 드랍] 버튼을 숨겼다(L589 `hideDropAction={demoMode}`). 이번엔 드랍 차례에만 이 버튼을 살리고, 두 API(`/api/inventory/items`·`/api/drops`)와 GA·`onDropOrPickupSuccess`를 연출 콜백으로 대체해야 한다.
- 단계 순서는 `mix_success` → `drop`이다(`types/database.ts` L96). 가방에 넣을 연출 아이템은 5단계 결과물 「최고급 캣닢 뭉치」(`DEMO_MIX_RECIPE.rewardBadges[0]`, `demo-data.ts`)다.

### 채원 사전 판정에 맡기는 항목
1. **드랍 후 화면**: 실제 흐름은 드랍 성공 토스트 뒤 같은 POI 카드의 드랍 목록에 방금 놓은 배지가 보인다(= "지도에 놓인 장면"). 카리나 제안은 연출도 로컬 `dropsCache`에 캣닢 뭉치 1건을 추가해 같은 장면을 보여 주고, 사용자가 모달을 닫으면 홈(`router.push('/')`)으로 이동하는 것이다. T3처럼 기록 직후 바로 홈으로 보내면 "놓인 장면"을 볼 수 없다.
2. **드랍 차례의 POI 초기 목록**: 3단계에서 주운 연출 드랍(`DEMO_PICKUP_DROP`)을 다시 보여 줄지, 빈 목록으로 시작할지. 카리나 제안은 빈 목록(실제 `EmptyState`)이다 — 이미 주운 배지가 그대로 남아 있으면 픽업이 반영되지 않은 것처럼 보인다.
3. **마커 라벨**: T3의 `pickupMarkerLabel`(「근처 드랍 지점」)을 그대로 쓸지. 카리나 제안은 그대로 재사용(새 문구 없음)이다.

## 완료 조건
- `drop` 차례인 테스트 계정이 `/drops`의 가상 지도 POI에 드랍하면 가방에서 연출용 결과물이 빠지고 진행도가 `drop`까지 바뀐다.

- `drop`이 차례가 아닌 계정은 실제 `/drops` 화면(실제 지도·실제 드랍) 그대로다.

### 구현 내용 요약
퀘스트 `drop` 차례인 유저가 `/drops`에 들어가면 `page.tsx`가 게이트 값을 `'pickup' | 'drop' | null`로 좁혀 넘기고, `DropsClient`는 두 값 모두에서 geolocation 조회 없이 연출 씬(`QuestPickupScene`, `mode` prop으로 pickup·drop 공용)을 보여 준다. drop 모드는 POI 목록을 빈 상태로 시작하고, `PoiCarouselModal`에 새로 추가한 `demoDropItems`·`onDropOverride`로 실제 드랍 흐름([여기에 드랍] → 가방 → 확인)을 그대로 밟는다. 가방에는 「최고급 캣닢 뭉치」(`DEMO_DROP_ITEM`) 1개가 보인다. 확정하면 `POST /api/onboarding-quest/step`({step:'drop'})만 호출하고, 성공하면 실제와 같은 성공 토스트를 띄운 뒤 순수 함수 `toDemoDroppedPickup()`으로 카드 목록에 놓인 배지 1건을 추가한다. 사용자가 카드를 닫으면 홈으로 이동한다. 연출 중에는 `/api/inventory/items`·`/api/drops`·`trackEvent('item_drop')`·`onDropOrPickupSuccess`를 호출하지 않는다. `hideDropAction={demoMode && !onDropOverride}`로 T3 픽업 연출은 기존처럼 버튼이 숨는다.
