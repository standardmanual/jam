# [Service] 온보딩 퀘스트 완료 시 완료 배지와 100P를 한 번만 지급한다 (T7b)

## 핵심 요약
- 요구사항: T6 완료 판정(`completed_at` 기록)이 실제로 일어난 순간, 건너뛰지 않은 유저에게 T7a가 등록한 완료 배지 1개와 배지의 `point_reward`(100P)를 한 번만 지급한다. 동기화 경로에서는 기존 배지 획득 카드에 이 배지를 함께 싣는다.
- 구현 계획: `recordOnboardingQuestCompletion`이 완료를 기록한 직후 `reward_granted_at` 선점 → 배지 발급 → 포인트·피드 이벤트 → 지급한 배지 id를 반환한다. `syncStravaActivities`는 반환값을 `earnedBadgeIds`에 합류시키고, 7단계 기록 API 경로의 표시 방식은 채원 사전 판정으로 정한다.
- 관련 파일: `jam-web/src/lib/onboarding-quest/completion.ts`(L45 `recordOnboardingQuestCompletion`, L90 `completed_at` 갱신), `jam-web/src/lib/strava/sync.ts`(L1289 완료 판정 호출, L1297 `buildEarnedBadgePayload`), `jam-web/src/app/api/onboarding-quest/step/route.ts`(L81~84 browse 직후 호출), `jam-web/src/lib/badge-engine/usageBadges.ts`(L211~243 발급 부수효과 선례), `jam-web/src/lib/onboarding-quest/config.ts`(T7a의 `ONBOARDING_COMPLETION_BADGE_ID`)

## 배경 / 문제 정의
완료 보상은 크지 않아도 된다는 결정(상위 결정 6)에 따라 100P가 담긴 완료 배지 1종을 지급한다. 착수 전 코드 확인 결과 T7을 둘로 나눴다(2026-09-28 사용자 결정). 배지 행 등록과 문서는 T7a(`20260928_1212`), 이 티켓은 지급 로직이다. 기획 전문과 결정 이력은 상위 티켓 `20260927_2123`에 있다.

## 사용자 결정 (2026-09-28, 카리나 코드 확인 후)
1. 자동 발급 방지 표시는 새 플래그 대신 기존 `mission_reward`를 재사용한다. 배지엔진 후보 제외는 이미 보장되므로 이 티켓은 엔진 코드를 바꾸지 않는다(상세는 T7a).
2. **동기화 경로 표시**: 지급한 배지를 `earnedBadgeIds`에 합류시켜 기존 배지 획득 카드로 보여 준다(새 UI 없음).
3. **7단계(`browse`) 경로 표시는 채원 사전 판정에 맡긴다.** 이 경로는 퀘스트 도중에 이미 Strava를 연동해 활동이 처리된 유저가 7단계를 기록하는 순간에만 지급이 일어나는 드문 경우다. 후보는 (가) 즉시 알리지 않음(배지함·포인트 내역에서만 확인), (나) 단계 기록 API가 지급 배지를 돌려주고 `/missions`에서 기존 배지 획득 카드를 띄움이다. 채원이 새 UI나 눈에 보이는 변경이 필요하다고 판정하면 승인 대기로 멈춘다.

## 상세 요구사항
- 지급 조건: 이번 호출에서 `completed_at` 갱신이 실제로 행을 바꿨고(`update ... .is('completed_at', null)`에 `.select()`를 붙여 바뀐 행 수로 판단), `skipped_at`이 없을 때만 지급한다. 건너뛴 유저는 완료 시각만 기록되고 보상은 받지 않는다(상위 결정 24).
- 멱등: 지급 전에 `reward_granted_at`을 조건부 갱신으로 선점한다(`.is('reward_granted_at', null)`, 바뀐 행이 없으면 중단). 배지 insert가 23505(이미 보유)면 포인트·피드를 건너뛴다. 23505가 아닌 오류(배지 행이 아직 없는 경우 포함)면 `reward_granted_at`을 다시 NULL로 돌리고 로그만 남긴다.
- 발급 부수효과는 `usageBadges.ts` L211~243과 같다: `user_activity_badges` insert(`triggered_by: 'onboarding_quest'`) → 배지의 `point_reward`만큼 `awardPoints(userId, pr, 'badge_point_reward', { sourceBadgeId })` → `recordFeedEvent(userId, 'badge_earned', …)`. 포인트 금액은 코드에 100을 하드코딩하지 않고 배지 행에서 읽는다.
- `recordOnboardingQuestCompletion`은 지금처럼 절대 throw하지 않는다. 반환형을 `Promise<void>`에서 지급한 배지 id(`string | null`)를 담는 형태로 바꾼다.
- `syncStravaActivities`: 반환된 배지 id가 있으면 `buildEarnedBadgePayload` 호출 전에 `earnedBadgeIds`에 합류시킨다(중복 제거).
- 기능 스위치(`ONBOARDING_QUEST_ENABLED`)가 꺼져 있으면 지금처럼 아무것도 하지 않는다.

## 구현 계획
### 파일 단위 계획 (예상 5~6개 파일·약 180줄, 테스트 포함)
1. `jam-web/src/lib/onboarding-quest/completion.ts`: 순수 판정 `shouldGrantQuestReward(completionUpdated, skippedAt)` 추가, 지급 함수 `grantOnboardingQuestReward(supabase, userId)`(선점·발급·포인트·피드·실패 시 선점 해제) 추가, `recordOnboardingQuestCompletion` 반환형 변경.
2. `jam-web/src/lib/strava/sync.ts` L1289: 반환값을 받아 `earnedBadgeIds`에 합류.
3. `jam-web/src/app/api/onboarding-quest/step/route.ts` L83: 채원 판정 (가)면 반환값을 무시, (나)면 응답에 지급 배지를 싣는다.
4. (채원 판정 (나)일 때만) `/missions` 쪽 기록 호출부에서 기존 배지 획득 카드 표시.
5. 테스트: `jam-web/src/lib/onboarding-quest/__tests__/completion.test.ts`(지급 판정 순수 함수: 완료 갱신 안 됨·건너뜀·정상), 필요하면 sync 합류 단위 테스트.

## 완료 조건
- 건너뛰지 않은 테스트 계정이 첫 활동을 동기화하면 완료 배지 1개와 `point_transactions`의 100P 1건이 생기고, 동기화 결과의 배지 획득 카드에 완료 배지가 보인다.
- 같은 계정에서 동기화를 다시 실행해도 배지·포인트가 추가로 생기지 않는다.
- 건너뛴 계정은 첫 활동을 동기화해도 완료 배지를 받지 않는다(`completed_at`만 기록된다).
- 활동 조건만으로는 이 배지가 발급되지 않는다(`mission_reward` 후보 제외, T7a에서 확인).
- 배지 행이 아직 없을 때 지급을 시도해도 동기화가 실패하지 않고 `reward_granted_at`이 NULL로 남는다.
