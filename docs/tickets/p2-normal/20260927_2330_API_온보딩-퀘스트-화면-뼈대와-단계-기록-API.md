# [API] 온보딩 퀘스트 전용 화면 뼈대와 단계 완료 기록 API를 만든다 (T2a)

## 핵심 요약
- 요구사항: `/onboarding-quest` 화면 뼈대(현재 단계 번호·타이틀·설명, 단계 부품이 들어갈 자리, 홈으로 돌아가기)와 단계 완료를 기록하는 `POST /api/onboarding-quest/step`을 만든다. 단계별 연출 부품은 T2b 이후 티켓이 채운다.
- 구현 계획: 순서 판정 순수 함수 → API 라우트(service_role로 `step_progress` 갱신) → 화면 뼈대 → 테스트.
- 관련 파일: `jam-web/src/lib/onboarding-quest/progress.ts`(신규, `validateStepAdvance`), `jam-web/src/lib/onboarding-quest/__tests__/progress.test.ts`(신규), `jam-web/src/app/api/onboarding-quest/step/route.ts`(신규, 패턴은 `jam-web/src/app/api/onboarding/complete/route.ts` L24~ 인증·`createServiceClient` 사용), `jam-web/src/app/(main)/onboarding-quest/page.tsx`(신규), `jam-web/src/lib/onboarding-quest/config.ts`(읽기, `ONBOARDING_QUEST_STEPS`), `jam-web/src/app/(main)/OnboardingQuestCard.tsx` L18(`ONBOARDING_QUEST_PATH`, 읽기), `jam-web/src/lib/i18n/ko.ts` L220~(`onboardingQuest`, 읽기), `jam-web/src/components/ui/TopNav.tsx`(L56 `TopNavProps`, L121 `logoNode`·L135 `SyncButton`·L88 아바타 링크에 표시 전용 prop)

## 배경 / 문제 정의
홈 퀘스트 카드(T1b)의 「시작하기/이어 하기」가 가리키는 `/onboarding-quest` 화면이 아직 없다. 단계마다 연출 부품을 붙이기 전에, 화면 뼈대와 서버 기록 경로를 먼저 만든다. 원래 T2(`20260927_2125`)를 규모 기준 때문에 T2a(이 티켓)와 T2b로 나눴다. 기획 전문은 상위 티켓 `20260927_2123`.

## 상세 요구사항
- 공통 원칙: 퀘스트 1~7단계는 연출용 데이터다. `inventory_items`·`poi_drops`·`user_activity_badges`·`point_transactions`에 행을 만들지 않는다. 서버에는 `user_onboarding_quests.step_progress`에 단계 완료만 기록한다.
- 진행 방식(2026-09-27 사용자 결정 A): 단계는 퀘스트 전용 화면 `/onboarding-quest`에서 진행하고, 실제 서비스의 화면 부품(배지 획득 연출 `BadgeRevealOverlay`, 인벤토리 그리드 `InventoryGrid`, 지도·믹서 부품)을 연출용 데이터로 재사용한다. 실제 동기화 버튼(`SyncButton.tsx`)·인벤토리 페이지·지도·믹서 페이지 코드는 퀘스트 분기를 넣지 않는다.
- API `POST /api/onboarding-quest/step` 본문 `{ step: OnboardingQuestStepKey }`
  - 로그인 필수. 기능 스위치(`ONBOARDING_QUEST_ENABLED`)가 꺼져 있거나, 행이 없거나, `skipped_at`이 있거나, 이미 7단계를 모두 마쳤으면 거부한다(409 등, 응답 형식은 기존 API 관례).
  - 순서 강제: 요청한 단계가 「아직 안 끝난 첫 단계」와 같을 때만 기록한다. 이미 끝낸 단계를 다시 보내면 성공으로 응답하고 아무것도 바꾸지 않는다(멱등). 뒤 단계를 먼저 보내면 거부한다.
  - 기록: service_role로 `step_progress`에 `{ [step]: ISO 시각 }`을 합친다.
- 화면 `/onboarding-quest`(서버 컴포넌트)
  - 퀘스트 대상이 아니면(행 없음·스위치 꺼짐·건너뜀·7단계 완료) 홈으로 보낸다.
  - 현재 단계(아직 안 끝난 첫 단계)의 번호(n/7)·타이틀·설명을 i18n `onboardingQuest` 문구 그대로 보여 준다.
  - 단계 부품 자리: 이 티켓에서는 비워 두되, 단계 키별로 부품을 꽂을 수 있는 구조(예: 단계 키 → 컴포넌트 매핑)로 만든다.
  - 상단 바: 홈과 같은 TopNav `logo` 모드(로고·동기화 버튼·아바타)를 쓰되 세 요소 모두 링크·동작이 없는 표시 전용이다(2026-09-27 사용자 결정). TopNav에 표시 전용 prop을 추가하고, 기존 호출부 동작은 바꾸지 않는다.
  - 홈 복귀는 하단 탭 바의 홈 탭이 맡는다. 헤더는 좌측 정렬.

## 구현 계획
1. `progress.ts`: `nextStepOf(progress)`, `validateStepAdvance(progress, step)` → `{ ok: true, alreadyDone } | { ok: false, reason }`
2. `progress.test.ts`: 첫 단계 기록, 이미 끝낸 단계 재요청(멱등), 건너뛴 단계 요청 거부, 7단계 완료 뒤 요청 거부
3. `route.ts`: 인증 → 행 조회 → 판정 → 갱신
4. `page.tsx`: 대상 판정 → 현재 단계 헤더 → 단계 부품 자리

## 완료 조건
- 1단계만 마친 테스트 계정이 `step: 'bag'`을 보내면 `step_progress.bag`이 기록되고, `step: 'drop'`을 보내면 거부된다.
- 같은 단계를 두 번 보내도 기록 시각이 바뀌지 않는다.
- 행이 없는 계정·스위치가 꺼진 상태에서는 API가 거부하고 화면은 홈으로 보낸다.
- `/onboarding-quest`에서 현재 단계의 번호·타이틀·설명이 확정 문구와 같게 보인다.
- 이 화면 상단 바의 로고·동기화 버튼·아바타는 홈과 같은 모양이지만 눌러도 이동·동기화가 일어나지 않는다. 다른 화면의 TopNav 동작은 그대로다.
- 판정 함수 단위 테스트가 위 경우를 다루고 `scripts/verify.sh`가 통과한다.

### 구현 내용 요약
- 순서 판정 순수 함수 `nextStepOf`·`validateStepAdvance`(`progress.ts`): 아직 안 끝난 첫 단계만 기록, 이미 끝낸 단계는 멱등 성공, 뒤 단계·7단계 완료 뒤 요청은 거부.
- `POST /api/onboarding-quest/step`: 스위치 꺼짐 403, 미인증 401, 잘못된 단계 400, 행 없음 404, 건너뜀·순서 위반·전체 완료 409, 통과 시 service_role로 `step_progress` 병합.
- `/onboarding-quest` 서버 화면: 대상이 아니면 홈으로 리다이렉트, 대상이면 현재 단계 n/7·타이틀·설명을 좌측 정렬로 보여 주고 `data-step` 빈 컨테이너를 둔다.
- `TopNav`에 `decorative` prop(기본 false) 추가: 로고·동기화 버튼·알림 종·아바타를 `inert`로 감싸 모양은 같고 동작만 없다.
