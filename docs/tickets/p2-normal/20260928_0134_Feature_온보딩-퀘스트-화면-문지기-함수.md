# [Feature] 실제 화면이 지금 이 유저의 퀘스트 차례인지 판정하는 문지기 함수를 만든다 (N1)

## 핵심 요약
- 요구사항: 퀘스트 단계 순서 판정을 화면마다 흩어 두지 않고, 문지기 함수 하나(`screen-gate.ts`)가 "지금 이 화면이 이 유저의 퀘스트 차례인가"만 판정한다. 차례면 해당 단계 키를 돌려주고, 아니면 null을 돌려줘 화면은 평소 그대로 렌더링된다(결정 19).
- 구현 계획: 단계 키 → 화면 식별자 지도(결정 18)를 정의하고, 기존 `status.ts`의 DB 조회 패턴과 `progress.ts`의 `nextStepOf`를 재사용해 "다음 단계가 이 화면에 속하는가"만 새로 판정한다. 순수 판정 함수와 DB 조회 함수를 분리한다(`status.ts`의 `resolveOnboardingQuestCard`/`getOnboardingQuestCard` 분리 패턴을 따른다).
- 관련 파일: `jam-web/src/lib/onboarding-quest/screen-gate.ts`(신규), `jam-web/src/lib/onboarding-quest/config.ts`(L11-19 `ONBOARDING_QUEST_STEPS`, 읽기), `jam-web/src/lib/onboarding-quest/progress.ts`(L13-15 `nextStepOf`, 읽기), `jam-web/src/lib/onboarding-quest/status.ts`(L49-76 `getOnboardingQuestCard`의 DB 조회 패턴, 참고), `jam-web/src/lib/onboarding-quest/__tests__/screen-gate.test.ts`(신규)

## 배경 / 문제 정의
결정 번복(2026-09-28)으로 퀘스트 전용 화면(`/onboarding-quest`)을 없애고 각 단계를 실제 메뉴 화면에서 진행한다(결정 14). 실제 화면(홈·인벤토리·드랍·믹서·미션)은 언제나 존재하고 퀘스트와 무관한 유저도 방문하므로, 각 화면이 "지금 내가 퀘스트 중이고 이 화면이 내 차례인가"를 판정할 방법이 필요하다. 이 판정을 화면마다 따로 구현하면 단계→화면 지도가 여러 곳에 흩어져 어긋나기 쉽다(결정 19: 문지기 함수 하나로 모은다). 기획 전문과 결정 이력은 상위 티켓 `20260927_2123`에 있다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 단계→화면 지도(결정 18): `sync`→home, `bag`→inventory, `pickup`→drops, `drop`→drops, `mix_fail`→combine, `mix_success`→combine, `browse`→missions.
- 판정 함수(이름은 구현 시 확정)가: 기능 스위치 꺼짐 · 행 없음 · 건너뜀(`skipped_at`) · 7단계 완료(`nextStepOf`가 null) 중 하나라도 해당하면 null을 돌려준다. 그 외엔 `nextStepOf(progress)`로 다음 단계를 구하고, 그 단계가 이 화면 소속이 아니면 null, 소속이면 그 단계 키를 돌려준다.
- DB 조회는 `status.ts`의 `getOnboardingQuestCard`처럼 `user_onboarding_quests`를 1회만 조회한다. 화면(page.tsx)마다 중복 조회하지 않도록 판정 로직과 조회 로직을 분리하고, 순수 판정 함수만 단위 테스트로 고정한다.
- 조회 실패는 카드 판정과 동일하게 null을 돌려주고 화면 렌더를 막지 않는다(콘솔에만 남긴다).
- 드랍·믹서처럼 한 화면이 단계 두 개(`pickup`/`drop`, `mix_fail`/`mix_success`)를 가지면, 문지기 함수가 정확히 어느 단계인지 단계 키로 구분해 돌려준다 — 화면은 이 키로 자신의 연출 상태(예: 픽업 화면 vs 드랍 화면)를 고른다.
- 관리자 우회(N5)가 이 함수 위에 얹히므로, 정상 판정 로직과 섞이지 않게 함수를 순수하게 유지한다(N5에서 오버라이드 파라미터를 추가할 여지를 남긴다 — 이 티켓에서 오버라이드까지 구현하지 않는다).

## 구현 계획
1. `jam-web/src/lib/onboarding-quest/screen-gate.ts`(신규, 약 45줄): 화면 유니언 타입, 단계→화면 지도 상수, 순수 판정 함수(진행 상태 + 화면 → 단계 키 | null), DB 조회 래퍼(`status.ts`의 `getOnboardingQuestCard` 조회부와 같은 패턴으로 1회 조회 후 순수 함수에 위임).
2. `jam-web/src/lib/onboarding-quest/__tests__/screen-gate.test.ts`(신규, 약 50줄): 화면별 정상 판정, 스위치 꺼짐·행 없음·건너뜀·7단계 완료·다른 화면 소속 단계일 때 null.

## 완료 조건
- 진행 중인 계정이 `bag` 차례일 때 `screen: 'inventory'`로 호출하면 `'bag'`을 돌려주고, `screen: 'drops'`로 호출하면 `null`을 돌려준다.
- 스위치 꺼짐·행 없음·건너뜀·7단계 완료 상태에서는 어떤 화면으로 호출해도 `null`을 돌려준다.
- `pickup`·`drop`이 같은 화면(drops) 소속이어도 문지기 함수가 정확한 단계 키를 구분해 돌려준다(순서상 다음 단계만).
- 단위 테스트가 통과하고 `scripts/verify.sh`가 통과한다.
