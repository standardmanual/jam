# [Service] 관리자 전용 쿠키로 퀘스트 단계를 덮어써 실제 화면에서 DB 기록 없이 미리보는 장치를 만든다 (N5a)

## 핵심 요약
- 요구사항: 관리자에게만 유효한 미리보기 쿠키 하나로 문지기 함수(N1)·홈 퀘스트 카드·단계 기록 API·건너뛰기 API가 "지정 단계"를 따르게 한다. 기능 스위치가 꺼져 있어도, 진행 행이 없어도 동작하고 DB에는 아무것도 쓰지 않는다. 단계를 마치면 쿠키만 다음 단계로 넘어간다.
- 구현 계획: 신규 `preview.ts`(쿠키 이름·순수 판정·관리자 재확인 조회) → `screen-gate.ts`·`status.ts`가 미리보기를 먼저 확인 → `step`·`skip` 라우트가 미리보기 요청을 가로채 DB 대신 쿠키만 갱신 → 관리자 전용 쿠키 설정 API → 테스트.
- 관련 파일: `jam-web/src/lib/onboarding-quest/screen-gate.ts`(L58 `getOnboardingQuestGate`), `jam-web/src/lib/onboarding-quest/status.ts`(L49 `getOnboardingQuestCard`), `jam-web/src/app/api/onboarding-quest/step/route.ts`(L17 `POST`, L18~20 스위치 검사), `jam-web/src/app/api/onboarding-quest/skip/route.ts`, `jam-web/src/lib/admin/auth.ts`(L43 `getAdminUser`, L55 `requireAdmin`), `jam-web/src/proxy.ts`(L83~90 `/admin` 경로 판정 — `/api/admin`은 이 판정 밖이다)

## 배경 / 문제 정의
N5(`20260928_0138`)를 착수 전 코드 확인 결과로 둘로 나눴다(2026-09-28 사용자 결정 2). 이 티켓은 미리보기 장치(보안 로직), N5b(`20260928_0138`)는 어드민 미리보기 화면과 실제 화면의 미리보기 표시다. 옛 관리자 미리보기(`/onboarding-quest/preview`)는 N2에서 삭제됐고, 이중 방어 비대칭 지적(`20260928_0119`)을 이 설계에서 처음부터 반영한다. 기획 전문은 상위 티켓 `20260927_2123`에 있다.

## 사용자 결정 (2026-09-28, 카리나 코드 확인 후)
1. **자동 진행**: 미리보기 중에 한 단계를 마치면 쿠키만 다음 단계로 넘어간다(DB 무기록). 관리자는 홈 카드의 [이어 하기]로 신규 유저처럼 1→7단계를 이어서 확인한다. 7단계를 마치면 `done`(마지막 연동 카드 상태)이 되고, 건너뛰기를 누르면 미리보기가 끝난다(쿠키 삭제).
2. **분할**: N5a(이 티켓, 장치) → N5b(`20260928_0138`, 어드민 화면·표시, 채원 사전 판정).

### 카리나가 확인한 코드 사실 (2026-09-28)
- 단계 기록 호출부가 6곳이다: `OnboardingSyncButton.tsx` L45, `QuestBagGrid.tsx` L36, `QuestPickupScene.tsx` L57·L82, `CombineClient.tsx` L252·L278·L285, `MissionsBrowseTracker.tsx` L17. 미리보기 중 이 호출이 그대로 나가면 스위치가 꺼져 있어 403 `DISABLED` → `StepSaveFailedError` 토스트로 연출이 멈추고, 관리자에게 진행 행이 있으면 실제로 기록된다. **그래서 라우트 한 곳에서 가로채고 화면 6곳은 고치지 않는다.**
- 쿼리 파라미터 방식은 화면 이동마다 값이 사라져 여러 화면을 오가는 퀘스트에 맞지 않는다. 쿠키로 한다.
- `proxy.ts`의 어드민 판정은 `pathname.startsWith('/admin')`이라 `/api/admin/*`은 보호하지 않는다. 관리자 API는 라우트 안에서 `requireAdmin()`으로 막는다(기존 어드민 API 관례).

## 상세 요구사항
- 쿠키: 이름 `jam_quest_preview`, 값은 단계 키 7종 또는 `done`. `httpOnly`, `sameSite: 'lax'`, `path: '/'`, 유효 1일. 그 밖의 값은 무시한다.
- **1차 방어**: 쿠키는 관리자 전용 API `POST /api/admin/onboarding-quest/preview`(`requireAdmin()`)와 관리자가 미리보기 중일 때의 `step`·`skip` 라우트(아래 2차 확인 통과 후)에서만 설정·갱신·삭제된다. 본문 `{ step: <단계 키> }`는 설정, `{ reset: true }`는 삭제.
- **2차 방어**: `getAdminQuestPreview()`가 쿠키를 읽고, 값이 있으면 `getAdminUser()`로 관리자 여부를 다시 확인한다. 관리자가 아니면 쿠키를 무시한다(null). **쿠키가 없으면 관리자 조회를 하지 않는다** — 일반 유저의 화면 진입 비용이 늘지 않는다.
- `getOnboardingQuestGate`: 미리보기가 있으면 스위치·DB 행을 보지 않고, 미리보기 단계가 이 화면 소속이면 그 단계를, 아니면 null을 돌려준다(`done`이면 null).
- `getOnboardingQuestCard`: 미리보기가 있으면 스위치·DB 행을 보지 않고, 단계 키면 `{ kind: 'in_progress', done: <그 단계의 순번>, total: 7, nextStep }`, `done`이면 `{ kind: 'awaiting_sync', stravaConnected: <실제 값>, skipped: false }`를 돌려준다.
- `POST /api/onboarding-quest/step`: 스위치 검사보다 먼저 미리보기를 확인한다. 미리보기 중이면 DB를 읽거나 쓰지 않고 `recordOnboardingQuestCompletion`도 부르지 않는다. 요청 단계가 현재 미리보기 단계면 쿠키를 다음 단계(마지막이면 `done`)로 바꾸고 `{ success: true, alreadyDone: false, preview: true }`, 이전 단계면 `{ success: true, alreadyDone: true, preview: true }`, 이후 단계면 409를 돌려준다(실제 경로의 순서 강제와 같은 의미). `CombineClient`가 `mix_fail`→`mix_success`를 연달아 부르는 흐름이 이 규칙으로 그대로 통과해야 한다.
- `POST /api/onboarding-quest/skip`: 미리보기 중이면 DB를 건드리지 않고 쿠키를 삭제한 뒤 성공을 돌려준다(미리보기 종료).
- 판정은 순수 함수로 분리해 테스트한다: 쿠키 값 파싱, 미리보기 → 문지기 결과, 미리보기 → 카드 상태, 요청 단계 → 쿠키 전이(`advancePreviewStep`).

## 완료 조건
- 관리자 계정에 쿠키를 `bag`으로 설정하면 기능 스위치가 꺼져 있어도 `/inventory`에 연출 도토리가 보이고, 도토리를 누르면 오류 없이 홈 카드가 `pickup` 차례로 바뀐다. `user_onboarding_quests` 등 어떤 테이블에도 행이 생기거나 바뀌지 않는다.
- 관리자가 아닌 계정이 같은 쿠키를 직접 심어도 모든 화면이 평소와 같고, `POST /api/admin/onboarding-quest/preview`는 403이다.
- 쿠키가 없는 요청은 관리자 조회를 하지 않는다(테스트 또는 코드로 확인).
- `{ reset: true }` 또는 건너뛰기로 쿠키가 지워지면 관리자도 평소 판정으로 돌아간다.
- `scripts/verify.sh`가 통과한다.
