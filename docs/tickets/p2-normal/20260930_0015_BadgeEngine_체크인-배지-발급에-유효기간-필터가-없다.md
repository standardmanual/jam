# [BadgeEngine] 체크인 배지 발급 경로에 유효기간 필터가 없어 기간 밖에도 발급된다

## 핵심 요약
- 요구사항: POI 매칭으로 배지를 발급하는 경로(`sync.ts`의 체크인·레거시 activity 경로, 어드민 시뮬레이터)가 `badges.valid_from`/`valid_until` 밖의 배지를 발급하지 않게 한다. 기준 시각은 배지 엔진·지도 마커와 같은 "지금"이다.
- 구현 계획: 연결 배지 조회에 `valid_from`·`valid_until`을 함께 select하고, 새 순수 함수로 기간 밖 배지를 `badgeById`에서 뺀다. 체크인 경로와 레거시 경로는 모두 `badgeById.get()`이 없으면 `continue`하므로 한 지점에서 둘 다 막힌다. 어드민 시뮬레이터도 같은 함수로 거른다.
- 관련 파일:
  - `jam-web/src/lib/strava/sync.ts` L740-756(`LinkedBadge` 타입, 연결 배지 조회·`badgeById` 구성), L783-786(`badgeById.get` 후 `continue` — 바꿀 필요 없음 예상)
  - `jam-web/src/app/api/admin/simulate/route.ts` L95-100(`poiBadgesRaw` 조회·`poiBadgesById` 구성)
  - 신규 순수 함수: `jam-web/src/lib/badge-engine/validPeriod.ts`(이름은 바꿔도 된다)
  - 테스트 신규: `jam-web/src/lib/strava/__tests__/sync-poi-checkin-valid-period.test.ts`(하네스는 같은 폴더 `sync-poi-checkin-shadow-ban.test.ts`를 따른다), 순수 함수 단위 테스트는 `jam-web/src/lib/badge-engine/__tests__/`에 둔다
  - 스펙: `docs/service/badge-engine/BADGE_ENGINE_UNIFIED.md` §3.18(L1815-1839) 「적용 지점」

## 배경 / 문제 정의
티켓 `20260912_1121`은 "유효기간은 발급 자격 심사에 이미 적용돼 있다"는 전제로 체크인 배지 지도 마커(`api/checkin-badges/route.ts` L112-121)에만 기간 필터를 더했다. 그런데 그 전제가 가리킨 발급 경로는 배지 엔진(`badge-engine/index.ts` L1013-1014, `usageBadges.ts` L80-81·L297-298)뿐이다. 체크인 배지는 배지 엔진이 아니라 `sync.ts`의 POI 매칭 블록이 발급하고, 그 연결 배지 조회(L745-749)는 `deleted_at`만 거른다. 그래서 지도에서는 마커가 사라지는데 그 지점을 지나면 배지는 발급된다.

실측(2026-09-30 DB 조회): 지하철·기차역 체크인 배지 `valid_from=2026-09-24 00:00 UTC`(KST 09:00)를 2026-09-12에 설정했다(`seed_checkin_badges_validity_metro_all.sql` 등). 설정 뒤인 2026-09-12 13:52 KST부터 2026-09-23 00:49 KST 사이에 기간 전 발급이 30건(배지 21개, 사용자 5명) 있다. 이 마이그레이션 주석은 "발급 판정과 지도 마커 양쪽에 동일하게 적용된다"고 적고 있어, 의도와 실제 동작이 달랐다. 현재 기간 밖 체크인 배지는 0개라 지금 새로 새는 발급은 없다.

재현(2026-09-30, 카리나, origin/staging `61da75e9` 기준 임시 워크트리 vitest): `sync-poi-checkin-shadow-ban.test.ts` 하네스에 `valid_from=2099-01-01` 체크인 배지, `valid_until=2000-01-01` 체크인 배지를 각각 넣고 `processFetchedActivities`를 부르면 두 경우 모두 `user_checkin_badge_earns` insert가 일어나고 `earnedBadgeIds`에 배지가 들어간다.

이 발견은 `docs/plan/vision/06 JAM! 라이브 운영 플랜.md` §7에 기록돼 있다. **그 플랜 문서와 티켓 `20260929_2226`은 기획이 끝날 때까지 수정하지 않는다.**

## 상세 요구사항

### 서비스/코드베이스 관점
- 기간 판정: `valid_from`이 있고 지금보다 뒤이면 제외, `valid_until`이 있고 지금보다 앞이면 제외, `NULL`은 그 방향 제한 없음. 경계값은 배지 엔진과 같게 포함(`valid_from <= now`, `valid_until >= now`)이다.
- 비교는 문자열 비교가 아니라 시각 값(`Date.parse` 등)으로 한다. DB 값(`+00:00`)과 `toISOString()`(`Z`)의 표기가 달라 문자열 비교는 깨지기 쉽다.
- 체크인 경로(최초·반복 획득 모두)와 레거시 activity+`poi_id` 경로 모두 기간 밖이면 발급하지 않는다. 기간 밖 반복 방문도 막는다(기간이 끝난 배지는 비활성 배지라는 §3.18 정의를 따른다).
- 어드민 시뮬레이터는 기간 밖 POI 배지를 획득 예정으로 보여주지 않고, `dryRun=false`일 때 기록하지도 않는다.
- 이미 발급된 이력(위 30건 포함)은 건드리지 않는다. DB 변경 없음.

### 주요 의사결정
- 쿼리 `.or()` 필터 대신 select 후 순수 함수로 거른다. 테스트 페이크가 PostgREST `.or()` 문자열을 해석하지 못해, 쿼리 필터만 두면 회귀 테스트가 "기간 밖 배지가 발급되지 않는다"를 증명할 수 없다. drop-engine(`drop-engine/index.ts` L258-259)·ambient-drop(`ambient-drop/index.ts` L200-201)도 select 후 코드에서 거르는 선례다. 두 곳의 기존 인라인 비교는 이 티켓에서 바꾸지 않는다.
- 기준 시각은 활동 시각이 아니라 지금이다. 배지 엔진(`index.ts` L1007)·지도 마커(`route.ts` L112)와 같다.

### 주의
- 기존 하네스(`sync-poi-checkin-shadow-ban.test.ts`)는 `@/lib/badge-engine/usageBadges` 모킹에 `evaluateCheckinUsageBadges`가 없어 실행 중 오류 로그가 찍힌다(테스트는 통과). 새 테스트 파일은 그 함수를 함께 모킹한다. 기존 파일은 고치지 않는다.
- 수정 금지: `docs/plan/vision/06 JAM! 라이브 운영 플랜.md`, `docs/tickets/p2-normal/20260929_2226_Feature_라이브-운영-루프-기획-인수인계.md`.

## 구현 계획
1. `badge-engine/validPeriod.ts` — `isWithinValidPeriod(badge: { valid_from: string | null; valid_until: string | null }, now: Date): boolean` 순수 함수를 만든다.
2. `sync.ts` L742 `LinkedBadge`에 `valid_from`·`valid_until`을 더하고 L747 select에 두 컬럼을 넣는다. L753 루프에서 `isWithinValidPeriod`가 거짓이면 `badgeById`에 넣지 않는다. 제외한 배지는 `console.info`로 한 줄 남긴다.
3. `simulate/route.ts` L98 select에 두 컬럼을 넣고, `poiBadgesById`를 만들 때 같은 함수로 거른다.
4. 테스트 — 순수 함수 경계값(NULL/NULL, 미래 시작, 지난 종료, 경계 시각 동일) 단위 테스트, `processFetchedActivities` 하네스로 체크인 최초 획득·체크인 반복 획득·레거시 경로 각각 기간 밖 미발급과 기간 안 발급 유지.
5. `BADGE_ENGINE_UNIFIED.md` §3.18 「적용 지점」의 발급 자격 심사 항목에 POI 매칭 발급 경로(`sync.ts` 연결 배지 조회, 어드민 시뮬레이터)를 더하고, 20260912_1121 시점에는 이 경로가 빠져 있었다는 사실을 한 줄 적는다.

## 완료 조건
- `valid_from`이 지금보다 뒤인 체크인 배지는 `processFetchedActivities`에서 `user_checkin_badge_earns`에 insert되지 않고 `earnedBadgeIds`에 없다(vitest, 수정 전 FAIL·수정 후 PASS).
- `valid_until`이 지금보다 앞인 체크인 배지도 같다(최초 획득·반복 획득 둘 다, vitest).
- 기간 밖 레거시 activity+`poi_id` 배지는 `user_activity_badges`에 insert되지 않는다(vitest).
- 기간이 둘 다 `NULL`이거나 기간 안인 배지는 종전대로 발급된다(vitest).
- 순수 함수가 경계 시각(`valid_from == now`, `valid_until == now`)을 기간 안으로 판정한다(vitest).
- 어드민 시뮬레이터가 기간 밖 POI 배지를 `badgesEarned`에 넣지 않는다(코드 대조 또는 테스트).
- `npm test`와 `scripts/verify.sh`가 통과한다.
- `BADGE_ENGINE_UNIFIED.md` §3.18의 적용 지점이 실제 코드와 일치한다.

## 재검증 (2026-10-25, 카리나, 읽기만)

- **절반은 해소됐다(확신도 높음).** 티켓 `20261018_1814`(JAM2 체크인 배지 서버)가 `lib/poi/checkin-window.ts` 9~25줄에 `isActivityWithinBadgeWindow`를 더했고, `lib/strava/sync.ts` 710·739줄이 `valid_from`·`valid_until`을 함께 걸러 낸다. 이 검사는 `record_checkin_earn` 앞에 있어 최초 획득과 반복 획득을 모두 막고, 시험은 `sync-checkin-earn.test.ts` 296~340줄에 있다. 옛 activity+`poi_id` 경로는 735줄 `type !== 'checkin'`에서 건너뛴다.
- **남은 것 둘**: ① 어드민 시뮬레이터 `app/api/admin/simulate/route.ts` 59~62줄이 `valid_*`를 읽지도 거르지도 않고, `dryRun=false`이면 77~90줄에서 기간 밖 배지도 기록한다. ② `docs/service/badge-engine/BADGE_ENGINE_UNIFIED.md` 3.18절(2471~2496줄)에 POI 발급 경로 설명이 없다.
- 기준 시각이 이 티켓 본문의 «지금»이 아니라 활동 시작 시각이다(`20261018_1814` 사용자 결정 4). 완료 조건의 해당 문장은 이 결정으로 바뀐 것으로 읽는다.
- 옛 수정 브랜치 `claude/jamwork-20260930_0015-checkin-badge-valid-period`(커밋 3개)와 워크트리를 남겼다. 남은 두 가지만 새 범위로 줄여 다시 시작한다.
