# [Admin] 운영툴 골격

> 상위: 20260930_1450 · 순서 2 · 07 인벤토리 A

## 핵심 요약

- 요구사항: 운영툴의 바탕을 만든다. 운영 묶음·항목·결정 기록 데이터, 기획안 제출 API, 받은 기획함(S2), 기획 상세(S3)의 단계 표시줄과
  상태 흐름, 한 주 묶음 일괄 승인, 직접 수정과 결정 기록, 슬랙 이력 알림, 오른쪽 서랍의 틀(07 4.1·4.3·4.4·4.6·4.7·4.8·4.9).
- 구현 계획: 1452의 운영툴 PRD를 따른다. 자원을 실제로 만드는 일은 1500, 미리보기는 1501, 운영 홈·일정표·신호는 1502에서 한다.
- 관련 파일: `jam-web/src/lib/admin/auth.ts`(`requireAdminRead`, 지금 GET 전용이다. 받은 기획함 제출 경로 하나에만 쓰기 예외를 둔다),
  `jam-web/src/app/admin/`, `jam-web/src/app/api/admin/`, `scripts/slack-post.mjs`(게시 방식 참고), 등록 묶음 형식 `docs/specs/prd/asset-generator/`.

## 시작 절차

상위 티켓 20260930_1450의 「진행 규칙」을 따른다. 새 세션에서 시작하고, **혜린의 검토와 사용자 질문을 거쳐 답을 이 티켓에 적은 뒤에만**
작업을 시작한다. 진행 중에 이미 개발된 것에 영향이 생기면 별도 티켓으로 떼어 바로 실행한다.

## 주의

- staging과 프로덕션이 DB 하나를 쓴다. 새 테이블은 마이그레이션 파일로 남기고 사용자 승인 뒤 메인 세션이 실행한다.

- 화면은 채원의 사전 판정을 받는다. 쉬운 문장, 단계 표시, 오른쪽 서랍 원칙을 따른다(07 4.1).

**가정 (사용자가 수정 없이 받아들임, 2026-09-30).**

1. 승인은 항목 상태를 `승인됨`으로 바꾸고 결정 기록을 남기는 데서 멈춘다. `준비중` 이후는 1500이 잇는다. 그동안 승인 화면에 「공개는 아직
   연결 전이에요」를 띄우고, 실제 공개는 지금 절차가 계속 맡는다(진행 규칙 7).
2. 1455는 자원 생성·이미지 생성·예약 공개, 미리보기와 서랍의 내용, 운영 홈·일정표·신호, 패턴 사전, 밸런스 규칙을 만들지 않는다. S3의 미리보기
   자리와 서랍은 빈 틀로 둔다. 단계 표시줄은 6단계를 모두 그리되 1455에서는 「준비」 단계까지만 움직인다.
3. 「도착 → 검토중」은 사용자가 기획 상세를 처음 열 때 화면이 따로 한 번 요청해 바꾼다(읽기 요청으로 상태를 바꾸지 않는다). 열어 보지 않은
   묶음은 「새로 도착」으로 남는다.
4. 새 테이블은 3개(운영 묶음, 묶음 항목, 결정 기록)이고 기존 테이블은 바꾸지 않는다. RLS를 켜고 정책은 만들지 않는다(service_role 전용,
   `185_asset_presets.sql:55-59` 선례). 되돌림 SQL과 생성 타입 재생성을 같은 커밋에 넣는다. 번호는 착수 때 최신 번호를 확인해 정한다.
5. 묶음: 제출자가 정한 `bundle_id`(유일), 대상 주차(`2026-W41` 표기), 가설, 제출 에이전트, 루틴 실행 기록, 제출 원본 전체, 형식 오류 목록,
   시험 표시, 받은 시각. 항목: 묶음 안 고유 키, 종류 7개, 패턴 번호·손잡이, 공개·종료 시각, 대상 세그먼트, 「유저가 겪는 것」, 연결(다른 항목 키),
   세계관 검수·밸런스 판정, 종류별 자원 블록(원본 JSON 그대로, 1455는 해석하지 않는다), 제출 원본(불변)과 수정본, 상태, 만들어진 자원 ID
   (1500이 채움), 항목 형식 오류.
6. 결정 기록: 누가(관리자 ID 또는 「토큰 제출: 에이전트 이름」), 언제, 무엇(제출·승인·반려·수정), 대상 항목, 수정 전후 차이, 사유, 슬랙 알림
   결과. 추가만 한다(수정·삭제 API 없음). 일괄 승인은 항목마다 1행을 남기고 같은 처리 번호로 묶는다.
7. 묶음 상태는 저장하지 않고 항목 상태에서 계산한다(함수 하나와 테스트, 규칙은 PRD §7에 적는다). 반려·취소 항목은 빼고 본다(전부 반려면
   「반려」, 전부 취소면 「취소」). 결정이 안 난 항목이 남아 있으면, 전부 도착일 때만 「도착」이고 아니면 「검토」다. 다 결정된 뒤에는 승인됨·준비중이
   하나라도 있으면 「준비」, 없고 게재중이 있으면 「게재」, 없고 예약됨이 있으면 「예약」, 전부 종료면 「종료」다. 실패 항목이 있으면 단계와 별개로
   「일부 실패」를 붙인다. 이유: 월요일 카드가 게재 중이고 일요일 카드가 예약 상태인 묶음을 가장 뒤처진 항목 기준으로 잡으면 한 주 내내 「예약」으로 보인다.
8. 시험 표시는 제출 본문의 `is_sample: true`다. 시험 묶음은 신호·결과·학습용 읽기 API(1502·1503)에서 뺀다. 결정 기록까지 지울 수 있는 것은
   시험 묶음뿐이다. 슬랙 글 앞에 「[시험]」을 붙인다. 이유: DB를 운영과 함께 쓰고 결정 기록은 에이전트의 학습 재료(07 3.4)다.
9. 제출 경로는 `POST /api/admin/ops-inbox`다. 토큰으로는 이 경로 밖의 모든 쓰기가 403이다. 초기 상한은 본문 1MB, 항목 60개, 시간당 제출
   20회이고 넘으면 400·429다(카드 21~35장 기준 추정값).
10. 요청은 JSON 한 벌이다. 최상위는 기존 `bundle_id`·`author`·`created_at`·`color_rationale_link`를 재사용하고 `week`·`hypothesis`·
    `routine_run`·`is_sample`·`items[]`를 더한다. 항목은 `item_key`·`kind`·`pattern_no`·`knobs`·`starts_at`·`ends_at`·`segment`·
    `user_experience`·`links`·`world_review`(기존 그대로)·`balance_check`·`copy`·`colors`·`image_spec`·`resource`(종류별 블록)다.
    `image.path`·`seed`는 뺀다(D1). 문안·색은 항목 공통 자리에만 둔다(등록 형식으로의 변환은 1500). 시각은 시간대가 붙은 ISO 8601이다.
11. 같은 `bundle_id`를 다시 내면 내용이 같을 때 200(「이미 받았어요」, 슬랙 재알림 없음), 다르면 409이고 덮어쓰지 않는다. 같은 주차에 묶음이
    둘 이상 있어도 받는다. 동시 제출은 `bundle_id` 유일 제약으로 막는다.
12. JSON이 아니거나 `bundle_id`·`author`가 없으면 400으로 거절한다. 그 밖의 형식 오류는 받아서 저장하고 응답에 「경로: 사유」를 모아 돌려준다.
    1455가 검사하는 것은 공통 필드(종류 허용값, 시각, 연결 키 실재, `item_key` 중복, 세계관 검수 규칙, `user_experience` 유무)뿐이고, 종류별
    세부 검증은 1500이 승인 때 등록 전 검증으로 한다(제출 때도 붙일 자리만 남긴다).
13. 직접 수정은 검토중 항목에서만 한다. 고칠 수 있는 것: 문안, 색, 공개·종료 시각, 대상 세그먼트, 「유저가 겪는 것」. 못 고치는 것: 종류, 패턴 번호,
    손잡이, 연결, 참조 ID, 세계관 검수·밸런스 판정. 저장할 때 공통 필드를 다시 검증한다.
14. 수정 전후 차이는 필드 단위 목록 `[{경로, 전, 후}]`으로 결정 기록에 저장하고, 화면에는 「문안: 전 → 후」로 한 줄씩 보여 준다. 제출 원본은
    바꾸지 않는다. 「수정 되돌리기」는 이전 값으로 돌리는 새 수정으로 기록한다.
15. 1455가 `#jam-report`에 보내는 것은 도착(에이전트, 항목 수, 형식 오류 수), 승인, 반려, 직접 수정 4가지다. 예약·공개·종료·실패·되돌림은
    1500, 루틴 실행 결과는 1504의 몫이다. 일괄 승인은 글 1건(「11개 승인, 1개 제외」)이고, 수정 글에는 항목 이름과 바뀐 필드 이름만 올린다.
    제출 문자열은 슬랙 특수문자를 이스케이프한다.
16. 슬랙 게시 실패는 요청을 실패시키지 않는다. DB에 먼저 확정하고 뒤에 게시하며, 실패하면 결정 기록에 「알림 실패」와 오류 이름, 서버 로그를
    남긴다. 자동 재시도와 「다시 보내기」 버튼은 두지 않는다. 채널 ID는 환경변수 2개이고, 완료 조건의 샘플 게시는 실제 채널에 「[시험]」으로 올린다.
17. (카리나) 화면 설계는 채원이 한다(07 4.1). 어드민 화면이므로 MODULAR 재사용 판정은 면제한다(D6).
