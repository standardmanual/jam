# [Feature] 레시피 공개 시각 예약 (O16)

> 상위: 20260930_1450 · 순서 2 병행 · 07 인벤토리 G(O16)

## 핵심 요약

- 요구사항: 레시피를 만들어 두고 정한 시각에 공개한다. 지금은 만들면 바로 모든 유저에게 공개된다(07 5.1, 06 7절). 운영툴에서 레시피를
  예약 공개하려면 먼저 필요하다.
- 구현 계획: 혜린 검토와 사용자 결정(2026-10-01, 아래 「주요 의사결정」)으로 확정했다. 아래 하위 티켓 3개로 나눠 순서대로 진행한다. 174에서 지운 비공개
  레시피(힌트로만 노출하고 우연히 발견)와는 다른 개념이라 충돌하지 않는다.
- 관련 파일: 하위 티켓마다 「구현 계획」에 파일·함수·줄 위치가 있다.

## 시작 절차

상위 티켓 20260930_1450의 「진행 규칙」을 따른다. 새 세션에서 시작하고, **혜린의 검토와 사용자 질문을 거쳐 답을 이 티켓에 적은 뒤에만**
작업을 시작한다. 진행 중에 이미 개발된 것에 영향이 생기면 별도 티켓으로 떼어 바로 실행한다.

## 완료 조건

- 공개 시각을 미래로 둔 레시피는 그 시각 전까지 일반 유저의 믹스 화면에 나오지 않고, 시각이 되면 나온다(테스트).
- 공개 시각 전 레시피로 믹스를 시도하면 일반 유저는 재료가 소모되기 전에 `recipe_not_found`로 거절된다(테스트. 2026-10-01 보강, 레시피를 내려주는 API는 따로 없다).
- 공개 시각 전에 공개를 취소할 수 있고, 공개된 뒤에는 시각 변경과 취소가 거절된다(테스트).
- 운영자 계정은 공개 전 레시피를 보고 시험 믹스할 수 있으며, 시험 믹스는 성공·실패 기록과 믹스 지표에 남지 않는다(테스트).
- `COMBINE_RECIPES.md`, 관련 PRD, 07 블루프린트 5.1절 레시피 행이 갱신됐다.
- 하위 티켓 1157·1158·1159와 영향 티켓 20261001_1200이 CLOSED다.

**혜린 시작 검토 (2026-10-01).** 판단: 만든다. 파일에서 확인한 사실과 카리나의 라이브 DB 조회(2026-10-01 11:40 KST)는 다음과 같다.

- 174가 지운 것(`174_combine_recipe_slots.sql:50-59`, 티켓 20260917_1427 L142-156·L330-348): 힌트로만 노출하고 유저가 재료를 섞다가 우연히 맞히는 비공개 레시피였다.
  레시피를 먼저 고르는 방식으로 바뀌면서 발견 경로가 사라져 사용자가 스펙 아웃했다. O16은 「정한 시각에 전원에게 열리고 그 전에는 없는 것」이라 다른 개념이다.
- 유저에게 레시피가 닿는 길은 두 곳뿐이다: `/combine` 서버 렌더(`app/(main)/combine/page.tsx:26,32-35`, 전부 조회 후 모두 공개 취급)와 믹스 시도
  (`lib/combine/index.ts:98-108`, id로 직접 조회 후 162줄부터 재료 소각). 힌트·도감·「본 레시피」 저장은 없고, 캐시(`revalidate`·`unstable_cache`)도 없다.
- 라이브 DB: 레시피 3개(9/24 등록, 슬롯 3·3·2), `valid_from`·`is_public`·`hint_text` 칸 없음, `combination_recipes`·`_slots`는 RLS 켜짐·정책 0개(anon·authenticated는
  SELECT 권한이 있어도 행을 못 읽는다), 믹스 성공·실패 기록 0건, `recipe_first_success` 조건 배지 0개, 삭제 표시 배지를 쓰는 레시피 0개, 마이그레이션 최신 203.
- 재사용: 노출 판정은 `lib/missions/visibility.ts`의 `isMissionExposed` 선례, 칸 이름은 `badges`·`item_books`의 `valid_from`(null = 처음부터) 선례, KST 입력은
  `lib/admin/kst-format.ts`. 운영툴(1455)의 예약·결정 기록은 `ops_inbox_items`에 이미 있어 1458은 새 예약 테이블을 만들지 않는다.

**가정 (사용자에게 보이고 확인받음, 2026-10-01).**

- A1 새 칸 `combination_recipes.valid_from TIMESTAMPTZ NULL`. 비어 있으면 지금처럼 바로 공개(기존 3개 포함, 백필 없음).
- A2 공개 전 레시피는 일반 유저에게 「없는 레시피」와 같다. 목록·검색·슬롯·보상 미리보기에 없고, 믹스 시도는 기존 `recipe_not_found`(소각·포인트 없음). 예고·카운트다운은 없다(06 3.1).
- A3 종료 시각은 없다. 레시피는 영구이고 내릴 때는 삭제한다(2226 L331의 「종료 시각」은 07로 대체된 초안).
- A4 예약 취소 = 레시피 삭제(슬롯 CASCADE). 초안 보관 상태는 만들지 않는다. 미루기는 시각 수정으로 한다.
- A5 공개 시각이 지난 레시피는 시각 변경과 취소를 서버가 409로 거절한다(07 4.9).
- A6 입력은 KST 분 단위 `datetime-local`(저장은 UTC ISO), 기본값은 「바로 공개」, 과거 시각은 거절. 경계는 `valid_from <= 지금`이면 공개.
- A7 판정은 DB 필터가 아니라 코드 함수 하나(`isRecipeReleased`). 화면과 믹스 시도가 같은 함수를 쓴다(테스트 스텁이 필터를 무시해 DB 필터로는 「안 나온다」를 증명할 수 없다,
  `combine-engine.test.ts:128-131,188-212`).
- A8 판정은 요청 시점. 이미 열어 둔 화면은 새로고침해야 새 레시피가 보인다.
- A9 일반 유저 화면은 문구 한 줄만 바꾼다(`ko.ts` `noRecipes` → 「아직 공개된 레시피가 없어요」).
- A10 1500은 HTTP가 아니라 서버 함수(`createRecipeWithSlots`·`cancelScheduledRecipe`·`recipeReleaseState`)를 부른다.
- A11 마이그레이션 번호 204(병행 브랜치 사용 없음 확인, push 직전 재확인).
- A12 세계관·카즈하 확인 불필요. 주간 KPI의 「레시피 총 수」(`kpiWeekly.ts:146`)는 예약분도 센다. 첫 예약 레시피가 생기기 전에 카즈하 브리핑이 구분해서 읽도록 1504에 넘긴다.
- A13(Q1 답에서 추가) 운영자 믹스 화면에서 공개 전 레시피에 「공개 예정 · 날짜 시각」 표시를 붙인다. 모양은 ③에서 채원이 판정한다.
