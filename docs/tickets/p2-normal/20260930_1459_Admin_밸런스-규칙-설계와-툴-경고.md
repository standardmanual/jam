# [Admin] 밸런스 규칙 설계와 툴 경고

> 상위: 20260930_1450 · 순서 2 병행(설계) · 3(툴 경고) · 07 인벤토리 H

## 핵심 요약

- 요구사항: 혜린이 밸런스 규칙(동시 개방 컬렉션 수, 개방 속도, 포인트 크기, 파밍 방지)과 초기값을 설계하고, 툴이 AI 없이 그 규칙으로
  경고를 띄운다(07 3.6·4.2·S7, 06 12.4의 2·5).
- 구현 계획: 두 단계다. 규칙 설계는 2026-10-01 사용자가 승인했다(아래 「규칙표」). 1단계는 07과 운영툴 PRD에 규칙을 적는 일이고,
  2단계는 툴 경고(조각 A), S7 밸런스 구역(조각 B), 1502 신호 기준값의 S7 이전(조각 C)을 `/jam-work`로 만드는 일이다(아래 「구현 계획」). 혜린의 「주간 밸런스 점검」
  모드 정의는 1504에서 한다.
- 관련 파일: 06 플랜 3.1(포인트 원칙)·6.2(O5 계산 방식), 07 4.2(신호 「밸런스 경고」)·4.7·4.8, `docs/specs/prd/ops-tool/PRD.md`
  §5·§6·§10·§11·§13, `jam-web/src/components/admin/ops/OpsItemDetail.tsx` 166~178행(「밸런스 판정」 표시 자리),
  `jam-web/src/lib/admin/opsInbox/query.ts`, `jam-web/src/app/api/admin/simulate/route.ts`(드랍 상수가 v1이라 근거로 쓰지 않는다,
  20261001_1219).

## 시작 절차

상위 티켓 20260930_1450의 「진행 규칙」을 따른다. 새 세션에서 시작하고, **혜린의 검토와 사용자 질문을 거쳐 답을 이 티켓에 적은 뒤에만**
작업을 시작한다. 진행 중에 이미 개발된 것에 영향이 생기면 별도 티켓으로 떼어 바로 실행한다.

## 주의

- 경제 수치에 닿는 규칙은 시뮬레이터 실측값을 근거로 쓴다(혜린 원칙). 시뮬레이션이 없으면 없다고 적는다.
- 드랍 확률과 포인트 보상 체계 자체는 바꾸지 않는다(07 3.6).

## 규칙표 (사용자 승인 2026-10-01)

## 구현 계획

### 1단계: 설계 문서 (카리나 직접, docs 유형)
1. 07을 먼저 고친다(상위 진행 규칙 5). 4.2 「밸런스 경고」 행(툴은 참고·주의만 쓴다),
   4.7 「밸런스 규칙」 데이터(이름·값·경고 수준·켜기·임시값 여부), 4.8에 규칙 읽기 API 행을 더한다.
2. 운영툴 PRD에 §5.2 「밸런스 규칙」을 새로 쓴다. 규칙표, 항목 종류별로 규칙이 읽는 자리(`resource` 필드 경로), 평가 시점(기획
   상세를 열 때 계산하고 저장하지 않는다), 「점검 못 함」 처리, 1502와 나누는 인터페이스(`BalanceWarning`·`evaluateBundleBalance`)를
   담는다. §6 S7, §10·§11·§13과 `docs/specs/prd/02_DATA_MODEL.md` §12(새 테이블)도 맞춘다. 1500·1457은 이 읽는 자리를 따른다.
3. S7 구역 구성(밸런스 규칙, 신호 기준값, 슬랙 대상·토큰 상태는 1221)을 PRD §6에 적는다.

### 2단계: 툴 경고·S7 구현 (`/jam-work`, 유형 `admin`, 조각 3개)
- 선행 조건: 1단계 문서. R1의 「열린 컬렉션」은 1516의 노출 판정 공용 함수를 쓰므로, 조각 A 착수 전에 1516 상태를 확인한다.
  화면 세부(경고 위치·칩·문구, S7 구성)는 채원 설계를 거친다(PRD §6).
- 조각 A 「경고가 뜬다」: 새 테이블과 승인된 초기값 시드, 되돌림 SQL을 담은 마이그레이션(번호는 착수 때 다시 확인한다. 실행은
  사용자 승인 뒤 카리나), `jam-web/src/lib/admin/opsInbox/` 아래 규칙 정의·순수 평가 함수·현재 서비스 상태 조회, `query.ts`의
  기획 상세 데이터, `OpsItemDetail.tsx` 166~178행과 `OpsBundleWorkspace.tsx`의 묶음 알림 자리. 테스트는 규칙별 경계값, 점검 못 함,
  수정본 반영 뒤 재계산, 시험 묶음이다.
- 조각 B 「값을 바꾼다」: S7 설정 화면의 밸런스 규칙 구역(어드민 새 화면과 사이드바 항목), 관리자 세션 전용 규칙 변경 API, 규칙
  읽기 API(에이전트 토큰은 GET만 쓴다. 기존 토큰 쓰기 계약 테스트를 지킨다), 1502가 읽을 평가 결과.
- 조각 C 「신호 기준값을 S7로 옮긴다」: 1502 신호 엔진(20261001_1155)이 코드 한 곳에 모은 기준값을 규칙 값 테이블로 옮기고 S7에
  신호 기준값 구역을 더한다. 1155가 staging에 머지된 뒤 시작한다.
- 규모: 세 조각 모두 `plan_only` 기준을 넘을 수 있다. 착수할 때 파일 단위 계획을 이 절에 적고 `planOnlyWaiver`를 넣는다.

**사용자가 확인한 가정**
- 「열린 컬렉션」은 노출 판정을 통과한 컬렉션 개수다. 1516이 판정을 통일하면 그 함수를 쓴다.

- 수치를 읽을 수 없는 항목은 통과로 보지 않고 「점검 못 함」(참고)으로 보인다.
- 규칙 값은 새 테이블 1개에 두고 S7에서 고친다. 혜린 루틴(1504)은 읽기 API로 같은 값을 읽는다. 근거 문장은 PRD에만 둔다.
- 툴은 참고·주의만 쓴다. 「중단」은 혜린 주간 점검(1504)에서만 쓴다.
- 등급 비율 규칙은 만들지 않는다(아이템이 모두 common이라 지금은 효과가 없다).
- 개방 이력은 툴이 기록한 `collection_launch`부터 센다.
- 1502는 1459의 평가 결과를 읽어 표시만 하고 규칙 계산을 따로 만들지 않는다.

**확인한 사실 (2026-10-01 12시 KST, DB 읽기 조회)**
- 포인트가 걸린 배지는 「퀘스트 클리어」 1개(100)뿐이다. 미션 55개는 `reward_points`가 모두 비어 있다. 컬렉션 100개 중 10개에
