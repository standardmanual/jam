### 1회차: 보내는 도구 (화면 없음, 클라우드·DB 영향 없음)

기준: 루틴은 쉘 명령으로 서버를 부르고, 윤진은 `curl`과 직접 명령이 금지라(`.claude/agents/jam-marketer.md` 53~59행) **스크립트 한 개로만** 보낸다. 서비스 롤 키는 쓰지 않고 읽기 토큰(`ADMIN_API_READ_TOKEN`)만 쓴다. 토큰의 쓰기가 열린 경로는 정확히 두 개(`POST /api/admin/ops-inbox`, `POST /api/admin/ops-inbox/routine-start`, 경로 상수는 `jam-web/src/lib/admin/opsInbox/constants.ts`)다.

1. `scripts/ops-submit.mjs` (새, `scripts/admin-api-read.mjs`의 환경변수·오류 처리 방식을 따른다): `node scripts/ops-submit.mjs bundle <묶음.json>`은 파일을 읽어 1MB를 넘으면 보내기 전에 막고 `POST ${ADMIN_API_BASE_URL}/api/admin/ops-inbox`로 보낸다. `node scripts/ops-submit.mjs start <시작.json>`은 16KB를 넘으면 막고 `.../routine-start`로 보낸다. 허용하는 경로는 이 두 개뿐이고 다른 경로 이름이 오면 실패한다. 응답은 요약만 출력한다(상태 코드, `id`, `bundle_id`, `item_count`, `format_errors`, `warnings`. 토큰·본문 전체는 출력하지 않는다). 상태별 문장: 201 받음, 200 이미 같은 묶음을 받음(재시도 안전), 409 같은 `bundle_id`에 다른 내용이라 **새 `bundle_id`로 다시 보내라**, 400 형식 오류(서버가 준 `details`를 그대로), 401·403 토큰 문제, 그 밖은 일반 실패. 종료 코드는 성공 0, 이미 받음 0, 그 밖 1. `ADMIN_API_BASE_URL`은 `https://`이거나 `http://localhost`일 때만 받는다(토큰을 평문으로 보내지 않는다). `ADMIN_API_READ_TOKEN`이 없으면 실행하지 않는다.
2. `scripts/ops-read.mjs` (새): `node scripts/ops-read.mjs <이름>`이 허용 목록의 GET 경로 하나를 읽고 JSON을 그대로 출력한다. 이름→경로: `trend-sources`(`/api/admin/ops-trend-sources`, 켜진 출처만), `patterns-draw`(`/api/admin/ops-patterns/draw`, 조합 뽑기), `rules`(`/api/admin/ops-rules`), `decisions`(`/api/admin/ops-decisions`), `patterns`(`/api/admin/ops-patterns`), `item-paths`(`/api/admin/item-paths`), `kpi-weekly`(`/api/admin/kpi/weekly`), `today-metrics`(`/api/admin/today/metrics`). 각 이름의 정확한 경로·메서드·쿼리는 `jam-web/src/app/api/admin/` 아래 라우트 파일에서 확인해 맞추고(조합 뽑기가 POST면 그에 맞게), 쿼리가 필요한 것은 `--query key=value`로 받는다. 응답이 너무 길면 줄이지 않고(재료 판단은 에이전트 몫) 그대로 낸다. 인증·URL 규칙은 `ops-submit.mjs`와 같다. 새 경로를 더할 때 쓰는 목록은 한 상수 객체 하나다.
3. 시험: `scripts/ops-submit.test.mjs`·`scripts/ops-read.test.mjs`(다른 `scripts/*.test.mjs`와 같은 방식, 로컬 `http.createServer` 가짜 서버로 201·200·409·400·401·네트워크 오류·1MB 초과를 확인하고, 토큰이 출력과 오류 문장에 없고, 허용 밖 경로·`http://` 원격 주소·토큰 없음이 거절됨을 확인한다). **두 경로 상수가 `jam-web/src/lib/admin/opsInbox/constants.ts`와 같은지** 파일 텍스트로 대조하는 시험을 둔다. 임시 저장소를 쓰는 시험은 `GIT_*` 환경변수를 지우고 쓴다.
4. 문서: `.claude/skills/jam-work/references/scheduled-jobs.md`의 「무인 경로에 적용하는 점검」과 「데이터 출처」에 두 스크립트를 허용 명령으로 적고(「예약 실행은 DB 쓰기·DB 변경을 하지 않는다」 문장 70·92줄 부근에는 받은 기획함 제출과 시작 기록 예외를 이미 적었는지 확인하고 빠진 것만 더한다), `docs/agents/contract.json`의 `paths_exist`에 새 스크립트·시험 경로를 더한다(`node scripts/check-contract.mjs`로 확인).

**1회차에서 하지 않는 것**: 에이전트 정의·루틴 스펙 수정(회차 2·3), 클라우드 루틴 등록·실행, 실제 묶음 제출(시험 제출도 이 회차에서는 로컬 가짜 서버로만), `routineCheckStartsAt` 쓰기.

## 0. 준비
- `git fetch origin staging && git checkout staging && git pull --ff-only origin staging`. 모든 작업은 staging 기준이다(기본 브랜치 main은 낡았다).
- 규칙의 원본은 절만 출력해서 읽는다: `node scripts/doc-section.mjs .claude/skills/jam-work/references/scheduled-jobs.md "### 새 체계 주간"`과 같은 파일의 `"### Slack 알림"`(채널 ID 표). 이 프롬프트와 다르면 그 절을 따른다. 「옛 체계」 소절은 읽지도 따르지도 않는다.
- 리포트 파일: KST 기준 이번 주 ISO 주차로 `docs/operations/reports/weekly/YYYY-Www.md`. 이미 있으면 덮어쓰지 말고 `#jam-alert`에 한 줄 알린 뒤 끝낸다.
- 시작 기록: `run_key`를 `weekly-YYYY-Www-HHMM`(KST 시작 시각)으로 정하고, `/tmp`에 시작 파일(`run_key`·`author`·`week`·`agents`)을 써서 `node scripts/ops-submit.mjs start <파일>`을 1회 실행한다(형식은 `jam-web/src/lib/admin/opsInbox/constants.ts`와 routine-start 라우트가 정한다). 실패해도 계속 진행하고 리포트 맨 위에 `시작 기록 실패 (사유)`를 적는다. 최종 묶음의 `routine_run.run_key`에 같은 값을 넣어야 시작 기록과 이어지므로, 이 값을 6번 윤진 호출에 넘긴다.

## 1. 에이전트 호출 (Task 도구, 각각 model sonnet, 한 번씩)
서브에이전트의 시스템 정의는 세션 시작 때 읽은 기본 브랜치(main) 판이라 낡았다(2026-10-28 시험으로 확인). 모든 호출 프롬프트 맨 앞에 「먼저 `.claude/agents/<해당 에이전트>.md`를 Read로 읽고, 시스템 정의와 다르면 읽은 파일을 우선해 따른다」를 넣는다.
에이전트는 서로를 부를 수 없으므로 네가 앞 단계의 결과 전문을 다음 호출에 붙여 넘긴다. 각 호출에 「자기 모드가 허용하는 것만 한다. 웹 검색과 외부 발행은 하지 않는다」를 넣는다. 형식이 틀려 돌아온 경우에만 같은 에이전트를 1회 다시 부른다.
서브에이전트 호출은 비동기로 시작된다. 보고가 돌아오기 전에는 다음 단계로 넘어가지 않고, 보고가 오면 이어서 진행한다. 호출 프롬프트마다 모드 이름을 분명히 적는다(정의가 호출 프롬프트에서 모드를 읽는다).
1. `jam-ops`(카즈하): `ops-weekly.md`와 `forms/weekly-briefing-format.md`를 읽고 브리핑을 쓴다.
2. `jam-marketer`(윤진, 모드 ⑨): 브리핑을 읽고 다음 주 묶음 초안을 쓴다. 이 호출에서는 제출하지 않는다.
3. `jam-designer`(채원): 초안에서 이미지가 필요한 카드만 색을 제시한다. 결과가 없으면 그 카드는 「색 대기」로 둔다.
4. `jam-tribe`(윈터, 모드 ⑥): 세계관과 닿는 항목을 검수하고 채원의 색도 본다. 「중단」 항목은 사유와 함께 뺀다.
5. `jam-pm`(혜린, 주간 밸런스 점검): 항목별 판정(참고·주의·중단)과 확신도를 돌려준다. 「중단」 항목은 사유와 함께 뺀다.
6. `jam-marketer`(윤진, 모드 ⑨): 2~5의 결과를 묶음의 `routine_run.stages`와 `excluded_items`에 반영해 최종 묶음을 만들고 `node scripts/ops-submit.mjs bundle <파일>`로 제출한다. 항목이 0개여도 제출한다. `routine_run.run_key`는 0단계에서 정한 값이다.

## 2. 저장·게시
- 브리핑만 리포트 파일에 저장한다(홈피드 초안·전략 변경안·유형 리뷰는 쓰지 않는다). 맨 위에 수집 실패와 시작 기록 실패를 적고, 「비용」 절에 서브에이전트 결과의 토큰 사용량(없으면 「측정 불가」)과 제출 결과(상태 코드·`bundle_id`·`item_count`·`format_errors`)를 적는다.
- 커밋 전 개인정보 검사: `@` 이메일 형태와 유저와 함께 쓰인 UUID가 없는지 grep한다. `git add docs/operations/reports/weekly/<파일>` 하나만 추가하고 `git commit -m "리포트: 주간 YYYY-Www (예약 작업)"` → `git push origin staging`. 거부되면 `git pull --rebase origin staging` 뒤 1회만 다시 시도한다. main으로 push하지 않는다.
- `node scripts/slack-post.mjs`로 `#jam-report`에 요약 3~5줄과 리포트 링크를 올린다. 제출이 실패했거나 리포트를 만들지 못하면 `#jam-alert`에 한 줄 올린다.

## 하지 않는 것

| 시작 기록 이음 | SQL ①에서 `linked`가 true(`run_key` 일치) | 5-0 문장 점검 |
| 묶음 도착 | SQL ②에서 `is_sample`이 true, `format_errors`가 `[]`, `stages`가 `plan`·`world_review`·`balance_check` | `format_errors` 문장대로 윤진 정의·프롬프트 정정 |
| 화면 | 어드민 받은 기획함에 「시험」 표식으로 보이고 항목마다 이유 칩·강조가 붙음(사용자 눈 확인) | |
| Slack | 「[시험]」 도착 알림과 루틴 한 줄이 보임 | `slack.com` 허용·토큰 점검 |
| 비용 | 서브에이전트 토큰 합계를 로그의 알림에서 합산(본체 사용량은 로그에 없어 「측정 불가」) | |

```sql
-- ① 시작 기록과 이음
select run_key, week, author, agents, started_at, bundle_id is not null as linked
from ops_routine_starts order by started_at desc limit 3;
-- ② 도착한 묶음
select bundle_id, week, author, is_sample, jsonb_array_length(coalesce(raw->'items','[]'::jsonb)) as items,
       format_errors, routine_run->>'run_key' as run_key,
       jsonb_path_query_array(routine_run, '$.stages[*].stage') as stages
from ops_bundles order by received_at desc limit 3;
```

**5-4 월간 시험의 영향**: 클라우드 세션 1회(추정 25~40만 토큰, 이전 월간 실측 20만 7,824에 새 호출이 더해진다). 웹 검색과 출처 6곳 읽기가 있다. DB에 「패턴 제안」 시험 묶음 1개(`is_sample: true`, 승인해도 패턴 사전에 들어가지 않도록 시험 표식이 막는지는 5-3에서 화면으로 먼저 확인한다). Slack은 「[시험]」 한 줄이다. 저장소 변경 없음.

**남는 것과 정리**: 시험 묶음은 사용자가 어드민 「시험 묶음 지우기」로 지운다. 시작 기록 행은 삭제 방법이 없어 남는다(묶음이 지워지면 `bundle_id`가 비워질 뿐이고, 7회차 `routineCheckStartsAt` 이후의 시작만 판정하므로 영향이 없다). Slack 글은 「[시험]」 표시로 남는다. 임시 시험 루틴 `trig_01BVuvkYBTdi52znhr5PEi3J`는 5-1 뒤에 사용자가 화면에서 지운다. 켜기와 첫 실제 실행은 6회차 이후다.
