# [Service] 컬렉션을 장착해서 완성하면 보상 배지가 나오지 않는 문제를 고친다

> 영향 티켓(1450 진행 규칙 4) · 1456 시작 검토 D7에서 발견 · 1500보다 먼저 한다

## 핵심 요약

- 요구사항: 컬렉션 완성 경로가 둘이다. 장착 RPC는 완성 포인트만 주고 보상 배지(`reward_badge_id`)를 주지 않는다(`jam-web/supabase/migrations/179_slot_item_into_book_all_excluded_fallback.sql:118-144`). 동기화 보정은 완성 기록이 이미 있으면 건너뛴다(`jam-web/src/lib/itembook/checker.ts:138-147,162`). 그래서 장착으로 완성한 유저는 보상 배지를 받지 못한다. 지금은 컬렉션 100개 모두 `reward_badge_id`가 비어 있어 드러나지 않았고, 1500이 컬렉션 런칭에서 보상 배지를 채우면 드러난다.
- 구현 계획(2026-10-01 사용자 결정: **장착 즉시 발급 + 동기화 보정**, 두 경로가 같은 발급 함수를 쓴다, DB 변경 없음):
  1. `jam-web/src/lib/itembook/checker.ts`: `checkItemBookCompletion()`의 7단계(보상 배지 발급, 약 179~252줄)를
     `issueItemBookRewardBadges(supabase, userId, books)`로 뽑아 export한다. 동작(보유 확인 → insert → `23505`는 건너뜀,
     타입 불일치 경고 로그)은 그대로 둔다. 5단계(완성 판정, 약 149~165줄)에서 완성됐지만 이미 완성 기록이 있는 북도
     보상 배지 후보에 넣는다(보정). `completedIds`는 지금처럼 새로 완성한 북만 담고, `rewardBadgeIds`·`rewardBadgesIssued`는
     보정 발급분까지 담는다.
  2. 신규 `jam-web/src/lib/itembook/slotReward.ts`: `runSlotRewardIssue(userId, itemBookId)` — 그 유저의 그 북 완성 기록과
     `reward_badge_id`를 읽어, 완성됐으면 1의 함수로 발급하고 발급분이 있으면 `notifyActivityBadgesEarned(service, userId, ids, [])`
     (기존 `activity_recap` 결산)로 알린다. 예외를 던지지 않는다(`runJamActionEvaluation`과 같은 try/catch 형태). `sync.ts`를
     import하므로 `checker.ts`에 두면 순환이 생겨 파일을 나눈다(`jamActionRoute.ts`와 같은 이유).
  3. `jam-web/src/app/api/itembooks/[id]/slot/route.ts` POST 성공 분기(약 115~119줄): 기존 `after()` 안에서 2를 먼저 부르고
     이어서 `runJamActionEvaluation`을 부른다. 해제(DELETE)·교체(PATCH)·실패 분기에서는 부르지 않는다. 응답은 그대로다.
  4. 테스트: 신규 `jam-web/src/lib/itembook/__tests__/reward-badges.test.ts`(새 완성 시 발급, 완성 기록은 있고 배지가 없을 때
     보정 발급, 이미 보유하면 다시 발급하지 않음, `23505` 경합은 오류 없이 건너뜀, `reward_badge_id`가 비면 발급 없음),
     `jam-web/src/app/api/itembooks/[id]/slot/__tests__/route.test.ts`(성공 시 `after()`에 보상 발급이 예약됨, 실패·해제·교체 시
     예약되지 않음).
  5. 문서: `docs/specs/badge-engine/BADGE_ENGINE_UNIFIED.md` 311줄 부근 「아이템북 완성 보정은 `sync.ts`에서만 호출」 서술을
     장착 라우트도 발급한다는 내용으로 고친다.
  - 장착 즉시 발급과 JAM! 판정이 같은 장착에서 함께 배지를 내면 결산이 두 행이 될 수 있다. 드문 경우라 이번 범위에서는 합치지 않는다.
- 관련 파일: `jam-web/src/lib/itembook/checker.ts`(`checkItemBookCompletion` 35줄~, 5단계 149~165줄, 7단계 179~252줄), 신규 `jam-web/src/lib/itembook/slotReward.ts`, `jam-web/src/app/api/itembooks/[id]/slot/route.ts`(POST 성공 분기 115~119줄), `jam-web/src/lib/badge-engine/jamActionRoute.ts`(형태 참고), `jam-web/src/lib/strava/sync.ts:251`(`notifyActivityBadgesEarned`), `docs/specs/badge-engine/BADGE_ENGINE_UNIFIED.md:311`. 원인 근거: `jam-web/supabase/migrations/179_slot_item_into_book_all_excluded_fallback.sql:118-144`(장착 RPC는 포인트만 지급)

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- 원인: 장착 RPC(`179_slot_item_into_book_all_excluded_fallback.sql:118-144`)는 완성 기록과 포인트만 만들고 보상 배지를 주지 않았다.
  동기화 보정은 완성 기록이 이미 있으면 건너뛰어, 장착으로 완성한 유저는 보상 배지를 받지 못했다.
- `checker.ts`: 보상 배지 발급을 `issueItemBookRewardBadges(supabase, userId, books)`로 뽑았다(보유 확인 → insert → `23505` 건너뜀 →
  타입 불일치 경고, 동작은 그대로). 완성 판정에서 완성 기록이 이미 있는 북도 보상 후보로 넣는다. `completedIds`·완성 기록 upsert는 새로
  완성한 북만, `rewardBadgeIds`·`rewardBadgesIssued`는 보정 발급분까지 담는다. 결과를 쓰지 않던 `inventory` 조회는 뺐다.
- 신규 `slotReward.ts`: `runSlotRewardIssue(userId, itemBookId)`가 `reward_badge_id`를 먼저 읽고(없으면 종료) 완성 기록이 있으면 같은
  함수로 발급해 `notifyActivityBadgesEarned`(기존 `activity_recap` 결산)로 알린다. 예외를 던지지 않는다.
- 장착 라우트 POST 성공 분기의 `after()` 한 번 안에서 보상 발급 → `runJamActionEvaluation` 순서로 부른다. 해제·교체·실패 분기와 응답은 그대로다.
- 문서: 아현이 `BADGE_ENGINE_UNIFIED.md` 세 곳(호출 지점 표 장착 행·311줄 부근·§3.16-1 「완성 기록」 행)을 고쳤다. 게이트 WARN에 따라 카리나가
  머지 때 `SERVICE_OPERATIONS.md` 7-4와 운영 플랜 06 §7 사실 메모를 보완했다.
