# [Admin] 운영 묶음 제출 형식에 카드 모양·트라이브·대상·「색 대기」·뺀 항목 칸을 정한다

> 상위: 20260930_1450 · 영향 티켓(진행 규칙 4) · 1502 시작 검토에서 발견, 1502 하위 ①보다 먼저 한다

## 핵심 요약

- 요구사항: 운영 묶음 항목에 카드 모양(`shape`)·노출 대상(`exposure_tags`)·트라이브(`tribe_id`)·「색 대기」(`color_pending`)를, 묶음에 뺀 항목과
  사유(`excluded_items`)를 정해진 칸으로 두고 제출 검증에서 검사한다. 이 칸이 없으면 1502의 겹침·단조로운 흐름·트라이브 거르기·「이미지 제작
  필요」·「색 대기」·「에이전트가 뺀 항목」을 계산할 수 없다.
- 구현 계획: 아래 「구현 계획」 절(파일 단위, 2026-10-01 확정). DB 변경 없이 기존 jsonb(`ops_bundle_items.original`, `ops_bundles.raw`)의
  정해진 키로 읽는다. 칸 읽기 함수는 `jam-web/src/lib/admin/opsInbox/fields.ts` 한 곳에 둔다. 트라이브는 제출과 수정 때 `tribes` 테이블에
  실제로 있는지까지 확인한다.
- 관련 파일: `jam-web/src/lib/admin/opsInbox/validate.ts`(`validateItem` 137행, `validateOpsBundle` 364행 근처), `constants.ts`, `labels.ts`
  (84~113행), `decide.ts`(`revalidateOpsItem` 호출 514·586행), `jam-web/src/app/api/admin/ops-inbox/route.ts`(97행 `validateOpsBundle`),
  새 파일 `jam-web/src/lib/today/shape.ts`·`jam-web/src/lib/admin/opsInbox/fields.ts`, `docs/specs/prd/ops-tool/PRD.md` §3.1(50~79행)·§13.

## 시작 절차

상위 티켓 20260930_1450의 「진행 규칙」과 20260930_1502의 「주요 의사결정」을 따른다. 2026-10-01 착수 때 사용자 결정은 아래 「주요 의사결정」에 있다.

## 주의

- 화요일 루틴과 지금의 홈피드 등록 절차(`registerHomeFeedBundle.mjs`)는 바꾸지 않는다(1450 진행 규칙 7). 이 형식을 실제로 채우는 것은 1504다.
- 마이그레이션을 만들지 않는다. `route.ts` 외의 라우트, `ValidatedOpsBundle`·`ValidatedOpsItem` 타입, `edit.ts`(수정 가능한 칸)는 바꾸지 않는다.

### 테스트 사례

- validate: 카드에 shape 없음 → 필수 오류(fatal 아님) / shape 허용값 밖·숫자 → 허용값 안내, 다섯 모양 통과 / 카드가 아닌 종류는 두 칸이 없어도
  오류 없음, 있으면 형식 검사 / exposure_tags 없음·문자열·빈 배열·허용값 밖·중복 → 각각 다른 문장, 등록 묶음 검사와 같은 입력에 같은 문장(`it.each`) /
  tribe_id 없음·null 통과, 목록에 있는 UUID 통과, 목록에 없는 UUID → 「없는 트라이브」 오류, `'ranger'`·숫자 → UUID 형식 오류, `ctx` 없이 부르면
  형식만 본다 / color_pending 불리언 통과, `'yes'` 오류 / excluded_items 없음·정상 통과, 배열 아님·원소 객체 아님·reason 없음·빈 값·줄바꿈·kind·stage
  허용값 밖 오류, 이 오류는 묶음 오류에만 있다 / 옛 형식 항목(`segment`만)은 fatal 없이 받고 shape·exposure_tags 오류만 붙는다 / `revalidateOpsItem`도
  같은 문장.
- fields: 각 읽기 함수의 정상·없음·형식 틀림 값, 수정본 우선(`color_pending: false` 덮어쓰기 포함), 기존 시험 묶음 고정 사례(`segment`만 있는 항목
  3개 → 모양·대상 `'unknown'`, 트라이브 `null`, 색 대기 `false`, 뺀 항목 `[]`), validate가 오류를 내지 않는 입력과 읽기 함수가 `'unknown'`이 아닌
  입력이 일치하는 계약 사례, `isOpsHomeFeedCard`.
- shape: 모양 5개·이미지 모양 3개, 대소문자 다른 값과 옛 layout 값 거절.
- labels: 새 칸 이름표, `excluded_items[0].reason`은 「뺀 항목 사유」.
- decide: 옛 형식 항목을 고치면 저장되고 새 칸 오류가 붙지만 막지 않는다. 고칠 때 없는 트라이브로 바꾸면 제출 때와 같은 오류.
- route: 옛 형식 묶음 201(오류 문장 포함, `original`의 `segment` 보존), excluded_items 사유 없음 201(묶음 오류만), 없는 tribe_id 201(항목 오류),
  트라이브 조회 실패 500이고 아무것도 저장되지 않음.
