# [Admin] 에셋 생성기에 16:9 비율을 더한다 (1453-a)

> 상위: 20260930_1453 「확정 설계」 5절·11절 조각 a · 결정 0

## 핵심 요약

- 요구사항: 어드민 에셋 생성기의 스테이지 비율에 16:9(1280×720)를 더한다. 프리셋 저장 API의 허용 값과 DB CHECK도 함께 넓힌다.
  기존 세 비율(1:1·4:5·9:16)과 이미 저장된 프리셋은 그대로 동작해야 한다.
- 구현 계획: DB CHECK를 넓히는 마이그레이션 205를 쓰고(실행은 승인 뒤 카리나. 204는 티켓 20261001_1157이 예약했다), 비율 타입·크기 계산·선택지·API 검증을 고친다.
  **DB 확장이 코드보다 먼저다**(1453 결정 16). 코드가 먼저 나가면 16:9 프리셋 저장이 CHECK 위반(500)이 된다.
- 관련 파일:
  - `jam-web/supabase/migrations/205_asset_presets_stage_ratio_16x9.sql`(신규. 번호는 착수 직전에 최신+1인지 다시 확인한다)
  - `jam-web/src/lib/asset-generator/types.ts` 24줄 `StageRatio`
  - `jam-web/src/app/admin/asset-generator/assetGeneratorHelpers.ts` 28~32줄 `resolveStageSize`(지금은 명시 분기가 없는 값을 9:16으로 처리한다), 34~38줄 `STAGE_RATIO_OPTIONS`
  - `jam-web/src/app/api/admin/asset-generator/presets/route.ts` 35줄 `VALID_STAGE_RATIOS`, 92~94줄 검증
  - 비율 문자열을 쓰는 그 밖의 파일(전수 확인 필요): `AssetGeneratorExport.tsx`, `PresetPanel.tsx`, `AssetGeneratorPanel.tsx`, `page.tsx`,
    `AssetGeneratorViewport.tsx`(모두 `jam-web/src/app/admin/asset-generator/`), `jam-web/src/lib/asset-generator/presetSerialize.ts`
  - 테스트: `jam-web/src/app/admin/asset-generator/__tests__/assetGeneratorHelpers.test.ts`, 프리셋 API 테스트(`presets/__tests__/`)
  - 문서: `docs/specs/prd/asset-generator/PRD.md`의 비율 절

## 배경 / 문제 정의

- 1453 결정 0·2: 홈피드 `hero` 카드와 기사 머리 이미지가 16:9 한 장을 잘림 없이 같이 쓴다. 지금 에셋 생성기는 1:1·4:5·9:16만 만든다.
- DB `asset_presets.stage_ratio`는 CHECK로 세 값만 허용한다(`185_asset_presets.sql` 51~53줄). 2026-10-01 기준 프리셋은 2행이다.
- 이 티켓은 비율만 더한다. 홈피드용 16:9·4:5 프리셋을 새로 배치하는 일과 글자수 가이드를 다시 재는 일은 범위 밖이다(1501·1504).
  `target_type` CHECK(`'badge'`만 허용)도 바꾸지 않는다.

## 구현 계획

1. 마이그레이션 205: `asset_presets_stage_ratio_check`를 지우고 `('1:1', '4:5', '9:16', '16:9')`로 다시 만든다.
   되돌림 SQL을 주석으로 함께 남긴다. 되돌림은 16:9 행이 있으면 CHECK 재생성이 실패하므로, 16:9 행을 먼저 정리하는 단계를 넣는다
   (`.claude/skills/jam-work/references/db-migration-rules.md`). 실행 뒤 확인 쿼리(제약 정의 조회, 기존 행 수 불변)도 주석으로 남긴다.
2. `StageRatio`에 `'16:9'`를 더하고, `resolveStageSize`에 16:9 → 1280×720 명시 분기를 둔다. 9:16도 명시 분기로 바꿔 기본값 처리에 기대지 않는다.
3. `STAGE_RATIO_OPTIONS`와 API `VALID_STAGE_RATIOS`에 16:9를 더한다. 비율 문자열을 쓰는 나머지 파일도 같은 값 목록을 쓰는지 확인한다.
4. 가로로 넓은 스테이지가 뷰포트 안에 맞게 축소돼 보이는지 확인한다(내보내기 해상도는 1280×720 그대로).
5. 테스트와 에셋 생성기 PRD를 갱신한다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)
- `resolveStageSize('16:9')`가 1280×720을 반환하고, 1:1·4:5·9:16의 결과는 지금과 같다(단위 테스트).
- 프리셋 API가 `stage_ratio: '16:9'`를 받아들이고, 목록 밖 값은 지금처럼 400으로 거절한다(단위 테스트).
- 마이그레이션 205에 CHECK 확장, 되돌림 SQL(16:9 행 정리 포함), 실행 뒤 확인 쿼리가 있다.
- 에셋 생성기 PRD의 비율 절이 네 비율과 각 해상도를 적는다.
- `scripts/verify.sh`가 통과한다.

### 후속 범위 (담당: 카리나, 시점: 머지 뒤 push 전)
- 사용자 승인 뒤 마이그레이션 205를 실행하고 확인 쿼리 결과를 이 티켓에 적는다. **코드를 staging에 push하기 전에** 실행한다.
- 로컬 어드민에서 16:9를 골라 스테이지가 1280×720 비율로 뷰포트에 맞게 보이는지, 16:9 프리셋 저장·불러오기가 되는지 실렌더로 확인한다
  (`docs/specs/DEV_PROCESS_GUARDRAILS.md` 패턴 13).
