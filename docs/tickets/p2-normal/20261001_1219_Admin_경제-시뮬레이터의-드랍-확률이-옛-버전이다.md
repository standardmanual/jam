# [Admin] 경제 시뮬레이터의 드랍 확률이 옛 버전(v1)이다

> 상위: 20260930_1450 · 영향 티켓(진행 규칙 4) · 20260930_1459 시작 검토에서 혜린이 발견

## 핵심 요약

- 요구사항: `/admin/simulator`의 아이템 드랍 결과가 지금 드랍 엔진과 같은 확률 체계로 나오게 한다. 지금은 v1 상수로 드랍을 굴려서,
  이 결과로 경제를 판단하면 어긋난다.
- 구현 계획: ① 결과 패널에 「드랍은 옛 기준이라 참고용」 고지를 달고 잘못된 주석을 바로잡는다(바로 할 수 있다). ② 드랍 롤을
  `drop-engine`의 순수 함수로 바꾸고 `drop_policy` 값을 읽게 한다. ②는 실측 티켓 20261001_1220와 함께 해도 된다.
- 관련 파일: `jam-web/src/app/api/admin/simulate/route.ts` 20~34행(`RARITY_THRESHOLDS` 40/25/10/5와 주석 「drop-engine과 동일」,
  `rollRarity`), `jam-web/src/lib/drop-engine/policy.ts` 12~15행(엔진 기본값 0.6/0.28/0.09/0.03), `jam-web/src/lib/drop-engine/layers.ts`,
  `jam-web/src/app/admin/simulator/page.tsx`(결과 패널).

## 배경 / 문제 정의

- 시뮬레이터는 등급별 누적 문턱 0.40/0.65/0.75/0.80으로 드랍을 굴린다. 엔진 기본값은 등급 비율 0.6/0.28/0.09/0.03이다
  (2026-10-01 코드 확인).
- 주석이 「drop-engine과 동일」이라 적혀 있어 결과를 그대로 믿기 쉽다. 20260930_1459의 밸런스 규칙은 시뮬레이터 실측값을 근거로
  쓰는 것이 원칙인데, 지금 시뮬레이터로는 그 근거를 만들 수 없다.

## 구현 계획 (파일 단위, 2026-10-01 확정)

사용자 결정 1(아래 「주요 의사결정」)대로 시뮬레이터가 엔진의 판정 단계를 그대로 따라간다. `tryItemDrop`의 동작은 바꾸지 않는다.

1. `jam-web/src/lib/drop-engine/index.ts` — `getDropState`(427행 부근)·`fetchDropStructure`(176행)·`selectBadge`(311행)·`applyShadowBanCap`(472행)·
   `updateLastPiecePity`(404행)에 `export`만 붙인다. 본문과 `tryItemDrop`(568행~)은 고치지 않는다.
2. `jam-web/src/lib/drop-engine/preview.ts`(신규) — 두 층으로 둔다.
   - 순수 함수 `planItemDrops(input, rand)`: 입력은 `policy`·`state`·`structure`·활동·`activityStartDate`·`activityWeight`·등급 상한 함수(섀도우밴, 동기).
     `tryItemDrop`의 판정 순서를 쓰기 없이 따라간다: 일일 카운터 리셋 → 복귀·주간 첫 활동·고강도 판정 → `rollBonusDrop`으로 드랍 개수 →
     드랍마다 슬롯 확인 → `RarityContext` → `rollRarityV2` → 등급 상한 → 맥락 오버라이드(`matchContextTribes`, `context_override_rate`) →
     `selectBadge` → 메모리 안의 상태·구조 갱신(`updateLastPiecePity`, `owned`, `daily_drop_count`, `common_streak`, 마지막 트라이브·북).
     `state`·`structure`는 복사본으로 다뤄 호출부 객체를 바꾸지 않는다. 드랍마다 결과(배지·등급·굴린 등급·트라이브·북·마지막 조각·
     보너스 드랍 여부)나 빠진 이유(`slot_full`·`shadow_ban_blocked`·`no_candidate`)를 돌려준다.
   - 비동기 함수 `previewItemDrop(userId, activity, activities)`: 정책·드랍 상태·드랍 구조·섀도우밴 수준을 읽어 `planItemDrops`를 부른다.
     DB에 아무것도 쓰지 않는다. 파일 머리 주석에 「`tryItemDrop`의 판정 순서를 고치면 여기도 함께 고친다」를 적는다.
3. `jam-web/src/app/api/admin/simulate/route.ts` — 20~43행(`RARITY_THRESHOLDS`·잘못된 주석·`rollRarity`·`weightedPick`)을 지운다. 127~176행(4. 아이템
   드랍)을 `previewItemDrop`으로 바꾼다. 응답은 `itemDrop`(1개) 대신 `itemDrops`(0~2개, 배지 이름·등급·트라이브 이름·컬렉션 이름·보너스 여부)와
   빠진 이유를 돌려준다. 적용 모드(`dryRun: false`)는 지금처럼 고른 배지를 인벤토리에만 넣고(드랍마다 같은 삽입 경로) 유저 드랍 상태는
   갱신하지 않는다.
4. `jam-web/src/app/admin/simulator/page.tsx` — 결과 타입(33행)과 결과 패널(326행 부근)을 `itemDrops` 목록으로 바꾼다. 드랍이 없으면 빠진
   이유를 한 줄로 보인다. 어드민 UI이므로 shadcn 컴포넌트만 쓴다.
5. `jam-web/src/lib/drop-engine/__tests__/preview.test.ts`(신규) — 완료 조건의 대조 테스트. 고정 난수열·정책·상태·구조를 주고,
   `planItemDrops`의 결과가 같은 난수열로 `rollBonusDrop`·`rollRarityV2`·`selectBadge`를 직접 부른 결과와 같은지 본다. 일일 하향·pity·복귀·
   보너스 드랍·슬롯 가득·후보 없음 경우를 포함한다. 입력 객체가 바뀌지 않는지도 본다.
6. `docs/specs/badge-engine/BADGE_ENGINE_UNIFIED.md` — 시뮬레이터를 언급하는 자리(1498행 부근 `/api/admin/simulate` 절 등)에 「아이템 드랍은
   엔진 판정(`previewItemDrop`)을 그대로 따른다」를 반영한다.

크기는 파일 6개·200줄 안팎으로 기준을 넘는다. 하나의 판정 흐름이라 쪼개면 중간 상태가 어긋나므로 파일 단위 계획을 적고 면제로 진행한다.

## 완료 조건

- 시뮬레이터 화면의 드랍 결과가 현재 `drop_policy` 값과 같은 확률 체계로 나온다(같은 난수 입력으로 엔진 함수와 대조하는 테스트).
- 잘못된 주석과 v1 상수가 남아 있지 않다.

### 주요 의사결정 / 핵심 메모

- (사용자 결정 1, 2026-10-01) 시뮬레이터를 엔진 판정과 같은 깊이로 맞춘다. 등급 비율만 맞추는 안과 엔진 본체를 쪼개 공용화하는 안은 고르지
  않았다. 엔진 함수는 바깥에서 쓸 수 있게 열기만 하고 `tryItemDrop`의 동작은 바꾸지 않는다.
- (가정, 카리나) 적용 모드는 지금처럼 고른 배지를 인벤토리에만 넣고, 드랍 상태(연속 common·pity·일일 카운터)·결산 소식·엔진 판정 로그는
  남기지 않는다. 시험 계정의 실제 드랍 흐름을 흔들지 않기 위해서다.
- (가정, 카리나) 섀도우밴 등급 상한도 엔진대로 적용하고, 결과가 바뀌거나 막히면 그 이유를 결과에 보인다. POI 배지 쪽의 「시뮬레이터는 밴과
  무관」 서술(BADGE_ENGINE_UNIFIED 529행)은 POI 발급에 관한 것이라 그대로 둔다.
