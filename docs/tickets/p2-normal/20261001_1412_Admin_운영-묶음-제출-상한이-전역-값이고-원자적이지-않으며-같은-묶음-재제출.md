# [Admin] 운영 묶음 제출 상한이 전역 값이고 원자적이지 않으며 같은 묶음 재제출 확인보다 먼저 걸린다

> `/jam-ship` 2026-10-01 병렬 점검(민지 모드 ②) 범위 밖 발견물. 점검 범위 `efd7be8d..946ebad7`(origin/main → origin/staging).

## 핵심 요약

- 요구사항: 제출 상한(1시간 20건)이 제출자 구분 없는 전역 값이라 토큰 유출이나 에이전트 루프 버그가 상한을 채우면 정상 제출이 429로 막힌다. 건수 확인과 저장이 원자적이지 않아 동시 요청은 상한을 넘을 수 있다. 상한 검사(⑤)가 같은 `bundle_id` 재제출 확인(⑥)보다 앞이라 이미 받은 묶음의 재시도도 429를 받는다. [보안/주의]
- 구현 계획: 재제출 확인을 상한 검사보다 앞에 두고, 상한을 제출자(또는 토큰)별로 나눌지와 원자적 카운트(DB 제약·RPC) 필요 여부를 정한다.
- 관련 파일: `jam-web/src/app/api/admin/ops-inbox/route.ts:117-132`

## 완료 조건

- 이미 받은 `bundle_id`의 재제출은 상한과 무관하게 기존 결과를 돌려준다(테스트).
- 상한 단위와 원자성 결정이 운영툴 PRD에 적혀 있다.

## 완료 기록

### 구현 내용 요약
운영 묶음 제출 라우트(`ops-inbox/route.ts`)에서 시간당 상한 검사가 같은 `bundle_id` 확인보다 앞이어서 이미 받은 묶음의 재제출도 429를 받았다. 같은 `bundle_id` 확인을 상한 검사보다 앞으로 옮겼다. 같은 내용이면 200(이미 받음), 다른 내용이면 409를 상한과 무관하게 돌려주고 새 `bundle_id`는 이전처럼 429가 걸린다. 상한은 전역 값 그대로이고 DB 변경은 없다. 사용자가 2026-11-09 질문 팝업에서 «재제출 확인을 상한보다 앞에»(코드만 고침)를 선택했고, 제출자별 상한과 원자적 카운트는 하지 않기로 결정해 PRD에 의도된 결정으로 적었다.
