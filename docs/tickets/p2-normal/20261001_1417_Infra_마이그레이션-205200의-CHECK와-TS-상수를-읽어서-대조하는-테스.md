# [Infra] 마이그레이션 205·200의 CHECK와 TS 상수를 읽어서 대조하는 테스트를 더한다

> `/jam-ship` 2026-10-01 병렬 점검(민지 모드 ③) 범위 밖 발견물. 점검 범위 `efd7be8d..946ebad7`(origin/main → origin/staging).

## 핵심 요약

- 요구사항: TS 상수와 SQL CHECK를 읽어 대조하는 테스트는 condition key에만 있다. 205 `asset_presets_stage_ratio_check`↔`VALID_STAGE_RATIOS`, 200 `user_combine_fail_logs_reason_check`↔`CombineFailReason`이 지켜지지 않는다(206 `today_cards_shape_check`↔`CARD_SHAPES`는 20261001_1305가 맡는다). 200의 `recipe_not_found` 누락(20261001_0636, CHECK 위반으로 저장이 조용히 실패)과 같은 사고가 다시 날 수 있다. [정확성/주의]
- 구현 계획: `condition-registry.test.ts:530~564`의 SQL 읽기 대조 방식을 두 쌍에 적용한다. 1305와 같은 도우미를 쓰도록 맞춘다.
- 관련 파일: `jam-web/src/app/api/admin/asset-generator/presets/route.ts:35`, `jam-web/src/types/database.ts:601`, `jam-web/supabase/migrations/205_asset_presets_stage_ratio_16x9.sql`, `jam-web/supabase/migrations/200_user_combine_success_logs.sql`, `jam-web/src/lib/badge-engine/__tests__/condition-registry.test.ts:530`

## 완료 기록

### 구현 내용 요약
마이그레이션 SQL의 CHECK와 TS 상수가 어긋나면 실패하는 시험 2건을 새 파일에 더했다. 프리셋 화면 비율(`VALID_STAGE_RATIOS` ↔ `asset_presets_stage_ratio_check`, 최신 205)과 믹스 실패 사유(`CombineFailReason` ↔ `user_combine_fail_logs_reason_check`, 최신 200)다. 최신 CHECK는 그 제약을 ADD하는 마이그레이션 중 번호가 가장 큰 파일을 자동으로 찾고, SQL 주석을 먼저 걷어 되돌림 SQL의 옛 값을 읽지 않는다. `CombineFailReason` 6개 중 `locked_item_not_allowed`·`pending_results_exist` 두 값은 재료를 소각하기 전에 거절해 기록을 남기지 않으므로 시험 안 목록에 사유와 함께 올렸다. 동작 변경은 없다.
