# [API] 투데이 카드 계측에 그려진 모양을 기록하고 모양별로 집계한다 (1453-c2)

> 상위: 20260930_1453 「확정 설계」 9절, 11절 조각 c2 · 결정 4·16·17 · 화면 변화 없음

## 핵심 요약

- 요구사항: 노출·열람 이벤트를 기록할 때 그 카드가 「그려진 모양」을 `today_card_events.card_shape`에 복사하고(`content_type_id`를 복사하는 지금 방식과 같다),
  어드민 집계 API에 모양별 합계 `byShape`를 더한다. 집계 API의 기존 응답(`range`·`types`)은 그대로 둔다(카즈하 브리핑이 읽는다).
- 구현 계획: `assertCardExposable`이 카드를 조회할 때 모양 판정에 필요한 칸을 함께 읽고, 1453-b1의 `drawnShape`로 그려진 모양을 정해 `recordTodayCardEvent`가
  insert한다. 집계 함수는 `card_shape`도 읽어 모양별 건수를 더 돌려주고, API가 `byShape`를 만든다.
  **DB 칸(`card_shape`, `today_cards.shape`)은 마이그레이션 206으로 이미 생겼다**(티켓 20261001_1203, 2026-10-01 실행). 그래서 이 코드는 바로 나가도 조회가 실패하지 않는다(1453 결정 16).
- 관련 파일:
  - `jam-web/src/lib/today/events.ts`: 54~56줄 `ExposableCard`, 64~84줄 `assertCardExposable`(68줄 select), 127~143줄 `recordTodayCardEvent`(133~139줄 insert),
    145~189줄 `TodayCardEventAggregateRow`·`aggregateTodayCardEvents`(167줄 select, 175줄 그룹 키)
  - `jam-web/src/lib/today/__tests__/events.test.ts`(28줄 `builder.select = () => builder`는 select 칸 이름을 보지 않는다. 아래 완료 조건 참조)
  - `jam-web/src/app/api/admin/today/metrics/route.ts` 40~60줄(`byType` → `types`), `jam-web/src/app/api/admin/today/metrics/__tests__/route.test.ts`
  - `jam-web/src/lib/today/shape.ts`(`drawnShape`·`ShapeCardInput`, 1357이 만들었다. 이 조각에서 고치지 않는다)
  - 문서: `docs/service/prd/home-feed/PRD.md` 313줄(「저장에는 카드 ID·기록 시점 유형 ID·이벤트 종류만 남고」), 325줄(`today_card_events` 칸 설명), §9의 조회 API 설명,
    `docs/service/prd/content-automation/PRD.md` 282줄(같은 저장 서술), `docs/service/prd/02_DATA_MODEL.md` 615줄 `today_card_events` 행

## 배경 / 문제 정의

- 1453 결정 4: 지금 유형 ID를 복사하는 방식과 같게 이벤트마다 모양을 복사 저장한다. 모양 열을 먼저 채우고, 패턴 열은 1503 뒤에 채운다. 집계 API는 옛 응답 모양을
  유지하고 항목을 더해 카즈하 브리핑이 깨지지 않게 한다.
- 1453 결정 17: 옛 카드는 b7 전환 전까지 옛 렌더러로 그려진다. 그래서 전환 전에는 `shape`가 없는 옛 카드의 `card_shape`가 NULL이어야 한다(`drawnShape`가 null을 돌려준다).
- GA `today_card_click`의 `shape` 파라미터는 `TodayCardTracker.tsx`를 고치는 b2에서 한다(이 조각은 서버만 다룬다).

## 상세 요구사항

1. `assertCardExposable`의 select에 모양 판정 칸(`shape`·`template_type`·`layout_type`·`cover_image_url`·`badge_ids`)을 더하고, `ExposableCard`에 그려진 모양
   (`CardShape | null`)을 싣는다. 판정은 `drawnShape`를 쓴다. 카드 재조회는 하지 않는다(지금처럼 한 번).
2. 그려진 모양은 화면이 실제로 그리는 모양과 같아야 한다. `cardView.ts`의 `toCardView`가 바꾸는 경우(예: 타일이 0개인 타일형 `list` → `brief`)가 있으면 같은
   규칙을 적용하거나, 두 곳이 한 함수를 쓰게 한다. 차이가 남으면 이유를 완료 기록에 적는다.
3. `recordTodayCardEvent`가 `card_shape`를 insert한다. 유저 식별자는 지금처럼 저장하지 않는다.
4. `aggregateTodayCardEvents`가 `card_shape`도 읽어 모양×이벤트 건수를 돌려준다(기존 유형×이벤트 건수는 그대로). 1,000행 페이지 반복은 유지한다.
5. 집계 API 응답에 `byShape`를 더한다: 모양별 노출·열람·후속 건수와 열람률. `card_shape`가 NULL인 기록은 `unknown`(옛 기록·전환 전 옛 카드)으로 묶는다.
   기존 `range`·`types`의 키와 값은 바꾸지 않는다.
6. 문서: 홈피드 PRD §9·§10과 자동화 PRD 282줄의 저장 서술에 「그려진 모양」을 더하고, 조회 API 설명에 `byShape`를 적는다. 데이터 모델 문서 615줄 행을 맞춘다.
   홈피드 PRD 325줄 「기록 시점에 그려진 모양을 `card_shape`로 복사한다」가 이 조각으로 사실이 된다.

## 완료 조건

- `shape`가 저장된 카드의 노출·열람 기록에 그 모양이 `card_shape`로 들어가고, `shape`가 없는 옛 카드는 `LEGACY_SHAPE_CUTOVER = false`에서 NULL이다(단위 테스트).
- `assertCardExposable`이 실제로 select하는 칸 목록에 모양 판정 칸이 있음을 테스트가 확인한다(지금 `events.test.ts`의 가짜 select는 칸 이름을 보지 않으므로,
  select 인자를 기록해 단언하는 방식으로 보강한다). 카드 조회는 한 번이다.
- 집계 API 응답에 `byShape`가 있고, 기존 `range`·`types`의 형태와 값이 바뀌지 않는다(기존 테스트 그대로 통과 + `byShape` 테스트, `unknown` 묶음 포함).
- 기록에 유저 식별자가 저장되지 않는다(기존 테스트 유지).
- 위 문서들이 갱신됐고 `node scripts/gen-home-feed-doc.mjs --check`와 PRD 동기화 검사가 통과한다.
- `scripts/verify.sh`가 통과한다.

### 주요 의사결정 / 핵심 메모
- 크기 기준 면제는 1453 결정 20에 따랐다. DB 칸은 206으로 먼저 만들어 두어 코드가 바로 나가도 조회가 실패하지 않는다(결정 16).
- 요구사항 2의 남은 차이(티켓이 완료 기록에 적으라고 허용): 화면은 타일 수를 삭제되지 않은 배지로 해석된 수(`resolved_badges`)로 세지만, 계측은 배지를 다시 조회하지 않으려고 `badge_ids` 개수로 갈음한다. 그래서 `badge_ids`가 전부 삭제된 배지인 타일형 list만 화면은 `brief`, 기록은 `list`로 갈린다(`events.ts` 98~106줄 주석).
- 아현 가정: 집계 반환 행을 유형×이벤트에서 유형×모양×이벤트로 세분화했다(기존 단위 테스트 1건에 `cardShape: null` 추가). 응답의 모양 키는 `shape`다.
- `shape.ts`와 `resolveShape` 시그니처·판정 순서는 바꾸지 않았다(1155 영향 없음). b7이 전환 상수를 켜면 「옛 카드 NULL」 테스트가 실패하도록 해 두었다(그때 기대값을 바꾼다).
- 범위 밖 발견물 2건은 1453 확정 설계 11절 b7 메모로 넘겼다: 전환 후 커버 없는 large_thumbnail의 기록 모양과 화면 모양 일치 재확인, 계측 모듈이 화면 모듈(`cardView.ts`)을 런타임 import해 이벤트 API 번들에 한국어 사전이 실리는 구조.
