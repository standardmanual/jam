# [Infra] 운영툴 패턴 사전 ① 문서 선행 수정과 DB 확장

> 상위: 20260930_1503 · 하위 순서 ① · 선행 없음(사용자 결정 Q1~Q5 확정, 2026-10-01) · 유형 `db`(마이그레이션 210·211)

## 핵심 요약

- 요구사항: 07 블루프린트와 운영툴 PRD를 먼저 고쳐 패턴 사전의 구조(원고 전부 담기, 상태 3값, 패턴 제안은 받은 기획함에서 승인)를 확정하고, 패턴 사전 테이블
  3개와 카드·카드 이벤트의 패턴 칸 2개를 마이그레이션 파일로 남긴다. 이 조각은 새 칸을 읽거나 쓰는 코드가 없다. 그래서 DB보다 먼저 나가도 동작이 바뀌지 않고,
  나중 조각들(②~⑬)이 이 구조에 기댄다.
- 구현 계획: 아래 「구현 계획」(파일 단위, 혜린 초안·카리나 확정)을 따른다.
- 관련 파일: 「구현 계획」에 파일·표·줄 위치가 있다.

## 시작 절차

상위 티켓 20260930_1503의 「주요 의사결정」(사용자 결정 Q1~Q5, 가정 목록)이 이 티켓의 전제다. 혜린 검토는 1503에서 끝났으므로 다시 하지 않는다. 그 결정과
다르게 가야 하면 멈추고 사용자에게 확인한다. 마이그레이션은 작성까지만 하고, 실행은 머지 뒤 사용자 승인을 받아 메인 세션(카리나)이 한다. DB는 staging·프로덕션
공용 단일 DB라 실행 즉시 프로덕션에 생긴다.

## 구현 계획

파일 단위 계획이다(혜린 초안, 카리나 확정 2026-10-01). 기준을 넘는 크기(약 10개 파일·600줄)라 이 계획으로 계획 반환을 면제한다. 줄 번호는 2026-10-01
staging(171e3a28) 기준이라 착수 때 표 이름·행 첫 칸으로 다시 찾는다. 순서는 **문서 → SQL → 타입 → 상수와 테스트**다(07 수정이 먼저, 진행 규칙 5).

     - **패턴 번호:** `P01`~`P18`, 새 패턴은 다음 번호(P19~). 번호는 재사용하지 않고 지우지 않는다(보관만). 홈피드 유형 번호 T01과 구분한다.
     - **상태 3값:** 사용 중(조합 뽑기에 나온다) · 쉬는 중(사전과 읽기 응답에는 있고 조합 뽑기에서만 빠진다, 이유 한 줄 필수) · 보관(S5 목록에서 기본 숨김, 읽기 응답
       기본 제외, 조합 뽑기 제외, 번호와 기록은 남는다, 보관한 패턴의 취향 신호는 에이전트가 계속 읽는다). 승인한 제안은 「사용 중」으로 들어간다. 초기 입력은 P14만
       「쉬는 중」(필요한 기능 O12·O14 대기)이다.
     - **패턴 제안 승인 흐름:** 받은 기획함 승인 → 같은 요청에서 사전 입력(실패하면 승인도 되돌린다) → S5에는 「승인 대기 제안 N건」 링크만 둔다(구현은 ⑪).
     - **취향 신호의 추정과 확정:** 폐기 43개의 이유는 처음에 「추정」이다. 운영자가 S5에서 이유를 고치고 확정하면 「확정」이 되고, 같은 패턴 항목의 반려 기록 하나를
       근거로 붙일 수 있다(반려 창은 바꾸지 않는다). 읽기 응답은 추정과 확정을 구분해 싣는다.
     - **읽기 응답 규칙:** 관리자 ID(`updated_by`·`confirmed_by`)를 싣지 않는다. 시험 묶음은 읽기 토큰에서 항상 뺀다.
     - **카드·이벤트 패턴 칸:** `today_cards.pattern_no`와 `today_card_events.pattern_no`(마이그레이션 211)는 운영 항목의 패턴 번호 복사본이다. CHECK·FK 없음, 옛
       카드와 옛 기록은 NULL이다. 채우는 쪽은 카드를 만드는 1500이고 기록하는 쪽은 ⑥이다.

4. **마이그레이션 210** `jam-web/supabase/migrations/210_ops_patterns.sql`(새 파일).
   - `.claude/skills/jam-work/references/db-migration-rules.md`를 먼저 읽는다. 새 테이블 3개만 만드는 확장 단계, 기존 테이블은 바꾸지 않는다. 백필·시드 없음(시드는
     ③의 212). `CREATE TABLE IF NOT EXISTS`·`CREATE INDEX IF NOT EXISTS`로 재실행 가능하게(198·207 선례). `updated_at`은 앱이 직접 갱신한다.
   - **`ops_patterns`**: `pattern_no` TEXT PK CHECK `~ '^P[0-9]{2,}$'` · `name` TEXT NOT NULL · `principle` TEXT NOT NULL · `user_experience` TEXT NOT NULL ·
     `menus` TEXT[] NOT NULL 기본 `{}` · `samples` JSONB NOT NULL 기본 `[]` CHECK 배열(`[{ no, name, role, impl }]`, `role`은 `main`·`aux`·`related`) ·
     `card_shapes` JSONB NOT NULL 기본 `[]` CHECK 배열(`[{ shape, note }]`, `shape`은 앱이 `CARD_SHAPES`로 검사, DB CHECK 없음) · `knobs` JSONB NOT NULL 기본
     `{}` CHECK 객체(`{ condition·place·time·reward: { open, closed }, tribe: { rule, example } }`) · `pitfalls` TEXT NOT NULL 기본 `''` · `status` TEXT NOT NULL
     기본 `active` CHECK `active`·`paused`·`archived` · `pause_reason` TEXT NULL CHECK(`status <> 'paused'`이거나 공백 아닌 값) · `origin` TEXT NOT NULL 기본 `manual`
     CHECK `seed`·`manual`·`proposal` · `origin_item_id` UUID NULL FK → `ops_bundle_items(id)` ON DELETE SET NULL, 값이 있는 행끼리 유일(부분 유일 인덱스) ·
     `created_at`·`updated_at` TIMESTAMPTZ NOT NULL 기본 now() · `updated_by` TEXT NULL(응답에 싣지 않는다).
   - **`ops_pattern_taste_signals`**: `id` UUID PK 기본 `gen_random_uuid()` · `pattern_no` TEXT NULL FK → `ops_patterns(pattern_no)`(NULL이면 공통 취향 신호) ·
     `name` TEXT NOT NULL · `reason` TEXT NOT NULL · `basis` TEXT NOT NULL 기본 `estimate` CHECK `estimate`·`confirmed` · `evidence_decision_id` UUID NULL FK →
     `ops_decisions(id)` ON DELETE SET NULL, CHECK(`evidence_decision_id IS NULL`이거나 `basis = 'confirmed'`) · `confirmed_at` TIMESTAMPTZ NULL CHECK(`basis =
     'estimate'`이거나 값이 있음) · `confirmed_by` TEXT NULL(응답에 싣지 않는다) · `sort_order` INTEGER NOT NULL 기본 0 · `created_at`·`updated_at`. 인덱스
     `(pattern_no)`, 유일 `(COALESCE(pattern_no, ''), name)`(③ 시드 재실행 대비).
   - **`ops_pattern_common_rules`**: `rule_no` INTEGER PK CHECK > 0 · `title` TEXT NOT NULL · `body` TEXT NOT NULL · `created_at`·`updated_at` · `updated_by` TEXT NULL.
   - 세 테이블 모두 `ENABLE ROW LEVEL SECURITY`, 정책 없음(서비스 롤 전용). 테이블·칸마다 `COMMENT`(티켓 번호, 응답에 싣지 않는 칸 표시).
   - 파일 끝 검증 쿼리: 세 테이블 `rowsecurity = true`, `pg_policies` 0개, 상태·출처·근거 CHECK 확인(`pg_get_constraintdef`), 행 수 0.
   - 파일 끝 `-- 되돌림 SQL`: 취향 신호 → `ops_patterns` → 공통 규칙 순서로 `DROP TABLE IF EXISTS`. 되돌리기 전에 `SELECT count(*) FROM public.ops_patterns WHERE
     origin <> 'seed';`와 취향 신호 `basis = 'confirmed'` 수를 확인하고, 0이 아니면 사람이 쓴 내용이 사라진다고 주석에 적는다.
   - **번호는 착수 때 원격 staging 기준으로 다시 확인한다**(1457 ① 20261001_2051이 209를 쓰므로 1503은 210부터). 밀리면 파일 이름과 이 티켓·테스트의 참조만 바꾼다.

## 적용 절차 (머지 뒤, 카리나)

1. 사용자에게 210·211 실행 승인을 받는다(채팅). 한 번의 승인으로 둘을 함께 실행한다.
2. 실행하고 검증 쿼리를 돌린다. 기대값: 세 테이블 RLS true·정책 0개·행 0개, 두 칸 존재·NULL 허용·기존 행 모두 NULL.
3. `generate_typescript_types`로 생성 타입을 대조해 어긋나면 고친다.
4. 02_DATA_MODEL과 PRD §13 E행에 적용일과 확인 결과를 적는다.
