# [API] 운영 묶음 제출 형식에 패턴 번호 확인·지점 카테고리·패턴 제안 칸을 더한다

> 상위: 20260930_1450 · 영향 티켓(진행 규칙 4) · 1503 시작 검토 E1 · 선행: 1503 하위 ③(사전 초기 데이터 입력)

## 핵심 요약

- 요구사항: 이미 구현된 운영 묶음 제출 검증(`jam-web/src/lib/admin/opsInbox/validate.ts` 305~313행)과 운영툴 PRD §3.1 표(62~78행)를 고친다.
  ① `pattern_no`는 `P`+숫자 형태이고 사전에 있어야 한다(없으면 「형식 오류」, 경고만이며 승인은 막지 않는다. 번호 목록 조회는 `loadTribeIds`처럼 제출·수정 때 하고,
  조회 실패면 저장하지 않고 500). ② `knobs.place_category`는 `poi_categories.slug` 문자열 배열(선택). ③ `pattern_proposal` 항목의 내용 칸(`resource.pattern`:
  이름·원리·유저가 겪는 것·메뉴·샘플·카드 모양·손잡이·주의점, 필수는 이름·원리·유저가 겪는 것·손잡이 5종)을 정의한다. 칸 읽기 함수는 `fields.ts` 한 곳에 둔다.
- 구현 계획: 착수할 때 파일 단위로 적는다(약 7개 파일·450줄 추정, 유형 `api`).
- 관련 파일: `jam-web/src/lib/admin/opsInbox/validate.ts` 305~313행, `jam-web/src/lib/admin/opsInbox/fields.ts`, `docs/specs/prd/ops-tool/PRD.md` §3.1.

## 배경 / 문제 정의

1503 ④(조합 뽑기)의 지점 카테고리 순위, ⑪(제안 승인 → 사전), 1504 제출 스크립트가 이 형식에 기댄다. 지금은 `pattern_no`를 문자열·숫자로만 보고 `knobs`는 검사
없이 저장한다.

## 완료 조건

- 사전에 없는 번호·틀린 카테고리·빠진 제안 필수 칸이 항목 `format_errors`에 「경로: 사유」로 들어가고 저장·승인은 막지 않는다(테스트).
- 기존 묶음(시험 묶음 1개)은 다시 검사하지 않고 읽을 때 모름으로 처리한다.
- 직접 수정에서 패턴 제안의 내용 칸은 읽기 전용이다.
- PRD §3.1 표가 갱신됐다.

### 주요 의사결정 / 핵심 메모

- (2056 게이트 범위 밖 발견물, 2026-10-01) 받은 기획함 항목의 `pattern_no`는 지금 문자열·숫자를 모두 받아 `7`·`P-07`도 통과하지만, 패턴 사전 번호는 `^P[0-9]{2,}$`(마이그레이션 210 CHECK)다. ⑪(제안 승인)과 1500(카드 칸 복사)이 값을 그대로 옮기면 어긋나므로, 이 티켓의 형식 검사가 사전 번호 형식을 기준으로 삼는다(`validate.ts:305`).
> 개발 과정에서 검토·결정된 사항, 선택하지 않은 대안과 그 이유.
