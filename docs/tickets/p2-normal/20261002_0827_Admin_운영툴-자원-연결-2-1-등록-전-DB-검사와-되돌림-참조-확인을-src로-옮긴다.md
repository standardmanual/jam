# [Admin] 운영툴 자원 연결 ②-1 등록 전 DB 검사와 되돌림 참조 확인을 src로 옮긴다

> 상위: 20260930_1500 ②(등록 전 검증 공용화)의 앞 절반. 유형 `api`(동작 불변). 1500 G2. ②의 뒤 절반(순수 검사·페이로드 함수의 TS 이전과 항목 → 등록 형식 변환)은
> ②-2로 나눴다(2026-10-02 카리나 규모 사전 판정: 한 티켓이면 약 25파일·1,000줄 이상).

## 핵심 요약

- 요구사항: 등록 스크립트 세 종류(배지·미션·홈피드 카드)의 DB 검사 함수와 `--undo` 전 참조 확인을 `jam-web/src/lib/admin/registerChecks/`의 TS 모듈로 옮기고, 스크립트는
  그 모듈을 가져다 쓴다. 운영툴의 예약 등록(1500 ③ 이후)이 서버에서 같은 함수를 쓰게 하기 위한 준비다. **동작·오류 문장·질의 모양은 바꾸지 않는다.**
- 구현 계획: 아래 「구현 계획 (파일 단위)」. 약 12파일·550줄이라 첫 호출부터 계획 반환 면제를 넘긴다.
- 관련 파일: `jam-web/scripts/asset-generator/registerFlow.mjs`(20·42–82·94–153·286–300행), `registerMissionFlow.mjs`(41–59·71–137·269–282행), `registerHomeFeedFlow.mjs`
  (41–52·64–134·266–279행), 새 폴더 `jam-web/src/lib/admin/registerChecks/`, 문서 `docs/specs/prd/asset-generator/REGISTRATION_BUNDLE.md` 236행, `docs/specs/prd/ops-tool/PRD.md` 586행.

## 착수 전 확인한 사실 (2026-10-02 Explore 지도)

- 세 DB 검사 함수(`runDbChecks`·`runMissionDbChecks`·`runHomeFeedDbChecks`)와 세 되돌림의 참조 확인 반복문은 `node:fs`·`node:path`·`process.argv`를 쓰지 않는다. `supabase`를 주입받는다.
- 세 함수의 결과 모양은 같다: `{ checks: [{ label, status, detail }], errors: string[] }`, `status`는 `통과`·`실패`·`건너뜀`·`해당 없음`. 검사 하나를 기록하는 `add` 보조 함수가
  세 벌(배지 102–123, 미션 79–100, 홈피드 73–94행) 같은 내용으로 있다.
- 세 flow 테스트(`jam-web/scripts/asset-generator/__tests__/registerFlow.test.ts`·`registerMissionFlow.test.ts`·`registerHomeFeedFlow.test.ts`)는 `vi.mock` 없이 손으로 만든 스텁을 넣어
  flow `.mjs`에서만 가져와 부른다. 스텁은 `select`·`eq`·`is`·`in`·`limit`·`maybeSingle`·`then`(배지만 `contains`·`single`)을 갖고, 필터 순서·호출 순서(`events`)·문장을 글자 그대로 본다.
- `.mjs`는 확장자 없는 상대 경로로 `src` TS를 가져온다(예: `registerHomeFeedRecord.mjs` 13행 `../../src/lib/admin/today-sections`, 실행은 `npx tsx`). `export *` 배럴은 tsx에서
  이름이 `default` 아래로 숨는 실측이 있다(`render.mjs` 44–53행).
- 어드민 배지 삭제의 `BADGE_REFERENCE_SOURCES`(`src/lib/admin/badge-references.ts` 93–229행)는 같은 14곳을 다른 질의 방식(`.in` 80개씩, `.order().range()`)으로 센다. 되돌림을
  그 함수로 바꾸면 스텁 테스트가 깨지므로 이번에는 합치지 않는다. `registerFlow.test.ts` 486행이 그 파일 원문을 읽으므로 그 파일은 건드리지 않는다.

## 구현 계획 (파일 단위)

1. **새 `jam-web/src/lib/admin/registerChecks/shared.ts`.** 타입 `RegisterCheck`(`label`·`status`·`detail`)·`RegisterDbCheckResult`, 스텁과 실제 클라이언트를 모두 받는 구조적 최소
   클라이언트 인터페이스(선례: `src/lib/admin/list-counts.ts` 32행, `ranking-mode-references.ts` 41–54행), `errorMessage`, 세 벌의 `add`를 하나로 합친 `createCheckCollector(supabase)`.
   「건너뜀」 문장(「서비스 키(.env.local)가 없어 DB를 읽지 않았어요」)은 그대로 둔다(서버는 늘 클라이언트를 넘기므로 이 문장이 나오지 않는다).
2. **새 `registerChecks/badge.ts`.** `runBadgeDbChecks({ supabase, badge })` ← `registerFlow.mjs` 94–153행 그대로. `findCheckinBadgeNamesNotFoundError`(`@/lib/admin/badge-validation`)가
   `SupabaseClient`를 요구하므로 호출하는 한 곳에서만 타입을 맞추고 사유 주석을 단다.
3. **새 `registerChecks/mission.ts`.** `runMissionDbChecks` ← `registerMissionFlow.mjs` 71–137행 그대로.
4. **새 `registerChecks/homeFeed.ts`.** `runHomeFeedDbChecks` ← `registerHomeFeedFlow.mjs` 64–134행 그대로.
5. **새 `registerChecks/references.ts`.** 상수 `BADGE_UNDO_REFERENCE_TABLES`(← `registerFlow.mjs` 42–63행, 설명 주석 포함)·`BADGE_UNDO_ARRAY_REFERENCE_COLUMNS`(← 65–76행)·
   `BADGE_UNDO_REFERENCES`(← 78–82행, 새로 export)·`MISSION_UNDO_REFERENCE_TABLES`(← `registerMissionFlow.mjs` 41–59행)·`HOME_FEED_UNDO_REFERENCE_TABLES`(← `registerHomeFeedFlow.mjs`
   41–52행). `as const`는 쓰지 않는다(테스트의 타입 단언). 내부 `countUndoReferences(supabase, refs, id)`(순차 await, 외래 키는 `.eq`, 배열은 `.contains`, `select(column, { count: 'exact', head: true })`)와
   판별 함수 `findBadgeUndoReferences`(← 286–300행)·`findMissionUndoReferences`(← 269–282행)·`findHomeFeedUndoReferences`(← 266–279행). throw 문장과 반환 모양(배지 `{ table, column, effect, count }`,
   미션·홈피드 `{ table, count }`)은 지금 그대로.
6. **`registerFlow.mjs`.** 20행 `findCheckinBadgeNamesNotFoundError` import를 registerChecks import로 바꾼다. 42–82행은 import 별칭과 `export { UNDO_REFERENCE_TABLES, UNDO_ARRAY_REFERENCE_COLUMNS }`로
   바꾸고(402·458행이 지역 이름을 쓰므로 `export … from` 한 줄로는 안 된다), 94–153행은 얇은 JS 래퍼 `runDbChecks({ supabase, badge })`로, 286–300행은 `findBadgeUndoReferences` 호출로 바꾼다.
   머리말 8–9행 설명을 고친다. TS 함수를 바로 다시 내보내지 않고 JS 래퍼를 두는 이유: 테스트 호출이 TS 시그니처로 typecheck되면 스텁이 통과하지 못한다.
7. **`registerMissionFlow.mjs`.** 30행 근처 import, 41–59행 재수출, 71–137행 래퍼, 269–282행 판별 함수 호출, 4행 「수정 금지」 문구.
8. **`registerHomeFeedFlow.mjs`.** 41–52행 재수출, 64–134행 래퍼, 266–279행 판별 함수 호출, 4행 「둘 다 고치지 않는다」 문구.
9. **새 테스트 `jam-web/src/lib/admin/registerChecks/__tests__/registerChecks.test.ts`.** 세 DB 검사와 세 판별 함수를 최소 스텁으로 부르는 테스트(통과·실패·조회 오류 각 1건 이상),
   그리고 `registerChecks/*.ts` 원문에 `node:`·`scripts/` import가 없음을 확인하는 계약 테스트(서버에서 가져올 수 있어야 한다).
10. **문서.** `docs/specs/prd/asset-generator/REGISTRATION_BUNDLE.md` 236행 「원본 목록은 `registerFlow.mjs`의 `UNDO_REFERENCE_TABLES` 한 곳」을 `registerChecks/references.ts`로,
    `docs/specs/prd/ops-tool/PRD.md` 586행 「②가 `src/lib`로 옮긴다」를 사실로, `registerRecord.mjs` 135행 주석의 「원본은 `registerFlow.mjs`」를 고친다. 미션·홈피드 등록 묶음 문서의
    frontmatter `code:` 목록에 새 경로가 필요하면 더한다.

## 완료 조건

- `jam-web/src/lib/admin/registerChecks/`의 TS 모듈 다섯 개(shared·badge·mission·homeFeed·references)가 있고, 어느 것도 `node:` 모듈이나 `scripts/` 아래 파일을 가져오지 않는다(계약 테스트).
- 세 flow `.mjs`가 그 모듈을 가져다 쓰고, 지금 내보내는 이름(`runDbChecks`·`runMissionDbChecks`·`runHomeFeedDbChecks`·`UNDO_REFERENCE_TABLES`·`UNDO_ARRAY_REFERENCE_COLUMNS` 등)은 그대로다.
- `jam-web/scripts/asset-generator/__tests__/` 아래 테스트 파일은 하나도 바뀌지 않았고(`git diff --stat` 확인) 모두 통과한다. 특히 세 flow 테스트, `makeHomeFeedCard.test.ts`,
  `applyMissionImagesFlow.test.ts`.
- 오류 문장·검사 라벨·질의 순서가 바뀌지 않았다(위 테스트 통과가 근거). `scripts/verify.sh` 전 항목 통과.
- 구현 계획 10의 문서·주석이 새 위치를 가리킨다.
