# [Admin] 운영툴 자원 연결 ②-2a 카드·미션 순수 검사와 페이로드를 src로 옮긴다

> 상위: 20260930_1500 ②-2의 앞 절반. 유형 `api`(동작 불변). ②-1(20261002_0827)과 같은 방식(얇은 JS 래퍼)이다. 뒤 절반(운영 항목 → 등록 형식 변환)은 ②-2b(20261002_1028).
> JAM! 배지 쪽(`validateBadge`·배지 페이로드)은 ⑨로 미뤘다(2026-10-02 사용자 결정). 배지 검증 모듈이 서버 전용 의존을 끌고 와 실제로 쓰는 ⑨에서 함께 하는 편이 안전하다.

## 핵심 요약

- 요구사항: 홈피드 카드와 미션의 순수 검사 함수(`validateCard`·`validateMission`)와 그 상수·보조 함수, 페이로드 함수(`buildTodayCardInsertPayload`·`buildMissionInsertPayload`)를
  `jam-web/src/lib/admin/registerChecks/`의 TS 모듈로 옮기고, 등록 스크립트는 그 모듈을 감싸서 쓴다. 서버(②-2b)가 같은 검사·변환을 쓰기 위한 준비다. **동작·오류 문장·페이로드 키
  집합은 바꾸지 않는다.** 페이로드 함수에는 서버가 쓸 선택 인자를 더하되, 인자를 주지 않으면 지금과 같은 값을 낸다.
- 구현 계획: 아래 「구현 계획 (파일 단위)」. 약 11파일, jam-web 약 +800/−450줄이라 첫 호출부터 계획 반환 면제를 넘긴다.
- 관련 파일: `jam-web/scripts/asset-generator/registerHomeFeedBundle.mjs`(41–114·116–205·207–333·500–526행), `registerMissionBundle.mjs`(38–107·137–242·381–408행),
  `registerBundle.mjs`(52·56·72행), `jam-web/src/lib/admin/registerChecks/`(새 파일 3개, `__tests__/registerChecks.test.ts` 322–324행), 등록 묶음 문서 2개, `docs/specs/prd/ops-tool/PRD.md` §8.4.

## 착수 전 확인한 사실 (2026-10-02 Explore 지도, HEAD 24f4f67)

- `validateCard`(RHB 207–333)와 `validateMission`(RMB 137–242)은 `node:fs`를 쓰지 않는 순수 함수다. `(errors, card)`·`(errors, warnings, mission)` 모양으로 배열에 push한다.
  카드는 `today-sections`(type import 포함)만, 미션은 `missions/condition-keys`·`missions/gateMissions`·`badge-labels`만 가져온다(서버 전용 의존 없음, 추정).
- 같은 보조 함수 7개(`isPlainObject`·`isNonEmptyString`·`hasControlOrLineBreak`·`isIsoDateTime`·`describeValue`·`unknownKeys`·`checkRequired`)가 세 Bundle 파일에 세 벌 있다.
  `CONTROL_OR_LINE_BREAK`(RB 72)·`UUID_PATTERN`(RB 56)·`AGENT_IMAGE_SOURCE`(RB 52)는 RB가 원본이고 RMB·RHB가 RB에서 가져온다.
- `validateWorldReview`(RMB 109–135, RHB 171–192)와 `validateImage`(이미지·글자 수, fs 사용)는 서버가 쓰지 않으므로 옮기지 않는다. `validate*Bundle`·`readBundleFile`·`findPreviousRecordError`도 .mjs에 남는다.
- 테스트가 가져오는 이름: RHB에서 `CONTENT_TYPE_IDS`·`EXPOSURE_TAGS`·`LAYOUT_TYPES`·`REQUIRED_REFERENCE_FIELDS`·`TEMPLATE_FIELD_KEY`·`TEMPLATE_TYPES`·`buildTodayCardInsertPayload`·
  `validateHomeFeedBundle`, RMB에서 `buildMissionInsertPayload`·`validateMissionBundle`, RB에서 `CONTROL_OR_LINE_BREAK`·`buildBadgeInsertPayload` 등. `registerHomeFeedBundle.test.ts` 140–148은
  상수에 타입 단언을 하므로 `as const`를 쓰지 않는다. 548–558과 `registerMissionBundle.test.ts` 312–320은 페이로드 키 집합을 생성 타입과 대조한다(카드는 `pattern_no`가 없어야 한다).
  `registerRecord.test.ts` 227–231은 `registerRecord.mjs` 원문에 `CONTROL_OR_LINE_BREAK` 이름이 있고 정규식 리터럴이 없어야 한다고 본다.
- tsconfig는 테스트도 typecheck한다. TS 함수를 `.mjs`에서 바로 재수출하면 테스트가 넘기는 `Record<string, unknown>`이 TS 매개변수와 충돌하므로 ②-1처럼 JS 래퍼를 둔다.
- `jam-web/src/lib/admin/registerChecks/__tests__/registerChecks.test.ts` 322–324행은 폴더 파일이 정확히 5개라고 단언하고, 326–334행은 폴더의 모든 `.ts`에 `node:`·`scripts/` import가 없는지 본다.
- `jam-web/src/lib/admin/opsInbox/__tests__/validate.test.ts` 12행이 RHB의 `validateHomeFeedBundle`을 대조용으로 가져온다(그대로 통과해야 한다).

## 구현 계획 (파일 단위)

1. **새 `jam-web/src/lib/admin/registerChecks/bundleRules.ts`.** `UUID_PATTERN`·ISO 시각 정규식·`CONTROL_OR_LINE_BREAK`·`AGENT_IMAGE_SOURCE`와 보조 함수(`isPlainObject`·`isNonEmptyString`·
   `hasControlOrLineBreak`·`isIsoDateTime`·`isPresent`·`describeValue`·`unknownKeys`·`checkRequired`·`visibleLength`). 정규식 원문과 문장은 RB·RMB·RHB 그대로. `as const` 없음.
2. **새 `registerChecks/homeFeedFields.ts`.** RHB 41–114행의 상수(`CARD_REQUIRED_FIELDS`·`CARD_OPTIONAL_FIELDS`·`TEMPLATE_TYPES`·`LAYOUT_TYPES`·`EXPOSURE_TAGS`·`CONTENT_TYPE_IDS`·
   `TEMPLATE_FIELD_KEY`·`REQUIRED_REFERENCE_FIELDS`·`BODY_FORBIDDEN_CONTROL` 등), RHB 165–169·195–205행의 보조 함수(`checkOneLine`·`isFilled`·`checkUuidField`), `validateCard`(207–333행 그대로),
   페이로드 코어 `buildTodayCardInsertPayload(card, { id, coverImageUrl, imageSource?, shape?, titleInImage? })`. 선택 인자를 주지 않으면 지금 값(`image_source = 'agent-generator'`,
   `shape`·`title_in_image` null)이다. 키 집합은 바꾸지 않는다(`pattern_no` 없음).
3. **새 `registerChecks/missionFields.ts`.** RMB 38–107행의 상수·보조 함수(`collectCheck` 포함), `validateMission`(137–242행 그대로), 페이로드 코어 `buildMissionInsertPayload(mission,
   { id, imageUrl, imageSource?, conditionText? })`. 인자를 주지 않으면 지금 값(`image_source = 'agent-generator'`, `condition_text` null)이다.
4. **`registerBundle.mjs`.** 52·56·72행의 `AGENT_IMAGE_SOURCE`·`UUID_PATTERN`·`CONTROL_OR_LINE_BREAK`를 `bundleRules.ts`에서 가져와 같은 이름으로 다시 내보낸다(RMB·RHB·Record·
   `applyMissionImagesFlow.mjs`가 이 이름으로 가져간다). `validateBadge`와 나머지는 그대로 둔다(배지는 ⑨).
5. **`registerHomeFeedBundle.mjs`.** 41–114행 상수는 `homeFeedFields.ts`에서 가져와 같은 이름으로 다시 내보내고, `validateCard` 본문은 TS 호출로, `buildTodayCardInsertPayload`는 얇은 JS 래퍼로
   바꾼다. `validateWorldReview`·`validateImage`·`validateHomeFeedBundle`은 남긴다. 머리말 9행 「고치지 않는다」를 고친다.
6. **`registerMissionBundle.mjs`.** 같은 방식(상수 재수출, `validateMission` TS 호출, `buildMissionInsertPayload` JS 래퍼). 머리말 10행을 고친다.
7. **`registerChecks/__tests__/registerChecks.test.ts` 322–324행.** 폴더 파일 목록을 8개로 고친다(이 한 줄만).
8. **새 테스트 `registerChecks/__tests__/registerFields.test.ts`.** 래퍼와 TS 함수가 같은 결과를 내는지(카드·미션 대표 입력), 선택 인자를 줬을 때의 값(`imageSource: null`, `shape`, `titleInImage`,
   `conditionText`), 키 집합이 그대로인지.
9. **문서.** `docs/specs/prd/asset-generator/HOME_FEED_REGISTRATION_BUNDLE.md`·`MISSION_REGISTRATION_BUNDLE.md`의 frontmatter `code:`에 새 경로, 「규칙 원본」 서술을 TS 모듈로.
   `docs/specs/prd/ops-tool/PRD.md` §8.4 「종류별 검사」 문장에 카드·미션 검사의 위치(`registerChecks/homeFeedFields.ts`·`missionFields.ts`)를 적는다.

## 완료 조건

- `registerChecks/`에 새 TS 모듈 3개(bundleRules·homeFeedFields·missionFields)가 있고, 기존 계약 테스트(`node:`·`scripts/` import 없음)가 새 파일까지 덮어 통과한다.
- 세 Bundle `.mjs`가 지금 내보내는 이름은 모두 그대로다.
- `jam-web/scripts/asset-generator/__tests__/` 아래 테스트 파일은 하나도 바뀌지 않았고(`git diff --stat`) 모두 통과한다. `jam-web/src/lib/admin/opsInbox/__tests__/validate.test.ts`도 통과한다.
- 페이로드 함수는 선택 인자 없이 부르면 지금과 같은 값을 내고, 키 집합이 그대로다(기존 테스트 통과가 근거). `scripts/verify.sh` 전 항목 통과.
- 구현 계획 9의 문서가 새 위치를 가리킨다.
