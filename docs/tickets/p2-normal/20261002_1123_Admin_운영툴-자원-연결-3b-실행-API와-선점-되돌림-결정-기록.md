# [Admin] 운영툴 자원 연결 ③-b 실행 API와 선점·되돌림·결정 기록

> 상위: 20260930_1500 ③의 뒤 절반. 유형 `api`. 선행: ③-a(20261002_1122, 머지 fcee79c).

## 핵심 요약

- 요구사항: `POST /api/admin/ops-inbox/[bundleId]/execute`(운영툴 PRD §11.7)를 만든다. `{ dryRun: true }`는 ③-a의 사전 점검 결과, `{ itemIds }`는 실행이다. 항목 단위 선점(`approved` →
  `preparing` 조건부 update, 하나도 못 차지하면 409), 그룹마다 변환·등록 전 검사·생성·역순 되돌림(핸들러 인터페이스), 상태 갱신(`updated_at` 포함), 결정 기록(`execute`·`fail`, 같은 `batch_id`),
  응답 뒤 슬랙(요약은 `#jam-report`, 실패는 `#jam-alert`), 시험 묶음은 자원을 만들지 않고 `{ "sample": true }`. 테스트는 가짜 핸들러로 한다(실제 카드 핸들러는 ④).
- 관련 파일(2026-10-02 Explore 지도): `jam-web/src/lib/admin/opsInbox/decide.ts`(`bulkApprove` 265–335행이 선점·409·`batch_id`·되돌림 선례, `notifyDecision` 658–672행), `opsInbox/slack.ts`
  (`postOpsSlack` 109–135행, `formatDecisionMessage` 81–106행, 머리말 4–5행), `jam-web/src/app/api/admin/ops-inbox/[bundleId]/decisions/route.ts`(라우트 순서·`after`), `decide.test.ts` 14–139행(스텁),
  `decisions/__tests__/route.test.ts`(라우트 계약 절 259–284행), `maxDuration` 선례 `ambient-drop/deploy/route.ts` 28–29행.

## 착수 전에 정한 것 (2026-10-02 카리나 가정, 사용자 확인 2026-10-02 「이대로 진행」)

1. 자원을 만든 뒤 결정 기록 insert가 실패하면 자원과 상태는 그대로 두고, 서버 로그와 응답 경고(`decisionLogFailed`)를 남기고 `#jam-alert`에 알린다. 결정 경로의 「되돌리고 500」은 이미 만든 자원을
   지워야 해서 쓰지 않는다.
2. 슬랙은 실행 한 번에 `#jam-report` 요약 한 건(「11개 예약 등록, 1개 제외, 1개 실패」)과, 실패가 있을 때 `#jam-alert` 한 건(항목 이름과 사유, 건수 상한)이다. 「제외」는 사전 점검에서 실행하지 못한
   승인 항목(기다리는 중·못 하는 항목)과 그사이 바뀌어 건너뛴 항목의 합이다. `slack_result`는 `batch_id`와 `action`으로 나눠 채운다.
3. 선점이 그룹 일부에서만 되면(동시 실행) 그 그룹의 차지한 항목을 `approved`로 되돌리고 그룹을 건너뛴다(응답의 건너뛴 항목).
4. 「실패로 닫을 항목」(③-a 가정 4)은 요청의 `itemIds`에 없어도 실행 때 함께 `failed`로 닫고 `fail` 기록을 남긴다.
5. 응답·결정 기록·슬랙에는 핸들러의 `reason`(쉬운 문장)만 싣고, DB 오류 원문과 CLI 문장(「서비스 키(.env.local)…」)은 서버 로그에만 남긴다(1500 메모 (2)).

6. (③-a 게이트 뒤 사용자 확정, 2026-10-02) 사전 점검에서 한 항목이 여러 분류에 걸리면 **실패로 닫을 항목 > 못 하는 항목 > 기다리는 중** 순으로 정한다(③-a의 해석 1을 바꿈).
   반려된 대상을 가리키는 항목은 어차피 예약될 수 없으므로 「승인됨」에 남기지 않고 실패로 닫는다.

## 구현 계획 (파일 단위)

1. **`jam-web/src/lib/admin/opsInbox/execute/precheck.ts` 보정(③-a 게이트).** (가) 분류 우선순위를 가정 6으로 바꾼다. (나) `PRECHECK_MESSAGES.startTooSoon`을 정확히 10분 남은 경우에도 맞는 문장
   (「공개 시각까지 10분보다 많이 남아야 해요」)으로 바꾼다. (다) 충돌 사유 문장에서 DB 칼럼 이름을 뺀다(예: 「연결된 미션이 둘 이상이라 카드 하나에 담을 수 없어요」). (라) 「공개 시각이 서로 달라요」
   경고는 이번에 예약할 항목(`ready`)과 결정 전·승인됨 항목끼리만 비교하고, 이미 게재 중·종료된 항목은 빼고 비교한다. `execute/__tests__/precheck.test.ts`를 함께 고친다.
2. **새 `opsInbox/execute/run.ts`(서버 전용).** `decide.ts`의 모양(`DecisionSuccess`·`DecisionFailure`, `fail`·`logError`, 서비스 주입)을 따른다.
   - 항목 열 목록: `id`·`bundle_id`·`position`·`item_key`·`kind`·`status`·`starts_at`·`ends_at`·`pattern_no`·`original`·`edited`·`created_resource`·`format_errors`·`updated_at`(`decide.ts`의 `ITEM_COLUMNS`에는
     `created_resource`·`pattern_no`가 없다).
   - `dryRunExecution(service, bundleId, deps)`: 묶음·항목을 읽고 `precheckBundle` 결과를 돌려준다. 쓰기 없음.
   - `executeBundle(service, { bundleId, itemIds, actor }, deps = { handlers: EXECUTE_HANDLERS, now })`:
     1) 입력 검사(1~60개, UUID, 이 묶음의 항목, `decide.ts` `bulkApprove` 270–288행 패턴). 2) 묶음·항목 읽기. 3) 사전 점검을 다시 해 `itemIds ∩ ready`만 실행하고 나머지 요청 항목은 건너뛴 항목으로 알린다.
     4) 선점: 그 항목들을 `.update({ status: 'preparing', updated_at }).in('id', ids).eq('status', 'approved').select('id')`. 하나도 못 차지하면 409. 5) 가정 3: 그룹 일부만 차지했으면 그 그룹의 차지한 항목을
     `approved`로 되돌리고 건너뛴다. 6) 그룹마다 생성 순서로 검증 단계: 모든 항목에 ID를 정하고(`crypto.randomUUID`) `prepare`(대상 ID는 `linkPlan`에서, 이미 처리된 대상은 `created_resource`에서) →
     `check(asRegisterChecksClient(service), prepared)`. 하나라도 실패하면 그룹 전체 실패(만든 것 없음). 7) 생성 단계: 시험 묶음이면 만들지 않고 `created_resource = { sample: true }`. 아니면 순서대로
     `idFirst`면 `created_resource`를 먼저 적고(`.eq('status','preparing')`) `create`, 아니면 `create` 뒤 적는다. 대상이 바로 앞에서 만들어진 ID를 쓰도록 `prepare`를 다시 부른다. 실패하면 이번에 만든
     자원을 역순으로 `undo`하고 그룹 전체를 실패로 둔다(`undo` 실패는 서버 로그와 실패 사유에 「되돌리지 못한 자원이 있어요」). 8) 상태: 성공은 `preparing` → `scheduled`, 실패는 → `failed`, 가정 4·6의
     실패로 닫을 항목은 `approved` → `failed`. 모두 `updated_at` 갱신(신호의 「실행 실패」가 이 시각으로 센다). 9) 결정 기록: `execute`(예약된 항목마다)·`fail`(실패한 항목마다, `reason` 필수)을 같은
     `batch_id`로 insert. 실패하면 가정 1. 10) 결과: `{ scheduled, failed: [{ id, reason }], skipped: [{ id, reason }], excludedCount, decisionLogFailed? }`.
   - `notifyExecution(service, outcome)`: 가정 2. `postOpsSlack('report', 요약)`, 실패가 있으면 `postOpsSlack('alert', 실패 글)`. `slack_result`는 `.eq('batch_id').eq('action', …)`로 나눠 채운다. 던지지 않는다.
   - 응답·결정 기록·슬랙에는 `ExecuteFailure.reason`만 싣고 `detail`은 `logError`로만 남긴다(가정 5).
3. **`opsInbox/slack.ts`.** 머리말 4–5행(「alert 채널은 뒤 티켓이 쓴다」)을 고치고, `formatExecuteSummaryMessage`(「[시험] 11개 예약 등록, 1개 제외, 1개 실패」)와 `formatExecuteFailureMessage`(항목 이름

## 완료 조건

- 가짜 핸들러로: 선점과 두 번째 실행 409, 동시 실행(가정 3), 그룹 일부 실패 때 역순 되돌림과 그룹 전체 실패, 시험 묶음 `{ sample: true }`, 가정 1·4·5·6, 결정 기록(`execute`·`fail`, 같은 `batch_id`)과
  슬랙 두 갈래·`slack_result` 나눠 채우기를 테스트로 확인한다.
- 지금 레지스트리가 비어 있어 실제 묶음에서는 모든 승인 항목이 「아직 연결하지 않은 종류」로 실행되지 않는다(사전 점검 결과).
- 라우트는 관리자 로그인만 받고(토큰 계약 테스트 무수정 통과), `maxDuration = 60`, 본문 상한이 있고, DB 원문을 응답에 싣지 않는다.
- precheck 보정 (가)~(라)가 테스트와 함께 반영돼 있다. `scripts/verify.sh` 전 항목 통과.
- 운영툴 PRD와 데이터 모델의 `action` 값이 구현을 반영한다.
