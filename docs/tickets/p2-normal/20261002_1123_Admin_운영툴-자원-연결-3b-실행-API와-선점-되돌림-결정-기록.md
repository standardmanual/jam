# [Admin] 운영툴 자원 연결 ③-b 실행 API와 선점·되돌림·결정 기록

> 상위: 20260930_1500 ③의 뒤 절반. 유형 `api`. 선행: ③-a(20261002_1122). 파일 단위 계획은 ③-a 머지 뒤 착수 때 쓴다.

## 핵심 요약

- 요구사항: `POST /api/admin/ops-inbox/[bundleId]/execute`(운영툴 PRD §11.7)를 만든다. `{ dryRun: true }`는 ③-a의 사전 점검 결과, `{ itemIds }`는 실행이다. 항목 단위 선점(`approved` →
  `preparing` 조건부 update, 하나도 못 차지하면 409), 그룹마다 변환·등록 전 검사·생성·역순 되돌림(핸들러 인터페이스), 상태 갱신(`updated_at` 포함), 결정 기록(`execute`·`fail`, 같은 `batch_id`),
  응답 뒤 슬랙(요약은 `#jam-report`, 실패는 `#jam-alert`), 시험 묶음은 자원을 만들지 않고 `{ "sample": true }`. 테스트는 가짜 핸들러로 한다(실제 카드 핸들러는 ④).
- 관련 파일(2026-10-02 Explore 지도): `jam-web/src/lib/admin/opsInbox/decide.ts`(`bulkApprove` 265–335행이 선점·409·`batch_id`·되돌림 선례, `notifyDecision` 658–672행), `opsInbox/slack.ts`
  (`postOpsSlack` 109–135행, `formatDecisionMessage` 81–106행, 머리말 4–5행), `jam-web/src/app/api/admin/ops-inbox/[bundleId]/decisions/route.ts`(라우트 순서·`after`), `decide.test.ts` 14–139행(스텁),
  `decisions/__tests__/route.test.ts`(라우트 계약 절 259–284행), `maxDuration` 선례 `ambient-drop/deploy/route.ts` 28–29행.

## 착수 전에 정한 것 (2026-10-02 카리나 가정, 사용자 확인 대기)

1. 자원을 만든 뒤 결정 기록 insert가 실패하면 자원과 상태는 그대로 두고, 서버 로그와 응답 경고(`decisionLogFailed`)를 남기고 `#jam-alert`에 알린다. 결정 경로의 「되돌리고 500」은 이미 만든 자원을
   지워야 해서 쓰지 않는다.
2. 슬랙은 실행 한 번에 `#jam-report` 요약 한 건(「11개 예약 등록, 1개 제외, 1개 실패」)과, 실패가 있을 때 `#jam-alert` 한 건(항목 이름과 사유, 건수 상한)이다. 「제외」는 사전 점검에서 실행하지 못한
   승인 항목(기다리는 중·못 하는 항목)과 그사이 바뀌어 건너뛴 항목의 합이다. `slack_result`는 `batch_id`와 `action`으로 나눠 채운다.
3. 선점이 그룹 일부에서만 되면(동시 실행) 그 그룹의 차지한 항목을 `approved`로 되돌리고 그룹을 건너뛴다(응답의 건너뛴 항목).
4. 「실패로 닫을 항목」(③-a 가정 4)은 요청의 `itemIds`에 없어도 실행 때 함께 `failed`로 닫고 `fail` 기록을 남긴다.
5. 응답·결정 기록·슬랙에는 핸들러의 `reason`(쉬운 문장)만 싣고, DB 오류 원문과 CLI 문장(「서비스 키(.env.local)…」)은 서버 로그에만 남긴다(1500 메모 (2)).

## 완료 조건 (착수 때 다듬는다)

- 가짜 핸들러로: 선점과 두 번째 실행 409, 동시 실행, 그룹 일부 실패 때 역순 되돌림과 그룹 전체 실패, 시험 묶음 `{ sample: true }`, 결정 기록·슬랙, 원문 비노출을 테스트로 확인한다.
- 라우트는 관리자 로그인만 받고(토큰 계약 테스트 통과), `maxDuration = 60`, 본문 상한이 있다.
- 운영툴 PRD §8.2·§9·§10·§11.7·§13과 데이터 모델의 `action` 값이 구현을 반영한다.
