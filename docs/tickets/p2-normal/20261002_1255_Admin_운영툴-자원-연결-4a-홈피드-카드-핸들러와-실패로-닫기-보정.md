# [Admin] 운영툴 자원 연결 ④-a 홈피드 카드 핸들러와 실패로 닫기 보정

> 상위: 20260930_1500 ④의 앞 절반. 유형 `api`. 선행: ③-b(20261002_1123, 머지 5cf404c). 뒤 절반 ④-b(20261002_1256)는 공개 전 취소 API다.

## 핵심 요약

- 요구사항: 실행 뼈대의 빈 레지스트리에 `home_feed_card` 핸들러를 붙여, 승인된 카드 항목이 예약 등록 실행 때 실제 `today_cards` 행(공개 전)으로 만들어지게 한다. 변환은 ②-2b의
  `toTodayCardRegisterInput`, 등록 전 DB 검사는 ②-1의 `runHomeFeedDbChecks`, 되돌림 전 참조 확인은 `findHomeFeedUndoReferences`를 감싼다. 함께 ③-b 게이트 해석 2(사용자 확정 2026-10-02 「④에서 고친다」)를
  고친다: 실행할 그룹이 없어도 실패로 닫을 항목은 닫고 응답에 싣는다.
- 관련 파일(2026-10-02 Explore 지도, 머지 5cf404c 기준): `jam-web/src/lib/admin/opsInbox/execute/handlers.ts`(`ExecuteHandler` 96–110행, `EXECUTE_HANDLERS` 116행, `asRegisterChecksClient`
  123–125행), `execute/run.ts`(`runGroup` 292–354행, `executeBundle` 390–523행, 실패로 닫기 480–494행, `nothingToRun` 430·434·459행), `execute/precheck.ts` 28행(레지스트리 import),
  `opsInbox/registerInput.ts`(`toTodayCardRegisterInput` 236–347행, `TodayCardRegisterPayload` 66–69행), `registerChecks/homeFeed.ts` 23–70행, `registerChecks/references.ts` 165–175행,
  `execute/__tests__/fakeDb.ts`·`run.test.ts`·`precheck.test.ts`, 운영툴 PRD §8.1(578행)·§8.2(606–653행)·§11.7(1052–1078행)·§13.

## 착수 전에 확인한 것 (2026-10-02 카리나)

- 카드 상세 `/today/[cardId]`(`app/(main)/today/[cardId]/page.tsx` 19–22행)는 `getPublishedArticleCard`(`lib/today/cards.ts` 404–422행)가 `is_active`와 기간으로 걸러 공개 전 카드면 404다.
  목록(`cards.ts` 101–118행)과 계측(`lib/today/events.ts` 73–91행)도 기간을 본다. `today_cards`를 읽는 앱 코드는 모두 service 클라이언트다.
- DB 정책 「today_cards: 인증 유저 읽기」는 `is_active = true`만 본다(`048_today_cards.sql` 43–46행, 2026-10-02 `pg_policies` 조회 결과도 같다). 로그인 유저가 공개 키와 세션으로 PostgREST를
  직접 부르면 공개 전 카드를 읽을 수 있다. 이 일은 별도 티켓 P2 20261002_1257(DB 변경, 사용자 승인 필요)로 넘기고 ④-a를 막지 않는다. 지금 어드민과 등록 스크립트로 만드는 미래 카드도 같은 상태다.

## 착수 전에 정한 것 (2026-10-02 카리나)

1. **나눔.** Explore 추정으로 핸들러와 취소 API를 합치면 12–14파일·약 1,050–1,300줄이라 둘로 나눈다. 이 티켓은 핸들러와 해석 2 보정만 한다. 공개 전 취소 API(`POST …/items/[itemId]/cancel`)는
   ④-b(20261002_1256)이고, ⑤(화면의 취소 확인창)보다 먼저 한다.
2. **순환 import를 피한다.** 레지스트리를 새 `execute/registry.ts`로 옮긴다. 카드 핸들러는 `handlers.ts`의 타입·`RESOURCE_KEY_BY_KIND`·`asRegisterChecksClient`를 가져오고, `handlers.ts`는 카드 핸들러를
   가져오지 않는다. 카드 핸들러와 레지스트리는 순수 모듈 계약(Supabase·서버 모듈 값 import 금지)을 지킨다. ⑤의 요약창이 사전 점검을 거쳐 이 파일들을 끌어오기 때문이다.
3. **사유 문장.** 응답·결정 기록·슬랙에 나가는 `reason`은 아래 고정 문장만 쓴다. DB 오류 원문, 기존 카드 ID, 칼럼 이름, 등록 스크립트용 문장(「이 스크립트 범위 밖」「서비스 키(.env.local)」)은
   `detail`(서버 로그)에만 둔다. 형식 오류는 운영 항목 경로가 붙은 변환 오류 문장이라 첫 문장을 싣는다.

   | 단계 | 경우 | `reason` |
   |---|---|---|
   | prepare | 변환 오류 | 「카드 형식이 맞지 않아요: {첫 오류 문장}」, 2건 이상이면 끝에 「 (외 N건)」 |
   | check | 제목·시작 일시 중복 | 「같은 제목·같은 공개 시각의 카드가 이미 있어요」 |
   | check | 미션 존재 | 「연결한 미션을 찾을 수 없어요」 |
   | check | 컬렉션 존재 | 「연결한 컬렉션을 찾을 수 없어요」 |
   | check | 배지 존재 | 「연결한 배지가 없거나 삭제됐어요」 |
   | check | 랭킹 모드 존재 | 「연결한 랭킹 모드를 찾을 수 없어요」 |
   | check | 실패 문장이 `DB 조회에 실패했어요`로 시작 | 「등록 전 확인 중 DB를 읽지 못했어요」 |
   | check | 표에 없는 라벨 | 「등록 전 확인을 통과하지 못했어요」 |
   | create | insert 오류 | 「카드를 만들지 못했어요」 |
   | undo | 참조 확인이 던짐(기록 있음·읽기 실패) | 「노출 기록이 있거나 확인하지 못해 카드를 지우지 않았어요」 |
   | undo | delete 오류 | 「카드를 지우지 못했어요」 |

4. **create는 정한 ID를 그대로 쓴다.** `run.ts` 336–339행은 `idFirst`이고 돌려준 ID가 정한 ID와 같을 때만 `created_resource`를 다시 쓰지 않는다. 그래서 insert 페이로드의 `id`는 `prepared.id`이고
   돌려주는 값도 `{ id: prepared.id }`다. insert가 오류를 받으면 같은 ID로 delete를 한 번 시도한다(오류 응답인데 행이 생긴 경우 대비. 결과는 `detail`에만 적는다).
5. **undo는 참조 확인 뒤 ID로 지운다.** `findHomeFeedUndoReferences` → `delete().eq('id', resourceId)`. 등록 스크립트의 `image_source` 확인(`registerHomeFeedFlow.mjs` 199–201행)은 운영툴 카드의
   `image_source`가 null이라 쓰지 않는다. 공개 전 여부 확인은 ④-b의 취소가 한다(되돌림은 방금 만든 공개 전 카드만 지운다).
6. **해석 2 보정.** 실행할 그룹이 하나도 없어도(선점할 항목 없음·동시 실행으로 다 건너뜀) 실패로 닫을 항목 블록을 탄다. 결과는 둘로 나눈다.
   - 예약한 항목도 실패로 닫은 항목도 없으면 지금처럼 409 `{ skipped, excludedCount }`다.
   - 하나라도 닫았으면 200(`scheduled: []`)이고, `fail` 결정 기록과 `#jam-alert` 실패 글을 남긴다.

   직접 요청한 실패로 닫을 항목은 응답의 `failed`(닫음) 또는 `skipped`(그사이 바뀜) 중 한 곳에 반드시 나온다.

## 완료 조건

- 승인된 카드 항목 하나로 실행하면 `today_cards`에 공개 전 행이 생기고, `id`가 항목의 `created_resource.today_card_id`와 같으며, 페이로드에 `pattern_no`·보충된 종료 시각·`cover_image_url`·연결 칸이
  들어간다(테스트).
- 등록 전 검사가 실패하거나 insert가 실패하면 그룹 전체가 실패하고, 만든 행은 역순으로 지워진다. `reason`은 가정 3 표의 문장이고, DB 오류 원문(`DB_SECRET`)·카드 ID가 응답·결정 기록·슬랙
  어디에도 없다(테스트).
- 시험 묶음은 등록 전 검사까지 하고 `today_cards`에 쓰지 않는다(테스트).
- 실행할 그룹이 없고 실패로 닫을 항목만 있으면 200으로 닫고 `fail` 기록을 남긴다. 둘 다 없으면 409다. 직접 요청한 실패로 닫을 항목이 응답에 나온다(테스트).
- 미션 등 다른 종류는 여전히 「아직 연결하지 않은 종류예요」로 막힌다.
- 순수 모듈 계약 테스트와 `token-write-contract.test.ts`가 통과하고, `scripts/verify.sh` 전 항목이 통과한다.
- 운영툴 PRD §8.1·§8.2·§11.7·§13이 구현을 반영한다.
