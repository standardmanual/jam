# [Admin] 운영툴 자원 연결 ④-b 공개 전 취소 API

> 상위: 20260930_1500 ④의 뒤 절반. 유형 `api`. 선행: ④-a(20261002_1255). ⑤(화면의 취소 확인창)보다 먼저 한다.

## 핵심 요약

- 요구사항: `POST /api/admin/ops-inbox/[bundleId]/items/[itemId]/cancel`(운영툴 PRD §11.7, 동작 §8.7 818–836행)을 만든다. 예약됨 항목의 자원을 공개 전에 지우고 항목을 「취소」로 둔다.
  - 그 항목을 가리키는 항목도 함께 취소한다. 그중 게재 중인 항목이 있으면 409다.
  - 운영툴 밖의 참조가 있으면 409다. 카드는 `findHomeFeedUndoReferences`로 확인한다.
  - 공개 시각이 지났으면 서버가 자원을 다시 읽어 확인하고 409다. 지울 때도 공개 시각 조건을 함께 건다(가정 2).
  - 사유는 500자까지 받는다. 결정 기록은 `cancel`(함께 취소한 항목은 같은 `batch_id`), 슬랙은 `#jam-report`다.
- ④-a에서 넘김(2026-10-02, 민지 범위 밖 발견물): 카드 insert가 실패한 항목에도 만들어지지 않은 카드 ID가 `created_resource.today_card_id`에 남는다(`idFirst`, `run.ts` 326행). 취소 대상은 「예약됨」뿐이라
  보통 닿지 않지만, 자원을 다시 읽을 때 행이 없으면 오류가 아니라 「밖에서 지워짐」으로 다룬다(PRD §8.6과 같은 뜻).
- 관련 파일(2026-10-02 카리나 확인, 머지 ceb8d4d 기준): `jam-web/src/lib/admin/opsInbox/constants.ts` 66–77행(결정 기록 값), `execute/handlers.ts`(`ExecuteHandler`), `execute/homeFeedCard.ts`, `execute/groups.ts`
  (`pairOf` 57행·`isNotYetCreated` 69행·`resolveLinkGraph` 90행은 내부 함수, `referencersOf` 210–236행은 아직 만들지 않은 항목만 따라가 취소에는 맞지 않는다), `execute/run.ts`(`loadBundleItems` 140–159행·
  `itemLabelOf` 161행·`postAndRecord` 534행·`notifyExecution` 557행), `opsInbox/slack.ts`(`formatExecuteSummaryMessage` 128행), `app/api/admin/ops-inbox/[bundleId]/execute/route.ts`(라우트 선례),
  `execute/__tests__/fakeDb.ts`(`gt` 없음)·`fixtures.ts`(`fakeHandler` 64–74행), `precheck.test.ts`의 순수 모듈 계약(서버 흐름 `run.ts`만 뺀다), 운영툴 PRD §8.7(818–836행)·§10·§11.7,
  `docs/specs/prd/02_DATA_MODEL.md`의 `ops_decisions`. `ops_decisions.action`에는 CHECK가 없어 DB 변경이 없다(`198_ops_inbox.sql` 24–25·114행).

## 착수 전에 정한 것 (2026-10-02 카리나)

1. **핸들러에 취소 메서드를 더한다.** `ExecuteHandler`에 필수 메서드 `cancel(service, resourceId, { now }): Promise<CancelResult>`를 둔다. `undo`(실행 중 되돌림)와 나누는 이유는 공개 전 확인이 취소에만
   필요하기 때문이다. `CancelResult`는 `{ ok: true; missing: boolean } | { ok: false; code: 'published' | 'referenced' | 'error'; failure: ExecuteFailure }`다. 가짜 핸들러(`fixtures.ts`)는 늘 성공하는 `cancel`을 갖는다.
2. **카드 취소(`homeFeedCard.ts`의 `cancel`).**
   - 행을 읽는다(`id, starts_at`). 없으면 `{ ok: true, missing: true }`(밖에서 지워짐).
   - `starts_at <= now`면 `published`다.
   - `findHomeFeedUndoReferences`가 던지면 `referenced`다(기록이 있는 경우와 읽기 실패를 문장으로 가를 수 없어 둘 다 409로 둔다).
   - 지울 때 `delete().eq('id', id).gt('starts_at', nowIso).select('id')`로 공개 시각 조건을 함께 건다. 지운 행이 0이면 다시 읽어서, 있으면 `published`(그사이 공개 시각이 지남), 없으면 `missing`이다.
   - 고정 사유: `published` 「공개 시각이 지나 취소할 수 없어요」, `referenced` 「노출 기록이 있거나 확인하지 못해 카드를 지우지 않았어요」, `error` 「카드를 지우지 못했어요」. DB 원문은 `detail`에만 둔다.
3. **함께 취소할 항목.** 새 `groups.ts` 함수(예: `cancelSetOf(items, itemId)`)가 연결 그래프로 「이 항목을 직접 또는 다른 항목을 거쳐 가리키는 항목」을 찾는다. 상태에 따라 나눈다.
   - 예약됨: 함께 취소하고, 그 너머도 따라간다.
   - 게재중: 막는 항목이다. 하나라도 있으면 아무것도 취소하지 않고 409 「이 항목을 가리키는 항목이 이미 게재 중이에요. 그 항목을 먼저 종료해 주세요.」.
   - 준비중: 막는 항목이다. 409 「예약 등록이 진행 중인 항목이 있어요. 잠시 뒤 다시 시도해 주세요.」.
   - 그 밖(결정 전·승인됨·종료·반려·취소·실패): 건드리지 않는다. 승인됨 항목은 다음 사전 점검이 「실패로 닫을 항목」으로 닫는다(§8.2).
   - 가리키는 대상(취소 항목이 가리키는 쪽)은 그대로 둔다(§8.7).
4. **흐름(`execute/cancel.ts`, 서버 흐름).**
   - 묶음과 항목을 읽는다(`run.ts`의 `loadBundleItems`·`ITEM_COLUMNS`를 내보내 같이 쓴다). 항목이 묶음에 없으면 404, 「예약됨」이 아니면 409 「예약됨 항목만 취소할 수 있어요」.
   - 함께 취소할 항목을 정하고 3의 막는 항목을 본다. 종류에 핸들러가 없으면 409 「아직 취소를 연결하지 않은 종류예요」.
   - 시험 묶음이면 자원 단계를 건너뛴다(`{ sample: true }`라 자원이 없다). 그래서 시험 묶음으로 「예약 → 취소」 한 바퀴를 DB 자원 없이 돌 수 있다.
   - 실제 묶음이면 되돌림 순서(`orderForUndo`, 가리키는 쪽 먼저)로 `cancel`을 부르고 첫 실패에서 멈춘다. 첫 항목에서 실패하면 아무것도 지우지 않은 것이라 `published`·`referenced`는 409, `error`는 500이다.
     앞 항목을 지운 뒤 실패하면 지운 항목만 취소로 두고 500 `{ error, cancelled }`와 `#jam-alert` 글을 남긴다(지금은 카드만 연결돼 있어 함께 취소할 항목이 생기지 않는다).
   - 상태: `scheduled` → `cancelled` 조건부 update(`updated_at` 포함, `.select('id')`). 바뀌지 않은 항목은 서버 로그를 남긴다. 자원이 없는 「예약됨」은 ⑦이 맞춘다.
   - 결정 기록: 취소한 항목마다 `cancel` 1행, 같은 `batch_id`, `reason`은 운영자가 적은 사유(없으면 null). insert가 실패하면 자원과 상태는 그대로 두고 응답 경고 `decisionLogFailed: true`와 `#jam-alert`(③-b 가정 1과 같다).
   - 응답: 200 `{ ok: true, cancelled: [항목 ID], missing: [자원이 이미 없던 항목 ID] }`.
5. **미리 보기.** 같은 경로에 `{ dryRun: true }`를 받는다. 쓰기 없이 `{ ok: true, dryRun: true, cancelIds, blockers: [{ id, reason }] }`를 돌려준다. ⑤의 확인창이 「함께 취소될 항목」을 보이는 데 쓴다.
6. **슬랙.** 응답 뒤(`after`) `#jam-report`에 한 건: 「[시험] 공개 전 취소 N건」과 항목 이름(「종류 · 공개 시각(KST)」, 5건까지·나머지 「외 N건」). 4의 부분 실패와 결정 기록 실패는 `#jam-alert`에 한 건.
   `slack_result`는 `batch_id`와 `action`(`cancel`)으로 채운다. 던지지 않는다.
7. **라우트 `POST /api/admin/ops-inbox/[bundleId]/items/[itemId]/cancel`.** `getAdminUser()` 403 → 두 ID `isUuid` 400 → 본문 16KB 이하 JSON 객체 → `{ dryRun: true }`이거나 `{ reason? }`(문자열, 앞뒤 공백을 뺀
   500자 이하, 빈 문자열은 없음으로 본다) → 실행 → `after(() => notifyCancel(...))`. `export const maxDuration = 60`. 500은 고정 문장이고 DB 원문을 싣지 않는다. 주석에도 제출 토큰 래퍼 함수 이름을 쓰지 않는다.

## 완료 조건

- 예약됨 카드 항목을 취소하면 `today_cards` 행이 지워지고 항목이 「취소」가 되며 `cancel` 기록이 남는다(테스트).
- 공개 시각이 지난 카드, 노출 기록이 붙은 카드, 게재 중인 항목이 가리키는 항목은 409이고 아무것도 지우지 않는다(테스트).
- 시험 묶음의 예약됨 항목은 자원 쓰기 없이 취소된다(테스트). 미리 보기는 쓰기 없이 함께 취소할 항목과 막는 항목을 돌려준다(테스트).
- 응답·결정 기록·슬랙에 DB 오류 원문이 없다(테스트). 라우트는 관리자 로그인만 받고 `token-write-contract.test.ts`가 고치지 않고 통과한다.
- `scripts/verify.sh` 전 항목 통과. 운영툴 PRD §8.7·§10·§11.7·§13과 `02_DATA_MODEL.md`가 구현을 반영한다.
