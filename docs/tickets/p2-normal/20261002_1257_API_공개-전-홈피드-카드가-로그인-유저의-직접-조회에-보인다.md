# [API] 공개 전 홈피드 카드가 로그인 유저의 직접 조회에 보인다

> 발견: 1500 ④-a(20261002_1255) 착수 전 확인(2026-10-02 카리나, Explore 탐색).

## 핵심 요약

- 현상(확인한 사실):
  - `today_cards`의 SELECT 정책 「today_cards: 인증 유저 읽기」는 `is_active = true`만 본다. 근거는 `jam-web/supabase/migrations/048_today_cards.sql` 43–46행이고, 2026-10-02 `pg_policies`
    조회 결과도 `qual = (is_active = true)`로 같다.
  - 로그인 유저는 공개 키와 자기 세션으로 PostgREST를 직접 불러 공개 전(`starts_at`이 미래)·종료된 카드를 목록째 읽을 수 있다.
  - 앱 화면과 API는 막혀 있다. 목록(`lib/today/cards.ts` 101–118행), 상세(`cards.ts` 404–422행, `app/(main)/today/[cardId]/page.tsx`), 계측(`lib/today/events.ts` 73–91행)이 기간을 거른다.
  - `today_cards`를 읽는 앱 코드(`jam-web/src`, 2026-10-02 grep)는 모두 service 클라이언트를 쓴다. 사용자 세션 클라이언트로 읽는 곳은 없다.
- 영향: 예약 공개할 캠페인 카드의 제목·문구·이미지 주소가 공개 전에 새어 나갈 수 있다. 운영툴 자원 연결(1500)이 미래 카드를 늘린다. 지금 어드민과 등록 스크립트로 만드는 미래 카드도 같은 상태다.
- 구현 계획(안): 정책에 기간 조건(`starts_at <= now()` 등)을 더하거나, 앱이 쓰지 않으므로 인증 유저 SELECT 정책을 없앤다. 착수 때 Realtime·RPC·뷰 등 정책에 기대는 경로가 있는지 다시 확인한다.
  DB 변경이라 사용자 승인 뒤 메인 세션이 실행한다(확장→전환→축소 규칙과 되돌림 SQL 포함).
- 경미한 같은 종류: 계측 API의 오류 문장이 「카드를 찾을 수 없습니다」와 「노출 기간이 아닌 카드입니다」로 달라 카드가 있는지 알 수 있다(`events.ts` 84–90행).
- 사용자 결정(2026-10-02 「1, 2 모두 승인」): 고친다. 마이그레이션 실행은 파일명·영향 범위·되돌림 SQL 위치를 보인 뒤 다시 승인받는다(`docs/agents/orchestrator.md` §4).

## 착수 전에 확인한 것 (2026-10-02 카리나, 라이브 DB 읽기 전용 조회)

- `today_cards`를 읽는 뷰·구체화 뷰·함수(정의에 `today_cards`가 들어간 것)가 없고, Realtime 발행(`pg_publication_tables`)에도 없다. 그래서 이 정책에 기대는 DB 쪽 경로가 없다.
- 테이블 권한은 `anon`·`authenticated` 모두 Supabase 기본값(전체 권한)이고 RLS가 막는다. 정책은 위 SELECT 하나뿐이라 `anon`은 읽을 수 없고 두 역할 모두 쓸 수 없다.
- 마이그레이션 번호 212는 1503 ③(시드)이 예약했으므로 이 티켓은 214를 쓴다.

## 착수 전에 정한 것 (2026-10-02 카리나)

1. 정책을 없애지 않고 기간 조건을 더한다: `is_active = TRUE AND starts_at <= now() AND ends_at >= now()`. 원래 정책의 뜻(인증 유저는 지금 보이는 카드를 읽을 수 있음)을 유지하고, 앱의 목록 조회
   (`cards.ts` 113–115행)와 같은 기간 조건이 된다. 노출 태그(`exposure_tags`) 거르기는 정책에 넣지 않는다(지금 공개된 카드라 노출 위험이 아니다).
2. 컬럼·함수 변경이 없는 정책 교체라 확장→전환→축소로 나누지 않는다. 한 파일 안에서 `DROP POLICY IF EXISTS` → `CREATE POLICY`(같은 이름)이고, 되돌림 SQL은 원래 정책(`is_active = TRUE`)을 다시 만드는 것이다.
3. 계측 API의 오류 문장 차이(위 「경미한 같은 종류」)는 이번에 고치지 않는다(DB 변경과 무관한 API 문장이고, 앱 화면에서 카드 ID를 알 수 없다).

## 구현 계획 (파일 단위)

1. **새 `jam-web/supabase/migrations/214_today_cards_select_period.sql`.** 머리 주석(티켓·이유·영향: 앱 코드는 service 클라이언트라 동작 불변), `DROP POLICY IF EXISTS "today_cards: 인증 유저 읽기" ON
   public.today_cards;` → `CREATE POLICY "today_cards: 인증 유저 읽기" ON public.today_cards FOR SELECT TO authenticated USING (is_active = TRUE AND starts_at <= now() AND ends_at >= now());`, 파일 끝
   `-- 되돌림 SQL` 주석 블록(`db-migration-rules.md` §4 형식). 048의 정책 주석(42행 「노출조건/기간 필터는 애플리케이션 레벨에서 추가 적용」)이 낡게 되므로 214 머리 주석에 그 사실을 적는다(048은 고치지 않는다).
2. **`docs/specs/prd/02_DATA_MODEL.md` 643행 `today_cards`.** RLS 서술을 더한다: 인증 유저 SELECT는 `is_active`이고 노출 기간 안인 행만(마이그레이션 214, 이 티켓), 쓰기 정책 없음, 앱은 service 클라이언트로 읽는다.
3. `docs/specs/prd/home-feed/PRD.md`에는 RLS·「인증 유저」 서술이 없어 고치지 않는다(2026-10-02 grep).
4. 규칙 5(환경 서술)에 따라 새 사실 서술에 대응하는 검사 줄이 필요하면 `docs/agents/contract.json`에 더한다(예: 214 파일에 기간 조건 문자열이 있는지).
