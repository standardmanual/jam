# [Admin] 운영툴 자원 연결 ⑤-b 공개 전 취소 확인창

> 상위: 20260930_1500 ⑤의 뒤 절반. 유형 `admin`(MODULAR·채원 판정 제외). 선행: ⑤-a(20261002_1648, 머지 98d0ad4c), ④-b(머지 b15b8404).

## 핵심 요약

- 요구사항: 예약됨 항목의 상세(`detailFooter`)에 [공개 전 취소하기]를 두고, 확인창이 미리 보기(`{ dryRun: true }` → `cancelIds`·`blockers`)로 함께 취소될 항목과 막는 항목을 보인 뒤 사유(선택, 500자)를 받아
  취소한다(운영툴 PRD §8.7 822–827행, §11.7 취소 행). 되돌릴 수 없다는 문장과 위험 톤을 쓴다.
- ⑤-a에서 넘김(2026-10-02, 민지 범위 밖 발견물): `executeClient.ts`의 `postExecute`와 `decisionClient.ts`의 `postDecision`이 같은 순서(fetch → 네트워크 오류 → JSON 읽기 → 오류 문장)를 두 벌 쓴다.
  취소 요청을 더할 때 공용 도우미로 합쳐 세 벌이 되지 않게 한다.
- 관련 파일(2026-10-02 Explore): `components/admin/ops/OpsItemActions.tsx`(반려 확인창 `OpsRejectPanel` 85–126행이 사유 칸 선례, 상태별 안내 `decisionGuidance` 27–34행·일찍 return 144–146행),
  `OpsDecisionWorkspace.tsx`(`detailFooter` 189–197행), `OpsConfirmDialog.tsx`, ⑤-a의 `executeClient.ts`, 서버 `execute/cancel.ts`·라우트 `items/[itemId]/cancel`.

## 착수 전에 정한 것 (2026-10-02 카리나)

1. **자리.** `OpsDecisionWorkspace.tsx`의 `detailFooter`(224–232행)에서 항목이 「예약됨」이면 새 `OpsCancelItem`을, 아니면 지금처럼 `OpsItemActions`를 그린다. `OpsItemActions`는 고치지 않는다.
   `OpsCancelItem`은 안내 한 줄 「예약된 항목이에요. 공개 시각 전에는 취소할 수 있어요」와 버튼 [공개 전 취소하기](외곽선 변형, 붉은 면은 확인창의 확인 버튼 하나뿐이라는 선례)를 그린다.
2. **확인창.** `OpsDialogShell`·`OpsConfirmPanel`을 쓰고 `tone="destructive"`다. 열 때 미리 보기(`{ dryRun: true }`)를 보낸다. 불러오는 동안 「함께 취소될 항목을 확인하는 중이에요」.
   - 제목 「이 항목을 공개 전에 취소할까요?」, 설명은 항목 한 줄 요약(`itemSummaryLine`).
   - 「함께 취소될 항목 N개」: 미리 보기의 `cancelIds`에서 이 항목을 뺀 것이 있을 때만, 항목마다 한 줄 요약(`ctx.items`에서 찾는다).
   - 「취소를 막는 항목 N개」: `blockers`가 있으면 항목마다 한 줄 요약과 서버 이유. 이때 확인 버튼을 끈다.
   - 사유 칸: 라벨 「취소 사유(선택)」, `Textarea`, `MAX_DECISION_REASON_CHARS` 카운터, 도움말 「결정 기록에 남아요」. 비워도 된다(④-b 해석 1).
   - 마지막 줄: 「공개 전 취소는 되돌릴 수 없어요. 예약해 둔 자원도 지워져요」. 시험 묶음이면 둘째 문장 대신 「시험 묶음이라 지울 자원은 없어요」.
   - 버튼: 보조 「닫기」(기본값 「취소」가 확인 버튼과 겹친다), 주 「공개 전 취소하기」(함께 취소될 항목이 있으면 「N개 공개 전 취소하기」, N은 이 항목 포함), 진행형 「취소하는 중」.
   - 미리 보기 요청이 실패하면 창 안에 서버 문장을 보이고 확인 버튼을 끈다.
3. **결과.**
   - 성공: 창을 닫고 토스트. 「공개 전에 취소했어요」(1개), 「N개를 공개 전에 취소했어요」(2개 이상). `decisionLogFailed`면 경고 토스트 「결정 기록을 남기지 못했어요. 취소는 그대로예요.」. 끝나면 `router.refresh()`.
   - 409: 창 안에 서버 문장(`decisionFailureMessage`가 「화면을 새로 불러왔어요」를 붙인다)과 화면 새로 읽기.
   - 500에 `cancelled`가 있으면(일부만 취소) 창 안에 서버 문장과 화면 새로 읽기. 그 밖의 500·네트워크 오류는 창 안에 문장만.
4. **요청 코드 합치기(⑤-a 범위 밖 발견물).** `decisionClient.ts`에 던지지 않는 공용 도우미(예: `postOpsJson(url, body)` → `{ ok, status, error, data }`)를 두고 `postDecision`·`postExecute`·새 `postCancel`이
   쓴다. `postDecision`은 지금처럼 `fieldErrors`를 덧붙인다. 바깥 동작(반환 모양·문장)은 바꾸지 않는다.
5. 실렌더 확인은 머지 뒤 PC 세션에서 카리나가 한다(⑤-a와 함께, 시험 묶음으로 「예약 → 취소」 한 바퀴).

## 구현 계획 (파일 단위)

1. `components/admin/ops/decisionClient.ts`: 공용 도우미(가정 4), `postDecision`을 그 위로 옮긴다.
2. `components/admin/ops/executeClient.ts`: `postExecute`를 도우미로 옮기고 `postCancel(bundleId, itemId, body: { dryRun: true } | { reason?: string })`를 더한다(머리 주석의 「⑤-b가 더한다」 갱신).
3. `lib/admin/opsInbox/executeView.ts`: 취소 문장 상수(안내·제목·구역 제목·마지막 줄·시험 묶음·토스트·버튼)와 순수 함수(미리 보기 응답 → 함께 취소될 항목·막는 항목, 버튼 문구, 결과 토스트).
4. 새 `components/admin/ops/OpsCancelItem.tsx`: 안내·버튼·확인창(가정 1~3). 패널은 포털 밖 알맹이(`OpsCancelPanel`)로 나눠 정적 렌더 테스트가 쓰게 한다(`OpsRejectPanel` 선례).
5. `OpsDecisionWorkspace.tsx`: `detailFooter` 분기, 취소 뒤 처리기(토스트·refresh·409). `isSample`을 넘긴다. 머리 주석의 `detailFooter` 설명을 고친다.
6. 테스트: 새 `__tests__/cancelItem.test.tsx`(패널 정적 렌더: 함께 취소될 항목·막는 항목과 꺼진 버튼·시험 묶음 문장·사유 카운터·버튼 문구), `executeClient.test.ts`(`postCancel` 200·409·500·네트워크),
   `executeView.test.ts`(취소 순수 함수), `render.test.tsx`(예약됨 항목의 footer가 취소 버튼, 그 밖은 기존 그대로). `no-html.test.ts` 규칙을 지킨다.
7. 문서: 운영툴 PRD §6.1(상세 카드 footer), §8.7 「구현됨(⑤-b 화면)」, §13 C행.

## 완료 조건

- 예약됨 항목에만 [공개 전 취소하기]가 보이고, 확인창이 함께 취소될 항목·막는 항목·되돌릴 수 없음·사유 칸을 보인다(테스트).
- 막는 항목이 있으면 취소 버튼이 꺼지고 이유가 보인다(테스트). 취소 결과·409·오류 문장이 ⑤-a와 같은 방식으로 나온다(테스트).
- `scripts/verify.sh` 전 항목 통과. 실렌더 확인은 머지 뒤 PC 세션(카리나).
