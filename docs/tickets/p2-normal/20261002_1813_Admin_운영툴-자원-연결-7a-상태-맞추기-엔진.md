## 착수 전에 정한 것 (2026-10-02 카리나, 1은 사용자 결정)

1. **운영툴 밖의 비활성(사용자 결정 2026-10-02 「기록만 하고 상태 유지」).** 자원이 있지만 비활성·숨김이면(지금은 카드 `is_active = false`) 「밖에서 바뀜」(`external_change`)으로
   기록만 하고 상태는 바꾸지 않는다. `diff`에 `is_active` 전후 값을 넣는다. 공개 판정이 거짓이므로 예약됨은 예약됨에 남고, 「예약 누락」 신호(공개 시각 + 30분)가 드러낸다. 다시 켜면 그대로 이어진다.
2. **`observe` 인터페이스.** `observe(service, resourceId, { now }): Promise<ResourceObservation>`. 결과는 넷 중 하나다.
   - `missing`: 자원이 없다(드랍은 `canceled`도 여기, ⑧이 붙인다).
   - `present`: `{ published, ended, startsAt, endsAt, inactive }`. `published`는 지금 유저 화면에 보이는지, `ended`는 자원의 종료 시각이 지났는지, `inactive`는 1의 비활성 여부다.
   - `failed`: `{ reason }`. 드랍의 `skipped`·`failed`·`missed`처럼 자원이 공개되지 못하고 끝났다(⑧이 붙인다. 카드에는 없다).
   - `error`: 읽지 못했다. 이번 회차에서 그 항목을 건너뛰고 서버 로그와 결과의 오류 수에 남긴다. 상태는 바꾸지 않는다.
   카드: `today_cards`에서 `id, is_active, starts_at, ends_at`을 읽는다. `published = is_active && starts_at <= now <= ends_at`, `ended = now > ends_at`. 다른 종류의 `observe`는 각 핸들러 조각(⑥·⑧·⑨·⑩)이 붙인다.
3. **판정(순수 함수, §8.6 표).** 대상은 상태가 `preparing`·`scheduled`·`live`인 항목이다. 시험 묶음이 아니면:
   - 예약됨 + `present` + `published` → 게재중(기록 없음). 예약됨 + `present` + `ended`(크론이 늦게 돌아 두 시각이 다 지남) → 곧바로 종료(기록 없음, 요약에는 종료로만 센다).
   - 게재중 + `present` + `ended` → 종료(기록 없음).
   - 예약됨 + `missing`, 또는 자원 ID가 없음(`created_resource`에 키가 없음, ④-b와 같은 해석) → 취소. `cancel`, 사유 「운영툴 밖에서 지워졌어요」.
   - 게재중 + `missing` → 종료. `end`, 같은 사유.
   - 예약됨 + `failed` → 실패. `fail`, 사유는 `observe`가 준 문장.
   - 예약됨·게재중 + `present`인데 자원의 `starts_at`·`ends_at`이 항목의 시각과 다르거나 1의 비활성이면 → 상태는 위 규칙대로 두고, 따로 `external_change`를 남긴다. `diff`는
     `{ starts_at?: { item, resource }, ends_at?: { item, resource }, is_active?: { item: true, resource: false } }`(다른 칸만). 시각은 밀리초로 비교한다. 그 항목의 가장 최근 `external_change`의
     `diff`와 같으면 다시 남기지 않는다(같은 차이는 한 번).
   - 준비중 + `updated_at` + 10분 ≤ 지금 → 실패. `fail`, 사유 「예약 등록이 끝나지 않았어요」. `created_resource`에 자원 ID가 있으면 핸들러 `undo`(참조 확인 포함)로 지운다.
     지우지 못하면(참조 있음·읽기 실패) 자원은 남기고 실패로 닫으며, 사유에 「만든 자원이 남아 있어요」를 덧붙이고 알림 글에 자원 ID를 싣는다. 그 항목의 가장 최근 결정 기록이 이미 `fail`이면
     새로 남기지 않는다(실행 API가 닫기에 실패하며 남긴 `fail`, 티켓 20261002_1123 메모).
   - 핸들러나 `observe`가 없는 종류는 건너뛰고 오류 수에 센다(지금은 카드만 예약할 수 있어 생기지 않는다).
4. **시험 묶음(§8.8).** 자원을 읽지 않고 항목의 시각만 본다. 예약됨 + `starts_at <= now` → 게재중(드랍 항목은 곧바로 종료), 게재중 + `ends_at < now` → 종료, 예약됨인데 두 시각이 다 지났으면 곧바로 종료.
   멈춘 준비중은 `undo` 없이 실패로 닫는다. `external_change`·`missing`은 없다.
5. **실행(서버 함수).** 한 회차가 대상 항목을 읽고(묶음의 `is_sample` 함께), 자원을 읽고, 판정하고, 상태를 조건부로 바꾼다(`.eq('status', 지금 상태)`, 돌아온 id로 실제 바뀐 항목만 센다).
   결정 기록은 바뀐 항목에만 남기고 행위자는 `system:reconcile`, 회차마다 `batch_id` 하나다. 항목 하나의 오류가 회차를 멈추지 않는다. 결과는 공개·종료·취소·실패·밖에서 바뀜 목록과 오류 수다.
   크론이 겹쳐 돌아도 상태는 한 번만 바뀐다(조건부 변경). 잠금이나 DB 변경은 두지 않는다.
6. **슬랙.** 한 회차에 공개·종료가 있으면 `#jam-report`(`postOpsSlack('report')`)에 요약 한 건(예: 「3개 공개, 2개 종료」와 항목 한 줄씩), 취소·종료(밖에서 지워짐)·실패가 있으면 `#jam-alert`에 한 건이다.
   바뀐 것이 없으면 보내지 않는다. 시험 묶음 항목은 따로 모아 「[시험]」을 붙인 글로 보낸다. 결정 기록이 있는 전이는 `postAndRecord`처럼 그 행의 `slack_result`를 채운다. 글은 응답 뒤에 보낸다(⑦-b가 `after()`로 부른다).
7. ⑦-b와 1154(매시 점검)는 5의 함수를 그대로 부른다. 화면 이름표(`end`·`external_change`·「시스템이」)는 ⑦-b다.
