# [Admin] 운영툴 자원 연결 ⑥ 미션 핸들러와 카드↔미션 연결

> 상위: 20260930_1500 ⑥. 유형 `admin`(화면 변경 없음). 선행: ③(연결 그룹·실행), ④(카드 핸들러·취소), ⑦-a(상태 맞추기 `observe`).
> 연결 그룹 묶기·ID 채우기·대기·그룹 실패·역순 되돌림·함께 취소는 이미 가짜 핸들러 테스트로 동작한다. 이 티켓은 실제 미션 핸들러를 붙이고 사용자 결정 두 개를 반영한다.

## 핵심 요약

- 요구사항: 미션 핸들러(`prepare`·`check`·`create`·`undo`·`cancel`·`observe`)를 만들어 레지스트리에 붙인다. 승인된 미션 항목이 예약되고, 카드↔미션이 함께 예약·함께 되돌려지고(Q2),
  공개 전 취소와 상태 맞추기가 미션에도 동작한다. 사용자 결정 두 개(아래 1·2)를 사전 점검과 등록 전 검증에 넣는다. DB 변경은 없다.

## 착수 전에 정한 것 (2026-10-02, 1·2는 사용자 결정)

1. **카드가 미션보다 먼저 공개되면 막는다(사용자 결정, G4 예외).** 사전 점검에서 card→mission 쌍의 카드 공개 시각이 대상 미션의 공개 시각보다 이르면 그 카드는 못 하는 항목이다.
   사유 「카드가 여는 미션보다 먼저 공개돼요」. 대상 미션이 이미 예약된 항목이면 그 항목의 공개 시각과 견주고, 이미 게재 중이면 견주지 않는다. 같은 시각은 통과다. 기존 규칙대로 그룹의 나머지 승인 항목은
   「연결된 항목을 예약할 수 없어요」로 막힌다. 07 4.5·PRD §8.2·1500 G4는 2026-10-02 카리나가 먼저 고쳤다(진행 규칙 5).
2. **미션 제목 중복은 기간이 겹칠 때만 막는다(사용자 결정).** `runMissionDbChecks`의 「제목 중복」이 같은 제목의 기존 미션을 모두 읽어(`id, starts_at, ends_at`) 기간이 겹치는 것이 있을 때만 걸린다.
   기간은 [공개, 종료)이고 종료가 없으면 끝없음이다. 한쪽의 종료 시각과 다른 쪽의 공개 시각이 같으면 겹치지 않는다. 검사 입력(`MissionDbCheckInput`)에 `starts_at`·`ends_at`을 더한다.
   같은 실행 안에서 앞 그룹이 만든 미션은 DB에 이미 있으므로 이 검사가 잡는다. 같은 묶음에서 이번에 예약할 미션 항목끼리 같은 제목·겹치는 기간이면 사전 점검이 뒤 항목(위치가 큰 쪽)을 못 하는 항목으로 둔다.
   사유 「같은 기획 안에 기간이 겹치는 같은 제목의 미션이 있어요」.
3. **미션 핸들러(`execute/mission.ts`, `MISSION_HANDLER`).** `idFirst: true`, `resourceKey: 'mission_id'`.
   - `prepare`: `toMissionRegisterInput(item, { id, linkedIds })`. `check`: `withoutLinkedFields`를 거친 사본으로 `runMissionDbChecks`(같은 실행에서 만들 연결 배지는 존재 확인을 건너뛴다).
   - `create`: 정한 ID로 `buildMissionInsertPayload` 결과를 insert한다. 오류면 같은 ID로 정리 delete를 시도한다(카드 선례). `undo`: `findMissionUndoReferences`로 참조를 확인한 뒤 delete한다.
     등록 스크립트의 `undoMissionRegistration`은 `image_source` 조건이 있어 쓰지 않는다.
   - `cancel`: `id, starts_at, ends_at, exposure_mode, exposure_at`을 다시 읽는다. 없으면 `missing`, `isMissionExposed(row, now)`면 `published`, 참조 확인 뒤 `.eq('id').gt('starts_at', now)`로 지우고, 지운 행이 없으면 다시 읽는다(카드 선례).
   - `observe`: 같은 칸을 읽는다. `ended = ends_at != null && now > ends_at`, `published = isMissionExposed(row, now) && !ended`, `startsAt`은 `exposure_mode`가 `scheduled`면 `exposure_at`, 아니면 `starts_at`, `endsAt = ends_at`,
     `inactive = exposure_mode === 'hidden'`(카드 `is_active = false`와 같게 「밖에서 바뀜」으로 기록만 하고 상태 유지, 앞선 사용자 결정의 적용).
   - 고정 문장: 형식 오류, 제목 중복(기간 겹침), 보상 배지 없음, 조건 배지 없음, 조건 지점 없음, DB를 읽지 못함, 만들기 실패, 참조가 있어 지우지 않음, 지우기 실패, 공개 시각 지남. 카드 핸들러와 같은 말투로 쓰고 DB 원문·칼럼 이름은 싣지 않는다.
4. **상태 맞추기의 멈춘 준비중 정리 순서.** 카드와 미션이 함께 준비중으로 멈추면 미션을 먼저 지우려다 카드의 `mission_id` 참조에 걸려 미션이 남는다. 멈춘 준비중 항목의 `undo`를
   `orderForUndo`와 같은 종류 순서(카드 먼저)로 부른다.
5. 레지스트리에 미션을 붙인다. 화면의 「아직 연결하지 않은 종류」 안내에서 미션이 빠진다(⑤-a 로더가 레지스트리를 읽는다).

## 완료 조건

- 승인된 카드+미션 그룹이 함께 예약되고, 그룹 안 하나가 실패하면 이번에 만든 것이 역순으로 지워진다(실제 핸들러 통합 테스트).
- 카드가 여는 미션보다 먼저 공개되면 사전 점검이 막고, 같은 제목 미션은 기간이 겹칠 때만 막힌다(테스트).
- 미션 공개 전 취소가 가리키는 카드를 함께 취소하고, 상태 맞추기가 미션의 공개·종료·밖에서 지워짐·숨김을 판정한다(테스트).
- `scripts/verify.sh` 전 항목 통과. DB 변경 없음.
