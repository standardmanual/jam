# [Admin] 운영툴 자원 연결 ⑧-a 레시피 핸들러

> 상위: 20260930_1500 ⑧(레시피·앰비언트 드랍 핸들러)을 ⑧-a(레시피)·⑧-b(드랍)로 나눴다(사용자 결정 2026-10-02, 규모 판정). 유형 `admin`(화면 변경 없음). DB 변경 없음.
> 선행: ③(연결 그룹·실행), ④(카드 핸들러·취소), ⑥(미션 핸들러), ⑦-a(상태 맞추기 `observe`), 영향 티켓 20261002_0710(레시피 종료 시각 `valid_until`, 마이그레이션 213 적용).

## 착수 전에 정한 것 (2026-10-02, 1·2는 사용자 결정)

1. **⑧을 둘로 나눈다(사용자 결정).** ⑧-a 레시피 → ⑧-b 드랍 순서다. 두 조각이 같은 파일(레지스트리·사전 점검·실행·취소 테스트, PRD)을 고치므로 병렬로 하지 않는다.
2. **안 열린 컬렉션 검사는 등록 전 검증에서 한다(사용자 결정).** 레시피의 슬롯 후보 배지(`slots[].allowed_badge_ids`)와 보상 배지(`reward_badge_ids`) 가운데 `item_book_id`가 있는 배지의 컬렉션이
   레시피 공개 시각(`valid_from` = 항목 `starts_at`)에 `isItemBookLaunched`가 거짓이면(비활성이거나 공개 시각이 레시피보다 늦음) 그 레시피는 `check` 실패다. 사유 「아직 열리지 않은 컬렉션의 배지가 들어 있어요」.
   배지·컬렉션 ID는 `detail`(서버 로그)에만 싣는다. 컬렉션을 읽지 못하면 실패로 본다(안전 쪽). 사전 점검은 DB를 읽지 않아 이 검사를 하지 못한다. PRD §8.4는 카리나가 먼저 고쳤다(진행 규칙 5).
   같은 묶음의 `collection_launch` 항목(⑩)이 만들 컬렉션은 아직 DB에 없으므로 이 조각은 다루지 않는다(⑩에 메모).
3. **ID를 먼저 적는다(카리나, PRD §8.5 「⑧이 정한다」의 답).** `createRecipeWithSlots`에 선택 인자 `options?: { id?: string }`를 더해 그 ID로 insert한다(`combination_recipes.Insert`에 `id?`가 있다).
   어드민 `POST /api/admin/recipes`는 인자를 넘기지 않아 동작이 같다. 레시피 핸들러는 `idFirst: true`다. 이유: 만든 직후 적는 방식은 적기 전에 요청이 끊기면 상태 맞추기(`reconcile.ts` `resourceIdOfItem`)가 자원을 찾지 못한다.
4. **핸들러 계약에 현재 시각을 더한다(카리나).** `prepare`·`check`·`create`의 context에 `now: Date`를 더하고 `run.ts`가 `executeBundle`의 `now()`를 넘긴다(`RunContext`에 `now`를 더한다).
   레시피 정규화(`normalizeRecipePayload`)와 ⑧-b의 드랍 입력 검사가 현재 시각을 받기 때문이다. 카드·미션 핸들러는 받지 않아도 된다(메서드 매개변수가 적으면 그대로 맞는다).
   `check`의 클라이언트 타입은 바꾸지 않는다. 레시피 `check`는 받은 클라이언트를 서비스 클라이언트로 캐스트해 `buildRecipeRow`에 넘긴다(실행 경로가 `asRegisterChecksClient(ctx.service)`로 서비스 클라이언트를 좁혀 넘기므로 실체는 같다. 캐스트는 한 곳에 두고 주석을 단다).
5. **레시피 핸들러(`execute/recipe.ts`, `RECIPE_HANDLER`).** `kind: 'recipe'`, `resourceKey: 'recipe_id'`, `idFirst: true`. 순수 모듈 계약(`node:`·Supabase·서버 모듈을 값으로 가져오지 않는다)을 지킨다.
   - `prepare`: 새 변환 `toRecipeRegisterInput(item)`(아래 6)으로 `RecipePayloadInput`을 만들고 `normalizeRecipePayload(payload, now)`로 형식을 본다. 오류면 「형식이 맞지 않아요: 첫 문장 (외 N건)」(미션과 같은 방식). 연결로 채우는 칸은 없다(`jam_badge` → `recipe` 쌍은 배지 쪽 칸이다).
   - `check`: `buildRecipeRow(service, payload, now)`(슬롯 후보·보상 배지 존재와 타입) → `assertValidPeriod(null, valid_from, valid_until)` → 위 2의 컬렉션 검사. `buildRecipeRow`·`assertValidPeriod`의 오류 문장은 이미 쉬운 문장이라 사유로 그대로 쓴다.
     컬렉션 검사는 새 순수 함수 `findUnlaunchedCollectionBadges(client, badgeIds, atIso)`(`lib/admin/registerChecks/recipe.ts`, `RegisterChecksClient`의 `in`·`is`만 쓴다)로 둔다.
   - `create`: `createRecipeWithSlots(service, payload, now, { id })`. 400이면 그 문장, 500이면 고정 문장 「레시피를 만들지 못했어요」(원문은 `detail`). 500이면 같은 ID로 정리 delete를 한 번 시도한다(카드·미션 선례, 슬롯은 CASCADE).
   - `undo`: `collectRecipeReferences`로 참조(이 레시피를 가리키는 배지)를 확인하고, 있거나 읽지 못하면 지우지 않는다(「연결된 배지가 있거나 확인하지 못해 레시피를 지우지 않았어요」). 없으면 ID로 delete한다.
     시각 조건은 걸지 않는다(상태 맞추기의 멈춘 준비중 정리는 공개 시각이 지난 뒤에 올 수 있다. 카드·미션 `undo`와 같다).
   - `cancel`: `combination_recipes`에서 `id, valid_from, valid_until`을 다시 읽는다. 없으면 `missing`. `recipeReleaseState`가 `scheduled`가 아니면 `published`(409 「공개 시각이 지나 취소할 수 없어요」).
     그다음 `cancelScheduledRecipe(service, id, now)`: 성공이면 지움, 404면 `missing`, 409면 다시 읽어 공개됐으면 `published`, 아직 예약 중이면 `referenced`(「가장 먼저 성공 배지가 이 레시피를 가리키고 있거나 확인하지 못해 지우지 않았어요」), 500이면 `error`(「레시피를 지우지 못했어요」).
     서버 함수의 문장은 사유로 쓰지 않는다(어드민 화면용 문장이다).
   - `observe`: 같은 칸을 읽는다. 없으면 `missing`, 읽지 못하거나 시각을 읽을 수 없으면 `error`. `state = recipeReleaseState(row, now)`로 `published = state === 'released'`, `ended = state === 'ended'`, `startsAt = valid_from`, `endsAt = valid_until`, `inactive = false`(레시피에는 비활성 칸이 없다).
   - 고정 문장은 미션 핸들러와 같은 말투로 쓰고 DB 원문·칼럼 이름은 싣지 않는다.
6. **변환(`registerInput.ts` `toRecipeRegisterInput`).** PRD §8.4 레시피 행: 공통 칸 `starts_at`(필수) → `valid_from`, `ends_at` → `valid_until`(없으면 칸을 넣지 않아 상시), `copy.name`(필수, 없으면 `resource.name`),
   `resource`의 `slots`(필수)·`reward_points`·`reward_badge_ids`. 표에 없는 키는 경고(`warnUnreadKeys`). 결과는 카드·미션과 같은 `{ payload, errors, warnings, linkFields: [] }`이고 DB에 접근하지 않는다.
7. **레지스트리에 레시피를 붙인다.** 화면의 「아직 연결하지 않은 종류」 안내에서 레시피가 빠진다(⑤-a 로더가 레지스트리를 읽는다).
8. **실제 드랍 예약은 하지 않는다.** 이 조각은 레시피만이다. 1500 「사용자 확인 지점」의 ⑧(첫 드랍 예약)은 ⑧-b와 그 뒤 PC 세션 확인에 해당한다.
