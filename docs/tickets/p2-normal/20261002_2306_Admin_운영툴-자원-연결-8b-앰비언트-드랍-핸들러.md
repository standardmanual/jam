## 착수 전에 정한 것 (2026-10-02 카리나. ⑧ 시작 검토의 사용자 결정·카리나 결정을 드랍에 적용)

1. **서버 전용 import를 푼다.** `fetchAllRows`·`fetchAllRowsIn`과 보조(`PAGE_SIZE`·`IN_CHUNK_SIZE`·`PagedQuery`·`ordered`)를 새 순수 파일 `jam-web/src/lib/db/fetchAllRows.ts`로 옮기고, `notifications/batch/shared.ts`는 같은 이름을 다시 내보낸다(나머지 12곳은 고치지 않는다).
   `scheduleTargets.ts`는 새 파일에서 가져온다. 동작은 바꾸지 않는다(오류 문장 접두 `[notifications-batch]`도 그대로).
2. **ID를 먼저 적는다(⑧ 결정, PRD §8.5).** `rowFromSpec`에 선택 인자 `id`, `createAmbientDropSchedule(supabase, body, createdBy, now, options?: { id?: string })`. 어드민 라우트는 인자를 넘기지 않아 동작이 같다. 드랍 핸들러는 `idFirst: true`다.
3. **드랍 핸들러(`execute/dropSchedule.ts`, `DROP_SCHEDULE_HANDLER`).** `kind: 'drop_schedule'`, `resourceKey: 'ambient_drop_schedule_id'`, `idFirst: true`. 순수 모듈 계약을 지킨다(1 뒤에는 `scheduleStore.ts`를 가져와도 서버 모듈이 끌려오지 않는다).
   - `prepare`: 새 변환 `toDropScheduleRegisterInput(item, { linkedIds })`(아래 4) → `parseAmbientDropScheduleInput(payload, now)`. 오류면 「형식이 맞지 않아요: 첫 문장 (외 N건)」(레시피·미션과 같은 방식). 드랍 파서의 오류 문장은 이미 쉬운 문장이다.
   - `check`: 받은 클라이언트를 서비스 클라이언트로 캐스트(⑧-a 레시피와 같은 한 곳)해, 지점 종류 확인과 `loadScheduleTargets(service, spec, scheduledAt)` → `describeScheduleTargetProblems`로 예정 시각 기준 대상을 본다.
     문제가 있으면 그 문장이 사유다(쉬운 문장). 읽기 실패는 고정 문장 「드랍 대상을 확인하지 못했어요」(원문은 `detail`). 같은 묶음의 컬렉션 항목이 만들 컬렉션(연결로 채운 `collection_ids`)은 아직 DB에 없어 걸린다.
     컬렉션 핸들러(⑩)가 없어 그런 그룹은 지금 실행되지 않으므로 이 조각은 따로 다루지 않는다(⑩에 메모, 1500 「⑩에 넘길 것」).
   - `create`: `createAmbientDropSchedule(service, payload, actorId, now, { id })`. `created_by`에는 실행한 관리자 ID를 넣는다(카드 `created_by`와 같다. 어드민 화면은 이 칸을 그리지 않는다). 400이면 그 문장, 500이면 고정 문장 「드랍 예약을 만들지 못했어요」이고
     같은 ID로 정리 delete(`status = 'scheduled'` 조건)를 한 번 시도한다.
   - `undo`: `status = 'scheduled'` 조건으로 행을 지운다(드랍 예약 테이블을 가리키는 외래 키가 없다). 지운 행이 없으면 다시 읽어 없으면 성공, 이미 실행이 시작·끝났으면 실패 「이미 실행이 시작돼 드랍 예약을 지우지 않았어요」.
     실행 중 되돌림은 방금 만든 예약이라 기록 없이 지운다. 공개 전 취소(아래)는 지우지 않고 서버 함수로 「취소」 상태를 남긴다.
   - `cancel`: `getAmbientDropSchedule`로 읽는다. 404면 `missing`, 500이면 `error`(「드랍 예약을 취소하지 못했어요」). 상태가 `canceled`면 `missing`(밖에서 취소됨). `scheduled`가 아니거나(실행 중·멈춤·완료·건너뜀·실패·놓침)
     예정 시각이 지금 이전이면 `published`(「공개 시각이 지나 취소할 수 없어요」. 서버 함수는 예정 시각을 보지 않으므로 핸들러가 먼저 막는다). 그다음 `cancelScheduledAmbientDrop`: 성공이면 취소, 404면 `missing`,
     409면 다시 읽어 `canceled`면 `missing`, 그 밖이면 `published`, 500이면 `error`. 서버 함수의 문장은 사유로 쓰지 않는다.
   - `observe`: `getAmbientDropSchedule`로 읽는다(404 → `missing`, 500 → `error`). 파생 상태로 나눈다: `canceled` → `missing`. `done` → `present`(`published: true`, `ended: true`). `skipped`·`failed`·`missed` → `failed`, 사유 「드랍을 놓지 못했어요(상태 이름)」
     (`SCHEDULE_STATE_LABEL`, 예: 「드랍을 놓지 못했어요(놓침)」). `scheduled`·`running`·`stalled` → `present`(`published: false`, `ended: false`. 게재중으로 넘기면 뒤의 실패가 무시된다, `reconcile.ts`의 게재중 `failed` 무시).
     공통으로 `startsAt = scheduled_at`, `endsAt = null`, `inactive = false`다. 예정 시각을 읽을 수 없으면 `error`.
   - 고정 문장은 레시피·미션 핸들러와 같은 말투로 쓰고 DB 원문·칼럼 이름·자원 ID는 싣지 않는다.
4. **변환(`registerInput.ts` `toDropScheduleRegisterInput`).** PRD §8.4 드랍 행: 공통 칸 `starts_at`(필수) → `scheduled_at`, 공통 칸 `ends_at`이 있으면 형식 오류, `copy.title`(100자, 없으면 `resource.title`), `resource`의 6개 키(`DROP_SCHEDULE_RESOURCE_KEYS`).
   연결로 채우는 칸 `collection_ids`는 `appendLinkedIds`로 `resource` 몫 뒤에 더하고 `linkFields`에 알린다(대상이 아이템 직접 선택이면 사전 점검이 이미 막는다, `directSelectKey`). 표에 없는 키는 경고. DB에 접근하지 않는다.
5. 레지스트리에 드랍을 붙인다. 화면의 「아직 연결하지 않은 종류」 안내에서 드랍이 빠진다. 드랍에는 「지금 종료」 버튼이 없다(⑪, PRD §8.7).

## 완료 조건
