## 착수 전에 정한 것 (2026-10-04, 1~3은 사용자 결정)

1. **⑨를 둘로 나눈다(사용자 결정).** ⑨-a는 E1에 기대지 않는 핸들러·변환·사전 점검·취소·상태 맞추기·R7이다. ⑨-b(요약창 「공개되면 약 N명에게 P포인트」)는 E1의 `previewUpcomingJamBadges`가 머지된 뒤 한다.
2. **미션·카드가 연결된 JAM! 배지보다 먼저 공개되면 막는다(사용자 결정).** 미션(`reward_badge_ids` 쌍)·카드(`badge_ids` 쌍)의 공개 시각이 연결로 채우는 대상 배지 항목보다 이르면 그 미션·카드가 못 하는 항목이다.
   사유 「연결된 JAM! 배지보다 먼저 공개돼요」. 같은 시각은 통과. 대상 배지 항목이 예약된 항목이면 그 공개 시각과 견주고, 게재 중·종료된 항목은 견주지 않는다. 두 시각 중 하나라도 읽을 수 없으면 견주지 않는다.
   `resource`가 직접 가진 기존 배지 ID는 견주지 않는다(사전 점검은 DB를 읽지 않는다). 카드→미션 규칙(`opensLaterMission`)과 같은 모양이다. PRD §8.2·07 4.5는 카리나가 먼저 고쳤다(진행 규칙 5).
3. **「가장 먼저 성공」 배지와 레시피의 공개 시각이 다르면 막는다(사용자 결정, PRD의 「덮고 경고」를 바꿈).** `jam_badge` → `recipe` 쌍에서 배지 항목과 대상 레시피 항목의 공개 시각이 다르면(밀리초 비교) 배지가 못 하는 항목이다.
   사유 「가장 먼저 성공 배지는 레시피와 같은 시각에 공개돼야 해요」. 대상 레시피 항목의 상태와 관계없이 견준다(이미 게재 중인 레시피에 나중에 여는 배지는 첫 성공을 놓친다). 읽을 수 없으면 견주지 않는다.
   연결이 아니라 `resource.condition_json.recipe_first_success.recipe_id`에 기존 레시피를 직접 적은 배지는 `check`가 DB의 레시피(`combination_recipes.valid_from`)를 읽어 같은 규칙으로 막는다(없으면 「가장 먼저 성공할 레시피가 없어요」, 읽지 못하면 실패).
4. **순수 모듈로 만든다(카리나).** `badge-validation.ts` 2행을 `@/lib/drop-engine/cumulativeConditionFields`로 바꾼다(⑧-b `fetchAllRows`와 같은 방식, 동작 불변). `JAM_ACTION_CONDITION_KEYS`(와 필요한 보조 상수)는 순수 파일
   `jam-web/src/lib/badge-engine/jamActionKeys.ts`로 옮기고 `jamActionBadges.ts`가 다시 내보낸다. `isValidFamilyKey`는 순수 파일(예: `lib/admin/familyKey.ts`)로 옮기고 `badge-families.ts`가 다시 내보낸다. 기존 호출부는 고치지 않는다.
5. **변환 `toJamBadgeRegisterInput(item, { linkedIds })`(PRD §8.4 `jam_badge` 행).** 공통 `starts_at`(필수) → `valid_from`, `ends_at` → `valid_until`(없으면 상시), `copy.name`·`copy.description`(필수, 없으면 `resource`),
   `resource`의 `condition_json`(필수)·`point_reward`·`rarity`·`level`·`family_key`·`sort_order`·`image_url`. 툴이 정하는 값: `type='activity'`, `admin_category='jam'`, **`activity_types=[]`**(JAM! 배지는 종목과 함께 쓰지 않는 어드민 폼 규칙. 항목에 값이 있으면
   「툴이 정하는 값이라 읽지 않아요」 경고), `id`. 표에 없는 키(`tribe_id`·`item_book_id` 등)는 경고. 연결 칸 `condition_json.recipe_first_success.recipe_id`는 `linkedIds.recipe_id`가 있으면 **덮어쓴다**(§8.3 「덮는 칸」, `resource`의 같은 값은 충돌이 아님).
   `image_url`이 없으면 null(G1). insert 값은 `buildBadgeInsertPayload`로 만든다.
6. **형식 검사(`prepare`).** `findRarityLevelError`(희귀도·레벨 중 정확히 하나), `findBadgeConditionSaveError`(조건 저장 규칙), `isValidFamilyKey`, 그리고 **발급 조건이 없는 배지**를 형식 오류로 막는다: `condition_json`에 `USAGE_METRIC_CONDITION_KEYS`·`JAM_ACTION_CONDITION_KEYS`·`recipe_first_success` 중 하나도 없고
   `mission_reward: true`도 아니면 「발급 조건이 없는 배지예요」(메인 엔진은 `admin_category='jam'`을 후보에서 빼므로 이런 배지는 영원히 발급되지 않는다). 오류면 「형식이 맞지 않아요: 첫 문장 (외 N건)」.
7. **JAM! 배지 핸들러(`execute/jamBadge.ts`, `JAM_BADGE_HANDLER`).** `kind: 'jam_badge'`, `resourceKey: 'badge_id'`, `idFirst: true`. 순수 모듈 계약.
   - `check`: `runBadgeDbChecks`(이름 중복 등)를 연결 칸을 뺀 사본으로 부르고, 라벨별 고정 문장으로 바꾼다(미션 선례). DB를 읽지 못하면 실패. 위 3의 직접 적은 레시피 확인. 같은 실행에서 만들 레시피(연결)는 존재 확인을 건너뛴다(생성 순서가 보장).
   - `create`: `{ id, ...payload }` insert, 오류면 같은 ID로 정리 delete 한 번. `undo`: `findBadgeUndoReferences` 뒤 ID로 delete(하드 삭제, 등록 스크립트 `--undo`와 같다).
   - `cancel`: `badges`에서 `id, valid_from, valid_until, deleted_at`을 다시 읽는다. 없거나 `deleted_at`이 있으면 `missing`. `valid_from`이 없거나 지금 이전이면 `published`(「공개 시각이 지나 취소할 수 없어요」).
     `findBadgeUndoReferences`가 던지면 `referenced`(「획득 기록이나 연결이 있거나 확인하지 못해 배지를 지우지 않았어요」). 지울 때 `.gt('valid_from', now)`를 걸고, 지운 행이 없으면 다시 읽어 `published`·`missing`을 가른다. 오류는 `error`(「배지를 지우지 못했어요」).
   - `observe`: 같은 칸을 읽는다. 없거나 `deleted_at`이 있으면 `missing`(운영툴 밖에서 지워짐). 시각을 읽을 수 없으면 `error`. `published = valid_from <= 지금 <= valid_until`(종료 없으면 끝없음, 발급 엔진과 같은 양 끝 포함),
     `ended = valid_until이 있고 지금 > valid_until`, `startsAt = valid_from`, `endsAt = valid_until`, `inactive = false`.
   - 고정 문장은 다른 핸들러와 같은 말투, DB 원문·칼럼 이름·자원 ID는 `detail`에만.
8. **밸런스 R7 이중 세기를 고친다.** `jam_badge` 항목에 `created_resource.badge_id`가 있으면 그 배지는 DB에서 세고 항목에서 다시 세지 않는다(PRD §8.5의 컬렉션 규칙과 같은 방식).
9. 레지스트리에 배지를 붙인다. 남는 미연결 종류는 `collection_launch`(⑩)뿐이다. 공개 뒤 「지금 종료」는 ⑪이다.

- 승인된 JAM! 배지 항목이 예약 등록 때 공개 전 `badges` 행(`type='activity'`, `admin_category='jam'`, `activity_types=[]`, 공개 시각 = 항목 공개 시각)이 되고, 만들기 전에 `created_resource.badge_id`가 적힌다.
