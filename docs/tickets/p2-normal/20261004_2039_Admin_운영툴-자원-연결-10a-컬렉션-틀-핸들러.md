# [Admin] 운영툴 자원 연결 ⑩-a 컬렉션 틀 핸들러

> 상위: 20260930_1500 ⑩(컬렉션 틀 핸들러)을 ⑩-a(핸들러 핵심)·⑩-b(새 컬렉션을 가리키는 드랍, 빈 컬렉션 신호)로 나눴다(2026-10-04 시작 검토, 사용자 이의 없음). ⑩-b는 ⑩-a 머지 뒤 착수 때 티켓을 만든다.
> 유형 `admin`(화면 변경 없음). DB 변경 없음. 선행: ③·④·⑥·⑦-a·⑧-a·⑧-b·⑨-a(핸들러 틀과 계약).
> 실제 컬렉션 예약은 이 조각에서 만들지 않는다(테스트와 시험 묶음만). 1500 「사용자 확인 지점」 ⑩의 첫 실제 컬렉션은 영향 티켓 20261004_2041(공개 전 컬렉션 직접 조회)·20261004_2043(어드민 폼 기간 입력)을 고친 뒤 PC 세션에서 사용자 승인을 받고 한다.

## 핵심 요약

- 요구사항: 컬렉션 틀 핸들러(`prepare`·`check`·`create`·`undo`·`cancel`·`observe`)를 만들어 레지스트리에 붙인다. 승인된 `collection_launch` 항목이 예약 등록 때 공개 전 `item_books` 행(틀만: 이름·설명·이야기·대표 이미지·보상 포인트·보상 배지·트라이브·공개/종료 시각)이 되고,
  카드 → 컬렉션(`item_book_id`), 컬렉션 → JAM! 배지(`reward_badge_id`) 연결이 실제로 채워지며, 공개 전 취소와 상태 맞추기가 컬렉션에도 동작한다. 컬렉션 보상으로 연결된 JAM! 배지는 발급 조건 없이 통과시키고(사용자 결정), 공개 순서 규칙 둘을 더하고, 밸런스 R1 이중 세기를 고친다.

## 착수 전에 정한 것 (2026-10-04 시작 검토. 2·3은 사용자 결정, 나머지는 카리나가 정하고 사용자 이의 없음)

1. **⑩을 둘로 나눈다.** ⑩-a는 이 티켓이다. ⑩-b는 새 컬렉션을 가리키는 드랍의 등록 판정 미루기(사용자 결정 「공개 때 판정」)와 운영 신호 「비어 있는 컨텐츠」의 「아이템이 없는 컬렉션」이다(PRD §8.4에 「구현 전: ⑩-b」로 적었다).
   ⑩-a에서는 같은 실행에서 만들 컬렉션을 가리키는 드랍 그룹이 드랍 `check`에서 실패한다. 이 동작을 바꾸지 않고 PRD에 「⑩-b 전까지」로 적어 둔다.
2. **컬렉션 보상으로 연결된 JAM! 배지는 발급 조건이 없어도 통과한다(사용자 결정).** 같은 그룹에서 `collection_launch` 항목이 `reward_badge_id` 칸으로 이 배지 항목을 가리키면 `jamBadge.ts`의 「발급 조건이 없는 배지」 검사를 건너뛴다.
   그 연결이 없으면 지금처럼 형식 오류다. 핸들러는 그룹을 모르므로 실행(`run.ts`)이 `prepare` 컨텍스트에 「이 항목을 연결 칸으로 가리키는 항목의 종류·칸」(예: `pointedBy: [{ kind: 'collection_launch', field: 'reward_badge_id' }]`)을 넘긴다.
   계산 근거는 그룹의 `linkPlan`이다(가리키는 항목이 이번 실행의 예약할 항목일 때만 들어 있다). 다른 핸들러는 이 값을 쓰지 않는다. 사전 점검·요약창은 바뀌지 않는다.
3. **새 영향 티켓 둘(사용자 결정 「둘 다 영향 티켓」).** 20261004_2041(공개 전 컬렉션이 로그인 유저의 직접 조회에 보인다, DB)·20261004_2043(어드민 컬렉션·배지 폼의 기간 입력이 날짜만 받는다). 이 티켓에서는 고치지 않는다. 첫 실제 컬렉션 예약 전에 끝낸다.
4. **공개 순서 규칙 둘(⑨ 사용자 결정과 같은 모양, PRD §8.2·07 4.5 선반영).** (가) `collection_launch` → `jam_badge` 쌍: 컬렉션의 공개 시각이 연결된 보상 배지보다 이르면 컬렉션이 못 하는 항목, 사유는 기존 `beforeLinkedBadge` 「연결된 JAM! 배지보다 먼저 공개돼요」
   (`LINKED_BADGE_FIELDS`에 `reward_badge_id`를 더한다). (나) `home_feed_card` → `collection_launch` 쌍: 카드의 공개 시각이 연결된 컬렉션보다 이르면 카드가 못 하는 항목, 새 사유 「연결된 컬렉션보다 먼저 공개돼요」(`item_book_id`).
   비교 조건은 기존 두 규칙과 같다(같은 시각 통과, 만들기 전·예약된 대상은 그 공개 시각과 견줌, 게재 중·종료된 대상과 읽을 수 없는 시각·`resource`에 직접 적은 ID는 견주지 않음).
5. **변환 `toCollectionLaunchRegisterInput(item, { linkedIds })`(PRD §8.4 `collection_launch` 행).** 공통 `starts_at`(필수) → `valid_from`, `ends_at` → `valid_until`(없으면 상시, 있으면 `starts_at`보다 늦어야 함), 항목 트라이브(`readOpsItemTribeId`) → `tribe_id`(없으면 NULL).
   `copy.name`·`copy.description`(둘 다 필수, 빈 문자열은 없음으로 본다)·`copy.story_text`. `resource`의 `image_url`(없으면 NULL, G1)·`reward_points`(0 이상 정수, 없으면 0)·`reward_badge_id`.
   툴이 정하는 값: `is_active = true`, `id`. `required_activity_badge_id`·`image_source`·배경 칸·`drop_condition_json`·`drop_excluded`는 쓰지 않는다(값이 들어오면 「표에 없는 칸이라 읽지 않아요」 경고. 어드민 표시 전용이거나 기본값이 맞다).
   연결 칸 `reward_badge_id`는 `fillLinkedId`로 채운다(`resource`에 같은 칸이 있으면 오류, 카드·미션과 같다). 오류는 「컬렉션 형식이 맞지 않아요: 첫 문장 (외 N건)」이다.
6. **등록 전 검사(새 `registerChecks/collection.ts` 또는 핸들러 안).** 연결 칸을 뺀 사본(`withoutLinkedFields`)으로: 같은 이름의 기존 컬렉션(정확히 같은 이름, 있으면 막음), 트라이브 존재, `resource`에 직접 적은 보상 배지의 존재·`deleted_at` 없음·`type = 'activity'`.
   DB를 읽지 못하면 실패. 연결로 채우는 보상 배지는 존재 확인을 건너뛴다(같은 실행에서 만들 배지, 생성 순서가 보장).
7. **되돌림 참조(새 `ITEM_BOOK_UNDO_REFERENCE_TABLES`와 `findItemBookUndoReferences(client, itemBookId)`, `references.ts`).** PRD §8.1 원칙대로 하나라도 있거나 읽지 못하면 지우지 않는다(던진다):
   `badges.item_book_id`(소프트 삭제된 배지도 센다. 아이템 배지가 붙은 컬렉션은 기존 어드민에서 아이템을 먼저 빼야 지울 수 있다), `today_cards.item_book_id`, `user_item_book_slots`, `user_item_book_completions`, `user_drop_state.last_drop_book_id`,
   `point_transactions.source_item_book_id`, `ambient_drop_config.collection_ids`, `ambient_drop_schedules.collection_ids`(끝나지 않은 예약만. 공개 전 취소된 드랍은 행이 「취소」로 남으므로 세지 않는다. 상태 값은 착수 때 확인).
   어드민 삭제 가드(`reference-guards.ts`)는 고치지 않는다.
8. **컬렉션 핸들러(새 `execute/collectionLaunch.ts`, `COLLECTION_LAUNCH_HANDLER`).** `kind: 'collection_launch'`, `resourceKey: 'item_book_id'`, `idFirst: true`. 순수 모듈 계약(Supabase·서버 모듈을 값으로 가져오지 않는다).
   - `create`: `{ id, ...payload }` insert, 오류면 같은 ID로 정리 delete 한 번. `undo`: `findItemBookUndoReferences` 뒤 ID로 delete(시각 조건 없음, 멈춘 준비중 정리는 공개 시각 뒤에 올 수 있다).
   - `cancel`: `item_books`에서 `id, is_active, valid_from, valid_until`을 다시 읽는다. 없으면 `missing`. `valid_from`이 없거나 지금 이전이면 `published`(「공개 시각이 지나 취소할 수 없어요」). 참조가 있거나 읽지 못하면 `referenced`.
     지울 때 `.gt('valid_from', now)`를 걸고, 지운 행이 없으면 다시 읽어 `published`·`missing`을 가른다. 오류는 `error`.
   - `observe`: 같은 칸을 읽는다. 없으면 `missing`. 시각을 읽을 수 없으면 `error`. `published`·`ended`·`inactive`는 카드 `observe`(`is_active`가 있는 자원) 선례를 따른다: 공개 시각 지남(`valid_from` 없음 포함), 종료 시각이 있고 지금이 그 뒤, `inactive = !is_active`.
     밖에서 비활성은 기록만 하고 상태를 유지한다(⑦-a 사용자 결정).
   - 사유는 고정 문장이다. DB 오류 원문·컬렉션·배지·트라이브 ID·칼럼 이름은 서버 로그(`detail`)에만 둔다. 문장(안, 말투는 다른 핸들러와 맞춘다):
     형식 「컬렉션 형식이 맞지 않아요: …」, 이름 중복 「같은 이름의 컬렉션이 이미 있어요」, 트라이브 없음 「트라이브를 찾을 수 없어요」, 보상 배지 없음·삭제 「보상으로 정한 배지가 없거나 삭제됐어요」, 보상 배지 종류 「완성 보상 배지는 활동 배지여야 해요」,
     DB 읽기 실패 「등록 전 확인 중 DB를 읽지 못했어요」, 생성 「컬렉션을 만들지 못했어요」, 되돌림·취소 참조 「아이템 배지나 유저 기록·연결이 있거나 확인하지 못해 컬렉션을 지우지 않았어요」, delete 오류 「컬렉션을 지우지 못했어요」, 취소 공개 지남 「공개 시각이 지나 취소할 수 없어요」.
9. **밸런스 R1 이중 세기를 고친다.** `collection_launch` 항목에 `created_resource.item_book_id`가 있으면 그 컬렉션은 DB에서 세고 항목에서 다시 세지 않는다(`createdBadgeIdOf`와 같은 도우미, PRD §8.5). 같은 개방 타임라인을 쓰는 R2·R3도 같은 기준인지 확인하고 맞춘다.
