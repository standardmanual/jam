  - 컬렉션 폼 `jam-web/src/app/admin/itembooks/ItemBookForm.tsx`: `toDateInput = iso.slice(0, 10)`(81행)으로 저장된 ISO(UTC)의 앞 10자를 `type="date"` 입력(360·365행)에 넣고,
    저장할 때 `new Date(validFrom).toISOString()`(131–132행)으로 보낸다. 날짜만 있는 문자열은 UTC 자정으로 읽힌다.

- 영향(위 사실에서 따라 나오는 결과): 운영툴이 만든 항목은 공개 시각이 KST 시각까지 정해져 있다. 예를 들어 `valid_from`이 KST 10/20 00:00(= UTC 10/19 15:00)이면 폼은 시작일을 10/19로 보이고,
  다른 칸만 고쳐 저장해도 `valid_from`이 UTC 10/19 00:00(= KST 10/19 09:00)으로 바뀌어 15시간 일찍 공개된다. 종료 시각도 같은 방식으로 바뀐다.
  - 컬렉션: 1500 ⑩-a(티켓 20261004_2039)가 만든 공개 전 컬렉션에 아이템을 채우러 이 화면을 연다.
  - 배지: 1500 ⑨-a가 만든 JAM! 배지, 특히 레시피와 공개 시각이 밀리초까지 같아야 하는 「가장 먼저 성공」 배지가 어긋난다.
  - 상태 맞추기는 이런 변경을 「밖에서 바뀜」으로 기록만 한다(1500 G8).
- 구현 계획(안): 두 폼의 기간 입력을 레시피 폼과 같은 KST `datetime-local`로 바꾼다. 표시는 `jam-web/src/lib/admin/kst-format.ts`의 `toKstLocalInputValue`(52행), 저장은 `+09:00`을 명시한 변환

  입력값을 바꾸지 않았으면 원래 ISO를 그대로 보낸다(분 단위로 왕복하면 초·밀리초가 잘려 「가장 먼저 성공」 배지와 레시피의 시각 일치가 깨진다).

## 착수 때 정한 것 (2026-10-05. 1은 사용자 결정, 나머지는 카리나)

1. **기존 값은 그대로 보인다(사용자 결정 「그대로 09:00 표시」, 추천안).** 지금 날짜만 넣어 저장된 값은 UTC 자정(= KST 09:00)이고 새 입력에서 「그날 09:00」으로 보인다. 안내 문장은 두지 않고 기간 라벨에 「한국 시각」만 밝힌다. 데이터는 고치지 않는다.
   라이브 사실(2026-10-05): 배지 `valid_from` 984개가 모두 UTC 자정이고 KST 자정은 0개, 배지 `valid_until`·컬렉션 `valid_from`·`valid_until`은 0개, 초·밀리초가 있는 값 0개.
2. **공용 변환은 `jam-web/src/lib/admin/kst-format.ts`에 둔다.** `kstLocalInputToIso(local)`(레시피 폼 `kstLocalToIso`와 같은 구현: 입력값 뒤에 `:00+09:00`을 붙여 `Date`로 읽고, 읽을 수 없으면 null)와
   `resolvePeriodInputIso(originalIso, local)`(빈 칸이면 null, 원래 ISO가 있고 `toKstLocalInputValue(originalIso) === local`이면 원래 ISO 그대로, 아니면 `kstLocalInputToIso(local)`)를 더한다.
   레시피 폼은 자기 `kstLocalToIso`를 지우고 공용 함수를 쓴다(구현이 같아 동작 불변).
3. **입력값을 바꾸지 않은 칸은 원래 ISO를 그대로 보낸다**(분 단위 왕복으로 초·밀리초가 잘리거나 UTC 자정 값이 바뀌지 않게). 칸을 비우면 null이다(지금과 같다). 「기간 지우기」 버튼 동작은 그대로다.
4. 폼의 다른 동작(도움말 문장, `min` 제약, 저장 API 형식)은 바꾸지 않는다. `type="datetime-local"`의 `min`은 같은 형식의 시작 값을 그대로 쓴다.

## 구현 계획 (파일 단위)
