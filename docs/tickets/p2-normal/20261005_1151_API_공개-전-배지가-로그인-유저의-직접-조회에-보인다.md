# [API] 공개 전 배지가 로그인 유저의 직접 조회에 보인다

> 발견: 티켓 20261004_2041(E4, 공개 전 컬렉션 직접 조회) 게이트의 민지 범위 밖 발견물([보안/참고]). 카리나가 라이브 DB로 확인하고 P2로 올렸다(E4·20261002_1257과 같은 종류의 누출이고,
> 운영툴이 공개 전 배지를 만들기 시작하면 실제로 새기 때문이다). 1500의 영향 티켓 E6이다(상위 1450 진행 규칙 4). 첫 실제 JAM! 배지·컬렉션 예약 전에 고친다.

## 핵심 요약

- 현상(확인한 사실, 2026-10-05):
  - `badges`의 SELECT 정책은 「badges: 전체 읽기 허용」(`FOR SELECT TO authenticated USING (TRUE)`) 하나다. 근거는 `jam-web/supabase/migrations/001_initial_schema.sql` 99–103행이고, 2026-10-05 `pg_policies` 조회 결과도 `qual = true`로 같다.
  - 그래서 로그인 유저는 공개 키와 자기 세션으로 PostgREST를 직접 불러 공개 전(`valid_from`이 미래) 배지와, 비활성·공개 전 컬렉션 소속 아이템 배지의 이름·설명·이미지 주소·조건을 읽을 수 있다.
  - 2026-10-05 라이브 DB에는 공개 전 배지가 0개, 비활성 컬렉션 소속 아이템 배지가 0개라 지금 새는 행은 없다.
- 영향: 운영툴 자원 연결이 공개 전 JAM! 배지(1500 ⑨-a, 티켓 20261004_1756)와 공개 전 컬렉션(⑩-a)을 예약으로 만들고, 컬렉션의 아이템 배지는 공개 전에 기존 어드민에서 채운다(1500 Q4).
  E4(마이그레이션 215)로 컬렉션 행은 숨겨지지만 그 아이템 배지와 공개 전 JAM! 배지는 이 정책 때문에 여전히 보인다.
- 구현 계획(2026-10-05 확정, 아래 「착수 전에 정한 것」·「구현 계획(파일 단위)」. 아래 문장은 착수 전 안): E4·1257과 같은 `ALTER POLICY`로 공개 조건을 더한다. 조건 후보는 「삭제되지 않음·공개 시각이 지났거나 비어 있음·소속 컬렉션이 있으면 그 컬렉션이 공개됨」이다.
  배지는 사용자 세션으로 읽는 곳이 컬렉션보다 많을 수 있으므로(배지 목록·상세·프로필·획득 기록 임베드 등) 착수 때 E4와 같은 절차로 조회 지도를 먼저 만든다.
  종료(`valid_until`)는 넣지 않는다(이미 받은 배지는 계속 보여야 한다).
- 관련 파일: `jam-web/supabase/migrations/001_initial_schema.sql` 99–103, 선례 `215_item_books_select_launched.sql`(E4)·`214_today_cards_select_period.sql`(1257), 앱 공개 판정(배지의 `valid_from` 판정 위치는 착수 때 찾는다), `docs/specs/prd/02_DATA_MODEL.md`의 `badges` 절.

## 착수 때 확인한 결과 (2026-10-05 카리나, Explore 코드 지도 + 라이브 DB 읽기 전용 조회, 기준 커밋 4e85560)

1. **사용자 세션으로 `badges`를 읽는 곳은 9파일 15곳이다**(E4는 4곳). 경로는 `jam-web/src/` 기준:
   `app/(main)/badges/page.tsx` 44–48(임베드 `badge:badges(*)`)·49–53·109–115·138·201, `app/(main)/inventory/page.tsx` 31–35(임베드), `app/(main)/badges/tree/page.tsx` 54–61·145–148(임베드),
   `app/(main)/badges/[id]/page.tsx` 86(`.single()`)·268–272, `app/(main)/collections/[id]/page.tsx` 105–111, `app/api/itembooks/route.ts` 42–48·73, `app/api/badges/[id]/share-data/route.ts` 100(`.single()`), `app/spike/badge-reveal/page.tsx` 33–37(스파이크).
   관리자 화면·API, 배지·드랍 엔진, 크론·알림 배치, 프로필(`[username]`)·조합·미션·드랍·인벤토리 API는 모두 service 클라이언트다. 브라우저 클라이언트·미들웨어·Realtime·사용자 세션 RPC는 `badges`를 읽지 않는다. 배지 공개 판정 함수는 앱에 없다(조회마다 직접 조건).
   - 소프트 삭제(`deleted_at`): 세션 조회 15곳 모두 쿼리에서 거르거나 임베드가 null을 견딘다(`x.badge && !x.badge.deleted_at`). 정책에 넣지 않는다(공개 전 누출이 아니고 회귀만 생긴다).
   - 종료(`valid_until`): 세션 화면이 종료된 배지를 보유자에게 보여 준다. 정책에 넣지 않는다.
   - 공개 시각(`valid_from`)을 보지 않고 배지를 주는 경로가 있다: 체크인 배지 발급(`lib/strava/sync.ts` 771–812), 레거시 지점 연결 활동 배지(900–925), 미션 보상(`lib/missions/rewards.ts` 44·124), 조합 보상(`lib/combine/index.ts` 402),
     컬렉션 완성 보상(`lib/itembook/checker.ts` 220), 온보딩 완료 배지(`lib/onboarding-quest/completion.ts` 125). 그래서 모든 배지에 공개 시각 조건을 걸면 「받았는데 내 화면에서 안 보임」이 생길 수 있다.
   - 아이템 배지에 공개 시각 조건을 걸면 화면의 컬렉션 완성 분모(`collections/[id]` 241–248, `badges/page.tsx` 161, `api/itembooks` 129)가 장착 RPC(`179_slot_item_into_book_all_excluded_fallback.sql` 96–98, SECURITY DEFINER)·완성 체커(service)와 갈린다.
2. **라이브 DB(2026-10-05):** 정책은 「badges: 전체 읽기 허용」(`authenticated`, `qual = true`) 하나. 다른 테이블 정책이 `badges`를 참조하지 않고, 뷰·구체화 뷰·Realtime 발행이 없다.
   `badges`를 읽는 함수는 `expire_stale_poi_drops`·`slot_item_into_book`(SECURITY DEFINER)와 트리거 함수 `check_family_condition_consistency`(SECURITY INVOKER, `badges` 쓰기 트리거 `badges_family_consistency`. 쓰기는 service라 정책 영향 없음)다.
   `type`은 NOT NULL 열거형이다. 테이블 권한은 E4와 같은 Supabase 기본값이다.
3. **데이터(2026-10-05):** 배지 3,366개(삭제되지 않은 것: 체크인 1,832·아이템 270·활동 634, 소프트 삭제 630). `item_book_id`가 있는 배지는 아이템 배지뿐이다. 공개 시각이 미래인 배지 0개(`valid_from`이 있는 984개는 모두 과거), JAM! 카테고리 배지 1개.
   소프트 삭제 630개는 모두 비활성 컬렉션 소속 아이템 배지이고, 인벤토리 222행·지점 드랍 144행이 이 배지를 가리킨다(세션 화면은 이미 삭제된 배지를 거른다). 공개 전 컬렉션 소속 삭제되지 않은 배지와 그 획득·보유 기록은 0건이다.
   그래서 아래 조건으로 지금 새로 숨겨지는 행은 소프트 삭제 630개뿐이고 세션 화면 결과는 바뀌지 않는다.

## 착수 전에 정한 것 (2026-10-05. 1은 사용자 결정, 나머지는 카리나)

1. **조건 범위는 「활동 배지 + 컬렉션」이다(사용자 결정, 추천안).** 활동 배지(`type = 'activity'`, JAM! 배지 포함)는 공개 시각이 지났거나 비어 있어야 보이고, 소속 컬렉션이 있는 배지(지금은 아이템 배지뿐)는 그 컬렉션이 공개돼야 보인다. 체크인 배지는 지금처럼 보인다.
   운영툴이 만드는 두 누출(공개 전 JAM! 배지, 공개 전 컬렉션의 아이템 배지)을 막고, 공개 시각을 보지 않는 체크인 발급 경로·아이템 완성 분모와는 엮지 않는다.
2. 정책 조건(`ALTER POLICY`, 214·215와 같은 형태):
   `(type <> 'activity' OR valid_from IS NULL OR valid_from <= now()) AND (item_book_id IS NULL OR EXISTS (SELECT 1 FROM public.item_books b WHERE b.id = badges.item_book_id AND b.is_active = TRUE AND (b.valid_from IS NULL OR b.valid_from <= now())))`.
   컬렉션 공개 조건은 서브쿼리에 직접 적는다(215의 `item_books` 정책에만 기대지 않는다. 인증 유저로 평가하면 215 정책도 함께 걸리고 두 조건은 같다). PK 조회라 성능 영향은 작다.
3. 받아들이는 경계(지금 데이터 0건, PRD에 사실로 적는다): (가) 공개 시각을 보지 않는 경로(미션·조합·컬렉션 완성·온보딩·레거시 지점)로 공개 전 활동 배지를 먼저 받은 유저는 공개 시각까지 세션 화면에서 그 배지를 보지 못한다.
   운영툴은 미션·컬렉션이 연결 배지보다 먼저 공개되는 것을 사전 점검에서 막는다(1500 ⑨·⑩). (나) 공개 전 컬렉션 소속 아이템을 가진 유저는 인벤토리 화면에서 그 아이템을 보지 못한다(조합·드랍 시트는 service라 보인다).
4. `badges/[id]/page.tsx` 86행과 `share-data/route.ts` 100행의 `.single()`을 `.maybeSingle()`로 바꾼다(E4와 같은 0행 로그 잡음 방지, 결과는 같은 404).
5. 바꾸지 않는 것: 발급 경로·엔진·RPC·관리자 화면, 세션 조회의 다른 코드. `deleted_at`·`valid_until`은 정책에 넣지 않는다.

## 구현 계획 (파일 단위)

1. **새 마이그레이션 `jam-web/supabase/migrations/216_badges_select_launched.sql`**(번호 216은 2026-10-05 비어 있음). 215의 형식을 따른다: 머리 주석(티켓·「작성만 하고 실행하지 않았다」 경고·이유·변경(가정 1·2)·정책 이름의 「전체」가 낡게 되는 사실·001 주석과의 관계·
   영향(위 「착수 때 확인한 결과」 1~3, 받아들이는 경계 가정 3)·재실행 가능), `BEGIN; ALTER POLICY "badges: 전체 읽기 허용" ON public.badges USING (...); COMMIT;`, 검증 쿼리 주석(① `pg_policies` ② `SET LOCAL ROLE authenticated`로 공개 전 활동 배지·공개 전 컬렉션 소속 배지 0행
   ③ 같은 역할로 보이는 배지 수 = service로 센 조건 충족 배지 수), 파일 끝 `-- 되돌림 SQL` 주석 블록(원래 `USING (TRUE)`).
2. **`jam-web/src/app/(main)/badges/[id]/page.tsx` 86행, `jam-web/src/app/api/badges/[id]/share-data/route.ts` 100행:** `.single()` → `.maybeSingle()`와 이유 주석. 다른 코드는 바꾸지 않는다.
3. **`docs/specs/prd/02_DATA_MODEL.md` `badges` 절(137행 부근):** RLS 단락(가정 1~3, 마이그레이션 216, service는 정책을 거치지 않음, `deleted_at`·`valid_until`은 정책에 없음).
4. **`docs/agents/contract.json` `paths_exist`:** 216 경로 1줄(215 선례).
