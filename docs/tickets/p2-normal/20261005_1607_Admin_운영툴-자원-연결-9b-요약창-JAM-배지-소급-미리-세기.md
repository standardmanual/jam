# [Admin] 운영툴 자원 연결 ⑨-b 요약창의 JAM! 배지 소급 미리 세기

> 상위: 20260930_1500 ⑨(JAM! 배지)를 ⑨-a(핸들러, 20261004_1756 CLOSED)·⑨-b(이 티켓)로 나눴다(사용자 결정 2026-10-04). 선행 E1 20261001_2203(열릴 예정 배지 미리보기)은
> 2026-10-05 staging 머지(3098c63a)로 충족됐다.

## 핵심 요약

- 요구사항: 예약 공개되는 JAM! 배지는 공개 시각에 옛 기록으로 소급 지급되고 회수할 수 없다. 예약 등록 요약창(⑤-a, 운영툴 PRD §8.2 「요약창」)에서 「예약할 항목」에 든 JAM! 배지마다
  「공개되면 약 N명에게 P포인트」를 미리 세어 보인다. 미리 세기는 요약창 사전 점검과 **따로 요청**하고, 대상 유저가 많으면 **무작위 표본으로 추정**한다(아래 사용자 결정).
- 구현 계획: 아래 「구현 계획 (파일 단위)」. 서버 전용 새 파일 `badgePreview.ts`가 E1의 `previewUpcomingJamBadges`를 묶음 단위로 부르고, 실행 라우트에 세 번째 요청 `{ badgePreview: true }`를 더한다.
  요약창은 사전 점검 결과로 구역을 먼저 그린 뒤, 예약할 JAM! 배지가 있을 때만 두 번째 요청을 보내 배지 구역을 채운다.
- 관련 파일: `jam-web/src/lib/admin/opsInbox/execute/run.ts`(`dryRunExecution` 170–175, `linkedIdsFor` 233–251, `pointedByOf` 257–267, `loadBundleItems` 142),
  `jam-web/src/app/api/admin/ops-inbox/[bundleId]/execute/route.ts`(`POST` 28–67, 모드 판정 46–50), `jam-web/src/lib/admin/opsInbox/execute/jamBadge.ts`(`JAM_BADGE_HANDLER.prepare` 166–181),
  `jam-web/src/lib/badge-engine/reevaluateCatalog.ts`(`previewUpcomingJamBadges` 318–391, 타입 282–301), `jam-web/src/lib/badge-engine/jamActionKeys.ts`(`JAM_ACTION_CONDITION_KEYS` 12–28, 순수),
  `jam-web/src/lib/admin/opsInbox/executeView.ts`(문구 15–25, `readPrecheck` 69–84, `SummarySource` 89, `buildExecuteSummary` 162–187), `jam-web/src/components/admin/ops/OpsExecuteBundle.tsx`

## 착수 전에 정한 것 (2026-10-05, 1·2는 사용자 결정)

1. **따로 요청한다(사용자 결정, 질문 1 추천안).** 요약창은 지금처럼 사전 점검(`{ dryRun: true }`)으로 바로 열리고, 배지 구역만 「미리 세는 중이에요」로 시작해 두 번째 요청(`{ badgePreview: true }`)의
   응답으로 채운다. 미리 세기가 느리거나 실패해도 요약창·예약 등록 버튼은 영향을 받지 않는다. 같은 실행 라우트(`maxDuration = 60`)에 세 번째 모드로 둔다.
2. **유저가 많으면 표본으로 추정한다(사용자 결정, 질문 2 추천안).** 전체 유저 ID를 읽어 무작위 순서로 섞은 뒤 20명씩 센다. 다 셌거나, 센 유저가 500명에 닿았거나, 40초가 지나면 멈춘다.
   다 세지 못했으면 배지별 유저 수를 `센 유저 수 대비 전체 유저 수`로 환산하고(반올림), 줄에 「유저 M명 중 K명을 세어 추정했어요」를 보인다. 유저가 적으면 전원을 센다.
3. (카리나 가정, 이의 없음) 미리 세는 대상은 사전 점검의 「예약할 항목」(`ready`)에 든 `jam_badge`뿐이다. 기다리는 중·못 하는 항목은 세지 않는다.
4. (카리나 가정) 배지 정의는 실행과 같은 `JAM_BADGE_HANDLER.prepare`로 만든다(`id`는 운영 항목 ID, `linkedIds`는 실행과 같은 규칙으로 채우되 아직 만들지 않은 대상은 자리표시 UUID, `pointedBy`는 그룹의 `linkPlan`).
   `prepare`가 실패하면(형식 오류) 세지 않고 「형식이 맞지 않아 세지 않았어요」다. DB 검사(`check`)는 부르지 않는다.
5. (카리나 가정) `badgeIds`로 좁히지 않는다. 이 묶음의 배지 정의를 `candidateBadges`로 넘겨 DB 배지와 함께 판정하고, 결과 `badges[]`에서 이 묶음 배지(운영 항목 ID)만 골라낸다.
   기존 계열에 새로 붙는 Lv.2 이상을 바르게 세기 위해서다. 배지마다 한 줄이고 여러 배지의 유저 수는 합치지 않는다.
6. (카리나 가정) JAM! 행동 지표가 아닌 조건으로 받는 배지는 세지 않고 줄을 구분한다. 판정 순서: 형식 오류 → JAM! 행동 지표 키(`JAM_ACTION_CONDITION_KEYS`)가 하나라도 있으면 센다 →
   같은 그룹 컬렉션의 완성 보상(`pointedBy`의 `collection_launch`·`reward_badge_id`)이면 「컬렉션을 완성하면 획득해요」 → `condition_json.mission_reward === true`이거나 미션 보상
   (`pointedBy`의 `mission`·`reward_badge_ids`)이면 「미션 보상으로 획득해요」 → 그 밖(사용량 지표 등)은 「이 조건은 미리 세지 않아요」.
7. (카리나 가정) 문구(UX 가이드 고정 용어 「획득」·「포인트」, 「P」 약어 금지):
   구역 제목 「공개되면 바로 획득하는 유저」, 센 값 「공개되면 약 N명에게 P포인트」(P는 `toLocaleString('ko-KR')` 숫자, 배지 포인트가 0이면 「공개되면 약 N명이 획득해요」),
   0명 「공개돼도 바로 획득하는 유저는 없어요」, 세는 중 「미리 세는 중이에요」, 실패 「미리 세지 못했어요」, 일부 유저 실패 「N명은 세지 못해 빼고 셌어요」.
8. (카리나 가정) 시험 묶음에서도 센다(읽기 전용이라 자원을 만들지 않는다).
9. (카리나 가정) 미리 세기는 예약 등록을 막지 않는다. 결정 기록·슬랙에도 남기지 않는다(읽기 전용 요청).
10. (카리나 가정) 유형 `admin`. 어드민 실렌더는 PC 세션에서 한다(클라우드 세션에는 환경 파일이 없다, E5와 같은 처리).

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

- 서버: 새 `execute/badgePreview.ts`(서버 전용)의 `previewBundleBadges`가 사전 점검의 예약할 `jam_badge`마다 `JAM_BADGE_HANDLER.prepare`로 정의를 만들고(`id` = 운영 항목 ID), 줄 상태를 센 값·컬렉션 보상·미션 보상·세지 않는 조건·형식 오류·실패로 나눈다.
  센 배지가 있으면 전체 유저 ID를 읽어 Fisher–Yates로 섞고 `previewUpcomingJamBadges`(E1)를 20명씩 부른다(`badgeIds` 없이 `candidateBadges`만, 결과에서 이 묶음 배지만 골라냄). 500명 또는 40초에서 멈추고, 다 세지 못했으면 `센 값 × 전체 ÷ 센 유저`로 반올림해 환산한다.
  유저 단위 오류는 분모에서 빼고 `failedUsers`로 세며, 덩어리 예외·유저 목록 실패·센 유저 0명은 센 줄을 `failed`로 둔다(던지지 않는다). 엔진은 동적 import로 불러 `run.ts`를 가져오는 다른 곳이 엔진을 끌어오지 않게 했다.
- `run.ts`: `badgePreviewExecution(service, bundleId, deps)`(묶음 읽기 → `precheckBundle` → `previewBundleBadges`). `linkedIdsFor`·`pointedByOf`는 `ctx` 대신 `byId`를 받게 바꿔 내보냈다(호출부 `runGroup` 한 곳, 동작 불변).
