# [Admin] 운영툴 자원 연결 ⑪-a 공개 뒤 「지금 종료」 API

> 상위: 20260930_1500 ⑪(공개 뒤 지금 종료)을 ⑪-a(서버, 이 티켓)·⑪-b(화면: 버튼·확인창·옛 안내 걷어 내기, 착수 때 티켓)로 나눴다(사용자 결정 2026-10-06).
> 선행 ⑤·⑦·⑩은 모두 끝났다(⑤는 PC 실렌더 대기).

## 핵심 요약

- 요구사항: 게재중인 운영 항목 하나를 「지금 종료」한다. 자원의 종료 시각 칸을 지금으로 바꾸고, 운영 항목을 「종료」로 닫고, 결정 기록 `end`와 슬랙 `#jam-report`를 남긴다.
  대상은 홈피드 카드·미션·JAM! 배지·컬렉션·레시피이고 드랍은 409다(운영툴 PRD §8.7·§11.7). 확인창(⑪-b)이 먼저 부를 미리 보기(`{ dryRun: true }`)는 그 항목을 가리키는
  게재 중 항목과 미션·컬렉션의 영향 유저 수를 돌려준다. 같은 순간 상태 맞추기(⑦)가 이 일을 「밖에서 바뀜」으로 잘못 기록하는 경합도 막는다.
- 구현 계획: 아래 「구현 계획 (파일 단위)」. 핸들러 계약에 선택 메서드 `end`를 더하고 다섯 종류가 구현한다. 새 서버 파일 `execute/end.ts`가 공개 전 취소(`execute/cancel.ts`)의
  모양을 따라 미리 보기·실행·슬랙을 맡고, 새 라우트 `POST /api/admin/ops-inbox/[bundleId]/items/[itemId]/end`가 부른다.
- 관련 파일: `jam-web/src/lib/admin/opsInbox/execute/handlers.ts`(`CancelResult` 73, `ExecuteHandler` 129–162), `execute/cancel.ts`(`MESSAGES` 32–46, `planCancel` 137, `previewCancel` 169,
  `cancelItem` 190, 결정 기록 264–274, `notifyCancel` 302), `execute/run.ts`(`ExecuteDeps` 125, `ITEM_COLUMNS` 145, `loadBundleItems` 149, `itemLabelOf` 170, `postAndRecord` 590),
  `execute/groups.ts`(`pairOf` 58, `resolveLinkGraph` 91, `cancelSetOf` 253), `execute/homeFeedCard.ts`(`cancel` 126, `observe` 151), `execute/mission.ts`(읽는 칼럼 61, `cancel` 139, `observe` 164),
  `execute/jamBadge.ts`(읽는 칼럼 73, `cancel` 226, `observe` 254), `execute/collectionLaunch.ts`(읽는 칼럼 60, `cancel` 130, `observe` 157), `execute/recipe.ts`(읽는 칼럼 48, `cancel` 146, `observe` 169),

## 착수 전에 정한 것 (2026-10-06, 1~4는 사용자 결정)

1. **⑪을 둘로 나눈다(사용자 결정, 질문 1 추천안).** 테스트·문서 포함 약 20파일·1,600줄이라 처음 추정(8파일·560줄)의 세 배다. 이 티켓은 서버(종료 처리·미리 보기·상태 맞추기 보완·슬랙),
   ⑪-b는 화면(게재중 항목의 [지금 종료하기]·확인창·옛 「아직 예약 등록을 연결하지 않았어요」 안내 걷어 내기)이다.
2. **컬렉션을 일찍 끝내면 완성 판정이 멈추는 것은 그대로 둔다(사용자 결정, 질문 2 추천안).** 예정대로 끝날 때와 같은 규칙이다(02_DATA_MODEL 264–272 「노출 중」, E1 결정).
   ⑪-b 확인창이 「채우던 유저는 더는 완성 보상을 받을 수 없어요」를 알린다.
3. **확인창에 미션·컬렉션의 영향 유저 수를 보인다(사용자 결정, 질문 3 추천안).** 미리 보기 응답이 미션은 참가자 수·진행 중 유저 수, 컬렉션은 채우는 중 유저 수를 준다. 카드·배지·레시피는 숫자가 없다.
4. **미션을 일찍 끝내도 종료 결과 알림은 그대로 보낸다(사용자 결정, 질문 4 추천안).** `lib/notifications/batch/missions.ts`의 #24(136–147행, `ends_at <= now`이고 2일 안)는
   다음 18시(KST) 배치에서 참가자 전원에게 한 번 간다. #21 마감 임박(74–81행, `ends_at`이 오늘+2일)은 더 가지 않고 이미 보낸 것은 그대로다. #23 순위 상승(210–218행)은 끝나면 멈춘다.
   순위 확정 알림과 종료 뒤 정산 배치는 없다. 코드 변경 없음. ⑪-b 확인창이 「다음 18시 알림에서 참가자 N명에게 종료 결과 알림이 가요」를 알린다.
5. (카리나 가정, 이의 없음) **레시피도 대상이다.** E3(20261002_0710) G5 사용자 결정과 PRD §8.7·07 4.9가 이미 넣었다. 1500 Q5의 「레시피는 안내만」은 그 앞의 결정이다. PRD §12 1554행의
   대상 목록에 레시피가 빠져 있어 함께 고친다.
6. (카리나 가정) **처리 순서는 PRD §11.7 그대로다.** 인증 → 본문 → 조건부 상태 update(선점: `status = 'live'` 조건으로 `ended`) → 자원 종료 → 결정 기록 → 응답 → 응답 뒤 슬랙.
   자원 종료가 실패하면 항목을 `live`와 원래 `ends_at`으로 되돌리고(`status = 'ended'` 조건) 500이다. 되돌리기도 실패하면 500 문장과 `#jam-alert` 글이 「항목은 종료로 바뀌었지만 자원은 아직
   게재 중」을 알린다(상태 맞추기는 `ended` 항목을 읽지 않으므로 사람이 기존 어드민에서 확인해야 한다).
7. (카리나 가정) **운영 항목의 `ends_at`도 같은 시각으로 바꾼다.** 선점 update가 `ends_at = 지금(ISO)`을 함께 쓰고, 원래 값은 결정 기록 `diff`(`{ ends_at: { before, after } }`)에 남긴다.
   운영 신호의 날짜별 구성(`opsSignals/composition.ts` `bundleItemPeriod` 282–289)이 `ended` 항목도 항목 기간으로 세므로, 바꾸지 않으면 일찍 끝낸 카드가 남은 날짜에 계속 잡힌다.
8. (카리나 가정) **자원이 이미 끝났거나 없으면 자원은 건드리지 않고 항목만 닫는다.** 핸들러 `end`가 `alreadyEnded`(종료 시각이 이미 지남, 상태 맞추기가 아직 돌지 않음) 또는 `missing`(행 없음,
   배지는 `deleted_at` 있음)을 돌려주면 성공으로 보고 항목을 `ended`로 닫는다(공개 전 취소의 「이미 없음」과 같은 해석). 자원 ID가 비어 있는 실제 묶음 항목도 `missing`이다.
9. (카리나 가정) **상태 맞추기 경합을 막는다.** 크론이 항목을 `live`로 읽은 뒤 이 API가 먼저 닫으면, 크론의 `live → ended` 전이는 0행인데 `external_change`(종료 시각 차이)는 지금 그대로 남는다
   (`reconcile.ts` 552–569). `reconcileOpsItems`에서 계획한 전이가 0행(`applyTransition`이 `null`)인 항목은 그 회차의 `externalChanges`에서 뺀다. 상태가 그사이 바뀌었다면 읽은 값이 낡았기 때문이다.
   전이를 계획하지 않은 항목의 차이와 전이가 오류로 던진 항목은 지금처럼 남긴다.
10. (카리나 가정) **그 항목만 끝낸다(PRD §8.7).** 미리 보기의 `pointedByLive`는 이 항목을 연결 칸으로 **직접** 가리키는 `live` 항목(같은 묶음)이고, 함께 끝내지 않는다. 막는 항목도 없다.
11. (카리나 가정) **영향 유저 수.** 미션: `countRowsByKey`로 `user_mission_participations`·`user_mission_completions`를 세어 `participants`와 `inProgressUsers`(`sumInProgressUsers`).
    컬렉션: `user_item_book_slots`(`item_book_id` = 자원 ID)의 `user_id`를 `fetchAllRows`로 읽어 중복을 없애고, `user_item_book_completions`의 같은 컬렉션 유저를 뺀 수가 `fillingUsers`다.
    체크인 배지 획득 이력은 세지 않는다(운영툴 컬렉션은 아이템 배지로 채운다. ⑪-b 문구는 「약 N명」). 세기가 실패하면 `impact: null`로 200이다(미리 보기는 막지 않는다). 시험 묶음은 세지 않는다.
12. (카리나 가정) **시험 묶음**은 자원 읽기·쓰기 없이 상태만 바꾸고 결정 기록은 같게 남기며 슬랙 글 앞에 「[시험]」을 붙인다(PRD §8.8의 취소와 같다).
13. (카리나 가정) **드랍**은 놓이는 순간 예약됨 → 종료로 가므로(§8.6 1053행) 실제로는 `live`가 되지 않는다. 그래도 API는 핸들러에 `end`가 없는 종류를 409로 막는다. 드랍 안내 화면은 ⑪-b도 만들지 않는다.
14. (카리나 가정) 서버 문장(응답 `error`, 화면에 그대로 나간다. DB 오류 원문은 싣지 않는다):
    - `notLive`(게재중이 아님·선점 0행): 「게재중인 항목만 지금 종료할 수 있어요. 화면을 새로 고쳐 상태를 확인해 주세요.」
    - `noEnd`(드랍 등): 「이 종류는 지금 종료가 없어요. 놓인 드랍은 그대로 둬요.」
    - `itemNotFound`: 취소와 같은 「찾을 수 없는 항목이에요.」
    - `endFailed`(자원 종료 실패, 되돌림 성공): 「지금 종료하지 못했어요. 자원은 그대로 게재 중이에요. 잠시 뒤 다시 눌러 주세요.」
    - `revertFailed`(되돌림도 실패): 「지금 종료하지 못했어요. 항목은 종료로 바뀌었지만 자원은 아직 게재 중이에요. 기존 어드민에서 종료 시각을 확인해 주세요.」
    - `previewFailed`: 「지금 종료할 항목을 확인하지 못했어요. 잠시 뒤 다시 눌러 주세요.」
    - 슬랙 `#jam-report`: 「지금 종료 1건」 다음 줄 `• {itemLabelOf}`, 사유가 있으면 `사유: {사유}` 줄. 자원이 이미 끝났거나 없었으면 항목 줄 끝에 「(이미 끝나 있었어요)」·「(자원이 이미 없었어요)」.
    - 슬랙 `#jam-alert`: 「지금 종료를 끝내지 못했어요」 다음 줄 `• {itemLabelOf} — {사유}`, 결정 기록을 남기지 못했으면 그 줄을 더한다(`formatCancelFailureMessage` 199–211과 같은 모양).
      결정 기록 실패만 있을 때(종료는 됨)도 이 글을 보낸다.
15. (카리나 가정) 유형 `api`. 화면이 없으므로 어드민 실렌더는 ⑪-b에서 한다.
