# [Admin] 운영툴 자원 연결 ⑫-b 카드의 레시피 칸과 운영툴 「카드 → 레시피」 연결 (DB)

## 핵심 요약

- 요구사항: 마이그레이션 217로 `today_cards_template_type_check`에 `recipe_reveal`을 더하고 `today_cards.recipe_id`(비어도 됨, `combination_recipes` 외래 키, `ON DELETE SET NULL`)를 만든다.
  어드민 카드 폼에 레시피 입력 칸을 둔다. 운영툴은 카드 → 미션과 같은 방식으로 카드 `links`가 레시피를 가리키면 `recipe_id`를 채우고(`resource.recipe_id`로 기존 레시피 직접 지정도 가능,
  둘 다 있으면 못 하는 항목), 레시피를 공개 전에 취소하면 그 레시피를 가리키는 예약된 카드도 함께 취소하며 게재 중 카드가 가리키면 409다. 카드가 레시피보다 먼저 공개돼도 막지 않는다(07 §4.5 예외).
- **금지(사용자 지시 2026-10-06)**: 217을 적용한 뒤 `/jam-ship`이 끝나기 전에는 staging 어드민에서 `recipe_reveal` 카드를 하나도 만들지 않는다(시험 카드 포함). DB가 staging·프로덕션
  공용이라, 그 카드를 프로덕션의 옛 코드가 돌리는 어드민 카드 화면이 읽고 오류를 낸다(사용자 설명. 옛 코드의 `todayTemplateFields`는 모르는 값에 칸 정의 없이 `undefined`를 돌려준다,
  `origin/main` 2026-10-06 확인). 217 적용 뒤의 확인은 테스트와 SQL 읽기로만 하고, 첫 카드는 아래 ⑫-a 「후속 범위」대로 `/jam-ship` 뒤에 만든다.
- 구현 계획: 아래 「구현 계획」(파일 단위, ⑫-a 머지 뒤 staging 0a3746c6b 기준). 유형 `db`(마이그레이션 파일 작성만, 실행은 머지 승인 뒤 메인 세션).
- 관련 파일: `jam-web/supabase/migrations/`(217, CHECK 교체 본보기 `158_ranking_modes.sql` 80–100의 DO 블록, 되돌림 SQL 포함), `jam-web/src/types/database.generated.ts`,
  `jam-web/src/lib/admin/opsInbox/registerInput.ts`(`CARD_RESOURCE_KEYS` 143–155, `toTodayCardRegisterInput` 332–443), `jam-web/src/lib/admin/opsInbox/execute/groups.ts`(`LINK_PAIRS` 37–46,
  `CREATION_KIND_ORDER` 49–56은 그대로 만족), `jam-web/src/lib/admin/recipe-references.ts`(`collectRecipeReferences` 79, 지금은 배지만 셈), `jam-web/src/app/admin/today/TodayCardForm.tsx`,
  `jam-web/scripts/asset-generator/__tests__/registerHomeFeedBundle.test.ts`(⑫-a의 임시 허용을 217 대조로), 문서 운영툴 PRD §8.3 쌍 표(889–898)·§8.4·§8.7, `docs/service/prd/02_DATA_MODEL.md`

## 완료 조건

- 217이 적용돼 라이브 DB CHECK에 `recipe_reveal`이 있고 `today_cards.recipe_id`가 있다(되돌림 SQL이 파일에 있다, 실행은 사용자 승인 뒤 메인 세션).
- 운영툴에서 카드가 레시피를 가리키는 묶음을 예약 등록하면 카드의 `recipe_id`가 그 레시피 ID이고, 레시피를 공개 전 취소하면 그 카드도 함께 취소된다(테스트).
- 운영툴에서 공개 전 레시피를 취소할 때 운영툴 밖 카드(어드민에서 만든 카드)가 그 레시피를 가리키면 지우지 않고 409다(가정 A, 운영툴 PRD §8.7). 어드민에서 레시피를 지울 때는
  카드가 가리켜도 막지 않고, 카드는 레시피 줄 없이 남는다(가정 B, 미션의 어드민 삭제와 같음, 혜린 가정 7)(테스트).
- 카드 → 레시피 연결에는 공개 순서 검사가 없고, 「가장 먼저 성공」 배지의 공개 시각 검사가 카드에 걸리지 않는다(테스트).
- ⑫-a의 템플릿 대조 테스트 임시 허용이 없어지고 217과 대조한다.
- 운영툴 PRD §8.3 쌍 표에 카드 → 레시피가 있고 02_DATA_MODEL에 `recipe_id`가 있다.
- 계측이 기록하는 모양이 화면과 같다: `jam-web/src/lib/today/events.ts`(`assertCardExposable`의 select, 105–107행 타일 수 판정)가 `recipe_id`와 레시피 공개 상태로 레시피 공개 카드의 타일 수를 정한다.
  ⑫-a(20261006_1217)는 `recipe_id` 칼럼이 없어 select에 더할 수 없어 `events.ts`를 건드리지 않았고, 그래서 공개 뒤 레시피 공개 카드는 화면 `list`·기록 `brief`로 어긋난다(홈피드 PRD §9 허용 차이 둘째).
  이 항목이 끝나면 PRD §9 허용 차이에서 그 줄을 지우고 `shapeParity.test.ts`의 「허용 차이 — 레시피 공개 카드」 케이스를 「둘 다 `list`」로 바꾼다.
- (⑫-a에서 넘김, 사용자 승인 2026-10-06) 레시피 공개 카드에 이동 주소 칸이 있다: `jam-web/src/lib/admin/today-sections.ts`의 `recipe_reveal` 받는 칸에 `targetHref: true`, 폼의 「/combine 고정」 안내 정리,
  운영툴 카드 변환이 이 칸을 받는다. 사용자 결정 Q4 「운영자 지정 주소가 우선」이 어드민·운영툴에서 실제로 닿는다(테스트).

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

- 마이그레이션 217(`217_today_cards_recipe_reveal.sql`): `today_cards.recipe_id`(uuid, 비어도 됨, `combination_recipes` 외래 키 `ON DELETE SET NULL`)와 `template_type` CHECK 9개 값(`recipe_reveal` 추가). 순수 확장,
  158 방식의 동적 CHECK 교체, 검증 쿼리·되돌림 SQL 포함. 생성 타입은 손으로 더했고 적용 뒤 Supabase 생성 결과와 `today_cards` 블록이 일치했다.
- 어드민: 카드 폼에 레시피 선택 칸(`recipe_reveal`만, 선택지는 `todayRecipeOptions.ts`, 종료된 레시피는 「종료됨」 표시)과 이동 주소 칸. 「/combine 고정」 안내를 지웠다. 상세 화면에 레시피 이름.
  날짜별 미리보기가 홈과 같은 함수로 `resolved_recipe`를 싣는다.
- 계측: `events.ts`가 `recipe_id`를 읽고 레시피 공개 카드만 레시피 행을 한 번 더 읽어 공개 중이면 `list`, 그 밖은 `brief`로 기록한다(읽기 실패는 기록을 막지 않음). 홈피드 PRD §9 허용 차이 둘째를 지웠다.
- 운영툴: `LINK_PAIRS`에 `home_feed_card → recipe`. 변환(`fillLinkedId`)·등록 전 검사(레시피 존재)·함께 취소·실패로 닫기가 카드를 포함한다. 함정 1은 `differsFromLinkedRecipe`가 `jam_badge`일 때만
  견주게 고쳤고, 카드 → 레시피에는 공개 순서 검사가 없다.
