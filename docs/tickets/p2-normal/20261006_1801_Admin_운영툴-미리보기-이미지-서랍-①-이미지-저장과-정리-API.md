# [Admin] 운영툴 미리보기·이미지·서랍 ① 이미지 저장·정리 API

> 상위: 20260930_1501 ① · 20260930_1450 순서 3 · 07 인벤토리 D

## 핵심 요약

- 요구사항: 운영자 브라우저가 만든 이미지를 받아 WebP로 저장하고 항목의 `resource`에 쓴다. 예약된 뒤에는 `created_resource`가 가리키는 자원에도 함께 쓴다(Q1 B). 파일은 새 자원 전용 경로에 올리고 예약 실패·공개 전 취소·되돌림 때 그 파일만 지운다(Q3 A). 렌더는 브라우저에서 하므로(Q8 A, 서버 렌더는 웹 서버에서 도는 선례가 없다) 이 조각에는 렌더 코드가 없다.
- 구현 계획(파일 단위, 2026-10-06 조사 결과를 따름):
  1. 신규 `jam-web/src/lib/admin/opsInbox/image.ts`(120~180줄): `imageKeyOfKind(kind)`(카드 `cover_image_url`, 미션·배지·컬렉션 `image_url`, 그 밖의 종류는 이미지 없음), `storagePathOf(kind, itemId)`(경로는 **항목 ID 기준** `ops-inbox/{접두사}/{itemId}.webp`·`.png`. 자원 ID 경로를 쓰지 않으므로 기존 이미지를 덮어쓰지 않고, 자원이 이미 지워진 뒤에도 정리할 수 있다),
     `applyItemImage(service, {itemId, url})`(`edited.resource`에 기존 `resource`와 합친 객체 전체를 쓴다. `edited`는 최상위 키 덮어쓰기라 합쳐서 써야 한다(`itemView.ts` `itemField`). 항목의 `updated_at`을 조건으로 쓰고 충돌하면 한 번 다시 읽어 재시도한다. 예약된 뒤(`created_resource`에 자원 ID가 있고 `sample`이 아님)에는 그 자원 행의 이미지 칸도 함께 갱신), `removeOpsImageFiles(service, {kind, itemId})`(두 파일을 지운다. 실패하면 던지지 않고 서버 로그에만 남긴다).
  2. 신규 `jam-web/src/app/api/admin/ops-inbox/[bundleId]/items/[itemId]/image/route.ts`(130~170줄): `POST` FormData(`image` PNG 5MB 이하). `cancel/route.ts` 패턴(`getAdminUser`, `isUuid`, 고정 오류 문장, `maxDuration = 60`). `convertBadgeImageToWebp`로 변환 → 두 파일을 `APPLY_GENERATED_IMAGE_BUCKET`에 upsert → `applyItemImage`. 상태가 반려·취소·실패·종료인 항목(예약된 뒤에도 쓰므로 승인됨·준비중·예약됨·게재중은 받는다, Q1 B)이나 시험 묶음,  이미지 칸이 없는 종류는 거절한다. 시험 묶음은 자원이 없어 이미지를 저장하지 않는다.
  3. `execute/cancel.ts` `cancelItem`(190줄, 자원 단계 214~232줄 근처): `cancelResource` 성공 직후 `removeOpsImageFiles` 호출(8~15줄). 자원 ID가 없거나 이미 없어도 호출한다.
  4. `execute/run.ts` `failGroup`(318~340줄): `handler.undo` 뒤에 `removeOpsImageFiles`(5~10줄).
  5. `execute/reconcile.ts` `undoLeftover`(434~446줄): undo 성공 분기에 `removeOpsImageFiles`(5~10줄).
  6. 테스트: 신규 `.../image/__tests__/route.test.ts`와 `opsInbox/__tests__/image.test.ts`(합 150~220줄, `asset-generator/apply/__tests__/route.test.ts`의 supabase mock 방식. sharp는 실제 실행), 기존 `execute/__tests__/cancel.test.ts`·`run.test.ts`·`reconcile.test.ts`에 정리 호출 검증 한 케이스씩(`fakeDb.ts`의 storage 스텁은 아현이 필요한 만큼만 추가).
  7. 문서: 운영툴 PRD §8.8 마지막 두 줄을 「항목 먼저, 예약 뒤 자원에도」 규칙으로 고치고, §11에 `### 11.12` 이미지 저장 API를 §12 앞에 더한다(30~50줄). 1801 완료 기록, 1501 「주요 의사결정」.
  - 정하지 않고 둔 것(아현은 이대로 구현): 이미지 저장은 결정 기록을 남기지 않는다(새 `action` 값 없음). 파일 삭제 실패는 취소·되돌림을 막지 않고 로그만 남긴다. `fakeDb`에 storage가 없으면 호출 기록만 남기는 스텁을 더한다.
  - 수정하지 않는 것: `asset-generator/apply/route.ts`, `opsInbox/edit.ts`, `decide.ts`의 `editItem`, `opsSignals/composition.ts`(`hasItemImage`는 카드 모양의 `cover_image_url`만 보며 그대로 둔다).
- 관련 파일: `jam-web/src/app/api/admin/asset-generator/apply/route.ts`(기존 행에만 붙임, 그대로 둠), `jam-web/src/lib/admin/opsSignals/composition.ts`(`hasItemImage`, 수정 없음)

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
- 항목 이미지 저장 API(`POST .../items/[itemId]/image`)와 파일 정리를 만들었다. PNG(5MB 이하)를 WebP로 바꿔 항목 ID 기준 경로 `ops-inbox/{접두사}/{항목ID}.png·.webp`에 올리고 항목의 `edited.resource`에 합쳐 쓴다. 예약된 뒤에는 자원 행의 이미지 칸에도 쓴다. 렌더 코드는 없다(브라우저 렌더는 ③).
- 공개 전 취소(`cancel.ts`)·예약 실패 되돌림(`run.ts` `failGroup`)·상태 맞추기 되돌림(`reconcile.ts` `undoLeftover`)에서 그 항목의 파일을 지운다. 삭제 실패는 로그만 남기고 막지 않는다. 결정 기록은 남기지 않는다.
- 운영툴 PRD §8.8을 「항목 먼저, 예약 뒤 자원에도」 규칙으로 고치고 §11.12를 더했다. DB 변경 없음.
