# [Admin] 운영툴 서랍 ④-a 승인 색 쌍 데이터와 「색 채우기」 서버

> 상위: 20261006_1804(④) → 20260930_1501. 코드 지도 조사(2026-10-07)로 ④를 ④-a(데이터·서버) → ④-b(서랍 화면) 두 조각으로 나눴다.

## 핵심 요약

- 요구사항: 트라이브별 승인 색 쌍 상수와 정본 문서를 만들고, 서버에 `fill_color` 결정을 더한다. 검토중 카드의 `color_pending`을 해제하며 `image_spec.bg`·`end`와 `colors.*`를 함께 채우고 결정 기록에 남긴다.
- 선행: 승인 색 쌍 값 확정(윈터·채원 검토안 → 사용자 확정). 값이 확정되기 전에는 상수 파일을 만들지 않는다.
- 구현 계획(파일 단위, 줄 번호는 2026-10-07 조사 시점):
  1. `jam-doc/planning/content/TRIBES.md`: 「승인 색 쌍」 절 신설(트라이브별 쌍·이름·근거). 정본이다.
  2. 신규 `jam-web/src/lib/admin/opsInbox/tribePalettes.ts`(서버·클라이언트 공용 순수 모듈): 트라이브 ID별 승인 쌍 상수와 `approvedPairsOf(tribeId)`·`isApprovedPair`. `tribe_id`가 null인 카드의 처리는 확정 때 함께 정한다.
  3. `jam-web/src/lib/admin/opsInbox/constants.ts`: `OPS_DECISION_ACTION_FILL_COLOR`(`ops_decisions.action`에 CHECK 없음, DB 변경 없음).
  4. `jam-web/src/lib/admin/opsInbox/decide.ts`: `fillColor()` 신설. `editItem`(462~560줄)은 검토중만·`color_pending` 불가·새 키 불가라 재사용하지 않고, 내부에서 `saveEditedItem`(391~446줄, 낙관적 잠금·결정 기록 insert·실패 복원)을 쓴다. 검토중이 아니면 409, 색은 `validateEditedColor`(validate.ts 421줄)로 검증한다.
  5. `jam-web/src/app/api/admin/ops-inbox/[bundleId]/decisions/route.ts`: `ACTIONS`(28줄)에 `fill_color`를 더하고 분기한다. 응답은 기존 `{ ok, updatedAt, changed }`·400 `{ error, fieldErrors }`를 따른다.
  6. `jam-web/src/lib/admin/opsInbox/labels.ts`(색 대기 107줄 근처)·`slack.ts`: 새 action 문구.
  7. 테스트: 신규 `tribePalettes.test.ts`, 수정 `decide.test.ts`·`decisions/__tests__/route.test.ts`·`fields.test.ts`·`labels.test.ts`·`slack.test.ts`·`opsSignals/__tests__/rules.test.ts`(채운 뒤 신호 사라짐).
- 규모: 소스 6개·약 170줄 + 테스트 7개·약 200줄 + 문서 2개. 임계값을 넘기므로 첫 호출부터 `planOnlyWaiver`를 넣는다.
- 관련 파일: 위 계획의 경로. 영향 스펙 `docs/specs/prd/ops-tool/PRD.md`(§3.1, 수정 절 595줄 근처).

## 결정 (2026-10-07 사용자 승인, 코드 지도 조사 뒤)

- 승인 색 쌍의 정본은 **코드 상수 + `jam-doc/planning/content/TRIBES.md` 새 절**이다. DB 변경 없음. 쌍의 실제 값은 윈터(세계관)·채원(디자인)이 검토한 안을 사용자가 확정한 것만 쓴다(카리나는 값을 임의로 정하지 않는다).
- 색 쌍 하나를 고르면 `image_spec.bg`·`end`와 `colors.*`(색 견본 칩)가 **같은 값으로 함께** 채워진다. 이미지 제작은 `image_spec`을 읽고 미리보기 칩은 `colors`를 읽기 때문이다.
- 채우기는 **검토중 항목에서만** 가능하다. 승인 전에 채우면 승인 직후 자동 제작(1031)이 바로 동작한다. 색 대기 카드는 승인을 막지 않고 신호만 남긴다.
- 색 채우기를 **되돌리는 기능은 이번에 제외**한다(다른 쌍을 다시 고르면 된다). 결정 기록에는 누가 어떤 쌍으로 채웠는지 남긴다.
- 직접 입력도 허용한다(`#rrggbb` 형식 검증, 서버 `validateEditedColor`와 같은 식).

## 완료 조건

- [ ] 트라이브별 승인 색 쌍이 상수와 TRIBES.md에 같은 값으로 있다(사용자 확정 값).
- [ ] 검토중 카드에 `fill_color`를 보내면 `image_spec.bg`·`end`와 `colors.*`가 함께 채워지고 `color_pending`이 해제되며 결정 기록에 남는다.
- [ ] 검토중이 아닌 항목·형식이 틀린 색은 거절된다(409·400).
- [ ] 채운 뒤 신호 「비어 있는 컨텐츠」에서 해당 카드가 사라진다(규칙 테스트).
