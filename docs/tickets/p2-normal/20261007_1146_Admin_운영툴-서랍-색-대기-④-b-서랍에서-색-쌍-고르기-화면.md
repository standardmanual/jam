# [Admin] 운영툴 서랍 ④-b 서랍에서 색 쌍 고르기 화면

> 상위: 20261006_1804(④) → 20260930_1501. 코드 지도 조사(2026-10-07)로 ④를 ④-a(데이터·서버) → ④-b(서랍 화면) 두 조각으로 나눴다.

## 핵심 요약

- 요구사항: 색 대기 카드의 서랍·기획 상세에서 트라이브별 승인 쌍 목록을 보여 주고, 하나를 고르면 미리보기(색 견본 칩)가 바로 바뀐다. 직접 입력도 허용하고 `#rrggbb` 형식을 검증한다. 적용하면 ④-a의 `fill_color`로 저장한다.
- 선행: ④-a 20261007_1145.
- 구현 계획(파일 단위):
  1. 신규 `jam-web/src/components/admin/ops/OpsColorPairPicker.tsx`: 승인 쌍 목록(견본 칩·이름), 직접 입력(`BackgroundColorField` 재사용), [적용] 버튼. 선택하면 초안(`draft.values['colors.<키>']`)을 바꿔 미리보기가 즉시 바뀐다. 검토중이고 `color_pending`인 카드에서만 그린다.
  2. `jam-web/src/components/admin/ops/OpsItemActions.tsx`(「수정하기」 183~190줄 근처) 또는 `OpsItemFooter.tsx`(122~152줄): 색 대기 카드의 진입점.
  3. `jam-web/src/components/admin/ops/OpsScheduleDrawer.tsx`(208·217~219줄)·`OpsBundleWorkspace.tsx`(318~320줄)·`OpsDecisionWorkspace.tsx`: 선택기 연결, 적용 뒤 화면을 새로 읽는다.
  4. `jam-web/src/components/admin/ops/decisionClient.ts`: `fill_color` 요청 함수(기존 `postDecision`·`splitFieldErrors` 재사용).
  5. `docs/specs/prd/ops-tool/PRD.md` §3.1·수정 절(595줄 근처)·§6.1 갱신, 1501 티켓 갱신.
  6. 테스트: 신규 `colorPairPicker.test.tsx`, 수정 `scheduleDrawer.test.tsx`·`itemFooter.test.tsx`·`decisionClient.test.ts`·`no-html.test.ts` 확인.
- ④-a(1145) 완료로 넘어온 사항: (1) `fill_color` 요청 본문은 `{ action: 'fill_color', itemId, bg, end, expectedUpdatedAt }`이다(`decisionClient.ts`의 `postDecision` 재사용). 400 응답은 `fieldErrors: { bg?, end? }`다. (2) 쌍 목록은 `tribePalettes.ts`의 `approvedPairsOf(tribeId)`가 준다(트라이브 카드는 그 트라이브 쌍, `tribe_id` null은 공통 쌍, 이력 없는 트라이브는 빈 목록이라 직접 입력만 보인다). (3) 채우면 수정본에 `colors.bg`·`colors.end`가 생기고 기존 `colors.background` 같은 키는 그대로 남는다. `OpsCardPreview`의 색 견본 칩(37·49~66줄)은 `colors`의 모든 키를 보이므로, 칩이 어느 키를 보일지(쌍 선택 때 미리보기에서 `colors.bg`·`end`로 덮어 보이는 방식, 기존 키와 겹쳐 보이지 않게 하는 방식)를 구현 때 정한다. (4) 서버는 되돌리기·승인 쌍 강제가 없으므로 화면이 승인 쌍 목록으로만 고르게 한다.
- 규모: 소스 5~6개·약 200줄 + 테스트 4개·약 150줄 + 문서. 임계값을 넘기므로 첫 호출부터 `planOnlyWaiver`를 넣는다.
- 실렌더: 색 대기 시험 항목(검토중, `color_pending: true`)이 있는 시험 묶음을 만들어 로컬 `ADMIN_EMAILS`로 확인하고, 확인 뒤 사용자 승인 하에 정리한다.
- 관련 파일: 위 계획의 경로.

## 결정 (2026-10-07 사용자 승인, 코드 지도 조사 뒤)

- 승인 색 쌍의 정본은 **코드 상수 + `jam-doc/planning/content/TRIBES.md` 새 절**이다. DB 변경 없음. 쌍의 실제 값은 윈터(세계관)·채원(디자인)이 검토한 안을 사용자가 확정한 것만 쓴다(카리나는 값을 임의로 정하지 않는다).
- 색 쌍 하나를 고르면 `image_spec.bg`·`end`와 `colors.*`(색 견본 칩)가 **같은 값으로 함께** 채워진다. 이미지 제작은 `image_spec`을 읽고 미리보기 칩은 `colors`를 읽기 때문이다.
- 채우기는 **검토중 항목에서만** 가능하다. 승인 전에 채우면 승인 직후 자동 제작(1031)이 바로 동작한다. 색 대기 카드는 승인을 막지 않고 신호만 남긴다.
- 색 채우기를 **되돌리는 기능은 이번에 제외**한다(다른 쌍을 다시 고르면 된다). 결정 기록에는 누가 어떤 쌍으로 채웠는지 남긴다.
- 직접 입력도 허용한다(`#rrggbb` 형식 검증, 서버 `validateEditedColor`와 같은 식).

## 완료 조건

- [ ] 승인되지 않은 쌍은 목록에서 고를 수 없고, 직접 입력은 형식을 검증한다.

- [ ] 실제 화면에서 확인한다.
