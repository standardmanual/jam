## 결정 (2026-10-07 사용자 승인, 코드 지도 조사 뒤)

- 승인 색 쌍의 정본은 **코드 상수 + `jam-doc/planning/content/TRIBES.md` 새 절**이다. DB 변경 없음. 쌍의 실제 값은 윈터(세계관)·채원(디자인)이 검토한 안을 사용자가 확정한 것만 쓴다(카리나는 값을 임의로 정하지 않는다).
- 색 쌍 하나를 고르면 `image_spec.bg`·`end`와 `colors.*`(색 견본 칩)가 **같은 값으로 함께** 채워진다. 이미지 제작은 `image_spec`을 읽고 미리보기 칩은 `colors`를 읽기 때문이다.
- 채우기는 **검토중 항목에서만** 가능하다. 승인 전에 채우면 승인 직후 자동 제작(1031)이 바로 동작한다. 색 대기 카드는 승인을 막지 않고 신호만 남긴다.
- 색 채우기를 **되돌리는 기능은 이번에 제외**한다(다른 쌍을 다시 고르면 된다). 결정 기록에는 누가 어떤 쌍으로 채웠는지 남긴다.
- 직접 입력도 허용한다(`#rrggbb` 형식 검증, 서버 `validateEditedColor`와 같은 식).

### 구현 내용 요약
- 신규 `OpsColorPairPicker.tsx`: 검토중이고 `color_pending`인 카드의 기획 상세(S3 `previewAction` 슬롯)와 일정표 서랍(`OpsImageProduction` 위)에 「색을 골라 주세요」 상자를 그린다. 승인 쌍 목록(`approvedPairsOf`), 시작색·끝색 직접 입력(`BackgroundColorField`, `#rrggbb` 검증), [적용하기](`fill_color`). 고른 값은 저장 전 임시 상태(`ctx.colorPick`)에만 두고 미리보기는 `withColorPick`으로 `colors.bg`·`end`를 덮어 보인다. 수정 초안(draft)이 아니라 승인·반려 버튼을 막지 않고, 같은 항목을 수정 중이면 상자를 숨긴다. 적용 성공 시 토스트 「색을 채웠어요」 뒤 화면을 새로 읽고, 400의 `bg`·`end` 문장은 칸 아래, 409는 화면 새로 읽기다.
