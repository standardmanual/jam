# [Admin] 운영툴 미리보기 ⑤-a 배지·컬렉션·미션 미리보기

> 상위: 20261006_1805(⑤) → 20260930_1501. 코드 지도 조사(2026-10-07)로 ⑤를 ⑤-a(배지·컬렉션·미션) → ⑤-b(레시피·드랍) 두 조각으로 나눴다.

## 핵심 요약

- 요구사항: 기획 상세 왼쪽 칸과 일정표 서랍에서 `jam_badge`·`collection_launch`·`mission` 항목이 「이 종류의 미리보기는 곧 열려요」 대신 서비스 카드 모양으로 보인다. 항목 안의 값만 쓰고 DB를 더 읽지 않는다. 저장하지 않는 렌더이고 링크·계측이 없다.
- 선행: 없음(② 1802 CLOSED, 시험 믹스 등 ⑤-b와 무관).
- 구현 계획(파일 단위, 줄 번호는 2026-10-07 조사 시점):
  1. `jam-web/src/lib/admin/opsInbox/cardPreview.ts`: 종류별 표시 데이터 순수 함수를 더한다. `previewOf(item, draft)`가 홈피드 카드는 기존 `previewViewOf`, 나머지는 판별 유니온(`{ type: 'badge' | 'collection' | 'mission', ... }`)을 돌려준다. 값은 `edited ?? original`, 초안은 `applyDraftToItem`으로 덮고, 글자 칸은 `copy`를 먼저 보고 없으면 `resource`를 본다. 값 형식은 변환이 검사하지 않으므로 관대하게 읽는다(`itemToPreviewCard` 선례). 종류 판별은 `fields.ts`의 `isOpsHomeFeedCard`·`registerInput.ts`의 종류 상수를 쓴다. 읽을 칸: 배지(`copy.name`·`copy.description`, `resource.rarity`·`level`·`point_reward`·`image_url`, `starts_at`·`ends_at`), 컬렉션(`copy.name`·`description`·`story_text`, `resource.image_url`·`reward_points`, 기간), 미션(`copy.title`·`description`·`condition_text`, `resource.reward_points`·`image_url`, 기간).
  2. `jam-web/src/components/admin/ops/OpsCardPreview.tsx`(34줄 `if (!view) return <p>{PREVIEW_NOT_CARD_TEXT}</p>`, 37줄 `colors`, 49~66줄 색 견본 칩): 종류별 분기로 바꾼다. 안내 문구는 알 수 없는 종류에만 남긴다. 색 견본 칩은 모든 종류에서 이 파일 안에서 그린다. 도착·검토중이면서 이미지 칸이 비면 홈카드의 기존 문구를 따른다.
  3. 신규 `jam-web/src/components/admin/ops/OpsKindPreview.tsx`: 배지는 `components/ui/BadgeGridCard.tsx`(name·imageUrl·rarity·level·earned=true, `href` 생략), 컬렉션은 `components/ui/CollectionGridCard.tsx`(name·imageUrl·collected=0·total=0, `href` 생략)를 쓴다. 미션은 서비스 목록 카드(`app/(main)/missions/MissionsListClient.tsx` 345~460줄)와 같은 모양(썸네일, 제목, 설명 2줄, 보상 줄)으로 새로 그린다. 카드 아래에 설명·조건·기간 한 줄 요약. 인라인 `style={` 금지(`no-html.test.ts` 93~110줄).
  4. 호출부 `OpsBundleWorkspace.tsx`(323~327줄)·`OpsScheduleDrawer.tsx`(212줄): `OpsCardPreview` 호출은 그대로이고 내부가 분기한다. 바꿀 것이 거의 없으면 건드리지 않는다.
  5. `docs/specs/prd/ops-tool/PRD.md` §6.1 「카드 미리보기」 행(375줄 근처)·§6.4 서랍 행(499줄 근처) 갱신, 1501 「주요 의사결정」에 한 줄.
  6. 테스트: 수정 `components/admin/ops/__tests__/cardPreview.test.tsx`(44~47줄이 mission에서 `PREVIEW_NOT_CARD_TEXT`를 기대하므로 반드시 바뀐다)·`lib/admin/opsInbox/__tests__/cardPreview.test.ts`(88줄 확인)·`no-html.test.ts`(style 목록 영향 확인), 신규 `kindPreview.test.tsx`.
- 규모: 소스 3~4개·약 250줄 + 테스트 3~4개·약 150줄 + 문서 2개. 임계값을 넘기므로 첫 호출부터 `planOnlyWaiver`를 넣는다.
- 실렌더: 배지·컬렉션·미션 시험 항목이 있는 묶음을 만들어 로컬 `ADMIN_EMAILS`로 확인하고, 확인 뒤 사용자 승인 하에 정리한다. 서랍 쪽은 승인·예약 이후 항목이 필요해 어려울 수 있다.
- 관련 파일: 위 계획의 경로.

## 결정 (2026-10-07 사용자 승인, 코드 지도 조사 뒤)

- ⑤를 ⑤-a(배지·컬렉션·미션, 항목 안의 값만 사용·DB 추가 조회 없음) → ⑤-b(레시피·드랍, 이름 조회·시험 믹스 안내)로 나눈다.
- 화면 모양은 **서비스 카드 재사용**이다. 배지·컬렉션은 서비스 그리드 카드(`BadgeGridCard`·`CollectionGridCard`)를 링크 없이 그대로 쓰고, 미션은 서비스 목록 카드와 같은 모양으로 새로 그린다. 설명·조건 문장은 카드 아래 한 줄 요약으로 덧붙인다.
- 레시피 재료·보상 배지와 드랍의 지점·배지는 **이름을 읽어 보여 준다**(②의 「연결된 값은 읽지 않는다」 결정을 ⑤-b에서 푼다). DB 변경은 없고 읽기만 한다. 같은 묶음에서 새로 만들 배지는 「이 묶음의 배지」로 표시한다.
- 레시피 서랍의 시험 믹스 안내는 **예약 전·후로 문구를 나눈다**: 예약 전(검토중·승인됨)은 「예약 등록하면 믹스 화면에서 미리 시험해 볼 수 있어요」, 예약 이후는 `/combine` 링크와 함께 「공개 전에도 믹스 화면에서 시험해 볼 수 있어요」. 시험 믹스(1159)는 이미 구현돼 있어 새로 만들지 않는다. 보는 사람은 운영자 계정뿐이다.
- 카리나 가정(조사 사실에서 도출, 틀리면 알려 주세요): (1) 기기 폭 360·430 전환은 홈피드 카드 전용이고 다른 종류는 칸 폭에 맞춰 보인다. (2) 이미지가 없으면 서비스 폴백 아이콘(`MedalIcon`·`BookIcon`·`PackageIcon`)을 쓴다. (3) 색 견본 칩은 모든 종류에서 지금처럼 `OpsCardPreview` 안에서 보인다(`no-html.test.ts`가 인라인 `style` 파일을 5개로 고정하므로 새 컴포넌트에 `style={`을 쓰지 않는다). (4) 조건 JSON은 문장으로 바꾸지 않고, `condition_text`가 있으면 그것을 쓴다.
