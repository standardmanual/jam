# [Admin] 운영툴 미리보기 ⑤-b 레시피·드랍 미리보기와 시험 믹스 안내

> 상위: 20261006_1805(⑤) → 20260930_1501. 코드 지도 조사(2026-10-07)로 ⑤를 ⑤-a(배지·컬렉션·미션) → ⑤-b(레시피·드랍) 두 조각으로 나눴다.

## 핵심 요약

- 요구사항: `recipe`·`drop_schedule` 항목의 미리보기를 만든다. 재료·보상 배지와 드랍의 지점·배지·컬렉션은 서버가 이름·이미지를 읽어 주입한다(②의 「연결된 값은 읽지 않는다」 결정을 푼다). 레시피 서랍·기획 상세에는 예약 전·후로 나눈 시험 믹스 안내와 `/combine` 링크를 둔다.
- 선행: ⑤-a 20261007_1400(**CLOSED**, 종류 분기 구조 `previewOf`·`OpsCardPreview`·`OpsKindPreview` 완료).
- ⑤-a에서 넘어온 사항: (1) `OpsKindPreview.tsx`가 이미 있으니 레시피·드랍은 그 파일에 더한다(신규 파일이 아니다). (2) 서비스 카드를 재사용할 때 서비스 상태(수집 진행·획득 여부)가 표시에 끼어드는지 실렌더로 본다(⑤-a에서 컬렉션 「0/0」 진행 바를 `hideProgress`로 숨겼다). (3) `no-html.test.ts`는 인라인 `style={`을 금지한다. (4) 개발 서버의 이미지는 첫 요청 때 몇 초 늦게 뜬다.
- 구현 계획(파일 단위, 줄 번호는 조사 시점):
  1. `jam-web/src/lib/admin/opsInbox/query.ts` `getOpsBundleDetail`(408~480줄): 반환에 `previewNames`를 더한다(배지 `id·name·image_url·rarity`, 지점(poi), 컬렉션(item_books) `id·name`, 카테고리 라벨). 읽기 실패하면 빈 맵으로 폴백한다(`lib/ambient-drop/scheduleList.ts` `readNames` 105~118줄 선례, 비공개 함수라 export하거나 새로 만든다). `lib/admin/opsSchedule/itemDetail.ts`의 `getScheduleItemDetail`이 `getOpsBundleDetail`을 부르므로 서랍도 같은 곳을 고치면 된다.
  2. 주입 경로: `app/admin/ops-inbox/[bundleId]/page.tsx` → `OpsDecisionWorkspace.tsx` → `OpsBundleWorkspace.tsx` → `OpsCardPreview`로 prop을 내린다. 서랍은 `ScheduleItemDetail`과 `app/api/admin/ops-schedule/items/[itemId]/route.ts`의 JSON에 `previewNames`를 싣는다. 초안으로 ID가 바뀌면 맵에 없으므로 「(이름을 읽지 못함)」 폴백을 둔다. 같은 묶음의 `jam_badge`가 후보·보상이면 「이 묶음의 배지」로 표시한다.
  3. `lib/admin/opsInbox/cardPreview.ts` `previewOf`에 `recipe`(이름, 슬롯 수·종류, 후보·보상 배지, 보상 포인트, 기간)·`drop_schedule`(제목, 공개 시각, 지점·배지·컬렉션, 지점당 N개 또는 총 N개) 유니온을 더한다. 문장 선례는 `lib/ambient-drop/scheduleView.ts`(`AmbientDropScheduleNames`, `formatScheduleAt`, `scheduleRequestedCount`)와 `app/admin/ambient-drop/ScheduleList.tsx`의 `poiText`·`itemText`·`summarizeNames`.
  4. 신규 `jam-web/src/components/admin/ops/OpsKindPreview.tsx`에 레시피(보상은 `app/(main)/combine/RecipeRewardRow.tsx`를 `onClick` 없이 표시 전용, 슬롯 칸·후보 개수는 새로 그림)와 드랍(요약 카드, 새로 그림)을 더한다. 인라인 `style={` 금지.
  5. 시험 믹스 안내: `previewAction` 자리(`OpsDecisionWorkspace.tsx` 129줄 근처, `OpsScheduleDrawer.tsx` 213~214줄)에 `recipe` 항목일 때만 안내를 둔다. 예약 전(검토중·승인됨): 「예약 등록하면 믹스 화면에서 미리 시험해 볼 수 있어요」, 예약 이후: `/combine` 링크와 「공개 전에도 믹스 화면에서 시험해 볼 수 있어요」. 「시험 믹스」는 운영자 전용 표현이라 UX 용어표에는 올리지 않는다(1159 기록). 새 믹스 기능은 만들지 않는다.
  6. `docs/specs/prd/ops-tool/PRD.md` §6.1·§6.4·§8.8 갱신, 1501 기록.
  7. 테스트: 수정 `query.test.ts`·`opsSchedule` 쪽 목(필요 시), `cardPreview.test.ts`·`cardPreview.test.tsx`·`scheduleDrawer.test.tsx`, 신규 `kindPreview` 확장 테스트(레시피·드랍·폴백).
- 규모: 소스 8~9개·약 300줄 + 테스트 5개·약 200줄 + 문서. 임계값을 넘기므로 첫 호출부터 `planOnlyWaiver`를 넣고, 아현이 크다고 하면 「서버 조회 주입」과 「화면」으로 더 나눈다.
- 실렌더: 레시피·드랍 시험 항목이 있는 묶음을 만들어 로컬 `ADMIN_EMAILS`로 확인하고 확인 뒤 사용자 승인 하에 정리한다. 예약 이후 문구(링크)는 예약 등록이 필요해 단위 테스트로 확인하거나, 필요하면 먼 미래 시각으로 예약 후 취소한다(승인 필요).
- 관련 파일: 위 계획의 경로.

## 결정 (2026-10-07 사용자 승인, 코드 지도 조사 뒤)

- ⑤를 ⑤-a(배지·컬렉션·미션, 항목 안의 값만 사용·DB 추가 조회 없음) → ⑤-b(레시피·드랍, 이름 조회·시험 믹스 안내)로 나눈다.
- 화면 모양은 **서비스 카드 재사용**이다. 배지·컬렉션은 서비스 그리드 카드(`BadgeGridCard`·`CollectionGridCard`)를 링크 없이 그대로 쓰고, 미션은 서비스 목록 카드와 같은 모양으로 새로 그린다. 설명·조건 문장은 카드 아래 한 줄 요약으로 덧붙인다.
- 레시피 재료·보상 배지와 드랍의 지점·배지는 **이름을 읽어 보여 준다**(②의 「연결된 값은 읽지 않는다」 결정을 ⑤-b에서 푼다). DB 변경은 없고 읽기만 한다. 같은 묶음에서 새로 만들 배지는 「이 묶음의 배지」로 표시한다.
- 레시피 서랍의 시험 믹스 안내는 **예약 전·후로 문구를 나눈다**: 예약 전(검토중·승인됨)은 「예약 등록하면 믹스 화면에서 미리 시험해 볼 수 있어요」, 예약 이후는 `/combine` 링크와 함께 「공개 전에도 믹스 화면에서 시험해 볼 수 있어요」. 시험 믹스(1159)는 이미 구현돼 있어 새로 만들지 않는다. 보는 사람은 운영자 계정뿐이다.
- 카리나 가정(조사 사실에서 도출, 틀리면 알려 주세요): (1) 기기 폭 360·430 전환은 홈피드 카드 전용이고 다른 종류는 칸 폭에 맞춰 보인다. (2) 이미지가 없으면 서비스 폴백 아이콘(`MedalIcon`·`BookIcon`·`PackageIcon`)을 쓴다. (3) 색 견본 칩은 모든 종류에서 지금처럼 `OpsCardPreview` 안에서 보인다(`no-html.test.ts`가 인라인 `style` 파일을 5개로 고정하므로 새 컴포넌트에 `style={`을 쓰지 않는다). (4) 조건 JSON은 문장으로 바꾸지 않고, `condition_text`가 있으면 그것을 쓴다.
