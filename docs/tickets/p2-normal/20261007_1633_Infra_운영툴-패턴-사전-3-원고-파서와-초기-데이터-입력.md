## 배경 / 문제 정의

- 원천은 툴(DB)이다(PRD §10.1). 지금 테이블 3개는 비어 있어 에이전트 읽기 API(②)가 빈 목록을 돌려준다. 조합 뽑기(④)와 1504(루틴 재설정)는 사전에 패턴이 있어야 시작할 수 있다.
- 1503 시작 검토(2026-10-01) 결정: 원고 전부를 툴에 담는다(Q1). 초기 입력은 P14만 「쉬는 중」(Q2). 초기 데이터는 원고 파서로 시드 SQL을 만들고 개수가 어긋나면 중단하며,
  입력 뒤 원고 머리말을 `source_of_truth: db`로 바꾼다(가정 목록, 카리나 확정).
- 사전 점검(카리나, 2026-10-07, 원고 현재본): 패턴 18, 주 샘플 57 + 보조 장치 6 = 63(겹침 없음), 취향 신호 패턴별 40 + 공통 3 = 43, 공통 규칙 7. 손잡이 4종 72줄은 모두
  「닫은 값」을 한 번씩, 트라이브 18줄은 모두 「예시:」를 한 번씩 담는다. 「샘플별 구현」 번호 집합은 패턴마다 주+보조 번호와 같다. 부록 A 63행의 소속(「(장치)」는 보조)이 본문과 같고,
  걸침 번호는 모두 63개 안에 있다. 형식이 불규칙한 곳은 카드 모양 줄 셋(P04·P07·P10)뿐이다.

### 파서가 멈추는 조건 (SQL 파일을 쓰지 않고 0이 아닌 코드로 끝나며, 어긋난 패턴 번호와 항목을 출력한다)

1. 패턴이 18개가 아니거나 번호가 P01~P18 연속이 아니다.
2. 주+보조 샘플 번호가 63개가 아니거나 두 패턴에 겹친다.
3. 취향 신호가 43개(패턴별 + 공통)가 아니거나, 같은 (패턴, 이름)이 두 번 나온다(유일 인덱스 충돌 예방).
4. 공통 규칙이 7개가 아니거나 번호가 1~7 연속이 아니다.
5. 패턴마다 손잡이 5줄이 없거나, 4종 줄에 「닫은 값」이 정확히 한 번이 아니거나, 트라이브 줄에 「예시:」가 정확히 한 번이 아니다.
6. 「샘플별 구현」의 번호 집합이 그 패턴의 주+보조 번호 집합과 다르다.
7. 「## 2. 패턴 목록」 표의 주 샘플·보조 장치·걸침 번호가 본문 샘플 줄과 다르다.
8. 부록 A 63행의 소속 패턴(「P13(장치)」는 P13의 보조)이 본문과 다르거나, 걸침 번호가 63개 밖이다.
9. 카드 모양 값이 `CARD_SHAPES`(hero·poster·square·brief·list) 밖이다. 파서의 허용 목록과 `jam-web/src/lib/today/shape.ts`가 같은지 테스트가 확인한다.

### 생성 SQL (`212_ops_patterns_seed.sql`)

- 머리 주석: 생성 파일이고 손으로 고치지 않는다는 문장, 생성 명령, 원고 경로, 생성 때 개수, 「작성만 하고 실행하지 않았다(실행은 카리나, 사용자 승인)」, 공용 단일 DB 주의.
  생성 시각은 넣지 않는다(같은 원고면 같은 파일이 나와야 한다).
- `BEGIN;` … `COMMIT;` 한 트랜잭션. 세 테이블 모두 `INSERT … ON CONFLICT DO NOTHING`으로 쓴다(다시 돌려도 사람이 고친 행을 덮지 않는다).
- 문자열은 작은따옴표를 두 번 써서 이스케이프하고, JSONB는 `'…'::jsonb`, 메뉴는 `ARRAY[…]::text[]`로 쓴다. 넣는 순서는 패턴 → 취향 신호(패턴을 가리킨다) → 공통 규칙.
- 커밋 전 확인 블록(`DO $$ … $$`): 원고의 패턴 번호 18개가 모두 있고 그중 `origin = 'seed'`가 18행인지, 원고의 (패턴, 이름) 43쌍이 모두 있는지, `rule_no` 1~7이 모두 있는지 세어
  어긋나면 `RAISE EXCEPTION`으로 트랜잭션을 되돌린다.
- 파일 끝 주석: 검증 쿼리(세 테이블 행 수, P14 상태와 이유, 패턴별 샘플 수), 되돌림 SQL(210의 형식처럼 먼저 사람이 고친 흔적
  `updated_by IS NOT NULL`·`basis = 'confirmed'`를 세는 쿼리, 그다음 원고 43쌍 중 `basis = 'estimate'`인 취향 신호 삭제 → `origin = 'seed' AND updated_by IS NULL`인 패턴 삭제 →
  `rule_no` 1~7 중 `updated_by IS NULL`인 공통 규칙 삭제).
- 파서에 `--check` 옵션: 파일을 쓰지 않고 생성 결과가 커밋된 212와 같은지만 비교해 다르면 0이 아닌 코드로 끝난다.

## 구현 계획 (파일 단위, 카리나 2026-10-07)

규모: 파일 4개, 손으로 쓰는 줄 약 450 + 생성 SQL 약 400~600줄. `plan_only` 임계값(파일 5개 초과 또는 100줄 이상)을 넘으므로 이 계획으로 첫 호출부터 계획 반환을 면제한다.

1. `scripts/ops-patterns-seed.mjs`(신규, 약 280줄): 순수 함수 `parseOpsPatterns(markdown)`(원고 → `{ patterns, tasteSignals, commonRules }`), `validateOpsPatterns(parsed, markdown)`
   (위 멈춤 조건 1~9, 어긋난 목록 반환), `toSeedSql(parsed)`(SQL 문자열)을 내보내고, 직접 실행하면 원고를 읽어 검사 → 통과 시 212를 쓴다. `--check`는 비교만 한다.
   괄호 밖 「, 」 나누기는 함수 하나(`splitTopLevel`)로 메뉴·구현·카드 모양이 함께 쓴다. 머리 주석에 위 칸 매핑 표를 요약한다(규칙의 원천은 이 티켓과 PRD §10.1이 가리키는 이 파일 머리 주석).
2. `scripts/ops-patterns-seed.test.mjs`(신규, 약 170줄, node:test): ① 작은 원고 조각으로 칸 매핑(카드 모양 (가)(나)(다)와 「없음」, 손잡이 나누기, 걸침 구현 가져오기,
   취향 신호 번호 괄호 유지·「(추정)」 제거, P14 상태) ② 멈춤 조건 대표 사례(개수 어긋남, 「닫은 값」 두 번, 부록 소속 어긋남, 허용 밖 카드 모양) ③ 작은따옴표가 든 글의 SQL 이스케이프
   ④ 실제 원고를 읽으면 18·63·43·7이고 검사 통과 ⑤ 파서의 카드 모양 허용 목록이 `jam-web/src/lib/today/shape.ts`의 `CARD_SHAPES`와 같다(파일을 읽어 배열 글자를 비교).
3. `jam-web/supabase/migrations/212_ops_patterns_seed.sql`(신규, 생성 파일): `node scripts/ops-patterns-seed.mjs`로 만든다. 손으로 고치지 않는다.
4. `docs/specs/prd/ops-tool/PRD.md` §10.1 「툴이 생기기 전 원고」 항목에 한 줄: 초기 입력은 `scripts/ops-patterns-seed.mjs`가 원고를 읽어 `212_ops_patterns_seed.sql`을 만들고,
   칸 매핑은 그 파일 머리 주석에 있다.

**하지 않는 것**: SQL 실행, 원고 머리말 변경, PRD §13 E행 적용 기록, 1454·1503 티켓 갱신(모두 「후속 범위」, 카리나). `jam-web/src/` 코드 변경 없음.

## 완료 조건

### 구현 범위 (게이트 판정 대상)
- `node scripts/ops-patterns-seed.mjs`가 현재 원고로 0으로 끝나고 패턴 18·샘플 63·취향 신호 43·공통 규칙 7을 출력한다. `node scripts/ops-patterns-seed.mjs --check`가 커밋된 212와 같아 0으로 끝난다.
- 원고의 손잡이 한 줄에서 「닫은 값」을 지운 사본으로 돌리면 SQL을 쓰지 않고 그 패턴 번호를 출력하며 0이 아닌 코드로 끝난다(테스트로 확인).
- 212의 P07 `card_shapes`가 두 항목(`brief`의 note 「드랍·예보」, `hero`의 note는 조각 글 「힌트나 목격담을 기사로 쓸 때는」 뒤에 백틱 hero가 붙은 원문 그대로)이고, P06은 빈 배열이며, P14만 `paused`와
  이유 「필요한 기능 O12·O14 대기」를 가진다. 걸침 샘플(예: P01의 60)의 `impl`이 소속 패턴(P09)의 구현 글과 같다.
- 212는 한 트랜잭션이고 세 INSERT가 모두 `ON CONFLICT DO NOTHING`이며, 개수 확인 블록과 되돌림 SQL 주석이 있다.
- `scripts/verify.sh`가 통과한다(새 테스트 포함).

### 후속 범위 (담당: 카리나, 시점: 머지 뒤, 사용자 승인 필요)

### 주요 의사결정 / 핵심 메모
- 유형 `db`(시드 데이터 SQL 작성, 실행은 4단계). 칸 매핑 판단(카리나, 2026-10-07): 취향 신호 이름은 원고의 번호 괄호를 지우지 않는다(번호를 담을 칸이 없고 06 대조에 쓰인다).
  닫은 값은 「닫은 값은」 접두를 뗀다(S5가 「닫은 값」 이름표를 붙인다). 다시 돌려도 덮어쓰지 않는다(`ON CONFLICT DO NOTHING`, 사람이 S5에서 고친 값 보호).

- **실행 방식을 나눠서 했다(카리나, 2026-10-07).** 212는 70KB이고 패턴 구간만 52KB라, 도구 호출 하나에 옮겨 적으면 잘리거나 글자가 틀릴 위험이 컸다. 로컬에는 DB 직접 연결
  수단(psql·연결 문자열)이 없다. 그래서 파일 내용을 구간별 `execute_sql`(패턴 2행씩, 취향 신호와 공통 규칙은 한 번)로 넣었다. 파일의 `BEGIN`…`COMMIT` 한 트랜잭션은 쓰지 못했고,
  확인 블록 대신 칸 단위 해시 대조(확인 블록이 세는 것을 모두 포함한다)로 확인했다. 테이블이 비어 있었고 모든 INSERT가 `ON CONFLICT DO NOTHING`이라 중간 실패에도 다시 돌리면 된다.
  `apply_migration`을 쓰지 않아 DB의 마이그레이션 이력에는 212가 없다(시드 파일은 저장소에 있다).
- **실행 중 실수와 정정(카리나, 2026-10-07).** P09 INSERT를 파일 읽기와 같은 차례에 보내, 파일 원문을 보기 전에 추측한 내용으로 P09 한 행을 넣었다. 다음 차례에 원문과 달라진 것을

  영향이 없었고, 최종 해시 대조에서 P09도 원고와 같다. 이후 구간은 읽기와 실행을 다른 차례로 나눴다. 처리 규칙표에 한 줄을 더하자고 제안한다.
