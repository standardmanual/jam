# [API] 운영 묶음 제출 형식 b: 패턴 제안 항목의 내용 칸

> 상위: 20261001_2057(E1) 하위 b. 2026-10-07 사용자 결정으로 a(20261007_1745 패턴 번호·지점 카테고리)와 나눴다. 1503 ⑪(패턴 제안 승인 → 사전 입력)이 이 형식을 쓴다.
> **시점: 1503 ⑪보다 먼저, 2026-11-01 첫 월간 루틴 전.** 선행: a(같은 파일 `validate.ts`·`fields.ts`·`labels.ts`를 고치므로 a 머지 뒤에 시작한다).

## 핵심 요약

- 요구사항: 운영 묶음 항목 중 `kind = 'pattern_proposal'`의 `resource.pattern` 칸을 정의하고 검사한다. 칸은 패턴 사전 한 행과 같다(마이그레이션 210 `ops_patterns`):
  이름(`name`)·작동 원리(`principle`)·유저가 겪는 것(`user_experience`)·메뉴(`menus`, 문자열 배열)·샘플(`samples`, `[{ no, name, role, impl }]`, role은 `OPS_PATTERN_SAMPLE_ROLES`)·
  카드 모양(`card_shapes`, `[{ shape, note }]`, shape는 `CARD_SHAPES`)·손잡이(`knobs`, 5종: 조건·장소·시간·보상 `{ open, closed }`, 트라이브 `{ rule, example }`)·주의점(`pitfalls`).
  **필수는 이름·작동 원리·유저가 겪는 것·손잡이 5종**이다. 빠지거나 틀리면 항목 `format_errors`에 「경로: 사유」로 넣고 저장·승인은 막지 않는다.
  칸 읽기 함수는 `fields.ts` 한 곳에 두고(형식이 틀리면 모름), 직접 수정에서 이 내용 칸은 읽기 전용이다.
- 구현 계획: 착수할 때 파일 단위로 적는다(약 300줄 추정, 유형 `api`). 지도는 아래 「관련 파일」.
- 관련 파일(2026-10-07 Explore 조사):
  - `jam-web/src/lib/admin/opsInbox/validate.ts` `validateItem`(260-384) — a가 더한 `place_category` 검사 뒤에 `kind === 'pattern_proposal'`일 때 `resource.pattern` 검사를 붙인다
  - `jam-web/src/lib/admin/opsInbox/fields.ts` — `readOpsPatternProposal(item)`(객체 또는 모름). kind·resource를 읽는 함수는 지금 없다(`itemField(item, 'kind')` 사용)
  - `jam-web/src/lib/admin/opsInbox/labels.ts` `parseFormatErrorPath`(128-146) — `resource.pattern.*`의 마지막 키(`name` 등)가 다른 칸 이름표와 겹치지 않게 `excluded_items`처럼 특례 처리
  - `jam-web/src/lib/admin/opsInbox/edit.ts` `readEditableValues`(75-95)·`EDIT_SCALAR_PATHS`(23) — `resource.*`는 이미 고칠 수 없는 칸이다(`computeEditDiff`가 거절). 읽기 전용임을 테스트로 고정
  - `jam-web/src/components/admin/ops/OpsItemEditForm.tsx` `readOnlyRows`(81-100) — 패턴 제안 내용 줄을 「고칠 수 없는 것」에 보인다
  - 상수: `jam-web/src/lib/admin/opsPatterns/constants.ts`(`OPS_PATTERN_KNOB_KEYS` 33, `OPS_PATTERN_SAMPLE_ROLES` 37), `jam-web/src/lib/today/shape.ts` 18 `CARD_SHAPES`
  - 시드 파서가 같은 칸 모양을 만든다: `scripts/ops-patterns-seed.mjs` 머리 주석(칸 매핑)
  - 지금 `pattern_proposal`을 종류 단위로 빼는 곳(바꾸지 않음): `execute/precheck.ts:45`, `opsSchedule/weekView.ts:58`, `opsHome/homeView.ts:41`, `opsSignals/composition.ts:461`, `opsSignals/statusRules.ts:265-266`
  - 문서: `docs/specs/prd/ops-tool/PRD.md` §3.1(79행 「`resource` 검사하지 않음」에서 제안 내용을 뺀다, 98-109 「모름」 표), §7.3(596행 읽기 전용 목록), §10.1(제안 승인 흐름)

## 완료 조건

- 필수 칸이 빠지거나 손잡이 5종 모양이 틀리거나, 선택 칸의 형식(샘플 역할·카드 모양 값)이 틀린 패턴 제안이 항목 `format_errors`에 「경로: 사유」로 들어가고 저장·승인은 막지 않는다(테스트).
- `readOpsPatternProposal`이 형식이 맞으면 객체, 틀리면 모름을 돌려주고 「검증 통과 = 모름이 아님」 계약 테스트가 있다.
- 직접 수정에서 `resource.pattern` 경로는 「고칠 수 없는 칸」으로 거절되고, 편집 폼의 「고칠 수 없는 것」에 제안 내용이 보인다.
- PRD §3.1·§7.3이 갱신됐다. `scripts/verify.sh`가 통과한다.
