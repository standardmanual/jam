## 핵심 요약

- 요구사항: 운영 묶음 항목 중 `kind = 'pattern_proposal'`의 `resource.pattern` 칸을 정의하고 검사한다. 칸은 패턴 사전 한 행과 같다(마이그레이션 210 `ops_patterns`):
  이름(`name`)·작동 원리(`principle`)·유저가 겪는 것(`user_experience`)·메뉴(`menus`, 문자열 배열)·샘플(`samples`, `[{ no, name, role, impl }]`, role은 `OPS_PATTERN_SAMPLE_ROLES`)·
  카드 모양(`card_shapes`, `[{ shape, note }]`, shape는 `CARD_SHAPES`)·손잡이(`knobs`, 5종: 조건·장소·시간·보상 `{ open, closed }`, 트라이브 `{ rule, example }`)·주의점(`pitfalls`).
  **필수는 이름·작동 원리·유저가 겪는 것·손잡이 5종**이다. 빠지거나 틀리면 항목 `format_errors`에 「경로: 사유」로 넣고 저장·승인은 막지 않는다.
  칸 읽기 함수는 `fields.ts` 한 곳에 두고(형식이 틀리면 모름), 직접 수정에서 이 내용 칸은 읽기 전용이다.
- 구현 계획: 아래 「파일 단위 계획」(2026-10-08 착수, 11파일·약 520줄, 유형 `api`). 검사는 `validate.ts`의 새 함수 하나(`validateOpsPatternProposal`), 읽기는
  `fields.ts`의 `readOpsPatternProposal`이 그 검사를 그대로 써서 「검사 통과 = 모름 아님」을 보장한다.

## 배경 / 확인 사실 (2026-10-08, 카리나)

- DB에 `kind = 'pattern_proposal'` 항목은 0건이다(시험 묶음 포함). 옛 제출을 다시 검사하거나 고칠 일이 없다.
- 패턴 사전 테이블(210)에서 `name`·`principle`·`user_experience`는 NOT NULL이고, `menus`(TEXT[])·`samples`·`card_shapes`(배열)·`knobs`(객체)·`pitfalls`('')는 기본값이 있다.
  시드(212)의 샘플 `impl`은 빈 값이 0개, 카드 모양 `note`는 빈 값이 1개다.
- 제출 형식의 정본은 운영툴 PRD §3.1 한 곳이다(에이전트 정의·스킬 문서에 `pattern_proposal` 서술 없음).

## 설계 결정 (2026-10-08, 카리나 가정 목록 D1~D8을 사용자가 「이대로 진행」으로 확인)

- **D1 검사 위치**: `kind`가 `pattern_proposal`일 때만 `resource.pattern`을 본다. `resource`가 객체가 아니거나 `pattern`이 없으면 `items[n].resource.pattern: 필수 항목이 없어요(…)` 한 줄이다.
  `pattern`이 객체가 아니면 그 한 줄로 끝내고 안쪽은 보지 않는다. 다른 종류의 `resource`는 지금처럼 보지 않는다.
- **D2 필수 칸**: `name`·`principle`·`user_experience`는 비어 있지 않은 문자열. `knobs`는 객체이고 `condition`·`place`·`time`·`reward`는 각각 `{ open, closed }`, `tribe`는 `{ rule, example }`이며
  네 값 모두 비어 있지 않은 문자열이다. 빠진 손잡이와 빠진 값은 각각 한 줄(`…knobs.place.closed: 필수 항목이 없어요(…)`)이다.
- **D3 선택 칸**(없으면 사전 기본값으로 읽음): `menus`는 비어 있지 않은 문자열 배열(기본 `[]`). `samples`는 `{ no, name, role, impl }` 배열(기본 `[]`) — `no`는 1 이상의 정수,
  `name`은 비어 있지 않은 문자열, `role`은 `OPS_PATTERN_SAMPLE_ROLES`(main·aux·related), `impl`은 문자열(빈 값 허용). `card_shapes`는 `{ shape, note }` 배열(기본 `[]`) — `shape`는 `CARD_SHAPES`,
  `note`는 문자열(빈 값 허용, 시드 선례). `pitfalls`는 문자열(기본 `''`). 원소 오류는 `excluded_items`처럼 `samples[2].role` 경로로 원소마다 알린다.
- **D4 모르는 키**: `pattern`·`knobs`·손잡이·샘플·카드 모양 안의 정의되지 않은 키는 오류로 보지 않고 읽기 함수가 버린다(오타는 「필수 항목이 없어요」로 이미 드러난다).
- **D5 읽기 함수**: `readOpsPatternProposal(item)` — 종류가 `pattern_proposal`이 아니면 `null`, 검사(D1~D3)에 오류가 하나라도 있으면 「모름」, 아니면 `OpsPatternProposal` 객체다.
  칸 이름은 `OpsPatternRecord`와 같은 camelCase(`name`·`principle`·`userExperience`·`menus`·`samples[{ no, name, role, impl }]`·`cardShapes[{ shape, note }]`·`knobs`·`pitfalls`)이고,
  문자열은 앞뒤 공백을 뗀다(⑪이 사전에 그대로 넣을 값). 선택 칸이 없으면 D3 기본값이다. 계약 테스트: 검사 오류 0 ⇔ 「모름」 아님.
- **D6 오류 이름표**: `resource.pattern…` 경로는 뺀 항목처럼 특례로 「제안 패턴」을 앞에 붙이고 원고 용어로 부른다. 예: `제안 패턴`, `제안 패턴 이름`, `제안 패턴 작동 원리`,
  `제안 패턴 유저가 겪는 것`(항목의 「유저가 겪는 것」과 구분), `제안 패턴 쓰는 메뉴`, `제안 패턴 샘플 역할`, `제안 패턴 카드 모양`, `제안 패턴 손잡이(장소) 닫은 값`, `제안 패턴 트라이브 예시`, `제안 패턴 주의점`.
- **D7 직접 수정**: `resource.pattern…`은 지금도 `isEditablePath`가 거절한다(「고칠 수 없는 칸이에요.」). 동작은 바꾸지 않고 테스트로 고정한다. 편집 폼 「고칠 수 없는 것」에는 패턴 제안 항목에만
  `제안 패턴` 줄 하나를 더한다. 값은 패턴 이름이고, 읽을 수 없으면 「형식이 틀려 읽을 수 없어요」다(전체 내용은 S5·⑪ 몫).
- **D8 하지 않는 것**: 사전의 기존 이름과 겹치는지 보지 않는다. 패턴 제안 항목의 항목 칸 `pattern_no`·`user_experience` 규칙은 바꾸지 않는다(새 번호는 ⑪이 승인 때 붙인다). 저장·승인은 막지 않는다
  (형식 오류가 있는 항목은 기존 규칙대로 일괄 승인 체크가 기본으로 풀린다). DB 변경 없음.

- 필수 칸이 빠지거나 손잡이 5종 모양이 틀리거나, 선택 칸의 형식(샘플 역할·카드 모양 값)이 틀린 패턴 제안이 항목 `format_errors`에 「경로: 사유」로 들어가고 저장·승인은 막지 않는다(테스트).
