# [API] 운영 묶음 검증 오류 문장이 값의 길이를 자르지 않는다

> 출처: 2026-10-07 `/jam-ship` 5단계 사후 점검(티켓 20261007_1745 범위) 민지 모드 ②의 [보안/참고]와 모드 ③의 [정확성/주의]. 두 모드가 같은 곳을 짚었고, 높은 쪽(주의)을 따라 P2로 둔다. 자동 티켓화(`/jam-work` 3.2절).

## 핵심 요약

- 요구사항: `jam-web/src/lib/admin/opsInbox/validate.ts`에서 없는 지점 카테고리 오류 문장(255행 부근)은 `MAX_LISTED_VALUES`로 개수만 5개로 자르고, 값마다 `describeShort`가 아닌
  `describeValue`를 쓴다. 그래서 긴 slug가 응답의 `details`와 `ops_bundles.format_errors`·항목 `format_errors`에 거의 그대로 되풀이된다. 같은 파일의 주석(「사유에 넣는 값은 길이를 자른다」)과
  어긋난다. 같은 패턴이 `validateExposureTags`(186행 부근)에도 있다. 두 곳 모두 값마다 길이를 자르게 고친다.
- 구현 계획: 두 곳의 `describeValue`를 `describeShort`로 바꾸고, 긴 값이 잘리는지 단정하는 테스트를 더한다. 다른 오류 문장에서 같은 패턴을 쓰는 곳이 있는지 함께 찾는다.
- 관련 파일: `jam-web/src/lib/admin/opsInbox/validate.ts` 255행·186행 부근, `jam-web/src/lib/admin/opsInbox/__tests__/validate.test.ts`.

## 배경 / 문제 정의

- 호출자는 인증된 제출 토큰과 관리자뿐이고 본문이 1MB로 막혀 있어 증폭은 2~3배로 제한된다. 보안상 악용 가능성은 낮다(모드 ② 참고).
- 같은 파일의 다른 오류는 `describeShort`(60자)로 자르는데 여기만 자르지 않고, 긴 slug 경계값 테스트도 없다(모드 ③ 주의).

## 완료 조건

- 두 오류 문장이 값마다 길이를 잘라 담는다. 테스트가 있다. `scripts/verify.sh`가 통과한다.
