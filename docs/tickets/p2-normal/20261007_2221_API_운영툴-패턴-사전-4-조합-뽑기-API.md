# [API] 운영툴 패턴 사전 ④ 조합 뽑기 API — 최근에 덜 쓴 패턴·트라이브·지점 카테고리

> 상위: 20260930_1503 하위 ④(선행 E1-a 20261007_1745 CLOSED, ③ 20261007_1633 CLOSED). 07 블루프린트 111행 「조합 뽑기」.

## 핵심 요약

- 요구사항: `GET /api/admin/ops-patterns/draw`를 만든다. 에이전트(윤진)가 다음 주 운영 묶음을 짤 때 최근 4주에 덜 쓴 **패턴·트라이브·지점 카테고리**를 각각 「덜 쓴 순」으로
  받는다. 새로움을 모델의 창의력에 맡기지 않기 위해서다. 무작위가 없어 같은 데이터·같은 기준 시각이면 결과가 같다. 읽기 토큰 GET과 관리자 세션 모두 허용, 관리자 ID 비노출.
- 구현 계획: 아래 「파일 단위 계획」. 계산은 순수 함수 하나(`rankOpsDraw`)에 모으고, 읽기는 기존 함수(`listOpsPatterns`·`loadPoiCategorySlugs`·`fields.ts` 읽기 함수)를 다시 쓴다.
- 관련 파일: `jam-web/src/lib/admin/opsPatterns/read.ts`(`listOpsPatterns` 175~180행, `comparePatternNo` 160행, 고정 오류 문장 24행),

  `jam-web/src/lib/admin/opsInbox/validationContext.ts`(`loadPoiCategorySlugs` 16~20행), `jam-web/src/lib/admin/opsInbox/constants.ts`(`OPS_ITEM_STATUSES` 46~57행),
  `jam-web/src/lib/admin/opsInbox/balance/evaluate.ts`(`APPROVED_STATUSES` 47행), `jam-web/src/lib/admin/opsDecisions/read.ts`(시험 묶음 제외 inner join 307~319행, `fetchAllRows`),

## 배경 / 문제 정의

- 1503 시작 검토(2026-10-01) 가정: 최근 4주, 승인 이후 상태의 실제 항목만 센다(반려·취소·실패·시험 제외), 사용 횟수 오름차순·동률은 더 오래 안 쓴 쪽, 무작위 아님,
  `limit` 기본 5, 패턴은 「사용 중」만, 지점 카테고리는 `knobs.place_category`만 읽는다. 트라이브는 「캐논 10종 전체」였으나 아래 D6으로 바뀌었다.
- 2026-10-07 조사 사실: `ops_bundle_items`에는 승인 시각 칸과 트라이브 열이 없다(트라이브는 `original`/`edited`의 `tribe_id`). 승인 이후 상태 목록은 `evaluate.ts` 47행에만
  지역 상수로 있다. `tribes`는 10행이고 그중 `is_active`가 켜진 것은 3행이다. 지점 카테고리는 18개이고 그중 `delete`(삭제대상)·`unassigned`(미분류(거부됨))가 있다.
  지금 시험이 아니면서 승인 이후 상태인 항목은 0건이라 첫 응답은 모두 0회다.

## 설계 결정 (2026-10-07, D6은 사용자 결정, 나머지는 카리나가 가정 목록으로 보이고 진행)

- **D1 사용 시각**: 항목의 `starts_at`(공개 시각), 없으면 묶음의 `received_at`. 「기준 시각 − 28일」 이후면 센다. 앞날로 예약된 항목도 센다(이미 예약된 패턴을 또 추천하지 않도록).
- **D2 마지막 사용(`lastUsedAt`)**: 기간과 무관하게 승인 이후 상태 전체 기록의 최댓값. 4주 안 0회끼리도 「더 오래 안 쓴 쪽」을 가른다.
- **D3 응답 모양**: `patterns`·`tribes`·`placeCategories` 세 목록을 따로 두고 각각 `limit`개로 자른다. 셋의 짝은 에이전트가 TRIBES.md 매핑으로 정한다.
- **D4 한 번도 안 쓴 것**: `lastUsedAt: null`, 같은 횟수 안에서 맨 앞.
- **D5 마지막 정렬 키**: 패턴은 `comparePatternNo`, 트라이브는 `sort_order` 다음 `id`, 카테고리는 slug 코드 포인트 순(지역 설정 영향 없음).
- **D6 트라이브 범위 (사용자 결정 2026-10-07 「활성만 추천」)**: `is_active = true`인 트라이브만 뽑기 대상이고 비활성은 응답에 싣지 않는다. 비활성 트라이브는 온보딩과
  어드민 배지·아이템북 만들기에서 고를 수 없어 추천해도 실제 배지를 만들 수 없기 때문이다. 트라이브를 켜면 자동으로 대상에 들어온다. 1503 가정 「캐논 10종 전체」를 대체한다.
- **D7 카테고리 제외**: `delete`·`unassigned`는 뺀다(늘 0회라 영구히 상위에 뜨므로). 상수로 둔다.
- **D8 세는 단위**: 항목 1건 = 1회. 한 항목 안에서 겹친 slug는 1회. `pattern_proposal` 종류 항목은 세지 않는다. 형식이 틀린 값(「모름」)과 사전·목록에 없는 값은 세지 않는다.
  칸은 `fields.ts` 읽기 함수로 읽어 수정본(`edited`)이 원본보다 우선한다.
- **D9 상태 상수**: `opsInbox/constants.ts`에 `OPS_POST_APPROVAL_ITEM_STATUSES`(approved·preparing·scheduled·live·ended)를 두고 `evaluate.ts` 47행이 그것을 가져다 쓴다(두 곳 어긋남 방지).
- **D10 시험 제외**: ⑤ 선례대로 `ops_bundles!inner(...)` + `.eq('ops_bundles.is_sample', false)`, 순수 함수에서도 `is_sample`을 한 번 더 거른다(⑤의 실제 DB 조인 필터 확인이 WAITING이라 이중으로).
- **D11 쿼리**: `limit`은 1~50 정수, 기본 5. 형식이 틀리면 400이고 아무것도 읽지 않는다. 기준 시각을 바꾸는 쿼리는 두지 않는다(재현성은 순수 함수가 `now`를 인자로 받아 테스트로 보장).

## 완료 조건

1. 읽기 토큰만으로도, 관리자 세션으로도 200이다. 토큰이 틀리거나 없으면 403이고 어느 테이블도 읽지 않는다. 라우트는 `GET`만 export한다.
2. 시험 묶음 항목과 반려·취소·실패·도착·검토중 항목은 `uses`에 들어가지 않는다. 승인됨·준비중·예약됨·게재중·종료만 센다.
3. 사용 시각(`starts_at`, 없으면 `received_at`)이 기준 시각 − 28일보다 앞이면 `uses`에서 빠지고 `lastUsedAt`에만 반영된다. 앞날 예약분은 센다.
4. 정렬은 `uses` 오름차순 → `lastUsedAt` 오래된 순(null이 맨 앞) → D5 키 순이다. 같은 행과 같은 `now`로 두 번 부르면 결과가 깊은 비교로 같다.
5. 패턴은 사용 중만 나온다(쉬는 중·보관 없음). 트라이브는 활성만 나온다(비활성 없음). 카테고리에는 `delete`·`unassigned`가 없다.
6. `limit`이 없으면 목록마다 5개다. 0·51·`abc`·`2.5`면 400이고 아무것도 읽지 않는다.
7. 칸은 `fields.ts`로 읽어 수정본이 원본보다 우선한다. `P-07`처럼 형식이 틀린 패턴 번호와 문자열 배열이 아닌 `place_category`는 세지 않는다. 한 항목 안에서 겹친 slug는 1회다.
8. 응답 본문 어디에도 `updated_by`·`actor`·`author`와 그 값이 없다. 조회가 실패하면 고정 문장 500이고 원문은 싣지 않는다.
9. `evaluate.ts`의 밸런스 점검 동작은 바뀌지 않는다(기존 테스트 통과). PRD §11.14가 생기고 `scripts/verify.sh`가 통과한다.
- (staging 머지 뒤 카리나 확인) `GET /api/admin/ops-patterns/draw`가 `[patternNo]` 라우트에 가로채이지 않고 200이다.

- 머지 전 오염 검사 실패: 아현 작업 중 다른 세션이 staging에 구상 문서 커밋 1개(3e3ba8013)를 올렸다. 리뷰 브랜치에는 이 티켓 커밋 3개만 있고 겹치는 파일 0개, 시험 머지 충돌 없음 → 규칙표(티켓 20261001_0633)대로 경위를 알리고 사용자 승인으로 머지했다.
