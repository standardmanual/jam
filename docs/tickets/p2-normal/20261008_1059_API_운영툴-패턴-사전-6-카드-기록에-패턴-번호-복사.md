# [API] 운영툴 패턴 사전 ⑥ 카드 노출·열람 기록에 패턴 번호를 복사하고 지표에 패턴별 집계를 더한다

> 상위: 20260930_1503 하위 ⑥(선행 ① 20261001_2056 CLOSED, 마이그레이션 211 적용 2026-10-01). 1453 사용자 결정 4 「이벤트마다 모양·패턴 복사 저장」의 패턴 열을 채운다.

## 핵심 요약

- 요구사항: 유저가 홈피드 카드를 보거나 열 때 남는 기록(`today_card_events`)에 그 카드의 패턴 번호(`today_cards.pattern_no`)를 복사하고, 어드민 카드 지표
  `GET /api/admin/today/metrics` 응답에 패턴별 노출·열람·열람률(`byPattern`)을 더한다. 기존 응답 항목(`range`·`types`·`byShape`)은 그대로 둔다. DB 변경 없음.
- 구현 계획: 아래 「파일 단위 계획」. 그려진 모양(`card_shape`, 티켓 20261001_1431)을 복사·집계하는 방식을 그대로 따른다. 카드 조회는 지금처럼 한 번이다.
- 관련 파일: `jam-web/src/lib/today/events.ts`(머리 주석 1~9행, `ExposableCard` 58~65행, `assertCardExposable` 76~98행의 select 80행·반환 97행,
  `recordTodayCardEvent` 189~205행의 insert 195~201행, `TodayCardEventAggregateRow` 208~214행, `aggregateTodayCardEvents` 226~256행의 select 233행·키 241행·복원 247~255행),
  `jam-web/src/app/api/admin/today/metrics/route.ts`(머리 주석 27~34행, 버킷 50~62행, 정렬·응답 64~76행), `jam-web/src/lib/admin/opsPatterns/read.ts`(`comparePatternNo` 160행),
  `jam-web/src/lib/admin/opsDecisions/read.ts`(`byPattern` 정렬 선례 296~301행), 테스트 `jam-web/src/lib/today/__tests__/events.test.ts`(가짜 클라이언트 19~95행, 집계 183행~),
  `jam-web/src/app/api/admin/today/metrics/__tests__/route.test.ts`(byShape 87~121행), `jam-web/src/app/api/today/events/__tests__/route.test.ts`(insert 비교 118~136행).

## 배경 / 문제 정의

- 1453 사용자 결정 4: 기존 계측과 패턴별 결과는 「이벤트마다 모양·패턴을 복사 저장」하는 방식으로 잇는다. 모양 열은 먼저 채웠고(20261001_1431) 패턴 열은 1503 뒤에 채운다.
  집계 API는 옛 응답 모양을 유지하고 항목을 더해 카즈하 브리핑이 깨지지 않게 한다.
- 1503 완료 조건: 카드 노출·열람 이벤트의 「패턴」 열이 패턴 사전의 패턴을 기록하고, 패턴별 결과에서 카드 노출·열람을 볼 수 있다.
- 2026-10-08 확인 사실(카리나, 코드·읽기 전용 SQL):
  - 마이그레이션 211의 칸 2개(`today_cards.pattern_no`·`today_card_events.pattern_no`)가 DB에 있다. ⑥의 머지 조건 「211 적용 뒤 머지」는 충족됐다.
  - 운영 항목으로 카드를 만들 때 `registerInput.ts` 405~443행이 패턴 번호 형식(`^P[0-9]{2,}$`)이 맞는 값만 카드의 `pattern_no`에 넣는다(1500, G11). 어드민 카드 폼에는 패턴 칸이 없다.
  - 패턴 번호가 붙은 카드 0장, 패턴 번호가 붙은 이벤트 0건, 전체 이벤트 492건(최근 7일 87건)이다.
  - 시험 묶음은 실제 카드를 만들지 않는다(`execute/run.ts` 399행이 `created_resource`에 `{ sample: true }`만 남김). 그래서 시험 묶음에서 나온 카드 이벤트는 생길 수 없다.
  - `today_card_events`를 읽는 다른 코드인 `admin/weeklyCardMetrics.ts`(`card_id, event, occurred_at`만 읽음)와 `registerChecks/references.ts`는 새 칸과 무관하다.

## 설계 결정 (2026-10-08, D4는 사용자 결정, 나머지는 카리나 가정 목록으로 보이고 이의 없이 진행)

- **D1 복사 값**: 카드 행의 `pattern_no`를 그대로 복사한다. 비어 있으면 `null`이다. 기록 경로에서 형식을 다시 검사하지 않는다(카드에 넣을 때 이미 거르고, DB에 CHECK가 없다). `card_shape` 선례와 같다.
- **D2 조회 한 번**: `assertCardExposable`이 이미 하는 카드 조회 칸에 `pattern_no`를 더하고 `ExposableCard`에 실어 `recordTodayCardEvent`로 넘긴다. 카드를 다시 조회하지 않는다.
- **D3 옛 기록 채우기 없음**: 패턴이 붙은 카드가 0장이라 채울 옛 기록이 없다. 직접 만든 카드와 옛 기록은 계속 `null`이다(211의 「백필 없음」).
- **D4 응답 모양 (사용자 결정 2026-10-08 「결정 기록 API와 같게」)**: `byPattern: [{ patternNo, impression, click, followup, clickThroughRate }]`를 더한다. `patternNo`가 `null`인 줄 하나에 패턴 없는 카드(직접 만든 카드·옛 기록)를 묶는다.
  키 이름과 `null` 처리는 결정 기록 API의 `byPattern`(운영툴 PRD §11.10)과 같게 해서, 에이전트가 결정 결과와 카드 반응을 같은 패턴 번호로 맞대어 볼 수 있게 한다.
  같은 응답의 `byShape`가 쓰는 `'unknown'` 문자열 방식은 따르지 않는다. `types`·`byShape`는 이름·값·순서를 바꾸지 않는다.
- **D5 정렬**: `comparePatternNo`(P09 < P10 < P100) 순서이고, `null` 줄은 맨 끝이다(결정 기록 API와 같다).
- **D6 시험 묶음**: 거를 조건을 따로 두지 않는다(위 확인 사실 — 시험 묶음은 실제 카드가 없다).
- **D7 이름·사전 확인 없음**: 응답에 패턴 이름을 싣지 않고 패턴 사전을 조회하지 않는다. 보관된 패턴의 번호도 기록된 그대로 센다(이름은 에이전트가 패턴 사전 API로 읽는다).
- **D8 집계 키**: `aggregateTodayCardEvents`가 유형 × 모양 × 패턴 × 이벤트로 센다. 행에 `patternNo`를 더할 뿐 기존 칸은 그대로라, 유형별·모양별 합계는 지금과 같다.
