# [Admin] 운영툴 패턴 사전 ⑧ 「획득 경로가 막힌 컬렉션」 신호를 계산한다

> 상위: 20260930_1503 하위 ⑧(선행 ⑦a 20261004_1640·⑦b 20261004_1641 CLOSED, 운영 홈 신호 자리 20261001_1156 CLOSED). 07 4.2 신호 표 「획득 경로가 막힌 컬렉션」(참고).

## 핵심 요약

- 요구사항: 운영 신호 13종 가운데 지금 「아직 확인하지 않아요」(`not_built`)로 자리만 있는 「획득 경로가 막힌 컬렉션」을 계산한다. **기간이 끝나지 않은(진행 중인) 컬렉션**에
  얻을 길(드랍·믹스·미션)이 모두 닫힌 아이템(`blocked`)이 하나라도 있으면 컬렉션 하나가 결과 한 건이다(수준 참고). 얻을 길 판정은 ⑦의 `computeItemPaths`를 그대로 쓴다. DB 변경 없음.
- 구현 계획: 아래 「파일 단위 계획」. 서버 전용인 얻을 길 읽기·계산은 `opsSignals/load.ts`에서 하고, 순수 계산(`compute.ts`)에는 막힌 컬렉션 목록만 넘긴다(`compute.ts`는 클라이언트 테스트도 가져다 쓰므로
  서버 전용 모듈을 끌어오지 않는다).
- 관련 파일: `jam-web/src/lib/admin/opsSignals/compute.ts`(머리 주석 14~16행, `ComputeOpsSignalsInput` 51~61행, 자리 170~172행), `jam-web/src/lib/admin/opsSignals/load.ts`(`OpsSignalSource` 65행,
  `loadOpsSignals` 434~477행: `settle` 441~449행, `Promise.all` 460~465행, 입력 475행), `jam-web/src/lib/admin/opsSignals/statusRules.ts`(결과 선례 `evaluateEmptyCollections` 230~255행),
  `jam-web/src/lib/admin/opsSignals/catalog.ts`(`OpsSignalResult` 88~104행, `makeSignalResult` 131행, `sortSignalResults` 146행), `jam-web/src/lib/admin/itemPaths/load.ts`(`loadItemPathInputs` 60행,
  읽는 칸 41~45행), `jam-web/src/lib/admin/itemPaths/compute.ts`(`computeItemPaths` 137행, 서버 전용 모듈을 값으로 가져옴), `jam-web/src/lib/admin/itemPaths/types.ts`(`CollectionPathSummary` 106~113행,
  `ItemPathCollectionInput` 11~17행). 테스트: `opsSignals/__tests__/compute.test.ts`(187~191행 기대 상태), `opsSignals/__tests__/load.test.ts`(641행), `components/admin/ops/__tests__/home.test.tsx`(455~462행).

## 배경 / 확인 사실 (2026-10-08, 카리나)

- 07 4.2·운영툴 PRD §5: 「획득 경로가 막힌 컬렉션 — 기간 한정 운영이 끝나 얻을 길이 없는 아이템이 있다(06 6.3), 참고」. 06은 「기간 한정 운영의 보상이 컬렉션 완성을 막는지」를 운영자가 보고
  복각이나 다른 길을 판단하게 한다고 적는다.
- 얻을 길 계산(⑦, PRD §11.11)은 공개된 컬렉션 전부(기간이 끝난 것 포함)를 읽고, 기간이 끝난 컬렉션은 드랍 사유 `collection_ended`로 닫혀 아이템이 대부분 `blocked`가 된다.
  「드랍 제외」(`drop_excluded`)는 막힘이 아니다(운영자가 일부러 뺀 것).
- 2026-10-08 실제 DB로 `loadItemPathInputs`+`computeItemPaths`를 읽기 전용 실행: 공개 컬렉션 30개, 기간이 끝난 것 0개, 드랍 제외 0개, 막힌 아이템 0개. 지금은 신호가 「안 뜸」이다.
- `loadOpsSignals`를 부르는 곳은 운영 홈(`app/admin/_home/sections.tsx`), 일정표(`opsSchedule/load.ts`), 매시 중단 점검(`opsSignals/stopAlert.ts`) 셋이다. 이 신호는 참고 수준이라 매시 점검의 슬랙 알림 대상이 아니다.

## 설계 결정 (2026-10-08, D1은 사용자 결정, 나머지는 카리나 가정)

- **D1 범위 (사용자 결정 2026-10-08 「진행 중인 컬렉션만」)**: 기간이 끝나지 않은 컬렉션(`valid_until`이 없거나 기준 시각보다 뒤)만 센다. 기간이 끝난 컬렉션은 모든 아이템이 막히는 것이 당연해서
  신호가 영구히 쌓이므로 세지 않는다(끝난 컬렉션의 막힘은 S6 ⑬ 화면에서 본다). 컬렉션 공개 판정·아이템 상태는 ⑦ 결과를 그대로 쓴다.
- **D2 결과 단위와 문장**: 컬렉션 하나가 한 건이다. 문장은 `컬렉션 「<이름>」의 아이템 <막힘 수>개는 지금 얻을 길이 없어요(전체 <전체 수>개).` — 이름은 `item_books.name`, 수는 ⑦의
  `blocked`·`total`. `date`·`bundleId`·`itemId`·`onsetAt`은 `null`, `isSample`은 `false`(실제 컬렉션이라 시험 묶음 스위치와 무관). 순서는 이름(`localeCompare('ko')`) 다음 컬렉션 ID.
- **D3 읽기**: `load.ts`에 새 원천 `item_paths`를 둔다. 기존 네 원천과 같은 `Promise.all`에서 `loadItemPathInputs(supabase, now)` → `computeItemPaths({ ...inputs, now })` → D1로 거른 막힌 컬렉션이
  있을 때만 그 ID들의 `item_books.id, name`을 한 번 더 읽는다. 하나라도 실패하면 `settle`이 `sourceErrors.item_paths`에 담고 이 신호만 「확인하지 못했어요」(`load_failed`)다(다른 신호는 계산).
- **D4 계산 입력**: `ComputeOpsSignalsInput`에 `blockedCollections?: readonly BlockedCollectionInput[] | null`(`{ collectionId, name, blocked, total }`)을 더한다. `null`은 읽지 못함(`load_failed`),
  넘기지 않음(`undefined`)은 빈 목록으로 계산한다(「안 뜸」). 판정 함수 `evaluateBlockedCollections`는 순수 함수다.
- **D5 서버 전용 경계**: `itemPaths/compute.ts`·`itemPaths/load.ts`는 `opsSignals/load.ts`(서버 전용)만 가져온다. `opsSignals/compute.ts`·`statusRules.ts`는 그 둘을 값으로 가져오지 않는다.
- **D6 하지 않는 것**: 「그 때문에 완성하지 못하는 유저 수」(06 6.3)는 ⑬ 화면 몫이다. 결과에 컬렉션 링크 칸을 더하지 않는다(`OpsSignalResult` 모양 유지). 밸런스 경고(1459)는 그대로 `not_built`다.
  운영 홈 화면 코드는 바꾸지 않는다(1502가 만든 자리가 결과를 그대로 그린다).

## 파일 단위 계획 (아현 몫 8파일·약 300줄 — 계획 반환 면제 근거)

1. 고침 `jam-web/src/lib/admin/opsSignals/statusRules.ts`(약 +30줄): 타입 `BlockedCollectionInput`과 순수 함수 `evaluateBlockedCollections(list): OpsSignalResult[]`(D2 문장·정렬, `makeSignalResult`).
   파일 머리 주석이 신호 목록을 적고 있으면 한 줄.
2. 고침 `jam-web/src/lib/admin/opsSignals/compute.ts`(약 +15줄): 머리 주석 14~16행(2종 → 밸런스 경고 1종만 자리, 획득 경로는 계산), `ComputeOpsSignalsInput`에 `blockedCollections`(D4 주석),
   172행을 `input.blockedCollections === null ? unchecked('load_failed') : decided(evaluateBlockedCollections(input.blockedCollections ?? []))`로.
3. 고침 `jam-web/src/lib/admin/opsSignals/load.ts`(약 +45줄): `OpsSignalSource`에 `'item_paths'`, 새 함수 `loadBlockedCollections(supabase, now)`(D1·D3, `loadItemPathInputs`·`computeItemPaths` 사용,
   이름 조회는 막힌 것이 있을 때만), `Promise.all`에 `settle('item_paths', …)` 추가, 입력에 `blockedCollections`. 진입점 주석의 「신호 13종」 설명에 원천 한 줄.
4. 고침 `jam-web/src/lib/admin/opsSignals/__tests__/compute.test.ts`(약 +60줄): 191행 기대 상태를 계산 결과로 바꾸고, `evaluateBlockedCollections` 문장·정렬·빈 목록, `null` → `load_failed`, 넘기지 않음 → 안 뜸.
5. 고침 `jam-web/src/lib/admin/opsSignals/__tests__/load.test.ts`(약 +70줄): 641행 기대값 갱신. `@/lib/admin/itemPaths/load`를 모킹해 진행 중 컬렉션만 세는지(끝난 컬렉션·드랍 제외는 안 셈),
   이름 조회가 막힌 것이 있을 때만 일어나는지, 얻을 길 읽기 실패 → 이 신호만 `load_failed`이고 `sourceErrors.item_paths`가 채워지는지.
6. 고침 `jam-web/src/components/admin/ops/__tests__/home.test.tsx`(약 ±6줄): 455~462행 「확인하지 않은 신호 3종」을 2종(밸런스 경고·루틴 실패)으로. 같은 파일에서 개수에 기대는 다른 기대가 있으면 맞춘다.
7. 고침 `docs/specs/prd/ops-tool/PRD.md`(약 +6줄): §5 신호 표 「획득 경로가 막힌 컬렉션」 행에 「진행 중인 컬렉션만(구현됨: 티켓 20261008_1301)」, 신호 계산 문단의 읽는 원천(얻을 길)과
   「확인 안 함」 사유 문장(186행)에서 이 신호를 빼고, 판정 규칙 표 211행 「밸런스 경고 · 획득 경로가 막힌 컬렉션」을 둘로 나눠 이 신호의 규칙(D1·D2·D3)을 적는다. §11.11에 「신호(§5)도 같은 계산을 쓴다」 한 줄.
8. (카리나, 아현은 고치지 않음) 1503 하위 표 ⑧ 행과 완료 기록은 카리나가 쓴다. 운영 홈은 화면 코드 변경이 없어 로컬 실렌더로 신호가 「안 뜸」으로 바뀐 것만 머지 뒤에 본다.

## 완료 조건

- 진행 중인 컬렉션에 막힌 아이템이 있으면 컬렉션마다 결과 한 건(D2 문장)이 뜨고, 기간이 끝난 컬렉션과 드랍 제외 아이템은 세지 않는다(테스트).
- 얻을 길 읽기가 실패하면 이 신호만 「확인하지 못했어요」이고 다른 신호는 계산된다(테스트).
- 신호 상태가 더 이상 `not_built`가 아니고, 운영 홈의 「아직 확인하지 않아요」는 밸런스 경고·루틴 실패 2종이다(테스트).
- `opsSignals/compute.ts`가 서버 전용 모듈을 가져오지 않는다. `scripts/verify.sh` 통과. DB 변경 없음. PRD §5·§11.11이 구현과 맞는다.
