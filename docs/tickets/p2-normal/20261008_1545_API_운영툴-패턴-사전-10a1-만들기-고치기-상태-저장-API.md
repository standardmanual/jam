## 설계 결정 (2026-10-08, 채원 판정 승인 + 사용자 확인 + 카리나 가정)

- **D1 입력 모양(카멜, `OpsPatternRecord` 칸 이름)**: `{ name, principle, userExperience, menus: string[], samples: [{ no, name, role, impl }], cardShapes: [{ shape, note }], knobs: { condition|place|time|reward: { open, closed }, tribe: { rule, example } }, pitfalls }`.
  타입 이름 `OpsPatternInput`. `OpsPatternProposal`과 같은 모양이라 ⑪이 변환 없이 넘긴다(타입 호환을 테스트로 고정).
- **D2 검사(`validateOpsPatternInput`, 칸별 `fieldErrors`)**: 필수 3칸(이름·작동 원리·유저가 겪는 것, 앞뒤 공백 뗀 뒤 비면 오류). 길이 상한(사용자 확인 ②): 이름 60자, 작동 원리·유저가 겪는 것·주의점·손잡이 칸 각 2,000자,
  메뉴 10개(각 비어 있지 않은 문자열, 30자 — 카리나 가정), 샘플 20개(번호 양의 정수·중복 없음, 이름 필수, 역할 3값, 구현은 선택 문자열), 카드 모양 `CARD_SHAPES`만(메모 선택, 200자 — 카리나 가정), 손잡이 칸은 **선택**(빈 문자열 허용, 문자열이 아니면 오류).
  `fieldErrors` 키는 칸 경로(`name`·`samples.2.role`·`knobs.place.open`)이고 값은 화면에 그대로 보일 한국어 문장이다. 알 수 없는 키는 버린다. 저장 값은 앞뒤 공백을 뗀다.
  지금 시드 P01~P18이 모두 검사를 통과한다(테스트로 고정 — 시드 SQL을 읽거나 원고 파서 출력을 쓴다).
- **D3 만들기(`createOpsPattern(service, input, { actor, origin, originItemId })`)**: 서버가 사전의 가장 큰 번호 + 1(두 자리 이상, P19~)을 정해 `insert`한다. 상태 `active`, 출처 기본 `manual`(⑪은 `origin: 'proposal'`·`originItemId`).
  PK 충돌(23505, `pattern_no`)이면 409 「그사이 다른 패턴이 만들어졌어요. 다시 저장해 주세요」(재시도하지 않는다). `origin_item_id` 유일 충돌이면 409 「이 제안으로 이미 만든 패턴이 있어요」. 성공하면 201 `{ pattern }`(`toPatternRecord`, `updated_by` 없음).
- **D4 고치기(`updateOpsPattern(service, patternNo, input, { actor, expectedUpdatedAt })`)**: 내용 칸 전체를 받아 덮어쓴다(부분 수정 아님). 번호·출처·상태·쉬는 이유는 이 경로로 못 바꾼다. 조건부 update(`eq('updated_at', expectedUpdatedAt)`), 0행이면 행 유무를 다시 읽어 404/409 구분.
  409 문장 「그사이 다른 곳에서 이 패턴을 고쳤어요. 최신 내용을 불러와 주세요」. `updated_at`·`updated_by` 갱신. 응답 200 `{ pattern, changed }`(값이 같으면 `changed: false`, 그래도 시각은 갱신하지 않는다 — 카리나 가정, `balance/save.ts`와 같게).
- **D5 상태 바꾸기(`changeOpsPatternStatus(service, patternNo, { status, pauseReason }, { actor, expectedUpdatedAt })`)**: 모든 전환 허용(승인 12). 쉬는 중은 이유 필수(공백 뗀 뒤 1~200자), 쉬는 중이 아닌 상태로 바꾸면 쉬는 이유를 지운다(사용자 확인 ①).
  같은 상태로 바꾸는 요청은 쉬는 중의 이유 변경만 허용, 그 밖에는 `changed: false`. 409 문장 「그사이 상태가 바뀌었어요」.
- **D6 PATCH 본문 구분(사용자 확인 ③)**: 본문에 `status`가 있으면 상태 바꾸기, 없으면 고치기. 둘을 섞으면(상태 + 내용 칸) 400 「상태 바꾸기와 내용 고치기는 따로 저장해 주세요」. `expectedUpdatedAt`은 둘 다 필수(ISO 문자열, 없거나 틀리면 400).
- **D7 라우트**: `POST`는 `route.ts`, `PATCH`는 `[patternNo]/route.ts`. 둘 다 `getAdminUser()`가 없으면 403(토큰을 보지 않는다), 본문 상한 64KB(카리나 가정, 2,000자 칸 다수), JSON 아님·객체 아님 400, 번호 형식이 틀리면 404(GET과 같은 처리).
  응답에 관리자 ID를 싣지 않는다. 오류 로그에 본문 원문을 남기지 않는다.
- **D8 문서**: PRD §11.6에서 「쓰기 메서드는 두지 않는다」를 지우고 쓰기 두 경로(세션 전용, 409, 응답 모양)를 적는다. §10.1에 「상태 전환은 모두 허용, 쉬는 중이 아니게 되면 이유를 지운다」 한 줄. §11 표에 「패턴 만들기·고치기·상태 | 운영자(S5) → 툴 | 관리자 세션만」 행.
- **D9 하지 않는 것**: 화면(⑩a-2), 취향 신호·공통 규칙 쓰기(⑩b), 제안 승인 연결(⑪ — 함수만 준비), 삭제(번호는 지우지 않는다, PRD §10.1), DB 변경, 이전 내용 이력 보관(「이전 내용은 남지 않아요」, 승인 13).

- 머지 전 오염 검사 실패: 브랜치 고유 커밋은 이 티켓 3개뿐, 분기 뒤 다른 세션 구상 문서 커밋 4개, 겹치는 파일 0개 → 경위를 알리고 사용자 승인으로 머지.
- 범위 밖 발견물: 민지 [참고] 1건(화면은 `expectedUpdatedAt`을 받은 문자열 그대로 보내야 함)은 별도 티켓을 만들지 않고 ⑩a-2 20261008_1617의 설계 결정 D5·완료 조건에 넣었다.
- 규모: 계획 약 1,100줄 → 실제 약 1,554줄, 테스트와 공용 메모리 DB 파일이 늘었다.
