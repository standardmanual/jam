## 설계 결정 (2026-10-08, 채원 판정 승인 + 사용자 확인 + 카리나 가정)

- **D1 취향 신호 고치기(`saveOpsTasteSignal(service, signalId, { reason, evidenceDecisionId }, { actor, expectedUpdatedAt })`)**: 이유는 필수(공백 뗀 뒤 1~500자, 사용자 확인 ①). 저장하면 항상 `basis = 'confirmed'`.
  처음 확정이면 `confirmed_at = now()`·`confirmed_by = actor`, **이미 확정이면 `confirmed_at`·`confirmed_by`를 바꾸지 않는다**(사용자 확인 ② — 「확정 · 날짜」는 처음 확정한 날). `updated_at` 갱신. 조건부 update(`eq('updated_at', expectedUpdatedAt)`), 0행이면 다시 읽어 404/409.
  409 문장 「그사이 다른 곳에서 이 취향 신호를 고쳤어요. 최신 값을 불러와 주세요.」. 값이 같고 이미 확정이면 `changed: false`. 추정으로 되돌리는 입력은 받지 않는다(`basis` 칸은 무시하거나 400 — 아현 재량, 테스트로 고정).
- **D2 근거 검사**: `evidenceDecisionId`는 `null`(근거 없이) 또는 UUID. UUID면 그 결정이 ① `action = 'reject'` ② 항목의 `pattern_no`가 이 신호의 패턴 번호와 같음 ③ 시험 묶음이 아님 — 셋 다 맞아야 한다. 아니면 400 `fieldErrors.evidenceDecisionId` 「이 패턴의 반려 기록만 근거로 붙일 수 있어요.」.
  **공통 취향 신호(`pattern_no = null`)는 근거를 붙일 수 없다**(UUID면 400, 판정 「근거 없이 확정만」). 근거로 붙인 결정이 나중에 지워지면 FK가 비우므로 「근거 없이 확정」으로 남는다(사용자 확인 ④, 따로 처리하지 않는다).
- **D3 공통 규칙 고치기(`saveOpsCommonRule(service, ruleNo, { title, body }, { actor, expectedUpdatedAt })`)**: 제목 1~60자·본문 1~2,000자(사용자 확인 ①), 공백 뗌. `ruleNo`는 양의 정수, 없는 번호 404. 조건부 update, `updated_at`·`updated_by` 갱신, 409 문장 「그사이 다른 곳에서 이 공통 규칙을 고쳤어요. 최신 값을 불러와 주세요.」. 값이 같으면 `changed: false`. 추가·삭제 경로는 두지 않는다.
- **D4 근거 후보 읽기(`listPatternRejections(service, patternNo, { offset, limit = 10 })`)**: `ops_decisions` ⋈ `ops_bundles!inner(is_sample = false)` ⋈ `ops_bundle_items!inner(pattern_no = patternNo)`, `action = 'reject'`, `created_at` 내림차순 + `id` 보조 정렬, `limit + 1`개 읽어 `hasMore`.
  기간 제한 없음(API 92일 제한과 별개, 위험·결합 3). 한 줄 `{ id, createdAt, actorType, agentName, bundleId(묶음 행 UUID — opsTargetHref용), itemId, itemName(describeBundleItem), reason }`(사용자 확인 ③). **`actor` 원문·`diff`·`slack_result`는 싣지 않는다.**
  `offset`은 0 이상 정수(틀리면 400), 상한 1,000(카리나 가정). 응답 `{ rejections, hasMore, total? }`(총 개수는 필요하면 `count: 'exact'` — 「반려 기록 N건」 문구에 쓴다, 아현 재량).
- **D5 읽기 응답 확장(사용자 확인 ⑤)**: `OPS_TASTE_SIGNAL_COLUMNS`에 `updated_at`, `OpsTasteSignalRecord`에 `updatedAt`. 기존 칸은 그대로(에이전트 읽기 호환). `confirmed_by`는 계속 싣지 않는다.
- **D6 라우트·인증**: 두 `PATCH`는 관리자 세션만(`getAdminUser`, 토큰 403), 본문 64KB, JSON·객체 아님 400, `expectedUpdatedAt` 필수. `signalId`가 UUID가 아니면 404, `ruleNo`가 양의 정수가 아니면 404. `GET rejections`는 `requireAdminRead`(세션 또는 읽기 토큰, 다른 읽기와 같음), 번호 형식이 틀리면 400(같은 경로 GET과 같게).
  경로는 정적 세그먼트 `taste-signals`·`common-rules`가 `[patternNo]`보다 먼저 잡히는지 테스트로 고정한다(번호 형식 `P..`과 겹치지 않음).
- **D7 문서**: PRD §11.6에 세 경로(인증·응답 모양·409), §10.1 「취향 신호의 추정과 확정」 줄에 「확정 날짜는 처음 확정한 날, 공통 신호는 근거 없음, 근거 후보는 기간 제한 없음」, §11 표의 쓰기 행에 두 경로.
- **D8 하지 않는 것**: 화면(⑩b-2), 취향 신호 추가·삭제(승인 18 범위 밖), 공통 규칙 추가·삭제, 추정으로 되돌리기, DB 변경, 반려 창 변경.

## 완료 조건

- 추정 신호를 확정하면 읽기 API에 `basis: 'confirmed'`·`confirmedAt`·고친 이유가 나오고 `confirmed_by`는 나오지 않는다. 다시 고쳐도 `confirmedAt`은 처음 날짜다.
- 근거는 같은 패턴의 시험 아닌 반려 기록만 붙고, 근거 없이도 확정된다. 공통 신호는 근거 없이만. 추정으로 되돌리는 경로가 없다.
- 공통 규칙이 바로 반영된다. 두 곳에서 고치면 409(취향 신호·공통 규칙 모두).
- 근거 후보가 시험 반려를 빼고, 92일보다 오래된 반려도 보이며, `actor` 원문이 없다.
- 쓰기는 관리자 세션만(토큰 403). `scripts/verify.sh` 통과. DB 변경 없음.

- 사용자 확인(2026-10-08): 길이 상한(이유 500·공통 규칙 제목 60·본문 2,000), 확정 날짜는 처음 확정한 날 유지, 근거 후보 줄 구성(날짜·결정 문장·항목 이름·반려 이유)과 10건씩, 지워진 근거는 「근거 없이 확정」으로 보임, 읽기 응답에 `updatedAt` 추가.
- 카리나 가정: 근거 후보 `offset` 상한 1,000, 경로 이름(`taste-signals/[signalId]`·`common-rules/[ruleNo]`·`[patternNo]/rejections`), 근거 후보 읽기는 읽기 토큰도 허용.
- 머지 전 오염 검사 실패: 브랜치 고유 커밋은 이 티켓 4개뿐, 분기 뒤 다른 세션 커밋 2개, 겹치는 파일 0개 → 경위를 알리고 사용자 승인으로 머지.
- 범위 밖 발견물: 민지 [참고] 2건(정적 세그먼트 가로채기·임베드 필터 실동작)은 위 로컬 실호출로 확인해 티켓을 만들지 않았다.
