# [API] 운영툴 패턴 사전 ⑪ 패턴 제안을 승인하면 같은 요청에서 사전에 넣는다

> 상위: 20260930_1503 하위 ⑪(**2026-11-01 첫 월간 루틴 전** 마감). 선행 ⑩a-1 20261008_1545(`createOpsPattern`), E1-b 20261007_1746(패턴 제안 내용 칸·`readOpsPatternProposal`) 모두 CLOSED.
> 1503 미확정 「승인된 제안 항목의 최종 상태」를 여기서 확정한다(사용자 결정, 2026-10-08).

## 핵심 요약

- 요구사항: 받은 기획함에서 `kind = 'pattern_proposal'` 항목을 승인하면, 같은 요청 안에서 제안 내용을 패턴 사전에 새 패턴(P19~, 출처 `proposal`)으로 넣는다. 사전 입력이 실패하면 승인도 되돌린다(PRD §10.1). 승인된 제안 항목의 상태는 바로 「종료」다.
  일괄 승인은 패턴 제안을 빼고 처리한다. 시험 묶음 제안은 승인되지만 사전에는 넣지 않는다. 화면은 승인 토스트 문장만 바뀐다. DB 변경 없음.
- 구현 계획: 아래 「파일 단위 계획」. `decide.ts`의 `approveItem`에 패턴 제안 분기를 더하고, `bulkApprove`가 패턴 제안을 거른다. 사전 입력은 `createOpsPattern`을 그대로 부른다.

## 설계 결정 (2026-10-08, 사용자 결정 3개 + 카리나 가정)

- **D1 처리 순서(단건 승인, `kind = 'pattern_proposal'`)**: ① 묶음·항목 읽기 → ② `readOpsPatternProposal`이 `OPS_FIELD_UNKNOWN`이면 **승인을 막는다**(400 「제안 내용 형식이 맞지 않아 패턴 사전에 넣을 수 없어요. 반려해 주세요.」, 사용자 결정) →
  ③ 조건부 update `reviewing → ended`(0행이면 409, 사용자 결정 「바로 종료」) → ④ 시험 묶음이 아니면 `createOpsPattern(…, { origin: 'proposal', originItemId: item.id })` → ⑤ 결정 기록 insert(`action = 'approve'`).
  ④가 실패하면 상태를 `ended → reviewing`으로 되돌리고 실패를 돌려준다(번호 충돌 409 「그사이 다른 패턴이 만들어졌어요. 다시 승인해 주세요.」, 내용 검사 400은 `fieldErrors`를 문장 하나로 요약, 그 밖 500). ⑤가 실패하면 상태만 되돌리고 500(만든 패턴은 남는다 — 아래 D2).
- **D2 다시 승인해도 패턴이 두 번 생기지 않음(카리나 가정)**: ④에서 출처 중복(`PATTERN_ORIGIN_CONFLICT_MESSAGE`, `origin_item_id` 유일 충돌)이면 실패가 아니라 **이미 만든 패턴을 찾아 성공으로** 이어 간다. ⑤ 실패 뒤 다시 승인하는 경우를 위한 처리다. 패턴은 지우지 않는다(PRD §10.1 「번호는 지우지 않는다」).
- **D3 시험 묶음(사용자 결정)**: 승인·종료·결정 기록은 같고 사전 입력(④)만 건너뛴다. 응답 `pattern: null`, `patternSkipped: 'sample'`.
- **D4 응답**: 단건 승인 응답 본문에 `status: 'ended'`, `pattern: { patternNo } | null`, `patternSkipped: 'sample' | null`을 더한다(패턴 제안이 아닌 승인은 지금과 같다 — `status: 'approved'`, 새 칸 없음).
- **D5 일괄 승인(사용자 결정)**: 요청 ID 중 패턴 제안은 처리하지 않는다. 남은 ID로 지금처럼 승인하고, 응답에 `patternProposals: N`(뺀 개수)을 더한다. 요청이 모두 패턴 제안이면 400 「패턴 제안은 하나씩 승인해 주세요.」. 거른 항목은 `skipped`·`excluded`에 섞지 않는다.
- **D6 화면 문장(카리나 가정)**: 단건 승인 토스트 — 사전에 넣었으면 「승인했어요. 패턴 사전에 P19로 넣었어요」, 시험 묶음이면 「승인했어요. 시험 묶음이라 패턴 사전에는 넣지 않았어요」, 그 밖 「승인했어요」(지금과 같음).
  일괄 승인 결과 문장 끝에 `patternProposals > 0`이면 「 · 패턴 제안 N개는 하나씩 승인해 주세요」. 새 부품 없음.
- **D7 슬랙 글**: 바꾸지 않는다(카리나 가정 — 승인 글에 패턴 번호를 더하는 것은 범위 밖).
- **D8 문서**: PRD §7.2에 「패턴 제안은 승인하면 바로 종료(예약 등록 대상 아님)」, §10.1 흐름에 D1~D3(형식 오류는 승인 막음, 시험 묶음은 사전 제외, 실패 시 승인 되돌림, 다시 승인해도 한 번만), 결정 API 응답 칸(D4·D5).
- **D9 하지 않는 것**: DB 변경, 제안 내용 고치기 화면, S5 「승인 대기 제안」 거르기(P3 후보), 슬랙 글 변경, 반려 흐름 변경.

## 완료 조건

- 시험이 아닌 패턴 제안을 승인하면 같은 요청에서 사전에 새 번호·출처 `proposal`·`originItemId`로 들어가고, 항목은 「종료」, 결정 기록은 「승인」 1행이다.
- 사전 입력이 실패하면 항목이 검토중으로 돌아가고 결정 기록이 남지 않는다. 결정 기록만 실패한 뒤 다시 승인해도 패턴은 하나다.
- 형식이 틀린 제안은 승인되지 않는다(400). 시험 묶음 제안은 승인·종료되지만 사전에는 안 들어간다.
- 일괄 승인은 패턴 제안을 빼고 처리하며, 뺀 개수를 응답과 결과 문장에 보인다. 패턴 제안이 아닌 승인·일괄 승인 동작은 그대로다.
- `scripts/verify.sh` 통과. DB 변경 없음.
