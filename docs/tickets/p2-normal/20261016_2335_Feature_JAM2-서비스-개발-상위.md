# [Feature] JAM 2.0 서비스 개발을 묶음 8개로 나눠 진행한다 (상위)

## 핵심 요약

- 요구사항: [JAM 2.0 서비스 운영 로직](<../../plan/jam2/10 JAM 2.0 서비스 운영 로직.md>)의 19장을 실제 서비스로 개발한다. 진행 노트 2절의 5단계(티켓)에 해당한다.
- 구현 계획: 아래 묶음 8개를 번호 순서대로 진행한다. 묶음 0과 1만 이 티켓을 만들 때 하위 티켓까지 썼고, 나머지는 차례가 오면 사용자 승인을 받고 쓴다.
- 관련 파일: `docs/plan/jam2/10 JAM 2.0 서비스 운영 로직.md`(장별 규칙), `docs/plan/jam2/service-redesign/현재 서비스 비교.md`(5.3절 분류, 4.1절 고칠 문제, 6절 운영 자동화)

## 배경 / 문제 정의

JAM 2.0의 정책(2단계), 현재 서비스와의 비교(3단계), 새 운영 로직 문서(4단계)가 끝났고, 디자인 시스템 적용도 staging에 반영했다(상위 티켓 20261015_2130).
사용자가 유저 화면 완성을 알려 5단계를 시작한다(2026-10-16). 운영 로직 문서의 19장을 한 번에 티켓으로 옮기면 장 사이의 의존 관계가 보이지 않으므로,
먼저 장을 묶음으로 모은 뒤 묶음 단위로 승인을 받으며 진행한다.

## 사용자 결정 (2026-10-16)

1. **티켓은 상위 1개 + 묶음 8개로 쓴다.** 묶음 안의 하위 티켓은 그 묶음을 시작할 때 쪼갠다. 앞 묶음의 결과를 보고 뒤 묶음을 다듬기 위해서다.
2. **이번에는 상위 티켓과 묶음 0·1만 상세히 쓴다.** 나머지 묶음은 아래 표의 한 줄 개요만 둔다.
3. **디자인과 관련된 열린 항목은 JAM 2.0이 완료된 뒤, 검토가 필요하면 그때 사용자가 확인한다.** 디자인 시스템 문서 6절의 열린 항목, 보조 버튼·입력창 경계·진행 바 색·탭바 아이콘 대비,
   로고 파운데이션, 옛 보라 바탕 썸네일, 상태 칩 MODULAR 승격, 배지 획득 오버레이 글자색이 여기에 든다. 이 티켓의 묶음에서는 이 항목을 먼저 제안하지 않는다.
   claude.ai/design 업로드본 갱신(티켓 20261016_2220)은 인증 문제로 WAITING이고, 사용자가 앱 입력창에서 직접 시도해 보겠다고 할 때 진행한다.
4. **화면은 완성된 새 디자인을 구현한다**(진행 노트 2절 규칙 15, 16). 어드민은 리뉴얼 범위 밖이라 지금처럼 shadcn/ui 표준을 따른다.

### 순서의 근거

- 챕터 점수는 배지, 미션, 컬렉션, 포인트가 있어야 계산되므로 챕터 연결은 묶음 5에 둔다. 저장 구조만 묶음 1에서 먼저 만든다.
- 온보딩 퀘스트의 실제 두 단계는 캡슐이 생긴 뒤에야 완성되므로 묶음 6을 뒤에 둔다.
- 컨텐츠 입력(묶음 7)은 컬렉션 4등급 구조(묶음 1)와 캡슐(묶음 3)이 있어야 데이터 모양이 맞는다.
- 4.1절의 문제 9건은 모두 위 표에서 해당 묶음에 배치했다. 묶음 2에 3건(Strava 다른 계정, 토큰 갱신 실패, 걸러진 활동 저장), 묶음 4에 3건(시스템 드랍 전체 무작위, 꺼진 장소 픽업, 배지 수정 폼의 장소 연결 20261006_1028), 묶음 5에 3건(게이트 미션 덮어쓰기, 선착순 잠금, 포인트 음수)이다.

## 진행 원칙

1. **DB는 staging과 프로덕션이 공용이다.** JAM 2.0을 staging에 쌓는 동안 프로덕션 코드는 옛 서비스이므로, DB는 새 테이블과 새 함수를 **추가**하는 변경만 한다.
   기존 컬럼과 함수를 바꾸거나 지우는 변경(축소)은 기존 유저를 정리하는 묶음 6의 전환 단계까지 미룬다. 규칙의 단일 원천은 `.claude/skills/jam-work/references/db-migration-rules.md`다.
2. **DB 실행은 사용자 승인 뒤 카리나가 한다.** 아현은 SQL 파일 작성까지만 한다. 실행 전에 파일명, 영향 범위, 되돌림 SQL 위치를 말하고 채팅에서 승인을 받는다.
3. **파일이 30개를 넘는 티켓은 처음부터 2~3회로 나눠 돌리고, 회마다 게이트를 돌린다.** 규모는 테스트, 문서, 스토리까지 센다.
   아현의 최종 요약은 2,500자 이내로 쓰게 하고 상세 목록은 커밋 본문에 남긴다(3,000자를 넘으면 워크플로가 실패한다).
4. **하위 티켓마다 시작 전에 사용자에게 주요 결정을 질문창으로 묻는다.** 추천안을 함께 보인다.
5. **staging에 쌓고 `/jam-ship`은 하지 않는다.** JAM 2.0 출시 전까지 main에 반영하지 않는다(상위 티켓 20261015_2130 결정 1). 프로덕션 긴급 수정은 main에서 따로 처리한다.
6. 정책 문서와 운영 로직 문서가 다르면 다른 곳을 사용자에게 확인하고 둘 다 고친다(운영 로직 0.3절).

## 완료 조건

- 묶음 0~7의 티켓이 모두 CLOSED다.
- 운영 로직 문서 19장 가운데 코드로 옮긴 장이 모두 해당 PRD(`docs/service/prd/`)와 컨텐츠·엔진 문서에 반영되어 있다.
- 4.1절의 문제 9건이 해당 묶음의 완료 기록에 "고침" 또는 "재현 안 됨"으로 남아 있다.
- JAM 2.0 출시를 위한 main 승격과 `docs/service/SERVICE_OPERATIONS.md` 덮어쓰기는 이 티켓의 범위 밖이며, 사용자 승인 뒤 `/jam-ship`으로 진행한다.
