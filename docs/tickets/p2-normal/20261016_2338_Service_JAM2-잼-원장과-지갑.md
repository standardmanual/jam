# [Service] JAM 2.0 잼 원장과 지갑을 DB에 추가한다

## 핵심 요약

- 요구사항: 운영 로직 4.2절의 "원장과 기록"을 DB로 만든다. 잼이 늘고 주는 모든 일을 원장에 한 줄씩 남기고, 잔액은 원장을 거쳐서만 바뀌며, 0 아래로 내려가지 않는다.
- 구현 계획: 포인트 원장 구조를 본떠 지갑, 원장, 일 단위 모은 양 집계, 지급·차감 함수를 새 마이그레이션 한 파일(되돌림 SQL 포함)로 추가한다. 동기화, 캡슐, 화면 연결은 하지 않는다.
- 관련 파일: `jam-web/supabase/migrations/080_point_system_renumbered_from_045_duplicate.sql`(본뜰 구조: `point_wallets` 43행, `point_transactions` 60행, `award_points` 111행), 새 파일 `jam-web/supabase/migrations/220_jam_ledger.sql`(2026-10-17 원격 staging 최신 번호가 219다. 아현이 쓰기 직전과 push 직전에 다시 확인한다), `docs/service/prd/02_DATA_MODEL.md`

## 배경 / 문제 정의

잼은 활동을 동기화하면 쌓이고 캡슐과 잠긴 아이템 배지를 채울 때 쓰는 자원이다(운영 로직 4장). 지금 서비스에는 잼이 없다.
잼은 돈과 달리 사라지지 않고 한도가 없지만, 쌓고 쓰는 내역이 정확해야 어드민이 오류를 바로잡을 수 있다.
그래서 포인트와 같이 "잔액은 원장을 거쳐서만 바뀐다"는 구조를 쓴다. 포인트 쪽에는 잔액이 0 아래로 내려가는 것을 막는 제약이 없어(비교표 4.1절) 이번에는 처음부터 넣는다.

## 사용자 결정 (2026-10-17, 질문창)

1. **모은 양은 별도 집계 칸에 저장한다.** 추천은 원장 합산이었으나 사용자가 집계 칸을 골랐다. 구체 모양은 아래 「가정」을 따른다.
2. **활동 식별자에 유일 제약을 건다.** 같은 활동은 DB에서 한 번만 정산된다(추천안).
3. **원장의 사유 값은 5개다.** 활동 정산, 캡슐 채움, 잠긴 아이템 배지 채움, 운영자 지급, 운영자 회수(추천안).

### 가정 (카리나가 정했고 SQL 실행 승인 전에 다시 확인한다)

- 집계 칸의 모양: 지갑에 `total_earned`(지금까지 모은 총량)를 두고, 기간별 모은 양은 KST 날짜 단위 집계 테이블(유저, 날짜, 그날 모은 양)을 둔다. 이번 주, 이번 달 같은 기간은 날짜 집계를 합산해 읽는다. 기간 종류가 정해져 있지 않아 주 단위 칸 하나로 고정하지 않았다.
- 「모은 양」은 활동 정산만 센다. 운영자 지급·회수는 가진 양만 바꾸고 모은 양에는 넣지 않는다. 운영 로직 4.5절이 "잼은 움직인 양만 재는 자원"이라고 했기 때문이다. 동기화 오류로 빠진 활동을 운영자가 채워 주는 경우도 모은 양에 넣을지는 승인 전에 사용자에게 다시 묻는다.
- 원장은 활동 테이블(`strava_activities`, 키 UUID)을 외래키로 묶지 않고 활동 식별자만 담는다. 원장은 지워지지 않는 기록이라 활동이 지워져도 남아야 하기 때문이다.
- 집계 칸은 지급·차감 함수 안에서만 바뀐다. 원장 한 줄과 집계 갱신이 같은 트랜잭션이다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 지갑(`jam_wallets`): 유저마다 지금 가진 양(`balance`, 0 이상 검사 제약)과 지금까지 모은 총량(`total_earned`) 하나씩. 본인만 읽을 수 있고, 쓰기는 함수로만 한다(`SECURITY DEFINER`).
- 날짜별 모은 양(`jam_daily_earned`): 유저, KST 날짜, 그날 모은 양. 활동 정산 때만 늘어난다. 본인만 읽는다.
- 원장(`jam_transactions`): 추가만 되고 고치거나 지울 수 없다. 늘어난 양은 양수, 쓴 양은 음수이며 0은 허용하지 않는다. 사유 5개(결정 3), 시각, 운영자 지급·회수일 때 운영자 식별자와 사유 문구를 담는다. 유저를 지우면 함께 지워진다(`ON DELETE CASCADE`, 포인트 원장과 같다).
- 활동 정산은 활동 식별자를 함께 기록하고, 그 식별자에 부분 유일 인덱스(사유가 활동 정산일 때)를 건다(결정 2).
- 함수는 지급(활동 정산, 운영자 지급)과 차감(캡슐 채움, 잠긴 아이템 배지 채움, 운영자 회수)을 다룬다. 차감이 가진 양보다 크면 거절한다.
- 지급·차감 사유가 서로 다른 함수 인자로 새지 않도록 사유별 허용 부호를 검사한다(활동 정산은 양수만, 채움은 음수만).
- 이용 정지 중 동작 차단은 이 티켓의 범위가 아니다(묶음 2의 어뷰징·제재).

### UI/UX 관점 (해당 시)

- 해당 없음. 화면은 묶음 2(동기화 결과), 묶음 3(캡슐), 묶음 5 이후 프로필에서 만든다.

## 구현 계획 (파일 단위)

규모 사전 판정: SQL 한 파일이 주석과 되돌림 SQL을 합쳐 100줄을 넘고, 문서 갱신을 더하면 파일은 2~3개다. `plan_only` 임계값(100줄 이상)에 걸리므로 첫 호출부터 `planOnlyWaiver`를 넘긴다.

1. `jam-web/supabase/migrations/220_jam_ledger.sql`(새 파일, 추가만)
   - `jam_wallets`, `jam_daily_earned`, `jam_transactions` 테이블과 RLS(본인 읽기만, 쓰기 정책 없음), `jam_transactions`의 `(user_id, created_at DESC)` 인덱스와 활동 식별자 부분 유일 인덱스.
   - 함수 `jam_apply(p_user_id, p_amount, p_reason, p_source_activity_id, p_admin_user_id, p_admin_reason_label, p_admin_reason_note)`처럼 하나로 묶거나 지급·차감 둘로 나눈다(이름과 시그니처는 아현이 `award_points`(`080_point_system_renumbered_from_045_duplicate.sql` 111행)를 본떠 정한다). 사유별 허용 부호(활동 정산·운영자 지급은 양수, 채움 둘·운영자 회수는 음수)를 검사하고, 가진 양보다 큰 차감은 거절한다.
   - 활동 정산일 때만 `total_earned`와 `jam_daily_earned`(KST 날짜)를 함께 늘린다. 같은 활동 식별자의 두 번째 정산은 오류로 거절하지 않고 기존 원장 줄을 돌려주는 방식 가운데 하나를 아현이 정해 요약에 적는다(동기화가 안전하게 다시 호출될 수 있어야 한다).
   - 파일 끝에 되돌림 SQL을 주석 블록으로 싣는다. 함수 인자 수를 나중에 바꾸지 않도록 시그니처를 확정해 둔다(`db-migration-rules.md` 3절).
   - 기존 테이블·함수는 건드리지 않는다. `award_points`와 `point_*`는 그대로다.
2. `docs/service/prd/02_DATA_MODEL.md`: 잼 지갑, 날짜별 모은 양, 잼 원장 세 테이블을 반영한다.
3. 읽을 것: `.claude/skills/jam-work/references/db-migration-rules.md`(작성 규칙), `080_point_system_renumbered_from_045_duplicate.sql`(본뜰 구조), `069_strava_activities.sql`(활동 테이블 `strava_activities`, 키 UUID).
4. 이 티켓에서 아현은 SQL 파일과 문서만 쓴다. 실행과 타입 갱신은 카리나가 한다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)

- 마이그레이션 파일이 새 테이블과 새 함수만 추가하고 기존 객체를 바꾸거나 지우지 않는다. 확인 방법은 `DROP`, `ALTER ... DROP`, 기존 함수에 대한 `CREATE OR REPLACE`가 없음을 검색한 결과다.
- 파일 안에 되돌림 SQL이 있다.
- 지갑, 날짜별 모은 양, 원장에 RLS가 켜져 있고, 일반 유저는 자기 행을 읽기만 할 수 있으며 쓰기 정책이 없다.
- `balance`가 0 아래로 내려갈 수 없다(검사 제약과 함수 검사).
- 지급·차감 함수는 사유별 허용 부호를 어기면 거절한다.
- 같은 활동 식별자로 활동 정산을 두 번 호출해도 원장에 한 줄만 남고 `total_earned`와 날짜별 모은 양이 두 배가 되지 않는다.
- 활동 정산만 모은 양을 늘리고 운영자 지급·회수와 채움은 모은 양을 바꾸지 않는다(위 가정).
- `docs/service/prd/02_DATA_MODEL.md`에 세 테이블이 반영되어 있다.

### 후속 범위 (담당: 카리나, 시점: 사용자 승인 뒤)

- 가정(운영자 지급을 모은 양에 넣을지)을 SQL 실행 승인 전에 사용자에게 다시 확인한다.
- 마이그레이션을 Supabase MCP로 실행했고, `DO` 블록 롤백 실측(지급 후 잔액과 총량, 가진 양보다 큰 차감 거절, 같은 활동 두 번 정산, 일반 유저 권한으로 쓰기 거절)의 결과가 완료 기록에 있다.
- `generate_typescript_types`로 타입을 대조한 결과가 완료 기록에 있다.
