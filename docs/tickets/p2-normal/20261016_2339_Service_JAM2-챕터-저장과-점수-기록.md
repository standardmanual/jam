# [Service] JAM 2.0 챕터와 점수의 저장 구조를 DB에 추가한다

## 핵심 요약

- 요구사항: 운영 로직 12장의 챕터를 저장할 구조를 만든다. 챕터 정의(필요 누적 점수), 트라이브별 챕터 이름 표, 활동별 점수 설정, 유저의 챕터와 누적 점수, 점수 기록, 오른 기록이다.
- 구현 계획: 새 마이그레이션 한 파일(`221_chapters.sql`, 되돌림 SQL 포함)로 테이블과 점수 가산·챕터 시작 함수를 추가하고, 챕터 10개와 활동별 점수 규칙을 초기값으로 넣는다. 점수를 주는 연결, 연출, 소식, 챕터 배지, 프로필 표시는 묶음 5에서 한다.
- 관련 파일: 새 파일 `jam-web/supabase/migrations/221_chapters.sql`(220이 잼 원장이다. 쓰기 직전과 push 직전에 원격 staging 최신 번호를 다시 확인한다), `docs/service/prd/02_DATA_MODEL.md`. 점수 세기가 나중에 기댈 JAM 조건 판정 코드는 `jam-web/src/lib/badge-engine/`에 있다(이 티켓에서는 읽지 않아도 된다).

## 배경 / 문제 정의

챕터는 유저마다 하나이고 서비스 활동량으로 오르며 내려가지 않는다(12.2절). 지금 서비스에는 유저의 단계가 없다.
점수를 주는 활동이 여러 묶음(캡슐은 3, 배지는 4, 미션은 5)에 걸쳐 있어서, 저장 구조와 "점수를 더하면 챕터가 오른다"는 규칙을 먼저 한 곳에 두고 각 묶음이 그 함수를 호출하게 한다.

## 사용자 결정 (2026-10-17, 질문창, 모두 추천안)

1. **점수 수치는 전용 테이블에 둔다.** 챕터 정의, 활동별 점수 규칙, 트라이브별 챕터 이름을 새 테이블에 둔다. 묶음 7의 「모은 설정 화면」이 이 테이블을 읽게 한다.
2. **같은 활동에서 점수가 두 번 쌓이지 않게 `(활동 종류, 원천 식별자)`에 유일 제약을 건다.**
3. **챕터 1은 퀘스트 완료 때 따로 호출한다.** 점수 0에서 시작하고, 호출하는 순간 챕터 1이 된다.
4. **잼 점수의 주간 상한 계산은 DB 함수가 한다.** 호출부는 활동 종류와 양만 넘기고, 이번 주(월~일, KST) 이미 센 점수를 보고 상한 초과분을 절반으로 줄이는 일은 함수가 한다.

### 가정 (카리나가 정했고 SQL 실행 승인 전에 다시 확인한다)

- **퀘스트를 마치기 전에 쌓인 점수**: 정책 문서에 없다. 점수 기록과 누적 점수는 챕터가 없어도 쌓고(`chapter_no`는 비어 있음), `chapter_start`가 챕터 1로 만드는 순간 쌓인 점수로 오를 챕터까지 한 번에 계산한다. 퀘스트 둘째 단계가 캡슐이 생긴 뒤라서(운영 로직 2장) 퀘스트 완료 전에 첫 동기화가 일어난다고 보고 정했다. 퀘스트 전 점수를 버리려면 이 규칙만 바꾸면 된다.
- **주간 상한의 기준**: 주(월~일)는 활동한 날(KST)로 정한다(잼 원장과 같은 기준). 상한 안의 점수는 그대로 세고, 넘는 부분만 `over_cap_ratio`(0.5)를 곱한다. 한 번의 호출이 상한 경계에 걸치면 경계까지는 전부, 넘는 양은 절반으로 나눠 센다. 소수점은 내림한다.
- **점수 규칙의 확장**: 활동 종류는 규칙 테이블의 행이다. 새 종류는 행을 더하면 되고 마이그레이션이 필요 없다. 원천 식별자는 호출부가 정한 UUID(예: 활동, 캡슐 열기 기록)이다.
- 점수 가산을 부를지 말지(예: 챕터 배지·포인트 조건 배지는 점수 제외, 자기 드랍 줍기 제외, 이용 정지 중 차단)는 부르는 쪽 책임이다. 이 함수는 호출된 활동을 그대로 센다.

## 상세 요구사항

### 서비스/코드베이스 관점

테이블(모두 새 테이블, RLS는 본인 읽기만 필요한 것만 두고 쓰기는 함수와 어드민 서버 경로로만 한다):

- `chapter_definitions`: 챕터 번호(1부터), 오르는 데 필요한 누적 점수. 초기값은 챕터 1이 0(퀘스트 완료), 챕터 2부터 1,000, 2,300, 3,800, 5,700, 8,500, 11,500, 15,000, 19,000, 23,000이다(12.4절). 챕터는 뒤에 더할 수 있다. 읽기는 로그인 유저 모두 가능(다음 챕터까지 게이지에 필요)하게 한다.
- `chapter_names`: 트라이브별 챕터 이름. 트라이브(`tribes`)와 챕터 번호가 키이고 이름 칸은 비어도 된다. 트라이브 다섯 개가 아직 등록되지 않았으므로 행을 미리 넣지 않는다. 읽기는 로그인 유저 모두 가능하게 한다.
- `chapter_score_rules`: 활동 종류, 단위당 점수, 주간 상한(없으면 비움), 상한 초과분의 비율(기본 0.5). 초기값은 운영 로직 12.2절 표를 따른다: 잼 1당 1점(주 300점 상한, 초과분 절반), 캡슐 열기 20, 잠긴 아이템 배지 열기 10, 배지 받기 10, 컬렉션 완성 Common 100·Rare 200·Epic 400·Mystic 800(등급마다 별도 활동 종류), 믹스 성공 20, 미션 완료 50, 드랍 5, 픽업 5. 읽기는 서버 전용으로 둔다(클라이언트 정책 없음).
- `user_chapters`: 유저마다 지금 챕터 번호(비어 있을 수 있음)와 누적 점수. 본인만 읽는다.
- `chapter_score_events`: 점수 기록. 유저, 활동 종류(규칙 테이블 참조), 원천 식별자, 활동한 날, 단위 수(호출된 양), 상한 적용 전 점수, 실제로 센 점수, 시각. `(활동 종류, 원천 식별자)` 유일 제약. 본인만 읽는다.
- `chapter_ups`: 오른 기록. 유저, 챕터 번호, 오른 시각, `(유저, 챕터 번호)`가 키. 한 번에 여러 챕터를 넘으면 챕터마다 한 줄이다. 본인만 읽는다.

함수(`SECURITY DEFINER`, `service_role`만 실행, 시그니처는 확정해 둔다):

- `chapter_add_score(p_user_id, p_activity_kind, p_source_id, p_amount, p_occurred_on DATE DEFAULT NULL)`: 규칙을 읽어 점수를 계산하고(주간 상한은 같은 유저·같은 활동 종류의 이번 주 상한 적용 전 점수 합을 보고 계산), 점수 기록과 누적 점수를 한 트랜잭션에 반영하고, 챕터가 있으면 올릴 수 있는 만큼 올린다. 같은 `(활동 종류, 원천 식별자)`는 오류 없이 이미 센 결과를 돌려준다. 활동한 날은 미래를 거절하고, 비우면 오늘(KST)이다. 돌려주는 값은 센 점수, 지금 챕터, 이번 호출로 오른 챕터 번호 목록이다.
- `chapter_start(p_user_id)`: 챕터가 비어 있으면 챕터 1로 만들고 오른 기록을 남긴 뒤, 쌓인 점수로 오를 수 있는 챕터까지 올린다. 이미 챕터가 있으면 아무것도 하지 않는다. 같은 값을 돌려준다.
- 챕터는 내려가지 않는다.

## 구현 계획 (파일 단위)

규모 사전 판정: SQL 한 파일이 테이블 6개, 함수 2개, 초기값 입력, 되돌림 SQL을 합쳐 250줄 안팎이라 `plan_only` 임계값(100줄 이상)을 넘는다. 사용자가 결정을 모두 답했고 아래가 파일 단위 계획이라 첫 호출부터 `planOnlyWaiver`를 넘긴다.

1. `jam-web/supabase/migrations/221_chapters.sql`(새 파일, 추가만): 위 테이블 6개(`chapter_definitions`, `chapter_names`, `chapter_score_rules`, `user_chapters`, `chapter_score_events`, `chapter_ups`), 함수 2개, 초기값 입력(다시 실행해도 중복이 생기지 않게 `ON CONFLICT DO NOTHING`), 파일 끝 되돌림 SQL 주석 블록. 기존 객체는 건드리지 않는다. 인자 수를 나중에 바꾸지 않도록 시그니처를 확정한다(`db-migration-rules.md` 3절).
2. `docs/service/prd/02_DATA_MODEL.md`: 9-2절(잼) 다음에 챕터 절을 더한다.
3. 읽을 것: `.claude/skills/jam-work/references/db-migration-rules.md`, `jam-web/supabase/migrations/220_jam_ledger.sql`(방금 적용한 같은 방식의 파일. 권한 회수, `SECURITY DEFINER`, 되돌림 SQL 형식을 그대로 따른다), 운영 로직 문서 12장, `tribes` 테이블 정의(`152_factions_to_tribes_rename.sql` 등).
4. 이 티켓에서 아현은 SQL 파일과 문서만 쓴다. 실행, 롤백 실측, 타입 갱신은 카리나가 한다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)

- 마이그레이션이 새 테이블과 새 함수만 추가하고 기존 객체를 바꾸거나 지우지 않으며 되돌림 SQL을 싣는다.
- 챕터 정의 10개의 필요 누적 점수와 활동별 점수 규칙의 초기값이 운영 로직 12.4절·12.2절과 같다. 잼 규칙은 주 300점 상한과 초과 비율 0.5를 가진다.
- 트라이브별 챕터 이름 표가 있고 행은 비어 있다.
- 점수 가산 함수가 같은 `(활동 종류, 원천 식별자)`를 두 번 받아도 한 번만 반영한다.
- 잼 점수가 한 주 안에서 300점까지는 그대로, 넘는 양은 절반으로 계산된다(경계에 걸치는 호출 포함).
- 챕터가 없는 유저의 점수는 쌓이고 챕터는 오르지 않는다. `chapter_start`는 챕터 1로 만들고 쌓인 점수로 오를 챕터까지 한 번에 올리며, 오른 챕터마다 오른 기록을 한 줄씩 남긴다. 챕터는 내려가지 않는다.
- 일반 유저는 자기 점수·챕터·오른 기록만 읽을 수 있고 모든 쓰기 권한이 회수되어 있다. 두 함수는 `service_role`만 실행할 수 있다.
- `docs/service/prd/02_DATA_MODEL.md`에 챕터 구조가 반영되어 있다.

### 후속 범위 (담당: 카리나, 시점: 사용자 승인 뒤)

- 가정(퀘스트 전 점수를 쌓아 두었다가 챕터 1 때 함께 계산)을 SQL 실행 승인 전에 사용자에게 다시 확인한다.
- 롤백 실측을 한 뒤 MCP로 실행한다(2026-10-17 잼 원장과 같은 방식): 같은 활동 두 번 정산, 주간 상한 경계, 챕터 없는 유저의 점수, 챕터 시작과 한 번에 여러 챕터 오름, 챕터가 내려가지 않음, 일반 유저 권한 거절.
- 생성 타입 파일을 맞춘다(열 단위 대조).
