# [Service] JAM 2.0 컬렉션 4등급 구조와 단일 완성 판정을 만든다

## 핵심 요약

- 요구사항: 운영 로직 8.3절의 컬렉션을 만든다. 같은 이름의 아이템 배지 4등급을 한 칸으로 묶고, 유저가 처음 꽂은 등급이 그 컬렉션의 등급이 되며, 완성과 보상은 등급마다 따로 기록하고, 완성 판정은 하나로 모은다.
- 구현 계획: 설계와 DB 추가(1회), 완성 판정 모듈 통일(2회), 새 장착 경로(3회)로 나눠 돌리고 회마다 게이트를 돌린다. 옛 장착 함수와 옛 완성 기록은 바꾸지 않고 새 구조를 덧붙인다. 컬렉션 화면 표시와 등급 올리기 레시피는 묶음 3, 컨텐츠 입력은 묶음 7이다.
- 관련 파일: `jam-web/supabase/migrations/017_item_book_slots.sql`(`user_item_book_slots`, `user_item_book_completions`), `157_item_book_completion_points.sql`·`178_slot_item_into_book_completion_basis.sql`(`slot_item_into_book`), `jam-web/src/lib/itembook/`(`checker.ts`, `completable.ts`, `completion-basis.ts`, `filled-by-book.ts`, `slotReward.ts`, `visibility.ts`), `jam-web/src/app/api/itembooks/[id]/slot/route.ts`, `jam-web/src/app/api/itembooks/route.ts`, `jam-web/src/app/api/users/[username]/itembooks/route.ts`, `jam-web/src/app/api/admin/itembooks/[id]/route.ts`, `jam-web/src/lib/admin/reference-guards.ts`. 정확한 줄 위치는 1회 시작 때 아현이 확인한다.

## 배경 / 문제 정의

지금 컬렉션은 아이템 배지 단위로 칸을 채우고, 완성은 컬렉션마다 한 번 기록하며, 완성 포인트와 보상 배지 칸도 컬렉션마다 하나다.
JAM 2.0은 컬렉션마다 9종(이름)이 있고 같은 이름의 아이템 배지가 Common, Rare, Epic, Mystic 4개로 있다. 유저가 처음 꽂은 등급을 따르고, 완성과 보상은 등급마다 한 번씩이다(8.3절).
비교표 5.2절의 A는 "등급마다 컬렉션을 따로 만든다"는 대안이었으나 사용자가 원안(한 칸 4등급)대로 개발하기로 했다(2026-10-10).
또 지금은 장착할 때, 보상을 줄 때, 동기화 보정 때, 화면에서 완성을 서로 다르게 센다(비교표 3.8절). 하나로 모은다.

**공용 DB 주의.** `slot_item_into_book`은 프로덕션 코드가 지금도 호출한다. 이 함수와 `user_item_book_completions`는 바꾸지 않고, 새 함수와 새 테이블을 덧붙인다.
옛 것을 지우는 축소는 묶음 6의 전환 단계에서 한다.

## 시작 전에 사용자에게 물을 결정

1. 4등급을 한 칸으로 묶는 키. 추천은 컬렉션 안의 "이름 칸" 한 단위를 두고, 그 칸에 등급이 다른 아이템 배지 4개를 연결하는 것이다. 컬렉션 입력(묶음 7)이 이름 단위로 이뤄진다.
2. 유저의 컬렉션 등급을 저장할 곳. 추천은 유저와 컬렉션마다 한 줄이고, 장착한 것을 모두 빼면 지우는 것이다.
3. 등급별 완성 기록과 보상 칸을 어디에 둘지. 추천은 새 테이블(유저, 컬렉션, 등급)과 컬렉션의 등급별 보상 칸 4세트다. 옛 칸과 옛 기록은 그대로 둔다.
4. 컨텐츠가 아직 4등급 모양이 아닐 때의 동작. 지금 컬렉션(켜진 것 30개)은 4등급 구조가 없다. 추천은 새 구조를 쓰는 컬렉션에만 새 규칙을 적용하고, 구분은 컬렉션의 칸 4등급 연결 유무로 한다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 데이터: 이름 칸과 4등급 연결(결정 1), 유저의 컬렉션 등급(결정 2), 등급별 완성 기록과 등급별 완성 보상(결정 3).
- 완성 보상 초기값: 포인트는 Common 100, Rare 200, Epic 400, Mystic 800이다(8.6절). 보상 배지는 컨텐츠 입력(묶음 7)에서 정한다.
- 장착 규칙: 처음 꽂은 아이템 배지의 등급이 그 유저에게 그 컬렉션의 등급이 된다. 그 뒤로는 같은 등급만 꽂을 수 있다. 장착한 것을 모두 빼면 등급이 풀린다. 같은 이름은 컬렉션마다 하나만 꽂는다.
  잠긴 아이템 배지는 꽂을 수 없다(잠김 자체는 묶음 3이므로 여기서는 검사 자리만 둔다).
- 완성: 그 등급으로 9칸을 모두 채우면 완성이다. 완성은 등급마다 따로 기록하고 보상도 등급마다 한 번만 준다. 장착을 풀어도 완성 기록은 남고, 다시 채워도 같은 등급의 보상을 또 주지 않는다.
- 완성 판정은 장착할 때, 보상을 줄 때, 동기화 뒤 보정할 때, 화면에 보여 줄 때 모두 같은 하나의 모듈이 한다.
- 기존 규칙 유지: 장착한 아이템 배지는 드랍과 믹스에 쓸 수 없다. 인벤토리가 가득 차 있으면 장착을 풀 수 없다. 공개 기간이 끝난 컬렉션에도 가진 아이템 배지를 꽂아 완성할 수 있다.
- 완성 포인트 지급은 포인트 원장 함수(`award_points`)를 쓴다. 챕터 점수 가산은 묶음 5에서 이 완성 이벤트에 연결한다.

### UI/UX 관점 (해당 시)

- 컬렉션 화면 표시는 묶음 3이다. 이 티켓은 화면이 기존 모양 그대로 새 API를 읽어도 깨지지 않게 응답 모양을 호환시키는 데까지만 한다.

## 구현 계획 (회차)

규모가 크므로 처음부터 3회로 나눠 돌리고 회마다 게이트를 돌린다. 파일 수는 테스트와 문서까지 세어 1회 시작 전에 다시 판정한다.

1. **1회: 설계와 DB 추가.** 결정 4개를 받는다. 마이그레이션을 쓴다(새 테이블, 새 칸, 새 장착 함수, 되돌림 SQL). 카리나가 승인 뒤 실행하고 롤백으로 실측한다(첫 꽂기로 등급이 정해짐, 다른 등급 거절, 다 빼면 풀림, 9칸 완성, 등급별 보상 한 번만).
2. **2회: 완성 판정 모듈 통일.** `jam-web/src/lib/itembook/`의 판정 모듈을 하나로 모으고, 장착 보상, 동기화 보정, 화면 표시 경로가 같은 모듈을 부르게 한다. 지금 서로 다른 분모와 분자 계산을 테스트로 고정한다.
3. **3회: 새 장착 경로와 API 호환.** 장착 API가 새 함수를 쓰게 하고(전환), 조회 API가 등급 정보를 함께 돌려주게 한다. 어드민 컬렉션 화면에 등급별 보상 칸이 필요한지는 묶음 7에서 다루고, 여기서는 기존 어드민 저장이 새 칸을 지우지 않는지만 확인한다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)

- 마이그레이션이 옛 테이블, 옛 함수, 옛 컬럼을 바꾸거나 지우지 않고 되돌림 SQL을 싣는다.
- 새 구조를 쓰는 컬렉션에서 첫 꽂기가 컬렉션 등급을 정하고, 다른 등급 장착은 거절되며, 장착한 것을 모두 빼면 등급이 풀린다. 단위 테스트로 확인한다.
- 같은 등급 9칸 완성이 등급마다 한 번만 기록되고 보상도 한 번만 나간다. 장착을 풀었다가 다시 채워도 같은 등급 보상이 다시 나가지 않는다. 단위 테스트로 확인한다.
- 장착, 보상, 동기화 보정, 화면 표시 네 경로가 하나의 완성 판정 모듈을 부른다. 확인 방법은 판정 모듈 외에 완성을 직접 세는 코드가 `jam-web/src`에 없음을 검색한 결과다.
- 새 구조를 쓰지 않는 기존 컬렉션은 이전과 같은 규칙으로 동작한다.
- `docs/service/prd/02_DATA_MODEL.md`와 컨텐츠 문서(`docs/service/content/`)에 새 구조가 반영되어 있다.

### 후속 범위 (담당: 카리나, 시점: 사용자 승인 뒤)

- 마이그레이션 실행과 롤백 실측 결과가 완료 기록에 있다.
- 프로덕션(옛 코드)에서 컬렉션 화면과 장착이 이전과 같이 동작하는지 확인한 결과가 완료 기록에 있다.
