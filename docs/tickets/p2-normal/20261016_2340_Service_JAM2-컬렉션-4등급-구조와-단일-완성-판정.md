# [Service] JAM 2.0 컬렉션 4등급 구조와 단일 완성 판정을 만든다

## 핵심 요약

- 요구사항: 운영 로직 8.3절의 컬렉션을 만든다. 같은 이름의 아이템 배지 4등급을 한 칸으로 묶고, 유저가 처음 꽂은 등급이 그 컬렉션의 등급이 되며, 완성과 보상은 등급마다 따로 기록하고, 완성 판정은 하나로 모은다.
- 구현 계획: 설계와 DB 추가(1회), 완성 판정 모듈 통일(2회), 새 장착 경로(3회)로 나눠 돌리고 회마다 게이트를 돌린다. 옛 장착 함수와 옛 완성 기록은 바꾸지 않고 새 구조를 덧붙인다. 컬렉션 화면 표시와 등급 올리기 레시피는 묶음 3, 컨텐츠 입력은 묶음 7이다.
- 관련 파일: `jam-web/supabase/migrations/017_item_book_slots.sql`(`user_item_book_slots`, `user_item_book_completions`), `157_item_book_completion_points.sql`·`178_slot_item_into_book_completion_basis.sql`(`slot_item_into_book`), `jam-web/src/lib/itembook/`(`checker.ts`, `completable.ts`, `completion-basis.ts`, `filled-by-book.ts`, `slotReward.ts`, `visibility.ts`), `jam-web/src/app/api/itembooks/[id]/slot/route.ts`, `jam-web/src/app/api/itembooks/route.ts`, `jam-web/src/app/api/users/[username]/itembooks/route.ts`, `jam-web/src/app/api/admin/itembooks/[id]/route.ts`, `jam-web/src/lib/admin/reference-guards.ts`. 정확한 줄 위치는 1회 시작 때 아현이 확인한다.

## 배경 / 문제 정의

지금 컬렉션은 아이템 배지 단위로 칸을 채우고, 완성은 컬렉션마다 한 번 기록하며, 완성 포인트와 보상 배지 칸도 컬렉션마다 하나다.
JAM 2.0은 컬렉션마다 9종(이름)이 있고 같은 이름의 아이템 배지가 Common, Rare, Epic, Mystic 4개로 있다. 유저가 처음 꽂은 등급을 따르고, 완성과 보상은 등급마다 한 번씩이다(8.3절).
비교표 5.2절의 A는 "등급마다 컬렉션을 따로 만든다"는 대안이었으나 사용자가 원안(한 칸 4등급)대로 개발하기로 했다(2026-10-10).
또 지금은 장착할 때, 보상을 줄 때, 동기화 보정 때, 화면에서 완성을 서로 다르게 센다(비교표 3.8절). 하나로 모은다.

**공용 DB 주의.** `slot_item_into_book`은 프로덕션 코드가 지금도 호출한다. 이 함수와 `user_item_book_completions`는 바꾸지 않고, 새 함수와 새 테이블을 덧붙인다.
옛 것을 지우는 축소는 묶음 6의 전환 단계에서 한다.

## 사용자 결정 (2026-10-17, 질문창, 모두 추천안)

1. **한 칸 묶기**: 같은 컬렉션(`badges.item_book_id`) 안에서 **이름(`badges.name`)이 같은 아이템 배지 4장**을 한 칸으로 본다. 새 테이블을 두지 않는다. 어드민은 지금처럼 배지를 컬렉션에 넣기만 하면 된다.
2. **컬렉션 등급은 저장하지 않는다.** 그 유저가 그 컬렉션에 지금 꽂아 둔 아이템 배지의 등급(`badges.rarity`, 열거형 `badge_rarity`: common·rare·epic·mystic)이 곧 컬렉션 등급이다. 다 빼면 저절로 풀린다.
3. **등급별 완성 기록과 보상은 새 테이블에 둔다.** 옛 `user_item_book_completions`와 `item_books.reward_points`·`reward_badge_id`는 그대로 둔다.
4. **새 구조는 컬렉션의 표시 칸으로 켠다.** `item_books.tier_mode`(기본 false)가 켜진 컬렉션에만 새 규칙을 적용하고, 지금 컬렉션(켜진 30개)은 옛 규칙 그대로다. 새 구조 컬렉션은 어드민에서 하나씩 켠다(어드민 화면의 켜는 칸은 묶음 7).

### 가정 (카리나가 정했고 SQL 실행 승인 전에 다시 확인한다)

- **등급별 보상의 기본값**: 컬렉션마다 등급별 보상 행이 없으면 기본값을 쓴다. 기본값도 설정 테이블의 행으로 두어 어드민에서 고칠 수 있게 한다(커먼 100, 레어 200, 에픽 400, 미스틱 800, 운영 로직 8.6절). 보상 배지는 컬렉션마다 정하며 없으면 주지 않는다.
- **등급별 완성의 분모**: 그 컬렉션에서 그 등급의 아이템 배지가 있는 **이름 수**다. 지금 `completion-basis.ts`의 드랍 제외 규칙(`drop_excluded`)과 같은 방식으로 제외분을 뺀다. 새 구조 컬렉션의 9종 모양을 가정하되 코드에 9를 박지 않는다.
- **교환(`swap_item_in_book`)**: 새 구조 컬렉션에서는 같은 등급끼리만 바꿀 수 있다. 등급을 바꾸려면 빼고 다시 꽂는다. 정책 문서에 없어 이 방식으로 정했고, 사용자가 다르게 원하면 이 규칙만 바꾼다.
- **옛 컬렉션과 새 구조 컬렉션은 호출 경로가 다르다**: 새 구조 컬렉션은 새 함수(`slot_item_into_book_tiered`), 옛 컬렉션은 지금 함수를 그대로 부른다. 프로덕션 코드는 지금 함수를 계속 부르므로 옛 함수는 바꾸지 않는다.

## 상세 요구사항

### 서비스/코드베이스 관점

- **데이터(회차 1, SQL 추가만)**:
  - `item_books.tier_mode BOOLEAN NOT NULL DEFAULT false`(칸 추가).
  - `item_book_tier_rewards`: `(item_book_id, tier)`가 키, `tier`는 `badge_rarity`, 보상 포인트(비우면 기본값), 보상 배지(비울 수 있음). 클라이언트 정책 없음.
  - `item_book_tier_default_rewards`: `tier`가 키, 기본 보상 포인트. 초기값 100·200·400·800.
  - `user_item_book_tier_completions`: `(user_id, item_book_id, tier)`가 키, 완성 시각. 본인만 읽는다.
  - 함수 `slot_item_into_book_tiered(p_user_id, p_item_book_id, p_inventory_item_id)`와 `swap_item_in_book_tiered(...)`: 옛 함수(`111`, `151`, 가장 최근 정의 `179`)의 검사와 반환 모양을 그대로 따르고 새 규칙만 더한다. `tier_mode`가 꺼진 컬렉션이면 거절한다.
- **장착 규칙**: 그 컬렉션에 이미 꽂힌 것이 있고 새로 꽂는 아이템 배지의 등급이 다르면 거절(`tier_mismatch`). 같은 이름은 컬렉션마다 하나(같은 등급이므로 같은 배지 중복 검사가 막는다). 기존 규칙은 그대로다: 인벤토리 소유, 이미 드랍됨, 이미 꽂힘, 다른 컬렉션 배지.
- **완성**: 그 등급으로 이름 칸을 모두 채우면 그 등급의 완성이다. `user_item_book_tier_completions`에 한 번만 기록하고(키가 막는다) 보상을 한 번만 준다. 포인트는 `award_points`(기존 사유 `item_book_completion_point_reward`)로, 보상 배지는 옛 함수가 하는 방식을 그대로 따른다. 장착을 풀어도 완성 기록은 남고, 다시 채워도 같은 등급 보상은 나가지 않는다.
- **완성 판정 통일(회차 2)**: 장착, 보상, 동기화 뒤 보정, 화면 표시가 같은 하나의 판정을 쓴다. DB 함수(회차 1)와 `jam-web/src/lib/itembook/`의 판정 모듈이 같은 결과를 내야 한다.
- 장착한 아이템 배지는 드랍·믹스에 쓸 수 없고, 인벤토리가 가득 차면 장착을 풀 수 없으며, 공개 기간이 끝난 컬렉션에도 꽂아 완성할 수 있다는 기존 규칙은 바뀌지 않는다.
- 잠긴 아이템 배지는 꽂을 수 없다(잠김 자체는 묶음 3이므로 지금은 검사 자리만 둔다).
- 챕터 점수 가산(`chapter_add_score`)은 묶음 5에서 이 완성 이벤트에 연결한다. 이 티켓은 연결하지 않는다.

### UI/UX 관점 (해당 시)

- 컬렉션 화면 표시는 묶음 3이다. 이 티켓은 기존 화면이 새 API를 읽어도 깨지지 않게 응답 모양을 호환시키는 데까지만 한다(회차 3).

## 구현 계획 (회차)

규모가 커서 처음부터 3회로 나눠 돌리고 회마다 게이트를 돌린다. 요약은 2,500자 이내, 상세 목록은 커밋 본문에 둔다.

### 1회: DB 추가 (SQL과 문서만)

규모 사전 판정: SQL 한 파일이 칸 1개, 테이블 3개, 함수 2개, 초기값, 되돌림 SQL을 합쳐 300줄 안팎이라 `plan_only` 임계값(100줄 이상)을 넘는다. 사용자가 결정을 모두 답했고 아래가 파일 단위 계획이라 첫 호출부터 `planOnlyWaiver`를 넘긴다.

1. `jam-web/supabase/migrations/222_item_book_tiers.sql`(새 파일, 추가만): 위 「데이터」의 칸, 테이블, 함수, 초기값. 파일 끝 되돌림 SQL 주석 블록. 인자 수를 나중에 바꾸지 않도록 두 함수의 시그니처를 확정한다. 기존 객체는 건드리지 않는다.
   - 읽을 것: `jam-web/supabase/migrations/179_slot_item_into_book_all_excluded_fallback.sql`(가장 최근 장착 함수), `157_item_book_completion_points.sql` 135행 이하(완성 보상 지급 방식, 보상 배지 부분은 179 이후 정의를 따른다), `111_item_slot_atomic_rpc.sql`(`unslot_item_from_book` 153행, 권한 회수 210행 이하), `151_item_slot_swap_atomic_rpc.sql`(`swap_item_in_book` 47행), `017_item_book_slots.sql`(슬롯·완성 테이블), `220_jam_ledger.sql`·`221_chapters.sql`(이번 묶음의 같은 방식 파일).
2. `docs/service/prd/02_DATA_MODEL.md`: 컬렉션 등급 구조를 반영한다.
3. 이 회차에서 아현은 SQL과 문서만 쓴다. 실행, 롤백 실측, 타입 갱신은 카리나가 한다.

### 2회: 완성 판정 모듈 통일 (코드)

`jam-web/src/lib/itembook/`(`completion-basis.ts`, `checker.ts`, `completable.ts`, `filled-by-book.ts`, `slotReward.ts`, `visibility.ts`)의 판정을 하나로 모아, 새 구조(등급별 이름 칸)와 옛 구조를 모두 처리하고 장착·보상·동기화 뒤 보정·화면 표시가 같은 모듈을 부르게 한다. 지금 서로 다른 분모와 분자 계산을 테스트로 고정한다. 파일 수는 시작 때 다시 판정한다.

**2회 시작 때 볼 호출 지점(2026-10-17 `git grep`, 테스트와 생성 타입 제외, 시작 때 다시 확인)**: 판정 모듈 `src/lib/itembook/`(`completion-basis.ts`, `checker.ts`, `completable.ts`, `filled-by-book.ts`, `slotReward.ts`). 화면 `src/app/(main)/badges/page.tsx`, `(main)/collections/[id]/page.tsx`, `(main)/[username]/collections/page.tsx`. API `src/app/api/itembooks/route.ts`, `api/users/[username]/itembooks/route.ts`, `api/admin/itembooks/[id]/route.ts`. 그 밖에 완성 기록을 읽는 곳 `src/lib/today/{cards,exposure,status}.ts`, `src/lib/notifications/batch/{collections,following}.ts`, `src/lib/badge-engine/jamActionCompletionMetrics.ts`, `src/lib/admin/{user-actions,reference-guards,opsSignals/load,opsInbox/execute/endImpact,registerChecks/references}.ts`. 이 가운데 **완성을 직접 세는 곳**과 **옛 완성 기록 테이블만 읽는 곳**을 먼저 나눠, 판정 통일 대상(세는 곳)과 새 구조 호환 대상(읽는 곳)을 구분한다.

#### 2회 시작 판정 (2026-10-17, 카리나, 사용자 승인: 추천 범위)

**범위 결정(사용자)**: 드랍 엔진은 분모 함수 `buildBadgeIdsOfBook`만 공유하고 드랍 선정 로직은 건드리지 않는다. DB 함수 `slot_item_into_book`(179)과 `slot_item_into_book_tiered`(222)는 코드와 같은 사례표로 일치 테스트를 만들어 고정한다. `visibility.ts`는 대상이 아니다.

**호출 지점 분류 (`git grep`과 코드 열람)**
- 직접 세는 곳(통일 대상): `itembook/completion-basis.ts`(원천), `checker.ts`, `completable.ts`, `filled-by-book.ts`, 화면 `badges/page.tsx`·`collections/[id]/page.tsx`·`[username]/collections/page.tsx`, API `api/itembooks/route.ts`·`api/users/[username]/itembooks/route.ts`, `today/status.ts`·`exposure.ts`·`cards.ts`(분모만), `notifications/batch/collections.ts`.
- 옛 기록만 읽는 곳(판정 변경 없음, 호환 확인과 기록만): `itembook/slotReward.ts`(3회), `badge-engine/jamActionCompletionMetrics.ts`(묶음 5), `admin/opsSignals/load.ts`, `admin/opsInbox/execute/endImpact.ts`(묶음 7), `notifications/batch/following.ts`, `admin/user-actions.ts`·`reference-guards.ts`·`registerChecks/references.ts`, `api/admin/itembooks/[id]/route.ts`(3회에서 칸 보존 확인).

**실측으로 드러난 위치별 불일치 (비교표 3.8절, 티켓 20260921_1114)**
1. 소프트 삭제 배지: `checker`·`completable`은 분모에 넣고, 179·222 SQL과 화면·API·today·알림은 뺀다. 지금 DB는 컬렉션 100개 중 70개에 삭제 배지가 있고 삭제된 아이템 배지가 630개다.
2. 분모 배지 종류: 화면·API·today 일부는 `item`만, `checker`·`completable`·`collections/[id]`는 `item`+`checkin`, 179 SQL은 종류 구분이 없다. 지금 DB에서 컬렉션에 속한 체크인 배지는 0개다.
3. 분자 집합: `checker`·`completable`은 컬렉션별, 화면 3곳·API 2곳·today 2곳·알림은 모든 칸의 배지 id를 한 집합으로 묶는다.
4. 완성 표시: 화면과 API는 `옛 완성 기록 있음 || 계산상 완성`으로 섞는다.

**가정(카리나가 정했고 사용자에게 알린다, 되돌리려면 이 규칙만 바꾼다)**
- 통일 기준은 실제로 완성 기록을 남기는 DB 함수(179·222)다: 소프트 삭제 배지는 분모에서 빼고, 분모 배지 종류는 `item`+`checkin`이며, 분자는 컬렉션별로 센다.
- 영향 실측(공용 DB, 읽기 전용): 위 규칙으로 바꿔도 완성 여부가 달라지는 유저가 없다. 기존 장착 96건 가운데 분모를 다 채운 곳은 이미 완성 기록이 있는 2곳뿐이고, 체크인 배지는 컬렉션에 0개다. 20260825_025의 「삭제 배지도 분모에 고정」 정책은 이 통일로 뒤집히므로 티켓 20260921_1114를 이 결정으로 닫는다.
- `tier_mode` 컬렉션은 분모를 「그 등급의 이름 수」로 세고(222와 같게, 그 등급이 전부 드랍 제외이면 제외 없이 센다), `checker`의 동기화 보정은 `tier_mode` 컬렉션에 옛 완성 기록을 쓰지 않는다(등급별 완성은 새 함수가 기록한다). 지금 `tier_mode` 컬렉션은 0개라 영향이 없다.

**회차 분할**: 한 번에 열 파일이 넘고 테스트와 SQL까지 포함하면 상한을 크게 넘으므로 2회를 둘로 나눠 돌린다. 요약은 2,500자 이내.
