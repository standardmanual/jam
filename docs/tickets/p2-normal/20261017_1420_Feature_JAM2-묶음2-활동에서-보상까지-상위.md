# [Feature] JAM 2.0 묶음 2: 활동에서 보상까지 (동기화 입구 거르기, Strava 연결, 잼 정산, 아이템 배지 발급, 가득 참 보류, 이용 정지)

## 핵심 요약

- 요구사항: 운영 로직 문서 3장(연동과 동기화), 4장(잼), 6장(아이템 배지 발급), 16장(어뷰징과 제재)을 코드로 옮긴다. 동기화하면 인정되는 활동만 걸러 남기고, 잼이 쌓이고, 소속 트라이브의 아이템 배지가 나오며, 인벤토리가 가득 차면 보상을 보류한다. 비교표 4.1절의 Strava 문제 세 건(걸러진 활동 저장, 다른 계정 재연결, 토큰 실패 표시)을 함께 고친다.
- 구현 계획: 하위 티켓 6개를 아래 순서로 하나씩 진행한다. 하위 티켓마다 시작 전에 주요 결정을 질문창으로 묻는다. 큰 티켓은 처음부터 회차로 나눠 돌리고 회마다 게이트를 돌린다.
- 관련 파일: `jam-web/src/lib/strava/sync.ts`(동기화 본체), `jam-web/src/lib/drop-engine/`(아이템 배지 발급), `jam-web/supabase/migrations/220_jam_ledger.sql`(잼 원장), `jam-web/src/lib/abusing/`(섀도우밴과 어뷰징 정책). 하위 티켓마다 함수와 줄 위치를 적었다.

## 배경 / 문제 정의

묶음 1에서 잼 원장, 챕터 저장, 컬렉션 4등급 구조를 DB에 더했다(20261016_2337). 이제 동기화가 그 위에 올라서야 유저가 잼을 받고 새 규칙의 아이템 배지를 받는다.
코드 조사(2026-10-17)에서 확인한 현재 상태는 다음과 같다. 근거 줄 위치는 각 하위 티켓에 있다.

- 활동을 거르는 단계가 한 곳에 없고 흩어져 있다. 가상 활동은 정상 종목으로 처리하고, 수동 입력과 파일 업로드는 가리지 않으며, 차량 속도로 걸러진 활동도 활동 기록에 저장되어 다음 평가부터 이력으로 다시 들어간다. 장소 체크인은 속도 필터보다 먼저 돈다.
- 잼 원장 함수(`jam_apply`)는 있지만 서비스 코드에서 부르는 곳이 없다.
- 드랍 엔진은 유저의 소속 트라이브(`users.tribe_id`)를 읽지 않고, 트라이브를 고르는 규칙 전체와 등급 보정 셋, 최근 3건 상한이 들어 있다. 인벤토리가 가득 차면 드랍을 버린다.
- 이용 정지 개념이 없다. 섀도우밴은 등급 확률만 낮추고 동기화를 막지 않는다.
- Strava 토큰 갱신이 실패해도 연결 행이 남아 홈이 «연결됨»으로 보인다. 다른 계정을 연결해도 «첫 동기화 완료» 표시(`users.initial_sync_done`)가 그대로다.

## 사용자 결정 (2026-10-17, 질문창, 모두 추천안)

1. **하위 티켓 6개로 나누고 2-1부터 시작한다.** 거르기가 모든 정산의 입구라서 가장 먼저 한다.
2. **중복 연결은 안내와 취소만 지금 만든다.** 이미 다른 JAM 계정에 연결된 Strava 계정을 연결하려 하면 확인 화면에서 세 가지 안내를 보여 주고 취소만 가능하게 한다. 기존 계정을 지우는 «그래도 연결하기»는 묶음 6의 탈퇴 구현(17장) 뒤에 잇는다.
3. **잠긴 채 배정(25%)은 묶음 3에서 한다.** 개체의 잠김 구조가 묶음 3이므로 이 묶음의 아이템 배지 발급은 잠김 없이 나온다.
4. **조정할 값은 설정 테이블 행으로 둔다.** 강도 배율, 아이템 배지 개수와 등급 확률 같은 값은 DB 설정 테이블 행에 기본값을 넣고 코드가 읽는다. 어드민 화면은 묶음 7에서 만든다. 지금 값을 고치려면 SQL로 바꾼다.

## 진행 원칙

상위 티켓 20261016_2335의 진행 원칙을 그대로 따른다. 특히 다음이 걸린다.

1. DB는 staging과 프로덕션이 공용이고 프로덕션 코드는 옛 서비스다. 옛 프로덕션 코드가 지금도 `users.initial_sync_done`, `user_shadow_bans`, `strava_activities`, `drop_policy`를 읽고 쓴다. 이 묶음은 새 칸·새 테이블·새 설정 행을 **덧붙이기만** 하고 기존 칸의 뜻을 바꾸지 않는다.
2. DB 실행은 사용자 승인 뒤 카리나가 한다(아현은 SQL 파일 작성까지). 실행 전에 파일명, 영향 범위, 되돌림 SQL 위치를 말하고 채팅에서 승인을 받는다.
3. 동기화 흐름은 공용 DB의 실제 유저 활동을 읽는다. staging에서 시험할 때 실제 유저의 데이터를 바꾸는 호출을 하지 않는다. 시험은 롤백 조건 또는 테스트 계정으로 한다.
4. 화면이 들어가는 하위 티켓(2-2, 2-5, 2-6)은 시작 전에 채원의 사전 판정을 받는다. 완성된 새 디자인이 있으면 그대로 구현한다(진행 노트 규칙 15, 16). 어드민은 shadcn/ui 표준을 따른다.
5. staging에 쌓고 `/jam-ship`은 하지 않는다.
