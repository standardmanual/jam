# [BadgeEngine] JAM 2.0 동기화로 받는 아이템 배지를 소속 트라이브 기준으로 발급한다

## 핵심 요약

- 요구사항: 운영 로직 6.1~6.3·6.5~6.7절의 동기화 발급을 만든다. 소속 트라이브 컬렉션에서만 발급하고, 개수는 활동마다 1개 확정(등산 2개)에 보너스 두 번(한 번마다 그 활동의 잼 ÷ 600, 최대 25%), 등급은 동기화 등급 확률(Common 84%, Rare 13%, Epic 2.5%, Mystic 0.5%)과 «Common 10번 연속이면 다음은 Rare 이상» 보정 하나, 아이템 배지는 그 등급에서 발급할 수 있는 후보 전체에서 무작위다. 트라이브를 고르는 규칙 전체와 등급 보정 셋, 컬렉션 쪽 보정, 최근 3건 상한을 없앤다.
- 구현 계획: 2회로 나눈다. 1회는 순수 판정 모듈(개수·등급·후보 선택)과 설정 행·발급 기록 SQL, 확률 시험이고, 2회는 동기화 연결과 옛 규칙 삭제다. 잠긴 채 배정은 이 티켓에 없다(묶음 3).
- 관련 파일(2026-10-17 조사, 시작 때 아현이 줄 위치를 다시 확인한다):
  - `jam-web/src/lib/drop-engine/index.ts`: `tryItemDrop`(568), `selectBadge`(311), 온보딩 첫 3드랍 제한(329-335), `applyShadowBanCap`(472), `insertDrop`(494, RPC `grant_inventory_item`), 가득 참 사전 확인 `isInventoryFull`(624), 639.
  - `jam-web/src/lib/drop-engine/layers.ts`: `rollRarityV2`(26, 복귀·연속 보정·일일 하향·주간 첫 활동 배수 포함), `rollBonusDrop`(76), `pickTribe`(129, 미스터리 → 맥락 → 모멘텀·인접·탐험), `pickBook`(188, 마지막 조각 보정). `context.ts`(맥락 규칙), `constants.ts:29`(걷기 가중 0.4), `policy.ts:38`(DB `drop_policy` 읽기, 실패 시 기본값).

## 배경 / 문제 정의

지금 드랍 엔진은 유저의 소속 트라이브를 읽지 않고, 처음 몇 번의 드랍에서 후보를 좁히는 온보딩 규칙, 쉬다 돌아온 날·추운 날·새벽 같은 맥락 규칙, 직전·이웃·탐험 규칙으로 트라이브를 고른다. 특수 트라이브(미스터리 헌터, 작심삼일 클럽)와 코드에 고정된 트라이브 UUID가 있다. 등급은 보정 셋 세 개와 컬렉션 쪽 보정(완성률, 직전 컬렉션, 없는 것 먼저, 마지막 조각)으로 움직인다. 새 활동 가운데 최근 3건만 드랍하고, 동기화로 받은 아이템 배지의 기한을 공개 종료일로 둔다.
JAM 2.0은 소속 트라이브로 고정하고 보정을 하나만 둔다(6.2절). 개수는 잼에 비례한다. 설정 값(드랍 확률, 인벤토리 칸 수)은 지금 DB 설정 테이블(`drop_policy` 등)에 있는데, 옛 프로덕션 코드가 같은 행을 읽는다.

공용 DB 주의: 옛 `drop_policy`와 옛 드랍 엔진을 쓰는 프로덕션 코드가 있다. 이 티켓은 옛 설정 행의 값을 바꾸지 않고 새 설정 행을 더한다. 드랍 엔진 코드 가운데 캡슐(묶음 3), 시스템 드랍(묶음 4)이 같은 함수를 재사용할 부분은 지우지 않고, 동기화 전용 규칙만 정리한다. 삭제 범위는 시작 때 호출처를 조사해 정한다.

## 시작 전에 사용자에게 확인할 것 (주요 결정, 질문창)

1. **`users.tribe_id`가 비어 있는 기존 유저의 동기화 발급**: 운영 로직은 트라이브를 고르지 않은 유저가 동기화할 수 없다고 한다(3.4절, 2장). 온보딩은 묶음 6이므로, 그때까지 소속이 없는 유저의 아이템 배지 발급을 어떻게 할지(발급하지 않고 알림 / 임시 규칙). 시작 때 공용 DB에서 `tribe_id`가 비어 있는 유저 수를 읽기 전용으로 센 뒤 묻는다.
2. **일련번호의 겹침 판정 단위**: 6자리 번호 상한(999,999)이 있어 번호의 범위나 겹침을 판정하는 단위를 정해야 한다(6.3절). 지금처럼 «파괴되지 않은 개체 사이에서 유일»을 유지할지, 믹스·탈퇴로 없어진 번호도 다시 쓰지 않도록 바꿀지(운영 로직은 다시 쓰지 않는다고 한다. 이 경우 번호 이력 저장이 필요하다).
3. **동기화 등급 보정 카운터의 저장 위치**: «Common 10번 연속이면 다음은 Rare 이상»은 동기화와 캡슐을 합쳐 센다. 캡슐은 묶음 3이므로 카운터를 유저별 한 곳에 저장하고 캡슐이 나중에 같은 값을 쓰게 한다. 새 칸을 어디에 둘지(유저 상태 테이블에 칸 추가를 추천).
4. **발급 기록 테이블**: 6.6절의 기록(경로, 대상 활동, 등급, 잠김 여부, 일련번호)을 새 테이블에 둔다. 칸 구성은 시작 때 정한다.

## 사용자 결정 (2026-10-17, 질문창, 모두 추천안)

묶음 2 상위 티켓의 결정(잠긴 채 배정은 묶음 3, 조정 값은 정책 테이블 행)에 더해 이 티켓 시작 때 아래 네 가지를 정했다.

1. **소속 트라이브(`users.tribe_id`)가 비어 있는 유저는 아이템 배지를 발급하지 않고 건너뛴다.** 잼 정산 등 다른 보상은 정상이다. 2026-10-17 공용 DB 조회에서 유저 8명 가운데 `tribe_id`가 채워진 유저는 0명이고 Strava 연결 유저 4명도 모두 비어 있다(온보딩 개편은 묶음 6). 그래서 온보딩 전까지 staging에서 아이템 배지를 받으려면 시험 계정의 `tribe_id`를 직접 넣어야 한다.
2. **일련번호는 지금 방식을 유지한다.** 파괴되지 않은 개체 사이에서 유일하게 무작위로 받는다(`trg_random_serial`, `assign_random_serial`). 살아 있는 개체 914개, 최대 번호 999,682라 충돌 확률이 거의 없다. 믹스·탈퇴로 없어진 번호도 다시 쓰지 않는 규칙(운영 로직 6.3절)은 개체가 많아질 때 정하고, 재검토 기준(살아 있는 개체가 약 50만 개에 가까워질 때)을 잔여 이슈에 남긴다.
3. **등급 연속 보정 카운터는 기존 `user_drop_state.common_streak`를 재사용한다.** 새 칸이 필요 없고 캡슐(묶음 3)도 같은 칸을 쓰면 합산이 된다. 옛 프로덕션 드랍 엔진도 같은 칸을 읽고 쓰므로 staging에서 시험할 때 값이 섞일 수 있다.
4. **발급 기록은 새 테이블 `item_issue_log`에 남긴다.** append-only, 경로·대상 활동·등급·잠김 여부·일련번호. 옛 인벤토리 함수와 개체 테이블은 바꾸지 않는다.
5. **(2회 시작 때) 뽑힌 등급에 후보가 없으면 한 등급씩 내려 다시 뽑는다**(추천안). 후보가 있는 가장 높은 등급까지 내려가며, 확정으로 받을 개체가 사라지지 않게 한다. 발급 기록에는 처음 뽑힌 등급(`rolled_rarity`)과 실제로 준 등급(`rarity`)을 함께 남겨 운영이 컨텐츠 채움 상태를 볼 수 있게 한다.

**DB 실행 기록(2026-10-17, 2회 준비)**: 사용자 승인 뒤 마이그레이션 228(`228_item_issue_log_rolled_rarity.sql`)을 공용 DB에서 롤백 실측(새 칸 1개, NULL 허용, 기록 0행, 롤백 뒤 칸 0개)하고 적용했다. 적용 뒤 확인: `item_issue_log.rolled_rarity`는 `badge_rarity`·NULL 허용·기본값 없음이고 기록은 0행이다. 생성 타입에 반영했고 `npm run typecheck`를 통과했다. 되돌림 SQL은 파일 끝 주석에 있다.

**DB 실행 기록(2026-10-17, 1회 준비)**: 사용자 승인 뒤 마이그레이션 227(`227_item_issue_policy_and_log.sql`)을 공용 DB에서 롤백 실측(기본값 1/2/2/600/0.25/84/13/2.5/0.5/10, 등급 합계가 100이 아닌 값은 제약이 거절, 기록 테이블 RLS 켜짐·0행, 롤백 뒤 새 칸·테이블 없음)하고 적용했다. 적용 뒤 확인: `jam_policy`의 새 칸 10개가 기본값이고 기존 칸(`intensity_light` 1)은 그대로, `item_issue_log`는 RLS 켜짐·정책 0개·0행이다. 생성 타입에 같은 모양으로 반영했고 `npm run typecheck`를 통과했다. 되돌림 SQL은 파일 끝 주석에 있다.

## 상세 요구사항

### 서비스/코드베이스 관점

- **소속 트라이브 고정**: 발급 후보는 유저의 소속 트라이브 컬렉션뿐이다. 트라이브가 바뀌면 그 뒤 동기화부터 새 트라이브 것이다.
- **개수**: 인정되는 활동마다 1개 확정(등산은 2개), 보너스를 두 번 굴린다. 한 번마다 확률은 그 활동의 잼 ÷ 600이고 최대 25%다. 개수 0개도 설정으로 둘 수 있다.
- **등급**: 동기화 등급 확률로 정하고 보정은 «Common 10번 연속이면 다음은 Rare 이상» 하나다(동기화와 캡슐 합산 카운터). 보정 셋 세 개(쉬고 돌아온 날, 그 주의 첫 활동, 하루 4번째부터)는 없앤다.
- **아이템 배지**: 소속 트라이브 컬렉션에서 그 등급으로 발급할 수 있는 후보(활성이고 공개 기간 안이며 드랍 제외가 아닌 것) 전체에서 무작위로 고른다. 없는 것 먼저, 컬렉션 비중, 마지막 조각 몰아주기 보정은 없앤다.
- **없애는 규칙**: 트라이브를 고르는 규칙 전부(온보딩 첫 3드랍 제한, 맥락 규칙, 직전·이웃·탐험 규칙), 특수 트라이브와 고정 UUID(이미 가진 유저의 기록은 지우지 않는다), 최근 3건 상한(처리하는 활동 수에 상한을 두지 않는다), 동기화로 받은 아이템 배지의 기한을 공개 종료일로 두는 규칙. 섀도우밴 등급 상한(`applyShadowBanCap`)은 2-6의 이용 정지와 정리한다.
- **공개 기간이 끝난 아이템 배지는 새로 발급하지 않는다**(6.5절).
- **일련번호**: 지금 방식을 유지한다(사용자 확인 2번에 따라 판정 단위만 정한다). 믹스·탈퇴로 없어진 개체의 번호를 다시 쓰지 않는 규칙이 필요하면 번호 이력 저장을 더한다.
- **설정 값**: 개수 값(확정 개수, 보너스 횟수, 분모 600, 상한 25%), 등급 확률, 보정 임계(10)를 설정 테이블 행으로 둔다(사용자 결정 4번). 옛 `drop_policy` 행은 바꾸지 않는다. 설정 조회가 실패하면 운영 로직 6.7절의 기본값으로 대체한다.
- **기록**: 아이템 배지를 줄 때마다 경로(동기화), 대상 활동, 등급, 잠김 여부(이 티켓은 항상 잠기지 않음), 일련번호를 새 테이블에 기록한다.
- 인벤토리가 가득 찼을 때의 처리는 2-5가 다룬다. 이 티켓에서는 지금의 «버림» 동작을 그대로 두되, 2-5가 끼울 수 있도록 발급을 «후보 선정»과 «지급» 두 단계로 나눈다.
- 유저가 받은 개체의 잼 연계 포인트(`badge.point_reward` → 구 포인트)는 바꾸지 않는다(14장, 묶음 5).

### UI/UX 관점 (해당 시)

- 화면은 만들지 않는다. 동기화 응답의 `earnedBadgeIds`에 아이템 배지가 합쳐지는 현재 계약은 그대로 둔다.

## 구현 계획 (회차)

규모가 커서 처음부터 2회로 나눠 돌리고 회마다 게이트를 돌린다. 시작 때 파일 단위 계획을 이 절에 옮겨 쓰고 `planOnlyWaiver`를 넘긴다. 유형은 `engine`이라 SQL 실행 승인과 문서 대조(엔진 문서)가 붙는다. 요약은 2,500자 이내.

### 1회: 순수 판정 모듈, 설정 행과 발급 기록 SQL, 확률 시험
### 2회: 동기화 연결과 옛 규칙 삭제

#### 2-4 구현 계획 (2026-10-17, 카리나, 파일 단위)

DB는 227 적용과 생성 타입 반영을 카리나가 끝냈다. 아현은 코드·시험·문서만 한다. 줄 위치는 2026-10-17 `staging` 기준이며 시작 때 아현이 다시 확인한다. 각 회차는 파일이 5개를 넘어 `planOnlyWaiver`를 첫 호출부터 넘긴다. `workType`은 `engine`이다(확률 시험이 근거다).

## 완료 조건

### 구현 범위 (게이트 판정 대상, 회차마다 해당 항목)

- (1회) 개수·등급·후보 선택이 순수 함수로 분리되어 있고, 시뮬레이션 시험으로 분포를 고정한다: 개수는 활동마다 1~3개이고 등산은 최소 2개, 60분 걷기 평균이 운영 로직 6.7절의 값 가까이(약 1.2개)이며, 등급 확률이 설정 값과 오차 범위 안에서 일치하고, Common 10연속 다음은 Rare 이상이다.
- (1회) 후보는 소속 트라이브 컬렉션에서 활성이고 공개 기간 안이며 드랍 제외가 아닌 배지뿐이다. 다른 트라이브의 배지가 후보에 들지 않는 시험이 있다.
- (1회) 마이그레이션이 옛 테이블·옛 함수·옛 설정 행을 바꾸거나 지우지 않고, 새 설정 행·발급 기록 테이블만 더하며 되돌림 SQL을 싣는다.
- (2회) 동기화가 새 판정 모듈로 발급하고, 트라이브를 고르는 규칙, 보정 셋, 컬렉션 쪽 보정, 3건 상한, 공개 종료일 기한이 동기화 경로에서 쓰이지 않는다. 확인 방법은 동기화 경로에서 옛 규칙 함수를 호출하는 코드가 없음을 검색한 시험이다. 캡슐·시스템 드랍이 재사용할 함수는 지우지 않았음을 호출처 검색 결과로 밝힌다.
- (2회) 아이템 배지가 줄 때마다 발급 기록 테이블에 한 줄씩 남는다.
- (2회) 공개 기간이 끝난 배지는 새로 발급되지 않는다.
- (전체) `docs/service/badge-engine/BADGE_ENGINE_UNIFIED.md`가 새 발급 규칙(소속 트라이브, 개수, 등급, 보정 하나)으로 갱신되어 있고, 지운 규칙이 «없어짐»으로 기록되어 있다.

### 후속 범위 (담당: 카리나, 시점: 사용자 승인 뒤)

- 사용자 확인 1~4번의 결정을 이 티켓 「사용자 결정」 절에 기록한다. SQL 실행은 승인과 롤백 실측 뒤에 한다.
- 시험 발급은 테스트 계정 또는 롤백 조건으로만 하고, 실제 유저의 인벤토리를 바꾸지 않는다.
