# [Feature] JAM 2.0 동기화 중 인벤토리가 가득 차면 보상을 보류하고 고르기 화면을 만든다

## 핵심 요약

- 요구사항: 운영 로직 6.4절의 동기화 행을 만든다. 받을 아이템 배지가 빈칸보다 많으면 결과 캐러셀에서 하나씩 보면서 빈칸만큼 고른다. 고르지 않은 것은 받지 못하고 다시 받을 수 없다. 고르기를 마치기 전에 화면을 닫으면 다음에 열 때 고르기 화면을 다시 보여 주고(그동안 받을 배지는 보류), 보류가 있는 동안 동기화 버튼을 누르면 남은 고르기를 먼저 보여 준 뒤 동기화한다.
- 구현 계획: 한 번에 돌리되 규모에 따라 2회로 나눌 수 있다. 화면이 있으므로 시작 전에 채원의 사전 판정을 받는다. DB는 새 테이블 추가만 한다. 미션 보상, 프로모션, 믹스 결과의 «받지 않은 보상» 구조는 묶음 3·5에서 쓰므로, 같은 구조를 확장할 수 있게 설계하되 이 티켓은 동기화 보류만 구현한다.
- 관련 파일(2026-10-17 조사, 시작 때 아현이 줄 위치를 다시 확인한다):
  - `jam-web/src/lib/strava/sync.ts`: 드랍 단계(995-1028), 응답 조립(1338-1349), 반환 타입(1167-1178), 결산 알림(1142).
  - `jam-web/src/lib/drop-engine/index.ts`: 가득 참 사전 확인 `isInventoryFull`(624)과 최종 RPC `slot_full`(마이그레이션 173)이 모두 드랍을 버린다. 2-4가 발급을 «후보 선정»과 «지급»으로 나눈 결과 위에서 작업한다.
  - `jam-web/src/lib/missions/rewards.ts:119`(미션 보상도 가득 차면 버림, 이 티켓에서는 건드리지 않음).
  - 화면: `jam-web/src/components/SyncButton.tsx`(62-100, `earnedBadges.length`가 결과 표시의 유일한 기준), `components/BadgeRevealOverlay.tsx`(결과 오버레이), `components/StravaConnectReveal.tsx`(~125, 콜백 뒤 `/api/badges/recent-earned`로 같은 계약을 읽음), `components/ui/TopNav.tsx:145`와 `OnboardingQuestCard.tsx`(`SyncButton` 배치).
  - 스펙: 운영 로직 6.4·6.6절, 비교표 3.7절.

## 배경 / 문제 정의

지금은 동기화 중 인벤토리가 가득 차면 드랍을 멈추고 알리지 않는다. 사용자가 정한 JAM 2.0 규칙은 «잼을 쓰거나 무언가를 해내서 얻은 보상은 사라지지 않는다»이다. 동기화는 빈칸이 모자라면 유저가 어떤 아이템 배지를 받을지 고르게 하고, 고르는 도중에 나가도 보류를 지킨다.
동기화 결과 응답에는 지금 잼 증가량, 개체 정보, 보류 정보가 없다. 클라이언트는 `earnedBadges` 배열 하나로 결과를 그린다.

## 시작 전에 사용자에게 확인할 것 (주요 결정, 질문창)

1. **보류 저장 구조의 범위**: 동기화 보류만 위한 테이블(추천, 작게 시작)과 미션 보상·프로모션·믹스 결과까지 담는 «받지 않은 보상» 공통 테이블을 지금 만드는 방식. 후자는 묶음 3·5의 설계를 앞당긴다.
2. **고르기 화면의 위치**: 결과 오버레이(`BadgeRevealOverlay`) 안의 한 단계로 넣을지, 별도 화면으로 둘지(채원 판정으로 정한다).
3. **가득 참 표시와 알림**: 인벤토리 메뉴의 가득 참 표시, 남은 칸 3칸·1칸일 때 알림(6.4절)을 이 티켓에 넣을지 묶음 3(인벤토리 화면)으로 둘지(추천: 묶음 3).
4. **고르지 않은 아이템 배지의 기록**: 6.6절의 기록 칸 구성(생긴 때, 받은 때, 고르지 않음 표시).

## 상세 요구사항

### 서비스/코드베이스 관점

- **보류 시점**: 2-4의 발급 단계에서 받을 개수가 빈칸보다 많으면 지급하지 않고 보류 목록(새 테이블)에 기록한다. 빈칸이 충분하면 지금처럼 바로 지급한다.
- **고르기**: 유저가 보류된 후보 중 빈칸만큼 고른다. 고른 것은 지급(`grant_inventory_item`)하고 나머지는 «고르지 않음»으로 기록해 다시 받을 수 없게 한다. 지급은 한 트랜잭션에서 슬롯을 확인한다.
- **재진입**: 고르기를 마치기 전에 닫으면 보류가 남고, 다음에 앱을 열 때 고르기 화면을 다시 보여 준다. 보류가 있는 동안 동기화 버튼을 누르면 남은 고르기를 먼저 보여 주고 마친 뒤에 동기화한다.
- **동시성**: 같은 보류를 두 번 지급하지 않는다(중복 클릭, 두 기기). 지급과 «고르지 않음» 처리를 한 함수로 묶는다.
- **기록**: 보류가 생긴 때와 받은 때, 고르지 않은 것의 기록을 남긴다.
- **응답**: 동기화 응답에 보류 여부와 고르기에 필요한 최소 정보를 더한다. 기존 응답 필드(`earnedBadges` 등)는 그대로 둔다.
- 공개 기간이 끝나도 보류된 것은 공개 기간 안에서 정해진 것이면 받을 수 있다(6.5절).
- 이용 정지 중에는 받지 않은 보상을 받을 수 없다(2-6의 공통 검사를 쓴다).
- 새 테이블은 덧붙이기만 한다. 생성 타입을 같은 커밋에 맞춘다.

### UI/UX 관점 (해당 시)

- 결과 캐러셀에서 하나씩 넘겨 보며 빈칸만큼 고르는 화면, 보류가 있을 때의 재진입 화면, 동기화 버튼의 선처리 동작을 새 디자인으로 구현한다. 채원의 사전 판정을 먼저 받는다. 사용자 노출 문구는 UX 라이팅 가이드(고정 용어 «획득», «인벤토리»)와 `fluent-korean` 지침을 따른다.

## 구현 계획 (회차)

규모를 시작 때 파일 단위로 센다. SQL(새 테이블, 지급·선택 함수)과 서버 코드, 화면 컴포넌트, 시험, 문서를 합치면 5개를 넘을 가능성이 높으므로 필요하면 «서버(보류 저장, 고르기 함수, 응답)»와 «화면(고르기, 재진입)» 2회로 나눈다. `workType`은 `ui`로 돌리고 SQL은 아현이 파일 작성까지만 한다. 요약은 2,500자 이내.

## 완료 조건

### 구현 범위 (게이트 판정 대상, 회차마다 해당 항목)

- 받을 개수가 빈칸 이하이면 이전과 같이 바로 지급되고 보류가 생기지 않는다. 빈칸보다 많으면 지급하지 않고 보류 목록에 기록된다. 사례별 시험으로 고정한다.
- 고르기를 마치면 고른 만큼만 인벤토리에 들어가고 나머지는 «고르지 않음»으로 기록되어 다시 받을 수 없다. 같은 보류를 두 번 지급하지 않는 시험이 있다.
- 고르기를 마치기 전에 닫아도 보류가 남고, 다음에 열 때 고르기 화면이 다시 뜬다. 보류가 있는 동안 동기화 버튼이 고르기를 먼저 보여 준다.
- 마이그레이션이 옛 객체를 바꾸거나 지우지 않고 새 테이블·새 함수만 더하며 되돌림 SQL을 싣는다.
- 동기화 응답의 기존 필드가 그대로이고 화면이 이전 응답에서도 깨지지 않는다.
- (화면) 새 디자인대로 구현되어 있고 채원 사후 리뷰에 중대 문제가 없다.
- (전체) `docs/service/prd/`와 `docs/service/badge-engine/`의 해당 문서에 보류와 고르기 규칙이 반영되어 있다.

### 후속 범위 (담당: 카리나, 시점: 사용자 승인 뒤)

- 사용자 확인 1~4번의 결정을 이 티켓 「사용자 결정」 절에 기록한다. SQL 실행은 승인과 롤백 실측 뒤에 하고, 실제 인벤토리를 바꾸는 시험은 하지 않는다.
- 화면 실렌더 확인은 카리나가 push 전 로컬에서 하거나 staging 배포 뒤에 한다.
