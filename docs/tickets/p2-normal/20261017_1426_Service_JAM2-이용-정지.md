# [Service] JAM 2.0 이용 정지를 만든다: 정지 상태 저장, 동기화 차단, 정지 기간 미정산, 어드민 제재 탭

## 핵심 요약

- 요구사항: 운영 로직 16.1·16.4절의 이용 정지를 만든다. 정지는 운영자만 걸고 풀며, 걸리면 유저에게 안내(까닭, 고객센터 연락 방법)를 보여 준다. 정지 중에는 로그인, 내 기록 보기, 문의만 가능하고 보상이나 기록이 새로 생기는 동작은 막는다. 유저 모르게 등급을 낮추는 섀도우밴 방식은 쓰지 않는다. 이 티켓은 정지 상태 저장, 모든 동작이 쓸 공통 검사 함수, 동기화 차단과 정지 기간 활동 미정산, 어드민 제재 탭, 유저용 정지 안내까지 만든다.
- 구현 계획: 2회로 나눈다. 1회는 정지 상태 저장(SQL)과 공통 검사 함수와 동기화 연결(차단, 정지 기간 활동 미정산), 2회는 어드민 제재 탭과 유저용 정지 안내 화면이다. 화면이 있으므로 시작 전에 채원의 사전 판정을 받는다(어드민은 shadcn/ui 표준).
- 관련 파일(2026-10-17 조사, 시작 때 아현이 줄 위치를 다시 확인한다):
  - 지금의 섀도우밴: `jam-web/supabase/migrations/010_abusing_policy.sql`(`user_shadow_bans`: `user_id UNIQUE`, `ban_level 'soft'|'hard'`, `reason`, `expires_at`, `created_by`), `jam-web/src/lib/abusing/shadow-ban.ts`(`getUserBanLevel`, `shouldAllowDrop`), 읽는 곳: `sync.ts` 797-803(체크인·POI 배지), `drop-engine/index.ts` 472·639(등급 강등), `badge-engine/index.ts` 1417-1426, `usageBadges.ts` 217-222. 모두 «등급별 확률 차단»이며 동기화 자체를 막지 않는다. `users`에는 정지·차단 칸이 없다(`database.generated.ts` 3606-3622).
  - 어드민: `jam-web/src/app/admin/abusing/`(탭 policy, bans, poi-blocks), API `app/api/admin/abusing/bans`(GET, POST, DELETE, `[id]` PATCH, bulk, ids), `lib/admin/user-list.ts:28`(제재 표시).
  - 픽업: `app/api/drops/[dropId]/pickup/route.ts`(75 `isPoiBlocked`, 90-93 GPS 조작 시 `applyBan(soft)`와 POI 블록. 묶음 4가 다룬다).
  - 동기화 차단 위치: `jam-web/src/lib/strava/sync.ts`(`syncStravaActivities` 1167, 수동 경로 `app/api/strava/sync/route.ts`, 콜백 직후 동기화 `callback/route.ts:127`).
  - 스펙: 운영 로직 16.1·16.4·16.7절, 비교표 3.20절.

## 배경 / 문제 정의

지금 서비스에는 이용 정지가 없다. 섀도우밴은 유저 모르게 드랍 등급을 낮추는 방식이라 JAM 2.0의 원칙(16.1절, «제재는 이용 정지 하나»)과 맞지 않는다.
새 규칙은 운영자가 정지를 걸면 유저에게 알리고, 그 시점까지 진행된 것을 멈추며(지우지 않음), 고객센터에서 이야기해 풀거나 유지한다. 정지를 건 시점부터 풀린 시점까지 시작한 활동은 풀린 뒤에 동기화해도 정산하지 않는다.

공용 DB 주의: 옛 프로덕션 코드가 `user_shadow_bans`와 어드민 어뷰징 화면을 쓴다. 이 티켓은 옛 테이블과 옛 어드민 경로를 바꾸거나 지우지 않고 새 테이블을 더한다. 섀도우밴을 읽는 새 코드 경로를 없애는 일은 스테이징 코드에서만 하고, 옛 테이블 삭제(축소)는 묶음 6의 전환 단계에서 한다.

## 시작 전에 사용자에게 확인할 것 (주요 결정, 질문창)

1. **정지 상태의 저장**: 정지를 건 이력(걸고 푼 시각, 운영자, 까닭)을 남기는 새 테이블(추천)과 `users`에 새 칸을 더하는 방식. 이력이 있어야 «정지 기간에 시작한 활동은 풀린 뒤에도 정산하지 않음»을 판정할 수 있다.
2. **정지 안내의 위치**: 앱 진입 시 전면 안내 화면으로 막는지(추천), 홈 상단 배너로 알리는지. 안내에는 정지 사실, 까닭, 고객센터 연락 방법(`문의`)을 둔다.
3. **정지 중 허용하는 동작의 구현 방식**: 공통 검사 함수를 쓰는 «막는 동작» 목록(동기화, 캡슐·잠긴 아이템 배지의 채우기와 열기, 믹스, 드랍, 픽업, 미션 참가, 받지 않은 보상 받기)을 이 묶음의 동기화와 2-5의 받기에만 연결하고 나머지는 각 묶음이 연결하는 것으로 확정한다(추천).
4. **옛 섀도우밴 데이터의 취급**: 지금 `user_shadow_bans`에 있는 행(실제 유저 제재)을 새 이용 정지로 옮길지, 새 코드가 읽지 않고 두기만 할지(추천: 두기만 하고 운영자가 필요하면 새 정지로 다시 건다).

## 상세 요구사항

### 서비스/코드베이스 관점

- **정지 상태**: 운영자만 걸고 푼다. 걸 때 까닭을 적는다. 정지는 끝나는 날 없이 걸고 고객센터에서 이야기한 결과로 푼다(16.7절).
- **공통 검사 함수**: «이 유저가 지금 이용 정지 중인가»를 한 곳에서 판정한다. 동기화, 2-5의 받지 않은 보상 받기가 이 함수를 쓰고, 이후 묶음(캡슐, 믹스, 드랍, 픽업, 미션)도 같은 함수를 쓴다.
- **동기화 차단**: 정지 중에는 동기화할 수 없다(수동 경로와 콜백 직후 동기화 모두). 가진 잼, 아이템 배지, 배지, 포인트는 그대로 둔다.
- **정지 기간 활동 미정산**: 정지를 건 시점부터 푼 시점까지 «시작한» 활동은 풀린 뒤에 동기화해도 정산하지 않는다(어떤 보상도 받지 않는다). 2-1의 인정 활동 판정에 «정지 기간 활동은 인정하지 않음» 조건을 한 줄로 더한다.
- **섀도우밴 경로**: 새 동기화·드랍 코드가 `user_shadow_bans`를 읽는 곳(체크인 판정 `sync.ts:797-803`, `applyShadowBanCap`, 배지 판정 1417-1426, 사용량 배지 217-222)을 정리한다. 유저 모르게 등급을 낮추는 동작은 새 코드 경로에서 쓰지 않는다. 옛 테이블은 지우지 않는다.
- **어드민 제재 탭**: 이용 정지를 걸고 푸는 화면(까닭 입력)과 정지 이력 보기. 기존 어뷰징 화면(`app/admin/abusing/`)의 «제재(bans)» 탭을 이용 정지 기준으로 다시 쓰되 옛 API 경로는 바꾸지 않고 새 경로를 더한다. 유저 목록의 제재 표시(`user-list.ts:28`)를 이용 정지 기준으로 맞춘다.
- **유저용 정지 안내**: 정지 중인 유저가 앱에 들어오면 정지 사실, 까닭, 고객센터 연락 방법을 보여 준다. 정지 중에도 로그인, 내 기록 보기(프로필, 배지, 인벤토리, 컬렉션), 문의는 가능하다.
- 정지 중인 유저를 순위형 미션의 순위에서 빼는 일(13장)은 묶음 5가 한다. GPS 자동 감지의 섀도우밴 삭제와 운영자 알림(16.5절)은 묶음 4가 한다. 어뷰징 기록 3개월 보관과 여러 계정 신호는 묶음 7이다.
- 새 테이블과 함수는 덧붙이기만 한다. 생성 타입을 같은 커밋에 맞춘다.

### UI/UX 관점 (해당 시)

- 유저용 정지 안내 화면은 새 디자인으로 구현한다(채원 사전 판정). 어드민 제재 탭은 shadcn/ui 표준이며 MODULAR 적용 대상이 아니다. 네이티브 `select` 등은 쓰지 않는다. 어드민 실렌더 확인은 카리나가 머지 뒤 push 전에 로컬에서 한다(`ADMIN_EMAILS` 셸 환경변수). 사용자 노출 문구는 UX 라이팅 가이드와 `fluent-korean` 지침을 따른다(정지 안내는 단호하되 해결 방법을 함께 알린다).

## 구현 계획 (회차)

규모가 커서 처음부터 2회로 나눠 돌리고 회마다 게이트를 돌린다. 시작 때 파일 단위 계획을 이 절에 옮겨 쓰고 `planOnlyWaiver`를 넘긴다. 요약은 2,500자 이내.

### 1회: 정지 상태 저장(SQL), 공통 검사 함수, 동기화 연결
### 2회: 어드민 제재 탭, 유저용 정지 안내 화면

## 완료 조건

### 구현 범위 (게이트 판정 대상, 회차마다 해당 항목)

- (1회) 정지 상태와 이력을 저장하는 새 테이블과 함수가 있고, 마이그레이션이 옛 테이블(`user_shadow_bans`)·옛 함수를 바꾸거나 지우지 않으며 되돌림 SQL을 싣는다. 클라이언트 역할은 정지 상태를 쓸 수 없다(권한 시험).
- (1회) 이용 정지 중인 유저는 동기화(수동 경로, 콜백 직후)를 할 수 없고 가진 잼, 아이템 배지, 배지, 포인트는 그대로다. 단위 시험으로 고정한다.
- (1회) 정지 기간에 시작한 활동은 풀린 뒤 동기화해도 어떤 보상도 만들지 않는다. 정지 직전과 직후에 시작한 활동이 정확히 갈리는 경계 시험이 있다.
- (1회) 새 동기화·드랍 코드가 `user_shadow_bans`를 읽지 않는다. 확인 방법은 읽는 곳 검색 결과다(옛 어드민·옛 API의 사용은 남는다).
- (2회) 어드민에서 이용 정지를 걸고 풀 수 있고 까닭이 필수이며, 걸고 푼 이력이 남는다. 어드민이 아닌 유저는 호출할 수 없다.
- (2회) 정지된 유저가 앱에 들어오면 정지 사실, 까닭, 고객센터 연락 방법이 보이고, 로그인과 내 기록 보기와 문의는 막히지 않는다.
- (전체) 비교표 3.20절의 «제재는 이용 정지 하나» 방향이 완료 기록에 반영되어 있고, 남은 섀도우밴 읽기·쓰기 경로가 어디인지(옛 어드민, 픽업 GPS 감지 등)와 어느 묶음이 정리하는지가 잔여 이슈에 적혀 있다.
- (전체) `docs/service/prd/`의 해당 문서(어뷰징·제재)가 반영되어 있다.

### 후속 범위 (담당: 카리나, 시점: 사용자 승인 뒤)

- 사용자 확인 1~4번의 결정을 이 티켓 「사용자 결정」 절에 기록한다. SQL 실행은 승인과 롤백 실측 뒤에 한다. 지금 `user_shadow_bans`에 들어 있는 실제 행의 수와 만료 상태를 읽기 전용으로 세어 사용자 확인 4번 때 보여 준다.
- 어드민 화면 실렌더 확인은 카리나가 머지 뒤 push 전에 한다.
