# [Service] 걸러진 Strava 활동을 필터 없이 읽는 백필과 관리자 통계를 새 인정 규칙에 맞춘다

## 핵심 요약

- 요구사항: 티켓 20261017_1421 1회가 `strava_activities`에 걸러짐 표시(`filter_reason`)를 더하고 이력 조회 함수를 한 곳으로 모았다. 그 함수를 거치지 않고 이 테이블을 직접 읽는 곳이 남아 있어, 걸러진 활동까지 집계하거나 다시 계산한다. 이를 새 인정 규칙에 맞춘다.
- 구현 계획: 한 번에 돌린다. 직접 읽는 곳을 모두 찾아 «인정된 활동만 읽을지, 걸러진 행도 포함할지»를 곳마다 정하고 고친다.
- 관련 파일(2026-10-17 게이트 판독, 시작 때 아현이 줄 위치를 다시 확인한다): `jam-web/src/lib/strava/backfillStats.ts:237`(관리자 통계가 걸러진 행까지 집계), `jam-web/src/lib/strava/backfill.ts:178`(소급 백필이 걸러진 행의 `normalized`까지 다시 계산, 걸러진 가상 종목 활동은 `jamActivityType`이 null이 될 수 있음), `jam-web/src/app/(main)/feed/page.tsx:78`·`app/(main)/[username]/page.tsx:350`(활동 이름 조회, 걸러진 활동은 피드 항목이 없어 영향 없음으로 판독). 스펙: 운영 로직 3.3·3.4절, 티켓 20261017_1421.

## 배경 / 문제 정의

20261017_1421 1회가 걸러진 활동을 사유와 함께 저장하고 이력 조회(`getActivityHistory`)가 `filter_reason IS NULL`인 행만 읽게 했다. 그러나 소급 백필(`backfill.ts`)과 관리자 통계(`backfillStats.ts`)는 이 테이블을 직접 읽는다. 소급 백필이 걸러진 행을 다시 계산하면 걸러진 활동이 이력으로 되살아나거나 종목 값이 바뀔 수 있다.

## 상세 요구사항

### 서비스/코드베이스 관점

- `strava_activities`를 `getActivityHistory`나 `getProcessedStravaIds`를 거치지 않고 읽는 곳을 모두 찾는다(검색 결과를 완료 기록에 싣는다).
- 곳마다 읽는 목적을 따져 «인정된 활동만»(통계, 계산)인지 «걸러진 행 포함»(이미 처리한 id 확인)인지 정한다.
- 소급 백필은 걸러진 행을 다시 계산하지 않는다. 옛 행(`filter_reason`이 NULL)을 소급해 다시 판정할지는 별도 결정이며, 이 티켓에서 하지 않고 필요하면 사용자에게 묻는다.
- 옛 프로덕션 코드가 같은 테이블을 읽으므로 칸의 뜻은 바꾸지 않는다.

## 구현 계획

한 번에 돌린다. 규모가 5개 파일 이하이면 `planOnlyWaiver`는 필요 없다. 요약은 2,500자 이내.

## 완료 조건

- `strava_activities`를 직접 읽는 곳이 목록으로 정리되어 있고, 인정된 활동만 읽어야 하는 곳은 `filter_reason IS NULL` 조건을 쓴다. 확인 방법은 직접 읽는 곳의 검색 결과와 단위 시험이다.
- 관리자 통계가 걸러진 활동을 인정 활동으로 세지 않고, 소급 백필이 걸러진 행을 다시 계산하지 않는 시험이 있다.

## 진행 기록

- 2026-10-23 JAM 2.0 부가 P2 티켓 일괄 처리(jam-work)로 착수한다. 카리나가 최신 `origin/staging`에서 아직 재현됨을 확인했다. 유형 `bug`, 경로 ③ 표준. 규모 사전 판정: 파일 4~6개, 변경 100줄 안팎이다. 구현 계획과 관련 파일에 경로·함수명이 적혀 있고 범위가 한 가지 일이라 `planOnlyWaiver`를 넘긴다. 확인한 사실: `backfill.ts:180`과 `backfillStats.ts:237`이 `strava_activities`를 직접 읽는데, `filter_reason`을 쓰는 파일 목록에 두 파일이 없다. 이 테이블을 직접 읽는 곳은 현재 14곳이다.
