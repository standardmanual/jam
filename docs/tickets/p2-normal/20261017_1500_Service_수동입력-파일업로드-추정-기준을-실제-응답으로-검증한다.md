# [Service] 수동 입력과 파일 업로드 활동의 추정 판정 기준을 실제 Strava 응답으로 검증한다

## 핵심 요약

- 요구사항: 티켓 20261017_1421 1회가 수동 입력(`manual`)과 파일 업로드(업로드 번호가 있고 외부 ID가 `.gpx`·`.fit`·`.tcx`·`.kml`·`.kmz`(+gz) 모양)를 추정 기준으로 거른다. 이 기준이 기기로 기록한 정상 활동을 잘못 거르지 않는지 실제 Strava 응답과 `source_meta`로 검증하고 필요하면 고친다.
- 구현 계획: 대기 상태다. 1회가 staging에서 실제 동기화를 한 번 이상 돈 뒤(`strava_activities.source_meta`에 값이 쌓인 뒤)에 시작한다. 시작 때 `source_meta`의 분포를 읽기 전용으로 집계하고, 필요하면 사용자의 시험 활동(기기 기록 1개, GPX 업로드 1개)으로 응답 값을 확인한다.
- 관련 파일: `jam-web/src/lib/strava/qualification.ts`(`isFileUploadActivity`, 판정 사유 상수), `strava_activities.filter_reason`·`source_meta`(마이그레이션 223_strava_activity_filter_marker.sql), `jam-web/src/types/strava.ts`(76-100, 선언된 Strava 필드). 스펙: 운영 로직 3.3절(«가려내는 방법은 티켓 단계에서 실제 Strava 데이터로 확인한다»).

## 배경 / 문제 정의

운영 로직 3.3절은 손으로 입력한 활동과 파일로 올린 활동을 인정하지 않는다고 하면서 가려내는 방법은 실제 Strava 데이터로 확인하라고 했다. 저장된 활동의 `normalized`에는 `manual`·`upload_id`·`external_id`가 없고 연결된 Strava 도구도 이 필드를 돌려주지 않아 과거 데이터로는 검증할 수 없었다. 사용자가 추정 기준으로 먼저 진행하기로 했으므로(2026-10-17), 실제 응답이 쌓이면 검증하는 일이 남는다. 기기 동기화 활동도 업로드 번호를 가질 수 있어 잘못 거를 위험이 있다.

## 상세 요구사항

### 서비스/코드베이스 관점

- `source_meta`의 분포를 읽기 전용으로 집계한다: `manual`, 업로드 번호 유무, 외부 ID 모양별 활동 수와 걸러짐 사유.
- 기기로 기록한 정상 활동이 `file_upload`나 `manual_entry`로 걸러진 사례가 있는지 확인한다.
- 필요하면 사용자의 시험 활동으로 실제 응답 값을 확인하고 기준을 고친다. 실제 유저 토큰으로 Strava를 호출하지 않는다(사용자 본인 계정의 시험만).

## 구현 계획

대기. 시작 조건이 갖춰지면 읽기 전용 집계 결과를 사용자에게 보이고 기준을 고칠지 묻는다.

## 완료 조건

- `source_meta` 분포와 오탐 사례 유무가 완료 기록에 있고, 기준을 고쳤거나 유지한 근거가 남아 있다.
- 기준을 고쳤다면 `qualification.ts`의 판정과 시험이 새 기준과 일치한다.
