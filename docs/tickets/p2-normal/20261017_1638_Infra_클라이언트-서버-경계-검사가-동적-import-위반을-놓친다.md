# [Infra] 클라이언트·서버 경계 검사가 동적 import로 생긴 위반을 놓치는 문제를 고친다

## 핵심 요약

- 요구사항: 클라이언트 컴포넌트가 가져오는 모듈 안에서 서버 전용 모듈(`@/lib/supabase/server`, `next/headers`)을 동적 `import()`로 불러도 번들러(Turbopack)가 따라가서 브라우저 번들에 서버 코드가 들어가 빌드가 깨진다. 타입 검사, lint, `scripts/verify.sh`의 경계 검사(`client-server-imports`)는 이를 잡지 못했다. 검사가 동적 import까지 따라가게 고친다.
- 구현 계획: 한 번에 돌린다. 먼저 현재 경계 검사가 무엇을 보고 무엇을 놓치는지 읽고, 동적 import를 포함한 전이 import 추적으로 넓힌다.
- 관련 파일(시작 때 아현이 위치를 확인한다): `scripts/verify.sh`가 부르는 경계 검사 스크립트(이름은 `client-server-imports`로 검색), 사례는 티켓 20261017_1422 2회의 `jam-web/src/lib/strava/connection-state.ts`(수정 전 커밋 fcde99d2c)다.

## 배경 / 문제 정의

티켓 20261017_1422 2회에서 아현이 «서버 모듈을 동적으로 불러와 클라이언트 번들에 `next/headers`가 들어가지 않게 했다»고 보고했고, 게이트와 CI(`verify`)도 통과했다. 그러나 머지 뒤 로컬 `next dev`에서 `/profile/edit`이 500으로 깨졌다. 원인은 클라이언트 컴포넌트 → `connection-state.ts` → 동적 `import('@/lib/supabase/server')` 경로를 Turbopack이 정적 import처럼 추적한 것이다. 같은 종류의 사고는 앞선 기록에도 있다(기억: 경계 위반은 실제 빌드에서만 드러남). 지금은 push 전에 사람이 로컬 실렌더를 해야 잡힌다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 경계 검사가 `'use client'` 파일에서 시작해 정적·동적 import를 모두 따라가 서버 전용 모듈에 닿으면 실패하게 한다.
- 수정 전 사례(커밋 fcde99d2c의 `connection-state.ts` 모양)를 시험 사례로 고정해 새 검사가 실패함을 보인다.
- 오탐을 줄이기 위한 허용 목록이 필요하면 사유를 적는다.

## 구현 계획

한 번에 돌린다. 요약은 2,500자 이내.

## 완료 조건

- 클라이언트 컴포넌트가 동적 import로 서버 전용 모듈에 닿는 경우를 `scripts/verify.sh`가 실패로 판정한다. 확인 방법은 수정 전 사례를 재현한 시험이다.
- 기존 정상 코드(서버 컴포넌트가 서버 모듈을 가져오는 것 등)가 오탐으로 막히지 않는다.

- 2026-10-23 JAM 2.0 부가 P2 티켓 일괄 처리(jam-work)로 착수한다. 카리나가 최신 `origin/staging`에서 아직 재현됨을 확인했다. 유형 `infra`, 경로 ③ 표준. 규모 사전 판정: 파일 3개(검사 스크립트, 그 시험, 주석·문서), 변경 100줄 안팎이다. 구현 계획과 관련 파일에 경로·함수명이 적혀 있고 범위가 한 가지 일이라 `planOnlyWaiver`를 넘긴다. 확인한 사실: `scripts/check-client-server-imports.mjs` 11줄이 «동적 import()는 따라가지 않는다»고 적고 있고 `parseValueImports`에 동적 import 처리가 없다. 이 규칙은 티켓 20260924_1639가 정한 것이므로, 이 티켓이 뒤집는다는 사실을 스크립트 머리 주석에 남긴다.
