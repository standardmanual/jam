# [Feature] JAM 2.0 묶음 3: 캡슐과 인벤토리 (잠긴 아이템 배지, 캡슐, 믹스 고치기, 인벤토리·컬렉션 마무리)

## 핵심 요약

- 요구사항: 운영 로직 5장(캡슐), 7장(잠긴 아이템 배지), 8장(인벤토리, 컬렉션, 믹스)을 만든다. 잼으로 캡슐과 잠긴 아이템 배지를 채워 열고, 믹스의 받지 않은 결과와 등급 올리기 레시피를 쓰고, 컬렉션과 인벤토리가 잠김을 이해하게 한다. 묶음 2(동기화 → 잼, 아이템 배지, 보류, 이용 정지)가 끝난 상태에서 시작한다.
- 구현 계획: 하위 티켓 6개를 순서대로 진행한다(아래 표). 서버(3-1~3-3)가 화면(3-4)보다 먼저 간다. 하위 티켓마다 시작 전에 주요 결정을 질문창으로 묻고, 화면이 있는 것은 채원 사전 판정을 받는다.
- 관련 파일: `docs/plan/jam2/10 JAM 2.0 서비스 운영 로직.md` 5·7·8장, `docs/plan/jam2/service-redesign/현재 서비스 비교.md` 3.5·3.6·3.8절, `docs/plan/jam2/service-redesign/19 게이미피케이션 밸런스.md`(수치).

## 배경 / 문제 정의

묶음 1이 잼 원장(220), 챕터 저장(221), 컬렉션 4등급(222)을 DB에 더했고, 묶음 2가 동기화가 잼을 쌓고 소속 트라이브의 아이템 배지를 주고 가득 차면 보류하게 했다. 이제 잼을 쓰는 쪽이 필요하다: 캡슐을 채워 열면 아이템 배지가 나오고, 잠긴 채 받은 아이템 배지는 잼을 채워야 열린다.
지금 서비스에는 캡슐도 잠금 개념도 없다. 믹스는 결과에 30일 기한이 붙고 빈칸이 모자라면 결과를 조용히 건너뛴다. 컬렉션 완성 판정은 묶음 1에서 하나로 모았다.

## 사용자 결정 (2026-10-18, 질문창, 추천안)

1. **하위 티켓은 6개로 쓰고 3-1(잠긴 아이템 배지의 저장과 규칙)부터 진행한다.** 캡슐 열기의 5단계(잠김 배정)와 동기화의 잠김 배정(2-4에서 미룬 것)이 모두 잠긴 개체 구조를 필요로 하기 때문이다.
2. **유저 화면(캡슐 화면, 잠긴 아이템 배지 카드와 채우기)은 서버 뒤 3-4에서 한 번에 만든다.** 서버 티켓은 API까지만 만든다. 캡슐 화면의 완성된 디자인은 문서에서 확인되지 않아 3-4 시작 때 채원 사전 판정으로 정한다.

### 순서의 근거

- 잠김(3-1)이 캡슐(3-2)보다 앞서야 캡슐 열기에서 «잠긴 채 배정»을 한 번에 구현한다. 반대로 하면 캡슐 열기에서 잠김을 빼 두었다가 다시 고쳐야 한다.
- 챕터 점수 연결(캡슐 열기, 믹스 성공 점수)은 묶음 5에서 한다(상위 티켓 순서의 근거). 이 묶음은 챕터 점수를 올리지 않고 기록만 남긴다. 액티비티 배지의 캡슐·잠김·믹스 횟수 조건은 묶음 4다.
- 드랍·픽업의 잠김 처리(잠긴 채 드랍, 채운 양 소멸 알림, 가린 모습)는 묶음 4다. 묶음 4 전까지 잠긴 개체의 드랍은 막는다(3-1).
- 이용 정지 검사(`assertNotSuspended`, 2-6)는 캡슐·잠긴 아이템 배지의 채우기와 열기(3-2, 3-3), 믹스(3-5)에 연결한다.
- 값(필요한 양, 확률, 최소값)은 설정 테이블 행으로 두고 코드는 읽기만 한다. 설정 화면은 묶음 7이다.

## 완료 조건

- 하위 티켓 6개가 모두 CLOSED다.
