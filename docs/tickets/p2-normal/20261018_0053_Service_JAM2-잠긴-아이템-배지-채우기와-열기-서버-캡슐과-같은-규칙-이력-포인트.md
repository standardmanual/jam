# [Service] JAM 2.0 잠긴 아이템 배지 채우기와 열기 서버: 캡슐과 같은 규칙, 이력, 포인트

## 핵심 요약

- 요구사항: 운영 로직 7.2절의 «채우기와 열기»를 서버까지 만든다. 잠긴 개체에 잼을 채우고(한 번에 한 곳, 나눠 채울 수 있음), 다 채우면 열어 이름과 그림을 드러낸다. 규칙은 캡슐과 같게 한다(3-2의 채우기 로직 재사용). 이미 칸을 차지하고 있으므로 인벤토리가 가득 차 있어도 열 수 있다(캡슐과 다른 점). 열기는 획득이 아니고 새로 뽑지 않는다. 포인트는 열린 상태가 될 때 한 번 준다. 잠김과 열림의 이력을 남긴다. 이용 정지 중에는 막는다. 화면은 3-4다.
- 구현 계획: 시작 때 사용자 결정 3건을 질문하고 파일 단위 계획을 옮겨 쓴다. SQL(이력 테이블, 열기 함수)은 사용자 승인과 롤백 실측 뒤 카리나가 실행한다. 1회로 돌린다.
- 관련 파일(2026-10-18 조사, 시작 때 아현이 줄 위치를 다시 확인한다):
  - 개체와 잠김 칸: 3-1이 만든 새 칸. 채우기 로직: 3-2가 만든 캡슐 채우기(공통 함수로 뺀다). 잼 원장 `jam_apply`의 사유 `locked_item_badge_fill`(220, 음수만, 대상 개체 참조 필요 여부는 220의 CHECK 확인).
  - 포인트: 지금 아이템 배지의 포인트 지급 경로(`jam-web/src/lib/` 포인트 모듈과 `app/api/points/`, 시작 때 조사), 한 일련번호당 한 번만 주는 보장.
  - 이력: 8.5절의 «개체가 거쳐 간 이력(받음, 장착, 드랍, 픽업, 소모, 잠김과 열림)».
  - 이용 정지: `jam-web/src/lib/suspension/suspension.ts`.
  - 스펙: 운영 로직 7장, 비교표 3.6절.

## 배경 / 문제 정의

3-1이 잠긴 개체의 저장과 제한을 만들고 3-2가 캡슐 채우기를 만든 뒤, 같은 규칙을 잠긴 아이템 배지에 쓴다. 7.2절은 «같은 동작을 두 곳에서 다르게 하면 유저가 헷갈린다»며 채우기와 열기를 캡슐과 같게 하라고 한다.
다른 점은 세 가지다: 열기에 인벤토리 빈칸이 필요 없고, 열면 새 아이템 배지가 나오는 것이 아니라 정해져 있던 아이템 배지가 드러나며 획득이 아니고, 필요한 양이 배정 때 고정된다.
공용 DB 주의: 옛 프로덕션 코드가 같은 테이블·함수를 쓴다. 새 칸·새 테이블·새 함수·새 설정 행만 덧붙이고 기존 칸의 뜻은 바꾸지 않는다. 축소는 묶음 6이다. SQL은 아현이 파일로 쓰고, 실행은 사용자 승인과 롤백 실측 뒤 카리나가 한다.

## 시작 전에 사용자에게 확인할 것 (주요 결정, 질문창)

1. **채우기 로직의 공통화**: 캡슐과 잠긴 아이템 배지가 같은 «채우기» 함수(가진 잼 확인, 남은 양 계산, 원장 차감)를 쓰고 대상만 다르게 한다(추천). 대안은 각각 따로 만드는 것이다.
2. **포인트 지급의 중복 방지**: 한 일련번호당 한 번만 주도록 개체별 지급 기록(새 칸 또는 새 테이블)을 둔다(추천: 잠긴 채 드랍된 것을 픽업해 열면 픽업한 유저가 받는 규칙까지 같은 기록으로 지킨다). 대안은 지금 포인트 기록(`point_transactions` 계열)에서 일련번호로 찾는 것이다.
3. **개체 이력의 저장**: 잠김과 열림, 채움을 개체 이력 테이블 하나에 쌓는다(추천, 8.5절의 이력과 같은 곳). 대안은 3-1의 새 칸과 원장만으로 두고 이력 테이블은 묶음 4(드랍·픽업)에서 만드는 것이다.

## 사용자 결정 (2026-10-18)

1. 채우기 로직: **공통 규칙 + 대상만 다르게.** 판정(기본값·줄인 양·부족·초과)을 새 함수 `jam_fill_decide`에 두고 잠긴 개체 채우기가 쓴다. 232·234의 `capsule_fill`은 바꾸지 않고(이번 묶음에서 만든 아직 쓰이지 않는 함수이지만 덧붙이기 규칙을 지킨다), 롤백 실측이 두 함수의 판정을 같은 표로 비교해 어긋남을 막는다. 캡슐 쪽이 공통 함수를 쓰게 바꾸는 일은 3-4 이후 필요하면 한다.
2. 포인트 중복 방지: **개체별 지급 기록 새 칸** `inventory_items.point_awarded_at`. 열기와 같은 트랜잭션에서 `award_points`를 부르고 칸을 채운다.
3. 개체 이력: **새 테이블 `inventory_item_events` 지금 만든다.** 이번에는 `filled`·`unlocked`만 쓰고 나머지 종류(받음·장착·드랍·픽업·소모·잠김)는 묶음 4 이후가 같은 표에 이어 쓴다.

## 상세 요구사항

### 서비스/코드베이스 관점

- **채우기**: 한 번에 한 곳(개체 하나)을 골라 채운다. 기본값은 남은 양, 가진 잼이 모자라면 가진 만큼 전부, 양을 줄여 채울 수 있고 나눠 채울 수 있다. 남은 양보다 많이 채울 수 없고 채운 잼은 꺼낼 수 없다. 채울 때마다 `jam_apply`(`locked_item_badge_fill`, 음수)와 개체의 채운 양 갱신과 이력이 한 트랜잭션이다. 열려 있거나 남이 가진 개체는 채울 수 없다.
- **열기**: 채운 양이 필요한 양에 도달하면 열 수 있다. 열면 같은 개체가 열린 상태가 되고(일련번호 그대로) 열린 시각을 기록한다. 새로 뽑지 않고 확률이 들어가지 않는다. 인벤토리가 가득 차 있어도 열 수 있다. 한 번 연 것은 다시 잠기지 않는다. 동시에 두 번 열어도 한 번만 열린다.
- **이용 정지 중**: 채우기와 열기를 거부한다(`user_suspended`, 403). 채운 양은 그대로 남는다.
- **포인트**: 아이템 배지에 붙은 포인트는 열린 상태가 될 때 연 유저에게 한 번만 준다. 열린 채 받으면 받을 때 주고(3-1에서 막은 경로가 이 시점에 풀림), 잠긴 채 받으면 연 때 준다.
- **트라이브가 바뀌어도** 잠긴 개체와 채운 양은 그대로 남는다.
- **기록(7.2절)**: 잠긴 개체마다 얻은 시각과 경로, 잠긴 까닭, 필요한 양, 채운 기록(언제, 얼마나), 연 시각과 연 유저, 준 포인트. 잠긴 아이템 배지를 연 횟수(액티비티 배지의 조건)는 기록으로 센다.
- **API**: 채우기와 열기 라우트, 개체의 현재 채운 양과 열 수 있는지 조회. 응답은 열기 전에는 이름·그림·설명·컬렉션·트라이브·일련번호를 싣지 않는다(7.3절). 열린 뒤에는 개체 정보를 싣는다.
- 새 칸과 새 함수는 덧붙이기만 한다. 생성 타입을 같은 커밋에 맞춘다.

### UI/UX 관점 (해당 시)

- 없음(화면은 3-4).

## 구현 계획 (회차)

1회로 돌린다(예상 파일 약 14개). DB는 마이그레이션 235가 이미 공용 DB에 적용되어 있다(`jam_fill_decide`, `locked_item_fill(p_user_id, p_item_id, p_amount)`, `locked_item_open(p_user_id, p_item_id)`, 표 `inventory_item_events`, 칸 `inventory_items.point_awarded_at`, 생성 타입 반영 끝). 앱은 이 함수를 부르기만 한다. 함수의 오류 코드는 `jam-web/supabase/migrations/235_locked_item_fill_and_open.sql` 머리말에 있다.

파일 단위 계획(줄 위치는 아현이 시작 때 다시 확인한다). 캡슐 모듈(`lib/capsule/capsule.ts`, `capsule-contract.ts`)과 `app/api/capsule/fill/route.ts`를 같은 모양으로 따른다.

1. `jam-web/src/lib/inventory/lockedItemFill-contract.ts`(신규, 순수): 채우기·열기 응답 타입, 오류 코드(`item_not_found`, `not_locked`, `already_full`, `exceeds_remaining`, `invalid_amount`, `insufficient_jam`, `not_full`, `user_suspended`), 양 상한은 `CAPSULE_AMOUNT_MAX`를 재사용한다. 서버 전용 모듈을 가져오지 않는다.
2. `jam-web/src/lib/inventory/lockedItemFill.ts`(신규, 서버 전용): `fillLockedItem(supabase, userId, itemId, amount?)`, `openLockedItem(supabase, userId, itemId)`, `getLockedItemStatus(supabase, userId, itemId)`, 오류 클래스 `LockedItemError`. 먼저 `assertNotSuspended`로 막고, RPC `locked_item_fill`·`locked_item_open`을 부른다. 열기 성공 뒤에는 개체의 이름·그림·설명·등급·컬렉션·트라이브·일련번호를 조회해 응답에 싣는다(열기 전에는 어떤 응답에도 싣지 않는다). 조회는 채운 양, 필요량, 가진 잼, `openable`(다 채웠고 아직 잠김)만 싣는다.
3. `jam-web/src/app/api/inventory/items/[itemId]/fill/route.ts`(신규): POST `{ amount? }`. 코드별 상태: `already_full`·`exceeds_remaining`·`invalid_amount` 400, `insufficient_jam`·`not_locked` 409, `item_not_found` 404, `user_suspended` 403, 그 밖 500.
4. `jam-web/src/app/api/inventory/items/[itemId]/open/route.ts`(신규): POST. `not_full` 409(채운 양·필요량 포함), `not_locked` 409, `item_not_found` 404, `user_suspended` 403.
5. `jam-web/src/app/api/inventory/items/[itemId]/lock/route.ts`(신규): GET 채운 양·열 수 있는지.
6. `jam-web/src/lib/i18n/ko.ts`와 `d.ts`: `d.lockedItem`에 채우기·열기 거절 문구와 성공 문구를 더하고, `d.suspension`에 잠긴 개체 채우기·열기 막힘 문구를 더한다. 문구는 UX Writing 가이드(해요체, 현상→원인→해결 3단계)를 따른다.
7. 테스트(신규): `lib/inventory/__tests__/lockedItemFill.test.ts`, 라우트 테스트 세 개(`fill`, `open`, `lock` 각각의 `__tests__/route.test.ts`). 기본값·줄인 양·부족·초과, 정지 403, 열기 전 응답에 이름·그림 등이 없음(소스 검색 경계 시험 포함), 클라이언트 경계(서버 전용 모듈 비가져오기).
8. 문서: `docs/service/prd/02_DATA_MODEL.md`(새 표·칸·함수), API PRD(새 라우트 세 개, 해당 파일은 시작 때 `docs/service/prd/`에서 찾는다), `docs/service/badge-engine/`의 잠긴 아이템 배지 절(채우기·열기·포인트 한 번), `docs/plan/jam2/service-redesign/현재 서비스 비교.md` 3.6절 상태.

하지 않는 일(범위 밖): 화면(3-4), 열 때 피드·알림 추가(3-4에서 정함), `capsule_fill`을 공통 판정 함수로 바꾸는 일, 잠긴 채 드랍·픽업(묶음 4), 인벤토리 목록·이력·타인 프로필의 가림(3-4). DB 안에서 포인트를 주므로 `awardPoints`의 알림(`notifyPointChange`)은 이 경로에서 나가지 않는다 — 이 사실을 완료 기록 「잔여 이슈」에 적는다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)

- 잠긴 개체를 채울 수 있고 기본값·줄인 양·부족·초과가 캡슐과 같게 동작하며, 원장 한 줄과 개체 갱신이 한 트랜잭션이다.
- 다 채우면 열 수 있고 같은 개체가 열린 상태가 되며 일련번호가 그대로다. 인벤토리가 가득 차 있어도 열린다. 동시에 두 번 열어도 한 번만 열린다. 다시 잠기지 않는다.
- 이용 정지 중에는 채우기와 열기가 막히고 채운 양이 남는다.
- 포인트는 한 일련번호당 한 번만, 열린 상태가 될 때 연 유저에게 간다(잠긴 채 받은 경우 연 때, 열린 채 받은 경우 받을 때).
- 열기 전에는 이름·그림·설명·컬렉션·트라이브·일련번호가 API 응답에 없다.
- 마이그레이션이 옛 객체를 바꾸지 않으며 되돌림 SQL을 싣는다. `docs/service/prd/`와 엔진 문서에 반영되어 있다.

### 후속 범위 (담당: 카리나, 시점: 사용자 승인 뒤)

- 사용자 확인 1~3번의 결정을 이 티켓 「사용자 결정」 절에 기록한다. SQL 실행은 승인과 롤백 실측 뒤에 한다.

### 잔여 이슈
- 열기 때 포인트 알림이 나가지 않는다(위 메모). 3-4에서 열림 피드·알림과 함께 정한다.
- 어드민 배지 삭제 가드(`lib/admin/badge-references.ts`)에 `inventory_item_events.badge_id`가 없다. 지금은 배지를 지우면 이력의 배지 칸만 NULL이 된다(후속 티켓 20261018_1004).
- 열기와 채우기, 열기와 열기의 진짜 동시 실행은 DB 한 연결로 시험하지 못했다. 개체 행 잠금(`FOR UPDATE`)과 열린 뒤 `not_locked`로 판단했다. 필요하면 staging에서 두 요청을 동시에 보내 확인한다.
- 잠긴 채 받은 개체를 열 때 포인트는 `point_awarded_at`이 비어 있을 때만 나간다. 열린 채 받은 개체는 기존 경로(`issueFollowUp`)가 주고 이 칸을 쓰지 않으므로, 두 경로가 같은 일련번호에 겹치지 않음은 «잠긴 개체는 열기 전까지 기존 경로가 포인트를 주지 않는다(3-1)»에 기댄다.
- 인벤토리 목록·이력·타인 프로필·컬렉션의 가림은 3-4 전까지 열기 전 이름이 보일 수 있는 상태다(3-4 티켓에 범위 추가됨).
