# [Feature] JAM 2.0 믹스 고치기: 받지 않은 결과, 기한 없앰, 등급 올리기 레시피, 설명 칸, 잠김 규칙

## 핵심 요약

- 요구사항: 운영 로직 8.4·8.8절에 맞춰 믹스를 고친다. 결과의 30일 기한을 없애고, 빈칸이 모자라면 결과를 조용히 건너뛰는 대신 받지 않은 결과로 남기고 받기 전에는 새 믹스를 막으며, 등급 올리기 레시피(같은 트라이브·같은 등급 5개 → 고른 컬렉션·이름의 바로 위 등급 1개, Mystic은 재료 아님)를 실행하고, 레시피에 설명 칸을 더하고 보상 없음을 허용하고, 잠긴·장착한 개체는 재료로 못 쓰게 하고, 결과의 잠김(레시피가 정함)을 따르고, 이용 정지 중 막는다. 레시피를 만드는 일(등급 올리기 일괄)은 묶음 7이다.
- 구현 계획: 시작 때 사용자 결정 4건을 질문하고 파일 단위 계획을 옮겨 쓴다. SQL(받지 않은 결과 새 테이블, 레시피 새 칸)은 사용자 승인과 롤백 실측 뒤 카리나가 실행한다. 규모에 따라 1~2회.
- 관련 파일(2026-10-18 조사, 시작 때 아현이 줄 위치를 다시 확인한다):
  - 믹스 실행: `jam-web/src/lib/combine/index.ts`(`combineRecipeAttempt` 101줄, 결과 지급 `p_expires_at` 30일 430줄 근처), `policy.ts`, `recipe-payload.ts`, `visibility.ts`, `app/api/combine/route.ts`, 화면 `app/(main)/combine/`(`CombineClient.tsx`, `RecipeRewardRow.tsx`).
  - 레시피 저장: 믹스 레시피 테이블(마이그레이션 검색, 보상 하나 이상 필수인 검증 위치는 어드민 레시피 저장 라우트).
  - 보류 구조의 선례: 2-5의 `sync_pending_items`(229)와 `resolve_sync_pending_items`.
  - 재료 제한: 3-1이 만든 잠김 칸과 `slotted_in`(장착).
  - 스펙: 운영 로직 8.4·8.5절, 비교표 3.8절.

## 배경 / 문제 정의

지금 믹스 결과에는 30일 기한이 붙고 빈칸이 모자라면 결과를 조용히 건너뛴다. 지금 레시피에는 설명 칸이 없고 보상이 하나 이상 있어야 저장된다. 운영 로직 8.4절: 재료는 성공과 실패에 상관없이 소모되고, 결과에는 기한이 없고, 결과가 들어갈 빈칸이 모자라면 결과를 받지 않은 상태로 두며 받기 전에는 새 믹스를 할 수 없다. 결과 아이템 배지의 공개 기간이 끝난 레시피는 믹스 화면에서 내려 쓸 수 없게 한다.
등급 올리기 레시피는 컬렉션 4등급(묶음 1)과 같은 «같은 이름의 4등급» 구조에 기댄다. 재료는 같은 트라이브·같은 등급 5개이고 결과는 유저가 고른 컬렉션과 이름의 위 등급이다.
공용 DB 주의: 옛 프로덕션 코드가 같은 테이블·함수를 쓴다. 새 칸·새 테이블·새 함수·새 설정 행만 덧붙이고 기존 칸의 뜻은 바꾸지 않는다. 축소는 묶음 6이다. SQL은 아현이 파일로 쓰고, 실행은 사용자 승인과 롤백 실측 뒤 카리나가 한다.

## 시작 전에 사용자에게 확인할 것 (주요 결정, 질문창)

1. **받지 않은 결과의 저장**: 믹스 전용 새 테이블 `combine_pending_results`(추천, 2-5의 동기화 보류와 같은 모양)와 미션 보상·프로모션까지 담는 공통 «받지 않은 보상» 테이블을 지금 만드는 방식. 후자는 묶음 5의 설계를 앞당긴다.
2. **기한 없앰의 범위**: 새로 받는 믹스 결과만 기한 없이 지급하고(추천), 이미 기한이 붙은 옛 개체는 그대로 둔다. 대안은 옛 개체의 기한도 지우는 것이다(공용 DB 데이터 변경이라 신중해야 한다).
3. **레시피의 설명 칸과 보상 없음**: `recipes`에 설명 새 칸을 더하고 보상 하나 이상 조건을 완화한다. 옛 프로덕션 어드민은 옛 검증을 유지하므로 새 어드민 라우트에서만 완화한다(추천).
4. **등급 올리기 레시피의 표현**: 레시피 한 건이 아니라 «규칙»으로 실행한다(재료 5개와 결과 계산을 코드가 하고 데이터에는 레시피 행을 만들지 않음, 추천: 컬렉션 9종×4등급이 늘어도 행이 늘지 않는다). 대안은 컨텐츠 입력(묶음 7)에서 레시피 행을 일괄로 만드는 것이다(운영 로직 8.7절은 이쪽을 말한다).

## 사용자 결정 (2026-10-18)

1. 받지 않은 믹스 결과의 저장: **믹스 전용 새 테이블**(`combine_pending_results`). 묶음 5에서 미션 보상·프로모션과 구조를 합칠 때 옮겨 가기 쉽게 동기화 보류(`sync_pending_items`)와 같은 모양으로 만든다.
2. 기한 없앰: **새 결과만** 기한 없이 지급한다. 이미 기한이 붙은 옛 개체는 그대로 둔다.
3. 레시피의 설명 칸과 보상 없음: **새 칸 + 새 어드민 라우트에서만 완화**한다. 옛 어드민의 저장은 옛 검증(보상 하나 이상) 그대로다. DB의 `combination_recipes_reward_present_check`(포인트 또는 보상 배지 하나 이상)는 «보상 없음»을 막으므로, 완화는 이 제약을 새 칸으로 우회하지 않고 제약을 «보상 없음 허용 칸이 켜진 레시피는 제외»로 바꾸는 방식이다(옛 행과 옛 어드민에는 영향 없음).
4. 등급 올리기 레시피: 사용자 답은 **«등급 올리기를 별도 표시하지 않음»**이다. 카리나의 해석: 등급 올리기를 별도 종류로 표시하거나 코드로 따로 실행하지 않고, 지금 레시피 구조(슬롯마다 `allowed_badge_ids` 후보 목록)로 만든 보통 레시피로 취급한다(현재 서비스 비교 5절 B 원안과 같다). 슬롯 5개 각각에 같은 트라이브·같은 등급의 아래 등급 후보 전부를 넣고 결과는 위 등급 개체 하나로 정해 두므로, «같은 트라이브·같은 등급 5개만 받고 등급 혼합을 거부한다»는 규칙은 후보 목록이 보장한다. **이 티켓은 등급 올리기 전용 코드·칸을 만들지 않는다.** 레시피를 만드는 일괄 생성과 목록 거르기는 묶음 7이다. 이 해석이 다르면 알려 주세요.
5. 카리나의 가정(확인 요청 없이 진행, 틀리면 알려 주세요): 믹스 칸 수 상한은 운영 로직 8.6절이 코드 상수 5로 정했고 지금 코드는 `MAX_ITEMS = 10`이다. 공용 DB의 기존 레시피 3개가 모두 칸 3개 이하라 5로 낮춰도 영향이 없다. 이 티켓에서 5로 맞춘다.

## 상세 요구사항

### 서비스/코드베이스 관점

- **받지 않은 결과**: 결과가 들어갈 빈칸이 모자라면 결과를 받지 않은 상태로 남긴다(재료는 소모됨). 받지 않은 결과가 있으면 새 믹스를 거부한다(409). 빈칸을 만든 뒤 받으면 지급한다. 받는 길은 2-5의 고르기와 같은 방식으로 한 번의 DB 함수로 처리한다. 생긴 때와 받은 때를 기록한다(8.5절).
- **기한 없앰**: 새 결과는 `expires_at`을 두지 않는다(`combine/index.ts`의 30일 지급을 없앰).
- **재료 제한**: 잠긴 개체, 장착한 개체는 재료로 쓸 수 없다. 재료는 공개 기간과 상관없이 가진 것이면 쓸 수 있다. 재료가 레시피에 맞지 않으면 실패이고 재료는 삭제되고 포인트 10을 준다(기존 규칙 유지, 값은 믹스 정책).
- **등급 올리기**: 같은 트라이브·같은 등급 5개(어느 컬렉션의 것이든, 등급을 섞을 수 없고 Mystic은 재료가 아님) → 유저가 고른 컬렉션과 이름의 바로 위 등급 1개(Common 5→Rare, Rare 5→Epic, Epic 5→Mystic). 고를 수 있는 컬렉션·이름과 결과 후보를 서버가 돌려준다.
- **결과의 잠김**: 레시피가 정한다(기본은 열림). 잠김으로 만든 아이템 배지는 늘 잠긴 채 나온다(3-1의 함수 사용, 필요한 양 배정). 믹스는 무작위로 잠기지 않는다.
- **공개 기간이 끝난 결과의 레시피**: 믹스 화면에서 내려 쓸 수 없게 한다(재료만 잃는 일을 막는다).
- **이용 정지 중**: 믹스와 받지 않은 결과 받기를 거부한다(`user_suspended`, 403).
- **레시피 설명 칸과 보상 없음**: 설명 칸을 더하고 보상 없음을 허용한다. 보상은 재료와 같은 등급, 상위 등급, 없음 가운데 레시피마다 정한다.
- **어드민(shadcn/ui 표준)**: 레시피 화면에서 설명 입력과 보상 «없음» 선택. 레시피 일괄 생성은 묶음 7이다.
- 믹스 시도·성공·실패 횟수와 트라이브를 넘는 레시피 성공 횟수는 기록으로 센다(액티비티 배지 조건은 묶음 4, 믹스 성공 챕터 점수는 묶음 5).
- 새 칸과 새 테이블은 덧붙이기만 한다. 생성 타입을 같은 커밋에 맞춘다.

### UI/UX 관점 (해당 시)

- 믹스 화면(`CombineClient.tsx`)에서 받지 않은 결과 받기, 등급 올리기 선택, 빈칸 모자람 안내가 필요하다. 모양은 채원 사전 판정으로 정한다(시작 때). 회차를 나누면 2회에 넣는다.

## 구현 계획 (회차)

2회로 나눈다(아현 크기 판단 2026-10-18). ### 배치

### A. 진입 위치 = 믹스 화면 자체 (새 라우트·새 탭 없음)
`TopNav` 바로 아래, 레시피 탐색 화면과 믹서 화면 둘 다에 같은 배너를 둔다. `pendingCount > 0`이고 연출 모드가 아닐 때만 보인다.

```
[TopNav 믹스하기]
┌ 배너(bg-surface, rounded-2xl, px-4 py-4, 한 면) ───────────────┐
│ 받지 않은 믹스 결과가 3개 있어요      (text-base bold, 좌측정렬)  │
│ 받은 뒤에 새로 믹스할 수 있어요       (text-sm, break-keep)       │
│                                          [ 받기 ]  (Button sm이 아닌 md, 우측 정렬) │
└──────────────────────────────────────────────────────────────┘
```
- 좁은 화면(320~360px)에서는 버튼이 문구 아래로 내려가도 된다. flex-wrap + `justify-between`으로 둔다.
- 배너는 경고색(빨강·노랑)을 쓰지 않는다. 오류가 아니라 «할 일»이다.
- 배너 안에 카드를 또 넣지 않는다.

### B. 받지 않은 결과 시트 (`PendingResultsSheet`, `BottomSheet` compact)
제목: «받지 않은 믹스 결과» (`CapsuleSheet`와 같은 `titleClassName`)

본문(`px-6 pt-2 pb-4`, 스크롤)
```
 (한 줄) 결과 3개를 한 번에 받아요        text-sm
 ┌ 3열 그리드 gap-2 ─────────────────┐
 │ [그림 64] [그림 64] [LockedTile 64] │
 │  이름      이름     잠긴 아이템 배지 │   이름 text-xs line-clamp-2
 │  (RarityBadge)                      │   잠긴 것은 등급 칩만, 이름·그림 없음
 └─────────────────────────────────────┘
```
- 열린 결과는 `SafeImage` 64px 타일 + 이름. 믹스 가방 시트(`CombineClient` 630~675줄)의 타일 모양을 따르되 `button`이 아니라 비상호작용 `div`다. 개별 선택이나 부분 받기는 없다(서버가 전부 한 번에 받는다).
- 잠긴 결과는 `LockedTile`(64) + «잠긴 아이템 배지»(`d.lockedItem.card.name`) + `RarityBadge`. 필요한 양(`unlockRequired`)이 응답에 있으면 `d.lockedItem.card.description` 줄을 `text-xs`로 더한다. 없으면 생략한다.
- 목록 응답은 `rarity`를 준다. 이름·그림이 없는 결과는 이름 자리에 가린 이름을 쓴다.

푸터(고정, `footer`) — 두 갈래
1) 빈칸이 충분함(`freeSlots >= pendingCount`)
```
 인벤토리 빈칸 5개 · 필요한 빈칸 3개   (text-sm, 좌측)
 [ 받기 ]  primary fullWidth  (제출 중 «받는 중» SwapText, aria-busy)
```
2) 빈칸이 모자람(`freeSlots < pendingCount`) — 버튼을 없애고 `CapsuleSheet`의 noSlots 블록을 그대로 따른다
```
 인벤토리 빈칸이 모자라요                       text-base bold
 지금 빈칸 1개, 받으려면 3개가 필요해요          text-sm  (free·needed)
 믹스 결과는 그대로 남아 있어요                  text-sm
 인벤토리 보기  →  /inventory                    min-h-11, --link
```
- 두 줄 이상의 문장은 모두 `break-keep wrap-break-word text-pretty`(제목은 `text-balance`)로 어색한 끊김을 막는다. 가운데 정렬하지 않는다.
- 시트를 열 때마다 GET으로 최신 `freeSlots`를 읽는다. 인벤토리에서 비우고 돌아오면 `page.tsx`가 다시 서버 값을 주고, 시트는 열릴 때 다시 읽는다.
- POST가 `insufficient_slots` 409를 주면 응답의 free·needed로 푸터를 2)로 바꾼다. 토스트는 쓰지 않는다.

### C. 받기 성공 → `BadgeRevealOverlay`
시트를 닫고, 시트 목록을 `RevealBadge[]`로 옮겨 오버레이를 연다. 열린 결과는 이름·그림·등급을, 잠긴 결과는 `locked:true`·`rarity`·(있으면) `unlockRequired`를 싣는다. `resultMessage`: «믹스 결과 {n}개를 받았어요». 닫을 때 `router.refresh()`로 배너를 지운다. 잠긴 결과를 열린 척 보여주지 않는다.

### D. 새 믹스가 막힌 상태 (믹서 화면)
- 배너가 위에 계속 있다.
- «믹스하기» CTA는 `disabled`(기존 `opacity-30`). 슬롯 채우기·레시피 탐색은 막지 않는다. 받기 전에 다음 믹스를 준비해 둘 수 있다.
- CTA 바로 아래, 소각 안내(`burnNotice`) 위에 한 줄: «받지 않은 믹스 결과를 받으면 믹스할 수 있어요»(`text-sm text-foreground`). `aria-describedby`로 버튼에 연결한다.
- 이유 문구는 muted가 아니라 foreground로 둔다. 비활성 이유는 읽혀야 하는 정보다.

### E. 믹스 직후 결과가 받지 않은 상태로 남음 (`resultStatus: 'pending'`)
`BadgeRevealOverlay`의 `emptyMessage` 셸을 그대로 쓴다. 캐러셀은 없다(`resultBadges`가 빈 배열). 문구는 서버 `message`(`d.combine.resultPending`)를 쓰지 않고 클라이언트가 숫자를 넣어 두 문장으로 만든다.
```
 믹스 결과 3개를 아직 받지 못했어요.
 지금 빈칸 1개, 받으려면 3개가 필요해요. 빈칸을 만든 뒤 믹스 화면에서 받아 주세요.   [X]
```
- 포인트가 있으면(`points > 0`) 문구에 «포인트 {points}는 먼저 받았어요»를 한 문장 더한다(서버는 pending이어도 포인트는 지급한다).
- 오버레이를 닫으면 `router.refresh()`로 A의 배너가 나타난다. 시트를 자동으로 열지 않는다(빈칸을 만들러 가야 하는 사람에게 또 가리면 방해다).

### F. 잠긴 채 나온 결과 (`resultBadges[].locked`)
`resultBadges`의 `locked:true` 항목은 id·name이 빈 문자열이다. 현재 코드의 `rewardBadges.find(rb.id === b.id)`는 빈 id에서 실패하므로 분기한다.
- 잠긴 항목: `{ id: 'locked-{index}', name:'', description:'', locked:true, rarity: b.rarity }`. `id`는 캐러셀 키 용도의 합성 값이다. 응답에 `unlockRequired`가 없어 필요한 양 줄은 생략된다. 이름·그림은 `toCarouselItem`이 가린다.
- 열린 항목은 지금처럼 `selectedRecipe.rewardBadges`에서 상세를 찾는다.
- 1회의 응답 계약은 바꾸지 않는다. 필요한 양 줄이 없는 것은 의도한 동작이다. 필요하면 후속으로 `unlockRequired`를 응답에 싣는 것을 아현에게 제안한다.

### G. 레시피 설명과 «보상 없음»
설명: 믹서 화면 상단 요약 행(`RecipeRewardRow`) 바로 아래, 슬롯 그리드 위에 한 문단.
```
 [레시피 행]
 설명 문단   text-sm text-foreground, whitespace-pre-line, break-keep, line-clamp-3
 더 보기     (넘칠 때만, text-sm --link, min-h-11, 누르면 접기/펼치기)
 [슬롯 그리드]
```
- 설명이 없으면(`description` 빈값/null) 이 영역을 렌더하지 않는다.
- 레시피 탐색 목록의 각 행에는 설명을 싣지 않는다(행이 길어지고 `releaseAt` 줄과 겹친다). 탐색 검색 대상에도 넣지 않는다.
- «보상 없음» 레시피(`배지 0개 && reward_points <= 0`): `RecipeRewardRow`에서 아이콘은 `CoinIcon`(포인트 암시)이 아니라 `PackageIcon`의 중립 원(40px, `bg-background`)으로 바꾸고 부제 자리에 «보상 없음»(`text-xs text-muted`)을 둔다. 지금은 `hasPoints`와 `hasBadges`가 둘 다 false라 코인 아이콘만 있고 아무 설명이 없는 «빈» 행이 된다.
- 결과가 «잠긴 채 지급»인 레시피(`reward_locked`): 부제의 `RarityBadge` 옆에 `LabelChip` «잠김»(`d.lockedItem.detail.chip`)을 `shrink-0`으로 붙인다(승인 항목 참고).

### H. 칸 수 5
- 슬롯 그리드: 칸 수가 4 이하면 지금 그대로 `grid-cols-4`. 5칸이면 `grid-cols-3`(3+2 줄, 왼쪽 정렬, 칸이 더 커진다). 5열은 360px에서 칸이 약 59px로 줄어 `MixerSlot`의 썸네일과 이름이 읽히지 않는다. 가운데로 모은 3+2 배치는 쓰지 않는다. 마지막 줄 2칸이 비어 보여도 정렬을 흔들지 않는 쪽이 낫다.
- `selectRangeError`(«2개에서 5개까지»)는 서버 문구라 이미 5로 맞다. 클라이언트는 따로 상한 검사를 두지 않는다.

### I. 이용 정지
믹스 `POST` 403 `{ error, code:'user_suspended' }` → `info` 토스트로 `data.error ?? d.suspension.combineBlocked`. 오버레이를 열지 않고 채운 슬롯도 비우지 않는다. 받기 POST 403도 같다(`combineClaimBlocked`). 시트는 열어 둔다.

### 상태 목록

필수 상태(로딩·빈·오류 포함)

믹스 화면(`CombineClient`)
- 기본(받지 않은 결과 없음): 지금과 같다. 배너 없음.
- 받지 않은 결과 있음: 배너 표시, 믹스 CTA 비활성, CTA 아래 이유 문구. 슬롯 채우기·레시피 탐색은 가능.
- 믹스 제출 중(`loading`): 기존 «믹스하는 중».
- 믹스 응답 분기(위에서부터 우선, 앞이 맞으면 뒤는 보지 않는다)
  1. HTTP 403 + `code:'user_suspended'`: info 토스트(`data.error`), 결과 오버레이 없음, 슬롯 유지.
  2. HTTP 409 + `code:'pending_results_exist'`: info 토스트(`data.message`), 재료는 소각되지 않았으니 슬롯 유지. 화면이 낡아 배너가 없던 경우이므로 `GET /api/combine/pending`으로 개수를 다시 읽어 배너를 띄운다(읽기 실패 시 `router.refresh()`). `locked_item_not_allowed` 409는 지금처럼 `data.message`를 오버레이 셸에 보인다.
  3. `success && resultStatus==='pending'`: E의 오버레이. 배지가 하나도 안 나오므로 `resultBadges`가 빈 것만으로 «포인트만 받음»으로 보내면 안 된다. 이 분기가 `successPointsOnly`보다 먼저다.
  4. `success && noReward===true`: `emptyMessage`: «믹스를 마쳤어요. 이 레시피는 받는 보상이 없어요»(문구 확정은 UX 라이팅). `successPointsOnly`가 «0 포인트 획득!»으로 나가는 지금의 거짓 표시를 막는다.
  5. `success && 배지 없음 && points>0`: 기존 `successPointsOnly`.
  6. `success && 배지 있음`: 캐러셀. 잠긴 항목은 F 방식으로 변환.
  7. `success===false`: `data.message ?? d.combine.genericFail`(기존 유지).
- 네트워크 예외: 기존 `genericError` 에러 토스트.

받지 않은 결과 시트(`PendingResultsSheet`)
- 닫힘 / 열림·로딩: 시트가 열리면 GET 대기. `Skeleton` 타일 3개(`aspect-square rounded-2xl`)와 비활성 «받기». 8초 안에 응답이 없으면 오류로 넘어간다(`PendingItemsPickOverlay`의 `LOAD_TIMEOUT_MS` 선례).
- 로딩 오류: GET 실패 → 시트 본문에 `d.combine.claim.loadFailed` + «다시 불러오기» `Button ghost`. 푸터 버튼은 없다.
- 빈 상태: 목록이 비었다(다른 기기에서 이미 받음) → `EmptyState`(title `d.combine.claim.noPending`), 푸터는 «닫기». 배너는 `router.refresh()`로 지운다.
- 준비됨·빈칸 충분: 목록 + «받기».
- 준비됨·빈칸 모자람: 목록 + 부족 블록 + 인벤토리 링크(받기 버튼 없음).
- 받는 중: «받는 중» + `aria-busy`, 재클릭 막음, 시트 닫기는 막지 않는다(닫아도 요청은 끝까지 간다).
- 받기 결과
  - 성공 → 시트 닫음 + `BadgeRevealOverlay`(C).
  - 409 `insufficient_slots` → free·needed로 부족 블록 갱신.
  - 409 `no_pending` → info 토스트 + 시트 닫음 + `router.refresh()`.
  - 403 `user_suspended` → info 토스트(`data.error`), 시트 유지.
  - 404/500/네트워크 → error 토스트(`data.error ?? d.combine.claim.failed`), 시트 유지, 버튼 재활성.

레시피 행
- 기본 / 포인트만 / 배지만 / 배지+포인트: 기존.
- 보상 없음: 중립 아이콘 + «보상 없음».
- 잠긴 채 지급: «잠김» 칩.
- 공개 예정: 기존.

설명 영역
- 없음(렌더 안 함) / 3줄 이하(토글 없음) / 길어서 접힘(더 보기) / 펼침(접기).

온보딩 연출 모드(`questStep`): 배너·받기·CTA 차단 모두 비활성(`pendingCount`를 0으로 본다). 연출 결과는 지금 그대로다.

### 모션

- 시트 열고 닫기: `BottomSheet`의 기존 전환을 그대로 쓴다. 새 모션을 만들지 않는다.
- «받기» ↔ «받는 중»: `SwapText`(기존). 푸터가 «받기 버튼» ↔ «부족 블록»으로 바뀔 때는 `PendingItemsPickOverlay`처럼 `--duration-quick`(150ms) 페이드 또는 전환 없이 즉시 교체. 둘 중 단순한 쪽으로 한다.
- 배너 등장·소멸: 모션 없음(즉시). 오버레이가 덮은 뒤에 사라지므로 끊김이 보이지 않고, 믹스 직후 나타나는 것도 오버레이를 닫은 뒤라서다.
- 설명 «더 보기»: 높이 전환 없이 `line-clamp` 해제만 한다.
- 받기 성공 연출: `BadgeRevealOverlay` 기본 캐러셀(기존). 추가 연출 없음.
- 모든 전환은 `prefers-reduced-motion`을 따르는 기존 컴포넌트 안에서만 일어나게 한다. 직접 `animate-*`를 새로 쓰지 않는다.
- 토스트(z-60)는 오버레이가 열려 있는 동안 띄우지 않는다. 오버레이를 닫은 뒤에 띄운다(`closeResult`의 `testMixNotice` 선례).

### 기기·접근성

- 360px 기준으로 확인하고 320px에서도 확인한다. 배너는 `flex-wrap`이라 버튼이 아래로 내려가도 깨지지 않아야 한다. 모든 한국어 문장은 `break-keep wrap-break-word`, 두 줄 이상은 `text-pretty`(제목·짧은 문구는 `text-balance`)로 마지막 한 글자만 떨어지는 줄을 막는다.
- 터치 영역: «받기»와 «더 보기»와 «인벤토리 보기»는 44px 이상(`Button md`, 링크는 `min-h-11`). 타일은 터치 대상이 아니다.
- 시트: `BottomSheet`가 안전영역과 포털(z-50)을 처리한다. 푸터는 `footer` 고정, 목록이 길면 본문만 스크롤한다. 시트 높이는 compact(최대 75vh)다.
- 오버레이(z-60)는 `BadgeRevealOverlay` 래퍼가 탭바 숨김·`main` 스크롤 잠금·430px 컬럼을 처리한다. 새로 만들지 않는다.
- 5칸 3+2 그리드와 설명 3줄 접힘이 겹친 레시피는 320x568(iPhone SE)에서 CTA까지 한 화면에 안 들어올 수 있다. 화면 전체가 스크롤되는 구조이므로 CTA가 접히지 않는지만 확인한다(고정 CTA를 새로 만들지 않는다).
- iOS Safari: 시트가 열린 채 주소창이 접히는 상태에서 푸터가 가려지지 않는지 `BottomSheet`의 기존 처리에 맡기고, 확인만 한다.
- 접근성: 배너는 일반 문단+버튼이고 `role="alert"`를 쓰지 않는다(상시 상태라 라이브 리전으로 알리지 않는다). 받기 성공은 `BadgeRevealOverlay`의 라이브 리전이 `resultMessage`를 알린다. 잠긴 결과 타일은 `aria-hidden`(장식)이고 «잠긴 아이템 배지» 텍스트가 이름을 전한다.

### 마감 메모

- 빈칸 모자람은 오류가 아니다. 빨강·경고 아이콘·진동을 쓰지 않는다. 배너와 부족 블록은 중립 면(`--surface`)과 글자 위계(제목 bold, 수치 text-sm)로만 구분한다.
- 시트 안에 카드를 또 넣지 않는다. 결과 타일은 면 위에 바로 놓는다. 배너 안에 안쪽 카드도 두지 않는다.
- 잠긴 결과에 등급 그라데이션·글로우·자물쇠 확대·반짝임을 더하지 않는다. `LockedTile`은 차분한 중립 타일이며 등급은 `RarityBadge` 칩 하나다.
- 습관적 가운데 정렬 금지. 문단·수치·링크는 좌측 정렬이고, 오버레이 셸(`emptyMessage`)만 기존 그대로 가운데다.
- 이모지·장식 일러스트·카운트다운식 압박 문구(«서둘러 받아요» 등)를 쓰지 않는다. 결과에는 기한이 없다(사용자 결정 2). «기한» «만료» 같은 말을 어떤 문구에도 넣지 않는다.
- 새 아이콘 금지. 필요한 것은 기존 `PackageIcon`·`LockIcon`(`LockedTile` 안)뿐이다. «보상 없음»에 코인 아이콘을 쓰지 않는다(포인트처럼 보인다).
- 숫자 표기: 빈칸·필요 칸은 `d.capsule`과 같은 어휘로 맞춘다. 캡슐은 «빈칸 {free}개, 열려면 {needed}개가 필요해요»이고 믹스는 «지금 빈칸 {free}개, 받으려면 {needed}개가 필요해요»다. 설명 문구에 퍼센트나 진행률 게이지를 넣지 않는다.
- UX 라이팅: 고정 용어 «획득» «빈칸» «인벤토리» «잠김» «믹스»를 쓴다. «잠금» 대신 «잠김», «보상 없음»은 레시피 용어로 쓴다. 제목에는 마침표를 쓰지 않는다. 오류는 현상→원인→해결 3단계(`d.combine.claim.*`는 이미 이 구조).
- 새 문구가 필요한 곳은 `lib/i18n/ko.ts`의 `d.combine` 아래 `pendingBanner`(제목·보조·버튼), `pendingSheet`(제목·안내·빈칸 줄·부족 제목·부족 수·남아 있음·인벤토리 링크·받는 중·다시 불러오기), `pendingBlockedNote`, `resultPendingCounts`, `noRewardResult`, `noRewardLabel`, `descriptionMore`·`descriptionLess`, `claimedToast`(resultMessage)다. 문구를 코드에 직접 쓰지 않는다.
- 믹스 CTA를 비활성으로 만들 때 기존 `opacity-30`만으로는 이유가 안 보인다. 반드시 이유 문구를 CTA 아래에 둔다. 말 없이 막지 않는다.
- 잠긴 결과의 필요한 양(`unlockRequired`)이 응답에 없는 것을 클라이언트에서 추측하거나 기본값으로 채우지 않는다. 줄을 생략한다.

### 범위

`ui` 유형이므로 `ds` 연결 범위 분류는 해당 없다. MODULAR(`design-system/`) 변경과 Story 작성도 필요 없다. 변경 범위는 서비스 쪽 파일로 한정한다.
- `jam-web/src/app/(main)/combine/` 아래: `page.tsx`(pendingCount prop), `CombineClient.tsx`, `RecipeRewardRow.tsx`, 신규 `PendingResultsSheet.tsx`, `CombineClient.test.tsx`(와 시트·행 시험).
- `jam-web/src/lib/i18n/ko.ts`: `d.combine` 아래 새 문구.
- 서버 코드(`lib/combine/*`, `app/api/combine/*`)와 응답 계약은 건드리지 않는다. 클라이언트가 가져올 때는 `lib/combine/pending.ts`의 `import type`만 쓴다. 이 파일은 서버 전용이라 값을 가져오면 번들링에서 터진다(`next dev`로 화면을 열어 확인할 것).

### 완료 조건

1. 받지 않은 결과가 있으면 믹스 화면 상단(탐색·믹서 모두)에 «받지 않은 믹스 결과가 N개 있어요»와 «받기»가 보이고, 믹스 CTA는 비활성이며 그 아래에 이유 한 줄이 있다. 없으면 배너도 이유 문구도 없다.
2. «받기»를 누르면 시트가 열리고, 열린 결과는 이름·그림, 잠긴 결과는 `LockedTile`+«잠긴 아이템 배지»+등급 칩으로 보인다. 잠긴 결과의 이름·그림은 DOM 어디에도 없다.
3. 빈칸이 충분하면 «받기» 한 번으로 전부 받고 `BadgeRevealOverlay`가 «믹스 결과 N개를 받았어요»와 함께 뜬다. 닫으면 배너가 사라지고 믹스 CTA가 활성이 된다. 같은 결과를 두 번 받는 길은 없다(제출 중 재클릭 막힘, 409 `no_pending` 처리).
4. 빈칸이 모자라면 시트에 «지금 빈칸 F개, 받으려면 N개가 필요해요»와 인벤토리 링크가 보이고 «받기»는 없다. POST가 `insufficient_slots`를 줘도 같은 블록으로 바뀐다. 오류색은 쓰지 않았다.
5. 믹스 직후 결과가 받지 않은 상태로 남으면(`resultStatus:'pending'`) 오버레이에 숫자가 든 안내가 나오고(포인트가 있으면 같이), «0 포인트 획득!»이나 서버 일반 문구가 나오지 않는다. 닫으면 배너가 나타난다.
6. 믹스 직후 잠긴 결과는 캐러셀에서 잠긴 카드(가린 이름, `LockedTile`)로 나오고 빈 이름 카드가 나오지 않는다.
7. 보상 없음 레시피는 행에 «보상 없음»이 보이고, 믹스 결과에 «0 포인트 획득!»이 나오지 않으며 안내 문구가 나온다. 레시피 설명은 믹서 화면에 있으면 보이고 길면 3줄로 접힌다. 없으면 영역이 없다.
8. 칸이 5개인 레시피가 360px에서 3+2 배치로 모두 보이고 채워진다. 4칸 이하는 지금과 같다.
9. 이용 정지 403은 info 토스트, 409 `pending_results_exist`는 info 토스트+배너 갱신이며, 두 경우 모두 슬롯이 유지된다.
10. 시험: `CombineClient.test.tsx`에 (a) pending 응답 분기 (b) 보상 없음 분기 (c) 잠긴 결과 변환 (d) 403·409 분기 (e) 배너·CTA 차단, 시트 시험에 (f) 로딩·오류·빈·부족·성공·`no_pending`, 행 시험에 (g) 보상 없음·잠김 칩을 포함한다. `scripts/verify.sh` 통과.
11. 메인 트리 `next dev`로 `/combine`을 실제로 열어 서버·클라이언트 경계 위반이 없는지 확인한다(`lib/combine/pending.ts`를 클라이언트가 값으로 가져오지 않았는지).
12. 사후 리뷰(모드 ②)용 캡처: 360px 기준 배너(탐색·믹서), 시트(충분·부족·잠긴 결과 포함), pending 오버레이, 5칸 믹서, 보상 없음 행, 설명 접힘·펼침.

### 판정 근거

근거는 네 가지다.
1. 서버 계약(1회)을 보면 받지 않은 결과를 받으려면 «목록(GET) → 전부 한 번에 받기(POST)»가 필요하고, 빈칸 부족은 409의 free·needed로 온다. 이 흐름은 `CapsuleSheet`의 본문, «빈칸 모자람 블록 + 인벤토리 링크» 푸터와 같다. 그래서 시트 껍데기(`BottomSheet` + `footer`)와 푸터 구조를 그대로 따른다.
2. `JamFillPanel`은 잼 수량 입력 전용이라 여기에 맞지 않는다. 받기는 입력이 없는 전부-또는-없음 동작이다. `JamFillPanel`은 재사용하지 않는다.
3. 지금 `CombineClient`(439~447줄)에는 거짓 표시 두 가지가 있다. 첫째, `noReward` 성공이 «0 포인트 획득!»으로 보인다. 둘째, 잠긴 결과는 id가 ''라서 `rewardBadges.find`가 실패하고 이름이 빈 카드가 나온다. 둘 다 완료 조건에 넣는다.
4. 새 시트와 배너, 5칸 그리드, 레시피 행의 칩은 눈에 보이는 변경이라 승인 항목으로 올린다. 모든 기존 컴포넌트와 토큰으로 구성되므로 새 토큰은 없다.

## 완료 조건

### 구현 범위 (게이트 판정 대상, 회차마다 해당 항목)

- 새 믹스 결과에 기한이 붙지 않는다. 옛 개체는 그대로다.
- 빈칸이 모자라면 결과가 받지 않은 상태로 남고(조용히 건너뛰지 않음), 그 동안 새 믹스가 거부되며, 빈칸을 만든 뒤 받으면 지급된다. 재료는 소모되고 같은 결과를 두 번 지급하지 않는 시험이 있다.
- 잠긴·장착한 개체는 재료로 거부된다. 등급 올리기가 같은 트라이브·같은 등급 5개만 받고 Mystic·등급 혼합을 거부하며, 고른 컬렉션·이름의 바로 위 등급 개체를 지급한다.
- 레시피에 설명 칸이 있고 보상 없음을 저장할 수 있다. 옛 어드민의 저장은 옛 검증 그대로다.
- 공개 기간이 끝난 결과의 레시피는 믹스 화면에서 쓸 수 없다. 이용 정지 중 믹스가 막힌다.
- 마이그레이션이 옛 객체를 바꾸지 않으며 되돌림 SQL을 싣는다. `docs/service/prd/`와 엔진 문서에 반영되어 있다.

### 후속 범위 (담당: 카리나, 시점: 사용자 승인 뒤)

- 사용자 확인 1~4번의 결정을 이 티켓 「사용자 결정」 절에 기록한다. SQL 실행은 승인과 롤백 실측 뒤에 한다. 어드민 화면 실렌더 확인은 카리나가 머지 뒤 push 전에 한다.
