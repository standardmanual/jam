# [Service] JAM2 드랍·픽업 서버: 잠긴 채 드랍과 가림, 이용 정지·꺼진 장소·가득 참 거절, 자기 드랍, 개체 이력

## 핵심 요약

- 요구사항: 운영 로직 9.3·9.5절에 맞춰 드랍·픽업 서버를 고친다. (1) 잠긴 채 드랍하고 픽업한다. 채우다 만 잠긴 개체를 드랍하면 채운 양은 사라지고 돌려주지 않는다(7.2절). 드랍 전에 사라질 양을 알려 줄 수 있어야 한다. 지도와 장소의 드랍 목록은 잠긴 개체를 «잠김»과 등급만으로 내리고 이름·그림·설명·컬렉션·트라이브·일련번호를 싣지 않는다(7.3절). (2) 이용 정지 중 드랍·픽업 거절(403 `user_suspended`). (3) 꺼진 장소에서 드랍도 픽업도 못 하고 목록에서도 안 보인다(꺼진 장소의 드랍은 그대로 남고 다시 켜면 돌아온다). (4) 인벤토리가 가득 차면 픽업하지 않고 안내한다. (5) 자기가 드랍한 것은 픽업할 수 있지만 챕터 점수와 드랍·픽업 횟수에 세지 않는다. (6) 드랍과 픽업을 개체 이력에 남긴다. 화면은 4-6이다.
- 구현 계획: 시작 때 사용자 결정 3건을 질문하고 파일 단위 계획을 옮겨 쓴다. SQL은 사용자 승인과 롤백 실측 뒤 카리나가 실행한다. 규모에 따라 1~2회(1회 거절 규칙과 이력, 2회 잠긴 채 드랍·픽업과 가림).
- 관련 파일(2026-10-18 조사, 시작 때 아현이 줄 위치를 다시 확인한다): 드랍 `jam-web/src/app/api/drops/route.ts`(POST 298~401줄, 목록 GET 207줄), 목록 `app/api/drops/poi/[poiId]/route.ts`(99줄, `poi.is_active`를 보지 않고 잠긴 개체를 가리지 않음), 픽업 `app/api/drops/[dropId]/pickup/route.ts`(POST 226줄, 순서: 드랍 존재 → 장소 조회 → 500m → `isPoiBlocked` → GPS 조작 감지 → `pickup_drop` RPC → `after()` 지표 → 피드·알림), DB 함수 `create_user_drop`(마이그레이션 108→181→238)과 `pickup_drop`(004→007→044→047→108→181), 장소 차단 `lib/abusing/poi-block.ts`(`poi_blocks`, 조회 실패 시 fail-open), 이용 정지 `lib/suspension/suspension.ts`(`assertNotSuspended`), 개체 이력 `custody_events`(108)와 `inventory_item_events`(235), 횟수 지표 `lib/badge-engine/jamActionDropMetrics.ts`(4개 지표, `poi_drops`에서 DISTINCT로 셈).

## 배경 / 문제 정의

238이 잠긴 개체의 유저 드랍을 DB에서 막았지만 이는 묶음 4 전까지의 임시 방어선이다. 운영 로직은 잠긴 채 드랍·픽업을 허용하고 채운 양이 사라지는 규칙을 둔다(유저 사이에 잼을 옮기는 길을 막기 위해). 지금 드랍·픽업 라우트에는 이용 정지 검사가 없고, 픽업은 꺼진 장소를 보지 않으며(비교표 4.1절), 드랍 목록은 잠긴 개체의 이름·그림·일련번호를 그대로 내린다.
조사에서 확인된 사실: 자기 드랍 픽업은 지금 허용되고(`pickup_drop`에 검사 없음, 라우트의 `cannot_pickup_own_drop` 문구 매핑은 죽은 코드), 픽업 쪽 JAM 지표 3개는 이미 자기 드랍을 뺀다(비교표 3.8절의 «빼는 규칙 없음»은 코드와 맞지 않음). 드랍한 횟수 지표 쪽과 챕터 점수(묶음 5)에서의 처리는 시작 때 확인한다.
공용 DB 주의: 옛 프로덕션 코드가 같은 테이블·함수를 쓴다. 새 칸·새 테이블·새 함수·새 설정 행만 덧붙이고 기존 칸의 뜻은 바꾸지 않는다. 축소는 묶음 6이다. SQL은 아현이 파일로 쓰고, 실행은 사용자 승인과 롤백 실측 뒤 카리나가 한다.

## 시작 전에 사용자에게 확인할 것 (주요 결정, 질문창)

1. **자기 드랍의 횟수 제외 방식**: 지금 픽업 지표는 조회 때 자기 드랍을 빼므로 그대로 두고 드랍한 횟수·챕터 점수(묶음 5)가 같은 기준을 쓰게 «세는 방법» 한 곳에 모은다(추천). 대안은 `poi_drops`에 «자기 픽업» 표시 칸을 새로 더하는 것이다.
2. **개체 이력의 기록 위치**: 드랍·픽업 이력을 `custody_events`(지금 DB 함수가 쓰는 곳)에 그대로 두고 `inventory_item_events`(235)에는 «잠김과 열림, 채움»만 둔다(추천). 대안은 둘에 모두 쓰는 것이다(중복 저장).
3. **채운 양 소멸의 안내**: 드랍 전에 사라질 양을 알려 주는 조회 API를 새로 두고(추천, 화면은 4-6), 드랍 API는 확인 없이 진행한다. 대안은 드랍 요청에 «확인했음» 값을 받는 것이다.

## 사용자 결정과 조사 결과 (2026-10-18)

1. 자기 드랍의 횟수 제외: **조사로 해소됐다.** `lib/badge-engine/jamActionDropMetrics.ts`의 4개 지표는 이미 조회 규칙으로 자기 드랍을 빼고 «서로 다른 개체·유저 수»로만 센다(같은 개체를 번갈아 놓고 줍는 왕복이 지표를 부풀리지 못함). 새 칸을 더하지 않는다. 챕터 점수(묶음 5)가 같은 기준을 쓰도록 «자기 픽업 판별 함수» 하나를 남긴다.
2. 개체 이력: **`custody_events`에 그대로 둔다**(드랍·픽업은 지금처럼 `create_user_drop`·`pickup_drop`이 `UserDrop`·`Pickup`을 남김). `inventory_item_events`에는 «잠긴 개체를 드랍할 때 사라진 채운 양»만 `dropped`(amount=사라진 양, filled_after=0)로 더한다.
3. 채운 양 소멸 안내: **사라질 양을 읽는 조회 API를 새로 둔다.** 화면이 드랍 확인 단계에서 읽어 «채운 잼 N은 사라져요»를 보이고(4-6), 드랍 API는 확인 값을 받지 않는다. 채운 양이 0이거나 열린 개체는 0을 돌려준다.
- DB(마이그레이션 239): `create_user_drop`은 잠긴 개체도 드랍하고 채운 양을 0으로 되돌리며 이용 정지를 거절한다. `pickup_drop`은 이용 정지와 꺼진 장소(`poi_inactive`)를 거절한다(조사: 둘 다 `is_active`·정지를 보지 않았다). 서명·권한·반환 형식은 그대로다.

- DB 적용 완료(마이그레이션 239): `create_user_drop`(잠긴 개체도 드랍, 채운 양 0, 사라진 양이 있으면 `inventory_item_events` `dropped` 한 줄, 반환에 `lost_fill`, 이용 정지 `user_suspended`)와 `pickup_drop`(이용 정지 `user_suspended`, 꺼진 장소 `poi_inactive`). 롤백 실측 24건 통과(열린 개체 드랍, 채우다 만 잠긴 개체 드랍 후 채운 양 0·필요한 양·잠김·일련번호 그대로·칸 -1·이력 한 줄, 채운 양 0 잠긴 개체 드랍, 정지 중 드랍·픽업 거절과 변화 없음, 남의 개체·이미 드랍함, 잠긴 채 픽업 후 소유 이전·잠김 유지·채운 양 0·일련번호·Pickup 이력, 꺼진 장소 픽업 거절·드랍 보존·다시 켜면 픽업, 가득 참, 자기 드랍 줍기 허용, 이미 주움, 권한). 적용 뒤 확인: 두 함수 SECURITY DEFINER·오버로드 1개·`authenticated` 실행 권한 없음·새 본문 포함. 남은 일은 앱이다(아래 구현 계획).

## 상세 요구사항

### 서비스/코드베이스 관점

- **잠긴 채 드랍**: `create_user_drop`(238의 `locked_item` 거절)을 «잠긴 개체도 드랍하되 `unlock_filled`를 0으로 되돌리고 필요한 양·잠긴 까닭은 그대로 둔다»로 바꾼다. 같은 이름의 `CREATE OR REPLACE`이고 열린 개체의 동작은 그대로다. 238이 쓴 «locked_item을 409로 거절» 시험은 새 규칙(드랍 성공, 채운 양 0)으로 바꾼다.
- **잠긴 채 픽업**: 픽업한 유저는 잠긴 채 받고 필요한 양은 드랍하기 전과 같고 채운 양은 0이다. 일련번호는 그대로다. 인벤토리가 가득 차면 픽업하지 않는다.
- **가림**: 드랍 목록 API는 잠긴 개체의 이름·그림·설명·컬렉션·트라이브·일련번호를 서버에서 비운다(`locked: true`, 등급만). 3-4에서 만든 가림 방식(서버에서 비우고 클라이언트로 내리지 않음)을 따른다. 픽업 응답도 잠긴 채 받은 경우 같은 정보를 싣지 않는다.
- **사라질 양 조회**: 내 잠긴 개체를 드랍하기 전에 채운 양(사라질 양)을 읽는 API. 열린 개체나 채운 양이 0이면 0이다.
- **이용 정지**: 드랍·픽업 라우트가 `assertNotSuspended`로 먼저 막는다(403 `user_suspended`). DB 함수는 한 번 더 막는다(`capsule_fill`·`locked_item_fill` 패턴).
- **꺼진 장소**: 픽업은 꺼진 장소(`poi.is_active = false`)를 `drop_not_found`처럼 거절하고, 드랍 목록 API(`drops/poi/[poiId]`)는 꺼진 장소의 드랍을 내리지 않는다. 드랍하기는 이미 막혀 있다(330줄 근처). 드랍 데이터는 지우지 않는다.
- **장소 차단**: 유지한다. 조회 실패 시 fail-open인 현재 동작을 바꿀지는 시작 때 확인하고 이 티켓에서는 바꾸지 않는다.
- **자기 드랍**: 픽업은 허용 그대로이고, 드랍한 횟수·픽업 횟수 지표가 자기 드랍을 세지 않는지 확인하고 빠진 곳을 고친다. 죽은 코드(`cannot_pickup_own_drop` 문구 매핑)를 정리한다. 챕터 점수 연결은 묶음 5이므로 «자기 픽업은 점수 대상 아님»이 드러나는 판별 함수 하나를 남겨 둔다.
- **이력**: 드랍·픽업이 개체 이력에 남는지(드랍한 사람, 장소, 시각, 픽업한 사람과 시각) 확인하고 빠진 칸이 있으면 더한다. 잠긴 개체의 채운 양 소멸도 이력에 남긴다.
- 새 칸과 새 함수는 덧붙이기만 한다(`create_user_drop`·`pickup_drop`을 바꾸는 것은 시작 때 사용자 승인을 받는다). 생성 타입을 같은 커밋에 맞춘다.

## 구현 계획 (회차)

1회로 돌린다(예상 파일 약 12개, 아현 판단으로 크면 «서버 거절 규칙»과 «가림·사라질 양 조회»로 나눈다). DB는 마이그레이션 239가 적용되어 있다(위). 앱 파일 단위 계획(경로는 jam-web/src 기준, 줄 위치는 아현이 다시 확인):

1. `app/api/drops/route.ts` POST: RPC 전에 `assertNotSuspended`(403 `user_suspended`, 문구는 `d.suspension` 쪽에 드랍용을 더함), RPC 응답 `user_suspended` 매핑, 성공 응답에 `lost_fill`(사라진 양)을 `lostFill`로 싣는다. 238 때 넣은 `locked_item` 매핑은 DB가 더는 그 코드를 돌려주지 않으므로 제거한다(트리거 오류 매핑은 유지).
2. `app/api/drops/[dropId]/pickup/route.ts` POST: `assertNotSuspended`를 맨 앞에 두고(GPS 판정보다 앞), 장소가 꺼져 있으면(`is_active`) 줍지 못하게 거절(`drop_not_found`와 같은 404, 정보 누출 없음), RPC 응답 `poi_inactive`·`user_suspended` 매핑(`user_suspended`는 403), 응답이 잠긴 개체의 이름·그림·일련번호를 싣지 않게 한다. 죽은 코드(`cannot_pickup_own_drop` 문구 매핑)를 정리한다.
3. `app/api/drops/poi/[poiId]/route.ts` GET: 꺼진 장소는 드랍을 내리지 않고(빈 목록), 잠긴 개체는 서버에서 이름·그림·설명·컬렉션·트라이브·일련번호를 비우고 `locked: true`와 등급만 싣는다(3-4 가림 방식, 클라이언트로 내리는 값에 없음).
4. `app/api/drops/route.ts` GET(장소별 드랍 개수)와 지도 쪽 조회: 꺼진 장소의 드랍이 개수에 잡히지 않는지 확인하고 빠진 곳을 고친다.
5. 신규 `app/api/inventory/items/[itemId]/drop-loss/route.ts` GET(사라질 양 조회): 내 개체의 `unlock_filled`(잠긴 개체만, 열린 개체·0은 0)를 `{ lostFill }`로 돌려준다. UUID 아님 404, 내 개체가 아니면 404, 401. 신규 순수 계약 `lib/drop/drop-loss-contract.ts`.
6. 신규 `lib/drop/self-pickup.ts`: `isSelfPickup(drop, userId)` 판별 함수 하나(챕터 점수가 묶음 5에서 쓴다). `jamActionDropMetrics.ts`의 «자기 드랍을 뺀다» 규칙과 같은 정의인지 시험으로 고정한다.
7. 시험: 위 라우트의 `__tests__/route.test.ts`(정지 403, 꺼진 장소, 잠긴 개체 가림에 DOM·응답 어디에도 값이 없음, `lostFill` 응답, 남의 개체 404), `drop-loss` 시험, `self-pickup` 시험. 문서: `docs/service/prd/02_DATA_MODEL.md`(239), 드랍·픽업 PRD(있으면 `docs/service/prd/` 아래에서 찾는다), `docs/service/badge-engine/` 해당 절, `lib/inventory/lockedItem.ts` 머리 주석(드랍 경로 서술 정정).

## 완료 조건

### 구현 범위 (게이트 판정 대상)

- 이용 정지 중 드랍·픽업이 403 `user_suspended`로 막히고 아무것도 바뀌지 않는다. 꺼진 장소에서는 픽업이 막히고 드랍 목록에서 안 보이며, 장소를 다시 켜면 돌아온다.
- 잠긴 개체를 잠긴 채 드랍하고 픽업할 수 있고, 채운 양은 0이 되며 필요한 양과 일련번호는 그대로다. 열린 개체의 드랍·픽업은 그대로다(롤백 실측 포함).
- 드랍 목록과 픽업 응답에 잠긴 개체의 이름·그림·설명·컬렉션·트라이브·일련번호가 없다(서버에서 비움, 시험으로 고정).
- 자기 드랍을 줍는 것은 허용되고 횟수 지표에 세지 않는다. 드랍·픽업이 개체 이력에 남는다.
- 마이그레이션이 옛 객체의 서명·권한을 바꾸지 않고 되돌림 SQL을 싣는다. `docs/service/prd/`와 엔진 문서에 반영되어 있다.
