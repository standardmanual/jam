# [Content] JAM2 액티비티 배지 컨텐츠와 어드민: 55개 계열 입력, 재활용 후보 확정·나머지 비활성화, 배지 양식

## 핵심 요약

- 요구사항: 운영 로직 10장의 새 액티비티 배지 컨텐츠와 어드민을 만든다. (1) 배지 양식에서 계열, 가지, 종류(등급형·반복형·레벨형), 등급, 조건, 공개 기간, 포인트, 숨김 여부를 정한다(기한 칸은 두지 않는다). (2) 지금 액티비티 배지 634개(195계열) 가운데 다시 쓸 약 269개(`액티비티 배지 재활용 후보.md`로 확정)를 남기고 나머지를 끈다(다시 쓰는 계열의 게이트 조건은 뺀다). (3) 새 55개 계열(`06 액티비티 배지.md`)을 입력한다. (4) 배지 포인트의 등급별 일괄 값(Common 10, Rare 20, Epic 50, Mystic 100, 레벨형은 레벨마다 10, 숨김 배지는 0)은 밸런스 설정 화면 몫(묶음 7)이므로 이 티켓은 값을 배지 행에 넣는다. 일괄 입력 도구와 밸런스 화면은 묶음 7이다.
- 구현 계획: 시작 때 사용자 결정 3건을 질문하고 파일 단위 계획을 옮겨 쓴다. 대량 데이터 변경은 SQL 파일(또는 스크립트)로 남기고 사용자 승인 뒤 카리나가 실행한다(드라이런·사후 검증 필수). 규모에 따라 1~3회(1회 배지 양식, 2회 비활성화, 3회 새 계열 입력).
- 관련 파일(2026-10-18 조사): 어드민 `jam-web/src/app/admin/badges/`(`BadgeForm.tsx`), 배지 계열 `app/admin/` 계열 화면, 시드 `jam-web/supabase/migrations/seed_v5_activity_badges.sql`, 문서 `docs/service/content/ACTIVITY_BADGES.md`, `docs/plan/jam2/service-redesign/액티비티 배지 재활용 후보.md`, `docs/plan/jam2/tribe-rethink/manuscript/06 액티비티 배지.md`, 조건 키 `jam-web/src/lib/badge-engine/conditionRegistry.ts`(4-4가 새 키를 더함).

## 배경 / 문제 정의

지금 `badges`에는 비활성 칸이 없다(`deleted_at`, `valid_until`뿐). 재활용 후보 밖의 약 365개를 «끄는» 방법(소프트 삭제 `deleted_at`, 공개 기간 `valid_until`, 또는 새 칸)을 정해야 한다. 받은 기록은 154건(유저 4명)이라 영향 범위는 작지만 이미 받은 배지는 그대로 남아야 한다(받은 배지에는 기한이 없다). 4-4가 새 조건 키와 숨김·가지 칸을 만든 뒤에 이 티켓이 그 칸을 어드민에서 입력하게 한다.
공용 DB 주의: 옛 프로덕션 코드가 같은 테이블·함수를 쓴다. 새 칸·새 테이블·새 함수·새 설정 행만 덧붙이고 기존 칸의 뜻은 바꾸지 않는다. 축소는 묶음 6이다. SQL은 아현이 파일로 쓰고, 실행은 사용자 승인과 롤백 실측 뒤 카리나가 한다.

## 시작 전에 사용자에게 확인할 것 (주요 결정, 질문창)

1. **재활용 후보 밖 배지를 끄는 방법**: 소프트 삭제(`deleted_at`)로 끄고 받은 기록은 그대로 둔다(추천, 새 칸이 필요 없고 «새로 발급되지 않음»이 기존 코드로 보장됨). 대안은 `valid_until`을 과거로 두는 것이다(배지가 목록에 남는다).
2. **새 55개 계열의 입력 방식**: 원고(`06 액티비티 배지.md`)를 파싱해 SQL 시드 파일로 만들어 드라이런 → 사후 검증 순으로 넣는다(추천, 기존 대량 마이그레이션 방식과 같음). 대안은 어드민에서 하나씩 입력하는 것이다(운영 부담).
3. **재활용 후보 확정 범위**: 문서에 적힌 후보 약 269개를 그대로 확정하고 이번에 추가·제외하는 항목은 시작 때 사용자가 표로 확인한다(추천). 대안은 후보를 이번에 다시 고르는 것이다.

## 사용자 결정 (2026-10-19 질문창 답, 카리나 기록)

1. **재활용 후보 밖 배지를 끄는 방법**: 소프트 삭제(`deleted_at`)로 끈다(추천). 받은 기록(`user_activity_badges`, 154건)은 지우지 않는다. 대상은 `type='activity'`이면서 재활용 후보(`액티비티 배지 재활용 후보.md` 대응 60계열 269개)에 들지 않는 배지다(폐기 112계열 342개 + 겹치는 단일 배지 23개).
2. **재활용 처리**: 확정한 기존 269개는 그대로 두고 게이트 조건(`gate_mission_badge`, `cross_between_axis`)만 뺀다. 원고 계열 중 «새로 만듦»만 새 행으로 입력한다(추천). 재활용 계열의 이름·설명을 원고 문구로 맞추는 일은 하지 않고 잔여 이슈로 남긴다.
3. **엔진 판정이 아직 없는 10계열은 입력 보류**: 1-4, 2-2, 3-4, 3-5, 5-1, 5-2, 5-4, 5-5, 8-4, 8-5(추천). 판정이 안 되는 배지를 넣으면 아무도 못 받는 배지가 생기므로 이번에 넣지 않는다. 엔진 보강은 별도 후속 티켓으로 만들어 4-6 전후에 처리하고 그때 입력한다. 5-6은 원고에 이름·설명이 아직 없어 이번에도 입력하지 못한다.
4. **새 배지의 이미지**: 가장 가까운 기존 배지(재활용 후보)의 이미지를 임시로 복사한다(사용자 선택, 추천은 비워 두기였다). 어느 새 계열이 어느 기존 배지의 이미지를 쓰는지는 시드 SQL을 승인받을 때 표로 보여 준다.
5. **입력 방식**: 원고(`06 액티비티 배지.md`)를 파싱하는 스크립트가 시드 SQL을 만들고 드라이런 후 사후 검증 순으로 넣는다(티켓의 추천 그대로).
- **입력 대상 새 계열은 18개에서 5-6을 뺀 17개**: 판정 키가 이미 있는 것 9개(3-2, 6-1, 6-2, 8-3, 8-6, 8-7, 8-11, 8-12)와 4-4가 더한 키(잼 4, 캡슐 1, 잠긴 아이템 배지 1, 챕터 1, 트라이브 조건 2)로 판정되는 9개 가운데 위 보류를 뺀 것이다(번호 대조는 시드 스크립트를 만들며 아현이 확인하고 어긋나면 멈춰 보고한다).
- **공용 DB 영향**: 소프트 삭제와 새 행 입력은 옛 프로덕션 코드가 도는 공용 DB에 바로 반영된다(유저 4명이 받은 154건은 남지만 꺼진 배지가 배지함·목록에서 사라질 수 있다). 2회·3회 SQL을 승인받을 때 이 영향을 다시 보여 준다.

## 상세 요구사항

### 서비스/코드베이스 관점

- **배지 양식(어드민, shadcn/ui 표준)**: 계열, 가지, 종류, 등급, 조건, 공개 기간, 포인트, 숨김 여부를 입력한다. 기한 칸은 두지 않는다. 4-4가 더한 칸을 쓴다. 저장 검증은 서버에서 한다.
- **비활성화**: 결정 1에 따라 재활용 후보 밖 배지를 끈다. 이미 받은 기록(`user_activity_badges`)은 지우지 않는다. 드라이런으로 대상 수를 먼저 확인한다.
- **새 계열 입력**: 결정 2에 따라 55개 계열을 넣는다. 조건은 4-4가 만든 조건 키로 적는다. 등급별 기준값(Common은 그 종목 보통 퍼소나의 한 번 활동, Rare는 1.5배, Epic은 열심 기준선의 한 번 활동, Mystic은 그 위의 의미 있는 숫자), 레벨형 기준값(Lv.1은 보통 퍼소나의 한 주 양, 레벨마다 1.5~2배), 잼 이정표(1,000, 5,000, 20,000, 50,000, 100,000), 횟수 배지(1·5·20·50회 등)는 스펙 10.5절을 따른다.
- **게이트 조건 정리**: 다시 쓰는 계열의 게이트 조건(옛 미션 게이트)은 뺀다(10.7절).
- 대량 변경은 SQL 파일로 `jam-web/supabase/migrations/`에 남기고 롤백 실측(또는 드라이런)과 사후 검증 쿼리를 싣는다. 생성 타입을 같은 커밋에 맞춘다.

### UI/UX 관점 (해당 시)

- 어드민 폼은 UX 라이팅 가이드를 따른다. 실렌더는 카리나가 머지 뒤 push 전에 로컬에서 한다.

## 구현 계획 (회차)

3회로 나눈다. 줄 위치는 시작 때 아현이 다시 확인한다. 회차마다 `workType`과 `planOnlyWaiver`를 넘긴다.

- **1회 배지 양식과 서버 쓰기** (`workType: 'admin'`, 코드): `jam-web/src/app/admin/badges/BadgeForm.tsx`에 숨김 여부(스위치)와 가지(선택) 입력을 더한다. 숨김을 켜면 종류는 액티비티만, 포인트는 0으로 고정하고 등급은 Common만 고르게 한다(마이그레이션 243의 DB 제약과 같은 규칙). 기한 칸이 없는지 확인하고 있으면 없앤다. 서버 쓰기(`jam-web/src/app/api/admin/badges/` 라우트와 검증, 정확한 위치는 아현이 찾는다)가 `is_hidden`·`branch_key`를 받아 같은 규칙으로 검증하고 저장하며 조회 타입(`types/database.ts` `BadgeRow`)과 어드민 목록·상세가 새 칸을 읽는다. shadcn/ui 표준을 따른다. 어드민은 채원 판정 대상이 아니다. 시험(검증 규칙)과 문서(`docs/service/prd/` 어드민 배지 양식, `docs/service/content/ACTIVITY_BADGES.md` 서술 중 손으로 쓰는 부분). SQL 없음.
- **2회 비활성화** (`workType: 'content'`): 사용자 결정 1·2에 따라 대상 배지 목록을 뽑는 스크립트(드라이런: 소프트 삭제 대상 수, 유지 수, 게이트 키를 뺄 행 수, 받은 기록이 걸린 배지 수)와 SQL 파일(마이그레이션 244: `deleted_at` 갱신, 재활용 계열 행의 `condition_json`에서 게이트 키 두 개 제거, 되돌림 SQL 포함)을 아현이 쓴다. 드라이런 결과를 보고하고 실행은 카리나가 승인·롤백 실측 후에 한다. 새 칸 없음.
- **3회 새 계열 입력** (`workType: 'content'`): 원고 `docs/plan/jam2/tribe-rethink/manuscript/06 액티비티 배지.md`의 이름·설명·조건 표기·임시 값(2절 계열 표, 4절 종목별 값, 11절 이름·설명)을 파싱하는 스크립트와 시드 SQL(마이그레이션 245)을 아현이 쓴다. 17개 계열을 등급형(Common~Mystic, 포인트 10·20·50·100), 레벨형(Lv.N, 레벨마다 10), 반복형, 숨김(포인트 0, Common)으로 입력하고 조건은 4-4가 만든 조건 키(`conditionRegistry.ts`)로 적으며 가지(`branch_key`)·계열 키(`family_key`)를 채운다. 이미지는 가장 가까운 기존 배지의 이미지 주소를 복사하고 대응표를 보고한다. 드라이런(새 행 수, 조건 JSON이 허용 키 80개 제약을 통과하는지, 계열 정합성 트리거 통과)과 사후 검증 쿼리를 싣는다. 시험 또는 시뮬레이터로 엔진이 평가할 수 있는지 확인한다. 실행은 카리나가 승인·롤백 실측 후에 한다.

## 완료 조건

### 구현 범위 (게이트 판정 대상, 회차마다 해당 항목)

- 배지 양식이 계열·가지·종류·등급·조건·공개 기간·포인트·숨김을 저장하고 기한 칸이 없다.
- 재활용 후보 밖 배지가 새로 발급되지 않고, 이미 받은 기록은 그대로다(드라이런 대상 수와 사후 검증이 일치).
- 새 55개 계열이 조건 키·등급·포인트·숨김과 함께 들어가 엔진이 평가할 수 있다(시험 또는 시뮬레이터로 확인).
- 마이그레이션이 옛 객체를 바꾸지 않으며 되돌림 SQL을 싣는다. `docs/service/content/ACTIVITY_BADGES.md`에 반영되어 있다.
- 어드민 화면 실렌더 확인은 카리나가 머지 뒤 push 전에 한다.

### 후속 범위 (담당: 카리나, 시점: 사용자 승인 뒤)

- 시작 때 결정 1~3번을 이 티켓 「사용자 결정」 절에 기록한다. SQL 실행은 승인과 롤백 실측(또는 드라이런) 뒤에 한다.
