# [BadgeEngine] JAM2 액티비티 배지 조건 엔진 보강: 판정 로직이 없는 12계열과 같은 이름 등급형 충돌(3-2·3-3)

## 핵심 요약

- 요구사항: 새 액티비티 배지 계열 중 지금 엔진에 판정 로직이 없거나 이름 묶음이 충돌해 4-5에서 입력을 보류한 계열(위 12계열과 3-2·3-3)의 판정을 만들고, 만든 뒤 그 계열을 입력한다. 판정이 안 되는 배지를 넣으면 아무도 받지 못하거나 첫 조건에서 최상위 단계가 한꺼번에 발급되기 때문이다(사용자 결정 2026-10-19, 티켓 `20261018_1816` 결정 3).
- 대상 12계열(번호는 원고 `06 액티비티 배지.md` 2절):
  1. **1-4** 한 주에 3일 이상 움직인 주가 이어짐(등급형 3단 2·3·4주): `weekly_streak`는 활동이 1건이라도 있는 주의 연속만 센다. «3일 이상인 주»의 연속을 세는 판정이 없다.
  2. **2-2** 돌아온 뒤 이어서 움직인 주(등급형 2단 2·4주): 복귀와 연속 주를 함께 보는 판정이 없다.
  3. **3-4** 일곱 요일을 모두 채움(등급형 3단 1·3·10회): 한 주(월~일) 안에 7일을 모두 활동한 주의 횟수. `weekly_active_days`는 역대 최고 주의 값 하나라 그런 주의 횟수를 세지 못한다.
  4. **3-5** 네 계절을 모두 채움(등급형 3단 1·3·10년): 해마다 네 계절을 채운 해를 세는 판정이 없다(`season_count_all`은 연도 구분 없이 계절별 누적).
  5. **5-1** 처음 가 본 동네(레벨형 5레벨 3·10·25·50·100곳), **5-4** 가입 뒤 첫 체크인 배지(단일), **5-5** 계절마다 처음 가 본 동네(등급형 3단 1·3·10해): 새로 받은 체크인 배지의 수를 세는 키가 없다(지정 체크인 배지 보유 수, 체크인 카테고리 보유 수만 있다). 5-5는 계절별 세기도 필요하다. 4-3의 `record_checkin_earn`이 «처음 받는지»(`is_first`)를 돌려주므로 방문 기록(`user_checkin_badge_earns`)의 배지별 첫 줄로 센다.
  6. **5-2** 처음 해 본 종목(등급형 3단 2·3·5종목): 해 본 종목의 수를 세는 키가 없다.
  7. **8-4** 내가 드랍한 것이 다른 유저에게 픽업된 횟수(레벨형 5레벨 1·5·30·50·100회), **8-5** 다른 유저가 드랍한 것을 픽업한 횟수(레벨형 5레벨): 가까운 키 `picked_up_by_user_count`·`pickup_item_count`는 서로 다른 유저 수·서로 다른 아이템 수를 센다. 횟수를 세는 키가 필요하다.
  8. **7-3** 한 주에 200 이상 모은 주를 쌓음(1·5·20주), **7-4** 그 주가 이어짐(2·3·4주 연속): 4-4가 만든 `jam_weekly_earned`는 역대 최고 한 주의 잼 하나의 숫자라 «200 이상 모은 주의 수»와 «연속 주 수»를 세지 못한다. 잼 지표 판정(`jamActionBadges.ts` 201~204줄)은 «조건값 ≤ 현재 숫자 하나»만 비교하고 `repeat_count`를 읽지 않는다. 잼 원장(`jam_daily_earned`, KST 날짜별)을 주(월~일)로 묶어 센다.
  9. **3-2·3-3(같은 이름 등급형 충돌)**: 3-2 «남은 재료의 저녁»(종목별 등급형)과 3-3 «소나무 아래의 주말»(주말 활동, 종목별 등급형)은 이름 하나에 종목마다 계열 5개를 만들어야 하는데, 엔진이 등급형을 이름으로 묶어(`jam-web/src/lib/badge-engine/index.ts` 1125줄 부근 `badgesByName`·`highestOwnedTierByName`, `usageBadges.ts` `gradedByName`) 두 종목을 하는 유저는 한 종목의 상위 등급이 다른 종목의 하위 등급을 막고 한 번에 1개만 발급된다. 처리 방법을 고른다: 종목별 이름을 다르게 하거나(원고 문구 변경) 엔진의 묶음 기준을 `family_key`로 바꾼다. 3-3은 재활용 «고쳐서 재활용»에도 걸려 있어(`cycling:D1`, `hiking:D1`, `running:D2`) 이미 같은 이름 묶음이 있는지 함께 본다.
- 구현 계획: 시작 때 사용자 결정(키 이름과 세는 방식, 조건 허용 키 CHECK 확장 마이그레이션 필요 여부)을 묻고 파일 단위 계획을 옮겨 쓴다. 새 조건 키는 `conditionRegistry.ts`에 더하고 마이그레이션(`badges_condition_json_known_keys` 확장, 242와 같은 방식)이 따로 필요하다. 만든 뒤 4-5 3회의 시드 스크립트로 12계열을 입력한다(마이그레이션 번호는 그때 정한다).
- 관련 파일: `jam-web/src/lib/badge-engine/`(`conditionRegistry.ts`, `activityFilters.ts` `calcMaxWeeklyStreak`, `repeatOccurrences.ts`, `jamActionBadges.ts`·`jamActionJamMetrics.ts`·`jamActionItemMetrics.ts`, `jamActionDayMetrics.ts`), `lib/strava/sync.ts`(체크인 구간), 원고와 재활용 후보 문서의 해당 계열 표.

## 사용자 결정 (2026-10-19 질문창 답, 카리나 기록)

1. **3-2·3-3 이름 묶음**: 엔진이 등급형을 «이름»으로 묶는 기준을 «계열(`family_key`)»로 바꾼다(추천). 스펙 «조건을 넘은 가장 높은 단계 하나를 받는다»를 계열 단위로 맞추고, 원고의 계열당 이름 하나를 그대로 입력한다. 이름 묶음 위치: `jam-web/src/lib/badge-engine/index.ts` `badgesByName`·`highestOwnedTierByName`(1054~1171줄 근처), `usageBadges.ts` `gradedByName`(157~173줄). `family_key`가 없는 행은 이름으로 묶는 지금 방식을 유지한다. 지금 있는 배지 중 단계마다 이름이 다른 계열(구간 계열 6-x)은 이제 한 번에 가장 높은 단계 하나만 발급된다(스펙대로).
2. **8-4·8-5 세는 방식**: 서로 다른 아이템 수(추천, 왕복 부풀림 방지). 8-5는 기존 `pickup_item_count`를 그대로 쓰고(레지스트리 최대값이 레벨 사다리 1·5·30·50·100을 담는지 확인), 8-4만 새 키 `dropped_item_picked_up_count`(내가 드랍한 서로 다른 아이템 중 다른 유저가 픽업한 수)를 만든다.
3. **2-2 복귀 기준**: 7일 이상 쉬었다가 돌아온 뒤 이어서 활동한 연속 주(추천). 공백 7일은 코드 상수다.
4. **3-5·5-5의 «한 해»**: 달력 연도(KST)이고 1·2월과 12월은 모두 겨울이다(추천). 한 해 안에서 봄(3~5월)·여름(6~8월)·가을(9~11월)·겨울(12~2월) 네 계절을 모두 채우면 그 해로 친다.
5. **새 조건 키 이름(카리나가 정함, 아현은 이 이름을 쓴다)**: 모두 `role: 'meta'`, `evaluation: 'external'`(4-4와 같은 방식, 측정 키 트리거 140에는 넣지 않고 `jamActionBadges.ts` 계열이 판정), 값은 정수 ≥ 1(`active_week_min_days`는 1~7).
   - 1회(활동 기반, 마이그레이션 246 적용 완료): `active_week_streak`(한 주에 활동한 날이 `active_week_min_days` 이상인 주가 이어진 최장 주 수, 1-4는 `active_week_min_days: 3`), `active_week_min_days`(보조 키, 기본 1), `return_streak_weeks`(2-2), `full_week_count`(월~일 7일을 모두 활동한 주의 수, 3-4), `full_season_year_count`(네 계절을 모두 채운 해의 수, 3-5), `distinct_activity_type_count`(인정된 활동의 서로 다른 종목 수, 5-2).
   - 2회(체크인·드랍·잼, 마이그레이션 247은 2회에서 쓴다): `new_checkin_badge_count`(새로 받은 체크인 배지의 서로 다른 종류 수, 5-1·5-4(값 1)), `checkin_season_year_count`(해마다 네 계절 모두에서 새 체크인 배지를 받은 해의 수, 5-5), `dropped_item_picked_up_count`(8-4), `jam_week_count`(한 주에 `jam_week_min_earned` 이상 모은 주의 수, 7-3), `jam_week_streak`(그 주가 이어진 최장 주 수, 7-4), `jam_week_min_earned`(보조 키, 7-3·7-4는 200).
6. **회차**: 1회(이름 묶음 + 활동 기반 키 6개 + SQL 246 반영) → 2회(체크인·드랍·잼 키 6개 + SQL 247) → 3회(보류 계열 입력: 마이그레이션 248 시드, 대상은 5-6을 뺀 13계열 = 1-4, 2-2, 3-2, 3-4, 3-5, 5-1, 5-2, 5-4, 5-5, 7-3, 7-4, 8-4, 8-5. 3-3은 «고쳐서 재활용»으로 기존 행이 있고 이름이 종목마다 달라 입력 대상이 아니다). 마이그레이션 번호는 시작 때 origin/staging 기준으로 다시 확인한다.
- **SQL 246**: 허용 키 CHECK를 80→86개로 넓혔다(롤백 실측: 기존 배지 전부 통과, 새 키 6종 통과, 242의 키 통과, 미등록 키 거부). 공용 DB 적용 완료. SQL 파일은 코드와 같은 커밋에 들어가야 조건 레지스트리 시험(가장 큰 번호의 마이그레이션 키 목록과 `ALL_CONDITION_KEYS` 대조)이 통과하므로, 아현이 스크래치패드의 원본을 한 글자도 바꾸지 않고 `jam-web/supabase/migrations/246_condition_json_activity_metric_keys.sql`로 복사해 커밋한다.
