# [Feature] JAM 2.0 묶음 5: 챕터·미션·포인트 (챕터 점수와 오름, 트라이브 미션, 포인트 회수 고치기)

## 핵심 요약

- 요구사항: 운영 로직 12장(챕터), 13장(미션), 14장(포인트)을 만든다. 서비스 활동 8종이 챕터 점수로 쌓여 챕터가 오르고, 오르면 소식과 챕터 배지를 받으며, 미션은 트라이브별로 참가 대상이 갈리고, 포인트 회수로 잔액이 음수가 되지 않는다. 비교표 4.1절의 문제 셋(게이트 미션 덮어쓰기, 선착순 잠금, 포인트 음수)을 함께 고친다. 묶음 4의 코드가 끝난 상태에서 시작한다.
- 구현 계획: 하위 티켓 8개를 순서대로 진행한다(아래 표). 서버 6개(미션 3, 포인트 1, 챕터 2)를 먼저 하고 화면 2개(유저, 어드민)를 마지막에 한다. 하위 티켓마다 시작 전에 주요 결정을 질문창으로 묻고, 화면이 있는 것은 채원 사전 판정을 받는다.
- 관련 파일: `docs/plan/jam2/10 JAM 2.0 서비스 운영 로직.md` 12·13·14장, `docs/plan/jam2/service-redesign/현재 서비스 비교.md`(5.3절 「17 챕터」「10 미션」「11 포인트」 행, 4.1절), 마이그레이션 `jam-web/supabase/migrations/221_chapters.sql`.

## 배경 / 문제 정의

묶음 1에서 챕터 저장 구조(마이그레이션 221)를 만들었지만 챕터 점수를 쌓는 호출이 앱에 하나도 없다. 그래서 챕터가 한 번도 오르지 않고, 배지 엔진의 `chapter_reached` 조건도 늘 0을 읽는다. 미션은 지금 트라이브 칸이 없는 개인형 55건뿐이고, 포인트는 어드민 회수로 잔액이 음수가 될 수 있다.

## 조사 결과 (2026-10-19, 코드와 공용 DB를 읽기만 함)

**공용 DB 현재 값(읽기 전용 조회)**: 챕터 정의 10행, 챕터 이름 0행, 유저 챕터 0행, 챕터 점수 기록 0건. 포인트 지갑 1개에 음수 잔액 0건. 미션 55건에 선착순 제한이 걸린 미션 0건.

**챕터 저장 구조(마이그레이션 221)**: 테이블 6개(`chapter_definitions`, `chapter_names`, `chapter_score_rules`, `user_chapters`, `chapter_score_events`, `chapter_ups`)와 함수 2개다.
- `chapter_add_score(p_user_id, p_activity_kind, p_source_id, p_amount, p_occurred_on)`는 `(score_added, current_chapter, reached_chapters)`를 돌려준다. 같은 (활동 종류, 원천 id)를 다시 부르면 기존 결과를 돌려주고 새로 오른 챕터는 빈 배열이다. 그 키가 다른 유저의 기록이면 예외다(유일 제약이 전역이기 때문이다).
- `chapter_start(p_user_id)`는 퀘스트 완료 때 챕터 1을 주고, 그때까지 쌓인 점수로 한꺼번에 오른다. 둘 다 service_role만 실행한다.
- 활동 종류 12개: `jam_earned`, `capsule_open`, `locked_item_badge_open`, `badge_receive`, `collection_complete_common/rare/epic/mystic`, `mix_success`, `mission_complete`, `drop`, `pickup`.
- 주간 상한(잼 300)과 초과분 절반은 DB가 처리한다. 챕터·포인트 조건 배지 제외, 자기 드랍 줍기 제외, 이용 정지 중 차단은 호출부 책임이다.
- 앱에서 이 함수들을 부르는 코드는 없다(직접 대조). 읽는 곳은 `lib/badge-engine/jamActionJamMetrics.ts:123`(`user_chapters.chapter_no`)과 DB 함수 `capsule_next_required`(234)뿐이다. 캡슐 필요량은 새 캡슐이 생길 때 챕터를 읽으므로 앱 작업이 없다.

**챕터 오른 직후 판정**: `chapter_reached` 조건은 동기화 끝 한 곳(`sync.ts:1258`, `jamActionProgressTriggers.ts:36`)에서만 판정된다. 캡슐 열기처럼 라우트에서 챕터가 오르면 다음 동기화까지 챕터 배지가 열리지 않는다. 오른 직후 호출용으로 `runJamActionEvaluation`(`jamActionRoute.ts:21`)이 이미 있다. 챕터 소식 종류는 없다. 새 종류를 더하는 순서는 마이그레이션(`ALTER TYPE notification_type ADD VALUE`, 237 참고), `types/database.ts`, `lib/notifications/types.ts`, `message.ts`, `href.ts`다. 새 enum 값은 같은 트랜잭션에서 쓸 수 없다(55P04).

**프로필 자리**: 내 프로필 헤더 `app/(main)/profile/ProfileClient.tsx:584-660`, 캡슐 위젯 `:664`. 타인 프로필 서버 페이지 `app/(main)/[username]/page.tsx`는 `users`에서 `id, username, display_name, avatar_url`만 읽고 트라이브와 챕터는 읽지 않는다. 챕터 이름 표(`chapter_names`)는 0행이고 읽는 코드와 어드민 화면이 없다. 이름 50개는 별도 주제라서 화면은 이름이 비어도 «챕터 N»만 보여야 한다.

**미션**: 트라이브 칸, 참가 제한과 목록 거르기, 트라이브 변경 때 참가 취소, 배지 획득·JAM·잼 조건, 밤 조건 보호 장치, 캡슐 횟수의 순위형 금지가 모두 없다. 앱에 유저의 트라이브를 바꾸는 코드도 없다(`api/onboarding/complete/route.ts:117`이 처음 설정만 한다).
- 문제 ① 게이트 폼 덮어쓰기: `admin/gate-missions/GateMissionForm.tsx`가 복합 조건 미션을 열면 유형을 `activity_type`으로 바꾸고, 저장 때 `condition_json`을 `{ [valueKey]: target, activity_type }`로 통째로 새로 만들어 보낸다. 서버 `api/admin/missions/[id]/route.ts`는 병합 없이 덮어쓴다. 복합 조건 키(repeat_count, weekly_streak, time_band_counts 등)와 보상 포인트, 순위 표시 수, 완료 인원 제한, 게이트 배지 칸도 함께 지워진다.
- 문제 ② 선착순: `lib/missions/checker.ts`가 달성 판정 → 완료 수 세기(`count ?? 0`, 조회가 실패해도 상한을 무시한다) → INSERT → 보상 지급 순서로 잠금 없이 진행한다. `UNIQUE(user_id, mission_id)`는 같은 유저의 중복만 막는다.
- 미션 보상 배지 선택: 어드민 검색(`api/admin/badges/search`)이 숨김 배지를 거르지 않고, 서버가 `reward_badge_ids`를 검증하지 않으며, 지급(`rewards.ts`)과 미션 상세(`(main)/missions/[id]/page.tsx`)도 숨김을 거르지 않는다(티켓 `20261019_0012`).
- 보상 지급: 이미 가진 아이템 배지와 가득 찬 인벤토리는 건너뛰고 나중에 받는 길이 없다(`rewards.ts:121-122`). 잠김 지정도 없다(`grant_inventory_item_locked`는 231에 있다).
- 날 기준: 연속·휴식·활동일·주·월·요일 개수는 5-2 2회에서 한국 시각(KST) 날짜로 통일했다(티켓 `20261019_1312`). 랭킹 `total_count`의 단위(활동 건수 대 활동일 수)만 티켓 `20261018_2303`에 남았다.

**포인트**: 잔액은 `point_wallets.balance`(CHECK 없음), 원장은 `point_transactions`다. `award_points`(157)에는 행 잠금도 잔액 검사도 없다. 어드민 회수는 `UserGrantForm.tsx` → `api/admin/points/grant` → `lib/points/admin-grant.ts`(`admin_deduct`)를 거친다. 14.1절 지급 8곳 가운데 체크인·아이템 배지·믹스·미션 보상·퀘스트 완료·운영자 지급은 규칙과 맞고, 다음 둘이 다르다.
- 액티비티 배지: 받을 때 한 번 주는 것은 맞지만 금액이 등급별 10/20/50/100이 아니라 배지마다 정한 `badges.point_reward`다. 반복형 재획득은 포인트가 없다. 숨김 배지 0은 243의 CHECK가 보장한다.
- 컬렉션 완성: 등급별 100/200/400/800과 등급당 한 번은 `slot_item_into_book_tiered`(222)에서만 맞고, 등급형을 켜지 않은 컬렉션은 옛 함수로 컬렉션당 한 번이다.

## 사용자 결정 (2026-10-19, 질문창, 추천안)

1. **하위 티켓은 서버 6개 + 화면 2개로 쓰고 서버를 먼저 진행한다.** 서버가 선 뒤 화면을 한 번에 만들어 다시 고칠 일을 줄인다(묶음 3·4와 같은 방식).
2. **서버 순서는 미션, 포인트, 챕터 순이다.** 챕터 점수를 미션 완료 지점과 포인트 지급 지점에 연결하므로, 그 두 곳을 먼저 고쳐 둔다.
3. **챕터 1을 시작하는 호출(퀘스트 완료 때 `chapter_start`)은 5-6에서 연결한다.** 지금 퀘스트 완료 처리 함수 한 곳에 붙이고, 묶음 6이 퀘스트를 새로 만들 때 완료 조건만 바꾼다.
4. **후속 티켓을 이 묶음에 포함한다.** `20261019_0012`(숨김 배지 차단)는 5-3, `20261018_2303`(날 기준 KST 통일)은 5-2, `20261019_1244`(배지 트리 제거 뒤 정리)는 5-8에서 함께 처리한다. 잠긴 개체 API 응답에서 일련번호·만료일을 비우는 일과 `20261018_2304`(노출용 시간대 경계)는 묶음 5 이후로 미룬다.
5. **오픈 직전 적용 SQL(244 → 245 → 248)의 사전 작업(백업 SELECT 결과 기록, 드라이런)은 오픈 직전에 한 번에 한다.** 지금은 아무것도 적용하지 않는다.
6. **사용자 staging 직접 확인 항목(캡슐·잠긴 개체, 위젯·키패드, 겹침, 배지 리셋 표기)은 이 묶음 진행과 병렬로 한다.** 결과를 알려 주시면 수정 티켓으로 반영한다.
7. **5-2의 조건 넓히기를 둘로 나눈다(2026-10-19).** 5-2는 활동 기록 조건·기간 경계·순위형 금지·날 기준 KST를, 5-2b(`20261019_1445`)는 DB 기록 조건과 기간 동안 모은 잼을 맡는다. 판정하지 못하는 조건은 저장을 허용하고 경고만 한다(추천은 거절이었으나 사용자가 경고만을 선택).
8. **5-3의 보상·보류·잠김 결정(2026-10-19).** 받지 못한 미션 보상은 미션 전용 표에 두고 미션 결과 화면에서 받는다(다른 기능을 막지 않는다). 잠김은 보상 아이템 배지 자체의 설정을 따르고 미션에 잠김 칸을 더하지 않는다. 이미 쓰이는 배지를 숨김으로 바꾸는 저장은 거절한다. DB는 마이그레이션 250·251로 적용했다.
9. **배포 전 결정(약관·방침 시행일과 개정 이력, 티켓 `20261001_0633`의 «장소» 금지어 시험 반전)은 묶음 5가 끝난 뒤 배포 준비 때 정한다.**

### 순서의 근거

- 챕터 점수의 «미션 완료 50점»은 완료 기록 id를 원천으로 쓰고(멱등 키), «배지 받기»는 미션 보상 지급 지점도 포함한다. 그래서 미션(5-1~5-3)과 포인트(5-4)를 먼저 고친다.
- 챕터 설정값 화면(챕터별 누적 점수, 활동별 점수, 주간 상한)은 밸런스 설정 화면(19장)이라 묶음 7이다. 이 묶음의 어드민은 챕터 이름 표 입력과 유저 상세의 챕터 기록까지 한다.
- 챕터 이름 50개는 별도 주제(2026-10-08 사용자 결정)라 이 묶음에서 짓지 않는다. 화면은 이름이 비어도 동작해야 한다.
- 트라이브를 바꾸는 코드가 앱에 없으므로 «트라이브 변경 때 참가 취소»는 함수와 시험까지 만들고, 호출 연결은 묶음 6(트라이브 변경 경로)에서 한다. 이 결정은 5-1 시작 때 다시 확인한다.
- 계산식의 값(챕터별 필요 점수, 점수 규칙, 주간 상한)은 마이그레이션 221의 설정 행으로 이미 있다. 코드는 읽기만 한다.
