# [Service] JAM2 미션 서버 ①: 트라이브 칸, 참가 제한, 참가 취소, 이용 정지, 선착순 동시 완료 막기

## 핵심 요약

- 요구사항: 운영 로직 13.2절 가운데 참가와 완료 규칙을 만든다. (1) 미션에 참가할 수 있는 트라이브를 하나 이상 고를 수 있고, 고르지 않으면 모든 유저가 참가하는 공통 미션이다. (2) 대상이 아닌 트라이브의 유저에게는 목록과 상세에 보이지 않고 참가도 거절한다. (3) 트라이브가 바뀌면 참가한 트라이브 제한 미션의 참가가 취소되고 순위에서 빠진다(이미 받은 보상은 그대로). (4) 이용 정지 중에는 참가할 수 없고 다른 유저에게 보이는 순위에서 빠진다. (5) 선착순 완료 제한이 동시 동기화에도 상한을 넘지 않는다(비교표 4.1절 문제 ②). (6) 완료 기록의 id를 돌려주어 챕터 점수(5-5)가 원천 id로 쓰게 한다.
- 구현 계획: 시작 때 사용자 결정 3건을 질문하고 파일 단위 계획을 옮겨 쓴다. DB는 새 테이블과 새 함수만 더한다. SQL은 사용자 승인과 롤백 실측 뒤 카리나가 실행한다.
- 관련 파일(2026-10-19 조사, 시작 때 아현이 줄 위치를 다시 확인한다): 완료 판정 `jam-web/src/lib/missions/checker.ts`(`evaluateMission` 149줄, 선착순 검사 164~171줄, 완료 INSERT 174~182줄, 보상 호출 188줄), 호출 `lib/strava/sync.ts:1221`, 참가 `app/api/missions/[id]/join/route.ts`(15~88줄), 목록 `app/(main)/missions/page.tsx`, 순위 `lib/missions/ranking.ts`, 완료 테이블 `user_mission_completions`(마이그레이션 011, `UNIQUE(user_id, mission_id)`), 이용 정지 `lib/suspension/suspension.ts`(`assertNotSuspended`), 조사 결과 전문은 상위 티켓 `20261019_1310`.

## 배경 / 문제 정의

지금 미션은 트라이브를 모른다. 미션 행, 양식, 어드민 API 어디에도 트라이브 칸이 없고, 참가 라우트에도 트라이브 검사가 없으며, 참가를 취소하는 길 자체가 없다. 앱에 유저의 트라이브를 바꾸는 코드도 없어서(`api/onboarding/complete/route.ts:117`이 처음 설정만 한다), 트라이브 변경 때 참가 취소는 호출할 자리가 아직 없다.
선착순은 완료 수를 센 뒤 INSERT하는 사이에 잠금이 없다. 동시에 동기화한 두 유저가 둘 다 `상한 - 1`을 읽고 둘 다 INSERT하면 상한을 넘는다. 개수 조회가 실패해도 `count ?? 0`으로 상한이 무시된다. 지금 선착순 제한이 걸린 미션은 0건이라 당장의 피해는 없지만, 트라이브 미션이 생기면 쓰이는 장치다. 재현은 하지 않았다.
공용 DB 주의: 옛 프로덕션 코드가 같은 테이블을 쓴다. 새 칸·새 테이블·새 함수만 덧붙이고 기존 칸의 뜻은 바꾸지 않는다.

## 시작 전에 사용자에게 확인할 것 (주요 결정, 질문창)

1. **트라이브 칸의 모양**: 새 연결 테이블(`mission_allowed_tribes`, 미션 하나에 참가할 수 있는 트라이브마다 한 행, 행이 없으면 공통 미션)을 둔다(추천, 트라이브가 지워지거나 바뀔 때 연결이 어긋나지 않는다). 대안은 `missions`에 `tribe_ids uuid[]` 칸을 더하는 것이다(칸 하나로 끝나지만 연결 무결성을 DB가 지켜 주지 않는다).
2. **선착순 완료의 동시 처리**: DB 함수 하나가 «미션 행 잠금 → 완료 수 세기 → 기록»을 한 번에 하게 하고(추천, 새 함수, 완료 id를 돌려줌), 앱 `checker.ts`는 이 함수를 부른다. 대안은 앱에서 기록 뒤 다시 세어 넘으면 지우는 낙관적 방식이다(잠깐 상한을 넘은 상태가 보일 수 있다).
3. **트라이브 변경 때 참가 취소의 호출 자리**: 취소 함수와 시험까지 만들고, 호출은 트라이브를 바꾸는 경로가 생기는 묶음 6에서 연결한다(추천, 지금 앱에 그 경로가 없다). 대안은 어드민에 «트라이브 변경» 기능을 이번에 더하고 거기에 연결하는 것이다(범위가 어드민까지 넓어진다).

## 사용자 결정과 적용 기록 (2026-10-19)

1. 트라이브 칸: **별도 연결 표**(`mission_allowed_tribes`, 미션 하나에 참가할 수 있는 트라이브마다 한 행, 행이 없으면 공통 미션)로 한다(추천 채택).
2. 선착순 동시 완료: **DB 함수 하나(`mission_complete`)가 «잠금 → 완료 수 세기 → 기록»을 한 번에 한다**(추천 채택). 앱 `checker.ts`는 이 함수를 부르고 완료 기록 id를 돌려받는다.
3. 트라이브 변경 때 참가 취소: **기능(`mission_cancel_for_tribe_change`)과 시험까지만** 만들고, 호출 연결은 유저 트라이브를 바꾸는 경로가 생기는 묶음 6에서 한다(추천 채택).
- 카리나의 해석(질문 없이 정함): 이미 완료한 미션도 트라이브가 바뀌면 참가를 취소한다. 완료 기록(`user_mission_completions`)과 받은 보상은 지우지 않는다(13.2절 «이미 받은 보상은 그대로 둔다»). 선착순 자리를 센 완료 기록도 남으므로 상한에는 계속 들어간다.
- **DB 적용 완료(마이그레이션 249, 사용자 승인 2026-10-19)**: 새 표 2개(`mission_allowed_tribes`, `mission_participation_cancellations`)와 새 함수 2개(`mission_complete(uuid,uuid) → jsonb`, `mission_cancel_for_tribe_change(uuid) → TABLE(out_mission_id, out_mission_title)`). 옛 표·칸·함수는 바꾸지 않았다. 둘 다 service_role만 실행하고 새 표는 RLS를 켜고 anon·authenticated의 권한을 모두 회수했다.
- 롤백 실측(DO 블록 하나에 DDL과 검증을 담고 마지막에 예외로 전부 되돌림, 6묶음 통과): 선착순 상한 1에서 첫 사람만 통과하고 둘째는 `mission_full`, 같은 유저의 재호출은 `already_completed`, 상한이 있는 미션에서만 어드바이저리 잠금 1개(상한 없는 미션은 0개). 트라이브 제한에서 대상이 아닌 유저는 `tribe_not_allowed`. 없는 미션 `mission_not_found`, 미참가 `not_participating`, 이용 정지 `user_suspended`(풀면 완료). 참가 취소는 대상 밖 미션만 취소하고 공통·대상 미션은 유지, 완료 기록 유지, 기록(`was_completed`, `new_tribe_id`) 남김, 두 번째 호출 0행, 트라이브 없음이면 제한 미션을 모두 취소, 없는 유저 0행. 연결된 트라이브 삭제는 FK로 막히고 미션 삭제는 연결을 함께 지움. 권한과 RLS 확인. 실측 뒤 새 객체·시험 행이 공용 DB에 남지 않았음을 확인했다.
- 적용 뒤 확인: 함수 2개 SECURITY DEFINER, `authenticated` 실행 권한 없음, `service_role` 실행 가능, 두 표 RLS 켜짐·`authenticated` 읽기 권한 없음, 새 표 0행, 기존 미션 55건 그대로. 생성 타입(`database.generated.ts`)에 새 표 2개·함수 2개를 반영했다.
- 앱이 지킬 반환 계약(`mission_complete`): `{ok:true, status:'completed', completion_id}` / `{ok:true, status:'already_completed'}` / `{ok:false, error:'mission_not_found'|'user_suspended'|'not_participating'|'tribe_not_allowed'|'mission_full'}`. `ok:false`와 `already_completed`는 완료 처리(보상·피드)를 하지 않고 건너뛴다. RPC 호출 자체가 실패하면 완료시키지 않는다(상한 검사를 건너뛰던 `count ?? 0`도 같은 이유로 없앤다).

## 상세 요구사항

### 서비스/코드베이스 관점

- **트라이브 칸**: 위 결정 1에 따라 추가한다. 읽기 정책은 기존 미션 읽기 정책을 따르되, 트라이브 거르기는 서버(API, 서버 컴포넌트)에서 한다.
- **보이기와 참가**: 미션 목록·상세 조회는 내 트라이브가 참가 대상이 아닌 트라이브 제한 미션을 돌려주지 않는다(상세는 404). 참가 라우트는 대상이 아니면 거절한다. 내 트라이브가 아직 없는 유저(온보딩 전)는 공통 미션만 본다.
- **참가 취소**: 새 함수가 «유저의 트라이브가 바뀌었을 때 그 유저가 참가한 트라이브 제한 미션 가운데 새 트라이브가 대상이 아닌 것의 참가를 취소하고 순위 계산에서 뺀다». 취소된 미션마다 소식 대상 목록(미션 이름 포함)을 돌려주어 호출한 쪽이 소식을 보내게 한다(소식 종류는 5-3). 이미 받은 보상은 그대로 둔다. 취소한 기록을 남긴다.
- **이용 정지**: 참가 라우트가 `assertNotSuspended`로 막는다(403 `user_suspended`). 순위 조회는 정지 중인 유저를 다른 유저가 보는 순위에서 빼고 본인 화면에는 보인다. 기간 안에 정지가 풀리면 다시 보인다.
- **선착순**: 결정 2의 함수가 상한 검사와 완료 기록을 한 트랜잭션에서 한다. 상한 검사가 실패(조회 오류)하면 완료시키지 않는다(fail-closed). 같은 유저의 중복 완료는 지금처럼 `UNIQUE`가 막고 함수가 «이미 완료»를 구분해 돌려준다.
- **완료 id**: `checker.ts`가 완료 기록의 id(`user_mission_completions.id`)를 돌려받아 보상 지급과 챕터 점수(5-5)에 넘길 수 있게 한다. 이 티켓에서는 챕터 점수를 연결하지 않는다.
- 새 칸·새 테이블·새 함수는 덧붙이기만 한다. 생성 타입을 같은 커밋에 맞춘다.

### UI/UX 관점 (해당 시)

- 없음(유저 화면은 5-7, 어드민 양식은 5-8).

## 구현 계획 (회차)

1회로 돌린다. 예상 파일 약 14개(코드 8, 시험 5, 문서 3 안팎)라 `plan_only` 임계값(파일 5개 초과)을 넘으므로, 아래를 파일 단위 계획으로 보고 `planOnlyWaiver`를 첫 호출부터 건다(사전 확인 끝: DB 249 적용·타입 반영·타입 검사 통과). 경로는 `jam-web/src` 기준이고 줄 위치는 2026-10-19 조사 시점이다.

**DB는 끝났다(마이그레이션 249).** 아현은 SQL을 쓰지 않고 `supabase.rpc('mission_complete', ...)` 등 앱 코드만 쓴다. 생성 타입에 새 표·함수가 이미 들어 있다.

1. **신규 `lib/missions/tribe-access.ts`**: 순수 함수 `isMissionOpenToTribe(allowedTribeIds, userTribeId)`(허용 목록이 비었거나 없으면 true, 목록이 있으면 유저 트라이브가 들어 있을 때만 true, 유저 트라이브가 null이면 목록이 있는 미션은 false)와 서비스 클라이언트 로더 `loadMissionTribeAccess(userId, missionIds)`(`users.tribe_id`와 `mission_allowed_tribes`를 `in('mission_id', ...)`로 한 번에 읽어 `{ userTribeId, allowedTribeIdsByMission }` 반환). 조회가 실패하면 throw한다(fail-closed, 제한 미션이 새는 것보다 오류 화면이 낫다).
2. **`lib/missions/visibility.ts`**: `MissionVisibilityContext`(108줄)에 **선택** 필드 `tribeAccess?`를 더한다(없으면 제한 없음, 기존 시험·호출부 호환). `resolveMissionVisibility`(252줄)에서 «완료» 판정 바로 다음, 게이트 판정 앞에 `isMissionOpenToTribe`가 false면 `{ visibility: 'hidden', requiredBadge: null }`을 돌려준다(`softenHidden`을 거치지 않는다. 트라이브가 바뀌면 참가가 취소되므로 완화할 참가 이력이 없다). 완료한 미션은 트라이브가 바뀌어도 «completed»로 남는다.
3. **`lib/missions/visibility-server.ts` `loadMissionVisibilityContext`(158줄)**: `loadMissionTribeAccess`를 불러 반환 컨텍스트에 `tribeAccess`를 싣는다. 이렇게 하면 목록(`app/(main)/missions/page.tsx` 66줄)·상세(`app/(main)/missions/[id]/page.tsx`)·참가 라우트가 같은 규칙을 쓴다. 목록에서 `hidden`은 이미 걸러지고(`page.tsx` 76줄 근처), 상세 페이지가 `hidden`을 어떻게 다루는지 확인해 대상이 아닌 트라이브는 «없는 미션»(404)이 되게 한다.
4. **`app/api/missions/[id]/join/route.ts`**: (a) 맨 앞(미션 조회 전)에 `assertNotSuspended`를 불러 이용 정지 중이면 403 `user_suspended`(응답 모양은 `app/api/drops/route.ts:310` 패턴을 따르고, 문구는 `lib/i18n/ko.ts`의 `d.suspension`에 `missionJoinBlocked`를 새로 더한다. 기존 `dropBlocked` 881줄 근처 문구와 어조를 맞춘다). (b) `isMissionExposed` 검사(44줄 근처) 다음에 트라이브 접근을 검사해 대상이 아니면 `missionNotFound` 404를 돌려준다(존재를 알리지 않는다. `visibility !== 'open'`의 403 분기에 닿기 전에 처리).
5. **`lib/missions/checker.ts` `checkMissions`(71줄)**: 선착순 검사와 완료 INSERT(163~182줄)를 `supabase.rpc('mission_complete', { p_user_id: userId, p_mission_id: mission.id })` 한 번으로 바꾼다. 반환(JSONB)은 위 「반환 계약」을 따른다. `ok:true`이고 `status:'completed'`일 때만 아래(보상·피드·소식 후보)를 이어서 하고, `already_completed`와 모든 `ok:false`는 `continue`한다(`mission_full`·`tribe_not_allowed`·`not_participating`·`user_suspended`는 조용히, 예상 밖 오류는 `console.error`). ## 완료 조건

### 구현 범위 (게이트 판정 대상)

- 미션에 참가할 수 있는 트라이브를 정할 수 있고, 대상이 아닌 트라이브 유저에게는 목록·상세에 보이지 않으며 참가가 거절된다. 대상을 정하지 않은 미션은 모두가 본다.
- 선착순 상한이 걸린 미션을 동시에 완료해도 완료 수가 상한을 넘지 않는다(롤백 실측과 시험으로 확인). 개수 조회가 실패하면 완료되지 않는다.
- 완료 기록의 id를 돌려받을 수 있다.
- 참가 취소 함수가 새 트라이브가 대상이 아닌 참가만 취소하고 순위에서 빼며, 이미 받은 보상은 그대로다.
- 이용 정지 중에는 참가가 403 `user_suspended`로 막히고, 다른 유저가 보는 순위에서 빠지며 본인에게는 보인다.
- 마이그레이션이 옛 객체의 서명·권한을 바꾸지 않고 되돌림 SQL을 싣는다.

### 후속 범위 (담당: 카리나, 시점: 사용자 승인 뒤)

- 시작 때 결정 1~3번을 이 티켓 「사용자 결정」 절에 기록한다. SQL 실행은 승인과 롤백 실측 뒤에 한다.
- 트라이브 변경 때 참가 취소의 호출 연결은 묶음 6에서 한다(결정 3).
