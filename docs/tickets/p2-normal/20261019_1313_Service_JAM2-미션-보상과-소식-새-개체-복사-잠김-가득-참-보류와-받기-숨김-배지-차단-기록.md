# [Service] JAM2 미션 보상과 소식: 새 개체 복사, 가득 참 보류와 받기, 숨김 배지 차단, 소식·기록

## 핵심 요약

- 요구사항: 운영 로직 13.2절의 «보상»과 «소식과 기록»을 서버에 맞춘다. (1) 보상은 액티비티 배지(미션 전용 포함), 포인트, 아이템 배지다. 잼은 주지 않는다. (2) 이미 가진 아이템 배지도 새 개체로 주고, 인벤토리가 모자라면 받지 않은 상태로 두며, 미션 기간이 끝난 뒤에도 기한 없이 미션 상세(결과 화면)에서 받는다(6.4절). (3) 숨김 배지를 미션 보상·선행 조건·교차 게이트·게이트 미션 배지로 쓰지 못하게 서버·어드민에서 막고, 이미 쓰이는 배지를 숨김으로 바꾸는 저장도 막는다(티켓 `20261019_0012`). (4) 소식은 지금 있는 6종(진행 50%·80%, 완료, 마감 이틀 전, 순위 상승, 종료 결과)을 두고 «트라이브가 바뀌어 참가가 취소됐어요» 소식만 더한다. (5) 참가·진행·완료·받은 보상·받지 않은 보상·참가 취소를 기록한다.
- 구현 계획: DB(마이그레이션 250·251)는 카리나가 먼저 적용했다. 앱 코드는 3회로 나눠 돌린다(1회 보상 지급·보류·받기, 2회 숨김 배지 차단, 3회 소식과 상세의 받지 않은 보상 데이터). 아래 「구현 계획」의 파일 단위 계획을 따른다.
- 관련 파일: 아래 구현 계획에 줄 위치와 함께 있다(2026-10-19 조사). 조사 결과 전문은 상위 티켓 `20261019_1310`과 이 티켓 「배경」에 있다.

## 배경 / 문제 정의

지금 미션 보상 지급(`jam-web/src/lib/missions/rewards.ts`)은 이미 가진 아이템 배지와 가득 찬 인벤토리를 흔적 없이 건너뛴다(121~122줄, 137~142줄). 보상 배지의 유형을 검증하지 않아 «그 밖의 유형은 모두 아이템 분기»라서 체크인 배지도 인벤토리로 들어간다. 지급(`checker.ts` 236줄)과 완료(`mission_complete`, 208줄)는 별도 트랜잭션이라 둘 사이에서 실패하면 재지급 경로가 없다(`already_completed`로 건너뜀).
동기화 보상용 `sync_pending_items`(마이그레이션 229)는 «고른 것만 받고 나머지는 폐기(`resolve_sync_pending_items`)»라서 미션 보상이 같은 표에 섞이면 영구 폐기되고 동기화를 막는다. 믹스는 별도 표 `combine_pending_results`와 `combine_claim_pending`(마이그레이션 236)으로 같은 문제를 풀었다.
숨김 배지(`badges.is_hidden`, 마이그레이션 243)는 액티비티 배지·포인트 0·Common만 허용하는 제약이 있어 숨김 아이템 배지는 존재할 수 없다. 그런데 어드민 보상 배지 검색은 숨김을 거르지 않고, `reward_badge_ids`는 존재·유형·숨김 모두 서버에서 검증하지 않으며(POST `missions/route.ts:72`, PATCH `[id]/route.ts:141`, 운영툴 `opsInbox/execute/mission.ts:126`, 등록 스크립트 `registerMissionFlow.mjs:141`), 지급과 미션 상세(`(main)/missions/[id]/page.tsx` 40~43줄, 21줄 `select('*')` 결과를 63줄에서 통째로 클라이언트에 넘김)·목록(`missions/page.tsx` 86~92줄)·투데이 카드(`lib/today/cards.ts:285`)도 숨김을 거르지 않는다. 선행 조건(`prerequisite_badge_names`)·교차 게이트(`crossGate.ts:89`)·게이트 미션 배지 지정도 서버 검증이 없다.
소식은 6종 가운데 5종이 이미 있고(`mission_milestone`, `mission_completed`, `mission_deadline`, `mission_rank_up`, `mission_ended`) «트라이브 변경에 따른 참가 취소»만 없다. 5-1의 `mission_cancel_for_tribe_change`가 (미션 id, 이름) 목록을 돌려주지만 부르는 곳이 앱에 아직 없다(호출 연결은 묶음 6).
기록은 참가(`user_mission_participations`), 완료(`user_mission_completions`), 참가 취소(`mission_participation_cancellations`, 249)가 이미 있고, 진행은 `progress_value` 현재값만 덮어쓴다. 받은 보상 가운데 아이템 개체는 미션과의 연결이 없고, 받지 않은 보상은 흔적이 없었다.

## 사용자 결정과 적용 기록 (2026-10-19)

1. **받지 못한 미션 보상은 미션 전용 표에 두고 미션 결과 화면(상세)에서 받는다**(사용자 답변: «믹스, 미션 결과에서 내 인벤토리로 가져오지 못하면 해당 화면에서 계속 유지된다. 미션은 그냥 결과 화면에 두면 된다»). 믹스처럼 받기 전까지 다른 기능을 막지 않는다(동기화를 막지 않고 앱을 열 때 자동으로 띄우지 않는다). 카리나의 해석: 동기화 보류 표에 합치지 않고 믹스의 방식(별도 표와 함수)을 따라 미션 전용 표 `mission_item_rewards`를 둔다.
2. **잠김은 보상 아이템 배지 자체의 설정을 따른다**(사용자 답변: «원래 보상 아이템을 지정할 때 잠금 여부를 결정한다. 별도의 보상 칸이 필요하지 않고, 보상 결과는 잠기든 잠기지 않든 같은 의미의 보상을 받는 것이다»). 카리나의 해석: 미션에 잠김 칸을 더하지 않고 배지의 «잠김으로 만든 아이템 배지»(`badges.always_locked`, 마이그레이션 231) 설정을 그대로 따른다. 이 미션에서만 일반 배지를 잠가서 주는 지정은 지원하지 않는다(필요해지면 그때 더한다). 어드민 미션 양식은 고른 아이템 배지가 잠김인지 읽기 전용으로 보여 주기만 한다(5-8).
3. **이미 미션 보상·선행 조건·교차 게이트·게이트 미션 배지로 쓰이는 배지를 숨김 배지로 바꾸려 하면 저장을 거절한다**(추천 채택). 거절 문구에 어느 미션·배지가 쓰고 있는지 알린다.
4. **숨김 배지 차단의 범위는 티켓 `20261019_0012`의 원래 결정대로 미션 보상·선행 조건·교차 게이트·게이트 미션 배지 모두를 서버와 어드민에서 막는다**(사용자가 1단계에서 이미 결정).
5. 카리나가 질문 없이 정한 것: (a) 받기는 «모두 들어갈 빈칸이 있어야 받는다»(믹스와 같다, 일부만 받기 없음). 현재 미션 보상은 미션마다 배지 1개라 영향이 없다. (b) 진행의 시점별 이력 표는 만들지 않는다(진행은 `progress_value` 현재값과 마일스톤 소식 50%·80%로 갖는다). (c) 보상 배지 유형은 액티비티·아이템만 허용하고 체크인 배지는 저장에서 거절한다(13.2절 «보상은 액티비티 배지, 포인트, 아이템 배지»). (d) 받기에는 트라이브 접근 검사를 하지 않는다(완료한 유저는 상세를 계속 볼 수 있다, 5-1 규칙).
- **DB 적용 완료(마이그레이션 250·251, 사용자 승인 2026-10-19)**: 250은 새 표 `mission_item_rewards`(미션이 준 `claimed`와 못 준 `pending` 아이템 배지 보상, `(user_id, mission_id, badge_id)` 유일, 잠김 정보는 기록 때 고정)와 새 함수 2개다. `mission_grant_item_rewards(p_user_id, p_mission_id, p_badge_ids) → jsonb`는 아이템 배지만 처리하고 이미 가진 배지도 새 개체로 주며(모두 들어갈 빈칸이 있으면 전부 주고 모자라면 전부 `pending` 기록), 같은 미션·배지는 한 번만 기록해 재호출해도 중복 지급이 없다. `mission_claim_item_rewards(p_user_id, p_mission_id) → jsonb`는 그 미션의 `pending`을 모두 받는다(모두 들어갈 빈칸 필요, 이용 정지 중 거부). 251은 `notification_type`에 `mission_participation_cancelled` 값을 더했다. 옛 표·칸·함수는 바꾸지 않았고, 두 함수 모두 service_role만 실행하며 새 표는 RLS를 켜고 anon·authenticated 권한을 모두 회수했다.
- 롤백 실측(DO 블록 하나에 DDL과 검증을 담고 마지막에 예외로 전부 되돌림, 9묶음 통과): 새 개체 지급과 칸 +1·기록·개체 이력, 같은 미션·배지 재호출 멱등, 이미 가진 배지도 다른 미션에서 새 개체(칸 +1), 액티비티 배지 제외, 잠김은 배지 설정(`always_locked`)을 따름(기록과 개체의 `locked`·`unlock_required`·`lock_reason` 일치), 빈칸 부족 시 전부 보류하고 일부만 받기 불가, 이용 정지 중 받기 거부와 풀리면 받기·재받기 방지, 없는 미션·인벤토리, 미션 삭제 시 기록 CASCADE, 권한과 RLS. 실측 뒤 새 객체·시험 행이 공용 DB에 남지 않았음을 확인했다.
- 적용 뒤 확인: 함수 2개 SECURITY DEFINER, `authenticated` 실행 권한 없음, `service_role` 실행 가능, 새 표 RLS 켜짐·`authenticated` 읽기 권한 없음·0행, 알림 값 1개, 기존 미션 55건 그대로. 생성 타입(`database.generated.ts`)에 새 표·함수 2개·알림 값을 반영했고 타입 검사를 통과했다.
- 공용 DB 읽기 전용 확인: 미션 55건이 각각 보상 배지 1개를 갖고 있고(링크 55개) 숨김 배지·삭제된 배지·액티비티/아이템 외 유형이 보상인 것은 0건이다. 아이템 배지 보상은 2건이다. 숨김 배지는 전체 0개이고 «잠김으로 만든» 아이템 배지도 0개다.
- 앱이 지킬 반환 계약: `mission_grant_item_rewards`는 `{ok:true, status:'none'|'granted'|'pending', itemIds, pendingCount[, free, needed]}` 또는 `{ok:false, error:'mission_not_found'|'inventory_not_found'}`, `mission_claim_item_rewards`는 `{ok:true, granted, itemIds}` 또는 `{ok:false, error:'user_suspended'|'inventory_not_found'|'no_pending'|'insufficient_slots'[, free, needed]}`다. 포인트와 소식은 이 함수가 주지 않으므로 앱이 결과를 보고 처리한다.

## 상세 요구사항

### 서비스/코드베이스 관점

- **새 개체로 주기·보류·받기**: 보상 지급이 아이템 배지를 `mission_grant_item_rewards`로 준다(위 계약). 건너뛰는 코드(이미 가짐, 가득 참 사전 체크, `slot_full` 흔적 없는 continue)를 없앤다. 받기 API가 `mission_claim_item_rewards`를 부른다.
- **포인트**: 아이템 배지의 포인트는 열린 개체는 받을 때, 잠긴 개체는 열 때 준다(14.1절, 열 때는 `locked_item_open`이 처리). 그러므로 이 티켓의 지급과 받기 후속에서 잠긴 개체의 배지 포인트는 0으로 두고 열린 개체만 준다(`lib/drop-engine/issueFollowUp.ts:36~38` 패턴을 따른다). 미션 자체의 포인트(`reward_points`)는 지금 방식 그대로다.
- **숨김 배지 차단과 유형 검증**: 보상 배지 저장은 존재·삭제·유형(액티비티, 아이템만)·숨김·중복을 서버가 검증한다. 어드민 검색은 숨김을 거른다. 선행 조건·교차 게이트·게이트 미션 배지도 서버가 검증한다. 이미 쓰이는 배지를 숨김으로 바꾸는 저장은 거절한다. 지급·미션 상세·목록·투데이 카드는 숨김 보상 배지를 내리지 않는다.
- **소식**: «트라이브가 바뀌어 「○○」 미션 참가가 취소됐어요» 소식을 만든다. 알림 종류는 마이그레이션 251로 더했다. 목록의 이동 위치는 `/missions`다(상세는 트라이브 비대상·미완료면 404이기 때문). 호출 연결은 묶음 6이다. 문구는 UX Writing 가이드를 따른다.
- **기록**: 받은·받지 않은 아이템 보상은 `mission_item_rewards`, 참가 취소는 `mission_participation_cancellations`가 갖는다. 진행의 시점별 이력은 만들지 않는다(결정 5-b).
- **미션 상세의 받지 않은 보상**: 서버가 내 받지 않은 보상 목록을 상세 페이지 데이터로 내려준다. 잠긴 아이템 배지 보상은 이름·그림·설명 없이 등급과 잠김 표시만 싣는다(7.3절 가림 규칙). 화면은 5-7이다.

### UI/UX 관점 (해당 시)

- 없음(미션 상세의 «받기» 버튼과 안내는 5-7, 어드민 양식은 5-8).

## 구현 계획 (회차)

3회로 나눠 돌린다. 예상 파일은 1회 약 16개, 2회 약 18개, 3회 약 14개(테스트·문서 포함)라 `plan_only` 임계값(파일 5개 초과)을 넘으므로, 아래를 파일 단위 계획으로 보고 `planOnlyWaiver`를 첫 호출부터 건다. 경로는 `jam-web/src` 기준이고 줄 위치는 2026-10-19 조사 시점이다. DB는 끝났으므로 아현은 SQL을 쓰지 않는다. 유형은 세 회차 모두 `api`다.

### 1회: 보상 지급·보류·받기

1. **`lib/missions/rewards.ts`**(`grantMissionRewards` 31줄): 배지 조회(47~50줄)에서 유형을 나눈다. 액티비티는 지금처럼 `user_activity_badges`에 넣고(102~113줄, 보유 skip 103줄 유지), 아이템은 `supabase.rpc('mission_grant_item_rewards', { p_user_id, p_mission_id, p_badge_ids })` 한 번으로 지급한다(114~148줄의 `grant_inventory_item` 루프, 121·122·137~142줄의 흔적 없는 건너뛰기를 없앤다). 그 밖의 유형(체크인 등)과 `is_hidden` 배지는 지급하지 않고 `console.warn`을 남긴다. 결과 `status`가 `granted`면 `itemIds`로 후속(아래 2번)을, `pending`이면 받지 않은 보상으로 돌려준다. 반환 타입에 `pendingItemBadgeIds`(받지 않은 보상 배지 id)를 더한다. 배지 포인트(163줄 `badge_point_reward`)는 아이템 배지에서는 열린 개체만 주고 잠긴 개체는 0으로 한다.
