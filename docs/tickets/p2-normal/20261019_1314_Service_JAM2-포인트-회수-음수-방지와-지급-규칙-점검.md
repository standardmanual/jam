# [Service] JAM2 포인트: 회수 음수 방지와 지급 규칙 점검

## 핵심 요약

- 요구사항: 운영 로직 14장에 맞춘다. (1) 어드민 회수로 잔액이 0 아래로 내려가지 않게 한다(비교표 4.1절 문제 ③). 회수가 거절되면 어드민에게 이유를 알린다. (2) 14.1절의 «주는 곳» 표 8곳이 규칙대로 동작하는지 점검하고 다른 곳을 맞춘다. 조사에서 다른 곳은 둘이다. 액티비티 배지 포인트(등급별 10/20/50/100, 레벨형은 레벨마다 10, 숨김 0)와 컬렉션 완성 포인트(등급별 100/200/400/800, 등급당 한 번). (3) 모든 지급과 회수를 원장에 남기고 원장은 지우거나 고치지 않는다.
- 구현 계획: 시작 때 사용자 결정 2건을 질문하고 파일 단위 계획을 옮겨 쓴다. DB는 새 함수만 더한다. SQL은 사용자 승인과 롤백 실측 뒤 카리나가 실행한다. 포인트 화면은 5-7이다.
- 관련 파일(2026-10-19 조사, 시작 때 아현이 줄 위치를 다시 확인한다): 지갑·원장 마이그레이션 `080_point_system_renumbered_from_045_duplicate.sql`(`point_wallets` 43~47줄, `point_transactions`, `point_treasury`), `award_points` 현재 정의 `157_item_book_completion_points.sql`(87~122줄, 잠금·잔액 검사 없음), 앱 `jam-web/src/lib/points/index.ts`(`awardPoints` 47~92줄), 어드민 회수 `app/admin/points/UserGrantForm.tsx`(93~96줄) → `app/api/admin/points/grant/route.ts`(41줄)·`app/api/admin/users/bulk/route.ts`(130줄) → `lib/points/admin-grant.ts`(검증 36~62줄, 실행 72~85줄, `admin_deduct`), 본보기 `220_jam_ledger.sql`(`balance >= 0` CHECK 26줄, `jam_apply` 176~187줄), 배지 포인트 `lib/badge-engine/index.ts:1505-1511`·`usageBadges.ts:249`, 컬렉션 `222_item_book_tiers.sql:262-278`·`app/api/itembooks/[id]/slot/route.ts:122`, 조사 결과 전문은 상위 티켓 `20261019_1310`.

## 배경 / 문제 정의

공용 DB의 포인트 지갑은 1개이고 음수 잔액은 지금 0건이다. 하지만 `award_points`에는 행 잠금도 잔액 검사도 없고, 어드민 회수 경로는 입력의 양수 여부만 검사한다. 그래서 잔액보다 큰 금액을 회수하면 음수가 된다.
14.1절 표와 비교하면 지급 8곳 가운데 체크인 배지(처음 한 번), 아이템 배지(열린 상태가 될 때 일련번호마다 한 번), 믹스(성공은 레시피별, 실패 10), 미션 보상, 퀘스트 완료(100), 운영자 지급은 맞다. 다른 곳 둘은 다음과 같다.
- **액티비티 배지**: 받을 때 한 번 주는 것은 맞지만 금액이 `badges.point_reward`로 배지마다 다르다. 등급별 일괄 값(10/20/50/100)이나 설정 화면이 없다. 반복형을 다시 받을 때는 포인트가 없다(`increment` 경로). 숨김 배지 0은 243의 CHECK가 보장한다. 등급별 일괄 값은 밸런스 설정 화면(19장)의 일이라 묶음 7이다.
- **컬렉션 완성**: 등급별 값과 등급당 한 번은 등급형(`tier_mode`)을 켠 컬렉션에서만 맞고, 켜지 않은 컬렉션은 옛 함수로 컬렉션당 한 번이다. 등급형을 켠 컬렉션이 지금 몇 개인지는 확인하지 못했다.
공용 DB 주의: 옛 프로덕션 코드가 `point_wallets`와 `award_points`를 쓴다. 이 둘의 정의와 제약을 바꾸는 변경은 새 칸·새 함수 덧붙이기 규칙의 예외라서 사용자 승인이 필요하다.

## 시작 전에 사용자에게 확인할 것 (주요 결정, 질문창)

1. **음수 방지 방식**: 새 회수 함수(`admin_deduct_points` 같은 이름, 행 잠금 + 잔액 검사 + 원장 기록, 거절 사유를 돌려줌)를 더하고 어드민 회수 경로가 그것을 쓰게 한다(추천, 옛 지갑과 `award_points`를 바꾸지 않는다). 대안은 `point_wallets`에 `balance >= 0` CHECK를 더하는 것이다(옛 테이블 변경이라 승인이 필요하고, 옛 프로덕션의 회수가 CHECK에 걸려 실패할 수 있다). CHECK는 옛 코드를 정리하는 묶음 6에서 더할 수 있다.
2. **액티비티 배지 포인트**: 지금처럼 배지마다 `point_reward`를 두고, 컨텐츠 시드(245·248)와 기존 배지의 값이 14.1절 등급별 값과 맞는지 점검한다(추천, 등급별 일괄 값과 설정 화면은 묶음 7). 대안은 등급별 기본값을 설정 행으로 두고 `point_reward`가 비어 있으면 그 값을 쓰는 것이다(일괄 값이 생기지만 범위가 커진다).

## 상세 요구사항

### 서비스/코드베이스 관점

- **회수 음수 방지**: 결정 1에 따라 새 함수를 더한다. 같은 지갑에 동시에 회수가 들어와도 잔액이 0 아래로 내려가지 않는다(행 잠금). 거절은 기존 500 대신 사유(현재 잔액, 요청 금액)를 어드민에게 돌려준다. 일괄 회수 경로(`users/bulk`)도 같은 함수를 쓴다.
- **원장**: 지급과 회수는 모두 `point_transactions`에 남는다. 원장을 지우거나 고치는 경로가 없는지 확인한다. 유저 화면에는 «회수» 용어를 쓰지 않는다(14.2절, 화면은 5-7).
- **지급 점검**: 14.1절 표 8곳의 현재 코드 위치와 판정(맞음/다름)을 이 티켓 「조사 결과」 절에 표로 남기고, 다른 곳을 결정 2에 따라 맞춘다. 컬렉션 완성은 시작 때 공용 DB에서 등급형을 켠 컬렉션 수를 읽기 전용으로 확인한 뒤, 켜지 않은 컬렉션의 포인트 처리 방침을 사용자에게 한 번 더 묻는다.
- **챕터 점수와의 경계**: 챕터 점수 연결(5-5)은 이 티켓에서 하지 않는다. 다만 «포인트를 조건으로 하는 배지는 챕터 점수에 넣지 않는다»를 5-5가 판별할 수 있도록, 배지 조건에 포인트가 들어 있는지 읽는 방법을 이 티켓에서 확인해 5-5에 넘긴다.
- 새 함수는 덧붙이기만 한다. 생성 타입을 같은 커밋에 맞춘다.

### UI/UX 관점 (해당 시)

- 없음(어드민 회수 안내는 5-8, 포인트 화면은 5-7).

## 구현 계획 (회차)

1회로 돌린다(예상 파일 약 10개). 앱 파일 단위 계획은 아현이 시작 때 쓴다.

1. 마이그레이션(번호는 시작 때 확인): 새 회수 함수. 되돌림 SQL을 싣는다.
2. `lib/points/admin-grant.ts`: 회수를 새 함수로 바꾸고 거절 사유를 돌려준다. `grant/route.ts`와 `users/bulk/route.ts`가 사유를 응답한다.
3. 지급 규칙 점검 결과에 따른 보정(결정 2).
4. 시험: 잔액보다 큰 회수 거절과 잔액 변화 없음, 동시 회수 두 건에서 잔액이 음수가 되지 않음, 일괄 회수 일부 거절, 원장 기록.
5. 문서: `docs/service/prd/02_DATA_MODEL.md`, 포인트 PRD(`docs/service/prd/` 아래에서 찾는다), 비교표 상태.

## 완료 조건

### 구현 범위 (게이트 판정 대상)

- 잔액보다 큰 회수가 거절되고 지갑과 원장이 바뀌지 않으며, 거절 사유가 어드민 응답에 담긴다. 동시 회수에서도 잔액이 음수가 되지 않는다(롤백 실측과 시험으로 확인).
- 14.1절 표 8곳의 현재 판정이 이 티켓에 표로 남아 있고, 다른 곳이 결정 2에 따라 맞춰져 있다.
- 마이그레이션이 옛 객체의 서명·권한을 바꾸지 않고(예외는 사용자 승인 기록) 되돌림 SQL을 싣는다.

### 후속 범위 (담당: 카리나, 시점: 사용자 승인 뒤)

- 시작 때 결정 1·2번과 컬렉션 완성 포인트 방침을 이 티켓 「사용자 결정」 절에 기록한다. SQL 실행은 승인과 롤백 실측 뒤에 한다.
