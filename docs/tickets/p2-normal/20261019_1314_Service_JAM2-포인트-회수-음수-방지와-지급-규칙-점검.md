# [Service] JAM2 포인트: 회수 음수 방지와 지급 규칙 점검

## 핵심 요약

- 요구사항: 운영 로직 14장에 맞춘다. (1) 어드민 회수로 잔액이 0 아래로 내려가지 않게 한다(비교표 4.1절 문제 ③). 회수가 거절되면 어드민에게 이유를 알린다. (2) 14.1절의 «주는 곳» 표 8곳이 규칙대로 동작하는지 점검하고 다른 곳을 맞춘다. 조사에서 다른 곳은 둘이다. 액티비티 배지 포인트(등급별 10/20/50/100, 레벨형은 레벨마다 10, 숨김 0)와 컬렉션 완성 포인트(등급별 100/200/400/800, 등급당 한 번). (3) 모든 지급과 회수를 원장에 남기고 원장은 지우거나 고치지 않는다.
- 구현 계획: 사용자 결정 4건(2026-10-20)을 받아 DB(마이그레이션 252·253, 카리나가 승인·롤백 실측 뒤 적용 완료)와 앱을 2회로 나눈다(1회 어드민 회수가 새 함수를 쓰고 거절 사유를 돌려줌, 2회 믹스 결과·컬렉션 보상 배지의 배지 포인트 지급 누락 보정). 아래 「구현 계획 (회차)」를 따른다. 포인트 화면은 5-7이다.
- 관련 파일(2026-10-19 조사, 시작 때 아현이 줄 위치를 다시 확인한다): 지갑·원장 마이그레이션 `080_point_system_renumbered_from_045_duplicate.sql`(`point_wallets` 43~47줄, `point_transactions`, `point_treasury`), `award_points` 현재 정의 `157_item_book_completion_points.sql`(87~122줄, 잠금·잔액 검사 없음), 앱 `jam-web/src/lib/points/index.ts`(`awardPoints` 47~92줄), 어드민 회수 `app/admin/points/UserGrantForm.tsx`(93~96줄) → `app/api/admin/points/grant/route.ts`(41줄)·`app/api/admin/users/bulk/route.ts`(130줄) → `lib/points/admin-grant.ts`(검증 36~62줄, 실행 72~85줄, `admin_deduct`), 본보기 `220_jam_ledger.sql`(`balance >= 0` CHECK 26줄, `jam_apply` 176~187줄), 배지 포인트 `lib/badge-engine/index.ts:1505-1511`·`usageBadges.ts:249`, 컬렉션 `222_item_book_tiers.sql:262-278`·`app/api/itembooks/[id]/slot/route.ts:122`, 조사 결과 전문은 상위 티켓 `20261019_1310`.

## 배경 / 문제 정의

공용 DB의 포인트 지갑은 1개이고 음수 잔액은 지금 0건이다. 하지만 `award_points`에는 행 잠금도 잔액 검사도 없고, 어드민 회수 경로는 입력의 양수 여부만 검사한다. 그래서 잔액보다 큰 금액을 회수하면 음수가 된다.
14.1절 표와 비교하면 지급 8곳 가운데 체크인 배지(처음 한 번), 아이템 배지(열린 상태가 될 때 일련번호마다 한 번), 믹스(성공은 레시피별, 실패 10), 미션 보상, 퀘스트 완료(100), 운영자 지급은 맞다. 다른 곳 둘은 다음과 같다.
- **액티비티 배지**: 받을 때 한 번 주는 것은 맞지만 금액이 `badges.point_reward`로 배지마다 다르다. 등급별 일괄 값(10/20/50/100)이나 설정 화면이 없다. 반복형을 다시 받을 때는 포인트가 없다(`increment` 경로). 숨김 배지 0은 243의 CHECK가 보장한다. 등급별 일괄 값은 밸런스 설정 화면(19장)의 일이라 묶음 7이다.
- **컬렉션 완성**: 등급별 값과 등급당 한 번은 등급형(`tier_mode`)을 켠 컬렉션에서만 맞고, 켜지 않은 컬렉션은 옛 함수로 컬렉션당 한 번이다. 등급형을 켠 컬렉션이 지금 몇 개인지는 확인하지 못했다.
공용 DB 주의: 옛 프로덕션 코드가 `point_wallets`와 `award_points`를 쓴다. 이 둘의 정의와 제약을 바꾸는 변경은 새 칸·새 함수 덧붙이기 규칙의 예외라서 사용자 승인이 필요하다.

## 시작 전에 사용자에게 확인할 것 (주요 결정, 질문창)

1. **음수 방지 방식**: 새 회수 함수(`admin_deduct_points` 같은 이름, 행 잠금 + 잔액 검사 + 원장 기록, 거절 사유를 돌려줌)를 더하고 어드민 회수 경로가 그것을 쓰게 한다(추천, 옛 지갑과 `award_points`를 바꾸지 않는다). 대안은 `point_wallets`에 `balance >= 0` CHECK를 더하는 것이다(옛 테이블 변경이라 승인이 필요하고, 옛 프로덕션의 회수가 CHECK에 걸려 실패할 수 있다). CHECK는 옛 코드를 정리하는 묶음 6에서 더할 수 있다.
2. **액티비티 배지 포인트**: 지금처럼 배지마다 `point_reward`를 두고, 컨텐츠 시드(245·248)와 기존 배지의 값이 14.1절 등급별 값과 맞는지 점검한다(추천, 등급별 일괄 값과 설정 화면은 묶음 7). 대안은 등급별 기본값을 설정 행으로 두고 `point_reward`가 비어 있으면 그 값을 쓰는 것이다(일괄 값이 생기지만 범위가 커진다).

## 사용자 결정과 적용 기록 (2026-10-20)

1. **음수 방지는 새 회수 함수로 한다**(추천 채택). `admin_deduct_points(p_user_id, p_amount, p_admin_reason_label, p_admin_reason_note) → jsonb`가 지갑 행을 `FOR UPDATE`로 잠그고 잔액을 검사해, 모자라면 아무것도 바꾸지 않고 `{ok:false, error:'insufficient_balance', balance, requested}`를 돌려준다. 통과하면 기존 `award_points(음수, 'admin_deduct')`로 원장·지갑·금고를 처리한다. 지갑이 없는 유저는 잔액 0으로 거절하고 빈 지갑 행을 만들지 않는다. **옛 프로덕션 코드는 계속 `award_points`로 회수하므로 새 앱이 배포되고 옛 코드가 사라질 때까지 그 경로는 막히지 않는다.** 모든 경로를 막는 `point_wallets.balance >= 0` CHECK는 옛 코드를 정리하는 묶음 6에서 더한다.
2. **배지 포인트 값: 아이템·체크인 배지를 규칙 값으로 지금 바로 맞춘다**(사용자가 추천(오픈 직전 적용)과 달리 «지금 바로 적용»을 골랐다). 공용 DB의 삭제되지 않은 아이템 배지 270개와 체크인 배지 1,832개는 모두 Common이고 `point_reward = 0`이었다. 마이그레이션 253이 이 2,102개를 등급별 규칙 값(Common 10, Rare 20, Epic 50, Mystic 100, 지금은 Common만 있다)으로 바꿨다. 이미 다른 값을 정해 둔 배지, 삭제된 배지, 액티비티 배지는 건드리지 않았다. 포인트는 앞으로 받는 배지부터 나가고(소급 없음) 프로덕션 유저에게도 즉시 나간다. 액티비티 배지는 새 계열 시드 245·248이 이미 규칙 값(등급형 10/20/50/100, 레벨형 레벨마다 10, 단일 10)을 넣고, 기존 재활용 배지(Common 85개 중 퀘스트 완료 배지 하나가 100)는 컨텐츠 확정(티켓 `20261018_1816`) 때 맞춘다(등급 기준 일괄 변경은 퀘스트 완료 배지 같은 예외가 있어 위험하다).
3. **컬렉션 완성 포인트는 지금 방식을 유지한다**(추천 채택). 공용 DB의 컬렉션 100개 가운데 등급형(`tier_mode`)을 켠 것은 0개라 전부 옛 경로(컬렉션당 한 번, `item_books.reward_points`)다. 등급형 전환(등급마다 100/200/400/800, 등급당 한 번)은 컬렉션 100개에 영향을 주는 데이터 변경이라 배포 준비 결정 목록에 올린다(`tier_mode`를 켜는 마이그레이션과 어드민 화면이 앱에 없다).
4. **믹스 결과로 받은 아이템 배지와 컬렉션 보상 배지가 배지 포인트를 주지 않는 것은 5-4 2회에서 고친다**(추천 채택). 14.1절은 아이템 배지를 «열린 상태가 될 때 일련번호마다 한 번», 액티비티 배지를 «받을 때»로 정한다.
5. 카리나가 질문 없이 정한 것: (a) 거절 응답은 HTTP 409에 [현상] → [원인] → [해결책] 문구(현재 잔액과 요청 금액 포함)이고 기존 고액 확인창의 422 + `requiresConfirmation`과 겹치지 않는다. 일괄 회수는 거절된 유저를 건너뛴 목록의 사유로 알린다. (b) 작업은 DB를 먼저 적용하고(앱이 새 함수를 부르므로) 앱을 잇는다. (c) 반복형 배지를 다시 받을 때 포인트가 0인 현재 동작은 그대로 둔다(14.1절이 정하지 않았고 포인트 파밍 길을 만들지 않기 위해). (d) 공개 전 레시피의 시험 믹스(`testMix`)가 포인트를 지급하는 점은 의도 확인이 필요해 기록만 하고 이 티켓에서 고치지 않는다(`lib/combine/index.ts` 336~340줄). (e) 5-5에 넘기는 판별: 배지 조건에 포인트를 가리키는 키는 없다.

**DB 적용 기록(2026-10-20, 사용자 승인)**: 마이그레이션 252(새 회수 함수 `admin_deduct_points`, SECURITY DEFINER, service_role만 실행)와 253(아이템·체크인 배지 포인트 2,102개를 10으로)을 롤백 실측 뒤 적용했다. 252 실측 8묶음(잔액 초과 거절 시 지갑·원장·금고 불변, 잔액 안 회수의 원장·금고·잔액, 전액 회수 뒤 0과 1 더 회수 거절, 0·음수·빈 금액 거절, 지갑 없는 유저·없는 유저는 잔액 0으로 거절하고 지갑 행이 안 생김, 권한, 음수 잔액 없음)과 253 실측(2,102행 갱신, 액티비티·삭제 배지 불변, 재실행 0행)이 통과했고 실측 뒤 공용 DB에 남은 것이 없음을 확인했다. 적용 뒤 확인: 함수 SECURITY DEFINER, `authenticated`·`anon` 실행 불가와 `service_role` 실행 가능, 아이템 270·체크인 1,832가 모두 `point_reward = 10`, 액티비티 배지의 0이 아닌 값 1개(퀘스트 완료 배지) 불변, 음수 잔액 0건. 생성 타입(`database.generated.ts`)에 새 함수를 반영했고 타입 검사를 통과했다.

- **회수 경로의 현재 동작**: `UserGrantForm`의 «회수»는 `-amount`로 `grant` 라우트에 보내고(검증은 양수 여부뿐) `lib/points/admin-grant.ts`가 `award_points`를 부른다. `award_points`(157)는 지갑 `ON CONFLICT DO UPDATE balance = balance + p_amount`뿐이라 잔액 검사가 없다. 잔액보다 큰 회수는 성공하고 지갑이 음수가 되며, 지갑이 없던 유저는 음수 잔액으로 지갑이 새로 만들어진다(HTTP 200). 기존 500은 DB 호출 실패 때만 나온다. 일괄 회수(`users/bulk`)는 유저마다 RPC 1회(동시 5건 워커, 한 번에 200명 상한)이고 일부만 실패하면 응답은 항상 200이며 `skipped`에 실패 사유가 담긴다. `toastBulkResult`가 `label: reason`을 이미 보여 주므로 사유만 담으면 화면 변경이 없다. 일괄 `dryRun`은 이미 `negativeBalanceCount`를 세지만(`lib/admin/user-bulk-impact.ts`) 실행을 막지 않는다(문구 «마이너스가 되는 유저»는 거절로 바뀌므로 5-8에서 고친다).
- **원장 보호**: `src` 전체에 `point_wallets`·`point_transactions`·`point_treasury`를 UPDATE·DELETE하는 앱 코드는 없다. 마이그레이션의 DML은 `award_points`뿐이다. 세 표 모두 RLS가 켜져 있고 anon·authenticated는 직접 쓸 수 없다(정책 없음). `080`에는 테이블 REVOKE도 불변 트리거도 없어(`220`의 `jam_*` 표는 REVOKE를 이중으로 건다) service_role이 쓰려 하면 DB가 막지 않는다. `point_wallets.user_id`·`point_transactions.user_id`는 `ON DELETE CASCADE`라 유저 탈퇴 때 함께 지워진다(운영 로직 17.2절이 정한 것이라 정책과 일치, 14.2절 «원장을 지우지 않는다»의 유일한 예외). `source_badge_id`·`source_mission_id`·`source_item_book_id`는 NO ACTION이라 참조된 배지·미션·컬렉션의 삭제를 막는다. 원장에는 처리한 어드민 id 칸이 없다(`jam_transactions`에는 `admin_user_id`가 있다). 14.4절은 «사유가 원장에 남는다»만 요구하므로 이번에는 더하지 않는다.
- **공용 DB 현황(2026-10-20)**: 포인트 지갑 1개(음수 0건), 원장 3줄(믹스 레시피 보상), 금고 total_minted 240·total_reclaimed 0. 원장 `reason` CHECK는 `badge_point_reward`·`mission_point_reward`·`admin_grant`·`admin_deduct`·`combine_fail_reward`·`combine_recipe_reward`·`item_book_completion_point_reward` 7가지다.
- **5-5(챕터 점수)에 넘기는 판별**: 배지 조건에 포인트를 가리키는 키는 없다(허용 키 CHECK `badges_condition_json_known_keys`의 최신판은 `247`이고 `point` 문자열이 없으며 `lib/badge-engine/conditionRegistry.ts`·`jamActionKeys.ts`·`BadgeCondition`에도 없다. `point_reward`는 지급 설정 칸이지 조건 키가 아니다). 5-5는 «포인트 조건 배지 제외»를 빈 집합으로 처리하면 된다(`badges.condition_json`의 키 목록과 제외 키 집합의 교집합). 같은 12.2절 제외 문장의 나머지는 `follower_count`·`following_count`(`conditionRegistry.ts` 1681·1703줄 근처)와 `chapter_reached`(2319줄 근처)다. `jam_total_earned`·`jam_weekly_earned`·`jam_week_*`는 «잼»이지 «포인트»가 아니다. 나중에 포인트 키를 더하면 CHECK(DB)와 레지스트리(앱)를 함께 고친다.

## 상세 요구사항

### 서비스/코드베이스 관점

- **회수 음수 방지**: 결정 1에 따라 새 함수를 더한다. 같은 지갑에 동시에 회수가 들어와도 잔액이 0 아래로 내려가지 않는다(행 잠금). 거절은 기존 500 대신 사유(현재 잔액, 요청 금액)를 어드민에게 돌려준다. 일괄 회수 경로(`users/bulk`)도 같은 함수를 쓴다.
- **원장**: 지급과 회수는 모두 `point_transactions`에 남는다. 원장을 지우거나 고치는 경로가 없는지 확인한다. 유저 화면에는 «회수» 용어를 쓰지 않는다(14.2절, 화면은 5-7).
- **지급 점검**: 14.1절 표 8곳의 현재 코드 위치와 판정(맞음/다름)을 이 티켓 「조사 결과」 절에 표로 남기고, 다른 곳을 결정 2에 따라 맞춘다. 컬렉션 완성은 시작 때 공용 DB에서 등급형을 켠 컬렉션 수를 읽기 전용으로 확인한 뒤, 켜지 않은 컬렉션의 포인트 처리 방침을 사용자에게 한 번 더 묻는다.
- **챕터 점수와의 경계**: 챕터 점수 연결(5-5)은 이 티켓에서 하지 않는다. 다만 «포인트를 조건으로 하는 배지는 챕터 점수에 넣지 않는다»를 5-5가 판별할 수 있도록, 배지 조건에 포인트가 들어 있는지 읽는 방법을 이 티켓에서 확인해 5-5에 넘긴다.
- 새 함수는 덧붙이기만 한다. 생성 타입을 같은 커밋에 맞춘다.

### UI/UX 관점 (해당 시)

- 없음(어드민 회수 안내는 5-8, 포인트 화면은 5-7).

## 구현 계획 (회차)

2회로 돌린다(1회는 DB 적용 뒤 앱 약 12~15개). 경로는 `jam-web/src` 기준이고 줄 위치는 2026-10-20 조사 시점이라 시작 때 아현이 다시 확인한다. 1회는 SQL을 쓰지 않는다(252·253은 적용 완료). 유형은 두 회차 모두 `api`다. 파일이 5개를 넘으므로 `planOnlyWaiver`를 첫 호출부터 건다.

### 1회: 어드민 회수가 새 함수를 쓰고 거절 사유를 돌려준다

1. **신규 `lib/points/deduct-contract.ts`**: `admin_deduct_points`의 반환 계약 파서 `parseAdminDeductResult(raw)`가 `{ok:true, transactionId, balance}`, `{ok:false, error:'insufficient_balance', balance, requested}`, `{ok:false, error:'invalid_amount'}`만 인정하고 계약 밖 응답은 `null`로 돌려준다(성공으로 보지 않는다, 5-3의 `claim-contract.ts` 방식).
2. **`lib/points/index.ts`**: `awardPoints`는 지급용으로 그대로 두고, 신규 `deductPointsByAdmin(userId, amount, { label, note })`가 `rpc('admin_deduct_points')`를 부른다. 성공이면 기존 `notifyPointChange`(비공개, 125~135줄 `admin_points_changed`)를 같은 방식으로 보내고, RPC 오류·계약 밖 응답은 `engine_decision_log`(`point_award_failed`)에 남기고 `null`을 돌려준다. 거절(`insufficient_balance`)은 알림 없이 결과로 돌려준다.
3. **`lib/points/admin-grant.ts`** `executeAdminGrant`(72~85줄): 금액이 음수면 `deductPointsByAdmin`을 쓰고(양수는 지금처럼 `awardPoints`), 반환 타입을 `ExecutedAdminGrant | AdminGrantRejected | null`로 넓힌다. 회수 성공 뒤 잔액은 RPC가 돌려준 `balance`를 쓴다(`getWallet` 재조회로 동시 실행과 어긋나지 않게). `getWallet`의 조회 오류가 0으로 보이는 기존 동작(`lib/points/index.ts` 147~150줄)은 바꾸지 않는다.
4. **`app/api/admin/points/grant/route.ts`**(POST 12~47줄, 실패 500은 42~44줄): 거절이면 HTTP **409**에 `{ error: 문구, code: 'insufficient_balance', balance, requested }`를 돌려준다. 문구는 [현상] → [원인] → [해결책] 구조(예: «회수하지 못했어요. 이 유저의 포인트가 N점이라 M점을 회수할 수 없어요. N점 이하로 줄여서 다시 회수해 주세요.»)이고 UX Writing 가이드를 따른다. 422 + `requiresConfirmation`(고액 확인창이 가로챈다, `UserGrantForm.tsx` 98~102줄)과 겹치지 않게 한다. 단건 폼은 서버의 `error` 문구를 그대로 보여 주므로 화면 변경이 없다.
5. **`app/api/admin/users/bulk/route.ts`**(129~132줄 근처): 거절된 유저를 `{ id, ok: false, error: 사유 }`로 담아 `skipped`로 돌려준다(사유에 현재 잔액과 요청 금액). 거절은 오류가 아니므로 응답은 200이고 나머지 유저는 계속 처리한다. 일괄 `dryRun`의 `negativeBalanceCount`와 `UserBulkImpactSummary.tsx`의 문구(«마이너스가 되는 유저»)는 5-8에서 고친다(이 티켓에서는 건드리지 않는다).
6. **시험**: 파서(계약 안·밖 응답), `deductPointsByAdmin`(성공 시 알림, 거절 시 알림 없음, RPC 오류 시 `null`과 로그), `executeAdminGrant`(회수 성공·거절·RPC 실패, 지급은 기존 경로), 신규 단건 `grant` 라우트 시험(401·403, 검증 실패, 회수 거절 409의 사유 필드, 회수 성공, 지급 회귀, RPC 오류 500, 내부 정보 비노출), 일괄 라우트 시험(일부 거절 시 `skipped` 사유와 나머지 `processed`). 동시 회수 시 음수 방지는 DB 롤백 실측(마이그레이션 252)에서 확인했고 앱은 DB 응답을 그대로 따르는지만 시험한다.
7. **문서**: `docs/service/prd/02_DATA_MODEL.md`(포인트 절 831·840줄 근처: 새 함수와 계약), `docs/service/prd/point-system/OBJECT_MODEL.md`(회수 규칙, 옛 경로 한계), `docs/plan/jam2/service-redesign/현재 서비스 비교.md`(4.1절 문제 ③ 상태, 5.3절 «11 포인트» 행), 배지 포인트 값 현황(253 적용: 아이템·체크인 배지 10, 액티비티 배지는 컨텐츠 확정 때)을 알맞은 컨텐츠·포인트 문서에 반영한다.

시작 때 아현이 코드를 읽고 파일 단위 계획을 이 절에 덧붙인 뒤 구현한다(1회 머지 뒤).
