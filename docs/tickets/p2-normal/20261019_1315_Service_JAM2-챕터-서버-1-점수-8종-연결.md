# [Service] JAM2 챕터 서버 ①: 점수 8종 연결

## 핵심 요약

- 요구사항: 운영 로직 12.2절의 점수 표를 앱에 연결한다. 모은 잼, 캡슐 열기, 잠긴 아이템 배지 열기, 배지 받기, 컬렉션 완성, 믹스 성공, 미션 완료, 드랍·픽업이 일어날 때 마이그레이션 221의 `chapter_add_score`를 부른다. 호출부가 지킬 제외 규칙을 구현한다. 포인트·팔로우·챕터를 조건으로 하는 배지는 점수에 넣지 않고, 숨김 배지는 세지 않으며, 자기가 드랍한 것을 주운 것은 세지 않고, 이용 정지 중에는 점수가 생기지 않고, 체크인 배지는 처음 받을 때만 센다.
- 구현 계획: 사용자 결정 4건(2026-10-20)과 시작 전 조사를 반영해 4회로 나눈다(1회 점수 연결 함수·원천 id 유틸과 잼·캡슐·잠긴 열기·드랍·픽업, 2a 배지 받기 공용 함수와 새 발급·체크인·온보딩, 2b 반복형 회차, 3회 컬렉션·믹스·미션과 종합 시험). DB 변경은 3회의 믹스 성공 로그 id를 돌려주는 새 함수 1개뿐이다(옛 함수는 바꾸지 않고, 그때 사용자 승인과 롤백 실측을 따로 받는다). 아래 「구현 계획 (회차)」를 따른다.
- 관련 파일(2026-10-19 조사, 시작 때 아현이 줄 위치를 다시 확인한다): 챕터 함수 `jam-web/supabase/migrations/221_chapters.sql`(`chapter_add_score` 201~211줄, 같은 키 재호출 255~265줄, 활동 종류 179~191줄, 주간 상한 267~282줄), 8개 지점의 위치는 상위 티켓 `20261019_1310`의 표를 따른다(잼 `lib/jam/settlement.ts:176`, 캡슐 `lib/capsule/open.ts:193`, 잠긴 열기 `lib/inventory/lockedItemFill.ts:168`, 배지 받기 여러 곳, 컬렉션 `api/itembooks/[id]/slot/route.ts:122`·`itembook/checker.ts:198`, 믹스 `lib/combine/index.ts:347`, 미션 `lib/missions/checker.ts:175`, 드랍·픽업 `api/drops/route.ts:374`·`api/drops/[dropId]/pickup/route.ts:156`), 자기 픽업 판별 `lib/drop/self-pickup.ts`, 이용 정지 `lib/suspension/suspension.ts`.

## 5-4에서 넘어온 항목 (2026-10-20)

- **«포인트를 조건으로 하는 배지는 챕터 점수에 넣지 않는다»의 판별**: 배지 조건에 포인트를 가리키는 키는 **하나도 없다**(허용 키 CHECK `badges_condition_json_known_keys`의 최신판 `247`, `lib/badge-engine/conditionRegistry.ts`, `jamActionKeys.ts`, `BadgeCondition` 모두 확인). 따라서 이 제외 규칙은 지금 빈 집합이고, 구현은 `badges.condition_json`의 키 목록과 «제외 키 집합»(포인트 키 0개 + `follower_count`·`following_count` + `chapter_reached`)의 교집합으로 판별하게 만들면 나중에 포인트 키가 생겨도 한 곳만 고치면 된다. `jam_total_earned`·`jam_weekly_earned`·`jam_week_*`는 «잼»이지 «포인트»가 아니라 제외하지 않는다. 포인트 키를 더하면 CHECK(DB)와 레지스트리(앱)를 함께 고친다. 상세 근거는 티켓 `20261019_1314`의 「조사 결과」에 있다.

## 배경 / 문제 정의

`chapter_add_score`는 (활동 종류, 원천 id)를 전역 유일 키로 써서 같은 일을 두 번 보내도 한 번만 센다. 그래서 점수 연결은 «원천 id를 무엇으로 정할지»가 핵심이다. 다른 유저의 기록과 키가 겹치면 예외가 나므로 원천 id는 전역에서 유일해야 한다.
8개 지점은 모양이 제각각이다. 잼과 미션은 동기화 파이프라인 한 곳이고, 캡슐·잠긴 열기·컬렉션·드랍·픽업은 API 라우트의 RPC 호출이다. 믹스 성공 RPC는 boolean만 돌려주고 로그 id가 없다. 컬렉션 완성은 등급형을 켜지 않은 컬렉션의 등급 값이 없다. «배지 받기»는 발급 코드가 약 8곳에 흩어져 있고, 숨김·포인트·팔로우·챕터 조건 배지를 거르는 공용 함수도 없다. 미션 완료의 INSERT는 id를 돌려받지 않는다(5-1에서 해결).
챕터가 없는 유저(퀘스트 전)의 점수는 쌓이고 `chapter_start`가 한꺼번에 승급시킨다(221). 퀘스트 전 점수가 쌓이는 것이 12.2절 규칙과 맞는지 시작 때 확인한다.

## 시작 전에 사용자에게 확인할 것 (주요 결정, 질문창)

1. **배지 받기 점수의 연결 방식**: 앱 코드의 한 함수(예: `lib/chapter/score.ts`)를 각 발급 지점이 부른다(추천, 제외 규칙을 한 곳에 둔다). 대안은 DB 트리거(활동 배지 지급 기록이 INSERT될 때 점수를 쌓음)다. 지점이 한 곳으로 모이지만, 같은 DB를 쓰는 옛 프로덕션의 유저에게도 점수가 쌓이고 호출부 제외 규칙을 SQL에 옮겨야 한다.
2. **컬렉션 완성 점수의 등급**: 등급형을 켠 컬렉션은 등급 값(Common 100 ~ Mystic 800)을 따르고, 켜지 않은 컬렉션은 Common으로 센다(추천, 완성 한 번에 한 번). 대안은 켜지 않은 컬렉션에는 점수를 주지 않는 것이다. 시작 때 공용 DB에서 등급형을 켠 컬렉션 수를 읽기 전용으로 확인하고 다시 묻는다.
3. **점수 연결이 실패했을 때**: 본 동작(캡슐 열기, 믹스 등)은 성공시키고 점수 실패는 기록만 남긴다(추천, 같은 원천 id로 다시 보낼 수 있다). 대안은 점수 실패 때 본 동작도 되돌리는 것이다(캡슐을 열었는데 실패하는 일이 생긴다).

## 사용자 결정과 적용 기록 (2026-10-20)

사용자가 아래 4건을 모두 카리나의 추천대로 정했다.

1. **퀘스트를 마치기 전(챕터가 없는 상태)에 쌓인 점수는 쌓아 두었다가 챕터 1 시작 때 한꺼번에 반영한다**(마이그레이션 221의 가정 그대로). 퀘스트 전에도 점수가 생기는 동작은 막는 코드가 없어 첫 동기화(잼, Common·Lv.1 배지, 체크인 첫 획득), 캡슐 열기, 잠긴 열기, 드랍·픽업·믹스·컬렉션·미션이다. 예상 양은 사실상 첫 동기화 안의 100~600점(가정이 섞인 추정)이라 챕터 2 기준 1,000점에는 보통 못 미친다.
2. **«배지 받기» 점수의 원천은 (유저, 배지) 기준 결정적 id로 한 번만 센다.** 같은 배지를 초기화나 삭제 뒤 다시 받아도 점수는 다시 들어가지 않는다(어드민 유저 초기화는 챕터 점수를 지우지 않는다). 반복형은 새 회차마다 따로 세어 다시 받을 때마다 10점이 들어간다(회차 구분은 `earn_history`의 활동 id).
3. **카탈로그 재평가 배치로 소급 발급되는 배지는 챕터 점수에 넣지 않는다.** 배지가 기존 유저에게 한꺼번에 수십 개씩 소급 발급되어 챕터가 한꺼번에 오르는 것을 막는다(오픈 준비 때 다시 정할 수 있다). 배치는 `reevaluateCatalog.ts`의 `silent: true`, `triggeredBy 'catalog_reevaluation'`으로 구분된다.
4. **등급형(`tier_mode`)을 켜지 않은 컬렉션(공용 DB 100개 전부)의 완성은 Common 100으로 세고 등급형 전환 뒤에도 이중 가산이 없다.** 완성 기록 표에 id가 없어 원천 id는 (유저, 컬렉션, 등급)으로 만든 결정적 id다. 옛 컬렉션도 등급 `common`으로 같은 키를 쓰므로 나중에 등급형으로 바뀌어도 같은 완성이 두 번 세어지지 않는다. 이미 완성한 유저가 다시 장착해도 소급 가산하지 않는다(장착 전후로 완성 기록 존재를 읽어 «이번에 새로 완성했는가»를 가린다).
5. 카리나가 질문 없이 정한 것: (a) 연결은 DB 트리거가 아니라 앱 한 함수(`lib/chapter/score.ts`)다(지점을 한 함수로 모으고 호출부 제외 규칙을 한 곳에 둔다, 같은 DB를 쓰는 옛 프로덕션 유저에게 점수가 쌓이지 않는다). (b) 점수 함수는 절대 던지지 않는다. 실패하면 본 동작은 성공시키고 `console.error`와 `engine_decision_log`(`points` 엔진, 이벤트 `chapter_score_failed`)에 기록만 남긴다(같은 원천 id로 다시 보낼 수 있다). 캡슐·믹스는 DB 트랜잭션이 끝난 뒤라 본 동작을 되돌리는 방식은 구조상 어렵다. 자동 보정은 «적용 시점 이후만» 보는 기준(워터마크)이 필요해 후속 티켓 `20261020_1010`으로 둔다. (c) 시스템 드랍(드랍한 유저 없음)은 드랍 점수가 없다(유저 드랍 라우트에만 연결). 시스템 드랍을 줍는 것은 픽업 점수가 들어간다. 자기가 드랍한 것을 줍는 경우는 `isSelfPickup`(`lib/drop/self-pickup.ts`)으로 뺀다(지금 이 함수를 부르는 라우트가 없어 연결한다). 드랍과 픽업은 활동 종류가 달라 같은 `drop_id`로도 키가 겹치지 않는다. (d) **컬렉션 장착은 지금 이용 정지 중에도 되고 완성 점수가 생길 수 있어서**(`api/itembooks/[id]/slot/route.ts`에 정지 가드가 없고 DB 함수 179·222에도 정지 참조가 없다) 12.2절의 전제(정지 중에는 점수가 생기는 동작이 막힘)에 맞게 장착 라우트에 정지 확인을 더한다(3회). 정지된 드랍 주인이 다른 유저가 줍는 순간 받는 배지(`picked_up_by_user_count` 등)의 점수도 공용 함수에서 정지 여부를 확인해 뺀다(2a). (e) 아이템 배지를 받는 것은 12.2절 «배지 받기»(액티비티·체크인만 말함)에서 뺐다. 어드민 시뮬레이터(`admin_simulate`, `admin_test`)와 `dryRun`은 점수에서 뺀다. (f) 믹스 성공 로그 id를 돌려주는 새 DB 함수 `record_combine_success_with_id`(가칭) 하나가 필요하다. 옛 `record_combine_success`의 서명은 바꾸지 않고 새 이름으로 더하며, 3회 전에 SQL 승인과 롤백 실측을 따로 받는다. (g) 기존 유저(옛 퀘스트 완료자)의 챕터 시작 정책은 5-6(`20261019_1316`)에서 다룬다. 공용 DB의 유저 8명 가운데 새 퀘스트를 마친 유저는 0명이다.

## 상세 요구사항

### 서비스/코드베이스 관점

- **점수 연결 함수**: 활동 종류, 원천 id, 점수, 발생 날짜(KST 날짜, 221의 `p_occurred_on`)를 받아 `chapter_add_score`를 부르고 결과(`reached_chapters`)를 돌려준다. 점수 표의 값은 221의 설정 행(`chapter_score_rules`)이 갖고 있으므로 코드에 상수로 두지 않는다.
- **원천 id 정하기**(시작 때 아현이 표로 확정한다): 잼은 활동 id, 캡슐은 `capsule_opens.id`, 잠긴 열기는 개체 id(같은 개체를 두 번 열 수 없다는 전제를 확인), 배지 받기는 발급 기록 id 또는 (배지 id, 레벨/회차)로 만든 값, 컬렉션은 (컬렉션 id, 등급)의 완성 기록, 믹스는 성공 로그 id(RPC에 로그 id를 돌려주는 방법은 시작 때 정한다, 새 함수를 더해야 하면 옛 RPC 서명은 바꾸지 않는다), 미션은 `user_mission_completions.id`(5-1), 드랍·픽업은 `drop_id`(두 종류는 활동 종류가 달라 키가 겹치지 않는다).
- **제외 규칙**: 포인트·팔로우·챕터를 조건으로 하는 배지는 «배지 받기» 점수에서 뺀다(배지 조건을 읽어 판별, 5-4에서 방법을 넘겨받는다). 숨김 배지(`badges.is_hidden`)는 세지 않는다. 체크인 배지는 `record_checkin_earn`의 `is_first`일 때만 센다. 액티비티 배지는 받을 때, 레벨형은 레벨이 오를 때, 반복형은 다시 받을 때마다 센다. 자기가 드랍한 것을 주운 것은 `isSelfPickup`으로 걸러 세지 않는다. 시스템 드랍(드랍한 유저 없음)은 드랍 점수에서 제외한다. 이용 정지 중에는 점수가 생기는 동작 자체가 막히므로 호출부 확인만 한다(막히지 않은 지점이 있으면 그 지점에서 막는다).
- **주간 상한**: 모은 잼 주 300점 초과분 절반은 DB가 처리하므로 호출부는 발생 날짜만 정확히 넘긴다.
- 이 티켓에서는 챕터 오름 처리(소식, 챕터 배지 판정)를 하지 않는다. 연결 함수가 `reached_chapters`를 돌려주기만 하고 5-6이 이어받는다.

### UI/UX 관점 (해당 시)

- 없음.

## 구현 계획 (회차)

4회로 나눈다(1회 약 15개, 2a 약 15개, 2b 약 8개, 3회 약 15개, 시험·문서 포함). 경로는 `jam-web/src` 기준이고 줄 위치는 2026-10-20 조사 시점이라 시작 때 아현이 다시 확인한다. 유형은 모든 회차 `api`이고 파일이 5개를 넘으므로 `planOnlyWaiver`를 첫 호출부터 건다. 1·2a·2b는 DB 변경이 없다. 3회만 새 DB 함수 1개(믹스 성공 로그 id)가 필요하고 그 SQL은 카리나가 승인과 롤백 실측 뒤에 적용한다.

### 1회: 점수 연결 함수와 원천 id 유틸, 잼·캡슐·잠긴 열기·드랍·픽업

1. **신규 `lib/chapter/kinds.ts`**: 활동 종류 유니온(`jam_earned`, `capsule_open`, `locked_item_badge_open`, `badge_receive`, `collection_complete_common|rare|epic|mystic`, `mix_success`, `mission_complete`, `drop`, `pickup`)과 등급 → 컬렉션 활동 종류 변환. 점수 값은 DB 설정 행이 갖고 있으므로 코드에 상수로 두지 않는다.
2. **신규 `lib/chapter/score.ts`**: `awardChapterScore(supabase, { userId, kind, sourceId, amount = 1, occurredOn? })`가 `rpc('chapter_add_score')`를 부르고(`p_occurred_on`은 값이 없으면 생략) `{ ok: true, scoreAdded, currentChapter, reachedChapters } | { ok: false }`를 돌려준다. **절대 던지지 않는다.** RPC 오류·계약 밖 응답·예외는 `console.error`와 `logEngineDecision('points', 'chapter_score_failed', userId, { kind, sourceId, amount, occurredOn, error })`로 남기고 `{ ok: false }`를 돌려준다. `lib/badge-engine`의 `EngineDecisionEvent` 타입에 `chapter_score_failed`를 더한다. 수량이 1 미만이면 호출하지 않는다. 챕터 오름 처리(소식·챕터 배지)는 하지 않고 `reachedChapters`를 돌려주기만 한다(5-6).
3. **신규 `lib/chapter/source-id.ts`**: `deterministicSourceId(namespace, ...parts)`가 입력이 같으면 항상 같은 UUID를 돌려주는 순수 함수다(Node `crypto` 해시, 새 의존성 없음, 버전·변종 비트를 UUID 형식에 맞춘다). 컬렉션과 배지 받기가 쓴다(2a·3회). 시험에 고정 벡터(입력 → 기대 UUID)를 둔다.
4. **잼**: `lib/jam/settlement.ts` `settleActivities`에서 `items.push` 직후, 오래된 활동부터(`ordered`) 순서를 지켜 `awardChapterScore(…, kind: 'jam_earned', sourceId: item.activityId, amount: item.amount, occurredOn: item.earnedOn)`를 부른다. 수량이 0 이하면 부르지 않는다. 점수 실패가 정산 항목을 버리지 않게 한다(기존 catch 195~197줄이 점수 실패 때문에 항목을 빼지 않도록 순서를 지킨다).
5. **캡슐 열기**: `lib/capsule/open.ts` 확정 블록(217줄 이후)에서 `recordIssuedRewards` 실패와 무관하게 `kind: 'capsule_open'`, `sourceId: result.openId`로 부른다.
6. **잠긴 아이템 배지 열기**: `lib/inventory/lockedItemFill.ts` `openLockedItem` 확정 블록(177줄 이후)에서 `kind: 'locked_item_badge_open'`, `sourceId: itemId`로 부른다.
7. **드랍**: `app/api/drops/route.ts` POST 성공 뒤(408~415줄, 기존 `after()` 안)에서 `kind: 'drop'`, `sourceId: result.drop_id`로 부른다(이 라우트는 유저 드랍만 만든다).
8. **픽업**: `app/api/drops/[dropId]/pickup/route.ts` 성공 뒤(204~213줄, 기존 `after()` 안)에서 `isSelfPickup(drop.dropper_user_id, user.id)`이면 부르지 않고, 아니면 `kind: 'pickup'`, `sourceId: dropId`로 부른다(시스템 드랍 줍기는 점수 대상).
9. **시험**: 점수 함수(성공 결과 파싱, 계약 밖·RPC 오류·예외는 던지지 않고 `{ ok: false }`와 로그, 수량 1 미만은 호출 없음, `p_occurred_on` 생략), 결정적 id(고정 벡터, 입력 순서·구분자 구별), 지점마다 «성공하면 한 번, 같은 일을 두 번 보내도 같은 (kind, sourceId)»(잼은 활동 순서와 `ordered`), 점수 실패가 본 동작·응답을 바꾸지 않음, 자기 픽업 제외·시스템 드랍 줍기 포함·드랍 점수는 유저 드랍만. 기존 시험이 `rpc` 호출 목록을 고정하고 있으면 새 호출을 반영한다.
10. **문서**: `docs/service/prd/02_DATA_MODEL.md`(챕터 절: 점수 호출 지점과 원천 id 표), `docs/plan/jam2/service-redesign/현재 서비스 비교.md` 5.3절 «17 챕터» 행, 이 티켓의 원천 id 표 상태.

### 2a회: 배지 받기 공용 함수와 새 발급 지점

11. **신규 `lib/chapter/badgeReceive.ts`**: `awardBadgeReceiveScore(supabase, { userId, badge: { id, type, is_hidden, condition_json }, origin })`. `type`이 `activity`·`checkin`이 아니면 건너뛰고(아이템 배지 제외), 숨김 배지(`is_hidden === true`)와 `condition_json`의 키가 제외 키 집합(`follower_count`·`following_count`·`chapter_reached`, 포인트 키 0개, 한 곳에 상수로 두고 나중에 포인트 키를 더하면 여기만 고친다)과 겹치는 배지를 뺀다. 이용 정지 중인 유저(`getActiveSuspension`)는 뺀다(정지된 드랍 주인이 받는 배지). 원천 id는 `deterministicSourceId('badge_receive', userId, badge.id)`다. `origin`이 카탈로그 재평가 배치(`triggeredBy 'catalog_reevaluation'`)·어드민 시뮬레이터(`admin_simulate`, `admin_test`)·`dryRun`이면 부르지 않는다(호출부에서 막는 쪽이 단순하다).
12. **새 발급 지점 연결**: 엔진 새 발급(`lib/badge-engine/index.ts` 1485줄 insert 뒤 부수효과 1500~1523줄, 레벨형은 레벨마다), `usageBadges.ts` `issueQualifyingBadges`(insert 237~239줄 뒤 250~272줄), 미션 보상(`lib/missions/rewards.ts` 118~147줄), 컬렉션 보상(`lib/itembook/checker.ts` `issueItemBookRewardBadges` 335~353줄, select에 `is_hidden`·`condition_json` 확장), 온보딩 완료 배지(`lib/onboarding-quest/completion.ts` 106~109줄, select 확장), 체크인 첫 획득(`lib/strava/sync.ts` 1042줄 `isFirstEarn`일 때만). 23505·이미 보유는 점수 대상이 아니다. select 확장이 필요한 두 파일은 기존 시험의 조회 모양을 함께 맞춘다.
13. **시험**: 제외 규칙마다 점수 없음(숨김, 아이템 배지, 팔로우·챕터 조건, 정지 유저, 재평가 배치, 시뮬레이터·`dryRun`), 같은 배지를 두 번 받아도(초기화 뒤 재획득 포함) 같은 (kind, sourceId)라 한 번, 레벨형 여러 레벨, 체크인은 처음 받을 때만, 실패가 발급을 막지 않음. 문서는 1회와 같은 문서를 이어서 갱신한다.

### 2b회: 반복형 재획득 회차

14. 반복형(`lib/badge-engine/index.ts` 1408~1428줄 `increment` 경로, `incrementRepeatEarnCount` 1659~1681줄)은 새 회차마다 10점이다. 원천 id는 `deterministicSourceId('badge_receive', userId, badge.id, stravaActivityId)`(회차 구분 값은 `earn_history[].strava_activity_id`)이고, 첫 획득 +10은 12번의 (유저, 배지) id다. ### 3회: 컬렉션 완성, 믹스 성공, 미션 완료, 종합

18. **컬렉션**: `lib/chapter/collection.ts`(신규)가 (유저, 컬렉션, 등급) 결정적 id로 `collection_complete_<등급>`을 부른다. `app/api/itembooks/[id]/slot/route.ts`는 등급형 RPC의 `completed_tier`를 쓰고, 옛 컬렉션(`tier_mode` 꺼짐)은 장착 전후로 `user_item_book_completions` 존재를 읽어 «이번에 새로 완성했는가»를 가려 등급 `common`으로 부른다(이미 완성한 유저의 재장착은 소급 가산하지 않는다). `lib/itembook/checker.ts`(동기화 보정)는 `completedIds`가 이미 새로 완성한 것만 담으므로 같은 함수를 부른다. **슬롯 라우트에 `assertNotSuspended`를 더한다**(403, `d.suspension`에 문구 추가, 5-1·5-3 방식).
19. **미션**: `lib/missions/checker.ts`가 `completedMissions.push`(267~268줄) 직후 `grantMissionRewards`(275줄) **앞**에서 `kind: 'mission_complete'`, `sourceId: completionId`로 부른다.
20. **종합 시험**: 8종 활동이 각각 한 번만 세어지는지(같은 일 두 번 보내기), 제외 규칙 종합(포인트·팔로우·챕터 조건 배지, 숨김 배지, 자기 드랍 줍기, 시스템 드랍, 체크인 두 번째 이후, 재평가 배치), 모은 잼 주 300점 초과분 절반은 DB가 처리하므로 날짜(`earnedOn`)가 정확히 넘어가는지, 점수 실패가 본 동작을 막지 않는지. 문서(운영 로직 12.2절의 «한계와 결정» 기록, `02_DATA_MODEL.md`, 비교표 5.3절)와 이 티켓의 원천 id 표 최종본.

**하지 않는 것**: 챕터 오름 처리(소식, 챕터 배지, 연출)와 `chapter_start` 호출(5-6), 프로필·화면(5-7), 챕터 이름 표 어드민(5-8), 점수 연결 자동 보정(후속 티켓 `20261020_1010`), 아이템 배지 수령 점수, 드랍 점수 남용 방지.

## 완료 조건

### 구현 범위 (게이트 판정 대상)

- 1회: 점수 연결 함수가 던지지 않고 실패를 기록하며, 모은 잼·캡슐 열기·잠긴 아이템 배지 열기·드랍·픽업이 일어날 때 12.2절의 점수가 쌓이고 같은 일을 다시 보내도 한 번만 센다(시험으로 확인). 자기 드랍 줍기는 세지 않고 시스템 드랍 줍기는 센다. 점수 실패가 본 동작과 응답을 바꾸지 않는다.
- 2a·2b회: «배지 받기»가 사용자 결정 2·3대로 센다(액티비티 배지는 받을 때, 레벨형은 레벨마다, 체크인은 처음 받을 때만, 반복형은 회차마다). 숨김 배지·아이템 배지·포인트·팔로우·챕터 조건 배지·재평가 배치·시뮬레이터·`dryRun`·이용 정지 유저는 점수에 들어가지 않는다.
- 3회: 컬렉션 완성(등급형 아닌 컬렉션은 Common 100, 재장착 소급 가산 없음), 믹스 성공, 미션 완료가 센다. 컬렉션 장착이 이용 정지 중에는 막힌다. 모은 잼은 주 300점을 넘는 분이 절반으로 세어진다(DB 처리, 날짜가 정확히 넘어가는지 시험). 새 마이그레이션은 옛 객체의 서명·권한을 바꾸지 않고 되돌림 SQL을 싣는다.
