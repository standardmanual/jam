# [Service] JAM2 챕터 서버 ②: 챕터 1 시작, 오름 처리, 소식, 읽기

## 핵심 요약

- 요구사항: 운영 로직 12.1~12.3절을 서버에 맞춘다. (1) 퀘스트를 마치면 챕터 1을 받는다(`chapter_start` 연결, 2026-10-19 사용자 결정으로 이 티켓에서 연결). (2) 챕터가 오르면 소식을 보내고, 그 챕터를 조건으로 하는 챕터 배지를 바로 판정해 받게 한다(지금은 동기화 끝에서만 판정돼 라우트에서 오르면 다음 동기화까지 안 열린다). 한 번에 여러 챕터를 넘으면 넘은 챕터를 모두 오른다. (3) 프로필이 쓸 읽기를 만든다. 내 챕터·이름·다음 챕터까지의 게이지(비율)와, 다른 유저가 보는 트라이브·챕터·이름. 점수의 숫자는 내려주지 않는다(12.3절). (4) 챕터 이름 표(`chapter_names`)를 읽는 함수를 만든다. 이름이 비어 있으면 null이다.
- 구현 계획: 시작 때 사용자 결정 3건을 질문하고 파일 단위 계획을 옮겨 쓴다. DB는 알림 종류 추가만 한다(새 enum 값은 같은 트랜잭션에서 쓰지 못해 마이그레이션을 따로 나눈다). SQL은 사용자 승인과 롤백 실측 뒤 카리나가 실행한다.
- 관련 파일(2026-10-19 조사, 시작 때 아현이 줄 위치를 다시 확인한다): 챕터 시작 연결 `jam-web/src/lib/onboarding-quest/completion.ts`(167줄 근처, 호출처 `lib/strava/sync.ts:1535`·`app/api/onboarding-quest/step/route.ts:101`·`skip/route.ts:84`), 오름 직후 판정 `lib/badge-engine/jamActionRoute.ts:21`(`runJamActionEvaluation`)·`jamActionProgressTriggers.ts:36`(`JAM_SYNC_TRIGGERS`, 라우트용 트리거 목록에 `chapter_reached` 없음)·`sync.ts:1258`, 챕터 읽기 `lib/badge-engine/jamActionJamMetrics.ts:123`, 소식 `lib/notifications/index.ts:124`(`createNotification`)·`lib/inventory/slotAlert.ts:66`(최신 예)·`lib/notifications/types.ts:152`·`message.ts:607`·`href.ts:136`·`types/database.ts:1860`, 알림 종류 추가 본보기 `237_inventory_slot_alert.sql:23`, 챕터 이름 표 `221_chapters.sql:51`, 캡슐 필요량 `234`의 `capsule_next_required`(앱 작업 없음).

## 5-5에서 넘어온 항목 (2026-10-20, 5-5 시작 전 조사)

- **`chapter_start` 호출 위치**: 앱 코드에서 `chapter_start`를 부르는 곳은 아직 0건이다. 호출 지점은 `jam-web/src/lib/onboarding-quest/completion.ts` 167줄 `recordOnboardingQuestCompletion`이고 호출처는 `lib/strava/sync.ts` 1535줄, `app/api/onboarding-quest/step/route.ts` 101줄, `skip/route.ts` 84줄이다.
- **지금의 완료 조건**: 활동 1건과 연출 7단계 또는 건너뛰기만 본다. 캡슐·잠긴 열기(실제 2·3단계)는 보지 않으므로 그대로 `chapter_start`를 붙이면 첫 동기화 직후 챕터 1이 되고, 캡슐·잠긴 열기 점수는 챕터 1 이후에 쌓인다. 퀘스트 전에 쌓이는 점수는 사실상 첫 동기화 안의 점수(예상 100~600점)다. 사용자 결정(2026-10-20): 퀘스트 전 점수는 쌓아 두었다가 챕터 1 시작 때 한꺼번에 반영한다.
- **기존 유저(옛 퀘스트 완료자)의 챕터 시작 정책**: 옛 퀘스트를 이미 마친 유저는 `completed_at`이 있어 `completion.ts`가 일찍 `null`을 반환하므로 `chapter_start`가 불리지 않는다. 점수만 쌓이고 챕터는 `NULL`로 남는다(221도 «기존 유저 백필 없음»). 이 유저들의 챕터 시작 정책을 5-6에서 정한다. 공용 DB 현황(2026-10-20): 유저 8명, 새 퀘스트를 마친 유저 0명이다.
- **오름 결과**: 5-5의 `awardChapterScore`(`lib/chapter/score.ts`)는 `reachedChapters`를 돌려주기만 하고 오름 처리(소식, 챕터 배지, 연출)는 하지 않는다. 5-6이 이 결과를 이어받아 처리한다.

## 사용자 결정과 적용 기록 (2026-10-20)

시작 전 질문 4건에 모두 추천대로 답했다.

1. **오름 소식**: 새 알림 종류 `chapter_up`을 더한다(마이그레이션 255, 별도 파일). 챕터 2 이상으로 오를 때만 보낸다. 한 번에 여러 챕터를 넘으면 가장 높은 챕터로 한 건만 보내고, 넘은 챕터의 챕터 배지는 모두 받는다. 챕터 1 시작은 퀘스트 완료 보상이 이미 알리므로 소식을 보내지 않는다.
2. **챕터 배지 판정 시점**: 오름 처리 안에서 바로 판정한다. 동기화 안에서 난 오름은 동기화 끝 판정(`JAM_SYNC_TRIGGERS`)이 이미 읽으므로 이중으로 판정하지 않게 아현이 설계한다. 지금 공용 DB에는 `chapter_reached`를 조건으로 하는 배지가 0개라 컨텐츠가 생길 때부터 나온다.
3. **이름이 비었을 때**: 서버는 null을 돌려주고 화면은 «챕터 N»만 보인다. 임시 이름 시드는 넣지 않는다.
4. **챕터 1 시작 재시도**: 퀘스트 완료 처리가 불릴 때마다 완료된 유저의 챕터가 비어 있으면 `chapter_start`를 다시 부른다(`chapter_start`가 멱등이라 안전하다). 옛 퀘스트 완료자는 다음 동기화 때 챕터 1을 받으므로 기존 유저 정책은 따로 두지 않는다(운영 로직 17.3절: 정식 오픈 전에 모든 테스트 유저를 지운다. 지금 옛 퀘스트 완료자는 0명).

**DB 적용(2026-10-20, 카리나, 사용자 승인 «승인, 지금 적용»)**: 마이그레이션 255 `255_notification_type_chapter_up.sql`로 `notification_type`에 값 `chapter_up`을 더했다. 롤백 실측(`DO` 블록에서 값을 더하고 `RAISE EXCEPTION`으로 되돌림): 적용 전 0개, 더한 뒤 1개, 다시 실행해도 1개(`IF NOT EXISTS`), 롤백 뒤 0개로 복구된 것을 확인했다. 적용 뒤 읽기 전용 확인: `pg_enum`에 `chapter_up` 1행. 생성 타입(`src/types/database.generated.ts`)의 `notification_type` 유니온과 상수 목록에 `chapter_up`을 손으로 더했고 `npm run typecheck`가 통과했다. 되돌림은 enum 값을 지울 수 없어 앱이 값을 만들지 않게 하고 값을 쓰지 않은 채로 두는 방식이다(SQL 파일 끝에 적음).

**구현 때 지킬 점(조사에서 나온 것)**: `chapter_start` 호출은 `completed_at` 갱신 직후(보상 지급 판정 앞)에 두어 건너뛴 유저도 챕터 1을 받게 한다. 오름 처리는 점수 함수와 `jamActionRoute`·`sync.ts` 사이의 순환 import를 만들지 않는다. 챕터 1 시작이 돌려준 `reached_chapters`가 2 이상을 포함하면(쌓인 점수로 한 번에 오른 경우) 그 오름도 같은 처리 경로를 탄다.

## 시작 전 조사 결과 (2026-10-20, 코드 읽기와 공용 DB 읽기 전용 확인)

- **`chapter_start`(마이그레이션 221)**: 챕터가 비어 있을 때만 동작한다. 이미 챕터가 있으면 아무것도 하지 않고 `{ score_added: 0, current_chapter: 지금 챕터, reached_chapters: [] }`를 돌려주므로 중복 호출은 DB가 막는다. 챕터 1은 점수와 상관없이 시작하고, 쌓인 점수로 오를 수 있는 챕터까지 한 번에 올리며, 오른 챕터마다 `chapter_ups`에 한 줄을 남긴다. 챕터 1 정의가 없으면 오류(`check_violation`)다.
- **퀘스트 완료 처리(`lib/onboarding-quest/completion.ts` `recordOnboardingQuestCompletion`)**: 호출처는 `lib/strava/sync.ts` 1540줄, `app/api/onboarding-quest/step/route.ts` 101줄, `skip/route.ts` 84줄이다. 흐름은 ① 행 없음 → 끝 ② 7단계를 안 마쳤고 건너뛰지도 않음 → 끝 ③ 완료 시각은 있는데 보상이 안 나간 비건너뜀 유저 → 보상만 다시 시도 ④ 완료 시각이 있음 → 끝 ⑤ 걸러지지 않은 활동 1건 확인 ⑥ `completed_at` 조건부 갱신(이번 호출에서 바뀐 경우에만 보상 지급, 건너뛴 유저는 보상 없음)이다. 건너뛴 유저도 ⑥에서 완료 시각이 기록되므로 `chapter_start`는 ⑥ 직후에 부르면 건너뛴 유저도 챕터 1을 받는다(운영 로직 2.2절 «건너뛰기는 연출 단계만 건너뛴다»).
- **재시도 문제**: `chapter_start`가 일시 오류로 실패하면 `completed_at`이 이미 있어 이 함수는 다음 호출에서 ④에서 끝나므로 다시 불리지 않는다. 보상 지급만 ③에서 다시 시도한다. 그래서 챕터 1을 다시 시도하는 경로가 따로 필요하다(`chapter_start`가 멱등이라 여러 번 불러도 안전하다).
- **퀘스트 행과 공용 DB 현황**: 퀘스트 행은 계정 정보 단계(`app/api/onboarding/complete/route.ts`)에서 만든다. 공용 DB: 유저 8명, 트라이브를 고른 유저 0명, 퀘스트 행 0건, 챕터 행·오름 기록·점수 기록 0건, 챕터 정의 10행(챕터 2부터 1,000·2,300·3,800·5,700·8,500·11,500·15,000·19,000·23,000), 챕터 이름 0행, `condition_json`에 `chapter_reached` 키를 가진 배지 0개다. 알림 종류 enum에 챕터 관련 값은 없다(31개 값).
- **기존 유저**: 운영 로직 17.3절과 온보딩 설계 5절은 «지금 가입 유저 가운데 트라이브를 고른 유저가 없고, 정식 오픈 전에 사용자가 모든 테스트 유저를 지운다»고 정했다. 옛 퀘스트 완료자는 지금 0명이다.
- **캡슐과 챕터 1의 관계**: 캡슐 행은 홈 진입 때 처음 만들어지고(`app/(main)/page.tsx` 56줄 주석), 그때 챕터가 없으면 퀘스트 전 값 5, 챕터가 있으면 챕터별 값(1: 90 … 10: 220)을 쓴다(`capsule_next_required`, 마이그레이션 234). 챕터 1은 지금 완료 조건(활동 1건과 연출 7단계 또는 건너뛰기)으로 첫 동기화 직후 시작되므로 캡슐 열기와 잠긴 열기는 챕터 1 뒤에 일어난다. 퀘스트는 홈 카드에서 진행되므로 캡슐 행은 챕터 1 전에 만들어진다고 보지만 모든 경로를 확인하지는 않았다.
- **챕터 읽기 현황**: 챕터 번호를 읽는 앱 코드는 `lib/badge-engine/jamActionJamMetrics.ts`(`chapter_reached`) 한 곳이다. `user_chapters`는 본인 행만 읽는 정책이고, `chapter_definitions`·`chapter_names`는 로그인 유저 모두가 읽을 수 있다. `chapter_names`는 (트라이브, 챕터)가 키이고 `name`이 비어도 된다.
- **오름 직후 판정의 구조 제약**: `chapter_reached`는 이미 동기화 끝 판정 목록(`JAM_SYNC_TRIGGERS`)에 있다. 라우트용 래퍼 `runJamActionEvaluation`(`jamActionRoute.ts`)은 `notifyActivityBadgesEarned`를 `sync.ts`에서 가져오므로, 점수 함수(`lib/chapter/score.ts`)가 오름 처리를 직접 가져오면 `sync.ts → 잼 정산 → score.ts → 오름 처리 → jamActionRoute → sync.ts` 순환이 생길 수 있다. 동기화 안에서 난 오름은 동기화 끝 판정이 이미 읽으므로 이중 판정을 피하는 설계가 필요하다(구현 때 아현이 정한다).
- **알림 종류 추가의 앱 수정 위치**: `types/database.ts`, `lib/notifications/types.ts`, `message.ts`, `href.ts`, `app/(main)/notifications/NotificationsClient.tsx`(최신 본보기 `mission_participation_cancelled`, 마이그레이션은 `237`·`251` 방식)다. 소식 생성은 `createNotification`이 던지지 않고 `null`을 돌려준다.

## 배경 / 문제 정의

챕터 점수가 쌓여도(5-5) 챕터가 오르는 순간에 할 일이 없다. 오름을 알리는 소식 종류가 없고, 챕터 배지는 동기화 끝에서만 판정된다. `chapter_start`는 지금 퀘스트 완료 처리(`completion.ts`)가 부르지 않아 챕터 1이 시작되지 않는다. 퀘스트 완료 처리는 활동 1건과 연출 7단계 또는 건너뛰기만 보고, 운영 로직 2.2절의 실제 2·3단계(캡슐·잠긴 아이템 배지 열기)를 보는 코드는 없다. 이 완료 조건은 묶음 6이 퀘스트를 새로 만들 때 바꾼다.
챕터 이름 표는 0행이고 이름 50개는 별도 주제라서 이름이 없는 상태로 동작해야 한다.

## 시작 전에 사용자에게 확인할 것 (주요 결정, 질문창)

1. **챕터 오름 소식 종류**: 새 알림 종류(`chapter_up`)를 더한다(추천, 문구·이동 위치가 챕터 전용이라 다른 소식과 섞이지 않는다). 대안은 기존 종류를 재사용하고 payload로 구분하는 것이다(마이그레이션이 없지만 문구 분기가 복잡해진다).
2. **오름 직후 챕터 배지 판정 시점**: 오름 처리 안에서 바로 판정한다(추천, 라우트에서 오른 즉시 배지가 나온다). 대안은 다음 동기화 때까지 기다리는 지금 방식이다(이미 동작하지만 캡슐을 연 직후 챕터 배지가 안 보인다).
3. **이름이 비었을 때의 표시**: 이름 없이 «챕터 N»만 보인다(추천). 대안은 임시 이름을 시드로 넣는 것이다(이름 50개 확정 때 지워야 한다).

## 상세 요구사항

### 서비스/코드베이스 관점

- **챕터 1 시작**: 퀘스트 완료 처리 함수 한 곳에서 `chapter_start`를 부른다(결과가 `reached_chapters`를 돌려주므로 오름 처리와 같은 경로를 탄다). 이미 완료한 유저는 다시 완료되지 않으므로 중복 호출은 DB가 막는지 확인한다. 건너뛴 유저도 챕터 1을 받는지 12.1·2장을 확인해 따른다.
- **오름 처리 함수**: 점수 연결(5-5)이 돌려준 `reached_chapters`를 받아 챕터마다 (a) 소식을 만들고(`createNotification`, 이미 같은 오름 소식을 보냈으면 건너뜀), (b) `runJamActionEvaluation`으로 챕터 조건 배지를 판정해 받게 하고 그 배지 소식을 기존 방식으로 보낸다. 챕터 배지가 다시 챕터 점수를 올리는 고리는 5-5의 제외 규칙이 막는다.

- **이용 정지**: 정지 중에는 점수가 생기는 동작이 막히므로 오름도 일어나지 않는다. 이 티켓에서는 확인만 한다.
- 알림 종류 추가는 마이그레이션 → `types/database.ts` → `lib/notifications/types.ts` → `message.ts` → `href.ts` 순서다. 문구는 UX Writing 가이드를 따른다.
