# [Service] JAM2 챕터 서버 ②: 챕터 1 시작, 오름 처리, 소식, 읽기

## 핵심 요약

- 요구사항: 운영 로직 12.1~12.3절을 서버에 맞춘다. (1) 퀘스트를 마치면 챕터 1을 받는다(`chapter_start` 연결, 2026-10-19 사용자 결정으로 이 티켓에서 연결). (2) 챕터가 오르면 소식을 보내고, 그 챕터를 조건으로 하는 챕터 배지를 바로 판정해 받게 한다(지금은 동기화 끝에서만 판정돼 라우트에서 오르면 다음 동기화까지 안 열린다). 한 번에 여러 챕터를 넘으면 넘은 챕터를 모두 오른다. (3) 프로필이 쓸 읽기를 만든다. 내 챕터·이름·다음 챕터까지의 게이지(비율)와, 다른 유저가 보는 트라이브·챕터·이름. 점수의 숫자는 내려주지 않는다(12.3절). (4) 챕터 이름 표(`chapter_names`)를 읽는 함수를 만든다. 이름이 비어 있으면 null이다.
- 구현 계획: 시작 때 사용자 결정 3건을 질문하고 파일 단위 계획을 옮겨 쓴다. DB는 알림 종류 추가만 한다(새 enum 값은 같은 트랜잭션에서 쓰지 못해 마이그레이션을 따로 나눈다). SQL은 사용자 승인과 롤백 실측 뒤 카리나가 실행한다.
- 관련 파일(2026-10-19 조사, 시작 때 아현이 줄 위치를 다시 확인한다): 챕터 시작 연결 `jam-web/src/lib/onboarding-quest/completion.ts`(167줄 근처, 호출처 `lib/strava/sync.ts:1535`·`app/api/onboarding-quest/step/route.ts:101`·`skip/route.ts:84`), 오름 직후 판정 `lib/badge-engine/jamActionRoute.ts:21`(`runJamActionEvaluation`)·`jamActionProgressTriggers.ts:36`(`JAM_SYNC_TRIGGERS`, 라우트용 트리거 목록에 `chapter_reached` 없음)·`sync.ts:1258`, 챕터 읽기 `lib/badge-engine/jamActionJamMetrics.ts:123`, 소식 `lib/notifications/index.ts:124`(`createNotification`)·`lib/inventory/slotAlert.ts:66`(최신 예)·`lib/notifications/types.ts:152`·`message.ts:607`·`href.ts:136`·`types/database.ts:1860`, 알림 종류 추가 본보기 `237_inventory_slot_alert.sql:23`, 챕터 이름 표 `221_chapters.sql:51`, 캡슐 필요량 `234`의 `capsule_next_required`(앱 작업 없음).

## 배경 / 문제 정의

챕터 점수가 쌓여도(5-5) 챕터가 오르는 순간에 할 일이 없다. 오름을 알리는 소식 종류가 없고, 챕터 배지는 동기화 끝에서만 판정된다. `chapter_start`는 지금 퀘스트 완료 처리(`completion.ts`)가 부르지 않아 챕터 1이 시작되지 않는다. 퀘스트 완료 처리는 활동 1건과 연출 7단계 또는 건너뛰기만 보고, 운영 로직 2.2절의 실제 2·3단계(캡슐·잠긴 아이템 배지 열기)를 보는 코드는 없다. 이 완료 조건은 묶음 6이 퀘스트를 새로 만들 때 바꾼다.
챕터 이름 표는 0행이고 이름 50개는 별도 주제라서 이름이 없는 상태로 동작해야 한다.

## 시작 전에 사용자에게 확인할 것 (주요 결정, 질문창)

1. **챕터 오름 소식 종류**: 새 알림 종류(`chapter_up`)를 더한다(추천, 문구·이동 위치가 챕터 전용이라 다른 소식과 섞이지 않는다). 대안은 기존 종류를 재사용하고 payload로 구분하는 것이다(마이그레이션이 없지만 문구 분기가 복잡해진다).
2. **오름 직후 챕터 배지 판정 시점**: 오름 처리 안에서 바로 판정한다(추천, 라우트에서 오른 즉시 배지가 나온다). 대안은 다음 동기화 때까지 기다리는 지금 방식이다(이미 동작하지만 캡슐을 연 직후 챕터 배지가 안 보인다).
3. **이름이 비었을 때의 표시**: 이름 없이 «챕터 N»만 보인다(추천). 대안은 임시 이름을 시드로 넣는 것이다(이름 50개 확정 때 지워야 한다).

## 상세 요구사항

### 서비스/코드베이스 관점

- **챕터 1 시작**: 퀘스트 완료 처리 함수 한 곳에서 `chapter_start`를 부른다(결과가 `reached_chapters`를 돌려주므로 오름 처리와 같은 경로를 탄다). 이미 완료한 유저는 다시 완료되지 않으므로 중복 호출은 DB가 막는지 확인한다. 건너뛴 유저도 챕터 1을 받는지 12.1·2장을 확인해 따른다.
- **오름 처리 함수**: 점수 연결(5-5)이 돌려준 `reached_chapters`를 받아 챕터마다 (a) 소식을 만들고(`createNotification`, 이미 같은 오름 소식을 보냈으면 건너뜀), (b) `runJamActionEvaluation`으로 챕터 조건 배지를 판정해 받게 하고 그 배지 소식을 기존 방식으로 보낸다. 챕터 배지가 다시 챕터 점수를 올리는 고리는 5-5의 제외 규칙이 막는다.
- **읽기**: 내 챕터 번호, 이름, 다음 챕터까지의 진행 비율(현재 챕터 시작 기준 점수 대비 다음 챕터 기준 점수)을 돌려주는 서버 함수와, 다른 유저 프로필용(트라이브, 챕터 번호, 이름만) 함수를 만든다. 점수 숫자는 응답에 싣지 않는다. 챕터가 없는 유저(퀘스트 전)는 챕터 0 또는 null로 구분해 화면이 «챕터 없음»을 보여 주게 한다.
- **이름 조회**: `chapter_names`에서 (트라이브, 챕터)로 읽는다. 트라이브가 바뀌면 이름만 새 트라이브의 것으로 바뀌며 챕터 숫자는 그대로다. 행이 없으면 null이다.
- **이용 정지**: 정지 중에는 점수가 생기는 동작이 막히므로 오름도 일어나지 않는다. 이 티켓에서는 확인만 한다.
- 알림 종류 추가는 마이그레이션 → `types/database.ts` → `lib/notifications/types.ts` → `message.ts` → `href.ts` 순서다. 문구는 UX Writing 가이드를 따른다.

### UI/UX 관점 (해당 시)

- 없음(프로필 표시와 오름 연출은 5-7).

## 구현 계획 (회차)

1~2회로 돌린다(아현 판단, 예상 파일 약 15개). 1회는 오름 처리·소식·챕터 1 시작, 2회는 읽기와 시험이다.

1. 마이그레이션(번호는 시작 때 확인): 알림 종류 추가(별도 파일). 되돌림 SQL을 싣는다(enum 값은 지울 수 없으므로 되돌림 대신 «쓰지 않음» 절차를 적는다).
2. `lib/chapter/`(5-5에서 만든 곳)에 오름 처리 함수, 읽기 함수.
3. 퀘스트 완료 처리에 `chapter_start` 연결.
4. 알림 종류 추가에 따른 앱 5곳 수정.
5. 시험: 점수로 챕터가 오르면 소식이 한 번만 가고 챕터 배지가 바로 판정됨, 한 번에 여러 챕터를 넘음, 퀘스트 완료로 챕터 1이 시작됨, 읽기 응답에 점수 숫자가 없음, 이름이 없을 때 null.
6. 문서: 챕터 PRD(없으면 `docs/service/prd/` 아래에 새로 만든다), `docs/service/prd/02_DATA_MODEL.md`, 엔진 문서의 `chapter_reached` 판정 시점 서술.

## 완료 조건

### 구현 범위 (게이트 판정 대상)

- 퀘스트를 마치면 챕터 1이 시작되고, 그때까지 쌓인 점수로 오를 챕터까지 오른다.
- 챕터가 오르면 소식이 한 번 가고, 그 챕터를 조건으로 하는 챕터 배지가 라우트 안에서 바로 판정되어 받아진다. 한 번에 여러 챕터를 넘으면 모두 처리된다.
- 내 챕터·이름·다음 챕터까지의 비율과, 다른 유저에게 보이는 트라이브·챕터·이름을 읽는 서버 함수가 있고 점수 숫자를 응답에 싣지 않는다. 이름 표가 비어 있어도 동작한다.
- 알림 종류 추가가 마이그레이션과 앱 5곳에 일관되게 반영된다. 마이그레이션이 옛 객체의 서명·권한을 바꾸지 않는다.

### 후속 범위 (담당: 카리나, 시점: 사용자 승인 뒤)

- 시작 때 결정 1~3번을 이 티켓 「사용자 결정」 절에 기록한다. SQL 실행은 승인과 롤백 실측 뒤에 한다.
- 챕터 이름 50개를 짓는 별도 주제는 이 묶음의 범위 밖이다.
