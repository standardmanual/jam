# [UI] JAM2 유저 화면: 프로필 챕터, 오름 연출, 미션 화면, 포인트 화면

## 핵심 요약

- 요구사항: 서버가 선 뒤 유저 화면을 한 번에 만든다. (1) 내 프로필에 챕터, 이름, 다음 챕터까지의 게이지(점수 숫자 없이 «다음 챕터까지»)를 보이고, 다른 유저의 프로필에는 트라이브·챕터·이름만 보인다. (2) 챕터가 오르면 축하 연출과 소식을 보인다. (3) 미션 화면: 대상이 아닌 트라이브 미션은 목록에 안 보이고, 상세에 참가·진행·순위, 완료 보상을 «받기»로 나중에 받는 자리, 밤 조건 미션의 안전 안내, 받기 전 숨김 배지의 이름 가림을 둔다. 참가 취소 소식을 소식 화면에서 읽을 수 있다. (4) 포인트 화면은 가진 포인트와 받은 내역을 보이고 «회수» 용어를 쓰지 않는다.
- 구현 계획: 채원 사전 판정(재사용할 컴포넌트, 새 UI의 MODULAR 승격 여부)을 받고 시작 때 사용자 결정을 질문창으로 묻는다. 완성된 새 디자인(JAM 2.0 디자인 시스템 문서)을 구현한다. 파일 단위 계획은 아현이 쓴다.
- 관련 파일(2026-10-19 조사, 시작 때 아현이 줄 위치를 다시 확인한다): 내 프로필 `jam-web/src/app/(main)/profile/ProfileClient.tsx`(헤더 584~660줄, 캡슐 위젯 664줄, 내 프로필 전용 prop 패턴 `capsuleInitial` 66~72·408줄), 타인 프로필 서버 페이지 `app/(main)/[username]/page.tsx`(47~48줄, `users`에서 `id, username, display_name, avatar_url`만 읽음), 미션 `app/(main)/missions/page.tsx`·`app/(main)/missions/[id]/page.tsx`(40줄), 포인트 화면(경로는 시작 때 찾는다), 소식 문구 `lib/notifications/message.ts`·`href.ts`, 서버 읽기 함수는 5-1~5-6의 완료 기록에서 받는다.

## 5-1에서 넘어온 항목 (2026-10-19)

- 오늘카드 랭킹 보드(`mission_participants` 모드)가 이용 정지 유저와 트라이브 제한을 처리하지 않는다. 별도 티켓 `20261019_1400`(P2)에서 고치고, 랭킹 모드를 만들기 전에 끝낸다. 이 화면 작업과 함께 해도 된다.

## 5-3에서 넘어온 항목 (2026-10-19, 5-3 3회 게이트 참고 사항)

- **잠긴 아이템 배지 보상 카드**(`jam-web/src/app/(main)/missions/[id]/page.tsx` 44~57줄 근처): 미션 상세가 보상 배지의 이름·그림·id를 `rewardBadges`와 `mission.reward_badge_ids`로 항상 내린다. 보상이 «잠김으로 만든»(`badges.always_locked`) 아이템 배지여도 걸러지지 않아 운영 로직 7.3절(열기 전에는 이름·그림을 보이지 않음)과 어긋난다. 5-3 이전부터 있던 동작이고 공용 DB에 잠김 아이템 배지가 0개(2026-10-19)라 지금 새는 곳은 없지만 어드민이 설정하면 바로 열린다. 보상 카드를 어떻게 보일지(이름 대신 등급만, «잠긴 보상» 표기 등)를 시작 때 정한다. 이 값과 대조하면 5-3의 `pendingRewards` 가림(잠긴 보상은 등급과 `locked`만)도 무력해진다.
- **받지 않은 보상 읽기 실패 구분**(같은 파일 64~65줄 근처): `mission_item_rewards` 조회가 실패하면 `pendingRewards`가 빈 배열로 내려가고 `console.error`만 남는다. 화면에서 «받을 보상 없음»과 구분되지 않으므로, 읽기 실패를 따로 알릴지 정한다(시험이 현재 동작을 고정하고 있어 바꾸면 시험도 바꾼다).
- **기록 읽기 함수의 잠긴 보상 `badgeId`**(`jam-web/src/lib/missions/records.ts` 42~52줄): `loadMissionRecords`의 보상 행은 잠긴 보상도 `badgeId`를 그대로 담는다. 유저 화면으로 내릴 때 소비하는 쪽이 빼야 한다(지금은 주석과 문서로만 지킨다).
- **받기 화면이 쓸 것**: 받기 API는 `POST /api/missions/[id]/claim`(5-3 1회)이고 `no_pending` 409·`insufficient_slots` 409(`free`·`needed`)·`user_suspended` 403·`inventory_not_found` 404로 답한다. 상세 페이지는 `pendingRewards`(열린 보상 `{locked:false,id,name,image_url,rarity}`, 잠긴 보상 `{locked:true,rarity}`)를 `MissionDetailClient`의 선택 prop으로 내린다. 잠긴 보상의 `unlock_required`는 싣지 않았다(필요하면 5-7에서 더한다, 7.3절이 허용하는 양).

## 5-4에서 넘어온 항목 (2026-10-20, 5-4 2회 게이트 참고 사항)

- **믹스 결과 화면과 «포인트 적립» 소식의 겹침**: 5-4 2회부터 믹스 결과로 받은 열린 아이템 배지가 배지 포인트를 준다(`lib/combine/resultPointFollowUp.ts`). 지급 때 `notifyPointChange`가 «포인트 적립» 소식(#5, `sourceMissionId` 없음)을 보내는데(드랍 엔진과 같은 동작), 믹스 결과 화면과 소식이 겹쳐 보이는지 확인하지 못했다. 믹스 결과 화면을 다룰 때 소식이 중복 안내가 되지 않는지 정한다. 포인트 화면의 «받은 내역»에는 배지 포인트가 `badge_point_reward`로 나온다(유저 화면에는 «회수» 용어를 쓰지 않는다, 14.2절).

## 5-6에서 넘어온 항목 (2026-10-20, 5-6 2회 게이트 참고 사항과 1회 확인 사항)

- **읽기 함수 연결**: 프로필이 쓸 서버 함수는 `jam-web/src/lib/chapter/read.ts`의 `getMyChapter`(내 프로필: `chapterNo`·`name`·`nextChapterNo`·`progress`)와 `getPublicChapter`(다른 유저: `tribe { id, name }`·`chapterNo`·`name`, 진행 없음)다. 어느 응답에도 점수 숫자가 없다. 챕터가 없는 유저(퀘스트 전)는 `chapterNo: null`이라 화면이 «챕터 없음»을 그리고, 이름이 비면 `name: null`이라 «챕터 N»만 보인다. 규칙은 `docs/service/prd/chapter/PRD.md`에 있다.
- **존재하지 않는 유저 걸러내기**: 두 함수는 행이 없는 `userId`에서도 오류 없이 `tribe: null`, `chapterNo: null`로 성공한다. 존재하지 않는 유저와 «트라이브도 챕터도 없는 유저»가 응답으로 구분되지 않으므로 호출부가 아이디(username)를 id로 바꿀 때 걸러야 한다. `service` 클라이언트가 모든 유저를 읽을 수 있어 «누구의 챕터를 보여도 되는가»도 호출부가 정한다.
- **`tribe:tribes(id, name)` 임베드 실제 확인**: `users`에서 트라이브를 함께 읽는 부분은 가짜 클라이언트로만 시험했다. 같은 별칭 방식이 `app/api/users/[username]/itembooks/route.ts`에 있고 외래키 `users_tribe_id_fkey`는 생성 타입에서 확인했지만, 프로필에 연결할 때 실제 DB 호출로 한 번 확인한다.
- **읽지 못함 처리**: 조회가 하나라도 실패하면 `{ ok: false }`다(챕터 없음과 다르다). 읽지 못했을 때 프로필이 무엇을 그릴지 정한다. 다른 유저용 `tribe`에 `id`·`name` 말고 다른 값(예: 색, 이미지)이 필요하면 화면에 맞춰 정한다.
- **오름 연출과 소식**: 오름 소식 `chapter_up`(문구 «축하해요! 챕터 N에 올랐어요», 누르면 내 프로필, 아이콘은 기존 메달)은 5-6 1회에서 서버가 만든다. 축하 연출은 이 티켓의 몫이다. 알림함에서 메달 아이콘의 실제 모양은 챕터 오름이 처음 일어난 뒤 staging에서 확인한다(소식 행이 없어 지금은 볼 수 없다).
- **챕터 시작과 캡슐**: 챕터 1은 지금 완료 조건(활동 1건과 연출 7단계 또는 건너뛰기)으로 첫 동기화 직후 시작된다. 캡슐 열기와 잠긴 열기는 챕터 1 뒤에 일어나고, 캡슐은 홈 진입 때 처음 만들어지며 그때 챕터가 없으면 퀘스트 전 값(5)을 쓴다. 운영 로직 2.2절은 실제 단계(첫 동기화, 캡슐 열기, 잠긴 열기)를 모두 마쳐야 챕터 1이 된다고 정했으므로, 퀘스트 화면이 그 순서를 보이게 할 때 묶음 6의 퀘스트 개편과 맞춘다.

## 사용자 결정과 적용 기록 (2026-10-20)

시작 전 질문 4건에 답했다. 3건은 추천대로이고 1건은 추천과 다르게 정했다.

1. **오름 연출 시점**: 다음에 앱을 열 때 한 번 보인다(추천). `(main)/layout.tsx`가 지금 챕터를 읽어 기기에 저장된 «마지막으로 축하한 챕터»보다 높으면 가장 높은 챕터로 한 번 띄운다. 저장값이 없거나 챕터 1이면 연출 없이 저장만 한다. 기기마다 한 번씩 보인다. 서버 변경은 거의 없다.
2. **오름 연출 모양**: 새 축하 카드 `ChapterRiseOverlay`를 만든다(추천). 배지 획득 연출의 껍데기(탭바 숨김, 스크롤 잠금, 닫기)를 따르고 «축하해요!» / «챕터 N에 올랐어요» / 이름(있을 때만)을 `Card` 면에 보인다. 점수와 게이지는 없다.
3. **내 프로필 챕터 줄 위치**: 캡슐 위젯 바로 위(추천).
4. **퀘스트 전과 읽지 못했을 때**: **아무것도 보이지 않는다**(추천은 «퀘스트를 마치면 챕터 1이 돼요» 안내 줄과 «다시 시도» 버튼이었으나 사용자가 정했다). 내 프로필은 챕터가 없거나 서버가 읽지 못했을 때 챕터 줄 자체를 그리지 않는다. 그래서 «챕터 없음»과 «읽지 못함»이 화면에서 구분되지 않고, 읽지 못했을 때 유저가 다시 시도할 길이 없다(새로 고침만 가능). 다른 유저 프로필은 원래 없거나 읽지 못하면 줄을 빼는 규칙이다.

**회차**: 오름 연출 방식이 서버 변경을 부르지 않으므로 채원이 제안한 나눔을 따른다. 1회 = 프로필(챕터 줄, 타인 프로필)과 오름 연출, 2회 = 미션 목록·상세, 3회 = 포인트 화면·소식·종합 시험. 아현의 최종 요약은 2,500자 이내로 쓰게 한다.

**구현 때 지킬 점**: ① 오름 연출은 `(main)/layout.tsx`가 화면을 열 때마다 읽으므로 읽는 비용을 줄이는 방법(번호만 읽고 이름은 연출을 띄울 때만 읽기 등)을 아현이 정하고 채원이 확인한다. 읽기 함수는 `getMyChapter`(`lib/chapter/read.ts`)다. ② 연출 문구와 챕터 줄 문구는 UX 라이팅 가이드를 따르고 결과에 문구 목록을 적는다. ③ 미션 목록(`missions/page.tsx` 93~101줄)이 잠긴 보상 배지의 이름·등급을 내리는 것도 이 티켓에서 가린다(채원 추가 발견).

## 시작 전 조사 결과와 채원 사전 판정 (2026-10-20, 코드 읽기와 공용 DB 읽기 전용 확인)

**카리나가 코드에서 확인한 사실**
- 디자인 시스템 문서(`11 JAM 2.0 디자인 시스템.md`)에는 토큰과 화면 규칙만 있고 챕터·미션·포인트 화면의 구체 설계는 없다. 이 화면들의 모양은 아래 채원 판정이 정한다.
- `/profile`은 실제 화면이 아니라 `/{username}`으로 넘기는 경유지다(`app/(main)/profile/page.tsx`). 프로필의 실제 서버 페이지는 `app/(main)/[username]/page.tsx`이고 대상 유저를 `users`에서 `id, username, display_name, avatar_url`만 읽어 `ProfileClient`로 넘긴다. 내 프로필에서만 포인트 잔액(`pointBalance`)과 캡슐 초기값(`capsuleInitial`)을 읽어 내려주고, 타인 프로필에는 prop 자체가 없다(DOM과 RSC 페이로드에 실리지 않는 방식). 챕터 줄도 같은 패턴을 따른다.
- 내 프로필 헤더는 아바타, 이름, 포인트와 «편집» 버튼 행으로 이루어지고(`ProfileClient.tsx` 584~660줄), 캡슐 위젯(`CapsuleWidget`)은 그 바로 아래에 `isOwnProfile && capsuleInitial !== undefined`일 때만 나온다. 타인 프로필은 같은 자리에 팔로우 버튼이 있다.
- 알림 표 `notifications`에는 읽음 열이 없다(열: id, user_id, type, actor_user_id, actor_count, group_key, payload, bumps_badge, created_at, updated_at). 읽음은 유저당 «마지막으로 본 시각» 하나(`api/notifications/seen`)다. 그래서 `chapter_up` 소식만으로는 «이 오름을 축하했는가»를 저장할 수 없다. `processChapterRise`는 값을 돌려주지 않아(void) 오름이 일어난 요청의 응답에도 오른 챕터가 실리지 않는다.
- 배지 획득 연출(`components/BadgeRevealOverlay.tsx`)은 동기화 응답과 최초 Strava 연동 도착 페이지(`StravaConnectReveal`), 캡슐 열기 결과(`capsuleReveal.ts`)가 같은 틀을 쓴다. 전부 «획득한 항목 목록» 캐러셀이다.
- 포인트 화면은 `app/(main)/points/page.tsx`다.

## 배경 / 문제 정의

지금 프로필에는 챕터를 보여 주는 곳이 없다. 타인 프로필 서버 페이지는 트라이브도 읽지 않는다. 미션 화면은 트라이브를 모르고 받지 못한 보상을 나중에 받는 자리가 없으며, 상세에서 받기 전에 숨김 배지의 이름이 보일 수 있다.
챕터 점수의 숫자를 보이면 점수를 올리려는 행동을 부추길 수 있어 12.3절이 숫자를 보이지 않게 정했다. 챕터 이름 표는 비어 있으므로 이름이 없을 때의 모양도 정해야 한다.
상위 티켓 `20261016_2335`의 결정 3에 따라 디자인 시스템의 열린 항목(보조 버튼, 입력창 경계, 진행 바 색, 탭바 아이콘 대비, 로고 파운데이션, 옛 보라 바탕 썸네일, 상태 칩 MODULAR 승격, 배지 획득 오버레이 글자색)은 JAM 2.0이 끝난 뒤 사용자가 검토할 때 다룬다. 이 티켓에서 먼저 제안하지 않는다.

## 시작 전에 사용자에게 확인할 것 (주요 결정, 질문창)

1. **챕터 오름 연출**: 배지 획득 오버레이와 같은 틀을 재사용해 전체 화면 축하 연출을 보인다(추천, 새 컴포넌트를 만들지 않는다). 대안은 소식과 프로필 갱신만으로 알리는 것이다(조용하지만 챕터가 오른 순간의 보상감이 약하다). 채원 사전 판정에서 구체 모양을 확정한다.
2. **프로필 게이지의 자리**: 캡슐 위젯 바로 위에 챕터 줄을 둔다(추천, 챕터와 캡슐이 필요량으로 이어진다). 대안은 이름 아래 헤더 안에 둔다. 채원 판정으로 확정한다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 서버가 정한 응답을 그대로 그린다. 클라이언트에서 점수를 계산하지 않고 트라이브 거르기도 하지 않는다.
- 타인 프로필 서버 페이지가 트라이브와 챕터를 읽도록 5-6의 읽기 함수를 쓴다. 내 프로필 전용 prop 패턴(`capsuleInitial`)처럼 내 챕터 진행(게이지)만 내 프로필에 내려준다.
- 소식 화면에 챕터 오름과 미션 참가 취소 소식이 나온다(문구는 5-3·5-6에서 정했다).

### UI/UX 관점 (해당 시)

- 챕터 표시: «챕터 3 · 단골»처럼 챕터와 이름. 이름이 없으면 «챕터 3»만. 게이지 문구는 «다음 챕터까지»이고 점수 숫자는 보이지 않는다. 퀘스트 전 유저는 챕터 줄이 없거나 «퀘스트를 마치면 챕터 1이 돼요» 같은 안내를 보인다(문구는 UX Writing 가이드를 따른다).
- 미션 목록: 트라이브 제한 미션은 대상 유저에게만 보인다. 진행 중·완료·마감 상태 표시는 지금 모양을 유지한다.
- 미션 상세: 참가는 취소할 수 없다는 안내, 진행과 순위(정지 중이면 본인에게만 보임), 완료 뒤 보상, 인벤토리가 모자라 받지 못한 보상은 «받기». 밤 조건 미션에는 «어두울 때는 무리하지 마세요» 같은 안전 안내를 늘 보인다. 숨김 배지는 받기 전에 이름과 그림을 가린다.
- 포인트 화면: 가진 포인트와 받은 내역. 유저 화면에는 «회수» 용어를 쓰지 않는다(14.2절).
- 사용자 노출 문구는 `docs/service/writing/UX_WRITING_GUIDELINE.md`를 따른다(해요체, 고정 용어).

## 구현 계획 (회차)

처음부터 2~3회로 나눠 돌리고 회마다 게이트를 돌린다(예상 파일 30개 이상, 스토리·시험 포함). 1회는 프로필(챕터 줄, 타인 프로필)과 오름 연출, 2회는 미션 목록·상세, 3회는 포인트 화면과 소식·시험이다. 아현의 최종 요약은 2,500자 이내로 쓰게 한다. 스토리와 MODULAR 반영은 `/jam-design` 판정에 따른다.
