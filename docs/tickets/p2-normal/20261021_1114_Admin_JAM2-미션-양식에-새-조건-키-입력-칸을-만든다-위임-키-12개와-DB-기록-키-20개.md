# [Admin] JAM2 미션 양식에 새 조건 키 입력 칸을 만든다 (위임 키 12개, DB 기록 키 20개)

## 핵심 요약

- 요구사항: 5-2와 5-2b가 서버에서 미션 조건으로 판정하게 한 키 32개(엔진 위임 키 12개, DB 기록 키 20개)는 어드민 미션 양식에 입력 칸이 없어 원본 그대로 보존만 된다. 양식에서 값을 정해 저장할 수 있게 입력 칸을 만든다.
- 구현 계획: 키마다 값 형식, 단위, 상한을 정한다(예: 주간 활동일 상한 7). 입력 칸을 만든 키는 `missionConditionFields.ts`의 보존 목록(`MISSION_ENGINE_PRESERVED_KEYS`, `MISSION_ENGINE_DB_PRESERVED_KEYS`)에서 빼고 «폼 + 보존 = 정본» 패리티 시험을 맞춘다. 서버 규칙(DB 키 기준 값은 1 이상의 정수)을 입력 칸에서도 막아 저장 전에 알린다. 기간을 걸 수 없는 키 5개(`jam_total_earned`, `chapter_reached`, `days_since_signup`, `other_tribe_item_kinds_count`, `signup_recent_active_days`)는 선택지에서 빼거나 안내를 더한다. 양식에서 미션 타입을 바꿀 때 DB 기록 키를 어떻게 다룰지(지우거나 경고)도 정한다. 큰 작업이므로 키를 묶음으로 나눠 회차로 돈다.
- 관련 파일: `jam-web/src/app/admin/missions/missionConditionFields.ts`(위임 키 14개 입력 칸 40~55줄, 보존 키 64~67·77~78줄, `buildEngineConditionJson` 342~349줄, `unsupportedMissionConditionKeys` 372~382줄), `jam-web/src/app/admin/missions/MissionConditionSection.tsx`(532줄), 시험 `jam-web/src/app/admin/missions/__tests__/missionConditionFields.test.ts`(`node:assert`와 tsx, `package.json` 15줄 `test:node`), 키 정본 `jam-web/src/lib/missions/condition-keys.ts`(111~139·154~205줄, 기준 값 검증 `checkMissionConditionValue`), 정책 `docs/plan/jam2/service-redesign/10 미션.md` 3절.

## 배경 / 문제 정의

티켓 20261019_1318(5-8) 1회 계획을 세우다가 분리했다(2026-10-21). 5-8은 미션 양식의 종류(트라이브 미션, 공통 미션)와 참가 트라이브 선택, 순위형 제한 안내, 잠김 표시를 만든다. 새 조건 키 입력 칸까지 넣으면 키 32개마다 값 형식과 상한을 정해야 해 한 회차가 두 배로 커진다. 지금도 운영자는 이 키들이 든 미션을 운영툴 등록 경로로 만들 수 있고, 양식은 이미 든 값을 그대로 지킨다(저장해도 지워지지 않는다는 안내 경고가 뜬다). 양식에서 처음부터 정하려면 입력 칸이 필요하다.

5-8의 완료 조건 «넓어진 조건을 정해 저장할 수 있다»는 이 티켓으로 넘어갔다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 서버 저장 검사(5-2, 5-2b)가 최종 방어선이고 양식은 안내와 사전 차단이다.
- 새 입력 칸마다 시험을 더하고 패리티 시험을 맞춘다.
- 미션 전용 키 `jam_period_earned`는 배지 조건 레지스트리에 없어 입력 칸 정의(레이블, 단위, 범위)를 미션 쪽에서 새로 정한다.

## 완료 조건

- [ ] 32개 키 중 정하기로 한 키가 양식에서 입력되고 저장된다
- [ ] 보존 목록과 패리티 시험이 맞다
- [ ] 키마다 입력 상한이 걸려 도달할 수 없는 값이 저장되지 않는다
- [ ] 기간을 걸 수 없는 키 5개가 선택지에 나오지 않거나 안내가 붙는다
