# [Feature] JAM2 입장: 트라이브 고르기 전 앱 차단, 고르기 화면, 어드민 트라이브 변경과 참가 취소 연결 (묶음 6, 6-1)

## 핵심 요약

- 요구사항: 운영 로직 2장을 서버와 화면에 맞춘다. (1) 트라이브를 고르기 전에는 앱에 들어오는 모든 경로에서 온보딩으로 보내고, Strava 연결과 동기화도 막는다. (2) 트라이브 고르기 화면에 대주제와 짧은 한 줄, «고른 뒤에는 바꿀 수 없다», «동기화로 받는 아이템 배지가 고른 트라이브의 것이다» 안내를 둔다. (3) 어드민이 유저의 트라이브를 바꿀 수 있게 하고, 바꾸면 참가 중인 트라이브 미션을 취소하며(`mission_cancel_for_tribe_change`) 취소 소식을 보낸다. 캡슐에 채우다 만 잼을 새 트라이브의 캡슐로 옮기는 규칙(온보딩 설계 13-5)도 확인한다.
- 구현 계획: 시작 때 사용자 결정을 질문하고 채원 사전 판정(트라이브 고르기 화면)을 받은 뒤 파일 단위 계획을 옮겨 쓴다. DB 변경이 필요하면 추가만 한다(기존 열·함수를 바꾸지 않는다).
- 관련 파일(2026-10-21 조사, 시작 때 아현이 줄 위치를 다시 확인한다): 게이트 후보 `jam-web/src/proxy.ts`, `app/(main)/layout.tsx`, `app/api/strava/`(연결·동기화 라우트), 이동 지점 `app/auth/callback/route.ts`, `app/(main)/profile/page.tsx`, 고르기 화면 `app/(main)/onboarding/page.tsx`와 `lib/i18n/ko.ts` 1285줄 근처, 참가 취소 `lib/missions/participation-cancel.ts`와 마이그레이션 249, 어드민 유저 화면 `app/admin/users`, 알림 종류 `lib/notifications/types.ts`(참가 취소 종류 있음).

## 배경 / 문제 정의

운영 로직 2장은 «트라이브를 고르기 전에는 앱의 어느 화면도 쓸 수 없다. 로그인 직후만이 아니라 앱에 들어오는 모든 경로에서 트라이브를 확인하고, 없으면 온보딩으로 보낸다. Strava 연결과 동기화도 할 수 없다»고 정했다. 동기화로 받는 아이템 배지가 모두 소속 트라이브의 것이라 트라이브가 없으면 줄 아이템 배지를 정할 수 없기 때문이다.
지금은 트라이브를 고르지 않아도 앱을 쓸 수 있다. 트라이브를 바꾸는 경로도 없어서 5-1이 만든 참가 취소 함수를 부르는 곳이 없다.

## 사용자 결정과 적용 기록 (2026-10-21)

시작 전 질문 6건에 답했다. 4건은 추천대로이고 2건은 추천과 다르게 정했다. 7번은 1회 게이트 뒤에 더한 결정이다.

1. **게이트 기준**: 트라이브가 있는지(`users.tribe_id`, 추천). 온보딩 화면의 되돌림 조건(`onboarding_completed_at` → `tribe_id`)과 로그인 콜백의 판정도 같은 기준으로 바꾼다. 공용 DB에서 온보딩 완료 시각은 있는데 트라이브가 없는 계정 7개는 다음 로그인 때 트라이브 고르기 화면에서 한 번 고르면 된다.
2. **개발 로그인 계정**: 개발 로그인 라우트가 이 테스트 계정에 트라이브가 없을 때만 활성 트라이브 하나를 지정한다(추천). 라우트는 개발과 staging에서만 열린다(프로덕션 404). 공용 DB의 테스트 계정 한 행만 바뀐다. 다른 트라이브로 바꾸려면 2회의 어드민 변경을 쓴다.
3. **회차**: 1회는 게이트와 고르기 화면, 2회는 어드민 트라이브 변경과 참가 취소 연결이며 5-8 뒤에 한다(추천). 어드민 유저 상세(`app/admin/users/[id]/page.tsx`)가 5-8 2회와 같은 파일이기 때문이다.
4. **대주제**: `tribes.tagline` 한 칸에 «대주제 · 한 줄»을 적는다(추천). 마이그레이션과 어드민 칸을 늘리지 않고, 운영이 트라이브 화면에서 내용을 적는다.
5. **선택 표시**: **지금처럼 색 반전을 유지한다**(채원 추천은 테두리 링과 체크 표시였으나 사용자가 정했다). 추가 질문에서 **1px 테두리를 더해 이번에 고치기로 했다**(추천은 디자인 시스템을 건드리지 않고 열린 항목으로 남기는 것이었으나 사용자가 정했다). MODULAR `Card`의 반전 톤(`inverse`)이 테두리가 없어, 기본 톤(`default`, 1px `--border`)에서 선택으로 바뀔 때 1px씩 내용이 움직이고 카드 공통 규칙과 어긋난다. 반전 톤에 같은 두께의 테두리를 더해 크기를 고정한다. MODULAR 변경이므로 Story(`Card.stories.tsx`)와 프롬프트 문서(`Card.prompt.md`)를 함께 고치고, 반전 톤을 쓰는 다른 화면(`forbidden`, `drops`, `profile`, `SlotGrid`, `BadgeRevealOverlay`, `login`, `philosophy` 등)이 깨지지 않는지 시험으로 확인한다.
6. **확인 단계**: 확인 시트 없이 버튼 문구로 확정한다(추천). 카드를 눌러도 확정되지 않고 «이 트라이브로 시작하기» 버튼을 한 번 더 눌러야 확정된다. 제목 아래에 «한 번 고르면 바꿀 수 없어요»가 늘 보인다.
7. **로그아웃 길**(1회 게이트 WARN 뒤 추가 질문, 추천대로): 트라이브를 고르지 않은 유저는 `/profile`과 하단 탭에 갈 수 없어서 로그아웃할 길이 없었다(로그아웃은 프로필 화면에만 있다). 고르기 화면에 «로그아웃» 보조 링크를 더하기로 정했다. 채원 사전 판정(2026-10-21): 공용 `Button`의 `ghost`(새 토큰·새 컴포넌트 없음), «뒤로» 아래 32px 떨어진 맨 아래, 로딩·읽기 실패·활성 0개 상태에서도 항상 보임, 문구는 프로필의 «로그아웃»을 그대로 재사용, 확인 시트 없음. **1단계(아이디·이름)에도 같은 링크를 넣는다**: 같은 `/onboarding` 주소의 같은 막힘이고 1단계에는 «뒤로»도 없어 잘못된 구글 계정으로 들어온 유저가 빠져나갈 길이 없다. 사용자가 머지 승인 때 1단계 포함을 확인했다. 실패 처리만 프로필과 다르다: `signOut`이 네트워크 오류로 실패하면 세션이 남고 `proxy.ts`가 로그인된 유저를 `/login`에서 `/`로, 홈은 트라이브 게이트가 다시 `/onboarding`으로 보내 아무 일도 없는 막다른 길이 된다. 그래서 실패하면 «네트워크 오류가 발생했어요.»를 보이고 잠금을 풀어 다시 누를 수 있게 한다.

## 시작 전 조사 결과와 채원 사전 판정 (2026-10-21, 코드 읽기와 공용 DB 읽기 전용 확인)

**카리나가 코드와 DB에서 확인한 사실**
- **요청 가로채기**: `jam-web/src/proxy.ts`는 모든 요청에서 세션만 확인하고 트라이브를 읽지 않는다. 트라이브를 읽는 판정을 여기 두면 모든 요청에 DB 조회가 하나씩 더 붙는다.
- **화면 쪽 후보**: `app/(main)/layout.tsx`가 이미 `users` 행에서 `username, avatar_url, notifications_seen_at`을 읽으므로 `tribe_id` 칸을 더해도 조회 횟수는 늘지 않는다. 다만 트라이브 고르기 화면(`app/(main)/onboarding/page.tsx`, 577줄, 클라이언트 컴포넌트)이 같은 `(main)` 레이아웃 안에 있어, 레이아웃이 트라이브 없는 유저를 `/onboarding`으로 보내면 그 화면에서도 다시 보내는 반복이 생길 수 있다. 화면을 다른 라우트 그룹으로 옮기거나, 경로를 판별하는 방법을 아현이 정한다.
- **API 쪽 후보**: `syncStravaActivities`(`lib/strava/sync.ts` 1331줄)는 1370줄에서 이미 `assertNotSuspended`를 부른다. 같은 자리에 트라이브 검사를 더할 수 있고, Strava 연결 시작(`app/api/strava/auth/route.ts`)과 콜백(`app/api/strava/callback/route.ts`)도 같은 방식으로 막는다. 이용 정지처럼 던진 오류를 라우트가 구분되는 응답으로 바꾼다.
- **지금 이동 지점**: 로그인 콜백(`app/auth/callback/route.ts`)은 `onboarding_completed_at`이 비어 있으면 `/onboarding`으로 보낸다. `app/(main)/profile/page.tsx`는 `username`이 없을 때만 `/onboarding`으로 보낸다. 온보딩 화면은 `onboarding_completed_at`이 있으면 홈으로 되돌린다.
- **온보딩 저장**: `app/api/onboarding/complete/route.ts`는 1단계(아이디·이름)와 2단계(트라이브)를 같은 API로 받는다. 2단계에서 `tribe_id`와 `onboarding_completed_at`을 한 번에 기록하고, 이미 트라이브가 있으면 `ALREADY_SET`(409)으로 거절한다(트라이브 불변). 트라이브가 활성인지 서버가 다시 확인한다.
- **공용 DB 현황**: 유저 8명, 트라이브를 가진 유저 0명, `onboarding_completed_at`이 있는 유저 7명, 아이디는 있는데 트라이브가 없는 유저 8명. 트라이브 10개 가운데 활성 3개(낭만 미식가, 아스팔트 레인저, 숲속의 갱단). 운영 로직은 다섯 개를 예정한다. 따라서 게이트를 `tribe_id` 기준으로 두면 온보딩 화면의 되돌림 조건과 로그인 콜백의 판정도 `tribe_id` 기준으로 함께 바꿔야 반복이 생기지 않는다.
- **개발 로그인 계정**: `app/api/dev-login/route.ts`로 들어오는 고정 테스트 계정(공용 DB의 유저 하나)에도 트라이브가 없다. 게이트가 켜지면 그 계정으로 하는 로컬 확인이 모두 고르기 화면으로 보내진다.
- **캡슐**: `user_capsules`에는 트라이브 칸이 없고, 캡슐을 열 때 `lib/capsule/open.ts` 81~84줄이 `users.tribe_id`를 읽는다(없으면 `no_tribe`). 트라이브를 바꿔도 채우던 잼은 그대로 남는다. 운영 로직 2.4절의 «캡슐에 채우다 만 잼을 새 트라이브의 캡슐로 옮긴다»에 맞춰 옮길 코드가 따로 필요하지 않다.
- **트라이브 변경 기록**: 변경 이력을 남길 표가 없다(`tribe` 이름이 든 표는 `tribes`뿐). 운영 로직 2.4절은 누가·언제·어느 트라이브에서 어느 트라이브로·왜를 기록하고 유저에게 알림 한 종류를 보낸다고 정했다. 참가 취소 함수(`mission_cancel_for_tribe_change`)와 소식 보조 함수(`lib/missions/participation-cancel.ts`)는 있지만 부르는 곳이 없다.
- **5-8과 겹침**: 어드민 유저 상세 `app/admin/users/[id]/page.tsx`(157줄)는 5-8 2회가 챕터 구역을 더하는 파일이다. 트라이브 변경 입력을 같은 파일에 더하면 충돌한다.

## 시작 전에 사용자에게 확인할 것 (주요 결정, 질문창)

### 2회 시작 전 조사 결과 (카리나, 2026-10-21, 코드 읽기와 공용 DB 읽기 전용 확인. 줄 위치는 서브에이전트 보고이며 시작 때 아현이 다시 확인한다)

- **어드민의 지금 상태**: 트라이브를 보여 주거나 바꾸는 길이 없다. 유저 상세(`app/admin/users/[id]/page.tsx` 39·108~141줄)는 `select('*')`로 읽지만 트라이브를 쓰지 않고, 이름과 필터는 목록에만 있다(`lib/admin/user-list.ts`). 비슷한 조치의 선례: 포인트 지급은 고정 사유 6종과 «기타» 메모 필수, 고액 확인창(`UserGrantForm.tsx` 177~264줄), 권한은 `AlertDialog`에 사유 없음(`AdminRoleToggle.tsx`), 정지는 사유 자유 입력 필수(`api/admin/suspensions/route.ts`). 인가는 라우트 첫 줄 `getAdminUser()`, 없으면 403이고 시험은 `vi.mock`으로 클라이언트와 인가를 바꾼다.
- **조치 기록 장치는 없다**: 공통 어드민 변경 기록 표가 없다. 정지는 `user_suspensions.reason`·`suspended_by`, 포인트는 `point_transactions`에 사유만(처리자 열 없음), 권한·초기화·삭제는 `console.info`뿐이다. 얹을 만한 표도 없다(`admin_badge_bulk_runs`는 대상 유저 열이 없고 `ops_decisions`는 `bundle_id` NOT NULL FK, 참가 취소 기록 표에는 옛 트라이브·처리자 열이 없다). **새 표가 필요하고 다음 마이그레이션 번호는 258이다**(257은 `drop_chapter_names`로 적용됨).
- **DB 지금 객체**: `users.tribe_id`를 막는 트리거·제약이 없다(트리거는 `is_admin` 차단 `trg_users_block_client_is_admin_write`, `updated_at`, 삭제 기록뿐). **보안 틈(카리나가 정책·권한·트리거를 직접 SELECT로 확인함)**: `users: 본인만 수정` 정책은 `USING (auth.uid() = id)`뿐이고 `WITH CHECK`가 없으며, `authenticated`에 `tribe_id`(와 `username`·`onboarding_completed_at`) 열 UPDATE 권한이 있다. 그래서 **로그인한 유저가 브라우저에서 자기 `tribe_id`를 직접 바꿀 수 있다**(화면은 «바꿀 수 없다»고만 한다). 앱 코드가 `tribe_id`를 쓰는 곳은 온보딩 완료 API와 개발 로그인 둘뿐이고 모두 service 클라이언트다(프로덕션 `main`의 온보딩 API도 같다). `is_admin`은 `current_user IN ('authenticated','anon')`일 때 막는 트리거가 있어 같은 방식으로 `tribe_id`도 막을 수 있고, service_role과 SECURITY DEFINER 함수는 영향이 없다.
- **참가 취소**: `mission_cancel_for_tribe_change(p_user_id) → (out_mission_id, out_mission_title)`(마이그레이션 249 151~217줄, SECURITY DEFINER, service_role 전용)는 **지금의 `tribe_id`**가 허용 트라이브에 없는 트라이브 제한 미션의 참가 행을 `FOR UPDATE`로 잠그고, 취소 기록(`mission_participation_cancellations`, 열: user_id, mission_id, joined_at, progress_value, was_completed, new_tribe_id, reason 기본 'tribe_changed', cancelled_at)을 넣은 뒤 참가 행을 지운다. 완료 기록은 두고 `ends_at`은 보지 않는다(끝난 미션의 참가도 취소한다). 그래서 **트라이브를 먼저 갱신한 뒤에 불러야 한다.** 앱 쪽 `lib/missions/participation-cancel.ts`에는 호출 래퍼가 없고 소식 함수(29~57줄, 시험 11건)만 있다. **취소 함수를 부르는 곳이 0곳이다.** 소식은 하루 단위 `once` 키로 한 행이고 문구는 `ko.ts` 1711~1712줄, 이동은 `/missions`, 실패해도 던지지 않는다. 순위는 참가 행으로 세므로 참가 행이 지워지면 순위에서 빠지고, 스냅샷은 upsert만 해서 옛 행이 남는다(`batch/missions.ts` 413~416줄, 참고).
- **바뀐 뒤 영향**: 동기화는 그때 트라이브로 컬렉션을 고른다(`syncIssueRun.ts` 135~145·170줄). 보류 행(없음, 지금 0행)은 배지가 정해져 있고 고르기 RPC가 트라이브를 보지 않아 옛 배지로 남으며 피드 `tribe_name`은 새 이름이 된다. 캡슐은 열 때 `users.tribe_id`를 읽고 **캡슐 표에 트라이브 열이 없어 «새 캡슐로 옮길 것»이 없다**(운영 로직의 «채우다 만 잼은 그대로 옮긴다»는 이미 지켜진다). 슬롯 라우트에 트라이브 참조가 없고 `tribe_id`를 쓰는 DB 함수는 미션 둘뿐이다. 프로필은 매번 조인하고 캐시가 없다. `chapter_names`는 이미 없다.
