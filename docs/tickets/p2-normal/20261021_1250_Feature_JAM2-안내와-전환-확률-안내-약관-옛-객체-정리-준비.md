# [Feature] JAM2 안내와 전환: 확률 안내, 약관, 옛 객체 정리 준비 (묶음 6, 6-4)

## 핵심 요약

- 요구사항: 운영 로직 18장과 묶음 6의 마지막 전환을 준비한다. (1) 확률 안내 페이지(캡슐 확률 공개 등)와 서비스 소개 문구를 만들고, 이용약관과 확인자료를 정리한다. (2) 옛 객체를 바꾸거나 지우는 DB 정리는 **SQL 작성과 롤백 실측까지만** 하고 실행은 출시(main 승격)로 옛 프로덕션 코드가 사라진 뒤 사용자 승인을 받아 한다(사용자 결정, 2026-10-21). (3) 오픈 전 모든 테스트 유저와 주인 없는 개체·장소 드랍을 지우는 일은 지울 범위를 보이고 승인을 받아 출시 전에 따로 한다.
- 구현 계획: 시작 때 사용자 결정을 질문하고 확률 안내 페이지는 채원 사전 판정을 받은 뒤 파일 단위 계획을 옮겨 쓴다. 정리 SQL은 아현이 파일로 쓰고 카리나가 롤백 실측을 한다.
- 관련 파일(2026-10-21 조사, 시작 때 아현이 줄 위치를 다시 확인한다): 법·안내 페이지 `jam-web/src/app/(legal)/`(지금 `privacy`, `location-terms`), `app/(main)/philosophy/page.tsx`(148·157줄 근처), 확률 정보 원천 `capsule_policy`(마이그레이션 232~234)와 `lib/capsule/policy.ts`, 옛 도둑 의심 제재 `app/api/drops/[dropId]/pickup/route.ts`(120줄 근처 `applyBan`)와 `lib/abusing/shadow-ban.ts`, 옛 객체 목록은 상위 티켓 `20261021_1246`의 «묶음 6으로 넘어온 항목».

## 배경 / 문제 정의

운영 로직 18장은 안전과 확률 안내를 정한다. 지금 `app/(legal)`에는 개인정보처리방침과 위치기반서비스 이용약관 두 개뿐이고 확률 안내 페이지, 서비스 이용약관, 확인자료가 없다.
앞 묶음이 DB를 바꾸거나 지우는 변경을 «옛 프로덕션 코드가 사라진 뒤»로 미뤘다. 상위 티켓은 main 승격을 이 개발의 범위 밖으로 두었으므로, 정리 SQL을 지금 실행하면 프로덕션이 깨진다. 그래서 이 티켓은 정리를 준비만 한다.

## 시작 전 조사 결과 (2026-10-21, 코드 읽기와 공용 DB 읽기 전용 확인. 줄 위치는 서브에이전트 보고이며 시작 때 아현이 다시 확인한다)

### 확률 안내·약관·소개 문구

- **요구 문서**: 확률 대상은 동기화(개수·등급·잠김), 캡슐(개수·소속·등급·잠김), 시스템 드랍(등급)이다. 믹스, 잠긴 아이템 배지 열기, 액티비티·체크인 배지에는 확률이 없다(운영 로직 18.3, 1610~1611줄). 확률 안내 페이지는 푸터 링크 옆에 두고 확률을 표로 모두 보이며 보정 장치도 적는다. 바꾸기 전에 공지하고 바뀐 날짜를 적고, 설정이 바뀌면 페이지도 바뀌어야 한다(운영 로직 1612~1615줄, 정책 14번 73~76줄). 18.4는 유료 결제가 없다고 정한다. 18.5는 방침에 장소 열람 기록과 검색 캐시를 더하라고 한다(1628줄, 지금 방침에는 둘 다 없다). **«확인자료»는 위치정보 수집·이용·제공사실 확인자료**를 가리킨다(`location-terms/page.tsx` 232~233줄). 이것만 담는 전용 기록은 없고, 6-3은 체크인 획득·장소 열람·드랍과 픽업 기록을 확인자료로 보고 탈퇴할 때만 `retained_records`로 복사한다(티켓 `20261021_1249`).
- **확률 값과 원천(공용 DB)**: `capsule_policy`: 개수 확정 1개 + 보너스 1개(확률 0.2), 다른 트라이브 0.2, 등급 70/22/6/2, 보정 1은 15회(Epic 이상 미출현). `jam_policy`: 보정 2(Common 10연속이면 다음은 Rare 이상, 동기화와 캡슐 합산), 동기화로 받는 개체의 잠김 0.25, 동기화 개수 1개 확정(등산 2개)과 보너스 2회(한 번마다 잼÷600, 상한 0.25), 동기화 등급 84/13/2.5/0.5. 퀘스트 전 첫 캡슐은 첫 개체를 반드시 잠그고 필요한 잼은 5다. `ambient_drop_config`(시스템 드랍): explicit 모드, Common 100%, 자동 배포는 꺼져 있다. 값은 운영 로직 5.4·6.7·7.4절 표와 같고 코드 상수(`capsule/policy.ts` 40~52줄, `jam/policy.ts` 54~78줄)는 DB 조회가 실패할 때 쓰는 사본이며 값이 같다. 믹스, 미션 보상, 유저 드랍에는 확률이 없다(`lockAssignment.ts` 79줄).
- **문서와 어긋나는 곳(공개할 때 정직하게 적어야 하는 것)**: ① 지금 발급할 수 있는 아이템 배지가 Common 270개뿐이다. 뽑힌 등급에 후보가 없으면 한 등급씩 내려 뽑기 때문에(`syncIssue.ts` 210~222줄) 지금은 결과가 전부 Common이다. ② 활성 트라이브가 3개라 문서의 «나머지 넷 가운데 고르게»가 실제로는 «후보가 있는 나머지 트라이브 가운데»로 동작한다. ③ 시스템 드랍의 random 모드는 등급 분포를 실행마다 무작위로 정해 고정된 확률 표를 만들 수 없다(`rarity.ts` 22~27줄).
- **지금 있는 문구와 입구**: 서비스 화면에서 «확률»이라는 말은 `philosophy/page.tsx` 147~148줄 한 곳뿐이다. 푸터에는 Philosophy, 개인정보 처리방침, 위치 약관 세 링크만 있고(`Footer.tsx` 55~74줄), 로그인 화면과 `(legal)` 페이지에는 푸터가 없다. 캡슐 시트와 잠긴 아이템 배지 상세에는 확률 링크가 없다. 로그인 화면의 약관 동의 문장에도 링크가 없다(`login/page.tsx` 76~78줄). `/philosophy`는 공개 경로 목록에 없어 로그인해야 열린다(`proxy.ts` 59~68줄).
- **법 페이지 구조**: `(legal)` 레이아웃은 로그인 확인을 하지 않고, 개인정보처리방침과 위치 약관은 DB를 읽지 않는 동기 서버 컴포넌트다(원고는 `docs/service/legal/*.md`). 두 페이지가 같은 보조 컴포넌트를 각자 복사해 쓰고 있다(공용으로 빼는 티켓 `1428`은 OPEN). 방침은 v1.1(2026.10.1)과 v1.0 개정 이력이 있고, 위치 약관은 시행일만 있고 개정 이력이 없다. 커밋 `43ac5d1db`(10-18)가 두 페이지의 표현을 «장소»로 고쳤지만 시행일과 개정 이력은 바꾸지 않았다. 새 페이지에 필요한 것: 공개 경로 추가(`proxy.ts`), 페이지 제목 메타데이터(법 페이지에는 없고 티켓 `1448`이 다룬다, OPEN), 푸터 링크, 시험. **서비스 이용약관 원고는 저장소에 없다**(`LOCATION_TERMS.md` 292~293줄), 위치기반서비스 이용약관 원고 티켓 `20260929_1303`은 WAITING이다.
- **소개 문구**: 고칠 대상은 `/philosophy`다(정책 14번 129줄). 147~148줄 «드랍이 없을 수도»는 지금 1개가 확정이다(설정으로 0개를 둘 수는 있다). 157~158줄 «지나가면 자동으로 체크인»은 실제 판정이 동기화 때다(운영 로직 1616줄). 에세이 72줄과 FAQ 195~201줄은 «보상을 조용히 비운다»고 적었는데 이는 운영 로직 1466줄의 «섀도우밴은 쓰지 않는다»와 반대다. **에세이는 수정 금지 원고로 표시돼 있어**(49줄) 사용자가 새 원고를 주어야 고칠 수 있다.
- **DB에서 읽는 구조**: `getCapsulePolicy(client)`는 서버 컴포넌트에서 그대로 쓸 수 있다(`capsule/policy.ts` 82~85줄). 설정 표 셋은 RLS가 켜져 있고 정책이 없어 서버(service_role)로만 읽힌다. 요청 정보를 쓰지 않는 페이지는 빌드 때 한 번만 조회하므로 설정이 바뀌면 따라 바뀌게 하려면 `force-dynamic`이 필요하다(선례 `admin/points/page.tsx` 23줄). 캡슐 값은 `capsule_policy`와 `jam_policy` 두 표에 나뉘어 있다. **`updated_at`을 갱신하는 트리거가 없어 «바뀐 날짜»로 쓸 수 없고**, 이 값들을 고치는 어드민 화면도 없다. 그래서 바뀐 날짜는 페이지에 이력으로 직접 적어야 한다.
- **UX 라이팅**: 가이드에 확률이나 % 표기 규칙이 없다(등급은 영문, 임의로 고르는 것은 «무작위»). 다시 열기를 부추기는 문구는 금지(운영 로직 494~497줄)인데 보정 장치는 공개해야 하므로(14번 75줄) 확률 페이지 문구에 두 규칙이 함께 걸린다.
- **범위 밖 발견물**: 어드민 배지 양식은 «뽑힐 상대 확률»을 보여 주지만 실제 추첨은 후보 사이에서 균등하게 고른다(`BadgeForm.tsx` 975~1003줄, `syncIssue.ts` 184~189줄). `/admin/drop-policy`는 새 발급이 읽지 않는 옛 확률 값을 편집한다(`DropPolicyForm.tsx`). 개인정보 처리방침은 기록을 «탈퇴 시까지 보관»한다고 적었는데 실제로는 탈퇴 뒤 6개월 보관한다(마이그레이션 263, 6-3). 소식 종류에 공지가 없다.
- **확인하지 못함**: 확률을 바꾸기 전 공지를 홈피드로 할 수 있는지, 옛 프로덕션 코드가 이 설정 표들을 읽는지, 기존 표를 확인자료로 보는 해석이 법적 요건을 채우는지(법률 판단이라 다루지 않았다).

### 도둑 의심 제재와 옛 객체 정리, 오픈 전 데이터

- **옛 도둑 의심 제재**: 픽업 때 직전 위치 대비 속도가 300km/h를 넘거나 하루 이동이 3,000km를 넘으면 감지한다(`abusing/gps-detector.ts` 92·100줄). 제재는 픽업 거부, 72시간 soft 밴(`applyBan`, staging `api/drops/[dropId]/pickup/route.ts` 120줄, main 93줄), 장소 차단, 기록이다. 밴이 실제로 막는 것은 **`main`에서만** 동기화 드랍의 Mystic을 Common으로 낮추고 Mystic 배지를 주지 않는 것이다(`drop-engine/index.ts` 639줄, `badge-engine/index.ts` 1426줄). **staging에서는 효과가 없다**: `applyShadowBanCap`(`drop-engine/index.ts` 472줄)을 부르는 곳이 어드민 미리 보기(`drop-engine/preview.ts` 231줄)뿐이다(카리나가 `grep`으로 확인). 밴 관리 API 4개(`api/admin/abusing/bans/**`)와 목록·일괄 처리(`lib/admin/abusing-list.ts`, `abusing-bulk.ts`)는 staging에 남아 있고 그 API를 부르는 어드민 화면(`admin/abusing/BanTable.tsx`)은 `main`에만 있다. 공용 DB에서 `user_shadow_bans`와 `user_suspensions`는 모두 0행이다.
- **새 이용 정지로 바꾸는 경우**: 정지를 자동으로 만드는 함수가 없다. `suspendUser`(`suspension/suspension-write.ts` 33줄)는 어드민 API만 부르고 사유가 필수다(DB CHECK). **정책 문서 20번 4절은 «자동으로 정지까지 걸지 않는다. 그 픽업을 거부하고, 그 장소를 72시간 차단하고, 기록을 남기고, 운영자에게 알린다. 운영자가 기록을 보고 정지를 건다»**(카리나가 직접 읽음)이라 자동 정지는 정책과 어긋난다. 같은 절의 «운영자에게 알린다»는 staging 픽업에 없다(앱 코드에 Slack 알림이 없고, `#jam-alert` 경보는 정기 점검 루틴이 DB를 읽어 띄우는 방식이다).
- **정리 대상 표(가·나·다·라)**: 공용 DB 상태, staging 참조, `main`(옛 프로덕션) 참조, 지우면 깨지는 것.

  **지금 안전하게 지울 수 있는 것은 없다.** 출시 직후 안전한 것은 위 표의 앞 세 줄((가) 두 개와 `user_shadow_bans`)이고, `user_shadow_bans`는 이 티켓에서 코드를 바꾼 뒤에만 안전하다. 나머지는 staging 코드도 아직 쓰므로 **출시 뒤에도 코드 작업이 먼저**다. 열이나 표를 지우면 데이터를 잃고(되돌릴 수 없다), 함수·제약·빈 표는 다시 만들면 되돌릴 수 있다. 섀도우밴이 없어지면 `abusing_policy`의 배율 8칸은 쓸 곳이 없어지고, `tier_mode`가 켜진 컬렉션이 하나도 없다(범위 밖 발견물).
- **순서와 선행 조건**: 코드 작업으로 `applyBan`, bans API, 목록·일괄 처리, 미리 보기의 밴 표시를 지운다. `logAbusingEvent(s)`는 다른 파일로 옮겨야 한다(`abusing/poi-block.ts` 8줄이 쓴다). SQL 순서(판단): 제약 → 함수 → 표 → 값 → 열. 옛 장착 함수가 완성 표를 읽으므로 함수를 먼저 지운다. 롤백 실측은 `DO` 블록 안에서 적용, 확인, 되돌림, 재확인을 하고 `RAISE EXCEPTION`으로 전부 취소하는 방식(6-3 선례)이고, 실측하는 동안 그 표에 배타 잠금이 걸린다.
- **파일 위치**: 마이그레이션을 자동으로 적용하는 도구는 없다(`supabase/config.toml`·CI에 supabase 없음). 적용은 카리나가 MCP로 한다(`docs/agents/orchestrator.md` 84줄). 단 `/jam-ship`의 «신규 파일이 운영 DB에 적용됐는지 확인» 점검(`.claude/skills/jam-ship/SKILL.md` 76줄)이 이 파일을 미적용으로 잡을 수 있다. 선례: 244·245·248의 머리말에 «작성만 하고 실행하지 않았다». 저장소 파일 대비 적용 기록에 없는 마이그레이션은 244·245·248·264(이 기록이 전수가 아니어서 실제 적용 여부는 확인하지 못함). 프로젝트 규칙 6(`CLAUDE.md`)은 «SQL 파일은 직접 실행하더라도 `jam-web/supabase/migrations/`에 반드시 남긴다»이므로 그 폴더에 둔다.
- **오픈 전 데이터(마)**: 유저 8명: 테스트 목록 4명(`lib/env/test-accounts.ts` 39줄), 어드민 2명, 그 밖 2명(그 2명이 테스트 유저인지는 확인하지 못함). 어드민 계정은 `deleteAccount`가 삭제를 거절한다. 주인 없는 아이템은 791개이고 모두 유효 드랍 위에 있어 어드민의 «소유자 없음» 정의로는 0개다(`admin/orphaned-items-query.ts` 7줄). 유효 드랍은 시스템 드랍 755개, 유저 드랍 36개(모두 어드민이 놓은 것)이고, 유저를 지워도 그 유저가 놓은 드랍은 남는다(유저를 참조하는 외래키는 CASCADE 47개, SET NULL 9개). 운영 로직 17.3절: «정식 오픈 전에 사용자가 모든 테스트 유저와, 그 유저들이 남긴 주인 없는 아이템 배지 개체와 장소 드랍을 지운다». 지울 범위를 보이는 미리 보기 쿼리 셋이 필요하다: 지울 대상 유저 목록, 유저별 연쇄 삭제 건수(`admin/user-bulk-impact.ts` 106줄), 출처별 드랍 수와 그 위의 아이템 수. **트라이브가 빈 기존 유저 7명**은 어드민 2명, 목록 테스트 3명, 그 밖 2명이고 모두 `initial_sync_done`이 true라 트라이브를 고른 뒤에도 첫 동기화 규칙을 받지 않는다(`strava/sync.ts` 1497줄). 이 유저들에게 퀘스트가 시작되는지는 확인하지 못함.

## 시작 전에 사용자에게 확인할 것 (주요 결정, 질문창)

1. **확률 안내 페이지의 위치와 내용**: 채원 사전 판정으로 확정한다. 확률 값은 DB 설정(`capsule_policy`)을 읽어 보인다(추천, 값이 바뀌어도 문서와 어긋나지 않는다).
2. **약관 문안과 시행일**: 서비스 이용약관 문안과 개인정보처리방침·위치기반서비스 약관의 시행일·개정 이력은 사용자가 확정한다(4-2에서 문구만 «장소»로 바꿨다). 티켓 `20260929_1303`(위치기반서비스 이용약관 원고, 대기 중)과 이어진다.
3. **옛 도둑 의심 제재의 대체**: 드랍 픽업 코드의 `applyBan`을 새 이용 정지(`user_suspensions`)로 바꿀지, 제재 없이 기록만 남길지 정한다. 옛 `user_shadow_bans` 정리의 선행 작업이다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 정리 SQL 파일은 `jam-web/supabase/migrations/`에 작성하되 번호 앞이나 이름에 «출시 뒤 실행»을 분명히 적고, 적용 목록(`list_migrations`)에 섞여 실수로 실행되지 않게 실행 순서와 선행 조건을 파일 머리말에 쓴다. 되돌림 SQL을 싣고 트랜잭션 안에서 롤백 실측을 한다.
- 정리 대상: 지갑 잔액 음수 방지 제약(`point_wallets.balance >= 0`), 옛 `record_combine_success`, 옛 `user_shadow_bans`와 abusing·bans API와 `applyShadowBanCap`, 옛 컬렉션 함수·열, `initial_sync_done`, 구 `drop_policy`, `all_random` 값, `poi_match` 행, `user_family_progress`. 제약과 열을 지울 때는 옛 코드를 참조하는 곳이 모두 사라졌는지 대조한다.
- 옛 도둑 의심 제재 코드의 대체(결정 3)는 이 티켓의 구현 범위다.
- 이 티켓은 정리 SQL을 **실행하지 않는다.**

### UI/UX 관점

- 확률 안내 페이지는 푸터·캡슐 화면 등에서 닿을 수 있다. 구성은 채원 판정이다. 사용자 노출 문구는 `docs/service/writing/UX_WRITING_GUIDELINE.md`를 따른다.

## 구현 계획 (회차)

시작 때 파일 단위로 옮겨 쓴다. 1회 확률 안내·약관·소개 문구, 2회 옛 도둑 의심 제재 대체와 정리 SQL 작성으로 나눈다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)

- 확률 안내 페이지가 열리고 캡슐 확률 값이 DB 설정과 같다(시험으로 확인).
- 이용약관과 소개 문구가 사용자가 확정한 문안으로 들어가 있다.
- 드랍 픽업 코드가 옛 `user_shadow_bans`에 더는 쓰지 않는다.
- 옛 객체 정리 SQL이 파일로 작성되어 있고 되돌림 SQL과 롤백 실측 결과가 이 티켓에 기록되어 있다. 실행하지 않았다.

### 후속 범위 (담당: 카리나, 시점: 출시 뒤)

- 출시(main 승격)로 옛 코드가 사라진 뒤 사용자 승인을 받아 정리 SQL을 실행하고 확인 쿼리를 남긴다. 오픈 전 테스트 유저 삭제는 지울 범위를 보이고 승인을 받아 출시 전에 따로 한다.
