# [Feature] 옛 컬렉션 구조를 줄이고 컬렉션 4등급 전환을 마무리한다

## 핵심 요약

- 요구사항: 새 컬렉션 구조(등급별 이름 칸, `item_books.tier_mode`)가 **한 컬렉션에도 켜져 있지 않아** 옛 함수와 옛 완성 표가 지금 모든 컬렉션이 쓰는 실제 경로다. 6-4 4회 조사에서 이것이 «정리 SQL 한 줄»이 아니라 **컬렉션 전환의 마무리**임을 확인했다. 컬렉션을 새 구조로 옮기고 옛 구조를 지우는 일을 설계부터 한다.
- 현황(공용 DB 2026-10-22 읽기 전용, 줄 위치는 시작 때 다시 확인한다):
  - 컬렉션 100개, `tier_mode` 켜진 것 0개. 새 표 `user_item_book_tier_completions`·`item_book_tier_rewards`·`item_book_tier_default_rewards`에 행이 없다(기본 보상 표 포함 확인은 시작 때).
  - 옛 함수: `slot_item_into_book`(`item_books.reward_points`를 읽고 `user_item_book_completions`에 기록), `swap_item_in_book`, `unslot_item_from_book`(`user_item_book_completions` 참조. **새 경로도 이 함수를 같이 쓴다**). 새 함수는 `slot_item_into_book_tiered`·`swap_item_in_book_tiered`.
  - 옛 완성 표 `user_item_book_completions` 3행, 옛 보상 열 `item_books.reward_points`(10개 컬렉션에 값)·`reward_badge_id`.
  - 장착 라우트 `app/api/itembooks/[id]/slot/route.ts`(143·208·267줄)가 `tier_mode`에 따라 옛·새 함수를 고른다.
  - 옛 완성 표를 읽는 코드(8곳 이상): `app/(main)/badges/page.tsx` 144줄, `app/(main)/collections/[id]/page.tsx` 156줄, `app/(main)/[username]/collections/page.tsx` 121줄, `app/api/itembooks/route.ts` 83줄, `app/api/users/[username]/itembooks/route.ts` 87줄, `lib/today/status.ts` 75줄, `lib/today/exposure.ts` 138줄, 어드민 `app/api/admin/itembooks/[id]/route.ts`(삭제 가드 주석 118줄), 어드민 컬렉션 폼(`ItemBookForm.tsx`, `api/admin/itembooks/route.ts`)의 `reward_points`·`reward_badge_id` 입력.
- 구현 계획(안, 시작 전 사용자 결정이 필요하다): ① 컬렉션을 새 구조로 옮기는 방침(전부 켜기, 켜는 시점, 등급별 보상 입력은 어드민 화면 묶음 7과 이어진다). ② 옛 완성 기록 3건과 `reward_points`·`reward_badge_id`를 새 등급 보상으로 어떻게 옮길지(옮기지 않고 버릴지 포함). ③ `unslot_item_from_book`을 새 구조 전용으로 바꿀지 새 함수를 둘지. ④ 읽는 코드 8곳을 새 표로 전환. ⑤ 마지막에 옛 함수 3개, 옛 완성 표, 옛 보상 열 삭제 SQL(`post_release`, 롤백 실측, 열·표 삭제는 데이터를 잃으므로 머리말에 적는다)과 실행은 출시 뒤 사용자 승인.
- 관련 티켓: `20261016_2340`(컬렉션 4등급 구조와 단일 완성 판정, 이 티켓이 «옛 것을 지우는 축소는 묶음 6의 전환 단계»라고 미뤘다), 묶음 7(어드민에서 `tier_mode`를 켜는 칸), 6-4 4회 `20261021_1250`.

- **2026-10-22 정정**: 시작 전 조사로 위 «구현 계획(안)»은 아래 「사용자 결정」과 「구현 계획」(4회차)으로 확정됐다. 읽는 코드 목록과 DB 현황은 아래 「시작 전 조사 결과」가 최신이다(`unslot_item_from_book`은 완성 표를 쓰지 않으므로 지우지 않는다).

## 배경 / 문제 정의

6-4 4회가 옛 객체 정리 SQL을 쓰려고 현황을 읽다가 옛 컬렉션 구조는 다른 후보와 성격이 다르다는 것을 확인했다. 새 4등급 구조가 아직 아무 컬렉션에도 켜져 있지 않아, 옛 함수를 지우면 모든 컬렉션 장착이 멈춘다. 사용자가 4회에서는 바로 안전한 것만 쓰고 이 구조는 후속 티켓으로 넘기기로 했다(결정 6).

발견: 2026-10-22 티켓 `20261021_1250` 6-4 4회 시작 전 조사.

## 상세 요구사항

### 서비스/코드베이스 관점

- 컬렉션 완성 판정과 보상이 새 구조 하나로 모인다. 옛 완성 기록이 있던 유저의 완성 표시와 이미 받은 보상이 사라지거나 중복 지급되지 않는다.
- 옛 함수·표·열은 출시 뒤, 읽는 코드가 모두 새 표로 옮겨진 다음에만 지운다.

### UI/UX 관점

- 컬렉션 화면과 완성 표시(`badges`, `collections`, 다른 유저 컬렉션, 오늘 카드)가 전환 전후에 같은 결과를 보인다(영향은 시작 때 실측한다).

## 사용자 결정과 적용 기록 (2026-10-22)

1. **순서**: **7-6 입력 뒤에 옛 경로를 걷는다**(추천). 지금은 새 구조에서 빠진 읽는 곳만 메우고, 옛 함수 호출 분기와 옛 완성 표 읽기를 걷는 일은 새 컬렉션이 4등급으로 들어간 뒤에 한다. 마지막에 옛 함수·표·열을 지우는 SQL은 출시 뒤에 실행한다.
2. **옛 데이터**: **옮기지 않고 정리 SQL에서 함께 버린다**(추천). 옛 완성 기록 3건(관리자 계정 한 명)과 옛 보상값(컬렉션 10개 합 200점, 보상 배지 0개)은 새 등급 구조로 옮기지 않는다. 이 기록으로 포인트가 나간 적이 없고 컬렉션에 새 컨텐츠를 덮어쓰면 아이템이 바뀌어 옛 완성이 뜻을 잃기 때문이다. 보상은 4등급 기본값(100·200·400·800점)으로 바뀐다. 되돌림 SQL에 값을 적어 둔다.
3. **완성한 컬렉션 수 기준**: **등급 하나라도 완성하면 센다**(추천). 컬렉션당 최대 1이고, 챕터 점수가 등급마다 완성을 인정하는 방식과 결이 같다. 옛 기록과 등급 기록이 같은 컬렉션에 겹쳐도 한 번만 센다.

**묻지 않고 추천대로 정한 것(다르게 하라고 하지 않으면 이대로)**

(가) 4회차로 나눈다. 1회 읽는 쪽 빈틈 메우기, 2회 서비스 경로에서 옛 방식 걷기, 3회 어드민 정리, 4회 정리 SQL. 회차마다 게이트를 돌린다. 모든 회차가 `planOnlyWaiver`를 쓴다.
(나) **2회 시작 조건**: 7-6의 DB 적용으로 활성 컬렉션이 모두 4등급이다. 시작 전에 `SELECT count(*) FROM item_books WHERE is_active AND NOT tier_mode`가 0이어야 하고, 아니면 멈추고 보고한다. 비활성 컬렉션은 4등급이 꺼져 있어도 된다(장착이 안 되는 상태로 남는다).
(다) 옛 방식을 걷은 뒤 4등급이 꺼진 컬렉션은 장착·교환 요청이 새 함수로 가서 DB가 `tier_mode_off`로 거절하고 라우트가 이미 409로 답한다(새 문구 없음). 어드민이 4등급이 꺼진 컬렉션을 활성으로 바꾸려 하면 409로 막는다(3회). `tier_mode` 열과 7-8의 «4등급 방식» 패널(켜기·끄기)은 그대로 둔다.
(라) `unslot_item_from_book`은 지우지 않는다. 본문 주석 한 줄이 낡은 표 이름을 가리키지만 동작과 무관하다. 4회 SQL의 선행 확인에서 이 함수 본문이 표를 언급하는 것은 주석뿐임을 보여 준다.
(마) 1회의 지표 보강은 옛 표와 등급 표를 합쳐 센다(옛 표를 읽는 쪽은 2회에서 걷는다). 시간 범위 인자(`window`)는 두 표의 `completed_at`에 모두 건다.
(바) 정리 SQL 번호는 시작 시점 `origin/staging`의 가장 높은 번호 다음부터 쓴다. 0938이 271~274를 썼고 7-6 티켓은 «273~277»로 적어 두었으므로(시작 때 다시 확인한다고 이미 적혀 있다) 먼저 만드는 쪽이 번호를 가져가고 나중 것이 비켜선다.
(사) 생성 타입(`database.generated.ts`·`database.ts`)은 SQL을 적용한 뒤에만 고친다. 지울 위치는 SQL 머리말에 적는다.
(아) 로컬 확인은 어드민 화면과 읽기 화면을 읽기만 한다. 공용 DB에서 «켜기»·«끄기»·저장·삭제는 누르지 않는다.
