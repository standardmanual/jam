# [Infra] GPS 조작 감지(도둑 의심)를 운영자에게 알린다: 감지 즉시 앱에서 #jam-alert (파일 이름의 «정기 점검 루틴»은 처음 가정이었고 아래 결정으로 바뀌었다)

## 핵심 요약

- 요구사항: 정책 20번 4절과 운영 로직 16.5절은 GPS 조작이 감지되면 «그 픽업을 거부하고, 그 장소를 72시간 차단하고, 기록을 남기고, **운영자에게 알린다**. 운영자가 기록을 보고 정지를 건다»고 정했다. 6-4 2회가 옛 72시간 섀도우밴을 지우면서 거부·장소 차단·기록은 유지했지만 «운영자에게 알린다»는 지금 어디에도 없다.
- **결정(2026-10-22, 시작 전 조사 뒤 사용자 답)**: ① **감지 즉시 앱에서 `#jam-alert`에 한 건**을 올린다. 픽업 라우트가 GPS 조작을 감지하면 응답 뒤(`after`)에 이미 있는 `postOpsSlack`으로 올린다(대량 수령 경보와 같은 방식). ② 글에 **유저 ID를 적는다**(대량 수령 경보와 같게). 장소 이름, 감지 사유(속도 또는 하루 이동거리), 장소 차단 시간, 확인할 곳(어드민 «장소 블록» 탭)도 적고 **좌표와 이메일은 적지 않는다**.
- 구현 계획(파일 단위는 아래 「구현 계획」): 새 `lib/abusing/gpsSpoofAlert.ts`(글 만들기와 보내기, 던지지 않는다)와 시험, 픽업 라우트 감지 분기에서 호출과 시험, 문서(운영 로직 16.5, 정책 20번, 예약 작업 문서 Slack 절·4-6의 적용 범위, `04_PROJECT_SPEC.md` 환경변수 표, `현재 서비스 비교.md`), `jam-web/.env.example`의 Slack 변수 3개.
- 관련 파일: `jam-web/src/app/api/drops/[dropId]/pickup/route.ts`(감지 분기 107~143줄 근처), `jam-web/src/lib/admin/opsInbox/slack.ts`(`postOpsSlack`, `escapeSlackText`), `jam-web/src/lib/jam/massEarnAlert.ts`(선례), `jam-web/src/lib/abusing/gps-detector.ts`, `jam-web/src/lib/abusing/abusing-log.ts`.

## 배경 / 문제 정의

사용자 결정 4(6-4, 2026-10-21)는 «운영자에게 알린다는 앱에 Slack을 넣지 않고 정기 점검 루틴이 기록을 읽어 `#jam-alert`에 띄우는 방식으로 별도 티켓에 남긴다»였다. 그 전제(앱 코드에 Slack 알림이 없다)가 사실과 달랐다. 앱 서버에 이미 Slack 게시 경로가 있어(아래 조사) 결정을 다시 받았고, 이 티켓은 그 새 결정을 따른다.

발견: 2026-10-21 티켓 `20261021_1250` 6-4 조사와 결정 4, 2026-10-22 이 티켓의 시작 전 조사.

## 시작 전 조사 결과 (카리나, 2026-10-22, 코드·문서 읽기와 Vercel 환경변수 이름 확인. 공용 DB는 읽지 않았다)

- **앱 서버에 Slack 게시 경로가 이미 있다**: `lib/admin/opsInbox/slack.ts`의 `postOpsSlack('alert' | 'report', 글)`이 `SLACK_BOT_TOKEN`, `SLACK_CHANNEL_JAM_ALERT`, `SLACK_CHANNEL_JAM_REPORT`를 읽어 `chat.postMessage`를 부른다(값이 없으면 `not_configured`를 돌려주고 던지지 않는다, 제한 시간 8초). 세 환경변수는 **운영 Vercel에 설정돼 있다**(`vercel env ls production`에서 이름만 확인, 값은 보지 않았다, 22일 전 등록). staging 프로젝트(`jam-stage`)의 설정은 확인하지 못했다.
- **선례 둘**: ① 운영 로직 16.3의 **대량 수령 경보**는 이미 구현돼 있다. 동기화(`strava/sync.ts` 1154·1182줄)가 `alertMassEarnIfNeeded`(`lib/jam/massEarnAlert.ts`)를 불러 `#jam-alert`에 직접 올리고, 실패해도 던지지 않는다. ② 매시 5분 Vercel 크론 `ops-stop-signals`(`vercel.json`)가 예약 누락·루틴 실패를 `#jam-alert`에 올린다(신호 체계의 한 시간 창 방식).
- **에이전트 예약 루틴은 쓸 수 없다**: 켜진 루틴은 데일리 미팅 하나뿐이고 나머지는 JAM 2.0 완료 뒤 재개로 꺼 두었다(`scheduled-jobs.md` 머리말). 루틴으로 만들면 출시 시점에 알림이 없다.
- **감지 지점**: 픽업 라우트의 `gpsCheck.detected` 분기 하나뿐이다(`checkAndUpdateLocation`의 호출처가 이곳 하나). 분기는 장소 차단(`blockPoiForUser`)과 기록(`logAbusingEvent('gps_spoof_detected', { poi_id, reason, speed_kmh, daily_distance_km, lat, lng })`)을 하고 403을 돌려준다. 감지 때마다 마지막 위치를 새 값으로 갱신한다(`gps-detector.ts` 121~130줄)라서 같은 순간이동이 연달아 감지되지 않는다. 이미 막힌 장소(`isPoiBlocked`)는 감지 전에 403으로 끝난다. 지금까지 감지 기록은 0건이다(공용 DB `abusing_logs` 0행, 2026-10-21).
- **운영자가 볼 곳**: 어드민 `/admin/abusing`의 «장소 블록» 탭(`PoiBlockTable.tsx`)이 유저, 장소, 사유(`gps_spoof_detected (속도 N km/h)`), 차단 만료를 보여 준다. **`abusing_logs`를 읽는 어드민 화면은 없다**(운영 로직 16.7이 말한 «어뷰징 기록을 보는 화면»은 미구현). 그래서 알림은 장소 블록 탭을 가리킨다. 기록 화면은 이 티켓 범위 밖이다.
- **개인정보 규칙과의 관계**: 예약 작업 문서 4-6은 «리포트와 Slack 글에는 집계 수치만 남긴다. 닉네임·이메일·유저 ID 등 개인 식별 정보는 쓰지 않는다»라고 한다. 그런데 기존 대량 수령 경보 글은 유저 ID를 적고 있다(`describeMassEarn`). 사용자가 이 알림에도 유저 ID를 적기로 했으므로 **4-6의 적용 범위를 «에이전트 루틴이 올리는 리포트와 글»로 좁히고, 앱이 올리는 운영자용 알림은 운영자가 유저를 찾도록 유저 ID를 적는다**고 문서에 적는다(이 티켓의 문서 항목).
- **글 형식**: 기존 `formatStopSignalAlertMessage`의 머리 «중단 신호가 새로 걸렸어요»는 운영툴 중단 신호용이라 이 알림에 맞지 않는다. 같은 모듈의 `escapeSlackText`로 장소 이름을 거르는 새 형식 함수가 필요하다(장소 이름은 외부 장소 검색에서 온 값이다).
- **작은 어긋남**: `jam-web/.env.example`에 Slack 변수 3개가 없다(`04_PROJECT_SPEC.md` 환경변수 표에는 있다). 이 티켓에서 함께 맞춘다.

## 사용자 결정과 적용 기록 (2026-10-22)

1. **알림 방식**: **감지 즉시 앱에서 `#jam-alert`에 한 건**(추천). 대안은 매시 크론이 `abusing_logs`를 읽어 한 시간 요약 1건(최대 1시간 지연, 창·중복 처리 코드가 늘어 파일 5~6개), 에이전트 예약 루틴(출시 시점에 알림 없음)이었다.
2. **글 내용**: **유저 ID도 적는다**(대량 수령 경보와 같게). 추천은 유저 정보 없이 장소·시각·사유만 적는 것이었으나 사용자가 달리 정했다. 4-6과 어긋나는 점은 위 조사 결과대로 문서의 적용 범위를 정리해 푼다.

**묻지 않고 추천대로 정한 것(다르게 하라고 하지 않으면 이대로)**: (가) 시험 계정(`lib/env/test-accounts.ts`)도 제외하지 않는다(대량 수령 경보와 같다. 구현이 단순하고, 시험 계정의 GPS 조작은 드물다). (나) 같은 감지에 글은 한 건이다. 반복 알림 억제는 두지 않는다(감지 때마다 위치를 갱신하므로 같은 건이 반복되지 않는다). (다) 글은 해요체이고 좌표, 이메일, 토큰은 싣지 않는다. 보내기에 실패해도 픽업 응답(403)과 장소 차단·기록은 그대로다. (라) 알림은 `after()`로 응답 뒤에 보낸다(픽업이 Slack 응답을 기다리지 않는다).

## 구현 계획 (파일 단위, 카리나, 2026-10-22, 줄 위치는 시작 때 아현이 다시 확인한다)

1. **글 만들기와 보내기**: 신규 `jam-web/src/lib/abusing/gpsSpoofAlert.ts`(서버 전용)와 시험 `lib/abusing/__tests__/gpsSpoofAlert.test.ts`. `formatGpsSpoofAlertMessage({ userId, poiName, reason, speedKmh?, dailyDistanceKm?, blockHours })`가 글을 만든다. 예시(문구는 UX 가이드 §1.3 고정 용어와 해요체에 맞춰 아현이 다듬고 결과의 koreanCopy에 적는다):
   ```
   GPS 조작이 의심돼서 픽업을 거부했어요
   • 유저({userId}) · 장소 {장소 이름} · 속도 412km/h
   • 이 장소는 72시간 막았고 기록을 남겼어요. 어드민 어뷰징 관리의 장소 블록에서 확인한 뒤 운영자가 정지를 정해요
   ```
   사유가 하루 이동거리면 «하루 이동거리 3,200km»로 쓴다. 장소 이름은 `escapeSlackText`로 거르고 길면 자른다(`opsInbox/slack.ts`의 `safeField` 방식, 그 함수가 내보내지 않으면 같은 규칙으로 이 파일에 둔다). `alertGpsSpoof(input)`는 `postOpsSlack('alert', 글)`을 부르고 성공하면 true, 값이 없거나 실패하면 서버 로그(`[gps-spoof-alert]`)만 남기고 false이며 **던지지 않는다**(`massEarnAlert.ts`의 `alertMassEarnIfNeeded`와 같은 형태). 시험: 글에 유저 ID·장소·사유·차단 시간이 들어가고 좌표·이메일이 없음, 사유 두 가지, 장소 이름의 Slack 특수문자 걸러짐, `postOpsSlack`이 `'alert'`로 불림, 실패·`not_configured`·던짐을 삼킴.
2. **픽업 라우트 호출**: `jam-web/src/app/api/drops/[dropId]/pickup/route.ts` 107~143줄의 `gpsCheck.detected` 분기에서 장소 차단·기록 `try/catch` 뒤, 403 반환 앞에 `after(() => alertGpsSpoof({...}))`를 부른다(`next/server`의 `after`, 장소 이름은 이 함수 안의 `poiRaw`의 이름). 장소 차단·기록 저장이 실패해도 알림은 보낸다. 시험 `pickup/__tests__/route.test.ts`: 감지되면 `alertGpsSpoof`가 한 번 불리고 인자에 유저 ID·장소 이름·사유가 있다, 감지되지 않으면 안 불린다, 이미 막힌 장소(`isPoiBlocked`)는 안 불린다, 알림이 던져도 403과 장소 차단·기록 호출은 그대로다.
3. **환경변수 예시**: `jam-web/.env.example`에 `SLACK_BOT_TOKEN`, `SLACK_CHANNEL_JAM_ALERT`, `SLACK_CHANNEL_JAM_REPORT`를 더한다(값은 적지 않는다. 채널 ID의 원천은 `scheduled-jobs.md` Slack 알림 절이라고 주석으로 가리킨다).
4. **문서**: `docs/plan/jam2/10 JAM 2.0 서비스 운영 로직.md` 16.5절(운영자에게 알리는 방식을 «감지 즉시 앱이 `#jam-alert`에 올린다»로 구체화), `docs/plan/jam2/service-redesign/20 어뷰징과 밴.md` 4절·알림 서술(위와 같게, 정책의 뜻은 바꾸지 않는다), `.claude/skills/jam-work/references/scheduled-jobs.md` Slack 알림 절(앱이 올리는 글 목록에 «GPS 조작 의심»을 더하고, 4-6 개인정보 규칙의 적용 범위를 «에이전트 루틴이 올리는 리포트와 글»로 좁히며 앱이 올리는 운영자용 알림(대량 수령 경보, GPS 조작 의심)은 운영자가 유저를 찾을 수 있게 유저 ID를 적는다고 사용자 결정(2026-10-22)과 함께 적는다), `docs/service/prd/04_PROJECT_SPEC.md` 환경변수 표의 `SLACK_CHANNEL_JAM_ALERT` 용도, `docs/service/prd/admin-ui/ADMIN_PRD.md`의 어뷰징 절(알림과 장소 블록 탭 확인 흐름), `docs/plan/jam2/service-redesign/현재 서비스 비교.md`의 도둑 의심 제재 행(6-4 2회가 «운영자 알림은 별도 티켓»이라고 적은 곳을 이 티켓으로 갱신). 티켓 기록과 `docs/plan/` 진행 노트는 카리나 몫이다.
5. **하지 않는 것**: 에이전트 루틴 등록, 크론 추가, `abusing_logs`를 읽는 어드민 기록 화면, 자동 정지, 알림에 좌표·이메일을 싣는 일, DB 변경.

## 상세 요구사항

### 서비스/코드베이스 관점

- GPS 조작이 감지되면 `#jam-alert`에 알림이 한 번 뜬다. 같은 감지로 두 번 뜨지 않는다.
