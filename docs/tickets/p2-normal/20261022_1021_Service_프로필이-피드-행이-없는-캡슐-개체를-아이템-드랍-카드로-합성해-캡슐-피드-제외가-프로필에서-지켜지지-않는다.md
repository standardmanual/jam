# [Service] 프로필이 피드 행이 없는 캡슐 개체를 «아이템 드랍» 카드로 합성해 캡슐 피드 제외가 프로필에서 지켜지지 않는다

## 핵심 요약

- 요구사항: 티켓 `20261021_1249` 5회가 운영 로직 15.3(«캡슐을 열어 나온 아이템 배지는 피드에 올리지 않는다», 2026-10-10 사용자 결정)에 맞춰 캡슐 열기의 `item_dropped` 피드 기록을 없앴다. 그런데 프로필 서버 화면(`app/(main)/[username]/page.tsx` 201~208줄의 `actDropsQuery`와 318~324줄)은 `inventory_items.obtained_by = 'drop'`인 개체를 피드 행이 없으면 `item_dropped` 카드로 합성해 그린다. 캡슐로 얻은 개체도 `obtained_by`가 `'drop'`(마이그레이션 233)이라, 이제 피드 행이 없는 이 개체가 중복 제거에 걸리지 않고 프로필에 «아이템 드랍» 카드로 나타난다(이전에는 피드 행이 있어 «아이템 획득» 라벨이었다). 결정의 취지가 `/feed`에서만 이뤄지고 프로필에서는 어긋난 채 남았다. 합성 경로에서 캡슐 개체를 뺀다.
- 구현 계획: ① 캡슐 개체를 가르는 기준을 정한다. `item_issue_log.route = 'capsule'`(마이그레이션 227, `inventory_item_id`로 개체와 잇는다)가 후보다. 합성 쿼리의 개체 id 목록에서 `route = 'capsule'`인 개체를 빼는 조회를 더한다(개체 수는 `limit(100)`이라 조회 비용은 작다). ② 시험(프로필 서버 화면은 지금 시험이 없으므로 합성 로직을 순수 함수로 빼서 시험): 캡슐 개체는 합성에서 빠지고, 동기화로 받은 개체와 POI 드랍은 그대로다. ③ 운영 로직 15.3과 데이터 모델의 서술이 코드와 맞는지 확인한다.
- 관련 파일: `jam-web/src/app/(main)/[username]/page.tsx` 201~208줄·318~324줄(민지 보고, 카리나가 코드로 확인했다), `jam-web/supabase/migrations/227_item_issue_policy_and_log.sql`, `jam-web/supabase/migrations/233_capsule_open.sql`, `jam-web/src/lib/capsule/open.ts`(`skipFeed`).

## 배경 / 문제 정의

6-3 5회 게이트(민지, 주의)가 발견했다. 계획 밖 파일이라 5회의 FAIL 사유로 삼지 않았지만, 후속 티켓이 없으면 운영 로직 15.3의 문장이 프로필에서 계속 거짓이다. 옛 캡슐 개체의 기존 피드 행(`item_dropped`)은 그대로 남아 있다(5회가 지우지 않기로 했다).

발견: 2026-10-22 티켓 20261021_1249 5회 게이트.

## 상세 요구사항

### 서비스/코드베이스 관점

- 동기화로 받은 개체의 합성 카드(피드 윈도우 밖 보정)는 그대로 둔다.
- 옛 캡슐 개체의 기존 피드 행을 지울지는 이 티켓에서 사용자에게 묻는다(지우면 이력이 사라지고, 두면 과거 항목이 남는다).

- [ ] 동기화 개체와 POI 드랍의 합성은 그대로다
