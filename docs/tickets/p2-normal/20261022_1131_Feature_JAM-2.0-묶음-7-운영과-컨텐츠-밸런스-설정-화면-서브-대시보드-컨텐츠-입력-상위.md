# [Feature] JAM 2.0 묶음 7: 운영과 컨텐츠 (모은 밸런스 설정 화면, 밸런스 서브 대시보드, 트라이브 컨텐츠 일괄 입력, 컬렉션 4등급 켜기, 상위)

## 핵심 요약

- 요구사항: 운영 로직 19장을 구현한다. (1) 지금 어드민에 흩어진 밸런스 설정을 한 화면으로 모으고 컨텐츠별 구역으로 나눈다(19.1). (2) 밸런스 서브 대시보드로 지표와 목표를 보고 문제가 되는 수치를 바로 조정한다(19.2). (3) 트라이브 컨텐츠(컬렉션 50개, 아이템 배지 450종 × 4등급, 단서 레시피 20개, 등급 올리기 레시피)를 일괄 입력한다(19.3). (4) 컬렉션 4등급을 켜는 화면을 만든다. 서비스 옵션 O1·O2·O9·O10의 흡수분 확인과 티켓 `20260930_1503`의 ⑬(컬렉션별 아이템 획득 경로)도 여기서 처리한다.
- 구현 계획: 하위 티켓 9개를 아래 표의 순서로 진행한다. 설정 화면 묶음(7-1~7-5), 컨텐츠 묶음(7-6, 7-7), 독립 티켓(7-8), 문서(7-9)다. 회차는 모두 11회쯤으로 본다. 각 하위 티켓은 시작 때 사용자 결정을 질문하고 파일 단위 계획을 옮겨 쓴다. DB 실행은 SQL 파일을 보여 드린 뒤 사용자 승인으로만 한다.
- 관련 파일: 운영 로직 `docs/plan/jam2/10 JAM 2.0 서비스 운영 로직.md` 19장(1660줄 근처), 상위 티켓 `20261016_2335`, 흩어진 옛 설정 화면 `jam-web/src/app/admin/`의 `drop-policy`·`ambient-drop`·`inventory-policy`·`combine-policy`·`abusing`·`ops-settings`(혜린 조사(2026-10-22), 카리나가 직접 확인하지는 않았다).

## 배경 / 문제 정의

묶음 0~6의 구현은 끝났고 묶음 6은 사용자의 staging 확인만 남았다. 밸런스 수치를 코드 수정 없이 바꾸는 화면과 새 컨텐츠 입력이 없으면 정식 오픈 전에 수치를 맞추거나 컨텐츠를 채울 수 없다. 새 설정 표(`jam_policy`, `capsule_policy`, `capsule_chapter_costs`, `chapter_definitions`, `chapter_score_rules`, `item_book_tier_default_rewards`)는 값을 바꾸는 데 마이그레이션이 필요 없지만 편집 화면이 없다(혜린 조사(2026-10-22), 카리나가 직접 확인하지는 않았다).

## 순서와 병렬

- 설정 묶음: 7-1이 먼저다. 7-1은 티켓 `20261022_0938`(옛 객체 참조 코드 정리)의 1회 머지 뒤에 시작한다(둘 다 어드민 메뉴 파일 `adminNavItems.ts`를 고치고, 0938이 옛 드랍 정책 화면을 지운다). 그 뒤 7-2, 7-3, 7-4는 병렬로 돌릴 수 있다(메뉴 파일 충돌만 조정한다). 7-5는 7-2 뒤이고, 7-5 2회(획득 경로)는 7-7 적용 뒤다.

## 사용자 결정 (2026-10-22)

- **분해안**: 위 9개 하위 티켓으로 나눈다(사용자 승인).
- **새 컨텐츠는 옛 컬렉션에 덮어쓴다**(혜린 추천은 «새로 넣고 옛 것은 오픈 직전에 끄기»였으나 사용자가 덮어쓰기를 골랐다). 운영 로직 19.3의 «자리가 확정된 기존 컬렉션은 이름을 되도록 살리고 설명은 새로 쓴다, 쓰지 않는 컬렉션은 비활성화한다»와 같은 방향이다. 공용 DB라 고치는 즉시 프로덕션 화면에 새 이름과 설명이 보인다(공용 DB에는 유저 8명이 있고 아이템 배지를 받은 유저는 4명이다).
- **새 트라이브와 컬렉션은 넣자마자 켠다**(혜린 추천은 «꺼 둔 채 넣고 확인할 때만 켜기»였다). 프로덕션 온보딩 화면에도 바로 보일 수 있다.
- **새 컬렉션 50개는 처음부터 4등급 방식으로 켠 채 넣는다**(혜린 추천과 같다).
- **옛 아이템 배지 행은 모두 덮어쓴다**(7-6 시작 전 조사 뒤 2026-10-22). 이어받는 44개 컬렉션의 옛 행 396개를 Common 행으로 덮어쓰고 나머지 등급은 새 행으로 넣는다. 보유 1,030개와 장착 42칸의 내용이 바뀐다(자세한 계산은 7-6 티켓 「사용자 결정」).
- **7-6의 실행 순서**(2026-10-22, 7-6 시작 전 결정 2~4번): 새 트라이브 5개는 비활성으로 먼저 등록하고, 덮어쓰기와 새 트라이브로 옮기기를 한 번의 DB 적용으로 하며, 그 직후 트라이브를 켠다. 이어받지 않는 컬렉션 56개의 비활성화는 오픈 직전까지 그대로 둔다.
- **두 결정이 만나는 곳**: 덮어쓰는 컬렉션에 이미 장착된 개체가 있으면 4등급을 켤 때 처리가 필요하다(「꽂힌 등급」 정리). 그래서 켜기 전 조회를 만드는 7-8을 7-6의 DB 적용보다 먼저 끝낸다. 7-6은 시작 때 덮어쓸 컬렉션의 장착 기록부터 조사한다.

## 열려 있는 질문 (해당 티켓을 시작할 때 묻는다)

1. **포인트 일괄 값을 기존 배지에 적용할 시점**(7-4): 혜린 추천은 새 배지는 기본값을 바로 쓰고, 기존 배지는 오픈 직전 SQL(마이그레이션 244와 같은 때)에 적용하는 것이다. 지금 바꾸면 프로덕션 유저가 받는 포인트가 오늘부터 달라진다.
2. **5-6 계열(액티비티 배지)의 이름과 설명 원고**(7-9에서 정리): 판정 키는 있으나 원고에 이름과 설명이 없어 이 계열이 빈 채 출시될 수 있다. 혜린 추천은 오픈 전에 윈터가 쓰고 입력하는 것이다.

## 겹치는 티켓 처리

- `20261018_1816`(액티비티 배지 55개 계열 입력과 비활성화)과 `20261019_0542`(판정 로직이 없는 12계열)는 묶음 4 소속으로 두고 이 묶음으로 옮기지 않는다. 운영 로직 19.3의 «액티비티 배지 55개 계열 입력» 문장은 «묶음 4 몫»으로 고쳤다. 이 묶음이 가져오는 것은 5-6 계열 입력, 244·245·248 적용 순서 기록, 7-4의 포인트 값 대조뿐이다. 1816은 1회 머지와 244·245 SQL 작성, 롤백 실측까지 끝났고, 0542는 246·247 적용과 248 SQL 작성까지 끝났으며 남은 일은 오픈 직전 적용(244, 245, 248 순서)이다(혜린 조사(2026-10-22), 카리나가 직접 확인하지는 않았다).
- 옵션 O1(페이스 하한)·O2·O9·O10은 이미 묶음 5·3·2로 흡수됐다고 기록돼 있으나 처리했다는 근거는 O1은 티켓 `20261019_1312`(미션 조건 넓히기)가 일부를 처리했고 페이스 하한은 확인하지 못했으며, O2는 티켓 `20261019_1445`의 검증까지만 확인했다. O9의 컬렉션 등급 칩과 O10은 처리한 근거를 찾지 못했다. 나머지는 사용자가 staging에서 보고 필요하면 7-8이나 별도 티켓으로 처리한다.
- 티켓 `20260930_1503`의 ⑬은 7-5 2회로 흡수한다. ⑫는 계속 보류한다.

## 위험과 모르는 점

- 등급 올리기 레시피는 1,350건에 칸 5개, 후보 90종이라 행이 약 60만 개다. 값을 직접 쓴 SQL로는 실행하기 어렵고 DB 안에서 `INSERT … SELECT`로 만들어야 한다. 믹스 화면과 어드민 목록의 성능은 확인하지 못했다.
- 1,800행 SQL이 한 번 실행 한도를 넘는지 확인하지 못했다. 트라이브별 파일로 나눈다.
- 시스템 드랍이 `ambient_drop_config`의 어느 열을 실제로 쓰는지 확인하지 못했다(`ambient_drop_policy`는 코드에서 읽히지 않는다).
- 대시보드의 지표 목표는 시뮬레이터 실측이 없어 검증하지 못했고, 가입자가 8명이라 오픈 전에는 검증할 수 없다. 걷기·자전거·등산은 실측이 거의 없어 통념으로 잡은 값이다.
- 확률 값을 바꾸기 전에 공지하는 수단은 6-4도 확인하지 못했다. 화면은 확인창으로만 경고한다.

## DB 규칙과의 관계

- 새 설정 표는 티켓 227 기록상 옛 프로덕션 코드가 읽지 않아 부딪치지 않는다(6-4는 미확인).
- 옛 표(`drop_policy`, `ambient_drop_config`, `inventory_policy`, `combine_policy`, `abusing_policy`, `ops_rules`)는 새 화면이 같은 열을 같은 뜻으로 읽고 쓰므로 스키마 변경이 없다. 옛 열과 표(`drop_policy`, 배율 8열, `all_random`)는 화면에서 빼기만 하고 삭제는 출시 뒤 SQL(266~269, 0938)에 맡긴다.
- 변경 이력은 옛 표에 트리거를 달지 않고 저장 API가 새 이력 표에 쓴다. 출시 전에는 옛 어드민도 같은 표를 쓰므로 마지막 저장이 이긴다. 인벤토리 저장은 기존 `set_inventory_max_slots` 경로를 유지한다.
