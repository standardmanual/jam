# [Admin] JAM2 모은 밸런스 설정 화면의 틀과 변경 이력: 잼·동기화·캡슐 구역 (묶음 7, 7-1)

## 핵심 요약

- 요구사항: 운영 로직 19.1의 모은 설정 화면의 틀을 만든다. 컨텐츠별 구역(잼, 동기화, 캡슐, 잠긴 아이템 배지, 인벤토리, 컬렉션과 믹스, 시스템 드랍, 챕터, 배지와 포인트, 어뷰징) 가운데 이 티켓에서는 틀과 **잼·동기화·캡슐 구역**을 만든다. 서버 검증, 확률 값을 바꿀 때의 확인창, 변경 이력(누가 언제 무엇을 어떤 값에서 어떤 값으로 바꿨는지)을 포함한다.
- 구현 계획: 1회 화면 틀, 서버 검증, 변경 이력 표(마이그레이션 271, 추가만)와 저장 API 공용 경로. 2회 잼·동기화·캡슐 구역(`jam_policy`, `capsule_policy`, `capsule_chapter_costs`)과 확률 변경 확인창. 변경 이력은 옛 표에 트리거를 달지 않고 저장 API가 새 이력 표에 쓴다.
- 관련 파일(시작 때 아현이 줄 위치를 확인한다): `jam-web/src/app/admin/`의 `adminNavItems.ts`(메뉴, 0938과 충돌), 새 설정 표 `jam_policy`·`capsule_policy`·`capsule_chapter_costs`(마이그레이션 220~234), 운영 로직 19.1과 18장(확률 변경 때 확률 안내 페이지 반영과 공지)(혜린 조사(2026-10-22), 카리나가 직접 확인하지는 않았다).

## 배경 / 문제 정의

밸런스 수치를 어드민 설정으로 두고 코드 수정 없이 바꾸는 것이 19.1의 요구다. 새 설정 표는 편집 화면이 없다. 화면은 shadcn/ui 표준을 따르고, 구성과 나누는 단위는 이 티켓의 화면 설계에서 정한다. 어드민 화면은 MODULAR 적용 대상이 아니고 채원의 판정 대상도 아니다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 확률이 들어간 값을 바꾸면 확률 안내 페이지에 함께 반영되는지 확인하고, 바꾸기 전 확인창으로 경고한다. 공지하는 수단은 6-4도 확인하지 못했으므로 확인창까지만 한다.
- 동기화 구역은 0개로 둘 수 있는 값을 허용한다(운영 로직 19.1 표).
- 믹스 칸 수(5)와 등급 올리기 재료 수(5)는 코드에 두고 화면에 올리지 않는다.

**코드 현황**

- 세 표를 읽는 정식 경로는 `lib/jam/policy.ts`의 `getJamPolicy`와 `lib/capsule/policy.ts`의 `getCapsulePolicy`다. **캐시가 없고 매 요청 읽는다**(칸마다 `VALIDATORS`로 검사하고 비정상이면 기본값으로 대체). 쓰는 경로는 **둘 다 없다**(편집 화면도 API도 없음). `capsule_chapter_costs`는 앱 코드가 아니라 DB 함수 `capsule_get_or_create`가 읽는다.
- 확률 안내 페이지(`/probability`, `lib/probability/disclosure.ts`)가 같은 표를 `force-dynamic`으로 매번 읽는다. 그래서 설정을 바꾸면 **페이지는 저절로 바뀐다**(운영 로직 18.3 «설정을 바꾸면 페이지도 함께 바뀌게»가 이미 충족된다). 페이지가 읽는 칸이 곧 «확률 안내에 반영되는 칸»이다: 캡슐 `guaranteed_count`·`bonus_count`·`bonus_probability`·`other_tribe_probability`·`rarity_*`·`pity_epic_threshold`, 잼 `sync_item_*`·`sync_rarity_*`·`common_streak_threshold`·`locked_roll_probability`. 강도 배율, 대량 수령 경보 기준, 퀘스트 전 양, 챕터별 채울 양은 페이지에 없다.
- 설정 화면의 선례는 운영 설정(`/admin/ops-settings`)이다. **세로 구역 + 구역 이동 링크(`OpsSettingsNav`) + 구역 틀(`OpsSettingsSection`) + 구역마다 `Suspense`로 따로 읽기**이고, 구역 추가는 배열 한 줄(`sections.tsx`)과 본문 컴포넌트 하나다. 확인창은 `OpsConfirmDialog`, 변경 비교는 `OpsDiffLines`가 있다. 옛 정책 저장 API(`api/admin/combine-policy` 등)는 `getAdminUser()`로 거르고 칸마다 숫자 검증을 한 뒤 갱신한다. 이력은 남기지 않는다.
- `ops_rules`의 저장 선례는 응답에 관리자 사용자 ID를 싣지 않고 바꾼 적이 있는지만 알린다. 이 티켓은 «누가 바꿨는지»가 요구라 표시 이름(username)만 보인다(가정 다).

## 사용자 결정과 적용 기록 (2026-10-22)

1. **화면 구성**: **한 화면에 구역을 세로로 쌓고 구역마다 따로 읽고 저장한다**(추천). 맨 위에 구역 바로가기가 따라다닌다. 한 구역을 저장해도 다른 구역은 건드리지 않고, 7-2~7-4가 구역 하나씩 더하면 되어 서로 충돌이 거의 없다.
2. **변경 메모**: **항상 선택**이다(추천은 «확률 값을 바꿀 때만 필수»였으나 사용자가 «항상 선택»을 골랐다). 어떤 값을 바꿔도 메모는 비워도 저장된다. 확률 안내에 반영되는 값을 바꿀 때는 확인창에서 한 번 더 확인한다(메모 칸은 같이 있다).
3. **잼 구역에 대량 수령 경보 기준 3칸을 넣는다**(추천). 운영 로직 19.1 표에는 없지만 같은 표의 칸이라 구현 부담이 작고 코드 수정 없이 고칠 수 있다.

**묻지 않고 추천대로 정한 것(다르게 하라고 하지 않으면 이대로)**

(가) **2회로 나눈다.** 1회는 틀, 변경 이력 표(마이그레이션 285), 공용 읽기·저장 모듈, 메뉴, **잼 구역**(가장 단순한 구역으로 틀을 끝까지 검증한다). 2회는 **동기화 구역과 캡슐 구역**(챕터별 채울 양 포함)과 확률 확인창. 회차마다 게이트를 돌리고 `planOnlyWaiver`를 쓴다.
(나) 새 화면은 `/admin/balance`, 메뉴 이름은 «밸런스 설정»이고 «정책 및 밸런스» 묶음의 맨 위에 둔다. 믹스 정책·인벤토리 최대치·앰비언트 드랍·어뷰징 관리는 7-3이 옮길 때까지 그대로다.
(다) **변경 이력 표(이름은 아현이 확정)**: 저장 한 번에 한 줄이다. 구역 키, 바꾼 칸 목록(칸 이름, 이전 값, 새 값)을 JSON으로, 메모(선택, 200자), 확률 안내에 반영되는 칸이 포함됐는지, 바꾼 어드민(`users.id`, 삭제 시 `SET NULL`), 시각. RLS를 켜고 정책을 두지 않으며 `anon`·`authenticated` 권한을 회수한다(`user_tribe_changes` 선례). 화면에는 어드민의 **표시 이름(username)만** 보이고 ID와 이메일은 싣지 않는다.
(라) **저장 경로**: `PUT /api/admin/balance/[section]`, 본문 `{ values, expectedUpdatedAt, note? }`. 서버가 ① 어드민을 확인하고 ② 칸마다 검증하며(`VALIDATORS` 재사용, 정수·범위, 등급 확률 4칸의 합 100±0.001, DB의 CHECK와 같은 기준) ③ 현재 행을 읽어 **바뀐 칸만** 계산하고(바뀐 칸이 없으면 400 «바뀐 값이 없어요») ④ `updated_at`이 읽은 때와 같을 때만 갱신한다(다르면 409 «다른 사람이 먼저 바꿨어요. 새로 불러온 뒤 다시 바꿔 주세요»). `updated_at`은 저장 때 직접 `now()`로 올린다(갱신 트리거가 없다). ⑤ 변경 이력 한 줄을 쓴다. 이력을 쓰지 못하면 방금 갱신을 이전 값으로 되돌려 보고(되돌리기까지 실패하면 로그에 남기고 오류로 답한다), 응답에 DB 오류 원문을 싣지 않는다. 읽기는 `GET`으로 현재 값, `updated_at`, 최근 이력 몇 건을 돌려준다.
(마) **확률 확인창**: `lib/probability/disclosure.ts`가 읽는 칸 목록을 내보내(`JAM_COLUMNS`·`CAPSULE_COLUMNS` 등 단일 원천) 저장 때 «확률 안내 반영 칸이 바뀌었는가»를 가른다. 바뀌었으면 확인창에 변경 전·후와 «확률 안내 페이지에 바로 반영돼요. 바꾸기 전에 공지가 필요한지 확인해요»를 보이고 확인해야 저장된다. 공지 수단은 6-4도 확인하지 못해 확인창까지만 한다. 공용 DB를 staging과 프로덕션이 함께 쓰므로 **저장 즉시 프로덕션에 반영된다**는 안내도 확인창에 넣는다.
(바) 동기화 구역은 **0개도 허용**한다(확정 개수 0, 보너스 횟수 0). 확정과 보너스가 모두 0이면 «아이템 배지가 나오지 않아요» 경고를 보이되 막지는 않는다.
(사) 믹스 칸 수(5)와 등급 올리기 재료 수(5)는 화면에 올리지 않는다(코드).
(아) `common_streak_threshold`와 `locked_roll_probability`는 동기화와 캡슐이 한 값이라 **동기화 구역에서 편집**하고 캡슐 구역에는 «동기화와 같은 값이에요» 안내만 둔다. 잠긴 아이템 배지 등급별 최소값(`locked_min_*`)은 7-2 구역이다.
(자) 챕터별 채울 양(`capsule_chapter_costs` 10행)은 값만 바꾼다. 챕터 번호를 늘리거나 줄이지 않는다(챕터 더하기는 7-2).
(차) 칸 옆에 기본값(코드 `DEFAULT_*_POLICY`)을 작게 보인다. «기본값으로 되돌리기» 버튼은 만들지 않는다.
(카) 마이그레이션 285는 새 표만 더한다(추가만, 되돌림 SQL 포함). 아현은 파일만 쓰고 **적용은 사용자 승인 뒤 카리나가** 한다(롤백 실측 뒤). 적용은 DB 먼저, 코드 push는 나중이다(코드가 먼저 나가면 이력 쓰기가 실패해 저장이 막힌다).
(타) **로컬 확인은 읽기만 한다.** 화면이 열리고 값과 기본값, 이력 목록이 보이는지 본다. 프로덕션이 쓰는 값을 바꾸는 «저장»은 누르지 않고 시험으로 확인한다.
(파) 어드민 화면이라 채원 판정과 사후 리뷰는 없다(MODULAR 적용 대상 아님). 유형은 `admin`, 표준 경로다. 새 컴포넌트는 shadcn/ui와 기존 `OpsSettings*`·`OpsConfirmDialog`·`OpsDiffLines`를 재사용한다.
