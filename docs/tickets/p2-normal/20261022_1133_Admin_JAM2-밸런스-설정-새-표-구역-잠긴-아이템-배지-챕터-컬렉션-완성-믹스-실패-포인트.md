# [Admin] JAM2 밸런스 설정 새 표 구역: 잠긴 아이템 배지, 챕터, 컬렉션 완성·믹스 실패 포인트 (묶음 7, 7-2)

## 핵심 요약

- 요구사항: 7-1이 만든 설정 화면 틀(`/admin/balance`)에 구역 셋을 더한다. (1) 잠긴 아이템 배지의 등급별 최소값(`jam_policy.locked_min_*`), (2) 컬렉션과 믹스(등급별 완성 포인트 `item_book_tier_default_rewards`, 믹스 실패 포인트 `combine_policy.fail_reward_points`), (3) 챕터(챕터별 필요 누적 점수 `chapter_definitions`, 활동별 점수·주간 상한·상한 초과 비율 `chapter_score_rules`). 사용자 결정(2026-10-22)으로 **챕터 더하기는 후속 티켓 `20261022_1718`로 뺐고**, 옛 «믹스 정책» 화면(`/admin/combine-policy`)은 새 구역으로 옮기며 걷어낸다.
- 구현 계획: 2회. 1회 = 여러 표를 한 구역으로 저장하는 공용 모듈, 잠긴 아이템 배지 구역, 컬렉션과 믹스 구역, 옛 믹스 정책 화면 걷기. 2회 = 챕터 구역. DB 변경은 없다.
- 관련 파일(시작 때 아현이 줄 위치를 확인한다): `jam-web/src/lib/admin/balance/`(7-1의 연결 객체 `BalanceSectionBinding`, 공용 저장 `saveBalanceSection`, 레지스트리 `sections.tsx`, 여러 행 저장의 선례 `capsule.ts`), `jam-web/src/components/admin/balance/`, 옛 믹스 정책 `jam-web/src/app/admin/combine-policy/`와 `jam-web/src/app/api/admin/combine-policy/route.ts`, 운영 로직 7.4·8.6·12.4절. 규모는 시작 전 조사로 다시 잡아 약 27파일 2,600줄이다.

## 배경 / 문제 정의

새 설정 표는 편집 화면이 없다. 챕터는 «챕터 3»처럼 숫자로만 표기하고 이름은 두지 않는다(2026-10-21 결정).

## 상세 요구사항

### 서비스/코드베이스 관점

- DB 변경은 없다. 값 검증(음수, 순서가 거꾸로인 누적 점수 등)은 서버에서 한다.
- 챕터 더하기(새 챕터 행을 추가하는 동작)는 이 티켓에서 뺐다. 후속 티켓 `20261022_1718`이 맡는다. 이 티켓의 챕터 구역은 지금 있는 챕터의 값만 바꾼다.

## 시작 전 조사 결과 (카리나, 2026-10-22, 코드 읽기와 공용 DB 읽기 전용 확인. 아무것도 바꾸지 않았다. 줄 위치는 시작 때 아현이 다시 확인한다)

**다른 세션과 겹침**

- 열려 있는 다른 세션은 «5-7»(유저 화면: 프로필 챕터, 미션, 포인트) 하나이고, 5-7은 3회까지 staging에 올라가 사용자 확인만 남았다. 어드민 밸런스 파일과 겹치지 않는다. 작업 폴더의 미커밋 변경은 팀 규칙 문서(`.claude/`, `CLAUDE.md`, `docs/agents/contract.json`, 정책 변경 티켓)라 겹치지 않는다.
- 이미 올라간 정책 대시보드(티켓 `20261022_1631`, 커밋 `bced619dd`)가 겹친다. 믹스 실패 포인트 카드의 `relatedAdminUrl`이 옛 화면(`/admin/combine-policy`)을 가리키고, `PUT /api/admin/policy-dashboard/field`가 `jam_policy`·`combine_policy` 등을 **변경 이력, 동시 수정 검사, 확률 확인창 없이** 직접 쓴다. 2026-10-22 17:08 KST에 `jam_policy` 이력 한 줄(`intensity_light` 2 → 1)이 있는데 그 앞의 1 → 2 변경은 이력에 없다(`jam_policy`를 쓰는 경로는 이 대시보드 라우트와 7-1 구역뿐). 이 문제는 별도 티켓 `20261022_1717`로 나눴다.

**지금 데이터 규모**: 챕터에 오른 유저 0명(`user_chapters`·`chapter_ups` 0행), 잠긴 개체 0개, 여는 양을 따로 정한 배지 0개, 컬렉션별 등급 보상 행 0건(모두 기본값을 쓴다), 4등급을 켠 컬렉션 10개. 값을 바꿔도 지금은 영향받는 유저가 없다. 설정 표에는 읽기 캐시가 없어 저장하면 바로 반영된다.

**설계에 쓰는 사실**

1. 설정 표(`jam_policy`·`capsule_*`·`chapter_*`·`item_book_tier_default_rewards`)에는 갱신 트리거가 없어 저장이 `updated_at`을 직접 올려야 한다. 7-1의 캡슐 구역이 «여러 행 조건부 갱신 + 중간 실패 시 되돌림»을 구현해 두었지만 캡슐 전용 코드라 새 구역이 쓰려면 공용 모듈로 뽑아야 한다.
2. `chapter_score_rules.weekly_cap`은 NULL이 «상한 없음»이다. 7-1 공용 폼은 숫자 칸만 다루므로 «0 = 상한 없음»으로 입력받아 NULL로 저장한다(DB에서 상한 0을 일부러 둘 일은 없다). 상한 칸이 필요한 까닭은 운영 로직 12.2절의 «드랍·픽업 5점에 상한이 없어 반복하면 점수가 쌓이는 틈»을 이 화면에서 막을 수 있어야 하기 때문이다.
3. 챕터 필요 점수를 낮추면 이미 점수가 넘은 유저는 바로 오르지 않고 **다음에 점수가 쌓일 때** 오른다(`chapter_add_score`만 챕터를 올린다). 챕터는 내려가지 않는다.
4. `user_chapters`·`chapter_ups`의 외래키가 `chapter_definitions`를 가리켜 유저가 있는 챕터는 지울 수 없다. 그래서 줄이기는 만들지 않는다. 7-1 캡슐 구역은 챕터 행을 1~10으로 고정해 읽는다(마지막 행보다 높은 챕터는 SQL이 마지막 행의 양을 쓴다, 마이그레이션 234).
5. 이 티켓의 칸 가운데 확률 안내 페이지(`/probability`)가 읽는 칸은 없다. `locked_roll_probability`는 동기화 구역이 맡는다. 확인창은 쓰지 않는다.
6. «챕터 점수»(`chapter_score_rules.collection_complete_*` 100·200·400·800)와 «포인트»(`item_book_tier_default_rewards` 100·200·400·800)는 값이 같지만 다른 설정이다. 화면 문구에서 구분한다.
7. 칸 검증 기준: 최소값 네 칸은 `lib/jam/policy.ts`의 `VALIDATORS`(정수 1 이상)가 있고, 믹스 실패 포인트는 0 이상 정수다. 컬렉션 기본 보상은 마이그레이션 222의 CHECK(0 이상)가 기준이고, 0이면 지급을 생략한다.

## 사용자 결정과 적용 기록 (2026-10-22)

1. **챕터 더하기**: 값 바꾸기까지만 하고 더하기는 뒤로 미룬다. 챕터 10에 닿는 데 기준 유저가 12.5달쯤 걸려 챕터 11이 필요해지는 때는 빨라야 1년 뒤라서다. 후속 티켓 `20261022_1718`(P3)을 만들었다.
2. **이미 오른 유저**: 더하기와 값 바꾸기만 두고 줄이기는 만들지 않는다. 이미 오른 유저는 내려가지 않고, 낮춘 기준은 그 유저가 다음에 점수를 쌓을 때부터 적용된다. 챕터 구역에 이 안내 문장을 둔다.
3. **옛 «믹스 정책» 화면**: 새 구역으로 옮기고 옛 화면(페이지, 폼, API)과 메뉴 항목을 걷어낸다. 정책 대시보드 믹스 실패 포인트 카드의 `relatedAdminUrl` 한 줄은 새 구역 링크로 바꾼다.
4. **정책 대시보드의 이력 우회**: 별도 티켓 `20261022_1717`(P2)로 수정 칸을 «밸런스 설정에서 바꾸기» 링크로 바꾼다. 이 티켓은 대시보드 파일을 `relatedAdminUrl` 한 줄 말고는 건드리지 않는다.

## 가정 (카리나, 구현 시작 전 사용자가 바로잡을 수 있다)

- (가) 구역 키와 순서: `locked`(잠긴 아이템 배지), `collection`(컬렉션과 믹스), `chapter`(챕터). 운영 로직 19.1 표의 순서(캡슐, 잠긴 아이템 배지, 인벤토리(7-3), 컬렉션과 믹스, …, 챕터)에 따라 레지스트리에 놓는다.
- (나) 잠긴 아이템 배지 구역은 `jam_policy`의 최소값 네 칸만 편집한다. 잠길 확률(`locked_roll_probability`)은 동기화 구역에서 바꾸므로 여기에는 안내와 동기화 구역 링크만 둔다(캡슐 구역의 «동기화와 같은 값이에요» 방식).
- (다) 최소값은 1 이상 정수이고 등급 사이 순서는 검사하지 않는다(운영 로직 7.4의 «등급마다 두 배»는 기본값이지 규칙이 아니다).
- (라) 최소값을 올렸을 때 배지에 따로 정한 값이 새 최소값보다 낮은 경우: 저장을 막지 않고 안내 문장만 둔다(여는 양은 배지 값이 우선이다, `resolveUnlockRequired`). 지금 따로 정한 배지는 0개다.
- (마) 컬렉션 구역의 칸은 등급별 완성 포인트 네 칸(0 이상 정수)과 믹스 실패 포인트 한 칸(0 이상 정수)이다. 컬렉션마다 따로 정한 값이 있으면 그 값이 먼저이고, 이미 받은 보상은 바뀌지 않는다는 문장을 화면에 둔다. 0은 지급 생략이다.
- (바) 챕터 구역은 필요 누적 점수를 챕터 2~10만 편집한다(챕터 1은 0으로 고정, 읽기만). 앞 챕터보다 커야 하고(같거나 작으면 저장 안 됨) 활동별 점수·주간 상한·초과 비율은 12종 모두 편집한다. 챕터 11 이상 행이 생겨도 읽지도 쓰지도 않는다(7-1 캡슐 구역과 같은 방식, 더하기는 후속 티켓).
- (사) 행 단위 저장: 구역의 수정 시각은 그 구역이 읽는 모든 행의 `updated_at` 가운데 가장 늦은 것이고, 행마다 «읽은 수정 시각이 같을 때만» 갱신하며 중간에 막히면 이미 쓴 행을 되돌린다. 공통 부분은 새 모듈 `rowwise.ts`로 뽑고 7-1 캡슐 구역 코드는 건드리지 않는다(캡슐도 옮길지는 나중에 정한다).
- (아) 변경 이력의 칸 이름: 잠긴 `locked_min_epic` 형식, 컬렉션 `default_reward:epic`과 `fail_reward_points`, 챕터 `required:3`과 `rule:jam_earned:points`·`rule:jam_earned:cap`·`rule:jam_earned:ratio`. 화면 칸 이름은 한국어 라벨이다.
- (자) 챕터 구역의 기본값 표기는 마이그레이션 221 시드를 코드 상수로 두고 시험이 시드 SQL과 대조한다(7-1 캡슐의 `CAPSULE_CHAPTER_DEFAULT_FILL` 방식). 컬렉션 구역 기본값은 마이그레이션 222와 `DEFAULT_COMBINE_POLICY`, 잠긴 구역은 `DEFAULT_JAM_POLICY`를 쓴다.
- (차) 확률 안내에 반영되는 칸이 없으므로 모든 칸의 `affectsDisclosure`는 `false`이고 확인창은 뜨지 않는다. 메모는 7-1과 같이 항상 선택이다.
- (카) `lib/combine/policy.ts`의 `updateCombinePolicy`는 정책 대시보드 저장 라우트가 쓰므로 남긴다(`20261022_1717`이 라우트를 지울 때 함께 정리한다).
