# [Admin] JAM2 밸런스 설정 옛 화면 이전: 인벤토리, 시스템 드랍, 어뷰징 기준값 (묶음 7, 7-3)

## 핵심 요약

- 요구사항: 옛 설정 화면 가운데 인벤토리(`admin/inventory-policy`), 시스템 드랍(`admin/ambient-drop`), 어뷰징(`admin/abusing`)의 기준값을 모은 설정 화면의 구역으로 옮긴다. 운영 설정(`admin/ops-settings`, `ops_rules`)은 링크만 둔다. 옛 열과 표(`drop_policy`, 어뷰징 배율 8열, `all_random`)는 화면에서 빼기만 하고 삭제는 출시 뒤 SQL(266~269, 티켓 `20261022_0938`)에 맡긴다.
- 구현 계획: 3회(1회 인벤토리, 2회 어뷰징, 3회 시스템 드랍). 각 구역을 같은 열을 같은 뜻으로 읽고 쓰게 옮기고(스키마 변경 없음), 옛 화면의 기준값 부분을 지운다. 인벤토리 화면은 통째로, 어뷰징은 «정책 설정» 탭만, 시스템 드랍은 숫자 칸만 지운다. 인벤토리 저장은 기존 `set_inventory_max_slots` 경로를 유지한다. 자세한 파일 목록은 아래 「구현 계획 (파일 단위)」.
- 관련 파일(시작 때 아현이 확인한다): 어드민 화면 폴더 inventory-policy(1회에서 삭제), `ambient-drop`, `abusing`, `ops-settings`, 표 `inventory_policy`·`ambient_drop_config`·`abusing_policy`·`ops_rules`(혜린 조사(2026-10-22), 카리나가 직접 확인하지는 않았다). 규모 약 20파일 1,400줄.

## 배경 / 문제 정의

출시 전에는 옛 어드민도 같은 표를 쓰므로 두 화면이 같은 값을 동시에 바꾸면 마지막 저장이 이긴다. 시스템 드랍이 `ambient_drop_config`의 어느 열을 실제로 쓰는지는 확인하지 못했다(`ambient_drop_policy`는 코드에서 읽히지 않는다). 시작 때 코드로 먼저 확인한다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 옮긴 구역에서 저장하면 옛 화면에서 저장한 것과 같은 열이 같은 값으로 바뀐다(시험으로 고정).
- 어뷰징 배율 8열처럼 쓰이지 않는 열은 화면에 올리지 않는다.

## 선행과 시작 전 확인

- 선행: 7-1. 티켓 `20261022_0938`이 옛 드랍 정책 화면을 지우는 범위와 겹치지 않는지 시작 때 확인한다.
- 시작 때 사용자에게 물을 것: 옛 화면을 안내 문구와 함께 남길지 바로 지울지. → 아래 「사용자 결정」에서 정했다.
- 0938과의 겹침: 없다(조사 결과). 0938 1회는 `drop-policy` 화면과 `all_random` 코드를 이미 지웠고 7-3은 그 화면을 건드리지 않는다.

## 조사 결과 (2026-10-24, 탐색 에이전트의 읽기 전용 조사, 카리나가 직접 확인하지는 않았다)

처음 범위의 전제가 어긋난 곳이 있어 사용자에게 다시 물었다.

- 옛 화면 가운데 기준값 전용인 곳은 인벤토리뿐이다. 어뷰징 화면은 탭 셋(정책 설정, 이용 정지, 장소 블록) 중 «정책 설정» 탭만 기준값이고 나머지는 제재 운영 도구다. 시스템 드랍 화면은 숫자 칸 외에 지금 배포, 날짜 예약, 최근 이력, 스위치가 있다. 운영 설정(`ops-settings`)은 운영툴 자체의 설정(`ops_rules`)이라 게임 밸런스가 아니다.
- 어뷰징 배율 8열, `all_random`, `drop_policy` 화면은 이미 화면과 코드에서 빠져 있다(6-4 2회, 0938 1회). 7-3에서 «화면에서 빼는» 일은 없다. `ambient_drop_policy` 표는 마이그레이션 100이 지웠다(공용 DB에서 직접 확인하지는 못했다).
- 시스템 드랍 설정 열 14개는 모두 서비스 코드가 읽는다. 배포 시각·상호 배제 창 상한은 코드가 180분인데 저장 오류 문구와 정책 카드는 720분이라고 적는다.
- 밸런스 설정의 공용 틀은 숫자 칸만 다룬다. `set_inventory_max_slots`는 `updated_at` 조건부 갱신이 아니고 거절 결과를 사용자에게 400으로 돌려줄 길이 틀에 없다. 그래서 1회에 틀 보강(거절 결과, 시험용 가짜 DB의 `rpc`)이 필요하다.
- 규모는 신규 9, 수정 약 22, 삭제 4파일, 약 2,500줄로 티켓 처음 추정(20파일 1,400줄, 1회)의 약 1.8배다.

## 사용자 결정 (2026-10-24)

- 범위: 숫자 칸만 옮기고 3회로 나눈다. 인벤토리 화면은 통째로 지우고, 어뷰징은 «정책 설정» 탭만, 시스템 드랍은 숫자 칸만 옮겨 지운다. 이용 정지·장소 블록, 스위치, 축 고르기, 지금 배포, 날짜 예약, 이력은 그대로 둔다. DB 변경과 마이그레이션은 없다. 안내 링크는 두지 않는다.
- 시스템 드랍: 8칸(배포 시각, 상호 배제 창, 배치 규모, 지점당 한도, 등급 비율 4칸)을 옮긴다. 등급 비율은 화면에서 퍼센트(소수 1자리)로 보이고 저장할 때 0~1로 바꾼다. 캡슐 구역과 같은 합계 100 검사를 재사용하고 등급 4칸은 확률 안내 확인창이 뜨게 한다.
- 인벤토리: 일반 확인창을 공용 폼에 더하지 않고 구역 본문에 «저장하면 전체 유저 N명의 인벤토리 최대치가 즉시 바뀌어요» 안내만 둔다. 남는 시스템 드랍 화면에는 배포 시각을 읽기 전용 글자로 보이고 «밸런스 설정에서 바꿔요» 한 줄(링크 없이)을 둔다.
- 나머지 다섯 가지(추천안 모두): ① 어뷰징 칸 최소값은 정수 1 이상(차량 속도 필터는 20 이상) ② 운영 설정 화면과 메뉴는 그대로 두고 링크도 새로 두지 않음 ③ 쓰는 곳이 없어지는 `updateAbusingPolicy`는 2회에 삭제 ④ 상호 배제 창 상한은 코드 기준 180분으로 두고 720분이라고 적힌 저장 오류 문구와 정책 카드 문구를 3회에 같이 고침 ⑤ 승인 정책 문서(`automation-list.md`, `05_자동화목록.md`)의 «항상 승인» 경로 표 수정은 미결로 넘기고 후속 티켓으로 남김.
