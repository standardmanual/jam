# [Admin] JAM2 배지 포인트 등급별 일괄 값 저장과 기존 배지 적용 (묶음 7, 7-4)

## 핵심 요약

- 요구사항: 운영 로직 19.1의 «배지와 포인트» 구역을 만든다. 배지 포인트의 등급별 일괄 값(Common 10, Rare 20, Epic 50, Mystic 100, 레벨형 10)을 저장하고, 배지 양식(`badges/BadgeForm`)의 포인트 칸에 이 값이 기본값으로 들어가게 하고, 이미 있는 배지에 적용하는 SQL을 쓴다. 값은 마이그레이션 253으로 아이템·체크인 행에 한 번 들어갔지만(2026-10-20 적용) 저장하는 자리와 설정 화면과 양식 기본값이 없다. 아이템북 양식은 이 티켓에서 고치지 않는다(컬렉션 완성 포인트는 7-2 «컬렉션과 믹스» 구역이 맡는다).
- 구현 계획: 2회. 1회는 마이그레이션 288(새 표 `badge_point_policy`, 추가만)과 설정 구역 «배지와 포인트», 배지 양식의 기본값 연결, 배지 생성 API의 기본값 채움, 정책 대시보드 카드. 2회는 기존 배지 적용 SQL 289(아이템·체크인)와 290(액티비티)을 파일로 쓴다(드라이런, 사후 검증, 되돌림). 마이그레이션 272는 이미 다른 용도로 있어 쓰지 않는다. SQL 실행은 파일을 보여 드린 뒤 사용자 승인으로만 카리나가 한다.
- 관련 파일: `jam-web/src/app/admin/badges/BadgeForm.tsx`, 운영 로직 10장·11장·14장의 포인트 값. 규모는 약 20파일 1,350줄(처음 추정 12파일 900줄에서 고침).

## 배경 / 문제 정의

포인트 칸이 배지·컬렉션·레시피 양식에 흩어져 있어 등급별 일괄 조정이 어렵다. 지금 기존 배지의 포인트를 바꾸면 프로덕션 유저가 받는 포인트가 바로 달라진다(공용 DB).

## 상세 요구사항

### 서비스/코드베이스 관점

- 새 배지는 양식에서 등급별 기본값이 채워진다. 기존 배지에 일괄 값을 적용하는 일은 SQL로 하고 적용 시점은 위 사용자 결정대로다.
- 7-6에서 입력한 새 배지의 포인트 값(1,404개가 0)과 이 일괄 값을 대조해 289가 맞춘다.

## 조사 결과 (2026-10-24, 탐색 에이전트의 읽기 전용 조사와 카리나의 공용 DB 읽기 확인)

조사 서술은 탐색 에이전트가 코드와 문서에서 확인한 것이고 카리나가 직접 코드를 확인하지는 않았다. 공용 DB 값은 카리나가 읽기 전용으로 확인했다.

- 일괄 값은 한 세트다. 액티비티(등급형·반복형)·체크인·아이템 배지가 모두 같은 4값(Common 10, Rare 20, Epic 50, Mystic 100)이고 레벨형 액티비티는 레벨마다 10, 숨김은 0이다(운영 로직 10.5·11.4·14.1절). 컬렉션 완성(100/200/400/800)과 믹스 실패는 7-2 구역이 맡는다.
- 마이그레이션 272는 이미 오픈 뒤 SQL로 쓰여 있다. staging 최대 번호는 287이라 288, 289, 290을 쓴다.
- 아이템·체크인의 `point_reward = 0` 행은 253이 한 번 10으로 바꿨다. 244는 `point_reward`를 건드리지 않는다. 245와 248은 새 행을 규칙 값으로 넣는다. 재활용으로 남는 기존 액티비티 배지의 포인트는 어느 마이그레이션도 맞추지 않아 7-4가 받는 자리다.
- `BadgeForm`은 새 배지의 포인트 기본값이 0이고 등급을 바꿔도 포인트가 바뀌지 않는다. 지급 코드는 모두 배지를 받는 때 `badges.point_reward`를 읽어 한 번 지급하므로 일괄 값을 바꿔도 기존 행이 자동으로 바뀌지 않고, 이미 받은 배지에는 소급되지 않는다. 아직 열지 않은 잠긴 아이템 개체는 열 때의 값을 읽는다.
- 숨김 배지는 DB 제약(`badges_hidden_no_points`)으로 포인트가 0이어야 한다. 온보딩 완료 배지 «JAM!»(id `cd20f271-9445-42cc-ac51-d8a96b25e1c3`)는 Common인데 100포인트라 적용에서 제외한다.
- 계열 화면의 «레벨 추가»(`FamilyDetailManager.tsx`)는 `point_reward` 없이 배지 생성 API를 불러 0포인트 배지가 만들어진다.
- 공용 DB(2026-10-24 읽기): 삭제되지 않은 아이템 배지 1,971개(Common 351개 0 / 270개 10, Rare·Epic·Mystic 각 450개 모두 0), 체크인 1,832개(모두 10), 액티비티 634개(Common 84, Rare 103, Epic 152, Mystic 101, 레벨형 193은 모두 0, 온보딩 배지 1개만 100). 아이템 Rare 이상 1,350개는 7-6이 넣은 새 행이라 0이다. 삭제된 아이템 배지 333개. 새 표 `badge_point_policy`는 아직 없다.
- 7-6의 새 행 1,404개는 INSERT 열에 포인트가 없어 0이고 덮어쓴 396개는 기존 값이 그대로다. 276 주석이 «포인트는 7-4가 일괄 적용»이라고 위임했다.
- 정책 대시보드에 배지 포인트 카드가 없다. 티켓 `20261022_1708`의 규칙에 따라 카드 1개를 추가한다.

## 사용자 결정 (2026-10-24)

- 적용 시점: 아이템 배지(1,701개: Common 351개 0에서 10, Rare 450개 20, Epic 450개 50, Mystic 450개 100)는 SQL을 드라이런·되돌림과 함께 보여 드리고 승인받아 적용한다. 체크인은 이미 10이라 바뀌는 행이 없다. 액티비티는 244, 245, 248을 오픈 직전에 적용한 **뒤** 별도 SQL(290)로 적용한다(7-9 목록 순서: 244 → 245 → 248 → 290. 245·248의 포인트 합 가드(1410, 1650)는 290 적용 전에 돌린다).
- 저장 설계: 새 표 `badge_point_policy`(id=1 한 행, Common·Rare·Epic·Mystic·레벨형 5칸, 기본 10·20·50·100·10, 0 이상 정수)를 마이그레이션 288로 추가한다(추가만). 밸런스 설정 맨 끝에 구역 «배지와 포인트»(키 `badgepoints`)를 더한다. 확률 안내 확인창은 없다.
- 기존 값: 규칙으로 덮어쓴다. 온보딩 배지 id, 숨김 배지, 삭제된 배지는 제외한다. 드라이런으로 바뀔 건수와 규칙 밖 값 목록을 먼저 보여 드리고, 백업 표에 바뀐 행의 이전 값을 남겨 되돌림이 그 값만 되돌리게 한다.
- 생성 경로: 배지 생성 API가 `point_reward`를 생략하면 일괄 값(레벨형이면 레벨형 값)을 채운다. 계열 화면의 «레벨 추가»가 여기에 든다. 운영툴 JAM! 배지 등록과 에셋 등록 스크립트는 P3 후속 티켓으로 남긴다.
- 회차: 1회 표·구역·양식 기본값·API 기본값·대시보드 카드·문서, 2회 기존 배지 적용 SQL 파일(289, 290). 아이템북 양식은 고치지 않는다.

### 2회 (카리나 작성, 1회 병합 뒤 확정, 경로는 `jam-web/` 기준)
- 신규 `supabase/migrations/289_apply_badge_point_defaults_item_checkin.sql`(아이템·체크인), `290_apply_badge_point_defaults_activity.sql`(액티비티), 시험 `src/lib/badge/__tests__/pointApplySql.test.ts`. **파일만 쓰고 실행하지 않는다.** 실행은 카리나가 드라이런 결과를 보여 드리고 승인받아 한다.
- 두 파일 공통 구조: (1) 읽기 전용 드라이런 SELECT 묶음을 파일 맨 앞 주석에 둔다(계획 행 수, 바뀔 건수, 종류·등급·이전 값 → 이후 값별 건수, 규칙 밖 값 목록). (2) 본문은 한 트랜잭션으로 실행된다. 값은 리터럴이 아니라 `public.badge_point_policy`(id=1)의 칸에서 읽어 `plan` CTE로 만든다(등급 → 해당 칸, 등급 없음(레벨형) → `leveled_points`). (3) 가드: 정책 표와 행이 있고 `plan`에 `after`가 NULL인 행이 0건이며 계획 행 수가 파일에 박은 기대 건수와 같다. (4) 바뀔 행(`before <> after`)만 백업 표 `public.badge_point_backup_289`(또는 `_290`)(`badge_id uuid primary key`, `before_point`, `after_point`, `backed_up_at`, RLS 켜고 정책 없음, 275 선례)에 넣는다. `badges`에는 `updated_at`이 없어 이 표가 유일한 원본이다. (5) `UPDATE public.badges b SET point_reward = plan.after_pt FROM plan WHERE b.id = plan.id AND plan.before_pt <> plan.after_pt AND b.point_reward = plan.before_pt`(읽은 뒤 바뀐 행은 건드리지 않음). (6) 건수 가드: 갱신 행 수 = 백업 행 수 = 기대 바뀔 건수가 아니면 예외로 전체를 되돌린다. (7) 사후 검증 SELECT를 주석으로(범위 안에서 규칙과 다른 행 0, 종류·등급·값 분포, `point_transactions` 건수·합계가 적용 전후 같음). (8) 되돌림 SQL(백업의 `before_point`로 되돌리되 `point_reward = after_point`인 행만, 적용 뒤 어드민이 직접 바꾼 행은 그대로 둠)과 백업 표 DROP을 주석으로. 이미 지급된 포인트는 원장이 불변이라 되돌려지지 않는다는 말을 머리말에 적는다.
- **289 범위와 기대 건수**(2026-10-25 공용 DB 읽기): `type IN ('item','checkin')`이고 `deleted_at IS NULL`이고 `is_hidden = false`. 계획 행 3,803개(아이템 Common 351개 0 → 10, Common 270개 이미 10, Rare 450개 0 → 20, Epic 450개 0 → 50, Mystic 450개 0 → 100, 체크인 Common 1,832개 이미 10). **바뀔 행 1,701개**, 바뀌지 않는 행 2,102개, `after`가 NULL인 행 0개. 파일에는 이 숫자를 기대 건수로 박고, 달라지면 가드가 실패한다.
