# [Content] JAM2 트라이브 컨텐츠 입력 1: 컬렉션 50개와 아이템 배지 1,800개 (묶음 7, 7-6)

## 핵심 요약

- 요구사항: 트라이브 재구상 원고(`docs/plan/jam2/tribe-rethink/manuscript/`)의 컬렉션 50개와 아이템 배지 450종 × 4등급(1,800개)을 DB에 넣는다. 같은 이름의 아이템 배지는 4등급 모두 이름이 같고 설명은 등급마다 따로 둔다. 이미지는 빈 이미지로 시작한다. 운동 속성 구간 이름도 원고에 있으면 함께 넣는다(원고 위치는 시작 때 확인한다).
- 구현 계획: 2회. 1회 원고 파서와 대응표(원고 컬렉션 ↔ 기존 컬렉션), 드라이런. 2회 트라이브별 SQL 파일(마이그레이션 273~277)과 적용·사후 검증. 한 번 실행 한도를 넘을 수 있어 트라이브별 파일로 나눈다. 번호는 시작 때 `origin/staging` 기준으로 다시 확인한다. SQL은 아현이 파일로 쓰고, 실행은 사용자 승인과 롤백 실측 뒤 카리나가 한다.
- 관련 파일(시작 때 아현이 확인한다): 원고 `docs/plan/jam2/tribe-rethink/manuscript/`, 컨텐츠 문서 `docs/service/content/`, 운영 로직 19.3·19.4, 정책 `docs/plan/jam2/service-redesign/15 트라이브 컨텐츠 제작.md`(혜린 조사(2026-10-22), 카리나가 직접 확인하지는 않았다). 규모 약 12파일 1,200줄(SQL 제외).

## 배경 / 문제 정의

공용 DB의 컬렉션 100개는 모두 4등급 방식이 꺼져 있다. 새 컨텐츠를 옛 컬렉션에 덮어쓰고 4등급을 켠 채 넣고 넣자마자 켜기로 사용자가 정했으므로(상위 티켓 「사용자 결정」), 입력 즉시 프로덕션 화면에 새 이름과 설명이 보이고 트라이브·컬렉션이 온보딩에도 나타난다.

## 상세 요구사항

### 컨텐츠 관점

- 같은 이름의 아이템 배지는 4등급 이름이 같고 설명만 등급마다 다르다. 아이템 배지 상세는 설명, 일련번호, 획득 이력만 보이고 조건은 적지 않는다.
- 기존 컬렉션 가운데 자리가 확정된 것은 이름을 되도록 살리고 설명은 새로 쓴다. 원고에 자리가 없는 컬렉션은 비활성화한다(비활성화의 적용 시점은 7-7이다).
- 컬렉션은 트라이브마다 3개로 시작해 석 달마다 1개씩 연다. 순서는 사용자가 어드민에서 고르며 운영툴의 예약 공개를 쓸 수 있다(19.4). 이 티켓이 «넣자마자 켠다»를 트라이브마다 3개로 시작하는 규칙과 어떻게 맞출지 시작 때 정한다.

### 서비스/코드베이스 관점

- 이미 장착된 개체가 있는 컬렉션에 4등급을 켜면 꽂힌 등급 정리가 필요하다. **이 티켓의 DB 적용은 7-8(켜기 전 꽂힌 등급 조회) 뒤에 한다.**

## 선행과 시작 전 확인

- 선행: 트라이브 5개 등록(사용자 결정에 따라 **비활성으로** 등록하고 컬렉션 적용 직후에 켠다, 트라이브 화면의 운영 입력, 사용자). 옛 트라이브를 끄는 일은 오픈 직전에 따로 한다. 7-8은 DB 적용 전까지.
- 시작 전 조사: 원고 컬렉션 50개와 기존 컬렉션 100개의 대응표(덮어쓸 것, 끌 것), 덮어쓸 컬렉션의 장착 기록, 1,800행 SQL이 한 번 실행 한도를 넘는지.
- 시작 때 사용자에게 물을 것: 대응표의 확정(어느 옛 컬렉션을 살리고 어느 것을 끌지)과 «트라이브마다 3개로 시작» 규칙과의 관계. 추천안은 시작 때 붙인다.

## 시작 전 조사 결과 (2026-10-22, 카리나, 공용 DB와 원고를 읽기 전용으로 확인)

**요약**
- 원고 컬렉션 50개 가운데 **44개는 기존 컬렉션을 이어받고 6개는 새로 만든다**(비사이드 레코즈 7~10번, 혼자들 9·10번). 44개의 옛 이름은 공용 DB의 컬렉션 이름과 모두 한 건씩 맞는다(원고의 «무명(無名)을 쫓는 야식가들»만 DB에는 한자에 괄호가 없는 «무명無名을 쫓는 야식가들»로 있어 이름이 글자 하나 다르다).
- 이어받는 44개 가운데 **11개는 지금 활성**이고 유저의 장착이 있다(63칸, 유저 3명 안에서). **33개는 이미 비활성**이고 소속 배지 9개가 모두 소프트 삭제 상태이며 장착이 없다. 이어받지 않는 나머지 **56개는 활성 19개**(장착 45칸, 13개 컬렉션)와 비활성 37개다.
- 이어받는 컬렉션의 옛 아이템 배지가 유저 보유로 남은 것은 모두 1,030개다(소프트 삭제 상태인 배지를 가리키는 보유 포함).

**시작할 때 사용자에게 물을 결정**

1. **옛 배지 행을 어떻게 이어받을지**(컬렉션 덮어쓰기에 이어 배지 단위를 정한다). 추천: **원고가 «살림·다듬음»이라 한 89개만 옛 배지 행을 Common으로 이어 쓰고**(이름·설명을 고치고 보유와 장착이 이어진다), «사물로 바꿈·새로 씀»은 새 행으로 넣고 옛 행은 소프트 삭제 상태로 둔다. 이유: 원고가 «이어 쓴다»고 한 것만 이어지고, 유저가 가진 아이템이 모르는 사이에 다른 아이템으로 바뀌지 않는다. 대안은 옛 행을 모두 덮어쓰기(보유 1,030개와 장착 29칸의 내용이 바뀐다)다.
2. (결정함: 오픈 직전까지 그대로 둔다) **장착이 있는 이어받지 않는 컬렉션 13개(45칸)**를 비활성화하면 그 유저 화면에서 해당 칸 진행이 보이지 않는다(기록은 남는다). 이 비활성화는 7-7에서 오픈 직전에 한다. 추천: 그때까지 그대로 둔다. 이유: 옛 트라이브의 유저가 있는 동안 그 컬렉션을 계속 볼 수 있어야 하고, 옛 트라이브 3개를 끄는 시점과 함께 처리하는 편이 순서가 맞다.
3. (결정함: 비활성으로 먼저 등록하고 컬렉션 적용 직후에 켠다) **새 트라이브 5개 등록 시점**(선행): 사용자가 트라이브 화면에서 한다. 등록하면 «넣자마자 켜기» 결정에 따라 프로덕션 온보딩에 바로 보일 수 있다. 추천: **트라이브는 비활성 상태로 먼저 등록하고, 7-6의 DB 적용(컬렉션을 새 트라이브에 연결해 활성으로 바꿈)이 끝난 직후 켠다.** «넣자마자 켜기»와 같은 효과이면서 컬렉션이 없는 트라이브가 온보딩에 보이는 시간이 없다.
4. (결정함: 덮어쓰기와 같은 DB 적용 한 번에 바꾼다) **이어받는 컬렉션의 `tribe_id`를 새 트라이브로 바꾸는 시점**: 옛 트라이브 3개의 활성 컬렉션이 이 순간 새 트라이브로 옮겨진다. 추천: **덮어쓰기와 같은 DB 적용 한 번에 바꾼다**(이름·설명·배지와 트라이브가 따로 어긋나는 시간이 없다).

## 사용자 결정 (2026-10-22)

② **`badges.tribe_id`도 새 트라이브로 바꾼다.** 드랍은 `badges.tribe_id`가 유저의 트라이브와 같은 배지를 후보로 고른다(`lib/drop-engine/syncIssue.ts` 165줄 근처). 컬렉션의 `tribe_id`만 바꾸면 새 트라이브 유저에게 아이템 배지가 나오지 않는다. 공용 DB의 아이템 배지 900개 모두 `tribe_id`가 컬렉션과 같다.
③ **이미지는 비운다.** 덮어쓰는 옛 배지 행 396개와 컬렉션 44개의 `image_url`(과 `image_source`)을 비우고 새 행도 비운다(운영 로직 19.3의 «이미지는 빈 이미지로 시작»). 옛 이미지를 두면 새 아이템 이름 옆에 옛 그림이 보인다. 공용 DB의 아이템 배지 900개 모두 지금 이미지가 있다.
④ **포인트**: 덮어쓰는 옛 행의 `point_reward`는 그대로 두고 새 행은 비운다. 등급별 값은 7-4가 일괄 적용한다.
⑤ **컬렉션 값**: `name` ← 새 이름, `description` ← 한 줄 서사, `tribe_id` ← 새 트라이브, `is_active` ← true, `tier_mode` ← true, `reward_points`·`reward_badge_id`는 건드리지 않는다(4등급 컬렉션은 등급별 보상을 쓴다, 7-8). 새 컬렉션 6개는 같은 값으로 새로 만든다. `story_text`는 비운다(원고에 없다).
⑥ **배지 값**: 덮어쓰는 행은 `name`, `description`(Common 설명), `rarity = common`, `deleted_at = NULL`을 새 값으로 고치고 새 행은 같은 이름으로 Rare·Epic·Mystic 설명을 넣어 만든다. 같은 이름이 4등급 모두 이름이 같고 설명만 다르다(7-8 이름 점검을 통과해야 한다).
⑦ **백업 표를 둔다**(되돌림용, 추가만). 덮어쓰기는 옛 내용을 잃으므로 되돌림 SQL이 쓸 원본이 필요하다. 6-4의 오픈 뒤 정리 SQL 때 지운다.
⑧ **옛 완성 기록 3건**(이어받는 컬렉션 중 «시장 골목의 전설»과 «무명을 쫓는 야식가들» 각 1건)은 건드리지 않는다. 4등급이 켜지면 그 유저가 Common 등급을 새 방식으로 다시 완성해 보상(포인트 100)을 한 번 더 받을 수 있다. 테스트 유저 2명이고 오픈 전 전환에서 지워지므로 허용한다.
⑨ **적용 직전 재점검**: 7-8의 켜기 전 점검(여러 등급을 꽂은 유저 0명)과 행 수(44개 컬렉션, 옛 행 396개)를 읽기 전용으로 다시 확인한 뒤 적용한다. 장착이 그 사이 늘어도 덮어쓰기라 막지는 않는다.
⑩ **롤백 실측**은 마이그레이션마다 «한 트랜잭션에서 실행 후 일부러 오류로 되돌림»으로 하고(270과 같은 방식), 중간에 행 수 검사(컬렉션 10, 배지 90 → 360)와 7-8 이름 점검 결과를 확인한다. 한입만 연구회 견본을 1회에서 먼저 실측한다.
⑪ 이어받지 않는 컬렉션 56개와 새 트라이브 켜기, 옛 트라이브 끄기는 이 티켓이 하지 않는다(결정한 대로 7-7과 사용자 몫).

- **트라이브마다 «3개로 시작해 석 달마다 1개씩 연다»(운영 로직 19.4)와 «넣자마자 켜기»의 관계**: 이 티켓의 SQL이 컬렉션 10개를 모두 활성으로 넣을지 정해야 한다. 추천: **10개 모두 활성으로 넣어 오픈 전 확인을 쉽게 하고, 오픈 직전에 트라이브마다 3개만 남기고 나머지 7개를 예약 공개로 바꾸는 일을 7-9의 적용 목록에 둔다**(처음 열 3개는 사용자가 고른다). 대안은 처음부터 3개만 활성으로 넣고 7개는 비활성으로 두는 것이다.
