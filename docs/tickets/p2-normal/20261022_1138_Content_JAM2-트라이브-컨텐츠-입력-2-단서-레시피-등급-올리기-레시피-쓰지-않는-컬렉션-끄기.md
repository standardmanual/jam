# [Content] JAM2 트라이브 컨텐츠 입력 2: 단서 레시피, 등급 올리기 레시피, 쓰지 않는 컬렉션 끄기 (묶음 7, 7-7)

## 핵심 요약

- 요구사항: (1) 단서 레시피 20개를 넣는다(Common 등급, 성공 포인트는 재료 수 × 10, 공개 전으로 숨긴 채). (2) 등급 올리기 레시피 1,350개를 만드는 SQL을 쓴다(DB 안에서 `INSERT … SELECT`). **공용 DB 적용은 선행 티켓 7-7a(`20261022_2119`, 믹스 화면이 재료 후보를 레시피를 고를 때만 불러오게 고침)가 staging에 반영된 뒤**에 한다. (3) 원고에 자리가 없는 옛 컬렉션(지금 켜진 19개)과 옛 레시피 3건을 끄는 SQL을 쓴다. **적용은 오픈 직전**이다.
- 구현 계획: 2회. 1회 = 단서 레시피 원고 읽기, 단서 레시피 SQL(281), 끄기 SQL(282). 2회 = 등급 올리기 SQL(283). 마이그레이션 번호는 시작 때 `origin/staging` 기준으로 다시 확인한다(2026-10-22 기준 281~284가 비어 있고 285는 7-1이 썼다).
- 관련 파일(줄 위치는 시작 때 아현이 다시 확인한다): 7-6 생성기 `jam-web/scripts/jam2-content/`(`parse-manuscript.mjs`, `gen-content-sql.mjs`, `pairing.json`), 원고 `docs/plan/jam2/tribe-rethink/manuscript/07 단서 레시피.md`(2절 짝, 5절 이름과 설명), 레시피 표 `combination_recipes`·`combination_recipe_slots`, 운영 로직 8.4·8.7·19.3·19.4, `docs/service/content/COMBINE_RECIPES.md`

## 배경 / 문제 정의

JAM 2.0의 믹스는 정해진 레시피대로 확률 없이 결과가 나온다. 새 서비스의 레시피는 트라이브를 넘는 단서 레시피 20개와, 같은 트라이브·같은 등급의 아이템 배지 5개를 위 등급 1개로 바꾸는 등급 올리기 레시피 1,350개다(트라이브 안의 일반 레시피는 만들지 않는다). 지금 공용 DB의 레시피 3건은 옛 트라이브 단독 레시피로, 운영 로직 15장 4절이 «쓰지 않는다»고 한 것이다.

## 시작 전 조사 결과 (카리나, 2026-10-22, 코드 읽기와 공용 DB 읽기 전용 확인. 아무것도 바꾸지 않았다)

**공용 DB의 지금 모양**

- `combination_recipes` 3건(이름 있음, 모두 공개 중, 잠김 0건), `combination_recipe_slots` 8건(모두 아이템 칸, 후보 id 19개). 받지 않은 믹스 결과 0건, 믹스 실패 포인트 10.
- 레시피 한 건은 보상 배지 목록(`reward_badge_ids`)과 칸마다 «넣을 수 있는 아이템 배지 목록»(`allowed_badge_ids`, 배열)을 갖는다. 칸 인덱스는 레시피 id 기준뿐이고 후보 배열용 인덱스는 없다. 레시피 이름은 중복을 막지 않는다.
- 값 제약: 칸 후보는 1개 이상, 칸 종류는 `item`·`activity`·`checkin`, 보상은 «보상 없음 허용이거나 포인트가 있거나 보상 배지가 하나 이상», 공개 시작이 종료보다 앞이어야 한다(종료가 없으면 검사 없음).

**단서 레시피 원고**

- 원고 07의 2절에 R01~R20(방향, 단서, 재료 3~5개, 보상 1개)이 있고 5절에 이름·설명 20개가 확정돼 있다(사용자 확정 2026-10-09). 재료와 보상은 «컬렉션 번호-아이템 번호 이름»으로 적혀 있다. 나가는 단서는 음악 5개, 내향인 3개, 나머지 4개씩이다.
- 성공 포인트와 등급 방식은 원고에 없다(성공 포인트는 레시피를 만들 때 사용자가 정한다). 재료 수는 3개 2건(R05, R07), 4개 10건, 5개 8건이다(원고 표의 «(N개)» 표기를 카리나가 센 값이고, 시험이 다시 센다).

**등급 올리기와 믹스 화면 (조사에서 드러난 문제)**

- 등급 올리기는 2026-10-18 결정(`20261018_0055`)에 따라 «별도 종류가 아니라 슬롯 후보 목록으로 만든 보통 레시피»이고 일괄 생성은 이 티켓이다. 레시피 1,350건 = 트라이브 5곳 × 아이템 이름 90종 × 올릴 등급 3개(Common→Rare, Rare→Epic, Epic→Mystic). 칸마다 후보는 같은 트라이브·같은 등급 90종이고 칸이 5개다.
- DB에 저장되는 양은 문제가 아니다(칸 6,750개, 후보 id 607,500개, 약 10MB). 문제는 믹스 화면 `app/(main)/combine/page.tsx`다. 열릴 때 공개된 레시피 전부(`select('*')`)를 읽고, 레시피 id 전부를 `.in('recipe_id', …)`에 실어 칸을 읽고, 칸마다 후보 배지 상세(이름, 설명, 그림, 등급)를 만들어 클라이언트에 내려보낸다. 레시피 1,350건이면 후보 약 60만 개가 한 번에 내려가고 요청 주소가 매우 길어진다. 후보·보상 배지 상세 조회도 등급별 후보와 보상을 합친 아이템 배지 1,800개 전체의 id를 주소에 싣는다. 실제 응답 크기와 주소 한도는 측정하지 못했다(코드 읽기로 추정, 7-7a가 시작 때 잰다).
- 운영자는 공개 전 레시피까지 믹스 화면에서 보므로 «공개 전으로 숨겨서 넣기»만으로는 운영자 화면의 같은 문제를 피하지 못한다. 일반 유저와 프로덕션 유저에게는 공개 전 레시피가 칸 조회 앞에서 걸러져 보이지 않는다.
- 믹스 시도(`combineRecipeAttempt`)는 선택한 레시피 한 건만 읽으므로 레시피가 1,371건이어도 영향이 없다.
- 확인하지 못한 곳: 어드민 레시피 목록(`admin/recipes`)과 `badge-references.ts`(배지 참조 검사가 레시피와 칸을 끝까지 훑는다)가 레시피 1,371건에서 얼마나 느려지는지. 2회 시작 때 확인한다.

**다른 세션과 겹침**: 이 티켓을 건드리는 열린 세션과 미커밋 변경은 없다. 7-6의 생성기와 같은 폴더에 파일을 더한다.

## 사용자 결정 (2026-10-22, 질문창, 4건 모두 추천안)

1. **등급 올리기**: 레시피 1,350건은 2026-10-18 결정대로 보통 레시피로 만든다. 믹스 화면이 후보를 레시피를 고를 때만 불러오게 먼저 고치고(선행 티켓 7-7a `20261022_2119`), 1,350건의 공용 DB 적용은 그 수정이 staging에 반영된 뒤에 한다. 이 티켓은 SQL 작성과 롤백 실측까지 한다. 코드 규칙으로 실행하는 방식(묶음 3 원안)은 쓰지 않는다.
2. **단서 레시피 등급**: Common 20개. 재료와 보상 모두 Common 아이템 배지다. 더 높은 등급의 단서 레시피는 오픈 뒤 운영자가 어드민 레시피 화면에서 더한다.
3. **성공 포인트**: 재료 수 × 10(믹스 실패 포인트 10 기준). 재료 3개는 30, 4개는 40, 5개는 50이다(`COMBINE_RECIPES.md` 4절의 기존 기준).
4. **공개 시작**: 오픈 전까지 숨긴다. 공개 시작을 먼 미래 자리 값으로 넣어 일반 유저와 프로덕션에는 보이지 않게 하고, 운영자는 staging에서 시험 믹스만 한다. 오픈 직전 SQL(7-9 목록)로 공개 시각을 맞춘다. 오픈 때 컬렉션을 트라이브마다 3개로 줄이므로, 재료나 보상 컬렉션이 닫힌 단서가 보이면 안 되기 때문이다.

## 가정 (카리나, 구현 시작 전 사용자가 바로잡을 수 있다)

- (가) 옛 레시피 3건(트라이브 단독 레시피)은 운영 로직 15장 4절에 따라 쓰지 않는다. 쓰지 않는 컬렉션 끄기 SQL에 함께 담아 오픈 직전에 끈다(공개 종료 시각을 오픈 시각으로 맞춘다). 삭제하지 않는다.
- (나) 단서 레시피의 이름과 설명은 원고 07의 5절 값을 그대로 쓴다(말투 «~습니다»). 레시피 잠김은 «열림»(기본), 보상 없음 허용은 꺼 둔다.
- (다) 공개 시작의 «먼 미래 자리 값»은 `2099-01-01 00:00 KST`로 한다. 오픈 직전 SQL이 실제 오픈 시각으로 바꾼다.
- (라) 컬렉션 10개 중 3개만 남기는 일(오픈 때 트라이브마다 3개로 시작)은 운영자가 어드민에서 고르는 일이라 이 티켓에 넣지 않고 7-9 목록에 둔다. 그때 단서 레시피 공개 시각을 재료와 보상 컬렉션이 모두 열리는 날에 맞춰야 한다는 연동을 7-9 목록에 같이 적는다(자동 연동 코드는 없다).
- (마) 쓰지 않는 컬렉션 끄기는 지우지 않고 비활성화한다(소프트 삭제, 이미 받은 기록은 그대로). 끄기 직전 상태를 백업 표에 담아 되돌림 SQL이 쓴다(7-6의 백업 표 `content_overwrite_backup_20261022`를 쓸 수 있으면 쓰고, 칸이 모자라면 아현이 시작 때 제안한다).
- (바) 등급 올리기 레시피의 이름과 설명 문구는 2회 시작 때 사용자에게 확인한다(예: 이름 «○○ Rare로 올리기», 설명 «같은 트라이브의 Common 아이템 배지 다섯 개로 ○○ Rare 한 개를 받습니다»). 단서와 달리 원고가 없고 1,350건에 같은 틀을 쓴다.
- (사) 재료와 보상 배지는 SQL 안에서 «트라이브 이름, 컬렉션, 아이템 이름, Common 등급»으로 찾고, 찾은 수가 기대(재료마다 1건)와 다르면 오류로 멈춘다(7-6 방식). 실행은 한 번의 호출로 통째로 하는 한 트랜잭션이다.
- (아) DB 적용은 파일마다 사용자 승인을 받은 뒤 카리나가 한다. 롤백 실측(`DO` 블록에서 오류를 일으켜 되돌리는 방식)을 먼저 한다. 281은 숨겨 넣으므로 승인 뒤 바로 적용할 수 있고, 282는 오픈 직전, 283은 7-7a 뒤다.
