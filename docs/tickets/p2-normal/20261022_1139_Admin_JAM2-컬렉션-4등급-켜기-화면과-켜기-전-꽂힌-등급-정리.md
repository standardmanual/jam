# [Admin] JAM2 컬렉션 4등급 켜기 화면과 켜기 전 꽂힌 등급 정리 (묶음 7, 7-8)

## 핵심 요약

- 요구사항: 컬렉션의 4등급 방식을 켜는 칸과 화면을 만든다. 등급별 보상을 입력하고, 켜기 전에 이미 꽂힌 등급(옛 방식으로 장착된 개체)을 조회해 정리할 수 있게 한다. 티켓 `20261016_2340`이 넘긴 정리 6건도 여기서 처리한다. 지금은 이 칸과 화면이 없다(혜린 조사(2026-10-22), 카리나가 직접 확인하지는 않았다).
- 구현 계획: 1회. 켜기 칸(컬렉션 설정의 4등급 방식 여부), 등급별 보상 입력(`item_book_tier_default_rewards`와 컬렉션별 값), 켜기 전 꽂힌 등급 조회와 정리 동작, 2340이 넘긴 정리 6건.
- 관련 파일(시작 때 아현이 확인한다): 티켓 `20261016_2340`(컬렉션 4등급 구조)의 넘긴 항목, 티켓 `20261022_0939`(옛 컬렉션 구조 축소), `jam-web/src/app/admin/itembooks/`. 규모 약 14파일 1,000줄. DB 변경은 없다.

## 배경 / 문제 정의

공용 DB의 컬렉션 100개는 모두 4등급 방식이 꺼져 있다. 사용자가 7-6에서 새 컨텐츠를 옛 컬렉션에 덮어쓰고 4등급을 켠 채 넣기로 했으므로(상위 티켓 「사용자 결정」), 켜기 전에 이미 장착된 개체를 확인하고 정리하는 동작이 7-6의 DB 적용보다 먼저 있어야 한다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 켜기 전 조회가 컬렉션별로 «꽂힌 개체 수»와 정리가 필요한 건수를 보인다. 정리하지 않고는 켜지 못한다.
- 이미 받은 기록과 장착은 지우지 않는다(정리는 등급 정보를 맞추는 동작이다).

## 선행과 시작 전 확인

- 선행 없음. **7-6의 DB 적용보다 먼저 끝낸다.**
- 시작 때 사용자에게 물을 것: 정리 6건의 내용과 처리 방식(2340의 완료 기록을 먼저 읽고 정한다). 추천안은 시작 때 붙인다.

## 시작 전 조사와 파일 단위 계획 (2026-10-22, 카리나)

**공용 DB 현황(읽기 전용 조회, 2026-10-22)**: 컬렉션 100개(활성 30), 4등급 방식이 켜진 것 0개. 장착 108행(컬렉션 24개, 유저 3명), 옛 완성 기록 3건, 등급별 완성 기록 0건, 등급별 보상 행 0건, 등급별 기본 보상은 common 100·rare 200·epic 400·mystic 800. 여러 등급을 꽂은 유저는 0명이다. 살아 있는 아이템 배지 270개는 전부 common이고 이름이 모두 다르다(소프트 삭제 630개, 소프트 삭제 배지에 꽂힌 슬롯 0건). 컬렉션에 속한 체크인 배지는 0개다. 그래서 지금 켜면 상위 3등급(rare·epic·mystic)은 7-6이 입력하기 전까지 비어 있다.

**2340이 묶음 7로 넘긴 정리 6건**(2340 「잔여 이슈」와 3회 계획 182줄에서 찾았다): ① 등급별 보상(`item_book_tier_rewards`) 입력 화면, ② 등급 보상 배지의 하드 삭제 가드(`badge-references.ts`), ③ `endImpact.ts`의 채우는 유저 수(등급별 완성 기록을 세지 않는다), ④ 소프트 삭제 배지 슬롯을 등급 판별에서 코드는 빼고 222 SQL의 `tier_mismatch`는 넣는 차이, ⑤ `ItemBookRow`의 `tier_mode` 타입 누락, ⑥ 체크인 획득 조회 6곳 복제. 켜기 전 꽂힌 등급 조회(`ITEMBOOK_TIERS.md` 2절)는 이 6건과 별도로 이 티켓의 중심이다.

**회차**: 2회로 나눈다. 아래 파일 수가 `plan_only` 기준(파일 5개 초과 또는 100줄 이상)을 넘어 두 회 모두 `planOnlyWaiver`가 필요하다. DB 변경은 없어 마이그레이션과 롤백 실측은 없다.

**카리나 몫(머지 뒤)**: 로컬 어드민에서 패널과 점검 결과를 보기만 한다. 공용 DB라 «켜기»·«끄기»·보상 저장은 누르지 않고 시험으로 확인한다. 기록과 push.

**7-8 가정(시작 전 확인 대상)**

① 유형 `admin`, 표준 경로, 채원 판정과 사후 리뷰는 없다(어드민 화면은 판정 대상이 아니다). 2회로 나눠 돌리고 회마다 게이트를 돌린다. DB 변경과 마이그레이션은 없다.
② **켜기를 막는 조건은 «여러 등급을 꽂은 유저가 있음» 하나**다. 막히면 컬렉션 id별 유저 수를 보이고, 어드민이 유저의 장착을 대신 풀어 주는 «정리 동작»은 만들지 않는다. 지금 해당 유저가 0명이고, 장착 해제는 인벤토리가 가득 차면 못 하는 규칙과 얽혀 위험하기 때문이다. 건수가 생기면 별도 티켓으로 한다.
③ 이름 점검(한 이름에 같은 등급이 둘 이상, 이름마다 등급 수가 다름)은 **경고로만** 보이고 켜기를 막지 않는다. 7-6이 SQL로 이름을 맞춰 넣으므로 켠 뒤 고칠 수 있고, 이름이 어긋나도 해당 컬렉션이 완성되지 않을 뿐 다른 곳에 번지지 않는다.
④ **끄기는 등급별 완성 기록이 하나라도 있으면 막는다**(삭제 가드와 같은 이유로 기록이 고아가 된다). 없으면 끌 수 있다.
⑤ 4등급이 켜진 컬렉션의 옛 보상 칸(완성 보상 배지, 포인트 보상)은 양식에서 접고 값은 지우지 않는다.
⑥ 등급별 보상은 **포인트를 비우면 기본값**(100·200·400·800, 기본값 편집은 7-2의 설정 구역)을 쓰고 보상 배지는 비울 수 있다(비우면 주지 않는다). **같은 배지를 두 등급에 고르면 저장을 거절한다**(두 등급이 공유하면 한 번만 나가 의도와 어긋난다, 2340 메모).
⑦ `PUT /api/admin/itembooks/[id]`는 계속 `tier_mode`를 쓰지 않는다(기존 시험 유지). 켜기·끄기는 새 라우트 `[id]/tier`, 보상은 `[id]/tier-rewards`가 맡는다.
⑧ 정리 6건 가운데 ①~⑤는 이 티켓에서 처리하고 **⑥ 체크인 획득 조회 6곳 복제는 하지 않는다**. 컬렉션에 속한 체크인 배지가 0개라 영향이 없고, 7-6이 체크인 배지를 컬렉션에 넣는 경우에만 필요하다. 그 경우가 생기면 별도 티켓으로 먼저 처리한다(이 티켓 「잔여 이슈」에 적는다).
⑨ 켜기·끄기의 변경 이력은 남기지 않는다(7-1의 변경 이력 표는 설정 값 전용이다). 필요하면 7-1이 끝난 뒤 한 줄로 연결한다.
⑩ 로컬 확인은 패널 보기와 점검 결과 확인까지만 한다. 공용 DB에서 «켜기»를 누르면 프로덕션 동작이 바뀌므로 누르지 않는다.

## 완료 조건

- 컬렉션 4등급 켜기 칸이 화면에서 바뀌고 변경 이력에 남는다.
- 켜기 전 꽂힌 등급 조회가 정확한 건수를 보인다(시험으로 고정).
- 2340이 넘긴 정리 6건이 처리됐거나 처리하지 않는 이유가 기록돼 있다.

## 진행 기록

- 2026-10-22 가정 ①~⑩을 사용자가 그대로 승인했다. 1회(켜기 전 점검과 켜기·끄기)를 시작한다. 로컬 확인에서 «켜기»·«끄기»는 누르지 않는다.
