# [Content] JAM2 운영과 컨텐츠 문서와 오픈 전후 SQL 적용 순서 목록 (묶음 7, 7-9)

## 핵심 요약

- 요구사항: 묶음 7이 끝난 뒤 PRD, 컨텐츠 문서, 데이터 모델을 맞추고, 오픈 직전과 오픈 뒤에 실행할 SQL의 순서를 한 목록으로 만든다. 5-6 계열(액티비티 배지)의 이름과 설명 원고를 누가 언제 쓸지 정리한다.
- 구현 계획: 문서만(카리나 직접). 오픈 전후 SQL 목록에 들어갈 것(오픈 직전): **트라이브마다 컬렉션 10개 가운데 3개만 활성으로 남기고 나머지 7개를 예약 공개로 바꾸는 일**(7-6이 10개를 모두 활성으로 넣는다, 2026-10-22 사용자 결정, 처음 열 3개는 사용자가 고른다), 마이그레이션 244·245·248(액티비티 배지 비활성화와 새 계열 입력, 이 순서), 7-4의 기존 배지 포인트 적용, 7-7의 쓰지 않는 컬렉션 끄기, 출시 뒤 정리 SQL 266~269와 티켓 `20261022_0938`·`0939`의 정리.
- 관련 파일: `docs/service/prd/`의 어드민·컨텐츠 관련 PRD, `docs/service/content/`, `docs/service/prd/02_DATA_MODEL.md`, 운영 로직 19장, 티켓 `20261018_1816`·`20261019_0542`(혜린 조사(2026-10-22), 카리나가 직접 확인하지는 않았다).

## 배경 / 문제 정의

5-6 계열은 판정 키는 있으나 원고에 이름과 설명이 없어 이 계열이 빈 채 출시될 수 있다. 혜린 추천은 오픈 전에 윈터가 쓰고 입력하는 것이다. 적용 순서가 흩어져 있으면 오픈 직전에 순서를 잘못 실행할 수 있다.

- 남은 일(이 티켓): 7-4 2회(289, 290)와 7-5 뒤에 문서의 미작성 SQL 칸(5-6 입력, 컬렉션 3개로 줄이기, 단서 레시피 공개 시각)을 채우고 테스트 유저 삭제 대상을 사용자와 정한다.
- 2026-10-25 **테스트 유저 삭제는 오픈 직전으로 미룸**(사용자 결정): 사용자가 «모두 삭제해»라고 했으나 에이전트는 운영 DB의 영구 삭제를 실행하지 않고, 사용자가 어드민 유저 화면에서 직접 지운다. 대상 후보 8명(테스트용으로 보이는 jam.local 4개와 실제 계정으로 보이는 gmail 4개, 그중 관리자 2개)과 지우는 순서는 `docs/plan/jam2/12 JAM 2.0 오픈 전후 적용 순서.md` 11절에 있다.
- 2026-10-26 **순서 메모(7-4 닫음 반영)**: 289는 적용했다. 오픈 직전의 액티비티 배지 순서는 244 → 245 → 248 → 245·248의 포인트 합 확인(티켓 1410, 1650) → 290(드라이런과 승인)이다. 290은 활성 액티비티 배지가 계획한 390개일 때만 진행한다. 새 표 `badge_point_backup_289`는 출시 직후 생성 타입 재생성에 포함한다.
- 2026-10-26 **290·291 순서 확정**(사용자 결정): 오픈 직전의 액티비티 배지 순서는 244 → 245 → 248 → 245·248 포인트 합 확인 → **290 → 291** 이다. 290의 가드(활성 액티비티 배지 390개)는 291(390 → 393개)보다 앞에서 통과하고, 291의 포인트 10·20·50은 정책 표 기본값과 같아 290 뒤에 넣어도 어긋나지 않는다. 291 실행 전에 활성 액티비티 배지가 390개인지, 정책 표가 기본값 그대로인지, `badge_point_backup_290`이 있는지(290 적용 여부)를 읽는다. 5-6 입력 SQL 291은 staging에 병합했다(티켓 `20261026_1018`). 문서 12의 4절 2·3번과 291 파일 머리 주석에 같은 결정을 적었다.
- 2026-10-26 **7-5 끝남**(티켓 `20261022_1136` 닫음): 선행 7-1~7-8이 모두 끝났다. 이 티켓의 남은 일은 문서 12의 미작성 SQL 칸(4절 5·6번, 컬렉션 3개로 줄이기와 단서 레시피 공개 시각)이다. 두 칸은 «예약 공개 방식과 트라이브 간 시기»가 운영 이슈로 보류돼 있어 그 결정 뒤에 쓴다.
- 2026-10-26 **오픈 직전 SQL 점검표 추가**(사용자 요청, 카리나): `docs/plan/jam2/12 JAM 2.0 오픈 전후 적용 순서.md`에 4.1절을 더했다. 244 → 245 → 248 → 포인트 합 확인 → 290 → 291 → 282 순서로 단계마다 실행 전 읽기 확인(기대값과 오늘 값), 실행 직후 확인, 되돌림을 한 표에 모았다. 오늘(2026-10-26) 공용 DB를 읽기 전용으로 확인한 값은 244 가드 대조(유지 270행·61계열·끄기 364·게이트 키 든 유지 행 72), 활성 액티비티 배지 634, 새 계열 행 0, 정책 표 기본값, 컬렉션 69·계획 50·끄기 후보 19, 허용 키 CHECK의 `jam_week_streak`·`same_spot_checkin_days`, `walking:K3` 6행·이미지 6행이다. 롤백 실측 기록이 없는 248·290·291은 오픈 직전에 실측한다(290·291은 244·245·248 적용 뒤에만 가능). 12 문서 1절의 낡은 «모든 SQL은 파일마다 채팅에서 사용자 승인» 문장은 `orchestrator.md` 4절(승인 대신 점검, 2026-10-25)을 가리키도록 고쳤고, 290만 드라이런을 보이고 승인받는 예외(2026-10-24)로 남겼다.
- 2026-10-26 **보류했던 컬렉션 공개 결정 확정**(사용자 답변, 질문창): ① 처음 열 3개를 뺀 컬렉션 35개는 **꺼 둔 채(`is_active=false`) 시작**하고 오픈 뒤 운영자가 어드민에서 컬렉션마다 직접 켠다. ② 다섯 트라이브가 같은 날 열지, 엇갈릴지는 정하지 않고 운영자가 어드민에서 수동으로 정한다. ③ 오픈 예정일은 개발이 끝나지 않아 미정이다. 두 SQL(문서 12 4절 5·6번)은 날짜를 쓰지 않으므로 오픈일 없이 쓸 수 있다: 5번은 35개를 끄는 SQL, 6번은 처음 여는 컬렉션 15개로 짝이 이뤄지는 단서 레시피 7개(28건)의 공개 시작을 비우는 SQL이다(나머지 52건은 자리 값 2099-01-01 KST 그대로). 결정의 결과로 오픈 때 필요한 아이템 배지 이미지는 1,800개가 아니라 처음 여는 컬렉션 15개의 540개이고 1,260개는 각 컬렉션을 켜기 전에 만들면 된다(코드로 읽어 확인, 문서 12 4절 1번). 컬렉션을 켤 때 함께 열 레시피는 문서 12의 9.1절 표에 정리했다. 오늘 읽은 값: 컬렉션 50개 모두 활성이고 공개 시작일이 없다(아무것도 하지 않으면 오픈 첫날 트라이브마다 10개가 모두 열린다), 단서 레시피 80건은 자리 값, 옛 레시피 3건은 상시 공개. 두 SQL의 작성과 실행(오픈 직전)은 사용자 지시를 받은 뒤 한다.
- 2026-10-26 **사용자 결정**: 컬렉션 7개의 예약 공개 방식과 다섯 트라이브의 공개 시기는 운영 이슈로 보류했다(4절 5·6번 SQL은 정해질 때까지 미작성). 7-5(밸런스 서브 대시보드)는 «목표와 부족 안내만» 보이고 오픈 전에 만든다. 트라이브 소개(`tagline`) 후보는 문서 12절에 있다.
- 2026-10-26 **tagline 5개 입력 완료**(사용자가 윈터 추천안을 승인, 공용 DB `apply_migration` 이름 `seed_tribe_taglines`, 파일 `jam-web/supabase/migrations/seed_tribe_taglines_20261026.sql`, 가드 5행 통과). 읽기로 5개 행에 소개가 들어갔고 옛 트라이브 3곳은 비어 있음을 확인했다. 되돌림은 5개를 NULL로 돌리는 한 문장이다.
