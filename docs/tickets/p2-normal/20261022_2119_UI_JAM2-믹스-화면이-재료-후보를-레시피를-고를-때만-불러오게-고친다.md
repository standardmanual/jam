# [UI] JAM2 등급 올리기를 레시피 없이 규칙으로 처리하고 믹스 화면에 입구를 둔다 (묶음 7, 7-7a)

## 핵심 요약

- 요구사항: 등급 올리기를 **아이템마다 만드는 레시피 1,350건이 아니라 규칙 하나**로 처리한다(2026-10-23 사용자 결정). 유저가 같은 등급의 아이템 배지 5개(트라이브는 상관없다)를 내면, 결과의 **등급이 확률로 정해지고(재료 등급 이상)** 그 등급의 아이템이 **균등 무작위**로 나온다. 믹스 화면에 «등급 올리기» 입구를 따로 둔다. 믹스의 «확률 없이 결과가 나온다» 원칙(운영 로직 8.4절)에 이 예외를 적고 확률 안내 페이지(18장)에 올린다.
- 구현 계획: 시작 때 채원 사전 판정(입구 모양, 확률 문구)을 받고 회차를 정한다. 7-7의 283(등급 올리기 레시피 1,350건 SQL)은 **적용하지 않고 폐기**하며, 그 정리(파일, 생성기 함수, 시험, 문서, 정책 카드)를 첫 회차에 함께 한다. 이 티켓이 끝나기 전에는 믹스 화면 구조를 바꿀 필요가 없다(레시피가 83건뿐이다).
- 관련 파일(시작 때 아현이 줄 위치를 다시 확인한다): 믹스 실행 `jam-web/src/lib/combine/index.ts`(`combineRecipeAttempt`, `grantResults`, `getPendingCount`), 받지 않은 결과 `lib/combine/pending.ts`, 캡슐의 등급·아이템 굴림 `lib/capsule/capsuleRoll.ts`·`open.ts`, 등급 확률 `lib/capsule/policy.ts`(`rarity_*`), 믹스 화면 `app/(main)/combine/CombineClient.tsx`, 확률 안내 `lib/probability/disclosure.ts`와 `/probability` 페이지, 운영 로직 8.4절·18장

## 배경 / 문제 정의

7-7 시작 전 조사(카리나, 2026-10-22)에서, 등급 올리기를 2026-10-18 결정대로 «슬롯 후보 목록으로 만든 보통 레시피»로 만들면 레시피가 1,433건(등급 올리기 1,350건 + 단서 80건 + 옛 3건)이 되고, 믹스 화면이 열릴 때 후보 약 607,500개(추정 약 107MB)를 한 번에 내려보내는 구조라 화면이 열리지 않을 수 있음이 드러났다. 이 티켓은 처음에 그 화면을 고치는 일(후보 지연 읽기, 설명 굵은 글씨)이었다. 사용자가 «레시피가 왜 이렇게 많냐»고 물어 컬렉션이 열릴 때마다 레시피 27건을 만들고 여는 운영 부담까지 확인한 뒤, 레시피 없이 규칙으로 처리하는 쪽으로 방향을 바꿨다(2026-10-23). 이 때문에 후보 지연 읽기, 설명 굵은 글씨, 가방 시트 «가진 것만», 검색 범위, 목록 «더 보기»는 필요 없어졌다.

## 사용자 결정 (2026-10-23)

1. **레시피 없이 규칙으로 처리한다.** 등급 올리기용 레시피 행을 만들지 않는다. 7-7의 283(1,350건)은 폐기한다.
2. **재료**: 같은 등급의 아이템 배지 5개. **트라이브, 컬렉션, 아이템 이름은 상관없다**(등급 기준으로 아무거나). 처음에는 «같은 트라이브»를 조건에 넣었으나 사용자가 «조건에서 트라이브는 제외»로 정정했다(2026-10-23). Mystic은 재료가 되지 않는다(2026-10-10 결정 그대로). 잠긴·장착한 개체는 쓸 수 없다(믹스와 같은 규칙).
3. **역할은 처분용**이다. 겹친 배지 5개를 내면 새 아이템 1개를 받고, **운이 좋으면 윗등급**이 나온다. 윗등급이 꼭 나오지는 않는다. 사용자 의견: 드랍·픽업에서도 윗등급을 얻을 여지가 있어 괜찮다.
4. **결과의 등급은 확률로 정한다.** 캡슐의 등급 확률(`capsule_policy`의 `rarity_*`, 2026-10-23 공용 DB 값은 Common 70, Rare 22, Epic 6, Mystic 2)을 «재료 등급 이상»으로 잘라 합이 100%가 되게 다시 맞춘다. Common 재료는 Common 70%, Rare 22%, Epic 6%, Mystic 2%. Rare 재료는 Rare 약 73.3%, Epic 20%, Mystic 약 6.7%. Epic 재료는 Epic 75%, Mystic 25%. 재료보다 낮은 등급은 나오지 않는다. (정정: 카리나가 처음에 이 값을 «동기화와 캡슐 모두 70/22/6/2»라고 잘못 말했다. 동기화(`jam_policy`)는 84/13/2.5/0.5다. 사용자가 확정한 제안의 숫자는 캡슐 쪽이므로 캡슐을 쓴다. 동기화 값을 쓰면 윗등급 확률이 Common 재료 16%, Rare 18.75%, Epic 약 16.7%로 낮아진다.)
5. **아이템은 균등 무작위**다. 정해진 등급의 아이템을 열린 컬렉션(활성) 안에서 같은 확률로 뽑는다. 어느 트라이브의 컬렉션에서 뽑는지는 가정 (바)다. «못 가진 것 우선»은 쓰지 않는다.
6. **원칙을 바꾼다.** 운영 로직 8.4절의 «정해진 레시피대로 확률 없이 결과가 나온다»에 «등급 올리기만 예외로 결과가 확률로 정해진다»를 더한다. 확률 안내 페이지(18장)에 등급 올리기 표를 올린다.

## 가정 (카리나, 구현 시작 전 사용자가 바로잡을 수 있다)

- (가) 결과는 열린 채 지급한다(잠긴 결과 없음). 인벤토리 빈칸이 모자라면 믹스와 같이 «받지 않은 결과»로 남기고 받기 전에는 새 믹스와 등급 올리기를 할 수 없다. 이용 정지 중이면 막는다.
- (나) 챕터 점수는 믹스 성공과 같이 20점을 센다. 액티비티 배지의 «믹스 시도·성공·실패 횟수»와 «레시피 첫 성공» 조건에는 넣지 않는다(레시피가 아니다).
- (다) 기록은 `user_combine_success_logs`를 쓰지 않는다(`recipe_id`가 필수라 레시피가 없는 이 믹스를 담을 수 없다). 시작 때 새 기록 표를 하나 더하는 안(추가만)과 기록 없이 가는 안 중 사용자에게 묻는다. DB 실행은 사용자 승인 뒤 카리나가 한다.
- (라) 확률은 캡슐 설정을 읽는다. 캡슐 등급 확률을 바꾸면 등급 올리기도 함께 바뀌고, 확률 안내 페이지도 따라 바뀐다(캡슐 칸에는 이미 «확률 안내에 반영되는 칸은 확인창이 뜬다» 규칙이 있다). 따로 조정하고 싶으면 오픈 뒤 밸런스 설정에 칸을 더한다.
- (마) 아이템 풀을 고르는 조건(삭제, 드랍 제외, 공개 기간, 컬렉션 활성)은 캡슐의 아이템 굴림과 같은 것을 쓴다. 풀이 비면 재료를 소각하기 전에 거절한다.
- (바) **결과 아이템의 트라이브**: 재료에서 트라이브 조건을 뺐으므로 결과의 트라이브는 따로 정해야 한다. 캡슐의 트라이브 굴림(내 트라이브가 기본이고 다른 트라이브일 확률 `capsule_policy.other_tribe_probability`, 공용 DB 0.2)을 그대로 쓴다고 가정한다. 이러면 유저가 소속 트라이브의 컬렉션을 채우는 흐름이 유지되고, 확률 안내의 «다른 트라이브일 확률» 문장도 캡슐과 같다. 대안은 열린 컬렉션 전체에서 트라이브 구분 없이 같은 확률로 뽑는 것인데, 오픈 때 트라이브가 5곳이라 소속 트라이브 아이템이 나올 확률이 약 20%로 떨어진다. 사용자가 다르게 정하면 바꾼다.
- (사) 재료는 `type = item`이고 등급 값이 있는 내 개체다. 옛 트라이브·옛 컬렉션의 아이템 배지도 포함되는지(등급 값이 모두 있는지)는 시작 때 공용 DB를 읽어 확인한다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 서버 규칙 하나(`lib/combine/`)와 API 하나. 재료 검사(5개, 같은 등급, Mystic 아님, 잠김·장착 아님, 내 것)가 모두 통과한 뒤에만 재료를 소각하고, 등급과 아이템을 굴려 지급한다. 소각 앞의 관문은 믹스와 같다(이용 정지, 받지 않은 결과).
- 굴림은 서버에서만 한다(클라이언트가 확률이나 결과를 정하지 않는다). 같은 입력에 같은 결과가 나오지 않으므로 시험은 난수를 주입한다.
- 확률 안내(`disclosure.ts`와 `/probability`)에 등급 올리기 표를 더한다. 읽기에 실패하면 기본값으로 대신하지 않는 기존 원칙을 따른다.
- 오픈 직전 목록(7-9)에서 «컬렉션이 열릴 때 등급 올리기 레시피 27건을 여는 SQL»은 필요 없어진다.

### UI/UX 관점

- 믹스 화면에 «등급 올리기» 입구를 둔다. 같은 등급 배지를 5개 고르면 결과가 나온다. 모양, 문구, 확률 안내 링크는 채원 사전 판정으로 정한다(시작 때). 결과 문구는 «운이 좋으면 윗등급»이라는 사실을 숨기지 않는다.

## 완료 조건

### 구현 범위 (게이트 판정 대상, 회차마다 해당 항목)

- 같은 등급의 내 아이템 배지 5개를 내면 재료가 소각되고 결과 1개가 지급된다. 결과 등급은 재료 등급 이상이고 확률은 결정 4와 같다(난수를 주입한 시험으로 고정).
- 재료 등급별 결과 등급 확률의 합이 100%이고 재료보다 낮은 등급은 나오지 않는다. Mystic 재료, 5개가 아닌 재료, 다른 등급이 섞인 재료, 잠기거나 장착한 개체, 남의 개체는 소각 없이 거절된다.
- 인벤토리 빈칸이 모자라면 받지 않은 결과로 남고, 받지 않은 결과가 있으면 새 등급 올리기와 믹스가 막힌다. 이용 정지 중이면 막힌다.
- 확률 안내 페이지에 등급 올리기 표(재료 등급별 결과 등급 확률, 아이템은 균등)가 있고 캡슐 설정을 바꾸면 따라 바뀐다.
- 운영 로직 8.4절에 예외 문장이 있고, 283과 관련 문서·카드가 정리됐다.

### 후속 범위 (담당: 카리나, 시점: 머지 뒤)

- 로컬 개발 서버에서 입구가 열리고 재료를 골라 결과가 나오는지 확인한다(공용 DB를 바꾸지 않는 시험 계정으로 한다).
- 기록 표를 더한다면 SQL을 롤백 실측하고 사용자 승인 뒤 적용한다.
