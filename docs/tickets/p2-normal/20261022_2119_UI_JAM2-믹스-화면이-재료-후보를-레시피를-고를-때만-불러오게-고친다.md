# [UI] 믹스 화면이 재료 후보를 레시피를 고를 때만 불러오게 고친다 (묶음 7, 7-7a, 등급 올리기 1,350건 대비)

## 핵심 요약

- 요구사항: 믹스 화면(`/combine`)은 열릴 때 공개된 레시피 전부와 칸마다 후보 배지의 상세(이름, 설명, 그림, 등급)를 한꺼번에 읽어 클라이언트에 내려보낸다. 등급 올리기 레시피 1,350건이 들어오면 칸 6,750개에 후보가 약 60만 개라 화면이 열리지 않을 수 있다. 레시피 목록에는 이름, 보상 미리보기, 재료 수 정도만 내려보내고, 칸별 후보 상세는 유저가 레시피를 골랐을 때 읽게 고친다.
- 구현 계획: 아현이 시작할 때 채원 사전 판정(레시피 고르기 흐름의 모양)을 받고 회차를 정한다. 모양은 지금 믹서 화면을 최대한 그대로 둔다. 7-7(`20261022_1138`)의 등급 올리기 입력(마이그레이션 283)은 이 티켓이 staging에 반영된 뒤에 공용 DB에 적용한다.
- 관련 파일(시작 때 아현이 줄 위치를 다시 확인한다): `jam-web/src/app/(main)/combine/page.tsx`(레시피 전체 조회 30줄 부근, 칸 조회 `.in('recipe_id', …)` 77줄 부근, 후보·보상 배지 상세 조회와 `slotsByRecipe` 조립 90~145줄), `jam-web/src/app/(main)/combine/CombineClient.tsx`(`RecipeWithSlots` 타입, 검색 `recipeMatchesSearch` 400줄 부근, 칸 선택 흐름), `jam-web/src/lib/combine/visibility.ts`, 시험 `CombineClient.test.tsx`

## 배경 / 문제 정의

티켓 `20261022_1138`(7-7) 시작 전 조사(카리나, 2026-10-22, 읽기 전용)에서 드러났다. 2026-10-18 결정(등급 올리기는 별도 종류 없이 슬롯 후보 목록으로 만든 보통 레시피, 전용 화면 없음)대로 레시피 행을 만들면 화면이 한 번에 감당할 양이 아니다.

- 지금 공용 DB의 레시피는 3건이다. 단서 20건이 더해져도 화면은 문제없다. 문제는 등급 올리기 1,350건이다(트라이브 5곳 × 아이템 이름 90종 × 올릴 등급 3개).
- 칸마다 후보는 같은 트라이브·같은 등급의 아이템 배지 90종이고 칸이 5개다. 후보 참조는 1,350 × 5 × 90 = 607,500개이고, 화면은 참조마다 후보 상세 한 건을 만들어 내려보낸다(후보 사이의 중복도 합치지 않는다).
- 레시피 id 1,350개를 `.in(…)` 조건으로 보내 요청 주소가 매우 길어진다. 후보·보상 배지 상세 조회도 아이템 배지 1,800개 전체(등급별 후보와 보상을 합친 수)의 id를 주소에 싣는다. 호스팅의 주소 길이 한도에서 거절될 가능성이 있다(확인하지 못했다).
- 운영자는 공개 전 레시피까지 믹스 화면에서 보므로, 공개 전으로 숨긴 레시피를 넣어도 운영자 화면은 같은 문제를 겪는다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 목록 응답에는 후보 상세(이름, 설명, 그림)를 싣지 않는다. 레시피 id를 `.in(…)`에 길게 싣는 조회도 없앤다.
- 유저가 레시피를 고르면 그 레시피의 칸과 후보를 읽는다(서버 라우트 하나 또는 서버 액션). 읽기 전에도 «칸 개수»와 «이 칸에 넣을 수 있는 아이템 배지 수»는 보일 수 있어야 한다.
- 이미 가진 재료로 채울 수 있는 레시피를 먼저 보여 주는 정렬이 있다면 지금 동작을 유지한다(시작 때 확인).
- 온보딩 연출 모드(`questStep`)와 운영자의 공개 전 레시피 보기는 지금 동작을 유지한다.

### UI/UX 관점

- 레시피 고르기와 칸 채우기 화면의 모양은 바꾸지 않는다. 후보를 읽는 동안의 짧은 로딩 표시만 더한다(채원 사전 판정으로 정한다).

## 구현 계획

시작 때 지금 화면의 응답 크기와 응답 시간을 레시피 3건(지금)과 레시피 1,371건·후보 60만 개(모의 자료)에서 재서 기준선으로 티켓에 적는다. 그 뒤 후보를 지연해서 읽는 구조로 고치고 같은 두 조건에서 다시 잰다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)

- 레시피 목록 응답에 칸별 후보 상세가 없고, 요청 주소 길이가 레시피 수에 비례해 늘지 않는다.
- 레시피를 고르면 칸과 후보가 지금과 같은 모양으로 열리고, 재료를 넣어 믹스하는 흐름이 지금과 같다(시험으로 고정).
- 레시피 1,371건과 후보 60만 개를 가진 모의 자료에서 목록 응답 크기와 시간이 레시피 3건일 때와 같은 자릿수다(측정값을 티켓에 남긴다).

### 후속 범위 (담당: 카리나, 시점: 머지 뒤)

- 로컬 개발 서버에서 믹스 화면이 열리고 레시피를 골라 후보가 보이는지 확인한다.
- 7-7의 마이그레이션 283(등급 올리기 1,350건)을 사용자 승인 뒤 공용 DB에 적용하고 적용 뒤 믹스 화면을 다시 확인한다.
