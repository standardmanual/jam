# [Infra] syncIssue 시험 두 건이 루프 안의 expect 때문에 느린 CI 러너에서 시간 초과한다

## 핵심 요약

- 요구사항: `jam-web/src/lib/drop-engine/__tests__/syncIssue.test.ts`의 «활동마다 1~3개다 (등산 제외)»와 «등산은 최소 2개이고 최대 4개다» 두 시험이 20만 번 반복하는 루프 안에서 매번 `expect()`를 불러 로컬에서도 각각 2초쯤 걸리고, 느린 CI 러너에서는 기본 제한 5초를 넘겨 `Test timed out in 5000ms`로 실패한다. 이 두 건이 GitHub `verify`의 `test` 단계를 간헐적으로 빨갛게 만든다.
- 구현 계획: 루프 안에서는 최솟값·최댓값(과 나온 값의 집합)만 모으고, 루프가 끝난 뒤 한 번씩 단언한다. 범위 밖 값이 하나라도 나오면 여전히 실패하므로 시험의 의미는 그대로다.
- 관련 파일: `jam-web/src/lib/drop-engine/__tests__/syncIssue.test.ts`(65~90행 부근 두 시험)

## 배경 / 문제 정의

티켓 `20261022_2119`(7-7a) 4회의 게이트(민지)가 CI `test` 단계 실패로 FAIL을 냈고, 로컬에서는 전체 시험이 통과해 원인을 찾지 못했다. `verify.sh`가 CI에서 시험 로그를 출력하지 않아서(티켓 `20261023_1423`) 진단용 브랜치로 CI를 한 번 돌려 로그를 열어 보니, 실패는 이 두 시험의 시간 초과 두 건뿐이었다(796개 파일 중 1개, 17,224건 중 2건). 이 두 시험은 4회가 건드리지 않은 파일이다. 같은 시험이 로컬 전체 시험에서도 부하가 높을 때 5초를 넘겼다(7-7a 1회·2회 머지 시험, 아현의 보고). 같은 코드의 다른 CI 실행이 성공한 것은 러너 속도 차이로 보인다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 두 시험의 단언 의미를 바꾸지 않는다(모든 호출이 범위 안이어야 한다).
- 평균을 재는 다른 시험(`meanCount`)은 루프 안에 expect가 없어 영향이 작다. 이번에는 두 시험만 고친다.

## 완료 조건

- 두 시험이 각각 수십 ms 안에 끝나고 통과한다.
- 범위 밖 값이 나오면 실패한다(단언 의미 유지).
- 진단용 CI 실행에서 `test` 단계가 통과한다.

- 닫기는 사용자 승인(2026-10-23, «닫아»)으로 했다.

- CI에서 실패한 단계의 로그가 보이지 않는 문제는 티켓 `20261023_1423`이다.
