# [Feature] JAM2 등급 올리기를 «컬렉션 고르기 + 윗등급 70%»로 바꾼다 (묶음 7, 7-7b)

## 핵심 요약

- 요구사항: 티켓 `20261023_1308`의 모의 실험에서 7-7a 규칙(결과 등급은 캡슐 확률, 아이템은 열린 컬렉션 전체에서 무작위)은 러닝 보통 Rare 컬렉션이 15달, Epic·Mystic은 5년 넘게 걸려 첫 완성 시간 목표를 크게 벗어났다. 사용자가 추천안 **«컬렉션 고르기 + 윗등급 70%»**를 골랐다(2026-10-23). 등급 올리기는 같은 등급 5개를 내면 **유저가 고른 컬렉션 안에서** 아이템이 같은 확률로 나오고, 결과 등급은 **재료 등급의 바로 위가 70%, 같은 등급이 30%**다. 70%는 밸런스 설정에서 바꿀 수 있는 칸으로 둔다.
- 구현 계획: 4회로 나눈다. 1회 DB 칸 추가(적용은 사용자 승인 뒤), 2회 서버 규칙·API·확률 안내, 3회 컬렉션 고르는 화면(채원 사전 판정부터), 4회 어드민 밸런스 칸·정책 카드·문서.
- 관련 파일(시작 때 아현이 줄 위치를 다시 확인한다): `jam-web/src/lib/combine/tierUpOdds.ts`(`tierUpProbabilities`), `jam-web/src/lib/combine/tierUp.ts`(`rollTierUp`·`tierUp`), `jam-web/src/app/api/combine/tier-up/route.ts`, `jam-web/src/lib/combine/policy.ts`, `jam-web/src/lib/probability/disclosure.ts`와 `jam-web/src/app/(legal)/probability/page.tsx`, `jam-web/src/app/(main)/combine/`(`page.tsx`, `CombineClient.tsx`, `TierUpPanel.tsx`, `tierUpClient.ts`), `jam-web/src/lib/admin/balance/collection.ts`와 `jam-web/src/components/admin/balance/CollectionSection.tsx`, `jam-web/src/lib/admin/policyDashboard/policiesData.ts`

## 배경 / 문제 정의

7-7a(티켓 `20261022_2119`)에서 등급 올리기를 레시피 없이 규칙으로 처리하기로 하며, 결과 등급을 캡슐 등급 확률에서 재료 등급 이상으로 잘라 정하고 아이템은 열린 컬렉션 전체에서 균등하게 뽑기로 했다. 머지 뒤 밸런스 문서 5절의 첫 완성 시간 표(Rare 3달, Epic 12달)를 새 규칙으로 다시 계산해 보니(티켓 `20261023_1308`, `scripts/balance-sim/collection-sim.mjs`) 목표와 크게 어긋났다. 원인은 둘이다. Common 5개가 Rare 이상이 될 확률이 30%뿐이고, 결과가 열린 컬렉션 전체(27~90칸)에 흩어져 내가 채우는 컬렉션의 빈칸이 나올 확률이 작다. 한 가지만 바꿔서는 Epic이 1~2년에 닿지 않아 둘을 함께 바꾼다.

모의 실험의 이 안(조정7) 값(중앙값): 러닝 보통 Rare 5.1달, Epic 19.5달, Mystic 5년 넘음. 걷기 보통 Rare 6.9달, Epic 25달. 등산 보통 Rare 7.6달, Epic 28달. 자전거 열심 Rare 3.0달, Epic 10.3달, Mystic 41달.

## 사용자 결정 (2026-10-23)

1. 추천안 **컬렉션 고르기 + 윗등급 70%**로 간다. 7-7a의 결정을 다음처럼 바꾼다. 결정 4(결과 등급 확률을 캡슐 확률에서 자름)는 «바로 위 등급 70%, 같은 등급 30%»로, 결정 5(열린 컬렉션 전체에서 균등)와 가정 (바)(캡슐의 트라이브 굴림)는 «유저가 고른 컬렉션 안에서 균등»으로, 가정 (라)(캡슐 등급 확률과 연동)는 «등급 올리기 전용 확률 칸»으로 바뀐다. 재료(같은 등급 5개, 트라이브·컬렉션·이름 무관, Mystic 제외, 잠김·장착 제외), 처분용 역할, 열린 채 지급, 챕터 점수는 그대로다.

## 가정 (카리나, 시작 전 사용자가 바로잡을 수 있다)

- (가) 고를 수 있는 컬렉션은 **소속 트라이브의 열린 컬렉션**(활성, 공개 기간 안, 드랍 제외 아님) 가운데 재료 등급의 바로 위 등급 아이템 배지가 하나 이상 있는 것이다. 다른 트라이브의 컬렉션은 고르지 못한다(모의 실험과 같다). 다른 트라이브까지 열지는 오픈 뒤 지표를 보고 정한다.
- (나) 윗등급 확률은 **한 칸**이다(재료 등급마다 따로 두지 않는다). Epic 5개가 Mystic이 될 확률도 같은 값이다. 칸은 `combine_policy.tier_up_probability`(0 이상 1 이하, 기본값 0.7)이고 어드민에는 «%»로 보인다.
- (다) 결과 등급(바로 위 또는 같은 등급)의 후보가 고른 컬렉션에 없으면 재료를 소각하기 전에 거절한다(`no_candidate`). 아래 등급으로 내려가지 않는다. 고르는 목록에서 후보가 없는 컬렉션(옛 컬렉션처럼 Common뿐인 것)은 미리 뺀다.
- (라) 윗등급 확률을 바꾸면 확률 안내 페이지에 함께 반영되고, 밸런스 설정은 저장 전에 확인창을 띄운다(`affectsDisclosure`).
- (마) **DB는 추가만 한다**: `combine_policy`에 칸 하나(`ADD COLUMN`, 기본값 0.7, 0~1 `CHECK`). 적용은 롤백 실측 뒤 **사용자 승인을 받고 카리나가** 한다. 코드는 칸이 DB에 없어도 기본값 0.7로 움직여(`getCombinePolicy`의 폴백) DB 적용 앞뒤 어느 쪽에서도 깨지지 않지만, 확률 안내(엄격히 읽음)와 어드민 칸은 칸을 읽으므로 **DB 적용 뒤에** 머지한다.
- (바) 결과의 지급, 받지 않은 결과, 챕터 점수 20점, 액티비티 배지 지표 제외는 7-7a와 같다. 결과 아이템의 트라이브는 고른 컬렉션의 트라이브(= 소속 트라이브)다.

## 상세 요구사항

### 서비스/코드베이스 관점

- `tierUpProbabilities(재료 등급, 윗등급 확률)`은 `[[재료 등급, 1 - p], [바로 위 등급, p]]`를 돌려준다. 확률 0인 줄도 남기고, 서버 굴림과 확률 안내가 같은 함수를 쓴다(7-7a 4회의 `tierUpOdds.ts` 구조를 지킨다). Mystic 재료는 지원하지 않는다(던진다).
- 서버 규칙: 입력에 `collectionId`(아이템북 id)를 더한다. 순서는 7-7a 「2회 규칙 명세」의 ①~⑪을 따르되 ⑥과 ⑦ 사이에 «고른 컬렉션 검사»를 넣는다(소속 트라이브의 열린 컬렉션이 아니면 `invalid_collection`, 소각 전). ⑦ 굴림은 등급을 `tierUpProbabilities`로 정하고 아이템을 고른 컬렉션의 그 등급 후보에서 균등하게 뽑는다(`pickItemBadge`가 쓰는 `listIssueCandidates`의 조건과 같다). 트라이브 굴림과 `other_tribe_probability`는 쓰지 않는다. 난수는 등급(1번) → 아이템(1번) 순서다.
- API: `POST /api/combine/tier-up` 본문이 `{ itemIds, collectionId }`가 된다. `invalid_collection`은 200 `success:false`(다른 소각 전 거절과 같은 규칙)다.
- DB: 마이그레이션은 `combine_policy`에 `tier_up_probability NUMERIC NOT NULL DEFAULT 0.7 CHECK (tier_up_probability >= 0 AND tier_up_probability <= 1)`을 더한다. 되돌림 SQL(`DROP COLUMN`)을 파일에 적는다. 생성 타입(`database.generated.ts`)과 `CombinePolicyRow`를 같은 커밋에서 맞춘다(Supabase CLI가 없어 MCP `generate_typescript_types`로 대조한다).
- 확률 안내: `disclosure.ts`가 `combine_policy.tier_up_probability`를 **엄격하게** 읽는다(읽기 실패·범위 밖이면 이 섹션을 숨기고 기본값으로 대신하지 않는다, 7-7a 4회와 같은 규칙). 표는 재료 등급마다 두 줄(예: Common 5개를 넣으면 Rare 70%, Common 30%)이다. 문구를 새 규칙에 맞춘다: 받는 컬렉션은 내가 고르고 그 안의 아이템 배지는 모두 같은 확률로 나온다는 설명을 쓰고, «캡슐의 등급 확률에서 … 비율을 다시 맞춘 값» 문장과 «한 등급씩 낮춰서 무작위로 골라요» 문장, «다른 트라이브의 것일 확률» 표는 뺀다. 문구는 승인이 필요하다(공개 페이지).

### UI/UX 관점

- 믹스 화면의 등급 올리기 화면에 **컬렉션을 고르는 단계**를 더한다. 어디에 어떻게 보일지(재료 5개를 채운 뒤인지, 먼저인지), 고를 수 있는 컬렉션 목록의 모양(이름, 진행 상태 여부), 결과 문구가 «윗등급이 나왔어요»·«같은 등급이 나왔어요»에 컬렉션 이름을 더할지는 **채원 사전 판정**으로 정한다. 새 문구는 사용자 승인을 받는다.
- 화면의 설명 문단(«운이 좋으면 윗등급이 나오고…»)이 새 규칙과 맞는지 판정에서 다시 본다.

### 어드민 관점

- 밸런스 설정 «컬렉션과 믹스» 구역에 «등급 올리기 윗등급 확률»(단위 %, 0~100) 칸을 더한다(`COLLECTION_FIELDS`, `combine_policy`에서 읽고 쓰기). 확률 안내에 반영되는 칸이므로 `affectsDisclosure`는 `true`다(저장 확인창이 뜬다). 운영 신호 받은편지함의 밸런스 평가(`lib/admin/opsInbox/balance`)와 정책 대시보드 카드도 맞춘다.

## 완료 조건

### 구현 범위 (게이트 판정 대상, 회차마다 해당 항목)

- 같은 등급(Common, Rare, Epic) 5개와 고른 컬렉션을 내면 재료가 소각되고 **고른 컬렉션의 아이템 1개**가 지급된다. 결과 등급은 재료 등급의 바로 위가 윗등급 확률, 같은 등급이 나머지다(난수를 주입한 시험으로 고정). 윗등급 확률 0과 1, 기본값 0.7이 모두 맞다.
- 소속 트라이브의 열린 컬렉션이 아니거나 결과 등급 후보가 없는 컬렉션은 소각 없이 거절된다. Mystic 재료, 5개가 아닌 재료, 다른 등급이 섞인 재료, 잠기거나 장착한 개체, 남의 개체도 소각 없이 거절된다.
- `combine_policy.tier_up_probability` 마이그레이션은 추가만 하고 되돌림 SQL이 있으며 롤백 실측을 마쳤다. 코드는 칸이 DB에 없어도 기본값 0.7로 움직인다.
- 확률 안내 페이지의 등급 올리기 표가 재료 등급마다 두 줄이고 설정 값을 바꾸면 따라 바뀐다. 읽기 실패 때는 숨기고 기본값으로 대신하지 않는다.
- 믹스 화면에 컬렉션을 고르는 단계가 있고, 고르지 않으면 제출할 수 없다. 레시피 믹서 화면은 달라지지 않는다.
- 밸런스 설정에서 윗등급 확률을 바꿀 수 있고 저장 전에 확인창이 뜬다.
- 문서(운영 로직, PRD, 밸런스 문서 5절, UX Writing)와 정책 카드가 새 규칙과 맞는다.

### 후속 범위 (담당: 카리나, 시점: 머지 뒤)

- 1회 SQL 롤백 실측과 공용 DB 적용(사용자 승인 뒤). **2026-10-23 완료.**
- staging 실렌더(360·390px): 믹스 화면의 컬렉션 고르기(행, 시트, 긴 컬렉션 이름과 정적 행 문장의 줄바꿈). 확률 안내의 새 표·소개 문단, 믹스 화면의 «넣은 재료는 사라져요» 위치, 어드민 입력칸·확인창은 2026-10-25에 확인했다(아래 메모). 데이터가 있는 계정이 필요한 컬렉션 행·시트는 미확인이다.
- 오픈 뒤 밸런스 서브 대시보드의 첫 완성 시간으로 다시 맞춘다(티켓 `20261023_1308`).

### 구현 내용 요약
