# [Feature] 어드민을 운영·생태계·개발배포 세 축의 상황판으로 다시 짠다 (상위)

## 핵심 요약

- 요구사항: 어드민을 세 축의 상황판으로 다시 짠다. ① 운영: 에이전트 기획의 흐름과 내 결정. ② 생태계: 순환과 정책. ③ 개발·배포: 진행과 배포 현황. 흐름·상태·내 결정이 한눈에 보이고, 기획 이유(트렌드 등)가 칩으로 보여야 한다.
- 구현 계획: 아래 하위 티켓을 순서대로 진행한다. 스펙 정본은 `docs/service/prd/admin-boards/PRD.md`, 화면 시안은 https://claude.ai/artifact/WJGwKczbiCTryjKvTWwo7i 다.
- 관련 파일: `jam-web/src/app/admin/page.tsx`·`_home/sections.tsx`, `jam-web/src/components/admin/ops/`, `jam-web/src/lib/admin/opsInbox/`, `jam-web/src/app/admin/policy-dashboard/`, `docs/service/prd/content-automation/PRD.md`

## 배경 / 문제 정의

2026-10-26 사용자가 지금 운영툴 화면에 피드백을 줬다: 글이 길고 많다, 에이전트별 상태와 흐름이 안 보인다, 승인·취소 같은 상태와 버튼이 흐름에서 명확하지 않다, 내가 무엇을 결정해야 하는지 알기 어렵다, 기획의 이유와 트렌드가 안 보인다. 원인 대조는 PRD §2다.

같은 날 조사한 사실:
- 운영툴 받는 쪽(받은 기획함·상세·일정표·패턴 사전·예약 대상 6종 핸들러)은 대부분 구현돼 있다.
- 에이전트가 실제로 묶음을 제출한 적은 없다(DB의 묶음 5건은 모두 `카리나(시험)`). 새 주간 루틴(20260930_1504)은 OPEN이다.
- 같은 날 아침 개정된 자동화 PRD에 코드와 다른 사실(노출 태그·트라이브·제출 경로·카드 모양 규칙·외부 링크)이 있어 이 티켓을 만들며 바로잡았다.

## 진행 규칙

1. 하위 티켓은 `/jam-work`로 처리한다. 화면 티켓(3·4·5·6·7·8)은 큰 UI라 회차로 나누고 요약을 짧게 유지한다.
2. 확인은 메인 작업 트리의 로컬 `next dev`에서 실제 화면을 열어 한다. JAM 2.0 출시 전까지 main 배포가 멈춰 있어 프로덕션 어드민에는 출시 때 나간다(PRD §9).
3. 하위 티켓이 끝날 때마다 PRD 해당 절 머리에 「구현됨」을 붙인다. 모두 끝나면 PRD를 `active`로 올리고, 운영툴 PRD에서 바뀐 부분(§6 화면, §7.3 결정 행동)을 정리한다.
4. DB 변경은 CLAUDE.md 절대 규칙 6을 따른다.
