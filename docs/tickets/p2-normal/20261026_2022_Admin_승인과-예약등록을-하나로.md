# [API] 승인과 예약 등록을 한 요청으로 합친다 (서버 쪽)

> 상위: 20261026_2020

## 핵심 요약

- 요구사항: 검토중 항목을 승인하면 바로 예약 등록까지 한 요청에서 한다(D1). 화면 쪽은 티켓 20261026_2031(2026-10-26 분할)이 맡는다.
- 구현 계획: 예약 실행 경로(`POST .../execute`)가 `approve: true`를 받아, 검토중 항목을 먼저 승인하고 같은 요청에서 예약 실행을 이어 간다. 사전 점검(`dryRun`)도 검토중 항목을 포함하는 모드를 받는다. 아래 「구현 계획」의 파일 표를 따른다.
- 관련 파일: `jam-web/src/lib/admin/opsInbox/decide.ts`, `execute/run.ts`, `executeView.ts`, `jam-web/src/app/api/admin/ops-inbox/[bundleId]/decisions`·`execute`, `jam-web/src/components/admin/ops/OpsItemActions.tsx`·`OpsBulkApprove.tsx`·`OpsExecuteBundle.tsx`, 스펙 `docs/service/prd/ops-tool/PRD.md` §7.3·§8

## 상세 요구사항

- 시험 묶음은 지금처럼 검증만 하고 자원을 만들지 않는다.
- 패턴 제안 항목은 지금처럼 승인 즉시 「종료」다.
- 승인된 상태에서 멈춘 옛 항목(지금 데이터에 「승인됨」으로 남은 것)은 상태 맞추기나 [다시 시도]로 처리할 길을 남긴다.
- 확인창 문구는 세 줄(공개 시작, 공개 전 취소 가능, 실패 시 연결 항목 함께 되돌림)이다(PRD §6.3).
- 결정 기록과 슬랙 알림은 승인 1건 + 예약 결과 1건으로 남긴다.

## 구현 계획 (파일 단위, 2026-10-26 카리나 사전 확인)

배경 사실: 예약 실행(`executeBundle`, `execute/run.ts` 446줄)은 `status = 'approved'`인 항목을 조건부로 선점해 만든다(496·541줄). 사전 점검 `dryRunExecution`(178줄)·배지 소급 미리 세기 `badgePreviewExecution`(189줄)이 요약창의 확인 내용이다. 지금 승인은 `decide.ts`의 `approveItem`(341줄)·`bulkApprove`(384줄)가 하고 되돌리는 UI가 없다. 그래서 **요약창(사전 점검 + 배지 소급 수)을 확인 단계로 그대로 살리고**, 그 확인을 누르면 승인과 예약이 한 번에 일어나게 한다(D1). 「승인하고 예약」 확인 전에는 아무 상태도 바뀌지 않는다.

| 파일 | 할 일 |
|---|---|
| `jam-web/src/lib/admin/opsInbox/execute/run.ts` | `dryRunExecution`·`badgePreviewExecution`·`executeBundle`이 `includeReviewing` 모드를 받는다. 모드가 켜지면 대상은 `status IN ('reviewing','approved')` 항목이다. `executeBundle`은 선점 전에 대상 중 `reviewing`을 `approved`로 바꾸고(조건부 update, `bulkApprove`와 같은 규칙) 승인 결정 기록을 남긴 뒤 기존 선점·그룹 생성으로 이어 간다. 승인 단계에서 이미 다른 사람이 처리한 항목은 건너뛰고 사유를 돌려준다. 시험 묶음은 승인도 하지 않고 검증만 한다(지금 동작 유지). 패턴 제안은 지금처럼 승인 즉시 종료이며 예약 대상이 아니다 |
| `jam-web/src/lib/admin/opsInbox/decide.ts` | `bulkApprove`의 승인 전환·결정 기록 부분을 `run.ts`가 불러 쓸 수 있게 함수로 뗀다(동작 변경 없음). 슬랙 알림은 승인 1건 요약 + 예약 결과 1건으로 나가며 `notifyDecision`·`notifyExecution`을 그대로 쓴다 |
| `jam-web/src/app/api/admin/ops-inbox/[bundleId]/execute/route.ts` | 본문에 선택 필드 `approve: true`(`itemIds` 또는 `dryRun`/`badgePreview`와 함께)를 받고 `run.ts`에 `includeReviewing`으로 넘긴다. `approve` 없이 보내면 지금 동작과 같다(옛 화면 호환) |
| `jam-web/src/lib/admin/opsInbox/executeView.ts` | 요약 구역에 「승인할 항목」 표시를 위한 필드(검토중이던 항목인지)를 읽는다. 문구는 짧게(화면은 2031이 그린다) |
| `jam-web/src/lib/admin/opsInbox/__tests__/executeView.test.ts` | 새 필드 읽기 |
| `jam-web/src/lib/admin/opsInbox/execute/__tests__/`(run 계열 기존 테스트 파일에 사례 추가) | ① `approve` 모드에서 reviewing → approved → scheduled ② 연결 그룹 중 하나가 생성에 실패하면 둘 다 되돌려지고 둘 다 `failed` ③ 이미 처리된 항목 건너뜀 ④ 시험 묶음은 상태 불변 ⑤ `approve` 없이 호출하면 reviewing은 건드리지 않는다 |
| `jam-web/src/app/api/admin/ops-inbox/[bundleId]/execute/__tests__/`(기존 route 테스트에 사례 추가) | `approve: true` 본문 검증과 응답 |
| `docs/service/prd/ops-tool/PRD.md` §7.3·§8 | 「승인과 예약이 한 번에 일어난다」로 문장을 바꾼다 |

## 주요 의사결정

- 승인과 예약을 합치되 **확인 단계(사전 점검 요약 + JAM! 배지 소급 지급 수)는 없애지 않는다.** 이유: 승인은 되돌리는 UI가 없고, JAM! 배지는 공개 시 유저에게 소급 지급되어 영향이 크다. 합치는 것은 「승인」 버튼과 「예약 등록」 버튼이지 확인이 아니다. 요약창이 곧 확인이므로 확인창을 한 번 더 두지 않는다(지금 구조와 같다).
- 별도 「승인만」 경로(`decisions` 라우트의 `approve`·`bulk_approve`)는 남긴다. 패턴 제안 승인과 옛 호출 호환 때문이다. 화면에서 쓰지 않게 되는 것은 2031이 정리한다.
- 지금 DB에는 「승인됨」에 멈춘 항목이 없다(2026-10-26 조회: failed 6, rejected 1, cancelled 3, ended 1). 옛 항목 처리 장치는 만들지 않는다.

## 완료 조건

- 시험이 아닌 묶음에서 `POST .../execute`에 `{ itemIds, approve: true }`를 보내면 검토중 항목이 승인되어 「예약됨」이 되고 해당 자원이 공개 전 상태로 생긴다(단위 테스트 + 로컬에서 실제 호출해 DB 대조는 카리나).
- 연결된 카드·미션 중 하나의 생성을 일부러 실패시키면 둘 다 되돌려지고 둘 다 「실패」다(단위 테스트).
- `approve` 없이 보낸 요청은 이전과 똑같이 동작한다(기존 테스트 통과).
- `{ dryRun: true, approve: true }`가 검토중 항목까지 점검 결과에 넣고, 어떤 상태도 바꾸지 않는다(단위 테스트).
- `docs/service/prd/ops-tool/PRD.md` §7.3·§8의 해당 문장이 새 동작으로 바뀌어 있다.
