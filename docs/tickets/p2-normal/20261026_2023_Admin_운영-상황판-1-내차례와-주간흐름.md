# [Admin] 운영 상황판 1: 내 차례와 주간 흐름 지도

> 상위: 20261026_2020

## 핵심 요약

- 요구사항: 운영 홈 맨 위에 「내 차례」 카드 줄과 「주간 흐름」 지도(7단계 × 최근 5주)를 둔다(PRD §3.1·§6.1·§6.2·§6.5).
- 구현 계획: 항목 상태 10개를 화면 상태 5개로 묶는 순수 함수, 주차별 단계 위치 계산(에이전트 단계 기록 포함), 화면 조립 순으로 만든다. 지금 운영 홈 구역의 이동처를 정한다(PRD Q3).
- 관련 파일: `jam-web/src/app/admin/page.tsx`·`_home/sections.tsx`, `jam-web/src/lib/admin/opsHome/homeView.ts`, `jam-web/src/lib/admin/opsInbox/bundleStatus.ts`, `jam-web/src/components/admin/ops/OpsWeekStatus.tsx`·`OpsStageBar.tsx`

## 선행 조건

20261026_2021(필드 저장)과 20261026_2032(루틴 시작 기록)이 끝나 있다. 「루틴 멈춤」 판정과 에이전트 단계 칸이 그 값을 읽는다.

## 구현 계획 (2회차로 나눈다)

큰 화면 티켓이라 회차로 나눈다(1회차 = 화면 없는 계산과 읽기, 2회차 = 화면). 요약은 2,500자 이내로 쓴다.

### 1회차: 계산과 읽기 (화면 없음)

모두 새 파일이다. 서버·클라이언트가 같이 불러오므로 계산 파일은 서버 전용 모듈을 가져오지 않는다.

1. `jam-web/src/lib/admin/opsBoard/screenState.ts`: 화면 상태 다섯 가지(PRD §3.1)를 순수 함수로 둔다.
   - `SCREEN_STATES = ['decide', 'progress', 'live', 'problem', 'done']`와 화면 글자(결정 필요·진행 중·게재 중·문제·끝남).
   - `screenStateOfItemStatus(status)`: arrived·reviewing → decide / approved·preparing·scheduled → progress / live → live / failed → problem / ended·rejected·cancelled → done. 10개 밖 값은 null.
   - `screenDetailOfItemStatus(status)`: 칸 안에 작게 쓰는 세부(「승인됨」「준비중」「예약됨」「종료」「반려」「취소」). 나머지는 null.
   - `isMyTurnState(state)`: decide·problem만 참.
2. `jam-web/src/lib/admin/opsBoard/weekFlow.ts`: 주간 흐름 지도의 계산.
   - `FLOW_COLUMNS`(7개): 기획(윤진)·세계관 검수(윈터)·밸런스 점검(혜린)·내 결정·예약(시스템)·게재(시스템)·결과(카즈하). 키는 `plan`·`world_review`·`balance_check`·`decision`·`schedule`·`live`·`result`. 「내 결정」 열만 `emphasis: true`.
   - `computeWeekFlow({ bundles, starts, now, weeks: 5, includeSample })` → 최근 5주(이번 주부터 거꾸로, 월요일 기준 ISO 주차)의 행 배열. 행: `{ week, weekStart, weekEnd, title, columns: FlowColumnState[7], problemCount }`. 한 주에 묶음이 여럿이면 항목을 합쳐 한 행으로 센다. 제목은 가장 늦게 받은 묶음의 제목(없으면 null).
   - 열 상태 `FlowColumnState`: `{ key, phase: 'done'|'current'|'upcoming', count: number|null, screenState: ScreenState|null, note: string|null }`.
   - 규칙 1(묶음이 있는 주): 항목 상태를 `stageOfItemStatus`(`bundleStatus.ts`)로 센다. 결정 열 = 도착+검토중, 예약 열 = 승인됨+준비중+예약됨, 게재 열 = 게재중, 결과 열 = 종료. 가장 앞에 항목이 있는 열이 `current`, 그 앞 열은 `done`, 뒤 열은 `upcoming`이다. 항목이 있는 뒤쪽 열(예: 일부는 이미 게재중)도 개수와 함께 `current`로 그린다(정류장이 여러 개일 수 있다). 반려·취소는 어느 열에도 세지 않는다. 실패 항목은 예약 열에 `problem` 정류장(`screenState: 'problem'`, `problemCount`)을 더한다.
   - 규칙 2(기획·세계관 검수·밸런스 점검 열): 묶음 `routine_run.stages`(`readOpsRoutineStages`)에 그 단계 기록이 있으면 `done`이고 `note`는 결과(「2건 뺌」 = `excludedCount`, 없으면 「N건」 = `outCount`, 둘 다 없으면 null). 기록이 없으면 `note: '기록 없음'`이고 `phase`는 `done`이다(묶음이 이미 도착했으므로).
   - 규칙 3(묶음 없이 시작 기록만 있는 주): `starts`(루틴 시작 기록, `bundle_id`가 null)가 있으면 기획 열이 `current`, `screenState: 'progress'`, `note: '시작 후 N분'`이다. `isRoutineStalled`가 참이면 `screenState: 'problem'`, `note: '루틴이 멈췄어요'`이다. 둘 다 없는 주는 모든 열 `upcoming`이다.
   - 시험 묶음은 `includeSample`일 때만 센다. 항목 상태가 10개 밖이거나 패턴 제안인 항목은 세지 않는다.
3. `jam-web/src/lib/admin/opsBoard/myTurn.ts`: 내 차례 카드의 계산.
   - `computeMyTurn({ bundles, starts, now, includeSample })` → 카드 배열. 카드: `{ id, kind: 'decide'|'problem', reason: 'items'|'failed_items'|'routine_stalled', title, count, deadlineIso, reasonChips, href }`.
   - 「결정 필요」 카드: 묶음마다 도착·검토중 항목이 있으면 한 장. `count` = 그 항목 수(패턴 제안 포함: 패턴 제안도 결정할 항목이다). 마감 = 그 묶음 `week`의 수요일 18:00 KST. `reasonChips`는 항목의 기획 이유(`readOpsItemRationales`)를 종류별로 세어 최대 3개(`{ kind, count }`).
   - 「문제」 카드: (a) 실패 항목이 있는 묶음마다 한 장, `count` = 실패 항목 수. (b) `isRoutineStalled`가 참인 시작 기록마다 한 장, `title`은 「루틴이 멈췄어요」, `count` = 1.
   - 정렬: 문제 → 결정 필요, 같은 종류는 마감이 이른 순(문제는 최근 순). `href`는 묶음이면 `/admin/ops-inbox/{묶음 행 ID}`, 시작 기록 카드면 `/admin/ops-inbox`.
   - `myTurnCount(cards)`: 카드 수(상단 바 숫자와 같은 값).
4. `jam-web/src/lib/admin/opsBoard/load.ts`: 서버 읽기(`createServiceClient`).
   - `loadWeekFlowInputs({ includeSample, now })` → `{ bundles, starts }` 또는 읽기 실패. 최근 6주(이번 주 월요일 −35일부터) 안에 받은 묶음을 `ops_bundles`(`id, week, is_sample, received_at, title, raw, routine_run`)와 그 항목(`ops_bundle_items`: `id, bundle_id, status, kind, original, edited, starts_at, ends_at`)으로 읽고, `ops_routine_starts`(`id, run_key, week, author, agents, started_at, bundle_id`) 최근 6주분을 읽는다. 읽다 실패한 출처 이름을 `sourceErrors`에 담아 돌려준다(던지지 않는다). 이름은 호출부가 안내 카드를 고르는 데 쓴다.
   - 입력 타입은 `weekFlow.ts`·`myTurn.ts`가 함께 쓰는 `BoardBundleInput`(묶음 + 항목 + `title`·`routineRun`)과 `BoardRoutineStartInput`으로 `lib/admin/opsBoard/types.ts`에 둔다.
5. 시험(모두 `.ts`): `jam-web/src/lib/admin/opsBoard/__tests__/screenState.test.ts`(10개 상태 전부 PRD 표대로, 10개 밖 값 null), `weekFlow.test.ts`(규칙 1~3, 5주 범위·정렬, 시험 묶음 제외·포함, 한 주에 묶음 여럿, 일부 실패), `myTurn.test.ts`(카드 종류·마감 계산·정렬·루틴 멈춤·시험 묶음 제외), `load.test.ts`(출처 하나가 실패하면 `sourceErrors`에 이름이 담기고 던지지 않는다. 가짜 서비스 클라이언트).
6. 문서: `docs/service/prd/admin-boards/PRD.md` §3.1 표 아래와 §6.1·§6.2에 위 규칙(열 상태 판정, 한 주에 묶음 여럿일 때 합치기, 기록 없음, 정류장이 여러 개일 수 있음)을 쓰고 「구현됨(계산·읽기): 티켓 20261026_2023 1회차」를 표시한다.

### 2회차: 화면 (1회차 머지 뒤에 계획을 이어서 쓴다)

내 차례 카드 줄, 주간 흐름 지도, 에이전트 줄·일정 띠를 새 컴포넌트로 만들어 운영 홈 맨 위에 둔다. `OpsWeekStatus`의 각주·「다음 주」 줄을 없애고 운영 홈 구역 이동(PRD Q3)을 정한다. 파일 지도는 1회차가 끝난 뒤 읽은 코드로 적는다.

## 상세 요구사항

- 화면 상태 대응은 PRD §3.1 표 그대로다. 순수 함수로 두고 테스트한다.
- 내 차례에는 「결정 필요」와 「문제」(실패, 루틴 멈춤)만 뜬다. 상단 바 숫자와 같다.
- 주간 흐름: 열 7개, 「내 결정」 열 강조, 지나온 단계는 시각·결과를 작게, 지금 단계에 정류장. 결정 필요·문제 정류장은 움직임(동작 줄이기 설정에서는 멈춤).
- 단계 기록이 없는 옛 묶음은 에이전트 열 셋을 「기록 없음」으로 비워 그린다.
- 에이전트 줄과 이번 주 일정 띠를 오른쪽에 둔다.
- 글은 한 줄을 넘기지 않는다. 지금 `OpsWeekStatus`의 각주·「다음 주」 줄은 없앤다.

## 완료 조건

- 로컬 `next dev`에서 시험 묶음 3건(도착, 예약됨, 일부 실패)을 넣고 운영 홈을 열면, 세 주차가 각 단계에 맞는 정류장과 화면 상태로 보인다(스크린샷 첨부).
- 상태 대응 함수가 10개 상태를 모두 PRD 표대로 바꾼다(단위 테스트).
- 정류장을 누르면 결정 패널 또는 서랍으로 간다.
- 운영 홈에서 옮기기로 한 구역이 옮겨졌거나 이동 계획이 2027에 적혀 있다.
