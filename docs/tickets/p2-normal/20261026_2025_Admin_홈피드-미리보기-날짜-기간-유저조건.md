# [Admin] 날짜·기간·유저 조건별 홈피드 미리보기

> 상위: 20261026_2020

## 핵심 요약

- 요구사항: 날짜와 유저 조건(트라이브·시간대, 날씨·특일)을 골라 그날 홈피드를 휴대폰 틀 안에 그대로 보고, 그 주 7일의 카드 수와 모양을 칸으로 비교한다(D4, PRD §6.3).
- 구현 계획: 가상의 유저 조건으로 노출 태그를 계산하는 서버 함수를 만들고, 예약·게재 카드와 묶음의 결정 전 카드를 합쳐 홈 정렬 규칙으로 줄 세운다. 카드는 서비스 카드 컴포넌트로 그린다.
- 관련 파일: `jam-web/src/lib/today/exposure.ts`(`computeUserExposureTags`), `jam-web/src/lib/admin/today-sections.ts`, `jam-web/src/app/admin/today/TodayPreviewModal.tsx`, `jam-web/src/components/admin/ops/OpsCardPreview.tsx`, `jam-web/src/components/today/`, 스펙 `docs/service/prd/home-feed/PRD.md` §3·§4

## 구현 계획 (2회차로 나눈다)

큰 티켓이라 회차로 나눈다(1회차 = 화면 없는 계산·읽기·API, 2회차 = 화면). 요약은 2,500자 이내다. 지금 어드민에는 날짜만 고르는 미리보기가 있다(`jam-web/src/lib/admin/todayPreview.ts`의 `getAdminTodayPreviewCards`, `jam-web/src/app/admin/today/TodayPreviewModal.tsx`, API `jam-web/src/app/api/admin/today/preview/`). 그것은 노출 태그를 무시한 「켜진 카드 전부」 상한선이다. 이번 티켓은 가상 유저 조건을 더해 실제 노출 규칙과 같은 목록을 만든다. 실제 홈 조회(`getTodayCards`, `jam-web/src/lib/today/cards.ts`)는 건드리지 않는다.

### 1회차: 계산·읽기·API (화면 없음)

1. `jam-web/src/lib/today/cardSelection.ts` (새, 순수 함수, 서버 전용 모듈을 가져오지 않는다): 실제 홈 조회가 SQL로 하는 노출 판정을 같은 규칙의 함수로 둔다.
   - `cardIsLiveDuring(card, startIso, endIso)`: `is_active`가 참이고 `starts_at ≤ endIso`이며 `ends_at ≥ startIso`(경계 포함).
   - `cardMatchesTags(card.exposure_tags, tags)`: 하나라도 겹치면(OR) 참. `all`은 유저 태그에 늘 있으므로 `all`이 붙은 카드는 기간만 맞으면 보인다. 태그가 비었으면 거짓.
   - `sortHomeCards(cards)`: `sort_order` 오름차순, 같으면 `starts_at` 내림차순(안정 정렬).
   - 파일 머리 주석에 「`getTodayCards`의 SQL(`is_active`·`starts_at`·`ends_at`·`overlaps('exposure_tags')`·정렬)과 같은 규칙이다. 한쪽을 바꾸면 다른 쪽도 바꾼다」와 근거 경로를 적는다.
2. `jam-web/src/lib/today/virtualViewer.ts` (새, 순수 함수): 가상 유저.
   - `VirtualViewer { tribeId: string | null; timeOfDay: TimeOfDayTag; weather: WeatherKind | null; specialDays: SpecialDayTag[]; newUser: boolean }`.
   - `virtualExposureTags(viewer)`: `['all', timeOfDay, ...(weather ? ['weather_' + weather] : []), ...specialDays, ...(newUser ? ['new_user'] : [])]`. 유저 개인 상태 태그(`has_participating_mission` 등)는 가상 유저가 알 수 없어 넣지 않는다(주석으로 밝힌다).
   - `isClosedToViewerTribe(allowedTribeIds, viewer)`: `!isMissionOpenToTribe(allowedTribeIds, viewer.tribeId)`(`jam-web/src/lib/missions/tribe-access.ts`).
   - 시간대 태그는 `jam-web/src/lib/today/exposure.ts`의 `TimeOfDayTag`·`timeOfDayTag`를, 특일 태그는 `jam-web/src/lib/inputs/special-days-config.ts`의 `SpecialDayTag`·`specialDayTags`를, 날씨는 `jam-web/src/lib/inputs/weather.ts`의 `WeatherKind`를 그대로 쓴다.
3. `jam-web/src/lib/admin/homePreview/dayInputs.ts` (새, 서버): `readDayInputs(dateKst)` → `{ weather: WeatherKind | null; specialDays: SpecialDay[] | null; stored: boolean }`. `jam-web/src/lib/inputs/daily-store.ts`의 `readDailyInput('weather' | 'special_days', dateKst)`로 그날 저장된 값을 읽고(값 해석은 `weather.ts`의 `getTodayWeather`·`holidays.ts`의 `getTodaySpecialDays`와 같은 방식), 저장된 값이 없으면 null이다(미래 날짜는 화면이 고르게 한다). 읽기 실패는 던지지 않고 null과 `stored: false`로 돌려준다.
4. `jam-web/src/lib/admin/homePreview/load.ts` (새, 서버): `loadHomePreview({ fromDate, days, viewer, bundleId, now })` → `{ days: DayPreview[] }`.
   - 실제 카드: 기간 전체(`fromDate`~`fromDate + days − 1`)와 겹치는 `is_active` 카드를 한 번에 읽어(`createServiceClient`) 날마다 메모리에서 `cardIsLiveDuring`(그날 KST 하루 경계, `jam-web/src/lib/admin/today-calendar.ts`의 `kstDayBoundsIso`)·`cardMatchesTags`·`sortHomeCards`로 고른다. `mission_spotlight`·미션을 가리키는 랭킹 보드 카드는 `mission_allowed_tribes`(미션 id → 허용 트라이브)를 한 번에 읽어 `isClosedToViewerTribe`로 거른다(`jam-web/src/lib/today/cards.ts` `filterMissionSpotlightCards`·`filterRankingBoardCardsByTribe`와 같은 규칙. 유저별 참가·완료 판정은 가상 유저가 없어 하지 않는다고 주석에 밝힌다). 카드 표시 데이터는 `getAdminTodayPreviewCards`(`todayPreview.ts`)와 같은 자원 값 읽기(`fetchMissionsById` 등)를 재사용한다. 필요하면 그 읽기 부분을 `todayPreview.ts`에서 함께 쓰는 함수로 꺼낸다(동작을 바꾸지 않는다).
   - 승인 전 카드: `bundleId`가 있으면 그 묶음의 `home_feed_card` 항목 중 도착·검토중인 것을 읽어(`ops_bundle_items`: `id, status, original, edited, starts_at, ends_at`) 그날에 걸치고 `exposure_tags`(수정본 우선)가 가상 유저 태그와 겹치는 항목을 `itemToPreviewCard`(`jam-web/src/lib/admin/opsInbox/cardPreview.ts`)로 카드 값으로 바꾼다. 정렬은 실제 카드 뒤에 `resource.sort_order` 오름차순이다.
   - `DayPreview { date, entries: PreviewEntry[], shapeCounts: Record<string, number>, pendingCount: number, inputs: { weather, specialDays, stored } }`, `PreviewEntry { source: 'live' | 'pending', id, card: TodayCardWithHref, rationale: { kind, label }[] }`(`rationale`은 승인 전 카드만, `readOpsItemRationales`). 날마다 `entries.length`가 그날 카드 수이고 `shapeCounts`는 `entries`에서 센다.
   - 읽기 실패는 던진다(호출부가 오류 응답으로 바꾼다. 실패를 빈 목록으로 보이지 않는다).
5. `jam-web/src/app/api/admin/home-preview/route.ts` (새): `GET`, 관리자만(`jam-web/src/lib/admin/auth.ts` 패턴, 기존 `app/api/admin/today/preview/route.ts`를 본다). 쿼리: `date`(`normalizeDateParam`), `days`(1~7, 기본 7), `tribe`(UUID 또는 비움), `time`(`TimeOfDayTag` 다섯 값, 기본은 `time_morning`), `weather`(`clear|mild|rain|extreme` 또는 비움, 비우면 그날 저장된 값), `special`(쉼표 목록, 허용값만, 비우면 그날 저장된 값), `newUser`(`1`), `bundle`(UUID 또는 비움). 형식이 틀리면 400. 응답은 `{ days }`와 날마다 `inputs`(저장된 값과 쓴 값). 쓰기는 하지 않고 캐시하지 않는다.
6. 시험(모두 `.ts`): `jam-web/src/lib/today/__tests__/cardSelection.test.ts`(기간 경계 포함, OR 겹침, `all`, 빈 태그, 정렬 안정성), `virtualViewer.test.ts`(태그 조합, 트라이브 제한), `jam-web/src/lib/admin/homePreview/__tests__/load.test.ts`(가짜 서비스 클라이언트: 같은 날짜에서 트라이브를 바꾸면 트라이브 전용 미션 소개 카드가 나타나고 사라진다, 승인 전 카드가 실제 카드 뒤에 `pending`으로 붙는다, 날마다 카드 수 = `entries.length`, 읽기 실패는 던진다), `dayInputs.test.ts`, `jam-web/src/app/api/admin/home-preview/__tests__/route.test.ts`(관리자 아님 403, 쿼리 검증 400, 정상 응답).
7. 문서: `docs/service/prd/home-feed/PRD.md` §3에 「어드민 미리보기는 같은 규칙(`lib/today/cardSelection.ts`)을 쓴다」 한 줄(생성 구간은 손으로 고치지 않는다. `code:` 경로를 건드리는 커밋은 그 문서도 함께 바꾸라는 훅이 있으니 요구되면 맞춘다), `docs/service/prd/admin-boards/PRD.md` §6.3 홈피드 미리보기에 「구현됨(계산·읽기·API): 티켓 20261026_2025 1회차」와 가상 유저 조건·승인 전 카드 규칙.

**1회차에서 하지 않는 것**: 화면, 실제 홈 조회(`getTodayCards`)의 변경, 유저별 참가·완료 판정.

### 2회차: 화면 (1회차는 머지됐다. 계산·읽기·API는 `lib/admin/homePreview/`·`lib/today/`·`GET /api/admin/home-preview`에 있다)

어드민 shadcn 부품(`components/admin/ui/`)과 Tailwind 토큰만 쓴다. 요약은 2,500자 이내다. 합치기 결정(근거는 완료 기록에 남긴다): **새 미리보기 부품 하나**(`HomePreviewPanel`)를 만들고 투데이 화면의 `TodayPreviewModal`(날짜만 고르는 상한선 시뮬레이션)이 그 부품을 담는 창이 되게 한다. 두 곳(결정 패널·투데이)이 같은 부품과 같은 API를 쓰면 판정이 한 벌이다. 운영툴 왼쪽 칸의 항목 한 장 미리보기(`OpsCardPreview`)는 그대로 둔다.

**먼저 고칠 것 (1회차 보강, `jam-web/src/lib/admin/homePreview/load.ts`)**
1. 수동 비노출 미션 소개 카드 거르기: 실제 홈 조회(`jam-web/src/lib/today/cards.ts`의 `filterMissionSpotlightCards`)는 `mission_spotlight` 카드가 가리키는 미션 중 관리자가 수동으로 비노출한 것(`isMissionExposed`, `jam-web/src/lib/missions/visibility.ts`)을 뺀다. 같은 규칙으로 맞춘다: 미션 행을 읽은 결과가 하나도 없으면 카드를 그대로 두고, 하나라도 있으면 읽은 미션 중 `isMissionExposed(미션, 그날 기준 시각)`가 참인 미션을 가리키는 카드만 남긴다(미션 행을 못 찾은 카드는 뺀다). 유저별 판정(`resolveMissionVisibility`: 완료·잠금·숨김)은 가상 유저가 없어 하지 않는다고 주석에 밝힌다. `jam-web/src/lib/admin/homePreview/__tests__/load.test.ts`에 수동 비노출 미션 카드가 빠지는 시험을 더한다.
2. 트라이브 목록: `GET /api/admin/home-preview` 응답에 `tribes: { id, name }[]`(`tribes` 테이블 읽기, 이름순)를 더한다. `route.ts`와 `route.test.ts`를 맞춘다. 읽기 실패는 빈 배열이 아니라 500이다.

**화면** (새 파일은 `jam-web/src/components/admin/ops/preview/` 아래, 클라이언트 컴포넌트)
3. `HomePreviewPanel.tsx`: 속성 `{ initialDate, bundleId?, days?: 7 }`. 상태: 선택한 날짜, 가상 유저 조건(트라이브, 시간대, 날씨, 특일, 신규), 「기획 이유 보기」. 조건·날짜가 바뀌면 `GET /api/admin/home-preview`를 한 번 부른다(이전 요청은 `AbortController`로 취소, 실패는 한 줄 오류와 「다시 불러오기」). 위에서 아래 순서: 조건 줄 → 7일 칸 → 선택한 날 휴대폰 틀.
4. 조건 줄: 트라이브(shadcn `Select`, 「전체(트라이브 없음)」 포함, 목록은 응답 `tribes`), 시간대(다섯 값: 새벽·아침·낮·저녁·밤, 기본 아침), 날씨(맑음·흐림·비·극단, 「저장된 값」 포함), 특일(공휴일·절기·기념일 세 개 토글, 「저장된 값」 포함), 신규 유저 체크. 날씨·특일은 선택한 날에 저장된 값이 있으면 「저장된 값 사용」이 기본이고, 없는 날(미래)은 「저장된 값이 없어요」 한 줄과 함께 고르게 한다(응답 `days[].inputs`로 판단).
5. `HomePreviewWeekStrip.tsx`: 7칸(요일·날짜, 카드 수 숫자, 모양별 막대(`shapeCounts`, 모양마다 구분되는 회색 농도와 범례 없이 `title` 툴팁), 승인 전 카드가 있으면 점선 점과 「승인 전 N」). 칸은 버튼이고 누르면 그 날이 선택된다. 선택한 칸은 테두리로 강조한다. 칸의 카드 수는 `entries.length`이고 휴대폰 틀에 그려지는 카드 수와 같다.
6. 휴대폰 틀: `jam-web/src/app/admin/today/TodayCardPreview.tsx`를 확장한다. 새 선택 속성 `annotations?: readonly ({ pending: boolean; chips?: ReactNode } | null)[]`(카드 순서와 같은 길이)를 받아, 승인 전 카드는 점선 테두리와 「승인 전」 표시를 두르고, `chips`가 있으면 카드 위에 이유 칩 줄을 올린다. 기존 호출부(날짜 모달, 카드 폼, 운영툴)는 속성을 안 주면 지금과 같다. 카드는 서비스 카드 컴포넌트(`TodayCard`)를 그대로 쓴다(`toCardView`, 계측 정보 없음). 이유 칩은 `OpsRationaleChips`(`components/admin/ops/board/OpsRationaleChip.tsx`)를 쓰고 「기획 이유 보기」가 켜졌을 때만 나온다. 카드가 0장이면 「이 날 보이는 카드가 없어요」.
7. 진입 두 곳: (a) 기획 상세 결정 패널(`OpsDecisionPanel.tsx`) 바닥에 줄 하나를 더한다: 「승인 대상 N건」 옆에 「공개 시작 12/30(목) 09:00」(체크한 항목 중 가장 이른 `startsAt`, 없으면 줄을 쓰지 않는다)과 버튼 「홈피드로 보기」. 누르면 shadcn `Sheet`(`components/admin/ui/sheet.tsx`, 오른쪽)가 열려 `HomePreviewPanel`(`bundleId` = 이 묶음, `initialDate` = 체크한 항목 중 가장 이른 공개일, 없으면 묶음 주 월요일)을 담는다. (b) 투데이 화면 `jam-web/src/app/admin/today/TodayPreviewModal.tsx`의 본문을 `HomePreviewPanel`(`initialDate = selectedDate`, `bundleId` 없음)로 바꾼다. 쓰이지 않게 된 옛 경로(`GET /api/admin/today/preview`, `getAdminTodayPreviewCards`와 그 시험)는 사용처를 grep으로 확인하고 없으면 함께 지운다(`resolvePreviewCards`는 새 읽기가 쓰므로 남긴다).

## 상세 요구사항

- 노출 판정은 서비스와 같은 규칙을 쓴다. 미리보기 전용 판정을 따로 만들지 않는다.
- 결정 전 카드는 점선과 「승인 전」 표시. 「기획 이유 보기」를 켜면 이유 칩을 카드 위에 올린다.
- 운영 상황판의 결정 패널·내 차례와 투데이 화면(`/admin/today`) 양쪽에서 열 수 있다. 지금의 `TodayPreviewModal`과 합칠지 정하고 근거를 완료 기록에 남긴다.
- 날씨·특일이 아직 저장되지 않은 미래 날짜는 고를 수 있게 한다.

## 완료 조건

- 같은 날짜에서 트라이브를 바꾸면 그 트라이브 전용 카드가 나타나고 사라진다(로컬 실화면, 시험 카드로 확인).
- 미리보기에 보인 카드 목록이 같은 조건의 실제 유저 노출 판정 결과와 같다(단위 테스트로 판정 함수 대조).

### 주요 의사결정 / 핵심 메모
- 큰 티켓이라 두 회차로 나눴다(계산·읽기·API → 화면).
- 실제 홈 조회(`getTodayCards`)는 SQL로 판정한다. 같은 규칙을 순수 함수로 따로 두고(`cardSelection.ts`) 머리 주석과 시험으로 한쪽을 바꾸면 다른 쪽도 바꾸게 했다. 실제 홈 쪽 코드는 건드리지 않았다. 판정 대조는 같은 규칙의 경계(경기 포함, OR, `all`, 빈 태그, 정렬 안정성)를 시험으로 고정하는 방식이다.
- 가상 유저는 개인 상태(참여 중 미션·컬렉션 진행도 등)를 알 수 없어 그 태그와 유저별 참가·완료 판정은 넣지 않았다. 코드 주석에 한계를 밝혔다.
- 수동 비노출 미션 소개 카드 거르기는 1회차 게이트의 참고 지적을 2회차에 포함해 처리했다.
- 워크플로에 넘긴 티켓 경로가 실제 파일명과 달라 아현이 직접 찾아 진행했다(결과 영향 없음, 2회차부터 정확한 경로를 넘김).
- API가 `special=none`을 받는다(티켓에 없던 값). 「특일 모두 끔」과 「저장된 값」을 구분하려는 것이다.
