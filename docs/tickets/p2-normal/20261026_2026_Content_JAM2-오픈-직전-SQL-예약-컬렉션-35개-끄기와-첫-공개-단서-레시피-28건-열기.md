# [Content] JAM2 오픈 직전 SQL: 예약 컬렉션 35개 끄기(292)와 첫 공개 단서 레시피 28건 열기(293) (묶음 7, 7-9)

## 핵심 요약

- 요구사항: 문서 12 4절 5번(컬렉션 35개 끄기)과 6번(단서 레시피 28건 공개)을 SQL 파일 두 개로 만든다. **파일만 만들고 실행하지 않는다.** 실행은 오픈 직전에 카리나가 롤백 실측과 함께 한다.
- 구현 계획: 새 생성기 `jam-web/scripts/jam2-content/gen-launch-sql.mjs`가 7-6 계획(원고 01~05의 컬렉션 50개)과 단서 원고(20건)에서 마이그레이션 `292`, `293`을 만든다. 시험이 생성 결과와 저장소의 파일이 같은지 비교한다. 패턴은 `gen-recipe-sql.mjs`의 `genRetireSql`(282)과 같다.
- 관련 파일: `jam-web/scripts/jam2-content/gen-launch-sql.mjs`(새 파일), `jam-web/scripts/jam2-content/__tests__/gen-launch-sql.test.mjs`(새 파일), `jam-web/supabase/migrations/292_close_reserve_collections_at_launch.sql`·`293_open_initial_clue_recipes_at_launch.sql`(생성 결과), `jam-web/scripts/jam2-content/gen-recipe-sql.mjs`(65번째 줄 `commentBlock`에 `export`만 붙인다).

## 배경 / 문제 정의

오픈 때 컬렉션은 트라이브마다 10개 가운데 3개만 열고 7개는 꺼 둔 채 시작한다(5개 트라이브, 15개 열림, 35개 꺼 둠). 꺼 둔 컬렉션은 운영자가 어드민에서 하나씩 켠다(2026-10-26 사용자 결정, 문서 12 4절 5번). 단서 레시피는 80건(20개 × 등급 4개)이 모두 공개 시작 자리 값(`2099-01-01 00:00 KST`)으로 들어가 있고, 이 가운데 재료와 보상 컬렉션이 모두 첫 공개 15개 안에 있는 7개(28건)만 오픈 때 열고 나머지 13개(52건)는 자리 값으로 남긴다(문서 12 4절 6번, 9.1절).

두 일은 지금 SQL 파일이 없어서 오픈 직전 점검표(문서 12 4.1절)에 넣을 수 없다. 이 티켓이 그 파일 두 개를 만든다.

#### 292: 예약 컬렉션 35개 끄기

- 계획 컬렉션 50개를 «트라이브 이름, 컬렉션 이름»으로 찾고, 한 건씩 맞지 않으면 멈춘다(임시 표 `_jam2_launch_book`: `tribe`, `book`, `is_initial`, `book_id`, `matches`).
- 첫 공개 15개가 모두 `is_active = true`가 아니면 멈춘다. 오픈 직전에 운영자가 따로 꺼 둔 것이 있다는 뜻이므로 사람이 보고 판단한다.
- 끄기 대상은 «계획 컬렉션 가운데 첫 공개가 아니고 지금 켜져 있는 것»이다. **35개가 아니면 멈춘다.** 적용된 뒤에는 0개가 되므로 같은 파일을 다시 실행해도 멈춘다.
- 끄기 직전의 행 전체를 백업 표에 `item_book` 종류로 담는다(`to_jsonb(ib)`, 이미 있으면 갱신).
- 끄기는 `is_active = false` 하나만 바꾼다. `valid_from`을 비롯한 다른 열은 건드리지 않는다(2026-10-26 결정: 켜는 일은 운영자가 `is_active`로 한다).
- 끝 검사: 끈 컬렉션 35개가 꺼져 있다 / 계획 컬렉션 가운데 켜진 것이 정확히 첫 공개 15개다 / 끈 35개의 `is_active`를 뺀 나머지 열이 백업과 같다(`to_jsonb(ib) - 'is_active' = snapshot - 'is_active'`) / 백업이 35건이다.
- 282(옛 컬렉션 19개 끄기)와 순서가 상관없다. 282는 «계획 밖의 활성 컬렉션»만 보고, 292는 «계획 안의 컬렉션»만 본다. 두 파일의 끝 검사가 서로를 깨지 않는지 시험으로 확인한다.

#### 293: 첫 공개 단서 레시피 28건 열기

- 위 7개 이름을 `combination_recipes.name`으로 찾는다. 이름마다 **정확히 4행**이어야 하고, 4행 모두 `valid_from`이 자리 값(`TIMESTAMPTZ '2099-01-01 00:00:00+09'`, 생성기의 `CLUE_VALID_FROM`)이며 `valid_until`이 비어 있어야 한다. 하나라도 어긋나면 멈춘다(이미 열었거나 281이 적용되지 않았다는 뜻이다).
- 7개 이름의 재료 컬렉션과 보상 컬렉션을 DB에서 다시 구해(칸의 `allowed_badge_ids` → `badges.item_book_id` → `item_books` → `tribes`, 보상은 `reward_badge_ids`로 같은 경로) 이름마다 위 표의 컬렉션과 **정확히 같은지** 대조한다. 어긋나면 멈춘다. 그리고 그 컬렉션이 모두 첫 공개 15개에 들고 `is_active`인지 확인한다. 이 검사는 292보다 먼저 실행해도 292 뒤에 실행해도 통과한다(첫 공개 15개는 어느 쪽이든 켜져 있다).
- 열기 전에, 7개 이름을 뺀 나머지 중 `valid_from`이 자리 값인 행이 정확히 52행인지 확인한다(80행 − 28행). 52행이 아니면 다른 세션이 레시피를 건드렸다는 뜻이므로 멈춘다.
- 열기 직전의 행 전체를 백업 표에 `combination_recipe` 종류로 담는다(28건).
- 여는 일은 28행의 `valid_from = NULL` 하나만 바꾼다. `valid_until`, 칸(`combination_recipe_slots`), 보상 열은 건드리지 않는다.
- 끝 검사: 28행의 `valid_from`이 NULL이다 / 자리 값으로 남은 행이 52행이다 / 28행의 `valid_from`을 뺀 나머지 열이 백업과 같다 / 백업이 28건이다.

#### 백업 표와 되돌림

- 백업 표 이름은 `launch_backup_20261026`(생성기 상수 `LAUNCH_BACKUP_TABLE`). 292와 293이 같은 정의를 `CREATE TABLE IF NOT EXISTS`로 만든다(`kind` 제약은 `item_book`, `combination_recipe`). 정의가 두 파일에서 한 글자도 다르지 않게 생성기가 한 곳에서 만든다. 282의 `retire_backup_20261022`와는 별개 표다.
- RLS를 켜고 `anon`, `authenticated` 권한을 회수한다(282와 같다).
- 각 파일 끝에 되돌림 SQL을 모두 주석(`-- `)으로 붙인다(282와 같은 방식, deploy-gate 표식 `되돌림`으로 시작). 292는 `is_active`를, 293은 `valid_from`을 백업 표의 값으로 되돌린다. 백업 표 지우기는 «두 파일을 모두 되돌린 뒤에만»이라고 적는다.
- BEGIN/COMMIT은 쓰지 않는다. 한 번의 호출로 통째로 실행하고, 롤백 실측은 파일 뒤에 일부러 오류를 내는 문장을 붙여 같은 호출로 한다(282와 같다).

### 컨텐츠 관점 (해당 시)

- 컬렉션과 레시피의 이름·설명·재료·보상은 바꾸지 않는다. 공개 여부(`is_active`, `valid_from`)만 바꾼다.
- 단서 레시피 13개(52행)와 꺼 둔 컬렉션 35개는 오픈 뒤에 운영자가 어드민에서 켠다. 특히 레시피 13개는 재료·보상 컬렉션이 켜져야 의미가 있고(문서 12 9.1절 «켜야 열리는 컬렉션»), 그 레시피를 여는 SQL은 이 티켓의 범위가 아니다.

**생성 타입**: 이 두 파일은 백업 표만 새로 만들고(앱 코드가 읽지 않는다) 아직 적용하지 않으므로 `database.generated.ts`는 건드리지 않는다. 오픈 직전에 적용한 뒤에도 앱 코드가 쓰지 않는 표다.

**실행하지 않는다.** 아현은 DB에 접근하지 않고 SQL 파일과 생성기, 시험만 만든다. 실행은 오픈 직전에 카리나가 한다(드라이런, 롤백 실측, 읽기 전용 확인).
