# [Admin] 생태계 상황판: 목표 대비·순환 지도·정책 패널

> 상위: 20261026_2020

## 핵심 요약

- 요구사항: 성장 순환과 필드 순환을 마디로 그리고, 마디마다 지표·상태를 보이며, 누르면 해당 정책 목록과 [값 바꾸기]·[개발 요청]을 보인다. 밸런스 목표 대비 주의 이상을 위에 띄운다(PRD §7).
- 구현 계획: 정책 대시보드(`policiesData.ts`)의 항목에 순환 마디 연결을 더하고, 마디별 지표 계산 함수를 만든다. 값 변경은 지금 설정 화면으로 보낸다. [개발 요청]은 2028의 요청 저장을 쓴다.
- 관련 파일: `jam-web/src/app/admin/policy-dashboard/page.tsx`, `jam-web/src/lib/admin/policyDashboard/policiesData.ts`·`types.ts`, `jam-web/src/components/admin/policyDashboard/`, `jam-web/src/app/admin/balance/`, `jam-web/src/app/admin/ops-settings/`

## 구현 계획 (3회차로 나눈다)

큰 티켓이라 회차로 나눈다. 순서: 1회차 = 개발 요청 저장(DB·API), 2회차 = 순환 마디·지표 계산(화면 없음), 3회차 = 화면(생태계 상황판 페이지·운영 홈 구역 이동). 요약은 2,500자 이내다. 어드민 shadcn 부품만 쓴다.

**조사로 알게 된 것 (2026-10-27)**
- 「밸런스 목표」 정책 5개(`policiesData.ts` 1288줄 부근, `ch19-kpi-*`)의 지표 계산·목표·상태는 이미 밸런스 서브 대시보드(`jam-web/src/lib/admin/balanceDashboard/`의 `compute.ts`·`load.ts`·`targets.ts`)에 있다. 목표 대비 칸은 새로 계산하지 않고 그 읽기를 재사용한다.
- 정책 대시보드 항목(`PolicyItem`)에는 마디 연결 칸이 없다. 2회차가 더한다.
- [개발 요청]의 저장소(DB)는 티켓 2028도 쓴다(PRD §8). 생태계 상황판이 먼저 시작되므로 **저장소와 API를 이 티켓 1회차에서 만들고** 2028은 그것을 읽어 보드에 보이는 일만 한다(2028 티켓에 한 줄 적는다).

### 1회차: 개발 요청 저장 (DB·API, 화면 없음)

1. `jam-web/supabase/migrations/297_ops_dev_requests.sql` (새, 아현은 **작성만** 하고 실행은 카리나가 한다. 머리 주석은 `296_ops_trend_sources.sql`과 같은 형식): `public.ops_dev_requests` 신규.
   - 칸: `id UUID PK DEFAULT gen_random_uuid()`, `no INTEGER GENERATED ALWAYS AS IDENTITY UNIQUE`(요청 번호), `title TEXT NOT NULL CHECK (char_length(btrim(title)) BETWEEN 1 AND 80)`, `detail TEXT NOT NULL DEFAULT '' CHECK (char_length(detail) <= 2000)`, `origin TEXT NOT NULL CHECK (origin IN ('ops','eco','other'))`(어디서 만든 요청인지: 운영 상황판·생태계 상황판·그 밖), `policy_id TEXT NULL CHECK (char_length(policy_id) <= 100)`(생태계 정책 패널에서 만든 요청이면 `policiesData.ts`의 항목 `id`), `status TEXT NOT NULL DEFAULT 'requested' CHECK (status IN ('requested','ticketed','dismissed'))`, `ticket_id TEXT NULL CHECK (char_length(ticket_id) <= 40)`(티켓으로 바꾼 뒤 그 티켓 ID), `created_by UUID NULL`, `created_at`·`updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`.
   - 색인: `(status, created_at DESC)`. RLS를 켜고 정책은 만들지 않는다(service_role만). `COMMENT ON TABLE`·`COMMENT ON COLUMN`, 검증 쿼리 주석, 되돌림 SQL(`DROP TABLE IF EXISTS public.ops_dev_requests;`)을 단다.
2. `jam-web/src/types/database.generated.ts`: 위 테이블의 `Row`·`Insert`·`Update`·`Relationships`(없음)를 SQL과 같게 손으로 더한다(`no`는 `GENERATED ALWAYS`라 Insert/Update에서 `no?: never`, `ops_trend_sources`와 같은 방식). 카리나가 적용 뒤 MCP 생성 타입과 대조한다.
3. `jam-web/src/lib/admin/devRequests/constants.ts` (새): `DEV_REQUEST_ORIGINS = ['ops','eco','other']`와 화면 글자(운영에서·생태계에서·그 밖), `DEV_REQUEST_STATUSES`, 상한(제목 80·내용 2000·정책 ID 100·본문 바이트 16384), 한 번에 읽는 최대 개수 200.
2번 뒤 4~8번은 이 순서로 한다.
4. `jam-web/src/lib/admin/devRequests/requests.ts` (새, 순수): `validateDevRequestCreate(raw)`(`title`·`detail?`·`origin`·`policyId?`, 앞뒤 공백 제거, 길이·허용값 검사), `validateDevRequestPatch(raw)`(`status`는 `'requested'|'dismissed'`만 받는다(`ticketed`는 카리나가 SQL로 정한다), `ticketId`는 `status`가 `ticketed`일 때만 의미가 있어 PATCH에서는 받지 않는다. 하나 이상 있어야 한다). `{ ok: true, value } | { ok: false, errors: string[] }`.
5. `jam-web/src/lib/admin/devRequests/store.ts` (새, 서버): `listDevRequests(service, { status })`(`no` 내림차순, 최대 200건), `createDevRequest(service, input, adminId)`, `updateDevRequest(service, id, patch)`(없는 행은 `{ ok: false, code: 'not_found' }`, 읽기·쓰기 실패는 던진다). 같은 정책(`policy_id`)에 이미 `requested` 상태 요청이 있으면 만들지 않고 `{ ok: false, code: 'duplicate_open', existingNo }`를 돌려준다(같은 정책에 요청이 쌓이지 않게. `policy_id`가 없는 요청은 중복 검사를 하지 않는다).
6. `jam-web/src/app/api/admin/dev-requests/route.ts` (새): `GET` — 관리자 세션 또는 읽기 토큰(`requireAdminRead`, 토큰 판별은 `jam-web/src/lib/admin/auth.ts`의 `isAdminReadTokenRequest`), 쿼리 `status`(`requested`(기본)·`ticketed`·`dismissed`·`all`), 응답 `{ requests: [{ no, title, detail, origin, policyId, status, ticketId, createdAt }] }`(`created_by` 없음). `POST` — **관리자 세션만**(`getAdminUser()`가 없으면 403, 토큰은 보지 않는다), 본문 16KB 상한, 검증 실패 400, 같은 정책의 열린 요청이 있으면 409(`existingNo`를 담은 문장), 성공 201 `{ request }`.
   `jam-web/src/app/api/admin/dev-requests/[id]/route.ts` (새): `PATCH` — 관리자 세션만, `id`가 UUID가 아니면 404, 검증 실패 400, 없는 행 404, 성공 200 `{ request }`. 응답에 내부 오류 문구를 싣지 않고 캐시하지 않는다.
7. 시험(모두 `.ts`): `requests.test.ts`(검증), `store.test.ts`(가짜 서비스 클라이언트: 목록·상태 필터, 같은 정책 열린 요청 중복, `policy_id` 없는 요청은 중복 검사 안 함, 없는 행, 읽기 실패는 던짐), `app/api/admin/dev-requests/__tests__/route.test.ts`(토큰 GET은 통과하고 `created_by`가 없음, 토큰으로 POST·PATCH 거부, 세션 CRUD, 400·404·409·500).
8. 문서: `docs/service/prd/admin-boards/PRD.md` §8 개발 요청 항목에 「구현됨(저장·API): 티켓 20261026_2027 1회차」(테이블·API·중복 규칙·`ticketed`는 카리나가 정함)를 쓰고, `docs/agents/orchestrator.md`의 세션 시작 절차(현황판 뒤 읽기 단계가 있는 절)에 「개발 요청 읽기」 단계를 더한다: 카리나가 세션을 시작할 때 `select no, title, origin, policy_id, created_at from ops_dev_requests where status = 'requested' order by no`를 읽고(Supabase MCP `execute_sql`, 읽기 전용), 있으면 사용자에게 건수와 제목을 알려 티켓으로 바꿀지 묻고, 바꾸면 티켓 frontmatter `origin`을 채우고 요청 행을 `status='ticketed'`, `ticket_id`로 갱신한다. 이 문서의 해당 절은 `scripts/ticket-dashboard.mjs`가 세션 시작 hook에서 잘라 쓰는 절이므로(15줄 주석) 그 절 안에 쓸지 별도 절로 둘지는 그 주석을 읽고 정한다. 새로 적는 환경 주장(테이블 이름·API 경로)은 `docs/agents/contract.json`에 검사 줄을 함께 더하고 `node scripts/check-contract.mjs`로 확인한다. `docs/tickets/p2-normal/20261026_2028_Admin_개발-배포-상황판과-개발요청.md`의 「구현 계획」에 「개발 요청 저장은 2027 1회차가 만들었다(테이블 `ops_dev_requests`, `GET/POST /api/admin/dev-requests`). 이 티켓은 읽어서 보드 「대기」에 「요청」으로 보이기만 한다」 한 줄을 더한다.

**1회차에서 하지 않는 것**: 화면, 마디·지표 계산, 티켓 파일 자동 생성(카리나가 세션에서 만든다).

### 2회차: 순환 마디·지표 계산 (화면 없음, 1회차 적용·머지 뒤에 계획을 이어서 쓴다)

### 3회차: 생태계 상황판 화면과 운영 홈 구역 이동 (2회차 뒤에 계획을 이어서 쓴다)

## 상세 요구사항

- 마디: 활동 동기화, 잼, 캡슐, 아이템 배지, 인벤토리, 컬렉션, 시스템 드랍, 유저 드랍, 지점, 픽업.
- 지표의 계산식과 기간을 이 티켓에서 정하고 PRD §7에 적는다. 정책 값은 대시보드처럼 실시간 설정값을 읽는다.
- 운영 홈에서 옮겨 오기로 한 구역(2023)을 받는다.
- 운영 홈에서 옮겨 올 구역: 주간 핵심 지표(`KpiSection`)·배지 경제 흐름(`TrendSection`)·통계(`StatsSection`). 2023 2회차는 옮기지 않고 운영 홈 아래쪽에 두었으므로, 이동(생태계 쪽에 붙이고 운영 홈 페이지에서 빼기)은 이 티켓에서 한다. 서비스 점검·신호·최근 이력은 운영에 남는다(PRD Q3).
- `policiesData.ts`를 고치므로 CLAUDE.md 절대 규칙 2의 정책 대시보드 동기화를 지킨다.

## 완료 조건

- 로컬에서 생태계 상황판을 열면 마디 10개가 지표와 함께 보이고, 인벤토리 마디를 누르면 인벤토리 정책 목록이 보인다.
- 설정값 정책의 [값 바꾸기]는 해당 설정 화면으로, 코드 고정 정책의 [개발 요청]은 개발 요청을 1건 만든다.
- 목표 대비 칸의 값이 같은 기간 DB 직접 집계와 같다(카리나가 SQL로 대조).
