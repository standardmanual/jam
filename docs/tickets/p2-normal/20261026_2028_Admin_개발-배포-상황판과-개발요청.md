# [Admin] 개발·배포 상황판(GitHub 읽기)과 개발 요청

> 상위: 20261026_2020

## 핵심 요약

- 요구사항: 배포 현황, JAM 2.0 묶음 진행, 개발 항목 보드(대기·진행·staging 반영·배포됨, 출처 표시)를 GitHub에서 실시간으로 읽어 보인다(D3, PRD §8). 다른 상황판의 [개발 요청]을 받는다.
- 구현 계획: 티켓 색인 파일을 저장소에 두는 방식을 정하고(커밋 훅 또는 생성 스크립트), 서버에서 GitHub API로 색인·브랜치 비교·배포 기록을 읽는다. 개발 요청은 DB에 쌓고 카리나가 세션 시작 때 티켓으로 바꾼다.
- 개발 요청 저장은 2027 1회차가 만들었다(테이블 `ops_dev_requests`, `GET/POST /api/admin/dev-requests`). 이 티켓은 읽어서 보드 「대기」에 「요청」으로 보이기만 한다.
- 관련 파일: `scripts/ticket-dashboard.mjs`(현황 집계 로직), `.githooks/pre-commit`, `docs/DOCUMENT_SCHEMA.md`(`origin` 선택 필드), `docs/agents/orchestrator.md`(세션 시작 절차), `jam-web/src/app/admin/`(새 화면)

## 구현 계획 (3회차로 나눈다)

큰 티켓이라 회차로 나눈다. 순서: 1회차 = 티켓 색인 파일과 생성기(코드 읽기 없음), 2회차 = GitHub 읽기와 보드·묶음 계산(화면 없음), 3회차 = 화면. 요약은 2,500자 이내, 어드민 UI는 shadcn 부품만 쓴다.

**조사로 알게 된 것 (2026-10-27)**

- 티켓은 지금 2,016개(색인 대상, modular·템플릿·README 제외)이고 `docs/`는 Vercel 배포 범위(`jam-web/`) 밖이라 서버 함수가 파일을 직접 읽을 수 없다. 티켓 파일을 하나씩 GitHub로 읽으면 요청이 수백 번이라, PRD §8대로 저장소에 **색인 파일 한 개**를 두고 그 한 파일만 읽는다.
- `origin/staging`이 `origin/main`보다 1,272커밋 앞선다(JAM 2.0 출시 전까지 main 배포 정지, 2026-10-15 결정). 그래서 「커밋 목록 비교」는 쓸 수 없고(GitHub 비교 API는 커밋 250개까지만 담는다) 앞선 개수(`ahead_by`)만 쓴다.
- 저장소에 GitHub API를 부르는 코드와 토큰 환경변수가 아직 없다. 배포 정지 상태를 기계가 읽을 수 있게 적은 곳도 없다(결정은 메모리와 대화에만 있다).
- 묶음은 상위 티켓 `20261016_2335`의 하위 티켓(`parent`)이고, 묶음 안의 하위 티켓은 그 묶음 티켓을 `parent`로 가진다(예: 묶음 4 `20261018_1811`의 하위 `20261018_1812`).

**정한 것 (카리나 제안)**

- **「staging 반영」과 「배포됨」을 가르는 규칙:** 색인 파일을 `staging`과 `main` 두 브랜치에서 읽어 티켓마다 견준다. staging 색인에서 `CLOSED`이고 main 색인에서 `CLOSED`가 아니거나 없으면 「staging 반영」, main 색인에서도 `CLOSED`이면 「배포됨」이다. 「티켓 커밋이 main에 있는지」와 같은 뜻이고, 커밋을 티켓에 잇는 규칙(커밋 메시지에 티켓 번호가 항상 있다는 보장)이 필요 없다. 보드 칸은 `OPEN`·`WAITING`=대기, `IN_PROGRESS`=진행, 위 두 가지=staging 반영·배포됨이다. 「배포됨」은 최근 14일(`closed` 기준)만 보인다.
- **색인 파일은 `docs/tickets/_index.json`**(생성물, 티켓 하나당 한 줄 `{id,title,status,category,priority,parent,origin,created,closed,path}`, id 순). 손으로 고치지 않는다. 생성기는 **작업 폴더가 아니라 git 인덱스(스테이지된 상태)에서 티켓을 읽는다.** 병렬 세션이 작업 폴더를 같이 써서, 작업 폴더를 읽으면 남의 미스테이지 티켓 변경이 이 커밋의 색인에 섞인다.
- **갱신은 커밋 훅이 자동으로 한다**(`.githooks/pre-commit`이 스테이지된 티켓 파일이 있으면 색인을 다시 만들어 스테이지). 티켓을 만들거나 닫을 때마다 직접 돌리는 일이 없게 한다. 병합으로 색인에 충돌이 나면 손으로 풀지 않고 생성기를 다시 돌린다(`docs/INDEX.md`와 같은 규칙). CI(`verify.sh`)는 `--check`로 최신인지 본다.
- **GitHub 읽기(2회차):** 저장소는 공개라 토큰 없이도 읽히지만 비인증 한도가 시간당 60번이라, 서버 환경변수 `GITHUB_READ_TOKEN`(읽기 전용 토큰, 있으면 쓰고 없으면 비인증으로 읽는다. 값은 사용자가 Vercel에 넣고 채팅에 쓰지 않는다) 하나만 쓴다. 저장소 `standardmanual/jam`은 코드 상수다. 읽는 것: 색인(`contents` 원문, `ref=staging`·`ref=main`), 앞선 커밋 수(`compare/main...staging`의 `ahead_by`), 프로덕션 마지막 배포(`deployments`, 없으면 main 마지막 커밋 시각), 배포 상태 파일. 요청에는 짧은 캐시(60초)를 둔다.
- **배포 상태 파일 `docs/operations/deploy-state.json`**(2회차, 새): `{ "frozen": true, "reason": "...", "nextDeploy": "..." }`. 동결 결정과 다음 배포 일정의 단일 원천이다. 카리나가 `/jam-ship`을 다시 켤 때 고친다.
- 보드 카드의 출처(운영에서·생태계에서·그 밖)는 티켓 `origin`이 있을 때만 쓴다(옛 티켓 수천 장에 「그 밖」이 붙는 소음을 피한다). 개발 요청은 요청 행의 `origin`을 쓴다.

### 2회차: GitHub 읽기와 보드·묶음 계산 (화면 없음)

**1회차 확인 결과 (2026-10-27, 카리나)**: 색인 `docs/tickets/_index.json`은 2,016건·약 750KB다. 격리 워크트리에서 실제 훅으로 확인했다: 새 티켓을 스테이지해 커밋하면 훅이 「`_index.json`를 갱신했습니다」를 출력하고 같은 커밋에 색인 변경(새 항목 1줄, `origin: eco`도 읽힘)이 들어간다, 남의 티켓(2027)을 미스테이지로 `CLOSED→OPEN` 고쳐 둔 채 임시 티켓만 커밋해도 색인의 2027은 `CLOSED` 그대로이고 임시 티켓만 갱신된다(작업 폴더를 읽지 않고 git 인덱스를 읽는다), 티켓 삭제는 색인에서 빠지고, 스테이지 후 색인이 낡으면 `--check`가 1을 낸다. 확인에 쓴 임시 워크트리·브랜치·티켓은 지웠다.

**조사로 알게 된 것 (2026-10-27, GitHub 실제 응답)**

- 저장소 `standardmanual/jam`은 **공개**다. 비인증으로도 `compare`·`contents`가 200이고 한도는 시간당 60번, 토큰이 있으면 5,000번이다.
- **프로덕션 배포의 환경 이름은 `Production – jam`**(가운뎃줄이 엔대시 `–`)이고 마지막 배포는 2026-10-14 07:31:59Z(커밋 `1e2d55e2`, 상태 `success`)다. 옛 이름 `Production`은 2026-08-14에서 멈췄고, `Production – jam-stage`는 staging 쪽 배포다(최신 2026-10-27). 이름이 바뀔 수 있어 배포를 못 찾으면 `main` 마지막 커밋 시각으로 대신한다(추정으로 표시).
- `compare/main...staging`의 `ahead_by`는 1,273(`git rev-list --count origin/main..origin/staging`과 같은 값)이고, 응답의 커밋 목록은 250개에서 잘리므로 `ahead_by`만 쓴다.
- **`main`에는 아직 `docs/tickets/_index.json`이 없다**(JAM 2.0 출시 전까지 main 배포 정지). 그래서 `main` 색인 읽기는 404가 정상이고, 이 경우 「배포됨」은 **추정 규칙**으로 가른다: `CLOSED`이고 `closed` 날짜(KST)가 프로덕션 마지막 배포 날짜 이하이면 「배포됨(추정)」, 그 뒤면 「staging 반영」이다. `main`에 색인이 생기면 1회차에서 정한 정확한 규칙(두 색인 견줌)이 자동으로 적용된다.
- 묶음 0~7의 티켓 ID는 상위 티켓 `20261016_2335`의 표에 있다: 0 `20261016_2336`, 1 `20261016_2337`, 2 `20261017_1420`, 3 `20261018_0050`, 4 `20261018_1811`, 5 `20261019_1310`, 6 `20261021_1246`, 7 `20261022_1131`. 묶음의 하위는 자손 전체(예: 묶음 2는 직속 17개, 묶음 5는 22개)이고 3단계 하위도 있다.

**정한 것**

- 색인과 배포 상태 파일의 읽기는 **모듈 안의 짧은 기억(60초)**으로 한다. Next 데이터 캐시는 항목 2MB 상한이 있어 색인(지금 750KB, 늘어남)이 상한을 넘으면 조용히 캐시되지 않으므로 쓰지 않는다. 같은 인스턴스에서 동시에 오는 읽기는 하나로 합친다.
- 읽기 실패는 그 부분만 `error`로 둔다(밸런스·생태계와 같은 방식): 색인을 못 읽으면 보드·묶음이, `compare`를 못 읽으면 앞선 커밋 수만, 배포 기록을 못 읽으면 마지막 배포만 `null`이 된다. 한도 초과(403/429)는 별도 사유로 알려 토큰을 권한다. 오류 문구는 고정 문장이고 응답 본문을 싣지 않는다.
- **배포 상태는 `docs/operations/deploy-state.json`**(새, `staging`에서 읽음): `{ "frozen": true, "reason": "...", "nextDeploy": "..." }`. 처음 값은 `frozen: true`, 사유 「JAM 2.0 출시 전까지 main 배포를 멈춤(2026-10-15 결정)」, 다음 배포 「JAM 2.0 출시 때」다. 상태 글자는 동결이면 「동결」, 아니고 앞선 커밋이 있으면 「배포 가능」, 앞선 커밋이 없으면 「배포할 것 없음」, 파일을 못 읽으면 「확인 안 됨」이다.
- 보드 칸: `OPEN`·`WAITING`=대기, `IN_PROGRESS`=진행, 그 밖은 위 판정으로 「staging 반영」·「배포됨」이고, 「배포됨」은 `closed`가 최근 14일인 것만 센다. 카드는 우선순위(P0→P3), 같으면 id 큰 것(최근) 순이고 칸마다 30장까지만 담고 전체 개수를 따로 준다. 개발 요청(`requested`)은 「대기」 칸 맨 앞에 요청 카드로 합친다. 카드의 출처는 티켓 `origin`이 있을 때만 쓴다.
- 묶음은 묶음 티켓의 자손 전체에서 끝남(`CLOSED`)·진행(`IN_PROGRESS`)·남음(`OPEN`·`WAITING`)을 센다(묶음 티켓 자신은 세지 않는다).

## 상세 요구사항

- GitHub 토큰은 서버 환경변수에만 둔다. 환경변수 추가는 사용자가 Vercel에서 한다(값을 채팅에 쓰지 않는다).
- 「staging 반영」과 「배포됨」은 티켓 커밋이 main에 있는지로 가른다. 판정 규칙을 이 티켓에서 정하고 PRD §8에 적는다.
- 티켓 frontmatter에 선택 필드 `origin`(`ops`·`eco`·`other`)을 더한다. 기존 티켓은 소급하지 않는다.
- 새로 적는 환경 주장(환경변수 이름 등)은 `docs/agents/contract.json`에 검사 줄을 함께 더한다(CLAUDE.md 절대 규칙 5).
