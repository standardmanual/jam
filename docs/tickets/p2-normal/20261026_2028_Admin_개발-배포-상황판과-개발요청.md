# [Admin] 개발·배포 상황판(GitHub 읽기)과 개발 요청

> 상위: 20261026_2020

## 핵심 요약

- 요구사항: 배포 현황, JAM 2.0 묶음 진행, 개발 항목 보드(대기·진행·staging 반영·배포됨, 출처 표시)를 GitHub에서 실시간으로 읽어 보인다(D3, PRD §8). 다른 상황판의 [개발 요청]을 받는다.
- 구현 계획: 티켓 색인 파일을 저장소에 두는 방식을 정하고(커밋 훅 또는 생성 스크립트), 서버에서 GitHub API로 색인·브랜치 비교·배포 기록을 읽는다. 개발 요청은 DB에 쌓고 카리나가 세션 시작 때 티켓으로 바꾼다.
- 개발 요청 저장은 2027 1회차가 만들었다(테이블 `ops_dev_requests`, `GET/POST /api/admin/dev-requests`). 이 티켓은 읽어서 보드 「대기」에 「요청」으로 보이기만 한다.
- 관련 파일: `scripts/ticket-dashboard.mjs`(현황 집계 로직), `.githooks/pre-commit`, `docs/DOCUMENT_SCHEMA.md`(`origin` 선택 필드), `docs/agents/orchestrator.md`(세션 시작 절차), `jam-web/src/app/admin/`(새 화면)

## 구현 계획 (3회차로 나눈다)

큰 티켓이라 회차로 나눈다. 순서: 1회차 = 티켓 색인 파일과 생성기(코드 읽기 없음), 2회차 = GitHub 읽기와 보드·묶음 계산(화면 없음), 3회차 = 화면. 요약은 2,500자 이내, 어드민 UI는 shadcn 부품만 쓴다.

**조사로 알게 된 것 (2026-10-27)**

- 티켓은 지금 2,049개이고 `docs/`는 Vercel 배포 범위(`jam-web/`) 밖이라 서버 함수가 파일을 직접 읽을 수 없다. 티켓 파일을 하나씩 GitHub로 읽으면 요청이 수백 번이라, PRD §8대로 저장소에 **색인 파일 한 개**를 두고 그 한 파일만 읽는다.
- `origin/staging`이 `origin/main`보다 1,272커밋 앞선다(JAM 2.0 출시 전까지 main 배포 정지, 2026-10-15 결정). 그래서 「커밋 목록 비교」는 쓸 수 없고(GitHub 비교 API는 커밋 250개까지만 담는다) 앞선 개수(`ahead_by`)만 쓴다.
- 저장소에 GitHub API를 부르는 코드와 토큰 환경변수가 아직 없다. 배포 정지 상태를 기계가 읽을 수 있게 적은 곳도 없다(결정은 메모리와 대화에만 있다).
- 묶음은 상위 티켓 `20261016_2335`의 하위 티켓(`parent`)이고, 묶음 안의 하위 티켓은 그 묶음 티켓을 `parent`로 가진다(예: 묶음 4 `20261018_1811`의 하위 `20261018_1812`).

**정한 것 (카리나 제안)**

- **「staging 반영」과 「배포됨」을 가르는 규칙:** 색인 파일을 `staging`과 `main` 두 브랜치에서 읽어 티켓마다 견준다. staging 색인에서 `CLOSED`이고 main 색인에서 `CLOSED`가 아니거나 없으면 「staging 반영」, main 색인에서도 `CLOSED`이면 「배포됨」이다. 「티켓 커밋이 main에 있는지」와 같은 뜻이고, 커밋을 티켓에 잇는 규칙(커밋 메시지에 티켓 번호가 항상 있다는 보장)이 필요 없다. 보드 칸은 `OPEN`·`WAITING`=대기, `IN_PROGRESS`=진행, 위 두 가지=staging 반영·배포됨이다. 「배포됨」은 최근 14일(`closed` 기준)만 보인다.
- **색인 파일은 `docs/tickets/_index.json`**(생성물, 티켓 하나당 한 줄 `{id,title,status,category,priority,parent,origin,created,closed,path}`, id 순). 손으로 고치지 않는다. 생성기는 **작업 폴더가 아니라 git 인덱스(스테이지된 상태)에서 티켓을 읽는다.** 병렬 세션이 작업 폴더를 같이 써서, 작업 폴더를 읽으면 남의 미스테이지 티켓 변경이 이 커밋의 색인에 섞인다.
- **갱신은 커밋 훅이 자동으로 한다**(`.githooks/pre-commit`이 스테이지된 티켓 파일이 있으면 색인을 다시 만들어 스테이지). 티켓을 만들거나 닫을 때마다 직접 돌리는 일이 없게 한다. 병합으로 색인에 충돌이 나면 손으로 풀지 않고 생성기를 다시 돌린다(`docs/INDEX.md`와 같은 규칙). CI(`verify.sh`)는 `--check`로 최신인지 본다.
- **GitHub 읽기(2회차):** 서버 환경변수 `GITHUB_READ_TOKEN`(읽기 전용 토큰, 값은 사용자가 Vercel에 넣고 채팅에 쓰지 않는다) 하나만 쓴다. 저장소 `standardmanual/jam`은 코드 상수다. 읽는 것: 색인(`contents` 원문, `ref=staging`·`ref=main`), 앞선 커밋 수(`compare/main...staging`의 `ahead_by`), 프로덕션 마지막 배포(`deployments`, 없으면 main 마지막 커밋 시각), 배포 상태 파일. 요청에는 짧은 캐시(60초)를 둔다.
- **배포 상태 파일 `docs/operations/deploy-state.json`**(2회차, 새): `{ "frozen": true, "reason": "...", "nextDeploy": "..." }`. 동결 결정과 다음 배포 일정의 단일 원천이다. 카리나가 `/jam-ship`을 다시 켤 때 고친다.
- 보드 카드의 출처(운영에서·생태계에서·그 밖)는 티켓 `origin`이 있을 때만 쓴다(옛 티켓 수천 장에 「그 밖」이 붙는 소음을 피한다). 개발 요청은 요청 행의 `origin`을 쓴다.

### 1회차: 티켓 색인 파일과 생성기 (화면·GitHub 없음)

1. `scripts/gen-ticket-index.mjs` (새, 형식은 `scripts/gen-doc-index.mjs`를 따른다): 내보내기 `TICKET_INDEX_PATH = 'docs/tickets/_index.json'`, 순수 함수 `parseTicketEntry(path, text)`(frontmatter와 첫 H1에서 `{id,title,status,category,priority,parent,origin,created,closed,path}`를 만든다. 따옴표를 벗기고, 제목의 `[카테고리] ` 접두와 뒤쪽 `(…)` 후속 표시는 그대로 두되 100자로 자르고, `origin`은 `ops`·`eco`·`other` 밖이면 빈 문자열, frontmatter가 없으면 `null`), `buildTicketIndex(entries)`(id 오름차순, 같으면 경로순), `serializeTicketIndex(entries)`(JSON 배열, **티켓 한 줄**, 끝에 줄바꿈, 시각·난수 없음). 제외: `docs/tickets/modular/`, `_TEMPLATE.md`, `README.md`, `Archive` 폴더(현황판 `ticket-dashboard.mjs`의 `walkMarkdownFiles`와 같은 기준). 읽기: `readTicketsFromGitIndex()`가 `git ls-files -s -z -- docs/tickets`로 블롭 목록을 얻고 `git cat-file --batch` 한 프로세스로 내용을 읽는다(티켓 2천여 개를 `git show`로 하나씩 부르지 않는다). 사용법: 기본은 색인 파일을 쓰고, `--check`는 git 인덱스에 올라간 색인 파일 내용과 생성 결과가 같은지만 보며(다르면 종료 코드 1과 「node scripts/gen-ticket-index.mjs를 돌리세요」 안내), `--stage`는 쓰고 `git add`까지 한다(훅용). frontmatter가 없는 파일은 건너뛰고 건수를 표준 오류에 한 줄 쓴다(실패로 치지 않는다).
2. `.githooks/pre-commit` (수정, 264줄 `gen-doc-index.mjs --check` 블록 뒤): 스테이지된 파일 중 `docs/tickets/` 아래 `.md`가 하나라도 있으면(추가·수정·삭제·이름 바꿈 모두) `node scripts/gen-ticket-index.mjs --stage`를 실행하고, 실패하면 커밋을 막는다(`doclint=1`과 같은 방식). 병합 충돌 안내 문구를 `gen-doc-index`와 같은 어조로 한 줄 단다. `git commit <경로>`처럼 경로를 지정한 부분 커밋은 훅의 `git add`가 그 커밋에 들어가지 않으므로, 그 경우를 `verify.sh --check`가 잡는다는 사실을 주석에 적는다.
3. `scripts/verify.sh` (수정, `gen-team-map.mjs --check` 블록 뒤): `node scripts/gen-ticket-index.mjs --check`를 같은 모양(`LOG_PREFIX.ticket-index`, `FAILED+=("ticket-index")`)으로 더한다.
4. `docs/tickets/_index.json` (새, 생성물): 처음 만든 색인을 커밋한다. 항목 수가 `docs/tickets/` 아래 대상 `.md` 수와 같아야 하고, `origin`은 지금 모두 빈 문자열이다.
5. `docs/DOCUMENT_SCHEMA.md` (수정): 티켓 필드 설명에 선택 필드 `origin`(`ops`·`eco`·`other`, 개발 요청에서 만든 티켓에만 적고 기존 티켓은 소급하지 않는다, §7 확장 규칙 1)을 쓴다. `scripts/doc-check.config.json`의 `types.ticket`에 `fields`에 `"origin"`을 더하고 `enums`로 `origin: ["ops","eco","other"]`를 둔다(다른 type의 `enums` 모양을 따른다). `docs/agents/orchestrator.md`의 「개발 요청 읽기」 단계가 이미 `origin`을 채우라고 쓰므로 그 문장과 어긋나지 않는지만 확인한다.
6. `docs/agents/contract.json` (수정): `paths_exist`에 `scripts/gen-ticket-index.mjs`, `scripts/gen-ticket-index.test.mjs`, `docs/tickets/_index.json`을 더하고, 파일 내용 검사 줄이 있는 형식이면 `.githooks/pre-commit`과 `scripts/verify.sh`에 `gen-ticket-index`가 들어 있다는 줄도 더한다(`node scripts/check-contract.mjs`로 확인).
7. `scripts/gen-ticket-index.test.mjs` (새, 다른 `scripts/*.test.mjs`와 같은 방식, 임시 git 저장소는 `GIT_*` 환경변수를 지우고 쓴다): `parseTicketEntry`(따옴표 있는 id·없는 id, `NNN` 옛 형식, `closed:` 빈 값, 허용 밖 `origin`, 제목 접두 제거와 100자 자르기, frontmatter 없음 → `null`), 직렬화(정렬·한 줄 한 티켓·같은 입력은 같은 결과), 제외 대상, 임시 저장소에서 `--check` 통과·미스테이지 작업 폴더 변경은 색인에 섞이지 않음(git 인덱스만 읽음)·티켓을 스테이지하고 색인이 낡으면 1, `--stage`가 색인을 스테이지함.
8. 문서: `docs/service/prd/admin-boards/PRD.md` §8에 「구현됨(색인): 티켓 20261026_2028 1회차」와 위 판정 규칙·색인 파일·갱신 방식·`origin`을 쓴다(이 판정 규칙은 2회차 구현 전에 PRD에 먼저 적어 두고 2회차가 따른다).

**1회차에서 하지 않는 것**: GitHub 호출, 화면, 배포 상태 파일, `/jam-ship` 변경, 기존 티켓의 `origin` 채우기.

**완료 조건 (1회차)**

- 구현 범위: `node scripts/gen-ticket-index.mjs --check`가 통과하고 시험·`verify.sh`가 통과한다. 새 티켓을 스테이지해 커밋하면 훅이 색인을 갱신해 같은 커밋에 넣는다(시험 또는 임시 저장소 실행으로 확인).
- 후속 범위(카리나, 머지 뒤): 이 저장소에서 티켓 하나를 고쳐 커밋해 훅이 색인을 자동 갱신하는 것을 보고, 병렬 세션이 쓰는 작업 폴더에서 `git add -A` 없이도 색인에 남의 변경이 섞이지 않는지 한 번 확인한다.

### 2회차: GitHub 읽기와 보드·묶음 계산 (화면 없음, 1회차 머지 뒤 계획을 이어서 쓴다)

개요: `jam-web/src/lib/admin/devBoard/`에 GitHub 클라이언트(주입된 `fetch`, 읽기 전용, 오류는 고정 문장), 색인 두 브랜치 견줌(위 규칙), 보드 네 칸 계산, 묶음 0~7 끝남·진행·남음 계산, 개발 요청을 「대기」 칸의 「요청」으로 합치기, 배포 현황(앞선 커밋 수, 마지막 배포, 동결 여부, 다음 배포)을 만든다. `docs/operations/deploy-state.json`과 환경변수 `GITHUB_READ_TOKEN`을 `contract.json`에 더한다.

### 3회차: 화면 (2회차 머지 뒤 계획을 이어서 쓴다)

개요: `/admin/dev-board` 페이지(배포 현황, JAM 2.0 묶음 막대, 개발 항목 보드), 사이드바 항목, 토큰이 없을 때의 안내(「GITHUB_READ_TOKEN을 Vercel에 설정하세요」), PRD §8 구현됨 표기.

## 상세 요구사항

- GitHub 토큰은 서버 환경변수에만 둔다. 환경변수 추가는 사용자가 Vercel에서 한다(값을 채팅에 쓰지 않는다).
- 「staging 반영」과 「배포됨」은 티켓 커밋이 main에 있는지로 가른다. 판정 규칙을 이 티켓에서 정하고 PRD §8에 적는다.
- 티켓 frontmatter에 선택 필드 `origin`(`ops`·`eco`·`other`)을 더한다. 기존 티켓은 소급하지 않는다.
- 새로 적는 환경 주장(환경변수 이름 등)은 `docs/agents/contract.json`에 검사 줄을 함께 더한다(CLAUDE.md 절대 규칙 5).

## 완료 조건

- 로컬에서 개발·배포 상황판을 열면 staging이 main보다 앞선 커밋 수가 `git rev-list --count origin/main..origin/staging`과 같다.
- 묶음 0~7의 끝남·진행·남음 수가 `node scripts/ticket-dashboard.mjs --all`의 집계와 같다.
- 생태계 상황판에서 만든 개발 요청 1건이 보드의 「대기」에 「요청」으로 보이고, 세션 시작 절차 문서에 요청을 읽는 단계가 있다.
