# [Service] JAM 2.0 노출 태그 더하기: 트라이브·챕터·캡슐·잼·인벤토리

> 상위: 20261026_2020

## 핵심 요약

- 요구사항: 홈피드 노출 태그에 소속 트라이브, 챕터 구간, 캡슐 게이지, 잼 보유량, 인벤토리 여유를 기준으로 한 태그를 더한다(자동화 PRD §5).
- 구현 계획: 태그 이름과 경계값을 정하고 `computeUserExposureTags`에 판정을 더한다. 어드민 태그 선택지와 홈피드 PRD 생성 표를 갱신한다.
- 관련 파일: `jam-web/src/lib/today/exposure.ts`(266~300줄 `computeUserExposureTags`), `TODAY_EXPOSURE_TAG_OPTIONS`, `scripts/gen-home-feed-doc.mjs`, 스펙 `docs/service/prd/home-feed/PRD.md` §4, `docs/service/prd/content-automation/PRD.md` §5

## 구현 계획 (2회차로 나눈다)

순서: **1회차 = 챕터·캡슐·잼·인벤토리 태그**(이름과 경계를 이 티켓이 정하고 바로 구현), **2회차 = 소속 트라이브 태그**(식별자 문제가 있어 1회차 머지 뒤 계획을 이어서 쓴다). 요약은 2,500자 이내다.

**조사로 알게 된 것 (2026-10-27)**

- 노출 태그의 선택지는 `jam-web/src/lib/admin/today-sections.ts`의 `TODAY_EXPOSURE_TAG_OPTIONS` 한 곳이고, 운영 묶음 검증(`opsInbox/validate.ts` 201~214줄의 `validateExposureTags`)·어드민 카드 폼·홈피드 PRD 생성 표(`node scripts/gen-home-feed-doc.mjs`)가 모두 이 목록을 읽는다. 태그 값에 DB 제약은 없다(`today_cards.exposure_tags`에 CHECK 없음) → 마이그레이션이 필요 없다.
- 태그는 `getTodayCards`(`lib/today/cards.ts` 145줄)가 요청마다 `computeUserExposureTags(userId, now, userCreatedAt)`로 계산하고, 읽기는 `Promise.all` 한 묶음이다. 호출부는 유저 `created_at`만 넘기므로 챕터·캡슐·잼·인벤토리는 이 함수가 직접 읽는다(추가 조회 4개).
- 읽을 곳(실제 DB 칸 확인): 챕터 `user_chapters(user_id, chapter_no, total_score)`, 캡슐 `user_capsules(user_id, required, filled, chapter_no)`, 잼 `jam_wallets(user_id, balance)`, 인벤토리 `inventory(user_id, max_slots, used_slots)`. 캡슐 채움 비용은 챕터마다 90~220(`capsule_chapter_costs`)이고 `user_capsules.required`가 지금 캡슐의 필요량이다.
- 가상 유저(`lib/today/virtualViewer.ts`, 홈피드 미리보기)는 개인 상태 태그를 넣지 않는 규칙이라 이번 태그도 넣지 않는다(문서에 한 줄 적는다).
- `policiesData.ts`에는 노출 태그 항목이 없고 이 태그의 경계값은 서비스 운영 정책·밸런스 수치가 아니라 홈피드 세그먼트 값이므로 갱신 대상이 아니다.
- 트라이브는 `tribes` 표에 슬러그 같은 식별자 칸이 없고 `id`(UUID)와 한글 `name`만 있다(8행, 활성 2행). 태그 이름을 만들 안정적인 짧은 식별자가 없어 2회차로 미룬다.

**정한 것 (카리나 제안, 경계값은 가정 값이고 오픈 뒤 실제 데이터로 맞춘다)**

| 태그 | 판정 | 경계 |
|---|---|---|
| `chapter_1_3` · `chapter_4_6` · `chapter_7_9` · `chapter_10` | `user_chapters.chapter_no`가 그 구간 | 구간: 1~3(초반)·4~6(중반)·7~9(후반)·10(최고). 챕터 행이 없거나 1~10 밖이면 태그 없음 |
| `capsule_full` | `filled >= required` (`required > 0`) | 열 수 있는 상태 |
| `capsule_nearly_full` | `filled / required >= 0.8`이고 아직 안 참 | `CAPSULE_NEARLY_FULL_RATIO = 0.8` |
| `jam_plenty` | `balance >= required × 2` | `JAM_PLENTY_MULTIPLE = 2` |
| `jam_low` | `balance < required / 3` | `JAM_LOW_FRACTION = 1/3` |
| `inventory_full` | 남은 칸(`max_slots - used_slots`)이 0 이하 | |
| `inventory_nearly_full` | 남은 칸이 1~3 | 3은 밸런스 대시보드와 같은 값을 쓴다(`lib/admin/balanceDashboard/targets.ts`의 `INVENTORY_LOW_FREE_SLOTS`, 마이그레이션 237 알림 기준) |

- **잼 경계는 캡슐 필요량에 대한 배수로 정한다.** 잼 보유량의 절대값(예: 300)은 캡슐 비용(챕터마다 90~220)을 바꾸면 의미가 어긋난다. 필요량 기준이면 비용 정책을 바꿔도 「한 캡슐을 두 번 채울 만큼」·「한 캡슐의 3분의 1도 안 됨」이라는 뜻이 유지되고, 정책 대시보드의 비용 값을 따로 적어 두지 않아 값이 겹치지 않는다. 캡슐 행이 없으면 잼 태그도 붙이지 않는다. 지갑 행이 없는데 캡슐 행이 있으면 잔액 0으로 본다.
- 한 유저는 챕터 구간 1개, 캡슐 태그 0~1개, 잼 태그 0~1개, 인벤토리 태그 0~1개를 가진다(서로 배타). 읽기 하나가 실패하면 로그를 남기고 그 태그만 뺀다(기존 태그와 같은 방식, 잘못된 태그를 붙이지 않는다).

### 1회차: 챕터·캡슐·잼·인벤토리 태그 (10개) — 완료: 2026-10-27 머지(`656999947`), 실DB 대조·응답 시간 측정 통과

1. `jam-web/src/lib/today/exposureThresholds.ts` (새, 순수): 위 표의 구간·경계 상수(`CHAPTER_BANDS`, `CAPSULE_NEARLY_FULL_RATIO`, `JAM_PLENTY_MULTIPLE`, `JAM_LOW_FRACTION`)를 한 곳에 두고, 인벤토리 3은 `INVENTORY_LOW_FREE_SLOTS`를 가져와 다시 내보낸다. 「가정 값, 오픈 뒤 실제 데이터로 맞춘다」는 머리 주석을 단다(`balanceDashboard/targets.ts`의 태도).
2. `jam-web/src/lib/today/exposure.ts` (수정, 266~300줄 `computeUserExposureTags`와 그 위 순수 함수 구역): 순수 함수 `chapterBandTag(chapterNo)`, `capsuleGaugeTag(capsule)`, `jamBalanceTag(balance, capsule)`, `inventoryRoomTag(inventory)`를 내보낸다(null·0·음수·`filled > required`·`required <= 0`·챕터 0/11 같은 경계 입력은 태그 없음 또는 가장 가까운 규칙대로). 서버 읽기 4개(`getUserChapterNo`·`getUserCapsule`·`getJamBalance`·`getUserInventory`, 각 `maybeSingle`, 오류는 `console.error('[…] … 조회 오류:', error.message)`와 `null`)를 만들고 `computeUserExposureTags`의 `Promise.all` 묶음에 더해 병렬로 읽는다. 태그는 기존 태그 뒤에 챕터 → 캡슐 → 잼 → 인벤토리 순으로 붙인다.
3. `jam-web/src/lib/admin/today-sections.ts` (수정, 159~178줄 `TODAY_EXPOSURE_TAG_OPTIONS`): 새 태그 10개를 `{ value, label }`로 더한다. 라벨은 기존 방식대로 `값 (설명)`이다(예: `chapter_1_3 (챕터 1~3)`, `capsule_nearly_full (캡슐 80% 이상 참)`, `jam_plenty (잼이 캡슐 필요량의 2배 이상)`, `inventory_nearly_full (인벤토리 남은 칸 1~3)`).
4. 시험: `jam-web/src/lib/today/__tests__/exposure-tags-jam2.test.ts` (새): 순수 함수 경계(구간 경계 3·4·6·7·9·10, 챕터 0·11·null, 캡슐 79.9%·80%·100%·초과·`required` 0, 잼 경계 `required/3`·`required×2` 바로 위아래, 캡슐 없음이면 잼 태그 없음, 인벤토리 남은 칸 0·1·3·4와 `used > max`)와 **통합**(기존 `exposure-tags-segment.test.ts`와 같은 방식의 Supabase 모의: 새 표 4개가 각각 읽히고, 읽기 오류가 나면 그 태그만 빠지고 나머지는 붙고, 조회가 표마다 한 번씩이며, 모든 태그가 배타 규칙을 지킨다). 기존 `exposure-tags-segment.test.ts`·`today-logic.test.ts`·`virtualViewer.test.ts`의 모의가 새 표 조회로 깨지지 않게 맞춘다(새 표는 빈 결과를 돌려주게). **방출 가능한 태그가 모두 `TODAY_EXPOSURE_TAG_OPTIONS`에 있고 새 선택지 10개가 모두 방출 가능한지 양쪽 대조하는 시험**을 둔다.
5. 문서: `node scripts/gen-home-feed-doc.mjs`로 `docs/service/prd/home-feed/PRD.md` §4 생성 표를 갱신하고, §4의 **판정 표(생성 구간 밖)**에 새 태그 행을 손으로 쓴다(판정 문장과 경계 상수 이름, 가상 유저는 넣지 않는다는 한 줄). `docs/service/prd/content-automation/PRD.md` §5의 「JAM 2.0에서 더할 태그(예정…)」 문장을 「구현됨(티켓 20261026_2030 1회차): 챕터 구간 4개·캡슐 2개·잼 2개·인벤토리 2개, 소속 트라이브는 2회차」로 바꾼다(이 문서에 태그 표를 다시 적지 않는다). pre-commit의 홈피드 문서 동기화 검사(`gen-home-feed-doc.mjs --staged`)가 요구하면 같은 커밋에 문서를 함께 스테이지한다.

**1회차에서 하지 않는 것**: 소속 트라이브 태그, 가상 유저(미리보기)에 새 태그 입력, 어드민 카드 폼 화면 변경(선택지는 목록에서 자동으로 보인다), DB 마이그레이션, 홈 호출부(`getTodayCards`)의 시그니처 변경.

**완료 조건 (1회차)**

- 구현 범위: 각 새 태그가 조건을 만족하는 시험 유저에게만 붙고(단위·통합 시험), 방출 태그와 선택지 목록이 양쪽 대조로 같으며, `node scripts/gen-home-feed-doc.mjs --check`·`npm run typecheck`·`verify.sh`가 통과한다.
- 후속 범위(카리나, 머지 뒤): 실제 DB의 유저 한두 명(챕터·캡슐·지갑·인벤토리 행이 있는 유저)에 `computeUserExposureTags`를 돌려 태그가 SQL로 센 값과 맞는지 보고, 태그 계산 호출을 20번 반복해 **홈 응답 시간 변화**(중앙값, 머지 전후 같은 조건)를 잰다. 증가가 눈에 띄면(예: 중앙값 +50ms 이상) 4개 읽기를 한 번의 읽기(RPC·뷰)로 합치는 후속 티켓을 만든다.

**1회차 후속 범위 결과 (2026-10-27, 카리나)**

- **태그 대조(실제 DB, `computeUserExposureTags`를 실제로 호출):** 실DB 유저에는 챕터 행 0건·캡슐 행 2건(필요량 5, 채움 0)·지갑 행 0건이라 인벤토리·잼 태그만 걸린다. 그래서 테스트 계정 2개(`…0002`, `…0003`)에 임시 행(챕터·캡슐·지갑, 인벤토리 사용 칸 8)을 넣고 SQL로 독립 계산한 기대 태그와 견줬다.

| 유저 | 입력 | 코드가 붙인 태그 | SQL 기대 | 일치 |
|---|---|---|---|---|
| `…0002` | 챕터 5, 캡슐 85/100, 잼 250, 인벤토리 10칸 중 0 사용 | `chapter_4_6`·`capsule_nearly_full`·`jam_plenty` | 같음 | 일치 |
| `…0003` | 챕터 10, 캡슐 100/100, 잼 10, 인벤토리 10칸 중 8 사용 | `chapter_10`·`capsule_full`·`jam_low`·`inventory_nearly_full` | 같음 | 일치 |
| `…ebc4`(실유저) | 인벤토리 10/10 | `inventory_full` | 같음 | 일치 |
| `…0001`(테스트) | 캡슐 0/5, 지갑 없음(잔액 0) | `jam_low` | 같음 | 일치 |
| `…8f34`(실유저) | 캡슐 없음 | (없음) | 같음 | 일치 |

  임시 행은 모두 지우고 인벤토리 사용 칸을 0으로 되돌렸다(챕터 0·캡슐 2·지갑 0행으로 복구 확인). 캡슐이 없는 유저에게 잼 태그가 붙지 않는 것도 확인했다.
- **홈 응답 시간(태그 계산 20회 반복, 같은 유저·같은 조건, 이 PC에서 DB까지의 왕복 포함):** 머지 전 중앙값 103·108ms → 머지 후 3세트 중앙값 99~104·101~112ms. 최소·p95도 같은 범위라 **눈에 띄는 증가가 없다**(새 읽기 4개가 기존 `Promise.all` 안에서 가장 긴 읽기에 가려진다). 증가 기준(+50ms)에 한참 못 미치므로 읽기 통합 티켓은 만들지 않는다. 실제 서버(서울 리전)에서는 왕복이 더 짧아 차이는 더 작을 것이다(추정).

### 2회차: 소속 트라이브 태그 — 완료: 2026-10-27 머지(`95c747409`), 실DB 대조·어드민 폼 실화면 확인 통과

**조사로 알게 된 것 (2026-10-27)**

- `tribes`에는 슬러그 같은 짧은 식별자 칸이 없고 `id`(UUID)와 한글 `name`뿐이다(8행, 활성 2행). 정본 문서(`docs/service/content/TRIBES.md`)의 세계관 트라이브는 10개이고 JAM 2.0 정식 오픈은 5개다.
- **JAM 2.0의 새 트라이브는 사용자가 트라이브 화면에서 비활성으로 등록한 뒤 켠다**(`276_tribe_content_hanipman.sql` 머리 주석의 적용 순서). 오픈 때 트라이브 행이 새로 생기고 바뀌므로, 코드에 트라이브 목록이나 UUID 대응표를 박아 두면 그때마다 어긋난다.
- 지금 트라이브를 겨냥한 홈 카드는 없다. 숲속의 갱단 편집 카드도 `exposure_tags = ['all']`이고 카드의 `tribe_id`는 색 쌍을 고르는 데만 쓴다. 유저의 트라이브는 `users.tribe_id`이고 홈 조회(`getTodayCards`)는 이 값을 넘기지 않는다.
- 태그 값을 검사하는 곳이 둘이다: `lib/admin/opsInbox/validate.ts`의 `validateExposureTags`(201~214줄, `TODAY_EXPOSURE_TAG_OPTIONS`의 값만 허용)와 등록 스크립트 `scripts/asset-generator/registerHomeFeedBundle.mjs`의 `EXPOSURE_TAGS`(같은 원천). 어드민 카드 폼(`app/admin/today/TodayCardForm.tsx` 706~730줄)은 같은 목록으로 체크박스를 그린다.
- 가상 유저(`lib/today/virtualViewer.ts`)는 `tribeId`를 이미 갖고 있어 트라이브 태그는 가상 유저가 알 수 있는 조건이다.

**추천 (카리나): 후보 (가) 「태그를 `tribe_<트라이브 ID>`로 만들고 검증기가 이 형식을 받는다」**

| | (가) `tribe_<UUID>` 패턴 | (나) `tribes.slug` 칸 추가 |
|---|---|---|
| 새 트라이브가 생겼을 때 | 코드를 고치지 않아도 바로 태그가 된다 | 슬러그를 정해 넣고 선택지 목록(코드)에도 더해야 한다 |
| DB 변경 | 없음 | 마이그레이션(공용 DB, 즉시 프로덕션) |
| 태그 가독성 | UUID라 값은 읽기 어렵다(화면에는 트라이브 이름을 보인다) | `tribe_forest_gang`처럼 읽기 쉽다 |
| 기존 검증기 | 형식(정규식)도 받게 고친다 | 그대로 쓴다 |

(나)는 읽기 쉬운 값이 장점이지만, 오픈 때 트라이브가 새로 생기는 흐름에서는 슬러그와 선택지 목록을 손으로 맞춰야 해서 어긋나기 쉽다. 이 값은 운영자가 직접 쓰는 것이 아니라 화면이 고르는 값이라 읽기 어려워도 비용이 작다. 그래서 (가)를 추천한다. 트라이브를 겨냥한 카드를 `tribe_id` 칸으로 암묵적으로 거르는 안(카드에 `tribe_id`가 있으면 그 트라이브 유저에게만 노출)은 기존 카드 노출을 조용히 바꾸므로 채택하지 않는다.

**파일 단위 계획** (아현은 이 순서로 한다.)

1. `jam-web/src/lib/today/exposureTribe.ts` (새, 순수): `TRIBE_TAG_PREFIX = 'tribe_'`, `tribeTagOf(tribeId)`(UUID 형식이 아니거나 null이면 null, 소문자로 정규화), `isTribeTag(value)`(접두어 + UUID 정규식 전체 일치), `tribeIdOfTag(tag)`.

### 주요 의사결정 / 핵심 메모
- 두 회차로 나눴다. 이름과 경계를 정하면 바로 구현되는 네 묶음(1회차)과, 태그 식별자 문제가 있는 트라이브(2회차)를 갈라 불확실한 부분이 앞 회차를 막지 않게 했다. 재작업은 없었다.
- **잼 경계는 절대값이 아니라 캡슐 필요량의 배수로 정했다.** 캡슐 비용이 챕터마다 90~220이라 절대값은 비용 정책이 바뀔 때 뜻이 어긋나고, 필요량 기준이면 뜻이 유지되며 정책 대시보드의 비용 값을 따로 적어 두지 않아 값이 겹치지 않는다. 캡슐 행이 없으면 잼 태그도 붙이지 않고, 캡슐은 있는데 지갑 행이 없으면 잔액 0으로 본다.
- 경계값(80%, 2배, 3분의 1, 챕터 구간)은 **가정 값**이다. 한 파일(`exposureThresholds.ts`)에 모아 두었고 오픈 뒤 실제 데이터로 맞춘다. 인벤토리 「남은 칸 3」은 밸런스 대시보드의 `INVENTORY_LOW_FREE_SLOTS`를 가져다 쓴다.
- **트라이브 태그는 `tribe_<트라이브 ID>` 패턴으로 만들었다(추천안 (가)).** JAM 2.0의 트라이브는 오픈 때 운영 화면에서 새로 등록하고 켜므로, 슬러그 칸(나)을 두면 슬러그와 선택지 목록을 손으로 맞춰야 한다. 값은 UUID라 읽기 어렵지만 화면이 이름으로 보인다. 카드의 `tribe_id`로 암묵적으로 거르는 안은 기존 카드 노출을 조용히 바꾸므로 채택하지 않았다. 이 구현 중 DB의 트라이브가 실제로 15개(활성 8)라는 것을 확인했다(조사 때 8행은 `LIMIT 8` 때문에 일부만 본 것이다).
- 가상 유저(홈피드 미리보기)는 개인 상태 태그를 넣지 않는 규칙이라 챕터·캡슐·잼·인벤토리 태그는 넣지 않고, 트라이브 태그만 가상 유저가 아는 조건이라 넣었다. PRD §4에 이 구분을 적었다.
- 티켓 본문의 `targets.ts` 경로 오기(`lib/admin/policyDashboard/balanceDashboard/` → 실제 `lib/admin/balanceDashboard/`)를 바로잡았다.
- 실화면 확인은 Browser 창을 보이게 한 상태에서 한다(숨겨져 있으면 하이드레이션이 멈춤).

### 잔여 이슈
- 경계값(80%, 2배, 3분의 1, 챕터 구간 4개)을 오픈 뒤 실제 데이터로 한 번 다시 본다.
- 홈피드 미리보기에 챕터·캡슐·잼·인벤토리 상태를 고르는 입력은 없다(가상 유저 규칙). 필요해지면 별도 기획으로 다룬다.
- 챕터·캡슐·잼 태그는 실DB에 해당 행이 거의 없어(챕터 0행, 캡슐 2행, 지갑 0행) 실제 유저 분포는 오픈 뒤에 처음 드러난다.
