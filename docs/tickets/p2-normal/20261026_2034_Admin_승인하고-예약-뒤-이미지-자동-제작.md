# [Admin] 「승인하고 예약」 뒤에 이미지를 자동으로 만든다 (2031 후속, 첫 실제 묶음 전에 끝낸다)

> 상위: 20261026_2020

## 핵심 요약

- 요구사항: 「N건 승인하고 예약」을 누르면, 이미지 지시(`image_spec`)가 있고 이미지가 비어 있는 항목은 이미지를 자동으로 만들어 올린다. 승인과 예약이 한 번에 일어나면서 사라진 「이미지 만들 시간」을 되살린다.
- 결정(카리나, 2026-10-27): 서버의 이미지 API는 예약됨 항목도 받는다(`image.ts`의 `BLOCKED_STATUSES`는 반려·취소·실패·종료뿐이고, 예약된 뒤에는 자원 행에도 쓴다). 그래서 서버는 고치지 않는다. 화면만 고친다.
- 관련 파일: 아래 「구현 계획」 참조. 스펙 `docs/plan/vision/07 JAM! 라이브 운영 블루프린트.md` 4.5, `docs/service/prd/ops-tool/PRD.md`(§7.3 이미지 제작 절, 221·407·1399~1402줄 부근)

## 구현 계획 (파일 단위)

1. `jam-web/src/lib/admin/opsSignals/composition.ts` 107줄 `OPS_IMAGE_PRODUCTION_STATUSES`에 `'scheduled'`를 더한다(`['approved', 'preparing', 'scheduled']`). 105~106줄 주석과 139~143줄 `needsImageProduction` 주석을 「승인됨·준비중·예약됨」으로 고친다. 이 한 줄로 [이미지 만들기] 버튼(`OpsImageProduction.tsx` 37줄), 미리보기의 「이미지 제작 필요」(`OpsCardPreview.tsx` 60줄), 구성의 `needsImageProduction`(344·439줄)이 예약됨 항목까지 넓어진다. 게재중(`live`)은 넣지 않는다.
2. `jam-web/src/lib/admin/opsInbox/executeView.ts` 374줄 `readExecuteResult` 아래에 `scheduledItemIds(data)`를 더한다. 응답의 `data.scheduled`(문자열 배열)에서 문자열만 골라 ID 배열로 돌려준다. 배열이 아니면 빈 배열이다.
3. `jam-web/src/components/admin/ops/useItemImageProduction.ts`:
   - 순수 함수 `produceItemImages(bundleId, itemIds, items, isSample)`를 `produceItemImage` 아래에 더한다. `itemIds` 순서대로 하나씩(순차, 병렬 아님) `produceItemImage`를 부르고 `{ done, failed, skipped }` 건수를 돌려준다. `items`에 없는 ID는 건너뛴 것으로 센다. 던지지 않는다.
   - 훅 반환에 `startMany(itemIds, items)`를 더한다. 이미 만드는 중인 ID는 빼고, 남은 ID를 `making`에 한꺼번에 넣은 뒤 `produceItemImages`를 돌리고 끝나면 `making`에서 빼고 `onDone`을 한 번 부른다. 실패가 하나라도 있으면 경고 토스트 하나(`IMAGE_FAILED_AFTER_SCHEDULE_TOAST`: 「예약은 유지했어요. 이미지 N건을 만들지 못해 「이미지 제작 필요」로 남겨 뒀어요.」)를 띄운다. 시험 묶음이면 아무것도 하지 않는다. 던지지 않는다.
   - 파일 머리 주석의 「일괄 승인은 이 훅을 부르지 않는다」를 새 동작에 맞게 고친다.
4. `jam-web/src/components/admin/ops/OpsDecisionWorkspace.tsx` 98~104줄 `handleExecuted`: `refresh()` 다음 줄에 `void imageProduction.startMany(scheduledItemIds(data), items)`를 더한다. `items`는 실행 전 스냅샷이어도 된다(`image_spec`만 읽는다). import에 `scheduledItemIds`를 더한다.
5. `jam-web/src/components/admin/ops/OpsImageProduction.tsx` 머리 주석(「아무것도 그리지 않는 경우」)에서 「게재중·예약됨 포함」을 「게재중 포함」으로 고친다.
6. 시험:
   - `jam-web/src/lib/admin/opsSignals/__tests__/composition.test.ts` 213~240줄: 「승인됨·준비중」 케이스에 `scheduled`를 더하고, 「표시하지 않는다」 목록(239줄)에서 `scheduled`를 뺀다.
   - `jam-web/src/lib/admin/opsInbox/__tests__/executeView.test.ts` 488줄 근처: `scheduledItemIds`(배열 아님·문자열 아닌 값 거르기)를 더한다.
   - `jam-web/src/components/admin/ops/__tests__/itemImageProduction.test.ts`: `produceItemImages`(순차 호출 순서, 건수 집계, 목록에 없는 ID, 시험 묶음) 케이스를 더한다.
   - `jam-web/src/components/admin/ops/__tests__/imageProduction.test.tsx` 68~72줄: 「그리지 않는다」 목록에서 `scheduled`를 빼고, 예약됨이면 버튼이 보이는 케이스를 더한다.
7. 문서:
   - `docs/service/prd/ops-tool/PRD.md` 221줄(「이미지 제작 필요」: 승인됨·준비중 → 승인됨·준비중·예약됨)·407줄(카드 미리보기 상태 문구)·1399~1402줄(자동 제작 절: 「[N건 승인하고 예약]도 자동 제작을 부르지 않는다」·「게재중·예약됨 항목에는 표시하지 않는다」를 새 동작으로 교체)을 고친다.
   - `docs/service/prd/admin-boards/PRD.md`의 승인하고 예약 절에 한 줄(승인 뒤 이미지 자동 제작, 실패해도 예약 유지)을 더한다.
   - 정책 대시보드(`policiesData.ts`)는 밸런스·확률 수치가 아니므로 갱신하지 않는다.

## 배경 / 문제 정의

2031 게이트(민지)가 찾았다. 예전에는 일괄 승인 뒤 항목이 「승인됨」에 머물러, 운영자가 [이미지 만들기]를 눌러 이미지를 채운 다음 「예약 등록」을 했다. 새 흐름은 항목이 곧바로 「예약됨」이 되고, 수동 버튼은 승인됨·준비중에만 나오므로 이미지 없이 예약될 수 있다. 사전 점검은 이미지 유무를 막지 않는다. 07 4.5는 「승인할 때 운영툴이 이미지를 만든다」다.

## 완료 조건

**구현 범위 (아현·민지)**
- 「승인하고 예약」 성공 응답의 `scheduled` 항목마다 `image_spec`이 있으면 이미지를 하나씩 순서대로 만들어 올린다(`produceItemImages`).
- 제작이 실패해도 예약은 유지되고 토스트 하나로 알린다. 예약됨 항목에도 「이미지 제작 필요」 표시와 [이미지 만들기]·다시 만들기 버튼이 보인다.
- 시험 묶음은 렌더도 저장도 하지 않는다(지금과 같음).
- 위 구현 계획의 시험과 문서 갱신이 들어 있다. 이 환경의 `.tsx` 시험 실패는 로컬 환경 문제라 CI 결과로 판정한다.

**후속 범위 (카리나, 머지 뒤 push 전)**
- 메인 트리에서 `jam-web-admin` 프리뷰로 시험 묶음이 아닌 실제 묶음을 승인하고 예약해, 이미지가 만들어져 자원 행(`cover_image_url`)에 붙는지 DB로 대조한다. 끝나면 공개 전 취소로 되돌린다.
