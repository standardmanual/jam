# [Infra] 트렌드 출처 종류 제약에 저장소 폴더(repo_folder)를 더하는 마이그레이션 298 (db, 조각 A)

## 핵심 요약

- 요구사항: `ops_trend_sources.kind`의 CHECK 제약에 `repo_folder`를 더한다. 확장만 하며 기존 행·컬럼은 건드리지 않는다.
- 구현 계획: `jam-web/supabase/migrations/298_ops_trend_sources_repo_folder_kind.sql` 파일 하나를 쓴다(번호는 착수 때 `ls`로 다시 확인한다. 2026-10-28 14:24 기준 마지막은 297). **파일 작성까지가 아현의 일이다. 실행은 머지 뒤 카리나가 한다**(`db-migration-rules.md`, CLAUDE.md 절대 규칙 6).
- 관련 파일: `jam-web/supabase/migrations/296_ops_trend_sources.sql` 23행(`kind` CHECK의 원본), 같은 파일의 머리 주석과 되돌림 블록(형식 본보기).

## 배경 / 문제 정의

- 상위 티켓 20261028_1422(트렌드 출처에 저장소 폴더 종류를 더한다)의 조각 A다. B(검증·API)가 `repo_folder`를 받으려면 DB가 먼저 이 값을 허용해야 한다.
- 2026-10-28 읽기 SQL로 확인한 제약 이름: `ops_trend_sources_kind_check`, 정의 `CHECK (kind = ANY (ARRAY['hashtag', 'channel', 'search_trend', 'manual_upload']))`. 같은 표의 다른 제약은 `ops_trend_sources_location_check`(300자), `ops_trend_sources_name_check`, `ops_trend_sources_no_key`, `ops_trend_sources_pkey`다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 한 트랜잭션 안에서 제약을 지우고 5종(`hashtag`, `channel`, `search_trend`, `manual_upload`, `repo_folder`)으로 다시 만든다. 제약 이름은 그대로 `ops_trend_sources_kind_check`를 쓴다.
- `kind`와 `location` 컬럼 주석을 새 종류에 맞게 고친다. 위치 주석에는 「저장소 폴더 종류는 허용 폴더 경로」를 더한다.
- 새 컬럼·인덱스·함수는 없다. 코드(`jam-web/src`) 변경도 없다.

## 구현 계획

파일 하나 `jam-web/supabase/migrations/298_ops_trend_sources_repo_folder_kind.sql`:

1. 머리 주석: 296 파일의 머리와 같은 형식(티켓 번호, 실행은 카리나라는 경고, 동기, 변경 요약 「확장만」).
2. 본문:
   ```sql
   BEGIN;
   ALTER TABLE public.ops_trend_sources DROP CONSTRAINT IF EXISTS ops_trend_sources_kind_check;
   ALTER TABLE public.ops_trend_sources
     ADD CONSTRAINT ops_trend_sources_kind_check
     CHECK (kind IN ('hashtag', 'channel', 'search_trend', 'manual_upload', 'repo_folder'));
   COMMENT ON COLUMN public.ops_trend_sources.kind IS '출처 종류: hashtag(해시태그) · channel(채널) · search_trend(검색어 추이) · manual_upload(직접 올린 자료) · repo_folder(저장소 폴더).';
   COMMENT ON COLUMN public.ops_trend_sources.location IS '주소·해시태그·검색어, 저장소 폴더 종류는 허용 폴더 경로(300자 이내). 직접 올린 자료는 비워도 된다.';
   COMMIT;
   ```
3. 검증 쿼리 주석: `SELECT pg_get_constraintdef(oid) FROM pg_constraint WHERE conrelid = 'public.ops_trend_sources'::regclass AND conname = 'ops_trend_sources_kind_check';` → 5종이 나와야 한다. 행을 넣어 확인하는 쿼리는 쓰지 않는다(`no`가 자동 증가라 시험으로 넣었다 롤백해도 번호가 건너뛰어진다).
4. 되돌림 SQL 블록(파일 끝, `-- 되돌림 SQL`로 시작): 제약을 4종으로 되돌리는 두 문장을 주석으로 싣는다. 단 `repo_folder` 행이 있으면 되돌릴 수 없다는 경고를 함께 적는다(출처 행은 지우지 않는 규칙이라, 실제 되돌림은 그 행을 `enabled = false`로 끄고 제약은 그대로 두는 것으로 대신한다).

규모: 파일 1개, 약 40줄(주석 포함). `plan_only` 임계값(파일 5개 초과 또는 100줄 이상)을 넘지 않는다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)

- `298_ops_trend_sources_repo_folder_kind.sql`이 있고, 한 트랜잭션에서 제약을 5종으로 바꾼다.
- 파일 끝에 `-- 되돌림 SQL`로 시작하는 블록이 있고 검증 쿼리 주석이 있다(`scripts/deploy-gate.mjs check`의 되돌림 표식 검사 통과).
- 기존 제약 이름(`ops_trend_sources_kind_check`)을 쓰고, 다른 제약·컬럼·인덱스를 건드리지 않는다.
- 코드 변경이 없고 `scripts/verify.sh`가 통과한다.

### 후속 범위 (담당: 카리나, 시점: 머지 뒤)

- 실행 전: 현재 제약 정의와 행 수를 읽기 전용 SQL로 확인하고 되돌림 SQL을 다시 읽는다.
- 실행: Supabase MCP로 파일 내용을 적용한다(공용 DB라 즉시 프로덕션에 반영된다).
- 실행 직후: 위 검증 쿼리를 읽기 전용으로 돌려 5종을 확인하고, 사용자에게 결과를 보고한다.
