# [API] 트렌드 출처 저장소 폴더 종류의 허용 폴더 검사를 더한다 (api, 조각 B)

## 핵심 요약

- 요구사항: 출처 종류 `repo_folder`(화면 이름 「저장소 폴더」)를 받고, 위치는 코드에 고정한 허용 폴더 목록과 글자 단위로 같을 때만 저장한다. 등록(`POST`)과 수정(`PATCH`) 둘 다 검사한다.
- 구현 계획: 상수 → 검증 → 저장소 → 라우트 → 테스트 순. **선행: 조각 A(마이그레이션 298)가 DB에 적용된 뒤** 시작한다(통합 테스트가 아니라 단위 테스트이므로 코드는 먼저 쓸 수 있지만, 머지·배포는 A 적용 뒤다).
- 관련 파일: 아래 「구현 계획」의 파일 단위 지도.

## 배경 / 문제 정의

- 상위 티켓 20261028_1422의 조각 B다. 위치는 지금 300자 이내 아무 문자열이다. 폴더 종류는 서버가 저장소 파일을 열 수 없으므로(배포본) 문자열 허용 목록으로만 지킨다.
- 허용 폴더 목록에 없는 경로(`docs/tickets/`, `../x/`, `/etc/`, 역슬래시 경로)가 저장되면 루틴이 엉뚱한 폴더를 읽게 될 수 있다. 그래서 등록과 수정에서 모두 막는다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 허용 폴더 목록: `OPS_TREND_SOURCE_FOLDERS = ['docs/operations/trendresearch/'] as const`. 목록에 폴더를 더하는 일은 코드 변경이라 리뷰를 거친다.
- `POST`: `kind`가 `repo_folder`이면 `location`이 비어 있으면 400(기존 「주소·해시태그·검색어를 적어야 해요」 문장을 이 종류에 맞게 풀거나 같은 문장 유지), 목록에 없으면 400이다. 오류 문장은 해요체로 「정해 둔 폴더 중에서 골라 주세요」를 알린다.
- `PATCH`: 본문에 종류가 없으므로 저장소(`updateTrendSource`)가 현재 행의 종류를 읽어 `repo_folder`일 때 새 위치를 허용 목록과 견준다. 목록에 없으면 새 결과 코드 `folder_not_allowed`를 돌려주고, 라우트가 400으로 바꾼다.
- 다른 종류의 위치 검사는 바꾸지 않는다.
- 화면 컴포넌트가 종류별 안내 문구를 `Record<OpsTrendSourceKind, string>`으로 가진다. 종류를 더하면 타입 오류가 나므로, 이 조각에서 `OpsTrendSources.tsx`의 `KIND_PLACEHOLDERS`에 `repo_folder: '목록에서 골라요'` 한 줄만 더해 타입 검사를 통과시킨다(입력 칸을 목록 선택으로 바꾸는 일은 조각 C).

### UI/UX 관점 (해당 시)

- 오류 문장만 해당한다. 해요체의 쉬운 문장으로 쓴다.

## 구현 계획

파일 단위 지도(변경 파일 약 9개, 테스트 포함 약 120~160줄이라 `plan_only` 임계값을 넘는다. **첫 호출부터 `planOnlyWaiver`를 넣는다.**)

1. `jam-web/src/lib/admin/opsTrends/constants.ts`
   - `OPS_TREND_SOURCE_KINDS`(6행)에 `'repo_folder'`를 더한다.
   - `OPS_TREND_SOURCE_KIND_LABELS`(9~14행)에 `repo_folder: '저장소 폴더'`를 더한다.
   - 새 상수 `OPS_TREND_SOURCE_FOLDERS`와 타입을 더한다.
2. `jam-web/src/lib/admin/opsTrends/sources.ts`
   - `validateTrendSourceCreate`(위치 필수 검사 약 100행 근처): `kind === 'repo_folder'`이면 `location`이 `OPS_TREND_SOURCE_FOLDERS`에 있어야 하고, 없으면 `errors`에 `location: ...` 문장을 더한다. 위치가 비어 있을 때의 기존 오류가 이 종류에도 걸리는지 확인한다.
   - 목록 검사 헬퍼 `isTrendSourceFolder(value: string): boolean`을 내보낸다(저장소와 테스트가 쓴다).
   - `validateTrendSourcePatch`(약 110~135행)는 종류를 모르므로 바꾸지 않는다.
3. `jam-web/src/lib/admin/opsTrends/sourceStore.ts`
   - `TrendSourceWriteResult`(48~50행)의 `code` 합집합에 `'folder_not_allowed'`를 더한다.
   - `updateTrendSource`(130행~): 지금은 `patch.location === ''`일 때만 현재 종류를 읽는다. `patch.location !== undefined`이면 읽도록 넓히고, 비움 검사(`manual_upload` 밖이면 `location_required`)는 그대로 둔 채 `repo_folder`이고 새 위치가 목록 밖이면 `folder_not_allowed`를 돌려준다.
4. `jam-web/src/app/api/admin/ops-trend-sources/[id]/route.ts`
   - `PATCH`의 결과 분기(약 55~62행)에 `folder_not_allowed` → `badRequest('출처 형식이 맞지 않아요. details를 보고 고쳐서 다시 보내 주세요.', ['location: ...'])`를 더한다.
5. `jam-web/src/app/api/admin/ops-trend-sources/route.ts`: `POST`는 `validateTrendSourceCreate` 결과를 이미 400으로 바꾸므로 변경 없음(확인만).
6. `jam-web/src/components/admin/ops/trends/OpsTrendSources.tsx`: `KIND_PLACEHOLDERS`(46행)에 한 줄(위 「서비스/코드베이스 관점」 마지막 항목).
7. 테스트:
   - `jam-web/src/lib/admin/opsTrends/__tests__/sources.test.ts`: 등록 검증 케이스 추가(허용 경로 통과, 목록 밖·`..`·절대 경로·역슬래시·빈 위치 거절, 다른 종류는 영향 없음).
   - `jam-web/src/lib/admin/opsTrends/__tests__/sourceStore.test.ts`: `updateTrendSource`가 폴더 종류에서 목록 밖 위치를 `folder_not_allowed`로 막고 허용 위치는 저장함.
   - `jam-web/src/app/api/admin/ops-trend-sources/__tests__/route.test.ts`: `POST` 201·400, `PATCH` 400(`folder_not_allowed`) 케이스.
   - `jam-web/src/components/admin/ops/trends/__tests__/OpsTrendSources.test.tsx`: 종류 목록에 「저장소 폴더」가 있는지 확인하는 기존 단언이 있으면 맞춘다.
8. 문서: `docs/service/prd/admin-boards/PRD.md` §6.4(181행 종류 목록, 185·186행 검증 설명)는 조각 D에서 한꺼번에 고친다. 이 조각은 문서를 바꾸지 않는다.

정책 대시보드(`policiesData.ts`) 동기화: 트렌드 출처는 정책·밸런스 수치가 아니므로 해당 없음(착수 때 한 번 확인한다).

## 완료 조건

### 구현 범위 (게이트 판정 대상)

- `POST`에 `{ name, kind: 'repo_folder', location: 'docs/operations/trendresearch/' }`를 보내면 201이다.
- `POST`의 위치가 비었거나 `docs/tickets/`, `../x/`, `/etc/`, `docs\operations\trendresearch\`이면 400이고 `details`에 위치 오류 문장이 있다.
- `PATCH`로 폴더 출처의 위치를 목록 밖 값으로 바꾸면 400이고, 목록 안 값으로는 200이다. 종류가 다른 출처의 위치 수정은 이전과 같다.
- 같은 이름 중복은 409, 없는 `id`는 404로 이전과 같다.
- 위 케이스가 단위 테스트에 있고 `scripts/verify.sh`(lint·타입·테스트)가 통과한다.

### 후속 범위 (담당: 카리나, 시점: A 적용 뒤 머지)

- 머지 전에 A(마이그레이션 298)가 DB에 적용됐는지 읽기 SQL로 확인한다.
- 머지·push 뒤 staging 배포가 완료됐는지 확인하고, 읽기 토큰 `GET`이 켜진 폴더 출처 행을 돌려주는지는 조각 C 배포 뒤 화면 등록으로 함께 확인한다.
