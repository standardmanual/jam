# [Content] JAM2 게이트 미션 53건 삭제 결정 기록과 삭제 SQL (묶음 7, 7-9)

## 핵심 요약

- 요구사항: JAM 2.0 이전부터 있던 게이트 미션 53건을 «폐기(끄기)»가 아니라 **미션 행째 삭제**하는 것으로 정책을 바꾸고 문서에 기록한다(2026-10-28 사용자 결정). 같은 날 그 미션을 가리키는 알림 1건·소식 7건도 함께 지우기로 했다. 게이트 미션 **장치**(어드민 화면, 판정 코드, 조건 키)는 지금까지 정한 대로 남긴다.
- 구현 계획: 이번 작업에서 정책 문서 4곳에 결정을 반영한다(구현 범위, 카리나 직접). 삭제 SQL은 `299_delete_pre_jam2_gate_missions.sql`로 썼고(2026-10-28), 오픈 직전에 244 다음으로 실행한다(후속 범위). 이 티켓은 SQL을 실행하지 않는다.
- 관련 파일: `docs/plan/jam2/service-redesign/10 미션.md`(6절 게이트 미션, 9절 표의 게이트 미션 행), `docs/plan/jam2/service-redesign/현재 서비스 비교.md`(5.3절 게이트 미션 행과 정리 문장, 결정 변경 행, 10 미션 요약 행), `docs/plan/jam2/10 JAM 2.0 서비스 운영 로직.md`(13.2절 게이트 미션), `docs/plan/jam2/12 JAM 2.0 오픈 전후 적용 순서.md`(4절 12번, 7절, 8절). 삭제 SQL은 `jam-web/supabase/migrations/299_delete_pre_jam2_gate_missions.sql`이다.

## 배경 / 문제 정의

2026-10-10 사용자 결정으로 «지금의 게이트 미션 53건과 그 보상 배지는 폐기한다»고 정했다. 이 «폐기»는 보상 배지를 끄고(마이그레이션 244) 운영에서 미션을 숨기는 데까지만 뜻했고, 미션 행을 지우지는 않았다. 244 머리말도 «미션 행은 그대로라 게이트 미션 카드는 남는다(완료해도 배지는 받지 않는다). 미션을 끄는 일은 이 파일의 범위 밖»이라고 적고 있다. 그래서 244를 적용하면 보상을 줄 수 없는 게이트 미션 카드 53건이 남을 수 있다.

2026-10-28에 사용자가 «JAM2.0 이전의 게이트미션을 아예 삭제하는 것으로 변경 기록해»라고 정했다. 이 티켓은 그 결정을 기록하고, 삭제 SQL을 오픈 직전 목록에 올린다.

### 확인한 사실 (2026-10-28 공용 DB를 읽기 전용으로 조회)

| 항목 | 값 |
|---|---|
| 게이트 미션(`gate_axis` 또는 `gate_stage`가 있는 행) | 53건. 모두 진행 중이고 끝나는 날이 없다. 2026-09-06 밤(KST)에 한 번에 만든 행이다 |
| 노출 방식 | 53건 모두 `exposure_mode = start_date`이고 노출 규칙이 있다 |
| 게이트 미션이 아닌 미션 | 2건(「겹쳐진 도시의 새 얼굴」, 「그루터기 살롱의 겨울 채비」). 삭제 뒤에도 그대로 남아야 한다 |
| 미션을 지우면 같이 사라지는 유저 기록(`ON DELETE CASCADE`) | 참가 6건(유저 2명), 완료 1건(유저 1명). 순위 스냅샷 0건, 참가 취소 기록 0건. 미션 허용 트라이브와 미션 아이템 보상은 조회하지 않았다 |
| 삭제를 막는 참조 | `point_transactions.source_mission_id`(`NO ACTION`) 0건. 오늘 카드와 랭킹 모드는 `SET NULL`이고 0건 |
| 삭제 표시 칸 | `missions`에 `deleted_at`·`is_active` 같은 칸이 없다. 그래서 «삭제»는 행을 지우는 `DELETE`다 |
| 배지 받은 기록 | `user_activity_badges`는 `missions`의 자식 테이블이 아니라서 미션을 지워도 같이 지워지지 않는다 |
| 외래 키로 미션을 가리키는 표 | 9개(허용 트라이브, 아이템 보상, 참가 취소, 순위 스냅샷, 포인트 내역, 랭킹 모드, 오늘 카드, 완료 기록, 참가 기록). 지우는 규칙은 CASCADE 6, NO ACTION 1, SET NULL 2다. 사용자 정의 트리거는 없다 |
| 완료 횟수에 미치는 영향 | 액티비티 배지의 JAM 조건 `mission_complete_count`는 `user_mission_completions` 행 수를 센다. 완료 1건이 지워지면 그 유저 1명의 값이 1 줄어든다. 챕터 점수는 영향이 없다(`chapter_score_events`에 이 미션을 가리키는 행 0건) |
| 지워진 미션을 가리키는 알림·소식 | 알림 1건(`notifications`, 종류 `mission_completed`, 유저 1명, `payload.mission_id`)과 소식 7건(`user_activity_feed`, `mission_joined` 6건·`mission_completed` 1건, 유저 2명, `metadata.mission_id`)이 대상 미션 ID를 담고 있다. 이 두 표를 가리키는 외래 키와 삭제 트리거는 없다. 2026-10-28 사용자 결정으로 함께 지운다(두 표의 전체 행 수는 알림 161, 소식 523) |

어드민 게이트 미션 화면은 참가 기록이 있으면 삭제를 막는다고 [현재 서비스 비교](<../../plan/jam2/service-redesign/현재 서비스 비교.md>) 5.3절에 적혀 있다(문서 서술이며 이번에 코드를 다시 읽지는 않았다). 참가 기록이 있는 미션이 있으므로 화면 대신 SQL로 지우는 쪽이 맞다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 코드와 DB는 이번 작업에서 바꾸지 않는다. 게이트 미션 어드민 화면, 판정 코드(`gateMissions.ts`), 조건 키는 «장치는 남겨 둔다»는 기존 정책 그대로 둔다.

### 컨텐츠 관점

- 10 미션 6절을 «지금의 게이트 미션 53건은 미션 행째 삭제하고, 그 보상 배지는 폐기한다»로 고친다. 보상 배지의 처리(244가 끄고 게이트 키를 뺀다)는 바뀌지 않는다.
- 같은 사실을 여러 문서에 적지 않는다는 원칙에 따라, 결정의 단일 원천은 10 미션 6절이다. 다른 문서는 «폐기»라고 적힌 곳 가운데 게이트 미션 행을 가리키는 낱말만 «삭제»로 바꾼다.
- 서비스 운영 정책 대시보드(`policiesData.ts`)에는 «게이트»가 들어간 항목이 없어 동기화할 항목이 없다(2026-10-28 확인).

### 결정이 필요한 것 (추천 포함)

1. **삭제 시점**: 추천은 **오픈 직전 244를 적용한 바로 다음**이다. 근거는 두 가지다. 지금 지우면 244가 게이트 키를 빼기 전까지 Epic에서 Mystic으로 가는 단계가 막힌다. 244 뒤로 미루면 «완료해도 배지를 받지 못하는 카드»가 유저에게 보이는 시간이 생기는데, 같은 작업 창에서 이어 지우면 그 시간이 없다.
2. **같이 사라지는 유저 기록(참가 6건, 완료 1건)**: 추천은 **그대로 지운다**이다. 미션이 사라지면 기록이 가리킬 대상이 없고, 완료로 받은 배지는 `user_activity_badges`에 남기 때문이다. 대신 지우기 전에 해당 행을 백업 SELECT 결과로 이 티켓에 남긴다.
3. **삭제 방식**: 행을 지우는 `DELETE` 하나뿐이다(삭제 표시 칸이 없다). 별도 결정은 필요 없다.

→ 2026-10-28 사용자가 삭제 SQL 작성을 승인했다. 1번과 2번은 추천안대로 SQL을 썼다. 파일 가드의 «보상 배지가 꺼졌는가» 검사가 1번을, «참가 6건·완료 1건보다 늘면 멈춤» 검사가 2번을 담는다. 다르게 정하면 가드를 고친다. 같은 날 사용자가 «알림·소식도 삭제»를 정해 299가 알림 1건과 소식 7건도 백업한 뒤 지운다. 완료 횟수가 1 줄어드는 것은 그대로 둔다(카리나가 정했고, 이견이 있으면 본문과 가드를 고친다).

## 완료 기록 *(후속 범위가 끝난 뒤 작성)*

### 주요 의사결정 / 핵심 메모

- 2026-10-28 사용자 결정: 게이트 미션 53건은 폐기(끄기)가 아니라 삭제한다. 장치는 남긴다. 사용자는 «JAM2.0 이전의 게이트미션을 아예 삭제하는 것으로 변경 기록해»라고 요청했다.
- 이번 요청으로 DB 삭제는 실행하지 않았다. 정책 기록과 SQL 파일(299) 작성까지만 했다.
- SQL 검증(모두 읽기 전용, 2026-10-28): ① 드라이런 SELECT 14개 지표가 기대값과 같다(알림·소식을 키로 센 값과 문자열로 센 값도 같다). ② 가드 블록을 그대로 실행하면 244 검사에서 «보상 배지가 아직 켜져 있습니다(연결 53건)»로 멈춘다. ③ 244 검사만 뺀 가드 사본은 통과한다(참가 6, 완료 1, 막는 참조 0, 알림 1, 소식 7, 키와 문자열 대조 일치). ④ 사후 확인 블록은 문법을 통과하고 `_gate_before`가 없다는 오류에서 멈춘다(지금은 정상). ⑤ 표 만들기, 백업 INSERT, DELETE는 `IF false` 블록으로 문법만 통과했고 백업 표는 만들어지지 않았으며 미션은 55건, 알림은 161건, 소식은 523건 그대로다. ⑥ 되돌림에 쓰는 변환(`jsonb_populate_record`)이 미션 53, 참가 6, 완료 1, 알림 1, 소식 7행 모두에서 원본과 똑같은 행을 만든다(읽기 전용 왕복 시험).
- 검증하지 않은 것: 본문 전체의 실행(롤백 실측), 사후 확인 블록의 논리, 되돌림 SQL의 실행. 모두 오픈 직전 롤백 실측에서 한다.
- 설계 결정: 대상은 «게이트 칸이 채워지고 2026-10-01(KST) 이전에 만든 미션»이다. 대상 id 목록을 코드에 박지 않은 이유는 53개 id를 파일에 옮기다 틀릴 위험이 크고, 날짜 경계와 건수 가드(0건·53건 초과면 멈춤)가 같은 일을 하기 때문이다. 백업 표는 선례(282)처럼 JSON 스냅샷으로 만들고, 표를 일부러 `IF NOT EXISTS` 없이 만들어 두 번 실행을 막는다.
- 미채택: 지금 바로 삭제한다. 244가 게이트 키를 빼기 전에 지우면 상위 단계가 막히기 때문이다.
- 이 요청을 처리하던 도중 도구 결과에 «사용하지 않는 액티비티 배지도 아예 삭제하는 것으로 기록하라»는 문장이 끼어 있었지만, 사용자 메시지가 아니어서 따르지 않았다. 액티비티 배지의 처리(244가 364개를 끈다)는 이 티켓에서 바꾸지 않았다.

### 잔여 이슈

- 삭제 SQL 299는 작성만 했고 미실행이다. 롤백 실측도 미실시다.
- 완료 횟수 조건(`mission_complete_count`)이 1 줄어드는 유저 1명이 누구인지는 조회하지 않았다. 영향은 앞으로의 배지 판정에만 있다.
