# [Feature] 잼 자동 채움과 포인트 열기 구조 개편 (상위)

> 출처: 사용자와 `/jam-plan` 1단계 문답(2026-10-28), 기획서 초안(혜린)을 카리나가 검토해 저장한다. 화면 근거는 프로토타입 티켓 `20261028_1516`(`/spike/capsule-fill`)이다.
> 사용자가 정리한 구조: **잼(액티비티 활동량과 서비스 활동량)과 포인트가 있다. 잼은 캡슐을 채워서 챕터를 상승시키고, 포인트는 잠긴 보상(문서의 용어는 «잠긴 아이템 배지»)을 연다.**

## 핵심 요약

- 요구사항: 잼이 생기면 자동으로 캡슐을 채우고, 100%에서 열기 없이 보상을 받고, 챕터는 «캡슐 양 × 100% 횟수»로 오르고, 잠긴 아이템 배지는 포인트로 여는 구조로 바꾼다. 바텀시트와 «채우기»·«열기»·«가진 잼»은 없어진다.
- 구현 계획: 하위 티켓 13개를 아래 표의 순서로 진행한다. 수치 시뮬레이터(U1) → DB 확장(U2) → 서버 규칙(U3~U6, U5b) → 퀘스트(U7) → 화면(U8~U10) → DB 축소(U11) → 오픈 전 점검(U12). 화면은 서버 규칙이 들어간 뒤에 반영한다.
- 관련 파일: 운영 로직 `docs/plan/jam2/10 JAM 2.0 서비스 운영 로직.md`(잼 4장, 캡슐 5장, 잠긴 아이템 배지 7장, 챕터 12장, 포인트 14장, 설정 19장), 캡슐 `jam-web/src/components/capsule/`·`lib/capsule/`·`app/api/capsule/`, 잼 정산 `jam-web/src/lib/jam/settlement.ts`, 챕터 `jam-web/src/lib/chapter/`, 퀘스트 `jam-web/src/lib/onboarding-quest/`, 프로토타입 `jam-web/src/app/spike/capsule-fill/`, 정책 대시보드 `jam-web/src/lib/admin/policyDashboard/policiesData.ts`.

## 배경 / 문제 정의

- 지금은 잼을 «채우기»로 옮기고 «열기»를 눌러야 해서 유저가 잼을 어디에 쓸지 매번 고르고 두 번 더 누른다.
- 포인트는 주기만 하고 쓰는 곳이 없다(운영 로직 14장).
- 챕터는 화면에 보이지 않는 점수 12종으로 오른다. 점수 숫자를 보여 주지 않는 규칙이라 무엇을 하면 오르는지 알기 어렵다.
- **실측(2026-10-28, 공용 DB 읽기 전용 집계):** 챕터를 가진 유저 0명, 잼 거래 0건, 캡슐 열기 0건, 캡슐은 테스트용 2개(채움 0%)뿐이다. 유저가 쓰기 전이라 규칙을 바꾸는 비용이 가장 작은 시점이다. 오픈 직전에 같은 집계를 다시 한다(U12).

## 확정한 결정

| # | 결정 |
|---|---|
| D1 | 잼은 동기화한 액티비티 양과 서비스 안 활동 양으로 얻는다. 캡슐은 잼이 채워지는 그래프이고 100%마다 보상을 준다. 챕터는 챕터별 캡슐 양과 100% 횟수가 정해져 있고, 횟수를 채우면 오른다. |
| D2 | 잼이 생기면 자동으로 캡슐에 채워진다. 바텀시트와 «채우기»는 없앤다. 홈피드와 프로필에 접속하면 가장 마지막 잼 양으로 표시한다. |
| D3 | 캡슐이 100%가 되면 «열기» 없이 한 번에 보상(아이템 배지)을 받는다. 개수, 소속, 등급, 잠김 추첨과 확률, 보정 장치는 지금과 같다. 넘친 잼은 다음 캡슐에 채운다. |
| D4 | 잠긴 아이템 배지는 잼이 아니라 **포인트**로 연다. 퀘스트 안에서 나온 **첫 잠긴 배지는 포인트 없이** 연다(A1). |
| D5 | 서비스 안 활동이 주는 잼은 **활동 종류별 고정값 + 하루·주간 상한**으로 정한다(밸런스 설정 한 곳). 드랍과 픽업은 상한이 생기기 전까지 잼을 주지 않고, «캡슐 가득 참»은 잼 대상에서 뺀다. |
| D6 | 포인트는 어드민이 배지·컬렉션·믹스·미션에 지정한 값이 있을 때 지금처럼 따로 받는다. 열 때 내는 포인트와 열린 뒤 받는 포인트는 **두 줄로 따로 기록**한다(A2). |
| D7 | 잼을 조건으로 쓰는 배지와 미션은 **활동 잼과 서비스 활동 잼을 합산**해서 세고, 조건 값을 올린다(A3). |
| D8 | 챕터 점수 12종 장부는 **점수를 잼으로 바꾸고 옛 장부는 쓰기를 멈췄다가 삭제**한다. 기존 호출 지점과 중복 방지 규칙을 재사용한다(A4). |
| D9 | 인벤토리 빈칸이 모자라면 보상은 **보류**한다. 보류가 있는 동안 다음 캡슐이 가득 차면 그 보상도 보류하고(최대 2개) 그 뒤부터 **잼을 받을 수 없으며, 받을 수 없는 동안의 잼은 사라진다.** 챕터 횟수는 100%에 닿는 시점에 센다. 빈칸이 생기면 캡슐 아래 «받기» 한 번으로 받는다. «닫기»는 보류를 그대로 두는 동작이고 보상을 포기하는 버튼은 두지 않는다(A5). |
| D10 | 다음 캡슐이 가득 차기까지 30%, 20%, 10% 남았을 때(채움 70%, 80%, 90% 도달)와 잼을 받을 수 없게 된 순간에 **소식과 캡슐 아래 안내 메시지**로 알린다. 한 번에 건너뛰면 가장 높은 단계 하나만 보낸다. |
| D11 | 한 번의 잼 적립에서 일어난 일은 **연출 한 번**으로 합친다. 챕터가 오르면 챕터 문구, 아니면 «캡슐이 가득 찼어요»를 제목으로 하고 보상을 한 화면에 모아 «보상 보기»·«닫기»를 둔다. 다른 오버레이가 열려 있으면 닫힌 뒤에 보여 준다. |
| D12 | 연출을 못 보고 앱을 떠나면 서버에 **«아직 보지 않은 캡슐 결과»**를 남겨 다음 접속 때 한 번 보여 준다(A6). |

## 성공 기준 (무엇을 어떻게 재면 달성인지)

| 기준 | 재는 방법 | 달성 | 상태 |
|---|---|---|---|
| 장부 일치 | 시험 계정 시나리오 5종(정상, 연속 가득 참, 보류, 소멸, 재시도)에서 «받은 잼 = 캡슐에 채운 양 + 소멸한 양 + 지금 채움»을 원장 조회로 대조 | 불일치 0건 | 구현 뒤 측정 |
| 중복 없음 | 같은 동기화와 같은 서비스 활동을 3번 다시 보낸 뒤 보상 수와 챕터 횟수 확인 | 1회분만 반영 | 구현 뒤 측정 |
| 연출 한 번 | 브라우저 실측(375×812). 채움만, 가득 참, 챕터 오름, 연속 오름과 보류의 4시나리오 | 시나리오마다 연출 1회 | 프로토타입은 오름 연출만 실측 |
| 경제 균형 | 새 시뮬레이터 결과를 운영 로직 19.2절 목표와 대조(캡슐 챕터 1 주 2~3번, 챕터 10 주 1번, 챕터 5까지 3개월쯤, 챕터 10까지 1년쯤, 월 20~30개, 인벤토리 여유) | 기준 유저(러닝 보통)의 전 지표가 목표 안 | **미검증**, 시뮬레이터 없음 |
| 소멸 규모 | 원장의 소멸 줄을 주 단위로 집계(유저 수, 양) | 목표 수치를 만들지 않는다. 오픈 뒤 4주 관찰값으로 정한다 | 기준선 없음 |
| 알림 | 캡슐 하나당 단계(30·20·10%, 받을 수 없게 됨)마다 최대 1회 | 중복 0건 | 구현 뒤 측정 |
| 전환 부담 | 오픈 직전 같은 읽기 전용 집계를 다시 실행 | 0이면 그대로, 0이 아니면 전환 계획을 추가 | 10-28 기준 0 |

## 범위

- 잼 자동 채움, 100% 즉시 보상, 보류와 소멸, 알림 4종, 합친 연출, 포인트로 잠긴 아이템 배지 열기, 챕터를 캡슐 횟수로 올리기.
- 서비스 활동 잼, 잼 조건 배지·미션 합산, 퀘스트 재정의, 밸런스 설정 구역, 정책 대시보드, 문서 갱신, 옛 구조 삭제.

## 하지 않을 것

- 드랍과 픽업이 주는 잼(상한이 생기기 전까지), 미션·프로모션 보상으로 잼 지급, 캡슐 보상 확률과 보정 장치 변경.
- 잼과 포인트의 교환, 캡슐을 빨리 채우는 상품, 챕터 이름 복구.
- 화면 세부 설계(채원의 몫), 우선순위 확정(카리나의 몫).

## 열린 질문

### 답이 없으면 진행하지 못하는 것

- **A7. 수치:** 챕터별 캡슐 양과 횟수, 활동별 잼과 상한, 잠긴 배지 포인트 양, 잼 조건 배지·미션의 상향 기준값. U1(시뮬레이터)이 후보를 내고 사용자가 확정한다. 구조 작업은 막지 않고 **오픈만 막는다.** 입력으로 쓸 현재 값은 캡슐 양 90~220, 잠긴 최소 30/60/120/240(잼 기준), 포인트 수입 목표 월 800~900이다.

## 가정

| 구분 | 내용 |
|---|---|
| 확인됨 | 사용자 결정 D1~D12. 공용 DB 실측 0건(10-28). 캡슐 양, 확률, 보정 장치 값(운영 로직 5.4절). 챕터 오름 카드는 «다음에 앱을 열 때 기기마다 한 번» 규칙(`lib/chapter/celebrate.ts`). 퀘스트 완료는 캡슐 열기와 잠긴 열기 기록을 읽는다(`lib/onboarding-quest/real-steps.ts`). 캡슐 연 횟수와 잠긴 연 횟수는 배지·미션 조건 키로 쓰인다. 포인트는 지금 쓰는 곳이 없고 잔액이 0 아래로 내려가지 않게 막는 제약이 없다(운영 로직 14.5절). 인벤토리가 가득 찬 경우 보상은 사라지지 않고 받지 않은 상태로 기다린다(운영 로직 6.4절). 잼 조건 배지·미션 유형(`jam_week_min_earned`, `jam_week_streak`, `jam_week_count`, `jam_period_earned` 등)이 코드에 있다. |
| 확인됨(문서) | 점수 호출 지점 열두 군데는 데이터 모델 문서 9-3절 표로 확인했고, 코드 대조는 구현 단계에서 한다. |
| 미확인 | 인벤토리 기본 칸 수(어드민 설정값), 대량 활동 한 번에 가득 차는 캡슐 수와 처리 시간, 서비스 활동 잼의 파밍 크기, 포인트 비용이 수입과 맞는지, 일일 잼 집계표(`jam_daily_earned`)를 잼 조건 유형이 읽는지, 채원 판정 결과, 오픈 직전 유저 수 |

## 판단: 만들자

- 이유 1: 유저가 쓰기 전이라 규칙 전환 비용이 가장 작다. 오픈 뒤에는 학습한 규칙을 바꾸는 비용이 커져서 미루는 쪽이 더 비싸다.
- 이유 2: 프로토타입으로 방향은 확인됐고, 포인트에 쓰는 곳이 생긴다.
- 조건: 수치가 모두 미검증이라 U1 결과를 사용자가 확정하기 전에는 오픈하지 않는다. 소멸 규칙은 윈터·채원 톤 확인을 통과해야 한다.
- 단계: 시뮬레이터, 서버 규칙, 화면, 옛 구조 삭제 순서이고, 화면은 서버 규칙이 들어간 뒤에 반영한다.
