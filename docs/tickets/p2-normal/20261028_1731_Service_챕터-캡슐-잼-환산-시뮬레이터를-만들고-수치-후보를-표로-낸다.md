# [Service] 챕터·캡슐·잼 환산 시뮬레이터를 만들고 수치 후보를 표로 낸다

> 상위 티켓 `20261028_1730`의 하위 티켓 U1다. 연결된 결정: D1, D5, D7, A7. 처리 유형(`/jam-work`): engine(시뮬레이터, 단독 호출).

## 핵심 요약

- 요구사항: 챕터·캡슐·잼 환산 시뮬레이터를 만들어 챕터별 캡슐 양과 횟수, 활동별 잼과 상한, 잠긴 아이템 배지 포인트 양의 후보를 퍼소나별 표로 낸다.
- 구현 계획: 컬렉션용 시뮬레이터의 퍼소나·구조를 읽고 같은 방식으로 챕터·캡슐용을 만든다. 운영 로직의 값과 19.2절 목표를 입력으로 쓴다.
- 관련 파일: `scripts/balance-sim/collection-sim.mjs`(참고, 지금 있는 유일한 시뮬레이터), `docs/plan/jam2/service-redesign/19 게이미피케이션 밸런스.md`(목표값), 운영 로직 `docs/plan/jam2/10 JAM 2.0 서비스 운영 로직.md` 4·5·12·14장. 줄 위치는 아현이 첫 호출에서 확인한다.

## 배경 / 문제 정의

- 챕터·캡슐·잼 환산 시뮬레이터가 없어서 새 규칙의 모든 경제 수치가 **미검증**이다.
- 기준 유저 주 잼 333을 전부 캡슐에 쓰면 챕터 1에서 주 3.7회, 챕터 10에서 주 1.5회 가득 차 목표(주 2~3회, 주 1회)를 넘는다는 산술이 있다(시뮬레이션이 아니다).

## 상세 요구사항

### 서비스/코드베이스 관점

- 시뮬레이터는 읽기 전용 계산이고 DB에 쓰지 않는다.
- 출력 표: 챕터 도달 시점, 캡슐이 가득 차는 주당 횟수, 월 아이템 배지 수, 포인트 수입·지출, 인벤토리 보류 비율, 서비스 활동 잼 상한 있음/없음 비교, 잼 조건 배지·미션에 주는 영향.
- 결과 표는 티켓에 기록하고, 다시 쓸 결론은 운영 로직 19장으로 환류한다.

## 구현 계획

컬렉션용 시뮬레이터(`scripts/balance-sim/collection-sim.mjs`)의 구조(머리 주석의 사용법, `mulberry32` 시드 난수, `weighted`, 퍼소나 표, 주 단위 반복, `SIM_JSON` 저장)를 그대로 본떠 새 파일 하나를 만든다. 기존 시뮬레이터는 고치지 않는다.

테스트 파일은 만들지 않는다. 서비스 코드(`jam-web/`)와 DB는 건드리지 않는다.

**모델 (`chapter-capsule-sim.mjs`)**

1. 입력 상수는 파일 위쪽 한 곳에 둔다. 값의 출처를 주석으로 적고, 운영 로직에 없는 값은 `// 추정` 표지를 붙인다.
   - 퍼소나 7종: 게이미피케이션 밸런스 2절 표(걷기 보통 180, 등산 보통 277, 러닝 보통 333, 트레일러닝 보통 456, 러닝 열심 828, 자전거 열심 960, 트레일러닝 열심 1,125). 회당 잼과 주 횟수는 `collection-sim.mjs`의 퍼소나 표와 같은 방식으로 쓴다.
   - 동기화 아이템 배지·캡슐 보상·잠길 확률·등급 확률·보정: 운영 로직 5.4절, 6.7절(`collection-sim.mjs`의 `CAPSULE`, `JAM`과 같은 값).
   - 서비스 활동 잼 표 `SERVICE_JAM`: 종류(잠긴 배지 열기, 배지 받기, 컬렉션 완성, 믹스 성공, 미션 완료)별 고정값, 하루 상한, 주간 상한. 드랍·픽업은 0, 캡슐 가득 참은 표에 넣지 않는다(D5). 종류별 주당 발생 횟수는 퍼소나마다 `// 추정`으로 둔다.
   - 인벤토리 칸 수(기본 10, 공용 DB `inventory_policy.max_slots` 2026-10-28 읽음)와 «주당 비우는 개수»(컬렉션 장착·믹스로 칸이 비는 속도, `// 추정`).
   - 포인트 수입: 운영 로직 14.1절 표에서 아이템 배지 열림 포인트는 시뮬레이션 안에서 계산하고, 나머지(액티비티·체크인 배지, 컬렉션 완성, 믹스, 퀘스트 100)는 퍼소나별 주당 고정값 `// 추정`으로 둔다(보통 유저 월 800~900 기준).
2. **후보안(`SCENARIOS`)**: 챕터 1~10의 캡슐 양 배열, 챕터별 100% 횟수 배열, 등급별 잠긴 배지 포인트 양, 서비스 활동 잼 표를 묶은 안을 여러 개 둔다. 최소 «현행 양(90~220)», «목표 역산안», «역산안 + 상한 없음» 세 개. 실행 인자로 안 id를 골라 돌린다.
3. **역산 보조 함수**: 기준 유저(러닝 보통)의 주당 잼(활동 + 서비스)과 목표(챕터 1 주 2~3번, 챕터 10 주 1번, 챕터 5 약 3개월, 챕터 10 약 12개월)에서 챕터별 캡슐 양과 횟수 후보를 계산해 출력한다. 출력은 후보일 뿐이며 시뮬레이션 결과(«실측»)와 구분해 표시한다.
4. **주 단위 반복(퍼소나 × 안 × 반복 N회, 기본 400, 최대 24개월)**: 잼이 생기면 전부 캡슐에 자동으로 채운다(D2). 100%가 되면 바로 보상을 받고 넘친 잼은 다음 캡슐로 간다(D3). 횟수가 챕터 기준에 닿으면 챕터가 오르고 다음 캡슐부터 새 양을 쓴다. 잠긴 아이템 배지는 포인트가 모이면 먼저 받은 것부터 연다(D4, 퀘스트의 첫 잠긴 배지는 0포인트). 인벤토리 빈칸이 모자라면 보상을 보류하고(최대 2개), 둘째 보류 뒤 잼은 소멸로 센다(D9).
5. **출력 표(티켓 완료 조건 순서)**: 퍼소나 × 안마다 ① 챕터 2·5·10 도달 시점(중앙값과 25~75%), ② 챕터 1·5·10에서 캡슐이 가득 차는 주당 횟수, ③ 월 아이템 배지 수(동기화·캡슐 나눠서), ④ 포인트 월 수입·잠긴 배지 열기 지출·남은 잔액, 열지 못하고 쌓인 잠긴 배지 수, ⑤ 인벤토리 보류가 있었던 주 비율과 잼 소멸량, ⑥ 서비스 활동 잼 상한 있음/없음 비교(같은 시드로 짝 비교), ⑦ 잼 조건 배지·미션 영향(한 주 합산 잼 분포와 원고 기준값 200·330·830·1,200, 누적 1,000~100,000 도달 시점, 그리고 활동만 셀 때와 같은 난이도가 되는 상향 기준값 후보). 마지막에 19.2절 목표와의 대조 줄(목표 안/밖)을 붙인다.
6. 콘솔 표와 `SIM_JSON` 저장을 둘 다 지원한다. 머리 주석에 사용법(`node scripts/balance-sim/chapter-capsule-sim.mjs [반복 횟수] [안 id 쉼표 목록]`)과 한계(추정 입력 목록)를 적는다.
