# [Infra] DB 확장: 챕터 횟수·서비스 활동 잼표·보류·소멸·포인트 차감의 새 구조만 덧붙인다

> 상위 티켓 `20261028_1730`의 하위 티켓 U2다. 연결된 결정: D4, D5, D6, D9, D12. 처리 유형(`/jam-work`): db(단독 호출, SQL 파일까지).

## 핵심 요약

- 요구사항: 새 구조만 덧붙이는 확장 SQL을 만든다. 유저 눈에는 변화가 없고, 옛 함수와 화면은 그대로 동작한다.
- 구현 계획: 챕터별 횟수 칸, 서비스 활동 잼표(종류별 잼·하루·주간 상한), 잠긴 아이템 배지 포인트 비용, 보류 보상 표(최대 2), «아직 보지 않은 캡슐 결과» 표시, 잼 원장 사유 추가(서비스 활동 잼·소멸), 포인트 원장 사유 추가(잠긴 열기 차감)와 잔액 0 미만 방지 제약을 한 묶음의 확장으로 쓴다. 생성 타입을 재생성한다.
- 관련 파일: `jam-web/supabase/migrations/234_capsule_concurrency_fix.sql`(옛 `capsule_fill`·`capsule_open`, 건드리지 않는다), `220_jam_ledger.sql`(`jam_transactions.reason` CHECK), `221_chapters.sql`(챕터 표), 포인트 원장 마이그레이션(아현이 첫 호출에서 위치 확인), `jam-web/src/types/database.generated.ts`. 줄 위치는 아현이 첫 호출에서 확인한다.

## 배경 / 문제 정의

- DB는 staging과 프로덕션이 공용이라 SQL 실행이 즉시 프로덕션에 반영된다. 프로덕션 main이 옛 함수를 아직 쓰는 동안 옛 함수를 지우면 깨진다.
- 챕터·잼 거래·캡슐 열기가 모두 0건이라 백필이 필요 없다(2026-10-28 실측). 오픈 직전에 다시 확인한다(U12).

## 상세 요구사항

### 서비스/코드베이스 관점

- 확장은 옛 함수의 시그니처를 그대로 둔다. 되돌림 SQL을 같은 묶음에 둔다.
- 포인트 잔액이 0 아래로 내려가지 않게 막는 제약을 이 묶음에 넣는다(운영 로직 14.5절의 알려진 문제).
- SQL 파일은 `jam-web/supabase/migrations/`에 남기고, 실행은 메인 세션이 읽기 전용 확인과 사용자 보고까지 한다(CLAUDE.md 규칙 6, `db-migration-rules.md`).

## 구현 계획

**카리나 사전 조사(2026-10-28, 공용 DB 읽기 전용).** 캡슐 필요량은 `capsule_chapter_costs(chapter_no, fill_amount)`에서 읽고(`capsule_next_required`, 234), 잠긴 배지 최소값은 `jam_policy.locked_min_*`, 잼 원장 사유는 `jam_transactions`의 CHECK 셋(`reason_check`, `sign_by_reason`, `source_by_reason`, 220), 포인트 원장 사유는 `point_transactions_reason_check`다. 유저 캡슐 2행(테스트), 챕터 0, 잼 거래 0, 음수 포인트 지갑 0. 다음 번호는 300이다(원격 브랜치 선점 없음, push 직전 다시 확인).

**확장 내용 (모두 덧붙이기. 옛 함수·옛 열·옛 값은 건드리지 않는다)**

1. `capsule_chapter_costs`에 `advance_count INTEGER NULL CHECK (advance_count >= 1)`를 더하고 U1 확정값(챕터 1~9: 6, 7, 7, 8, 9, 9, 10, 11, 12, 챕터 10은 NULL)을 넣는다. 새 열 `fill_amount_v2 INTEGER NULL`에 U1 확정 양(145~365)을 넣는다. 옛 `fill_amount`(90~220)는 지금 staging의 수동 채우기가 계속 읽으므로 바꾸지 않는다. U3가 새 함수에서 `fill_amount_v2`를 읽고, U11에서 정리한다.
2. `user_chapters`에 `capsule_full_count INTEGER NOT NULL DEFAULT 0 CHECK (>= 0)`(지금 챕터에서 100%에 닿은 횟수)를 더한다.
3. `jam_policy`에 `service_jam_daily_cap INTEGER NOT NULL DEFAULT 40`, `service_jam_weekly_cap INTEGER NOT NULL DEFAULT 100`, `locked_points_common/rare/epic/mystic INTEGER NOT NULL DEFAULT 50/100/200/400`(모두 `>= 0`)을 더한다.
4. 새 표 `service_jam_rules(kind TEXT PK CHECK (kind IN ('locked_unlock','badge_earned','combine_success','mission_complete','collection_complete','drop','pickup')), amount INTEGER NOT NULL CHECK (amount >= 0), updated_at)`. 값: 5, 5, 5, 20, 30, 0, 0. 캡슐 가득 참은 종류에 넣지 않는다(D5).
5. 새 표 `jam_service_daily(user_id, kst_date DATE, amount INTEGER CHECK (>= 0), PK(user_id, kst_date))`. 하루·주간 상한 집계용이다(주간은 이 표의 월~일 합).
6. `jam_transactions`: 열 `source_event_key TEXT NULL`과 부분 유일 인덱스 `(user_id, source_event_key) WHERE source_event_key IS NOT NULL`(같은 서비스 활동을 다시 보내도 한 번만). 사유에 `service_activity`(+, `source_event_key` 필수)와 `capsule_forfeit`(−, 받을 수 없는 동안 사라진 잼)를 더한다. CHECK 셋은 지금 정의의 **상위집합**으로 바꾼다(옛 사유의 조건은 글자 그대로 유지).
7. 새 표 `capsule_pending_rewards(id, user_id, slot SMALLINT CHECK (slot IN (1,2)), chapter_no, fill_amount, reached_at, UNIQUE(user_id, slot))`. 보류는 최대 2개(D9). 보상은 받을 때 추첨하므로 아이템 칸은 두지 않는다(운영 로직 5.2절 «빈칸을 만든 뒤 열면 그때 공개 중인 것»).
8. 새 표 `capsule_unseen_results(id, user_id, payload JSONB, created_at, seen_at NULL)`와 `(user_id) WHERE seen_at IS NULL` 인덱스(D12).
9. `inventory_items`에 `unlock_points_required INTEGER NULL CHECK (>= 0)`(배정할 때 고정, 운영 로직 7.2절).
10. `point_transactions`: 열 `source_inventory_item_id UUID NULL REFERENCES inventory_items(id) ON DELETE SET NULL`, 사유 `locked_unlock_cost`(−) 추가, 부분 유일 인덱스 `(source_inventory_item_id) WHERE reason = 'locked_unlock_cost'`(한 개체에 한 번만 차감). 사유 CHECK는 상위집합으로 바꾼다.
11. 새 표는 모두 RLS만 켜고 클라이언트 정책은 두지 않는다(232와 같다. service_role만 읽고 쓴다). 표마다 `COMMENT`.

**이 묶음에서 빼는 것**

- 포인트 잔액 0 미만 방지 제약: 이미 `266_post_release_point_wallets_balance_check.sql`로 작성돼 있고 «출시 뒤 실행»으로 묶여 있다(옛 프로덕션 코드의 음수 회수가 실패하기 때문). 같은 제약을 지금 실행하면 같은 문제가 생긴다. 그래서 U2는 제약을 넣지 않고, 차감은 U6의 새 함수가 잔액을 잠그고 확인해서 거절한다. 거절 시험은 U6 완료 조건으로 옮긴다.
- 서버 함수(자동 채움, 보류 받기, 포인트 열기, 서비스 잼 적립): U3~U6.
- 알림 단계 기록과 소식 종류: U4.

## 주요 의사결정

- 2026-10-28 카리나 규모 사전 판정: 파일 3개, 생성 타입을 포함해 300줄 이상 예상으로 `plan_only` 기준을 넘는다. DB 확장은 단독 배포 단위여야 하는 예외(상위 티켓 «하위 티켓» 표 아래)라 쪼개지 않고, 위 파일 단위 계획을 사용자가 검토한 뒤 면제로 간다.
- 2026-10-28 포인트 잔액 제약은 266과 겹치므로 이 묶음에서 빼고, 거절 시험은 U6으로 옮긴다(사용자 확인 대상).
