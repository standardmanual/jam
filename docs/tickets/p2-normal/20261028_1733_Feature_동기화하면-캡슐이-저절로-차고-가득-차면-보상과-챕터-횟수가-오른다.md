# [Feature] 동기화하면 캡슐이 저절로 차고 가득 차면 보상과 챕터 횟수가 오른다

> 상위 티켓 `20261028_1730`의 하위 티켓 U3다. 연결된 결정: D1, D2, D3, A6(서버 표시). 처리 유형(`/jam-work`): engine·api(단독 호출).

## 핵심 요약

- 요구사항: 동기화 정산 안에서 «잼 적립 → 캡슐 채움 → 가득 차면 보상 추첨과 지급 → 챕터 횟수 판정»을 한 번에 처리한다. 넘친 잼은 다음 캡슐에 채우고, 한 번에 여러 번 가득 찰 수 있다.
- 구현 계획: 정산 직후에 자동 채움 단계를 붙이고 `capsule_fill`·`capsule_open`의 규칙을 서버 한 곳에서 부른다. 챕터는 100%에 닿을 때마다 횟수를 세고 횟수를 채우면 오른다(`processChapterRise` 연결). 밸런스 설정의 캡슐 구역에 챕터별 횟수 칸을 더한다(기존 티켓 `20261022_1718` 흡수).
- 관련 파일: `jam-web/src/lib/jam/settlement.ts` `settleActivities`, `jam-web/src/lib/capsule/open.ts` `openCapsule`, `jam-web/src/lib/capsule/capsule-flow.ts` `runFill`·`runOpen`, `jam-web/src/lib/chapter/`(오름 처리), `jam-web/src/app/api/capsule/`, `jam-web/src/components/admin/balance/CapsuleSection.tsx`, `jam-web/src/lib/admin/policyDashboard/policiesData.ts`. 줄 위치는 아현이 첫 호출에서 확인한다.

## 배경 / 문제 정의

- 지금은 유저가 «채우기»와 «열기»를 눌러야 캡슐이 진행되고 챕터는 보이지 않는 점수로 오른다.
- 동시성 사고 이력이 있다(마이그레이션 234). 적립과 보상 사이의 실패는 가득 찬 캡슐이 남는 문제를 만든다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 같은 동기화를 3번 다시 보내도 1회분만 반영된다(중복 방지 키).
- 중간 실패(잼은 들어갔는데 보상 지급이 끊김)는 «대기» 상태로 두고 다음 접속에 이어 처리한다. 기존 티켓 `20261017_1713`(잼 정산 실패 확인과 재정산)과 함께 설계한다.
- 미션 즉시 판정(`20261019_1740`)의 판정 시점이 캡슐 열기 위치 이동으로 바뀌는지 확인한다.
- 서버는 «아직 보지 않은 캡슐 결과»를 남기고 이벤트 순서를 화면(U9)에 그대로 준다.
- 퀘스트 전 첫 캡슐(양 5)은 챕터 1 횟수에 넣지 않는다(B5).

## 구현 계획

정산 직후에 자동 채움 단계를 붙이고 `capsule_fill`·`capsule_open`의 규칙을 서버 한 곳에서 부른다. 챕터는 100%에 닿을 때마다 횟수를 세고 횟수를 채우면 오른다(`processChapterRise` 연결). 밸런스 설정의 캡슐 구역에 챕터별 횟수 칸을 더한다(기존 티켓 `20261022_1718` 흡수).

### 규모 사전 판정 (2026-10-29)

파일 12개·900줄 안팎(SQL 약 250줄, 서버 코어, 정산·동기화 연결, 생성 타입, 밸런스 화면, 정책 대시보드, 문서, 시험 포함)이라 `plan_only` 기준을 크게 넘는다. 사용자 승인(2026-10-29)으로 **4회차로 나눠** 회차마다 워크플로를 돌리고 민지 게이트를 거친다. 티켓은 하나로 유지한다. 각 회차는 이전 회차를 머지한 `origin/staging`에서 분기한다.

### 동작 설계 (모든 회차의 기준)

- **대기 상태 = 가득 찬 캡슐.** 자동 채움은 한 번에 캡슐 하나씩만 채운다. 가득 찼는데 열지 못한 캡슐(지급 실패, 트라이브 없음, 인벤토리 빈칸 모자람)은 `user_capsules.filled >= required`로 남고, 다음 동기화의 맨 앞에서 가장 먼저 연다. 별도 대기표를 만들지 않는다. 잼은 사라지지 않는다.
- **반복 구조.** 동기화 정산 뒤 «가득 찬 캡슐이 있으면 열기 → 지갑 잼으로 채우기 → 가득 차면 열기»를 지갑이 비거나 열 수 없을 때까지 되풀이한다. 한 동기화당 최대 50회로 막고, 남은 잼은 지갑에 남아 다음 동기화가 이어서 쓴다.
- **중복 방지.** 정산은 `jam_apply`의 활동 단위 유일성이 지킨다. 자동 채움은 지갑 잔액만 쓰므로 같은 동기화를 다시 보내면 잔액이 0이라 아무 일도 없다. 원장 등식은 `받은 잼(+) = 캡슐에 채운 양(−, capsule_fill) + 지금 지갑`이다(소멸은 U4).
- **챕터 횟수.** 열기와 같은 트랜잭션에서 `user_chapters.capsule_full_count`를 1 올리고, 지금 챕터의 `advance_count`에 닿으면 다음 챕터로 올려 횟수를 0으로 돌린다(`chapter_ups`에 한 줄). `advance_count`가 NULL(챕터 10)이면 멈춘다(B4). 챕터가 아직 없는 퀘스트 전 첫 캡슐은 세지 않는다(B5). U3에서는 100%에 닿는 시점이 열기 시점과 같다(U4가 보류를 더하며 «닿는 시점»으로 옮긴다).
- **새 캡슐 양.** 새 함수는 `capsule_chapter_costs.fill_amount_v2`(145~365)를 읽고 옛 열 `fill_amount`와 옛 함수 `capsule_next_required`·`capsule_fill`·`capsule_open`은 건드리지 않는다(프로덕션 main이 옛 함수를 쓴다). 열린 직후 다음 캡슐의 필요량은 새 함수가 v2로 덮어쓴다.
- **옛 점수 장부.** U3에서는 «모은 잼»(`lib/jam/settlement.ts`)과 «캡슐 열기»(`lib/capsule/open.ts`) 두 곳의 점수 쓰기만 멈춘다. 나머지 다섯 곳은 U5가 잼 지급으로 바꾼다. 그 사이 점수로 챕터가 오를 수 있으나 유저가 0명이다.
- **아직 보지 않은 캡슐 결과.** 동기화에서 자동으로 열린 결과(이벤트 순서대로의 개체·챕터 오름)를 `capsule_unseen_results`에 한 건 남긴다. 화면에 내려주는 응답과 «봤어요» 처리는 U8·U9의 몫이다.
- **미션 즉시 판정.** 자동 열기가 하나라도 있었으면 동기화 안에서 `jamTriggersForCapsuleOpen()`(`capsule_open_count`, `other_tribe_item_kinds_count`)을 다시 판정한다. 열기 위치가 사용자 행동에서 동기화로 옮겨가는 것 외에 판정 키는 바뀌지 않는다.

### 2회차 (서버 코어, 2026-10-29)

- **분기 방식**: 워크플로가 `origin/staging`에서 분기하는데 1회차 병합분이 로컬에만 있어, 로컬 staging 끝(`29e082854`)에서 `claude/jamwork-20261028_1733-run2`를 만들어 원격에 올리고 `retryBranch`로 이어받게 했다. 리뷰 브랜치라 배포는 돌지 않는다. 민지의 검토 범위는 `29e082854..60e325476`(2회차 변경분만)이다.
- **면제 사유**: 변경이 100줄을 넘을 것으로 보여 `planOnlyWaiver`를 첫 호출부터 넘겼다. 사용자가 4회차 분할을 승인했고 티켓 「회차별 파일 계획」이 파일·함수 단위로 적혀 있다는 두 조건이다.
- 커밋 `60e325476`, 민지 게이트 PASS(12항목 중 해당 항목 전부 통과), CI `verify` 성공, 채원② 생략(`api` 유형). 머지 전 오염 검사를 통과해 로컬 staging에 병합했다(병합 커밋 `b98b2ee05`, push 전).
- 파일 4개, +497/-6: `jam-web/src/lib/capsule/auto-fill.ts`(신규 145줄), `jam-web/src/lib/capsule/open.ts`(+65/-6), `jam-web/src/lib/capsule/__tests__/auto-fill.test.ts`(신규 193줄, 11건), `jam-web/src/lib/capsule/__tests__/open.test.ts`(+94, counted 7건).
- **동작**: `runCapsuleAutoFill`은 한 라운드에 `capsule_auto_fill` RPC를 부르고 가득 찼으면 `openCapsule({counted:true})`로 연다. 최대 50라운드이고 멈춤 사유는 `wallet_empty`·`blocked`(열 수 없음, 오류 아님)·`suspended`·`max_rounds`·`error` 다섯 가지다. 던지지 않는 쪽(`runCapsuleAutoFill`)은 실패해도 그때까지의 `opens`·`filledAmount`를 담고, 던지는 쪽(`runCapsuleAutoFillOrThrow`)은 `error`일 때만 던진다. `counted`를 켜면 RPC가 `capsule_open_counted`로 바뀌고 `awardChapterScore('capsule_open')`을 건너뛰며, 열기 확정 직후(퀘스트 완료 처리보다 앞)에 `processChapterRise`를 잇는다. 옵션이 없으면 응답 모양까지 옛 경로와 같다(오버로드).
- **3회차에 넘기는 일**: ① 동기화 안에서 부를 때 `processChapterRise`가 동기화 끝 배지 판정과 겹칠 수 있다. 발급은 UNIQUE로 한 번뿐이지만 결과 카드보다 결산 소식이 먼저 나갈 수 있어, `skipRiseBadgeEvaluation` 옵션이 필요한지 3회차에서 확인한다. ② 던지는 쪽은 예외 시 진행분을 응답에 못 싣는다(DB에는 남음). 동기화는 던지지 않는 쪽을 쓴다. ③ `opens`는 열린 순서이며 `capsule_unseen_results` 기록의 재료다.
