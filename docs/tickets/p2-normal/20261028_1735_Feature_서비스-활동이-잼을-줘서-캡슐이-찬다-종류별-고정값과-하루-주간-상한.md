# [Feature] 서비스 활동이 잼을 줘서 캡슐이 찬다: 종류별 고정값과 하루·주간 상한

> 상위 티켓 `20261028_1730`의 하위 티켓 U5다. 연결된 결정: D5, D8. 처리 유형(`/jam-work`): engine(단독 호출).

## 핵심 요약

- 요구사항: 챕터 점수를 쌓던 호출 지점에서 점수 대신 잼을 준다. 활동 종류별 고정값과 하루·주간 상한을 밸런스 설정 한 곳에서 정한다. 옛 점수 장부는 쓰기를 멈춘다.
- 구현 계획: 기존 호출 지점과 중복 방지 키를 재사용해 `awardChapterScore`를 잼 지급으로 바꾼다. 대상은 배지 받기, 잠긴 아이템 배지 열기, 컬렉션 완성, 믹스 성공, 미션 완료다. 드랍과 픽업은 0이고 «캡슐 가득 참»은 제외한다.
- 관련 파일: `jam-web/src/lib/chapter/score.ts` `awardChapterScore`, `jam-web/src/lib/chapter/kinds.ts`(활동 12종), `jam-web/src/lib/chapter/source-id.ts`, `jam-web/src/lib/chapter/collection.ts`·`mix.ts`, `jam-web/src/lib/missions/checker.ts`, `jam-web/src/lib/itembook/checker.ts`, `jam-web/src/lib/inventory/lockedItemFill.ts`, `jam-web/src/lib/chapter/__tests__/score-wiring.test.ts`(호출 지점 고정 시험). 줄 위치는 아현이 첫 호출에서 확인한다.

## 배경 / 문제 정의

- 지금 점수표를 그대로 잼으로 바꾸면 미션 1번은 러닝 약 17분, 컬렉션 Mystic 완성은 러닝 약 4시간 반치 잼이다.
- 드랍→내가 줍기→다시 드랍을 반복하면 점수가 끝없이 쌓이는 알려진 틈이 있다(운영 로직 12.2절). 잼이 되면 이것이 아이템 배지를 얻는 길이 된다.

## 상세 요구사항

### 서비스/코드베이스 관점

- «잼 지급은 움직인 양에만 한다»는 지금 원칙(운영 로직 4.5절)에서 서비스 활동 잼을 별도 종류로 원장에 구분해 남긴다.
- 캡슐 가득 참이 잼을 낳는 순환을 막기 위해 «캡슐 가득 참»은 잼 대상에서 뺀다.
- 이용 정지 중에는 서비스 활동이 막혀 잼도 생기지 않는다.
- 옛 점수 장부는 쓰기를 멈추고, 삭제는 U11에서 한다. `20261020_1010`(점수 연결 실패 재전송)은 이 티켓으로 요구를 옮기고 중단 후보로 둔다.

### UI/UX 관점

- 어드민 밸런스 설정에 «서비스 활동 잼» 구역을 둔다(종류별 잼, 하루·주간 상한).

## 구현 계획

기존 호출 지점과 중복 방지 키를 재사용해 `awardChapterScore`를 잼 지급으로 바꾼다. 대상은 배지 받기, 잠긴 아이템 배지 열기, 컬렉션 완성, 믹스 성공, 미션 완료다. 드랍과 픽업은 0이고 «캡슐 가득 참»은 제외한다.

### 규모 사전 판정 (2026-10-29)

파일 25개 안팎(호출 지점 8곳, 새 DB 함수, 밸런스 구역 3~4파일, 시험 10개 안팎, 문서·정책 카드)이라 `plan_only` 기준을 크게 넘는다. U3·U4와 같은 방식으로 **4회차로 나눠** 회차마다 워크플로를 돌리고 민지 게이트를 거친다. 티켓은 하나로 유지하고 각 회차는 이전 회차를 병합한 로컬 staging 끝 커밋에서 `claude/jamwork-20261028_1735-runN`을 만들어 이어받는다(원격 staging push는 티켓 끝에 한 번). 현재 코드와 문서의 사실은 2026-10-29 조사(읽기 전용)로 확인했다.

### 현재 사실 (조사 결과)

- `awardChapterScore`(`lib/chapter/score.ts:104`)가 `chapter_add_score` RPC로 점수를 쌓는다. 중복 방지는 DB의 `chapter_score_events UNIQUE(activity_kind, source_id)`(원천 id는 UUID)다. 던지지 않고 실패는 `console.error`와 `engine_decision_log`(`chapter_score_failed`)에만 남으며 자동 재전송은 없다.
- 아직 점수를 쌓는 호출 지점: `locked_item_badge_open`(`inventory/lockedItemFill.ts:227`), `badge_receive`(`chapter/badgeReceive.ts:153`, 발급 지점 6곳이 이 공용 함수를 부름), `collection_complete_*`(`chapter/collection.ts:94`, 장착 라우트와 동기화 보정 두 경로), `mix_success`(`chapter/mix.ts:51`와 등급 올리기 `combine/tierUp.ts:282`, 후자는 매번 새 UUID), `mission_complete`(`missions/checker.ts:287`), `drop`(`api/drops/route.ts:420`), `pickup`(`api/drops/[dropId]/pickup/route.ts:235`, 자기 픽업 제외). `jam_earned`(`jam/settlement.ts`)와 `capsule_open` counted 경로는 U3에서 멈췄다. `capsule_open` 옛 경로(`counted` 아님)는 `/api/capsule/open` 라우트가 아직 쓴다.
- 원장 쪽은 U2에서 준비됐다: `jam_transactions.source_event_key`(유저별 유일 인덱스), 사유 `service_activity`(양수, 키 필수), `jam_service_daily`(KST 날짜별 합), `service_jam_rules`(7종 kind: `locked_unlock`·`badge_earned`·`combine_success`·`mission_complete`·`collection_complete`·`drop`·`pickup`, 시드 5·5·5·20·30·0·0), `jam_policy.service_jam_daily_cap`(40)·`service_jam_weekly_cap`(100). **읽고 쓰는 코드와 함수는 아직 없다.**
- **옛 `jam_apply`는 `service_activity`를 허용하지 않는다**(사유 5개를 하드코딩, `source_event_key` 인자 없음). U4의 소멸과 같은 사정이라 새 DB 함수가 필요하다. 프로덕션 main이 `jam_apply`를 쓰므로 시그니처는 바꾸지 않는다.
- `service_jam_rules`의 kind 이름은 `ChapterScoreKind`와 다르고 컬렉션 4등급을 `collection_complete` 하나로 모은다. 호출 지점에서 매핑이 필요하다. 원천 id는 UUID(챕터) → TEXT(`source_event_key`, 유저별 유일)로 바뀌므로 키에 kind를 넣는다.
- 어드민 밸런스 구역은 `lib/admin/balance/sections.tsx`의 `BALANCE_SECTIONS` 레지스트리에 등록하고, 이력(`balance_setting_changes`)은 새 구역에 마이그레이션이 필요 없다. 선례는 `chapter.ts`(표 둘을 행 단위로 갱신)와 `jam.ts`(`jam_policy` 한 행)다.
- `score-wiring.test.ts`는 소스 검색으로 호출 지점과 kind 리터럴을 고정한다(헤더가 «나머지 다섯 곳은 U5 전까지 그대로»). 같은 호출 지점을 mock으로 아는 시험이 10개 안팎 더 있다.
- 정책 대시보드에는 점수 카드가 `ch7-locked-open-score`·`ch12-score-thresholds`·`ch12-jam-weekly-cap` 셋뿐이고 «서비스 활동 잼» 카드는 없다. 운영 로직 4.5절 447줄 «미션 보상으로는 잼을 주지 않는다»와 새 구조(미션 **완료** 20잼)는 구분해 적어야 한다(미션 **보상**으로서의 잼 지급 금지는 유지, 상위 티켓 108줄).
- 드랍→줍기 반복 파밍을 직접 돌리는 도구는 없다. 가짜 DB(`score-wiring.test.ts`)와 읽기 전용 시뮬레이터(`scripts/balance-sim/`)만 있다.

### 동작 설계 (모든 회차의 기준)

- **서비스 활동 잼 지급 DB 함수** `jam_apply_service_activity(p_user_id, p_kind, p_event_key)`(새 함수, service_role 전용, 한 트랜잭션): 정지 확인 → `service_jam_rules`에서 값을 읽고 0이면 아무것도 쓰지 않음 → 같은 `(user_id, source_event_key)`가 이미 있으면 새로 쓰지 않고 기존 양을 돌려줌 → 오늘(KST)과 이번 주(월~일 KST)의 이미 받은 양을 `jam_service_daily`로 읽어 `LEAST(값, 하루 상한 남은 양, 주간 상한 남은 양)`만큼만 지급(상한에 걸리면 남은 만큼 일부 지급, 0이면 줄을 만들지 않음) → 원장 `service_activity` 한 줄 + 지갑 증가 + `jam_service_daily` 가산. 지갑의 «모은 양»(`total_earned`)은 바꾸지 않는다(활동 잼과 서비스 활동 잼을 합산할지는 U5b가 정한다). 이 함수 자체는 캡슐을 채우지 않는다. **캡슐은 지급 직후 서버가 바로 채운다**(아래 «지급 즉시 채움»).
- **지급 즉시 채움 (사용자 결정 2026-10-29: «지갑의 개념이 없고 발생한 잼은 바로바로 캡슐을 채운다»)**: 서비스 활동 잼도 활동 잼과 같이 지급되는 순간 캡슐을 채운다. 지갑 잔액은 사용자에게 보이는 개념이 아니라 서버 안의 임시 보관일 뿐이므로, 지급이 0보다 크면 `awardServiceJam`이 곧바로 U3·U4의 자동 채움(`runSyncCapsuleAutoFill`: 채움 → 100%에 닿으면 열기 또는 보류 → 보류 2개면 소멸 → 단계 알림 → «아직 보지 않은 캡슐 결과» 기록)을 이어서 돈다. 열린 캡슐이 있거나 챕터가 올랐으면 응답 뒤에 JAM! 행동 지표(캡슐 연 횟수·다른 트라이브 종류 수·챕터 도달)를 판정한다. 자동 채움은 던지지 않으므로 지급 응답은 바뀌지 않는다. 캡슐이 채워져 보상(열린 개체, 챕터 오름)이 생기면 그 결과를 서버가 기록해 두고, 보상을 알려 주는 흐름(U8 화면, U9 연출)이 그 기록을 보여 준다. 잼이 생기는 대로 캡슐을 채우므로 기록도 보상이 생긴 때마다 쌓이고, 화면은 쌓인 순서대로 알린다(사용자 결정 2026-10-29).
- **보상으로 생긴 잼도 같은 규칙으로 채운다 (재진입 방지)**: 캡슐 보상으로 받은 아이템 배지가 컬렉션·미션을 완성해 다시 서비스 활동 잼을 주면, 그 잼도 곧바로 캡슐을 채운다. 이때 자동 채움 안에서 자동 채움이 또 불린다. 같은 서버 프로세스에서 한 유저의 자동 채움이 이미 돌고 있으면 안쪽 호출은 건너뛰고(바깥 루프가 라운드마다 지갑 잔액을 다시 읽어 새로 들어온 잼을 이어서 채운다), DB 쪽은 캡슐 행 잠금이 직렬화한다.
- **호출 지점**: 위 8곳에서 `awardChapterScore`를 `awardServiceJam`(서버 래퍼, 던지지 않음, 실패는 기록만, 지급 뒤 즉시 채움 포함)으로 바꾼다. kind 매핑: `locked_item_badge_open`→`locked_unlock`, `badge_receive`→`badge_earned`, `mix_success`(등급 올리기 포함)→`combine_success`, `mission_complete`→`mission_complete`, `collection_complete_*`→`collection_complete`, `drop`→`drop`, `pickup`→`pickup`. 이벤트 키는 `<kind>:<기존 원천 id>`로 기존 중복 방지 규칙을 그대로 쓴다. «캡슐 가득 참»은 종류에 없다.
- **드랍·픽업**: 호출은 남기고 값은 설정에서 정한다(기본 0이라 지금은 잼이 없다). 값을 올려도 하루·주간 상한이 막는다. 반복 파밍 틈(드랍→줍기→다시 드랍)은 값 0으로 닫히고 값을 올리면 상한이 한계가 된다.
- **옛 점수 장부는 쓰기를 멈춘다**: 위 8곳과 `/api/capsule/open` 수동 열기 경로(옛 `awardChapterScore('capsule_open')`)에서 점수 쓰기를 끊는다. `chapter_add_score` 함수와 표는 프로덕션 main이 쓰므로 건드리지 않고 삭제는 U11이다. 챕터는 U3의 횟수로 오른다.
- **이용 정지 중**에는 DB 함수가 지급하지 않는다(정지 확인이 맨 앞). **퀘스트 전 유저**의 서비스 활동 잼도 지갑에 바로 들어간다(챕터 점수처럼 챕터 1 시작까지 보류하지 않는다).
- **밸런스 설정 «서비스 활동 잼» 구역**: 칸 `rule:<kind>:amount`(7종)와 `service_jam_daily_cap`·`service_jam_weekly_cap`. 표 `service_jam_rules`와 `jam_policy` 한 행을 쓰고 이력은 기존 `balance_setting_changes`를 쓴다. «챕터» 구역에 남은 활동별 점수 칸은 안내 문구로 «더 이상 쌓이지 않는다»를 알린다(삭제는 U11).
- **정리되는 것**: «캡슐이 다음 동기화에서 찬다»는 해석은 폐기했다. 활동 잼이 동기화 안에서 바로 캡슐을 채우는 것과 서비스 활동 잼이 지급되자마자 채우는 것이 같은 규칙이 된다. 지갑에 잼이 남는 경우는 캡슐이 빈칸 외 이유(트라이브 없음 등)로 열리지 않고 가득 찬 채일 때뿐이고, 이는 U3 규칙 그대로다.
- **반복 파밍 시험(체크포인트)**: 1회차에서 실제 Postgres 롤백 드라이런으로 같은 이벤트 재전송, 드랍→줍기 반복(값 5로 올렸을 때), 하루·주간 상한 경계(KST 월요일), 상한 부분 지급, 정지 중 지급 없음, 원장 등식을 돌려 결과를 사용자에게 보고한다.
