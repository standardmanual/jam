# [Feature] 포인트가 있으면 잠긴 아이템 배지가 열린다(서버)

> 상위 티켓 `20261028_1730`의 하위 티켓 U6다. 연결된 결정: D4, D6. 처리 유형(`/jam-work`): api(단독 호출).

## 핵심 요약

- 요구사항: 잠긴 아이템 배지를 잼 채우기 대신 포인트를 내고 한 번에 연다. 포인트가 모자라면 사유와 함께 거절하고, 퀘스트 안의 첫 잠긴 배지는 포인트 없이 연다.
- 구현 계획: `openLockedItem`을 포인트 차감 방식으로 바꾸고 포인트 원장에 «잠긴 배지 열기 −N»과 «아이템 배지 획득 +M»을 두 줄로 남긴다. 필요 포인트는 배지가 유저에게 배정될 때 고정한다.
- 관련 파일: `jam-web/src/lib/inventory/lockedItemFill.ts` `openLockedItem`, `jam-web/src/app/api/inventory/items/[itemId]/fill/route.ts`, 포인트 지급·원장 코드(아현이 첫 호출에서 위치 확인), `jam-web/src/lib/i18n/ko.ts`. 줄 위치는 아현이 첫 호출에서 확인한다.

## 배경 / 문제 정의

- 포인트는 지금 주기만 하고 쓰는 곳이 없다. 잠긴 아이템 배지 열기가 첫 쓰는 곳이 된다.
- «잼과 포인트는 서로 바꿀 수 없다»는 원칙(운영 로직 14.1절)은 그대로다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 잔액은 0 아래로 내려가지 않는다(제약은 U2).
- 이용 정지 중에는 열 수 없다. 이미 칸을 차지하고 있으므로 인벤토리가 가득 차도 열 수 있다.
- 열릴 때 받는 포인트(등급별 10~100)는 기존 규칙대로 일련번호마다 한 번만 준다.
- 퀘스트 안의 첫 잠긴 배지는 포인트 없이 연다(A1, 지금의 «잼 5 예외»와 같은 방식).

## 구현 계획

`openLockedItem`을 포인트 차감 방식으로 바꾸고 포인트 원장에 «잠긴 배지 열기 −N»과 «아이템 배지 획득 +M»을 두 줄로 남긴다. 필요 포인트는 배지가 유저에게 배정될 때 고정한다.

### 규모 사전 판정 (2026-10-30)

바뀌는 파일은 SQL 1개, 생성 타입 1개, 서버 코드 4개(`lockedItemFill.ts`, `lockedItemFill-contract.ts`, `open/route.ts`, `ko.ts`), 어드민 설정 2개(`locked.ts`, `LockedSection.tsx`), 정책 대시보드 1개, 문서 5개 안팎, 시험 5개 안팎으로 20개 안팎이고 800줄 안팎이다. 티켓의 처음 추정(4~5파일)을 크게 넘고 `plan_only` 기준(5개 초과 또는 100줄 이상)도 넘는다. U3 선례대로 **3회차로 나눠** 회차마다 워크플로와 민지 게이트를 거친다. 티켓은 하나로 유지하고, 각 회차는 앞 회차를 머지한 로컬 staging 끝에서 분기한다.

### 현재 사실 (2026-10-30, 코드와 공용 DB 읽기 전용 확인)

- `openLockedItem`은 DB 함수 `locked_item_open`(마이그레이션 235)을 부른다. 이 함수는 채운 양이 필요량에 닿았는지(`not_full`)만 보고, 배지의 `point_reward`를 연 유저에게 한 번만 준다(`inventory_items.point_awarded_at`).
- U2(마이그레이션 300)가 `inventory_items.unlock_points_required`, `point_transactions.source_inventory_item_id`, 사유 `locked_unlock_cost`, 한 개체에 한 번만 차감하는 부분 유일 인덱스, `jam_policy.locked_points_*`(50, 100, 200, 400)를 이미 더했다. 공용 DB에서 잠긴 개체는 0개이고 포인트 지갑 3개, 원장 15줄이다.
- 지갑 잔액이 0 아래로 내려가지 못하게 하는 제약(266)은 출시 뒤에 걸린다. 그 전에는 지갑 행을 잠그고 잔액을 확인하는 함수가 유일한 방어다. 선례는 `admin_deduct_points`(252)다.
- `award_points`는 원장 연결 열로 배지·미션·컬렉션만 받고 개체를 받지 않는다(8개 인자, 마이그레이션 157). 개체에 연결된 차감 줄을 남기려면 인자를 하나 더해야 한다.
- 잠금은 개체를 만든 뒤 `UPDATE ... SET locked = TRUE`로 입히는 경로가 많다(`grant_inventory_item_locked`, 캡슐 세 함수, 동기화 보류 고르기, 미션·믹스 보상, 시스템 드랍). 경로마다 값을 넘기게 하면 RPC 시그니처 여러 개를 바꿔야 한다. `inventory_items`에는 이미 트리거 3개가 있다(`trg_inventory_items_reject_locked` 등).
- 퀘스트 전 캡슐(챕터가 아직 없는 유저)이 첫 개체를 반드시 잠그고 필요한 잼을 5로 고정한다(`jam-web/src/lib/capsule/capsuleRoll.ts` 168줄). A1의 «잼 5 예외»가 이것이다.
- 지금 열기 API(`/api/inventory/items/[itemId]/open`)는 응답에 `pointsAwarded`만 싣고, 상태 조회(`getLockedItemStatus`)는 잼 잔액만 싣는다.

### 동작 설계 (모든 회차의 기준)

1. **새 함수 `locked_item_open_points(p_user_id, p_item_id)`** 를 더한다. 옛 `locked_item_open`은 U11까지 그대로 둔다(확장, 전환, 축소).
2. **필요 포인트** = `inventory_items.unlock_points_required`. 비어 있으면 `jam_policy.locked_points_<등급>`을 쓴다. 0이면 차감 줄을 만들지 않는다.
3. **순서**(한 트랜잭션): 이용 정지 확인 → 개체 행 잠금(내 것, 잠겨 있음) → 지갑 행 잠금과 잔액 확인(모자라면 `insufficient_points`와 `required`, `balance`를 돌려주고 아무것도 바꾸지 않음) → 차감 줄(`award_points(−N, 'locked_unlock_cost')`, 개체 연결) → 열림(`locked=false`, `unlocked_at`) → 획득 줄(배지 포인트가 있고 `point_awarded_at`이 비었을 때만 `award_points(+M, 'badge_point_reward')`) → 이력(`unlocked`).
4. **`award_points`에 9번째 인자 `p_source_inventory_item_id`를 더한다.** 157과 같은 방식으로 옛 8개 인자 시그니처를 먼저 지우고 새로 만든다. 기존 호출부는 이름으로 부르므로 그대로 동작한다.
5. **배정 때 고정**은 `inventory_items`의 BEFORE INSERT OR UPDATE OF locked 트리거로 한다. 잠긴 채로 되는 순간 `unlock_points_required`가 비어 있으면 등급별 정책값을 넣는다. 한 곳에서 모든 경로를 덮고, 값은 그 뒤 정책이 바뀌어도 변하지 않는다.
6. **퀘스트의 첫 잠긴 배지는 0**: 같은 트리거에서, 그 유저에게 챕터가 아직 없고(`user_chapters` 행 없음) 이 개체 말고는 잠긴 적 있는 개체(`lock_reason`이 있는 개체)가 없으면 0으로 고정한다. «잼 5 예외»가 쓰는 조건(챕터 없음)과 같고, 어느 경로로 받든 첫 하나만 무료다. 두 번째부터는 정책값이다.
7. **앱**: `openLockedItem`이 새 함수를 부른다. 응답에 `pointsSpent`(낸 포인트)와 `pointBalance`(연 뒤 잔액)를 더하고, 거절 코드에 `insufficient_points`(409, `required`, `balance`)를 더한다. `getLockedItemStatus`에 `pointsRequired`와 `pointBalance`를 더한다. 채우기 API와 함수는 이 티켓에서 지우지 않는다(화면 전환 U10, 삭제 U11).
8. **어드민**: 밸런스 설정의 «잠긴 아이템 배지» 구역에 «여는 포인트» 4칸(`locked_points_*`)을 더한다(0 이상 정수).
9. 이 티켓이 하지 않는 것: 퀘스트 단계 판정과 카드(U7, `readLockedOpenTarget`이 «남은 잼이 가장 적은 개체»를 고르는 기준도 U7에서 바꾼다), 잠긴 배지 화면(U10), 옛 함수 삭제(U11).

### 위험과 대응

| 위험 | 대응 |
|---|---|
| `award_points` 교체가 포인트 지급 전 경로에 영향 | 옛 7개·8개 인자로 부르는 호출이 그대로 되는지 롤백 드라이런에서 확인. 합계 불변식(Σ지갑 = 발행 − 회수 = Σ원장) 대조 |
| `inventory_items` 트리거가 개체 생성 경로를 막음 | 트리거는 값만 채우고 예외를 던지지 않는다. 드라이런에서 동기화형·캡슐형·믹스형 잠금 입히기 3가지를 재현 |
| 퀘스트 전 첫 잠긴 배지가 다른 경로의 개체로 먼저 쓰임 | 퀘스트는 «아무 잠긴 개체를 열면» 되므로(사용자 결정 2) 영향이 없다. 무료 개체가 하나는 반드시 있다 |
| 동시에 두 번 열기 | 개체 행 잠금 때문에 두 번째는 `not_locked`다. 지갑 행 잠금으로 잔액 확인도 직렬화된다 |
| 옛 화면(채우기 후 열기)과 새 열기의 불일치 | 화면 전환은 U10이고 유저가 0명이다. U10 전에는 옛 화면의 «열기»가 포인트를 쓴다 |
| 첫 개체를 드랍해 다른 계정이 무료로 여는 길 | 잠긴 개체는 드랍하면 안 된다는 트리거가 있어 지금은 막혀 있다. 드랍 허용이 되돌아오면 다시 본다 |

## 완료 조건

- 포인트가 부족하면 사유와 함께 거절되고 잔액이 바뀌지 않는다.
- 잔액을 0 아래로 만드는 차감이 거절된다는 시험이 있다(U2에서 옮김, 2026-10-29. DB 제약은 출시 뒤 266으로 걸리므로 그 전에는 이 함수가 잔액을 잠그고 확인하는 것이 유일한 방어다). 차감 비용은 `inventory_items.unlock_points_required`(배정 때 고정)를 쓰고, 비어 있으면 `jam_policy.locked_points_*`를 쓴다(마이그레이션 300).
- 포인트로 열면 원장에 두 줄(차감, 획득)이 남는다.
- 퀘스트 안의 첫 잠긴 배지는 포인트 없이 열린다는 시험이 있다.
- 운영 로직 7장·14장과 인벤토리 PRD가 갱신되어 있다.

## 작업 기록

### 1회차 (db, 2026-10-30)

- **분기**: 로컬 staging 끝(`531635e58`)에서 `claude/jamwork-20261028_1737-run1`을 만들어 원격에 올리고 `retryBranch`로 이어받게 했다. 면제 사유는 사용자가 3회차 분할과 1회차 시작을 승인했고 티켓에 파일·함수 단위 계획이 있다는 두 가지다.
- **결과**: 마이그레이션 `304_locked_item_open_points.sql`(332줄)과 생성 타입(+6줄)이 들어왔다. 민지 게이트 PASS, CI `verify` 성공. 병합 커밋 `f7caf7b94`.
- **롤백 드라이런**(공용 DB, 데이터 없는 시험 계정 02·03, 끝에서 `RAISE EXCEPTION`으로 전체를 되돌림): 36개 점검 모두 통과.
  - `award_points` 위치 7개·8개 인자와 이름 지정 호출이 모두 동작하고 오버로드는 하나만 남는다.
  - 트리거: 챕터 없는 유저의 첫 잠긴 개체 0, 둘째 Common 50, Rare 100, 믹스·보상형(`UPDATE ... SET locked`) 50, 챕터 있는 유저의 첫 개체 50, 정책값을 77로 바꿔도 이미 고정된 개체는 50 그대로이고 새 개체만 77.
  - 열기: 필요 0이면 차감 줄 없음, 잔액 충분이면 차감(−50, 개체 연결)과 획득(+10) 두 줄과 이력 한 줄, 잔액 부족은 `insufficient_points`(required, balance)로 거절되고 개체·지갑·원장이 그대로, 두 번째 열기 `not_locked`, 남의 개체와 없는 개체 `item_not_found`, 이용 정지 `user_suspended`, 인벤토리가 가득 차도 열림, 이미 지급된 개체는 획득 줄 없이 차감만.
  - 합계 불변식(지갑 = 발행 − 회수 = 원장): 시작 480/480/480, 끝 1462/1462/1462, 음수 지갑 0. 실행 직후 읽기 전용 확인으로 공용 DB가 원래 상태로 돌아온 것을 봤다.
- **적용**(사용자 확인 뒤): `apply_migration`(이름 `304_locked_item_open_points`)으로 공용 DB에 적용했다. 드라이런과 같은 주석 없는 SQL이다. 적용 후 읽기 전용 확인: `award_points`는 9개 인자 하나, 새 함수와 옛 `locked_item_open`·`locked_item_fill`이 함께 있고, 트리거 `trg_inventory_items_fix_unlock_points`는 켜짐(`O`), `locked_item_open_points`와 `award_points`는 `authenticated`·`anon` 실행 불가이고 `service_role`만 가능, 음수 지갑 0, 합계 불변식 480/480/480, 원장 15줄과 잠긴 개체 0개는 적용 전과 같다.
- **민지 참고(처리하지 않음)**: ① 첫 무료 판정이 버려졌거나 드랍된 개체도 «잠긴 적 있는 개체»로 센다. 버려진 첫 개체 때문에 다음 개체가 무료가 되지 못할 수 있다. 잠긴 개체 드랍이 막혀 있어 지금은 생기지 않는다. ② 생성 타입의 새 함수 위치가 알파벳 순서와 다르다. 3회차에서 MCP 생성 타입과 대조할 때 순서 차이가 날 수 있다.
- **2회차에 넘기는 일**: 열기 RPC 응답 키는 `ok, itemId, badgeId, serialNumber, pointsAwarded, pointsSpent, pointBalance`이고 거절은 `user_suspended, item_not_found, not_locked, insufficient_points(+required, balance)`다.
