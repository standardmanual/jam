# [UI] 한 번의 적립이 합친 연출 한 번으로 보인다

> 상위 티켓 `20261028_1730`의 하위 티켓 U9다. 연결된 결정: D11, D12. 처리 유형(`/jam-work`): ui(채원 사전 판정 필요).

## 핵심 요약

- 요구사항: 한 번의 잼 적립에서 일어난 일을 연출 한 번으로 보여 준다. 제목은 챕터가 오르면 챕터 문구, 아니면 «캡슐이 가득 찼어요»이고, 보상(캡슐 보상 여러 개와 챕터 배지)을 한 화면에 모아 «보상 보기»와 «닫기»를 둔다.
- 구현 계획: 프로토타입의 오렌지 확장 연출(`LevelUpOverlay`)을 서비스 오버레이 규칙(z 60, body 포털, 스크롤 잠금)에 맞춰 옮기고, 서버가 준 이벤트 순서를 그대로 재생한다(화면에서 다시 계산하지 않는다). 닫으면 디졸브로 닫히고 게이지가 2% 원에서 남은 잼을 채운다.
- 관련 파일: 프로토타입 `jam-web/src/app/spike/capsule-fill/LevelUpOverlay.tsx`·`CapsuleFillModule.tsx`, `jam-web/src/components/chapter/ChapterRiseOverlay.tsx`·`ChapterRiseWatcher.tsx`, `jam-web/src/components/BadgeRevealOverlay.tsx`, `jam-web/src/lib/chapter/celebrate.ts`. 줄 위치는 아현이 첫 호출에서 확인한다.

## 배경 / 문제 정의

- 서비스의 챕터 오름 카드는 기기 저장값 기준으로 다음에 앱을 열 때 한 번 뜬다. 보상 결과는 놓치면 안 되므로 서버의 «아직 보지 않은 결과»로 복구한다(D12).

## 상세 요구사항

### 서비스/코드베이스 관점

- 다른 오버레이가 열려 있으면 닫힌 뒤에 보여 준다(기존 챕터 카드 규칙).
- 높은 등급이 나와도 낮은 등급을 실패처럼 표현하지 않고, 다시 열기를 부추기는 말을 쓰지 않는다(운영 로직 5.2절 연출 규칙).

### UI/UX 관점

- 문구는 UX Writing 가이드를 따른다: «축하해요!», «챕터 N에 올랐어요», «캡슐이 가득 찼어요». «보상 보기»는 고정 용어(획득, 아이템 배지)에 맞춰 다듬는다(B6).
- 모션 줄이기 설정에서는 확장 없이 페이드로 대체한다(프로토타입에서 확인됨).

## 구현 계획

프로토타입의 오렌지 확장 연출(`LevelUpOverlay`)을 서비스 오버레이 규칙(z 60, body 포털, 스크롤 잠금)에 맞춰 옮기고, 서버가 준 이벤트 순서를 그대로 재생한다(화면에서 다시 계산하지 않는다). 닫으면 디졸브로 닫히고 게이지가 2% 원에서 남은 잼을 채운다.

### 현재 코드 상태 (2026-10-30 카리나 확인)

- 서버는 동기화와 서비스 활동 잼 지급 직후 자동 채움을 돌리고, 열린 캡슐이 있으면 `capsule_unseen_results`에 한 동기화당 한 건을 남긴다(`lib/capsule/sync-auto-fill.ts`, `recordUnseenCapsuleResult`). `payload.events`는 열린 순서 그대로이고 이벤트 하나가 열기 하나다(`openId`, `items`, `next`, `chapterNo`, `reachedChapters`, `chapterCount`). 이 표는 service_role 전용이다.
- 화면에 내려주는 응답과 `seen_at`을 채우는 처리는 없다. `CapsuleWidget`은 이 기록을 읽지 않는다(U8 결정).
- 챕터 오름 카드(`ChapterRiseWatcher`)는 `(main)/layout.tsx`에서 기기 저장값 기준으로 다음에 앱을 열 때 한 번 뜬다. 같은 오름이 합친 연출과 이 카드로 두 번 보이면 안 된다.
- 챕터 배지는 동기화 끝 판정(`chapter_reached`)이 발급하므로 `payload`에는 들어 있지 않다. 보상 화면에 싣으려면 읽어 오는 길이 필요하다(2회차에서 정한다).
- 프로토타입 `LevelUpOverlay`는 챕터 문구와 «닫기»만 있고 보상은 없다. 번호는 `chapterNo + 1`로 계산해 서버 이벤트를 쓰지 않는다.

### 회차 계획

크기를 센 결과 새 컴포넌트, 서버 응답 2개, 화면 연결, 삭제, 문서까지 합쳐 15개가 넘는 파일을 건드린다. 한 번에 돌리지 않고 4회차로 나눈다. 1회차에서 채원 판정을 받고, 승인된 판정은 `reuseDecision`으로 이어 쓴다.

### 가정 목록 (사용자가 바로잡을 수 있다)

- 여러 동기화의 결과가 쌓여 있으면 하나로 합쳐 한 번만 보여 준다. D12가 «다음 접속 때 한 번»이라고 했고, 유저가 그 사이에 화면에 없었기 때문이다. 합칠 때 제목은 오른 챕터가 있으면 가장 높은 챕터를, 없으면 «캡슐이 가득 찼어요»를 쓴다.
- «봤어요» 처리는 «보상 보기»나 «닫기»를 눌러 연출을 끝낸 시점에 한다. 연출 도중 앱을 떠나면 다시 보인다.
- 챕터 오름 카드는 합친 연출이 같은 챕터를 보여 준 경우 같은 기기에서 다시 뜨지 않는다.

### 2회차 구현 계획 (api): 보지 않은 결과를 내려주고 «봤어요»를 받는다

화면 연결은 3회차다. 이번 회차는 서버 읽기·쓰기와 응답 모양까지다. DB 변경은 없다(`capsule_unseen_results`는 마이그레이션 300에 있고 service_role 전용이다).

- `jam-web/src/lib/capsule/capsule-contract.ts`: 응답 타입을 더한다. `CapsuleUnseenResult`는 `{ ids: string[], events: CapsuleUnseenEventView[], chapterBadges: CapsuleChapterBadge[] }`이다. `events`는 1회차 `buildCapsuleResultView`의 입력(`openId`, `items`, `reachedChapters`)을 만족하는 화면용 모양이고, `chapterBadges`는 `id`, `name`, `description`, `imageUrl`, `rarity`, `level`을 담는다. 이 파일은 아무것도 가져오지 않는 규칙을 지킨다(`capsule-boundary.test.ts`).
- `jam-web/src/lib/capsule/unseen.ts`(서버 전용, 새 파일):
  - `readUnseenCapsuleResult(supabase, userId)`: `seen_at IS NULL`인 행을 오래된 순서로 최대 50건 읽고, 가정 1에 따라 이벤트를 열린 순서대로 이어 붙여 하나로 합친다. `payload.version`이 맞지 않거나 `events`가 배열이 아닌 행은 건너뛰고 로그만 남긴다(그 행은 `ids`에 넣지 않는다). 읽을 행이 없으면 `null`이다.
  - 챕터 배지: 합친 `reachedChapters`에 든 챕터마다 `badges.condition_json`에 `chapter_reached`가 그 챕터인 배지를 찾고, 그 유저가 이미 받은 것만 싣는다(받은 곳은 유저 배지 표이며 정확한 표·열 이름은 아현이 확인한다). 동기화 끝 판정이 아직 발급하지 않은 배지는 싣지 않는다. 배지 조회가 실패해도 결과 자체는 내려준다(`chapterBadges: []`, 로그).
  - `markUnseenCapsuleResultsSeen(supabase, userId, ids)`: `user_id`가 본인이고 `seen_at IS NULL`인 행만 `seen_at = now()`로 바꾼다. 이미 본 행이나 남의 행은 건드리지 않고, 같은 요청을 두 번 보내도 결과가 같다. 바뀐 행 수를 돌려준다.
  - 던지지 않는 쪽과 던지는 쪽을 구분해 적는다(조회 실패는 호출부가 «보여 주지 않고 다음에 다시»로 처리하도록 오류를 돌려준다).
- `jam-web/src/app/api/capsule/unseen/route.ts`(새 파일): `GET`. 세션 확인(401), 서비스 클라이언트로 `readUnseenCapsuleResult`. 응답은 `{ result: CapsuleUnseenResult | null }`이다. 이용 정지 중에도 막지 않는다(내 결과 보기). 오류는 500과 일반 문구, 내부 원문은 싣지 않는다. `force-dynamic`.
- `jam-web/src/app/api/capsule/unseen/seen/route.ts`(새 파일): `POST`. 본문 `{ ids: string[] }`(UUID 문자열, 1~50개)를 검사하고(400), `markUnseenCapsuleResultsSeen`을 부른다. 응답은 `{ marked: number }`이다.
- `jam-web/src/lib/capsule/capsule-client.ts`: `fetchUnseenResult()`와 `markUnseenSeen(ids)`를 더한다(기존 `fetchCapsule` 방식을 따른다).
- 시험: `lib/capsule/__tests__/unseen.test.ts`(여러 행 합치기 순서, 깨진 행 건너뛰기, 챕터 배지 조회, 이미 본 행·남의 행 제외, 같은 요청 반복), `app/api/capsule/unseen/__tests__/route.test.ts`와 `seen/__tests__/route.test.ts`(401, 400, 200, 500), `capsule-boundary.test.ts`에 계약 파일 유지.
