# [UI] 잠긴 아이템 배지 화면에서 포인트로 연다

> 상위 티켓 `20261028_1730`의 하위 티켓 U10다. 연결된 결정: D4, D6. 처리 유형(`/jam-work`): ui(채원 사전 판정 필요).

## 핵심 요약

- 요구사항: 잠긴 아이템 배지 상세에서 필요 포인트와 부족 안내를 보여 주고 포인트로 연다. 잼 채우기 패널과 «채운 잼이 사라져요» 경고는 없앤다.
- 구현 계획: 잠긴 상세의 게이지와 채우기 입력을 포인트 열기 버튼으로 바꾼다. 이력 시트, 드랍 확인 문구를 갱신한다.
- 관련 파일: `jam-web/src/components/jam/JamFillPanel.tsx`(잠긴 배지 쪽 사용 제거), `jam-web/src/app/(main)/inventory/`(잠긴 상세), `jam-web/src/lib/i18n/ko.ts`(드랍 경고 문구), 인벤토리 PRD. 줄 위치는 아현이 첫 호출에서 확인한다.

## 배경 / 문제 정의

- 잠긴 아이템 배지 상세는 지금 캡슐과 같은 `JamFillPanel`을 `BottomSheet`로 띄워 채운다. 새 규칙에서는 잼이 아니라 포인트로 열므로 입력 단계가 없다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 포인트가 모자라면 사유와 함께 안내하고 버튼을 막는다. 잔액은 서버(U6)가 최종 판정한다.

### UI/UX 관점

- «획득»과 «열기»의 구분(열기는 획득이 아니다, 운영 로직 7.2절)을 문구에 지킨다. 고정 용어는 «잠김»이고 «잠금»을 쓰지 않는다.

## 구현 계획

잠긴 상세의 게이지와 채우기 입력을 포인트 열기 버튼으로 바꾼다. 이력 시트, 드랍 확인 문구를 갱신한다.

### 규모 사전 판정 (2026-10-30)

잠긴 개체의 «필요한 잼» 값을 화면에 쓰는 곳이 상세 하나가 아니다. 읽기 전용으로 확인한 곳은 ① 잠긴 상세(`inventory/[itemId]/LockedItemDetail.tsx` 279줄, `page.tsx`), ② 줍기·드랍 시트(`drops/BadgeDetailSheet.tsx` 232줄), ③ 믹스 보류 결과 시트(`combine/PendingResultsSheet.tsx` 66줄), ④ 인벤토리 목록의 잠긴 타일 게이지(`inventory/page.tsx` 68줄의 `fillPercent`), ⑤ 드랍 확인 시트의 «채운 잼은 사라져요»(`components/PoiCarouselModal.tsx`, `/api/inventory/items/[itemId]/drop-loss`)이고, 이 값을 내려 주는 API(`api/inventory/items/route.ts`, `api/drops/poi/[poiId]/route.ts`, `api/drops/[dropId]/route.ts`)와 문구(`ko.ts`)가 따라온다. 코드 15개 안팎, 시험 10개 안팎, 문서 4개 안팎으로 30개 안팎이고 1,000줄 안팎이다. `plan_only` 기준을 넘고 한 회차에 담으면 U7 1회차(27파일)보다 크다. **3회차로 나눈다**: 1회(ui) 잠긴 상세, 2회(ui) 나머지 표면(필요 잼 문구, 목록 타일, 드랍 경고), 3회(content) 문서와 정책 카드. 두 화면 회차는 `ui` 유형이라 채원 사전 판정을 각각 거친다.

### 현재 사실 (2026-10-30, 코드 읽기 전용 확인)

- 잠긴 상세는 게이지(`ProgressBar`)와 가진 잼 줄(`JamBalance`)을 보이고, 다 채우지 못했으면 «채우기» 버튼이 `JamFillPanel`을 `BottomSheet`로 띄우고, 다 채웠으면 «열기» 버튼이 나온다. 서버 페이지는 `getLockedItemStatus`의 `required`·`filled`·`balance`(잼)를 내린다. U6 2회가 이 상태 조회에 `pointsRequired`와 `pointBalance`를 이미 더했다.
- 열기 API는 포인트를 쓰는 새 함수를 부른다(U6). 거절 `insufficient_points`는 409이고 `required`와 `balance`를 싣는다. 그런데 화면의 열기 흐름(`lockedItemFill-flow.ts`의 `runLockedOpen`)은 옛 거절 코드(`not_full`)만 알고 `insufficient_points`의 처리 문구가 없다.
- 열기 성공 응답에는 `pointsAwarded`(받은 포인트)와 `pointsSpent`(낸 포인트)가 있고, 화면은 `pointsAwarded`만 «{points} 포인트를 받았어요»로 보인다.
- 카드 문구 `d.lockedItem.card.description`(«여는 데 잼 {n}만큼 채워야 해요»)과 `requiredChip`(«잼 {n} 필요»)이 상세 설명, 줍기 시트, 믹스 보류 시트에 쓰인다. 사실과 다르다.
- 드랍 확인 시트는 잠긴 개체를 드랍할 때 사라질 채운 양을 `/api/inventory/items/[itemId]/drop-loss`로 읽어 «채운 잼은 사라져요» 안내를 보인다. 공용 DB에는 잠긴 개체가 0개라 지금 채운 양이 있는 개체는 없다.
- 퀘스트 카드(U7)는 이미 «인벤토리 가기»로 이 상세를 가리키고, 안내에는 «잠긴 배지를 열 수 있어요»를 쓴다. 상세의 어휘가 이것과 달라지는 어긋남이 U10 전까지 남아 있다.

### 동작 설계 (모든 회차의 기준)

1. **잠긴 상세(1회)**: 게이지와 가진 잼 줄, «채우기» 버튼, `JamFillPanel` 시트를 없애고 «열기» 버튼 하나로 바꾼다. 필요 포인트(`pointsRequired`)와 가진 포인트(`pointBalance`)를 보여 주고, 가진 포인트가 필요 포인트보다 모자라면 사유를 안내하고 버튼을 막는다(0이면 «포인트 없이» 열린다). 잔액은 서버가 최종 판정하므로 `insufficient_points` 409를 받으면 안내 뒤 서버 값을 다시 읽는다. 열린 뒤 화면은 지금처럼 같은 자리에서 바뀌고, 열기로 받은 포인트(`pointsAwarded`)와 낸 포인트(`pointsSpent`)를 «열기는 획득이 아니다» 원칙(운영 로직 7.2절)에 맞게 문구로 구분한다.
2. **서버 페이지(1회)**: 상세에 `pointsRequired`와 `pointBalance`를 내리고, 필요 포인트가 비어 있는 개체는 일반 문구로 접는다. 잼 값(`required`·`filled`·`balance`)은 상세 props에서 뺀다.
3. **열기 흐름(1회)**: `runLockedOpen`이 `insufficient_points`를 알아보고 `required`·`balance`를 화면에 돌려준다. 화면에서 더는 쓰지 않는 `runLockedFill`과 채우기 호출은 호출처가 없으면 없앤다(채우기 API와 DB 함수는 U11까지 둔다).
4. **카드 문구와 다른 표면(2회)**: 줍기 시트·믹스 보류 시트·상세 설명의 «여는 데 잼 {n}만큼 채워야 해요»를 포인트 기준으로 바꾸거나, 포인트 값을 싣지 않는 일반 문구로 바꾼다(채원 판정). 인벤토리 목록의 잠긴 타일에서 게이지를 걷어낸다. 드랍 확인 시트의 «채운 잼은 사라져요» 안내와 `drop-loss` 조회·API를 없앤다. 이 값을 내려 주던 API 필드는 새 화면이 쓰지 않으면 없앤다.
5. **문서(3회)**: 인벤토리 PRD와 운영 로직 7.2·7.3·7.6절, 정책 대시보드 카드 `ch7-*`, 가이드에서 «채우기»·«게이지» 서술을 지금 사실로 고친다.
6. 이 티켓이 하지 않는 것: 캡슐 위젯·시트와 `JamFillPanel`의 캡슐 쪽 사용(U8), 옛 채우기·열기 DB 함수와 채우기 API 삭제(U11), 잠긴 개체 드랍 경로 판단(후속 `20261030_0947`), 퀘스트 카드 문구(U7에서 끝).

### 위험과 대응

| 위험 | 대응 |
