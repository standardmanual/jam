# [UI] 홈과 프로필의 캡슐 진입 모션을 접속 때 보이게 하고, 챕터 표기를 정리한다

## 핵심 요약

- 요구사항(사용자, 2026-10-31):
  1. 프로필과 홈에 접속하면 캡슐 게이지가 채워지는 모션이 보여야 한다.
  2. 홈의 캡슐 바 위 «챕터 N» 글자를 없앤다.
  3. 프로필의 챕터 프로그레스바를 없애고, 이름 위에 작은 글씨로 «챕터 N»을 보여 준다.
- 구현 계획: 아래 «구현 계획»의 파일별 항목을 따른다. 계획 반환 면제(`planOnlyWaiver`)를 쓴다. 파일은 5개를 넘지만 삭제·이동이 대부분이고 계획을 파일 단위로 적었다.
- 관련 파일: `jam-web/src/app/(main)/page.tsx`(홈, 46·47·89·98·156~164줄), `jam-web/src/app/(main)/profile/ProfileClient.tsx`(33·118~126·598~620·678~690줄), `jam-web/src/components/chapter/ChapterLine.tsx`, `jam-web/src/components/capsule/CapsuleGauge.tsx`(`useEffect` 진입 모션, 112~165줄), `jam-web/src/lib/i18n/ko.ts`(461~470줄 `chapter.line`), 시험 `components/chapter/__tests__/ChapterLine.test.tsx`·`app/(main)/profile/ProfileClient.chapter.test.tsx`. 스펙: 운영 로직 5.2·12.3절, 홈피드 PRD 7번 줄·캡슐 위젯 절.

## 배경 / 문제 정의

2026-10-31에 스테이징(232 계정)에서 측정한 사실이다.

- 진입 모션(`CapsuleGauge`)은 이미 있다. 마운트하고 260ms 쉰 뒤 1,500ms 동안 2% 원에서 지금 값까지 차오른다. 프로필에서는 앱 내 이동 약 1.3초 뒤에 0→67%(28px→269px)로 차오르는 것을 확인했다.
- 그런데 모션이 «마운트 시각 기준»이라 **화면에 보이는 때와 맞지 않는다.** 홈에서는 게이지가 첫 화면 맨 아래(뷰포트 768px 중 위쪽 733px)라 모션이 도는 1.8초 동안 탭바 근처에 가려 거의 보이지 않는다. 사용자가 스크롤해 내려왔을 때는 이미 끝나 있다.
- 홈의 «챕터 N» 글자와 프로필의 «챕터 N + 다음 챕터까지 8px 막대»는 사용자가 정리하기로 했다(2026-10-31).

## 상세 요구사항

### UI/UX 관점

1. **캡슐 진입 모션**: 홈과 프로필 모두, 게이지가 화면에 보이는 순간부터 채움이 2% 원에서 지금 값까지 차오른다. 게이지가 이미 보이면 지금처럼 260ms 쉰 뒤 바로 시작한다. 게이지가 화면 밖이면 보일 때(절반 이상 들어올 때) 시작한다. 한 화면 방문에 한 번이다(재진입마다 반복하지 않는다). 모션 줄이기 설정에서는 모션 없이 바로 끝 값을 그린다. 합친 연출이 게이지를 붙드는 동안(`gaugeHeld`)의 동작, 값이 바뀔 때의 이동(700~1,500ms), 번개 튐은 그대로 둔다. 값이 0이면 모션이 없다.
2. **홈**: 게이지 위 «챕터 N» 글자를 뺀다. 게이지가 그만큼 위로 올라온다. 홈에는 챕터 번호가 더 나오지 않는다.
3. **내 프로필**: «챕터 N + 다음 챕터까지 + 막대»를 그리는 줄을 없앤다. 챕터가 있을 때만 프로필 헤더의 이름(표시 이름) 위에 «챕터 N»을 작은 글씨로 보여 준다. 챕터가 없거나 읽지 못하면 아무것도 그리지 않는다. 글씨 크기·색은 채원의 판정을 따른다(홈의 기존 글자는 `text-sm text-muted`였다). 캡슐 게이지 위젯은 프로필에 그대로 남고, 줄이 빠진 뒤의 간격도 채원이 정한다.
4. **다른 유저 프로필**: 바꾸지 않는다(«트라이브 · 챕터 N» 한 줄).
5. 점수 숫자는 어디에도 그리지 않는다(운영 로직 12.3절). 새 문구를 만들지 않고 `d.chapter.line.chapter`(«챕터 {chapterNo}»)를 쓴다. 안 쓰게 되는 문구 `d.chapter.line.untilNext`는 쓰는 곳이 없으면 지운다.

### 서비스/코드베이스 관점

- 홈이 챕터 번호를 더 쓰지 않으면 `getMyChapter` 호출과 `chapterPromise`를 `Promise.all`에서 뺀다(서버 읽기 1건 감소). `getMyChapter` 자체와 어드민의 사용처(`lib/admin/user-chapter-view.ts` 등)는 건드리지 않는다.
- 내 프로필이 `progress`·`nextChapterNo`를 더 쓰지 않으면 `MyChapterLineData`에서 두 값을 뺄지 호출부(`[username]/page.tsx` 120~124줄)와 함께 판단한다. 읽기 함수의 반환 형태는 바꾸지 않아도 된다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)

- 홈의 캡슐 게이지 위에 «챕터 N» 글자가 없다. 홈이 `getMyChapter`를 부르지 않는다(안 쓰는 경우).
- 내 프로필에 «다음 챕터까지»와 챕터 막대가 없다. 챕터가 있으면 표시 이름 위에 «챕터 N»이 작은 글씨로 보이고, 없으면 아무것도 없다. 캡슐 게이지는 남아 있다.
- 다른 유저 프로필의 «트라이브 · 챕터 N» 줄은 그대로다.
- `CapsuleGauge`의 진입 모션이 «게이지가 화면에 보일 때» 시작한다. 시험이 이미 보임·나중에 보임·관찰자 없음·모션 줄이기를 확인한다. 합친 연출 붙들림(`gaugeHeld`)과 값 변경 이동·번개 튐 시험이 그대로 통과한다.
- `scripts/verify.sh`(린트·타입·시험·ds 검사·문구 검사)가 통과한다. 문구에 새 글이 없다.
- 운영 로직·홈피드 PRD·17 챕터 문서가 새 화면 구성과 맞다.

### 후속 범위 (담당: 카리나, 시점: 머지와 push 뒤)

- 스테이징(232 계정, 챕터 3·캡슐 120/180)에서 홈을 새로 열어 게이지가 화면에 보일 때 채움이 차오르는지 잰다(채움 너비 변화 샘플). 프로필도 같다. 홈에서 «챕터 N»이 없고, 프로필 이름 위에 «챕터 3»이 있고 막대가 없는지 읽는다.
- 측정 시 주의: 내장 브라우저는 창 포커스가 없고 하이드레이션이 느려(홈은 접속 뒤 6초 이상) 타이머가 늦게 돈다. 값은 «시작 시점»이 아니라 «차오르는 변화가 보이는가»로 본다.

## 완료 기록

### 구현 내용 요약

- **진입 모션**: `CapsuleGauge`가 바깥 트랙을 `IntersectionObserver`(threshold 0.5, 아래쪽 rootMargin -72px)로 관찰한다. 탭바 위쪽에서 절반 이상 보일 때 관찰자를 해제하고 260ms 쉰 뒤 2%에서 지금 값까지 1,500ms 차오른다. 이미 보이면 바로, 관찰자가 없는 환경(시험)은 즉시 시작한다. 모션 줄이기·값 0·`held`·값 변경 이동·번개 튐은 그대로다. 상수는 `capsule-gauge.ts`의 `GAUGE_ENTRY_VISIBLE_RATIO`, `GAUGE_ENTRY_TABBAR_CLEARANCE_PX`.
- **홈**: «챕터 N» 글자와 감싸던 `div`를 지웠다. `getMyChapter` 호출·`chapterPromise`·`Promise.all` 항목을 뺐다(서버 읽기 1건 감소).
- **내 프로필**: `ChapterLine mine`이 막대와 «다음 챕터까지» 없이 `text-xs text-muted` «챕터 N» 한 줄만 그린다. 헤더 이름 열의 첫 줄(이름 위)에 두고, 챕터가 없으면 그리지 않는다. 캡슐 위젯은 묶음 없이 바깥 `gap-6`으로 이어진다. `MyChapterLineData`는 `chapterNo`만 남겼고 `ko.ts`의 `untilNext`를 지웠다. 다른 유저 프로필 줄은 그대로다.
- **채원 판정**: 서비스 전용, 새 토큰·컴포넌트 없음, 승인 필요 항목 없음. 사후 리뷰는 중대 문제 없음(제안 3건은 모두 아래 후속 확인).
