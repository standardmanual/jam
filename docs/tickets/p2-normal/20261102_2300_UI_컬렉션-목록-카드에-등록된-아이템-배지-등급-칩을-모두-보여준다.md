# [UI] 컬렉션 목록 카드에 그 컬렉션에 등록된 아이템 배지의 등급 칩을 모두 보여준다

## 핵심 요약

- 요구사항: 컬렉션 목록의 각 카드 썸네일 **왼쪽 상단(안쪽 여백 있음)** 에, 그 컬렉션에 등록된 아이템 배지의 **등급 칩을 등급별로 모두** 보여준다. 배치 순서는 **완성 칩이 먼저, 등급 칩이 그 뒤**다(사용자 지시 «완성칩 뒤에 두면 되»).
- 현재: 카드에는 등급 칩이 **한 개**만 있다. 값은 컬렉션에 «처음 등록된 아이템 배지 한 장»의 등급이고(`rarityByBook`에서 `created_at` 순으로 처음 만나는 값), 순서는 등급 칩 → 완성 칩이다. Common은 `RarityBadge`가 그리지 않는다.
- 구현 계획: ① 컬렉션별 «등록된 등급 목록»(중복 없음, Common → Rare → Epic → Mystic 순)을 만드는 공용 함수를 `src/lib/itembook/`에 둔다. ② 세 곳의 데이터 계산(`badges/page.tsx`, `api/users/[username]/itembooks/route.ts`, `[username]/collections/page.tsx`)이 그 함수를 쓰게 한다. ③ `CollectionGridCard`의 `rarity` prop을 `rarities`(배열)로 바꾸고 태그 행을 «완성 → 등급들» 순으로 그린다. 칩이 한 줄에 다 안 들어가면 줄바꿈한다. ④ 디자인시스템 사본을 같은 방식으로 맞춘다. ⑤ `[username]/collections` 화면의 인라인 카드에도 왼쪽 상단 등급 칩을 더한다(완성 칩은 지금처럼 오른쪽 위에 둔다).
- 관련 파일:
  - `jam-web/src/components/ui/CollectionGridCard.tsx` (`rarity` prop, 태그 행 `{(rarity || completed) && ...}` 구간)
  - `jam-web/src/app/(main)/badges/page.tsx` (150~155행 `rarityByBook`, 181행 `itemBookProgress` 조립) · `jam-web/src/app/(main)/badges/BadgesClient.tsx` (`ItemBookProgress.rarity`, 컬렉션 탭의 `CollectionGridCard` 호출)
  - `jam-web/src/app/api/users/[username]/itembooks/route.ts` (97~102행 `rarityByBook`, 159행 응답의 `rarity`) · `jam-web/src/app/(main)/profile/ProfileClient.tsx` (76행 타입 `rarity: BadgeRarity`, 464~472행 호출)
  - `jam-web/src/app/(main)/[username]/collections/page.tsx` (111행 배지 조회에 `rarity`는 이미 있음, 207~226행 카드 마크업)
  - `jam-web/src/components/admin/ops/OpsKindPreview.tsx` (110행 호출, 등급 없음 — 영향 없음 확인)
  - `jam-web/design-system/components/patterns/CollectionGridCard.{jsx,d.ts,prompt.md,stories.tsx}` (`showRarity`·태그 행 99~102행)
  - `jam-web/src/components/ui/__tests__/{cardFacePairs,pressClass}.test.tsx` (`CollectionGridCard`를 쓰는 기존 시험)
  - 신규: `jam-web/src/lib/itembook/book-rarities.ts` + 단위 시험

## 배경 / 문제 정의

- 컬렉션 안에는 여러 등급의 아이템 배지가 들어 있다. 지금 카드는 한 장의 등급만 보여줘서 «이 컬렉션에서 어떤 등급까지 모을 수 있는지»가 드러나지 않는다.
- 같은 정보를 칩으로 모두 보여주면 수집 목표가 카드에서 바로 읽힌다.

## 상세 요구사항

### 서비스/코드베이스 관점
- «등록된 아이템 배지»는 그 컬렉션의 `type = 'item'`이고 `deleted_at`이 없는 배지다. 체크인·그 밖의 종류는 등급 칩에 넣지 않는다.
- 등급 목록은 중복 없이, Common → Rare → Epic → Mystic 순이다. `rarity`가 NULL인 배지(무한레벨형)는 건너뛴다.
- `RarityBadge`가 Common을 그리지 않는 현재 동작은 바꾸지 않는다. 따라서 Common만 등록된 컬렉션은 등급 칩이 없다.
- 데이터를 계산하는 세 곳은 같은 공용 함수를 쓴다(같은 규칙을 세 번 쓰지 않는다).

### UI/UX 관점
- 칩 위치: 썸네일 왼쪽 위, 안쪽 여백은 지금 값(`top-2 left-2`)을 유지한다.
- 칩 순서: 완성 칩 → 등급 칩들. 완성하지 않은 컬렉션은 등급 칩만 나온다.
- 카드 폭이 좁으면(2열 그리드, 320px 화면) 칩이 넘치지 않고 다음 줄로 내려간다. 썸네일 밖으로 잘리거나 가로 스크롤이 생기지 않는다.
- `[username]/collections` 화면에서는 완성 칩이 오른쪽 위에 있어 순서 문제가 없다. 등급 칩만 왼쪽 위에 더한다.

## 구현 계획

> 파일 단위 지도는 위 «관련 파일»에 적었다. 바뀌는 파일은 5개를 넘으므로 카리나가 지도를 근거로 `planOnlyWaiver`를 넘겨 호출한다.

1. 채원①이 칩 배치(줄바꿈 규칙, 칩 개수가 많을 때의 처리)와 디자인시스템 연결 범위를 판정한다.
2. 아현이 공용 함수·시험을 만들고 세 곳의 데이터, `CollectionGridCard`, 디자인시스템 사본, `[username]/collections` 카드를 같은 브랜치에서 고친다.
3. `docs/service/prd/` 중 컬렉션 목록 카드를 서술한 문서가 있으면 맞춘다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)
- 공용 함수가 컬렉션별 등급 목록을 «중복 없음, Common → Mystic 순, 삭제·NULL·item 아닌 배지 제외»로 돌려준다(단위 시험).
- `CollectionGridCard`에 `rarities`를 주면 태그 행에 «완성 칩(있을 때) → 등급 칩들» 순서로 그려지고, Common은 그려지지 않는다(단위 시험과 Story).
- `/badges` 컬렉션 탭, 프로필 컬렉션, `[username]/collections`의 데이터가 같은 공용 함수에서 나온다.
- `[username]/collections` 카드 왼쪽 위에 등급 칩이 나오고 완성 칩은 오른쪽 위에 그대로 있다.
- 디자인시스템 `CollectionGridCard`(`.jsx`·`.d.ts`·`.prompt.md`·Story)가 서비스와 같은 동작이다.
- `scripts/verify.sh`가 통과한다.

### 후속 범위 (담당: 카리나, 시점: 머지 뒤)
- 메인 트리 로컬 `next dev`에서 `/badges#collection`과 프로필 컬렉션을 열어 칩 순서·줄바꿈을 눈으로 확인한다(여러 등급이 있는 컬렉션과 완성한 컬렉션).
- push 뒤 staging에서 같은 화면을 확인한다.
