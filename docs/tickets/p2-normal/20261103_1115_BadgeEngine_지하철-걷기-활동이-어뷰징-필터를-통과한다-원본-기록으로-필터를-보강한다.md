## 배경 / 문제 정의

### 활동에서 확인한 값

| 항목 | Strava 원본(동기화 때) | JAM!에 저장된 값 |
|---|---|---|
| 거리 | 5.27km | 1.707km |
| 움직인 시간 | 589초 | 339초 |
| 평균 속도 | 32.2km/h | 18.1km/h |
| 최고 속도 | 87km/h | 87km/h (프로덕션은 구간을 빼도 최고 속도를 낮추지 않는다) |

- 속도 기록에 지하철 4~5구간이 이어져 있고, 구간 사이에 GPS가 10~20초씩 끊긴 곳이 있다.
- 교통수단 구간 감지는 동작했다. 시속 20km를 30초 넘게 이어 넘는 구간 3.563km(250초)를 뺐다. 이 값은 재현 시험이 소수 6자리까지 같게 다시 만든다.
- 빠지지 않은 것은 출발·정차 때 30초 안에 끝나는 가속·감속 구간과 20km/h 아래로 달린 구간이다. 남은 1.7km도 평균 18km/h라 걷기 속도가 아니다.
- 평균 속도 필터(`vehicle_speed_filter_kmh` 60)는 평균이 60km/h를 넘어야 걸러낸다. 원본 32km/h도, 남은 18km/h도 통과했다.
- 걷기·등산에는 «걷기로는 너무 빠른 평균»을 막는 기준이 없다. 종목 불일치 판정은 러닝·자전거가 너무 느릴 때만 본다.

### 프로덕션과 staging의 차이

- 프로덕션은 `main`(2026-10-14) 코드다. staging에 있는 «움직인 시간 10분 미만 제외»(`qualification.ts`)가 프로덕션에는 없다. 이 활동은 남은 시간이 339초라 staging 규칙으로는 걸러지지만, 더 긴 지하철+걷기 활동은 똑같이 통과한다.
- staging은 구간을 뺀 뒤 최고 속도도 낮춘다(티켓 20261018_1815 3회). 프로덕션은 그렇지 않아 87km/h가 최고 속도 조건 배지에 쓰일 수 있다.
- JAM 2.0을 main에 올리기 전까지 프로덕션에는 필터 보강이 닿지 않는다(2026-10-15 결정). 급하면 main에서 별도 수정이 필요하다.

### 기준값과 근거

- **교통수단 비율 = 50%**: 구간 감지가 뺀 거리가 원래 거리의 절반 이상이면 활동 전체를 `vehicle_speed`로 거른다. 거리로 센다(이 활동은 거리 68%, 시간 42%라 시간 기준으로는 놓친다). 다섯 종목 모두에 적용한다(감지가 종목별로 돌기 때문).
- **걷기·등산 평균 속도 상한 = 16km/h**: 구간을 뺀 뒤 평균이 이 값을 넘는 걷기·등산 활동은 `vehicle_speed`로 거른다.
  - 근거 1: 20km 경보 세계기록의 평균 속도가 남자 1:16:10(2025) 약 15.75km/h, 여자 1:23:49(2021) 약 14.3km/h다. 걸어서는 낼 수 없는 속도라 16을 상한으로 둔다. ([20 kilometres race walk](https://en.wikipedia.org/wiki/20_kilometres_race_walk))
  - 근거 2: 걷기에서 달리기로 바뀌는 속도는 평균 약 7km/h, 빠른 걷기는 5~6km/h다. 기존 걷기 배지 게이트(`passesWalkingGate`, 평균 2~8km/h)가 이 근거를 쓴다. ([Polar](https://www.polar.com/en/guide/time-to-run-or-time-to-walk-your-body-knows-the-answer))
  - 8이 아니라 16인 이유: 이 필터에 걸린 활동은 배지뿐 아니라 드랍·미션·잼까지 전부 받지 못한다. 걷기로 기록한 조깅(8~16km/h)은 부정이 아니라 종목 오기록이라, 걷기 배지에서만 빠지고(기존 게이트) 드랍은 받게 둔다. 걸러야 할 것은 사람이 낼 수 없는 속도다.
  - 두 값 모두 `abusing_policy` 칸이라 어드민 밸런스 «어뷰징» 구역에서 조정한다.

## 시험 자료 (보존 완료)

- Strava에서 이 활동을 지우기 전에 스트림을 저장했다. 저장한 것: `time`·`velocity_smooth`·`distance`·`altitude`(639개, 활동 요약, 랩, 프로덕션이 저장한 행, 동기화 때의 정책값).
- 저장하지 않은 것: `location`(이동 경로 좌표)은 개인 위치 정보라 넣지 않았다. `moving`(움직임 여부)은 옮겨 적는 중 길이가 어긋나 믿을 수 없어 뺐다. 이 두 가지가 필요하면 Strava를 지우기 전에 활동 화면의 «원본 내보내기»로 파일을 따로 받아 둔다.
- 저장본이 정확한지는 구간 감지를 다시 돌려 확인했다: 뺀 거리 3.5629435km, 뺀 시간 250초, 남은 움직인 시간 339초가 프로덕션 저장값과 같다(5개 시험 통과).
- 동기화 때 Strava 거리는 5270.0m였고 지금은 5270.5m다. 재현 시험은 동기화 때 값(5.27km)을 쓴다.

## 구현 계획

`/jam-work` 유형 `engine`, 표준 경로. 새 `abusing_policy` 칸 두 개를 만들고(DB 확장), 판정 함수를 따로 두어 동기화가 부르게 한다. 지난 활동은 다시 판정하지 않는다(소급 없음).

1. **DB 확장(아현은 파일만 쓰고 실행은 카리나)**: `jam-web/supabase/migrations/314_abusing_policy_transit_ratio_walk_avg.sql`과 `314_..._down.sql`(313 쌍을 본뜬다). `ALTER TABLE public.abusing_policy ADD COLUMN IF NOT EXISTS transit_ratio_filter_pct INTEGER NOT NULL DEFAULT 50, ADD COLUMN IF NOT EXISTS walk_avg_max_speed_kmh INTEGER NOT NULL DEFAULT 16;` 열 주석 포함. 프로덕션 코드는 `select('*')` 뒤 자기 키만 읽으므로 열이 늘어도 깨지지 않는다.
2. **정책 로더**: `jam-web/src/lib/abusing/policy.ts`. `AbusingPolicy`에 두 키, `DEFAULT_POLICY`에 50·16, `getAbusingPolicy`의 정규화에서 두 키는 양수가 아니면 기본값으로 대체(`MISMATCH_POLICY_KEYS` 방식). 비율은 100 이하.
3. **판정 함수(새 파일)**: `jam-web/src/lib/abusing/vehicleFilter.ts`. `judgeVehicleActivity({ before, after, policy }): { filtered: boolean; reason: 'speed' | 'transit_ratio' | 'walk_avg' | null }`. `before`는 구간 감지 전 정규화 활동, `after`는 감지 후. 순서는 평균 속도 필터(기존) → 교통수단 비율 → 걷기·등산 평균 상한. 비율 = `1 - after.distanceKm / before.distanceKm`(before 거리가 0이면 비율 규칙은 건너뛴다).
4. **동기화에 연결**: `jam-web/src/lib/strava/sync.ts`의 `checkAbusingFilters`(약 600~625행). 구간 감지 전에 `const before = activity`를 쥐고, 마지막의 `activity.averageSpeedKmh > vehicleSpeedFilterKmh ? 'vehicle_speed' : null`을 위 함수로 바꾼다. 걸러진 사유는 계속 `vehicle_speed` 하나다(`FilterReason` 값을 늘리지 않는다). 첫 동기화와 일반 동기화가 같은 함수를 쓰므로 한 곳만 고친다. 종목 불일치(`applyTypeMismatch`)가 걷기로 바꾼 활동에도 걷기 상한이 걸리는지 시험으로 확인한다.
5. **밸런스 화면**: `jam-web/src/lib/admin/balance/abusing.ts`. `ABUSING_BALANCE_KEYS`·`ABUSING_FIELDS`에 두 칸(그룹 «차량», 라벨 «교통수단 비율 상한(%)»·«걷기·등산 평균 속도 상한», 단위 %·km/h, 정수, 비율 1~100, 속도 1 이상)과 읽기 열 목록(187행 부근 select 문자열)을 더한다. `jam-web/src/lib/admin/balance/__tests__/abusing.test.ts`가 지키는 키 목록 일치를 갱신한다.
6. **생성 타입**: `jam-web/src/types/database.generated.ts`의 `abusing_policy` Row/Insert/Update 세 곳(59·81·103행 부근, `mismatch_run_min_speed_kmh` 옆)과 `jam-web/src/types/database.ts`의 같은 표에 두 열을 더한다. 카리나가 DB 실행 뒤 열 이름·형식을 정보 스키마로 대조한다.

### 잔여 이슈
- 이 티켓의 실제 활동(남은 움직인 시간 339초)은 staging에서 `too_short`(10분 미만)가 먼저 돌아 `too_short`로 기록된다. 새 규칙은 10분 이상의 더 긴 지하철+걷기 활동에서 효력이 있다.
