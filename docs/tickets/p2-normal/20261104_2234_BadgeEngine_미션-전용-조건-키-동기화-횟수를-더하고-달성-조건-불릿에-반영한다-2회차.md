# [BadgeEngine] 미션 전용 조건 키 «동기화 횟수»를 더하고 달성 조건 불릿에 반영한다 (2회차)

## 핵심 요약

- 요구사항: 「드랍하고, 픽업하고, 이어가기」의 달성 조건에 `동기화 1회` 불릿이 나오게 한다. 이를 위해 «참가한 뒤 미션 기간 안의 동기화 횟수»(`sync_count`)를 미션 전용 DB 기록 키로 더한다. 상위 `20261104_2146`의 2회차다.
- 구현 계획: 아래 「구현 계획」 표. `jam_period_earned`(3-A회, 티켓 20261019_1445)가 같은 모양의 선례라 그 연결 지점을 그대로 따른다. 파일이 5개를 넘으므로 첫 호출부터 `planOnlyWaiver`를 넣는다.
- 관련 파일: 「구현 계획」 참조.

## 배경 / 문제 정의

상위 티켓의 결정: 달성 조건 불릿은 조건 데이터와 지표 라벨로 만든다(1회차 완료). 「동기화 1회」는 조건 데이터에 넣기로 했다(사용자 2026-11-04).

실측한 사실:

- 동기화 횟수의 원천이 없다. `user_daily_sync_counts`는 유저·날짜별 카운터 한 행이라 마지막 동기화 시각(`updated_at`)만 남는다. 참가 시각 이후의 횟수를 정확히 셀 수 없다(참가한 날 이전의 동기화가 같은 행에 섞인다). 그래서 **동기화 한 번에 한 줄을 남기는 기록 표를 새로 만든다.**
- **기록 시점이 판정보다 앞이어야 한다.** 동기화(`processFetchedActivities`, `jam-web/src/lib/strava/sync.ts`)에서 미션 판정 `checkMissions`는 979~980줄 부근이고, 하루 카운터 기록 `recordDailySyncAndEvaluate`는 996줄 부근으로 판정 뒤다. 새 기록을 판정 뒤에 두면 이번 동기화가 세어지지 않아 미션이 한 번 늦게 완료된다. 새 기록은 `checkMissions` **앞**에 둔다.
- 미션 판정은 새 활동을 1건 이상 받은 동기화에서만 돈다(새 활동이 없는 경로 `evaluateWithoutNewActivities`는 `checkMissions`를 건너뛴다, 같은 파일 463~500줄). 새 기록도 같은 지점(활동을 받은 동기화)에서만 남기므로 «동기화 횟수 = 미션이 판정된 동기화 수»다. 이 정의는 하루 카운터(`daily_sync_count`)와 같은 기준이다.
- 결과로, `동기화 1회` 조건은 판정 시점에는 항상 충족된다(판정이 도는 동기화 자체가 1회다). 그래도 사용자가 지표를 추가하는 쪽을 택했고, 이후 「동기화 N회」 미션을 어드민에서 쓸 수 있게 되므로 진행한다.

## 상세 요구사항

### 서비스/코드베이스 관점

1. **기록 표**(확장 단계, 되돌림 SQL 포함): `user_sync_events`(`id` bigint 자동 증가, `user_id` uuid, `synced_at` timestamptz 기본 `now()`). `(user_id, synced_at)` 인덱스. RLS 켬·정책 없음(서버 service_role 전용). 선례 모양: `200_user_combine_success_logs.sql`. 과거 동기화는 채우지 않는다(참가한 뒤의 기록만 세므로 필요 없다).
2. **기록 지점**: `processFetchedActivities`에서 `checkMissions` 호출 **직전**에 한 줄을 넣는다. 실패해도 동기화는 계속된다(try/catch로 격리, 로그만 남긴다). 새 활동이 없는 경로(`evaluateWithoutNewActivities`)에서는 남기지 않는다.
3. **미션 전용 키 `sync_count`**: `jam_period_earned`와 같은 연결을 따른다.
   - `MissionCondition`에 `sync_count?: number`(`jam-web/src/types/database.ts` 912줄 부근).
   - `jam-web/src/lib/missions/condition-keys.ts`: `MISSION_ONLY_CONDITION_KEY_LIST`(94줄 부근)와 `MISSION_ONLY_DB_CONDITION_KEY_LIST`(195줄 부근)에 더한다.
   - `jam-web/src/lib/missions/dbMetrics.ts` `READERS`(미션 전용 DB 키 항목): `sync_count: (s, u, w) => countSyncEvents(s, u, w)`. 읽기 함수는 `user_sync_events`에서 `synced_at`이 `[fromIso, toIso)` 안인 행 수를 센다(다른 읽기 함수와 같은 모양, 읽지 못하면 던진다). `Record<MissionDbConditionKey, …>`라 읽기를 빠뜨리면 컴파일 오류다.
   - 판정(`engineCondition.ts`)은 «값 이상»이면 충족이다. 다른 DB 키와 같은지 확인하고 다르면 맞춘다.
   - 어드민 저장 규칙(`jam-web/src/app/api/admin/missions/route.ts`·`[id]/route.ts`의 조건 검사)이 새 키를 통과시키는지, 1 이상의 정수만 받는지 확인한다(`jam_period_earned` 검사 위치 참조).
   - 시뮬레이션(`jam-web/src/app/api/admin/missions/simulate-condition/route.ts`): `missionDbKeysPresent`·`missionOnlyKeysPresent`에 자동으로 잡히는지 확인한다.
4. **어드민 미션 양식**: «기록으로 세는 조건»에 `sync_count` 입력 칸을 더한다. `jam-web/src/app/admin/missions/missionConditionFields.ts`(그룹 표 132줄 부근에 `{ title: '동기화', keys: ['sync_count'] }`, 칸 정의 164줄·읽기·쓰기 406~418줄·460줄·724줄·828줄의 `jam_period_earned` 분기와 같은 자리)와 `MissionConditionSection.tsx`(265줄 분기, 721줄 `renderJamPeriodEarnedField`와 같은 모양의 렌더 함수). 칸은 1 이상의 정수, 단위 «회», 도움말은 «새 활동을 불러온 동기화만 세요. 참가한 뒤 미션 기간 안의 횟수예요.»(해요체, 문구는 아현이 가이드에 맞춰 다듬는다).
5. **라벨 시드**: `badge_metric_labels`에 `sync_count`=`동기화`/`회`를 더한다(마이그레이션과 같은 파일, `ON CONFLICT DO NOTHING`).
6. **불릿 생성기 확장**(`jam-web/src/lib/missions/conditionBullets.ts` `conditionBulletKeys`·`buildConditionBullets`): 레지스트리에 없는 미션 전용 키(`MISSION_ONLY_CONDITION_KEY_LIST`)를 «모르는 키»로 막던 곳을 풀어, **레지스트리 키가 선언 순서로 먼저, 미션 전용 키가 목록 순서로 뒤에** 오게 한다. 그래서 이 미션은 `아이템 배지 드랍 1회` → `아이템 배지 픽업 1회` → `동기화 1회` 순이다. 미션 전용 키에 라벨이 없으면 여전히 `null`(기존 표시로 되돌림)이다. `jam_period_earned`는 라벨이 없으므로 그대로 `null`이다.
7. **생성 타입**: 새 표를 `jam-web/src/types/database.generated.ts`(+ 필요하면 `database.ts`)에 같은 모양으로 맞춘다. `npm run db:types`는 쓰지 않는다. 컬럼 추가 SQL 실행 뒤 Supabase 타입 생성 결과와 대조하는 것은 카리나가 4단계에서 한다.
8. 데이터(`condition_json`)는 이 회차에서 바꾸지 않는다. 「드랍하고, 픽업하고, 이어가기」의 `condition_json`에 `sync_count: 1`을 더하는 것은 3회차(콘텐츠)에서 한다.

### UI/UX 관점

- 미션 상세 화면의 변경은 불릿 생성기 확장뿐이다. 새 컴포넌트·토큰은 없다.
- 어드민 폼 칸은 기존 `jam_period_earned` 칸과 같은 shadcn 구성(네이티브 `select` 금지)을 따른다.

### 컨텐츠 관점

- 문구는 라벨 `동기화`/`회`와 어드민 도움말 한 문장뿐이다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)

- 조건에 `sync_count`가 든 미션이 `loadMissionDbMetrics`로 «참가한 뒤 기간 안» 동기화 횟수를 읽고, 조건의 숫자 이상이면 충족한다(시험: 기간 안·밖 기록, 하한 없음 오류).
- 동기화 기록이 `checkMissions`보다 앞에서 남는다(호출 순서 시험). 기록 실패는 동기화를 막지 않는다. 새 활동이 없는 경로에서는 남기지 않는다.
- `condition_json`이 `{drop_item_count:1, pickup_item_count:1, sync_count:1}`인 미션의 불릿이 `아이템 배지 드랍 1회`, `아이템 배지 픽업 1회`, `동기화 1회` 순이다(시험, 라벨 맵은 시험에서 준다).
- 미션 전용 키에 라벨이 없으면 불릿 전체가 `null`이다(시험).
- 어드민 미션 양식에서 `sync_count`를 입력·저장할 수 있고, 1 미만·소수는 거절된다(시험).
- 마이그레이션 두 파일이 있고 되돌림 SQL이 맞다(`DROP TABLE`과 라벨 행 삭제).
- `scripts/verify.sh` 통과, CONDITION_JSON_SPEC 갱신.

### 후속 범위 (담당: 카리나, 시점: 머지 전·후)

- 317 실행(롤백 드라이런 후 적용, 읽기 확인), 타입 대조(MCP `generate_typescript_types`).
- 머지 후 로컬 실렌더: 불릿은 데이터를 바꾼 뒤에야 `동기화 1회`가 나오므로, 데이터 반영은 3회차에서 한다.

## 주요 의사결정

- 2026-11-04: 기록 표를 새로 만든다. 하루 카운터 재사용안은 참가한 날 이전 동기화가 섞여 정확한 횟수를 셀 수 없어 채택하지 않았다.
- 2026-11-04: 기록은 «새 활동을 받은 동기화»에서만 남긴다. 하루 카운터와 같은 기준이고, 미션 판정이 도는 동기화와 일치한다.
- 2026-11-04: `condition_json`에 키를 넣는 데이터 반영은 3회차로 미룬다. 이 회차는 판정·입력·표시의 틀만 만든다.
