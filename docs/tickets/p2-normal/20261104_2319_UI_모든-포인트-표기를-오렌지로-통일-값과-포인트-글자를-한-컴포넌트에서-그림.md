# [UI] 서비스의 모든 포인트 표기를 오렌지로 통일한다 (값과 «포인트» 글자 모두, 한 컴포넌트에서)

## 핵심 요약

- 요구사항(사용자 지시 2026-11-04): «모든 포인트는 오렌지 컬러로 표기하는 걸 규칙으로 한다.» 포인트 값(숫자)과 «포인트» 글자 모두 오렌지다. 규칙은 UX Writing 가이드 «포인트(POINT)» 행에 이미 적었다(티켓 20261104_2315). 이 티켓은 서비스 전 화면에 그 규칙을 적용한다.
- 지금 규칙을 따르는 곳: 믹스 레시피 행(`RecipeRewardRow.tsx`)뿐이다.
- 구현 계획(제안, 채원 사전 판정 필요):
  1. 값+단위를 그리는 공용 컴포넌트(예: `PointText`)를 한 곳에 둔다. 색은 `text-warning`(`--warning` #f5a300) 하나만 받는다.
  2. 문구 사전(`ko.ts`)의 «{n} 포인트»가 문장 속에 섞인 문자열(약 87곳 중 사용자 노출분)은 문장 전체가 아니라 «{n} 포인트» 조각만 칠해야 한다. `t()`가 ReactNode 조각을 받을 수 있게 하거나, 조각만 감싸는 도우미를 둔다.
  3. 화면별로 값·단위가 보이는 곳을 전수 조사해 적용한다: 홈 피드·온보딩 퀘스트 카드·프로필·포인트 내역(`points/page.tsx`)·미션 목록/상세 보상·믹스·배지 상세·잠긴 아이템 상세·인벤토리 상세·드랍 시트·알림·배지 공개 오버레이·픽업 선택 오버레이·지도·회원 탈퇴 시트 등(`grep 포인트`로 약 30개 파일).
  4. MODULAR(`design-system/`)에 같은 규칙이 들어가야 하는지는 채원이 판정한다.
- 관련 파일: 위 화면 목록, `jam-web/src/lib/i18n/ko.ts`·`t()` 구현, `jam-web/src/components/ui/`(공용 컴포넌트 위치), `docs/service/writing/UX_WRITING_GUIDELINE.md`(§1.3 포인트 행)

## 사용자 결정과 회차 계획 (2026-11-04)

채원 사전 판정(2026-11-04)과 사용자 답:

- **글자색**: 새 색값을 만들지 않는다. 기존 오렌지 계열 토큰 중 대비가 가장 높은 `--accent-content-red`(#ff4400)를 `--point-text` 별칭으로 쓴다. 대비는 흰 면 3.45:1, 어두운 면(#1c1917) 약 4.98:1이다. `--warning`(#f5a300)은 흰 면 2.07:1이라 쓰지 않는다. **알려진 한계**: 흰·크림 면 위 12~16px 글자는 4.5:1에 못 미친다(3:1은 넘는다).
- **어두운 면**: 같은 토큰이 4.5:1을 넘으므로 어두운 면용 별칭과 `surface` prop을 두지 않는다. (사용자가 «어두운 면은 밝은 주황»으로 답했지만, 그 질문은 짙은 주황을 쓰는 전제였다. 전제가 바뀌어 한 토큰으로 갔다. 밝은 주황을 원하면 별칭 한 줄을 바꾼다.)
- **예외**: 차감 표기(-N 포인트)도 부호까지 오렌지다. 버튼 안의 포인트 글자는 버튼 글자색을 따른다.
- **제외**: 캔버스로 구운 이미지와 DOM 밖 문구(푸시·슬랙).
- **회차**: ① 토큰·`PointText`·MODULAR 반영·`RecipeRewardRow` 교체, ② 문장 속 조각 도우미와 홈·미션·믹스, ③ 나머지 화면과 전수 확인.

### 3회차 파일 단위 계획 (2026-11-05)

변경 파일이 25개쯤이라 두 번으로 나눠 진행한다. 3회차(가)는 도우미와 값이 중심인 화면이고, 3회차(나)는 카드·오버레이·잠긴 아이템 같은 문장 속 화면과 전수 확인이다. 이 회차의 사전 판정은 1회차 채원 판정과 사용자 결정(토큰 `--point-text`, 차감·버튼 예외)을 그대로 이어받는다. 새 토큰·새 컴포넌트는 없다.

카리나가 정한 기본값(바꾸려면 한 줄씩 고친다):

- **이미 완성된 문자열로 오는 곳**(알림, 오늘 카드 줄, 믹스 결과 오버레이)은 `tPoint`를 쓸 수 없으므로 `pointify(text)`로 `[부호]숫자 포인트` 조각만 `PointText`로 바꾼다. 정규식은 `([+\-−]?\d[\d,]*) 포인트`다.
- **값만 보이는 자리**(필요 포인트 행, 가진 포인트 행)는 `PointText`의 `unit`을 빈 문자열로 주면 값만 그리게 넓힌다. 같은 토큰이고 새 컴포넌트가 아니다.
- **사진 위 어두운 막(scrim) 카드**(`PosterCard`, `DomeCard`의 포스터 모양)는 칠하지 않고 흰 글자를 유지한다. 막이 검정 60%라 밝은 사진 위에서는 `--point-text` 대비가 최악 약 1.6:1까지 떨어지기 때문이다. 흰 면 위 카드(히어로·정사각·목록·티켓·브리프·돔 일반)는 칠한다.
- **자릿수 팝인 잔액**(포인트 내역 화면의 큰 숫자)은 훅이 숫자 칸을 직접 만들어 `PointText`를 쓸 수 없다. 같은 토큰을 가리키는 `text-point-text` 클래스로 교체하고 예외로 기록한다.

## 먼저 정해야 할 것 (채원 판정에서 다룬다)

- **글자 대비**: `--warning`(#f5a300)은 흰 면 위에서 대비가 약 2:1이라 12~16px 글자로는 WCAG 기준(4.5:1)에 못 미친다. 서비스 전체 규칙으로 쓰면 읽기 어려운 곳이 생긴다. 더 짙은 오렌지 글자용 토큰을 새로 정할지, 굵은 큰 글자에만 쓸지, 지금 색을 그대로 쓸지는 사용자 승인이 필요한 새 토큰 판단이다.
- 크림·색 배경(캡슐, 배지 상세 테마 배경) 위의 포인트는 같은 색이 읽히는지 확인한다.
- 다크 테마에서도 같은 토큰인지 확인한다.

## 완료 조건

- 사용자에게 보이는 포인트 값과 «포인트» 글자가 모든 화면에서 같은 오렌지로 보인다(어드민 제외). 문장 속 «{n} 포인트» 조각도 같다.
- 색은 한 컴포넌트·한 토큰에서만 정의하고 화면별로 색 클래스를 따로 적지 않는다.
- 글자 대비 판정 결과(새 토큰 또는 현행 유지)가 티켓에 기록된다.
- `scripts/verify.sh` 통과.
