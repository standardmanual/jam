# [Feature] 인벤토리가 가득 차 캡슐 보상을 받을 수 없으면 잼 획득을 막고, 보류·받기·소멸 구조를 걷어 낸다 (상위)

## 핵심 요약

- 요구사항: 캡슐이 가득 찼는데 인벤토리 빈칸이 모자라 보상을 열 수 없으면, 잼이 들어오는 두 길(동기화 정산, 서비스 활동 잼)을 닫고 홈에 붉은 안내를 계속 보여 준다. 못 받은 보상 보관, «받기», 잼 소멸은 없앤다.
- 구현 계획: 하위 티켓 7개(T1~T7)를 선행 순서대로 진행한다. DB는 확장(T1~T3), 코드 전환(T4~T5), 축소(T6), 문서(T7) 순이다.
- 관련 파일: `jam-web/src/lib/capsule/`(`auto-fill.ts`, `sync-auto-fill.ts`, `capsule.ts`, `claim.ts`), `jam-web/src/lib/strava/sync.ts`(입구 차단), `jam-web/src/lib/jam/serviceActivity.ts`, `jam-web/supabase/migrations/`(220·301·302·303), `docs/plan/jam2/10 JAM 2.0 서비스 운영 로직.md`

## 배경 / 문제 정의

지금은 빈칸이 모자라면 캡슐 보상을 최대 2개까지 보관하고, 2개가 되면 지갑 잼 전액이 사라진다(마이그레이션 302). 유저가 «받기»를 알아야 하고, 사라지는 잼이 있고, 상태가 세 갈래(보관 0·1·2)라 설명이 길어진다. 운영 로직 5.2절·6장·15.4절·16.4절과 정책 대시보드가 이 구조를 따로따로 설명한다.

사용자 결정(2026-11-04, 232 계정 캡슐이 가득 찬 사례에서 시작): 한 번 막히면 아무것도 사라지지 않고 «정리하면 이어진다»는 한 줄 규칙으로 바꾼다. 출시 전이고 유저가 8명이며 보관 행이 0건이라 이관 비용이 없다.

## 결정 기록

확정(사용자 승인 2026-11-05, 혜린 추천안 그대로):

1. **Q1. 막힌 동안의 운동 기록**: 활동 자체를 미룬다. 동기화를 입구에서 막고, 풀린 뒤 정상 반영한다. (대안: 동기화는 허용하고 잼만 지갑에 적립. 미채택 이유: 막힌 채로 아이템 배지가 계속 발급되어 보류 고르기(`sync_pending_items`)와 겹친다.)
2. **Q2. 서비스 활동 잼(믹스·미션·배지 받기)**: 막힌 동안 지급을 거절한다. 소액 영구 손실이 생기지만(하루 40·주 100 상한 안) «막히면 잼이 늘지 않는다» 한 줄이 유지된다. 믹스는 빈칸을 만든 뒤 지급하므로 손실이 없다. (대안: 지갑에 적립. 미채택 이유: 규칙이 거짓이 된다. 손실 0을 우선하면 나중에 바꿀 수 있다.)
3. **Q3. 붉은 안내**: 면 전체를 칠하지 않고 붉은 제목·아이콘 같은 포인트로 시작하고, 채원 사전 판정과 윈터 톤 확인을 받는다. 이유는 정지 배너가 «겁주지 않기»(운영 로직 18.2절) 때문에 면을 칠하지 않는 것과 같다. 문구는 해요체다.

미결(해당 하위 티켓에서 정한다): Q4 232 계정의 쓰이지 않은 잼 2,640 처리(T3 배포 뒤, 사용자 승인 후), Q5 막히는 순간 소식 `capsule_jam_blocked` 재사용 여부(T5), Q6 배너 범위(T4, 추천: 홈 배너 + 캡슐 위젯 + 동기화 버튼 토스트), Q7 «빈칸 N개» 표기(T4, 추천: 부족분 `needed - free`), Q8 보류 고르기 409와의 우선순위(T1, 추천: 이번 막힘 안내를 먼저), Q9 `jam_forfeit_weekly` 뷰(T6, 추천: 유지).

## 동작 정의

1. **막힘 판정** `capsule_receive_blocked(user)`: DB 읽기 전용 함수. 「캡슐 가득(`user_capsules.filled >= required`) 그리고 빈칸(`inventory.max_slots - used_slots`)이 필요 칸수(`guaranteed_count + bonus_count`)보다 적음」이면 `blocked=true`와 `free`·`needed`를 돌려준다. 이용 정지와 트라이브 없음은 별개이며 먼저 적용한다.
2. **막히는 순간**: 자동 채움이 여러 캡슐을 열다가 `insufficient_slots`를 만나면 보관하지 않고 멈춘다(`stopped: 'inventory_blocked'`). 그 캡슐은 가득 찬 채 남고 지갑의 남은 잼은 그대로다. 그때까지 열린 캡슐은 «아직 보지 않은 결과» 한 건으로 합쳐 보인다.
3. **막힌 동안**: 동기화 버튼과 콜백 직후 동기화는 입구에서 409 `capsule_inventory_blocked`로 멈춘다(Strava 호출 없음). 서비스 활동 잼은 `{ok:true, granted:0, blocked:true}`를 돌려주고 원장에 쓰지 않는다. 운영자 지급·회수는 막지 않는다. 믹스와 장착·내려놓기 같은 인벤토리 정리는 열어 둔다.
4. **풀림**: 빈칸이 필요 칸수 이상이 되면 다음 동기화 맨 앞, 또는 서비스 활동 잼 지급 직후의 자동 채움이 가득 찬 캡슐부터 연다.
5. **화면**: 홈 상단에 붉은 안내가 막힌 동안 계속 보이고 풀리면 사라진다. 동기화 버튼을 누르면 같은 이유를 안내 토스트(info)로 낸다. 문구 시안(해요체): 제목 «인벤토리가 가득 차서 잼을 얻을 수 없어요», 본문 «캡슐을 열려면 빈칸이 N개 필요해요. 인벤토리를 정리하면 다시 잼을 모을 수 있어요.», 링크 «인벤토리 보기».
6. **없애는 것**: «받기» 버튼과 `POST /api/capsule/claim`, 캡슐 위젯의 보류 안내 4종, 소식 `capsule_nearly_full`(70·80·90% 단계), 잼 소멸.

## 하지 않을 것

- 잼 규칙값·상한·캡슐 필요량 같은 경제 수치 변경.
- 새 아이템을 받는 행동(줍기, 미션 보상, 믹스 결과 수령, 동기화 아이템 배지 발급)을 새로 막기. 각자 빈칸 검사가 이미 있고, 아직 읽지 않은 경로는 T3에서 확인한다.
- 동기화 아이템 배지의 «보류 고르기»(`sync_pending_items`, 운영 로직 6.4)는 건드리지 않는다.
- 알림 enum 값 삭제(PostgreSQL이 지원하지 않음), 과거 `capsule_forfeit` 원장 줄 삭제, 이미 소멸한 잼의 자동 환불.

## 리스크와 미확인

- **경제 균형은 «미검증»**이다. 수치 변경은 없지만 두 방향의 크기를 재지 못했다. ① 소멸 폐지로 순유입이 늘 수 있고, 서비스 활동 잼 거절로 소액 손실이 생긴다. ② 막힘이 길었던 유저가 풀린 뒤 활동을 한꺼번에 정산하면 단기 급증이 생기고 대량 수령 경보(`alertMassEarnIfNeeded`)가 울릴 수 있다.
- 이중 입금은 없다. 활동 정산은 `source_activity_id` 부분 유일 인덱스, 서비스 활동 잼은 `(user_id, source_event_key)` 중복 확인이 막는다.
- 이용 정지는 «정지 기간 활동은 정산하지 않는다»(16.4절)인데 이번 차단은 풀린 뒤 정산한다. 두 규칙이 다르다는 점을 문서에 분명히 적는다.
- Strava: 막힘이 길면 풀린 뒤 한꺼번에 가져오는 양이 늘고, 60초(`maxDuration`) 안에 못 끝나면 `last_synced_at`이 롤백되어 같은 실패가 반복될 수 있다. T1에서 큰 백로그로 시험한다.
- 미확인: Strava 과거 활동 조회 한도, `settleActivities` 내부 기록·정산 순서, 콜백 직후 동기화(`connection-save.ts`)와 백필(`backfill.ts`) 경로, 줍기·미션 보상·믹스 결과 수령의 빈칸 부족 시 동작, 현재 `capsule_policy` 값, `capsule_nearly_full`·`capsule_jam_blocked` 소식 행과 과거 `capsule_forfeit` 줄의 개수, 카즈하 일일 요약의 소멸 신호 코드 위치.
- 운영 부담: 카즈하 일일 요약의 «소멸» 신호가 항상 0이 되므로 «막힌 유저 수»로 바꿀지 카즈하와 확인한다. 임계는 오픈 4주 관찰 뒤 정한다(운영 로직 477줄).

## 구현 계획

하위 티켓 순서대로 `/jam-work`로 처리한다. 하위 티켓마다 시작 전에 주요 결정을 사용자에게 묻고, 정책·수치 문구가 바뀌면 같은 커밋에서 `policiesData.ts`(정책 대시보드)와 PRD를 갱신한다. 마이그레이션 번호는 `320`부터 쓰되, push 직전에 원격 staging 기준으로 다시 확인한다.
