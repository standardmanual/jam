# [Service] 막힌 유저의 동기화가 입구에서 멈추고 이유를 알려 준다 (T1)

## 핵심 요약

- 요구사항: 캡슐이 가득 차고 인벤토리 빈칸이 필요 칸수보다 적은 유저가 동기화를 누르면, Strava를 부르지 않고 409 `capsule_inventory_blocked`로 멈추며 안내 토스트(info)가 나온다.
- 구현 계획: 막힘 판정 DB 함수 `capsule_receive_blocked(uuid)`(읽기 전용)를 만들고, 동기화 입구(`assertNotSuspended` 바로 뒤, 보류 고르기 검사 앞)에서 부른다.
- 관련 파일: `jam-web/supabase/migrations/320_capsule_receive_blocked.sql`과 `_down.sql`(신규, 번호는 push 직전 재확인), `jam-web/src/lib/capsule/receive-block.ts`(신규), `jam-web/src/lib/strava/sync.ts`(1144~1148행 `SyncPendingItemsError` 선례 옆), `jam-web/src/app/api/strava/sync/route.ts`(59~64행 409 매핑), `jam-web/src/lib/strava/sync-flow.ts`, 동기화 버튼 컴포넌트(`SyncButton.tsx`), `jam-web/src/lib/i18n/ko.ts`, `jam-web/src/lib/admin/policyDashboard/policiesData.ts`

## 배경 / 문제 정의

상위 티켓 20261105_0100의 첫 조각이다. 동기화 조회 커서는 `strava_activities`의 최신 `start_date`이고 `last_synced_at` 선점 잠금은 입구 뒤라, 입구에서 막으면 활동 기록이 사라지지 않고 풀린 뒤 이어서 정상 반영된다(코드 읽기로 확인). 같은 선례로 `SyncPendingItemsError`가 가져오기 전에 던져 409로 알린다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 판정은 DB 함수 하나가 단일 원천이다. TS에 같은 판정을 따로 구현하지 않는다.
- 함수는 `blocked`, `free`, `needed`를 돌려준다. 필요 칸수는 `capsule_policy`의 `guaranteed_count + bonus_count`다(`neededSlotsOf`와 같은 값).
- 이용 정지가 먼저 적용되고, 트라이브 없음은 기존 `tribe_required` 그대로다.
- 보류 고르기 대기(409 `sync_pending_items`)와 겹치면 이번 막힘 안내를 먼저 낸다(Q8 추천).
- 콜백 직후 동기화(`connection-save.ts`)와 백필(`backfill.ts`)이 막혀 던져도 Strava 연결 저장은 성공해야 한다.

### UI/UX 관점
- 안내 토스트(info)는 동기화 버튼을 눌렀을 때 낸다. 문구는 UX 라이팅 가이드의 해요체·[현상]→[원인]→[해결책] 구조를 따른다(윈터 톤 확인).

## 구현 계획

파일 단위 계획(카리나가 2026-11-05에 코드를 읽고 적었다). 마이그레이션 실행은 아현이 하지 않고 카리나가 4단계에서 한다.

1. **`jam-web/supabase/migrations/320_capsule_receive_blocked.sql`(신규)**: `capsule_receive_blocked(p_user_id uuid) RETURNS jsonb`, `STABLE`, `SECURITY DEFINER`, `SET search_path = public`, 읽기 전용. 반환 `{blocked, free, needed}`.
   - 캡슐: `user_capsules`에서 이 유저의 행을 읽고 `filled >= required`를 «가득»으로 본다(열 이름·행 수는 301·302를 읽어 확인한다).
   - 빈칸: `GREATEST(0, inventory.max_slots - inventory.used_slots)`(302의 463줄과 같은 식).
   - 필요 칸수: `capsule_policy`(`id = 1`)의 `guaranteed_count + bonus_count`.
   - 캡슐 행이나 인벤토리 행이 없으면 `blocked=false`다(모르면 막지 않는다). 이 결정을 SQL 머리말에 적는다.
   - 실행 권한은 302·303이 쓴 방식을 따른다(`REVOKE ... FROM PUBLIC`과 서비스 역할에만 `GRANT`).
2. **`jam-web/supabase/migrations/320_capsule_receive_blocked_down.sql`(신규)**: `DROP FUNCTION IF EXISTS public.capsule_receive_blocked(uuid);`.
3. **`jam-web/src/lib/capsule/receive-block-contract.ts`(신규, 아무것도 가져오지 않는 순수 파일)**: `CAPSULE_INVENTORY_BLOCKED_CODE = 'capsule_inventory_blocked'`와 응답 타입. 클라이언트가 가져와도 서버 모듈이 번들에 끌려오지 않게 `pending-items-contract.ts`와 같은 이유로 분리한다.
4. **`jam-web/src/lib/capsule/receive-block.ts`(신규)**: `readCapsuleReceiveBlocked(supabase, userId)`(RPC 호출 래퍼, 응답 모양 검사, 오류는 던진다)와 `CapsuleInventoryBlockedError`(`free`·`needed`를 가진다). 모양은 `SyncPendingItemsError`(`jam-web/src/lib/strava/pending-items.ts` 15행)와 같게 한다.
5. **`jam-web/src/lib/strava/sync.ts`**: `assertNotSuspended`(1138행 일대) 바로 뒤, `countPendingItems` 검사(1143행) **앞**에 막힘 검사를 더한다. 막히면 `console.info`로 한 줄 남기고 `CapsuleInventoryBlockedError`를 던진다. 이 지점은 토큰 복호화와 Strava 호출 앞이라 `strava_activities`·`last_synced_at`이 움직이지 않는다.
6. **`jam-web/src/app/api/strava/sync/route.ts`**: `SyncPendingItemsError` 매핑(59~64행) 옆에 409 `{ error, code: 'capsule_inventory_blocked', free, needed }`를 더한다. 같은 파일의 콜백·백필 호출부(`connection-save.ts`, `backfill.ts`)가 던져진 오류를 삼키고 연결 저장은 성공시키는지 읽어 확인하고, 필요하면 시험으로 고정한다.
7. **`jam-web/src/lib/strava/sync-flow.ts`**: 응답 분류에 `{ kind: 'inventory_blocked' }`를 더한다(67행 일대, `isSuspendedBlock` 옆). 보류 고르기 409와 겹치면 이번 막힘이 먼저다(서버가 이미 먼저 던진다).
8. **`jam-web/src/components/SyncButton.tsx`**: 89행 일대 분기에 `inventory_blocked`를 더해 `toast(문구, 'info')`를 낸다.
9. **`jam-web/src/lib/i18n/ko.ts`**: `syncPending`(1137행) 옆에 막힘 문구를 더한다. 해요체, [현상]→[원인]→[해결책] 구조: «인벤토리가 가득 차서 잼을 얻을 수 없어요. 인벤토리를 정리하면 다시 동기화할 수 있어요.»(윈터 톤 확인은 T4의 배너 문구와 함께 받는다.)
10. **`jam-web/src/lib/admin/policyDashboard/policiesData.ts`와 `policiesData.test.ts`**: «인벤토리 가득 참 잼 차단» 항목을 캡슐 챕터에 신설하고 개수 검사를 맞춘다.
11. **`jam-web/src/types/database.generated.ts`**: `Functions`에 `capsule_receive_blocked`를 손으로 더한다(마이그레이션 적용 전이라 MCP 재생성이 안 된다). 적용 뒤 카리나가 MCP `generate_typescript_types`로 대조한다.
12. **시험(신규)**: `receive-block.test.ts`(RPC 응답 해석, 오류 던짐), `sync-flow` 분류 시험, 라우트 409 시험, `sync.ts` 입구 시험(막히면 Strava 호출 0회). 기존 시험 파일이 있으면 그 옆에 더한다.
13. `docs/service/prd`에 `sync_pending_items` 응답을 설명하는 API 표가 있으면 같은 곳에 `capsule_inventory_blocked` 한 줄을 더한다. 규칙 전체의 문서 정리는 T7이다.

크기: 상한(파일 5개·100줄)을 넘는다. 사용자가 상위 티켓과 하위 티켓 분해를 승인했고(2026-11-05), 위 계획이 파일 단위로 적혀 있으며 사전 확인(`sync.ts`·`route.ts`·`SyncButton.tsx`·`sync-flow.ts`·`pending-items.ts`를 읽음)이 끝났으므로 카리나가 «계획 반환 면제»를 부여한다.

큰 백로그(수십 건) 풀림 시험은 아현의 범위 밖이다(후속 범위).

## 완료 조건

### 구현 범위 (게이트 판정 대상)
- 막힌 시험 계정이 동기화를 누르면 Strava 호출 없이 409 `capsule_inventory_blocked`와 안내 토스트(info)가 나온다.
- 그때 `strava_activities` 행과 `last_synced_at`이 변하지 않는다.
- 막히지 않은 계정의 동기화 동작은 이전과 같다(단위 시험과 시험 계정 실측).
- 콜백 직후 동기화·백필이 막혀 던져도 연결 저장은 성공한다.
- 빈칸을 필요 칸수 이상으로 만든 뒤 다음 동기화가 정상이다.
- `capsule_receive_blocked`가 읽기 전용이고 `_down.sql`로 되돌려진다(롤백 실측 기록).
- `policiesData.ts`에 «인벤토리 가득 참 잼 차단» 항목이 있다.

### 후속 범위 (담당: 카리나, 시점: 머지 뒤)
- 큰 백로그(수십 건) 풀림 시험은 가능한 범위에서 기록하고, 60초를 넘는 위험이 확인되면 별도 티켓을 만든다.

체크포인트: db 유형이므로 DB 단독 호출 전 사용자 확인. 롤백 실측 후 실행한다.
