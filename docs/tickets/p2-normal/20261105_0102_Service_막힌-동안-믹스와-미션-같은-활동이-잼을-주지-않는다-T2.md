# [Service] 막힌 동안 믹스·미션 같은 서비스 활동이 잼을 주지 않는다 (T2)

## 핵심 요약

- 요구사항: 막힘 상태(T1의 판정)에서 서비스 활동 잼(믹스·미션·배지 받기 등) 지급은 `{ok:true, granted:0, blocked:true}`를 돌려주고 원장·날짜별 합·지갑을 바꾸지 않는다. 운영자 지급은 막지 않는다.
- 구현 계획: `jam_apply_service_activity`(마이그레이션 303)를 같은 시그니처로 교체해 `capsule_receive_blocked`를 부르고 `blocked` 키만 추가한다. `serviceActivity.ts`는 오류가 아니므로 실패 기록(engine-log)에 남기지 않는다.
- 관련 파일: `jam-web/supabase/migrations/321_service_activity_jam_blocked.sql`과 `_down.sql`(303 본문 복원, 번호는 push 직전 재확인), `jam-web/src/lib/jam/serviceActivity.ts`, 관련 시험

## 배경 / 문제 정의

서비스 활동 잼은 `awardServiceJam`이 `jam_apply`가 아니라 `jam_apply_service_activity`를 불러 지갑과 원장에 직접 쓴다. 믹스 성공·미션 완료·배지 받기는 이미 일어난 일이라 «활동을 미룬다»가 되지 않고, 막으면 그 잼은 사라진다. 규모는 작다(303 기준 규칙값 5~30, 하루 40·주 100 상한). 사용자 승인으로 거절을 택했다(상위 티켓 Q2).

## 상세 요구사항

### 서비스/코드베이스 관점
- 막힘 판정은 T1의 `capsule_receive_blocked`를 그대로 쓴다. 판정을 복제하지 않는다.
- 믹스는 빈칸을 만든 뒤 지급하므로 믹스 직후에는 막힘이 이미 풀려 있어 지급되고, 가득 찬 캡슐이 바로 열린다.
- 중복 키 `(user_id, source_event_key)`와 일·주 상한 동작은 이전과 같다.
- 막혀서 거절한 지급은 `blocked: true`로 구분되어야 하고 오류·실패 기록이 아니다.

## 구현 계획

파일 단위 계획(카리나가 2026-11-05에 303·`serviceActivity.ts`를 읽고 적었다). 마이그레이션 실행은 아현이 하지 않고 카리나가 4단계에서 한다.

1. `jam-web/supabase/migrations/321_service_activity_jam_blocked.sql`(신규): `jam_apply_service_activity(uuid, text, text)`를 같은 시그니처로 교체한다(303 본문 기준). 303의 1~6단계는 그대로 두고, **6단계에서 지급량(`v_granted`)이 0보다 크다고 확정된 직후, 7단계(원장 쓰기) 앞**에 막힘 검사를 한다: `public.capsule_receive_blocked(p_user_id)`의 `blocked`가 참이면 `{ok:true, granted:0, blocked:true, ruleAmount, duplicate:false, dailyUsed, weeklyUsed, balance}`를 돌려주고 아무것도 쓰지 않는다(호출 전 값). 이렇게 두면 이벤트 키 재전송은 여전히 `duplicate`이고, 규칙값 0·상한 도달은 각자의 이유로 돌아가며, `blocked`는 «막혀서 못 받은 경우»만 뜻한다. 판정을 복제하지 않고 T1의 함수를 부른다. 잠금은 지갑 행 하나뿐이고 막힘 판정은 잠금 없는 읽기라 교착이 생기지 않는다(303 머리말의 잠금 설명을 그대로 둔다). COMMENT를 고치고 권한은 `CREATE OR REPLACE`가 유지한다.
2. `jam-web/supabase/migrations/321_service_activity_jam_blocked_down.sql`(신규): 303의 함수 본문(`CREATE OR REPLACE FUNCTION public.jam_apply_service_activity` ~ COMMENT, 303 이 파일 91~156줄 일대)을 그대로 복원한다. 카리나가 롤백 실측 때 정규화 해시(주석·빈 줄 제외)로 프로덕션 현재 본문과 대조할 수 있게 본문을 바꾸지 않는다.
3. `jam-web/src/lib/jam/serviceActivity.ts`(181줄): `parseGrant`(76~85줄)가 `blocked: true`를 읽고, `AwardServiceJamResult`(61~72줄)의 `ok: true` 변형에 `blocked: boolean`을 더한다. 막힌 응답은 오류가 아니므로 `recordServiceJamFailure`(engine-log)를 부르지 않고, 지급이 0이라 자동 채움도 부르지 않는다(`granted > 0` 조건이 이미 막는다). 머리말의 «응답 해석» 목록에 한 줄을 더한다. 이 결과를 읽는 호출부(`awardServiceJam`의 반환을 쓰는 곳)가 새 필드 때문에 깨지는지 `grep`으로 확인한다.
4. 시험: `jam-web/src/lib/jam/__tests__/serviceActivity.test.ts`(339줄)에 «막힌 응답이면 지급 0, 실패 기록 없음, 자동 채움 호출 없음, 행동 지표 판정 없음», «막히지 않은 응답은 이전과 같음»을 더한다.
5. `jam-web/src/lib/admin/policyDashboard/policiesData.ts`와 시험: 서비스 활동 잼 항목(343줄 일대)에 «캡슐이 가득 차고 인벤토리 빈칸이 모자라 막혀 있으면 지급하지 않음(거절, 나중에 보충하지 않음)»을 더하고, `ch5-inventory-full-block`(496줄 일대)에 서비스 활동 잼 거절을 한 줄 더한다.
6. 코드를 읽어 확인해 반환 요약에 적는다: (가) 믹스 성공 지급(`combine_success`)이 빈칸을 만드는 일(재료 소모) **뒤**에 일어나는지, 일어나는 시점의 트랜잭션 경계. (나) 운영자 지급·회수가 `jam_apply`의 `admin_grant`·`admin_deduct`라 막히지 않는지. (다) `jam-web/src/lib/admin/balance/serviceJam.ts`가 이 함수를 부르는지 이름만 참조하는지.

크기: 파일 6개 이상(SQL 2개, TS 1개, 시험 2개, 정책 데이터). 위 계획을 첫 호출부터 `planOnlyWaiver` 사유로 쓴다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)
- 막힌 상태에서 서비스 활동 잼을 지급하면 `{granted:0, blocked:true}`이고 원장·날짜별 합·지갑이 불변이며 실패 기록이 남지 않는다.

- 운영자 지급·회수는 막히지 않는다.
- `_down.sql`이 303 본문을 복원한다(롤백 실측 기록).

선행: T1. 체크포인트: db 유형이므로 DB 단독 호출 전 사용자 확인.

## 완료 기록

### 구현 내용 요약
캡슐이 가득 차고 인벤토리 빈칸이 필요 칸수보다 적으면(막힘) 서비스 활동 잼(믹스·미션·배지 받기 등) 지급을 거절한다. 거절한 지급은 나중에 보충하지 않는다.
- DB `jam_apply_service_activity(uuid, text, text)`를 같은 시그니처로 교체했다(마이그레이션 321). 지급량이 0보다 크다고 확정된 직후, 원장 쓰기 앞에서 T1의 `capsule_receive_blocked`를 부른다. 참이면 `{ok:true, granted:0, blocked:true, ruleAmount, duplicate:false, dailyUsed, weeklyUsed, balance}`를 돌려주고 아무것도 쓰지 않는다. 검사 위치 때문에 중복 키·규칙값 0·상한 도달은 이전과 같은 이유로 돌아간다. 판정을 복제하지 않았다.
- `serviceActivity.ts`의 `parseGrant`가 `blocked`를 읽고 결과 타입에 `blocked: boolean`을 더했다. 막힌 응답은 오류가 아니라서 실패 기록(`service_jam_failed`)·자동 채움·행동 지표 판정을 부르지 않는다.
- 정책 대시보드 `ch4-service-jam`·`ch5-inventory-full-block`과 운영 로직 문서 4.2절에 거절 문구를 더했다.

### 코드 확인 결과 (구현 계획 6번)
- (가) 믹스 성공 지급은 재료 소각 뒤에 일어난다. `combine/index.ts` 257행 소각(`burnMaterials`, 안에서 `release_inventory_slots`) → 결과 지급 → `recordCombineSuccess` → `awardServiceJam` 순이고, 등급 올리기(`tierUp.ts`)도 소각 → 지급 → `awardServiceJam`이다. 단계마다 별개 호출이라 하나의 트랜잭션으로 묶이지 않는다.
- (나) 운영자 지급·회수는 `jam_apply`(`admin_grant`)와 `admin_deduct_points`를 지나므로 막히지 않는다.

### 주요 의사결정 / 핵심 메모
- 카리나가 파일 단위 계획을 적고 «계획 반환 면제»를 부여했다. 아현은 계획대로 끝냈다.
- 막힘 검사를 «지급량이 0보다 크다고 확정된 뒤»에 둔 것은 `blocked`가 «막혀서 못 받은 경우»만 뜻하게 하려는 선택이다. 재전송은 계속 `duplicate`, 규칙값 0과 상한 도달은 각자의 이유로 돌아간다.
- 프로덕션 main 코드는 `blocked` 키를 모른다. 막힌 유저가 생겨도 `granted:0`을 «지급 0»으로 읽어 오류 없이 지나가므로 배포 순서의 위험이 없다.
- DB는 사용자 승인을 기다리지 않고 실행하는 규칙(CLAUDE.md 6)에 따라 롤백 실측 뒤 바로 적용했다.

### 잔여 이슈
- 믹스 직후 막힘이 풀려 있다는 가정은 순증 빈칸이 생길 때만 성립한다(민지 참고, 아현 주의). 재료 수와 결과 수가 같은 레시피는 빈칸이 늘지 않아, 이미 막힌 유저의 `combine_success` 지급(5잼)이 거절될 수 있다. 등급 올리기(5개 소각·결과 1개)는 풀린다. 규모는 지급 5잼이고 거절은 보충되지 않는다. 레시피별 재료·결과 수를 확인해 영향이 의미 있으면 후속 티켓으로 정한다.
- 막힘 상태에서 서비스 활동 잼 거절이 화면에 어떻게 보이는지는 T4(붉은 안내)에서 정한다.
