# [Service] 여러 캡슐을 열다 인벤토리가 차면 거기서 멈추고 남은 잼은 지갑에 남는다 (T3)

## 핵심 요약

- 요구사항: 자동 채움이 여러 캡슐을 열다가 빈칸 부족(`insufficient_slots`)을 만나면 보상을 보관하지 않고 멈춘다(`stopped: 'inventory_blocked'`). 그 캡슐은 가득 찬 채 남고 지갑의 남은 잼은 그대로다. 소멸 분기와 단계 올림은 없앤다.
- 구현 계획: `capsule_auto_fill`(마이그레이션 301·302)을 같은 시그니처로 교체한다. 응답 키(`pendingCount`·`forfeited`·`alertStage`)는 유지하고 값을 고정(`pendingCount`=0 등)하며, 키 제거는 T6(축소)에서 한다. TS는 `auto-fill.ts`가 `inventory_blocked`로 멈추고 응답에 `inventoryBlocked: true`를 싣는다.
- 관련 파일: `jam-web/supabase/migrations/322_capsule_auto_fill_inventory_block.sql`과 `_down.sql`(302 본문 복원, 번호는 push 직전 재확인), `jam-web/src/lib/capsule/auto-fill.ts`, `sync-auto-fill.ts`, `capsule.ts`, 시험(`auto-fill` 계열), `policiesData.ts`

## 배경 / 문제 정의

지금은 열 수 없는 캡슐을 만나면 `capsule_hold_reward`로 보관하고, 보관이 2개가 되면 지갑 잼 전액이 사라진다(302). 한 번 막히면 아무것도 사라지지 않게 하는 사용자 결정에 맞춰, 보관 대신 멈추게 한다. 232 테스트 계정(캡슐 180/180, 인벤토리 9/30, 지갑 잼 2,640)은 이 구조가 들어간 뒤 다중 캡슐 정산과 막힘 안내를 시험하기 좋은 사례다(Q4, 실행은 사용자 승인 후).

## 상세 요구사항

### 서비스/코드베이스 관점
- 열린 캡슐은 지금처럼 합쳐서 «아직 보지 않은 결과» 한 건(`capsule_unseen_results`)으로 보인다.
- 지갑 잔여 잼은 불변이고 `capsule_forfeit` 신규 원장 줄이 0건이다.
- 줍기·미션 보상·믹스 결과 수령이 빈칸 부족일 때 각자 막히는지 읽어서 확인하고 결과를 티켓에 적는다.
- 이용 정지 중 캡슐 보류 규칙과 정책 대시보드 «보류 2개 잼 소멸»·«이용 정지 중 캡슐 보류» 항목을 같은 커밋에서 갱신한다.

## 구현 계획

1. `_down.sql`로 302 본문을 복원할 수 있게 쓴다. 롤백 실측으로 N개째 캡슐 막힘을 시험한다.
2. `auto-fill.ts`가 멈춤을 처리하고 `inventoryBlocked`를 응답에 싣는다.
3. 시험을 새 규칙에 맞게 고친다(기존 시험 551줄 안에 보류·소멸 기대값이 있다).

크기: `auto-fill.ts` 350줄과 시험, DB 교체로 상한 초과 예상. 어려우면 «DB 교체»와 «TS 멈춤 분기»로 나눈다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)
- 시험에서 N개째 캡슐이 `insufficient_slots`이면 보관하지 않고 `inventory_blocked`로 멈춘다.
- 멈춘 캡슐은 가득 찬 채이고 지갑 잔여 잼이 변하지 않으며, 그때까지 열린 캡슐은 합쳐서 보인다.
- `capsule_forfeit` 신규 줄이 0건이다.
- 응답에 `inventoryBlocked`가 실린다.
- `_down.sql`이 302 본문을 복원한다(롤백 실측 기록).
- 줍기·미션 보상·믹스 결과 수령의 빈칸 검사 확인 결과가 티켓에 있다.
- `policiesData.ts`의 관련 항목이 갱신되어 있다.

### 후속 범위 (담당: 카리나, 시점: 배포 뒤)
- 232 계정 잼 2,640의 시험(Q4)은 사용자 승인을 받은 뒤에 한다.

선행: T1. 체크포인트: db 유형이므로 DB 단독 호출 전 사용자 확인.
