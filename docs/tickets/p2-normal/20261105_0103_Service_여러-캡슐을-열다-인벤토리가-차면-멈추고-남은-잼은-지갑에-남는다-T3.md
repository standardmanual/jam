# [Service] 여러 캡슐을 열다 인벤토리가 차면 거기서 멈추고 남은 잼은 지갑에 남는다 (T3)

## 핵심 요약

- 요구사항: 자동 채움이 여러 캡슐을 열다가 빈칸 부족(`insufficient_slots`)을 만나면 보상을 보관하지 않고 멈춘다(`stopped: 'inventory_blocked'`). 그 캡슐은 가득 찬 채 남고 지갑의 남은 잼은 그대로다. 소멸 분기와 단계 올림은 없앤다.
- 구현 계획: `capsule_auto_fill`(마이그레이션 301·302)을 같은 시그니처로 교체한다. 응답 키(`pendingCount`·`forfeited`·`alertStage`)는 유지하고 값을 고정(`pendingCount`=0 등)하며, 키 제거는 T6(축소)에서 한다. TS는 `auto-fill.ts`가 `inventory_blocked`로 멈추고 응답에 `inventoryBlocked: true`를 싣는다.
- 관련 파일: `jam-web/supabase/migrations/322_capsule_auto_fill_inventory_block.sql`과 `_down.sql`(302 본문 복원, 번호는 push 직전 재확인), `jam-web/src/lib/capsule/auto-fill.ts`, `sync-auto-fill.ts`, `capsule.ts`, 시험(`auto-fill` 계열), `policiesData.ts`

## 배경 / 문제 정의

지금은 열 수 없는 캡슐을 만나면 `capsule_hold_reward`로 보관하고, 보관이 2개가 되면 지갑 잼 전액이 사라진다(302). 한 번 막히면 아무것도 사라지지 않게 하는 사용자 결정에 맞춰, 보관 대신 멈추게 한다. 232 테스트 계정(캡슐 180/180, 인벤토리 9/30, 지갑 잼 2,640)은 이 구조가 들어간 뒤 다중 캡슐 정산과 막힘 안내를 시험하기 좋은 사례다(Q4, 실행은 사용자 승인 후).

## 상세 요구사항

### 서비스/코드베이스 관점
- 열린 캡슐은 지금처럼 합쳐서 «아직 보지 않은 결과» 한 건(`capsule_unseen_results`)으로 보인다.
- 지갑 잔여 잼은 불변이고 `capsule_forfeit` 신규 원장 줄이 0건이다.
- 줍기·미션 보상·믹스 결과 수령이 빈칸 부족일 때 각자 막히는지 읽어서 확인하고 결과를 티켓에 적는다.
- 이용 정지 중 캡슐 보류 규칙과 정책 대시보드 «보류 2개 잼 소멸»·«이용 정지 중 캡슐 보류» 항목을 같은 커밋에서 갱신한다.

## 구현 계획

1. `jam-web/supabase/migrations/322_capsule_auto_fill_inventory_block.sql`: `capsule_auto_fill(uuid)`를 같은 시그니처로 교체한다(302 본문 136~277줄 기준). `v_pending`·`v_forfeited`·`v_new_stage`와 `IF v_pending >= 2` 소멸 분기, `IF v_pending = 1` 단계 올림 블록을 없앤다. 잔액 읽기·채움·챕터 횟수·오름 판정은 그대로다. 응답 키는 모두 유지하되 `forfeited`=0, `pendingCount`=0, `alertStage`=null로 고정한다(키 제거는 T6). `_down.sql`은 302의 136~280줄 블록(함수와 COMMENT)을 그대로 복원한다. 시작 시 `capsule_pending_rewards` 행이 0이 아니면 예외로 중단하는 확인을 넣는다(읽은 값: 보류 0행, `capsule_forfeit` 0줄, `alert_stage`≠0 0행). 롤백 실측으로 N개째 캡슐 막힘과 잔액 불변을 시험한다.
2. `jam-web/src/lib/capsule/auto-fill.ts`(350줄): `holdReward`(168~183줄)와 `knownPending`·`needHold` 분기(232·268~326줄)를 없앤다. 열기가 `insufficient_slots`면 보관하지 않고 `stopped: 'inventory_blocked'`로 멈추며 캡슐은 가득 찬 채 남는다. `CapsuleAutoFillStop`에 `'inventory_blocked'`를 더하고 결과에 `inventoryBlocked: boolean`을 싣는다. `holds`·`forfeitedTotal`·`alerts`·`blockedNow`는 소비처(`sync-auto-fill.ts` 105~115줄이 `blockedNow`·`alerts`를 읽는다)가 T5까지 남아 있으므로 필드는 두고 값만 빈 배열·0·false로 고정한다. 머리말 주석을 새 규칙으로 고친다.
3. `jam-web/src/lib/capsule/sync-auto-fill.ts`: 새 멈춤 값을 알림 단계에서 무시하는지 확인하고 필요한 만큼만 고친다. 소식 발송 변경은 T5의 몫이다.
4. 시험: `jam-web/src/lib/capsule/__tests__/auto-fill.test.ts`(551줄)의 보류·소멸·단계 기대값을 «N개째에서 멈춤, 보관 없음, 지갑 잼 불변, 열린 캡슐은 합쳐서 보임, `inventoryBlocked` 응답»으로 바꾼다. 그 밖에 `holds`·`forfeitedTotal`·`alerts`를 기대하는 시험이 있으면 같이 고친다(`sync-auto-fill` 계열, `open.test.ts`, `serviceActivity.test.ts`).
5. `jam-web/src/lib/admin/policyDashboard/policiesData.ts`와 시험: `ch5-auto-fill`(394줄 일대), `ch5-pending-reward`(409줄 일대), «보류 2개일 때 잼 소멸»(444줄 일대), «이용 정지 중 캡슐 보류·잼 소멸·보류 받기»(1285줄 일대), 서비스 활동 잼 항목의 «열기 또는 보류 → 보류 2개면 소멸 → 단계 알림»(343줄 일대)과 챕터 횟수 항목의 «보류돼도 센다»(1099줄 일대)를 새 규칙으로 고친다. 받기(428줄)·소식(479줄)·위젯(512줄) 항목은 T4·T5의 몫이라 건드리지 않는다.
6. 줍기·미션 보상·믹스 결과 수령의 빈칸 검사를 코드에서 읽어 확인하고 결과를 이 티켓 완료 기록에 적는다.

크기: 파일 8개 이상, 변경 줄 수 상한 초과 예상. 위 계획을 첫 호출부터 `planOnlyWaiver` 사유로 쓴다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)
- 시험에서 N개째 캡슐이 `insufficient_slots`이면 보관하지 않고 `inventory_blocked`로 멈춘다.
- 멈춘 캡슐은 가득 찬 채이고 지갑 잔여 잼이 변하지 않으며, 그때까지 열린 캡슐은 합쳐서 보인다.
- `capsule_forfeit` 신규 줄이 0건이다.
- 응답에 `inventoryBlocked`가 실린다.
- `_down.sql`이 302 본문을 복원한다(롤백 실측 기록).
- 줍기·미션 보상·믹스 결과 수령의 빈칸 검사 확인 결과가 티켓에 있다.
- `policiesData.ts`의 관련 항목이 갱신되어 있다.
