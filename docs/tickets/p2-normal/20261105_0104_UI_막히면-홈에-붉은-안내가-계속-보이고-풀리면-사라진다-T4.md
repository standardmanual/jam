# [UI] 막히면 홈에 붉은 안내가 계속 보이고 풀리면 사라진다 (T4)

## 핵심 요약

- 요구사항: 막힌 계정의 홈에 안내 배너(제목·본문·«인벤토리 보기»)가 계속 보이고, 풀리면 사라진다. 캡슐 위젯의 보류 안내 4종은 «막힘» 한 종류로 정리한다.
- 구현 계획: T1의 `capsule_receive_blocked`를 홈 서버 데이터에 더해 배너를 그린다. 면 전체를 붉게 칠하지 않고 붉은 제목·아이콘 포인트로 시작하며, 채원 사전 판정과 윈터 톤 확인을 먼저 받는다.
- 관련 파일: `jam-web/src/app/(main)/SuspensionBanner.tsx`와 `jam-web/src/lib/suspension/home-banner.ts`(참고 선례), `jam-web/src/components/capsule/` 위젯, 홈 데이터 로더, `jam-web/src/lib/i18n/ko.ts`, `docs/service/writing/UX_WRITING_GUIDELINE.md` 「캡슐 위젯 안내 문구」 절(215줄 일대)

## 배경 / 문제 정의

사용자가 «붉은색 토스트를 상시 노출»하자고 했다. 서비스의 이용 정지 배너는 «면을 빨강·노랑으로 칠하지 않는다»(채원 판정 2026-10-17)와 «겁주지 않기»(운영 로직 18.2절)를 원칙으로 삼으므로, 붉은 면 여부를 채원이 판정한다. 사용자가 든 문구 «획득할 수 없습니다»는 합니다체라 해요체로 바꾼다(가이드). «토스트 상시 노출»은 «홈 상단 배너(상시) + 동기화 버튼을 눌렀을 때 토스트»로 나눈다(사용자 승인).

## 상세 요구사항

### UI/UX 관점
- 문구 시안(윈터 톤 확인 필요): 제목 «인벤토리가 가득 차서 잼을 얻을 수 없어요», 본문 «캡슐을 열려면 빈칸이 N개 필요해요. 인벤토리를 정리하면 다시 잼을 모을 수 있어요.», 링크 «인벤토리 보기».
- «빈칸 N개»는 부족분(`needed - free`)을 쓴다(Q7 추천).
- 노출 범위는 홈 배너 + 캡슐 위젯 + 동기화 버튼 토스트(Q6 추천).
- 풀리면 새로 읽기 1회 안에 사라진다.

## 사용자 결정과 채원·윈터 판정 (2026-11-05)

- 채원 사전 판정(모드 ①): 서비스 전용, 신규 컴포넌트 1개와 기존 부품 조합, 신규 토큰·MODULAR 승격 없음. 붉은 면은 쓰지 않는다. 승인 항목은 사용자가 아래처럼 정했다.
- 붉은 포인트: **아이콘만 붉게**(`text-danger` 경고 삼각형 20px). 제목 글자는 foreground다. 제목을 붉게 하면 흰 면 위 3.57:1이라 4.5:1에 못 미치고 상시 노출이라 피로가 쌓인다.
- 문구: **윈터 제3안**. 제목 «인벤토리에 빈칸이 필요해요» / 본문 «캡슐을 열 빈칸이 모자라서 잼 모으기가 잠시 멈췄어요. {N}칸만 더 비우면 바로 다시 모을 수 있어요.» / 버튼 «인벤토리 보기». {N}은 부족분 `max(1, needed - free)`다. 윈터 의견: «잼을 얻을 수 없어요»는 이미 모은 잼까지 사라지는 것처럼 읽히므로 쓰지 않고, 한 배너 안에서 원인 어휘를 «캡슐을 열 빈칸이 모자라서»로 통일한다.
- 위젯 중복: **홈에서만** 위젯의 빈칸 줄과 «인벤토리 보기» 버튼을 숨기고 안내를 한 줄(기존 «캡슐이 가득 찼어요»)로 줄인다. 내 프로필의 위젯은 지금처럼 둔다. 받기 버튼 제거는 T5이고 이 숨김과 파일은 겹치지만 대상(안내 줄·보기 버튼 대 받기 버튼)이 다르다.
- 배너 버튼은 primary(`surface="main"`, 검정 알약), 정지 배너와 겹치면 정지 배너만 그린다(상시 배너 최대 1개).

## 구현 계획

파일 단위 계획(카리나가 2026-11-05에 채원 판정의 변경 파일 지도를 옮겨 적었다). DB 변경은 없다.

1. `jam-web/src/lib/capsule/home-blocked-banner.ts`(신규, 서버 전용): `loadHomeCapsuleBlockedBanner(supabase, userId)`가 `readCapsuleReceiveBlocked`(`receive-block.ts`)를 불러 `blocked`면 `{ shortfall: Math.max(1, needed - free) }`, 아니거나 조회가 실패하면 null(`console.error`만, 던지지 않음)을 돌려준다. `jam-web/src/lib/suspension/home-banner.ts`와 같은 패턴이다.
2. `jam-web/src/app/(main)/CapsuleBlockedBanner.tsx`(신규, 클라이언트): `SuspensionBanner.tsx`와 같은 문법. `Card`(기본 톤) 안에 `AlertTriangleIcon`(`@/components/ui/icons`, `w-5 h-5 text-danger`, `aria-hidden`)과 제목(`<h2>`, foreground bold)을 한 줄 flex(`items-start gap-2`)로, 본문(`text-muted`), 전체폭 primary 버튼(`router.push('/inventory')`). `<section aria-labelledby>`, `role` 없음, 닫기 버튼·칩·애니메이션 없음. 서버 모듈을 가져오지 않고 `receive-block-contract.ts` 타입만 쓴다.
3. `jam-web/src/app/(main)/page.tsx`(54~143줄): `loadHomeSuspensionBanner` 옆에 막힘 배너 조회를 더해 병렬로 읽고, 정지 배너가 없을 때만 `CapsuleBlockedBanner`를 정지 배너 자리 바로 뒤에 그린다. 위젯 호출(143줄)에 홈 전용 prop을 넘긴다.
4. `jam-web/src/lib/capsule/capsule-contract.ts`의 `CapsuleNoticeKind`와 `capsule.ts`의 `getCapsuleStatus`·`toNotice`: 안내 종류 4종(`pending`·`pending_nearly_full`·`jam_blocked`·`full_waiting`)을 `blocked` 한 종류로 정리한다. 막힘 판정은 `readCapsuleReceiveBlocked`를 재사용한다(복제 금지). 이용 정지는 지금처럼 안내 없음이 우선이다. `capsule_pending_rewards`를 읽는 부분은 T5·T6의 몫이라 남겨 두되 `notice` 계산에는 쓰지 않는다.
5. `jam-web/src/components/capsule/CapsuleWidget.tsx`(41~64·166~194줄): `noticeText`·`gaugeAriaLabel`을 `blocked` 한 종류로 줄이고, 홈 전용 prop(예 `hideBlockedAction`)이 참이면 빈칸 줄과 «인벤토리 보기» 버튼을 숨기고 한 줄만 보인다. 프로필 쪽 호출은 prop 없이 지금처럼 둔다. «받기» 버튼은 건드리지 않는다(T5).
6. `jam-web/src/lib/i18n/ko.ts`: `d.capsule.blockedBanner`(`title`·`body`(N 보간)·`cta`)를 더하고, T1이 넣은 `capsuleReceiveBlock.syncBlocked`(동기화 토스트)를 같은 톤으로 고친다: «잼 모으기가 잠시 멈췄어요. 인벤토리를 정리하면 다시 동기화할 수 있어요.»(«잼을 얻을 수 없어요»·«인벤토리» 중복을 없앤다).
7. `docs/service/writing/UX_WRITING_GUIDELINE.md`(215줄 일대 「캡슐 위젯 안내 문구」): 표를 `blocked` 한 종류로 갱신하고 배너·토스트 문구를 더한다.
8. `jam-web/src/lib/admin/policyDashboard/policiesData.ts`와 시험: 위젯 안내 항목(512줄 일대)을 새 규칙으로 갱신한다(같은 커밋).
9. 시험: `CapsuleBlockedBanner` 시험(문구·N·링크·아이콘 `aria-hidden`), `home-blocked-banner` 시험(blocked·아님·실패→null·N 최소 1), `CapsuleWidget` 시험(홈 prop으로 줄과 버튼 숨김, 프로필은 유지), `capsule.ts` 안내 종류 시험, 홈 `page` 시험이 있으면 정지와 겹침 시나리오.

크기: 파일 12개 안팎, 변경 줄 수 상한 초과. 위 계획을 첫 호출부터 `planOnlyWaiver` 사유로 쓴다.
