# [Feature] «받기»와 못 받은 보상 흐름을 걷어 낸다 (T5)

## 핵심 요약

- 요구사항(Q10 개정): 캡슐 위젯의 «받기» 버튼, `POST /api/capsule/claim`, 소식 `capsule_nearly_full`(70·80·90% 단계) 발송을 없앤다. **보관 표(`capsule_pending_rewards`)와 보류·지급 함수는 R1·R2가 다시 쓰므로 남기고, 지급 로직(`claim.ts`)은 R2가 자동 지급으로 옮긴 뒤에 받기 전용 부분만 지운다.** 막히는 순간 소식은 Q5 결정대로 한 번만 보낸다. 보류를 읽던 화면도 새 구조에 맞춰 정리한다. 선행은 R2, R3다.
- 구현 계획: 두 묶음으로 나눌 수 있다. ① API·위젯(`claim.ts`와 시험 삭제, 라우트 삭제, 위젯 버튼 삭제), ② 소식·신호(`dailySignals`, `today/exposure`, 어드민 홈 미리보기, 소식 발송부).
- 관련 파일: `jam-web/src/lib/capsule/claim.ts`(191줄)와 시험(253줄), `jam-web/src/app/api/capsule/claim/`, `jam-web/src/components/capsule/` 위젯, 소식 발송부(`capsule_nearly_full`·`capsule_jam_blocked`), `dailySignals`, `today/exposure`, `docs/service/prd/notification/PRD.md` 53·54번

## 배경 / 문제 정의

T3 이후 보관 구조는 더 쓰이지 않는다. DB를 걷어 내는 T6 전에 코드가 보관 표·함수를 부르지 않게 먼저 전환해야 한다(확장→전환→축소 분할).

## 상세 요구사항

### 서비스/코드베이스 관점
- 과거에 만들어진 소식 행(`capsule_nearly_full`)은 깨지지 않고 표시되어야 한다. enum 값은 지우지 않는다.
- `capsule_jam_blocked` 소식을 «막히는 순간 한 번»으로 의미를 바꿔 재사용할지는 Q5(추천: 재사용). 반복 발송이 없어야 한다.
- 카즈하 일일 요약의 «소멸» 신호는 항상 0이 되므로 «막힌 유저 수»로 바꿀지 카즈하와 확인한다.
- 알림 PRD 53·54번과 구현 상태 문단은 이 티켓에서 갱신하거나 T7에 남긴다.

## 구현 계획

1. (Q10 개정) `capsule_hold_reward`·`capsule_claim_pending`·`capsule_pending_rewards` 호출은 걷지 않는다. 받기 버튼·API·단계 소식·`user_capsules.alert_stage` 쓰기만 걷는다.
2. 소식 발송과 보류를 읽던 화면을 정리한다.
3. 같은 커밋에서 `policiesData.ts`의 알림(479~484줄 일대)·보관·받기(417~435줄 일대) 항목을 갱신한다.

크기: 삭제 줄이 많아 상한 초과 예상. 면제하거나 둘로 나눈다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)
- 위젯에 «받기» 버튼이 없고 `POST /api/capsule/claim`과 `claim.ts`가 없다.
- `capsule_nearly_full` 소식이 더는 발송되지 않고, 오래된 소식 행이 깨지지 않고 표시된다.
- 막히는 순간의 소식이 Q5 결정대로 한 번만 간다.
- 보류를 읽던 화면(`dailySignals`, `today/exposure`, 어드민 홈 미리보기)이 정리되어 있다.
- 코드 전수 검색에서 `capsule_hold_reward`·`capsule_claim_pending` 호출이 0건이다.

선행: T3, T4. DB 변경 없음. 사용자 확인 필요 지점은 없으나 T6의 선행이다.

## 완료 기록

> **Q10 개정(2026-11-05)으로 위 «배경»·«구현 계획»의 일부는 무효다.** 보관 표 `capsule_pending_rewards`와 보류·지급 함수는 지우지 않고 R1·R2가 다시 쓴다. 그래서 «코드에서 보류 함수 호출을 모두 걷어 낸다»와 «claim.ts·`capsule_claim_pending` 호출 0건»은 적용하지 않았다. 아래가 실제로 한 일이다.

### 구현 내용 요약
- 받기 제거: 위젯의 «받기» 버튼·`runClaim`·획득 연출과 `claim.available`, `POST /api/capsule/claim` 라우트와 시험, `capsule-client`의 `claimCapsule`, `capsule-flow.ts`, 받기 전용 계약 타입, `ko.ts`의 `claim*` 문구를 지웠다. 위젯에는 막힘 문구와 빈칸 줄, «인벤토리 보기»만 남았다.
- 소식·단계: `notifyCapsuleAlerts`와 자동 채움 결과의 `holds`·`forfeitedTotal`·`alerts`·`blockedNow`를 지웠다. `GET /api/capsule` 응답에서 `alertStage`와 `alert_stage` 읽기를 뺐다. 소식 enum과 문구는 남겨 과거 행이 표시되고 `NotificationsClient` 시험이 이를 고정한다.
- 일일 요약: `dailySignals`와 `cron/capsule-signals`에서 소멸 신호를 지웠다.
- `claim.ts`의 `claimPendingCapsules`는 R2의 `settle-pending.ts`가 쓰는 자동 지급이라 그대로 뒀다.
- 정책 대시보드 `ch5-claim-pending`·`ch5-capsule-alerts`, 알림 PRD 53·54번, 홈피드 PRD, 인벤토리 PRD §10, `02_DATA_MODEL`, 운영 로직 5.3·15.4·4.5절, `04_PROJECT_SPEC` cron 설명을 맞췄다.
