# [Service] 빈칸이 모자라면 먼저 추첨해 대기 보상으로 저장하고 멈춘다 (R1)

## 핵심 요약

- 요구사항: 캡슐이 가득 차 열어야 하는데 인벤토리 빈칸이 모자라면, 열지 않고 두는 대신 **그 자리에서 추첨해 결과를 보류 표(`capsule_pending_rewards`)에 저장**하고 자동 채움을 멈춘다. 남은 잼은 지갑에 남는다. 막힘 판정은 「대기 보상이 있음」으로 바꾼다. 대기 보상은 기한 없이 남고 소멸하지 않는다.
- 구현 계획: ① 막힘 판정 DB 함수 `capsule_receive_blocked`(마이그레이션 320)를 대기 보상 기준으로 교체한다. 반환 `{blocked, pending, free, needed, shortfall}`이고 `needed`는 대기 개수다. ② 자동 채움의 «빈칸 부족이면 멈춘다»(마이그레이션 322, `stopped: 'inventory_blocked'`)를 «추첨해 `capsule_hold_reward`로 저장한 뒤 멈춘다»로 바꾼다. 대기 보상이 이미 있으면 채움을 시작하지 않는다. ③ 열기 모듈의 «빈칸이 모자라면 추첨하지 않는다» 사전 확인을 걷는다.
- 관련 파일: `jam-web/supabase/migrations/320_capsule_receive_blocked.sql`, `322_capsule_auto_fill_inventory_block.sql`, `302_capsule_pending_forfeit.sql`(보류 함수의 옛 정의), 새 마이그레이션 `323_*`과 `_down.sql`, `jam-web/src/lib/capsule/open.ts`(사전 확인 구간), `auto-fill.ts`(`stopped` 처리), `receive-block.ts`·`receive-block-contract.ts`, `capsule.ts`(`getCapsuleStatus`), `capsule-contract.ts`

## 배경 / 문제 정의

T3까지는 빈칸이 모자라면 캡슐을 열지 않고 가득 찬 채 둔다. 그러면 사용자에게 «배지 n개를 얻었다»고 말할 수 없고(추첨 전이라 n이 없다), 막힘이 풀려도 다음 동기화까지 캡슐이 열리지 않는다. 사용자 결정 Q10(상위 티켓)으로 먼저 추첨해 저장하는 구조로 바꾼다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 막힘 판정: `blocked = 대기 보상 행이 1건 이상`. 반환에 `pending`(대기 개수)과 `shortfall`(`max(0, pending - free)`)을 더하고, 기존 키 `free`·`needed`는 유지한다(`needed`는 대기 개수).
- 대기는 한 캡슐분(1~2개)까지만 쌓인다. 대기가 있으면 자동 채움은 새 캡슐을 열지 않고 `stopped: 'inventory_blocked'`로 멈춘다.
- 열려는 순간 빈칸이 충분하면 지금처럼 바로 지급한다(대기 없음).
- 보류 함수가 캡슐 소진, 다음 캡슐 필요량, 챕터 횟수를 어떻게 다루는지 302와 300 정의를 읽어 확인한다(미확인). 열기와 같은 기록이 남아야 한다.
- 소멸(잼 전액)은 되살리지 않는다. 322가 걷어 낸 단계 올림도 되살리지 않는다.
- DB는 SQL 파일 작성 뒤 카리나가 실행한다. 되돌림 SQL(`323_*_down.sql`)과 롤백 실측이 필수다.

## 구현 계획

**확인된 사실(카리나 조사 2026-11-05)**: 지금 보류 표 한 줄(`capsule_pending_rewards`: user_id, slot, chapter_no, fill_amount, reached_at)은 «가득 찬 캡슐 자체»를 옮겨 둔 것이고 **추첨 결과를 담지 않는다.** `capsule_hold_reward(uuid)`(302 6절)는 가득 찬 캡슐을 빈 slot으로 옮기고 새 캡슐(v2, filled=0)을 만든다. 추첨은 받을 때 `claim.ts`가 `rollCapsuleItems`(`open.ts` 191줄 부근)로 하고 `capsule_claim_pending(uuid, uuid, jsonb)`에 `p_items`로 넘긴다. 받기는 빈칸 ≥ `guaranteed_count + bonus_count`(최대 개수)를 요구한다. 열기는 `openCapsule`(`open.ts` 약 270줄)이 사전 확인으로 `no_free_slots`면 추첨 없이 `insufficient_slots`를 던지고, `auto-fill.ts` 254~256줄이 그걸 받아 `inventory_blocked`로 멈춘다.

**새 구조**: 보류 줄에 **추첨 결과를 같이 저장**한다.

1. **마이그레이션 `323_capsule_pending_drawn_items.sql`(+ `_down.sql`)**, 확장만:
   - `capsule_pending_rewards`에 `drawn_items JSONB`(NULL 허용, 추첨 결과 배열. `toRpcItems` 모양 그대로: badge_id·rarity·rolled_rarity·locked·lock_reason·unlock_required)를 더한다. 옛 행(현재 0건)은 NULL이면 기존 최대 개수로 다룬다.
   - 새 함수 `capsule_hold_rolled(p_user_id UUID, p_items JSONB) RETURNS JSONB`: `capsule_hold_reward`와 같은 잠금 순서·검사(정지, 캡슐 행 잠금, `not_full`)를 하고, 보류가 이미 있으면 `pending_exists`로 거절하며(대기는 한 캡슐분만), 보류 줄에 `drawn_items`를 넣고 새 캡슐을 만든다. 반환 `{ok, pendingItemCount, next{required, filled, chapterNo}}`. `capsule_hold_reward`는 시그니처를 바꾸지 않는다.
   - `capsule_receive_blocked(uuid)` 교체(같은 시그니처): `blocked = 보류 줄이 있음`. 반환 `{blocked, pending, free, needed, shortfall}`. `pending`(= `needed`) = 보류의 `drawn_items` 길이 합(NULL이면 `guaranteed_count + bonus_count`), `shortfall = max(0, needed - free)`. 정책·캡슐·인벤토리 행이 없으면 막지 않는다(320과 같다).
   - `capsule_auto_fill`(322 교체본)은 **보류가 있으면 채우지 않고** 멈춘다는 반환 키(`pendingCount` 기존 키 재사용)를 확인하고, 필요하면 같은 시그니처로 교체한다. 소멸은 되살리지 않는다.
2. **`open.ts`의 `openCapsule`**: 사전 확인에서 `no_free_slots`로 던지는 대신 추첨(`rollCapsuleItems`)을 먼저 한다. 빈칸 ≥ 뽑힌 개수면 지금처럼 `capsule_open_counted`로 바로 지급한다. 빈칸 < 뽑힌 개수면 `capsule_hold_rolled`를 불러 저장하고, 호출부가 구분할 수 있게 결과에 `held: true`와 뽑힌 개수를 싣는다(새 반환 변형 타입 `CapsuleHeldPayload`를 `capsule-contract.ts`에 더한다). `capsule_open_counted`/`capsule_open`이 빈칸을 «최대 개수»로 보는지 «뽑힌 개수»로 보는지 233·234 정의를 읽고 확인한다(미확인, 최대 개수라면 이번에 뽑힌 개수로 낮추는 교체가 필요하다).
3. **`auto-fill.ts`**: `openCapsule`이 `held`를 돌려주면 `inventoryBlocked: true`, `stopped: 'inventory_blocked'`로 멈춘다(254~256줄 갈래를 대체). 시작 단계에서 보류가 있으면 채우지 않고 같은 이유로 멈춘다. 지갑 잔액은 건드리지 않는다. `sync-auto-fill.ts`가 이 신호를 쓰는 곳을 확인한다.
4. **`receive-block.ts`·`receive-block-contract.ts`·`home-blocked-banner.ts`·`capsule.ts`(`getCapsuleStatus`)**: 새 반환 키 `pending`·`shortfall`을 읽고 계약 타입에 더한다. 화면 문구는 R3이 바꾼다.
5. **시험**: 빈칸 충분(바로 지급, 보류 없음), 빈칸 부족(1개 뽑힘/2개 뽑힘, 보류 저장, 캡슐 소진, 지갑 잼 불변), 보류 있음(채움 안 함), 막힘 판정 개정, 기존 막힘 시험 개정.
6. 같은 커밋에서 `policiesData.ts`(보관·막힘·소멸 항목)와 운영 로직 문서 5.2절·6장·15.4절을 갱신하고 타입을 MCP `generate_typescript_types`로 대조해 `database.generated.ts`에 반영한다.

크기: 마이그레이션 2개 + TS 6~8파일 + 시험 + 문서로 `plan_only` 상한을 넘기므로 처음부터 `planOnlyWaiver`를 준다(위 계획이 파일 단위다).

### 주요 의사결정 / 핵심 메모
- `capsule_open`이 빈칸을 최대 개수로 봤던 것을 뽑힌 개수로 낮췄다. 최대 개수 기준이면 1개가 뽑힌 유저도 빈칸 2칸이 있어야 열렸다. 뽑힌 개수가 최대 이하라 옛 코드에는 완화일 뿐이다.
- 대기는 한 캡슐분만 쌓는다(`pending_exists`). 보류가 있으면 자동 채움이 멈추므로 두 번째 캡슐이 열릴 일이 없다.
- 경쟁으로 `capsule_open_counted`가 `insufficient_slots`를 돌려주면 `blocked`로 멈추고 캡슐은 가득 찬 채 남는다(드문 경로, 다음 호출에서 다시 판정).
