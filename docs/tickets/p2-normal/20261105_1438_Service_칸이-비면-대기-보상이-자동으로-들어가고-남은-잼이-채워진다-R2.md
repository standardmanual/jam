# [Service] 칸이 비면 대기 보상이 자동으로 들어가고 남은 잼이 채워진다 (R2)

## 핵심 요약

- 요구사항: 대기 보상이 있고 빈칸이 대기 개수 이상이 되면, 사용자가 아무것도 누르지 않아도 **대기 보상이 인벤토리에 들어가고, 이어서 지갑에 남은 잼으로 다음 캡슐이 자동으로 채워진다.** «받기» 버튼은 필요 없다.
- 구현 계획: ① 지급: 기존 `capsule_claim_pending`(또는 같은 일을 하는 새 함수)를 자동 호출한다. ② 호출 지점: 칸이 줄어드는 서버 경로 뒤에 공통 도우미 `settleAfterSlotsFreed(userId)`를 부른다. 그 안에서 지급 후 자동 채움(`auto-fill.ts`)을 한 번 돈다. ③ 따라잡기: 홈 조회와 동기화 시작 때도 같은 도우미를 불러, 어떤 경로로 칸이 비었든 늦어도 다음 접속에는 지급되게 한다.
- 관련 파일: `jam-web/src/lib/capsule/claim.ts`(지급 로직의 재사용 원본, 191줄), `auto-fill.ts`, `sync-auto-fill.ts`, `jam-web/src/lib/inventory/slots.ts`, 칸이 줄어드는 경로: `src/app/api/itembooks/[id]/slots/route.ts`(꽂기), `src/lib/combine/`(`burn.ts`·`index.ts`·`tierUp.ts`·`pending.ts`), 내려놓기·버리기를 처리하는 `src/app/api/inventory/`, 어드민 `src/lib/admin/user-actions.ts`·`orphaned-item-actions.ts`. 칸을 줄이는 DB 함수는 마이그레이션 108·111·157·178·179에 있다.

## 배경 / 문제 정의

R1로 대기 보상이 생기면 풀려도 사용자가 «받기»를 알아야 하는 옛 구조로 돌아간다. 사용자 결정 Q10은 풀림과 동시에 자동 지급과 채움이다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 지급은 빈칸이 대기 개수 이상일 때만 한다(부분 지급 없음). 지급은 DB 함수 하나로 원자적으로 한다. 이중 지급이 없어야 한다(같은 대기 행을 두 요청이 동시에 지급하려는 경우 잠금).
- 칸이 줄어드는 경로 목록은 구현 첫 단계에서 전수 조사해 티켓에 적는다(위 목록은 출발점이다). 모든 경로에 일일이 붙이는 대신 DB 트리거로 지급만 하는 방안은 조사 뒤 비교한다(자동 채움의 추첨은 TS에 있어 트리거에서 못 한다).
- 자동 채움 직후 챕터 오름·소식은 기존 `auto-fill.ts` 흐름 그대로 처리한다.
- **지급 결과는 따로 보여 주지 않는다(사용자 결정 2026-11-05).** 열기 연출·토스트·소식 없이 인벤토리에 배지가 들어와 보이는 것으로 끝이다. 그래서 자동 지급은 새 UI가 없다. 단 지급 후 처리(포인트·`recordIssuedRewards`는 피드 제외로 기존 열기와 같게)는 그대로 한다.
- 보류 줄의 `drawn_items`(R1이 저장)로 지급한다. `capsule_claim_pending`을 «저장된 항목으로 지급, 빈칸 ≥ 저장된 개수이면 지급»으로 교체하거나 새 함수로 만든다(지금은 `p_items`를 받고 빈칸 ≥ 최대 개수를 요구한다). TS는 저장된 `badge_id`로 `CapsuleBadge`를 다시 읽어 `recordOpenedItems`에 넘긴다(`claim.ts`의 방식을 따른다).
- 이용 정지, 트라이브 없음이면 지급하지 않는다.

## 구현 계획

**전제(R1 완료, DB 323 적용됨)**: 보류 줄에 `drawn_items`(추첨 결과)가 저장된다. `capsule_receive_blocked`는 `{blocked, pending, free, needed, shortfall}`을 돌려주고, 보류가 있으면 `capsule_auto_fill`이 채우지 않는다.

**칸이 줄어드는 경로(카리나 조사 2026-11-05, 출발점)**: DB 함수는 마이그레이션 108(내려놓기/회수 계열 277줄), 111·157·178·179·222(책에 꽂기), 173(`release` 계열, 99줄), 238·239(드랍 만들기·줍기). API 라우트: `src/app/api/itembooks/[id]/slots/route.ts`, `itembooks/[id]/slot/route.ts`, `drops/route.ts`(POST, 내려놓기), `drops/[dropId]/route.ts`, `combine/route.ts`, `combine/tier-up/route.ts`, `combine/pending/route.ts`, `inventory/items/[itemId]/open/route.ts`, 어드민 `src/lib/admin/user-actions.ts`·`orphaned-item-actions.ts`. 아현은 구현 첫 단계에서 이 목록을 코드로 확인하고, 실제로 `used_slots`를 줄이는 경로만 골라 티켓 「완료 기록」에 적는다.

1. **마이그레이션 `324_*.sql`(+ `_down.sql`)**, 같은 시그니처 교체 한 개: `capsule_claim_pending(uuid, uuid, jsonb)`(302 7절)를 바꾼다. ① 보류 줄에 `drawn_items`가 있으면 그것을 지급 항목으로 쓰고(`p_items`는 무시) 없으면(옛 줄) `p_items`를 쓴다. ② 빈칸 검사를 «최대 개수»에서 «지급할 항목 수»(`v_n`)로 낮춘다. ③ 나머지(잠금 순서, 지급, `item_issue_log`·`user_drop_state`·`capsule_opens` 기록, 보류 줄 삭제)는 302와 같다. 번호는 원격 staging 기준으로 다시 확인한다(323 다음).
2. **`src/lib/capsule/claim.ts`(191줄)**: 추첨 대신 저장된 `drawn_items`로 지급한다. 저장된 `badge_id`로 `CapsuleBadge`를 읽어 `rollCapsuleItems`가 만드는 `rolled` 모양(`RolledCapsuleItem`: badge·rarity·rolledRarity·lock·tribeId)을 다시 만들어 `recordOpenedItems`(`open.ts`)에 넘긴다. 지급 직후 `notifyInventorySlotsLow`를 부른다. 옛 줄(`drawn_items` NULL)은 지금처럼 받을 때 추첨하고 최대 개수 빈칸을 요구한다(현재 0건). 함수 이름·반환 모양은 `POST /api/capsule/claim`과 위젯 «받기»가 컴파일되도록 유지한다(T5가 지운다).
3. **새 파일 `src/lib/capsule/settle-pending.ts`**: `settleAfterSlotsFreed(supabase, userId): Promise<void>`, **던지지 않는다**. ① 보류 줄이 없으면 바로 끝낸다(가벼운 존재 확인 한 번). ② 있으면 빈칸 ≥ 저장된 개수일 때만 `claim.ts`의 지급 함수를 부른다. ③ 지급했으면 이어서 `runCapsuleAutoFill`(`auto-fill.ts`)로 지갑에 남은 잼을 채운다. ④ 같은 프로세스에서 같은 유저의 동시 호출은 한 번만 돌린다(`auto-fill.ts`의 `busy` 방식을 따른다). 이중 지급은 DB의 보류 줄 잠금이 막는다.
4. **호출 지점**: (a) 위 경로 중 실제로 칸을 줄이는 라우트 핸들러 끝(응답 직전)에서 부른다. (b) **따라잡기**: 홈(`src/app/(main)/page.tsx`가 `loadHomeCapsuleBlockedBanner`를 읽기 전), `GET /api/capsule`(캡슐 상태 조회 라우트), 동기화 입구 막힘 검사(`src/lib/strava/sync.ts`의 `capsule_inventory_blocked` 409 앞)에서 부른다. 어떤 경로로 칸이 비었든 늦어도 다음 접속에는 지급된다. 막힘 검사는 지급 시도 뒤에 다시 읽는다.
5. **보여 주기**: 별도 연출·토스트·소식을 만들지 않는다(사용자 결정). 인벤토리에 배지가 들어와 보이는 것으로 끝이다.
6. **시험**: 지급 성공(저장된 항목 그대로, 포인트 후속 처리 호출), 빈칸 부족이면 지급 안 함, 동시 호출 이중 지급 없음, 지급 뒤 자동 채움 호출, 이용 정지·트라이브 없음이면 지급 안 함, 옛 줄(NULL) 경로, 라우트 호출 지점 시험, 동기화 입구 시험 개정.
7. 같은 커밋에서 `policiesData.ts`(`ch5-pending-reward`, `ch5-inventory-full-block`; `ticketId`를 이 티켓으로)와 운영 로직 문서 5.2절을 갱신하고, 마이그레이션 뒤 MCP `generate_typescript_types`로 `database.generated.ts`를 대조한다.

크기: 마이그레이션 1개 + TS 8~12파일 + 시험으로 상한을 넘기므로 처음부터 `planOnlyWaiver`를 준다. 둘로 쪼갤 경우 («지급 함수·도우미» / «호출 지점 붙이기»)로 나눈다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)
- 빈칸이 대기 개수 이상이 된 뒤 칸이 줄어드는 서버 경로를 한 번 지나면, 대기 보상이 인벤토리에 들어가고 `capsule_pending_rewards` 행이 0건이 된다.
- 같은 유저에게 지급을 동시에 두 번 요청해도 보상이 한 번만 들어간다.
- 지급 직후 지갑에 남은 잼이 있으면 다음 캡슐이 채워진다(232 시험: 240 → 60 채움).
- 빈칸이 부족하면 지급하지 않고 대기 보상이 그대로 남는다.
- 이용 정지 유저에게는 지급하지 않는다.

### 후속 범위 (담당: 카리나, 시점: 머지 뒤)
- 232 계정 재설정(지갑 잼 240)과 사용자 시험 안내.
