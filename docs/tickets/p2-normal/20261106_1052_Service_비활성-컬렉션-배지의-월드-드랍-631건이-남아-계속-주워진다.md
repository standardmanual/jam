# [Service] 비활성 컬렉션 배지의 월드 드랍 631건이 남아 계속 주워진다

## 완료 기록 (폐기·대체, 2026-11-06 KST)

- **결과: 구현하지 않고 폐기했다. 이 티켓의 방향(비활성 컬렉션의 월드 드랍을 내린다)은 사용자 결정으로 뒤집혔다.**
- 사유: 구현·게이트 리뷰(WARN)까지 끝난 뒤 사용자가 전제를 바로잡았다. «어드민에서 컬렉션을 비활성하는 것은 신규로 아이템 배지를 생성해 발급하는 것을 막는 것이다. 이미 드랍됐거나 유저가 소유한 것은 보여야 한다.» 따라서 월드 드랍·보유 개체는 소각 대상이 아니라 **보여야 하는 것**이고, 원인은 `badges` 읽기 정책이 비활성 컬렉션 배지를 모두에게 숨기는 데 있다.
- 폐기한 산출물: 리뷰 브랜치 `claude/jamwork-20261106_1052-close-inactive-collection-drops`(커밋 3개, 마이그레이션 326 정리 함수·트리거·`expire_stale_poi_drops()` 확장, 크론 로그, 정책 항목, 문서 5곳). **머지하지 않았고 DB에 실행하지 않았다.** 브랜치는 원격에 남아 있으며 지워도 된다.
- 되돌린 것: 부모 티켓 20261106_1044의 마이그레이션 325가 파괴한 개체 21개를 같은 날 복구했다(325 되돌림 SQL 실행, 일련번호 충돌 0건). 5개 인벤토리가 원래 값(13/30·10/10·10/10·4/10·10/10)으로 돌아왔고 `AdminDestroy` 이력 21건도 지웠다. 파일 `325_..._down.sql`은 그대로 남긴다.
- 대체 티켓: 20261106_1124(1단계: 배지 읽기 정책), 20261106_1125(2단계: 컬렉션 화면·장착).
- 이 티켓에서 얻은 사실(후속이 쓴다): 매일 0시 `expire_stale_poi_drops()`는 «삭제된 배지(`deleted_at`)»의 미픽업 드랍만 소각한다. `item_books`에는 트리거가 없다. 어드민의 `drop_excluded`(컬렉션 전체 드랍 제외)는 이미 «화면·보유는 두고 신규 드랍에서만 뺀다»는 뜻이다. 기간이 끝났는데 켜져 있는 컬렉션은 0개였다.

## 핵심 요약

- 현상: 어드민에서 끈 컬렉션(`item_books.is_active = false`)의 아이템 배지가 월드에 아직 떨어져 있고(`poi_drops.is_available = true`, `picked_up_at IS NULL`), 사용자가 주우면 읽기 정책이 숨기는 개체가 칸만 차지한다. 2026-11-06 측정: 631건(시스템 611·사용자 20), 모두 비활성 컬렉션 소속이고 만료 시각이 없다.
- 요구사항(사용자 2026-11-06 결정): **컬렉션을 비활성하면 그 컬렉션 배지의 미픽업 월드 드랍을 함께 내린다.** 유저가 소유한 개체와 컬렉션 진행 기록은 건드리지 않는다. 다시 켜도 드랍을 복구하지 않는다. 기간이 끝난 컬렉션도 «비활성» 취급이다(기간 종료 때 `is_active`를 자동으로 끄는 장치는 코드에 아직 없다. 이 티켓은 그 장치를 만들지 않고, 매일 0시 정리가 «기간이 끝난 컬렉션»도 함께 거른다).
- 구현 계획(요지): ① 정리 함수 하나 신설 ② `is_active`가 true→false가 되는 순간 그 컬렉션 대상으로 즉시 호출하는 트리거 ③ 매일 0시 `expire_stale_poi_drops()`가 전체 대상으로 한 번 더 호출(안전망, 기간 종료 포함) ④ 크론 응답·로그에 새 건수 추가 ⑤ 정책 대시보드·문서 갱신. 내려갈 때는 기존 만료와 같은 방식으로 개체를 파괴한다(어드민 «소유자 없음» 목록에 남지 않게 한다).
- 관련 파일(지도): 아래 「구현 계획」.

## 배경 / 문제 정의

- 부모 티켓 20261106_1044에서 비활성 컬렉션 배지의 보유 개체 21개를 정리했다(마이그레이션 325). 월드 드랍이 남아 있으면 같은 개체를 다시 줍는다.
- 원인: 줍기 함수는 장소가 켜져 있는지만 보고 컬렉션이 켜져 있는지는 보지 않는다(306번 71행). 컬렉션 `is_active`를 끌 때 소속 배지의 월드 드랍을 내리는 연쇄는 티켓 20260914_1729에서 배지 연쇄 소프트삭제와 함께 폐지돼 지금은 없다. 배지 폐기(`deleted_at`) 쪽은 단건·일괄 API(`invalidateUnclaimedDrops`)와 매일 0시 크론 안전망(`expire_stale_poi_drops()` 두 번째 루프)이 이미 드랍을 내린다.
- 구성(2026-11-06): `편의점 심야 만찬` 시스템 드랍 500건(장소 500곳, 2026-09-09~10-02), 그 밖의 시스템 드랍 111건, 사용자 드랍 20건. 켜진 컬렉션 중 드랍이 있는 것은 `시장 골목의 전설`·`무명을 쫓는 야식가들`(둘 다 오픈 첫 공개 15개)뿐이다. 기간이 끝났는데 켜져 있는 컬렉션은 0개, 아직 열리지 않은 컬렉션(`valid_from` 미래)도 0개다.
- `item_books`에는 트리거가 하나도 없다(2026-11-06 확인).

## 결정 / 검토한 대안

- **채택: 컬렉션 비활성 시 미픽업 드랍을 파괴(기존 만료 방식).** 다시 켜도 복구하지 않기로 했으므로(사용자 결정), 개체를 살려 두면 어드민 «소유자 없음»(`deriveItemBadgeStatus`가 활성 드랍이 없는 주인 없는 개체를 `Orphaned`로 판정)에 631건이 나타난다. 그래서 `expire_stale_poi_drops()`와 같이 `is_available=false`, 개체 `destroyed_at`·`inventory_id=NULL`, `custody_events 'Expire'`로 처리한다.
- **트리거와 크론을 함께 둔다.** 토글 경로가 여럿이다(어드민 PATCH, 전체 저장 PUT, 오픈 SQL 292, 운영 묶음 실행기). 앱 코드에 넣으면 놓치므로 DB 트리거로 `is_active` true→false 전환을 잡는다. 기간 종료는 사건이 없어 트리거가 못 잡으므로 매일 0시 크론이 대신 거른다(최대 하루 늦다).
- 미채택 ① 줍기 때 컬렉션 상태를 읽어 거르는 안: 되돌릴 일이 없는 장점이 있으나 사용자가 «켜도 복구 불필요»를 택해 필요 없어졌다. 상태 읽기 안은 줍기·지도 목록 세 군데를 고쳐야 한다. ② 배지 일괄 비활성(`deleted_at`): 예약 컬렉션 오픈 계획(292)과 충돌하고 칸 수도 풀지 못한다(티켓 20261106_1044 참고).
- **범위 밖(알려 둔다):** 컬렉션이 이미 꺼진 뒤 새로 생기는 드랍(예: 사용자가 이미 가진 비활성 컬렉션 개체를 내려놓는 경우)은 다음 0시 크론이 정리할 때까지 남는다. 줍기 차단은 이번에 하지 않는다. 아직 열리지 않은 컬렉션(`valid_from` 미래)의 드랍은 대상에 넣지 않는다.

## 상세 요구사항

### 데이터/DB 관점
- 정리 대상 한 건의 정의: `poi_drops.is_available = true AND picked_up_at IS NULL`이고 그 드랍 배지의 컬렉션이 `is_active = false` **또는** (`valid_until IS NOT NULL AND valid_until < now()`)인 것. `item_book_id`가 NULL인 배지(체크인·활동 배지 등)는 대상이 아니다.
- 유저가 소유한 개체(`inventory_id IS NOT NULL`)·장착 슬롯·컬렉션 완성 기록·포인트 원장은 건드리지 않는다. 대상은 오직 `picked_up_at IS NULL`인 드랍 행과 그 드랍이 가리키는 개체뿐이다.
- 되돌림 SQL: 새 객체 삭제, `expire_stale_poi_drops()`를 직전 본문으로 복원. **파괴한 개체·내린 드랍은 되돌림 SQL이 되살리지 않는다**(복구 불필요가 결정이므로). 기존 631건은 정리 직전에 백업 표에 담아 별도 복구 SQL을 남긴다(카리나, 4단계).

## 구현 계획

아현은 아래 파일만 만든다. 번호 326은 현재 `origin/staging` 최신이 325라서 쓴 값이며 push 직전에 다시 확인한다. DB는 실행하지 않는다.

1. **`jam-web/supabase/migrations/326_close_unclaimed_drops_of_inactive_collections.sql`** (신규)
   - `public.close_unclaimed_drops_of_inactive_collections(p_item_book_id uuid DEFAULT NULL) RETURNS integer`, `LANGUAGE plpgsql SECURITY DEFINER SET search_path TO 'public'`. `poi_drops pd JOIN badges b ON b.id = pd.badge_id JOIN item_books ib ON ib.id = b.item_book_id`에서 위 정의의 대상을 `FOR UPDATE OF pd`로 읽고(`p_item_book_id`가 있으면 `ib.id = p_item_book_id`로 좁힌다), 한 건씩 `expire_stale_poi_drops()`(108번 본문, 두 루프)와 같은 모양으로 처리한다: `UPDATE poi_drops SET is_available = FALSE`; `inventory_item_id`가 있으면 `UPDATE inventory_items SET destroyed_at = NOW(), inventory_id = NULL WHERE id = … AND destroyed_at IS NULL`과 `INSERT INTO custody_events (inventory_item_id, event_type, poi_id) VALUES (…, 'Expire', …)`. 처리한 건수를 돌려준다.
   - 트리거 함수 `public.trg_item_books_close_drops()`(`SECURITY DEFINER`, `search_path` 고정)와 트리거 `trg_item_books_close_drops AFTER UPDATE OF is_active ON public.item_books FOR EACH ROW WHEN (OLD.is_active IS DISTINCT FROM NEW.is_active AND NEW.is_active = FALSE)`: `PERFORM public.close_unclaimed_drops_of_inactive_collections(NEW.id)`.
   - `CREATE OR REPLACE FUNCTION public.expire_stale_poi_drops()`(시그니처 그대로, 오버로드 금지): 기존 두 루프를 **글자 그대로 유지**하고 끝에 `v_closed := public.close_unclaimed_drops_of_inactive_collections(NULL)`를 더해 반환 JSON에 `'closed_by_inactive_collection', v_closed`를 추가한다. 현재 DB 본문은 108번과 같다(2026-11-06 `pg_get_functiondef` 확인, `search_path TO 'public'` 포함).
   - 권한: 새 함수들은 `REVOKE EXECUTE … FROM PUBLIC`, 정리 함수는 `service_role`에만 `GRANT EXECUTE`(109·110번 패턴). `expire_stale_poi_drops()`의 기존 권한(service_role만)은 `CREATE OR REPLACE`로 유지되는지 확인한다.
   - 헤더 주석에 왜·하는 일·하지 않는 일(보유 개체·진행 기록 불변, 복구 없음, 기간 종료는 크론만)과 정리 대상 기준을 적는다. 적용 시점 데이터 정리는 이 파일에 넣지 않는다(카리나가 함수를 따로 호출한다).
2. **`jam-web/supabase/migrations/326_close_unclaimed_drops_of_inactive_collections_down.sql`** (신규): 트리거·트리거 함수·정리 함수를 `DROP … IF EXISTS`로 지우고 `expire_stale_poi_drops()`를 108번 본문으로 복원한다. 헤더에 「파괴한 개체는 되살리지 않는다」를 적는다.
3. **`jam-web/src/app/api/cron/poi-cleanup/route.ts`**(약 33~48행): 결과 타입에 `closed_by_inactive_collection: number`를 더하고, 0보다 크면 `[poi-cleanup] 비활성 컬렉션 드랍 소각 — N건`을 남긴다(기존 두 줄과 같은 모양). 응답 JSON에 이 값이 실리는지 현재 구조를 읽고 맞춘다.
4. **`jam-web/src/app/api/cron/poi-cleanup/__tests__/route.test.ts`**: 새 키가 있을 때 로그가 나가는 경우와 없는(0) 경우를 기존 두 항목 시험과 같은 방식으로 더한다.
5. **`jam-web/src/lib/admin/policyDashboard/policiesData.ts`**(9장 «장소, 드랍과 픽업», 약 905~975행 근처): 정책 항목 하나를 더한다 — 「컬렉션을 끄면 월드에 남은 미픽업 드랍도 내려간다」. `ticketId: '20261106_1052'`, 유형은 같은 장의 읽기 전용 항목 형식을 따르고(필드 목록은 파일 위쪽 타입으로 확인), `userExperience`는 사용자 말로 «운영 중단된 컬렉션의 아이템은 더 이상 장소에 놓여 있지 않아요» 정도의 해요체 한 문장, `basisDoc`은 운영 로직의 월드 드랍 절. 이 파일을 읽는 시험(고유 ID·필수 칸 등)이 있으면 함께 통과시킨다.
6. **문서**(코드와 같은 저장소): `docs/service/prd/02_DATA_MODEL.md`(약 675~681행 poi_drops 절과 `expire_stale_poi_drops()` 서술에 새 정리 함수·트리거·크론 응답 키), `docs/service/prd/04_PROJECT_SPEC.md`(105행 크론 설명), `docs/service/SERVICE_OPERATIONS.md`(1112행 크론 설명), `docs/service/badge-engine/BADGE_ENGINE_UNIFIED.md`(약 2314행 안전망 문단 옆에 컬렉션 비활성 경로 한 줄), `docs/plan/jam2/10 JAM 2.0 서비스 운영 로직.md`(월드 드랍 절에 한 줄, 절 위치는 검색). 같은 사실을 여러 곳에 길게 적지 않고 02_DATA_MODEL을 정본으로 두고 나머지는 한 줄 참조로 한다.
- 아현이 하지 않는 것(카리나, 4단계): 마이그레이션 실행, 드라이런(적용→점검→되돌림→원상 대조→예외로 전부 취소), 기존 631건 백업 표 만들기와 정리 함수 호출, `database.generated.ts` 재생성(MCP), 사후 읽기 전용 확인.

## 완료 조건

- 마이그레이션·되돌림 파일이 있고 파일 끝 표식 검사(`deploy-gate`)를 통과한다. 정리 함수는 `picked_up_at IS NULL`이 아닌 드랍, `inventory_id`가 있는 개체, `item_book_id IS NULL` 배지를 건드리지 않는다.
- 트리거는 `is_active` true→false 전환에서만 돌고 false→true·다른 열 변경에서는 돌지 않는다.
- 크론 라우트 시험이 통과하고 `scripts/verify.sh`가 통과한다.
- 정책 대시보드에 항목이 있고 문서 다섯 곳이 갱신돼 있다.

## 실행 계획 (카리나, 승인 후 4단계)

1. 드라이런으로 정리와 되돌림이 원상 복귀하는지 확인한 뒤 마이그레이션을 실행한다.
2. 기존 631건: 대상 드랍·개체 행을 백업 표 `backup_drop_cleanup_20261106`에 담고, 정리 함수를 한 번 호출해 631건이 0이 되는지 읽기 전용으로 확인한다. 백업 표는 복구 SQL과 함께 티켓에 남긴다.
3. 트리거 시험: 시험용 컬렉션이 아니라 드라이런 트랜잭션 안에서 켜진 컬렉션 하나를 껐다 켜 보고 취소한다(실제 컬렉션을 끄지 않는다).
4. `database.generated.ts`를 MCP로 재생성해 대조·반영하고, 정책 대시보드를 확인한다.

- 기간 종료 때 `is_active`를 자동으로 끄는 장치가 없다. 지금은 크론이 «기간 종료»도 대상으로 거르지만 화면 노출(읽기 정책)은 `valid_until`을 보지 않는다.
