# [Service] 컬렉션 비활성은 신규 발급만 막고 이미 발급된 아이템 배지는 계속 보이게 한다 (1단계: 배지)

## 핵심 요약

- 요구사항(사용자 2026-11-06 결정): **어드민에서 컬렉션을 비활성하는 것은 신규로 아이템 배지를 생성해 발급하는 것을 막는 것이다.** 이미 생성되어 서비스에 보이게 된 모든 상태(유저가 가진 개체, 장착된 개체, 월드에 놓인 드랍)의 배지는 컬렉션이 비활성이어도 보인다. 월드 드랍은 서비스에서 할 수 있는 기능(보기·줍기)을 그대로 할 수 있다. 오픈 전 비밀 유지는 개발 중이라 고려하지 않는다.
- 증상(2026-11-06 staging, `sihyunrr@gmail.com`): 칸은 10/10인데 화면에는 8개만 보이고 가득 참 안내가 나온다. 원인은 `badges` 읽기 정책이 비활성 컬렉션 배지를 모두에게 숨겨 가진 사람도 못 보는 것이다.
- 구현 계획(요지, **2026-11-06 성능 조정으로 방식이 바뀌었다**): «한 번이라도 개체가 만들어진 배지»를 작은 표 `issued_item_badges`에 기록하고, `badges` 읽기 정책이 그 표를 보게 한다. 표는 개체 INSERT 트리거가 채우고, 적용 때 기존 개체의 배지 323종을 백필한다. 함수·부분 인덱스는 쓰지 않는다. 신규 발급을 막는 쪽(드랍 엔진·완성 판정)은 이미 컬렉션 노출 판정을 쓰므로 바꾸지 않는다.
- 범위 밖(2단계 20261106_1125): 컬렉션(`item_books`) 읽기 정책과 컬렉션 화면·장착 서비스 코드.

## 배경 / 문제 정의

- 현재 `badges: 전체 읽기 허용` 정책(`TO authenticated`, 마이그레이션 216): `(type <> 'activity' OR valid_from IS NULL OR valid_from <= now()) AND (item_book_id IS NULL OR 소속 컬렉션이 is_active AND (valid_from IS NULL OR valid_from <= now()))`.
- 화면(`jam-web/src/app/(main)/inventory/page.tsx` 51~53행)은 `item.badge`가 읽히는 개체만 그린다. 칸 수(`used_slots`)는 읽기 정책과 무관하게 모든 개체를 센다.
- 2026-11-06 측정: 개체 1,429행(살아 있는 것 1,000개, 배지 185종, 개체가 한 번이라도 만들어진 배지 323종), 월드 드랍 1,182행. 정책 때문에 가려진 배지 중 살아 있는 개체가 있는 것은 107종이다.
- `inventory_items`의 읽기 정책은 «본인만 읽기»(`inventory.user_id = auth.uid()`), `poi_drops`는 «인증 유저 읽기(true)»다.
- 선행 이력: 티켓 20261106_1052(월드 드랍 소각 안)는 이 결정으로 폐기했다. 마이그레이션 325가 파괴한 개체 21개는 복구했다.

## 결정 / 검토한 대안

- **채택: 정책 예외(개체가 한 번이라도 만들어진 배지는 읽힌다).** «이미 발급되어 서비스에 보이는 것»을 «그 배지의 개체가 한 번이라도 만들어졌다»로 정의한다. 보유·장착·월드 드랍·소유자 없음은 물론 파괴(소모·만료)된 개체의 배지도 계속 보인다. 개체가 한 번도 만들어지지 않은 예약 컬렉션 배지는 지금처럼 숨는다. 정책의 `is_active` 조건 자체를 지우는 안은 채택하지 않았다: 예약 컬렉션 배지 수천 개가 한꺼번에 노출된다(2,304개).
- **채택한 구현: 발급 기록 표 + 개체 INSERT 트리거.** 정책은 `EXISTS (SELECT 1 FROM issued_item_badges s WHERE s.badge_id = badges.id)`만 본다.
- **미채택(2026-11-06 측정으로 갈음): 정책 안에서 `SECURITY DEFINER` 함수 `badge_has_live_item(id)`를 부르는 안**(게이트 PASS까지 갔다). 행마다 함수가 불려 컬렉션 33개 조회가 2.0ms에서 9.7ms, 배지 전체 읽기가 2ms에서 30ms로 느려졌다. 표 방식은 아래 측정대로 적용 전 수준이다. 함수 방식은 «살아 있는 개체»만 보는 장점이 있었으나(파괴되면 다시 숨음) 사용자 결정(«이미 생성되어 서비스에 보이게 된 모든 상태는 보인다»)에 «한 번 보인 것은 계속 보인다»가 더 가깝다고 판단했다. 함수 안을 단일 하위 질의(1회 계산)로 바꾸는 안도 검토했으나 개체 표가 커지면 질의마다 전체를 훑어 규모에 약하다.
- 미채택 ① 비활성 컬렉션의 드랍·개체를 소각: 사용자 결정으로 폐기(티켓 20261106_1052). ② 칸 수에서 가려진 개체를 빼는 안: 보이지 않는 개체는 장착·드랍도 못 하므로 권하지 않았고 사용자도 «보이게»를 택했다. ③ `badges`에 `issued` 열을 더하는 안: 정책 비용은 가장 작으나 `badges` 행의 모양이 바뀌어 `select('*')` 응답과 생성 타입·시험이 함께 바뀐다. 별도 표가 더 가볍다.

## 성능 측정 (2026-11-06, 드라이런 트랜잭션 안, `authenticated`·`god` 계정, 전부 취소)

|---|---|---|---|

## 상세 요구사항

### 데이터/DB 관점
- 새 표 `public.issued_item_badges (badge_id uuid PRIMARY KEY REFERENCES public.badges(id) ON DELETE CASCADE, first_issued_at timestamptz NOT NULL DEFAULT now())`. RLS를 켜고 정책 하나만 둔다: `issued_item_badges: 인증 유저 읽기` `FOR SELECT TO authenticated USING (true)`. 쓰기 정책은 두지 않는다(트리거와 `service_role`만 쓴다).
- 백필: `INSERT INTO public.issued_item_badges (badge_id) SELECT DISTINCT badge_id FROM public.inventory_items ON CONFLICT (badge_id) DO NOTHING`(2026-11-06 기준 323행). 적용 시점의 값이다.
- 트리거 함수 `public.trg_inventory_items_mark_issued()`(`plpgsql`, `SECURITY DEFINER`, `SET search_path TO 'public'`, 본문은 `INSERT INTO public.issued_item_badges (badge_id) VALUES (NEW.badge_id) ON CONFLICT (badge_id) DO NOTHING; RETURN NEW;`)와 트리거 `trg_inventory_items_mark_issued AFTER INSERT ON public.inventory_items FOR EACH ROW`. 함수는 `REVOKE ALL … FROM PUBLIC`. 개체가 만들어지는 모든 경로(민트·시스템 드랍·조합·캡슐·어드민 재배정)가 `inventory_items` INSERT라 한 곳에서 잡는다.
- `badges: 전체 읽기 허용` 정책을 `DROP POLICY` 후 다시 만든다. 첫 번째 조건(`type <> 'activity' …`)은 글자 그대로 두고, 두 번째 조건 끝에 `OR EXISTS (SELECT 1 FROM public.issued_item_badges s WHERE s.badge_id = badges.id)`를 더한다. 값싼 조건(`item_book_id IS NULL`, 컬렉션 노출)을 앞에 둔다. 정책을 지우고 만드는 사이에 읽기가 비지 않도록 표·백필·트리거·정책 교체를 한 트랜잭션(`BEGIN`/`COMMIT`)에서 처리한다.
- 함수 `badge_has_live_item`과 부분 인덱스 둘은 **만들지 않는다**(함수 방식으로 폐기).
- 되돌림 SQL: 정책을 216 조건으로 복원한 뒤 트리거·트리거 함수·표를 지운다(정책을 먼저 복원해야 표를 지울 수 있다).
- 성능: 위 측정을 완료 기록에 남긴다. 적용 후에도 컬렉션 33개 조회가 2ms 안팎인지 한 번 더 잰다(카리나).

### 서비스/코드베이스 관점
- 서비스 코드 변경은 이번 단계에 없다. 인벤토리 페이지·배지 상세·월드 드랍 화면은 `badges` 읽기가 열리면 그대로 보인다. 월드 드랍 3개 라우트(`/api/drops`, `/api/drops/poi/[poiId]`, `/api/drops/[dropId]/pickup`)에 컬렉션 활성 여부로 거르는 곳이 없음을 확인했다(2026-11-06 아현).
- 정책 대시보드 `jam-web/src/lib/admin/policyDashboard/policiesData.ts`의 항목 `ch9-collection-inactive-keeps-issued-visible`(`ticketId: '20261106_1124'`)은 이미 있다. 문구가 «살아 있는 개체»에 묶여 있으면 «발급된 적 있는 배지»에 맞게 고친다.
- 문서: `docs/service/prd/02_DATA_MODEL.md`(`badges` 읽기 정책 절, 약 286행: 함수·인덱스 서술을 새 표·트리거·백필로 바꾸고 `issued_item_badges` 표를 데이터 모델에 한 절 추가), `docs/plan/jam2/10 JAM 2.0 서비스 운영 로직.md`(9.3절, «살아 있는» 서술이 있으면 «발급된 적 있는»으로). 같은 사실은 `02_DATA_MODEL.md`를 정본으로 두고 나머지는 한 줄 참조로 한다.

## 잔여 이슈

- 2단계(20261106_1125): 컬렉션 읽기 정책과 컬렉션 화면·장착 서비스 코드. 이 단계가 끝나도 비활성 컬렉션 화면에서 소유자가 컬렉션 자체를 못 보는 부분은 남는다.
- «한 번 보인 배지는 계속 보인다»: 개체가 모두 파괴돼도(소모·만료) 배지는 숨지 않는다. 숨겨야 하는 요구가 생기면 `issued_item_badges`에서 행을 지우는 별도 규칙이 필요하다.
- 발급 표는 INSERT 트리거로만 갱신된다. 배지를 다른 배지로 바꾸는 UPDATE(`badge_id` 변경)가 생기면 트리거를 `AFTER UPDATE OF badge_id`로 넓혀야 한다(현재 그런 경로는 없음, 아현이 확인).
- 관련: 20261005_1151(공개 전 배지가 로그인 유저의 직접 조회에 보인다 — 이번 예외는 «개체가 만들어진 배지»만 열어 취지와 충돌하지 않는지 완료 때 대조한다), 292(예약 컬렉션 끄기), 20260914_1729, 20261106_1044.
