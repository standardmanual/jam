# [Service] 컬렉션 비활성은 신규 발급만 막고 이미 발급된 아이템 배지는 계속 보이게 한다 (1단계: 배지)

## 핵심 요약

- 요구사항(사용자 2026-11-06 결정): **어드민에서 컬렉션을 비활성하는 것은 신규로 아이템 배지를 생성해 발급하는 것을 막는 것이다.** 이미 생성되어 서비스에 보이게 된 모든 상태(유저가 가진 개체, 장착된 개체, 월드에 놓인 드랍)의 배지는 컬렉션이 비활성이어도 보인다. 월드 드랍은 서비스에서 할 수 있는 기능(보기·줍기)을 그대로 할 수 있다. 오픈 전 비밀 유지는 개발 중이라 고려하지 않는다.
- 증상(2026-11-06 staging, `sihyunrr@gmail.com`): 칸은 10/10인데 화면에는 8개만 보이고 가득 참 안내가 나온다. 원인은 `badges` 읽기 정책이 비활성 컬렉션 배지를 모두에게 숨겨 가진 사람도 못 보는 것이다.
- 구현 계획(요지): `badges` 읽기 정책에 «살아 있는 개체가 있는 배지는 보인다» 예외를 더한다. 개체 테이블이 본인 것만 읽히는 정책이라 정책용 `SECURITY DEFINER` 함수를 쓰고, 조회가 느려지지 않도록 부분 인덱스 두 개를 만든다. 신규 발급을 막는 쪽(드랍 엔진·완성 판정)은 이미 컬렉션 노출 판정을 쓰므로 바꾸지 않는다.
- 범위 밖(2단계 20261106_1125): 컬렉션(`item_books`) 읽기 정책과 컬렉션 화면·장착 서비스 코드.

## 배경 / 문제 정의

- 현재 `badges: 전체 읽기 허용` 정책: `(type <> 'activity' OR valid_from IS NULL OR valid_from <= now()) AND (item_book_id IS NULL OR 소속 컬렉션이 is_active AND (valid_from IS NULL OR valid_from <= now()))`.
- 화면(`jam-web/src/app/(main)/inventory/page.tsx` 51~53행)은 `item.badge`가 읽히는 개체만 그린다. 칸 수(`used_slots`)는 읽기 정책과 무관하게 모든 개체를 센다.
- 2026-11-06 측정: 개체 1,429행(살아 있는 것 1,000개, 배지 185종), 월드 드랍 1,182행. 정책 때문에 가려진 배지 중 살아 있는 개체가 있는 것은 **107종**이다. `inventory_items`·`poi_drops`에는 `badge_id` 인덱스가 없다.
- `inventory_items`의 읽기 정책은 «본인만 읽기»(`inventory.user_id = auth.uid()`), `poi_drops`는 «인증 유저 읽기(true)»다. 그래서 정책 안에서 개체 테이블을 직접 조회하면 타인의 개체(프로필에 보이는 장착 개체, 월드에 놓인 개체)가 빠진다.
- 선행 이력: 티켓 20261106_1052(월드 드랍 소각 안)는 이 결정으로 폐기했다. 마이그레이션 325가 파괴한 개체 21개는 복구했다.

## 결정 / 검토한 대안

- **채택: 정책 예외(살아 있는 개체가 있는 배지는 읽힌다).** «이미 발급되어 서비스에 보이는 것»을 «파괴되지 않은 개체가 하나라도 있는 배지»로 정의한다(보유·장착·월드 드랍·소유자 없음 모두 포함). 개체가 하나도 없는 예약 컬렉션 배지는 지금처럼 숨는다. 사용자가 오픈 전 비밀 유지를 따지지 않기로 했으므로 이 예외가 새로 열어 주는 범위는 «발급된 것»으로 충분하다. 정책의 `is_active` 조건 자체를 지우는 안은 채택하지 않았다: 배지 목록·카탈로그가 정책에 기대어 거르는 곳이 있으면 예약 컬렉션 배지 수천 개가 한꺼번에 노출된다(2,304개).
- 미채택 ① 비활성 컬렉션의 드랍·개체를 소각: 사용자 결정으로 폐기(티켓 20261106_1052). ② 칸 수에서 가려진 개체를 빼는 안: 보이지 않는 개체는 장착·드랍도 못 하므로 권하지 않았고 사용자도 «보이게»를 택했다.

## 상세 요구사항

### 데이터/DB 관점
- 새 함수 `public.badge_has_live_item(p_badge_id uuid) RETURNS boolean`: `STABLE`, `SECURITY DEFINER`, `SET search_path TO 'public'`. `EXISTS (SELECT 1 FROM inventory_items WHERE badge_id = p_badge_id AND destroyed_at IS NULL)`가 참이거나, 같은 배지의 `poi_drops`에 `is_available = TRUE`인 행이 있으면 참이다. `PUBLIC`에서 실행 권한을 회수하고 `anon`·`authenticated`·`service_role`에는 정책이 쓸 수 있게 준다(정책 평가는 호출자 권한으로 함수를 부른다).
- `badges: 전체 읽기 허용` 정책을 `DROP POLICY` 후 다시 만든다. 첫 번째 조건(`type <> 'activity' …`)은 글자 그대로 두고, 두 번째 조건을 `(item_book_id IS NULL OR 소속 컬렉션 노출 OR public.badge_has_live_item(id))`로 바꾼다. 비교 순서는 값싼 조건을 앞에 둔다. 정책을 지우고 만드는 사이에 읽기가 비는 순간이 없도록 한 트랜잭션에서 처리한다.
- 부분 인덱스: `idx_inventory_items_badge_live ON inventory_items (badge_id) WHERE destroyed_at IS NULL`, `idx_poi_drops_badge_available ON poi_drops (badge_id) WHERE is_available`. 표가 작아(1천 행대) `CONCURRENTLY` 없이 같은 트랜잭션에서 만든다.
- 되돌림 SQL: 정책을 옛 조건으로 복원하고 함수와 인덱스 둘을 지운다(정책을 먼저 복원한 뒤 함수를 지운다).
- 성능: 적용 전후로 `authenticated` 권한으로 `SELECT … FROM badges`와 인벤토리 페이지의 조인 질의를 `EXPLAIN ANALYZE`해 비교한다(카리나, 드라이런 때). 악화되면 정책에서 함수 호출 순서나 인덱스를 다시 본다.

### 서비스/코드베이스 관점
- 서비스 코드 변경은 이번 단계에 없다. 인벤토리 페이지·배지 상세·월드 드랍 화면은 `badges` 읽기가 열리면 그대로 보인다. 단, 아래를 확인하고 막히는 곳이 있으면 이 티켓에서 고친다: 월드 드랍 목록(`/api/drops`, `/api/drops/poi/[poiId]`)과 줍기(`/api/drops/[dropId]/pickup`)가 컬렉션 활성 여부로 거르거나 거절하는 곳이 없는지.
- 정책 대시보드 `jam-web/src/lib/admin/policyDashboard/policiesData.ts`에 «컬렉션 비활성은 신규 발급만 막고 이미 발급된 배지는 계속 보인다» 항목을 더한다(9장 «장소, 드랍과 픽업»과 가까운 장 또는 컬렉션 장 중 맞는 곳, 유형은 같은 장의 읽기 전용 항목 형식, `ticketId: '20261106_1124'`, 사용자 문구는 해요체 한 문장).
- 문서: `docs/service/prd/02_DATA_MODEL.md`(`badges` 읽기 정책 서술, 약 289행 부근, 새 함수·인덱스), `docs/plan/jam2/10 JAM 2.0 서비스 운영 로직.md`(컬렉션 비활성의 뜻을 한 줄로: 신규 발급만 막고 발급된 것은 보인다). 컬렉션 비활성이 «화면 노출 자체를 끈다»고 적힌 곳(`/api/admin/itembooks/[id]/drop-exclude/route.ts` 머리 주석, `lib/itembook/visibility.ts` 머리 주석 포함)은 2단계에서 고치므로 이번에는 건드리지 않는다. 같은 사실은 `02_DATA_MODEL.md`를 정본으로 두고 나머지는 한 줄 참조로 한다.
