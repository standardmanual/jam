# [Service] 가진 개체를 비활성 컬렉션에 장착하고 완성 보상을 받게 한다 (2단계 T3)

## 핵심 요약

- 요구사항(사용자 결정 질문 1 = A): 가진 개체를 꺼진 컬렉션에 장착할 수 있고, 마지막 칸을 채우면 **완성 기록·완성 포인트·보상 배지·챕터 점수가 기간이 끝난 컬렉션과 똑같이 그대로 지급**된다. 같은 컬렉션을 다시 채워도 중복 지급이 없다.
- 구현 계획(요지): 장착 `POST`의 «공개됨» 검사를 T2의 «열람 가능»으로 바꾼다. 장착 RPC(마이그레이션 179·222)와 보상 발급(`slotReward.ts`)은 컬렉션 노출을 보지 않아 **라우트 차단만 풀면 완성·보상이 자동으로 따라온다**.
- 선행: T2(20261106_1228). **체크포인트: 보상 지급이 실제로 일어나는 변경이다. 착수 전에 카즈하가 완성 보상이 걸린 꺼진 컬렉션 10개(포인트·보상 배지 × 보유 사용자 수)의 지급 상한을 계산해 사용자에게 보이고 진행 확인을 받는다.**
- 열린 질문 결정(사용자 추천대로): `checker.ts`(완성 확인 배치, 보상 배지 발급 실패 따라잡기)는 **건드리지 않는다**. 꺼진 컬렉션에서 보상 발급이 실패하면 따라잡지 못하는 사각이 있음을 완료 기록에 적고 필요하면 수동으로 보정한다(기간이 끝난 컬렉션과 같은 상태).
- 크기 상한: 파일 약 3개(`slot/route.ts`, 시험, 필요 시 보상 시험).

## 배경 / 문제 정의

- 장착 `POST`(`jam-web/src/app/api/itembooks/[id]/slot/route.ts` 107~121행)는 `isItemBookLaunched`가 아니면 «컬렉션을 찾을 수 없음»(404)을 돌려준다. 주석대로 장착 RPC는 노출을 보지 않아, 이 확인이 없으면 공개 전 컬렉션을 주소로 직접 완성할 수 있다(티켓 20260930_1516). 기간이 끝난 컬렉션은 막지 않는다(결정 E1).
- 장착 해제(`DELETE`, 195행)·교체(`PATCH`, 240행)와 일괄 해제(`slots` 라우트 `DELETE`)에는 노출 검사가 없어 **이미 가능**하다. 막힌 곳은 `POST` 하나다.
- 실측(2026-11-06): 꺼진 컬렉션 91개 중 완성 보상이 걸린 것 10개(등급형 보상 0개), 꺼진 컬렉션에 개체를 꽂은 사용자 3명·짝 36개, 이미 기록된 완성 2건(재지급 없음). 시뮬레이터 검증은 **미검증**이다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `POST`의 컬렉션 조회(112~121행)를 «열람 가능»(T2의 `visibility.ts` 판정, 발급 기록은 서비스 키로 `issued_item_books` 한 행)으로 바꾼다. **발급 기록이 없는 꺼진 컬렉션은 지금처럼 404**다(주소 직접 호출로 공개 전 컬렉션을 완성하지 못한다).
- 장착 RPC 인자·완성 기록·등급별 완성 포인트·챕터 점수(`completedBefore` 읽기 포함)·보상 배지 발급 흐름은 바꾸지 않는다.
- `DELETE`·`PATCH`·`slots` 일괄 해제는 무변경임을 확인해 요약에 적는다.
- `lib/itembook/checker.ts`·`completable.ts`·`lib/combine/tierUpCollections.ts`·`lib/notifications/batch/collections.ts`·`lib/content-corpus/active.ts`는 **무변경**(꺼진 컬렉션 제외 유지).

1. `jam-web/src/app/api/itembooks/[id]/slot/route.ts`: 컬렉션 검사 교체(약 107~125행), 머리 주석(결정 E1) 갱신.

- 실DB 확인은 staging 테스트 계정이 쓰는 공용 DB라 **사용자 확인 뒤** 테스트 계정으로만 하고, 만든 장착·완성 기록을 지우는 정리 SQL을 함께 둔다.

## 완료 조건

- 꺼진 컬렉션 + 발급 기록 있음에서 장착 `POST`가 성공하고, 마지막 칸 장착 시 완성 기록 1건, 등급별 완성 포인트, 챕터 점수, 보상 배지 발급이 일어난다. 같은 컬렉션 재장착에서 중복 지급 0(S4, 시험으로 고정).
- 꺼진 컬렉션 + 발급 기록 없음 → 404. 켜진 컬렉션과 기간이 끝난 컬렉션의 동작은 변하지 않는다.
- `DELETE`·`PATCH`·일괄 해제 무변경 확인이 요약에 있다. `checker.ts` 등 제외 유지 5곳이 무변경이고, 꺼진 컬렉션에 대해 완성 가능 소식·티어 승급 후보·배치 알림·콘텐츠 코퍼스가 0건임을 회귀 시험으로 고정한다(S5). **→ S5 회귀 시험은 T4(20261106_1230)에서 한꺼번에 고정한다(사용자 결정 2026-11-06, T3 게이트 WARN 대응. 이 항목을 T3 구현 요청에서 빠뜨린 것은 카리나의 실수였고, T4 완료 조건에 이미 같은 항목이 있어 중복을 피해 이관했다).**
- 지급 상한 계산 결과(카즈하)가 완료 기록에 있고 `checker.ts` 사각(보상 배지 발급 실패 시 따라잡기 불가)이 명시돼 있다. `scripts/verify.sh`가 통과한다.

### 주요 의사결정 / 핵심 메모
- 게이트 WARN(S5 회귀 시험 누락)은 사용자 결정으로 T4에서 한꺼번에 고정하기로 하고 T3을 머지했다. 5곳은 무변경이고 같은 공용 필터를 써서 동작 회귀 위험은 없었다.
- 기록 조회는 사용자 클라이언트(`supabase`)로 한다. `issued_item_books`는 마이그레이션 328의 읽기 정책(`authenticated`)으로 읽히므로 서비스 키가 필요 없다(컬렉션 상세는 서비스 키로 읽는다).

- **`checker.ts` 사각(받아들이기로 결정)**: 꺼진 컬렉션에서 장착 직후 보상 배지 발급(`runSlotRewardIssue`)이 실패하면 완성 확인 배치(`checker.ts`)가 따라잡지 못한다(켜져 있고 기간 안인 컬렉션만 본다. 기간이 끝난 컬렉션과 같은 상태). 필요하면 수동으로 보정한다. 보정 범위를 넓히려면 기간이 끝난 컬렉션 동작까지 바뀌어 별도 티켓이 필요하다.
