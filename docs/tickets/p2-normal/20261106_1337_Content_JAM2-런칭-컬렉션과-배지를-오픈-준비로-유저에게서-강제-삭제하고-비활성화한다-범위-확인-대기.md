- **백업 표 `launch_backup_20261106`**(행 단위 보안 켬, 정책 없음, 로그인 사용자 접근 막힘 확인): 개체 741·인벤토리 5·장착 슬롯 89·완성 2·월드 드랍 631·컬렉션 발급 63·배지 발급 222·컬렉션 63·알림 6. **복구 확인 뒤 `DROP TABLE public.launch_backup_20261106`으로 지운다.**

### 알려 둘 점
- 이 정리는 **이번 한 번만의 일회성**이다(일반 규칙 아님). 이후 컬렉션을 끌 때는 상위 티켓 20261106_1125의 규칙(신규 발급만 막고 발급된 것은 보임)을 따른다.

- 되돌릴 때 정리로 풀린 일련번호를 다른 개체가 받았다면 제약에 걸려 되돌림이 취소된다(백업 표는 그대로 남음).

## 확정이 필요한 것 (열린 질문, 추천 포함)

1. **«런칭하기로 했던 컬렉션»이 어느 집합인가?** 후보: ① 오픈 때 처음 여는 컬렉션 15개(현재 활성 15개와 같은 것으로 보임, 292 헤더에 이름이 있음) ② JAM 2.0 원고의 계획 컬렉션 50개 전체(5 트라이브 × 10) ③ JAM 2.0 이후 새로 만든 컬렉션 전부. **추천: 사용자가 이름 목록으로 확인한다.** 오픈 직전 목록 5번이 «처음 열 15개 + 꺼 둘 35개»라서 ②일 가능성도 있다.
2. **«비활성화»의 뜻**: 컬렉션 `is_active = false`만인가, 소속 아이템 배지의 소프트 삭제(`deleted_at`, 어드민 «폐기»)까지인가? 오픈 때 첫 공개 15개를 **다시 켜는** 계획(292·293)과 어떻게 이어지는가(끈 뒤 오픈 직전에 다시 켜는지, 이후 새로 발급하는지)? **추천: 컬렉션은 `is_active`만 끄고 배지는 건드리지 않는다**(배지를 폐기하면 컬렉션을 켜도 배지가 살아나지 않는다, 티켓 20261106_1044에서 확인).
3. **«강제 삭제»의 대상**: 그 컬렉션 배지의 (a) 인벤토리 보유 개체 (b) 컬렉션 장착 슬롯 (c) 완성 기록과 등급별 완성 기록 (d) 완성·획득으로 지급된 포인트와 포인트 원장(불변 기록, 보통 지우지 않음) (e) 알림·소식·월드 드랍(소유자 없는 개체). 어디까지인가? **추천: (a)(b)(c)와 해당 개체가 놓인 월드 드랍을 지우고, 포인트 원장은 건드리지 않는다**(원장은 불변 기록).
4. **삭제 방식**: 개체는 하드 삭제가 아니라 기존 소모·만료와 같은 소프트 파괴(`destroyed_at`, 보관 이력 `custody_events`)로 할지, 행째 삭제할지. **추천: 소프트 파괴 + 칸 수 재계산**(되돌릴 수 있고 이력이 남는다. 개체 파괴가 일련번호를 풀로 돌려준다).
5. **대상 사용자와 시기**: 지금 보유자는 5명(테스트 계정으로 보이는 4명과 이 계정). 실제 사용자가 섞여 있는가? 테스트 유저 삭제(11절, 사용자가 직접)와 같은 시기(오픈 직전)에 하는가, 아니면 그 전에 하는가? **추천: 오픈 직전 목록 13번으로 올리고 main 승격 직전에 실행한다.** 지금 지우면 staging 화면 확인(컬렉션 2단계 T2~T5)에 쓸 데이터가 사라진다.
6. **보호할 것**: 이 계정(`god`)을 포함해 staging 검증에 계속 쓸 계정과 컬렉션이 있는가?

## 실행 방식(확정되면, 제안)

- `db` 유형으로 `/jam-work` 진행. 아현은 SQL 파일(번호는 그때의 원격 최신 + 1)과 되돌림 SQL을 쓰고 실행은 카리나가 한다.
- 실행 전: 대상 행을 백업 표(`launch_backup_…` 선례, 마이그레이션 292)에 담고, 드라이런(적용→점검→되돌림→원상 대조→예외로 전부 취소), 대상 건수 가드(어긋나면 전체 되돌리는 트랜잭션), 실행 직후 읽기 전용 확인과 사용자 보고.
- 정리 뒤 `used_slots` 재계산, `issued_item_books`·`issued_item_badges`(발급 기록 표)에서 해당 컬렉션·배지를 어떻게 할지 함께 정한다(«한 번이라도 발급됐다»는 기록이 남으면 비활성 컬렉션이 계속 보인다. 이번 정리가 «출발선 맞추기»라면 기록을 지우는 것까지 포함해야 한다).
- 정책 대시보드·운영 로직 문서에는 «이번 한 번만의 정리»임을 명시한다(일반 규칙이 아님).
