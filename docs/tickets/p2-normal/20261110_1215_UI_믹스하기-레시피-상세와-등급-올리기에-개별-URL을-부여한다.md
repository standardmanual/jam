# [UI] 믹스하기 레시피 상세와 등급 올리기에 개별 URL을 부여한다

## 핵심 요약

- 요구사항: `/combine`의 레시피 상세(믹서)와 등급 올리기 화면이 지금은 `selectedRecipeId`·`tierUpOpen` 상태로만 전환된다. 이를 쿼리 URL에 싣는다: 레시피 상세 `/combine?recipe=<레시피ID>`, 등급 올리기 `/combine?view=tier-up`. 목록에서 열 때 history 항목을 쌓고(push), 브라우저·기기 뒤로가기와 TopNav 뒤로가기가 모두 한 단계 앞(목록)으로 돌아간다. 새로고침·링크 공유로 같은 화면이 열린다.
- 구현 계획: 아래 「구현 계획」 참조.
- 관련 파일: `jam-web/src/app/(main)/combine/CombineClient.tsx`(`selectedRecipeId` L379 안팎, `pickRecipe`·`closeMixer` L464~470, 등급 올리기 `openTierUp`·`closeTierUp` L541~547, TopNav `onBack` L954), `jam-web/src/app/(main)/combine/CombineClient.test.tsx`, `jam-web/src/app/(main)/combine/page.tsx`(변경 없음 예상), 스펙 `docs/service/prd/01_PRD.md`(믹서 설명)

## 배경 / 문제 정의

디자이너가 «믹스하기의 개별 레시피 상세 화면처럼 개별 URL이 없는 화면들은 뒤로 가기(history back)가 안 돼서 불편하다. 같은 방식으로 표시되는 화면들에 개별 URL을 부여하라»고 했다(2026-11-10). 지금은 화면 안의 상태(`useState`)로만 화면이 바뀌어서, 브라우저·기기의 뒤로가기를 누르면 그 화면이 아니라 앞서 있던 다른 라우트로 나가 버린다. 전수 조사로 URL이 없는 곳을 찾았고, 디자이너가 아래 범위를 정했다: ① 믹스하기 레시피 상세·등급 올리기, ② 드랍 지도의 장소 캐러셀, ③ 탭·필터 전환. URL 모양은 쿼리 방식이고, 잘못된 값은 목록(기본 화면)으로 조용히 돌려보낸다. 온보딩 2단계와 시트·확인 오버레이는 이번 범위에 넣지 않는다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 화면 상태의 단일 원천을 URL(`useSearchParams`)로 옮긴다. `selectedRecipeId`는 `recipe` 쿼리에서, `tierUpOpen`은 `view=tier-up`에서 파생한다. `recipe`와 `view`가 함께 있으면 `view=tier-up`이 이긴다.
- 열기: `router.push`로 history 항목을 쌓는다. 같은 화면에서 다른 레시피로 바꾸는 «다른 레시피» 전환은 `router.replace`(항목을 쌓지 않는다).
- 닫기(TopNav 뒤로가기·화면 안 닫기): 이 화면이 `/combine` 목록에서 push로 열린 것이면 `router.back()`, 링크·새로고침으로 바로 열린 것(앞 항목이 없거나 다른 라우트)이면 `router.replace('/combine')`으로 목록을 보여 준다. 브라우저 뒤로가기는 기본 동작이 곧 정답이다.
- 잘못된 값: 공개 목록(`publicRecipes`)에 없는 레시피 ID(종료·공개 전 포함)는 목록 화면으로 보내고 `router.replace('/combine')`으로 주소도 정리한다.
- 레시피가 바뀌면 채운 슬롯(`fills`)과 가방 시트를 비운다(지금 `closeMixer` 동작과 같다). 믹스 성공 결과 오버레이·받기 시트·가방 시트는 상태 그대로 둔다(이번 범위 아님).
- 온보딩 퀘스트 연출 모드(`questStep`)의 레시피 선택 반짝임과 `mix_fail`·`mix_success` 흐름이 URL 전환으로도 그대로 이어져야 한다. 연출 레시피(`DEMO_MIX_RECIPE`)의 ID도 URL에 실린다.
- `useSearchParams`를 쓰는 클라이언트 컴포넌트에 필요한 Suspense 경계가 `page.tsx`에 있는지 확인한다.

### UI/UX 관점
- 화면 모양은 바뀌지 않는다. 뒤로가기 동작만 바뀐다.
- 목록 → 상세 → 뒤로가기 → 목록 → 뒤로가기 → 이전 라우트의 순서가 자연스럽게 이어진다.

### 컨텐츠 관점
- 새 문구 없음.

## 구현 계획

1. `jam-web/src/app/(main)/combine/CombineClient.tsx`: `useRouter`·`useSearchParams`로 `recipe`·`view`를 읽어 `selectedRecipe`·`tierUpOpen`을 파생한다(상태 `selectedRecipeId`·`tierUpOpen` 제거). `pickRecipe`는 `router.push('/combine?recipe=ID')`, 레시피 간 전환은 `replace`. `closeMixer`·`closeTierUp`은 위 «닫기» 규칙(push로 열린 표시는 `history.state` 또는 목록에서 만든 플래그로 판별, 판별이 어려우면 `window.history.length` 대신 `router.back()` 후 폴백 없이 «직접 열기» 케이스만 `replace`)을 따른다. TopNav `onBack`(L954)은 이 닫기 함수를 그대로 넘기고, 목록 화면에서는 기존대로 `undefined`(= `router.back()`).
2. 잘못된 ID 처리: `publicRecipes`에 없는 `recipe` 값은 `useEffect`에서 `router.replace('/combine')`.
3. `jam-web/src/app/(main)/combine/CombineClient.test.tsx`: `next/navigation` 모의(`useRouter`·`useSearchParams`)로 열기=push, 전환=replace, 닫기=back/replace, 잘못된 ID=목록, `view=tier-up`=등급 올리기를 시험한다. 퀘스트 연출 시험이 URL 전환에서도 통과하는지 확인한다.
4. `docs/service/prd/01_PRD.md`: 믹서 설명(「레시피 상세는 `/combine?recipe=`」)과 퀘스트 4~5단계 문단에 URL 규칙을 적는다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)
- 목록에서 레시피를 열면 주소가 `/combine?recipe=<ID>`가 되고 history 항목이 하나 쌓인다. 브라우저 뒤로가기와 TopNav 뒤로가기 모두 목록으로 돌아가고, 한 번 더 누르면 `/combine` 이전 라우트로 나간다.
- 등급 올리기를 열면 `/combine?view=tier-up`이 되고 같은 방식으로 뒤로가기가 목록으로 돌아간다.
- `/combine?recipe=<ID>`를 새로고침하거나 링크로 직접 열면 같은 레시피 상세가 열리고, 이때 TopNav 뒤로가기는 목록(`/combine`)으로 간다.
- 공개 목록에 없는 레시피 ID로 열면 목록 화면이 나오고 주소가 `/combine`으로 정리된다.
- 상세에서 «다른 레시피»로 바꿔도 history가 쌓이지 않는다.
- 온보딩 퀘스트 4~5단계 연출이 URL 전환으로도 끝까지 동작한다.
- 시험이 통과하고 `scripts/verify.sh`가 통과한다(메인 폴더의 어드민 `Invalid hook call` 실패는 티켓 20261110_1157의 기존 문제이니 그것만 남아도 된다).

### 후속 범위 (담당: 카리나, 시점: 머지 뒤)
- 로컬 `next dev`에서 `/combine`을 열어 위 흐름(push·replace·직접 열기·잘못된 ID)을 실제로 눌러 확인한다.

## 완료 기록

### 구현 내용 요약
믹스하기의 레시피 상세와 등급 올리기를 쿼리 URL로 옮겼다. 상세는 `/combine?recipe=<ID>`, 등급 올리기는 `/combine?view=tier-up`이며 둘이 같이 있으면 등급 올리기가 이긴다. 목록에서 열면 `router.push`로 history를 쌓고, 닫기는 push로 연 경우 `router.back()`, 링크·새로고침으로 바로 연 경우 `router.replace('/combine')`다. 공개 목록에 없는 ID와 알 수 없는 `view` 값은 목록으로 보내고 주소를 정리한다. 화면 모양은 바뀌지 않았다.

### 주요 의사결정 / 핵심 메모
- 상태의 단일 원천을 URL로 옮겼다. 지금 화면에 «다른 레시피»로 바꾸는 진입 경로가 없어 replace 분기는 순수 함수 시험으로만 확인됐다.
- push로 열었는지는 모듈 표시로 판별한다(새로고침하면 저절로 false).
- 주소가 바뀔 때 서버 컴포넌트가 다시 렌더된다. 로컬에서는 체감 지연이 없었다.

### 잔여 이슈
- 서버 재렌더가 실서비스에서 거슬리면 `window.history.pushState` 방식으로 바꾸는 후속이 필요하다.
