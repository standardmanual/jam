## 상세 요구사항

### 서비스/코드베이스 관점

- 서비스 풀: 컬렉션 `is_active`·`drop_excluded=false`·공개 기간 안(`valid_from`/`valid_until`), 배지 `type='item'`·`deleted_at is null`·`drop_excluded=false`·공개 기간 안. 트라이브 비교는 하지 않는다(`tribe_id`가 null인 컬렉션도 포함).
- 시작 검사: 풀의 등급 집합에 재료 등급과 바로 윗등급이 모두 있어야 한다(Mystic 재료는 Mystic만). 아니면 소각 전에 `no_candidate`.
- 굴림: 등급(난수 1번) → 정한 등급의 풀 전체에서 배지마다 균등(난수 1번). 난수 호출 순서·횟수는 그대로.
- 등급 올리기는 유저 트라이브를 읽지 않는다. 소속 트라이브가 없는 유저도 등급 올리기를 할 수 있다(이전에는 `CapsuleError('no_tribe')`가 500을 냈다).
- 어드민 아이템 길: 아이템의 «등급 올리기» 길은 `서비스 풀에 들고 그 등급을 낼 재료 등급이 풀에 있다`면 열린다. 동기화·캡슐 길과 드랍 길은 지금 판정 그대로. 닫힘 사유 `tier_up_rarity_pair_missing`의 의미와 문구는 서비스 전체 기준으로 바꾼다.
- API 응답 모양·상태 코드·`reason` 값은 바꾸지 않는다.
