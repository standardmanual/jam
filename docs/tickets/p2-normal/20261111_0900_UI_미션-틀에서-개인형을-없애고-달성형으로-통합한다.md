# [UI] 미션 틀에서 개인형을 없애고 달성형으로 통합한다

## 핵심 요약

- 요구사항: 미션 틀(`status_display_type`)의 세 값 중 `individual`(개인형)을 없애고 `achievement`(달성형)로 통합한다(사용자 지시, 2026-11-11). 틀은 `ranking`·`achievement` 두 가지가 된다.
- 구현 계획: 타입·어드민 선택지·등록 검사·시험·문구에서 `individual`을 지우고, DB 제약을 두 값으로 좁히는 축소 마이그레이션 336을 쓴다. **336은 코드가 프로덕션에 배포된 뒤에 적용한다.**
- 관련 파일:
  - `jam-web/src/types/database.ts` — `MissionStatusDisplayType`(717행)
  - `jam-web/src/app/admin/missions/MissionForm.tsx`(68행 선택지)·`jam-web/src/app/admin/gate-missions/GateMissionForm.tsx`(64행 선택지, 93행 기본값을 `achievement`로)
  - `jam-web/src/lib/admin/registerChecks/missionFields.ts` — `STATUS_DISPLAY_TYPES`(60행)
  - `jam-web/src/lib/missions/condition-keys.ts`(오류 문장 443행 포함)·`jam-web/src/app/admin/missions/missionFormRules.ts`(안내 72행) — «달성형이나 개인형으로» → «달성형으로»
  - `jam-web/supabase/migrations/336_mission_status_display_drop_individual.sql`(+`_down`)
  - 문서: `docs/service/prd/01_PRD.md`·`02_DATA_MODEL.md`·`badge-engine/CONDITION_JSON_SPEC.md`·`prd/asset-generator/MISSION_REGISTRATION_BUNDLE.md`·`prd/content-automation/PRD.md`·`writing/UX_WRITING_GUIDELINE.md`·`docs/plan/jam2/10 JAM 2.0 서비스 운영 로직.md`

## 배경 / 문제 정의

개인형과 달성형을 다르게 다루던 곳은 미션 상황 화면과 API뿐이었다. 티켓 20261111_0850·0856으로 상황 화면은 랭킹형만 열게 됐고 달성형·개인형 코드는 지웠다. 그 뒤 두 값을 다르게 읽는 곳이 없다. 반면 «랭킹형인가, 아닌가»는 밤 조건·캡슐 연 횟수를 저장할 수 있는지(`condition-keys.ts`), 순위 상승 알림, 랭킹모드 연결을 가르므로 그대로 둔다.

## 상세 요구사항

### 동작
- 어드민 미션 폼과 게이트 미션 폼의 «미션 상황 표시 방식»은 «랭킹형 (등수/진행값)»·«달성형 (랭킹 없음)» 두 가지다. 게이트 미션 폼의 기본값은 `achievement`다(전에는 `individual`).
- 등록 검사(`missionFields.ts`)는 `individual`을 받지 않는다. 오류 문장은 값 목록에서 `individual`이 빠진다.
- 랭킹형이 아닐 때의 해결 안내는 «달성형으로 바꾸거나»가 된다.

### 지우지 않는 것
- 컬럼 `missions.status_display_type`과 `ranking` 값, 기본값 `ranking`.
- 역사 기록인 `docs/plan/jam2/service-redesign/*`, `docs/plan/jam2/09 …진행 노트.md`, `BADGE_ENGINE_UNIFIED.md` 1046행(당시 시드의 기록)은 고치지 않는다.
- 이미 실행된 시드 `seed_v5_gate_missions.sql`은 `individual`을 넣는다. 336 적용 뒤 이 파일을 다시 돌리면 제약에 걸린다.

## 완료 조건

- 코드에 `individual`(미션 틀) 참조가 없다(`checkin-badges`의 `mode: 'individual'`은 다른 뜻이라 대상이 아니다).
- 관련 시험과 `eslint`·`typecheck`가 통과한다.
- 336 적용 전 실측: `individual` 행 0건, 이 값을 쓰는 함수·뷰 0건.
- 336을 적용하고 제약이 두 값인지 읽어 확인한다(코드 배포 순서는 사용자 지시로 바꿨다).

### 주요 의사결정 / 핵심 메모
- 카리나가 직접 처리했다(직전 티켓들과 같은 이유: 앞 커밋이 push 전이라 워크플로가 그 위에 쌓지 못한다). 민지 게이트 리뷰는 거치지 않았다.
- 336은 원래 코드 배포 뒤에 적용하려 했다. 프로덕션의 옛 게이트 미션 폼은 기본값이 `individual`이라 제약을 먼저 좁히면 그 폼의 저장이 실패한다. 사용자가 그 오류를 감수하고 먼저 적용하라고 지시했다. 새 코드가 배포되기 전까지 프로덕션 어드민에서 게이트 미션 폼을 저장하면 실패한다(기본 선택을 달성형·랭킹형으로 바꾸면 저장된다).
- 적용 전 `DO` 블록 드라이런(적용 → 새 제약 정의 읽기 → `individual` 대입 거절 확인 → 예외로 전부 취소)을 했다: 새 제약 두 값, `individual` 거절, 8행 모두 통과. 이어서 실제 적용하고 읽기로 확인했다: 제약 두 값, 8행, 제약 밖 값 0건.

### 잔여 이슈
- 새 코드가 프로덕션에 배포되기 전까지는 옛 게이트 미션 폼 저장이 실패한다(위 의사결정 참고). 배포로 풀린다.
- `MissionForm.test.tsx`는 hook 오류가 없는 환경에서 한 번 더 돌려야 한다.
