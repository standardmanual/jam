# [Service] 배지 이미지가 UI보다 늦게 뜨는 원인을 실측하고 해결 순서를 정한다 (상위)

## 핵심 요약

- 요구사항: 배지 이미지를 보여 주는 화면에서 그림이 다른 UI보다 늦게 나타난다. 스켈레톤이나 로딩 표시를 더하는 방법이 아니라,

**변환 주소(`/_next/image`)의 응답** (`stage.j-a-m.app`, 원본 8개 × 폭 128·256)

- 변환본의 용량은 1.7~13KB다
- 변환 캐시에 없을 때의 첫 응답은 0.39~1.09초, 캐시에 있을 때는 0.27~0.47초다(매번 새 연결로 잰 값)
- 저장소 원본을 변환한 응답의 헤더는 `public, max-age=14400, must-revalidate`(4시간)다
- 정적 파일 원본을 변환한 응답의 헤더는 `public, max-age=0, must-revalidate`다
- 재요청에서 `x-vercel-cache: STALE`이 관측됐다(원본 2·6의 폭 256)

**화면 단위** (헤드리스 크롬, 390×844, 배율 3, `/badges` 첫 탭, 배지 이미지 31장이 모두 변환 주소를 거친다)

| 조건 | 화면 첫 표시(FCP) | 이미지 요청 시작 | 이미지 도착 |
|---|---|---|---|
| 빠른 통신, 첫 방문 | 516ms | 506~507ms | 557~608ms |
| 빠른 통신, 다시 방문 | 576ms | 브라우저 캐시 31장 | 0ms |
| 4G 조건(지연 165ms, 9Mbps), 첫 방문 | 528ms | 517~518ms | 771~827ms |
| 4G 조건, 다시 방문 | 556ms | 브라우저 캐시 31장 | 0ms |

위 «다시 방문»은 첫 방문 직후(4시간 이내)에 잰 값이다. 변환 캐시가 비어 있는 상태의 화면 단위 수치는 재지 못했다.

**표시 크기로 줄였을 때의 용량** (sharp, WebP 품질 80)

|---|---|---|
| PNG 600px 208KB | 3.3KB | 5.2KB |
| PNG 600px 339KB | 9.8KB | 17.3KB |
| WebP 1024px 74KB | 6.0KB | 10.6KB |

**코드에서 확인한 사실**

- 서비스 화면의 배지 이미지 가운데 미리 받기(`priority`)를 지정한 곳은 `TierUpRevealOverlay.tsx` 두 군데뿐이다. 나머지는 지연 로딩 기본값을 쓴다
- `next.config.ts`의 `images`에는 `minimumCacheTTL` 지정이 없다(Next 16 기본값은 14400초다)
- 배지 업로드 경로 다섯 갈래에 `cacheControl` 지정이 없다
- `<link rel="preload">`·`preconnect` 지정과 서비스 워커가 없다
- 컬렉션 상세의 체크인 배지, 컬렉션 히어로, 지도 마커는 변환 주소를 거치지 않고 원본을 받는다

### 판단

실측을 근거로 원인을 넷으로 정리했다.

1. **요청이 화면이 그려진 뒤에 시작된다.** 이미지 요청 시작 시점이 화면 첫 표시 시점과 같다. 그래서 통신 한 번의 왕복 시간만큼
   그림이 반드시 늦는다(빠른 통신 0.05~0.09초, 4G 조건 0.25~0.3초)
2. **캐시 수명이 짧다.** 저장소 이미지는 4시간, 정적 파일 이미지는 0초다. 한 번 본 배지도 수명이 지나면 서버에 다시 묻는다.
   변환본 캐시의 수명도 4시간이라, 방문이 뜸한 배지는 요청할 때마다 변환을 새로 기다린다(0.4~1.1초)
3. **데이터 응답 뒤에야 주소를 아는 화면이 있다.** 드랍 지도, 지점 카드, 배지 상세 시트는 API 응답을 기다린 뒤에 이미지 요청을
   시작하므로 두 번 기다린다
4. **원본을 그대로 받는 화면이 세 곳 있다.** 200~500KB짜리 파일을 56~200px 자리에 받는다

그 기기에서 처음 보는 배지는 통신 왕복이 한 번은 필요하다. 이 왕복을 화면과 같은 시점에 끝내려면 요청을 HTML과 함께
시작해야 하고(원인 1), 두 번째부터는 요청 자체가 없어야 한다(원인 2).

### 분해안 (승인 대기)

| 회차 | 없애는 원인 | 내용 | 눈에 보이는 변화 |
|---|---|---|---|
| 1 | 1·2·4 | 변환 이미지 캐시 수명을 4시간에서 31일로 늘린다. 정적 파일 배지도 같은 수명을 받게 한다. 첫 화면에 보이는 배지를 HTML과 함께 요청한다. 원본을 받는 세 곳을 변환 주소로 통일한다. 저장소 업로드에 캐시 수명을 지정한다 | 없음(속도만 달라진다) |
| 2 | 3 | 드랍 지도에서 지점 목록이 도착하면 가까운 지점의 드랍 배지 그림을 미리 받아 둔다. 지점 카드와 배지 상세 시트가 열릴 때 그림이 이미 도착해 있게 한다 | 없음 |
| 3 | 2의 나머지 | 표시 크기 파생본을 업로드 시점에 미리 만들어 저장하고 화면이 그것을 직접 받는다. 요청 시점의 변환 대기가 사라진다 | 없음 |

- 3회차는 업로드 경로 다섯 갈래와 기존 저장소 이미지 약 2,800장의 일괄 생성을 건드린다. 1·2회차 뒤에 «처음 요청되는 배지의 변환
  대기»가 실측으로 남아 있을 때에만 진행한다
- 캐시 수명을 늘리면 같은 주소로 그림을 교체했을 때 옛 그림이 남는다. 저장소 주소의 대부분은 `?v=` 값이 붙어 교체 때 주소가
  바뀐다. `?v=`가 없는 저장소 주소 81건과 정적 파일 2,083건은 1회차에서 교체 시 처리 방법을 정한다
  (Vercel에는 원본 주소 단위로 변환 캐시를 무효화하는 기능이 있다)

### 1회차 결과 (2026-11-15, 티켓 20261115_1237, staging 배포)

- 변환 응답의 캐시 수명이 4시간에서 31일로, 정적 파일 배지가 0초에서 하루(그 뒤 30일은 옛 사본을 먼저 보여 주고 뒤에서 확인)로 바뀌었다
- 원본을 받던 세 곳이 줄인 그림을 받는다
- 첫 방문에서 그림이 화면보다 늦는 간격은 4G 조건에서 0.24~0.30초가 0.14~0.26초가 됐다. **없어지지 않았다**
- 원인: 그림 주소가 실린 HTML이 화면 첫 표시 직전에 도착한다. 요청을 화면보다 충분히 앞당길 방법이 이 구조 안에는 없다

### 2회차 범위 조정안 (승인 대기)

첫 방문의 간격을 없애려면 화면을 열기 전에 그림이 기기에 있어야 한다. 2회차를 «드랍 지도의 미리 받기»에서
«곧 열 화면의 배지 그림을 미리 받기»로 넓힌다.

- 홈이 뜬 뒤 한가한 시점에, 배지함·인벤토리의 첫 화면 분량 그림을 미리 받는다
- 드랍 지도에서 지점 목록이 도착하면 가까운 지점의 드랍 배지 그림을 미리 받는다(처음 분해안의 2회차)
- 미리 받는 주소는 화면이 실제로 요청하는 주소(폭·품질 값 포함)와 같아야 한다. 다르면 같은 그림을 두 번 받는다

### 2회차 메인 탭 결과 (2026-11-15, 티켓 20261115_1344, staging 배포)

- 4G 조건의 첫 방문에서 배지함·인벤토리의 앞 칸 그림이 모두 화면 첫 표시보다 먼저 준비된다(미리 받기를 끄면 0.12~0.16초 늦다)
- 드랍 지도 부분은 티켓 20261115_1455로 잇는다

### 2회차 드랍 지도 결과 (2026-11-15, 티켓 20261115_1455, staging 배포)

- 지점 카드를 처음 열 때 갤러리 그림이 목록과 같은 시점에 준비된다(변경 전에는 0.17~0.57초 늦었다)
- 56px 칸이 90px 카드와 같은 변환본을 써서, 한 번 받은 그림을 두 곳이 함께 쓴다

### 3회차 진행 여부 (결정 대기)

1·2회차 뒤에 남은 것은 «변환본을 그 자리에서 처음 만드는 0.4~1.1초»다. 미리 받기가 있는 화면에서는 이 시간이 화면 밖에서
지나가므로 보이지 않는다. 미리 받기가 없는 화면(컬렉션 상세, 프로필, 배지함의 체크인·컬렉션 탭, 배지 상세의 대표 그림)에서는
그 배지를 누군가 처음 볼 때 나타난다.

### 3회차 설계 실측과 조정안 (2026-11-15, 사용자가 3회차 진행을 결정한 뒤)

**실측한 사실** (`stage.j-a-m.app`, 서울에서 curl)

| 무엇을 받았나 | 처음 요청 | 다시 요청 |
|---|---|---|
| 저장소의 작은 파일을 직접(약 10KB PNG 4개, `images/badges/checkin/`) | 0.42~0.75초(`cf-cache-status: MISS`) | 0.06~0.08초(`HIT`) |
| 변환본(`/_next/image`, 오전 측정) | 0.39~1.09초(`x-vercel-cache: MISS`) | 0.05~0.15초(`HIT`) |

- 12시 20분쯤 만들어진 변환본 4개가 그 뒤 세 번의 배포를 거친 15시 59분에도 `HIT`였다(`age` 약 13,420초)
- 변환본의 보관분은 브라우저가 달라도 함께 쓰인다. `image/webp`를 받는 요청으로 만든 보관분에 크롬과 사파리의 `Accept` 값이 모두 `HIT`였다.
  `Accept: */*`는 PNG로 응답하며 보관분이 따로다
- 저장소 주소를 쓰는 활성 배지의 그림은 577개(중복 제외), 컬렉션 그림은 72개다

**판단**

- 처음 분해안의 3회차(줄인 그림을 저장소에 파일로 만들어 두고 화면이 직접 받는다)는 목표를 이루지 못한다. 저장소의 파일도 그 지역의
  CDN에 보관분이 없으면 처음 요청에 0.42~0.75초가 걸린다. 없애려던 «처음 만드는 0.4~1.1초»와 같은 크기의 지연이 남는다
- 지연을 없애는 것은 파일의 위치가 아니라 «그림을 올린 직후에 화면이 쓸 주소를 한 번 요청해 두는 것(예열)»이다. 지금의 변환 경로에
  예열을 더하면 화면 쪽 코드를 바꾸지 않고 같은 목표를 이룬다

**조정안 (승인 대기)**

| 단계 | 내용 |
|---|---|
| 3-1 | 그림을 올리거나 바꾸는 다섯 경로에서, 저장한 직후에 화면이 쓰는 변환 주소(폭 96·256·640, WebP)를 서버가 한 번 요청해 둔다 |
| 3-2 | 이미 있는 그림 649개를 한 번 예열한다(요청 약 1,950건). staging 대상으로 먼저 하고, 프로덕션은 JAM 2.0을 올린 뒤에 다시 한다 |

- 예열은 Vercel 프로젝트마다 따로다. staging과 프로덕션은 프로젝트가 달라 보관분도 따로다
- 변환본의 보관 기간은 31일이다. 기간이 지난 뒤의 응답은 오전 측정에서 `STALE`(옛 보관분을 먼저 주고 뒤에서 갱신)이 관측됐다.
  31일 뒤에도 그렇게 동작하는지는 확인하지 못했다
- 저장소 업로드의 캐시 수명 지정은 하지 않는다. 화면이 저장소 원본을 직접 받지 않는다
