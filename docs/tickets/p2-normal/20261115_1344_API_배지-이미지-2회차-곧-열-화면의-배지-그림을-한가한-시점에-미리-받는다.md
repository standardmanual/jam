# [API] 배지 이미지 2회차: 곧 열 화면의 배지 그림을 한가한 시점에 미리 받는다

## 핵심 요약

- 요구사항: 배지함과 인벤토리를 그 기기에서 처음 열 때에도 배지 그림이 화면과 함께 보이게 한다. 메인 화면이 뜬 뒤 한가한 시점에
  두 화면의 첫 화면 분량 그림을 미리 받아 브라우저 캐시에 넣어 둔다. **화면의 모양은 바꾸지 않는다.**
  상위 티켓 20261115_1232의 2회차 가운데 메인 탭 부분이다(사용자 승인 2026-11-15). 드랍 지도 부분은 별도 티켓으로 잇는다.
- 구현 계획: 미리 받을 주소 목록을 돌려주는 API 하나, 그 목록을 한가한 시점에 받는 클라이언트 컴포넌트 하나, 화면이 실제로 요청하는
  주소와 같은 주소를 만드는 함수 하나를 더한다. 파일 단위 계획은 아래 「구현 계획」에 있다.
- 관련 파일(지도):
  - `jam-web/src/lib/imageSrc.ts`의 `optimizedImageUrl`, `isDirectStaticBadgeSrc`, `FIRST_SCREEN_GRID_COUNT`
  - `jam-web/src/app/(main)/layout.tsx` 91~144행(트리), 131행 `<TabBar />`
  - `jam-web/src/app/(main)/inventory/page.tsx` 31~35행(조회), 50~52행(필터), 62·70행(그림 주소)
  - `jam-web/src/app/(main)/badges/page.tsx` 45~49행(조회), 86~92행(activity 타입 필터와 `pickHighestLevelPerFamily`)
  - `jam-web/src/app/(main)/badges/BadgesClient.tsx` 90~99행(처음 보이는 탭은 `activity`), 172~177행(필터 기본값 `all`)
  - `jam-web/src/lib/activity-feed/collapseLeveled.ts` 93행 `pickHighestLevelPerFamily`
  - `jam-web/src/app/api/inventory/items/route.ts` 9~11행(인증 관례)
  - `jam-web/src/components/ui/BadgeGridCard.tsx` 258행 부근(90px `SafeImage`)

## 배경 / 문제 정의

### 실측한 사실 (2026-11-15, `stage.j-a-m.app`, 헤드리스 크롬 390×844 배율 3)

- 1회차 뒤에도 배지함 첫 방문에서 그림은 화면 첫 표시보다 4G 조건에서 0.14~0.26초 늦게 도착한다(티켓 20261115_1237)
- 실험: 새 기기 조건의 홈 화면에서 배지함이 요청할 주소 31개를 `new Image()`로 미리 받은 뒤 배지함을 처음 열었다

| 조건 | 화면 첫 표시(FCP) | 그림 도착 | 브라우저 캐시에서 온 그림 |
|---|---|---|---|
| 빠른 통신 | 464ms | 377~388ms | 31장 / 31장 |
| 4G 조건 | 580ms | 510~517ms | 31장 / 31장 |

- 폭 90px 이미지에 `next/image`가 만드는 주소는 1배 화면에서 `w=96`, 2배 이상 화면에서 `w=256`이고 품질은 75다
  (`jam-web/src/lib/imageSrc.ts`의 `slotOutlineTraceSrc` 주석)
- 인벤토리 화면의 조회에는 정렬이 없다. 인벤토리는 30칸이 한도다
- 배지함은 처음 열면 `activity` 탭이 보이고, 목록은 `earned_at` 내림차순으로 읽은 뒤 계열마다 가장 높은 레벨만 남긴 것이다
- 배지함 목록을 돌려주는 API는 없다. `/api/inventory/items`는 `obtained_at` 내림차순이라 화면과 순서가 같다는 보장이 없다

### 판단

- 미리 받는 주소가 화면이 요청하는 주소와 한 글자라도 다르면 캐시가 맞지 않아 같은 그림을 두 번 받는다. 주소를 만드는 규칙을
  한 곳에 두고 시험으로 고정한다
- 인벤토리는 한도가 30칸이므로 전체를 받는다. 그러면 화면의 순서를 몰라도 된다

## 상세 요구사항

### 기능 요구사항

1. **목록 API** `GET /api/badge-images/warmup`
   - 로그인한 사용자 본인의 주소만 돌려준다. 인증은 기존 라우트의 관례를 따른다(없으면 401과 `{ error }`)
   - 응답은 `{ urls: string[] }`이고, 원본 주소(`badges.image_url`)를 그대로 담는다. null과 중복은 뺀다
   - 인벤토리: 화면과 같은 필터(`dropped_at`·`slotted_in`이 null, 소프트 삭제된 배지 제외)로 전체. 잠긴 개체는 뺀다
     (화면이 그림을 그리지 않는다)
   - 배지함: `activity` 탭의 앞 12칸(`FIRST_SCREEN_GRID_COUNT`). 화면과 같은 조회·같은 정렬·같은 접기 규칙을 쓴다
   - 합쳐서 42개를 넘기지 않는다
2. **주소 규칙** `imageSrc.ts`
   - `nextImageWidthFor(displayWidth, dpr)`: next 기본 폭 목록에서, 1배 화면이면 표시 폭 이상인 가장 작은 값, 그 밖에는
     표시 폭의 두 배 이상인 가장 작은 값을 돌려준다
   - 미리 받는 주소는 `optimizedImageUrl(src, nextImageWidthFor(90, dpr))`이다. 정적 파일 배지는 원래 주소 그대로다
3. **미리 받기 컴포넌트** `BadgeImageWarmup`(아무것도 그리지 않는다)
   - `(main)` 레이아웃에 한 번 마운트한다
   - 탭(브라우저 세션)마다 한 번만 실행한다(`sessionStorage`)
   - 페이지 로드가 끝난 뒤 `requestIdleCallback`으로 시작한다. 지원하지 않는 브라우저에서는 `setTimeout` 2초로 대신한다
   - `navigator.connection.saveData`가 켜져 있으면 실행하지 않는다
   - 그림은 6장씩 차례로 받고 `fetchPriority`를 `low`로 둔다
   - API나 그림 요청이 실패해도 화면에 아무 영향이 없어야 한다(오류를 던지지 않고 토스트도 띄우지 않는다)

### UI/UX 관점

- 새 UI가 없고 눈에 보이는 변화가 없다. 채원 사전 판정 대상이 아니다

### 범위 밖

- 드랍 지도와 지점 카드(별도 티켓)
