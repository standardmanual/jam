# [API] 배지 이미지 3회차: 그림을 올린 직후 화면이 쓸 변환본을 미리 만들어 둔다

## 핵심 요약

- 요구사항: 새로 올리거나 바꾼 배지 그림을 누군가 처음 볼 때 생기는 «변환본을 그 자리에서 만드는 0.4~1.1초»를 없앤다.
  그림을 저장한 직후에 서버가 화면이 쓰는 변환 주소를 한 번 요청해 변환 캐시에 넣어 둔다(예열).
  상위 티켓 20261115_1232의 3회차 조정안이다(사용자 승인 2026-11-15). **화면 쪽 코드는 바꾸지 않는다.**
- 구현 계획: 예열 함수 하나를 만들고, 그림을 저장하는 다섯 경로가 저장 직후에 부른다. 이미 있는 그림을 한 번에 예열하는 스크립트도 만든다.
  스크립트의 실행은 이 티켓의 구현 범위가 아니다(카리나가 머지 뒤에 실행한다).
- 관련 파일(지도):
  - `jam-web/src/lib/imageSrc.ts`의 `optimizedImageUrl`, `isOptimizableImageSrc`, `isDirectStaticBadgeSrc`
  - `jam-web/scripts/recraft/register-badge-images.js` 56행(업로드), 66행(`publicUrl`에 `?v=` 부여), 70행(DB 반영)
  - `jam-web/src/app/api/admin/badge-image-generator/apply/route.ts` 72~76행 부근(PNG·WebP 업로드와 WebP 주소 저장)
  - `jam-web/src/app/api/admin/badge-image/generate/route.ts` 117~120행 부근(업로드와 `image_url` 갱신)
  - `jam-web/src/app/api/admin/activity-badge-image/generate/route.ts` 86~89행 부근(업로드와 `image_url` 갱신)
  - `jam-web/src/app/api/admin/upload-image/route.ts` 59행(업로드), 65행(`publicUrl`)
  - `jam-web/node_modules/next/dist/docs/01-app/03-api-reference/04-functions/after.md`(응답 뒤에 실행하는 `after`)

## 배경 / 문제 정의

실측과 판단의 근거는 상위 티켓 20261115_1232의 「3회차 설계 실측과 조정안」에 있다. 이 티켓에 필요한 사실만 옮긴다.

- 변환본의 처음 요청은 0.39~1.09초, 보관분이 있으면 0.05~0.15초다(`stage.j-a-m.app`)
- 변환 캐시는 배포를 거쳐도 남는다. 보관분은 응답 형식별로 나뉘고, `image/webp`를 받는 요청으로 만든 보관분을 크롬과 사파리가 함께 쓴다
- 변환 주소의 형식은 `/_next/image?url=<encodeURIComponent(원본 주소)>&w=<폭>&q=75`다(`optimizedImageUrl`)
- 화면이 쓰는 폭: 카드와 작은 칸은 96(1배)·256(2배 이상), 배지 상세의 대표 그림은 256(1배)·640(200px의 2배),
  시트의 대표 그림은 256(1배)·384(176px의 2배)다(`BadgeHeroSection.tsx` 29~30행, `nextImageWidthFor`)
- 정적 파일 배지(`/badges/…`)는 변환을 거치지 않는다

## 상세 요구사항

### 기능 요구사항

1. **예열 함수** `warmImageVariants(imageUrl, origin)` (서버 전용)
   - 폭 96·256·384·640마다 `<origin>` + `optimizedImageUrl(imageUrl, 폭)`을 `Accept: image/webp` 헤더로 한 번씩 GET 요청한다
   - 변환 대상이 아닌 주소(정적 파일 배지, 최적화할 수 없는 주소, 빈 값)는 요청하지 않는다
   - 요청마다 시간 제한(8초)을 두고, 실패해도 던지지 않는다. 폭별 결과(HTTP 상태, `x-vercel-cache` 값)를 돌려준다
2. **업로드 경로 연결** (API 라우트 넷)
   - 그림 주소를 저장한 직후에 `after()`로 예열을 건다. 응답을 늦추지 않는다
   - `origin`은 요청이 들어온 출처(`new URL(request.url).origin`)를 쓴다
   - 예열의 실패가 업로드 결과에 영향을 주지 않는다
3. **등록 스크립트 연결** (`register-badge-images.js`)
   - DB 반영 뒤에 같은 폭으로 예열한다. 대상 출처는 `--warm-origin` 인자로 받고 기본값은 `https://stage.j-a-m.app`이다
   - `.js` 스크립트는 TS 모듈을 가져올 수 없으므로, 주소 형식을 스크립트 안에 다시 적을 때는 `optimizedImageUrl`과 같은 형식임을 주석으로 밝힌다
4. **일괄 예열 스크립트** `jam-web/scripts/warm-badge-image-variants.mjs`
   - 입력: 원본 주소 목록이 든 JSON 파일(`["https://…", …]`). DB 접속 정보를 쓰지 않는다
   - 인자: `--origin`(필수), `--dry-run`(요청하지 않고 건수만 출력), `--concurrency`(기본 6)
   - 출력: 폭별 요청 수, `x-vercel-cache` 값의 분포(MISS·HIT·STALE), 실패 목록
   - 정적 파일 배지와 변환 대상이 아닌 주소는 건너뛰고 건수를 따로 센다

### UI/UX 관점

- 화면 변화가 없다. 채원 사전 판정 대상이 아니다

### 범위 밖

- 화면이 저장소의 파생본 파일을 직접 받는 방식(상위 티켓의 처음 분해안). 실측으로 기각했다
- 저장소 업로드의 `cacheControl` 지정
- 일괄 예열의 실행, 프로덕션 예열(JAM 2.0을 올린 뒤에 한다)
- 배지가 아닌 그림(홈 피드 카드 표지, 미션 그림)의 폭

### 주요 의사결정 / 핵심 메모

- 규모 사전 판정: 바뀌는 파일이 약 9개, 250줄 안팎으로 `plan_only` 임계값을 넘는다. 사용자가 3회차 조정안의 실행을 승인했고(2026-11-15)
  구현 계획을 파일 단위로 적었으므로, 첫 호출부터 계획 반환 면제를 넘긴다
- 유형은 `api`로 판정했다. 어드민 API 라우트와 스크립트만 바뀌고 화면 변화가 없다
- 예열 폭을 96·256·384·640 네 개로 정했다. 조정안을 보고할 때는 세 개(96·256·640)로 적었는데, 시트의 대표 그림(176px)이 2배 화면에서
  384를 쓰는 것을 확인하고 더했다. 기존 그림 649개의 일괄 예열 요청은 약 1,950건에서 약 2,600건이 된다
- 대상 출처는 요청이 들어온 출처 하나로 했다. staging과 프로덕션은 Vercel 프로젝트가 달라 변환 캐시가 따로다
