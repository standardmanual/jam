# [Admin] 배지 획득 조건에서 템플릿 분류와 값 글자를 뽑는 규칙을 만든다

## 핵심 요약
- 요구사항: 액티비티 배지의 획득 조건(`condition_json`)을 넣으면 템플릿 분류(운동 수치·쌓은 날·이어 온 날·횟수와 양)와 배지에 넣을 값 글자(«21.1km», «14일 연속», «5회» 등)를 돌려주는 순수 함수를 만든다. 화면과 API는 만들지 않는다(상위 티켓 20261115_2353의 1회차).
- 구현 계획: 조건 칸과 분류·값 꼴의 대응을 표 한 곳에 두고, 함수가 그 표로 판정한다. 표에 없는 칸은 판정하지 않고 `null`을 돌려준다. 아래 「규칙표」의 모든 줄을 시험으로 고정한다.
- 관련 파일:
  - 새 파일 `jam-web/src/lib/admin/activityBadgeTemplate/resolveTemplateText.ts` (대응표와 함수)
  - 새 파일 `jam-web/src/lib/admin/activityBadgeTemplate/__tests__/resolveTemplateText.test.ts`
  - 읽기만: `jam-web/src/types/database.ts`(1448줄 부근 `BadgeCondition`, 135줄 부근 `BadgeRow`), `jam-web/src/lib/badge-engine/conditionRegistry.ts`(조건 칸 등록부. 등록된 칸 목록을 꺼낼 수 있는 내보내기가 있는지 확인), `jam-web/src/lib/badgeConditionText.ts`(370줄 부근 `formatBadgeConditionText`, 숫자·시간 표기 방식 참고)

## 배경 / 문제 정의
새 배지 이미지 제작 기능은 배지를 선택하면 분류의 템플릿을 자동으로 적용하고 값을 자동으로 채운다. 그러려면 획득 조건에서 분류와 값을 기계적으로 뽑는 규칙이 먼저 있어야 한다. DB에는 분류를 가리키는 칸이 없고(`branch_key`의 일곱 가지로는 가릴 수 없다), 값 글자를 만들어 주는 기능도 없다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 함수의 입력은 배지의 `condition_json`과 `is_hidden`이다. 출력은 `{ classKey, value }` 또는 `null`이다. `classKey`는 `'metric' | 'days' | 'streak' | 'count'` 가운데 하나다(차례대로 운동 수치, 쌓은 날, 이어 온 날, 횟수와 양). 분류의 한글 이름도 같은 모듈에서 내보낸다.
- 부수 효과가 없는 순수 함수로 만든다. DB를 읽지 않는다. 서버와 브라우저 양쪽에서 불러 쓸 수 있어야 한다(서버 전용 모듈을 들여오지 않는다).
- 숫자는 천 단위 쉼표를 넣고, 소수는 조건에 적힌 그대로 둔다(21.1, 42.195, 7.5).

#### 규칙표
| 조건 칸 | 분류 | 값의 꼴 | 예 (조건 → 값) |
|---|---|---|---|
| `single_distance_km`, `distance_km` | metric | `{n}km` | `{ single_distance_km: 21.1 }` → `21.1km`, `{ distance_km: 2500 }` → `2,500km` |
| `single_elevation_m`, `elevation_gain_m`, `max_elevation_m` | metric | `{n}m` | `{ max_elevation_m: 1947 }` → `1,947m` |
| `duration_minutes` | metric | 60분 미만은 `{n}분`, 60분 이상은 `{h}시간` 또는 `{h}시간 {m}분` | `60` → `1시간`, `90` → `1시간 30분`, `45` → `45분` |
| `max_pace_sec_per_km` | metric | `{m}분 {s}초`, 초가 0이면 `{m}분` | `375` → `6분 15초`, `300` → `5분` |
| `personal_record_break` | metric | 지표가 거리면 `최장 거리`, 페이스면 `최고 페이스` | `personal_record_break_metric`으로 가린다 |
| `streak_days` | streak | `{n}일 연속` | `14` → `14일 연속` |
| `active_week_streak`, `jam_week_streak`, `return_streak_weeks` | streak | `{n}주 연속` | `{ active_week_min_days: 3, active_week_streak: 4 }` → `4주 연속` |
| `return_gap_days` | streak | `{n}일 만에` | `7` → `7일 만에` |
| `active_days_count`, `same_spot_checkin_days` | days | `{n}일` | `100` → `100일` |
| `total_count` (`time_range`나 `day_of_week`와 함께 쓰일 때) | days | `{n}일` | `{ time_range: …, total_count: 5 }` → `5일` |
| `jam_week_count`, `full_week_count` | days | `{n}주` | `{ jam_week_min_earned: 230, jam_week_count: 5 }` → `5주` |
| `full_season_year_count`, `checkin_season_year_count` | days | `{n}년` | `3` → `3년` |
| `capsule_open_count`, `locked_item_open_count`, `combine_success_count`, `cross_tribe_combine_success_count`, `dropped_item_picked_up_count`, `pickup_item_count`, `collection_complete_count`, `mission_complete_count` | count | `{n}회` | `{ capsule_open_count: 5 }` → `5회` |
| `new_checkin_badge_count` | count | `{n}개`, 다만 1이면 `첫 체크인` | `50` → `50개`, `1` → `첫 체크인` |
| `distinct_activity_type_count` | count | `{n}가지` | `3` → `3가지` |
| `other_tribe_item_kinds_count` | count | `{n}종` | `20` → `20종` |
| `follower_count`, `following_count` | count | `{n}명` | `20` → `20명` |
| `chapter_reached` | count | `챕터 {n}` | `10` → `챕터 10` |
| `jam_total_earned`, `jam_weekly_earned` | count | `잼 {n}` | `1250` → `잼 1,250`, `110000` → `잼 110,000` |

- **보조 칸:** `activity_type`, `active_week_min_days`, `jam_week_min_earned`, `time_range`, `day_of_week`, `repeat_count`는 그 자체로 분류를 정하지 않는다. 다른 칸의 전제이거나 종목·시간대 한정이다.
- **우선순위:** 한 조건에 규칙표의 칸이 둘 이상 있으면 streak 칸이 먼저, 그다음 days, metric, count 순으로 본다. 예: `{ jam_week_min_earned: 230, jam_week_streak: 4 }` → streak `4주 연속`.
- **밤 배지:** `is_hidden`이 참이고 조건에 `time_range`가 있으며 규칙표의 다른 칸이 없으면 days `밤`을 돌려준다.
- **판정 불가:** 규칙표와 보조 칸 어디에도 없는 칸만 있거나 조건이 비어 있으면 `null`을 돌려준다. 예외를 던지지 않는다.
- 조건 칸 이름이 위 표와 `BadgeCondition` 타입에서 다르면(오타, 이름 변경) 타입에 있는 이름을 따르고 완료 보고의 `alerts`에 `[참고]`로 적는다. 표에 적힌 칸이 타입에 아예 없으면 그 줄은 만들지 않고 같은 방식으로 알린다.
- **새 칸 감시:** `conditionRegistry.ts`가 등록된 조건 칸의 목록을 내보내고 있으면, 그 목록의 모든 칸이 «규칙표», «보조 칸», «아직 지원하지 않음»(이 모듈 안에 명시한 목록) 셋 중 하나에 들어 있는지 확인하는 시험을 더한다. 새 조건 칸이 생겼을 때 이 시험이 실패해서 분류를 정하게 만들려는 것이다. 목록을 꺼낼 방법이 없으면 이 시험은 만들지 않고 `alerts`에 `[참고]`로 적는다.

## 구현 계획
1. `resolveTemplateText.ts`에 분류 키 타입, 분류 한글 이름, 대응표(칸 → 분류와 값 만드는 함수), 보조 칸 목록, 지원하지 않는 칸 목록을 둔다.
2. `resolveBadgeTemplateText(input)`이 우선순위 순서로 대응표를 훑어 첫 번째로 맞는 칸의 결과를 돌려준다.
3. 시험 파일에 규칙표의 예를 모두 옮기고, 우선순위·밤 배지·판정 불가·새 칸 감시 시험을 더한다.
4. PRD는 이 회차에서 고치지 않는다(화면에 드러나는 변경이 없다. 상위 티켓의 구현 계획에 적혀 있다).

## 완료 조건
- 규칙표의 «예» 칸에 적힌 조건을 넣으면 적힌 값과 분류가 나온다. 재현 경로: `cd jam-web && npx vitest run src/lib/admin/activityBadgeTemplate`.
- `{ jam_week_min_earned: 230, jam_week_streak: 4 }`는 streak `4주 연속`, `{ jam_week_min_earned: 230, jam_week_count: 5 }`는 days `5주`가 나온다.
- `is_hidden`이 참이고 `time_range`만 있는 조건은 days `밤`이 나온다.
- 규칙표에 없는 칸만 있는 조건과 빈 조건은 `null`이 나오고 예외가 나지 않는다.
- 새 모듈이 서버 전용 모듈(`@/lib/supabase/server` 등)을 들여오지 않는다.
- `scripts/verify.sh`의 검사를 통과한다.
