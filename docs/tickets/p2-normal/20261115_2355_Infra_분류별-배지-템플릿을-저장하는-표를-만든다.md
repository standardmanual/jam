# [Infra] 분류별 배지 템플릿을 저장하는 표를 만든다

## 핵심 요약
- 요구사항: 액티비티 배지 템플릿(SVG)을 분류마다 하나씩 저장하는 표 `activity_badge_templates`를 만드는 SQL 파일과 되돌림 SQL 파일을 작성하고, 타입 정의를 더한다. SQL 실행은 카리나가 한다(상위 티켓 20261115_2353의 2회차).
- 구현 계획: 표를 새로 더하기만 하는 확장 단계다. 기존 표와 칸은 건드리지 않는다. 어드민 API가 서비스 권한으로만 읽고 쓰므로 RLS를 켜고 정책은 두지 않는다.
- 관련 파일:
  - 새 파일 `jam-web/supabase/migrations/344_activity_badge_templates.sql`, `jam-web/supabase/migrations/344_activity_badge_templates_down.sql` (번호는 작성 시점의 `origin/staging`에서 가장 큰 번호의 다음으로 다시 확인한다. 2026-11-15 기준 마지막은 343이다)
  - `jam-web/src/types/database.generated.ts` (`public.Tables`에 새 표의 `Row`·`Insert`·`Update`를 기존 표와 같은 형식으로 더한다)
  - `jam-web/src/types/database.ts` (새 `ActivityBadgeTemplateRow` 인터페이스와 `Database` 타입의 표 항목. `asset_presets`의 Row 정의 방식을 따른다)
  - 읽기만: `jam-web/supabase/migrations/185_*.sql`(`asset_presets`를 만든 마이그레이션. 어드민 전용 표의 RLS와 권한 회수 방식), `.claude/skills/jam-work/references/db-migration-rules.md`

## 배경 / 문제 정의
새 배지 이미지 제작 기능은 분류 4개에 템플릿을 하나씩 등록해 두고, 배지를 선택하면 그 분류의 템플릿을 불러온다. 템플릿을 둘 자리가 DB에 없다. 기존 `asset_presets`는 레이어 묶음을 이름으로 저장하는 표여서, 분류마다 정확히 하나만 두는 제약과 SVG 본문 저장에 맞지 않는다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 표 이름: `public.activity_badge_templates`
- 칸:
  | 칸 | 타입 | 제약 | 뜻 |
  |---|---|---|---|
  | `class_key` | text | 기본 키. `metric`, `days`, `streak`, `count`만 허용(CHECK) | 템플릿 분류. 분류마다 한 줄 |
  | `svg` | text | NOT NULL | 템플릿 SVG 본문 |
  | `slots` | jsonb | NOT NULL, 기본값 `'{}'` | SVG에서 읽어 낸 이름 자리와 값 자리의 정보 |
  | `default_params` | jsonb | NOT NULL, 기본값 `'{}'` | 색과 글자의 기본 조정값 |
  | `updated_by` | text | NULL 허용 | 마지막으로 고친 운영자의 이메일 |
  | `created_at` | timestamptz | NOT NULL, 기본값 `now()` | |
  | `updated_at` | timestamptz | NOT NULL, 기본값 `now()` | |
- RLS를 켜고 정책을 만들지 않는다. `anon`과 `authenticated`의 권한을 명시적으로 회수한다(`REVOKE ALL … FROM anon, authenticated`). 서비스 권한만 읽고 쓴다.
- `class_key`의 허용값은 티켓 20261115_2354의 분류 키와 같아야 한다.
- 되돌림 SQL은 표를 지운다. 이 표를 참조하는 다른 객체는 없다.
- SQL 파일 맨 위에 무엇을 왜 만드는지와 되돌림 파일의 이름을 주석으로 적는다.
- 아현은 SQL을 실행하지 않는다. `database.generated.ts`는 CLI로 재생성할 수 없으므로 기존 표의 형식을 따라 손으로 더한다. 카리나가 SQL을 실행한 뒤 Supabase의 생성 타입과 대조한다.

## 구현 계획
1. `origin/staging`의 `jam-web/supabase/migrations/`에서 가장 큰 번호를 확인하고 그다음 번호로 두 파일을 만든다.
2. 185번 마이그레이션의 RLS와 권한 회수 방식을 따라 작성한다.
3. 두 타입 파일에 새 표를 더한다.
4. PRD는 이 회차에서 고치지 않는다(상위 티켓의 구현 계획에 적혀 있다).

## 완료 조건
### 구현 범위 (게이트 판정 대상)
- 마이그레이션 파일과 되돌림 파일이 있고, 번호가 `origin/staging`의 기존 번호와 겹치지 않는다.
- SQL이 위 칸 표와 일치한다: 기본 키, CHECK의 허용값 4개, NOT NULL과 기본값, RLS 켜기, `anon`·`authenticated` 권한 회수.
- 되돌림 SQL이 이 표만 지운다.
- `database.generated.ts`와 `database.ts`에 새 표가 들어 있고 `npm run typecheck`가 통과한다.
- `scripts/verify.sh`의 검사를 통과한다.

### 후속 범위 (담당: 카리나, 시점: 게이트 통과 뒤)
- 되돌림 SQL을 확인하고 프로덕션 공용 DB에 SQL을 실행한다. 실행 뒤 읽기 전용 조회로 표와 권한을 확인한다.
- Supabase의 생성 타입과 `database.generated.ts`를 대조한다.

### 주요 의사결정 / 핵심 메모
- 아현 단계의 리뷰 브랜치 push가 자동 권한 검사에서 거부돼 중단됐다. 사용자가 그 브랜치의 push를 허락해 카리나가 올리고 게이트만 돌렸다.
- 첫 게이트의 FAIL은 staging의 기존 실패 시험 때문이었다(티켓 20261115_0030에서 해결). 구현 커밋을 그 위로 옮겨 다시 받았다.
- SQL 파일에는 `BEGIN`·`COMMIT`이 있지만 Supabase 마이그레이션으로 실행할 때는 같은 문장을 그 두 줄 없이 넘겼다(마이그레이션 실행이 자체 트랜잭션으로 감싼다).
- `asset_presets`를 재사용하지 않고 표를 따로 둔 까닭: 분류마다 정확히 한 줄이어야 하고 SVG 본문을 담아야 해서, 이름으로 여러 개를 저장하는 프리셋 표의 구조와 맞지 않는다.
