# [Admin] 액티비티 배지 제작 화면의 배지 검색에 분류 필터를 더한다

## 핵심 요약
- 요구사항: 어드민 «액티비티 배지» 화면의 배지 검색에서 네 분류(운동 수치, 쌓은 날, 이어 온 날, 횟수와 양)로 결과를 좁힐 수 있게 한다(사용자 지시, 2026-11-16: «배지 검색 시 4가지 타입을 필터할 수 있도록 해»).
- 구현 계획: 분류는 DB 칸이 아니라 획득 조건에서 계산하는 값이다. 분류 조건이 있을 때만 검색 API가 다른 조건에 맞는 배지를 모두 읽어 분류를 계산하고, 걸러 낸 뒤 페이지를 자른다. 분류 조건이 없을 때의 동작은 바꾸지 않는다.
- 관련 파일:
  - `jam-web/src/lib/admin/activityBadgeImageSearch.ts`: `ActivityBadgeImageSearchParams`(27행), `parseActivityBadgeImageSearchParams`(46행). 여기에 `templateClass`를 더하고, 걸러서 페이지를 자르는 순수 함수를 새로 둔다
  - `jam-web/src/app/api/admin/activity-badge-image/search/route.ts`: 조건을 거는 구간(62~82행), `range`로 자르는 구간(84~92행), 응답(94~115행)
  - `jam-web/src/app/admin/activity-badge-template/BadgePicker.tsx`: `KIND_OPTIONS`(34행) 아래에 분류 선택지, `BadgeFilters`(54행), 검색 카드의 선택 상자들(104행부터)
  - `jam-web/src/app/admin/activity-badge-template/BadgeStudio.tsx`: 필터의 처음 값(29~34행), 검색 요청 본문(139~148행)
  - 시험: `jam-web/src/lib/admin/__tests__/activity-badge-image-search.test.ts`, `jam-web/src/app/admin/activity-badge-template/__tests__/BadgeStudioParts.test.tsx`(`describe('BadgePicker')` 93행부터), 새 파일 `jam-web/src/app/api/admin/activity-badge-image/search/__tests__/route.test.ts`
  - 문서: `docs/service/prd/asset-generator/PRD.md` 17.2(637행, 검색 API)와 17.5(653행부터, 제작 화면)
  - 읽기만: `jam-web/src/lib/admin/activityBadgeTemplate/resolveTemplateText.ts`(`BadgeTemplateClassKey`, `BADGE_TEMPLATE_CLASS_LABEL` 7~14행), `studioBadge.ts`(`toStudioBadgeFields`), `jam-web/src/app/api/admin/activity-badge-templates/register/__tests__/route.test.ts`(Supabase와 권한을 흉내 내는 시험의 본보기)

## 배경 / 문제 정의
제작 화면은 배지를 고르면 그 배지가 속한 분류의 템플릿을 자동으로 적용한다. 템플릿은 분류마다 하나씩 들어오고, 지금은 «운동 수치» 템플릿부터 만들고 있다. 운영자가 «운동 수치 배지만 모아서 차례로 만들기»를 하려면 검색 결과를 분류로 좁힐 수 있어야 한다. 지금 검색 조건은 이름, 종류(등급형·레벨형), 등급, 활동 종목뿐이고, 분류는 결과 표의 칸으로만 보인다.

분류는 `badges` 표의 칸이 아니다. `resolveBadgeTemplateText`가 `condition_json`과 `is_hidden`으로 계산한다. 그래서 DB 조건으로는 거를 수 없다. 액티비티 배지는 2026-11-16 기준 390개다(삭제되지 않은 것).

## 상세 요구사항

### 서비스/코드베이스 관점

#### 검색 조건 (`activityBadgeImageSearch.ts`)
- `ActivityBadgeImageSearchParams`에 `templateClass: BadgeTemplateClassKey | null`을 더한다. `parseActivityBadgeImageSearchParams`는 `raw.templateClass`가 `BADGE_TEMPLATE_CLASS_LABEL`의 키(`metric`·`days`·`streak`·`count`) 가운데 하나일 때만 받고, 그 밖의 값은 `null`로 둔다.
- 새 순수 함수 `pickActivityBadgeImageSearchPage<T extends { templateClass: string | null }>(items: T[], templateClass: BadgeTemplateClassKey, page: number): { items: T[]; total: number }`: `templateClass`가 같은 것만 남기고(순서 유지), `activityBadgeImageSearchRange(page)`의 범위로 자른다. `total`은 자르기 전의 수다.

#### 검색 API (`search/route.ts`)
- `templateClass`가 없으면 지금과 같다(DB에서 `range`로 한 페이지만 읽는다).
- `templateClass`가 있으면:
  1. 다른 조건(이름, 종류, 등급, 활동 종목, 계열, JAM 카테고리 제외)과 정렬(`name`, `level`, `id`)은 그대로 걸고, 페이지 범위 대신 1,000줄씩 끝까지 읽는다(한 번에 받은 줄이 1,000보다 적으면 멈춘다). Supabase 질의는 한 번 쓰면 다시 쓸 수 없으니, 조건을 거는 부분을 함수로 묶어 읽을 때마다 새로 만든다.
  2. 읽은 줄을 지금과 같은 응답 항목으로 바꾼다(`toStudioBadgeFields` 포함).
  3. `pickActivityBadgeImageSearchPage`로 걸러서 자른다.
  4. 응답의 꼴은 그대로다: `badges`, `total`(걸러 낸 뒤의 수), `page`, `pageSize`, `totalPages`.
- DB 오류의 응답(500, «배지를 검색하지 못했어요. 잠시 후 다시 시도해 주세요.»)은 두 경로가 같다.
- 분류를 정하지 못한 배지(`templateClass`가 `null`)는 분류 조건이 있으면 결과에 들어가지 않는다.

#### 화면
- `BadgeFilters`에 `templateClass: string`을 더한다. 처음 값은 `ALL_VALUE`다.
- `BadgeStudio`의 검색 요청 본문에 `templateClass`를 싣는다. `ALL_VALUE`이면 싣지 않는다.

### UI/UX 관점 (해당 시)
- 검색 카드의 이름 입력 칸 바로 다음에 «분류» 선택 상자를 둔다(종류·등급·활동 종목보다 앞). 기존 선택 상자와 같은 `Select` 컴포넌트(`@/components/admin/ui/select`)를 쓴다. 네이티브 `select`는 쓰지 않는다.
- 선택지: «전체 분류», «운동 수치», «쌓은 날», «이어 온 날», «횟수와 양». 이름은 `BADGE_TEMPLATE_CLASS_LABEL`에서 가져온다(다시 적지 않는다).
- 다른 선택 상자와 마찬가지로, 값을 바꾼 뒤 «검색»을 눌러야 결과가 바뀐다.
- 폭은 `sm:w-36`으로 종류 선택 상자와 맞춘다.

## 구현 계획
1. `activityBadgeImageSearch.ts`에 `templateClass` 해석과 `pickActivityBadgeImageSearchPage`를 더하고 시험을 더한다.
2. `search/route.ts`에 분류 조건이 있을 때의 경로를 더하고, 라우트 시험을 새로 만든다. 시험은 `register` 라우트 시험처럼 Supabase와 권한만 흉내 낸다.
3. `BadgePicker.tsx`에 선택 상자를, `BadgeStudio.tsx`에 처음 값과 요청 본문을 더하고 `BadgeStudioParts.test.tsx`를 고친다.
4. PRD 17.2에 요청의 `templateClass`를, 17.5에 분류 필터를 적는다.

## 완료 조건
### 구현 범위 (게이트 판정 대상)
- `parseActivityBadgeImageSearchParams({ templateClass: 'metric' })`의 `templateClass`가 `'metric'`이고, `'etc'`·숫자·빈 글자·없음은 `null`이다.
- `pickActivityBadgeImageSearchPage`: 분류가 섞인 120개(그 가운데 `metric` 70개)를 주면 1쪽은 `metric` 50개와 `total: 70`, 2쪽은 20개와 `total: 70`, 3쪽은 0개다. 순서가 바뀌지 않는다.
- 라우트(흉내 낸 Supabase): `templateClass: 'metric'`으로 부르면 응답의 `badges`가 모두 `templateClass: 'metric'`이고, `total`과 `totalPages`가 걸러 낸 뒤의 수로 나온다. `templateClass` 없이 부르면 지금처럼 `range`로 한 페이지만 읽고 DB의 `count`가 `total`이 된다. 권한이 없으면 403이다. 1,000줄을 넘는 경우(흉내 낸 1,200줄)에 두 번 읽어 모두 거른다.
- `BadgePicker`가 «분류» 선택 상자와 선택지 다섯 개를 그린다. `BadgeStudio`가 분류를 고른 채 검색하면 요청 본문에 `templateClass`가 실리고, «전체 분류»면 실리지 않는다.
- 분류 조건 없이 검색한 결과와 일괄 등록(`familyKey`로 부르는 검색)이 그대로다.
- PRD 17.2와 17.5가 갱신돼 있다.
- 재현 경로: `cd jam-web && npx vitest run src/lib/admin src/app/admin/activity-badge-template src/app/api/admin/activity-badge-image`.
- 리뷰 브랜치의 CI verify가 success다.

### 후속 범위 (담당: 카리나, 시점: 게이트 통과 뒤 머지 전)
- 로컬 어드민 실렌더: «운동 수치»를 골라 검색하면 결과 표의 분류 칸이 모두 «운동 수치»이고, 쪽수가 맞게 나오는지 본다. 8-2회차의 화면 확인과 함께 한다.
- 아현과 민지는 격리 워크트리에서 화면 실렌더를 시도하지 않는다.

### 주요 의사결정 / 핵심 메모
- 분류를 DB 칸으로 만들지 않은 까닭: 분류는 획득 조건에서 계산하는 값이고 규칙(`resolveTemplateText.ts`)이 단일 원천이다. 칸으로 두면 규칙을 고칠 때마다 프로덕션 공용 DB의 값을 다시 채워야 한다. 액티비티 배지는 390개라서 모두 읽어 계산해도 부담이 작다.
- «분류 없음»만 모아 보는 선택지는 넣지 않았다. 사용자가 말한 것은 네 분류다.
- 바뀌는 파일이 여덟 개이고 100줄을 넘어 `plan_only` 기준을 넘는다. 파일 단위 계획과 함수 꼴, 시험 기대값을 이 티켓에 적었으므로 면제를 넘긴다.
- `BadgeStudio.tsx`는 8-2회차(제작 화면이 코드의 템플릿을 쓰게 하는 일)도 고친다. 그래서 이 티켓을 먼저 머지한 뒤에 8-2회차 티켓을 만든다.

### 잔여 이슈
- 아현의 리뷰 브랜치 push가 자동 권한 검사에서 거부됐다. 사용자가 «올려»라고 허락한 뒤 카리나가 같은 워크트리에서 같은 커밋을 올리고 게이트만 돌렸다(코드 수정 없음).

- 범위 밖 발견물(민지, 참고/성능): 분류로 검색할 때마다 조건에 맞는 배지를 모두 읽는다. 지금은 390개라 부담이 작다. 티켓 20261116_1514로 넘겼다.
