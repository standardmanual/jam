# [Infra] 홈피드 개편 2회차: today_cards에 새 카드 구성 값을 저장할 칸을 더한다 (db)

## 핵심 요약

- 요구사항: 상위 티켓 20261120_2026의 2회차. 새 카드 유형·박스·색·칩·도장·목록형·컬렉션 모션의 값을 담을 칸을 `today_cards`에 더한다(확장 단계만). 모든 칸은 비워 둘 수 있고, 비어 있으면 자동 규칙(5회차)이 정한다.
- 구현 계획: 마이그레이션 349와 되돌림 SQL을 쓰고, 드라이런과 롤백 실측을 거쳐 메인 세션이 실행한다. 생성 타입, 수기 타입, PRD §10을 새 칸에 맞춘다. 배정 코드는 만들지 않는다.
- 관련 파일: `jam-web/supabase/migrations/349_today_cards_feed_redesign_columns.sql`(+`_down.sql`), `jam-web/src/types/database.generated.ts`, `jam-web/src/types/database.ts`, `docs/service/prd/home-feed/PRD.md` §10, `docs/service/prd/02_DATA_MODEL.md`.

## 배경 / 문제 정의

1회차(20261120_2129)가 규격을 문서로 확정했다. 3회차(화면 부품)가 다른 세션에서 병렬로 진행 중이고, 4회차(카드 유형 화면)부터는 카드가 값을 저장할 자리가 있어야 한다. 지금 `today_cards`에는 색·칩·박스를 담는 칸이 없고, 옛 모양 `shape`는 새 유형과 이름이 겹친다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 칸 이름과 구조를 규격(PRD §6 「개편 규격」)과 기존 코드(`cards.ts`, `cardView.ts`, `registerInput.ts`, `homeFeedFields.ts`)를 읽고 정한다.
- DB는 staging·프로덕션 공용이다. 확장만 하고, 지금 프로덕션 코드가 새 칸을 모르고도 그대로 동작함을 확인한다.
- UI와 화면 코드는 건드리지 않는다(`jam-web/design-system/`, `jam-web/src/components/today/`).

### 정한 칸 15개와 이유

| 칸 | 형식 | 정한 이유 |
|---|---|---|
| `feed_type` | text, 값 8개 | 새 유형 키. 옛 `shape`의 `ticket`·`hero`·`list`와 새 박스 모양 «티켓»이 같은 말이라 `shape`·`card_shape`·계측 집계가 섞이는 것을 피하려 별도 칸으로 했다. `shape`는 옛 카드를 위해 그대로 둔다 |
| `box_shape` | text, `round`·`ticket`·`stamp`·`wave`·`bump` | 박스 모양 5가지(우표=`stamp`, 물결=`wave`, 반원 돌출=`bump`). 텍스트 박스·이미지 마스크·아이템 배지 박스가 같은 값을 쓴다 |
| `box_kind` | text, `text`·`image_mask` | 박스 용도. `feed_type`의 `text_box`와 헷갈리지 않게 값 이름을 `text`로 했다 |
| `bg_color_key`·`chip_color_key`·`box_color_key` | text, 색 키 15개 | 카드에는 hex가 아니라 키를 저장한다(규격). 색 값은 디자인 시스템이 정본이라 DB에는 목록만 둔다 |
| `chips` | JSONB 배열 ≤2 | 칩 목록. 아래 구조 |
| `title_chip_words` | text[] ≤2 | 제목 문자열은 그대로 두고 낱말 목록만 따로 저장한다(규격) |
| `show_description` | boolean | 설명 노출 여부. NULL이면 유형 기본값 |
| `stamp_enabled`·`stamp_slot` | boolean·text | 도장 사용 여부와 자리. JSONB 하나로 묶지 않고 두 칸으로 했다(값이 둘뿐이라 조회·수정이 단순하다) |
| `list_items` | JSONB 배열 ≤3 | 목록형 항목(이름·그림·링크) |
| `list_more_href` | text | «→» 칸의 대표 페이지 주소. 항목과 따로 있는 값이라 별도 칸이다 |
| `collection_burst` | JSONB 배열 ≤4 | 컬렉션 배지 4개의 도착 위치 |
| `feed_seed` | bigint, 0 이상 2^32 미만 | 무작위 값을 고정하는 시드. 32비트 부호 없는 정수를 담으려면 integer가 모자라 bigint로 했다 |

**NULL의 뜻**: 모든 칸이 NULL이면 «자동 규칙이 정한다». 예외 둘: 제목 칩 낱말과 도장은 NULL이 «없음»이다. `chips`는 NULL(자동)과 `[]`(칩 없음)를 구분한다 — «배지만» 유형처럼 칩을 일부러 쓰지 않는 카드를 자동 규칙이 다시 채우지 않게 하려는 것이다.

**JSONB 구조**(DB는 아래 형태만 지킨다. 알 수 없는 키는 허용해 뒤 회차에서 키를 더해도 함수를 고치지 않게 했다)

- `chips`: `[{kind, source?, text?, slot?, tilt?}]`, 최대 2개. `kind`는 `value`(값 칩)·`phrase`(문구 칩)·`label`(구분 칩). `value`는 `source`(값의 출처 키), `phrase`는 `text`가 필수다. `label`은 자원에서 말이 정해져서 둘 다 없어도 된다. `tilt`는 −8·−6·−4·4·6·8. `slot`은 유형마다 허용 자리가 달라 코드 상수가 정본이므로 소문자·숫자·하이픈 24자 이하의 모양만 본다. 값 출처 키 목록(`mission.reward_points` 같은 이름)은 PRD가 «자동 규칙 회차에서 코드와 대조해 확정»한다고 했으므로 DB에 닫지 않았다.
- `list_items`: `[{name, href, image_url?}]`, 최대 3개. `name`·`href`는 비어 있으면 안 된다.
- `collection_burst`: `[{x, y, tilt?, size?, delay_ms?}]`, 최대 4개. `x`·`y`는 가운데에서 카드 가장자리까지를 1로 본 −1~1(카드 크기에 따라 늘고 주는 값이라 픽셀이 아니다), `size`는 규격의 68~84px, `delay_ms`는 70~210.
- 문구 칩 글자 수 상한(12자 제안)은 아직 확정 전이라 DB에 넣지 않았다. 확정되면 저장 코드가 검사한다.
- `title_chip_words`의 «제목에 그대로 들어 있어야 한다»는 DB에 넣지 않았다. 제목만 고치는 수정이 DB 오류로 막히는 것을 피하려는 것이고, 저장하는 코드(5·6회차)가 검사한다. DB는 개수(≤2)와 빈 낱말만 본다.

### 배정 시점 결정

규격 초안은 «등록 때는 이웃을 보지 않고 정하고, 편성 확정 때 겹치는 것만 다시 고른다»였다. 코드를 읽어 보니 이 안은 그대로 맞지 않는다.

- 홈 피드는 `sortHomeCards`가 유저와 날짜를 씨앗으로 순서를 섞는다(`getTodayCards`, 새 카드 24시간 이내만 앞). 그래서 한 카드의 이웃은 유저마다, 날마다 다르다. «편성 확정 때 이웃과 겹치는 것을 다시 고른다»는 저장된 순서(`sort_order`)의 이웃만 볼 수 있어 실제 화면의 이웃을 보장하지 못한다.
- 또 한 번 저장한 값을 다시 고르면 «배정한 값은 이후에 바뀌지 않는다»와 부딪친다.

**결정(추천안)**: ① 에이전트가 낸 카드는 운영 항목이 승인되어 `today_cards`에 들어갈 때, 어드민 카드는 저장할 때 값을 정한다. 사용자가 지정한 값은 덮어쓰지 않는다. ② 정하는 순간 이웃은 보지 않는다. ③ 대신 배경색은 «같은 시기에 노출되는 카드의 집합»(`starts_at`~`ends_at`이 겹치는 활성 카드)에서 가장 덜 쓰인 색 쪽으로 고른다. 같은 날 노출되는 카드의 배경색이 골고루 퍼지면 어떤 순서로 섞여도 같은 배경이 붙을 가능성이 낮아진다. ④ 값은 저장한 뒤 바꾸지 않는다. ⑤ 화면에서 우연히 같은 배경이 붙는 경우는 허용한다(필요하면 4회차가 저장값을 바꾸지 않는 보정을 정한다). 이 칸 구조는 위 어느 선택에도 새 칸이 필요하지 않다. 구현은 5회차다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

`today_cards`에 새 카드 구성 값 15칸(전부 NULL 허용)과 허용 값 CHECK 13개, JSONB 구조 검증 함수 4개를 더했다(마이그레이션 349, 확장 단계). 값을 채우는 코드는 없다(5·6회차). 옛 `shape`·`title_in_image`와 기존 카드 121건은 그대로다. 실행은 2026-11-20 21:4x KST에 메인 세션이 Supabase MCP로 했다(적용 이름 `349_today_cards_feed_redesign_columns`).

### 실행 결과

- **드라이런(DO 블록 + 일부러 낸 오류로 롤백)**: 첫 시도에서 검증 함수의 구멍 둘을 잡았다. 필수 키가 아예 없을 때 `jsonb_typeof`가 NULL을 돌려줘 비교가 통과했다(예: `chips=[{"kind":"value"}]`, `list_items=[{"name":"a"}]`). 비교를 `IS DISTINCT FROM`으로 고쳤다. 고친 뒤: 모든 칸에 유효한 값을 채우는 갱신 성공, 잘못된 값 25가지(유형·박스·색 키 오타, 칩 3개, 기울기 5도, 슬롯 대문자, 필수 키 없음, 항목 4개, 위치 범위 밖, 크기 90, 지연 300, 시드 −1·2^32 등)가 모두 거절됐고 새는 값 0. 롤백 뒤 칸 27개·함수 0개·행 121개로 DB가 그대로임을 확인했다.
- **실행**: `apply_migration`으로 적용했다(성공).
- **실행 직후 읽기 전용 확인**: 칸 27개 → 42개(새 칸 15개 모두 NULL 허용), 검증된 제약 13개, 검증 함수 4개, 행 121개 그대로, 새 칸에 값이 들어간 행 0개, 칸 설명(COMMENT) 적용.
- **되돌림 SQL 실측**: 적용된 상태에서 `_down.sql`과 같은 문장을 DO 블록으로 돌려 칸 27개·함수 0개로 돌아가는 것을 확인하고 오류로 롤백했다. 롤백 뒤 칸 42개·함수 4개 상태 그대로.
- **영향 범위**: 공용 DB라 프로덕션에 즉시 반영됐다. 새 칸은 NULL이라 지금 배포된 코드의 화면과 등록 경로는 달라지지 않는다.

### 기존 동작 확인 (프로덕션 코드가 새 칸을 모르고도 그대로 동작함)

- 홈 화면의 조회는 `today_cards`를 `select('*')`로 읽는다(`getTodayCards`). 칸이 늘어도 응답에 NULL 칸이 더 실릴 뿐 해석에 쓰이지 않는다. 읽기 전용으로 같은 조건(활성·노출 기간·태그)의 조회가 17건을 그대로 돌려줌을 확인했다.
- 기존 카드 등록 경로(`buildTodayCardInsertPayload`와 같은 열 집합, 새 칸 없음)로 삽입하는 문장을 롤백 실측으로 돌려 삽입 성공, 읽은 행의 새 칸이 모두 NULL임을 확인했다.
- 코드에서 열 이름을 직접 고르는 조회·갱신(`select('id, starts_at')` 등)은 새 칸과 무관하다.
- 타입 검사 `tsc --noEmit` 오류 0건. 홈피드·어드민 관련 시험 350파일 9,049건 통과.

### 주요 의사결정 / 핵심 메모

- 2026-11-20: 새 유형 키는 `feed_type`(옛 `shape`와 별도). 모든 칸 NULL 허용, NULL은 자동. 색은 키만 저장. JSONB는 구조만 DB가 지키고 자리 이름·값 출처 키는 코드 상수에 맡긴다.
- 2026-11-20: 배정 시점은 등록(승인·저장) 때 이웃을 보지 않고 정한다. 이웃 겹침은 «같은 시기 노출 카드의 배경색 사용 빈도 분산»으로 줄이고, «편성 확정 때 재선택»은 쓰지 않는다(홈 순서가 유저·날짜마다 섞여 저장된 순서가 실제 이웃이 아니고, 한 번 정한 값을 바꾸지 않는다는 원칙과 부딪친다).
- 이 일을 하는 동안 `registerInput.test.ts`의 «생성 타입 컬럼 대조» 시험이 새 칸 때문에 실패했다. 등록 경로가 칸을 빠짐없이 채우는지 보는 안전장치이므로, 새 칸 15개를 «6회차가 채울 때까지 제외» 목록으로 명시했다. 6회차가 등록 페이로드에 새 칸을 채울 때 이 제외 목록을 지운다.

- 생성 타입은 `generate_typescript_types` 전체 출력(5,700줄)을 받지 않고 `today_cards` 블록에 기존 형식대로 새 칸 15개를 알파벳 순으로 더했다. 칸·널 허용 여부는 `information_schema`로 대조했다.
