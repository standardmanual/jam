# [Feature] 홈피드 개편 4회차-1: 색 자동 규칙과 칩 배정 계산을 만든다

## 핵심 요약

- 요구사항: 상위 티켓 20261120_2026의 4회차(카드 유형)를 넷으로 나눈 첫째다. 화면은 만들지 않고, 카드에 색·칩 자리·기울기를 자동으로 정해 주는 계산 함수와 DB 값 칩 규칙표를 `lib/today/`에 새 파일로 만든다. 4-2부터는 이 함수가 돌려주는 값을 그대로 그린다.
- 구현 계획: 아래 「구현 계획」의 파일 단위 표를 따른다. 유형은 `feature`(순수 계산과 시험, 화면 없음)다.
- 관련 파일: 아래 표. 규격 정본은 `docs/service/prd/home-feed/PRD.md` §6 끝의 「개편 규격」 절 «색»·«칩»·«구현 때 지킬 점»이다.

## 배경 / 문제 정의

1회차가 규격을, 2회차가 DB 칸(`today_cards.bg_color_key`·`chip_color_key`·`box_color_key`·`chips`·`feed_seed` 등)을, 3회차가 색 15개와 화면 부품(칩·박스·도장)을 마련했다. 새 카드를 그리려면 «이 카드의 배경·칩·박스 색은 무엇이고 칩은 어느 자리에 몇 도 기울여 놓는가»를 정해 주는 계산이 있어야 한다. 사용자가 색·자리를 지정하지 않은 카드(칸이 NULL)는 이 계산이 정한다. 같은 카드는 언제 어디서 열어도 같은 값이 나와야 하므로 카드 id를 시드로 쓰고 `Math.random`은 쓰지 않는다.

## 상세 요구사항

### 서비스/코드베이스 관점

- DB·마이그레이션·`src/types/`·`src/lib/admin/`·화면 컴포넌트는 건드리지 않는다. `lib/today/`에는 새 파일만 더한다(기존 `feedConstants.ts`·`boxShape.ts`·`titleChips.ts`는 읽기만 한다. 필요한 상수 추가가 있으면 추가만 한다).
- **색 규칙 함수는 hex를 입력으로 받는다**(사용자 의견 2026-11-20, 컬러셋 교체 어드민을 위한 전제). 색 키를 hex로 바꾸는 표는 호출하는 쪽이 넘기고, 규칙 함수는 `(hexA, hexB)` 같은 순수 입력만 본다. 키 표(`FEED_COLORS`)를 기본값으로 쓰는 편의 함수는 따로 둔다.
- 거르는 규칙은 PRD §6 «자동으로 거르는 규칙» 1~4번 그대로다: ① 같은 색 제외, ② 대비 규칙(상대 휘도 비 1.15 미만 / 색상 차이 30도 미만이면서 HSL 명도 차이 0.09 미만 / 채도 0.85 초과·명도 0.4~0.62의 원색 둘이 색상 차이 90도 초과), ③ 키즈 규칙(채도 높은 원색 둘의 조합 / 명도 0.7 초과 밝은 색 둘이 색상 차이 40도 초과), ④ 명도 규칙(칩과 칩 아닌 것은 CIE L* 차이 15 이상이거나 색상 차이 150도 이상). 아래 순서로 걸러 남은 조합만 쓴다.
- **정답 대조 시험**: 15색의 210가지 순서쌍에서 대비 규칙 50, 키즈 규칙 36, 명도 규칙 50이 빠져 74가지가 남는다(PRD가 적은 2026-11-20 샘플 계산값이다. 규칙을 순서대로 적용한 누적 개수다). 구현 결과가 이 숫자와 다르면 **숫자를 맞추려 임계값이나 규칙을 바꾸지 않는다.** 어느 규칙에서 몇 개가 다른지와 가능한 원인(HSL 계산 방식, 휘도 공식, 순서쌍과 무순서쌍의 차이)을 티켓의 「주요 의사결정」에 적고, 시험은 «지금 구현의 값»을 고정하되 PRD 값과 어긋난다는 표시를 남긴다. 어긋남은 사용자와 채원이 판단한다.
- **자동 배정**(PRD «자동 배정»): 입력은 `(시드, 지정값 일부, 같은 시기 노출 카드의 배경색 사용 빈도 표)`이다. 사용자가 지정한 값(`bg`·`chip`·`box` 중 NULL이 아닌 것)은 덮어쓰지 않는다. 배경색은 규칙을 통과하는 쪽에서 «같은 시기에 가장 덜 쓰인 색»을 고르고 동률이면 시드로 정한다. 그 배경과 규칙을 통과하는 색에서 칩 색과 박스 색을 시드로 고른다. 칩 색과 박스 색도 서로 규칙을 통과해야 한다. 흰색은 자동 배정에 쓰지 않는다. 통과하는 조합이 하나도 없으면(사용자 제외 조합이 많을 때) 정해진 안전한 기본 조합으로 되돌리고, 그렇게 됐다는 표시를 결과에 담는다. 사용자가 검수 화면에서 제외한 조합 목록을 입력으로 받을 수 있게 한다(저장은 6회차).
- **칩 자리·기울기 배정**: 유형마다 허용 자리 목록(PRD 카드 유형 표의 «칩 자리 묶음»)과 한 유형이 가질 수 있는 칩 개수를 상수로 둔다(새 파일 `feedChipSlots.ts`). 자리 이름은 소문자·숫자·하이픈 24자 이내로 한다(2회차 DB 검증 규칙). 칩이 2개면 서로 대각선 자리에 두고, 자리가 하나뿐인 유형(목록형의 오른쪽 위, 드랍·픽업의 박스 줄 위)은 칩을 1개만 둔다. 기울기는 `FEED_TILTS` 여섯 값 중 시드로 고른다. 사용자가 지정한 자리·기울기는 덮어쓰지 않는다. 같은 카드의 두 칩 기울기가 같은 방향·같은 크기로 겹치지 않게 한다.
- **시드 무작위**: `boxShape.ts`의 `createRng`·`hashSeed`를 재사용한다(새로 만들지 않는다). 같은 시드는 같은 값이고, 서버와 브라우저가 같다.
- **DB 값 칩 규칙표**(PRD «DB 값 칩의 규칙표(초안)»): 자원(미션·액티비티 배지·컬렉션·체크인 장소·드랍픽업)마다 어떤 값을 칩으로 낼지와 구분 칩 문구를 한 표로 둔다(`feedValueChips.ts`). 값 하나를 칩 문구로 바꾸는 함수를 포함한다: 미션 남은 기간(종료 7일 이내 «N일 남음», 지난 것은 칩 없음), 보상 포인트, 조건 값(«걷기 8km»), 배지 달성 기준(«10회»·«700m»·«14일 만에»)·레벨(«Lv.1»), 컬렉션 아이템 수, 체크인 필요 배지 수(«배지 3종류»)·장소 이름. **정확한 칸 이름은 코드를 읽어 대조해 정한다**(`CardView`·`cardView.ts`·`cards.ts`가 자원별로 어떤 값을 갖는지). 값이 없거나 0이면 칩을 만들지 않는다. 카드당 칩 최대 2개 상한은 배정 쪽에서 지키고, 값 칩 후보는 우선순위 순서로 낸다.
- 서버 전용 값(시각)은 인자로 받는다(`now`를 직접 읽지 않는다). 시험이 날짜를 고정할 수 있어야 한다. 시간 표시는 KST 기준이다.
- 문구 칩 글자 수 상한은 12자 제안이다(PRD 1회차 후속). 길이 검증 함수를 두되 **막지 않고 경고 정보만** 돌려준다.

### UI/UX 관점

- 화면 변경 없음. 사용자 노출 문구는 값 칩 문구(«N일 남음» 등)뿐이고 해요체가 아닌 칩 라벨이다. `docs/service/writing/UX_WRITING_GUIDELINE.md`의 고정 용어를 쓴다(획득·드랍·픽업·체크인·포인트).

## 완료 조건

- 새 파일 4개와 시험 3개가 있고 `scripts/verify.sh`가 통과한다.
- 15색 순서쌍 필터의 단계별 제외 개수가 PRD 값(50·36·50, 남는 74)과 같거나, 다르면 차이와 원인이 「주요 의사결정」에 적혀 있다.
- 같은 시드는 같은 배정을 낸다. 100장 이상 배정 시험에서 규칙 위반과 제외 목록 겹침이 0이다.
- 규칙 함수가 hex를 입력으로 받고, 색 키 표에 묶여 있지 않다.
- 기존 파일(`feedConstants.ts` 등)은 추가 외에 바뀌지 않았다.

### 구현 범위 (게이트 판정 대상)

위 표의 8개 파일만이다. 화면 컴포넌트·DB·타입·어드민·`cards.ts`는 이 티켓의 범위 밖이다.
