# [Feature] 홈피드 개편 6회차-1: 운영 묶음 카드 항목의 새 칸 읽기와 검증과 등록 변환을 만든다

## 핵심 요약

- 요구사항: 6회차(에이전트 자동)의 첫 조각이다. 에이전트(윤진)가 내는 운영 묶음의 `home_feed_card` 항목이 개편 칸(유형·박스·색·칩·제목 속 칩·설명 노출·도장·목록 항목·컬렉션 모션)을 **선택 칸**으로 실을 수 있게 한다. 묶음 검증이 그 칸을 읽어 형식 오류를 알리고, 승인된 항목이 `today_cards` insert 페이로드로 바뀔 때 새 칸이 실린다. 칸을 안 적은 기존 묶음은 이전과 똑같이 검증·등록된다.
- 구현 계획: 아래 표. 유형은 `feature`(화면 없음). 등록 때 비어 있는 값을 자동 규칙으로 정해 고정하는 일(시드·색)은 6-2, 운영툴 미리보기는 6-3, 윤진 규칙·문서는 6-4가 한다.
- 관련 파일: `jam-web/src/lib/admin/opsInbox/validate.ts`(`validateOpsCardFields`), `registerInput.ts`(`toTodayCardRegisterInput`, 칸 목록 상수), `jam-web/src/lib/admin/registerChecks/homeFeedFields.ts`(`buildTodayCardInsertPayload`), 5-1이 만든 `jam-web/src/lib/admin/feedCardFields.ts`(`validateFeedCardColumns`·`pickFeedCardColumns` 등). 규격 정본은 `docs/service/prd/home-feed/PRD.md` §6 끝 「개편 규격」, 묶음 형식은 `docs/service/prd/ops-tool/PRD.md` §8.4.

## 배경 / 문제 정의

사용자는 «에이전트는 유형·칩·색을 스스로 자동으로 정한다»고 확정했다(상위 티켓). 지금 묶음의 카드 항목은 옛 7모양(`shape`)을 필수로 요구하고 새 칸을 읽지 않아, 에이전트가 새 유형을 기획해도 묶음에 담을 수 없다. DB·화면·어드민 수동 작성(5회차)은 끝났으므로 에이전트 경로만 남았다.

## 상세 요구사항

### 서비스/코드베이스 관점

- DB·마이그레이션·`src/types/`·서비스 홈 컴포넌트·어드민 저장 API(`app/api/admin/today`)·어드민 화면은 건드리지 않는다. 이미지·로고 규칙(7회차)도 범위 밖이다.
- **새 칸의 위치(결정)**: 항목의 `resource` 그룹에 DB 칸과 같은 이름의 평평한 키로 싣는다(`template_type`·`cover_image_url`·`title_in_image`가 이미 이 자리에 있다). 키: `feed_type`, `box_shape`, `box_kind`, `bg_color_key`, `chip_color_key`, `box_color_key`, `chips`, `title_chip_words`, `show_description`, `stamp_enabled`, `stamp_slot`, `list_items`, `list_more_href`, `collection_burst`. `feed_seed`는 에이전트가 정하지 않는다(등록 때 시스템이 정한다, 6-2). 에이전트가 이 키를 읽지 못하는 칸으로 보지 않도록 `registerInput.ts`의 «읽을 칸 목록»(`CARD_RESOURCE_KEYS`)에 더한다. 값 의미는 DB 칸 설명(마이그레이션 349)과 5-1의 값 의미를 따른다: 키가 없거나 `null`이면 «자동»(홈 규칙이 정한다), `chips`는 `[]`이 «칩 없음», `stamp_enabled`는 `false`가 «쓰지 않음».
- **`shape` 필수 조건**: 지금은 홈피드 카드에 `shape`가 필수다. `resource.feed_type`이 있으면 `shape`는 선택이 된다(없으면 NULL로 등록, 옛 집계용 모양은 행 값에서 홈이 판정한다). `feed_type`도 `shape`도 없으면 지금처럼 `shape` 필수 오류다. 둘 다 있으면 둘 다 저장한다. 오류 문장에 «또는 `resource.feed_type`»을 덧붙인다.
- **검증(`validateOpsCardFields`)**: `resource`의 새 칸이 하나라도 있으면 5-1의 `validateFeedCardColumns`로 구조·허용 값을 본다(허용 값 밖, 칩 3개 이상, 칩 자리 허용 밖·대각선 짝 아님, 기울기 밖, 제목 칩 낱말이 제목에 없음, 도장 자리 밖, 목록 항목 4개 이상·주소 안전하지 않음, 모션 범위 밖). 오류 문장은 운영 항목 경로(`items[2].resource.chips[0].slot` 등)를 붙여 «현상 → 원인 → 해결책»으로 쓴다. 5-1의 warnings(칩 12자 초과, 색 규칙에 걸린 조합, 목록형 항목 0개, 유형 없이 새 칸이 채워짐)는 **경고**로만 알린다(저장·승인을 막지 않는다. 이 묶음 검증의 기존 «형식 오류 → 저장은 한다» 규칙과 같다). 제목 속 칩 낱말 검사의 «제목»은 `copy.title`(또는 `resource.title`)이다. 새 칸이 모두 없으면 새 검사는 돌지 않는다.
- **순수 모듈 계약**: `homeFeedCard.ts`는 «`node:`·Supabase·서버 모듈을 값으로 가져오지 않는다»는 계약이 있고 요약창이 이 파일을 클라이언트 번들로 끌어온다. 5-1의 `feedCardFields.ts`는 `isSafeListHref`를 `components/today/feed/FeedGalleryListCard.tsx`(`next/link`·`SafeImage` 사용)에서 값으로 가져오고 있어 이 경로로 끌려오면 번들 경계가 위험하다. 따라서 **먼저 `isSafeListHref`를 순수 파일 `jam-web/src/lib/today/listHref.ts`(신규)로 옮기고**, `FeedGalleryListCard.tsx`는 같은 이름으로 다시 내보내(동작·이름 불변) 기존 가져오기·시험이 깨지지 않게 하며, `feedCardFields.ts`는 순수 파일에서 가져오게 한다. 옮긴 뒤 `scripts/check-client-server-imports`(verify의 `client-server-imports` 단계)가 통과해야 한다.
- **등록 변환(`toTodayCardRegisterInput` → `buildTodayCardInsertPayload`)**: `registerInput.ts`가 `resource`의 새 칸을 읽어 `buildTodayCardInsertPayload`의 선택 인자(예: `feedColumns`)로 넘기고, `buildTodayCardInsertPayload`는 그 칸을 insert 페이로드에 싣는다. 인자를 안 주면 새 칸 키를 **페이로드에 넣지 않는다**(지금 반환 객체 그대로여야 기존 등록 스크립트(`registerHomeFeedBundle.mjs`)와 «생성 타입 컬럼 대조» 시험이 그대로다). 값은 5-1의 `buildFeedCardColumns` 같은 정규화(빈 문자열 → `null`, 문구 trim)를 따른다. `feed_seed`는 이 티켓에서 넣지 않는다(6-2).
- **읽지 못한 칸 경고**: `warnUnreadKeys`는 읽을 목록에 없는 키를 경고한다. 새 키를 목록에 더해 경고가 나지 않게 하고, 알 수 없는 새 이름(오타)은 지금처럼 경고한다.
- **정책 대시보드**: 규칙·밸런스 수치를 바꾸지 않으므로 `policiesData.ts`를 갱신하지 않는다(판단을 「주요 의사결정」에 적는다).

## 완료 조건

- 새 칸을 적은 `home_feed_card` 항목이 검증을 통과하고 승인 뒤 변환하면 insert 페이로드에 새 칸이 실린다. 칸을 안 적은 기존 항목·기존 등록 스크립트의 결과는 이전과 완전히 같다(기존 시험 불변).
- `feed_type`만 있고 `shape`가 없는 항목이 통과하고, 둘 다 없으면 오류다.
- 잘못된 새 칸 값은 운영 항목 경로가 붙은 해요체 문장으로 알린다. 경고는 저장·승인을 막지 않는다.
- `isSafeListHref`가 순수 파일로 옮겨졌고 `scripts/verify.sh`(`client-server-imports` 포함)가 통과한다.
- DB·타입·홈 컴포넌트·어드민 저장 API·어드민 화면이 바뀌지 않았다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약

운영 묶음 카드 항목이 개편 칸을 선택 칸으로 싣고, 묶음 검증과 등록 변환이 그 칸을 읽는다. 칸을 안 적은 기존 항목·기존 등록 스크립트의 결과는 이전과 같다.

- `lib/today/listHref.ts`(신규): `isSafeListHref`를 순수 파일로 옮겼다(동작 불변). `FeedGalleryListCard.tsx`는 같은 이름으로 다시 내보내고 `feedCardFields.ts`는 순수 파일에서 가져온다. 이로써 5-1이 남긴 번들 경계 우려가 풀렸다.
- `feedCardFields.ts`: 묶음용 보조 `FEED_CARD_BUNDLE_KEYS`(14개, `feed_seed` 제외)·`hasFeedCardBundleKeys`·`isFeedTypeWritten`·`checkFeedCardBundleColumns`(5-1 `validateFeedCardColumns` 호출)·`buildFeedCardBundleColumns`.
- `validate.ts`: `resource.feed_type`이 있으면 `shape`는 선택이다(없으면 오류 문장에 «또는 `resource.feed_type`»). 새 칸 오류는 `items[n].resource.<칸>: 문장`, 경고는 항목 `warnings`(저장·승인을 막지 않음).
- `registerInput.ts`: 새 키 14개를 읽을 칸 목록에 더해 «읽지 못한 칸» 경고를 없애고(오타와 `feed_seed`는 계속 경고), 새 칸 오류는 등록을 막고 경고는 알린다. `shape`는 없으면 `NULL`로 등록한다.
- `homeFeedFields.ts`: `buildTodayCardInsertPayload`에 선택 인자 `feedColumns`(생략하면 반환 객체 불변, 주면 14개 키를 싣는다).
