# [Feature] 홈피드 개편 6회차-2: 카드 등록 때 비어 있는 시드와 색을 자동으로 정해 고정한다

## 핵심 요약

- 요구사항: 6-1로 운영 묶음의 카드 항목이 개편 칸을 실을 수 있게 됐다. 이 티켓은 **승인된 `home_feed_card` 항목이 `today_cards`로 등록되는 순간**(예약 등록 실행의 `create`) 유형이 있는 카드의 비어 있는 `feed_seed`와 배경·칩·박스 색 키를 자동 규칙으로 정해 저장하게 한다. PRD의 «값을 정하는 시점»(«에이전트가 낸 카드는 운영 항목이 승인되어 `today_cards`에 들어갈 때 정한다. 사용자가 지정한 값은 자동 배정이 덮어쓰지 않는다»)을 에이전트 경로에 적용하는 일이다. 어드민 수동 경로(5-1)와 같은 규칙·같은 코드를 쓴다.
- 구현 계획: 아래 표. 유형은 `feature`(화면 없음).
- 관련 파일: 5-1이 만든 `jam-web/src/lib/admin/feedCardFields.ts`의 `decideFeedCardValues`, 어드민 저장 라우트 두 개(`app/api/admin/today/route.ts`·`[id]/route.ts`)의 보조 함수 `serverRandomUint32`·`overlappingBgUsage`(두 곳에 중복, 5-1 잔여 이슈), 실행 핸들러 `jam-web/src/lib/admin/opsInbox/execute/homeFeedCard.ts`의 `create`.

## 배경 / 문제 정의

에이전트가 색·칩 자리를 적지 않으면(대부분의 경우 «자동») 홈이 시드로 그때그때 계산하지만, 배경색은 «같은 시기에 노출되는 카드의 사용 빈도»를 보고 고르게 퍼뜨리도록 정해야 해서 등록 때 DB를 읽어 정해 고정해야 한다. 이 계산이 없으면 에이전트가 낸 카드는 시드도 없이 카드 ID 해시로만 그려져 배경색 분산이 안 되고, 같은 주에 같은 색 카드가 몰릴 수 있다. 어드민 수동 경로(5-1)는 이미 이 계산을 하는데, 그 보조 함수가 두 라우트에 중복돼 있어 에이전트 경로까지 세 곳이 되지 않도록 한 곳으로 모은다.

## 상세 요구사항

### 서비스/코드베이스 관점

- DB·마이그레이션·`src/types/`·서비스 홈 컴포넌트·어드민 화면·묶음 검증(`validate.ts`)·`registerInput.ts`는 건드리지 않는다(6-1 몫). 이미지·로고(7회차)도 범위 밖이다.
- **공용 서버 모듈**: 새 파일 `jam-web/src/lib/admin/feedCardServer.ts`(서버에서 Supabase 클라이언트를 받아 쓰는 보조). 내용: `serverRandomUint32()`, `fetchOverlappingBgUsage(client, { startsAt, endsAt, excludeId? })`(두 라우트의 `overlappingBgUsage`와 같은 조회·같은 오류 처리: 기간 없음·조회 실패 → 빈 빈도, 서버 로그만), 위 둘과 `decideFeedCardValues`를 묶는 `completeFeedCardValues(client, columns, { startsAt, endsAt, excludeId? }, random?)`. 두 라우트는 이 모듈을 쓰게 바꾸되 **동작·응답·기존 시험은 바뀌지 않는다**(리팩터링).
- **삽입 지점**: `homeFeedCard.ts`의 `prepare`는 순수라 그대로 둔다. `create(service, prepared)`가 insert 직전에 `prepared.payload`에 `feed_type`이 있으면 `completeFeedCardValues`로 비어 있는 `feed_seed`·`bg_color_key`·`chip_color_key`·`box_color_key`를 채워 insert 행에 합친다(`feed_type`이 없으면 아무것도 하지 않는다: 옛 모양 카드는 이전과 같다). 사용자(에이전트)가 적은 값은 보존한다. 자동 배정이 통과 조합을 못 찾아 기본 조합으로 되돌린 경우(`usedFallback`)는 등록을 막지 않고 서버 로그에 남긴다(응답·슬랙 문구는 늘리지 않는다).
  - **번들 경계**: 요약창·사전 점검이 `homeFeedCard.ts`를 클라이언트 번들로 끌어오므로 «`node:`·Supabase·서버 모듈을 값으로 가져오지 않는다»는 이 파일의 순수 모듈 계약을 지킨다. 그래서 `feedCardServer.ts`를 핸들러가 값으로 가져오는 대신, `create`가 이미 받는 `service` 인자를 `completeFeedCardValues`에 넘기는 형태로 호출하되 이 가져오기가 `client-server-imports` 검사를 통과하는지 먼저 확인한다. 통과하지 못하면 보조를 핸들러 폴더의 서버 전용 파일(`execute/`, `handlers.ts`와 같은 위치)에 두는 안을 택한다. 어느 쪽이든 `verify.sh`의 `client-server-imports` 단계가 통과해야 한다.
- **빈도 입력**: 같은 실행 안에서 앞 항목이 먼저 등록되면 DB에 이미 들어가 뒤 항목의 빈도에 자연히 반영된다(별도 배치 계산 없음). `excludeId`는 `prepared.id`다(자기 자신 제외).
- **제외 조합**: 운영 코드에 연결된 제외 목록이 없어 5-1과 같은 빈 목록을 쓴다(연결되면 두 경로가 함께 바뀌도록 한 곳에서 읽는다).
- **정책 대시보드**: 규칙·밸런스 수치를 바꾸지 않으므로 `policiesData.ts`를 갱신하지 않는다(판단을 「주요 의사결정」에 적는다).

### UI/UX 관점

- 화면 변경 없음. 에이전트 경로는 사용자가 채우는 칸이 없고, 결과 색은 운영툴 미리보기(6-3)와 홈에서 보인다.

## 완료 조건

- 승인된 카드 항목에 `feed_type`이 있으면 등록된 행에 `feed_seed`와 세 색 키가 채워진다. 에이전트가 적은 값은 보존된다. `feed_type`이 없는 항목은 이전과 똑같이 등록된다.
- 두 어드민 라우트의 동작과 기존 시험은 그대로이고 보조 함수 중복이 없다.
- 같은 시드·같은 빈도는 같은 값이고, 시드 100개 이상의 자동 배정이 색 규칙을 모두 통과한다(시험).
- `scripts/verify.sh`(`client-server-imports` 포함)가 통과한다. DB·타입·홈 컴포넌트·어드민 화면·묶음 검증이 바뀌지 않았다.

- `feedCardServer.ts`(신규): `serverRandomUint32`·`fetchOverlappingBgUsage`(기간 없음·조회 실패 → 빈 빈도, 서버 로그만, 로그 머리말 보존용 선택 인자 `logLabel`)·`completeFeedCardValues`. Supabase는 `import type`으로만 읽는다.

- 이 브랜치의 이전 회차 커밋은 staging에 합쳐지기 전에 전체를 한 번 더 확인한다(알림).
