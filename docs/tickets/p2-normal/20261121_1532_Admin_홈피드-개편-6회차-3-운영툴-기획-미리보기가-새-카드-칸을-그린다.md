# [Admin] 홈피드 개편 6회차-3: 운영툴 기획 미리보기가 새 카드 칸을 그린다

## 핵심 요약

- 요구사항: 운영툴의 운영 항목 미리보기(요약창·운영 묶음 화면의 `home_feed_card` 카드 미리보기)가 6-1로 묶음에 실린 개편 칸(`resource.feed_type`·박스·색·칩·제목 속 칩·설명 노출·도장·목록 항목·모션)을 읽어 **홈과 같은 새 카드 모습**으로 그리게 한다. 칸이 없는 항목은 지금처럼 옛 7모양(`shape`)으로 그린다. 상위 티켓의 요구 «어드민 미리보기와 운영툴 기획 미리보기가 실제 화면과 같은 모습을 보여야 한다»를 에이전트 경로까지 채운다.
- 구현 계획: 아래 표. 유형은 `admin`(MODULAR 적용 제외).
- 관련 파일: `jam-web/src/lib/admin/opsInbox/cardPreview.ts`(운영 항목 → 카드 행 변환), `jam-web/src/components/admin/ops/OpsCardPreview.tsx`·`OpsKindPreview.tsx`(그리는 쪽), `jam-web/src/lib/admin/homePreview/load.ts`(묶음의 홈 미리보기). 5회차-4(20261121_1318)가 폼 미리보기에 같은 일을 이미 했다(폼 값 → 미리보기 행 `feedPreviewFields`).

## 배경 / 문제 정의

미리보기는 카드 행(`TodayCardRow`)을 만들어 `toCardView`로 홈과 같은 틀(`TodayCard`)에 그린다. 지금 `cardPreview.ts`는 행에 `shape`·`title_in_image`만 싣고 새 칸을 싣지 않아, 에이전트가 새 유형을 기획해도 운영자는 승인 전에 옛 모양 미리보기만 보게 된다. 운영자가 «이 카드가 홈에서 어떻게 보이나»를 보고 승인하려면 새 칸이 그려져야 한다.

## 상세 요구사항

### 서비스/코드베이스 관점

- DB·마이그레이션·`src/types/`·서비스 홈 컴포넌트(`components/today/` 전체)·묶음 검증(`validate.ts`)·등록 변환·실행 핸들러는 건드리지 않는다. `toCardView`·`TodayCard`는 읽기만 한다.
- **행 변환(`cardPreview.ts`)**: 운영 항목의 `resource`에서 6-1이 정한 새 키를 읽어 카드 행의 같은 이름 칸(`feed_type`·`box_shape`·`box_kind`·`bg_color_key`·`chip_color_key`·`box_color_key`·`chips`·`title_chip_words`·`show_description`·`stamp_enabled`·`stamp_slot`·`list_items`·`list_more_href`·`collection_burst`)에 싣는다. 값 읽기·정규화는 6-1의 정규화(5-1 `pickFeedCardColumns`·`buildFeedCardColumns`)를 재사용하고 새로 만들지 않는다. **허용 값이 아닌 칸은 싣지 않는다**(미리보기는 검증 도구가 아니라 그리는 도구다. 오류 문장은 검증(6-1)이 이미 알린다). `feed_type`이 없거나 모르는 값이면 새 칸을 하나도 싣지 않는다(옛 7모양 미리보기 그대로).
- **시드**: 항목에 `feed_seed`가 없으므로(등록 때 6-2가 정한다) 미리보기의 시드는 5회차-4와 같은 고정 상수를 쓴다(`Math.random`·`Date.now` 금지). 같은 항목은 언제 열어도 같은 미리보기다.
- **연결 자원 값**: 미리보기는 연결 미션(`linkedMission`)·배지·컬렉션이 있을 때 그 값을 쓰고, 없으면 값 칩·컬렉션 배지·드랍·픽업 배지 그림이 비어 지금 구조 그대로 «값이 없으면 옛 경로로 간다»는 4-3 동작을 따른다. 어떤 유형이 어떤 값이 있어야 새 모습인지는 5-2의 안내(`FEED_TYPE_VALUE_NOTES`)와 같으므로 운영 항목 미리보기에도 같은 안내를 그 미리보기 아래에 한 줄 보인다(재사용, 새 문구를 만들지 않는다).
- **미리보기와 실제가 다를 수 있는 것**: 자동으로 정해지는 배경색·칩 자리(비어 있는 칸)는 등록 때 정해져서 미리보기와 다를 수 있다. 미리보기 아래 한 줄(해요체): «색과 칩 자리는 등록할 때 정해져서 홈과 조금 다를 수 있어요». 에이전트가 색·칩 자리를 직접 적은 칸은 그대로 보인다.
- **홈 미리보기(`homePreview/load.ts`)**: 묶음의 홈 미리보기가 같은 행 변환을 쓰는지 확인하고, 쓰면 새 칸이 자동으로 반영되며 쓰지 않으면 같은 변환을 쓰도록 맞춘다(별도 변환 복제 금지).
- **정책 대시보드**: 규칙·밸런스 수치를 바꾸지 않으므로 `policiesData.ts`를 갱신하지 않는다(판단을 「주요 의사결정」에 적는다).

### UI/UX 관점

- 미리보기 안내 문구는 해요체이고 한 줄이며 `break-keep wrap-break-word`를 붙인다. 새 하드코딩 색·간격이 없다(어드민 토큰·shadcn 부품).
- 새 칸이 없는 항목의 미리보기는 지금과 똑같고 안내 줄도 없다.

## 완료 조건

- 새 칸을 실은 `home_feed_card` 항목의 미리보기가 홈과 같은 새 카드 모습으로 그려지고, 칸이 없는 항목은 지금과 똑같다(기존 시험 불변).
- 같은 항목은 언제 열어도 같은 미리보기이고(고정 시드), 새 유형 미리보기 아래에 안내가 보인다.
- `scripts/verify.sh`가 통과한다. DB·타입·홈 컴포넌트·검증·변환·핸들러가 바뀌지 않았다.
- **화면 실렌더(카리나가 머지 뒤 push 전에 한다)**: 운영 묶음 화면은 서비스 키가 필요한 서버 조회를 거치므로, 가짜 항목 props로 미리보기 컴포넌트를 그리는 임시 경로(저장소에 남기지 않는다)로 새 유형 8개를 직접 열어 확인한다. 서비스 키·서버 비밀은 쓰지 않는다.
