# [Feature] 홈피드 개편 7회차-3: 카드 커버 이미지의 대표 색을 추출해 저장한다

## 핵심 요약

- 요구사항: 카드 커버 이미지(`today_cards.cover_image_url`)의 **대표 색**(원색 최대 3개, 밝기 높은 순 hex)을 새 칸 `today_cards.cover_colors`에 저장한다. 상위 티켓의 «그림 색과 배경색이 겹치지 않게 하려면 이미지의 대표 색을 알아야 한다»와 홈피드 PRD §6 「아직 정하지 않은 것」 4번(이미지 위 칩과 이미지를 채운 박스의 색 규칙은 «이미지 대표 색·밝기 저장이 먼저다»)의 선행 조건이다. **이 티켓은 값을 저장하는 데까지다.** 저장한 색으로 색 배정을 바꾸는 규칙은 사용자가 정하지 않았으므로 이 티켓에 넣지 않는다.
- 구현 계획: 마이그레이션 351(칸 추가와 낡은 색을 비우는 트리거, 메인 세션이 실행)과 추출·저장 코드(워크플로). 유형은 `feature`. 배지 대표 색(`badges.bg_colors`, 마이그레이션 347·티켓 20261119_1651)의 구조와 코드를 그대로 본뜬다.
- 관련 파일: `jam-web/supabase/migrations/347_badge_bg_colors.sql`(칸·트리거 모양의 본보기), `jam-web/src/lib/badgeColorExtract.ts`·`badgeColorExtract.core.mjs`(추출), `jam-web/src/lib/admin/badgeBgColors.ts`(쓰기 헬퍼 본보기), 카드 커버를 쓰는 지점: `app/api/admin/today/route.ts`·`[id]/route.ts`, `app/api/admin/asset-generator/apply/route.ts`, `lib/admin/opsInbox/image.ts`(`applyItemImage`), `lib/admin/opsInbox/execute/homeFeedCard.ts`(`withFeedValues`).

## 배경 / 문제 정의

`today_cards`에는 이미지에서 뽑은 색을 담는 칸이 없다(색 칸 `bg_color_key` 등은 15색 «키»이고 이미지와 무관하다). 배지는 이미지 주소를 쓰는 모든 경로가 같은 쓰기에 대표 색을 담고, 이미지만 바뀌면 트리거가 색을 비워 낡은 색이 남지 않게 한다. 카드 커버도 같은 방식으로 저장해 두면 뒤에서 색 규칙을 정할 때 이미지를 다시 읽지 않아도 된다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 서비스 홈 컴포넌트·`toCardView`·색 배정(`feedAssign.ts`)·어드민 화면·`src/types/database.ts` 수기 타입은 바꾸지 않는다. **저장만** 한다(읽는 쪽은 값이 생겨도 바뀌지 않는다).
- **DB(메인 세션이 실행)**: 마이그레이션 `351_today_cards_cover_colors.sql`·`351_…_down.sql`(번호는 실행 직전 원격 staging 기준으로 다시 확인). `today_cards.cover_colors jsonb NULL`(의미: `badges.bg_colors`와 같다. NULL=아직 안 뽑음, `[]`=색 없음, 값이 있으면 hex 문자열 최대 3개). 구조 검증 CHECK(배열·최대 3개·각 `#rrggbb`)와, `cover_image_url`만 바뀌고 `cover_colors`가 같은 UPDATE에서 새로 오지 않으면 `cover_colors`를 NULL로 비우는 트리거(`today_cards_cover_colors_stale_guard`, 347과 같은 모양)를 둔다. 전부 NULL 허용·기본값 없음이라 기존 행·기존 코드에 영향이 없다(확장 단계). 생성 타입 `database.generated.ts`는 Supabase MCP `generate_typescript_types`로 대조해 같은 커밋에 반영한다(CLAUDE.md의 생성 타입 규칙. 이 규칙의 «타입 파일은 건드리지 않는다» 제한은 이 티켓에 한해 풀려 있고, 수기 `database.ts`는 선택 필드 한 줄만 더한다).
- **쓰기 헬퍼**: `lib/admin/coverColors.ts`(신규, `badgeBgColors.ts`를 본뜬다): `coverColorsFields(url)`·`coverColorsFieldsIfChanged(existing, next)`. 추출은 기존 `extractBadgeColors`를 그대로 쓴다(저장소 밖 주소는 추출 단계가 막는지 확인하고, 막지 않으면 저장소 주소만 허용해 외부 주소 fetch를 막는다). 추출 실패는 저장을 막지 않는다(색 없이 저장하고 트리거가 NULL로 둔다).
- **쓰는 지점**(커버 주소를 쓰는 곳마다 같은 쓰기에 담는다): ① 어드민 카드 생성·수정 라우트(`cover_image_url`이 바뀔 때만, `imageSourceReset`과 같은 시점) ② 에셋 제너레이터 적용 라우트의 `home_feed`(`bg_colors`는 배지일 때만 쓰는 기존 줄 옆) ③ 운영툴 이미지 저장 후 예약된 카드의 `today_cards` 갱신(`applyItemImage`의 예약 뒤 분기) ④ 예약 등록 때 새 행 생성(`homeFeedCard.ts`의 `create`가 insert 직전에 하는 `withFeedValues` 옆에서 `cover_image_url`이 있으면 대표 색을 함께 싣는다. 이 파일의 순수 모듈 계약(번들 경계)을 지키고 `client-server-imports` 검사를 통과한다). 에이전트용 등록 스크립트(`register-home-feed-card.mjs`)는 이 티켓에서 다루지 않는다(NULL로 남고 일괄 계산 대상, 잔여 이슈에 적는다). 동영상 커버(MP4·WebM)는 추출하지 않는다.
- **일괄 계산**: 기존 카드의 `cover_colors`는 채우지 않는다(게시 중인 카드는 고려하지 않는다는 상위 결정, NULL은 «아직 안 뽑음»). 필요하면 `backfill-badge-bg-colors.mjs`를 본뜬 스크립트는 후속으로 남긴다.
- **문서**: `docs/service/prd/home-feed/PRD.md` §10 개편 칸 표(새 칸 `cover_colors` 행)와 §6 «아직 정하지 않은 것» 4번에 «이미지 대표 색은 저장한다(7회차-3), 색 규칙은 미정», 구현 위치 한 단락.
- **정책 대시보드**: 규칙·밸런스 수치를 바꾸지 않으므로 `policiesData.ts`를 갱신하지 않는다.

### UI/UX 관점

- 화면 변경 없음.

## 완료 조건

- 카드 커버 주소를 쓰는 네 경로가 같은 쓰기에 `cover_colors`를 담고, 추출이 실패해도 저장은 성공한다. 이미지 주소만 바뀐 UPDATE는 트리거가 낡은 색을 비운다(DB 실측).
- 기존 카드·기존 동작·기존 시험이 바뀌지 않는다. `scripts/verify.sh`가 통과한다.
- 홈·색 배정 코드는 이 값을 읽지 않는다(바뀐 것 없음).
