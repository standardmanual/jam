# [Feature] 홈피드 개편 7회차-6: 이미지 대표 색을 자동 색 배정에 쓴다

## 핵심 요약

- 사용자 결정(2026-11-21, «제안대로 함»): 저장한 이미지 대표 색(카드 커버 `today_cards.cover_colors`, 배지 `badges.bg_colors`)으로 자동 색 배정을 보완한다. 규칙은 아래 «확정 규칙» 그대로다. 임계값은 새 숫자를 만들지 않고 기존 색 규칙의 척도(색상 차이 30°, 밝기 L* 차이 15)를 쓴다. 배지 대표 색을 포함하고, 수동 지정 색은 경고만 한다(경고 화면은 7-7).
- 구현 계획: 아래 표. 유형은 `feature`(화면 없음).
- **선행**: 7-3(20261121_1724)이 `today_cards.cover_colors` 칸과 커버 색 저장을 끝내고 병합돼야 한다(이 티켓은 그 칸을 읽는다).
- 관련 파일: `jam-web/src/lib/today/feedColorRules.ts`(규칙·임계값 `COLOR_RULE_THRESHOLDS`, 함수 `hexToHsl`·`hueDifference`·`cieLightness`), `feedAssign.ts`(`assignFeedColors`), 6-2가 만든 `jam-web/src/lib/admin/feedCardServer.ts`(`completeFeedCardValues`), 두 어드민 라우트(`app/api/admin/today/route.ts`·`[id]/route.ts`)와 운영 등록(`lib/admin/opsInbox/execute/homeFeedCard.ts`의 `create`).

## 확정 규칙 (홈피드 PRD §6 「색」에 적는다)

- **적용 대상**: 이미지가 색 면 위에 놓이거나 색 면을 채우는 유형.
  - 커버 이미지: 히어로(`hero_box`), 텍스트 박스의 이미지 마스크(`text_box`이고 `box_kind = image_mask`), 컬렉션 소개(`collection_intro`) → 카드의 `cover_colors`.
  - 배지 그림이 배경 위에 놓이는 유형: 배지 소개(`badge_intro`)·배지만(`badge_only`) → 카드가 가리키는 첫 배지의 `bg_colors`, 드랍·픽업(`drop_pickup`) → 아이템 배지(최대 3개)의 `bg_colors` 전부.
  - 그 밖(글자만 있는 텍스트 박스, 목록형, 꺼진 전체 배경 이미지)은 적용하지 않는다.
- **규칙 ⑤ 그림과 배경**: 카드 배경색이 해당 이미지 대표 색(저장된 최대 3개 중 하나라도)과 «색상 차이 30° 미만이고 밝기(L*) 차이 15 미만»이면 그 배경은 자동 배정에서 제외한다.
- **규칙 ⑥ 그림과 칩**: 이미지 위에 걸치는 칩(`hero_box`·이미지 마스크 `text_box`·`collection_intro`)의 색도 같은 조건이면 제외한다.
- **안전장치**: 이미지 규칙까지 통과하는 조합이 하나도 없으면 이미지 규칙을 건너뛰고 기존 규칙(①~④)만으로 고른다(결과에 `imageRuleSkipped = true`를 남기고 서버 로그에만 알린다. 기본 조합 되돌림 `usedFallback`과 구분한다). 대표 색이 `NULL`(아직 안 뽑음)이거나 `[]`(색 없음)이면 이미지 규칙은 적용하지 않는다.
- **수동 지정**: 사용자가 지정한 색은 덮어쓰지 않는다. 규칙에 걸리면 경고만 한다(7-7).
- **한계**: 저장된 색은 밝기 높은 순이라 면적 비중을 모른다. 3개를 모두 검사한다(보수적).

## 상세 요구사항

### 서비스/코드베이스 관점

- DB·마이그레이션·`src/types/`(생성 타입 외)·서비스 홈 컴포넌트·어드민 화면은 건드리지 않는다. **홈이 그릴 때(`resolveFeedLook`)의 자동 배정은 바꾸지 않는다**(등록·저장 때 고정하는 경로만 이 규칙을 쓴다. 홈 쪽은 배지 대표 색을 카드 행에서 알 수 없고, 저장된 색이 있으면 그대로 그린다).
- **규칙 함수**(`feedColorRules.ts`): `violatesImageColorRule(candidateHex, imageHexes)` — 색상 차이 `< COLOR_RULE_THRESHOLDS.closeHueDegrees(30)`이고 CIE 밝기 차이 `< COLOR_RULE_THRESHOLDS.minCieLightnessDiff(15)`인 대표 색이 하나라도 있으면 참. hex만 받는 순수 함수다(컬러셋 교체 어드민의 전제와 같다). 새 임계값 상수를 만들지 말고 기존 두 값을 읽는다(규칙 번호 이름은 `ColorRuleName`에 `'image'`를 더하는 안).
- **자동 배정**(`assignFeedColors`): 입력에 선택 필드를 더한다: `imageHexes?: readonly string[]`(해당 카드의 이미지 대표 색), `chipOnImage?: boolean`(칩이 이미지 위에 걸치는 유형인가). 배경 후보는 `imageHexes`가 있으면 규칙 ⑤를 통과해야 하고, `chipOnImage`이면 칩 후보도 규칙 ⑥을 통과해야 한다. 조합이 없으면 이미지 규칙만 건너뛰고 다시 계산해 결과에 `imageRuleSkipped`를 담는다. 인자를 안 주면 지금과 **완전히 같은 결과**다(기존 시험 불변). 같은 입력은 같은 결과(시드 결정성)다.
- **유형 → 이미지 색 선택**: 순수 함수 `imageColorsForCard({ feedType, boxKind, coverColors, badgeColors })`(예: `lib/today/feedImageColors.ts`)가 위 «적용 대상» 표대로 `imageHexes`·`chipOnImage`를 돌려준다. 유효하지 않은 hex는 걸러낸다.
- **서버 읽기**(`completeFeedCardValues`와 그 호출 세 곳): 자동 배정에 쓸 `badge_ids`의 `bg_colors`를 서비스 클라이언트로 한 번 조회한다(`badges` 표에서 `id in (…)`, 칸 `bg_colors`만. 조회 실패는 이미지 규칙 없이 진행하고 서버 로그에 남긴다). 커버 색은 같은 저장 요청이 쓰는 `cover_colors`(7-3이 같은 쓰기에 담는 값)를 쓰고, 수정 저장에서 커버가 안 바뀌면 저장된 값을 읽는다. `homeFeedCard.ts`의 `create`는 순수 모듈 계약(번들 경계)을 지키고 `client-server-imports` 검사를 통과한다.
- **정책 대시보드**: 색 거르는 규칙의 임계값은 화면 표시 규칙이지 운영 정책·밸런스 수치가 아니어서 `policiesData.ts`를 갱신하지 않는다(4회차-4와 같은 판단, 「주요 의사결정」에 적는다).

### 구현 내용 요약

확정 규칙 ⑤ 그림과 배경, ⑥ 그림과 칩, 안전장치를 자동 색 배정(등록·저장 때 값을 고정하는 경로)에 구현했다. 임계값은 새로 만들지 않고 기존 `COLOR_RULE_THRESHOLDS`의 색상 차이 30°와 밝기 L* 차이 15를 읽는다. 홈이 그릴 때의 자동 배정(`resolveFeedLook`)은 바꾸지 않았다.

- `feedColorRules.ts`: `violatesImageColorRule(candidateHex, imageHexes)`(대표 색 3개 중 하나라도 걸리면 참, 읽을 수 없는 hex는 건너뜀), `isHexColor`, `ColorRuleName`에 `'image'`.
- `feedAssign.ts`: `assignFeedColors`가 선택 입력 `imageHexes`·`chipOnImage`를 받는다. 지정값은 걸러 내지 않는다. 조합이 없으면 이미지 규칙만 건너뛰고 `imageRuleSkipped = true`를 남기며, 건너뛴 뒤에도 없으면 `usedFallback`과 함께 켠다. 입력이 없으면 결과가 지금과 같고 `imageRuleSkipped` 칸도 없다(`toStrictEqual` 시험).
- `feedImageColors.ts`(신규): `imageColorsForCard`가 유형 8개 표대로 이미지 색을 고른다(`hero_box`·`collection_intro`·이미지 마스크 `text_box`=커버 색+칩 걸침, `badge_intro`·`badge_only`=첫 배지, `drop_pickup`=배지 3개, 그 밖은 미적용).
- `feedCardServer.ts`: `fetchBadgeBgColors`(`badges`를 한 번 조회, 삭제된 배지 제외, 실패는 서버 로그만), `fetchFeedCardImageColors`(배지 유형일 때만 조회), `completeFeedCardValues`의 선택 인자 `imageSource`.
- 호출부: `POST`는 검증을 통과한 뒤 배정 전에 커버 색을 뽑고 같은 insert에 재사용한다. `PATCH`는 커버가 바뀌었으면 새 색, 아니면 저장된 `cover_colors`를 쓰며 추출이 실패하면 낡은 저장 색은 쓰지 않는다. 운영 등록 `create`는 커버 색을 먼저 뽑아 넘긴다(번들 경계 유지).

### 주요 의사결정 / 핵심 메모

- **정책 대시보드(`policiesData.ts`)는 갱신하지 않았다**: 색 거르는 규칙의 임계값은 화면 표시 규칙이지 운영 정책·밸런스 수치가 아니다(4회차-4와 같은 판단).

- `feedCardFields.ts`에는 `COLOR_RULE_REASON`의 `image` 문구 한 줄 외에 `DecideFeedCardValuesInput.image`·`DecidedFeedCardValues.imageRuleSkipped`·배정 호출 연결이 들어갔다(`completeFeedCardValues`가 이미지 색을 배정에 넘기는 데 필수라 범위 이탈이 아니다).
- 이 브랜치에는 이전 회차(7-3 포함) 커밋 114개가 쌓여 있어 게이트는 이 티켓 몫(3커밋 905줄)만 판정했다. 이전 커밋은 각 티켓에서 이미 게이트를 거쳤다.

### 잔여 이슈

- `COLOR_RULE_REASON.image` 문구는 7-7(수동 색 경고)이 쓴다. 지금은 쓰는 호출부가 없다.
- 7-3의 트리거 경계 동작(같은 색 세트면 `NULL`)은 이미지 규칙이 건너뛰어질 뿐이라 해가 작다.
