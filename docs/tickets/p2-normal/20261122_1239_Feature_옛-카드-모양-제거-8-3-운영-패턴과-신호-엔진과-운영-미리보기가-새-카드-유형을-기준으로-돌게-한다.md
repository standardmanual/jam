# [Feature] 옛 카드 모양 제거 8-3: 운영 패턴·신호 엔진·운영 미리보기가 옛 모양 대신 새 카드 유형을 기준으로 돌게 한다

## 핵심 요약

- 요구사항: 운영툴 쪽이 옛 모양(`CardShape`·`resolveShape`·`isImageShape`)을 읽는 곳을 새 카드 유형(`feed_type`, 8-1의 `resolveFeedType`, 7회차의 `feedTypeUsesCoverImage`) 기준으로 바꾼다. 신호 엔진의 «이미지가 있어야 하는 카드» 판정, 날짜별 구성 규칙, 운영 항목 서랍·미리보기·홈 미리보기 패널의 모양 표시와 개수 막대, 운영 패턴의 「카드 모양」 입력·상세, 운영 미리보기의 `layout_type` 읽기가 대상이다. **DB·마이그레이션·`src/types/`는 건드리지 않는다.**
- 구현 계획: 아래 표. 유형은 `admin`(MODULAR 적용 제외).
- 관련 파일: `jam-web/src/lib/admin/opsSignals/{load,composition,dayRules}.ts`(`shape`·`shapeStored`·`isImageShape` 판정, `load.ts` ~125~144줄), `lib/admin/opsInbox/{fields,labels,validate,cardPreview}.ts`(`readOpsItemShape`·`card_shapes` 제안 칸·`layout_type` 읽기 ~150줄), `lib/admin/opsBoard/drawerView.ts`(~117줄 «모양»), `lib/admin/homePreview/load.ts`(~78·238줄 모양별 개수), `components/admin/ops/preview/{homePreviewClient.ts,HomePreviewPanel.tsx}`(`SHAPE_STYLES` ~40줄·`isImageShape` ~99줄), `components/admin/ops/{OpsCardPreview,OpsPatternFormParts,OpsPatternForm,OpsPatternDetail}.tsx`, `lib/admin/opsPatterns/{input,formDraft,detailView,read,write}.ts`(`card_shapes`). 규격 `docs/service/prd/ops-tool/PRD.md`·`docs/service/prd/home-feed/PRD.md`.

## 배경 / 문제 정의

상위 티켓 20261122_1100 참조. 8-1·8-2로 홈과 어드민 폼이 새 유형만 쓴다. 운영툴의 신호·패턴·미리보기가 아직 옛 모양 이름으로 카드를 분류하면, 새 유형 카드가 «모양 모름»으로 잡히거나 이미지 누락 신호가 엉뚱하게 켜진다.

## 상세 요구사항

### 서비스/코드베이스 관점

- **신호 엔진**: 조회(`opsSignals/load.ts`)는 `feed_type` 칸을 읽고 `resolveFeedType`으로 유형을 정한다(`shape`·`resolveShape`·`shapeStored` 삭제). «이미지가 있어야 하는 카드»는 `feedTypeUsesCoverImage(유형, box_kind)`로 정한다(옛 `isImageShape`). 날짜별 구성 규칙(`dayRules.ts`)의 «이미지 모양·이미지 없는 모양» 비율 규칙도 같은 판정을 쓴다. 규칙의 이름·문구가 «모양»을 말하면 «카드 유형»으로 바꾼다. 신호의 임계값·판정 결과가 새 유형에서도 같은 뜻이 되게 하고, 바뀐 뜻이 있으면 완료 기록에 적는다.
- **운영 항목(묶음)**: `readOpsItemShape`는 `resource.feed_type`(허용 8가지, 아니면 «모름»)을 읽는다(이름을 `readOpsItemFeedType` 등으로 바꾼다). 서랍(`drawerView.ts`)의 «모양» 줄은 «카드 유형»이다. 운영 미리보기(`cardPreview.ts`)는 `resource.layout_type`을 읽지 않는다(8-2에서 묶음이 이 칸을 무시하도록 했다).
- **홈 미리보기 패널**: `homePreview/load.ts`의 모양별 개수는 유형(`resolveFeedType`)별 개수가 되고, `homePreviewClient.ts`의 `SHAPE_STYLES`는 새 8유형 키로 바꾼다(막대 색·라벨 새로 정한다: 기존 디자인 토큰 안에서). `HomePreviewPanel.tsx`·`OpsCardPreview.tsx`의 옛 `isImageShape` 분기는 `feedTypeUsesCoverImage`로 바꾼다.
- **운영 패턴의 «카드 모양»**: DB 칸 이름 `card_shapes`(jsonb)와 기존 39개 패턴의 값은 **바꾸지 않는다**(데이터 이관은 이 티켓 밖). 코드는 입력·검증·표시를 새 유형으로 바꾼다: 입력 폼(`OpsPatternFormParts`)의 선택지는 새 8유형, 목록에 없는 값(옛 모양 이름)은 상세(`detailView.ts`)에서 «옛 모양 이름(그대로 보관)»으로 표시하고 폼에서 불러오면 빈 선택으로 보여 다시 고르게 한다. 저장·묶음 제안(`validate.ts`의 `validatePatternCardShape`, `opsPatterns/input.ts`)은 새 8유형만 받는다(옛 이름은 허용값 오류). 라벨(`labels.ts`)은 «카드 모양»을 «카드 유형»으로 바꾼다. JSON 키 이름(`shape`)은 DB 호환을 위해 그대로 둔다.
- **에이전트 정의·문서**: `.claude/agents/jam-marketer.md`의 이미지 프리셋 문단(모양별 프리셋·«dome이면 layout_type을 banner로»)과 `docs/service/prd/content-automation/` 등록 묶음 문서의 «노출 형태» 표(`HOME_FEED_REGISTRATION_BUNDLE.md` §1.1 등, 파일 위치는 grep으로 찾는다)를 새 유형 기준(커버 이미지가 필요한 유형은 `hero_box`, `box_kind`가 이미지일 때)으로 고친다. `docs/service/prd/ops-tool/PRD.md`·`docs/service/prd/home-feed/PRD.md`에 8회차-3 단락.
- 건드리지 않는 것: DB·마이그레이션·`src/types/`, 서비스 홈 컴포넌트, `shape.ts` 상수(8-4), 집계 API `metrics/route.ts`(8-4), `TODAY_LAYOUT_OPTIONS`·`SUGGESTED_LAYOUT_FOR`(8-4). `policiesData.ts`는 임계값을 바꾸지 않으면 갱신하지 않는다(바꿨다면 갱신하고 이유를 적는다).

### UI/UX 관점

- 어드민 화면(shadcn 표준). 운영자에게 보이는 것은 라벨 «카드 모양»→«카드 유형», 패턴 폼 선택지 8가지, 홈 미리보기 막대의 유형 이름이다. 문구는 해요체.

## 완료 조건

### 구현 범위 (게이트 판정 대상)

- `lib/admin/opsSignals`·`opsInbox`·`opsBoard`·`homePreview`·`components/admin/ops`에 `resolveShape`·`isImageShape`·`CardShape`·`CARD_SHAPES`·`layout_type` 읽기가 남지 않는다(`grep`으로 확인, 운영 패턴의 DB 칸 이름 `card_shapes`·`cardShapes` 식별자와 옛 이름을 «옛 모양 이름»으로 표시하는 코드는 예외).
- 신호 엔진: `hero_box`(커버 이미지 필요) 카드에 커버가 없으면 «이미지 누락» 신호가 켜지고, `text_box` 카드는 커버가 없어도 켜지지 않는다(시험으로 고정). 날짜별 구성 규칙 시험이 새 유형 기준으로 통과한다.
- 패턴 폼 선택지는 새 8유형이고, 옛 모양 이름이 저장된 패턴의 상세는 오류 없이 «옛 모양 이름»으로 보인다(시험). 새 저장·묶음 제안은 새 8유형만 받는다.
- 홈 미리보기의 유형별 개수 막대가 새 유형 이름으로 나오고 모르는 유형도 오류 없이 묶인다(시험).
- `scripts/verify.sh`가 통과한다. DB·마이그레이션·`src/types/` 변경이 없다.

### 후속 범위 (담당: 카리나, 시점: 머지 뒤)

- 기존 39개 패턴의 `card_shapes` 값(옛 모양 이름)을 새 유형으로 이관할지는 사용자와 정한다(이관하면 DB 변경이라 별도 승인·드라이런).

## 완료 기록 *(작업 완료 후 작성)*
### 구현 내용 요약

- **신호 엔진**(`opsSignals/load·composition·dayRules`): `feed_type`·`box_kind`를 읽어 `resolveFeedType`으로 유형을 정하고, 이미지가 있어야 하는 카드는 `feedTypeUsesCoverImage`(히어로·컬렉션 소개·이미지 마스크 텍스트 박스)로 판정한다. `shape`·`shapeStored`를 지우고 `usesCoverImage`를 더했다. 규칙 문구·기준값 라벨의 «모양»은 «카드 유형»이다. 임계값·키 이름은 그대로라 `policiesData.ts`는 갱신하지 않았다.
- **운영 항목·서랍·미리보기**: `readOpsItemShape` → `readOpsItemFeedType`(`resource.feed_type`, 허용 8가지, 아니면 «모름»). 서랍 «모양» 줄은 «카드 유형». `cardPreview`는 `resource.layout_type`을 읽지 않는다.
- **홈 미리보기 패널**: 유형별 개수를 `resolveFeedType`으로 세고 `SHAPE_STYLES`는 새 8유형 키다. 이미지 분기는 `feedTypeUsesCoverImage` 하나다.
- **운영 패턴**: 선택지·저장 검증·묶음 제안은 새 8유형만 받고 옛 이름은 허용값 오류다. 상세는 옛 이름을 「옛 모양 이름(그대로 보관)」으로 보이고 폼은 빈 선택으로 연다. `card_shapes` 칸 이름·JSON 키 `shape`·저장된 39개 값은 그대로다. 유형 이름 표를 `lib/admin/feedTypeLabels.ts`로 옮겼다(`'use client'` 파일 값을 서버 모듈이 가져오면 클라이언트 참조가 되는 문제를 피함, `FeedCardSection`이 다시 내보낸다).
