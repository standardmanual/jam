# [Feature] 통합 팔레트 2: 홈피드 색 체계를 통합 팔레트로 바꾸고 기존 카드를 다시 배정한다

## 핵심 요약

- 요구사항: 상위 티켓 [20261122_2217](20261122_2217_Feature_홈피드와-배지-상세를-통합-팔레트와-새-칩-규칙으로-리뉴얼한다-상위.md) 「확정 결정 §1·§2·§5」를 홈피드 계산에 반영한다. 홈피드 15색 키(`FEED_COLORS`)를 통합 팔레트 키(노랑·초록·짙은 초록·분홍·하늘·빨강·보라·파랑·흰색)로 바꾸고, 쓰임 표(바탕·박스·값 칩·스티커), 카드 바탕+박스 조합 9개와 가중치, 짙은 초록 바탕 카드 리듬(다섯~여섯 장에 한 장, 바탕 위 글자 흰색), 배제 조합 표(대비·키즈·명도 계산 규칙 대체, 배지 그림 색 겹침 규칙은 유지)를 만든다. 저장된 카드 121장은 모두 새 규칙으로 다시 배정한다(결정 9, SQL은 파일만 쓰고 실행은 카리나).
- 하위 1번에서 넘어온 점(2026-11-23): 연한 노랑 `--jam-yellow-soft`(#FFDD73)·참조 노랑 `--feed-ref-yellow`(#F2EC6A)가 새 노랑 #F9FD69와 같은 계열이라 한 카드 안에서 구분되지 않는다. 15색 키를 통합 팔레트 키로 바꿀 때 연한 색 5개(`--jam-*-soft`)·참조 색 5개(`--feed-ref-*`) 토큰과 `globals.css`의 `--color-jam-*-soft` 매핑도 쓰는 곳이 없으면 함께 걷는다. 1번 머지 뒤 옛 색 규칙을 통과하는 조합이 74쌍에서 86쌍으로 늘었지만, 이 계산 규칙은 이 티켓에서 배제 표로 바뀌므로 따로 맞추지 않는다.
- 구현 계획: 하위 1번(색 토큰) 뒤에 한다. 규모가 커서 착수 전에 파일 단위 계획을 이 티켓에 적고 회차로 나눌지 판정한다.
- 관련 파일: `jam-web/src/lib/today/feedConstants.ts`(`FEED_COLOR_KEYS`·`FEED_COLORS`·`feedColorVar`), `jam-web/src/lib/today/feedColorRules.ts`(`COLOR_RULE_THRESHOLDS`·`firstViolatedRule`·`passesColorRules`·`summarizeColorPairs`), `jam-web/src/lib/today/feedAssign.ts`(`assignFeedColors`·`DEFAULT_FEED_PALETTE`·`FEED_FALLBACK_COLORS`), `jam-web/src/lib/today/feedLook.ts`(`resolveFeedLook`), `jam-web/src/lib/admin/feedCardServer.ts`(`completeFeedCardValues`), `jam-web/supabase/migrations/`(색 키 제약·재배정), `jam-web/src/types/database.generated.ts`.

## 회차 분할안 (초안, 2026-11-23 계획 에이전트 조사 + 카리나 정리, 사용자 결정 대기)

조사 사실: 옛 15색 키는 파일 약 45개에서 쓰인다(시험 약 25·스토리 5 포함). DB는 `today_cards`의 `bg_color_key`·`chip_color_key`·`box_color_key`(text, CHECK 15키, 최신 정의 `349_today_cards_feed_redesign_columns.sql` L157~171)와 `feed_color_overrides.color_key`(CHECK, `352` L22~27)다. 칩·제목 속 칩·도장 색은 `chip_color_key` 하나로 정해진다. 저장된 카드 121장은 세 칸 모두 옛 키다(2026-11-23 확인: 텍스트형 69·히어로 33·배지 소개 19, 어드민 덮어쓰기 0건). 연한 색·참조 색 토큰은 코드에서 `FEED_COLORS.cssVar`로만 쓰이고 Tailwind 클래스 사용은 0건이다.

순서는 확장→전환→축소다. 옛 10키는 12회차까지 읽기 전용으로 남겨 재배정 SQL 실행 전에도 화면과 저장이 깨지지 않게 한다.

적용·되돌림 순서: 357은 2회차가 staging에 올라가기 전, 359는 358 실행 뒤에 적용한다. 되돌릴 때는 359→358→357이고, 359 뒤에는 355_down을 실행할 수 없다. 축소 전에 운영 묶음 대기 항목·클라우드 루틴 프롬프트에 옛 키가 없는지 확인한다. 「바뀌는 카드 수 121」은 우연히 같은 이름의 키(노랑·초록·빨강·보라·파랑)로 재배정된 카드가 빠지므로 UPDATE 121장과 실제 바뀐 수를 따로 적는다.

컬러셋 메뉴는 3번 티켓이 지우기 전까지 이 티켓에서 최소 대응한다(`FEED_COLOR_KEYS`를 그대로 읽게 두고 이름표 추가, 357에서 overrides CHECK 확장, 미리보기 키 교체, hex 규칙 함수는 «메뉴 전용»으로 남김).

### 결정 (2026-11-23 사용자 «모두 승인», 계획 에이전트 추천을 따름)

1. 컬러셋 메뉴는 3번 티켓이 지우기 전까지 이 티켓에서 최소 대응으로 살려 둔다.
2. «바로 앞 카드와 같은 바탕» 기준은 등록 순서다. 재배정도 같은 기준으로 차례대로 처리한다.
3. `chip_color_key`도 재배정에 넣는다(6번 티켓에서 이 칸을 계속 저장값으로 쓸지 함께 정한다).
4. 짙은 초록 박스는 글자가 들어가는 박스 전부(텍스트형·드랍 픽업 배지 상자·목록형 타일)에 쓰지 않는다. 이유는 검정 글자 대비 3.9로 같다.
5. DB 제약은 세 칸이 같은 9키 공통 목록을 쓰고 쓰임 표는 코드가 지킨다. 재배정 재료는 카리나가 읽기 전용 SELECT 결과(JSON)로 넘긴다.

### 진행 기록

- 회차 1(DB 확장) 완료 2026-11-23: `357_feed_color_keys_expand.sql`(+`_down`)을 롤백 드라이런(새 키 수용·이상한 키 차단·되돌림 뒤 제약 정의 원상, 예외로 전부 취소)한 뒤 실행했다. 제약 4개에 새 키 4개(green-deep·pink·sky·white)가 들어갔고 모두 검증됨이다. 옛 키 행은 그대로라 화면·저장 변화가 없다.
- 회차 2·3 완료 2026-11-23(로컬 staging 머지 `07071b634`, push 전): 색 키 4개를 타입·표·어드민 이름표에 더하고(자동 배정은 임시로 제외), 쓰임 표·조합 9개와 가중치(합 12)·짙은 초록 조합 2개와 리듬(5~6장)·`feedTextOnBg`·`boxAllowedFor`·`chipExclusionRule`을 만들었다. 배정은 아직 새 표를 읽지 않는다. 1차 판정은 컬러셋 시험의 hex 칸 개수 15가 남아 FAIL이었고 카리나가 한 줄 보정(+새 키 자동 배정 제외 단언)해 2차 PASS. 투입: 구현 호출 2명·약 21만 토큰·24분(출력 아현 53,246), 재판정 1명·약 6.7만 토큰·8분.
- 회차 4와 5는 한 번에 돌린다(바탕·박스 배정과 칩 배정을 따로 바꾸면 사이 상태에서 칩이 옛 규칙으로 새 바탕을 읽게 된다).
- 다음 회차로 넘기는 정합성 항목(민지 `sideFindings`): `FeedChip.stories.tsx:39`의 `ALL_COLORS`가 `'white'`를 두 번 포함해 중복 키 경고가 난다. 새 `white` 키(`--jam-chip-white`)가 `FeedChip.tsx:41`·`FeedBox.tsx:32`의 직접 지정용 `white`(`--snow`)와 이름이 겹친다(8회차 처리, 그때까지 새 white 키는 `--snow`로 그려진다). `FeedChip.tsx:17`·`FeedChip.stories.tsx`·`FeedStamp.stories.tsx`의 «색 15개» 문구는 8·13회차에서 19키에 맞춘다. 컬러셋 메뉴가 19키를 모두 편집 대상으로 삼지만 영향 계산은 옛 15색만 본다(3번 티켓이 메뉴를 지운다).
- 회차 4·5 완료 2026-11-23(로컬 staging 머지 `4eb34dcbb`, push 전): `assignFeedColors`가 조합 9개 가중 추첨·앞 카드 같은 바탕 회피·글자 박스에 짙은 초록 박스 제외·값 칩 7색의 배제 표·짙은 초록 바탕 리듬으로 바탕·박스·칩을 정한다. 배지 그림 색 규칙·지정값·제외 조합·안전 조합(노랑 바탕·초록 박스·분홍 칩)은 유지. 1차 판정은 WARN(리듬이 «사이 5~6장»으로 구현돼 주기 6~7장이었다, 요청문의 «이후 장수» 표현이 모호했던 탓), 카리나가 «마지막 짙은 초록 카드로부터 5번째 30%·6번째 이상 필수»(사이 4~5장)로 보정해 2차 PASS. 5번째 30%는 구현이 정한 값이다. 투입: 구현 호출 2명·약 27.7만 토큰·34분(출력 아현 81,202), 재판정 1명·약 5.6만 토큰·6분.
- 회차 6과 7도 한 번에 돌린다(같은 서버 파일 `feedCardServer.ts`·라우트 두 개·운영 묶음 실행이 겹친다). 짙은 초록 바탕 카드는 회차 6이 `recentBgKeys`를 넘기기 전까지 새 카드에 나오지 않는다(의도된 상태). 목록이 짧으면 «목록 앞에 짙은 초록이 있었던 것으로 센다»는 가정이 어긋나므로 앞 카드 목록은 6장 이상으로 가져온다(민지 `sideFindings`).
- 회차 6·7 완료 2026-11-23(로컬 staging 머지 `6524a45db`, push 전): 서버가 같은 시기 노출 카드의 바탕 키를 등록 순서로 최근 12장(`fetchRecentBgKeys`) 가져와 배정에 넘기고, 글자 박스 여부(`boxHasTextFor`)를 박스 종류로 정한다. 컬렉션 소개의 그림 색 규칙이 대표 그림에 아이템 배지 4개 색을 더해 본다(선택 규칙은 순수 모듈 `collectionBurstBadges.ts` 한 곳). 민지 판정은 «서버 검증 확인» 조건부 통과였고, 리뷰 브랜치 push 뒤 CI verify(run 45115750242)가 통과해 조건이 충족돼 재판정 없이 머지했다. 투입: 구현 호출 2명·약 26만 토큰·33분(출력 아현 56,118).
- 회차 10에서 확인할 점(민지): `fetchRecentBgKeys`는 등록 시각이 같은 카드의 순서 기준이 없고, 수정 저장(PATCH) 때는 수정 대상보다 나중에 등록된 카드도 «앞 카드»로 센다. 저장된 카드 121장 재배정(«등록 순서대로 차례 처리»)이 이 기준과 어긋나지 않게 맞춘다.

## 완료 조건

- 홈피드가 통합 팔레트 키만 쓰고, 자동 배정이 쓰임 표·조합 9개·가중치·배제 표·짙은 초록 바탕 카드 리듬을 따른다(단위 시험).

- 재배정 SQL과 되돌림 SQL이 `jam-web/supabase/migrations/`에 있고, 드라이런 결과(바뀌는 카드 수 121)를 티켓에 적는다. 실행은 카리나가 머지 뒤에 한다.
