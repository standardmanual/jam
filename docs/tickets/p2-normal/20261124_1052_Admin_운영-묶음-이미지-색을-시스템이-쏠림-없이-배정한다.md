# [Admin] 운영 묶음 이미지 색(시작색·끝색)을 에이전트 대신 시스템이 쏠림 없이 배정한다

## 핵심 요약

- 요구사항: 49주차(11/30~12/6) 운영 기획에서 카드·미션 이미지 색이 초록과 파랑 계열에 몰렸다(이미지 색 칸 12개 중 초록 계열 4개, 파랑 계열 4개, 합쳐 67%). 윤진(`jam-marketer`)이 `image_spec.bg`·`image_spec.end`를 고르는 기준이 정의에 없고, 같은 정의 안에 «색은 직접 고르지 않는다»는 금지(Boundaries)와 «`bg`·`end`를 반드시 낸다»는 지시가 충돌한다. 이미지 색 선택권을 에이전트에게서 거두고, 운영 묶음을 받는 서버가 통합 팔레트 색 쌍 표에서 한 계열이 몰리지 않게 배정한다. 사용자가 2026-11-24에 «통합 팔레트 9색으로 쌍 표를 새로 짠다»로 정했다.
- 구현 계획: 새 순수 모듈 `imageColorAssign.ts`(쌍 표 + 묶음 안 균형 배정)를 만들고, 묶음 제출 경로(`route.ts`)가 항목을 저장하기 직전에 부른다. `imageSpecWarnings`의 «`bg`·`end` 없음» 경고를 이 항목들에서 거두고, 윤진 정의와 PRD를 «색은 비운다»로 고친다. DB 변경 없음.
- 관련 파일: 아래 「구현 계획」의 파일 목록. 규칙 정본은 `docs/service/prd/ops-tool/PRD.md` §3.1(`image_spec` 항목).

## 배경 / 문제 정의

49주차 묶음(`ops_bundles.week = '2026-W49'`, 항목 12개 중 이미지 색이 있는 6개)을 DB에서 읽은 결과다. 시작색→끝색 순서다.

| 항목 | 시작색 → 끝색 |
|---|---|
| 미션 1 | 초록 → 짙은 초록 |
| 미션 2 | 보라 → 분홍 |
| 미션 3 | 하늘 → 파랑 |
| 히어로 카드 1 | 노랑 → 초록 |
| 히어로 카드 2 | 초록 → 하늘 |
| 히어로 카드 3 | 보라 → 파랑 |

초록 계열(초록·짙은 초록) 4칸, 파랑 계열(하늘·파랑) 4칸이고 나머지는 보라 2칸, 분홍 1칸, 노랑 1칸이다. 같은 주에 홈에 등록된 카드의 바탕색은 분홍·하늘·노랑·짙은 초록이라(등록 시 시스템이 배정, `assignFeedColors`) 카드 색 쪽은 쏠리지 않았다. 쏠림은 에이전트가 제출한 이미지 색에서 생겼다.

원인은 세 가지다.

1. **선택 기준이 없다.** 윤진 정의(모드 ⑨)는 «`image_spec.bg`·`image_spec.end`(`#rrggbb`)를 반드시 낸다»고만 적고, 어떤 색을 어떻게 고르는지는 적지 않는다. 에이전트는 주제(걷기 → 초록, 찬 공기 → 하늘)에 맞춰 즉흥으로 고른다.
2. **같은 정의 안의 충돌.** Boundaries에는 «choosing colors myself»가 금지로 있고, 카드 색에 대해서는 «Leave the colors and the seed empty, because the system sets them»라고 적혀 있다. 이미지 색만 에이전트가 정한다.
3. **승인 색 쌍(`tribePalettes.ts`)이 이 경로에 걸려 있지 않다.** 공통 5쌍은 «색 채우기»(`fill_color`) 서랍에서 사람이 고를 때만 쓰이고, 에이전트가 낸 `bg`·`end`는 어떤 표와도 대조하지 않는다. 그 5쌍도 청록·초록이 2개라 표 자체가 한쪽으로 기운다.

## 상세 요구사항

### 서비스/코드베이스 관점

- **배정 대상**: 종류가 `home_feed_card` 또는 `mission`이고, `image_spec.preset_id`가 있으며, `tribe_id`가 없고, 미션 소개 카드(`resource.template_type = 'mission_spotlight'`, `usesMissionImage`)가 아닌 항목. 에이전트가 `bg`·`end`를 보내도 **무시하고 덮어쓴다**(쏠림의 원인이 에이전트 색이므로). `tribe_id`가 있는 항목은 이번에 건드리지 않는다(트라이브 승인 쌍과 «색 대기»(`color_pending`) 흐름이 따로 있다).
- **색 쌍 표(`IMAGE_COLOR_PAIRS`)**: 통합 팔레트 9색(`FEED_COLORS`: 빨강·노랑·초록·보라·파랑·짙은 초록·분홍·하늘·흰색)에서 만든 시작색→끝색 쌍 10개 안팎. 각 쌍에 «계열»을 달아 둔다(노랑·초록·분홍·파랑(하늘·파랑)·보라·빨강 여섯 계열). 흰색은 이미지 바탕으로 쓰지 않는다. 쌍 목록과 계열은 채원①이 판정에서 정하고(시각 결정), 정본은 `docs/service/prd/ops-tool/PRD.md`의 새 절에 표로 둔다. 코드 상수는 hex를 직접 적지 않고 `FEED_COLORS` 키로 적어 `hex`를 읽는다.
- **균형 배정(`assignImageColors`)**: 한 묶음의 대상 항목 전체를 한 번에 받아, 항목마다 «지금까지 이 묶음에서 가장 적게 쓰인 계열의 쌍»을 고른다. 같은 계열이 몰리지 않게 계열별 사용 칸 수를 세고, 동점이면 항목 ID에서 만든 고정 시드(`stableImageSeed`)로 정한다. 같은 쌍은 모든 쌍을 한 번씩 쓰기 전에는 다시 쓰지 않는다. 같은 입력은 언제나 같은 출력이다(난수·시각 없음). 항목 순서가 바뀌어도 결과가 달라지지 않게 정렬 기준을 항목 ID로 둔다.
- **쏠림 한도**: 대상이 4개 이상인 묶음에서 한 계열이 색 칸의 25%(올림)를 넘지 않는다. 49주차 입력(대상 6개, 칸 12개)이면 한 계열 3칸 이하이고, 그러면 초록+파랑 두 계열의 합도 50%를 넘지 않는다.
- **저장 위치**: 배정 결과는 항목 `original.image_spec.bg`·`end`에 쓴다(`ops_bundles.raw`에는 에이전트가 제출한 원문이 그대로 남고 `raw_hash`도 그대로다). 호출 위치는 `route.ts`의 항목 저장 직전이다(약 176~190행, `items.map`으로 `original`을 넣는 곳).
- **검증 경고**: `imageSpecWarnings`(`imageSpec.ts`)의 «`preset_id`는 있는데 `bg`·`end`가 없다» 경고는 이 항목들에서 더 내지 않는다(시스템이 채운다). 에이전트가 `bg`·`end`를 보내면 «이미지 색은 시스템이 정해서 보낸 값은 쓰지 않아요» 경고를 낸다(오류는 아니다). `jam_badge`·`collection_launch`는 이전 그대로다.
- **에이전트 정의**: `.claude/agents/jam-marketer.md` 모드 ⑨의 «Always give `image_spec.bg` and `image_spec.end`…» 문장을 «`image_spec`에는 `preset_id`만 내고 `bg`·`end`는 비운다. 이미지 색은 시스템이 묶음 안에서 쏠리지 않게 정한다»로 바꾼다. Boundaries의 «choosing colors myself»와 모순이 없어진다.

### UI/UX 관점 (해당 시)

- 어드민 화면 변경은 없다. 승인 전 미리보기·자동 제작은 이미 `original.image_spec.bg`·`end`를 읽으므로 그대로 동작한다(`pickAutoImageItemIds`가 색이 있는 항목을 대상으로 삼는다).

### 컨텐츠 관점 (해당 시)

- 쌍 표의 색 조합은 디자인 결정이다. 시안을 새로 그리지 않고 기존 통합 팔레트 색만 짝지으며, 사용자가 표를 바꾸고 싶으면 PRD 표와 코드 상수 한 곳씩 고친다.

## 구현 계획

1. **새 모듈** `jam-web/src/lib/admin/opsInbox/imageColorAssign.ts`: `IMAGE_COLOR_PAIRS`(색 키 쌍 + 계열), `isImageColorTarget(item)`(대상 판정: 종류·`preset_id`·`tribe_id` 없음·`usesMissionImage` 제외), `assignImageColors(items)`(순수 함수. 대상 항목 ID → `{ bg, end }` 맵을 돌려준다). `FEED_COLORS`·`stableImageSeed`·`usesMissionImage`를 가져다 쓴다.
2. **제출 경로** `jam-web/src/app/api/admin/ops-inbox/route.ts`(약 176~190행 항목 저장 부분): 검증을 통과한 `items`에 `assignImageColors`를 적용해 `original.image_spec`에 `bg`·`end`를 덮어쓴 뒤 저장한다. 시험 묶음(`is_sample`)도 같은 규칙을 쓴다.
3. **검증 경고** `jam-web/src/lib/admin/opsInbox/imageSpec.ts`(`imageSpecWarnings`): 대상 종류에서 «`bg`·`end` 없음» 경고를 거두고 «에이전트가 낸 색은 쓰지 않는다» 경고를 더한다. `validate.ts` 약 771~774행의 호출은 그대로다.
4. **윤진 정의** `.claude/agents/jam-marketer.md`(모드 ⑨ 줄의 `image_spec` 문장), 루틴 설명 `.claude/skills/jam-work/references/scheduled-jobs.md`의 `image_spec` 관련 문장(있으면).
5. **문서** `docs/service/prd/ops-tool/PRD.md` §3.1의 `image_spec` 행(약 84행)과 §8.8 자동 제작 절(약 1417행: «색이 없는 항목은 만들지 않는다»는 서술은 `color_pending` 항목에 대한 말로 좁힌다), 새 절 «이미지 색 배정»(쌍 표·계열·균형 규칙·쏠림 한도). `docs/service/content/TRIBES.md` 「승인 색 쌍」은 바꾸지 않고 «트라이브 카드와 사람이 직접 고르는 색 채우기용»이라는 한 줄만 더한다.
6. **시험**: `__tests__/imageColorAssign.test.ts`(균형·고정 시드·같은 쌍 재사용 순서·대상 판정·트라이브 제외·미션 소개 카드 제외·49주차 입력 재현), `imageSpec.test.ts`(경고 변경), 제출 경로 시험(`ops-inbox/__tests__/route.test.ts`)에 «에이전트가 낸 색을 시스템 색으로 덮어 저장한다» 1건.

계획 규모: 변경 파일 약 8개(새 모듈·시험 포함), 변경 줄 수 약 400줄이라 `plan_only` 임계값을 넘길 수 있다. 워크플로 호출 때 `planOnlyWaiver`에 이 계획을 근거로 적는다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)

- 49주차 묶음과 같은 입력(미션 3개 + 히어로 카드 3개, 각각 49주차의 원래 색을 `bg`·`end`로 가진 항목)을 `assignImageColors`에 넣으면 한 계열이 색 칸 12개 중 3칸을 넘지 않고, 초록 계열과 파랑 계열의 합이 6칸을 넘지 않는다. 시험이 이 입력으로 확인한다.
- 대상 항목이 4개 이상인 묶음(4~12개 여러 경우)에서 한 계열이 색 칸의 25%(올림)를 넘지 않는다. 같은 입력을 두 번 넣으면 같은 결과이고, 항목 순서를 섞어도 항목마다 같은 쌍이 나온다.
- `tribe_id`가 있는 항목, `mission_spotlight` 카드, `preset_id`가 없는 항목, `badge_intro` 등 이미지를 만들지 않는 유형은 배정 대상이 아니고 `original`이 바뀌지 않는다.
- 제출 경로 시험: 에이전트가 `bg`·`end`를 보낸 대상 항목이 저장된 뒤 `original.image_spec`의 `bg`·`end`가 쌍 표의 값이고, `ops_bundles.raw`와 `raw_hash`는 제출 원문 그대로다.
- `imageSpecWarnings`: 대상 항목에서 `bg`·`end`가 비어 있어도 경고하지 않고, 값을 보내면 «쓰지 않는다» 경고를 낸다. `jam_badge`·`collection_launch`의 기존 경고는 그대로다.
- `jam-marketer.md`에 `bg`·`end`를 내라는 문장이 남아 있지 않고 «비운다»로 바뀌어 있다. PRD §3.1·§8.8과 새 절이 코드와 같은 규칙을 적는다. `bash scripts/verify.sh`가 통과한다.

### 후속 범위 (담당: 카리나, 시점: 머지 뒤)

- 이미 제출된 49주차 묶음의 이미지는 그대로 둔다. 이미 만들어진 이미지(예약된 항목)를 새 색으로 다시 만들지는 사용자에게 따로 묻는다.
- 윤진의 주간 예약 실행은 저장소의 `.claude/agents/jam-marketer.md`를 읽으므로 이 정의 변경은 push 뒤에 반영된다. push는 사용자 요청 때만 한다.
- 50주차(12/7~) 묶음이 들어오면 이미지 색 계열 분포를 DB에서 다시 읽어 한도 안인지 보고한다.

## 완료 기록

### 구현 내용 요약
- 운영 묶음 제출 경로(`ops-inbox` POST)가 홈피드 카드·미션 이미지의 시작색(`bg`)과 끝색(`end`)을 서버에서 배정한다. 에이전트가 보낸 색은 덮어쓰고, 제출 원문(`raw`·`raw_hash`)은 그대로 보존한다.
- 배정 규칙은 `imageColorAssign.ts` 한 곳에 있다. 통합 팔레트 9색으로 만든 쌍 11개를 항목 ID 순으로 하나씩 고른다. 쌍을 가장 적게 쓴 후보를 먼저 보고, 같으면 계열 쏠림이 작은 쪽, 그다음 제곱합이 작은 쪽, 마지막에 `stableImageSeed`로 정한다. 난수는 쓰지 않아서 같은 입력은 같은 결과다.
- 대상이 4개 이상인 묶음에서는 한 계열이 색 칸의 25%(올림)를 넘지 않는다. 49주차와 같은 입력으로 시험하면 한 계열이 3칸 이하이고 초록과 파랑 합이 6칸 이하다.
- 대상이 아닌 항목(`tribe_id`가 있는 항목, `mission_spotlight`, `preset_id`가 없는 항목)은 그대로 둔다.
- 윤진(`jam-marketer.md` 모드 ⑨)은 `preset_id`만 내고 `bg`·`end`는 비운다. 비워도 경고하지 않고, 값을 보내면 «쓰지 않는다» 경고가 나온다.
- 원인은 49주차 이미지 색 12칸 중 초록 4칸과 파랑 4칸을 에이전트가 직접 골랐다는 점이었다. 카드 배경·박스·칩 색은 시스템이 이미 배정하고 있었으므로 원인이 아니다.
