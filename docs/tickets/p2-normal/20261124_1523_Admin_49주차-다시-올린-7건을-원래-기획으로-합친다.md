# [Admin] 49주차 다시 올린 7건을 원래 기획으로 합친다

## 핵심 요약

- 요구사항: 티켓 20261124_1050에서 49주차 실패 7건을 새 기획 `weekly-2026-W49-retry-01`로 다시 올려 예약했다. 그러나 어드민의 원래 기획 「12월 첫 주: 해 짧은 날의 걷기」(`weekly-2026-W48-0901`)에는 7건이 여전히 「실패」로 보여서, 사용자가 문제가 남았다고 판단했다. 사용자 결정(2026-11-24 「원래 기획으로 합치기」)에 따라, 다시 올린 7건의 예약 결과를 원래 기획의 같은 항목으로 옮기고 다시 올린 기획을 지운다.
- 구현 계획: 일회성 데이터 마이그레이션 `jam-web/supabase/migrations/360_ops_w49_retry_merge.sql`(되돌림 `360_ops_w49_retry_merge_down.sql`)을 쓴다. 백업 표에 바뀌는 행을 담은 뒤 ① 원래 항목 7개를 「예약됨」으로 바꾸고 만든 자원·이미지 색·이미지 주소·문안을 다시 올린 항목 값으로 채운다 ② 다시 올린 항목의 승인·실행 결정 기록 14건을 원래 항목으로 옮긴다 ③ 다시 올린 기획을 지운다.
- 관련 파일: 위 마이그레이션 두 개. 코드 변경은 없다.

## 배경 / 문제 정의

- 실패(`failed`)는 끝 상태라서 같은 항목을 다시 예약하는 기능이 없다. 그래서 티켓 20261124_1050은 실패 7건을 같은 주차의 새 기획으로 다시 제출했고, 원래 기획의 실패 기록은 그대로 두었다.
- 어드민 목록과 상세는 기획 단위로 보인다. 원래 기획은 「예약 · 일부 실패」로, 다시 올린 기획은 별도 줄로 보인다. 그래서 사용자 입장에서는 49주차 기획의 실패가 해결되지 않은 것으로 보였다.
- 미션 3개와 카드 4장은 이미 예약돼 있었다(다시 올린 기획 쪽). 홈 노출에는 문제가 없었다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 만든 미션·카드(`missions`·`today_cards`)는 건드리지 않는다. 이 자원들은 운영 항목을 거꾸로 가리키는 칸이 없고, 항목의 `created_resource`만 자원 ID를 가진다.
- 원래 항목에서 바꾸는 칸은 `status`·`created_resource`·`original.image_spec`·`edited`·`updated_at`뿐이다.
  - `original.image_spec`: 티켓 20261124_1052가 다시 올린 항목에 새로 배정한 색으로 바꾼다(이미지 색은 시스템 배정 값이라 사용자 수정으로 보지 않는다).
  - `edited.copy`: 사용자가 검토중에 고친 문안을 그대로 두고, 다시 올릴 때 고친 `c-lock-open` 제목(「잠긴 배지를 열어 봐요」)을 더한다.
  - `edited.resource`: 다시 올린 항목 값(지금 미션·카드가 쓰는 이미지 주소)으로 바꾼다.
- 원래 항목의 실패 결정 기록(`fail` 7건)은 이력으로 남긴다. 목록의 실패 사유 줄은 상태가 「실패」인 행에만 그려지므로(`OpsItemList.tsx`) 화면에는 나오지 않는다.
- 이미지 파일은 다시 올린 항목 ID 경로(`ops-inbox/missions/<다시 올린 항목 ID>.webp` 등)에 그대로 둔다. 미션·카드가 이 주소를 쓰고 있어서 옮기지 않는다.

## 완료 조건

- 드라이런(DO 블록 안에서 합치기 → 되돌림 → 예외로 취소)에서 합친 뒤 상태가 기대와 같고, 되돌린 뒤 두 기획의 항목·결정 기록이 실행 전과 똑같다(행 전체의 해시 비교).
- 실행 뒤 원래 기획의 12개 항목이 모두 「예약됨」이고, 7개 항목의 `created_resource`가 다시 올린 항목과 같은 미션·카드를 가리킨다.
- 다시 올린 기획 `weekly-2026-W49-retry-01`이 없고, 옮긴 결정 기록 14건이 원래 항목을 가리킨다.
- 로컬 어드민에서 원래 기획을 열면 「일부 실패」 표시가 없고 12개가 「예약됨」으로 보인다.

## 완료 기록

### 구현 내용 요약
- 일회성 데이터 마이그레이션 360(되돌림 짝 파일 포함)을 쓰고 공용 DB에 실행했다. 코드 변경은 없다.
- 원래 기획 `weekly-2026-W48-0901`의 실패 항목 7개를 다시 올린 항목의 예약 결과로 채워 「예약됨」으로 바꿨다. 승인·실행 결정 기록 14건을 원래 항목으로 옮기고, 다시 올린 기획 `weekly-2026-W49-retry-01`(항목 7·제출 기록 1)을 지웠다.
- 원래 항목의 실패 결정 기록 7건은 이력으로 남겼다. 그래서 각 항목의 결정 기록은 승인(10:40) → 실패(10:40) → 승인(11:16) → 실행(11:16) 순서로 보인다.

### 실행
- 드라이런과 실행(2026-11-24 15:23~15:28 KST 사이): 합치기와 되돌림을 한 DO 블록에서 돌리고 예외로 취소했다. 결과는 다음과 같다.
  - 합친 뒤: 원래 기획 12개 모두 예약됨, 다시 올린 기획 0행, 결정 기록은 실패 7·승인 19·제출 1·실행 12·수정 8이었다. `c-lock-open`의 `edited.copy.title`은 「잠긴 배지를 열어 봐요」, 이미지 주소·색은 다시 올린 항목 값이었다.
  - 되돌린 뒤: 두 기획의 기획·항목·결정 기록 행 전체 해시가 실행 전과 같았다(`state_restored=t`). 미션 3개·카드 4장의 행 해시도 바뀌지 않았다(`res_untouched=t`).
- 실행: 드라이런과 같은 합치기 DO 블록을 실행했다. 백업 표 `ops_w49_retry_merge_backup_20261124`(RLS 켬, anon·authenticated 권한 회수)에 30행(원래 항목 7·기획 1·다시 올린 항목 7·결정 기록 15)이 담겼다.

### 검증
- DB(실행 직후, 읽기 전용): 원래 기획 12개 모두 예약됨, 49주차 기획은 원래 기획 하나뿐, 주인 없는 결정 기록 0건이었다. 12개 항목의 `created_resource`가 모두 있는 미션·카드를 가리켰고, 미션은 `image_url`이 항목의 `edited.resource.image_url`과 같았다.
- 로컬 어드민(`jam-web-admin` 실행 설정, dev 로그인): 기획 상세의 단계 표시줄이 「예약 12개」였고 「일부 실패」 표시가 없었다. 운영플랜 목록에는 49주차가 「예약됨 · 12개」 한 줄로만 보였다.

### 주요 의사결정 / 검토한 대안
- 사용자가 「원래 기획에 「다시 올림」 표시」(데이터는 두고 화면 코드만 고치는 안) 대신 「원래 기획으로 합치기」를 골랐다(2026-11-24).
- 이미지 파일은 옮기지 않았다. 미션·카드가 다시 올린 항목 ID 경로의 파일을 쓰고 있어서, 옮기면 자원 주소까지 바꿔야 한다.

### 잔여 이슈
- 이 항목들은 이미지 파일이 항목 ID와 다른 경로에 있다. 그래서 어드민에서 「공개 전 취소」를 하면 이미지 파일 정리(`removeOpsImageFiles`, 항목 ID 경로 기준)가 이 파일을 지우지 못하고 남긴다. 「이미지 다시 만들기」를 하면 원래 항목 ID 경로에 새 파일을 쓰고 자원 주소를 바꾸므로 문제가 없다.
- 실패 항목을 같은 기획에서 고쳐 다시 예약하는 기능은 여전히 없다. 다음에 실패가 나면 또 새 기획으로 다시 올려야 한다.
- 백업 표는 복구가 필요 없다고 확인되면 지운다(`DROP TABLE IF EXISTS public.ops_w49_retry_merge_backup_20261124;`).
- 티켓 20261124_1517의 후속 범위(49주차 이미지 6건 다시 배정)는 이제 원래 기획의 항목을 대상으로 한다.
