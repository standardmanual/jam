# [Infra] UI 소스 정리 2-3회차: 토큰과 정본 컴포넌트 변경에 사용자 승인 관문을 건다

## 핵심 요약

- 요구사항: 상위 티켓 20261125_1923 2회차(관문 1차)의 셋째 조각. 토큰 파일과 정본 컴포넌트(`jam-web/src/components/ui/`)를
  바꾸는 커밋은 **티켓(또는 그 상위 티켓)에 사용자 승인 기록이 있을 때만** 들어가게 git 훅으로 막는다. 새 정본 컴포넌트는
  스토리 파일이 함께 있어야 한다. 승인 줄은 카리나만 쓰고 에이전트는 쓰지 못하게 아현·민지 정의와 jam-work 절차에 한 줄씩 넣는다.
- 사용자 결정(2026-11-25): 관문은 토큰만이 아니라 UI 개발 전 과정에 건다. 새 컴포넌트·variant·토큰은 사용자 승인 기록이 있어야 한다.
- 서비스 화면은 바뀌지 않는다.
- 관련 파일: `scripts/check-ui-approval.mjs`(신규), `scripts/check-ui-approval.test.mjs`(신규), `.githooks/commit-msg`(신규,
  실행 권한), `.claude/agents/jam-developer.md`(규칙 한 줄), `.claude/agents/jam-reviewer.md`(「Checklist」 절 62행 근처
  한 줄), `.claude/skills/jam-work/SKILL.md`(1.5절 «needsApproval» 단락과 4절에 한 줄씩)

## 배경 / 문제 정의

지금은 새 토큰·새 컴포넌트를 채원① 판정이 `needsApproval`로 올릴 때만 사용자에게 묻는다. 그 판정은 모델의 판단이라
놓치면 그대로 커밋된다. 커밋 단계에서 기계적으로 확인하는 장치가 없다.

## 구현 계획

1. **`scripts/check-ui-approval.mjs`** (Node 표준 라이브러리 + `git` 명령)
   - 입력: 커밋 메시지 파일 경로(첫 인자). 시험용으로 `--root <dir>`, `--staged <경로…>`(스테이징 목록 대신), `--status <A|M|D…>`를 받는다.
   - 건너뜀: 머지·리베이스·체리픽 진행 중(`git rev-parse --git-path MERGE_HEAD`·`REBASE_HEAD`·`CHERRY_PICK_HEAD`가 있으면).
     이미 검사를 거친 커밋을 옮기는 경우라서다.
   - 보호 경로: `jam-web/design-system/tokens/**`, `jam-web/src/app/globals.css`, `jam-web/src/components/ui/**`
     (단 `*.test.*`·`*.stories.*`·`__tests__/**`는 제외). 스테이징된 파일(추가·수정·삭제 모두)에 보호 경로가 없으면 통과.
   - 보호 경로가 있으면:
     - 커밋 메시지에서 티켓 번호(`\d{8}_\d{4}`)를 모두 찾는다. 없으면 실패.
     - 각 번호의 티켓 파일(`docs/tickets/**/<번호>_*.md`, 한글 파일명 NFC·NFD 모두 대응)과 그 frontmatter `parent:` 티켓을 읽는다.
       스테이징된 판이 있으면 스테이징 판(`git show :경로`)을, 없으면 작업 폴더 판을 읽는다.
     - 그중 하나라도 `^- 사용자 승인: YYYY-MM-DD — 내용` 형식의 줄이 있으면 통과, 없으면 실패.
   - 새로 추가된(`A`) 정본 컴포넌트 `jam-web/src/components/ui/<이름>.tsx`(시험·스토리 제외)는 같은 폴더의 `<이름>.stories.tsx`가
     스테이징돼 있거나 이미 있어야 한다. 없으면 실패.
   - 실패 메시지(한국어): 무엇이 막혔는지(보호 경로 목록), 왜(사용자 승인 기록 없음 / 스토리 없음), 어떻게 푸는지
     («카리나가 사용자 승인을 받은 뒤 티켓에 `- 사용자 승인: YYYY-MM-DD — 내용` 줄을 적는다. 에이전트는 이 줄을 쓰지 않고,
     `--no-verify`로 우회하지 않는다»).
2. **`.githooks/commit-msg`** (bash, 실행 권한) — `node "$(git rev-parse --show-toplevel)/scripts/check-ui-approval.mjs" "$1"`을
   부르고 종료 코드를 그대로 돌려준다. 우회 환경변수는 두지 않는다(기존 pre-commit의 무인 루틴 방어와 같은 이유).
3. **`scripts/check-ui-approval.test.mjs`** — 임시 git 저장소 픽스처로: 보호 경로 없음 → 통과, 보호 경로 + 승인 줄 있는 티켓 →
   통과, 승인 줄이 상위 티켓에만 있음 → 통과, 승인 줄 없음 → 실패, 메시지에 티켓 번호 없음 → 실패, 새 정본 컴포넌트 + 스토리 없음
   → 실패, 머지 진행 중 → 건너뜀, 시험·스토리 파일만 바뀜 → 통과.
4. **`.claude/agents/jam-developer.md`** — 규칙 목록에 한 줄: 티켓의 `- 사용자 승인:` 줄을 쓰거나 고치지 않는다. 승인 관문에
   커밋이 막히면 `--no-verify`로 우회하지 말고 그 메시지를 담아 `halted`로 돌아온다.
5. **`.claude/agents/jam-reviewer.md`** — 「Checklist」에 한 줄: diff가 티켓의 `- 사용자 승인:` 줄을 추가·수정하면 FAIL(카리나만 쓴다).
6. **`.claude/skills/jam-work/SKILL.md`** — 1.5절 «needsApproval이 승인되면» 단락과 4절(승인 후 처리)에 한 줄씩: 사용자가 승인하면
   카리나가 Workflow를 다시 부르기 **전에** 해당 티켓(또는 상위 티켓)에 `- 사용자 승인: YYYY-MM-DD — <승인한 항목>` 줄을 적고 커밋한다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)
- 시험 8가지 경우가 모두 통과한다.
- `.githooks/commit-msg`가 실행 권한을 갖고, 보호 경로를 바꾸면서 승인 줄 없는 티켓 번호로 커밋하면 실제로 막힌다(시험 저장소에서 확인).
- 보호 경로를 건드리지 않는 커밋(문서·티켓·시험만)은 영향이 없다.
- 아현·민지 정의와 SKILL.md에 위 규칙이 한 줄씩 들어간다. 그 밖의 문장은 고치지 않는다.
- `scripts/verify.sh` 전체 통과. 서비스 화면 코드와 토큰 파일은 바뀌지 않는다.

### 후속 범위 (담당: 카리나, 시점: 머지 뒤)
- 지금 진행 중인 다른 UI 티켓(정본 컴포넌트를 바꾸는 것)이 이 관문에 막힐 수 있다. 머지 직후 해당 티켓 목록을 사용자에게 보여 주고
  승인 줄을 소급할지 묻는다.
