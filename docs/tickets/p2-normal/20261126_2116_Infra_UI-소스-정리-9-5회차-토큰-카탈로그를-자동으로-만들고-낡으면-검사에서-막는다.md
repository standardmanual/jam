# [Infra] UI 소스 정리 9-5회차: 토큰 카탈로그를 자동으로 만들고 낡으면 검사에서 막는다

## 핵심 요약

- 요구사항: 상위 티켓 20261125_1923 9회차 다섯 번째 조각. 토큰이 어느 층에 어떤 이름·값으로 있고 몇 곳에서 쓰이는지 한 문서로 본다. 손으로 쓰지 않고 생성기가 만들며, 토큰이나 코드가 바뀌었는데 문서가 낡았으면 verify가 실패한다.
- 사용자 승인: 2026-11-26 — 9회차 분할안(9-5 토큰 카탈로그 자동 생성). 형식은 정본 목록 문서(`docs/service/prd/ui-components/README.md`, 생성기 `scripts/gen-component-list.mjs`)와 같은 방식의 생성 문서다. 스토리북 토큰 페이지는 만들지 않는다(토큰 소개 스토리 6개는 그대로).
- 관련 파일: 새 `scripts/gen-token-catalog.mjs`(+시험 `scripts/gen-token-catalog.test.mjs`), 새 생성 문서 `docs/service/prd/ui-components/tokens.md`, `scripts/verify.sh`(`component-list` 단계 바로 뒤), `.githooks/pre-commit`(티켓 색인 `--stage` 단계 근처, 283~301줄), `docs/service/prd/ui-components/README.md` 머리 또는 `docs/INDEX.md` 생성 근거에 새 문서 안내 한 줄(필요할 때).
- 화면 변화: 없음.

## 구현 계획

1. **생성기 `scripts/gen-token-catalog.mjs`**: 아래 원천을 읽어 `docs/service/prd/ui-components/tokens.md`를 만든다.
   - 층과 원천: 기본값(`jam-web/design-system/tokens/primitive.css`, `jam-web/src/app/jam-theme.css`의 `@theme`), 의미(`semantic.css`), 컴포넌트(`component.css`), 어드민(`jam-web/src/app/admin-theme.css`와 `globals.css`의 `[data-admin-theme]`). `fonts.css`·`@theme inline` 매핑은 표의 «클래스» 칸 근거로만 쓴다.
   - 표 칸: 이름 · 정의 값(파일에 적힌 그대로) · 최종 값(`:root` 기준으로 `var()`를 끝까지 따라간 값, 못 풀면 정의 값) · 클래스(`@theme inline`·`@theme`으로 이어진 유틸리티 이름, 예 `text-muted`·`bg-card-bg`) · `var()` 참조 수 · 클래스 사용 수 · 쓰는 파일 수.
   - 사용 수는 `jam-web/src/**`와 `jam-web/design-system/**`의 `.ts`·`.tsx`·`.css`에서 센다(시험·스토리 제외, 토큰 파일 자신 제외). 토큰 파일 안에서 다른 토큰이 참조하는 수는 «토큰 안 참조» 칸으로 따로 센다. 주석 안 글자는 세지 않는다(`scripts/strip-code-comments.mjs`).
   - 같은 이름이 `:root`와 `@media`·`[data-service-theme]` 블록에 다시 정의되면 한 줄에 «덮어쓰기 있음»을 적는다. `primitive.css`와 `jam-theme.css` 양쪽에 같은 이름이 있으면 두 값이 같은지 표시한다(다르면 문서 머리 «주의»에 목록).
   - 머리에 생성 표식(`<!-- BEGIN generated: gen-token-catalog -->` 형식, 기존 생성 문서 관례), 층 규칙 요약 3줄(9-1 티켓 20261126_1908 «층 규칙»을 가리킨다), 층별 개수, **쓰는 곳 0인 토큰 목록**(10회차 정리 근거)을 둔다.
   - 출력은 결정적이어야 한다(정렬 고정, 날짜·시각을 넣지 않는다).
2. **`--check`**: 메모리에서 만든 결과와 파일이 다르면 차이 요약과 함께 종료 코드 1. **`--stage`**: 파일을 다시 쓰고 `git add`한다(티켓 색인 `gen-ticket-index.mjs --stage`와 같은 방식).
3. **연결**: `scripts/verify.sh`에 `token-catalog` 단계(`--check`)를 `component-list` 단계 바로 뒤에 더하고 마지막 «verify 통과» 목록에 이름을 더한다. `.githooks/pre-commit`은 스테이지된 파일에 토큰 파일·`jam-web/src/**`·`jam-web/design-system/**`가 있으면 `--stage`로 다시 만든다(티켓 색인 단계 옆). 9-4가 동시에 `verify.sh`의 `token-refs` 단계 뒤와 pre-commit의 ui-rules 단계를 고치므로 그 자리는 건드리지 않는다.
4. 시험: 작은 임시 토큰 파일·소스 폴더로 층 분류, 최종 값 풀기(두 단계 참조·`color-mix` 안 참조), 사용 수(주석 제외·클래스 수), `--check` 종료 코드(같음 0, 다름 1)를 본다. 생성기는 `--root`로 원천 위치를 바꿀 수 있게 한다.
5. 확인(아현): 시험, 생성 실행, `--check` 통과, `node scripts/gen-doc-index.mjs --check` 등 문서 색인 검사(새 문서가 색인 규칙에 걸리면 그 규칙대로). **push하지 않는다.** `verify.sh` 전체는 카리나가 돈다.
