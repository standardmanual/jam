## 핵심 요약

- 요구사항: A3에서 확정한 챕터 오름 보상(개수·확률)을 어드민에서 코드 수정 없이 바꿀 수 있게 새 편집 구역을 만든다.
- 구현 계획: 아래 «구현 계획»의 단계를 파일 단위로 따른다(3단계).
- 관련 파일: `jam-web/src/components/admin/balance/ChapterRewardSection.tsx`(신규), `jam-web/src/lib/admin/balance/chapterReward.ts`(신규) / `sections.tsx`, `jam-web/src/app/admin/balance/page.tsx`, `jam-web/src/app/api/admin/balance/route.ts`와 시험
- 선행 티켓: 20261127_1726(B3), 20261127_1723(A3)
- 상위 티켓: 20261127_1720(챕터 게이지 카드로 전환하고 캡슐을 폐지한다). 기획 경위와 사용자 확정 결정은 상위 티켓에 있다.

## 배경 / 문제 정의

상위 티켓 20261127_1720의 단계 C(전환, 같은 배포 창)에 속하는 조각이다. 잼은 챕터를 올리는 경험치이고 포인트는 별도 재화이며, 캡슐은 폐지한다(2026-11-27 사용자 결정). 챕터 1~9의 필요 잼은 870, 1,120, 1,260, 1,600, 1,980, 2,205, 2,700, 3,300, 3,960이고, 넘친 잼은 이월한다.

## 구현 계획 (2026-11-28, 현재 코드 기준으로 다시 씀)

밸런스 설정(`/admin/balance`)에 구역 `chapter_reward`(라벨 «챕터 보상»)를 새로 만든다. 구역 키는 C8이 정한 `chapter_reward`이고 확률 안내 «바뀐 날짜»가 이 키로 칸 이름을 읽는다. 모델은 «캡슐» 구역(`lib/admin/balance/capsule.ts`)이다: 표 둘을 한 구역으로 편집하고, 행 단위 저장·충돌·되돌림은 공용 모듈(`save.ts`, `rowwise.ts`)에 맡긴다. DB·SQL 변경은 없다(표는 B3 마이그레이션 366에 이미 있다). 어드민 «캡슐» 구역은 이 티켓에서 그대로 두고 C10b에서 걷는다(C9a 순서 결정).

편집하는 값(시작값은 A3 확정 후보 E이고 DB 기본값 366과 같다):
- `chapter_reward_policy`(`id = 1` 한 행): 등급 확률 `rarity_common`·`rarity_rare`·`rarity_epic`·`rarity_mystic`(퍼센트, 기본 30·40·22·8, 네 칸 합계가 100이어야 저장), `other_tribe_probability`(0~1, 기본 0.2), `pity_epic_threshold`(1 이상 정수, 기본 15).
- `chapter_definitions.reward_count`(챕터 1~9, 마지막 챕터 10은 NULL이라 칸이 없다): 그 챕터를 마칠 때 받는 아이템 배지 개수(1 이상 정수, 기본 1~3은 3, 4~6은 4, 7~9는 5). 읽기는 가공하지 않은 행에서 읽고 챕터 1~9가 NULL이면 던진다(챕터 10은 NULL을 0으로 바꿔 보이지 않는다). C9a의 `chapter.ts`(챕터별 필요 잼 편집, 같은 `chapter_definitions` 행을 `required_jam`으로 편집한다)와 같은 행을 건드리지만 열이 달라 서로 막지 않는다. 구역 수정 시각은 정책 행과 챕터 행들의 수정 시각 중 가장 늦은 것이고(`capsule.ts`와 같은 방식), 어느 구역이든 같은 챕터 행을 저장하면 수정 시각이 올라가 다른 구역의 저장이 conflict(409)가 될 수 있다. 이 점은 요약에 적고, 두 구역이 같은 행의 서로 다른 열을 쓰므로 열 단위 조건(`.eq('updated_at', 읽은 시각)`)이 그대로 맞는지 확인한다.
- 확률 안내가 읽는 칸(정책 6칸과 챕터별 개수)은 `affectsDisclosure = true`로 저장 전 확인창(`BalanceProbabilityConfirm`)이 뜬다. 정책 6칸의 목록 단일 원천은 `jam-web/src/lib/probability/disclosure.ts`의 `CHAPTER_REWARD_COLUMNS`이고 여기에 다시 적지 않는다. 챕터별 개수도 확률 안내 «개수» 표에 보이는 값이라 `affectsDisclosure = true`다.
- 같은 등급 연속 보정(`common_streak_threshold`)과 잠길 확률(`locked_roll_probability`)은 동기화와 한 값(`jam_policy`)이라 **동기화 구역에서 편집**하고 이 구역에는 안내만 둔다(캡슐 구역이 하던 것과 같다). 안내 컴포넌트는 `CapsuleSection.tsx`에서 가져오지 말고 이 구역 파일에 새로 둔다(C10b가 `CapsuleSection.tsx`를 지울 때 걸리지 않게).

1. 새 `jam-web/src/lib/admin/balance/chapterReward.ts`(구역 연결 객체 `CHAPTER_REWARD_BINDING`, 구역 id `chapter_reward`): 칸 정의(`BalanceFieldDef`)·기본값·`validateSumTo100`(등급 네 칸)·읽기·쓰기. 칸 이름은 정책은 열 이름 그대로, 챕터별 개수는 `reward_count:N`(N = 1~9). 쓰기는 정책 행 한 번과 챕터 행들을 `capsule.ts`의 `write`처럼 한 번의 충돌 검사 뒤 행 단위로 쓰고, 중간 실패 때 이미 쓴 행을 이전 값과 이전 수정 시각으로 되돌린다. 기본값 상수는 `lib/chapter/reward/policy.ts`·마이그레이션 366 시드와 같은 값이고 코드에 따로 있던 값이 아니라 화면용 사본이다(시드를 바꾸면 같은 티켓에서 바꾼다). `pity_epic_threshold` 안내(`hint`): «챕터 오름 보상은 챕터 1~9에서 최대 9번이라, 이 값이 9보다 크면 이관된 유저의 기록이 있을 때만 이 보정에 닿아요.»

### 구현 내용 요약

밸런스 설정(`/admin/balance`)에 구역 `chapter_reward`(라벨 «챕터 보상»)를 «챕터» 바로 뒤에 더했다. 입력 칸은 15개다.
- 챕터 1~9 보상 개수 `reward_count:N`(`chapter_definitions.reward_count`, 1 이상 정수, 시작값 3·3·3·4·4·4·5·5·5).
- 등급 확률 4칸 `rarity_common/rare/epic/mystic`(`chapter_reward_policy`, 시작값 30·40·22·8, 네 칸 합계가 100이 아니면 저장 거절).
- 다른 트라이브 확률 `other_tribe_probability`(0~1, 시작값 0.2), Epic 보정 `pity_epic_threshold`(1 이상 정수, 시작값 15).
정책 6칸(`CHAPTER_REWARD_COLUMNS`)과 개수 9칸은 모두 `affectsDisclosure`라 저장 전에 확률 안내 확인창이 뜬다. 읽기는 가공 없이 읽고 정책 행이 없거나 챕터 1~9 개수가 NULL이면 던진다. 챕터 10은 읽지도 쓰지도 않는다. 쓰기는 `rowwise.ts`로 정책 행을 먼저, 챕터 행은 번호 순으로 쓰고, 막히면 이미 쓴 행을 이전 값·수정 시각으로 되돌린다. 동기화와 한 값인 두 칸(Common 연속 보정·잠긴 채 나올 확률)은 이 구역에 안내와 «동기화 구역» 링크만 둔다(안내 컴포넌트는 `CapsuleSection.tsx`에서 가져오지 않고 새로 뒀다). 확률 안내 «바뀐 날짜»가 `reward_count:N`을 «N번째 챕터를 마칠 때 받는 개수»로 읽는다(숫자 뒤 을/를이 숫자마다 달라 티켓의 «챕터 N을 마칠 때»를 바꿨다). DB·SQL 변경은 없다.

### 주요 의사결정 / 핵심 메모
- «챕터» 구역(C9a)과 이 구역은 같은 `chapter_definitions` 행의 서로 다른 열(`required_jam`·`reward_count`)을 편집한다. 열이 달라 값은 겹치지 않지만 행의 `updated_at`이 하나라서, 한 구역을 저장하면 다른 구역 화면에서의 다음 저장이 conflict(409)가 될 수 있다. 새로 불러와 다시 저장하면 된다(시험·ADMIN_PRD에 적음).
- 챕터 보상 개수는 DB 제약이 0 이상이지만 화면은 1 이상으로 좁혔다(`getChapterRewardCount`도 1 미만이면 던진다).
- `pity_epic_threshold` 안내: 챕터 오름 보상은 챕터 1~9에서 최대 9번이라 이 값이 9보다 크면 이관된 유저의 기록이 있을 때만 이 보정에 닿는다.
- 범위 밖 발견물(새 티켓 없이 기존 소관): `policiesData.ts`의 챕터 보상 항목은 C10a, 어드민 «캡슐» 구역의 `CAPSULE_COLUMNS` 확인창은 C10b·D. 합계 오류 문구 «지금은 105이에요»는 공용 `validateSumTo100`(`fields.ts`)의 문장이라 숫자 끝 받침에 따라 «이에요»가 어색하다(예: «105예요»가 맞다). 이 티켓에서 고치지 않았고 P3 후속으로 남긴다.
