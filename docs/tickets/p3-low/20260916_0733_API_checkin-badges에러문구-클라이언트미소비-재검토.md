# [API] checkin-badges 에러 문구 클라이언트 미소비 — 재검토

> 출처: 티켓 20260915_2238(배지 도메인 텍스트 정비) 게이트 리뷰 sideFinding — 자동 티켓화

## 배경 / 문제 정의

티켓 20260915_2238에서 `src/app/api/checkin-badges/route.ts`의 하드코딩 에러 문구를
`d.badges.checkinMap*Error`로 이관하고 ADR 0001에 맞춰 3단계 구조를 적용하려 했으나,
현재 클라이언트(`DropsClient.tsx`)가 `!res.ok`일 때 응답 본문을 읽지 않고 조용히 무시하고
있어 이 문구가 실제로는 사용자에게 노출되지 않는다는 사실이 게이트 리뷰에서 확인됐다.

## 상세 요구사항

### 서비스/코드베이스 관점
- `DropsClient.tsx`가 `checkin-badges` 호출 실패 시 사용자에게 아무 피드백도 주지 않는
  현재 동작이 의도된 것인지 확인한다(예: 백그라운드 조회라 실패해도 무해한 경우 vs
  실제로는 사용자가 알아야 하는 실패인데 누락된 경우).
- 노출이 필요하다고 판단되면 `DropsClient.tsx`가 응답 본문의 `message`를 읽어 토스트로
  띄우도록 고치고(ADR 0001에 따라 서버 메시지를 그대로 신뢰), 이미 이관된
  `d.badges.checkinMapMissingBoundsError` 등 4개 문구가 실제로 3단계([현상]→[원인]→[해결책])
  구조를 충분히 갖추고 있는지 이 시점에 다시 검토한다(현재는 간결하게만 작성돼 있음 —
  후속 티켓 20260916_0734의 한국어 리뷰 지적사항 참고).
- 노출이 불필요하다고 판단되면(백그라운드 실패 허용) 그 판단과 근거를 이 티켓에 기록하고
  CLOSED 처리한다.

## 구현 계획
- 먼저 `DropsClient.tsx`의 `checkin-badges` 호출 목적과 실패 시 UX 의도를 코드·티켓 이력에서
  확인한다.
- 노출 여부 결정 후 필요한 만큼만 구현한다.

## 완료 기록 *(작업 완료 후 작성)*

### 구현 내용 요약
코드 조사만으로 결론이 났다 — 노출 불필요로 판단해 코드 변경 없이 종료한다.

`DropsClient.tsx`의 `handleViewportChange`(152~169행)는 지도 뷰포트가 바뀔 때마다
`checkin-badges`를 호출해 근처 POI의 배지 마커를 표시하는 **백그라운드 보강 조회**다.
`catch` 블록(167행)에 이미 "배지 마커 조회 실패는 드랍/픽업 플로우에 영향을 주지 않으므로
조용히 무시"라는 명시적 주석이 있고, `!res.ok`일 때도 마찬가지로 `return`만 하고 넘어간다
(162행). 즉 이 화면의 핵심 기능(드랍·픽업)은 이 API 실패와 무관하게 정상 동작하고,
실패 시 사용자에게 보이는 유일한 영향은 "지도에 배지 마커가 잠깐 안 뜨는 것"뿐이다 —
이건 재시도할 대상이 있는 사용자 액션의 실패가 아니라, 다음 뷰포트 변경이나 재조회 때
자연히 복구되는 보조 정보 로딩이다. 토스트로 노출하면 오히려 사용자가 대응할 방법이
없는 알림 소음이 된다.

따라서 **현재 동작(조용히 무시)이 의도된 설계로 타당하다**고 판단해 코드는 그대로 두고
이 판단 근거만 기록한다.

### 주요 의사결정 / 핵심 메모
- `d.badges.checkinMap*Error` 4개 문구는 여전히 딕셔너리에 남아 있지만 실제로 소비하는
  화면이 없다. 지금 당장 죽은 문구를 정리하지는 않는다 — 향후 이 API 실패를 실제로
  노출해야 하는 요구가 생기면(예: 배지 마커가 서비스 핵심 정보로 격상되는 경우) 그때
  이 문구들을 재사용하면 된다. 삭제와 유지 중 유지를 택한 이유는, 삭제 후 나중에 다시
  필요해지면 §4.1 3단계 구조를 처음부터 다시 작성해야 하는 비용이 더 크기 때문이다.
