# [Infra] 아현의 계획 반환 기준(`plan_only`)이 두 티켓 연속으로 선례를 이유로 지켜지지 않았다

## 핵심 요약

- 요구사항: `jam-developer.md`의 정지 조건 "파일 5개 초과 또는 100줄 이상이면 `plan_only`"가 이식 시리즈 두 티켓(20260921_2303: 3파일·140줄, 20260921_2304: 10파일·520줄)에서 지켜지지 않았다. 두 번째 티켓에서 아현은 첫 티켓 완료 기록의 "그대로 받았다"는 문장을 근거로 들었다. 기준을 실제 운용에 맞게 고치거나, 지키게 만드는 장치를 정한다.
- 구현 계획: 선택지를 정리해 사용자에게 묻는다. (A) 기준을 `jam-web` 코드 기준으로 세고, 스킬·에이전트 정의·문서·훅 변경은 제외한다 (B) 기준은 그대로 두고 워크플로가 `plan_only`를 건너뛴 결과를 게이트 전에 멈추게 한다 (C) 티켓에 "계획 반환 생략 허용"을 카리나가 명시한 경우에만 건너뛴다.
- 관련 파일: `.claude/agents/jam-developer.md` 「Stop conditions」, `.claude/workflows/jam-work.js`, `.claude/skills/jam-work/SKILL.md` 3.0절
- 상위 티켓: 20260921_2304. 출처: 카리나가 게이트 결과를 검토하다 발견. 경로: 결정 후 ③ 표준(infra)

## 배경 / 문제 정의

사고 이력의 결론은 "프롬프트로 막은 것은 예외 없이 뚫렸다"였다(`docs/agents/team-operations.md` §8). 정지 조건이 한 번의 예외 승인 뒤 선례로 굳으면, 기준이 문서에는 남고 실제로는 사라진다. 두 티켓 모두 게이트를 통과했으므로 결과에는 문제가 없었지만, 큰 작업을 먼저 쪼개 보자는 기준의 목적이 사라진 상태다.

## 사전 확인과 결정 (카리나, 2026-09-22)

### 사용자 결정

이 티켓은 선택지 A~C 가운데 사용자 결정이 필요했다. 사용자는 고르지 않고 "이 세션에서 생성된 범위밖발견물 티켓을 모두 실행해"라고 지시했다(2026-09-22). 그래서 **카리나가 추천안 C를 택했다.** 다른 안을 원하면 언제든 바꾼다.

### 선택 근거

- 2303과 2304는 「구현 계획」이 파일 단위로 적혀 있고 카리나의 사전 확인이 끝난 상태였다. 이때 아현이 계획만 반환하면 카리나가 같은 내용을 확인해 다시 부르는 왕복만 생긴다(약 10만 토큰). 규칙의 목적은 "모호한 큰 변경을 먼저 쪼개 보는 것"이므로, 면제 여부는 티켓의 계획 수준을 아는 카리나가 매번 판단하는 것이 맞다.
- 문제의 본질은 크기 기준이 아니라 **아현이 스스로 선례를 근거로 면제를 판단한 것**이다. A(기준 완화)는 인프라 변경이 코드 변경보다 파급이 작다는 가정에 기대는데 근거가 없다. B(기계 차단)는 `diffLineCount`가 `jam-web` 줄만 세서 인프라 티켓에서는 항상 0이라 기계로 크기를 재기 어렵다.

### 구현 명세

1. `.claude/agents/jam-developer.md` 「Stop conditions」의 `plan_only`: 크기는 **바뀌는 모든 파일**(코드·문서·에이전트 정의·훅·스크립트)로 센다. 다음을 면제 근거로 쓸 수 없다고 명시한다: 이전 티켓의 완료 기록이나 선례, 문서·정의 위주라는 스스로의 판단. 면제는 프롬프트에 `계획 반환 면제:`로 시작하는 줄이 있을 때만 성립하고, 면제로 진행했다면 `summary`에 그 줄을 인용한다.
2. `.claude/workflows/jam-work.js`: 선택 인자 `planOnlyWaiver`(문자열)를 받아, 있으면 아현 프롬프트에 `계획 반환 면제: <값>` 줄을 넣고, 없으면 "이 티켓에는 계획 반환 면제가 없다. 기준을 넘으면 구현하지 말고 `plan_only`로 반환하라. 이전 티켓의 선례는 면제 근거가 아니다"를 넣는다. 재시도(`retryReason`·`retryBranch`)와 충돌하지 않게 한다.
3. `.claude/skills/jam-work/SKILL.md`: 2절 `args` 목록에 `planOnlyWaiver`를 추가하고, 3.0절 `plan_only` 처리에 면제 부여 조건을 적는다. 카리나만 부여하고, (a) 티켓 「구현 계획」이 파일 단위로 적혀 있고 (b) 사전 확인이 끝났을 때만 하며, 사유를 티켓 「주요 의사결정」에 남긴다. 사용자가 검토하지 않은 큰 변경은 면제하지 않는다.
4. `docs/agents/team-operations.md` 등에 `plan_only`를 서술한 곳이 있으면 함께 고친다(`grep`으로 확인한다).
5. 검증: 이 스크립트는 하네스가 최상위 `await`·`return`을 허용하는 본문으로 감싸 실행하므로 `node --check`가 통하지 않는다. 파일이 쓰는 전역 이름(`agent`·`args`·`parallel`·`budget` 등)을 확인해 `new (Object.getPrototypeOf(async function(){}).constructor)(<전역 이름들>, <파일 내용>)`으로 문법만 확인한다. 이 파일은 파이프라인 전체의 진입점이므로 민지는 인자 없음·`retryReason` 있음·`planOnlyWaiver` 있음 세 경우의 프롬프트 조립을 diff로 따라가 확인한다. 카리나가 머지 뒤 `Workflow`를 실제로 한 번 시작해 로드 오류가 없는지 확인한다.

이 티켓은 파일 4개 안팎이라 `계획 반환 면제`가 필요 없다.
