# [Infra] retryReason으로 재작업 요구사항이 커질 때 plan_only 임계값 사전 판단 누락

> 티켓 `20260923_1237`(반복 배지 피드 표시)의 2차 구현(재작업) 게이트 리뷰 중 민지가 남긴
> `sideFindings`를 그대로 옮겨 티켓화한다. 카리나가 직접 만든 절차 개선점이라 처리 주체도
> 카리나다.

## 핵심 요약
- 요구사항: `retryReason`으로 재작업 요구사항 자체가 커지는 경우(단순 버그 수정 → 데이터 확장
  로직으로 확대), 재시도 호출 전에 `planOnlyWaiver` 필요 여부를 다시 판단하는 절차가 없다.
- 구현 계획: (research/process 성격 — 코드 변경이 아니라 `/jam-work` 스킬 문서 보완 여부를
  검토한다.)
- 관련 파일: `.claude/skills/jam-work/SKILL.md` 1단계 3번(규모 사전 판정)·2단계
  `planOnlyWaiver`/`retryReason` 설명.

## 배경 / 문제 정의

티켓 `20260923_1237`은 1차 구현(158줄, 1파일)이 게이트에서 WARN을 받은 뒤, 사용자가 요구사항
자체를 "표시 시각 텍스트 수정"에서 "회차별 가상 피드 항목 생성"으로 확장했다. 카리나가 티켓을
고쳐 `retryReason`으로 재시도를 걸었는데, 결과 diff가 279줄·3파일로 늘어 `plan_only` 임계값
(파일 5개 초과 또는 100줄 이상, `stop-conditions.md`)의 줄 수 기준을 넘겼다. `planOnlyWaiver`
없이 호출했으므로 원칙대로면 아현이 `plan_only`로 멈췄어야 했는데, 실제로는 그대로 구현까지
진행됐고 게이트 리뷰에서야 민지가 `[주의]`로 지적했다.

`/jam-work` 1단계 3번의 "규모 사전 판정"은 **최초 호출** 시점 기준으로만 서술돼 있고, 재시도
(`retryReason`)로 요구사항이 커지는 경우를 다시 판정하라는 지시가 없다 — 그래서 이번처럼
누락이 생겨도 절차상 걸러지지 않는다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 해당 없음(코드 변경 없음).

## 구현 계획

`/jam-work` SKILL.md 1단계 3번 또는 2단계 `retryReason` 설명에, "재시도로 요구사항 자체가
바뀌거나 커지면 규모 사전 판정을 다시 하고, 필요하면 `planOnlyWaiver`를 함께 넘긴다"는 문장을
추가할지 검토한다. 이번 건은 결과적으로 범위 이탈은 없었고(민지가 diff를 스펙과 대조해 PASS로
판정) 절차 누락만 있었으므로, 문서 한 줄 보완으로 충분한지 아니면 별도 자동 검사가 필요한지
판단이 필요하다.
