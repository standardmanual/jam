# [API] 이벤트 API의 빈도 제한 맵 항목 정리 + 카드 조회 1회로 통합

> 티켓 20260924_0111 게이트 리뷰(민지)의 범위 밖 발견물 2건([성능/참고])에서 자동 생성. P3.

## 핵심 요약

- 요구사항: (1) `checkRateLimit`의 인스턴스 메모리 Map은 유저별 항목이 빈 배열이 돼도 삭제되지 않아 장수 인스턴스에서 키가 누적된다. 빈 항목을 지우거나
  주기적으로 정리한다. (2) `assertCardExposable`과 `recordTodayCardEvent`가 `today_cards`를 각각 조회해 이벤트 1건당 DB 왕복이 2회다. 한 번 조회한 카드 행을
  넘겨 1회로 줄인다.
- 관련 파일: `jam-web/src/lib/today/events.ts`, `jam-web/src/app/api/today/events/route.ts`, 테스트.

## 완료 조건

- 요청이 0건으로 걸러진 유저 키가 Map에 남지 않는다(테스트). 이벤트 1건당 `today_cards` 조회가 1회다(모킹 호출 횟수로 확인). 기존 테스트 통과.
- (0111 게이트 WARN에서 이관) 회귀 테스트 2건 추가: `now === ends_at`이면 통과(양끝 포함), DB 조회 오류 시 클라이언트 메시지가 일반 문구('카드를 확인할 수 없습니다.')다.

크기 상한: 파일 3개, 40줄 이내.

## 완료 기록

### 구현 내용 요약
(1) `checkRateLimit`가 창(windowMs)마다 한 번 `sweepExpiredKeys`를 돌려 마지막 요청이 창 밖인 유저 키를 지운다. (2) `assertCardExposable`이 `content_type_id`까지 조회해 `{ ok: true, card }`를 돌려주고 `recordTodayCardEvent(input, card)`가 재조회하지 않아, 이벤트 1건당 DB 왕복이 2회에서 1회로 줄었다. (3) 0111 게이트 WARN에서 이관된 회귀 테스트 2건(종료 시각 `ends_at` 양끝 포함, DB 오류 시 일반 문구)을 추가했다.

### 주요 의사결정 / 핵심 메모
- 티켓의 "빈 항목 정리"는 문면대로 구현하면 삭제할 경우가 생기지 않아(호출 시 항상 새 타임스탬프를 push), 실제 누적 원인인 "다시 오지 않는 유저의 키"를 지우는 창 주기 스윕으로 해석했다. 스윕은 현재 호출의 windowMs로 판정하므로 호출부가 하나뿐인 지금은 문제없다.
- **규칙 점검 필요**: 실제 변경이 106줄로 `plan_only` 임계값(100줄 이상)에 걸렸는데, 카리나가 사전 규모 판정에서 티켓 문면(40줄)만 보고 세지 않았고 아현이 `[참고]`만 남기고 진행했다. 판정은 임계값 미준수였다. 사전 규모 판정은 티켓의 예상 줄 수가 아니라 테스트·시그니처 변경까지 포함해 세어야 한다.
- 크기 상한 40줄을 넘겼다(테스트 4건과 시그니처 변경).

### 잔여 이슈
- 라우트가 `exposure.card`를 넘기는 연결은 별도 테스트가 없다(WARN 사유 2). 라우트 변경은 1줄이라 후속 티켓으로 만들지 않고 관찰한다.
