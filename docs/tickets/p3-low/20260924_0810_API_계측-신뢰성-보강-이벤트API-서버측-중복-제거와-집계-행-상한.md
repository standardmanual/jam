# [API] 계측 신뢰성을 보강한다 (이벤트 API 서버측 중복 제거, 집계 1,000행 상한)

> 배포 전 점검 발견물이다. 성공 기준 4의 지표 신뢰도와 관련된다.

## 핵심 요약

- 요구사항: (1) `POST /api/today/events`가 서버에서 같은 유저·카드·이벤트의 반복 삽입을 걸러내지 못해 로그인 유저가 노출·클릭을 부풀릴 수 있다(빈도 제한은 인스턴스 메모리라 다중 인스턴스에서 약하다). (2) `aggregateTodayCardEvents`가 원본 행을 읽어 서버에서 세므로 PostgREST 기본 행 상한(1,000건)에서 조용히 잘릴 수 있다. (3) `followup`은 UI가 보내지 않는데 API는 임의 값을 받아 저장한다(보관 기한 없음).
- 구현 계획(2026-09-24 갱신): 결정이 필요 없는 두 가지를 먼저 한다. ① `aggregateTodayCardEvents`를 `.range()` 페이지 반복(1,000행 단위)으로 바꿔 행 상한에서 잘리지 않게 한다(DB 변경 없음). ② `validateTodayCardEventInput`이 `impression`·`click`만 받고 `followup`은 400으로 거부한다(2026-09-24 사용자 결정 "후속 행동은 수집하지 않는다"). DB CHECK 제약은 그대로 둔다. **결정 대기 두 가지**: ③ 서버측 중복 제거(추천: 하지 않음. 클릭 확인을 GA 기준으로 하기로 했고 규모가 작다) ④ GA 카드 클릭 이벤트 추가(GA에 지금 투데이 카드 이벤트가 없다, 2026-09-24 확인).
- 관련 파일: `jam-web/src/lib/today/events.ts`(검증 50행 근방, 집계 159~175행), `jam-web/src/lib/today/__tests__/events.test.ts`, `jam-web/src/app/api/today/events/route.ts`(검증 호출부, 변경 없을 수 있음)

## 배경 / 문제 정의

`/jam-ship` 2026-09-24 민지 모드 ② 발견물(보안 주의 1건·참고 3건). 활성 유저 17~19명 규모라 지금은 영향이 작다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)
- 집계가 1,000행을 넘어도 정확하다(테스트로 확인).
- `followup` 이벤트는 400으로 거부한다.
- `followupAction`은 받지 않고 저장하지 않는다(요청 본문에 있어도 무시하며 400으로 거부하지 않는다, insert의 `followup_action`은 항상 null). 관련 테스트를 정리한다.

### 결정 기록 (사용자, 2026-09-24)
- 서버측 중복 제거는 **하지 않는다**. 카드 클릭은 GA로 확인하기로 했고 규모가 작다. 게이트 판정 대상이 아니다.
- GA 카드 클릭 이벤트는 티켓 [20260924_0859](../p2-normal/20260924_0859_Service_투데이-카드-클릭을-GA-이벤트로도-보낸다.md)로 분리해 구현했다. 이 티켓에서는 손대지 않는다.

## 완료 기록

### 구현 내용 요약
① `aggregateTodayCardEvents`를 `.range()` 페이지 반복(1,000행 단위, `id` 오름차순)으로 바꿔 PostgREST 행 상한에서 집계가 조용히 잘리지 않게 했다. ② 기록 API가 `impression`·`click`만 받고 `followup` 이벤트는 400으로 거부한다(DB CHECK 제약은 그대로). ③ `followupAction`은 읽지 않아 요청 본문에 있어도 무시하고, insert의 `followup_action`은 항상 null이다. PRD §9에 두 동작을 반영했다. 서버측 중복 제거는 하지 않기로 결정했고, GA 카드 클릭 이벤트는 티켓 0859로 분리해 구현했다.

### 주요 의사결정 / 핵심 메모
- **1차 FAIL은 카리나의 티켓 작성 오류였다.** 구현 계획에만 "③④는 결정 대기"라고 적고 완료 조건의 "반복 삽입 서버 방어"를 「후속 범위」로 옮기지 않아, 게이트가 그 조건을 미구현으로 판정했다. 사용자 결정(중복 제거 하지 않음)을 받아 완료 조건을 고친 뒤 재작업했다.
- 재작업 브랜치 안의 티켓 파일이 staging 쪽과 다르게 고쳐져 병합 때 충돌했고, 링크가 살아 있는 staging 쪽 내용으로 정리했다.
- 재시도로 커밋 두 개가 쌓이면서 이 티켓의 총 변경이 문서 포함 144줄로 크기 기준(100줄)을 넘었다(민지 참고, 판정 영향 없음).
- 동시에 여러 파이프라인을 돌려 워크플로의 에이전트별 출력 토큰 값이 섞였다. 전체 토큰은 완료 알림의 값이다.
