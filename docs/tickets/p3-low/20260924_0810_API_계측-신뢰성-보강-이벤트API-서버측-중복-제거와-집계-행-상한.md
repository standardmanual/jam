# [API] 계측 신뢰성을 보강한다 (이벤트 API 서버측 중복 제거, 집계 1,000행 상한)

> 배포 전 점검 발견물이다. 성공 기준 4의 지표 신뢰도와 관련된다.

## 핵심 요약

- 요구사항: (1) `POST /api/today/events`가 서버에서 같은 유저·카드·이벤트의 반복 삽입을 걸러내지 못해 로그인 유저가 노출·클릭을 부풀릴 수 있다(빈도 제한은 인스턴스 메모리라 다중 인스턴스에서 약하다). (2) `aggregateTodayCardEvents`가 원본 행을 읽어 서버에서 세므로 PostgREST 기본 행 상한(1,000건)에서 조용히 잘릴 수 있다. (3) `followup`은 UI가 보내지 않는데 API는 임의 값을 받아 저장한다(보관 기한 없음).
- 구현 계획: 집계는 DB 쪽 `count`·`group by`(RPC 또는 뷰)로 옮기거나 페이지네이션한다. 서버측 중복 제거는 개인 식별자 미저장 원칙을 지키는 방식(예: 세션 토큰 해시 없이 시간창 제한)을 `/jam-plan`으로 먼저 정한다. `followup`은 사용하지 않는 것으로 정했으니(2026-09-24, 카드 클릭은 GA로 확인) 수신 자체를 끄거나 값을 제한한다.
- 관련 파일: `jam-web/src/lib/today/events.ts` 50·102·159~170행, `jam-web/src/app/api/today/events/route.ts` 30행, `jam-web/src/app/api/admin/today/metrics/route.ts`

## 배경 / 문제 정의

`/jam-ship` 2026-09-24 민지 모드 ② 발견물(보안 주의 1건·참고 3건). 활성 유저 17~19명 규모라 지금은 영향이 작다.

## 완료 조건

### 구현 범위 (게이트 판정 대상)
- 집계가 1,000행을 넘어도 정확하다(테스트로 확인).
- 이벤트 API가 반복 삽입에 대해 서버에서 방어한다(방식은 사전 기획 결과).
- `followup` 수신 정책이 정해져 반영된다.

크기 상한: 4파일/100줄(분할 가능).
