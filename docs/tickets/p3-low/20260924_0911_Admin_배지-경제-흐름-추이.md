# [Admin] 어드민 메인에 최근 배지 발급량과 앰비언트 드랍 추이를 그래프 두 개로 표시한다

## 핵심 요약

- 요구사항: 어드민 메인 주간 캘린더 아래에 최근 7일 또는 30일(기본 30일)의 **일별 배지 발급량**과 **일별 앰비언트 드랍량**을 CSS 막대 그래프 **두 개**로 표시한다. 두 그래프는 눈금을 따로 쓴다(값 크기가 다르기 때문, 아래 배경). 7일·30일 전환은 `?trend=7|30`이다.
- 구현 계획: 아래 「구현 계획」 1~5를 따른다.
- 관련 파일:
  - `jam-web/src/lib/admin/kpiWeekly.ts` (배지 발급량 정의 참고: `user_activity_badges.earned_at`, 102줄 부근 조회)
  - `jam-web/supabase/migrations/` 중 `mint_and_place_ambient_drop`을 만든 파일(앰비언트 드랍이 `poi_drops`에 `source = 'system'`으로 기록됨), `104_ambient_drop_reintroduce.sql`·`137_ambient_drop_schedule_hour.sql`(설정 구조 참고)
  - `jam-web/src/lib/admin/today-calendar.ts` `todayKstDateString` (14줄), `shiftDateStr` (53줄), `kstDayBoundsIso` (45줄)
  - `jam-web/src/app/admin/page.tsx` (`searchParams` 처리, 캘린더 아래 배치 구간)
  - 신규: `jam-web/src/lib/admin/economyTrend.ts`, `jam-web/src/app/admin/EconomyTrend.tsx`
  - `docs/specs/prd/admin-ui/ADMIN_PRD.md` §5-7

## 배경 / 문제 정의

배지 발급이 갑자기 늘거나 줄었는지(포인트 인플레, 드랍 정지)를 추이로 확인할 수단이 없다.

2026-09-24 읽기 전용 조회로 확인한 사실(계획의 근거):
- **앰비언트 드랍의 기록 위치**: `poi_drops` 테이블이다. `mint_and_place_ambient_drop` 함수가 `source = 'system'`으로 넣고, 유저 드랍(`create_user_drop`)은 `source = 'user'`로 넣는다. 함수 정의에서 확인했다. `source` 값은 `system` 1,055건과 `user` 27건뿐이다. `poi_drops.dropped_at`이 발생 시각이다.
- **배지 발급량의 정의**: `user_activity_badges.earned_at`(최초 발급 시각 고정)이다. 주간 KPI(`kpiWeekly.ts`)와 같은 정의를 쓴다.
- **값의 크기가 크게 다르다**: 2026-08-26~09-24 일별 값에서 배지 발급은 0~14건이고 앰비언트 드랍은 0~500건이다(9/9 500건, 9/21 164건, 9/23 33건, 9/24 13건, 나머지 날은 대부분 0~95건). 한 눈금에 그리면 배지 발급이 바닥에 붙어 보이지 않는다.
- 기준 값(과거 날짜라 바뀌지 않음, KST): 2026-09-21 배지 5·앰비언트 드랍 164, 2026-09-09 배지 14·앰비언트 드랍 500, 2026-09-13 배지 14·앰비언트 드랍 0.

## 상세 요구사항

### 서비스/코드베이스 관점
- 날짜 묶음은 KST 달력 날짜 기준이다(`todayKstDateString`). 오늘 칸은 진행 중인 값이며 표시에 "오늘"을 붙인다.
- 조회는 필요한 컬럼(시각 컬럼 하나)만 읽고, 범위 시작~끝으로 좁혀 1,000행씩 페이지를 넘겨 읽는다(`.order('id')` + `.range()`가 없는 테이블은 시각 컬럼과 기본 키로 정렬). 30일 범위로 한 번씩만 읽고 7일 보기는 그 결과에서 잘라 쓴다.
- 두 그래프는 각자 최댓값으로 눈금을 잡는다. 값이 모두 0이면 막대 없이 "기간 내 없음"을 표시한다. 막대마다 날짜와 값을 마우스를 올렸을 때(`title`)와 스크린 리더용 텍스트로 제공한다.
- 그래프 라이브러리를 새로 들이지 않고 CSS 막대로 그린다.
- 배지 발급 조회와 앰비언트 드랍 조회는 서로 독립적으로 실패한다(한쪽 그래프만 오류 카드로 바뀌고 다른 쪽과 나머지 영역은 그대로).
- 조회만 하며 경제 수치는 바꾸지 않는다. DB 변경은 없다.
- 어드민 유형이므로 MODULAR를 적용하지 않는다.
- 실렌더는 격리 워크트리에서 시도하지 않는다(티켓 20260924_1016). 머지 뒤 카리나가 확인한다.

### 주요 의사결정 / 핵심 메모
- 그래프를 두 개로 나누고 눈금을 따로 둔 이유: 2026-08-26~09-24 일별 값에서 배지 발급은 0~14건, 앰비언트 드랍은 0~500건이라 한 눈금에 그리면 배지 발급이 바닥에 붙어 보이지 않는다.
- 앰비언트 드랍의 기록 위치 확인 과정: 처음에는 `poi_drops.source`가 `'ambient'`일 것으로 짐작해 조회했으나 0건이 나왔다. `source` 값은 `system`(1,055건)과 `user`(27건)뿐이었고, `mint_and_place_ambient_drop`이 `'system'`으로, `create_user_drop`이 `'user'`로 넣는 것을 함수 정의에서 확인해 티켓 계획에 반영했다. 다른 함수가 `system`으로 기록하는지는 확인한 함수 두 개 밖에서는 조사하지 않았다.
- 티켓을 갱신한 직후에 파이프라인을 돌렸기 때문에 처리 규칙표(티켓 0908에서 추가한 규칙)대로 아현·민지에게 티켓을 원격에서 직접 읽도록 지시했다. 이번에는 낡은 티켓 문구로 인한 오판정이 없었다.
- 머지 전 검사는 오염 검사 종료 코드 0, 겹치는 파일과 충돌 없음이었다.

### 잔여 이슈
- 조회 함수가 30일치 시각을 전부 읽어 서버에서 센다(민지 참고 사항). 앰비언트 드랍이 하루 500건까지 나온 적이 있어 데이터가 크게 늘면 읽는 페이지 수가 늘어난다. 지금 30일치는 앰비언트 드랍 약 1천여 건이라 문제없다. 커지면 DB에서 날짜별로 집계하는 방식으로 바꾸는 변경(DB 함수 추가)이 필요하며, 그 시점에 티켓으로 분리한다.
- 반복 획득(`earn_count` 증가)은 "발급"이 아니라 이 그래프에 포함되지 않는다(주간 KPI와 같은 정의).
