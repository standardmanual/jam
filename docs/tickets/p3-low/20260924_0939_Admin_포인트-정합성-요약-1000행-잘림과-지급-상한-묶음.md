# [Admin] 포인트 관리의 잠재 정합성 문제 묶음 — 요약 1,000행 잘림, 유저 삭제 뒤 발행량 불일치, 지급 금액 상한 없음

## 핵심 요약

- 요구사항: 오픈 후 거래가 쌓이면 드러날 포인트 관리 문제 세 가지를 정리한다.
- 구현 계획: (1)은 바로 고칠 수 있다. (2)·(3)은 정책 결정이 먼저 필요하다.
- 관련 파일: `jam-web/src/lib/points/summary.ts:55-59`, `jam-web/src/app/api/admin/users/[id]/route.ts`(유저 삭제),
  `jam-web/src/app/api/admin/points/grant/route.ts:30-53`(지급 입력 검증)

## 배경 / 문제 정의

상위 티켓 20260924_0916의 파일 지도 작성 중에 발견했다(2026-09-24). 현재 운영 DB의 거래는 3건, 지갑은 1개라
아직 드러나지 않았다.

1. **요약이 1,000행에서 잘린다.** `getPointsSummary()`는 지갑과 거래를 한 번에 읽는다(거래는 `.limit(50000)`).
   그러나 API 응답은 1,000행에서 잘리므로, 거래가 1,000건을 넘으면 합계가 틀어져 정합성 경고가 잘못 뜬다. 합계는
   DB 집계로 구해야 한다.
2. **유저를 삭제하면 발행량과 유통량이 어긋난다.** 유저를 삭제하면 지갑과 거래가 CASCADE로 함께 지워지지만,
   발행 합계(`point_treasury`)는 그대로 남는다. 대안은 삭제 전에 잔액을 회수 거래로 기록하는 것이다(스키마 변경
   없음). 채택 여부를 정해야 한다. 상위 티켓의 유저 일괄 삭제가 들어가면 더 자주 일어난다.
3. **어드민 지급 금액에 상한이 없다.** 단건 검증은 "0이 아닌 정수"뿐이다(1,000P 이상은 확인 체크만 요구).
   상위 티켓의 포인트 일괄 지급은 금액 × 대상 수만큼 커지므로 상한을 정할지 결정해야 한다.

## 완료 조건

- (1) 거래 1,001건 이상을 가정한 단위 테스트에서 요약의 합계가 DB 집계와 같다.
- (2)·(3) 결정이 `docs/service/prd/`의 포인트 관련 문서에 적혀 있고, 채택한 방식이 구현돼 있다.
