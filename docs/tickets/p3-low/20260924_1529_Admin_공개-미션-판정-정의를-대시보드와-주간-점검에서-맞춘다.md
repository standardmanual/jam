# [Admin] 공개 미션 판정 정의를 대시보드 「미션 공백」 카드와 주간 점검 스크립트에서 맞춘다

> **연결 메모 (2026-09-30 티켓 20260930_1451 사용자 결정):** 20260930_1502(운영툴 운영 홈·일정표·신호)가 같은 화면을 넓히므로 착수 때 함께 판단한다.

## 핵심 요약

- 요구사항: 같은 "공개 미션"을 두 곳이 다르게 판정한다. 같은 입력에서 같은 공개 미션 집합을 돌려주도록 정의를 맞추고, 정의의 원천을 한 곳으로 정한다.
- 구현 계획: 아래 「구현 계획」의 대안 중 하나를 정한 뒤 진행한다. 추천은 대안 A다.
- 관련 파일:
  - `jam-web/src/lib/admin/contentGaps.ts` `isPublicMission`, `checkMissionGaps` (티켓 20260924_0912)
  - `scripts/public-mission-check.mjs` `isPublic`, `isExposed`, `isNotEnded`, `computePublicMissionCheck` (티켓 20260924_1502)
  - `jam-web/src/lib/missions/visibility.ts` `isMissionExposed` (345줄, 실제 노출 규칙)
  - `docs/specs/SERVICE_OPERATIONS.md` §9-5 공개 미션 운영 원칙 (정의·공백 금지)

## 배경 / 문제 정의

2026-09-24 티켓 0912를 머지하기 직전에 병렬 세션이 티켓 1502(주간 점검용 공개 미션 점검)를 머지해서, 같은 개념이 두 곳에 있는 것을 발견했다.

| 항목 | 대시보드 「미션 공백」(`contentGaps.ts`) | 주간 점검(`scripts/public-mission-check.mjs`) |
|---|---|---|
| 공개 미션 정의 | `gate_axis`와 `visibility_rule_json`이 없음 | 위 두 조건에 `gated_badge_id`도 없음 |
| 노출 판정 | `starts_at`이 지났는가 | `exposure_mode`(`hidden`은 제외, `scheduled`는 `exposure_at`)를 반영. `isMissionExposed`와 같은 규칙이라고 주석에 적혀 있음 |
| 종료 판정 | 종료일(KST 달력 날짜)까지 포함 | `ends_at`이 지금보다 뒤 |
| 산출 | 날짜별 공백·상시 미션 유무·종료 14일 전 후속 유무 | 참가 가능 건수·상시 공개 미션 보상 배지 유효성 |

2026-09-24 실측(읽기 전용 조회)에서는 두 판정이 **같은 결과**를 낸다: `gate_axis`가 없으면서 `gated_badge_id`가 있는 옛 게이트 미션 0건, `exposure_mode`가 기본값(`start_date`)이 아닌 미션 0건, 공개 미션 2개(상시 입문 미션, 10/1~10/31 기간 미션). 그런 미션이 생기면 두 곳이 서로 다른 말을 하게 된다(대시보드는 경고를 안 하는데 주간 브리핑은 "참가 가능 0건 [주의]"를 내는 식).

## 상세 요구사항

### 서비스/코드베이스 관점
- 두 구현은 실행 환경이 다르다(TypeScript 앱 vs Node 스크립트). 한쪽이 다른 쪽을 import하기 어렵다면, 정의의 원천을 문서 한 곳(`SERVICE_OPERATIONS.md` §9-5)으로 두고 두 구현이 같은 픽스처 표로 검증되게 한다.
- 조회만 하며 DB 변경은 없다. 어드민 유형이라 MODULAR를 적용하지 않는다.

## 구현 계획

- **대안 A (추천)**: 대시보드가 주간 점검과 같은 기준을 따르게 한다. `isPublicMission`에 `gated_badge_id` 조건을 더하고, "노출됨"을 `isMissionExposed`와 같은 규칙(`exposure_mode`, `exposure_at`)으로 판정한다. `SERVICE_OPERATIONS.md` §9-5 「정의」에 `gated_badge_id`와 노출 방식을 함께 적는다. 실제 유저에게 미션이 보이는 규칙(`isMissionExposed`)이 원천이므로 가장 자연스럽다.
- **대안 B**: 주간 점검을 대시보드 기준에 맞춘다. 실제 노출 규칙과 어긋나므로 권하지 않는다.
- **대안 C**: 지금대로 두고 §9-5에 두 구현의 차이를 적는다. 데이터에 차이가 생기는 순간 두 곳이 어긋난다.

## 완료 조건

- 같은 미션 픽스처 표(옛 게이트 미션, `hidden`, 노출 시각이 미래인 `scheduled`, 노출 시각이 지난 `scheduled`, 종료 경계, 일반 공개 미션)를 대시보드 판정과 주간 점검에 넣었을 때 같은 공개 미션 집합을 돌려준다는 테스트가 있다.
- 정의의 원천이 `SERVICE_OPERATIONS.md` §9-5 한 곳이고, 두 구현이 그곳을 참조한다.
- 기존 「미션 공백」 카드의 표시와 주간 점검 출력 형식은 (데이터에 차이가 없는 한) 바뀌지 않는다.
