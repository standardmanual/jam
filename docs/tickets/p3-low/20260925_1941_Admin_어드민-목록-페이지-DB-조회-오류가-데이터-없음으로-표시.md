# [Admin] 어드민 목록 페이지가 DB 조회 오류를 확인하지 않아 오류가 "데이터 없음"으로 보인다

> 티켓 [20260925_1411](../p2-normal/20260925_1411_Admin_에셋제너레이터-홈피드-적용탭-제작경로표시.md)
> 로컬 실렌더에서 실제로 겪은 사고이자 게이트 범위 밖 발견물이다. 같은 계열의 서비스 쪽 티켓은
> [20260924_0901](20260924_0901_Service_노출태그-나머지-조회-7곳의-오류-무시.md)이다(노출 태그 계산의
> 조회 오류 무시, CLOSED).

## 핵심 요약

- 요구사항: 어드민 목록 페이지가 Supabase 조회의 `error`를 받아, DB 오류를 「데이터 없음」과
  구분해서 보여주고 서버 로그에도 남긴다.
- 구현 계획: 먼저 어드민 목록 페이지 전수(4곳 + 그 밖의 목록 페이지)의 오류 처리 현황을 확인하고,
  오류 시 기존 어드민 오류 화면(`admin/error.tsx`, 「다시 시도」 버튼 있음)으로 보내는 방식을 기본으로
  적용한다(아래 「결정 필요」).
- 관련 파일: `jam-web/src/app/admin/today/page.tsx`(47행), `jam-web/src/app/admin/missions/page.tsx`
  (47행), `jam-web/src/app/admin/itembooks/page.tsx`(36행, `fetchItemBookListPage`),
  `jam-web/src/app/admin/badges/page.tsx`(29행, `fetchBadgeListPage`),
  `jam-web/src/app/admin/error.tsx`.

## 배경 / 문제 정의

### 사실 (2026-09-25 확인한 결과)

- **사고 실측**: 1411 로컬 실렌더에서 마이그레이션 190 실행 전에 `/admin/today?date=2026-09-29`를
  열었더니 목록이 「총 0개 · 이 날짜에 노출되는 카드가 없었어요」로 나왔다. 같은 날짜에 노출되는
  카드는 DB에 있었다(읽기 전용 조회로 확인). 원인은 목록 쿼리가 아직 없는 `image_source` 컬럼을
  select해서 실패한 것이다(`42703 column "image_source" does not exist`). 개발서버 터미널 로그에도
  오류는 남지 않았다. 마이그레이션 190 실행 후 같은 URL에서 3건이 정상 표시되었다.
- **코드 현황**: `today`·`missions`·`itembooks`·`badges` 4개 어드민 목록 `page.tsx`에는 `error`
  라는 문자열이 한 번도 나오지 않는다.
  - `today/page.tsx:47`: `const { data: cardsRaw, count } = await query.range(from, to)`
  - `missions/page.tsx:47`: `Promise.all`로 받은 `{ data: missionsRaw, count }`, `{ data: summaryRaw }`
  - `itembooks`·`badges`는 조회를 `fetchItemBookListPage`·`fetchBadgeListPage` 안에서 하며, 그 함수
    안의 오류 처리는 이번에 확인하지 않았다. 두 페이지가 함께 조회하는 `tribes` 등 부가 조회도
    `{ data }`만 받는다.
- 이런 패턴이 어드민의 다른 목록 페이지에도 있는지는 확인하지 않았다.

### 왜 문제인가 (판단)

스키마와 코드가 어긋나는 배포(마이그레이션 전 배포, 컬럼 이름 오타 등)나 일시적 DB 오류가 있으면
어드민은 오류 대신 빈 목록을 보여준다. 운영자는 「카드가 없다」고 받아들이고 로그에도 단서가
없어, 고장을 발견하는 시점이 늦어진다. 1411에서는 마이그레이션을 병합보다 먼저 실행해 피했다.

## 결정 필요

오류를 어떻게 보여줄지 정해야 한다. 추천은 판단이다.

- **A. 오류를 던져 기존 어드민 오류 화면으로 보낸다**(`admin/error.tsx`, 「다시 시도」 버튼 있음).
  변경이 작고 빈 목록과 확실히 구분된다. 부가 조회(`tribes` 등)의 오류까지 화면 전체를 막을지는
  별도로 정한다.
- **B. 목록 영역에만 오류 안내를 보이고 화면 골격은 유지한다.** 운영자 경험은 낫지만 페이지마다
  분기가 늘어난다.
- 카리나 추천: **A**(필수 조회만 던지고, 부가 조회는 로그만 남긴다). 기존 오류 화면을 재사용하고
  변경 범위가 가장 작기 때문이다.

## 결정 기록

- **2026-09-25 사용자가 방침 A(오류를 던져 기존 어드민 오류 화면으로 보낸다)를 결정했다.**
  카리나 추천 그대로 「필수 조회는 던지고, 부가 조회는 로그만 남긴다」로 적용한다.

## 구현 계획 (방침 A 확정)

접근: 목록의 **필수(주) 조회**가 오류를 돌려주면 `throw`해 `admin/error.tsx`가 받게 하고, **부가
조회**(선택지용 집계·코드 목록 등)는 `console.error`만 남기고 기존 동작을 유지한다. 조회가
성공하면 동작은 그대로이며, 결과가 비어 있으면 여전히 「데이터 없음」이다.

가정(범위 결정, 사용자가 이의를 제기하면 조정):
- **구현 범위는 이 티켓이 이름을 든 4개 목록 페이지**(`today`·`missions`·`itembooks`·`badges`)다.
  나머지 목록 페이지는 「확인 단계」 전수 표에만 기록하고, 고칠 필요가 있으면 분할안으로 제안한다
  (한 티켓에서 16곳을 건드리면 게이트 판정 범위가 커진다).
- `fetchBadgeListPage`의 전량 정렬 경로(`fetchAllRows`)는 이미 「오류를 로그로 남기고 부분 목록으로
  이어간다」고 의도적으로 설계되어 있어 그대로 둔다. 기본 경로(`range` 한 번 조회, 284행 근방)만
  던지도록 바꾼다.

파일 단위 지도(예상 8~9개 파일, 임계값 5개/100줄 초과 확실 → `planOnlyWaiver` 부여):
1. 신규 `jam-web/src/lib/admin/queryError.ts`: `throwOnQueryError(error, label)`. `error`가
   있으면 `console.error`로 라벨과 오류를 남기고 `Error('[admin/{label}] 조회 실패: {message}')`를
   던진다. `logQueryError(error, label)`는 던지지 않고 로그만 남긴다.
2. 신규 `jam-web/src/lib/admin/__tests__/queryError.test.ts`: 오류 없음(통과)·오류 있음(던짐,
   메시지에 라벨 포함)·로그 전용 함수(던지지 않음).
3. `jam-web/src/app/admin/today/page.tsx` 47행: `const { data: cardsRaw, count, error } = ...`
   후 `throwOnQueryError`. `TodayListQuery` 반환 타입에 `error`가 없으면 추가한다.
4. `jam-web/src/app/admin/missions/page.tsx` 47행: 주 조회 `error`는 던지고, 함께 조회하는
   유형 집계(`summaryRaw`)는 로그만 남긴다.
5. `jam-web/src/lib/admin/itembook-list-query.ts` `fetchItemBookListPage` 144행: `error`를 받아
   던진다. `jam-web/src/app/admin/itembooks/page.tsx` 36행의 부가 조회(`tribes`)는 로그만 남긴다.
6. `jam-web/src/lib/admin/badge-list-query.ts` `fetchBadgeListPage` 284행: 기본 경로 `error`를
   받아 던진다. `jam-web/src/app/admin/badges/page.tsx` 29행 근방의 부가 조회
   (`tribes`·`item_books`·`poi_categories`)는 로그만 남긴다.
7. 테스트: `itembook-list-query`·`badge-list-query` 기존 테스트 파일에 「주 조회가 오류를 돌려주면
   던진다」와 「성공하면 기존 결과 그대로」를 추가한다. `today`·`missions` 페이지는 서버
   컴포넌트라 단위 테스트 대신 카리나가 로컬 실렌더로 확인한다(완료 조건의 재현 경로).

## 완료 조건

### 확인 단계 (담당: 카리나, 시점: 이 티켓 착수 직후)
- 어드민 목록 페이지 전수(위 4곳과 그 밖의 목록 페이지)에서 조회 `error`를 어떻게 다루는지가
  「페이지 · 조회 · 오류 처리 여부」 표로 완료 기록에 남아 있고, 방침 A/B 중 사용자 결정이 적혀 있다.

### 구현 범위 (게이트 판정 대상, 방침 A를 고른 경우의 예)
- 목록의 필수 조회가 실패하면 빈 목록이 아니라 어드민 오류 화면이 보이고 서버 로그에 오류가
  남는다. 재현 경로: 로컬에서 목록 쿼리가 존재하지 않는 컬럼을 select하도록 임시로 바꾼 뒤
  `/admin/today`에 접속(확인 후 원복).
- 조회가 성공하면 기존 동작이 그대로다(빈 결과는 여전히 「데이터 없음」).
- 오류 시 동작이 테스트로 고정되어 있다.
- `scripts/verify.sh` 통과.
