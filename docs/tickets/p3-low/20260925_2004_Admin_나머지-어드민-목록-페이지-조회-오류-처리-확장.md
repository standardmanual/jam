# [Admin] 나머지 어드민 목록 페이지에도 조회 오류 처리를 확장한다

> 티켓 [20260925_1941](20260925_1941_Admin_어드민-목록-페이지-DB-조회-오류가-데이터-없음으로-표시.md)의
> 후속이다. 1941은 이름을 든 4개 페이지(`today`·`missions`·`itembooks`·`badges`)만 고쳤고, 나머지는
> 1941 「완료 기록」의 전수 표를 근거로 이 티켓이 맡는다. **그 표가 이 티켓의 조사 근거이자 단일
> 원천이므로 표를 여기에 옮겨 적지 않는다.**

## 핵심 요약

- 요구사항: 1941에서 만든 `throwOnQueryError`·`logQueryError`(`jam-web/src/lib/admin/queryError.ts`)를
  나머지 어드민 목록 페이지의 조회에도 같은 기준으로 적용한다. 필수(주) 조회 오류는 던져 어드민 오류
  화면으로 보내고, 부가 조회 오류는 로그만 남긴다.
- 구현 계획: 아래 「범위」의 페이지를 성격이 비슷한 묶음으로 나눠 티켓 크기 임계값(5개 파일·100줄)
  안에서 처리한다. 묶음 나누기는 착수 시 정한다.
- 관련 파일: `jam-web/src/lib/admin/queryError.ts`, 아래 「범위」의 각 `page.tsx`와 조회 함수.

## 배경 / 문제 정의

### 사실 (2026-09-25, 1941 전수 조사 결과)

- 목록 조회 페이지 16곳 중 주 조회의 `error`를 확인하지 않는 곳이 12곳이었고, 그중 4곳은 1941에서
  고쳤다. **남은 8곳**: `drop-policy/exclusions`, `item-badges`, `poi/categories`, `poi`, `points`,
  `ranking-modes`, `recipes`, `users/[id]`(배지 획득 히스토리).
- `drop-policy/exclusions`는 `error`를 읽지만 `page > 1`일 때 1쪽으로 되돌리는 리다이렉트에만 쓰고,
  1쪽에서 오류가 나면 던지지도 로그를 남기지도 않아 빈 목록이 그대로 보인다.
- 대시보드(`app/admin/page.tsx`)는 목록이 없지만 상단 통계 4개(배지·POI·컬렉션·유저)가 `count`만 읽고
  `error`는 보지 않아, 오류가 나면 0으로 표시된다. `try/catch`는 supabase-js가 오류를 던지지 않고
  반환하므로 걸리지 않는다.
- 부가 조회(선택지용 집계·이름 조회 등) 중 오류를 확인하지 않는 곳이 다수다. 위치는 1941 완료 기록의
  전수 표에 있다.
- 1941 게이트에서 확인하지 못한 두 곳: `badge-list-query.ts`의 `fetchCheckinCategoryCandidates`
  (161행 근방, 배지 지점 카테고리 필터 경로)와 `itembooks/page.tsx`의 2차 부가 조회(현재 페이지 배지
  이름 조회).
- 이미 오류를 던지거나 로그로 처리하는 곳: `abusing`(던짐), `users`(던짐), `poi/review`(로그만).

### 정정 (기록 오류 방지)

1941 게이트(민지)가 「`missions` 페이지의 `countRowsByKey`가 오류를 확인하지 않는다」고 지적했으나
`jam-web/src/lib/admin/list-counts.ts`의 `countRowsByKey`는 조회 실패 시 `throw`한다(코드로 확인).
이 항목은 이 티켓의 범위가 아니다.

## 범위 (제안)

1. 남은 주 조회 8곳을 던지기로 바꾼다(`exclusions`는 1쪽 오류도 던지도록 리다이렉트 조건과 분리).
2. 대시보드 상단 통계 4개가 오류를 0으로 감추지 않게 한다(오류 표시 방식은 착수 시 정한다).
3. 부가 조회 미확인 곳을 로그만 남기는 방식으로 정리한다.
4. 1941에서 확인하지 못한 두 곳을 확인하고 필요하면 고친다.

## 완료 조건

- 남은 8개 페이지의 주 조회가 실패하면 빈 목록이 아니라 어드민 오류 화면이 보이고 서버 로그에 오류가
  남는다. 성공·빈 결과 동작은 그대로다.
- 대시보드 상단 통계가 조회 실패를 0이 아닌 오류 상태로 구분해 보여준다.
- 부가 조회 오류가 로그로 남는다.
- 변경 동작이 테스트로 고정되어 있다(서버 컴포넌트 페이지는 실렌더 확인으로 갈음할 수 있다).
- `scripts/verify.sh` 통과.
