# [Admin] 나머지 어드민 목록 페이지에도 조회 오류 처리를 확장한다

> 티켓 [20260925_1941](20260925_1941_Admin_어드민-목록-페이지-DB-조회-오류가-데이터-없음으로-표시.md)의
> 후속이다. 1941은 이름을 든 4개 페이지(`today`·`missions`·`itembooks`·`badges`)만 고쳤고, 나머지는
> 1941 「완료 기록」의 전수 표를 근거로 이 티켓이 맡는다. **그 표가 이 티켓의 조사 근거이자 단일
> 원천이므로 표를 여기에 옮겨 적지 않는다.**

## 핵심 요약

- 요구사항: 1941에서 만든 `throwOnQueryError`·`logQueryError`(`jam-web/src/lib/admin/queryError.ts`)를
  나머지 어드민 목록 페이지의 조회에도 같은 기준으로 적용한다. 필수(주) 조회 오류는 던져 어드민 오류
  화면으로 보내고, 부가 조회 오류는 로그만 남긴다.
- 구현 계획: 아래 「범위」의 페이지를 성격이 비슷한 묶음으로 나눠 티켓 크기 임계값(5개 파일·100줄)
  안에서 처리한다. 묶음 나누기는 착수 시 정한다.
- 관련 파일: `jam-web/src/lib/admin/queryError.ts`, 아래 「범위」의 각 `page.tsx`와 조회 함수.

## 배경 / 문제 정의

### 사실 (2026-09-25, 1941 전수 조사 결과)

- 목록 조회 페이지 16곳 중 주 조회의 `error`를 확인하지 않는 곳이 12곳이었고, 그중 4곳은 1941에서
  고쳤다. **남은 8곳**: `drop-policy/exclusions`, `item-badges`, `poi/categories`, `poi`, `points`,
  `ranking-modes`, `recipes`, `users/[id]`(배지 획득 히스토리).
- `drop-policy/exclusions`는 `error`를 읽지만 `page > 1`일 때 1쪽으로 되돌리는 리다이렉트에만 쓰고,
  1쪽에서 오류가 나면 던지지도 로그를 남기지도 않아 빈 목록이 그대로 보인다.
- 대시보드(`app/admin/page.tsx`)는 목록이 없지만 상단 통계 4개(배지·POI·컬렉션·유저)가 `count`만 읽고
  `error`는 보지 않아, 오류가 나면 0으로 표시된다. `try/catch`는 supabase-js가 오류를 던지지 않고
  반환하므로 걸리지 않는다.
- 부가 조회(선택지용 집계·이름 조회 등) 중 오류를 확인하지 않는 곳이 다수다. 위치는 1941 완료 기록의
  전수 표에 있다.
- 1941 게이트에서 확인하지 못한 두 곳: `badge-list-query.ts`의 `fetchCheckinCategoryCandidates`
  (161행 근방, 배지 지점 카테고리 필터 경로)와 `itembooks/page.tsx`의 2차 부가 조회(현재 페이지 배지
  이름 조회).
- 이미 오류를 던지거나 로그로 처리하는 곳: `abusing`(던짐), `users`(던짐), `poi/review`(로그만).

### 정정 (기록 오류 방지)

1941 게이트(민지)가 「`missions` 페이지의 `countRowsByKey`가 오류를 확인하지 않는다」고 지적했으나
`jam-web/src/lib/admin/list-counts.ts`의 `countRowsByKey`는 조회 실패 시 `throw`한다(코드로 확인).
이 항목은 이 티켓의 범위가 아니다.

## 결정 기록 (2026-09-25, 사용자가 범위 결정을 카리나에게 맡기고 진행을 승인했다)

- **한 티켓·한 번의 파이프라인 실행으로 처리한다.** 1941처럼 같은 헬퍼(`throwOnQueryError`·`logQueryError`)를 같은 방식으로
  적용하는 기계적 변경이라 파일 수는 많지만 판단이 새로 필요하지 않다. 파일이 5개를 넘으므로 착수할 때 `planOnlyWaiver`를 부여한다.
  (판단: 묶음을 쪼개면 병합·게이트가 여러 번이 되고 같은 패턴을 반복 검토하게 된다. 게이트 판정이 어려워지면 그때 쪼갠다.)
- **대시보드 통계 4개는 던지지 않는다.** 이 페이지는 출처별 격리 원칙(한 출처가 실패해도 나머지 영역은 그대로 표시)을 따르고 어드민
  첫 화면이라, 통계 한 칸 때문에 화면 전체를 오류 화면으로 바꾸지 않는다. 조회가 실패한 칸은 숫자 대신 「—」와 「불러오지 못했어요」
  안내(`title` 또는 보조 문구)를 보이고 서버 로그를 남긴다. 0건과 구분되는 것이 요점이다.
- **새 헬퍼를 만들지 않는다.** `lib/admin/queryError.ts`의 두 함수를 그대로 쓴다.

## 범위 (확정)

포함:
1. **주 조회 8곳을 `throwOnQueryError`로 던진다.** `drop-policy/exclusions/page.tsx`(배지 탭 :73·컬렉션 탭 :85, 1쪽 오류도 던지도록
   기존 `page > 1` 리다이렉트 조건과 분리), `item-badges/page.tsx`(:53-54), `poi/categories/page.tsx`(:8), `poi/page.tsx`(:39-40),
   `points/page.tsx`(:49), `ranking-modes/page.tsx`(:51-54), `recipes/page.tsx`(:41), `users/[id]/page.tsx`(:44-53, 배지 획득 히스토리).
2. **대시보드 상단 통계 4개**(`app/admin/page.tsx` :286-312, `badgeCount`·`poiCount`·`itemBookCount`·`userCount`가 `?? 0`으로 오류를 0으로
   감춘다): 오류를 `logQueryError`로 남기고 그 칸을 「—」+안내로 표시한다. 오류가 아닌 0은 그대로 0이다.
3. **부가 조회의 오류를 `logQueryError`로 남긴다**(던지지 않는다): exclusions(트라이브·컬렉션 :52-53), item-badges(:55-56),
   poi/categories(POI 수 집계 :17-20), poi(카테고리 :41·검토 대기 :47·연결 배지 이름 :53-54), poi/review(카테고리 :48),
   points(유저명 :54-56, 요약 `lib/points/summary.ts`), ranking-modes(무결성 `lib/ranking/rankingDataSource.ts:317-321`),
   recipes(슬롯 :49·배지 이름 :70), users/[id](유저 단건 :36·믹스 실패 이력 :60-65·배지 이름 :70), users(트라이브 :31).
   줄 번호는 1941 전수 표 기준이며 착수 때 어긋났으면 함수 이름으로 찾는다.
4. **1941에서 확인하지 못한 두 곳을 확인하고, 오류를 확인하지 않으면 로그만 남긴다**: `lib/admin/badge-list-query.ts`의
   `fetchCheckinCategoryCandidates`(161행 근방), `itembooks/page.tsx`의 2차 부가 조회(현재 페이지 배지 이름).

제외(이미 처리됨 또는 의도된 설계): `abusing`·`users`(던짐)·`poi/review` 주 조회(로그만), `missions`의 `countRowsByKey`(코드가
던진다, 위 정정), `badges`의 전량 정렬·지점 카테고리 경로(`fetchAllRows`가 로그 후 부분 목록으로 계속하는 기존 설계, 1941).

## 완료 조건

- 남은 8개 페이지의 주 조회가 실패하면 빈 목록이 아니라 어드민 오류 화면이 보이고 서버 로그에 오류가
  남는다. 성공·빈 결과 동작은 그대로다.
- 대시보드 상단 통계가 조회 실패를 0이 아닌 오류 상태로 구분해 보여준다.
- 부가 조회 오류가 로그로 남는다.
- 변경 동작이 테스트로 고정되어 있다. lib 함수(`lib/points/summary.ts`·`lib/ranking/rankingDataSource.ts` 등)는 단위 테스트로
  고정하고, 서버 컴포넌트 페이지는 아래 후속 범위의 실렌더 확인으로 갈음한다.
- `scripts/verify.sh` 통과.

**후속 범위(카리나, 병합 뒤 push 전, 로컬)**: 1941과 같은 방식으로 페이지별 주 조회 select에 존재하지 않는 컬럼을 로컬 소스에만 임시로
넣어 오류 화면과 서버 로그를 확인하고 즉시 원복한다(DB 무변경). 대시보드는 통계 조회를 실패시켜 「—」 표시를 확인한다. 아현·민지는 하지 않는다.
