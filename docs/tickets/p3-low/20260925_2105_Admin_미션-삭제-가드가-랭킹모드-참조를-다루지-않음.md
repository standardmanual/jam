# [Admin] 어드민 미션 삭제 가드가 랭킹 모드 참조를 다루지 않는다

> 티켓 [20260925_1412](../p2-normal/20260925_1412_Infra_미션-등록묶음-포맷과-등록스크립트.md)
> 게이트(민지)의 범위 밖 발견물이다.

## 핵심 요약

- 요구사항: 미션을 삭제할 때 그 미션을 대상으로 삼는 랭킹 모드가 있으면 운영자가 알 수 있게 한다.
- 구현 계획: 먼저 「결정 필요」를 정한 뒤 `MISSION_REFERENCE_SOURCES`에 랭킹 모드 항목을 추가하고 테스트로
  고정한다.
- 관련 파일: `jam-web/src/lib/admin/reference-guards.ts`(`MISSION_REFERENCE_SOURCES` 135행 근방,
  `collectMissionReferences` 168행 근방), 사용처 `jam-web/src/app/api/admin/missions/[id]/route.ts`(DELETE)·
  `jam-web/src/app/api/admin/missions/bulk/route.ts`·`jam-web/src/lib/admin/mission-bulk.ts`,
  `jam-web/scripts/asset-generator/registerMissionFlow.mjs`(되돌림 검사 6곳).

## 배경 / 문제 정의

### 사실 (2026-09-25 코드를 읽어 확인한 결과)

- 어드민 미션 삭제 가드 `MISSION_REFERENCE_SOURCES`는 5곳을 본다: 완료 이력·참여 이력·랭킹 스냅샷·
  포인트 지급 원장(이상 4곳은 삭제를 막는다)과 투데이 카드 연결(막지 않고 안내만 한다).
- `ranking_modes.target_mission_id`는 `missions(id)`를 참조하고 `ON DELETE SET NULL`이다
  (`jam-web/supabase/migrations/158_ranking_modes.sql` 42행). 이 컬럼은 가드 목록에 없다
  (`reference-guards.ts`에서 `ranking_modes`·`target_mission_id`를 검색해 0건).
- 미션 등록 스크립트(티켓 1412)의 되돌림은 미션을 참조하는 6곳을 모두 검사해 하나라도 데이터가
  있으면 중단한다. 6곳은 생성 타입의 `referencedRelation: "missions"` 외래 키와 일치함을 민지가 확인했다.
  따라서 스크립트의 되돌림 검사와 어드민 삭제 가드가 다루는 범위가 다르다.

### 추론 (코드 읽기로 도출했고 재현하지는 않았다)

- 랭킹 모드가 특정 미션의 참여자를 대상으로 삼는데(`target_type='mission_participants'`, 158
  마이그레이션 주석) 그 미션을 어드민에서 삭제하면 `target_mission_id`가 조용히 NULL이 되고, 삭제
  화면은 이를 알려 주지 않는다. 그 뒤 해당 랭킹 모드가 어떻게 동작하는지는 확인하지 않았다.

## 결정 필요

- **A. 가드 목록에 랭킹 모드를 추가하되 안내만 한다**(투데이 카드 연결과 같은 `blocks: false`).
  삭제는 막지 않지만 운영자가 「이 미션을 대상으로 한 랭킹 모드 N건이 대상 없음이 된다」를 본다.
- **B. 삭제를 막는다**(`blocks: true`). 랭킹 모드가 대상 없는 상태가 되는 것을 원천 차단하지만
  운영자가 먼저 랭킹 모드를 정리해야 한다.
- 카리나 추천: **A**. SET NULL이라 데이터 손상은 없고, 삭제 자체를 막는 것은 과하다. 다만 삭제 뒤 랭킹
  모드 동작을 확인한 결과 화면이 깨진다면 B가 맞다(착수 시 확인).

## 결정 기록

- **2026-09-25 사용자가 방침 A(가드 목록에 랭킹 모드를 추가하되 안내만 한다, `blocks: false`)를 결정했다.**

## 계획 정정 (2026-09-25, 아현 확인 결과)

처음 계획(2~3개 파일)은 사용처를 읽기 전에 쓴 것이라 틀렸다. 아현이 코드를 읽고 확인한 사실: **삭제를 막지 않는 참조(`blocks: false`)는 가드 목록에 넣어도 운영자에게 보이지 않는다.**
`hitLabels`는 삭제가 막힐 때(`blockingTotal > 0`)만 화면에 나간다. 단건 삭제(`missions/[id]/route.ts` 148~156행)는 막는 참조가 없으면 삭제 후 `{ ok: true }`만 돌려주고(호출 화면은
`GateMissionManager.tsx` 57행 하나뿐, 응답 본문을 읽지 않는다), 일괄 삭제(`mission-bulk.ts` `classifyMissionDeletion` 153~160행)는 안내만 하는 참조를 표시하지 않으며 삭제 확인창
(`MissionTable.tsx` 363~369행)은 건너뛴 건수만 보여 준다. 기존 `today_cards`(`blocks: false`) 안내도 같은 이유로 지금 보이지 않는다(같은 방식으로 함께 해결된다).

**사용자가 (가) 6개 파일로 진행하기로 결정했다(2026-09-25).** 방침 A와 완료 조건(「단건·일괄 모두 운영자에게 보인다」)을 그대로 지키는 안이다.

## 구현 계획 (방침 A 확정, 6개 파일 · 60~80줄 — `planOnlyWaiver` 부여)

접근: 랭킹 모드를 삭제를 막지 않는 안내 항목으로 추가하고, 막지 않는 참조를 운영자에게 실제로 보여 주는 표시를 단건·일괄 삭제에 더한다. `ON DELETE SET NULL`(마이그레이션 158)이라 삭제는 성공한다.
단건은 삭제 전 미리보기 경로가 없어 **삭제 직후** 안내한다.

1. `jam-web/src/lib/admin/reference-guards.ts`: `MISSION_REFERENCE_SOURCES`(135행 근방) `today_cards` 뒤에 `{ key: 'ranking_modes', label: '랭킹 모드 연결', location: 'ranking_modes.target_mission_id', blocks: false }`
   추가, `collectMissionReferences`(168행 근방)에 `fetchAllRows` 조회·`errors.push`·`tally` 추가(fail-closed는 그대로), 파일 머리 「FK 규칙 실측」에 SET NULL(마이그레이션 158) 한 줄,
   막지 않는 참조 문구만 뽑는 작은 함수(예: 요약의 `noticeLabels`)를 더한다.
2. `jam-web/src/lib/admin/__tests__/mission-reference-guards.test.ts`(신규, `tribe-reference-guards.test.ts`의 스텁 패턴): 랭킹 모드 참조는 `total`에 잡히지만 `blockingTotal`은 늘지 않는다, 안내 문구에
   「랭킹 모드 연결」이 나온다, 조회가 실패하면 `error`가 채워진다, 참조가 없으면 기존 결과 그대로다.
3. `jam-web/src/app/api/admin/missions/[id]/route.ts`(DELETE): 삭제 성공 응답에 안내 문구 `notice`를 추가한다(막지 않는 참조가 있을 때만, 없으면 기존 응답 그대로).
4. `jam-web/src/app/admin/gate-missions/GateMissionManager.tsx`(57행 근방): 성공 응답의 `notice`를 토스트로 보여 준다(기존 토스트 컴포넌트가 있으면 그것을 쓴다).
5. `jam-web/src/app/api/admin/missions/bulk/route.ts`(삭제 dry-run 응답의 `impact`, 89행 근방): 대상 미션들의 랭킹 모드 연결 건수를 더한다. 실행 응답과 기존 필드는 그대로 둔다.
6. `jam-web/src/app/admin/missions/MissionTable.tsx`(삭제 확인창, `impactOf`의 delete 분기 363~369행 근방): 랭킹 모드 연결이 있으면 확인창에 표시한다.

**화면에 보이는 문구는 `docs/specs/UX_WRITING_GUIDELINE.md`를 먼저 확인하고 정한다**(해요체, 고정 용어). 문구 후보: 토스트 「삭제했어요. 이 미션을 대상으로 한 랭킹 모드 {N}건은 대상이 비워졌어요.」, 확인창
「랭킹 모드 {N}건의 대상이 비워져요.」. 최종 문구와 근거를 완료 기록 보고에 적는다.

## 완료 조건

- 결정한 방침이 완료 기록에 남아 있다.
- 랭킹 모드가 참조하는 미션을 삭제하려 할 때(단건·일괄 모두) 그 사실이 운영자에게 보인다(방침 B면
  삭제가 막힌다). 테스트로 고정되어 있다.
- 참조하지 않는 미션의 기존 삭제 동작은 그대로다.
- `scripts/verify.sh` 통과.

## 완료 기록

### 구현 내용 요약
- 사용자가 방침 A(랭킹 규칙 연결은 삭제를 막지 않고 안내만 한다)와 (가) 6개 파일 안을 결정했다(2026-09-25).
- `MISSION_REFERENCE_SOURCES`에 `ranking_modes.target_mission_id`를 `blocks: false`로 추가했다. 조회가 실패하면 삭제를 실행하지 않는 규칙은 그대로다. 막지 않는 참조 문구는 `noticeLabels`로 따로 뽑는다.
- 단건 삭제는 삭제가 성공한 응답에 `notice`를 담고 게이트 미션 화면이 토스트로 보여 준다. 일괄 삭제는 dry-run 응답의 `impact.rankingModeLinks`를 확인창에 붙인다. 참조가 없으면 응답과 화면은 기존 그대로다.
- 화면 문구는 어드민 화면이 이미 쓰는 「랭킹 규칙」으로 통일했다(UX Writing 가이드가 같은 개념을 화면마다 다른 단어로 쓰지 말라고 한다). 「랭킹 모드」는 코드·테이블 이름으로만 남는다.
  - 단건 토스트: 「삭제했어요. 연결이 풀린 곳이 있어요 (투데이 카드 연결 N건, 랭킹 규칙 연결 M건).」
  - 일괄 확인창: 기존 문장 뒤에 「랭킹 규칙 N건의 대상이 비워져요.」
- 게이트 1차 FAIL(점검 11 문서 반영)을 카리나가 직접 패치했다. 미션 등록 묶음 정본의 「가드는 `ranking_modes`를 다루지 않는다」를 「4곳 차단, 투데이 카드·랭킹 규칙 연결은 안내 참조」로 고쳤고, 랭킹보드 오브젝트 모델의 「어드민 화면이 경고 표시」를 단건 토스트·일괄 확인창으로 구체화했다.
