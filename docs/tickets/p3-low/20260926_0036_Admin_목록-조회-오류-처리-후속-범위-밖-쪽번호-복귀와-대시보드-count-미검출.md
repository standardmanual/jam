# [Admin] 목록 조회 오류 처리 후속: 범위 밖 쪽 번호가 오류 화면이 되는 문제와 대시보드 통계 오류 미검출

> 티켓 [20260925_2004](20260925_2004_Admin_나머지-어드민-목록-페이지-조회-오류-처리-확장.md)의 게이트(민지)와
> 카리나 실렌더에서 발견한 두 가지다. 2004는 주 조회를 던지도록 바꿔 「오류를 빈 목록으로 감추지 않는다」는 목적을 달성했지만,
> 그 부작용과 한계가 확인됐다.

## 핵심 요약

- 요구사항: (1) 범위를 벗어난 쪽 번호가 빈 목록이 아니라 500 오류 화면이 되는 회귀를 막는다. (2) 대시보드 통계가 조회
  실패의 일부(없는 테이블)를 0으로 계속 감추는 것과, 실패 로그의 원인 문구가 비는 것을 고친다.
- 구현 계획: 「결정 필요」를 정한 뒤 처리한다.
- 관련 파일: `jam-web/src/app/admin/{item-badges,poi,points,ranking-modes,recipes,users/[id],badges,itembooks,today,missions}/page.tsx`
  (또는 `lib/admin/{badge,itembook}-list-query.ts`), `jam-web/src/app/admin/drop-policy/exclusions/page.tsx`(이미 처리한 참고 구현),
  `jam-web/src/app/admin/page.tsx`(통계 :286-312), `jam-web/src/lib/admin/queryError.ts`, `jam-web/src/lib/admin/pagination*`(쪽 계산 함수 위치는 착수 때 확인).

## 배경 / 문제 정의

### 사실 (2026-09-26 로컬 실렌더로 확인한 결과)

- **범위 밖 쪽 번호**: 2004 병합 코드에서 `?page=999`를 붙이면 `item-badges`·`poi`·`points`·`ranking-modes`·`recipes`·`users/[id]`가
  HTTP 500과 서버 로그 `[admin/…] 조회 실패: Requested range not satisfiable`을 낸다(PostgREST가 offset이 행 수를 넘으면 416을 돌려준다).
  이전에는 빈 목록이었다. `drop-policy/exclusions`는 1쪽으로 리다이렉트(HTTP 307)하는 기존 처리가 있어 500이 아니다.
  1941에서 고친 `badges`·`itembooks`(그리고 `today`·`missions`)도 같은 구조다(이 4곳을 이번에 실렌더로 확인하지는 않았다).
- **정상 사용 중에도 만날 수 있는지**: 공용 목록 부품은 필터를 바꾸면 `page`를 지운다(`use-list-params.ts:103`). 그러나 마지막 쪽의
  항목을 모두 지운 뒤 목록이 새로고침될 때처럼 쪽 수가 줄어드는 상황에서는 URL의 옛 쪽 번호가 남을 수 있다(이 상황은 재현하지 않았다).
- **대시보드 통계 오류 미검출**: 통계 4개는 `head: true` 카운트 조회다. 없는 **컬럼** 필터는 `error`가 채워져(상태 400) 2004가 「—」로 표시하고
  로그를 남긴다(실렌더 확인). 그러나 없는 **테이블**은 `error`가 null이고 `count`만 null(상태 204)이라 2004 코드가 잡지 못해 0으로 표시된다
  (`supabase-js` 직접 호출로 확인). 또 HEAD 요청은 응답 본문이 없어 `error.message`가 빈 문자열이라 서버 로그가
  `조회 오류: { message: '' }`로만 남아 원인을 알 수 없다.

### 왜 문제인가 (판단)

(1) 오류 화면의 「다시 시도」는 같은 URL을 다시 열어 계속 실패하고, 운영자가 사이드바로 벗어나야 한다. 새 오류를 못 감추게 한 대가로 생긴 불편이다.
(2) 없는 테이블은 배포·마이그레이션 사고 때 나올 수 있는 상황이라 0으로 표시되면 1941·2004가 막으려던 「고장이 데이터 없음으로 보이는 일」이 남는다.

## 결정 필요

- **(1) 범위 밖 쪽 번호 처리**
  - A. `exclusions`와 같이 1쪽(또는 마지막 유효 쪽)으로 리다이렉트한다. 카리나 추천이다(판단). 공용 함수로 만들면 14개 안팎의 페이지가 한 줄씩 쓴다.
  - B. 지금 상태(오류 화면)를 유지한다. 손으로 입력한 큰 쪽 번호에만 해당하고 변경이 없다.
- **(2) 대시보드 통계**: `count == null`도 실패로 취급하고, 로그에 상태 코드를 함께 남긴다. 추천이다. 변경이 통계 4줄과 로그 문구 정도다.

## 완료 조건

- (1)을 A로 정하면 위 페이지에서 `?page=999`가 오류 화면이 아니라 유효한 쪽으로 이동한다(로컬 실렌더로 확인). 성공·빈 결과 동작은 그대로다.
- (2)를 정하면 없는 테이블·컬럼 두 경우 모두 통계 칸이 「—」로 나오고 로그에 원인을 알 수 있는 문구가 남는다(임시 주입 실렌더로 확인).
- `scripts/verify.sh` 통과.
