# [API] 프리셋 라우트: 스토리지 경로 값 검증, 업로드 순서, 무권한·경계 테스트를 보강한다

> 2026-09-26 프로덕션 배포 전 점검의 발견물이다(민지 모드 ②의 주의, 모드 ③의 주의 두 건을 묶었다). 관리자 전용 라우트라 외부 공격 경로는 아니다.

## 핵심 요약

- 요구사항: (1) 프리셋 저장·삭제가 스토리지 경로에 형식 검증 없는 값을 넣는 것을 막는다. (2) 존재하지 않는 `id`로 덮어쓸 때 404가 나도 파일이 남는 순서를 고친다. (3) 빠진 테스트를 채운다.
- 관련 파일: `jam-web/src/app/api/admin/asset-generator/presets/route.ts`(:93 폼 `id`, :104 레이어 `id`, :124-128 경로 구성과 업로드, :140 존재 확인), `presets/[id]/route.ts`(:38-45 삭제 경로), 테스트 `presets/__tests__/route.test.ts`.

## 배경 / 문제 정의

### 사실 (코드로 확인, 2026-09-26)

- 저장 시 경로는 `asset-generator/presets/${presetId}/${overlayLayer.id}.${ext}`이고 `presetId`는 폼의 `id`(`trim`만)나 `randomUUID()`, `overlayLayer.id`는 JSON 레이어의 값이다. 둘 다 형식 검증이 없다. `upsert: true`이고 업로드(126-128행)가 프리셋 존재 확인(140행)보다 먼저 일어난다. 삭제 라우트도 URL의 `[id]`를 그대로 경로에 넣어 `list`+`remove`한다.
- `..` 같은 경로 조각이 `images` 버킷의 다른 경로에 닿는지는 Storage의 경로 처리에 달려 있어 확인하지 못했다.
- 테스트 공백: 프리셋 저장(POST)의 무권한 403 테스트가 없다(GET·`[id]`에는 있음). 이름 60자 경계, 잘못된 `stageRatio` 400, `layers` 파싱 실패·비배열 400, 404일 때 파일이 남는지 확인하는 테스트가 없다.

## 결정 필요

- **검증 방식**: `id`·레이어 `id`를 UUID 또는 `[A-Za-z0-9_-]` 형식으로 제한하고 위반이면 400. 카리나 추천이다(판단).
- **업로드 순서**: 존재 확인을 업로드 앞으로 옮긴다.

## 완료 조건

- 형식이 다른 `id`·레이어 `id`는 400이고 스토리지에 아무것도 쓰지 않는다(테스트로 고정).
- 없는 `id`로 덮어쓰면 404이고 스토리지에 파일이 남지 않는다.
- POST 무권한 403 등 위 빠진 테스트가 추가되어 있다. 기존 응답 모양은 그대로다. `scripts/verify.sh` 통과.
