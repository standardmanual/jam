# [Admin] 유저 제재 필터를 재설계한다 (제재 행이 수백 건에 가까워지면 착수)

> 2026-09-26 티켓 20260926_1345 게이트(민지)의 [참고/정합성] 발견물이다.

## 핵심 요약

- 요구사항: `fetchActiveBanUserIds`는 이제 제재 행이 1,000건에 닿으면 오류를 던진다(조용한 잘림 대신). 그러나 한도 근처에 다가가기 전에 알려 주는 장치가 없고, 제재 id를 `.in('id', ids)`·`.not('id','in', ...)`에 통째로 넣는 필터 구조는 수백 건에서 요청 주소 길이 한계가 먼저 온다. 제재 행이 수백 건에 가까워지면 필터를 DB 쪽에서 판정하는 구조(예: `users` 조회에 `user_shadow_bans` 관계를 `!inner`·조건으로 붙이거나 DB 뷰·함수)로 바꾼다.
- **착수 트리거**: 어드민 유저 조회 화면의 제재 필터가 오류를 내거나, `user_shadow_bans` 행이 300건을 넘을 때(2026-09-26 기준 0건). 트리거 확인은 카즈하 주간 점검에서 행 수를 함께 보면 된다.
- 관련 파일: `jam-web/src/lib/admin/user-list.ts`(`fetchActiveBanUserIds`, `applyUserListFilters`), `jam-web/src/lib/admin/__tests__/user-list.test.ts`.

## 완료 조건

- 제재 행이 수천 건이어도 제재 필터가 정확한 결과를 내고 요청이 실패하지 않는다(테스트). 또는 트리거 전이라 두고 보기로 한 근거를 남기고 닫는다.

### 배포 전 점검에서 추가 확인 (2026-09-26, 프로덕션 배포 `8265beec`, 민지 모드 ③)
- `fetchActiveBanUserIds`가 던지는 오류는 `resolveActiveBanIds`와 `fetchUserListPage`를 거쳐 `admin/users/page.tsx:31`까지 그대로 올라간다. 제재 기록이 1,000건에 닿았을 때 화면이 오류 페이지로 끝나는지, 어드민이 알아볼 안내가 나오는지는 확인하지 못했다(`error.tsx`·`try/catch` 처리는 읽지 않았다). 착수할 때 이 페이지의 오류 표시도 함께 확인한다. [주의]
