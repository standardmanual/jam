# [Admin] 레이어 이미지 로더의 URL·경로 방어와 경계 테스트를 보강한다

> 발견 경위: 티켓 20260927_0119 배포(`/jam-ship`) 전 점검(민지 모드 ②·③)의 범위 밖 발견물이다(참고). 같은 점검에서 나온 「`renderCardPng`의 `--img01` 연결부·캐시 키 테스트」는 티켓 20260927_0124가, 「인자 파서가 값 자리의 다른 인자를 삼키는 문제와 빈 문자열 값」은 티켓 20260927_0129가 이미 다루므로 여기서 다시 만들지 않는다.

## 핵심 요약

- 요구사항: 새 이미지 원본 로더(`loadLayerImage.mjs`)와 CLI 조립부의 남은 발견물을 정리한다. 신뢰 경계가 로컬 CLI 인자와 계획 파일이라 외부 입력이 직접 닿는 경로는 아니며 모두 참고 수준이다.
- 구현 계획: 결정 후 작성한다. 아래 항목별로 「고칠 것」과 「그대로 둘 것」을 정한다.
- 관련 파일: `jam-web/scripts/asset-generator/loadLayerImage.mjs` 30~47줄, `jam-web/scripts/asset-generator/apply-mission-images.mjs` 73~80줄, `jam-web/scripts/asset-generator/applyMissionImagesFlow.mjs`(`items.push`의 `values`), `jam-web/scripts/asset-generator/render.mjs` 82줄

## 배경 / 문제 정의

### 방어(보안 참고)

1. `--img01`과 계획 파일 `values.imgNN`의 http(s) URL을 `fetch`로 받는데 호스트 허용 목록, 사설 IP·loopback 차단, 타임아웃이 없고 리다이렉트를 자동으로 따른다. 크기 상한 5MB는 `arrayBuffer()`로 다 받은 뒤에 검사한다. 에이전트가 프롬프트 인젝션으로 URL을 만들어 내는 경우에만 내부망 요청이나 메모리 소진 가능성이 있다(확신도 보통).
2. `--img01`에 로컬 절대 경로를 주면 경로 제한 없이 읽는다. PNG 시그니처·`<svg` 검사와 5MB 상한으로 임의 파일 유출은 사실상 막혀 있으나, SVG 안의 외부·로컬 `href`를 렌더러(`serverCanvas.ts` `loadImageAsCanvas`)가 따라가는지는 확인하지 못했다(추정, 확신도 낮음).
3. 이미지 값(로컬 경로·URL)이 `resolved.json`의 미션별 `values`에 그대로 기록된다. 로컬 out-dir에만 쓰이고 DB나 프리셋 저장 경로는 없다(위험 낮음).

### 테스트 공백(참고)

4. `createTextOverflowDetector`는 인자가 `{presetId, values}`로 바뀌고 `applyLayerValues(...).layers`를 쓰지만, `runPreview` 테스트는 스텁으로 넣어 실제 구현을 시험하지 않는다.
5. `loadLayerImage`의 두 경계: URL 응답이 5MB를 넘는 경우(`assertSize` 두 번째 호출이 URL 경로에만 걸리는데 시험은 파일 경로만 있다), `<svg`가 4096바이트 뒤에 나오는 경계값.
6. `render.mjs` 표준 출력의 `layers: {applied, saved}` 필드는 진입점 스크립트라 직접 시험하지 않는다(확신도 낮음).

## 상세 요구사항

### 서비스/코드베이스 관점

- 1~3번: 고칠지 그대로 둘지 정한다. 고친다면 최소한 fetch 타임아웃, 응답 크기의 사전 검사(`content-length`와 스트림 상한), 사설 IP·loopback 차단을 검토한다. 그대로 둘 때는 「신뢰 경계는 로컬 CLI 인자」라는 전제를 `loadLayerImage.mjs` 머리 주석에 적는다.
- 4~6번: 테스트를 추가한다.

## 완료 조건

- 1~3번에 대해 「고침」 또는 「전제를 주석으로 남기고 그대로 둠」 중 하나가 정해져 있고 반영됐다.
- 4~6번은 해당 분기를 확인하는 테스트가 있거나, 테스트하지 않는 이유가 티켓에 적혀 있다.
- `scripts/verify.sh`가 통과한다.
