# [Infra] 퀘스트 클라이언트 컴포넌트의 누르기·로딩·실패 흐름을 자동으로 검증할 테스트 환경을 정한다

## 핵심 요약
- 요구사항: 저장소에 jsdom·testing-library가 없어 클라이언트 컴포넌트는 초기 서버 렌더(`renderToStaticMarkup`)만 검증된다. 온보딩 퀘스트 작업에서 같은 공백이 세 번 나왔다 — 믹스 연출 탭 상호작용(`CombineClient.tsx`, 티켓 20260927_2127), 건너뛰기 시트의 전송 중·실패·성공(`OnboardingQuestSkipSheet.tsx`, 20260927_2131), 미리보기 띠 [끝내기]의 로딩·실패·성공(`QuestPreviewBanner.tsx`, 20260928_0138). 테스트 환경을 도입할지(또는 순수 함수 추출로 대체할지) 정하고, 정하면 이 세 컴포넌트부터 적용한다.
- 구현 계획: 도입 비용(의존성·설정·CI 시간)과 대안(상호작용 로직을 순수 함수로 빼기, 브라우저 E2E)을 비교해 결정 → 세 컴포넌트 테스트 추가.
- 관련 파일: `jam-web/src/app/(main)/combine/CombineClient.tsx`, `jam-web/src/app/(main)/OnboardingQuestSkipSheet.tsx`, `jam-web/src/components/QuestPreviewBanner.tsx`, 선례 `jam-web/src/app/(main)/OnboardingSyncButton.test.tsx`(서버 렌더 방식)

## 배경 / 문제 정의
티켓 `20260928_0138`(N5b) 채원 사후 리뷰 제안(「로딩·오류·성공 상태의 통합 테스트 추가 고려」)을 계기로, 같은 원인의 공백을 한 티켓으로 모았다. 기존 테스트 공백 티켓 `20260927_0107`의 (1)도 같은 원인(jsdom 없음)이라 결정 결과를 그 티켓에도 반영한다.

## 완료 조건
- 도입 여부와 방식이 결정돼 있고, 도입하면 세 컴포넌트의 상호작용 테스트가 추가돼 있다.
