# [Infra] v5 시드 생성기 묶음을 `planning/content/`에서 `assets/content-seed/`로 옮긴다

> 발견 경위: 월간 리포트 `jam-doc/operations/reports/monthly/2026-10.md` §6 「수명주기 위반」.
> 사용자가 2026-10-01 채팅에서 해결을 지시했다.

## 핵심 요약

- 요구사항: `jam-doc/planning/content/`에 섞여 있는 v5 시드 생성기 스크립트와 그 입출력 데이터
  16개를 `jam-doc/assets/content-seed/`로 옮긴다. 컨텐츠 문서(`ACTIVITY_BADGES.md`·
  `v5_badge_name_split.md` 등)는 그대로 둔다.
- 구현 계획: 16개를 `git mv`로 한 묶음째 옮기고, 경로 문자열과 살아 있는 참조처를 새 경로로
  고친다. 생성기를 이동 전후로 임시 폴더에서 돌려 산출물이 경로 문자열 외에는 같은지 대조한다.
- 관련 파일:
  - 이동 대상(16개): `v5_catalog_design.json`·`v5_catalog_names.json`·`v5_catalog_verified.json`·
    `v5_catalog_verify.py`·`v5_catalog_writing.json`·`v5_condition_mapping.json`·
    `v5_doc_build.mjs`·`v5_gate_build.py`·`v5_gate_mapping.json`·`v5_mission_axis_groups.json`·
    `v5_mission_badges.json`·`v5_mission_badges_verify.py`·`v5_mission_seed_build.py`·
    `v5_seed_build.py`·`v5_verify_db.py`·`seed_v5_activity_badges.rows.json`
  - 생성기 경로 문자열: `v5_doc_build.mjs`(28·30·200행 안내문, 240행 출력 경로),
    `v5_seed_build.py`(17·754·763행), `v5_mission_seed_build.py`(432행),
    `v5_catalog_verify.py`(7행)·`v5_mission_badges_verify.py`(4행)·`v5_verify_db.py`(27행) 실행 안내
  - 생성 산출물의 머리 주석: `jam-doc/planning/content/ACTIVITY_BADGES.md`(frontmatter `source`,
    서두, 「산출물 색인」), `jam-web/supabase/migrations/seed_v5_activity_badges.sql`(25·34행),
    `jam-web/supabase/migrations/194_missions_condition_text_backfill.sql`(3행)
  - 참조처: `jam-doc/README.md`(폴더 표·경로 표기 규칙 절), `.claude/agents/jam-developer.md`
    규칙 9, `docs/specs/badge-engine/BADGE_ENGINE_UNIFIED.md`(701·764·774·800행),
    `jam-web/src/lib/badgeConditionText.ts`(17행 주석), `jam-web/src/lib/missions/gateMissions.ts`
    (39행 주석), `docs/agents/contract.json`(`paths_exist`·`paths_absent`)
  - 미종료 티켓의 관련 파일 경로: `20260927_0103`, `20260928_1234`

## 배경 / 문제 정의

`jam-doc/planning/content/`는 「덮어쓰기 방식의 현재 상태 문서」 자리다(`CLAUDE.md` 「폴더 =
수명주기」). 그런데 v5 카탈로그를 만들 때 쓴 생성 스크립트 6개와 JSON 데이터 10개가 컨텐츠 문서와
같은 폴더에 섞여 있어, 문서를 찾는 사람과 에이전트가 180KB짜리 JSON까지 문서 후보로 훑게 된다.
월간 리포트가 이를 수명주기 위반으로 짚었다.

이전에 이 스크립트를 코드 쪽으로 옮기려던 티켓 `20260920_0044`는 기각됐다. 기각 근거는 ① 당시
`jam-doc`이 별도 저장소라 이동하면 저장소 경계를 넘는 방향이 늘어난다는 점, ② 세 생성기가 서로의
소스를 자기 위치 기준 상대경로로 `exec`하는 사슬이라는 점이었다. ①은 재통합(티켓
`20260920_1412`)으로 사라졌다. ②는 16개를 한 폴더로 함께 옮기면 상대 관계가 그대로 유지된다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 새 위치는 `jam-doc/assets/content-seed/`다. `planning/content/`와 깊이가 같아, 스크립트가
  작업 폴더 루트를 계산하는 `REPO = HERE/../../..` 식을 고치지 않아도 된다.
- `assets/`는 「생성 산출물, 문서 검색 대상이 아님」 수명주기이고 `doc-check` 범위에서도 빠져
  있다. 생성기와 그 입출력 데이터가 놓이기에 맞는 자리다.
- `v5_doc_build.mjs`는 `ACTIVITY_BADGES.md`를 자기 폴더에 쓰고 있으므로, 출력 경로만
  `jam-doc/planning/content/ACTIVITY_BADGES.md`를 가리키도록 고친다.
- 이미 실행한 번호 마이그레이션 중 사람이 쓴 `138`·`139`의 「정본:」 주석은 작성 당시 기록이므로
  고치지 않는다. `194`는 `v5_mission_seed_build.py`가 다시 만들어 내는 파일이라 생성기와 같이
  머리 주석만 맞춘다(주석 한 줄, DB 영향 없음).
- 종료된 티켓 본문의 옛 경로는 작업 이력이므로 고치지 않는다.

## 구현 계획

1. 이동 전 기준선: 임시 폴더에 현재 구조를 복사해 생성기 6개를 돌리고 산출물을 보관한다.
2. `git mv`로 16개를 옮긴다.
3. 위 「관련 파일」의 경로 문자열·참조처를 고친다.
4. 이동 후 구조를 임시 폴더에 복사해 생성기를 다시 돌리고, 1의 기준선과 비교한다.
5. `docs/agents/contract.json`에 새 경로(`paths_exist`)와 옛 경로(`paths_absent`)를 넣어 되돌아감을
   기계가 잡게 한다.

## 완료 조건

- `jam-doc/planning/content/`에 실행 스크립트(`*.py`·`*.mjs`)와 생성기 JSON이 남아 있지 않다
  (`ls`로 확인).
- 이동 후 생성기 6개(`v5_catalog_verify.py`·`v5_seed_build.py`·`v5_gate_build.py`·
  `v5_mission_seed_build.py`·`v5_mission_badges_verify.py`·`v5_doc_build.mjs`)가 모두 종료 코드
  0으로 끝난다.
- 이동 후 산출물이 이동 전 기준선과 비교해 경로 문자열 외에는 같다(`diff`로 확인).
- `v5_doc_build.mjs`의 출력이 `jam-doc/planning/content/ACTIVITY_BADGES.md`로 간다.
- 티켓·리포트·폐기 폴더를 뺀 살아 있는 문서와 코드에 옛 경로(`jam-doc/planning/content/v5_` 중
  옮긴 파일)가 남지 않는다(`git grep`으로 확인).
- `node scripts/check-contract.mjs`와 커밋 훅(`doc-check` 포함)이 통과한다.

### 주요 의사결정 / 핵심 메모

- **새 위치로 `jam-doc/assets/content-seed/`를 골랐다.** 루트 `scripts/`로 옮기면 깊이가 달라져
  생성기 4개의 루트 계산식을 고쳐야 하고, 사람이 고치는 정본 JSON(`v5_catalog_writing.json` 등)이
  코드 폴더에 섞인다. `assets/`는 깊이가 같아 계산식을 그대로 쓸 수 있고, `doc-check` 범위 밖이라
  대용량 JSON이 문서 검색에 걸리지 않는다.
- **티켓 `20260920_0044`의 기각 근거와 충돌하지 않는다.** 그 티켓은 저장소가 둘이던 시절에 생성기를
  코드 저장소로 옮기는 안을 기각했다. 이번에는 같은 저장소 안에서 묶음째 옮겨 `exec` 사슬의 상대
  관계도 그대로 유지된다.
- **`v5_badge_name_split.md`는 옮기지 않았다.** 생성기 입출력이 아닌 사람이 읽는 기록 문서이고
  `docs/specs/INDEX.md`에 색인돼 있다.
- **이미 실행한 번호 마이그레이션 중 손으로 쓴 `138`·`139`의 「정본:」 주석은 고치지 않았다.**
  작성 당시 기록이기 때문이다. `194`는 생성기가 다시 만드는 파일이라, 재생성했을 때 차이가 나지
  않도록 머리 주석을 생성기와 함께 맞췄다(주석 한 줄, DB 영향 없음).
- **생성 문서는 재생성하지 않고 손으로 고쳤다.** `ACTIVITY_BADGES.md`에는 생성기가 만들지 않는
  frontmatter가 붙어 있어, 재생성하면 지워진다.

### 잔여 이슈
- 생성기 산출물과 저장소 파일 사이에 **이동 전부터 있던** 차이가 있다. 이번 이동과 무관하며 손대지
  않았다. ① `v5_gate_build.py`를 다시 돌리면 `seed_v5_gate_conditions.sql`의 「실행 완료」 머리
  주석이 「작성만 하고 실행하지 않았다」로 바뀌고 레벨형 축 게이트 12건이 추가되며,
  `v5_gate_mapping.json`에도 `레벨형_패치` 항목이 붙는다(티켓 `20260908_1028`의 스크립트 수정이
  산출물에 재생성·커밋되지 않은 상태). ② `v5_doc_build.mjs`를 다시 돌리면
  `ACTIVITY_BADGES.md`의 frontmatter가 사라진다. 누군가 생성기를 다시 돌릴 때 손으로 고친 기록을
  덮어쓸 수 있으므로, 별도 티켓으로 다룰지 사용자 판단이 필요하다.
