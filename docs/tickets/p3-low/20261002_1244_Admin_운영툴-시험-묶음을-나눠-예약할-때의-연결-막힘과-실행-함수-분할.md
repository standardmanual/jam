# [Admin] 운영툴 시험 묶음을 나눠 예약할 때의 연결 막힘과 실행 함수 분할

> 범위 밖 발견물(티켓 20261002_1123 게이트, 민지 `sideFindings`).

## 핵심 요약

- 요구사항 1(정확성): 시험 묶음(`is_sample`)에서 예약된 항목의 `created_resource`는 `{ "sample": true }`라 자원 키가 없다. 같은 시험 묶음에서 나중에 승인한 연결 항목은 사전 점검이
  「대상 자원 ID를 읽을 수 없음」으로 막는다. 시험 묶음을 두 번에 나눠 예약하는 흐름이 막힌다. 시험 묶음에서는 이미 처리된 대상의 자원 ID를 요구하지 않는 쪽으로 정한다.
- 요구사항 2(가독성): `executeBundle`이 입력 검사·사전 점검·선점·그룹 실행·실패로 닫기·결정 기록을 한 함수(약 130줄)에서 처리한다. 단계별 함수로 나눈다. 동작은 바꾸지 않는다.
- 관련 파일: `jam-web/src/lib/admin/opsInbox/execute/precheck.ts` 148–153행(`hasCreatedResourceId`)·222–226행(`targetResourceMissing` 판정), `execute/run.ts` 344행(`{ sample: true }` 기록)·
  390행부터(`executeBundle`). 줄 번호는 2026-10-02 머지 5cf404c 기준이다.
- 착수 시점: 1500 ④(카드 핸들러)에서 해석 2 수정으로 `executeBundle`을 손대므로, 분할은 ④가 머지된 뒤에 한다.
- 함께 고칠 것(④-a 게이트 범위 밖 발견물, 2026-10-02): `run.ts` 머리 주석 10행 「하나도 차지하지 못하면 409라 …」는 낡은 문장이다. 지금 규칙은 13–14행(예약한 항목도 실패로 닫은 항목도 없을 때만 409)이다.
  ④-a(머지 ceb8d4d)가 실행 흐름을 바꿨으므로 위 줄 번호는 착수 때 다시 확인한다.

## 완료 조건

- 시험 묶음에서 연결 대상을 먼저 예약하고 그 대상을 가리키는 항목을 나중에 따로 예약해도, 사전 점검이 뒤 항목을 막지 않는다(테스트).
- 실제 묶음의 「대상 자원 ID를 읽을 수 없음」 판정은 그대로다(기존 테스트 무수정 통과).
- `executeBundle` 분할 뒤 `execute/__tests__/run.test.ts`·`route.test.ts`가 고치지 않고 통과한다.
