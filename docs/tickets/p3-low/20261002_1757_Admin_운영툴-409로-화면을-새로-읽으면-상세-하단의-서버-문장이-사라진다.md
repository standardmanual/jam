# [Admin] 운영툴: 409로 화면을 새로 읽으면 상세 하단의 서버 문장이 사라진다

> 범위 밖 발견물(2026-10-02 민지, 티켓 20261002_1649 ⑤-b 게이트 리뷰). 신호 **참고**.

## 핵심 요약

- 요구사항: 상세 하단(`detailFooter`)의 확인창이나 결정 버튼이 409를 받으면 서버 문장을 보이고 `router.refresh()`로 화면을 새로 읽는다. 새로 읽은 항목의 상태가 바뀌어 있으면
  (예: 「예약됨」이 아니게 됨) 하단 컴포넌트가 바뀌거나 사라지면서 서버 문장도 함께 사라진다. 운영자가 왜 실패했는지 읽지 못할 수 있다. 문장이 화면을 새로 읽은 뒤에도 남게 한다
  (예: 토스트로 한 번 더 띄우거나, 상위 `OpsDecisionWorkspace`가 마지막 충돌 문장을 들고 있다가 보인다).
- 관련 파일: `jam-web/src/components/admin/ops/OpsCancelItem.tsx`(`OpsCancelItem` 145행~, 미리 보기·취소 실패 처리 167–168·188–189행의 `onConflict()`),
  `OpsDecisionWorkspace.tsx`(`detailFooter` 분기 234–252행, `refresh` 91행), `OpsItemActions.tsx`(상태별 일찍 return 144–146행, 승인 화면도 같은 방식).
  공용 문장은 `decisionClient.ts`의 `decisionFailureMessage`(「화면을 새로 불러왔어요」).

## 배경 / 문제 정의

- ⑤-b는 409에서 창 안에 서버 문장을 보이고 화면을 새로 읽는다(1649 「착수 전에 정한 것」 3). 다른 운영자가 먼저 취소하거나 상태 맞추기가 상태를 바꾸면 새로 읽은 항목은
  「예약됨」이 아니므로 `OpsCancelItem` 대신 `OpsItemActions`가 그려지고, 확인창과 그 안의 문장이 함께 사라진다.
- 승인·반려(`OpsItemActions`)도 409 뒤 항목 상태가 바뀌면 같은 일이 생긴다. 위험은 없다(서버가 막고 화면은 최신이다). 운영자가 「왜 안 됐지」를 알 길이 없는 것이 문제다.

## 완료 조건

- 409를 받은 뒤 화면을 새로 읽어 하단 컴포넌트가 바뀌어도 서버 문장이 운영자에게 한 번은 보인다(테스트).
- 승인·반려·공개 전 취소가 같은 방식으로 처리된다.
