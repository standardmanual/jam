# [Service] 유저 드랍 만료 서술을 무기한 대기 동작에 맞춘다

## 핵심 요약
- 요구사항: 유저 드랍을 "30일 만료"로 적은 현재 상태 문서를 실제 동작(만료 없이 픽업될 때까지 대기)에 맞춰 덮어쓴다. 서비스 코드·DB는 바꾸지 않는다.
- 구현 계획: 드랍 생성 경로와 운영 DB를 읽기 전용으로 확인한 뒤, 어긋난 문서 줄만 고친다(`docs` 유형, 카리나 직접 처리).
- 관련 파일: `docs/service/prd/01_PRD.md` 시나리오 3(78행)·기능 표 「드랍/픽업」(106행), `docs/service/prd/04_PROJECT_SPEC.md` 크론 표 `poi-cleanup`(105행), `docs/service/SERVICE_OPERATIONS.md` 크론 API 표(1093행), `docs/service/prd/02_DATA_MODEL.md` `poi_drops.expires_at`(373행), `docs/service/badge-engine/BADGE_ENGINE_UNIFIED.md` §3.5(1630행), `docs/service/prd/notification/PRD.md` 「보류」 표(579행), `docs/plan/vision/02 JAM! 서비스 플랜.md` 페르소나 표(132행)·4.1.2(243행)·8.1(502행)

## 배경 / 문제 정의

`01_PRD.md`는 유저 드랍을 "30일 만료"로 적고 있는데, `BADGE_ENGINE_UNIFIED.md` §3.5와
`02_DATA_MODEL.md`는 유저 드랍에 기한이 없다고 적는다. 정책은 티켓 20260829_2101(마이그레이션
108)에서 무기한 대기로 바뀌었고, 그때 PRD 등 일부 문서가 함께 갱신되지 않았다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 확인한 사실(2026-10-07):
  - `jam-web/src/app/api/drops/route.ts`는 `create_user_drop` RPC에 `p_dropper_id`·`p_poi_id`·`p_inventory_item_id`만 넘긴다.
  - `create_user_drop()`(마이그레이션 108 본문, 181은 `search_path`만 지정)은 `poi_drops`에 `expires_at`을 넣지 않는다.
  - 마이그레이션 108이 `expires_at`의 30일 기본값을 `DROP DEFAULT`했고, 그때 활성 상태이던 유저 드랍의 값을 NULL로 바꿨다.
  - 운영 DB(읽기 전용 조회): `expires_at` 컬럼 기본값 없음. 유저 드랍 41건 중 값이 있는 행은 4건이고, 4건 모두 2026-08-27 이전에 생성됐으며 비활성(`is_available = false`)이다. 2026-08-30 이후 생성된 유저 드랍 36건과 시스템 드랍 1,097건은 모두 NULL이다. 활성 드랍 중 값이 있는 행은 0건이다.
  - `expire_stale_poi_drops()`(크론 `/api/cron/poi-cleanup`)에는 ① `expires_at`이 지난 활성 드랍 ② 삭제된 배지에 연결된 미픽업 활성 드랍, 두 갈래가 있다. ①은 값이 채워진 활성 드랍이 없어 대상이 없다.

## 구현 계획
- 문서 7개의 해당 줄만 덮어쓴다. 변경 이력은 본문에 남기지 않는다.
- `02_DATA_MODEL.md`의 `poi_drops` 표를 `expires_at`의 단일 원천으로 두고, `BADGE_ENGINE_UNIFIED.md`는 그 표를 가리키게 한다.

## 완료 조건
- `docs/specs/`와 `jam-doc/planning/`에서 유저 드랍(POI 드랍)을 30일 만료·소각으로 서술한 줄이 없다. 재현: `grep -rn "30일" docs/specs jam-doc/planning | grep -E "드랍|픽업"`의 결과에 POI 드랍 만료 서술이 없다(아이템 배지 자체의 만료 서술은 대상이 아니다).
- 크론 `poi-cleanup` 설명이 실제 함수의 두 갈래와 일치한다.
- 서비스 코드(`jam-web/`)와 DB는 바뀌지 않는다.

### 구현 내용 요약
- PRD 시나리오 3과 기능 표에서 "30일 만료"를 지우고 "만료 없이 픽업될 때까지 대기"로 바꿨다.
- 크론 `poi-cleanup` 설명(프로젝트 스펙·서비스 운영 스펙)을 "삭제된 배지에 연결된 미픽업 드랍 소각"으로 바꾸고, 만료 분기가 대상을 갖지 않는 이유를 적었다.
- 데이터 모델의 `expires_at` 설명을 이력 서술에서 현재 상태 서술로 바꾸고, 옛 30일 값이 남은 비활성 유저 드랍 행의 존재를 적었다.
- 배지 엔진 문서의 "항상 NULL"을 "채우지 않는다"로 바로잡고 데이터 모델 표를 가리키게 했다(옛 비활성 행 때문에 "항상"은 사실이 아니다).
- 알림 PRD 보류 표의 「드랍 만료 임박/소각」 보류 사유 칸에 만료가 없다는 사실을 채웠다.
- 서비스 플랜: 페르소나 표의 "(30일 후 만료 소각)", 4.1.2의 「앰비언트 드랍 제거(2026-08-25)」 항목(다음 날 재도입돼 현재와 맞지 않음), 8.1의 「드랍 아이템 만료일 규정」 해소 사유를 현재 상태로 바꿨다.

### 주요 의사결정 / 핵심 메모
- 고칠 쪽은 문서다. 코드와 운영 DB가 무기한 대기로 일치하고, 무기한 대기는 티켓 20260829_2101에서 정한 정책이다.
- 옛 30일 값이 남은 비활성 유저 드랍 4건은 그대로 둔다. 비활성이라 크론의 정리 대상이 아니고, `poi_drops.expires_at`을 읽는 화면 코드도 없다(화면이 읽는 만료값은 `inventory_items.expires_at`이다). DB를 바꾸지 않는 작업 범위이기도 하다.
- `docs/agents/contract.json`에 검사 줄은 추가하지 않았다. 이 계약은 에이전트 환경(경로·훅·설정)에 대한 주장을 다루고, 이번 사실은 서비스 데이터의 동작이다.
- 서비스 플랜 4.1.2의 「앰비언트 드랍 제거」 항목은 "(30일 만료)"만 고치면 "앰비언트 드랍이 없다"는 거짓 서술이 남기 때문에 항목 전체를 현재 상태로 바꿨다(앰비언트 드랍은 다음 날 재도입됐다, 티켓 20260826_009).
- 재설계 진행 노트(`09 JAM! 서비스 재설계 진행 노트.md`)는 사용자 답을 기록한 문서라 고치지 않았다. 그 노트 6-8이 인용한 아이템 배지 만료 서술의 정확성은 범위 밖 발견물 20261007_2121에서 다룬다.
