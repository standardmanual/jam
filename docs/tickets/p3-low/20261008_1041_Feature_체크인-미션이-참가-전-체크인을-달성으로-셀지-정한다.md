# [Feature] 체크인 미션이 참가 전 체크인을 달성으로 셀지 정한다

## 핵심 요약
- 요구사항: 지금 `checkin` 미션은 참가 시점과 관계없이 대상 지점 체크인 이력이 하나라도 있으면 달성된다. 그래서 미션에 참가하기 전에 그 지점에 체크인한 사용자는 참가 직후 첫 동기화에서 바로 완료된다. 이 동작을 유지할지, 참가 이후 체크인만 셀지 기획에서 정한다.
- 구현 계획: 결정 전에는 코드를 바꾸지 않는다. 참가 이후만 세기로 정하면 `loadOwnership`의 `checkin` 갈래 조회에 미션별 참가 시각 조건을 더한다(아래 「구현 계획」).
- 관련 파일:
  - `jam-web/src/lib/missions/checker.ts` L127-145(`checkMissions`의 대상 지점 id 수집, `joinedAtByMission` 사용 가능), L421-489(`loadOwnership`의 `user_checkin_badge_earns` 조회)
  - 스펙: `docs/specs/SERVICE_OPERATIONS.md` §9-3 의사코드의 `checkin` 줄, §9-4 표의 `checkin` 행

## 배경 / 문제 정의
2026-10-08 게이트 리뷰(민지)의 범위 밖 발견물이다. 티켓 `20260930_0014`는 「주요 의사결정」에서 판정 의미를 "참가 시점과 무관하게 이력이 있으면 달성"으로 두고, 참가 이후만 셀지는 기획 판단이라 범위 밖으로 남겼다.

같은 판정 파일 안에서 누적형 미션(`distance`·`activity_count` 등)은 참가 시점 이후 활동만 센다(`checker.ts`의 `joinedAt` 필터). `checkin`·`item_collect`만 보유 현황 기준이다.

2026-10-08 DB 조회 결과 `checkin` 미션은 0건이라 지금 영향받는 사용자는 없다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 선택지 A(현행 유지): 대상 지점에 한 번이라도 체크인했으면 달성한다. `item_collect`의 보유 판정과 의미가 같다.
- 선택지 B(참가 이후만): 미션 참가 시각(`user_mission_participations.joined_at`) 이후의 체크인만 달성으로 센다. 누적형 미션과 같은 기준이다.
- 추천: B. 체크인 미션은 "이 지점에 가 보세요"처럼 새 방문을 부르는 미션이라, 이미 다녀온 사용자가 참가와 동시에 완료되면 미션의 의미가 약해진다. `item_collect`는 보유 자체가 목표라 A를 유지한다.
- 이 결정은 사용자(기획) 승인이 필요하다.

## 구현 계획
> 선택지 B로 정했을 때만 진행한다.

1. `checkMissions`가 `checkin` 미션마다 대상 `poi_id`와 그 미션의 `joined_at`을 함께 `loadOwnership`에 넘긴다.
2. `checkin` 갈래 조회 결과에서 `triggered_by_activity_date >= joined_at`인 행만 그 미션의 방문으로 센다(활동 시각 기준이어서 누적형 미션의 `startDate >= joinedAt` 필터와 같다). 같은 지점을 대상으로 하는 미션이 여럿이면 미션마다 따로 판정한다.
3. `checker-ownership.test.ts`에 참가 전 체크인만 있는 사용자는 미달성, 참가 후 체크인이 있는 사용자는 달성인 사례를 더한다.
4. `SERVICE_OPERATIONS.md` §9-3·§9-4의 `checkin` 줄·행을 고친다.

## 완료 조건
- 선택지 결정과 근거가 이 티켓 「주요 의사결정」에 적혀 있다.
- (B일 때) 참가 전 체크인만 있는 사용자의 `checkin` 미션이 `completedMissionIds`에 들어가지 않고, 참가 후 체크인이 있으면 들어간다(vitest).
- (B일 때) 레거시 `triggered_by_poi_id` 근거와 `item_collect` 판정은 그대로다(기존 테스트 통과).
