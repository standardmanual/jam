# [Infra] 위험 진단 검토의견 검증: 차단 감사와 시드 파일 방침

## 핵심 요약

- 요구사항: 2026-10-14에 들어온 「개발 결과물 전방위 리스크 진단」 검토의견 중, 코드 변경이 필요 없는 두 건(서비스 롤 노출 감사, 번호 없는 시드 파일 방침)의 확인 결과를 기록한다.
- 구현 계획: 코드 변경 없음. 확인 결과를 이 티켓에 남기고, 오해를 줄이는 문서 한 줄(`docs/agents/orchestrator.md` §4)만 고친다.
- 관련 파일: `jam-web/src/app/api/dev-login/route.ts`, `jam-web/src/app/api/drops/debug/route.ts`, `jam-web/src/lib/env/test-accounts.ts`, `jam-web/src/lib/admin/auth.ts`, `jam-web/supabase/migrations/seed_*.sql`, `docs/agents/orchestrator.md`

## 배경 / 문제 정의

검토의견은 서비스 롤을 쓰는 라우트가 많다는 점과 마이그레이션 폴더에 시드가 섞여 있다는 점을 위험으로 짚었다. 아래는 코드·저장소·외부 시스템에서 직접 확인한 결과다. 판단과 사실을 나눠 적는다.

## 확인 결과

### 1. `api/dev-login`, `api/drops/debug` 차단 감사 (읽기 전용)

**사실**

- `api/dev-login`은 `isStagingOrDevEnv()`가 거짓이면 404를 반환한다. 이 함수는 `NODE_ENV === 'development'` 또는 `STAGING_MODE === 'true'`일 때만 참이다(`test-accounts.ts` 14~19줄).
- Vercel 프로덕션 프로젝트 `jam`의 환경 변수 키 목록에 `STAGING_MODE`가 없다(2026-10-14, Vercel MCP `filter_project_envs`로 조회. 값은 복호화하지 않았다. 조회 결과에 `hiddenProductionEnvCount`는 0이었다).
- `api/drops/debug`는 첫 줄에서 `requireAdmin()`을 호출해 어드민이 아니면 반환한다.
- staging 자동 로그인 계정이 어드민이 되는 경로는 `hasAdminAccess`가 `ADMIN_EMAILS`·`is_admin`보다 먼저 거절한다(`auth.ts`, 티켓 20261006_1527).

**판단**

- 두 라우트 모두 프로덕션에서 차단된다. 수정은 필요 없다.
- 남은 보강은 이미 별도 티켓이 있다: 요청 횟수 제한(20261007_0955), 인가 함수 통합 테스트(20261007_0957).

**범위 밖 관찰 (참고)**

- 프로덕션 프로젝트 `jam`의 preview 대상 환경 변수에 `SUPABASE_SERVICE_ROLE_KEY`, `ADMIN_EMAILS`, `GOOGLE_CLIENT_SECRET`이 등록돼 있다. `vercel.json`의 `ignoreCommand`가 프로덕션이 아닌 빌드를 막는 동안은 영향이 없다. 그 전제가 바뀌면 노출 범위가 넓어지므로, 전제를 바꾸는 변경 때 함께 점검한다.

### 2. 번호 없는 `seed_*.sql` 방침

**사실**

- `jam-web/supabase/migrations/`에서 숫자로 시작하지 않는 파일은 34개이고, 모두 `seed_` 접두다. 그중 7개가 에셋 제너레이터의 홈피드 카드 등록 기록(`seed_agent_home_feed_*`)이다.
- Supabase 프로젝트 `jam-prod`의 적용 이력(`list_migrations`)에 `seed_agent_home_feed_*` 이름이 하나도 없다(2026-10-14 조회). 즉 이 파일들은 직접 실행한 SQL의 기록 파일이다. 저장소 파일과 적용 이력은 1:1이 아니다. 적용 이력에는 번호 078 미만 이름이 없다.
- 이름과 위치는 규칙으로 정해져 있다: `CLAUDE.md` 규칙 6과 `docs/agents/orchestrator.md` §4(`seed_*.sql`은 1회성 데이터). `jam-web/scripts/asset-generator/registerHomeFeedRecord.mjs`(23~25줄), `docs/service/prd/asset-generator/HOME_FEED_REGISTRATION_BUNDLE.md`(107줄, 361줄), `registration.sql` 7개의 헤더, 관련 테스트 2개가 같은 경로와 이름을 가리킨다.
- 번호 122 결번은 `122_background_animation_column.sql`이 `124_background_animation_column.sql`로 번호가 바뀐 흔적이다(git 이력 확인). 적용 이력의 이름은 `background_animation_column`이다.

**판단**

- 검토의견의 「`supabase/seeds/`로 분리」는 채택하지 않는다. 옮기면 규칙 6, 등록 스크립트, PRD, 테스트가 한꺼번에 어긋나고, 얻는 것은 폴더 모양뿐이다.
- 오해를 줄이려고 `orchestrator.md` §4의 해당 항목에 「적용 이력에 올라가지 않는 기록 파일이며 옮기지 않는다」는 한 줄을 더한다.

**미확인**

- 번호 001, 012가 중복되어 있다(`ls`로 확인). 이번에는 원인을 보지 않았다.
- Supabase CLI가 번호 없는 파일을 어떻게 취급하는지는 이 환경에 CLI가 없어 확인하지 못했다.
