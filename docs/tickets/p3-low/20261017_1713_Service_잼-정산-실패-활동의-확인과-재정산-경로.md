# [Service] 잼 정산이 실패한 활동을 확인하고 다시 정산하는 경로를 만든다

## 핵심 요약

- 요구사항: 티켓 20261017_1423이 동기화에서 활동마다 잼을 정산한다. 정산(`jam_apply`)이 실패해도 동기화는 막지 않고 로그만 남기는데, 그 활동은 이미 처리 완료로 저장되어 다음 동기화에서 다시 정산되지 않는다. 실패를 운영이 확인하고, 실패한 활동만 안전하게 다시 정산하는 경로를 만든다.
- 구현 계획: 시작 전에 정산 실패가 실제로 얼마나 나는지 로그와 `strava_activities`·`jam_transactions` 대조로 확인한다. 실패가 드물면 대조 쿼리와 운영 절차만 두고, 잦으면 자동 재정산을 만든다. 시작 전에 사용자에게 방향을 묻는다.
- 관련 파일(2026-10-17 게이트 판독): `jam-web/src/lib/jam/settlement.ts`(정산 실패 처리), `jam-web/src/lib/strava/sync.ts`(저장 뒤 정산 호출), `jam-web/supabase/migrations/220_jam_ledger.sql`(`jam_apply`는 같은 활동 식별자에 한 번만 줌). 스펙: 운영 로직 4.2절.

## 배경 / 문제 정의

정산은 `strava_activities.id`를 활동 식별자로 `jam_apply`를 부르고, 같은 활동을 다시 부르면 기존 줄을 돌려준다(멱등). 그러나 동기화는 이미 저장된 활동을 다시 가져오지 않으므로 정산이 일시적으로 실패한 활동은 잼을 영영 받지 못한다. 옛 저장 활동(JAM 2.0 이전에 저장된 행)은 정산 대상이 아니므로, 무작정 «정산 줄이 없는 활동»을 다시 정산하면 옛 활동에 잼이 소급 지급된다. 이를 구분할 기준(정산 도입 시각, 정산 시도 표시 등)이 필요하다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 정산 실패를 운영이 볼 수 있게 한다(실패 기록 또는 대조 쿼리).
- 재정산은 JAM 2.0 정산 도입 뒤에 저장된 활동만 대상으로 하고, 옛 저장 활동에 소급 지급하지 않는다.
- 재정산 중복 지급이 없음을 `jam_apply`의 멱등으로 보장하고 시험으로 고정한다.

## 구현 계획

실패 빈도 확인 뒤 정한다. 요약은 2,500자 이내.

## 완료 조건

- 정산 실패 활동을 확인하는 방법이 있고, 재정산이 중복 지급 없이 동작하며 옛 저장 활동에 소급 지급하지 않는 시험이 있다.
