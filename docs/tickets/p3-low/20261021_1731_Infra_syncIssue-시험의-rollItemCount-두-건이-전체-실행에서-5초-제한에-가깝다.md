# [Infra] `syncIssue.test.ts`의 `rollItemCount` 시험 두 건이 전체 실행에서 5초 제한에 가깝다

## 핵심 요약

- 요구사항: `npx vitest run` 전체 실행에서 `rollItemCount`를 반복 호출하는 시험 두 건이 3.2~4.7초를 쓴다. 5초 제한에 가까워서 부하가 조금 더 높은 날에는 티켓 `20261021_1019`와 같은 거짓 실패가 이 시험에서 날 수 있다. 아직 실패한 적은 없다.
- 구현 계획: 먼저 반복 횟수 `N`이 시험의 통계 판정에 정말 필요한 크기인지 확인한다. 필요하면 시험 안의 반복 비용을 줄이거나 시험 두 건에만 더 긴 제한을 준다. 제한을 늘리면 이유를 시험 파일 주석에 남긴다.
- 관련 파일: `jam-web/src/lib/drop-engine/__tests__/syncIssue.test.ts` 65줄(`활동마다 1~3개다`)과 77줄(`등산은 최소 2개이고 최대 4개다`). 소요 시간은 민지 보고이며 카리나가 다시 재지는 않았다.

## 배경 / 문제 정의

티켓 20261021_1019 게이트(민지)가 발견했다. 민지가 전체 실행을 세 번 돌렸을 때 이 시험이 3.2~4.7초였고, 한 번은 4.7초였다. 수정 전 구현에서도 3.5초였으므로 1019의 수정이 만든 현상은 아니다.

발견: 2026-10-21 티켓 20261021_1019 게이트.

## 상세 요구사항

### 서비스/코드베이스 관점

- 시험이 확인하는 분포(활동마다 1~3개, 등산은 2~4개)의 판정 기준은 바꾸지 않는다.

## 완료 조건

- [ ] 로컬 전체 실행에서 두 시험이 제한에 여유를 두고 끝난다(여러 번 실행해 확인)
- [ ] 판정 기준이 그대로다
