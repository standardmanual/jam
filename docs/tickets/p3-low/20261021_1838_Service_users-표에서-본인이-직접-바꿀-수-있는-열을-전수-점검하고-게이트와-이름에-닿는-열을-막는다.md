# [Service] users 표에서 본인이 직접 바꿀 수 있는 열을 전수 점검하고, 게이트와 이름에 닿는 열을 막는다

## 핵심 요약

- 요구사항: 공용 DB의 `users` 표는 «본인만 수정» 정책이 `USING (auth.uid() = id)`뿐이고 `WITH CHECK`와 열 제한이 없으며, `authenticated` 역할에 열 UPDATE 권한이 넓게 열려 있다. 티켓 20261021_1247 2회에서 `tribe_id`는 마이그레이션 260 트리거로 막았고 `is_admin`은 219가 막았지만, `username`, `onboarding_completed_at`, 그 밖의 열은 로그인한 유저가 브라우저에서 PostgREST로 직접 바꿀 수 있다. `users`의 모든 열을 훑어 «서버만 정해야 하는 열»(게이트나 정책에 쓰이는 열, 이름·표시 규칙을 서버가 검사하는 열, 집계 열 등)을 가려내고 막는다.
- 구현 계획: (1) 열 전수 목록과 각 열의 쓰는 곳(서버 경로, 클라이언트 직접 쓰기 여부)을 조사한다. (2) 서버만 쓰는 열은 `tribe_id`·`is_admin`과 같은 방식의 트리거(또는 열 권한 회수)로 막는다. 유저가 화면에서 실제로 직접 쓰는 열(예: 프로필의 `display_name`)은 막지 않는다. (3) 마이그레이션은 확장(트리거와 함수 추가)만 하고 롤백 실측과 사용자 승인 뒤 적용한다. 지금 공용 DB에는 유저가 8명뿐이라 막아도 데이터 정리는 필요 없다.
- 관련 파일: `jam-web/supabase/migrations/260_users_block_client_tribe_write.sql`(같은 방식의 선례), `219`의 `users_block_client_is_admin_write`, 클라이언트가 `users`를 직접 쓰는 곳(`jam-web/src/**`에서 `from('users')`와 `.update`·`.upsert`를 찾는다). 줄 위치는 시작 때 확인한다.

## 배경 / 문제 정의

티켓 20261021_1247 2회 시작 전 조사와 게이트(민지, 참고)가 발견했다. 2회는 트라이브 직접 쓰기만 막았다. `username`을 직접 바꾸면 서버가 하는 중복 검사와 금지어 검사를 거치지 않을 수 있고, `onboarding_completed_at`처럼 흐름에 쓰이는 시각 열도 같은 틈이 있다.

발견: 2026-10-21 티켓 20261021_1247 2회 시작 전 조사.

## 상세 요구사항

### 서비스/코드베이스 관점

- 서버만 정해야 하는 `users` 열은 로그인한 유저가 직접 쓸 수 없다.
- 유저가 화면에서 실제로 쓰는 열(프로필 편집 등)은 계속 동작한다.
- 어드민 화면과 서버 라우트(service role)는 영향이 없다.

## 완료 조건

- [ ] 서버만 쓰는 열을 로그인한 유저가 직접 바꾸려 하면 DB가 거절한다(롤백 실측)
