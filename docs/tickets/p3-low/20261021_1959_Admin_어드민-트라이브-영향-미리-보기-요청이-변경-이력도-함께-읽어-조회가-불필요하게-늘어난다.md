# [Admin] 어드민 트라이브 영향 미리 보기 요청이 변경 이력도 함께 읽어 조회가 불필요하게 늘어난다

## 핵심 요약

- 요구사항: `GET /api/admin/users/[id]/tribe`는 `?newTribeId=`가 있어 영향 미리 보기를 읽는 요청에도 변경 이력을 함께 읽는다. 어드민 유저 상세의 변경 양식은 트라이브를 고를 때마다 이 요청을 보내므로, 이력(트라이브 이름과 어드민 이메일 조회 포함)이 매번 불필요하게 3~4건 더 읽힌다. 이력은 화면이 서버에서 이미 읽어 그리고 있어 미리 보기 응답에는 필요 없다. 미리 보기 요청에서는 이력을 읽지 않거나, 이력과 미리 보기를 별도 경로로 나눈다.
- 구현 계획: 라우트에서 `newTribeId`가 있으면 미리 보기만 읽어 돌려주고, 이력은 `newTribeId`가 없을 때만 읽는다(응답 형태가 바뀌므로 어드민 화면의 `UserTribeChangeForm`이 쓰는 필드를 먼저 확인한다). 시험을 맞춘다.
- 관련 파일: `jam-web/src/app/api/admin/users/[id]/tribe/route.ts` 100줄 근처, `jam-web/src/lib/admin/user-tribe.ts`(`fetchTribeChangeHistory`), `jam-web/src/app/admin/users/[id]/UserTribeChangeForm.tsx`. 줄 위치는 민지 보고이며 카리나가 직접 확인하지는 않았다.

## 배경 / 문제 정의

티켓 20261021_1247 3회에서 아현(범위 밖이라 두었다고 보고)과 민지 게이트(참고)가 발견했다. 2회가 한 라우트에서 미리 보기와 이력을 함께 돌려주도록 만들었고 3회 화면은 그 응답에서 미리 보기만 쓴다. 어드민 한 명이 가끔 쓰는 화면이라 영향은 작다.

발견: 2026-10-21 티켓 20261021_1247 3회.

## 상세 요구사항

### 서비스/코드베이스 관점

- 미리 보기 요청은 미리 보기에 필요한 것만 읽는다.
- 화면이 쓰는 응답 필드는 바뀌지 않는다.

## 완료 조건

- [ ] `?newTribeId=`가 있는 요청에서 변경 이력을 읽지 않는다(시험으로 확인)
- [ ] 이력 요청과 어드민 화면의 동작이 그대로다
- [ ] 관련 시험이 통과한다
