# [Service] 확률 안내 페이지 보강 거리: 확정 0개 조합, 요청마다 읽기, 로그아웃 입구, 머리 h1 두 개

## 핵심 요약

- 요구사항: 확률 안내 페이지(`/probability`)를 만든 6-4 1회에서 민지(게이트, 참고)와 아현이 짚었고 이번 범위 밖이라 두었던 네 가지를 한 곳에 모은다. 지금 공용 DB 값에서는 틀린 표가 나오지 않는다. 설정이 바뀌거나 출시 뒤 방문이 늘 때 손볼 거리다.
  1. **확정 0개 조합**: `sync_item_guaranteed`가 0이고 `sync_item_bonus_rolls`가 0보다 크면 페이지는 «확정 0개»와 보너스 기회·확률 줄을 함께 보인다. 그런데 동기화 발급은 확정 개수가 0이면 보너스도 굴리지 않는다(`syncIssue.ts`의 `guaranteed <= 0` 조기 반환). 이 조합일 때 보너스 줄을 빼거나 «확정이 없으면 보너스도 없어요»로 바꾼다.
  2. **요청마다 읽기**: 공개 경로가 `force-dynamic`이라 방문마다 service role로 설정 표 3개를 읽는다. 지금은 문제가 없지만 방문 수만큼 읽기가 늘어난다. 설정 변경이 즉시 보여야 한다는 요구와 맞추어 짧은 서버 캐시(수십 초)나 태그 무효화가 가능한지 본다.
  3. **로그아웃 방문자의 입구**: 입구가 푸터와 캡슐 시트뿐이라 로그인하지 않은 사람은 주소를 알아야 한다(푸터는 로그인 화면과 `(legal)` 페이지에 없다). 로그인 화면의 약관 동의 문장 곁이나 법 페이지 끝에 링크를 둘지 정한다(사용자 결정 필요).
  4. **머리 `h1` 두 개**: `LegalTopNav`가 제목을 `h1`로 그리고 본문에도 `h1`이 있어 문서 제목이 둘이다(개인정보처리방침과 같은 구조). 법 페이지 공용 보조 컴포넌트를 뽑는 티켓 `20261021_1428`과 함께 정리한다.
- 구현 계획: 1은 `jam-web/src/lib/probability/disclosure.ts`의 동기화 표 행 만들기(152~160줄 근처)와 시험. 2는 `jam-web/src/app/(legal)/probability/page.tsx`의 `dynamic` 설정과 읽기 함수. 3은 사용자 결정 뒤 로그인 화면 문구. 4는 `1428`에 합친다. 줄 위치는 민지 보고이며 카리나가 다시 확인하지는 않았다.
- 관련 파일: `jam-web/src/lib/probability/disclosure.ts`, `jam-web/src/app/(legal)/probability/page.tsx`, `jam-web/src/lib/drop-engine/syncIssue.ts`, `docs/service/prd/probability/PRD.md`.

## 배경 / 문제 정의

티켓 20261021_1250 6-4 1회(확률 안내 페이지)의 게이트 참고 사항과 아현의 알림에서 나왔다. 네 건 모두 채원 사전 판정과 사용자 결정 안에서 구현한 결과이고 결함이 아니다. 출시 전에 3번만 사용자 결정이 필요하고 나머지는 서두르지 않아도 된다.
