# [API] `strava/replace` 라우트가 기존 계정 삭제와 첫 동기화를 한 요청에서 기다려 실행 시간 한도에 닿을 수 있다

## 핵심 요약

- 요구사항: 티켓 `20261021_1249` 4회의 `POST /api/strava/replace`는 한 요청 안에서 기존 계정 삭제(아바타 파일 삭제, 준비 RPC, `auth.admin.deleteUser`), 새 연결 저장, 첫 동기화(`syncStravaActivities`)를 모두 기다린다. 지울 데이터가 많은 기존 계정이면 서버리스 실행 시간 한도에 닿을 수 있는데 라우트에 `maxDuration` 설정이 없다. 한도에 닿으면 기존 계정은 지워졌는데 새 연결 저장이나 동기화가 끊기는 상태가 될 수 있다(응답은 restart 안내로 이어진다).
- 구현 계획: ① 실제로 얼마나 걸리는지 잰다(공용 DB에서 가장 큰 계정 기준: 아이템 수십~수백 개, 이력 수백 건). ② 한도에 가까우면 `export const maxDuration`을 정하거나, 첫 동기화를 응답 뒤로 미룬다(콜백은 이미 첫 동기화 실패를 연동 성공으로 보므로 같은 규칙). ③ 파괴적 POST의 Origin 검사는 티켓 `20261021_2242`와 함께 본다.
- 관련 파일: `jam-web/src/app/api/strava/replace/route.ts` 121줄 근처(민지 보고, 카리나가 직접 확인하지는 않았다), `jam-web/src/app/api/strava/callback/route.ts`(콜백의 첫 동기화 처리).

## 배경 / 문제 정의

6-3 4회 게이트(민지, 참고)가 발견했다. 실측하지 않았다. 일괄 삭제의 Strava 해제 소요를 다루는 티켓 `20261021_2243`와 같은 종류의 문제다.

발견: 2026-10-22 티켓 20261021_1249 4회 게이트.
