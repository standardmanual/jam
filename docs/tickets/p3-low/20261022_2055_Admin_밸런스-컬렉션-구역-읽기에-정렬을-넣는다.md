# [Admin] 밸런스 설정 «컬렉션과 믹스» 구역의 읽기에 정렬을 넣는다

## 핵심 요약

- 요구사항: «컬렉션과 믹스» 구역이 `item_book_tier_default_rewards` 네 행을 정렬 없이 읽는다. 두 행의 수정 시각이 밀리초까지 같고 마이크로초만 다르면 구역 수정 시각을 고르는 `latestStamp`의 결과가 호출마다 달라질 수 있다. 챕터 구역(티켓 `20261022_1133` 2회)이 쓴 방식으로 고친다.
- 구현 계획: 읽을 때 `tier` 순서로 정렬하고, 구역 수정 시각은 DB가 준 순서가 아니라 고정 순서(common, rare, epic, mystic, 믹스 정책 행)로 계산한다. 쓰기 뒤 돌려주는 값도 같은 순서로 계산해 다음 읽기와 같게 한다.
- 관련 파일: `jam-web/src/lib/admin/balance/collection.ts`(읽기 함수 117줄 부근과 쓰기 뒤 반환), 선례 `jam-web/src/lib/admin/balance/chapter.ts`(정렬 읽기와 고정 순서 `latestStamp`), 시험 `jam-web/src/lib/admin/balance/__tests__/collection.test.ts`와 `fakeDb.ts`(`order` 호출 기록이 챕터 구역 때 들어갔다)

## 배경 / 문제 정의

티켓 `20261022_1133` 1회 게이트의 범위 밖 발견물이다. 같은 문제를 2회 챕터 구역에서는 막았고 컬렉션 구역에는 그대로 남아 있다. 지금 네 행은 같은 시각에 쓰인 값이라 일어나지 않고, 일어나도 불필요한 409(안전한 쪽 오류)로 끝난다. 그래서 P3이다.

## 상세 요구사항

### 서비스/코드베이스 관점

- 읽기 질의에 `order('tier')`를 넣는다. 정렬 기준이 DB 정렬 규칙에 기대지 않도록 고정 순서 배열로 한 번 더 맞춘다(챕터 구역과 같은 방식).
- 저장 직후 연속 저장이 409 없이 되는 현재 동작은 그대로 유지한다.

## 구현 계획

`chapter.ts`의 읽기와 `latestStamp` 호출 부분을 그대로 따라 `collection.ts`에 적용하고, 시험은 챕터 시험의 «수정 시각 동률» 사례를 컬렉션 표로 옮긴다.

## 완료 조건

- 네 행의 `updated_at`이 밀리초까지 같고 마이크로초만 다른 상태에서, 읽기를 여러 번 해도 구역 수정 시각이 항상 같은 값이다(시험으로 고정).
- 정렬 호출을 되돌린 변형에서 위 시험이 실패한다.
- 저장 직후 같은 화면에서 이어서 저장해도 409가 나지 않는다(기존 시험 유지).
