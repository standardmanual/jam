# [Infra] CI 전체 검증(`verify.sh`) 대기 시간을 줄인다

> 후속 티켓(2026-10-23 카리나, 티켓 20260922_0205 1주 실측에서 나왔다). 처음에는 «Actions 월 사용량 절감»을 목적으로 P2로 만들었으나, 같은 날 저장소가 공개로 전환돼(0205 「전제 변경」) 그 목적이 사라져 P3와 «대기 시간 단축»으로 줄였다.

## 핵심 요약

- 요구사항: 리뷰 브랜치 `verify`의 전체 경로가 평균 약 3분 10초다. 검사를 하나도 빼지 않고 이 시간을 줄여 push 뒤 검증 결과를 기다리는 시간을 낮춘다.
- 구현 계획: ① `verify.sh`의 단계별 시간을 먼저 잰다 ② 측정에 따라 줄일 방법을 고른다 ③ 같은 방식으로 1주 재측정한다. 목표값은 착수 때 사용자와 정한다.
- 관련 파일: `scripts/verify.sh`(`run_step` 함수 24행 부근, 34~37행의 lint·typecheck·test·ds:check 순차 실행, 39행 asset-bundle, 43~120행의 문서·계약 검사 스크립트 호출), `.github/workflows/verify.yml`(Node 설치의 `cache: npm`, `npm ci` 단계), `.githooks/pre-push`(리뷰 브랜치 push에서 같은 `verify.sh`를 로컬에서 실행)
- 함께 볼 티켓: 20260922_0205(실측 근거, 집계 방법), 20260922_1755(`verify.sh` 3중 실행 제거, CLOSED)

## 배경 / 문제 정의

실측(티켓 20260922_0205, 2026-09-22~09-29 KST, 전체 경로 성공 220건)이다.

| 단계 | 평균 | 비중 |
|---|---|---|
| `전체 검증 (scripts/verify.sh)` | 153.6초 | 82% |
| `의존성 설치 (jam-web)`(`npm ci`) | 22.6초 | 12% |
| 체크아웃 | 6.1초 | 3% |
| 그 밖의 단계 합 | 약 6초 | 3% |
| 합계 | 188초 | |

- 실행 시간 분포는 중앙값 184초, 하위 25% 168초, 상위 25% 223초다.
- 그 뒤 시간이 늘었다(2026-10-23 확인): 첫 staging 런(런 `39971238203`)은 `verify.sh` 226초, 잡 전체 4분 39초였다. 같은 날 14:10·14:24 KST 리뷰 브랜치 성공 런의 잡 전체 시간은 293초·333초였다. 1주 실측 평균 188초보다 길다. 원인(시험 수 증가 등)은 확인하지 않았다.
- 가벼운 경로의 시간은 체크아웃이 대부분이었다(2026-10-23 두 번째 staging 런 `39972055303`): 잡 81초 중 체크아웃 68초, 가벼운 검증 2초. 1주 실측의 가벼운 경로 체크아웃 평균은 5.8초였고 같은 날 첫 staging 런의 체크아웃은 20초였다. 표본이 1건이라 변동 폭은 확정하지 못했다. 전체 이력을 받는 `fetch-depth: 0` 설정이 원인인지는 확인하지 않았다. 같은 날 전체 경로 staging 런 `40025291223`의 잡 시간은 3분 49초였다.
- 사실로 확인하지 못한 것: `verify.sh` 안의 단계별 시간. CI 로그에는 `전체 검증` 한 단계로만 보인다. `verify.sh`는 lint, typecheck, test, ds:check, asset-bundle을 순서대로 돌리고 문서·계약 검사 스크립트 여덟 개를 잇따라 호출한다. 어느 단계가 시간을 쓰는지는 재 봐야 안다.
- 이 티켓이 비용을 다루지 않는 이유: 저장소가 비공개였을 때는 Actions 무료 한도 때문에 잡마다 분 단위로 올림 과금되는 시간이 비용이었다. 공개 전환 뒤에는 그 비용 제약이 없어졌다고 보지만, 공개 저장소의 표준 러너가 무료라는 점은 공식 문서로 확인하지 못했다(0205 「전제 변경」).
- push 횟수를 줄이는 쪽(재작업 push 묶기 등)은 이 티켓의 범위가 아니다.

## 상세 요구사항

### 서비스/코드베이스 관점

1. `verify.sh`의 각 단계 소요 시간이 로컬 실행과 CI 로그 양쪽에서 한 줄씩 보이게 한다.
2. 측정 결과에서 시간을 가장 쓰는 단계부터 줄인다. 아래는 확인 전의 후보이고 채택은 측정 뒤에 정한다.
   - 서로 의존하지 않는 단계의 병렬 실행(러너 코어 수는 확인하지 않았고, 병렬화는 로컬 `pre-push`에도 영향을 준다)
   - `npm ci`(평균 22.6초) 대신 잠금 파일 해시를 키로 `node_modules`를 캐시하는 방법
   - 같은 검사를 두 번 도는 곳이 있는지 확인(`verify.sh` 내부와 워크플로 사이)
3. 어떤 검사도 제거하거나 느슨하게 하지 않는다. 단축은 병렬화·캐시·중복 제거로만 한다(티켓 20260921_2304 «기준을 낮추는 변경을 막는다»의 취지).

### 컨텐츠 관점 (해당 시)

- 해당 없음.

## 구현 계획

1. 측정: `scripts/verify.sh`의 `run_step`과 문서 검사 호출부에 단계별 소요 시간 출력을 더한다. CI 1주 분량을 모아 단계별 분포를 본다(집계 방법은 20260922_0205 「집계 방법」과 같다).
2. 고르기: 측정 결과를 사용자에게 보이고 목표값을 정한다.
3. 적용·재측정: 고른 방법을 적용하고 같은 방식으로 1주 재측정해 실행 시간 분포를 비교한다.

## 완료 조건

- `verify.sh` 단계별 소요 시간이 CI 로그와 로컬 실행에서 보인다.
- 단축 뒤 전체 경로 성공 실행의 중앙값이 착수 때 사용자와 정한 목표 이하다(1주 재측정, 집계 방법은 20260922_0205와 같고 과금 분 대신 잡 시간을 쓴다).
- 단축 전후로 `verify.sh`가 실행하는 검사 목록이 같다(`run_step` 호출과 스크립트 호출 목록의 diff가 비어 있다).
- 로컬 `pre-push` 게이트가 단축 뒤에도 같은 결과를 낸다(실패해야 하는 변경에서 실패한다).
