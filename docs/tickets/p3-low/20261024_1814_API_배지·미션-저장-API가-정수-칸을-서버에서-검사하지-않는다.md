# [API] 배지·미션 저장 API가 정수 칸을 서버에서 검사하지 않아 직접 호출하면 소수와 0·음수가 저장된다

## 핵심 요약

- 요구사항: 티켓 `20261023_1940`이 배지·미션 양식에서 정수 여섯 칸의 소수·지수·범위를 저장 전에 막았지만, 서버 API는 그대로다. 양식을 거치지 않는 호출(스크립트, 다른 도구)은 막히지 않는다. 서버에서도 같은 판정을 하도록 보강할지 정한다.
- 구현 계획: 사용자가 방침을 정한 뒤 정한다. 후보는 (가) 서버가 양식과 같은 범위로 검사해 400으로 거절, (나) 지금처럼 두고 양식 검사에만 기댐. (가)라면 배지 API(POST·PATCH)와 미션 API(POST·PATCH)에 같은 판정 함수를 쓴다.
- 관련 파일: `jam-web/src/app/api/admin/badges/` 의 `badge-insert-payload.ts`(105·118·137줄)와 `[id]/route.ts`(60·74·157줄), `badges/route.ts:68`, `jam-web/src/app/api/admin/missions/route.ts`(104~114줄)와 `[id]/route.ts`(175~191줄), 양식 쪽 판정 `jam-web/src/lib/admin/integerRangeInput.ts`.

## 배경 / 문제 정의

1940의 읽기 전용 확인(아현 확인, 민지가 다시 읽어 확인) 결과는 다음과 같다. 배지의 포인트 보상·패치 가격·레벨은 서버가 소수를 거절하지 않고 `Math.trunc`로 조용히 버려, 직접 호출하면 `2.5`가 `2`로 저장된다. 미션의 공개 인원·선착순 인원·미션 포인트는 서버에 검사가 없어 본문이 그대로 insert·update되고, 0과 음수도 막지 않는다. DB 열은 모두 INTEGER이고 미션 세 칸에는 CHECK가 없다. Postgres INTEGER 열이 소수 JSON 값을 거절하는지는 쓰기 요청을 보내지 않아 확인하지 못했다.

## 완료 조건

- 사용자가 (가)와 (나) 중 하나를 정해 이 티켓에 적었다.
- (가)라면 여섯 칸을 직접 호출했을 때 양식과 같은 범위에서 400으로 거절되고 시험이 있다. 이미 저장된 값을 수정 저장하는 흐름이 깨지지 않는지(공용 DB 미션 55건에는 범위 밖 값이 없음을 2026-10-24에 읽기로 확인했다) 확인한다.
- (나)라면 «하지 않는다»와 사유를 완료 기록에 적는다.
