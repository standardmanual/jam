# [Feature] 처음 연동한 직후의 첫 동기화에서도 이번에 받은 잼 합계를 보여 준다

## 핵심 요약

- 요구사항: 티켓 `20261025_2050`은 수동 동기화 뒤 결과 화면에 «이번에 잼 {n}만큼 받았어요»를 보인다. 처음 Strava를 연동한 직후의 첫 동기화는 서버 콜백이 동기화를 끝내고 곧바로 리다이렉트해서 응답 본문이 없고, 화면(`StravaConnectReveal`)이 되읽는 `recent-earned`는 배지만 돌려주므로 잼 합계가 도착하지 않는다. 이 경로에서도 합계를 보이게 한다.
- 구현 계획: 서버 변경이 필요하다. 되읽기 응답(`jam-web/src/app/api/badges/recent-earned/route.ts`)에 이번 연동의 잼 합계를 더하거나 콜백이 합계를 남기는 방식을 시작 때 정한다. 화면은 `jam-web/src/components/StravaConnectReveal.tsx`가 같은 문구(`d.today.syncJamEarned`)를 쓴다. 첫 동기화는 최근 인정 활동 1건만 정산하므로(`users.initial_sync_done` 첫 동기화 게이트) 합계가 작거나 0일 수 있고, 0이면 보이지 않는다.
- 관련 파일: `jam-web/src/app/api/badges/recent-earned/route.ts`, `jam-web/src/components/StravaConnectReveal.tsx`, `jam-web/src/lib/strava/sync.ts`의 첫 동기화 경로, Strava 연동 콜백 라우트(`jam-web/src/app/api/strava/` 아래).

## 배경 / 문제 정의

`20261025_2050`의 채원 사전 판정(2026-10-26)이 첫 동기화를 범위에서 빼자고 제안했고 사용자가 승인했다(별도 티켓 분리). 분리 뒤 첫 동기화에서는 잼 합계가 보이지 않는다.

## 완료 조건

- 처음 연동 직후 연출에 이번에 받은 잼 합계가 보이고, 합계가 0이거나 없으면 지금 화면 그대로다.
- 서버 응답 변경에 시험이 있고 기존 시험이 통과한다.

### 구현 내용 요약

처음 Strava를 연동한 직후 도착 화면의 배지 연출 상단에 «이번에 잼 {n}만큼 받았어요» 한 줄을 더했다. 수동 동기화(`20261025_2050`)에서 만든 문구와 접기 규칙을 그대로 쓴다. 채원 사전 판정은 «재사용, 승인 필요 없음»이다(새 문구·토큰·컴포넌트 없음).

- **서버** `GET /api/badges/recent-earned`: 배지 되읽기와 같은 10분 창에서 `jam_transactions`의 `activity_settlement` 줄(인증한 `user.id`)의 `amount`를 코드에서 더해 `jamEarned`로 싣는다. 응답은 덧셈만이고 기존 칸(`earnedBadges`, `earnedBadgesMore`, `isFirstBadgeEver`)은 그대로다. 읽기 오류와 예외는 `console.error` 뒤 0으로 접고 던지지 않으며, 피드 오류의 조기 반환에도 `jamEarned: 0`이 실린다. 마이그레이션은 없다.
- **화면** `StravaConnectReveal.tsx`: `summaryMessage` 상태 하나와 응답 선택 칸 `jamEarned?`를 더했다. 성공 분기에서 `setPhase('open')` 앞에 `jamEarnedMessage(data.jamEarned)`로 접어 담고 오버레이에는 `summaryMessage`만 넘긴다. 스타일·마크업·문구 조립 코드는 늘지 않았고 배지 0개와 오류 분기는 그대로다.
- 문서: `01_PRD.md` 115행, `02_DATA_MODEL.md` 1112행에 첫 연동 도착 화면 표시를 적었다.

### 주요 의사결정 / 핵심 메모
- 사용자 결정(2026-10-26): 첫 동기화 합계 표시를 `20261025_2050`에서 분리해 별도 티켓으로 둔다. 표시 자리와 문구는 2050에서 확정됐다.
- 1차 호출은 바뀌는 파일이 6개(코드 2, 신규 시험 2, 문서 2)라 `plan_only`로 멈췄다. 아현의 파일 단위 계획을 카리나가 코드와 마이그레이션 220으로 대조해 확인한 뒤 계획 반환 면제를 붙여 다시 실행했다(`stop-conditions.md` 부여 조건).
- 합계는 잼 원장(`jam_transactions`)의 같은 10분 창 합계다. `jam_apply`가 재호출에 기존 줄을 돌려줘 `created_at`이 첫 정산 시각이므로 같은 활동의 중복 합산은 없다.

### 잔여 이슈
- 배지가 0개이고 잼만 있는 첫 동기화는 범위 밖이다. 이 경우 수동 동기화는 잼 토스트를 내지만 첫 연동은 연동 성공 토스트만 나가 두 경로가 어긋난다. 필요하면 후속 티켓으로 정한다.
- 연동 직후 10분 안에 수동 동기화로 받은 잼도 같은 합계에 들어간다(배지 되읽기와 같은 기준, 코드 주석에 적음).
- «이번에»가 첫 연동에서는 지난 활동을 모은 합계라 의미가 조금 넓다. 두 경로의 문구를 같게 두기로 해서 그대로 두었고, 출시 뒤 반응을 보고 윤진이 따로 정할지 판단한다.
- 실제 정산 줄로 합계가 맞는지는 JAM 2.0 출시 뒤 첫 연동에서 한 번 확인한다.
