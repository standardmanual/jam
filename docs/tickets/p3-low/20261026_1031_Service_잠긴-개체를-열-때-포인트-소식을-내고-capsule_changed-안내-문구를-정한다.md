# [Service] 잠긴 개체를 열 때 포인트 소식을 내고 `capsule_changed` 안내 문구를 정한다

## 핵심 요약

- 요구사항: 묶음 3(`20261018_0050`)에 남았던 사용자 결정 둘을 구현한다(사용자가 채원 추천을 승인, 2026-10-26). ① 잠긴 개체를 열 때 **열린 채 받을 때와 같은 포인트 소식**을 낸다. **(정정 2026-10-26)** 처음 결정은 «피드는 만들지 않는다(받을 때 `item_dropped`가 이미 나가서 중복)»였으나 그 전제가 틀렸다. 잠긴 채 받은 개체는 받을 때도 피드에 나가지 않는다(가림 원칙). 그래서 사용자가 **열 때 `item_dropped`를 올리기로** 바꿨고, 캡슐에서 나온 잠긴 개체는 기존 결정(캡슐 개봉 결과는 피드에 올리지 않는다)에 따라 제외했다. 동기화로 받은 잠긴 개체만 열 때 올린다. ② `capsule_changed`(캡슐이 열리는 사이 바뀐 경우)의 안내 문구를 «캡슐이 방금 바뀌었어요. 다시 시도해 주세요.»로 한다(고정 용어 «다시 시도»).
- 구현 계획: 서버 변경이다. 잠긴 개체 열기 서버(`20261018_0053`이 만든 열기 경로, `jam-web/src/lib/capsule/` 또는 `lib/inventory/` 아래)의 성공 뒤에 포인트 알림을 보내는 지점을 시작 때 확인한다. 알림 종류는 열린 채 받는 경로가 쓰는 것을 재사용하고 새 종류가 필요하면 마이그레이션이 따른다. 문구는 `jam-web/src/lib/i18n/ko.ts`에서 `capsule_changed`를 찾아 바꾼다.
- 관련 파일: 잠긴 개체 열기 서버, `jam-web/src/lib/notifications/`, `jam-web/src/lib/i18n/ko.ts`, 시험.

## 배경 / 문제 정의

잠긴 개체를 열면 배지 포인트가 지급되는데 소식이 없어 유저가 포인트가 들어온 걸 알 수 없다. `capsule_changed` 거절 문구는 아직 정해지지 않았다.

## 완료 조건

- 잠긴 개체를 열면 포인트 소식이 한 번 나가고, 동기화로 받은 개체는 `item_dropped` 피드가 한 번 올라가며 캡슐에서 나온 개체는 피드가 올라가지 않는다(시험). (정정: 처음 조건은 «피드는 나가지 않는다»였다.)
- `capsule_changed` 거절이 지정한 문구로 보인다(시험).
- 새 알림 종류가 필요하면 마이그레이션과 롤백 실측 기록이 있다.

## 완료 기록

### 구현 내용 요약

잠긴 개체를 열 때의 소식 둘과 `capsule_changed` 안내를 구현했다. 구현 도중 처음 결정의 전제가 틀린 것을 찾아 사용자가 두 번 결정을 바로잡았다(아래 의사결정).

- **포인트 소식**(`lib/inventory/lockedItemFill.ts` `openLockedItem`): 열기 성공 뒤 `pointsAwarded`가 0보다 크면 `recordActivityRecap(userId, {points}, {client})`로 기존 «활동 결산» 알림의 포인트 꼬리를 한 번 낸다. 열린 채 받을 때(`awardPoints`)와 같은 조각이다. 원인은 포인트가 RPC `locked_item_open` 안에서 지급돼 앱의 포인트 소식 경로를 거치지 않던 것이다. 포인트가 없거나 이미 지급된 개체, 이미 연 개체(`not_locked`), 정지·거절·해석 불가에서는 소식이 없고 소식 실패는 열기 응답을 막지 않는다.
- **열 때 피드**: 동기화로 받은 잠긴 개체를 열면 `item_dropped`를 한 번 올린다. 칸 구성을 `issueFollowUp.ts`의 `recordItemDroppedFeed`로 빼 열린 채 받은 개체의 피드와 열기 경로가 함께 쓴다(열린 채 받는 경로 동작 불변). 시각은 연 시각이고 개체 정보를 읽지 못하면 피드 없이 로그만 남긴다. 올리기 전에 `item_issue_log`에서 경로를 읽어 `capsule`이면 올리지 않는다(캡슐 개봉 결과는 피드에 올리지 않는다는 2026-10-10 결정 유지). 경로가 `sync`이거나 기록이 없으면 올리고, 읽기 오류면 올리지 않는다.
- **`capsule_changed`**: 계약의 거절 코드 목록(`CAPSULE_FILL/OPEN_ERROR_CODES`)에 더하고 `d.capsule.changed`(«캡슐이 방금 바뀌었어요. 다시 시도해 주세요.»)를 채우기·열기 라우트가 409로 돌려준다. 전에는 일반 오류(500)였다.
- 새 알림 종류와 마이그레이션은 없다(기존 `activity_recap` 재사용).

### 주요 의사결정 / 핵심 메모
- **처음 결정의 전제가 틀렸다.** «열 때 피드를 만들지 않는다, 받을 때 `item_dropped`가 이미 나가서 중복»이라고 했지만 잠긴 채 받은 개체는 받을 때도 피드가 없다(`recordIssuedRewards`가 잠긴 개체의 포인트와 피드를 모두 건너뛴다, 가림 원칙). 게이트가 찾아 카리나가 코드와 문서로 확인했다. 사용자가 결정을 바꿨다(2026-10-26): 열 때 `item_dropped`를 올린다.
- **캡슐 출처는 제외한다.** 운영 로직 15.3절의 «캡슐을 열어 나온 아이템 배지는 피드에 올리지 않는다(남의 뽑기 결과를 보여 주면 뽑기를 부추기므로, 2026-10-10 사용자 결정)»와 충돌해서 사용자가 기존 결정을 지키기로 했다(2026-10-26). 동기화로 받은 잠긴 개체만 열 때 올린다.
- 포인트 소식은 `notifyPointChange`를 내보내지 않고 `recordActivityRecap`을 직접 부른다(결과는 같고 공개 범위가 늘지 않는다).
- 1차 호출은 파일 9~10개라 `plan_only`로 멈췄다. 아현의 파일 단위 계획을 카리나가 코드로 대조한 뒤 면제를 붙여 다시 실행했다. 재작업 두 번도 같은 방식으로 면제를 붙였다.

### 잔여 이슈
- 발급 기록 읽기에 실패하면 그 열기의 피드는 다시 시도되지 않고 영구히 빠진다. 로그에만 남아 누락 건수를 볼 수단이 없다(캡슐 제외 결정을 어기지 않으려는 안전 쪽 선택).
- 이미 열린 옛 개체에는 피드를 소급하지 않는다.
- 연 뒤 피드 행이 프로필의 «피드 윈도우 밖 보정»(`lib/activity-feed/capsuleItems.ts`)과 겹쳐 같은 개체가 두 번 보이는지는 확인하지 못했다. 확인하려면 공용 DB에 쓰기가 필요하다.
- 열 때의 피드는 트라이브 이름이 채워지면 «아이템 획득»으로 보인다(열린 채 받은 개체와 같은 문구). 운영 로직은 «열기는 획득이 아니다»라고 하므로 문구가 맞는지 채원 판단이 필요하다(별도 티켓 후보).
- 캡슐 시트(`capsule-flow.ts`)는 열기 거절 중 `not_full`만 화면을 새로 읽는다. `capsule_changed`는 문구만 보이고 새로 읽지 않아 «다시 시도»가 같은 화면 상태에서 시도된다. 이번 범위 밖이다.
- 클라이언트 거절 코드 시험(`capsule-client.test.ts`)에 `capsule_changed`가 없다. 목록이 두 상수에서 파생돼 지금은 동작하지만 새 코드가 화면까지 닿는 경로는 시험이 고정하지 않는다.
- `현재 서비스 비교.md` 233·237행의 «남은 일: 열 때의 피드·알림(3-4)»는 2026-10-18 시점 진행 기록이라 고치지 않았다.
