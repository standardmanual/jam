# [Admin] 트렌드 출처 표에 저장소 폴더의 최근 갱신 일시를 GitHub에서 읽어 보인다 (후속 조각 E)

> 후속 조각이다. 상위 티켓 20261028_1422의 조각 A~D가 끝나고 12-01 월간 읽기를 본 뒤, 화면에서 알고 싶은 정보가 실제로 부족한지 보고 범위를 정한다. 그때까지 WAITING이다.

## 핵심 요약

- 요구사항(사용자 질문, 2026-10-28): 저장소 폴더 출처의 행에서, 어드민 서버가 GitHub의 해당 폴더를 열어 폴더가 실제로 있는지와 최근 갱신 일시를 확인해 표에 보여 준다. 예: 「최근 갱신 10/27 14:03」, 폴더 바로가기 링크.
- 구현 계획(안): 개발 보드가 쓰는 GitHub 읽기 모듈에 「경로의 최근 커밋」 조회를 더하고, 출처 표가 폴더 종류의 행에만 그 값을 붙인다. 읽기가 실패해도 표는 그대로 그려진다.
- 관련 파일(지도, 착수 때 줄 위치를 다시 확인한다):
  - `jam-web/src/lib/admin/devBoard/github.ts` — `createGithubReader`(65행)·`getDefaultGithubReader`(184행). 인터페이스(38~44행)에 `readFile`·`compareAhead`·`latestDeployment`·`latestCommit(branch)`가 있고, 「경로의 최근 커밋」은 없다. 새 메서드(예: `latestCommitForPath(path, branch)`, `GET /repos/{repo}/commits?path=...&sha=...&per_page=1`)를 더한다.
  - `jam-web/src/lib/admin/devBoard/constants.ts` — `GITHUB_REPO`, `STAGING_BRANCH`, `READ_MEMORY_MS`(60초), `GITHUB_TIMEOUT_MS`(10초), `GITHUB_TOKEN_ENV`(`GITHUB_READ_TOKEN`).
  - `jam-web/src/app/admin/ops-trends/page.tsx` — 출처와 레이더를 따로 읽는 `settle()` 패턴. 폴더 읽기도 같은 방식으로 격리한다.
  - `jam-web/src/lib/admin/opsTrends/sourceStore.ts` — `listTrendSources`(85행~)가 `lastReadAt`을 붙이는 곳.
  - `jam-web/src/components/admin/ops/trends/OpsTrendSources.tsx` — 표 위치 칸(214~220행).

## 배경 / 문제 정의

- 조각 B의 허용 폴더 검사는 문자열 목록 비교다. 폴더가 저장소에 실제로 있는지, 마지막으로 언제 채워졌는지는 화면에서 알 수 없다.
- 어드민 서버는 이미 개발 보드에서 GitHub API로 저장소를 읽는다(공개 저장소, 토큰이 있으면 시간당 5,000번, 없으면 60번). 읽기 모듈은 던지지 않고 `ReadResult`(`ok`·`missing`·`rate_limited`·`error`)를 돌려주며 같은 요청을 60초 기억한다.
- 루틴이 폴더를 읽는 데는 이 기능이 필요 없다(루틴은 GitHub에서 받은 staging을 이미 체크아웃해 실행한다). 이 기능은 사람이 화면에서 「이 출처가 낡았는지」를 보기 위한 것이다.

## 결정이 필요한 것 (착수 때)

- 서버에 `GITHUB_READ_TOKEN`이 설정돼 있는지 확인한다. 없으면 시간당 60번 한도에 걸리기 쉽다(개발 보드와 한도를 나눠 쓴다).
- 보이는 정보의 범위: 최근 갱신 일시만 / 폴더 존재 여부 / 최신 파일 이름까지.
- 읽기에 실패했을 때 표시: 빈 칸 / 「GitHub에서 읽지 못했어요」 한 줄.

## 완료 조건(안)

- 폴더 종류 출처 행에 폴더의 최근 갱신 일시(KST)가 보이고, 폴더가 없으면 「폴더를 찾지 못했어요」가 보인다.
- GitHub 읽기가 실패하거나 한도에 걸려도 출처 표와 레이더는 그대로 그려진다(구역 격리).
- 새 메서드와 표시 규칙에 단위 테스트가 있고 `scripts/verify.sh`가 통과한다.
