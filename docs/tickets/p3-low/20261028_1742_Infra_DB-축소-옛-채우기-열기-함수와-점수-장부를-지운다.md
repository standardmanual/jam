### 3회 정정 (2026-10-31, 민지 게이트 FAIL과 재작성)

- 민지가 SQL 검토에서 FAIL을 냈다. `capsule_open_counted`(새 흐름 함수)가 본문에서 `capsule_open`을 호출한다(301·302). 위 «확인한 사실»의 «다른 함수가 부르는 곳은 없다»가 틀렸다. 호출자 확인을 `chapter_add_score`·`capsule_fill`에만 하고 `capsule_open`은 하지 않았고, 첫 드라이런은 «함수가 존재하는가와 본문이 같은가»만 대조해서 이 결함을 잡지 못했다. 305를 적용했다면 캡슐 열기 전체가 «function does not exist»로 막힐 뻔했다. 실행 전이라 DB에는 아무 영향이 없었다.
- 카리나가 살아 있는 모든 함수 본문(`pg_proc.prosrc`)과 뷰를 전수 검색해 범위를 다시 정했다. 결과: `capsule_open`은 `capsule_open_counted`가 호출하고, `capsule_next_required`(옛 v1)는 `capsule_open`과 `capsule_get_or_create`가 호출하므로 둘 다 지우지 않는다. `capsule_get_or_create`도 바꾸지 않는다(그래서 «첫 캡슐 필요량이 바뀌는» 동작 변경도 사라졌다). `capsule_fill`은 `capsule_auto_fill`과 `jam_apply` 본문에 잼 원장 사유 문자열 `'capsule_fill'`로만 나오고 호출이 아니다.
- **최종 305의 지우는 것:** 함수 `capsule_fill`, `locked_item_fill`, `locked_item_open`, `jam_fill_decide`, `chapter_add_score`와 표 `chapter_score_events`(0건), `chapter_score_rules`(12건). 지우는 객체를 호출하는 살아 있는 함수·뷰는 0개다.
- 드라이런을 강화했다: 한 트랜잭션에서 ① 적용본·되돌림본 md5 대조 ② 적용 ③ 지운 객체 부재 ④ 지우지 않는 10개 함수의 본문·권한 불변 ⑤ 살아 있는 모든 함수 본문의 지운 함수 호출 전수 검사와 뷰 검사 ⑥ 새 흐름 함수 5개(`capsule_get_or_create`, `capsule_open_counted`, `capsule_auto_fill`, `capsule_claim_pending`, `capsule_hold_reward`)를 실제로 불러 «함수 없음» 오류가 없는지 시험 ⑦ 되돌림 ⑧ 지우기 전과 완전히 같은지 대조, 마지막에 예외로 전부 취소. 결과는 모두 이상 없음이었다.
- 후속으로 둘 것(U11 밖): `capsule_open_counted`를 `capsule_open`을 부르지 않는 자기완결형으로 다시 쓰면 `capsule_open`과 옛 v1을 지울 수 있다. 같은 때 `capsule_get_or_create`가 아직 옛 v1(옛 수동 채우기 값 90~220)로 첫 캡슐 필요량을 정하는 불일치(새 값은 145~365)도 바로잡을 수 있다. 챕터는 있는데 캡슐 행이 없는 유저에게만 영향이 있어 급하지 않다.

### 3회 기록 (2026-10-31, SQL 실행)

- 사용자가 «실행해»로 승인해 메인 세션(카리나)이 공용 DB에 `305_shrink_old_fill_open_and_score_ledger.sql`을 적용했다(`apply_migration`). 실행 직전 읽기 전용 점검에서 지울 함수 5개와 표 2개가 있었고 `chapter_score_events` 0건, `chapter_score_rules` 12건이었으며, 지우는 객체를 부르는 살아 있는 함수·뷰는 0개였다.
- 실행 직후 읽기 전용 확인: 지운 함수 5개와 표 2개가 0개 남았고, 지우지 않은 함수 10개(`capsule_open`, `capsule_next_required`, `capsule_next_required_v2`, `capsule_get_or_create`, `capsule_open_counted`, `capsule_auto_fill`, `capsule_claim_pending`, `capsule_hold_reward`, `locked_item_open_points`, `chapter_start`)가 모두 있다. 유저 8, 캡슐 2, 캡슐 열기 0건으로 실행 전과 같다.
- 생성 타입(`database.generated.ts`): MCP로 받은 최신 타입과 대조해 지운 표 2개(`chapter_score_events`, `chapter_score_rules`)와 함수 5개의 항목을 파일에서 걷었다. `npm run typecheck`가 통과한다. 대조 중에 이 파일이 실제 DB와 다른 곳이 더 보였지만 이번 변경과 무관하다고 보고 손대지 않았다: DB에만 있는 백업 표 `badge_point_backup_289`가 파일에 없다.
- 문서 정정: 「U11까지 남는다」·「U11 전까지」 문구를 실제 상태로 고쳤다(운영 로직 5곳, `현재 서비스 비교.md`, `BADGE_ENGINE_UNIFIED.md`, `02_DATA_MODEL.md` 여러 곳, `ADMIN_PRD.md`, 인벤토리 PRD). 지운 함수·표를 설명하던 옛 구간에는 「마이그레이션 305에서 지웠다」 표지를 붙였다. 칸 `unlock_required`·`unlock_filled`, `fill_amount`, `jam_policy.locked_min_*`는 남아 있어 문구를 「잠긴 개체 드랍 경로 결정(`20261030_0947`)이 정한다」로 바꿨다.
- 아직 확인하지 못한 것: 실제 동기화에서 캡슐 열기까지 끝에서 끝으로 한 시험(U12 점검 항목). 드라이런에서는 새 흐름 함수 5개를 직접 불러 「함수 없음」 오류가 없음만 확인했다.

### 완료 기록 (2026-10-31)

- 결과: 옛 채우기·열기 함수 4개(`capsule_fill`, `locked_item_fill`, `locked_item_open`, `jam_fill_decide`), `chapter_add_score`, 점수 표 2개가 공용 DB에서 사라졌다. 코드는 1·2회에서 이미 걷었고 staging에 배포돼 있었다. 프로덕션(main)이 대상 객체를 코드에서 쓰지 않는다는 것은 2026-10-31 `origin/main`의 `jam-web/src` 검색 0건으로 확인했다.
