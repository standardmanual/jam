## 회차 계획 (2026-10-31 카리나 확인과 분할)

### 확인한 사실 (읽기 전용, 공용 DB와 코드)
- 프로덕션 `main`은 이 티켓의 DB 객체(`capsule_*`, `chapter_*`, `locked_item_fill`, `user_capsules`, `user_chapters`, `chapter_ups`)를 코드에서 한 곳도 쓰지 않는다(`origin/main`의 `jam-web/src` 검색 0건). 그래서 DB를 지워도 프로덕션은 깨지지 않는다. 깨질 수 있는 쪽은 지금 staging 코드(`stage.j-a-m.app`)다. **코드를 먼저 정리해 staging에 배포한 뒤 SQL을 실행한다.**
- DB에 있는 대상: 함수 `capsule_fill`, `capsule_open`, `locked_item_fill`, `chapter_add_score`, `capsule_next_required`(옛 v1), 표 `chapter_score_events`(0건), `chapter_score_rules`(12건). 다른 함수가 `chapter_add_score`·`capsule_fill`을 부르는 곳은 없다. `capsule_next_required`(v1)는 `capsule_get_or_create`와 `capsule_open`이 부른다.
- **지우지 않는 것:** `capsule_open_counted`·`capsule_next_required_v2`·`capsule_get_or_create`·`capsule_auto_fill`·`capsule_claim_pending`·`capsule_hold_reward`와 표 `capsule_opens`·`user_capsules`·`user_chapters`·`chapter_ups`·`chapter_definitions`는 새 흐름이 쓴다.
- 코드 쪽 참조: 옛 API(`POST /api/capsule/fill`, `/open`, `/api/inventory/items/[itemId]/fill`), 클라이언트 `fillCapsuleRequest`·`openCapsuleRequest`·`runFill`·`runOpen`, `fillLockedItem`, 옛 `openCapsule` 비집계 경로(`capsule_open`과 `awardChapterScore('capsule_open')`), 점수 코드(`lib/chapter/score.ts`·`kinds.ts`·`failure.ts`), 어드민의 점수 규칙 편집(`components/admin/balance/ChapterSection.tsx`, `lib/admin/balance/chapter.ts`)과 사용자 상세의 점수 기록(`lib/admin/user-chapter-view.ts`), 정책 카드와 밸런스 대시보드.
- 이 소식은 입력(상위 D8, 사용자 결정): 점수 장부는 쓰기를 멈췄다가 삭제한다. 배지 받기 점수는 이미 서비스 활동 잼(`awardServiceJam`)으로 바뀌었다. 점수 장부에 남은 호출부는 옛 비집계 열기뿐이다.

### 1회 (api, 코드): 캡슐·잠긴 아이템의 옛 채우기·열기를 코드에서 걷어낸다
- 삭제: `app/api/capsule/fill/`, `app/api/capsule/open/`, `app/api/inventory/items/[itemId]/fill/`(각 `__tests__` 포함). 각 라우트를 부르는 곳이 없는지 먼저 확인한다.
- 정리: `lib/capsule/capsule-client.ts`(`fillCapsuleRequest`, `openCapsuleRequest`), `capsule-flow.ts`(`runFill`, `runOpen`), `capsule.ts`(`fillCapsule`과 그 계약 타입), `open.ts`(비집계 경로: RPC `capsule_open`과 `awardChapterScore` 호출을 걷고 집계 경로만 남긴다), `lib/inventory/lockedItemFill.ts`와 `lockedItemFill-contract.ts`(`fillLockedItem`과 채우기 거절 코드, 열기와 상태 읽기는 둔다), `lib/jam/jam-fill.ts`(쓰는 곳이 없어지면 삭제).
- 삭제: `components/jam/JamBalance.tsx`와 `lib/capsule/__tests__/capsule-boundary.test.ts`의 해당 항목.
- `lib/i18n/ko.ts`: 고아가 된 키(`d.capsule.sheet.*`, `pill.*`, `aria.ready/noSlots`, 채우기·옛 잠긴 아이템 채우기 문구)를 `grep`으로 가려 지운다. `BadgeRevealOverlay`의 `RevealBadge.unlockRequired`가 더는 쓰이지 않으면 함께 정리한다.
- DB는 건드리지 않는다. 생성 타입(`database.generated.ts`)도 이 회차에서는 그대로다. 문서(운영 로직 구현 상태, PRD)에서 «옛 API가 서버에 남아 있다»는 줄은 삭제 사실로 고친다.

### 2회 (service, 코드와 어드민): 점수 장부 코드와 어드민 화면을 걷어낸다
- `lib/chapter/score.ts`·`kinds.ts`·`failure.ts` 중 호출부가 없어진 것을 삭제하고, `chapter_score_events`·`chapter_score_rules`를 읽는 어드민 코드(`components/admin/balance/ChapterSection.tsx`, `lib/admin/balance/chapter.ts`, `lib/admin/user-chapter-view.ts`)와 정책 카드(`policiesData.ts`의 `dbTable: 'chapter_score_rules'` 카드), 밸런스 대시보드의 점수 항목을 걷거나 바꾼다. 챕터 정의·챕터 횟수·오름 기록은 남는다. 어드민 화면은 MODULAR 제외 대상이라 채원 판정이 필요 없다.
- `user_chapters.total_score` 컬럼은 이번에 지우지 않는다(프로필 «다음 챕터까지»가 읽고 있어 후속 티켓 `20261030_1738`이 기준을 정한 뒤에 다룬다).

### 3회 (db): 코드가 staging에 배포된 뒤 SQL을 쓰고 실행한다
- 순서: 1·2회를 staging에 push하고 Vercel이 READY가 된 것을 확인한 뒤에 시작한다.
- SQL 파일과 되돌림 SQL을 `jam-web/supabase/migrations/`에 둔다. 대상: `capsule_fill`, `capsule_open`, `locked_item_fill`, `chapter_add_score`, `chapter_score_events`, `chapter_score_rules`. `capsule_next_required`(v1)는 `capsule_get_or_create`가 부르므로 v1과 v2의 본문을 비교해 같은 값을 돌려주면 `capsule_get_or_create`를 v2로 바꾸고 지운다. 다르면 지우지 않고 사유를 적는다.
- 실행 전 읽기 전용으로 행 수를 다시 센다, `DO` 블록 롤백으로 드라이런과 되돌림을 실측한다(되돌림이 실제로 원상 복구하는지), 생성 타입을 MCP로 받아 대조해 같은 커밋에 넣는다. **실행 전에 사용자 확인을 받는다**(상위 티켓 지침).
- 실행 뒤 읽기 전용 질의로 새 함수만 남은 것을 확인하고 사용자에게 보고한다.
