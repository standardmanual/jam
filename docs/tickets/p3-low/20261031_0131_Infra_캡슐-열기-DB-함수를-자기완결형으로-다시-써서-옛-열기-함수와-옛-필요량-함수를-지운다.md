# [Infra] 캡슐 열기 DB 함수를 자기완결형으로 다시 써서 옛 열기 함수(capsule_open)와 옛 필요량 함수(capsule_next_required)를 지운다

## 핵심 요약

- 요구사항: 새 흐름 함수 `capsule_open_counted`가 본문에서 옛 `capsule_open`을 호출하고, `capsule_open`과 `capsule_get_or_create`가 옛 `capsule_next_required`(v1)를 호출한다. 그래서 U11(`20261028_1742`)이 이 둘을 지우지 못했다. `capsule_open_counted`를 다른 옛 함수를 부르지 않는 자기완결형으로 다시 쓴 뒤 `capsule_open`과 `capsule_next_required`(v1)를 지운다.
- 같이 바로잡을 것: `capsule_get_or_create`가 캡슐 행이 없는 유저의 첫 캡슐 필요량을 옛 v1(`capsule_chapter_costs.fill_amount` 90~220)로 정한다. 새 흐름 값은 v2(`fill_amount_v2` 145~365)다. 챕터는 있는데 캡슐 행이 아직 없는 유저에게만 영향이 있어 급하지 않다. 이때 `capsule_get_or_create`를 v2로 바꾼다.
- 관련 파일: `jam-web/supabase/migrations/301_capsule_auto_fill.sql`(190행 근처 초판), `302_capsule_pending_forfeit.sql`(308행 근처 현행 `capsule_open_counted`), `305_shrink_old_fill_open_and_score_ledger.sql`(U11이 남긴 이유 주석), `docs/tickets/p3-low/20261028_1742_Infra_*.md`의 «3회 정정». 줄 위치는 아현이 확인한다.

## 배경 / 문제 정의

U11 3회 SQL 검토(민지)에서 `capsule_open_counted`가 `v_open := public.capsule_open(p_user_id, p_items);`를 호출한다는 사실이 드러났다. 코드는 1회에서 비집계 경로를 걷어 `capsule_open_counted`만 부르지만 DB 안에서는 옛 함수가 아직 살아 있는 의존이다. 이 티켓은 그 의존을 끊어 옛 함수를 지운다. 옛 `capsule_open`은 챕터 횟수·알림 단계 처리가 없는 옛 열기라 새 함수가 그 위에 덧입혀 있다.

## 상세 요구사항

- `capsule_open_counted`의 새 본문은 `capsule_open`이 하던 일(정지 확인, 인벤토리 빈칸 확인, 개체 지급, 열기 기록, 다음 캡슐 필요량)을 안에 가지고, 지금 동작(챕터 횟수 세기, 오름, 알림 단계 0, 다음 필요량 v2)을 그대로 지킨다. 새 본문은 옛 본문과 입출력이 같다는 것을 같은 입력의 비교 시험(롤백 드라이런)으로 확인한다.
- 실행 전에 `db-migration-rules.md` 5절을 따른다: 지우는 객체의 호출을 살아 있는 모든 함수 본문·뷰에서 전수 검색하고, 새 흐름 함수를 실제로 불러 «함수 없음» 오류가 없는지 시험한다.

## 완료 조건

- `capsule_open_counted`가 `capsule_open`·`capsule_next_required`(v1)를 부르지 않는다.
- `capsule_open`과 `capsule_next_required`(v1)가 DB에서 지워졌고, `capsule_get_or_create`가 v2로 필요량을 정한다.
- SQL·되돌림 SQL·드라이런 기록이 티켓에 있고 실행 전에 사용자 확인을 받았다. 실행 뒤 생성 타입을 재생성해 같은 커밋에 넣었다.
