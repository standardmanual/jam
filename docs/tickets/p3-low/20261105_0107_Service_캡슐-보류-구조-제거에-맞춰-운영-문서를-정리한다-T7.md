# [Service] 캡슐 보류 구조 제거에 맞춰 운영 문서와 정책 대시보드를 정리한다 (T7)

## 핵심 요약

- 요구사항: 보류·받기·소멸 설명을 «막힘» 규칙으로 바꾼 문서를 마무리한다. 각 하위 티켓이 자기 항목을 같은 커밋에서 바꾸므로, 이 티켓은 남은 잔여를 정리한다.
- 구현 계획: 아래 문서를 장별로 나눠 갱신한다.
- 관련 파일: `docs/plan/jam2/10 JAM 2.0 서비스 운영 로직.md`(5.2절 «보류와 받기»·«잼 소멸»·«알림 단계»와 결정 기록 교체, 425줄 «쉬어도 잃지 않는다» 예외 삭제, 433·474·477줄, 500·504줄, 611~613줄, 702·703·710줄, 1331~1336줄, 1656~1663줄, 1713·1714줄, 1830줄), `docs/service/prd/notification/PRD.md` 53·54번과 구현 상태 문단, `docs/service/prd/inventory/PRD.md` 137줄, `docs/service/prd/02_DATA_MODEL.md`(`capsule_pending_rewards`·`alert_stage` 기술 24건), `docs/service/writing/UX_WRITING_GUIDELINE.md` 「캡슐 위젯 안내 문구」, `docs/plan/jam2/service-redesign/현재 서비스 비교.md`, `jam-web/src/lib/admin/policyDashboard/policiesData.ts`와 `policiesData.test.ts`

## 배경 / 문제 정의

규칙이 «보관 2개·소멸»에서 «막힘·정리하면 이어짐»으로 바뀌었고, 같은 설명이 여러 문서에 흩어져 있다. 중복은 드리프트의 필요조건이므로 단일 원천(운영 로직 5.2절)을 두고 나머지는 참조만 한다.

## 상세 요구사항

- 신설 문장: 막힘 판정(캡슐 가득 그리고 빈칸 < 필요 칸수), 입구 차단, 서비스 활동 잼 차단, 열어 두는 행동(믹스·정리), 풀림, 보류 고르기(6.4)와의 관계.
- 인벤토리 PRD 137줄 «꽉 차도 동기화는 된다»를 «캡슐도 가득일 때는 멈춘다» 예외로 고친다.
- 이용 정지(정산 안 함)와 이번 차단(풀린 뒤 정산)이 다르다는 점을 분명히 적는다.
- 챕터 횟수 규칙(«열기 못 해도 센다»)은 유지한다.

## 구현 계획

장별로 분할한다(문서 위주, 파일 5개 초과 가능). 새 환경 주장은 `docs/agents/contract.json` 검사 줄이 필요한지 확인한다.

## 완료 기록

> 상위 티켓 Q10 개정(2026-11-05)으로 구조가 «막힘만 걸고 보류를 걷는다»에서 «먼저 추첨한 대기 보상 + 자동 지급»으로 바뀌었다. 위 요구사항의 «막힘 판정(캡슐 가득 그리고 빈칸 < 필요 칸수)»은 «대기 보상이 있음»으로 바뀌었고, `capsule_pending_rewards` 0건 조건은 적용하지 않는다(표를 다시 쓴다).

- 각 하위 티켓(R1~R3, T5)이 자기 항목을 같은 커밋에서 고쳤고, 이 티켓에서 남은 낡은 서술을 정리했다.
