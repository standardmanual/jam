# [UI] 잠긴 아이템 배지 상세를 일반 아이템 배지 상세의 카드와 행으로 맞춘다

## 핵심 요약

- 요구사항(사용자 지시, 2026-11-09): 잠긴 아이템 배지 상세 페이지를 일반 아이템 배지 상세 페이지의 컴포넌트를 활용해, 칩·설명·이름 같은 비슷한 내용끼리 맞춰 바꾼다.
- 구현 계획: 잠긴 상세(`LockedItemDetail`)가 직접 그리던 이미지·칩·제목·설명을 일반 상세의 `BadgeHeroSection`으로 바꾸고, 일련번호·얻은 날·컬렉션도 일반 상세와 같은 자리와 같은 부품(`ItemSerialCode` 블록, `Card` + `ListRow` 행)으로 맞춘다.
- 관련 파일: `jam-web/src/app/(main)/inventory/[itemId]/LockedItemDetail.tsx`, `jam-web/src/app/(main)/badges/[id]/BadgeHeroSection.tsx`(선택 슬롯 4개 추가), `jam-web/src/lib/i18n/ko.ts`(`lockedItem.detail.obtainedBy`), 시험 `inventory/[itemId]/__tests__/LockedItemDetail.test.tsx`.
- 담당 에이전트: 오케스트레이터.

## 완료 조건

- 잠긴 상세의 대표 이미지(잠금 타일)·등급 칩·«잠김» 칩·이름·설명이 일반 상세와 같은 카드 안에 있다.
- 열기 전후의 전환(타일 → 그림 크로스페이드, 이름·설명 교체, «잠김» 칩 사라짐)과 포인트 블록·열기 버튼의 동작은 그대로다.

  | 컬렉션(열린 뒤) | «컬렉션 이름» 문장 | 타일 lead + 이름 + 쉐브론 `ListRow`, 컬렉션 상세로 연결 |
  | 카드와 아래 영역 간격 | 따로 정함 | 20px(`gap-5`) |

- **공용 카드 확장**: `BadgeHeroSection`에 선택 슬롯 네 개를 더했다: `imageSlot`(대표 이미지 자리), `chipExtra`(등급 칩 옆 칩), `titleNode`, `descriptionNode`. 기본값이 없으면 기존 마크업 그대로라 활동·체크인·아이템 배지 상세와 어드민 미리보기는 달라지지 않는다(시험 119건, 전체 14,719건 통과). 열기 전후의 전환은 슬롯 안에서 그대로 한다(타일과 그림의 크로스페이드, `SwapText`).
- **그대로 둔 것**: 포인트 블록(필요·가진 포인트, 모자람 안내, 접힘 전환), 열기 버튼·열린 뒤 링크, 트라이브·낸 포인트·받은 포인트 문장, 서버가 내리는 값(배지 id·이름·그림·설명은 열기 전에 내리지 않는다). 문구 규칙(«획득»·«잠금» 금지)도 그대로이고 새 라벨은 «얻은 경로»다.
- **같이 바뀐 시험**: 컬렉션 행은 이름만 보이고 `/collections/{id}`로 이어진다는 기대로 고쳤다. `ListRow`가 자기 CSS를 `<style>`로 함께 그려서 마크업 검사가 CSS 글자(`var(--link)`, `%`)까지 보지 않게 `<style>`을 빼고 검사한다. 일반 상세와 같은 구성을 고정하는 시험 6건을 더했다.
- **검증**: eslint, `tsc --noEmit`, `ds:check`(오류 0), 슬롭 검사 통과. 실렌더에서 잠긴 개체(열기 전)가 일반 상세와 같은 흰 카드(잠금 타일, «잠김» 칩, «잠긴 아이템 배지», 설명), 포인트 블록, 얻은 날·경로 카드, 열기 버튼으로 보이는 것을 확인하고 스크린샷으로 봤다.
- **확인하지 못한 것**: 열린 뒤 화면의 실렌더. 열기는 사용자 포인트를 쓰는 동작이라 확인용으로 열지 않았다. 열린 뒤는 시험(일련번호 위치, 이름 교체, 등급 칩, 컬렉션 행, 문장 순서)으로만 확인했다. 열릴 때 크로스페이드가 새 카드에서 자연스럽게 보이는지도 보지 못했다. 등급이 있는 잠긴 개체의 등급 칩과 «잠김» 칩이 나란한 모습도 이 계정의 잠긴 개체(등급 없음)로는 보지 못했다.
- **후속(2026-11-09, 사용자 지시)**: ① 필요 포인트를 방금 고친 포인트 보상 카드처럼 바꾼다. ② 얻은 날·경로 같은 표현을 다른 배지 상세에 맞춘다. 필요 포인트는 `ListRow tone="tint"` + 서클 코인 lead + `tPoint('{points} 포인트 필요')`로, 가진 포인트는 같은 행의 보조 줄(`가진 포인트 {balance}`)로 두었다(필요 포인트가 0이면 «포인트 없이 열 수 있어요» 한 줄을 같은 행 모양으로, 모르면(null) 블록 없음, 모자라면 행 아래 `InlineNotice`). 획득 정보는 다른 배지 상세의 카드와 같은 문구(`badges.earnInfoTitle`·`badges.earnedAt`)와 새 라벨 `badges.earnRoute`(«획득 경로»)를 쓴다. 이전 키 `lockedItem.detail.obtainedAt`·`obtainedBy`와 `points.required`·`points.balance`는 지웠다.
- **문구 규칙과 부딪히는 점(판단 필요)**: 잠긴 상세에는 «열기는 획득이 아니다(운영 로직 7.2절)»는 이유로 화면의 «획득» 문구를 쓰지 않는 규칙이 있었다. 사용자가 다른 배지 상세와 같은 표현으로 맞추라고 해 «획득 정보»·«획득 일시»·«획득 경로»를 이 카드의 라벨에 썼다. 이 라벨은 개체를 받은 시점과 경로를 말하는 것이지 «열기»를 획득이라 부르는 것이 아니다. 시험은 이 세 라벨을 뺀 나머지 화면과 소스에 «획득»·«잠금»이 없음을 계속 확인한다. 이 규칙을 되돌리길 원하면 `earnInfoTitle` 대신 잠긴 상세 전용 라벨(예: «얻은 날»)로 돌릴 수 있다.
- **후속 검증**: eslint, `tsc --noEmit`, `ds:check`(오류 0), 슬롭 검사, 관련 시험 14,719건 통과. 실렌더에서 필요 포인트 행(회색 tint 행, 서클, 오렌지 «50 포인트» + «필요», «가진 포인트 1,270»)과 획득 정보 카드(획득 일시 «2026년 11월 6일 오전 10시 11분», 획득 경로 «활동 드랍»)를 확인하고 스크린샷으로 봤다. 포인트가 모자란 상태와 열린 뒤 화면은 실렌더로 보지 못했다(시험으로만 확인).
- **후속(2026-11-09, 사용자 결정과 지시)**: ① «열기는 유저 UI 행위라 획득과 다른 개념»이므로 «획득»을 써도 된다. 필요하면 규칙도 고친다. ② 획득 경로는 «활동 드랍» 대신 더 분명하게(예: 캡슐 열기 보상, 미션 보상, 체크인 픽업) 보인다.
- **획득 문구 규칙 수정**: 이전 규칙은 «열기는 획득이 아니다»를 이유로 잠긴 상세 화면 전체에서 «획득»·«얻었어요»를 막았다. 바꾼 규칙: 열기 동작의 문구(버튼·토스트·안내·포인트 문장)에는 «획득»·«얻었어요»를 쓰지 않고, 개체를 받은 일시·경로를 말하는 카드는 다른 배지 상세와 같은 «획득 정보»·«획득 일시»·«획득 경로»를 쓴다. UX Writing 가이드 «열기» 용어 행, `ko.ts`의 `lockedItem.detail` 주석, `LockedItemDetail` 설명 주석을 고쳤다. 시험은 «잠금» 금지(고정 용어는 «잠김»)와 열기 문구의 «획득» 금지를 계속 확인하고, 획득 정보 카드의 표현은 새로 확인한다. 공통 용어 문서의 «받는 것은 획득, 드러내는 것은 열기»와 같은 뜻이라 그 문서는 그대로다.
- **획득 경로 문구**: 이전 «활동 드랍»은 불명확했을 뿐 아니라 **틀린 값이었다.** 확인한 이 계정의 잠긴 개체는 `obtained_by`가 `drop`이지만 발급 기록의 경로가 `capsule`(캡슐 열기 보상)이었다. 캡슐에서 나온 개체도 `obtained_by`가 `drop`이라 `obtained_by`만 보고는 활동 드랍과 가를 수 없다. 그래서 서버 페이지가 발급 기록(`item_issue_log.route`)의 경로 값 하나를 읽어 `issueRoute`로 내려보내고(조회가 실패해도 `obtained_by`만으로 그린다), `resolveObtainRoute`가 경로를 정한다. 경로와 문구: 캡슐 → «캡슐 열기 보상», 활동 동기화(`sync`, 또는 `obtained_by`가 `drop`) → «활동 동기화 드랍», `pickup`·`ambient_drop` → «체크인 픽업», `drop_event` → «이벤트 드랍», 그 밖 → «시스템 지급». 실렌더에서 이 개체의 획득 경로가 «활동 드랍»에서 «캡슐 열기 보상»으로 바뀐 것을 확인했다.
- **«미션 보상»은 지금 구분하지 못한다(데이터 한계)**: 미션 보상으로 받은 개체는 발급 기록(`item_issue_log`)에도 `obtained_by`에도 따로 구분되는 값이 없다. 발급 기록의 경로는 현재 `capsule`과 `sync` 둘뿐이다. 그래서 미션 보상으로 받은 개체는 지금 «시스템 지급» 등으로 보인다. 미션 보상 경로를 구분하려면 미션 보상이 개체를 줄 때 발급 기록에 경로 값을 남기게 하는 변경이 먼저 필요하다(별도 작업). 값이 생기면 `resolveObtainRoute`에 한 줄과 문구 키 하나를 더하면 된다. 또 «체크인 픽업»은 `pickup`과 지점에 놓인 시스템 드랍(`ambient_drop`)을 함께 가리킨다고 판단했는데, `ambient_drop`을 주운 개체가 모두 체크인으로 주운 것인지는 코드로 확인하지 못했다.
- **후속 검증**: eslint, `tsc --noEmit`, `ds:check`(오류 0), 슬롭 검사, 관련 시험 14,731건 통과(경로 해석 시험 신규, 서버 페이지 시험에 발급 경로 전달과 조회 실패 경우 추가, 경로 문구 3건 추가).
- **후속(2026-11-09, 사용자 지시)**: 화면 문구 «가진 포인트»를 «보유 포인트»로 바꿨다. 잠긴 상세의 보조 줄(`lockedItem.detail.points.balanceLine`: «보유 포인트 {balance}»), 정책 대시보드의 같은 화면 설명, 인벤토리 PRD의 화면 서술, 시험을 함께 고쳤다. 코드 안 변수·응답 필드명(`pointBalance`, `balance`)과 온보딩 퀘스트 등 다른 화면의 주석·시험 설명에 남은 «가진 포인트»는 사용자에게 보이는 문구가 아니라 손대지 않았다.
- **PRD 갱신**: 인벤토리 PRD의 «잠긴 아이템 배지 화면» 절을 실제 화면(일반 상세와 같은 히어로 카드, 포인트 행, 획득 정보 카드, 획득 경로 규칙, 열기와 획득의 용어 구분)에 맞게 고쳤다.
