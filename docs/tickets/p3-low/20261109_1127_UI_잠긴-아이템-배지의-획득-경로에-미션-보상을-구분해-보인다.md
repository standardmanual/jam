# [UI] 잠긴 아이템 배지의 획득 경로에 미션 보상을 구분해 보인다

## 핵심 요약

- 요구사항(사용자 지시, 2026-11-09): 잠긴 아이템 배지 상세의 «획득 경로» 줄이 받은 경로를 미션 보상, 캡슐 열기 보상, 체크인 픽업 등으로 구분해 보인다. 캡슐·활동 동기화·체크인 픽업·이벤트는 직전 티켓 `20261109_1048`에서 이미 구분한다. 남은 것은 **미션 보상**이다(지금은 «시스템 지급»으로 보인다).
- 구현 계획: 미션 보상으로 받은 개체는 `mission_item_rewards.inventory_item_id`에 개체 id가 남는다(DB 변경 없음). 서버 페이지가 이 표에 그 개체 행이 있는지 하나만 읽어 `missionReward: boolean`으로 내려보내고, `resolveObtainRoute`가 새 경로 키 `mission`(«미션 보상»)을 돌려준다.
- 관련 파일(지도):
  1. `jam-web/src/lib/inventory/obtainRoute.ts` — `ObtainRouteKey`에 `'mission'` 추가, `resolveObtainRoute(obtainedBy, issueRoute, missionReward = false)`로 세 번째 인자 추가. 판정 순서: 발급 기록 `capsule` → `sync` → **`missionReward`이면 `mission`** → `obtained_by` 판정(지금 그대로). 파일 머리 주석의 «미션 보상은 가르지 못한다» 문단을 «`mission_item_rewards`로 가른다»로 고친다.
  2. `jam-web/src/lib/inventory/__tests__/obtainRoute.test.ts` — `mission` 경우(`system_event` + `missionReward: true` → `mission`), 발급 기록이 있으면 발급 기록이 앞선다는 경우, 기본값 false면 지금과 같다는 경우를 더한다.
  3. `jam-web/src/app/(main)/inventory/[itemId]/page.tsx` 57~68줄(발급 기록 조회) 바로 뒤 — `service.from('mission_item_rewards').select('id').eq('inventory_item_id', itemId).limit(1).maybeSingle()`. 오류는 `console.error`만 하고 false로 둔다(발급 기록 조회와 같은 방식). `LockedItemDetail`에 `missionReward` prop을 넘긴다(80줄 근처).
  4. `jam-web/src/app/(main)/inventory/[itemId]/__tests__/page.test.tsx` 145줄(prop 키 목록)에 `missionReward` 추가, 미션 보상 행이 있을 때 true·조회 실패 때 false인 경우를 더한다. 목(mock)이 `from(table)`을 표 이름으로 가르도록 고친다.
  5. `jam-web/src/app/(main)/inventory/[itemId]/LockedItemDetail.tsx` — props 타입 55줄 근처에 `missionReward?: boolean`(기본 false), `OBTAIN_ROUTE_LABEL`(59~65줄)에 `mission: d.inventory.obtainByMission`, 242줄 `resolveObtainRoute(obtainedBy, issueRoute, missionReward)`.
  6. `jam-web/src/app/(main)/inventory/[itemId]/__tests__/LockedItemDetail.test.tsx` 446줄 근처 — `missionReward: true`면 «획득 경로 미션 보상»이 보이는 경우 하나.
  7. `jam-web/src/lib/i18n/ko.ts` 631~636줄(`obtainBy*`) — `obtainByMission: '미션 보상'` 추가.
  8. `docs/service/prd/inventory/PRD.md` 237줄 — 경로 목록에 «미션 보상(`mission_item_rewards`에 개체가 있으면)»을 발급 기록 다음 순서로 더한다.
- 예상 규모: 파일 8개, 추가+삭제 약 60~90줄.

## 배경 / 문제 정의

- 미션 보상 지급 함수(`mission_grant_item_rewards`·`mission_claim_item_rewards`, 마이그레이션 250)는 `obtained_by`에 `system_event`를 넣고 `item_issue_log`에는 쓰지 않는다. 그래서 지금 «시스템 지급»으로 보인다.
- 두 함수 모두 받은 개체를 `mission_item_rewards`의 `claimed` 행에 `inventory_item_id`로 남긴다(DB 함수 정의로 확인, 2026-11-09). 이 표만 읽으면 DB를 바꾸지 않고 가를 수 있다.
- 2026-11-09 기준 `mission_item_rewards`에 개체가 연결된 행은 0건이다. 그래서 실렌더로는 볼 수 없고 시험으로만 확인한다.

## 상세 요구사항

### 서비스/코드베이스 관점
- 서버 페이지가 내려보내는 값은 boolean 하나다. 미션 id·이름은 내리지 않는다(열기 전 화면의 값 제한과 같다).
- `mission_item_rewards`는 service_role만 읽는다. 페이지는 이미 `service` 클라이언트를 쓴다.
- 조회 실패는 화면을 막지 않는다(경로 줄의 정확도만 낮아진다).

### UI/UX 관점
- 화면 모양은 바뀌지 않는다. «획득 경로» 행의 값 문구만 «미션 보상»이 될 수 있다.

## 범위 밖(이번 티켓에서 하지 않음)

- **믹스 결과**: 믹스로 바로 받은 개체(`combine_grant_results`)는 `obtained_by = system_event`이고 발급 기록·보상 기록 어디에도 개체 id가 남지 않는다(빈칸이 모자라 보류됐다 받은 경우만 `combine_pending_results`에 남는다). 구분하려면 DB 함수를 고쳐 기록을 남겨야 하므로 별도 티켓으로 둔다.

## 완료 조건

- 미션 보상으로 받은 잠긴 개체의 «획득 경로»가 «미션 보상»이다.
- 캡슐·활동 동기화·체크인 픽업·이벤트·시스템 지급의 판정은 지금과 같다(기존 시험 통과).
- `scripts/verify.sh` 통과.

## 완료 기록

- **결과**: 미션 보상으로 받은 개체(`mission_item_rewards`에 `inventory_item_id`가 같은 행이 있는 개체)의 «획득 경로»가 «미션 보상»으로 보인다. 판정 순서는 발급 기록(`capsule` → `sync`) → 미션 보상 → `obtained_by`다. 서버 페이지는 boolean 하나(`missionReward`)만 내리고 미션 id·이름은 내리지 않는다. 조회가 실패하면 `console.error`를 남기고 false로 둔다. DB 변경은 없다.
