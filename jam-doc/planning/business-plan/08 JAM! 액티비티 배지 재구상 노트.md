# JAM! 액티비티 배지 재구상 노트

> **구상 단계 문서다.** 사용자가 "생각이 완성됐다"고 선언하기 전까지 코드·DB·티켓·다른 문서에
> 반영하지 않는다. 에이전트는 이 문서를 현재 서비스 사실의 근거로 쓰지 않는다.
> 대화 일자: 2026-10-06(KST). 이 노트는 그날의 대화를 다음 세션으로 넘기기 위한 기록이다.

## 1. 출발점

사용자가 던진 질문은 일곱 가지였다. 기존 액티비티 배지 원칙은 참고만 하고 새로 생각하기로 했다.

1. 액티비티 종목 카테고리가 필요한가
2. 종목이 있어서 거리·누적·시간·속도 같은 불확실한 값에 의존하게 되는 것이 아닌가
3. 활동 속성을 직접 드러내지 않고 '활성에너지' 같은 가상 지표로 바꿔 배지를 발급하면 어떤가
4. "어떤 운동을 했는가"에서 삶의 '활동'으로 관점을 옮기면 타겟 유저가 넓어지지 않는가
5. 학생으로 치면 과목별 점수나 석차 같은 1차원 평가가 아니라, 공부라는 근원적 행동과 학생으로서의
   가치를 보는 편이 낫지 않은가
6. 만보계 수준이던 활동을 가상 컨텐츠를 소비하는 또 하나의 재미 축으로 바꾸면 어떤가
7. 그렇다면 어떤 배지를 만들고 발급해야 하는가

## 2. 확정한 것

| # | 결정 | 이유·메모 |
|---|---|---|
| 1 | 현재 생성된 액티비티 배지(630종)는 고려하지 않고 백지에서 설계한다 | 이관·유지 논의를 하지 않는다 |
| 2 | 거리·페이스 같은 운동형 배지를 없애고, 시간과 강도 환산값을 기준으로 하는 비운동형 배지로 간다 | 성적표가 아니라 생활기록부(5절) |
| 3 | 동기화한 활동을 평가해 **활성에너지(가칭)** 를 지급한다 | 종목과 무관한 단일 지표 |
| 4 | 기본 루프: 동기화 → 활동 평가 → 에너지 + 비운동형 배지 + 아이템 배지 + 체크인 배지 | 아이템 배지는 지금과 같은 방식·비율로 바로 지급한다 |
| 5 | 에너지는 **쓰는 자원**이고, 쓸 곳을 유저가 **한 곳씩** 고른다 | 한 번 움직임이 여러 축에 동시에 반영되면 보상이 너무 쉬워진다. 운동형 배지가 빠져 배지 양이 줄어드는 것과 균형을 맞춘다 |
| 6 | 에너지를 쓸 곳: **원정**(에너지를 투자해 돌리는 가챠형 사이드 루프), **봉인 열기** | 원정은 언제나 쓸 수 있고, 봉인 열기는 봉인 아이템을 가졌을 때만 쓸 수 있다 |
| 7 | 봉인은 일반 규칙이 아니다. **아이템 배지를 만들 때 붙일 수 있는 선택 속성**이다 | 운영자가 시즌 상자·트라이브 유물 같은 특별 컨텐츠를 만드는 도구가 된다 |
| 8 | 에너지를 **어디에 썼는지가 트라이브 관계를 키우고**, 관계가 '나의 위치'가 된다 | "무엇을 골랐는가"가 "나는 어떤 사람인가"가 된다 |
| 9 | 체크인, 드랍/픽업, 아이템 수집(컬렉션)은 유지한다 | |
| 10 | 봉인 아이템을 열지 않은 채 POI에 놓는 '봉인째 드랍'은 하지 않는다 | 봉인 아이템은 연 뒤에만 드랍할 수 있다 |
| 11 | 연동 소스를 Strava 외에 애플헬스·구글·가민으로 넓히되, **한 번에 하나만** 연동한다 | 방향만 정했다. 세부 규칙은 4절 |
| 12 | 트라이브의 현재 스토리는 사용자가 다시 검토한다 | 8절 브리프 |

## 3. 구조 한눈에 보기

```
[기본 루프 · 동기화할 때마다 · 자동]
동기화 → 활동 평가 → ① 에너지  ② 비운동형 배지  ③ 아이템 배지(지금과 같은 비율)  ④ 체크인 배지

[선택 · 유저가 에너지를 쓸 곳을 한 곳 고름]
에너지 ─┬→ 원정 보내기   변동 보상(가챠) · 며칠 뒤 귀환 · 상시 가능
        └→ 봉인 열기     확정 보상 · 바로 · 봉인 아이템이 있을 때만

[나의 위치 · 장기]
에너지를 쓴 곳 → 트라이브 관계 → 관계 지도와 칭호

[유지]
체크인 · 드랍/픽업 · 컬렉션 · 믹스
```

유저에게 보이는 층은 세 가지로 정리했다.

| 층 | 유저가 하는 일 | 한 문장 |
|---|---|---|
| 핵심 | 움직이고, 에너지를 쓸 곳을 고른다 | "움직이면 에너지가 생기고, 어디에 쓰느냐가 나를 만든다." |
| 저절로 따라오는 것 | 없음(보기만 함) | 관계 지도, 결 기록, 주간 리듬 상자 |
| 골라서 하는 것 | 원할 때만 | 체크인, 드랍/픽업, 컬렉션·믹스 |

## 4. 정하지 않은 것과 추천안

대화에서 제안했지만 사용자가 아직 확정하지 않은 항목이다.

### 4.1 에너지

| 항목 | 추천안 |
|---|---|
| 환산 방식 | 종목별 고정 강도 계수(MET) × 실제로 움직인 시간. 속도는 보상에 쓰지 않고 검증에만 쓴다(예: '달리기'로 올렸는데 걷는 속도면 걷기 계수 적용) |
| 대안 | 속도에 따라 계수를 올리는 방식(페이스가 숨은 보상으로 돌아옴), 심박 기반(측정 기기가 없는 유저가 불리함) |
| 주간 기준 | 주 600 MET-분. 세계보건기구 권장 신체활동량(주 150분 중강도)에 해당한다 |
| 인정 활동 최소 기준 | 에너지 30 이상(빠른 걷기 약 10분, 요가 약 12분). 1분짜리 기록으로 횟수를 채우는 것을 막는다 |
| 시간 기준과 에너지 기준 | 리듬·시간대·요일·연속·달력 성격의 배지는 '인정 활동이 있었는가'만 본다. 누적·기록 성격은 에너지를 본다. 강도 계수가 낮은 종목(요가 약 2.5)이 불리해지지 않게 하려는 것이다 |
| 표시 | 현재 잔액만 보여 준다. 누적 에너지와 유저 간 순위는 보여 주지 않는다. 잔액 상한은 두지 않는다 |
| 구매 | 돈으로 에너지를 살 수 없다 |
| 포인트와의 관계 | 둘 다 '사이드에서 쓰는 자원'이라 역할이 겹친다. 하나로 합치는 방향을 검토한다 |

### 4.2 원정 (다음에 정할 1순위)

원정은 에너지를 언제나 쓸 수 있는 유일한 곳이어서 경제의 중심이다.

| 항목 | 추천안 |
|---|---|
| 고르는 것 | 어느 트라이브 영역으로 보낼지. 이 선택이 관계로 쌓인다 |
| 귀환 | 1~3일 뒤. 쉬는 동안에도 돌아와 있다(복귀할 이유가 되고, 벌이 없다) |
| 보상 | 변동 보상. 확률을 공개하고 천장을 둔다(예: 10회 안에 희귀 등급 1회 확정) |
| 고르기 부담 | 가볍게 쓰는 유저를 위한 기본값이 필요하다(예: 마지막으로 고른 영역으로 자동 원정) |
| 정할 값 | 비용, 기간, 보상 풀, 천장 |

### 4.3 봉인 속성 (아이템을 만들 때 정하는 값)

| 항목 | 추천안 |
|---|---|
| 여는 비용 | 등급별 기본값을 두고 아이템마다 조정한다 |
| 내용물 | 확정 1개와 확률형을 모두 지원한다. 확률형은 확률을 공개한다 |
| 봉인 중 만료 | 멈춘다. 30일 만료는 연 뒤부터 흐른다 |
| 봉인 중 드랍·믹스 | 할 수 없다 |
| 연 뒤의 모습 | 상자형(상자가 사라지고 내용물이 나옴)으로 시작한다. 각성형(같은 일련번호가 열린 모습으로 바뀜)은 나중에 검토한다 |
| 추가 열기 조건(선택) | 에너지에 '결' 조건을 붙일 수 있다(예: 비 오는 날 활동 뒤에만 열리는 상자) |

### 4.4 나의 위치

| 항목 | 추천안 |
|---|---|
| 표현 | 숫자 등급이 아니라 트라이브별 관계 지도. 프로필 칭호는 가장 깊은 관계 두 개로 만든다 |
| 단계 | 관계 단계마다 칭호만이 아니라 플레이가 바뀌는 해금을 준다(예: 원정 가능 → 비용 절감 → 숨은 컬렉션 공개 → 특별 드랍) |
| 소속과 관계 | 소속 트라이브(온보딩에서 고르고 바꿀 수 없음)는 '출신', 관계는 '행보'로 구분한다 |
| 유연성 | 트라이브 수가 바뀌어도 그대로 작동하게 설계한다 |

### 4.5 강화 포인트 (남은 후보)

| 후보 | 내용 |
|---|---|
| 결 조합 기록 | 한 활동에 결이 두 개 겹치면(새벽 + 비 등) 특별한 기록 칸이 열린다. 결이 8개면 조합은 28개다 |
| 관계 단계별 능력 해금 | 4.4 참고 |
| 주간 리듬 상자 | '충분히 움직인 주'를 채우면 받는다. 한 주를 빠져도 잃는 것이 없다 |

### 4.6 비운동형 배지의 모양

생활기록부 비유에서 나온 후보 계열이다.

| 생활기록부 항목 | 배지 계열 | 판정 데이터 |
|---|---|---|
| 출결 | 리듬: 충분히 움직인 주 | 활동 날짜, 주간 에너지 |
| 창의적 체험활동 | 탐험: 처음 가 본 동네, 처음 해 본 움직임 | GPS 경로, 종목 |
| 봉사활동 | 나눔: 내가 놓은 아이템을 누군가 주움 | 드랍·픽업 기록 |
| 행동특성 | 결: 새벽형, 비 오는 날형, 출퇴근형 | 시간대, 날씨, 출퇴근 표시 |
| (복학) | 회복: 쉬었다가 다시 돌아옴 | 활동 공백 |

등급은 노력의 크기가 아니라 지속 기간, 폭, 드문 조합에서 나오게 한다.

### 4.7 연동 소스 확장 (한 번에 하나만)

| 규칙 | 추천안 |
|---|---|
| 소스 전환 | 가능하되 대기 기간을 둔다(예: 30일) |
| 전환 시점 | 전환한 뒤의 활동만 인정한다(지금의 소급 금지 원칙을 연장) |
| 보유 배지 | 전환해도 유지한다 |
| 계정 묶음 | 외부 계정 1개당 JAM 계정 1개 |
| 에너지 계산 | 기기가 준 칼로리는 쓰지 않고 JAM이 직접 계산한다. 칼로리는 기기 알고리즘과 체중에 따라 달라진다 |
| 수동 입력 | 소스마다 '직접 입력' 표시를 확인해 제외한다 |
| 날씨 조건 | 기기 온도 대신 위치·시각으로 조회한 날씨를 쓴다 |
| 일상 데이터 | 걸음 수 같은 데이터는 운동 기록과 다른 '일상 트랙'으로 분리하고 하루 상한을 둔다 |
| 단계 | 구상은 "네이티브 앱이 있다"를 전제로 끝까지 그리고, 웹만으로 가능한 최소안(가민 + 구글 헬스 API)을 비교안으로 남긴다 |

판단: 웹만으로 되는 소스(가민, Fitbit 계열)는 확장 효과가 작고, 확장 효과가 큰 소스(애플워치, 갤럭시워치)는
네이티브 앱이 필요하다. 그래서 이 항목에서 실제로 결정할 것은 "JAM이 앱을 가질 것인가"다.

## 5. 설계 원칙

대화에서 합의한 방향이다.

- **성적표가 아니라 생활기록부.** "얼마나 많이"가 아니라 "어떻게 움직이며 살았는가"를 기록한다.
- **에너지는 성적이 아니라 연료다.** 쌓아서 자랑하는 숫자가 아니라 쓰는 자원이다.
- **자원마다 쓰임새는 하나.** (하데스: 어둠은 거울, 열쇠는 무기, 넥타는 관계)
- **양과 유형을 나눈다.** 에너지는 '얼마나', 결은 '무엇이'를 정한다. (포켓몬 슬립)
- **하지 못한 날을 벌하지 않는다.** 일 단위 연속 대신 주 단위 리듬을 쓴다. (Finch)
- **개인 순위 대신 공동 목표.** (헬다이버즈 2)
- **한 문장 테스트.** 각 층을 한 문장으로 말할 수 있어야 한다.
- **처음에는 핵심만 보이고, 나머지는 필요해지는 순간에 하나씩 열린다.**

## 6. 게임 참고 사례

포인트·마일리지가 아닌 중간 개념으로 보상하는 사례를 일곱 갈래로 정리했다.

| # | 개념 | 대표 사례 | 이 구상에서의 자리 |
|---|---|---|---|
| 1 | 품는 시간 (움직임이 부화 시계) | 포켓몬 GO 알, 피크민 블룸 묘목 | 봉인 속성 아이템 |
| 2 | 결이 결과를 정한다 | 포켓몬 슬립, 네코 아츠메 | 드랍의 트라이브 결정, 봉인 열기 조건 |

## 7. 조사로 확인한 사실

2026-10-06에 명령과 검색으로 확인한 내용이다. 판단은 섞지 않았다.

### 7.1 저장소

- 액티비티 배지 카탈로그(`jam-doc/planning/content/ACTIVITY_BADGES.md`)의 194계열을 조건 문구로 자동 분류하면
  미션 40, 운동형 70, 생활형 84계열이다. 생활형 84계열의 서로 다른 조건은 47가지다.
- Strava의 수영·요가·웨이트 등은 JAM 분류가 `null`이어서 배지 평가와 드랍에서 빠진다
  (`docs/specs/SERVICE_OPERATIONS.md` §16).
- 드랍 엔진에는 활동 맥락(복귀, 극한 기온, 새벽, 심야, 고도, 90분 이상)으로 트라이브를 정하는 맥락 오버라이드가
  있다. 매핑은 `jam-web/src/lib/drop-engine/context.ts`가 원본이다.
- Strava 활동 타입에 `manual`(직접 입력) 필드가 정의돼 있고, `jam-web/src/lib/strava`, `badge-engine`,
  `drop-engine`, `abusing` 폴더에서 이 값으로 활동을 거르는 코드는 검색되지 않았다(확신도 보통).
- `docs/specs/prd/01_PRD.md` §6은 Garmin 연동을 미착수, Apple Health 연동을 범위 밖(네이티브 앱 필요)으로 둔다.

### 7.2 외부 연동

| 소스 | 확인한 내용 |
|---|---|
| 가민 | Connect Developer Program은 승인된 사업자에게 무료이고, 승인은 3~10영업일이다. Activity API는 서버 간 통신이다 |
| 구글 헬스 API | Fitbit Web API를 대체하는 클라우드 REST API이고 Google OAuth 2.0을 쓴다. Fitbit Web API는 2026년 9월 종료 예정으로 안내됐다 |
| 구글 핏 | 2024년 5월 1일부터 신규 개발자 가입을 받지 않고, 2026년 말 서비스 종료 예정이다 |
| Health Connect | 기기 안에서 동작하며 OAuth가 없다 |
| 애플헬스 | HealthKit에는 웹 API가 없고, iOS 앱을 통해서만 읽을 수 있다 |

## 8. 트라이브 재검토 브리프

다음 세션에서 트라이브를 분석할 때 쓰는 기준이다.

### 8.1 목적

현재 트라이브 설정이 새 구조에서 트라이브가 맡게 될 역할을 감당할 수 있는지 진단하고, 유지·수정·통합·신설
여부를 제안한다. 서비스에는 반영하지 않는다.

### 8.2 새 구조가 트라이브에 요구하는 것

| # | 요구 | 확인할 질문 |
|---|---|---|
| 1 | 관계를 맺을 대상 | 우호에서 동맹까지 단계적으로 가까워질 만한 성격과 이야기가 있는가. 단계 이름을 트라이브 말투로 지을 수 있는가 |
| 2 | 원정을 보낼 영역 | 원정의 목적지가 될 장소가 있는가. 각 트라이브의 전설적 목적지(무명 푸드트럭, 블랙 트랙, 그루터기 살롱, 매직 아워 25시, 카본 앨리, 노이즈 캔슬링 0, 오아시스 자판기, 분실물 센터 999, 섬데이, 화이트 룸)가 원정 영역 후보가 될 수 있는가 |
| 3 | 결과의 연결 | 시간대·날씨·계절·복귀·장소 유형 같은 움직임의 맥락과 트라이브가 겹치지 않고 또렷하게 이어지는가 |
| 4 | 종목 중립성 | 지금 설명은 러닝·라이딩 중심 서술이 많다. 요가·수영·웨이트·일상 걷기 유저에게도 자기 이야기로 읽히는가 |
| 5 | 운동형 정서와의 거리 | 속도·장비·한계 돌파처럼 운동 성과를 앞세우는 설정이 '생활기록부' 방향과 부딪히지 않는가 |
| 6 | 봉인 아이템의 서사 | 트라이브 유물, 시즌 상자 같은 봉인 컨텐츠를 만들 이야기 재료가 있는가 |
| 7 | 트라이브 수 | 10개가 관계 지도와 원정 영역으로 다루기에 적절한가. 줄이거나 늘릴 근거가 있는가 |
| 8 | 특수 노드 | 작심삼일 클럽(복귀·결심)과 미스터리 헌터(전역 스파이스)를 새 구조에서 어떻게 다룰 것인가. 미스터리 헌터는 다른 관계가 깊어져야 열리는 숨은 관계 후보다 |
| 9 | 소속과 관계 | 온보딩에서 고르는 소속 트라이브와 에너지로 쌓는 관계가 서로 어떤 의미를 갖는가 |

### 8.3 읽을 자료

- `jam-doc/planning/content/TRIBES.md`: 트라이브 10종, 인접 그래프, 소재·POI 유형 매핑
