> **2026-10-09(KST) 기준 스냅샷이다.** 서브에이전트가 코드를 읽고 DB를 SELECT로만 조회해 정리했다. 3단계(현재 서비스와 비교)의 근거로 쓰고,
> 다른 작업에서 현재 서비스의 근거로 쓸 때는 코드로 다시 확인한다. 안내와 읽는 법은 [기능 지도 안내](<README.md>)에 있다.

# Strava 연동, 동기화, 활동 평가, 어뷰징 필터와 제재

조사 기준: 코드 `staging` 브랜치(2026-10-09), DB는 Supabase `execute_sql` SELECT로 2026-10-09에 확인했다. 시각은 KST로 적는다.

## Strava 연결 (Strava 연동하기)
- **유저 화면**: 홈(`/`)의 왼쪽 상태 카드가 연결이 없으면 `strava_disconnected` 카드로 `/api/strava/auth`를 연다. 온보딩 퀘스트 카드와 상단 내비게이션도 같은 주소로 보낸다. 승인 후 `/profile?strava=connected&reveal=1`로 돌아와 획득 연출을 띄운다. 실패하면 `/profile?strava=error&reason=…`로 돌아온다.
- **어드민**: 없음. 연결 해제 기능도 코드에 없다(`strava_connections` 삭제 경로 없음).
- **규칙과 값**: 권한 범위 `read,activity:read_all`. state는 무작위 256비트 값이고 httpOnly 쿠키(`path=/api/strava`, 수명 600초)와 대조한다. 연결할 유저는 로그인 세션으로 정한다. 토큰은 암호화해 저장하고 `strava_athlete_id` 기준으로 upsert한다. 콜백은 저장 직후 첫 동기화를 await로 실행하고, 동기화가 실패해도 연결은 성공으로 처리한다.
- **데이터**: `strava_connections`(user_id, strava_athlete_id, access_token, refresh_token, token_expires_at, last_synced_at, backfill_completed). DB 연결 수 4건.
- **코드**: `app/api/strava/auth/route.ts`, `app/api/strava/callback/route.ts`, `lib/strava/oauthState.ts`
- **알려진 문제**: `backfill_completed`는 콜백(true)과 어드민 초기화(false)에서 쓰기만 하고 읽는 곳이 없다.

## 활동 동기화 (동기화 버튼, 첫 동기화)
- **유저 화면**: 상단 내비게이션 중앙의 `SyncButton`이 `POST /api/strava/sync`를 부른다. 자동 동기화, 예약 동기화, Strava 웹훅은 없다. 동기화를 부르는 경로는 이 버튼과 연동 콜백 두 곳뿐이다. 온보딩의 `OnboardingSyncButton`은 실제 API를 부르지 않는다.
- **어드민**: 없음.
- **규칙과 값**:
  - 조회 커서는 `strava_activities`의 최신 `start_date`에서 15분(`SYNC_OVERLAP_SECONDS`)을 뺀 값이다. 행이 없으면 `after` 없이 최신 1페이지를 조회한다.
  - 한 번에 가져오는 활동 수는 200건(`ACTIVITIES_PAGE_SIZE`, 1페이지만)이다. 이미 처리한 `strava_id`는 제외한다.
  - 첫 동기화(`users.initial_sync_done=false`)는 가져온 활동 중 최신 1건만 처리하고 저장한다. 날짜가 가입 전이어도 그 1건을 처리한다.
  - 지점 매칭과 교통수단 감지용 경로 조회는 배치 최신 10건(`MAX_POI_MATCH_ACTIVITIES_PER_SYNC`)만 한다.
  - 아이템 배지 드랍 시도는 첫 동기화 1건, 일반 동기화 최신 3건(`MAX_DROP_ACTIVITIES_PER_SYNC`)이고 오래된 순으로 처리한다.
  - 동시 실행은 `last_synced_at` 선점 갱신으로 막고, 처리 중 오류가 나면 이전 값으로 되돌린다.
  - 새 활동이 0건이어도 활동 배지 평가와 가입 경과일 판정은 돈다. 드랍, 미션, 컬렉션 완성 체크는 건너뛴다.
  - 처리 순서: 정규화 → 경로 조회 → 교통수단 구간 재산정 → 지점 체크인 → 차량 속도 필터 → 드랍 → 활동 배지 평가 → 컬렉션 완성 → 미션 → 활동 기록 저장 → 계열 진행 스냅샷 → 하루 동기화 횟수 배지 → JAM! 행동 지표 → 결산 소식.
  - 응답에는 획득 배지 상세를 최대 10장(`EARNED_BADGE_DETAIL_LIMIT`)까지 싣고 나머지는 개수로 준다. API 실행 시간 상한은 60초다.
  - 실패하면 `strava_sync_failures`에 유형(`token_refresh_failed`, `rate_limited`, `strava_api_error`)을 남긴다.
- **데이터**: `strava_activities`(user_id, strava_id, start_date, jam_activity_type, distance_km, normalized jsonb, processed_via), `strava_sync_failures`, `users.initial_sync_done`. DB 활동 605건(sync 588, reconcile 16, manual_backfill 1), 동기화 실패 기록 0건, `initial_sync_done=true` 유저 7명.
- **코드**: `lib/strava/sync.ts`, `lib/strava/api.ts`, `lib/strava/syncFailures.ts`, `app/api/strava/sync/route.ts`, `components/SyncButton.tsx`
- **알려진 문제**:
  - 첫 동기화 1건 제한 때문에 연결 전 활동은 최신 1건 외에는 처리되지도 저장되지도 않는다. 그런데 DB에는 가입 시각 이전 활동이 605건 중 510건 있다. 지금 코드 경로로 이 행이 어떻게 들어왔는지는 확인 못 함.
  - `lib/strava/activity-history.ts` 주석은 "첫 싱크가 저장은 이력 전체를 한다"고 적었지만, 현재 `syncStravaActivities`는 1건으로 자른 뒤 그 1건만 저장한다.
  - 어드민 유저 초기화(`lib/admin/user-actions.ts`)는 주석에 "다음 싱크가 과거 이력 전체를 다시 불러온다"고 적었다. 그러나 초기화는 `strava_activities`를 지우지 않고, 커서는 `strava_activities` 최신 시각을 쓰므로 과거 이력을 다시 가져오지 않는다.
  - `processed_via`의 `reconcile`, `manual_backfill` 값을 쓰는 코드는 현재 `src`와 `scripts`에 없다.
- **문서 어긋남**: SERVICE_OPERATIONS §3-1은 "소급 동기화 없음: 연동 이후 활동만 처리"라고 적었지만, 코드는 첫 동기화에서 날짜와 무관하게 최신 1건을 처리한다.

## 토큰 갱신과 연결 끊김 소식
- **유저 화면**: 토큰 갱신이 실패하면 알림함에 `strava_disconnected` 소식이 생긴다(KST 하루 1건, `mode: 'once'`). 동기화는 실패 응답을 돌려준다.
- **어드민**: 없음.
- **규칙과 값**: 만료 1분 전부터 refresh_token으로 갱신한다. Strava 요청 타임아웃 8초. 레이트리밋 사용량이 90%를 넘으면 서버 로그만 남긴다.
- **데이터**: `strava_connections`, `notifications`(type `strava_disconnected`, DB 0건), `strava_sync_failures`.
- **코드**: `lib/strava/sync.ts`(3단계), `lib/strava/api.ts`(`refreshStravaToken`), `lib/notifications/feed.ts`
- **알려진 문제**: 갱신 실패 후에도 `strava_connections` 행은 남는다. 그래서 홈 카드는 "연결됨"으로 판단한다. 소식의 경고 표시 판정은 `stravaConnected`가 true면 경고가 아니다(`message-href.test.ts` 기준).

## 활동 저장과 종목 매핑
- **유저 화면**: 직접 보이지 않는다. 배지 진행과 활동 기록의 근거가 된다.
- **어드민**: 없음. 매핑은 코드 상수다.
- **규칙과 값**:
  - `sport_type` 우선: TrailRun·TrailRunning→trail_running, Run·VirtualRun→running, Ride·MountainBikeRide·GravelRide·VirtualRide·EBikeRide→cycling, Hike→hiking, Walk→walking. 그 외는 `type` 매핑으로 폴백하고, 없으면 null이다.
  - 가상 활동(VirtualRide, VirtualRun)과 전기자전거(EBikeRide)는 일반 종목과 똑같이 처리된다. Strava의 `manual`, `trainer`, `commute` 칸은 타입에 선언만 있고 판정에 쓰는 코드가 없다. 수동 입력 활동도 같은 경로로 들어간다.
  - GPS 경로가 없는 활동(Streams 404)은 지점 매칭과 교통수단 감지만 건너뛰고 배지 평가, 드랍, 미션에는 들어간다.
  - 종목이 null인 활동은 드랍 대상에서 빠진다. 지점 체크인은 종목을 보지 않는다.
  - Strava 활동 타입(`types/strava.ts`)에는 경로 요약(`map.summary_polyline`), 수동 입력 표시(`manual`), 업로드 번호(`upload_id`, `external_id`)가 선언되어 있다. 테스트 밖의 서비스 코드에서 이 값을 쓰는 곳은 없다(2026-10-09 카리나 확인).
  - 러닝·트레일러닝 케이던스는 저장 시 2배로 바꾼다. 값이 없는 확장 필드는 키를 만들지 않는다.
- **데이터**: `strava_activities.normalized`(distanceKm, movingTimeSec, averageSpeedKmh, maxSpeedKmh, weatherTempC, 심박·파워·케이던스 등). DB 종목 분포: running 428, null 99, trail_running 48, walking 14, cycling 12, hiking 4.
- **코드**: `types/strava.ts`(`getJamActivityType`, `extractExtendedActivityFields`), `lib/strava/sync.ts`(`normalizeActivity`)
- **문서 어긋남**: SERVICE_OPERATIONS §16은 Velomobile을 cycling으로, TrailRun을 running으로 적었다. 코드에는 Velomobile 매핑이 없고 TrailRun은 trail_running이다.

## 교통수단 구간 감지
- **유저 화면**: 없음. 거리·시간이 줄어든 값으로 평가된다.
- **어드민**: `/admin/abusing` 정책 탭에서 걷기·러닝·자전거 임계값과 최소 지속시간을 바꿀 수 있다.
- **규칙과 값**: walking·running·trail_running·cycling만 대상이다. 최고 속도가 종목 임계값을 넘는 활동에서 `velocity_smooth` 구간 평균속도가 임계값을 최소 지속시간 이상 연속으로 넘으면 그 거리·시간을 빼고 평균속도를 다시 계산한다. 임계값: 걷기 20km/h(코드) / DB 20, 러닝·트레일러닝 27 / 27, 자전거 55 / 55, 최소 지속 30초 / 30초. 스트림 조회가 실패하면 원본 그대로 쓴다. 배치 최신 10건만 검사한다.
- **데이터**: `abusing_policy.transit_*`. 재산정 결과는 `strava_activities.normalized`에 저장된다(원래 값은 남지 않는다).
- **코드**: `lib/strava/transitSegment.ts`, `lib/strava/api.ts`(`getActivityStreams`)
- **알려진 문제**: 최신 10건 밖 활동은 검사하지 않는다.

## 차량 속도 필터
- **유저 화면**: 없음.
- **어드민**: `/admin/abusing` 정책 탭 "차량 속도 필터" 값. 저장 API가 20km/h 미만을 400으로 거부한다.
- **규칙과 값**: 기본 60km/h(코드) / DB 60. 통과 조건은 `averageSpeedKmh <= 값`(교통수단 재산정 후 값)이다. DB 값이 0 이하이거나 숫자가 아니면 60으로 폴백한다. 걸러진 활동은 이번 동기화의 드랍 대상, 활동 배지 평가 배치, 미션 배치에서 빠진다. JAM! 행동 지표의 "활동한 날" 판정(`jamActionDayMetrics.ts`)은 저장된 이력에 같은 필터를 다시 적용한다.
- **데이터**: `abusing_policy.vehicle_speed_filter_kmh`. DB에서 평균속도 60km/h 초과 활동은 0건이다.
- **코드**: `lib/strava/sync.ts`(Phase 18 블록), `lib/abusing/policy.ts`(`effectiveVehicleSpeedFilterKmh`, `MIN_VEHICLE_SPEED_FILTER_KMH`), `app/api/admin/abusing/policy/route.ts`
- **알려진 문제**: 걸러진 활동도 `strava_activities`에 저장되고, 배지 엔진과 미션은 그 이력을 다시 읽는다(아래 확인 항목 4). 지점 체크인은 필터 전에 돈다.
- **문서 어긋남**: SERVICE_OPERATIONS §3-2와 §12-1은 걸러진 활동이 배지·미션에서 빠진다고만 적었다. 다음 동기화부터 이력으로 들어가는 점은 적혀 있지 않다. §3-2는 필터(4단계)를 지점 매칭(5~6단계)보다 앞에 두고, 지점 배지를 `user_activity_badges`에 넣는다고 적었다. 코드는 체크인을 먼저 처리하고 체크인 배지를 `user_checkin_badge_earns`에 넣는다.

## GPS 조작 감지
- **유저 화면**: 드랍 줍기(픽업) 때만 검사한다. 감지되면 "위치를 확인할 수 없음" 계열 문구로 거부된다.
- **어드민**: `/admin/abusing` 정책 탭의 GPS 최고 속도, 일일 누적 이동거리 상한.
- **규칙과 값**: 직전 위치 대비 속도 > 300km/h(코드) / DB 300이면 조작이다. UTC 하루 누적 이동거리 > 3000km(코드) / DB 3000이어도 조작이다. 이동 0.15km 미만이거나 경과 5초 미만이면 판정을 건너뛴다. 감지되면 soft 제재(기간 `poi_block_hours`), 그 지점 차단, `abusing_logs` 기록을 함께 건다. 위치는 감지 여부와 무관하게 항상 갱신한다.
- **데이터**: `users.last_location_lat/lng/at`, `gps_daily_distance_km`, `gps_daily_distance_date`.
- **코드**: `lib/abusing/gps-detector.ts`, `app/api/drops/[dropId]/pickup/route.ts`
- **알려진 문제**: 드랍 놓기(`POST /api/drops`)는 GPS 검사를 하지 않는다.
- **문서 어긋남**: SERVICE_OPERATIONS §12-2는 "정상 → 위치 업데이트"라고 적었지만 코드는 감지 때도 갱신한다. §6-2는 사전 검증을 `pickup_drop` RPC 안의 일로 적었지만, 반경·지점 차단·GPS 검사는 라우트에서 하고 RPC 본문에는 `poi_blocks` 참조가 없다.

## 섀도우밴 (유저 제재)
- **유저 화면**: 없음(유저에게 알리지 않는다).
- **어드민**: `/admin/abusing?tab=bans`. 수동 적용(유저 UUID, soft/hard, 사유), 목록 검색·상태 필터(유효/만료/전체), 행별 등급 전환(soft↔hard), 선택 일괄 해제, 선택 일괄 만료 연장(1·3·7·30일). `/admin/users`는 제재 열(등급, "~까지" 또는 "기한 없음") 표시와 제재 필터만 있다. 상세는 확인 항목 5.
- **규칙과 값**: 등급별 허용 배율(아래 정책)로 판정한다. 0이면 차단, 1이면 허용, 그 사이는 확률이다. 적용처: 아이템 배지 드랍(차단 등급은 common으로 강등하고, common도 막히면 취소), 활동 배지, 사용량 배지, 체크인 배지 최초 획득(반복 체크인은 대상 밖). 활동·체크인 배지는 강등 없이 미발급이다. 레벨형(rarity 없음)은 대상 밖이다. `expires_at`이 지나면 제재가 없는 것으로 본다.
- **데이터**: `user_shadow_bans`(id, user_id, ban_level, reason, expires_at, created_at, created_by). DB 0건.
- **코드**: `lib/abusing/shadow-ban.ts`, `lib/abusing/rate-keys.ts`, `app/api/admin/abusing/bans/*`, `app/admin/abusing/BanTable.tsx`, `lib/drop-engine/index.ts`(`applyShadowBanCap`)

## 넘겨받은 확인 항목

1. **차량 속도 필터의 기준 속도**: 코드 기본값 60km/h(`lib/abusing/policy.ts` `DEFAULT_POLICY.vehicle_speed_filter_kmh`), DB 60(`SELECT * FROM abusing_policy`). 통과 조건은 `averageSpeedKmh <= 60`이다. 저장 하한은 20km/h(`MIN_VEHICLE_SPEED_FILTER_KMH`, 정책 저장 API에서 400)다. 소비 시점에 0 이하나 숫자가 아니면 60으로 폴백한다(`effectiveVehicleSpeedFilterKmh`).

2. **abusing_policy DB 실제 값 전체**(id=1, updated_at 2026-08-31 12:48 KST): soft_common_rate 1.00, soft_rare_rate 1.00, soft_epic_rate 1.00, soft_mystic_rate 0.00, hard_common_rate 1.00, hard_rare_rate 0.00, hard_epic_rate 1.00, hard_mystic_rate 0.00, gps_max_speed_kmh 300, gps_daily_distance_cap_km 3000, vehicle_speed_filter_kmh 60, poi_block_hours 72, transit_walk_max_speed_kmh 20, transit_run_max_speed_kmh 27, transit_cycling_max_speed_kmh 55, transit_segment_min_duration_sec 30. 코드 `DEFAULT_POLICY`와 16개 모두 같다. 실효 결과: soft 제재는 Mystic만, hard 제재는 Rare와 Mystic만 막는다.

3. **지점 차단은 픽업만 막는다.** `isPoiBlocked`를 부르는 곳은 `app/api/drops/[dropId]/pickup/route.ts` 한 곳이다. 드랍 놓기 `POST /api/drops`(`app/api/drops/route.ts`)는 지점 차단도 GPS 검사도 하지 않는다. DB 함수 `create_user_drop`, `pickup_drop` 본문에도 `poi_blocks`와 `user_shadow_bans` 참조가 없다(`pg_proc.prosrc` 조회).

4. **걸러진 활동의 저장과 재평가, 체크인 순서**
   - 저장된다. `recordProcessedActivities(supabase, userId, activities, …)`는 필터 전 배열 `activities`를 `strava_activities`에 저장한다(`lib/strava/sync.ts`, `processFetchedActivities` 끝부분). 필터 결과 `activitiesFiltered`는 저장에 쓰이지 않는다.
   - 다음 평가에 다시 들어간다. 이번 동기화의 `evaluateBadges(userId, activitiesFiltered)`는 저장 전에 돌아서 이번 배치의 걸러진 활동을 보지 않는다. 그러나 `evaluateBadgesDetailed`는 `getActivityHistory`(가입 시각 이후 `strava_activities` 전체)를 읽고, 차량 속도 필터를 다시 적용하지 않는다(`lib/badge-engine/index.ts`, `activityFilters.ts`에 해당 필터 없음). 그래서 다음 동기화부터 누적 조건 이력에 포함된다. `checkMissions`도 `getActivityHistory`로 이력을 합친다(`lib/missions/checker.ts` 124행). 예외로 JAM! 행동 지표의 활동일 판정은 필터를 다시 적용한다. 드랍 엔진 내부가 이력을 다시 읽는지는 확인 못 함. 현재 DB에는 평균속도 60km/h 초과 활동이 0건이라 실제 영향은 아직 없다.
   - 지점 체크인이 필터보다 먼저 돈다. 체크인 루프는 `routesByActivity`(배치 최신 10건, 필터 전)로 돌고, 필터(`activitiesFiltered`)는 그 뒤에 만들어진다. 체크인은 종목(null 여부)도 보지 않는다.

5. **어드민 제재 걸기·풀기·끝나는 날**
   - 걸기: 가능하다. `/admin/abusing?tab=bans` "수동 섀도우밴 적용"에서 유저 UUID, soft/hard, 사유를 넣는다. 화면에 끝나는 날 입력이 없어 영구 제재(`expires_at` null)가 된다. `POST /api/admin/abusing/bans`는 `expires_at`을 받지만 화면(`AbusingClient.tsx` `addBan`)이 보내지 않는다.
   - 풀기: 가능하다. 목록에서 선택해 일괄 해제하면 행을 지우고 `abusing_logs`에 `ban_released`를 남긴다(`releaseBans`).
   - 끝나는 날: 기한이 있는 제재(GPS 자동 제재 등)만 "만료 연장"으로 지금부터 1·3·7·30일 뒤로 늦출 수 있다(API는 1~365일). 영구 제재는 연장 대상에서 빠지므로(`summarizeBanExtend`, `extendBans`의 `.lt('expires_at')`) 영구 제재에 끝나는 날을 정하는 화면 경로는 없다. 기한을 앞당기는 기능도 없다.
   - 등급 전환(soft↔hard)은 행별로 가능하고 기한은 유지된다(`PATCH /bans/[id]`).
   - `/admin/users`와 유저 상세(`/admin/users/[id]`)에는 제재를 걸거나 푸는 버튼이 없다. 목록의 제재 열 표시와 제재 필터만 있다.
